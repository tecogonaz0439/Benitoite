1. **重さ: 高**
   - **場所:** `formal/Benitoite/Release/Assumptions.lean:50`（`admits_sat`。同ファイルの `store_admits`・`ref_get` と組み合わせた場合）
   - **問題:** `Builtins.Assumptions` が充足不能になっている。そのため、この仮定を受け取る四つの定理は、対象となる組み込みの関数の集まりが存在しないまま成立している。

     `ref_get` により、`B.sig B.refGet = some s` かつ `s.kind = .refGet` となる `s` が存在する。`store_shape` から、この `s` の型パラメータの個数は 1 である。一方、`store_admits` は型引数の個数に前提を置かず、すべての `ts` について `s.admits C ts` を要求する。したがって、`C = []`・`ts = []` にも適用できる。

     ここに追加した `admits_sat` を適用すると、`SatAll B [] [] s.tparams` が得られる。`SatAll` は個数の一致を含むため、`0 = s.tparams.length = 1` となり、矛盾する。証明本体が Lean の検査を通ることや、使用公理の一覧からは、この矛盾は排除されない。
   - **原因の分類:** その他（仮定どうしの矛盾）
   - **直し方の案:** `store_admits` に `ts.length = s.ntys` の前提を加える。ストアの操作が「制約を要求しない」ことと、「個数の違う型引数も受け入れる」ことを区別する必要がある。修正後は、具体的な `Builtins` について `Builtins.Assumptions` を満たす例を構成し、仮定の充足可能性も確認する。

2. **重さ: 高**
   - **場所:** `formal/Benitoite/Release/WellFormed.lean:33`（`Ty.VarsIn` の `.cont`）、01-12「ハンドラ」の型構文・V-Lam
   - **問題:** 継続の型を項に書けないとする変更には、提示された 01-12 に明確な根拠がない。現状の規則を文字どおり読むと、形式化が除外する項に 01-12 では型が付く。

     例えば、次の項である。

     ```text
     return λ(x:Cont(Unit → Unit ! { })). return ()
     ```

     01-12 の型構文は `A ::= … | Cont(B → A ! ε)` を含む。V-Lam では、使わない引数 `x` にこの型を与えても、本体の `return ()` に型が付く。この項は継続の値を返したり渡したりせず、`resume` も使わないので、「継続の型の値は `resume` の第一引数にだけ書ける」という制限にも抵触しない。

     しかし、変更後の `Ty.VarsIn` はラムダの引数の型にある `.cont` を拒否するため、この項は `ClosedNoEffVars` を満たさず、`effect_soundness` の対象から外れる。`StateTy` も同じ理由で初期状態を除外する。「値として書けるのは節の中だけ」は継続の値の使用箇所の制限であり、型注釈への継続の型の記載禁止までは導かない。
   - **原因の分類:** 書き写しの誤り（現行の 01-12 にない構文上の制限を追加している）
   - **直し方の案:** 継続の型を項に書けない設計を採るなら、ADR を添え、01-12 で「項の型注釈と型引数に使える型」と「型付け判断の内部で使う継続の型」を区別する。前者は、内部にも `Cont` を含まないことを明記する。その規範上の変更に合わせて、現在の `Ty.VarsIn` を維持する。現行の型構文を維持するなら、`.cont` を一律に拒否する変更を戻す必要がある。

3. **重さ: 低**

   - **問題:** 変更後の仮定と、07-04 の仮定の表が一致していない。

     表は依然として「並びの先頭」を置き換えると説明しているが、現在の `admits_subst`・`sat_subst` が置き換えるのは、`C1 ++ C0` の外側の部分 `C0` である。また、表の「型の変数を含まない型が制約を満たすかは、制約の並びによらない」に対し、`sat_local`・`admits_local` は、内側の `C1` だけを使う型について、外側に `C0` を追加しても制約を満たすという片方向の性質を要求する。閉じた型だけに限らない一方、任意の環境間の同値を直接要求するものでもない。

   - **原因の分類:** その他（仮定の説明の更新漏れ）
   - **直し方の案:** 表の該当行を、次の三つに分けて記す。
     - 内側の束縛 `C1` を残し、外側の `C0` を制約を満たす閉じた型で置き換えたときの制約の保存。
     - `C1` だけを使う型について、外側への制約環境の追加による制約の保存。
     - 組み込みの関数の制約全体から、宣言された型パラメータの組み込みの制約への含意。

     これらの仮定の内容自体は、指摘 1 の矛盾を解消したうえで、B1 の置き換えに必要な性質として妥当である。

4. **重さ: 低**
   - **場所:** 01-12・K-Handle と、その後の `releases(K')` の型付けを説明する箇条
   - **問題:** ADR 0302 による規則の変更後も、説明に旧規則の等式が残っている。

     「継続の枠が先頭で許すエフェクトは、下の枠のものに K-Handle が `handled(H)` を加えたもの」は、新しい規則では成り立たない。下の枠が許すのは `ε`、上で許すのは `εc ∪ handled(H)` であり、前提は `εc ⊆ ε` である。

     同じ箇条の「E-Op が積む `drop κ` の枠では、ε' は……`drop` の枠の位置のエフェクトと等しい」も、新しい K-Handle では等しいとは限らない。捕まえた継続の型のエフェクトは `εc`、`drop` の下の継続が許すエフェクトは `ε` となり、包含関係で足りる。
   - **原因の分類:** その他（規則変更に伴う説明の更新漏れ）
   - **直し方の案:** `State` の下向きの保存を包含関係で説明する。すなわち、`State ∈ εc ∪ handled(H)` なら、`State` は `handled(H)` に含まれないので `State ∈ εc`、さらに `εc ⊆ ε` から `State ∈ ε` となる。E-Op が積む K-Drop の前提も、この包含関係により成り立つと書く。

- **問題なし — 変更 1:** `Ty.shift`・`Ty.substAt` は番号の繰り上げ、捕獲を避けた置き換え、束縛の除去後の番号の繰り下げを正しく表している。節の下で切れ目を `c + k` にすること、`sg.tparams ++ C`、`shiftEnv k Γ`、`t.shift k 0`、`R.map (Ty.shift k 0)` は、操作の型パラメータを新しい内側の束縛として扱うことに一致する。E-Op の `c.body.substTy ts []` はその束縛を除去するため、θ = `[T̄/ᾱ]` に一致する。
- **問題なし — 変更 2:** 型付け判断に現れる型は、その判断で有効な型パラメータだけを使うという通常の束縛の解釈のもとでは、追加した `Ty.WF` は 01-12 の暗黙の前提を明示したものである。Ψ の型を閉じた型に限ることも、実行状態には型パラメータの環境を持たせない解釈に一致する。
- **問題なし — ADR 0301 の規則:** `A ≤ A'` の値を、`A'` を受け取る継続へ渡せるという K-Sub の向きは正しい。R・エフェクト・結果の型を変えず、受け取る値の包含だけを許すため、修正は過剰ではない。
- **問題なし — ADR 0302 の規則:** 節のエフェクト `εc` が下の継続の許す `ε` に含まれる条件は、節の実行と捕まえた継続の再接続に十分である。`εc = ε` とすれば旧規則を含み、上で許すエフェクトを `εc ∪ handled(H)` とすることにも不整合はない。
- **問題なし — 変更 6 と定理の結論:** 使用しない前提の削除は定理を強める変更である。`UnhandledOp` の移動は意味を変えない。進行・保存の結論は初回リリース版の性質 2 に対応し、エフェクトの健全性の結論は解放の事象も禁止する分だけ性質 3 より強い。ただし、四つの定理の仮定には指摘 1、扱う項の範囲には指摘 2 の問題がある。
