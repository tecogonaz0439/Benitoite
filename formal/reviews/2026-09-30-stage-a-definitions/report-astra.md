### 1. エフェクト集合に有限性の条件がない

- **重さ:** 高
- **場所:** [Syntax.lean:25](/Users/tecogonaz/src/Benitoite/formal/Benitoite/Core/Syntax.lean:25)、[Typing.lean:153](/Users/tecogonaz/src/Benitoite/formal/Benitoite/Core/Typing.lean:153)。01-12「構文」の `ε ::= { e1, …, en }`。
- **問題:** 01-12 はエフェクトを有限集合としているが、`Eff := Atom → Bool` は無限集合も許す。例えば、次の集合を関数の型や C-Sub の拡大先に使える。

  ```lean
  fun a => match a with
    | .io => false
    | .rho _ => true
  ```

  `Def.Scoped` と `PrimSig.Scoped` は宣言内の番号を有限の範囲に制限するため、その範囲では有限性も確保できる。しかし、`HasTypeV`・`HasTypeC`・`StateTy` には同じ制限がなく、`progress` と `preservation` の対象には、無限のエフェクト集合を型注釈に持つラムダなども含まれる。

  これは主要定理の反例ではないが、07-04 が説明している「並びの違いを持ち込まないための表現の違い」を超えて、構文の範囲を広げている。
- **原因の分類:** 表現の都合
- **直し方の案:** `Eff` 自体に有限性を持たせるか、構文と型付けに有限性の条件を組み込む。現在の関数表現を残すなら、「ある番号以上の `rho` はすべて `false`」という条件でも段階 A の有限性を表せる。定理の前提にだけ条件を追加する場合は、型付け規則そのものは広い範囲を許すことと、01-12 に対応する範囲を 07-04 に明記する必要がある。

### 2. 関数呼び出しの遷移が、引数個数の不一致を許す

- **重さ:** 高
- **場所:** [Semantics.lean:44](/Users/tecogonaz/src/Benitoite/formal/Benitoite/Core/Semantics.lean:44)、同ファイル 46–49 行・83–86 行。01-12 の E-Lam・E-Fun。
- **問題:** `E_Lam` に `ws.length = ps.length` がなく、`E_Fun` にも値・型・エフェクトの各引数の個数を確認する条件がない。01-12 の `M[W̄/x̄]` は、束縛変数と渡す値が対応する置き換えである。

  例えば、Lean の `Step` では次の遷移が成立する。

  ```text
  ⟨(λ(x:Integer). return x)(), []⟩
      → ⟨return var 0, []⟩
  ```

  `instantiate []` が自由な番号をそのまま残すためである。逆に、引数を余分に渡すと、ラムダが束縛していない外側の変数まで置き換えうる。

  `HasTypeVs` が個数を揃えるので、これは型が付いた状態からの `preservation` の反例にはならない。しかし、`Step` と `step` が書き写している遷移関係は、01-12 より広い。
- **原因の分類:** 書き写しの誤り
- **直し方の案:** `E_Lam` に値引数の個数の一致を、`E_Fun` に値・型・エフェクト引数の個数の一致を加え、`step` にも対応する検査を入れる。型が付いた項についてだけ実行規則の対応を主張する方針なら、その限定を 07-04 に記し、`step` と `Step` の一致とは別に管理する。

### 3. `step_sound` の oracle 条件が、未登録の関数名にも応答を要求する

- **重さ:** 中
- **場所:** [Theorems.lean:21](/Users/tecogonaz/src/Benitoite/formal/Benitoite/Core/Theorems.lean:21)
- **問題:** `horacle` は次を要求する。

  ```lean
  ∀ b ws, B.ioResponse b ws (oracle b ws)
  ```

  この条件は、IO を行わない関数や、`B.sig b = none` となる名前にも適用される。ところが `Builtins.Assumptions.io_exists` が応答の存在を保証するのは、登録された IO 関数だけである。したがって、07-04 の仮定から、この oracle 条件を満たせることは導けない。

  提示された `Examples.builtins` では、`"add"` や未登録の名前に対する `ioResponse` が常に `False` なので、**どの oracle でも `horacle` を満たせない**。定理自体は偽ではないが、IO を伴わない実行例にすら適用できない。
- **原因の分類:** その他（定理の前提が強すぎる）
- **直し方の案:** 少なくとも条件を次の範囲に限定する。

  ```lean
  ∀ b s ws, B.sig b = some s → s.io = true →
    B.ioResponse b ws (oracle b ws)
  ```

  後述の `io_exists` も型の付いた引数に限定するなら、`step_sound` 側も、その一歩で実際に問い合わせる IO 呼び出しについてだけ応答の妥当性を要求する形が適している。

### 4. `io_exists` が、型も個数も合わない引数への応答まで要求する

- **重さ:** 中
- **場所:** [Assumptions.lean:38](/Users/tecogonaz/src/Benitoite/formal/Benitoite/Core/Assumptions.lean:38)、[Examples.lean:36](/Users/tecogonaz/src/Benitoite/formal/Benitoite/Core/Examples.lean:36)
- **問題:** `io_exists` は、IO 関数であれば任意の `ws : List Val` に対して応答を要求する。引数の個数や型が間違っていても、自由な項変数を含んでいても対象になる。

  この強さは、型が付いた状態の進行を証明するためには不要である。また、提示された例では、`print` の応答を引数が一つの場合にだけ定義しているため、`b = "print"`、`ws = []` とすれば `io_exists` を満たせない。

  07-04 の「IO の応答の存在」という仮定の項目には対応しているが、引数についての量化範囲が説明されておらず、現在の定義では `delta_typed` より強い全域性を要求している。
- **原因の分類:** その他（仮定の量化範囲が過大）
- **直し方の案:** `io_typed` と同様に、型・エフェクト引数の個数、制約、`HasTypeVs` を前提に加え、型が付いた呼び出しへの応答の存在を要求する。07-04 の表にも「型が付いた引数に対して」と明記する。

### 5. 現在の保存定理だけでは、複数ステップのエフェクト健全性を導けない

- **重さ:** 中
- **場所:** [Semantics.lean:124](/Users/tecogonaz/src/Benitoite/formal/Benitoite/Core/Semantics.lean:124)、同ファイル 131 行、[Theorems.lean:45](/Users/tecogonaz/src/Benitoite/formal/Benitoite/Core/Theorems.lean:45)・55 行。01-12 の K-Let・性質 3。
- **問題:** `StateTy` は型とエフェクトを存在量化し、`ContTy` は各枠のエフェクトを記録しない。そのため `preservation` の結論からは、遷移後も実行中の計算と継続が純粋であるとは分からない。

  例えば、`StateTy` は「現在は `return ()` だが、次の `let` の枠で IO を行う状態」にも成立する。純粋な初期計算からその状態へ到達しないことは、別の不変条件で示す必要がある。

  現在の言明は 01-12 の性質 2 を正しく写している。問題は、性質 3 の証明と段階 B の拡張に必要な情報が、この補助関係にはないことである。
- **原因の分類:** 表現の都合
- **直し方の案:** 公開する性質 2 の言明は維持しつつ、実行中の計算と全継続枠に許すエフェクトを記録する補助的な状態型付けを定義し、その保存を証明する。これは新しい仮定にせず、型付け規則から証明する補題にする。

  段階 B では、資料にあるとおり継続の入口と出口のエフェクトを区別し、ストアの型付けと整合させる必要がある。一度だけ再開できる継続についても、項の型付けを別の関係にする方針は維持できるが、継続の使用済み状態を含むストアの不変条件が必要になる。de Bruijn の番号だけでは、この使用回数の条件は表せない。

### 6. 固定された oracle では、同じ呼び出しへの応答が途中で変わる実行を表せない

- **重さ:** 中
- **場所:** [Semantics.lean:112](/Users/tecogonaz/src/Benitoite/formal/Benitoite/Core/Semantics.lean:112)、[Theorems.lean:28](/Users/tecogonaz/src/Benitoite/formal/Benitoite/Core/Theorems.lean:28)
- **問題:** `run` は、全ステップで同じ純粋関数

  ```lean
  PrimName → List Val → Outcome
  ```

  を使う。このため、同じ名前・同じ引数の IO 呼び出しは、必ず同じ応答になる。`Step` が許す応答に二つの値があれば、同じ呼び出しが一回目と二回目で異なる値を返す遷移列を組み立てられるが、一つの oracle による `run` では再現できない。

  `step_complete` は一歩だけを対象とするので、この理由では偽にならない。ただし、その定理から `run` と遷移列全体の一致へは拡張できない。
- **原因の分類:** 表現の都合
- **直し方の案:** `run` で一般の IO の列を扱うなら、oracle に状態を持たせて更新後の状態も返すか、呼び出しごとに応答の列を消費する形にする。現状を維持するなら、`run` は同じ入力への応答を固定した実行例を調べる道具であり、完全性の主張は一歩に限ることを明記する。

### 7. `Exhaustive` は「型 A の値すべて」より広い集合について量化している

- **重さ:** 低
- **場所:** [Typing.lean:87](/Users/tecogonaz/src/Benitoite/formal/Benitoite/Core/Typing.lean:87)・110 行、07-04「01-12 との対応」の型付け規則の行
- **問題:** `Inhabits` は `HasTypeV P B [] v a` と同じ集合を表していない。

  - 関数型と型パラメータでは、定数や自由変数を含む任意の `Val` を許す。
  - 構成子値の型引数 `tys'` を、判定対象の型の引数 `ts` と一致させない。

  したがって `Exhaustive` は、型が付いた閉じた値の集合を広げた、値の形の集合に対する条件である。コード内の説明はこの意図を述べているが、07-04 の「型 A のどの値にも照合する分岐がある」という説明では、両者の違いが分からない。

  この拡大が進行を弱めることはない。型が付いた値が `Inhabits` を満たせば、進行に必要な網羅性を導ける。
- **原因の分類:** 表現の都合
- **直し方の案:** 07-04 に、型が付いた値を含む「値の形」の集合に対して網羅性を要求することを記す。証明では、少なくとも次を補題として明示する。

  1. 型が付いた閉じた値は `Inhabits` を満たす。
  2. 型・エフェクトの置き換えで網羅性が保たれる。
  3. 項の置き換えで網羅性の前提が維持される。

  特に 2 は E-Fun の保存で必要になる。`tvar` を任意の値として扱う現在の定義は、型パラメータを具体化した後の値も対象に含めるための選択として説明できる。

## 問題なしと判断した観点

- **主要定理の言明:** 問題なし。`progress`・`preservation` は資料にある性質 2 と一致し、`effect_soundness` は到達可能な任意の状態からの IO 遷移を禁止することで、性質 3 の「実行全体で IO がない」を表している。
- **項の de Bruijn 表現と置き換え:** 問題なし。引数と束縛型の反転、パターンの束縛値の連結順、束縛を越える `upRen`・`upSubst` は対応しており、提示範囲では変数捕獲や順序の誤りは見つからなかった。
- **型の包含と計算結果の包含:** 問題なし。`Ty.Le` は最外側の関数型のエフェクトだけを広げ、V-Sub・C-Sub は資料の規則に対応している。
- **パターンと分岐の選択:** 問題なし。P-Const の制限、構成子の照合、束縛順、最初に照合する分岐の選択は、型が付いた項について資料の規則に対応している。
- **残りの組み込み仮定とプログラムの前提:** 問題なし。`sig_scoped`・`admits_subst`・`delta_typed`・`io_typed`・`io_effect`、および `P.WellTyped`・`P.WellFormed` は、資料 2 の仮定と前提に対応している。構成子宣言が自由なエフェクト変数を持たない条件も、その宣言にエフェクト変数の束縛がないことと整合する。
- **型付けを項と別の関係にする選択:** 問題なし。段階 B でも維持できる。ストアと継続について必要になる条件は、項の構文に埋め込まず、状態の型付けとその不変条件として追加できる。
