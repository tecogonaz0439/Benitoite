1. **エフェクト集合に有限性の条件がない**

   - **重さ:** 高（01-12 と意味が違う）
   - **場所:** `formal/Benitoite/Core/Syntax.lean` 25–26 行、`formal/Benitoite/Core/Typing.lean` 135–136 行・153–154 行
   - **問題:** 01-12 のエフェクトは有限集合であるが、`Eff := Atom → Bool` は無限集合も含む。例えば `fun _ => true` は、`IO` とすべての `rho i` を含む。この集合を V-Sub や C-Sub の包含先に使えるため、Lean では 01-12 に存在しない型付けも導出できる。

     `Def.Scoped` と `PrimSig.Scoped` によって、宣言中のエフェクト集合は有限個の変数に制限される。しかし、任意の項の型引数・エフェクト引数や、型付け規則で選ぶ包含先には同じ制限がない。したがって、プログラムの `WellFormed` だけではこの差を解消できない。この差から、提示された三つの性質の反例が直ちに生じるわけではない。
   - **原因の分類:** 表現の都合。集合を関数で表すこと自体は妥当であるが、元の構文の有限性が失われている。
   - **直し方の案:** 有限性の証拠を持つ集合、または `Finset Atom` を使う。関数による表現を保つ場合は、有限台を持つことを `Eff` 自体の条件にする。定理の前提にだけ有限性を足す方法では、型付け規則全体と 01-12 の差が残る。

2. **関数の遷移規則が、束縛変数と実引数の個数が違う場合にも適用できる**

   - **重さ:** 高（01-12 と意味が違う）
   - **場所:** `formal/Benitoite/Core/Semantics.lean` 44–49 行・83–86 行、01-12 の E-Lam・E-Fun
   - **問題:** `Step.E_Lam` に `ws.length = ps.length` の条件がない。例えば、次の状態から遷移できる。

     ```lean
     .run (.app (.lam [intTy] (.ret (.var 0))) []) []
     ```

     この遷移では束縛変数が置き換わらず、遷移先は `.run (.ret (.var 0)) []` になる。01-12 の `M[W̄/x̄]` は、束縛した各変数に対応する実引数による置き換えであり、個数の違う並びによるこの動作を定めていない。

     E-Fun も、実引数、型引数、エフェクト引数の個数を確認せず、足りない型変数などを残したまま遷移する。型が付いた呼び出しでは V-Fun・V-Lam・C-App が必要な個数を保証するため、これは `progress` や `preservation` の反例ではない。問題は、型付けを前提としない `Step` と `step` の意味が広がっていることである。
   - **原因の分類:** 書き写しの誤り。並びどうしの対応という暗黙の条件を、独立したリストに移す際に落としている。
   - **直し方の案:** E-Lam に実引数の個数の一致、E-Fun に実引数・型引数・エフェクト引数の個数の一致を加え、`step` も同じ条件で分岐させる。遷移関係を型が付いた項だけについて対応させる方針を採る場合は、07-04 の「表現の違い」にその対象範囲を明記する必要がある。

3. **IO の存在仮定と `oracle` の前提が、使用しない入力にまで応答を要求する**

   - **重さ:** 中（前提が強すぎ、提示された例に適用できない）
   - **場所:** `formal/Benitoite/Core/Assumptions.lean` 40 行、`formal/Benitoite/Core/Theorems.lean` 21–24 行、`formal/Benitoite/Core/Examples.lean` 36–38 行
   - **問題:** `io_exists` は、IO の組み込みに対して、型も個数も問わずすべての `ws` に応答を要求する。提示された例では `ioResponse "print" [] o` はすべての `o` について偽であるため、例の `builtins` は `Builtins.Assumptions` を満たせない。進行の証明に必要なのは、型が付いた実引数に対する応答の存在である。

     `step_sound` の `horacle` はさらに強く、IO を行わない組み込みや、存在しない組み込みの名前にも応答を要求する。例では `ioResponse "add" ws o` が常に偽なので、どの `oracle` もこの前提を満たせない。`step_sound` の言明自体を偽にする問題ではないが、適用に必要な前提が成立しない。

     `io_exists` は 07-04 に列挙された種類の仮定ではある。しかし、その適用範囲は進行に必要な範囲を超えている。`horacle` は実行器と関係を比較するための条件であり、言語の性質に関する追加仮定とは区別して記すべきである。
   - **原因の分類:** その他（仮定と定理の前提の適用範囲）
   - **直し方の案:** `io_exists` に、V-Prim のインスタンス化条件と `HasTypeVs` の条件を加える。`step_sound` を任意の状態について保つなら、`horacle` を少なくとも「存在する、IO を行う組み込み」に限定する。その場合、不正な引数についても関係との一致を求めるかを決める必要がある。型が付いた状態についての健全性と、任意の状態についての対応を別に言明する方法もある。

4. **多相の組み込みが型引数付きの構成子を返す場合、δ のインターフェースが型の保存と両立しない**

   - **重さ:** 中（該当する組み込みを扱うと、仮定を満たせなくなる）
   - **場所:** `formal/Benitoite/Core/Typing.lean` 48 行、`formal/Benitoite/Core/Assumptions.lean` 28–31 行、01-12 の E-Prim
   - **問題:** δ は組み込みの名前と実引数だけを受け取るが、返す値の構成子には型引数が含まれる。この組合せでは、同じ実引数に対する結果を異なる型でインスタンス化できない場合がある。

     例えば、次の型を持ち、空リストに対して `None[α]()` を返す組み込みを考える。

     ```text
     b[α](xs: List[α]) : Option[α] ! {}
     ```

     実引数の `.list []` は `List[Integer]` と `List[Boolean]` の両方の型を持つ。ところが `delta b [.list []]` の結果は一つに決まり、返す `.con "None" ts []` の `ts` も固定される。その値に `Option[Integer]` と `Option[Boolean]` の両方の型を付けることは、現在の V-Con と V-Sub ではできない。したがって、この振る舞いを持つ δ は `delta_typed` を満たせない。

     提示資料には実際の組み込み一覧がないため、段階 A の既存の組み込みがこの問題に該当するとは断定しない。また、これは三つの定理の反例ではなく、意図した組み込みに仮定を適用できないという問題である。
   - **原因の分類:** 01-12 の規則の誤り。01-12 自体が、型引数付きの構成子値と、型引数を受け取らない δ を組み合わせている。
   - **直し方の案:** 該当する組み込みがあるかを確認したうえで、δ に型引数・エフェクト引数を渡す、δ の結果にインスタンス化を施す、または実行時の値から型引数を消す方式を選ぶ。01-12 の変更を伴うため、ADR を添えて規則を直してから Lean を合わせる。

5. **固定された `oracle` では、同じ操作への応答が実行中に変わる実行を再現できない**

   - **重さ:** 中（実行例と段階 B の拡張で制約になる）
   - **場所:** `formal/Benitoite/Core/Semantics.lean` 77 行・112–119 行、`formal/Benitoite/Core/Theorems.lean` 28–31 行
   - **問題:** `run` は実行全体で同じ `oracle : PrimName → List Val → Outcome` を使うため、同じ組み込みに同じ実引数を渡すと、必ず同じ応答を得る。`Step` は各遷移で `ioResponse` を満たす応答を選べるため、同じ操作に異なる応答が返る遷移列も許す。

     `step_complete` は一歩についての言明なので、この違いによって偽にはならない。ただし、「一歩の対応」から「任意の実行を `run` で再現できること」は導けない。段階 B でリソースの状態や継続の再開済み状態を扱う際も、固定された応答関数だけでは状態の変化を表せない。
   - **原因の分類:** 表現の都合。
   - **直し方の案:** 現段階では `run` が固定した応答を使う実行例の道具であることを明記する。応答の変化を含む実行を扱う際は、応答列、履歴、または外部状態を受け取り、更新後の状態も返す `oracle` に拡張する。段階 B のストアが管理する状態と、外部の応答を選ぶ状態との役割も分けて定める。

6. **型付け規則の構成子名が、07-04 の命名規約に揃っていない**

   - **重さ:** 低（表記・対応管理）
   - **場所:** `formal/Benitoite/Core/Typing.lean` 67–81 行・117–175 行、07-04「01-12 との対応」
   - **問題:** 07-04 は Lean の定義名を規則名に対応させると定めているが、型付け規則は `PatTy.wild`、`HasTypeV.fnRef`、`HasTypeC.ret` などになっている。`Step.E_Let` や `ContTy.K_Let` と対応の付け方が異なり、例えば `HasTypeC.sub` が C-Sub に当たることを名前だけから直接確認できない。
   - **原因の分類:** その他（命名規約との不一致）
   - **直し方の案:** `P_Wild`、`V_Fun`、`C_Return`、`C_Sub` などに揃えるか、名前空間と構成子名による対応も許すことを07-04 に明記する。

定理の言明と性質 2・3 の対応：問題なし。`preservation` が結果の型の一致まで述べず、遷移先に何らかの状態の型付けがあることを述べる点も、提示された01-12 の性質 2 と一致している。

型が付いた状態からの具体的な反例：問題なし。提示された定義と仮定のもとで、`progress`・`preservation`・`effect_soundness` を偽にする反例は見つからなかった。上記の不正な個数の呼び出しは型が付かず、δ の問題は仮定を満たせない場合の問題である。

de Bruijn の番号と項の置き換え：問題なし。引数・パターン束縛を左から並べ、型環境と置き換えでは最後の束縛を番号 0 にする対応は一致している。`upRen`・`upSubst` は、ラムダ、`let`、各分岐の束縛を考慮している。

意味による網羅性：問題なし。07-04 に明記された表現の違いの範囲である。`Inhabits` が関数型と型変数で任意の値を許し、構成子値の型注釈を無視する点は、値の集合を広く取る方向であり、それだけで進行を弱めない。ただし、証明には、閉じた値の型付けから `Inhabits` を導く補題に加え、型とエフェクトの置き換えによる網羅性の保存が必要である。

型付けを項と別の関係にする表現：問題なし。段階 B でも使用できる。ただし、一度だけ再開できる継続については、項の変数の扱いだけで使用回数を保証できるわけではなく、予定するストアの状態と継続・状態の型付けを合わせて定める必要がある。

仮定の種類とプログラムの前提：問題なし。`Builtins.Assumptions` の六つの欄と `WellTyped`・`WellFormed` は、07-04 に列挙された種類に対応している。`ConDecl.Scoped` がエフェクト変数を禁止する点も、構成子の宣言にはそれを束縛する宣言がないことと整合する。仮定の適用範囲に関する問題は指摘3のとおりである。
