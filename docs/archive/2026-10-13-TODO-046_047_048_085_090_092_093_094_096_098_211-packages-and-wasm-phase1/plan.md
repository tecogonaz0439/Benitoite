# 実装プラン

作業は直列に進める。どの作業も、メインの作業ディレクトリで作業ごとのブランチ（`mod/<作業>`）の上で Codex（GPT-6.1-Sol、high）が実装し、終えたらすぐ `san_benito` に取り込む。作業を渡す前に、作業の文書を Opus のサブエージェントが点検する（事前点検）。点検の補足は作業の指示に加えて渡す（W1〜W3 は `reviews/preflight-W1W3.md`）。レビュー（Opus）は取り込んだコミットを `git show` で読み、直しは後のコミットで行う。作業ごとには関係するテスト・clippy・fmt だけを走らせ、`scripts/check.sh` は最後に一度だけ行う。

各作業の根拠は `decisions.md`（Q1〜Q8、R1〜R15）と `study/` の調査である。調査と `decisions.md` が違うときは、`decisions.md` を正とする。到達点の例は `study/package-samples/`（`proposed/` は提案の構文で書いた形。この改造の構文は `decisions.md` に従い、`project` のブロックをやめ `package.bnt` にするなど、例と違う点がある）。

## 到達点

スクリプトが手元のパスの Benitoite のパッケージを依存として取り込み、そのパッケージが同梱した純粋な WASM のコンポーネントの関数を `@external` で呼べる（形 2。例の Fuzzy）。形 1（Benitoite だけのパッケージ。例の Textkit・Todo）と形 3（根の下のコンポーネントを入口のファイルや根のモジュールから直接呼ぶ）も、同じ仕組みで動く。依存の記述は入口のファイルの先頭か `package.bnt` に書け、言語の版の宣言を照合し、`benitoite package add`・`update`・`move` で記述を書き換えられる。

## どの作業にも共通する決まり

- 診断の文言は `diag::codes` の表（型板）と、各モジュールの `text` にまとめる（AGENTS.md「文言」）。新しい診断コードは、既存の区分の空いた番号を使う（調査 A 8 節。パッケージと設定ファイルの誤りは新しい区分にしてよい。区分を決めたら 02-10 の表に書く）。
- 診断の文言・コード・修正案を変えたら、同じ作業で次を行う。
  - 影響するゴールデンを `BENITOITE_BLESS=1 cargo test -p benitoite --test golden` で作り直し、差分が意図したものだけであることを確かめて報告に書く。
  - `cargo run -p benitoite --example gen_skill` で Skill の生成物を作り直す。
  - 設計書（`docs/design/`）の該当の節を、改造の後の実装に合わせて直す。`###` 以下の既存の見出しは変えない（新しい見出しは加えてよい）。決定の直後の「理由: 〜。」は 1〜3 文。
  - 利用者から見える変更は `CHANGELOG.md` の Unreleased の節に英語で書く。
- テストを加えるときは、スキル `test-audit` の作成時の関門を通す。新しい振る舞いは、ゴールデンか単体テストのどちらか適したほうで一度だけ確かめる。新しいゴールデンの名前に作業の ID を付けない。仕様の節に対応するテストには `// spec: <章> <見出し>` の印を付ける。
- 凍結した型やシグネチャ（`docs/archive/2026-10-09-implement-first-release/10-interfaces/`）のうち、変えてよいのは次の表のものだけである（設計者の了承: 下の「凍結した型の変更の了承」）。欄・列挙子・引数を足す変更に限り、既存の欄の意味を変えない。ほかに変える必要が生じたら、作業を止めて報告する（非公開の補助の関数・型・欄は自由に加えてよい）。

  | 凍結の文書 | 変えてよいもの | 作業 |
  |---|---|---|
  | 10-03 構文 | ファイルの先頭の部分（言語の版の宣言、依存の記述、`package` のブロック）を表す構文木の欄と型 | W1 |
  | 10-04 モジュールと名前解決 | パッケージを区別するためのモジュールの識別（`ModulePath`・`ModuleKind` に欄か列挙子を足す）、探索の関数の引数、外部の関数の束縛（`BindingKind` に列挙子を足す）。設定ファイルのモジュールの種類（`ModuleKind` に列挙子を足す。モジュールの番号とファイルの番号を揃えるため） | W1・W2・W4 |
  | 10-06 中間表現 | 外部の関数を指す値（コア IR の `ValKind` に列挙子を足す） | W5 |
  | 10-07 バイトコード | コンパイル済みプログラムの外部の関数の表（`CompiledProgram` に欄を足す）、外部の関数を呼ぶ命令（`Opcode` を足すか、既存の命令の解釈を広げる） | W5 |
  | 10-09 VM | 実行ごとの状態に WASM の実行系を置く欄（`RunState` など） | W5 |
  | 10-13 パイプラインと CLI | `package` のサブコマンド（`Command`・`ToolCommand` に列挙子を足す）、パイプラインの段に外部の関数の照合を足すこと | W1・W4・W6 |

- `formal/` は変えない（R11）。`unsafe` を書かない。大域の可変状態を加えない（epoch を進めるスレッドは実行ごとの状態として持つ）。
- 依存のクレートを加えるのは W4 の Wasmtime（とそれが引く依存）と、テストだけの依存 `wat`（Q14）だけである。ほかのクレートが要るときは止めて報告する。

どの作業の完了の条件にも、最後に次を含める（以下では省く）。

```sh
cargo test -p benitoite --test golden
cargo test -p benitoite --test skill_docs
cargo test --test spec_examples
cargo run -q -p benitoite --example gen_skill && git status --porcelain -- crates/benitoite/skill   # 作り直した結果を作業の変更に含める
cargo clippy --workspace --all-targets --no-default-features --features gc-mark-sweep,heap-verify,alloc-stats
cargo clippy -p benitoite --lib --tests --no-default-features --features gc-mark-sweep
cargo fmt --all --check
```

## 作業 W1: ファイルの先頭の部分と `package.bnt`（Q3・Q4、R1・R2・R3）

1. 構文: ファイルの先頭の部分（先頭の `//!` の後、最初の `import` か宣言の前）に、`language "X.Y.Z"` の一行、`dependency 別名 … end dependency` のブロック、`package 名前 … end package` のブロックを読む。語は予約語にせず、この位置でだけ意味を持つ。`dependency` の欄は `path`・`hash`（この改造で意味を持つ）と `source`・`version`・`commit`（読むが「この版では使えない」誤り）。`package` の欄は `license` など調査 C の D2 の例を参考に決め、知らない欄は書ける欄の一覧を示す誤りにする。欄の順は問わず、二度書きは誤り。先頭の部分より後にこれらを書いたら「ファイルの先頭に書く」誤りにする（どう見分けるかは事前点検で決める）。
2. 置き場所の規則: 依存の記述と `language` を書けるのは、入口のファイルの先頭と、根の `package.bnt` だけ。取り込まれるモジュールのファイルに書いたら誤り。`package` のブロックは `package.bnt` にだけ書ける。一つの根で入口のファイルの先頭と `package.bnt` の両方に依存の記述があれば誤り（`language` も同じ扱いにするかは事前点検で決める）。
3. `package.bnt`: 根（入口のファイルのディレクトリ）の直下だけを見て、親を遡らない。中身は先頭の部分と同じ構文だけで、`import` と宣言を書いたら誤り。`benitoite run package.bnt` などで入口に指定したら、設定ファイルであり実行できない旨の誤りにする。`benitoite test <ディレクトリ>` の走査では入口として拾わない。`fmt` は整形の対象にする。
4. 言語の版: `MAJOR.MINOR.PATCH` の形を確かめる。処理系の版より新しければ誤り。古ければ「互換性を壊した版の表」（この作業では空の表として置く）と比べる仕組みを作る。パッケージの `package.bnt`（`package` のブロックがあるもの）では必須（この必須の検査はパッケージを読む W2 で効く）。
5. 依存の記述は、この作業では読んで検査するだけで、`import` の解決には使わない（W2）。
6. 整形器: 先頭の部分の整形の規則を加える。
7. 設計書: 01-02 に先頭の部分の構文、01-03 に置き場所と `package.bnt`（新しい章 06-09 を作って詳細をそこに置いてもよい。R12）、02-10 に診断、06-01 に `package.bnt` の扱い、06-04 に走査の除外。
8. テスト: 構文と各誤りの診断（ゴールデン）、整形の往復、走査の除外。

## 作業 W2: パッケージの読み込みと取り込みの名前（R2・R3・R4）

1. 依存の解決: `path` の依存のディレクトリを根からの相対パスで解決し、その `package.bnt` を読む（なければ誤り。`package` のブロックと `language` は必須。`package.bnt` に `dependency` があれば誤り）。言語の版を処理系の版と照合する。
2. 取り込み: `import 別名.パス` を依存のパッケージの根からのモジュールに解決する。パッケージの中の `import` はそのパッケージの根から探す。`import` が根のモジュールと依存の両方に当たれば誤り。別名に `Benitoite` は使えない。
3. モジュールの同一性: 同じパスのモジュールが根とパッケージにあっても取り違えない（調査 A 1.5）。診断の位置はパッケージのファイルのパスで示す。
4. パッケージのモジュールも全体の名前解決と型検査に入れる。パッケージの中の警告を利用者に示すかは、標準ライブラリの扱いと比べて決め、設計書に書く。
5. 設計書: 01-03 にパッケージの取り込みの名前・同一性・衝突、02-01・02-04 に読み込み、06-09 にパッケージの構成。
6. テスト: 例の Textkit・Todo を `testdata/` のゴールデンに置き（形 1。Todo はハンドラで `File.readText` を差し替えるテストも含める）、衝突・別名・依存の依存・版の誤りなどの診断。

## 作業 W3: 中身のハッシュ（Q5、R10）

1. 含めるファイルの一覧（R10 の許す一覧）、シンボリックリンク・大文字と小文字だけ違うパス・UTF-8 でない名前の誤り、ファイルの数と合計の大きさの上限。
2. 計算の形: Go の dirhash を一次資料で確かめて近い形にし、設計書に正確に書く。`sha256:` と 16 進の 64 文字。処理系が既に使う `sha2` を使う。
3. `hash` を書いた依存は読み込みのたびに確かめ、食い違えば、期待した値と計算した値を示す誤りにする。
4. 設計書: 06-09 に規則を書く。
5. テスト: 一覧の規則の単体テスト、食い違いの診断のゴールデン、計算の値が固定の入力で変わらないことの単体テスト。

## 作業 W4: Wasmtime の導入と `@external` の検査（Q1、R5・R6・R7・R8・R14）

1. Wasmtime を加える（R7 の機能だけ）。入れる前と後の release の実行ファイルの大きさ（strip の前と後）を測って報告する。依存の数・ライセンス・C のコードの有無を確かめ、deny.toml、03-01「使う Rust のクレート」、05-01 の第三者のライセンスを直す。
2. 構文と検査: `@external` を知っている属性にし、本体を省いてよい属性に加える。R5 の付けられる宣言の規則、`uses` の誤り（R6）、第 1 引数が `"wasm"` でない誤り。
3. コンポーネントの照合を検査（`check`）の段で行う: コンポーネントのパスの解決（根かパッケージの根。根の外の誤り）、ファイルがない・コンポーネントでない誤り、取り込みが空でない誤り、指す関数が world の直下にない誤り、引数と戻り値の WIT の型が宣言の型と R8 の表で対応しない誤り（期待した型と WIT の型を示す）。一つのコンポーネントは検査の間に一度だけ読む。
4. 試験用のコンポーネント: テキスト形式で書いてテストの中で変換できるかを確かめ、できればそれを主にする（R14）。Fuzzy は Rust で作ったものを置く（作り方は調査 B 6.2。元のソースと手順を `testdata/` の README に書く）。
5. 設計書: 01-02「属性」の規則の改め、03-10（新）の外部の関数の章（型の対応、パスの基準、照合）、01-07 に外部の関数のエフェクト。
6. テスト: 各誤りの診断のゴールデン。

## 作業 W5: 外部の関数の呼び出し（Q2、R7・R8・R9）

1. 経路: 外部の関数を専用の経路で表す（調査 A 3.3 の案 A）。名前解決の束縛、コア IR の値、コンパイル済みプログラムの外部の関数の表（コンポーネントのパス、関数の名前、型の変換表）、呼ぶ命令。参照インタプリタ・検証器・逆アセンブラ・解析も対応させる。外部の関数の呼び出しはすべて一か所の入口を通す（R6）。
2. 実行: コンポーネントは実行ごとに一度コンパイルし（最初の呼び出しのときか読み込みのとき。事前点検で決める）、インスタンスは呼び出しごとに作る。値を両方向に変換する（大きさの上限、UTF-8 の確かめ）。
3. 上限と中断: 燃料の上限、メモリの上限（`StoreLimits`）、epoch の期限の呼び戻しで中断の印を読む（epoch を進めるスレッドは実行ごとに持ち、外部の関数を使うプログラムでだけ起こす）。02-09「中断の要求」と AGENTS.md「大域の状態」の中断の印を読む場所の一覧に加える。上限の既定値を測って決める。
4. 失敗: トラップ・燃料・メモリ・中断を R9 のとおりに分けて報告する。
5. 設計書: 02-08・02-09（または 02-13 の新しい章。R12）、03-10、01-09 の外部の関数の失敗、02-10 の診断。
6. テスト: 例の Fuzzy（形 2）と形 3 の実行のゴールデン、値の変換（R8 の各型）、トラップ・燃料・メモリの各失敗、中断（無限に回る関数を `SIGINT` で止める）。呼び出しの費用を短く測って報告する（スキル `benchmark` の短い測定）。
