## 2. フェーズ 1 で決めること

各論点に、問い、選択肢、設計原則（00-01「設計原則」。番号の小さい方が優先）による評価、推す案を書く。推す案の一覧は最後の 2.21 にまとめる。

### D1. 依存の記述の構文とキーワード

**事実**

- 依存の記述は言語の構文で書き、コメントに埋めない。設定ファイルにも同じ構文のブロックを書く（出典: platform-and-tooling.md の TODO-090・085 の「方向（2026-10-11）」）。
- 見た目は構文の見直しで変わる前提で置き、この改造では意味を固める（出典: stdlib-and-interop.md の TODO-211）。
- 例の形は、`dependency 別名 … end dependency` の中に `source`・`version`・`commit`・`hash` か `path`・`hash` を並べるもの、`project … end project`、`package 名前 … end package`、入口のファイルの先頭の `language "0.2"` である（出典: 例の `proposed/project/project.bnt`、`proposed/single-script/notes.bnt`、`proposed/packages/*/package.bnt`）。
- 外部の関数のために予約語を加えない（出典: ADR 0139 の決定 5）。予約語を加える変更は互換性を壊す（出典: language.md の TODO-018 の「前提・制約」）。`0.1.0` までは、どのリリースでも互換性を壊してよい（出典: 05-01「互換性の方針」）。

**選択肢**

| 案 | 形 | 評価 |
|---|---|---|
| A. 例のまま、語を予約語にする | `dependency`・`package`・`project`・`language` をキーワードにする | 構文解析は単純になる。しかし `language` や `package` を識別子に使ったスクリプトが壊れ、構文の見直しで見た目を変えたときに予約語が残る。原則 5 には中立 |
| B. 例の形で、語を文脈で決める | ファイルの先頭の部分（最初の `import` と宣言の前）でだけ、行頭の `language`・`dependency`・`package` を記述の始まりとして読む。欄の名前（`source`・`path`・`hash` など）もブロックの中でだけ意味を持つ | 予約語を増やさない（ADR 0139 の考え方と揃う）。見直しで形を変えても互換性の負担が小さい。先頭の部分の範囲を構文で決めるので、位置の付いた診断を出せる（原則 1・4） |
| C. 依存を一つのブロックにまとめる | `dependencies … end dependencies` の中に `Fuzzy path "…" hash "…"` を並べる | 依存が一目で分かる。しかしブロックが入れ子になり、一つの依存を足す・消す差分が大きくなる。例と設計案から離れる |
| D. 属性の形にする | `@dependency("Fuzzy", path: "…")` | 属性は宣言に付くもので、引数は文字列リテラルに限る（出典: 01-02「属性（初回リリース版）」）。欄に名前を付けられない。採りにくい |

**推す案**: B。ブロックの形は例のまま `dependency 別名 … end dependency` とし、`project` のブロックはやめる（D2・D3 で、`language` を独立の行にするため）。理由: 予約語を増やさず、構文の見直しで見た目を変えるときの負担を小さくする。

**決める細部**

- 先頭の部分の範囲。案: ファイルの先頭のドキュメントコメント（`//!`）の後、最初の `import` か宣言の前。その後に書いた記述は「先頭に書く」誤りとする。
- 欄の並びの自由度。案: 順は問わず、同じ欄の二度書きを誤りとする。
- 知らない欄。案: 誤りとし、書ける欄の一覧を示す（属性と同じ扱い。出典: 01-02「属性」）。

### D2. 設定ファイルの名前と、プロジェクトとパッケージの設定を一つにするか

**事実**

- 設定ファイルは根の直下だけを見る。根は実行を始めるファイルのあるディレクトリ（出典: platform-and-tooling.md の TODO-085、ADR 0127 の決定 3）。
- 名前は未定で、例は `project.bnt`。プロジェクトの設定とパッケージの設定（例の `package.bnt`）を一つにするかは改造で決める（出典: 同 TODO-085）。
- 取り込むファイルの名前は大文字で始まる識別子の形に限る（出典: ADR 0126 の決定 3）。したがって小文字で始まる `project.bnt` は import で取り込めず、モジュールの名前と衝突しない。
- 根の下のファイルのうち import で辿れないものは読まない（出典: ADR 0156 の決定 1）。

**例の食い違い（事実）**: 入口のファイルの先頭では `language` を独立の行に書き（`notes.bnt`）、設定ファイルでは `project` のブロックの中に書く（`project.bnt`）。同じ役割の書き方が二つあり、「先頭から設定ファイルへブロックを動かすだけで移せる」という方向（TODO-085）とも合わない。

**選択肢**

| 案 | 形 | 評価 |
|---|---|---|
| A. 二つのファイル（例のまま） | プロジェクトは `project.bnt`（`project` のブロック＋依存）、パッケージは `package.bnt`（`package` のブロック＋依存） | 役割が名前から分かる。しかし同じ役割（依存と言語の版）を二つのファイルの名前で書く（原則 5 に反する）。パッケージを開発しながらテストを走らせる根は、両方を持つことになる |
| B. 一つのファイル、中身で役割を分ける | 名前を一つ（例: `package.bnt`）にし、`package 名前 … end package` のブロックがあればパッケージ、なければプロジェクトの設定とする。ほかの中身（`language`・`dependency`）は入口のファイルの先頭と同じ | 「先頭の部分をそのまま切り出したもの」が設定ファイルになり、移す命令も単純になる（原則 5）。パッケージの根で `benitoite test` を走らせるとき、同じファイルが依存の設定を兼ねる |
| C. 一つのファイル、名前を言語名にする | `benitoite.bnt` など | B と同じ。名前から処理系の設定と分かる。`package` のブロックのある設定の名前としては、B の方が読みやすい |

**推す案**: B（ファイル名は設計者が選ぶ。候補は `package.bnt` か `project.bnt`）。設定ファイルに書けるのは、入口のファイルの先頭に書けるもの（`language`・`dependency`）に `package` のブロックを加えたものとし、関数などの宣言と `import` は誤りとする。

**決める細部**

- `benitoite run package.bnt` のように設定ファイルを実行しようとしたときの診断。案: 「設定ファイルであり実行できない」と示す。
- `fmt` の対象にするか。案: する。整形の規則は先頭の部分と同じにする。
- 入口のファイルの先頭に `package` のブロックを書けるか。案: 書けない（パッケージの根には設定ファイルを置く）。一つのファイルのパッケージは設けない。

### D3. 言語の版の宣言の場所と意味

**事実**

- 手段 5（パッケージごとの言語の版の宣言）を入れる。最小の形は「対応する処理系の版の範囲」の案。構文の見直しの後に、旧い構文で書かれたパッケージを読み込んだときに、その旨を診断で示すために使う（出典: platform-and-tooling.md の TODO-096、language.md の TODO-205）。
- 例では、スクリプトとプロジェクトは一つの版（`"0.2"`）、パッケージは範囲（`">= 0.2, < 0.3"`）を書く（出典: 例）。
- 今の処理系の版は `0.0.3`（出典: `crates/benitoite/Cargo.toml`）。`0.1.0` までは、どのリリースでも互換性を壊してよい（出典: ADR 0358 の決定 2、05-01「互換性の方針」）。

**選択肢**

| 案 | 意味 | 評価 |
|---|---|---|
| A. 範囲（例のパッケージの形） | 処理系の版が範囲の外なら誤り | 作者が上限を予想して書くことになり、予想は外れやすい。`0.0.x` の間は、どのリリースでも壊れうるので、範囲が狭くなるか、意味のない広さになる |
| B. 書いた時点の版を一つ書く | 「この版の処理系に向けて書いた」。処理系は、自分の版より新しければ「新しい処理系が要る」と誤りにする。古ければ、処理系が持つ「互換性を壊した版の表」と比べ、その後に壊れた点があれば、旧い構文である旨と移行の手掛かりを示す | 作者（主に LLM）は今の版を写すだけでよい（原則 6）。互換性を壊した点の知識は処理系の側に集まり、構文の見直しの後の診断（TODO-205 の目的）に直接使える（原則 1・2）。Go の `go.mod` の `go` の行に近い（未確認） |
| C. A と B の両方を書ける | 書き方が二つになる（原則 5 に反する） | 採りにくい |

**推す案**: B。どこに書いても同じ形（`language "0.0.4"` のように独立の行）とする。

**決める細部**

- 書くことを必須にするか。案: パッケージの設定では必須、入口のファイルと根の設定では任意。書かれていなければ版を照合しない。理由: 単体のスクリプトに一行を強いない（原則 6）。一方、パッケージは別の版の処理系から読まれる。
- 版の書式。案: `MAJOR.MINOR.PATCH` の 3 つの数に限る。
- 処理系が持つ「互換性を壊した版の表」は、フェーズ 1 では空でよい。比べる仕組みと診断の型だけを作る。
- 根の宣言とパッケージの宣言が違うとき。案: それぞれを処理系の版とだけ比べる。根とパッケージの間では比べない。

### D4. フェーズ 1 の取得元の種類

**事実**: フェーズ 1 の依存は手元のパス（S4）のパッケージとする。S4 は開発の途中の確認と Skill のディレクトリに写して置く用途に限り、公開するパッケージの依存の記述には書けない。写して置いたものも記述のハッシュで確かめる（出典: platform-and-tooling.md の TODO-093、TODO-211 のフェーズ 1）。

**選択肢**

| 案 | 内容 | 評価 |
|---|---|---|
| A. 手元のパスだけ | `path` だけを受け付ける。`source` を書いたら「後の段階」の誤り | TODO-211 の到達点に合う。git のライブラリ選び（TODO-093 の要検証）を後に回せる |
| B. git（HTTPS）も入れる | `source`・`version`・`commit` を実装する | 依存の記述の意味を一度に固められる。しかし git のライブラリ、取得の時点、キャッシュ、`--offline` まで広がり、フェーズ 1 が大きくなる |

**推す案**: A。`source`・`version`・`commit` の欄は構文として読み、意味を持たせずに「フェーズ 1 では使えない」誤りとする（D1 の知らない欄の誤りとは分け、診断で区別する）。

**決める細部**

- `path` の基準。案: その記述を書いたファイル（入口のファイルか設定ファイル）のあるディレクトリ、すなわち根。根の外を指してよい（例の `../packages/fuzzy`）。
- 「公開するパッケージの依存の記述には書けない」の扱い。フェーズ 1 は依存の依存を許さない（D7）ので、パッケージの設定に `dependency` があれば誤りとなり、この規則は自然に満たされる。

### D5. 手元のパスの依存に版とハッシュを要するか

**事実**: 例の `Fuzzy` は `path` と `hash` を書く（出典: 例の `project.bnt`）。ハッシュのない記述は取得せずに誤りとする方向（出典: TODO-090 の「取得の時点」）。写して置いたものも記述のハッシュで確かめる（出典: TODO-093）。

**選択肢**

| 案 | 内容 | 評価 |
|---|---|---|
| A. ハッシュを必須にする | パスの依存も `hash` がなければ誤り | 完全性の規則が一つで済む（原則 2）。しかし開発中のパッケージを直すたびに `hash` を書き直す手間が要る（原則 6 に反する） |
| B. ハッシュを任意にする | 書けば確かめ、なければ確かめない | 開発中は書かず、Skill のディレクトリに写して置くときは書く、と使い分けられる。書かなかったことは記述から読める |
| C. 使い分けを欄で表す | 開発中は `path`、写して置いたものは `vendored`（仮）とし、後者だけハッシュを必須にする | 意図が記述に残るが、同じ役割（手元のパス）の書き方が二つになる（原則 5） |

**推す案**: B。`version` はパスの依存には書けない（選ぶものがないので、書いたら誤り）。

**理由と補足**: フェーズ 1 でハッシュの計算と照合を実装しておくと、git の依存を入れるときに規則を変えずに済む。`benitoite check` が、ハッシュのないパスの依存について「完全性を確かめていない」と注意を出すかも決める（案: 出さない。警告が日常的に出ると読まれなくなる）。

### D6. 中身のハッシュの計算の規則

**事実**

- ハッシュは、git のコミットの ID によらず、パッケージに含めるファイルのパスと中身から SHA-256 で計算する（出典: TODO-090）。
- 含めるのは `.bnt` のソース、WASM のコンポーネント、パッケージの設定、使用許諾の文書、説明の文書に限り、ほかは読まずハッシュの対象にも入れない。サブモジュール、根の外を指すシンボリックリンク、大文字と小文字だけが違う二つのパスは誤り。大きさの上限を設ける（出典: TODO-093 の方向（2026-10-06・2026-10-11））。
- 残る点は、パスの正規化、改行、実行の属性（出典: TODO-090 の「残る点」）。`rust/` と `wit/` を含めるかは改造で決める（出典: 例の `packages/fuzzy/package.bnt` のコメント）。
- 処理系は既に `sha2` 0.11.0 に依存している（出典: `crates/benitoite/Cargo.toml`）。

**選択肢（含めるファイル）**

| 案 | 内容 | 評価 |
|---|---|---|
| A. 許す拡張子と名前の一覧 | `*.bnt`・`*.wasm`・設定ファイル・`LICENSE*`・`COPYING*`・`README*`（大文字と小文字の扱いも決める） | TODO-093 の方向のまま。`rust/`・`wit/`・`target/` は含めない。処理系が読むものと人が読む文書だけを固める |
| B. A に `*.wit` を加える | WIT はコンポーネントから取り出せる（`wasm-tools component wit`。未確認）ので重複する | 得るものが小さい |
| C. A に元のソース（`rust/` など）を加える | WASM を読めないことへの対策（TODO-049・098 の論点 1）の「元のソースの同梱」に備える | 同梱しても、ソースと WASM が対応することは保証しない。対策を決める前に含めると、対象の一覧を後で変えにくい |
| D. 除く一覧の方式 | `.git/`・`target/` などを除くすべてのファイル | 単純だが、ビルドの生成物や大きなファイルが入りやすく、TODO-093 の方向と逆 |

**推す案**: A。`rust/` と `wit/` はパッケージのディレクトリに置いてよいが、パッケージの一部とせず、ハッシュにも入れない。論点 1 の対策を決めるときに見直す（TODO-098 に残す）。

**選択肢（計算の形）**: 案は次のとおり。どれも決める必要がある。

- パス: パッケージの根からの相対パスを `/` で区切り、UTF-8 として正しくない名前は誤りとする。Unicode の正規化はしない（バイト列のまま）。理由: 正規化の有無で OS ごとに結果が変わるのを避ける。大文字と小文字だけが違う二つのパスは誤り（TODO-093）。
- 並べ方: パスのバイト列の順。
- 中身: バイト列のまま。改行を正規化しない。理由: 正規化すると、ハッシュが同じでも処理系が読む中身が違いうる（文字列リテラルの中の改行など）。今の対応環境は macOS と Linux だけ（出典: 02-09「中断の要求」の最後の段落）なので、CRLF の問題はまだ小さい。
- 実行の属性: 含めない。理由: `.bnt` と `.wasm` の意味に関係しない。
- シンボリックリンク: 根の外を指すものは誤り（TODO-093）。案: フェーズ 1 では、根の中を指すものも誤りとする（扱いを一つにする）。
- 空のディレクトリ: 無視する。
- 一つの値にまとめる形: 案は「各ファイルの `SHA-256(中身)` の 16 進とパスを一行に書いた行を並べ、その全体の SHA-256」を `sha256:` の後に 16 進で書く。Go の dirhash（`h1:`）に近い形であると記憶しているが未確認であり、採るなら一次資料（TODO-091）で確かめる。
- 大きさの上限: ファイルの数と合計の大きさに上限を設ける。値は試作で決める。

### D7. 最小版選択と、依存の依存

**事実**: 版は大きな版ごとに一つとし、最小版選択で選ぶ方向。最小版選択とハッシュの連鎖の組み合わせは改造で詰める（出典: TODO-090）。フェーズ 1 の依存は手元のパス（出典: TODO-211）。

**選択肢**

| 案 | 内容 | 評価 |
|---|---|---|
| A. 依存の依存を許さない | パッケージの設定に `dependency` があれば「フェーズ 1 では使えない」誤り | 同じパッケージを二つの経路で読む場合（ダイヤモンド）と、パッケージの同一性の規則を後へ回せる。最小版選択はフェーズ 1 に要らない |
| B. パスの依存の依存を許す | パッケージの根からのパスで依存を書ける。同一性は実体のパス（正規化した絶対パス）で決める | 形 1 のパッケージが別の形 1 のパッケージを使う例を確かめられる。しかし、パスで決めた同一性は git の依存（版で決める）と別の規則になり、後で捨てることになりうる |

**推す案**: A。最小版選択は git の依存を入れる段階で、ハッシュの連鎖とあわせて決める（TODO-090 に残す）。

### D8. 取り込みの名前と、根のモジュールとの衝突（TODO-092）

**事実**

- 取り込みの名前は「依存の別名 + パッケージの根からのモジュールのパス」とする方向（`import Fuzzy.Distance`）。別名と `Benitoite`・`Benitoite.Unofficial`・利用者のモジュールの名前との衝突は未検討（出典: TODO-092）。
- 根の直下に `Benitoite` という名前のファイルやディレクトリを置いて取り込むことは誤り（出典: ADR 0128 の決定 4）。
- 二つの取り込みの最後の要素が同じなら、少なくとも一方に `as` が要る（出典: ADR 0126 の決定 5）。

**選択肢（根の `Fuzzy/` と依存の別名 `Fuzzy` が両方あるとき）**

| 案 | 内容 | 評価 |
|---|---|---|
| A. 衝突する import を誤りにする | `import Fuzzy.Distance` が根のモジュールと依存の両方に当たるとき誤り。当たらなければ問わない | 読まないファイルを読まない ADR 0156 と合う。取り違えを実行前に示す（原則 1） |
| B. 別名と同じ名前の根の直下のファイル・ディレクトリがあれば、import の有無によらず誤り | 衝突を早く示せる。しかし Skill のディレクトリにある無関係のディレクトリまで制約する（ADR 0156 の代替案が避けた形） |
| C. 依存を優先する | 黙ってどちらかを選ぶ。利用者が読むものと処理系が使うものが食い違いうる（原則 1・2 に反する） |

**推す案**: A。加えて次の案を推す。

- 別名は大文字で始まる識別子とし、`Benitoite` は使えない。
- 別名はパッケージの設定の `package 名前` と違ってよい。診断ではパッケージの名前と別名の両方を示す。
- パッケージの中のモジュールは、パッケージの根からのパスで互いに取り込む（`import Internal.Table`）。パッケージの中から、取り込む側の根のモジュールや、自分の別名を通した取り込みはできない。
- モジュールの同一性は「パッケージの識別（フェーズ 1 では根からの依存の別名）とパッケージの根からのパス」で決める。診断の位置は、パッケージのファイルのパスで示す。

### D9. `@external` の表面と、01-02 の「属性」の規則

**事実**

- `@external("wasm", "モジュールのパス", "関数の名前")` を本体のない関数に付ける。引数・戻り値・エフェクトの型の注釈は省略不可。初回リリース版は知らない属性として誤りにする（出典: ADR 0139 の決定 2・6、TODO-046）。
- 01-02 は「属性は、宣言の型付けと評価の意味を変えず」「宣言の意味を変えるものは、キーワードで表す」と定め、本体のない宣言を標準ライブラリのソースの `@builtin` だけに認める（出典: 01-02「属性（初回リリース版）」）。`@external` は評価の意味を変える（本体を与える）ので、この規則と食い違う。
- ADR 0139 の例は旧い構文（`function renderMarkdown(source: String): String`）。例は今の構文（`-> Integer`）（出典: ADR 0139 の決定 2、例の `Distance.bnt`）。

**決めること（案）**

1. 01-02 の規則を「評価の意味を変える属性は `@builtin` と `@external` だけとし、どちらも本体のない関数の宣言に付ける」と改める。キーワードにしない理由は ADR 0139 の決定 5（予約語を加えない）。
2. 付けられる宣言: トップレベルの関数だけ。型パラメータと型クラスの制約を持つ関数には付けられない。理由: WIT の関数は単相（未確認）。
3. 書ける場所: 根のモジュール（形 3）とパッケージのモジュール（形 2）。入口のファイルにも書ける。`public` を付けてよい。
4. 第 3 引数の名前: フェーズ 1 は world の直下で export した関数（例の `export distance: func(...)`）だけを指せる。インターフェースの中の関数（`ns:pkg/iface#name` の形など）は後に回す。
5. 照合: 引数は位置で照合し、名前は照合しない。理由: WIT の名前は kebab-case であり（設計案「4. 値の受け渡し」）、名前の変換の規則を今決めなくて済む。

### D10. `@external` のエフェクトと、「ハンドラで除けない」規則

**事実**: フェーズ 1 は取り込みが空のコンポーネントを純粋と判定するところまで。「外部の関数のエフェクトはハンドラで型から除けない」規則を、フェーズ 3 で外す暫定の制限として置く（出典: TODO-048 の方向）。

**分析（案）**: フェーズ 1 のコンポーネントは取り込みが空なので、外部に作用する操作を一つも行わない。宣言の `uses` にエフェクトを書けるとしても、そのエフェクトの操作は実際には起きないので、ハンドラが型から除いても保証は破れない。したがって「ハンドラで除けない」規則は、ホストの関数を与えるまで要らない。

**選択肢**

| 案 | 内容 | 評価 |
|---|---|---|
| A. `uses` を書けない | フェーズ 1 の `@external` は純粋な関数だけ。`uses` を書いたら「ホストの関数は後の段階」の誤り | 型の規則に手を入れずに済む。後で `uses` を許しても、それまで誤りだったものを受け付けるだけ |
| B. 広い `uses` を許す | 取り込み（空）⊆ 宣言、の照合だけを行う | 規則としては TODO-048 の形に近い。しかし、ホストの関数を与えたときに「ハンドラで除けない」規則を加えると、それまで通ったスクリプトが誤りになりうる |
| C. B に「ハンドラで除けない」規則も入れる | 規則を今入れる | 使い道のない規則を型検査に加えることになる |

**推す案**: A。「ハンドラで除けない」規則と取り込みの対応表は、ホストの関数を与える段階で決める（TODO-048 に残す）。フェーズ 3 のための「呼び出しを一か所の入口に通す」こと（TODO-213）は、実装の形として守る。

### D11. 実行系の選択とライセンス・大きさ

**事実**: 形式は Component Model と WIT（出典: TODO-046）。実行系とライセンス、配布物の大きさへの影響はフェーズ 1 で決める（出典: TODO-047・005）。WASM の実行エンジンは既存の OSS を使う。「WASM プラグインの ABI は自作する」との関係を整理し直す必要がある（出典: TODO-005）。依存のクレートは C のコードを含まない性質を保ってきた（出典: TODO-099）。

**未確認**（W0 で確かめる）

- Rust から Component Model のコンポーネントを動的な型（`Val`）で呼べる成熟した実行系は Wasmtime だけかどうか。wasmi などのインタプリタが Component Model に対応しているか。
- Wasmtime のライセンス（Apache-2.0 WITH LLVM-exception と記憶している）。
- Wasmtime と Cranelift を入れたときの実行ファイルの増え方。Cranelift を使わない構成（Pulley のインタプリタなど）があるか、その大きさと速さ。
- ビルドに C コンパイラを要するか（`cc` クレートを使う部分があるか）。
- Wasmtime がプロセス全体のシグナルの処理器（トラップを捕まえるため）を入れるか、それを切れるか。入れるなら、03-01「使う Rust のクレート」に依存の大域の状態として書き、`signal-hook` の `SIGINT`・`SIGTERM` の登録と干渉しないことを確かめる（AGENTS.md の「大域の状態」は、依存の大域の状態を 03-01 に書くと定める）。
- 動的な型での呼び出し、epoch による中断、燃料（fuel）、メモリの上限の API が、同期の実行で使えるか（D13）。
- `unsafe` を書かずに使えるか。コンパイル済みのコードを保存して読み直す API は `unsafe` だったと記憶している。

**選択肢**: A. Wasmtime（Cranelift で機械語にする）、B. Wasmtime（インタプリタの構成）、C. Component Model を持たない実行系（素のモジュール）。C は TODO-046 の方向に反する。

**推す案**: W0 の結果で A か B を選ぶ。B が十分に小さく速さが足りるなら B を推す（純粋な関数は短い計算が多く、配布物の大きさの増加を抑えられる）。自作の部分は「Benitoite の型と WIT の型の対応と、境界での値の変換」と書き、00-03「自作する部分と既存の OSS を使う部分」の表を直す（TODO-005 の案のとおり）。コンパイル済みのコードは保存せず、実行のたびにコンパイルする。理由: バイトコードを保存しない方針（出典: ADR 0236 の決定 5）と揃い、`unsafe` を避けられる。

**決める細部**: Cargo の機能（feature）で実行系を外せるようにするか。案: 外せるようにはしない（構成の組み合わせを増やさない）。

### D12. 型の対応の、フェーズ 1 の部分集合

**事実**: 対応の表の案がある。WIT の側の型の一覧と、再帰する型を書けないことは未確認（出典: TODO-047、設計案「4. 値の受け渡し」）。WIT の基本の型は `bool`・`s8`〜`s64`・`u8`〜`u64`・`f32`・`f64`・`char`・`string`（出典: language.md の TODO-020。2026-10-11 に確かめた）。

**選択肢**

| 案 | 範囲 | 評価 |
|---|---|---|
| A. 最小 | `Integer`/`s64`・`Float`/`f64`・`Boolean`/`bool`・`Character`/`char`・`String`/`string`・`Byte`/`u8`・`Unit`/戻り値なし | 例の Fuzzy は足りる。`Bytes` を渡せないので、フェーズ 2 の `Hash` の前に広げ直すことになる |
| B. 中 | A に `Bytes`/`list<u8>`・`List[T]`/`list<T>`・`Option`/`option`・`Result`/`result`・`Pair`・`Triple`/`tuple` を加える | 名前の変換の規則が要らない型だけで閉じる。フェーズ 2 の `Hash` と `Json` の越え方 1 を書ける |
| C. 全部 | B にレコード・直和型・`enum` を加える | 欄と構成子の名前の変換の規則（kebab-case）を決める必要があり、構文の見直しで名前の規則が変わりうる |

**推す案**: B。レコード・直和型・リソースの型はフェーズ 2 以降（TODO-047 に残す）。

**決める細部（案）**

- `Bytes` は `list<u8>` に対応させる。`List[Byte]` も `list<u8>` に対応する。宣言の型が `Bytes` か `List[Byte]` かで、受け取る値の形を決める。
- `result` の欄を省いた形（`result<_, E>`・`result`）は、省いた側を `Unit` とみなす（WIT の意味は未確認）。
- 宣言の側に型がない WIT の型を使う関数は、読み込みのときに誤りとする（TODO-047）。
- 戻り値から言語の値を作るときは、02-09「一つの操作で作る値の大きさの上限」の確かめと、UTF-8 を確かめる文字列の値の API を通す（AGENTS.md の「組み込みの関数の書き方」）。
- `Float` の NaN のビットの形がコンポーネントの中で変わりうること（未確認）を、純粋な関数の同じ入力に同じ出力という性質との関係で確かめる。

### D13. トラップ・上限・中断

**事実**

- 外部の関数の失敗（トラップ、メモリの不足）の扱いと `Result` との対応、実行時間とメモリの上限を決める。上限はサーバモードの前でも設ける（出典: TODO-047）。
- 実行時エラーは型に現れない（出典: TODO-002 が引く ADR 0146）。
- 純粋な組み込みの関数は、待つ・タスクの起動・終了を返せない文脈を受け取る（出典: AGENTS.md の「組み込みの関数の書き方」）。
- 中断の印を読むのは、VM の実行の区切り、ランタイムが実行を終えるとき、テストの実行器がファイルとテストを始める前だけ（出典: 02-09「中断の要求」、AGENTS.md の「大域の状態」）。
- Regex の改造（TODO-201）は、繰り返す照合を一致ごとの組み込みの呼び出しに分け、VM の区切りで取り消しと中断を効かせた（出典: `docs/archive/2026-10-11-TODO-185_201_202-regex-and-http-details/README.md`）。

**分析（案）**: 純粋な外部の関数は、待つことのできない文脈から呼ばれる。したがって、作業用のスレッドへ渡して結果を待つ形（IO 実行器の形）は採れず、VM のスレッドで同期に実行することになる。実行の間はほかのタスクへ切り替えられない。これは長い純粋な組み込みの関数と同じ制約である。

**選択肢（トラップ）**

| 案 | 内容 | 評価 |
|---|---|---|
| A. 実行時エラーにする | 0 での除算と同じく実行を止める。新しい診断コードで、関数の名前・コンポーネントのパス・トラップの種類を示す | ADR 0146 と揃う。宣言の型を変えずに済む |
| B. 戻り値を `Result[T, ExternalError]` に限る | 宣言の型でトラップを扱わせる | 純粋な関数の多く（例の `distance`）で、起きないはずの誤りを毎回扱わせることになる（原則 6 に反する） |

**推す案**: A。メモリの上限を超えたときは、既存の「資源の不足」の終わり方に合わせる（今の終わり方の種類との対応は、02-09 と 01-09 を確かめて決める）。

**選択肢（時間の上限と中断）**

| 案 | 内容 | 評価 |
|---|---|---|
| A. epoch で中断の印を調べる | 一定の間隔で epoch を進め、期限の呼び戻しで中断の印を読み、立っていればトラップにして止める手順に入る | `SIGINT`・`SIGTERM` で止められる。ハーネスの時間切れも `SIGTERM` で届く。中断の印を読む場所を一つ加えるので、02-09 と AGENTS.md の「大域の状態」の文を直す必要がある。epoch を進める仕組み（実行ごとのスレッドなど）が要る |
| B. 燃料（fuel）で一回の呼び出しの計算量を限る | 上限を超えたら実行時エラー | 同じ入力に同じ結果になる（決定的）。中断には効かない |
| C. 実時間の上限 | 一回の呼び出しの時間を限る | 機械の速さで結果が変わる（非決定的） |

**推す案**: A と B の組み合わせ。中断は epoch で効かせ、燃料の上限は既定で大きめの値（試作で決める）とする。C は採らない。理由: 純粋な関数の結果が機械の速さで変わると、検査を通ったスクリプトの結果の再現性を損なう。形式化の側で、組み込みの関数の結果を関数（決定的）として仮定しているかを 07-04 で確かめ、燃料の上限による失敗を E-Err として扱えるかを見る。

**決める細部（案）**

- メモリの上限の既定値（線形メモリの大きさの上限）。試作で決める。上限を利用者が変えられるか（案: フェーズ 1 では変えられない）。
- インスタンスの単位。案: 呼び出しごとに新しいインスタンスを作る。理由: 呼び出しの間で状態が残らず、純粋な関数として扱える。費用が大きければ、コンポーネントのコンパイルは実行ごとに一度にし、インスタンスだけを呼び出しごとに作る。
- `Task.withTimeout` の取り消しは、外部の関数の実行中には効かない。文書に書く。

### D14. `benitoite package` のサブコマンド

**事実**: `package` は予約済み（出典: 06-01「予約したサブコマンドの名前（初回リリース版）」）。依存を加える命令（`add` に当たるもの）がハッシュを書き込む。先頭の記述を設定ファイルへ移す命令を設ける（出典: TODO-090・084）。

**選択肢**

| 案 | 内容 | 評価 |
|---|---|---|
| A. 設けない | 診断が書くべきハッシュを示し、利用者か LLM が書き写す | 実装は最小。ハッシュを手で書き写させるのは原則 6 に反する |
| B. 最小 | `package add 別名 --path ディレクトリ`（記述を書き、ハッシュを書き込み、エフェクトを示す）、`package update [別名]`（ハッシュを計算し直し、エフェクトの差分を示す） | ハッシュの規則を日常の手順で確かめられる |
| C. B に移す命令を加える | `package move`（仮。入口のファイルの先頭の記述を設定ファイルへ移す） | 設計案の方向。フェーズ 1 の到達点には必須ではない |

**推す案**: B を必須とし、C の移す命令は最後の作業（W9）に置いて、時間が足りなければ後へ回す。命令の名前は設計者が決める。

**決める細部（案）**

- ファイルを書き換えるとき、先頭の部分だけを書き換え、ほかの字句とコメントを保つ。
- 書き込み先は、依存の記述が既にある場所。どちらにもなければ入口のファイルの先頭か設定ファイルかを引数で選ばせる（既定は設計者が決める）。
- `--json` の出力を設けるか（ハーネスが読む）。案: フェーズ 1 では設けない。

### D15. 依存を加えるときにエフェクトとその差分を示すか（TODO-094 の前半）

**事実**: この改造では、依存を加える・更新するときにエフェクトとその差分を示すところまでとする案（決定ではない）（出典: TODO-094 の方向）。例の Todo は、加えるときに「File.Read、File.Write を使う」と示す想定（出典: 例の `packages/todo/package.bnt`）。

### D16. 形式化の範囲（07-04）

**事実**: `@external` と依存の記述が、形式化した範囲の内側に入るかを詰める。内側なら処理系より先に Lean を直し、外側なら 07-04 の表に「対象外」と書き足す（出典: TODO-211、07-04「01-12 との対応」）。07-04 の表は、組み込みの関数の型と制約を仮定の欄として与え、モジュールを「対象外（入力の時点で一意な名前に消えている）」とする（出典: 07-04「01-12 との対応」の表）。

## 3. 作業の分け方（案）

Codex が一作業ずつ直列に実装する前提で、依存の順に並べた。大きさは S（半日程度）・M（1〜2 日）・L（それ以上）の目安である。各作業は、その作業で加えた機能のテスト（ゴールデンテストを含む）と、触れた設計書の節の更新を含める。重い検査（`scripts/check.sh` の全体）は最後に一度とする。

| 作業 | 内容 | 前提 | 大きさ |
|---|---|---|---|
| W0 試作と確かめ | 実行系の候補を確かめる（D11 の未確認の点すべて: ライセンス、大きさ、C コンパイラ、シグナルの処理器、動的な型の呼び出し、epoch・燃料・メモリの上限の API、`unsafe` の要否）。例の Fuzzy を Rust でビルドし、取り込みが空になる方式を確かめる（TODO-047 の `wasm32-unknown-unknown` と `wasm32-wasip2` の比較）。テキスト形式でコンポーネントを書けるかを確かめる（D19）。WIT の型の一覧と再帰する型を一次資料で確かめる。結果を改造のディレクトリの調査の文書に書く。処理系のコードは変えない | なし | M |
| W1 先頭の部分と設定ファイル | 先頭の部分の構文（`language`・`dependency`・`package`）を文脈で決まる語として読む。設定ファイルを根の直下から読む。置き場所の規則（入口とモジュール、両方にある誤り、設定ファイルに宣言を書く誤り）。言語の版の照合（互換性を壊した版の表は空）。`source` などのフェーズ 1 で使えない欄の誤り。フォーマッタの対応。診断コード | W0（版の書式などの決定） | M |
