## TODO-046 外部の関数の言語の表面

- 状態: 方針あり
- 出どころ: [04-01「外部の関数」（章全体）](../archive/2026-10-09-design-first-release/04-extensions/04-01-external-functions.md)、[ADR 0139](../archive/2026-10-09-design-first-release/decisions/0139-external-functions-via-wasm.md)、[ADR 0137](../archive/2026-10-09-design-first-release/decisions/0137-first-release-library-scope.md) の決定 1、[ADR 0157](../archive/2026-10-09-design-first-release/decisions/0157-stdlib-sources-as-modules-with-builtin-attribute.md)、[03-01「外部に作用する関数の規則」](../archive/2026-10-09-design-first-release/03-interop/03-01-library-structure.md)、[2026-10-11 のパッケージ管理と WASM の設計案](sources/2026-10-11-package-wasm/memo.md)

標準ライブラリにない機能を利用者が呼ぶための外部の関数の層は、初回リリース版では実装していない。後から加えても既存のスクリプトを壊さないように、言語の表面だけを ADR 0139 で先に決めてある。決まっている方針は次のとおりである。

- 対象は WASM のモジュールの関数だけとする。C の ABI の共有ライブラリを呼ぶ経路は設けない。ネイティブのコードは IO 実行器を通らずに外部に作用できるので、実行時の権限制御が保証として成り立たなくなるからである。Rust のクレートの機能は、WASM にビルドすれば使える。Rust の ABI は安定していないので、別にビルドしたクレートを処理系が直接読み込むことはしない。
- 宣言は、本体のない関数に属性 `@external("wasm", "モジュールのパス", "関数の名前")` を付けて書く。第 1 引数は対象の種類であり、今は `"wasm"` だけを書ける（後で対象を加えられるように引数として残す）。モジュールのパスは根のディレクトリからのパスで、根のディレクトリの下に限る（import と同じ）。引数・戻り値・エフェクトの型の注釈は省略できない。
- WASM のモジュールが外部に作用できるのは、処理系が与えるホストの関数だけである。ホストの関数は標準ライブラリの IO の操作であり、IO 実行器と実行時の権限制御を通る。外部の関数の型のエフェクトは、モジュールが取り込むホストの関数のエフェクトを含まなければならない。ホストの関数を取り込まないモジュールの関数は、純粋な関数として宣言できる。
- 外部の関数のために、新しいキーワード・エフェクト・権限の種類は設けない。予約語も加えない。
- 初回リリース版の処理系は `@external` を知らない属性として誤りにする。本体のない宣言は、初回リリース版では標準ライブラリのソースの `@builtin` に限られる。`@external` は `@builtin` と同じ本体のない宣言の仕組みで加えられる（ADR 0157）。

実装するときに残る作業は、後続の項目（実行基盤、ホストの関数とエフェクトの照合、パッケージの WASM、WASM 以外の経路）で扱う。ホストの関数に許可を与える方法は、実行時の権限制御の方式とあわせて決める（関連: OPEN-052）。外部の関数の宣言を LLM が正しく書けるかは、構文の測定の対象に含める（関連: OPEN-012）。

方向（2026-10-11、設計者。[パッケージ管理と WASM の設計案](sources/2026-10-11-package-wasm/memo.md)）:

- `@external` は、パッケージ管理とあわせた一つの改造で入れる（TODO-211）。サーバモードより先に入れる。
- 呼ぶ対象の形式は Component Model と WIT とする。理由: 将来、Rust 以外の言語で書いたコンポーネントも同じ宣言から呼べるようにするためである。
- パッケージに同梱した WASM を指すときのモジュールのパスは、パッケージの根からのパスとする（TODO-049・098）。パッケージを介さない外部の関数は、ADR 0139 の決定 3 のとおり根からのパスとする。
- `@external` の見た目は構文の見直し（TODO-205）で変わる前提で置き、この改造では何を書くか（意味）を固める。

外部の関数を実行する基盤（04-02「プラグイン基盤」）は、章の題と範囲だけがあり、中身は書いていない。章が扱うと定めた範囲は、WASM の実行環境、ホストの関数の呼び出しの規約（ABI）、値の受け渡しとメモリの管理の責任の分担、WASM の実行とランタイム（タスクの切り替え、IO 実行器、中断の要求）の関係である。設計メモは実行環境に wazero（Go）を想定していたが、処理系を Rust で書くことにしたので選び直す。決めることは次のとおりである。

- 実行環境（Wasmtime など）とそのライセンス。モジュールの形式（素の WASM のモジュールか、Component Model と WIT か）。実行環境を処理系に含めると配布物が大きくなる点も比べる。
- 言語の値と WASM の値の対応。`String`・`Bytes`・リスト・レコードの受け渡しと、宣言の型とモジュールの型の照合。幅の違う整数の型を加えるか（関連: OPEN-042）。

- 実行時間とメモリの上限。【要検証】実行環境が持つ手段（Wasmtime の fuel など）で上限と中断を実現できるか。

方向（2026-10-11、設計者。[パッケージ管理と WASM の設計案](sources/2026-10-11-package-wasm/memo.md)の「WASM の形式と、関数を書く言語」「値の受け渡し」「フェーズ 1」）:

- モジュールの形式は Component Model と WIT とする（TODO-046）。
- 値の受け渡しは、Benitoite が今持つ型と WIT が持つ型の共通部分に限る。WASM に合わせた新しい型（TODO-020）は、構文の見直しの改造で検討する。リソースの型（01-10）は WIT の `resource` に対応させる（フェーズ 2 の `Regex` で使う。TODO-212）。

## TODO-048 ホストの関数とエフェクトの照合

- 状態: 方針あり
- 旧: OPEN-051
- 出どころ: [OPEN-051](../archive/2026-10-09-design-first-release/open-issues.md#open-051)、[ADR 0139](../archive/2026-10-09-design-first-release/decisions/0139-external-functions-via-wasm.md) の決定 4、[ADR 0150](../archive/2026-10-09-design-first-release/decisions/0150-resource-release-as-state.md)、[08-03「権限の対象の範囲を型や値で表す仕組み」](../archive/2026-10-09-design-first-release/08-appendix/08-03-language-surveys.md)、[2026-10-11 のパッケージ管理と WASM の設計案](sources/2026-10-11-package-wasm/memo.md)

モジュールに与えるホストの関数の範囲と、それを IO 実行器と実行時の権限制御に通す方法を決める。宣言のエフェクトとモジュールが取り込むホストの関数の照合を、検査のどの段で行うかも決める。

2026-10-01 に、外部の関数のエフェクトをモジュールの取り込み（imports）から求める案を候補に加えた。WASM のモジュールは、それ自体では外部に作用できず、ファイル・ネットワーク・時刻などの操作はホストが与える関数を取り込んで呼ぶ。依存するライブラリもビルドのときに一つのモジュールに組み込まれるので、取り込みの一覧からモジュールが起こしうるエフェクトの上限を機械的に求められる。案の形は次のとおりである。

- 宣言の `uses` に、モジュールの作者が申告したエフェクトを書く。
- 処理系は読み込むときに、取り込みから求めたエフェクトが申告に含まれるかを検査し、含まれなければ誤りとする。
- 処理系は、申告したエフェクトに当たるホストの関数だけをモジュールに与え、ほかの取り込みは解決しない。申告がそのまま実行時の強制になる。

Rust などのソースを解析してエフェクトを推論する方式は、依存・`unsafe`・C の関数の呼び出し・動的な呼び出し・マクロの生成物を漏れなく扱う必要があり、正しさを保ちにくいので採らない方向である。取り込みで判定する案を採るときは、次の点を決める。

- ホストの関数（WASI のインターフェースの関数を含む）と組み込みのエフェクトの対応表。関数ごとか、インターフェースごとか。
- 取り込んでいても呼ばない関数による広い見積もりの扱い。例えば Rust の標準ライブラリは panic の表示のために標準エラー出力への書き込みを取り込むので、利用者に示す権限が実際より広くなる。
- 操作の対象の範囲（パス、ホスト）。取り込みから分かるのはエフェクトの種類までなので、範囲は実行時の権限制御で制限する。WASI の、許可したディレクトリだけを渡す方式との関係（関連: OPEN-052）。
- 申告を書く場所。宣言の `uses` のほかに、モジュールのカスタムセクションにも書かせて一致を検査するか。

ホストの関数の操作と言語のハンドラの関係も決める。外部の関数の型のエフェクトは、ほかの関数と同じくハンドラで処理でき、処理したエフェクトは型から除かれる。

- WASM の中から呼んだホストの関数の操作をハンドラに渡すなら、WASM の実行を途中で止めて節を実行し、再開する仕組みが要る。節が `resume` を呼ばずに終わるときの WASM の実行の終え方も決める。
- 渡さないなら、ハンドラが型から除いたエフェクトの操作を処理系が実際に行うことになり、エフェクトの保証が破れる（解放について同じ問題を扱ったのが ADR 0150）。この場合は、外部の関数のエフェクトをハンドラで除けないようにする規則が要る。

方向（2026-10-11、設計者。[パッケージ管理と WASM の設計案](sources/2026-10-11-package-wasm/memo.md)の「保証の範囲と、エフェクトの照合」「ホストの関数の操作と、言語のハンドラ」）:

- パッケージ管理と外部の関数の改造（TODO-211）のフェーズ 1 で、取り込みによる照合を入れる。フェーズ 1 が扱うのは、取り込みが空のコンポーネントを純粋と判定するところまでである。ホストの関数と組み込みのエフェクトの対応表、広い見積もりの扱い、申告を書く場所は、ホストの関数を与える段階で決める。
- 操作の対象（パス、ホスト）を実行時に絞る仕組みは、サーバモードで加える。この改造で宣言する保証の案は、「エフェクトは型に現れ、宣言を超えるホストの関数は解決せず呼べない」「操作の対象は絞らない」である（決定ではない。TODO-004）。
- この改造では、WASM の中から呼んだホストの関数の操作を言語のハンドラに渡さない。外部の関数のエフェクトはハンドラで型から除けない、という規則で保証を保つ。この規則は、ハンドラに渡す実装（フェーズ 3 以降。TODO-213）で外す暫定の制限として置く。
- ホストの関数の呼び出しは、すべて一か所の入口（IO 実行器の入口）を通す。フェーズ 3 で、そこにハンドラへの経路を差し込むためである。

## TODO-049 パッケージにビルド済みの WASM を含める場合

- 状態: 方針あり
- 旧: OPEN-051
- 出どころ: [OPEN-051](../archive/2026-10-09-design-first-release/open-issues.md#open-051)、[06-05「パッケージに WASM を含める場合」](../archive/2026-10-09-design-first-release/06-tooling/06-05-package-manager.md)、[パッケージ管理の検討メモ「パッケージに WASM を含める場合」](../archive/2026-10-09-design-first-release/sources/post-first-release/post-first-release-package-management.md)、[2026-10-11 のパッケージ管理と WASM の設計案](sources/2026-10-11-package-wasm/memo.md)

2026-10-02 に、パッケージにビルド済みの WASM のモジュールを含める場合を検討した。モジュールはホストの関数を通してしか外部に作用できない（ADR 0139 の決定 4）ので、含めてもエフェクトの保証と、導入のときにコードを実行しない性質は保たれる。含めるかを、次の点とあわせて決める。

- 中身をソースとして読めない。ハッシュで固定できるのは配られたものが変わっていないことまでで、公開されたソースからビルドしたことは保証しない。対策の候補は、元のソースを同梱させる、再現可能なビルドで照合できるようにする、公式のパッケージだけはこちらでビルドして配る、である。署名との関係はパッケージ管理の側で扱う（関連: OPEN-076）。

- 処理系の大きさ。WASM の実行系を含めると配布物が大きくなる。

## TODO-098 パッケージにビルド済みの WASM を含める場合

- 状態: 方針あり

WASM に特有の論点:

1. 中身をソースとして読めない。ハッシュが保証するのは配られたものが変わっていないことまでで、公開されたソースからビルドしたことではない。対策の候補は、元のソースを同梱させる、再現可能なビルドで照合する、公式のパッケージだけはこちらでビルドして配る、など。影響は「宣言したエフェクトの範囲の中で意図と違うことをする」可能性に限られる。
2. 資源の消費。WASM の関数は VM の外で計算するので、実行系の側で計算量（Wasmtime の fuel など）とメモリの上限が要る。【要検証】採る実行系での手段。中断の印（ADR 0163）を WASM の実行中にどう効かせるかも決める。
3. モジュールのパスの基準。ADR 0139 の決定 3 は根のディレクトリからのパスとしているので、パッケージの中の WASM はパッケージの根からのパスとする規則が要る。
4. 処理系の大きさ。WASM の実行系を含めると配布物が大きくなる。
5. Elm のように、WASM を含められるのを公式のパッケージに限る選択肢もある。

## TODO-085 プロジェクトの設定ファイルと、根のディレクトリの指定

- 状態: 方針あり
- 旧: OPEN-048
- 出どころ: [open-issues の OPEN-048](../archive/2026-10-09-design-first-release/open-issues.md#open-048)、[06-01「CLI」](../archive/2026-10-09-design-first-release/06-tooling/06-01-cli.md)の「ディレクトリの指定（初回リリース版）」「エージェントハーネスの設定ファイル（初回リリース版の後）」、[06-05「パッケージ管理」](../archive/2026-10-09-design-first-release/06-tooling/06-05-package-manager.md)の「前提」、[ADR 0126](../archive/2026-10-09-design-first-release/decisions/0126-import-by-module-name.md)、[ADR 0127](../archive/2026-10-09-design-first-release/decisions/0127-directory-run-and-root.md)、[ADR 0187](../archive/2026-10-09-design-first-release/decisions/0187-standalone-reads-user-policy-file.md)、[ADR 0343](../archive/2026-10-09-design-first-release/decisions/0343-agent-harness-user-config-file.md)、[2026-10-11 のパッケージ管理と WASM の設計案](sources/2026-10-11-package-wasm/memo.md)

初回リリース版は設定ファイルを設けず、根のディレクトリを実行を始めるファイルのあるディレクトリとする。処理系は作業ディレクトリや親を辿って設定ファイルを探さないので、どこから起動しても同じファイルを取り込む。その代わり、実行を始めるファイルを根の直下に置く必要がある。

決めること:

- 設定ファイルを設けるか。設けるなら名前、置き場所、書くもの（名前、入口、根、権限、依存）。
- 探し方。作業ディレクトリから親へ辿る方法は、起動した場所で効く設定が変わる（ADR 0127 が避けた理由）。
- 一つの根の下に、実行を始めるファイルを複数置く方法。
- 依存の記述をここに置くか、実行を始めるファイルの先頭に置くか（パッケージ管理の項目。依存は根ごとに一か所に書く方向）。

この規則の対象外としたもの:

- サーバが書く利用者単位の方針のファイル。スタンドアロンモードが起動のたびに読む（ADR 0187）。
- エージェントハーネスの利用者単位の設定ファイル（TOML。決まった場所に置き、探さない。ADR 0343）。
- エージェントハーネスのプロジェクトごとの設定ファイル（根だけに置いて辿らない方向。エージェントハーネスに限った例外。関連: OPEN-102）。この項目で設定ファイルを設けるときは、それと一つにまとめるかをあわせて決める。

方向（2026-10-11、設計者。[パッケージ管理と WASM の設計案](sources/2026-10-11-package-wasm/memo.md)の「書く場所」「書き方」）:

- パッケージ管理と外部の関数の改造（TODO-211）で、依存の記述を書く設定ファイルを設ける。依存の記述は、単体のスクリプトのために入口のファイルの先頭に書け、プロジェクトのために設定ファイルにも書ける。どちらに書くかは利用者が選ぶ。
- 設定ファイルは根のディレクトリの直下だけを見て、親を遡らない。根は今のとおり実行を始めるファイルのあるディレクトリとする（ADR 0127）。プロジェクトの下のサブディレクトリに置いた単体のスクリプトは、別の根になる。
- 一つの根の依存は一か所に書く。入口のファイルの先頭と設定ファイルの両方に依存の記述があれば、誤りとする。理由: 片方を黙って無視すると、利用者が読む依存と実際に使う依存が食い違い、設計原則 1・2 に反する。
- 設定ファイルにも、入口のファイルの先頭と同じ言語の構文のブロックを書く。理由: 先頭から設定ファイルへ移すときはブロックを動かすだけで済み、同じ役割の構文を二つに増やさない（設計原則 5）。
- 設定ファイルの名前は決めていない。例では根に置く `project.bnt` とした（[package-samples/proposed/project/](sources/2026-10-11-package-wasm/package-samples/proposed/project/project.bnt)）。
- プロジェクトの設定とパッケージの設定（例では `package.bnt`）を一つのファイルにするかは、改造のときに決める。パッケージも依存を持つので、一つにまとめる案もある。
- 一つの根の下に実行を始めるファイルを複数置く方法と、エージェントハーネスの設定ファイルとの関係は、この方向では扱っていない。

設計の条件（06-05。既存の ADR から導かれる性質）:

1. パッケージのエフェクトが型に現れる（公開の契約はエフェクトを含む。ADR 0154）。版を上げてエフェクトが増えれば型が変わる。
2. 導入のときにコードを実行する仕組みが要らない（ソースを読んで全体を検査する。ADR 0156。外部の関数はビルド済みの WASM に限る。ADR 0139）。
3. 依存の書き手は主に LLM、確認するのは人間である。名前だけで取得できる方式は、LLM が書いた存在しない名前や似た名前を攻撃者が先に登録する攻撃に弱い。
4. 一つのファイルのスクリプトと Agent Skill が主な用途である。Skill はディレクトリを単位に配るので、依存を写して置く形と合う。設定ファイルを親へ辿る方式は避けた（ADR 0127）。
5. サーバモードの署名で依存まで覆うには、依存の中身をハッシュで固定する必要がある。
6. 吟味の前のモジュールを標準へ移す仕組みがある（ADR 0286）。公式のライブラリを別に配るなら線引きが要る。

検討の方向（2026-10-02〜06。どれも決定ではない）:

- 設けるか、どの版で設けるか。設けない場合は標準ライブラリを厚くし、手元のファイルを写して使うだけにする。用途（個人の道具、Skill）でこれで足りる範囲を先に見積もる。
- 中央のレジストリは初めは持たず、取得元と中身のハッシュで依存を固定する。比べる軸は運営の手間と、条件 3 の攻撃への耐性。
- 依存は根ごとに一か所（実行を始めるファイルか、プロジェクトの設定ファイル）に書き、モジュールのファイルごとには書かない。パッケージの側も根に一か所置く。
- 一つの依存の記述は、取り込みの別名、取得元、版（版の番号の形のタグ）、コミットの ID、中身のハッシュを含む（メモの仮の形は `dependency Git` に `source`・`version`・`commit`・`hash` を並べたもの）。後の二つは処理系の命令（`add` に当たるもの。`package` の下に置くか）が取得して書き込む。ハッシュのない記述は取得せずに誤りとし、診断で書き込む命令を示す。実行のときに黙って取得することはしない。
- ロックファイルは設けず、版とハッシュを記述に直接書く。一つのファイルのスクリプトのまま配れ、スクリプトの署名が依存の中身まで覆う。
- 版は大きな版ごとに一つとし、その中では依存が求めた版のうち最大のものを選ぶ（最小版選択）。修正版の違いだけで型が分かれることがない。選んだ結果は依存の依存も含めて根の記述に書き出す。
- 中身のハッシュは、git のコミットの ID によらず、パッケージに含めるファイルのパスと中身から SHA-256 で計算する。取得の手段によらず同じ値で確かめられ、SHA-1 の弱さに依らず、署名の一覧の SHA-256 と揃う。コミットの ID は、タグが消えたり付け直されたりしたときに取り直すための手掛かりとする。
- 取得の時点: スタンドアロンモードの `run`・`check` は手元にない依存を取得してよい（ハッシュで確かめる）。ネットワークを使わない指定（`--offline` など）を設ける。サーバモードは登録のときに取得し、実行のときには取得しない。
- 保存: 利用者のキャッシュのディレクトリに、中身のハッシュを名前にして読み取り専用で置き、共有の導入先を持たない。プロジェクトの中に写す命令（`benitoite vendor` など）を設け、Skill のディレクトリにまとめて配れるようにする。取得元が消えたときのプロキシは持たず、備えは写して置くことで利用者が行う。タグが付け直されていたら示し、記述のコミットの ID で取り直す。
- 依存を加える・更新するときに示すもの: 取得元の URL（ホストと所有者の名前を目立たせる）、版、コミットの ID、パッケージが使うエフェクトと前の版からの差分、署名の有無と鍵。URL の所有者が意図した相手かは利用者でなければ判断できないので、取得の後に確認を求める。

残る点:

- 0.x の版の扱い（`v0.3` と `v0.4` を別の大きな版とするか、0.x の間は版ごとに別とするか）。
- 根の記述の版と依存の依存が求める版が食い違ったときの規則（根が古い版を書いていたら誤りにするか）。
- 中身のハッシュの計算の規則（パスの正規化、改行の扱い、実行の属性を含めるか）。
- 依存を書く場所と記述の構文（設定ファイルの項目とあわせる）。

- 版とハッシュ: 上の方向（ロックファイルを設けず、記述に版と中身のハッシュを直接書く）を引き継ぐ。
- 取得の時点: 上の方向（`run`・`check` は手元にない依存を取得してハッシュで確かめる、ネットワークを使わない指定を設ける、ハッシュのない記述は取得せずに誤りとする）を引き継ぐ。フェーズ 1 の依存は手元のパスのパッケージとする（TODO-211）。

記述を短くする案（決定ではない）: 上の「選んだ結果は依存の依存も含めて根の記述に書き出す」に代えて、次の形を案とする。

- 根の記述には、直接の依存だけを版とハッシュ付きで書く。
- 依存の依存は、ハッシュの連鎖で固定する。各パッケージの依存の記述はそのパッケージの中身のハッシュの対象に含まれるので、直接の依存のハッシュが、その先の依存のハッシュまで固定する。
- 最小版選択の結果、あるパッケージが自分で固定した版と違う版が選ばれた依存だけを、根の記述に書き出す。
- 最小版選択とハッシュの連鎖の組み合わせ方（選び直した版のハッシュの書き方、根の記述と依存の依存の記述が食い違ったときの規則）は、改造のときに詰める。

調査（2026-10-11）: 一つのスクリプトに依存を書く方式を、関数型の言語（F#、Scala CLI、cabal、Stack、Elixir、Roc など）とそれ以外（PEP 723 と uv、cargo script、Deno、Ruby、Kotlin、Go）について一次資料で調べた。結果と出典は設計案の付録 A・B にある。両方に書ける言語の扱いは、片方を無視する（uv、Stack、Ruby）、誤りにする（Elixir）、合算する（Scala CLI）に分かれた。ハッシュを記述に直接書く先例は Roc だけだった。

- パッケージが宣言してハンドラで処理するエフェクトは `main` の型に現れないので、そうしたエフェクトを権限の表示にどう出すかも OPEN-081 とあわせて決める。

## TODO-096 依存関係地獄を言語仕様で防ぐ手段

- 状態: 方針あり
- 旧: OPEN-077
- 出どころ: [open-issues の OPEN-077](../archive/2026-10-09-design-first-release/open-issues.md#open-077)、[06-05「パッケージ管理」](../archive/2026-10-09-design-first-release/06-tooling/06-05-package-manager.md)の「依存関係地獄を言語仕様で防ぐ手段」、[パッケージ管理の検討メモ](../archive/2026-10-09-design-first-release/sources/post-first-release/post-first-release-package-management.md)の「依存関係地獄を言語仕様で防げるか」「版の選び方と、同じパッケージの複数の版」、[2026-10-11 のパッケージ管理と WASM の設計案](sources/2026-10-11-package-wasm/memo.md)

依存関係の問題は原因の違う六つの問題からなる。1 版の衝突（ダイヤモンド依存）、2 環境の汚染、3 再現しないこと、4 ネイティブのコードのビルド、5 版の番号が互換性を表さないこと、6 処理系の版との不一致。メモの見立ては、手段 (1)・(2)・(3)・(6) が既存の規則と組み合わせやすく、特に (2) と (3) は型とエフェクトを静的に追跡する言語だから検査できるので特徴にできる、というものである（決定ではない）。

1. 同じパッケージの互換性のない版を一つのプログラムに共存させる。モジュールの同一性を、パッケージの識別とモジュールのパスで決める。版の違う型は別の型になるので、診断に版と依存の経路を示す。トップレベルに可変の状態を置けないこと（ADR 0055・0123）と孤立した実装の禁止（ADR 0061）により、同じモジュールが二つ読まれても複製による不具合が起きにくい。識別を版ごと（中身のハッシュ）にすると修正版の違いだけで型が分かれるので、大きな版ごととする案（最小版選択。依存の記述の項目）と組み合わせる。
2. 公開の依存と非公開の依存を区別し、非公開と宣言した依存の型が公開の関数の型に現れたら誤りとする。利用者が版を揃える必要があるのは公開の依存だけになる。
3. 公開の契約の差分を検査し、互換性を壊す変更なのに大きな版を上げていなければ公開を拒む（Elm の方式をエフェクトまで広げた形）。エフェクトの増加も互換性を壊す変更とする。保証するのは型とエフェクトの互換性だけである。
4. パッケージに含められるものをソースと WASM のモジュールに限る（ADR 0139）。環境ごとのネイティブのビルドが要らない。【要検証】WASM の実行系が対応しない環境の有無（関連: OPEN-051）。
5. パッケージごとに言語の版を宣言する。処理系が複数の版の規則を保つ負担が生じるので、0.x の間は対応する処理系の版の範囲だけを宣言する案もある。正式リリース版の互換性の方針とあわせて決める。
6. 共有の導入先を持たず、どのスクリプトがどの版を使うかを、そのスクリプトの依存の記述だけで決める。

どの手段でも防げないもの: 版の違う二つのパッケージの間での値の受け渡し（変換の関数を書くか版を揃えるしかなく、言語仕様にできるのは明確な診断まで）、意味の互換性、依存の数そのものの増加（標準ライブラリと公式の追加のライブラリを厚くするライブラリの方針の問題）。

方向（2026-10-11、設計者。[パッケージ管理と WASM の設計案](sources/2026-10-11-package-wasm/memo.md)の「入れるもの」）: 手段 5（パッケージごとの言語の版の宣言）を、パッケージ管理と外部の関数の改造（TODO-211）で入れる。構文の見直し（TODO-205）の後に、旧い構文で書かれたパッケージを読み込んだときに、その旨を診断で示すために使う。最小の形は「対応する処理系の版の範囲」とする案である（決定ではない。例では `language` の欄とした）。宣言の形と旧い構文のパッケージを読んだときの診断は、改造のときに詰める。ほかの手段は、この方向では扱っていない。

- 出どころ: [open-issues の OPEN-094](../archive/2026-10-09-design-first-release/open-issues.md#open-094)、[ADR 0138](../archive/2026-10-09-design-first-release/decisions/0138-crates-and-licenses-for-stdlib.md)、[ADR 0143](../archive/2026-10-09-design-first-release/decisions/0143-http-and-tls-crates.md)、[ADR 0176](../archive/2026-10-09-design-first-release/decisions/0176-first-release-targets-and-static-linux-build.md)、[秘密の情報の扱いの検討メモ](../archive/2026-10-09-design-first-release/sources/post-first-release/post-first-release-secrets.md)の「実装の課題」

初回リリース版の依存は、どれも C のコードを含まず、ビルドに Rust のツールチェーンだけを要する。この性質はクレートを選んだ決定（ADR 0138・0143）の帰結として成り立っており、Linux 向けを musl で静的にリンクする決定（ADR 0176）がそれを前提にしている。「C コンパイラを避ける」こと自体を一般の方針とした ADR はなく、ADR 0143 は C コンパイラを要する `aws-lc-rs` を代わりの案として残している。

初回リリース版の後の機能には、この性質を崩しうるものがある。FIDO2 のクレートは C のライブラリ（hidapi、libfido2）かシステムのライブラリに依存する（サーバモードの認証と承認）。OS のキーストアのクレートが Linux で C の libdbus に依存するか（関連: OPEN-090）、端末の表示を止めるクレートも同様か（関連: OPEN-089）を確かめる必要がある。こうした依存を加えるときは、次の二つを分ける。

1. 調査: ビルドに C コンパイラが要るか。実行時に共有ライブラリ（Linux の libudev など）を読み込むか。後者は musl の静的な実行ファイルと両立しない。macOS の IOKit のような OS の部品のフレームワークを使うことは C コンパイラを要しない。
2. 判断: 依存の基準（ビルドは Rust のツールチェーンだけ、実行時は OS の部品以外の共有ライブラリを読まない）を一般の方針として ADR にし、新しい機能をその範囲で作るか、例外を認めるかを決める。基準の文言と例外の認め方も決める。

初回リリース版が宣言する保証は静的検査（型とエフェクトの規則への適合）だけであり、実行時の権限制御を行わない。スクリプトは処理系を起動した利用者の OS の権限で行える操作をすべて行え、隔離はハーネスのサンドボックス・コンテナ・OS の権限に委ねる。後の版では、サーバモードとあわせて、利用者が許可した範囲の外の操作を拒否する仕組みと OS のサンドボックスによる強制を加え、その範囲はサーバモードの設計で決める（関連: OPEN-055）。各段階で、表に書いていない保証を宣言しない規則は続ける。

未解決の問い:

- サーバモードを加えた版で、スタンドアロンモードの保証をどう宣言するか（サーバモードを加えた後のスタンドアロンモードは、利用者の方針のファイルを読み、OS のサンドボックスを掛けた子プロセスで実行する方針がある。ADR 0187・0204。関連: サーバモードの分野）。
- 外部の関数・パッケージ・篩型を加える版で、それぞれ何を保証に加えるか（ロードマップは「機能ごとに定める」とだけ書いている）。

方向（2026-10-11、設計者。[パッケージ管理と WASM の設計案](sources/2026-10-11-package-wasm/memo.md)の「保証の範囲と、エフェクトの照合」）: パッケージ管理と外部の関数の改造（TODO-211）はサーバモードより前に行うので、保証に加えるのは静的な照合だけとし、操作の対象を実行時に絞る仕組みはサーバモードで加える。この改造で宣言する保証の案は次のとおりである（決定ではない）。

- パッケージと外部の関数が起こしうるエフェクトは型に現れる。宣言を超えるホストの関数は解決せず、呼べない（TODO-048）。
- 操作の対象（パス、ホスト）は絞らない。
