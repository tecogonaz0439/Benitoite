## M1. `wasm/` の下の小文字のディレクトリを辿らないので、W4 の `@external` が読めるのにハッシュで確かめないファイルが生じる

- 場所: `src/modules/hash.rs:77-87`、06-09「中身のハッシュ」（`docs/design/06-tooling/06-09-packages.md:68`）。
- 問題: 走査は「各段で」ASCII の大文字で始まる名前か `wasm` に一致する名前のディレクトリだけを辿る。このため `wasm/` の中では、`wasm/Sub/` は辿るが `wasm/sub/`・`wasm/components/` は辿らず、その下の `.wasm` はハッシュに入らない。一方、W4 の事前点検（`reviews/preflight-W4W5.md`「パスの規則」の 3）は、パッケージのモジュールの `@external` のパスを「最初の段が `wasm`」とだけ定め、2 段目以降の段の名前は `.` で始まるものしか拒否しない。W4 をその案のまま実装すると、`@external("wasm", "wasm/impl/x.wasm", "f")` は読めて実行できるが、`hash` を書いた依存でも `wasm/impl/x.wasm` の変更を検出しない。R10・Q10 の目的（「ハッシュの対象と処理系が読めるファイルの範囲が一致する」）に反する。また W4 の事前点検は W3 の範囲を「`wasm/` の下の `*.wasm`」と書いており、実装と食い違う。
- 再現（ハッシュの側）: 依存 `lib/` に `wasm/impl/x.wasm` を置き、`hash` を書いた状態で中身を書き換えても `check` は E0919 を出さない（`Mod/` などと違い `impl` が小文字のため）。単体テストは `wasm/x.wasm` だけを確かめ、`wasm/<小文字>/` を確かめていない。
- 修正案（どちらか。W4 の前に決める）:
  - (a) 推す: パッケージの根の直下の `wasm/` に入ったら、その下は名前が `.` で始まるもの以外をすべて辿る（`pending` に「`wasm` の下か」の印を持たせる）。`wasm` を特別に扱うのは根の直下だけにし、`Mod/wasm/` は大文字の規則に従わせる（Q10 の「`wasm/`」は根の直下の一つを指すと読める）。06-09 の文を「根の直下のファイル、名前が ASCII の大文字で始まるディレクトリ（各段）、根の直下の `wasm/` の下のすべて」に直し、単体テストに `wasm/impl/x.wasm` を含める・`Mod/wasm/` の扱いを加える。
  - (b) W4 のパスの規則で、`wasm/` の下の段を「ASCII の大文字で始まる」ものに限る。利用者に分かりにくい規則が増えるので (a) を推す。
  - どちらでも、W4 の事前点検の「W3 のハッシュの範囲」の記述を実装に合わせる。

## M2. 名前が `.` で始まる壊れたシンボリックリンク（Emacs のロックの `.#File.bnt` など）があると、ハッシュの計算もモジュールの探索も失敗する

- 場所: `src/modules/mod.rs:151-163`（`RealFs::list_dir`。W3 より前からある）、`src/modules/hash.rs:53-60`、06-09 の注記の表の `symlink` と `read` の行（`06-09-packages.md:96,101`）。
- 問題: `RealFs::list_dir` は項目ごとに `std::fs::metadata(entry.path())?`（リンクを辿る）を呼ぶので、リンク先のないシンボリックリンクが一つでもあると、ディレクトリ全体の一覧が誤りになる。W3 は名前が `.` で始まる項目を「辿らず、含めない」とし、`symlink` の注記も `.` で始まる項目を除くと書くが、一覧そのものが失敗するので、`.` で始まる壊れたリンクでも E0920（`read`）になる。注記はディレクトリの名前を示して「No such file or directory」と言うので、原因が分からない。Emacs は編集中のファイルの隣に `.#<名前>` という壊れたシンボリックリンクをロックとして作るので、依存のファイルを Emacs で開いているだけで検査が止まる。
- 再現（W3 の範囲）:
  ```text
  lib/package.bnt, lib/Mod/Value.bnt, app/main.bnt（hash を書いた dependency Lib、import Lib.Mod.Value）
  ln -s 'user@host.1:1' lib/Mod/.#Value.bnt
  benitoite check app/main.bnt
  → error[E0920] ... note: cannot read `Mod`: No such file or directory (os error 2)
  ```
  依存の根に置くと W2 の段で E0916（「cannot read the dependency `Lib` at `../lib`」と OS の文言だけ）と E0318 が出る。`hash` を省いた依存の `Mod/` に置くと E0318 だけが出る。根のディレクトリに `.#Helper.bnt` を置くと、`import Helper` が E0318 と「E0101: cannot read file `.`」で失敗する（W3 より前からの不具合）。
- 修正案: `RealFs::list_dir` で、`entry.file_type()` がシンボリックリンクのときだけ `metadata` を引き、失敗したら `is_dir: false` として返す（または一覧から除く）。凍結した `ModuleFs` のシグネチャは変わらない。そのうえで W3 の走査は、`.` で始まる項目を今のとおり飛ばし、ほかの壊れたリンクは `canonicalize` の失敗ではなく `symlink` として報告する（`canonicalize` の失敗の前に、リンクかどうかを判定できない点は残る。`canonicalize` が `NotFound` を返した項目は、一覧に出た以上は壊れたリンクとみなして `symlink` にする、が `ModuleFs` だけでできる近似）。根のモジュールの探索への影響も同じ修正で直るので、この改造の中で直すか、docs/todo に項目を加える。ゴールデンにシンボリックリンクは置けないので、`real_files_reject_links_and_non_regular_files` に壊れたリンク（`.` で始まるものと始まらないもの）を足す。

## L1. どの誤りを報告するかが、ディレクトリの列挙の順で変わる

- 場所: `src/modules/hash.rs:52-111`。
- 問題: 走査は `list_dir` が返す順に項目を見て、最初に当たった誤りで止まる。シンボリックリンクと大文字小文字の衝突が両方ある、`TooMany` を超える前にリンクがある、などのとき、報告する注記と、`case` の `path`・`other` のどちらが先かが、ファイルシステムの列挙の順で変わる。`find.rs` は「診断の候補もファイルシステムの項目の順に依存させない（設計書 02-02）」としており、方針と揃わない。ハッシュの値そのものは `BTreeMap` で並べるので決定的である。
- 修正案: `list_dir` の結果を名前の UTF-8 のバイト列の順に並べてから処理する（`entries.sort_by(|a, b| a.name.cmp(&b.name))`）。費用は小さい。

## L3. 走査そのものの量に上限がない

- 場所: `src/modules/hash.rs:52-111`。
- 問題: 上限は「含めるファイル」の数と大きさだけで、辿るディレクトリの項目（含めないファイルを含む）の数は制限しない。項目ごとに `canonicalize`（`realpath`）を呼ぶので、根や大文字のディレクトリに含めないファイルが大量にあると、検査のたびに時間がかかる。06-09 の「検査のたびに読む量を制限する」という理由は、読む量については正しいが、走査の時間は保証しない（06-09 も測定の段落で「全パッケージの所要時間は保証しない」と書いており、矛盾はしない）。
- 修正案: 今は記録だけでよい。必要なら、見た項目の数にも上限（例えば含めるファイルの上限の 10 倍）を設け、`too_many` と同じ注記の別の文で報告する。docs/todo の項目にしてもよい。

## 確かめて問題がなかった点

- **計算の形**: ゴールデンのパッケージ（`testdata/packages/hash-match/deps/hashkit/`）で `sha256sum Value.bnt package.bnt | sha256sum`（`/sbin/sha256sum`）と `shasum -a 256 … | shasum -a 256` の両方が `8e94a7a4…ada02` を出し、`package.bnt` の値と E0919 のゴールデンの `computed:` に一致した。単体テストの固定値 `0b480539…45377` も、Python の `hashlib` で、パスを UTF-8 のバイト列で並べ「16 進 64 文字、空白二つ、パス、改行」をつないで独立に求めた値と一致した（CRLF の中身、非 UTF-8 の中身、`wasm/x.wasm` を含む）。06-09 の手順 1〜4 と Go の `Hash1` との違いの説明は、実装と一致する。
- **決定性**: パスは `/` で組み立て（`format!("{relative}/{}")`）、`BTreeMap<String, _>` の順（UTF-8 のバイト列の順）で要約を作る。根は `canonicalize` した後の相対パスだけを使うので、根の実パスに依らない。
- **「大文字」の意味**: `u8::is_ascii_uppercase` で先頭のバイトを見る。01-01 の字句の規則で、大文字識別子は英大文字で始まり ASCII だけからなるので、import で辿れるディレクトリ（`find.rs` は `list_dir` の名前と完全に一致する項目だけを選ぶ）は、すべてハッシュの走査に入る。ファイルの名前も `Z.bnt` と完全に一致するものだけを読むので、大文字小文字を区別しないファイルシステムでも、ローダが読む `.bnt` はハッシュに含めた名前と同じ綴りである。`Z.BNT` を除くことと矛盾しない。
- **ローダが読むファイルとハッシュの対象**: ローダは `canonicalize` した `resolved` を読み、ハッシュはリンクを拒否したうえで同じ正規化したパスを読む。M1 を除き、今のローダが依存から読むファイル（`package.bnt` と大文字のディレクトリの `.bnt`）は、すべてハッシュの対象に入る。二つの読みの間の書き換えは 06-09 の最後の段落が明記しており、事前点検の判断どおりである。
- **シンボリックリンクの判定**: 根を正規化し、辿るディレクトリは「正規化した結果と一致した」ものだけなので、`dir.join(name)` は常に正規化したパスの子である。`canonicalize` の結果がそれと違えばリンクと判定でき、`RealFs` では正しく働く（ファイル・含めないファイル・ディレクトリへのリンクを実ファイルで確かめるテストあり。CLI でも `result -> /tmp` の小文字のリンクで E0920 を確認）。名前に制御文字を含むリンクは、診断の表示で `\u{1B}` のようにエスケープされることを確かめた。
- **上限**: ファイル数は挿入の前に `>=` で比べ、合計は `checked_add` の後に `<=` で比べるので、上限ちょうどを許す（境界のテストあり）。1 ファイルは既存の 256 MiB の読み込みの上限に従い、06-09 に書いてある。
- **呼ぶ回数と時点**: `check_hash` は入口の反復の中で、依存の設定ファイルを検査した直後に依存ごとに一度だけ呼ぶ（`load.rs:248-253`）。設定ファイルに誤りがあれば計算しない。`hash` を省いた依存では計算しない（MemFs に置いたリンクで、省いたときに E0920 が出ないことを単体テストが確かめている）。
- **W2 との関係**: 照合に失敗すると `hashes_valid` を偽にし、入口の import をすべて解決しない（`load.rs:266`）。パッケージのモジュールを読まないことを単体テストが確かめている。06-09 の「照合に失敗した入口では import を解決しない」と一致する。
- **規約**: 走査は明示の積み重ね、`unwrap`・`as`・添字なし、文言は `diag::codes` と `modules::text`、`ModuleFs` のシグネチャは不変、`sha2` は既存の依存。`skill/references/diagnostics.md` は再生成されている。テストのビルドの `#[allow]` は表の範囲内。一時ディレクトリを `target/` の下に作る形は既存のテストと同じ。
- **テスト（test-audit）**: 単体テスト 5 件は、それぞれ別の規則（固定値と一覧、衝突と改行、上限の境界、読み込みからの呼び出し、実ファイルのリンクと FIFO）を確かめ、関門のコメントがある。固定値は実装で求めていない。ゴールデン 2 件は成功と E0919 の CLI の形を確かめる。足りないのは M1（`wasm/` の下の小文字のディレクトリ）と M2（壊れたリンク）の場合である。
- **設計書**: 06-09「中身のハッシュ」、01-03 の一文と 06-09 へのリンク、02-10 の E09 の行は実装と一致する（M1・M2 で直す箇所を除く）。新しい見出しは「中身のハッシュ」だけで、既存の `###` の見出しは変えていない。
