# 判断とその理由

## 設計者の決定

### Q1 対策の方式

- 答え（2026-10-13）: 引数と戻り値に直接現れる `List[Byte]`・`List[Integer]`・`List[Float]` を、`Vec<u8>`・`Vec<i64>`・`Vec<f64>` に詰めて Wasmtime の型付きの呼び出しで渡す（相談の案 1）。JIT は要らない（40 倍は Wasmtime の動的な値の API の性質で、Benitoite の VM の作りとは関係がない）。
- 理由: 一次資料の調査（2026-10-13）では、Wasmtime の動的な API・C API・wasmtime-py・wasmtime-dotnet は `list<u8>` を汎用の値で持ち、`bindgen!` と jco は型付きの表現でバイト列のまま渡す。Benitoite の `Bytes` の速い経路と同じ形に `List[Byte]` などを載せれば、`unsafe` も依存の追加も要らない。

### Q2 実行ファイルの大きさ

- 答え（2026-10-13）: T1 の後、strip の後の実行ファイルが 2.17 MB 増えた（具体化 340 → 1,554 通り）。`List[Integer]`・`List[Float]` を引数に含む関数は、引数が 2 個以下のときだけ型付きの経路で渡す（レビューの案 A、具体化 642 通り、増分の見込みは約 0.5 MB）。`Integer`・`Float`・`String`・`Bytes`・`List[Byte]` だけの組は 3 個まで型付きの経路のままとし、戻り値はどの組でも 6 種を扱う。外した組は動的な経路で渡す。
- 理由: `List[Byte]` は具体化を共有するので、案 A でも 1 要素 1 バイトのまま 3 引数まで速い。数のリストを 3 引数の関数で渡す例は測定の課題になく、具体化の大半を占めるその組を外すのが最も効く。検討した代替案は、数のリストの引数を 1 個の関数に限る案（D、約 0.33 MB）、今のまま受け入れる案、release のビルドの最適化の設定で縮める案（VM の速さが変わりうる）。

## 推す案どおりとした点

### R1 型付きの経路の範囲

- 速い経路（フェーズ 2 の R6）の対象を、引数が 0〜3 個で、引数と戻り値の型がそれぞれ `Integer`・`Float`・`String`・`Bytes`・`List[Byte]`・`List[Integer]`・`List[Float]`（WIT の `s64`・`f64`・`string`・`list<u8>`・`list<u8>`・`list<s64>`・`list<f64>`）のどれかの関数に広げる。戻り値のない関数は今のとおり含めない。
- `List[Byte]` と `Bytes` は、Wasmtime の側では同じ `&[u8]`／`Vec<u8>` の具体化を共有し、Benitoite の値との変換だけを分ける。新しい具体化は `list<s64>`（`&[i64]`／`Vec<i64>`）と `list<f64>`（`&[f64]`／`Vec<f64>`）の分だけ増える。
- 入れ子の中（レコードの欄、`Option`・`Result`・タプルの中、リストのリスト）のリストは、今のとおり動的な経路で渡す。この限界を 03-10 に書く。
- 受け渡しの予算は、Wasmtime の型付きの持ち上げと同じく、`list<u8>` を 1 要素 1 バイト、`list<s64>`・`list<f64>` を 1 要素 8 バイトと数える（引数は処理系が同じ規則で数える）。`--wasm-stats` も同じ数え方にする。
- 理由: 型付きの経路は具体化の数だけ実行ファイルが大きくなる（フェーズ 2 の V4 で 340 通り、strip の後 +0.65 MB）。`List[Byte]` を `Bytes` と同じ具体化に載せれば、問題の中心（バイト列）は具体化を増やさずに直せる。

### R2 戻り値のリストの作り方

- T1 のレビュー（`reviews/2026-10-13-T1/report.md` の M1）に従い、型付きの経路の戻り値のリストは、要素を 32 個ずつ葉に詰めて作り、要素の数だけの中間の値の並び（1 要素 16 バイト）を作らない。6 MB の `List[Byte]` を返すときの中間の 96 MB がなくなる。
- 理由: 受け渡しの予算 1 バイトあたりのホストの確保を小さく保つためである。リストを作る関数を `runtime::list` に足す（既存の関数のシグネチャは変えない）。
