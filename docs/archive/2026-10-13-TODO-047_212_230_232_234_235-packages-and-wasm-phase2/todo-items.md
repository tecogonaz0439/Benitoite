### TODO-212 `Benitoite.Unofficial` のモジュールを WASM で書けるかの検証（フェーズ 2）

- 状態: 方針あり
- 出どころ: [2026-10-11 のパッケージ管理と WASM の設計案](sources/2026-10-11-package-wasm/memo.md)の「フェーズ 2: Unofficial のライブラリを WASM で書けるかの検証」「Json の三つの実装の性能の比較（案）」

パッケージ管理と外部の関数の改造（TODO-211）のフェーズ 2 として、今 `Benitoite.Unofficial` で提供しているモジュールのうち、どれを WASM で実装できるかを仮の実装で確かめる。結果は、非公式のモジュールの行き先（TODO-097）の材料になる。

事前の見込み（設計案。確かめていない）:

| モジュール | 見込み |
|---|---|
| `Console`・`File`・`Process`・`Clock`・`Random`・`Http` | 移せない。WASM に与えるホストの関数の側にあたる |
| `Path` | 移せるが利点が小さい。OS ごとの区切りを引数で渡す必要がある |
| `Hash`・`Encoding`・`Csv` | ほぼそのまま移せる。大きなバイト列を境界で写す費用がかかる |
| `Regex` | 移せる。コンパイル済みの正規表現を WIT の resource で持つ |
| `Json` | 工夫が要る。WIT で再帰する型を書けないなら（未確認）、木構造の値をそのままは渡せない |
| `Time` | 大部分は移せる。タイムゾーンのデータの同梱が別の問題になる |

仮に実装する対象は、次の三つとすると設計者が了承した（2026-10-11）。

- `Hash`: 最も単純な形（バイト列を渡して結果を受け取る）。境界で値を写す費用を、ほかの二つと比べる基準にする。
- `Regex`: WIT の resource と Benitoite のリソースの型の対応。長い照合を fuel か epoch で区切り、取り消しと中断を効かせること。
- `Json`: 再帰する値の受け渡しと、三つの実装の性能の比較。

検証の観点は、移せるか、境界を越える費用（今の `@builtin` の実装との比）、WIT の型での表しやすさ、中断との関係、WASM のバイナリと処理系の大きさである。費用は `benchmark` スキルの短い測定で取る。

`Json` の三つの実装の比較（案）:

- 比べる実装は、A. 今の Unofficial の `Json`（Rust の `@builtin`）、B. Benitoite で書いた構文解析器（形 1。今でも根の下のモジュールとして書いて測れる）、C. Rust で書いた WASM の実装（形 2。フェーズ 1 とフェーズ 2 の resource の後）である。
- C の境界の越え方の候補は、文字列から文字列へ（検証・整形・パスで指した値の取り出し）、平らな節点の表で返して Benitoite の側で木に組み直す、resource で文書を WASM の側に持たせて要る値だけを問い合わせる、の三つである。
- 課題を分けて測る（解析して `Json.Value` を全部作る、`Json.Value` を文字列に書く、解析して数か所の値だけを読む、整形・検証だけ）。一つの数字では、境界の費用と構文解析の速さが混ざるからである。入力は 1 KB・100 KB・10 MB 程度の三段とし、C は初回の読み込み（機械語へのコンパイル）と 2 回目以降の呼び出しを分ける。測る前に、三つの実装が同じ入力に同じ結果を返すことを確かめる。
- 分かること: B と A の差は、Unofficial のモジュールを Benitoite で書き直したときの遅さ（TODO-097 の手段 (i) の判断の材料）。C と A の差は WASM の境界の費用。C と B の差は、速さが要るライブラリを WASM にする価値。

設計者が決めること: B は今書けるので、先に作っておけばフェーズ 2 で C ができたときにすぐ並べられる。B をいつ作るか。

フェーズ 1 の結果（2026-10-13。改造 `docs/archive/2026-10-13-TODO-046_047_048_085_090_092_093_094_096_098_211-packages-and-wasm-phase1/`）: 外部の関数が受け渡せる型は、03-10「型の対応」の表の型に限る。リソースの型・レコード・直和型・`Map` は受け渡せない（TODO-047）。したがって `Regex` の resource と `Json` の再帰する値を試すには、型の対応を広げる作業が先に要る。境界の値は Wasmtime の動的な値（`Val`）に変換して受け渡すので、`Bytes` は 1 バイトごとに約 40 バイトの値になり、受け渡しの予算 256 MiB の中で渡せるのは約 6.7 MB までである（TODO-230）。`Hash` で境界の費用を測る前に、TODO-230 を決めるかを考える。

パッケージ管理と外部の関数の改造のフェーズ 1（2026-10-13。改造 `docs/archive/2026-10-13-TODO-046_047_048_085_090_092_093_094_096_098_211-packages-and-wasm-phase1/`）で、実行系（Wasmtime 49.0.2。機能 `runtime`・`component-model`・`std`・`cranelift`）、呼ぶ対象の形式（Component Model と WIT）、受け渡す型、トラップ・上限・中断の扱いを決めて実装した。内容は 03-10「外部の関数」と 02-09「外部の関数の実行」にある。残る点は次のとおりである。

- 受け渡す型を広げる。今の型の対応は、03-10「型の対応」の表に限る。広げる候補は、レコードと `record`（WIT の名前は kebab-case なので、欄の名前の変換の規則が要る）、利用者が定義した直和型と `variant`・`enum`（再帰せず、型パラメータを持たない型に限る案）、リソースの型と WIT の `resource`（フェーズ 2 の `Regex`。TODO-212）、`Map` と WIT の `map<K, V>` である。宣言の側に型がない `s32` などを使う関数は、今は誤りにしている（TODO-020）。
- WASM の実行中のタスクの切り替え。今は同期で実行し、その間ほかのタスクへ切り替えないので、`Task.withTimeout` の取り消しは外部の関数の実行中には効かない。実行を区切って VM に戻すには、VM に途中で止めた外部の呼び出しの状態を加える必要がある（同改造の `decisions.md` の Q2）。ホストの関数の操作をハンドラに渡す仕組み（TODO-213）とあわせて考える。

- 上限を利用者が変える方法。燃料、線形メモリ（一回の呼び出しの合計 64 MiB）、受け渡しの予算（引数と戻り値でそれぞれ 256 MiB）は、今は利用者が変えられない。
- コンパイル済みのコードの再利用。今は検査と実行のたびにコンポーネントを Cranelift でコンパイルし、結果を保存しない。Wasmtime の事前にコンパイルしたコードを読む API（`deserialize`）は `unsafe` で、改ざんされたキャッシュから任意のコードが走りうるので使っていない（同 Q1）。一回の `benitoite test` の中での共有は TODO-229、大きなコンポーネントのコンパイルの費用は TODO-228 で扱う。

### TODO-230 大きな `Bytes` とリストを外部の関数の境界で受け渡す費用

- 状態: 未着手
- 出どころ: 改造 `docs/archive/2026-10-13-TODO-046_047_048_085_090_092_093_094_096_098_211-packages-and-wasm-phase1/`の `decisions.md` の R20、`reviews/2026-10-13-W5/report.md` の H2・M2・M3

外部の関数の引数と戻り値は、Wasmtime の動的な値（`Val`）に変換して受け渡す。受け渡しの予算（引数と戻り値でそれぞれ 256 MiB）は、Wasmtime と同じく、リストの要素ごとに `Val` の大きさ（64 ビットの対応環境で 40 バイト）を数える（02-09「外部の関数の実行」）。`Bytes` も 1 バイトごとに `Val` 一つになるので、予算の中で渡せる `Bytes` は約 6.7 MB（2^28 / 40 バイト）までである。変換の時間とホストのメモリも、バイト数の約 40 倍に比例する。

決めること: 大きな `Bytes` と数のリストを速く安く渡す経路を設けるか。候補は、宣言の型ごとに Wasmtime の型付きの呼び出し（`TypedFunc`）を使う形と、ゲストの線形メモリへ直接写す形である。どちらも、Wasmtime 49.0.2 で使えるかと、受け渡しの予算をどう数えるかを確かめていない。フェーズ 2 の `Hash`・`Json` の境界の費用（TODO-212）を測る前に決めないと、その測定は動的な値の費用を主に測ることになる。

### TODO-232 外部の関数の呼び出しの短い性能の測定と、燃料の既定値の見直し

- 状態: 要検証
- 出どころ: 改造 `docs/archive/2026-10-13-TODO-046_047_048_085_090_092_093_094_096_098_211-packages-and-wasm-phase1/`の `decisions.md` の Q15・R9

燃料の既定値（一回の呼び出しで 10^10）は、試験用の Fuzzy に 3,000 文字どうしの距離を計算させたときの燃料の消費量（549,697,585）の約 18.2 倍として決めた（02-09「外部の関数の実行」）。この改造では、スキル `benchmark` に従う短い測定（呼び出し一回の費用、燃料あたりの時間）を行わなかった。スキルが測定の前に設計者に機械の状態を確かめてもらうと定めており、改造の間に確かめを得られなかったからである。

### TODO-234 パッケージの中だけで公開する段階

- 状態: 未着手

今の公開の段階は、宣言したモジュールの中だけ（既定）と、取り込んだ側すべて（`public`）の二つである（01-03「公開（初回リリース版）」）。パッケージの中の複数のモジュールで補助の関数や型を共有するには `public` を付けるほかなく、パッケージを使う側からも見えて取り込めてしまう。名前（`Calc/Internal.bnt` など）で内部用と示すことはできるが、取り込みを防ぐ仕組みではない。WASM のコンポーネントの中の補助の関数は、WIT で書き出さなければ外から見えないので、この問題は Benitoite の側のモジュールにだけ当たる。

設計者の方向（2026-10-13）: パッケージの中だけの公開（Rust の `pub(crate)` に当たるもの）が欲しい。

決めること:

- 書き方（新しいキーワードか、`public` の修飾か、属性か）。予約語を増やすかは TODO-018 と、見た目は構文の見直し（TODO-205）と合わせて決める。

- `benitoite package` のエフェクトの表示（パッケージを使う側から見える関数だけを集計する。R24）との関係。

### TODO-048 ホストの関数とエフェクトの照合

- 状態: 方針あり
- 旧: OPEN-051
- 出どころ: [OPEN-051](../archive/2026-10-09-design-first-release/open-issues.md#open-051)、[ADR 0139](../archive/2026-10-09-design-first-release/decisions/0139-external-functions-via-wasm.md) の決定 4、[ADR 0150](../archive/2026-10-09-design-first-release/decisions/0150-resource-release-as-state.md)、[08-03「権限の対象の範囲を型や値で表す仕組み」](../archive/2026-10-09-design-first-release/08-appendix/08-03-language-surveys.md)、[2026-10-11 のパッケージ管理と WASM の設計案](sources/2026-10-11-package-wasm/memo.md)、改造 `docs/archive/2026-10-13-TODO-046_047_048_085_090_092_093_094_096_098_211-packages-and-wasm-phase1/`の `decisions.md` の R6

パッケージ管理と外部の関数の改造のフェーズ 1（2026-10-13。改造 `docs/archive/2026-10-13-TODO-046_047_048_085_090_092_093_094_096_098_211-packages-and-wasm-phase1/`）では、ホストの関数を与えず、取り込みが空のコンポーネントだけを受け付けて、その関数に純粋な関数として型を付けた。`@external` の宣言には `uses` を書けない（03-10「宣言の形」「照合」）。取り込みのないコンポーネントは外部に作用できないので、ハンドラが型からエフェクトを除いても保証は破れない。このため、「外部の関数のエフェクトはハンドラで除けない」規則はまだ入れていない（同改造の `decisions.md` の R6）。後で `uses` を許しても、それまで誤りだったものを受け付けるだけである。

ホストの関数を与える段階で、次の点を決める。方式の案は 2026-10-01 に候補に加えたもので、外部の関数のエフェクトをコンポーネントの取り込みから求める。宣言の `uses` に作者が申告したエフェクトを書き、処理系は読み込むときに、取り込みから求めたエフェクトが申告に含まれるかを検査し、申告に当たるホストの関数だけを与える。Rust などのソースを解析してエフェクトを推論する方式は、依存・`unsafe`・C の関数の呼び出し・動的な呼び出し・マクロの生成物を漏れなく扱う必要があり、正しさを保ちにくいので採らない方向である。

- ホストの関数（WASI のインターフェースの関数を含む）と組み込みのエフェクトの対応表。関数ごとか、インターフェースごとか。
- 取り込んでいても呼ばない関数による広い見積もりの扱い。例えば Rust の標準ライブラリは panic の表示のために標準エラー出力への書き込みを取り込むので、利用者に示す権限が実際より広くなる。
- 操作の対象の範囲（パス、ホスト）。取り込みから分かるのはエフェクトの種類までなので、範囲は実行時の権限制御で制限する。操作の対象を実行時に絞る仕組みはサーバモードで加える。WASI の、許可したディレクトリだけを渡す方式との関係（関連: OPEN-052）。
- 申告を書く場所。宣言の `uses` のほかに、コンポーネントのカスタムセクションにも書かせて一致を検査するか。
- ホストの関数の操作と言語のハンドラの関係。方向（2026-10-11、設計者）は、WASM の中から呼んだホストの関数の操作を言語のハンドラに渡さず、外部の関数のエフェクトはハンドラで型から除けない、という規則で保証を保つことである。渡さないまま除けると、ハンドラが型から除いたエフェクトの操作を処理系が実際に行うことになり、エフェクトの保証が破れる（解放について同じ問題を扱ったのが ADR 0150）。この規則はホストの関数を与えるときに入れ、ハンドラに渡す実装（フェーズ 3 以降。TODO-213）で外す暫定の制限とする。
- ホストの関数の呼び出しは、すべて一か所の入口（IO 実行器の入口）を通す。フェーズ 3 で、そこにハンドラへの経路を差し込むためである。外部の関数の呼び出しそのものは、フェーズ 1 で一か所の入口に通した（TODO-213）。

### TODO-213 ホストの関数の操作を言語のハンドラに渡す（フェーズ 3 以降）

### TODO-097 公式の追加のライブラリの配り方と、非公式のモジュールの行き先

- 状態: 未着手
- 旧: OPEN-078
- 出どころ: [open-issues の OPEN-078](../archive/2026-10-09-design-first-release/open-issues.md#open-078)、[06-05「パッケージ管理」](../archive/2026-10-09-design-first-release/06-tooling/06-05-package-manager.md)の「公式の追加のライブラリ」、[パッケージ管理の検討メモ](../archive/2026-10-09-design-first-release/sources/post-first-release/post-first-release-package-management.md)の「公式のライブラリの名前と取得元」「非公式のモジュールを公式の追加のライブラリへ移せるか」、[ADR 0286](../archive/2026-10-09-design-first-release/decisions/0286-unofficial-modules-imported-under-unofficial.md)、[ADR 0338](../archive/2026-10-09-design-first-release/decisions/0338-password-manager-wrappers-as-official-libraries.md)、[2026-10-11 のパッケージ管理と WASM の設計案](sources/2026-10-11-package-wasm/memo.md)

標準ライブラリに入れず処理系と別に配る公式のライブラリ（公式の追加のライブラリ。例: git のラッパー）を設けるか、設けるなら名前と取得元をどうするかを決める。ライブラリは三つの層に分けて考える。標準ライブラリ（`Benitoite.*`。処理系に同梱し取得元を書かない。版は処理系に従う）、公式の追加のライブラリ、第三者と利用者のライブラリ（依存の記述の別名。取得元とハッシュ、または手元のパス）。

名前と取得元の案:

- (a) ほかのパッケージと同じく取得元とハッシュで書く。規則が一つで済むが、URL が長く、移転で変わり、LLM が書き誤ったときに原因が分かりにくい。
- (b) 予約した短い名前（例: `benitoite:git`）を、処理系が対応表で公式の取得元とハッシュに変える。対応表を埋め込めば移転に処理系の更新で追従でき、ハッシュも処理系が保証する。更新が処理系のリリースに縛られる。対応表をネットワークから取ると小さなレジストリになり運営が要る。
- (c) 自前のドメインの URL を名前にして転送する（Go の vanity import path）。ドメインを失うと名前が他人に渡る。
- (d) 設けず標準ライブラリ（非公式のモジュールを含む）に入れる。配布物が大きくなり、外部のコマンドの版に追従するものも処理系のリリースに縛られる。

方向: 標準ライブラリには取得元を付けない。公式の追加のライブラリは (b) で対応表を処理系に埋め込む形が有力で、更新を処理系のリリースと切り離したくなった時点で対応表を取得する形へ広げる。

非公式のモジュールの行き先: ADR 0286 の「標準」「非公式」は吟味の状態であり、配り方とは別の軸である。行き先に公式の追加のライブラリを加えるには、吟味を終えたモジュールを標準に移すとした ADR 0286 の決定 7 を改める ADR が要る。移せるモジュールの制約:

- 組み込みのエフェクトを宣言するモジュール（`Console`・`File`・`Process`・`Clock`・`Random`・`Http`）は移せない。処理系が `Benitoite` の名前空間の名前で照合し（ADR 0128 の決定 6）、実行時の権限制御の対象になるからである。`Clock` は prelude の `Task.race`・`Task.withTimeout` からも使われる。
- `@builtin` は標準ライブラリのソースにだけ書ける（ADR 0157 の決定 3）。使うモジュールを移すには、(i) Benitoite で書き直す（速さが要るものは遅くなる）、(ii) 公式の追加のライブラリにも `@builtin` を許す（得られるのは名前の整理だけ）、(iii) 外部の関数の層の後に実装を WASM として含める、のどれかが要る。
- 選ぶ基準の案: 組み込みのエフェクトを宣言するもの、標準のモジュールが依存するもの、多くのスクリプトが使うもの（`Path`・`Json` など）は処理系に残す。外部の仕様やコマンドの版に追従するもの、使う場面が限られるものを公式の追加のライブラリにする。この基準で候補になりうるのは `Csv`・`Encoding`・`Hash` くらいで、初回リリース版ではどれも公開の関数をすべて `@builtin` で宣言している（2026-10-08 に確認）。移す時期は外部の関数の層の後か、書き直すと決めたときになる。git のラッパーは `Process` の上に Benitoite で書けるので、最初から公式の追加のライブラリとして作れる。

主なパスワードマネージャ（Proton Pass、KeePass 系、1Password、Bitwarden）のラッパーを公式のライブラリとして用意すると決めた（ADR 0338）。標準ライブラリに入れるか公式の追加のライブラリとして配るかは、この項目で決める。

方向（2026-10-11、設計者。[パッケージ管理と WASM の設計案](sources/2026-10-11-package-wasm/memo.md)の「パッケージに含めるもの」「後回しにするもの」「フェーズ 2」）:

- 公式の追加のライブラリの配り方は、パッケージ管理と外部の関数の改造（TODO-211）では扱わない。
- 公式の追加のライブラリ（git やパスワードマネージャのラッパー）は、Benitoite だけで書いたパッケージ（TODO-211 の形 1）として書く想定である。
- 上の手段 (iii)（実装を WASM として含める）は、その改造のフェーズ 2 で、`Hash`・`Regex`・`Json` を仮に WASM で実装して確かめる（TODO-212）。手段 (i)（Benitoite で書き直す）でどれだけ遅くなるかは、`Json` を Benitoite で書いた実装と今の実装を比べて測る案がある（TODO-212）。

### TODO-018 キーワードと予約語の見直し

- 状態: 要検証
- 旧: OPEN-012
- 出どころ: [open-issues の OPEN-012](../archive/2026-10-09-design-first-release/open-issues.md#open-012)、[01-01 字句構造](../archive/2026-10-09-design-first-release/01-spec/01-01-lexical.md)の「キーワード」、[ADR 0092](../archive/2026-10-09-design-first-release/decisions/0092-unabbreviated-keywords.md)、[ADR 0093](../archive/2026-10-09-design-first-release/decisions/0093-no-reserved-words-for-absent-constructs.md)、[ADR 0115](../archive/2026-10-09-design-first-release/decisions/0115-structured-io-concurrency.md)、[01-11 並行処理](../archive/2026-10-09-design-first-release/01-spec/01-11-concurrency.md)の「未決事項」、[2026-10-11 の言語の方向のメモ](sources/2026-10-11-language-direction/memo.md)

初回リリース版は、測定の前の暫定の案として次のように決めた。

- キーワードは省略しない語（`function`・`public`・`implement`）とし、省略形（`fn`・`pub`・`impl`）と `mut` は予約しない（ADR 0092。【方針】）。
- 他の言語の制御構文に当たる語（`for`・`while`・`loop`・`break`・`continue`）と `where`・`switch`・`as` は予約しない（ADR 0093。【方針】）。`return` はキーワードである。
- 使う予定の決まっていない構文の語（`class`・`instance`・`var`・`mutable`・`module`・`derive`）は予約せず、その語を使う構文を加えると決めたときにキーワードにする（ADR 0093）。
- 並行処理はライブラリの関数と `with` で提供し、`async`・`await`・`spawn`・`select` を予約しない（ADR 0115）。

未解決の問い（どれも、LLM が診断を読んで 1 回で直せた率で比べる）:

1. 省略形と省略しない語のどちらが誤りにくいか。省略形は Rust・Gleam の書き方を、省略しない語は JavaScript・Java の書き方（`return` を書く、型を書き忘れる、`private` を書く）を思い出させるという見込みがあるが、確かめていない。関数の型とラムダも同じキーワードを使うので比べる対象に含める。
2. 省略しない語を採る場合に、省略形を予約語に加えるか。予約すれば、式の中の `fn(x) { ... }` も「`function` と書く」という構文の誤りとして示せる。予約しなければ、式の中の `fn(...)` は変数 `fn` の呼び出しとして構文解析を通り、名前解決の誤りとしてしか報告できない。
3. 制御構文の語と `as`・`where` を予約して「この言語にはその構文がない。再帰を使う」のような診断を出すか、識別子として読んで一般の誤りにするか。
4. 並行処理の語を予約して、Benitoite の書き方（`uses IO` を付けた普通の関数、`Task.await`・`TaskGroup.spawn`・`Task.race`）を診断で示すか。

前提・制約: 予約語を加えると、その語を識別子に使ったスクリプトが誤りになる。OPEN-012 は「キーワードと予約語は測定の結果で決めきる」としていたが、初回リリース版（0.0.1）は暫定の案のまま出た。したがって、これから予約語を加える変更は互換性を壊す変更であり、0.x のマイナーの版で `CHANGELOG` に移行の手順を書いて行う（ADR 0236）。

方向（2026-10-11、設計者）: 構文の見直し（TODO-205）とともに最重要とし、その改造で扱う。基準は、プログラミングに馴染みのない人が読んで拒否反応を起こしにくいこと（TODO-205）である。上の問いのうち、LLM の誤りを診断で案内するための予約（問い 2〜4 の `fn`・`for`・`async` など）は副次の論点に下がる。

- 版の付け方（ADR 0358）。ソースだけのリリースは `0.0.1`・`0.0.2`…とし、`0.1.0` までは、どのリリースでも互換性を壊してよい。実行ファイルを配る最初のリリースを `0.1.0` とし、その後は互換性を壊す変更を `0.x.0` のリリースに限る。正式リリースは `1.0.0` とし、機能が揃い、互換性を壊す変更が要らなくなったと設計者が判断した後に行う。コードネーム `San Benito` はメジャーバージョンが 1 の間まで使い、2 の候補は `Itoigawa` と `Okutama` である（ADR 0090）。
- `0.1.0` から `1.0.0` の前までの互換性（ADR 0236）。マイナーの版では言語・標準ライブラリ・CLI・診断の互換性を壊してよい。パッチの版は不具合の修正だけを含め、仕様（言語・標準ライブラリ・CLI・診断コードと JSON の形）を変えない。診断の文言と修正案の中身は約束に含めない。互換性を壊す変更は `CHANGELOG` に移行の手順とともに記録する。廃止した診断コードの番号は使い回さない。バイトコードは保存も配布もしないので対象にしない。同梱の Agent Skill は同じ版の処理系だけを対象にする。非公式のモジュールを標準へ移すことは互換性を壊す変更であり、マイナーの版で行う。
- 正式リリース版の条件に、スクリプトを埋め込んだ単一バイナリの実装（ADR 0175）と、すべての未決事項の決着（ADR 0178。扱わない事項は扱わないことを ADR に記して決着させる）を含める。設計書の最終版もこの時点で発行する。

未解決の問い:

- 正式リリース版とする条件の詳細。言語仕様のどの範囲を固めたら `1.0.0` とするか、将来拡張のどの機能を `1.0.0` より前に入れるか。
- 正式リリース版で互換性を約束する範囲。言語のソース（構文と型の規則）、標準ライブラリ、CLI のオプションと終了状態、診断のコードと JSON の形、保存したバイトコード（埋め込みでコンパイル済みプログラムを扱う場合）のどれを含めるか。
- 構成子を後から加えうる代数的データ型（`IOErrorKind`・`NetworkErrorKind` など）の `match` に `_` の分岐を必須にする仕組み（Rust の `#[non_exhaustive]`、Swift の `@unknown default` に当たるもの）を設けるか。設けないなら、正式リリース版の後は構成子を加えられない（ADR 0144）。0.x の間は構成子の追加をマイナーの版で行う（ADR 0236 の帰結）。パッケージの型にも同じ仕組みが要るかも、本項で検討する（パッケージの名前空間の項目 TODO-092 から移した。TODO-092 は 2026-10-13 に閉じた）。
- パッケージごとの言語の版の宣言（依存関係地獄の項目の手段 5）は、2026-10-13 に、書いた時点の処理系の版を一つ書く形で入れた（TODO-096）。互換性を約束する範囲を決めるときに、宣言の意味（互換性を壊した版の表と比べること）も見直す。

初回リリース版の数の型は、`Integer`（64 bit）・`Float`（倍精度）・`Byte`（0〜255）・`Decimal`（128 bit の 10 進の小数）である。固定幅の数は、バイト列から読み書きする関数で扱う（ADR 0107）。

2026-10-11 に設計者が、将来の WASM のライブラリと WASM のランタイムへの対応を想定し、WASM に合わせた型を検討する方向とした（関連: OPEN-051、外部の関数と WASM のプラグインの分野）。C のライブラリとの受け渡しと、単精度の数の大量の保持にも使う。`Float` は倍精度のまま変えないと決めてある。

WASM の型（2026-10-11 に確かめた）:

- コアの仕様の数の型は `i32`・`i64`・`f32`・`f64` で、ベクトルの型 `v128` がある。整数の型は符号の有無を持たず、解釈は個々の命令が決める（WebAssembly の仕様の「Types」）。
- コンポーネントモデルのインターフェースの記述（WIT）の基本の型は、`bool`・`s8`〜`s64`・`u8`〜`u64`・`f32`・`f64`・`char`・`string` である（コンポーネントモデルの「WIT」）。

ライブラリとの受け渡しを考えるなら、型の集まりを WIT の基本の型に合わせるのが自然という見立てがある（決定ではない）。

方向（2026-10-11、設計者。[パッケージ管理と WASM の設計案](sources/2026-10-11-package-wasm/memo.md)の「値の受け渡し」）: パッケージ管理と外部の関数の改造（TODO-211）では、Benitoite が今持つ型と WIT の型の共通部分だけを受け渡す（TODO-047）。WASM に合わせた新しい型は、構文の見直し（TODO-205）の改造で検討する。

加える場合に決めること:

- 型の間の変換
- 演算子の型の集まり（01-06「演算子の型付け」の規則の拡張）
- リテラルの書き方
- 型ごとの溢れの規則（`Integer` の溢れは実行時エラーである）
- 型の名前。省略しない名前の方針（ADR 0101）と、構文の見直しの可読性の基準（TODO-205）の両方で決める
