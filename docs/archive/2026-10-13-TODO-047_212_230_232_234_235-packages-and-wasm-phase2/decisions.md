### Q5 resource を受け渡す外部の関数のエフェクト

- 答え（2026-10-13）: `uses State` を付ける（調査 C の論点 4.2 の (A)）。対照として、resource を使わず照合ごとにパターンを渡す純粋な形（同 (D)）も作って測る。

### Q6 パッケージの中だけの公開の書き方

- 答え（2026-10-13）: `public(package)`（調査 C の論点 1.2 の (a)）。
- 理由: 予約語を増やさず（`package` は予約しない語）、三つの段階を「`public` の広さ」として一列に読める。語の選び直しは構文の見直し（docs/todo の TODO-205）で行う。

### Q7 速い経路の範囲と予算の数え方

- 答え（2026-10-13）: 宣言の型が `Integer`・`Float`・`String`・`Bytes` だけからなり、引数が 3 個までの関数を Wasmtime の型付きの呼び出しで呼ぶ。この経路では `Bytes` を受け渡しの予算で 1 バイトにつき 1 と数える。同じ大きさの `Bytes` でも関数の型で上限が変わることを受け入れ、03-10 に書く。
- 理由: 調査 B で、1 MiB の往復が動的な値の経路で 16.7 ms、型付きの呼び出しで約 40 µs だった。予算の数え方は Wasmtime の型付きの持ち上げの数え方に合わせる。

## 推す案どおりとした点

調査 C の「推す案どおりとしてよい点」を基に、オーケストレータが次のとおり決めた。

### R1 パッケージの中だけの公開の範囲と契約（TODO-234）

- 依存のパッケージでは、同じパッケージの根の下のモジュールを「パッケージの中」とする。パッケージでない根（入口のファイルとその根の下のモジュール）は、根の側全体を一つのパッケージとみなす。根では `public(package)` と `public` の見え方が同じになるが、誤りにしない。
- 段階を「非公開 < `public(package)` < `public`」と順序づけ、宣言の型（公開する契約）に現れる名前は、その宣言の段階以上でなければならない（Swift と同じ規則）。構成子・欄・メソッド・操作は包む宣言の段階を受け継ぐ。
- 括弧の中に書けるのは `package` だけとする。`public(crate)` などほかの語は、書ける語を示して誤りにする。
- `benitoite package` のエフェクトの集計は `public` の宣言だけを数える（R24 の「使う側から見える関数だけ」を保つ）。
- 理由: 調査 A の 4.2 のとおり、今のモジュールの識別だけで同じパッケージかを判定できる。Swift の規則は、契約の検査を二値から段階の大小に一般化するだけで済む。

### R2 インターフェースの関数の指し方（TODO-235）

- 第 3 引数に `#` があれば、最後の `#` で区切り、前半をコンポーネントの書き出し（インターフェース）の名前、後半をその中の名前とする。`#` がなければ、今のとおり world の直下を引く。
- インターフェースの名前は、版を含めて文字列の完全一致を求める。Wasmtime の名前の引き方は semver で互換な版も通す（調査 B 1.3）ので、それに頼らず、コンポーネントの書き出しを列挙して照合する。照合の誤りでは、書き出しの名前の一覧（インターフェースの中の関数は `名前#関数` の形）を示す。
- WIT から `@external` の宣言を作る道具は今回入れない。照合の誤りの診断で、期待する宣言の型を示す。
- 理由: `#` は WIT の名前の文字に含まれないので、区切りとして一意に決まる。宣言より古い版が通る照合は、宣言の契約の検査として緩すぎる。

### R3 レコードと直和型の照合（TODO-047）

- 型の名前は照合せず、構造で照合する（Wasmtime の型の API が record の名前を返さない）。
- 欄と場合の名前は、WIT の名前から `-` を除いたものと Benitoite の名前を、英字の大小を無視して比べる（例: `byte-start` と `byteStart`）。一つの record・variant の中で、比べた結果が二つ以上に当たる名前は誤りとする。欄の順も一致を求める。
- 引数が 0 個か 1 個の構成子だけの `data` を `variant` に照合し、引数のない構成子だけの `data` を `enum` か `variant` に照合する。引数が 2 個以上の構成子、型パラメータを持つ型、再帰する型は誤りとする。
- `Map` と `map<K, V>`、`flags`、幅の違う整数は今回入れない。
- 理由: 調査 C は Benitoite の名前から kebab-case を作って比べる案を推したが、略語（`HTTPError` など）の区切り方で規則が増える。`-` を除いて大小を無視して比べる規則は、作る側の名前の付け方に依らず一つに決まり、利用者と LLM が覚えやすい。順の一致を求めておけば、後で緩めても互換性を壊さない。

### R4 resource の宣言と照合

- resource に当たる型を `@external("wasm", "パス", "インターフェース#resource の名前") type 名前` で宣言する（`=` と右辺のない `type`）。型パラメータは持てない。値は中身を見せない値で、等値の型ではない。
- 関数は第 3 引数に `インターフェース#[constructor]R`・`#[method]R.名前`・`#[static]R.名前` などの名前を書く。メソッドの最初の引数は宣言した型で、WIT の `borrow<R>` と照合する。
- 引数の位置の resource は `borrow<R>` だけを受け付け、`own<R>` の引数は誤りとする。戻り値の位置は `own<R>` だけを受け付ける。
- 型に resource の型を含む外部の関数は `uses State` を書かなければならない（Q5）。書けるのは `State` だけで、resource の型を含まない外部の関数には今のとおり `uses` を書けない。
- 理由: `own` の引数は、渡した後の Benitoite の値を使えなくする仕組み（作った後に変えない中身を見せない値と合わない）を要する。`Regex` と `Json` の検証には借りる形で足りる。

### R5 resource のインスタンスと解放

- 型に resource の型を含む外部の関数は、実行ごと・コンポーネントごとに一つの、状態を持つインスタンスで呼ぶ。resource の型を含まない関数は、今のとおり呼び出しごとにインスタンスを作る。
- 燃料・epoch の期限・受け渡しの予算は、呼び出しの前に設定し直して呼び出しごとのままにする。線形メモリの上限 64 MiB は、状態を持つインスタンスではその寿命の合計になる。上限の意味の違いを 03-10 に書く。
- resource の値が回収されたら、その番号を解放待ちの列に入れ、次にその状態を持つインスタンスへ入る前に `resource_drop` で片付ける。解放の時期は回収の時期に依存し、ゲストが共有の状態を持つ場合は結果が回収の時期に依存しうることを 03-10 に書く。明示の解放の関数は入れない。実行の終わりと中断では、実行系を捨てるだけでよい。
- 参照インタプリタは中身を見せない値を写せないので、resource を受け渡すプログラムを差分テストから除く。
- 理由: 調査 B で、resource を作り続けて捨てないとゲストの線形メモリが 100 MB に達した。列に入れて片付ければ、使い捨ての resource を多く作るプログラムが上限に当たりにくい。取り込みのないゲストの後始末は外部に作用しないので、時期が決まらなくても外部から観測できる違いは結果と消費量に限られる。

### R6 速い経路の詳細（TODO-230）

- 型付きの呼び出しを使うのは、引数が 0〜3 個で、引数と戻り値の型がそれぞれ `Integer`・`Float`・`String`・`Bytes`（WIT の `s64`・`f64`・`string`・`list<u8>`）のどれかの関数である。戻り値のない関数は含めない。ほかの関数は今の動的な値の経路で呼ぶ。
- 速い経路でも、引数と戻り値の大きさの上限（文字列・`Bytes` は 2^30 バイト）、UTF-8 の確かめ、燃料・メモリ・epoch の扱いは動的な値の経路と同じにする。
- 理由: 調査 B で、この組み合わせ（340 通り）を具体化しても実行ファイルの増分は約 0.8 MB だった。`ComponentType` を自前で実装するには `unsafe impl` が要り、規約に合わない。

### R7 検証のためのパッケージと測定のプログラム（TODO-212）

- `Hash`・`Regex`・`Json` の WASM の版（C）と、Benitoite で書いた `Json`（B）は、例の Fuzzy と同じ形でゴールデンテストの下のパッケージとして置く。Rust のソースと作り方を README に書き、ビルド済みの `.wasm` を置く。処理系の Unofficial のモジュールは置き換えない。
- `Regex` の C は、resource の形（`compile`・`isMatch`・`find`・`findAll`・`replaceAll`）と、照合ごとにパターンを渡す純粋な形（`isMatch`・`findAll`）の二つを作る。`Match` は resource にせず record にする。
- `Json` の C は、越え方 1（文字列から文字列: 検証と整形）、越え方 2（平らな節点の表を返し、Benitoite の側で `Json.Value` に組み直す）、越え方 3（文書を resource で持ち、JSON Pointer で指した値だけを読む）を作る。
- `Json` の B は `parse`・`stringify`・`stringifyPretty` を、A（今の Unofficial の `Json`）と同じ結果を返すように書く。
- 測定のプログラムと入力の生成は `tools/bench/` に置き、10 MB の入力をリポジトリに置かない。三つの実装が同じ入力に同じ結果を返すことを、ゴールデンテストで確かめる。
- 理由: 調査 C の論点 6。Q5 で (A) を採ったので、越え方 3 も作る。

### R8 V1〜V3 の事前点検で決めた細部

V1〜V3 の事前点検（`reviews/preflight-V1V3.md`）が挙げた点を、推す答えどおりとした。

- 標準ライブラリのレコードと `data`（`Json.ParseError` など）も、R3 の制限の中で外部の関数に渡せる。理由: 利用者の型と区別する理由がなく、V6 で使う。
- R2 の「期待する宣言の型を示す」は、引数の数・型・戻り値の照合の誤り（E1007〜E1009）の注記にする。WIT の型の中に Benitoite の型へ逆に引けないものが一つでもあれば、注記を付けない。
- 同じパッケージの中の非公開の名前を引いたときの修正案（E0330）は、今のとおり `public` を挿入する案とする。理由: 既存の出力を変えない。`public(package)` を示す案は、構文の見直しのときに見直す。
- `_` を含む Benitoite の欄の名前は、WIT の名前（`_` を含められない）に一致しないので照合の誤りになる。R3 の帰結として受け入れる。
- R2 の理由の補足: 検査で使うコンポーネントの型の `get_export` はもともと完全一致で引く。semver で互換な版を通すのは、実行時の索引の引き方（`get_export_index`）である。実行時も照合で決めた完全な名前で引く。

### R9 `public` と `(package)` の間の改行（V1 のレビューの M2）

- `public` と `(package)` の間の改行を許す（レビューの案 (a)）。01-02 の「改行は置けない」と、構文解析器がソースの文字列で改行を確かめる処理を除く。`public(package)` の後の改行は、`)` の後の改行として区切りになるので誤りのままとし、その旨を 01-02 に一文で書く。
- 理由: 01-01 の「改行による区切り」の規則 2 は `public` の直後の改行を空白として扱うので、許すほうが章どうしで一貫する。`(` で始まる宣言はないので曖昧さは生じない。

### Q9 型の表示のための `TyNames` の欄（V4・V5 の事前点検）

- 答え（2026-10-13）: 欄を足す。`TyNames`（凍結の 10-05）に束縛の表を引く欄を足し、外部の型の名前を診断で示す。
- 理由: 型の表示は利用者の型の名前を型の表からしか引けない。外部の型を構成子のない利用者の型として型の表に載せる代わりの形は、「型の宣言は少なくとも一つの構成子を持つ」前提を例外で破る。

### R10 V4・V5 の事前点検で決めた細部

V4・V5 の事前点検（`reviews/preflight-V4V5.md`）が挙げた点を、推す答えどおりとした。

- 設計書では、WIT の resource に当たる Benitoite の型を「外部の型」（external type）と呼ぶ。01-10 の「リソースの型」と取り違えないためである。00-04 用語集に加える。
- 外部の型の値の大きさ（回収の契機に使う値の大きさ）に、その値を作った呼び出しで増えたゲストの線形メモリの量を含める。理由: ゲストのメモリはヒープの大きさに現れないので、確保の少ないループでは回収が起きず、解放待ちの列（R5）が働かないまま 64 MiB の上限に当たりうる。副作用として、ヒープの統計の最大値にゲストのメモリの一部が入る。この扱いを 02-09 に書く。
- 外部の型を型に含まない `[static]` の関数は、R5 のとおり呼び出しごとのインスタンスで呼ぶので、状態を持つインスタンスの状態を見られない。このことを 03-10 に書く。
- 外部の型の宣言は `ResolveOutput` に欄を足さず、既存の外部の宣言の表に入れる。
- `uses` の検査は、構文解析の段に「`State` 以外の `uses`」の検査だけを残し、外部の型を含むかで決まる検査（`uses State` がない誤りなど）は照合の段で行う。構文解析の段では、引数の型が外部の型かを決められないためである。

### Q10 debug のビルドでの Regex のコンポーネントのコンパイルの時間

- 問い: 試作の Regex のコンポーネント（926 KB）は、debug のビルドの処理系で検査一回に約 9 秒かかった（2026-10-13 にオーケストレータが測った。Json の試作は約 0.9 秒）。ゴールデンの一件は検査と実行を何度も行うので、10 秒の上限を超える。
- 答え（2026-10-13）: ワークスペースの `Cargo.toml` の `[profile.dev.package]` で、Cranelift と Wasmtime のクレートだけ `opt-level` を上げる。入れた後に測り、それでも 10 秒を超えるなら、Regex の C のゴールデンを長いテスト（`#[ignore = "long: ..."]`）に回す。
- 理由: 外部の関数のテスト全体が速くなり、Regex の C を普通のゴールデンで確かめられる見込みがある。debug の最初のビルドが少し伸びる。

### Q11 WASM のゲストに組み込んだクレートの著作権表示

- 答え（2026-10-13）: ゲストのパッケージごとに、組み込んだクレートの名前・版・使用許諾と、著作権表示・使用許諾の本文を置くファイル（THIRD-PARTY の表示）を置く。
- 理由: ビルド済みの `.wasm` はリポジトリとソースのアーカイブに含まれて配られるので、MIT などが求める著作権表示を添える。

### R11 V6 を三つに分ける（V6・V7 の事前点検）

V6・V7 の事前点検（`reviews/preflight-V6V7.md`）の推すとおり、V6 を V6a（三つのゲストと C のパッケージ、A と C の同じ結果のゴールデン）、V6b（Json の B と、A と B の同じ結果のゴールデン）、V6c（測定のプログラムと道具、A・B・C を比べるゴールデン）に分ける。点検が挙げた細部（試作の WIT の直し、A の Rust のコードをゲストに写して依存の版を本体に揃えること、`.wasm` にリポジトリの外のパスを埋め込まないこと、測定の大きさの改め、置き場所）は、補足の推す形どおりとする。Json の B で A と合わせにくい点（誤りの位置と文言、浮動小数点数の書式）は、正しい入力では完全な一致を求め、残りは既知の違いとして報告に書く。

### Q12 外部の関数の上限を利用者が変えられるようにするか

- 問い（2026-10-13、設計者）: WASM 側のメモリの上限 64 MiB を、プログラムの引数で小さくしたり大きくしたりできるか。
- 答え（2026-10-13）: フェーズ 2 の残りで対応し、測定で必要なら上限を変えられるようにする。作業 V6d として加える。細部は R12。

### R12 外部の関数の上限を変える引数（Q12）

- 実行する利用者が決める。`benitoite run` と `benitoite test` に、外部の関数の上限を変える引数を足す: 線形メモリ（`--wasm-memory`）、燃料（`--wasm-fuel`）、受け渡しの予算（`--wasm-transfer`）。既定の値は今のまま（64 MiB、10^10、256 MiB）とする。
- 大きさは `KiB`・`MiB`・`GiB` の単位つきか、バイト数で書く。範囲は、線形メモリと受け渡しの予算が 1 MiB 以上 4 GiB 以下、燃料が 1 以上とし、範囲の外は実行の前の誤りにする。
- 値の意味は今の上限と同じにする（線形メモリは一回の呼び出しの合計、状態を持つインスタンスでは寿命の合計。燃料と受け渡しの予算は一回の呼び出しごと）。
- パッケージが要る大きさを `package.bnt` に申告する仕組みと、実行の前に示す情報に上限を含めることは、今回入れず docs/todo の項目にする。
- 理由: 上限は信頼しない WASM から実行する機械を守るためのものなので、最終的に決めるのは実行する利用者である。小さくする向きは安全側で、テストで上限に当たる振る舞いを確かめるのにも使える。測定で Json の大きな入力を C で比べるには、線形メモリと受け渡しの予算の両方を変えられる必要がある。

### Q13 上限の引数のための `Command` の欄

### Q14 上限と消費量の記録

### R13 外部の関数の消費量の報告（Q14）

- `benitoite run` と `benitoite test` に、外部の関数の消費量の報告を出す引数（`--wasm-stats`）を足す。指定したときだけ、実行の終わりに標準エラー出力へ、機械で読める形（JSON の一行）で次を出す。指定しないときの出力は変えない。
  - 設定した上限（線形メモリ・燃料・受け渡しの予算。既定の値か引数で変えた値か）。
  - 外部の関数の呼び出しの回数（関数ごとと合計）。
  - 消費量の最大と合計: 一回の呼び出しで使った燃料、一回の呼び出し（状態を持つインスタンスでは寿命）の線形メモリの最大の大きさ、一回の呼び出しの受け渡しの量（引数と戻り値を分ける）。状態を持つインスタンスは、インスタンスごとの寿命の線形メモリの最大も出す。
  - 上限に達して止まった場合は、どの上限か。
- 受け渡しの量は、処理系が数える引数の側と、Wasmtime が数える戻り値の側（hostcall fuel の残りから求める。Wasmtime 49.0.2 で残りを読めない場合は、戻り値を変換するときに処理系が同じ規則で数える）を合わせる。数え方を 03-10 に書く。
- `tools/bench/wasm_bench.py` は、測定ごとに設定した上限と `--wasm-stats` の報告を結果に記録する。
- 理由: 上限の既定の値を、実際の消費量の分布から決められるようにする。報告は引数を指定したときだけ出すので、普段の出力とゴールデンを変えない。

### R14 戻り値の受け渡しの量の数え方の範囲（V6d の報告とレビュー）

- Wasmtime 49.0.2 は、受け渡しの予算（hostcall fuel）の残りを読む API を持たない（`Store::hostcall_fuel()` は最後に設定した値を返す）。このため、`--wasm-stats` の戻り値の受け渡しの量は、R13 の代わりの方法として処理系が数える。数え方は Wasmtime の持ち上げの規則に合わせるが、文字列は UTF-8 のバイト数で数えるので、UTF-16 の文字列を使うゲストでは Wasmtime の実際の消費量と一致しない。この違いを 03-10 とリファレンスに書いた形で受け入れる。持ち上げが失敗した呼び出しは `incomplete_calls` に数え、合計と最大に推測の値を加えない。
- 理由: 今回作ったゲストはどれも Rust と wit-bindgen の UTF-8 の文字列を使い、測定に影響しない。UTF-16 のゲスト（JavaScript など）を扱うのは、他の言語の例（docs/todo の TODO-236）の段階である。そのときに数え方を見直す項目を docs/todo に加える。
