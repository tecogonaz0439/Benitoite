# 実装プラン

作業は直列に進める。どの作業も、メインの作業ディレクトリで作業ごとのブランチ（`mod/<作業>`）の上で Codex（GPT-6.1-Sol、high）が実装し、終えたらすぐ `san_benito` に取り込む。作業を渡す前に、作業の文書を Opus のサブエージェントが点検する（事前点検。補足は `reviews/preflight-*.md`）。レビュー（Opus）は取り込んだコミットを `git show` で読み、直しは後のコミットで行う。作業ごとには関係するテスト・clippy・fmt だけを走らせ、`scripts/check.sh` は最後に一度だけ行う。

各作業の根拠は `decisions.md`（Q1〜Q8、R1〜R7）と `study/` の調査（A 処理系、B WASM の実行系と試作、C 決めること）である。調査と `decisions.md` が違うときは、`decisions.md` を正とする。調査 B の試作のソース（Wasmtime のホストの試し、Hash・Regex・Json のゲスト）は、オーケストレータの作業場所にある。作業 V6 で要るものは、その作業の指示に場所を書く。

## 作業 V1: パッケージの中だけの公開（Q6、R1）

1. 構文: `public(package)` を宣言の前に書ける（`public` を書ける位置すべて）。括弧の中に `package` 以外を書いたら、書ける語を示して誤りにする。`implement` の前では `public` と同じく誤り。整形器は `public(package)` をそのまま出す。
2. 名前解決: 束縛に段階（非公開・パッケージの中・公開）を持たせる。構成子・欄・メソッド・操作は包む宣言の段階を受け継ぐ。ほかのモジュールの名前を引くとき、同じパッケージ（R1。調査 A 4.2 の判定）なら `public(package)` と `public` の名前を、違えば `public` の名前だけを引く。見えない名前の診断（E0330 の系）は、`public(package)` の名前を別のパッケージから引いたときに、その旨（パッケージの中だけで公開されている）を示す。
3. 公開する契約の検査（E0329 の系）を段階の大小に広げる（R1）。`public(package)` の宣言の契約も集める。
4. `benitoite package` のエフェクトの集計は `public` だけを数える（R1）。標準ライブラリの文書の生成（`skill/generate.rs`）は `public` だけを載せる。
5. 設計書: 01-02（宣言の構文）、01-03「公開（初回リリース版）」（三つの段階、範囲、契約。契約の規則は今「同じモジュールの型」に限った書き方なので、同じパッケージの別のモジュールの `public(package)` の型を `public` の宣言が使う場合も誤りになるよう書き直す）、02-04（束縛と表、宣言の検査、名前の引き方、誤りと修正案）、06-09（エフェクトの集計）、02-10（診断を足したら）。言語リファレンスの 12 節「Modules」。
6. テスト: 同じパッケージの別のモジュールから引ける・別のパッケージから引けない・根の側では引ける（ゴールデン。依存のパッケージは `testdata/packages/` の形に倣う）、契約の検査の三段階、括弧の中の誤りの語、整形の往復、エフェクトの集計から除かれること。

## 作業 V4: 大きな `Bytes` の速い経路（Q7、R6）

1. 照合のときに、関数が速い経路の型の組み合わせ（R6）に当たるかを決め、変換表に印を持たせる。
2. 実行: 速い経路の関数は Wasmtime の型付きの呼び出し（`TypedFunc`）で呼ぶ。組み合わせごとの具体化は宣言のマクロか生成で書き、手で 340 通りを並べない。燃料・メモリの上限・epoch・中断・失敗の分類は今の経路と同じにする。
3. 予算: 速い経路では `Bytes` を 1 バイトにつき 1 と数える（引数は処理系が数え、戻り値は Wasmtime が数える。調査 B 4.3）。今の 256 MiB の値は変えない。

5. 設計書: 03-10「実行」の予算の説明（関数の型で上限が変わること）、02-09「外部の関数の実行」。
6. テスト: 速い経路と動的な値の経路が同じ結果を返すこと（`Integer`・`Float`・`String`・`Bytes` の組み合わせのいくつか）、速い経路で 10 MiB 程度の `Bytes` を往復できること（今の経路では予算を超える大きさ）、速い経路での大きさの上限・燃料の失敗・中断。

## 作業 V5: resource（Q5、R4・R5）

V2（インターフェース）と V3（照合の変換表）の後に行う。

1. 構文と名前解決: `@external("wasm", パス, 名前) type 名前` を受け付ける（R4。右辺のない `type`。`@external` のない右辺のない `type` は今のとおり誤り）。型パラメータは誤り。`public` と `public(package)` を付けられる。束縛と型の構成子に resource の型を加える（凍結の表）。等値・順序・`Show` などの型クラスは持たない（今の `Regex.Pattern` と同じ扱いにする。表示が要る箇所はそれに倣う）。
2. 照合: resource の型の宣言は、インターフェースの中の resource の書き出しに照合する。関数の `[constructor]`・`[method]`・`[static]` の名前を引けるようにし、引数の `borrow<R>`・戻り値の `own<R>` と宣言の resource の型を、同じ resource（同じコンポーネントの同じ書き出し）であることまで照合する。`own<R>` の引数は誤り（R4）。型に resource の型を含む外部の関数は `uses State` を書かなければ誤り、`State` 以外を書いたら誤り、resource の型を含まない外部の関数に `uses` を書いたら今のとおり誤り（R4。今の E0812 の検査の場所を確かめて改める）。脱糖で、resource の型を含む外部の関数のエフェクトを `State` にする。
3. 実行: 実行ごとの外部の関数の実行系に、コンポーネントごとに一つの状態を持つ `Store` とインスタンスを、初めて要るときに作って持たせる（R5）。呼び出しの前に燃料・epoch の期限・受け渡しの予算を設定し直す。resource の値は中身を見せない値で、その状態を持つインスタンスの中の番号だけを持ち、言語の値を実行系に置かない（02-08「外部の関数の実行系」の約束）。
4. 解放: 値が回収されたら番号を解放待ちの列に入れ、次にその状態を持つインスタンスへ入る前に片付ける（R5）。列は実行系と値で共有してよいが、大域の状態にしない。gc-stress の構成でも結果が変わらないことをテストで確かめる。
5. 参照インタプリタ: resource を受け渡すプログラムは、処理系の不具合ではなく「参照インタプリタでは扱わない」ことが分かる形で止め、差分テストから除く（R5）。
6. 設計書: 03-10（resource の宣言・照合・実行・解放・上限の意味）、01-07「外部の関数のエフェクト」（`State`）、02-08・02-09（実行ごとの状態、外部の関数の実行）、07-01 の保証の表、言語リファレンスの 21 節。01-02 の宣言の構文（右辺のない `type`）。
7. テスト: `testdata/external/` に、resource を作り・メソッドを呼び・回収で片付けるコンポーネント（状態を持つインスタンスでの呼び出しで、resource をまたいで状態が残ることを確かめる）を `.wat` か小さな Rust のゲストで加える。各誤り（`uses State` がない・ほかのエフェクト・`own` の引数・違う resource・型パラメータ）、解放待ちの列で線形メモリの上限に当たらないこと（resource を多く作って捨てるループ）。
