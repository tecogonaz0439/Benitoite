## 結論

段2（T1〜T3）は、型・効果・診断順・辞書・番号を変えていない。コードで確かめたのは次の点である。

## 中

### 中1 const 由来の推移的な集合が二乗で膨らみ、64 MiB の予算の外にある

- ファイル: `crates/benitoite/src/typeck/consts.rs` 113〜116 行（`consts::check`）、1275〜1281 行（`eval_name`）。`typeck/checked_args.rs` 92 行・232 行（補助位置の出力）。
- 問題: K2 は、トップレベルの const の評価を `EvalBudget::traced()` に切り替えた。各 const について、参照先の由来をすべて含む推移的な `BTreeSet<BindingId>` を `d.const_origins` に保存する。由来の集合を作り写す処理は、`charge` も `slots` も通らない。そのため、`const c1: Integer = c0 + 1`、`const c2: Integer = c1 + 1`、… と N 個の const が連鎖すると、保存する要素の総数は N(N+1)/2 になり、作る時間も同じ程度かかる。この経路は Regex・Scope を使わないプログラムを含む、すべてのプログラムの const 検査で通る。
- 根拠: 02-05 と 01-06 は、定数の評価に掛かる検査時の資源を 64 MiB の予算で抑えると定める。ソースの上限は `MAX_SOURCE_BYTES = 256 MiB` であり、連鎖の長さを抑えるものはない。`eval_name` は評価済みの値を引くだけで再帰しないため、深さの上限にも掛からない。例えば 2 万個の連鎖（ソース約 640 KB）では約 2 億要素になり、BTreeSet の節点の分を含めて数 GB の確保になると見積もる（未計測）。また、その連鎖の末端の const を E0457 の引数に使うと、補助位置の「constant declared here」が N 個並ぶ。
- 修正案: const ごとに保存するのは、直接参照した const の集合だけにする。推移的な閉包は、診断を出す時点で、訪問済みの集合を持つ明示の積み重ねで求める。補助位置は、引数が直接参照した const と、連鎖の起点（値の出どころ）の数件に限り、残りの数を note に回す。この場合は 01-06・02-05 の「補助位置は参照したconstとその参照先の宣言」の書き方も合わせて直す。少なくとも、由来の集合を作り写す処理を `EvalBudget` で数える。直したら、長い連鎖の検査時間と確保量を確かめる測定かテストを足す。長いテストにするかは 07-03 に従う。
- 設計者に確認: 補助位置に推移的な由来をどこまで示すか（全部・直接だけ・上限付き）。

### 中2 「opaque type」の語が、用語集の「中身を見せない prelude の型」と衝突している

- ファイル: `docs/design/00-overview/00-04-glossary.md` 215 行、`docs/design/01-spec/01-06-type-system.md` 26 行と 323 行、`docs/reference/benitoite.md` 500 行・788 行以降、`docs/design/03-interop/03-06-stdlib.md`（Scope・Range の節）、D/design.md 2.1。
- 問題: 用語集は「opaque type」を「構成子を公開せず、パターンで分解できない prelude の型。等値の型ではない」と定義している。一方、今回の `@opaque` の型（design 2.1 の「中身を宣言モジュールへ隠す型（opaque type）」）は通常の名目型であり、内部構造が等値の型なら等値の型になる（01-06 323 行）。英語リファレンスの 500 行は、等値の型を「関数の型と opaque type を含まない型」と説明したままである。そのため、788 行以降で `@opaque` を読んだ利用者や LLM は、`CheckedInteger` を `=` で比べられないと読みうる。
- 根拠: AGENTS.md「文章の規範」は、章をまたいで同じ概念に別の語を使わないこと、および用語集の定義に揃えることを定める。レビューの観点の 1（章どうしの整合）にも当たる。
- 修正案: 用語集に `@opaque` の型の項目を加え、既存の項目と語を分ける。例えば、日本語は「作り方を隠す型」、英語は「opaque representation」または「`@opaque` type」とし、既存の項目に「`@opaque` の型とは別」と書き添える。リファレンス 500 行の「no opaque type」は、「no built-in opaque type such as `IOError` …」のように、既存の組み込みの型だけを指す語へ改める。01-06 の 26 行の表と 323 行の語も揃える。日本語訳（docs/ja）は V1 で揃える。
- 設計者に確認: 新しい概念の正式な日本語名と英語名。

### 中3 Regex の組み立て予算がソースのバイト数だけを数え、組み立ての手間を抑えていない

- ファイル: `crates/benitoite/src/typeck/checked_args.rs` 11〜57 行（`REGEX_PATTERN_BYTES`・`REGEX_TOTAL_BYTES`・`CheckedArgsState::regex`）。
- 問題: 暫定の上限（R101。一パターン 1 MiB・全体 8 MiB のソース長）は、組み立てるソースのバイト数を数える。ところが、`\w{1000}` のように数バイトのソースでも、regex の組み立てはコンパイル済みの大きさの上限（10 MiB）に達するまで働く。全体 8 MiB の範囲で、異なる短いパターン（`\w{1000}a1`、`\w{1000}a2`、…）を数十万件並べられる。その場合、各件が上限近くまで組み立ててから E0458 を返し、`check` の時間が呼び出しの数に対して大きく増える（未計測）。実行時なら実行した呼び出しだけが組み立てられるが、静的検査は到達しない分岐の中の呼び出しも組み立てる。
- 根拠: design 5.1 と 02-05 は、取得と組み立ての予算を、検査時の資源を抑えるために設けている。静的検査の健全性（拒否の判定は実行時と一致させる）を保つには、静的だけ size_limit を小さくはできない。そのため、手間の抑制は件数か費用の見積もりで行うことになる。
- 修正案: 組み立ての回数に上限を設ける（例: 一検査で異なるソース 256 件まで。超えたら Unknown）。または、一回の組み立てに最低の費用（例: 64 KiB 相当）を全体 8 MiB の予算へ課す。いずれの場合も、上限を超えたら実行時へ残す（Unknown）という今の意味を保つ。直す前に、短いソースで E0458 に達する組み立ての時間を一件だけ測り、見込みを確かめるのがよい。
- 設計者に確認: R101 の暫定値を、件数の上限か最低の費用で補うか。

### 軽4 Scope の Show で、表示を切り詰めた位置がエスケープの途中になりうる

- 修正案: 現状のままでよい。直すなら、外側の切り詰めでは構成子の名前と括弧を残し、各引数の表示の長さを先に割り当てる。直さない場合は、03-06 に「切り詰めはエスケープの途中でも起こる」と一文書く。

### 軽5 T3 の待ち行列は実際には毎巡すべてを再投入しており、索引による削減は重複の照合だけである

- ファイル: `crates/benitoite/src/typeck/solve.rs` 1832〜1962 行、02-05 の「効果の伝播は登録番号の待ち行列で行い」の段落。

## 観点ごとの確認の結果（指摘なし）

### T

- T1: `BodyNodeMap`・`BodyBindingMap` は BTreeMap で、get・insert・iter の意味（未登録の番号は None、番号の昇順での走査）は旧来の密な表と同じである。全体の出力の `TypeckOutput` は、密な表のまま残している。
- T2: 入口の `zonk` が型の上限に掛かると Error になり、Unit を返す。これは旧実装の根での失敗と同じ結果である。正規化済みの子を再び zonk せず、潜在効果だけを `finalize_effect` の各 Fail で正規化する。Rust の再帰は旧来からあり、`#[inline(never)]` を付けて枠を変えた（release_stack は T2 で通過済み）。
- T3: `EffectConstraintKey` は次を、前置順の列に種類と子の数を付けて写している。
  - 型と効果の全構成子
  - `IContract`、`EffectSet`、`EffInfer`、Fail の列
  - `Reason` の全欄（`ReasonKind` の判別子と、全部の引数付きの変種の値）
  - 型の対の有無

  したがって、derive した `PartialEq` と同じ等号になる。Debug の表示は鍵にしていない。`self.effects` を変えるのは push と `solve_effects` の取り出しだけであり、索引の消去はその取り出しと一緒に行う。巡の途中で `equal` が加える制約は、旧実装と同じく次の巡の Fail の処理から入る。上位クラスの道筋の記憶は、本体ごとの Solver に閉じている。比較の状態（map.patch・solve.patch とハッシュ）も保存してある。
- 深い入れ子: 索引のキーは明示の積み重ねで作る。追加の訪問（`visit_block`）と評価（`eval`）は AST の再帰であり、規約の範囲内である。

### K1

`reject_opaque` は、次の三つの入口で、解決後の束縛から親の型（`Ctor.data`・`Field.record`・Record 自身）を引き、所有元のモジュールと比べる。

- `checked_name` の Value・Ctor・Record の位置
- `record_call_name`
- パターン（shadow.rs が `name` を通る）

このため、次の迂回はどれも親の型の所有元で判定される。

- 型の別名・import の別名
- 値化・部分適用・穴・パイプ
- 構築・更新・レコードパターン・構成子パターン
- 自動アクセサ

テストは、二つの import の形のそれぞれで 18 例を確かめている。型の別名による構築は、従来どおり拒否される。公開関数の E0329、全構成子の表、網羅性の判定は保たれている。Lean の Checked/Access.lean の判定（所有元が一致するときだけ内部を使える）とも一致する。derive は軽2 のとおり G1 に残る。

### K2・K3

- 対象: `CallPlan.direct_callee` は、名前による直接呼び出しで、挿入も穴もない場合に限る。標準の束縛の同定は `consts::std_call` の解決済みの ID で行い、綴りでは照合しない。
- 予算: 64 MiB は `CheckedArgsState` で全本体に共有し、本体ごとに作り直していない（テストあり）。トップレベルの const と警告の予算は別である。
- Regex: 静的検査と実行時は同じ `checked_regex::compile` を使い、失敗は構造化した `regex::Error` の種類で分類する。
- Scope: `checked_scope` の判定順は、パターン → 対象 → 下端 → 上端 → 端点の順序 → port → ホスト所属 → ポート所属であり、既知の部分だけを調べる。どの静的拒否も、未知の引数がどの値でも実行時には同じ失敗か先行する失敗になるので、必ず Error を返す。
- 位置: 一次位置・補助位置は design 5.3 と一致する。
- 既存の例の移行: l40-regex.bnt と regex/tests.rs は、動的な引数を通す形に移し、観察する Error・理由の非空・出力をそのまま保っている。共有入力には、旧来の 4 入力をすべて残して `[` を足した。テストは弱まっていない。

### K3・K4

- Scope: 保存（ホストは小文字化、パスは字面のまま、Endpoint は入力した整数のまま）、根と `/**` の特例、要素の境界、IPv4 形式の拒否、0 と 65535・一点区間は、Lean の Scope.lean の Valid* と Matches の各定義、および生成の順序に対応する。
- Range: 逆転を先に返し、上端に 1 を足さずに比較する。Integer の両極を golden で確かめている。Range.lean の `make` と一致する。
- 保証の限界: 許可・DNS・実ファイル・IO の成功を保証しないことは、01-06・03-06・リファレンス・Skill に書いてある。

### 規約

追加したコードについて、次を確かめた。

- panic・unwrap・添字の禁止を守っている（テストのモジュールを除く）。
- 文言は `text` のモジュールと診断の表に置いている。`Stop::Internal` の説明は、規約の例外に当たる。
- 大域の状態を加えていない。Solver の RefCell は実例ごとにある。
- コメントは設計書の節を引き、作業の ID を引いていない。
