### TODO-142 操作の対象の範囲を型で表す案

- 状態: 未着手
- 旧: OPEN-052
- 出どころ: [open-issues の OPEN-052](../2026-10-09-design-first-release/open-issues.md#open-052)（2026-10-01 の追記）、[08-03「他の言語の調査記録」](../2026-10-09-design-first-release/08-appendix/08-03-language-surveys.md)の「権限の対象の範囲を型や値で表す仕組み」「AI エージェントの権限制御の研究」、[ADR 0117](../2026-10-09-design-first-release/decisions/0117-capabilities-as-effects.md)

現在の方針では、実行の前の判定は `main` の型のエフェクトで行うが、エフェクトは対象（ホスト、ポート、パス）を持たないので、対象の範囲は方針の側にしか書けない。範囲を関数の型に書ければ、範囲を超える操作を実行の前に型の誤りとして報告でき（設計原則 1）、範囲の変更を関数の契約の変更として示せる（設計原則 2）。候補は次の三つである。

- エフェクトに範囲の引数を持たせる（`Net.Https["*.example.com"]`、`Net.Tcp["db.internal", 5432..5439]`、`File.Write["/data/reports/**"]` など）。エフェクトの包含は範囲の包含になる。範囲をホスト名のパターン・ポートの範囲・パスのパターンのような限られた形に限れば、包含は有限の手順で判定でき、依存型は要らない。
- 範囲の検査を通った値だけが持てる中身を見せない型（`AllowedHost`・`AllowedPath` など）を設け、操作の関数はその型の値を受け取る。範囲の判定は実行時の検査の関数が行う。
- 許可された範囲を表すケーパビリティの値（根のディレクトリのハンドルなど）を通してだけ操作する。ケーパビリティの値を設けないとした ADR 0117 の見直しになる。

一つ目と二つ目は組み合わせられる（対象が定数なら型で、実行時に決まる値なら検査の関数を通して扱う）。検討するときは次を決める。

- 対象が実行時に計算した文字列のとき、型の誤りにするか、検査の関数を通すことを求めるか。
- 範囲の書き方と包含の規則。パスは許可したパスの照合（ADR 0072、OPEN-057 の確認）と同じ規則で `..` とシンボリックリンクの扱いを含めて定め、ホストはネットワークの操作の論点（別項「実行時の権限制御の方式の残りの論点」）と合わせる。
- 型に書いた範囲と方針の関係。型の範囲を方針で許可を求める範囲として利用者に示し、実行時の権限制御と OS のサンドボックスはその範囲と方針の共通部分を強制する、などの形がある。
- エフェクト変数、エフェクトの宣言とハンドラ、高階関数の型との関係。
- 形式化への影響。エフェクトの原子に引数を加え、包含を範囲の包含に置き換える拡張になる見込みである（別項「性質 1（脱糖の型の保存）の形式化と、形式化の範囲の見直し」）。

試作の結果（2026-10-17。sources/2026-10-17-feasibility-spikes/142/）: 推す判断は「設計を変えて進める」。
- 方針（2026-10-17、設計者）: 試作の推す範囲から始める。
- 制限した範囲のパターン（ホスト・パスのパターン、ポートの区間）の包含の判定は、健全性と完全性まで Lean で証明できた。エフェクトの和、行の具体化、代入の合成とのつなぎも、小さなモデルでは通った。
- 一方、二つの反例が出た。一つの原子ずつ被覆を判定すると、区間を分けた和による包含を取りこぼす。また、互いに包含し合う範囲の集合は、整列と重複の除去だけでは同じ正規形にならない。
- 第一案（エフェクトに範囲を持たせる）を全体につなぐと、Lean は 28〜65 時間、処理系は 34〜80 時間かかる見込み。和による包含の完全な判定まで求めると、それぞれ 20〜50 時間・12〜30 時間増える。
- 推す範囲: 最初は第二案（検査済みの値の型）と、定数の表層の検査に絞る。Lean は 2〜6 時間、処理系は 8〜20 時間の見込みで、Release の層を変えない。第一案は後で別に判断する。
- 0.0.8 の表し方 B は、閉じた範囲の定数を原子として足す土台に使える。ただし、意味の包含から型の等号を得る部分は流用できない。
- サーバモード（TODO-256）とは、権限の判定の正しさの形式化でつながる。

### TODO-026 正規表現の構文を検査の時点で確かめるか

- 状態: 未着手
- 旧: OPEN-062
- 出どころ: [open-issues の OPEN-062](../2026-10-09-design-first-release/open-issues.md#open-062)（R08）、[ADR 0316](../2026-10-09-design-first-release/decisions/0316-no-compile-time-regex-check-in-first-release.md)、2026-10-11 の言語の方向のメモ（docs/todo の sources/2026-10-11-language-direction/memo.md）

初回リリース版の処理系は、検査の時点で正規表現の構文を確かめない。`Regex.compile(r"[")` は、引数が文字列リテラルや定数式でも、実行時に `Result.Error` を返す（ADR 0316）。これは設計原則 1 に対する、正規表現の構文についてだけの例外として ADR に記した。理由は、検査の段と標準ライブラリの個々の関数（非公式のモジュール `Benitoite.Regex`）との結び付きを初回リリース版ではできるだけ少なくするためである。標準ライブラリを見直すときに結び付きを加える判断をすることは妨げない（ADR 0316 の決定 3）。診断コード E0444 は欠番として残し、ほかの誤りに転用しない。

見直すときの選択肢（ADR 0316 で検討したもの）:

- 名前解決で `Regex.compile` を指す名前を直接書いた呼び出しの引数が定数式なら、検査の段で組み立てる。値として渡した呼び出しは調べない。型検査器が名前と組み立ての設定を知るので、モジュールを改めるたびに合わせて直す費用がかかる。
- lint の道具として別に置く。検査の段からは切り離せるが、道具が一つ増え、見直しの費用は残る。
- 正規表現のリテラルの構文を加える。構文解析の時点で確かめられるが、書き方が二つになり（原則 5）、構文が標準ライブラリの型を直接作る。

方向（2026-10-11、設計者）: 他の関数型言語の扱いと比べてから決める。

### TODO-022 篩型（値の範囲を型で表す）

- 状態: 方針あり
- 出どころ: [ADR 0146](../2026-10-09-design-first-release/decisions/0146-runtime-errors-not-in-types.md)の「検討した代替案」、2026-10-11 の言語の方向のメモ（docs/todo の sources/2026-10-11-language-direction/memo.md）

初回リリース版では、関数の型はその関数が実行時エラーを起こしうるかを表さず、実行時エラーはプロセスを異常終了させる（ADR 0146、ADR 0064）。値の範囲を型で表して、実行時エラーを起こさないことを実行の前に証明する篩型（refinement types）は、形式検証の題材であり初回リリース版の範囲を大きく超えるとして、ロードマップの将来拡張に残した。初回リリース版の時点では、採るかどうかも、どの実行時エラー（整数の溢れ、0 による除算、定義域の外の引数など）を対象にするかも検討していなかった。

方向（2026-10-11、設計者）: 実装する方向で検討する。

検討の範囲の案（メモの Claude の所見。確かめていない事実を含む）:

- 篩型の検査は型システムの一部なので、「言語の中核は自作する」の方針（00-01「目的の衝突」）に当たる。SMT ソルバ（Z3 など）を外部の OSS として使うかが最初の分かれ目になる。
- 範囲の案は、(a) 整数の区間や長さなど決定可能な小さな断片を自前で解く、(b) Liquid Haskell のように SMT ソルバに任せる、(c) 先に実行時に確かめる契約（値を作る関数で範囲を確かめる smart constructor）として入れ、静的な検査を後から足す、の三つである。
- どの実行時エラー（整数の溢れ、0 による除算、添字の範囲）を対象にするかを合わせて決める。
- 形式化（`formal/`）に響く。

試作の結果（2026-10-17。sources/2026-10-17-feasibility-spikes/022/）: 推す判断は「設計を変えて進める」。
- 方針（2026-10-17、設計者）: 試作の推す範囲から始める。
- 推す範囲: 最初は、範囲を実行時に確かめて `Option`・`Result` を返す API と、その小さな意味の証明に限る（Lean 4〜12 時間・処理系 6〜20 時間）。静的な区間の解析は後から足す。
- 整数の区間と長さの包含、部分型の健全性、加算、定数との比較による if の絞り込み、途中のすべての値を確かめた場合のあふれのなさは、小さなモデルで証明できた（5 ファイル・69 定理）。
- 値に依存する `n` を入れると、束縛・置換・範囲の管理が主な難所になる。Release に部分型を直接足すと、「関数でない型の包含は等号」という既存の補題も組み直しになる（Lean 32〜80 時間・処理系 40〜100 時間）。
- SMT の結果を信用する方式と、証明書を検査する方式を区別した。小さな証明書の検査器の健全性は通った。ただし、`2x = 1` のような整数の上の矛盾は扱えないことも示した。
- smart constructor には、公開の範囲の制約がある。今の公開の data・record は作り方も公開するので、包みだけでは不変条件を守れない。

### TODO-164 型構成子の部分適用と、Result を Monad として扱うこと

- 状態: 未着手
- 出どころ: [01-06 型システム](../2026-10-09-design-first-release/01-spec/01-06-type-system.md)の「高カインド型（初回リリース版）」、[03-06 標準ライブラリ](../2026-10-09-design-first-release/03-interop/03-06-stdlib.md)の「標準の型クラス（初回リリース版）」、[ADR 0059](../2026-10-09-design-first-release/decisions/0059-higher-kinded-traits-without-prelude-monad.md)、[ADR 0134](../2026-10-09-design-first-release/decisions/0134-standard-type-classes.md)の「検討した代替案」、2026-10-11 の言語の方向のメモ（docs/todo の sources/2026-10-11-language-direction/memo.md）

初回リリース版の高カインド型では、型構成子を表す型パラメータ（`F[_]`、`F[_, _]` など）は `_` の個数だけ型引数をとる型構成子を表し、型クラスの引数と関数の型パラメータにだけ書ける（今の 01-06「高カインド型（初回リリース版）」）。型構成子を書く位置では、型構成子がとる型引数の個数が型パラメータの個数と一致しなければならず、型の部分適用はない。そのため、型引数を二つとる `Result[T, X]` は `Trait.Functor`・`Trait.Monad` などを実装できない（今の 03-06「標準の型クラス（初回リリース版）」）。ADR 0134 は、`Result` の片方の引数を固定して `Functor` などを実装する案を、型の部分適用か型の関数が要り、型推論の規則が大きく増えるとして退けた。設計者は、採るかを決めずに検討の対象に加えた（2026-10-09）。

検討すること:

1. 型構成子の部分適用。`Result` の誤りの型を固定した型構成子（たとえば `Result[_, String]` のような書き方）を、`F[_]` の位置に書けるようにするか。書き方、どちらの引数を固定できるか（Haskell の `Either e` は先頭の引数を固定する。`Result[T, X]` は値の型が先にあるので、そのままでは誤りの型を固定できない）、型の別名や型の関数を設けるかを比べる。
2. 型引数を二つ以上とる型構成子を表す型パラメータ（`F[_, _]` など）で、すでにできることを確かめたうえで残る論点。初回リリース版の実装は、構文解析で `_` の個数を数え、型検査で個数の一致を照らし、推論で `F[A, B]` と `D[B1, B2]` を個数が一致するときに等しくする。テストが確かめているのは、関数の型パラメータに `F[_, _]` を宣言した関数の構文解析と、`F[_, _]` に型引数を一つとる型構成子の型クラス（`trait Container[F[_]]`）の制約を付けたときの誤り（E0427）までである。`trait Bifunctor[F[_, _]]` の宣言、`implement Bifunctor[Result]`、`[F: Bifunctor]` の制約を持つ関数からのメソッドの呼び出しが、型検査・辞書渡し・実行まで通ることを確かめるテストはない。2026-10-09 に、`trait Bifunctor[F[_, _]]` を宣言して `implement Bifunctor[Result]` を書き、制約 `[F[_, _]: Bifunctor]` を持つ関数から `Bifunctor.bimap` を呼ぶスクリプトを `benitoite run` で実行し、`Result.Ok` と `Result.Error` のどちらの値も期待どおりに写されることを確かめた（ゴールデンテストにはしていない）。残る作業は、この形をゴールデンテストに加えることである。そのうえで、`Bifunctor` のような型クラスを標準ライブラリ（`Benitoite.Trait`）に入れるかを検討する。
3. `Result` を `Trait.Monad` として扱うこと。1 を採ったときに、標準ライブラリで `Result` に `Trait.Functor`・`Trait.Monad` などを実装するか。既存の `try`（01-09「`Result.Error` と `Option.None` を呼び出し元へ返す構文 `try`」）と `Result` の関数との役割の重なり（原則 5。TODO-021 と同じ論点）をどう扱うか。

前提・制約:

- 推論の規則は、`F[A]` と `D[B1, ..., Bn]` を等しくするときに、型引数の個数の一致を求めている。部分適用を入れると、どの引数を `F` に含めるかの選び方が増え、型の誤りの診断が分かりにくくなりうる（原則 1・4）。LLM が書く普通のスクリプトには高カインド型が現れないという見込み（ADR 0059）も、判断の材料にする。
- 形式検証の段階 B2 は、型の種類を検査しない広い型付けで、高カインド型を含む型クラスの辞書について性質 2・3 を証明した（07-04）。拡張するときは、Lean の定義（`formal/`）と 01-12 の写しの変更の要否を確かめる。
- 型検査器（02-05）、脱糖と辞書渡し（02-06）、標準ライブラリの型クラス（03-06）、Skill の文書の生成物に響く。

方向（2026-10-11、設計者）: 採る方向で検討する。状態を「方針あり」に改めるかは、書き方を決めた時点で判断する。TODO-021 で重複する関数を隠さないと決めたので、3 の `try` と `Monad` の重なりは障害になりにくい。書き方の候補は、1 の `Result[_, X]` のような穴あきの型か、型の別名による固定である（メモの Claude の所見。比べていない）。

試作の結果（2026-10-17。sources/2026-10-17-feasibility-spikes/164/）: 推す判断は「設計を変えて進める」。
- 方針（2026-10-17、設計者）: 型引数を二つとる型構成子のための型クラス（仮の名前 `Monad2[F[_, _]]`。誤りの型 E を各関数の型パラメータとして持ち回る）をライブラリに置く方向で検討する。型構成子の部分適用は採らず、型の規則と Release の層を変えない。名前は設計のときに決める。TypeScript の fp-ts が、部分適用のない言語で型引数の数ごとに `Monad1`・`Monad2` などを分けている前例を参考にする（確かめていない記憶による）。既存の一引数の `Trait.Monad` 向けの汎用の関数へ `Result` を渡せないことと、同じ役割の型クラスが二つ並ぶこと（設計原則 5）は、設計のときに扱いを決める。
- 推す範囲: 最初は、成功の側に明示した穴を一つだけ置く部分適用（`Result[_, E]` に当たる形）に絞る。束縛を増やさない小さなモデルで、適用と代入・ずらす操作の交換を Lean で証明できた。
- 一般の型ラムダは、閉じた小さなモデルでは正規化できた。ただし、比較の成功から得られるのは正規形どうしの等号である。自由な高カインドの変数や、正式なモデルへのつなぎは確かめていない。見積もりは Lean 80〜200 時間・処理系 64〜160 時間で、初段には含めない。
- 誤りの型を先に置く別名だけでは、Monad として扱うことには届かない。Release の層を保つなら、二引数の `Monad2[Result]` か、閉じた誤りの型専用の包みが候補（Lean 2〜8 時間・処理系 4〜16 時間）。
- 穴一つの部分適用は、Lean も処理系も 24〜64 時間の見込み。
- TODO-189 の辞書渡しは、部分適用の問題を解かない。0.0.8 の正規形の基盤も、β 簡約の証明までは代わりにならない。
- 透明な別名に別々の Monad の実装を許すと、辞書の選び方で結果が変わる例がある。実装の重なりの規則が要る。

### TODO-021 標準の型クラスと重複する既存の関数の、同梱の Skill で推す書き方

- 状態: 方針あり
- 旧: OPEN-050
- 出どころ: [open-issues の OPEN-050](../2026-10-09-design-first-release/open-issues.md#open-050)、[01-06 型システム](../2026-10-09-design-first-release/01-spec/01-06-type-system.md)の「型クラス（初回リリース版）」、[ADR 0134](../2026-10-09-design-first-release/decisions/0134-standard-type-classes.md)、2026-10-11 の言語の方向のメモ（docs/todo の sources/2026-10-11-language-direction/memo.md）

標準の型クラス（`Benitoite.Trait`）のメソッドは、既存の関数と同じ役割を持つ（`Trait.Functor.map` と `Option.map`・`List.map`、`Trait.Foldable.fold` と `List.fold`、`Trait.Semigroup.combine` と `List.concatenate` など）。この重複は、設計者が辞書渡しを学ぶために、原則 5（同じ役割の構文を、必要な理由なく増やさない）の例外として認めた（ADR 0134）。ADR 0134 は、初回リリース版を実装した後に評価して、重複する既存の関数を隠す（利用者から見えなくする、または非推奨にする）かを決めるとしていた。

### TODO-248 関数内に閉じた文字列・リスト・バイト列の構築器

- 状態: 方針あり
- 出どころ: 2026-10-14 の設計者との相談と、独立した TODO として追加する依頼

文字列・リスト・バイト列を繰り返し構築する処理の高速化のため、関数内だけで使える可変の構築器を追加する方向で検討する。仮の型名は `StringBuilder`、`ListBuilder[T]`、`BytesBuilder` とし、完成した値をそれぞれ `String`、`List[T]`、`Bytes` として取り出す。型名、操作の名前、宣言の表記は、設計時に決める。

決めた方針:

- 構築器への追記は内部の状態を変更する。同じ局所名を繰り返し束縛し直す必要はなく、構築器を指す名前は一回の束縛で使える。
- 通常の値を取り出すときはコピーする。取り出した後も構築器を使え、その後の追記によって、先に取り出した文字列・リスト・バイト列の内容は変化しない。構築器を消費してバッファの所有権を渡す方式は採用しない。
- リストのコピーは、要素を保持する構造をコピーする。要素の再帰的な複製はしない。不変の要素は共有でき、要素が `Reference[T]` なら同じセルを参照する。そのセルの操作の `State` は、構築器の局所状態と区別する。
- 構築器は、その関数の呼び出しの中で作り、使う。利用者が定義する関数の引数・戻り値として構築器を受け渡さず、関数の外へ持ち出せないよう静的に検査する。追記や取り出しの専用操作には渡せる。
- 構築器への局所的な状態操作を、関数の外側のエフェクトに残さない設計を第一候補とする。局所状態の隔離とエフェクトを除く規則を十分に設計・検証できない場合は、構築器の操作に `State` を付けて提供する。保証を弱めてエフェクトだけを省略しない。

設計・検証する点:

- 外へ持ち出す経路の検査。構築器を直接返す場合のほか、リスト・レコード・可変セルへの格納、ラムダ・遅延への捕捉、タスクへの受け渡し、ハンドラと継続を通じた持ち出しを扱う。構築器を含む値も検査し、型注釈を省略した場合や型パラメータを経由した場合にも制約を保つ。
- 関数内のラムダで構築器を使える条件。利用者が定義する別の関数への受け渡しを禁じる範囲と、専用操作に渡せる範囲を明確にする。`ListBuilder[T]` に別の構築器など局所状態を含む要素を格納する場合も扱う。
- 局所状態を識別する型とエフェクトの規則。構築器の状態だけを除き、通常の `Reference` や外部操作のエフェクトは残す。現在の `State` を一括で除く方式にはしない。利用者に寿命の注釈を求めるかも含め、文法と推論を設計する。
- 作成、容量の予約、要素・断片の追加、長さの取得、コピーによる取り出しの操作の範囲。文字列の UTF-8 の不変条件、バイト列の扱い、リストの要素の型を定める。
- バッファの容量の増やし方、確保の前の大きさの検査、整数のオーバーフロー、回収の根と書き込みの障壁、早期リターン・停止・取り消しの際の解放。既存の値の大きさの上限を、複数回の追記で迂回できないようにする。
- 多数の小さな断片を追加する場合の処理時間と確保量、短い構築での費用、コピーして取り出す費用を三種類ごとに測る。リストの既存の永続データ構造や、一括で組み立てる既存の操作と比較する。高速化の効果は測定前に断定しない。

改造を始めるときは、型とエフェクト、標準ライブラリ、ヒープと VM、診断、必要なテスト、設計書・リファレンス・同梱の Skill の更新を実装プランに含める。形式化した範囲との対応は 07-04「01-12 との対応」に従い、範囲の内側なら処理系より先に Lean の定義と必要な証明を直し、範囲の外側なら対象外として記録する。性能の測定はスキル `benchmark` に従う。

関連: TODO-247（名前付き引数、束縛は原則一回という文書の推奨）。構築器の追加は TODO-247 とは別の改造として扱う。

試作の結果（2026-10-17。sources/2026-10-17-feasibility-spikes/248/）: 推す判断は「設計を変えて進める」。
- 方針（2026-10-17、設計者）: 試作の推す範囲から始める。
- 構築器を普通の型・値と分けた局所の文脈で扱えば、寿命や領域の型変数なしで、局所の操作だけをエフェクトから除く規則の健全性を小さなモデルで証明できた。取り出した値が、後の追記で変わらないことも確かめた。
- 次の三つには、Lean で反例を確かめた。普通の `State` まで一括で消す案、具体化の前の型だけを見る検査、関数の引数と戻り値だけを見る捕捉の検査。

### TODO-032 大きなスクリプトの検査の時間

- 状態: 要検証
- 旧: OPEN-009
- 出どころ: [open-issues の OPEN-009](../2026-10-09-design-first-release/open-issues.md#open-009)、[07-02 性能](../2026-10-09-design-first-release/07-quality/07-02-performance.md)（「測る項目」の検査にかかる時間）、[完了時の測定の記録](../../../tools/bench/results/2026-10-09-first-release-4304d507f6bf.md)（「起動と検査の内訳」「所見 2」）、later-issues の 11・22・118・F13（docs/todo の sources/later-issues.md）

約 1 万個の関数を並べて生成したスクリプトの `check` が約 1.1 秒かかった（最小実行版は約 17 ms）。何もしない `main` の検査は約 3.5 ms なので、差の約 1.08 秒は標準ライブラリの読み込みと検査だけの費用ではない。起動から終了までも約 8.6 ms（最小実行版は約 3.1 ms）に延びた。

最小実行版とは検査の規則とソースが違うので、この変化を同じ仕事の退行とは断定できない。検査の段（読み込み・字句解析・構文解析・名前解決・型検査）ごとの内訳を測り、規模に対して時間が線形を超えて増える処理がないかを調べる。初回リリース版はプログラム全体を毎回検査し直す（ADR 0156。「インクリメンタルな検査」の項目）。

規模に対して線形を超える処理として、初回リリース版の作業の確認で次のものが見つかっている。どれも分岐の数や連鎖の長さが大きい入力で現れるもので、上の約 1.1 秒（関数の数が多い入力）の原因かどうかは確かめていない。

- 網羅性の判定が、リテラルの分岐の数 n に対して約 O(n³) になる（later-issues の 11）。`typeck/patterns.rs:192-247` の `shapes` は区間ごとに全リテラルを走査し、文字列の重複の除去も線形の探索（`patterns.rs:237-245`）である。990 分岐でリリースのビルドが 0.27 秒と計測済みで、絶対値は小さい。次の事項とあわせて、予算を設けるか計算量を改めるかを決める。
- 網羅性の検査と判定の木への変換が、分岐の数に対して指数的に増える（later-issues の 118）。`typeck/patterns.rs` の網羅性の検査は 16 本の分岐で 9.9 秒かかり、40 本では終わらない。`ir/decision.rs` の判定の木への変換は 24 本で 4 GiB を超える。どちらにも予算や上限がない。予算を設け、超えたら診断か処理系の制限として止める。
- コード生成の自由変数の走査が、長い `let` の連鎖で O(N²) になる可能性がある（later-issues の 22。推測で、測っていない）。`bytecode/codegen/analysis.rs:211-215` の `with_reads` と `captured`、`emit.rs:216-222` が、残りの本体を毎回 `free_keys` で走査する。自由変数の集合を下から一度だけ求める案がある。コード生成は上の検査の段に含まれないので、測るときは段を分けて測る。
- 関数の数に対して、検査の時間が二乗で伸びる（2026-10-18、0.0.8 の最後の本測定。`tools/bench/results/2026-10-18-1c545d8f5c5d.md` の所見 2）。関数を一つずつ並べたスクリプトで、2,500 で 0.06 秒、5,000 で 0.19 秒、10,000 で 0.68 秒、20,000 で 2.62 秒だった（リリースのビルド）。プロファイルでは、`typeck/context.rs` の `Body::finish`・`Body::check_type_limits` と、`NodeMap`（`base/mod.rs`。全体の節の番号を添字にする密な表）の `resize_with`・解放が大半を占める。後ろの関数ほど本体ごとの表が大きくなるためと見ている（確かめていない）。本体ごとに番号を詰めるか、疎な表にする案がある。上の約 1.1 秒の主な原因の候補である。
- コア IR の検査（`ir/check.rs`）が、子を検査するたびに `Env`（複数の `BTreeMap` を持つ。`check.rs:49-57`）を丸ごと clone する（`check.rs:448,597,662,1040,1134`）ので、長い `let` の連なりで O(n²) になる（later-issues の F13）。`check_program` を呼ぶのはテストの補助（`ir/desugar.rs:372`）だけなので、本番の検査の時間には影響せず、テストの時間だけに影響する。テストの時間の問題として残すか、可変の表と巻き戻しの形に改めるかを決める。
