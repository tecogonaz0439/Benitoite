# T1の比較状態

`map.patch` は開始版 `95378554353786cab7b323336937ced204d036c7` に適用する、032だけの処理系と02-05の差分である。`map-state.json` に基準、パッチ・比較用ソース・記録・Cargo.lockのSHA-256、Rust/Cargoの版を固定した。後のT2/T3でこのパッチと記録を上書きしない。開始版とoldの公開版 `6b0568a3ddcc46b0a0e64504139ce286a27fd86a` の間には、Cargo.toml・Cargo.lock・crates/の差分がない。

`probe.rs` は公開の読み込み・名前解決・型検査を通し、拒否例でも返るTypeckOutputの全欄と診断の列を保存する。成功例では脱糖コアを保存し、独立したIR検査器を通す。加えて公開パイプラインからCLI形式の診断を保存し、実際の診断順・英語文面・元位置も比較する。全体のNodeId/BindingId、型、効果、NoFail、辞書、呼び出しの対応、節の情報を比較に含む。

`compare.py` は生成する5例と既存の14例を両状態で実行する。old/mapの各JSONは入力と出力のSHA-256、番号数、拒否コード、型検査の局所時間を保存する。11成功例と8拒否例の計19例、68ファイルのハッシュが一致した。全体の型表は密なままなので、欠番の位置も比較される。

本体内の疎な表の走査は、登録された要素だけを辿る。関数の位置に応じた先行番号の空き領域を持たず、Scopeのcloneも存在するパラメータだけを複製する。一つの本体に128/512局所束縛を持つ例では、番号を詰める代案へ戻す必要のある費用増加は観測しなかった。

| 入力 | oldの型検査（ms） | mapの型検査（ms） |
|---|---:|---:|
| 32関数 | 53.878 | 20.324 |
| 128関数 | 151.476 | 22.647 |
| 一つの本体、128局所束縛 | 63.529 | 17.660 |
| 一つの本体、512局所束縛 | 85.710 | 22.336 |

この時間はdebugの単一標本による局所確認であり、読み込み・名前解決・出力整形を含まない。標準ライブラリの型検査は含む。oldの取得中には別のビルドの負荷もあったため、速度の倍率やR17/R19/R22の合否には使わない。静かな計算機で行う改造末のrelease本測定、段別プロファイル、最大RSSは後の担当へ残す。

比較を再実行するときは、次の順とする。コマンドはリポジトリの根から実行し、`T1_DOCS` は本ディレクトリ、`T1_BASE` は上記の開始版とする。

1. `git archive "$T1_BASE" Cargo.toml Cargo.lock LICENSE-MIT LICENSE-APACHE crates docs/design/02-impl/02-05-typechecker.md` を、oldとmap用の別々の一時ディレクトリへ展開する。map用だけに `git apply --directory=<展開先> "$T1_DOCS/map.patch"` を適用する。今回の展開物に対する `git apply --check` は成功した。
2. それぞれ `cargo build -p benitoite --lib --manifest-path <展開先>/Cargo.toml --target-dir <状態別のビルド先>` を実行する。二つの展開物で同じtargetを使うとCargoが成果物を再利用するため、再現時はビルド先を分ける。
3. `rustc --edition=2024 "$T1_DOCS/probe.rs" --extern benitoite=<ビルド先>/debug/libbenitoite.rlib -L dependency=<ビルド先>/debug/deps -o <probeの実行ファイル>` で状態ごとの比較器を作る。本番の処理系には差し込み口を加えない。
4. `python3 -B "$T1_DOCS/compare.py" <oldのprobe> old`、続いて同じ指定で `<mapのprobe> map` を実行する。既定の保存先はtarget/t1であり、既存の状態JSONがあれば上書きを拒否する。別の再実行には両状態に同じ `--root target/t1-replay` を指定できるが、生成例の診断ファイル名もそのパスになる。

後のsolve比較では、固定したold.jsonをtarget/t1/old.jsonへ置き、同じ入力パスで `compare.py <solveのprobe> solve` を実行できる。全形式化比較はT1では実行していない。

テスト作成時の関門は次のように適用した。比較の境界は公開の型検査の出力と診断、脱糖コアである。疎な表の番号・欠番・昇順・Scopeの保持の誤りがあれば比較が失敗する。既存テストは個別の期待値を守る一方、TypeckOutput全欄の変更前後の一致までは保存しないため、この改造の比較資料として補った。公開範囲や本番用のフラグは増やしていない。既存テストのassert・期待値・ignore指定は変更せず、同じ契約の恒久的な単体テストも追加しなかった。
