# T2の比較資料

基準B_WORKは `f0e6c71d29cbc8704093dcf5c355469ad50c4381` であり、T1のmap状態の取り込み直後である。T1の比較器・固定corpus・map.patchと記録は変更しない。T3のsolve状態の保存と全形式化比較は後の担当へ残す。

`compare.py` は公開の読み込み・名前解決・型検査・脱糖を通すT1の `probe.rs` を使う。深さ8/16/32/64の `T0=String, T(d+1)=Option[Td]` を生成し、Fail[Td]と、引数・戻り値・潜在FailのすべてにTdを持つ関数型のFailを別々に検査する。8例はいずれも既存の上限内で受理される。既存goldenから8例を加え、単一Fail/NoFail・未確定の失敗型・剛な型の脱出・関数型の失敗値の契約を比較する。拒否コードの期待は既存のdiag.jsonから読み、順序を含めて一致を要求する。成功例では独立したIR検査器も通す。

T1の `compare.py` も別の保存先で使い、関数・局所束縛・lambda・節・複数モジュール・辞書の19例を比較する。型出力の全欄、全体番号と欠番、型・効果・NoFail・辞書・呼び出しの対応、診断列、CLI診断の文面と位置、コアのファイル全体のSHA-256を照合する。T2の16例と共有19例の記録は `deep-comparison.json`・`shared-map.json`・`shared-t2.json` に保存する。共有記録のラベルold/solveはT1比較器の引数名であり、このディレクトリでは変更前map/変更後T2を意味する。T3完了時のsolve状態ではない。

`count.py` と `count_probe.rs` は訪問節数の実験用である。基準から一時ディレクトリへソースを展開し、変更後だけsolve.rsを作業ツリーの版で置き換える。展開物のzonk入口、zonkのVisit/Count、型の確定の訪問にだけ計数を挿入する。本番のコードにフラグ・公開API・可変の計数器を加えない。展開物のlibテストの一件だけを実行し、深さ系列8例と、未知型・エラー回復・型パラメータ・剛な型・未確定/パラメータの型構成子・未知の契約名の7例を比較する。実ソースのOption入力とは分け、計数では固定の束縛番号の単項ADTを使って同じ形の型を作る。潜在効果では直接のFail・固定集合のFail・推論行のFailを合わせ、同じ型の重複除去と行番号も比較する。各状態の型の確定結果は `counts-map.json`・`counts-t2.json` にそのまま保存する。

この計数は実装の費用を調べるための資料であり、非公開の関数の呼び出し方を固定する恒久的な単体テストにはしない。型検査時間を性能目標の判定には使わない。潜在Failを入れ子にした関数型に対するzonkの上限計数の反復はR157に記したとおり残る。

| 深さ | 単一の型のzonk訪問節数（map → T2） | 関数型のzonk訪問節数（map → T2） | T2の確定の訪問節数（単一／関数型） |
|---|---:|---:|---:|
| 8 | 45 → 9 | 177 → 41 | 9／31 |
| 16 | 153 → 17 | 533 → 73 | 17／55 |
| 32 | 561 → 33 | 1821 → 137 | 33／103 |
| 64 | 2145 → 65 | 6701 → 265 | 65／199 |

単一の型のT2のzonk入口は深さによらず1回、関数型は4回であった。後者は外側の関数型と、潜在効果の直接・固定集合・推論行の3つのFailの入口である。両系列の型の確定結果と7つの回復/境界例はすべて変更前と一致した。型の上限は変更していない。

再現する場合はリポジトリの根から実行する。`T2_DOCS` は本ディレクトリとする。

1. 変更前mapは基準からCargo.toml・Cargo.lock・LICENSE-MIT・LICENSE-APACHE・cratesを一時ディレクトリへ展開し、`cargo build -p benitoite --lib --manifest-path <mapの展開先>/Cargo.toml --target-dir <map専用target>` で作る。変更後T2は作業ツリーから `cargo build -p benitoite --lib` で作る。異なるソースのビルド先を共用しない。
2. T1の `probe.rs` を、それぞれのlibへ `rustc --edition=2024 <D>/t1/probe.rs --extern benitoite=<状態別target>/debug/libbenitoite.rlib -L dependency=<状態別target>/debug/deps -o <比較器>` でリンクする。今回の変更前には既存の `target/t1/probe-map` を使い、既存のmap記録と固定入力の出力も照合した。
3. `python3 -B "$T2_DOCS/compare.py" <mapの比較器> <T2の比較器>` で深さ・拒否例を比較する。既定の入力パスはtarget/t2/deepである。
4. `python3 -B <D>/t1/compare.py <mapの比較器> old --root target/t2/shared`、続いて `<T2の比較器> solve` と同じ指定で共有corpusを比較する。既に記録がある場合は上書きを拒否するので、再実行には別の--rootを使う。CLIの元位置を含むため入力パスが変われば保存済みのハッシュも変わる。
5. `python3 -B "$T2_DOCS/count.py" map`、続いて同じ指定で `t2` を実行する。既定の保存先はtarget/t2/countであり、状態別のソース・ビルド先を使う。成功済みのJSONがあれば上書きを拒否する。新しい再実行には両状態で同じ別の--rootを指定する。各JSONに計数したsolve.rs・実験用RustソースのSHA-256、コマンド、終了状態、外側の時間を含む。

テスト作成時の関門では、受理/拒否・確定型と効果・診断・脱糖コアの一致を公開の段の境界で確かめる比較資料とした。関数の契約名や潜在Failを落とす変更、型変数の解決漏れ、既存NoFail/剛な型の拒否範囲の変化を捕まえる。既存の個別テストだけでは変更前後のTypeckOutput全欄の一致と、深さ別の処理回数までは保存しないため、その部分を補う。恒久的なテストの重複と、本番のテスト用APIは追加しない。既存assert・期待値・ignoreは変更しない。
