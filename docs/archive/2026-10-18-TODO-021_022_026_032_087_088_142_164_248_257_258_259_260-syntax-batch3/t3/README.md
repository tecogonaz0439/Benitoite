# T3の比較資料

B_WORKは `aa3c896449882906a3b12ddc52f99dc23a5b0496` である。T1のmap状態の保存物は変更しない。`solve.patch` はT1と同じ開始版 `95378554353786cab7b323336937ced204d036c7` に適用する、032と257だけの処理系・02-05の差分である。新しい公開APIや構築器は含めない。`solve-state.json` に基準、パッチ、関係する全ソース、Cargo.lock、比較記録のSHA-256とRust/Cargoの版を保存する。基準の展開物に対する `git apply --check` も成功した。後の測定ではこの保存物を上書きしない。

`compare.py` はT1の公開段の比較器 `probe.rs` を共有し、old・map・T2までの開始版・solveの四状態を同じ入力で比べる。小さな関数32/128個、一つの本体の128/512束縛、二箇所の誤ったreturn、既存の効果・Fail・NoFail・剛な型・節・辞書・複数モジュールの正負21例、局所交換用の3例、高階呼び出しと上位経路の8/32/128回の9例、計38例を使う。高階呼び出しはFailureのimportなし/ありを別系列とする。入力は `target/t3/compare/corpus/` へ決定的に生成する。既存goldenの静的な拒否コードを読み、順序も期待する。実行時のRコードは型検査の期待へ混ぜない。

`comparison.json` は入力と四状態の全出力のSHA-256、全体番号の数、拒否コード、型検査時間の単一標本を保持する。全状態で型表全欄・欠番・効果・NoFail・辞書の番号と捕捉・診断列・CLI形式の英語診断と元位置・脱糖コアが一致した。成功例では独立したIR検査も通す。このdebugの時間は出力の整形を含まない局所確認であり、R17/R19/R22の合否や性能倍率には使わない。

`key_probe.rs` は索引の構造キーと既存のPartialEqを比較する、独立した実験である。理由の全種類と全欄、推論型の種類、生の型/行/契約変数、関数の引数と戻り値、名前の順、Fail列と固定Fail列、型の対の有無を変える。156変種の24,336組で等号が一致し、153種類を通常のHashSetとハッシュを常に0にするHashSetの両方で区別した。`key-results.json` に件数を残す。キーの細部を固定する恒久的な単体テストにはせず、本番のAPIも広げない。

`count.py` は開始版を一時展開し、solve側だけ処理系の変更を写す。一時展開物のSolverにだけ本体ごとの計数を加え、既存の線形探索の比較回数、索引の参照回数、列全体から複製する制約数、一項ずつの複製数、上位経路の探索とキャッシュのヒットを記録する。各本体の値を合計し、標準ライブラリも含む一回の公開checkを数える。solveの実際の登録では、索引と旧Vec.containsの重複判定が一致することも検査する。この照合用containsの回数は計数へ入れず、時間も性能の判断に使わない。本番へ計数用の状態・API・フラグを追加しない。

計数の主な結果は次のとおりである。索引の参照回数には通常の包含制約の登録も含み、旧方式の比較回数とは一操作の費用が異なる。

| 入力 | 旧線形比較 → 索引参照 | 上位経路の探索（開始版 → solve） | キャッシュのヒット |
|---|---:|---:|---:|
| 高階8回、importなし | 2,793 → 607 | 0 → 0 | 0 |
| 高階32回、importなし | 14,313 → 751 | 0 → 0 | 0 |
| 高階128回、importなし | 198,633 → 1,327 | 0 → 0 | 0 |
| 高階128回、Failure importあり | 198,695 → 1,344 | 0 → 0 | 0 |
| 上位経路8回 | 2,299 → 591 | 13 → 6 | 7 |
| 上位経路32回 | 6,163 → 663 | 37 → 6 | 31 |
| 上位経路128回 | 67,699 → 951 | 133 → 6 | 127 |

全9例で索引と旧PartialEqの実際の登録の判定が一致した。Failureをimportした3例では列全体の複製で扱う81制約が、一項ずつの81回の複製になった。標準ライブラリを含む件数であり、Failを含まない本体の制約まで複製したという意味ではない。再処理する制約の数を減らす実験ではない。

効果の伝播は、一巡の開始時の登録番号を待ち行列に持ち、変化があれば全番号を登録順に再投入する。単一化が変更する型・契約名・Failの依存を捕捉する通知が現行にはないためであり、部分的な再処理の最適化は主張しない。Failの巡で扱う制約の総数も減らすとは主張しない。削減するのは全列を一度に複製する処理とその一時領域であり、一項ずつの複製は残る。

局所の実ソースは `crates/benitoite/tests/desugar_export/batch3/` に置く。高階呼び出し、同じ長さの上位経路と直接の制約の優先、メソッドの値化、Failの伝播/除去の3入力・9定義を既存の書き出しから五形式へ出す。各定義を対象内に保ち、独立IR検査も通す。大域の版切り替えはB3へ残し、この局所corpusだけを版12にする。六入口の結果と五形式のハッシュは `exchange-results.json` に保存する。L7の手書きの独立入力と旧版の拒否の11自己検査も成功した。全本番corpusの比較や最終manifestの再集計は実施していない。

再現はリポジトリの根で、次の順に行う。`D` は改造のディレクトリとする。

1. T1のREADMEに従ってold/mapを、B_WORKからT2までの開始版をビルドする。solveは上記の基準から必要なビルド入力を展開して `solve.patch` を適用するか、T3取り込み版からビルドする。各状態のtargetディレクトリは分ける。公開の比較器はT1の `probe.rs` を同じrustcで各libへリンクする。
2. `python3 -B "$D/t3/compare.py" --probe old=<old> --probe map=<map> --probe base=<開始版> --probe solve=<solve> --report <新しい比較記録>` を実行する。既存の記録への上書きは拒否する。別の入力先を使う場合は `--root` も四状態で共通にする。
3. `rustc --edition=2024 "$D/t3/key_probe.rs" --extern benitoite=<solveのlibbenitoite.rlib> -L dependency=<solveのdeps> -o <実行ファイル>` でキーの実験をビルドして実行する。キーのソースは作業ツリーの版を読む。
4. `python3 -B "$D/t3/count.py" base` と同じ指定の `solve` を実行する。生成した小入力が先に必要である。計数記録が既にあれば上書きを拒否する。再実験では記録と一時展開先を別の場所に変更し、元の記録を保つ。
5. 作業末のworkに含むdesugar_exportが `target/formal-batch3/t3/` へ一度書き出す。計画の二つのPython入口を、この同じ五形式へ実行する。PythonからCargoを起動しない。改造末の全比較は別に行う。

テスト作成時の関門は、公開の型検査・脱糖の出力と実ソースの交換を境界とした。番号や辞書の選択、reasonの混同、潜在効果の欠落、対象外への除外、空入力による偽の成功を捕まえる。通常workでは全件の形式化書き出しを実行しないため、その接続を短い実ソースで守る。恒久的な同じ契約の単体テストを各層へ重ねず、既存のassert・期待値・ignoreは変更していない。
