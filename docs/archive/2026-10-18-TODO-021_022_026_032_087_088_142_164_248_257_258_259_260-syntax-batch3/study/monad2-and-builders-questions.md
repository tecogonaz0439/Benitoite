# Result の Monad2 と関数内の構築器について設計者に尋ねる問い

2026-10-18、S2 の判断資料である。M1〜M10 は中心 B（docs/todo の TODO-164・021）、B1〜B12 は中心 D（TODO-248）の22問である。根拠と現行実装の位置は [調査](monad2-and-builders.md)、元の項目は [写し](../todo-items.md) にある。ここに示す名前とコードは提案であり、実行を確かめた現行仕様ではない。

推す組み合わせは全問の A である。回答があったことにはせず、設計者の判断後に decisions.md と plan.md へ移す。型構成子の部分適用を採らないこと、State を残して既存の Reference へ展開すること、局所エフェクト消去とネイティブの高速化を含めないことは今回の依頼の前提である。これを変更する案は0.0.9の追加の候補として扱わない。

## M1 二引数の型クラスの名前と最初の範囲

問い: `Functor2`・`Applicative2`・`Monad2` の三クラスを、一引数版と同じ階層で用意するか。

| 選択肢 | 内容 |
|---|---|
| A（推す案） | Functor2.map、Applicative2.pure/apply、Monad2.flatMap を追加する。後者ほど前者を上位クラスに持つ |
| B | Monad2 だけを追加し、pure と flatMap を直接のメソッドにする。map は普通の補助関数にする |
| C | BinaryFunctor・BinaryApplicative・BinaryMonad という名前で A の範囲を追加する |

推す案は A である。理由: fp-ts に引数の数ごとに分ける前例があり、現行の Functor・Applicative・Monad とメソッドの役割を揃えられる。map だけを要する関数が Monad2 全体を要求せずに済む。B は宣言を減らせるが、一引数版と異なる階層を説明する必要がある。Foldable2・Traversable2・Bifunctor・三引数以上の版は初版へ加えない。

## M2 置き場所と import

問い: 新しい三クラスも既存の `Benitoite.Trait` に置くか。

| 選択肢 | 内容 |
|---|---|
| A（推す案） | Benitoite.Trait に追加する。import が必要な現行の扱いを保つ |
| B | Benitoite.Trait2 の別モジュールに三クラスを置く |
| C | Monad2 の名前を prelude に入れ、明示的な import を不要にする |

推す案は A である。理由: 型クラスを探す場所を一つに保ち、`Trait.Monad2.flatMap` から既存版との対応が読める。既存の Monad を Monad1 へ改名する変更は含めない。B は導入の範囲を分けられるが、同じ役割の標準クラスが別モジュールへ分かれる。

## M3 保つ引数の位置と Result 以外への実装

問い: `F[A, X]` の第1引数を写し、第2引数 X を保つ汎用クラスとして公開するか。

| 選択肢 | 内容 |
|---|---|
| A（推す案） | 標準実装は Result から始める。利用者は自分の二引数の型に実装できる。X は各メソッドの型パラメータとする |
| B | クラスは Result 専用の内部部品にし、利用者の二引数の型には公開しない |
| C | 第1・第2の両方の位置を対象にする別クラス群を、この版で用意する |

推す案は A である。理由: 現行の `F[_, _]` を使い、特定の型名への特例を増やさずに目的を満たせる。成功型を先に置く利用者の Either 相当の型にも使える。エラー型が先の Either 相当の型には、そのまま実装できない。名前だけで引数順を入れ替える部分適用は追加しない。標準に Result と重複する Either 型も増やさない。

## M4 メソッドの意味とエラー型

問い: メソッドの名前・引数名を一引数版へ揃え、Result の apply は最初のエラーを返す意味にするか。

| 選択肢 | 内容 |
|---|---|
| A（推す案） | map(x, f)、pure(x)、apply(fs, x)、flatMap(x, f)。X を保ち、apply は fs の Error を優先し、次に x の Error、両方 Ok なら一度適用する |
| B | flatMap を既存 Result と同じ andThen という名前にし、それ以外は A とする |
| C | apply にはエラーの結合用の制約を求め、両方のエラーを集める |

推す案は A である。理由: クラスのメソッドは現行の Monad.flatMap と対応し、Result.andThen に実装を委ねられる。エラーの蓄積は同じ X に結合の意味を要求する別の契約である。異なる X を暗黙に混ぜず、必要なら mapError で型を揃える。引数式はソース順に評価し、失敗時に省くのは fs の中の関数の適用である。pure の結果型が決まらないときは型注釈で示す。

## M5 一引数の Monad と並ぶこと

問い: 既存の一引数版向けの汎用関数へ Result を渡せない制限を残し、重複を設計原則5の例外として記録するか。

| 選択肢 | 内容 |
|---|---|
| A（推す案） | 一引数版と二引数版を別の制約として保つ。型の規則を保って Result を扱うための例外とする |
| B | A に加え、閉じたエラー型ごとの一引数の包みを標準に複数用意する |
| C | クラスを公開せず Result の既存関数だけにとどめ、汎用化を次へ送る |

推す案は A である。理由: 型構成子の部分適用を避けるという今回の前提と両立する。`F[_]: Monad` の関数や Traversable の G に Result を渡せるようになったとは説明しない。B は包む・戻す操作と型名を増やす。C は範囲を減らせるが、設計者が求めた Result の二引数クラスによる抽象化を提供しない。

## M6 透明な別名と実装の重なり

問い: 別名のために独立した実装を選ばず、現行の一意な実装の規則を保つか。

| 選択肢 | 内容 |
|---|---|
| A（推す案） | 型引数を省いた別名を型構成子には渡せない。完全適用した別名は展開後の型で扱い、同じクラス・対象型構成子への重なる実装を拒否する |
| B | 透明な別名にも独立した実装の名前を与え、使用箇所の綴りで辞書を選ぶ |
| C | 特定モジュールからの import を優先し、複数実装から選べるようにする |

推す案は A である。理由: 同じ型なのに別の辞書の意味を選ぶ経路を増やさず、現行の孤立した実装と重複の拒否を保てる。別名へ実装を書けるようにする改造は今回の要件ではない。別の意味が必要なら、別の data 型とその実装を宣言する。試作の不適切な辞書の反例は、同じ辞書型だけでは意味の一致を得られないことを示している。

## M7 do 記法などの構文を増やすか

問い: Result をクラスで扱うための新しい構文を加えず、既存の呼び出し・lambda・try で提供するか。

| 選択肢 | 内容 |
|---|---|
| A（推す案） | do、Monad 用の新しい bind、専用演算子を加えない。裸の try と明示した処置の意味も保つ |
| B | 一引数と二引数の両方へ展開する do 記法を追加する |
| C | 現行の bind 文の意味を戻り値の型で切り替える |

推す案は A である。理由: ライブラリ追加で表せる範囲に留め、クラスの選択と制御を終える処置を区別できる。B・C は今回の前提を見直す案であり、採るなら別の構文・型・脱糖・形式化の設計が必要となる。Monad2 を追加しただけで既存 try を任意の利用者型へ一般化しない。

## M8 TODO-021 で Skill に推す書き方

問い: 具体的な型には既存関数、型を抽象化する関数には型クラスを推す使い分けにするか。

問い: 021 の初版の推奨は用途で決め、辞書渡しの同条件の比較を後の性能の判断材料にするか。

| 選択肢 | 内容 |
|---|---|

推す案は A である。理由: 現在の trait は別の計算を含むので C の因果を示せない。B は測定が判断の前提になるが、具体型と汎用の使い分けは速度が等しくても説明できる。測定を行うときは benchmark スキルに従い、同じ計算・入力・コールバック・構成で比べる。今回の調査では測らない。

## M10 Monad2 の形式化と法則の保証

問い: 既存の規則を保ち、二引数の辞書の接続を確認する範囲にするか。

| 選択肢 | 内容 |
|---|---|
| A（推す案） | 新しい Ty・型の等号・Release の規則は設けない。二引数の宣言・上位辞書・値化・実行と既存の検査を接続する。法則は純粋な Result の小さな意味の性質として区別する |
| B | 利用者の全 Monad2 実装に対し、三法則の証明を受理の条件にする |

推す案は A である。理由: 試作は本体を import しておらず、エフェクト付きのコールバックや本番の辞書の全経路を証明していない。一方で、法則を証明する言語機構は今回の目的に不要である。操作の高カインド引数は追加せず、0.0.8 の値の型に対する操作の辞書の規則を保つ。

## B1 構築器の型名と置き場所

問い: 三種類の名前を `StringBuilder`・`ListBuilder[T]`・`BytesBuilder` とし、同名の標準モジュールを import して使う形にするか。

| 選択肢 | 内容 |

| A（推す案） | Benitoite.StringBuilder・ListBuilder・BytesBuilder を明示的に import する。通常型とは別の局所の分類として扱う |
| B | 一つの Benitoite.Builder に、Builder.String・Builder.List[T]・Builder.Bytes をまとめる |
| C | String.Buffer・List.Buffer[T]・Bytes.Buffer を既存のモジュールの下へ加える |

推す案は A である。理由: TODO の仮名と前例に対応し、操作を名前から探せる。通常の Reference の別名として公開しない。S1 の作り方を隠す型は値の受け渡しを許すため、構築器の禁止規則を代用しない。prelude に新しい名前を増やさない。

## B2 宣言の表記と型注釈

問い: 明示した局所型と専用の new を組にした bind を使うか。

| 選択肢 | 内容 |
|---|---|
| A（推す案） | `bind b: StringBuilder <- StringBuilder.new()` 等に限る。ListBuilder[T] の T も注釈に書く。既存トークンを使い、専用の宣言として検査する |
| B | `builder b: String` 等の新しい宣言の文法と予約語を設ける |
| C | new の結果を普通に型推論し、後から構築器を含む型を調べる |

推す案は A である。理由: 通常値の多相な推論へ局所型を混ぜず、使える場所を宣言時に決められる。見た目が既存の bind でも、受理する意味と展開は新規なので Lean との対応が要る。new の値化・部分適用・別の関数からの戻り値、構築器名の別名束縛を認めない。import の別名は解決した専用の束縛で判断する。

## B3 最初に用意する操作

問い: 作成・一つまたはまとまりの追記・取り出し・長さの五操作に絞るか。

| 選択肢 | 内容 |
|---|---|
| A（推す案） | new・append・appendAll・copy と長さ。文字列は byteLength、リストとバイト列は length。予約・clear・finish は加えない |
| B | A に clear・reserve と容量の読み取りも加える |
| C | new・append・copy だけとし、まとまりの追記と長さを次へ送る |

推す案は A である。理由: 既存の不変値への展開で正直に提供できる範囲である。容量を持たない内部表現に reserve を設けても、ネイティブの予約と同じ約束はできない。appendAll は B8 の反復の制約を補う。

String の append は text: String、appendAll は texts: List[String]、List の append は value: T、appendAll は values: List[T]、Bytes の append は value: Byte、appendAll は bytes: Bytes とする。操作の戻り値は Unit とし、構築器自身を返す連鎖は設けない。文字列への任意のバイトの追記は受け付けず、UTF-8 の規則を保つ。

## B4 State を残す契約

問い: 読み取りも含め、全操作の State を関数の外へ残すことを API に明記するか。

| 選択肢 | 内容 |
|---|---|
| A（推す案） | new・追記・copy・長さのすべてに State を付ける。既存の通常の State も残す |
| B | 追記だけに State を付け、copy と長さの読み取りを純粋とする |
| C | 関数内でだけ使うことを根拠に、構築器の State を外側の型から省く |

推す案は A である。理由: copy と長さも、呼ぶ時点のセルの状態で結果が変わる。B は既存 Reference.get の契約と合わない。C は今回の前提を変更し、新しい隔離とエフェクト消去の証明を必要とするため、この版では選ばない。既存の純粋な構築を機械的に構築器へ移す推奨も行わない。

## B5 コピーによる取り出しと不変値の共有

問い: 0.0.9 は取り出し後の安定性を契約にし、不変値の共有を認めるか。

| 選択肢 | 内容 |
|---|---|
| A（推す案） | copy は取り出した値の構造上の内容が後の追記で変わらないことを約束する。初版の内部では不変値を共有してよい。物理コピーはネイティブ版の再検討へ残す |
| B | TODO の「構造をコピーする」を物理コピーの必須条件とし、取り出すたびに文字列・リスト構造・バイト列を複製する |
| C | 構築器を消費する finish に変更し、取り出した後は使えなくする |

推す案は A である。理由: セルを別の不変値へ置き換える実装なら、取り出した値の安定性を全体の物理コピーなしで保てる。これは TODO の原文をそのまま実装したとする判断ではなく、今回の初版の契約の具体化として回答を求める点である。B は安定性も守れるが、必須のコピーの費用を増やす。C は取り出した後も構築器を使えるという既決の方針を見直す案であり、初版には推さない。

A・B のどちらも、List の要素の再帰的な複製はしない。要素が Reference なら同じセルを参照し、そのセルへの変更は取り出し済みのリストからも観測できる。構築器への追記で要素列が変わらないことと、この共有は両立する。

## B6 持ち出し禁止の中心となる規則

問い: 構築器名を通常の値の環境へ入れず、専用操作の直接の対象にだけ許すか。

| 選択肢 | 内容 |
|---|---|
| A（推す案） | 局所名を別の文脈に置く。返却、利用者関数の引数、通常データ・セルへの格納、通常の型引数、別名束縛、専用操作の値化を拒否する |
| B | 普通の Builder 型として扱い、関数の引数型と戻り値型だけに禁止をかける |
| C | 寿命・領域の型変数と、それを推論する一般の機構を追加する |

推す案は A である。理由: 値として取り出す規則を作らなければ、型注釈の省略や多相関数を通して構築器を普通の型へ紛れ込ませる入口を閉じられる。B は入れ子の格納や捕捉を防げない。C は今回使わない借用や高階の受け渡しまで扱う基盤になるが、範囲・代入・一般化の仕事が増える。ListBuilder の T も構築器を含めない通常の型に限る。

## B7 ラムダ・遅延・タスクと専用操作の値化

問い: 外側の構築器名を捕捉する形を、すぐ実行するラムダも含めて拒否するか。

| 選択肢 | 内容 |
|---|---|
| A（推す案） | ラムダ・lazy・タスクへの捕捉を拒否する。専用操作も直接呼び出しだけとし、構築器を通すパイプ・プレースホルダ・関数値化を拒否する |
| B | 直接記述した List.forEach や即時呼び出しのラムダだけ例外にする |
| C | 捕捉を許し、作成元の関数を越えて使われたときに実行時エラーにする |

推す案は A である。理由: B の「持ち出されない」を証明する規則をまだ持たず、C は静的に持ち出しを防ぐ契約を変える。引数型と戻り値型が普通でも捕捉環境に構築器が入りうるので、解決済みの束縛を使って捕捉自体を検査する。内側のラムダが自分の構築器を作って使い切ることは許す。完成した普通の値を捕捉して渡すことも許す。

## B8 ループ文がない初版での反復追記

問い: 動的な個数の断片は先に作って appendAll へ渡す範囲を受け入れるか。

| 選択肢 | 内容 |
|---|---|
| A（推す案） | 既存の List.map 等で断片を作り appendAll する。構築器を捕捉して反復する使い方とストリームへの逐次追記は初版の対象外とする |
| B | 構築器だけを扱う専用の反復操作と、その中でだけ使えるコールバックの規則を追加する |
| C | 一般の for／while／loop をこの改造へ含める |

推す案は A である。理由: 現行にはループ文がなく、B7 で捕捉を禁じると List.forEach からの追記もできない。この制限を隠した「多数の小さな追記に便利」という説明はしない。B は用途を広げられるが、新しい捕捉境界・制御の終了・効果と脱糖を決めて再見積もりする必要がある。A でも有限個の段階的な操作と一括追加は提供できるが、当初の高速な反復構築まで終えたとは扱わない。

## B9 分岐・ハンドラ・継続の扱い

問い: 通常の分岐と handle の本体からは使え、節は別の捕捉境界にする保守的な規則で始めるか。

| 選択肢 | 内容 |
|---|---|
| A（推す案） | 同じ範囲の if・match・handle 本体から使える。handle の節から外側の構築器名を参照する形は拒否する。節の内側で作ってそこで使う形は許す |
| B | 節も同じ関数内として外側の構築器を自由に参照できる |
| C | 関数内に handle があれば、構築器との併用をすべて拒否する |

推す案は A である。理由: 既存のハンドラはタスクへ引き継がれるので、節を単なる if の分岐と同じに扱わず、外側の状態の捕捉を初版では閉じる。一方、本体の続きを保存する継続は、展開した通常の Reference と State の既存の規則で扱える。セルを関数終了時に手動で解放する規則は設けず、継続の保持・再開・破棄へ新しい局所ストアの所属を追加しない。継続が保持する内部のセルを「ソースで構築器を普通の値として返せた」とは数えない。

## B10 持ち出し禁止を Lean に含める範囲

問い: 型付き表層の局所名の制限と Reference への展開を Lean にも入れるか。

| 選択肢 | 内容 |
|---|---|
| A（推す案） | 型付き表層の局所文脈・専用操作・捕捉境界・検査器と脱糖を形式化する。ソースの名前解決は対象外とする。Release の型・効果・実行は保つ |
| B | 局所名の禁止は Rust の表層の検査だけに置く。脱糖の型と State の保存は Lean に入れ、持ち出し禁止自体は保証外と記録する |
| C | Rust が出した変換後の通常の表層だけを検査し、新しい変換元の表層と脱糖は証明しない |

推す案は A である。理由: 静的な禁止の規則と、そこから既存 Reference へ移す規則を一緒に確認できる。通常値から局所名を分けることで、一般の領域多相や局所エフェクト消去を避ける。ソースの名前の読み取りから実行まで全体を証明したとは説明しない。

B は保証の範囲を狭めて形式化の負担を減らす案である。その場合も、07-04 に従い新しい脱糖は内側として扱う。C は変換元との接続が欠けるため、このままでは規約を満たす実装計画にできない。A は Lean 8〜20時間、B は脱糖の接続を含め4〜12時間の未実測の見込みであり、最初の定義と言明の具体化で再見積もりする。版に含む Lean は全項目を先行の一段へまとめ、ビルドとレビューを終えてから処理系へ進む。

## B11 展開する値・上限・失敗時の状態

問い: 完成途中の不変値をセルに保持し、各追記の既存の大きさの検査が成功してからセルを置き換えるか。

| 選択肢 | 内容 |
|---|---|
| A（推す案） | Reference[String]・Reference[List[T]]・Reference[Bytes] を使う。引数はソース順に一度評価し、純粋な更新と大きさの検査の後に set する |
| B | 文字列・バイト列は断片のリストをセルへ蓄積し、copy の時点で初めて結合と全長の検査をする |
| C | Bytes も全量を List[Byte] としてセルに保持し、最後に Bytes.fromList する |

推す案は A である。理由: 既存の上限と、追記が失敗した時点でセルを変更しない挙動を既存操作へ合わせられる。B はコピー量を減らす候補になるが、断片保持の量・累積長・失敗時点を別に設計する必要がある。C は Bytes より小さいリストの要素数の上限に当たる入力がある。既存の上限超過は従来の実行時エラーの扱いを保ち、構築器だけの新しい Fail や Result へ変更しない。

## B12 初版で約束する効果と完了の扱い

問い: 速度の改善を受け入れ条件にせず、局所名による記述と取り出しの契約を初版の成果にするか。

| 選択肢 | 内容 |
|---|---|
| A（推す案） | State 付きの限定版と明記する。性能改善を約束せず、既存の一括操作を推す例も残す。当初の高速化と局所エフェクト消去は未実装の範囲として区別する |
| B | 同じ不変値への展開でも、既存の操作より速くなることを0.0.9の受け入れ条件にする |
| C | 高速化がない構築器は提供せず、名前と禁止規則だけを設計して実装を次へ送る |

推す案は A である。理由: 追記に既存のコピーとセル操作を使う案では、速度を保証する根拠がない。B を必須にすると、依頼で含めないとしたネイティブの高速化へ範囲が広がりうる。C は設計者が選んだ初版の実装をさらに減らす判断となる。三種類ごとの短い構築・多数の断片・一括結合・取り出しの比較は、後の benchmark の計画で条件を固定する。今回の調査で測ったことにはしない。
