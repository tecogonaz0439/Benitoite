## R1 doctest の印と期待の書き方

問い: コメント内でも、既存の文書検査と同じコードブロックの印を使うか。

| 選択肢 | 内容 |
|---|---|
| A（推す案） | `benitoite test` は @test の成功、`benitoite check` は静的検査、`benitoite error` と diagnostic は指定コードの拒否、`benitoite` と output は出力と終了状態を照合する。text・無印は対象外とする |

## R21 重複除去の制約

問い: 組み込みの縮小器の equality を保ち、比較も遅延して予算に数えるか。

| 選択肢 | 内容 |
|---|---|
| A（推す案） | 元の値と既出の候補への等値比較を一回ずつ進め、初出順を保つ。Property.check 自体へ equality を追加しない |
| B | すべて key 制約へ強め、Set で既出の候補を除く |
| C | Trait.Order または Show の結果で重複を判定する |

推す案は A である。理由: key は Float を含む型に使えず、Order の Equal や同じ表示文字列から組み込みの等値を導けない。候補を誤って同一視するより、比較の予算で早く打ち切る方が現在の意味を保てる。一回の等値比較自体に値の大きさの費用があることは残る。ハッシュを使う拡張は衝突時の等値比較とハッシュの整合の契約を別に設計する。

## R22 TODO-258 の移行・再現・性能の目標

問い: API と規則の版を上げ、実際の処理回数と時間の両方で受け入れを判断するか。
