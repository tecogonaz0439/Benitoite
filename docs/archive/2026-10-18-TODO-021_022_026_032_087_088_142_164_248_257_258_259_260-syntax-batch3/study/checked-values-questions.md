# 検査済みの値と範囲の API について設計者に尋ねる問い

2026-10-18 の S1 の判断の案である。A1〜A16 は TODO-142・026 と共通の土台、C1〜C7 は TODO-022 の計23問である。すべて未回答であり、推す案を採用済みの判断にしない。今回の依頼は調査までであり、回答を先取りして実装へ進まない。

根拠は [調査結果](checked-values.md)、元の項目は [todo-items.md](../todo-items.md) にある。判断の基準は [00-01「目的と設計原則」](../../../design/00-overview/00-01-goals.md) とする。静的に分かる誤りを先に報告し、検査済みの値の保証を、利用者の許可や OS の隔離の保証へ広げない。

以下の型名・関数名・属性の例はすべて未実装の案である。A1・A2 の公開境界を A・C で共有し、A9 の定数の引数を得る処理を142と026で共有する。C は実行時検査から始めるため、C の API を自動で静的検査の対象へ加える前提は置かない。

## A1 作り方を隠す型をどう書くか

問い: 型を公開し、作り方を宣言したモジュールの中へ隠す指定を、どの形で加えるか。

| 選択肢 | 内容 |
|---|---|
| A（推す案） | 引数なしの属性 `@opaque` を public／public(package) の data・record に加える。既存の属性と同じく宣言の前に書く |
| B | `public opaque data`・`public opaque record` のように修飾の語を増やす。予約語または宣言位置だけの語として定める |
| C | public の細分、または構成子・フィールドごとの公開指定を導入する。たとえば `public(type)` や個別の private 指定を設ける |

推す案は A である。理由: 型と作り方の分離を明示でき、public の三段階を別の目的へ広げずに済む。新しい予約語も不要となる。B の語を全位置で予約するなら既存識別子へ影響し、C は型全体と欄ごとの公開をどう合成するかという追加の問いが生じる。

A は既存の型の公開範囲を変えず、新しい指定を付けた型だけを制限する。既存の公開型へ後から付ける場合は互換性を壊す。標準型だけを組み込みとして増やす案も可能だが、利用者が同じ契約を作れず、A・C の型ごとに組み込みの実装が増えるため推さない。

## A2 作り方を隠す境界と拒否する操作

問い: `@opaque` の境界をモジュールとし、構築・取り出しの自動の入口をまとめて隠してよいか。

| 選択肢 | 内容 |
|---|---|
| A（推す案） | 同じモジュールだけが構成子・構築・更新・パターン・自動アクセサを使える。同じパッケージの別モジュールも外部とする |
| B | 同じパッケージなら作り方を見せる。外部パッケージだけを制限する |
| C | 構築と更新だけを隠し、パターン・自動アクセサは公開する |

推す案は A である。理由: 一つのモジュールを読めば、値を作る全関数を確認できる。C でも単純な不変値の構築は制限できるが、中身に Reference があれば公開した中身から変更されうるため、作り方を隠す仕組みの一般の保証にしにくい。必要な読み出しは明示的な公開関数にする。

構成子を関数値として持ち出すこと、部分適用、型の別名、名前の別名でも境界を迂回できないようにする。`public(package)` は型を使える範囲だけを表し、構築の境界を広げない。隠した構成子の引数・欄に使う非公開型は外部契約へ数えず、公開関数の署名には従来の公開段階の検査を残す。

`@extensible` との併用は初版では拒否する案を推す。両方を必要とする具体例がまだなく、構成子を一切見せない型の外部網羅性に新しい規則を足す必要を避けられる。隠した内部の構成子は、形式化へ渡す型表から消さない。

## A3 142 の型名と置き場所

問い: 対象の検査済みの型を、権限の許可を意味しない名前で、一つの非公式モジュールに置いてよいか。

| 選択肢 | 内容 |
|---|---|
| A（推す案） | `Benitoite.Unofficial.Scope` に `CheckedHost`・`CheckedPath`・`CheckedEndpoint` を置く。import 後は `Scope.CheckedHost` 等と書く |
| B | `AllowedHost`・`AllowedPath` を IO や Network の各モジュールへ置き、操作の許可を表す型として始める |
| C | `Host`・`Path`・`Port` の構文上正しい値だけを用意し、指定した範囲への適合は後にする |

推す案は A である。理由: 「渡した条件で検査した」という保証を名前で示せる。Allowed は許可する主体と方針を先に要し、サーバモードの判断を含めてしまう。C は有用な解析済みの値だが、今回の142の範囲の照合を満たさない。

prelude には追加しない。標準の同じ名前の正式化は別の判断とする。CheckedEndpoint はホストとポートを一緒に検査した値であり、HTTP の URL 全体を検査した値ではない。

## A4 ホストの範囲をどう書くか

問い: 最初のホストパターンを、完全一致、一段の `*.`、一段以上の `**.` に限ってよいか。

| 選択肢 | 内容 |
|---|---|
| A（推す案） | `example.com` は完全一致、`*.example.com` はちょうど一段、`**.example.com` は一段以上とする。後二者は頂点自身を含まない |
| B | `*.example.com` を一段以上にする。試作の tree(stem, 1) に記法を合わせる |
| C | 任意位置のワイルドカード、否定、正規表現、範囲の和も最初から認める |

推す案は A である。理由: 一段と多段を見分けられ、パスの `**` とも深さの意味を合わせやすい。`*.example.com` で `a.b.example.com` は拒否、`**.example.com` では受理する。どちらも `badexample.com` は拒否する。試作は記法を決定していないので、B が既存仕様ではない。

解析は ASCII のドメインラベルに限り、ASCII 大文字は小文字へ揃えて保存する。空ラベル、各ラベルの先頭・末尾のハイフン、英数字とハイフン以外、末尾のドットは拒否する案を推す。単一ラベルの `localhost` は認める。四つの十進数ラベルからなる IPv4 形式も明示的に拒否する。IPv4・IPv6 の数値アドレス、非ASCII名、URL、ポートを含む文字列はこの初版の対象外と明記する。これは Scope の入力規則の案であり、DNS で有効な名前の完全な判定だとは宣言しない。

## A5 パスの範囲と正規化をどこまで扱うか

問い: パスの検査を、OS に問い合わせない字面の照合に限ってよいか。

| 選択肢 | 内容 |
|---|---|
| A（推す案） | `/` 区切りの絶対形式に限り、完全一致と末尾 `/**` だけを認める。`.`・`..`・空の中間要素・NUL・逆斜線は拒否する |
| B | 相対パスを作業ディレクトリで解決し、File.canonicalize も呼んで検査済みの値にする |
| C | OS ごとの通常のパス・ドライブ・リンク・glob 全体を扱い、対象の隔離にも使う |

推す案は A である。理由: 純粋な関数にでき、要素列の照合の意味を試作から小さく確定できる。`/data/reports/**` はそのディレクトリ自身と任意段の子を含み、`/data/reports-old/a` は含まない。根 `/` を例外として認め、根以外の末尾 `/` は拒否し、受理する表記を一つにする。

字面の適合は、存在・読み書きの成功・シンボリックリンクの解決先・検査後に変わったファイルを保証しない。OS のパスの一般の置き換えとも説明しない。B は IO と基準ディレクトリを要し、検査後の変更も残る。実際の対象を制限する設計はサーバ側で改めて行う。

## A6 ポートの範囲とホストとの組

問い: ポートは閉区間の整数二つを普通の引数として渡し、ホストと一緒に保持する形でよいか。

| 選択肢 | 内容 |
|---|---|
| A（推す案） | `minimumPort`・`maximumPort`・`port` を受け、`0 ≤ minimumPort ≤ port ≤ maximumPort ≤ 65535` を確かめる |
| B | `5432..5439` 等を String や専用の新しい式の構文として受ける |
| C | ポート0を全用途で禁じ、1〜65535に固定する |

推す案は A である。理由: 型引数や新しい範囲式を要さず、C の整数の比較の意味を使える。ポート0は既存の listen で用途があるため、型の作成時に一律に除かない。接続先の有効性は使用する IO の契約で確かめる。逆転した端点は空区間の成功値を作らず、不正な範囲として返す。

## A7 実行時の作成関数と値に残す情報

問い: 検査に使った範囲と対象を一緒に保存し、失敗は Result で返す形でよいか。

| 選択肢 | 内容 |
|---|---|
| A（推す案） | `checkHost(pattern: String, host: String)`、`checkPath(pattern: String, path: String)`、`checkEndpoint(hostPattern: String, host: String, minimumPort: Integer, maximumPort: Integer, port: Integer)` が対応する Checked 値の Result を返す |
| B | 範囲を捨てた Checked 値だけを返し、「どれかの条件で検査済み」とする |
| C | `CheckedHost[P]` のように範囲を型引数に入れ、型の包含で範囲を広げる |

推す案は A である。理由: 検査した条件を後から確認でき、別の範囲への適合を誤って導かずに済む。返り値は、たとえば `Result[CheckedHost, ScopeError]` とし、エラーは不正なパターン・不正な対象・範囲外・不正なポート範囲を区別する。

取り出しは `host`・`path`・`port` と、`hostPattern`・`pathPattern`・`minimumPort`・`maximumPort` の必要な関数に限る。保存した範囲の変更関数は設けず、別の範囲に使うなら元の対象で再検査する。A の API 自体は純粋で State を持たず、ホストは小文字化した照合対象を保存する。パスは受理した表記を保存する。C は型に値を持たせる重い拡張になる。

## A8 142 のどの定数の引数を先に調べるか

問い: A7 の直接呼び出しについて、定数で分かる入力の誤りを検査時のエラーにしてよいか。

| 選択肢 | 内容 |
|---|---|
| A（推す案） | 定数のパターンの文法と定数の対象の形式、定数のポート端点を検査し、所属に必要な引数がすべて定数なら範囲外もエラーにする |
| B | パターンの文法だけを先に検査し、対象の不適合は定数でも Result.Error にする |
| C | 定数で判定できてもすべて実行時へ残す |

推す案は A である。理由: 許す対象を固定して書いた呼び出しの間違いを実行前に示せる。たとえば `checkHost(pattern: "*.example.com", host: "badexample.com")` を拒否する。動的な host と定数の pattern なら、pattern の文法だけを先に調べ、host の所属は実行時へ残す。

これは定数の不適合を期待して Result.Error を照合するコードも拒否する追加の規則である。エラー処理を試す場合は引数を受ける関数を通して動的な検査を呼ぶ。入力が未知・予算超過の場合を範囲外と混同しない。予算超過で成功と判断せず、追加検査の資源制限として明示する。型や名前に誤りがある引数は追加評価しない。

## A9 定数を得る処理を026と共有するか

問い: 標準の束縛を直接呼ぶ式の引数を、既存の定数式の範囲で調べる小さな共通処理にしてよいか。

| 選択肢 | 内容 |
|---|---|
| A（推す案） | 名前解決後の束縛を固定表と照合し、型検査済みのリテラル・const参照・基本演算・定数の補間等を既存の評価規則で得る |
| B | リテラルだけをそれぞれの検査で読む。const参照は調べない |
| C | 任意の純粋関数を実行できる仕組み、または利用者が検査関数を登録する属性を作る |

推す案は A である。理由: const に名前を付けただけで検査の成否が変わることを減らし、Regex と Scope の走査・予算・診断位置の管理を共用できる。判定本体まで一つの文法にしない。プログラム全体の引数用の評価予算を設け、同じ定数値の再取得で費用が膨らまないようにする。

通常の直接呼び出しに限り、import の別名は同じ束縛なら対象にする。同じ綴りの利用者関数、局所関数値、高階関数経由、プレースホルダ・パイプ経由の適用は初版では対象外とする。後二者で同じ関数を呼べても、実行時の検査は常に残る。トップレベルの const に Regex や Scope の関数呼び出しを許す変更は含めない。

## A10 既存 IO の引数を変更するか

問い: 0.0.9 では検査済みの値の API を追加し、既存 IO の String・Integer の引数を保ってよいか。

| 選択肢 | 内容 |
|---|---|
| A（推す案） | 既存 IO を保ち、Scope の検査と取り出しを利用者が明示する。今回の保証を値自身の不変条件に限る |
| B | Checked 値だけを受け取る並行の IO API を、少数の File・HTTP 操作に追加する |
| C | 既存 IO の引数を Checked 値へ変更し、すべての呼び出しを移行する |

推す案は A である。理由: URL とホストの違いや OS のパスの解決を未設計のまま、検査済みと称する IO を公開することを避けられる。142の最初の段として値と検査を提供するが、「全 IO の対象を型で制限した」とは記録しない。

B は追加だけで導入できるが、Checked の中の対象をそのまま使うことと、どの範囲の条件を求めるかの規則が要る。C は互換性を壊し、Command、ClientRequest のレコード更新、開いたハンドル経由の操作、shell の扱いも含む全入口の調査・移行が必要になる。採るなら本書の見積もりを作り直す。

## A12 026 の静的検査をどの方式で入れるか

問い: `Regex.compile` を指す名前の直接呼び出しで、引数が定数式なら検査時に組み立てる形でよいか。

| 選択肢 | 内容 |
|---|---|
| A（推す案） | A9 の共通処理で引数を得て、実行時と同じ判定本体・設定で組み立てる。失敗は検査のエラーにする |
| B | 別の lint とし、通常の check では誤りにしない |
| C | 正規表現リテラルを新設し、その記法だけを検査時に確かめる |

推す案は A である。理由: 現在の関数呼び出しと raw string を使い続けられ、定数で分かる誤りを実行前に報告できる。B は見落としを防ぐ実行手順が増え、C は Regex の値を作る書き方が増える。比較した他言語には複数の方式があり、一つの慣例を理由に記法を足す根拠は得られなかった。

`bind pattern <- Regex.compile(source: r"[a-z]+")` の型は引き続き Result である。`Regex.compile(source: userInput)`、関数値として渡した compile の呼び出しは従来どおり実行時に判定する。組み立て済みの Pattern をバイトコードへ埋めたり、Result.Ok へ自動で書き換えたりはしない。実行時にも同じ検査を行う。組み立てが失敗する理由には構文以外の大きさの制限も含め、構文不良と資源の制限を診断で区別する。Regex の組み立てを含む追加検査の費用にも上限を設け、共通の定数評価予算だけで抑えられるとは扱わない。

## A13 診断コードと表示

問い: E0444 を欠番のまま残し、正規表現と範囲の誤りへ新しいコードを割り当ててよいか。

| 選択肢 | 内容 |
|---|---|
| A（推す案） | E0444 は再利用せず、Regex の定数の不正、Scope の定数の形式不良・範囲外へ未使用番号を割り当てる |
| B | 同じ用途の復活として E0444 を使う。その例外を診断コードの規約へ記録する |
| C | 一般の定数評価の誤りと同じコード一つにまとめる |

推す案は A である。理由: 現行の RETIRED と番号を使い回さない規約を保てる。エラーの原因と修正手順を区別できるので、形式不良と不適合はメッセージだけに埋めない。具体的な新番号は版全体の診断の割り当て時に重複を調べて決める。

一次位置は呼び出しの引数、補助位置は参照した定数の宣言とする。文言は英語で表へ集め、正規表現の理由は実行時と同じ判定から得る。長い文字列は既存の上限に合わせて切り詰める。raw string の位置は元ソースへ戻せるが、補間やconst参照で一つの文字位置に戻せない場合は引数全体を示す。復号後のバイト位置をそのままソース位置にしない。

## A14 静的検査の追加による互換性とエラーの試験

問い: 定数の壊れた Regex／Scope が実行時の Error から検査のエラーになる変更を、明示した受理範囲の縮小として扱ってよいか。

| 選択肢 | 内容 |
|---|---|
| A（推す案） | 移行案内に対象の直接呼び出しを示し、失敗を期待する試験には引数を受ける関数を通した動的入力を使う |
| B | 互換性のため初版は警告にとどめ、後でエラーへ変える |
| C | 失敗が match で処理される場合やテスト中だけ、静的なエラーを出さない |

推す案は A である。理由: 静的に不正とする規則を置く位置で変えずに済む。B では原則1への例外が残り、C は呼び出しの周囲の処理を追う新しい解析を必要とする。実行時の失敗処理も引き続き確かめる必要があるので、静的拒否の例へ置き換えるだけで済ませない。

初版の直接呼び出しに限る規則は、呼び出しの書き換えで静的検査の対象から外れる。その限界と実行時の検査が残ることを同梱 Skill にも示す。正常な呼び出し、動的入力の型、既存の public data・record の公開範囲は変わらない。

## A15 形式化の内外と先行する証明

問い: 公開境界と定数の追加検査を既存の名前解決・定数評価の外側として扱い、範囲の意味だけを小さく証明する方針でよいか。

| 選択肢 | 内容 |
|---|---|
| A（推す案） | 通常の data・Call・Result へ渡す形を保つ。小さな意味の証明を足し、実装との対応と07-04の対象外の説明を整える |
| B | モジュールの可視性と実際の文字列解析の全体も形式化し、構築できないことから値の不変条件まで本体全体で示す |
| C | 範囲を Release のエフェクトや型へ入れ、対象安全の新しい定理を今回の完成条件にする |

推す案は A である。理由: 既存の型と規則を保ちながら、成功値の範囲への適合を学習・検証の対象にできる。B・C は現在の小モデルを本体の保証へ接続する追加の大きな設計を要する。

A の分類は、型付き表層・型付け・脱糖を変えないことが条件である。隠した型を新しい Ty の場合へ替える、型表を削る、検査を除去する等へ範囲が変わったら、内側として再判断する。「Release を保つ」だけで Surface の変更まで外側とは扱わない。

版に含む Lean の改造は全項目を最初の段へまとめ、既定のビルドと定義・言明・仮定のレビューを終えてから処理系へ進む。この順序は選択肢で省ける条件ではない。内側なら01-12の写しと対応表、Rustとの接続を閉じる時点と最終状態の全比較も計画へ割り当てる。

## C1 最初に用意する値の範囲

問い: 022の初版は任意の整数の閉区間を確かめる一種類に絞ってよいか。

| 選択肢 | 内容 |
|---|---|
| A（推す案） | 整数の区間と `CheckedInteger` だけを提供する。長さ・空でないリスト・添字は次の判断へ残す |
| B | 整数に加えて `NonEmptyList[T]` と、リストの長さの上下限を保持する型も提供する |
| C | 対象のリストと添字を一緒に持つ `Indexed[T]` を最初の題材とする |

推す案は A である。理由: 成功・失敗・保存する情報の意味を小さく確定でき、A のポートの区間の意味とも重なる。既存の List.get は Option を返すため、C を異常終了の解消だけで評価することはできない。B を採るなら文字列の長さも混ぜず、まずリストに限る。

0以外、正、非負も候補だが、0以外は一つの凸な区間で表せない。専用型を増やすか、負と正を分けるかは別の判断とする。ポートを唯一の固定範囲にすると A に用途が偏るため、C では利用者が整数の端点を渡す案を推す。

## C2 名前とモジュール

問い: 初版を `Benitoite.Unofficial.Range` に置き、篩型という構文上の名前は付けない形でよいか。

## C3 API と Option・Result の選択

問い: 最初の作成関数を `checkInteger(minimum: Integer, maximum: Integer, value: Integer) -> Result[CheckedInteger, RangeError]` にしてよいか。

| 選択肢 | 内容 |
|---|---|
| A（推す案） | Result を返し、不正な端点と範囲外を別のエラーとする。成否だけ必要なら `Result.ok` で Option にする |
| B | `Option[CheckedInteger]` だけを返す |
| C | 元の `Integer` の Result だけを返し、検査済みの型を作らない |

推す案は A である。理由: 条件そのものの誤りと入力が条件に合わない場合を診断でき、何を確かめた値かを型の名前でも示せる。CheckedInteger には両端と値を保存し、外部から変更できないようにする。型の等しさだけで、別の区間にも適合するとは扱わない。

RangeError の案は `InvalidBounds(minimum, maximum)` と `OutOfRange(minimum, maximum, value)` である。エラーの情報は公開してよいが、CheckedInteger の構成子は隠す。Fail は必要とせず、必要な利用者は既存の Failure.fromResult で境界を選ぶ。試作の Option の定理は、この Result の区別に合わせて直す。

## C4 区間の端と空区間

問い: Integer の全域を表せる閉区間とし、逆転した端点をエラーにしてよいか。

| 選択肢 | 内容 |
|---|---|
| A（推す案） | `minimum ≤ value ≤ maximum`。端点が等しい区間は一つの値を含み、minimum > maximum は InvalidBounds |
| B | 試作と同じ半開区間 `[minimum, stop)`。逆転と等しい端点は空区間として扱う |
| C | 端点なし・開区間・閉区間・和をすべて扱う |

推す案は A である。理由: 最大の Integer を含む区間も、表せない上端を用意せずに書ける。B を `maximum + 1` へ自動変換すると、その加算自体があふれうる。比較だけで判定し、端点の加算や負号を挟まない。C は最初の少数APIの証明と説明を増やす。

## C5 検査済みの値へ用意する操作

問い: 初版の操作を読み出しと再検査に限り、演算と暗黙の型変換は加えない形でよいか。

| 選択肢 | 内容 |
|---|---|
| A（推す案） | `Range.value`・`minimum`・`maximum` を公開し、別の区間は checkInteger で再検査する |
| B | 同じ区間の加算・減算も Result で提供する |
| C | Integer の演算と相互に暗黙で変換し、範囲を型検査で追跡する |

推す案は A である。理由: 成功値を保つ操作が少なく、全操作の不変条件を見直せる。B は範囲を調べる前の整数のあふれも失敗値にする実装が必要であり、試作の数学的な加算だけでは足りない。C は静的な篩型の設計に入る。

value で元の整数を取り出した後の演算は、従来の Integer の契約に従う。CheckedInteger を受ける関数が特定の区間を要求する場合は、保存した端点を確認するか、自分の範囲で再検査する。A7の Scope と同じく、添字のない型だけから特定の範囲を導かない。

## C6 Lean で示す小さな意味の性質

問い: 初版の証明を、成功値の保存と所属、失敗の分類、証拠を消した実装との対応に限ってよいか。

| 選択肢 | 内容 |
|---|---|
| A（推す案） | 閉区間の checkInteger の成功から三つの入力の保存と所属、InvalidBounds／OutOfRange の条件、取り出しの保存を示す |
| B | A に区間の包含・広げる変換・加算の安全性を加える |
| C | 本体の進行・保存の定理から任意の範囲エラーの不在まで示す |

推す案は A である。理由: 今回公開する API の全成功値を対象にでき、実装しない演算や変換の証明を先取りしない。`Contracts.make_success`・`make_none_iff`・`erase_make` の形が出発点になる。Result の分類と閉区間への変更は新しく示す。

Lean の数学的な Int と Benitoite の Integer の対応は、比較だけを使い、入力を表現可能な整数へ制限して結ぶ。文字列や数値の格納、実行時の全コードの正しさまで証明したとは説明しない。定義・言明・仮定のレビューと実装との対応表を残す。

## C7 静的な区間解析を含めない境界

問い: 0.0.9 の022では、実行時の API と小さな意味の証明までとし、静的な区間解析も定数引数の特別扱いも加えない形でよいか。

推す案は A である。理由: 実行時に範囲を確かめ、Option・Result を返すという採用済みの最初の範囲に合う。Range は検査する値が範囲外である場合も通常の処理として扱いやすくし、定数の Error を返すコードも書ける。A の Scope／Regex は、特定の定数の不正を前もって拒否する別の言語規則として対象を明記する。
