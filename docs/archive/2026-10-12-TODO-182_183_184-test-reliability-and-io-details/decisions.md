# 判断とその理由

利用者から見える振る舞いを変える四つの点を、改造を始める前に設計者に尋ねた（2026-10-12）。設計者はどれも推奨を選んだ。設計者は、作業の途中で決める点が出たときは推奨の方法で進めるよう指示した。そうして決めた点は、後の「推奨どおりとした問い」に書く。

## 設計者に尋ねた問い

### Q1 `File.readLine` の上限の数え方（TODO-184 の 1 点目）

決定: 上限（2^30 バイト）を、行末（LF・CRLF）を除いた内容の長さで数える。ちょうど 2^30 バイトの内容に行末が付いた行は読める。

理由: 02-09「一つの操作で作る値の大きさの上限」は作る値の大きさを抑える決まりであり、行末は作る値に含まれない。

代替案: 行末を含めて数え、02-09 にそう書き添える（今の実装のまま）。

### Q2 `File` の上限の失敗の種類（TODO-184 の 2 点目）

決定: `File.readLines` の行の数の超過も、`walk`・`listDirectory` の項目の数の超過と同じく InputTooLarge にそろえる。

理由: どれも、大きさの決まっていない外部の入力を読む操作で起きる失敗であり、読む入力が大きすぎる側に寄せると分け方が一つの規則で説明できる。

代替案: ValueTooLarge にそろえる。

### Q3 `File.Writer` の書き込みが失敗した後の扱い（TODO-184 の 3 点目）

決定: 書き込み（途中の書き出しを含む）が失敗したら、そのライターを失敗の状態にし、バッファに残った分を捨てる。以後の書き込みと `closeWriter` は同じ失敗を返し、残りを書き直さない。明示の `closeWriter` は close の失敗を返す。解放（drop）での close の失敗の扱いは 03-07 に書く。

理由: 失敗の後に残りを書き直すと、どこまで書けたかがスクリプトから分からなくなる。

代替案: 今の振る舞い（残りを後で書き直す）を 03-07 に書くだけにする。

### Q4 孫のプロセスがパイプを持ち続ける場合の `Process.run`（TODO-184 の 4 点目）

決定: 待ち方は変えず、孫のプロセスが標準出力・標準エラー出力を開いたままだと `Process.run` が返らないことを 03-07 に書き、時間の上限（`Task.withTimeout`）を使う回避を示す。

理由: Rust の `Command::output` と同じ性質で、待ち方を変えると子の出力を読み落とす危険が生じる。

代替案: 子が終わったら少し待ってパイプを読むのをやめる。

## 推奨どおりとした問い

調査（`study.md`）の途中で決めた点である。括弧の中は `study.md` の節を示す。

### R1 上限を差し込む口（2.7・2.8 節）

決定: `readLine` と `Process.run`・`Console.readAll` 系の上限は、非公開の関数の引数として渡す。本番の呼び出しは `MAX_STRING_BYTES` を渡し、テストは小さな上限を渡す。三つのモジュールの上限の確かめを一つの関数にまとめる。

理由: 1 GiB の入力を作らずに上限の経路を通せる。AGENTS.md「大域の状態」に反する大域の値も、`cfg(test)` の分岐も要らない。差し込む口は非公開の関数の引数だけで、公開の範囲は広げない。

代替案: 1 GiB の入力で確かめる長いテスト（メモリと時間がかかり、回収の強制の構成でも走る）。大域の上限の値をテストで差し替える（規約に反する）。

### R2 `Console.readAllLines` の行の数の超過（3.2 節）

決定: Q2 と同じく InputTooLarge にする。

理由: 大きさの決まっていない外部の入力を読む操作であり、Q2 の理由がそのまま当てはまる。`String.lines` などの純粋な関数は ValueTooLarge のままとする。

代替案: `File.readLines` だけを変える（`Console` と `File` で分け方が食い違う）。

### R3 `Console.readLine` の上限の数え方（3.1 節）

決定: Q1 と同じく、行末を除いた内容の長さで数える。

理由: `File.readLine` と同じ関数を通り、03-07「共通の規則」が二つを一つの規則で定める。

代替案: なし（分けると共通の規則が崩れる）。

### R4 失敗した `File.Writer` の `closeWriter` が返す誤り（3.3 節）

決定: 記録した失敗と同じ文を、`IOErrorKind.Other` で返す。書き込みの関数（`write`・`writeLine`・`writeChunk`）は、記録した失敗を種類ごと返す。

理由: 解放の結果は、すべてのリソースが共有する口（`OsResource::release` の `Result<(), String>`）で文だけを運び、`closeWriter` は今も `Other` を付ける。種類を運ぶにはこの口を変える必要があり、ほかのリソースにも及ぶ。

代替案: 解放の口を変えて種類も運ぶ。

### R5 close(2) の誤り（3.3 節）

決定: close(2) が返す誤りは、明示の `closeWriter` でも解放（drop）でも捨てる。`closeWriter` が返すのは、書き出し（`flush`）の失敗と、記録した書き込みの失敗までとする。03-07 にそう書く。

理由: 標準ライブラリには close(2) の結果を受け取る安全な口がない。rustix の `try_close` は `unsafe fn` であり、AGENTS.md は `unsafe` を `runtime::heap` の内部の層に限る。Q3 の「明示の `closeWriter` は close の失敗を返す」を、この制約の中で書き出しの失敗を返すことと読んだ。設計者に確かめる。

代替案: close(2) の結果を返す依存のクレートを加える。`sync_all` を呼んで遅れる誤りを先に受け取る（ファイルごとに同期の時間がかかる。03-07 は同期を求めない）。

### R6 `closeWriter` が解放を待つ間の取り消し（3.3 節）

決定: 今の振る舞い（記録した解放の失敗を捨てる）を保ち、01-10「解放の失敗」に一文足す。振る舞いを固定するテストを一つ足す。

理由: 2026-10-07 に設計者が今のままでよいとした。`close` を呼んだリソースは解放済みとみなし、その失敗は `close` の結果としてだけ報告する。結果を受け取るタスクの続きが取り消しで捨てられたので、報告の先がない。`with` のブロックを抜けるときの解放の規則とは対象が違い、矛盾しない。

代替案: 実行時エラーにする（スクリプトが扱うと決めた失敗を、止まる誤りに変える）。

### R7 jiff の内部の大域の状態（3.5 節）

決定: 03-01「使う Rust のクレート」の jiff の項に、システムのタイムゾーンのキャッシュ（5 分）と zoneinfo のデータベースの二つの大域の状態を書く。03-07「Clock」に、同じプロセスの中ではシステムのタイムゾーンの変更が最大 5 分遅れて現れることを書く。AGENTS.md「大域の状態」に、規約は処理系のコードに当てはまり、依存のクレートの内部の状態は 03-01 に書くと一文足す。AGENTS.md の例外の一覧には加えない。

理由: 例外の一覧は処理系が自分で持つ状態を数えるもので、依存のクレートの内部は処理系が選べない。実行ごとの状態の分離（02-01）に影響するのは、同じプロセスで複数の実行をするときに地方時のキャッシュを共有する点だけである。

代替案: AGENTS.md の例外の一覧に加える。

### R8 HTTP クライアントの時間の上限の頭打ち（3.6 節）

決定: ureq に渡す時間を 2^40 ミリ秒（約 34.8 年）で頭打ちにし、`timeoutMilliseconds` を `i64::MAX` にした要求がループバックのサーバから応答を受け取るテストを足す。03-09 に書く。

理由: ureq は `Instant + Duration` で期限を計算し、標準ライブラリはこの足し算の溢れで panic する。macOS と Linux では溢れない見込みだが確かめておらず、頭打ちにすれば OS とライブラリの内部に頼らずに済む。34.8 年は実行の時間として区別できない。

代替案: テストだけを足し、頭打ちにしない。上限を超える値を時間の上限なし（`None`）にする。

### R9 失敗の注入の表の名前の照合（3.6 節）

決定: HTTP のクライアントは、URL の host から IPv6 の角括弧を除いた名前で失敗の表を引く。02-09 の表の説明に書き添える。

理由: 表は名前ごとに失敗を当てる仕組みで、テストの書き手は `::1` と書く。`Http.listen` は角括弧付きの名前を受け付けないので、サーバ側はそのままでよい。

代替案: 表の側で両方の形を当てる。

### R10 時間に依存するテストの直し方（1.4・1.7・1.8・1.9 節）

決定: 待ちの上限は停止の検出にだけ使い、上限は内側から外側へ長くする（内側 10〜30 秒、外側 120 秒）。時間切れの文言には何を待っていたかを書き、時間切れのときは中断の印を立てるかロックを放してから失敗させる。ポートの再利用の競合は、競合だと分かる結果（待ち受けの失敗、ほかの相手への接続）のときに限り 3 回までやり直す。回収の強制の構成でだけ上限を延ばすことはしない。

理由: 上限を構成で変えると、どの構成で何秒かを読み手が追う必要が増える。今の上限（10〜120 秒）は回収の強制の構成でも通る大きさで、落ちた記録は上限の重なりと上限のない待ちによるものだった。

代替案: 回収の強制の構成でだけ上限を延ばす。待ちを条件の通知だけにする（ループバックの通信では作れない待ちがある）。

### R11 扱わない点

決定: 次の点は直さない。理由は `study.md` の各節に書いた。

### R12 later-issues の 41 と 103（1.1・1.2 節）

決定: 41 は、巻き戻しの途中で panic しうる `Drop` を直すことで扱い、原因の再現は試みない。103 は、待ちが既に `receive`（120 秒、文言付き）に統一されているので、テストを変えず、X1 の完了の条件で回収の強制の構成で走らせる。

### R13 書き込みに失敗した `File.Writer` を `with` が解放するとき（作業 X4 の事前点検）

決定: `with` の解放も `closeWriter` と同じく記録した失敗を返すので、書き込みの失敗をスクリプトが扱っていても、`with` のブロックを抜ける解放は解放の失敗（実行時エラー）になる。扱うには、ブロックの最後で `closeWriter` を呼んで結果を調べる（01-10「解放の失敗」の今の決まり）。03-07・言語リファレンス・CHANGELOG（互換性のない変更）に書き、VM を通すテストで固定する。設計者が起きた後に、この点を知らせる。

理由: 解放の口はすべてのリソースが共有し、`with` と `closeWriter` を区別するには口を変える必要がある。バッファの残りを捨てたことは書けなかったデータを意味し、ブロックを抜けるときに報告するほうが失敗を見落とさせない（設計原則 2）。今もバッファに残りがあれば同じく解放の失敗になっており、規則が一つにそろう。

代替案: 失敗の状態の Writer の `with` の解放を成功とし、`closeWriter` だけが記録した失敗を返す（解放の口か `closeWriter` の経路を変える必要があり、捨てた残りが報告されない）。

注記（作業 X4 のレビュー）: R6 の「`with` の規則とは対象が違い、矛盾しない」は、`with` で束縛していないリソースに限る。`with` で束縛したリソースで `closeWriter` の待ちが取り消されると、今の処理系は、`closeWriter` が受け取るはずだった失敗を `with` の解放の失敗（実行時エラー）として報告する。この改造より前からある振る舞いで、どちらにするかは docs/todo の新しい項目で決める。
