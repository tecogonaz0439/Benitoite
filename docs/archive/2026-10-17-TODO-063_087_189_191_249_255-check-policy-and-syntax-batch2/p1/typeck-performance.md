# RV3 軽3の短い型検査測定

開始版は `8604e358d68e9f19897903afeb5c5b3635a97c18`、現在版は P1 の未コミット差分を含む `04e82f6f8d7510b0aca968c4573fee0e249cd62e` である。Rust の release 構成・既定機能で、同じ計算機の同じセッションで測った。環境は macOS-27.0.1-arm64-arm-64bit、cargo 1.98.1 である。CPU の sysctl は sandbox に拒否されたので型番は断定しない。電源・他アプリケーションの状態は調整していない短い観察であり、本測定の結果には使わない。測定中にほかのビルド・検査・エージェントの処理は起動しなかった。

`typeck_probe.rs` を一時的に各版の `examples/p1_typeck_probe.rs` へ写し、`cargo build --release --example p1_typeck_probe` でビルドした。開始版は git archive から無視対象の target/p1-baseline-src へ展開し、共有 target の生成物をコピーした。現在版を作る前に Cargo の dep-info が開始版のパスを保持していることに気付き、その記録が指す lib.rs・example の時刻を更新して現在版の再ビルドを起こした。バイナリの SHA-256 が異なることと、ビルドの現在版のパスを確認した。

- 開始版バイナリ: `386e9bd713da2240f2f674a6e56700a57ec6eec0f238a2c1afc99ef4381c147c`
- 現在版バイナリ: `2f27acc4ac34bec4fd56a6a5cd0b22202d9633d5e0a3c67e663d387b4c09025c`

高階関数 apply へラムダを渡す100/300/900個の bind を同じ一つの関数本体へ置いた。最初に pipeline::check_text が成功することを確かめ、そのモジュール・AST・名前解決済み表を使って typeck::typecheck を4回呼んだ。計時は型検査本体だけで、読み込み・構文解析・名前解決を含まない。最初の一回を準備として除き、残る3標本の最小値を比べる（benchmark の短い測定の規則）。診断に誤りがあれば測定を中断する。

| 呼び出し数 | 開始版・Failure なし (ms) | 現在版・Failure なし (ms) | 比率 | 現在版・Failure あり (ms) |
|---|---:|---:|---:|---:|
| 100 | 6.107 | 6.964 | 1.14 | 8.838 |
| 300 | 10.634 | 14.507 | 1.36 | 17.965 |
| 900 | 24.279 | 47.784 | 1.97 | 60.107 |

開始版には Failure モジュールがなく、false の全12標本を出した後の true の準備で E0321・終了1となった。false の成功した型検査の標本だけを比較に使い、存在しないモジュールの検査時間は集計しない。現在版は false/true とも全24標本が成功し、外側は1.182秒、終了0だった。開始版の外側は0.573秒である。生の標本は typeck-baseline.csv・typeck-current.csv に保存した。

900個で現在版は開始版の約1.97倍であり、差は現れる。現在版の300→900個は約3.29倍、開始版は約2.28倍だった。この大きさでは各回は約48ms、Failureを取り込んでも約60msで終わった。3種類の入力と短い標本だけでは二乗の増加とは断定できず、原因を equal_function_effects / propagate_effects のどちらかへ帰属させる測定でもない。見立てとして制約の線形探索と複製の費用は残る。最適化の要否は取りまとめの判断へ渡し、P1では変更しない。

RV3軽4の finalize_failure_type が各段で zonk し直す深い型の費用も未修正の観察として残す。この入力は深い型の測定ではない。
