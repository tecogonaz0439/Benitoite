## TODO-250 の C に沿った三方式の比較

実装を導くこと（derivation）は、型の宣言から変換や生成の実装を機械的に作ることを指す。どこで作るかと、何を型の規則に加えるかで作業は異なる。

| 観点 | A 処理系が決まった実装を導く | B 処理系は汎用の型の構造を導く | C 外部の道具が通常のソースを作る（推す案） |
|---|---|---|---|
| 利用者の指定 | `@derive(Json.Encode, Json.Decode, …)` のような新しい属性 | `@derive(Generic)` などの指定、または構造を暗黙に用意する規則 | 生成設定とコマンド。`.bnt` の構文は増えない |
| 生成結果 | 型ごとの実装と辞書を処理系の内部で作る | 型を積と和で表す型の対応と、値の相互変換を作る | 明示した関数、または通常の implement。人と LLM が読める |
| Json との結び付き | Json の型クラス・メソッド・失敗の型・変換の規則を処理系が知る | 処理系は構造の共通の規則だけを知り、Json の変換はライブラリが受け持つ | 生成道具とテンプレートは Json を知るが、型検査・脱糖・VM はその関数を特別扱いしない |
| 型の変更への追従 | コンパイルのたびに導く | 構造と型クラスの解決をやり直す | 生成し直しと設定・型・出力の照合が要る |
| 型の規則 | 欄ごとに要る制約の導出、重複・所属・再帰・未対応型・可視性の規則が要る | 型と構造の型の対応、関連する型を表す方法、異なる型の欄の集まりと辞書の対応が要る | 出力を既存の型の規則で検査する。手書きと生成の優先順位を型検査に加えない |
| 脱糖と形式化 | 生成された実装をどう型付き表層へ渡すかを定める。辞書生成や表層の型付けの規則を変えるなら内側 | 型の表現・辞書・相互変換を増やすなら内側。積と和を普通の data として実装できる部分とも分ける | 生成道具の文字列出力自体は証明の外。出力は既存のレコード・関数・型クラスの脱糖を通る |
| 主な費用 | 最初は小さく見えるが、新しい用途ごとに処理系とライブラリを同時に変える | 中核の設計と証明が先に要る。JSON と生成器だけでなく一般化の範囲も決める | 道具の安全な編集、照合、ライブラリ、生成の品質が中心。既存ソースの一括移行は要らない |

標準の型クラスでなく利用者の任意の型クラスを導けるようにするなら、A の単純な固定規則では足りず、B または利用者が生成の規則を書ける別の仕組みになる。`@derive` を付ければ任意の関数の正しい本体が決まるわけではない。

### A の型付けと、標準ライブラリへの結び付き

A では、例えばレコード Box[T] の各欄の変換に Decode[T] が必要なら、それを生成する実装の型パラメータの制約として明示しなければならない。手書きの実装と両方ある場合は現在の重複の誤りとし、黙ってどちらかを選ぶ規則は加えない案が考えられる。再帰の辞書の構築を停止させる規則、見えない構成子、関数・Reference・Task などの未対応型の診断も要る。

Json の型の名前だけでなく、Option.None を省略と null のどちらにするか、数をどの Value にするか、失敗をどの型にするかまで処理系の導出に書けば、Json を吟味し直すたびに処理系も直す。設計者の「個々の標準関数の特別扱いを小さくする」という条件では、この方式を第一案にしない。

属性を読み取る部分と生成器を形式化の対象外にし、生成された通常の型付き表層だけを既存の検査で確かめる設計もありうる。その場合でも「導出が要求した実装を漏れなく作る」ことは既存の性質 1（脱糖の型の保存）から得られない。隠れた生成物を検査に通すだけで、導出全体を証明済みと扱うことはできない。

### B に必要になる型の構造の表現

レコードの欄の組合せを積（product）、構成子の選択を和（sum）として表し、型 T とその表現の型 R の相互変換を作る方式である。現在の一引数の型クラスでは「T ごとに違う R を型として選ぶ」機能がない。関連型や複数引数の型クラスを加える案、表現を型引数として明示した値にする案、異なる型の欄を扱う多相な操作を持つ案を先に比較する必要がある。

積と和の型自体は普通の data で宣言できる。そのことだけで、任意のレコードの欄の型・名前・制約の辞書を一般の関数へ渡せるわけではない。中身を共通の動的な値へ落とす案は、欄の取り違えを静的に検出する保証を別に作ることになる。型から導く仕組みの代わりとして安易に選ばない。

Scala 3 は Mirror に構成要素の型と名前を持ち、型クラス側の derived を呼ぶ方式を公式に説明する。[Scala 3 の一次資料](https://docs.scala-lang.org/scala3/reference/contextual/derivation.html) を 2026-10-17 に確認した。これは処理系が JSON を知らずに済む先例だが、Benitoite に Mirror の構文だけを加えれば使えるという根拠にはならない。現在ない型の対応と辞書の規則を導入する費用は残る。

B は学習の対象として価値がある。ただし今回の JSON と生成器の提供を前提に、関連型・型の構造・再帰と辞書を一度に確定する案は推さない。

## C の生成道具の具体案

道具は Benitoite の構文木（abstract syntax tree、AST）と名前解決した型の宣言を読み、既存の `.bnt` の宣言を出力する。型を正規表現だけで読み取らず、利用者の関数を実行して型を調べない。初版は `tools/derive/` に Rust の読み取り用 example と編集・照合の道具を置く案を推す。既存の移行道具と同様に、parser と型の情報を再利用でき、生成の都合を言語の型検査へ混ぜずに済む。Python の編集部で既存の `tools/source-migrate/` を使える範囲は後の実装プランで確認する。

サブコマンドと、エディタからの生成の操作（code action）は別の入口の選択肢である。初版から CLI に組み込む場合も、内部の生成部とテンプレートを型検査・脱糖から独立させる。公開の CLI の追加には help・使用法の誤り・`--version=json` の capabilities・Skill の案内との整合が要るので、C が「言語の変更なし」であることと「道具の実装が小さい」ことを同一視しない。

Gleam の公式記事は、復号の関数と JSON への関数を言語サーバの操作でソースへ生成する方式を説明している。外部生成の先例として確認したものであり、Benitoite で生成し直し忘れを防げる根拠は別に要る。[復号の生成](https://gleam.run/news/improved-performance-and-publishing/)、[JSON への変換の生成](https://gleam.run/news/hello-echo-hello-git/)（2026-10-17 確認）。

### 生成設定、出力の所属、再生成の照合

生成対象・種類・名前・欄の対応・手書きの変換を指す設定を、言語外の設定ファイルに置く。型を宣言したモジュール内の印で囲んだ領域に、通常の関数と必要なら implement を生成する。別モジュールに出す場合は関数だけにし、型と型クラスのどちらも宣言しない場所へ implement を出さない。非公開の欄を使う場合も型の宣言元のモジュール内を原則にする。

初版は型ごとの普通の変換関数と生成器を基本とし、Json.Encode・Json.Decode・Arbitrary という新しい公開の型クラスは必須にしない。汎用のコンテナの変換や生成には、要素用の関数を明示的に渡せる。後で型クラスを採る場合も、通常の implement と既存の辞書渡しで表せる範囲から始める。

| 操作の案 | 契約 |
|---|---|
| preview | 対象と未対応の欄を報告し、差分を出す。ファイルを書かない |
| apply | 読み込んだソースと設定のハッシュが一致する場合だけ、対象の生成領域を更新する。領域外と手書きの編集を上書きしない |
| check | 同じ型・設定から再生成した内容と管理された出力を比べ、不一致なら非零で終わる。自動で修正しない |
| 管理から外す操作 | 印と管理の記録を明示的に外し、以後は手書きとして扱う。単なる変更を検出しただけで管理を解除しない |

管理の記録（manifest）には道具と書式の版、対象の型の識別、宣言の構造、変換に使う関連型・手書き関数の契約、設定、生成出力のハッシュを含める。ローカルな通し番号だけを型の識別に使わない。単なる空白やコメントと、欄の追加・削除・改名・型の変更を区別する。生成器の規則を変えたときも check で検出する。

encode が getter で既知の欄を読むだけなら、新しい欄を黙って落としうる。decode と生成器の構築式は不足の欄で型の誤りになる場合があるが、それをすべての変更の検出に代用しない。キーの対応や Option の規則は型が変わらなくても意味が変わるため、設定と再生成の照合が要る。通常の `benitoite check` に Json 専用の照合は加えず、利用者の検査手順に生成道具の check を明示して組み込む案を推す。このため、その手順を実行しない利用者には自動で追従を保証できない。

生成済みの本体を利用者が編集したら、上書きせず差分を報告する。個別の変換を指定するか管理を外すかを選べるようにする。生成のファイルを信頼して型検査を省かず、通常の check と test へ渡す。

## JSON 変換の範囲と契約の案

0.0.8 の初版は型パラメータのない、再帰しない利用者のレコードを対象とし、入れ子のレコードも非循環なら扱う。型パラメータ・再帰型・直和型全体の導出は追加の範囲として別に判断する。カスタムの欄の型には、型の合う encode と decode の関数を設定から指定できる。型を変換できない場合は対象と欄の位置を示して生成を止め、コンパイルが通る仮の本体を出さない。

API の形は、例えば `encodePerson(value: Person) -> Result[Json.Value, ConversionError]` と `decodePerson(value: Json.Value) -> Result[Person, ConversionError]` とする。仮名 ConversionError は、入力の JSON の文法の ParseError と分け、欄・添字のたどり方、期待した型、見つかった値の種類を保持する。成功値の全データや秘密を失敗の説明へ自動で埋め込まない。最初の失敗を宣言の欄順に返す案を推す。複数の失敗を集める案は異なる戻り値と処理が要る。

| 論点 | 推す既定 |
|---|---|
| 欄の名前 | 宣言した名前をそのままキーにする。改名は設定の明示対応とし、重複するキーは生成前に拒否する。snake_case 等の一括変換は初版の必須にしない |
| 必須の欄 | 欠落・null・種類の不一致を失敗とする。既定値を暗黙に補わない |
| Option[T] | None は null と符号化し、欠落または null を None と復号する。Some は T の変換を使う。入れ子の Option や null を成功値として持つ欄は区別が消えるので、自動変換を拒否して手書きの対応を求める |
| 余分なキー | 初版の既定は拒否する。許す設定を選ぶ場合は、その契約と往復で捨てる情報を明記する |
| 数 | Integer は Integer、Float は有限値だけを Float として扱い、非有限値の符号化は Result.Error とする。Float の復号で Integer を受ける暗黙変換を初版の既定にしない |
| 基本型・コンテナ | String・Boolean・Integer・有限の Float、List、String を鍵とする Map、上記の Option を基本とする。他の幅の数・Decimal・Character・Bytes は自動の表現を先に決めず、明示した変換に委ねる |
| 外部の型など | 関数・Reference・Lazy・Task・継続・中身を見せない型は自動変換しない。既存の公開関数を使う変換を指定する |

Option の規則では欠落と null の違いは失われる。往復の約束は、対応した型の値で、各欄の変換が往復の条件を満たす場合の `decode(encode(x))` に限る。任意の JSON を戻した字面が同じになる保証や、NaN を含む浮動小数点の `=` による保証はしない。Json.stringify と parse を挟む場合の数の表現も別に確かめる。

重複キーは parse 後の Map には残らないので、Value からレコードへの変換だけでは「入力文字列に重複があった」ことを検出できない。これを厳密に拒否する JSON の入口は parser 側の別の契約になる。今回のレコードの変換の保証へ含めない。

これらの規則はテンプレートと通常のライブラリ関数に置く。処理系が `decodePerson` や Json の関数の束縛名を認識して特別な型付けを行う必要はない。非公式の Json に依存する補助ライブラリの名前空間も、その状態に合わせて決める。

## TODO-087 を生成器と実行の仕組みに分ける

入力の生成器（generator）は値を作る処理であり、性質を繰り返し検査する処理と同じものではない。縮小（shrinking）は、失敗する入力からより小さい失敗の例を探す処理である。どの型にも任意の値を作れるわけではなく、例えば型の構造だけでは「正の数」「整列済み」「二つの欄の合計が一定」といった利用上の条件は分からない。

### 入力の生成器と縮小を提供するライブラリ

生成器は、明示的な Random.Generator と大きさの予算を受け、値と次の Generator を返す関数として表す。例えば `Gen[T]` のレコードが `function(generator: Random.Generator, size: Integer) -> Pair[T, Random.Generator]` の関数を持ち、`Shrinker[T]` が `function(value: T) -> List[T]` の関数を持つ形である。型の別名や新しい組み込みの型は要らない。生成に失敗しうるものは、空の候補から無限に選び直すのでなく明示した失敗を返す別の組合せ方にする。

map・組合せ・List の長さ・Option の比率・整数の区間などを指定する普通の関数を用意する。値域の端・0・空・最小の要素なども候補に含め、一様な乱数だけが有用な入力だと決めない。fromSeed で作った Generator を明示して使えば、プロパティ自体のテストのエフェクトを増やさずに済む。Random.Generate の隠れた状態の種をグローバルに差し替える設計は初版の前提にしない。

生成道具は各欄の生成器を順に組み合わせる。縮小は、ほかの欄を固定して一欄ずつ縮めた候補を順に出す。全欄を同時に縮めるだけの方法は、一欄がこれ以上縮まないと他の欄も縮まらなくなるため避ける。利用者の条件を壊す縮小を自動で安全とはみなさず、欄または型全体の手書きの生成器・縮小へ置き換えられるようにする。

初版の導出は JSON と同じ非循環のレコードまでとする。再帰の data の自動生成には、大きさ 0 のときに選べる構成子、必ず値を作れるか、再帰の予算の分配が要る。葉のない `Loop(Loop)` のような型に、無限再帰する生成器を出すことはできない。関数・リソース・Task の生成、全型への無条件の Arbitrary の実装は加えない。Show・Order の導出も同じ改造の必須条件にしない。

### 既存の @test から呼ぶ性質の検査

ライブラリは明示した seed・試行数・大きさ・縮小回数の上限、Gen[T]、Shrinker[T]、純粋な `function(value: T) -> Result[Unit, String]` の性質の関数を受ける案とする。結果は成功か、元の入力・縮小後の入力・失敗の説明・再現に必要な情報を持つ失敗の値とする。反例（counterexample）の表示関数も普通の引数にでき、Show の導出を先に作る必要はない。

| 段階 | 振る舞いの案 |
|---|---|
| 生成・試行 | seed から順に入力を作り、指定回数まで性質の関数を呼ぶ。最初の Result.Error で縮小へ進む |
| 縮小 | 順序を固定した候補のうち、同じ性質が失敗するものへ進む。元の値と同じ候補や循環に対処し、試した候補の総数に上限を置く。全候補を試せなければその事実を残す |
| 報告 | seed、試行の番号、size、試行・縮小の設定、生成道具とライブラリの版、元の入力と得た反例を報告する。「最小」は保証せず、探索で得た小さい反例と呼ぶ |
| テストとの接続 | `@test` が失敗の値を文字列へ変換し Result.Error で返すか、最後に一度 Assert.fail を呼ぶ。既存の実行器では一つの @test の結果として報告する |
| 失敗の区別 | property の Result.Error を失敗として縮小する。生成不能・設定の誤りは検査の準備の失敗、実行時エラー・exit・中断は通常の実行の失敗として扱い、自動で縮小へ変換しない |

seed だけではライブラリや生成の順序を変えた後の同じ入力は保証できない。Random.fromSeed 自体の版をまたぐ契約と、生成器全体の再現の契約を分ける。長く保存したい失敗は具体的な入力も固定例にする。[QuickCheck の一次資料](https://hackage-content.haskell.org/package/QuickCheck-2.18.0.0/docs/Test-QuickCheck.html) も、生成と縮小を分け、版をまたぐ seed の再現を保証しないことを説明している（2026-10-17 確認）。

初版は純粋な性質を対象とする。外部の IO を繰り返す性質や State を使う性質を縮小するには、毎回の環境の初期化、操作の再現、実行回数と許可の意味を別に決める必要がある。既存の副作用のある @test は従来どおり書けるが、すべてをプロパティの縮小へ自動で適用する機能は約束しない。

回数の上限は性質や縮小の関数を呼ぶ回数を制限するものであり、利用者の関数自体の停止性を保証しない。縮小の候補の List を作る処理の資源量も、候補を試す回数だけでは制限できない。組み込みの縮小は有限の大きさの候補を作るよう設計し、利用者の関数による中断や資源不足は既存の実行の失敗として扱う。

### 実行器を拡張する案との差

専用の `@property` や引数付き `@test` を設ける案では、実行器が生成器を探す規則、型パラメータの具体化、seed・試行数の CLI、失敗した試行と縮小の JSON、途中の中断の報告が要る。S1 の検査方針と、0.0.7 の `test --check` の対象一覧・エフェクト上限・実行前の全入口の照合・formats の版まで合わせて変えることになる。引数の生成を非実行の検査中に実行する設計にはしない。

初版のライブラリ案では専用の属性を加えない。テストの型とエフェクトは既存の `@test` の宣言から分かり、testCheckReport の形式も増やさない。代わりに、seed や縮小の情報は既存の失敗の message に入る。機械が構造化した反例を直接扱いたい場合は実行器の報告の拡張に用途がある。この差を理由に、ライブラリ案を実行器の機能と同等とは説明しない。

## TODO-189・249 との関係

[操作の制約の調査](op-constraints.md) が扱う TODO-189 は、任意の型の値とその型クラスの辞書を操作からハンドラの節へ渡すための拡張である。JSON の変換、明示的な生成器、性質の結果の値は、通常の関数・引数・戻り値で書ける。したがって推す案に制約付きの操作は不要である。

例えば Show[T] を持つ関数が失敗を表示して Assert.fail(String) を呼べば、Show の辞書は関数の環境にあり、操作へ辞書を渡す必要はない。`Assert.equal[T: Show & equality]` を新設して任意の値を節で表示する案なら TODO-189 が関係するが、現在の Assert.equal の型を変える理由は本件からは生じない。既存の Assert は VM の型の情報を使って表示しており、Show を宣言しているとはみなさない。

型クラスを使う Gen や Json.Decode を後で設けても、メソッド呼び出しだけなら現在の関数の辞書渡しで足りる。「型クラスを使う」と「型クラスの制約を持つ操作を使う」を区別する。操作を使う設計にすると、S2 が調べた節の辞書の所属・引数順・値化・交換形式の作業が増える。

[型付きの失敗の調査](typed-failure.md) の TODO-249 も必須にしない。decode と性質の関数は Result で失敗を返せる。任意の Assert の失敗を捕まえて試行し直す設計は、利用者の Assert ハンドラで書く候補もあるが、全四操作の差し替えと非再開時の解放を確認する作業になる。型付きの失敗の境界が、実行時エラー・die・中断まで捕まえることもない。初版は明示した Result の性質に絞り、捕捉と縮小を一つの機能にしない。

| C が出す通常の record・関数・implement | 既存の型付き表層・型検査・脱糖を通す。規則を増やさない限り新しい構文と性質 1 の場合分けは要らないが、生成結果を検査から除外しない |

後の検査は、実際の型の宣言から生成し、普通の check・test を通ることを主な契約にする。欄の追加で符号化が黙って古いままになる退行、名前の変更・衝突・見えない欄、手書き領域の保護、同じ入力での差分の安定、設定変更の検出を確認する。型が変わらない JSON の規則には、欠落・null・余分なキー・数の失敗・入れ子の欄の位置を観測する対照例が要る。

生成器は同じ seed と版での再現、予算内の大きさ、縮小の候補の順序と上限、既に縮んだ値での停止、失敗した性質の保持、通常の @test からの失敗報告を確認する。生成した本体の文字列だけを固定してもこれらの契約を確かめたことにはならない。テストを追加する段で test-audit を適用し、重複する検査を増やさず、TODO-255 の方針に沿って実行時期を決める。今回は実装もテストの追加も行っていない。

## 大きさと段の見込み

推す C の範囲では、TODO-063 は 6〜9 作業、TODO-087 のライブラリとレコードの生成器・縮小は 6〜10 作業、共通の読み取り・設定・差分・更新の保護・再生成の照合は 3〜5 作業、合わせて 15〜24 作業を見込む。共通部を各項目へ重ねて数えていない。関係する文書・Skill・受け入れの確認はこの内数である。

順序は、共通の読み取りと生成の管理、JSON の変換と照合、手書きでも使える生成・縮小・性質の検査のライブラリ、レコードからの生成器の生成とする。TODO-255 を最初に実装する方針は保ち、全六項目の設計を一度に行い、実装はこの順序と S2 の形式化先行の順序を合わせて段に分ける。

A の固定導出まで含める方式なら合計 20〜32 作業、B の汎用の型の表現を先に設ける方式なら 28〜45 作業以上という粗い比較になる。実行器の専用対応はどの方式でも別に 4〜7 作業、型パラメータと再帰の data の導出は別に 4〜8 作業以上を見込む。B は型の表現を選んでおらず、証明も試していないため、この数を上限の約束にできない。

作業は、型と関係する検査が通るレビュー可能な単位であり、日数・機械の検査時間ではない。初版の範囲を選ぶなら、未対応の型と実行器の専用対応を TODO-087 全体の実装済み機能に含めず、後の課題の扱いを設計者と決める。今回は docs/todo への追記や項目の完了扱いは行わない。
