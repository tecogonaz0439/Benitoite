# TODO-189 操作の型パラメータの制約の調査

2026-10-17、HEAD `0027a22c171269cf5e5d975ee86bfd568efebb49` を基準とする。型クラス（type class）の制約を操作からハンドラの節へ渡す方法を調べた。処理系と Lean は変更せず、過去の試みの再実行もしていない。追加する規則は合意前の案である。

## ADR 0312 が禁じた理由

[ADR 0312](../../2026-10-09-design-first-release/decisions/0312-no-trait-constraints-in-operations.md) は、構文の難しさや型クラスとエフェクトの原理的な両立不能を理由にした制限ではない。呼び出し側から節へ実装の辞書を渡す規則が、コア計算・型検査・脱糖・実行の設計に欠けていたため、制約を組み込みのものに限った判断である。

組み込みの制約（built-in constraint）は、型の構造から満たすかを判定し、辞書を渡さない。型クラスの制約は、メソッドをまとめた実装の辞書を渡す。節で `[T: Show]` の Show を使うには、呼び出した位置で選んだ Show[T] の辞書を受け取る必要がある。節の定義位置で、任意の T に対する具体的な実装を選び直すことはできない。

現行の [01-06](../../../design/01-spec/01-06-type-system.md#エフェクトの宣言とハンドラの型付け初回リリース版) と `crates/benitoite/src/syntax/parser/effects.rs::push_op` はこの制限を保つ。parser は関数のシグネチャを読んだ後、型クラスの制約に E0510 の `trait_constraint` を出し、その制約を除く。操作の型構成子のパラメータ、エフェクト変数、自分で書く uses も別の理由で拒否する。TODO-189 でこれらを一括して許す必要はない。

## TODO-162 フェーズ 2 の試みで分かったこと

[adr0312-trial.md](../../2026-10-10-TODO-162-desugar-formalization-phase2/adr0312-trial.md) は、取り込んでいない試みの枝 `exp/TODO-162-adr0312-trial` の記録である。試みの Lean の定義を現在の formal/ にあるものとして扱わない。

| 試した方式 | 記録にある結果 | 結果の限界 |
|---|---|---|
| 辞書を操作の値引数より前へ渡す | 操作の宣言の params に辞書型を前置し、呼び出しは辞書を前置し、値化は辞書を捕えるラムダにし、節でも同じ順に束縛した。Release と性質 1 の言明を変えず、型の保存を sorry なしで証明した | 表層の WellFormed には辞書の型パラメータ番号の範囲条件を追加した。処理系は変更していない |
| 呼び出しと節から辞書を除く | 表層では型が付くが、節の辞書変数に写し先がなく脱糖が none となる反例を得た | 一般の全域性を否定する定理がある。辞書が要る規則そのものを表層から消せば検出できない |
| 辞書を束縛せず変数番号だけ残す | 節の本体の型付けが成立しないことを示した | 比較用の保存証明の試行だけに意図的な sorry を一つ残した。取り込み可能な成果物ではない |

具体例では二つの辞書を持つ直接呼び出し、値として使う形、節の変数番号を確認し、`choose[T: Echo](x: T) -> T` の節が辞書の echo を使って再開する結果も計算した。一方、最終の既定の lake build が成功したことから、差分テストまで通ったとは言えない。記録の Exchange.Convert と desugarDiff は節の追加の ndicts に未対応で失敗し、既定の build はそれらを import していなかった。

この試みは、辞書を引数として渡す表層の規則が整合する根拠になる。現在の契約名付きの関数型、呼び出しのソース順、die、表層の checker にまでそのまま適用できる根拠ではない。古い枝を丸ごと取り込む案は推さない。

## 現在の辞書渡しと、操作で不足する情報

現行の [02-05](../../../design/02-impl/02-05-typechecker.md)、[02-06「辞書の引数」](../../../design/02-impl/02-06-ir-and-lowering.md#辞書の引数)、[01-12「型クラス」](../../../design/01-spec/01-12-core-calculus.md#型クラス) は、関数とメソッドについて次の仕組みを持つ。

1. 型検査が宣言の制約の順に辞書の根拠（dictionary evidence）を求める。実装を具体化した辞書、関数が受け取る辞書、上位の型クラスの辞書の取り出しを表す。
2. 制約付きの関数へ、辞書を値の引数の前に渡す。関数型の利用者のパラメータ名に隠れた辞書の名前を混ぜない。
3. 制約付きの関数を値として渡すときは、値の引数だけを受け、選んだ辞書を捕えるラムダにする。
4. メソッドは、受け手の辞書からメソッドを取り出して呼ぶ。単相化（monomorphization）によって型ごとに関数を複製しない。

調査した処理系の箇所と差分は次のとおりである。パスは `crates/benitoite/src/` の下を示す。

| 箇所 | 現在の実装 | TODO-189 で必要になること |
|---|---|---|
| `typeck/decls.rs` の parameters・操作の宣言 | Scheme に class_constraints を記録できる共通処理で操作も作る。ただし parser が型クラスの制約を除く | 禁止の解除だけで済ませず、操作の制約が最後まで保たれることを確認する |
| `typeck/traits/solve.rs::resolve_normalized` | 定義の Param の制約から辞書を探す。節の Rigid を局所の型クラスの辞書へ対応付ける分岐はない | 節の識別番号・型パラメータ番号に対応する局所辞書と、上位の型クラスへの解決を加える |
| `typeck/effects/handle.rs::check` | 操作の型パラメータを節の Rigid にし、値引数と継続の型を検査する | 宣言の制約の辞書を節の環境に加える。外側の関数と内側の節で制約の番号が衝突しないようにする |
| `types/mod.rs::DictExpr` と `ir/desugar/dicts.rs::dict` | DictExpr::Param は現在の定義の制約番号を指し、desugar は self.scheme から読む | 単に同じ番号を流用すると外側の辞書を指す。節の辞書の所属を保持する表現と環境への対応を定める |
| `ir/desugar/exprs.rs::prepare`・name_expr、`dicts.rs::dictionary_lambda` | 直接の Op の呼び出しは name_dicts を通る。一方、名前の値化は制約付き Fn と Method だけを辞書ラムダにする | 制約付き Op の値化を追加し、部分適用・パイプも同じ辞書の捕捉にそろえる |
| `ir/core_ir.rs::Clause`・DictParam、`ir/desugar/effects.rs::handle` | Clause は値の params と cont を持ち、節の辞書の引数を持たない | Rust の IR では辞書を普通の値と別に表すので、節に辞書の束縛を保つ欄と走査・自由変数・低位化の対応が要る |
| `ir/check.rs::clause`・辞書の検査 | 節の値の params と Scheme の params を照合し、値と継続の環境を作る | 辞書の個数・対象の rigid 型・上位の辞書・参照の範囲を独立して照合する |
| `ir/desugar/decls.rs` の OpDef、`bytecode/codegen/tables.rs` | 操作の arity は値の params.len() から作る | 実行時の個数を「辞書数＋値引数数」にする。表層の個数とは分ける |
| `bytecode/codegen/emit.rs` の Op の直接呼び出し | dicts が空でなければ `operation with dictionary arguments` という内部エラーを返す | 辞書を先頭のレジスタへ置いて PERFORM する。単に禁止を外しても動かない |
| `vm/dispatch/handlers.rs::handle`・invoke_clause | operation.arity 個の引数を読み、節の原型を arity＋1 と照合する。最後の引数は継続 | 既存の一般の引数受け渡しを使える候補である。辞書もヒープの値として保持し、GC・継続の捕捉・引き継いだ節の実行を確認する |

VM の表に型クラスの名前を加えて実装を探し直す必要はない。選んだ辞書を既存の値として渡す案なら、命令の符号化を保てる見込みがある。ただし、コード生成と操作・節のメタデータの更新は必須であり、命令の変更が不要であることは実装で確かめるまで確定しない。[02-08「ハンドラと継続」](../../../design/02-impl/02-08-vm.md#ハンドラと継続) の実行時の範囲検査も保つ。

## 推す規則と用途の例

次のコードは TODO-189 の提案を示す。現行の parser では制約を拒否する。モジュール全体や main の定義は省く。

```text
import Benitoite.Unofficial.Trait

effect Render
  function render[T: Trait.Show](value: T) -> String
end effect

handle
  render(42)
with
  case render(value) ->
    resume(Trait.Show.show(value))
end handle
```

呼び出しでは Show[Integer] の辞書を選ぶ。節では T を具体的な Integer とは見なさず、任意の T とその Show[T] の辞書を受け取る。節のソースには辞書の引数を書かない。制約の順に辞書、宣言の順に値引数、最後に継続を渡す案を推す。組み込みの制約には辞書を割り当てない。

複数の辞書、上位の型クラス、外側の制約付き関数の中の節、節内のラムダが辞書を捕える場合、制約付きの操作を値として高階関数へ渡す場合を、設計の例に含める。現在の契約名と評価順を保ち、ソース順に値引数を評価した後、宣言位置へ配置する。辞書を余分な公開の引数名として要求しない。辞書を作る内部処理も、関数値を得る時点と操作を呼ぶ時点のどちらで行うかを既存の辞書ラムダとそろえる。

docs/todo の TODO-206 のログも用途の候補だが、ログの標準モジュールの実装を前提としない。上の純粋な Render は、辞書を受け取った節がメソッドを使った結果をそのまま観測できる小さな例である。新しいテストを設計するときは test-audit に従い、既存の操作・辞書の検査に不足する契約だけを補う。

## 形式化で更新する範囲

操作の呼び出しと値化・節の束縛・辞書渡しは、[07-04「01-12 との対応」](../../../design/07-quality/07-04-formal-semantics.md#01-12-との対応) の内側である。TODO-189 は、parser の許可だけを対象外として済ませる変更ではない。

現在の `formal/Benitoite/Surface/Typing.lean` の E_Op は操作の元の関数型を与え、HasClauses は継続、逆順の値引数、外側の環境を作る。`Surface/Desugar.lean` は opName をコアの op へ写す。`Release/Syntax.lean::OpDecl.params` は普通の型の列であり、辞書型も表せる。したがって、試みの方式では次を先に行う。

1. Surface の宣言に操作の制約を保持し、呼び出しの辞書の根拠、値化のラムダ、節の辞書の束縛を追加する。WellFormed、型の置換、番号の移動、自由変数の範囲も更新する。
2. コアの操作の引数列へ辞書型を前置する。現行の契約名の NamesWF に対して内部の辞書の名前をどう付けるかを定め、公開の値引数の名前とは区別する。元の試みには、その後に加わった契約名と呼び出し順の規則の確認がない。
3. 性質 1 の証明、表層のエフェクト健全性、Check の節と辞書の検査・健全性を直す。Release の V_Op・C_Handle・E_Op が同じ規則の形で使えるか確かめる。形が保てる場合も、辞書を含む引数であることを 01-12 に写す。
4. Exchange・Rust の書き出しと六入口を更新する。昔の試みで失敗した Convert と desugarDiff を今回は完了条件に含める。新しい入力を対象外へ分類して成功としない。

Release が通常の引数として辞書を受け取る方式を保てるなら、性質 2・3 の言明を変える必要はない見込みである。コアの構成を変えないことを先に仮定して証明を省かず、既存の定理・仮定が保たれることを確認する。定義・言明は所定のレビューを受け、Lean の定義と性質 1 の証明を通してから処理系を変える。01-12 と 07-04 の更新、sorry のない lake build、check-formal.sh が必要になる。今回はいずれも実行していない。

## TODO-249 と段を分けられる理由

TODO-189 は「任意の型 T の値について操作の節がメソッドを呼ぶ」ための拡張であり、TODO-249 は「境界が処理するエラー型 E を呼び出しから捕捉まで同じ型として保つ」ための拡張である。`raise[T, E: Show](error: E) -> T` の辞書だけを渡しても、節で分かるのは未知の E を表示できることまでである。境界が指定した AppError として Error に包むための同一性は得られない。

逆に、TODO-249 の E の追跡に Show は不要である。表示が必要な境界の普通の関数に `[E: Show]` を付ければ、現在の関数の辞書渡しを使える。0.0.6 の Q9 とも一致する。Result の Monad 化（docs/todo の TODO-164）、ログの標準化（TODO-206）は両項目の前提にしない。

共通の設計として、操作の型引数の束縛、節の環境、辞書・値引数・継続の順序、部分適用と値化、交換形式を合わせて決める。実装の段は TODO-255 の後、TODO-189 の Lean → 処理系、TODO-249 の Lean → 処理系と分ける案を推す。189 を先にする理由は、既存のコアへの写し方が試されており、節の内部引数の契約を先に揃えられるためである。249 の仕様を決めずに 189 を前提化する意味ではない。問いは [O1〜O6](typed-failure-questions.md#o1-操作に許す制約と型パラメータの範囲) にある。
