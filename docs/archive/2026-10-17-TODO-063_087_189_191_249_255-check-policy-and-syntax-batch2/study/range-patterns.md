# TODO-191 範囲のパターンと網羅性の調査

2026-10-17、HEAD `0027a22c171269cf5e5d975ee86bfd568efebb49` の設計書・処理系・Lean の定義を調べた。以下の追加規則と作業数は判断の案であり、設計者の合意や実装済みの仕様ではない。処理系・現行の設計書・テスト・formal/ は変更せず、ビルドと差分検査も実行していない。

網羅性（exhaustiveness）は、対象の型のどの値にも分岐が照合する性質である。型付き表層（elaborated surface syntax）は、型検査が求めた型や辞書の情報を付けた表層の構文を指す。

推す案は、0.0.8 では `Character` の全域を覆う範囲とリテラルの組合せを網羅と認め、`Integer` は現在の保守的な判定を維持することである。理由: 文字では現在の値のモデルのまま判定を改められるが、整数では実際の 64 bit の値域と Lean の数学的な整数の違いを先に解消する必要がある。両方を一度に変更する案も、下の「整数の全域も認める場合」に必要な作業を示す。判断は [P1〜P5](range-derive-questions.md) に残す。

## 現行の仕様と、判定で失う情報

[01-02「パターンの拡張」](../../../design/01-spec/01-02-syntax.md#パターンの拡張初回リリース版) と [01-05](../../../design/01-spec/01-05-data-types.md#パターンの拡張初回リリース版) は、両端を含む `下端..上端` を定める。両端は同じ型の Integer のリテラルか Character のリテラルであり、片端の省略、浮動小数点、Byte と追加の幅の数は対象ではない。下端が上端を超える形は誤りである。Integer64 は Integer の別名なので同じ扱いになる。型の値域は [01-04](../../../design/01-spec/01-04-types-basic.md) が定める。

| 型 | 実際の値の全体 | 現行の網羅性の判定 |
|---|---|---|
| Integer | −2^63〜2^63−1 | 全域を覆っても `_` か変数が要る |
| Character | U+0000〜U+D7FF と U+E000〜U+10FFFF | 全スカラー値を覆っても `_` か変数が要る |
| String | スカラー値の有限列 | リテラルだけでは網羅と認めない。範囲は書けない |
| Byte、追加の幅の整数 | 幅ごとの値域 | 定数・範囲パターン自体を許さない。今回自動的に解禁しない |

[01-05「網羅性の検査」](../../../design/01-spec/01-05-data-types.md#網羅性の検査) は、意味として全値を覆うことと、処理系が網羅と判定することを区別している。現在は後者を保守的にしており、範囲・リテラルをどう並べても「残りの値」があると扱う。ガード（guard）の付いた分岐は網羅性に数えず、コンマで並べる選択肢は別々に数える。選ばれない分岐・選択肢は警告でなく誤りである。

[02-05「本体の後の検査」](../../../design/02-impl/02-05-typechecker.md#本体の後の検査) は、有用性（usefulness）の手順を定める。問いのパターンに照合し、それまでの行に照合しない値があるかを調べる手順である。問いを `_` にすれば網羅性、一つの束縛のパターンと比べれば必ず照合するか、前の選択肢と比べれば選ばれないかを判定できる。

| 処理系の箇所（`crates/benitoite/src/` 以下） | 調べた内容 |
|---|---|
| `typeck/pattern_ext.rs::pattern`・`range_end` | 両端の種類、負号、i64 の値域、逆転を検査し、確定した端を `range_bounds` に保存する |
| `typeck/patterns.rs::shapes`・`specialize` | 列のリテラルと範囲を端で分割する。範囲に覆われる区間を構成子のように扱い、常に `Shape::Other` を足す。サロゲートだけの区間は除く |
| `typeck/patterns.rs::check_match`・`check_binding` | 網羅性・選ばれない選択肢・覆っている前の選択肢・束縛の判定を同じ手順で行う。`CoverageView` で拡張可能な型の将来の形も扱う |
| `typeck/pattern_ext.rs::check_body` | 結果を E0601・E0602・E0607・E0608 に変換する。予算を超えたら E0609 だけを出す |
| `ir/desugar/patterns.rs`・`ir/decision.rs` | 脱糖（desugaring）後も範囲を保持し、実行のための分岐を作る。`Domain` は整数の最小・最大と文字のサロゲートの境界を扱う |

Rust の `interval` は i64 の値を i128 へ広げ、`Shape::Interval` も i128 の端を持つ。`shapes` が上端の次に使う `saturating_add(1)` は、この入力範囲では飽和せず、i64 の最大値の次も表せる。Lean は数学的な整数で `hi + 1` を作る。端の加算の実装に同じ変更を重ねる必要はないが、両者とも「型の全域に残りがあるか」を調べる規則はまだない。`Shape::Other` を無条件に消す一行の変更では足りない。

Character の全スカラー値は Lean の Char の値の全体でもある。そのため `Exhaustive` は現在も全域の範囲について成り立ちうる。しかし Integer の i64 全域の範囲は、Lean の `Int` 全体を覆わない。例えば 2^63 は現在のモデルでは Integer の定数であり、その範囲に入らない。この差は [07-04「01-12 との対応」](../../../design/07-quality/07-04-formal-semantics.md#01-12-との対応) が数の値域を形式化の保証に含めないこととも関係する。文字の変更と同じ大きさには扱えない。

`Coverage.shapes_cover` と `shapeStep_character` は、型の値の形を調べるときに必要な形が列挙されることを証明する。`.other` が常にあることを使う箇所を、文字では「全スカラー値を覆っていなければ残りを置き、覆っていれば任意の Char が列挙した区間のどれかに入る」という補題へ改める必要がある。範囲の意味や新しいコア構文の追加は不要と見込むが、手順の健全性の証明を省けるわけではない。

## 他の言語との比較

2026-10-17 に次の一次資料を確認した。網羅性を採用する理由は言語の多数決ではなく、型の値域を静的に確定でき、覆っていない値を作らない判定を定義できることである。

| 言語 | 確認した範囲 | Benitoite への示唆 |
|---|---|---|
| Rust | 固定幅整数と char の範囲が型の全値を覆えば、必ず照合するパターンとする。char はスカラー値の二つの区間である。[言語リファレンス](https://doc.rust-lang.org/reference/patterns.html#range-patterns) | 整数の幅と文字の欠けた区間を型ごとに定める方式の先例になる |
| OCaml 5.3 | 文字の範囲は文字リテラルの選択肢の省略形であり、整数範囲はその文法にない。[マニュアル](https://ocaml.org/manual/5.3/patterns.html)。処理系の `full_match` は文字の定数の集合が 256 個なら全体と扱う。[一次ソース](https://github.com/ocaml/ocaml/blob/5.3/typing/parmatch.ml) | 文字の全体を列挙して認める方式もある。ただし 256 個の文字と Unicode スカラー値は同じ集合ではない |
| F# | 公式のパターン一覧に数値区間のパターンはなく、範囲の比較の例は `when` のガードと `_` を用いる。[パターン](https://learn.microsoft.com/en-us/dotnet/fsharp/language-reference/pattern-matching)、[match の説明](https://learn.microsoft.com/en-us/dotnet/fsharp/language-reference/match-expressions) | ガードの比較を全域として推論する拡張まで必要だとは言えない |
| Haskell 2010 | パターンの文法はリテラル・構成子・変数などを持つが、区間のパターンを持たない。[Report §3.17](https://www.haskell.org/onlinereport/haskell2010/haskellch3.html#x8-600003.17) | 数列の式の構文があることから範囲パターンの網羅性を類推できない |

OCaml の全域判定については文法とソースから確認した。F# と Haskell のガードを含む任意の式の網羅性について、比較した資料以上の保証を主張しない。他の処理系をインストールして実行する比較は行っていない。

## Character の全域を認める規則の案

型の値の集合を `Dchar = [0, 0xD7FF] ∪ [0xE000, 0x10FFFF]` とする。文字のリテラルも両端の等しい区間として扱う。区間の和が Dchar を覆えば、その列に残りの値の形を置かない。数えるのはガードのない行であり、入力値が実行時にどこから来るかは調べない。

1. 区間は文字の有効な値域との共通部分をとり、サロゲートだけからなる隙間は不足としない。型の全体の二つの区間の端も分割に使う。全スカラー値の列挙は不要である。
2. 単独の範囲だけでなく、分けた範囲、リテラルとの組合せ、コンマで並べた選択肢にも同じ規則を使う。先頭のパターンが全域を覆う場合だけの特例にしない。
3. レコード・構成子・リストの中の文字も、行列の再帰の各列で同じように判定する。複数の欄の相関は行列のまま保持し、欄ごとの和だけで match 全体を網羅と決めない。
4. ガードが `true` と書かれていても、それだけで覆う行に数えない。既存の評価・型の規則を保つ。
5. 単独で全域を覆う範囲は、`bind`・`shadow` の左辺でも必ず照合すると認める。複数の範囲の選択肢は match だけの構文なので、束縛へ新たに加えない。
6. 将来の構成子に備える `CoverageView` の規則はそのまま使う。文字の欄をすべて覆っても、パッケージ外の拡張可能な型の将来の構成子は覆わない。

以下は変更後の受理の案であり、0.0.7 では E0601 の対象である。

```text
function classify(c: Character) -> Boolean
  return match c with
    case '\u{0}'..'\u{d7ff}' -> true
    case '\u{e000}'..'\u{10ffff}' -> false
  end match
end function
```

一文字でも有効な値を残せば E0601 のままとする。診断の反例は、実際に存在する未被覆の文字か区間を表示する案を推す。サロゲートを反例として示さず、Integer を現行維持とする場合の `_` と区別する。反例が示す値と元のパターンの照合の不一致も確認対象になる。

### 診断と互換性

新しい診断番号は原則として要らない。全域を覆う match の E0601 と束縛の E0607 が消え、既存の範囲の種類の誤り E0606・逆転 E0605・値域の誤り E0408 は保つ。覆い尽くした後の選択肢には E0602（分岐全体）または E0608（一部の選択肢）を出す。覆った前の分岐の位置の選び方と、予算超過 E0609 も保つ。

この変更は受理の追加だけではない。例えば全域の文字の範囲の後に `_` を置いた既存コードは、現在は必要な分岐として通るが、変更後は選ばれない分岐となる。ガードの付いた後続の `_` も、先のガードなしの行で覆われていれば同じである。移行は、選ばれないと確認できた分岐を除くか、必要な処理を前の分岐へ移す。自動で `_` を消すだけではその本体の意図を判断できないため、生成した差分を確認する形にする。破壊の扱いと CHANGELOG への記載は docs/todo の TODO-250 の方針に従って判断する。

### 形式化と処理系を変える順序

TODO-191 は網羅性の判定を変えるので形式化の内側である。新しい字句がないことを理由に対象外とはしない。

3. 01-12 の写し、02-05 の手順、01-05 の規範、07-04 の対応表を揃える。定義と言明の所定のレビューと `sorry` なしの `lake build` を終えてから処理系へ進む。
4. Rust の区間の分割・残りの判定・反例の表示を揃える。`ir/decision.rs` の実行用の分割と参照インタプリタが受理の増えたソースを正しく扱えることも確認する。
5. 独立した入力の比較と、本番ソースからの型検査・脱糖・実行への接続を確認する。例・言語リファレンス・Skill の生成物も後の実装で更新する。

現在の [check-formal.sh](../../../../scripts/check-formal.sh) は、`coverage_export` が出す独立した入力を `formal/CoverageDiff/Main.lean` で比較し、型検査が出力したプログラムの match・束縛を `formal/CoverageProgramDiff/Main.lean` でも比較する。前者には i64 の両端・サロゲート境界・全域の範囲が既にある。比較は網羅したかだけでなく、反例・選ばれない選択肢・覆っている選択肢も扱う。六入口の件数と対象外・再帰の打切りも照合する。独立した入力で全域が通るようにするだけでは、本番の parser からの接続の確認にならない。

## Integer の全域も認める場合

Integer の規則を変えるなら、`Dint = [−2^63, 2^63−1]` とする。数え方は文字と共通にし、任意の有限個の区間とリテラルの和が Dint を覆えば網羅とする。Rust では既存の i128 の端を使って上端の次も正確に扱い、値域の最小と最大の次を分割に含める。新しい幅や片端省略を加えない場合でも、次のどちらかの形式化が要る。

| 方法 | 必要な根拠と影響 |
|---|---|
| コアの整数の値を有界にする | 定数の型付け・値の形・組み込み演算の仮定を合わせ、代入・保存・進行・表層のリテラル・検査の健全性まで再点検する。演算の実装全体を証明する必要性とは分けるが、現在の無条件の `Inhabits.const` のままでは済まない |
| 有界の値についての別の網羅性を設ける | 実際に型の付く値が有界の値の形に入ることを示し、C-Match・表層の型付け・検査の健全性へ接続する。広い `Int` の値を含む旧 `Exhaustive` を結論にしたまま通すことはできない |

交換形式で i64 外を拒否するだけでは、Lean の任意の値についての定理の反例は消えない。範囲の端だけを制限する方法も同じである。証明の前提と結論を変えるなら、その言明を先にレビューする。文字の判定に合わせて整数の `.other` も無条件に消す案は推さない。

## 作業の大きさの見込み

Character に限る案は 5〜8 作業を見込む。内訳は Lean の定義・補題と健全性 2〜3、Rust の判定・診断と交換の接続 2〜3、移行の調査と文書・生成物・受け入れの確認 1〜2 である。Integer まで含める場合は、これに有界のモデルの設計・証明と Rust の整数の全域判定と接続で少なくとも 4〜8 作業を加える見込みである。証明の試作前なので上限を確定できない。
