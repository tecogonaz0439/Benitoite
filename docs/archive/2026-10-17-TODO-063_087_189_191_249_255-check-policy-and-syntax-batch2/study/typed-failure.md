前の改造では TODO-251 と TODO-249 を一緒に検討し、TODO-251 を先に実装した。[decisions.md](../../2026-10-15-TODO-018_027_072_251-keywords-open-types-try-or/decisions.md) の Q6〜Q10・Q20 と、[design.md](../../2026-10-15-TODO-018_027_072_251-keywords-open-types-try-or/design.md) の範囲の記述を照合すると、引き継ぐ判断は次のとおりである。

| 終了（Q8・Q10） | die は任意の戻り値の関数で使え、`Process.Exit` を持つ。既存の exit に内部の報告を付ける | 回復可能な失敗の捕捉は die を自動で捕まえない |

## 現在の失敗・戻り値・終了の区別

現行の標準ライブラリに `Fail` というエフェクトはない。利用者は任意の名前のエフェクトを宣言できる。[01-06「エフェクトの宣言とハンドラの型付け」](../../../design/01-spec/01-06-type-system.md#エフェクトの宣言とハンドラの型付け初回リリース版) の `Abort` は、その例である。

```text
effect Abort
  function fail[T](message: String) -> T
end effect
```

この `T` は操作を呼ぶたびに決まる結果の型であり、失敗の型ではない。ハンドラの節では T をほかの型と等しくできない型（rigid type）として扱う。T の値を受け取らない節では成功値を作って resume することができず、節の結果で handle 全体を終えられる。String を具体的な AppError に替えれば、AppError を失わずに複数の関数をまたぐ打ち切りも、現在の機構で書ける。

一方、`fail[T, E](error: E) -> T` と操作の型パラメータを増やすだけでは、汎用の型付きの失敗にはならない。この形の節では E も呼び出しごとに異なる rigid な型となり、境界で指定した一つの E として照合したり、`Result[U, E]` に格納したりする根拠がない。操作の多相性と、呼び出しから捕捉まで共通に追跡するエラー型を区別する必要がある。

| 現在の機能 | 型と作用先 | 脱糖・実行 |
|---|---|---|
| `Result[T, E]` | Ok に T、Error に E を保持する普通の直和型（sum type） | 構成子の値と match。保存・集計ができ、制御を打ち切らない |
| `try r`、`try r or return` | r は標準の Result または Option。最も内側の関数・ラムダへ Error / None を返す。Result の E は戻り値と同じ型 | 入力を一度保存し、match の失敗側を escape にする。関数の境界 mark まで抜ける |
| `try r or die` | 成功値の型 T を持ち、囲む戻り値を制約しない。Result の E に Show、追加の効果に Process.Exit | 失敗側で説明、Show の原因、`Process.exit[T](1)` の順に計算する |
| `Process.exit[T](code)` | `function(code: Integer) -> T uses Process.Exit`。利用者のハンドラで処理できる | 既定の操作なら実行全体を終了する。型付きの失敗を返す操作ではない |
| 利用者の `Abort.fail` | 関数型に Abort が残る。すべての操作を処理する handle が Abort を除く | 最も内側の該当操作の節を呼ぶ。非再開の節なら本体の続きを捨てる |

根拠は [01-09「エラー処理」](../../../design/01-spec/01-09-errors.md)、[01-07「エフェクト」](../../../design/01-spec/01-07-effects.md)、[01-12「コア計算と脱糖」](../../../design/01-spec/01-12-core-calculus.md) である。`try` は外側の handle を探す構文ではなく、List.map のラムダ内に書けばそのラムダを終える。型付きの失敗は List.map の呼び出し自体を囲む境界まで打ち切れることに追加の用途がある。

## 型付きの失敗の追加方式の比較

| 案 | 得られること | 残る問題・作業 |
|---|---|---|
| 具体的なエラー型ごとに利用者が effect を宣言する | 現在も可能。型を消さず、非再開ハンドラで処理できる | 汎用の相互変換関数が一つの E を扱えず、TODO-249 の全体を満たさない |
| 一般の `effect L[E]` | 利用者の失敗・状態などへ同じ仕組みを使える | 宣言、操作と節の型引数、同じ L の複数の具体化、型の代入と効果の集合全体を設計する必要がある |
| 標準の失敗だけに `Failure.Fail[E]` を設ける | 任意の E を静的に保持し、既存の handle と操作の実行を基礎にできる | 標準専用の型付き原子と節の規則が増える。名前だけを追加して済む方式ではない |
| 内部で全関数の戻り値を Result 相当へ変換する | 打ち切りを戻り値で表せる | 高階関数・関数型・既存のハンドラとの対応を新たに証明する。成功時の費用も測定が要る |

推す案は、0.0.8 の公開範囲を標準の失敗に絞り、既存のハンドラへ統合する第三案である。理由: TODO-249 が求める任意のエラー型と境界変換を提供しながら、一般のエフェクト宣言の型パラメータや高カインド型まで同時に確定せずに済む。内部の表現は、一般化の見込みだけを理由に公開の構文を増やさず、Lean の先行作業で選ぶ。一般の `effect L[E]` を選ぶ案も、[F1](typed-failure-questions.md#f1-エラー型をどこに保持するか) に残す。

### 追加案の型と名前

次は提案を比べるための記法であり、0.0.7 で実行できるコードではない。`Failure` は明示的に import する標準モジュールの仮名で、prelude に同名の名前を追加しない。

```text
Failure.raise[T, E](error: E) -> T uses Failure.Fail[E]
Failure.fromResult[T, E](result: Result[T, E]) -> T uses Failure.Fail[E]
Failure.toResult[T, E, effect Rest](body: function() -> T uses Failure.Fail[E], Rest)
  -> Result[T, E] uses Rest
```

raise の T は節の内側で任意のままにし、E は境界が処理するエラー型に固定する。この二つの束縛を分ける。fromResult は引数を一度評価し、Ok なら T を返し、Error なら E をそのまま raise する。toResult は、受け取ったゼロ引数のラムダをハンドラの内側で一度呼び、成功を Ok、非再開の節の E を Error にする。引数に計算済みの T を取る関数では、捕捉前に失敗してしまう。

回復して T を返す形と、別のエラー型へ変換する形は既存の handle の節で書く案とする。節は自分が処理するハンドラの外側で実行するので、節から raise すれば外側へ伝える。Error の原因をラップした直和型にするか、そのまま同じ E を伝えるかをコードで選ぶ。標準の IOError・NetworkError・Json.ParseError を String に変えることは必須にしない。

### 同じ失敗の型と捕捉先の一致

エラー型を型の注釈に加えるだけでは実行が安全になるとは限らない。現在の VM は同じ raise の操作番号なら最も内側の節を呼ぶ。`Fail[A]` を処理するつもりの節に `Fail[B]` の値を渡せないようにする条件が要る。

最初の案では、一つの計算の効果で同じ失敗の系統に付く E を一つに定め、異なるエラーは明示的な直和型にそろえる。同じ E の入れ子は最も内側が捕捉する。異なる E の入れ子は、内側の計算が自分の E をすべて処理してから外へ出る形を許す。内側の境界を通過させたい別の E を、名前が同じという理由で誤って捕まえる形は認めない。

この制限を、エフェクト変数 Rest を具体化した後にも維持できるかは未検証である。Rest に隠れた `Fail[B]` が内側の `Fail[A]` と衝突する例、失敗の型を含むラムダを境界の外へ持ち出す例を先に Lean で調べる。候補は、捕捉の境界で Rest に同じ系統の失敗が含まれない条件を検査する方式と、境界を識別する内部の値を操作へ渡す方式である。後者なら、その値を捕捉した関数を外へ持ち出す場合の型も要る。型引数を消してよいことを証明できる前に、既存の操作番号だけで足りると決めない。

複数の `Fail[A]`・`Fail[B]` を同時に持ち、型で捕捉先を選ぶ方式は別の候補である。これを採るなら、同じ操作番号に対する実行時の識別、効果の除去、型変数が一致したときの重複を設計する必要がある。型を文字列にして比較するだけの実装や、型情報を失う共通のエラーへ包む実装は推さない。

## リソース・タスク・遅延評価の境界

[01-10](../../../design/01-spec/01-10-resources.md) では、非再開ハンドラが続きを捨てるとき、内側の with から逆順に解放する。そこでの解放の失敗は実行時エラーとなる。型付きの失敗でもこの規則を引き継ぐ案を推す。E を捕捉して Result.Error を返す予定でも、解放が失敗すれば通常の Result は返らない。die の終了中の解放の失敗を補足にする規則と同じものとして扱わない。E と後始末の失敗を両方保持する新しい公開型は今回加えず、E の補足報告が必要かは F8 で判断する。既に行った外部操作や状態変更を巻き戻す意味は加えない。

[01-11「タスクとハンドラ」](../../../design/01-spec/01-11-concurrency.md#タスクとハンドラ) は、子タスクが引き継いだ節を末尾で再開する節（tail-resumptive clause）に限る。非再開の失敗ハンドラをそのまま親から引き継ぐと、現在は節を実行せず実行時エラーとなる。親の toResult が子の raise を捕まえ、await で E を受け取れると説明してはならない。推す使い方は子タスク自身の内側で toResult を呼び、Result をタスクの値として返すことである。既存の Task.allOk を使える。親へ未捕捉の失敗を伝える方式とタスクの取消規則の変更は、今回の前提にしない。

現行の lazy 本体は純粋でなければならない（`typeck/effects/mod.rs::lazy_expr`）。未処理の `Fail[E]` を含む本体は拒否し、本体内で toResult まで済ませた `Lazy[Result[T, E]]` は候補とする。失敗する関数を値として保存する場合は、その関数を呼ぶ時点のエフェクトと捕捉範囲で扱う。lazy が純粋であることと、中に保存した関数の呼び出しが純粋であることを混同しない。

## 形式化の現在の範囲と必要な作業

[07-04「01-12 との対応」](../../../design/07-quality/07-04-formal-semantics.md#01-12-との対応) により、今回の型・操作・ハンドラ・脱糖は形式化した範囲の内側である。新しい標準機能という理由で全体を対象外にすることはできない。

| 対象 | 現在のモデル | TODO-249 の影響 |
|---|---|---|
| コアの型と効果 | `formal/Benitoite/Release/Syntax.lean` の Atom は name / rho。OpDecl.eff は型引数のない名前 | E を含む効果とその代入の表現を選ぶ。単に Surface に構文を足すだけで済むとは見込まない |
| 操作・ハンドラ | Release の Typing の V_Op・C_Handle・HasTypeClauses、Semantics の E_Op・SplitAt | E の具体化、T の任意性、捕捉する効果、実行の節の選択が対応する必要がある |
| 表層と脱糖 | Surface の Syntax・Typing・Desugar、Lemmas/ReturnTry・Extensions・Dict、Theorems | raise・変換・境界を表し、性質 1（脱糖の型の保存）を維持する。既存 try の escape の規則を保持する |
| 検査の関数 | Surface の Check・CheckSoundControl・CheckProgramSound、Release の型と効果の補題 | 新しい正の規則だけでなく、不正な捕捉、型の不一致、効果の漏れを拒否する条件と健全性を直す |
| 処理系との比較 | Exchange と Rust の書き出し、check-formal.sh の比較と六入口の集計 | 新しい効果・節の情報を交換し、対象内の入力を対象外へ落として成功としない |
| 解放と終了 | Release の use・drop・exit と保存・進行・エフェクト健全性 | コアの規則を変える場合は性質 2・3 も含めて修正する。型保存だけから解放・報告の実装全体の正しさを主張しない |

並行処理、VM の GC・レジスタ・終了報告、ABI の実装は証明の外であり、それぞれ 07-04 の対象外の記録と実装の検証が要る。Result への変換は実行時エラー、資源不足、外部のトラップ、取消し、Process.Exit を自動で捕まえない。

後の実装では、Lean の定義・型付け・脱糖と性質 1 の証明を処理系より先に直し、必要ならコアの保存・進行・エフェクト健全性も直す。01-12 の写しと 07-04 の対応表を同じ変更で更新し、定義・定理の言明・仮定のレビューを受ける。証明が通らない場合は、仕様の抜け、コアの不足、書き写しの誤りを分け、反例と判断を記録する。制限の追加で保証を弱めたまま通ったことにはしない。

## TODO-189 との関係と規模の見込み

TODO-249 は TODO-189 を必須の前提としない。E を伝えて境界で捕まえるだけなら辞書は要らない。境界で E を表示する関数に `[E: Show]` を付ければ、既存の関数の辞書渡しが使える。さらに `Failure.toResult(body)` の結果に既存の `try … or die` を使えば、表示と終了の契約も既存のものを使える。

一緒に決める必要があるのは、操作の型パラメータと捕捉側に固定するエラー型の区別、節の環境、隠れた引数の順、関数値と部分適用で何を捕えるか、形式化と交換形式の更新の分担である。TODO-189 の Show を任意の E を追跡する代わりにしてはならない。[操作の制約の調査](op-constraints.md) と [問い F1〜F12・O1〜O6](typed-failure-questions.md) に判断の案を置く。

現時点の粗い見込みは TODO-249 が 12〜18 作業、TODO-189 が 6〜9 作業、共通の設計の確定・文書と生成物の整合・統合確認が 3〜5 作業、計 21〜32 作業である。うち Lean の定義・証明・checker・交換形式の接続に 6〜10 作業程度を見込む（内数）。作業はコンパイルと該当する検査が通る単位を指し、レビューの回数や機械の検査時間の予測ではない。一般の型パラメータ付きエフェクト、複数の型による動的な捕捉、親タスクへの伝播まで選ぶ場合はこの範囲で見積もれない。最初の Lean の検討で捕捉と型引数の扱いを確かめてから、実装プランの作業数を確定する。
