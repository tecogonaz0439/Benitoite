## F1 エラー型をどこに保持するか

問い: 0.0.8 では標準の失敗に型引数を持たせる範囲で始めるか、一般のエフェクト宣言にも型パラメータを許すか。

| 選択肢 | 内容 |
|---|---|
| A（推す案） | 標準の `Failure.Fail[E]` を既存の操作・handle に統合する。利用者定義の `effect L[E]` は今回の公開範囲に加えない |
| B | 一般の `effect L[E]` と `uses L[E]` を設け、その一つとして失敗を定義する |
| C | 今の具体的なエラー型ごとの effect と補助コードだけを案内する |

## F3 操作・相互変換・回復の API

問い: 次の三つの契約と、回復には既存の handle を使う形で始めるか。

| 選択肢 | 内容 |
|---|---|
| A（推す案） | 明示的に import する Failure の raise・fromResult・toResult。回復と別のエラーへの変換は handle の節で書く |
| B | A に catch/recover/mapFailure などの補助関数と、捕捉ブロックの新しい構文も加える |
| C | 相互変換は専用構文に限り、普通の関数としては提供しない |

仮の型を次に示す。`E` はエラーの値の型、`Rest` は残りのエフェクトを表す変数である。

```text
raise[T, E](error: E) -> T uses Failure.Fail[E]
fromResult[T, E](result: Result[T, E]) -> T uses Failure.Fail[E]
toResult[T, E, effect Rest](body: function() -> T uses Failure.Fail[E], Rest)
  -> Result[T, E] uses Rest
```

推す案は A である。理由: 生成・変換・捕捉の役割を三つの契約で示し、回復に既存の節を使える。名前は `Failure`・`Fail`・`raise` を第一の候補とする。実装プランを作る前に標準モジュールの配置、import の綴り、名前の衝突を確定する。

fromResult は引数の評価を一回、Ok なら値を返し、Error ならその E を失わず伝える。toResult はラムダをハンドラの内側で一度実行する。入力が計算済みの値では捕捉が間に合わない。成功時と失敗時の両方で他の効果を維持し、入力や失敗後の続きの二重実行を許さない。`Rest` に許す失敗の系統の条件は F4 に含める。上の型だけでその条件を解決済みと扱わない。

比較する例は、外部の File.readText の Result を fromResult で取り出し、List.map の各ラムダは成功値を直接返し、公開関数の境界の toResult がリスト全体の結果を返す形とする。現行の `try … or return` を各ラムダで使った `List[Result[T, E]]` とは結果型と打ち切り先が異なる。途中で File.Read などのエフェクトが消えないことも例で示す。

```text
function loadAll(paths: List[String]) -> Result[List[String], IOError] uses File.Read
  return Failure.toResult(body: lambda()
    return List.map(xs: paths, f: lambda(path)
      return Failure.fromResult(File.readText(path))
    end lambda)
  end lambda)
end function
```

この提案の例は File と Failure の import を省いている。失敗の境界を List.map の外側に置き、一件でも失敗すればリスト全体の Error を返す。全件の失敗を集計したいときは、Result のリストを返す現在の方法を使う。

## F4 エラー型の一致と、ハンドラの捕捉先

問い: 同じ失敗の系統の型を一つに制限して始め、型の異なる値を誤った節へ渡さない条件を先に形式化するか。

| 選択肢 | 内容 |
|---|---|
| A（推す案） | 一つの計算で同じ失敗の系統に付く E は一つとする。型を消せる条件を Lean で確かめ、境界では E を具体化し、結果の T は節で任意とする |
| B | `Fail[A]`・`Fail[B]` を同時に持ち、型を含む識別で捕捉先を選ぶ |
| C | エフェクトには Fail の名前だけを残し、E を操作の呼び出しの型パラメータにだけ持たせる |

推す案は A である。理由: 複数の失敗の組合せを明示的な変換で扱い、既存の「最も内側の該当操作の節」という意味を使える範囲を確定できる。C は境界で E の同一性を保証できない。B はエフェクト集合と捕捉の識別の変更が大きくなる。

A で認める同じ E の入れ子は、最も内側の節が捕まえ、節から同じ失敗を起こすと外側へ伝わる。異なる E の入れ子は、内側がその E を処理し終えた結果を外側で使う形を許す。別の E を内側の同じ操作の節を越えて透過させたい例は、単に効果の集合を引き算して許さない。失敗の系統の識別はエラー型の名前ではなく、操作とエフェクトの宣言の同一性を使う。

節のソースは `case Failure.raise(error) -> …` とする案である。E は handle 本体の失敗の型と境界の型注釈から決め、節の error にその型を与える。操作の結果型 T は節の任意の型として別に束縛する。型が決まらないときは toResult の明示型引数や戻り値の型注釈を案内し、節に任意の E が書けることだけを根拠に本体の違う E を取り除かない。独立した catch ブロックの構文は加えない。

設計の関門は、`Rest` に隠れた `Fail[B]` があるとき内側の `Fail[A]` の節に B が渡る入力を拒否できることである。効果の列に特定の系統がない条件（lacks constraint）を使うか、境界の識別値を操作に渡すかは Lean の先行作業で比べる。現在の型検査にその条件があるとは扱わない。失敗の型を持つラムダを返す場合と部分適用も対象とする。型引数を実行時に消去する方式で証明が通らなければ、反例と代案を記録し、処理系へ進む前に設計者と決める。

## F5 異なるエラー型の組合せと型推論

問い: IOError と NetworkError などは、明示した公開のエラー型へそろえるか。

| 選択肢 | 内容 |
|---|---|
| A（推す案） | 境界の前で Result.mapError、または節から別の E を raise して明示変換する |
| B | 構造を持つ暗黙のエラーの和を推論し、呼び出し先が増えると自動で広げる |
| C | すべて String、または中身の型を消した共通エラーにする |

推す案は A である。理由: 宣言した契約の変更を検査でき、元の原因を保持する直和型も利用者が定義できる。異なる E は自動変換しない。B の型の拡大は関数型の適合、ラムダ、部分適用、型クラスのメソッド、高階関数での推論を増やし、C は型情報を失う。

`uses Failure.Fail[AppError]` を関数型に書けるものとし、呼び出し・ラムダ・エフェクト変数への代入で AppError を保つ案とする。外側の戻り値は T でよく、Result を強制しない。E が決まらない場合は型注釈で指定する診断を出し、String などを暗黙に選ばない。複数の失敗の系統を利用者が個別に宣言して使う現在の形は保つが、同じ標準 Fail の複数の具体化は F4 の制限に従う。

## F6 失敗操作を再開できない条件

問い: raise の結果型 T を任意のままにし、標準の失敗の節には resume を認めないか。

| 選択肢 | 内容 |
|---|---|
| A（推す案） | 結果の T は任意とし、標準の失敗を処理する節の resume を静的に拒否する。続きを捨てる既存の意味を使う |
| B | T の値を作れない型付けだけに依存し、標準の失敗にも一般の resume の文法を許す |
| C | 失敗の節から代替の T を渡して、失敗した位置の続きを再開できるようにする |

推す案は A である。理由: 回復は handle 全体の結果を選ぶ操作だと明示でき、成功値を捏造して再開する意味を加えずに済む。E は境界に固定し、T を E や外側の型と等しくしない。通常の利用者の再開可能な操作の規則はそのままにする。

Never 型や一般の非再開操作の宣言構文を同時に加えることは前提にしない。型の保存だけで「実行時に値を返さない」すべての性質が証明されたと扱わず、raise の節の規則と実際の続きを捨てる動作を対応させる。標準の失敗の節では、resume の引数の式の形によらず再開を拒否する。

## F7 Show と、die・実行時エラーとの区別

問い: 0.0.6 の Q9 を引き継ぎ、表示は終了の境界だけで要求するか。

| 選択肢 | 内容 |
|---|---|
| A（推す案） | raise・fromResult・toResult・回復に Show を求めない。表示する関数や既存の or die だけに求める |
| B | 失敗を起こす段階から E: Show を必須にする |
| C | Show と別のエラー表示専用の型クラスを加える |

推す案は A である。理由: 表示せず処理・保存・再伝播する E を扱え、既決の方針と一致する。`try Failure.toResult(body) or die` なら既存の Show と Process.Exit の契約を使える。これは説明用の形であり、body は計算を包むラムダである。

型付きの失敗の捕捉は die、Process.Exit、実行時エラー、資源不足、外部のトラップ、タスクの取消しを捕まえない。Process.Exit を利用者の専用ハンドラで差し替える既存の意味は保つ。型付きの失敗を main に未処理で残したときは静的に拒否し、暗黙の表示と exit を足さない。ハーネスのエフェクト上限と権限制御の違いも保つ。

## F8 打ち切り時の解放と、二つの失敗の扱い

問い: 非再開の節の既存の解放規則を維持するか。

| B | E と解放の失敗を新たな複合エラー型に包み、回復可能な値として返す |
| C | E を優先し、解放の失敗を捨てるか注記だけにする |

## F9 子タスクと遅延評価での範囲

問い: 同期の捕捉を先に提供し、タスクの中では Result へ変換して返す使い方とするか。

| 選択肢 | 内容 |
|---|---|
| A（推す案） | 現在のハンドラ継承の制限を保つ。子タスク自身の toResult で捕捉し、Task.allOk などへ渡す。lazy の本体の純粋性も保つ |
| B | 親が子の失敗を捕捉し、await で E を受け取る新しい意味まで入れる |
| C | 型付きの失敗を使う計算では、内部で捕捉する形も含めタスクを一律に禁じる |

推す案は A である。理由: 親から引き継いだ非再開の節は現在実行時エラーとなるため、外側の toResult だけで子の raise を扱えるとは説明できない。子の内側で捕捉すれば既存の Result のタスク API を使える。これで親の継承の制限が静的に保証されるとは主張しない。外側の捕捉に依存した子の操作には、現行の引き継いだハンドラの実行時エラーを維持する。

## O2 辞書・値引数・継続の順序

問い: 操作の辞書も既存の関数と同じく隠れた先頭引数にするか。

| 選択肢 | 内容 |
|---|---|
| A（推す案） | 宣言の制約の順に辞書、宣言の順に値引数、節には最後に継続を渡す。表層の個数と名前には辞書を数えない |
| B | 利用者が辞書を普通の値の引数として明示する |
| C | 呼び出しでは辞書を渡さず、節を定義した場所で具体的な実装を選び直す |

推す案は A である。理由: 既存の辞書渡しと試みの成功した方式にそろえられる。C は節の未知の T の実装を選ぶ根拠がなく、試みでも辞書を欠く脱糖が失敗した。組み込みの制約は辞書数に含めない。Lean のコアでは普通の引数列へ写せるが、Rust の IR は辞書を別の分類で保持するので、節の辞書の欄と対応する独立の検査を設計する。

## O3 節の局所辞書と型の範囲
