# 範囲のパターンと、型から導く仕組みについて設計者に尋ねる問い

2026-10-17 の調査に基づく判断の案である。P は TODO-191、G は TODO-063・087 の問いである。いずれも未回答であり、推す案を合意済みの決定とは扱わない。今回は調査だけを行い、ここで選んだものとして実装へ進まない。

判断の基準は [00-01「目的と設計原則」](../../../design/00-overview/00-01-goals.md) である。静的に確かめられる誤りを先に報告し、型や許可する操作の契約の変更を見落とさせず、同じ役割の構文を理由なく増やさない。設計者が示した、処理系による標準ライブラリの個々の関数の特別扱いを小さくする条件も適用する。

根拠と調べたソースは [範囲のパターンの調査](range-patterns.md) と [導出の調査](derive.md) にある。TODO の原文は [項目の写し](../todo-items.md) に置く。S1・S2 が扱う検査方針・型付きの失敗・操作の制約をここで確定し直すものではない。

## P1 全域を網羅と認める型の範囲

問い: 0.0.8 では Character の全域を認め、Integer は現在の判定を残す形でよいか。

| 選択肢 | 内容 |
|---|---|
| A（推す案） | Character の範囲・リテラルの和が全域を覆えば認める。Integer は `_` か変数を必要とする現行規則を保つ |
| B | Integer と Character の両方を認める。有界の整数のモデルと健全性の接続も今回行う |
| C | 両方とも現行維持とする |

推す案は A である。理由: 文字の全域は現在の Lean の Char の全体と一致し、常に残りの値を置く判定を改める作業に絞れる。Integer は表層では 64 bit だが Lean の定数は範囲条件のない Int なので、残りの値を消すだけでは既存の健全性の定理が成り立たない。B を選ぶなら有界の値についての規則と保存・進行への接続を先に設計し、作業を少なくとも 4〜8 件加える見込みとする。A の場合、TODO-191 の両型を実装完了したとは記録しない。

新しい幅の数・Byte の範囲パターン、片端省略、ガードの式の解析まで広げる案は、どの選択肢にも含めない。

## P2 分割・入れ子・束縛に同じ全域の規則を使うか

問い: 採用する型の全域の判定を、範囲を分けた選択肢、リテラルとの組合せ、入れ子の欄、必ず照合する束縛へ共通に適用してよいか。

| 選択肢 | 内容 |
|---|---|
| A（推す案） | 有用性の手順の各列へ適用する。単独のパターンが全域なら束縛も認める |
| B | match の最上位の単一の全域の範囲だけに限る |
| C | match の判定だけ変え、束縛は現在の制限を保つ |

推す案は A である。理由: 同じ照合の意味を、置く位置や範囲の分け方で変えずに済む。現在の行列の再帰を使えば、二つの欄の相関も保てる。Character のサロゲートは型の値に含めず、ガードのある行は全域の判定へ数えない。束縛へ選択肢の新しい構文を加える提案ではない。

## P3 後続の包括的な分岐と互換性

問い: 全域を覆った後の `_`・変数・ほかの選択肢を、既存の選ばれない分岐の誤りとして扱ってよいか。

| 選択肢 | 内容 |
|---|---|
| A（推す案） | E0602・E0608 を適用し、既存コードの調査と移行案内を今回に含める |
| B | 網羅性だけを変え、全域の範囲の後の分岐には例外として誤りを出さない |
| C | 選ばれない分岐全般を警告へ変える |

推す案は A である。理由: 現在も選ばれない選択肢は誤りであり、全域の範囲だけを例外にすると同じ判定結果を二種類の意味で扱うことになる。受理の追加に加えて、今通る末尾の `_` が誤りになる変更があると明記する。移行の差分から人が本体の意図を確認できるようにし、不要に見える分岐を無条件に削除しない。

## P4 不足の診断に何を示すか

問い: 全域を認める型では、存在する未被覆の値か区間を反例として示す形でよいか。

| 選択肢 | 内容 |
|---|---|
| A（推す案） | E0601・E0607 を保ち、文字の実在する不足を示す。Rust と Lean の反例の表示も揃える |
| B | 不足があれば常に `_` だけを示す |

推す案は A である。理由: 一文字の漏れと全体を覆った場合の違いが診断から分かり、LLM が不足する分岐を修正できる。サロゲートを反例に出すことを防ぎ、反例が元のパターンに照合しないことも確かめる。Integer を据え置く場合は、その保守的な不足の `_` を実在する整数の反例だとは説明しない。

## P5 形式化の作業と完了条件

問い: 現在の Lean の判定を直接改め、健全性と既存の型保存を通してから処理系を変更する順でよいか。

| 選択肢 | 内容 |
|---|---|
| A（推す案） | Lean の列挙・補題 U・系を先に更新し、表層の検査と性質 1、写し・対応表、Rust と本番ソースからの差分の接続を揃える |
| B | Rust を先に変え、形式化は改造末に合わせる |
| C | 変更を形式化の外へ分類する |

推す案は A である。理由: 網羅性の判定は 07-04 の形式化した範囲の内側であり、B・C は現在の規約に合わない。独立した全域の入力だけでなく、本番の型検査の出力からも比較する。TODO-255 による検査の実行時期の見直しは、この順序と保証を省く理由にしない。

## G1 型から実装を作る方式

問い: JSON 変換と生成器は外部の道具から通常のソースを生成する方式で始めてよいか。

| 選択肢 | 内容 |
|---|---|
| A（推す案） | 通常の関数を生成する道具と補助ライブラリを作る。言語構文は加えない |
| B | `@derive` のような指定を設け、処理系が決まった型クラスの実装を作る |
| C | 汎用の型の構造と相互変換を処理系が用意し、Json と生成器をライブラリで書く |

推す案は A である。理由: 処理系が Json や生成器の関数と変換の方針を知らずに済む。B は標準ライブラリの見直しのたびに処理系を変える結び付きが生じる。C は共通化と学習の題材になるが、現在の型クラスにはない、型ごとに違う表現の型と辞書を関連付ける規則の設計が先に要る。A でも生成し直しと照合の費用は残るため、G3 を必須とする。

## G2 生成道具の入口と型ごとの API

問い: 初版はリポジトリの道具として配り、型ごとの通常の関数を生成する形でよいか。

| 選択肢 | 内容 |
|---|---|
| A（推す案） | `tools/derive/` に読み取りと編集・照合を置く。関数を基本とし、Json.Encode・Decode・Arbitrary の型クラスは必須にしない |
| B | 同じ生成部を初版から benitoite のサブコマンドに組み込む |
| C | 言語サーバの生成の操作を先に提供する |

推す案は A である。理由: 生成の規則を確かめながら利用でき、CLI の機能一覧や言語サーバの実装を前提にせずに済む。B は利用者が導入しやすいが、公開の help・capabilities・Skill を合わせて設計する費用がある。C だけでは LLM の非対話の操作と継続的な照合の入口が不足する。A の導入手順と生成の設定の渡し方を文書に含める。

型クラスを選ぶ場合も型か型クラスの宣言元へ implement を生成し、別の Generated モジュールへ孤立した実装を出さない。手書きの実装と重複した場合に自動で上書きする規則は加えない。

## G3 生成し直し忘れと手書きの編集

問い: 生成道具に preview・ハッシュ付きの apply・再生成して比べる check を設け、生成の check を利用者の検査手順に入れてよいか。

| 選択肢 | 内容 |
|---|---|
| A（推す案） | 型・設定・道具の版・出力を管理し、食い違いで非零にする。通常の言語の check に Json 専用の処理は加えない |
| B | 通常の benitoite check に生成の記録の検査を組み込む |
| C | ソースに印だけを付け、型の誤りにならない古い生成物は利用者の確認に委ねる |

推す案は A である。理由: encode は型変更後も古い欄だけを出力して通る場合があり、普通の型検査だけでは足りない。完全なレコードパターンの不足を拒否する実装も、ソース上で確認できなかった。生成領域を人が編集したら上書きせず、個別の変換の指定か管理を外す操作を求める。A では専用の check を実行しない利用者の追従は保証できない、という限界も明記する。

G3 の実装に、レコードパターンの不足の拒否そのものの修正は含めない。その修正も同時に行う場合は、再現の確認と影響の判断を追加の作業として決める。

## G4 自動で扱う型の最初の範囲

問い: 初版の対象は型パラメータのない、再帰しないレコードと基本的なコンテナに限ってよいか。

| 選択肢 | 内容 |
|---|---|
| A（推す案） | 非循環の入れ子のレコード・基本型・List・String 鍵の Map・区別を失わない Option を扱い、特殊な欄は関数を指定する |
| B | 型パラメータと再帰の data まで初版の自動生成に含める |
| C | 一段のレコードだけとし、入れ子もすべて手書きで指定する |

推す案は A である。理由: レコード間の非循環の依存を追えば実用的な入れ子を扱え、再帰の生成で値を作れない型や、無限の大きさになる条件を先に一般化せずに済む。B には生成の予算・基底の構成子・型パラメータの変換と生成の関数の扱いが増える。未対応の型を仮の本体や内部エラーで埋めず、生成前に対象と欄の位置を示して拒否する。

## G5 JSON の欠落・null・余分なキー・名前

問い: 以下の既定を採り、欄の名前の対応と個別の変換は言語外の設定に書く形でよいか。

| 選択肢 | 内容 |
|---|---|
| A（推す案） | 必須欄の欠落・null と余分なキーは拒否。Option は欠落・null を None、None を null とする。キーは欄名のまま、改名は明示する |
| B | 余分なキーを許し、None の欄は出力から省く。ほかは A と同じ |
| C | 型だけから既定を選ばず、全欄について設定を要求する |

推す案は A である。理由: 必須の欄の誤りと意図しないキーを検出し、生成される変換の方針を一定にできる。Option の欠落と null は区別を失うので、その違いが要る入力は手書きの変換を指定する。入れ子の Option や null 自体を成功値にする変換は、None と Some の区別が消える場合には自動生成を拒否する。JSON の重複キーを Value からの変換で検出する保証は加えない。

## G6 JSON の数と失敗の契約

問い: 変換は純粋な Result とし、数の暗黙変換と非有限の Float を自動で受け入れない形でよいか。

| 選択肢 | 内容 |
|---|---|
| A（推す案） | encode・decode は変換の失敗を返し、欄・添字の位置と期待値を残す。Float は有限値に限り、Integer からの復号は明示指定とする |
| B | encode は常に Json.Value を返し、非有限の Float は stringify と同様 null にする |
| C | TODO-249 の失敗エフェクトを変換の必須の戻り方とする |

推す案は A である。理由: null に変わる情報の損失と、数の丸めを明示できる。ParseError は文字列の文法の失敗なので、レコードへの変換の失敗と分ける。Result は現在の関数だけで扱え、必要な利用者は将来 TODO-249 の変換を使える。往復の約束は対応した型と変換の条件を満たす値に限り、任意の JSON の字面の再現は約束しない。

## G7 生成器と縮小の表し方

問い: 明示的な Random.Generator と size を渡す純粋な生成器と、候補の列を返す縮小を普通の値として提供してよいか。

| 選択肢 | 内容 |
|---|---|
| A（推す案） | Gen[T] と Shrinker[T] を通常のレコード・関数で表し、手書きも導出も同じ組合せを使う |
| B | Arbitrary[T] の型クラスを最初から必須にし、各型の一つの既定を使う |
| C | Random.Generate の操作に統一し、ハンドラで種を固定する |

推す案は A である。理由: 同じ Integer でも正の数・境界を重視する数など複数の生成を引数で選べる。外部の状態を使わず再現を管理でき、制約付きの操作も要らない。B は通常の型クラスで追加できるが、単一の実装を利用上の条件に合わせた生成の代わりにしない。欄をまたぐ条件と再帰の停止は型の構造だけから保証しない。

## G8 プロパティの失敗と実行器の拡張

問い: 初版は純粋な Result[Unit, String] を返す性質をライブラリで繰り返し検査し、既存の @test の一件として報告する形でよいか。

| 選択肢 | 内容 |
|---|---|
| A（推す案） | 試行・縮小・失敗の値はライブラリで扱い、最後に @test の Result.Error または Assert.fail へ接続する |
| B | 専用の属性・引数付きテスト・seed の CLI・構造化した反例の報告を実行器へ加える |
| C | 任意の Assert を含むエフェクト付きの性質を初版から捕捉して縮小する |

推す案は A である。理由: 現在の @test の型・非実行の報告・エフェクト上限の契約を保ったまま利用できる。B には構造化した情報をハーネスが使う利点があるが、形式の版と実行前の照合まで設計が増える。C は操作の差し替え・解放と、IO や状態を繰り返すときの環境を追加で決める必要がある。生成器の導出だけを終えたことと、プロパティの実行を提供したことは別に記録する。

## G9 再現と縮小の上限

問い: seed と試行設定・道具とライブラリの版を報告し、失敗した具体的な入力も残す形でよいか。

| 選択肢 | 内容 |
|---|---|
| A（推す案） | 試行数・size・候補を試す総数に上限を置く。元と縮小後の入力を残し、版を固定した再現を約束する |
| B | seed だけを残し、将来の版でも同じ反例になると約束する |
| C | 各実行で OS の種を使い、失敗時の文字列だけを残す |

推す案は A である。理由: 生成の順序や縮小の規則を変えれば同じ乱数列でも入力は変わる。Random.fromSeed の契約だけでは生成器全体の再現を保証できない。縮小は探索の上限で止め、得た入力を最小と呼ばない。具体的な反例を固定例として残す方法も案内する。性質の関数そのものの停止性は静的な型とエフェクトの保証には含まれない。

## G10 形式化の範囲と、ほかの項目との依存

問い: C の生成は外側として記録し、出力は既存の型付き表層へ渡し、TODO-189・249 を導出の必須条件にしない形でよいか。

| 選択肢 | 内容 |
|---|---|
| A（推す案） | C の設定・生成・照合は対象外と記録。通常の関数・レコード・必要なら implement を検査する。規則を増やさない限り Lean の新しい構文は加えない |
| B | 導出を目的に制約付きの操作を新設し、TODO-189 に接続する |
| C | 導出を目的に汎用の型の構造を加え、その形式化も先に行う |

推す案は A である。理由: 普通の関数に渡す辞書や表示の関数だけで目的を満たせ、操作へ辞書を渡す必要はない。TODO-249 の捕捉も Result で済む範囲の前提ではない。B や C を選ぶ場合は、型付き表層・型の規則・辞書渡し・脱糖（desugaring）へ加える部分を内側として Lean から先に変更する。「属性を足すだけ」「ライブラリだから外」という一括した分類はしない。

## 回答後に具体化する範囲と大きさ

P1 の A と G1 の A を選ぶ場合、範囲のパターンは 5〜8 作業、JSON とプロパティのライブラリ・生成道具の共通部は合わせて 15〜24 作業、S3 の範囲で計 20〜32 作業を見込む。Integer の全域は別に少なくとも 4〜8、実行器の専用対応は 4〜7、型パラメータと再帰の data の生成は 4〜8 作業以上を加える粗い見込みである。証明と生成の試作前なので日数と上限の約束ではない。S1・S2 の作業数へ単純に足した全改造の見積もりとはしない。

回答後は D の README.md・decisions.md・plan.md に採用範囲・理由・手順を整理し、後の実装結果を results.md に分ける形が考えられる。これは前回の記録の構成を参考にした案であり、今回それらの実装プランや完了記録を作ったことにはしない。TODO-255 から始める順序と、一度の公開にまとめる方針を保つ。範囲を絞った場合の未対応部分をどう残すかも設計者が決め、今回は docs/todo に書き込まない。
