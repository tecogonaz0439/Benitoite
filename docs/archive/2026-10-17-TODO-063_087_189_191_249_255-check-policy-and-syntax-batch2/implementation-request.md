## 依頼する内容

最初に AGENTS.md を読み、指定した作業を計画の目的・対象ファイル・完了条件に従って実装する。C13の30〜60分は目安であり、計画は残り24作業、段1込み28（Z1込み29）を見込む。未実測の時間と根拠、超過を設計者が確認してから着手する。L0は60分で必ず区切り、両案の未達も報告する。試作は/private/tmpの独立ファイルに限り取り込まない。以後の正式なLeanは各作業末に全体がsorryなしでビルドできることを保つ。処理系と設計書・生成物を同じ状態へそろえ、未接続の仮置きを完了にしない。

作業途中は、関係するテストだけを Cargo 等で直接実行する。L0の試作に使うLeanと文書検査はwork L0の行に従う。V1はworkを重ねずchangeだけを行う。それ以外の作業末は、計画の work 行にある `scripts/check.sh --level work --base <基準> [--test <関連ターゲット> ...]` を一度実行する。計画に名指しの `--only` があればそれを使う。Rust の作業末の既定の lib 全件・関連統合テスト・clippy・fmt はこの入口に任せ、直接のコマンドを重ねない。work が未実装の移行中だけは計画の直接のコマンドを使う。文書だけ・シェルや Python だけ・Lean だけの作業に Rust の全 lib を追加しない。

検査前に種類を知らせ、計画で固定した基準と指定へ `--dry-run` を付け、選択と理由を確認する。長い検査・heap・全件の特殊構成を含む場合は見込み時間も知らせる。変更範囲が増えたら、入力を読む側と必要な構成を含めて計画の検査を更新する。共有の入力を変えたときは、その入力を読む全統合ターゲットを指定する。O1/F1/F2の一覧は各作業の開始時にtests直下の*.rsから作り直す。`--test` は統合テスト名ごとに繰り返し、Rust の自動 work で省略すれば全統合ターゲットとなる。

ヒープの不変条件や安全点を越える値を変える作業では、局所の heap-verify・gc-stress と必要な `check-heap.sh` を、次の作業の前提にする前に通す。GC本体を変えなければO1/F2のheap_checks・lint_heap・doc_defaultを一律に加えず、計画の条件付き指定に従う。形式化の内側では 07-04 の Lean 先行を守り、既定の `lake build` が `sorry` なしで通ることと、定義・言明・仮定のレビューを処理系へ進む条件にする。定義と言明はL0後とL2aのビルド外の文書で先にレビューし、未証明の定理を正式なLeanへ取り込まない。Rust と Lean の全比較は、L4b末の旧10/3出力の回帰、P1末の三項目の接続、V1の最終関係状態に割り当てる。

作業中の新たな60分超の見通し、確認した見積もりの2倍、仮定の追加、層の区切りでのビルド不能では止め、状態と未完の条件を記録してR12へ戻す。作業の完了のために段・改造・リリースの全件検査を先取りしない。失敗の修正や関係する追加変更の後は、古くなった検査だけを再実行し、初回の失敗と修正も残す。テストの期待値・大きさ・ignore・時間制限を緩めない。テストを加える・変えるときは test-audit の作成時の関門を通す。

普通の作業の results.md は、基準のコミット、走らせたコマンド、終了状態、外側の時間、計画からのずれと申し送りだけを記す。失敗した場合は原因と修正も残す。結果を引用するときに限り、07-03「結果の保存と引用」の全欄を記す。基準と HEAD の完全な ID、差分の有無と一覧、コマンド・構成・入力・ツールチェーン・件数・終了状態・時間・環境の制限、元の記録、以後の変更、関係状態が一致する理由、判断者と日付を残し、別の状態への引用には未コミット差分と未追跡入力の SHA-256 も保存する。未実施は担当と時期を明記し、この作業が受け持つ失敗を後へ送って完了にしない。

自動分類が終了3で停止したら、分類不能のファイルまたは存在しない基準を示し、規約に従って設計者へ当該水準の `--level … --only`（停止までに選んだ単位を案内し、分類不能のファイルに必要な単位を補う）、互換の `--full`・水準なしの `--only`、`--none` のどれで続けるかを尋ねる。計画に既に名指しがあればその指定で進める。`--level` と `--only` の併用は分類せず、名指しだけを実行する。指定の誤りは終了2として計画を直す。検査失敗と道具不在は1、選んだ検査の成功は0であり、水準全体の完了とは区別する。release は候補と証拠の手動照合も要る。

結果を指定の results.md へ記録し、最後に変更したファイルの要約、検査と結果、計画からのずれ、後の作業への申し送りを日本語で短く報告する。コミット・取り込み・docs/todo の更新・公開の操作は「作業の指定」の明示の指示に従う。
