**先に直すべき点あり。**

表現の選択（R6 の案B）と正規形（R13）は妥当であり、選び直す必要はない。型の上の全順序は、関数の部分も含めて数学的に定義でき、全順序になる（問い1）。正規化と代入の交換、正規化した一般の合成も、S の補題の形で成り立つ見込みがある（問い2）。K_Handle_Fail と伝播の補題による捕捉の安全の筋も正しい（問い3）。

ただし、次の二つを S と decisions.md で先に決めておく必要がある。どちらも設計の選び直しではなく、決定の記録である。

1. 正規形の証拠を、既存の整形式のどこに持たせるか（重大1）。S は「既存の整形式から正規形の証拠を導く」と書くが、今の整形式は正規形を含まない。その一方で、S は前提の追加を R12 の停止条件にしている。このままでは L1b の途中で必ず停止条件に当たる。

  - (B) 型付けの規則が注釈を読む位置で `.norm` を掛ける。そのうえで、型付けが出す型が正規形であることを、正則性の補題として証明する。定理の前提は変えずに済む。ただし、`K_Empty` の型 a や `K_Sub` の a' のように、規則が任意の型を受ける位置がある。(B) を選ぶなら、それらの位置にも正規化か Canonical の前提を置く。規則を変える箇所が (A) より多い。

## 中

### 中1 `EqSoundGoal` の Canonical の前提は、位置ごとの比較なら要らない

- 箇所: S「L1c」の `EqSoundGoal`（153〜159行目）と、161行目「効果比較はname/rhoをS上で、正規形のFail列を順に再帰比較する」。
- 問題: Fail 列を位置ごとに比べる比較なら、成功は生の列の `=` を意味する。したがって、`effEq_sound`・`tyEq_sound` は、今と同じく支持の前提だけで生の `=` を返せる。Canonical を前提に置くと、11 件のすべての呼び出し元で正規形の証拠を作る義務が増える（S 171行目「すべての呼び出し元で新しい証拠を構築する」）。正規形が要るのは、Rust が受理するものを Lean も受理するためであり、健全性のためではない。そちらは読者の正規化で満たせる。表層で書ける効果は Fail を高々一つしか持たない。Fail が 0 個か 1 個の列だけからなる型は、子が正規形なら自動で正規形になる（`sortUnique [x] = [x]`）。
- 修正案: `effEq_sound`・`tyEq_sound` から Canonical の前提を外し、支持の前提だけで生の `=` を返す言明にする。検査器は注釈を正規化せずに位置ごとに比べ、計算した型は `normWith` で正規化する。補題 `canonical_of_failsLeOne`（効果の Fail がどの深さでも高々一つなら正規形）を L1b に加え、交換の読者が出す注釈の正規形の根拠にする。逆に、検査器が注釈を正規化してから比べる設計にするなら、`checkProgram_sound` の結論は、正規化したプログラムについての言明になる。その場合は、脱糖と性質1を正規化したプログラムへ適用することを S に書く。どちらかに決める。

### 中2 Fail の中まで再帰させる定義の一覧と、正規化がそれらを保つ補題が足りない

- 箇所: S「L1b」の補題群の表、「shift・代入・一般の合成」の節。
- 問題: S は `Ty.Support` を Fail の中へ再帰させると書くが、次の定義には触れていない。`Ty.WF`・`Ty.WFList`（`Typing.lean` 127行目。今は効果を見ない）、`Ty.VarsIn`・`Ty.VarsInList`・`Eff.RhosIn`（`WellFormed.lean`。Fail の型の中の関数型にある ρ も対象になる）、項の注釈の `NamesWF`、`ClosedNoEffVars`。どれも Fail の型の中へ再帰させないと、閉じた状態の Fail の型に型の変数や ρ が残りうる。
- 修正案: S の L1b に、Fail の中まで再帰させる定義の一覧を置く。正規化がこれらの述語を保つ補題（`norm_WF`・`norm_VarsIn`・`norm_RhosIn`・`norm_support`）も加える。あわせて、次の補題を加えると L1b の証明が軽くなる。型の変数のずらし `i ↦ if i < c then i else i + k` は狭義の単調な単射である。したがって、生のずらしは `tyCompare` を保ち、正規形を保つ（`shift_compare`・`shift_canonical`）。S は「型のshiftは順序を保つことを前提にしない」と書くが、これは前提ではなく証明できる性質である。これを使えば、`norm_shift` は「生のずらしをした結果がすでに正規形」の系になる。

### 中3 全順序の証明の組み立てを決めておく

- 箇所: S「型の上の固定した全順序」（47〜55行目）。
- 問題: Ty の 15 の構成子について、推移律と反対称律を構成子の組ごとに示すと、場合の数が 15×15 になる。相互再帰と入れ子の列も重なり、L1b の工数を押し上げる。
- 修正案: 次の二つの進め方を S に書いておく（強制はしない）。
  1. 型を、ラベル付きの多分木（rose tree）へ単射で写す。ラベルは、構成子の順位・`Nat`・`String`・`List String`・`Atom → Bool` の和の型とし、線形順序を持たせる。多分木の辞書式順序の法則を一度だけ証明し、Ty の順序は単射で引き戻す。`tyCompare_eq_iff` は単射性から出る。
  2. Ty に依らない部分を、表現の切り替えの前に、独立したモジュールとしてビルドする。部分とは、任意の線形順序の上の `sortUnique` の補題（`mem_sortUnique`、`sortUnique_eq_iff_mem`、冪等性）と、`Atom → Bool` の最初の相違点による順序（`atomsCompare` の全順序と、関数の外延性による等号）である。こうすれば、L1b の中に `sorry` なしでビルドできる途中の区切りができ、60 分ごとの報告にも区切りが出る。

  問い1への見解も記しておく。最初の相違点による順序は、無限の二値列の辞書式順序を、Atom の符号の単射で引き戻したものである。最小の相違点は `Nat` の整礎性から存在するので、線形順序になる。整列の対象は有限の列だけなので、整列順序（well-order）である必要はない。文字列の辞書式順序は整列順序でないので、Atom の添字の順に自然数の符号を使う S の判断は正しい。

### 中6 Release で、通常の handle が raise の節を持つ場合と、K_Handle_Fail の h の形

- 箇所: S「L2a」の表（「通常のhandle … Fail節との混在は表層とcheckerで拒否する」）と K_Handle_Fail。
- 問題: 混在の拒否は、表層と検査器にしか書かれていない。Release の通常の `K_Handle`・`HasTypeClauses` は、raise の節を拒まない。SplitAt は型を見ずに raise を処理する最も内側の枠を選ぶので、選ばれる枠が通常の handle でありうる。その場合、`failure_clause_selected_typed` の「選ばれた枠の境界 E」が定まらない。通常の節は E を固定しない型パラメータとして受けるので、型の安全は保たれる見込みがある。しかし、定理の場合分けが言明に現れていない。K_Handle_Fail の `HasFailureClause E R h t ec` も、h が「Fail の節一つだけ」であることを述べていない。
- 修正案: L2a で、Release の型付けにも混在の禁止を置く。案は二つある。一つは、通常の `HasTypeClauses` が Fail の操作の節を拒み、`HasFailureClause` が h をちょうど一つの Fail の節に限る案である。もう一つは、通常の節が選ばれる場合を定理の場合分けに含める案である。前者が表層・IR の独立検査（E0518）と揃うので、前者を推す。`handled h に Fail はない` は、新しい表現では `handled` が Fail 列を空にするので恒真になる。前提から外すか、定義からの補題にする。

### 中7 Fail の節を選んだときの継続のストア型と、節の型の代入

- 箇所: S「L2a」の `HasFailureClause`（「継続用0番は予約して利用不能とする」）、「L2b」の表。`Release/Semantics.lean` の `E_Op`（260行目付近）と `K_Drop`、`CellOk`。
- 問題:
  1. E-Op は、選んだ枠までの継続 `k1 ++ [.handleF h]` を κ に保存し、`.drop κ :: k2` を積む。K_Drop は `Ψ κ = some (.cont b' t' ε' R')` を要し、ストアの型付けは保存した継続の `ContTy` を要する。Fail の節では、0 番が利用できないことは書かれているが、`Ψ κ` の型と、Fail の枠で終わる保存した継続の型付けは書かれていない。
  2. E-Op は節の本体に `c.body.substTy ts []` を施す。raise では ts=[T, E′] である。Fail の節が型を一つだけ（T だけ）束縛するなら、二つの型を代入すると、束縛の外の番号が二つずれる。閉じた状態では外側の型の変数がないので結果は変わらないが、それを示す補題が要る。そうでなければ、規則を分けて T だけを代入する。
- 修正案: L2a で、Fail の節の型の束縛数（T の一つ）、E-Op での代入（ts の先頭だけを代入する規則を置くか、閉じた状態で余分な代入が無害であることを補題にするか）、`Ψ κ` の型、保存した継続の `ContTy`（最後の枠を K_Handle_Fail、その下を K_Empty で型付けする形）をコード片で決める。0 番を利用不能にする方法は、既存のガードの `hideConts` と同じく、環境の `none` で表すのが手早い。
