## 総評

既存の classify を保ったまま、種類の和集合を検査の単位へ写す薄い対応になっている。旧 `--only`・`--full` の実行部と固定記録の照合、終了状態の 2・3・1・0 の区別、`set -u` の下の空配列の扱い、引数の配列での組み立て、`run_check` による失敗の伝播は、読んだ範囲と自己検査の両方で正しい。`check_skill_generated` の `|| return 1`（実装時の判断 R4）も妥当である。ヒープの規則（heap/ の変更で work・change とも `heap_checks` を選ぶ）と、形式化の選択（formal/ と `check-formal.sh` を `formal_build` へ、`formal/reviews/` は対象外）も設計どおりである。

問題は、主に次の運用時の詰まりと検出の遅れにある。第一に、停止したときの案内が旧指定だけを示す。第二に、長いテストの一覧の更新が規約に書かれておらず、ずれが改造の最後まで見つからない。第三に、ヒープの作業で compile_fail のテストが走らない。第四に、長い対象の実行器は目的に対して大きい。

## 中

### 中1 停止の案内が旧指定だけを示し、0.0.8 の最後の change で確実に止まる

- 箇所: `scripts/check.sh` 620〜627 行（`== stop:` の案内）、同 14〜15 行の先頭コメント、AGENTS.md「テストの運用」の停止の項、07-03「入口・基準・終了状態」の停止の段落（331 行）、`docs/workflow/implementation-request.md` 32 行。
- 問題: work・change の自動選択が止まると、案内は `--full`（「all checks and long tests」）と旧13名の `--only` だけを示す。新しい水準では `--full` は「旧集合」で、change の集合とは違う（`test_default_all`・`doc_default`・`heap_checks` を含まない）。そのため「all checks」という説明は誤りになる。旧名の `--only rust` を選ぶと heap-verify の workspace 全件と gc-stress を走らせることになり、削減の目的にも反する。さらに段1で `scripts/check-heap.sh` を変えたので、0.0.8 の最後の `--level change --base 1294ba97` は必ず止まる（dry-run で確認した）。そのとき取りまとめ担当は、change の単位を分類ごとに手で `--only` へ並べ直す必要があり、licenses や python などの条件付きの単位を落としやすい。
- 修正案: 水準を指定した停止では、停止までに選んだ単位をカンマで連ねた `scripts/check.sh --level <水準> --base <基準> --only <選んだ単位>` を案内に出す。そのうえで、その水準で使える名前を示し、分類できなかったファイルに要る単位を設計者が足す形にする。`--full` の説明は「legacy set (not the change/release set)」へ直す。規約・依頼文の「互換の `--full`・名指しの `--only`・`--none`」も、水準があるときは「当該水準の `--level … --only`」を第一の選択肢として書く。数行の表示の変更で済み、仕組みは増えない。

### 中2 長いテストの一覧の更新が規約になく、ずれは change の最後の実行で初めて見つかる

- 箇所: AGENTS.md 162 行（長いテストの規約）、07-03 401〜403 行、`scripts/check/run_ignored.py` 108〜110 行、`scripts/check.sh` 46 行（`unit_names` で `long_only` が後ろにある）。
- 問題: AGENTS.md と 07-03 は、長いテストに `#[ignore = "long: ..."]` を付けることだけを求め、`scripts/check/ignored-tests.json` へ行を足すことを求めていない。規約どおりに長いテストを足すと一覧は必ずずれる。ずれを検出するのは `long_only` の列挙だけである。`long_only` は change だけが選び、実行順も test_default_all・test_heap_all・test_stress などの後になる。したがって、改造の最後の重い検査の終わり近くで初めて失敗する。失敗の文言（`lib: unknown ignored tests [...]`）は、直す場所（一覧のファイル）も示さない。work の `policy_selftest` も本物の一覧を検査しない（軽6）。
- 修正案: 次の三つを行う。(a) AGENTS.md 162 行と 07-03 401 行に「同じ変更で `scripts/check/ignored-tests.json` に行を足す」と書く。(b) 失敗の文言に、一覧のパスと足すべき行の形（target・name・kind）を出す。(c) change では、`long_only` の照合だけ（`--list-only` 相当）を重い検査の前に置くか、選び方の表示に一覧の更新の注意を出す。中4 の簡素化を採るなら、この所見の大半は不要になる。

### 中3 ヒープを変える work で、compile_fail の文書テスト（回収しない区間の型の保証）が走らない

- 箇所: `scripts/check.sh` 425 行（work の heap → `lint_heap heap_checks`）、07-03 490 行（「回収しない区間の外へ値を持ち出せない……コンパイルの失敗のテスト」）、`scripts/check-heap.sh` 21 行のコメント。

### 中4 長い対象の一覧と実行器が目的に対して大きく、直列の実行で遅くなる

- 箇所: `scripts/check/ignored-tests.json`（33 行の写し）、`scripts/check/run_ignored.py` 全体（162 行）、07-03 403〜407 行。
- 問題: 目的は「long_only で formal の書き出しを走らせない」ことと「対象 0 件を成功にしない」ことである。今の実装は、ソースの属性を JSON へ写した一覧、`cargo metadata`、構成ごとに lib と 36 の統合ターゲットすべてを `--list --ignored` で列挙する処理（heap・stress で約 75 回の cargo 呼び出し）、テストごとに一回ずつの直列の実行を持つ。写した一覧はずれる（中2）。直列の実行は、従来の一回の `--include-ignored` が libtest の並列で走らせていた長いテスト約 26 件を一件ずつにするので、壁時計の時間が増えうる。これは「実行の費用を下げる」目的と逆向きである（W1 は列挙だけを確かめ、本体の時間は未計測）。
- 修正案: 次のどちらかにする。
  - (A) 一覧を廃止する。formal の書き出しは `coverage_export` と `desugar_export` の二つの専用ターゲットだけにある。そこで long_only は `cargo test --workspace <構成> --lib --tests -- --ignored --skip export_coverage --skip export_desugar_corpus` の一回とし、要約の行で通過数が 0 でないことだけを確かめる。release_stack は従来の名前の頭による絞り込み（`pipeline::tests::stages_fit_the_measured_stack_`）に戻し、通過数が 10 であることを確かめる。
  - (B) 一覧を残す場合は、ターゲットごとに一回の呼び出しへまとめ、`--exact` に複数の名前を渡して、通過数と一覧の件数の一致を確かめる。libtest が複数のフィルタを受け付けることは、実施前に手元の版で確かめる。

  どちらも、設計の決定（07-03 403 行、design.md「長い対象の一覧と実行」）の変更として設計者に諮る。
