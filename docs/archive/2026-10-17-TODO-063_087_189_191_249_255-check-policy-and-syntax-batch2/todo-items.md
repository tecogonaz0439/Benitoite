### TODO-249 任意のエラー型を扱う失敗エフェクトと Result との相互変換

- 状態: 方針あり
- 出どころ: 2026-10-14 の設計者との相談と、追加検討の依頼

目的は、複数の関数や高階関数を組み合わせる処理で、成功値を直接扱いながら、回復可能な失敗を指定した境界で処理できるようにすることである。独立した typed throws の機構を導入するより、既存の利用者定義エフェクトと `handle` を基礎に拡張する方向とする。検討する追加は、任意のエラー型を静的に追跡できる失敗の仕組みと、`Result` との相互変換である。具体的な型・関数の名前、表層構文、型付け、実装方式は未決である。

現在の仕様との関係:

- `Result` は、失敗を値として返す・保存する・集計する用途のために残す。現在の `try` は、最も内側の関数かラムダから `Result.Error` または `Option.None` を返す構文であり、複数の関数をまたぐ捕捉ではない。この意味を変更するかは別途判断し、既存の意味と新しい変換を混同させない。
- 現在でも、具体的なエラー型を受け取る `failT -> T` のような操作を宣言し、`handle` の節で `resume` を呼ばずに終えることで、複数の関数をまたぐ処理の打ち切りを書ける。01-06「エフェクトの宣言とハンドラの型付け」の `Abort` が基礎となる。
- 現在のエフェクト宣言自体は型パラメータを持たない。操作の戻り値に型パラメータ `T` を持たせることと、失敗エフェクトのエラー型 `E` を呼び出しから捕捉まで一貫して追跡することは別であり、後者のための拡張を検討する。

任意のエラー型を扱う仕組みの検討:

- `IOError`・`NetworkError`・利用者定義の直和型など、値の型 `E` を保持したまま失敗を伝播できるようにする。共通の文字列や型情報を失う汎用エラーへの変換を必須にしない。扱える型への制約が必要かも決める。
- 型パラメータを持つ一般のエフェクトを導入する案と、失敗専用の型付きエフェクトを既存のハンドラに統合する案を比較する。一般のエフェクトの拡張全体を、この機能の前提として決め打ちしない。
- 失敗操作は成功値を返さず、捕捉側で通常の処理を再開しないものとして設計する。既存の汎用の操作と `resume` で表現する場合も、成功値を捏造して再開できない型付けと、続きを捨てる意味を確認する。
- 中間の関数では、失敗の可能性をエフェクトとして型に残す。境界のハンドラで処理した失敗だけを外側のエフェクトから除く。失敗を処理しても、ファイル操作など他のエフェクトまで除いたことにはしない。エフェクトの静的追跡と実行時の権限も区別する。
- 関数型の適合、型推論、ラムダ、部分適用、型クラスのメソッド、エフェクト多相の高階関数で、エラー型を維持する規則を定める。特に `List.map` のラムダから失敗したとき、ラムダの結果だけを `Result` にする場合との違いを明示する。
- 異なるエラー型を起こす処理をまとめる場合の規則を決める。境界で明示的に一つの直和型へ変換する案を基準に、複数の失敗エフェクトを併存させる案と比較する。暗黙のエラー変換や型の拡大は未決とし、型情報を失う仕組みを既定にしない。
- 同じエラー型を使う複数の失敗操作や、入れ子のハンドラを区別する方法を定める。どのハンドラが捕捉するか、捕捉した節から別の失敗を伝えるときの作用先、網羅性と未処理の失敗の診断を確認する。

`Result` との相互変換の検討:

- `Result[T, E]` から、`Result.Ok(value)` なら `T` の値を取り出し、`Result.Error(error)` なら `E` の失敗を起こす操作を設ける。現在の `try` による関数からの早期リターンとは、作用先と型の規則を区別する。
- `T` を返して `E` の失敗を起こしうる計算を囲み、成功なら `Result.Ok`、捕捉した失敗なら `Result.Error` とする変換を設ける。計算を表すラムダを渡す関数にするか、既存の `handle` による記述を補助するかを決め、引数を評価してからでは捕捉が間に合わない点と評価順序を明示する。
- 指定した失敗だけを捕捉し、それ以外のエフェクトは維持する。成功経路でも失敗経路でも計算を重複実行せず、失敗後の処理を実行しない。関数やラムダの `return`、現在の `try` と組み合わせた際の作用範囲を定める。
- 外部ライブラリの `Result` を局所的な失敗へ変換し、中間の処理では成功値を直接扱い、公開する関数の境界で `Result` に戻す例を用意する。境界では、回復して値を返す、公開するエラー型へ変換して再伝播する、`Result` にする、の各用途を区別する。エラーの種類や原因を保持する方法も検討する。
- 外部コンポーネントの ABI に失敗エフェクトをそのまま持ち込むことは、この追加の前提にしない。既存の外部関数が返す `Result` を Benitoite 側で変換する方法から検討する。実行時エラー、トラップ、資源不足、タスクの取り消しを回復可能な失敗へ変換することは、本項目で自動的に認めない。

実行と検証の論点:

- 打ち切り時の `with` の解放順序と解放の失敗、内側のハンドラの続きを捨てる処理、早期リターンとの組合せを確認する。主な失敗と後始末の失敗の扱いを明示し、失敗が起きる前に行った外部操作や状態変更を巻き戻す意味は与えない。
- 子タスクに引き継いだハンドラの現在の制約（末尾で再開する節に限る）との関係を整理する。子タスクの失敗を `await` で観測するか、結果に保持するか、タスク群の取り消しとどう組み合わせるかを決める。同期の非再開ハンドラが、そのまま子タスクにも使えるとは扱わない。遅延評価で失敗が起きる時期と捕捉範囲も確認する。
- 既存のハンドラによる実装、内部で `Result` 相当の戻り値へ変換する実装、失敗の操作を専用に最適化する実装を比較する。成功時・失敗時・境界変換・多数のリソースを解放する場合の費用と、コンパイル時の費用を分ける。測定前に性能への影響を断定せず、測定は `benchmark` スキルに従う。
- 具体的な処理例で、現在の `Result` と `try`、具体的なエラー型の既存エフェクト、追加後の汎用の失敗の仕組みを比較する。高階関数、異なるライブラリのエラーの変換、入れ子の捕捉を含め、追加が必要な範囲を確かめてから実装方式と記法を決める。
- 実装プランには型検査・脱糖・VM・必要なテストと診断、標準ライブラリ、設計書、リファレンス、同梱の Skill の更新を含める。生成される Skill の参照文書は生成元から作り直す。07-04「01-12 との対応」に従い、形式化した範囲の内側なら処理系より先に Lean の定義と必要な証明を直し、外側なら対象外として記録する。

### TODO-063 JSON とレコードの間の変換を作る仕組み

- 状態: 未着手
- 旧: OPEN-108
- 出どころ: OPEN-108、03-08「Json」、一般的な Web システムの検討メモ「5. JSON とレコードの間の変換を自動で作る仕組み」

初回リリース版では、`Json.Value` から利用者のレコードへの変換とその逆を、手で書くしかない。REST API では、要求の本体を検証してレコードにし、レコードを JSON にして返す処理がほぼすべての経路に現れる。手書きの変換は量が多く、LLM が書くとフィールドの名前の綴りや `Option` の扱いを誤りやすい。案は次の三つである。

- (a) 処理系が、決まった型クラスの実装を導出する（`@derive(Json.Encode, Json.Decode)` のような属性。Haskell の stock deriving や Roc に近い）。処理系が `Json` のモジュールを知る必要がある。
- (b) 処理系は型の構造の汎用の表現だけを導出し、変換はライブラリが書く（Haskell の `Generic`、Scala 3 の `Mirror`）。処理系は `Json` を知らずに済むが、型システムに積と和の型の水準の表現が要り、言語の中核の変更が大きい。
- (c) 道具がコードを生成する。`benitoite` のサブコマンドか言語サーバのコードアクションで、型から変換の関数のコードを生成してソースに置く（Gleam の言語サーバの形）。言語は変わらず、生成したコードを人と LLM が読んで直せる。

(c) には、型を変えた後に生成し直すのを忘れる危険がある。復号の関数はレコードを作るのでフィールドを加えると型の誤りになるが、符号化の関数は加えたフィールドを黙って落とす。メモは、生成したコードに印を付け、型と食い違ったら `check` が警告する形でこの危険を減らす案を挙げている。

メモの見立ては、処理系が標準ライブラリの関数を特別扱いする結び付きを小さくする方針から (a) を避け、先に (c) を道具として加えることである。(b) は型システムの学習の題材としても価値があるので、型クラスの扱い（ADR 0059）とあわせて後で検討する。メモの優先の順（暫定）では 4 番目である。決定ではない。あわせて次の点を決める。

- (c) の生成の道具の置き場所（サブコマンドか、言語サーバのコードアクションか）、生成したコードの印の形、`check` が食い違いを調べる規則。
- (b) を採るか。入力の生成器や標準の型クラスの実装を導出する仕組み（関連: OPEN-046）と同じ仕組みにするかを含める。
- フィールドの名前と JSON のキーの対応（`snake_case` など）を指定する方法。(b) と (c) のどちらを採るかで形が変わる。
