## 総評

Y2 の指摘 1〜9 はすべて解消した。新しく持ち込んだ不具合は見つからなかった。ただし、R14 と 01-10 の文が、スケジュールによっては成り立たない場合を断定している（指摘 1）。

確かめた点:

- **release_starter の記録**: `begin_close`・`begin_release` は、`Blocking`・`AfterReturn` を受けたときだけ `mark_release_starter` を呼ぶ。`InProgress` では記録を変えない。`request_release` は、`Lent` の間の close には毎回 `AfterReturn` を返し、`Releasing` になってからの close には `InProgress` を返す。このため、`get_or_insert` で最初の呼び手を保つのは正しい。代入にすると、貸し出し中の後続の close が記録を上書きする。返却の後の `Accepted::StartRelease` は `request_release` を直接呼び、記録を変えない。このため、`AfterReturn` を受けた最初の呼び手が解放を始めた呼び手として残る。解放の枠（`unwind.rs`）も記録しないが、その項目は `with_bound` が立っているので、捨てるかどうかの判断には効かない。
- **世代と古い記録**: `TaskId` は世代込みで比べる。番号を使い回したタスクが、前のタスクの記録に一致することはない。記録は下ろさないが、解放を終えた後の close は `AlreadyReleased` で待たずに返る。このため、`Release(r)` で待った状態から `cancel::begin` に来ることは二度と起きない。リソースの番号も使い回さない。古い記録が判断に効く経路はない。
- **current_task の受け渡し**: 本番で `BorrowedStateServices` を作るのは `vm/dispatch/tasks.rs` の `dispatch` だけである。`state.current_task` は `restore` と `start_main` が書く。組み込みの関数は今のタスクの実行の中で呼ばれるので、記録する番号は呼び手のものになる。`cancel::begin` は `restore` が `current_task = id` を書いた後に呼ばれるので、照合する番号も取り消されたタスクのものになる。参照インタプリタは独自の `begin_release` を持ち、タスクを扱わないので、影響を受けない。
- **失敗の報告の回数**: 失敗の理由を取り出すのは `take_release_failure` だけで、取り出すと理由は消える。このため、報告が二重になる経路はない。報告が零回になる筋書きも調べた。
  - B が解放を始め、A が待って取り消された場合は、A は始めた呼び手でないので捨てず、B が受け取る。
  - A が始めて取り消された場合は、A が捨てる。ここで捨てても失敗を失うことにはならない。その失敗を受け取るはずだった A の続きは、取り消しで捨てられているからである（R14）。
  - 止める手順では `cancel::begin` を通らない。理由は `close_all_silently` で項目と一緒に捨てる。02-09 にもそう書いた。
  - `with` の枠では、`with_bound` が立っているので捨てず、後の close か枠が一度だけ受け取る。
- **テストの 7 行**: `PickTask` の番号はタスクを起動した順の通し番号である（`sched/testing.rs`）。このため、6・7 行目の `[0,1,2,3,2]` と `[0,2,1,3,2]` は、「B が始め、A が `InProgress` で待つ」と「A が始め、B が待つ」を組み立て、完了の後に A を先に選ばせている。6 行目は R14 の退行を捕まえる。修正の前の実装で両方のモードとも落ちたことを、実装者の報告で確かめた。7 行目は、A が始めた呼び手として記録されていなければ B が `Error` を受け取って落ちるので、記録が正しいことを確かめている。3 行目は、`with` のブロックの中の後の close が失敗を受け取り、ブロックを抜けるときに `ReleaseFailed` を出さないこと（Y2 の指摘 2）を確かめる。どの行も、スケジュールの誤りがないことと、指示を使い切ったこと（`remaining == 0`）を確かめている。
- **文書**: 01-10・02-08・02-09・CHANGELOG は、Y2 の指摘 2〜8 の修正案のとおりに直っている。01-10 の二つの節は、互いを参照するようになった。

## 指摘

### 1. 推奨: 解放を始めたタスクより先に、待っていた別のタスクが選ばれると、失敗は捨てられずそのタスクに返る。01-10 と R14 は、この場合も「捨てる」「`Ok` を受け取る」と断定している

- 場所:
  - `docs/design/01-spec/01-10-resources.md`「解放の失敗」の、`with` で束縛していないリソースの【決定】。「その解放の失敗を…捨てる。後に同じリソースの `close` などの関数を呼んでも、解放済みのリソースとして `Result.Ok(())` を返す」の部分。
  - 改造のディレクトリの decisions.md の R14。「B は解放済みのリソースへの `close` として `Result.Ok(())` を受け取る」の部分。
  - 02-09「リソースの追跡」の解放の失敗のまとめの 5 点目（この場合に触れていない）。
- 問題: 捨てる処理は、取り消された A を `restore` して `cancel::begin` に入るときにだけ走る。`with` で束縛していないリソースで、A が解放を始めて取り消され、B が `InProgress` で待っていたとする。解放が失敗で終わると、`wake_all` が A と B の両方を起こす。ここで B が先に選ばれると、B は close をやり直し、`AlreadyReleased` の分岐の `take_release_failure` で理由を取り出して `Result.Error` を返す。A は後で選ばれても、捨てる理由が残っていない。A が選ばれる前に、別のタスク C が新しく close を呼んだ場合も、同じく C が `Error` を受け取る。
  - 失敗は一度だけ報告されるので、失敗を失う方向の誤りではない。R12（誰が受け取るかがスケジュールで変わることは仕様に書かない）の範囲に収まる。
  - しかし 01-10 は、捨てることと後の close が `Ok` を返すことを、条件なしに書いている。今の処理系では、選ばれる順によってはどちらも成り立たない。設計書は処理系の振る舞いに一致させる規約があるので、直したほうがよい。
  - 7 行目のテストは A を先に選ばせているので、この順序は確かめていない。
  - これは Y2 から続く振る舞いで、Y2fix が持ち込んだものではない（Y2 でも捨てる処理は `cancel::begin` にあった）。
- 修正案（どちらかを設計者に選んでもらう）:
  - (a) 文書だけ直す。01-10 の文を「その解放の失敗を、取り消されたタスクの続きには返さず、実行時エラーにもしない。ほかの `close` などの関数が先に受け取らなければ捨てる」の趣旨に改める。「後に…`Result.Ok(())` を返す」は、「取り消されたタスクが取り消しの手順に移った後に呼んだとき」と条件を付ける。誰が受け取るかには立ち入らない（R12）。R14 の該当の文も「A が先に選ばれれば」と条件を付けて訂正する。02-09 の 5 点目にも、捨てるのは取り消されたタスクが選ばれたときであり、それより前に close をやり直した側が理由を取り出すことがある、と一文を足す。
  - (b) 振る舞いを決まった形にする。`begin_close`（と `begin_release`）の `AlreadyReleased` の分岐で、記録した始めた呼び手がまだ `Release(r)` で待っているなら、その呼び手以外には理由を渡さず `Ok` を返す。始めた呼び手は自分で受け取るか、取り消されていれば捨てる。B は常に `Ok` になり、01-10 の今の文が成り立つ。ただし、呼び手がまだ待っているかを調べる手段を足す必要がある。そのうえ、始めた呼び手が理由を取り出さないまま終わる経路がないことを示さないと、報告が零回になる危険を持ち込む。このため、この改造では (a) を勧める。
  - どちらを選んでも、7 行目の変種として B を先に選ばせる行（例: `[0,2,1,3,1]`）を足し、選んだ振る舞いを固定する。(a) なら期待は `Error("fake flush failure")`、(b) なら `Ok` になる。

### 2. 軽微: `get_or_insert`（最初の呼び手を保つ）を確かめるテストがない

- 場所: `crates/benitoite/src/runtime/io/resources.rs` の `mark_release_starter`。表のテストの 7 行。
- 問題: 7 行はどれも `File.Writer` を貸していない状態で close するので、`Blocking` しか通らない。`AfterReturn` を二度受ける場合を通らないので、`get_or_insert` を代入に変えても、どのテストも落ちない。実装者の報告と 02-09 の【方針】は、この点を理由付きで決めている。
- 修正案: `resources.rs` の単体テストを一つ足す。貸した項目に二つのタスクで `request_release` してから `mark_release_starter` を呼び、`is_release_starter` が最初のタスクにだけ真を返すことを確かめる。関門のコメントには 02-09 の【方針】を引く。VM を通す行にするなら、書き込みの仕事を保留した間に二つのタスクが close する行を足すことになるが、準備が重くなる。単体テストで足りる。

### 3. 軽微: 01-10 の「解放を始め」が、貸し出し中の close の場合にどう読めるかが言語仕様の中で定まっていない

- 場所: 01-10「解放の失敗」の、`with` で束縛していないリソースの【決定】の「`close` などの関数を呼んだタスクがその解放を始め」。
- 問題: 貸し出し中のリソースへの close では、実際の解放は返却の後に始まる。言語仕様の読み手には、最初に close を呼んだタスクが「解放を始めた」とみなされることが読み取れない。02-09 の【方針】には書いてある。
- 修正案: 「そのリソースの解放を最初に求めた（`close` などの関数を最初に呼んだ）タスク」のように、実装の方式に依存しない言い方にする。
