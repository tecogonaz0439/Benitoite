## 総評

直し方は事前点検の (a)(b) のとおりで、次の点は正しい。

- 印を立てる位置: `Opcode::Use` の `check_release` の直後で、枠を積む前に立てる。上限で `CallStackTooDeep` を返す場合も枠は積むので、印だけが立って枠がない状態は生じない。
- 捨てる条件: `restore` が取り出すのは `TaskState::Waiting(WaitReason::Release(r))` だけである。この状態で保存されるのは、`StateWait::Resource` を返した close の関数・`begin_release` と、戻りの `RELEASE` の待ちだけである。辿りの途中の解放の枠の待ち（`TaskState::Unwinding` の `work.waiting`）は対象に入らず、`begin` もそのときは `state.unwinding.is_some()` で早く戻る。戻りの `RELEASE` で待つリソースには必ず印があるので捨てない。
- 取り消しと解放の完了の順序: 解放の完了より前の取り消し（`cancel::request` は `Release` の待ちを外さない）も、完了で起きた後で選ばれる前の取り消しも、`task.state` は `save` が書いた `Waiting(Release(r))` のまま残る。したがって、どちらの順序でも `begin` で捨てる。`AfterReturn`（貸している最中の close）でも、`wake_all(Release)` は解放の完了の後にしか呼ばれない（`Accepted::StartRelease` の `Done` と `Accepted::ReleaseFinished`）。このため、理由が書かれる前に起きて捨て損なうことはない。
- 止める手順: `begin_stop_all` はタスクを `Unwinding` に変えるので `begin` を通らない。印のないリソースの理由は、これまでどおり `close_all_silently` で項目と一緒に捨てる。止める手順ではユーザーのコードが走らないので、理由を後の close が受け取ることはない。
- 印を下ろさないこと: `with` の枠は、解放が終わり、残った理由を取り出すまで降りない。降りた後のリソースは `Released` なので、後の close は待たずに `AlreadyReleased` を返す。印が立ったままでも、捨てるはずの理由を残す場合は生じない。項目が `prune_released` で消えると `is_with_bound` は偽を返すが、消えるのは理由のない項目だけなので結果は変わらない。
- 通常の切り替えの費用: `restore` に増えたのは、照合の分岐一つと `Option<ResourceId>` の引数一つだけである。`cancel::begin` の呼び出しは前から切り替えのたびに行っており、増えた処理は要求があるときだけ走る。無視できる。
- テスト: 親の `bind` の行（後の close が `Ok`）と親の `with` の行（ブロックを抜けるときに `ReleaseFailed`）は、Q5 と Q9 の契約を直接確かめている。報告によれば、捨てる処理を外すと親の `bind` の行が `Finished(Error("fake flush failure"))` で落ち、印の条件を外すと親の `with` の行が `Finished(Ok)` で落ちた。退行を捕まえられることは確かめてある。
- Y1 のレビューの推奨 2（02-09 を印で書き分ける）は解消した。指摘 5（後の close が `Ok` を返すことを確かめる）も、親の `bind` の行で解消した。

要修正は 1 件ある。同じリソースを複数のタスクが閉じる場合に、Y2 の変更で失敗が一度も報告されなくなる筋書きがある（指摘 1）。Y1 のレビューの推奨 1 と軽微 3・4 は解消していない（指摘 2・6・7）。

## 指摘

### 1. 要修正: 取り消されたタスクが、取り消されていない別の close の待ち手の受け取るはずの失敗を捨てる

- 場所: `crates/benitoite/src/vm/dispatch/tasks/cancel.rs` の `begin` で足した `take_release_failure`。02-09「リソースの追跡」の解放の失敗のまとめの 5 点目（「close の関数を呼んだタスクが…取り消されたときは、`with` で束縛していないリソースでは、取り消しの手順に移るときに失敗の理由を捨てる」）。
- 問題: `with` で束縛していないリソース `r` について、次の順に進むと失敗が失われる（コードを読んで判断した。実行では確かめていない）。
  1. タスク B が `File.closeWriter(r)` を呼ぶ。`request_release` が `Blocking` を返し、B が解放を始めて `Release(r)` で待つ。
  2. タスク A も `File.closeWriter(r)` を呼ぶ。`InProgress` が返り、A も `Release(r)` で待つ。
  3. A だけが取り消される。`cancel::request` は `Release` の待ちを外さない。
  4. 解放が失敗で終わる。`finish_release` が理由を残し、`wake_all` が A と B の両方を起こす。
  5. A が先に選ばれると、`begin` が印のない `r` の理由を捨てる。その後に B が `begin_close` をやり直すと、`AlreadyReleased` で理由がなく、`Result.Ok(())` を返す。

  B は取り消されておらず、自分で解放を始めた呼び手である。02-09 の 4 点目（「close の関数が始めた解放の失敗は…close の関数がそれを `Result.Error` にして返す」）に反する。Y2 の前は、A が理由を取らないので B が必ず受け取っていた。したがって、これは Y2 が持ち込んだ退行である。R12 は「誰が受け取るかはスケジュールで変わるが、どの場合も一度だけ報告する」ことを前提にしていた。この筋書きでは、スケジュール次第で報告が 0 回になり、その前提が崩れる。B が先に選ばれれば B が受け取るので、結果がスケジュールで変わる点も残る。同じリソースを複数のタスクが閉じる使い方は珍しい（study 5 節の点 2）が、失敗を黙って失う側の退行なので、設計原則 1・2 の趣旨に照らして放置しないほうがよい。
- 修正案（どれかを設計者に選んでもらう）:
  - (a) 捨てる条件を、取り消されたタスクがその解放を始めた呼び手である場合に限る。`begin_close`・`begin_release` が `Blocking`・`AfterReturn` を受けた（自分が解放を始めた）ときに、項目に始めたタスクの番号を記録する（例 `release_starter: Option<TaskId>`）。`begin` は `release_starter == Some(current_task)` のときだけ捨てる。A が始めて取り消され、B が `InProgress` で待っていた逆の場合は、A の理由を捨てるので、B は解放済みのリソースへの close として `Ok(())` を受け取る。これは 01-10 の二つの規則に合う。ただし、凍結した型 `ResourceEntry` にもう一つ欄を足すので、Q9 と同じく設計者の了承が要る。
  - (b) 今回は直さず、docs/todo に新しい項目として登録する。あわせて、02-09 の 5 点目に「同じリソースの解放をほかのタスクも待っていたときは、そのタスクより先に選ばれると、ほかのタスクも失敗を受け取らない」と今の振る舞いを書き、R12 の前提の文を改造のディレクトリで訂正する。
  - どちらを選んでも、表のテストに「B が解放を始め、A が `InProgress` で待って取り消される」行（スケジュールで A を先に選ばせる）を足し、選んだ振る舞いを固定する。

### 2. 推奨（Y1 の推奨 1 の未解消の部分）: 01-10 の `with` の段落の「ただし」の文が、実行で確かめられていない。「解放したリソースの使用」とも参照し合っていない

- 場所: `docs/design/01-spec/01-10-resources.md`「解放の失敗」の、`with` で束縛したリソースの【決定】の 3 文目と理由の文。同じ章の「解放したリソースの使用」の【方針】。
- 問題:
  1. Y2 で足した親の `with` の行は、ブロックの中で close を呼ばずに抜ける。そのため、「ブロックを抜ける前に同じリソースの `close` などの関数をもう一度呼んだときは、その関数が失敗を `Result.Error` で返す」は、Y2 の後も実行で確かめていない。設計書は処理系が実装していると確かめた内容だけを書く、という規約に照らすと、テストの裏付けが要る。
  2. Y2 は、`with` で束縛していない段落に「後に…`close`…を呼んでも、解放済みのリソースとして `Result.Ok(())` を返す」を足した。これで「解放したリソースの使用」との整合は束縛していない側だけ取れた。束縛した側の「ただし」（後の close が `Result.Error` を返す）は、「解放済みのリソースへの close は `Ok(())`」の例外のままで、どちらの節も相手を参照していない。隣り合う二つの【決定】で後の close の結果が逆になるので、例外であることを示さないと矛盾に見える。
  3. 「もう一度呼んだとき」の主語が書かれておらず、呼べるのはブロックの持ち主（または別のタスク）であることが読み取れない。理由の文も「ブロックを抜けるときに報告して」だけで、但し書きの場合を支えていない。
- 修正案:
  - 表のテストに、親の `with` の行の変種を一行足す。`after` を `bind r <- File.closeWriter(w) |> Result.mapError(_,IOError.message)` などにして後の close が `Error("fake flush failure")` を返すことを確かめ、ブロックを抜けるときに `ReleaseFailed` が出ない（二重にしない）ことを、Direct と Request の両方で確かめる。準備はほかの親の行と同じでよい。
  - 文を「ただし、そのブロックを抜ける前に、いずれかのタスクが同じリソースの `close` などの関数を呼んだときは、その関数が失敗を `Result.Error` で返し、ブロックを抜けるときには報告しない。」とする。理由の文は「失敗を一度だけ、受け取れる側に返して見落とさせないためである」のように、両方の場合を支える形にする。
  - 「解放したリソースの使用」の「解放済みのリソースに呼ぶと、何もせずに `Result.Ok(())` を返す」に、「（「解放の失敗」の、取り消された `close` の失敗を `with` のブロックの中で受け取る場合を除く）」と参照を足す。

### 3. 推奨: 02-09 で、止める手順で待っていた close の理由の扱いが書かれなくなった

- 修正案: 5 点目の束縛していない場合の文の後に、「止める手順で解放の完了を待っていた場合は捨てる処理を通らず、理由は実行を終えるときに項目と一緒に捨てる（止める手順ではユーザーのコードが走らないので、後の close が受け取ることはない）。」を足す。

### 4. 軽微: 02-09 の `with_bound` の【方針】の理由の文が読み取りにくい

- 場所: 02-09「リソースの追跡」の、足した【方針】の「理由: 解放の枠は…枠を降ろした後にこの印によって残る失敗はない。」
- 問題: 「この印によって残る失敗」が、何と比べて残る失敗なのかが分かりにくい。言いたいのは、印を下ろさなくても、捨てるべき理由を誤って残す場合が生じない、ということである。また、取り消された close の側から見た根拠（枠を降ろした後のリソースは解放済みで、close は待たずに返る）が抜けている。
- 修正案: 「理由: 解放の枠は、解放を終えて未報告の失敗を取り出すまで降ろさない。降ろした後のリソースは解放済みであり、close の関数は解放の完了を待たずに返るので、印が立ったままでも取り消された close の失敗を残すことはない。」とする。

### 8. 軽微: CHANGELOG の文が、`with` で束縛した場合の受け取り手を言い切りすぎている

- 修正案: 例「Cancelling a task while it waits in a close function such as `File.closeWriter` now discards the release failure when the resource is not bound by `with`, so a later close returns `Ok`. For a resource bound by `with`, including one bound in another task, the failure is still reported once: by a later close in the block, or when the block exits.」。指摘 1 で (b) を選ぶ場合は、複数のタスクが閉じるときの例外もここに書くかを決める。
