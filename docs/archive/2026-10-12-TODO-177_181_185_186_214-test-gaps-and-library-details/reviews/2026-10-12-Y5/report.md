## 指摘

### 1. 推奨: 段の並べ替えのテストが、検査器が定数を先に検査するという実装の順序に頼っている

- 場所: `crates/benitoite/src/pipeline.rs` の `checking_sorts_each_stage_and_stops_before_later_errors` の追加の入力（「定数の検査は関数の本体より先に進むので」のコメントの後）。
- 問題: 入力は「関数の本体の誤り → 後ろの定数の誤り」の順のソースである。型検査が定数を先に検査する今の順序のときだけ、並べ替える前の診断が逆順になる。検査器が定数と関数をソースの順か関数の先に検査するように変わると、このテストは `sort_by_key` を消しても通るようになる。空振りしても誰も気づかない（test-audit の「実装の詳細に結び付いたテスト」）。
- 修正案: 関数の前と後ろの両方に、誤りのある定数を置く（例: `const a: Integer = "x"`、誤りのある `main`、`const b: Integer = "y"`）。定数を先に検査する順序では a, b, main の順に診断が出て、関数を先に検査する順序では main, a, b の順に出る。どちらの順序でも、並べ替えを消せば位置が昇順にならない。診断の数の期待は 3 にする。コメントも「どちらの順で検査しても、並べ替えがなければ位置の順にならない」という趣旨に改める。

### 2. 推奨: 07-03 の `list_hof_long` の理由の文が、測った事実を超えて断定しており、何が「繰り返し」なのかも不正確である

- 場所: `docs/design/07-quality/07-03-compiler-testing.md`「差分テスト」の追加の段落（150 行）。`tests/golden.rs` の `EXPENSIVE_REFERENCE_CASES` のコメントも同じ文である。
- 問題:
  - 「長いリストを組み込みの関数へ繰り返し渡す」とある。しかしスクリプト自身は、`List.map`・`filter`・`fold` に一度ずつリストを渡すだけである。繰り返し渡しているのは、標準ライブラリの `List.bnt` の `mapFrom` などで、要素ごとに `get(xs, i)` と `append(acc, y)` を呼ぶ。読み手がスクリプトを開くと文と合わない。
  - 「時間はリストの長さの二乗で増える」は、長さを変えて測った結果ではない。measurements.md が残すのは、5 万要素で段 1 が 300 秒で終わらなかったことと、段 2 が 274 秒だったことだけである。「呼び出しごとに O(n)」も「実装者のコードからの見立て。内訳は測っていない」と書いている。二乗という結論は、コードから導いた見積もりとしては正しい（呼び出しの回数が長さに比例し、各呼び出しで長さ n の `xs` を変換する）。ただ、今の文はその導き方を示さずに、測った事実のように断定している（AGENTS.md「事実と出典」、japanese-tech-writing の論証の厳密さ）。
  - 「呼び出しごとに引数と結果を変換するため」だけでは、変換の費用が値の大きさに比例するという、二乗を導くのに要る前提が抜けている。
- 修正案: 例えば次のようにする。「理由: 参照インタプリタは、組み込みの関数を呼ぶたびに、引数と結果のリストの全体を変換する。標準ライブラリの `List.map`・`filter`・`fold` は要素ごとに組み込みの関数（`get`・`append`）を呼ぶので、このケースの変換の量はリストの長さの二乗に比例し、5 万要素の差分比較は 2026-10-12 の測定で 300 秒以内に終わらなかった。参照インタプリタは簡単さを優先する道具であり、このケースの値は VM 側のゴールデンの期待値で確かめる。」冒頭の句も「長いリストに標準ライブラリの高階関数を使う `list_hof_long`」に改める。`EXPENSIVE_REFERENCE_CASES` のコメントも同じ趣旨に揃える。
