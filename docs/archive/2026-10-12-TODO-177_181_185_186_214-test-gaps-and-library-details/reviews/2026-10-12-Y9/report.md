# Y9 のレビュー

対象: 15137ad7「Limit each value rendered in an Assert failure to 4 KiB」（取り込みは 328d59de）。`git show` だけで読み、何も走らせていない。

## 結論

要修正はない。上限の契約（`…` を含めて 4,096 バイト以下、4,093 バイト以下の最後の文字の境界で切る、超えたら辿るのをやめる）は、読んだ範囲のすべての経路で守られている。推奨 1 件、軽微 3 件。

## 確かめたこと

- **上限と境目**: `render_value` のループは `out.len() <= 4096` の間だけ回り、ちょうど 4,096 バイトで仕事が尽きれば切らない。1 バイトでも超えたら抜け、`end = 4093` から `is_char_boundary` で後ろへ戻して `…` を足す。結果は最大 4,096 バイトになる。超えた後に残った仕事が何も書かずに終わる場合はない（閉じ記号・区切り・名前はどれも空でない）ので、「ちょうど 4,096 バイトで、続きがあるのに切らない」ことは起きない。
- **出力の伸び**: `append_within` は予算＋1 文字までしか足さない。`quoted_within` は追加の前に `out.len() > budget` を見るので、超過は逃がし 1 つ分（最大 10 バイト程度）にとどまる。数値・`Decimal`（固定長。`to_text(self)`）・タグの表記は短い。出力の `String` は上限付近にとどまる。
- **多バイト文字・逃がし**: 切る位置は出力の文字の境界なので、UTF-8 の途中では切れない。逃がしの並び（`\u{202e}` など）の途中では切れうるが、study.md 3.3 で「`…` が切ったことを示すので足りる」と決めたとおりであり、06-04 の規則（文字の境界）にも合う。逃がしの記号は ASCII なので、切っても制御文字は現れない。テストの `\u{202e}` ×600 の行が、逃がした後の長さによる判定と、逃がしの途中での切断の両方を期待値に含めている。
- **辿るのをやめる**: リストは `list::cursor`、マップ・集合は `map::Cursor`、`Bytes` は添字で、一度に一要素ずつ進める。`to_vec`・`map_to_vec`・`set_to_vec` と全バイトの仕事の積み上げは除かれた。文字列は `ctx.str` の借用を `chars()` で読み、予算を超えたら残りを読まない。構成子の引数を `constructor_parts` で全部取り出すのは宣言で決まる数なので、時間は上限で抑えられる。各値の最初の仕事が 1 バイト以上を書くという論証のコメントも、`render_typed` の ADT（名前の `Owned`）・レコード・形だけの経路で成り立つ。
- **明示の積み重ね・回収しない区間**: 走査は `Vec<Work>` の積み重ねのままで、`Work` の新しい形（`List`・`Tree`・`Bytes`）も `Value<'e>` とカーソルを関数の中の `Vec` に置くだけである。安全点を越える保存や構造体の欄への格納はない。型の再帰（`has_params`・`substitute`）は値でないので従来どおり。
- **文書**: 06-04「結果の報告」の【決定】と理由、JSON Lines の `left`・`right` の一文、言語リファレンス §16 の段落、CHANGELOG の Changed の行は、数値（4,096・4,093・U+2026）と「残りを辿らない」で一致し、実装とも合う。02-10 は study.md のとおり変えなくてよい。`docs/ja/` はリリースのときに訳す決まりである。
- **テスト**: 境目（4,094 と 4,095 の `a`）、多バイト（`"a"`＋`あ`×1400 で 4,091 バイトの境界）、逃がした後の長さ、List・Set・Map・Bytes、深い入れ子、`Assert.notEqual` の両側を、型付きの経路と総称関数（形だけの経路）の両方で確かめている。期待値は `cut_expected` が Show の全体から作り、本番の書き出しを使わない。`Byte`・`Bytes`・制御文字の表の行も study.md 3.3 の 4 のとおり。長いテストの `#[ignore]` と gc-stress の分岐を外したのも study.md 3.4 の推奨どおり。

## 指摘

### 1. 【推奨】共有した構造のテストが、型付きの経路しか通らない

- 場所: `crates/benitoite/src/runtime/assert/tests.rs` の `shared_values_stop_rendering_at_the_limit`。
- 問題: `Assert.equal(grow(64, Tree.Leaf), Tree.Leaf)` は静的な型 `Tree` があるので `render_typed` の ADT の分岐だけを通る。形だけの経路（`render_object` の `FieldsKind::Ctor` → `<constructor #タグ>(…)` と `arguments`）は別の入口で、ここで辿るのをやめない退行があっても、指数時間の退行を捕まえるテストがない。同じファイルの長い値のテストは、入口が違うことを理由に両方の経路を通しており、このテストだけ片方である。
- 修正案: 同じソースに `function check[T: equality](a: T, b: T) -> Unit uses Assert.Check` と、`check(grow(64, Tree.Leaf), Tree.Leaf)` を呼ぶテストの関数を足し、`left` が `<constructor #` で始まり、4,096 バイト以下で `…` で終わることを確かめる。値を作る時間は増えない（64 段）。

### 2. 【軽微】上限の定数と `render_value` の説明に、上限と設計書の節がない

- 場所: `crates/benitoite/src/runtime/assert.rs` の `const MAX_RENDERED_BYTES` と、`pub fn render_value` の `///`。
- 問題: 定数にコメントがなく、根拠の節（06-04「結果の報告」）が定数の位置から辿れない。公開の関数 `render_value` の `///` は「`Show.show` の形に揃えて書き出す」のままで、4 KiB で切ることを書いていない。
- 修正案: 定数に `/// 一つの値の書き出しの上限（`…` を含む）（設計書 06-04「結果の報告」）。` を置き、`render_value` の `///` に「4,096 バイトを超えるときは切って `…` で終える」と一文足す。`text::ELLIPSIS` にも、ほかの定数に合わせて用途の `///` を置くとよい。

### 3. 【軽微】逃がしの途中で切れることが、利用者向けの文書から読めない

- 場所: `docs/reference/benitoite.md` §16 の追加の段落、06-04「結果の報告」の【決定】。
- 問題: 規則（文字の境界で切る）どおりだが、`"\u{20…` のように逃がしの並びの途中で終わる表示がありうることは書いていない。報告の第一の読み手の LLM が、これを壊れた逃がしと読む余地がある。
- 修正案: 必須ではない。書くなら、リファレンスに「The cut may fall inside an escape sequence such as `\u{202e}`.」程度を足す。06-04 は今のままでよい。

### 4. 【軽微】平らなコレクションと文字列で「辿るのをやめる」退行は、テストで捕まらない

- 場所: `long_values_are_cut_at_4_kib_with_an_ellipsis`。
- 問題: リスト・集合・マップ・`Bytes`・文字列を全部写してから切る形に戻しても、期待値は同じなので今のテストは通る（1,000 要素・1,400 バイトでは時間の差も出ない）。指数時間の退行は 1 の共有した構造のテストが捕まえるが、大きな平らな値での時間の退行は捕まえない。
- 修正案: 時間で確かめるテストは不安定になりやすいので、足さなくてよい。今のとおり `render_value` のコメントの論証（一度に一要素ずつ進める）で守り、確認の観点として残す。
