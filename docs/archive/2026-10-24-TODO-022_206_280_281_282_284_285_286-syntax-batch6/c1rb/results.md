## 事前点検で確かめた接続箇所

`BudgetAnalyze.lean` の expr は、具体規則のない二項演算と既定の構成子で skipChildren の後に unsupported を返す。`BudgetWalk.lean` の Context は、一つの warningsRev と一つの identitiesRev、次キー、予算を持ち、独立した入力に属する解析結果の保存先を持たない。report と analyze は、この一つの警告列を入力自身の警告として公開する。

`BudgetLocated.lean` の skip_silent は skip 群が警告列を変えないこと、`BudgetTraversal.lean` の skip_walk・analysis_walk は保存した対応が先行順の接頭辞であることを示す。`BudgetNormal.lean` と `BudgetSound.lean` は、その実際の中間状態と番号消費を使って正常値と拒否原因を合成する。`BudgetBody.lean` の本体入口の三つの系も、この expr と保存列へ接続している。

したがって、skipChildren を子の expr に単純に置き換えるだけでは足りない。子の警告を親の warningsRev へ混ぜると、親の EvalPartial の導出では未知の内側の trace が空であるため、親の WarningSoundness だけでは子の警告原因を実質的に説明できない。これが RV-C1 中1 の指摘であり、独立した入力の警告として扱う必要がある。親の警告列をそのまま保ち、子の入力・忘却後の環境・元のキー・結果を別に対応付ける接続と、その保存についての証明が必要になる。

後から子をもう一度 analyzeExpr するだけの二段階処理も、そのままでは D8a の「skip の代わり」に合わない。現行の skip が既に消費する番号・操作・保存を重ねず、子の解析が使った本体・全体予算を次へ引き継ぐ必要がある。子の完了時に finishBody で親の一時項目を返したり、本体の操作数を初期化したりしてはならない。

with と handle の本体は Expr ではなく Block である。独立入力を表す際は、Block の容器自体には番号を加えない約束を保ち、with では束縛を一つ加えた位置の形を用意してから外の整数の事実を忘れる必要がある。ラムダ・lazy・handler 節は、既存の別本体の列挙との役割を分ける。これらは実装を選ぶ際の確認事項であり、今回、新しい内部の契約を確定したものではない。
