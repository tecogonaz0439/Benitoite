# CheckedInteger の型の符号化の調べ（Q-opaque）

2026-10-26、取りまとめが Codex（GPT-6.1-Sol）に依頼した読み取りだけの調べの報告を写す。

**案 A（Lean 側を現行の `data` 表現に合わせる）を推す。** 現行の交換は、設計書が定める「`@opaque` の data・レコードも、内部構造を持つ代数的データ型として表す」という契約に合っている。今回の不一致は、区間解析の Range モデルが、言語の可視性を表す `@opaque` と、Lean の別の型構成子である `.opaque` を対応させた箇所で直すのが適切である。

ただし、案 A を「`.opaque owner` を `.data owner []` に置き換えるだけ」と見積もってはならない。型の変更に伴う評価導出の補完と、三欄の構成子値への移行を分け、各枝で証明を閉じる進め方を推す。停止解消だけを先行させる第三案として、既存の証拠付き値 `checkedRange` を残し、その型を `data` に合わせる方法も成立する見込みがある。

今回は読み取りだけを行った。ファイルの作成・変更、git の変更操作、Lean・cargo のビルドとテスト、担当の委任は行っていない。`private/` と、それを指すスキルのリンクも読んでいない。以下の時間は過去の記録とソースの依存関係に基づく見積もりであり、今回の実測値ではない。パスはすべて `<repo>` を基準とする相対パスで示す。改造のディレクトリは依頼文と同じく D と略す。

**判断の根拠は、交換の契約と `.opaque` の意味の違いにある。**

[01-12「構文」](docs/design/01-spec/01-12-core-calculus.md#構文)の84〜85行は、次の二つを区別している。

- `@opaque` の data・レコードは、内部構造を持つ `D` に含める。
- `O` は、等値を持たない組み込みの不透明型である。

実際の交換器は `src/` ではなく、[tests/desugar_export/exchange.rs](crates/benitoite/tests/desugar_export/exchange.rs) にある。568行の `TyCon::Adt` → `data` は、この契約に対応する。組み込みの Task などを `opaque` にする別の分岐も同じ関数にあり、両者は意図的に分けられている。

[03-06](docs/design/03-interop/03-06-stdlib.md)も、`@opaque` による構築・更新・表現パターン・自動アクセサの制限と、値の等値・鍵としての性質を区別している。特に200〜202行と222〜224行は、CheckedLength・CheckedIndex・NonEmptyList の構造の等値と鍵の順序を定めている。表現を外部から操作できないことは、Lean の `.opaque` に移してよい根拠にはならない。

一方、[07-04:122](docs/design/07-quality/07-04-formal-semantics.md) は、Range の評価導出が Surface の型と `StandardRule.argumentType`・`resultType` の一致に依存すると明記している。A18a は、その接続条件が満たされていないことを保存済みの実交換で示した。ここは A1 の限界を追記するだけで完了とせず、型の対応を実際に直す必要がある。

**案 B では、標準の本体よりも、既存の型付けと宣言表への影響が問題になる。**

標準の Range.bnt の本体は、通常の脱糖交換には入らない。`exchange.rs:2438` 以降の `definitions` は、`DefOrigin::User` 以外の定義を除いている。標準関数については、2776行以降の `named_stdlib_declarations` が、参照した関数の署名を本体なしの別表へ書き出す。したがって、**通常の Range 利用入力では「Range.bnt の本体を `data` のまま交換するか」は直接の衝突点ではない。**

しかし、一般の利用者定義の `@opaque` まで案 B を適用すると、宣言モジュールの本体も交換される。既存の `testdata/eval/k1-opaque/` は、Model 内で Positive を構築・更新・分解し、外側の main から同じ公開関数を呼ぶ入力である。内部を `data`、外部を `opaque` にすると、同じ `M.make` や `M.value` の署名が利用元によって変わる。現在の Lean の準備は、一つの関数名に一つの宣言を対応させる。単に `Surface` に現在のモジュールを追加するだけでは、内部の本体と外部の呼び出しの双方を同じ宣言表で検査できない。

案 B の実装対象は、少なくとも次の範囲になる。

- `tests/desugar_export/exchange.rs` の `Surface`、`ty`、`type_arg`、関数・取得関数・定数の書き出し、標準宣言・型クラス・実装の表。
- `tests/desugar_export/builtins.rs` のデータ宣言、欄の型、要約、補充する標準型の扱い。
- モジュールごとの型の見え方、公開署名と内部署名の接続を表す交換契約。
- 意味を保つ方式によっては、`formal/Benitoite/Exchange/`、`Release/`、`Surface/` の型・代入・制約判定・宣言表・関連証明。

`Binding` には既に `module` と `opaque` があるので、属性の検出自体は可能である。ただし、現在の交換器の `Surface` は利用元のモジュールを保持していない。補充した標準型についても、元の宣言とローカルな番号の対応を保って属性を渡す必要がある。

Lean の読み込みは、[Exchange/Syntax.lean:71〜72](formal/Benitoite/Exchange/Syntax.lean)で `opaque` と `data` を別々に読み、`Convert.lean:60` もその区別を保つ。正規化で同一になる型ではない。表層の扱いは次のとおりである。

| 操作 | 現行 Lean での `.opaque` の扱い | 案 B への含意 |
|---|---|---|
| 局所値・引数・戻り値・通常の受け渡し | 型として保持できる | 署名と注釈を揃えれば、この範囲は扱える |
| `match` の変数・`_` | 任意の型を受け入れる | `Result.Ok(value)` の中身をそのまま束縛する用途は扱える |
| 構成子・レコードのパターン | `CheckPatterns.patTy` は `.data` に対して構成子を照合する | `.opaque` の内部表現を分解する規則はない |
| 構築・更新 | `Check.lean:337〜363` は結果・更新元を `.data cd.data ts` とする | 内部を `data` に保つ必要があり、外部型との接続が別途必要 |
| 等値・鍵の制約 | `Release/BuiltinTable.lean:113` 付近の `satisfiesB` は `.opaque` に `false` を返す | 既存の不透明レコードの等値・鍵をそのまま検査できない |
| 型引数・型代入 | `.opaque` は名前だけを持ち、型代入はその内部を辿らない | 多相な不透明レコードを一般に表せない |
| リソースの `with` | 専用に `.opaque owner` と `isResource` を使う | Range の不透明レコードとは用途が異なる |

特に、`CheckedLength[Integer]` と `CheckedLength[String]` を同じ `.opaque owner` に潰す方法は採れない。名前の文字列へ型引数を埋め込んでも、標準宣言の `CheckedLength[T]` に対する型代入がその文字列を辿らない。既存の組み込み型についても、この制約は `builtins.rs` の `opaque_arguments` と `unconvertibleTypes` に明記されている。また、高カインドの型引数を扱う `type_arg` と Lean の `TyCon` にも、代数的型構成子に相当する不透明型の頭が必要になる。

標準ソースの `@opaque` は **7型**である。

| モジュール | 型 | 現行の交換と案 B の問題 |
|---|---|---|
| Range | CheckedInteger | 引数なしの `data`。Range モデルとの今回の不一致 |
| Range | CheckedLength[T]、CheckedIndex[T] | 型引数を保つ `data`。`opaque` へ移すなら型代入・等値・鍵の対応が必要 |
| NonEmptyList | NonEmptyList[T] | 同上。`map` は入力と出力で要素型も変える |

このほか、利用者が宣言できる `@opaque data`・レコードも対象になる。標準の7型だけの問題として案 B を実装すると、属性一般を扱う契約にはならない。

**案 A の実装では、三欄の構成子値と、検査由来の証拠を分ける。**

案 A の型と成功値の形は、概ね次になる。

```text
CheckedInteger の型:
  .data owner []

checkInteger の正常結果の型:
  .data result [.data owner [], .data error []]

成功値の実表現:
  .con owner [] checkedConstructor
    [.integer minimum, .integer maximum, .integer value]
```

現在の `RangeNames` は CheckedInteger の型の所有元を持つが、そのレコード構成子の名前を持たない。完全に `.con` へ移す場合は、**実交換の構成子宣言から `checkedConstructor` を同定する情報**が要る。型名や表示名から構成子名を推測する方法は避けるべきである。`StandardRule.rangeValue` は現在 owner しか持たないため、正しい三欄の構成子を読む方式に合わせて、その情報の受け渡しも直す。

`.opaque` の検索結果は Interval 配下の9ファイル・79行だったが、その全件が修正対象ではない。逆に、完全な構成子化では、`.opaque` が現れない `RangeState.lean` や依存証明も対象になる。

案 A の最も注意すべき点は、**`ConcreteValue.type` が構成子の内部まで検査していない**ことである。現行では次が成り立つ。

```text
(.con owner types constructor arguments).type = .data owner types
```

したがって、`.data owner []` へ揃えた後の `range_value_total` は、正しい三欄の値と `other` だけを扱えばよいわけではない。任意の欄数・構成子名・欄の型を持つ `.con` も外側の型は一致する。現在の表現を残す移行段階では、同じ所有元を指定した `rangeError` も型だけでは排除できない。

このため、次の条件を完了条件にする必要がある。

- 正しく認定した三欄の値からは、保存された value を正確に射影する。
- `other (.data owner []) …` には、従来と同様に任意の正常 Integer64 と未知の失敗を許す。
- 正しい三欄と認定できない残りの具体表現にも導出を残す。
- 未知の場合の規則を、正確な射影の規則と重ねない。重ねると `range_value_exact` が成り立たなくなる。
- `Models`・`SlotModels` を強めて、不都合な値を定理の対象から除かない。

`NormalTyped` 自体は「正常結果の型が入力型と一致する」という定義のままでよい。作り直すのは、その定義を満たす評価規則と証明である。完全な構成子化で三欄を有界な `.integer` にすれば、現在の小モデル由来の `rangeValueUnrepresentable` は整理できるが、これを未知の表現への導出まで削る理由にしてはならない。

中心二命題の `NormalSoundness`・`WarningSoundness`、公開入口の主定理、既存の `Models`、`Builtins.Assumptions` と公理の言明を保つ設計は可能である。Range の成功値の構造は評価関係の定義として与え、由来の条件は現在と同じく内部の補助関係から構成する。ただし、**言明の本文を保っても、その中で参照する評価関係は変わるため、依存する証明の再構築と定義・言明・仮定のレビューは必要**である。今回は証明が通ることまでは確認していない。

D18 は、解決済み標準束縛・三入力・三欄の保存・逆転優先・同じ成功値との対応を要求するが、Lean の型を `.opaque` にするとは規定していない。案 A はこの判断と両立する。公開境界としての不透明性は Rust の名前解決の E0340 が担い、コアで `data` を使うことによって解除されるものではない。

**第三案 C は、案 A の最初の閉じた段階として有用である。**

C では、`checkedRange owner origin checked` という既存の証拠付き表現を残し、その `ConcreteValue.type` と Range の引数・結果・Resultの認定を `.data owner []` に揃える。これにより、三欄・所属・呼び出しキーを使う既存の証明を大きく作り直さず、実交換との型の食い違いを解消できる。

C でも `range_value_total` の対象は増えるため、型の合う `.con`・`rangeError` などに未知の射影の導出を補う必要がある。`checkedRange` への正確な射影と、それ以外の型の合う値への近似規則を分ければ、`Models` を強めずに済む見込みである。閉じた評価器は、従来どおり三欄を知る `checkedRange` だけを決定的に評価し、未知の値を任意に選ばない。

C だけで区切る場合は、「型の符号化は整合したが、CheckedInteger の具体値を一般の三欄の `.con` に統一してはいない」と記録すべきである。案 A を最後まで実施するなら、この段階を先に閉じてから構成子化へ進められる。

独立した interval 交換だけで `data` → `opaque` の対応を挿入する方法も考えられるが、今回は推さない。実 Surface と標準宣言の型を読む途中に別の型変換を置き、その正当性と適用範囲を A1 の接続条件へ追加することになるためである。

**検査は、既存六入口の全比較と、区間解析の接続を別々に割り当てる必要がある。**

現在の `scripts/check-formal.sh` は、既定の Lean ビルド、六実行器、独立交換、全件の Rust 書き出し、脱糖・組み込み表・網羅性・表層検査・manifest の照合を行う。区間解析専用の `intervalDiff` は、現在のスクリプトにはまだ入っていない。したがって、**`check-formal.sh` 全体が成功しても、A18a・X02・X03 の Range 接続が済んだことにはならない。**

全体の再実行は、案 B では交換契約を変える接続の区切りで必要である。案 A・C でも、今回の修正を含む最終の関係状態の全比較は必要である。ただし、交換器と六入口の入力を変えない Lean 内部の各枝で、全比較を毎回重ねる必要はない。計画の K1/K2 等へ一度まとめ、同じ関係状態に対する成功を引用する割り当てでよい。
