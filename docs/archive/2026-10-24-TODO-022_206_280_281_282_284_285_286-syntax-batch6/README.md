## 設計者の決定（2026-10-24、C1 のレビューの後）

C1 のレビュー（`reviews/RV-C1.md` の中5）を受けて、未知の形の内側の扱いを (b) に決めた。未知の形（未同定の呼び出し・補間・リスト・レコード・pipe・try・with・handle など）の直接の子のうち評価順の定まる式と、with の本体・handle の保護された本体を、外の局所の事実を忘れた環境と元のキーで、独立した入力として解析する。外の bind の事実は持ち込まないが、子の内側だけで分かる除数0・あふれは警告できる。評価関係と中心の命題は変えない。理由: 費用が小さく、利用者に届く警告の範囲が大きく広がるためである。

## 設計者の決定（2026-10-25、用語）

C1Rb1 で加えた「警告領域」（一つの解析入力の根から、対象構文の評価関係の具体規則だけで辿れる構文上の出現の集合）の名前を、原語 syntactic reachability、日本語「構文的な到達可能性」とする（候補と出典は `c1rb3c/results.md`）。理由: 説明の言い換えは既に術語のように読め、英語の名前がないと英語の文献を調べにくいためである。実行で到達できることとは違う意味であることを、定義に残す。

## 設計者の決定（2026-10-25、処理系の作業の途中）

- 区間解析の部品を作る A01〜A06 の間は、型検査へ接続する前の関数が未使用の警告（`dead_code`）になり、警告を誤りにする設定で検査が通らない。`src/typeck/interval/mod.rs` の先頭に限り、理由のコメント付きで `#![allow(dead_code)]` を一時的に置くことを認める。AGENTS.md の許可の表に一時的な行を足し、型検査への接続を終える A07 が許可と行を消す。理由: todo!() の仮置きの許可と同じく、作業の途中でもクレートがコンパイルでき、検査を通るようにするためである。
- 勧告の照合の扱い（2026-10-24 の指示）: 改造の最初に勧告を照合し、その結果を見て改造と合わせてセキュリティの対応を組み込むかを決める。最後の検査（change・release）で新たな勧告が出た場合は、その旨を表示するだけにして不合格にしない。改造がない場合にも対応できるよう、手動と周期的に呼び出せるスキル（`security-advisories`）を設ける。
