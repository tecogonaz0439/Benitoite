## 中

### 中1 規則のない base の形が残り、契約の「未対応は型内の任意値か失敗」と食い違う（読めば確定）

- 場所: `Eval.lean` の `Unsupported`（230行）・`UnknownAt`（234行）・`EvalPartial`（303行〜）。`plan.md` の契約表「評価と中心定理」（48行）と「Surfaceの全構成子の分類」の「土台で読む」（70行）。用語集の「対象構文の評価関係」の行。01-12「区間解析の土台の解析と健全性」の表の「それ以外」の行（1504行）。07-04「区間解析の対象構文の評価関係」の98行・106行。
- 問題: `UnknownAt` は構成子の分類が `boundary`・`unknownValue`、または同定のない `api` の場合だけを未知とする。分類が `base` の構成子のうち、具体的な規則のない形には、未知の規則も具体の規則も適用されず、導出がない。該当するのは次の形である。
  - Integer64・Boolean 以外のリテラル（`Literal` の string・float・decimal・character・integer8〜unsignedInteger64・byte・float32）。
  - 加算・整数除算・剰余・六比較を Integer64 で行う場合以外の `binary`（減算・乗算・Float の演算・String の連結、Boolean や String の等値と比較など）。

  規則はすべて子の導出を前提に持つので、評価する経路にこれらの形が一つでもあれば、それを含む式・Block・本体全体に導出がなくなる。例えば `let s = "x"` を含む本体や、`x - 1` を一度でも計算する本体では、除数0やあふれの警告について中心命題は何も述べない。契約表は「未対応の式は型内の任意の正常値または失敗を許し」とし、分類表も「binaryは加算・比較・除数0だけから開始、他はTop」とする。01-12 の表と用語集の定義も、これらを未知として扱うと読める書き方である。07-04 の98行は規則のない形が残ることと空虚に成立しうることを明記しており、隠れた欠陥ではない。しかし、短絡・match（C1）、幅付き整数（C2）、同定済み API（C3・C4）には後続の L 作業があるのに対し、上の二群に規則を足す作業は計画にない。07-04 の106行は未証明の範囲を「X03 の VM 比較で補う」と書くが、Lean の側に導出がない入力には VM と比べる期待値がない。したがって X03 はこの空虚さを解消できない。
- 修正案: 中心命題の言明を変えずに、評価関係の定義を直す（L07c・L07d と同じ種類の変更であり、D15 の停止条件に当たらない）。
  1. `UnknownAt` に「具体の規則を持たない base の形」を加える。具体的には、Integer64・Boolean 以外のリテラルと、`(op, operandType)` が「加算・intDiv・mod・六比較 × Integer64」の外にある `binary` である。具体の規則と重ならないように定義する（重なると、Integer64 の加算に任意値の導出ができ、正常値の健全性が崩れる）。`analyzeBaseExpr` は既にこれらを `baseUnknown` にしているので、追加で要るのは `unknown_base` などの場合分けの補題だけの見込みである。
  2. 改良の案として、非対象の二項演算は左右の子を左から評価してから型内の任意値か未知の失敗を返す規則にする方法もある。この形なら子の中の除算の警告も定理の対象に入る。ただし、契約の「その子へ外の事実を持ち込まない」との関係を整理する必要がある。
  3. どちらを採るにしても、C1 の閉鎖の条件に入れる（L08〜L10 のいずれかの枝か、小さな枝 L07e として計画に加える）。C2 で減算などの具体の規則を足すときは、同じ変更で未知の側から外す。
  4. 07-04 の106行の「X03 の VM 比較で補う」は、「導出のある入力について VM と比べる。規則のない形の空虚さは VM 比較では補えない」と書き直す。

### 中2 警告の演算・キーが構文上の対象演算に対応することを、言明も補題も保証しない（読めば確定）

- 場所: `Eval.lean` の `Reached`（875行）・`WarningSoundness`（962行）。`Sound.lean` の `base_warning_bounds`（604行）。
- 問題: `Reached` は trace 内の事象と警告のキー・演算の一致を条件とする。`WarningSoundness` の結論は、一致する事象が存在するときだけ要求される。そのため、どの導出にも現れない `(key, operation)` を名乗る警告は、つねに空虚に健全となる。例えば、任意のキーに `⟨k, .standard 偽の束縛, .zeroDivisor⟩` や `⟨k, .binary .sub (.base .integer), .overflow⟩` を出す解析も、C0 の評価関係の下では `WarningSoundness` を満たす（C0 には `.standard` や減算の事象を作る規則がない）。現在の `analyzeBase` は、構文の演算子から演算を作るので、この形の警告は出さない。しかし、それを述べる定理はない。`base_warning_bounds` が保証するのは、警告のキーが入力の部分木の番号範囲にあることだけであり、そのキーの出現が警告の演算と同じ構文であることは保証しない。Rust の側と交換の比較が警告をキーと原因で照合すると、Lean の言明が許す「演算の取り違え」を検出できない。L22〜L24 で `TargetOperation.standard` の警告が加わると、演算の一致は束縛の同一性まで含むので、取り違えの余地が大きくなる。
- 修正案: 中心命題は変えずに、補助の定理を加える。例えば「警告の位置」の命題 `WarningLocated analyze` を、「`analyze Γ input b` の各警告 w について、`numbered input.key input.source` に `w.key` の出現 e があり、e の構文から決まる対象演算が `w.operation` と一致する」と定義する。構文から対象演算を決める関数（例: `.binary op (.base .integer) _ _` で op が対象なら `some (.binary op (.base .integer))`）は、評価規則と同じ集合にする。`analyzeBase` について、`base_warning_bounds` を強めてこれを証明する。C1・C2 以降の解析もこの命題を保つことを各区切りのレビューの観点に加え、X02 の比較では警告の演算の種類も照合する。

### 中3 標準束縛の同定が具体環境の欄にあり、解析から見えないため、案I の正常値の健全性が現在の形では成り立たない（読めば確定。L18 以降への申し送り）

- 場所: `Eval.lean` の `ConcreteEnv`（219行。`standards`・`apiAt`）と `UnknownAt`。`Environment.lean` の `Models`（42行。「標準束縛表を制限せず」）。`NormalSoundness` の解析関数の型 `AbstractEnv → EvalInput → Budget → AnalysisResult`。
- 問題: 呼び出しが Range などの標準束縛かどうかは、具体環境の `apiAt` と `standards` で決まる。しかし `Models` はこの二欄を制限せず、解析関数は抽象環境・入力・予算しか受け取らないので、解析は同定の結果を知る手段を持たない。C0 では同定済み API に規則がなく、未同定なら未知として扱うので、問題は表に出ない。案I で解析が `Range.value` の結果に `[lo, hi]` を与えると、局所値が同じで `apiAt := fun _ => none` の具体環境では、同じ呼び出しが `unknownNormal` により任意の Integer64 を返す。この環境でも `Models` は成り立つので、`NormalSoundness` は top 以外の区間を許さない。つまり、現在の `Models` と解析の入力の形のままでは、L18〜L20 の正常値の健全性は証明できない。直すには `Models` を強めるか、同定を評価と解析が共有する引数に移す必要がある。これは D15 の停止条件（中心定理の前提の変更）や、D18 の「profile の追加で中心定理の前提を増やさない」に触れる可能性がある。案III の W0404 の警告は、`.standard binding` の一致を `Reached` が要求するので空虚に成立するだけで、偽にはならない。影響を受けるのは主に案I である。
- 修正案: L18 の着手前、できれば C1 の閉鎖までに、次のどちらかを設計者に確認して `decisions.md` に記録する。
  - (a) 抽象環境を、局所位置の列・標準束縛表・出現の同定表を持つ構造体にし、`Models` に「具体環境の `standards`・`apiAt` が抽象環境のものと等しい」を加える。中心命題の文面は変わらない。ただし、同定の一致を前提に加えることになるので、それが D18 の禁じる「前提の追加」（標準 API の挙動や δ との一致の仮定）に当たらないことを明記する。
  - (b) `standards`・`apiAt` を `ConcreteEnv` から外し、`EvalPartial` と解析の両方が受け取る固定の引数（標準束縛の文脈）にする。同じ表を構成上共有できるが、`EvalPartial` の引数が増えるので、中心命題の文面の変更になる。
  - 推すのは (a) である。文面を保ち、同定を名前の字面ではなく解決済みの表で行う契約（契約表「標準呼び出し」）とも合う。

### 軽3 mayFail の性質を述べる定理がない（読めば確定。成り立つかは未確認）

## 確かめて正しかった主な事実

- 中心命題: `NormalSoundness`・`WarningSoundness`・`Reached`・`AnalysisResult`・`IntervalWarning`・`WarningCause.toFailure` の定義本文は、L02（`f635f26d`）と同じである。変わったのは `EvalPartial` の定義（L07c・L07d、計画の変更で承認済み）と、`Models`・解析関数の具体化だけである。
- 空虚さの抜け道: 二定理は任意の抽象・具体環境と任意の fuel を量化する。fuel 0 だけで成り立つ形ではなく、`Sound.lean` の独立例は fuel 16 で警告を出す解析を確かめる。`Models` は `LocalsModels` による長さと位置の対応であり、空の環境などで満たせる。

- 警告の原因: 加算の警告は `addAlwaysOverflows`（正常な二引数がすべて値域外）のときだけ `overflow` を出す。除数0の警告は `IntegerDivisionOp` と一点0のときだけ `zeroDivisor` を出す。`min64 intDiv -1` は `overflow` で拒否されるので、そこに除数0の警告を付けると結論を満たさない。
- 言語の意味との対応: 加算はあふれを失敗とする。`intDiv` は `Int.tdiv`（0 方向）、`mod` は `Int.tmod`（左辺と同符号か0）で、除数0を先に拒否し、`min64 mod -1 = 0` が成功する。これは 01-04「整数」の表と【決定】（74〜77行）に一致する。左から右の評価、子の失敗・return の伝播、if の選んだ枝だけの評価、bind・shadow の新しい先頭位置、return の正常値だけを `returned` に変える規則は、01-08「評価順序」と 01-12 の写しに一致する。短絡・match は規則がなく、C1 の範囲として明記されている。
