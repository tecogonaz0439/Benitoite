# RV-C4 への対応

2026-10-26、取りまとめ。判定は条件付き受け入れ（重大1・中2・軽5）。重大1 は設計者が決め、Lean の作業 L25R で A19 の前に閉じる。中1 は計画の変更と L25R、中2 と軽1〜軽5 は D15 の追記・計画の変更・L25R で閉じる。

## 重大1 の再現

取りまとめは、レビューが求めた再現を 39768486 の処理系（`target/debug/benitoite`）で行った。次のスクリプトは `check` が終了状態 0、`run` が `handled 300` を出して終了状態 0 で終わる。ハンドラが処理した `Process.exit(300)` は停止しない。

```benitoite
import Benitoite.Unofficial.IO.Console
import Benitoite.Unofficial.IO.Process
function finish() -> Integer uses Process.Exit
  return Process.exit(300)
end function
function main() -> Unit uses Console.Write
  bind code <- handle finish() with
    case Process.exit(c) -> c
  end handle
  Console.writeLine("handled ${Integer.toString(code)}")
end function
```

## 重大1 の原因

区間解析の対象構文の評価関係は、標準の call に組み込みの既定の実装の振る舞いを規則として付け、`handle` は外の事実を持ち込まない解析の境界として扱うだけだった。案I の Range の API は純粋な関数なので、この作り方で問題はなかった。案III で操作を対象に加えたとき、study・D4・D18・計画は操作と純粋な関数を区別せず、計画のレビュー（RV-P1）と取りまとめの点検も気付かなかった。Lean の定理は評価関係に対して成り立ち、評価関係と VM の一致は A1 の信頼の範囲として比較で確かめる約束だったが、X03c の比較範囲にもハンドラの下の呼び出しがなかった。そのため証明でも比較でも見つからない形だった。

## 設計者の選択

設計者は (b)（評価関係で操作にハンドラの結果を許す）を選んだ。取りまとめは、操作の W0404 の健全性が示せなくなり W0404 がシフトだけになること、HTTP の欄の追跡が警告に使われなくなることを示した。設計者は続けて、W0404 をシフトだけにし、欄の追跡を除く案を選んだ（decisions.md の「D4 の変更」）。main の本体の handle の外の呼び出しに警告を残す改善は、docs/todo に加える。
