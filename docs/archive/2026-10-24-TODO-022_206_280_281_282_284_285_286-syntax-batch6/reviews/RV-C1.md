### 中1 未知の部分木の内側を名乗る警告は、中心命題と WarningLocated の下で空虚に健全になる（読めば確定）

- 場所: `Eval.lean` の `EvalPartial.unknownNormal`・`unknownFailed`（356〜360行）と `Reached`（1073行）。`Sound.lean` の `targetOperationAt`・`WarningLocated`（1056〜1077行）。
- 問題: 未知の規則は子を評価せず trace を空にする。trace のキーは出現の位置ごとに一意である（`eval_trace_keys`）。したがって、未知の構成子（`call`・`list`・`interpolation`・`pipe`・`tryResult`・`withE`・`handleE` など）の部分木の内側にあるキー k には、根の入力のどの導出でも事象が現れない。その位置を名乗る警告は `Reached` を満たす事象を持たないので、`WarningSoundness` を空虚に満たす。`WarningLocated` も、k の構文が `intDiv` などの対象演算でありさえすれば成り立つ。例えば「呼び出しの引数の中のすべての `intDiv` に除数0の警告を出す」解析は、現在の二命題と `WarningLocated` をすべて満たす。現在の Lean の解析はそうした警告を出さない（`skip_silent` が skip 群は警告を加えないことを示す）。しかし、それは実装の性質であり、評価関係に対する言明としては述べていない。Rust の側で精度を上げるつもりで未知の部分木の内側を解析すると、言明の上では区別できない誤った警告になる。RV-C0 の中2 と同じ種類の抜けが、「位置」の代わりに「評価される領域」について残っている。
- 修正案: 中心命題は変えずに、補助の定理を一つ加える。構文から「具体規則で評価されうる位置」の集合を定義する。根から当該の出現までの祖先がすべて具体規則を持つ形（現 profile では base・flow の構成子。match の腕は整数の照合値の可能性があるので含める）である位置とする。各警告のキーがその集合に属すことを `analyze` について示す（`skip_silent` と `analysis_located` の組み合わせで足りる見込み）。X02 の比較と A07 の受け入れに「未知の部分木の内側に新しい警告を出さない」を加える。中5 の案 (b) を採る場合は、別の入力として解析した部分木の警告を、その入力について同じ定理で扱う。

### 中2 処理系が使う本体の入口 analyzeBody に定理がなく、独立例は本体の最初の式を番号0にして L26 の約束と食い違う（読めば確定）

- 場所: `BudgetAnalyze.lean` の `analyzeBody`（248行）。`BudgetAnalysisExamples.lean` 134〜157行（`key = ⟨"Example.budget", 0⟩` を渡し、本体の最初の除算の警告を番号0とする）。`Examples.lean` 123行（`analyzeBody … (key 0) …`）。`Identity.lean` の `bodyRoot`・`bodyRootKey`・`bodyContentKey`。01-12「区間解析の本体の識別と元の出現の対応」と「区間解析の予算付きの式とフロー」。
- 問題: 三つの中心的な定理は式の入口 `analyze`（`analyzeExpr`）について述べる。契約表「呼ぶ位置と共有状態」が想定する本体ごとの解析は、Lean では `analyzeBody` に当たる。`analyzeBody` は、全体上限の事前判定、`forgetEnv` の計上、Block の解析という別の手順を踏み、根の block 式を `identify` しない。これについて正常値・警告・位置の系は証明されていない。07-04 の最後の段落（「この接続に対する任意の予算での正常値・警告の中心二定理と WarningLocated は前段落までのとおり」）は、`analyzeBody` も含むと読める。

  加えて、L26 は「根の block 式が番号0、内容は番号1から」と定めた。しかし `analyzeBody` は渡された key から Block の最初の式を数えるので、独立例のように `(定義名, 0)` を渡すと最初の式が番号0になる。根の block 式に番号を付ける `analyze`（`bodyRootKey` を渡す）と、渡さない `analyzeBody` では、同じ本体の番号が一つずれ、操作数も根の一訪問の分だけ異なる。A01・A02 の担当は、どちらの入口と番号を写すかを文書から一意に決められない。X01・X02 で番号の対応表と消費を照合すると、この選択の違いはすべて不一致になる。
- 修正案: 本体の入口を一つに固定する。推すのは、`analyzeBody` を「`forgetEnv` の計上の後に、`bodyRoot body` を `bodyRootKey definition` から式の入口で解析する」形に改めることである。こうすれば中心定理の `analyze` と番号の約束が一致する。Block から始める形を残すなら、引数を定義名にして `bodyContentKey` から始め、根の番号0の扱いを 01-12 に書く。どちらの場合も、`Models seed.initial ρ`（または `Models (forget seed.initial) ρ`）と `EvalBlock`・`EvalPartial` の導出から、正常値の所属・警告原因どおりの拒否・WarningLocated を結論する系を置く（`block_normal`・`block_causal`・`block_located` と `forgetEnv` の `_agrees` から短く導ける見込み）。独立例の key を新しい約束へ直し、07-04 の該当段落を、どの入口に定理があるかが分かる文へ直す。

### 中3 検査全体の駆動、別本体の予算付きの発見、深さ fuel の選び方が Lean に定義されていない（読めば確定）

- 場所: `BudgetAnalyze.lean` の `analyzeBody`・`Parameters.fuel`。`BudgetWalk.lean` の `Halt.depth`。`Analyze.lean` の `discoverBodies`・`functionBodies`（予算を計上しない走査）。`Identity.lean` の `bodyManifest`（数学的な指定）。plan.md の契約表「呼ぶ位置と共有状態」「予算の交換」「比較報告」、D16「読み込み済みモジュールのソース順で処理し、同じ入力と予算では同じ位置で退く」。
- 問題: 全体の予算は本体をまたいで共有するので、本体を解析する順序が、どの本体が全体上限で止まるか、どの警告が残るかを決める。Lean には、モジュール・定義・別本体（ラムダ・lazy・節・定数）をどの順に `analyzeBody` へ渡すかの定義がない。別本体の初期環境 `BodySeed` を作る `discoverBodies` は予算を計上しない全走査である。01-12 は「本体の列を予算外で先に発見する入口は定義しない」「別本体自身の番号付けも同じ規則を使い、全体の予算消費を引き継ぐ」と書くが、それを満たす予算付きの発見の手続きは Lean にない。

  深さ fuel も同じ問題を持つ。`analyze` は fuel を `Parameters` に取り、不足すれば `Halt.depth` で止まる。Rust の処理系に同じ深さの打ち切りはない見込みであり、契約表「比較報告」の分類（型検査成功・未対応・本体予算超過・全体予算超過・番号未取得）にも深さの停止はない。十分な fuel なら深さで止まらないこと（例えば fuel が部分木の大きさの定数倍以上なら `Halt.depth` にならないこと）は証明されていない。このままでは、X02 の比較で Lean の側の fuel をどう選ぶかが決まらない。
- 修正案: L28 または A02 の前に次を決め、契約表と 01-12 に書く。(1) 検査全体の本体の順序（例: モジュールのソース順、定義の順、親の本体を終えた後に別本体を先行順・節の順で処理する）。(2) 別本体の発見と初期環境の構築の計上（`analyzeBody` に渡す前の予算付きの走査を定義するか、親の解析の走査で seed を同時に得る）。(3) fuel の扱い。交換の入力で fuel を `2 * surfaceSize + c` などの式で固定し、その値で `Halt.depth` が起きないことを補題で示すのが簡単である。補題を置かない場合は、比較報告に深さの停止を別の件数として加え、Rust との一致の対象から外す。

### 中4 定数の埋め込み本体を、親での解析と別本体の両方で解析し、同じ元の出現の警告候補が重複する。重複抑制の契約がない（読めば確定。利用者に見える重複は A07 の実装次第で、実行しないと分からない）

- 場所: `BudgetAnalyze.lean` の `expr` の `.constE _ child => expr fuel (clearLocals env) child`。`Analyze.lean` の `discoverBodies` の `.constE`（`startBody .constant [] (clearLocals env) (.last expr)`）。`Identity.lean` の `embeddedBodies` の `.constE`。`Surface/Syntax.lean` の `constE` の注釈（「本体の中の定数参照も埋め込んだ有限の木」）。plan.md の A07（「旧const警告の元NodeId/原因を使って候補を重複抑制」）。
- 問題: 定数の参照は、その位置に定数の本体の木を埋め込んだ `constE` になる（P5）。この本体は二回解析される。一回目は、それを囲む本体の解析の中で、親の番号のまま局所位置を空にして解析される。二回目は、`embeddedBodies`・`discoverBodies` が作る別本体 `…%body:n:0` として解析される。局所位置はどちらも空なので、結果も警告も同じになり、キーだけが異なる。どちらのキーも、元の AST では定数の宣言の中の同じ NodeId に対応する（多対一）。定数を k か所で参照すれば、同じ元の演算に 2k 件の候補が生じ、定数の宣言そのものの解析の候補もこれに加わりうる。A07 の重複抑制は旧定数警告との組だけを定めており、新しい候補どうしが同じ NodeId と原因を持つ場合の扱いを定めていない。

  予算にも同じ影響がある。参照ごとに本体の木全体を番号付けし、二回解析する。定数の本体がさらに定数を参照すると、展開した木の大きさは参照の連鎖に沿って指数的に増えうる。その場合、本体の番号付けは予算で止まり、番号未取得になる。
- 修正案: A01 の前に次の二点を決める。(1) 定数の本体を別本体として列挙するのをやめる。局所位置を空にした親の中の解析と同じ結果になるからである。または、親の中では `constE` を skip して別本体だけで解析する。(2) 利用者に出す警告は、元の NodeId・原因・一次位置の組で一件にまとめることを契約表「警告」に加える。X02 の比較は、キー単位の候補の列と、まとめた後の利用者の警告の両方を照合する。展開の大きさによる番号未取得は、U01 の棚卸しで既存の入力の最大の展開の大きさを測って確かめる。

### 中5 未同定の呼び出しの引数・補間・リスト・レコード・パイプ・try のオペランド・with の本体・handle の保護された本体を一切解析しない帰結が、限界として書かれていない（読めば確定。設計者の確認を推す）

- 場所: `Eval.lean` の `Unmodeled`（`.call ..` などを常に真とする）と `UnknownAt`。`BudgetAnalyze.lean` の `expr` の既定の場合（`skipChildren` の後に `unsupported`）。`Analyze.lean` の `discoverBodies`（with・handle の保護された本体・try を別本体にしない）。01-12「区間解析の対象構文の評価関係」の「境界を囲む本体から子へ整数の事実を伝えない」。plan.md の「Surfaceの全構成子の分類」。
- 問題: 未知の形の子は、外の事実を持ち込まない形でも解析されない。親の解析では skip し、別本体にもならないからである。その結果、次の位置では、局所の事実が完全に分かっていても新しい W0401・W0402 は出ない。

  - 局所束縛 `z = 0` の後の、呼び出しの引数の中の `10 div z`。
  - 補間の式の部分の、最大値への加算。
  - リストの要素の `a div 0`。
  - with の本体や handle の保護された本体の中の `1 div 0`。外の環境を Top に忘れても、本体の内側だけで一点0と分かる。

  最後の例のように、外の事実を持ち込まなくても、部分木の内側だけで分かる事実は多い。D8 の「関数の境界を越えない」は関数本体へ入らないことを指し、引数の式を解析しないことまでは述べていない。01-12 の上の一文は「子を外の事実なしで解析する」とも読める。plan.md の分類表は「内部へ事実を持ち込まない」と書いており、内部を解析しないことと区別していない。後から方針を変えると、中心命題は変わらないものの、Rust の A01〜A12 の実装・独立交換の期待値・U01 の棚卸しをやり直すことになる。
- 修正案: A01 の前に設計者が次のどちらかを選ぶ。
  - (a) 現在の範囲を保つ。01-12・07-04・02-05 と利用者向けの説明に、上記の位置では新しい警告を出さないことを限界として明記する。D8 にもその旨を加える。
  - (b) 未知の形の直接の子のうち評価順が定まる式（呼び出しの頭と引数、補間・リスト・レコードの要素、パイプの両辺、try のオペランド、with の束縛式）と、with の本体・handle の保護された本体を、外の局所位置を `forget` した環境と元のキーで、独立した入力として解析する。中心定理は任意の入力・`Models` について成り立つので、ラムダの本体と同じ条件付きの保証がそのまま得られる。評価関係の変更は要らない。予算の計上と番号の消費は、skip の代わりにその解析を使う形で定める。中1 の補助定理は、この独立した入力ごとに述べる。

  推すのは (b) である。費用が小さく、利用者に届く警告の範囲が大きく変わるからである。どちらを選んでも、その選択を decisions.md に記録する。

### 軽1 番号未取得の意味が「停止した操作が番号付けの操作だった」であることが書かれていない（読めば確定）

- 場所: 01-12「区間解析の本体の識別と元の出現の対応」の「番号の計上・保存・走査枠の確保が予算を超えたら、原因を残した unidentified として停止し」。`BudgetAnalyze.lean` の `expr`（`scope` の作業枠と `tick .expression` は `numbering` の外）。`BudgetAnalysisExamples.lean` 40〜46行。
- 問題: `expr` は作業枠の確保と式の計上で止まると `exceeded`、`identify` の計上と保存で止まると `unidentified` を返す。どちらの場合も、その出現と後続の番号は取得されない。例えば保持の上限が0なら `exceeded`、1なら `unidentified` になる。上の一文は、番号が取れなかったときは常に unidentified であるかのように読める。契約表の `unidentifiedBodies` と `bodyBudgetExceeded` の件数は、この細かな区別に依存する。
- 修正案: 01-12 と契約表「比較報告」に、unidentified は「上限を超えた操作が番号付けの操作（identify の計上・保存、skip の走査枠・分類）だった」ことを表し、番号が取れなかった本体の全体ではないことを書く。A11 と X02 で同じ分類を照合する。

### 軽3 ConcreteValue.other は不透明型やデータ型を除外しないので、Range の値に二つの表現がある（申し送り）
