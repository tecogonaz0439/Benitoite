## B. 価値の評価

- **V1（重）1 節・4.2 節・12.2 節: 利用者に見える効果の出どころが分解されていない。** 新しい警告は、オペランドが確実に失敗する区間に入ったときだけ出る。関数の引数・IO の結果・一般の呼び出しは Top なので、有限の区間の元はリテラル・const・局所の bind、`= k` とリテラルのパターンによる一点への絞り込み、定数との比較、Range の成功に限られる。Integer64 の加算が必ずあふれるのは下端の和が 2^63 を超えるときだけで、比較からこれが生じるのは作為的なコードに限られる。実際に効くのは、局所の bind の定数の伝播（`bind n <- 0` の後の `t div n`）と、等値の枝・リテラルの腕での除数 0（`if n = 0 then t div n`）であり、どちらも区間ではなく定数の伝播と一点の絞り込みで得られる。区間の上下端・合流・成功値の区間は、Integer64 では主に学習の価値である。修正案: 1 節と 12.2 節に、利用者に見える効果は主に局所の定数と一点の絞り込みから来ること、狭める案の価値は推す案とほぼ同じであることを書く。
- **V2（中）5 節・12.2 節: 同じ規模で価値の高い範囲の比較が不公平。** (a) 固定の定義域を持つ API の引数（シフト量 0〜63、`Process.exit` の code 0〜255、`Http.listen` の port、`Http.respond` の status 200〜599、`timeoutMilliseconds` 1 以上）は範囲外が実行時エラーになり、リテラルの引数なら既存の定数の評価器（checked_args の枠組み）で報告でき、区間と組み合わせれば局所の bind や比較の後にも届く。(b) 幅付きの整数の加算は Integer64 よりあふれが現実に起きやすく、領域を幅で引数にすれば追加の費用は小さい。12.2 節の「広げる案」は一括にしていて大きく見える。減算・単項の負号・定数倍は加算と同じ形の補題である。修正案: 「Range の要約の代わりに減算・負号・各幅を入れる」と「Range の要約の代わりに固定の定義域の API の引数を入れる」を、推す案と並べて評価する。
- **V3（中）8.3 節・Q7: Range の成功の要約について、本文の結論と推す案が食い違う。** 4.2 節は利用者に見える差がないと認めているのに、Q7 で A を推す。要約には標準束縛の同定、match の腕と成功値の束縛番号の対応、Lean の `Checked/Range.lean` と Range.bnt の本体の関係の仮定が加わる。Q7 は B を推すか、A の理由を学習の目的として明示する。
- **V4（軽）Q12**: 範囲は README で設計者が決めている。Q7 を B にすれば、試作の「API が使われる形を確かめる」条件はこの段の価値と無関係になる。Q12 を「価値の根拠を学習の目的と除数 0 の警告と書くことの確認」に言い換える。

## C. 形式化の見通し

- **F1（重）9.3 節・Q10: 健全性の定理が何の意味に対してなのかが決まっていない。** 今の `formal/` には Surface の評価器がなく、表層の意味は脱糖して Release の抽象機械で実行することで定まる（07-04 の 11 行。Surface/ に `eval`・`Step` はなく、Release/Semantics.lean の `Step`・`run` だけがある）。証明済みなのは脱糖の型の保存（性質 1）だけで、意味の保存はない。07-04 の 34 行は各幅の値域とあふれを証明の対象外とし、Release の Builtins の δ は抽象的である。9.3 節の `Surface/IntervalEval.lean` は新しい評価器を定義する案で、それと 01-12 の意味の一致は証明されない。一致まで証明するなら局所の位置を機械の状態へ対応させる模倣（simulation）の定理が要り、20〜40 時間に収まらない見込みである。修正案: Q10 を A1（Surface の部分の評価器に対する健全性。01-12 との一致は証明せず、VM との差分テストで確かめると明記する。今の見積もりの範囲）と A2（脱糖と Release の実行への接続まで証明する。再見積もりが要り大きい）に分け、A1 を推し、07-04 に保証の限界を書く条件を付ける。
- **F2（中）9.3 節: 「実 Surface の接続」の費用。** Surface の `Expr` は約 55 の構成子で、Exprs・HoleArgs・Block・Arms・Clauses と相互帰納である（Surface/Syntax.lean 300 行以降）。実ソースの全定義で解析を走らせるには、すべての構成子に規則と健全性の場合が要り、de Bruijn の番号もパターンの束縛・ハンドラ・ラムダの中でずらす必要がある。20〜40 時間の上側に寄る見込み。修正案: 未対応の構成子を一様な規則（Top、境界）で処理する補題を先に作ることと、個別の規則を対象の構文（局所の名前・リテラル・加算・比較・ite・elseIf・ifOnly・matchE・bind/shadow・and/or）に限ることを、計画の受け入れ条件にする。
- **F3（中）9.4 節・Q11: 式の識別の費用が見積もりに入っていない。** 今の交換の Surface（Exchange/Syntax.lean）には節の識別や位置がない。警告の位置と区間を比べるには識別を加えることになり、Rust の書き出し・Lean の読み取り・版の規則（Version.lean）の変更が要る。修正案: 木の先行順の番号（ソースの位置を持たない経路）で比べる案を第一にし、独立の形式にするか sidecar を上げるかの費用を比べ、どの見積もりに含めるかを書く。「全 Top だけの一致を完了としない」は妥当である。
- **F4（軽）公理と主定理**: 新しい解析を別の名前空間の定義と定理として置き、Ty・Eff・部分型を変えない限り、既存の性質 1〜3 と検査の健全性の言明を変えずに済むという主張は正しそうである。δ が具体的な演算に一致する条件を補題の引数として明示する方針も妥当である。

## D. 他の言語との比較

- Wuffs の assert が実行時の効果を持たず証明できなければコンパイルが失敗すること、Free Pascal の `{$R+}` が範囲外で終了状態 201 になること、GNATprove の「medium: overflow check might fail」と Ada の実行時検査が残ること、LLVM の ConstantRange が折り返す範囲を表すことは一致した。要約は全体に慎重で、誤りは E3 だけである。

## E. 問いの立て方

- **Q1（軽）**: Q5 は A⊂B⊂C の段階で、Q6 の C は A への追加である。段階として示すか、追加の可否の問いに分ける。
- **Q2（中）設計者が決めるべき点の漏れ**: (i) 健全性の基準の意味（F1）、(ii) W0401・W0402 を流用するか新しい W のコードにするか（01-04 の規範の文の変更を伴い、LLM が警告の出どころを説明するときに効く）、(iii) Range の要約の代わりに幅や定義域の API を入れるか（V2・V3）、(iv) 01-04 と 02-05 の不一致をこの改造で直すか。
- **Q3（軽）設計者が決めなくてよい細部**: Q4（無限の端）と Q8 の予算の数値は、実装プランの受け入れ条件で足りる。既定値として計画に書く。
- **Q4（軽）8.4 節: 全体の予算の性質**: 全体の予算にすると、無関係な関数を足しただけで別の関数の警告が消え、`--deny-warnings` の下では受理の可否が無関係なコードに左右される。本体ごとの予算と全体の上限の併用を併記する。明示の積み重ねで書く方針は AGENTS.md の規約（AST を辿る処理は再帰でよい）より強い指定なので、必須にするかを書き分ける。

## 実行しないと分からない点

- 新しい警告がリポジトリ全体で何件出るか（本文も未取得と書いている）。
- 実行時エラーを確かめるゴールデンテストの多くはリテラルを直接書く形である（`eval/int_overflow_add.bnt` など）。局所の bind で警告を避けている例があるかは実装後に照合が要る。
- 大きな入力での解析の時間と、O(N log B) の見込み。

## 総合の所見

- Integer64 での利用者の価値は、局所の定数と等値の絞り込みによる除数 0 の警告にほぼ限られる。閉区間の上下端と Range の要約は、学習の価値が主である。作業量は 74〜140 時間の見込みで、学習の目的を正面の根拠にするなら進める理由はあるが、本文はその内訳を示していない。
- 推す修正は三つである。(1) Q7 を B にして要約の費用を外す。(2) 空いた分で、減算・負号・幅付きの整数か、固定の定義域の API の引数を入れる（どちらも実際のクラッシュに近い対象である）。(3) 形式化の保証を「Surface の部分の評価器に対する健全性」と明記する。これで同じ費用の帯で利用者の価値が上がり、保証の範囲も誤解なく示せる。
