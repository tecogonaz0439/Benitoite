# 整数の区間の局所解析の調べと判断の案

2026-10-24、S1。RV-S1 に対する修正 S1R を同日に反映した。調査の基準は `6ecc9996747db03801004ebee6c38a5283b590a7`（v0.0.11）である。[改造の README](../README.md)の決定を前提とする。以下の「推す案」は設計者の未回答の案であり、現在の保証を述べる箇所と区別する。問いの短い一覧は [interval-analysis-questions.md](interval-analysis-questions.md) に置く。

## 1. 推す範囲と、価値の出どころ

範囲は、第12.1節の案 II（Range の成功要約を外し、加算・減算・単項の負号・定数倍と幅付き整数を扱う）を推す。新しい構文・公開部分型・関数型への篩を加えず、本体ごとに閉区間を求める。確実な除数0とあふれは警告にし、実行時検査は全て残す。警告コードは W0401・W0402 の流用を推すが、報告水準とコードの選択は別の判断として Q3 に示す。README の中心である加算と定数比較による局所解析を保ち、幅と演算の追加は Q1 への回答を得てから計画へ入れる。

利用者に見える効果を、情報を得る方法ごとに分ける。下の断片は、その演算に到達してオペランドの評価が正常に終わった場合の診断候補である。プログラム全体の失敗や到達を予言するものではない。

| 情報を得る方法 | コード片 | 追加できる報告と、区間の上下端が要るか |
|---|---|---|
| 局所の定数伝播 | `bind n <- 0` の後の `t div n` | 除数0。一点の定数だけで足りる。`bind x <- 9223372036854775807` の後の `x + 1` も同じ種類である |
| 一点への絞り込み | `if n = 0 then` の枝の `t div n`、Integer の `case 0 ->` の腕 | 除数0。等値とリテラルのパターンだけで足り、一般の上下端は要らない |
| 複数の値を含む区間の上下端 | `n: Integer8` に対し `if n > 100s8 then` の枝の `n + 100s8` | `[101,127] + [100,100]` の全域が127を超えるのであふれ。未知の n を一点に定めずに報告できる。幅付き整数を入れる案 II の追加価値である |
| 合流した区間 | `bind n <- if flag then 100s8 else 110s8 end if` の後の `n + 100s8` | 合流した `[100,110]` からあふれ。単一の定数伝播では得られない。到達しない枝の結果は合流しない |
| 固定の定義域との不交差 | `if n > 63 then` の枝の `Integer.shiftLeft(a: 1, n: n)` | n が一点でなくても、全域がシフト量の定義域外と分かる。案 III の追加価値であり、案 II の対象には入れない |
| Range の成功から得た区間 | 第4.2節の `Range.value(checked) + 1` | `[1,65535]` を得ても、その例に追加の警告はない。元の案 I で成功要約を入れる主な理由は学習である |

元の案 I で利用者が出会う追加警告は、主に最初の二行から来る。Integer64 の加算が区間の全域であふれるには、正側なら下端どうしの和が最大値を超えなければならない。一般の関数の引数・IO の結果・通常呼び出しを Top（型の全値域）から始める本案では、64ビットの端近くを比較する例の使用頻度を裏付ける実績はない。定数伝播と一点への絞り込みだけに狭めても、案 I の診断の価値の多くは得られる。閉区間・合流・Range の成功要約が加える価値は、案 I では主に抽象解釈の学習にある。

案 II は、小さい幅でのあふれと符号なし減算の下限違反を、同じ区間の仕組みで扱う。使用頻度や LLM の修正成功率の改善は未測定であり、例から実用効果の大きさまでは断定しない。第12節では、診断例を増やす価値と、区間の健全性・幅による共通化を学ぶ価値を採用理由とする。Range の利用評価を、この段の実装の前提にはしない。

### 2.2 整数・失敗・既存の警告

01-04 は `Integer` / `Integer64` を符号付き64ビット、値域を −2^63〜2^63−1 と定める。この値域はホストのポインタ幅で変わらない、と本書では解釈する（01-04の直接の文言と、この帰結を区別する）。数学的な和が値域を超える加算は折り返さず実行時エラーになる。`Integer8`・`Integer16`・`Integer32` と `UnsignedInteger16`・`UnsignedInteger32`・`UnsignedInteger64` にも検査付きの算術がある。正確な型名は `src/types/builtin.rs:232–264,299–332` の登録表でも確認した。`UInteger16` 等という型名はない。`Byte` は0〜255だが算術演算子を持たない。異なる幅を暗黙に混ぜない（[01-04「型の一覧」「Integer」](../../../design/01-spec/01-04-types-basic.md)）。

実装では [typeck/consts.rs](../../../../crates/benitoite/src/typeck/consts.rs) の `binary`（735行以降）が定数の整数演算を、[base/prim/numeric.rs](../../../../crates/benitoite/src/base/prim/numeric.rs) の `integer_binary` が幅付きの整数六種を検査する。実行時の通常の整数演算は [builtins/funcs/operators.rs](../../../../crates/benitoite/src/builtins/funcs/operators.rs)、幅付きは同ディレクトリの `operators/signed.rs`・`unsigned.rs`、整数の標準関数は [integer.rs](../../../../crates/benitoite/src/builtins/funcs/integer.rs) にある。Range の検査はこれらの算術を変更しない。

`div` は0方向への商、`mod` はその商による数学的な剰余である。除数0はともに実行時エラー、最小値 `div -1` はあふれ、最小値 `mod -1` は0である。`floorDivide` / `floorModulo` は負の無限大方向の商を使い、同じ零と最小値の区別を保つ。区間の式を `a - (a div b) * b` に展開すると途中のあふれを誤って持ち込むので、剰余の定義と実装を直接扱う必要がある。

通常の本体の定数演算の失敗は W0401（除数0）・W0402（あふれ）、const の計算の失敗は E0435 である。現在は局所 bind の値を伝播しない。警告は実行を止めず、`--deny-warnings` が指定されたときは拒否される（[02-05「警告」](../../../design/02-impl/02-05-typechecker.md#警告)、[diag/codes.rs](../../../../crates/benitoite/src/diag/codes.rs) 1296行付近、[02-10 の JSON の severity](../../../design/02-impl/02-10-diagnostics.md)）。

**今回の点検で、現行文書内の不一致も一件見つかった。** 01-04 の前提（22行付近）は「幅付きの整数の標準関数の呼び出しには、この算術の警告は適用しない」とするが、02-05「警告」と実装は `absolute`・`floorDivide`・`floorModulo` の直接呼び出しを含める。`Integer8.absolute(-128s8)` の実機確認でも W0402 が出た。0.0.10 の [decisions.md「R10 整数モジュールの警告の範囲と扱い」](../../2026-10-19-TODO-022_032_087_168_191_192_200_206_222_226_227_229_246_248_253-syntax-batch4/decisions.md)とも後者が一致する。この改造で、01-04 を現行の実装・02-05 に合わせて直す案を Q4 に示す。これは新しい局所解析の拡張とは別の、現行契約の記述の訂正である。本作業では現行の設計書を変更していない。

### 2.3 補助解析を置く段

| 段 | 現在の処理と、追加するときの境界 |
|---|---|
| 読み込み・構文・名前解決 | [pipeline.rs](../../../../crates/benitoite/src/pipeline.rs) の `check_stages_counted`（285行以降）。名前の文字列だけで標準関数を認定しない |
| 本体の制約生成・解決 | [typeck/generate.rs](../../../../crates/benitoite/src/typeck/generate.rs) 112〜164行。`solve`、型の上限、到達性の検査を終える |
| 既存の警告 | 同153行付近で `consts::warnings`、その後156行で `ctx.finish()`。型や名前の誤りがある本体を追加評価しない。標準ソース内の算術警告は `consts.rs:1167` の入口で省く |
| 定数引数の追加検査 | 同162行付近で `checked_args::check`。[checked_args.rs](../../../../crates/benitoite/src/typeck/checked_args.rs) 73〜137行は CallPlan の直接呼び出しと標準束縛を同定し、契約名から引数を得る |
| 脱糖 | `pipeline::desugar_checked`。以降でソースの bind・if を再構成する案は採らない |

推す差し込み位置は、`consts::warnings` と同じ `valid` の条件の下、`ctx.finish()` より前である。加算が Integer・幅付き整数か、Decimal や String の連結かを、`ctx.operand_types` の推論型を `ctx.solver.finalize` して区別する。これは `consts::warnings`（1189行付近）が既に使う型の取り方であり、型表の所在を実装時まで未定にしない。既存警告と新解析は同じ `(Rustの式ID, 診断コード)` で重複を抑える。

`checked_args::check` は `finish` の後に `d.out.call_plans` を使う別の入口である。`context.rs:584–608` の `finish` は E0208 があると表を写す前に戻るので、解析のために後段の表へ依存する案は第一案にしない。案 I の Range、案 III の定義域 API の直接呼び出しを同定するときは、`consts::std_call`（178〜186行）の解決済み束縛の照合と `standard_argument`（591行以降）を使う。CallPlan を要求せず、穴・パイプ・関数値を対象外にする。案 II は通常演算の型と束縛の番号を主に使う。解析結果を型推論へ戻さず、型の誤りによる回復値を整数定数として評価しない。

E0457・E0458 は Regex の定数の構文不良・組み立て資源制限、E0459〜E0462 は Scope の形式・対象・端点/port・所属の不良を拒否する。import の別名は対象、局所関数値・穴・パイプ・高階・利用者のラッパーは対象外である。追加取得の64 MiBの予算超過は Unknown であり、RegexBuilder 自身が返す E0458 と同じ意味ではない（`checked_args.rs:14–68`、`consts.rs:284–345,456`、01-06 の203〜209行付近）。

この先例から利用するのは、標準束縛の同定、引数の対応、誤りのある本体の抑制、予算、由来の表示である。Range の Result.Error を E0462 に読み替えたり、局所の区間を既存の Scope/Regex の「定数式」に加えたりする案は採らない。それは既存の拒否範囲を別途広げる変更になる。

### 4.2 利用形と価値の確かめ方

典型例の候補は、設定の数値を読む→`Range.checkInteger(minimum: 0, maximum: 65535, value: port)`→成功値を使う、または入力の件数を確かめてから処理する形である。前者ではポートの妥当性と IO の成功・権限は別である。後者では現在の `List.get` はすでに Option を返すため、CheckedIndex の価値は検査後の読み出しが T を返し、対象の取り違えを API の形で防げる点にある。

元の案 I の局所解析で試す例は、成功枝で `Range.value(checked)` に1を足して別の Range 検査へ渡す処理である。例えば `[0,9]` の成功値なら加算結果は `[1,10]` と分かる。これは実行時の分岐の削除には使わず、後の失敗の診断に使う。入出力の多い実際のスクリプトでこの診断に出会う頻度は未確認である。

利用形の案は次のとおりである。これは次の空きポートを保証する関数ではなく、候補番号を一つ進めて定義域を確かめる通常の関数である。

```benitoite
import Benitoite.Unofficial.Range

function nextPortCandidate(port: Integer) -> Result[Range.CheckedInteger, Range.RangeError]
  match Range.checkInteger(minimum: 0, maximum: 65534, value: port) with
    case Result.Ok(checked) ->
      bind next <- Range.value(checked) + 1
      return Range.checkInteger(minimum: 1, maximum: 65535, value: next)
    case Result.Error(error) -> return Result.Error(error)
  end match
end function
```

この例では解析が得る `[1,65535]` は内部情報であり、成功の通知も検査除去も行わないので、そのままでは利用者に見える差はない。最後のmaximumを小さく変えても、RangeのErrorは正常な値なので本案は警告しない。得られる差を算術失敗の診断に限定すると、この例は Range 成功の要約を採る根拠にならない。そのため推す案 II では要約を外す。案 I を選ぶなら、標準束縛の同定・成功値と束縛番号の対応・Range.bnt と小モデルの関係を学ぶ費用として選ぶことになる（第8.3節・第12.1節）。

Range 自体の価値を別途確かめる Skill 評価の案は、(a) 設定のポートと既定値、(b) 上端付近の連番の加算、(c) 件数の上限と対象付き添字の三課題を固定し、正常入力・境界・不正入力の期待結果を用意することである。構文/型検査の通過、期待結果、警告から修正を終えるまでの回数、不要な型注釈やラッパーの増加、利用者への失敗理由の説明を比較する。範囲を静的に証明できなかったコードを LLM が不必要に書き換えないかも見る。成功率への影響は仮説であり、今回は LLM 評価を実行していない。評価の実施と回数は別途設計者の了承を得る。案 II の採否や受け入れの条件にはしない。

## 5. 対象にできる失敗の候補

大きさは本体の区間解析ができた後に必要な追加量を小・中・大で表す。小は既知の引数の区間と固定範囲の比較、中は API の意味・成功枝の情報・交換を加えるもの、大は変数間の関係や状態を追うものを指す。単なる None/Error を異常終了と数えない。

### 5.1 案 III の固定定義域の候補と実装の境界

次の値域は設計書とソースの双方で確認した。単に区間と定義域の交差が空かを調べる部分と、API の引数やレコード欄を得る部分を分けて費用に数える。リテラルだけでも、現在の `checked_args` と同様の標準束縛と引数の取得の枠組みで報告する実装を足せる。ただし現行 `checked_args` が下表を既に診断するわけではない。

| API と検査する値 | 正常な定義域 | 設計書と実装の根拠 | 案 III の対象にする形と追加費用 |
|---|---|---|---|
| `Integer.shiftLeft`・`shiftRight`・`shiftRightUnsigned` の n | `[0,63]` | 01-04「ビット演算」、`builtins/funcs/integer.rs:134–187` | 直接呼び出しの n を読む。左シフトの捨てるビットはあふれの警告にしない |
| 幅付き整数と Byte のシフトの n | 幅 w なら `[0,w−1]`。Byte は `[0,7]` | 01-04同節、`width_bits.rs:49–157`・`byte.rs:68–82` | 入力値の型が幅付きでもシフト量の型は Integer。固定の契約表を幅で共通化する |
| `Process.exit` の code | `[0,255]` | 03-07「Process」248行、`process.rs:41–52` の `u8::try_from` | 直接呼び出しの code を読む。範囲内でも正常に呼び出し元へ戻るとはしない |
| `Http.listen` の port | `[0,65535]`。0は OS が選ぶ | 03-09「Http」95行、`http_server.rs:18` の `u16::try_from` | 名前付きの直接引数。使用可能なモジュールを追加ロードしない |
| `Http.respond` の `Response.status` | `[200,599]` | 03-09同節97行、`http_server.rs:99–104` | 引数は status 自体ではなく Response レコード。直接のレコード構築・局所束縛・明示した欄の更新だけを追う規則が追加で要る |
| `Http.request` へ渡す `ClientRequest.timeoutMilliseconds` | `[1,max64]`。2^40を超える値は上限へ丸め、定義域外にはしない | 03-09「クライアント」200行付近、`http_client.rs:151–163` の `< 1`、同ファイル19・194行の時間制限の上限の扱い | ClientRequest の明示した欄と更新を追う。一般関数から返るレコードや任意の射影は未知とする。組み込みの失敗条件は他にもあり、全入力の成功とは結論しない |

例えば `bind code <- 300` の後の `Process.exit(code)` は局所の定数伝播、`if code = 300 then` の枝も一点の絞り込みで足りる。`if code > 255 then` の枝の `Process.exit(code)` は、複数値の区間と定義域の不交差を使う追加価値である。`bind response <- Http.Response(status: status, headers: [], body: body)` の status を追うには、整数だけの環境に加えてレコード欄の対応が要る。案 III の見積もりは下表の全候補を含み、HTTP の二つの欄を費用から落とさない。

案 III を選んでも、定義域外は新しい警告コードで報告し、実行時エラーを残す案とする。既存の E0457〜E0462 を局所値へ広げず、Result.Error・Option.None も警告しない。案 II と III の比較に、既存コードの新しい通常拒否を紛れ込ませない。

| LLVM [ConstantRange](https://llvm.org/doxygen/classllvm_1_1ConstantRange.html)、[LazyValueInfo](https://llvm.org/doxygen/classllvm_1_1LazyValueInfo.html) | 固定幅の範囲、辺・使用位置での値情報、交差・合流・演算のAPI。これらはSMT問い合わせのAPIではない | 主に最適化用の内部情報であり、利用者へ数値契約のエラーを出す仕組みとは異なる | ホスト独立の幅・使用位置ごとの情報を参考にする。LLVM の折り返す範囲表現を、折り返さない Benitoite の算術へそのまま移さない |

これらの言語の規則から Benitoite での LLM 成功率の順位は導けない。新構文を増やさないことと、未知を拒否しないことは修正の負担を抑える仮説である。非プログラマ向けには、「この分岐では値は0なので割れない」「ここで1を足すと上限を超える」という具体的な理由をLLMが説明できる診断を目指す。型の包含やsolverの設定を利用者への主な説明にしない。

## 7. 利用者に見える規則の選択肢

### 7.1 構文と契約の既定案

新しい構文を加えず、現在の bind・shadow・if・match を読む案を推す。原則3・4・5に沿い、README の局所解析を実施できるため、旧 Q1 の新構文の選択は設計者への独立した問いから外す。局所の区間注釈や assert 相当の構文を加える案には、未知の拒否や実行時効果の規則が別途要る。今回の比較範囲には入れない。

通常の `Assert` の成功を範囲の根拠にせず、公開部分型・型の等号・単一化・Fail の型列・生成コアへ区間を加えない。SMT を使わない既定案と、関数境界を越えない既定案は第8〜9節に置く。

### 7.2 成否・未知と警告のコード（問い Q3）

「必ず失敗」は、その位置へ到達してオペランドを正常に得て対象演算を実行する場合についていう。前の IO の成功、到達、停止性を含めない。

| 対象 | 必ず失敗 | 正常値が定義域内 | 分からない・予算超過 |

| 案 II の算術 | 除数0またはあふれの警告。実行時検査も残す | 通知せず実行時検査を残す。計算全体の成功を宣言しない | 新しい報告をせず、実行時検査を残す |

警告コードの選択肢は、除数0に W0401・あふれに W0402 を流用する案と、局所解析に専用の新しい二コードを割り当てる案である。前者を推す。失敗の種類によって検索・修正でき、由来の違いは補助位置と note で伝えられるためである。後者なら LLM やハーネスがコードだけで定数評価と局所解析を区別できるが、同じ式への旧新の重複抑制と診断表の項目が増える。新番号は計画時に未使用を確認して割り当て、ここでは予約しない。

どちらを選んでも、01-04 の規範の条件「除数が定数式で」「すべての引数が定数式であり」と、02-05「警告」を、定数評価と局所解析の二つの検出条件を示す形に直す。流用を選ぶ場合は特に、既存コードの適用条件が広がったと明記する。これは Q4 の現行文書不一致の訂正とも区別する。02-10、コード一覧、JSON の報告、生成 Skill の診断表も同じ変更で更新する。

## 8. 解析の定義の案

### 8.1 領域と演算の既定案

推す領域は `Bottom | Closed(lo,hi)` で、非空の値は対象型 T の `min(T) ≤ lo ≤ hi ≤ max(T)` を満たす。Top は型ごとの `[min(T),max(T)]`、Bottom は空集合である。未知の入力はTop、到達不能はBottomとし、区別する。無限の端を導入する代案は将来の数学的整数に再利用できるが、今回の有界整数には不要なので採らない。無限端の有無は設計者への問いから外し、この既定値を計画の受け入れ条件にする。公開Rangeの逆転した端点という入力値と、解析内部のBottomも区別する。

包含は空集合の特例と端点比較、交差は `[max(lo1,lo2),min(hi1,hi2)]`、合流は両方を覆う最小の閉区間である。合流は関係や穴を失う。例えば `[-2,-1]` と `[1,2]` の合流に0が入るので、合流後の除数が非零だとは証明しない。変数間の相関も保持しない。

加算は数学的な `[lo1+lo2,hi1+hi2]` をまず求める。Rust の内部計算は i128 を使い、各段で対象型の値域と比較する。これは言語の整数幅を128ビットへ変えることではない。正のあふれと負のあふれを区別して条件を判定する。成功したときの値域は数学的な結果区間と対象型の全値域の交差である。

**成功値の区間と、途中で失敗しうる情報は別に持つ。** 各式の解析結果には正常終了値の区間と、解析した計算の失敗の有無についての情報を持たせる。加算の結果区間が全域外なら、正常に得た二引数でその加算を評価すると必ず失敗する。一部だけ外なら警告せず、後続へは成功値だけの区間と途中の失敗の可能性を渡す。子がBottomなら親の正常値もBottomだが、親に新しい警告を重ねない。

この区別により、`(max64 + 1) + (-1)` の最終的な数学値だけを見て「安全」としない。今回の区間が返すのは、**式が正常終了した場合**の値の所属である。「必ず成功する」と結論するには、子の正常評価と演算の全入力の安全性も必要になる。未知の一般呼び出しは正常値をTopとし、失敗しないと証明した扱いにしない。

| 操作 | 案 II の扱いと定義 |
|---|---|
| 加算 | `[a,b]+[c,d]=[a+c,b+d]` を対象型の値域と交差する。成功区間と失敗の情報を分ける |
| 減算 | `[a,b]−[c,d]=[a−d,b−c]`。UnsignedInteger の下限は0。`x-x` の関係の特例を加えない |
| 単項の負号 | 符号付き整数だけ `−[a,b]=[−b,−a]` とする。最小値の負号はあふれ。符号なしの負号は元から型の誤りなので解析で受理しない |
| 定数倍 | 型の同じ既知の一点 k と区間の積。k が非負なら `[k*a,k*b]`、負なら端点を交換する。左右どちらが一点でもよい。両辺とも複数値なら結果は Top |
| div/mod | 除数が一点0なら除数0の警告。結果区間は Top。最小値 `div -1` や標準関数の既存の定数警告は保つが、今回その新しい区間伝播は足さない |
| 通常の関数の結果 | Top。Range の射影も含む。利用者関数の本体の実行や再帰的な要約をしない |

整数七種（Integer64 と第2.2節の六種）の領域を型の上下限で引数化する。Byte は算術を持たず、案 II の新しい算術伝播には加えない。Rust では全型の端点を i128 で表せる。加減算と符号付き64ビットまでの定数倍の中間値も i128 に収まる。UnsignedInteger64 の定数倍は u128 で求め、対象型の上限と比較した後で戻す。`(2^64−1)^2` は u128 に収まり i128 には収まらないので、符号なし積を先に i128 に変換しない。Lean は数学的な Int で端点を求め、Rust の符号別計算との対応を独立入力で照合する。

### 8.2 比較・分岐・束縛の対象構文

比較は、解決済みの同じ整数型の局所変数と既知の定数の `<,<=,>,>=,=,<>`、および左右を交換した形を対象とする。`x<k` の真枝は上端 `k-1`、偽枝は下端kと交差する。`<=` なども同様で、内部の `k±1` はi128で計算して値域と交差する。`x=max64` などの境界で実装の整数をあふれさせない。

`x=k` の真枝は一点、偽枝は一般に穴を持つため元の区間を残す。端点の一点を除く場合だけ狭めてよい。`<>` は真偽を交換する。`x+y<k` の逆算や、両方が未知の `x<n` の関係は対象外とし、既存の比較として実行する。定数に見えても型が別幅なら通常の型検査で断る。

`if` の両枝を各一度解析し、結果を合流する。`and` の右辺では左辺の真、`or` の右辺では左辺の偽を使い、短絡順を保つ。複雑な論理式の真偽ごとの環境も各変数の凸な合流までとし、経路の組み合わせを列挙しない。計画では、単一比較の if を基本の段、短絡の合成と match のガードをその追加の段として示す。互いに排他的な選択肢にはしない。見積もりは両段を含む。追加の段の証明が終わらないときは、機能を黙って落とさず、範囲の変更として設計者へ戻す。

`match` は各腕の Integer64 の整数リテラル・範囲パターンと、ガードが真という事実をその本体の中だけで使う。01-02「パターン」により、Integer8 等の接尾辞付きの値はリテラル・範囲パターンに使えないので、その型では束縛した変数へのガードで絞る。前の腕が選ばれなかった理由の列挙と否定条件は持たず、後の腕には元の環境から入る。選択肢は各結果を凸に合流する。既存の網羅性判定へ区間の事実を渡して、ガード付きの腕を新たに網羅と認めることはしない。

通常の `bind`（依頼の let に相当）では、右辺の正常値の区間を新しい束縛番号へ保存する。`shadow` は再代入ではなく新しい束縛なので、古い番号の事実を書き換えず、新しい番号へ追加する。別名を束縛したときはその時点の区間をコピーするが、以後の比較から他の別名まで逆向きに狭める関係解析はしない。Leanの内側から数える番号との対応は、通常束縛・パターン束縛・ワイルドカードごとに定める。

最初の範囲では、return/try/escape/handleをまたいだ事実の伝播を保守的に切る。returnする枝を除いた残りへ条件を残す改善は後の段とし、ifの中では使えてもifの後へ残すとは約束しない。ラムダ・lazy・ハンドラの節・別の関数の本体は新しい解析の境界である。外から捕捉したIntegerを使う場合もTopで始める。再帰・相互再帰・List.foldなどの反復回数や不変条件は求めず、wideningを導入しない。

### 8.3 Range の成功要約を外す理由と、案 I の費用

推す案 II は Range の成功要約を外す。第4.2節には追加警告がなく、Range の使用実績も文書例・検査入力が中心である一方、要約には算術にない三つの接続が要るためである。三つとは、解決済み標準束縛の同定、`Result.Ok(checked)` のパターンと成功値の束縛番号の対応、`Checked/Range.lean` の小モデルと Range.bnt の実際の本体の関係である。原則4の診断の明確さと、00-01の学習の目的を比べても、この段は幅による共通化を先に学ぶ案を推す。

案 I を選ぶ場合だけ、固定端点の `checkInteger` と `value` に要約を設ける。直接の呼び出しか、一つの局所束縛に保存して match した結果について、端点 `[l,h]` を保持する。Ok の枝のその成功値の束縛番号に所属を付け、同じ値への直接の `Range.value(checked)` から `[l,h]` を得る。Error・別の成功値・動的端点・任意の容器・関数引数の CheckedInteger には固定端点を仮定しない。import 別名は解決した同じ標準宣言だけを認め、関数値・穴・パイプ・利用者の同名関数は含めない。

案 I でも CheckedLength・CheckedIndex・NonEmptyList の要約は加えない。正常値の所属を小モデルの `make_ok`・射影から導けても、それだけで標準ソースの実行との一致が証明されたことにはならない。第9.3節の A1 ならこの関係は明示した接続条件と実行比較で確かめ、A2 なら脱糖・Release の実行との接続の追加証明に含める。案 I を学習目的で選ぶ費用は第12.1節に独立して示す。

### 8.4 費用・本体ごとの予算・全体の上限

対象のASTノード数をN、活きた局所束縛の数をBとする。全環境を枝ごとにコピーしない。束縛番号の辞書と差分の積み重ねを使い、変更した束縛だけを復元・合流する案を推す。辞書の操作を含め、おおむね `O(N log B)` を目指すが、全構文についての厳密な計算量の証明や実測はまだない。診断の由来は最大8箇所で打ち切り、依存の推移閉包を各式へ複写しない。標準ソースの本体を利用者の呼び出しごとに再解析しない。

計画の暫定値は、一つの本体につき10万回、検査全体で100万回の解析操作、補助記憶は一つの本体につき4 MiB・全体の同時保持16 MiBとする。解析操作は、式の訪問、環境の参照・更新の各一回、合流の各項、由来の一箇所の走査を各1と数える。識別番号付けと対象判定の追加走査も同じ予算に数え、計上のための走査を上限の外で無制限に行わない。由来の表示、識別番号の対応表、作業スタックも記憶量に含める。本体の予算は本体ごとに作り直し、全体の回数は作り直さない。全体の同時保持量は本体を離れると解放してよいが、保持した診断と対応表を計上から落とさない。数値は未測定の既定案であり、設計者への問いにせず、短い試行で調整して計画に固定する。

本体ごとの予算は、無関係な本体の操作数が通常の解析結果に及ばないようにするために設ける。全体の上限を併用する以上、その上限に達すれば無関係な関数の追加で後の本体の警告が消え、`--deny-warnings` の下で受理が変わる可能性は残る。この限界を仕様と CLI の説明に書き、全体上限による未解析の本体数・本体予算の超過・未対応の構文を別々に検査報告へ残す。警告がないことを安全の証明として表示しない。全体上限に達した後も既存の定数警告を止めない。

消費順は読み込み済みモジュールとソース位置による決定的な順序にする。超過時は残りを Unknown に退避し、既に健全な根拠で得た警告は保持する。Lean の健全性は任意の予算について述べる。解析に興味のない本体で環境を作らず、標準ソースの警告を省く境界を保ち、案 I でも要約のために標準本体を追加走査しない。

AST の走査を明示したスタックで書くことは必須条件にしない。AGENTS.md の再帰を認める規約に従い、既存の深さ制限の範囲で再帰を使ってよい。明示したスタックは、深い入力の短い試行で必要と分かった場合の実装候補とする。必須にするのは、操作数と記憶量を数え、超過を安全な未知へ退避すること、および既存の入力制限内でホストのスタックを破壊しないことである。

本体ごとの予算の下で全体上限に達しない場合は、無関係な小さい関数を足しても元の本体の診断が同じであることを受け入れ条件にする。全体上限に達する例は別に確認し、消えた診断を安全と解釈しないことを確かめる。計算量の `O(N log B)` は全環境のコピーを避けた場合の目標であり、未証明・未測定である。

docs/todo の TODO-032 は2026-10-21に全体を閉じ、数値目標の判定を TODO-262、残りの時間と0.0.10の退行を TODO-275へ移した（同目次の終了項目）。TODO-275 の本体ごとのクラス索引の再構築・標準ソースの固定費を、この解析でも繰り返さない。将来の受け入れでは空 main、関数数を変えた入力、深い加算、分岐、局所束縛、各幅の演算を短い試行で測り、時間・記憶量・予算消費を分けて記録する。案 I なら Range の成功も加える。今回は測定していない。

0.0.10 の局所構築器は、専用の束縛と共有番号を持つ（`Surface/BuilderSyntax.lean`・`Builders.lean`、07-04「01-12 との対応」の構築器の段落）。区間の環境にはその位置を通常の整数として登録しない。builderの追記・copy・lengthから動的長さを推論せず、長さの結果はTopとする。構築器が局所だからという理由でStateや他のエフェクトを今回さらに取り除かない。Referenceの読出しも未知の整数として扱う。同じ可変内容を二度読んだ式を同じ値として狭めない。

## 9. SMT・形式化・交換

### 9.1 自作する判定器の既定案

| 案 | 今回の評価 |

### 9.4 式の識別と交換の受け入れ条件

現行 `Exchange/Syntax.lean` の Surface の表現には、ソース位置も節や式の識別番号もない。警告位置の比較には新しい対応付けが要る。第一案は、定義を識別する名前と、交換する型付き Surface の木を先行順に訪問した番号の組である。ソースのバイト位置は Lean の比較のキーにせず、Rust の表示用の表にだけ持たせる。

番号の意味は解析結果や予算で変えない。上限で番号付けを打ち切った部分は未取得として記録し、残りにずれた番号を振って続けない。Expr・Exprs・HoleArgs・Block・Arms・Clauses のフィールド順とリスト順を交換の仕様で固定し、未対応の部分木も含めて番号を振る。Rust の書き出しと Lean の読み取りが、それぞれ同じ規則から番号を得る。Rust 側に `(定義名, 先行順番号) → (元の式ID, span)` の多対一の表を持たせ、リテラルの負号・名前付き引数の並び・return 等で表層の節点と元ASTが一対一にならない場合を定める。合成した節点の位置は元の演算を明示して割り当てる。対象演算の全てで対応を作ることを受け入れ条件とし、対応漏れを警告の抑制で隠さない。対応の定義のない合成節点は解析の対象外として明示する。区間の比較で番号が一つずれた場合を、同じ警告の一致として通さない。

| 交換の案 | 必要な変更と費用の見込み | 推す理由と限界 |
|---|---|---|
| 独立した版付き `interval-corpus` | 既存の Surface の読者を再利用し、解析予算・対象の型・識別規則・区間と警告の結果を独立した入口で読む。識別の対応・書き出し・読み取り・版の拒否を含め、Lean 4〜8時間、Rust 6〜10時間を第12.2節の共通費に含める | 推す。既存のコア・型比較の読者を変えずに受け入れ条件を固定できる。入力の Surface 本文を複製する管理費がある |
| sidecar を上げて解析情報を追加 | 現行 sidecar の版規則、Rust 出力、Lean の深い欄の拒否、比較の入口を更新する。識別を含めLean 3〜6時間、Rust 4〜8時間の見込み。独立形式に代えて選んだ場合の費用であり、両方を足さない | Surface の本文の重複は避けやすいが、既存の六入口の読者・旧版の拒否との回帰確認が増える。節約を実測した見積もりではない |

現行 `Exchange/Version.lean:140` は corpus 8〜14、sidecar 2〜6 を扱う。新しい解析情報を旧版が無視して一致した扱いにはしない。独立形式の初版では識別の走査順も版の規則に含め、旧版・未知の欄・未知の構成子を拒否する。既存 Surface の構文が変われば、解析の対象構文と番号の対応も同じ変更で点検する。

正常値の区間、Top、Bottom、未対応、予算超過、失敗の種類、警告位置をRustとLeanで比べる。端点は文字列等から厳密に読み、64ビット値を浮動小数点へ丸めない。型の幅・定数の取得結果・解決した標準束縛の対応も入力へ明記する。標準束縛を認定する Rust の名前解決の正しさは、この比較で証明されない。

受け入れでは、独立した期待値を持つ区間入力と実ソースからの全関係定義を比べ、全Topだけの一致を完了としない。上端・下端・空・一点・合流の穴・中間あふれ・各幅・shadow・パターンの束縛・短絡・guard・境界・予算超過を含め、正常checkerの件数と解析の対象外・Top・予算超過の件数を別々に記録する。案 I なら偽の標準束縛と別個体の成功値、案 III なら引数順・レコード更新・モジュール不在を追加する。

Rust/Lean の解析結果の一致だけでは A1 の評価器と VM の一致を検査したことにはならない。別の差分テストとして、対象構文から作る小さい閉じた入力と固定の境界例を部分評価器・VMの双方で実行し、値・失敗の種類・対象演算への到達を照合する。未知の呼び出しを含む部分評価器は単一の期待値を持たないので、この実行比較は具体的に評価できる対象部分に限り、未知の境界は区間への所属と警告の独立期待値で確かめる。実行位置の観測方法は計画で固定する。VM の入力が未到達なら警告定理の前提を満たす実行例には数えない。

既存の進行・保存・エフェクト健全性・脱糖の型保存・checker/網羅性の主定理は、前提・結論を変えず維持できる設計を推す。新しい解析の意味の定理は追加する。新公理、主定理の前提追加や結論の弱化が必要になった場合は、その理由と別案を設計者へ戻し、Rustの依存作業へ進む条件にしない。既存の本体の型保存だけを引用して区間の健全性を済ませる案も採らない。

推す案による通常モードでの新しい拒否は0である。RangeのResult.Errorを観察する標準ソース・テスト・Skillの例も受理を保つ。新しい警告により `--deny-warnings` の入力が拒否される可能性はある。新解析がまだないので、リポジトリ全体の新規警告件数は**未取得**であり、0と主張しない。実装段で標準/利用者モジュール・文書例・Rust内の検査入力・ゴールデン・examples・Skill例を旧新で照合する必要がある。

対して、Range の固定値の失敗までEにする代案は、今回の指定領域だけでも少なくとも次の11呼び出しを拒む。これは呼び出し数であり、ファイル数や課題数とは異なる。

## 11. 組込み構成とホスト幅

解析は整数の値域と表層に依存する小さいモジュールに置き、ネットワーク・Wasmtime・暗号・サーバへの直接依存を増やさない。案 II は幅ごとの算術の規則を型の上下限で共通化し、ホストの `usize/isize` を言語の値域にしない。構成で使えるモジュールが変わっても、型・エフェクト・整数・解析の意味を変えない。

案 I の要約、案 III の契約表は、実際に構成へ含まれロードした標準宣言にだけ適用する。含まれないモジュールの呼び出しを解析が補って受理しない。HTTP の契約を加える場合も、ネットワーク実装を中核の解析へリンクせず、解決済み宣言と固定の値域の表として渡す。

案 II の端点は i128、加減算・符号付きの積は i128、符号なし64ビットの積は u128で扱う（第8.1節）。ノード数・記憶量は usize の検査付き計算を使い、予算定数は32ビットにも収まる値にする。JSONの端点をusizeで読まない。Integer64の `max64+1` 等を言語の値として構築せず、中間の比較にだけ使う。

局所構築器や List の論理長と、OSが確保できる量は別である。区間が数値上の定義域に入っても確保失敗・IO失敗を排除しない。32ビット向けの実行や構成ごとのビルドは今回未実施であり、将来の計画で型幅の点検と可能なクロス検査を割り当てる。
