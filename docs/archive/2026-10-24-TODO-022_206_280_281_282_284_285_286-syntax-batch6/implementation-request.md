## 依頼する内容

最初にAGENTS.mdを読む。ただし、この依頼ではprivate/を読まず、AGENTS.mdの「private/AGENTS.mdがあれば読む」を適用しない。.claude/skills/・.agents/skills/のうちprivate/を指すシンボリックリンクも読まない。docs/todoを読む前提にせず、必要な内容はplanとdecisionsに写してある。過去の改造文書を実装の根拠にせず、現行設計書・ソースを読む。

改造の最初の依存の勧告照合は2026-10-24にP2で実施済みであり、ワークスペースとfuzzの同じ19件はTODO-284・285に一致した。設計者は第6弾に対応を組み込むと決めた。取りまとめはpreflightのP2記録とこの判断を起動前に確認し、担当へ要る内容を渡す。ツールチェーンの網羅的な照合まで実施済みとは扱わない。今後の最初の照合はD25の公開手順、改造がない時の手動・周期的な照合はD30/S05のsecurity-advisoriesスキルに従う。

指定した枝ID一つ（枝のない作業はそのID）を、計画の目的・対象ファイル・完了条件に従って実装する。処理系と設計書・生成物を同じ状態へそろえ、未接続の仮置きを完了にしない。

Leanの作業では、旧主定理と今回の中心の健全性定理の前提・結論の変更、公理（Builtins.Assumptionsを含む）の追加が必要と分かったら当該作業を止める。取りまとめへ該当する言明・行き詰まった例・代案を報告し、未証明の仮定を隠してRustへ進めない。Rangeと固定域APIの評価規則はD18のとおり対象構文の評価関係の定義に置き、中心定理やδの前提を増やさない。実本体との一致はVMとの比較で扱う。既定ビルドと定義・言明・仮定のレビューを通した区切りだけを処理系の前提にする。C1とL26が閉じた後、S01→S02a→S02b→S03→S04→S05を受け入れてからA01〜A12へ進める。S作業はformal/・01-12・07-04を変更しない。勧告の照合はD25/D26に従い、勧告あり・照合済みの検出0件・取得不能を区別して表示・記録する。change/releaseで新しい勧告が出ても検査を不合格にせず、取りまとめが設計者へ報告し、次の改造の最初の照合で組み込むかを判断する。ignoreの追加・期限による候補の停止は計画しない。C2/C3/C4は各拡張のA、C5はXの前提とする。拡張のLが見込みの2倍を超えたら、取りまとめが設計者へ閉じた範囲で処理系へ進むかを尋ねる。独立したR作業と、完了済みのLeanの区切りに対応する処理系作業は継続できるが、三案全体が未完なら版上げ・受け入れへ進まない。

新構文・公開部分型・SMT・関数間解析を足さない。型とエフェクトの既存規則、実行時検査、構成で外せるモジュールの境界を保つ。整数幅をusizeにせず、UnsignedInteger64の定数倍にはu128を使う。利用者向けの案内はハーネス経由の検査報告と実行を中心に書く。

各作業の初回の着手は45〜60分を目安とする。検査・修正・レビューを含む完了の平均は2〜3時間を想定し、実装と記録の個別の見込みはplanの枝の表と末尾の全体表に従う。開始時の事前点検で収まらないと分かったら、取りまとめが対象・中間の不変条件・後続IDを追記して分割してから依頼し直す。所要時間を過ぎても黙って続行せず、見込みの2倍を超えたら原因と残りを報告する。結果の記録と検査・レビューの時間はplanの全体表の別枠も参照する。

Lean のメモリの上限: `formal/lakefile.toml` の `moreLeanArgs` が `lake build` の各 Lean に `-M 12288`（MiB）を付ける。ファイルを一つ検査するときは `lake env lean -M 12288 <file>` のように同じ上限を必ず付ける。大きな計算を `rfl` で展開させる証明は避け、`decide +kernel` などを使う。Lean のビルドを並行して走らせない。作業末の検査は `/usr/bin/time -l` で包み、最大常駐量を results.md に記す（2026-10-24、設計者の指示）。

作業途中は、関係するテストだけを Cargo 等で直接実行する。作業末は、計画の work 行にある `scripts/check.sh --level work --base <基準> [--test <関連ターゲット> ...]` を一度実行する。計画に名指しの `--only` があればそれを使う。Rust の作業末の既定の lib 全件・関連統合テスト・clippy・fmt はこの入口に任せ、直接のコマンドを重ねない。work が未実装の移行中だけは計画の直接のコマンドを使う。文書だけ・シェルや Python だけ・Lean だけの作業に Rust の全 lib を追加しない。

検査前に種類を知らせ、計画で固定した基準と指定へ `--dry-run` を付け、選択と理由を確認する。長い検査・heap・全件の特殊構成を含む場合は見込み時間も知らせる。変更範囲が増えたら、入力を読む側と必要な構成を含めて計画の検査を更新する。共有の入力を変えたときは、その入力を読む全統合ターゲットを指定する。`--test` は統合テスト名ごとに繰り返し、Rust の自動 work で省略すれば全統合ターゲットとなる。

ヒープの不変条件や安全点を越える値を変える作業では、局所の heap-verify・gc-stress と必要な `check-heap.sh` を、次の作業の前提にする前に通す。形式化の内側では 07-04 の Lean 先行を守り、既定の `lake build` が `sorry` なしで通ることと、定義・言明・仮定のレビューを処理系へ進む条件にする。Rust と Lean の全比較は、計画で接続を閉じる区切りと最終の関係状態に割り当てる。

作業の完了のために段・改造・リリースの全件検査を先取りしない。失敗の修正や関係する追加変更の後は、古くなった検査だけを再実行し、初回の失敗と修正も残す。テストの期待値・大きさ・ignore・時間制限を緩めない。テストを加える・変えるときは test-audit の作成時の関門を通す。

普通の作業の results.md は、基準のコミット、走らせたコマンド、終了状態、外側の時間、計画からのずれと申し送りだけを記す。失敗した場合は原因と修正も残す。結果を引用するときに限り、07-03「結果の保存と引用」の全欄を記す。基準と HEAD の完全な ID、差分の有無と一覧、コマンド・構成・入力・ツールチェーン・件数・終了状態・時間・環境の制限、元の記録、以後の変更、関係状態が一致する理由、判断者と日付を残し、別の状態への引用には未コミット差分と未追跡入力の SHA-256 も保存する。未実施は担当と時期を明記し、この作業が受け持つ失敗を後へ送って完了にしない。

自動分類が終了3で停止したら、分類不能のファイルまたは存在しない基準を示し、規約に従って設計者へ当該水準の `--level … --only`（停止までに選んだ単位を案内し、分類不能のファイルに必要な単位を補う）、互換の `--full`・水準なしの `--only`、`--none` のどれで続けるかを尋ねる。計画に既に名指しがあればその指定で進める。`--level` と `--only` の併用は分類せず、名指しだけを実行する。指定の誤りは終了2として計画を直す。検査失敗と道具不在は通常1である。ただしadvisoriesは、勧告ありと取得不能/道具不在を表示・記録して終了0、設定の誤り/実行器の不具合は1とする。選んだ検査の成功0は、水準全体の完了とは区別する。release は候補と証拠の手動照合も要る。

結果を指定の results.md へ記録し、最後に変更したファイルの要約、検査と結果、計画からのずれ、後の作業への申し送りを日本語で短く報告する。コミット・取り込み・docs/todo の更新・公開の操作は「作業の指定」の明示の指示に従う。
