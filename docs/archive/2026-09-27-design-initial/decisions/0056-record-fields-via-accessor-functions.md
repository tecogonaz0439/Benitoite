# 0056. レコードのフィールドは、型のモジュールの関数で参照する

- 状態: 採択
- 日付: 2026-09-26
- 関連章: [代数的データ型とパターンマッチ](../01-spec/01-05-data-types.md), [構文](../01-spec/01-02-syntax.md), [名前・スコープ・モジュール](../01-spec/01-03-names-modules.md), [ロードマップ](../00-overview/00-03-roadmap.md)
- 関連する未決事項: [OPEN-023](../open-issues.md#open-023)

## 背景

v1 では、名前の付いたフィールドを持つレコードを加える（[ロードマップ](../00-overview/00-03-roadmap.md)）。`r.name` のようにフィールドを値の型から引くと、ドットの右の名前を値の型から解決することになる。ドットをモジュールと型名の修飾に限り、値に続けてドットを書く形を誤りとした決定（[ADR 0004](0004-surface-syntax-skeleton.md)）と食い違い、HM 型推論も型が分かるまで名前を解決できなくなる（[OPEN-023](../open-issues.md#open-023)）。

## 決定

レコードの型を宣言すると、フィールドごとに、同じ名前の関数がその型のモジュールに入る。`record Person { name: String ... }` なら、`Person.name` は `fn(Person) -> String` の関数である。フィールドの値は、`Person.name(p)` か `p |> Person.name` で取り出す。パターンでも分解できる。

値に続けてドットを書く形（`p.name`）は、最小実行版と同じく構文エラーとし、診断は `Person.name(p)` と `|>` を使った書き方を修正案として示す。

## 検討した代替案

- **`p.name` と書き、フィールドの名前をモジュールの中で一意にする**（OCaml 系）: LLM には書きやすい。しかし、ADR 0004 の規則を改めることになり、同じフィールドの名前（`name` など）を二つのレコードで使えない。
- **行多相のレコード型**: `p.name` をどのレコードにも使える。しかし、型推論と型の誤りの診断が大きく複雑になる。

## 帰結

- フィールドの参照は、ほかの関数の呼び出しと同じ規則で型付けでき、HM 型推論を変えずに済む。
- フィールドを取り出す関数は値として使える（`List.map(people, Person.name)`）。
- `p.name` と書く誤りが LLM にどの程度起きるかを、[OPEN-012](../open-issues.md#open-012) の測定で確かめる。
