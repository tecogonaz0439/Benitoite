# 0019. 検査の段で誤りが見つかったら、次の段に進まない

- 状態: 採択
- 日付: 2026-09-26
- 関連章: [パイプライン](../02-impl/02-01-pipeline.md), [字句解析器と構文解析器](../02-impl/02-03-frontend.md), [名前解決とモジュール読込](../02-impl/02-04-resolver.md), [型検査器](../02-impl/02-05-typechecker.md), [診断エンジン](../02-impl/02-10-diagnostics.md)
- 関連する未決事項: なし

## 背景

処理系は、字句解析・構文解析、名前解決、型検査の段を順に通してスクリプトを検査する（[全体像](../00-overview/00-02-architecture.md)）。ある段で誤りが見つかったときに、後の段をどこまで進めるかを決める必要がある。

診断の第一の読み手は LLM であり、LLM は診断を読んでスクリプトを直し、再び検査する（[全体像](../00-overview/00-02-architecture.md)）。構文解析器は、LSP サーバのために、誤りを含むソースからも回復して解析を続ける必要がある（同）。ただし、LSP サーバは v1 に含めない（[ロードマップ](../00-overview/00-03-roadmap.md)）。

## 決定

検査の各段は、出力と診断の組を返す。誤りの診断が一つでもあれば、処理系は次の段を行わない。警告の診断は、次の段に進むことを妨げない。

各段の中では、誤りから回復して処理を続け、その段で見つけられる誤りをできるだけ多く報告する。構文解析器は、一つの構文エラーで解析をやめない。

## 検討した代替案

- **誤りを含んだまま後の段へ進める**: 誤りの箇所を「誤りのノード」や「未知の型」として後の段に渡し、一度に多くの診断を出す。LSP サーバでは、編集途中のソースに対しても型の情報を示せるので有利である。しかし、後のすべての段が誤りのノードを扱う必要があり、前の段の誤りから派生した診断（構文エラーの箇所を参照する名前が未定義になる、など）を抑える仕組みも要る。派生した診断が混ざると、LLM がどの診断を直せばよいかを判断しにくくなる。

## 帰結

- 名前解決と型検査は、構文エラーを含まない AST だけを扱えばよい。型検査は、名前の誤りを含まない入力だけを扱えばよい。
- 前の段の誤りを直すまで、後の段の誤りは報告されない。LLM が検査と修正を繰り返す回数は、誤りを含んだまま進める場合より増えうる。
- 構文解析器が回復のために作る誤りのノードは、構文解析器の出力には現れうるが、名前解決より後の段には渡らない。LSP サーバを実装するときに、誤りを含んだまま後の段へ進める方式に変えるかを見直す。その場合も、構文解析器の回復の仕組みはそのまま使える。
- 型検査の中でどの単位まで回復して検査を続けるか（トップレベルの関数ごとなど）は、[型検査器](../02-impl/02-05-typechecker.md)で定める。
