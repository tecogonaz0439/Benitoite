# 0085. 最小実行版の実装の確認は、オーケストレータが行い、Opus が実装した作業は Codex も確かめる

- 状態: 採択
- 日付: 2026-09-27
- 関連章: [ロードマップ](../00-overview/00-03-roadmap.md), [処理系のテスト戦略](../07-quality/07-03-compiler-testing.md)
- 関連する未決事項: [OPEN-019](../open-issues.md#open-019)

## 背景

実装 LLM が書いた実装を、受け入れテストと設計書に照らして確かめる作業を、誰が担うかが未決であった（[OPEN-019](../open-issues.md#open-019)。置き場所は [ADR 0040](0040-single-repository.md) で決着済み）。予定していた形は、Claude Code がレビューし、Claude Code 自身が実装した部分は別のフロンティアモデルがレビューする、というものであった。実装した LLM と同じ LLM にレビューさせないためである。

[ADR 0084](0084-implementer-assignment-for-minimal.md) で、実装を Opus 5.5 のサブエージェントと Codex（GPT-6-Luna）で分担し、Claude Code（Opus 5.5）がオーケストレータを担うと決めた。

## 決定

1. オーケストレータ（Claude Code）は、すべての作業の結果を、`scripts/check.sh` の実行と、実装プランの[実装の確認の観点](../../2026-09-27-implement-initial/00-common/00-04-review-checklist.md)に従う読み取りで確かめる。
2. Opus のサブエージェントが実装した作業は、オーケストレータの確認に加えて、Codex にも読み取り専用のサンドボックスで確かめさせる。オーケストレータとサブエージェントが同じモデルだからである。
3. 確認で見つかった問題は、オーケストレータがその作業の担当に直させる。担当を変えて直させることもある。
4. オーケストレータは、確認を終えた作業をコミットし、`san_benito` に取り込む。実装 LLM はコミットしない。
5. 実装プランの型やシグネチャを変える必要があるとの報告を受けたときは、オーケストレータが実装プランの改め方を設計者に示し、合意を得てから作業を続ける（実装プランの[作業の進め方](../../2026-09-27-implement-initial/00-common/00-03-workflow.md)）。

## 検討した代替案

- **オーケストレータだけで確かめる**: Opus が実装した作業を、同じモデルが確かめることになる。同じモデルは同じ誤解を共有しやすいので、予定していた形の理由（実装した LLM と同じ LLM にレビューさせない）を満たさない。
- **Codex が実装した作業も、Opus のサブエージェントに別に確かめさせる**: オーケストレータの確認が既に別のモデルによる確認になっているので、重ねる必要はない。

## 帰結

- Codex は、実装の担当と確認の担当を兼ねる。どちらも同時に一つだけ起動するので、オーケストレータは実装と確認を一つの列に並べる。
- 設計者は、完了の報告と確認の結果を読んで、実装の理由を質問できる（[目的と設計原則](../00-overview/00-01-goals.md)の「学び方」）。
