# 0044. 実行環境のメモリが尽きたときは、評価意味論の停止の手順によらずに終わってよいとする

- 状態: 採択（決定の一部を [0079](0079-rust-readings-of-go-based-decisions.md) で改めた）
- 日付: 2026-09-26
- 関連章: [評価意味論](../01-spec/01-08-evaluation.md), [ランタイム](../02-impl/02-09-runtime.md), [スクリプト実行と埋め込み](../02-impl/02-11-embedding.md), [CLI](../06-tooling/06-01-cli.md)
- 関連する未決事項: [OPEN-030](../open-issues.md#open-030), [OPEN-031](../open-issues.md#open-031)

## 背景

[評価意味論](../01-spec/01-08-evaluation.md)は、処理系がメモリの使用量に上限を持ってよく、上限に達したときは実行時エラーと同じ手順で停止するとしていた。この手順では、出力のバッファをすべて書き出し、理由を標準エラー出力に書き、失敗を表す終了状態で終わる。最小実行版の処理系は、呼び出しの情報の大きさには上限を設ける（[ADR 0030](0030-call-stack-size-limit.md)）が、ヒープの使用量には上限を設けない。ヒープが尽きたときにこの手順で停止できるかを、[OPEN-030](../open-issues.md#open-030) で確かめることにしていた。

Go の一次資料で、次のことを確かめた（2026-09-26。Go のソースは master、2026-06 時点）。

- Go のランタイムは、ヒープを確保できないと `throw("out of memory")` を呼ぶ（`src/runtime/mcache.go`、`src/runtime/mheap.go`）。`throw` は、スタックトレースを書いて終了する致命的なエラー（fatal error）であり（`src/runtime/panic.go` のコメント）、panic ではないので `recover` では捕捉できない。
- 致命的なエラーで終わるときの終了状態は 2 である（`src/runtime/panic.go` の `fatalthrow` が `exit(2)` を呼ぶ）。
- `runtime/debug.SetMemoryLimit` で設けるメモリの上限は soft な上限である。Go のランタイムは、GC の頻度を上げてこの上限を守ろうとするが、どんな場合でも守るとは保証しない（[runtime/debug](https://pkg.go.dev/runtime/debug#SetMemoryLimit)、[GC ガイド](https://go.dev/doc/gc-guide)）。
- Linux の既定の設定（heuristic overcommit）では、明らかに過大な確保だけを拒み、物理メモリを超える確保を受け付けることがある（[overcommit accounting](https://www.kernel.org/doc/html/latest/mm/overcommit-accounting.html)）。このため、Go の中で確保の失敗が起きる前に、OS の側でメモリが足りなくなることがある。その後にプロセスがどう終わるかは確かめていない。

したがって、処理系の外から与えられたメモリが尽きたときは、Go で書いた処理系の中からは、評価意味論の手順で停止することを保証できない。

## 決定

評価意味論の手順で停止する資源の不足は、処理系が自ら設けた上限に達した場合に限る。処理系が上限を設けていない資源が実行環境で尽きたとき（メモリが足りない場合など）は、処理系はこの手順によらずに終わってよい。このとき、出力のバッファに残った内容が書き出されないことがあり、終了状態は言語仕様では定めない。

最小実行版の処理系は、ヒープの使用量に上限を設けない。ヒープが尽きたときは、Go のランタイムの致命的なエラーで終わる。このときの終了状態は 2 であり、検査の誤りと使い方の誤りに割り当てた値（[ADR 0037](0037-exit-status-values.md)）と重なる。処理系の形式の診断が標準エラー出力にないことで、検査の誤りと見分ける。

## 検討した代替案

- **ヒープの使用量の目安を処理系が数えて、先に止める**: `runtime/metrics` を定期的に読んで目安を超えたら止め、大きな値を作る組み込み関数では作る前に大きさを確かめる。多くの場合は手順どおりに止まる。しかし、読み取りの間に一度に大きく確保した場合と、OS の側でメモリが足りなくなった場合を取りこぼすので、保証にはならない。最小実行版の実装の量も増える。v1 で設けるかを [OPEN-031](../open-issues.md#open-031) で決める。
- **処理系を親と子の二つのプロセスで動かす**: 子のプロセスが致命的なエラーで終わったら、親のプロセスが処理系の形式で報告し、終了状態も改める。報告の形式と終了状態は保てるが、最小実行版には重い。子のプロセスの出力のバッファに残った内容は、この形でも書き出せない。
- **終了状態の割り当てを変えて、2 を避ける**: Go の致命的なエラーの終了状態と重ならなくなる。しかし、2 を使い方の誤りに使うのはコマンドの慣例に沿っており、重なるのはヒープが尽きるまれな場合だけである。標準エラー出力の内容で見分けられるので、割り当ては変えない。

## 帰結

- 評価意味論の手順で停止することを、最小実行版で保証する資源の不足は、呼び出しの情報の大きさの上限に達した場合だけになる。
- ヒープの使用量と実行時間の上限は、処理系を起動する側（Agent Skills を実行するハーネス、シェル、OS）に委ねる（[スクリプト実行と埋め込み](../02-impl/02-11-embedding.md)）。
- LLM とハーネスは、終了状態 2 で処理系の形式の診断がないときに、コードの誤りではなく、処理系が異常に終わったと判断する必要がある。
- 後で処理系がヒープの使用量に上限を設けても（[OPEN-031](../open-issues.md#open-031)）、この決定の範囲で、評価意味論の手順で停止する場合が増えるだけであり、既存のスクリプトの意味は変わらない。
