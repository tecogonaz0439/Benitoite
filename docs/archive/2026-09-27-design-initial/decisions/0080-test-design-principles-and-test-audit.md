# 0080. テストは振る舞いを確かめる原則で書き、新しいテストは関門を通してから加える

- 状態: 採択
- 日付: 2026-09-27
- 関連章: [処理系のテスト戦略](../07-quality/07-03-compiler-testing.md)
- 関連する未決事項: [OPEN-038](../open-issues.md#open-038)

## 背景

処理系は LLM が実装する（[ADR 0076](0076-initial-implementation-in-rust.md)）。LLM は、小さな変更のたびにテストを足す傾向があり、テストが膨らんでいく。膨らんだテストは、実行に時間がかかるだけでなく、実装の詳細に結び付いたものが混ざると、振る舞いを変えない作り直しのたびに壊れる。処理系の学習を目的とする設計者にとっても、テストが何を守っているかが読み取れなくなる。

設計者は、テストを Vladimir Khorikov『Unit Testing Principles, Practices, and Patterns』（邦訳『単体テストの考え方/使い方』）の考え方に沿って書くことを求めた。また、テストの膨張を抑える手順の例として、OpenClaw の test-audit スキル（MIT License）を挙げた。

test-audit スキルと同書の考え方は、次の点で重なる。

- テストは維持の費用がかかるので、守る振る舞いや契約によって価値を示す必要がある。
- 振る舞いを変えない作り直しで壊れるテストは、振る舞いではなく実装を確かめている。
- テストのためだけに本番のコードの公開の範囲を広げたり、差し込み口を設けたりしない。
- 期待値をテストの対象の処理で作らない。確かめたい振る舞いをテストダブルの側で実装しない。
- 網羅率のためだけのテストを書かない。似たテストは、表の形のテストにまとめる。

同書の考え方との主な違いは、次の二点である。いずれも対立ではなく、力点の違いである。

- test-audit スキルは、一つの契約を「最も適した境界」の一つのテストで守ることを求める。同書は、込み入った規則の場合分けは速い単体テストで広く確かめ、統合テストは主な流れと、単体テストで届かない場合に絞ることを勧める。処理系では、各段の公開の関数と型を持ち主の境界とすることで、両者は一致する（各段は外部に作用しないので、段の公開の関数のテストは、同書のいう出力を確かめる単体テストになる）。
- test-audit スキルは、遅いことを削除の理由にしない。同書は、速いフィードバックを良いテストの性質の一つに数える。本決定では、遅いテストも守る契約があれば残し、速さは新しいテストをどの境界に置くかを選ぶときに考慮する。

## 決定

1. 処理系のテストは、同書の考え方に沿った原則（[処理系のテスト戦略](../07-quality/07-03-compiler-testing.md)の「テストの設計の原則」）で書く。
2. OpenClaw の test-audit スキルを、このリポジトリに合わせて日本語に翻案し、プロジェクトのスキル `test-audit` として置く（`.claude/skills/test-audit/`）。元の著作権表示と許諾の条件をスキルに添える。
3. テストを加える・変える作業では、`test-audit` の作成時の関門を通す。実装プランの各作業の完了条件に含める。
4. テストが増えたときは、`test-audit` の監査の手順で、定期的に価値の低いテストを整理する。

## 検討した代替案

- **テストの数や行数に上限を設ける**: 機械的に抑えられる。しかし、必要なテストまで削る圧力になり、守る契約で判断するという原則と合わない。
- **原則だけを書き、手順は定めない**: 文章の原則は、LLM が作業の最中に読み飛ばしやすい。関門の四つの問いのように、作業の場面で答える形にした方が守られやすい。

## 帰結

- 実装 LLM は、テストを足すたびに、守る振る舞い、捕まえる退行、既存のテストで足りない理由を示す必要がある。
- 同書の内容の要約は、原典の該当箇所で確かめていない（[OPEN-038](../open-issues.md#open-038)）。
- `test-audit` スキルは、元のスキルが改められても自動では追従しない。取り込み直すかは、必要になったときに判断する。
