# 0001. 利用者が怠惰・短気・傲慢のままでいられることを目指す

- 状態: 採択
- 日付: 2026-09-25
- 関連章: [目的と設計原則](../00-overview/00-01-goals.md)
- 関連する未決事項: [OPEN-001](../open-issues.md#open-001), [OPEN-012](../open-issues.md#open-012), [OPEN-015](../open-issues.md#open-015)

## 背景

設計メモは二つの目的（Agent Skills から実行できるスクリプト言語、設計者の関数型プログラミングの学習）を定めているが、どのような利用者に何を提供する言語かという方向は定めていなかった。設計原則と構文の判断基準を決めるには、この方向が先に必要になる。

設計者は Perl の哲学のうち、「簡単なことは簡単に、難しいことも可能に」と、プログラマの三大美徳（怠惰・短気・傲慢）から影響を受けている。一方で、言語仕様の細部については Python に賛同する点が多い。

## 決定

利用者が怠惰・短気・傲慢のままでプログラムを使い続けられることを、言語の目指す方向とする。Perl の利用者は、三大美徳を発揮する前に、言語を学ぶ勤勉さ、デバッグに付き合う長気、自分のコードを疑う謙虚さを払っていた。Benitoite ではこの負担を利用者から外し、処理系の検査と、コードを書く LLM に負わせる。想定する利用者はプログラマに限らず、主な接点はコードではなく実行前の権限の確認と実行後の結果の確認とする。

この方向は到達できるかどうか分からない目標として掲げる。「怠惰・短気・傲慢のままで」は、利用者に求める習得・調査・再確認の負担を減らす、という設計上の解釈として定める。

一方で、静的検査が保証する範囲は、型とエフェクトの規則への適合に限る。処理結果が利用者の意図に合うこと、外部操作の成功、停止性は保証しない。型とエフェクトの契約を満たしていても、意図と異なる結果になりうるからである（集計条件を「以上」から「超える」へ変えても、型とエフェクトは同じままでありうる）。目標が未達であることと、何を保証しようとしているかが曖昧であることは別の問題なので、目標を大きく掲げたまま、保証の意味だけは明確にする。同じ理由で、エフェクトの静的な追跡と実行時の権限制御を区別する（設計メモ 3.2）。

設計原則は、利用者の読みやすさと壊しにくさを 3 番目に置く。想定する利用者の中心はプログラマでない人なので、記述量の少なさや構文の統一のために、利用者が権限や結果を理解しにくくなる判断を許さないためである。

あわせて、設計メモ 0.1 の表向きの目的（Agent Skills から実行できるスクリプト言語であること）を、「Perl の精神を受け継ぎ、利用者が怠惰・短気・傲慢のままで使えるスクリプト言語であること」に改める。Agent Skills から実行できることは、この目的を実現する手段とする。LLM がスクリプトを書いて実行する Agent Skills は、利用者が言語を学ばずに済むという方向を成り立たせる手段であり、方向そのものではないからである。

同じく設計メモ 0.1 の実質的な目的に、関数型プログラミングに加えて言語処理系（解析器・仮想機械・ランタイムなど）の学習を明記する。処理系を自作するという既存の決定（自作バイトコード VM など）は、学習の対象としても位置付けられるからである。

## 検討した代替案

- **Perl の構文と文脈依存の意味論を受け継ぐ**: 設計者の好みには合う。しかし、文脈によって意味が変わる構文（スカラー文脈とリスト文脈、暗黙の `$_`）は、LLM にも人間にも誤りの原因になり、「LLM が誤りなく生成できる」という基準に反するので採らない。Perl から受け継ぐのは哲学と、テキスト処理・ワンライナーの得意さとする。
- **TMTOWTDI（やり方は複数ある）を採る**: 書き手が LLM の場合、書き方の自由は出力の揺れになり、差分の確認と改造後の検査を難しくする。Python の「やり方は一つ」に倣い、同じ役割の構文を必要な理由なく増やさない原則を採る。
- **利用者をプログラマに限る**: LLM がコードを書く前提では、利用者に言語の習得を求める必要が薄い。利用者を限らない方が、表向きの目的の対象が広がる。
- **利用者の読みやすさを設計原則の最下位に置く**: 当初の草稿の順序。番号で機械的に判断すると、「少ない記述」や「やり方は一つ」のために、プログラマでない利用者が権限や結果を理解しにくくなる判断を許してしまうので改めた。
- **「改造しても契約が残る」を原則とする**: 当初の草稿の文言。LLM が実装と契約を同時に変えた場合、変更後の契約で検査が通っても以前の契約を守ったことにはならない。そのため、既存の契約への適合と契約そのものの変更を区別して示す原則に改めた。

## 帰結

- 記述量の少なさより検査と診断の明確さを優先する設計原則が導かれ、実質的な目的（型システム・エフェクトの学習）と整合する。
- エフェクトは、学習の対象であると同時に、利用者がコードを読まずに権限を確認するための情報になる。エフェクトの設計は、プログラマでない人に見せる形まで含めて考える必要がある。
- 構文は設計者の好みでなく、LLM の生成精度と読みやすさで選ぶ。生成・修正の成功率は、期待結果の達成まで含めて試作で測る（OPEN-012）。
- 契約の変更と権限の差分を、区別して利用者に示す方法を決める必要がある（OPEN-015）。
- 利用者がコードに触る箇所（文字列の書式など）は、プログラマでない人にも扱える形にする必要がある。
