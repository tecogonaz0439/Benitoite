# 0066. 明示遅延は `lazy { ... }` と `Lazy.force` で書き、本体は純粋な式に限る

- 状態: 採択
- 日付: 2026-09-26
- 関連章: [評価意味論](../01-spec/01-08-evaluation.md), [型システム](../01-spec/01-06-type-system.md), [構文](../01-spec/01-02-syntax.md), [字句構造](../01-spec/01-01-lexical.md)
- 関連する未決事項: なし

## 背景

評価は正格であり、遅延は明示の構文で選ぶ（[設計メモ](../sources/fp-language-design.md) 1、[評価意味論](../01-spec/01-08-evaluation.md)）。最小実行版には遅延の構文がなく、評価を遅らせるときは引数のないラムダで包む。ラムダは呼ぶたびに本体を評価するので、一度だけ計算して結果を使い回すことはできない。

## 決定

1. `lazy { ... }` は、ブロックを評価せずに `Lazy[T]` の値を作る。`Lazy.force(l)` は、最初の呼び出しでブロックを評価し、その結果を覚えて返す。二度目以降は、覚えた結果を返す。`lazy` をキーワードにする。
2. `lazy` のブロックは、エフェクトを持たない（純粋な）式でなければならない。IO を行う式を書くと型検査の誤りとし、診断は引数のないラムダを使う書き方を修正案として示す。
3. `Lazy.force` はエフェクトを持たない。

## 検討した代替案

- **本体で IO も行えるようにする**: 本体のエフェクトを `Lazy.force` の呼び出しのエフェクトにする（`Lazy[T, E]`）。書けるものは広がる。しかし、IO が起きる時期が、最初に `Lazy.force` を呼んだ位置で決まり、ソースの書いた位置から読み取れなくなる。型も複雑になる。
- **`lazy` と `delay` を分ける**（[設計メモ](../sources/fp-language-design.md) 0.3・1 の `lazy`・`delay`・`force`）: 遅延の値を作る構文が二つになる。同じ役割の構文を増やさない（原則 5）ので、作る構文を `lazy` の一つにし、評価する操作を `Lazy.force` にした。
- **v1 に入れない**: 同じ役割の構文を増やさない（原則 5）。しかし、結果を覚えるには `Ref` を使うことになり、`Ref` の操作は IO なので、純粋な関数の中で使えない。

## 帰結

- 本体が純粋なので、いつ `Lazy.force` を呼んでも、何度呼んでも、結果は同じである。結果を覚えることは、観測できる振る舞いを変えない。
- 本体の実行時エラーは、最初に `Lazy.force` を呼んだ時点で起きる。
- IO を遅らせるときは、引き続き引数のないラムダを使う。
