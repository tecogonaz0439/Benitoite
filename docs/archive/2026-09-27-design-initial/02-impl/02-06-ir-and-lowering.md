# 中間表現と脱糖

## 目的と範囲

処理系が使うコア IR のデータ構造と変換工程、脱糖（desugaring）、パターンマッチのコンパイル、v1 で行う最適化。言語の意味を定義するコアは[コア計算と脱糖](../01-spec/01-12-core-calculus.md)が扱う。

現在の版は、最小実行版（[ロードマップ](../00-overview/00-03-roadmap.md)）の範囲だけを定める。最小実行版では最適化を行わない。

## 前提

処理系の中間表現はコア計算と同じ形であり、脱糖は[コア計算と脱糖](../01-spec/01-12-core-calculus.md)の規則 ⟦·⟧ を実装する（[ADR 0017](../decisions/0017-ir-in-core-calculus-form.md)）。脱糖の段は、型検査を通ったプログラムの AST と、名前解決と型検査の表を受け取る（[パイプライン](02-01-pipeline.md)、[ADR 0022](../decisions/0022-side-tables-keyed-by-node.md)）。

## 仕様

### 工程

【方針】脱糖の段は、次の二つの工程からなる。

1. 脱糖: AST を、コア計算と同じ形の中間表現（以下、コア IR）に移す。
2. 判定の木への変換: コア IR の `match` を判定の木に置き換え、コード生成に渡す中間表現（以下、下位 IR）を作る。

参照インタプリタ（[ADR 0018](../decisions/0018-reference-interpreter.md)）はコア IR を実行し、コード生成（[バイトコードとコード生成](02-07-bytecode.md)）は下位 IR を受け取る。

### コア IR

【方針】コア IR は、[コア計算と脱糖](../01-spec/01-12-core-calculus.md)の構文の値・計算・パターン・定義を、そのまま Rust の型（列挙型と構造体）で表したものである。

| 分類 | ノード |
|---|---|
| 値 | 変数、定数、トップレベルの関数 `f[T̄; Ē]`、組み込みの関数 `b[T̄; Ē]`、関数 `λ(x̄:Ā). M`、構成子を適用した値 `C[T̄](V̄)`、リスト `[V̄]` |
| 計算 | `return V`、`let x ⇐ M in N`、適用 `V(W̄)`、`if V then M else N`、`match V { p̄ ⇒ M̄ }` |
| パターン | `_`、変数、定数、`C(p̄)` |
| 定義 | `fn f[ᾱ; ρ̄](x̄:Ā) : B ! ε = M` |

- 各ノードは、型（値は A、計算は A ! ε）と、由来位置（[ソース管理と位置情報](02-02-source-and-spans.md)の「合成ノードの由来位置」）を持つ。型とエフェクトの求め方は、この節の後の表で定める。
- 変数は、定義ごとに重ならない番号で表す。脱糖で作る新しい変数も、ソースの名前から移した変数も、同じ数え上げから番号を振る。したがって、コア IR の中で変数の名前が衝突することはない。ソースの名前は、診断と読みやすさのために変数に添える。
- 組み込みの関数 `b` は、組み込みの表の項目を指す（[名前解決とモジュール読込](02-04-resolver.md)）。
- 演算子 `⊕_T`（[コア計算と脱糖](../01-spec/01-12-core-calculus.md)）は、演算子によって二通りに表す。`==` と `!=` は、それぞれ型パラメータを一つ持つ組み込みの関数 `eq` と `ne` の項目とし、オペランドの型 T を型の引数として `eq[T]`・`ne[T]` と書く。T は等値の型ならどの型でもよいので、型ごとの項目は作らない。コード生成は、T が基本型なら型ごとの比較の命令を、代数的データ型かリストなら構造を比べる命令を選ぶ（[バイトコードとコード生成](02-07-bytecode.md)）。そのほかの演算子（`+ - * / %`、`< <= > >=`、単項の `-`）は、オペランドの型が基本型のいくつかに限られるので、演算子とオペランドの型の組ごとに組み込みの表に用意した項目（`+` と `Int` の組など）を指す。
- プログラムは、定義の集まり（利用者のトップレベルの関数と、prelude のソースの関数）と、型の宣言の集まりからなる。定義は、名前解決の束縛の番号で識別する（[名前解決とモジュール読込](02-04-resolver.md)）。名前は表示のためだけに持つので、利用者の関数 `mapInto` と prelude のソースの補助の関数 `mapInto` のように名前が同じ定義も区別できる。トップレベルの関数の値 `f[T̄; Ē]` の `f` も、束縛の番号で定義を指す。構成子には、同じ型の中で 0 から数えた番号（タグ）を振る。

【方針】コア IR の各ノードの型とエフェクトは、次のように付ける。表の「元の式の型」は、そのノードを作った表層の式について、型検査の「式の型」の表に書いた型である。

| ノード | 型 | エフェクト |
|---|---|---|
| 変数 | 束縛したときの型 | — |
| 定数 | 定数の型 | — |
| `f[T̄; Ē]`、`b[T̄; Ē]` | 宣言の型（f は型検査の「宣言の型」の表、b は組み込みの表）の型パラメータを T̄ で、エフェクト変数を Ē で置き換えた型 | — |
| `C[T̄](V̄)` | `D[T̄]`（D は C を宣言した型） | — |
| `[V̄]` | 元の式の型 | — |
| `λ(x̄:Ā). M` | `(Ā) → B ! ε`。B は M の型、ε は型検査の「ラムダのエフェクト」の表の値 | — |
| `return V` | V の型 | 空集合 |
| `let x ⇐ M in N` | N の型 | M のエフェクトと N のエフェクトの和集合 |
| `V(W̄)` | V の型（関数の型）の戻り値の型 | V の型（関数の型）のエフェクト。V が `b[T̄; Ē]` なら上の行で置き換えた型のエフェクトであり、IO を行う組み込みの関数では IO を含み、演算子の項目では空集合である |
| `if V then M else N` | 元の式の型 | M と N のエフェクトの和集合 |
| `match V { p̄ ⇒ M̄ }` | 元の式の型 | 各分岐の本体のエフェクトの和集合 |

計算のエフェクトは、子の計算から順に下から求める。下位 IR で加える計算（後述）は、`case` は各分岐のエフェクトの和集合、`join k(x̄) = M in N` は M と N のエフェクトの和集合、`jump` は空集合とする。求めたエフェクトは、型付け規則で導けるエフェクトのうち最小のもの（C-Sub を使わないもの）であり、定義の本体のエフェクトは宣言したエフェクトに含まれる。含まれないことは、型検査を通ったプログラムでは起きないので、コア IR の検査器（後述）が処理系の不具合として検出する。

### 脱糖

【方針】脱糖は、[コア計算と脱糖](../01-spec/01-12-core-calculus.md)の「表層からの脱糖」の表を、構文ごとに一つの Rust の関数として実装する。`[T̄; Ē]` と `⊕_T` の T は、型検査の「型の引数」と「演算子の型」の表から読む（[型検査器](02-05-typechecker.md)）。

- パイプとプレースホルダは、[構文](../01-spec/01-02-syntax.md)の展開の規則をこの工程で適用してから移す。パイプの右辺が括弧の式なら規則 2 で `(e)(x)` と展開し、規則 1 のプレースホルダの有無は右辺の呼び出しの直接の引数だけで判定する（[ADR 0050](../decisions/0050-pipe-with-parenthesized-rhs.md)）。
- 型の表の型変数は、型検査器が `Unit` と空集合に置き換えてある（[型検査器](02-05-typechecker.md)）。
- 脱糖は、型検査を通ったすべてのプログラムについて成功しなければならない。表を引いて結果がないなど、脱糖を続けられないときは、処理系の不具合として報告する（[パイプライン](02-01-pipeline.md)）。

【方針】脱糖した結果は、`let` の右側が入れ子になった形（`let x ⇐ (let y ⇐ M in N) in P`）を含みうる。脱糖の段はこの形をそのまま残す。この形を平らにする変換は、[コア計算と脱糖](../01-spec/01-12-core-calculus.md)の結合則の向き（左辺から右辺）に当たるので行ってよいが、最小実行版では、コード生成が入れ子の形を扱う（[バイトコードとコード生成](02-07-bytecode.md)）。

### コア IR の検査器

【方針】コア IR に[コア計算と脱糖](../01-spec/01-12-core-calculus.md)の型付け規則で型が付くかを調べる検査器を作る。検査器は処理系のテストで使い、脱糖の結果に型が付かなければ処理系の不具合とする。これは、同章の「確かめる性質」の 1（脱糖の型の保存）を、テストで反例を探す手段になる（[処理系のテスト戦略](../07-quality/07-03-compiler-testing.md)）。

検査器は、V-Sub と C-Sub を、型が求められる位置（関数の引数、構成子の引数、リストの要素、`if`・`match` の分岐、`let` の右側と束縛した変数の型、ラムダの本体と戻り値の型、定義の本体と宣言した型）でだけ使う。その位置で、ノードの型が求められる型と等しいか、同章の `≤` の関係にあるか、ノードのエフェクトが求められるエフェクトに含まれるかを調べる（[ADR 0081](../decisions/0081-subsumption-on-computation-results.md)）。

網羅性の条件（C-Match）は、検査器では調べない。型検査器が検査済みである（[型検査器](02-05-typechecker.md)）。

### 判定の木への変換

【決定】`match` は判定の木（decision tree）にコンパイルする。コンパイルは分岐の順序を保ち、どの値についても、元の `match` で最初に照合する分岐と同じ分岐を選ぶ（[ADR 0026](../decisions/0026-match-to-decision-trees.md)）。

【方針】下位 IR は、コア IR から `match` とパターンを除き、次の計算を加えたものである。

| 計算 | 意味 |
|---|---|
| `case V of { C1(x̄1) ⇒ M1 \| … \| Cn(x̄n) ⇒ Mn \| _ ⇒ M }` | V の構成子で分岐し、構成子の引数を x̄i に束縛する。`_` の分岐は、並べていない構成子のときに選ぶ。すべての構成子を並べたときは省く |
| `case V of { c1 ⇒ M1 \| … \| cn ⇒ Mn \| _ ⇒ M }` | V が定数 ci と等しいかで分岐する。`_` の分岐は、並べていない定数のときに選ぶ。`Bool` で `true` と `false` を、`Unit` で `()` を並べたときは省く |
| `join k(x̄) = M in N` | N の中で、k を「x̄ を束縛して M へ跳ぶ先」として使えるようにする |
| `jump k(V̄)` | k へ跳ぶ。`jump` は、k を定めた `join` の N の末尾位置にだけ書ける |

【方針】変換は、分岐のパターンの行列から判定の木を作る。行列の各列は、照合する値を入れた変数（以下、列の変数）に対応する。行列の各行は、パターンの並び、選ぶ分岐の番号、束縛の記録（パターンの変数と、その値を入れた列の変数の組の並び）を持つ。列の変数の型は、最初の列では `match` の対象の型、構成子の引数の列では、構成子の宣言の引数の型を、分岐した列の型（`D[T̄]`）の型引数 T̄ で置き換えた型である。最初の行列は、`match V` の V を列の変数とする 1 列からなり、分岐ごとに 1 行を元の順に持ち、束縛の記録は空である。

1. 行列に行がなければ、処理系の不具合として報告する。網羅性の検査（[型検査器](02-05-typechecker.md)）を通った `match` では、行のない行列は生じない。
2. 最初の行がワイルドカードと変数だけからなれば、その行の分岐を選ぶ葉にする。このとき、最初の行の変数のパターンごとに、変数とその列の変数の組を束縛の記録に加える。
3. そうでなければ、最初の行でワイルドカードでも変数でもないパターンを持つ列のうち、最も左の列 c を選ぶ。まず、列 c が変数のパターンである行ごとに、変数と列 c の変数の組を束縛の記録に加え、その行の列 c をワイルドカードに置き換える。この後、列 c の各行はワイルドカードか、構成子（または定数）のパターンである。
4. 列 c の型が代数的データ型なら、構成子で分岐する `case` を作る。
   - 列 c に現れる構成子ごとに、タグの順に分岐を作る。構成子 C の引数が n 個なら、新しい変数 y1, …, yn を作って C の分岐の引数に束縛する。その分岐の行列は、列 c が C のパターンの行とワイルドカードの行を元の順に残し、列 c を n 個の列 y1, …, yn に置き換えたものである。C のパターンの行ではその引数のパターンを、ワイルドカードの行では n 個のワイルドカードを置く。
   - 型の構成子のうち列 c に現れないものがあれば、`_` の分岐を作る。その行列は、列 c がワイルドカードの行だけを元の順に残し、列 c を取り除いたものである。
5. 列 c の型が基本型（`Int`・`String`・`Char`・`Bool`・`Unit`）なら、定数で分岐する `case` を作る。
   - 列 c に現れる定数ごとに、最初に現れた順に分岐を作る。その分岐の行列は、列 c がその定数の行とワイルドカードの行を元の順に残し、列 c を取り除いたものである。
   - 並べていない値がありうるとき、すなわち型が `Int`・`String`・`Char` のとき、`Bool` で `true` と `false` の一方しか現れないときは、`_` の分岐を作る。その行列は、列 c がワイルドカードの行だけを元の順に残し、列 c を取り除いたものである。
6. 各分岐の行列から、1 に戻って木を作る。

行は、分岐するたびに束縛の記録を引き継ぐ。葉では、その行の束縛の記録にある組ごとに、パターンの変数に列の変数の値を束縛する `let x ⇐ return y` を、記録の順に本体の前に置く。3 で束縛を記録するので、列を取り除いたり構成子の引数の列に置き換えたりしても、変数のパターンの束縛は失われない。

`String` の定数で分岐する `case` は、`String` の `==` で順に比べる。定数どうしの等しさは、`==` の意味に従う（[コア計算と脱糖](../01-spec/01-12-core-calculus.md)）。

【方針】複数の葉が同じ分岐の本体を選ぶときは、本体を `join` で一度だけ定め、各葉からは `jump` で跳ぶ。`join` の引数は、その分岐のパターンが束縛する変数を、パターンの中で左から現れる順に並べたものである。各葉からの `jump` は、その葉の束縛の記録で各変数に当たる列の変数を渡す。一つの葉からしか選ばれない本体は、その葉に直接置く。`jump` は呼び出しと違い、継続を伸ばさず、関数の値も作らない。分岐の本体が末尾位置にあれば、跳んだ先の本体も末尾位置にある。

### 最適化

【方針】最小実行版では、中間表現の最適化を行わない。v1 以降に最適化を加えるときは、[コア計算と脱糖](../01-spec/01-12-core-calculus.md)の「置き換えてよい等式」の向き（左辺から右辺）に従う変換と、観測できる振る舞いを変えないことを示せる変換に限る。
