# X4（3cc9d0b）のレビュー

## まとめ

重大な所見はありません。H12（文字列の対象の中身は正しい UTF-8）は 3cc9d0b の版で成り立っており、正しくない UTF-8 の `&str` を作る経路は見つかりませんでした。unsafe の書き方、heap-verify の扱い、文書もおおむね周りと合っています。以下の所見はどれも小さなもので、直さなくても取り込んでよいと判断します。

なお、作業ツリーは HTTP の作業が変えている最中なので、コードはすべて `git show 3cc9d0b:<path>` で読みました。

## 確かめたこと

### 1. 安全性（H12）

文字列の対象（`ObjKind::Str`）の中身を書く経路を、事前点検の結論に頼らず洗い出しました。

- **作る関数**: `core.rs` で `ObjKind::Str` を使うのは次の二か所だけです。
  - 343 行の `alloc_str` は `&str` を受け取り、`alloc_byte_data` に渡します。
  - 346 行の `alloc_str_parts` は `&[&str]` を受け取ります。合計の長さを確保の前に照合し、食い違えば `Stop::Internal` を返して確保しません。各部分をそのまま写すので、正しい UTF-8 をつないだ結果も正しい UTF-8 です。
- **`alloc_byte_data`（399 行）**: 種類を引数に取りますが、非公開です。本番で `Str` を渡すのは `alloc_str` だけで、ほかは `alloc_bytes` の `Bytes` とテスト（tests.rs:29）だけです。
- **公開の層（ctx.rs 441〜469 行）**: 公開の層は内部の層に `&str` しか渡せません。
  - `alloc_str_utf8` は `from_utf8` で確かめてから渡します。
  - `alloc_str_buf` は Rust の `String` を渡します。`build.rs` の `StrBuf` も、ヒープの外の層も `unsafe` を書けません（ワークスペースの `unsafe_code = "deny"`。ヒープの外に `unsafe` はありません）。
- **書き換え**:
  - 中身への可変の借用を渡すのは `alloc_bytes_with` だけで、種類は `Bytes` に固定です。
  - `cell_set`・`with_host_mut`・`reuse_ctor` は `Cell`・`Host`・`Fields(Ctor)` に限ります。マーク・スイープの `reuse_ctor` は `Ok(None)` を返すだけです。
  - 頭の `kind` は `Cell` でない欄で、確保のとき（296 行）にしか書きません。
- **頭の長さを書き換える箇所**: core.rs:1099 と 1105 の二つは、`cfg(all(test, feature = "heap-verify"))` のテストにしかなく、対象はセルです。
- **回収と復元**: 回収は対象を動かしません。毒（`0xDB`）で埋めるのは heap-verify の構成で解放した後だけです。死んだ対象の読み出しは `checked_object` が先に止めます。heap-verify のない構成では H1 の契約に頼る点は、変更の前と同じです。`Slot` から値に戻す処理は寿命を付け直すだけで、中身に触れません。
- **内部の層のほかのファイル**（alloc・layout・mark_sweep・verify・probe）: `Str` の中身を書く箇所はありません。
- **heap-per-object・gc-mark-sweep の構成**: 作る経路は同じです。
- **テスト**: 正しくない文字列の対象を作るのは、新しいテスト（`#[cfg(feature = "heap-verify")]` 付き）だけです。ほかの `str(...)` の呼び出しは、作る関数を通した値か、種類の違う値（`None` を期待）だけを読みます。heap-verify のないビルドで正しくない対象を `str` で読むテストはありません。

### 2. unsafe の書き方

- 新しいブロックは `from_utf8_unchecked` の一つの操作だけを含み、直前に `// SAFETY:` があります。
- 一覧の範囲は `mod.rs:4` と `core.rs:2` の両方で「H1〜H12」に直っています。
- H12 は二行の形で周りと揃っています。

### 3. heap-verify の扱い

- `record_fault(CorruptHeader, …)` と `None` を返す形は、`checked_object`（184〜203 行）と同じ作りです。新しい `HeapFaultKind` は足していません。
- VM は `dispatch.rs:1898`〜`1958` で、区間の後と安全点ごとに `take_fault` を見て `Stop::Internal(fault.detail)` にします。`serve_io` も同じです。記録した不具合は止める処理に届きます。

### 4. 文書

- 02-09 の新しい段落（25 行）は、既存の 106 行（確かめは文字列の値を作る API に集める）と食い違いません。
- 07-03 の表の行と、CHANGELOG の Unreleased に足した `### Changed`（Incompatible changes と Fixed の間）は、実装と合っています。
- 「遅かったのを直した」とは書いていないので、補足の決まりにも合っています。

## 所見（重大な順）

### 1. SAFETY のコメントが前提を混ぜている（`core.rs:537`）

- **問題**: `from_utf8_unchecked` が前提とするのは、正しい UTF-8 であることだけです（H12）。寿命と別名の条件（H1・O3・O4）は、直前の `from_raw_parts`（527〜528 行）の前提で、そちらで既に引いています。また heap-verify の構成では、直前に確かめ済みであることに触れていません。
- **直し方の案**: 「SAFETY: H12。作る経路だけが中身を書き、どれも正しい UTF-8 を写す。heap-verify の構成では直前に確かめた。」のように、この操作の前提に絞る。
- **推奨**: 直さなくてよい（依頼文が引き方を指定しており、引きすぎで害はない）。

### 2. H12 の二行目の「守る側」の書き方（`mod.rs:30`）

- **問題**: 「内部の層が守る」としたうえで、「外部のバイト列は公開の層の `alloc_str_utf8` が確かめてから渡す」と書いています。実際には、内部の層の `alloc_str` が `&str` しか受け取らないので、公開の層は確かめずに渡す手段を持ちません。不変条件を保証しているのは、型と内部の層です。今の文は、公開の層の確かめを外すと H12 が破れると読めます。
- **直し方の案**: 「型と内部の層が守る。`Str` の中身を書くのは `alloc_str`（`&str` を写す）と `alloc_str_parts`（`&str` の部分を写す）だけで、どちらも `&str` しか受け取らない。」
- **推奨**: 直すとよい（次にヒープに触れる作業でよい）。

### 3. 新しいテストの置き場所と見出しのコメント（`core/tests.rs:2`、`22〜36`）

- **問題**:
  - 新しいテストは、既存のコメント「作成時の関門: 既存のヒープのテストはない。下の各テストは…」（38〜39 行）より上にあります。読む順では、関門のコメントが二つ並びます。
  - ファイルの先頭は「H12 を確かめる」としていますが、このテストが確かめるのは、heap-verify が H12 の破れを見つけることです。作る経路が H12 を保つことは、既存の `object_kinds_headers_and_payloads` と ctx.rs の `r06_strings_bytes_and_fields_preserve_contents_and_check_kinds` が確かめています。
- **直し方の案**: テストを `Dropped` の定義の後、または末尾へ移す。先頭の行を「H12 の検証の構成での検出」のように限る。
- **推奨**: 直さなくてよい。

### 4. 新しいテストが不具合の出どころを特定していない（`core/tests.rs:28〜35`）

- **問題**: `str` を呼ぶ前に不具合が記録されていないことを確かめていません。そのため、記録が `alloc_byte_data` から来ても通ります。現状の確保は不具合を記録しないので、実害はありません。
- **良い点**:
  - test-audit の関門の答えはコメントにあります。
  - 直す前に失敗したことを報告で確かめています（`None` は返すが記録しなかった）。
  - 注入口を足していません。
  - heap-verify のない構成ではコンパイルしません。
- **直し方の案**: `str` の前に `assert!(core.take_fault().is_none());` を一行足す。
- **推奨**: 直さなくてよい。

### 5. 参考（X4 の範囲の外）: 題材の時間が見込みに届いていない

- **問題**: 報告の測定は中央値 0.78 秒で、Q5 の見込み（0.1 秒前後）と X1 の前の 0.07 秒のどちらにも届いていません。X4 の正しさの問題ではありません。ただ、`Regex.findAt`・`spanAt` を一致ごとに呼ぶ形（regex.rs:293〜321）に、まだ一致ごとの費用があるか、ほかの所で全体に比例する処理が残っている可能性があります。0.0.2 と比べると約 10 倍遅いままです。
- **直し方の案**: X1 を閉じる前に、リリースのビルドで `sample` を取り、残りの内訳を確かめる。CHANGELOG と Q5 の記述は、数字を書かない今の形でよい。
- **推奨**: 直すとよい（X4 ではなく X1 の確認として）。

### 6. 参考: check.sh の構成では 2 乗の時間が残る

- **問題**: `scripts/check.sh` の通常の検査は heap-verify を有効にするので、借りるたびの確かめと 2 乗の時間が残ります。02-09 と 07-03 の記述から読み取れ、補足で大きな題材をテストに足さないと決めてあるので、問題はありません。
- **推奨**: 直さなくてよい。

## 結論

H12 は成り立っており、取り込んでよいと判断します。直すとよいのは所見 2（H12 の二行目の書き方）と所見 5（X1 の時間の内訳を確かめること）の二つで、ほかは直さなくてよいものです。
