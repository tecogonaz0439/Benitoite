# X3（f6b9718）のレビュー

## まとめ

重大な誤りは見つからなかった。除くヘッダの判定、OPTIONS の絶対形を `*` にすること、`#` の 400 の三つは、決めた規則にも、study-202.md 2 節の RFC の引用にも合っている。直すべきものは CHANGELOG の一項目だけである。そのほかは、計算量、テストの揺れにくさ、文言の細部についての「直すとよい」である。

## 所見（重大な順）

### 1. CHANGELOG の Fixed の OPTIONS の項目が、方法の条件を落としている【直す】
- 場所: `CHANGELOG.md` 40 行
- 問題: 「An absolute request target with no path or query component, such as `OPTIONS http://host:8001`, now gives the handler `path` `*`」と書いてある。これだと、`GET http://host` を含む、どの方法でも `*` になると読める。実装（`http.rs` 1028 行の `method == "OPTIONS"`）と 03-09 は、大文字の `OPTIONS` に限っている。
- 直し方の案: 「An uppercase `OPTIONS` request whose absolute target has no path or query component, such as `OPTIONS http://host:8001`, now gives … Other methods, and targets with `/` or a query component (including a trailing `?`), keep the previous behavior.」とする。

### 2. 除くヘッダの判定が、ヘッダの数の 2 乗の手間になる【直すとよい】
- 場所: `crates/benitoite/src/runtime/io/http.rs` 1107〜1115 行（`replaced_response_header`）と、1150・1162 行の呼び出し
- 問題: 判定の関数を、ヘッダ一つごとに 2 回（長さの計算と書き出し）呼んでいる。そのたびに、すべてのヘッダと、すべての `connection` の値を走査する。手間はおよそ「ヘッダの数 ×（ヘッダの数 ＋ `connection` の値のバイト数）」になる。前の版は、ヘッダの数に比例していた。
  - `Http.respond` は同期で動く組み込みの関数で、その間は中断も効かない。台本が数十万個のヘッダを渡すと、数秒から数分止まる。
  - 遠くのサーバから写したヘッダ（`Http.send` の応答を中継する使い方）では、数が限られるので実害は小さい。
  - 「上限の検査より前に確保しない」という制約は、ここでは守る意味が薄い。呼び出し元の `http_server.rs` の `read_pairs` が、検査の前にすべてのヘッダを `Vec<(String, String)>` に写しているからである。
- 直し方の案: `response_bytes` の先頭で一度だけ走査し、`connection` の値の要素を `Vec<&str>` に集める。大きさは、既に確保した入力より小さい。集めた要素を小文字にそろえて並べ替え（または `HashSet`）、各ヘッダの判定を対数か定数の手間にする。判定の結果を `Vec<bool>` に残して、長さの計算と書き出しで使い回してもよい。`connection` の項目が一つもないとき（ふつうの場合）に、それ以上走査しない早道を設けるだけでも、ふつうの場合はヘッダの数に比例する手間に戻る。

### 3. 100-continue のテストの時間の検査と、メッセージのない検査【直すとよい】
- 場所: `crates/benitoite/src/runtime/io/http/tests.rs` 200 行、98〜101 行、136〜139 行
- 問題:
  - 200 行の `assert!(started.elapsed() < 10s)` は、性質を確かめていない。負荷が高いときに、正しい実行を落とすだけである。各待ちは 8 秒の期限で抑えてあるが、その外にある 200 ms の待ちと、最後の `join` は数えていない。10 秒の目安は、作業で測って報告すれば足りる（X3b の 5 回の実行は約 1.2〜1.4 秒）。
  - 埋め直し（`fill`）の直後の `accept` は、`matches!(…, (AcceptStep::Waiting, None))` を確かめている。しかしメッセージがない。埋め直しと `accept` のわずかな間に空きが戻ると、100 を書き切って `Accepted` が返る。そのとき失敗の理由が読めない。136 行がこれに当たる。98 行は、`Accepted` が返れば同じく理由のない失敗になる。
- 直し方の案: 200 行を消す。消さないなら、最後の `eprintln!` で時間を出すだけにする。98・136 行には、「100 を書き切った（埋め直しの後に送りのバッファへ空きが戻った）」と分かるメッセージを付ける。

### 4. 100-continue のテストの揺れにくさと時間（参考）【直さなくてよい】
- 作りについて:
  - 二つの点で、待ちの経路を確かめる形は妥当である。一つは、1 バイトの書き込みで `WouldBlock` を確かめた直後に `accept` を呼ぶこと。もう一つは、300 ms 書けない状態が続くまで埋め直すこと（85 行付近）。
  - 揺れる余地は、埋め直しと 100 の書き込みの間（数マイクロ秒）に空きが戻る場合に限られる。相手は読まないので、受けの窓は 0 である。空きが戻るのは、窓の探り（zero-window probe）への応答や、受け手が受けのバッファを詰めて窓を開く場合くらいで、まれと見込む。
  - 158 行の「200 ms の間に準備が来ない」という検査も、ほとんど揺れない。Linux の `tcp_poll` は空きがある程度溜まるまで書き込みの準備を返さない。わずかな空きでは誤って起きない。ただし、これは机上の見込みである。
- 時間について:
  - 300 ms の静止の待ちを、少なくとも 3 回（89・96・135 行。96 行は頭の到着の待ちのループの回数だけ増える）くり返す。1 回の実行は約 1.2 秒になる。並列の負荷や gc-stress の段で 2〜3 倍になっても、8 秒の期限に収まる見込みで、長いテストにする必要はない。
  - 静止の待ちを 150 ms ほどに縮めても、確かめる性質は変わらない。
- 確かめる性質について: 書き切れないときに `Waiting` を返すこと、読み込みを進めないこと、`WRITABLE` を登録すること、書き込みの準備で再開すること、100 を一度だけ送ることの五つを、すべて確かめている。test-audit の観点でも、`// 関門:` のコメントと、本番の型にテストのための欄を加えないことが守られている。
- 未確認の点: 実行は macOS だけである。Linux（送りのバッファの自動の拡大、`tcp_collapse`）での揺れは確かめていない。Linux で検査を走らせる環境があれば、一度走らせるとよい。

### 5. 言語リファレンスの要求の対象の箇条書きの順序と「still」【直すとよい】
- 場所: `docs/reference/benitoite.md` 809 行
- 問題: 「An absolute target with neither a path nor a query component, such as `OPTIONS http://host`, gives `path` `*`」と、方法を問わない形で先に書いている。方法の条件は文の最後で補っており、所見 1 と同じ誤読を招く。また「still give」は前の版との比較の言い方で、リファレンスの文には合わない。
- 直し方の案: 「For an uppercase `OPTIONS` request, an absolute target with neither a path nor a query component (`OPTIONS http://host`) gives `path` `*` and an empty `query`; `OPTIONS http://host/`, `OPTIONS http://host?x=1`, `OPTIONS http://host?`, and other methods give `path` `/`.」とする。

### 6. 03-09 の `#` の 400 の理由が、authority 形と `*` の形の文法を引いていない【直さなくてよい（直すなら一言）】
- 場所: `docs/design/03-interop/03-09-network.md` 126 行（【決定】要求の対象が `#` を含めば…）
- 問題: 本文は「形を問わず」とし、実装も `CONNECT h:443#f` と `OPTIONS *#f` を拒んでいる（テストもある）。ところが理由は、RFC 9112 §3.2.1・§3.2.2（起点形・絶対形）だけを引いている。
- 直し方の案: 理由に「authority 形（§3.2.3）と `*` の形（§3.2.4）の文法も `#` を含まない」と一言足す。

## 照らし合わせて問題のなかった点

- 除くヘッダ:
  - 名前が `connection` の項目を、大文字と小文字によらずすべて読む。各値をカンマで区切り、要素の前後から空白と水平タブだけを除き（`trim_matches([' ', '\t'])`）、空の要素は飛ばす。比べるときは `eq_ignore_ascii_case` を使う。RFC 9110 §5.6.1・§5.6.3・§7.6.1 に合う。
  - 長さの計算と書き出しで、同じ判定を使う。上限の検査（`CheckedLen::bytes`）より前に、要素の数に比例する確保はしない。
  - 処理系が付ける `connection: close` は変えない。
  - テストは、複数の `connection`、空の要素、空の名前のヘッダが残る場合、U+00A0 で一致させない場合を、`response_bytes` の入口から確かめている。
- OPTIONS: `*` にするのは、`path.is_empty()`（authority の後に `/` も `?` もない）で、方法が大文字の `OPTIONS` のときだけである。`http://h?` は `?` がクエリの部分になるので `/` のまま。§3.2.4 の「empty path and no query component」と §3.3 に合う。https も同じ扱いになる。表には、今の行を変えずに 6 行を足している。
- `#` の 400: 判定は、httparse から対象を取り出した直後、`origin_target` より前（`http.rs` 826〜828 行）にあるので、起点形・絶対形・authority 形・`*` のすべてに当たる。応答は、今の文法の誤りと同じ `ParseStep::Reject(400)` → `error_response` の経路で作る。`%23` は受け付け、符号化は戻さない（表に行がある）。
- 03-09:
  - 66 行の `path` の説明に、`*` の例外を足している。125 行の絶対形の項に、例外と §3.2.4・§3.3 の理由を足している。131 行の除くヘッダの一覧と、§7.6.1・§7.8 の理由も、実装と合う。
  - 見出しは変えていない。
- CHANGELOG の Incompatible changes の表の行（27 行）と、Fixed の除くヘッダの項目（39 行）は、実装と合う。
- 規約:
  - テストの外に `unwrap`・添字を加えていない。
  - コメントは日本語で書き、根拠を「（設計書 03-09「サーバの接続と要求の読み方」）」と RFC の節で示している。保管した実装プランも作業の ID も引いていない。
  - 細かい点として、1102〜1103 行のコメント「chunked の区切りと、閉じる接続や切り替えなしの実際に合わないヘッダを除く」は少し読みにくい。「chunked の区切りのヘッダと、接続を閉じ切り替えをしない実際と食い違うヘッダを除く」などにすると読みやすい（直さなくてよい）。
