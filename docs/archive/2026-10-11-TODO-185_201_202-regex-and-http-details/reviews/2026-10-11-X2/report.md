# X2（90c52a5）のレビュー

## 結論

本番のコードの変更（`crates/benitoite/src/runtime/run.rs` 408〜415 行）は、計画（decisions.md Q2 と依頼文の補足）のとおりで、正しいと判断した。重大な所見はない。直したほうがよいのは、文書の 2 点（1・2）とテストの抜け 1 点（3）である。cargo は走らせていない。所見は、コードと文書を読んで確かめた結果である。

## 確かめたこと（問題なし）

- **印を読む位置**: 読むのは `run_vm_entry` の、最後の転送（`for port in [&mut rt.stdout, &mut rt.stderr]`）の後、`heap_stats` の前の一か所である。
  - `rt.interrupt` は、`run_epoch` が `InterruptLease` で一時的に別のものに差し替える。差し替えは `Drop` で戻るので（`vm/dispatch.rs` 155〜166 行）、panic のときも含め、`vm.run` を抜けた後は元の読み口に戻っている。
  - シグナルの登録は `rt` が持っている。そのため、読む時点まで登録が残っている。
- **書き換える範囲**: 書き換えるのは `Returned | MainError` のときだけである。
  - `worker_bug` と書き出し用のスレッドの panic（`WriteFailure::Panicked`）は、どちらも読む位置より前に `end` を `Internal` にしている。したがって確実に除かれる。
  - `start_main` の失敗は `Stopped` になる。`Exited`・`CheckFailed` も条件に当たらない。
- **転送の失敗との関係**: `flush_failure` は `Returned | MainError` のとき、`exit_code = 1` にして `write_failed` を積む。中断の要求のときは、同じ `write_failed` を積むだけである。
  - 書き換えの後は「報告を残し、終了状態は 130」になり、もともと中断の要求で止まった場合と同じ報告になる。02-09 の転送の失敗の箇条とも合う。
  - `main_error = None` にするので、CLI（`cli/mod.rs` 689 行）は `Result.Error` の文字列を書かない。
- **テストの実行器**: `run_test` も同じ関数を通る。`EndKind::Interrupted` の分岐（`test_runner/mod.rs` 420 行）が、結果の行を書かず数にも入れずに `Flow::Interrupted` を返し、要約は interrupted になる。
  - 捕らえる出力先は詰まらないので、テストの実行器では転送の待ちの窓は事実上ない。
- **他の呼び出し元**: 埋め込みの API（`run_program`）は、`NoInterrupt` を渡せば `requested()` が偽なので変わらない。テスト用の `run_vm` も同じ関数を通る。
- **プロセスのテストが揺れない理由**: どの時点で SIGINT が届いても 130 になる。
  - `List.sort` は `@builtin`（PRIM）なので、ソートの途中で届いても、ソートの後に印を読む位置がない。最後に読む位置でだけ拾われる。
  - ソートの後に届いても、親が準備の行の後を読み始めるのは `kill` が終わった後である。2 MiB の転送はそれまで終わらないので、転送の後に読む印には必ず間に合う。
  - 仕組みは既存の `sigint_interrupts_tail_recursive_computation` と同じである。
  - 依頼文の補足が述べたとおり、転送の「前」に読む作りではこの保証が崩れる。後に読む今の作りが正しい。
- **規約**: コメントは日本語で理由と節を書いており、引いた見出し（02-09「中断の要求」「プログラムの実行の流れ」、02-11「テストの実行」、07-03「中断の要求のテスト（初回リリース版）」）はどれも実在する。本番のコードに `unwrap`・添字はない。大域の状態も増えていない。

## 所見（重大な順）

### 1. 印を読む場所の「だけ」の一覧に、テストの実行器が読む場所が抜けている【直すとよい】

- **場所**: `AGENTS.md` 226 行と `docs/design/02-impl/02-09-runtime.md` 309 行（「中断の要求」の最初の【決定】）。どちらも「読むのは VM の実行の区切りと、ランタイムが実行を終えるときの一度だけである」とある。
- **問題**: テストの実行器も、ファイルごと（`test_runner/mod.rs` 152 行）とテストごと（377 行）に、`SharedInterrupt::requested()` で同じ印を読んでいる。この食い違いは前からあったが、このコミットで同じ文を書き直したのに直っていない。
- **直し方の案**: 両方を同じ変更で、たとえば「読むのは、VM の実行の区切り、ランタイムが実行を終えるとき（一度）、テストの実行器がファイルとテストを始める前だけである」に直す。

### 2. テストの関数が値で終わった後に中断になったときの扱いが、02-11 と 06-04 に書かれていない【直すとよい】

- **場所**: `docs/design/02-impl/02-11-embedding.md` 66 行と `docs/design/06-tooling/06-04-test-runner.md` 133 行。どちらも「実行中のテストを止める手順で止め（取り消し）、それまでの結果を報告」とある。
- **問題**: このコミットで、値で終わったテスト（`Result.Error` で失敗したテストを含む）は、止める手順を通らずに中断として扱われるようになった。結果の行も、捕らえた出力も、数も報告しない。
  - 前の版では、このテストは成功（または失敗）として数え、次のテストの前に中断していた。
  - 一方、実行時エラー・確認の失敗・`Process.exit` で終わったテストは、印が立っていても失敗として報告される。終わり方によって扱いが分かれる。
  - 02-09 の新しい決定は「（テストではテストの関数）」と書くだけで、テストの実行器から見た扱いは書いていない。
- **直し方の案**: 02-11「テストの実行」の 66 行の後に、次の 1 文を足す。「テストの関数が値で終わった後に中断の印を見つけたときも（02-09「中断の要求」）、そのテストの結果を報告せず、数にも入れずに中断として終える」。06-04 は 02-11 を引くだけでもよい。CHANGELOG の項目にも、`test` では最後のテストを数えないことを短く足すとよい。

### 3. 「値で終わった以外の終わり方は書き換えない」ことと、転送の失敗の報告が残ることを、テストが確かめていない【直すとよい】

- **場所**: `crates/benitoite/src/runtime/run/tests/interrupt.rs` 101〜122 行と `run.rs` のテスト。
- **問題**: 足した単体テストは、`Returned`・`MainError` が `Interrupted` になる側だけを確かめている。
  - たとえば `matches!` の条件が `Stopped`・`Exited`・`Internal` まで広がる退行があっても、捕まらない。02-09 の「止める理由を後の出来事で置き換えない」に反するが、どのテストも失敗しない。
  - 転送の失敗と中断が重なったときに `reports` を残すこと（02-09 の転送の失敗の箇条に足した文）も、確かめていない。
  - 単体テストは印を最初から立てているので、「転送の後に読む」という位置も確かめていない。
- **直し方の案**: 既存の `writer_failure_and_panic_finish_with_the_required_reports`（`run.rs` 690 行〜）の表を広げる。
  - 書き出し先を、`write` の中で共有の `Arc<AtomicBool>` を立ててから `BrokenPipe` を返すものにする。転送の途中で SIGINT を受けた場合に当たる。読み口には同じ印を読む `Flag` を渡す。
  - 期待する結果は次のとおりである。
    - `Returned`・`MainError`: `Interrupted`・130・`main_error == None`・`reports` は R0201 の一件。
    - `Stopped`（`1 div 0`）: `Stopped`・1 のまま。
    - 書き出し用のスレッドの panic: `Internal`・3 のまま。
  - こうすると、転送の前に印を読む作りへの退行も捕まえられる。
  - ただし、この経路で `Flag::attach` が呼ばれるか（`RuntimeParts::real` を使っている）は、事前に確かめる必要がある。呼ばれて panic するなら、`attach` が `Ok(None)` を返す読み口を使う。

### 4. プロセスのテストは、シグナルの処理がとても遅く届く場合まで、理屈の上で保証しているわけではない【直さなくてよい】

- **場所**: `crates/benitoite/tests/interrupt_process.rs` 284〜310 行。
- **問題**: 130 になる保証は、「`kill` が終わってから、子のシグナルの処理が印を立てるまでの時間が、親が 2 MiB を読み、子が転送を終えるまでの時間より短い」ことに頼っている。実際には十分に成り立つし、既存のテストも同じことに頼っているので、揺れる心配は小さい。
- **直し方の案**: このままでよい。07-03 に書いた保証の範囲（「最後の転送の完了より前にシグナルを送ることを保証するが、`List.sort` の途中で届くことは保証しない」）も正確である。

### 5. 単体テストとプロセスのテストに重なりがある【直さなくてよい】

- **場所**: `test_entry.rs` 278〜308 行と `interrupt.rs` 101〜122 行。`interrupt_process.rs` の `Result.Error` の場合。
- **問題**: 同じ一か所のコードを、`run_program` と `run_test` の両方の入口から確かめている。プロセスのテストの `Result.Error` の場合も、単体テストの `main_error == None` と重なる。
- **判断**: それぞれに独立した危険があるので、残してよい。
  - `run_test` のテストは、印を読む位置を `run_program` だけに移す退行を捕まえる。
  - プロセスのテストは、本物のシグナルと転送の待ちを通る。
- 実装担当によれば、直す前の版で次のように失敗した（意図どおりの理由）。
  - 単体テスト: `Returned` になる。
  - プロセスのテスト: `Unit` を返す場合は 0、`Result.Error` の場合は 1 と `x\n` になる。
