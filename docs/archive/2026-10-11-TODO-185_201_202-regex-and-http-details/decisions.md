# 判断とその理由

調査（`study-201.md`・`study-202.md`）の問いの候補から、利用者から見える振る舞いを変える四つを設計者に尋ねた（2026-10-11）。設計者はどれも推奨を選んだ。残りの問いは、振る舞いの差が小さいか、作業の中の選び方なので、推奨どおりとした。検討した代替案と理由の詳細は、括弧の中の調査の節にある。

## 設計者に尋ねた問い

### Q1 繰り返す照合の区切り方（study-201 の 3.1 節・問い 1・3）

決定: 案 A。非公開の組み込みの関数を設け、`findAll`・`replaceAll`・`replaceAllWith`・`split` を `Regex.bnt` のループで書く。一致が 2^24 を超えるときは、値を作り終えた後に `List.append` の上限で止まり、報告の関数の名前は `List.append` になる。この変化を受け入れる。

理由: VM の呼び出しの区切りで中断・予算・取り消しを調べているので、一致の間で Ctrl-C・取り消し・`Task.withTimeout` が効く。VM を変えずに済む。先に数える走査を足すと時間が倍になり、止められない時間を延ばす。

代替案: 案 B（N 個ずつまとめて探す）は止められるまでの時間が N 倍になり型も複雑になる。今のまま（文書だけ）は TODO-201 の問題を残す。

### Q2 実行の終わりの中断の印（study-201 の 3.2 節・問い 4）

決定: `main` が値で終わった後（`Result.Error` を返したときを含む）に中断の印を一度読み、立っていれば中断の要求として終了状態 130 で終わる。実行時エラーや資源の不足で止まったときは変えない。

理由: 速い経路（`PRIM` の戻り）を変えずに、中断の要求を受けた実行が 0 で終わる窓をなくせる。実行時エラーで止まったときは既に止める手順に入っており、止める理由を後の出来事で置き換えない今の決まりに合わせる。

印を読む位置は、出力の最後の転送を終えた後とする（X2 の事前点検で決めた）。転送の前に読むと、転送の待ちの間に届いた中断の要求を読み落とし、0 で終わる窓が残るうえ、別のプロセスのテストが揺れる。止める手順は始めない（このときすべてのタスクは終わっている）。`main` が `Result.Error` を返していても、その文字列は書かない。

代替案: 今のまま（窓が残る）、`PRIM` の戻りごとに調べる（命令の振り分けの速い経路を変え、性能の関門の測定が要る）。

### Q3 要求の対象の `#`（study-202 の 3.3 節・Q3）

決定: 要求の対象が `#` を含めば 400 にする。互換性を壊す変更として CHANGELOG に書く。

理由: 起点形・絶対形とも文法が断片を許さず（RFC 9112 §3.2.1・§3.2.2、RFC 3986 §4.3）、RFC 9112 §3.2 は文法に合わない要求の行を 400 にし、直して処理しないことを勧める（SHOULD）。設計原則 1 にも合う。

代替案: 取り除く（hyper・nginx の挙動）。今まで通っていた要求は通り続けるが、文法に合わない入力を黙って直すことになる。

### Q4 応答から除く接続ごとのヘッダ（study-202 の 3.1 節・Q1）

決定: 今の 4 つ（`content-length`・`connection`・`transfer-encoding`・`trailer`）に加えて、`keep-alive`・`proxy-connection`・`te`・`upgrade` と、利用者の `connection` に挙げた名前を除く。

理由: 処理系は `connection: close` で置き換え、接続の切り替えをしないので、これらのヘッダは接続の実際と食い違う。RFC 9110 §7.6.1・§7.8 の送り手の規則に合う。426 の応答に `Upgrade` を付けられなくなるが、101 を送れないので実害は小さい。

代替案: `upgrade` だけ残して `connection: upgrade, close` を送る案、今のまま。

### Q5 文字列の値を借りるときの UTF-8 の確かめ（X1 の後の短い測定で分かった）

決定: ヒープの不変条件に「文字列の対象は正しい UTF-8 を持つ」を加え、文字列の値を借りるとき（`runtime/heap/core.rs` の `str`）は確かめずに `&str` にする。確かめは文字列の値を作る経路だけで行う。

理由: 作業 X1 の後の短い測定で、20 万の一致の `findAll`・`replaceAll`・`split` が、直す前の 0.07 秒から 18 秒になった。組み込みの関数が文字列の値を借りるたびに全体の UTF-8 を確かめ直すので、一致ごとに借りる形では全体が 2 乗の時間になる。作る経路は既に UTF-8 を確かめている（`&str` から作るか、`alloc_str_utf8` で確かめる。02-09「外部から受け取るバイト列を `String` にする操作」）ので、借りるたびの確かめは同じ事実を確かめ直しているだけである。ほかの文字列の操作も速くなる。

代替案: 一回の呼び出しで N 個ずつまとめて探す案（確かめの回数は 1/N になるが 2 乗のまま、止められるまでの時間が N 倍に延びる）、照合を一回の組み込みの呼び出しに戻す案（TODO-201 を残す）。

## 推奨どおりとした問い

- 内部の関数は二つにする（study-201 の問い 2）。捕獲グループつきの `findAt` と範囲だけの `spanAt`。理由: `replaceAll`・`split` は捕獲グループを要らず、範囲だけの探索の方が速い。
- `Regex.compile` の誤りの文面は、4 KiB を超えたら切り詰める（study-201 の問い 5）。理由: 言語に新しい上限を足さずに、文面の大きさだけを抑えられる。切り詰め方は作業で決め、設計書に書く。
- Q1 の延長として、`replaceAll` の結果が文字列の長さの上限（2^30 バイト）を超えるときも、組み立ての途中の関数（`String.join` など）で止まり、報告の関数の名前が `Regex.replaceAll` から変わることを受け入れる（X1 の事前点検で分かった）。理由は Q1 と同じで、止まるまでのメモリは上限の内で成功する呼び出しと同じ大きさで抑えられる。
- TODO-185 の `findAll` のグループの確保の点は、案 A で一回の操作が作る `Match` が一つになるので、解消したとして扱う（study-201 の問い 6）。`replaceAllWith` の計算量の点も、ループで書き直して確かめる。
- パスもクエリも空の `OPTIONS` の絶対形は、`*` として扱う（study-202 の Q2）。理由: RFC 9112 §3.3 で `OPTIONS *` と同じ対象 URI になる。方法が `OPTIONS` 以外なら今のまま `/` とする。
- 要求の対象の文法の検査を `#` より広げること（起点形が `/` で始まらない対象、httparse が通す文法の外の文字）は、この改造では扱わず、docs/todo の新しい項目にする（study-202 の Q4）。
- `100-continue` の 100 を書き切れない経路のテストは、サーバ側の送りのバッファを `WouldBlock` が返るまで埋めて作る（study-202 の Q5、T-a）。理由: 本番のコードを変えずに、OS のバッファの大きさに依存せずに通せる。
