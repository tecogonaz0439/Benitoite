# V1「ヒープの内部」のレビュー（コミット 42011c65）

読んだもの: `git show 42011c65` の差分と、同じコミットの `core.rs`・`core/mark_sweep.rs`・`ctx.rs`（テストの部分）・改造のディレクトリの decisions.md（Q3・R6・R8）・study.md（173 部 2.3 節）、実装担当の報告、事前点検。ビルドとテストは走らせていない。

結論: 正しさに関わる問題は見つからなかった。高・中の指摘はない。文書の細部の低い指摘が 5 件ある。

## 1. unsafe の正しさ

問題なし。

- 新しい `unsafe` は 3 箇所で、どれも操作は `as_ref` の一つだけである。`object_ids` の既定の構成（core.rs 185-186。O1・O4）、`object_id` の heap-verify の構成（core.rs 243-244。H1・H4・H5・O2・O4・O5）、番号が一周したときの戻し（mark_sweep.rs 165-166。O1・O4・M1）。引いた番号は、どれも core.rs か mark_sweep.rs の先頭の一覧にある。
- `object_id` の既定の構成は、既存の `header()`（既存の SAFETY）を通すだけで、新しい `unsafe` を持たない。heap-verify の構成は `checked_object` で生存と世代を確かめてから頭を読むので、O5「死んだ対象の検査は頭を読む前に行う」に合う。
- 解放した対象に `object_id` を呼ぶ可能性。本番のコードは `object_id` を呼ばない（`git grep` で確かめた。呼ぶのはテストだけ）。本番で頭を読む新しい経路は増えていない（`same_object` は番地の比較のまま）。テストでは、vm/tests.rs の回収の後の `object_id`（事前点検が挙げた 480-485 行・951 行）が、Trace の漏れがあるときに限り、既定の構成で解放した領域を読むようになった（前は番地を数に変えるだけで読まなかった）。V2 で直す予定のとおりなので、V2 を V1 の後に必ず取り込むこと（指摘ではなく注意）。

## 2. 通し番号

問題なし。

- 番号は `HeapCore::next_serial`（1 から）で、ヒープごとの状態に置いている。大域の状態の規約に合う。
- 番号は `allocator.allocate` より前に取り、`checked_add` が溢れたら `size_overflow()` で確保を失敗させる。計数器の更新は `objects.push` の後（core.rs 352）なので、確保器の失敗や `initialize` の途中の panic では番号を進めず、使われた番号が重ならない。64 ビットで一周しない。
- 既定の構成は頭（空いていた 24〜32 バイト目）、heap-verify の構成は `ObjectRecord` に置く。どちらも確保の時点で同じ値を書くので、二つの構成で意味は同じである。頭は両構成で 32 バイトのまま（core.rs 115 の表明が通る）。
- `free_object` の `swap_remove`（core.rs 679）では記録ごと移るので heap-verify の構成の番号は保たれ、既定の構成は頭にあるので移動の影響を受けない。テスト `identity_and_immediates` が、移った対象の番号を確かめている。
- `object_ids` の費用: 既定の構成で記録ごとに頭を一度読むようになったが、呼ぶのはテストだけである。heap-verify の `object_id` は `objects.borrow()` と添字を一度引くだけで、テストの構成だけの費用である。

## 3. 回収ごとの番号の印

問題なし。

- 新しい対象の印は 0（core.rs 332）で、回収の番号は 1 以上（初めの値 0 に 1 を足し、一周したときも 1 から始める）なので、新しい対象はどの回収でも未訪問とみなされる。
- 番号は `Marker` を作る前に `mark_epoch` に書く（mark_sweep.rs 173）ので、印付けの途中で panic しても、次の回収は別の番号を使い、途中まで付けた印を未訪問とみなす。掃き出しの途中（`free_object` の中の `Host` の drop など）で panic した場合も、残った対象は次の回収で印を付け直すので問題ない。
- 一周したときの戻し: `objects.get_mut()` の全対象の `word` を 0 にしてから 1 で始める。生きている対象はすべて並びにある（O1）ので漏れはない。届かない分岐で、テストがないのは事前点検のとおり妥当である。
- 掃き出しの判定は `word.get() != epoch` で、印付けの判定と対になっている。`failed` で戻る経路でも印を消さなくてよい。
- 「印 0 = 未印」を前提にする箇所: `git grep` で `word` の読み書きを探した。印を読むのは `Marker::mark` と掃き出しの一巡だけで、ほかは `core/tests.rs:102` の「確保した直後は 0」という表明だけである（今も成り立つ）。verify.rs・probe.rs・heap-per-object の経路は印を読まない。前提にする箇所はない。

## 4. same_object を番地の比較にしたこと

問題なし。`checked_object` を通すので、heap-verify の構成で古い参照を不具合として記録する働きと、即値で `false` を返す働きを保っている。以前の既定の構成の `object_id` も番地を数に変えたものだったので、結果は変わらない。本番の `runtime/map/tree.rs:455` の近道で頭を読まないことも保たれている。

## 5. テストの質

問題なし。

- `reachable_child_survives_collection_after_marking_panics`: 検証器が `trace` を呼ぶ回数を先に数えてから、その次の呼び出し（印付けの中）で panic させるので、heap-verify の構成でも検証器の中の panic で通ってしまうことはない。直す前のコードでは、親の印が 1 のまま残って子を辿らず、子が解放されるので、`object_ids().contains(&child_id)` の表明で落ちる（報告も両構成で落ちたことを確かめている）。中身を読む前に生存と不具合の有無を確かめ、解放した領域を読まない。差し込み口を加えていない。
- `identity_and_immediates`: 番地で番号を作る形に戻すと、再利用した番地の対象の `assert_ne` で落ちる（報告が確かめた）。heap-per-object の構成では番地の一致を表明しないよう `cfg` で分けている。
- 残りの 2 件は、番号を番地として使っていた箇所を値のポインタに改めたもので、確かめる内容は変わっていない。

## 6. 文書と規約

コメントに作業の ID（V1・Q3・R6 など）や保管した実装プランの節は書かれていない。`#[allow]` は増えていない。次の低い指摘がある。

### 6.1（低）M1 が「印 0 は未訪問」と一周のときの戻しを書いていない

- 場所: `crates/benitoite/src/runtime/heap/core/mark_sweep.rs` 7-8 行（M1）。
- 問題: 正しさは「新しい対象の印 0 は、どの回収の番号とも等しくない」ことに頼っているが、M1 にその条件がない。また M1 は「前の回収の印は消さない」と書くのに、一周のときの戻し（165-167 行）は全印を消し、その SAFETY が M1 を引いている。
- 直し方: M1 に「確保した対象の印は 0 で、回収の番号は 1 以上なので、確保した対象は次の回収で未訪問とみなす。番号が一周するときだけ、印付けの前に全対象の印を 0 に戻す」の趣旨を足す。

### 6.2（低）`ObjHeader` の `///` が通し番号を挙げていない

- 場所: `crates/benitoite/src/runtime/heap/core.rs` 98-99 行。
- 問題: 「種類、長さ、印、heap-verify の構成では確保の世代を持つ」のままで、既定の構成で頭に置いた `serial` を挙げていない。
- 直し方: 「既定の構成では確保の通し番号（heap-verify の構成では生存対象の記録に置く）」を足す。

### 6.3（低）`Heap::collect` の追記が強すぎる

- 場所: `crates/benitoite/src/runtime/heap/ctx.rs` 335-336 行。
- 問題: 「`roots` が辿らなかった `Slot` を……読むと解放した対象を読む」と断定しているが、辿らなかった `Slot` でも、即値を持つものや、対象が別の根から辿れるものは読んでも解放した対象を読まない。mod.rs の「安全の範囲」（根に入れず、根から辿れる対象の中にもない `Slot`）とも食い違う。読んではならない、という契約の部分は H4 のとおりでよい。
- 直し方: 「読むと、解放した対象を読むことがある」とするか、mod.rs と同じ条件で書く。

### 6.4（低）heap-verify の `object_id` が記録の食い違いを黙って `None` にする

- 場所: `crates/benitoite/src/runtime/heap/core.rs` 245-250 行。
- 問題: 頭の添字が並びの範囲外か、記録のポインタが対象と違うとき（O1 が破れたとき）に、不具合を記録せず `None` を返す。検証の構成はこうした食い違いを見つけるためのものであり、また decisions.md の Q3 のとおり TODO-220 で `ObjId` を本番の比較の鍵に使うと、黙った `None` は原因の分かりにくい結果の違いになる。
- 直し方: 食い違いのときに `self.record_fault(HeapFaultKind::CorruptHeader, ...)` を呼んでから `None` を返す（文言は既存の表に合わせる）。

### 6.5（低）02-09 の一つ目の追記に「理由:」がない

- 場所: `docs/design/02-impl/02-09-runtime.md` 25 行（「根の列挙の漏れにより解放された対象への参照は……既定の構成では見つけない」）。
- 問題: AGENTS.md「決定の書き方」は決定の直後に理由を書くとしているが、この【決定】には理由がない（27 行の `ObjId` の段落にはある）。
- 直し方: 「理由: 既定の構成で読み出しのたびに領域の外の表を引く費用を避けるためである。」の趣旨を足す（理由の中身は設計者の判断に合わせる）。

## 7. 性能への影響

問題なし（測っていない。机上の見積もり）。

- 確保: `next_serial` の読み・`checked_add`・書きが一回ずつと、頭の空いていた 8 バイトへの書き込みが増えた。頭は同じ 32 バイトの書き込みの中に収まるので、費用は小さい。
- 印付け: `replace` が `get`＋`set` になっただけで、書き込みの回数は同じ。
- 掃き出し: 全対象への `replace(0)` の書き込みがなくなり、読むだけになった。生きている対象の多いヒープでは、わずかに速くなる見込みである。
- `same_object`: 前と同じ番地の比較。
- 報告のとおり、短い測定はオーケストレータが行う予定である。
