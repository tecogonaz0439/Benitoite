# V6「拒否した接続の段階的な閉じ方」のレビュー

対象: 538c2587 "Close rejected HTTP connections gracefully"（san_benito の 8537c727 の第 2 親）。`git show` で読んだ。ビルドとテストは走らせていない。行番号は 538c2587 の版のもの。

## 結論

高の指摘はない。計画（plan.md の V6、study.md 3.3 の L1・3.4 の中の上限・3.6・3.7）のとおりに実装されている。イベントループの扱い（段を移した直後の読み捨て、WouldBlock まで読むこと、期限と `retry_at` を分けること、期限で起きた accept が受け付けをやり直さないこと）はどれも正しい。中の指摘が 1 件、低の指摘が 5 件ある。

## 観点ごとの確認

### 1. イベントループの正しさ

- 段を移した直後の読み捨て: `Connection::advance`（http.rs 414-430）は、拒否の応答を書き終えると `shutdown(Write)` の後に、同じ呼び出しの中で `Lingering::advance` を呼ぶ。拒否の判定は `reader.advance` の `Reject` で読み込みを WouldBlock の前に止める（`break`）ので、受信のバッファに残りがあっても新しい edge は来ない。その場で読み始めるのは必要な処置であり、正しい。加えて `arm` は毎回 `reregister` するので、二重に守られている。
- WouldBlock まで読む: `Lingering::advance`（324-345）は、`Interrupted` で続け、`WouldBlock` でだけ `Waiting` を返す。`Ok(0)`・誤り・量の上限の超過・期限の到達では `Dropped` を返す。一回の呼び出しの仕事は 8 KiB × 約 128 回で抑えられる。
- 期限の判定: `now >= deadline` で閉じる。スケジューラの `expire_timers` は `deadline > now` で止まる（sched/mod.rs 125）ので、タイマーで起きた `accept` が読む時刻（同じ `monotonic_millis`）は必ず期限以上になり、早起きによる空回りはない。
- `Armed::deadline` と `retry_at`: `arm`（1382-1392）は、閉じる途中の接続の期限と `retry_at` の最小値を返すだけで、`retry_at` を書き換えない。`retry_at` が `Some` のときの待ち受けの登録の解除（1306・1331 付近）は、従来どおり `retry_at` だけで決まる。閉じる途中の期限が待ち受けの登録を外すことはない。
- 期限で起きた accept: `accept`（467）の条件は `retry_at.is_none_or(now >= retry_at)` のままで、閉じる途中の期限で起きても `retry_at` の前なら受け付けをやり直さない。単体テスト `rejected_connection_deadline_survives_registration_retry` が、2,000 で接続が消え `retry_at` が 3,000 のまま残ることを確かめている。
- 期限のタイマーの経路: `expire_retry`（vm/dispatch/tasks/io.rs 838-）が `retry_request` で `Http.accept` をやり直す。準備の通知とタイマーが重なっても `clear_ready` がタイマーを外す。取り消しでも同じ。
- 費用: 期限の最小値の計算は全件の走査（O(n)）だが、同じ `arm` が全接続を `reregister`（接続ごとにシステムコール）しているので、比べて無視できる。後述の低 L3 に、閉じる途中の接続が増えたときの全体の費用を書く。

### 2. 資源

- 記述子: 閉じる途中の接続は `Listener::connections` に残り、`Listener` の `release`・`Drop` で `Vec` ごと落ちて、`Connection::drop`（登録の解除）と `TcpStream` の `Drop`（close）で閉じる。`Http.serve` の終わりと取り消しは `Listener` の解放を通るので、同じく閉じる。
- `shutdown(Write)` の失敗: `Dropped` にして閉じる。相手が既に RST した場合（ENOTCONN など）に当たり、妥当である。
- 上限のない保持: 一つの接続は、`Http.accept` を呼んでいる間は 2 秒か 1 MiB で必ず閉じる。呼んでいない間は保持が続くが、03-09 と CHANGELOG に書いてある。接続の数に上限がないことは 03-09 に書き足してある（TODO-069 の範囲）。ただし保持する記憶域について中 M1 がある。

### 3. 文書

- 03-09: 当てる応答（400・413・431）、上限（1 MiB を「超える」、2 秒に「達したら」）、`Http.accept` を呼ばない間は進まないこと、`Http.Exchange` に当てないことは、どれも実装と一致する。「応答を書き終えるまでの時間には上限を設けない」も、拒否の応答の書き込みに期限がない今の実装と一致する。
- 02-09: `Http.Listener` の解放で閉じる途中の接続も閉じ、未読があれば RST になりうること。実装と一致する。
- CHANGELOG: 「more than 1 MiB」は `>` と、「2 seconds have elapsed」は `>=` と一致する。「Closing proceeds while `Http.accept` is called.」も正確である。
- 細部は低 L1・L2。

### 4. テスト

- 直す前に落ちたこと: 報告によると、表の順序を入れ替えて 413・431 のそれぞれを先頭にし、各 3/3 回 `ConnectionReset` で落ちた。直した後は 20/20 回通った。
- 時間: 単体テストは `accept` に渡す `now` を進めるだけで、実時間を待たない。統合テストは各回約 1 秒。10 秒を超えるテストはない。
- 揺らぎ: 統合テストの 200 ms の待ちは、直す前の実装で RST を起こしやすくするためのもので、直した後の合否はこの待ちに依らない（サーバは応答の直後に FIN を送るので、`read_to_end` は待ちの後すぐ終わる）。直した後に落ちうるのは、相手が 256 KiB を書いてから読み始めるまでに 2 秒を超えて、サーバが未読を残して閉じる場合だけで、遅い CI でも起きにくい。低 L4 に、待ちの意図をコメントに書くことを挙げる。
- 量の上限のテストは、1 MiB ちょうどで残り、1 バイト足すと消えることを境目の両側で確かめており、相手のソケットを開けたまま保つので EOF の経路と混ざらない。決定的である。

### 5. 規約

`unwrap`・`expect`・添字・`as` はない（加算は `saturating_add`）。大域の状態はない。文言の追加はない。コメントは日本語で、根拠の節を示している。非公開の型 `Lingering` に `///` がないのは規約の範囲内である。

## 指摘

### M1（中）閉じる途中の接続が、解析用の入力のバッファを持ち続ける

- 場所: crates/benitoite/src/runtime/io/http.rs 414-430（`Connection::advance` の閉じる途中の段への移行）
- 問題: 段を移しても `self.reader`（`RequestReader` の `input` と解析済みの `request`）を捨てない。431 の場合、`input` は頭の上限 64 KiB に読み込みの 8 KiB を足した程度まで育っており、直す前はすぐに解放されていた記憶域を、閉じる途中の間（`Http.accept` を呼ぶ間は最長 2 秒、呼ばない間は解放まで）持ち続ける。拒否される要求を続けて送られると、閉じる途中の接続の数 × 約 72 KiB を保持する。閉じる途中の段では `reader` を二度と使わないので、保持する理由がない。
- 直し方: 閉じる途中の段に移すときに `self.reader = RequestReader::default();`（または `std::mem::take(&mut self.reader)` を落とす）。単体テスト `rejected_connection_closes_only_after_discard_limit` の `assert_eq!(connection.reader.input.len(), input_len)` は、「読み捨てたバイトを解析用の入力に足さない」ことを確かめているので、`input.is_empty()` を確かめる形に直す（`input_len` の取り出しも要らなくなる）。

### L1（低）`Armed` と `expire_retry` のコメントが、閉じる途中の期限を含まない

- 場所: http.rs 1286（`/// 登録した準備のトークンと、資源不足で再試行する期限`）、vm/dispatch/tasks/io.rs 836 付近（`/// 満了した受け付けの再試行を Ready の完了として処理する。`）
- 問題: `Armed::deadline` は、資源不足の再試行の期限だけでなく、閉じる途中の接続の最も早い期限も表すようになった。`expire_retry` も、その期限の満了を扱う。コメントが古いままで、読み手が期限の意味を取り違える。
- 直し方: 「資源不足で再試行する期限と、閉じる途中の接続の最も早い期限のうち早い方」「受け付けの再試行か、閉じる途中の接続の期限の満了を…」のように直す。名前（`retries`・`expire_retry`）は変えなくてよい。

### L2（低）期限の起点が「応答を書き終えた時刻」より少し早い

- 場所: http.rs 423-426、03-09「サーバの接続と要求の読み方」の追加の項目
- 問題: 期限は `accept` の入口で読んだ `now` から数える。一回の `accept` で多くの接続を進めると、応答を実際に書き終えた時刻より前の時刻が起点になり、2 秒より少し短くなる。実害はほぼない。
- 直し方: 直さなくてよい。直すなら、03-09 に「応答を書き終えた `Http.accept` の呼び出しの時刻から」と書くか、そのままにする旨をレビューの記録に残す。

### L3（低）閉じる途中の接続が多いとき、起きるたびの費用が接続の数に比例する

- 場所: http.rs 495-505（`accept` が全接続を `advance`）、1335-1378（`arm` が全接続を `reregister`）
- 問題: 準備の通知かタイマーで起きるたびに、閉じる途中の接続のそれぞれに `read` と `reregister` のシステムコールを一回ずつ行う。読みかけの接続については従来からの形だが、閉じる途中の接続は最長 2 秒残るので、拒否される要求が続くと n が増える（例: 毎秒 1,000 件で約 2,000 接続、起きるたびに約 4,000 回のシステムコール）。期限の最小値の全件の走査は、これに比べて小さい。
- 直し方: この作業では直さない。03-09 の「サーバをインターネットに直接さらさない」の前提の範囲に収まる。TODO-069（接続の数の上限）を扱うときに、準備の通知が来た接続だけを進める形と合わせて検討するよう、docs/todo の TODO-069 に一文書き足すことを勧める。

### L4（低）統合テストの 200 ms の待ちの意図がコメントにない

- 場所: crates/benitoite/tests/l30_http_server.rs 326（`std::thread::sleep(Duration::from_millis(200));`）
- 問題: 待ちは、直す前の実装でサーバが未読を残して閉じ、RST が先に届くようにするためのもので、直した後の合否には効かない。コメントがないと、後の読み手が揺らぎの元と見て消すか、合否を時間に頼るテストと誤解する。
- 直し方: 「直す前の実装で、応答を読む前にサーバが未読を残して閉じるのを待つ。直した後の合否はこの待ちに依らない」の旨のコメントを一行加える。

### L5（低）相手が送信の側を閉じたときに閉じる経路を、直接確かめるテストがない

- 場所: crates/benitoite/src/runtime/io/http/tests.rs
- 問題: 閉じる条件のうち、時間と量は単体テストで境目まで確かめているが、`Ok(0)`（相手の FIN）で `connections` から消えることは確かめていない。統合テストでは相手がソケットを落とした後のサーバの状態を見ない。退行（例: `Ok(0)` を `Waiting` にして期限まで持つ）は、合否に現れない。
- 直し方: `lingering_connection()` の後に `client.shutdown(Shutdown::Write)` し、`now = 0` のまま `accept` を回して `connections` が空になることを確かめる単体テストを一つ加える（実時間は待たない）。test-audit の作成時の関門で、価値が見合うかを判断してよい。
