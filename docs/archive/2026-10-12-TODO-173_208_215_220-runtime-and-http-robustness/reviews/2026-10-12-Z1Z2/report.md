## 結論

正しさを壊す問題は見つからなかった。V1 の低 1〜5、V2 の中 1・低 2〜5、V3 の中 1・中 2・低 3・低 4（AGENTS.md の文言で範囲を示す案）・低 5・低 8、V4 の中-1・低-1〜低-4 は、どれも指示どおりに直っている。

- PairHasher は FxHash（v1）と同じ形で、確定処理（`finish`）で混ぜ直さない。hashbrown がバケットの番号に使う下位のビットが入力の下位のビットだけで決まるので、通し番号が 2 の冪の間隔で並ぶ対象どうしの組では、バケットが大きく偏る（中 1）。

## 指摘

### 中 1: PairHasher の下位のビットの偏り（2 の冪の間隔の通し番号で、バケットが偏る）

- ファイル: `crates/benitoite/src/runtime/equal.rs` 14〜47 行（9b0c95ea。`PairBuildHasher`・`PairHasher`）。
- 問題:
  - `ObjId` は `#[derive(Hash)] struct ObjId(pub u64)`（`heap/value.rs` 236〜237 行）である。組 `(a, b)` のハッシュは `write_u64(a)`・`write_u64(b)` の 2 回の呼び出しになり、値は `h = ((a·K).rotl(5) ^ b)·K` となる（K は FxHash の定数）。`finish` は `self.0` をそのまま返す。
  - 奇数を掛ける演算では、積の下位 k ビットが、掛けられる数の下位 k ビットだけで決まる。hashbrown はバケットの番号に下位のビットを使い、上位の 7 ビットを制御のバイトに使う。そのため、バケットの番号は `(a·K).rotl(5) ^ b` の下位のビットだけで決まる。このうち第 5 ビットより上は、`a` と `b` の下位のビットそのものである。
  - 比べる二つの値の対象が、どちらも 2^m の間隔の通し番号で並ぶと、下位の第 5〜第 m−1 ビットが定数になる。たとえば、要素ごとに決まった数の対象を確保して作った値がこれに当たる。このときバケットの数は 2^(m−5) 分の 1 に減る。10 万組（容量 131,072）で模擬した結果は次のとおりである。

    | 通し番号の間隔 | 使われたバケットの数 | 一つのバケットの最大の組の数 |
    |---|---|---|
    | 1（連続）・3・96 | 約 7 万〜8.7 万（ランダムと同程度） | 2〜8 |
    | 2^8 | 16,384 | 8 |
    | 2^10 | 4,096 | 27 |
    | 2^12 | 1,024 | 101 |
    | 2^14 | 256 | 394 |

  - 偏ったバケットでは探索が長くなり、挿入の費用が組の数に対して二次に近づく。結果は変わらない。`HashSet` は組そのものの `Eq` で区別するので、正しさには響かない。連続する通し番号や 2 の冪でない間隔では、偏りは見られない。ただし間隔はスクリプトの書き方で決まるので、「利用者が通し番号を選べないので固定のハッシュでよい」という V4 の前提は、この偏りまでは覆わない。
  - Z2 の報告は「回転・排他的論理和・折り返す乗算で混ぜる」と書いているが、コードは折り返さない `wrapping_mul` だけである。報告とコードが食い違っている。
- 直し方: `finish` で上位のビットを下位へ折り返す。次のどれでも、上の 2^8〜2^14 の間隔で偏りが消えることを模擬で確かめた（使われたバケットは約 7 万、最大は 6〜7）。
  - `fn finish(&self) -> u64 { self.0.rotate_left(26) }`（rustc-hash 2 と同じ考え方。上位のよく混ざったビットを下位へ移す）
  - `let x = self.0; x ^ (x >> 32)`
  - `write_u64` の乗算を u128 にして、上位と下位の 64 ビットの排他的論理和をとる（折り返す乗算）

  費用は命令 1〜2 個なので、測定の値はほとんど変わらない見込みである。合わせて、コメント（14〜16 行）に「`finish` で上位のビットを下位へ移す。hashbrown はバケットの番号に下位のビットを使うため」と、固定のハッシュでよい理由を一文ずつ書く。テストを足すなら、間隔 2^12 の `ObjId` の組を数万入れたときのバケットの偏りではなく、`PairHasher` の出力の下位のビットが `a` の上位のビットに依ることを確かめる小さな単体テストで足りる（任意）。

### 中 2: 「旧版に対して +7.8 %」は別の時刻の測定どうしの比で、同じ時刻の比では +15 % を超える見込みがある

- ファイル: Z2-report.md の「4.」の性能の表。`measurements.md` の「大きな等しい値の比較」（3f9d721d が約 45 ms、d5a57c45 が約 64 ms）。
- 問題: Z2 が測った修正前（d5a57c45 と同じ比較のコード）は 59.5 ms／回である。オーケストレータが同じコードで測った値は約 64 ms なので、Z2 の時刻の環境は約 7 % 速い。比較なしの時間も 0.36 秒に対して 0.31〜0.32 秒で、同じ方向にずれている。同じ比率で直すと、Z2 の環境での旧版（3f9d721d）は約 41.8 ms になり、修正後の 48.5 ms は約 +16 % になる。依頼の限度（+15 %）の境目にあり、「限度内に収まった」とは言い切れない。
- 直し方: 最後の短い測定で、3f9d721d と Z2 の後の版を同じ時刻に交互に測り、比を `measurements.md` に書く。中 1 の直しを入れた版で測ればよい。限度を超えるなら、依頼の補足にあるほかの手（集合の初めの容量を歩数から見積もる、閾値の調整）を試すか、設計者に判断を仰ぐ。V4 の中-1 が求めた最大 RSS も、同じ測定で記録する。V4 の中-1 の直し方は、ハッシュを替えた判断と測定の結果を改造のディレクトリに書くよう求めている。この記録もオーケストレータの側で残っている。

### 低 4: `check_unsafe_allows` は当たった行を示した後の grep の失敗で、残りのファイルを示さずに戻る

- ファイル: `scripts/check.sh` 122 行（f63f5d86。`grep -Hnw -- unsafe_code "$source_file" >&2 || return 1`）。
- 問題: 一覧を取った後に当のファイルが消えたか読めなくなった場合などに、そこで `return 1` するので、後に続く外れたファイルの名前が示されない。失敗としては正しく伝わり（`run_check` が `FAILED` を出して `exit 1`）、偽の成功にはならない。実害はほぼない。
- 直し方: 任意。`|| failed=1` にして一巡を続ける。

  そのほかの grep の誤りの伝わり方には問題がない。確かめた点は次のとおりである。
  - `local` を代入とは別の行で宣言している。`source_files="$(grep …)" || { grep_status=$?; … }` の `$?` は、コマンド置換の終了状態になる（bash 3.2 でも同じ）。
  - `if grep -Fq …; then continue; else grep_status=$?` の `else` の中の `$?` は、条件の grep の終了状態である。前の版の `!` を外してあるので、1 と 2 を区別できる。
  - 両方の関数は `run_check` の `if "$@"` からしか呼ばれない。`set -e` が効かない文脈であるが、`return 1` と `failed` を明示しているので、失敗は伝わる。
  - here-string（`<<<`）は bash 3.2 にあり、ループは今のシェルで回るので、`failed=1` は残る。一覧が空のときの空の行は `[ -n … ] || continue` で飛ばしている。
  - BSD grep も GNU grep も、誤りのときの終了状態は 2 である。

### Z2

- **V4 中-1**: ハッシュを替えた（品質は中 1、測定は中 2）。`write` が u64 以外の入力で呼ばれたときは、1 バイトずつ `write_u64` に渡す。同じ入力には必ず同じ値を返すので、`Hash` と `Eq` の約束は守られる。`(ObjId, ObjId)` は `write_u64` を 2 回呼ぶだけなので、この経路は通らない。乱数の鍵を使わないので、大域の状態も増えない。

- **V4 低-2**: 両テストの先頭に、組を覚える仕組みが壊れると終わらなくなる旨の一文が入った。
- **V4 低-3**: 02-08 と `SharedPairs` の `///` に、「比較が続いていることから 1 回目は等しかった」と「種類・`tag`・欄の数・長さ」が入った。Z2 は鍵の比較を「成分を比べた後に数を比べる」と書き分けた。`keys.rs` の構成子の分岐は `tag` だけを確かめて覚え、`Work::Order(an.cmp(&bn))` を欄の下に積む。リスト・マップ・集合の分岐は長さを先に比べない。Z2 の書き分けは、この実装と合う。2 回目に出会った時点では `Order` も `Equal` で処理を終えているので、論証も成り立つ。
- **V4 低-4**: 記憶の量（共有のない値では大きさに比例し、共有がある値では左右の対象の数の積が上限）と、上限を設けない理由が入った。Z2 の報告の補正（「常に大きさに比例する」とは言えない）は正しい。
