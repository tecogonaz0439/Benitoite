## 結論

重さ「高」の指摘はない。(A) の 3 件と (C) の 5 件は計画どおりに直っており、V1 の通し番号の `ObjId` を前提にすれば、番地の再利用による偽の成功と偽の失敗はどちらも起きない。回収の後に読む順序も正しい。解放したかもしれない対象を `object_id` や中身の読み出しより前に、`object_ids().contains` で確かめている。

ただし、`numeric.rs`・`collections.rs`・`traits/tests.rs` の 3 件で足した生存の確かめは、キャッシュの Trace の漏れを捕まえない。対象がレジスタからも根になっているためである（指摘 1）。このほかに直すとよい点が「低」で 5 件ある。

## 観点ごとの確認

1. **番地の再利用と読む順序**
   - (A) の 3 件は、元のリストの値から `reachable_object_ids` で対象を集める。言語の値を確保しないので、テストが作った捨てる対象は集めない。判定は `vm.heap.object_ids()`（`core.rs:176-190`、生きている記録の頭の通し番号）だけで行い、解放した対象を読まない。通し番号は使い回さないので、回収の後の確保が同じ番地を使っても偽の失敗にならない。`kept`（`vm/tests.rs` の `suspended_callers_...`）の「残っている」の確かめも、番地が一致するだけで通る偽の成功ではなくなった。
   - (C) の 5 件は、回収の前に生きている値から ID を取り、`heap.collect` の直後に確保を挟まず `contains` を確かめ、その後で `object_id`・`same_object`・中身を読む。`roots_constants_and_waiting_arguments_survive_collection` は、回収の前にあった中身の読み出しを回収の後へ移したうえで、3 対象の生存を先に確かめている（`vm/tests.rs:948-962`）。事前点検の「表明を読み出しより前に置く」を満たしている。
2. **閾値の固定**
   - `trigger_min_bytes: 1` と `trigger_factor_percent: 0` で、閾値は `max(0, 1) = 1` バイトになり（`mark_sweep.rs:46-61`）、回収の後に 1 バイトでも確保すれば次の安全点で回収する。stress = false の場合に回収が起きるのは、再開の後の確保（`LOADK Func(leaf)`、`leaf` の `LOADK "after"`）による。テストの核心はリストの対象が残っていないことを確かめる表明にあり、閾値はいつ回収するかを決めるだけなので、確かめる契約（安全点が死んだレジスタを根にしない）は弱まっていない。stress = false は、確保の合図から回収する経路を、stress = true は強制の経路を通すので、二つの場合を分ける意味も残っている。
   - 回収の回数の増加の表明（1344 行）は適切である。リストが死ぬ前の回収しか起きなければ「残っていない」の表明が落ち、偽の成功にはならない。この表明は、回収が起きなかったという別の原因を見分ける診断になる。
3. **補助の関数**
   - `constant` は、元の 5 か所の式と同じ意味を持つ。`reachable_object_ids` は、明示の積み重ね（`Vec`）で辿り（AGENTS.md「再帰の深さ」）、`HashSet` で共有した対象を一度だけ辿る。`ObjKind::Fields(_)` の欄だけを辿るので、永続ベクタの tag の意味や欄の配置（`runtime/list.rs`）に頼らない。`test_support` は `#[cfg(test)]`（`dispatch.rs:1871-1872`）の下にあり、許可（`unwrap_used`・`indexing_slicing`）の範囲で書かれている。
   - `miri_tests.rs:55` は `check_dead_list_at_safepoints(12)` をそのまま呼び、シグネチャは変わっていない。12 要素は頭と末尾の葉の 2 対象になり（根は Unit）、`objects.len() >= 2` で意味のある確かめになる。
4. **名前とコメント**: `cells` と「セル数」の言い回しは消えた（`grep` で残りはない）。作業の ID も書いていない。参照する見出し（02-08「値の表現」、02-07「定数表」、02-09「メモリの管理」、03-06「List の内部の表現」）は、どれも設計書にある。
5. **漏れ**: study の (C) の 5 件と (A) の 3 件は、すべて直っている。`constants.last()` の 4 か所は、計画では任意としていた（指摘 6 で補足する）。

## 指摘

### 1. 【中】3 件の定数のテストで足した生存の確かめは、キャッシュの Trace の漏れを捕まえない

- ファイル: `vm/dispatch/numeric.rs:389-393`、`vm/dispatch/collections.rs:94-99`、`vm/dispatch/traits/tests.rs:186-190`
- 問題: 3 件とも、IO を待つ間もキャッシュの対象をレジスタが持っている（`collections.rs:69`「待つ前のレジスタを後で使い、生存解析が回収前に消さないようにする」、`traits/tests.rs:162`、`numeric.rs` の `EqD 2, 0, 1`）。このため、キャッシュの Trace が漏れても、対象はレジスタから辿れて生き残る。足した `contains` も、続く `same_object` も通る。解放後の読み出しも起きないので、study 1.2 節の (C) の前提（「キャッシュの `Slot` だけが古い番地を指す」）は、この 3 件には当てはまらなかった。変更そのものは無害だが、コミットメッセージの「キャッシュした定数が生きていることを確かめる」という主張は、実際に確かめている範囲より広い。
  - キャッシュだけを根にした確かめは、`heap_constants_keep_identity_when_only_the_cache_roots_them` が担う。この関数は Str・Func・Ctor・List・Map・Set・Decimal の 7 種類を扱うが、**`ConstDesc::Dict` を含まない**。辞書の定数をキャッシュだけが根として持つ状態での回収は、どのテストも確かめていない。
- 直し方: (a) `heap_constants_keep_identity_...` の `kind` に `ConstDesc::Dict` を加える（`traits/tests.rs` の `implementation` の補助のように、実装の表を一つ作る）。(b) 3 件のテストは、足した確かめを残すなら「レジスタも根なので、ここでは回収の後もキャッシュと同じ対象であることを確かめる。キャッシュだけを根にした回収は `heap_constants_...` が確かめる」という趣旨のコメントを置く。足した確かめを外してもよい。いずれにしても、この 3 件のコミットメッセージの主張を、報告で訂正しておく。

### 2. 【低】閾値のコメントの句読点と、回収が依存する確保の書き方

- ファイル: `vm/tests.rs:1323-1325`、1341-1342
- 問題: 「…回収を要求する。」の後に、次の行の「（設計書 02-09「メモリの管理」）。」が続き、句点が二重になっている。さらに、stress = false の場合の回収が、リストが死んだ後の確保（関数の定数と `"after"` の文字列）に依存することが書かれていない。1341 行の「run の呼び出し前の安全点で回収した直後に確かめる」は、stress = false では、実際に回収する安全点（`leaf` の CALL か IO の前）とずれて読める。
- 直し方: 例えば「観察では確保しない。再開の後の小さな確保（関数の定数と "after"）でも次の安全点で回収するよう、生存量に比例する閾値を 0 にする（設計書 02-09「メモリの管理」）。」とし、句点を一つにする。

### 3. 【低】`suspended_callers_...` の回収の回数の表明が、ほかの 2 件より弱い

- ファイル: `vm/tests.rs:1625`
- 問題: `collections > 0` は、観察より前の回収でも満たされる。`check_dead_list_at_safepoints`（1344 行）と `tail_window_...`（1491 行）は、観察の後の増加を表明している。stress = true なので実害はなく、核心の表明（`old` が残っていない）も正しい。
- 直し方: `serve_request(before)` の前に回数を記録し、`after` の後に `>` で比べる形に揃える（今回は既存の行なので任意）。

### 4. 【低】`reachable_object_ids` の前提を文書のコメントに書く

- ファイル: `vm/dispatch/test_support.rs:30-32`
- 問題: この関数は、ほかの生きている値と共有した対象（キャッシュした定数の要素など）も集める。そのため、「集めた対象がすべて解放された」と表明する使い方では、要素が共有した対象なら偽の失敗になる。今の 3 件は要素が整数（即値）なので問題はないが、使い回されたときの落とし穴になる。
- 直し方: `///` に「解放を確かめる用途では、元の値だけが持つ対象から成る値に使う」と一文を足す。

### 5. 【低】大きいリストでの対象の数の下限が緩い

- ファイル: `vm/tests.rs:1338`、1442、1614
- 問題: `>= 2` は 12 要素にも 4096 要素にも同じ値を当てる。4096 要素では葉だけで 128 対象あるので、例えば辿り方の誤りで頭と葉 1 つしか集めなくても通る。
- 直し方: 任意。表現に深く結び付けないよう、「葉の数 `ceil(count / 32)` に頭を加えた数以上」程度の下限にする。葉の幅 32 に依存するのを避けたいなら、今のままでよい。

### 6. 【低】`constants.last()` で観察の根を読む 4 か所に、同じ種類の解放後の読み出しが残る（範囲外の残り）

- ファイル: `vm/dispatch/tasks/tests.rs:1187`、`vm/dispatch/cell/tests.rs:224`・`318`・`379`
- 問題: これらのテストは、テストが `constants` に積んだ `Slot` を観察の根として使い、回収（あるいは実行）の後に中身を読む。定数の表の Trace が漏れれば、heap-verify なしの構成では解放した領域を読む。実際には `heap_constants_...` が先に落ちるので、検出力は落ちない。計画では任意とした範囲なので、今回の作業の誤りではない。
- 直し方: 直すなら、`constant` と同じ形の補助（例: `last_constant`）にまとめ、積む前に ID を取り、読む前に `object_ids().contains` で確かめる。急がないので、docs/todo の TODO-173 を閉じるときの「後の課題」に一行で残せば足りる。
