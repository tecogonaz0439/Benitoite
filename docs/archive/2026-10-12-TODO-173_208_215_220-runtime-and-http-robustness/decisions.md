# 判断とその理由

調査（`study.md`）の後に、利用者から見える振る舞いと検査の時間に関わる四つの問いを設計者に尋ねた（Q1〜Q4）。残りの点は、調査の推奨どおりとした（R1〜）。

## 設計者に尋ねた問い

### Q1 TODO-208: 文法に合わない要求の対象のうち、どこまでを 400 にするか

- 選択肢: 形と文字（0x80 以上も 400）／形と文字（0x80 以上は受け付ける）／文字だけ／RFC 3986 のとおり全部。
- 設計者の答え: **形と文字、0x80 以上も 400**（推奨）。
- 内容: 形は、`*` を `OPTIONS` だけ、authority 形を `CONNECT` だけに限り、`CONNECT` の port を確かめる。`/` で始まらない起点形と、`http`・`https` 以外の scheme の絶対形も 400 にする。文字は、`"`・`<`・`>` と 0x80 以上のバイトを 400 にする。`[`・`]`・`\`・`^`・`` ` ``・`{`・`|`・`}` は受け付けたままにする。
- 理由: RFC の MUST に当たる形の誤りを確実に拒み、文字は標準に従うクライアントが生で送らないものだけを拒む。WHATWG URL Standard の符号化の集合では、`[` などはクエリに生のまま残りうるので、拒むとブラウザで試した要求が 400 になる。RFC 3986 のとおり全部を拒む案は、03-09 の `%G0` の扱いとも衝突する（`study.md` の 208・215 部 2.3 節）。
- 互換性のない変更なので、CHANGELOG の Incompatible changes に書く。

### Q2 TODO-215: 拒否の応答を返して閉じるとき、段階的な閉じ方を入れるか

- 選択肢: 入れる（上限 1 MiB・2 秒）／入れる（上限 64 KiB・1 秒）／入れない。
- 設計者の答え: **入れる、上限 1 MiB・2 秒**（推奨）。
- 内容: 調査の L1。応答を書き終えたら送信の側だけを閉じ（`shutdown(Write)`）、イベントループの中で上限まで読み捨て、相手が閉じるか、読み捨てた量が 1 MiB を超えるか、応答を書き終えてから 2 秒を過ぎたら閉じる。
- 理由: RFC 9112 §9.6 の形に合い、相手が先に閉じれば RST を送らずに閉じられる。作業用のスレッドを塞がず、今の再試行のタイマーの経路で書ける（208・215 部 3.3・3.4 節）。

### Q3 TODO-173: 回収のテストが番地の再利用で誤らないよう、`ObjId` をどう作るか

- 選択肢: 64 ビットの確保の通し番号／32 ビットの確保の通し番号／番地のまま、テストを heap-verify の構成に限る。
- 設計者の答え: **64 ビットの確保の通し番号**（推奨）。凍結したコードのコメント「番地から作る」の意味が変わることも了承を得た。
- 内容: 確保ごとにヒープの中で一意な 64 ビットの番号を振り、`object_id`・`object_ids` はその番号を返す。番号は一周しない。
- 理由: 調査は 32 ビットの番号を対象の頭の空きに置く案を推した（173 部 1.4 節）。しかし TODO-220 の直しは、本番の比較で `ObjId` を組の記憶の鍵に使う。32 ビットの番号は約 43 億回の確保で一周し、生きている二つの対象が同じ番号になると、比較が誤って等しいと答えうる。64 ビットなら一周しない。heap-verify のない構成では頭の空きに収まる見込みで、heap-verify の構成で頭が大きくなっても、テストの構成だけの費用である。
- `ValueCtx::same_object` の中身は番地の比較に改める（本番の `map/tree.rs` の近道で頭を読まないため）。

### Q4 TODO-173: 配布物の構成（heap-verify なし）の検査を `scripts/check.sh` に加えるか

- 選択肢: ライブラリのテストと Clippy／Clippy だけ／加えない。
- 設計者の答え: 「2 は追加、ライブラリのテストは明示的に指示した時とライブラリ改造時のみ。」
- 受け取り方: 既定の機能（`gc-mark-sweep` だけ）の Clippy は、`rust` を選んだときに走らせる。既定の機能のライブラリのテスト（`cargo test -p benitoite --lib --no-default-features --features gc-mark-sweep`）は、明示の指定（`--only` で名指しするか `--full`）と、`runtime::heap` を変えたとき（`check-heap.sh` を走らせるのと同じ条件）にだけ走らせる。

## 推奨どおりとした問い

- **R1 TODO-220 の方式**: 調べ始めた子を持つ対象の組を覚え、同じ組に再び出会ったら調べない（220 部の案 (a)）。小さな比較の費用を増やさないよう、一定の歩数を超えてから覚え始める。同じ対象で `Float` を含まない型なら省く案 (b) は、別々に作った等しい値を速くせず、`[T: equality]` の関数の中では型の情報がないので採らない。
- **R2 覚える組の数の上限**: 設けない。覚える組は比較の手数を超えず、比べる値がヒープで占める量に比例する。上限を設けると、上限を超える値で指数時間に戻る。
- **R3 マップの鍵の比較**（`runtime/map/keys.rs` の `compare`）: 同じ改造で同じ仕組みを入れる。
- **R4 参照インタプリタの橋渡しの変換が共有を展開する問題**: この改造では直さず、docs/todo に新しい項目として加える。
- **R5 TODO-220 のゴールデンテスト**: 置かない。どの経路も同じ `values_equal` を呼び、参照インタプリタの側は R4 の問題で終わらないため。主なテストは `runtime/equal.rs` と `runtime/map/tests.rs` の Rust のテストに置く。
- **R6 印付けの途中の panic**: 回収ごとの番号を印にする（173 部 2.3 節の案 (a)）。番号はヒープの回収の状態に `u64` で置き、`stats.collections` は使わない。今の処理系では panic の後に同じヒープで回収を続ける経路はなく、潜在の弱さである。
- **R7 既定の構成の Miri**: この改造では扱わず、docs/todo の TODO-161 に書き足す。
- **R8 印の表し方を 02-09 に書くか**: 書かず、コードの `//!` に書く（実装の細部のため）。
- **R9 `allow(unsafe_code)` の場所の検査**: `check.sh` に加え、`rust` を選んだときに走らせる（173 部 5.2 節）。AGENTS.md の `#[allow]` の表の文言を、検査の一覧と同じ書き方に改める。
- **R10 `http`・`https` 以外の scheme の絶対形の状態コード**: 400。
- **R11 `CONNECT` の port 0**: 受け付ける（handler が決める）。空・数字以外・65535 を超える port だけを 400 にする。
- **R12 段階的な閉じ方を当てる応答**: `Connection` で返す 400・413・431 のすべて。`Exchange` の応答と解放には当てない。閉じる途中の接続は `Listener::connections` に残す（TODO-069 で同時の接続の数の上限を加えるときに数えられる位置）。
- **R13 l30 の `request` の RST を許す分岐**: macOS と Linux の両方で確かめられるまで残す。この改造では、段階的な閉じ方を確かめる新しいテストを加える。
- **R14 作業の分け方**: 一つの改造のディレクトリで、作業を直列に積む（`plan.md`）。
- **R15 共有のない大きな値の比較の費用**: 作業 Z4 の後、共有のない 20 万要素のリストの比較は約 20 % 遅くなり、最大 RSS が約 11 MB 増えた（`measurements.md`）。fib・loop には差がない。共有した構造の比較が深さに対して指数時間になるのを防ぐ費用として受け入れ、さらに減らす工夫（組の表の作り、覚える対象の絞り方）は docs/todo の TODO-223 に残した。
- **R16 最後の検査**: `scripts/check.sh --base 3f9d721d` は、`scripts/check.sh` の変更を理由に止まった。設計者に範囲を尋ね、設計者は検査しない（`--none`）を選んだ。作業ごとに、関係するテスト（heap-verify・既定の機能・gc-stress・heap-per-object の構成を含む）と二つの構成の Clippy・fmt を走らせて通したことで代えた。長いテスト、`check-heap.sh`（Miri）、ワークスペース全体のテストは、この改造の後に走らせていない。
