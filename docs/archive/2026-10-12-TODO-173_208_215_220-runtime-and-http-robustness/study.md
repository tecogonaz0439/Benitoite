### 0. 結論の要約

- `ObjId` は、heap-verify の有無にかかわらず、対象の番地から作る（`core.rs:170-180`・`220-223`）。heap-verify の機能は `ObjId` を整理しない。TODO-173 と C-3 が挙げた「テストの前提（ヒープの検証器が対象の ID を整理すること）」は、事実と違う。
- heap-verify で変わるのは次の二つである。(1) `ObjRef` が確保の世代（`u32`）を持つので、`Value` が 16 バイトから 24 バイトになる（`value.rs:30-38`、`ctx.rs:682-690` の表明は heap-verify なしの構成だけ）。(2) 読み出しのたびに世代の表を引き、解放した対象を読めば不具合として記録する（`core.rs:183-203`）。確保器は二つの構成で同じで、解放した番地を後入れ先出しで再び使う（`core/alloc.rs:116-126`）。
- したがって、「回収の後、古い id が残っていない」を番地で確かめるテストは、どちらの構成でも、回収と確かめの間に確保があれば揺らぐ。heap-verify の構成で通るのは、`Value` が大きいぶん値の並びの対象の大きさの区分（`SIZE_CLASSES`）がずれ、番地の再利用がたまたま起きにくいからだと読める。回収の振る舞いの誤りではなく、テストの前提の誤りと判断する（実際に再現して確かめる必要はある）。
- 印付けの途中の panic で印が残る経路は、コードの上では実在する。ただし、今の処理系には、panic の後に同じヒープで回収を続ける経路がない（`runtime/run.rs:321-370`）。潜在の弱さであり、回収ごとの番号を印にする形（推す案）で、費用をほとんどかけずに消せる。
- 推す作業の分け方は 3 本（ヒープの内部、VM のテスト、検査の道具と設計書）。設計者に決めてもらう点は 6 つ（8 節）。

### 1. `ObjId` と、番地で「解放された」を判定するテスト

#### 1.1 今のコードの事実

- `ObjId` の定義は `runtime/heap/value.rs:233-235` の `pub struct ObjId(pub u64)` で、文書のコメントに「番地から作る」とある。凍結したコード（10-08 の `file=src/runtime/heap/value.rs`、`docs/archive/2026-10-09-implement-first-release/10-interfaces/10-08-values-and-heap.md:488-490`）と同じ文である。
- `HeapCore::object_ids`（`core.rs:170-180`）は生きている対象の記録の並び（`objects`）の番地を返し、`HeapCore::object_id`（`core.rs:220-223`）は値の番地を返す。heap-verify の構成でも同じで、世代は ID に入らない。
- `HeapCore::same_object`（`core.rs:226-232`）は `object_id` どうしを比べる。`same_object` は本番のコードでも使う（`runtime/map/tree.rs:455` の近道）。
- 確保器（`core/alloc.rs`）は、塊の構成では大きさの区分ごとの空きの並びから `pop` で取り出す（116-126 行）。解放した番地は次の同じ区分の確保で必ず再び使われる。heap-verify は空きを寝かせる（隔離する）処理を持たない。
- heap-verify の構成の違い: `ObjRef` の世代（`value.rs:30-38`）、`generations` の表と `next_generation`（`core.rs:75-78`）、読み出しの前の生死と世代の照合（`core.rs:183-203` の `checked_object`）、解放した中身を `POISON_BYTE` で埋める（`core.rs:683-698`）、ヒープの検証器（`core/verify.rs`、`HeapCore::verify` は heap-verify なしでは `Ok` を返すだけ。`core.rs:1055-1066`）、文字列を借りるときの UTF-8 の確認。
- 対象の大きさの例（頭は両構成で 32 バイト。`core.rs:108-110`）。

| 対象 | heap-verify なし | heap-verify あり |
|---|---|---|
| 欄 2 個の値の並び | 32 + 32 = 64（区分 64） | 32 + 48 = 80（区分 96） |
| リストの頭（欄 4 個。`runtime/list.rs:268-279`） | 32 + 64 = 96（区分 96） | 32 + 96 = 128（区分 128） |
| 文字列 `"after"` | 32 + 5 → 48（区分 64） | 同じ（区分 64） |

構成によって、同じ区分を取り合う対象の組が変わる。heap-verify の構成で通り、ないと落ちる、という報告（later-issues の 42・43 (c)・44）と合う。

#### 1.3 どちらが誤りか

テストの前提が誤りと判断する。理由は三つある。(1) 確保器は二つの構成で同じで、heap-verify は ID の作り方も解放の時期も変えない。(2) heap-verify の構成では、解放した対象を読めば世代の照合で必ず不具合になり、ヒープの検証器と到達可能性の比較も通っている。回収が到達できる対象を解放していれば、そちらで見つかる。(3) (A) の 3 件は、回収の後に確保が起きる手順になっており、番地の再利用が起きる区分の組は、`Value` の大きさで構成ごとに変わる。

ただし、heap-verify なしの構成で今も落ちるか、落ちるならどの確保が番地を再び使うかは、走らせないと分からない。作業の最初に再現の記録を取る（8 節の W2 の手順 0）。

### 2. 印付けと panic

#### 2.1 今の実装

- 印は対象の頭の `word: Cell<u64>`（`core.rs:103`）で、確保のときに 0（`core.rs:301`）。`word` を読むのは `core/mark_sweep.rs` だけである（`core.rs:255-257` の `word` は内部の関数。ほかに `core/tests.rs:102` が初期値 0 を表明する）。
- `Marker::mark`（`core/mark_sweep.rs:89-99`）は `word.replace(1) == 0` のときに積む。掃き出しの前の一巡（170-178 行）で全対象の `word` を `replace(0)` で消し、0 だったものを死んだ対象に集める。根の契約違反（`failed`）のときも、印を消してから解放せずに戻る（179-182 行）。
- 不変条件 M1（7 行）は「対象は印を立てたときに一度だけ積み、掃き出し前に全印を消す」。

#### 2.2 panic で印が残る経路

印付けは 151-167 行の `roots.trace(...)` と `trace_object` のループで行う。この間に panic しうる箇所は次のとおりである。

- `Host` の `Trace` の実装（`trace_object` の 117-123 行、根の `Trace`。VM の状態・タスク・継続など、処理系の Rust のコード）。lint で `unwrap`・`expect`・`panic!`・添字・算術の溢れを禁じているので、残るのは処理系の不具合（`RefCell` の二重の借用など）だけである。
- `pending.push` の容量の溢れ（現実には起きない。確保の失敗は abort で、`catch_unwind` は捕らえない。02-09「panic 境界」）。
- heap-verify の構成の `verify`（143 行）は印付けの前なので、印を残さない。

`Host` の `Trace` で panic すると、それまでに印を立てた対象の `word` が 1 のまま残る。同じヒープで次に回収すると、`mark` はその対象を積まないので、その子を辿らず、子（`word` が 0）を解放する。到達できる対象の解放であり、その後の読み出しは解放後の使用になる。経路はコードの上で実在する。

一方、panic の後に同じヒープで回収を続ける経路は、今の処理系にはない。

- VM の実行は `run_vm_entry`（`runtime/run.rs:313-373`）が `runtime::panic::catch` で囲み、panic を捕らえたら処理系の不具合の報告を作るだけである。その後は `vm.heap_stats()`（統計の写し）を読み、`vm` を捨てる。`HeapCore` の `Drop`（`core.rs:704-714`）は印を見ずに全対象を解放する。
- テストの実行器は、テストの関数ごとに `run_vm_entry` で新しい `Vm`（新しいヒープ）を作る（`run_test` → `run_entry`）。
- 設計書 02-09「panic 境界」は、panic を処理系の不具合として報告して終了状態 3 で終えると定める。
- ヒープのテストの `verification_tests.rs:150` の `catch_unwind` は、panic を種と操作の番号を添えて投げ直すためのもので、同じヒープで続けない。

したがって、今は潜在の弱さである。Rust のライブラリとして呼ぶ API や REPL（docs/todo の TODO-045）で、panic の後もヒープを使い続ける形を作ると表に出る。

#### 2.3 案の比較

| 案 | 内容 | 回収の速さ | 複雑さ |
|---|---|---|---|
| (a) 回収ごとの番号を印にする（推す） | 回収のたびに番号を 1 増やし、`word == 番号` を「印あり」とする | 掃き出しの一巡が生きている対象の頭を書かなくなる（読むだけ）ので、わずかに速くなる見込み。印付けは今と同じ（読んで書く） | 小さい。`mark_sweep.rs` の中だけで閉じる |
| (b) 印付けの前に全印を消す | 印付けの前に全対象の `word` を 0 にする一巡を加える | 回収ごとに全対象を一巡多く書く。遅くなる | 小さい |
| (c) `Drop` の見張りで戻す | 印付けを終えるまで生きる見張りを置き、巻き戻しのときに全印を消す | 正常時は費用なし | 巻き戻しの中でヒープを辿る。見張りの中の panic は abort になる。`Marker` が `&HeapCore` を持つ間の借用の組み立てが要る |

(a) の詳細。

- 番号の置き場所は `mode::State`（`core/mark_sweep.rs:22-38`）に `mark_epoch: Cell<u64>` を加える。`stats.collections`（`stats.rs`）は使わない。根の契約違反で解放せずに戻る回収は `collections` を増やさないので、その回収の印が次の回収の番号と一致してしまうからである。
- 頭の配置は変えない（`word: Cell<u64>` のまま）。新しい対象は 0 で、番号は 1 から始めるので一致しない。前の回収の印は番号が違うので「印なし」と読む。途中で止まった回収の印も同じである。
- 巻き戻り: `u64` は回収ごとに 1 増えるだけで、現実には溢れない。lint（`arithmetic_side_effects`）のために `checked_add` で書き、溢れたら全対象の `word` を 0 にして 1 から始める（届かない分岐だが、panic にも誤りにもしない）。
- 掃き出しの印を消す処理は要らなくなる。死んだ対象を集める一巡（170-178 行）は残り、`replace(0) == 0` が `get() != 番号` になる。`failed` のときの「印を消してから戻る」（179-182 行のコメント）は、消さずに戻ってよくなる。
- 性能: 掃き出しの書き込みが減るだけで、増える処理は回収ごとの整数の加算 1 回である。memory の運用（作業ごとは短い測定）に従い、性能の関門の短い測定で差がないことを確かめれば足りる。

### 3. rustdoc に書く解放後の使用の範囲

#### 3.1 材料

- ADR 0281（`docs/archive/2026-10-09-design-first-release/decisions/0281-heap-number-in-slot-and-contract-safety.md`）の要点: (1) `Slot` はヒープの番号を持ち、すべての構成で照合する（別のヒープの `Slot` を拒む）。(2) 根の列挙の漏れと、根に入れなかった `Slot` を回収の後に読むことは VM の契約とし、検証用の構成の世代の検査・回収の強制・ヒープの検証器・到達可能性の比較で見つける。(3) 公開の API の安全性は「VM が根の列挙の契約を守り、列挙しなかった `Slot` を回収の後に読まないかぎり安全」と述べ、無条件に安全とは述べない。
- 設計書 02-09「メモリの管理」の 23 行目は既にこの条件を書いている。
- 今の rustdoc: `runtime/heap/mod.rs:13-14` の H4 は「根に入れなかった `Slot` を回収後に読まない」と義務だけを書き、破ったときに安全な関数だけで解放後の使用になることと、どの構成で見つかるかを書いていない。`Heap::collect`（`ctx.rs:334-337`）の `///` は H4 を引くだけ、`NoGcCtx::load`（`ctx.rs:357-365`）の `///` はヒープの番号と世代の照合だけを書く。
- 読み出しで頭を読む安全な関数: `NoGcCtx::load`・`take`（`ctx.rs:357`・`389`）、`SlotOps` の読み出し、`Tracer` が辿る `Slot`。heap-verify なしでは `checked_object`（`core.rs:183-203`）が何も確かめないので、解放した塊の中の頭を読む。個別の領域（大きい対象と heap-per-object）では OS に返した記憶を読む。

### 5. `Decimal: Copy` の表明と `allow(unsafe_code)` の場所の検査

#### 5.1 `Decimal: Copy`

- `Decimal`（`base/decimal.rs:12-16`）は `#[derive(Clone, Copy, Debug)]` で、`i128` と `u8` を持つ。
- ヒープは中身を `ptr.read()` で写して返す（`core.rs:565-569` の `decimal`）。解放のときは `Decimal` の中身を drop しない（`core.rs:663-681` の `match` で `ObjKind::Decimal` は何もしない）。確保は `ptr.write`（`core.rs:443-444`）。
- `Decimal` が将来 `Copy` でなくなり、所有する領域（`Vec` など）を持つと、`read` の写しが所有を重ね、二重の解放か解放後の使用になる。解放で drop しないので漏れも起きる。安全な関数の側の変更（`base/decimal.rs`）で内部の層の前提が崩れ、コンパイルは通るので、型の性質で止める。
- 表明の案（`core/layout.rs` の `DECIMAL_BYTES` の近く、または `core.rs` の `decimal` の近くに置く）:

```rust
// Decimal の中身は ptr::read で写して返し、解放のときに drop しない（core.rs の decimal と free_object）。
// Copy でない型になると所有が重なるので、型の性質で止める（設計書 02-09「メモリの管理」）。
const _: () = {
    const fn copy<T: Copy>() {}
    copy::<Decimal>();
    assert!(!std::mem::needs_drop::<Decimal>());
    assert!(std::mem::align_of::<Decimal>() <= super::alloc::ALIGN);
};
```

整列の表明は任意である（今は `Allocator::checked_layout` が実行時に `size_overflow` で拒むので、未定義動作にはならない）。`unsafe` を含まないので、AGENTS.md の規約には触れない。

## TODO-220 共有した構造を持つ等しい値の比較が指数時間になる — 調査の結果

### 0. 結論の要約

- 推奨は案 (a)「調べ始めた対象の組を覚え、同じ組を二度調べない」である。`values_equal` の中だけで閉じ、凍結したシグネチャ（10-08 の `values_equal`、10-07 の `Opcode`）に触れない。NaN の扱い（`[nan] = [nan]` も、同じ参照の `x = x` も `false`）は変わらない。
- 案 (b)「同じ対象で `Float` を含まない型なら調べない」では足りない。別々に作った二つの値（`grow(64)` を二回呼んだ結果どうし）には同じ対象の組が一度も現れず、指数時間のままである。さらに、`Assert.equal` と `List.contains` は `[T: equality]` の多相な関数なので、型の情報を実行時に得られない。
- 同じ指数時間は、マップの鍵の比較（`runtime/map/keys.rs` の `compare`）にもある。鍵に共有した構造があると、`Map.insert`・`Map.get`・マップどうしの `=` が指数時間になる。同じ仕組みで直せる。
- 参照インタプリタの `=` は、組み込みの関数 `%eq` を橋渡し（`refinterp/convert.rs`）で呼ぶ。そのときの値の変換が共有を展開するので、指数時間の入力のゴールデンテストは参照インタプリタとの比較から除く必要がある。主なテストは `runtime/equal.rs` の Rust のテストに置くのがよい。

### 1. 今の実装

#### 1.1 `values_equal` の辿り方

`crates/benitoite/src/runtime/equal.rs` の `values_equal`（11 行）は、仕事の積み重ね `pending: Vec<Work>`（12〜17 行）で辿る。仕事は 3 種類ある。

- `Work::Values(a, b)`: 二つの値を比べる。
- `Work::Lists(cursor, cursor)`（21〜31 行）: リストの要素を、カーソルで一つずつ取り出して比べる。要素の組を積み、カーソルの続きをその下に積む。

#### 1.2 指数時間になる理由

`grow(n)` を「`grow(n - 1)` の結果 `t` を二度持つ構成子 `Node(t, t)`」とすると、`grow(n)` の対象は n 個しかないが、共有を展開した木の葉は 2^n 個ある。`values_equal(grow(64), grow(64))` は、`(Node_a, Node_b)` の組から `(t_a, t_b)` の組を二つ積み、それぞれがまた二つ積むので、2^64 回の比較を行う。`x = x`（同じ値どうし）も、49 行のとおり省かないので同じである。

この比較は一つの命令（`EQV`）か一つの組み込みの関数の中で走るので、途中に安全点も中断の印を調べる位置もない（02-09「中断の要求」）。一度目の `SIGINT` は効かず、二度目の `SIGINT` で OS の既定の振る舞いによって終わるまで、処理系は止まらない。

### 2. 設計書の定め

- 01-06「等値の型」（`docs/design/01-spec/01-06-type-system.md` 298〜326 行）: `=` と `<>` のオペランドは等値の型でなければならない。関数の型と中身を見せない prelude の型（`IOError`・`NetworkError`・`Reference`・`Lazy`・`Task`・リソースの型、`Regex.Pattern` など）を含む型は等値の型ではない。代数的データ型は構成子と引数で、リストは長さと要素で、集合は要素の集まりで、マップは鍵の集まりと各鍵の値で、`Bytes` は長さと各バイトで比べる。`Float` の成分は IEEE 754 に従う（`Option.Some(0.0 / 0.0) = Option.Some(0.0 / 0.0)` は `false`）。`a <> b` は `a = b` の否定である。
- 01-04（`docs/design/01-spec/01-04-types-basic.md` 88 行）: NaN と比べた `=` はすべて `false`、NaN 自身とも等しくない。`0.0 = -0.0` は IEEE 754 のとおり `true`（`equal.rs` のテストの 191 行も同じ）。
- 01-06「鍵の型（初回リリース版）」（330〜335 行）: 鍵の型は `Float` を含まない等値の型である。型の宣言ごとの「`Float` を含むか」の要約は型検査器が求めている（02-05、`docs/design/02-impl/02-05-typechecker.md` 43・96・260 行）。
- 01-06「組み込みの制約（初回リリース版）」（339〜351 行）: 型パラメータに `equality`・`key` を付けられる。組み込みの制約は辞書を渡さない（00-04 用語集の「組み込みの制約」）。したがって、`[T: equality]` の関数の本体では、`T` が `Float` を含むかを実行時に知る手段がない。`[T: key]` なら `Float` を含まないと静的に分かる。
- 01-12（`docs/design/01-spec/01-12-core-calculus.md` 267 行）: δ は 01-06「等値の型」の `=` を返す。処理系は型を消して値を表し、組み込みの関数に型引数を渡さない。
- 02-07「コード生成」の「演算子の移し方」（`docs/design/02-impl/02-07-bytecode.md` 160〜183 行）: `EQV` は「そのほかの等値の型」の構造の `=` であり、関数の値や中身を見せない型の値を受け取らない。
- 02-08「組み込みの関数の呼び出し」（`docs/design/02-impl/02-08-vm.md` 204 行）: `EQV` など値の構造を辿る処理は、Rust の再帰に頼らず明示の積み重ねで辿る。比較の時間についての定めはない。
- 02-09「メモリの管理」（`docs/design/02-impl/02-09-runtime.md` 27 行）: 回収は止めて行う非移動のマーク・スイープで、安全点でだけ行う。`values_equal` は回収しない区間（`ValueCtx<'e>`）の中で走るので、比較の間に対象は動かず消えない。`ValueCtx::object_id`（`crates/benitoite/src/runtime/heap/ctx.rs` 436 行、番地から作る `ObjId`。`runtime/heap/value.rs` 235 行、`Hash`・`Eq` を持つ）は、比較の間ずっと対象の識別に使える。
- 02-09「一つの操作で作る値の大きさの上限」（247〜269 行）: 上限は、組み込みの関数が結果として作る `String`・`Bytes`・`List` の値の大きさに当てる。比較の作業用のメモリ（今の `pending` の `Vec` も含む）は対象ではない。

### 3. 対策の案の比較

#### 案 (a): 調べ始めた対象の組を覚える

内容: 二つのヒープの対象の組 `(object_id(a), object_id(b))` を、局所の検査（種類・`tag`・欄の数・長さ）を通して子を積んだときに集合へ入れる。同じ組に再び出会ったら、子を積まずに等しいとして進める。

正しさ:

- `values_equal` は、どこかの組が等しくないと分かった時点で `false` を返して終わる（146〜148 行、28・37・44 行）。したがって、子を積んだ組は、最後には「等しいと確かめ終える」か「全体が `false` で終わる」かのどちらかである。2 回目以降の出会いを省いても、全体が `true` を返すのは、覚えたすべての組の子孫を一度ずつ調べ終えて、どれも等しかったときだけである。よって結果は今と同じになる。
- 1.1 のとおり辿る順序は深さ優先なので、循環がなければ、同じ組に 2 回目に出会う時点で、1 回目の組の子孫はすべて調べ終えている（等しくなければ既に終わっている）。「調査中の組に出会う」場面は循環があるときにしか起きない。
- 循環: 等値の型の値は、作った後に変わらない値を子に持って下から作るので、等値の型の対象だけをたどる限り循環しない。循環を作れる `Reference`（セル）と `Lazy` は等値の型ではなく、比較に来れば `Stop::Internal` を返す。仮に循環があっても、案 (a) は同じ組を二度展開しないので必ず終わる（そのときの結果は、循環を無限に展開した木どうしの等しさになる）。
- NaN: `[nan] = [nan]`（別々のリスト）は、要素の組 `(Float(NaN), Float(NaN))` が即値なので覚える対象にならず、毎回 IEEE 754 で比べて `false`。同じ参照 `x = x`（`x` は NaN を含む）も、1 回目の出会いで `(x, x)` の子孫を辿って NaN の組に当たり `false` を返す。2 回目の出会いが省かれるのは、1 回目が等しいと確かめ終えたときだけである。今のテスト（275〜278 行、419〜425 行）は変えずに通る。
- 非等値の型の検査: 1 回目の出会いでは今と同じ検査を行うので、`values_equal(ctx, bad, bad)` が `Stop::Internal` を返すテスト（434〜437 行、481〜485 行）も変わらない。覚えるのは局所の検査を通した後とする。

費用:

- 時間は、覚えた組の数と各組の子の数の積の和、すなわち「共有を展開しない大きさ」に比例する。二つの値の対象の数を m・n とすると、異なる組の数は最悪 m×n であり、多項式で抑えられる。共有を持たない値どうしでは、組の数は今の比較の手数と同じである。
- 普通の比較の速さへの影響: 小さな値の比較で毎回 `HashSet` を作ると、確保と SipHash の費用がかかる。次の工夫で抑える。
  1. 歩数を数え、一定の歩数（例: 1,024）を超えてから集合を作り、覚え始める。超える前に調べた組は覚えていないので、超えた後にもう一度だけ展開されうるが、展開された組はそこで覚えるので、全体は「閾値＋共有を展開しない大きさ」で抑えられる。
  2. 覚えるのは、子にヒープの対象（`Value::Obj`）を一つ以上持つ組だけにする。欄がすべて即値の構成子（`Pair(1, 2)` など）や文字列は、もう一度比べても欄の数か中身の長さに比例する費用しかかからず、指数の展開を起こさない。指数の展開は子を持つ組を通ってしか起きないので、子を持つ組を覚えれば足りる。リストの頭の組とマップ・集合の根の組も覚える。リストの内部ノードは要素の並びとしてしか辿らない（67〜74 行）ので、要素の数より多く展開されることはなく、覚えなくてよい。
- `fib`・`loop` などのベンチマークは `EQV` を通らないので影響しない。1 の閾値の下では、`EQV` を通る普通の比較に加わるのは歩数の加算一つである。`tools/bench/programs/` の `tree`・`map`・`eval` などが `EQV` を使うかは、短い測定（スキル `benchmark`）で確かめる。
- メモリ: 集合の要素は 16 バイトの組と表の付加分で、1 要素あたりおよそ 20〜40 バイトである。覚える組の数は比較の手数を超えない。例えば `Option.Some(Pair(1, 2))` を 100 万個持つ二つのリストの比較では、100 万個の組を覚え、数十 MB を一時に使う。比べる二つの値自身がヒープで占める量（対象一つが頭 32 バイトと欄）より小さいが、今の比較（積み重ねは深さ程度しか使わない）より多い。02-09 の大きさの上限は作る値に当てるもので、作業用のメモリには当てない。確保に失敗したときは、今の `pending` の `Vec` と同じく Rust の確保の失敗として処理系が止まる。上限を設けるかは 6 節で設計者に尋ねる。

実装の大きさ: `equal.rs` の中に、閾値と集合を持つ非公開の小さな型（例: `PairMemo`。`fn should_expand(&mut self, a, b) -> bool`）を加え、構成子・リスト・マップ・集合の分岐で子を積む前に呼ぶ。数十行である。マップの鍵の比較（`keys.rs`）にも同じ型を使えるよう、`runtime` の中の非公開のモジュールに置くとよい。`ValueCtx::object_id` の `///` のコメント（`value.rs` 233 行の `ObjId` の「テストで到達可能性を独立に計算するために使う」）を、比較でも使う旨に直す。

凍結した型とシグネチャ: `values_equal` のシグネチャ（10-08「構造の等しさ」の `sig=src/runtime/equal.rs`）も、`ValueCtx::object_id` と `ObjId`（10-08 の 490・1050 行）も変えない。`Opcode` も変えない。

#### 案 (b): 同じ対象で `Float` を含まない型なら調べない

内容: `same_object(a, b)` で、かつ型が `Float` を含まないなら、成分を調べずに等しいとする。

正しさ: `Float` を含まない等値の型の値は、どの成分も反射的に等しい（`Decimal` は数で比べ、NaN を持たない）ので、同じ対象なら等しい。条件を満たすときに限れば正しい。

足りない点:

- 別々に作った等しい値（`grow(64)` を二回呼んだ結果どうし、ファイルから二度読んで作った木どうしなど）では、比べる組の左右が同じ対象になることがない。TODO-220 の本文の「共有した構造を持つ等しい二つの値」はこの場合を含み、案 (b) では指数時間のままである。案 (b) が効くのは、`x = x` と、共有した部分を持つ値どうし（元の値と、その一部を変えた値）の比較だけである。
- `Float` を含む型（`Float` の葉を持つ木など）では、同じ対象でも省けず、指数時間のままである。

型の情報が実行時に要るか:

- 値の頭に型の情報はない。対象の頭（`runtime/heap/core.rs` 98〜106 行の `ObjHeader`）は種類・長さ・`tag` などを持つだけで、型を消している（01-12 267 行）。
- コード生成は `equality`（`emit.rs` 545 行）で型を見ているので、型が具体的に分かる位置では「`Float` を含まない」印を命令に渡せる。型検査器が求めた鍵の型の要約（02-05）を使えば判定できる。ただし `EQV A B C` にオペランドの空きはないので、別の命令（例: `EQVK`）を加えることになり、凍結した `Opcode`（10-07 の 225 行ほか）と、検証器・生存の解析・逆アセンブラの表を変える。
- 型変数の多相な関数の中の `=` は、`[T: key]` なら `Float` を含まないと分かるが、`[T: equality]` では分からない。組み込みの制約は辞書を渡さないので、実行時にも知る手段がない。`Assert.equal`・`Assert.notEqual`・`List.contains` はどれも `[T: equality]` であり、組み込みの関数には型を渡さないので、案 (b) の利益を受けない。

変形 (b'): 対象の頭に「推移的に NaN を含む」印を持たせる。作るときに子の印から求めれば、同じ対象で印がなければ等しいと正確に言える。しかし、すべての構成子・リストの内部ノード・マップのノードの確保で子を調べる費用がかかり、ヒープの頭の形（10-08 の内部の層）を変える。別々に作った値には効かない点は案 (b) と同じである。

#### 案 (c): そのほか

- 構造のハッシュを対象ごとに持ち、まず比べる: ハッシュが違えば等しくないとすぐ分かるが、ハッシュが同じでも等しいとは言えない（衝突と NaN）ので、等しい値どうしの比較は速くならない。本項目は等しい値どうしが問題なので役に立たない。対象ごとにハッシュを持つ費用もかかる。
- 値を作るときに同じ構造の対象を一つにまとめる（hash-consing）: 確保のすべてに表の引きを加え、ヒープと回収の設計を変える。費用が大きすぎる。
- 同じ対象の組だけを覚える（`same_object` の組に限った案 (a)）: `x = x` には効くが、別々に作った値に効かない点は案 (b) と同じである。
- 比較の歩数に上限を設けて資源の不足で止める: 指数時間で止まらない状態は避けられるが、正しく等しい値の比較が失敗する。保証を弱めるので採らない。

#### 比較の表

| | (a) 組を覚える | (b) 同じ対象で `Float` を含まない型 | (b') NaN の印 |
|---|---|---|---|
| 別々に作った共有を持つ値 | 多項式 | 指数のまま | 指数のまま |
| `x = x`（`Float` を含む型） | 多項式 | 指数のまま | 印がなければ定数時間 |
| `Assert.equal`・`List.contains`・`[T: equality]` | 効く | 効かない | 効く |
| NaN の扱い | 今と同じ | 今と同じ | 今と同じ |
| 普通の比較への影響 | 閾値の下では歩数の加算だけ | なし | 確保ごとに印を求める |
| 凍結した型・シグネチャ | 触れない | `Opcode` を加える | ヒープの頭を変える |
| 実装の大きさ | 小（`equal.rs` と `keys.rs`） | 中（コード生成・命令の表・VM） | 大（ヒープ・全確保経路） |

### 4. 推奨とテストの案

#### 4.1 推奨

案 (a) を採る。次の範囲とする。

1. `runtime/equal.rs` の `values_equal` に、閾値付きで子を持つ組を覚える仕組みを入れる。49 行のコメントを、同じ対象でも 1 回目は成分を調べる理由と、2 回目からは省く理由に書き直す。
2. 同じ仕組みを `runtime/map/keys.rs` の `compare` にも入れる。順序の比較でも、深さ優先で辿るので、2 回目の出会いの時点で 1 回目は `Ordering::Equal` と確かめ終えている（そうでなければ既に結果を返している）。`tree.rs` 233 行の自己比較は 1 回目の出会いなので、種類の確かめは保たれる。鍵の型は `Float` を含まないので、同じ対象なら `Equal` とする近道も正しいが、233 行の確かめを省いてしまうので、案 (a) の形で揃える。
3. 参照インタプリタの `values_equal`（`refinterp/value.rs` 121 行）と橋渡しの変換は直さない。前者は本番の経路で複合の値を比べず、後者は共有を展開する別の問題である（4.3 と 6 節）。

#### 4.2 テスト

持ち主の境界は、ランタイムの公開の関数 `values_equal` と `compare_keys` である（スキル `test-audit`「持ち主の境界」）。主なテストは `runtime/equal.rs` の `mod tests` に一つ、表の形で置く。

- 作成時の関門の答え: 守る契約は「共有した構造を持つ値の比較が、共有を展開しない大きさに比例した時間で終わり、NaN の扱いを変えない」である。退行は、覚える仕組みを外す、同じ対象の組を無条件に等しいとする（NaN を取りこぼす）、覚える時点を局所の検査の前にする（非等値の型を取りこぼす）、のどれかである。既存のテストは共有した構造を持つ値を作らないので、前者を捕まえない。公開の口は加えない。
- 準備（`heap.epoch` の中）:
  1. `a` と `b` を、`Value::Int(1)` から始めて `ctx.alloc_fields(FieldsKind::Ctor, 1, &[x, x])` を 64 回重ねて、別々に作る。`values_equal(a, b)` が `true`、`values_equal(a, a)` が `true`。
  2. `c` を、一番下の葉だけ `Value::Int(2)` にして同じく作る。`values_equal(a, c)` が `false`。
  3. `n` を、一番下の葉を `Value::Float(f64::NAN)` にして作る。`values_equal(n, n)` と、別に作った `n2` との `values_equal(n, n2)` がどちらも `false`。
  4. 一番下の葉を `Value::Float(0.0)` と `Value::Float(-0.0)` にした二つが `true`。
  5. 同じ形を、リストで（`list::from_values(ctx, &[x, x], ..)` を重ねる）と、マップの値で（`map::map_insert` で `0 → x` と `1 → x`）作り、1 と 3 を確かめる。リストの分岐とマップの分岐で覚える処理を通すためである。
  6. 鍵の比較: 1 の `a` と `b` を鍵にして `compare_keys(a, b)` が `Equal`、2 の `c` と比べて `Less`。置き場所は `runtime/map/tests.rs` の既存の表（318〜322 行の付近）に行を足す。
- 大きさ: 64 段なら、覚える組は 64 個程度で、テストは一瞬で終わる。Miri でも同じ大きさで済むので `cfg!(miri)` で変える必要はない。長いテスト（`#[ignore = "long: ..."]`）にしなくてよい。
- 直す前に失敗することの確かめ: 直す前のコードではこのテストは 2^64 の手数で終わらない。前の改造（TODO-186 の作業 A）と同じく、直す前に `timeout` を付けて走らせ、止まることを確かめて報告に書く。直す前に終わる形で失敗させたいなら、段数を 30 程度にして時間を測るのではなく、`timeout` で確かめるほうが環境の速さに左右されない。
- `gc-stress` の構成: `values_equal` は回収しない区間の中で走り、安全点を持たないので、Rust のテストは `gc-stress` の影響を受けない。

ゴールデンテスト（`crates/benitoite/testdata/eval/`）は、次の理由で主なテストにしない。

- VM の `EQV`・`%eq`・`Assert.equal`・`List.contains` は、どれも同じ `values_equal` を呼ぶ（1.3）。経路ごとにテストを足すことは、`test-audit` の「共有の補助の処理を、使う側ごとに繰り返し確かめるテスト」に当たる。
- ゴールデンテストは参照インタプリタとの差分も取る（`crates/benitoite/tests/golden.rs` 664〜715 行）。参照インタプリタは `%eq` を呼ぶときに値を変換し、共有を展開する（1.4）ので、`grow(64)` どうしの `=` は参照インタプリタの側で終わらない。置くなら `EXPENSIVE_REFERENCE_CASES`（47 行）に加えて参照インタプリタとの比較から除く必要がある。

CLI からの確かめ（言語の利用者が書く `grow` の形）を残したい場合は、次の形のゴールデンテストを一つだけ置き、参照インタプリタとの比較から除く。`gc-stress` の構成でも、生きている対象は 64 個程度なので短い。

```text
// spec: 01-06 等値の型
import Benitoite.Unofficial.IO.Console

data Tree
  Leaf(Float)
  Node(Tree, Tree)
end data

function grow(n: Integer, leaf: Float) -> Tree
  return if n = 0 then
    Tree.Leaf(leaf)
  else
    bind t <- grow(n - 1, leaf)
    Tree.Node(t, t)
  end if
end function

function main() -> Unit uses Console.Write
  bind a <- grow(64, 1.0)
  Console.writeLine(if a = grow(64, 1.0) then "equal" else "different" end if)
  bind n <- grow(64, 0.0 / 0.0)
  return Console.writeLine(if n = n then "equal" else "different" end if)
end function
```

期待する出力は `equal` と `different` である。構文は実装の前に `benitoite check` で確かめる（この調査では走らせていない）。

#### 4.3 参照インタプリタ

- 4.2 のゴールデンテストを置かないなら、参照インタプリタは直さなくてよい。言語の `=` は橋渡しで VM と同じ `values_equal` を呼ぶので、案 (a) の結果を共有する。
- ただし、橋渡しの変換が共有を展開する問題は残る。共有した構造を持つ値を組み込みの関数に渡すと、参照インタプリタの差分テスト（ゴールデンテストと `random_programs`）が指数時間とメモリを使う。差分テストの道具の問題なので、新しい項目の候補とする（6 節の 3）。

### 5. 設計書の直し方

- 02-08「組み込みの関数の呼び出し」（`docs/design/02-impl/02-08-vm.md` 204 行の段落）: 明示の積み重ねで辿る決定の後に、次の趣旨を【決定】で加える。「構造の `=`（`EQV`）と鍵の順序の比較は、子を持つ対象の組を調べ始めたら覚え、同じ組に再び出会ったら調べない。比較の時間は、共有を展開しない値の大きさに比例する。同じ対象の組でも 1 回目は成分を調べるので、`Float` の NaN を含む値は自分自身と等しくならない。」理由として、共有した部分木を持つ値の比較が深さに対して指数時間になるのを防ぐことと、型を消した値では「`Float` を含まない型なら同じ対象を省く」判定ができないこと（`[T: equality]` の関数の中の `=` に型の情報がない）を 1〜3 文で書く。歩数の閾値を書くかは、比較の結果を変えない実装の細部なので、数値は書かず「小さな比較では覚えない」とだけ書く。
- 02-07「コード生成」の「演算子の移し方」（`docs/design/02-impl/02-07-bytecode.md` 183 行）: `EQV` の意味の段落は変えなくてよい。案 (b) を採らないので、命令の表も変えない。
- 01-spec: 意味は変わらないので直さない。形式化（`formal/`、07-04）も、δ の値が変わらないので直さない（`check-formal.sh` は不要）。
- 03-06「Map と Set（初回リリース版）」: 鍵の順序の定義は変わらないので直さない。
- 07-02「性能の見込み」に比較の時間の性質を書くかは任意である。02-08 に書けば足りる。

### 6. 設計者に決めてもらう点

1. 覚える組の数に上限を設けるか。
   - 選択肢 A（推奨）: 上限を設けない。覚える組は比較の手数を超えず、比べる二つの値がヒープで占める量より小さい。上限を設けると、上限を超える大きな値で指数時間に戻りうる。
   - 選択肢 B: 上限（例: 2^20 組）を設け、超えたら覚えるのをやめる。作業用のメモリは抑えられるが、計算量の保証は上限の内側だけになる。
   - 選択肢 C: 上限を超えたら資源の不足として止める。正しく等しい値の比較が失敗するので推奨しない。
2. マップの鍵の比較（`keys::compare`）も同じ改造で直すか。
   - 推奨: 直す。同じ仕組みを使え、実装は小さい。鍵に共有した構造を持つ値を使う場面は少ないが、`Map.insert`・`Map.get` が指数時間になる穴を同じ理由で残さない。
   - 別の項目にする場合は、docs/todo に新しい項目として加える。
3. 参照インタプリタの橋渡しの変換が共有を展開する問題（4.3）を、新しい項目として docs/todo に加えるか。
   - 推奨: 加える。本改造ではゴールデンテストを置かないか、置くなら `EXPENSIVE_REFERENCE_CASES` で除き、変換の直しは別の項目にする。
4. ゴールデンテストを置くか。
   - 推奨: 置かない。主なテストは `runtime/equal.rs` と `runtime/map/tests.rs` の Rust のテストとする（4.2 の理由）。CLI の経路を残したいなら、4.2 の一つだけを参照インタプリタとの比較から除いて置く。

### 7. 範囲の外で見つけた点

### 2. TODO-208 要求の対象の文法

#### 2.1 一次資料で確かめた規則

- RFC 9112 §3.2: `request-target = origin-form / absolute-form / authority-form / asterisk-form`。要求の対象に空白を許さない。正しくない要求の行を受けた側は、400 か、対象を正しく符号化した 301 で応じるべきであり（SHOULD）、直して処理するべきでない（SHOULD NOT）。理由として、正しくない要求の行が経路の上の安全のための検査をすり抜けるために作られうることを挙げる。この文は §3.2 にある（rfc9112.txt で、直前の見出しが「3.2. Request Target」であることを確かめた）。
- RFC 9112 §3.2.1: `origin-form = absolute-path [ "?" query ]`。RFC 9110 §4.1: `absolute-path = 1*( "/" segment )`。起点形は必ず `/` で始まる。
- RFC 9112 §3.2.2: クライアントは中継へ要求するときに絶対形を送る。「A server MUST accept the absolute-form in requests」。
- RFC 9112 §3.2.3: 「The "authority-form" of request-target is only used for CONNECT requests.」`authority-form = uri-host ":" port`。
- RFC 9112 §3.2.4: `*` の形は、サーバ全体への `OPTIONS` に使う。クライアントは `*` だけを送らなければならない。
- RFC 9110 §7.1: `CONNECT` の対象は host と port、`OPTIONS` の対象は `*` でもよく、「These forms MUST NOT be used with other methods.」。
- RFC 9110 §9.3.6: `CONNECT` の対象は host と port だけからなる。「A server MUST reject a CONNECT request that targets an empty or invalid port number」で、典型的には 400 で応じる。また、起点のサーバは `CONNECT` を受け付けてもよい（MAY）が、ほとんどは実装しないとする。
- RFC 3986: `pchar = unreserved / pct-encoded / sub-delims / ":" / "@"`（§3.3）、`query = *( pchar / "/" / "?" )`（§3.4）、`pct-encoded = "%" HEXDIG HEXDIG`（§2.1）、`unreserved = ALPHA / DIGIT / "-" / "." / "_" / "~"`（§2.3）、`sub-delims = "!" / "$" / "&" / "'" / "(" / ")" / "*" / "+" / "," / ";" / "="`（§2.2）、`reg-name = *( unreserved / pct-encoded / sub-delims )`（§3.2.2）、`port = *DIGIT`（§3.2.3）。

このため、起点形のパスとクエリに現れてよい 0x21〜0x7E の文字は、英数字と `-._~!$&'()*+,;=:@/?%` である（`%` は後に 16 進の 2 桁が続くときだけ）。外の文字は `"`・`#`・`<`・`>`・`[`・`\`・`]`・`^`・`` ` ``・`{`・`|`・`}` の 12 個である。TODO-208 の本文の一覧は `[` と `]` を落としている（`[` と `]` は RFC 3986 の gen-delims で、authority の IP-literal にだけ現れ、pchar にも query にも入らない）。0x80 以上のバイトは、どの規則にも入らない。

ブラウザなどが従う WHATWG URL Standard（https://url.spec.whatwg.org/ 、2026-10-12 に確かめた）の符号化の集合は次のとおりである。

- C0 control percent-encode set: C0 の制御文字と、U+007E より大きいすべての符号位置。
- query percent-encode set: 上に、空白・`"`・`#`・`<`・`>` を加える。special-query の集合は、さらに `'` を加える。
- path percent-encode set: query の集合に、`?`・`^`・`` ` ``・`{`・`}` を加える。

つまり、この規格に従う URL の直列化では、`"`・`<`・`>`・0x80 以上はパスにもクエリにも生で現れないが、`[`・`\`・`]`・`|` はパスにもクエリにも、`^`・`` ` ``・`{`・`}` はクエリに、生のまま残りうる（例: `?a[]=1`、`?q={x}`）。実際のブラウザがこの規格どおりに送るかは確かめていない。curl などのコマンドの道具が、利用者の書いた 0x80 以上の文字や `"` を符号化するかも確かめていない。

#### 2.3 案

**案 A（最小: 文字だけ）**: 変換前の対象が、標準に従うブラウザが生で送らない文字（`"`・`<`・`>` と 0x80 以上のバイト）を含めば 400 にする。形は検査しない。

- 長所: 変更が小さい。`#` の 400 と同じ位置（http.rs:828）に一つの判定を足すだけで済む。WHATWG の符号化の集合に従うクライアントからの要求は拒まない見込みである。
- 短所: `/` で始まらない起点形と、`CONNECT` の port の MUST が残る。0x80 以上を拒むと、生の UTF-8 を送る道具（あるかは確かめていない）からの要求が 400 になる。

**案 B（中: 文字＋形。推奨）**: 案 A に加えて、変換前の対象の形を次のとおり確かめる。

1. `/` で始まれば起点形。どの方法でも受け付ける。ただし `CONNECT` は 400。
2. `*` だけなら `*` の形。方法が `OPTIONS` のときだけ受け付け、ほかは 400。`*` の後に文字が続けば 400。
3. `http://`・`https://` で始まれば絶対形。今の `origin_target` のとおり外す。`CONNECT` は 400。外した後のパスの部分にも案 A の文字の検査を当てる（変換前の対象全体に当てれば足りる）。
4. 方法が `CONNECT` なら authority 形として、最後の `:` で host と port に分け、host が空でなく `valid_host_characters` に合い、port が 1 桁以上の数字で 65535 以下であることを確かめる。外れれば 400。
5. 上のどれにも当たらない対象（`foo`、`?x`、`ftp://h/p`、`GET h:443`）は 400。

`[`・`\`・`]`・`^`・`` ` ``・`{`・`|`・`}` と、`%` の後が 16 進でない場合は、今のとおり受け付け、受け付ける理由を 03-09 に書く。

- 長所: RFC 9110 §7.1 の MUST NOT と §9.3.6 の MUST に合わせられる。RFC 9112 §3.2.2 の MUST（絶対形を受け付ける）は `http`・`https` について今のとおり守る。handler に渡る `path` が、`/` で始まるか、`OPTIONS` の `*` か、`CONNECT` の host:port のどれかに限られ、`Http.pathSegments` での振り分けを書く側が想定しやすい。ブラウザが生で送りうる文字は拒まない。
- 短所: 文字の検査は RFC 3986 の一部だけになる（「直して処理しない」は守るが、「文法に合わない要求の行を 400 にする」は一部の文字について守らない）。この逸脱の理由（WHATWG の集合に従うクライアントが生で送りうる）を設計書に書く必要がある。
- `http`・`https` 以外の scheme の絶対形の状態コード: 400 にする案を書いた。RFC 9110 には誤った宛先の要求への 421 があるが、その節の当てはまりは確かめていない。

**案 C（全部）**: 案 B に加えて、12 個の文字すべてと、`%` の後が 16 進の 2 桁でない場合を 400 にする。RFC 3986 の文法どおりになる。

- 長所: RFC 9112 §3.2 の SHOULD を文字どおり守る。
- 短所: `?a[]=1`（PHP 風の配列の名前）や `?q={x}` のように、WHATWG の規格では生で残る文字を含む要求が 400 になりうる。03-09 が決めた `query` の `%G0` の扱いと、l30 のテスト `QUERY_CASES`（`/path?q=a+b%20c&a&&b=c=d&bad=%G0&tail=%`。`crates/benitoite/tests/l30_http_server.rs:177-186`）を変える必要がある。`Http.pathSegments` の「戻せない要素を残す」規則も、サーバから来る `path` については使われなくなる。

**推奨: 案 B。** 理由: 設計原則 1（誤りを実行前・処理前に報告する）に沿って、RFC の MUST に当たる形の誤りは確実に拒み、文字については、標準に従うクライアントが生で送らないものだけを拒む。案 C は、利用者（非プログラマを含む）がブラウザで試したときに 400 になる場合を増やし、原因が分かりにくい。0x80 以上を拒むかは、設計者に決めてもらう点に挙げる（6 節の D2）。

#### 3.2 他の実装（一次資料で確かめた範囲）

- nginx（https://nginx.org/en/docs/http/ngx_http_core_module.html 、2026-10-12 に確かめた）: `lingering_close` の既定は `on` で、クライアントがまだ送ってくると推定したときだけ、閉じる前に追加のデータを待って読み捨てる。`lingering_time`（既定 30 秒）が読み捨てる総時間、`lingering_timeout`（既定 5 秒）がデータを待つ一回の時間の上限である。`off` はプロトコルを壊すので通常は使うべきでないと書く。
- Go の `net/http`（`src/net/http/server.go` の master、2026-10-12 に確かめた）: `closeWriteAndWait` は、残りを書き出して `CloseWrite`（送信の側を閉じて FIN を送る）した後、読まずに `rstAvoidanceDelay`（500 ミリ秒）眠ってから閉じる。コメントは、クライアントが RST の前に FIN を処理する見込みを上げるためと書く。`maxPostHandlerReadBytes`（256 KiB）は、handler が読まなかった本体を接続の再利用のために読む上限で、段階的な閉じ方の上限ではない。
- hyper: 確かめていない（未確認）。

#### 3.3 実装の案

今の作りでは、拒否した接続は `Listener::connections` の中にあり、`accept` の呼び出しのたびに VM のスレッドで非ブロックに進む。この形に合わせて、`Connection` に「閉じる途中」の段を足すのが素直である。

**L1（推奨）: イベントループで段階的に閉じる。**

1. 拒否の応答を書き終えたら（今 `Dropped` を返す 378 行）、`socket.shutdown(Shutdown::Write)` を呼び、`Connection` を閉じる途中の段（例: `Lingering { deadline, discarded }`）にする。`mio::net::TcpStream::shutdown` は mio 1.2.4 の `src/net/tcp/stream.rs:134` にある。`shutdown` が失敗したら、今のとおり落とす。
2. 閉じる途中の接続は READABLE で登録し（`arm` の 1259-1263 行の向きの選び方に段を足す）、読めるたびに `WouldBlock` まで読み捨てる。`read` が 0（相手が閉じた）、誤り、読み捨てた量が上限を超えた、期限を過ぎた、のどれかで落とす（`close(2)`）。
3. 期限で `accept` に戻るため、`arm` が返す `Armed::deadline` を、`retry_at` と閉じる途中の接続の最も早い期限のうち早い方にする。期限で起きた `accept` は、`retry_at` を過ぎていなければ受け付けをやり直さず、接続を進めるだけにする（今の 412 行の条件のとおり）。`Connection::advance` に `now` を渡す必要がある。
4. 読み捨ては、上限を超えたら読むのをやめて落とすので、一つの接続が VM のスレッドに課す仕事は上限で抑えられる。上限の前に `WouldBlock` を待たずに読むのをやめる形（一回あたりの予算）は、mio の通知が edge triggered であるため、再登録で準備の通知が再び来るかを確かめてからでないと使えない（未確認）。

- 長所: 作業用のスレッドを使わない。今の `retry_at` のタイマーの経路をそのまま使える。読み捨てる間も、ほかのタスクと受け付けは進む。将来の 408（TODO-069）も同じ段で閉じられる。
- 短所: `accept` が呼ばれている間しか進まない。`Http.serve` は受け付けを繰り返すので問題にならないが、`Http.accept` を一度だけ呼んで待ち受けを閉じるスクリプトでは、閉じる途中の接続は `Http.Listener` の解放のときに落ちる（そのときは今と同じく RST になりうる）。02-09 の 219 行にこのことを書き足す。

**L2: Go の形（半分閉じて、読まずに待つ）。** `shutdown(Write)` の後、読まずに一定時間（例 500 ミリ秒）保持してから閉じる。

- 長所: 読まないので CPU を使わず、量の上限が要らない。相手の書き込みは受信のバッファが埋まると止まる。
- 短所: 期限で閉じるときに未読が残れば、結局 RST を送る（相手がそれまでに読んでいれば害はない）。相手が先に閉じたことに気付けず、毎回期限まで記述子を持つ。RFC 9112 §9.6 の「読み続ける」形ではない。

**L3: 作業用のスレッドでブロックして読み捨てる。** 拒否した `std::net::TcpStream` を作業用のスレッドへ渡し、読み取りの期限付きで読み捨てる。

- 短所: 作業用のスレッドは最大 64（`crates/benitoite/src/runtime/sched/parts.rs:150`）で、1〜2 秒ずつ塞ぐと、拒否が続くとほかの IO（ファイル、クライアント、`Exchange` の解放）が待たされる。採らない。

#### 3.4 上限の案

拒否の応答は 100 バイトに満たないので、相手が応答を読むまでの時間は往復一回と OS の切り替え程度である。相手が本体を書き終えてから応答を読む作りなら、相手が書き終えるまで読み捨てなければ応答は届かない。413 の相手は 16 MiB を超える本体を送るので、どんな上限でもこの種の相手は救えない（相手が並行して読むか、書き込みの失敗の後にも受信を読む作りでなければならない）。各種のクライアントがどちらの作りかは確かめていない。

| 案 | 量 | 時間 | 向き |
|---|---|---|---|
| 小 | 64 KiB | 1 秒 | 今のテストのような小さな残り（431 の数バイトなど）だけを救う |
| 中（推奨） | 1 MiB | 総時間 2 秒（拒否の応答を書き終えてから） | 並行して読む相手には十分で、書き終えてから読む相手でも 1 MiB 以内の残りなら救える。一つの接続の仕事を 1 MiB の読み（8 KiB で 128 回）に抑える |
| 大 | 16 MiB（本体の上限と同じ） | 5 秒 | 正しい要求でも 16 MiB は読むので、一つの接続あたりの負担は正しい要求と同じ。ただし 413 の相手の残りは 16 MiB を超えるので救えず、得るものが少ない |

nginx の既定（総 30 秒、待ち 5 秒）は、インターネットに出すサーバの既定であり、手元か中継の後ろで使う前提の Benitoite には長い。データを待つ一回の期限（nginx の `lingering_timeout` に当たるもの）は、総時間 2 秒なら分けなくてよい。

#### 3.5 同時の接続の数の上限に数えるか

今は上限がないので、数えるかどうかは振る舞いを変えない。閉じる途中の接続は記述子を持ち続けるので、TODO-069 で読みかけの接続の数の上限を加えるときは、閉じる途中の接続も数えることを勧める（数えないと、拒否される要求を繰り返し送って記述子を使い果たせる）。ただし上限に達したときは、新しい接続を拒むより、最も古い閉じる途中の接続を先に落とす方が、正しい要求を通しやすい。この点は TODO-069 の改造で決めればよく、本改造では「`Listener::connections` に残す（数えられる位置に置く）」ことだけを決める。

#### 3.6 当てる応答

- 処理系が `Connection` で返す 400・413・431 のすべてに当てる。本体の途中の chunk の誤りの 400 でも、413 と同じく残りがありうるからである。
- `Exchange` の通常の応答と解放の 500 には当てない。要求を読み終えてから返すので、未読が残るのは相手が宣言より多く送ったときだけである。当てるには、`Exchange` を落とした後の記述子を `Listener` か実行ごとの状態の「閉じる途中」の並びへ移す仕組みが要り（`Exchange` は自分の `Listener` を知らない）、変更が大きい。keep-alive は今ない（一つの接続で一つの要求。03-09 の 123 行）ので、「keep-alive を切るとき」は当てはまらない。
- 将来 408 を加えるとき（TODO-069）も、同じ段を使う。

#### 3.7 テストの案

- 再現のテスト（統合、`l30_http_server.rs`）: 相手は、`content-length: 16777217` の頭と、本体の一部（例 256 KiB。中の案の上限 1 MiB より小さい）を書いて書き込みを止め、応答をすぐには読まずに少し待つ（例 200 ミリ秒。サーバが 413 を書いて閉じるまでの時間）。その後に `read_to_end` し、`Ok`（RST でない）で、応答が `HTTP/1.1 413 ` で始まることを確かめる。今の実装では、サーバが未読の本体を残して `close(2)` するので RST になり、相手の OS が未読の応答を捨てれば応答が空になって落ちる。直した後は、サーバが FIN を送った後に相手が読み終えて閉じ、サーバはその EOF で閉じる。431 にも同じ形（64 KiB を超える頭の後に残りを送る）を一つ作る。
- 作業の最初に、このテストを今の実装に対して macOS で数回走らせ、落ちる（応答が消える）ことを確かめる。macOS で再現しなければ、TODO-216 の Linux のコンテナで確かめる。どちらでも再現しなければ、テストは退行の検査（FIN で終わること＝`read_to_end` が `Ok` になること）として残す。macOS で RST が未読の応答を消すかは確かめていない（未確認）。
- 期限と量の上限: 単体テスト（`http/tests.rs`）で、相手が上限を超えて送り続けるとき、時計（`now`）を進めると接続が `connections` から消えることを確かめる。本物の時間を待たずに、`accept` に渡す `now` を進めて確かめる。`Armed::deadline` が閉じる途中の接続の期限を返すことも確かめる。
- 今の `request` の補助（l30 の 129-141 行）の RST を許す分岐は、直した後は小さな残りの場合に要らなくなる。Linux でも通ることを確かめたうえで外すと、段階的な閉じ方の退行を全部の拒否の場合で捕まえられる。外すかは作業の中で決める（macOS と Linux の両方で確かめられなければ残す）。
- test-audit の作成時の関門を通し、テストが 10 秒を超えないことを確かめる（期限 2 秒を本物の時間で待つテストを作らない）。

### 6. 設計者に決めてもらう点

- **D1 TODO-208 の範囲**: 案 A（文字だけ）／案 B（文字＋形）／案 C（RFC 3986 のとおり全部）。推奨は案 B。理由: RFC の MUST に当たる形の誤り（`*` と authority 形の方法、`CONNECT` の port）を確実に拒み、文字は標準に従うクライアントが生で送らないものだけを拒むので、ブラウザで試した要求が 400 になる場合を増やさない。
- **D2 0x80 以上のバイトを 400 にするか**: (a) 400 にする／(b) 今のとおり受け付け、生の UTF-8 を `path` と `query` に渡す。推奨は (a)。理由: RFC 3986 の文法の外であり、WHATWG の規格ではすべての部分で符号化されるので、標準に従うクライアントは生で送らない。ただし、生の UTF-8 を送るクライアントがあるかは確かめていない。迷うなら (b) で始め、変更を一つ減らしてもよい。
- **D3 `http`・`https` 以外の scheme の絶対形の状態コード**: 400（推奨。正しくない要求の行と同じ扱いで単純）／421（RFC 9110 の当てはまりは未確認）。
- **D4 `CONNECT` の port 0**: 400 にするか受け付けるか。RFC 9110 §9.3.6 は「empty or invalid port number」を拒むとし、0 が invalid に当たるかは確かめていない。推奨は、空・数字以外・65535 超だけを 400 にし、0 は受け付ける（handler が決める）。
- **D5 TODO-215 を実装するか、どの形か**: L1（イベントループで読み捨てて閉じる）／L2（半分閉じて読まずに待つ）／実装しない。推奨は L1。理由: RFC 9112 §9.6 の形に合い、相手が先に閉じれば RST を送らずに閉じられ、今の `retry_at` のタイマーの経路で書ける。
- **D6 読み捨ての上限**: 小（64 KiB・1 秒）／中（1 MiB・2 秒）／大（16 MiB・5 秒）。推奨は中。
- **D7 当てる応答**: `Connection` で返す 400・413・431 のすべて（推奨）／413・431 だけ／`Exchange` の応答と解放にも当てる（仕組みの変更が大きい）。
- **D8 l30 の `request` の RST を許す分岐を外すか**: macOS と Linux の両方で通ることを確かめられたら外す（推奨）／残す。
- **D9 作業の分け方**: 一つの改造のディレクトリで W1 → W2 を直列に（推奨）／二つの改造に分ける／一つの作業にまとめる。
