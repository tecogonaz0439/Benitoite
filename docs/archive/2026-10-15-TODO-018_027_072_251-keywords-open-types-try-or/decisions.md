# 設計者に尋ねる問いと推す案

## 前提

Q1〜Q20 と R2・R13・R18 に対して、2026-10-15 に設計者の回答を受けた。各問いの末尾に回答を追記した。提案時の本文は判断の経緯として残し、回答と食い違う箇所は回答を優先する。他の R は推す案で詳しい設計を進めた判断であり、設計者の回答とは区別する。今回の依頼は詳しい設計と実装プランまでであり、処理系の実装開始を意味しない。

基準は [00-01「目的と設計原則」](../design/00-overview/00-01-goals.md) である。利用者が操作と結果を理解できること、契約を変えたときに検査が残ること、同じ役割の構文を増やさないことを優先する。LLM による生成・修正の成功率と人の読みやすさが構文の基準だが、今回は成功率の比較を測っていない。「こちらの語なら LLM が誤らない」という未確認の理由で決めない。

## Q1 いまの長い語とラムダの綴りを保つか

問い: `function`・`public`・`implement` と `lambda` を保ち、今回、綴りだけの置き換えを行わない形でよいか。

| 選択肢 | 内容 |
|---|---|
| A（推す案） | 現在の 34 語の綴りを保つ。宣言と関数型は function、無名の関数は lambda とする |
| B | fn・pub・impl へ縮める。宣言・関数型・終端・例を一度に直す |
| C | 長い語と短い語の両方を同義として受理する |

推す案は A である。理由: 宣言・型・終端の現在の対応を保ち、今回の失敗の扱いに関係しない大量の書き直しを避けられる。C は同じ役割の構文を増やす（原則 5）。B のほうが生成・修正に成功しやすいという実測の根拠はない。`const`・`div`・`mod` も機械的に長い語へ変えない。`else`・`shadow` の非推奨は廃止に変えない。現状の一覧と判断材料は [study/lexical.md](study/lexical.md) にある。

答え（2026-10-15、設計者）: 推す案 A で決定する。

## Q2 fn・pub・impl を名前として禁止するか

問い: 省略形を書いたときの専用の案内のために、これらをすべて予約するか。

| 選択肢 | 内容 |
|---|---|
| A（推す案） | fn・pub・impl・mut は予約しない。他言語の構文に似た形だけで案内する |
| B | 省略形を予約し、どこでも名前として禁止する |

推す案は A である。理由: すでに `fn(...) { ... }` を普通の fn の呼び出しと区別する診断がある。存在しない構文を案内するために、有効な名前まで壊す必要はない（原則 1・4）。有効な fn の呼び出しを保つ既存の負・正の入力も維持する。同梱の Skill は推奨する綴りを一つにする。

答え（2026-10-15、設計者）: 推す案 A で決定する。

答え（2026-10-15、設計者）: 推す案 A で決定する。

## Q5 新しく加える語を、どこで特別に読むか

問い: die をキーワードにし、構成子を増やせる指定は属性の名前として読む形でよいか。

| 選択肢 | 内容 |
|---|---|
| A（推す案） | die を予約する。指定は @extensible とし、extensible 自体は予約しない |
| B | die も or の後だけで読み、同名の局所変数・関数を許す |
| C | die と open / non_exhaustive 相当の語をともに予約する |

推す案は A である。理由: `try … or die` の処置と、Boolean の `… or die()` を構文だけで明確に区別できる。調べた候補内で die は 0 出現であり、今回まとめる破壊的変更として扱いやすい。C の open は File.open など既存の名前にも影響する。追加するキーワードは die の一語、削除と改名はなし、意味を持たない予約語の追加もなしとする。249 やカテゴリ C の将来の語は先取りして予約しない。

答え（2026-10-15、設計者）: 推す案 A で決定する。`die` を予約語にし、`@extensible` の `extensible` は予約しない。

## Q6 裸の try を今後も「失敗を返す」と固定するか

問い: `try e` を今後も `try e or return` と同じ意味で受理し、新しく生成するコードでは明示形を勧めるか。

| 選択肢 | 内容 |
|---|---|
| A（推す案） | 裸の try を同じ意味で残す。戻り値や実行方式で意味を変えない |
| B | 今回、明示形を必須にする |
| C | 戻り値・main・サーバモードによって return と die を自動で選ぶ |

推す案は A である。理由: 既存の契約と意味を保ち、TODO-249 の新しい捕捉も現在の try と混同させない（原則 2・4）。明示形には「返すか終了するかを同じ位置で示す」という追加の役割がある。裸の形は既存コードと短い記述のための固定した省略と位置付け、廃止を予定しない。B なら最大 646 出現の候補を確認する移行が要る。C は同じ式から作用先が読み取れなくなる。

答え（2026-10-15、設計者）: 推す案 A で決定する。裸の `try e` は `try e or return` と同じ意味で残し、廃止しない。ただし、利用者・LLM が手本として読むサンプルのソースは、文書内のサンプルを含め、すべて `or return` または `or die` の明示形へ直す。言語リファレンス（英日）、設計書の例（01-spec・08-04 の text ブロックを含む）、同梱 Skill とその生成物・日本語訳、examples の .bnt と例のソースなどを対象とする。テストデータとゴールデンテストには裸の形を確かめる入力を残し、その検査を減らさない。対象の線引きと処置の選択基準を R1 に定める。

## Q7 or の後と、式の終わりをどう決めるか

問い: 今回は処置を return・die・die(説明) に限り、任意の式への拡張は、後の明示した処置として残す形でよいか。

| 選択肢 | 内容 |
|---|---|
| A（推す案） | 専用の処置の文法にする。同じ深さの or return / or die で入力を終える |
| B | or の右を今から任意の式にし、Boolean の or との区別を型で決める |
| C | return・die を固定し、今後ほかの処置は追加しない |

推す案は A である。理由: 現在のパイプ全体に try がかかる規則を保ちながら、処置を構文で判定できる（原則 1・4）。`try r |> convert or return` はパイプ全体を入力とし、内側の括弧・ラムダ・match・try の処置まで探さない。明示形の後に演算を続ける場合は `(try r or die) + 1` と囲む。改行継続は現行の規則を使い、短いラムダは処置も同じ物理行に置く。詳細な読み方は [study/try-and-exit.md](study/try-and-exit.md#or-の境界の案) にある。

`or return` は裸の return という専用の処置であり、`or return e` は受理しない。後に、失敗 E を受け取る操作、代替値、ラムダの処置を加える場合は、明示した印と失敗時だけの評価を持つ別の文法を定められるようにする。現在未定義の `or fail …` などは今回受理しない。TODO-249 の具体名をここで決めたことにはしない。

答え（2026-10-15、設計者）: 推す案 A で決定する。

## Q8 die の型・エフェクトと使える場所をどうするか

問い: die は任意の戻り値の関数内で使え、今回の実行の失敗終了を Process.Exit で追う形でよいか。

| 選択肢 | 内容 |
|---|---|
| A（推す案） | 成功時は T、失敗時は実行結果に報告を残して終了。追加のエフェクトは Process.Exit |
| B | Console へ説明を書いて Process.exit(1) を呼ぶ。Process.Exit と Console.Write を持つ |
| C | main だけで使える、または終了のエフェクトを省く |

推す案は A である。理由: 終了を型の契約から追え、補助関数と高階関数を経由しても失われない（原則 2・3）。囲む戻り値へ Result / Option を強制せず、Process.exit[T] と同じ扱いで失敗側に T を与え、Never は新設しない。main 以外でも許すが、再利用する関数では return / 回復可能な失敗を勧める。

A の報告は、main_error と同じくホストが実行結果から描画する。Console の呼び出しへ展開しないため、Console.Write は要求しない。終了時に説明が標準エラー出力へ出ることは、Process.Exit の説明と Skill に含める。B を選ぶなら両エフェクトが必須であり、出力だけの実装で原因が結果から消えない措置も要る。ガードと lazy の直接の本体は、既存の try の禁止と純粋性の条件を保つ。

答え（2026-10-15、設計者）: 推す案 A で決定する。どの関数でも使え、`Process.Exit` が加わる。

## Q9 失敗の値を何で表示するか

問い: Result の E には既存の Show を求め、表示を要するのは die の境界だけとする形でよいか。

| 選択肢 | 内容 |
|---|---|
| A（推す案） | E: Show。IOError・NetworkError に message を使う標準実装を加える |
| B | String・IOError・NetworkError など処理系が知る型だけを許し、他は mapError で変換する |
| C | 新しいエラー表示専用の型クラスを設ける |

推す案は A である。理由: 利用者の直和型も既存の実装の仕組みで扱え、同じ表示のためだけの仕組みを増やさずに済む（原則 5・6）。Show のない型には、Show を実装するか mapError で String にする診断を出す。現在の Show[String] は引用符とエスケープを付けるので、その表示を保つ。説明の String はそのまま表示し、エラー型を消さずに使えることと、人向けの文面が全型で同じであることを混同しない。

None は `expected a value, got Option.None` という固定の原因を報告する案とする。説明付きは失敗時だけ純粋な String 式を一度評価し、元の原因を併記する。説明から直接 return・try・resume で抜ける形を禁止し、Show / 説明の計算が実行時エラーになれば既存の停止規則を使う。一般の型付きの失敗の伝播や捕捉には Show を要求しない。必要な Trait モジュールと Process.exit の依存は処理系が接続し、利用者の名前空間へ同名の暗黙の import を増やさない。

答え（2026-10-15、設計者）: 推す案 A で決定する。

## Q10 終了した理由を、出力と実行結果にどう残すか

問い: die の原因・説明・位置を今回の実行の結果に保持し、CLI とテストの実行器がそれを表示する形でよいか。

| 選択肢 | 内容 |
|---|---|
| A（推す案） | 明示的な失敗終了の情報を結果へ持つ。終了状態は 1。既存の終了と解放の経路を使う |
| B | 標準エラー出力へ書くだけで、結果は理由のない Exited(1) にする |
| C | Stop::Runtime の新しい種類にし、実行時エラーの診断として表示する |

推す案は A である。理由: テストと将来のサーバの結果にも原因を残せ、利用者が結果を確認できる（原則 3）。内部の情報はヒープの寿命を越える Value ではなく、所有した文字列とソース位置などにする。言語の新しい回復可能なエラー型として公開しない。CLI は出力の最後の転送後に失敗の報告を一度描画し、テストの実行器はそのテストを失敗として続行する。

すべてのタスクの取り消しと with の解放を既存の明示的な終了と揃え、解放・flush の失敗を補足に残して 1 を保つ。競合する終了・中断・処理系の不具合は既存の優先順位を維持し、die が常にそれらを上書きすると約束しない。任意の終了状態には Process.exit を使う。Rust の panic や即時の OS の終了は使わない。Process.Exit を明示して差し替えるハンドラは既存の機構どおり認め、TODO-249 の型付きの失敗の捕捉が die を自動で捕まえることはない。

新しい操作を Process.Exit の集合へ加えると既存のハンドラを壊すため、既存の exit の呼び出しへ報告の内部の情報を付ける案とする。ハンドラの操作の識別とシグネチャを変えず、既定の exit に到達した場合だけ原因を終了結果へ移す。処理された呼び出しの原因を後の別の終了へ持ち越さない。内部の情報の保持は形式化した型とエフェクトとは別に実行で検査する。

答え（2026-10-15、設計者）: 推す案 A で決定する。

## Q12 どの失敗の型に、その他の分岐を求めるか

問い: 今回は IOErrorKind と NetworkErrorKind に、パッケージ外で将来の構成子を扱う分岐を求める形でよいか。

| 選択肢 | 内容 |
|---|---|
| A（推す案） | この二型に指定を付ける。Result / Option は今の二択のままにする |
| B | 失敗に使う型は名前や用途から処理系が特別扱いする |
| C | 全 data、または Result の失敗の照合に一律に包括的な分岐を求める |

推す案は A である。理由: これから失敗の種類を増やす要請のある型の契約を明示できる。一般の Result を閉じたままにすれば、成功と失敗を処理する基本の二分岐を保てる（原則 1・4）。不透明な IOError / NetworkError 自体には属性を付けない。Other は既知の構成子なので、将来の構成子を覆う分岐の代わりにはならない。調べた既存の二型の照合には、今回追加すべき包括的な分岐は見つからなかった。

答え（2026-10-15、設計者）: 提案の二型への限定を採らず、標準ライブラリで失敗を表す型のうち、構成子で照合できる失敗の種類・失敗の型をすべて対象にし、`@extensible` を付ける。IOError・NetworkError など中身を見せない型は対象外とする。Result・Option は失敗の型ではなく、閉じた二択のままにする。対象の一覧と、標準ライブラリ・テストデータ・例・Skill で新たに包括的な分岐が必要になる照合の数を design.md に記す。ParseError の record への適用は R2 の補足案で扱う。

## Q13 指定の書き方・既定・利用者の型をどうするか

問い: 普通の data は今のままにし、必要な型だけに利用者も `@extensible` を付けられる形でよいか。

| 選択肢 | 内容 |
|---|---|
| A（推す案） | 引数なしの @extensible を data に付ける。既定は閉じた型 |
| B | @nonExhaustive / @non_exhaustive という名前で同じ規則を設ける |
| C | 既定を拡張可能にし、@frozen を付けた型だけ固定する |

推す案は A である。理由: 「網羅でない」という検査器側の表現より、「後の版で選択肢を増やせる」という宣言の目的を名前にできる。構文の種類を増やさず属性を使える。利用者が定義する public / public(package) の data にも同じ規則を使い、型の作者が後で増やす契約として説明する。他のモジュールから構成子を追加する機能は設けない。

同じパッケージ内は全構成子の列挙で網羅を認め、外で指定を有効にする。境界は既存の public(package) と揃える。record の欄の追加、構成子個別の欄の追加、外部の不透明な型や別名への属性は今回認めない。属性の引数・重複は診断する。C は既存のほぼすべての data の照合へ影響し、今回の目的を越える。

答え（2026-10-15、設計者）: 推す案 A で決定する。

## Q14 入れ子のパターンと選ばれない分岐も同じ規則にするか

問い: 指定付きの型を外から見る位置では「将来の値」の形を残し、入れ子・束縛・到達可能性の判定にも使うか。

| 選択肢 | 内容 |
|---|---|
| A（推す案） | 網羅性の共通の判定に将来の形を加え、変数または _ で覆う |
| B | match の最上位に _ が書かれたかだけを検査する |
| C | 現在の構成子だけで判定し、その他の分岐は文書で勧める |

推す案は A である。理由: `Result.Error(otherKind)` なら Kind の将来の値も覆える一方、Error 内を既知の種類だけで列挙すると不足することを検査できる（原則 1）。ガード付きの変数の分岐は網羅に数えない。全既知構成子の後の case other は必要なので選ばれないと警告せず、すでに case _ がある場合の後続の重複は検出する。

### R2 ParseError の record と data 限定の整合

問い: Q12 の「構成子で照合できる失敗の型を全部」には Json.ParseError・Csv.ParseError も含まれる。Q13 の data 限定をどう補うか。

推す案: Q12 の今回の明示的な対象指定を優先し、`@extensible` を data と record に認める。二つの ParseError は record のままにし、属性を付ける。外部から書いたレコードパターンも検査用の将来の形を覆わないものとする。`ParseError(message: m, ..)` の `..` は欄の省略であって、将来の形を覆う分岐ではない。match には変数か `_` の分岐が要り、構成子で分解する bind は外部では拒否する。

この補足は欄の追加を互換とする新しい保証を含まない。record は引き続き一構成子であり、構築・更新・getter の契約は保つ。属性は、外部のソースが既知の分解形だけを前提としないという保守的な使用条件を付ける。現行 record の将来の構成子を言語の値として作れるようにはしない。コンパイラが作る getter・record 更新の内部の照合には、現行宣言の閉じた網羅性を使う。利用者が書くパターンの受理条件と混ぜない。

代替案は二つの record を data へ変換して getter を手書きすることだが、構築の名前付き引数・更新・WIT の record の対応まで壊すため採らない。二型を対象外とする案は設計者の Q12 の回答を満たさない。一般の record も同じ属性・同じ使用条件にし、失敗型名に依存した特例は作らない。

理由: 指定された全失敗型を対象に含め、既存のレコード API と外部の表現を保つ。ただし将来の record の拡張方法の約束としては data より弱いので、この差を文書と公開の説明に記す。

### R3 説明・表示・終了の評価順

推す案: A。B6 の受理と同時に変更し、括弧の外で処置の後の改行を文末にし、次の字句の continues_before より優先する。通常の return、括弧内の改行の省略、or の前後の継続は保つ。die は continues_after に加えず、die や説明の閉じ括弧の後も次行の演算子へ継続しない。説明の開始括弧は同じ物理行に限る。

理由: 現在は KwReturn が continues_after に入るため、次の bind や式を取り込んでしまう。A は変更を新しい処置へ限定し、物理行の情報を捨てる前に判定できる。

設計者に尋ねる価値: 大きい。説明の開始括弧を同じ行に限ることと、通常の return の継続を残すことは利用者に見える文法である。設計では A を反映し、回答済みの決定とは扱わない。

答え（2026-10-15、設計者）: B で決定する。普通の `return` も含め、`return` の直後の改行は常に文を終え、値を次の行から書き始める継続を全面的に廃止する。値を `return` と同じ物理行で書き始めれば、その後は行末の演算子・開き括弧・`then` など、現在の改行の規則で複数行に続けてよい。`or return` もこの一般の規則で終わる。

理由（設計者）: JavaScript・Go・Python・Ruby では、`return` だけを書いた行の改行で文が終わり、値を次の行から書く形は一般的でない。JavaScript では、次の行の式の値を返さずに終わる落とし穴になる。Benitoite の普通の `return` は値が必須なので、値のない行を誤りとして報告でき、黙って意味が変わらない。普通の return と処置で規則を一つにし、検査と診断を明確にする（設計原則 4）。「一般的でない」はこの判断の理由であり、生成精度や使用頻度を今回測定した結果ではない。

改行の比較の一次資料（2026-10-15 確認）: [ECMAScript の ReturnStatement](https://262.ecma-international.org/5.1/#sec-12.9) の行終端の制約、[Go の Semicolons](https://go.dev/ref/spec#Semicolons) の return 後のセミコロン挿入、[Python の Simple statements](https://docs.python.org/3/reference/simple_stmts.html#the-return-statement) の一論理行の単文と return、[Ruby の文の区切り](https://docs.ruby-lang.org/en/3.3/syntax/miscellaneous_rdoc.html) と [return](https://docs.ruby-lang.org/en/3.3/syntax/control_expressions_rdoc.html#label-return+Statement)。Python・Ruby などの明示した行継続まで禁止されるという意味ではない。

影響の補足（設計者に確認済み）: 書けなくなる既存の形は、`return` だけを一行に書き、値を次の行から始める形である。初めの約 27 か所という見込みを調べ直した結果、現行の有効な入力の書き直しは tools/bench/wit-transfer の .bnt 6 ファイルの 24 行である。長い `if … end if` を `return if …` と同じ行から始める。その他の検査入力・文書・生成経路の調査と、A4 への割り当ては design.md・plan.md に記す。

### R81 M6a のワークスペース外の lock と翻訳元の版
