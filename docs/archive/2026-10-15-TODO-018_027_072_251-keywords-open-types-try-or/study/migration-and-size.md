# 既存入力への影響、移行の手順、規模の見込み

## 集計の条件と限界

基準コミットは `5ef09b51f4f5fabb321eab610ba0a709441d16eb` である。[inventory.py](inventory.py) をリポジトリの根から次のように実行した。処理系の実行やテスト、LLM を呼ぶ測定は行っていない。

```sh
python3 -B docs/2026-10-15-TODO-018_027_072_251-keywords-open-types-try-or/study/inventory.py > /tmp/keywords-open-types-inventory.json
```

入力は Git の追跡ファイルの `.bnt`・`.rs`・`.md` である。reference/、docs/archive、docs/todo、過去の測定記録、旧版の最小リファレンス、第三者のライセンス類、移行道具自身、今回の改造の文書を除いた。日本語訳と生成済み Skill は、別の集計群として含めた。今回作った文書を後で追跡へ加えても、文書自身は候補に入らない。

ホストのコード部分の抽出には、前回の `tools/named-arguments-migrate/extract.py` をそのまま読み込んだ。`.bnt` は全体、Rust は復号した文字列、Markdown は text / bnt / benitoite / 言語指定なしのブロックを読む。Rust と Markdown の候補には言語の語の有無による絞り込みも使った。コメントと文字列を除く簡易の字句走査を行い、match / end match を対応付け、最上位の各 case のパターンを集めた。各候補のホストの行・UTF-8 バイト位置、生成断片の保留理由、入力ハッシュを [inventory.json](inventory.json) に残した。

これは現在の parser・resolve・typeck を通した集計ではない。Rust の診断の文言や生成断片、失敗を試す入力、文法の説明も候補に残り、補間の中の式は読まない。行頭でない language 宣言や、文字列の組み立てでできる語は数え落としうる。`try` の件数をそのまま「通るコードの書き直し数」にせず、変更範囲を見積もる候補数として使う。適用する移行の manifest は、後の実装で型情報と元の診断を使って別途作る。

## language 宣言と E0908

行頭の `language "版"` の候補は全体で 102 出現 / 64 ファイルであり、0.0.5 が 93 出現ある。`.bnt` に限ると 50 出現 / 50 ファイルで、うち 0.0.5 が 46、99.0.0 が 3、0.0.4 が 1 である。古い版・新しい版・不正な版を試す入力を含むので、102 件をすべて上げる対象にしない。位置と版は inventory.json の `language_declarations` にある。

`src/modules/package.rs::BreakingChange` は現在 version・summary の二欄で、表には 0.0.5 の一項目だけがある。`check_language` は宣言より後の最初の変更を一つ選び、E0908 の固定の help を使う。0.0.6 を加えると、名前付き引数だけの案内では今回の指定を説明できない。TODO-252 の方針どおり変更ごとの help を持たせ、宣言より後かつ現在以下の全項目を版順に案内する必要がある。

推す登録は、0.0.5 の既存項目を保ち、0.0.6 に「予約語 die・構成子を増やせる二型の照合」を一項目として加える形である。251 は追加の構文として同じリリースの説明に含める。古い宣言を処理系が自動で現在の版へ読み替えることはしない。依存の内容が変わる入力では package のハッシュも再確認し、ハッシュ不一致を試す入力と実際の依存の控えを分ける。

既存の migrate.py は TODO-247 専用で、`BASE` と reconcile が保管した N1 の基準へ依存する。これを無変更で再実行することは再利用にはならない。ホスト抽出・編集検証・diff・適用記録を共通部分へ整理し、今回の候補を集める入口と新しい基準を加える案を推す。古い確認済み manifest を新しい改造へ読み替えない。具体的な道具の配置と変更する公開の型・シグネチャの表は、実装プランを作る段で明記する。

## 改造の規模の見込み

一作業を実装と差分確認の 30〜60 分程度とした、作業を分けるための粗い見積もりである。ビルド待ち、所定のレビュー、証明の試行時間は別に要る。実装プランや納期の約束ではない。

| まとまり | 作業数の目安 | 主な不確かさ |
|---|---:|---|
| 基準の固定、A の語・診断・境界 | 2〜3 | 予約語一語の接続と他言語風の診断の維持 |
| D の Lean・処理系・交換形式 | 5〜8 | パッケージの内外と入れ子、束縛・到達可能性の証明の追従 |
| B2 の Lean・解析・型・脱糖・表示・終了 | 7〜11 | 新しい表層の場合の補題、内部の終了理由を全経路で保持する変更 |
| 移行道具・例・生成物・E0908・最終整合 | 4〜6 | 生成断片、負の入力の診断、language と固定ハッシュ |
| 合計 | 18〜28 | 定義を直接直す試作をしていないため、証明の難しさで分割が増えうる |

字句の変更は小さい。B2 は `Expr::Try`・TryExpr・try_kinds に触れる本体の Rust ファイルが現在 22、tryResult / tryOption の場合に触れる Lean ファイルが 14 あり、単に parser に二語を足す大きさではない。D は主要な関数型の表現を変えないため前回より小さい見込みだが、Coverage 全体を使う束縛と到達可能性を忘れると手戻りが出る。

実装前に作る型・シグネチャの変更表には、TryExpr / TryInfo / Constraint、AdtDef、網羅性へ渡す文脈、終了理由・実行結果、BreakingChange と、交換形式を含める。AGENTS.md の凍結した型の規約への変更の承認を、今回の文書作成の依頼から得たものとは扱わない。

## 後の実装で行う検証

各段のレビューと取り込みを分け、A → D → B2 → 文書と移行・版の最終整合の順を推す。設計は先に一度に判断し、D と B2 の Lean はそれぞれの処理系より先に直す。途中で一般の旧規則を新設して維持する必要は少なく、裸の try は最終仕様として残る。未公開の中間状態は改造の文書に記録する。

実装を始めた後は、検査の前に dry-run の選択を設計者へ知らせ、関係する parser・typeck・golden・formatter・reference / skill の例、生成物、`check.sh` を確認する。形式化の範囲の変更には `lake build` と `check-formal.sh` を必須とする。正式な公開の前の `--full` と性能測定は、今回の調査では実行せず、実装後に各規約へ従って行う。性能の改善・退行は今回推測で断定しない。
