````markdown
初回リリース版は、測定の前の暫定の案として次のように決めた。

- キーワードは省略しない語（`function`・`public`・`implement`）とし、省略形（`fn`・`pub`・`impl`）と `mut` は予約しない（ADR 0092。【方針】）。
- 他の言語の制御構文に当たる語（`for`・`while`・`loop`・`break`・`continue`）と `where`・`switch`・`as` は予約しない（ADR 0093。【方針】）。`return` はキーワードである。
- 使う予定の決まっていない構文の語（`class`・`instance`・`var`・`mutable`・`module`・`derive`）は予約せず、その語を使う構文を加えると決めたときにキーワードにする（ADR 0093）。
- 並行処理はライブラリの関数と `with` で提供し、`async`・`await`・`spawn`・`select` を予約しない（ADR 0115）。

未解決の問い:

1. 省略形と省略しない語のどちらが誤りにくいか。省略形は Rust・Gleam の書き方を、省略しない語は JavaScript・Java の書き方（`return` を書く、型を書き忘れる、`private` を書く）を思い出させるという見込みがあるが、確かめていない。関数の型とラムダも同じキーワードを使うので比べる対象に含める。
2. 省略しない語を採る場合に、省略形を予約語に加えるか。予約すれば、式の中の `fn(x) { ... }` も「`function` と書く」という構文の誤りとして示せる。予約しなければ、式の中の `fn(...)` は変数 `fn` の呼び出しとして構文解析を通り、名前解決の誤りとしてしか報告できない。
3. 制御構文の語と `as`・`where` を予約して「この言語にはその構文がない。再帰を使う」のような診断を出すか、識別子として読んで一般の誤りにするか。
4. 並行処理の語を予約して、Benitoite の書き方（`uses IO` を付けた普通の関数、`Task.await`・`TaskGroup.spawn`・`Task.race`）を診断で示すか。

前提・制約: 予約語を加えると、その語を識別子に使ったスクリプトが誤りになる。OPEN-012 は「キーワードと予約語は測定の結果で決めきる」としていたが、初回リリース版（0.0.1）は暫定の案のまま出た。したがって、これから予約語を加える変更は互換性を壊す変更であり、0.x のマイナーの版で `CHANGELOG` に移行の手順を書いて行う（ADR 0236）。
````

````markdown
### TODO-251 try の失敗時の処置を明示する or return・or die

- 状態: 方針あり
- 出どころ: 2026-10-15 の設計者との相談と TODO 追加の依頼

`try` が `Result.Error` または `Option.None` を受け取ったときの処置を、`try e or return`・`try e or die` と明示できるようにする。`or die` の主な用途は、一回限りのスクリプトを作成・実行するときに、失敗を呼び出し元へ返し続ける記述を省くことである。`die` の名前は Perl へのオマージュとするが、捕捉できる例外や実行時エラーを起こす意味は与えない。

構文と意味の方針:

- `or return` は、現在の `try e` と同じく、成功なら中身を取り出して続け、失敗なら最も内側の関数かラムダから `Result.Error(error)` または `Option.None` を返す。エラーの中身だけを返す意味にはしない。`Result` のエラー型の一致と、`Result`・`Option` の間を暗黙に変換しない規則を維持する。
- `or die` は、成功なら中身を取り出して続け、失敗なら理由を表示し、終了状態 1 で今回のスクリプト実行を終える。実行時エラーとは別の、明示的な失敗終了とする。囲んでいる関数の戻り値を `Result`・`Option` にする必要はない。
- 終了には既存の `Process.exit` に相当する手順を使い、今回の実行のタスクを止め、`with` のリソースを解放し、出力を書き出す。Rust の panic や OS の即時終了で実装しない。解放や出力の失敗の扱いも、既存の明示的な終了と整合させる。
- 終了の範囲は実行方式によらず今回のスクリプト実行とする。将来のサーバモードでは当該ジョブを終え、デーモンや他のジョブを終えない。サーバモードで暗黙に `or return` へ読み替えることはしない。
- `or die` は `Process.Exit` のエフェクトを持つ。標準エラー出力への説明を `Console.writeErrorLine` 相当で行う場合は `Console.Write` も持たせる。補助関数や高階関数を経由しても、終了する操作を型のエフェクトから追えるようにする。記述の簡略化を理由にエフェクトの検査を省かない。
- 最初は `or` の後を `return`・`die` に限定し、説明を添える `or die("説明")` を用意する方向とする。引数なしでは元の失敗理由を表示し、説明を添えた場合も元の原因を捨てずに併記する。任意の終了状態が必要なら `Process.exit` を直接使う。分岐、ログ出力、再試行、代替値の選択など、複雑な処理は既存の `match` とライブラリの関数で書く。
- 既存の `try e` は導入時には許し、常に `try e or return` と同じ意味にする。囲んでいる関数の戻り値や実行方式に応じて、リターンと終了を切り替えない。新しく生成するコードで推す形は明示形に統一する方向とし、省略形を恒久的に残すか、後に明示を必須にするかは、互換性と読みやすさを踏まえて決める。
- 入力は一度だけ評価し、成功時には失敗側の処理や説明の式を評価しない。処置を選ぶ対象は値として得た `Result.Error`・`Option.None` であり、入力の評価中の実行時エラー、資源の不足、取り消しなどを捕捉する構文にはしない。

用途と推奨:

- 一回限りのスクリプトでは、失敗時に作業全体を終えてよい箇所に `or die` を使えるようにする。
- サーバモードで実行するスクリプトと、プロジェクトの再利用する関数では `or die` を非推奨とし、`or return` や `match` で呼び出し元へ判断を委ねることを勧める。プロジェクトの実行入口で作業全体の終了を決める場合は、必要に応じて使えるものとする。
- 非推奨は同梱の Agent Skill とマニュアルによる案内とし、プロジェクトで構文を禁止することとは区別する。将来、lint や実行の方針で制限する場合は、構文の直接使用だけでなく、別の関数を経由する `Process.Exit` も対象にできるようにする。

実装前に決める点:

- `or` は既存の Boolean の短絡論理演算子でもあるため、処置を指定する `or` を専用の文法として区別する。現在の `try` がパイプ全体にかかる規則を保ち、オペランドの終わり、括弧、改行、入れ子、ラムダの終端省略との関係を一意に定める。`die` を予約語にするか文脈で識別するか、既存の同名の識別子との互換性も扱う。
- `Result[T, E]` の `E` の表示方法を定める。最初は `String`・`IOError` など対応する型を限り、ほかは `Result.mapError` で変換する案と、表示の型クラスを用意する案を比較する。任意の型を暗黙に文字列へ変換できるとは扱わない。`Option.None` に説明を付けない場合の報告も定める。
- 終了の説明を出力として書くか、実行結果の報告として持つかを決め、テストの実行器と将来のサーバのジョブの結果にも原因が残るようにする。実行時エラーや処理系の不具合として分類しない。
- `or return` の戻り値への制約と、`or die` の終了のエフェクトを型検査・脱糖で区別する。値を返さない処理の型の表現は、既存の `Process.exit[T](code) -> T` を基準に検討し、この追加のために `Never` 型の新設を前提としない。
- TODO-249 の型付きの失敗と役割を区別する。本項目は失敗の値を関数から返すか実行を終える構文であり、複数の関数をまたいで回復可能な失敗を捕捉する機構ではない。TODO-250 の方針に従い、型付け・脱糖の変更と移行の範囲を調べて、まとめる改造と実装の順序を決める。

実装プランには、構文解析器、型検査、脱糖、終了と報告、フォーマッタ、必要なテスト、設計書、リファレンス、同梱の Skill の更新を含める。`try` は形式化した範囲の内側にあるため、07-04「01-12 との対応」に従い、処理系より先に Lean の型付き表層の定義・型付け・脱糖と必要な証明を更新し、01-12 の写しも直す。成功時の値と評価回数、失敗時の作用先と後続の未評価、エフェクトの検査、リソースの解放、子タスクからの終了、実行器を終了せず一回の実行だけを終えることを確認する。生成される Skill の参照文書は生成元から作り直す。

関連: TODO-018（キーワードと予約語）、TODO-249（型付きの失敗と Result との相互変換）、TODO-250（構文の変更を伴う項目のまとめ方）。
````

````markdown
### TODO-249 任意のエラー型を扱う失敗エフェクトと Result との相互変換

- 状態: 方針あり
- 出どころ: 2026-10-14 の設計者との相談と、追加検討の依頼

目的は、複数の関数や高階関数を組み合わせる処理で、成功値を直接扱いながら、回復可能な失敗を指定した境界で処理できるようにすることである。独立した typed throws の機構を導入するより、既存の利用者定義エフェクトと `handle` を基礎に拡張する方向とする。検討する追加は、任意のエラー型を静的に追跡できる失敗の仕組みと、`Result` との相互変換である。具体的な型・関数の名前、表層構文、型付け、実装方式は未決である。

現在の仕様との関係:

- `Result` は、失敗を値として返す・保存する・集計する用途のために残す。現在の `try` は、最も内側の関数かラムダから `Result.Error` または `Option.None` を返す構文であり、複数の関数をまたぐ捕捉ではない。この意味を変更するかは別途判断し、既存の意味と新しい変換を混同させない。
- 現在でも、具体的なエラー型を受け取る `fail[T](error: AppError) -> T` のような操作を宣言し、`handle` の節で `resume` を呼ばずに終えることで、複数の関数をまたぐ処理の打ち切りを書ける。01-06「エフェクトの宣言とハンドラの型付け」の `Abort` が基礎となる。
- 現在のエフェクト宣言自体は型パラメータを持たない。操作の戻り値に型パラメータ `T` を持たせることと、失敗エフェクトのエラー型 `E` を呼び出しから捕捉まで一貫して追跡することは別であり、後者のための拡張を検討する。

任意のエラー型を扱う仕組みの検討:

- `IOError`・`NetworkError`・利用者定義の直和型など、値の型 `E` を保持したまま失敗を伝播できるようにする。共通の文字列や型情報を失う汎用エラーへの変換を必須にしない。扱える型への制約が必要かも決める。
- 型パラメータを持つ一般のエフェクトを導入する案と、失敗専用の型付きエフェクトを既存のハンドラに統合する案を比較する。一般のエフェクトの拡張全体を、この機能の前提として決め打ちしない。
- 失敗操作は成功値を返さず、捕捉側で通常の処理を再開しないものとして設計する。既存の汎用の操作と `resume` で表現する場合も、成功値を捏造して再開できない型付けと、続きを捨てる意味を確認する。
- 中間の関数では、失敗の可能性をエフェクトとして型に残す。境界のハンドラで処理した失敗だけを外側のエフェクトから除く。失敗を処理しても、ファイル操作など他のエフェクトまで除いたことにはしない。エフェクトの静的追跡と実行時の権限も区別する。
- 関数型の適合、型推論、ラムダ、部分適用、型クラスのメソッド、エフェクト多相の高階関数で、エラー型を維持する規則を定める。特に `List.map` のラムダから失敗したとき、ラムダの結果だけを `Result` にする場合との違いを明示する。
- 異なるエラー型を起こす処理をまとめる場合の規則を決める。境界で明示的に一つの直和型へ変換する案を基準に、複数の失敗エフェクトを併存させる案と比較する。暗黙のエラー変換や型の拡大は未決とし、型情報を失う仕組みを既定にしない。
- 同じエラー型を使う複数の失敗操作や、入れ子のハンドラを区別する方法を定める。どのハンドラが捕捉するか、捕捉した節から別の失敗を伝えるときの作用先、網羅性と未処理の失敗の診断を確認する。

`Result` との相互変換の検討:

- `Result[T, E]` から、`Result.Ok(value)` なら `T` の値を取り出し、`Result.Error(error)` なら `E` の失敗を起こす操作を設ける。現在の `try` による関数からの早期リターンとは、作用先と型の規則を区別する。
- `T` を返して `E` の失敗を起こしうる計算を囲み、成功なら `Result.Ok`、捕捉した失敗なら `Result.Error` とする変換を設ける。計算を表すラムダを渡す関数にするか、既存の `handle` による記述を補助するかを決め、引数を評価してからでは捕捉が間に合わない点と評価順序を明示する。
- 指定した失敗だけを捕捉し、それ以外のエフェクトは維持する。成功経路でも失敗経路でも計算を重複実行せず、失敗後の処理を実行しない。関数やラムダの `return`、現在の `try` と組み合わせた際の作用範囲を定める。
- 外部ライブラリの `Result` を局所的な失敗へ変換し、中間の処理では成功値を直接扱い、公開する関数の境界で `Result` に戻す例を用意する。境界では、回復して値を返す、公開するエラー型へ変換して再伝播する、`Result` にする、の各用途を区別する。エラーの種類や原因を保持する方法も検討する。
- 外部コンポーネントの ABI に失敗エフェクトをそのまま持ち込むことは、この追加の前提にしない。既存の外部関数が返す `Result` を Benitoite 側で変換する方法から検討する。実行時エラー、トラップ、資源不足、タスクの取り消しを回復可能な失敗へ変換することは、本項目で自動的に認めない。

実行と検証の論点:

- 打ち切り時の `with` の解放順序と解放の失敗、内側のハンドラの続きを捨てる処理、早期リターンとの組合せを確認する。主な失敗と後始末の失敗の扱いを明示し、失敗が起きる前に行った外部操作や状態変更を巻き戻す意味は与えない。
- 子タスクに引き継いだハンドラの現在の制約（末尾で再開する節に限る）との関係を整理する。子タスクの失敗を `await` で観測するか、結果に保持するか、タスク群の取り消しとどう組み合わせるかを決める。同期の非再開ハンドラが、そのまま子タスクにも使えるとは扱わない。遅延評価で失敗が起きる時期と捕捉範囲も確認する。
````
