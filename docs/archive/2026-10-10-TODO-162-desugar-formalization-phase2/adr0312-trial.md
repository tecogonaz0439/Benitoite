## 段 1: 二つの脱糖が共有する表層

`Declarations` と `Program` に、既定値が空の `opDicts : OpName → List (ClassName × Nat)` を加えた。操作の表は `Release.OpDecl` のままである。組み込みの操作の辞書列は空とする。`WellFormed` は、宣言された操作の辞書の型パラメータ番号が宣言の範囲内であることを要求する。

制約のない操作は `opName`、制約を持つ操作は `opDicts o ts ds ps` として区別した。後者は辞書の根拠 `ds` と具体化した値引数型 `ps` を持つ。型付けは元の操作の値引数だけの関数型を与え、辞書の根拠を宣言の辞書型と照合する。

`Clauses.cons` に `ndicts` を加えた。`arity` は辞書を含む引数数である。`HasClauses.cons` は `Declarations.opSig` から元のシグネチャを読み、`binds (opDictTys o ++ sg.params)` で辞書と値引数を束縛する。`ndicts = (opDictParams o).length` を求める。`patternProgram` の操作の表を節の型付けに使わない。番号 0 は継続、その後に逆順の値引数、逆順の辞書、外側の環境が続く。

`lake build Benitoite.Surface.Syntax Benitoite.Surface.Typing Benitoite.Surface.WellFormed` は成功した（8 jobs）。この段は定義だけを確認し、後続の証明は段 2・3 で修正する。

共通検査の既定の比較先 `origin/san_benito` はこの作業開始時の版と差があり、965 ファイルを選んだ。`scripts/check.sh --base HEAD --dry-run` では今回の変更だけから `formal` を選んだ。依頼の指定どおり、既定対象 `Benitoite` の `lake build` を最終検査とする。

## 段 2: (b) の脱糖と宣言の条件

脱糖した操作の表は、元の `OpDecl` の `params` の先頭に `opDictTys` を加える。型パラメータ・戻り値・エフェクト名は変えない。`patternProgram` の操作の表は元のままであり、パターンと処理するエフェクトの判定だけに使う。

`desugar_wellFormed` は辞書型の番号の範囲を `WellFormed` の追加条件から得る。`desugar_effectsOk` は、操作を写しても操作名・所属エフェクト・エフェクトの操作一覧が変わらないことから証明した。`opDecl_desugared`・`opSig_desugared` は、元の宣言と辞書を含むコアの宣言との対応を示す。組み込みの操作の場合は空の辞書列を加えるだけである。

この時点の既定の `lake build` は成功した（67 jobs）。段 3 の一般の証明も同じ構築で検査できた。追加した定理に `sorry` はない。

## 段 3: (b) の型の保存と例

`desugar_typed` と `surface_effect_soundness` の言明と前提を変えずに構築できた。`Release`・`Core` は変更していない。`HasType.desugar` の `E_Op`・`E_OpDicts`、`HasClauses.desugar` を修正した。制約を持つ操作を値として使う形は、値引数だけを束縛するラムダであり、捕えた辞書の番号を値引数数だけずらす。直接の頭は `CallHead.app (.op o ts) ds` として、引数を計算した後に辞書を値引数より先に渡す。

`inv_opDicts` は `inv_funDicts` と同様に表層の導出を逆転し、`E_Sub` の連鎖も扱う。`inv_ret` によって値化したラムダから頭を逆算する方式は使っていない。節の型の保存は `opSig_desugared` でコアの引数列を得て、表層と同じ辞書・値引数の環境で本体の帰納法の仮定を使う。

`TrialExamples.lean` に、操作の宣言、二つの辞書を持つ直接呼び出し、値として使うラムダ、節の脱糖を `rfl` で確かめる例を加えた。宣言と実行を含む具体例は `choose[T: Echo](x: T) -> T` とし、呼び出しで `EchoInteger` の辞書と整数 11 を渡す。節は番号 2 の辞書の `echo` を呼び、その戻り値で `resume` する。`EchoInteger.echo` が 17 を返すので、最終結果は 17、事象数は 0 になる。実行結果も `rfl` で確かめた。例のプログラムの `WellFormed` と `WellTyped`、操作呼び出しと節の導出も証明した。

既存の `Examples.lean` の節には `ndicts = 0` を加え、`E_Op` と `HasClauses.cons` の追加の前提を補った。既存の脱糖の期待値は変えていない。追加の例は、辞書の順・ラムダの自由変数・節への受け渡しという今回増える契約を確かめる。処理系のテストは変更していない。

## 段 4: (a) の脱糖と失敗の位置

### 辞書の位置を除く部分的脱糖

`Surface/TrialA/Desugar.lean` に別の脱糖を置いた。共通の表層を (b) の構造的脱糖で値と計算に分けた後、構造的再帰の `eraseCompOpt` で操作の辞書引数と節の辞書束縛を除く二段の定義である。操作の表は元の `p.ops` のままにする。呼び出しの `.app (.op o ts) (ds ++ ws)` は `.app (.op o ts) ws` にする。節の引数数は辞書数だけ減らす。

変数の番号は `Nat → Option Nat` で写す。節の引数数が 2、辞書数が 1 の例では、継続の 0 と値引数の 1 はそのまま、辞書の 2 は `none`、外側の変数の 3 は `some 2` になる。新しい let やラムダ、パターンの束縛の下では `upRenOpt` がその束縛を保護する。`DictEv.toValOpt` は `local` の写し先がなければ `none` を返し、実装と上位の辞書も再帰的に写す。根拠から直接写す結果と、根拠を値にした後に部分的に写す結果が等しいことを `dict_toValOpt_eq` で証明した。

`Program` の定義と実装の表は名前から `Option` を返す関数であり、そのすべての値を計算で走査できない。このため `desugarProgramOpt` は、関数名と実装名、および実装の上位の型クラス名とメソッド名の有限の一覧を追加の引数に受け取る。これは部分的な結果をプログラム全体の `Option Release.Program` にまとめるための列挙であり、共有する表層の構文と型付けは変えない。具体例の一覧は `enumerations_complete` で完全さを証明した。任意の関数として表した表に対する一般の全域性は、この試みの対象ではない。

段 3 と同じ `trialProgram` は `WellFormed` と `WellTyped` を満たすが、(a) の脱糖結果は `none` になる。`typed_program_none_row` はこの結果を `rfl` で示す。呼び出しは辞書を除いて `some` に移せる一方、節のメソッドの受け手が辞書位置を参照するため、節の本体が `none` になる。辞書の位置そのもの、新しい let の下の位置、外側の変数の移動も `rfl` の例で確かめた。

したがって、「型の付いた入力では脱糖の結果は `none` にならない」という補題は言えない。`typed_counterexample` は範囲条件・型付け・`none` の三つを一緒に示し、`not_total_on_typed_programs` は全域性の命題の否定を証明する。名前の一覧の不足や、元から型が付かない入力によって失敗させた例ではない。

### 変数番号をそのまま残す節の局所比較

`Surface/TrialA/Naive.lean` は、最初に止まる節だけを比べる。操作の表を元に戻し、節の引数数を値引数だけの 1 にする一方、辞書の根拠 `local 2` を従来どおり `.var 2` に写し、脱糖した節の本体の番号を残す。プログラム全体の第二の (a) の脱糖や一般の保存証明は作っていない。

`HasTypeClauses.cons` の操作シグネチャ・引数数・型パラメータ数の前提は満たせる。しかし、本体の型付けで残る目標は次である。Lean が `trace_state` で出した表示をそのまま記す。

```text
case a
⊢ HasTypeC naiveProgram B StoreTy.empty [{ }] naiveEnv (some intTy) naiveBody intTy Eff.empty
```

ここで `naiveEnv` と `naiveBody` は次の値である。

```lean
naiveEnv = [some (.cont (.tvar 0) intTy Eff.empty), some (.tvar 0)]
naiveBody = .letIn
  (.letIn (.ret (.var 1)) (.meth (.var 3) "echo" [] [] [.var 0]))
  (.resume (.var 1) (.var 0))
```

表層の環境には継続・値引数・辞書の三つがあったが、コアの環境には継続と値引数しかない。メソッドの引数を let で束縛した後、受け手の `.var 3` を型付けする環境の長さは 3 であり、番号 3 の要素がない。`naive_body_untypable` は、二つの let、メソッド、変数の逆転補題を使い、この本体が任意の結果型・エフェクトについて型を持たないことを証明した。外側の変数がある場合も、番号を辞書数だけ詰めなければ、本来と別の要素を指す。

比較用の `naive_clause_preservation_attempt` の上の目標にだけ、意図的に `sorry` を置いた。この言明は成立しないものであり、保存の結果として使わない。(b) の証明や、部分的脱糖の反例、`naive_body_untypable` はこれに依存しない。

| (a) の書き方 | 辞書と外側の変数の扱い | 抜けが現れた段 | Lean で確かめた結果 |
|---|---|---|---|
| 部分的な番号の写し | 辞書位置は `none`、外側の位置は辞書数だけ詰める | 脱糖の定義を具体的入力に適用する段 | 型の付いたプログラムの結果が `none`（`rfl`）。全域性を否定する定理も成立 |
| 番号をそのまま残す節 | 辞書を束縛せず、元の番号を残す | `HasTypeClauses.cons` の本体の型の保存 | 本体の型付けが閉じない。型を持たないことを逆転補題で証明。保存の試行に `sorry` 1 個 |

ADR 0312 の背景で欠けていた規則は、操作の呼び出しから節へ制約の辞書を渡す規則である。この試みでは、表層の節が辞書を使えることを先に型付けで表した。その結果、辞書を渡さない脱糖は、節の辞書に写し先がないという形、または表層とコアの環境が対応しないという形で検出された。

## (b) の結果の範囲と、言語を広げる場合の変更の見込み

`Release` を変えずに通ったことの中心は、新しい表層の制約・呼び出し・値化・節の束縛について、型の保存を証明できたことである。既存の表層でも、操作の `params` に辞書型を書き、辞書型の局所変数を普通の値引数として渡すプログラムは型を持てる。`Release` が辞書型を引数として扱えること自体は、今回初めて得た結果ではない（C5a-1 のレビューの指摘 2・6）。

今回確かめたのは、操作の型クラスの制約からその引数列を作り、呼び出しの根拠を列の先頭に置き、値として使うときは辞書を捕えるラムダにし、節の環境に同じ辞書を束縛する一連の表層の規則が整合することである。`desugar_typed` の言明と前提は変えていないが、`Program.WellFormed` の定義には、依頼どおり辞書の型パラメータ番号の範囲条件を加えている。

処理系への変更はこの作業では実装していない。候補 (b) を採る場合は、次の作業が要る見込みである。実行器の命令や構造体の欄の変更がどこまで要るかは、実装の設計の段で確認する。

| 対象 | 要る変更の見込み |
|---|---|
| 構文解析 | `syntax/parser/effects.rs` にある E0510 の `trait_constraint` による禁止を外す。ADR 0311 の型構成子の制限や組み込みの制約の規則は別に扱う |
| 型検査 | 操作の制約から呼び出しの辞書の根拠を解決する。節では操作の型パラメータを従来の rigid 型として扱い、その制約に対応する局所辞書をメソッドの解決に使えるようにする。表層の節に書く値引数数と、脱糖後の辞書を含む引数数を区別する |
| 脱糖 | 制約を持つ関数と同じ辞書の並びを操作にも適用する。直接の呼び出しでは辞書を先頭に渡し、値として使う形では値引数だけのラムダに捕える。`ir/desugar/effects.rs` の節の生成は、現在 AST の値引数だけから `params` を作るので、その前に辞書の束縛を生成して本体の辞書の根拠と対応させる |

## フェーズ 2 の目的に対する所見

この土台は、ADR 0312 の種類の抜けを、今回定義した表層と脱糖の組み合わせについて検出できた。表層の型付けで節の辞書を要求し、脱糖後の型の保存を調べると、呼び出しから節への辞書の受け渡しを欠く (a) は通らない。部分的な定義では写し先の不足が `none` になり、無理に全域的に写す局所比較では本体の型付けが成立しない。

この結果は、Lean に書いていない規則の抜けを自動で発見することを保証しない。表層の型付けからも節の辞書を省けば、今回の反例を入力として作れなくなる。処理系と Lean の脱糖が同じ規則を実装することも、今回許可された範囲では検査していない。新しい表層の規則を先に書き、その規則を満たす例と保存の証明を用意し、処理系との対応を差分テストで確かめるという手順の材料になる。
