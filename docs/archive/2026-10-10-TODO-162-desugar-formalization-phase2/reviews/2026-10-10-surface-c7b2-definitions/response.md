# 段階 C7b（C7b-1 c57e2e1・C7b-2 f57da11）の定義と言明のレビュー

レビュー担当: Opus 5.5（medium）。

レビューの結論として、定理が偽になる、弱まる、または 01-05・01-06・01-12 と意味が違う「高」の指摘はない。性質 1 の 2 定理（`desugar_typed`・`surface_effect_soundness`）の言明と前提は、2 コミットのどちらでも変わっていない（`git diff c57e2e1~1 f57da11` で確認した）。以下、重要な順に並べる。

## 指摘

### 1. 中: ガードの中の `resume` を拒むことが、今の 01-06 の本文より狭い（P12 の過渡期の差）

- 場所: `Surface/Typing.lean` の `HasArms.guarded`（`hideConts (binds δ ++ Γ)`）。設計書は 01-06 の 495 行付近（`resume` の制限）、07-04「01-12 との対応」の表、01-12 の 415 行付近。
- 問題:
  - P12 (a) の写し方としては正しい。`hideConts` はラムダ（`E_Lam`）と同じ扱いで、ガードの中の `handle` が自分の節で `resume` することは許している。
  - ただし今の 01-06 は、ラムダと `lazy` の本体の中の `resume` しか禁じていない。処理系も、ガードの中の `resume` を受け付ける（TODO-190 が未完了のため）。
  - そのため、今の言語の文面で型が付くプログラムの一部に、性質 1 が及ばない。ほかの差はすべて「表層の型付けが広い」向きだが、これだけが逆向きである。
- 原因の分類: 設計の決定（P12）と、言語の規則・処理系の修正（TODO-190）の時期のずれ。
- 直し方の案:
  - Lean は直さない。
  - C7 を設計書に反映するとき、07-04 の表に「ガードの中で外側の継続を `resume` するプログラムは、TODO-190 で 01-06 を直すまで性質 1 の対象外」と書く。
  - TODO-190 の文面は「ガードの中に直接書いた `resume`（ガードの中の `handle` の節は除く）を禁じる」とし、`hideConts` が隠す範囲と揃える。
  - C7c の差分テストでも、この種の関数を既知の差として数える（報告の 6 のとおり）。

### 2. 中: C7c で `slots` をどの順で求めるか（レコードの並べ替え）

- 場所:
  - `crates/benitoite/src/ir/desugar/patterns.rs` の `pattern`。`vars` はソースの順に積むが、レコードの引数は宣言の順に並べ替えている。
  - `crates/benitoite/tests/desugar_export/exchange.rs` の 1533 行付近（行と分岐が一対一でないと対象外にしている）と、876 行付近（表層の選択肢とガードを `outside` にしている）。
  - Lean の `Surface/Syntax.lean` の `Alternative`、`Release.AltsTy`。
- 問題:
  - `MatchArm.vars` は、レコードのパターンではソースの順になり、Lean の束縛の順（`toCore` の後の宣言の順）と一致しない。
  - 今の書き出しは、コア IR の照合順で `vars` を集め直しているので、単一の選択肢では食い違いが出ていない。
  - C7c で次の 2 点を誤ると、`AltsTy` の「最初の対応は恒等」が成り立たない形になる。
    - 最初の選択肢の変数の順と、ガード・本体の番号を、`MatchArm.vars` から作ること。
    - 後の選択肢の `slots` を、ソースの順で数えること。
  - 表層の側でも、`slots` はレコードを宣言の順に並べ替えた後の位置で数える必要がある。
- 原因の分類: 後の段階（C7c）の妨げ。
- 直し方の案: C7c の作業文書に、次の決まりを明記する。
  - 行 j のコアのパターンを Lean の照合順（構成子の引数、レコードは宣言の順、リストは前・残り・後の順）で辿り、`VarId` の列 γ_j を得る。
  - 分岐の変数の順は γ_0 とする。`slots_j[i]` は「γ_0[i] が γ_j の中で占める位置」とする。こうすると `selectSlots γ_j slots_j = γ_0` になる。
  - ガードは本体と同じ局所環境で書き出す。
  - 同じ分岐の行は連続している（02-06）ので、`arm` の番号でまとめる。
  - 表層の書き出しも、同じ手順で `slots` を作る。
  - あわせて、`Exchange/Convert.lean` の `toArms`（今は `.single` だけを作る）と `fromComp`（選択肢が二つ以上・恒等でない `slots`・ガードを `throw` する）を広げる。交換形式には、範囲（符号付きの整数と文字）とリストの残りの 3 通りを足す。

### 3. 低: 「言語との既知の差」の範囲が報告の書き方より広い

- 場所: 報告の 3、`E_Match`、`B_LastPat`・`B_BindPat`。設計書は 01-12 の 415 行付近と 07-04 の表の C1〜C6 の行。
- 問題:
  - `Exhaustive` は値の形で網羅を定めている。そのため、`'\u{0}'..'\u{10FFFF}'` のような `Character` のすべての値を覆う範囲は、束縛の左辺だけでなく、`match` の唯一の分岐としても網羅とみなされる。
  - 01-05 は「範囲のパターンは `Integer`・`Character` を網羅したとみなさない」とし、範囲を束縛の左辺に書けないと明記している。処理系も拒む。
  - 差は「表層の型付けが広い」向きなので、性質 1 は 01-05 の検査を通ったプログラムにも成り立ち、残してよい。
  - `Integer` は Lean の `Int` に上限がないので、この差は起きない。
  - 設計書の既存の記述は「`Character` を並べ尽くす分岐」だけで、範囲と束縛の左辺に触れていない。
- 原因の分類: 文書の記述漏れ（形式化の意図した緩和）。
- 直し方の案:
  - C7 を設計書に反映するとき、01-12 の 415 行付近と 07-04 の表を「`Character` のすべての値を覆うリテラルの並びや範囲を網羅とみなす（`match` と束縛の左辺の両方）」に改める。
  - 選ばれない分岐の検査（選択肢ごとの検査を含む）を表さないことも、同じ箇所に残す。

### 4. 低: ガードの中の外側の `resume` の例が、型が付かないことを直接示していない

- 場所: `Surface/Examples.lean` の `c7Guard_hides_outer_cont`・`c7Guard_outer_resume_lookup_impossible`。
- 問題:
  - 2 つの例が示すのは、隠した環境の番号 1 が継続の型でないことだけである。
  - 「`.resume 1 e` に型が付かない」ことは、`E_Resume` だけが `resume` を型付けし、かつ `E_Sub` を通しても前提が変わらない、という読み手の推論に頼っている。
- 原因の分類: 例が弱い。
- 直し方の案:
  - `¬ HasType D B op C (hideConts (binds [intTy] ++ some (.cont b t ε) :: Γ)) none .other (.resume 1 e) a ε'` を、`E_Sub` についての帰納法で示す例を足す。あるいは、`c7GuardArms` のガードを `resume` にした `HasArms` に型が付かない例でもよい。
  - あわせて、ガードのエフェクトが空でない例と、ガードの中の `return` に型が付かない例（`R = none`）を一つずつ置く。そうすると、P12 と 01-05 の 3 条件が例で揃う。

### 5. 低: `Pattern.Valid` のリストの形の条件が `P_List` と重なり、範囲の両端の表し方がリテラルのパターンと違う

- 場所: `Surface/Syntax.lean` の `Pattern.Valid`、`Pattern.range`。
- 問題:
  - `rest = none → after = []` は `Release.P_List` も課しているので、`Valid` の側は冗長である。害はない。
  - 範囲の両端は `Release.Const` を直接持つ。リテラルのパターンは `integer`・`negInt` で書き方を写しているので、表し方が揃っていない。`-0..3` と `0..3` を区別しないが、処理系も `range_bounds` で値に直すので、意味の差はない。
  - 種類の合わない両端（`.integer` と `.character` など）は `Valid` の `_ => True` に落ち、`PatTy` が拒む。これも正しい。
- 原因の分類: 表記・コメント。
- 直し方の案:
  - `Pattern.Valid` の直前のコメントに「リストの形の条件は P_List と同じで、束縛の左辺と選択肢で同じ述語を使うために重ねて置く」と書く。
  - `range` のコメントに「両端は処理系の `range_bounds` と同じく値で持つ」と添える。

## 観点ごとの結果

1. 表層の型付け: 指摘 1・3 を除き問題なし。各点の確認結果は次のとおり。
   - 範囲の `lo ≤ hi`: `Character` は `toNat` の比較で、`Const.inRange` と処理系の `pattern_ext.rs` の判定と一致する。
   - リストの形と、選択肢の束縛: `Perm` と `selectSlots γ slots = some δ` で、同じ個数・同じ型の束縛を表している。
   - ガード: `hideConts`・`R = none`・`.other`・`Eff.empty`・`Boolean` で写している。01-05 の「内側のラムダの中を除き `return`・`try` を書けない」も、`E_Lam` を通して成り立つ。
   - 網羅性: ガードの付いた分岐を除き、選択肢を別々に数えている。
   - 束縛の左辺への `Valid`: 足してある。
   - 報告の 3 の差は残してよい（文書化は指摘 3）。
2. 脱糖と処理系のコア IR の対応: 問題なし。
   - 選択肢の順と、偽のガードで同じ分岐の残りの選択肢を飛ばすこと（`E_MatchXGuard`・`E_GuardF`）は、02-06 と `match_expr` と一致する。
   - ガードと本体は、同じ `upRen (Arm.bindersOf …) (· + 1)` で付け替えている。
   - 照合対象の `let` は従来どおりである。
   - 例 `c7Guard_run`（99）と `c7Choice_run`（20）が、実行で確かめている。
3. `Arms.Exits`・範囲の条件・網羅性の関数: 問題なし。
   - `Arms.Exits` が本体だけを見るのは、01-06 の「すべての分岐の本体が必ず抜けるとき」と一致する。
   - 網羅性があるので、ガードが偽でもどれかの本体に達する。
4. 性質 1 の言明と例: 言明と前提は変わっておらず、補題も言明を弱めていない。
   - `HasArms.desugar` は、ガードの空のエフェクトを保ったまま `HasTypeXArms.guarded` へ移している。
   - 例の弱さは指摘 4。
5. C7c の妨げ: 指摘 2 にまとめた。報告の 6 の見込みは妥当である。今の書き出しは、すでに照合順で変数を集め直しているので、その方針を `slots` にも広げればよい。
6. `Comp.match` を `Release` から消すかどうか（所見）:
   - 現状:
     - `Comp.match` は表層の脱糖からもう使われない。
     - 残っているのは、`Release` の簡約規則・型付け（`E_Match`・`C_Match`・`firstMatch`・`HasTypeArms`）と、約 15 の補題のファイルの場合分けである。
     - ほかに、`Release/Examples.lean` と、`Surface/Lemmas/ScopedRename.lean`・`Exchange/Convert.lean` の構造的な場合だけである。
   - 消したときに失うもの:
     - 1 段で終わる単純な照合の規則（学習用の読みやすさ）。
     - 既存の `Release` の例（`Release.run` の燃料が足りなくなる可能性がある）。
     - ただし段階 A の `Benitoite.Core` が単純な `match` を保つので、学習用の題材は残る。
     - 交換形式の `matchC` は処理系の書き出しの形であり、`Release.Comp.match` とは独立しているので、消しても差分テストに影響はない。
   - 残す理由: 薄い。
     - `match v arms` は `matchX v (arms.map (fun (p, m) => mkArm p m))` で表せる。
     - 残すと、`Release` の補題の場合分けを二重に保つことになる。
     - また、処理系に `Match` が一つしかないのに、01-12 の写しが 2 種類の `match` を説明し続けることになる。
   - 推奨: C7c の差分テストを通した後、C7 を設計書に反映する作業と同じ変更で消す。
     - 01-12 の C-Match は「選択肢とガードを持つ一つの `match`」に書き換える。
     - 必要なら `Release` に `mkArm` を使う略記の `def` を置いて、例を読みやすく保つ。
     - C7c の前に消すと、C7c の不具合と削除の影響が区別しにくくなるので、順序は後にする。
