# 段階 C4a-1 の定義のレビュー結果

レビュー担当: Claude Code の Opus 5.5（medium）。

性質 1 を偽にする反例は見つからなかったので、重さが「高」の指摘はない。指摘は「中」1 件と「低」4 件である。`lake build` は成功し、`sorry` は報告どおり 12 か所だった。

## 指摘

### 1. 末尾位置の `with` の本体にある `return` の注釈が決まらない

- 重さ: 中（C4c の妨げ。01-12 の写しの定義にも関わる）
- 場所: `formal/Benitoite/Surface/Typing.lean` 207–211 行（`E_With` の本体を `.other` で型付けする箇所）、`crates/benitoite/tests/desugar_export/exchange.rs` 462–464 行（`returnE` の注釈に `node_ty` を書く箇所）、01-12「型の情報を付けた表層の構文と型付け」の「末尾位置にない `return e` は、その位置の型を持つ」
- 問題: `E_With` は本体を `.other` で型付けするので、本体の中の `return` は `E_ReturnOther` で注釈の型を持ち、`with` の型はその注釈の型になる。関数の本体の最後の `with` で本体が必ず抜ける場合（`with x = e do return 1 end with`）、01-06 では必ず抜ける文の型は任意なので、型検査は `return` の型を新しい型変数のまま残し（`return_expr` は `ctx.fresh_ty()` を返す）、注釈は既定の型になりうる。`Def.WellTyped` は本体の型が `d.ret` であることを求め、`E_Sub` はデータ型を広げないので、注釈が R と違うと、処理系が受け付けたプログラムを書き出しても表層の型付けを満たさない。処理系は `Position::Result` の `result_ty` で、同じ箇所の型を戻り値の型にしている。定理そのものは偽にならない（注釈を R にすれば型が付く）が、01-12 の「型検査が決めた情報を付ける」という説明のままでは、性質 1 の前提から外れるプログラムが出る。
- 原因の分類: 表現の都合（`with` の本体の位置を `.other` に統一したこと）と、01-12 の注釈の定義の不足
- 直し方の案: 01-12 の写しに「末尾位置の `with` の本体（処理系の `Position::Result`）で、型が決まらない `return` の注釈は R とする」を加え、C4c で書き出しの `returnE` の注釈を、処理系の `result_ty` と同じ規則で R にする（`if`・`match` の分岐を通って伝わる場合も含める）。`E_With` の本体を `.tail` で型付けする案は、01-12 と 01-10 の「末尾位置にない」に反するので採らない。

### 2. `try` の型付けが 01-09 より広い

- 重さ: 低
- 場所: `Typing.lean` 190–204 行（`E_TryResult`・`E_TryOption`）
- 問題: 01-09 は `try` を `Result` と `Option` に限るが、規則は構成子の形（`ntys`・`args`・同じデータ型）と網羅性を満たせば、どのデータ型でも受け付ける。広い側で証明すれば狭い側でも成り立つので性質 1 には害がないが、01-12 の「表層の型付けは〜より広い」の列挙に載っていない。
- 原因の分類: 表現の都合
- 直し方の案: 規則は今のままにし、01-12 の同節の「広い」の箇条に「`try` は構成子の形と網羅性だけを検査し、型の名前を問わない」を加える。

### 3. 01-12 と 07-04 への反映が残っている（オーケストレータの担当分）

- 重さ: 低
- 場所: 01-12「型の情報を付けた表層の構文と型付け」「ストア：可変のセルと明示遅延」、`Desugar.lean` 160 行のコメント
- 問題: 01-12 の写しに、`try` が戻り値の型引数の並びと構成子の名前を持つこと、`with` を一つの束縛の入れ子で表すこと、「必ず抜ける」に `with` を加えたこと、`try` の E が同じであること、`lazy` の R がないことがまだない。`plan.md` の C4「仕様の作業」には「`lazy` を表の一行にする」とあるが、01-12 は箇条のままである。`Desugar.lean` のコメント「表の行はない」は、行を足したら直す必要がある。
- 原因の分類: その他（反映の残り）
- 直し方の案: C4 の反映で 01-12 の同節に上記の項目を写す。`lazy` の行を表に足したら、`Desugar.lean` 160–161 行のコメントをその行の写しにする。

### 4. C4c の差分テストで正規化や除外が要る違い

- 重さ: 低（C4c への申し送り）
- 場所: `exchange.rs` 481–500 行（今は `try`・`lazy`・`with` を `outside` にしている）、`effects.rs` 8–110・143–196 行
- 問題: 形の違いは見つからなかった。`try` は `eval` と `finish` で必ず `let` を作り、`with` も `let_comp` で必ず `let` を作るので、Lean と同じ形になる。書き出しに要る作業は次のとおりである。`try` の `retArgs` は処理系が使う `try_kinds` の戻り値の型から取り、構成子の名前は `std_ctor` の `(adt, tag)` から `con_name` で作る。`with` は束縛の並びを本体の最後の `withE` の入れ子に変え、`o` を書き出しの `opaque` の名前の形（`"id:args"`）にそろえる。`Escape` と `Use` の型やエフェクトの付随情報、`Lazy` の `BodyId` は捨ててよい。プレースホルダの引数の中の `try`（TODO-178 と `decisions.md` の P10）は、処理系が外側の関数の戻り値の型を使い、Lean は展開後のラムダの R を使うので、入力に入れると必ず食い違う。再現テストで確かめるまで、差分の入力から除くか、既知の差として記録する。
- 原因の分類: その他
- 直し方の案: C4c の作業文書に上記の対応を書く。

### 5. C4a-2 で `try` の型引数の番号がずれる

- 重さ: 低
- 場所: `Typing.lean` 193・201 行（`R = some (.data … [u, e'])`）
- 問題: `handle` の節の中では、R が `R.map (Ty.shift k 0)` になる。節の中の `try` の `retArgs` は節の中の番号で書く必要があり、書き出しと C4a-2 の脱糖の両方でずらしを合わせる必要がある。今の定義を妨げるものではない。
- 原因の分類: 表現の都合
- 直し方の案: C4a-2 の作業文書に「節の中の `try` の `retArgs` は、節の型パラメータの分だけずらした番号で書く」と書く。

## 観点ごとの結論

- 観点 1（脱糖の各場合）: 問題なし。`try` の失敗側は `Error[U, E](var 0)` と `None[U]()` で、パターンの番号 0 を使う。`with` は入れ子にして `use (var 0)` とし、`rename` は要らない。`lazy` の本体は `.other` で移す。どれも 01-12 の表と処理系に一致する。
- 観点 2（型付けの規則）: 指摘 1 と 2 のほかは問題なし。`try` の E が同じであること（自動で変換しない）と、R = `none` によって `lazy` の中で書けないことは、01-09 と一致する。`with` のエフェクトは束縛・本体・`State` の和で、01-10 と `C_Use` の形に合い、束縛が後の束縛の式から見えることは入れ子で表せている。`lazy` のエフェクトが空であることは 01-06「明示遅延の型」に合う。`Exits` に `with` を加えたのは 01-06「必ず抜ける文」に合う。
- 観点 3（構文と規則の対応）: 問題なし。空の束縛列と `_` の束縛は表せず、01-02 の文法と一致する。文法より広い形（パイプの右辺の `try` など）にも脱糖の場合と型付けの規則がある。
- 観点 4（反例と証明の見込み）: 反例は見えない。`report.md` の 7 の見込みは妥当である。`try` は、網羅性を `Exhaustive.consCongr` で移し、入力の型の `TyOK` から引数の `TyOK` を出して `V_Var` の「継続の型でない」と `C_Escape`・`HasTypeArms.nil` の `Ty.WF` を得る。`V_Con` は型引数の WF を求めないので、`u` の条件は要らない。`with` は、`EnvClean.cons` に `TyOK (.opaque o)` を渡し、束縛の式と本体を `C_Sub` で全体の ε に広げ、`Eff.union` から `State` を含むことを示す。`lazy` は `hideConts_length` と `EnvClean.hide` を使い、`hR` は R = `none` なので自明に成り立つ。
- 観点 5（C4c）: 指摘 1 と 4 のとおり。
- 観点 6（後の段階）: 指摘 5 のほかは問題なし。`E_Lazy` は `hideConts` の形なので、C4a-2 で `EnvClean` を広げても `E_Lam` と同じ扱いで済む。`try` のパターンは `Release.Pat` を直接書いているので、C7 で `Release` の照合の形を変えるときだけ、`try` の脱糖も合わせて直す。
