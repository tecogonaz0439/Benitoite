# C6a-2 のレビュー結果（Opus）

レビュー担当: Claude Code の Opus 5.5（medium）。lake と cargo のビルドは走らせず、読むことだけで確かめた。

重さが高の指摘はない。定理が偽になる・弱まる箇所や、01-02・01-05・01-06・01-12 と意味が違う箇所は見つからなかった。脱糖の `rfl` の例（構築・一部の更新・逆順の更新・全フィールドの更新・パターン・入れ子・取得関数）は、手で番号を追い、意図どおりの値になることを確かめた。

## 指摘

### 1. 01-12 の写しと 07-04 が未反映

- 重さ: 中
- 場所: 01-12 の「レコード」の表、「型の情報を付けた表層の構文と型付け」、07-04 の「01-12 との対応」の表の「初回リリース版の拡張: モジュール、…、レコード、…」の行と「確かめる性質」の行
- 問題: 01-12 の更新の行と取得関数の行は、まだ全フィールドを変数に束縛すると書くが、Lean と処理系は更新で書き換える位置を `_` にし、取得関数で取り出す位置だけを変数にする。表層の構文の箇条に、構築・更新・パターンが構成子・型引数・位置・総数を持つこと、`accessors`、`lookupFun` が `defs` を先に引くことがない。型付けの箇条に、構築の規則（位置が `range n` の並べ替え）、更新の規則（型引数を `base` と共通にする、位置が空でなく重複せず範囲内、一分岐の網羅性）、パターンに独立した規則を置かないこと、`RecordsOk` の内容、01-05 より広い点（構築は構成子が一つかを問わずフィールドが 0 個でもよい、パターンの位置の重複・範囲外・リストの長さの違いを排除しない、`R(..)` も表せる）がない。07-04 はレコードを「対象外」に残している。
- 原因の分類: 01-12 の規則の誤り（更新・取得関数の行）と、表現の都合（写し）
- 直し方の案: 01-12 の更新の行を `match r { C_R(q1,…,qn) ⇒ … }`（qi は書き換えるなら `_`、そうでなければ zi）、取得関数の行を `C_R(_,…,zi,…,_)` にする。「型の情報を付けた表層の構文と型付け」に上の各項目を足し、広い点には「性質 1 は広い側で証明した」を添える。07-04 ではレコードを表層からの脱糖の行（段階 C6）へ移し、表現の違い（位置で持つ、`accessors` から取得関数を作る、`RecordsOk` を `Program.WellFormed` に置く）を書き、「確かめる性質」の行に C6 を加える。

### 2. レコードのパターンの束縛の番号の付け方が、Lean と処理系で違う

- 重さ: 中（C6c-2 の妨げ。01-12 の記述があいまい）
- 場所: `Syntax.lean` 90〜92 行（`Pattern.record`）、01-12 の 369 行（「束縛する変数は照合の順に番号を付ける」）、`patterns.rs` の `ast::Pattern::Record`
- 問題: Lean では、宣言の順に並べた後のコアのパターンの順で番号が決まり（最後に宣言したフィールドの束縛が 0）、分岐の本体もこの順に従う。処理系は書いた順に変数を積む。01-12 の「照合の順」はどちらとも読める。意味は同じだが、差分テストでは入れ子を含めて番号の付け替えが要る。
- 原因の分類: 表現の都合
- 直し方の案: Lean の定義はこのままにする。01-12 に「レコードのパターンは、宣言の順に並べたコアのパターンの照合の順に番号を付ける」と書き足す。C6c-2 の書き出しで、処理系の変数の並びを `toCore` の後の束縛の並びへ並べ替える対応表を作り、分岐の本体の変数にも使う。

### 3. 書き出しと交換用の表現がレコードに未対応

- 重さ: 中（C6c-2 の妨げ）
- 場所: `crates/benitoite/tests/desugar_export/exchange.rs` 1562〜1583 行（`definitions()`）、Lean の `Benitoite.Exchange`
- 問題: `definitions()` は `DefKind::Fn` 以外を飛ばすので、取得関数を比べられず `accessors` も作れない。交換用の表現は `Expr.record`・`Expr.recordUpdate`・`Pattern.record` を持たない。名前は `fun_name(BindingId)` で一意なので `RecordsOk` の重ならない条件は書き出した入力でも成り立つ。標準ライブラリなど利用者のもの以外のレコードの取得関数を呼ぶ場合は、`accessors` にその項目がないと表層の型付けが関数を引けない。
- 原因の分類: その他（後の作業の範囲）
- 直し方の案: C6c-2 で、`DefKind::FieldGetter { record, index }` から `accessors` を作り（使われる取得関数をすべて入れる）、生成した `accessorDef` を処理系の定義と個別に比べ、構築と更新は書いた順のフィールドを宣言の位置へ変換して書き出し、指摘 2 の対応表を使う。

### 4. 更新だけが位置の条件を検査する

- 重さ: 低
- 場所: `Typing.lean` 133〜141 行（`E_RecordUpdate`）
- 問題: 前提の `positions ≠ []`・`positions.Nodup`・`∀ i ∈ positions, i < n` は性質 1 の証明では使っていない。01-05 を写したもので置いてよいが、パターンは同じ種類の条件を排除せず、構築にも「一つ以上」の前提がないので、構文ごとに検査がそろっていない。定理への影響はない。
- 原因の分類: 表現の都合
- 直し方の案: 残すなら 01-12 の写しに「更新は位置の条件を検査し、構築とパターンは検査しない」と明記する。そろえて広くするなら三つの前提を外す。

### 5. コメントと記録の文言

- 重さ: 低
- 場所: `Syntax.lean` 59〜61 行（`fieldAt`）、コミット dd8dd5e のメッセージの "prefers defs, as Rust does"
- 問題: 処理系の `patterns.rs` は `BTreeMap::insert` を使うので同じフィールドを二度書くと後の値が勝つが、`fieldAt` は最初の値を使う（どちらも型検査を通らない入力なので意味に違いはない）。処理系は定義を `BindingId` で区別し、`defs` を先に引く優先の順は持たない（`RecordsOk` の下では優先の順は結果に影響しない）。
- 原因の分類: その他（記述の正確さ）
- 直し方の案: `fieldAt` のコメントに「重複は型検査で排除される。処理系は後の値を使うが、型の付いた入力では区別がない」と添える。`lookupFun` のコメントに「`RecordsOk` の下では優先の順は結果に影響しない」と書く。コミットメッセージは直さなくてよい。

## 観点ごとの所見

1. 脱糖の各場合の一致: 問題なし。構築は書いた順に評価してから宣言の順に並べ、更新は `base`・書いた値の順に `let` を置き、書き換える位置を `_` にし、書いた値をパターンの束縛の数だけずらし、全フィールドの更新でも `match` を残し、取得関数は取り出す位置だけを変数にする。処理系の `record` と `getters` に一致し、`let` の数も一致する。
2. 表層の型付け: 指摘 4 のほかは問題なし。型引数を `base` と共通にする点は 01-05 に、取得関数の型パラメータに制約がない点は 01-06 に一致する。`RecordsOk` の構成子が一つという条件は型検査を通ったプログラムで成り立つ。
3. `lookupFun` と性質 1 の言明: 問題なし。`HasMain` も `lookupFun` も `defs` を先に引くので `main_typed` と整合する。`desugar_typed` の引数と `Program.WellTyped` は変わっていない。
4. 広くなった型付けと性質 1: 問題なし。パターンの束縛の数・範囲の検査・脱糖はすべて `Pattern.toCore` を通るので、位置の重複や範囲外があっても表層とコアは食い違わない。総数 `n` の誤りは `P_Con` の `PatTys` が排除する。
5. 後の作業: 指摘 2・3 のほかは問題なし。取得関数を `accessorDef` として独立させてあるので、C6a-3 の定数を加えても名前の検索と混ざらない。C7 でも `recordFields` は `toCoreList` の結果に被せるだけなのでそのまま使える。
6. 01-12 の写し: 指摘 1・2 のとおり直す。
