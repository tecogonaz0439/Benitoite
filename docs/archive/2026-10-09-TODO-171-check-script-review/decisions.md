# 判断とその理由

測定の結果（[measurements.md](measurements.md)）をもとに案を作り、2026-10-09 に設計者が決めた。

## 1. 検査を 2 段に分ける（決定）

設計者の決定（2026-10-09）: 全体の検査は、リリースの前と、設計者が指示したときに行う。

`scripts/check.sh` を次の 2 段にする。

- **選んだ検査**（既定。`scripts/check.sh`）: 基準の版からの変更を調べ、変更したファイルの種類に応じて走らせる検査を選ぶ。改造と作業の途中、改造を取り込む前に使う。
- **全体の検査**（`scripts/check.sh --full`）: 今の `check.sh` と同じく全部を走らせ、加えて長いテスト（「3.」）も走らせる。リリースの前と、設計者が指示したときに使う。

理由: 改造の多くは処理系の一部か文書だけを変えるので、毎回の全体の検査（約 28 分）の大半は変更と関係のない確かめである。全体を通す区切りを残せば、選び方の漏れもそこで見つかる。

検討した代替案:
- 選ばずに全体を速くするだけ（「3.」「4.」だけを行う）: 文書だけの変更でも数分のビルドとテストが残る。
- CI に任せる: 07-03 は GitHub Actions を使わないと定めている。

基準の版: 既定は `origin/san_benito`（まだ公開していない変更の全体）とし、`--base <版>` で変えられるようにする。作業ツリーの未コミットの変更と、追跡していない新しいファイルも含める。

## 2. 変更の種類と走らせる検査（決定）

変更したファイルを次の種類に分け、該当する種類の検査をすべて走らせる。どの種類にも当たらないファイルがあれば、検査を始めずに止まる（終了状態 3）。設計者が、全体の検査（`--full`）・一部の検査（`--only <検査,...>`）・検査なし（`--none`）のどれで続けるかを決める（設計者の決定、2026-10-09。初めの案は全体の検査に倒す形だった）。

| 種類 | 対象のパス | 走らせる検査 |
|---|---|---|
| 文書 | `docs/`（下の行を除く）、`*.md`（下の行を除く）、`assets/`、`.claude/`（`settings` を除く） | なし |
| 言語仕様の例 | `docs/design/01-spec/`、`docs/design/08-appendix/08-04-*` | `cargo test --test spec_examples`、仕様の網羅の集計の本番 |
| 言語リファレンス | `docs/reference/benitoite.md` | `cargo test --test reference_examples` |
| Skill の生成の元 | 構文の章、`crates/benitoite/skill/`、標準ライブラリのソース、診断の表 | `gen_skill` で作り直して差分がないこと、`cargo test --test skill_docs` |
| 道具 | `tools/<道具>/` | その道具の自己検査（`spec_coverage.py --self-test`、`skill_eval.py --self-test`、`tools/bench/run.py --verify` など、道具が持つもの） |
| 処理系 | `crates/`、`fuzz/` | 書式、lint、テスト（長いテストを除く）、回収の強制（長いテストを除く）、仮置きの許可の残り、仕様の網羅の集計の本番（`testdata/` を変えたとき） |
| 依存 | `Cargo.toml`、`Cargo.lock`、`deny.toml`、`about.*` | 処理系の行の検査に加えて、ライセンス |
| ヒープ | `crates/benitoite/src/runtime/heap/` | 処理系の行の検査に加えて、`scripts/check-heap.sh`（今の AGENTS.md の決まりと同じ） |
| 形式化 | `formal/` | `lake build`（`sorry` がないこと） |
| 検査そのもの | `scripts/`、`.cargo/`、`rust-toolchain.toml`、`clippy.toml`、`.gitignore` など | 止まって設計者に尋ねる |

理由: 文書の変更で処理系の振る舞いは変わらない。例を含む章と生成の元だけは、テストが文書を読むので、そのテストを走らせる。

設計者の決定（2026-10-09）:
- 処理系を変えたときは、回収の強制を常に走らせる。根の数え漏れは、コード生成・組み込みの関数・VM のどこからでも生じうるからである（長いテストを除けば数分の見込み）。
- `formal/` を変えたときは、選んだ検査で `lake build` を走らせる（`sorry` がないことも確かめる）。全体の検査には含めない。
- 少なくともテストを走らせる前に、何を走らせるかを知らせる。スクリプトは検査を始める前に選んだ検査と理由を示し（`--dry-run` で示すだけにもできる）、エージェントは全体の検査や長いテストを含む検査を走らせる前に設計者へ報告する（AGENTS.md「テストの運用」）。

## 3. 長いテストを分ける（決定）

10 秒を超える単体テスト（約 20 件。百万規模の構造や深い再帰で、Rust の再帰を使わないこと・空間が一定であることを確かめるもの）に `#[ignore = "long: ..."]` を付け、全体の検査で `-- --include-ignored` を与えて走らせる。

理由: 単体テストの壁時計の時間は最も長い 1 件（407〜421 秒）で決まり、残りの 800 件ほどは数十秒で終わる。長いテストは、値の表現やヒープ・VM の作りを変えたときに価値があり、ほかの変更では結果が変わりにくい。

検討した代替案:
- 大きさを小さくする: テストの目的（百万規模で Rust のスタックを溢れさせない）を弱める。
- 環境変数で飛ばす: 飛ばしたテストが「通った」と表示され、見落としやすい。`#[ignore]` は「ignored」と数えて表示される。

設計者の決定（2026-10-09）: ランタイム・VM・参照インタプリタ（`src/runtime/`・`src/vm/`・`src/refinterp/`）を変えたときは、選んだ検査でも長いテストを走らせる（その変更で壊れうる性質を確かめるテストだから）。

対象は、測定で 10 秒を超えた 22 件のうち、大きさそのもので確かめる 16 件とした。残りの 6 件（正規表現の上限、コード生成の 2 件、CLI のコード生成の上限、リストの境界の操作、マップの無作為の操作。長いもので 50 秒）は、大きさではなく契約を確かめるテストなので、普段の検査に残した。ヒープのモジュールの 2 件は、`check-heap.sh` の Miri で大きさを縮めて走らせているので、`#[cfg_attr(not(miri), ignore = ...)]` とした。

## 4. ゴールデンテストを並べて走らせる（決定）

`tests/golden.rs` の `golden_suite` は、506 のスクリプトを一つずつ順に走らせる（152〜190 秒）。ケースごとに別の一時ディレクトリで動くので、スレッドに分けて並べて走らせる。失敗の報告の順と集計の表示は、今と同じにする。

理由: 選んだ検査でも全体の検査でも、処理系を変えたときに毎回かかる時間である。

検討した代替案: `cargo-nextest` を入れてテストを並べる。テストのバイナリをまたいで並べられるが、`golden_suite` は 1 件なので速くならず、開発の道具が一つ増える。

## 5. `list_hof_long` の除外（決定）

- 回収の強制からの除外は残す。回収の強制は安全点ごとに生きている構造の全体を辿るので、5 万要素のリストでは二次の時間になる。これは回収の強制の方式の性質であり、除外の理由を 07-03 に書いてある（「ヒープとランタイムの確かめ方（初回リリース版）」）。
- 参照インタプリタとの差分比較からの除外は、参照インタプリタが組み込みの呼び出しごとにリストの全体を写すこと（TODO-181）が原因なので、TODO-181 で直すまで、全体の検査でも残す。初めは全体の検査で除外を外す（環境変数で差分比較も走らせる）案にしたが、2026-10-10 の全体の検査で、このケースの差分比較が 1 時間 49 分を超えても終わらなかったので、やめた（二次の時間で、コードのコメントの「30 秒を超える」は控えめすぎた）。

## 6. 仕様の網羅の集計の本番（決定）

`secf1-*.bnt` の 9 件の印を 2 行に分けて直し（見出しは 01-06「エフェクトの宣言とハンドラの型付け（初回リリース版）」と 01-12「ハンドラ」）、本番の集計（0.1 秒）を、言語仕様の章か `testdata/` を変えたときの選んだ検査と、全体の検査に入れる。

## 7. 設計書と AGENTS.md に反映すること

- 07-03「処理系のテスト戦略」の完了条件の検査の表と、その前の【方針】（「各作業の完了条件に、次の検査がすべて通ることを含める」）を、2 段の検査の形に書き直す。
- AGENTS.md の `scripts/` の行（「作業を取り込む前に `check.sh` を通す」）と、関係する節。
- `check-heap.sh` の頭のコメントのうち、`check.sh` との分担を述べた行。

## 8. 実装の途中で決めたこと

- 仕様の網羅の道具の本番の集計は、secf1 の印を直した後も失敗した。道具がロードマップの完了条件を 5 行と決め打ちし、そのうち「処理系の単一バイナリを各環境で実行する」の行を除く仕組みを持っていたが、設計書の見直し（2026-10-09）でこの行をロードマップから外し、4 行にしたためである。道具の行の数を 4 にし、除く行の仕組みを外した（自己検査は、リンクを含む行の確かめを残る行に移した）。07-03 の「受け入れ例と仕様の項目の対応」の表にも同じ行が残っていたので消した。
- secf1 の印を 2 行にしたので、期待値（`.diag.json`）の行番号が 1 ずつずれた。`BENITOITE_BLESS=1` で 9 件だけを作り直し、差分が行番号と位置のずれだけであることを確かめた。
- Skill の生成物の確かめ（`gen_skill` で作り直して差分がないこと）を、構文の章（01-02）か処理系を変えたときの検査に加えた。今まではスクリプトの外で行っていた（AGENTS.md の `crates/benitoite/skill/` の行）。
- 道具の Python は、自己検査を持つもの（`spec_coverage.py`、`skill_eval.py`）は自己検査を走らせ、すべての道具の構文を読む確かめ（`ast.parse`。`__pycache__` を作らない）を加えた。`tools/bench/run.py --verify` は比較対象の処理系が要るので含めない。
- macOS の `/bin/bash` は 3.2 で、連想配列を持たず、空の配列を `set -u` のもとで展開すると誤りになる。選んだ検査の印は間接参照の変数で持った。
