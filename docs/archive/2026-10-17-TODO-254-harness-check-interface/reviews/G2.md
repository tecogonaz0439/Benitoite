1. **02-01 の shell の判定に R15 が反映されていない**（`docs/design/02-impl/02-01-pipeline.md:76`）

2. **harness-response の「検査失敗では unknown です」が checkReport の出力と合わない**（`harness-response.md:120`。`design.md:181` も同じ書き方）
   - 問題: checkReport で検査が失敗すると `main` が null になり、`processShellReference` の欄そのものが出ない。文字列の `"unknown"` は checkReport には現れない（`check_report.rs:82-84`。この形は C1b の計画のとおりである）。
   - 失敗の場面: ハーネスが `main.processShellReference == "unknown"` で検査失敗を見分けようとすると、その値は来ない。null を空集合に読み替えない規則があるので、偽の absent にはならない。ただし、外部に渡す契約の文と実装が食い違っている。
   - 修正案: BH-022 と design.md の段 2 に、「checkReport では検査失敗を `main: null` で表し、shell の参照も未確定とする。`unknown` は testCheckReport の Target で返す」と書く。

3. **標準ソース内の誤りの場合に、報告の diagnostics が通常の check と一致しない**（`check_report.rs:94-118`、06-01:261「順序も通常の検査と同じ」）

6. **受け入れ表のテストが重い**（`tests/cli_process.rs:53`）
   - 問題: 35 件の入力を一つの `#[test]` で扱い、約 70 回プロセスを起動する。10 秒を超える見込みが高いが（推測）、長いテストにするかを考えた記録がない。途中の一件が失敗すると、後の件を観測できない。
   - 修正案: 所要時間を記録する。分類ごとに分割するか、長いテストにするかを決める。

7. **コマンドの語を探すときにも分離値を消費するようになった**（`cli/mod.rs` の `parse_invocation` の最初のループ）

## 問題のなかった観点

- 報告の欄名・型・null:
  - schemaVersion、kind、producer、status、complete、targetsComplete、executed、requestedTargets、targets、sources、sourceSets、aggregateEffects、diagnostics、diagnosticTargets は、design.md・06-01・harness-response と一致する。
  - Effects の basis と expanded（辞書順）、Hash の形は一致する。
  - usageError の kind:check・code:null・primary:null は、報告の中だけに出る。
- ハッシュ: `Source::text()` の元のバイト列から取る。BOM・CRLF・不正な UTF-8・package.bnt・依存・標準ソースを、テストが独立に照合している。
- 終了状態: 0/2/3/1 と、書き込みを一度だけ行うこと（R14）が、閉じたパイプを使うテストで確かめられている。
- R3: 報告モードは引数の順に依らない。スクリプトの後の字面と分離値は報告モードを選ばない。明示した diagnostics=text と既定値を区別する。--diagnostics=json は併用でき、--deny-warnings の昇格は checkError になる。
- エフェクト:
  - 宣言した上限（`Scheme.effects`）を使う。IO.All の 10 個への展開、Http のエフェクト、main の Assert.Check（E0415）、die、ハンドラで処理した場合と宣言に残した場合、裸の try と or return を、それぞれ確かめている。
  - エフェクト変数、利用者エフェクト、未展開の IO.All は内部エラーになる。
- shell:
  - IO.Process を読まなければ absent になる。読んだのに束縛がなければ内部エラーになる。
  - 利用者定義の同名、組み込みの別名（E0339）、ハンドラの操作名とハンドラの本体、依存・呼ばれない関数・die による内部依存を、それぞれ確かめている。
  - 脱糖がすべての式に expr_types を要求するので、偽の absent は起きにくい。
- 不完全な結果: effects と aggregateEffects は null になり、空集合と区別される。sourceId が null になる場合と、R14 の Target の保持も確かめられている。
- 既存の経路:
  - run と通常の check は、準備関数を共有した後も、検査の回数、段のスレッドでの AST の破棄、不具合の報告の内容、終了状態を保っている。run は inspection を計算しない。
- 規約: panic・unwrap・添字を使っていない。文言は `cli::text` に置いている。大域の状態を加えていない。#[allow] を加えていない。コメントは日本語で設計書の節を引き、作業 ID を引いていない。
- テストは実プロセスで観測しており、テスト専用の本番 API はない。
- 06-01・02-02・02-10 の記述は実装と一致する。リンクの見出しも存在する。
