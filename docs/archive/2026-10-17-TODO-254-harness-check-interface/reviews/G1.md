## 【中】

1. **監視を登録できなくても、commit を `git` の由来で埋め込む**（`crates/benitoite/build.rs:109-131`）
   - 問題: `--git-dir`・`--git-path` の解決が失敗したとき、またはパスが非 UTF-8 のとき、`watch` は何も出さない。それでも `rev-parse --verify HEAD^{commit}` は成功するので、commit は埋め込まれる。次の二つの場合に、以後の HEAD の更新を検知しないまま古い commit を `git` の由来で返し続ける。
     - Git 2.31 より古い版。`--path-format` を知らないので出力が二行になり、`git()` が None を返す。
     - reftable の形式のリポジトリ。ref は `reftable/` に置かれ、HEAD は内容の変わらないスタブなので、監視しても変化が現れない。
     05-01 が書く検知の限界には、どちらも含まれない。
   - 修正案: git-dir の HEAD を監視に登録できなかったら、None（`unknown`）を返す。symbolic HEAD では、ref のファイルか packed-refs のどちらかを登録できなかったときも None にする。reftable は `<common-dir>/reftable` の有無で見分けて `unknown` にするか、05-01 と harness-response.md の限界に書き足す。

2. **ref を pack した後の普通の `git commit` を検知しない**（R2、05-01:68）
   - 問題: この限界は R2 で受け入れたものである。ただ、`git gc` は `pack-refs --all --prune` を行うので、gc の後の最初のコミットはいつもこの場合に当たる。そのときの値は null ではなく、古い commit が `git` の由来で返る。このリポジトリでも `.git/packed-refs` に `refs/heads/san_benito` がある。
   - 修正案（R の追加として設計者が判断する）: `<git-dir>/logs/HEAD` を、ファイルが存在するときだけ監視に加える。非 bare のリポジトリでは既定で reflog を取るので、HEAD が動けば、HEAD が指すブランチを `update-ref` で更新した場合も含めて、このファイルに追記される。ディレクトリを監視しないので、R2 の「存在するファイルだけを監視する」とも食い違わない。

## 【軽】

3. `tests/cli_process.rs:114-160` は、期待値を本体と同じ `env!` から組み立てている。このため、`""`→null と true/false の変換は、そのビルドで実際に埋め込んだ値の分しか通らない。本体に依存しない制約を加えるとよい。
   - commit は null か、小文字の十六進 40 桁または 64 桁であること。
   - 由来はそれぞれ許す値の集合に入ること。
   - provenance.commit が `git` なら commit が null でないこと。
4. `serde_json` に preserve_order がない（Cargo.lock に indexmap がない）ので、`--version=json` の欄は名前の順に出る。design と harness-response の例の順とは違う。契約上の問題はないが、06-01 に「欄の順序は契約に含めない」と一文書くとよい。
5. 05-01:66 の「HEAD は worktree 側」は、worktree を使わない場合を含めて正確に書くなら「`--git-dir` の側」である。
6. commit のない（unborn の）ブランチに最初のコミットを作っても、再採取は起きない。値は null のままで安全側だが、05-01:68 の限界の例に加えてよい。
7. `tests/build_info.rs:325` は、独立した fixture を使う五つの群を一つの `#[test]` にまとめている。前の群が失敗すると後の群を観測できない。群ごとに long の印を付けたテストに分けると、並列にも走らせられる。

## 問題のなかった観点

- 明示入力の検証: 空、前後の空白、短縮 ID、非 UTF-8 を拒否する。改行を含めて Cargo の命令を差し込む値を、`rustc-env` を出す前に拒否する。明示した `unknown` では Git を起動せず、由来を `environment` にする。
- Git を呼ぶ子の環境から六つの変数を除き、`--no-optional-locks` と `core.fsmonitor=false` を付けている。
- 根の三重の照合をしている。アーカイブで親の commit を採らない。worktree・detached・packed-refs の解決は design のとおりである。
- 存在しないパスを監視に登録しない。TARGET を監視に登録しない。
- `--version=json` の欄名、null、provenance、formats の三つのキーは、design と harness-response に一致する。未提供のキーを出さない。
- 既存の `--version` の二行と、後続の引数を無視する扱いを保ち、テストで固定した。
- 使い方の誤りは 2、書き込みの失敗は 1 を返す。
- panic・unwrap・添字を使っていない。文言は `text` に置いている。大域の状態を加えていない。`#[allow]` は表のとおりである。コメントは日本語で設計書の節を引き、archive の作業 ID を引いていない。
- テストは本当の入口で観測している。build_info は本番の build.rs を写した一時クレートと Cargo の命令ファイルを、cli_process は実プロセスを見ている。長いテストの印もある。
- 06-01・05-01 の記述と実装が一致する。harness-response.md の限界の記述とも食い違わない。
