## 検査・実行・文書の用途

benitoiteh は処理系をライブラリとして組み込まず、check/run/test を子プロセスとして起動する。制限モードでは、実行前にエフェクトを利用者へ示し、その確認を使って OS のサンドボックスの範囲を決める。処理系には、利用者向けの権限の説明や OS の設定を求めていない。

現在は `--version` の最初の行から版を読み、Skill は 0.0.5 の写しを埋め込む設計である。0.0.6 の処置の書き分けや language 宣言とずれるため、起動した処理系の文書を取得できることに意味がある。ビルドの区別と形式の版があれば、リリース番号の大小や文章の解析だけに頼らず機能を選べる。

## 字句から推し量る現在の手順

main では、まず check が成功した入口のファイルを読む。コメントと文字列を飛ばして字句に分け、ブロックの深さが 0 の `function main` を探し、引数と戻り値を飛ばして `uses` の名前を読む。IO.All は十個のエフェクトへ開く。読み取りに失敗した場合と、構文を確かめた版の一覧（0.0.5 のみ）にない版では、IO.All と Http.Listen・Http.Connect の和を用いる。

この手順は、組み込みのエフェクトを main の uses に書く規則と、組み込みのエフェクトを宣言するモジュールの import に別名を付けられない規則に頼る。処理系が構文を変えると、読み取りの失敗を検出できずに小さい集合を得るおそれもある。

テストには main がないことがあるので、現在の check では検査できない。ハーネスは対象のファイルの全 uses の和を取り、知らない名前があれば最大の集合とみなす。処理系のディレクトリ探索を作り直さないため、テストの対象をファイルに限る設計である。機能 2 では実際の test と同じ対象の選択を処理系が行うため、この制約を取り除く材料を返せる。

## 検査後の変更で防げることと残ること

検査と実行は別の子プロセスであり、その間に依存も含むファイルが変わりうる。ソースのハッシュを返すだけでは、後の実行を同じ内容に固定できない。機能 3 は、run/test が実際に検査したプログラムの契約を、渡された集合と比べることによって、確認していない種類のエフェクトを持つプログラムの開始を断る。

同じエフェクトのまま、書くファイルや送る内容が変わる場合は検出しない。Process.shell の参照の変化も、Process.Run の集合が同じなら機能 3 だけでは拒否できない。外部コマンドとその子孫、許したエフェクトの中の対象、外部の関数の振る舞いは OS の隔離などの別の範囲に残る。この限界は依頼元への返答にも含める。

## レビューの出力の案から採る部分

レビューは、明示した機械向けモードで単一の JSON を返す案を先に挙げる。JSON Lines にするなら開始・対象ごとの結果・最後の集計を設け、最後まで受信しなければ完全と認めない案である。共通の情報には、形式の版、作成した処理系の情報、結果の分類、完全かどうか、対象、宣言と展開後のエフェクト、読んだソースとハッシュ、診断を挙げている。

shell の参照は、名前解決の結果として「ある／ない／不明」を区別し、到達可能性の証明にはしない案である。テストの報告は `executed: false` と専用の kind を持ち、ファイルごとの成功と全体の完全性を分ける。版情報は形式ごとに対応する版を列挙し、コミットが分からなければ null とする。Skill は相対の論理名と長さ・ハッシュを持つ取得手段を挙げている。

レビューが推す環境制限のオプション化は拘束しない案である。[判断の案](../decisions.md) では、すべての実行で明示したローダ変数を拒否する案と比較する。レビューにある入力全体の固定、存在しない入力の記録、実行ファイルの信頼の証明までは今回の API の保証に加えない。
