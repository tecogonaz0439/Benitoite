# 設計者に尋ねる問いと推す案

## 判断の前提

Q1〜Q14 の推す案は、2026-10-17 に設計者とハーネスの担当がすべて了承した。各問いの検討時の本文を残し、末尾に答えを追記する。詳しい設計で生じた問いは R1 以降に記し、設計者が不在の間は必ず記載した推す案で進める。今回実装は行わない。[依頼](request.md) の機能番号 1〜6 と BH の番号を併記する。

判断の基準は [00-01「目的と設計原則」](../../design/00-overview/00-01-goals.md) である。原則 1・2 に従い、検査で確定できない結果を空の集合に見せず、報告と実行前の照合に同じ契約を使う。原則 3・4 に従い、LLM が失敗を説明できる情報を出す。原則 5 に従い、言語の構文やエフェクトの別名を増やす範囲へ広げない。

## Q1 main の報告は check のオプションにするか（機能 1、BH-022）

問い: `benitoite check --report=json <入口>` で、実行せずに一つの JSON を標準出力へ返す形でよいか。

| 選択肢 | 内容 |
|---|---|
| A（推す案） | check に --report=json を加え、kind: checkReport の単一 JSON を返す |
| B | inspect などの新しいサブコマンドを設ける |
| C | 既存の --diagnostics=json に成功時のエフェクトの行を加える |

推す案は A である。理由: check が行う検査をそのまま使い、現在の診断の流れに成功時のデータを混ぜずに済む（原則 4・5）。新しいサブコマンドは、サブコマンド省略時の同名ファイルの扱いまで変える。JSON Lines より一つの JSON の完了を確認しやすく、今回の静的な一覧に逐次表示は要らない。

オプションなしの check の出力は保つ。report のモードだけ、診断も JSON の diagnostics に収め、同じ診断を標準エラー出力へ重ねて書かない。`--diagnostics=json` の併記は許すが diagnostics の中身は変えず、`--diagnostics=text` の明示とは使い方の誤りとする。--report は json のみ受け付け、text という別の表示は加えない。

終了状態は成功 0、検査・読み取り・使い方の誤り 2、不具合 3 とする。新しい成功・失敗専用の終了状態は増やさない。E0414（main なし）、E0101（読み取り）など既存の診断を保ち、報告のためだけの E は加えない。パイプへの書き込み失敗は既存の規約に従って 1 とし、完成した JSON を返せない場合として扱う。check の中断は OS の既定のままとする。

答え（2026-10-17、設計者・ハーネスの担当）: 推す案

## Q2 報告するエフェクトと shell の参照はどこまでにするか（機能 1・2）

問い: エフェクトは宣言した上限を開いた集合とし、shell は検査したプログラム内の参照の有無を別に示す形でよいか。

| 選択肢 | 内容 |
|---|---|
| A（推す案） | 型検査を通った Scheme.effects を報告・照合に使い、shell は参照がある／ない／不明を示す |
| B | 本体から最小のエフェクトと、main から到達する shell だけを改めて解析する |
| C | uses のソースの文字列を報告し、展開をハーネスへ任せる |

推す案は A である。理由: 既存の契約と一致し、生成・修正の後も同じ上限を比較できる（原則 2）。B は高階関数や辞書を通る呼び出しまで扱う追加の解析となり、今回必要な保証より広い。C では独自の構文の解釈をハーネスに残す。[調査](study/effects.md) に具体的な表と関数を記す。

effects は `basis: "declaredUpperBound"` と `expanded` を持つ。IO.All は十個に開き、表示は正規名の辞書順、重複なしとする。宣言の綴りをもう一つ API として保つ欄は加えず、最小の集合を示すと読めない basis を付ける。Assert.Check もテストの契約の一部として報告する。

or die の Exit は型検査が既に追跡している。ハンドラで完全に処理し、関数の契約にも Exit を残さなければ expanded から消える。使わない Exit を uses に残した場合と IO.All の場合は残す。報告の処理が AST を見て Exit を足したり引いたりしない。or return と裸の try だけでは Exit を加えない。

`processShellReference` は present/absent/unknown、`shellReferenceScope` は `checkedProgram` とする。名前解決した標準の shell への式の参照を、入口と依存を含む検査対象で探す。到達しない関数の中も含め、ハンドラの case の操作名だけは参照の判定から外す。検査失敗では unknown とする。テストごとの到達可能性は示さない。Process.Run と shell を別のエフェクトに分ける要求には変えない。

答え（2026-10-17、設計者・ハーネスの担当）: 推す案

## Q3 main とテストに共通する報告をどう揃えるか（機能 1・2）

問い: 完全な成功と、不明な部分のある結果を区別できる次の共通形式でよいか。

| 選択肢 | 内容 |
|---|---|
| A（推す案） | 形式の版・分類・完全性・対象・ソース・診断を共通にし、成功時だけ確定した集合を返す |
| B | 成功では集合だけ、失敗では既存の標準エラー出力だけを返す |
| C | 不明な集合を常に最大の集合へ置き換える |

推す案は A である。理由: 検査の失敗と純粋な関数を機械で区別でき、失敗を誤って許可の根拠にしない（原則 1・4）。最大の集合へ置き換える判断は、結果を使う側に残す。

次の欄を checkReport と testCheckReport に持たせる。欄名は既存の診断の camelCase に揃え、schemaVersion を処理系のリリース番号と分ける。

| 欄 | 提案する意味 |
|---|---|
| schemaVersion | 整数 1。各 kind の形式ごとに管理する |
| kind | checkReport または testCheckReport |
| producer | name、version、build。Q7・Q8 の版情報と同じ値 |
| status | ok / checkError / usageError / internalError / interrupted。最後は test の中断だけ |
| complete | 必要な対象と全結果が確定し、許可の判断に使えるときだけ true。status: ok のときに限る |
| targetsComplete | test の探索を最後まで終えたか。全入口の検査成功とは区別する。main では入口を決められたか |
| executed | 常に false。利用者の main、テスト、補助関数を実行していないことを表す |
| requestedTargets | 与えた順の入力の番号・表示用のパス。誤った指定も残す |
| targets | 入口ごとの通し番号、入口の表示名、根、sourceId、対象の種類、ファイルごとの status/complete、main または tests |
| sources | 実際に読み込んだソースの sourceId、displayPath、kind、contentHash。kind は現在の SourceKind に対応する user/prelude であり、prelude は埋め込みの標準ライブラリ全体も含む。設定ファイル・依存も一覧に含む |
| sourceSets | 各 targetId が参照した sourceId の一覧。テストの入口ごとの検査の入力を対応させる |
| aggregateEffects | main の集合または全テストの和。complete: false のとき null。部分的な和を全体の集合として返さない |
| diagnostics | 既存の診断オブジェクトの配列。code: null を許す |
| diagnosticTargets | diagnostics の配列の添字と targetId の対応。探索全体や使い方の誤りは targetId: null |

main の項目は symbol: main、location、effects、processShellReference、shellReferenceScope を持つ。tests の項目は function、description（省略時 null）、location、effects を持つ。shell はファイルの検査対象のプログラム単位で返す。関数ごとの情報が確定しなければ effects は null とする。成功した純粋な関数は `expanded: []`、成功したテストなしの入口は `tests: []` とし、不明な tests は null とする。

sourceId と targetId は報告内だけで一意な文字列とする。別の check/run の識別値を照合して同一性の証明にはしない。テストの同じパスを二回指定した場合は別の targetId を持つ。sourceId は各検査の FileId へ対応させ、同名の表示パスがあってもまとめて失わない。

使い方の誤りは status: usageError とし、認識した --report=json のモードでは、既存の診断と同じ欄を持つ kind: check、severity: error、code: null の説明を diagnostics に収める。主位置がなければ primary は null とする。既存の CLI の文章による使い方の誤りは report 以外では変えない。

contentHash は `{ "algorithm": "sha256", "value": "64 桁の小文字の十六進数" }` とする。元のバイト列全体を対象とし、BOM・改行・不正な UTF-8 を正規化しない。読み取ったバイト列を再利用し、報告のために開き直さない。ソース表に完全な入力がないもののハッシュを推測しない。

表示パスは既存の診断と同じ表示用の文字列であり、OS のパスの完全な符号化や、親がファイルを開く指示ではない。UTF-8 でないパスの復元はこの版の契約にしない。診断は従来の file/位置を保ち、報告の識別値を位置オブジェクトへ差し込まず、sourceSets と表示名の対応で参照する。曖昧な同名は sourceId で別々に残すが、診断から実ファイルを一意に開ける保証は加えない。

完全性が false の場合も、読み込めたソースと診断、他の成功した対象を返してよい。全体の状態は test では interrupted、internalError、usageError、checkError、ok の順に優先する。複数の種類の失敗の詳細は diagnostics に残す。強制終了・abort・出力の切断では JSON 自体が欠けうる。受け取る側は、構文が完全な一個の JSON、既知の版・kind、status: ok、complete: true、終了状態 0 をすべて満たす場合だけ確定した集合として扱う。

source の一覧はビルドの全入力の記録にはしない。Wasm バイナリ、ハッシュ検証だけの読み取り、存在しなかった設定ファイルの一覧は初版から外す。理由: 依頼が求める読み込んだソースの識別と、後の実行を固定する仕組みは別であり、後者を満たすように見せるほうが誤りとなる。必要になれば別の形式の契約として検討する。

答え（2026-10-17、設計者・ハーネスの担当）: 推す案

## Q4 テストの非実行の検査は test のオプションにするか（機能 2、BH-023）

問い: `benitoite test --check --report=json <パス>...` で、他のファイルの結果も集めて返す形でよいか。

| 選択肢 | 内容 |
|---|---|
| A（推す案） | test --check を設け、--report=json で単一の testCheckReport を返す |
| B | check --tests を設け、test の対象選択をそこへ呼び出す |
| C | 最初の検査失敗で止める専用命令にする |

推す案は A である。理由: 対象を選ぶ test_entries と関数を選ぶ collect_tests を実行と共有でき、利用者にも test の対象であることが分かる（原則 2・4）。--check 単独なら非実行の検査と既存の形式の診断だけを行い、成功時も標準出力は空とし、警告があれば標準エラー出力へ書く。test --report=json 単独は、実行結果の別形式と取り違えないよう使い方の誤りとする。

通常の検査の誤りはファイルごとに残し、他のファイルも検査する。探索の失敗・中断・処理系の不具合では停止してよいが、全体を incomplete にする。成功した関数の結果があっても、全体の aggregateEffects は null となる。テストがない有効なファイル、空のディレクトリは成功した空の結果である。main は要求しないが、ファイルにある宣言は従来どおり検査する。

対象の順、重複、パッケージの境界、直接指定とディレクトリ経由の根の違いは現在の test と同じにする。明示パスの重複を今回取り除かない。L のコードが生じるコード生成は行わず、check の段までの報告であることを示す。実行可能と確定した保証にせず、通常の test でコード生成の制限に当たる場合は残る。

終了状態は成功 0、検査・入力・使い方の誤り 2、不具合 3、中断を処理できた場合 130 とする。非実行の検査にテスト失敗の状態 1 や kind: test/testSummary は使わない。出力失敗の 1 は Q1 と同じである。E0806 などの既存の診断を使い、非実行の検査だけの E は増やさない。利用者コードが書いた出力や変更が一切生じないことを、CLI の境界で確かめる。

test --check は --deny-warnings と診断の形式を受け、実行だけで意味を持つ --max-call-stack・--wasm-*・--allow-effects は受けない。check の --report と run の --allow-effects も役割を混ぜず、run --report は受けない。処理系のオプションの重複・未知の値の扱いは既存の CLI に揃える。

答え（2026-10-17、設計者・ハーネスの担当）: 推す案

## Q5 許すエフェクトはどのように渡すか（機能 3、BH-027）

問い: `--allow-effects=Console.Write,File.Read` のように、正規名だけを列挙する形でよいか。

| 選択肢 | 内容 |
|---|---|
| A（推す案） | run/test に一回だけ指定し、コンマ区切りの原子的な正規名を受ける。空文字列は空集合 |
| B | IO.All、import の別名、全許可の * も受ける |
| C | JSON のファイルを指定して集合を読む |

推す案は A である。理由: 報告の expanded を同じ名前のまま返せて、ソースや設定からの追加の名前解決が要らない（原則 2・4・5）。B は将来 IO.All の中身が増えた場合に、確認した集合まで意図せず広がる。C はファイルを読む時点の変更という別の問題を増やす。

run はスクリプトのパスより前、test は処理系のオプションの位置で受ける。サブコマンド省略の run も受ける。`--allow-effects <値>` と `--allow-effects=<値>` を許し、二回の指定、空の要素、余分な空白、未知の名前、IO.All、別名、*、同じ名前の重複は使い方の誤りとする。順序は自由である。空の集合は `--allow-effects=` と書く。オプションなしは現在どおり上限を掛けない。

main もテストも報告と同じ declaredUpperBound を比較する。Assert.Check を使うテストでは許す集合にもそれが必要となる。run の許す集合に余分な Assert.Check があっても、それだけでは誤りにせず、main の契約を含むかだけを見る。ユーザー定義のエフェクトは受けない。

収まらない場合は新しい検査の診断 **E0512**（仮の割り当て、現行の表に未使用）と終了状態 2 とする。足りない名前と許す集合、対象関数と位置を示す。診断の文言は英語の表へ集める。`--diagnostics=json` では既存の診断の一行として標準エラー出力へ返し、kind: check と code: E0512 で区別する。新しい実行の報告の形式を標準出力へ設けない。形式の版 `effectLimit: [1]` はこの引数・比較・診断の契約を示す。

答え（2026-10-17、設計者・ハーネスの担当）: 推す案

## Q6 一つでも許す集合に収まらないテストがあれば、全体を止めるか（機能 3）

問い: 上限を指定した test は、全対象の事前の検査を終え、全部が成功して収まった場合だけ一つ目を実行する形でよいか。

| 選択肢 | 内容 |
|---|---|
| A（推す案） | 関数ごとの包含を確かめ、対象全体を一度に開始するか断る |
| B | 各ファイルまたは各関数の直前に判定し、通るものだけ実行する |
| C | ファイルのすべての uses を合わせて判定する |

推す案は A である。理由: 後ろに拒否する関数があったとき、先のテストがファイルを書いた後では「何も実行しない」を満たせない（原則 1・2）。C は実行対象でない関数まで混ぜ、依頼の関数ごとの契約とずれる。

比較する集合は対象の @test ごとに求め、同じ許す集合と比べる。各関数が含まれることと、全関数の和が含まれることは同値だが、診断は不足のある関数を名指しする。検査の失敗・コード生成の制限・不具合がある場合も全体を開始しない。通常の test の「誤りのあるファイルだけ飛ばす」振る舞いは、上限のオプションを指定しない場合に保つ。

事前に検査・コンパイルした成果物を保持し、その成果物を実行する。検査だけ先に行って、後でファイルを読み直す方式は採らない。ディレクトリの対象も一度確定し、その後に追加されたファイルを途中から実行しない。依存の内容が入口ごとの検査中に変わる場合でも、各成果物に対応する契約を検査する。複数ファイル全体の一時点のスナップショットは保証しない。

E0512 だけなら 2、処理系の不具合なら 3、中断は 130 とし、現在の test の優先順位を保つ。開始しなかった場合に kind: test の行や passed/failed の件数を作らない。従来の集計行を必要とするモードでは testSummary の passed/failed を 0、filesNotRun を開始しなかった入口の数とし、E0512 を標準エラー出力に出す。既存の行の欄は増やさず、実行後の報告に新しい report を加えない。

答え（2026-10-17、設計者・ハーネスの担当）: 推す案

## Q7 版と使える形式は --version=json で返すか（機能 4、BH-025）

問い: 通常の --version の二行を保ち、`benitoite --version=json` だけを機械向けの問い合わせにする形でよいか。

| 選択肢 | 内容 |
|---|---|
| A（推す案） | --version=json の単一 JSON。--version はそのまま |
| B | version --format=json という新しいサブコマンド |
| C | --version の文章の後に JSON を加える |

推す案は A である。理由: 既存の version というファイル名の扱いを変えず、問い合わせる形式を明示できる（原則 4・5）。最初の引数だけで受け、余分な引数・未知の値は使い方の誤りにする。

欄は schemaVersion: 1、kind: version、name、version、unicodeVersion、build、formats とする。formats のキーは version、checkReport、testCheckReport、effectLimit、diagnostics、testResults、loaderEnvironment、skillList、skillDocument であり、それぞれ対応する整数の配列を持つ。初版はいずれも `[1]`、未実装の能力はキーを出さない。loaderEnvironment には Q10・Q11 のポリシーも別欄で返す。実装の途中では提供していない形式を先に宣言しない。

成功 0、使い方の誤り 2、不具合 3、出力の失敗 1 とし、専用の E は加えない。使い方の誤りは既存の文章の形式、不具合は既存の報告を標準エラー出力へ書く。これは非実行の問い合わせである。版情報自身の形式が分からなければ、利用する側は他の能力を推測しない。

答え（2026-10-17、設計者・ハーネスの担当）: 推す案

## Q8 コミットが分からないビルドはどう示すか（機能 4）

問い: ビルド時の明示値を優先し、なければ Git から採取し、分からない欄は null とする形でよいか。

| 選択肢 | 内容 |
|---|---|
| A（推す案） | 小さな build.rs と環境変数・Git を使い、不明を null とする |
| B | 明示した環境変数だけを使う |
| C | Git の情報を採取する専用クレートを加える |

推す案は A である。理由: 普通の手元のビルドを区別でき、アーカイブや Git のない環境も受け入れられる。JSON とハッシュは既存の依存で足り、新しいクレート・C の依存・実行時の Git を増やす理由がない。基盤を既存の道具で扱うという言語の目的にも合う。

### R1 全体を拒否した test の非実行を、形式1のままどう示すか

問い: E0512 または検査の誤りで一つも始めなかった場合に、0 passed/0 failed が成功に見えない形式をどう定めるか。

推す案: 対象の探索が完了して N>0 の入口が確定している場合、既存の testSummary の filesNotRun=N とし、kind:test を出さない。N は全体拒否で開始しなかった全入口の数であり、失敗した入口だけの数ではない。探索失敗などで数が分からなければ集計行を出さず、診断と非0終了を返す。中断は130、不具合は3、検査の拒否は2とする。通常の上限なしの数え方は保つ。

理由: 既存の行の欄と型で、開始しなかった対象があることを表せる。既知の件数のふりをして0を入れず、形式1の変更も不要である。新しい executed/status 欄、testAborted の行、null の件数へ変える案は Q9 の既存形式を保つ合意への影響が広い。受け手の成功判定は終了状態・filesNotRun・interrupted・集計行の有無まで含める。詳しい数え方は design.md の段3に定める。

### R2 commit の再採取の条件と dirty の不明をどう定めるか（事前点検後に改訂）

問い: 毎回の build.rs の再実行によるクレートの作り直しを避け、どのファイルと明示入力を再採取の条件とするか。

推す案: commit は Git から自動採取するが、再採取は build.rs 自体、HEAD・参照中のブランチの ref・packed-refs のファイル、`BENITOITE_BUILD_COMMIT`・`BENITOITE_BUILD_DIRTY` の変化だけにする。worktree の実際の管理場所は `rev-parse --git-dir`・`--git-common-dir` から求め、ref のパスも Git で解決する。dirty は自動で取らず、未指定は null・provenance.dirty は `notCollected`、明示値は `environment` とする。Git 不在・アーカイブ・採取失敗の commit は null・`unknown`、明示した unknown は null・`environment` とする。commit を明示した場合は Git を起動も監視もしない。不正な明示入力はビルドを止める。

理由: status を自動採取すると作業ツリーの変更に依存する。毎回の採取は Cargo が当該パッケージを作り直す原因となるためやめる。dirty を null とすれば、古い情報を false と推測せずに済む。欠けた provenance-refresh、index、作業ツリー全体の監視は採らない。V1 は変更なしで同じ cargo test を二回実行し、二回目に lib の再コンパイルと `Compiling benitoite` がないことを確かめる。

ファイルだけの監視の限界: 存在しない ref/packed-refs を登録すると毎回の再実行になる（[Cargo FAQ](https://doc.rust-lang.org/cargo/faq.html#why-is-cargo-rebuilding-my-code)、2026-10-17確認）ため、存在するファイルだけを登録する。packed ref だけの状態から loose ref が新設され、登録済みファイルが変わらない場合などは自動検知できない。Git の導入やアーカイブへの Git 管理の追加も同様である。この場合は明示入力の変更かパッケージの clean build が要る。参照する親ディレクトリの監視や毎回の再採取へ広げる案は、今回指定されたファイルだけの監視に反するため採らない。V1 でこの条件も観測し、「全 Git 更新を検知する」とは記載しない。監視の根拠は [Cargo Book](https://doc.rust-lang.org/cargo/reference/build-scripts.html#change-detection) と [git-rev-parse](https://git-scm.com/docs/git-rev-parse)（2026-10-17 再確認）である。

判断（2026-10-17、事前点検へのオーケストレータの指定）: 改訂後の推す案を採用する。設計者・ハーネスの担当の新たな了承とは扱わない。Q8 の自動採取の細部は本 R で置き換える。

### R3 report モードを引数順に依存させずに判定する方法（事前点検後に改訂）

問い: 公開 parse_args の Result<Command,String> を保ち、処理系のオプションの範囲内の使い方の誤りをどのように JSON へ包むか。

推す案: 内部入口は CliParseError(detail,report) を返し、公開 parse_args は detail へ写す。解析は途中の誤りを記録してオプションの範囲の走査を続け、走査後に有効な --report=json の有無でモードを決める。check はスクリプトの前まで、test は従来の全オプションの範囲を対象とし、既知の分離値はその場で消費する。--diagnostics=text と report の順序、--bogus が report より前か後かによって報告の kind を変えない。test --report=json は --check がなくても testCheckReport の usageError・2とし、実行しない。有効な report がなければ従来の文章を返す。

## Z1 で確認したビルド情報の監視の補足（2026-10-17）

## C2b で確認した報告の失敗の補足（2026-10-17）

### R14 捕捉後に保持できるソースと、失敗報告の境界をどう扱うか

問い: 共通の prepare_script は検査段の panic を診断へ変換するが、巻き戻された段の SourceTable は返さない。C1b の報告はこの診断を標準エラー出力へ送っていた。また、06-01 の「報告を組み立てる前の panic」は stderr へ送るという記述では、C2b が求める報告モード確定後の捕捉の範囲を区別できない。

推す案: 非公開の ReportContext に確定した入口と持ち出し済みの検査結果を保持し、入口選択から検査・抽出・組立・直列化までを捕捉する。検査段が返す不具合の診断を保ち、internalError・complete=false・main:null・aggregateEffects:null の報告へ包む。入口が確定していれば Target と targetsComplete=true を保つ。SourceTable を持ち出せなければ sources と該当する sourceIds は空配列、入口の sourceId は null とする。選択前の捕捉なら targets と sourceSets は空配列、targetsComplete=false とする。ソースの再読や検査のやり直しは行わない。

報告と直列化を終えてから一度だけ書き込みを試み、出力失敗は1で終える。失敗報告自身の組立が内部エラーを返せば、まだ書き込んでいない場合に限って既存の stderr の経路で3を返す。失敗報告自身の panic、報告境界外の初期化失敗・panic、abort・強制終了・出力切断には完成した JSON を保証しない。

理由: 段の巻き戻し後にソースを読み直すと、診断が使った入力と報告が食い違う可能性がある。既存の prepare_script の型と run/check の処理を保ち、報告側に残った情報だけで不完全さを示す変更が最小である。失敗した組立の途中の診断を再利用して再び失敗しないよう、再組立には内部エラーの診断だけを使う。出力開始後の再報告は、一つの JSON として解釈できない出力を増やすため採らない。

適用（2026-10-17、C2b）: 作業範囲内の最小の判断として推す案を実装し、design.md・06-01・02-10・harness-response.md に捕捉の範囲とソースを保持できない場合を明記する。形式の版・必須欄・公開 API は変更しない。設計者の新たな了承とは扱わない。test 側の接続は T2b に残す。

## C3 で確認した shell の参照の補足（2026-10-17）
