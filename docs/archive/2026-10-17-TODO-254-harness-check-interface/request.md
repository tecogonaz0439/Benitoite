2026-10-16 に benitoiteh（BenitoiteHarness）の担当から受け取った依頼であり、原本は reference/2026-10-16-benitoite-v0.0.7-request.md にあるが、reference/ は消えることがある。

Benitoite の `v0.0.7` のリリースに向けて、処理系に次の 6 つの機能を加えてください。どれも、別のリポジトリで試作している Benitoite 専用のエージェントハーネス `benitoiteh`（BenitoiteHarness）が使う機能です。設計（ADR、設計書、docs/todo の項目など）は Benitoite の規約に従って処理系の側で決め、設計が固まった段階で、実装の前に一度、私に内容を示してください。

### 背景

- `benitoiteh` は、処理系をライブラリとして組み込まず、`benitoite check`・`run`・`test` を子プロセスとして起動し、OS のサンドボックス（macOS の Seatbelt、Linux の Landlock と seccomp）を掛けて動かします。サーバモードはまだないので、その代わりの構成です。
- 制限モード（sh や Python を使わせないモード）では、実行の前に `main` のエフェクトを利用者に示して確認を受け、確認したエフェクトに合わせて OS のサンドボックスを狭めます。
- `v0.0.6` の処理系も `main` のエフェクトを出力しないので、`benitoiteh` はソースを字句の単位で読み直してエフェクトを推し量っています。この読み取りは処理系の構文の変更に弱く、`benitoiteh` は構文を確かめた版（今は `0.0.5` だけ）でしか読み取りを信じず、ほかの版では最大の集合とみなします。リリースのたびに確かめ直す必要があり、`v0.0.6` の `die` の予約や `return` の直後の改行の規則のような変更が入るたびに、ハーネスの側の作業が増えます。また、テストのファイルは検査もできません（`check` は `main` のないファイルを誤りとします）。また、`benitoiteh` が検査してから処理系が実行するまでの間にファイルが変えられると、確認したエフェクトと実行するスクリプトのエフェクトが食い違いえます。今回の機能は、これらを処理系の側で確定させるためのものです。
- サーバモードや、実行時の権限制御を前倒しで求めるものではありません。どれも、実行の前の静的な検査の結果を外に出すか、その結果で実行を断るだけの機能です。

ハーネスの側の設計は、次の文書にあります（コミット `b442d2b` に固定したリンクです）。設計書は `v0.0.5` を対象に書いたもので、`v0.0.6` に合わせた見直しはこれからです。この依頼文は `v0.0.6` の内容を確かめた上で書いています。

- 今のエフェクトの読み取りの手順（置き換えたい処理）: 同じ章の「`main` のエフェクトの読み取り」

### 依頼する機能

番号は優先の順です。実装の順は処理系の側で決めてください（4 を先に入れ、その版の情報を 1・2 の出力に含める順も考えられます）。オプションの名前、出力の形、終了状態の割り当ては、処理系の CLI の規約に合わせて決めてください。

#### 1. `main` の検査の結果を機械で読める形で出す（BH-022）

- `main` を実行せずに検査し、その結果を機械で読める形（JSON など）で出力する手段を設けてください。`check` のオプションでも、別の形でもかまいません。
- 含めてほしいもの:
  - `main` のエフェクトの集合。`IO.All` などのまとめた名前は、組み込みのエフェクトに開いた形で。`v0.0.6` の `try e or die` が加える `Process.Exit` も、ほかのエフェクトと同じ規則（ハンドラで処理したものを除くなど）で含めてください。
  - `Process.shell` を参照しているか。字面の検索ではなく、名前の解決の結果として。
- 利用者向けの権限の表示や、許可の判定は含めなくてかまいません（それは事前検討がサーバモードで行うとした別の機能です）。
- 処理系は `package add`・`update` で依存の公開の宣言のエフェクトを報告しているので、その仕組みを流用できるかもしれません（ハーネスの側では確かめていません）。

#### 2. テストを実行せずに検査し、テストの関数とエフェクトを出す（BH-023）

- テストの対象（ファイルとディレクトリ）を、テストを実行せずに検査し、実行の対象になるテストの関数と、それぞれのエフェクトを出力する手段を設けてください。
- 対象の選び方（ディレクトリを辿り、`package.bnt` を持つ下位のパッケージを除くなど）は、`test` の実行と同じ処理を使ってください。ハーネスが同じ規則を作り直すと、エフェクトを読んだ対象と実行する対象がずれるからです。
- テストの関数を一切実行しないこと（標準出力への書き込みもファイルの変更も起きないこと）を保証してください。
- 一つのファイルに検査の誤りがあっても、ほかのファイルの結果を出す作りにするなら、ファイルごとの結果と、全体が完全かどうかを分けてください。
- 出力の形は、既存の `test --diagnostics=json` の JSON Lines（`kind: "test"` と `kind: "testSummary"`）に揃えても、別の形にしてもかまいません。揃えるときは、実行の結果の行と、実行しない検査の結果の行を、形式の上で取り違えないようにしてください。

#### 3. `run` と `test` に許すエフェクトの集合を渡し、収まらなければ実行しない（BH-027）

- `run` と `test` に、許すエフェクトの集合を渡すオプションを設けてください。検査した `main`（`test` では実行の対象のテストの関数）のエフェクトがその集合に収まらなければ、何も実行せずに終わります。
- 終わり方は、ほかの失敗と区別できるようにしてください（診断のコードを分けるなど）。
- ハーネスは、利用者が確認したエフェクトをこのオプションで渡します。処理系が実際に読み込んだスクリプトで確かめるので、ハーネスが検査してから処理系が実行するまでの間にファイルが変えられても、確認していないエフェクトのスクリプトは動きません。
- 実行時の権限制御ではありません。実行の前の静的な検査の結果と、渡された集合を比べるだけです。

#### 4. `--version` を機械で読める形にする（BH-025）

- 版に加えて、ビルドを区別する情報（コミット、作業ツリーに変更があったか）を、機械で読める形で出す手段を設けてください。ソースからビルドした処理系は、版が同じでもコミットが違いうるからです。
- 1・2・3・6 の機械で読める出力の形式の版（どの形式に対応するか）も含めてください。ハーネスは、使える機能を、版の数の大小ではなく形式の版で判定します。既存の出力も版の間で変わります（`v0.0.6` では、診断に `kind: "die"`・`code: null` の報告が加わり、`test --diagnostics=json` の `exit` の失敗に `die` の欄が加わりました）。既存の `--diagnostics=json` と `test` の JSON Lines にも形式の版を付けるかは、処理系の側で判断してください。
- コミットが分からないビルド（ソースのアーカイブからのビルドなど）では、推し量った値を入れず、分からないことを示してください。

#### 5. `Process.Command` の `environment` でローダの環境変数を設定させない（BH-026）

- `Process.Command` の `environment` で、動的リンクのローダに働く環境変数（`DYLD_*`・`LD_PRELOAD`・`LD_LIBRARY_PATH`・`LD_AUDIT` など）を設定できないようにしてください。
- 黙って無視するのではなく、誤りとして返す形を望みます。LLM が原因を理解して書き直せるからです。
- すべての実行で禁じるか、オプションで有効にする制約とするかは、処理系の側で判断してください。ハーネスはどちらでも使えます。
- 外部コマンドに渡す環境変数の扱いの項目（docs/todo の TODO-058）と関係します。TODO-058 は環境変数を引き継がない手段を、こちらは危険な変数を渡させない手段を扱います。
- ハーネスは OS のサンドボックスでも同じ道を塞いでいます（書ける場所のファイルを実行できる形でメモリに写すことを拒む、Linux では静的なプログラムだけを許す）。これは言語の側で重ねて塞ぐためのものです。

#### 6. 同梱の Skill の文書を標準出力に書く（BH-024）

- 同梱の Agent Skill の文書を、インストールの先に書かずに、標準出力に書く手段を設けてください。文書の一覧と、名前を指定した一つの文書の両方です。
- ハーネスは今、`v0.0.5` の Skill の写しを実行ファイルに埋め込む設計です。`v0.0.6` で Skill の文書が変わったので（`or die` と `or return` の書き分け、`die` の予約、`language "0.0.6"`）、`v0.0.5` の写しのまま `v0.0.6` の処理系と使うと、LLM は古い書き方を学び、`language "0.0.5"` の宣言は `E0908` になります。これがあれば、起動した処理系と同じ版の文書を使えます。
- 文書の名前は `references/stdlib/IO.File.md` のような相対の論理名とし、`..` や絶対パスを含まないことを保証してください。

### 1・2 の出力に共通して含めてほしいもの

ハーネスは、出力が完全か、どの入力についての結果かを確かめられないと、少ないエフェクトを誤って信じる側に倒れえます。そのため、次のものを含めてください。

- 出力の形式の版（処理系のリリースの版とは別のもの）。
- 結果の分類（成功、検査の誤り、使い方の誤り、処理系の不具合）と、結果が完全か（対象をすべて調べ終えたか）。完全でない結果を、エフェクトのない結果と区別できること。
- 検査の対象（入口のファイル、`main`、テストの関数）と、検査で読み込んだソースのファイルの一覧と内容のハッシュ。
- 診断（既存の `--diagnostics=json` の形。`kind: "die"` のように `code` が `null` の報告もあるので、ハーネスはコードのない診断も受け付けます）。

### 守ってほしいこと

- 今の出力の約束を壊さないでください。`run` と `check` の標準出力にはスクリプトが書いた内容だけを書くこと、`--diagnostics=json` の診断の形（`v0.0.6` の `kind: "die"` を含む）、終了状態（0・1・2・3・130）の意味です。機械で読める出力は、明示したオプションのときだけ出し、スクリプトの出力や人向けの表示と混ざらない形にしてください。
- 新しい機能は、OS のサンドボックスの代わりにはなりません。説明の文書に、そう読める書き方をしないでください。
- この依頼は `v0.0.6` の CLI とエフェクトの規則を前提にしています。`v0.0.7` のほかの変更がこの前提（`main` の `uses` には組み込みのエフェクトしか書けないこと、組み込みのエフェクトを宣言するモジュールに `as` で別の名前を付けられないこと、終了状態の意味など）を変えるなら、そのことを教えてください。ハーネスの設計を直します。

### 受け入れの確かめ

それぞれの機能に、少なくとも次の場合のテストを置いてください。

- エフェクトがないもの、複数あるもの、`IO.All` を使うもの、エフェクトの別名を含む取り込みがあるもの。
- `try e or die` を使うもの（`Process.Exit` が含まれること）、`Process.Exit` を処理するハンドラの中で `or die` を使うもの、`or return` と裸の `try` だけを使うもの（`Process.Exit` が含まれないこと）。
- コメントや文字列の中に `uses` の字面があるもの（字面に頼らずに正しく出すこと）。
- 構文の誤り、名前の解決の失敗、処理系の内部の誤り（不明を空の集合として出さないこと）。
- `main` のないファイル、テストのないファイル、入れ子のパッケージ、重ねて指定したパス、ないパス（2 では `test` の実行と同じ対象になること）。
- 標準出力に書くテスト、ファイルに書くテスト（2 では一切実行しないこと）。
- 許す集合に収まる場合と収まらない場合（3 では、収まらないときに何も実行しないこと）。
- 親から引き継いだ値、`environment` での設定と上書き（5）。

### 終わったら知らせてほしいこと

- 決めたオプションの名前、出力の形（形式の版を含む）、終了状態と診断のコード。
- 入った版（`v0.0.7`）と、そのリリースのタグ。
- 依頼から外したものや、形を変えたものがあれば、その理由。

ハーネスの側では、これを受けて、エフェクトの字句の読み取りを処理系の出力に置き換え、未決事項（BH-022〜BH-027）を閉じます。
