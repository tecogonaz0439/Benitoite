# 作業の進め方

本章は、実装 LLM が一つの作業を始めてから終えるまでの手順と、複数の LLM が並行して作業するときの決まり、オーケストレータ（Claude Code）が作業を配って取り込む手順を定める。

## 作業を始める前に読むもの

1. リポジトリの `AGENTS.md`（T00 の後は、実装の規約の節を含む）。
2. 本実装プランの [README](../README.md) と、本章、[実装の規約](00-02-conventions.md)。
3. 担当する作業の文書（`20-tasks/Tnn-*.md`）。
4. 作業の文書の「読む設計書の節」に挙げた節と、「インターフェース」に挙げた 10-interfaces の章。

作業の文書に書いたファイルのパスは、`src/`・`tests/`・`testdata/` で始まるものは処理系のクレート `crates/benitoite/` からの相対パス、それ以外（`scripts/`・`tools/bench/`・`fuzz/`・`doc/` など）はリポジトリの根からの相対パスである。

設計書の節は、作業の文書が挙げたものを読めば足りるように作業を分けてある。挙げていない節を読む必要を感じたら、読んでよい。

## ブランチと並行作業

- 一つの作業を一つのブランチで行う。ブランチの名前は `impl/Tnn-<短い名前>`（例 `impl/T02-lexer`）とし、`san_benito` から分ける。
- 複数の LLM が同時に作業するときは、`git worktree add ../Benitoite-Tnn impl/Tnn-<名前>` で作業ごとに作業ディレクトリを分ける。
- 作業を始められるのは、作業の文書の「依存する作業」がすべて `san_benito` に取り込まれた後である。
- 作業が触れてよいファイルは、作業の文書の「作るもの」に挙げたファイルと、そのファイルのテストである。`src/lib.rs` と各 `mod.rs` の `pub mod` の宣言は T01 がすべて置くので、作業は変えない。ただし、作業が `sig=` で受け持つファイルの中に、非公開の子のモジュール（`mod decl;` など）を宣言して加えることはしてよい。ほかの作業のファイルを変える必要が生じたら、作業を止めて報告する。
- この決まりにより、並行する作業のブランチは同じファイルを変えない。`san_benito` への取り込みで衝突が起きたら、後から取り込む側が直す。

## 作業の手順

1. 作業の文書の「作るもの」と「手順の要点」に従って実装する。
2. テストを書く。新しいテストは、スキル `test-audit`（`.claude/skills/test-audit/SKILL.md`。Codex や OpenCode では `.agents/skills/test-audit/`）の作成時の関門を通してから加える（07-03「テストの設計の原則」）。作業の文書の「受け入れテスト」は、少なくとも満たすべき場合の一覧であり、一つの場合に一つのテストを書くことを求めるものではない。似た場合は表の形のテストの行にまとめる。
3. `scripts/check.sh` を実行し、すべての検査が通ることを確かめる（[実装の規約](00-02-conventions.md)の「完了条件の共通の検査」）。
4. 作業の文書の「完了条件」をすべて満たしたことを確かめる。
5. 完了の報告を書く（後述の「完了の報告」）。実装 LLM はコミットしない。確認を終えた作業は、オーケストレータがコミットする（[ADR 0085](../../2026-09-27-design-initial/decisions/0085-review-assignment-for-minimal.md)）。

## 型やシグネチャを変える必要が生じたとき

[10-interfaces](../10-interfaces/) の型とシグネチャを変えずに実装できないと分かったら、実装を進めずに、次のことを報告して止まる（07-03「実装の規約と静的な検査」）。

- 変えたい型またはシグネチャと、変えた後の形
- 変えないと実装できない理由（どの設計書の節の、どの規則を満たせないか）
- 影響する作業（その型を使うほかの作業）

報告を受けたオーケストレータ（Claude Code）が実装プランの改め方を設計者に示し、ユーザーの合意を得てから作業を続ける。設計書と実装プランが食い違うと気付いたときも、同じく止まって報告する。

## 完了の報告

作業を終えたら、次の項目を報告する。報告は、作業を依頼した会話の最後の応答として書く（Codex では、オーケストレータが `-o` で指定したファイルに書き出される）。

| 項目 | 内容 |
|---|---|
| 作業 | 作業の ID と名前、作業ディレクトリ、ブランチ |
| 作ったもの | 追加・変更したファイル |
| 検査の結果 | `scripts/check.sh` の結果（通ったか） |
| 受け入れテスト | 作業の文書の受け入れテストの各項目を、どのテストで確かめたか |
| 判断したこと | 作業の文書に書いていなかったことを、自分で決めた箇所と理由 |
| 残したこと | 作業の範囲で実装しなかったこと、気付いた問題 |

実装の確認（レビュー）は、[実装の確認の観点](00-04-review-checklist.md)に従って行う。誰が確認するかは、後述の「確認と取り込み」で定める。

## 作業の状態

README の作業一覧の「状態」の欄は、次の値をとる。欄を更新するのは、オーケストレータである。

| 状態 | 意味 |
|---|---|
| 未着手 | 依存する作業が終わっていないか、担当が決まっていない |
| 着手可 | 依存する作業がすべて取り込まれ、担当が決まった |
| 作業中 | 実装 LLM が作業している |
| 確認中 | 完了の報告を受け、実装を確認している |
| 完了 | 確認を終え、`san_benito` に取り込んだ |

## オーケストレータによる進め方

本節は、オーケストレータ（Claude Code）が作業を配り、確かめ、取り込む手順を定める（[ADR 0084](../../2026-09-27-design-initial/decisions/0084-implementer-assignment-for-minimal.md)、[ADR 0085](../../2026-09-27-design-initial/decisions/0085-review-assignment-for-minimal.md)）。実装 LLM は本節を読まなくてよい。

### 担当と起動の方法

| 担当 | 起動の方法 | 同時に起動する数 |
|---|---|---|
| Opus（medium） | Agent ツールで、エージェントの定義 `impl-medium`（`.claude/agents/impl-medium.md`。Claude Opus 5.5、推論の度合い medium）を起動する | 制限しない |
| Opus（low） | Agent ツールで、エージェントの定義 `impl-low`（`.claude/agents/impl-low.md`。Claude Opus 5.5、推論の度合い low）を起動する | 制限しない |
| Codex | Bash で `codex exec` をバックグラウンドで起動する（下のコマンド）。モデルと推論の度合いは `~/.codex/config.toml` の `gpt-6-luna` と `max` を使う | 二つ（実装と確認を合わせて。2026-09-27 に一つから改めた） |

Codex の起動のコマンドは次のとおりである。`<作業ディレクトリ>` は次節の worktree、`<報告のファイル>` はオーケストレータの作業用のディレクトリに置く。

```sh
codex exec -C <作業ディレクトリ> -s workspace-write -o <報告のファイル> - < <依頼の文面のファイル>
```

- `-s workspace-write` のサンドボックスでは、作業ディレクトリの外に書き込めず、ネットワークも使えない。Rust の版 1.98.1 のツールチェーンと cargo-deny は、オーケストレータが T00 の前に `rustup toolchain install 1.98.1 --profile minimal -c clippy -c rustfmt` と `cargo install cargo-deny --locked` で入れておく。
- ネットワークが要る作業（T30 の `libfuzzer-sys` の取得と nightly の Rust の導入、T31 の比較用の処理系の導入）は、オーケストレータが事前に取得と導入を済ませてから起動する。
- worktree のコミットは作業ディレクトリの外（リポジトリの `.git`）に書き込むので、Codex はコミットできない。この点でも、コミットはオーケストレータが行う。

### 依頼の文面

どの担当にも、次の内容を依頼の文面として渡す。

1. 作業の ID と、作業の文書のパス（`doc/archive/2026-09-27-implement-initial/20-tasks/Tnn-*.md`）。
2. 作業ディレクトリのパスと、そこから出ないこと。
3. 本章の「作業を始める前に読むもの」を読み、「作業の手順」に従うこと。コミットしないこと。
4. 型やシグネチャを変える必要が生じたら、本章の「型やシグネチャを変える必要が生じたとき」に従って止まること。
5. 最後の応答を、本章の「完了の報告」の表の形で書くこと。

### 配る順

Opus の作業は、依存する作業が取り込まれたら直ちに起動する。Codex の作業は、依存を満たすものを次の順に、同時に二つまで起動する。依存を満たしていない作業は飛ばし、満たした時点で列の先頭に戻す。

T00 → T01 → T06 → T04 → T05 → T07 → T08 → T09 → T10 → T29 → T24 → T25 → T32 → T30 → T26 → T27 → T28 → T31

Opus が実装した作業の確認（次節）も Codex が行うので、確認の依頼は、この列の実装の作業より先に起動する。確認を先にするのは、確認を待つ作業が後の作業を待たせるからである。

### 確認と取り込み

1. 作業ごとに `git worktree add ../Benitoite-Tnn -b impl/Tnn-<名前> san_benito` で作業ディレクトリを作り、担当を起動する。
2. 完了の報告を受けたら、状態を「確認中」にし、作業ディレクトリで `scripts/check.sh` を実行し、差分を[実装の確認の観点](00-04-review-checklist.md)に従って読む。
3. Opus が実装した作業は、Codex にも確かめさせる。`codex exec -C <作業ディレクトリ> -s read-only -o <報告のファイル>` で起動し、作業の文書と実装の確認の観点を示して、問題の一覧（ファイル、行、問題、直し方）を最後の応答に書かせる。
4. 問題があれば、同じ担当（直らなければ別の担当）に、問題の一覧を添えて直させ、2 に戻る。
5. 問題がなければ、作業ディレクトリでコミットする。コミットメッセージはスキル `git-workflow` に従い、1 行目を `Tnn <作業の名前>` で始める。
6. `san_benito` に取り込み（`git merge --no-ff impl/Tnn-<名前>`）、取り込んだ後の `san_benito` で `scripts/check.sh` が通ることを確かめ、状態を「完了」にする。作業ディレクトリは `git worktree remove` で消す。
7. 取り込みで依存を満たした作業の状態を「着手可」にし、起動する。
