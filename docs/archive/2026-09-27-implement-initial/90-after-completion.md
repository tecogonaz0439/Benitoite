# 最小実行版の完了の後の作業

本章は、20-tasks の作業をすべて終えた後に行う作業を定める。これらは実装 LLM に割り当てる作業ではなく、Claude Code と設計者が行う。

## 完了条件の確認

ロードマップの最小実行版の完了条件（[ロードマップ](../2026-09-27-design-initial/00-overview/00-03-roadmap.md)の「完了条件」）を、次の手順で確かめる。

1. `scripts/check.sh` がすべて通る。
2. `testdata/acceptance/INDEX.md` の対応表で、完了条件の 8 行のそれぞれに、通っているゴールデンテストが一つ以上ある（T25 の道具で確かめる）。
3. [性能](../2026-09-27-design-initial/07-quality/07-02-performance.md)のベンチマークのすべてが、`benitoite run` で小さな入力で実行できる（T31）。
4. 仕様の網羅の道具（T25 の `tools/spec-coverage/`）が出す「確かめるテストのない節」の一覧を読み、足りないテストを補うか、テストが要らない理由を記録する。

2026-09-27 に、1〜3 が満たされていることを確かめた（`scripts/check.sh` がすべて通り、ゴールデンテストは 197 本）。4 は行わず、v1 に回した。道具が挙げた 33 節の多くは v1 の範囲の節（01-09 の `?`、01-10 の `with`、01-12 のストアなど）であり、最小実行版のテストは v1 の処理系で作り直す見込みが大きいので、ここで節ごとに読み分けても v1 で使えない（設計者の判断）。

## テストの整理

07-03「テストの設計の原則」は、マイルストーンの完了のときに、スキル `test-audit` の監査の手順で、価値の低いテストを整理すると定めた。段ごとに一つのまとまりとして監査する。

最小実行版では行わず、v1 に回した。理由は完了条件の確認の 4 と同じく、最小実行版のテストが v1 で作り直しになる見込みが大きいからである（2026-09-27、設計者の判断）。

## 性能の測定

07-02「ベンチマーク集合」「測る項目」に従って測定し、`tools/bench/results/` に記録する。記録を 07-02「測定の結果の使い方」の三つの観点で並べ、v1 に進む前に最適化に取り組むかを決める。あわせて、IO の実行の二つの方式（ADR 0029）の扱いを決める材料にする。測定の手順は、スキル `benchmark`（`.claude/skills/benchmark/SKILL.md`）にまとめた。以後の測定もこのスキルに従う。

測定は次の段で進めた（2026-09-27 に設計者と合意した）。

| 段 | 内容 |
|---|---|
| 準備 | 比較対象の版を確かめ、`run.py --verify` で出力の一致を確かめる。CPython は macOS に付属の版（3.9.6。JIT なし）のまま使う。Ruby（YJIT の有無の両方）、Lua、OCaml、samply は設計者が導入した |
| 道具の補完 | 07-02 の測る項目のうち `run.py` になかったものを足した。実行時間と確保の計数でビルドを分ける（`--benitoite-alloc`）、バイトコードの大きさ（開発用の例 `bytecode_stats`、`--bytecode-stats`）、呼び出しの情報の上限に達する段数（`tools/bench/programs/depth.bnt`） |
| 入力の大きさの調整 | Benitoite での実行時間が 1〜3 秒になるように `run.py` の `BENCH_INPUTS` を合わせた。eval は、式の深さを入力にすると CPython の再帰の上限に先に達したので、深さを固定した式を繰り返し評価する形に改めた |
| 本測定 | スキル `benchmark` の手順で測る。測る間は、電源につなぎ、ほかの重いアプリケーションと、Codex やサブエージェントの作業を止める |
| プロファイル | samply でベンチマークを一つずつ記録し、`profile_summary.py` で関数ごとに集計して、命令の振り分け、値の操作、参照の数の増減と解放、組み込みの関数に分けて内訳を読む |
| 記録と判断 | 記録を 07-02 の三つの観点で並べ、最適化に取り組むか、OPEN-009 の扱い、IO の方式（ADR 0029）を決める |

結果は次のとおりである。

- **最適化**: 最初の測定のプロファイルで見つけた二つの費用を、設計書の決定を変えずに直した。O1 は、値の解放のたびに作業列を確保していたのを、確保しない作業列に改めた（list・string・lines で 5〜13% 短縮）。O2 は、VM の呼び出しのたびの引数の複製と、レジスタの並びの伸び縮みをなくした（fib・loop・tree・eval・println・list で 16〜44% 短縮）。どちらも Opus が実装し、Codex が確かめた。
- **記録**: O1・O2 の後に測り直した `tools/bench/results/2026-09-27-1ff816b0b156.md`（グラフ付きの HTML とプロファイルが同じ場所にある）を正とし、最適化の前の記録は消した。
- **判断**: 所見と方針は 07-02「最小実行版の測定の結果」に書いた。v1 に進む前の最適化は、命令の形と値の表現を変えずに行える局所的な直しに限り、値の表現の見直しは OPEN-039 として v1 の設計で扱う。IO の二つの方式は両方残す（ADR 0088）。比較対象に OCaml を加えた（ADR 0089）。OPEN-009 は、v1 の測定を残す事項として書き直した。
- **次の最適化の候補**: コード生成が出す余分な `MOVE` を減らすこと（変数を一時のレジスタへ写す `MOVE` が多く、loop の一回の反復で 8 回ある）と、振り分けのループで原型と枠を命令ごとに引き直すのをやめること。取り組むかは設計者が決める。

## 学習のための読み方

設計者が処理系を読んで学ぶ（[目的と設計原則](../2026-09-27-design-initial/00-overview/00-01-goals.md)）ための入口として、次の順を勧める。パスは `crates/benitoite/` からの相対である。各モジュールの先頭の `//!` のコメントが、対応する設計書の章を示す。

1. 開発用の例 `examples/disasm.rs` で、小さなスクリプトのコンパイル済みプログラムを表示する（`cargo run --example disasm -- <スクリプト>`）。既定では利用者の関数とラムダの原型だけを示し、`--all` を付けると prelude の原型も示す。表示の形式は `src/bytecode/disasm.rs` が決める。
2. `src/ir/desugar.rs` と `src/refinterp/` で、コア計算（01-12）の規則が Rust のコードにどう対応するかを読む。値と計算を分ける形（fine-grain call-by-value）の `return` と `let` が、モナドの単位と bind に当たる（01-12「本章の位置付け」）。
3. `src/typeck/solve.rs` で、単一化とエフェクトの最小解の求め方を読む。
4. `src/vm/mod.rs` で、末尾呼び出しとレジスタの窓を読む。
