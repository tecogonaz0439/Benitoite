## 手順の要点

### 字句の読み進めと報告の抑制

- `Parser` は、`resolve_newlines` の出力（`LineBreak` を含まず、最後が `Eof`）を受け取る。`Eof` の後を読もうとしたら、`Eof` を返し続ける。
- 02-03「誤りからの回復」の最後の方針（一つの誤りから派生した構文エラーを出さない）は、`Parser` に「報告を抑制中」の印を持たせて実装する。構文エラーを報告したら印を立て、期待どおりの字句を一つ読み進めたら（`expect` などが成功したら）印を下ろす。印が立っている間は、新しい構文エラーを報告しない。
- 誤りの字句（`TokenKind::Error`）は、その位置で期待していた構文（式・型・パターン・名前）の誤りのノード（`ErrorNode`）にし、新たな構文エラーを報告しない（02-03「字句」の最後の段落）。誤りの字句は字句の切り出しで既に報告されている。未知の記号（E0105）も誤りの字句として届く。`;`（E0106）は、字句の切り出しが改行の印（`LineBreak`）を置くので、改行の判定を経て `Newline` として届き、構文解析器からは文の区切りに見える（T02）。
- ノード番号は `ids.node()` で振る。ノードの span は、そのノードを構成する最初の字句の開始から最後の字句の終了までにする（02-02「span」）。字句が一つもないノード（回復で作る長さ 0 の誤りのノードなど）は、その位置の字句の開始に長さ 0 の span を置く。

### 診断 E0201 の文言の値

E0201 の型板は `expected {expected}, found {found}` と `unexpected {found}` である。`{expected}` と `{found}` に入れる語句は字句と構文の名前であり、子のモジュール `parser/text.rs` の定数の表にまとめ、`describe_token` はそこから引く（00-02「文言」）。期待する構文の名前の定数も同じモジュールに置く。語句は次のとおりとする。

| 置き換える値 | 語句 |
|---|---|
| キーワード・演算子・区切り記号の字句 | その字面をバッククォートで囲んだもの（`` `fn` ``、`` `)` ``、`` `=>` ``） |
| `LowerIdent`・`UpperIdent` | `` identifier `綴り` `` |
| `IntLit`・`FloatLit`・`StringLit`・`CharLit` | `integer literal`・`floating-point literal`・`string literal`・`character literal` |
| `Newline` | `a newline` |
| `Eof` | `end of file` |
| 期待する構文 | `a declaration (`fn` or `type`)`、`a type`、`a pattern`、`an expression`、`a name`、`a parameter`、`a type parameter`、`a constructor`、`a newline or `}``（ブロックの文の後など）、`` `{` ``（ブロックの始め）など |

期待する字句が一つに決まるときは、その字句の語句を使う（`` expected `)`, found `,` `` ではなく、`` expected `)`, found identifier `x` `` のように）。

### 誤りからの回復

02-03「誤りからの回復」の表のとおりに読み飛ばす。読み飛ばした範囲を一つの `ErrorNode` にし、その親の並び（トップレベルの宣言の並び、ブロックの文の並び、括弧の中の要素の並び）に置く。ただし、10-03 の型が誤りの要素を持てない並び（型パラメータの並び `Vec<TypeParam>`、引数の並び `Vec<Param>`、型の宣言の構成子の並び `Vec<Variant>`）では、回復した後に失敗した要素を並びに置かずに捨てる。診断は報告済みであり、構文エラーのある AST は名前解決へ渡らない（ADR 0019）ので、要素が欠けても後の段に影響しない。

- トップレベル: 括弧（`(`・`[`・`{`）の外にあり、直前の字句が `Newline` であるか先頭である `fn` または `type` まで読み飛ばす。
- ブロックの中の文、型の宣言の構成子: 同じ波括弧の中の次の `Newline`、またはその波括弧を閉じる `}` まで。`}` は読み飛ばさずに残す（ブロックの解析が閉じる）。
- 丸括弧・角括弧の中の要素: 同じ括弧の中の次の `,`、または閉じる字句まで。`,` と閉じる字句は残す。
- 開いた括弧と閉じた括弧を数え、内側の括弧の中の字句を読み飛ばす先とみなさない。`Eof` に達したら止める。

`match` の分岐の回復は T12 が同じ仕組みで書く。本作業は、回復の関数を「止まる字句の条件」を引数にとる一つの関数として作り、T12 から使えるようにする。

### 入れ子の深さ

02-03「入れ子の深さ」の数え方を、各解析の関数の引数 `depth: u32` で持つ。

- プログラムのノードの深さは 0、その子は 1 である。子のノードを解析するときは、親の深さに 1 を加えて渡す。
- ブロックの i 番目（0 から数える）の文は、ブロックの深さに `i + 1` を加えた深さで解析する。`match` の分岐（T12）も同じく、並びの i 番目に `i + 1` を加える。
- パターンの節は、行きがけ順に通して数えた番号で深さを決める（02-03「入れ子の深さ」、ADR 0086）。パターンを解析する関数は、`depth` の代わりに、基準の深さと、それまでに数えた節の数を持つ数え手（`&mut` で渡す）を受け取る。節を一つ作るたびに数え手を 1 進め、`k` 番目（0 から数える）の節の深さを基準の深さに `k + 1` を加えたものとする。最小実行版の文法では、パターンは `match` の分岐にだけ現れる（`let` の左辺は名前か `_`）。T12 は、一つの `match` のすべての分岐のパターンで一つの数え手を共有し、基準を `match` の深さにする。
- 深さが `MAX_DEPTH`（1000）を超えるノードを作ろうとしたら、その位置で E0208（`limit` に `1000`）を報告し、解析を打ち切る。打ち切りは `Parser` の印で表し、印が立ったら各関数は字句を読まずに誤りのノードを返して戻る。`parse` は、それまでに作った AST と診断を `ParseOutput` として返す。打ち切った後は、報告の抑制の印によらず、新しい診断を出さない。
- 深さの計算は `checked_add` で行う（`arithmetic_side_effects` の lint）。溢れたら上限を超えたとして扱う。

### 関数の宣言と型の宣言

- `fn` の後の名前が `UpperIdent` で、その後に `.` と `LowerIdent` が続けば、修飾した関数の宣言である。`kind` が `SourceKind::Prelude` なら `FnDecl.module` に入れる。`SourceKind::User` なら E0207（`module` に修飾の名前、`help("remove")`）を報告し、`module` に入れたまま解析を続ける。
- 関数の型パラメータの並びは `FnTypeParam`（`effect` を付けてよい）、型の宣言の型パラメータの並びは `TypeParams`（`effect` を付けられない）で読む。型の宣言で `effect` を書いたら E0201（期待する構文 `a type parameter`）とする。
- 戻り値の型を読んだ後、次の字句が `uses` なら `FnDecl.uses` に読む。戻り値の型が関数の型なら、その関数の型の解析が先に `uses` を読む（02-03「型の解析」）ので、`FnDecl.uses` は `None` になる。
- 戻り値の型（と `uses`）の直後が `Newline` で、その次の字句が `{` なら、E0205 を `{` の位置に報告し（`help("same_line")`）、`Newline` を読み飛ばして本体の解析を続ける。回復のためのこの読み飛ばしは、本プランで決めたものである。
- データ構成子の名前の直後が `(` で、その直後が `)` なら、E0206（`name` に構成子の名前、`help("remove")`）を報告し、引数のない構成子として続ける。
- 構成子のない型の宣言（`type T {}`）は構文エラーにしない。型検査が E0411 を報告する。

### 型

- 02-03「型の解析」の四つの項目のとおりに書く。`uses` の並びは、最初の `UpperIdent` を読んだ後、「次が `,` で、その次が `UpperIdent`」である間だけ読み進める。
- 並びの 2 番目以降の名前の直後に `[` が来たら E0209（`help("paren")`）を報告する。その `[` から対応する `]` までを読み飛ばし、並びを終える。回復の方法は本プランで決めたものである。
- 括弧の型は `ParenType` にする。`()`（中身のない括弧）は型ではないので E0201（期待する構文 `a type`）とする。

### パターン

- 01-02 の `Pattern` の規則を読む。`-` は、直後が `IntLit` のときだけ `LitPat { negative: true }` にする。
- `FloatLit` のパターンは E0201（期待する構文 `a pattern`、見つけた字句 `floating-point literal`）とする。
- 構成子のパターンは、括弧を書いたかを `has_parens` に入れる（`Tree.Leaf()` は `has_parens: true`、引数なし）。

### ブロックと文

- `Block` は `{` `LineList(Stmt)` `}` である。先頭と末尾の `Newline` を許し、文と文の間に `Newline` を一つ求める。
- 文の後に `Newline` でも `}` でもない字句が来たら、E0201（期待 `` a newline or `}` ``）を報告し、同じ波括弧の中の次の `Newline` か `}` まで回復する。
- `LetStmt` の名前は `LowerIdent` か `_`（`LetName::Wildcard`）である。

### 仮の式の解析（`parser/expr.rs`）

`fn parse_expr(p: &mut Parser, depth: u32) -> Expr` を、次の式だけを読む関数として書く。それ以外の字句は E0201（期待 `an expression`）とし、`Stmt` の回復に任せる。

- リテラル（整数・浮動小数・文字列・文字、`true`・`false`）
- 名前（`LowerIdent`、`UpperIdent`、`UpperIdent "." (LowerIdent | UpperIdent)`）
- `()`
- ブロック

T12 は、この関数を同じ名前とシグネチャのまま、完全な式の解析に置き換える。

## 受け入れテスト

テストは `lex` と `resolve_newlines`（T02・T03）で字句の列を作ってから `parse` を呼び、AST の形と診断のコードと主な位置を確かめる。

| 場合 | 入力（要点） | 期待 |
|---|---|---|
| 関数の宣言 | `fn f[T, effect E](x: Int, g: fn(T) -> Unit uses E) -> Unit uses E { () }` | 型パラメータ 2 個（2 個目は `is_effect`）、引数 2 個、`uses` に `E`、診断なし |
| 戻り値の型に付く `uses` | `fn f() -> fn() -> Int uses IO { 1 }` | 戻り値の `FnType.uses` に `IO`、`FnDecl.uses` は `None` |
| 括弧で囲んだ関数の型 | `fn f() -> (fn() -> Int uses IO) uses IO { 1 }` | 戻り値は `ParenType`、`FnDecl.uses` に `IO` |
| `uses` の最長一致 | 引数の型 `fn(fn() -> Unit uses IO, E) -> Unit`（`E` は大文字の識別子） | 内側の関数の型の `uses` に `IO` と `E`、外側の引数は 1 個、診断なし（名前の誤りは名前解決が報告する） |
| `uses` の後の `[` | `fn(fn() -> Unit uses IO, List[Int]) -> Unit` | E0209 |
| 型の宣言 | `type Tree[T] {` 改行 `Leaf` 改行 `Node(Tree[T], T, Tree[T])` 改行 `}` | 構成子 2 個、診断なし |
| 空の括弧の構成子 | `Leaf()` を含む型の宣言 | E0206、構成子は引数なし |
| 型の宣言の `effect` | `type T[effect E] { A }` | E0201 |
| 利用者の修飾した関数 | `fn List.map(...)`（`SourceKind::User`） | E0207 |
| prelude の修飾した関数 | 同じ入力を `SourceKind::Prelude` で | 診断なし、`module` に `List` |
| `{` を次の行に書く | 01-01「改行による区切り」の `fn double` の例 | E0205 が `{` の位置、本体は解析される |
| パターン | `-1`、`"a"`、`'c'`、`()`、`Tree.Node(l, _, r)`、`Some(x)`、`Tree.Leaf()` | 各 AST（`Tree.Leaf()` は `has_parens: true`） |
| 浮動小数のパターン | `1.5` | E0201 |

| `let` 文 | `let x: Int = 1`、`let _ = f` | `LetName::Var`・`LetName::Wildcard` |
| 文の後の余分な字句 | `{ let x = 1 2 }` | E0201 が一つだけ（派生した誤りを出さない） |
| トップレベルの回復 | 1 個目の関数の宣言の途中に誤りがあり、2 個目の `fn` が行の先頭にある | 誤りは 1 個、2 個目の関数は正しく解析される |
| 誤りの字句 | 予約語 `return` を名前の位置に置く | 構文解析の診断なし（字句の誤りは T02 が報告済み）、誤りのノード |
| 深さの上限 | 1000 を超えて入れ子にしたブロック、または 1001 個の文を持つブロック | E0208 が一つ、`parse` が戻る |
| 深さの上限の内側 | 入れ子の深さがちょうど上限のブロック | 診断なし |
| パターンの節の数の上限 | パターンの解析の関数を直接呼び、入れ子が浅く節の数が上限を超えるパターン（例: 引数が 40 個の構成子で、各引数が 30 段の入れ子）を解析する | E0208 が一つ |
| コメント | コメントを含むソース | `ParseOutput.comments` に字句の切り出しのコメントがそのまま入る |
| `;` の後の文 | `{ let x = 1; let y = 2 }` | 構文解析の診断なし（`;` は T02 が E0106 を報告し、改行の印として渡す） |

パターンは、仮の式の解析に `match` がないので、`parser/mod.rs` のテストのモジュールから `pattern.rs` の解析の関数を直接呼んで確かめる。T12 が `match` を加えた後、T12 はこれらを `match` の分岐を通したテストに書き換え、直接呼ぶテストを消す（T12 の「作るもの」）。

深い入れ子のテストは、テストのスレッドの既定のスタックの大きさで通らなければならない（[実装の規約](../00-common/00-02-conventions.md)の「再帰の深さ」）。通らなければ、再帰の各段で使うスタックを減らす。

## 難易度の理由

回復・報告の抑制・深さの数え上げという横断的な仕組みを、すべての解析の関数に一貫して組み込む必要があり、どこか一か所の抜けが派生した診断や打ち切りの失敗として現れる。`uses` の最長一致と戻り値の型への結び付き、E0205 の検出は、字句の並びの細部に依存する。後の T12 がこの基盤の上に式の解析を載せるので、基盤の作りの良し悪しが T12 の難しさも左右する。
