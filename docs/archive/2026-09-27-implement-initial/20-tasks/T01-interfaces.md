# T01 型の定義を置く

- 依存する作業: [T00](T00-foundation.md)
- 難易度: 1（1〜5。README の「難易度の目安」）
- 規模の見込み: 大（1500 行超。ただし書くのではなく取り出して置く）
- ブランチ: impl/T01-interfaces

## 目的

実装プランの [10-interfaces](../10-interfaces/) の `file=` のコードを、処理系のクレートにそのまま置く。以後の作業は、ここで置いた型と、全モジュールの宣言（`lib.rs` と各 `mod.rs` の `pub mod`）の上に中身を書く。型を先にすべて置くことで、段の実装を並行して進められる（07-03「実装の規約と静的な検査」）。

## 読む設計書の節

- [実装プランの README](../README.md): 「インターフェースの読み方」
- [リポジトリとクレートの配置](../00-common/00-01-repository-layout.md): 「処理系のクレートのモジュール」
- [実装の規約](../00-common/00-02-conventions.md): 「型とシグネチャを変えない」「`#[allow]` を書いてよい箇所」
- インターフェース: [10-01](../10-interfaces/10-01-base.md) から [10-11](../10-interfaces/10-11-prelude-source.md) まで（中身を理解する必要はない。何が置かれるかを知るために目を通す）

## 作るもの

- `crates/benitoite/src/` の下の、10-interfaces の `file=` のコードブロックが指すすべてのファイル（`lib.rs`、各モジュールの `mod.rs` とファイル、prelude のソース `prelude/*.bnt`）。
- `sig=` だけが指すファイルと、`pub mod` で宣言したのにコードブロックのないモジュールには、先頭のコメント 1 行だけの空のモジュールのファイル。
- T00 が置いた 1 行だけの `lib.rs` は、取り出した `lib.rs` で置き換える。

`src/main.rs` は置かない。`main.rs` は `cli::main`（T24）を呼ぶので、T24 が置く（10-01「クレートの骨組み」）。

## 手順の要点

1. T00 が置いた `crates/benitoite/src/lib.rs` を消す（取り出しの道具は既存のファイルを上書きしない）。
2. リポジトリの根で `python3 doc/archive/2026-09-27-implement-initial/tools/extract_interfaces.py place crates/benitoite` を実行する。道具は、コードブロックを文書に現れた順につなげて書き出し、空のモジュールのファイルを作る。
3. `scripts/check.sh` を実行する。
4. 取り出したコードは手で直さない。コンパイルや lint が通らなければ、誤りの内容と、どの 10-interfaces の章のどのコードブロックが原因かを報告して止まる（00-03「型やシグネチャを変える必要が生じたとき」）。実装プランの側を直してから、取り出しをやり直す。書式の検査（`cargo fmt --check`）だけが通らない場合も、手で整形せずに報告する。
5. `lib.rs` の `#![allow(dead_code)]` はそのまま残す。作業の途中では、後の作業が使う欄が読まれないからである（00-02「`#[allow]` を書いてよい箇所」）。T24 で外す。

## 受け入れテスト

- `scripts/check.sh` がすべて通る。
- `cargo doc -p benitoite --no-deps` が警告なしに通る。
- `git status` で、`crates/benitoite/src/` の下に新しいファイルができ、`main.rs` がないことを確かめる。
- 取り出したファイルの内容が 10-interfaces のコードブロックと一致する（取り出しの道具の出力のまま、手を加えていない）。

この作業は型の定義だけを置き、振る舞いを持たないので、Rust のテストは書かない。テストを書いても、宣言した型を読み直すだけの価値の低いテストになる（スキル `test-audit` の「価値の低いテストの型」）。

## 完了条件

- scripts/check.sh が通る（00-02「完了条件の共通の検査」）
- 受け入れテストのすべての場合を確かめ、完了の報告に結果を書いている
- 取り出したコードを手で直していない

## 難易度の理由

道具を実行して検査を通すだけの作業である。検査が通らない場合も、自分で直さずに報告すればよい。
