# 第5弾の判断の記録

2026-10-23、P1作成、P2でRP1対応。[README の設計者の決定](README.md#設計者の決定2026-10-23)と[調べの後の決定](README.md#設計者の決定2026-10-23調べの後)を具体化する。D1〜D27は設計者が決めた範囲、D28以降は不在中の委任に従って計画で決めた点である。実装済みの仕様の記録ではない。代替案の詳しい比較と外部資料は、各項の出どころに示した study に置く。

## 設計者の決定

### D1 ファイルの宣言の適用範囲

【決定】トップレベルのファイル単位のエフェクトの宣言を、そのファイルの直下の関数宣言すべての最外側の `uses` へ、型検査の前に一律に加える。公開関数、main、@test、外部関数、生成されたトップレベルの関数も含む。implement のメソッド、trait のメソッド宣言、ラムダ、引数・戻り値の中の関数型、エフェクトの操作の宣言、定数、ハンドラの節、局所の関数値、自動アクセサ等の内部生成物は対象にしない。文書の例は外側のファイル宣言を引き継がず、独立した仮想モジュールとして扱う（[plan.mdのA3](plan.md#作業-a3-入口の許可検査報告縮小警告)）。宣言できる効果の種類は制限せず、追加が原因の診断に追加元の位置を示す。

理由: 関数の型に契約の変化を残し、個別の関数だけを暗黙に例外とする規則を増やさない。メソッドには既存の型クラスの契約がある。

出どころ: README の最初の決定、[file-effects 3.2・3.5](study/file-effects.md#32-対象ごとの効果と既存の制約)。

### D2 エフェクトを宣言する語

【決定】個別・ファイルの宣言とも `uses` を使う。語の改名、旧語の移行診断、語を比較するLLM評価は今回の実装に入れない。

理由: 語を変えた場合の成功率の改善は未確認であり、既存構文と生成・移行の費用を増やす根拠がない。

出どころ: README の調べの後の決定、[effect-keyword 8](study/effect-keyword.md#8-今回決める範囲と推す案)、file-effects のQ1。改名した場合だけのQ9は適用しない。

### D3 書式の区切り

【決定】`${e:spec}` とする。通常の完全な式を一度解析した直後に残るコロンから、対応する閉じまでを元のソースから読む。式の内側のコロンを維持し、短いラムダ全体の後に残るコロンも書式の区切りとする。補間の入れ子を区別する先読み・字句の前処理と、範囲付きの字句診断の扱いを整えることを採用条件とする。

理由: 値と書式の対応を同じ補間内で読め、既存の名前付き引数や型注釈を壊さない。最初のコロンの探索や候補ごとの再解析では、この条件を満たせない。

出どころ: [format-and-width 4.1・4.2](study/format-and-width.md#4-書式の区切りと現在の--の全用途)、問い1。

### D4 最初の書式の範囲

【決定】小数桁、符号、ゼロ埋め、最小幅、左・右・中央寄せ、整数のd/b/o/x/Xと基数接頭辞を加える。負の整数は負号と絶対値の数字列とする。桁区切り、指数・有効数字、切断、任意の埋め文字、動的書式、暗黙の数の変換は加えない。書式なしの型集合・表記・定数式・評価順を保つ。

理由: 金額や表の用途を満たす範囲を先に定め、型別の丸めや切断単位を新たな未決事項にしない。

出どころ: [format-and-width 5.1〜5.3](study/format-and-width.md#5-最初の版の書式の案)、問い2。

### D5 精度なしの f

【決定】Float・Float32の `f` は6桁、Decimalの `f` は現在のscaleを保つ。`${1.5m:f}` は `1.5`、`${1.50m:f}` は `1.50`、`${1.5:f}` は `1.500000` とする。

理由: Decimalの既存の表記と先例に揃え、精度の省略でscaleを失わない。

出どころ: format-and-width 5.1、問い3、RS1-response M2。

### D6 符号と空白

【決定】符号指定は `+` だけを受理する。書式内の空白はすべて誤りとし、削除の候補を示す。`-` は省略への修正案を示して拒否する。式末尾からコロンまでの通常の空白は許す。

理由: 空白一つの混入を別の有効な指定にせず、省略と同じ受理条件の指定を増やさない。

出どころ: format-and-width 5.1・7.1、問い4。

### D7 型を限定する d・s・c

【決定】dは整数、sはString、cはCharacterに限定する指定として受理する。利用者定義のShowを補間の受理条件に加えない。各型と各フラグの適合はstudy 5.2の表をそのまま採る。5.1の文法（FormatSpec）と指定・意味の表も採り、`#`は値0にも接頭辞を付け、精度0では小数点を付けず、ゼロは符号・接頭辞の後、数字の前に補う。

理由: 出力が省略時と同じでも、型が変わったときに不適合を検出する役割がある。

出どころ: format-and-width 5.1・5.2、問い5。

### D8 書式の上限と組み合わせ

【決定】精度0〜28、幅1〜65535、数字はASCIIとする。空書式を拒否し、精度にはf、寄せには幅、ゼロ埋めには数と幅を要求する。ゼロ埋めと明示の寄せは併用せず、#はb/o/x/Xだけに使う。既定の寄せは数が右、それ以外が左、中央の奇数余りは右へ一つ多く置く。長い内容は切らない。

理由: 数字の範囲を型・ホストのビット数に依存させず、極端な指定と書きかけを静的に断る。この上限は測定から求めた値ではない。

出どころ: format-and-width 5.1、問い6および問い2の条件。

### D9 丸め・特殊値・地域設定

【決定】固定小数の丸めは三型とも最近接偶数丸めとする。Float系の負の零と、負の値から丸めた零の負号を保ち、Decimalで丸めた零の負号は消す。NaNへ符号を付けず、正のInfinityには+を適用し、非有限値のゼロ埋めは空白の右寄せにする。ASCII数字・小数点`.`・固定の符号と接頭辞を使い、地域設定を参照しない。

理由: 型を変えても丸めの中間の規則を揃え、各型の既存の零と特殊値の意味を保つ。整形で既存のFloat.roundの仕様は変えない。

出どころ: [format-and-width 6](study/format-and-width.md#6-丸め数の境界地域設定)、問い7。

### D10 幅の単位と補間の境界

【決定】幅は表示の幅とし、String関数と補間で同じ算法を使う。数える対象は一つの整形済みの補間値であり、隣の本文や別の補間との結合後の幅は保証しない。

理由: 日本語の列を揃える用途に合い、一般の文字列の連結に成り立たない加法性を前提にしない。

出どころ: format-and-width 9.4、問い8。

### D11 既定とCJK

【決定】`String.displayWidth` と `String.displayWidthCJK` を公開する。既定では曖昧な文字を原則1とし、CJKはクレートのwidth_cjkの列の例外も含む規則に従う。補間は既定に固定し、CJKは明示のpadding関数で先に整形する。端末から自動検出しない。

理由: 同じ入力の結果を環境で変えず、新しいモードの公開型や省略引数を増やさない。

出どころ: format-and-width 9.1・9.2・9.4、問い9。

### D12 制御文字の境界

【決定】U+0000〜001F、007F〜009F、2028、2029を幅0の境界とし、それらを除いた最大の連続部分ごとの幅を合計する。全入力にIntegerを返す。ANSI列の解釈・除去、カーソル移動量、行の最大幅を意味しない。列を揃える用途は制御文字のない一行を前提とする。

理由: 任意のStringに幅を定義し、値依存の書式失敗や端末の状態への依存を加えない。

出どころ: format-and-width 9.2、問い10。

### D13 幅で埋める四関数

【決定】`displayWidthPadStart`・`displayWidthPadEnd` と各CJK版を公開する。型は `function(s: String, width: Integer) -> String`、幅の二関数は `function(s: String) -> Integer`、すべて純粋とする。U+0020だけを補い、確保に成功した結果の幅は `max(W(s), width)` とする。0以下や既に十分な幅なら元の値を返す。

理由: 既存の単位が先の命名に揃え、切断や幅0の埋め文字の繰り返しを避ける。空白の加法性は両モードの状態遷移の再確認と独立期待値で確かめる条件を付ける。

出どころ: format-and-width 9.3、問い11。

### D14 幅の依存とUnicode版

【決定】unicode-width 0.2.2、表示の幅のUnicode 17.0.0を固定して共通に含める。更新による幅の変化は互換性の変更として記録し、CharacterのUnicode版と分けて示す。数・幅の本体をVM・Host・Wasmtimeから独立させ、予算と検査済みの整数変換を介して確保する。

理由: 文字列全体の例外を既存の基盤OSSに委ね、構成やOSごとに同じ関数の意味を変えない。

出どころ: format-and-width 7.2・7.3・10、問い12。

### D15 形式化の範囲と先行条件

【決定】TODO-273の書式の妥当性、型との適合、脱糖の型保存、検査の健全性をLeanで先行する。数の整形とUnicode幅の算法の証明は含めず、独立期待値で検査する。主な定理の前提・結論を変えず、公理とBuiltins.Assumptionsを増やさない。変更が必要と判明した作業を止めて取りまとめへ報告し、設計者の指示を待つ。その間はLeanに響かない作業を進められる。

理由: 既存の組み込みの境界と宣言済みの保証を維持し、通る証明のために仮定を追加しない。

出どころ: README の不在中の委任、format-and-width 7・8、問い13。

### D16 ファイルの宣言の位置・回数

【決定】メタデータ、import群、ファイルのuses、通常宣言の順とし、usesは一回だけ置ける。遅い宣言と重複を診断する。省略が空集合であり、空のusesやuses[]は受理しない。

理由: ファイル全体への効力を固定し、複数宣言の累積や後続だけへの適用という別の解釈を作らない。

出どころ: file-effects 3.1、Q3。

### D17 リスト間の合併

【決定】個別とファイルの有効なリストを合併する。各リスト内部の明示重複の既存診断は保つ。同じFailは型の別名を展開した同一性で合併し、異なる失敗型は既存どおり拒否する。IO.Allの意味上の展開とリスト内部の重複検査を区別する。

理由: 既存のusesを残した導入を可能にし、Failを名前だけで消して契約の衝突を隠さない。

出どころ: file-effects 3.4、Q4。

### D18 入口・外部・純粋さの既存規則

【決定】合併後の契約へmain・@test・外部関数・公開性・高階関数・Property・deriveの既存規則を適用する。main内のhandleでは宣言済みの追加を取り消せない。必要ならファイルを分けると案内する。生成した通常関数も合併後の純粋さを検査する。

理由: 一律追加の規則を守りながら、個別の入口や標準機能の保証を弱めない。

出どころ: file-effects 3.2・3.3、Q5・Q6。

### D19 ファイル位置の名前解決とNoFail

【決定】既存の参照と具体型をファイルのスコープで一度解決し、各関数の同名パラメータを取り込まない。Failの種類を制限せず、合併したシグネチャからNoFailを計算する。Stateを加えた後に、純粋な局所構築器だからという理由でStateを除かない。

理由: 関数ごとに同じファイル宣言の意味が変わらず、既存のFailの整形式を保てる。

出どころ: file-effects 3.4・3.5、Q7。

### D20 IO.Allの警告

【決定】ファイルのIO.Allにも関数ごとのW0501を出し、追加元を示す。共通宣言を一関数の実効果だけで狭める自動編集は出さない。個別usesの編集も追加分を考慮して安全なものに限る。

理由: 共通宣言の変更で別の関数を壊す編集を提案しないためである。

出どころ: file-effects 3.6、Q8。

### D21 回復の由来と抑制の範囲

【決定】診断済みの原因から生じた未確定な型の部分の由来を、Declared制約を先に解く前から保持する。E0467からのExpr::Errorだけでなく、E0403等で結果が未確定になる経路も対象とする。後の注釈・引数型・パターンから元の回復変数へ流し込まれた型を、その値の型を確定する根拠にしない。

理由: zonkや制約の処理順で元の原因を失い、後の使用に余分な不一致を出すことを防ぐ。

出どころ: [file-effects 5.3](study/file-effects.md#53-比較する案と抑制の境界)、Q10の条件1〜3。

### D22 独立した誤りの保存

【決定】束縛自身の明示契約、既知の外側の構造、正常な関数の宣言した結果型による不一致を残す。List[Error]の要素の不確定さとList/Integerの外側の不一致を分ける。関数全体や連結成分全体を一律に抑制せず、型クラス・網羅性・名前・ラベル・個数・禁止効果へ無条件に広げない。原因を少なくとも一件残し、誤り入力を実行しない。原因修正後は通常の型検査をやり直す。

理由: 依存した診断を消すために独立した誤りまで失わず、成功する型付けと実行可否を保つ。

出どころ: file-effects 5.3の条件3〜7と受け入れ表、Q10、RS2-response 中6。

### D23 標準ソースの規約

【決定】標準ソースはファイルの宣言を使わず、既存の処理系の検査でこの規約を守る。利用者の構文や@builtinの適用範囲に新しい例外は作らない。

理由: 元のソースから署名を切り出すSkill生成器で、合併した効果が抜けることを防ぎ、標準の契約を個別に読めるようにする。

出どころ: file-effects 3.6、Q12。

### D24 人間に示す上限

【決定】Skillで、`check --report=json` を受ける際は、06-01「main の非実行の検査報告」の受け手の条件全体（完全な単一のJSON、理解するschemaVersionとkind、status:ok、complete:true、終了状態0）を確かめたうえで、`targets[0].main.effects.expanded` を宣言上限としてハーネスが人間へ示すよう案内する。失敗・不明を空集合や自動許可に変えず、通常checkの標準出力の契約を保つ。

理由: ファイルの宣言でmainの一行から読めなくなる契約を、検査済みの報告から確認できる。ハーネス固有の画面や操作手順は写さず、処理系の版を固定した報告仕様を参照する。

出どころ: file-effects 3.3、Q13。

### D25 packageの構文による集計

【決定】型検査なしの集計を保ち、外部公開の直下の関数があるファイルだけファイル宣言の識別可能な組み込みの効果を一度合併する。public(package)のみ、非公開のみ、trait等だけのファイルには追加しない。入れ子の型やtraitへ複製せず、既存の明示usesの集計は保つ。IO.Allは展開しない。記録とupdateの増減に反映する。

理由: 開発中の型の誤りがある依存も記録する既存契約を保ち、宣言だけで増えた効果を報告から落とさない。

出どころ: file-effects 3.5「package が記録する依存のエフェクト」、Q14。

### D26 packageでのLogの識別

【決定】裸のLogとBenitoite.Logの標準束縛を個別・ファイルの両リストで同じ規則で識別し、名前を隠す宣言や別のimportがあれば標準Logと数えない。従来の裸のLogの記録も変わり得ることを案内する。

理由: 主用途であるLogを集計しつつ、構文だけで判定する集計の限界を越えない。

出どころ: file-effects 3.5、Q14の条件。

### D27 不在中の実装と公開候補

【決定】取りまとめは作業ごとのブランチで実装を受け、レビュー後にsan_benitoへ取り込める。版0.0.11とrelease検査まで進める。実装担当は新しいCodexセッションで一作業ずつ動き、git操作をしない。push・タグは行わず、履歴の集約も設計者の指示を待つ。Leanの停止条件はD15を優先する。

理由: 委任された実装と確認を継続し、公開と主定理の変更を設計者の判断に残す。

出どころ: README の調べの後の決定、本依頼。

## 計画で決めた点

### D28 字句診断の保留と前処理

【決定】補間内で通常の数リテラル・BadSymbolとして生じる診断を、補間ID・元span・診断の種別を持つ保留列へ分ける。構文解析が式の直後のコロンと対応する閉じを確定してから、その範囲だけを専用書式解析へ渡して保留分を置き換える。範囲外・式の解析失敗時は元の診断を残し、UTF-8・双方向制御・コメント・物理改行・個数制限の診断は保留による除外の対象にしない。改行・ラムダの前処理は文字列の入れ子ごとに状態を隔離し、外側の先読みは対応する文字列全体を読み飛ばす。内側の式の前処理は維持する。

理由: 元の空白と位置を失わず、字句の段で式の文法を重ねて実装しない。F0で有限の試行により接続方式を点検し、同方式で成立しなければ範囲を拡大する前に取りまとめへ報告する。

出どころ: format-and-width 4.1・4.2と「計画で決める点」1、RS1 X1・X2。割り当て: F0・F1・F2。

### D29 内部の整形契約と符号化

【決定】`%Format.<基本型名>` を内部の直接の組み込み頭とし、valueと七つの定数引数を渡す。順はkind・align・sign・alternate・zero・width・precision、型はInteger・Integer・Integer・Boolean・Boolean・Integer・Integerである。kindは既定0/d1/b2/o3/x4/X5/f6/s7/c8、alignは既定0/左1/右2/中央3、signは既定0/+1、幅省略0、精度省略-1とする。省略の精度を具体値へ直す意味は型別に定め、交換には省略を残す。Stringを含む14型に各一つとし、種類ごとに頭を増やさない。

理由: 新しい公開型や生の書式の実行時再解析を加えず、LeanとRustが同じ固定シグネチャへ独立に脱糖できる。

出どころ: format-and-width 7.2・8と計画事項2。割り当て: L1・L2a・L2b・L3・F3・F4a・F4b・F5。

### D30 交換形式の版

【決定】現行corpus13/sidecar5に対し、新しいformattedを持つcorpus14/sidecar6を導入する。既存の旧版の意味と拒否条件を保ち、旧版に新構成を混ぜた入力は再生成を案内して拒否する。書式なしのstringExpr/convertedは保ち、書式ありのStringをstringExprに落とさない。表層の書式を残し、双方が別々に定数引数を作る。

理由: 新構成を旧版の読者が読み落とすことを防ぎ、補間自体の型付けと脱糖の比較を維持する。

出どころ: format-and-width 2.3・8.3と計画事項2、現行Exchange/Version.lean。割り当て: L3・F5。

### D31 依存宣言と版表示

【決定】`unicode-width = { version = "=0.2.2", default-features = false, features = ["cjk"] }` を通常の直接依存にする。`--version=json`に任意の文字列欄 `displayWidthUnicodeVersion` を加え、形式の版は保つ。人間向けは既存の二行を維持し、表示の幅の版はJSONと英語リファレンスで示す。第三者表示と依存ライセンス検査を割り当てる。

理由: 必要な機能を明記し、既存の二行契約を変えずにCharacterと表示の幅の版を区別できる。

出どころ: format-and-width 10と計画事項3・4、06-01「版と対応する形式の問い合わせ」。割り当て: W1・W2・Z1。

### D32 有効な宣言と追加元の保持

【決定】元のASTの `FnDecl.uses` を編集せず、Moduleに `file_uses: Option<UsesList>` を保持する。名前解決でファイルの参照を一度解決し、型検査の宣言収集で有効な効果行と効果ごとの個別・ファイルの元spanを作る。公開性も追加元の解決済み参照で検査する。型付け・入口・外部・NoFail・警告・CLIはこの有効な契約を使い、整形や編集は元ASTを使う。呼び名は「ファイル単位のエフェクトの宣言」とし、00-04に「ファイルの直下の関数の最外側の効果行へ一律に合併する宣言」という定義と、定める01-02・01-07の章を加える。独立した理論概念の新しい訳語にはしない。

理由: 元ソースの編集範囲と合併後の意味を分け、NodeIdを複製して同じ名前を関数スコープで解決し直す必要をなくす。

出どころ: file-effects 3.5・3.8と計画事項3・4。割り当て: A1〜A4。

### D33 生成・移行のプロトコル

【決定】derive inventoryを2から3へ上げ、moduleの `fileUses`（nullまたは元の宣言とspan）と `importInsertLimit`（宣言開始、宣言なしはnull）を必須にする。preambleEndの意味は保つ。生成器版を `3.1.0-syntax-batch5` へ上げ、意味ハッシュの算法版3と生成記録・manifest/receipt版3は保つ。旧inventoryを拒否し、旧生成記録は現行の本文・ハッシュ検証を経たpreviewによる再確認だけを許す。旧manifestのapplyと旧記録のcheckは互換としない。

【決定】try-actions inventoryにはversion2を新設し、owner.usesを個別の元文字列のまま保ち、file_uses（元文字列とspan）・effective_effects（検査済みなら上限、未確認ならnull）を必須にする。manifestも1から2へ上げて旧版を拒否する。実装メソッド・ラムダへはファイル効果を加えない。共通宣言を一関数の編集範囲に使わず、確認不能な契約を自動承認しない。

理由: 新しい境界情報を古い読者が無視して適用するのを防ぎ、既存の個別usesの欄の意味と確認済みハッシュの条件を保つ。

出どころ: file-effects 3.2・3.8と計画事項3。割り当て: A5・A6。

### D34 診断と回復の実装方式

【決定】開始版で未使用のE0261をファイル宣言の位置・回数、E0262を書式の構文・範囲・組み合わせ、E0468を書式と型の不適合に割り当てる。既存の意味の誤りは既存コードを使い、書式なしE0422は保つ。回復では既存Provenanceのshapes/recovered/components/usesを拡張し、診断済みの原因IDと型の部分への経路・束縛自身の契約を保持する。成功入力の単一化順と実行用Ty・交換は変えない。

理由: 原因と利用側の要求を区別し、診断コードの衝突や第二の無条件な依存グラフを増やさない。

出どころ: format-and-width 7.1、file-effects 3.6・5.3・5.4と計画事項4、diag/codes.rs。割り当て: A1・F1・F2・F4a・C1・C2。

### D35 分割・検査・測定

【決定】Leanを最初の段にまとめ、定義・言明・仮定のレビューとsorryなしの既定ビルドをF1以降の形式化の内側の実装の先行条件とする。F0は本番を変更しない接続試行としてB0直後、L1の前に行う。W・A・CはLeanから独立した作業列とし、停止時はそちらを選べる。workは各作業、stageは新接続、changeは改造全体で一度、releaseは最終候補で一度割り当てる。check-formal全体は接続を閉じるF5と最終の関係状態で行う。shortは処理系を変えた取り込みごとに行う。未接続の本体と依存だけのW1はW2後の一回へまとめ、examples/toolsだけのA5は外し、F5は処理系本体を変えた場合に追加する。targets/fullとLLM評価、実行ファイルの大きさの増分の測定は計画に入れない。

理由: 形式化の先行と独立作業の継続を両立する。今回は性能目標を約束する改造でもバイナリ配布でもなく、targets/fullの開始には別途了承が要るため、未承認の測定を約束しない。

出どころ: 両questionsの計画事項、README の委任、本依頼。割り当てと時間は[plan.md](plan.md)を正とする。

### D36 A1の取り込み途中の防御

【決定】A1とA2は別の取り込みを保ち、A1ではファイルの宣言をASTに保持したうえで、型検査へ入る前に宣言のあるモジュールを処理系の未接続の制限として拒否する。A2がこの防御を外し、有効な契約の合併へ切り替える。構文だけを読むpackage・整形器・inventory等も、未対応のまま宣言を黙って無視する入口はA1で拒否し、A4〜A6が各接続の完成と同時に防御を外す。

理由: 一時的な取り込みやshort用の状態でも、ファイルの宣言を読み落とした小さい契約や記録を成功として返さないためである。A1とA2を一つにまとめると、構文と契約のレビューが一作業へ集中する。

出どころ: RP1指摘3。割り当て: A1・A2・A4〜A6。

### D37 0.0.11の互換性変更の登録

### D38 L2とF4の分割

【決定】L2をL2a（型付け・脱糖・型保存・範囲と捕捉）とL2b（表層検査・健全性・計算可能性・有限支持）、F4をF4a（型集合・適合・E0468・回復との接続）とF4b（脱糖・定数評価・実行器との接続）へ分ける。L2aでも既定ビルドをsorryなしで通すため、新構成に対する判定器の一時的な拒否と、その拒否を根拠にした既存の健全性等の証明の最小限の追随を含める。L2bはその拒否を外し、正負両方の判定と残る証明を完成させる。F4aはF2の未接続の防御を保ち、F4bが全実行経路をつないで外す。

理由: 構成子の追加は全再帰読者へ影響するため、ファイル名だけで分けるとL2a末のビルドが成立しない。一時的な拒否の状態は段の完成とは扱わず、主定理の言明・公理と取り込み途中の実行の境界を維持する。

出どころ: RP1指摘6、現行のInterpPartとCheckの読者。各IDを別セッション・別work・別結果として扱い、同じ担当が続ける場合も新しいセッションへ引き継ぐ。共通依頼文の一セッション一作業を保つ。

### D40 仮予算と見積もりの更新

【決定】一作業30〜60分はセッションを区切る仮予算とし、所要時間の予測や完了を保証する上限として使わない。分割後23作業の仮予算は990〜1320分（16.5〜22時間）であり、studyの実装・文書の見込み30〜59時間は別に保持する。F0後とL1後に、実装・記録の実時間、残る箇所数、検査・ビルド・レビューの時間を分けて表全体を更新する。

理由: セッションの分割だけでは工数は減らない。studyのLeanの時刻補正も数・幅・回復の実装時間の短縮を裏付けないため、初回の実績がない段階で短い仮予算を終了見込みへ読み替えない。

出どころ: RP1指摘5・6、format-and-width 12、file-effects 6。割り当てと集計はplan.md。

### D41 性能の比較 short の比べる元

【決定】short の比べる元（before）を、開始版 B0 でなく、W1 の取り込み `a1f4fb5f3e5c3619aad6ecb2b1f7c9d20586317a` とする。W2 以降の取り込みの short は、この版と比べる。

理由: 比較の道具（`tools/bench/compare/`）は、依存の差を測定に混ぜないよう、比べる版どうしで `Cargo.lock` の依存の記録が一致することを求め、W1 で `unicode-width` を加えた後は B0 と比べられない。W1 は依存と、まだ呼ばれない関数を加えただけなので、W1 との比較で W2 以降の変更の影響を測れる。B0 から W1 までの差（依存の追加による実行ファイルの変化）は short では測っていない。

出どころ: 2026-10-23、W2 の後の short で道具が `Cargo.lock dependency records differ across comparison states` で停止した。plan.md「検査の割り当て」の性能の比較 short の行の before を読み替える。
