### F2 の解析と診断

- 区切りの規則: `parse_interp` は式を一度解析し、残った `Colon` のときだけ `parse_format` を呼ぶ。閉じは入れ子の数で `StrMid`・`StrEnd` を探し、元のソースから範囲を読む。字句をつなぎ直していない。D3 と study 4.2 に合う。
- E0262 の範囲: 空、空白（Unicode の空白すべて）、`-`、未知の種類と順序の違反（`kind`）、幅 1〜65535、精度 0〜28（数字列の桁数と辞書順で比べてから変換する）、精度に `f` が必要なこと、寄せとゼロ埋めに幅が必要なこと、ゼロ埋めと明示の寄せを併用しないこと、`#` を b・o・x・X に限ること。D6・D8 の表と一致する。`${x:.2}` には `}` の直前へ `f` を足す修正案があり、テストで適用後の再解析も確かめている。
- 式側の保留診断: 書式の範囲（`formats` の補間 ID と span の両方）に入る保留分だけを除き、それ以外の数・記号の診断は戻す。式の解析に失敗したときは `parse_format` に入らないので、元の診断が残る。
- F0 の申し送り（短いラムダの直後の `:end lambda`）: F1 でラムダの境界の対応表を文字列ごとに分け、F2 で明示のラムダの本体を `BlockEnd::Lambda` でコロンの位置で止める。そこで終わったときは、`end lambda` を閉じとして消費しない。`${lambda() x:end lambda}` が E0262 一件だけになることをテストで確かめている。
- 整形器: 書式の範囲（コロンから閉じの字句まで）の字句の前の空白をすべて消し、字面を写す。式の末尾とコロンの間の空白も消える。式の末尾の字句とコロンを密着させても字句の切り方が変わる組み合わせは、正しい式にはない（式は `:` で終わらず、`<`・`-` で終わる完全な式もない）。
- 一時防御: 型検査（`generate.rs` の E0262 と `pending` の注記）、定数評価（`Unavailable`）、脱糖（`InternalError`）の三か所で、書式を捨てて旧経路へ進むことを防いでいる。型検査の後に AST を読む箇所（`runtime/assert.rs`・`resolve/walk.rs`・`modules/internal.rs` ほか）は、型検査で止まるので書式付きの入力に届かない。

### F1

- 保留列は、lex の結果から parse の必須引数へ渡る。parse の呼び出し元 27 か所（examples・道具・テストを含む）はすべて同じ lex の `pending` を渡しており、空の列を渡して診断を失う箇所はない。fuzz のクレートは parse を直接呼ばない。数の誤りが字句の診断から構文の診断へ移ったので、字句の診断だけで可否を決める呼び出し元がないかも確かめた。formatter・verify・package・skill/generate・try_actions_inventory は、どれも構文の診断も見ている。
- 改行の前処理: `StrStart` で外側の状態（括弧の積み、深さ、die の深さ）を保存して初期化し、`StrMid` で初期化し、`StrEnd` で戻して `previous = StringLit` とする。従来は `StrEnd` が `previous` になっていたが、`previous_ends_die` は `KwDie` と die の閉じ括弧だけが立てるので、die の判定は変わらない。
- ラムダの境界の対応表: 文字列ごとに積みを分け、文字列全体の対応だけを外側へ渡す。補間の中の閉じていない括弧や `end` が、外側の対応を変えない。
- 先読み: `when_ahead` と `legacy_clause_after_with` は `outside_strings` を通す。外側から見ると文字列全体を飛ばし、内側から始めた先読みは自分の補間の閉じで止まる。study 4.1 の受け入れの例（`when + "${n:>3}"`）は、F2 で診断なしになった。
- 二乗の処理: 先読みも `restore_pending` も字句列を一度だけ辿る。候補のコロンごとに解析し直す処理はない。

### 組込み向けの構成と規約

- `base/format.rs` が依存するのは `base::prim`・`base::display_width`・`base::Decimal` だけで、VM・Wasmtime・言語の値・ホストに依存しない。数の変換は `try_from` か、収まることが明らかな箇所に限られている。
- `builtin!` に加えた型付きタプルの形は、言語側の 8 引数を宣言の順に `FromArg` で取り出し、数の過不足を断る。`arity` の `as u16` は既存の形と同じ書き方である。clippy の `too_many_arguments` を `#[allow]` で抑えず、Rust の本体の引数をまとめる方法をとっている。AGENTS.md の「内部の共通の形を直接書かない」にも反しない。02-06 にこの形の記述がある。

#### L9（軽）F2: 一つの文字に字句と書式の二つの診断が出るおそれ

- 問題: 全角の数字や U+3000 は、字句解析が E0103 を出す（保留しない）。そのうえで `read_spec` が同じ文字に `kind` か `whitespace` の E0262 を出すと読める。テストは E0103 があることだけを確かめている。
- 修正案: 再現したら、書式の範囲に保留しない字句の誤りがあるときは E0262 を出さないか、E0262 の主位置を重ねないようにする。

#### L10（軽）F2: 書式付きの定数で、E0262 に別の診断が加わるおそれ

- 場所: `typeck/consts.rs` 1413 行（`EvalError::Unavailable`）。
- 問題: `const s: String = "${1:d}"` で、型検査の E0262（`pending`）に加えて、`Unavailable` から「定数式でない」類の診断が出るかもしれない。一時防御の間だけの問題である。
- 修正案: F4b で定数評価を接続するときに、この入力で診断が E0262 だけ（接続後はなし）であることを確かめる。

#### L11（軽）F2: `BlockEnd::Lambda` が補間の中のすべての明示のラムダに効く

- 場所: `syntax/parser/exprs.rs` の `block_end`（`BlockEnd::Lambda`）と `parse_lambda` の `format_boundary`。
- 問題: `p.interpolation` は補間の式の解析中ずっと立っている。そのため、呼び出しの引数の中など、補間の最上位でない明示のラムダでも、文の始まりのコロンで本体を閉じる。正しいコードでは文の始まりにコロンが来ないので、影響は誤りの回復の経路の診断に限られる。
- 修正案: 必須ではない。気になるなら、F4a の回復のテストに `"${f(lambda() x\n: 1 end lambda)}"` のような誤りの入力を加え、診断が F1 の前と同等であることを確かめる。
