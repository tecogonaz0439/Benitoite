## 1. effects と dependency の欄名の衝突

**受け入れた。** 再開時点で本文4.1・4.2・5.1には、既存の effects 欄との字句・意味の衝突と、第二候補の撤回まで反映されていた。一方、本文8節と問いの一覧は effects を第二候補とする初稿のままだったため、両方を直した。最終比較を uses と can に絞り、effects は with より下に置いた。

01-02「ファイルの先頭の部分」、`syntax/header.rs:11,18`、`syntax/parser/header.rs:221` を照合した。欄の解析は LowerIdent を要求するので、内部の字句の名前を KwUses に保っても、effects を全域キーワードにする衝突は解消しない。依存の記録 `effects "Console.Write"` と契約の追加 `effects Console.Write` は、ブロックの内外・引用符から構文的には区別できる。従って「文法が曖昧」とはせず、二用途の意味の取り違えを未測定の懸念として記した。

本文5.1に、欄解析の特例・文脈語・欄名の変更という解消案と、package の記録・E0929・移行案内への影響を残した。本文7.3では解消の追加分を Δ欄名、不明とした。第二候補に残していないため、解消案未採用のまま数値を仮定することはしなかった。CHANGELOG 0.0.5 は過去の記録として保ち、採用するなら今回の移行案内を加えるという範囲である。

## 2. can・may・allows の許可の読みの評価

**受け入れた。** 再開時点の本文4.1の三軸と対照表を確認し、問いにも同じ区別を反映した。軸は、作用の上限として読めるか、人間が許す操作の一覧として読めるか、注釈による権限付与・実行時の強制と誤解されるか、である。人間が許す操作と読むことは目的に合い、三語とも実行時の強制との区別を説明する必要がある。

can を改名の第一候補に残す理由は「行いうる」という上限の読みと Ante の同位置の先例である。may を個々の実行の推量、allows を宣言による権限付与と読みやすいとする順位は、読解実験による事実ではなく調査担当の判断として残した。can だけ説明で問題が解決するとする扱いはしていない。Cambridge の公式検索結果で can・may の可能性・許可の用法を照合し、直接取得が403で本文全体を取得できなかった範囲も本文に明記した。

## 3. 新語の文脈判定と旧 uses の移行診断

**費用の漏れを受け入れた。反例の具体的な改行位置には限定を付けた。** 再開時点の本文5.2・6.2は、新語の扱いと旧語の解除を分け、一版だけ旧 uses を診断用キーワードとして残す案へ改めていた。問いと本文8節に残っていた「すぐ通常の識別子へ戻す」という推す案を、この条件へ揃えた。

新語も旧語も KwUses として切り出し、注釈では元の綴りから旧形を拒否する案を見積もりの条件とした。旧形を成功として受理する別名にはせず、名前の位置でも拒否する。原則5との関係、01-01に一版の例外を設ける判断、解除する版の明記、解除後にも同じ診断精度を保つなら文脈判定が必要になることを本文5.2に記した。すぐ識別子へ戻す別案には Δ旧語文脈、新語を文脈で読む案には Δ新語文脈をそれぞれ計上し、不明とした。

RS3は `-> String` の次行に uses を置く例を挙げたが、現行の `newline.rs` では KwUses は `continues_after` に含まれ、`continues_before` には含まれない。従って、通常の関数ヘッダでその位置に改行する例を、現行で有効な旧注釈の代表例としては使わない。uses の直後で改行する旧注釈、括弧内の関数型、短いラムダは別に照合する。変更後の診断や回復の振る舞いは実行しておらず、今回の位置計算でも確認していない。採用後の再現で確かめる事項とした。

## 4. 新語の見積もりと短い移行の試行

**見積もりの指摘を受け入れた。整形の折り返しの想定は反映しない。** 再開時点の本文7節は、with の5〜9時間を新語にもそのまま仮置きする初稿のままだった。本文7節を組み直し、内部の KwUses を保つ新語案を次の三つに分けた。

| 追加作業 | 実装・文書 | 局所検査 | レビュー |
|---|---:|---:|---:|
| 字句の切り替え | 0.5〜1時間 | 0.25〜0.5時間 | 0.25〜0.5時間 |
| 既存の注釈と生成物の移行 | 2.5〜4時間 | 0.5〜1時間 | 0.5〜1時間 |
| 旧 uses の拒否・診断・回復 | 1〜2時間 | 0.25〜0.5時間 | 0.25〜0.5時間 |
| 小計 | 4〜7時間 | 1〜2時間 | 1〜2時間 |

共通の受け入れ照合0.25〜0.5時間を加え、新語の追加を6.25〜11.5時間、基準15〜30時間との合計を21.25〜41.5時間（約21〜42時間）と見込む。実装・文書の合計は13〜25時間である。これは変更箇所と分類した作業からの計画用の見込みであり、試行時間からの換算ではない。with 固有の境界判定を除きつつ、診断位置、生成器、旧語の診断を別に積み上げた。全コーパスの分類と実装による更新はまだ必要である。

残っていた `work/m011/scratch/rs3-keyword-dry-run.py` を `python3 -B` で再実行した。source-migrate の `proposed` で、8入力・15箇所の置換後のバイト列をメモリ上に作る試行である。終了0、内部時間約0.002秒、入力のバイト列が変わっていないことを確認した。既存の診断JSONの14位置について、with では列・バイト位置の差は0、can と effects では列が10位置、バイト位置が14位置変わった。結果は `work/m011/scratch/rs3-keyword-dry-run.json` にある。新しい字句解析・構文解析・診断・整形の実行ではなく、全体への外挿もしていないことを本文7.2に明記した。

「語の長さによって整形器の行の折り返しが変わる」という部分は、現行には当てはまらない。[06-03「整形の考え方」](../../../design/06-tooling/06-03-formatter.md#整形の考え方)は長い行を折り返さないと定め、`cli/tools/formatter/print.rs:25` も改行を保つ。従ってその追加費用は含めない。語の字面を含む整形の期待値と再解析・冪等性、診断位置の照合は含めた。

本文6.3の生成器・表示の分類も確認した。`types/mod.rs:713`、`tools/derive/derive.py:264,559`、`cli/tools/skill/generate.rs:454,506`、`examples/try_actions_inventory.rs:21,215` を対象とし、try-actions の内部キー uses まで一括改名しない条件を保った。effects の欄名、文脈判定、記号固有の追加分は不明とした。with の約22〜44時間は従来の比較枠であり、旧語をすぐ識別子へ戻す案には Δ旧語文脈の留保を加えた。計画・事前レビュー、全体の形式化比較・change・release・最終受け入れ、LLM測定は数値の合計に含めない。

## 5. file-effects.md 4.4との関係

**受け入れた。** 再開時点では本文8節に説明がなかったため、「維持するなら uses、改名するなら can」という条件付きの関係を加えた。取り違えの具体例、ファイル単位の一律追加による上限の読み、Ante の先例は候補を絞る新しい比較材料であり、改名による成功率の改善の証拠ではない。問いの uses の行と時期の選択肢Cに、元資料の推す案であることを記した。

旧 uses の扱いは元資料と異なるため、その相違も本文8節に明記した。元資料の「すぐ識別子へ戻し、旧注釈の診断を保つ」案には文脈判定の留保を加え、本書は一版の例外を選ぶ案を推す。元資料を無条件に追認した説明にはしていない。依頼に従い file-effects.md は変更していない。

## 7. Nimのforbidsとtags

**受け入れた。** 再開時点で本文2.2に forbids、4.1に tags の比較行が加わっていた。Nim公式Manualの Tag tracking と Forbids pragmaを照合し、procの型に禁止一覧を書けることを確認した。tagsは作用の追跡の先例として残し、任意の分類・メタデータに読まれる懸念から上位には推さない。forbidsは禁じる一覧であり、許す一覧の今回の置換にはしない。概念や保証の変更は提案していない。

## 8. 問いの一覧の不足と短縮

**受け入れた。** 再開時点では問いの一覧全体が初稿のままだった。言語の規則の問いを「語と決める時期」「改名する場合の新語と旧語」にまとめ、推す案と別案を並べた。canの短所として `-> String can E`、effectsの依存欄との衝突、旧語の一版の例外を短い表に入れた。時間を増やすかどうかを独立した言語仕様の問いにはしない。
