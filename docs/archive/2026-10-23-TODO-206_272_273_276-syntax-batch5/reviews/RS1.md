## 3. 指摘

重さ: 重＝推す案や結論が成り立たない、中＝問いを出す前に直すか問いに加えるべき、軽＝文書の質や後の計画で直せばよい。

### 3.1 読めば確定するもの

#### M1（中）回復処理の先読みが書式の `:` を拾う

- 箇所: 本文 4.1 の表の後の段落（「`default:`・誤ったラムダの戻り値 `: Type` など、回復処理が読むコロンを正しい構文の用途に数えない」）、4.2 の推す案、11「既存コードとの互換性」。
- 問題: 構文解析器には、字句の並びを括弧の深さ0の `:` まで先読みして、旧式の分岐かどうかを決める処理がある。`parser/foreign.rs` の `when_ahead`（`Newline`・`KwEnd`・`Eof`・`Arrow` で止まる）と、`parser/exprs.rs` の `legacy_clause_after_with`（705行付近）である。どちらも `StrMid`・`StrEnd` で止まらない。`when_ahead` は `is_block_end` の `BlockEnd::Arm`（exprs.rs 682行付近）から、選択肢の本体の文の始まりごとに呼ばれる。`when` は予約語でない。今は補間の中に括弧の外の `:` が現れないので問題にならないが、書式を加えると、例えば次の選択肢の本体の2行目が、正しい式の文なのに旧式の分岐の始まりと判定されうる。

  ```text
  match k with
    case 1 ->
      log(k)
      when + "${n:>3}"
  end match
  ```

  同様に、`default` の後に `Colon` が続くかを見る判定（exprs.rs 684・1368行）、ラムダの見出しの後の `:` を戻り値の型の誤りとして読む `return_arrow`（exprs.rs 1047行）も、書式の `:` と隣り合いうる。また、字句の並びを前もって走査する `lambda_bounds.rs` と `newline.rs` は `Colon` を数えており、書式の中の `<-`（`${x:<-8}` は `<` と `-` でなく `LeftArrow` に分かれる）や `BadSymbol` もそこへ入る。本文 4.2 の「既存の正しい Expr が消費するコロンの範囲を変えない」は書式なしの既存コードについては成り立つが、書式を含む正しい新しいコードを断らないことまでは示していない。
- 修正案: 4.1 に「`:` を先読みする回復処理と字句の前処理」の小表を加え、`when_ahead`・`legacy_clause_after_with`・`default:`・`return_arrow`・`lambda_bounds`・`newline` を挙げる。先読みを `StrMid`・`StrEnd`・`StrStart` の境界で止める（または補間の枠の深さを数える）ことを、案 A の実装条件にする。上の例のような机上の反例は、AGENTS.md「レビューの観点」に従い、実装の段で再現テストにする（段0の字句接続の試行の確認項目に含める）。問い1にも「回復処理の先読みの修正が要る」と一言添える。

#### M2（中）`Decimal` に精度なしの `f` を6桁にする案

- 箇所: 本文 5.1 の表「`.pf`」の行（「`f` のみなら6桁とする案」）、問い3。
- 問題: Python の書式の文書は「With no precision given, uses a precision of 6 digits after the decimal point for float, and uses a precision large enough to show all coefficient digits for Decimal」と書く。本文は Python 系の `.2f` を基本にすると述べながら、Decimal でこの点だけ違う意味を選び、その理由を書いていない。`${1.5m:f}` が `1.500000` になるのは、本文 5.2 の「scale を保つ既存の表記」とも食い違う。
- 修正案: 選択肢を三つにする。A: 三型とも6桁、B: Float と Float32 は6桁、Decimal は scale を保つ（Python と同じ）、C: 精度なしの `f` を誤りにする（本文の問い3の C）。B と C のどちらかを推すのが自然である。C は「書きかけを断る」という空の書式 `${e:}` を断る理由と揃う。

#### M3（中）幅で埋める関数の名前が、今の `String` の名前の並びと合わない

- 箇所: 本文 9.3（「既知の操作名の直後へ単位を続け、通常の補完で同じ操作を探せる」）、問い8。
- 問題: 今の `String` の位置と長さの関数は、すべて単位を先に置く（`byteLength`・`byteSlice`・`byteIndexOf`・`characterCount`・`characterAt`・`characterSlice`。03-06「String」）。01-04「String」の【決定】は「名前に単位を含める」だけで並びを定めていないが、既存の名前は例外なく単位が先である。推す案 A（`padStartDisplayWidth`）は操作が先で、この並びから外れる。「補完で同じ操作を探せる」は、Benitoite に `padStart` という関数がまだない以上、根拠になっていない。また、`displayWidthCJK` を加えると名前が `padStartDisplayWidthCJK` のように長くなる。
- 修正案: 本文 9.3 に既存の名前の並びを事実として書き、候補 B（`displayWidthPadStart` など、単位が先）を既存の並びに合う案として示す。推す案を A のままにするなら、並びから外れる理由を書く。名前は AGENTS.md「文章の規範」の造語の確認の対象でもあるので、どの候補も「既に合意した名前ではない」とする本文の書き方は保つ。

#### M4（中）空白の符号指定は、空白一つで誤りにならずに出力を変える

- 箇所: 本文 5.1（「Sign の位置にある空白一つは符号指定として読み」「`${x: }` も空白の符号指定だけを持つ書式」）、5.1 の表「`+`・`-`・空白」、問い2・3。
- 問題: `${x: .2f}` と `${x:.2f}` は、どちらも誤りにならず、正の数で出力が空白一つ違う。LLM や利用者の手直しで空白が混ざっても検査が気付かない。本文は「余った空白は誤りとして削除の修正案を出す」と書く一方で、コロン直後の空白だけは意味を持たせており、原則1（静的に検出できる誤り）と原則3（直接編集する箇所を壊しにくくする）との関係を論じていない。先例の Rust には空白の符号指定がない（std::fmt の `sign := '+' | '-'`）。
- 修正案: 空白の符号指定を最初の版から外す案（コロン直後の空白は誤りとし、削除の修正案を出す）を選択肢として示し、推す案を見直す。残すなら、`${x: }` が通ることも含めて理由を書き、問いに独立した項目として出す。

## 4. 互換性・複数行と raw・組込み向けの構成（確認の観点3）

- 書式なしの `${e}` との互換性: 本文 11 の表に見落としはない。今の正しい式で、式の後に括弧の外の `:` が残る構成は文法上ないので、書式なしのコードの読み方は変わらない。
- 今の文字列で書式と衝突する字面: `${…}` の外の `:`・`%`・`#` は本文どおり普通の文字である。`${x:…}` は今は構文の誤りなので、受理が増えるだけである。新しいエスケープは要らないという結論は正しい。
- 複数行の文字列と raw 文字列: 本文 2.1 の最後の段落と 11 の扱いで足りる。複数行の文字列で書式の範囲を元のソースから切り出すときに、字下げの除去と元のバイト位置の対応を保つ必要がある点も本文が挙げている。
- 組込み向けの構成: 数と幅の本体を VM・Wasmtime から独立させる、32ビットでも同じ上限にする、Cargo の機能で表だけを減らして同じ関数の意味を変えない、という配慮は AGENTS.md「改造の設計で守ること」と docs/todo の TODO-263 に合っている。主表の大きさ（約6.5〜7.7 KB）からみて、全構成に含める推す案は妥当である。
