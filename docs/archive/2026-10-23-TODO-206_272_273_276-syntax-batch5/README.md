# 書式付きの埋め込み・表示の幅・ファイル単位のエフェクトの宣言の改造（第5弾）

## 目的と範囲

2026-10-23、設計者と相談して、次の4件を一つの改造として設計する。中心は、文字列の埋め込みの中に書式を書き、型検査で確かめる構文である。形式化（Lean）に響くのは中心の項目だけとし、ほかは形式化に響かない、または軽い項目として相乗りさせる（docs/todo の TODO-250「形式化の重さによる組み方」）。

| 分野 | 対象 | 今回扱う範囲 |
|---|---|---|
| 中心 | docs/todo の TODO-273 | 埋め込みの書式の書き方、書式と値の型の組み合わせの検査、整形の関数への脱糖。埋め込みの脱糖は形式化の範囲の内側なので、Lean を先に直す |
| 相乗り | docs/todo の TODO-272 | `String` の表示の幅を数える関数と、表示の幅で揃える関数。TODO-273 の幅の指定と数え方を揃える |
| 相乗り | docs/todo の TODO-206 の残り | ソースファイルのトップレベルに、そのファイルの関数に書き足すエフェクトを宣言する構文 |
| 相乗り | docs/todo の TODO-276 | 誤りの式からの回復で、後の使用に余分な型の誤りが残ること |

## 設計者の決定（2026-10-23）

TODO-206 の残りについて、次のとおり決めた。

- エフェクトを関数の型から外す形は採らない。ソースファイルのトップレベルに、書き足すエフェクトを宣言する構文を加える。
- 宣言はトップレベルだけに書ける。宣言したエフェクトは、型検査の前に、そのファイルのトップレベルの関数の宣言すべての `uses` に一律に書き足す。公開の関数にも書き足す。関数の型にエフェクトが残るので、契約の変化は今までどおり型に現れる。
- `implement` の中の関数（型クラスの実装のメソッド）、ラムダ、引数の関数の型には書き足さない。理由: 実装のメソッドのエフェクトは型クラスの宣言の範囲内でなければならない（01-06）。
- 宣言できるエフェクトは制限しない。主な用途がログとコンソールの出力であることは、同梱の Skill などの文書に書く。
- 書き足したエフェクトが原因の誤りは、診断で宣言の位置を示す。
- 書き方は、他の言語の似た仕組みを調べてから決める。エフェクトを宣言する語を `uses` から `with` に改めた場合の不具合も調べる。

## 設計者の決定（2026-10-23、調べの後）

- エフェクトを宣言する語は `uses` のままとする。ファイル単位の宣言にも `uses` を使う（study/effect-keyword.md、study/file-effects.md の 4 節）。
- 調べの問いは、語の問い以外をすべて推す案で決めた（study/format-and-width-questions.md の 1〜13、study/file-effects-questions.md の Q3〜Q8・Q10・Q12〜Q14）。決定の記録は `decisions.md` に置く。
- 設計者の不在の間の委任: 作業ごとのブランチでの実装、レビューの後の san_benito への取り込み、版の上げ（0.0.11）と release の検査まで進めてよい。push とタグは行わない。問い合わせたい点は推す案で進め、判断と理由を `decisions.md` に記して戻った後に報告する。ただし、Lean の主な定理の前提・結論の変更と公理の追加が必要になったら、その段で止め、Lean に響かない作業を先に進める。

## 進め方

1. 調べと判断の案（`study/`）。設計者が言語の規則を決める。
2. 判断の記録（`decisions.md`）と実装プラン（`plan.md`）。
3. Lean の先行、処理系の実装、段ごとのレビューと取り込み。
4. 全体を終えてから一度だけ版を上げる。
