# ファイル単位のエフェクトと回復について設計者に決めてもらうこと

2026-10-23、S2。根拠と影響は [file-effects.md](file-effects.md) に示す。README の決定（一律の書き足し、公開関数を含む、implement・ラムダ・引数型を除外、効果の種類を制限しない）は問い直さない。RS2への対応で、旧Q2・Q11は末尾の「計画で決める点」へ移し、追加の問いをQ12〜Q14とした。

| 問い | 選択肢 | 推す案 |
|---|---|---|
| Q1 エフェクトを宣言する語を改めるか | uses 維持／全位置を with に変更／effects・using・requires 等へ変更 | uses 維持。ZIO 1.xでは要件を `A with B` とつなぐが、先頭の `with A, B` とは位置と意味が違う。改行・回復・移行の費用に対する改善は未確認 |
| Q3 宣言を書ける位置と回数をどうするか | メタデータ・import の後に一回／import の前に一回／複数を合併 | import 群の後、最初の通常宣言の前に一回。ファイル全体への効力は固定したまま、遅い宣言と重複を診断する |
| Q4 明示の uses とファイルの同じ効果が重なる場合をどうするか | リスト間は合併／E0419で拒否 | リスト間は合併。各リスト内部の明示重複は既存どおり拒否し、Fail は型の同一性も比較する |
| Q5 main・@test・外部関数で既存の制約に反した追加をどう扱うか | 一律追加の後に既存規則で拒否／既存規則自体の変更を別途検討 | 既存規則で拒否し、追加元を示す。main 内の handle だけでは追加済みの宣言を取り消せないことと、ファイルの分割を案内する |
| Q6 trait 内の宣言と生成された関数の境界をどうするか | trait のメソッド宣言は除外・生成されたトップレベル関数は対象／これらへ別の例外を設ける | trait のメソッド宣言は除外し、生成されたトップレベル関数は対象。Property・derive が求める純粋さは追加後の型で検査する |
| Q7 ファイルで宣言する Fail と型・効果変数をどう扱うか | ファイルで解決できる既存の参照と具体型／各関数の同名のパラメータを取り込む | 前者。Fail の種類は禁止せず、合併後のシグネチャから NoFail を計算し、異なる失敗型は既存どおり拒否する |
| Q8 ファイルの IO.All による縮小警告をどうするか | 各関数でW0501を出し共通宣言への自動編集はしない／ファイル全体で集約する新警告 | 前者。宣言位置を示し、一関数の実効果だけで全関数の共通宣言を書き換えない |
| Q9 Q1でwithを選んだ場合、旧usesをどうするか | 非予約の識別子へ戻し旧注釈の位置だけ移行診断／移行期間は両方成功として受理／予約のまま拒否 | 識別子へ戻し旧注釈に移行診断。恒久的な同義構文と将来用の予約を増やさない |
| Q10 TODO-276 の回復をどの範囲で改善するか | 型の部分の由来を保持して依存診断を抑制／単純なbindだけを直す／現行維持 | 由来を保持する。利用側が誤り由来の変数へ流し込む型は根拠にせず、束縛自身の明示契約・既知の構造・正常な関数の結果型による独立した誤りは残す |
| Q12 標準ソースでファイルの宣言を使ってよいか | 使わない規約を検査で守る／許してSkillの署名生成も合併後の契約へ対応する | 使わない規約を推す。標準の個別契約を明記し、参照文書から効果が消えることを防ぐ。利用者の構文への制限は増やさない |
| Q13 mainの合併後の宣言上限を人間へどう示すか | Skillで既存のJSON報告を示すよう案内／ソースの二箇所を読む注意だけ／checkの文章の出力に上限の行を新設 | Skillで成功した報告のmain.effectsをハーネス側から示す。宣言上限と説明し、失敗を空集合や自動許可にしない。通常checkの出力契約は保つ |
| Q14 packageのエフェクトの集計をどう変えるか | 型検査なしの構文の集計へ追加／型検査済みの契約の集計へ切り替える | 構文の集計を保ち、外部公開の直下の関数があるファイルだけ追加分を合併。Logの識別も揃え、trait・入れ子の型へは追加せず、記録とupdateの増減に反映する |

## 計画で決める点

次は言語の規則としての回答を求めず、上の採否に従って計画で具体化する。

| 項目 | 計画へ入れる案 |
|---|---|
| 用語集への反映（旧Q2） | 呼び名は「ファイル単位のエフェクトの宣言」とし、採用後に00-04へ定義と定める章を加える。推論や暗黙の値の補完と区別する |
| 段の分け方（旧Q11） | Aは契約と利用側、Cは原因保持と複合型の各二作業。with採用時だけ先行Bを追加する。四つの利用側の漏れを補った見積もりと、検査・レビュー・受け入れは本文6節に従う |
| 整形と生成・移行の接続 | fmtの新宣言の保持、deriveのimportを宣言前へ置く境界、try-actionsの個別usesと追加元の分離を計画する。inventoryの版・生成記録・manifestの互換性と検証の割り当てを固定する |
| 規約と診断の検査先 | Q12の規約を選ぶなら、標準ソースにファイルの宣言がないことを既存の処理系の検査で守る。診断の採番・由来の保持方式・関連統合ターゲットと、形式化の接続の確認時点も計画で固定する |
