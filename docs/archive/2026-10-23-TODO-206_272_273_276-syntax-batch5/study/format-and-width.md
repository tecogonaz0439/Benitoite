# 埋め込みの書式と表示の幅の調べと判断案

2026-10-23、S1。docs/todo の TODO-273・272 を対象とする調査であり、以下の推奨は設計者の決定ではない。[改造の README](../README.md)の決定を前提とする。共通条件の開始版は `san_benito` の `a0d652c0` である。ソース・設計書・Lean・依存は変更せず、ビルド・テスト・測定・LLM を呼ぶ評価も行っていない。現行の振る舞いについては、文書とソースを読んで確認した範囲を示す。

## 1. 推す案と判断の境界

書式付き補間（string interpolation）は `"${x:+.2f}"` の形を推す。書式指定（format specification）は字面だけに書けるものとし、型検査（type checking）で構文・範囲・組み合わせをすべて検査する。書式なしの `${e}` は、変換・評価順・定数式での使用も含めて保つ。一般の printf 型の可変引数関数や、利用者が書式の処理を定義する機構は加えない。

最初の版は、小数点以下の桁数、符号、ゼロ埋め、最小幅、左・右・中央寄せ、整数の十進・二進・八進・十六進までを候補とする。桁区切り・指数・有効数字・百分率・動的な幅・任意の埋め文字は後へ送る。丸めは `Float`・`Float32`・`Decimal` とも最近接偶数丸めを推す。表示の幅は Unicode の版を固定した一つの関数で数え、補間と `String` の幅・詰め物の関数で共有する。

判断に要る選択肢は節ごとに示し、[短い問いの一覧](format-and-width-questions.md)に集めた。LLM の成功率と非プログラマの読みやすさについて、今回の資料だけから測定済みの順位は付けられない。Python・Rust に似た字面が生成を助けるという評価は、00-01「構文の判断基準」と同じく、未測定の見込みである。

### 2.3 交換形式と比較の対象

[Exchange/Syntax.lean](../../../../formal/Benitoite/Exchange/Syntax.lean)は補間を `interpolation(parts, es, converters)` として JSON へ出し入れする。[Exchange/Convert.lean:286、383](../../../../formal/Benitoite/Exchange/Convert.lean)は変換する型、式数と変換数、変換の頭が直接であることを検査する。Rust 側は [tests/desugar_export/exchange.rs:1277](../../../../crates/benitoite/tests/desugar_export/exchange.rs)で、型検査後の AST からこの表層の形を書き出す。空の head・tail も残し、型が `String` のときだけ `stringExpr` にする。

[scripts/check-formal.sh](../../../../scripts/check-formal.sh)は、既定の Lean ビルドに加え、脱糖・組み込み宣言表・網羅性・全定義の表層検査、独立交換入力、名前付きプログラムごとの六入口と件数を照合する。脱糖の比較は最終の文字列を比較するものではなく、呼ぶ頭、型・エフェクトの引数、定数引数、束縛、順序を含むコアの形を比較する。JSON 変換そのものは主定理の外である（07-04「幅付きの数の交換形式の読み込みと比較」）。

書式付き補間を、Rust が先に整形関数の通常呼び出しへ変えてから表層として書き出す方法は避ける。それでは補間の型と書式の対応、および補間独自の脱糖を比較できない。新しい書式の構成を表層交換に残し、Lean と Rust が別々に引数列を作る必要がある。

## 3. 他言語の書式と、Benitoite へ採る範囲

外部資料の確認日は、以下すべて **2026-10-23** である。リンク先の仕様がそのまま Benitoite の仕様になるわけではない。知名度の欄は、共通する記法からの推論であり、学習データの量や成功率の実測値を表さない。

| 言語と例 | 静的な検査・Decimal・地域設定 | 字面と今回の判断 |
|---|---|---|
| Python: `f"{amount:+.2f}"` | f-string の構造は構文であるが、書式と値の適合は `__format__` で処理する。幅・精度に別の埋め込みも使える。`Decimal` は書式を持ち、丸めのコンテキストを利用する。`n` は地域設定に依存する。[字句](https://docs.python.org/3.14/reference/lexical_analysis.html#f-strings)・[書式](https://docs.python.org/3/library/string.html#format-specification-mini-language)・[Decimal の実装](https://raw.githubusercontent.com/python/cpython/3.14/Lib/_pydecimal.py) | `:` と `.2f` は候補の基本にできる。動的な指定・`!r`・地域依存の `n` まで写さない。説明なしに全書式を静的検査できる言語と紹介しない |
| Rust: `format!("{amount:+.2}")` | リテラルをコンパイラが解析し、書式の trait と引数を検査する。地域設定に依らず、浮動小数の丸めは half-to-even。Decimal 専用の組み込み書式は同資料にはなく、対応する型の trait 実装に委ねる。[std::fmt](https://doc.rust-lang.org/std/fmt/) | 静的な書式検査の最も近い先例である。ただし Rust の固定小数では `f` を付けない。Benitoite の `.2f` は Python 系であり、Rust と同一とは説明しない |
| C#: `$"{amount,10:F2}"` | 幅は定数式で、正は右寄せ・負は左寄せ。`F2` は小数2桁で `decimal` にも使える。書式と型の全適合を通常の補間の構文だけでは保証しない。既定は現在の culture、固定には明示した provider が要る。[補間](https://learn.microsoft.com/en-us/dotnet/csharp/language-reference/tokens/interpolated)・[数の書式](https://learn.microsoft.com/en-us/dotnet/standard/base-types/standard-numeric-format-strings) | 幅と数の書式を分けるのは読めるが、符号付きの幅は寄せの意味を覚える必要がある。Benitoite では `<`・`>` を推す |
| Scala: `f"${amount}%10.2f"` | `f` は書式と引数型をコンパイル時に検査する。書式は Java Formatter を使う。Decimal 相当のどの Scala 型が自動でどこまで受理されるか、地域設定を固定する保証があるかは、この資料では未確認である。[Scala 3 Book](https://docs.scala-lang.org/scala3/book/string-interpolation.html#the-f-interpolator-f-strings) | 型検査の先例として有用。ただし `${e}` の後へ書式を置く方式を既存補間へ追加すると、従来の出力本文 `%…` と衝突する |
| Swift: `"\(amount)"`、拡張の `"\(x, label: y)"` | 補間を `appendInterpolation` の呼び出しへ展開し、通常の引数型として検査する。受理するラベル・型は overload で定める。任意の書式文字列の妥当性まではこの機構だけから導けない。Decimal・地域設定の意味は選ぶ API の仕様に依る。[Swift Book](https://raw.githubusercontent.com/swiftlang/swift-book/main/TSPL.docc/LanguageGuide/StringsAndCharacters.md#string-interpolation)・[SE-0228](https://raw.githubusercontent.com/swiftlang/swift-evolution/main/proposals/0228-fix-expressiblebystringinterpolation.md) | 名前付き指定を読みやすくする先例である。Benitoite に利用者定義の補間や overload を加える必要はない |
| OCaml: `Printf.sprintf "%+.2f" amount` | 書式は `format` の型を持ち、引数の型・数と結び付く。`%ld`・`%Ld` は幅の異なる整数、`%a` は利用者の出力関数を指定する。Decimal 専用指定は列挙されていない。地域設定の不変性はこの API 文書からは未確認である。[Printf](https://ocaml.org/manual/5.4/api/Printf.html) | 型付きの printf は可能であるが、その仕組みを持たない Benitoite へ関数の形だけ持ち込むと静的検査を作り直すことになる |
| Go: `fmt.Sprintf("%+.2f", amount)` | 幅・精度は rune 単位。不適合は出力に `%!…` を含める。printf 解析器による静的点検は別にある。ユーザー定義の Formatter は扱えるが、Decimal 専用の標準 verb は示されていない。地域設定による幅や通貨の API とは区別する。[fmt](https://pkg.go.dev/fmt)・[printf analyzer](https://pkg.go.dev/golang.org/x/tools/go/analysis/passes/printf) | `%` 系を LLM が知ると見込む根拠にはなるが、型の誤りを実行時の文字列へ残す意味は採らない。fmt 全体の地域不変性を今回の資料だけから保証とは記さない |
| Java: `String.format(Locale.ROOT, "%+.2f", amount)` | Formatter は `BigDecimal` を `f`・`e`・`g` などで扱い、不適合を例外にする。地域設定を指定でき、BigDecimal の桁を減らすときの丸めは half up。[Formatter](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/util/Formatter.html) | 十進小数の先例として有用である。例外と既定の地域依存、丸めをそのまま継承しない |
| F#: `$"{amount:F2}"`、`$"%0.2f{amount}"` | `%s{e}`・`%d{e}` のような型付きの補間は型不一致をコンパイルエラーにする。通常の `.NET` 書式の補間とは区別される。[F# interpolated strings](https://learn.microsoft.com/en-us/dotnet/fsharp/language-reference/interpolated-strings) | 型指定を補間の前に置く先例。ただし二系統を新設すると、書き方が増える。今回の推奨では一系統にまとめる |

Python・Rust 系を推す理由は、値と書式の対応が同じ `${…}` の中で閉じ、本文の `%`・コンマを変えずに済むためである。非プログラマが直接直す場所は、主に幅の数字や `.2f` の数字に限れる。一方、`+08.2f` の順序は説明が要る。診断と同梱の Skill に、目的から例を引ける表を置くことを採用条件とする（設計原則1・3・4）。

用語は新設せず、既存の「文字列補間」「書式指定」「精度」「配置」の日本語の用例を [Python 日本語版](https://docs.python.org/ja/3.14/library/string.html#format-specification-mini-language)と [C# 日本語版](https://learn.microsoft.com/ja-jp/dotnet/csharp/language-reference/tokens/interpolated)で確認した。幅の処理には本文で「表示の幅」、不足を空白で補う操作には「埋める」を使う。「書記素クラスタ」は UAX #29 の grapheme cluster を指す原語付きの候補とし、今回、利用者向けの新しい型名にはしない。

## 4. 書式の区切りと現在の `:` の全用途

### 4.1 式の内側で現れる `:`

[01-02 の集約文法](../../../design/01-spec/01-02-syntax.md)の933〜1035行と、`syntax/parser/exprs.rs`・`records.rs`・`types.rs` の `Colon` を照合した。現行の正しい補間式で `:` が入り得る構成は次のとおりである。型の中の `:` は型注釈を介して再帰的に現れ得る。

| 構成 | 字面の例・現れる理由 | 判定の注意 |
|---|---|---|
| 呼び出しの名前付き引数 | `f(x: 1)`。部分適用の `f(x: _)`、パイプ右辺にも同じ Arg がある | `()` の中である |
| レコードの構築と更新 | `R(x: 1)`、`R(..r, x: 1)` | FieldArg の区切りである |
| レコードパターン | `match r with case R(x: n) -> n end match`。`bind`・`shadow` の左辺のパターンにも同じ構成を使う | `()` の中だが、式だけを走査してパターンを忘れない |
| ラムダの引数の型注釈 | `lambda(x: Integer) ...` | 引数の括弧内である |
| 関数型のパラメータ名 | `lambda(f: function(x: Integer) -> Integer) ...`。ラムダの戻り値型にも関数型を書ける | 型の括弧にも `:` がある |
| 文列中の `bind`・`shadow` の型注釈 | `block bind n: Integer <- 1 end block`、`if`・`match`・`lazy`・`with`・`handle` の本体、短いラムダの本体にも同じ Stmt が現れる | 括弧の深さが0でも現れる。補間に不適合な結果型でも、構文としては式の内側である |
| 入れ子の文字・文字列・raw 文字列 | `':'`、`"x:y"`、その文字列の補間式の中の各構成 | 文字列ごとの枠を分ける。入れ子の補間の区切りは外側に影響させない |

文法上のほかの `:` は、トップレベル関数・操作・メソッドの仮引数、const の型、record の欄宣言、trait の上位制約、型パラメータの制約である。これらの宣言は補間式へ直接入らない。`NamedType` を含む型は前表の型注釈から入る。辞書・マップのコロンリテラル、式の一般的な `e: T`、`?:` 条件式、スライスのコロンは現行の文法にない。`default:`・誤ったラムダの戻り値 `: Type` など、回復処理が読むコロンを正しい構文の用途に数えない。

ただし、回復処理と字句の前処理は、正しいコードにも先に適用される。コロンを使う正しい構文の列挙だけでは、書式付きの正しい式が拒否されないことを確認できない。[RS1のM1](../reviews/RS1.md)を受け、次も案Aの接続条件に加える。

| 先読み・前処理 | 読んで確認した現在の処理 | 案Aで確認する条件 |
|---|---|---|
| [foreign.rs:213 `when_ahead`](../../../../crates/benitoite/src/syntax/parser/foreign.rs)、[exprs.rs:681 `block_end`](../../../../crates/benitoite/src/syntax/parser/exprs.rs) | 分岐の本体の名前 `when` に対し、括弧の深さ0の `Colon` で旧式の分岐と判定する。停止条件に `StrStart`・`StrMid`・`StrEnd` がない | 内側の補間のコロンを分岐の区切りとしない。外側の先読みは文字列の枠を読み飛ばし、補間内部からの先読みはその枠を越えない |
| [exprs.rs:695 `legacy_clause_after_with`](../../../../crates/benitoite/src/syntax/parser/exprs.rs) | `with when` の後も同じ深さのコロンを探す。文字列の枠を区別していない | 同じ境界の扱いを適用し、通常の式と旧式の節を分ける |
| [exprs.rs:684、1368 `default:`](../../../../crates/benitoite/src/syntax/parser/exprs.rs) | `default` の直後の `Colon` で判定する | 直接隣り合う字句の判定と、枠を越える先読みを区別する。書式のコロンを普通の式のコロンとして見せない |
| [exprs.rs:1047、foreign.rs:251 `return_arrow`](../../../../crates/benitoite/src/syntax/parser/exprs.rs) | ラムダの引数の直後のコロンを、誤った戻り値型の区切りとして読む | 完全な式の後の書式と、見出し内の既存の誤記の診断を区別する |
| [lambda_bounds.rs:33、85、240](../../../../crates/benitoite/src/syntax/lambda_bounds.rs) | ASTを作る前にラムダの境界を調べる。`StrMid`・`StrEnd` で止まる処理は既にあるが、`Colon`・`LeftArrow`・`BadSymbol` も字句列に入る | 既存の文字列境界を保ち、書式内の記号からラムダの見出し・本体の境界を決めない |
| [newline.rs:193、255](../../../../crates/benitoite/src/syntax/newline.rs) | `Colon`・`LeftArrow` 等から改行の継続を分類する | 書式の範囲を式の演算子列として解釈しない。複数行文字列でも周囲の文の改行を変えない |

例えば次の `when` は普通の値の名前であり、候補の書式を加えた後も旧式の分岐として断らないことを受け入れ条件にする。

```text
match k with
  case 1 ->
    log(k)
    when + "${n:>3}"
end match
```

現行の先読みが文字列の枠を区別していないことはソースで確認したが、この新書式を含む入力の誤判定は未再現である。`default:`・`return_arrow`・改行分類のすべてに同じ反例があるとも断定しない。段0で各経路を小さく確かめ、段3で再現した組み合わせと対照例を検査する。書式なしの互換性と、新書式の正しいコードの受理は別の確認項目とする。

### 4.2 候補と推奨

| 案 | 利点 | 問題・互換性・形式化 |
|---|---|---|
| A: `${e:spec}`。式の解析が終わった位置の `:` を区切りとする | Python・Rust・C# に近い。式内部の文法をそのまま使える | 字句との接続の作業が要る。既存の正しい式の `:` は内部の構文として先に消費する。Lean には解析後の同じ書式を渡せばよい |
| B: 括弧・角括弧の深さ0で最初の `:` を取る | 字句解析だけで見つけやすい | 型注釈を持つ block 等を誤分割するため採らない。ブロックと短い lambda の文法を字句解析器で重ねて実装する方法にも保守の負担がある |
| C: `${e;spec}` | `;` は現在の正しい式に現れず、字句の切り替えが単純 | 新しい区切りを覚える必要がある。既存コードは保て、Lean の負担はAと同等。Aの字句接続が見積もりを超える場合の代案である |
| D: `${e!spec}`、`${e%spec}` | いずれも現在の正しい式の演算子ではない | `!` は Python の変換指定との混同、`%` は printf の型記号との二重の役割がある。Aに対する読みやすさの利点を確認できていない |
| E: `${e}%.2f`、`%.2f${e}` | Scala・F# に先例がある | 現在は本文として出る字面の意味を変える。互換性を守るために別の文字列種別を足すと、同じ役割の構文が増える |
| F: `${e: fixed(places: 2)}` のような名前付き指定 | 数字と意味を対応付けやすい | 記述が長く、新しい小言語になる。一般式や名前解決を許さず静的な指定に限れば形式化の種類は同じだが、既存書式の知識を使いにくい |

推す案はAである。規範は「一つの完全な Expr を通常どおり解析し、その直後に残る `:` があれば、対応する `}` の直前までを書式とする」とする。単なる『式の最上位』より、この手順を明記する。短いラムダの本体の式に続く `:` は、ラムダ全体を読み終えた後に書式として扱う。書式を内側の値へ適用したければ、その位置に別の補間を書く。構文解析が失敗した式を、書式の開始位置を後ろへずらして救済しない。

実装では、`parser/interp.rs` が式の後に `Colon` を見つけ、元のソースのその位置から閉じまでを専用の書式解析へ渡す案を先に検討する。空白は普通の字句で失われるため、トークンをつなぎ直して書式を復元してはならない。`#`・`^` の `BadSymbol` は書式の範囲でだけ専用解析が扱い、`8.2f` などの通常の数リテラルとしての診断は、その範囲が確定するまで保留する。字句解析と構文解析の間で、範囲付きの保留診断を受け渡す必要がある。式側の誤った数や、UTF-8・双方向制御文字・物理改行の誤りまで捨ててはならない。

この保留方式が現在のエラー回復や字句の個数制限と整合しない場合は、補間内部の字句を必要に応じて読む方式との比較を実装プランで行う。全候補の `:` の前を何度も解析する試行は、長い入力で作業が二乗になるため採らない。未知の書式文字を一般の式で有効にする必要もない。ここはRust側の不確実性であり、Lean の証明が通ることだけでは方式を確定できない。

案Aの方式は、補間の枠を区別する先読みと、書式の範囲を構文解析へ渡す順序を合わせて決める。単に三種類の文字列字句で一律に打ち切ると、文字列の後に本物の旧式の区切りがある診断まで失う可能性があるため、枠の読み飛ばしと枠の外への停止を使い分ける。現行の最長一致では `${x:<-8}` の `<-` も `LeftArrow` になる。修正案では `-` を許さないが、不正な指定として回復するときにも普通の束縛の矢印として扱わず、書式の元の位置へ診断を出す必要がある。

この選択は、原則1・3・4に沿う。形式化には区切りの字句自体を入れず、解析後の書式だけを入れる。互換性の条件は、既存の正しい Expr が消費するコロンの範囲を変えないことである。

## 5. 最初の版の書式の案

### 5.1 指定の形と意味

以下は採用候補の文法である。`[ ]` は省略可能、各数字は ASCII とする。書式の中に一般の式、変数、追加の `${…}`、エスケープは書けない。

```text
FormatSpec = [ Align ] [ Sign ] [ "#" ] [ "0" ] [ Width ] [ Precision ] [ Kind ] .
Align      = "<" | ">" | "^" .
Sign       = "+" .
Width      = NonZeroDigit { Digit } .
Precision  = "." Digit { Digit } .
Kind       = "d" | "b" | "o" | "x" | "X" | "f" | "s" | "c" .
```

空の書式 `${e:}` は誤りとする案を推す。`${e}` に統一でき、書きかけの指定を検出できるためである。書式の中の空白はすべて誤りとし、読み飛ばさない。`${x: .2f}`・`${x: }`・`${x:8 }` は該当する空白を示し、意図に合う場合に削除できる修正案を出す。式の末尾から区切りのコロンまでの、通常の式の空白はこの制限の外である。

符号の選択肢は、A: `+` だけを許す、B: 省略と同義の `-` も許す、C: Bに正の値の先頭を空白にする指定も加える、である。Aを推す。Pythonには空白の符号指定があるが、[Rustの書式文法](https://doc.rust-lang.org/std/fmt/#syntax)にはない（2026-10-23再確認）。空白の符号指定があると、`${x:.2f}` に空白を一つ入れた `${x: .2f}` も受理され、正の値の表記が変わる。入力だけから意図した挿入かを区別できないので、原則1を根拠に意図の不一致を検出できるとは主張しない。原則3に従って最初からこの指定を外し、空白の混入を構文の誤りとして検出できる規則を選ぶ。`-` には省略と異なる型制約もないため、原則5に従い省略へ直す診断を出す。いずれも新書式への制限であり、書式なしの既存コードは変えない。Leanの妥当性の選択肢も減る。

| 指定 | 推す意味 | 組み合わせの制限 |
|---|---|---|
| 指定なしの種類 | 型ごとの既存の表記を保ち、指定された符号と幅だけ適用する | `.p` を書くときは `f` を必須にする |
| `d` | 整数の十進表記 | 整数だけ。精度を付けない |
| `b`・`o`・`x`・`X` | 二進・八進・小文字／大文字の十六進 | 整数だけ。負の値は負号＋絶対値の数字列とする。2の補数の全ビット表記にはしない |
| `#` | `0b`・`0o`・`0x`・`0X` の接頭辞を付ける | 上記の四種類だけ。値0にも接頭辞を付ける |
| `.pf` | 小数点以下を正確に p 桁にする。p=0 なら小数点を付けない | `Float`・`Float32`・`Decimal` だけ。精度なしの `f` は下記の型別の既定を使う。`.p` だけは拒否する |
| `+` | 正と零にも `+` を付け、負には `-` を付ける。省略時は負号だけ | 数だけ。明示した `-` と空白の符号指定は拒否する |
| 幅 W | 整形済みの結果の最小の表示の幅 | 長ければ切らない。Wは1〜65535を暫定の上限とする |
| `<`・`>`・`^` | 左・右・中央寄せ。不足は U+0020 で埋める | 幅を必須とする。中央で余りが奇数なら右側の空白を一つ多くする |
| `0` | 符号・基数の接頭辞の後、数字の前にゼロを補う | 数だけ。幅を必須とし、明示した Align とは併用しない |
| `s`・`c` | `String` をそのまま／`Character` を一文字の文字列へ変換する | 符号・精度・`#`・`0` は不可。幅・寄せだけを付けられる |

精度なしの `f` には、A: 三型とも6桁、B: FloatとFloat32は6桁、Decimalは現在のscaleを保つ、C: 精度を必須として拒否、の選択肢がある。Bを推す。[Pythonの書式指定](https://docs.python.org/3/library/string.html#format-specification-mini-language)は、floatの既定を6桁、Decimalの既定を係数の全桁を表示する精度とする（2026-10-23再確認）。BenitoiteのDecimalは指数の別表現を持たず、scaleを保つ既存の固定小数表記に対応させられる。候補の `${1.5m:f}` は `1.5`、`${1.50m:f}` は `1.50`、`${1.5:f}` は `1.500000` となる。

Aも明示した `f` だけに別の既定を定めれば、書式なしのscale保存と論理的に矛盾するわけではない。ただし先例と違う精度を暗黙に選ぶ理由がなく、scaleを失う。Cは書きかけの検出を優先できるが、既存言語で有効な指定を常に直す必要がある。Bは原則3・4に沿い、既存の書式なしの出力を保つ。型が具体化された後に省略した精度を決め、実行時の生の書式の再解析は要らない。Leanでは省略の表現と型別の解釈を定義するが、型の等号やエフェクトは変えない。

同じ結果になる `d`・`s`・`c` については、A: 型を限定する指定として受理、B: 省略への修正案を出して拒否、を比べ、Aを推す。例えば `${n:d}` はnを整数に限定し、nをStringへ変えると型検査で断るが、種類を省略するとStringも受理する。`s` と `c` もそれぞれStringとCharacterに限定する。このため、`-` と異なり受理条件は省略と同じではなく、原則1・2の検査を追加する理由がある。別の書き方を常に通すためだけには受理しない。型ごとの表を保つ範囲の追加であり、既存コードを壊さず、形式化ではそれぞれの型集合を検査する。

寄せの既定は数が右、それ以外が左とする。精度は各三型とも0〜28を推す。28は `Decimal` と揃えるための言語上の上限であり、Float の表現能力の限界ではない。Float だけ大きな精度を許す案も可能だが、最初の版で型により許す数字の範囲が変わることを避ける。幅65535は、極端な出力を静的に断り、32ビットでも同じ範囲にするための候補値であり、測定から求めた値ではない。両上限は設計者への問いに含める。

### 5.2 型ごとの受理表

「数」は暗黙の型変換を意味しない。型の別名は同じ行として扱う。表の「○」にも前節の組み合わせの条件を課す。

| 値の型 | 書式なし | 幅・寄せ | 符号・ゼロ埋め | `d` | `b/o/x/X`・`#` | `.pf` | `s/c` |
|---|---|---|---|---|---|---|---|
| `Integer8`・`Integer16`・`Integer32`・`Integer`（`Integer64`） | 各 `toString` | ○ | ○ | ○ | ○ | 不可 | 不可 |
| `Byte`（`UnsignedInteger8`）・`UnsignedInteger16`・`UnsignedInteger32`・`UnsignedInteger64`（`UnsignedInteger`） | 各 `toString` | ○ | ○。負号は生成しない | ○ | ○ | 不可 | 不可 |
| `Float`（`Float64`）・`Float32` | 各型の最短表記 | ○ | ○ | 不可 | 不可 | ○ | 不可 |
| `Decimal` | scale を保つ既存の表記 | ○ | ○ | 不可 | 不可 | ○ | 不可 |
| `String` | 元の値 | ○ | 不可 | 不可 | 不可 | 不可 | `s` のみ |
| `Character` | `Character.toString` | ○ | 不可 | 不可 | 不可 | 不可 | `c` のみ |
| `Boolean` | `true` / `false` | ○ | 不可 | 不可 | 不可 | 不可 | 不可 |
| `Unit`・コレクション・利用者の型・通常の型パラメータ | 不可 | 不可 | 不可 | 不可 | 不可 | 不可 | 不可 |

Boolean には `b` を割り当てない。`b` は整数の二進の意味に固定する。Character の整数コードへの変換、Boolean の0/1化、Integer から Float への暗黙の変換は行わない。利用者の型は明示して String に変換してから幅を指定できる。この線引きは既存の閉じた型集合を保ち、原則1・4・5に従う。形式化では有限の種類と基本型の表の追加で表せる。

負の整数の基数表記には、負号と絶対値の数字列、または型の幅に対応する2の補数のビット列、という選択肢がある。前者を推す。同じ数をInteger8からIntegerへ変えても表記を保て、幅の違いと負号の解釈を混ぜずに済むためである。絶対値を元の符号付き型へ格納せず、最小値も符号なしの大きさとして扱う。書式なしの十進表記は変えず、Leanでは基本型ごとの受理条件と引数の型だけを変更する。

例は次の出力を仕様候補とする。現行処理系で実行した結果ではない。

| 候補の式 | 出力の候補 |
|---|---|
| `"${1.5m:+08.2f}"` | `+0001.50` |
| `"${-42:#08x}"` | `-0x0002a` |
| `"${2.5m:.0f}"` | `2` |
| `"${3.5m:.0f}"` | `4` |
| `"${"猫":>4}"` | 空白二つと `猫` |

|---|---|---|
| 桁区切り | 今回追加／後へ送る。後者を推す | `,`・`_`、十進と各進数の区切り、ゼロ埋めとの順序を別に定める必要がある。地域設定には依らせない。後日の追加は未使用指定の解禁で済み、同じ有限表を拡張できる |

| [01-04「Decimal」](../../../design/01-spec/01-04-types-basic.md)、326・341〜352行、[base/decimal.rs:201、395](../../../../crates/benitoite/src/base/decimal.rs) | 演算で精度を減らすときは最近接偶数丸め。`Decimal.round` は5種類の `RoundingMode` を明示する。places は0〜28で、ゼロを補う場合も係数の値域を検査する | 固定の既定丸めを新設しても既存関数を変える必要はない。整形のために有界な Decimal を作り直す方法は避ける |

選択肢は、A: 三型とも最近接偶数丸め、B: 三型とも四捨五入（中間は0から遠い側）、C: 型ごとに分ける、D: 書式に丸め方も書く、である。Aを推す。Rust の数の整形と現在の Decimal の演算に先例があり、型を変えたとき中間の丸め方まで変わるCを避けられる。Bは `Float.round` に揃うが、Decimal の演算と違い、Rust の整形の利用にも追加処理が要る。Dは将来可能であるが、今回の書式の選択肢を増やす。

例えば候補の `${2.5:.0f}` は `2`、`${-2.5:.0f}` は `-2` である。現在の `Float.round(2.5)` は `3.0` になる。`Decimal.round(..., mode: RoundingMode.HalfToEven)` との数としての対応は、丸めた値が Decimal の値域に収まる場合に限る。`2.675` のような二進で正確に表せない入力は、入力の binary64/binary32 の正確な値を丸める。十進で表された数学的な `2.675` を丸める操作とは区別する。

Decimal の整形では、係数と scale から数字列を作り、その数字列上で必要な桁を減らすかゼロを補う。最大値 `(2^96−1)` に `.2f` を付けるときも、値を `Decimal.round(x, 2, …)` で作り直さない。現行の `round` は係数が100倍になると値域を超えるが、表示文字列には `.00` を追加できる。この問題は仕様と `base/decimal.rs` の読解で確定する実装上の制約であり、今回、再現実行はしていない。

### 6.2 特殊値と符号の候補

Float の `NaN`・`Infinity`・`-Infinity` は現在の綴りを保ち、精度で変えない。`+` は正の Infinity にも付け、NaN には付けない。負の零と負から丸めた零は負号を保つ。非有限値の `0` 指定は、数字列がないため空白の右寄せとして扱う案を推す。値によって型検査の可否を変えず、いずれも String を返せる。

Decimal は現行の値が負の零を持たないので、丸めて零となった結果も負号を付けない案を推す。`+` 指定なら `+0.00` となる。これは Float と表記が違うが、既存の零の意味の違いを保つ選択である。浮動小数の負の零を消す新しいフラグは今回設けない。

全書式は ASCII 数字、小数点 `.`、符号 `+`・`-`、上記の基数接頭辞を使う。OS の地域設定、環境変数、端末への問い合わせは行わない。通貨記号を自動で付けず、利用者が本文に書く。原則2・3に従って、同じスクリプト・値・処理系の版で同じ表記を返す。文字の表示幅だけは Unicode の版にも依るため、節9の版の固定を適用する。

## 7. 型検査・脱糖・実行時の案

### 7.1 型検査の制約と診断

書式の解析結果には、種類・寄せ・符号・接頭辞・ゼロ埋め・幅・精度と、各部分の元の span を保持する。構文として読めること、数字の上限、フラグの組み合わせを先に検査し、型推論後に基本型との受理表を照合する。`f` の集合は `{Float, Float32, Decimal}`、整数の集合は八つの整数型、幅だけは既存の補間集合である。型変数はこれらの有限の候補を持ち、既存と同様に本体の検査が終わる時点で具体化されなければならない。

| 誤りの例 | 推す診断の内容 |
|---|---|
| `${x:.f}`、`${x:8.2q}`、`${x:>}` | 不足した桁／未知の種類／必要な幅を示す。書式の該当する1部分を primary とする |
| `${x:.2}` | 精度の後に種類 `f` が要ることを示し、`.2f` への修正案を出す。値の型との適合は別に検査する |
| `${x: .2f}`、`${x: }`、`${x:8 }` | 空白を許さない規則と該当位置を示し、削除の候補を出す。空白を黙って読み飛ばさない |
| `${x:-8}` | `-` は省略と同義で受理しないと示し、`${x:8}` への修正案を出す |
| `${s:.2f}` | `f` が許す三型と実際の String を示す。値を数へ勝手に parse する修正案は出さない |
| `${n:.2f}` で n が Integer | 整数には `d`、小数点付きの計算なら明示した変換、という別の意図の候補を示す。自動修正はしない |
| `${x:>08.2f}`、`${n:#d}` | 個別の字句の正しさでなく、互換でない指定の組み合わせを示す |
| `${x:.29f}`、極端に長い幅の数字 | 許す上限と元の数字を示す。数字を機械の整数へ変換してから判定しない |
| `${e:}`、`${e:8 }` | 空の指定／末尾の空白を示し、削除の候補を出す |

診断コードは実装プランで診断表との重複を確認して割り当てる。ここでは番号を予約しない。書式なしの E0422 と、書式の構文の誤り、値の型との不適合を区別する。式に既に根の誤りがある場合は、それを原因とする不適合を重ねない。これは相乗りする docs/todo の TODO-276 の回復方針との接続箇所である。

### 7.2 脱糖の形

`"a${e1:+08.2f}b${e2}c"` は、現行と同じく先に e1、e2 を左から各一度評価する。その後、e1 を純粋な型別の整形関数、e2 を既存の変換で文字列にして、断片と左から連結する。書式ごとに元の式を複数回評価したり、式ごとの変換を全式の評価の前へ移したりしない。これにより、書式なしの評価順を保てる。

整形関数には可変の書式文字列を渡さず、検査済みの列挙値を整数の定数へ換算した値と、Boolean、幅、精度を渡す案を推す。例えば内部の `%Format.Decimal` は `value: Decimal` と、固定個数の `kind: Integer, align: Integer, sign: Integer, alternate: Boolean, zero: Boolean, width: Integer, precision: Integer` を受け、純粋な String を返す。名前と列挙値の符号化は内部案であり、公開APIではない。省略には固定した値（例えば精度の−1）を一つだけ割り当て、書式解析結果からの換算を明記する。

候補は、A: このような基本型の固定引数、B: 公開の FormatSpec レコード、C: 実行時にも文字列を再解析、である。Aを推す。新しい言語型・辞書・依存した関数型を要さず、コア計算の通常の組み込み呼び出しで表せる。Bは公開APIの設計とその組み合わせ検査まで広がり、Cは静的に解析したこととの重複と不一致を生む。入力型ごとの表の宣言は、String を含む14基本型を上限とし、種類ごとに無制限に組み込みを増やさない。Boolean や Character では不使用の項目も、検査済みの既定値だけを渡す。

数の整形と幅計算の本体は、VM の Value、Host、Wasmtime に依存しない Rust の関数に置く。builtins は値の取り出し・予算・結果の確保を担当する。定数評価器は同じ数の整形本体と幅計算を呼ぶ。VM と参照評価器は同じ組み込みの契約で実行できる。これにより、実行時と定数評価で丸めや幅が異なることを避け、組込み向けの境界も保てる。

### 7.3 「書式の誤りを実行時に残さない」の条件

この保証には、次の三つを実装の受け入れ条件にする必要がある。

1. 字面にしか書けない全書式を、種類・上限・組み合わせ・値の型まで検査し、不正な組み合わせをコアへ渡さない。
2. 内部の整形関数は可変の書式を再解析しない。検査済みの指定と各型のすべての値について、特殊値・整数最小値・Decimal 最大値も含めて出力を定義する。
3. 定数評価と実行時で同じ規則を使い、サイズ計算・整数変換・確保前の予算検査を行う。巨大な数字列をホストの整数へ変換してからエラーにしない。

検査済みの書式があっても、式の評価の失敗、燃料・メモリの上限、出力のIOの失敗は起き得る。`String` を返す型は、これらまで成功すると保証する型ではない。整形の本体に、`Decimal.round` の値域超過や整数最小値の符号反転のような、避けられる値依存の失敗を残さないことが今回の条件である。署名の正しさと、丸め・桁列の正しさは別に確認する。

### 8.2 0.0.8 の三種類との照合

docs/todo の TODO-250 は、難しい変更を「エフェクトに値や型を持たせる」「エフェクトを外す」「型を計算してから比べる」の三種類に分けている。0.0.8 の [R6・R7](../../2026-10-17-TODO-063_087_189_191_249_255-check-policy-and-syntax-batch2/decisions.md#r6-型を含む効果の表現)には、効果への型の追加と捕捉の条件が共有の表現に影響した経緯がある。

| 難しさ | 今回の推奨案との対応 |
|---|---|
| エフェクトに値や型を持たせる | 当たらない。幅・精度は表層の通常データとコアの定数引数であり、Eff や Ty の構成に加えない |
| エフェクトを外す | 当たらない。整形は空エフェクト、式のエフェクトは既存どおり和として残す。補間が許可や失敗のエフェクトを捕捉しない |
| 型を計算してから比べる | 当たらない。有限の種類から既存の基本型と固定シグネチャを選ぶだけである。型レベルの幅、書式から生成するタプル型、型の簡約による等号は導入しない |

ここで書式の妥当性を計算することや、`converterTypes` が通常の型のリストを返すことは、型の等号に新しい計算規則を入れることとは異なる。ただし、利用者定義の Formatter、可変引数の printf、書式から型が変わる API まで広げると、この見積もりは使えない。

### 8.3 交換と検査で落とさない項目

新しい独立入力には、全受理型、種類ごとの不適合、上限とその外側、空書式、許さないフラグ、String の書式あり／なし、空の断片、連続する補間、式数と変換数の不一致、非純粋・間接の変換頭を含める。期待するコアには指定の定数引数と契約名を残す。型別の組み込みへの対応を、同じ Rust の選択関数から生成した期待値だけで確かめない。

接続を閉じる段では `check-formal.sh` 全体を一度通し、最終の関係状態でも実行または07-03の条件を満たして引用する。新構成が対象外へ落ちた件数も確認する。Unicode の幅と丸めの出力は、主定理やコア形の比較だけからは分からないので、別の小さい独立期待値で確認する。

## 9. 表示の幅の仕様候補

### 9.1 East Asian Width、絵文字、書記素の区別

[UAX #11 rev.44（Unicode 17.0）](https://www.unicode.org/reports/tr11/tr11-44.html)は文字を F・W・H・Na・A・N に分類するが、端末の全状況にそのまま使える幅の算法ではないと明記する。字形の実幅は書体や配置にも依る。結合文字の幅0や絵文字の並びの幅を、East Asian Width 一属性だけで決めたことにはできない。

[UAX #29 rev.47](https://www.unicode.org/reports/tr29/tr29-47.html)の書記素クラスタ（grapheme cluster）は、人が一文字と見るまとまりの境界を扱う。[UTS #51 rev.29](https://www.unicode.org/reports/tr51/tr51-29.html)は絵文字の表示指定・修飾子・ZWJなどの並びを定める。どちらも「すべての書記素クラスタの表示幅は1または2」という規則ではない。幅を数えるために、まず汎用の書記素分割APIを公開する必要はない。

| 先例 | 一次資料で確認したこと | 今回への判断 |
|---|---|---|
| Rust `unicode-width` 0.2.2 | `str` 全体の幅を扱い、文字単位の足し算と違う絵文字・合字の規則がある。`width_cjk` もある。[API と規則](https://docs.rs/unicode-width/0.2.2/unicode_width/) | 本体を使う第一候補。`char` の幅を足す実装に置き換えない |
| Python `unicodedata.east_asian_width` | 一つの文字の EAW 属性を文字列で返す。[Python 3.14](https://docs.python.org/3.14/library/unicodedata.html#unicodedata.east_asian_width) | 文字列全体の端末幅APIではない。これだけで書く実装は不十分 |
| Python `wcwidth` | `wcwidth` と `wcswidth` は制御文字で−1を返す。文字列用の処理、配置、幅の曖昧な文字の指定、端末固有の補正を別に提供する。[公式文書](https://wcwidth.readthedocs.io/en/latest/intro.html) | 失敗を表す設計と端末補正の先例。自動検出は純粋な String の関数に入れない |

推す基本は、`unicode-width` 0.2.2 の文字列の算法を版付きで採り、F・W を原則2、H・Na・N を原則1、Aを既定1として、同クレートの幅0と列の例外を優先することである。例えば結合アクセントを含む `e\u{301}` は1、`猫` は2、完全な絵文字 ZWJ の列は2とする候補である。「原則」と書くのは、同クレートに幅3などの例外もあるためであり、単純な0/1/2の表として写してはならない。

候補の受け入れ例には、ASCII、日本語、半角カナ、結合文字、ZWJ 家族絵文字、肌色修飾子、国旗の地域指示記号の対、キーキャップ、VS15/VS16、幅が曖昧な記号、単独の結合文字・ZWJを含める。例の値は採用する版の規則から固定し、端末で見た一例を全端末の保証にしない。書記素を切断・省略する操作は今回の範囲外である。

### 9.2 曖昧な文字と制御文字

幅が曖昧な文字には、A: 常に1、B: 常に2、C: 既定1で明示的に2を選べる、D: 環境から選ぶ、の選択肢がある。Cを推す。`String.displayWidth(s)` は1を使い、`String.displayWidthCJK(s)` は `unicode-width` の `width_cjk` に従う。後者は文字列の例外も含む別モードであり、「属性Aを機械的に全部2に置く」とだけ仕様化しない。`CJK` の綴りはクレートの既存の呼び名から採るAPI名の候補である。

別案は `displayWidth(s, wideAmbiguous: Boolean)` または列挙型の引数一つに統一する形である。通常の関数には省略引数がないため、`displayWidth(s)` を残すと別関数も必要となる。最初は既定とCJKを名前で区別し、Booleanの位置引数や新しい公開型を増やさない案を推す。この二つの選択は型やエフェクトを変えず、形式化の新しい規則も要さない。既存APIには追加だけである。

制御文字の扱いは、採用前に決める必要がある。`unicode-width` の素の文字列幅には CRLF の幅1などがあるため、端末操作の幅0を当然と見なしてはいけない。選択肢は次のとおりである。

| 案 | 意味と費用 |
|---|---|
| A: クレートをそのまま公開 | 実装は最小だが、改行・タブ・ESCを画面上の移動量として読めない。クレートの制御文字の規則も利用者へ説明する必要がある |
| B: C0・DEL・C1と行／段落区切りを幅0の境界として扱う | 全入力で Integer を返せる。改行やタブの端末操作を計算せず、境界の前後で文字列の幅の状態をリセットする。ANSI列全体を除く処理はしない |
| C: 制御文字を含むと `Option.None` | 不明な幅を数値にしない。反面、String の幅付き補間にも値依存の失敗か別の規則が要る |
| D: 改行・タブ・ANSI列を解釈 | 開始列、タブ幅、端末の機能などの引数が増える。今回の純粋な一行の列幅の用途を超える |

Bを推す。対象は U+0000〜001F、007F〜009F、2028、2029と明記し、各境界を除いた最大の連続部分をクレートへ渡して、その幅を足す。改行を含む値について、返り値を行の最大幅やカーソル位置とは説明しない。例えば `a\nb` の候補値は2、タブだけは0、ESCに続く `[31m` は普通の印字部分として数える。端末に列を揃える用途は、制御文字のない一行を前提とする。これは新しく選ぶ Benitoite の意味であり、UAX #11 やクレートがこのBを定めているという主張ではない。

この案は、String の任意の値を静的検査だけでは一行に限定できない状況で、幅付き補間を全値に定義するための選択である。Cを選ぶ場合は、String の幅付き補間の値依存の扱いも同時に決める必要がある。異なる行や制御列を正しく配置する機能は後の独立した項目とする。

### 9.3 公開する関数と引数

[01-04「String」](../../../design/01-spec/01-04-types-basic.md#string)は、位置・長さを扱う名前に単位を含め、`byte` と `character` を省略しないと定める。語順自体はこの決定に含まれないが、[標準のStringの宣言](../../../../crates/benitoite/src/prelude/stdlib/String.bnt)は `byteLength`・`byteSlice`・`byteIndexOf`・`characterCount`・`characterAt`・`characterSlice` と、いずれも単位を先に置く。今回は第三の単位 `displayWidth` も先に置く案を推す。裸の `padStart`・`padEnd` は、文字数か表示の幅かが分からないため採らない。

| 候補API | 型と意味 |
|---|---|
| `String.displayWidth(s)` | `function(s: String) -> Integer`。節9の既定の列幅 |
| `String.displayWidthCJK(s)` | 同じ型。CJKモードの列幅 |
| `String.displayWidthPadStart(s: s, width: w)` | `function(s: String, width: Integer) -> String`。wから既定の計算幅を引いた正の個数の空白を先頭に補う |
| `String.displayWidthPadEnd(s: s, width: w)` | 同じ型と個数の規則で、末尾に空白を補う |
| `String.displayWidthPadStartCJK(s: s, width: w)` | 同じ型。CJKモードで先頭へ補う |
| `String.displayWidthPadEndCJK(s: s, width: w)` | 同じ型。CJKモードで末尾へ補う |

名前の先例は JavaScript の [StringPadding と padStart/padEnd](https://tc39.es/ecma262/multipage/text-processing.html#sec-string.prototype.padstart)である。英語名はその操作名に単位を付けた候補であり、既に Benitoite で合意した名前ではない。日本語の「先頭から埋める」の用例は [MDN日本語版](https://developer.mozilla.org/ja/docs/Web/JavaScript/Reference/Global_Objects/String/padStart)で確認した。ECMAScript と同じ長さの単位や任意の fillString を採る意味ではない。

別候補の `padStartDisplayWidth`・`padEndDisplayWidth` はJavaScriptの操作名から探しやすく、`padStartByDisplayWidth`・`padEndByDisplayWidth` は関係を明記できる。ただしBenitoiteにはまだ `padStart` という関数がなく、操作が先の並びを推す根拠にはしない。上表は既存の単位が先の並びを保ち、`displayWidth` の共通接頭辞から幅の操作を探せる案である（原則3・4）。CJK版も含めて名前は長くなるが、単位や操作を略さない。どれも既存の他言語の名前そのものではなく、単位の規約と既知の操作名を組み合わせた未合意の候補である。新しい型・エフェクトの規則を要さず、形式化への影響は通常の関数宣言の照合に限られる。

wが0以下、または既に幅がw以上なら元の文字列を返す。内容を切らず、埋め文字は空白一つに固定する。幅0の文字列を繰り返す停止性の問題や、幅2の埋め文字と奇数の余りを今回持ち込まない。動的なwは文字列の論理上限・実行時の予算を検査してから確保する。`String.repeat` と同じく巨大な引数まで成功する保証はしない。`usize` へは検査した変換を使い、32ビットでwの意味を変えない。

一般の連結と、U+0020の空白を前後に加える操作は区別できる。[クレート0.2.2の規則](https://docs.rs/unicode-width/0.2.2/unicode_width/#rules-for-determining-width)が列挙する幅の非加法的な列に、U+0020は加わらない。さらに[生成済みソースの `width_in_str`・`width_in_str_cjk`・`str_width`・`str_width_cjk`](https://raw.githubusercontent.com/unicode-rs/unicode-width/v0.2.2/src/tables.rs)を2026-10-23に読み、両モードとも右から集計し、U+0020で幅1を足して状態をDEFAULTへ戻すことを確認した。空白は絵文字の表示列を始める文字でもない。したがって前後へn個・m個の空白を加えた幅は `n + W(s) + m` になると、状態遷移から判断できる。これは実行やLeanでの証明の結果ではない。

節9.2の制御文字の境界Bは各連続部分を別に数える。空白はその境界に含めないため、同じ関係を保つ。この読解を根拠に、確保に成功した結果の幅を `max(W(s), w)` とする契約を推す。元の幅がw以下ならちょうどw、wを超えるなら内容と幅を保ち、負のwでも元の値を返す。計画には、両モードの状態遷移の再確認と、小さい独立の期待値による先頭の結合文字・末尾のVS/ZWJ・合字・制御文字の境界・空文字・幅超過の例を割り当てる。これによって一般の `W(a + b)` の加法性まで主張するわけではない。

### 9.4 補間の幅との統一

選択肢は、A: スカラー値の個数、B: 表示の幅、C: 両方を記号で選択、である。Bを推す。Aでは日本語の表が揃わず TODO-272 の目的と食い違う。Cは精度や幅の指定に単位を選ぶ記号が増える。文字数で扱う処理には既存の `characterCount` 等を使う。

補間の幅と既定の String の関数は、同じ幅本体・同じ Unicode 版・同じ制御文字の境界・同じ空白を使う。CJKが必要なときは上記の明示した padding 関数で先に整形し、補間には追加の幅を指定せず埋め込む。今回の書式にはCJKの切替記号を追加しない。これにより、既定の幅は常に同じで、地域・端末で変わらない。

幅を数える対象は各 `${…}` の整形済みの文字列一つである。隣の本文や別の補間と結合して新しい絵文字列・合字になる場合の幅までは揃えない。`displayWidth(a + b)` と `displayWidth(a) + displayWidth(b)` が常に等しいという規則も作らない。隣接する絵文字列を一つの欄として揃えたい場合は、一つのStringにしてから幅を指定する。

## 10. 幅の表、依存、Unicode の版、組込み向けの構成

| 実装案 | 利点 | 費用と判断 |
|---|---|---|
| A: `unicode-width` を直接の依存にする | 文字列の列の扱いと表の更新を再利用できる。0.2.2は `no_std`、通常構成の必須依存なし、MIT OR Apache-2.0。[Cargo.toml](https://raw.githubusercontent.com/unicode-rs/unicode-width/v0.2.2/Cargo.toml) | 第一候補。文字列の算法を基盤OSSとして扱い、言語の中核の自作の方針と区別する |
| B: Unicodeデータから表を自作生成 | 版・表の圧縮・対象を自分で固定できる | EAWに加え、絵文字・結合・列の算法も実装・更新する必要がある。出典・ライセンス・生成器・正準データのハッシュ・再生成手順の保守が増える |
| C: EAWだけの小さい表 | 実装が小さい | 絵文字と結合を正しく扱うという今回の範囲を満たさない |
| D: OSのwcwidthを呼ぶ | OSの端末慣行に近い可能性がある | OS・localeによる結果と依存が増え、版を固定しにくい。純粋で移植可能な関数の既定にはしない |

現在の [Cargo.lock:1450](../../../../Cargo.lock)には `unicode-width` 0.2.2 があり、`wast` の依存に含まれる（1804行）。引き込む `wat` は [crates/benitoite/Cargo.toml:49](../../../../crates/benitoite/Cargo.toml)の `[dev-dependencies]` にだけある。本体の通常の依存にはまだなく、現在の配布物に入っている依存の流用ではなく、直接依存として新しく加える案である。既にlockにあることを、宣言と配布時の確認を省く根拠にはしない。

本体のほかの依存と同じく `=` で版を固定する。計画で具体化する候補は `unicode-width = { version = "=0.2.2", default-features = false, features = ["cjk"] }` である。`cjk` はクレートで既定の機能だが、ここでは必要な機能として明示する。既定を有効にした `version = "=0.2.2"` のみの宣言とも比較できる。どちらでもCJKを含めるという公開の意味は同じに保つ。

採用時は、[03-01「使う Rust のクレート」「依存のライセンス」](../../../design/03-interop/03-01-library-structure.md)へ用途と出典を加え、直接依存とlockを照合する。許可済みの MIT または Apache-2.0 を選べるため、現時点で新しいライセンス名を許可一覧へ足す理由はない。実装時に `cargo deny` のライセンス検査と既定の依存検査を行い、配布用の著作権・ライセンス表示にも反映する。今回、検査を実行したわけではない。

`unicode-width` 0.2.2 の [生成済み表](https://raw.githubusercontent.com/unicode-rs/unicode-width/v0.2.2/src/tables.rs)は `UNICODE_VERSION = (17, 0, 0)` を公開する。幅の主表の配列長から計算すると、通常分は `256 + 64×16 + 32×163 = 6496` バイト、CJKを含む分は二つのrootを合わせて `512 + 64×20 + 32×186 = 7744` バイトである。この値は主表の要素の合計だけであり、追加の絵文字・合字の表、コード、リンク時の配置、最終の実行ファイルの増分は含まない。最終の大きさは未測定である。

同クレートの `cjk` 機能を外すと静的な表が小さくなることは [API文書](https://docs.rs/unicode-width/0.2.2/unicode_width/#cjk-feature-flag)に示される。ただしCJK関数を提供するなら、tinyだけで同じ関数の意味を変えたり、CJKを既定へ読み替えたりしない。今回は小さい基盤の依存として共通に含める案を推す。将来、丸ごと外す必要が分かった場合は、モジュールと組み込みの提供集合から外して検査時に断る境界を、補間の幅機能との関係も含めて別に設計する。Cargoの機能で表だけを減らして同じ言語機能を黙って変える方法は、docs/todo の TODO-263 の方針に合わない。

数と幅の本体を Wasmtime・VM から独立させることで、将来の標準ライブラリの分割でも同じ算法を使える。検査器は Unicode の表を使って型を計算せず、幅を指定できる型を検査するだけである。幅の集計はcheckedな整数で行い、`usize` のビット数や64ビット専用のレイアウトを契約に含めない。

Unicode の版は、最初は採用する0.2.2の **17.0.0** に固定する案を推す。「その時点の最新版」を規則にはしない。処理系の版ごとにクレートの版・Unicodeの版・Benitoiteの制御文字の扱いを文書化し、依存の更新だけで幅を変えない。現在の Character の分類はRust標準ライブラリのUnicode版に従う（03-06、308〜311行）ため、その版と表示幅の版は別に示す。既存のUnicode版表示を、表示幅にも同じ版が使われるという意味へ広げない。

表示場所は、版問い合わせと英語リファレンスのStringの節を候補とする。[06-01「版と対応する形式の問い合わせ」](../../../design/06-tooling/06-01-cli.md#版と対応する形式の問い合わせ)の `unicodeVersion` はCharacter用のまま保ち、`--version=json` に `displayWidthUnicodeVersion` という別の任意欄を加える案を推す。人間向けの `--version` にも、既存の二行を保った上で表示幅用の版を一行追加する案を示す。ただし現行06-01は二行の出力を契約としているため、これは互換性を確認してその規約も改める選択である。二行を厳密に保つ必要がある場合は、人間向けはリファレンスで示し、JSONから問い合わせる代案と比べる。出力の具体形・JSONの追加欄と形式の版の扱いは計画で決め、06-01とCLIの確認を変更対象に加える。CHANGELOGには幅が変わる版の変更を記し、実行中の処理系の版を知る唯一の場所にはしない。

将来の更新では、同じ文字列の幅が変わり得ることを互換性の変更として記録し、差が出る代表例と処理系の版を示す。古い版のStringの内容や `characterCount` は変えない。性能の数値はCHANGELOGへ書かず、大きさ・速度を測る場合は測定の記録に分ける。

## 11. 既存コードとの互換性

| 対象 | 保つ条件 |
|---|---|
| `${e}` | 受理する型、型の推論、各型の既存表記、定数式、全式評価→変換→連結の順序を維持する |
| 式内の `:` | 名前付き引数・レコード・パターン・型注釈を従来どおり内部の構文として読む。最初のコロンを無条件に区切らない |
| 本文の `:`・`%`・`#`・`^` | `${…}` の外は普通の文字のままである。`"${x}:08"` の `:08` も本文である |
| 入れ子の文字列 | `"${"a:b"}"` のコロンは内側の内容である。内外の書式を混ぜない |
| 補間を表す文字列そのもの | 普通の文字列では既存の `"\${x:.2f}"`、rawでは `r"${x:.2f}"` で内容を表せる。新たなエスケープは要らない |
| 複数行・raw | 普通の複数行文字列には同じ書式、式と書式は一行。rawには書式処理を加えない |
| 以前は不正な `${x:…}` | 新しく受理される場合がある。以前に成功していた値の意味の変更ではない。ただし誤りの診断と回復の変化は比較対象である |
| 新書式と先読み・前処理 | `when_ahead` 等が書式のコロンを旧式の分岐として読まず、ラムダ境界・改行分類にも書式の記号が漏れないことを、4.1の未再現例と対照例で確認する |
| 公開する新しい関数名 | `String` の既存関数は変更しない。幅とpaddingの追加を利用者向け資料・Skillへ反映する |

この互換性の主張は文法の読解によるものであり、既存入力全件の実行による確認ではない。実装では、式内部のコロンと新しい書式の共存、書式なしのコア形と出力が変わらないことを、接続の受け入れ例にする。

|---|---|---|---|
