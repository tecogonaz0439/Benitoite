# ファイル単位のエフェクトの宣言、uses と with、誤りの式からの回復

調査日: 2026-10-23。対象の開始版: `a0d652c0`。担当: S2。外部資料の確認日は、すべて2026-10-23である。断りのない短い実装パスは `crates/benitoite/src/` からの相対パスである。以下の「推す案」は設計者の採否を待つ判断案であり、実装済みの仕様ではない。

2026-10-23に [RS2](../reviews/RS2.md) の指摘を照合して改めた。指摘ごとの判断は [RS2-response.md](../reviews/RS2-response.md) に記す。

## 1. 前提と判断案

[改造 README](../README.md#設計者の決定2026-10-23)の決定を固定する。ファイルのトップレベルで宣言したエフェクト（effect）は、そのファイルのトップレベルの関数すべての宣言に、型検査より前に一律に書き足す。公開関数も対象とする。`implement` のメソッド、ラムダ、引数の関数型は対象にしない。宣言できるエフェクトの種類を制限せず、追加が原因の誤りでは宣言位置を示す。

推す構文は、既存の語を使う `uses Log, Console.Write` である。ファイルの先頭のメタデータの後、import 群の後、最初の通常宣言の前に一度だけ置く。効力はファイル全体に及ぶ。`main` や外部関数だけを暗黙に除外せず、追加後の型を既存の入口・外部関数・公開契約の規則で検査する。

型の要件を `with` で書く用例として、ZIO 1.x（Scala 2）の `ZIO[Console with Random, Nothing, Unit]` を確認した。これは必要なサービスの型をつなぐ語である。一方、Koka・Effekt・Unison・Flix は、型のエフェクトを記号や型の位置で表し、`with` は主にハンドラの導入・適用に使う。「with を使う先例がある」ことは認めるが、確認した資料から言語全般の頻度は断定できない。語の位置と意味の比較は2.3に記す。

誤りの式の回復は、既存の誤りの型を維持し、誤りから生じた未確定の型の部分の由来を、型注釈を先に解く前から保持する案を推す。関数全体や型変数の連結成分全体を一律に抑制する案は、独立した誤りを消すため採らない。短い問いの一覧は [file-effects-questions.md](file-effects-questions.md) に置く。

## 2. 他言語にある共有の宣言と推論

### 2.1 宣言を共有する単位と、型に現れるもの

次の表は、書き方の骨格を抜き出したものである。エフェクトを追跡する仕組み、値の引数を共有する仕組み、制約を共有する仕組みは、同じ意味ではない。特に「宣言以後の使う定義だけ」と「ファイルの全関数に一律に加える」を区別する。

| 言語・一次資料 | 書き方 | 適用範囲・追加の条件 | 型への現れ方と Benitoite との差 |
|---|---|---|---|
| Lean 4 [Namespaces and Sections](https://lean-lang.org/doc/reference/latest/Namespaces-and-Sections/) | `section`、`variable (α : Type) (x : α)`、`end`。型クラスは `[C α]` | 宣言以後から section/namespace の終わりまで。通常の定義では実際に依存する変数を引数へ抽象化する。定理ではヘッダの依存等に従う別の条件があり、`include` で後続の定理へ強制追加できる。`include` を全種類の宣言の一律追加と解釈しない | 明示・暗黙・インスタンス引数として残る。ファイル内の全関数へ無条件に加える今回の決定とは異なる |
| Rocq/Coq [Sections](https://staging.rocq-prover.org/doc/V9.1.0/refman/language/core/sections.html) | `Section S.`、`Variable A : Type.`、`Context {A : Type}.`、`End S.` | section の後続で利用でき、閉じるとその変数等に依存した大域宣言を一般化する。Context は暗黙引数や let 束縛も扱う | 依存したパラメータが型に残る。未使用の仮定まで全関数へ加えるものではない |
| Agda [Module System](https://agda.readthedocs.io/en/latest/language/module-system.html#parameterised-modules) | `module M (A : Set) where`、`module _ (A : Set) where` | そのモジュールに含まれる定義全体をパラメータで抽象化する。匿名モジュールも使える。モジュールの外にある同じファイルの宣言には及ばない | 関数では明示・暗黙のモジュール引数が同種の引数になる。今回の一律追加に近い範囲の先例。ただし加えるのは値・型の引数である |
| Koka [Programming Language §3.1.3・3.2](https://koka-lang.github.io/koka/doc/book.html) | `fun f(x : int) : console int`、関数型の効果行 `<console,exn>`、省略・`_` を使った推論 | 個々の式・関数の型と効果を推論する。注釈を省くことと、明示注釈で `total` を省くことは別である。ファイルの全宣言へ固定集合を加える記法としては確認していない | 推論したエフェクトは関数の型に残る。型からエフェクトを消す先例ではない |
| Effekt [Effects](https://effekt-lang.org/tour/effects)、[Effect Polymorphism](https://effekt-lang.org/docs/concepts/effect-polymorphism) | `def f(...): Double / { Exception }`。非再帰関数の戻り値の型を省略できる | 個々の関数について型・必要なエフェクトを決める。ブロック引数は呼び出し位置の文脈で処理する独自の多相性を持つ | `/` の後に必要なエフェクトが残る。`/ {}` を Benitoite の純粋な関数引数と同一視できない |
| Unison [Abilities and ability handlers](https://www.unison-lang.org/docs/language-reference/abilities-and-ability-handlers/) | `Text ->{IO} Nat`、`A ->{} B` | 関数本体が呼ぶ関数の能力要件を合併して推論する。トップレベルの即時評価の定義は純粋さを要求する。ファイル単位の一律追加とは別 | 能力の要件が矢印の後の集合に残る。`A -> B` の略記は能力多相の糖衣であり、空集合とは限らない |
| Flix [Effect Polymorphism](https://doc.flix.dev/effect-polymorphism.html)、[Effect System](https://doc.flix.dev/effect-system.html) | `def f(...): Unit \ { FsRead, IO }`、`a -> b \ ef` | 名前付き関数には型・エフェクトの契約を記す。空集合の注釈は省略できる。高階関数の効果変数を引数から具体化する | 効果集合を型に保持する。省略したトップレベル関数の任意の非純粋な効果をすべて推論する言語、と説明する根拠にはならない |
| Scala 3 [Using Clauses](https://www.scala-lang.org/api/3.6.2/docs/docs/reference/contextual/using-clauses.html)、[Capture Checking Basics](https://www.scala-lang.org/api/current/docs/experimental/capture-checking/basics.html) | `def f(...)(using log: Logger): T`、`T^{c}` や `A ->{c} B` の捕捉集合 | `using` はその宣言の引数節。呼び出し時に文脈から値を補う。capture checking は値が参照するケーパビリティ（capability）を型で追う。クラス等の囲むスコープを使うことと、全メソッドへの引数の追加は別 | 文脈引数や捕捉集合として現れる。`using` と capture checking は同一の機構ではない。ファイル全体の一律なエフェクト追加の先例としては確認していない |
| OCaml 5.3 [Effect handlers §24.1・24.5](https://ocaml.org/manual/5.3/effects.html) | `type _ Effect.t += Xchg : int -> int Effect.t`、`try ... with \| effect ...` | ハンドラが囲む計算で操作を処理する。一般の関数型に未処理エフェクトの集合を列挙せず、未処理なら実行時に `Effect.Unhandled` を送出する | エフェクトの推論による注釈省略の例には数えない。Benitoite が固定した静的な契約とは異なる保証である |
| Haskell/GHC [Implicit parameters](https://ghc.gitlab.haskell.org/ghc/doc/users_guide/exts/implicit_parameters.html) | `f :: (?log :: Logger) => a -> a`、型クラスなら `Show a => a -> String` | 使用した暗黙パラメータの制約を呼び出し元へ伝える。`let ?log = ... in ...` で供給する。拡張をファイルで有効にする pragma は、全関数へ制約を加える宣言ではない | `=>` の左の制約に残る。暗黙パラメータは動的束縛であり、型クラスの辞書の選択とも区別する |
| Kotlin [Context parameters](https://kotlinlang.org/docs/context-parameters.html) | `context(users: UserService) fun f(...)` | 個々の関数・プロパティが依存値を宣言し、呼び出し位置のスコープから型で解決する。現行資料の供給例は `context(users) { ... }`。ファイル全体へ自動追加する宣言ではない | 文脈パラメータは宣言の依存として残る。副作用の集合を検査するエフェクトシステムと同一ではない |
| Java SE 21 [JLS §8.4.6](https://docs.oracle.com/javase/specs/jls/se21/html/jls-8.html#jls-8.4.6)、[§11.2](https://docs.oracle.com/javase/specs/jls/se21/html/jls-11.html#jls-11.2) | `void f() throws IOException` | メソッド・コンストラクタごと。検査例外は捕捉するか宣言へ伝える。クラス/ファイルに一つ書いて全メソッドへ加える規則ではない | throws は検査される宣言上の契約。JLS の method signature の定義に throws を含める、という意味ではない。IO 全般を追跡するものでもない |

Agda のパラメータ付きモジュールは「囲んだ宣言の型に要素を加え、外から見てもその要素が残る」点で参考になる。一方、Lean・Rocq の通常の section は依存した宣言を選ぶので、今回の「使わない関数にも加える」という決定を説明する直接の例にはならない。推論を使う Koka・Unison も、今回採らない選択肢の比較資料である。

### 2.2 呼び名と日本語の用例

新機構に「暗黙のエフェクト」という名前は推さない。型に残る固定集合の書き足しであり、暗黙のパラメータの解決や本体からの推論を行わないためである。既存の用語集の「エフェクト」「宣言」「ファイル」を使い、説明上の呼び名を「ファイル単位のエフェクトの宣言」とする案を推す。独立した理論概念の新しい訳語とは扱わない。採用後は00-04の「Benitoite の仕様と設計の語」に、適用範囲と合併後の契約を示す行を加える。この編集は採用後の計画に割り当て、今回の調査では用語集を変更しない。

| 呼び名の候補 | 対応する既存の呼び名・日本語の用例 | 評価 |
|---|---|---|
| ファイル単位のエフェクトの宣言 | Python 公式日本語訳は [global 文](https://docs.python.org/ja/3.13/reference/simple_stmts.html#the-global-statement)等を「宣言」と記す。Benitoite の用語集には「エフェクト」がある | 範囲と行うことを既存語で説明できる。推す案。Python と同じ意味という主張ではない |
| セクション変数／モジュールパラメータ | Lean の原語は section variables、Agda は module parameters。[TPIL 4 日本語訳「依存型理論」](https://aconite-ac.github.io/theorem_proving_in_lean4_ja/dependent_type_theory.html)には「変数とセクション」の用例がある | 引数を導入しない今回の機構には適さない。日本語訳は用語の使用例としてだけ参照し、Lean の意味は公式英語資料で確認した |
| 文脈パラメータ | Scala は context parameters、GHC は implicit parameters。[Scala By Example 日本語訳](https://www.scala-lang.org/docu/files/ScalaByExample-ja_JP.pdf)には第15章に「暗黙のパラメータ」の用例がある | ケーパビリティの値や辞書を自動補完する仕組みと混同する。採らない |
| 既定のエフェクト／共通のエフェクト | 今回と同じ意味に定着した英語名と日本語訳の組は未確認 | 「個別宣言で置き換えられる既定値」と誤読されうる。正式名にはせず、採る場合は設計者が選ぶ |

### 2.3 エフェクトを型に書く語・記号と with の役割

| 言語 | 型のエフェクト・能力・制約の表記 | with がある位置と意味 | 一次資料 |
|---|---|---|---|
| Koka | 結果型の前のエフェクト／`<e1,e2>` | `with ctl op(...) ...` はハンドラを残りのスコープに適用する。一般の `with x <- f` は残りをクロージャとして渡す糖衣でもある | [Koka §3.1.5・3.4](https://koka-lang.github.io/koka/doc/book.html#sec-with) |
| Effekt | `T / { E }` | `try { ... } with E { ... }` のハンドラ | [Effect Polymorphism](https://effekt-lang.org/docs/concepts/effect-polymorphism) |
| Unison | `A ->{E} B` | `handle e with h` のハンドラ関数 | [Abilities and ability handlers](https://www.unison-lang.org/docs/language-reference/abilities-and-ability-handlers/) |
| Flix | `T \ E`、`T \ {E1,E2}` | `run { ... } with handler E { ... }` | [Effects and Handlers](https://doc.flix.dev/effects-and-handlers.html) |
| OCaml 5 | 関数型にエフェクト集合を宣言しない | `try ... with` 等の例外・エフェクトの節 | [Effect handlers](https://ocaml.org/manual/5.3/effects.html) |
| Haskell | `C a => ...`、`(?x :: T) => ...`。IO は `IO a` の型 | ImplicitParams の宣言語として with は使わない | [Implicit parameters](https://ghc.gitlab.haskell.org/ghc/doc/users_guide/exts/implicit_parameters.html) |
| ZIO 1.0.18（Scala 2） | `ZIO[Console with Random, Nothing, Unit]`、`ZIO[Console with Clock, IOException, Unit]` | 効果の型の環境要件を Scala 2 の複合型の `with` でつなぐ。型の要件を列挙する位置での with の先例である | [Contextual Types](https://zio.dev/1.0.18/reference/contextual/)、[Promise の使用例](https://zio.dev/1.0.18/reference/concurrency/promise/#example-usage)、[Scala 2.13「Compound Types」](https://www.scala-lang.org/files/archive/spec/2.13/03-types.html#compound-types) |
| Scala 3 | `(using c: C)`、capture checking の捕捉集合、交差型 `A & B` | using 句の宣言語は using。型をつなぐ `A & B` は Scala 2 の複合型 `A with B` を置き換える。これとエフェクトリストの導入語は区別する | [Using Clauses](https://www.scala-lang.org/api/3.6.2/docs/docs/reference/contextual/using-clauses.html)、[Intersection Types の詳細「Relationship with Compound Type」](https://docs.scala-lang.org/scala3/reference/new-types/intersection-types-spec.html#relationship-with-compound-type-with) |
| Kotlin | `context(c: C)` | 文脈パラメータの宣言語は context。with をエフェクト型の宣言語とする根拠はない | [Context parameters](https://kotlinlang.org/docs/context-parameters.html) |
| Java | `throws E` | エフェクト型の宣言語として with は使わない。try-with-resources は別の文法 | [JLS §8.4.6](https://docs.oracle.com/javase/specs/jls/se21/html/jls-8.html#jls-8.4.6) |
| Python | エフェクト集合の型注釈ではない | `with expression as name:` はブロックの前後で context manager を実行する | [Language Reference §8.5](https://docs.python.org/3/reference/compound_stmts.html#the-with-statement) |

ZIO の環境は、計算に必要なサービスを型に残すため、能力の要件を契約に書く比較対象になる。[ZIO 1.0.18「Runtime」](https://zio.dev/1.0.18/reference/core/runtime/#default-runtime)にも `type ZEnv = Clock with Console with System with Random` がある。ただし、`with` は Scala の汎用の複合型の構文であり、ZIO 専用の効果宣言語ではない。`A with B` では二つの型の間に置き、今回の `with A, B` 案ではリストの先頭に置く。Benitoite の宣言の語として採用する判断には、この形の違いと、現行の with の開閉規則への影響も含める。

Koka 等の実行側の用例と ZIO の要件側の用例の両方を比べても、uses からの変更による生成・修正の成功率の改善は未確認である。LLM の取り違えの頻度は測定していない。先例の有無と、今回の変更の利点の見込みを分け、uses 維持を推す。

## 3. A: ファイル単位の宣言の具体案

### 3.1 構文、位置、宣言の回数

推す形は次である。これは未実装の提案であり、現行 CLI の受理例ではない。

```text
language "0.0.11"
import Benitoite.Unofficial.IO.Console

uses Log, Console.Write

function helper() -> Unit
  ()
end function

function main() -> Unit
  helper()
end function
```

この場合、helper と main の最上位のエフェクトは、ともに `Log, Console.Write` になる。helper の本体が純粋でも同じである。例の版番号は次版の候補であり、改造全体の版上げの決定を先取りしない。

| 論点 | 選択肢 | 推す案・理由 | 原則・互換性・形式化 |
|---|---|---|---|
| 宣言語 | `uses`／`with`／`effects`／`using`／`requires`／`effect` | uses。関数の契約と同じ語を使い、新しい予約語を増やさない。effect は既存の操作の宣言と競合し、using 等は新しい文脈依存語の処理を要する | 原則4・5。uses 維持なら既存ソースは有効。いずれも具体構文だけなら形式化の外 |
| 位置 | import より前／import より後／トップレベルのどこでも | メタデータ、import 群、ファイルの uses、通常宣言の順。import の対象を確認してから名前を読める | 原則2・4。新しい uses を置かない旧ソースはそのまま。先頭のパーサとヘッダ検出の変更が必要 |
| 回数 | 一回／複数を合併／後続だけへ累積 | 一回。複数は重複宣言の診断で一つに統合するよう案内する。後続だけへ累積する案は「全関数へ一律」の決定と合わない | 原則2・5。既存への影響なし。形式化の外 |
| 適用範囲 | 宣言以後／ファイル全体 | ファイル全体という決定を維持。位置を先頭に限るのは効力の違いではなく、読み取りと診断のための制限 | 公開型にも反映し原則2を保つ |
| 省略・空集合 | 宣言なし／`uses` だけ／`uses []` | 宣言なしで空集合。新しい空の表記は増やさず、空の宣言は構文の誤り | 原則5。今の uses の要素リストの形を再利用 |
| 列挙するもの | 既存の EffectRef／ファイルの型・効果パラメータも新設 | 既存のエフェクト参照と具体的な型引数を使う。ファイルの型・効果パラメータは新設しない | 種類の制限は追加しない。`Fail[MyError]` は候補に含め、束縛されていない T や E は既存どおり名前の誤り。原則1・4 |

現行の字句規則では uses はキーワードなので、新しいトークンは要らない。`syntax/ast.rs:46` の Module にファイルの宣言の保持先を加え、`syntax/parser/mod.rs` のモジュールの読み取りと `syntax/parser/header.rs`、`syntax/header.rs` のヘッダ抽出との境界を合わせる。Module は header、imports、decls を別々に保持するので、通常の関数宣言である `Item::Fn` に仮装させない。

リストの要素の基本形には `syntax/parser/types.rs:243` の `parse_uses` と `syntax/ast.rs:391` の UsesList/EffectRef が使える。ただし parse_uses は入れ子の関数型のコンマと角括弧を区別するため、二番目以降の単純名の型引数に特別な回復を持つ。ファイルの宣言には外側の型引数リストがない。`uses Log, Fail[MyError]` を誤って既存の E0209 の回復へ送らないよう、ファイル位置に合うリストの読み取りを分ける必要がある。末尾のコンマ・複数物理行の扱いは、既存の改行の継続規則に合わせ、宣言の末尾の実改行を境界にする。

### 3.2 対象ごとの効果と既存の制約

根拠の規範は、[01-06「多相な名前」「型付きの失敗と行の条件」](../../../design/01-spec/01-06-type-system.md)、[01-07「プログラムの入口」「型付きの失敗」](../../../design/01-spec/01-07-effects.md)、[06-04「テストの宣言」「Property」](../../../design/06-tooling/06-04-test-runner.md)である。実装上、FnDecl という Rust の型は実装メソッドにも使われる（`syntax/ast.rs:148`）。FnDecl を再帰的に全件書き換えると決定に反する。対象を Module.decls 直下の `Item::Fn` に限定する必要がある。

| 対象 | 書き足しの案／決定 | 生じることと扱い |
|---|---|---|
| 入口の main | 書き足す | 利用者定義のエフェクトと Fail を含むと E0506。Assert.Check を含むと E0415。main だけを省く変更は提案しない。ファイルの宣言を外し個別に書くか、main を別ファイルへ置くよう案内する |

| 局所の関数 | 足さない | 現行の局所の関数値はラムダと束縛で書く。名前付きの function 宣言を局所に置く規則はない。ラムダは本体からの既存の推論／明示の uses に従う |

| trait 内のメソッドの宣言 | 足さない案を推す | TraitDecl 内の契約であり、そのファイルのトップレベルの関数宣言ではない。ここまで追加すると、除外した implement に新しい効果の契約を課す。メソッドの明示契約はそのまま |

`@external` の現行検査は `typeck/external.rs:11–45` にあり、外部値のない宣言では `f.uses.is_some()` 自体も見ている。追加を Scheme にだけ入れ、元の AST の uses の有無を残すと、この判定をすり抜ける。入口の検査も `typeck/effects/declarations.rs:77` が AST の uses を走査する。従って「型表の集合に足すだけ」の実装では足りず、これらの検査は追加済みの宣言とその由来を参照しなければならない。

derive の個別指定の純粋な関数は、`tools/derive/derive.py:529` 以降でシグネチャの effects も検査している。生成前の inventory が手書きの uses だけを見ると、ファイルの宣言を見落とす。生成先に宣言があることを黙って無視せず、追加後の inventory と生成後の通常の型検査の両方で扱う。生成器の管理領域や出力ハッシュを人手で書き換える方法は採らない。

derive の import の挿入位置も変更対象である。現行の [tools/derive/README.md「Markers, records, and review artifacts」](../../../../tools/derive/README.md#markers-records-and-review-artifacts)は、文書・ヘッダ・既存の import の後、通常宣言の前に新しい領域を置く。`tools/derive/derive.py:1036` は import と preambleEnd から挿入位置を求め、`:1106` 以降は通常宣言より前の既存領域も新しい import の置き場所に選ぶ。ファイルの宣言を導入した後は、この既存領域がファイルの宣言の後にある場合も区別する必要がある。

推す規則は「メタデータと既存の import の後、ファイルの宣言の前」である。`examples/derive_inventory/mod.rs:458` 以降の preambleEnd をファイルの宣言の終わりまで広げず、ファイルの宣言の位置を import 挿入の上限として inventory に渡す。宣言後の既存領域へ import を追加しない。安全な新規領域を作れず手書き部分の移動が必要な場合は、既存の拒否と案内を保つ。import がない場合、文書・メタデータ・コメント・CRLF がある場合、既存領域が宣言の前後にある場合を自己検査の対照にし、README と inventory の版・生成記録への影響を計画に含める。単に新しい import を末尾へ足す実装にはしない。

### 3.3 main のハンドラ、許可、検査の報告

利用者定義の U をファイルで宣言した場合、main の本体の中ですべての U の操作を handle しても、main の宣言には U が書き足される。既存の規則は本体の最小の効果ではなく、入口が宣言する型に未処理の利用者エフェクトを認めない。従って、この main は拒否される。これは「ハンドラを書けばファイルの宣言も取り消せる」という規則にはならない。Assert.Check を扱う場合も、main の宣言に含められないという制限は残る。これらは現行規則から導く追加後の帰結であり、新構文での実行確認ではない。

Log・Console.Write を加えた場合は、追加済みの main/@test の宣言上限を実行前の照合に使う。本文で操作を実行しなくても、`--allow-effects` の列挙が不足すれば E0512 となる。[06-01「実行前のエフェクト上限の照合」](../../../design/06-tooling/06-01-cli.md#実行前のエフェクト上限の照合)、`cli/effect_limit.rs` の ID による比較を維持する。ファイルの uses を書いたことは、ハーネスからの許可でも実行時の権限制御でもない。

`test --check` 系の JSON 報告は `cli/tools/test_runner/check_report.rs:138` で契約から効果を取り出し、`basis: declaredUpperBound` と `expanded` を記す。追加したものもこの展開済みの集合へ含める。入口の報告を実際に行った作用と表示しない。`check` の通常の成功表示に、全関数の型を新たに列挙する機能まであるとは扱わない。追加が原因の許可不足では、入口位置に加えファイルの宣言位置を補助位置で示す案を推す。これは型検査の診断以外の CLI の診断にも由来を渡す作業を含む。

ファイルの宣言を使うと、ソースの main の行だけでは合併後の宣言上限を読めなくなる。この影響は、main も対象にする決定を保ったうえで、利用者へ示す手順として補う必要がある。選択肢は、Skill を通じて既存の `check --report=json` の結果を人間へ示す、ソースの main とファイルの宣言を一緒に読むよう文書で案内する、通常の check の文章の出力に上限の行を新設する、である。

推す案は、Skill で、検査に成功した報告の `targets[0].main.effects.expanded` をハーネス側で人間向けに示すよう案内することである。[06-01「main の非実行の検査報告」](../../../design/06-tooling/06-01-cli.md#main-の非実行の検査報告)の `status: ok`・`complete: true` を条件とし、宣言上限であることを説明する。失敗・不明を空集合と表示せず、上限を自動で許可へ変換しない。通常の check の標準出力は空という既存契約を維持する。ソースの二箇所を合わせて読む注意は補足とし、主な接点はハーネスが示す検査済みの上限に置く。これは原則2・3とハーネス経由の利用を主に置く方針に沿い、古いスクリプトと報告の形式を変えず、形式化の規則にも影響しない。表示する処理系の報告の意味は版を固定した06-01を参照し、ハーネス固有の許可画面や操作手順をSkillへ写さない。

### 3.4 型変数、Fail、局所構築器、重複

| 論点 | 選択肢と推す案 | 理由・既存規則への接続 |
|---|---|---|
| エフェクト変数 E | 固定集合 F を関数の最外側の行へ合併する／引数型の E にも加える。前者を推す | `[effect E]`、引数型の `uses E` はそのまま、宣言の `uses E` は `uses E, F` となる。E の推論や引数に現れる条件（01-06）を変更しない |
| ファイルでの自由な型・効果変数 | 各関数の同名変数を拾う／ファイルのスコープで解決する。後者を推す | 関数ごとに意味を変えず、未束縛は診断する。閉じた MyError を使う Fail は宣言可能。各関数の T を取り込む新機能は設けない |
| Fail と NoFail | 書き足し前の条件を保存／書き足したシグネチャから計算。後者を推す | `typeck/decls.rs:620` の `signature_no_fail` より前に追加する。`Fail[MyError]` と E が同じ行に並べば E に NoFail が必要となる。関数の本体から契約を追加推論しないという規則は維持 |
| Fail の別型 | どちらかを優先／既存の E0514。後者を推す | 明示 Fail[A] と追加 Fail[B] が異なる型なら衝突を報告する。型引数の別名を展開した同一性で比較する。Fail を名前だけで除重しない |
| 明示とファイルの同じ効果 | E0419／合併。合併を推す | 各リスト内の明示重複は既存どおり E0419。二つの有効な宣言の間では集合の合併として冪等にする。既に uses Log と書いた関数へファイルの uses Log を導入しやすい |
| 同じ型の Fail の重複 | リスト間も重複診断／リスト間は同一型を合併。後者を推す | リストの内部の明示した Fail の重複は既存の検査を保つ。型の同一性を確認できる段で合併する。異なる型の衝突を隠さない |

NoFail が加わる影響は、ログの名前の合併だけの場合より大きい。例えば、以前は任意の Fail を運べた `uses E` の高階関数にファイルの `Fail[MyError]` が加わると、E が運べる集合の契約も変わる。これは宣言を制限しないという決定の帰結として示す。既存の Fail の制限を緩める案には広げない。

### 3.5 モジュールと公開契約、由来の保存

ファイル F の宣言は F 内の関数の型だけを変える。F を import する G の全関数へ宣言そのものを引き継がない。G から F の関数を呼ぶと、追加済みの型を既存の包含規則で検査する。F で許した Log を G が宣言しなければ、G の呼び出しで E0501 となる。関数値を純粋な引数へ渡す場合にも型の不一致が起きうる。従ってファイルの宣言を追加することは、公開 API の契約を変える操作である。

公開関数へ非公開の利用者エフェクトを追加した場合は、既存の公開契約の可視性の検査も必要である。現行の `resolve/walk.rs:112` の signature と `resolve/checks.rs` の検査は、元の AST の参照を基に公開性を調べる。名前解決の後で追加する場合も、追加した参照に対して同じ公開性の検査を通さなければならない。

推す処理順は、ファイル位置で効果名と型引数を解決し、各トップレベル関数の有効な宣言へ合併し、その宣言について公開性・入口・外部関数・NoFail 等を検査し、全関数の Scheme を確定してから本体を調べる、である。生の文字列を各関数のスコープで解決し直さない。ファイルのスコープでは未束縛の E や T が、関数ごとに別の型パラメータやエフェクト変数に捕まるのを防ぐためである。既にファイル位置で解決できる名前は、01-03「型パラメータとエフェクト変数の有効範囲」の同名禁止によって関数のパラメータには隠されない。そこまで意味が変わるという理由にはしない。

由来は、効果ごとに「関数自身に書いた範囲」「ファイルで書いた範囲」を保持する。構文木（abstract syntax tree、AST）を複製する実装なら共有 IdGen から新しい NodeId を振り、参照先の束縛は解決済みの同じものに結ぶ。型表へ合併する実装なら、元の AST の uses を直接見る入口・外部・警告の検査を、有効な宣言を見る共通の入口へ変更する。どちらも、元のソースに存在しない挿入範囲を自動修正に使わないことが条件である。

合併する場所は FnDecl 自身の最外側の効果に限る。戻り値が関数型である場合も、戻り値の関数型の潜在効果へ追加しない。ソースの戻り値の型の末尾へ文字列を足す方法では、この区別を保てない。レコードの自動アクセサ等、ソースにトップレベルの関数宣言として書かれていない内部生成物も、型の中の関数を再帰的に辿って追加する対象にはしない。

#### package が記録する依存のエフェクト

[06-09「`benitoite package`」](../../../design/06-tooling/06-09-packages.md)のエフェクトの報告は、型検査をせず、依存の公開宣言の構文を読む。`cli/tools/package/effects.rs:43` 以降の Summary::collect も、公開の Item::Fn の function.uses と、公開の trait のメソッド等の型を直接読む。この経路にファイルの宣言を反映しないと、追加だけで増えた Console.Write や Process.Run が `effects` の記録と update の `+`・`-` から抜ける。型表や検査報告への反映とは別に修正する必要がある。

選択肢は、現在の構文だけの集計へファイルの宣言を加える、型検査済みの契約を使う集計へ切り替える、である。前者を推す。後者は型の誤りがある開発中の依存も記録できるという06-09の契約を変えるため、今回の書き足しに必要な範囲を超える。前者なら既存ソースの記録は原則として保ち、追加した効果による差分だけを update で示せる。原則2に対応し、Lean の定義と交換用の表現は変えない。

集計の規則の案は次のとおりである。

1. そのファイルに外部へ公開したトップレベルの Item::Fn（`public(package)` を除く）が一つでもあれば、ファイルの宣言にある識別可能な組み込みの効果を、既存の集計の和へ一度加える。非公開の関数だけのファイルには加えない。関数の本体を実行・型検査せず、宣言上の追加として扱う。
2. 同じファイルの正式な import と標準の登録表から、個別の uses と同じ規則で組み込みを識別する。エフェクト変数、利用者定義のエフェクト、標準の表にない import を経由する名前は数えない。IO.All はこの報告では展開せず、State と IO.All の import 不要の識別は保つ。ファイルの型引数や入れ子の関数型へ効果を再帰的に書き足さない。
3. 公開の trait のメソッド、型の別名、レコードや data の欄しかないファイルでは、そのことだけを理由にファイルの宣言を加えない。それらが元から明示している uses の集計は維持する。公開関数のあるファイルでも、書き足しを trait や入れ子の型の要素として複製しない。
4. 効果名の正規表示・辞書順・集合の重複除去・update の増減・字句や構文の誤りなら書かない規則を保つ。標準の識別規則を共有してから、関数個別のリストとファイルのリストを合併する。

Log の識別には注意が要る。現行の `effects.rs:139` 以降の短縮名の特別扱いは State と IO.All だけであり、prelude の裸の Log をそのまま追加しても取りこぼす。主用途を報告できるよう、裸の Log と既存の修正案が示す Benitoite.Log を標準の Log と識別する規則を、個別・ファイルの双方へ揃える案を推す。トップレベルの大文字の宣言や別の import が Log を隠す場合は標準 Log と数えず、型検査なしの集計という限界を保つ。この補完により、従来の裸の Log の記録にも差分が出うるので、06-09の改訂と移行の案内に明記する。

受け入れでは、ファイルの宣言だけの変更で記録と update の増減が変わる例、複数の公開関数と個別 uses の重複、非公開のみ・trait のみ・public(package) のみの対照、IO.All の非展開、Log の識別と名前の衝突、型の誤りはあるが構文は正しい依存を確認する。`tests/package_command.rs` の既存の記録と増減の検査へ割り当て、06-09の集計規則と利用者向けの説明も同じ変更で改める。

### 3.6 診断、警告、同梱 Skill

既存の意味の誤りは既存の番号を使い、ファイルの宣言を補助位置に追加する案を推す。関数の契約へ追加された経緯を note で説明すれば、入口の制限の誤りと名前の誤りを別の番号で重ねずに済む。`diag/codes.rs` の最終的な採番は並行する TODO-273 の診断と合わせて実装プランで固定する。

| 場合 | 診断の案 | 位置と修正案 |
|---|---|---|

### 3.7 形式化への影響

[01-12「型の情報を付けた表層の構文と型付け」](../../../design/01-spec/01-12-core-calculus.md)は、名前解決と型推論で型の情報を付けた入力から始める。[07-04「01-12 との対応」「形式化の対象外」](../../../design/07-quality/07-04-formal-semantics.md)は、型推論の健全性・完全性を対象外とし、E2 で処理系が書いた情報を入力ごとに再検査する、と分けている。

Lean の `formal/Benitoite/Surface/Syntax.lean:504` の FunDecl は `eff : Eff` を持ち、`:593` の Def がそれを継承する。`Surface/Check.lean:859` の checkDef と `Surface/CheckTables.lean:219` の checkProgram は、その完成した宣言と本体を検査する。従ってファイルの宣言をこの入力の作成前に合併し、既存の効果集合・型・NoFail の情報として出せば、新しい表層項や効果の意味は要らない。Lean の定義・主定理・交換用の表現の変更は0件の見込みである。

ただし、新構文を含む Rust 側の入力を交換テストへ追加し、個別に uses を書いた同等の入力と同じ宣言・本体が出ること、E2 が追加済みの契約を検査することを確かめる必要はある。新しい効果名だけを `atoms` の収集から落としたり、Fail の NoFail 条件を追加前のものにしたりすると、既存形式のままでも接続を誤る。これは形式化済みの定理がソースの書き足し自体を証明している、という保証にはならない。

## 4. B: uses を with に改める場合

### 4.1 現行の with の全用途と衝突

現行の01-01「キーワード」「改行」と、`syntax/parser/exprs.rs`・`effects.rs` を照合すると、with の言語上の用途は、リソーススコープの開始・`end with` の終端、match の分岐の導入、handle の節の導入である。属性等の文字列内の with や、withTextLogger のような関数名の一部は別である。

| 位置 | 現行／改めた案 | 解析への影響 |
|---|---|---|
| リソース | `with r = open() do ... end with` | 既存用途。式の開始にある with はこの解析へ進む |
| match | `match e with case p -> ... end match` | 既存用途。with の後の case で分岐と判別する |
| handle | `handle ... with case E.op(...) -> ... end handle` | 既存用途。`exprs.rs:687` の BlockEnd::WithCase は、既存の誤記の when からの回復も扱う |
| 関数の宣言 | `function f() -> Unit with Log` | 戻り値の型の後という位置で効果リストを読める。ただし本体の最初のリソース with と、改行による区切りを保つ必要がある |
| 関数の型 | `function() -> Unit with Log` | 型を解析中という文脈では区別可能。括弧・角括弧の内側の改行判定が先行するので、パーサの置換だけでは済まない |
| ラムダ | `lambda() -> Unit with Log ... end lambda` | 明示の戻り値の後の効果と、ラムダ本体のリソース with の区別が必要。短いラムダの物理行の境界も維持する |
| 操作の宣言 | `effect E ... function op() -> Unit with Log ...` | 現在 uses を拒否する箇所を with に合わせて拒否する。操作へ独立の効果を許可する変更は含めない |
| ファイルの宣言 | `with Log, Console.Write` | 宣言位置を先頭に限定すればリソースとは区別できるが、現行の字句前処理はこれをブロックの開始と数える |

現行の `syntax/newline.rs:112` は、with の次の改行以外の字句が case でない限り、ブロックの開始を積む。01-01も同じ規則を定める。エフェクト注釈の with は case が続かず、`end with` も持たないため、この規則のままでは余分な開きが残る。括弧内で、ブロックの内外により改行を残すかどうかも変わる。`syntax/lambda_bounds.rs`、パーサの回復の開閉スタック、`syntax/parser/effects.rs:340` の不正な with の読み飛ばしも確認対象となる。

正しい入力なら、リソース束縛の小文字名と `=`、エフェクトの大文字名、節の case、型を読んでいる文脈を組み合わせて区別できる見込みである。従って with への変更を「文法的に不可能」とは判断しない。しかし大文字・小文字を誤った入力や、ヘッダ末尾の効果の書き忘れ、戻り値が関数型である場合には、誤りからの回復がどこまで読み飛ばすかも変わる。全位置の with を一律に「次が大文字なら注釈」とするだけでは、既存の不正なリソース・ハンドラへの案内を保証できない。

採るなら、注釈／節／リソースの三つを改行の前処理から区別する規則を先に定め、関数型の入れ子、ラムダの短い形と終端のある形、match/handle の内外、CRLF、コメント、ヘッダの誤記を組にして検証する。意味が一意に定まる文法と、誤った入力で診断を保つ実装は別の確認事項である。

### 4.2 原則5、生成と修正、読みやすさ

原則5は「同じ役割の構文を必要なく複数持たない」であり、同じ語を複数の役割に使うことを直接禁止してはいない。全位置を with に統一して uses を廃止すれば、効果の宣言の書き方自体は一種類にできる。一方、uses と with を恒久的な同義の構文として両方受理する案は、原則5に反する重複を作る。

読み取りでは、現行の uses は契約の効果を示し、with はリソースかハンドラ・分岐の境界を示す。with に統一すると、同じ語から「作用を伝える契約」か「作用を処理するスコープ」かを判別する必要が生じる。ZIO 1.xの要件の表記に慣れた読み手には連想できる利点がある一方、語の置かれる位置は異なる。Koka 等からの生成では with をハンドラの導入として持ち込む可能性があり、Python からはリソースの導入として持ち込む可能性がある。この利点と負担が生成成功率をどれだけ変えるかは未確認であり、今回 LLM を呼ぶ評価は行っていない。

### 5.3 比較する案と抑制の境界

| 案 | 利点 | 不具合 | 判断・原則・互換性・形式化 |
|---|---|---|---|
| 現行を維持し説明だけ残す | 変更が小さく、独立した誤りを消す危険を増やさない | 確認済みの連鎖した E0401 が残り、TODO-276 の改善にはならない | 保留案。受理する成功プログラム・Lean は変わらない |
| Expr::Error の直後の単純 bind だけ Error にする | 今回の再現に小さな変更で対処できる | 呼び出しの失敗、構成子・リスト・レコードの一部分、遅延制約には届かない | 局所の第一歩としては可。これだけで一般の回復を完了とはしない |
| 由来を持つ型変数／型の部分を保持する | 後の注釈を通った後でも原因を追え、必要な診断だけ選べる | 原因の伝播方向、宣言による確定、複合型の部分の扱いが必要 | 推す。原則1・4。成功入力の型付け・制約順は保ち、誤り入力の診断だけ変える。Lean の規則は変えない |
| Error を含んだ比較の両型・由来の連結成分をすべて無効にする | 既存 poison の拡張で実装しやすい | List[Error] と Integer の外側の不一致や、同じ関数の正常な引数の誤りまで消しうる | 推さない。原則1の独立した誤りを損なう |
| 誤りのある関数の後続診断をすべて止める | 連鎖の見分けが不要 | 今回の independent の誤りも消す | 採らない。原則1に合わない |

推す案の条件は、次のとおりである。詳細なデータ構造をこの調査で固定せず、実装プランで現行の Provenance との統合を決める。

1. 原因を報告した時点で、その値の未確定な結果の部分へ診断済みの由来を付ける。Expr::Error だけでなく、呼び出し不能 E0403 等で結果が Error になる経路を含める。新しい利用者向けの「誤りの型」は作らない。
2. Declared の制約を先に解く前から、誤りから新しい束縛へ渡る依存を保持する。zonk で具体型になっても由来が失われないようにする。単純な変数だけでなく、型の引数・関数の各部分・失敗型の部分へ対応付ける。
3. 注釈がない `bind f <- error` の f の推論結果は回復の仮の情報である。後の `bind n: Integer <- f`、正常に宣言された関数の引数の型、パターン等が f の型変数へ流し込んだ型は、f の値の型を確定する根拠としない。その変数を通じた不一致を抑え、再現の5行目のOptionパターンのE0401も抑える。制約を解く順序によってこの判断を変えない。
   一方、`bind f: Integer <- error` の f 自身の明示契約は、右辺の推論に依存しない根拠である。f を後でStringとして使う不一致は残す。また `bind n: Integer <- f` の n 自身は明示契約を持つので、n の後のStringとしての使用まで抑えない。利用側が求めた型と、その利用側自身の宣言の型を区別する。
4. 型の既知の構造は残す。List[Error] と List[Integer] の比較で未知なのは要素の部分だが、List[Error] と Integer の比較は外側の構造の独立した不一致である。Error を一か所含むだけで比較全体を成功とする既存 has_error/poison の拡張にはしない。
5. 呼び出し元の誤りの引数と、正しく宣言された関数の戻り値を区別する。`idInt(error)` の戻り値が宣言でIntegerと決まるなら、その戻り値とStringの独立した不一致を残す。引数の契約がIntegerだからといって、誤りに由来する元の値の型までIntegerに確定したとはみなさない。同じ由来のグラフに属することだけでは抑制しない。
6. 型クラス、演算子の制約、網羅性、名前・ラベル・引数個数、エフェクトの禁止などは、それぞれ原因の依存を調べる。今回一括してすべての診断へ抑制を広げない。不明な場合は独立した誤りを残す側にし、連鎖が残る限界を説明する。
7. 診断済みの原因が少なくとも一つ残ること、誤りが一つでもあれば成功や実行に進まないことを保つ。由来の情報を実行用の Ty や交換の型へ書き出さない。

初期の受け入れ例は、再現の E0467・E0403 の二経路で、依存した Option パターンの E0401 が消え、同じ関数と別関数の Integer/String の独立した誤りが残る組とする。明示の Integer の注釈、正常な関数の宣言の結果、List の外側の不一致、入れ子の一部だけの誤りを負の対照にする。テストの件数を増やす前に test-audit の作成時の関門を適用する。今回はテストの編集・実行をしていない。

受け入れの境界を次の表で固定する。error は診断済みで結果が未確定な式を表す説明用の記号であり、利用者が書く構文ではない。

| 入力の関係 | 抑える診断 | 残す診断・型 |
|---|---|---|
| `bind f <- error`、`bind n: Integer <- f`、fをOptionパターンに使う | 利用側の注釈とパターンの要求どうしが、fの回復の型を通じて食い違う診断 | 元の原因の診断、同じ関数の独立したInteger/Stringの不一致 |
| 同じfをInteger引数の関数へ渡した後、Optionパターンに使う | 引数の契約がfへ流し込んだ型と、後のパターンの不一致 | 引数の個数・ラベルや別引数の独立した不一致。呼んだ関数自身の宣言した結果型 |
| `bind f: Integer <- error` のf、または `bind n: Integer <- f` のnを後でStringとして使う | 誤りの値そのものと束縛時の期待型の比較 | fまたはn自身の明示契約と、後の使用の不一致 |

この抑制は、原因を報告してプログラム全体を拒否した状態で、根拠のない回復の情報だけを診断の根拠から外すものである。原因の式を直した後は通常の型検査ですべての使用を再検査し、実際の型と合わない使用を報告する。修正後の型次第で一致する使用もあるため、「以前抑えたすべての箇所で必ず診断する」とは約束しない。原則1との関係は、原因と独立した誤りを残し、誤りを含むプログラムを受理しないことで保つ。
