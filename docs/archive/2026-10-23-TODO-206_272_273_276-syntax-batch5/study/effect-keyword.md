調査日・外部資料の確認日: 2026-10-23。対象の開始版: `a0d652c0`。担当: S3。本書は調べと判断の案であり、採否は設計者が決める。外部の構文・意味を一次資料で確認した事実と、英語の読みやすさ・LLM の生成や修正への影響についての未測定の見込みを分ける。

## 1. 比較する範囲と固定した意味

[改造 README](../README.md#設計者の決定2026-10-23)の決定を前提にする。ファイル単位の宣言は、型検査の前に、そのファイルのトップレベルの関数すべてへエフェクト（effect）を一律に書き足す。公開関数にも加え、`implement` のメソッド、ラムダ、引数の関数型には加えない。宣言するエフェクトの種類を制限せず、追加が原因の誤りでは宣言位置を示す。語を改めても、この意味を変えない。

現行の対象は、関数宣言の `function f(x: Integer) -> String uses Console.Write, Log`、ラムダの注釈、関数型の注釈である。新しいファイル単位の宣言にも同じ導入語を使う案を比較する。`effect Log … end effect` はエフェクト自体の定義、`[effect E]` はエフェクト変数の束縛であり、列挙を導入する `uses` とは役割が異なる。どちらも今回の改名対象に含めない。現行の解析は `syntax/parser/decls.rs:309`、`exprs.rs:1053`、`types.rs:243` の `parse_uses` を共有する。断りのない実装パスは `crates/benitoite/src/` からの相対パスである。

比較する意味は「計算が起こしうる作用の集合」である。[用語集の「エフェクト」](../../../design/00-overview/00-04-glossary.md#関数型プログラミング)の定義と、[01-07「エフェクトの型と権限制御の区別」](../../../design/01-spec/01-07-effects.md#エフェクトの型と権限制御の区別)に従う。集合は、本体が毎回そのすべてを実行するという主張でも、実行に不可欠な最小集合という主張でもない。今回のファイル宣言は、使わない作用も関数の契約に加えるので、この区別が語の選択に直接関わる。

人間には、実行前に「許可する操作」を確かめる一覧として読めることが求められる。ただし、注釈を書く行為と、利用者が実行を許可する行為を同一視しない。現行処理系には実行時の権限制御がなく、注釈の語だけから隔離を約束できない。`Log` のような利用者定義のエフェクトや、ハンドラで処理する作用も含むため、すべての項目を OS の権限とも呼ばない。

確認した範囲では、`can` に今回と近い先例があり、記号には多数の方式がある。`needs`・`may`・`performs`・`effects`・`does` を今回と同じ位置と意味で用いる先例は、本調査では確認できていない。「先例がない」と言語全体について断定するものではない。with と ZIO 1.x の関係は [file-effects.md 2.3・4節](file-effects.md#23-エフェクトを型に書く語記号と-with-の役割)の確認に従い、Scala 2 の `A with B` という複合型と、`-> T with A, B` という先頭の導入語を分ける。

今回変えるのはエフェクトの列挙を導く綴りであり、新しい理論概念の名前は導入しない。日本語の説明には既存の「エフェクト」「エフェクト変数」「契約」「権限」を使い続ける。他言語の contexts・abilities・reference capabilities を Benitoite の新しい術語に転用する案は推さない。

## 3. uses の懸念を事実と見込みに分ける

| 確認できた事実 | Benitoite で起こりうる取り違え（未測定の見込み） | 違いを説明する点 |
|---|---|---|
| Free Pascal のプログラムは `uses` 節で unit を使う。[公式 Quick Start](https://www.freepascal.org/_new/docs/quick-start/) | ファイルの `uses Console.Write, Log` が取り込みの一覧に見える可能性がある | Benitoite は `import` で名前を取り込み、uses で関数の契約を宣言する。Pascal 一般の標準機能という範囲には広げない |
| Delphi の uses 節は、依存する unit をカンマ区切りで並べる。[Programs and Units](https://docwiki.embarcadero.com/RADStudio/Athens/en/Programs_and_Units_%28Delphi%29) の The Program Uses Clause と Editor の例を2026-10-23のRS3対応で再確認した | ファイル先頭・カンマ区切りという形まで近くなり、関数末尾の注釈より取り込みを連想しやすい見込みがある | 効果宣言を置いても import を省略できず、名前の可視性も増えない。取得方法によって本文を取得できないことと、取得した本文で確認した事実は分ける |
| Rust の `use` はパスに対応する名前の束縛を作る。[Rust Reference](https://doc.rust-lang.org/reference/items/use-declarations.html) | use と uses の綴りの近さから、モジュールへの依存と解釈する可能性がある | 語も位置も完全一致ではない。Rust の先例だけから実際の混同率を主張できない |
| PHP のクロージャは `function (…) use ($x)` で外側の変数を捕捉する。戻り値型は use 節の後。[Anonymous functions](https://www.php.net/manual/en/functions.anonymous.php) | ラムダの uses が、値の捕捉や文脈の受け取りを宣言するように見える可能性がある | Benitoite の効果名は捕捉する変数の一覧ではない。PHP とは語・引数の形・型との順序が異なる |

`uses` 自体にも、「この関数はこれらの作用を使う」と名詞を目的語にできる利点がある。ただし、その読み方は実際に使う集合や必要な依存を連想させ、余分な作用を許す上限であることまでは伝えない。特にファイル単位で一律に書き足す決定によって、この弱点は従来より目立つ。

したがって懸念は、既存の uses が字句として曖昧だという事実ではなく、取り込み・捕捉・必要な依存という既習の意味と、今回の契約の意味との距離である。現行の `syntax/lexer.rs:789` は uses を専用のキーワードへ分類し、`parse_uses` は効果の位置でだけ読む。人間の誤読例や LLM の失敗例は今回採集していないので、懸念の存在から改名の効果の大きさへは飛躍しない。

## 4. Benitoite の位置に置いた比較

### 4.1 読みやすさと意味

各行の関数例は `function f(x: Integer)` に続く末尾、ファイル例は import 群の後に置く独立の宣言である。すべて同じ上限集合を指定する仮案とする。英語についての評価は調査担当の判断であり、英語話者・非プログラマによる読解実験の結果ではない。識別子 `Console.Write` は自然言語の句でないことも織り込む。

許可の読みは、三つの軸を分けて評価する。第一は計算が起こしうる作用の上限と読めるか、第二は人間がこの関数に許す操作の一覧と読めるか、第三は注釈を書くことで実行権限が付与され、実行時にも強制されると誤解されるか、である。第二は00-01の目的に合い、第三を避ける必要がある。can と may の両方に可能性と許可の用法があることは、[Cambridge の Can, could or may?](https://dictionary.cambridge.org/grammar/british-grammar/can-or-may)で確認した（2026-10-23、公式ページの検索結果に表示された Possibility・Permission の説明。直接取得は403となり、本文全体は未取得）。can だけ説明で解決できるとは扱わない。

| 候補 | 作用の上限としての読み | 人間が許す操作の一覧としての読み | 権限の付与・実行時の強制との誤解と、相対評価 |
|---|---|---|---|
| can | 「行いうる」という一般の可能性に結び付けやすい | 「この関数に行うことを許す」とも読め、目的に合う | 許可済み・実行可能と誤解される余地はある。mayと同じ説明が要る。上限との結び付きとAnteの同位置の先例を理由に第一候補とする |
| may | 「起こるかもしれない」と読めるが、個々の実行の推量にも読まれる | 許可の一覧とも読め、この点はcanと同じ利点を持つ | 権限の付与・強制との誤解はcanと同様に残る。低く置く理由は許可の読み自体ではなく、上限より個々の実行の推量を連想させるという未測定の判断である |
| allows | 関数の内部で許す作用の上限と説明できる | 許す操作の一覧であることは直接的に読める | 宣言・関数が権限を与える主体のように見える点を懸念する。これも読み方の仮説であり、実際の誤読率がcanより高いと確認したわけではない |

| 候補 | 関数の末尾／ファイルの宣言 | 英語の読みと、非プログラマへの説明 | 意味の一致・取り違えと評価 |
|---|---|---|---|
| `uses` | `-> String uses Console.Write, Log`／`uses Console.Write, Log` | 「これらを使う」。名詞の一覧を続けやすいが、可能性や許容上限は明示しない | 取り込み・捕捉との混同が懸念。移行不要という利点と分けて評価する。最終比較に残す |
| `with` | `-> String with Console.Write, Log`／`with Console.Write, Log` | 「これらを伴う」。名詞を続ける形は読みやすいが、何を伴うかは語だけでは分からない | 契約・処理するハンドラ・リソースの導入が同じ語になる。採用可能だが優先度は下げる |
| `can` | `-> String can Console.Write, Log`／`can Console.Write, Log` | 「これらの操作を行いうる」「この関数に許す」と読める。`-> String can E` は特に英文としての接続が弱い | 三軸の比較では上限との結び付きと Ante の先例を評価する。実行時に強制するという誤解への説明は may と同じく必要。改名の第一候補 |
| `may` | `-> String may Console.Write, Log`／`may Console.Write, Log` | 可能性と許可の両方に読める。can と同じく後続が名詞リストであり、英文としては省略がある | 許す操作の一覧という読みは利点。個々の実行についての推量に見える点で can より下に置くが、読解実験による順位ではない |
| `needs` | `-> String needs Console.Write, Log`／`needs Console.Write, Log` | 「これらが必要」。目的語は名詞として読みやすい | 呼び出し文脈に求める効果という読みに合うが、使わない作用も加えるファイル宣言を不可欠な操作と誤読しうる。推さない |
| `requires` | `-> String requires Console.Write, Log`／`requires Console.Write, Log` | 「これらを要求する」。必要な権限を申告するように読める | Dafny・F* の事前条件と競合する。作用の最小要件と上限も区別しにくい。推さない |
| `performs` | `-> String performs Console.Write, Log`／`performs Console.Write, Log` | 「これらを行う」。performs IO は説明しやすい | 毎回の実行を述べるように見える。型の契約と操作の実行を区別したいので、推さない |
| `effects` | `-> String effects Console.Write, Log`／`effects Console.Write, Log` | 「エフェクト: この一覧」という項目名として読める。英文の動詞として effects を読む場合は意図とずれる | 用語集との対応は利点だが、既存の dependency の effects 欄と字句・意味が衝突する（5.1）。第二候補という評価を撤回し、with より下に置く |
| `tags` | `-> String tags Console.Write, Log`／`tags Console.Write, Log` | 「付ける印の一覧」という項目名として読める | Nim に一般の作用の追跡の先例があるが、許す操作より任意の分類・メタデータに見える。effects の代わりの第二候補には推さない。forbids は禁止の一覧であり、今回の許す一覧の置換にはしない |
| `does` | `-> String does Console.Write, Log`／`does Console.Write, Log` | 「これらをする」。抽象名詞 Log・State に続く形は意味が薄い | 実行そのものと読まれ、可能性の上限を示しにくい。既存の `do` とも見分けにくい。推さない |
| `throws`・`raises` 型 | `-> String throws Console.Write, Log`／`throws Console.Write, Log`（raises も同形） | 「これらを送出する」。例外については既習の読み方がある | Console.Write・State を例外扱いする読みになる。Failure.Fail 以外も含む一般の一覧には推さない。Swift の async のように性質ごとの専用語へ分割する案も、一般のリストの置換にはしない |
| `using` | `-> String using Console.Write, Log`／`using Console.Write, Log` | 「これらを使って」。名詞は続けやすい | Scala の文脈引数や uses と同じ依存の読みが残る。新語への全面移行に対して改善点が弱い |
| `allows` | `-> String allows Console.Write, Log`／`allows Console.Write, Log` | 「これらを許す」。許可の一覧としては直接的で、目的に合う | 宣言が権限を付与する主体のように見える点から上位には推さない。can・mayと同じく、注釈と実行時の強制を分ける説明が要る |
| `!` | `-> String ! Console.Write, Log`／`! Console.Write, Log` | 見出しの意味を学ぶ必要があり、記号だけでは「許可する操作」と読めない | Eff の計算型・Roc の命名には近い形があるが役割は別。現在の否定への誤記診断も変わる。短さだけでは推さない |
| `/` | `-> String / Console.Write, Log`／`/ Console.Write, Log` | 結果型と作用を視覚的に分離できるが、除算にも見える | Effekt に近い区切り。単独のファイル宣言は意味を読み取りにくい。推す上位案には入れない |
| 角括弧 | `-> String [Console.Write, Log]`／`[Console.Write, Log]` | 一覧であることは見えるが、何の一覧かは語から分からない | 型引数と同じ直後位置になり、現行構文をそのまま使えない。Hack のように引数の直後へ移す別案も必要。今回の語の置換より広い変更になる |
| `\`・矢印内の集合 | `-> String \ Console.Write, Log`、または `->{Console.Write, Log} String` | 計算型に慣れた読者には区切りが明確。ファイル先頭の独立形は別途決める必要がある | Flix・Unison の先例があるが、Benitoite では新記号や区切りを導入する。今回の上位案には入れない |

can を選んだ場合も、次の四つの位置へ同じ語を置く。以下は注釈の配置だけの模式形であり、関数の本体を含む実行用の例ではない。ほかの一語の候補も、同じ位置で比較する。

| 位置 | can を選んだ場合の形 |
|---|---|
| 関数の宣言 | `function f(x: Integer) -> String can Console.Write, Log` |
| ラムダ | `lambda(x: Integer) -> String can Log` |
| 関数の型 | `function(x: Integer) -> String can Log` |
| ファイル単位の宣言 | `can Console.Write, Log` |
| エフェクト変数を含む契約 | `function apply[effect E](f: function() -> String can E) -> String can E`。束縛の `effect E` は維持する |

### 4.2 LLM の生成・修正についての仮説

既存言語との近さは、正しい構文を思い出しやすい利点と、異なる意味を持ち込む不利の両方を持つ。Java の throws がよく知られていると見込んでも、Console.Write を例外として生成すれば課題の成功には結び付かない。Ante に can の先例があっても、その語が学習データに多いことは確認していない。次の仮説に成功率の順位や数値を与えない。

| 候補の群 | 生成で期待する点（未測定） | 修正・混在で懸念する点（未測定） |
|---|---|---|
| uses の維持 | 現行 Skill、例、診断と同じ語で出力できる | 先頭の宣言を import と混同する、上限を使った作用の一覧と取り違える |
| can | 契約を「行いうる」と説明でき、Ante に同位置の先例がある | 旧資料の uses が残る、自然言語に寄せて `can use` や `can perform` と二語にする |
| effects / tags | 効果の一覧という見出しを覚えれば全位置へ使える | effects は dependency の記録との混同とキーワード化の衝突、tags は任意のメタデータとの混同が加わる |
| with / using | 既存の語やサービス要件の例を連想できる | ハンドラ・リソース・文脈引数の構文を持ち込む。with は既存のブロック境界にも影響する |
| may / needs / requires / performs / does / allows | 一般語による説明から表記を連想できる | 必須性・実行済み・権限付与など、異なる契約へ合わせて実装を変えてしまう |
| throws / raises | 例外の宣言・伝播には近い先例がある | 一般の作用を例外化する、Result と効果と例外を混ぜる |
| 記号 | 研究言語の型と似た形を生成できる可能性がある | ! を否定、/ を除算、[] を型引数として持ち込む。語の案より良いとの証拠はない |

## 5. 字句・構文・予約語との関係

### 5.1 既存の衝突と新しい識別子の制限

`syntax/lexer.rs:753` の keyword と `syntax/token.rs:25` の表では、上の語のうち uses と with だけが既存のキーワードである。ただし、キーワードでない語にも既存の構文の用途がある。effects は `syntax/header.rs:11` の EFFECTS と DEPENDENCY_FIELDS にあり、dependency の欄名として既に使う。do と effect は単数形で別の既存語である。標準ライブラリの `src/prelude/stdlib/**/*.bnt` の関数名・`名前:` の形の限定検索では、新候補と同じ宣言名・引数等は見つからなかったが、欄名 effects の衝突はこの検索から漏れていた。

| 構文の種類 | 確認できた現行の制約 | 採用時に要る判断・変更 |
|---|---|---|
| 新しいキーワード（can 等） | 現在は小文字識別子として使える。効果リストは大文字で始まる名前を読む（`parser/types.rs:257`） | 完全一致の語をキーワードにすると、関数・変数・ラベル・フィールド・import の別名・ドットの後の利用者名も制限される。名前の移行を別に調べる。canopy 等の部分一致は変えない |
| 先頭の部分の欄名 effects | 01-02「ファイルの先頭の部分」の dependency の effects は、最後に記録した組み込みの作用を表す文字列で、読み込み時に中身と照合しない。`parser/header.rs:221` の field は LowerIdent を要求し、01-01は欄名を予約しない | effects を全域キーワードにすると、内部名が KwEffects でも KwUses でも現在の欄解析を通らない。欄名を保つ特例と01-01の改訂、または欄名の移行が要る。can にはこの衝突がない |
| 既存 with | リソース、match、handle の三用途。`newline.rs:112` は case が続かなければブロックの開きを積む | 効果注釈の with をブロックと数えない規則が要る。戻り値が関数型、短いラムダ、改行・コメントを挟む形、誤記からの回復も揃える。パーサだけの単語交換では済まない |
| `!` | `TokenKind::BadSymbol` であり、現行01-01「演算子と区切り記号」は not の案内を出す | 注釈位置では合法、否定位置では従来の修正案という分岐が要る。`!=` や `//!` 等まで意味を変えず、字句の最長一致と改行の扱いを決める |
| `/` | 除算の字句であり、改行の前後を継続させる記号（01-01「改行による区切り」） | 型の注釈と式の除算を分ける。関数ヘッダの次行の `/` を注釈と見る範囲、誤記時の回復を固定する |
| `[]` | 型名の直後の型引数と、リスト等に使う。`parse_uses` 内でも Fail[E] の型引数を読む | `String [Console.Write]` は現行なら String への型引数の形になる。同じ場所への単純置換はできない。`function f()[Console.Write] -> String` 等へ位置を移すか、別の区切りが要る。内側の Fail[E] と外側の一覧も区別する |
| `\`・`{}` を含む形 | 現行では合法な区切りに含めない | 新しい字句・括弧の対応・整形・診断と型の結び付きの規則を増やす。先頭でのファイル宣言も独立に定める |

effects の二用途は、`dependency Textkit … effects "Console.Write" … end dependency` という依存の記録と、トップレベルの `effects Console.Write` という自ファイルの契約の追加である。ブロックの内外と引用符から構文的には区別できるので、文法上の曖昧さとは断定しない。一方、先頭部分に同じ語で、記録した文字列と実効的な上限の二種類が現れることは、人間・LLMの取り違えの懸念になる（原則3・4）。この懸念の発生率は未測定である。

effects をなお採る選択肢は、欄名の位置でキーワードを許す特例、文脈語として読む案、依存の欄名の変更である。特例なら01-01の「欄名を予約しない」との関係を明示し、`header_ahead`・回復まで確認する。文脈語でも二用途の意味の違いは残る。欄名の変更なら package の記録・更新（`cli/tools/package/mod.rs` と `edit.rs:109`）、E0929、現行文書と移行案内を改める。CHANGELOG 0.0.5 の過去の仕様は書き換えず、今回の移行項目から旧欄との対応を案内する。この追加費用は7節で別扱いとし、衝突を解消する案が未採用の現状では第二候補に戻さない。

新語は、字句の種類を現在の `TokenKind::KwUses` に対応させれば、`newline.rs:248` の改行継続、`lambda_bounds.rs:228,344` の短いラムダの境界、パーサの同期点を使い続けられる。したがって、これらを改造する費用を全域の新語へ無条件に加えない。内部の種類を KwCan 等へ改名する場合でも、意味を変えず参照先を揃える作業と、with のブロック判別の新規則を作る作業は分ける。「衝突しない新語」は、利用者名の非互換性までないという意味にはしない。

### 5.2 文脈だけで読む案と 0.0.6 の整理

[01-01「キーワード」](../../../design/01-spec/01-01-lexical.md#キーワード)は「キーワードでない予約語はない」とし、as、language、permissions 等を特定位置だけで読む。この方針は、新しい構文に必要な語をキーワードにすることを禁じていない。0.0.6 で die を導入した際も、利用者名の変更を [CHANGELOG の移行案内](../../../../CHANGELOG.md#006-san-benito)に記している。

新語を全域のキーワードにするか文脈で読むかと、旧 uses をいつ識別子へ戻すかは、別の言語の規則である。新語だけを全域にしても、旧 uses を識別子に戻して位置を限った移行診断を出すなら、旧語のための文脈判定が要る。この費用を初稿では落としていた。

| 対象 | 選択肢 | 利点・負担と推す案 |
|---|---|---|
| 新語 | 全域のキーワード／注釈の位置でだけ読む | 全域を推す。内部の KwUses に対応させれば既存の解析・改行の判定を保てる。文脈語なら `can()` 等の普通の呼び出しと注釈を分け、改行の前処理と回復の位置を決める必要がある。追加分を Δ新語文脈 とする |
| 旧 uses | 一つの版だけ移行診断用のキーワードとして残す／今回から普通の識別子へ戻す | 一版残す案へ改める。旧注釈は成功として受理せず、診断と安全な編集だけを出す。名前の位置ではキーワードを使った誤りとして断る。新旧の綴りを KwUses へ対応させ、注釈位置では元ソースの綴りを区別する案なら、既存の境界判定を利用できる |
| 旧 uses を今回から戻す別案 | `uses()` 等は普通の名前、旧注釈の位置だけ診断 | 新語を文脈で読む案と同様に、LowerIdent へ戻した後の改行・短いラムダ・回復の処理が要る。新語が全域の場合にもこの追加分 Δ旧語文脈 は残る。無料の付随作業とは扱わない |

旧語を一版残す案は、旧構文を成功として残す別名ではないので、原則5の同じ役割の受理構文は一つに保てる。一方、通常の構文として使えない語を名前にも使わせない期間を設けるため、01-01と0.0.6の予約を減らす方向に対する期限付きの例外として、設計者が明示的に選ぶ必要がある。採用する版と次の版での解除を記録し、恒久的な予約へ延長しない。解除後も同じ精度の旧注釈の診断を続けるとは約束しない。続けるなら、その時点で文脈判定の費用を計画する。

文脈判定の実行時の振る舞いは、今回の読み取りだけでは確定していない。ただし、`uses` の直後の改行は `newline.rs:248` の継続対象であり、LowerIdent に変えれば同じ扱いにはならない。`-> String` の次行に uses を置く例は別で、現行でも uses は `continues_before` に含まれず、同じ許容例として扱えない。採用後は、旧来の正常な `uses` の直後の改行と、もともと不正な次行の uses、括弧内の関数型、短いラムダ、普通の識別子の呼び出しを分けて再現を確認する。机上の懸念だけを理由に現在の規則を変更しない。

`UsesList` や AST の `uses` という内部の欄名は、公開する構文・交換の契約でない限り、全件改名を必須としない。型に持つ集合を同じまま解析できれば、型検査器の本体を綴りに合わせて作り直す必要はない。一方、`cli/tools/skill/generate.rs:454` の署名文字列の生成や、`:506` の元ソースからの署名の切り出しは、内部名を保っても外へ出す新構文に揃える必要がある。

### 6.2 共通の移行器と旧 uses の案内

[tools/source-migrate](../../../../tools/source-migrate/README.md)のホスト抽出、元の UTF-8 バイト範囲への対応、SHA-256、編集範囲と diff、確認済み manifest、適用・再適用の検証を再利用できる。候補の意味・採否、生成物や過去記録を編集しない方針は各移行器の責務である。共通ライブラリは意味を判定する CLI ではなく、Markdown のインラインのコードや説明文の分類も自動では行わない。

| 移行の種類 | 構文から作る編集 | 一括置換では扱えない部分 |
|---|---|---|
| (a) 新語 | 旧パーサまたは旧形を識別できる読み取り器で注釈の uses の範囲を取り、新語へ置換 | 新語と一致する利用者の識別子は別の名前と参照へ改める必要がある。文脈語案ならこの非互換性を減らせるが、位置判定の実装が増える |
| (b) with | 注釈の uses を with へ置換 | 既存のリソース・match・handle の with はそのまま。改行・括弧・短いラムダで新形を解析し直して、意味が変わっていないことを照合 |
| (c) 記号 | ! や / の単純な区切りなら注釈範囲の交換。[] や矢印内集合なら、リストを囲む範囲・移す位置も編集 | 閉じ記号の欠落、型引数、入れ子の関数型、Rust のエスケープ、文字列内の ! や /、診断の位置の変化を扱う。複数文字への変更はバイト位置もずれる |

旧い `function f() -> T uses E` は、新しい綴りと編集を示す構文診断にする案を推す。5.2の一版残す案では、旧語も KwUses として切り出し、`Parser::snippet`（`syntax/parser/mod.rs:863`）等で注釈の元の綴りを見て拒否する。ラムダ・関数型にも同じ案内を出す。名前の位置では E0216 と同様にキーワードを名前にできない理由を示す。既存の E0216 は die の専用処理を含むので、番号や共通化の方法は計画で決める。壊れたリストに安全な範囲が得られなければ、診断だけを出して編集は付けない。旧注釈を一つの原因として回復し、その後の本文へ不要な連鎖診断を増やさないことも受け入れに含める。

ファイル単位の uses は現行版に存在しない。今回 can 等へ直接決めるなら、「旧ファイル宣言 uses からの移行」が既にあるようには案内しない。新しい宣言の先頭で uses と誤記した場合の案内は、新構文への誤記診断として設計する。

旧版を指す language の宣言に対する E0908 の移行案内と、注釈位置の診断は別に整える。版の文字列を変えても旧コードが移行されたことにはならず、旧パーサを選んで実行する機能にもならない。依存内容が変われば package の記録のハッシュも更新する。`effects` の報告にある効果名・集合は維持し、ソースの導入語の変更を理由に報告の schema や `--allow-effects` の意味まで改名しない。

### 6.3 同梱物と形式化

同梱 Skill は、手書きの SKILL.md と参照文書の生成入力を先に直し、文法・診断・標準ライブラリの生成参照を作り直す（`examples/gen_skill.rs`、`cli/tools/skill/generate.rs`）。新語への統一を、本文だけでなく、LLM に提示される例と診断の help まで揃える。tools/skill-eval の課題の更新と、LLM を呼ぶ評価の実行は分ける。今回後者は行わず、将来の比較では各候補と同じ語に揃えた Skill・課題を使う。

生成器と型の表示は別の編集対象である。`types/mod.rs:713` の型の表示、`tools/derive/derive.py:264` の契約を表す文字列と`:559`の生成する関数型、`cli/tools/skill/generate.rs:454` の固定の署名を新語へ揃える。try-actions の inventory は `examples/try_actions_inventory.rs:18,215` で元ソースの注釈範囲を読むため、新しい範囲を保てるか確認し、`tools/try-actions-migrate/migrate.py:214` の contract_changes の内部キー uses やJSON欄まで無条件に改名しない。生成記録の契約・ハッシュと外へ出す構文の綴りを区別して照合する。

英語の地の文は、構文の案内を「can の後の一覧」のように採用語へ揃え、作用を説明する本文は「計算が起こしうる作用の上限」という意味へ揃える。`docs/reference/benitoite.md` の Effects 節、診断の note・help、Skill の説明を対象とし、引用したキーワード以外の一般動詞 uses や performs を機械的に can へ変えない。許す一覧と実際に生じた作用、利用者の許可と実行時の強制の区別は語を変えても同じに保つ。この編集範囲は計画で照合し、別の言語仕様の採否にはしない。

ゴールデンでは、正常入力を新語に移すだけでなく、旧形を拒否する観測を残す。旧形の字句位置に関わる表示・JSON・自動編集と、整形の期待値を再確認する。docs/ja はリリース候補で英語の正本に合わせて訳し直す。docs/archive や、tools の過去の測定・評価結果を現行構文に直して過去の証拠を変えない。

語だけを改める場合、Lean の定義・定理・交換形式の変更は0件の見込みである。根拠は `formal/Benitoite/Surface/Syntax.lean:504` の FunDecl が完成した `eff : Eff` を持ち、ラムダも同じく Eff を持つことである。`Surface/Check.lean:859` の checkDef と `Surface/CheckTables.lean:219` の checkProgram は、その情報を検査し、uses という字句を解析しない。formal にある uses の1出現は `Surface/Desugar.lean:461` の説明コメントである。

ただし、具体構文を含む Rust 側の交換入力の読み取り・生成は変わる。新語と旧語から移行した入力が同じ型・効果・脱糖結果を作ること、ファイル宣言の合併後の集合と NoFail 条件を E2 へ渡すことは回帰確認が要る。07-04「01-12 との対応」に従い、語の置換を効果の意味の保存の新しい証明とは呼ばない。今回の改造には TODO-273 の Lean 先行が別にあり、その費用が0になるという見積もりでもない。

## 8. 今回決める範囲と推す案

[file-effects.md 4.4](file-effects.md#44-予約語の整理との関係と結論)は uses の維持を推している。本書も、未測定のまま無条件に改名する結論にはしない。同資料に対して、取り込み・捕捉との取り違えの具体例、一律追加に伴う上限の読み、Ante の can の同位置の先例を比較材料として加えた。これらは読み方を理由に改名する候補を絞る根拠であり、uses より生成成功率が高いという証拠ではない。「維持するなら uses、改名するなら can」という条件付きの判断で両立させる。effects は既存の欄名との衝突を踏まえ第二候補から外す。file-effects.md 自体は変更しない。

また、同資料4.4の「旧 uses をすぐ識別子に戻し、位置を限って移行診断を出す」案には、5.2の文脈判定と7.3の追加費用の留保を補う。本書は一版だけ診断用キーワードとして残す案を推すため、この点は元資料と異なる。恒久的な予約はどちらも推さず、一版の例外を設計者が選ぶ必要がある。元資料の案がそのまま無償で実装できるという扱いにはしない。

改名を選ぶなら、今回の改造に含め、ファイル宣言も最初から同じ新語にする案を推す。README で決めた一度の版上げに、既存注釈・同梱 Skill・移行案内・依存ハッシュの更新をまとめられるからである。先に uses のファイル宣言を公開して後で改名すると、その位置も次回の移行対象になる。ただし、測定で再変更すれば利用者の移行も増える。

測定なしで選ぶ場合は、人間の読み方と意味の対応による暫定判断として記録する。00-01「構文の判断基準」は期待結果まで含む生成・修正の成功率を求めており、先例の類似だけでは改善を断定できない。docs/todo の TODO-017 の第二段階、TODO-019 の効果名・エフェクト変数・ハンドラを含む題材の比較は未実施のままである。

測定を先に行うなら、まず uses と can に絞る案を推す。関数・ラムダ・関数型・エフェクト変数・ファイル宣言の全位置で、過大な IO.All へ広げずに課題の期待結果を満たすか、診断から修正できるかを比べる。各候補の Skill と診断を同じ品質にし、モデル・ハーネスの版と試行数を固定する。非プログラマによる「起こしうる作用の上限」「許す操作」「実行時に強制される範囲」の理解は別に確かめる。計画・時間・費用は不明であり、今回 LLM を呼ぶ評価は行わない。

| 論点 | 選択肢 | 推す案と理由 | 互換性・形式化への影響 |
|---|---|---|---|
| 語 | uses／can／with／effects／その他・記号 | uses と can を最終比較に残す。改名するなら can。上限の読みと同位置の先例が理由。effects は欄名の衝突から with より下に置く | 改名は既存注釈を壊す。全域の新語は利用者名も制限。綴りだけなら Lean 定義・定理・交換形式の変更0件の見込み |
