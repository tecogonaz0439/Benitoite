# エフェクトを宣言する語についての設計者への問い

2026-10-23、S3。[調べと比較](effect-keyword.md)の判断案であり、決定ではない。[改造 README](../README.md#設計者の決定2026-10-23)の一律追加の意味を保つ。

## 1. 語と決める時期

**最終比較は uses と can。改名するなら can を推す。** 読み方と意味の対応による判断であり、LLM の成功率の改善は未測定である。

| 語 | 関数末尾／ファイル宣言の例 | 評価 |
|---|---|---|
| can（改名なら推す） | `-> String can Console.Write`／`can Console.Write`。変数は `-> String can E` | 「行いうる」という上限の読みと Ante の同位置の先例。`can E` は英文として弱い。許す操作の一覧とは読めるが、権限付与・実行時の強制とは分けて説明する |
| uses（維持するなら推す） | `-> String uses Console.Write`／`uses Console.Write` | 移行不要。[file-effects.md 4.4](file-effects.md#44-予約語の整理との関係と結論)の推す案。取り込み・捕捉・実際に使う依存との混同は懸念にとどまる |
| with | `-> String with Console.Write`／`with Console.Write` | 既存のリソース・match・handle との判別と改行の規則の変更が要る |
| effects | `-> String effects Console.Write`／`effects Console.Write` | dependency の既存の `effects "Console.Write"` と字句・意味が衝突する。第二候補から外す。解消案の追加費用は不明 |

| 時期の選択肢 | 推す条件・留保 |
|---|---|
| A: 今回 can を暫定採用 | 読み方を根拠に決めてよいなら推す。ファイル宣言も初めから同じ語にし、一度の版上げにまとめる |
| B: uses と can を測定してから決める | 成功率の実証を条件とするなら選ぶ。測定の時間・費用は不明で、別計画と了承が要る |
| C: 今回は uses のままファイル宣言を加える | file-effects.md の推す案。今の移行を省けるが、後で改名すればファイル宣言も移行対象になる |

どの語でも関数・ラムダ・関数型・ファイル宣言に統一し、`effect E` の束縛は変えない。原則4・5に従い、契約の明確さと成功する表記の一意性を保つ。綴りだけなら Lean 定義・定理・交換形式は変更0件の見込みで、Rustからの接続の検査は要る。

## 2. 改名する場合の新語と旧語

| 論点 | 推す案 | 別案・互換性 |
|---|---|---|
| 新語 | 全域のキーワードにする。内部の KwUses を保つ | 同じ利用者名は改名が要る。文脈でだけ読むなら普通の呼び出しと注釈を分ける追加費用は不明 |
| 旧 uses | 一版だけ診断用キーワードとして残し、旧注釈は拒否して移行診断・安全な編集を示す。解除する版も決める | 名前にも使えない一版の例外を01-01に明記する。すぐ識別子へ戻す案は、改行・短いラムダ・回復の文脈判定の追加費用が不明。旧形の成功としての受理・恒久的な同義語は推さない |

## 計画で決める点

- 英語の地の文・診断・Skillの構文の案内を「can の後の一覧」へ揃える。一般動詞 uses／performs の機械的な置換はせず、作用の上限・利用者の許可・実行時の強制を区別する。
- 移行器の入力分類、生成元と生成物・契約の記録、旧語の診断と解除の作業、検査の基準・割り当てを固定する。長い検査・測定・公開候補の最終受け入れの不明な時間は別途見積もる。

| 対象群の作業量（実測ではない） | 実装・文書 | 局所検査・レビュー・作業の受け入れ照合まで |
|---|---:|---:|
| uses 維持 | 9〜18時間 | 15〜30時間 |
| can 等の衝突しない新語。内部の KwUses と旧語の一版の予約を保つ | 13〜25時間 | 21.25〜41.5時間（約21〜42時間） |
| with | 14〜27時間 | 従来の比較枠で約22〜44時間。旧語をすぐ識別子に戻して診断を保つなら追加は不明 |
| 文脈語・記号・effects | 新語の範囲を比較の基準とする | 文脈判定・記号の規則・欄名の衝突の解消の追加は不明 |

[本文7節](effect-keyword.md#7-作業の大きさと時間の見込み)に内訳と試行の限界を示す。新語の追加は実装・文書4〜7時間、検査1〜2時間、レビュー1〜2時間、受け入れ照合0.25〜0.5時間の計6.25〜11.5時間。対象はファイル宣言と誤り回復の群であり、TODO-273・272を含む全改造の総時間ではない。計画・事前レビュー・回答待ち、形式化の全比較・change・release・最終受け入れ、LLM測定は合計に含まない。
