## 依頼する内容

最初に AGENTS.md を読み、指定した作業を計画の目的・対象ファイル・完了条件に従って実装する。一作業は機能のまとまりで30〜60分を目安とする。処理系と設計書・生成物を同じ状態へそろえ、未接続の仮置きを機能全体の完了にしない。A1・L2a・F2・F4aの途中状態はplan.mdの一時防御を必須とし、防御を外す後続IDと未接続の範囲をresults.mdへ渡す。各分割IDは別セッションとし、30〜60分は所要時間の予測ではなく継続を判断する仮予算として扱う。

TODOの必要な範囲はplan.mdとdecisions.mdへ写した。docs/todoを読む必要はない。READMEの二つの設計者の決定を確認し、`uses` の改名を混ぜない。標準ソースはファイルの宣言を使わない規約を守り、生成されたトップレベル関数には通常の合併後の契約を適用する。数と幅の本体はVM・Wasmtimeから独立させ、構成によって型とエフェクトの意味を変えない。利用者向けの説明はハーネス経由の検査報告と実行を中心に置く。

LeanのL1・L2a・L2b・L3では、主な定理の前提・結論の変更、公理（Builtins.Assumptionsを含む）の追加が必要と判明した時点で当該作業を止め、変更が必要な言明・行き詰まった場合・代案を取りまとめへ報告する。補助補題の変更を主定理の変更へ広げない。F0はB0直後、L1の前にscratchだけで行い、本番のソースは開始時と同一に保つ。F1以降の形式化の内側の実装はLean段の既定ビルドと定義・言明・仮定のレビューが通るまで始めない。停止中も取りまとめはW・A・Cの独立した作業を選べるが、その取り込み・short・レビューを終えたら報告して待ち、G1・Z1や版上げへ進まない。言語の規則そのものを変える必要が出た場合は決めずに記録する。

作業途中は、関係するテストだけを Cargo 等で直接実行する。作業末は、計画の work 行にある `scripts/check.sh --level work --base <基準> [--test <関連ターゲット> ...]` を一度実行する。計画に名指しの `--only` があればそれを使う。Rust の作業末の既定の lib 全件・関連統合テスト・clippy・fmt はこの入口に任せ、直接のコマンドを重ねない。work が未実装の移行中だけは計画の直接のコマンドを使う。文書だけ・シェルや Python だけ・Lean だけの作業に Rust の全 lib を追加しない。Leanのworkも自動分類で01-12の例と集計を含める。F2より前は新書式の表層の例を01-12のtextフェンスへ追加しない。check.shは文書のリンクや作業IDを検査しないため、文書の静的確認は計画の別手段で行う。

検査前に種類を知らせ、計画で固定した基準と指定へ `--dry-run` を付け、選択と理由を確認する。長い検査・heap・全件の特殊構成を含む場合は見込み時間も知らせる。変更範囲が増えたら、入力を読む側と必要な構成を含めて計画の検査を更新する。共有の入力を変えたときは、その入力を読む全統合ターゲットを指定する。`--test` は統合テスト名ごとに繰り返し、Rust の自動 work で省略すれば全統合ターゲットとなる。

ヒープの不変条件や安全点を越える値を変える作業では、局所の heap-verify・gc-stress と必要な `check-heap.sh` を、次の作業の前提にする前に通す。形式化の内側では 07-04 の Lean 先行を守り、既定の `lake build` が `sorry` なしで通ることと、定義・言明・仮定のレビューを処理系へ進む条件にする。Rust と Lean の全比較は、計画で接続を閉じる区切りと最終の関係状態に割り当てる。

作業の完了のために段・改造・リリースの全件検査を先取りしない。S-W・S-Cと条件を満たすS-Fは、計画に従って最後のworkを引用し、同じ対象を繰り返さない。失敗の修正や関係する追加変更の後は、古くなった検査だけを再実行し、初回の失敗と修正も残す。テストの期待値・大きさ・ignore・時間制限を緩めない。テストを加える・変えるときは test-audit の作成時の関門を通す。

普通の作業の results.md は、基準のコミット、走らせたコマンド、終了状態、外側の時間、計画からのずれと申し送りだけを記す。失敗した場合は原因と修正も残す。結果を引用するときに限り、07-03「結果の保存と引用」の全欄を記す。基準と HEAD の完全な ID、差分の有無と一覧、コマンド・構成・入力・ツールチェーン・件数・終了状態・時間・環境の制限、元の記録、以後の変更、関係状態が一致する理由、判断者と日付を残し、別の状態への引用には未コミット差分と未追跡入力の SHA-256 も保存する。未実施は担当と時期を明記し、この作業が受け持つ失敗を後へ送って完了にしない。

自動分類が終了3で停止したら、分類不能のファイルまたは存在しない基準を示し、規約に従って設計者へ当該水準の `--level … --only`（停止までに選んだ単位を案内し、分類不能のファイルに必要な単位を補う）、互換の `--full`・水準なしの `--only`、`--none` のどれで続けるかを尋ねる。計画に既に名指しがあればその指定で進める。`--level` と `--only` の併用は分類せず、名指しだけを実行する。指定の誤りは終了2として計画を直す。検査失敗と道具不在は1、選んだ検査の成功は0であり、水準全体の完了とは区別する。release は候補と証拠の手動照合も要る。

結果を指定の results.md へ記録し、最後に変更したファイルの要約、検査と結果、計画からのずれ、後の作業への申し送りを日本語で短く報告する。コミット・取り込み・docs/todo の更新・公開の操作は「作業の指定」の明示の指示に従う。
