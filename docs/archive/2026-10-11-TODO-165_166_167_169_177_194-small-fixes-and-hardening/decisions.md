## Q1 `Json.parse` の直し方（TODO-194）

- A（推奨）: serde_json の機能 `arbitrary_precision` を外して `float_roundtrip` を付け、`serde_json::Value` でなく自前の `Visitor` で値を組み立てる。入力を字句として走査して文字列の外の数の字面を文書の順に並べ、`Visitor` が数を受け取るたびに次の字面を今の規則（`number_value`）で分類する。字面が合わないときと範囲外の数は、`Visitor` の誤りとして `Result.Error` にする。
- A': `arbitrary_precision` を外し、`serde_json::Value` をそのまま使う。serde は `-0` を `-0.0` として渡すので、03-08 の「`-0` は `Json.Value.Integer(0)`」を「`Float(-0.0)`」に変える（互換でない変更）。
- B: 自前の JSON の構文解析器を書く。serde_json は処理系の依存から外れ、テストだけの依存になる。

理由: A は、03-08 の数の規則（`-0` と `-0.0` の区別、範囲外の数の誤りと位置、`u64` を超える整数の字面は `Float`、Float の往復）と、誤りの文言と位置を保ち、変える範囲が `json.rs` と Cargo.toml に収まる。JSON の文法の検査は既存の OSS に任せたままにできる（AGENTS.md「目的の衝突」）。字面の対応が万一崩れても `Result.Error` になり、処理系の不具合には戻らない。A' は利用者に見える規則を変え、B は文字列の逃がし方・深さの上限・誤りの文言をすべて書き直すので作業が大きい。調査の試しのクレートで、A の形が特殊なキーの object を object のまま読み、`-0` と `-0.0` を分けることを確かめた。

## Q2 誤りの報告の順（Q1 で A のとき）

- 受け入れる（推奨）: 構文の誤りと範囲外の数がどちらもある入力（`[1e400,}` など）で、文書の順で先の誤り（範囲外の数）を報告するように変わる。
- 今の順を保つ: 構文の誤りを範囲外の数より先に報告する処理を足す。

理由: 03-08 は順を定めておらず、先の位置を示すほうが直しやすい。

## Q3 fmt が 0444 のファイル・固いリンクのあるファイル・所有者の違うファイルを置き換える件

- (a)（推奨）: 拒んで、ファイルを書けない誤り（E0125）として理由とともに報告する。
- (b): 置き換えることを 06-01 と言語リファレンスに書く。
- (c): 0444 と所有者の違うファイルは拒み、固いリンクは置き換えることを書く。

理由: 0444 は利用者が書き換えを望まない印である。固いリンクを黙って切ると、もう片方の名前に古い中身が残ったことに気付く機会がない。拒んでも、許可を変えれば整形できる。

## Q4 panic の境界で囲む範囲（TODO-167）
