## L1 エフェクトと標準モジュールを何と呼ぶか

選択肢:

- A: エフェクトの正規名を Log、標準モジュールを Benitoite.Unofficial.Log とし、prelude から uses Log と Log.info を使えるようにする。
- B: 現在の名前解決だけで扱える Log.Output と Log.info にする。
- C: Console.Write にログを含め、独立したエフェクトを作らない。

推す案はAである。理由: ログを書く契約を出力先から分け、利用者のハンドラにより差し替えられる。uses Log を短く書く設計者の方針にも合う。

Aは名前解決の追加を伴う。現行の final_name は、標準モジュールと同名の宣言を Effect の位置で選ばない。標準モジュール内の同名エフェクトを選ぶ一般の規則を足し、Log.info のモジュール解決と併存させる。ソース宣言の完全名Log.Logから正規の表示名Logへの変換も、型表示・許可名・JSON報告・公開契約の集計で揃える。根の束縛でモジュールを隠す実装にしない。これは暗黙のエフェクトを採る判断ではない。[調査2.3節](riders-a.md#23-名前と操作の案)

## L2 Log の操作と値の形をどうするか

選択肢:

- A: Log.emit(record: Log.Record) -> Unit と Log.enabled(level: Log.Level) -> Boolean の二操作にする。
- B: emit だけにし、捨てるメッセージの構築も通常の引数評価に任せる。
- C: debug/info/warn/error をそれぞれ独立した操作にする。

推す案はAである。理由: 水準・メッセージ・属性・位置を一つの記録として受け渡せ、重いメッセージを作る前に水準を問い合わせられる。

Record は普通の公開レコードとし、利用者のハンドラは両操作を処理する。既定の enabled と emit は同じ最低水準を使う。問い合わせは出力の予約ではなく、その間の利用者の状態変更まで防がない。Cの補助名は通常の標準関数として提供する。[調査2.3節](riders-a.md#23-名前と操作の案)

## I2 有界の整数を Lean でどう表すか

選択肢:

- A: Const.integerとSurfaceの整数リテラルに符号付き64ビットの値を使い、区間計算では数学上のIntへ戻す。
- B: 型付きの全値と実行状態へ、整数の表現可能性の述語を追加して保存を証明する。
- C: 現行Intのまま、網羅性定理を実装の入力に限る追加仮定付きへ弱める。

推す案はAである。理由: 有効な値の全体と網羅性の定理の範囲を一致させ、値の上限を毎回別の仮定で運ぶ必要を減らせる。

モデル案は { n : Int // −2^63 ≤ n ∧ n ≤ 2^63−1 } である。Surfaceの正の大きさは2^63−1以下、直接の負号の大きさは2^63以下に分け、最小値を表せる形を保つ。max+1を有限の値へ戻さず、端点の計算だけに使う。演算のあふれの不在を新しく証明する範囲にはしない。入力の読み込みで範囲外を拒否するだけでは不十分である。[調査3.2節](riders-a.md#32-有界のモデルを先にそろえる理由)

## C2 長さの検査の対象と単位をどうするか

- C: 型引数が変わる再帰、任意のdata、モジュール間の再帰も初版から全て含める。

推す案はAである。理由: 対象TODOの再帰と多相の双方を進めながら、生成する値の有限性を宣言から判断できる範囲に絞れる。

必須欄だけの循環で有限値が作れない場合は生成前に拒否する。Nest[List[T]]へ進む型引数が変わる再帰と、高カインド・関数・リソースを通る再帰は対象外と明記する。通常の言語で書ける型や手書きの関数まで禁じない。[調査5.2節](riders-a.md#52-再帰するレコードの生成器)

## P2 大きさ0と生成の予算をどう決めるか

選択肢:

- A: 有限の最小基底を先に求め、sizeを基底より増やせる再帰節点数として子へ分配する。
- B: 各子へsize−1を同じように渡し、深さだけを制限する。
- C: size=0では生成を実行時エラーにする。

推す案はAである。理由: 多分岐の木の増え方を抑え、Gen.runがsize=0でも値を返す契約を保てる。

子の生成器はrunまで作成を遅らせる。各必須欄の最小量を予約し、残りだけを配る。再帰するListの各要素へ同じ残量を複製しない。これは再帰節点の予算であり、独自の生成器の停止や全記憶量の保証ではない。[調査5.2節](riders-a.md#52-再帰するレコードの生成器)

## P3 型パラメータの生成器と縮小器をどう渡すか

選択肢:

- A: 必要な型パラメータのGen/Shrinkerを普通の引数に取り、必要なequality/keyとShow/Orderの制約を署名へ出す。
- B: 新しい型クラスを使って全て暗黙に解決する。
- C: 全パラメータをStringかIntegerへ固定して生成する。

推す案はAである。理由: 要素の分布と縮小方法を呼ぶ側が選べ、通常の型付き関数として検査できる。

Box[T]のGenは要素のGen[T]を受ける。List/Option等の標準縮小器が求めるequalityは必要な位置だけに伝える。phantomのパラメータへ不要な生成器を要求しない。辞書や種類の新しい規則は追加しない。[調査5.4節](riders-a.md#54-型パラメータを持つレコード)

## P4 縮小と Show・Order の再帰をどう扱うか

選択肢:

- A: 子を削る候補と一欄ずつの縮小を遅らせてつなぐ。Show/Orderは通常の再帰関数と制約付きimplementを生成する。
- B: 縮小器だけは再帰に対応せず、常に候補なしとする。
- C: 再帰する辞書をコアの新しい値として導入する。

推す案はAである。理由: 既存のShrinkStepと通常の実装を使い、再帰型のためだけの型付け規則を加えずに済む。

生成した標準縮小では、構造の削除と葉の縮小の順序を定め、同じ値を往復する候補を作らない。maxShrinks/maxShrinkWorkは保ち、利用者のコールバックの時間と最小反例は保証しない。Show/Orderの依存は、生成予定のまとまり内のシグネチャと外側の制約で閉じるかを確認する。型に循環があるだけで拒否する現行検査を、無条件の受理には変えない。[調査5.3節](riders-a.md#53-縮小の停止と-showorder)

## P5 循環する依存の記録と移行をどうするか

選択肢:

- A: 到達する宣言と型引数付きの辺を名前ごとに一度だけ記録し、生成規則・意味のハッシュと必要な契約の版を更新する。通常のpreview/review/apply/checkを保つ。
- B: 循環の先のハッシュを省き、最初の宣言だけを見る。
- C: 同じ型名なら古いmanifestで新しい生成を適用できるようにする。

推す案はAである。理由: 子や相互再帰の相手の変更を見逃さず、確認した差分だけを適用できる。

基底・予算・生成関数の引数・制約・選んだ実装も記録する。旧本文のハッシュの照合後に新しい案を出し、旧manifestの受理はしない。JSONの再帰・多相対応は含めず、同時指定の非対応を機能別に拒否する。[調査5.5節](riders-a.md#55-生成記録と移行)

## P6 専用の Property 実行を今回含めるか

選択肢:

- A: 含めない。普通の@testからConfig・Property.check・formatFailureを明示して使う。
- B: 種を指定するCLIだけを足し、内側のConfigを上書きする。
- C: 専用入口・Configの受け渡し・CLIの優先順・構造化した反例と報告の版を一組で加える。

推す案はAである。理由: R12の隠れた入力の問題は残っており、再帰・多相の生成を完成させる方に作業を使える。

専用実行は形式化の重さだけで除くものではない。Cは3〜5作業・10〜20時間の追加案として比較する。含める場合は任意のTの反例を構造化する変換も明示し、Showの文字列をその代用にしない。種・Config・生成規則とライブラリの版を保存し、具体的な反例を固定テストにする現在の案内は保つ。[調査5.6節](riders-a.md#56-専用の-property-cli)
