## R13 一度目の中断で Writer の何を確かめるか

選択肢:

- A: with 内で短い内容を書き、準備行の時点で未書き出しを確認し、SIGINT／SIGTERM 後の終了 130 と全内容を両 IO 方式で検査する。

## R14 解放中の二度目の SIGINT をどう受け入れるか

選択肢:

- A: 本物の File.Writer と親が制御する FIFO の同期を先に試作し、解放の開始と完了できない状態を確認してから二度目を送る。同期を実現できなければ未達として判断へ戻す。
- B: 既存の標準出力を止めるテストを、Writer の解放の検査としても数える。
- C: 準備行後の固定 sleep と連続する二回の SIGINT で代用する。

推す案は A である。理由: B は別の契約を検査しており、C は受信や解放の進行を示さない。失敗する理由を時間のばらつきから区別できる同期が必要である。

同期は未試作であり、成功を約束しない。実装時は最初にこの前提を確認する。runtime のリソースの境界で解放を止める検査は補助として使えるが、File.Writer の別プロセスの検査と区別する。二度目は OS の既定のシグナル終了を求め、正常な解放と同じ終了 130 を期待しない。[調査 8 節](riders-bc.md#8-todo-168-中断と-writer-の解放)

## R15 参照インタプリタの橋渡しで共有を保つ範囲

選択肢:

- A: 双方向の変換に対応表を持ち、構成子・List・Map・Set・文字列・Bytes の同じ対象を再変換しない。表は一つの呼び出しの区間に限る。

推す案は A である。理由: VM のヒープを独立した評価器へ持ち込まず、実在する対象に比べて変換が指数的に増える原因を除ける。

## R16 差分テストから外す基準をどうするか

## R17 test の外部関数の準備をどの単位で共有するか

## R18 共有時の上限と中断の見張り

選択肢:

- A: 燃料と受け渡しの予算は呼び出しごと、メモリは Store ごとの現行規則を保つ。CLI 全体の中断の印に一つの見張りを付け、所有者の終了で合流する。
- B: コンパイル結果と一緒に Store と見張りを共有し、テストの間で燃料だけ戻す。
- C: 見張りを外し、外部コードから戻った後だけ中断を調べる。

推す案は A である。理由: stateful の経路は実行の間にリソースとメモリの計数を持つ。テストごとに Store を作り直すことが隔離の条件になる。外部コードが戻らない場合にも中断する契約を保てる。

同じ Engine の epoch を進めるとほかの Store の期限にも関わる。全体の SIGINT は共有できるが、将来の個別のタイムアウトと同一視しない。今回は TODO-219 の並行実行を追加せず、共有部分の Send・Sync から実行状態全体の共有を推定しない。[調査 9.3 節](riders-bc.md#93-上限中断の見張り並行実行)

## R19 性能の目標と測る入力をどう固定するか

選択肢:

- A: 調査 10.2 節の入力・比率・正しさの目標を採り、詳しい設計で既存 compare の targets 用 JSON に固定する。未対応の指標は共通の probe と runner に足す。
- B: 探索の数値が短いことだけで受け入れ、性能目標を置かない。
- C: 今回の改造だけの測定器と結果の形式を作る。

推す案は A である。理由: 入力の種類によって check・コンパイル・実行・検査用 IR の費用が違い、同じ CLI の総時間だけで全部の改善を判断できない。

約束する値は次のとおりである。

| 直す費用 | 入力と目標 |
|---|---|
| shapes | Integer／String の n=900 の check の入力部分を開始版の 1/2 以下。n=250→500 の増加を 3 倍以内 |
| 判定の木 | n=13・16・24 を正しく実行。候補の n=12→24 の入力部分を 4 倍以内。n=12 は開始版以下 |
| 自由変数 | n=900 の run の入力部分を開始版の 1/2 以下。候補の n=250→500 を 3 倍以内 |
| IR 環境 | 公開 check_program の n=1,000 を開始版の 1/2 以下、n=500→1,000 を 3 倍以内 |
| 穴の Let | 穴一つにつき Let 一つを削減。反復実行の部分を開始版の 1.10 倍以内 |
| 橋渡し | 候補の深さ 24 を実行し、実在する節数が 2 倍の点で時間・割当量を 3 倍以内 |
| 外部の準備 | 10・50 テストを開始版の 1/2 以下。同じキーの実行用のコンパイルは一度。1 テストは 1.10 倍または +2 ms の大きい方以内 |

族は既存の functions と、新設する patterns・codegen・bridge・external-tests とする。short は小さい代表点、targets はこの表、full は公開候補の必要な範囲へ割り当てる。check_program と橋渡しの補助の観測は既存の共通 probe を広げて記録し、実行しない段を CLI 時間で測ったことにしない。退行の合図、ばらつき、取り出せない内部計数と未取得のプロファイルも報告する。[調査 10.2 節](riders-bc.md#102-compare-に置く測定と受け入れの案)

## R20 形式化と検査の順序をどうするか

選択肢:

- A: 192 と、意味を変える場合の Coverage の変更を、中心 248 と相乗り A を含む版の Lean 先行段へまとめる。Rust と Lean の接続、保持・再利用、作業末、改造末、公開候補の検査を分けて計画する。
- B: Rust を全て実装した後で Lean を合わせる。
- C: 相乗りは軽いとして、形式化と特殊構成をまとめて省く。

推す案は A である。理由: 192 は現在の性質 1 の対象であり、Rust の出力だけを直すと保証との対応を失う。T2／T3 や診断は下位の実装の変更に絞れば、第二の重い形式化を増やさずに扱える。
