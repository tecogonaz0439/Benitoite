### 2.2 shapes とリテラルの分岐

[patterns.rs](../../../crates/benitoite/src/typeck/patterns.rs) の `shapes` は 386 行にある。Integer の境界を整列して重複を除く部分は 416–454 行、String の重複を線形に探す部分は 456–467 行である。Integer では各小区間が既存のどれかの区間に含まれるかを全走査する。String では、既に作った全ての形と次の文字列を比較する。一回の列挙に O(n²) の仕事があり、先行する分岐を一行ずつ増やして有用性を調べると、その部分だけで O(n³) になりうる。全入力に同じ次数が現れるという意味ではない。

直す案は、Integer の境界を一度整列し、区間の開始と終了を順に処理して被覆を求めることである。区間を単に合併して一つの形にしてはならない。例えば二つの欄を持つレコードでは、境界ごとの特殊化に残る行が異なり、欄どうしの相関を失うからである。String は、出現順の Vec を残し、別の集合で挿入済みかを判定すれば、反例の選び方を保って重複探索を減らせる。ハッシュの計算と文字列比較の費用は文字列長にも依存する。

この変更だけで、全体が線形になるとは約束しない。`check_match_with:191` は接頭辞ごとに判定し、`enter:732` は記憶表を引く前に shapes を作り、特殊化は残る各行を調べる。最初の最適化で目標へ届かなければ、同じ接頭辞の境界情報の再利用を次に試す。問いに関係する形だけを列挙する変更は、探索の順と反例を変えうるので、別の証明・比較を要する。

現在の予算はセルの複製と探索の入口を数え、shapes 内の文字列比較や境界の全走査を直接は数えていない。したがって「1,048,576 だから実時間も一定以下」とは言えない。列挙と記憶の鍵の生成にも、確保前の検査と上限を設ける案を R3 にする。既存の上限を引き上げるだけの案は推さない。

形式化の扱いは二段に分ける。結果の列挙順を保つ Rust の整列・集合・記憶の変更は、既存の Lean 手順との一致を確認する実装上の変更である。Lean の `Release/Coverage.lean:174–205` の `shapes` と `shapesWithView` を正として、同じ列を返すことを要求する。列挙する形や順序を変える場合は、Lean の定義・補題 U・網羅性と到達不能の系を先に直す。相乗り A の Integer 全域の判断とも境界と other の扱いを一度に決める。

### 2.3 T2 と T3 の比較

現行の [decision.rs](../../../crates/benitoite/src/ir/decision.rs) は `Matrix:618` から `Tree:625` を作る。`tree:753` は先頭行の最も左の検査を選ぶ。構成子・定数・区間・長さに特殊化し、全て照合する先頭行に達したら葉にする。ガードが失敗すれば、同じ分岐に属する全ての行を飛ばす。葉が複数ある本体は join の飛び先で共有するが、残りの照合の木は共有しない。木の子は Box または Vec の値であり、同じ残りの行列でも再び木を作る。

| 案 | 作り方 | 利点 | 必要な注意と費用 |
|---|---|---|---|
| T2: 木を共有する | 同じ残りの行列を一度だけコンパイルし、有向非巡回グラフ（directed acyclic graph、DAG）にする。共有する節を join／jump へ移す | 同じ検査を枝ごとに複製する費用を減らし、通常の木の実行特性を保ちやすい | 鍵を VarId の一致だけにすると、別の枝で新しく作った列の変数を同一視できない。列と取り出し元を正規化し、参照する値を飛び先の引数にする。鍵・辺・下位 IR・命令生成まで共有を維持する必要がある |
| T3: 行ごとの照合 | 上限に当たる match を、ソース順の各分岐を順に試す形で作り直す | 同じ後続を次の分岐の飛び先にでき、照合の組合せの展開を避けられる。T2 で共有できない入力にも対応できる | 実行時の検査が増える。選択肢の全組合せを先に展開すると別の指数増加になる。各パターンと失敗先を直接作る必要がある |

推すのは、予算付きの T2 と、超過時の T3 を組み合わせる案である。T2 による共有が一般の照合を多項式時間にするとは主張しない。T3 は別の VM 命令体系を増やさず、既存の CaseCtor・CaseConst・CaseLength・ListGet・ListSlice・Join・Jump へ移す。T2 を試してから T3 へ切り替えるときは、途中の木と一時表を破棄し、変数・本体・飛び先の番号と定義の予算を整合した状態へ戻す。失敗した試行の部分結果を出力しない。

両案で保つ契約は、最初に照合する分岐、束縛の対応、ガードを評価する回数と順序、ガード失敗時に同じ分岐の次の選択肢へ戻らないこと、return・停止・ハンドラの振る舞いである。共有節の鍵には、型、残る行、分岐番号、束縛の取り出し元、ガード失敗時の飛び先を含める。join の外側で使えない列の値は明示した引数にする。共有しても、その下の下位 IR を clone して再展開してはならない。

T3 も無制限にはしない。パターンの節・辺・生成する命令と一時領域の予算を置き、超過は L0112 に残す。check の E0609 と run の L0112 は別の段の制限である。網羅性を確認できない入力を T3 に任せて実行する案は採らない。現行の 600,000／2,400,000 は、木の試行を止める初期値として保つ。新しい表現の最終予算は受け入れ入力と標準ソースを数えて詳しい設計で固定する。

下位 IR とコード生成は、07-04 の本体の形式化の外側である。T2／T3 が元の Core Match を保つなら、Lean の網羅性の定義や脱糖の定義は変わらない。独立した照合器との比較は `decision.rs` の公開の `lower_program` を境界に置く。Rust と Lean の接続は、相乗り A の網羅性と TODO-192 の変更を含む版全体の比較で確認する。T2 のために Core Match や表層の型付けを変える実装へ広げる場合は、この範囲判定をやり直す。

一次資料では、Maranget の論文が判定の木とバックトラック方式を比較し、木の部分の共有による DAG 化を扱っている。今回の T3 は Benitoite の順序規則へ合わせた案であり、論文の実装をそのまま採るものではない。[Compiling Pattern Matching to Good Decision Trees](https://www.cs.tufts.edu/~nr/cs257/archive/luc-maranget/jun08.pdf)。Rust の処理系の資料も、同じ有用性の計算で網羅性と到達不能を検査し、関連しない枝を省く手法を説明している。これを理由に Benitoite の予算や Lean との一致を省かない。[rustc_pattern_analysis::usefulness](https://doc.rust-lang.org/nightly/nightly-rustc/rustc_pattern_analysis/usefulness/index.html)。いずれも 2026-10-19 に確認した。

### 2.4 自由変数の再走査とコア IR の環境

[codegen/analysis.rs](../../../crates/benitoite/src/bytecode/codegen/analysis.rs) の `free_keys:26` は、束縛の有効範囲を数えながら自由変数（free variable）を順に集める。`with_reads:220` は future を clone し、子全体の free_keys を足す。`captured:227` は、ラムダ・lazy・ハンドラの本体の自由変数を調べつつ、その子へも走査を続ける。

[codegen/emit.rs](../../../crates/benitoite/src/bytecode/codegen/emit.rs) の `let_:169–203` は再帰を避けて連鎖を辿るが、各 Let の残りの body を 184 行で改めて走査する。長さ N の一本の連鎖では、走査する節の合計が N+(N−1)+… になる。case の `captured:714`、if の `with_reads:471`、クロージャの `body_proto:1351` も同じ解析を使う。これは TODO の推測だけでなく、現行のループから確認できる再走査である。実行時間全体の何割かは、段別計測やプロファイルなしには断定しない。

案は、本体ごとの読み出し・捕捉の情報を一度計算し、コード生成は必要な変数が後で読まれるかを問い合わせる形にすることである。全ての部分木について巨大な集合を別々に保存すると、表だけで O(N²) になる。let の連鎖は後ろから使用回数を増減して処理し、分岐では共有する集合または読み出しの索引を使う。クロージャの捕捉順は、従来の初出順を保つ。枝ごとの同じ VarId、辞書の ImplParam、join の引数、内部の終了報告の値、構築器の保持値も解析へ含める。その場での値の再利用の安全性を、速度のために弱めない。

[ir/check.rs](../../../crates/benitoite/src/ir/check.rs) の Env は 49–60 行に複数の表を持つ。clone はラムダ 520、Let 713、lazy 779、ハンドラの節 1188、match の分岐 1322 行にある。Let ごとに増大した表を clone するため、コア IR の検査にも二乗の費用がある。案は、変更しない宣言の情報を借用し、局所の表は可変にして、追加・上書きの前の値を記録し、有効範囲から出るときに戻すことである。早い return や検査失敗でも復元し、枝の束縛や継続の利用可能性を兄弟へ残さない。長い Let は検査自体も明示した積み重ねで処理する。

TODO の「check_program を呼ぶのは脱糖のテスト補助だけ」も現在より狭い。`tests/golden.rs:762`、`tests/random_programs.rs:270`、`tests/verify.rs:254`、`tests/named_arguments.rs:144` 等も呼ぶ。本番の CLI check の段ではないという区別は今も成り立つ。通常の CLI の時間でこの改善を受け入れたことにしてはならない。コア IR の公開境界で、正しい入力と独立した不正入力の診断を保ちつつ測る。Rust の環境の持ち方だけを変えるなら形式規則は変わらない。

### 3.2 直す案と形式化

短い修正案は、移した報告を実際に出したかにかかわらず、記録した根を誤りの型にしてから dependent_late を判断することである。これは Z3 の M1 を扱うが、包んだ値・演算子・再束縛・部分のパターン・try を単独では直せない。

推すのは、宣言から仮に決めた型の出どころ（provenance）を、型変数の根だけでなく、値を束縛する制約と使う制約の依存として残す案である。具体的には、宣言側の理由、束縛側の制約、構成子やリストの何番目の部分か、再束縛・try の成功値へ引き継いだ関係を番号で記録する。型の形を zonk しても、この関係は消さない。依存の辺は共有し、使う箇所ごとに全履歴を複製しない。

失敗時は、宣言と値の食い違いの型・理由・位置を誤りの型にする前に保存する。依存する使用の報告は保留し、原因側の報告の処理と根の無効化を終えてから判断する。宣言から仮に得た型との比較だけで失敗した使用は抑える。単に同じ型変数を含むだけの別の誤りは消さない。宣言どうしの本当の衝突と、宣言へ流れ込む式の内側の誤りは、従来の理由・位置・修正案を保つ。

全ての E0401 を最後まで遅らせる案は推さない。Z1 の M1 のように、先にある本当の引数の誤りが後続の別の誤りへ置き換わりうるからである。成功するプログラムの制約の解き方を変更することも、この修正の要件にはしない。診断のための記録と報告順を変える範囲で試作し、既存の成功・失敗の受理結果が変わるなら別の判断を要する。

診断の選び方は形式化の対象外である。ただし受理する型付けを変えてしまえば、通常の出力と E2 の検査の接続へ影響する。最初の作業で再現表と既存の `typeck/tests.rs:756,823,885,924` をまとめて確認する。根の無効化だけで TODO 全体を閉じず、表の全種類と「使う側だけが本当に誤っている」対照を受け入れ条件にする。

案は、一つの組み込み呼び出しの引数全体と結果の変換に、それぞれ対応表を持つことである。行きは Rc の対象の同一性と値の種類、構成子のタグを鍵にする。同じ Rc<Values> が別の意味で使われても取り違えない。Rc::as_ptr をハッシュの鍵として使う場合も、ポインタから値を逆参照する実装を足さない。文字列や Bytes では長さを含む対象の識別も考慮する。戻りは公開の `ValueCtx::object_id`（`runtime/heap/ctx.rs:446`）が返す ObjId と種類を鍵にする。

表への登録は子の変換を終えて親を組み立てた時点で行い、後の同じ対象は表の値を使う。現在の通常の構成子・コレクションはこの境界で循環しない前提である。処理中の同じ対象へ再び来た場合は、循環した普通の値を作って進まず、変換できない入力として扱う。セル・Lazy・継続・リソース・Opaque の同一性は、現在の独自ストア・番号・根の表に任せる。

現在の組み込み呼び出しは一つの `heap.epoch` 内（convert.rs:185–245）で変換し、終わってから回収する。対応表に区間内の HeapValue を置くなら、その区間から外へ出さない。表を次の呼び出しへ持ち越して裸の値を保存しない。Opaque は既存の RootStack の番号で保持し、関数と Location の RefValue の世代検査も保つ。外部の関数の変換は convert.rs:101–162 の別の入口を使うため、組み込みだけ直して全ての橋渡しが直ったとは説明しない。

平坦な参照リストと VM の永続リスト・Map の木の形は違う。ここで保つのは、同じ通常の値や要素の対象が複数回現れたときの共有である。平坦な配列を全ての永続リストの接尾部と同じ構造に変える要求は含めない。

差分テストから「共有がある」ことだけで除く案は推さない。変換の境界で共有した木・複数の引数に共通の部分・戻り値・呼び出しを越えた回収を確かめる。一つの値の同一性を確かめるための本番専用 API は増やさず、ヒープの公開の対象番号と、変換結果の意味・数を使う。二倍ずつ展開してしまう入力は既定で小さく、gc-stress ではさらに小さくし、大きい入力は compare の測定へ置く。

注意として、独自の `value.rs:135` の values_equal も、同じ Rc でも子を再び比較する。橋渡しだけを直した後も、別々に作った深い共有木の等値比較を参照側で行えば遅くなりうる。深い性能入力では結果を小さい整数や真偽にして照合し、変換の改善と参照側の等値判定の別の費用を区別する。この点を黙って差分対象の全般的な縮小に替えない。

除外を残すなら、既存の RefOutcome::Unsupported が表す非対応の操作など、機能の境界を名指しする。除外したケース数と理由を記録し、正常な比較の成功に数えない。VM 専用の期待値を持つ検査は、独立に書いた結果を検査する別の境界として明記する。今回の通常の共有値は対応表で扱う方針とする。

変換の実装は形式化の対象外である。ただし回収を越える値の扱いに関わるため、局所の heap-verify・gc-stress と doc_default を、次の作業へ渡す前に要求する。

### 9.2 test 内の Engine とコンポーネントの共有

現行の実行のつながりは次のとおりである。

| 段 | 現行コードの位置 | 所有しているもの |
|---|---|---|
| 各テストの起動 | `cli/tools/test_runner/mod.rs:676–734` | テストごとに RunEnv と出力を作り、run_test_with_externals を呼ぶ |
| VM の起動 | `runtime/run.rs:325–328,1090–1096`、`vm/state.rs:22–23` | VM ごとに外部の実行状態を持つ。ExecutionOptions は上限と統計を渡す |

| 生成した補助 | `external/adapter/runtime.rs:134–179`、`external/adapter/component.rs:183–202` | 入力のコンポーネントと変換の計画から ComponentKey を作り、生成したコンポーネントをコンパイルする |

ここでも `src/` は省いた。文書例の実行も `cli/tools/test_runner/docs/execute.rs:140–157` から別の run を作る。通常の @test だけ共有しても test --doc の費用は残る。

TODO の「インスタンスは呼び出しごと」は現在の全経路には当たらない。外部のリソースを持つ stateful の経路は、同じ実行の間で Store を保ち、呼び出しごとに燃料等を入れ直す。メモリの計数は Store の寿命全体で持つ。テスト間へこの Store を渡すと、状態・外部ハンドル・メモリの上限が混ざる。

推すのは、一回の test 起動が持つ共有の準備と、各実行だけが持つ可変状態を分ける案である。共有するものは Engine とコンパイル済みの通常／補助の Component だけにする。Store・Instance・ResourceAny・解放のキュー・ハンドル表・言語ヒープ・出力・実行番号は共有しない。test --doc でも同じ準備を渡す。run の単独実行には専用の所有者を作り、既存の公開の run_program／run_test の既定動作は保てる。

コンパイル表をモジュール内の配列番号や表示パスだけで引かない。test の複数の入口では、同じ番号が別のコンポーネントを指しうる。読み込んだバイト列のハッシュと Engine の所有者を使い、同一キーでバイト列も照合する。補助は ComponentKey が含む ABI・型・関数の条件も保つ。キャッシュはプロセスの大域やディスクへ残さず、その起動の間だけにする。使わない外部関数の実行用のコンパイルは遅らせたままとし、外部を呼ばないテストのために実行用の Engine と見張りを作らない。

静的な外部宣言の検査も `external/check.rs:130,277` で別の Engine と Component を作る。この検査は一つの入口の準備時に行われ、関数ごとの run の準備とは異なる。今回の「同じキーは一度」の目標は実行用の共有表のコンパイルに限る。宣言の検査を飛ばしたり、その Engine のコンパイル結果を異なる Engine へ渡したりする案ではない。静的検査のコンパイル回数と時間も観測に残す。

Wasmtime は固定版 49.0.2 を使っている。Component の複製は同じコンパイル結果への参照を作る操作であり、スレッド間で共有できることを、その版の一次資料で確認した。[Component 49.0.2](https://docs.rs/wasmtime/49.0.2/wasmtime/component/struct.Component.html)。Engine の共有と epoch、Store の燃料と期限は、公式の [Engine](https://docs.wasmtime.dev/api/wasmtime/struct.Engine.html)・[Store](https://docs.wasmtime.dev/api/wasmtime/struct.Store.html) の説明も確認した。これら二ページは確認時点で 51.0.0-dev なので、固定版の根拠は Cargo が取得した 49.0.2 の `src/engine.rs:38–61,875`、`src/runtime/store.rs:1016,1084` でも照合した。最新版の API へ依存を更新する提案ではない。

### 9.3 上限、中断の見張り、並行実行

燃料の既定は一呼び出し 10,000,000,000、線形メモリは 64 MiB、受け渡しは引数・結果それぞれ 256 MiB である（external/runtime.rs:22–26）。メモリの制限器は Store のデータに置き、燃料・hostcall fuel・epoch の相対期限は reset_limits:594–598 で設定する。この設定は新しい実行へも毎回行い、コンパイル結果を共有しただけで予算を共用しない。stateful の呼び出しでは現行どおり燃料を入れ直し、メモリの累積を維持する。テストが変わったら Store ごと新しくする。

現行 Watcher:102–139 は、実行の印を 10 ms ごとに見て、その Engine の epoch を進める。Engine を共有して各テストが見張りだけを起こし直す案は、起動費用を少し残す。test 起動全体で同じ中断の印を持つ範囲に一つの見張りを置く案を推す。見張りは最後の所有者が終わるときに unpark と join を行う。中断した test は残りを起動せず、次の別の CLI 起動にはその印も epoch の所有者も残さない。

Engine の epoch は Engine を共有する全 Store の期限に関係する。将来、テストごとのタイムアウトだけで epoch を進めると、ほかの Store も止めうる。一方、CLI 全体の SIGINT／SIGTERM は全実行を止める要求なので、共有の見張りと整合する。今回は TODO-219 の並行実行を追加しない。将来は個別の取消と全体の中断を分けて設計する必要がある。Engine／Component の Send・Sync だけを根拠に、Rc を含む ExternalRuntime 全体を共有可能と説明しない。

この変更は形式化の対象外である。既存の燃料切れ、メモリ超過、中断、stateful の解放、実行番号ごとの統計を実際のコンポーネントで確かめ、test 内の共有と各実行の隔離を同時に受け入れる。

通常の改造末は short、約束する目標は targets を使う。quick は出力照合と所要時間の見積もりだけに使う。targets の本測定は、静かな計算機、標本数 10、全体と各節の見込みを確認し、設計者の了承後に行う。full は実際のバイナリのリリースまたは大きな性能変更の受け入れで別途割り当てる。今回の探索から本測定の時間を外挿して確約しない。既存の VM の 5% の関門と short の退行の合図も保つ。

builders の requires の直しは S1 の測定の前提として合流させる。S3 が新しい族を足すことを理由に、TODO-262 の旧版四状態の本測定を今回へ戻さない。

### 10.4 形式化と検査の順序

S3 で確実に形式化の内側に入るのは 192 の脱糖である。これを中心の 248、相乗り A の Integer 全域などと同じ Lean 先行段へ置く。032 は列挙の意味を変える場合だけ Coverage の定義・健全性・写しを先行させる。ほかの最適化と診断は、07-04 の対象外の対応を明記し、型付けやコアの意味を便宜的に変更しない。
