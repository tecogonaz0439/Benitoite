# 関数内の構築器について設計者に尋ねる問い（S1）

2026-10-19、TODO-248の残りと測定に必要な修正についての16問である。根拠と実装位置は [調査](local-builders.md)、元の項目は [写し](../todo-items.md) にある。全問のAを推す。回答済みとは扱わず、判断後に改造全体のdecisions.md・design.md・plan.mdへ反映する。選択肢のコードや数値は提案であり、実証済みの仕様・速度ではない。

今回の前提は、0.0.10でできるだけ多くの指定項目を扱い、形式化の重い項目を構築器の局所エフェクトの規則一つに限ることである。他の14件の範囲をこの問いで縮めない。証明が閉じない場合の代案は、設計者へ判断を戻す選択肢であり、自動で先送りする指示にはしない。

## B1 外側のStateを外す対象

問い: 専用の構築器の操作だけを外側のエフェクト（effect）から除くか。

| 選択肢 | 内容 |
|---|---|
| A（推す案） | StringBuilder・ListBuilder・BytesBuilderの専用操作だけを対象にする。通常のReference・リソース解放・通常引数の評価のStateは残す |
| B | 外へ出ないと検査できた通常のReferenceにも同じ規則を適用する |
| C | Stateをすべて残し、この版は専用バッファの高速化だけを扱う |

理由: Aは既存の第二級の値（second-class value）という制限を使える。Referenceは通常値として格納・捕捉・多相な関数への受け渡しができ、Bには追加の持ち出しの解析（escape analysis）または領域の型規則が必要になる。Cは保証を保つ戻り先であるが、今回の第一候補の完了にはならない。

## B2 局所性を表す規則

問い: 0.0.9の局所文脈Δをコアの規則まで拡張するか。

| 選択肢 | 内容 |
|---|---|
| A（推す案） | 通常型・値と別の局所文脈（local context）、専用の束縛と操作、通常値へ変換できない識別子を使う。型付きの検査成功から局所性を導く |
| B | 通常のBuilder型に寿命・領域の型の印を加え、関数型と潜在エフェクトも含めて範囲を検査する |
| C | 通常のReferenceへ展開し、Rust側の持ち出し検査が通ったときだけ効果を空にする |

理由: Aは試作と0.0.9の形式化を再利用し、通常Ty/Effの領域の束縛・置換を増やさずに済む。Bは利用者関数への受け渡しを広げる将来案としては比較できるが、今回その利点を使わない。CではState付きの脱糖（desugaring）と性質1が一致せず、正式な規則への接続が不足するため推さない。

## B3 bind・new・注釈と捕捉境界

問い: 宣言の書き方と持ち出し禁止を0.0.9のまま保つか。

| 選択肢 | 内容 |
|---|---|
| A（推す案） | 明示import、型を注釈したbind、直接new、Listの要素型の明記を保つ。lambda・lazy・部分適用・節への外側の構築器の捕捉を拒否する |
| B | 注釈なしのnewから種類を推論するが、捕捉禁止は保つ |
| C | 専用の構築ブロックや即時実行するコールバックを新設し、その中の捕捉を認める |

理由: Aなら局所エフェクトの規則と物理実装の変更に集中できる。Bは通常の束縛と専用束縛を推論中に分ける新規則、Cは境界と継続（continuation）の追加の証明を要する。一般のループやList.forEachへの捕捉を今回の高速化に暗黙に含めない。

## B4 Stateを明記した既存コードと移行

問い: 構築器だけを使う関数に残った `uses State` を引き続き受理するか。

| 選択肢 | 内容 |
|---|---|
| A（推す案） | 効果の上限として受理し、余分なStateだけを理由に新しい警告・誤りを加えない。純粋に使うには宣言と関数型のStateを明示的に除くと案内する |
| B | 受理するが、不要なStateの警告と削除案をこの版で新設する |
| C | 不要なStateを誤りにし、全呼び出し経路のusesを同時に移行させる |

理由: 現行は効果の拡大を許し、W0501はIO.Allを狭める警告である。Aなら「Stateが消えたら既存の明記が誤りになる」という不要な破壊を避けられる。関数の公称の契約にStateを残せば呼び出す側にも残るため、実装が局所的になっただけで宣言を書き換えたことにはしない。CHANGELOG・英語リファレンス・同梱Skillに、Stateの除去は構築器分だけであり、通常ReferenceやIOの除去ではないと案内する。IO.Allの既存警告の推奨集合が変わる場合は別に確認する。

## B5 主定理と証明が閉じない場合の停止点

問い: 主定理の外側の前提・結論と、既存の組み込みの動作の仮定を保つことを実装開始の条件にするか。

| 選択肢 | 内容 |
|---|---|
| A（推す案） | Lean段で定義・証明・写し・レビューを閉じる。主定理の前提追加・結論の弱化・新公理が必要、または区切りの見込みの2倍に達する見通しが出たら、依存する処理系へ進まず設計者へ戻す |
| B | 局所性の仮定を主定理やBuiltins.Assumptionsへ追加し、後で証明する計画で処理系を進める |
| C | State除去の代わりに、Stateを残す専用バッファへ自動で切り替える |

理由: Aは00-01の宣言済みの保証と07-04のLean先行に従う。内部のStateTy・型付け・Stepの拡張は認めるが、定義に未証明の前提を隠して旧プログラムを除外することも停止理由とする。戻り先の第一候補は0.0.9のState付きReference展開であり、State付きバッファを残すかはその対応の証拠を見て別に決める。

## B6 専用バッファのヒープ上の表現

問い: 既存のHostを使って、三種類のバッファの私有データを保持するか。

| 選択肢 | 内容 |
|---|---|
| A（推す案） | ObjKind::HostにString/Vec<u8>/Vec<Slot>を持たせ、HostData・Trace・host_mut・SlotOps・heap_bytesを使う |
| B | ObjKindへ構築器専用の種類を追加し、内部層で配置・走査・破棄・容量を扱う |
| C | Referenceに不変値を置く現在の実装を使い続ける |

理由: Aには既存の根・書き込みの障壁・容量の計上を利用できる根拠がある。新しいunsafeもまず必要としない。Hostの型検査や間接参照が性能を支配すると実測で分かった場合はBを再検討する。Bを先に選んでも局所性の証明が簡単になるとは限らない。

## B7 copyの安定性と物理コピー

問い: 取り出し済みの値を変えない現在の契約を保ち、最初は通常値へのコピーを行うか。

| 選択肢 | 内容 |
|---|---|
| A（推す案） | copyは非消費のまま保つ。String/Bytesは不変値へ写し、Listは通常の永続ベクタを作る。要素の深い複製はしない |
| B | 最初からcopy-on-writeを入れ、取り出しと次の追記の間で所有を切り替える |
| C | 消費するfinishへ置き換え、取り出した後の利用を拒否する |

理由: Aは可変領域の別名を通常値へ渡さずに済む。0.0.9の共有copyより高くなる費用は測定で明示する。Bには所有と共有の判定、Cには消費後の検査と移行が加わる。copyを多用する用途をこの版の中心にするならBが必要かを先に再判断する。

## B8 容量の予約・消去・構築器どうしの結合

問い: この版で新しい容量・結合APIを足すか。

| 選択肢 | 内容 |
|---|---|
| A（推す案） | new・append・appendAll・copy・長さを保ち、reserve・clear/reset・構築器どうしの結合・finishは足さない |
| B | reserveまたは初期容量を指定するnewだけを足す |
| C | reserve・clear/reset・appendBuilderをまとめて足す |

理由: 専用バッファは既存APIの範囲でも実装できる。追加APIは容量を数える単位、clear後の領域保持、自分自身の結合、複数局所識別子の所属と別名の規則を増やす。多数のTODOを進めるためにも、測定前に必要性の分からないAPIを増やさない。

## B9 容量の増やし方と上限検査

問い: 容量の増加率を私有の実装方針とし、論理長と確保量を別に検査・記録するか。

| 選択肢 | 内容 |
|---|---|
| A（推す案） | newは容量0、必要時に概ね2倍へ増やす。必要長と上限を先に検査し、要求容量の加算・乗算・変換も検査する。実容量はheap_bytesで計上する |
| B | Rustのtry_reserveへ増加率をすべて任せ、必要長だけを検査する |
| C | 毎回必要長ちょうどの領域を新しく確保する |

理由: Aなら確保前の要求量を追え、多数の追記で毎回全量を移すCを避けられる。Rustの実容量が要求値より大きくなる余地は残るため、容量の厳密な倍率を仕様として約束しない。初回64バイト/8要素は測定用の仮置きである。論理長の上限超過は従来のValueTooLargeとし、失敗時に一部だけ追記しない。

## B10 ホストの確保失敗

問い: 上限内のバッファ予約に失敗した場合を、言語の停止理由として扱うか。

| 選択肢 | 内容 |
|---|---|
| A（推す案） | try_reserve系の容量あふれは確保前に処理し、ホスト確保失敗には資源不足の停止理由を用意する。停止後は既存のunwindへ接続する。実OSのOOMは強制せず失敗を注入して検査する |
| B | 論理長の超過だけを言語の停止とし、ホストOOMは現在の内部確保器と同じ異常終了の扱いにする |
| C | try_reserveのすべての失敗を既存のValueTooLargeへ写す |

理由: Aなら回復可能な予約失敗をpanicや偽の大きさ超過にしない。ResourceErrorには汎用の確保失敗の項目がないため、停止理由・診断・テストの追加は詳しい設計へ明記する。Aも、停止の報告やunwind自体が物理メモリ不足で失敗しないこと、他の確保を含むプロセス全体のOOM耐性までは保証しない。Bを採る場合はその限界を明示し、異常終了まで後始末を保証しない。

## B11 継続の捕捉とメモリの後始末

問い: 保存継続からバッファを保持し、不要な参照がなくなったときに通常のGCで回収する形にするか。

| 選択肢 | 内容 |
|---|---|
| A（推す案） | 実行中・保存中の枠のSlotから追跡し、return/Stop/drop/取消で参照を手放す。バッファ自体はIOを伴うreleaseを持たず、既存の一回のresumeを保つ |
| B | 関数を抜けるとバッファを直ちに破棄し、保存継続にも内容を複製する |
| C | バッファの解放をwithと同じState付きのリソース解放にする |

理由: Aなら捕捉時に後続計算が使う領域を失わず、局所メモリの回収を外から観測するrelease事象にしない。Bの複製は現在のReferenceによる再開の意味と違い得る。CはStateを外す目的と衝突する。全制御経路で生存と不要参照の破棄を確認するが、到達不能になった瞬間の物理返却は約束しない。

## B12 純粋さを要求する位置と長い一操作

問い: 専用操作が外側にStateを残さなくなることで受理範囲が広がる位置をどう扱うか。

| 選択肢 | 内容 |
|---|---|
| A（推す案） | ガード等で同じΔを渡す位置は新しい局所規則で判定する。通常のStateは拒否し、構文によるreturn/tryの禁止は保つ。lazy等は外側の捕捉を許さず、内側で新しく作る場合を証明する |
| B | ガード等では専用操作を一律に新しい診断で拒否し、0.0.9の受理範囲へ固定する |
| C | Stateが消えたことを理由に、捕捉境界でも外側の構築器を許す |

理由: Aはエフェクトと局所文脈による判定を揃えられる。局所操作を含むガードの評価や遅延の途中でも隔離が保たれることをLeanで示す。Cは外側の効果の有無と値の生存を混同するため推さない。大きいappendAll/copyは最初は一操作として完了させ、途中のGC・利用者コールバック・中断の安全点を新設しない。長い待ち時間が問題なら、進捗を保存する別の設計を相談する。

## B13 参照インタプリタとの照合

問い: 専用コア操作の参照実装を、VMの可変バッファと分けるか。

| 選択肢 | 内容 |
|---|---|
| A（推す案） | 参照評価器の独自ストアと不変列の更新で意味を実装し、通常値の結果・評価順・停止時点を比較する。物理GCや未対応のタスクの制御はVMの局所検査で確かめる |
| B | 参照評価器もHostの同じバッファ操作を呼ぶ |
| C | 構築器を含む入力を差分テストから除く |

理由: Aならcopyや追記の誤りを独立した表現で検出できる。TODO-222の共有構造の変換とは通常値の境界を合わせるが、構築器の内部Slotを通常の橋渡しへ流さない。Bは物理実装の共通の誤りを見落としやすく、Cは現在の照合を後退させる。

## B14 測定段と数値目標

問い: shortに加え、三種類の構築器のtargetsで高速化の目標を判定するか。

| 選択肢 | 内容 |
|---|---|
| A（推す案） | shortで全族の退行を調べ、targetsの10標本以上で下記の目標を判定する。判定不能・未達は設計者へ戻す |
| B | shortだけを行い、速度と確保量は観察値として報告する |
| C | fullの全族・全点をこの版の必須条件にする |

理由: Aは専用バッファの費用を測る依頼に対応し、約束した点を起動時間が大半のshortだけで判断することを避けられる。CはTODO-262の本測定など今回対象外の仕事まで広げる。

数値案は、n=1024・途中copyなしの反復の時間増分を、三種類それぞれ0.0.9の同じbuilderの1/2以下とする。String/Bytesのallocated_bytesは1/2以下、Listは旧版以下を目標とする。n=0/8のCLIの退行はmax(10%, 2 ms)以内、一回appendAll+copyは同じ準備条件の既存一括操作の2倍以内を目安とする。完成済みListを直接返すだけの基準と、途中copy4回は倍率の合否を課さず費用を示す。これらは測定前の提案値であり、実測の見込みではない。

## B15 比較入力の修正と測定できる費用

問い: requiresだけでなくimportと計算の条件も、builders族の中で修正するか。

| 選択肢 | 内容 |
|---|---|
| A（推す案） | requiresと構築器のimportをbuilder系だけに付ける。一回appendAll、copyだけ、結果の内容を後で確かめる入力、関数内構築の反復を既存族へ追加する |
| B | TODO-262にあるrequiresの変更だけを行い、既存の長さの入力で比較する |
| C | 実行時間だけを測る改造専用の新しい道具を作る |

理由: Bでは旧版がimportで失敗し得るうえ、長さだけでは取り出した内容の変化を見つけられない。現在のbuilder-allは短い断片を繰り返し渡す系列で、一回の一括追加ではない。Aでは入力の違いと未取得のVM実行区間を明記し、同じソースの反復数の差がばらつきより大きい場合だけ時間増分を使う。Cは既存compareを使う今回の前提に従わない。

## B16 表示だけから局所Stateを除く代案

問い: 正式なState除去の証明が閉じない場合、mainの表示だけを変える案を採るか。

| 選択肢 | 内容 |
|---|---|
| A（推す案） | 自動では採らず、Stateを残す戻り先とともに設計者へ判断を戻す。型上の純粋さと権限説明の変更を別の判断にする |
| B | Stateは契約に残し、由来を追跡して局所と分かった構築器分だけ表示から除く。保証は表示の簡略化に限る |
| C | 最終的なState集合からStateを除き、局所性を確認済みと説明する |

理由: 現在の集合は同じStateの出どころを区別しない。Bにも説明用の追跡と、通常Reference・リソース解放を省かない検査が要る。Bを採っても純粋な関数にはならず、実行時の許可を狭める根拠にもならない。Cは普通のStateまで消す試作の反例に当たるため採らない。
