### TODO-248 関数内に閉じた文字列・リスト・バイト列の構築器

- 状態: 方針あり
- 出どころ: 2026-10-14 の設計者との相談と、独立した TODO として追加する依頼、0.0.9 の改造（`docs/archive/` の下の `2026-10-18-TODO-021_022_026_032_087_088_142_164_248_257_258_259_260-syntax-batch3/`）

文字列・リスト・バイト列を繰り返し構築する処理の高速化のため、関数内だけで使える可変の構築器を追加する方向で検討してきた（2026-10-14 の方針）。追記は内部の状態を変え、取り出しはコピーし、利用者が定義する関数の引数・戻り値として受け渡さない。局所の状態操作を関数の外側のエフェクトに残さない設計を第一候補とし、局所状態の隔離とエフェクトを除く規則を十分に設計・検証できない場合は、構築器の操作に `State` を付けて提供する。保証を弱めてエフェクトだけを省略しない。

0.0.9 で、試作の推す範囲（2026-10-17 の設計者の方針）のうち、`State` を残して既存の `Reference` と不変の値に展開する案を実装した。`Benitoite.StringBuilder`・`Benitoite.ListBuilder`・`Benitoite.BytesBuilder` を明示して取り込み、型を注釈した `bind` と専用の `new` で関数内に作り、`append`・`appendAll`・`copy`・長さの専用操作だけに渡せる。専用操作はすべて `State` を持つ。持ち出しと捕捉の検査を含む構築器の表層の規則と脱糖は、処理系より先に Lean で形式化した。

残る論点:

- 局所の状態操作を関数の外側のエフェクトに残さない設計（第一候補）。試作（2026-10-17。sources/2026-10-17-feasibility-spikes/248/）では、構築器を普通の型・値と分けた局所の文脈で扱えば、寿命や領域の型変数なしで、局所の操作だけをエフェクトから除く規則の健全性を小さなモデルで証明できた。普通の `State` まで一括で消す案、具体化の前の型だけを見る検査、関数の引数と戻り値だけを見る捕捉の検査には、反例を確かめた。正式なモデルにつなぐと 30〜60 ファイル、定義・補題 80〜220 件ほどに手が入る見込みで、継続の保存（`E_Op` が残りの枠を保存する）と破棄の規則が難所である。
- 専用のバッファによる実装。今は `Reference` と不変の値への展開なので、高速化の効果は確かめていない。容量の増やし方、確保の前の大きさの検査、整数のオーバーフロー、回収の根と書き込みの障壁、早期リターン・停止・取り消しの際の解放を設計する。0.0.9 は容量の予約・消去・構築器どうしの結合の操作を加えていない。
- 多数の小さな断片を追加する場合の処理時間と確保量、短い構築での費用、コピーして取り出す費用を三種類ごとに測り、リストの既存の永続データ構造や、一括で組み立てる既存の操作と比べる。0.0.9 の短い比較は、0.0.8 に構築器がないので判定していない。性能の測定はスキル `benchmark` に従う。

### TODO-206 ログ出力（ロガーの差し替えと複数の出力先）

- 状態: 方針あり
- 出どころ: 2026-10-11 の言語の方向のメモ（`sources/2026-10-11-language-direction/memo.md`）の「ログ出力」、試しのスクリプト log-trial/（`sources/2026-10-11-language-direction/log-trial/`）

目標は、Go の `log/slog` のように、ロガーの差し替え、出力先の変更、複数の出力先への同時の出力を容易にすることである。構文の見直し（TODO-205）とは別の改造とし、標準ライブラリの追加として進める。

確かめたこと（2026-10-11、設計者が Claude と試した）: 利用者が宣言するエフェクトとハンドラで、今の言語のまま次のことを書けた。試しのスクリプトは `benitoite run` で動いた（リリースのビルドは 2026-10-11 18:01 のもの）。

- log.bnt（`sources/2026-10-11-language-direction/log-trial/log.bnt`）: エフェクト `Log` の操作 `emit(level, message, attributes)`、包む関数によるロガーの差し替え（`withTextLogger`）、水準での絞り込み、slog の `With` に当たる属性の追加（`withAttributes`。節はハンドラの外側で動く（01-07）ので、節で呼び直した `emit` は外側のロガーに届く）。包む関数はエフェクト変数を使って `function withTextLoggerT, effect E（`minimum: Level, body: function(`） -> T uses Log, E) -> T uses Console.Write, E` と書け、`Log` を除いて残りのエフェクトを通す。
- sinks.bnt（`sources/2026-10-11-language-direction/log-trial/sinks.bnt`）: 出力先を普通の関数の値のリストとして渡し、一つのハンドラが順に呼ぶ形（slog の Handler を複数にする形）。属性を型クラス `ToLogValue` と補助の関数 `attr(key, value)` で作る形。一つの `emit` が、標準出力へすべてを書く出力先と、標準エラーへ `Error` だけを書く出力先の両方に渡った。
- project/（`sources/2026-10-11-language-direction/log-trial/project/`）: 複数のファイルに分けた形。`benitoite run project` で `project/main.bnt` から始まる。`Lib/Logging.bnt` が `public effect Log`・水準・属性の型・書く側の補助の関数 `info`・`error`・差し替えられるロガーを持ち、`Shop/Order.bnt` は `uses Logging.Log` の関数から `Logging.info(...)` を呼ぶだけで、どこに書くかを知らない。ロガーの差し替えは `main.bnt` の 1 行だけで済んだ。`public effect` を別のモジュールから `uses Logging.Log` と書けること、エフェクト変数を持つ包む関数を `public` にして別のファイルから使えること、型クラスの実装を宣言したモジュールの外から変換に使えることを確かめた。
- どの例も、水準・メッセージ・`key=value` を並べた形式で出し、時刻と呼び出した位置は出していない。時刻は出力先の関数で `Clock.Time` を使えば足せる。呼び出した位置は今の言語では出せない（方針の 2）。
- 確かめていないこと: 一度開いたファイルを出力先の関数に捕えて書き続ける形。JSON の形式の出力先。

方針（設計者、2026-10-11）:

1. ログを組み込みのエフェクトとして実装する。どのハンドラも処理しなければ処理系が既定の出力（標準エラーなど）を行い、`main` に `uses Log` と書くだけで使える（slog の既定のロガーに当たる）。差し替えと複数の出力先は、ハンドラで行う。既定の出力の形式と出力先、水準の種類、属性の値の型は、改造のときに決める。
2. 呼び出した位置（ファイルと行）を出力する仕組みは、標準ライブラリとの密結合を避け、ログに専用の仕組みにせず、言語の一般の仕組みとして設ける。候補は、どの操作の節でも呼び出し元の位置を受け取れる仕組みと、位置を表す式（Rust の `#[track_caller]`、Swift の `#fileID` に当たるもの）である。どちらにするかは改造のときに決める。
3. `uses Log` を書く手間を省くために、暗黙のエフェクト（`uses` に書かなくてよいエフェクト）の概念を入れるかを検討する。深いところでログを書くと、呼び出しの経路のすべての関数に `uses Log` が要るからである。原則 2（契約と権限の変更を見落とさせない）と、利用者が実行前に権限を確かめる主な接点（`main` の `uses`）を損なわない範囲で、どのエフェクトを暗黙にできるかを決める。構文の見直しの「非公開の関数のエフェクトを推論で省くか」とも関わる（TODO-205）。

複数のファイルに分けると目立つ手間（`project/` で確かめた）:

- ログを書くモジュールのすべてに `import Lib.Logging` が要る。prelude の外のモジュールは、`uses` に書くだけでも import が要るからである。組み込みのエフェクトにして prelude に置けば要らなくなり、`uses Log` と短く書ける（方針の 1）。
- 呼び出しの経路のすべての関数に `uses Logging.Log` が要る。深いところで 1 行ログを足すと、`main` までのすべての関数のシグネチャを直すことになる。ファイルが増えるほど大きくなる手間であり、暗黙のエフェクト（方針の 3）が消そうとするものである。
- 利用者が作ったログの仕組みを別のプロジェクトと共有できない。パッケージの仕組みがないので、プロジェクトごとに写すしかない。標準ライブラリに入れれば解消する。利用者のライブラリの共有は、パッケージの仕組み（platform-and-tooling の分野）で扱う。

そのほかの論点:

- 標準ライブラリの名前。試しでは操作を `emit` と `write` にし、書く側の補助の関数を `info`・`error` にした。`Log.info(...)` のように、書く側が水準を関数の名前で選べる形が読みやすい。
- 属性の書き方の長さ（`[attr("n", n), attr("user", "ada")]`）。可変長の引数と任意の型の値がないためである。標準ライブラリの関数で足りるとするか、構文の見直し（TODO-205）で扱うか。
- 捨てる水準のメッセージを組み立てる費用。`lazy … end lazy` を使うか、`enabled(level)` に当たる操作を設けるか。
- 操作の型パラメータに型クラスの制約を書ければ（TODO-189）、`attr` を挟まずに `emit` へ値を渡せる。必須ではない。
- 組み込みのエフェクトにするときに、`IO.All` に含めるか、実行時の権限制御（TODO-023）で許可の対象にするか。

### TODO-022 篩型（値の範囲を型で表す）

- 状態: 方針あり
- 出どころ: ADR 0146（`../archive/2026-10-09-design-first-release/decisions/0146-runtime-errors-not-in-types.md`）の「検討した代替案」、2026-10-11 の言語の方向のメモ（`sources/2026-10-11-language-direction/memo.md`）、0.0.9 の改造（`docs/archive/` の下の `2026-10-18-TODO-021_022_026_032_087_088_142_164_248_257_258_259_260-syntax-batch3/`）

初回リリース版では、関数の型はその関数が実行時エラーを起こしうるかを表さず、実行時エラーはプロセスを異常終了させる（ADR 0146、ADR 0064）。値の範囲を型で表して、実行時エラーを起こさないことを実行の前に証明する篩型（refinement types）は、形式検証の題材であり初回リリース版の範囲を大きく超えるとして、ロードマップの将来拡張に残した。初回リリース版の時点では、採るかどうかも、どの実行時エラー（整数の溢れ、0 による除算、定義域の外の引数など）を対象にするかも検討していなかった。

方向（2026-10-11、設計者）: 実装する方向で検討する。

0.0.9 で、試作の推す範囲（2026-10-17 の設計者の方針）のとおり、整数の閉区間を実行時に確かめて `Result` を返す API（`Benitoite.Unofficial.Range` の `CheckedInteger` と `checkInteger`）と、その小さな意味の証明を加えた。型は不透明型（`@opaque`）とし、作り方を宣言したモジュールの中に閉じた。静的な篩型は加えていない。

残る論点:

- 静的な検査。整数の区間と長さの包含、部分型、定数との比較による if の絞り込み、範囲付きの演算による検査の除去。試作（2026-10-17。sources/2026-10-17-feasibility-spikes/022/）では、これらとあふれのなさを小さなモデルで証明できた（5 ファイル・69 定理）。値に依存する `n` を入れると、束縛・置換・範囲の管理が主な難所になる。Release に部分型を直接足すと、「関数でない型の包含は等号」という既存の補題も組み直しになる（Lean 32〜80 時間・処理系 40〜100 時間の見込み）。
- SMT ソルバ（Z3 など）を外部の OSS として使うか（「言語の中核は自作する」の方針、00-01「目的の衝突」）。SMT の結果を信用する方式と、証明書を検査する方式を区別する。試作では小さな証明書の検査器の健全性は通ったが、`2x = 1` のような整数の上の矛盾は扱えないことも示した。
- どの実行時エラー（整数の溢れ、0 による除算、添字の範囲）を対象にするか。長さ・空でないリスト・添字の検査済みの値も加えていない。
- 形式化（`formal/`）への影響。

### TODO-032 大きなスクリプトの検査の時間

- 状態: 要検証
- 旧: OPEN-009
- 出どころ: open-issues の OPEN-009（`../archive/2026-10-09-design-first-release/open-issues.md#open-009`）、07-02 性能（`../archive/2026-10-09-design-first-release/07-quality/07-02-performance.md`）（「測る項目」の検査にかかる時間）、完了時の測定の記録（`../../tools/bench/results/2026-10-09-first-release-4304d507f6bf.md`）（「起動と検査の内訳」「所見 2」）、later-issues の 11・22・118・F13（`sources/later-issues.md`）、0.0.9 の改造（`docs/archive/` の下の `2026-10-18-TODO-021_022_026_032_087_088_142_164_248_257_258_259_260-syntax-batch3/`）

約 1 万個の関数を並べて生成したスクリプトの `check` が約 1.1 秒かかった（最小実行版は約 17 ms）。何もしない `main` の検査は約 3.5 ms なので、差の約 1.08 秒は標準ライブラリの読み込みと検査だけの費用ではない。起動から終了までも約 8.6 ms（最小実行版は約 3.1 ms）に延びた。

最小実行版とは検査の規則とソースが違うので、この変化を同じ仕事の退行とは断定できない。検査の段（読み込み・字句解析・構文解析・名前解決・型検査）ごとの内訳を測り、規模に対して時間が線形を超えて増える処理がないかを調べる。初回リリース版はプログラム全体を毎回検査し直す（ADR 0156。「インクリメンタルな検査」の項目）。

0.0.9 で、関数の数に対して検査の時間が二乗で伸びる費用を減らした。0.0.8 の最後の本測定（`tools/bench/results/2026-10-18-1c545d8f5c5d.md` の所見 2）で、関数を一つずつ並べたスクリプトが 10,000 で 0.68 秒、20,000 で 2.62 秒かかり、プロファイルでは型検査の本体ごとの密な表（`NodeMap`）の初期化・走査・解放が大半を占めていた。型検査の本体ごとの表（`typeck/context.rs` の `Body`）と、宣言の検査の本体ごとの表（`typeck/decls.rs` の `Scope`）を、本体に実在する番号だけを持つ疎な表に替えた。数値目標（I_map(10000) ≤ I_old(10000)/4 など）の判定は、TODO-262 の本測定に移した。上の約 1.1 秒のうち何が残るかも、その測定の後に確かめる。

規模に対して線形を超える処理として、初回リリース版の作業の確認で見つかった次のものが残っている（0.0.9 は扱っていない）。どれも分岐の数や連鎖の長さが大きい入力で現れるもので、上の約 1.1 秒（関数の数が多い入力）の原因かどうかは確かめていない。

- 網羅性の判定が、リテラルの分岐の数 n に対して約 O(n³) になる（later-issues の 11）。`typeck/patterns.rs:192-247` の `shapes` は区間ごとに全リテラルを走査し、文字列の重複の除去も線形の探索（`patterns.rs:237-245`）である。990 分岐でリリースのビルドが 0.27 秒と計測済みで、絶対値は小さい。次の事項とあわせて、予算を設けるか計算量を改めるかを決める。
- 網羅性の検査と判定の木への変換が、分岐の数に対して指数的に増える（later-issues の 118）。`typeck/patterns.rs` の網羅性の検査は 16 本の分岐で 9.9 秒かかり、40 本では終わらない。`ir/decision.rs` の判定の木への変換は 24 本で 4 GiB を超える。どちらにも予算や上限がない。予算を設け、超えたら診断か処理系の制限として止める。
- コード生成の自由変数の走査が、長い `let` の連鎖で O(N²) になる可能性がある（later-issues の 22。推測で、測っていない）。`bytecode/codegen/analysis.rs:211-215` の `with_reads` と `captured`、`emit.rs:216-222` が、残りの本体を毎回 `free_keys` で走査する。自由変数の集合を下から一度だけ求める案がある。コード生成は上の検査の段に含まれないので、測るときは段を分けて測る。
- コア IR の検査（`ir/check.rs`）が、子を検査するたびに `Env`（複数の `BTreeMap` を持つ。`check.rs:49-57`）を丸ごと clone する（`check.rs:448,597,662,1040,1134`）ので、長い `let` の連なりで O(n²) になる（later-issues の F13）。`check_program` を呼ぶのはテストの補助（`ir/desugar.rs:372`）だけなので、本番の検査の時間には影響せず、テストの時間だけに影響する。テストの時間の問題として残すか、可変の表と巻き戻しの形に改めるかを決める。
