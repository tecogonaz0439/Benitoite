## FE-02: 型クラスの辞書の解決

### 所見の確かめ

コードの位置は次のとおりである。

- `src/typeck/traits/solve.rs:61` の `resolve` は、型が型構成子なら実装を表から引き、その実装の型パラメータの制約ごとに `resolve` を再帰で呼ぶ（`:170-180`）。結果は `DictExpr::Impl { args: Vec<DictExpr> }` の木で、同じ（型クラス、型）の組を何度でも解き直す。組み込みの制約の並び `bounds` も子の並びをそのまま継ぐ（`:179`）ので、同じ割合で増える。
- 呼び出し元は、本体の制約（`solve_classes`、`:227-288`）、実装の上位の型クラス（`src/typeck/traits/impls.rs:130-131`）、修正案の判定（`src/typeck/traits/mod.rs:72-87` の `implements`）の三つである。
- `DictExpr` は木である（`src/types/mod.rs:288-300`）。型検査の出力 `dicts: NodeMap<Vec<DictExpr>>`（`src/typeck/mod.rs:95`）と `ImplDef::supers`（`src/types/mod.rs:271`）に入る。
- 後の段も木を節ごとに辿り、同じ大きさのものを作る。脱糖 `src/ir/desugar/dicts.rs:7-40`（`DictVal` の木）、コア IR の検査 `src/ir/check.rs:676`、参照インタプリタ `src/refinterp/eval.rs:277`（節ごとに値を作る）、コード生成 `src/bytecode/codegen/emit.rs:1143-1176`（節ごとに `DICT` の命令を一つ出す）と `src/bytecode/codegen/tables.rs:220-238`（上位の型クラスの辞書の作り方）。実行時は、`DICT` の命令（`src/vm/dispatch.rs:480`）が評価のたびに節ごとの辞書の値を作る（推測。命令の処理は読んでいない）。

測った結果は次のとおりである（debug のビルド。`trait_N` は N 段の入れ子のリストを `consume` に渡す、レビューと同じ形）。

|---|---|---|
| trait_10 | 0.03 秒・19 MiB | |
| trait_12 | 0.03 秒・20 MiB | 0.19 秒・32 MiB |
| trait_14 | 0.07 秒・24 MiB | 0.71 秒・62 MiB |

`check` は深さが 2 増えるごとに約 4 倍になり、節の数 2^(N+1) − 1 と合う。`run` は同じ深さで `check` の 10〜14 倍かかる。`run` の時間の内訳（脱糖・コード生成・実行）は分けて測っていない。

### 直し方

案は三つある。

- 案 A（予算だけ）: `resolve` に仕事量の数え（呼び出しごとに 1。辞書の節の数に等しい）を渡し、一つの辞書（呼び出し元の一回の `resolve`）の数えが上限を超えたら、新しい `Failure::Limit` を返して制限の診断にする。木の表現は変えない。超えた時点で解決をやめるので、検査の時間とメモリは上限に比例し、後の段が作るものも辞書ごとに上限で抑えられる。修正案の判定（`implements`）は、上限に当たれば実装がないものとして扱う（修正案を出さないだけで、誤りを隠さない）。
- 案 B（記憶と DAG）: 解決の結果を（型クラス、正規化した型）の鍵で覚え、辞書を共有の表現にする。型パラメータ（`ITy::Param`）を含む鍵は、いま検査している定義の制約によって結果が変わるので、記憶は本体ごと（`solve_classes` の一回）に持つ。記憶だけでは出力の木を写すたびに指数的になるので、`DictExpr` の子を `Rc` か表の番号にする必要がある。そうすると、脱糖の `DictVal`（`src/ir/core_ir.rs:169-186`）、コア IR の検査、参照インタプリタ、コード生成（共有した部分の辞書を一度だけ作ってレジスタに置く）、形式化の E2 の交換形式（型検査の出力の辞書。07-04 の段階 E2）まで共有を保たなければ、後の段で同じ増え方が戻る。コア IR に辞書の局所の束縛を足すことになれば、01-12「型クラス」と性質 1 の形式化（段階 C5）に触れる（推測）。
- 案 C（A と記憶）: 案 A に、本体ごとの記憶で「この（型クラス、型）の辞書の節の数」を覚える処理を足し、木を作る前に大きさを求める。検査の段の時間は線形になるが、出力の木の大きさは案 A と同じく上限で抑えるしかない。

推奨は案 A である。案 A だけで検査の段と後の段の両方が上限で抑えられ、普通のプログラムでは辞書の節の数が型の節の数と同程度にとどまる（指数的になるのは、各段の実装が同じ型パラメータに二つ以上の利用者の型クラスの制約を求める形に限られる）。案 B は大きな変更のわりに、正しいプログラムで得るものが少ない。

予算の単位と範囲は次のとおりとする。

- 単位は辞書の節（`resolve` の呼び出し）の数とする。節ごとの仕事には型の置き換え（`finalize`・`zonk`）が含まれ、型の大きさに比例するが、型は既存の上限（深さ 1,000、節 16,384。`src/typeck/limits.rs`）で抑えられる。
- 範囲は一つの辞書とする。辞書の数は制約を持つ名前の使用の数で、ソースの大きさに比例するので、プログラム全体の量は「上限 × 使用の数」で抑えられる。プログラム全体の予算も設けるかは問いの候補 2 に挙げる。

### 影響

- 処理系: `src/typeck/traits/solve.rs`（`resolve` の数えと `Failure::Limit`、`report` の診断）、`src/typeck/traits/impls.rs` と `src/typeck/traits/mod.rs`（呼び出し元）、`src/diag/codes.rs`（新しいコード）、`src/typeck/text`（上限の値を埋める型板。E0208 の `TYPE_NODES` と同じ形）。

## FE-03: 網羅性と選ばれない選択肢の判定

### 所見の確かめ

コードの位置は次のとおりである。

- `src/typeck/patterns.rs:60-95` の `check_match` は、選択肢ごとに前の行の行列に対する有用性（`:66`）、全体の網羅性（`:90`）を調べ、選ばれない選択肢には覆っている分岐を求める（`covering_alternatives`、`:498-542`。一行だけの行列と先頭からの接頭辞の行列で有用性を繰り返す）。束縛の文は `is_irrefutable`（`:97`）と、必ず照合しないときの反例のための `check_match` を使う（`src/typeck/pattern_ext.rs:377-390`）。
- 有用性の探索 `usefulness`（`:357-440`）は、先頭の列の構成子ごとに行列を特殊化して再帰する。`Boolean` は `true` と `false` の二つに分ける（`:213-215`）。仕事量の数えも、同じ行列の結果の記憶もない。
- レビューの入力では、各群の 4 欄について「最初に `true` になる位置」の 4 通りの道が、同じ残りの行列に行き着く。`true` を先に試し、`false` の道では行が残るので、探索は 4^n の道をすべて辿る。

測った結果は次のとおりである（debug のビルド。`pat_N` はレビューの `pattern_groups4_N` と同じ形）。

| 入力 | `check` | `run` |

| pat_4 | 0.02 秒・19 MiB | |
| pat_6 | 0.05 秒・19 MiB | 0.46 秒・66 MiB |
| pat_7 | 0.12 秒・20 MiB | 1.79 秒・199 MiB |
| pat_8 | 0.41 秒・20 MiB | 7.28 秒・723 MiB |
| pat_9（2,066 バイト） | 1.57 秒・20 MiB | |

`check` のメモリは増えず、時間が約 4 倍ずつ増える。`run` の増え方は判定の木の生成による（次の節）。

探索の仕事量を確かめるため、`usefulness` を `Boolean` だけの行列について Python に写し（`check_match` と同じく、選択肢ごとの判定と全体の網羅性の判定を順に行う）、呼び出しの数と、特殊化で作った行列のセルの数を数えた。

記憶の鍵は（型の並び、行列、問い）とし、一つの `match` の判定の間だけ持った。n=9 の debug の 1.57 秒は、記憶なしの呼び出し約 175 万回に当たり、debug で 1 回あたり約 0.9 マイクロ秒である。写しは処理系の手順を `Boolean` に限って書き直したもので、処理系の数と完全には一致しない（推測）。

選ばれない分岐が多い形も確かめた。`pat_8` の最後の 2 分岐を先頭に移すと、8 個の分岐が選ばれない（E0602 が 8 件）。この入力は 0.71 秒かかり、`covering_alternatives` の繰り返しも同じ増え方をする。

### 直し方

予算は、有用性の手順の外から「網羅していると確かめられなかった」と報告する保険として設ける。網羅していると決めつけて通すことはしない。

- 単位: `usefulness` の呼び出しごとに、特殊化で作った行列のセルの数（行の長さの和）と 1 を足す。セルの数は時間とメモリの両方に比例する。
- 範囲: 一つの `match`（`check_match` の一回）と、一つの束縛の文（`is_irrefutable` と反例のための `check_match`）。選択肢ごとの判定、全体の網羅性、`covering_alternatives`、`overlaps` を同じ予算で数える。
- 超えたとき: その `match` の判定をやめ、選ばれない選択肢と網羅性の診断（E0601・E0602・E0607・E0608）を出さずに、新しい診断 E0609 を一つ出す。`check` は終了状態 2 で終える。予算に当たる前に見つけた選ばれない選択肢も出さない（判定の途中の結果を混ぜると、同じソースで予算の大きさによって診断が変わるため）。`covering_alternatives` だけで予算に当たったとき（選ばれないことは決まり、覆っている分岐の補助の位置だけを求めているとき）は、E0602 を補助の位置なしで出す案もある。手順を簡単にするため、推奨は E0609 にまとめることである。
- 公開の API: `check_match` と `is_irrefutable` は `tests/coverage_export.rs` が直接呼ぶ公開の関数なので、結果に「判定をやめた」を表す形（`MatchIssue::Undecided` か `Result`）を足すと、差分テストの書き出しも直す。

記憶と列の選び方は、次のように扱う。

- 記憶: 一つの `match` の判定の間、（型の並び、行列、問い）から結果（反例の並びか、有用でないこと）を引く表を持つ。`usefulness` は同じ入力に同じ結果を返す関数なので、記憶は結果を変えず、Lean の手順との一致も保つ。表に入れた行列のセルも予算に数えれば、記憶のメモリも予算で抑えられる。`Pat` に `Hash`（または `Ord`）の derive を足す（`Ty` は既に `Hash` を持つ。`src/types/mod.rs:93`）。上の表のとおり、レビューの入力は記憶があれば n=10 でも数万セルで終わり、予算に当たらない。
- 列の選び方: 一番右の列を先に調べれば、レビューの入力は直ちに終わる。ただし、反例の文字列と、選ぶ道によっては Lean の手順の結果（`firstUseful` は左の列から構成子の順に選ぶ）が変わり、Lean の定義と 02-05 の写しを同時に直す必要がある。この改造では変えない。
- 有用性の判定は、一般の入力では記憶を足しても指数的な時間がかかる入力が残りうる（推測。パターンの網羅性の判定は一般に NP 困難と言われるが、出典を確かめていない）。したがって記憶は性能の改善であり、予算は外せない。

推奨は、予算（必須）と記憶（入れる）の両方をこの改造で行い、列の選び方は変えないことである。記憶を入れないと、レビューの入力の n=8 前後から E0609 になり、正しい `match` を拒む範囲が記憶ありより広い。

### 判定の木の生成（`src/ir/decision.rs`）

`check` は判定の木を作らない（`src/cli/mod.rs:515-536` は `run` のときだけ脱糖とコンパイルを行い、`src/pipeline.rs:200-213` の `compile` が `lower_program` を呼ぶ）。判定の木の生成は、網羅性の判定とは別の手順であり、次の形で出力が増える。

- `tree`（`:519`）は、先頭の行の最も左の検査する列を選び、構成子・定数・区間・長さごとに行列を特殊化して再帰する（`ctor_tree` の `:668`・`:671`、`const_tree` の `:734`・`:737`、`range_tree` の `:898`・`:900`、`list_branch` の `:1055`）。ワイルドカードの行は特殊化したすべての枝に写る（`Matrix::specialize`、`:475-509`）。同じ残りの行列の木を共有しないので、木の大きさは入力に対して指数的になりうる。分岐の本体は、葉が二つ以上あるときに飛び先（join）を作って共有する（`count`、`:416-457`）が、検査の木そのものは共有しない。
- `emit`（`:1107-1200`）は、木を同じ大きさの下位 IR に移し、コード生成はその節ごとに命令と分岐表を作る。

測った結果は次のとおりである（debug のビルド）。`tree_N` は、`Boolean` の欄を 2N 個持つレコードについて、i 番目の分岐が 2i 番目と 2i+1 番目の欄を `true` と決め、最後に `case _` を置いた `match` である。網羅性の判定は先頭の行が `case _` を含むので速い。

| 入力 | `check` | `run` |
|---|---|---|
| tree_8 | 0.02 秒・19 MiB | 0.05 秒・24 MiB |
| tree_10 | 0.02 秒・20 MiB | 0.12 秒・32 MiB |
| tree_12（1,550 バイト） | 0.02 秒・20 MiB | 0.39 秒・62 MiB |

`run` は N が 2 増えるごとに 4〜6 倍になる。どれも終了状態 0 で、L01 の制限（分岐表の数 65,536 など）には当たらなかった。時間が判定の木の生成とコード生成のどちらに多くかかっているかは分けて測っていない。増え方の原因が判定の木の重複であることは、コードを読んだ判断である（推測）。

この増え方は `check` では出ないので、TODO-195 の題（check の資源消費）の外にある。ただし、`run` と `test` は実行の前にこの段を通るので、利用者が実行を許可した後、スクリプトの最初の行を実行する前にメモリを使い尽くしうる。また、網羅性の判定に予算を設けても、予算の内側の入力（pat_7 の `run` が 1.79 秒・199 MiB）でこの増え方は残る。

案は三つある。

- 案 T1（予算）: 一つの `match` の判定の木の節の数（または特殊化で作った行列のセルの数）に上限を設け、超えたら新しい処理系の制限 L0112 を出して実行しない。`lower_program` の誤りの型を `InternalError` から、制限と不具合を分けた形（`CompileError` と同じ形）に変える。L01 の先例どおり、`check` は出さず `run` と `test` だけが出す（02-07「処理系の制限」、言語リファレンスの「`L` for limits of `benitoite` (reported by `run` and `test` only)」）。
- 案 T2（木の共有）: 同じ残りの行列の木を記憶し、飛び先（join）として共有する。共有する木が参照する変数（特殊化で作った欄の変数と、それまでに束縛したパターンの変数）を飛び先の引数にする必要があり、02-06「判定の木への変換」の手順を書き直す。大きさの最悪は抑えられない（推測）。
- 案 T3（行ごとの照合への切り替え）: 木が上限を超えた `match` だけ、分岐を上から順に照合する形（行ごとに入れ子の検査を作り、失敗したら次の行へ飛ぶ）で下位 IR を作る。出力はパターンの大きさの和に比例し、利用者に制限を見せない。照合の結果は同じだが、下位 IR の第二の作り方と、そのテスト（判定の木との結果の一致）が要る。

推奨は案 T1 をこの改造で行い、案 T2・T3 を docs/todo の新しい項目にすることである。案 T1 は小さく、ほかの L01 の制限と同じ扱いで説明できる。正しいプログラムの `match` の木は、普通は数百の節に収まる（推測）。

## Lean との揃え方（07-04「01-12 との対応」）

今の形は次のとおりである。

- 02-05「本体の後の検査」は、有用性の手順について Lean の定義（`formal/Benitoite/Release/Coverage.lean`）を正とし、処理系が Lean の定義と違う点を 02-05 に差として記すと定めている（07-04「01-12 との対応」の 132 行）。
- Lean の `usefulFuel`（`Coverage.lean:298-331`）は、入力の大きさから決めた燃料（`fuelFor`、`:363-366`。再帰の深さの燃料で、仕事量ではない）で再帰を打ち切り、尽きたときは「有用」と答えて `fuelExhausted` を記録する。補題 U（`usefulFuel_none_sound`、`:1181`）は「有用でない」と答えた場合だけを言明するので、燃料切れを含めて成り立つ。
- 差分テスト（`formal/CoverageDiff/Main.lean`、`formal/CoverageProgramDiff/Main.lean`）は、燃料切れの数が 0 であることを確かめる（`CoverageDiff/Main.lean:307`）。入力は、`tests/coverage_export.rs` の無作為な 10,000 件（型の深さ 3、パターンの節 40 以下、分岐 6 以下、選択肢 3 以下）と境界の 20 件、ゴールデンテストの `match` である（07-03「差分テスト」）。

案は三つある。

- 案 L1（対象外として書き足す。推奨）: 処理系の仕事量の予算と、予算を超えたときの E0609 を、形式化の対象外として 07-04 の段階 E1 の行に書き足す。02-05「本体の後の検査」に、処理系と Lean の差として「処理系は一つの `match` の判定の仕事量に予算を持ち、超えたら判定をやめて E0609 を出す。予算の内側で答えた結果は Lean の手順の結果と同じである」と書く。記憶は結果を変えないので、差として書かない（性能のための実装の詳細として 02-05 に一文書く）。差分テストでは、処理系の書き出しが予算に当たった件数を数え、0 であることを確かめる（Lean の燃料切れと同じ扱い）。
- 案 L2（Lean に仕事量の燃料を足す）: `usefulFuel` を、深さの燃料に加えて仕事量の数えを引き回す形に書き換え、尽きたら「判定をやめた」を返す。処理系と同じ単位で数えれば、予算に当たる `match` まで差分テストで一致を確かめられる。代わりに、`usefulFuel` と `firstUseful` の定義、補題 U とその系の証明（`Coverage.lean:1181-1300` ほか）を直す必要があり、予算の単位を変えるたびに Lean も直すことになる。
- 案 L3（予算を超えたら「有用」と答える）: Lean の燃料切れと同じく、予算を超えたら「有用」と答え、E0601 と問いの形の反例を出す。補題 U の向きは保つが、網羅している `match` に「網羅していない」と誤った反例を示すので、02-10 の診断の明確さと TODO-195 の「網羅していると確かめられなかった」と報告する方針に反する。採らない。

推奨は案 L1 である。予算を超えた `match` は受け付けないので、処理系が受け付けた `match` の判定はすべて予算の内側で行われ、そこでは処理系と Lean の手順の結果が一致する（差分テストで確かめる範囲）。したがって、補題 U と網羅性の系（`checkMatch_exhaustive_sound` など）を処理系に結び付ける論証は、予算を足しても変わらない。07-04「01-12 との対応」の 163 行の決まりは、触れる要素が形式化の範囲の外なら表に「対象外」を書き足すとしており、予算はこの場合に当たる。

差分テストが予算に当たる入力を生成しうるかについて、`tests/coverage_export.rs` の書き出しを一度走らせ、10,020 件を debug で 5.0 秒（JSON の書き出しを含む）で終えた。1 件あたり平均 0.5 ミリ秒であり、上の測定（n=7 の `check` が 0.12 秒）と比べて予算の候補（後述）より十分小さい（推測。件ごとの最大は数えていない）。実装では、書き出しが予算の使用量の最大を報告するようにして確かめる。`coverageProgramDiff` の入力はゴールデンテストの `match` なので、同じく予算に当たらない（推測）。

判定の木（案 T1）と辞書の予算（FE-02）は、形式化の範囲の外（判定の木は 02-06 の下位 IR、型クラスの制約の解決は形式化していない）なので、Lean は変えない。E2 の検査（`surfaceCheckAll`）は型検査を通ったプログラムだけを入力にするので、予算に当たったプログラムは現れない。

## 予算の大きさの決め方

次の手順を推奨する。

1. 予算の数えを実装した後、使用量の最大を報告する仕組み（テストからだけ呼べる関数か、`#[cfg(test)]` の計数）で、標準ライブラリのソース、`testdata/` のゴールデン、`crates/benitoite/examples/`、`tools/bench/` のスクリプト、`tools/skill-eval/` の課題の解答、`docs/reference/benitoite.md` の例（`tests/reference_examples.rs`）、網羅性の差分テストの 10,020 件を検査し、辞書の節の数・網羅性の仕事量・判定の木の節の数の最大を記録する。
2. 予算は、その最大の 100 倍以上で、かつ一つの `match`（辞書）の予算いっぱいの処理が release のビルドで 0.1 秒前後に収まる大きさの 2 の冪とする。
3. 予算いっぱいの入力（レビューの形を大きさだけ変えたもの）の時間を、debug と release の両方で測って記録に残す。

上の測定からの初めの見込み（推測）は次のとおりである。

| 予算 | 見込みの大きさ | 根拠 |
|---|---|---|
| 一つの辞書の節の数 | 16,384（型の節の数の上限 `MAX_TYPE_NODES` と同じ） | 型の節に比例する正しい辞書を拒まない。trait_13（16,383 節）まで通り trait_14 で当たる。debug の `check` は 0.07 秒以下 |
| 一つの `match` の網羅性の仕事量 | 2^20（約 105 万セル） | 記憶なしで n=7（約 85 万セル、debug の `check` 0.12 秒）まで通り、n=8 で当たる。記憶ありならレビューの入力には当たらない |
| 一つの `match` の判定の木の節の数 | 16,384 | tree_12 前後で当たる見込み（debug の `run` 0.39 秒・62 MiB） |

プログラム全体の予算は、辞書と網羅性のどちらも、ソースの大きさに比例する数（使用と `match` の数）を掛けた量で抑えられる。それ以上に抑えるかは問いの候補 2 とする。

## 問いの候補

1. 予算の大きさ
   - 選択肢: (a) 上の見込み（辞書 16,384 節、網羅性 2^20 セル、判定の木 16,384 節）で始め、実装の後の測定で直す。(b) 先に測定の仕組みだけを作って最大を測り、その結果から決める。(c) 定数の予算と同じく、バイト数（作った値の大きさ）で数える。
   - 推奨: (a)。理由: 見込みは正しいプログラムの規模より桁違いに大きく、実装の作業の中で測定の手順 1〜3 を行って直せる。(c) は辞書と行列のメモリの見積もりが型ごとに変わり、説明しにくい。
2. 予算の範囲（一つの辞書・`match` ごとか、プログラム全体か）
   - 選択肢: (a) 一つの辞書・一つの `match` ごとだけ。(b) それに加えてプログラム全体の予算（例えば一つの予算の 64 倍）。(c) プログラム全体だけ（定数の予算 E0435 と同じ）。
   - 推奨: (a)。理由: 診断の位置が明確で、利用者（LLM）が直す箇所（その `match` を分ける、`case _` を足す）が分かる。プログラム全体の量はソースの大きさに比例する数で抑えられ、ソースの大きさには上限（256 MiB・512 MiB。02-02）がある。(b) は、大きなプログラムで、どの `match` を直せばよいかを示せない診断になる。
3. 診断の番号と文言
   - 空きは、E06 の続き E0609、E07 の続き E0715、L01 の続き L0112 である（`src/diag/codes.rs` の表と廃止のコードの一覧 `RETIRED` を確かめた。E0444 は廃止）。
   - 案: E0609 `could not confirm that this \`match\` covers every value` ／ラベル `checking stopped after {limit} steps` ／修正案 `split the \`match\` into smaller ones, or check fewer fields in one branch`。束縛の文には同じコードで `could not confirm that this pattern matches every value` を出すか、文言の型板を分ける。E0715 `the dictionary for \`{trait_name}\` on \`{ty}\` is too large` ／ラベル `more than {limit} parts are needed here` ／説明に、同じ型パラメータに二つ以上の制約を求める実装を入れ子にすると辞書が倍々に増えることを書く。L0112 `the \`match\` in \`{name}\` is too large to compile` ／注記 `a \`match\` can have at most {limit} tests; split it into smaller ones`。
