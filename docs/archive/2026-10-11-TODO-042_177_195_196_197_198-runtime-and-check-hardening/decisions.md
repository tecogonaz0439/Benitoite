# 判断と問い

設計者に決めてもらう問いである。選択肢・推奨・理由を示す。根拠の詳細は、各問いに挙げた調査の文書にある。

## `uses` の別名（TODO-177 の F-2。`study-uses.md`）

### Q1 直し方の強さ

- 選択肢: (a) エフェクトを宣言する標準ライブラリのモジュールへの `as` を誤りにする／(b) 警告にする／(c) 別名を許し、処理系が本来の名前で `uses` を示す／(d) `uses` には本来の名前だけを書けるようにする。
- 推奨: (a)。新しい診断 E0339 を加える。
- 理由: 偽装の経路は別名の一点だけなので、そこを閉じれば「`main` の `uses` を読めば分かる」（言語リファレンスと同梱の Skill の手順）が成り立つ。警告では、偽装を意図するスクリプトを止められない。(c) は初回リリース版に含めないと決めた実行前の権限の表示に当たる（docs/todo の TODO-143）。(d) は名前の引き方に特別な規則を足す（設計原則 5）。今のリポジトリでこの形の別名を使うのは、単体テスト 1 件だけである。

### Q2 対象のモジュールと、本来の名前と同じ別名

- 推奨: 組み込みのエフェクトを宣言するモジュールのすべて（`Benitoite.IO`、`Benitoite.IO.Console`・`File`・`Process`・`Clock`・`Random`、`Benitoite.Network.Http`、`Benitoite.Assert`）を対象とし、名前の綴りではなく組み込みのエフェクトの表から決める。`as Console` のように本来の名前と同じ別名も誤りにする。純粋なモジュール（`Json`・`Time`・`Trait` など）への `as` は今までどおり許す。
- 理由: `IO.*` と `Network.*` だけでは、`import Benitoite.IO as Pure` の `uses Pure.All` が漏れる。本来の名前と同じ別名は意味がなく、例外を作らないほうが規則と診断が短い。

### Q3 名前の衝突の修正案

- 推奨: E0323（二つの import の名前が同じ）は、`as` の編集を利用者のモジュールの側に付ける。E0305（import の名前がトップレベルの宣言と同じ）は、対象のモジュールなら `as` の編集を出さず、宣言の名前を変えるよう示す。同梱の Skill は、import の箇条に一文を足すだけにする。
- 理由: 今の修正案（`as IOConsole`・`as IOFile`）は、Q1 の (a) の後に E0339 を生む。

## check の資源消費（TODO-195。`study-check.md`）

### Q4 予算の範囲と、判定の木を含めるか

- 選択肢: 予算を設けるのは (a) 辞書の解決と網羅性の判定の二つ（TODO-195 の範囲）／(b) それに判定の木の生成を加えた三つ。
- 推奨: (b)。どれも一つの辞書・一つの `match` ごとの予算とし、プログラム全体の予算は設けない。
- 理由: 網羅性の判定に予算を設けても、その内側の入力で `run` と `test` が指数的なメモリを使う（予算の内側の n=7 で `run` が 1.79 秒・199 MiB）。判定の木の予算は、既存の処理系の制限（L01、`run` と `test` だけが出す）と同じ扱いで説明できる。一つの辞書・`match` ごとにすれば、診断の位置から直す箇所が分かる。プログラム全体の量は、使用と `match` の数（ソースの大きさに比例し、ソースには上限がある）で抑えられる。

### Q5 予算の大きさ

- 推奨: 一つの辞書は 16,384 節、一つの `match` の網羅性の判定は 2^20 セル、一つの `match` の判定の木は 16,384 節の見込みで始める。作業の中で、標準ライブラリ・ゴールデン・例・`tools/bench`・`tools/skill-eval` の解答・言語リファレンスの例・網羅性の差分テストの入力の最大を測り、その 100 倍以上で、予算いっぱいの処理が release のビルドで 0.1 秒前後に収まる 2 の冪に直す。測った値は改造の記録に残す。
- 理由: 見込みは正しいプログラムの規模より桁違いに大きい。測ってから決めるために作業を二段に分けるより、作業の中で測って直すほうが手間が少ない。

### Q6 診断の番号

- 推奨: E0715（辞書が大きすぎる）、E0609（網羅していると確かめられなかった）、L0112（判定の木が大きすぎる）。`src/diag/codes.rs` の空きを確かめてある。網羅していると決めつけて通すことはせず、予算を超えた `match` は誤りとする。予算を超えたときは、その `match` の選ばれない選択肢と網羅性の診断を出さず、E0609 を一つだけ出す。
- 理由: 検査の段の上限は、E0208（型が深すぎる）と E0435（定数の評価の予算）が E のコードで報告している先例がある。予算に当たる前に見つけた診断を混ぜると、同じソースで予算の大きさによって診断が変わる。

### Q7 言語仕様（01-spec）に書くか

- 推奨: 01-05「網羅性の検査」に「処理系は判定の仕事量に上限を設けてよく、上限を超えた `match` は誤りとする」と一文書き、01-06「型クラス（初回リリース版）」にも辞書の大きさについて同じ形の一文を書く。
- 理由: 01-05 は網羅したと判定しない `match` を誤りとしており、上限で判定をやめる場合もその中に入ることを規範として書ける。02-05 だけに書くと、仕様だけを読む実装者が上限の存在を知らない。

### Q8 形式化（Lean）との揃え方と、網羅性の判定の記憶

- 選択肢: (L1) 予算と E0609 を形式化の対象外として 07-04「01-12 との対応」の段階 E1 の行に書き足し、02-05 に処理系と Lean の差として書く／(L2) Lean の有用性の手順に仕事量の燃料を足し、証明を直す／(L3) 予算を超えたら「有用」と答える（Lean の燃料切れと同じ）。
- 推奨: (L1)。あわせて、一つの `match` の判定の間、同じ行列の結果を覚える処理をこの改造で入れる。列の選び方は変えない。
- 理由: 予算を超えた `match` は受け付けないので、受け付けた `match` の判定は予算の内側で Lean の手順と一致し、補題 U を処理系に結び付ける論証は変わらない。(L2) は予算の単位を変えるたびに Lean も直すことになる。(L3) は網羅している `match` に誤った反例を示す。記憶は結果を変えないので Lean との一致を保ち、記憶があればレビューの入力は予算に当たらずに通る。列の選び方を変えると反例の文字列が Lean の手順と変わる。

### Q9 辞書の共有の表現（DAG）と、判定の木の共有

- 推奨: どちらもこの改造では採らず、予算だけにする。判定の木の共有と、上限を超えた `match` だけ分岐を上から順に照合する形への切り替えは、docs/todo の新しい項目にする。
- 理由: 辞書の DAG は、脱糖・コア IR の検査・参照インタプリタ・コード生成・形式化の E2 の交換形式まで変える。普通のプログラムの辞書と判定の木は小さく、予算で各段の大きさが抑えられる。

### Q10 `Regex.find` の入力の写し

- 選択肢: (A) `Match` が元の文字列の値を追跡される `Slot` で指す／(B) `Match` に一致の部分だけを写す／(C) 写しを残し、TODO-042 で容量を数えるだけにする。
- 推奨: (B) と TODO-042 の容量の計上。名前付きグループの名前の表は、組み立てのときに一度作って `Pattern` に持たせる。
- 理由: 言語から見える値（`matchText`・位置・グループ）は変わらず、変更が `regex.rs` に閉じる。(A) は、純粋な組み込みの関数の文脈に `Host` と `Slot` を作る口を足す設計の変更になる。(C) は呼び出しごとに全文を写す時間が残る。

### Q11 容量の計上の範囲（TODO-042）

- 推奨: `OpaqueData`・`HostData` に既定で 0 を返す容量の関数を足し、確保のときに数え、`host_mut` の後に数え直す。容量が減ったときは生きている量から引くが、前回の回収からの確保の量 A は減らさない。`Rc` で共有する領域は数えない（共有をやめる）。枠の積み重ねを持つ `TaskObj`・`ContState` の容量は 0 のままにし、扱いを docs/todo の新しい項目にする。`Pattern` の内部の容量（regex の自動機械）は数えず、docs/todo の TODO-185 で扱う。
- 理由: 枠の積み重ねは止めるたびに移すだけで確保していないので、数え直しで A に加えると、タスクの切り替えや `perform` のたびに回収が増える。積み重ねは呼び出しの情報の上限が別に抑えている。regex 1.13.1 の `Regex` は容量を返さない。

### Q12 繰り返す照合の 2 乗の時間（TODO-196）

- 選択肢: (1) 文書を直すだけ／(1＋2) 文書を直し、二度の走査を一度にする／(5) 一致ごとに区切って、標準ライブラリのソースのループで照合し、取り消しと中断を効かせる。
- 推奨: (1＋2)。(5) は docs/todo の新しい項目にする。入力の長さや時間の上限は設けない。
- 理由: 文書（標準ライブラリのソースと言語リファレンスの「線形」）は実際と合わないので必ず直す。二度の走査をやめるのは定数倍の改善で、作業は小さい。(5) は取り消しを効かせる決定的な手段だが、空の一致の扱いと性能の確かめが要り、ほかの直しより大きい。入力の長さの上限は普通のログの処理を拒み、時間の上限は結果が実行ごとに変わる。

## HTTP（TODO-198。`study-http.md`）

### Q15 1xx の応答

- 選択肢: (A) `Http.respond` は 1xx を実行時エラーにする（範囲を 200〜599 にする）／(B) 今のまま送って閉じる／(C) 処理系の 500 に置き換える。
- 推奨: (A)。互換でない変更として CHANGELOG に載せる。
- 理由: `Http.respond` は一度しか応答できず、1xx を最終の応答として送るのは RFC 9112 §6.3 と RFC 9110 §15.2 に合わない。1xx を返すのはスクリプトの書き手が決めることで、要求を送る相手には引き起こせないので、止めて知らせてよい。(C) は誤りを隠す。

### Q16 本体を持たない応答（204・205・304、HEAD、CONNECT）

- 推奨:
  - 204・205・304 に渡した空でない本体は、黙って落とす。204 と 304 は `content-length` を送らず、205 は `content-length: 0` を送る。
  - HEAD への応答は本体を送らない。`content-length` は、渡された本体が空でなければその長さ、空なら送らない。
  - CONNECT への 2xx は、本体・`content-length`・`transfer-encoding` なしで送り、接続を閉じる。
- 理由: handler の実行時エラーはサーバ全体を止める。HEAD と CONNECT は要求を送る相手が選べるので、実行時エラーにすると一つの要求でサーバを止められる。`Http.text(204, "...")` は LLM が書きやすい形で、止めると影響が大きい。RFC 9110 §8.6 は、HEAD の `Content-Length` が GET の本体の長さと等しくなければ送ってはならないとする。

### Q17 要求の検査の範囲

- 推奨:
  - Host: HTTP/1.1 で Host がない要求と、版を問わず Host が二つ以上の要求に 400 を返す。値は使える文字の集合（英数字、`-._~`、sub-delims、`:`、`[`、`]`、`%`）だけを確かめる。
  - トレーラ: 頭のヘッダと同じ規則で確かめて捨てる。
  - 絶対形の対象（`GET http://host/path`）: scheme と authority を外して、起点からのパスにする。
  - `Expect: 100-continue`: HTTP/1.1 の要求で本体を読む必要があるとき、本体を読む前に 100 を送る。
- 理由: RFC 9112 §3.2 は Host の誤りを 400 で拒むことを求める。処理系は Host を使わず handler に渡すだけなので、区切りの文字や空白を入れさせないことが要点で、RFC 3986 の厳密な解析の手間に見合わない。RFC 9112 §3.2.2 はサーバが絶対形を受け付けることを求め、今の `path` は `Http.pathSegments` で正しく分けられない。RFC 9110 §10.1.1 は本体を待たずに 100 か最終の応答を送ることを求める。

### Q18 接続と警告の細部

- 推奨:
  - Linux の `accept(2)` の man ページが挙げる 8 つの errno（`ENETDOWN`・`EPROTO`・`ENOPROTOOPT`・`EHOSTDOWN`・`ENONET`・`EHOSTUNREACH`・`EOPNOTSUPP`・`ENETUNREACH`）は、接続ごとの失敗として次の受け付けに進む。`EPERM` は含めない。
  - `accept` の警告は、標準エラーに書く余地がなければ捨てる。
  - RFC 6585 の 428・429・431 の理由句を表に足す。
  - 応答から除くヘッダは `transfer-encoding` と `trailer` までとし、ほかの接続ごとのヘッダ（`keep-alive`・`upgrade` など）は docs/todo の新しい項目にする。
- 理由: man ページは、これらを `EAGAIN` と同じくやり直すよう求めている。`EPERM` は条文を確かめていない。警告は補助で、届かなくても処理は正しい。431 は処理系自身が返す。本体の区切りを壊すのは TE と CL の組だけである。

## 決まったこと

2026-10-11 に、設計者が Q1（誤りにする）・Q4（三つの予算）・Q13（`None` にする）・Q15（実行時エラー）を推奨どおりに選んだ。ほかの問い（Q2・Q3・Q5〜Q12・Q14・Q16〜Q18）は推奨どおりで進め、変えるときは設計者が知らせる。

作業 R の事前点検で、Q12 の 2（二度の走査を一度にする）を取りやめた。一度の走査にすると、リストの長さの上限を超える入力で、止めるまでに一致の位置を最大で上限の件数（16 Mi 件）だけ積むので、今の「先に数えてから作る」形より、誤りで止める前に使うメモリが大きく増える。得られるのは定数倍の改善だけであり、資源の消費を抑えるこの改造の目的に反する。文書の直し（Q12 の 1）は行う。
