## 要点

1. TODO-042 の未計上は今のコードで成り立つ。`alloc_opaque`・`alloc_host` は `size_of::<T>()` だけを確保の量に加える。`Regex.find` を 4 MiB の入力に繰り返すと、1 回あたり約 4.2 MB の常駐メモリが増え、確保の量は 1 回あたり 168 バイトしか増えなかった（32 回で最大 RSS 161 MB、回収は 1 回）。
2. 容量を返す口は、二つのトレイトに既定の本体（0 を返す）付きのメソッドを足す形でよい。対象ごとの記録（`ObjectRecord::charged_bytes`）が既にあるので、`host_mut` の後の数え直しと解放の引き算は、内部の層の安全なコードで書ける。新しい `unsafe` は要らない。注意すべき点は、枠の積み重ねを持つ `Host`（タスク・継続）で、確保ではない移動を確保の量 A に数えると、タスクの切り替えや `perform` のたびに A が増え、回収が増えることである。
3. TODO-196 の入力の写しは、`Match` に一致の部分だけを写す案（案 B）と、元の文字列の値を `Slot` で指す案（案 A）がある。言語から見える値（`matchText`・位置・グループ）はどちらでも変わらない。案 A は純粋な組み込みの関数の文脈（`PureCtx`）が `Slot` と `Host` を作れないので、ヒープの公開の層の API を足す必要がある。推奨は案 B と TODO-042 の組み合わせである。
4. 2 乗の時間は再現した（release で 64 KiB が 1.09 秒、128 KiB が 4.36 秒）。`replaceAll` と `split` も同じ形である。regex 1.13.1 の文書（`src/lib.rs` 1093〜1124 行）が、繰り返す照合を最悪 O(m n²) と書いている。照合の途中では取り消しも中断の要求（SIGINT）も効かない。SIGINT を送った実行が、照合の後にそのまま終了状態 0 で終わった（付随の所見）。
5. TODO-197 も再現した。`Task.withTimeout(20, …)` の中の `Regex.findAll` が 1,106 ミリ秒かかり、結果は `Some(65536)` だった。原因はレビューのとおりで、期限の判定が「満了を記録したか」だけで決まる。直し方は、子が終わった直後の境界で時刻を読んで判定を確定させる形が、命令の振り分けの速い経路を変えずに済む。

## TODO-042 `Opaque`・`Host` の対象が持つ別の領域の容量

### 所見の確かめ

確保の量の計上は、内部の層の `HeapCore::allocate`（`src/runtime/heap/core.rs` 254〜336 行）に集まっている。引数 `external` を、配置から求めた容量に足して `charged` とし（262〜265 行）、対象ごとの記録 `ObjectRecord::charged_bytes`（78〜83 行、306〜310 行）と、確保している量 `current_bytes`、統計の `allocated_bytes`、回収の方式への通知 `mode.allocated`（334 行）に渡す。解放（`free_object`）は記録の `charged_bytes` を `current_bytes` から引く（601〜606 行）。

`alloc_opaque`（462〜475 行）と `alloc_host`（476〜489 行）は、`external` に `size_of::<T>()` だけを渡す。467〜468 行と 481〜482 行のコメントが、別の領域を数えていないことと TODO-042 を明記している。トレイト（`src/runtime/heap/value.rs` 216〜224 行）は、`OpaqueData: Any + Debug {}` と `HostData: Trace + Any + Debug {}` であり、メソッドを持たない。

回収の要求は、`core/mark_sweep.rs` の `State::allocated`（42〜58 行）が、前回の回収からの確保の量 A が `max(L × k, 4 MiB)` に達したときに立てる。L は回収の終わりの `current_bytes` である（193〜203 行）。下限と係数は `src/runtime/heap/mod.rs` 29〜32 行（4,194,304 バイト、100%）。

再現（release、レビューの `regex_gc_source.bnt` の回数だけを変えたもの。入力は `A` が 4,194,304 個）:

| `Regex.find` の回数 | 最大 RSS | `allocated_bytes` | 回収の回数 |
|---:|---:|---:|---:|
| 1 | 31.2 MB | 4,195,560 | 1 |
| 16 | 93.9 MB | 4,198,080 | 1 |
| 32 | 161.3 MB | 4,200,768 | 1 |

### 直し方

#### 容量を返す口

二つのトレイトに、既定の本体を持つメソッドを足す。

```rust
pub trait OpaqueData: Any + Debug {
    /// この対象だけが所有する別の領域の容量（バイト）。共有する領域は数えない。
    fn heap_bytes(&self) -> usize { 0 }
}
```

`HostData` にも同じものを足す。既定が 0 なので、テストの型と、別の領域を持たない型は変えなくてよい。`Box<dyn OpaqueData>` として使うので、関連の定数は足せない（トレイトが dyn にできなくなる）。数え直しを省くための印が要るときは、`fn tracks_heap_bytes() -> bool where Self: Sized { false }` のように `Self: Sized` を付けた関数にすれば、dyn のままで型ごとに静的に分けられる。

#### 確保のときの計上

`alloc_opaque`・`alloc_host` は、値を `Box` に移す前に `data.heap_bytes()` を読み、`size_of::<T>()` に足して `external` に渡す。`allocate` の中は変えなくてよい。

#### `host_mut` の後の数え直し

`with_host_mut`（`core.rs` 941〜952 行）で、閉包 `f` から戻った後に `heap_bytes()` を読み直し、記録との差を反映する内部の関数（仮に `recharge`）を呼ぶ。

- 記録の位置は、頭の `index`（`allocate` が書き、`free_object` が更新する）で引ける。`objects` は `RefCell` であり、閉包が戻った後なので借用は衝突しない。閉包に渡す `SlotOps` は対象を確保も借用もしない（`core.rs` 先頭の O8）。
- 増えたときは、`charged_bytes`・`current_bytes`・`allocated_bytes`・`peak_heap_bytes` に差を足し、`mode.allocated` に差を渡す。減ったときは、`charged_bytes` と `current_bytes` から引き、A は減らさない（A は前回の回収からの確保の累計なので）。
- 記録を直さずに `current_bytes` だけを動かすと、解放の `checked_sub`（601〜606 行）が食い違いで `Stop::Internal` になるか、量がずれる。記録と合計を同じ関数で直すことが要る。
- この関数は内部の層（`core.rs`）に置くが、生のポインタを読まないので `unsafe` は要らない。`with_host_mut` が既に持つ `unsafe` のブロック（948〜949 行）はそのまま使う。AGENTS.md の「`unsafe` を書いてよいのは `runtime::heap` の内部の層だけ」には触れない。

#### 共有する領域を二重に数えない形

`Match` は、一回の `findAll` で作るすべての一致が、入力の写しと名前の表を `Rc` で共有する（`regex.rs` 139〜144 行）。各一致が `Rc` の中身を全部数えると、一致の数だけ同じ領域を数える。案は次の三つである。

| 案 | 内容 | 評価 |
|---|---|---|
| 共有をやめる | 大きな領域は対象ごとに持つか、ヒープの値にして `Slot` で指す | 正確。`Match` は TODO-196 の案 A・案 B のどちらでも共有がなくなる |
| 持ち主を一つに決める | 共有する領域を作った対象だけが数え、ほかは 0 | 持ち主が先に死ぬと、残りが数えられない。1 回の呼び出しにつき 1 つ分の過小 |
| 参照の数で割る | `capacity / Rc::strong_count` | 数えた時点の値で固定されるので、ほかの対象の死とともにずれる |

推奨は「共有をやめる」であり、トレイトの文書に「この対象だけが所有する領域を返す。`Rc` で共有する領域は数えない」と書く。名前の表は、今は `Regex.find` の呼び出しごとに作り直している（40〜48 行、122 行）。組み立てのときに一度作って `Pattern` に持たせ、`Pattern` の容量として数えれば、`Match` は名前の表を数えなくてよい。

#### 生きている量 L と確保の量 A への影響

- `Opaque` の別の領域は、組み込みの関数が新しく確保したものなので、A と L の両方に数えるのが実際に合う。`Match` の写しを A に数えれば、レビューの例では 1 回の `find` で A が約 4 MiB 増え、ほぼ呼び出しごとに回収が要求されるので、メモリは入力の数倍で止まる（推測。数え方を入れた版で確かめる）。
- `TaskObj` の枠の積み重ねは、実行中は実行ごとの状態（`RunState`）へ移してあり（`src/vm/task.rs` 99 行のコメント）、止まっている間だけ対象の中にある。`host_mut` で数え直すと、タスクを止めるたびに積み重ねの容量が「増えた」と数えられ、A に加わる。実際には `Vec` を移しただけで確保していない。`ContState` の捕まえた区画も、`perform` で積み重ねから移したもの（推測）であり、同じ問題がある。`tools/bench/programs/` の `tasks.bnt` と `handler.bnt` で回収が増えうる。
- したがって、この改造では、枠の積み重ねを持つ型（`TaskObj`・`ContState`）の `heap_bytes` は 0 のままにし、扱いを別の項目にするのがよい。積み重ねの大きさは、既に呼び出しの情報の上限（`src/vm/budget.rs` の `StackMeter`、既定 1 GiB）が抑えている。`HandlerRecord` と `LazyState` の `Vec` は小さいので、数えても数えなくても回収の時期はほとんど変わらない。

#### heap-verify と統計

- `HeapStats::allocated_bytes` の文書（`src/runtime/heap/stats.rs`）は「頭と切り上げと別の領域を含む」と書いており、今は事実と合わない。直した後は合う。
- 機能 `heap-verify` の検証（`core/verify.rs`）は、今は量の整合を調べていない。検証に「記録の `charged_bytes` の合計が `current_bytes` と一致する」ことと、「`Opaque` の対象の記録が、頭と箱と `size_of` と `heap_bytes()` の和と一致する」ことを加えると、数え直しの漏れを見つけられる。`Opaque` は作った後に変えない約束（`value.rs` 216〜218 行）なので、後者は内部の可変性で容量を変える型（regex の作業用の領域を持つ `Pattern` など）を見つける働きもある。ただし `Pattern` の内部の容量はそもそも返せない。
- `alloc-stats` の一行（`src/cli/mod.rs` 153 行）と `tools/bench/results/` の記録は、`Regex` を使う負荷でだけ値が変わる。ベンチマーク集合は `Regex` を使わない（推測。`programs/` の名前から）。

### 影響

- 設計書: 02-09「メモリの管理」に、確保の量 A と生きている量 L に別の領域の容量を含めること、`Opaque` と `Host` の値が容量を返すこと、`Host` は書き換えた後に数え直すこと、共有する領域を数えない決まり、枠の積み重ねを持つ対象の扱いを書く。今の 02-09 は A と L に何を含めるかを書いていない（ADR 0259 の決定 6 は保管した写しにだけある）。02-08「値の表現」の表は変えなくてよい。
- テスト: `core/tests.rs` 317 行は、`Opaque` と `Host` の記録が頭と箱と `size_of` の和以上であることを確かめている。容量を返す型の確保・`host_mut` での増減・解放の後の `current_bytes` が 0 に戻ることのテストを足す。公開の境界のテストとして、大きな容量を持つ `Opaque` を繰り返し作って捨てると回収が要求されることを確かめる（レビューの「修正方針と検証」の提案）。
- 性能の関門（07-02「性能の関門」）: ヒープを変えるので対象になる。`host_mut` は `TaskObj` について切り替えのたびに呼ばれる（`src/vm/dispatch/tasks.rs` に 13 か所）。既定の 0 を返す型で数え直しを静的に省けば、fib と loop の速い経路には触れない。`tests/call_allocations.rs`（普通の呼び出しと戻りで Rust の確保が起きないこと）は、数え直しが確保をしないので影響しない。

## TODO-196 `Regex` の入力の写しと、繰り返す照合の時間

### 所見の確かめ（入力の写し）

`Regex.find`（`src/builtins/funcs/regex.rs` 115〜126 行）は、一致したとき `Rc::new(text.to_owned())`（122 行）で入力の全文を写し、`match_value`（50〜64 行）が `Match` に持たせて `alloc_opaque` する。一文字の一致でも全文を写す。`findAll`（128〜147 行）は、呼び出しごとに一度だけ写し（139 行）、全一致で共有する。`Match` が持つ写しは、`matchText`（149〜159 行）と `group_value`（74〜91 行）が部分を切り出すためだけに使う。位置（`matchByteStart`・`matchByteEnd`）はグループの位置の表から返す。前節の再現が、この写しの未計上の影響である。

### 所見の確かめ（2 乗の時間）

再現（release。パターン `.*[^A-Z]|[A-Z]`、入力は `A` の列。時間はプロセス全体）:

| 入力 | `findAll` の一致の数 | 時間 |
|---:|---:|---:|
| 4 KiB | 4,096 | 0.033 秒 |
| 16 KiB | 16,384 | 0.094 秒 |
| 32 KiB | 32,768 | 0.298 秒 |
| 64 KiB | 65,536 | 1.09 秒 |
| 128 KiB | 131,072 | 4.36 秒 |

入力を 2 倍にすると時間は約 4 倍になる。64 KiB の入力に `replaceAll` と `split` を続けて呼ぶと、合わせて 2.21 秒だった。

- `findAll` は、`find_iter(text).count()`（135 行）で一致を数え、`captures_iter`（142 行）でもう一度辿る。
- `replace`（199〜223 行）は `find_iter` で数えた後（209〜215 行）、`replacen`（221 行）でもう一度辿る。`replaceAll` は回数の制限なし（0）で呼ぶ（233〜239 行）。`replaceFirst` は 1 回だけ探すので線形である。
- `split`（241〜257 行）は `pattern.split(text)` を二度辿る（250 行と 252 行）。
- `replaceAllWith`（`src/prelude/stdlib/Regex.bnt` 52〜64 行）は `findAll` を使うので同じ時間がかかる。

regex 1.13.1 の文書（`~/.cargo/registry/src/<レジストリ>/regex-1.13.1/src/lib.rs` 1093〜1124 行、「Iterating over matches」）は、`is_match`・`find`・`captures` の最悪 O(m n) が `find_iter`・`captures_iter` には当てはまらず最悪 O(m n²) であること、例として `.*[^A-Z]|[A-Z]` と `AAAAA` を挙げ、避ける方法はないこと、`regex-automata` の `meta::Regex` で earliest の探索にすれば O(m n) に戻るが一致の意味が変わることを書いている。

一方、標準ライブラリのソース（`Regex.bnt` 1 行）と言語リファレンス（`docs/reference/benitoite.md` 796 行）は、照合の時間が入力に線形だと書く。同梱の Skill の生成物（`skill/references/stdlib/Regex.md` 8 行、`skill/references/stdlib/index.md` 43 行）も同じ文を写している。設計書 03-08「Regex」は時間に触れていない。

照合は純粋な組み込みの関数として、VM の中で同期的に走る（`src/vm/dispatch.rs` 565〜593 行）。照合の途中では、タスクの切り替え・取り消し・中断の印のどれも調べない。128 KiB の入力の `findAll` に、始めて 0.3 秒後に SIGINT を送ると、プロセスは 4.34 秒後に結果を書いて終了状態 0 で終わった。02-09「中断の要求」は、印を調べる位置をタスクを切り替える位置と外部の操作を待つ位置と定めており、`main` がその位置を通らずに終わると、要求は読まれない。仕様の範囲内の振る舞いではあるが、利用者からは「Ctrl-C が効かなかった」と見える（付随の所見。この改造の範囲に入れるかは問いの候補 7）。

### 直し方（入力の写し）

| 案 | 内容 | 言語の値 | 費用 |
|---|---|---|---|
| A: `Slot` で指す | `Match` を `HostData` にし、元の文字列の値を `Slot` で持ち、`Trace` で訪れる | 変わらない | 純粋な組み込みの関数の文脈 `PureCtx` は `ValueCtx` だけを持ち（`src/builtins/iface.rs` 433〜451 行）、`new_slot`・`alloc_host`・`host` は `NoGcCtx` の関数である（`src/runtime/heap/ctx.rs` 356〜380 行、546〜580 行）。`ValueCtx` に「値を `Slot` に入れた変えない `Host` を作る」関数と「`Host` を読み、`Slot` を読む」関数を足す必要がある。`OpaqueData` に `Slot` を足すだけでは辿られない（`value.rs` 216 行の約束に反する） |
| B: 一致の部分だけを写す | `Match` は一致の全体 `[start, end)` の部分の文字列と、`start` と、グループの位置を持つ。グループは一致の全体の中にある | 変わらない | `regex.rs` の中だけで閉じる。`find` の写しは一致の長さになり、`findAll` の写しの合計は入力の長さ以下になる（一致は重ならない） |

## TODO-197 `Task.withTimeout` の期限を過ぎた完了

### 所見の確かめ

再現（release）: レビューの `regex_timeout_source.bnt` を、64 KiB の入力で実行した。

```text
elapsed_ms=1106
Some(65536)
```

期限は 20 ミリ秒である。判定の流れは次のとおりで、レビューの記述と今のコードが一致する。

1. `Task.withTimeout` の起動で、今の時刻に期限を足してタイマーを登録する（`src/vm/dispatch/tasks.rs` 618〜629 行）。
2. 子のタスクが純粋な組み込みの関数を同期的に呼ぶ（`src/vm/dispatch.rs` 565〜593 行）。
3. 期限の満了は、境界の関数 `boundary`（`tasks.rs` 140〜163 行）が時刻を読み（149 行）、`expire_timers` で期限の来たタイマーを取り出し（150 行）、`cancel::expire`（`tasks/cancel.rs` 198〜224 行）が `timed_out` に記録したときにだけ起きる。
4. 子が境界より先に戻ると、`return_plain`（`dispatch.rs` 822〜868 行）から `tasks::finish`（`tasks.rs` 652〜665 行）、`finish_task` に入り、735 行の `deliver_all` から `cancel::deliver` に進む。
5. `cancel::deliver` は `timed_out` に親があるかだけで `None` と `Some` を決め（`cancel.rs` 326〜339 行）、終わった時刻を期限と比べない。
6. 続けてタイマーを外す（351 行）ので、後の境界で期限切れに気付く機会もない。

今のテスト（`src/vm/dispatch/tasks/tests/cancellation.rs` 186〜300 行の `timeouts_wait_for_cancellation_and_remove_obsolete_timers`）は、仮の時計（`VirtualClock`、`src/runtime/sched/testing.rs` 240〜254 行）を筋書きの `Advance` で進める。`Advance` は待つときの作業用の部品（`ScriptWorkers::advance`、同 365〜380 行）でだけ読まれるので、子が走っている間に時刻だけが進む場合を作れない。期限が 0 と −1 の場合は、子を選ぶ前の境界でタイマーが満了するので、今でも `None` になる（同 260〜273 行）。

### 直し方

| 案 | 内容 |
|---|---|
| A: 終えた時刻で判定する | 子が終わったときの時刻を期限と比べ、期限を過ぎていれば結果を捨てて `None` にする |
| B: 今の振る舞いを文書にする | 「期限を過ぎてから、次に切り替えうる位置より前に終えたタスクの結果は `Some` になりうる」と 01-11 と `Task.bnt` に書く |

案 A の時刻の読み方には二つの形がある。

- A1: 判定を、子が終わった直後の境界へ遅らせる。`cancel::deliver` の `WithTimeout` で、子がすべて終わり、`timed_out` がなく、タイマーがまだあるときは、結果を書かずに親を「判定待ち」の集合（`RunState::scheduling` に新しい欄。`timed_out` の隣、`src/vm/state.rs` 186 行）に入れ、タイマーも外さない。子の `finish_task` は切り替え（`Switch::Done`）を立てるので、次の `switch_inner`（`tasks.rs` 182〜273 行）が必ず `boundary` を通る。`boundary` は時刻を読んで `expire_timers` を先に処理するので、期限を過ぎていれば今の満了の経路（`cancel::expire` → `deliver_all`）がそのまま `None` を作る。`expire_timers` の後に判定待ちが残っていれば、期限の前に終えたとして `Some` を書く。命令の振り分けの速い経路（`return_plain`）を変えない。
- A2: 子の `finish` の中で時刻を読む。`return_plain` と `finish` は `IoRuntime`（時計を持つ）を受け取らないので、引数を通すか、時計を実行ごとの状態から読める形にする必要がある。`return_plain` は速い経路の `inline(always)` の関数であり、引数を増やすと性能の関門（07-02）の機械語の確かめに影響しうる。

A1 で、終えた時刻は「子が終わった後に処理系が最初に時刻を読む位置」になる。その間に回収が入ると（`switch_inner` 202〜204 行で回収を先に行う）、回収の停止の分だけ遅く読む。停止は数ミリ秒であり（02-09「メモリの管理」）、期限のごく近くで終えたタスクが `None` になりうる程度の差である。期限の内か外かの境は、`expire_timers` と同じく「期限の時刻 ≦ 今の時刻」なら過ぎたとする。期限が 0 以下のときは、今と同じく常に `None` になる。

A1 で押さえる場合:

- 判定待ちの親が取り消された（`deliver_all` の `discard_cancelled_parent`、`tasks.rs` 786〜788 行）、全体の停止に入った（783〜785 行）、親の終了（743 行の `timed_out.remove` と同じ位置）で、集合から外す。`timed_out` を消している 351 行と 972 行でも消す。
- `Task.race` の子の中の `withTimeout` のような入れ子（今のテストの 283〜298 行）で、判定待ちの間に外側から取り消しが来る場合。

推奨は案 A1 である。01-11「タスクを起動する関数」と `Task.bnt` 18 行の約束（期限の内に終われば `Some`）に実装を合わせられ、レビューの結論（期限を過ぎた成功の処理を `withTimeout` で抑えられない）のうち、結果の判定の部分を直せる。照合の途中で取り消せないことは残り、それは TODO-196 の案 5 の範囲である。

### テストで時計を差し替える方法

既存の差し込み口だけで書ける。`cancellation.rs` のテストは、境界ごとに呼ばれる `test_boundary` の閉包（`tasks.rs` 217〜222 行）に、筋書き（`ScheduleHandle`）の写しを捕えている（同テストの 204 行）。筋書きを `[Advance(20), PickTask(1), PickTask(0)]` とし、閉包で、子を選ぶ前の境界で先頭が `Advance` なら `advance_time()`（`testing.rs` 149 行）を呼べば、境界の時刻の読み取り（期限 10 に対して 0）の後、子が走る前に時刻が 20 になる。子は境界を通らずに `return 42` で終わり、次の境界が 20 を読む。今の実装ではこのテストは `Some(42)` になって失敗し、案 A では `None` になる。期限の前に終えたときに `Some` のままであること（今の 238〜248 行の場合）と、判定待ちの間に親が取り消される場合も同じ形で書ける。時計の型を新しく作る必要はない。
