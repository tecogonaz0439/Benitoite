## 所見

### 1. 単純な `match` でも、幅の広いレコードの後ろの欄を調べると E0609 になる（要修正: 予算か数え方を決め直す）

- 場所: `crates/benitoite/src/typeck/patterns.rs:547-621`（`enter`）。記憶の鍵の複製を数えるのが `:553`、ワイルドカードだけの列を落とした行列を数えるのが `:592`。予算の値は `crates/benitoite/src/typeck/limits.rs` の `MAX_COVERAGE_WORK`。
- 問題: 仕事量は行列のセルの数で数える。ワイルドカードだけの先頭の列を一つ落とすたびに残りの行列全体を複製して数え（複製そのものは基準の版も同じ）、さらに記憶の鍵として同じ大きさをもう一度数える。欄が F 個・行が R 個の行列で後ろの欄を調べる判定は約 R×F² のセルを数え、`check_match` は選択肢ごとに前の行で判定するので、一つの `match` 全体では約 R²×F² になる。こうして、指数的でない単純な形が予算 2^20 に当たる。
- 確かめた形: `Boolean` の欄を F 個持つレコードに `case Wide(f{F-1-k}: true, ..) -> ()` を R 個並べ、最後に `case _` を置いた。

  | 分岐の数 R | E0609 になる欄の数 F |
  |---:|---:|
  | 3 | 418 |
  | 5 | 264 |
  | 10 | 138 |
  | 20 | 72 |
  | 30 | 51 |

- 同じ仕組みで当たるほかの例: 前の欄を調べる形は F=1,000 でも通り、F=3,000 で E0609 になる。束縛の文でも、`Unit` の欄を 1,100 個持つレコードの `bind Units(f1099: (), ..) <- units` が E0609 になる（`pattern_ext.rs:483` のテストがこの形を使う）。追加したゴールデン `testdata/patterns/todo195-coverage-budget.bnt` が予算に当たる理由も指数的な探索ではなく、193 欄のレコードで 48 個の分岐が選ばれず、そのたびに `covering_alternatives` の判定を繰り返すためである。
- 測定の不足: 報告の測定（コーパスの最大 3,196 に対して予算は約 328 倍）は幅の広いレコードを含まないので、正しいプログラムを誤りとする範囲を測っていない。
- 時間とメモリ: 予算いっぱいでも時間は短い（境目の直前の F=137・R=10 は release で 0.02 秒、ゴールデンは 0.04 秒）。最大 RSS は予算いっぱいの入力で 64〜117 MB（小さい入力では約 10 MB）で、記憶の表の大きさは予算に比例する。
- 直し方の案: (a) 数え方を実際の費用に合わせる。ワイルドカードだけの列を落とす段では記憶の鍵を作らず、行を複製せずに先頭の位置だけを進める表現にするなどして、この段を軽くする。記憶の鍵は構成子で分ける段の入力にだけ作る。鍵と探索の順序は変わらないので、結果も変わらない。(b) 予算を上げる。記憶の表の大きさが予算に比例するので、2^24 なら最大 RSS は 1 GB 前後と見込まれる。(c) 今のまま受け入れ、設計書 02-05 に書く。どれを選んでも、E0609 のゴールデンは予算と数え方に結び付いているので作り直しが要る。

### 2. 束縛の文の E0609 の修正案のとおりに書き換えても、同じ E0609 になる（望ましい）

- 場所: `crates/benitoite/src/diag/codes.rs:754` の `split_pattern`（``match the value with `match ... with`, or check fewer fields in this pattern``）。
- 問題: 束縛の文の判定は `useful(ty, [pat], _)` で、同じパターンを `match` に書き換えても同じ計算が残る。`Units` の例を `match` に書き換えると、`match` の側で E0609 になることを確かめた。
- 直し方の案: 修正案から `match` への書き換えを外し、調べる欄を減らすことを書く（例: ``check fewer fields in this pattern, or bind the record first and check the field separately``）。直したら `gen_skill` で作り直す。

### 3. `is_irrefutable` がテストのためだけに残っている（望ましい）

- 場所: `crates/benitoite/src/typeck/patterns.rs:197`。
- 問題: 本番の呼び出し元と `tests/coverage_export.rs` はどちらも `check_binding` に移り、`is_irrefutable` を呼ぶのは単体テストの 4 か所だけである。スキル `test-audit` は、テストのためだけにある本番のコードを整理の対象にしている。
- 直し方の案: `is_irrefutable` を消し、単体テストを `check_binding(..)` で書く。

### 4. 深いパターンのセルも 1 と数える（参考）

- 場所: `patterns.rs:107-121`（`charge`・`matrix`）と `:553`。
- 問題: セルは入れ子の大きさによらず 1 と数えるが、複製・ハッシュ・比較は入れ子の全体を辿る。実際には型と入れ子の深さの上限（E0208）が先に効き、`Option` を 60〜100 段入れ子にした入力も 0.05 秒以内で終わった。
- 直し方の案: 今は直さず、設計書 02-05 に予算の単位が「セルの数」であることを書く。

### 5. テストのコメントが古い名前を指している（参考）

- 場所: `crates/benitoite/tests/desugar_export/exchange.rs:1303`。
- 直し方の案: `is_irrefutable` を `check_binding` に直す。

## 確かめて問題がなかった点

- 明示のスタックへの書き直し（`usefulness`・`enter`・`next_branch`）は、基準の再帰の版と同じ手順を辿る。長さの違う行を除く処理と退避（`fallback`）は順序が入れ替わったが、どちらも問いだけで決まるので結果は同じである。構成子は順に試し、最初に有用だったもので反例を組み、Lean の `usefulFuel`・`firstUseful` と同じく左の列から構成子の順に選ぶ。10,020 件の一致もこれを裏付ける。
- 記憶の鍵（型の並び、長さの違う行を除いた後の行列、問い）は結果を一つに決める。鍵の外で結果に関わるのは `adts` だけで、一つの `Search` の間変わらない。表は引くだけで巡回しないので、`HashMap` の順序は結果にも仕事量にも響かない。
- 予算は呼び出しごとに新しい `Search` で始まり、選択肢ごとの判定、全体の網羅性、`covering_alternatives`、`overlaps` が同じ `Search` を使う。予算に当たると途中の結果と表は捨てられ、E0609 を一つだけ出す。
- `check_binding` の反例は、基準の版の「`is_irrefutable` と、分岐が一つの `check_match`」の組み合わせと同じになる（書き出しの中の `assert_eq!` が 10,020 件で通った）。
- 差分テストの書き出しは最上位に `budget` の鍵を足しただけで、`formal/CoverageDiff/Main.lean` は `deriving FromJson` で読むので知らない鍵は無視される。`formal/` は変わっていない。
- 規約: 本番のコードに `unwrap`・`expect`・添字・`as`・panic はなく、足し算は `saturating_add` で書いている。
- テスト: 予算の境目、記憶あり・なしの比較、n=12 の記憶ありで通り記憶なしで当たること、束縛の文の E0609、E0609 のゴールデンがある。時間で確かめるテストはない。

## 総評

正しさは確かめた。基準の版・記憶あり・記憶なしの三つの版が、差分テストの書き出しの 10,020 件で完全に一致した。取り込みの前に判断が要るのは所見 1 である。今の数え方は、ワイルドカードだけの列を落とすたびに行列を複製する費用を数え、記憶の鍵の分でそれを 2 倍にしているので、幅の広いレコードの後ろの欄を調べるだけの単純な `match` が E0609 になる。所見 2 の修正案の文言と、所見 3 のテストのためだけに残った関数も、あわせて直すのが望ましい。
