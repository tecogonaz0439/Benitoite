## TODO-042 `Opaque`・`Host` の対象が持つ別の領域の容量を確保の量に数える方法

- 状態: 未着手
- 旧: OPEN-071
- 出どころ: open-issues の OPEN-071、ADR 0259（決定 6）、02-09 ランタイム（「メモリの管理」）

回収の閾値の確保の量 A と生きている量 L には、対象の頭、配置の切り上げ、対象が持つ別の領域の容量を含めると定めた（ADR 0259 の決定 6）。しかし、ヒープの対象のうち `Opaque` と `Host` は任意の Rust の値を持ち、そのトレイト（`OpaqueData`・`HostData`）には、値が別に確保した領域（`Vec`・`String` など）の容量を返す口がない。初回リリース版の確保器は `size_of::<T>()` だけを数えている。

正しさには影響せず、回収の時期と測定の記録だけに影響する。`Opaque` の対象には正規表現の組み立てた値などの組み込みの中身を見せない値が、`Host` の対象にはハンドラの記録と継続の状態が入る。これらを多く作る負荷では、回収が実際のメモリの量より遅れる可能性がある。

設計者は第 2 段（R20）の前に扱うと決めていたが、初回リリース版では実装しなかった。案は次の形である。

- 二つのトレイトに容量を返すメソッドを加える（既定の実装は 0 を返す。例: `fn heap_bytes(&self) -> usize`）。
- `Host` の対象は、書き換える関数（`NoGcCtx::host_mut`）で書き換えた後に数え直す。

決めた形は ADR を添えて、ヒープの章の確保の量の定めに加える。

2026-10-10 の外部のセキュリティのレビュー（外部のセキュリティのレビュー の RUNTIME-01）は、この未計上で回収が実際のメモリより大きく遅れることを、普通のスクリプトで再現した。一致した `Regex.find` は入力の全文を写して `Opaque` の対象に持たせ、確保の量には約 168 バイトしか数えないので、4 MiB の入力に 64 回呼んで結果を捨てると、回収が一度も起きないまま約 256 MiB が残った。外部の入力を繰り返し処理するサーバやメモリの小さい環境では、メモリの上限で先に止まる。「正しさには影響せず」は保たれるが、可用性には影響するので、優先を上げる。`Regex.Match` の写しそのものは TODO-196 で扱う。同じ領域を複数の対象が `Rc` で共有するときに二重に数えない形も決める。

## TODO-195 check の資源消費（型クラスの辞書の解決と網羅性の判定）

- 状態: 方針あり
- 出どころ: 外部のセキュリティのレビュー の FE-02・FE-03
- 関連: TODO-031（検査の段の時間）

信頼できないソースを `check` に渡すと、小さなソースで型検査が指数的な時間とメモリを使う。自動で第三者のソースを検査するハーネスやサービスでは、可用性の問題になる。同じレビューの FE-01（定数の倍々の連結）は、TODO-178 の作業 T7 で設けた定数の評価の予算（64 MiB、E0435）で直っていた。

- 型クラスの辞書の解決（FE-02）: `src/typeck/traits/solve.rs` の `resolve` は、実装の制約ごとに再帰で辞書を解決し、結果を木（`DictExpr::Impl` の `args: Vec<DictExpr>`）として持つ。同じ部分問題を共有しないので、`implement[T: A & B] A[List[T]]` と `implement[T: A & B] B[List[T]]` の下で 24 段の入れ子のリストを渡すと、辞書の節の数が 2^25 − 1 になる（585 バイトのソースで、release のビルドがメモリを使い尽くして止まった）。型の節の数の上限は、型が小さいので効かない。2026-10-11 に debug のビルドで、深さ 20 が 3.2 秒・最大 RSS 341 MiB になることを確かめた。直し方の案は、解決の結果を（型クラス、正規化した型）の鍵で覚え、辞書を共有の表現（DAG）にすることと、解決の仕事量の予算を設けて超えたら制限の診断にすることである。脱糖とコード生成が辞書の木を写すところにも、同じ増え方がないかを確かめる。
- 網羅性の判定（FE-03）: `src/typeck/patterns.rs` の有用性の探索は、仕事量の予算も、同じ行列の結果の記憶も持たない。`Boolean` の欄を 4n+1 個持つレコードについて、n 個の分岐がそれぞれ別の 4 欄を `false` と決め、最後の 2 分岐が最後の欄だけで全体を覆う形にすると、左の列から分けていく探索が同じ残りの行列を 4^n 回調べる。release のビルドで、n=12（3,119 バイト）が 8 秒を超えた。2026-10-11 に debug のビルドで、n=10 が 6.2 秒になることを確かめた。直し方の案は、網羅性と到達可能性の判定に共通の仕事量の予算を設け、超えたら「網羅していると確かめられなかった」制限の診断にすることである。網羅していると決めつけて通すことはしない。行列の正規化と記憶、列の選び方は、性能の改善として別に扱う。Lean の網羅性の判定（`formal/`）と差分テストで一致を確かめているので、予算の扱いを Lean の側とどう揃えるかを決める（07-04「01-12 との対応」）。判定の木の生成（`src/ir/decision.rs`）にも、出力が増える同じ種類の入力がないかを確かめる。

予算の大きさと制限の診断のコード・文言を決める必要がある。

## TODO-196 `Regex` の繰り返す照合の時間と、入力の写し

- 状態: 方針あり
- 出どころ: 外部のセキュリティのレビュー の RUNTIME-01・RUNTIME-02
- 関連: TODO-042、TODO-185（`Regex` の確保の上限）、TODO-197

- 2 乗の時間（RUNTIME-02）: `Regex.findAll` は、パターン `.*[^A-Z]|[A-Z]` と `A` の列の入力で 2 乗の時間になる（release のビルドで 64 KiB の入力に約 7.6 秒）。使っている regex 1.13.1 の文書は、一回の照合を O(mn)、繰り返す `find_iter`・`captures_iter` を最悪 O(mn²) と書いている。一方、標準ライブラリのソース（`src/prelude/stdlib/Regex.bnt` の先頭）と言語リファレンス（`docs/reference/benitoite.md` の Regex の節）は、照合の時間が入力の長さに線形だとしている。`findAll`（`src/builtins/funcs/regex.rs`）は、一致を数える走査と値を作る走査で入力を二度辿る。`replaceAll` の内部の関数と `split` も同じ形である。照合は VM の中で同期的に走る純粋な組み込みの関数なので、`Task.withTimeout` で止められない。直し方として、まず文書を「一回の照合は線形、繰り返す照合は最悪 2 乗」に直す。そのうえで、入力の長さ・一致の数・仕事量の上限を設けるか、長い照合を分けて取り消しを効かせるかを決める。照合の意味（貪欲さと左の優先）を変える置き換えは採らない。二度の走査をやめるのは定数倍の改善である。
- 入力の写し（RUNTIME-01）: 一致した `Regex.find` は、一文字の一致でも `Rc::new(text.to_owned())` で入力の全文を写し、`Match` の値（`OpaqueData`）に持たせる。回収は `Opaque` の対象を `size_of::<T>()` だけ数えるので（TODO-042）、4 MiB の入力に 64 回 `find` を呼んで結果を捨てると、回収が一度も起きないまま約 256 MiB が残る。release のビルドで、仮想メモリを 384 MiB に制限した実行が確保の失敗で止まった（呼び出しが 1 回なら 22 MiB で終わる）。`Match` が元の文字列の値を、追跡される `Slot` で指す形（`HostData` と正しい `Trace`）にすれば、写しをなくせる。`OpaqueData` に `Slot` を足すだけでは追跡の漏れになる。

## TODO-197 `Task.withTimeout` が、期限を過ぎて終えたタスクの結果を `Some` で返す

- 状態: 未着手
- 出どころ: 外部のセキュリティのレビュー の RUNTIME-02（`Task.withTimeout` の実測）
- 関連: TODO-196

`Task.withTimeout(20, …)` の中で長い組み込みの関数（TODO-196 の `Regex.findAll`）を呼ぶと、release のビルドで 471 ミリ秒かかり、結果は `Some(16384)` だった。01-11 と `src/prelude/stdlib/Task.bnt` は、期限の内に終われば `Some`、終わらなければ取り消して `None` と定める。

取り消しが、次にタスクを切り替えうる位置まで遅れることは、01-11 と 02-08 に書いてある。問題は結果の判定である。期限の満了は、タスクの切り替えの境界（`src/vm/dispatch/tasks.rs` の `boundary`）で時刻を読んだときにだけ記録される。子がその前に戻ると `tasks::finish` が値を確定し、`src/vm/dispatch/tasks/cancel.rs` は、満了の記録（`timed_out`）があるかだけで `None` と `Some` を決め、終えた時刻を期限と比べない。その後でタイマーも外すので、後の境界で期限切れに気付く機会もなくなる。

直し方の案は、子が終えた時点の単調な時刻を期限と比べ、過ぎていれば `None` にすることである。期限を過ぎた後の成功を受け付ける今の振る舞いを残すなら、01-11 にそう書く。どちらにするかを決める。今のテスト（`src/vm/dispatch/tasks/tests/cancellation.rs`）は、仮の時刻を境界で進めるので、組み込みの関数の間に実際の時刻だけが進む場合を作れない。完了の判定に時計を渡し、時刻の進み方と結果の判定を別々に操れる形でテストする。

## TODO-198 HTTP サーバの応答の組み立てと、要求の検査

- 状態: 方針あり
- 出どころ: 外部のセキュリティのレビュー の HTTP-01〜04 と「既知の制約と、強化項目として扱う点」、later-issues の 115、later-issues の 116（後半）
- 関連: TODO-069（流しながら読み書きする HTTP の本体と、接続の再利用）

レビューが実際の TCP の通信で確かめた、サーバの応答の組み立てと要求の検査の誤りである。TODO-069 の改造を待たずに直せる。どれも別の利用者への応答の混入や要求の密輸（request smuggling）までは確かめていない（サーバは一つの接続で一つの要求だけを扱い、応答の後に閉じる）。

- 応答の `Transfer-Encoding`（HTTP-01。以前は TODO-069 の一点）: 応答の組み立て（`src/runtime/io/http.rs` の `response_bytes`）は、`content-length` と `connection` だけを処理系が決めるヘッダとして除き、`Transfer-Encoding` を残したまま、本体の長さの `content-length` と復号済みの本体を送る。`Http.get` の結果をそのまま `Http.respond` に渡す中継で、上流が chunked なら、RFC 9112 §6.2 が禁じる TE と CL の両方を持つ応答になり、Python の `http.client` は読めなかった。直し方: 本体を固定長で送る今の形では、`Transfer-Encoding` と `Trailer` も処理系が決めるヘッダとして除く。
- 本体を持たない応答（HTTP-02）: HEAD の要求への応答、204・304 の応答に本体と `content-length` を付けて送る。100 などの 1xx を最終の応答として送り、閉じる。RFC 9112 §6.3 と RFC 9110 §8.6 に合わない。直し方: 要求の方法（要求のデータは添付にある）と状態コードで、本体と `content-length` を送るかを決める。HEAD と 304 は本体を送らない。204 と 1xx は本体も `content-length` も送らない。`Http.respond` は一度しか応答できないので、1xx を拒むことを 03-09 に定める。205 と CONNECT の 2xx も確かめる。
- Host とトレーラの検査: HTTP/1.1 の要求で Host がないもの、Host が二つあるものに 200 を返した（RFC 9112 §3.2 は 400 で拒むとする）。トレーラの行は `:` を含むかだけを確かめ、NUL を含む行を受け付けた（トレーラは捨てるので、これだけでヘッダの注入にはならない）。普通のヘッダの欄の規則で確かめる。
- 再開のたびの応答の作り直し（HTTP-03）: `Http.respond` の組み込みの関数は、書き込みの待ちから戻って呼び直されるたびに、ヘッダを写し、応答の全体のバイト列を作り直す（`src/builtins/funcs/http_server.rs`）。二回目からは作ったものを捨てる（`http.rs` は応答がまだないときだけ受け取る）。4 MiB の応答を遅い相手に送ると、全体の確保が 1 回から 3 回になった。最初の検証と組み立てを、続きを書くだけの再開と分ける。
- 取り消した待ちの記録の残り（HTTP-04）: 取り消したタスクの readiness の待ち（`Http.accept` など）の操作の記録は、その資源のイベントが来るか、資源を閉じるまで残る（`src/vm/dispatch/tasks/io.rs` の `clear_ready`。テスト `src/vm/dispatch/tasks/io/tests.rs` は残ることを期待している）。同じ listener に `Task.withTimeout(1, lambda() return Http.accept(listener) end lambda)` を 10,000 回繰り返すと、記録が 9,960 件残った。作業用のスレッドの操作と違い、readiness の待ちは登録を外せばすぐ終えられるので、取り消しのときに記録と対応を外す。同じ資源にほかの生きた待ちがあれば登録は残す。
- `accept` の警告の書き出し（要確認）: `src/builtins/funcs/http_server.rs` は、警告の書き出しが返した容量の待ちを捨てる。出力の口は容量が足りないとき書き込みを預けるので、標準エラーが詰まった状態で警告が続くと、預けた警告が上限なく溜まる可能性がある。再現していない。
- 接続と要求の細部（要確認。later-issues の 116 の後半から移した）: Linux の `accept` が返す接続ごとの errno（`ENETDOWN` など）を接続ごとの失敗に含める（`http.rs` は `ConnectionReset`・`ConnectionAborted` などだけを数える）。状態コード 431 の理由句と `100-continue` の扱いを確かめて決める。
