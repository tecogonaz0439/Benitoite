# 実装の確認の観点

本章は、実装 LLM が書いた実装を確認するときに読む観点の一覧である。道具で確かめられる規約（書式、lint、テスト、ライセンス、`// SAFETY:` のコメントの有無）は、`scripts/check.sh` と `scripts/check-heap.sh` が通ったことで確かめたものとし、ここでは読まない。最小実行版の観点（最小実行版の実装プランの 00-04）を引き継ぎ、`unsafe` とヒープ、メモリの管理の方式への依存、タスクとリソースの状態の観点を加える。

## すべての作業で読む観点

| 観点 | 確かめること |
|---|---|
| インターフェースからの逸脱 | `10-interfaces/` の型とシグネチャを変えていないか。変えたなら、報告と合意があったか |
| `#[allow]` | [実装の規約](00-02-conventions.md)の表にない箇所に `#[allow]` がないか。ある箇所に理由のコメントがあるか |
| `todo!()` の仮置き | 受け持つ関数に `todo!()` が残っていないか（作業の文書が後の作業に残すと定めたものを除く）。`todo!()` のなくなったファイルの仮置きのための許可を消したか（[実装の規約](00-02-conventions.md)の「`todo!()` の仮置き」） |
| `unsafe` の場所 | `runtime::heap` の内部の層の外に `unsafe` がないか |
| `as` による数値の変換 | 値が収まることが明らかな箇所に限っているか |
| 誤りを文字列で表している箇所 | `Stop::Internal`・`InternalError` の説明と CLI の使い方の誤り以外で、誤りを `String` で表していないか。診断の文言を処理の中に直接書いていないか |
| 大域の状態 | [実装の規約](00-02-conventions.md)の三つの例外のほかに、大域の可変状態がないか |
| 再帰の深さ | 実行時の値やリストを Rust の再帰で辿っていないか。言語の関数の呼び出しで Rust の関数を入れ子に呼んでいないか |
| 言語の値を作る経路 | ヒープの対象を `runtime::heap` の公開の層を通さずに作っていないか |
| 回収の方式への依存 | `runtime::heap` の外のコードが、メモリの管理の方式（暫定に採ったマーク・スイープ）に依存していないか。方式は R33 の測り直しの後に変わることがある（[OPEN-036](../../2026-10-09-design-first-release/open-issues.md#open-036)） |
| 設計書との対応 | 作業の文書が挙げた設計書の規則を満たしているか。規則を満たさない箇所を、作業の文書に書いていない独自の判断で埋めていないか |
| テスト | テストが観察可能な振る舞いを確かめているか。非公開の関数や中間のデータの並びを確かめていないか（スキル `test-audit`） |
| コメント | モジュールの先頭に役割と設計書の章があるか。「なぜ」のコメントが設計書の根拠を示しているか |
| 依存するクレート | [実装の規約](00-02-conventions.md)の「依存するクレート」が認めたもの以外を加えていないか |
| テストの削除 | 作業の文書が決めていないテスト（最小実行版から移したテストを含む）を消したり飛ばしたりして `check.sh` を通していないか（移行の間の `legacy` の扱いは C18 で終わった。[リポジトリとクレートの配置](00-01-repository-layout.md)の「移行の間の配置」） |

## 作業の種類ごとに加えて読む観点

| 作業 | 確かめること |
|---|---|
| 字句と構文（F01〜F04） | 誤りの後に続けて解析しているか。一つの誤りから派生した診断を出していないか。AST の深さの数え方が 02-03「入れ子の深さ」と一致しているか。他の言語の書き方への診断（`let`・`:` の戻り値の型・`...xs` など）が、設計書の修正案を示しているか |
| モジュールと名前解決（F05・F06） | 循環する import と見つからないモジュールを、読み込みを続けたまま報告しているか。`bind` と `shadow` の規則が 01-03「シャドーイング」と一致しているか |
| 型検査（F07〜F10） | 本体ごとに状態を作って捨てているか。誤りの型を含む制約で診断を出していないか。辞書の解決とエフェクトの検査が 02-05 の順序のとおりか |
| 脱糖と変換（F11・F12） | 01-12 の脱糖の規則と、02-06 の判定の木の手順に一対一で対応しているか。由来位置の付け方が 02-02 のとおりか |
| コード生成（F15）と生存の情報（R05） | 末尾位置の呼び出しがすべて末尾呼び出しの命令になっているか。生存の情報（最後の使用、使わなくなったレジスタ）がメモリの管理の方式によらず同じものを渡しているか。命令ごとの入口の生きているレジスタ（`live_in`）が、跳躍の先と合流で欠けない流れの解析の入口の集合か、呼び出しの命令の結果のレジスタ（`call_writes`）が呼び出しの命令だけに付いているか（[ADR 0314](../../2026-10-09-design-first-release/decisions/0314-clear-dead-registers-at-safepoints.md)。[ADR 0259](../../2026-10-09-design-first-release/decisions/0259-compare-mark-sweep-and-rc-in-stage-1.md) の決定 2） |
| ヒープの内部の層（R01〜R04、R06） | `// SAFETY:` のコメントが引く不変条件が、そのブロックの直前までのコードで実際に成り立つか。対象の頭の読み書き、塊の確保と解放、ポインタの計算に、確保した範囲の外を指す場合がないか。解放した対象を指す値が根や対象の中に残らないか |
| 回収しない区間（R02） | `Value<'epoch>` を区間より長く持てる抜け道（`'static` への変換、構造体の欄への保存、作業用のスレッドへの受け渡し）がないか。コンパイルの失敗のテストが、それぞれの抜け道を塞いだことを確かめているか。`Slot` を読む・書き換える・辿るすべての経路で、ヒープの番号をすべての構成で比べているか。`discard` が `Trace` でなく `Discard` を使っているか |
| マーク・スイープ（R03） | 根の列挙が、レジスタ・枠・保存領域・タスク・定数のキャッシュを漏れなく含むか。回収を安全点の外で行っていないか。回収の閾値が ADR 0259 の決定 6 のとおりか |
| 参照カウント（R04。R14 が外したので、R33 の判断で戻すときに読む） | 増減の対が崩れる経路（途中で `Stop` を返す経路、取り消し）がないか。その場での再利用が、どの `Slot` からも指されない（数が 0 の）対象に限られ、一意であることを引数の参照がまだ数えられている間に判定しているか。解放の候補の並びが 10-08「区間と回収」の四つの規則を守っているか。解放の連鎖を明示の積み重ねで辿っているか |
| VM（R09、R15・R16、R20〜R25、R39、R34・R35） | 振り分けのループの局所の状態を、呼び出し・戻り・切り替え・回収・待ち・継続の移動・止める手順の前に書き戻し、後に読み直しているか。予算の退避と戻しが [ADR 0263](../../2026-10-09-design-first-release/decisions/0263-dispatch-loop-locals-and-verifier.md) の決定 3 のとおりか。枠を降ろす処理が、原因と枠の種類の表（02-08）の各行に対応しているか。命令の処理の中で区画・枠・原型を表から引き直していないか、回収へ出るすべての経路で、区間を閉じる前に ADR 0314 の決定 3 の集合で枠のレジスタを空にしているか。第 2 段の作業は、加える枠の状態（ハンドラの本体と節、継続の捕捉と再開、待ちと完了）を決定 5 の二つの状態のどちらかに分け、呼び出し元の `pc` を進めて保存しているか。普通の呼び出しと戻りで動的確保・`ReturnWork` の構築をしていないか（[ADR 0313](../../2026-10-09-design-first-release/decisions/0313-vm-performance-recovery-before-stage-2.md) の決定 2・3）。VM・`runtime::heap`・コード生成・生存の情報を変える作業は、完了の報告に短い測定（作業を始めた版との比）と、振り分けのループの頭の機械語の命令の数とスタックへの退避の数を書いているか。遅い経路を冷たい関数に置き、普通の経路（`CALL`・`TAILCALL`・`RETURN` の速い経路、ループの頭）に処理を足していないか。本測定は R26 の後と最後の 2 回だけオーケストレータが行う（同 ADR の帰結） |
| 組み込みの関数（R07・R08・R29） | 型付きの形で書いているか（内部の共通の形を直接書いていないか）。大きさの上限を、値を作る前に確かめているか。計算が溢れを検査しているか。作業用のスレッドへ渡すものに言語の値を含めていないか |
| スケジューラと IO（R25〜R28、R39、R40） | タスクを待たせてから要求を公開しているか。待たせる位置と遅い経路で、要求の送り出しと完了の取り込みを行っているか。完了の処理が「リソースを返す → 処理系の不具合を報告する → 配送する」の順か（[ADR 0266](../../2026-10-09-design-first-release/decisions/0266-task-and-resource-state-machines.md)）。タスクとリソースの状態の組み合わせごとにテストがあるか |
| 出力（R27） | 書き込みの受け付けの条件が ADR 0265 の決定 4 のとおりか。転送の完了を待つ位置で、VM がイベントの処理と中断の確かめを続けているか |
| 参照インタプリタ（R10・F14） | VM と値の型を共有していないか。VM と共有するのが組み込みの関数の本体だけか（[ADR 0276](../../2026-10-09-design-first-release/decisions/0276-reference-interpreter-shares-builtin-bodies.md)）。値の変換が `runtime::heap` の公開の層だけを使っているか。言語の関数の呼び出しで Rust の関数を入れ子に呼んでいないか |
| 永続コレクション（R36・R37） | 操作の列を単純なモデル（`Vec`、`BTreeMap`・`BTreeSet`）と同時に適用して比べるテストがあるか。木の不変条件（平衡の条件など）を `debug_assert!` で確かめているか（03-06、ADR 0211）。ノードを作った後に書き換えていないか |
| テストの書き直しと切り替え（C03・C05） | 書き直したテストが、元のテストと同じ入力で同じ規則を確かめているか。最小実行版の言語の機能だけを使い、初回リリース版で加わる機能に置き換えていないか。C05 で期待する出力を変えた箇所が、構文の改めから説明できるか |

## 回収の強制での確かめ方

`runtime` と `vm` を変えた作業について、`scripts/check.sh` が回収の強制を含めて通ったかも確かめる（完了の報告の「検査の結果」）。

第 1 段の間（R14 まで）は、二つのメモリの管理の機能の組み合わせのそれぞれで通ったかと、一方の方式だけで通るテストをもう一方の方式から黙って外していないか（`#[cfg(feature = ...)]` で限ったテストに、限る理由のコメントがあるか）も確かめた。
