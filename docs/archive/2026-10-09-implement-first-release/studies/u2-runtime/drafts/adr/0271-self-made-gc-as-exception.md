# 0271. メモリの管理（GC）を、目的と設計原則の線引きの例外として自作する

- 状態: 提案
- 日付: 2026-09-30
- 関連章: [目的と設計原則](../../../../../2026-10-09-design-first-release/00-overview/00-01-goals.md), [ランタイム](../02-09-runtime.md)（草稿）
- 関連する未決事項: [OPEN-036](../../../../../2026-10-09-design-first-release/open-issues.md#open-036)

## 背景

[目的と設計原則](../../../../../2026-10-09-design-first-release/00-overview/00-01-goals.md)の「目的が衝突したときの判断基準」は、言語の中核と言語処理系の主要部を自作し、それ以外の基盤は既存の OSS を使うと定め、既存の OSS を使う基盤の例に GC を挙げている。

一方、[ADR 0240](../../../../../2026-10-09-design-first-release/decisions/0240-runtime-redesign-in-first-release-plan.md) は、値の表現とランタイムを自作で作り直すと決め、値の表現とメモリの管理の設計を、設計者が学ぶ対象の中心に置いた。作り直しの検討（[03-options.md](../../03-options.md) の Q2・Q3）と ADR の草稿 [0259](0259-compare-mark-sweep-and-rc-in-stage-1.md)・[0260](0260-heap-and-unsafe-boundary.md) は、GC を自作する前提で書いた。相談の第 4 回（[記録](../../consult/04-draft-review.md)の指摘 12）で、この前提が上の線引きと食い違うことが分かった。

## 決定

1. メモリの管理（マーク・スイープまたは参照カウントと循環の回収、確保器、根の列挙）は自作する。既存の GC のクレートは、設計の参考として読むが、依存には加えない。
2. これは「目的が衝突したときの判断基準」の線引きに対する、メモリの管理についてだけの例外とする。線引きの本文は改めない。プラグインの実行環境など、ほかの基盤は、線引きのとおり既存の OSS を使う。

## 理由

値の表現、メモリの管理、VM の枠の持ち方は、互いの設計を縛り合う（[03-options.md](../../03-options.md) の「問いどうしの依存」）。安全点の定義、回収しない区間を寿命で表す境界、継続の区画の移動は、どれも GC の根の列挙と回収の時期に依存しており、GC を外部のクレートに任せると、これらの設計の多くをそのクレートの API に合わせることになる。設計者が学ぶ対象として ADR 0240 が選んだのはこの組み合わせそのものであり、GC だけを外すと学ぶ対象の中心が欠ける。

## 検討した代替案

- **既存の GC のクレートを使う（線引きのとおり）**: 実装の量と `unsafe` の検証の負担は減る。しかし、上の理由で学ぶ対象の中心が欠け、第 1 段で二つの方式を比べる計画（ADR 0259）も成り立たない。設計者は自作を選んだ。
- **線引きの本文を改め、GC を自作の範囲に入れる**: 原則の例外は原則を直さずに ADR に記すという運用に合わせ、採らなかった。

## 帰結

- ADR 0259・0260 の前提が、この ADR で根拠を持つ。ADR 0260 の「検討した代替案」で GC のクレートを使わない理由として線引きを引いていた箇所は、この ADR を引く形に改める。
- `unsafe` を含む自前のヒープの検証（ADR 0260 の確かめ方）の負担を、このプロジェクトが負う。
