# R13 窓を重ねる形の比較

- 依存する作業: [R09](R09-vm-core.md)
- 難易度: 3（1〜5。README の「作業一覧」）
- 規模の見込み: 小（500 行未満。比べるための変更と測定のテスト）
- ブランチ: impl/R13-overlapping-windows

## 目的

呼び出し元が関数と引数を窓の末尾に並べ、呼ばれた側の窓をその位置から始める形（窓を重ねる形）を、R09 の独立した窓と比べて測り、採るかを設計者が決めるための記録を作る（[OPEN-063](../../2026-10-09-design-first-release/open-issues.md#open-063) の 1 つ目の箇条、[ADR 0262](../../2026-10-09-design-first-release/decisions/0262-segment-frames-split-call-and-wrapping.md) の決定 5）。比べるのは、引数の準備を含む総移動量、レジスタの領域の最大量、長い末尾再帰の時間であり、呼び出しの部分だけの短縮では決めない。引数を写す処理が、呼び出しの前の命令（引数を窓の末尾へ `MOVE` する命令）に移るだけのことがあるからである（[相談の第 2 回](../studies/u2-runtime/consult/02-frames-and-dispatch.md)の「要点」の 2）。

OPEN-063 の 2 つ目の箇条（継続を捨てた後の区画の記憶域の再利用）は、継続を扱う第 2 段の後でなければ測れないので、本作業の範囲に入れない。記録にその旨を書く。

本作業は比べて記録するところまでを行う。窓を重ねる形を本番の VM に入れるかは、記録を見て設計者が決める。入れる場合は、コード生成（F15）と VM の変更を別の作業として起こす。

## 作るもの

- 測定のためだけのリビジョン（本番の枝に取り込まない）: R09 の VM の `CALL` に、窓を重ねる形を加えたもの。重ねる形はテストから切り替えられるようにし（`VmConfig` か `RunState` の欄。既定は独立した窓）、一つのバイナリで両方の形を測る。既定のままなら R09 の既存のテストと `scripts/check.sh` がそのまま通る。測定のリビジョンでは、凍結した型（`StackMeter`・`RunState`・`VmConfig` など）に欄や計数を足してよく、`dispatch.rs`・`budget.rs` などの凍結したファイルを変えてよい。本番の枝に取り込む部分では変えない。
- コミットの扱い: 実装担当は 00-03 のとおりコミットせず、測定のリビジョン全体を作業ツリーに作る。完了の報告で、本番の枝に取り込むファイルと測定だけのファイルを分けて挙げる。オーケストレータが全体を `measure/R13-overlap` の枝にコミットし、本番の枝には挙げられたファイルだけを取り込む。比べるもう一つのコミット（独立した窓）は、作業を始めたときの `san_benito` の HEAD とする。
- 測定のテスト: 両方の形で同じ入力を測る、`#[ignore]` を付けたテスト（`cargo test --release -- --ignored` で走らせる）。R05 の `bytecode::asm` はテストのときだけ使えるので、測定もテストの形で行う。`bytecode::asm` はクレートの中の単体テストでしか使えないので、測定のテストは `src/vm/` の下（`tests.rs` か、`#[path]` の子モジュール）に置く。窓の形によらず書けるテスト（総移動量を数えるプログラムの組み立てなど）は、本番の枝に取り込んでよい。既存のテスト（`src/vm/tests.rs` の上限と長い末尾再帰の場合）と重なるだけなら、本番に取り込むテストは空でよい。
- 記録: `tools/bench/results/<日付>-open-063-<コミット>.md`。`TEMPLATE.md` は使わず、後述の「記録」の項目を見出しにした自由な書式で書く。コミットは仮の字句（`<COMMIT>`）にして書き、ファイル名も仮の字句で置く。オーケストレータがコミットの後に埋めて改名する。

## 手順の要点

### 窓を重ねる形

`CALL A B C` で `R[B]` が関数、`R[B+1]`…`R[B+C]` が引数のとき、呼ばれた側の窓の先頭を呼び出し元の窓の `B + 1` の位置にし、引数を写さずに呼ばれた側の `R[0]`…`R[C-1]` として使う。10-07 の命令の符号化は変えない。条件は次の三つである（相談の第 2 回の要点の 2、OPEN-063）。

1. 重なったスロットの所有者を一つに決める。呼び出しの間、`R[B+1]` から後ろのスロットは呼ばれた側のものであり、呼び出し元はそこを読まない。呼び出し元の窓のうち `B + C` より後ろのレジスタが呼び出しの後に生きているなら重ねられないので、そのときは独立した窓に戻す（生存の情報で判定するか、重ねられる呼び出しだけを組み立てのプログラムで作る。どちらにしたかを記録に書く）。
2. 末尾呼び出しで窓の先頭を進め続けない。`TAILCALL` は R09 と同じく現在の窓の先頭に置き直す。
3. 区画の境目で窓を共有しない（第 1 段に区画の境目は現れないが、記録に条件として書く）。

戻るとき、結果を呼び出し元の `A` に書き、呼ばれた側の窓を空にしてから縮める。上限の計数（`StackMeter`）は、重なった分を二重に数えない形にする。計数の仕方が変わることを記録に書く。

### 比べるプログラム

R05 の組み立てで、F15 が作る形（関数と引数を、使用中のレジスタの末尾の連続した区画に置いてから `CALL` する。10-07 の `CALL A B C` と 02-07「レジスタの割り当て」）で組み立て、両方の形で同じ命令列を走らせる。F15 の割り当てでは、引数を準備する `MOVE` の数は二つの形で等しく、差は `CALL` の中で写す値の数と窓の大きさに出る。重ねる形で `MOVE` が増えるのは、`B+C` より後ろに呼び出しの後も生きるレジスタがある場合だけである。このことを結果の一つとして記録に書く。条件 1 の判定は、生存の情報（10-07 の `LastUse`・`Dead` だけで、生きている集合は持たない）からは得にくいので、重ねられる呼び出しだけを組み立てのプログラムで作る形にしてよい。重ねる形の `CALL` は、引数を読み出さずにそのまま残す（`read_many` は最後の使用の引数を空にするので通さない）。呼ばれた側の窓のうち引数より後ろのスロットは空にする。

- 末尾でない再帰（fib）
- 長い末尾再帰（100 万回。数え上げ）
- 引数の多い関数を多く呼ぶ（引数 6 個程度）
- 呼び出しの結果を引数に使う入れ子の呼び出し（`f(g(x), h(y))`）

### 測るもの

| 項目 | 取り方 |
|---|---|
| 総移動量 | 引数の準備の `MOVE` の数と、`CALL` の中で写した値の数の合計。VM の中の計数（測定のリビジョンだけに入れる）か、命令の実行回数から数える |
| レジスタの領域の最大量 | 区画の `regs` の長さの最大と `StackMeter` の最大 |
| 時間 | release のビルドで、各プログラムを複数回実行した時間の中央値 |

時間の測定は計算機の状態に影響されるので、スキル `benchmark` の「始める前に確かめること」の 1 に従い、計算機を静かにして行う。実装担当は、決まった値になる項目（総移動量、`regs` の最大、`StackMeter` の最大）と同じ結果のテストを自分で走らせて記録に書く。時間の `#[ignore]` のテストは書いて、動くことだけを短い回数で確かめ、本測定はしない。記録の時間の欄は空けておき、オーケストレータがほかの作業を止めてから `cargo test --release -p benitoite --lib -- --ignored <名前>` で測って埋める。回収の受け入れテストは、`scripts/check.sh` と同じ `--no-default-features --features gc-mark-sweep,heap-verify` と `gc-refcount,heap-verify`（それぞれ `gc-stress` を足した組も）で走らせる。

### 記録

記録には、比べた二つのコミット、ビルドの設定、プログラムの命令列の要約、三つの項目の結果、重ねる形の条件（上の 1〜3）を満たすためにコード生成と VM に要る変更の見積もり、採るかの案を書く。案であって決定ではないことを明記する。OPEN-063 の 2 つ目の箇条を測っていないことも書く。

## 受け入れテスト

- 同じ結果: 四つのプログラムが、二つの形で同じ結果を返す（測定のリビジョンで確かめる）。
- 上限: 重ねる形でも、末尾でない再帰が上限で `CallStackTooDeep` になり、長い末尾再帰が小さな上限で止まらない。
- 回収: 重ねる形で、`HeapConfig::stress` の設定と二つのメモリの管理の両方で、結果が変わらない（重なったスロットの所有を誤ると、ここで壊れる）。

## 完了条件

- 本番の枝に取り込む部分について、`scripts/check.sh` が通る
- 測定の記録が `tools/bench/results/` にあり、上の「記録」の内容を含む
- 測定のためだけのリビジョンのコミットを書く欄が記録にあり（オーケストレータが埋める）、本番の枝に取り込むファイルが本番の VM の `CALL` を変えていない
- 完了の報告に、設計者に確かめてもらう事項（採るかの案と、判断に効いた数値）を挙げている

## 確認の観点

[実装の確認の観点](../00-common/00-04-review-checklist.md)の「すべての作業で読む観点」に加えて、次の点を読む。

- 二つの形が同じ命令列（F15 が作る形）を走らせているか（一方だけ引数の準備の命令を省いていないか）。
- 総移動量に、引数の準備の命令を含めているか。
- 本番の枝の差分に、測定のリビジョンの変更が混ざっていないか。

## 難易度の理由

VM の変更は `CALL` と `RETURN` の窓の計算に限られるが、重なったスロットの所有と、生存の情報・回収・上限の計数との整合を崩さずに試作する必要がある。比べる命令列を公平に組み立てることにも注意が要る。
