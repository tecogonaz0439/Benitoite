# R17 呼び出しの手順と定数の読み出しの費用を減らす

- 依存する作業: [R16](R16-liveness-at-safepoints.md)
- 難易度: 3（1〜5。README の「作業一覧」）
- 規模の見込み: 小〜中（200〜700 行の変更。多くは `src/vm/dispatch.rs`）
- ブランチ: impl/R17-call-path-and-constants

## 目的

R16 の後の本測定（[記録](../../../../tools/bench/results/2026-10-05-r16-9bc60b3.md)）で、VM は最小実行版の VM に fib(35) で 1.01 倍（2.082 s 対 2.059 s）、loop で 1.17 倍（1.167 s 対 0.994 s）届かなかった（[ADR 0313](../../2026-10-09-design-first-release/decisions/0313-vm-performance-recovery-before-stage-2.md) の決定 5 の関門）。loop の 1 回の繰り返しの命令の数は最小実行版とほぼ同じ（16 対 17）なので、差は命令あたりの費用にある。記録の「残りの費用」が挙げた次の三つを直す。設計者が本作業の起動を承認した（2026-10-06）。

1. ヒープの定数の `LOADK`（fib・loop では自分自身の関数の値）が、毎回、定数の値の表（順序付きの写像 `BTreeMap<ConstIdx, Slot>`）を引く（CPU プロファイルの `constant` が 3%）。
2. 正常な経路で `drop_glue::<RuntimeError>` が走っている疑いがある（loop で 2%）。
3. 呼び出しの手順 `call`（普通の呼び出しと末尾呼び出し）が独立した関数として残り、loop で 13%、fib で 10% を占める。

振る舞いは変えない。ADR 0313 の決定 2・3（局所の状態、普通の呼び出しと戻りの規約）と ADR 0314（回収の前の整理）は変えない。

次のことは本作業の範囲に入れない。

- `Slot` の表現とヒープの番号の確かめ（ADR 0281）の変更。`runtime::heap` の内部の層の変更。値の大きさ（OPEN-065）。
- 範囲の確かめの省略（OPEN-064、R32）と、振り分けのループの `unsafe`。
- 命令の集合とコード生成の変更（上位命令、`MOVE` の削減など）。
- 窓を重ねる形（OPEN-063）。

## 作るもの

- `src/vm/state.rs`: 定数の値の表の形を、`ConstIdx` の番号で直接引ける形（たとえば `Vec<Option<Slot>>` を `CompiledProgram::consts` の長さで作る）に改める。`RunState` の欄は作業が決めてよい（10-09「実行ごとの状態」）。`RunState` の `Trace` は、表のすべての `Slot` を辿り続ける（10-09 の根の表の「定数の値の表」）。
- `src/vm/mod.rs` の `Vm::new` の本体（`sig=` の関数の本体だけ。シグネチャは変えない）: `RunState::new` に定数の数（`program.consts.len()`）を渡す。`RunState::new` の引数は作業が決めてよい（`RunState` は `sig=` の空の構造体で、欄と関連の関数は作業が決める）。
- `src/vm/dispatch.rs`（と子のモジュール）: 定数の読み出し、呼び出しの手順の書き換え。
- 定数の値の表を引く既存のテスト（`vm/tests.rs`・`vm/dispatch/collections.rs`・`vm/dispatch/numeric.rs` の `state.constants.get(&idx)` と、`vm/dispatch/traits/tests.rs` の `state.constants[&idx]`）を、新しい形で引くように直す。期待は変えない。

凍結したコードは変えない。00-03 の R15 の例外と同じ範囲の `#[inline]` の属性（release だけ `inline(always)` にする `cfg_attr` を含む）を、`file=` のファイルの小さな関数に加えることだけは認める（00-03「インターフェースの凍結」の R17 の例外）。

## 手順の要点

一つずつ入れ、入れるたびに既存のテストを通し、短い測定で効果を確かめる。効果のなかった変更は、コードが単純になるものだけを残す。どの変更でどれだけ速くなったかを、完了の報告に表で書く。

1. **定数の値の表**: 定数の値の表を番号で直接引ける形にし、`LOADK` でヒープの定数を作り終えた後の読み出しを、添字一つ（範囲を確かめる `get`）と `load` だけにする。作り終えた定数の読み出しは、振り分けのループの `LOADK` の分岐の中で行い、作る処理（今の `constant` の作業の積み重ね）は作っていない定数のときだけ呼ぶ。回収の要求の知らせを調べるのは、新しく作ったときだけとする（作り終えた定数の読み出しは確保しない）。
2. **正常な経路の `RuntimeError` の後始末**: release のビルドを逆アセンブルし（`objdump -d --demangle` などで、振り分けのループの関数の中の `bl` の呼び先を一覧にする）、振り分けのループと `call` の正常な経路で `drop_glue::<RuntimeError>`（や `Stop`・`Result<_, Stop>` の後始末）を呼んでいる箇所と、その原因を特定する。原因が、正常な経路で `Stop` の値を作って捨てる処理（`ok_or(…)` の引数で失敗の値を先に作る、`Result` を一時的に作って捨てるなど）なら、失敗の値を失敗のときだけ作る形（冷たい関数 `missing` など、R15 の形）に改める。特定できなかったら、調べたことを報告する。事前点検では、`integer_result` の `.ok_or(Stop::Runtime(RuntimeError::IntegerOverflow))`（成功のときにも失敗の値を作って捨てる。`ADDI`・`SUBI` が毎回通る）が疑わしいと見た（推測）。
3. **呼び出しの手順**: `CALL`・`TAILCALL`（と `METHOD`・`TAILMETHOD` が共通に使う部分）の普通の経路を軽くする。たとえば次の手を、測りながら選ぶ。
   - 普通の呼び出しと末尾呼び出しを、共通の `call` の中で何度も分岐し直す形から、命令の種類ごとの経路に分け、それぞれを振り分けのループに展開できる大きさにする（R15 で `call` 全体の強制展開は遅くなった。経路を分けたうえで、どちらをどこまで展開するかを測る）。
   - 呼び出しの前の安全点の普通の経路（上限の確かめ、`precall_done` の比較、`Budget::tick`）と、呼ばれた原型の確かめ（関数の値であること、引数の数）を、一度ずつに減らす。範囲の確かめと型の確かめは省かない。
   - 末尾呼び出しの窓の大きさの調整（`resize_with`・片付け）と計数（`StackMeter`）を、窓の大きさが変わらない場合に短く済ませる。
   - 新しい枠を積むときの `CallFrame` の組み立てと、局所の状態の設定で、同じ値を二度読まない。
   呼び出しの前の安全点の手順と順序（10-09）、予算を一つの呼び出しにつき一度だけ数えること、回収の前の整理（ADR 0314）の前提（呼び出し元の枠の `pc` を次の命令へ進めて保存するまで回収を挟まない）は変えない。
4. **残りの費用の内訳**: 1〜3 の後に、R15・R16 と同じ方法（処理を外した測定用の版との差。作業の環境で samply が動けば CPU プロファイル）で、fib と loop の残りの費用を報告する。

`[profile.release]` の設定は変えない。

## 受け入れテスト

- 振る舞い: 既存のテスト（VM、R11 のヒープの確かめ、ゴールデンテスト、参照インタプリタとの差分）が、期待を変えずに通る。`scripts/check.sh` の `gc-stress` の構成でも通る。`tests/call_allocations.rs` が通る。
- 定数: ヒープの定数（文字列、関数の値、構成子の値、リスト・写像・集合の定数）を、同じ実行の中で何度も `LOADK` しても同じ対象が返ることと、回収の後も定数の値の表から辿れることを、既存のテストで確かめる（足りなければ加える）。定数の番号が表の長さを超える場合に `Stop::Internal` で止まることも確かめる。
- 呼び出し: 末尾呼び出しで窓が大きくなる場合・小さくなる場合・変わらない場合、引数の多い呼び出し、呼び出しの前の安全点での回収と切り替え（`call_budget` を 1 にする）、上限の `CallStackTooDeep`、100 万回の末尾再帰を、既存のテストで確かめる（足りなければ加える）。

### 性能の確かめ方

- 実装担当: R15・R16 と同じく、作業を始めたときの `san_benito` の HEAD と本作業の版を、fib(30)・loop 300 万回で交互に数回走らせ、最小の時間を比べる。比較の版の展開と target は作業ディレクトリの中（`target/` の下）に置き、終えたら消す。
- オーケストレータ: 取り込みの前に、`tools/bench/gate.py` で関門を測る（最小実行版の VM と R16 の版を同じ機会に測り直す）。測定の前に設計者の確認を得る。記録を `tools/bench/results/<日付>-r17-<コミット>.md` に残す。

### 目標に届かなかった場合

R15・R16 と同じく、範囲の外の手に進まず、届かなかった値と残りの費用の内訳を報告して止まる。範囲の中の変更が正しく速くなっていれば、作業は完了として取り込む。

## 完了条件

- `scripts/check.sh` が通る（`runtime::heap` の内部の層を変えないので `check-heap.sh` は要らない。公開の層に `#[inline]` を付けた場合は `check-heap.sh` も通す）
- 定数の値の表を番号で引き、作り終えた定数の `LOADK` が表の写像を引かない
- 完了の報告に、手順ごとの効果の表、手順 2 で特定したこと、残りの費用の内訳、凍結したファイルに加えた属性の一覧を書いている

## 確認の観点

[実装の確認の観点](../00-common/00-04-review-checklist.md)の「すべての作業で読む観点」と VM の行に加えて、次の点を読む。

- 定数の値の表のすべての `Slot` を `RunState` の `Trace` が辿っているか。作っていない定数と作り終えた定数を取り違えていないか。番号の範囲を確かめているか。
- 呼び出しの前の安全点の手順と順序、予算の数え方、回収の前の整理の前提（呼び出し元の `pc` を進めて保存するまで回収を挟まない）を変えていないか。
- 末尾呼び出しの窓の調整を短く済ませる場合に、窓の外のレジスタを `Unit` に保つ規則（10-09）と、まだ読んでいない引数を壊さない順序を守っているか。
- 範囲の確かめと型の確かめを省いていないか。`unsafe` と `unwrap` を加えていないか。

## 難易度の理由

変更は VM の内部に閉じ、R15 で形を作った部分の手直しである。呼び出しの手順は、安全点・予算・回収の前の整理の前提と絡むので、順序を変えると回収の強制の下でだけ現れる誤りになりうる。
