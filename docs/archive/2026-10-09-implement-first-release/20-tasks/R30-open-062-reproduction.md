## 目的

設計書の 2 回目のレビューが挙げた実行時の振る舞いの机上の反例（[OPEN-062](../../2026-10-09-design-first-release/open-issues.md#open-062)）のうち、U2 の範囲の項目（R01〜R05、R13）について、反例を再現するテストを書き、再現するかを確かめる。順序に依存する振る舞いは、順序を与えるスケジューラと仮想の時間（ADR 0274）で順序を固定して書く。「再現しなかった」ことを「起きない」ことの根拠にできるようにするためである。

本作業は、再現したときに直さない。再現した項目は、テストを失敗する形のまま残して作業を止め、報告する（後述の「再現したとき」）。直し方は、OPEN-062 の表の「再現したときの修正の候補」をもとに設計者が決め、設計書と ADR を改めてから別の作業で直す（OPEN-062 の手順、[ADR 0270](../../2026-10-09-design-first-release/decisions/0270-open-062-items-in-runtime-rebuild.md) の決定 2）。

R14（HTTP のクエリとヘッダが UTF-8 でないときの扱い）は、HTTP の関数が U3 で入るので、U3 の作業 L33（[README](../README.md) の「U3 標準ライブラリ」）が同じ形で書き、本作業と同じ手順で OPEN-062 に記録する。R04 の HTTP の受け付けの確かめも L33 が加える。R08（正規表現のリテラルの検査）は、初回リリース版では対処しない（[ADR 0316](../../2026-10-09-design-first-release/decisions/0316-no-compile-time-regex-check-in-first-release.md)）。

## 手順の要点

### 書き方

- 一つの項目に一つのテストの関数を置き、関数の名前に項目の番号を入れる（`open_062_r02_request_mode_starts_io` など）。先頭のコメントに、OPEN-062 の反例の文と、確かめる性質（「起きない」なら何が成り立つか）を書く。
- 順序に依存する項目は、筋書きで順序を与えた実行を、再現しうる順序ごとに並べる。反例の文が「切り替えの順序によって」と書く項目は、少なくとも反例が起きうる順序と起きない順序の二つを並べる。
- 筋書きで順序を与えた実行は、筋書きの記録（R25）で、筋書きを使い切ったことと、狙ったタスクを選び、狙った時点で仕事を実行し時間を進めたことを確かめる。待ち行列の先頭を選ぶ既定の振る舞いで偶然に狙った順序になった実行を、再現した・しなかったの根拠にしない（10-10「テストで差し替える部品」、相談の第 7 回の指摘 7）。時間を進める指示と仕事を実行する指示は、完了の取り込みの境界（待たせる位置と、予算を使い切った遅い経路）で行われるので、「B が計算を続けている間」の時点は、B の予算の一巡りを単位として筋書きの位置で決める。
- 筋書きの `RunWorker(ExtOpId(n))` の番号は、実行の中の外部の操作ごとに 0 から順に振られる。番号を推測で書かず、`WorkerExec` を包む実装で `submit` の `job.op` を記録し、狙った仕事の番号であることを確かめる形で書く。
- スクリプトは、`import Benitoite.Unofficial.IO.Console` などの非公式の名前でモジュールを取り込む。U3 で入る名前は使わない。
- IO の二つの方式で同じテストを実行する（ADR 0264 の決定 7）。
- 予算は、切り替えが起きるように小さな値（1 など）にした実行と、既定の値の実行を並べる。
- 実時間の待ちに頼らない。出力先を止める・動かすのは channel の知らせで行う。結果の判断に実時間を使うのは、後述の「届いていないことの判断」の上限付きの待ちだけとする。

### 補助の作り方

- 部品を包む実装: `ScheduleHandle::parts` が返す `RuntimeParts` の `picker`（`TaskPicker`）と `workers`（`WorkerExec`）を、自前の実装で包んでから `RunEnv::parts` に渡す。包む実装は、`TaskPicker::spawned` と `WorkerExec::wakeup` を含むすべての関数を中の実装へ渡す。`wakeup` を渡さないと既定の `None` になり、前提の待てる形の `Wakeup` が使われない。
- R04 の標準出力の止め方: `OutputTarget` は `Stdout`・`Stderr`・`Capture(Arc<Mutex<Vec<u8>>>)` の閉じた列挙で、利用者の `Write` を渡す口がない。そこで標準出力を `Capture` にし、テストの助けのスレッドがその `Mutex` を握って書き出し用のスレッドを止める。書き出し用のスレッドは、書くたびに `Capture` の `Mutex` を取る（`runtime::run` の `TargetWriter` が `OutputTarget::write_bytes` を呼ぶ）ので、握っている間は書き込みで止まる。助けのスレッドは、`Mutex` を握ったことを channel で知らせてから待ち、テストは知らせを受けてから `run_program` を呼ぶ（`MutexGuard` は別のスレッドへ渡せないので、助けのスレッドが自分で握る）。助けのスレッドは、channel の放す知らせを受けて `Mutex` を放す。放す知らせを送るのは、後述の偽の中断の読み口の印を立てた後の、包んだ `TaskPicker` である。知らせが来ないまま止まり続けないように、助けのスレッドの待ちには上限（数秒）を置き、上限で放したときはテストを失敗にする。
- R04 の観測: 包んだ `TaskPicker` が `pick` のたびに標準エラー出力の `Capture` を読み、標準出力を止めている間にタイマーの満了の後の出力と標準エラー出力の内容が届いたことを記録する。止める手順に移ったことを、標準出力を放す前の観測でどう示すかは本作業が決め、決めた形を完了の報告に書く。
- 偽の中断の読み口: `InterruptSource` を実装し、一つの `AtomicBool` を `requested`（`Relaxed` で読む）と `flag`（`Some(&印)` を返す）の両方で返す。R28 は、呼び出しの速い経路で `InterruptSource::flag` を読み、`None` なら印を読む処理を飛ばすので、`requested` だけの実装では計算を続けるタスクの途中で印が調べられない。印を立てるのは包んだ `TaskPicker` であり、標準出力を止めている間に、標準エラー出力の `Capture` に期待した内容が届いたことを `pick` で観測した時点で立てる。
- R13 の観測の時点: 包んだ `TaskPicker` が `pick` のたびに標準出力の `Capture` を読み、筋書きで定めた時点（B の予算の何巡り目か）の内容を記録する。プロンプトの行では、包んだ `WorkerExec` が、標準入力の読み取りの仕事を `submit` で受けた時点の内容を記録する。
- 届いていないことの判断: 書き出し用のスレッドは VM のスレッドと別に動くので、観測の時点で `Capture` に行がないだけでは、届いていないと判断できない。観測の時点で行がなければ、その場で（VM のスレッドを止めたまま）上限付きの待ち（例 300 ミリ秒）の間 `Capture` を読み直し、上限までに現れれば届いた、現れなければ届いていないと判断する。行が現れた時点で待ちを打ち切る。

### 再現したとき

- 再現した項目のテストは、成り立つべき性質を表明する形のまま残し、失敗する状態で作業を止める。`#[ignore]` を付ける、表明を反転する、期待値を今の振る舞いに合わせる、といった形で通さない（テストを消したり飛ばしたりして `check.sh` を通さない。[作業の進め方](../00-common/00-03-workflow.md)の「最小実行版の実装からの移行」の箇条と同じ扱い）。
- 処理系を直さない。直し方を自分で考えて入れない。
- 完了の報告の「残したこと」に、項目ごとに、再現した順序（筋書き）、観測した結果、OPEN-062 の表の「再現したときの修正の候補」を書く。候補がない項目（R13 の準備を知らせる行の場合など）は、候補がないことを書く。オーケストレータが設計者に示し、設計者が直し方を決める。直しは設計書と ADR を改めた後に別の作業で行い、そのときにこのテストが通るようになる。
- 再現した項目があっても、再現しなかった項目のテストは完成させる。取り込みは、再現した項目の扱いを設計者が決めてから行う。

### 再現しなかったとき

テストを回帰のテストとして残す。完了の報告に、項目ごとに再現しなかったことと、その理由（どの規則がどの順序で反例を防いだか。ADR 0264〜0266 のどの決定か）を書く。オーケストレータはこれを OPEN-062 の本文に記録する（OPEN-062 の手順の「再現しない理由をこの項目に記録する」）。

## 受け入れテスト

- 上の表の各行について、テストがある。順序に依存する行は、筋書きで与えた順序ごとのテストがある。
- どのテストも、IO の二つの方式で実行する。
- 再現しなかった項目のテストが通る。

## 完了条件

- 再現した項目がなければ、`scripts/check.sh` が通る
- 再現した項目があれば、そのテストだけが失敗し、完了の報告にその項目と修正の候補が書かれている
- 項目ごとの結果（再現したか、しなかったなら理由）が完了の報告にある
- `src/` を変えていない

## 確認の観点

- 各テストが、OPEN-062 の反例の文をそのまま形にしているか。反例より弱い形（再現しにくい形）に変えていないか。
- 順序を筋書きで与えており、実時間やスレッドの順序の偶然に頼っていないか。
- 「起きない」とした項目で、起きないことを示す表明（終わる、届く、一度だけ解放される）が、観察できる振る舞いで書かれているか（非公開の状態を読んでいないか。スキル `test-audit`）。
- 再現した項目を、テストを弱めて通していないか。

## 難易度の理由

仕組みはすべて揃っているので、書く量は多くないが、反例の文を順序を与えた実行に正確に移す必要がある。とくに R13 の後半と R01 は、再現するかどうかが順序の与え方に依存し、与え方を誤ると「再現しなかった」ことの根拠にならない。
