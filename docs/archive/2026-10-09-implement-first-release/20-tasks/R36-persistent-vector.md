# R36 `List` を永続ベクタ（RRB 木）に移す

- 依存する作業: [R14](R14-stage1-wrap-up.md)
- 難易度: 4（1〜5。README の「作業一覧」）
- 規模の見込み: 大（1500 行超。テストを含む）
- ブランチ: impl/R36-persistent-vector

## 目的

`List` の値の表現を、第 1 段の連結リストのセル（`FieldsKind::ListCell`）から、分岐の数を 32 とする RRB 木（relaxed radix balanced tree）の永続ベクタに移す（[ADR 0104](../../2026-10-09-design-first-release/decisions/0104-list-as-persistent-vector.md)、03-06「List の内部の表現」）。`runtime::list` の関数のシグネチャは変えない。組み込みの関数と VM はリストの表現を `runtime::list` の関数だけで扱う（10-08「リスト」）ので、ほかのコードは変えずに済む。

03-06 は「木の形の細部（緩和したノードを詰め直す条件など）は、実装プランで定める」とする。本文書の「木の形」で定める。

第 1 段の測定の途中で表現を変えない（ADR 0268 の決定 4）ので、本作業は第 1 段の締め（R14）の後に行う。

## 木の形

`M = 32`（分岐の数）とする。

- リストの値は、`Value::EmptyList` か、頭のノード（`FieldsKind::ListNode`、下の役割が「頭」）を指す値である。頭のノードは、長さ（`Integer` の値）、木の高さ（シフトの量）、根のノード（空の木なら `Unit`）、末尾の葉を持つ。
- ノードは `FieldsKind::ListNode` の対象とし、`tag` の下位 2 ビットに役割（頭、厳密な内部のノード、緩和した内部のノード、葉）を、残りのビットに高さを入れる。この割り当ては本作業が決めて、`list.rs` の先頭の `//!` に書く。
- 葉は要素を 1〜32 個持つ。厳密な内部のノードは、子を 1〜32 個持ち、最後の子のほかの子はすべて満ちている（その高さの最大の要素の数を持つ）。添字は基数（5 ビットずつ）で子を選べる。
- 緩和した内部のノードは、子を 1〜32 個持ち、子の並びの後に、子ごとの要素の数の累積の表を同じ数の `Integer` の値として持つ（値の並びは 2k 個）。添字は累積の表を探して子を選ぶ。
- 末尾の葉は木とは別に持ち、末尾への追加をほとんどの場合に葉の写し一つで済ませる（03-06）。末尾の葉が満ちていれば、木に押し込んでから新しい末尾の葉を作る。
- 根が子を一つだけ持つ内部のノードになったら、高さを一つ下げる。

### 連結と分割

- 連結（`concat`）は、RRB 木の連結の手順で行う。二つの木の境目の並び（左の木の右端と右の木の左端の、同じ高さのノード）を下から順に一つにまとめ、各高さで、子の数の合計を s としたときにまとめた後のノードの数が `⌈s / M⌉ + E_MAX` 以下になるように、子の少ないノードの中身を隣へ詰め直す。`E_MAX = 2` とする。この詰め直しの条件は、RRB 木の文献（Bagwell と Rompf の RRB-Trees の報告）の探索の緩和の条件に当たる【要検証：文献の定めと数値】。本文書の条件を正とし、文献と違っていても本文書の条件で書き、違いを完了の報告に書く。
- 末尾の葉は、連結の前に木に押し込む。
- 分割（`slice`、`tail`）は、根から切る位置までの道筋のノードだけを写し、境目のノードを緩和したノードにする。道筋の外のノードは共有する（構造共有）。
- `prepend` は、要素一つのリストとの連結として書いてよい（計算量は O(log n)。03-06 の表）。
- `from_values` は、要素の並びから、下から厳密な木を作る。

### 共通の規則

- ノードと葉は作った後に変更しない。更新は根から変わる葉までの道筋のノードだけを写す（03-06）。
- どの関数も Rust の再帰を使わず、明示の積み重ね（`Vec`）で辿る（AGENTS.md「再帰の深さ」）。木の高さは長さの上限（2^24）で 5 程度に収まるが、規約のとおり明示の積み重ねで書く。
- 長さの上限（2^24 要素）を超えるリストを作る関数（`from_values`・`prepend`・`append`・`concat`）は、作る前に `ResourceError::ValueTooLarge` を返す。
- 木の不変条件（累積の表が子の要素の数の和と一致する、長さが木と末尾の葉の要素の数の和である、厳密なノードの最後の子のほかは満ちている、連結の後の各高さのノードの数が上の条件を満たす）を、`debug_assert!` で確かめる（ADR 0211）。操作ごとに確かめるのは、その操作で新しく作ったノード（道筋）だけとする。木の全体を辿って確かめるのは、モデルとの比較のテストの小さな大きさに限る（全体を毎回辿ると、長さ 2^20 のテストや既存の 1000 万要素のテストが、デバッグのビルドで O(n²) になる）。
- 長さ 0 の結果（`slice`・`tail` が空になる場合など）は、必ず `Value::EmptyList` にする。
- 一回の操作で確保する対象の数は O(log n) に収まる。

## 手順の要点

1. 第 1 段の `runtime::list` のテスト（R06 が書いたもの）が、表現を変えた後もそのまま通ることを先に確かめられるよう、書き換えの前に今のテストを読んでおく。テストが表現（`ListCell`）に依存していれば、観察できる振る舞いのテストに直す（スキル `test-audit`）。たとえば `list.rs` の既存のテストの、連結リストの共有を前提にした `same_object` の確かめ（`tail(prepend(l))` や `slice` の結果が元と同じ対象であること）と、`ListCell` を長さ 2^24 で作る上限のテストが当たる。上限のテストは、長さだけを持つ頭のノードを非公開の補助で作る形にしてよい。
2. 木の型と役割の割り当て、読み出し（`len`・`get`・`to_vec`）、作成（`from_values`）、末尾への追加（`append`）、連結（`concat`）、分割（`slice`・`tail`）、先頭への追加（`prepend`）の順に書く。
3. 構造の `=`（`values_equal`）と、リストを要素の順に辿るほかの箇所が、表現によらずに要素の並びで比べる（10-08「構造の等しさ」の「リストは要素の並びで比べる」）ことを確かめる。
4. 回収の強制のビルドで、ゴールデンテストと差分テストが通ることを確かめる。

## 受け入れテスト

- 単純なモデルとの比較（ADR 0211、07-03）: 無作為に選んだ操作の列（`from_values`・`append`・`prepend`・`concat`・`slice`・`tail`・`get`・`len`・`to_vec`）を、リストと Rust の `Vec` の両方に同じ順に適用し、各操作の後に要素の並びと長さが一致することを確かめる。操作の引数（位置、長さ）は、境目（0、31、32、33、1023、1024、1025 など、葉と内部のノードの大きさの境目）を多く選ぶ。乱数はテストの中の小さな生成器で作り、種を固定する。テストはデバッグのビルドで実行するので、操作のたびに `debug_assert!` の不変条件も確かめられる。
- 引数を変えないこと: どの関数も、呼ぶ前後で引数のリストの要素の並びが変わらない（同じ値を二度 `to_vec` して比べる）。連結と分割を繰り返して構造を共有したリストどうしで確かめる。
- 大きなリスト: 長さ 2^20 のリストを `append` の繰り返しで作り、`get` で全要素を読み、`concat` と `slice` を繰り返しても、処理系のスタックを使い果たさない。
- 連結の繰り返し: 短いリストを 10 万回連結したリストが、モデルと要素の並びで一致し、処理系のスタックを使い果たさない。木の高さはテストでは確かめず、連結の詰め直しの条件の `debug_assert!` と性能の測定に任せる（ADR 0211 の決定 3、03-06 の表）。
- 上限: 長さ 2^24 のリストへの `append` と、合計が 2^24 を超える `concat` が `ValueTooLarge` になる（大きなリストを実際に作るテストは時間がかかるので、上限の確かめが作る前に行われることを、長さだけを変えた単体テストで確かめる方法を選んでよい）。
- 既存のテスト: `List` の組み込みの関数の単体テスト（R08）、ゴールデンテスト、差分テストが、表現を変えた後もそのまま通る。
- 回収の強制のビルドで、上のテストが通る。

## 難易度の理由

RRB 木の連結と分割は、緩和したノードの累積の表と詰め直しの条件を正しく扱う必要があり、誤りは特定の長さの境目でだけ現れる。単純なモデルとの比較を境目の多い操作の列で行うことで見つける。
