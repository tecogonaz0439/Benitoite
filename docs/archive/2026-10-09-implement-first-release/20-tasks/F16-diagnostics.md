# F16 診断の拡張

- 依存する作業: [F06](F06-resolver.md)
- 難易度: 3（1〜5。README の「作業一覧」）

## 目的

診断の内部の表現（10-02 の `Diagnostic`）を、文章の形式と JSON の形式に書き出す関数（`diag::render`）を、初回リリース版の報告に広げる（02-10「文章の形式」「JSON の形式」「実行時エラーと資源の不足の報告」「解放の失敗の報告」「処理系の不具合と処理系の制限の報告」）。加わるのは、複数のファイルの位置、置き換えを持つ修正案、警告と `--deny-warnings`、呼び出しの履歴の新しい段の名前、タスクの起動の履歴、行き詰まりの報告、解放の失敗の報告である。

あわせて、診断コードの表の形を確かめる単体テストを書き、[F06](F06-resolver.md) までの段が出す診断（E01〜E03、W0301）の修正案と置き換えを、02-10「修正案」の表と照らして揃える。F07 以降が出す診断の置き換えは、それぞれの作業が付けて確かめる（10-02「作業の割り当て」）。出力はパイプラインと CLI（F18）、実行時エラーの報告（R38 が組み立てた `Diagnostic` を書く）、ゴールデンテストの実行器（C10）が使う。

## 手順の要点

### 写して広げる

最小実行版の書き出し（抜粋、行番号の幅、`^`・`-` の並べ方、色、JSON の文字列の書き出し、呼び出しの履歴の列の揃え）は写して使う。ファイルの表示名と行と列は、span のファイル ID で `SourceTable::get` を引き、`Source::line_col`・`line_text` で求める（列はコードポイントで数える。ADR 0025）。JSON の文字列の書き出しは、依存するクレートを使わずに手で書く（10-02）。

文言と見出しの文は `codes::text` の定数だけを使い、`render.rs` に英語の文を直接書かない（00-02「文言」）。`error`・`warning`・`runtime error` などの重大度の語と JSON の鍵の名前は、書式の一部として `render.rs` の定数に置いてよい（最小実行版のとおり）。

### 10-02「診断の書き出し」の変更

表の各行を実装する。本プランで補う点を次に示す。

- **複数のファイル**: 補助の位置が主な位置と別のファイルにあれば、`::: 表示名:行:列` の行と抜粋を加える。別の行でも同じファイルなら、最小実行版のとおり `:::` の行を加える（02-10 の例）。標準ライブラリのソースの位置も表示名 `<benitoite>/X/Y.bnt` で同じく示す。
- **置き換えを持つ修正案**: `= help:` の行の後に、置き換えを当てた後の行を行番号付きで示し、変わった部分の下に `~` を並べる（02-10 の `uses IO` の例）。本プランの決定として、次のように書く。
  - 置き換えをファイルごとにまとめる。主な位置と別のファイルの置き換えは、その前に `::: 表示名:行:列` の行を置く。
  - 置き換えが当たる元の行の範囲（最初の置き換えの開始の行から、最後の置き換えの終了の行まで）を取り出し、その範囲の文字列に置き換えを当てる。当てた後の行を、元の範囲の最初の行番号から順に番号を振って示す（行を挿入する置き換えでは、後の行の番号が一つずつ増える）。
  - `~` は、当てた後の行の中の、置き換えで入れた文字の下に並べる。入れる文字列が空の置き換え（削除）は `~` を付けず、当てた後の行だけを示す。入れる文字列の中の改行は表示の上の幅を持たないので、`~` を付けない。入れる文字列が改行だけの置き換え（行の途中の `;` を改行に置き換える E0106 の修正案）は、削除と同じく `~` を付けず、改行で分かれた後の行をすべて示す。どの行にも `~` が付かないときは、`~` の行を書かない（最小実行版は置き換えを示さないので、本プランで決める）。
  - `~` の色は、補助の位置の `-` と同じ青の太字とする。
  - 修正案の行（当てた後の行と `~` の行）の後に、`= help:` などの `=` の行が続くときは、その間に `|` の行を一つ置く。抜粋の後に `=` の行が続くときに `|` の行を置く最小実行版の規則を、修正案の行にも当てはめたものである。修正案の行で診断が終わるときは `|` の行を置かない。
  - 行番号の欄の幅は、その診断で示すすべての行番号（修正案の行を含む）の最大の桁数で揃える。
  - 抜粋の中のタブは空白 4 つにする（`^`・`-`・`~` の位置を揃えるため。02-10）。
- **警告**: 重大度の語を `warning` とする。`Diagnostic::deny_warning` で誤りにした警告は `severity` が `Error` なので `error` と書く。件数の行は 02-10 の表のとおり誤りと警告を分けて数え（`text::SUMMARY_*`・`SUMMARY_WARNINGS_*`・`WARNINGS_ONLY_*`）、警告だけのときは `warning:` で始める。色を付けるときは、`warning` の重大度の語と、警告の主な位置の `^` と、`warning:` で始める行の頭の語を黄の太字（`\x1b[1;33m`）にする。誤りの色（赤の太字）は最小実行版のとおりとし、`deny_warning` で誤りにした警告も赤にする（最小実行版は警告を持たないので、本プランで決める）。
- **50 件の打ち切り**: 誤りと警告を合わせて数え、超えた分は `text::TOO_MANY` の行で示す。`TOO_MANY` の行の頭の語は、続く件数の行と同じにする（誤りが一件でもあれば `error:`、警告だけなら `warning:`。最小実行版は警告を持たず、常に `error:` と書いた）。件数の行の数は打ち切る前の件数で数える。JSON の形式は打ち切らず、件数の行も書かない。
- **動詞**: `Verb::Run`・`Check`・`Test` を `run`・`check`・`test` として件数の行に埋める。
- **呼び出しの履歴**: `FrameName::Handle`・`Case`・`Lazy` を `<handle ファイル:行:列>`・`<case 操作 ファイル:行:列>`・`<lazy ファイル:行:列>` と書く。`Lambda` は最小実行版のとおり。
- **タスクの起動の履歴**: `task_origins` が空でなければ、呼び出しの履歴の後に `text::TASK_ORIGINS_HEADER` の注記として並べる。
- **履歴の列の揃え**: 呼び出しの履歴とタスクの起動の履歴の各段は、最小実行版のとおり、行番号の欄の幅に 11 を足した数の空白で字下げして名前を書く。呼び出した位置を持つ段は、名前の後を、呼び出しの履歴とタスクの起動の履歴を合わせた中で最長の名前の幅まで空白で埋め、空白 1 つの後に `at 位置` を書く。位置を持たない段は名前だけを書き、後ろに空白を付けない。名前の幅はコードポイントの数で数える。最小実行版は呼び出しの履歴の中だけで最長の名前の幅に揃えており、この規則は同じ揃え方を二つの履歴を合わせて当てはめたものである（02-10 の `count.bnt` と `server.bnt` の例）。
- **注記の順**: 注記は、呼び出しの履歴とタスクの起動の履歴の後に、`notes` の順に書く。末尾呼び出しの注記は R38 が `notes` の末尾に入れ、止める途中の解放の失敗の注記はその前に差し込む（`runtime::report` の `insert_before_tail`）ので、書き出しの側で注記を足したり並べ替えたりしない。
- **行き詰まり**: `waiting` が空でなければ、`-->` の行と抜粋を書かず、`text::WAITING_HEADER` の注記として、待つタスクごとに一行を並べる（02-10 の R1001 の例）。各行は、履歴と同じ字下げの後に、タスクの列（`WaitingTask::task` の名前。位置があれば ` at 位置` を続ける）、待つ種類の列（`text::WAITS_FOR` に `waits_for` を埋めた文字列）、待つ位置（` at 位置`）を並べる。タスクの列と待つ種類の列は、それぞれの列の最長の幅まで空白で埋め、列の間を空白 1 つで区切る。待つ位置がない行は ` at …` を書かず、待つ種類の列を空白で埋めない（行末に空白を残さない）。行き詰まりの報告では、R38 の `deadlock_diagnostic` が段のない呼び出しの履歴（`frames` が空の `CallTrace`）を `trace` に入れるが、文章の形式では `text::TRACE_HEADER` の注記を書かない。JSON の形式では、後述のとおり `trace` を空の配列として書く。
- **報告の種類ごとの重大度の語**: `Check` は `error`・`warning`、`Runtime`・`Resource` は `runtime error`、`Release`・`Limit`・`Args` は `error`、`Internal` は最小実行版のとおり（02-10 の各例）。JSON の `kind` は 02-10「JSON の形式」の表の値（`Release` は `"release"`）とする。
- **JSON**: `helps` の要素を `{"message":…,"edits":[…]}` とし、置き換えは `file`・`start`・`end`（それぞれ `line`・`column`・`offset`）・`replacement` を持つ。項目の順は 10-02 のとおり（`kind`・`severity`・`code`・`message`・`primary`・`secondary`・`notes`・`helps` の後に、あれば `trace`・`traceOmitted`・`taskOrigins`・`waitingTasks`・`backtrace`）。`trace` があるときは `taskOrigins` も書く（空なら `[]`）。行き詰まりでは `trace` と `taskOrigins` を空の配列にし、`waitingTasks` を加える（02-10）。`:` と `,` の後に空白を入れない。

### 表の形を確かめるテスト（10-02「作業の割り当て」）

- すべてのコードについて、`fixes` の鍵がどれも `extras` の鍵である。`extras` の鍵が一つのコードの中で重ならない。
- `ALL` のコードの `id` が重ならず、`RETIRED` のどれとも重ならない。`id` の形が英大文字 1 文字と 4 桁の数字で、頭の文字と `kind` が 10-02「表の項目」の対応（`E`・`W` は `Check`、`L` は `Limit`、`R09` は `Resource`、`R03` は `Args`、ほかの `R` は `Runtime`）に合い、`W` だけが `Warning` である。
- 型板（`message`・`label`・`extras` の文）から `{名前}` の置き場所を除くと、残る `{` と `}` は、バッククォートで囲んだコードの字面の中にしかない。E0110・E0119・E0212 などは、コードの字面の中に波括弧を一つだけ書いているので、`{` と `}` が対になることは求めない。`explanation` は型板でないので対象にしない。

### 修正案の揃え（E01〜E03、W0301）

02-10「修正案」の表の行のうち、E01〜E03 の診断に当たる行（`;`、複数のスカラー値からなる文字、波括弧、比較演算子の連なり、値に続けたドット、`try` の直後の `{`、見つからない名前、修飾しない構成子、取り込んでいないモジュール、`uses` の並び、`uses IO`、範囲のパターンの形、最小実行版の書き方の各行、`bind` と `shadow`、左辺の混ざり、変数のない `shadow`、キーワードを書けない束縛）について、次を確かめ、足りなければ直す。

- 修正案を示している。置き換えの欄が「あり」の行は置き換えを付け、「なし」の行は付けない。「候補が一つのときだけ」の行は、候補の数で付けるかを変える。
- 置き換えを付けた診断について、`help_tests.rs` で、置き換えを当てたソースを F05 の `modules::memfs` と F06 の `resolve::test_support` で読み直し、同じコードの診断が消えることを確かめる（置き換えを当てれば誤りがなくなるときだけ付けるという 02-10 の条件）。構文の誤りは字句解析と構文解析だけで読み直す。
- 修正案の鍵が、そのコードの `fixes`（置き換えのあるもの）か `extras`（文だけのもの）にある。

直すのは修正案だけである。直した箇所は完了の報告の「判断したこと」に挙げる。F07〜F10 のコード（E04〜E07 の型の誤り）の修正案は、それぞれの作業が付けるので、本作業は扱わない。

## 受け入れテスト

単体テストで確かめる。書き出しのテストは、手で組み立てた `Diagnostic` とソースの表（`SourceTable::add`）を与え、出力の文字列全体を比べる。02-10 の例を再現するテストも、02-10 の文言・ラベル・注記の文字列をそのまま入れて `Diagnostic` を手で組み立てる。`DiagBuilder` や実際の段（名前解決、R38 の報告の組み立てなど）では作らない。02-10 は例の診断コードと文言を説明のためのものとしており、段が実際に出す診断と一致するとは限らないからである。

## 確認の観点

- 文章の形式と JSON の形式が、同じ `Diagnostic` から同じ内容を作っているか（位置、注記、修正案、履歴）。
- 列をコードポイントで数え、`^`・`-`・`~` を表示の上で揃えているか（タブ、多バイト文字）。
- 置き換えの表示が、置き換えを当てた結果と一致しているか（置き換えの順、重ならない置き換えの前提）。
- 修正案の揃えで、何を誤りとするかや主な位置を変えていないか。F07 以降の作業のファイルに触れていないか。
- 50 件の打ち切りと件数の行の数え方が、警告を含めて 02-10 のとおりか。

## 難易度の理由

書き出しの骨格は最小実行版から写せる。加える書式（置き換えの表示、複数のファイル、履歴の新しい段、行き詰まり、解放の失敗）は 02-10 が例で定めており、判断の余地は小さい。手間がかかるのは、置き換えを当てた後の行の組み立て（挿入・削除・複数行）と列の揃えを、境界の場合まで正しく書くことと、E01〜E03 の修正案を 02-10 の表と一行ずつ突き合わせることである。
