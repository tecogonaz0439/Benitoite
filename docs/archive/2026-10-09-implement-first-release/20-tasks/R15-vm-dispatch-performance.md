# R15 振り分けのループと呼び出しの手順の性能の回復

- 依存する作業: [R14](R14-stage1-wrap-up.md)
- 難易度: 4（1〜5。README の「作業一覧」）
- 規模の見込み: 中（500〜1500 行の変更。多くは `src/vm/dispatch.rs` の書き換え）
- ブランチ: impl/R15-vm-dispatch-performance

## 目的

初回リリース版の VM を、最小実行版の VM 以上の速さに戻す（[ADR 0313](../../2026-10-09-design-first-release/decisions/0313-vm-performance-recovery-before-stage-2.md)）。第 1 段の測定で、初回リリース版の VM は最小実行版の VM より 5〜6.6 倍遅かった（fib(35) 10.1 s 対 2.06 s、loop 6.6 s 対 1.0 s。[第 1 段の測定の要約](../../../../tools/bench/results/2026-10-05-stage1-5b300d4-summary.md)）。原因の大半は、R09 が書いた振り分けのループが、[ADR 0263](../../2026-10-09-design-first-release/decisions/0263-dispatch-loop-locals-and-verifier.md) の決定 1 と 10-09「振り分けのループの局所の状態」を守っていないことにある（ADR 0313 の背景の 1〜9）。

本作業は、ADR 0313 の決定 2・3 に従って振り分けのループと呼び出しの手順を直す。振る舞いは変えない。目標は ADR 0313 の決定 5 の第 2 段の開始の関門（fib(35) と loop の時間が、同じ計算機で測り直した最小実行版の VM 以下）である。時間の本測定はオーケストレータが行う（後述の「性能の確かめ方」）。

次のことは本作業の範囲に入れない。

- 生存の情報の処理を回収の安全点へ移すこと（ADR 0313 の決定 4。R16 で扱う）。本作業は、即値のレジスタへの書き込みを省く安い経路（ADR 0313 の決定 2 の「即値の安い経路」）だけを行い、生存の情報の形と、ヒープの値を持つレジスタの `take`・`clear` は変えない。
- 窓を重ねる形（[OPEN-063](../../2026-10-09-design-first-release/open-issues.md#open-063)）と、範囲の確かめの省略（[OPEN-064](../../2026-10-09-design-first-release/open-issues.md#open-064)。R32）。`unsafe` を振り分けのループに書かない。
- 命令の集合、コード生成、生存の情報の計算（`bytecode::liveness`）の変更。上位命令と命令の特殊化（ADR 0263 の決定 5）。
- 値の大きさの変更（[OPEN-065](../../2026-10-09-design-first-release/open-issues.md#open-065)）。

## 作るもの

- `src/vm/dispatch.rs` と子のモジュール（`dispatch/numeric.rs`・`dispatch/traits.rs`・`dispatch/collections.rs`）: 振り分けのループと命令ごとの処理を、後述の「手順の要点」のとおり書き換える。
- `src/vm/state.rs`・`src/vm/frame.rs`・`src/vm/budget.rs` の非公開の部分: 局所の状態を支える補助の関数。`RunState` の欄は作業が決めてよい（10-09「実行ごとの状態」）。
- 非公開の補助の型: 局所の状態のうち `LoopLocals`（`file=` のコード）が持たないもの（実行中の原型への参照、窓の大きさなど）を持つ型を、`dispatch.rs` に加えてよい。`LoopLocals` の欄と、`LoopLocals::load`・`save` のシグネチャは変えない。
- `#[inline]` の付与: 振り分けのループから命令ごとに呼ぶ小さな関数に `#[inline]` を付ける。対象は、`runtime::heap` の公開の層の `Slot` と `NoGcCtx` の読み書き（`load`・`store`・`take`・`clear` など、`sig=` の関数）と、それが呼ぶ内部の層の小さな関数（`HeapCore` の読み書き）、命令の種類を得る `Instr::opcode` と `Opcode::from_u8` である。
- `tests/call_allocations.rs`: 普通の呼び出しと戻りで動的確保がないことを確かめるテスト（後述の「受け入れテスト」）。

凍結したコードの扱いは次のとおりとする。どれも完了の報告の「判断したこと」に挙げる。

- 10-09 の `file=`・`sig=` のコード（`LoopLocals`・`LoopExit`・`CallFrame`・`Segment` などの型と、`sig=` の関数のシグネチャ）は変えない。`sig=` の関数の本体は書き換えてよい。
- `#[inline]` の属性を加えることだけは、`file=` のファイル（`src/bytecode/instr.rs`、`src/runtime/heap/slot.rs` など）でも行ってよい。型・シグネチャ・本体は変えない。これは 00-03「インターフェースの凍結」に挙げた例外であり、本作業に限る。
- 後述の手順 7 で、戻りでレジスタの `Vec` を縮めない形を採る場合に限り、`Segment::reg_count`（`file=src/vm/frame.rs`）の本体を、使用中の終端に従う形に改めてよい（ADR 0313 の決定 3 の最後から二つ目の箇条）。使用中の終端は、区画の最も上の呼び出しの枠の `base + size`（枠がなければ 0）から求め、`Segment` に欄を加えない。シグネチャは変えない。なお `reg_count` は今どこからも呼ばれておらず、上限の計数は `StackMeter` が枠の `size` で数えている。採らない場合は変えない。
- `runtime::heap` の内部の層は、`#[inline]` の付与のほかに変えない。`unsafe` のブロックを加えない。

## 手順の要点

一つずつ入れ、入れるたびに既存のテストを通し、短い測定（後述の「性能の確かめ方」の実装担当の分）で効果を確かめる。効果のなかった変更は、コードが単純になるものだけを残す。どの変更でどれだけ速くなったかを、完了の報告に表で書く（ADR 0268 の決定 4 のとおり、改善の効果を別に測るため）。

試作の差分（相談の第 8 回の `08-prototype-dispatch.diff`）は、手順 1〜3 の一部を、一部の命令だけの速い経路として書いた測定のための形である。予算の遅い経路でタスクを切り替える場合と、`main` の `RETURN` を省いている。考え方の参考にとどめ、そのまま写さない。本作業では、速い経路と遅い経路の二つの振り分けを作らず、すべての命令の処理を同じ規則で書く。

1. **窓を命令ごとに一度だけ得る**（背景の 1・5）: 命令の処理の初めに、実行中の区画のレジスタの窓（窓の先頭から窓の大きさの分のスライス）と実行中の原型を局所から得て、レジスタの読み書きはその窓への添字で行う。`state.frame()` で区画と枠を引き直す関数（今の `absolute`・`reg_ref`・`reg_mut`）を、命令の処理の中で使わない。原型・定数・生存の情報は、命令ごとに `program.proto` で引き直さず、補助の型に持つ。実行中の枠の関数の値を読む命令（`GETCAP`・`CLOSURE`・`GETDICT` など）は、窓と同じ区画の `calls.last()` を、窓と分けた借用で読んでよい（区画を表から引き直すことには当たらない）。補助の型が区間の中だけで生きる局所の型（振り分けのループの関数の中で作り、区間を閉じる前に捨てる型）なら、`Value<'e>` を持ってもよい（AGENTS.md「回収しない区間と値の扱い」の「区間より長く生きる場所」に当たらない）。範囲の確かめは残す（添字は `get` で読み、外れたら `Stop::Internal`）。
2. **引数と被演算子を集めない**（背景の 4）: `CALL`・`TAILCALL`・`METHOD`・`TAILMETHOD`・`PRIM`・`IO` などで、引数のレジスタの番号の `Vec`（今の `reg_range`）と引数の値の `Vec`（今の `read_many`）を作らない。普通の呼び出しでは、引数を呼び出し元の窓から呼ばれた側の窓へ直接写す。最後の使用の被演算子は、写した後に元のレジスタを `take` する（今の規則のとおり）。末尾呼び出しでは、写し元（`B + 1 + i`）が写し先（`i`）より後ろにあることを確かめてから、先頭から順に写す。算術と比較の命令も、被演算子を `Vec` に集めずに読む。組み込みの関数は引数を `&[Value<'e>]` で受け取る（10-11）ので、`PRIM`・`IO` では、引数の数の上限の大きさのスタック上の配列（`Value` は `Copy` なので `[Value::Unit; N]` で作れる）に読み出して渡すなど、確保をしない形にする。上限を表す定数はないので、`dispatch.rs` に非公開の定数を置き、組み込みの関数の表のすべての `BuiltinRef::arity` がそれ以下であることをテストで確かめる。上限を超える引数の数が来たら `Vec` に落としてよい。`CON` などの構築の命令も同じとする。確保なしに書けない箇所が残ったら、その箇所と理由を報告する（`PRIM`・`IO`・構築の命令は ADR 0313 の決定 3 の普通の呼び出しではないので、残っても関門には反しない）。
3. **跳ぶ命令と回収の要求の知らせ**（背景の 2・3）: `JMP`・`JMPF` などの跳ぶ命令は、局所の `pc` だけを変える（`Control::Reload` を返さない）。`NoGcCtx::take_collect_signal` は、確保をする命令と組み込みの関数の呼び出しの後にだけ調べる（10-09「呼び出しの前の安全点」の表の「回収の要求の知らせ」の行）。どの命令が確保をするかを、完了の報告に一覧で書く。
4. **呼び出しと戻りの後の局所の状態**: `CALL`・`TAILCALL`・`RETURN` の後は、積んだ枠か戻り先の枠から局所の状態と補助の型を直接設定し、ループの外側で読み直す経路（`Control::Reload` からの `LoopLocals::load`）を通らない。回収・止める手順・`main` の戻りへ進む場合は、今の経路を使う。呼び出しの前の安全点の手順（10-09「呼び出しの前の安全点」。上限の確かめ、中断の印、`Budget::tick`、遅い経路、印 `precall_done`）と、予算と要求の知らせ（ADR 0263 の決定 3・4）は変えない。
5. **命令の種類と `LOADK`**（背景の 6）: `Opcode::from_u8` と `Instr::opcode` がインライン化されるようにする（`#[inline]`）。番号から種類への表を作る形は、インライン化した形と測り比べてから採る。`LOADK` は、定数の記述が即値（整数・浮動小数点数・真偽値など、対象を作らない定数）なら定数の値の表を引かずに値を作る。対象を作る定数は今の経路（定数の値の表と、その根）のまま変えない。
6. **算術と比較の判定**（背景の 9）: 型ごとの算術と比較の命令を、命令の種類で一度だけ分ける。種類を判定した後の関数の中で、命令の種類を条件の連鎖で判定し直さない。溢れと 0 での除算の扱い（`Stop` か `Err` の値で返す）は変えない。
7. **戻りでレジスタを縮めない形**（背景の 7）: `RETURN` が `regs` を縮め、次の `CALL` が伸ばして初期化し直す今の形と、縮めずに記憶域を残す形を測り比べる。残す形は、ADR 0313 の決定 3 の不変条件（使用中の終端より後ろのレジスタはつねに `Unit`、新しい窓の先頭と上限の計数と片付ける範囲と `Segment::reg_count` は使用中の終端に従う）を守る。戻りで片付けるのは降ろした窓だけとし、記憶域の末尾まで片付けない。効果がなければ今の形のまま残し、その測定の値を報告する。今の `regs.len()` を窓の先頭や使用中の終端として使う箇所、`truncate`・`resize_with`・`skip(base)` で記憶域の末尾まで片付けるか縮める箇所をすべて直す。少なくとも、`dispatch.rs` の `CALL`・`TAILCALL` の処理、`pop_call`、`absolute`・`reg_ref`・`reg_mut`・`serve`、`dispatch/traits.rs` の `METHOD`・`TAILMETHOD` の処理がある（末尾呼び出しの `resize_with(end)` は、新しい窓のほうが小さいと `Vec` を切り詰める）。
8. **`runtime::heap` の小さな関数**（背景の 8）: 上の「作るもの」の `#[inline]` を付ける。`Slot` から `Value` への変換で同じ `Slot` の種類を何度も判定していないかも確かめ、公開の層の本体の中で直せるなら直す（ヒープの番号の確かめ（ADR 0281）は省かない）。
9. **即値の安い経路**（ADR 0313 の決定 2）: 生存の情報が `LastUse` を示すレジスタに即値が入っているときは、`take` の代わりに読むだけにする。`Dead` を示すレジスタに即値が入っているときは、`clear` を省く。即値かどうかは `Slot` の種類で判定する（判定のほうが書き込みより重くならないかを測る）。宛先のレジスタへの書き込みは省かない。ヒープの対象を指すレジスタは、今の規則のとおり `take`・`clear` する。死んだレジスタが `Unit` であることを前提にしたテストや検査（`heap-verify` の検査、R11 のテスト）があれば、前提を崩さずに直せるかを確かめ、直せなければ本手順を採らずに報告する。
10. **残りの費用の内訳**: 手順 1〜9 の後に、fib と loop の CPU プロファイルを取れるなら取る（スキル `benchmark` の「CPU プロファイル」。作業の環境で samply が動かなければ、試作と同じく一部の処理を外した測定のための版を作業ツリーの外で作り、差で見積もる）。命令ごとの残りの費用（生存の情報の処理、`Slot` の変換、範囲の確かめ、予算の確かめなど）の割合を、完了の報告に書く。R16 を起動するかの判断の材料になる。

`[profile.release]` の設定（`codegen-units`、`lto`）は変えない。効果を見たい場合は、短い測定で比べた値を報告に書くだけにする。

## 受け入れテスト

- 振る舞い: 既存のテスト（`src/vm/tests.rs`・`src/vm/verification_tests.rs`・R11 のヒープの確かめ・ゴールデンテスト・参照インタプリタとの差分）が、変えずにすべて通る。期待する出力を変えたテストがあれば、その理由を報告する（原則として変えない）。予算の値を厳密に比べるテスト（`src/vm/tests.rs`）が、回収の要求の知らせを調べる位置の変更で変わる場合は、10-09 の定めに合う値へ直してよく、直した箇所と理由を報告する。
- 回収の強制: `scripts/check.sh` の `gc-stress` の構成で、すべてのテストが通る。末尾呼び出しで写し元と写し先が重なる場合、引数の多い呼び出し、呼び出しの結果を引数に使う入れ子の呼び出しを、回収の強制の下で確かめる既存のテストがなければ、`bytecode::asm` で組み立てたプログラムのテストを加える（スキル `test-audit` の作成時の関門を通す）。
- 上限: 末尾でない深い再帰が上限で `CallStackTooDeep` になり、長い末尾再帰（100 万回）が小さな上限で止まらない（既存のテストで足りれば加えない）。手順 7 で縮めない形を採った場合は、深い再帰から戻った後に、もう一度深く呼んでも上限の計数が正しいことと、`Segment::reg_count` が使用中の終端に従うことを確かめる。
- 動的確保がないこと: 普通の呼び出しと戻りで Rust の動的確保が起きないことを、呼び出しの回数の違う二つの実行で確保の回数を数えて確かめる。たとえば fib(18) と fib(22)（呼び出しの回数がおよそ 7 倍違う）を同じ方法で実行し、確保の回数の差が、呼び出しの回数に比例しない小さな定数（容量を伸ばす分）に収まることを確かめる。確保を数えるには、数える確保器（`#[global_allocator]`）を `tests/call_allocations.rs` に置き、そのテストのバイナリだけに入れる。確保器は `unsafe impl GlobalAlloc` で `std::alloc::System` へ委ねて数えるだけとし、このファイルに限って `#![allow(unsafe_code)]` を書き、`unsafe` のブロックごとに `// SAFETY:` のコメントを書く（00-02「`#[allow]` を書いてよい箇所」に、このファイルの行がある）。新しい依存のクレートは加えない。gc-stress の構成では回収の要求がつねに立ち、戻りのたびに回収（確保を伴う）へ進むので、このファイルは `#![cfg(not(feature = "gc-stress"))]` とする（回収そのものは普通の呼び出しと戻りの外である）。処理系の本体のコードに確保器も計数も置かない（AGENTS.md「大域の状態」の対象は処理系の段であり、このテストのバイナリの確保器はそれに当たらない。設計者が承認した。ADR 0313 の背景）。プログラムの実行には、パイプラインの公開の関数（10-13）を使う。
- 局所の状態: 命令の処理の中で `state.frame()` などで区画と枠を引き直していないことは、テストではなく確認の観点で読む（後述の「確認の観点」）。

### 性能の確かめ方

R12・R13 と同じく、実装担当とオーケストレータで分担する。

- 実装担当: release のビルドで、短い入力（fib(30) と loop の 300 万回程度）を、作業を始めたときの `san_benito` の HEAD と本作業の版で交互に数回走らせ、最小の時間を比べる。HEAD は作業ツリーの外（たとえば `/tmp` の下）に `git worktree add --detach` で置き、`--target-dir` を分けて両方の `examples/stage1_bench` を release でビルドし、`stage1_bench` を直接走らせて出力の実行の段の時間を比べる（`tools/bench/stage1.py --smoke` は時間を測らず、`--output` を省くと `tools/bench/results/` に書くので使わない）。比較のために置いた worktree は、終えたら `git worktree remove` で消す。手順ごとの効果と、全体の比を完了の報告に書く。値は計算機の状態に左右される参考値であり、本測定ではない。最小実行版の VM は測らなくてよい。
- 実装担当: 命令あたりの処理の構造を報告する。`MOVE`・`LOADK`・`ADDI`・`LTI`・`JMP`・`JMPF`・`CALL`・`TAILCALL`・`RETURN` のそれぞれについて、区画と枠を表から引く回数、原型を引く回数、Rust の動的確保の有無、`take_collect_signal` を調べるか、を表にする。
- オーケストレータ: 取り込みの前に、ほかの作業を止めて、スキル `benchmark` に従い本測定を行う。最小実行版の VM（`d4668a9^`）を同じ機会に測り直し（第 1 段の振り分けの記録の「振り分けのループの変化」のコマンド）、fib(35) と loop の実行の段の時間の中央値を比べる。記録を `tools/bench/results/<日付>-r15-<コミット>.md` に残す。ADR 0313 の決定 5 の関門の判定と、取り込みごとの関門の基準の記録は、オーケストレータが行う。

### 目標に届かなかった場合

手順 1〜10 を終えても、実装担当の短い測定で最小実行版の VM の時間（第 1 段の測定の値 fib(35) 2.06 s・loop 1.0 s から、入力の大きさで換算した値）に届きそうにないときは、生存の情報の処理を変えるなど本作業の範囲の外の手に進まず、届かなかった値と残りの費用の内訳（手順 10）を報告して止まる。範囲の中の変更が正しく、速くなっていれば、作業は完了として取り込む。オーケストレータは本測定の値と内訳を設計者に示し、R16 を起動するかを決める（ADR 0313 の決定 4・5）。

- 完了の報告に、手順ごとの効果の表、命令あたりの処理の構造の表、残りの費用の内訳、変えた凍結したファイルの箇所（`#[inline]` の属性と、採った場合の `Segment::reg_count`）を書いている

## 確認の観点

[実装の確認の観点](../00-common/00-04-review-checklist.md)の「すべての作業で読む観点」に加えて、次の点を読む。

- 命令の処理の中で、区画・枠・原型を表から引き直していないか。引き直すのが ADR 0313 の決定 2 の境目に限られているか。
- 呼び出しと戻りの後に局所の状態を直接設定する箇所が、`LoopLocals::load` と同じ状態（原型、命令の並び、`pc`、窓の先頭、窓の大きさ）を作っているか。回収・止める手順・タスクの切り替えへ進む前に、局所の状態を書き戻しているか（10-09「振り分けのループの局所の状態」）。
- 呼び出しの前の安全点の手順と、予算・中断の印・回収の要求の知らせの順序を変えていないか。予算を一つの呼び出しにつき一度だけ数えているか。
- 末尾呼び出しの引数の写し方が、まだ読んでいない引数を壊さないか。最後の使用の被演算子を、写した後に一度だけ `take` しているか。
- 即値の安い経路で、ヒープの対象を指すレジスタの `take`・`clear` を省いていないか。宛先の書き込みを省いていないか。
- 縮めない形を採った場合、使用中の終端より後ろのレジスタがつねに `Unit` か。新しい窓の先頭・上限の計数・`Segment::reg_count` が使用中の終端に従うか。回収（`Segment::trace`）が記憶域の末尾まで辿っても正しいか。
- 範囲の確かめを省いていないか。`unsafe` と `unwrap` を加えていないか。

## 難易度の理由

変更は VM の内部に閉じ、型とシグネチャを変えない。しかし、振り分けのループのほぼ全体を書き換えるので、呼び出しの前の安全点、予算と要求の知らせ、生存の情報、回収の根の規則を一つでも崩すと、回収の強制の下でだけ現れる誤りになる。性能の効果を手順ごとに測りながら進める必要もある。
