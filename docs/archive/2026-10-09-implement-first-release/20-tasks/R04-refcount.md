# R04 改良した参照カウント

- 依存する作業: [R02](R02-no-gc-region.md)、[R06](R06-values-and-lists.md)
- 難易度: 5（1〜5。README の「作業一覧」）
- 規模の見込み: 大（1500 行超）
- ブランチ: impl/R04-refcount

## 目的

機能 `gc-refcount` の構成のメモリの管理を作る。改良した参照カウントであり、数は区間の外で値を保つ場所（`Slot`）の参照だけで数え、区間の中で数が 0 になった対象は安全点の回収でまとめて解放する（[ADR 0277](../../2026-10-09-design-first-release/decisions/0277-refcount-defers-freeing-to-safepoints.md)）。最後の使用での移動（数を変えない `move_slot`）と、どの `Slot` からも指されない対象のその場での再利用（`reuse_ctor`）の口を作り、`Reference` のセルが作る循環を [ADR 0239](../../2026-10-09-design-first-release/decisions/0239-cycle-collection-for-reference-cells.md) の方式で回収する。

第 1 段では、言語の `Reference` の操作は VM に組み込まない（第 2 段の R23）。循環の回収は、本番の回収の API（`NoGcCtx::alloc_cell`・`cell_set`・`Heap::collect`）を通して循環を作り回収できる、ヒープの単位の範囲で入れる（[ADR 0268](../../2026-10-09-design-first-release/decisions/0268-staged-runtime-rebuild.md) の決定 2 の最後の箇条）。

本作業は R03（マーク・スイープ）と並行して、R02 が作った方式の境目の向こうに中身を書く。値の並びの対象は R06 の `ValueCtx::alloc_fields` で作れるので、テストは公開の層だけで書ける（R06 を待つのはそのためである）。本作業は生存の情報（R05）を使わない。二つの方式は、同じ根と同じ生存の情報から、同じ生きている値の集合を持たなければならない（[ADR 0259](../../2026-10-09-design-first-release/decisions/0259-compare-mark-sweep-and-rc-in-stage-1.md) の決定 2）。

## 手順の要点

### 数え方

- 数は、対象を指す参照の数（根と `Host` の対象の中の `Slot`、値の並びとセルの中の値）である（不変条件 H6）。区間の中の `Value<'e>` の写しは数えない。R02 の方式の境目の「指し始めた」で一つ増やし、「指さなくなった」で一つ減らす。`move_slot` は数を変えない。増減の回数を `rc_increments`・`rc_decrements` に、`move_slot` で省いた増減の組の数を `rc_elided` に数える。
- 数が 0 の対象は、区間の中では解放しない（H1、ADR 0277 の決定 2）。解放の候補の並びに加え、安全点の `Heap::collect` で解放する。候補の並びは、10-08「区間と回収」の四つの規則に従う。要点は次のとおりである。
  - 確保した対象は数 0 で始まるので、R02 の境目の「対象を確保した」で候補に加える。一度も `Slot` に書かれない一時の値も、これで次の回収で解放される。
  - 候補の登録は対象ごとに一つにする。対象の頭に「候補に並んでいる」印を置き、印のある対象は並びに加えない。同じ区間で数が 0 → 1 → 0 と変わっても、項目は一つのままである。単純なポインタの並びに重複して積むと、最初の項目で解放した後、二つ目の項目が解放した頭を読む。
  - 対象を解放するのは、その対象の項目を並びから取り出したときだけである。取り出したら印を下ろし、解放の直前に数を確かめる。数が 1 以上なら解放しない（次に 0 になったときに、改めて並ぶ）。
  - `reuse_ctor` は候補から外さない（下の「その場での再利用」）。
- 解放は明示の積み重ねで辿る。解放する対象の中の値の先の数を減らし、0 になった対象を、印がなければ候補の並びに加えて続ける（00-02「再帰の深さ」）。`Host` の対象は、その Rust の値の `Trace` で中の `Slot` を辿って数を減らしてから、Rust の値を捨てる（10-08「根と対象を辿る」）。
- 解放は R01 の解放の関数で行い、`frees` はその関数だけが数える（R01「確保と解放」）。本作業は `frees` を足さない。
- 数の語の溢れは、処理系の不具合として扱う（`checked_add` で確かめ、溢れたら不具合を記録する）。

### 回収の要求

- 参照カウントでも、解放は安全点に寄る。回収の要求は、次のどれか一つで立てる（10-08「設定と測定の記録」）。
  - 解放の候補の並びの対象の量が、決めた量を超えた。量の決め方は本作業が決め、完了の報告と R12 の測定の記録に書く。初めの値は、マーク・スイープの `trigger_min_bytes` と同じ 4 MiB を目安にしてよい。
  - 前回の循環の回収の後に作ったセルの数が、下の「循環の回収」の閾値に達した。
  - 生きているセルがあり、前回の循環の回収の後の確保の量が、マーク・スイープと同じ式 `max(trigger_min_bytes, k × L)` に達した（L は前回の循環の回収の後に生きていた量）。セルを新しく作らないプログラムでも、既にあるセルで作った循環を回収する機会を作るためである。

  後の二つは、候補の並びの量によらず、それだけで要求を立てる。循環した対象は、根を失っても数が 0 にならないので、候補の並びに現れないからである。
- `take_collect_signal` と `collect_requested` の意味は、マーク・スイープ（R03）と同じにする。`HeapConfig::stress` が真なら `collect_requested` は常に真を返す。
- `Heap::collect` は、10-08「区間と回収」の順（候補の解放 → 循環の回収 → 循環を切って新たに 0 になった対象の解放 → 統計と回収の後の検査 → 要求を下ろす）で行う。統計と検査を、解放の連鎖の途中で行わない。
- 回収ごとの停止の時間（遅らせた解放と循環の回収を合わせた時間）を `pause_nanos` に加え、`collections` を更新する。`live_bytes` は、回収の後に生きている対象の量とする。

### その場での再利用

- `reuse_ctor(candidate, tag, args)` は、10-08「その場での再利用」の手順 1〜4 のとおりに書く。候補の種類と長さの確かめ（手順 1）は、どの方式・設定でも行う。数が 0 であることと、引数が候補の対象を指さないこと（手順 2・3）は、何かを書き換える前に確かめる。途中で `Stop::Internal` を返すときに、対象を一部だけ書き換えた状態を残さないためである。
- 候補の対象が解放の候補の並びにあっても、並びから外さない。再利用した対象は、呼び出し側が `Slot` に書くので数が 1 以上になり、解放の直前の確かめで残る。呼び出し側が書かなかったとき（途中で止まったときなど）は、数 0 のまま解放される。外すと、書かれなかった対象がどの並びにもなく漏れる。
- `HeapConfig::reuse` が偽なら、数によらず `Ok(None)` を返す（ADR 0280 の決定 4）。
- 引数を書くときは、前の値の数を一つ減らし（0 になれば候補に加える）、新しい値の数を一つ増やす。
- `reuses` は、`reuse_ctor` が `Some` を返した回数で数える（10-08 の `HeapStats::reuses`）。

VM でこの口を使うのは 10-07 の `CONR` だけである（ADR 0280、10-07「その場での再利用の命令」）。本作業はヒープの単位で口を確かめる。`CONR` で再利用が実際に起きることは R11 が確かめる。

### 循環の回収（ADR 0239 の読み替え）

ADR 0239 は最小実行版の `Rc` と `Weak` で手順を書いている。本作業のヒープでは、次のように読み替える。

| ADR 0239 | 本作業 |
|---|---|
| 生きているセルの弱い参照の表 | 生きているセルの対象の表（数に数えない）。`alloc_cell` の方式の境目で加え、セルを解放するときに除く |
| `Rc::strong_count` | 対象の頭の数 |
| `Rc::as_ptr` の番地を鍵にする | `ObjId`（番地） |
| 中身を `Unit` に置き換える | セルの中身の `Slot` を「指さなくなった」として空にする（書き込みの障壁の位置を通さない内部の操作でよい。言語から観測できる書き込みではないので、版の番号は変えない） |

手順は ADR 0239 の決定 4 の 1〜5 のとおりとし、候補を辿る処理と、中身を置き換えた後の解放は明示の積み重ねで行う。回収は `Heap::collect` の中（安全点）で、遅らせた解放の後に行う。

- 回収を行う条件: 次のどちらかを満たしたときの `Heap::collect`。
  - 前回の循環の回収の後に作ったセルの数が、max(1,000, 前回の循環の回収の後に生きていたセルの数) 以上になった。ADR 0239 の決定 3 が実装プランで定めるとした閾値であり、R12 の測定で見直す。
  - 生きているセルがあり、前回の循環の回収の後の確保の量が、上の「回収の要求」の式に達した。

  どちらの条件も、達した時点で回収の要求を立てる（上の「回収の要求」）。`HeapConfig::stress` が真なら（機能 `gc-stress` のビルドを含む）、回収ごとに行う（00-01「機能（feature）」の `gc-stress` の行）。
- 回収の費用（時間の合計と一回の最大）は `pause_nanos` に含まれる。R12 がヒープの単位の測定で循環の回収だけを取り出せるように、循環の回収の回数と時間を内部の記録に持ち、`HeapStats` に入れない項目は `Heap::stats` の外のテスト用の口で読めるようにしてよい（公開の型は変えない）。

### マーク・スイープの構成での扱い

`reuse_ctor` は公開の層の関数なので、マーク・スイープの構成でもコンパイルされる。候補の確かめ（手順 1）の後、常に `Ok(None)` を返す。

## 受け入れテスト

テストは公開の層を通して書く。値の並びの対象は R06 の `ValueCtx::alloc_fields` で作る。参照カウントに固有のテストは `#[cfg(feature = "gc-refcount")]` で限り、限る理由をコメントに書く（00-02「テストの規約」）。両方の方式で意味を持つテスト（到達と解放）は、機能で限らない。解放の数は「増えた」でなく、`HeapStats::frees` の前後の差がちょうど期待する数であることで確かめる。

- 数の増減: `new_slot`・`store`・`clear`・`take`・`discard`・`reuse_ctor` の後の数が、指す参照の数と一致する（テストのモジュールの中の、数を読む内部の補助で確かめる）。`move_slot` の前後で数が変わらず、`rc_elided` が増える。
- 遅らせた解放: 区間の中で数が 0 になった対象は、区間の終わりまで読め（`ValueCtx::str` などで中身を読める）、`collect` の後に解放される。
- 解放の候補の状態遷移（10-08「区間と回収」の四つの規則）:
  - 一時の値: 区間の中で確保し、一度も `Slot` に書かなかった対象が、次の `collect` で解放される（`frees` の差が確保した数と等しい）。
  - 再保存: 数が 0 になった後に同じ区間で再び `Slot` に書いた対象は、`collect` の後も残る。
  - 再破棄: 同じ区間で数を 0 → 1 → 0 と変えた対象が、`collect` で一度だけ解放される（`frees` の差が 1。Miri と `heap-verify` の構成で、解放した頭を読まない）。
  - 失敗した再利用: `reuse_ctor` が `Some` を返したが結果をどの `Slot` にも書かなかった対象は、`collect` で解放される。`reuse_ctor` が手順 3 で `Stop::Internal` を返したとき、対象の中身は書き換わっていない。
- 連鎖の解放: 長さ 100 万の連結した値の並びの先頭を指す最後の `Slot` を空にして `collect` すると、すべて解放され（`frees` の差が 100 万）、スタックを使い果たさない。深さ 100 万の入れ子も同じ。Miri では `cfg!(miri)` で長さと深さを 1,000 程度に縮め、大きな規模の確かめは通常の実行に残す。
- 共有: 二つの `Slot` が共有する部分構造は、一方を空にしても残り、両方を空にすると解放される。
- 再利用: 最後の `Slot` から `take` した対象に `reuse_ctor` が `Some` を返し、同じ `object_id` のまま、読める `tag` と値の並びが書き換えた値になる。ほかの `Slot` が指している対象では `None` を返し、対象は変わらない。別の二つの `Slot` が同じ対象を指し、一方を `take` して候補にし、もう一方を `load` した値を引数に渡すと、`None` を返す（引数の参照がまだ数えられているため）。`FieldsKind::Ctor` でない対象、長さの違う対象は、どの方式・設定でも `Stop::Internal`。`HeapConfig { reuse: false, .. }` の設定とマーク・スイープの構成では、数が 0 の対象にも `None` を返す。解放の候補の並びにある対象を再利用して `Slot` に書いた後、`collect` を呼んでもその対象が解放されない。
- 循環の回収: セルの中身が自分自身を指す循環、二つのセルが互いを指す循環、セルと値の並びが交互に並ぶ長い循環（長さ 10 万。Miri では縮める）が、根から辿れなくなった後の `collect` で解放される（`HeapConfig::stress` を真にした設定か、閾値に達した後の `collect` で）。循環の一部が根から辿れるあいだは、どの対象も解放されない。セルを通らない値の並びだけの循環は、ADR 0239 の前提（循環は必ずセルを通る）の外にあり、言語からは作れない。テストでは作らない。
- 閾値と要求: 既定の設定で、セルを閾値の数だけ作るまで循環の回収が行われず、閾値に達したときに `collect_requested` が真になり、その後の `collect` で行われる（内部の記録の回数で確かめる）。セルを作らずに確保だけを続けたとき、生きているセルがあれば確保の量の閾値で要求が立ち、既にあるセルで作った循環が回収される。
- 回収の後の統計: 循環を切って新たに数が 0 になった対象の解放を終えた後に `live_bytes` と `frees` が更新され、`heap-verify` の構成の回収の後の検査が不具合を記録しない。
- 二つの方式の一致: 同じ操作の列（確保、`Slot` への書き込み、空にすること、セルの書き換え）を両方の方式で、`HeapConfig::stress` を真にした設定で行い、`collect` の後の `Heap::object_ids` の集合が、テストが操作と同時に持つ独立のグラフの模型（本番の `Trace` と内部の層の辿りを使わない）から計算した、根から辿れる対象の `ObjId` の集合と一致する（数でなく集合で比べる）。本格的な無作為の比較は R11 が書く。ここでは代表的な列で確かめる。

## 確認の観点

[実装の確認の観点](../00-common/00-04-review-checklist.md)の「ヒープの内部の層」「参照カウント（R04）」に加えて、次の点を読む。

- 区間の中で対象を解放する経路がないか（H1）。数が 0 になった対象を解放する箇所が、`collect` の中だけか。
- 数の増減の対が崩れる経路がないか。とくに、`store` で同じ値を書き直す場合、`move_slot` で `dst` と `src` が同じ対象を指す場合、`reuse_ctor` で前と同じ値を書き直す場合。
- 解放の候補の並びが、10-08「区間と回収」の四つの規則（確保の時点の登録、重複の防止、解放の直前の確かめ、`reuse_ctor` で外さないこと）を守っているか。同じ対象を二度解放する経路、候補からも根からも外れて漏れる経路がないか。
- `reuse_ctor` が、何かを書き換える前にすべての条件を確かめているか。
- 循環の回収で、候補の外から参照される対象を誤って解放しないか。内部の参照を差し引いた数の計算に、根の `Slot` を含めていないか。

## 難易度の理由

数の増減、解放の候補の並び、再利用、循環の回収の四つが同じ数の語と印を読み書きし、どれかの誤りは解放後の使用か漏れになる。漏れは未定義動作にならないのでテストで見落としやすく、解放後の使用は区間を越えてから初めて現れる。ADR 0239 の手順を `Rc` から自前の頭に読み替える部分にも注意が要る。
