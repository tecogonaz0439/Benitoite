# C05 テストと CLI の切り替え

- 依存する作業: C03, [C10](C10-golden-runner.md), F14, F16, F18, R03, R04, R08
- 難易度: 3（1〜5。[README](../README.md) の「作業一覧」の目安）
- 規模の見込み: 大（書く Rust のコードは少ないが、197 件の期待値の差を読み分ける）
- ブランチ: impl/C05-test-switchover

## 目的

最小実行版のテストと CLI を、初回リリース版の実装に切り替える（[作業の進め方](../00-common/00-03-workflow.md)の「構文の改めとテストの移行」、[リポジトリとクレートの配置](../00-common/00-01-repository-layout.md)の「移行の間の配置」の C05 の行）。

- C03 が新しい構文で書き直したテスト（`testdata-next/`）を `testdata/` に移し、C10 の実行器で、二つのメモリの管理と回収の強制の下で走らせ、参照インタプリタとの差分も確かめる。期待する出力が書き直しの前と変わった箇所を、後述の「受け入れる期待値の変化」に照らして読み分ける。
- 古い構文のテストと、それを走らせる `legacy` の実行器（`tests/golden.rs`）と、C03 の読めることを確かめるテスト（`tests/next_syntax.rs`）を消す。
- `src/main.rs` を初回リリース版の CLI（`benitoite::cli::main`）を呼ぶ形に改め、CLI のプロセスのテスト（`tests/cli_process.rs`）とベンチマークのプログラム（`tools/bench/programs/` の `.bnt`）を新しい構文に移す。

この作業が取り込まれた時点で、書き直した最小実行版のすべてのテストが初回リリース版のパイプラインで通る。これは U2 第 1 段の完了の条件のうちテストの条件である（[ADR 0268](../../2026-10-09-design-first-release/decisions/0268-staged-runtime-rebuild.md) の決定 3、[ADR 0278](../../2026-10-09-design-first-release/decisions/0278-stage-1-completes-on-new-syntax-tests.md)、[README](../README.md) の「決めたこと」の 5）。第 1 段の測定（R12）は、この作業の後の `benitoite` のコマンドで行う。

## 手順の要点

### テストの移し方

1. `git rm` で `testdata/` の古いテストを消し、`git mv` で `testdata-next/` の区分のディレクトリを `testdata/` に移す。移した後の `testdata/acceptance/INDEX.md` が、移したテストの名前と一致することを確かめる。`testdata-next/` には、C03 が書き直したテストのほかに、U1 の作業（F02〜F15）が置いた誤りのないゴールデンテスト（`types/`・`traits/`・`effects/`・`handlers/`・`patterns/`・`modules/`・`names/`・`eval/` などの区分と、`syntax/` の `fNN_` で始まるもの）がある。これらも同じく移し、同じ実行器で走らせる。
2. `tests/golden.rs`（最小実行版の実行器）を消し、`tests/golden_next.rs` を `tests/golden.rs` に改める。二つの定数を上の表のとおりに改める。`tests/next_syntax.rs` を消す。
3. `scripts/check.sh` を実行し、失敗したテストの一覧を得る。`BENITOITE_GOLDEN_FILTER` で一件ずつ調べてよい。
4. 失敗ごとに、実際の結果と期待値の差を、`REWRITE.md` の見込みと、次節の「受け入れる期待値の変化」に照らして読む。
   - 受け入れる変化だけからなる差なら、`BENITOITE_BLESS=1` で期待値を書き直し、書き直した差分を読んで確かめる。
   - それ以外の差があれば、書き直さない。処理系の不具合か本プランの誤りとして、テストの名前・差・原因の見込み（どの作業の範囲か）を報告して止まる。直した後に、この作業を続ける。
   - 段が 2 の命令に出会って `Stop::Internal` で止まったテストは、コード生成か本プランの誤りとして報告する（00-03「構文の改めとテストの移行」の最後の段落）。
   - U1 の作業が置いたゴールデンテストは、初回リリース版の実行器で初めて走る。書き直しの前の期待値がないので、上の「受け入れる変化」の読み分けは当てはまらない。期待値との差があれば、書き直さずに、テストを置いた作業（名前の `fNN_` または区分から分かる）の不具合として報告する。これらの多くは `check` の方式であり VM で実行しない。`run` の方式のもの（F15 の `eval/`）は段が 1 の命令だけに移るものに限ってある（F15「受け入れテスト」）。
5. `REWRITE.md` の「書き直せなかったもの」のテストは、移さずに完了の報告に挙げる（C03 の後に書けるようになっていれば、C03 の規則で書き直して加えてよい）。移した後に `testdata-next/` を消す。

### 受け入れる期待値の変化

00-03 は、期待する出力が変わってよいのを「診断の位置と文言のように構文の改めから説明できるもの」に限る。この作業では、その範囲を次の表のとおりに読む。表の各行は、書き直し（C03）か初回リリース版の設計書の決定から説明できる変化である。

| 変化 | 説明 |
|---|---|
| 診断・報告の位置（行と列、span の長さ）と、文章の形式のソースの抜き出しの行 | 構文の書き直しで字句の位置とソースの行が変わった。import の宣言の行が加わった |
| 表示名 | C10 の実行器は、クレートのディレクトリからの相対パス（`testdata/<区分>/<名前>.bnt`）を処理系に与える（C10「テストの見つけ方と表示名」） |
| 診断の文言・ラベル・注記・修正案 | 10-02 が文言の型板を初回リリース版の構文と型の名前（`function`・`Integer`・`Boolean`・`bind` など）に合わせて書き直した。意味は変えていない |
| 診断コード | 10-02 の廃止したコードの表のとおりに、別のコードに移った（C03 が `REWRITE.md` の「規則を改めたテスト」に挙げたもの）。また、初回リリース版の名前解決・構文解析・型検査が細かく分けたコードに移った（`names/prelude_only_hidden` の E0303 → E0330「公開していない名前」と補助の位置 `declared`、`names/wrong_kind` の E0304 → E0331、`lexical/unknown_symbol` の `?` の E0105 → E0211（10-02 は `?` を含むほかの言語の演算子に E0211 を当て、01-01 の `try` の修正案を付ける）、`types/type_arg_count` の `value: List` の E0410 → E0426）。分けたコードの条件（10-02 のコードの表の説明）に当たることを、テストごとに確かめる |
| 警告の追加 | 初回リリース版で加えた警告が、その条件に当たる入力に加わった: W0501（使わない `IO.All` などの広すぎる宣言。`REWRITE.md` が `IO.All` を残した 7 件）、W0401・W0402（定数式の 0 による除算と溢れ。`1 div 0` や `eval/int_overflow_*` の定数式）。加わった警告が、その規則で説明できる場合に限る。終了状態は変わらない |
| JSON・文章の形式 | 02-10 と 10-02 の形式の変化: JSON の `helps` の各要素のオブジェクト化（`message` と `edits`）、`trace` を持つ報告の `taskOrigins`、打ち切りの行の `more errors` → `more diagnostics`、`--version` の Unicode の版の行（00-03「構文の改めとテストの移行」） |
| 呼び出しの履歴の段 | 02-10「実行時エラーと資源の不足の報告」の段の規則による変化: 直接呼んだ組み込みの関数は枠を作らず段にならない（段になるのは値として使った組み込みの関数だけ）。標準ライブラリの公開の関数が補助の関数へ末尾呼び出しで去った段は現れない（`List.map` → `mapFrom` など。末尾呼び出しの注記の規則）。上限（`CallStackTooDeep`）で止まったときの、活動中の呼び出しの数と省いた段の数（10-09 の計数が最小実行版と違う）。止まる種類と主な位置は変わってはならない |
| 関数・型・エフェクトの名前 | 初回リリース版の名前に改めた（`REWRITE.md` の対応表。呼び出しの履歴の段の名前を含む） |
| 報告の数 | 02-10 の規則が、一つの誤りから派生した診断を出さないことを求めるので、書き直した構文で読み直した結果、同じ誤りの派生の診断がなくなった。減った診断が派生のものであることを、テストごとに説明できる場合に限る。また、字句に使えない記号は一つずつ報告し、派生の抑制の対象にしない（02-03）ので、それに当たる報告が増えた場合（`syntax/brace_next_line` の閉じる `}` の E0212）も受け入れる |

終了状態と、スクリプトが書いた標準出力と標準エラー出力の内容（名前の改めによるものを除く）は、変わってはならない。変わっていたら、処理系の不具合として報告する。表示名と文言のほかに、行や列の値が不自然に変わった場合（位置が別の字句を指す）も報告する。

### CLI の切り替え

- `src/main.rs` の `benitoite::legacy::cli::main()` を `benitoite::cli::main()` に改める。
- `tests/cli_process.rs` の各場合のスクリプトを新しい構文と名前に書き直し、初回リリース版の CLI で通るようにする。場合の一覧（使い方の誤り、`--version`・`--help`、固定の文字列の出力、存在しないスクリプト、`BENITOITE_DEV_PANIC=check`・`run`、`--diagnostics=json` の処理系の不具合、読み手が先に終わったパイプ、正しい UTF-8 でない引数）は変えない。期待する文言が変わる場合は、上の表の範囲に限る。
- 初回リリース版で出力の転送は書き出し用のスレッドが行う（[ADR 0265](../../2026-10-09-design-first-release/decisions/0265-output-transfer-by-writer-threads.md)）。第 1 段の実行の関数での振る舞いが、パイプのテストと `BENITOITE_DEV_PANIC=run` のテストの期待（02-09「panic 境界」「プログラムの実行の流れ」）と合わないときは、テストを直さずに報告する。

### ベンチマークのプログラム

- `tools/bench/programs/` の `.bnt` を、C03 と同じ規則（最小実行版の言語の機能だけを使い、書き方と名前だけを改める）で書き直す。比較対象の言語のプログラムは変えない。
- 書き直した後、`tools/bench/run.py --verify` で、各ベンチマークの出力が Python の版と一致することを確かめる（見つからない処理系は飛ばされる）。
- `run.py` の確保の記録の正規表現（`ALLOC_STATS_RE`）を、10-13 の `text::ALLOC_STATS` の形（`alloc-stats: allocations=… allocated_bytes=… peak_heap_bytes=… collections=…`）に合わせ、記録の欄の名前を改める。
- `--bytecode-stats` は開発用の例 `examples/bytecode_stats.rs` を使い、この例は C18 まで `legacy` の構文解析器で動く。新しい構文のプログラムを読めないので、C18 までこの選択肢は使えない。`tools/bench/README.md` にそう書き、`run.py` が選択肢を受けたときに理由を示して止まるようにする。
- 差分テスト（C10 の `BENCH_DIRS`）が、書き直したベンチマークで通ることを確かめる。

## 受け入れテスト

| 場合 | 期待 |
|---|---|
| `scripts/check.sh` | すべて通る。回収の強制の行（両方式）で、移したすべてのゴールデンテストと差分テストが通る |
| 件数 | `testdata/` のテストの数が、C03 の分（197 から「書き直せなかったもの」の数を引いたもの）と、U1 の作業が置いた分と、C10 が `runner/` に加えた分の和と一致する |
| 差分テスト | 移したテストと書き直したベンチマークについて、差分テストが実行され、外した数（資源の不足、`Unsupported`、`.stdin`）が示される |
| CLI | `cargo run -- run crates/benitoite/testdata/acceptance/hello.bnt`（書き直したもの）が、初回リリース版の CLI で動く。`tests/cli_process.rs` の場合がすべて通る |
| ベンチマーク | `run.py --verify` が、本言語のすべてのベンチマークで Python の版と同じ出力を示す |
| `legacy` の残り | `tests/golden.rs` と `testdata/` が `legacy` を参照しない（`grep` で確かめる） |

## 完了条件

- `scripts/check.sh` が通る（00-02「完了条件の共通の検査」）
- 受け入れテストのすべての場合を確かめている
- 完了の報告に、期待値を書き直したテストの一覧を、「受け入れる期待値の変化」の行ごとに分けて書く。行に当てはめた理由を、少なくとも区分ごとに一件の例で示す
- 完了の報告に、U2 第 1 段の完了の条件のうちテストの条件を満たしたこと（両方式と回収の強制で通ったこと）を書く

## 確認の観点

[実装の確認の観点](../00-common/00-04-review-checklist.md)の「テストの書き直しと切り替え（C03・C05）」の行を読む。期待値の書き直しの差分は、全件を読む（197 件のうち書き直したものだけでよい）。受け入れた変化の区分を取り違えていないかを、区分ごとに数件ずつ元のテストと並べて確かめる。

## 難易度の理由

操作は移動と名前の改めが中心だが、期待値の差の一件ずつについて、受け入れる変化か不具合かを判断する必要がある。判断を誤ると、不具合を期待値に固定してしまう。
