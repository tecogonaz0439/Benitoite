## 目的

[ADR 0260](../../2026-10-09-design-first-release/decisions/0260-heap-and-unsafe-boundary.md) の決定 7 の確かめ方を、第 1 段のヒープと VM に揃えて完成させる。R01〜R04 と R09 は、それぞれの範囲のテストを書いてある。本作業は、それらの作業の範囲をまたぐ確かめ（根から独立に計算した到達可能性との比較、二つの方式と回収の強制で同じプログラムを VM に通すこと、ヒープの検証器の残りの検査、対象ごとの確保の構成での Miri）を書き、`scripts/check.sh` と `scripts/check-heap.sh` で走るようにする。第 1 段の完了の条件の「ADR 0260 の確かめ方が、`scripts/check.sh` と別のスクリプトで動く」（[ADR 0268](../../2026-10-09-design-first-release/decisions/0268-staged-runtime-rebuild.md) の決定 3）は、本作業の完了で満たされる。

型で守れない不変条件（10-08 の H4「回収のとき、この先使う `Slot` はすべて根か根から辿れる対象にある」と H5「`Trace` はすべての `Slot` を訪れる」）は、安全な関数だけで破れる。ヒープの公開の API は、VM がこれらを契約として守るかぎりにおいて安全である（10-08「安全と言える範囲」、[ADR 0281](../../2026-10-09-design-first-release/decisions/0281-heap-number-in-slot-and-contract-safety.md)）。本作業のテストが、契約の破れを見つける主な手段である。

## 作るもの

- `Heap::verify` の残りの検査（R02 が最初の形を書いた）: 参照カウントの数の食い違い（`CountMismatch`）、根から辿れる対象の解放（`ReachableFreed`）。内部の層の検証器のファイル（例: `src/runtime/heap/core/verify.rs`）に書く。
- 到達可能性を独立に計算して比べるテスト（ヒープの単位）。
- 組み立てたバイトコードのプログラムを、二つの方式と回収の強制で VM に通すテスト（VM の単位）。
- 世代・毒・対象ごとの確保の構成のテストのうち、R01〜R04 が書いていないもの。
- `scripts/check.sh` と `scripts/check-heap.sh` の、本作業のテストを走らせる行（C00 が置いた形に足す。どの検査をどちらに置くかは、00-02「完了条件の共通の検査」の規則に従い、スクリプトの冒頭のコメントに書く）。

コンパイルの失敗のテストは、R02（`Heap::epoch` の `///`）と R07（`builtin!` の `///`）が置いた。本作業は、それらが `cargo test --doc` で走り、`scripts/check.sh` の検査に含まれていることを確かめる。10-08 の例のほかに、`SlotOps` と `Discarder` を区間の外へ持ち出す例など、R02 の例でふさいでいない抜け道が見つかれば、同じ形（`compile_fail` と対の `no_run`）で `Heap::epoch` の `///` に足す。

## 手順の要点

### ヒープの検証器の残りの検査

- 根から辿れる対象の解放: 根（`Heap::verify` の `roots`）から明示の積み重ねで辿り、辿れた `Slot` と値が指す対象がすべて生きている（世代が合い、`Slot` のヒープの番号が合う）ことを確かめる。
- 数の食い違い（`gc-refcount`）: すべての生きている対象の中の `Slot` と、根の `Slot` が指す回数を数え、対象の頭の数と比べる。区間の中の写しは数えない（H6）ので、検証器は区間の外（`Heap::collect` の前後と、テストが呼ぶとき）でだけ働く。遅らせた解放の並びにある対象（数 0）は、どこからも指されていないことを確かめる。

### 到達可能性の比較（ヒープの単位）

確保・参照の書き換え・根の追加と削除を無作為に組み合わせ、独立に計算した到達可能性と比べる（ADR 0260 の決定 7、07-03 の表）。

- テストは公開の層だけで書く: `RootStack` を根とし、`alloc_fields`・`alloc_str`・`alloc_cell`・`cell_set`・`alloc_host`・`host_mut`・`reuse_ctor` で対象を作って書き換える。操作の列には、R04 の解放の候補の状態遷移（一度も `Slot` に書かない一時の値、数が 0 になった後の再保存、同じ区間での 0 → 1 → 0、結果を書かない再利用）を含める。
- 独立の計算: テストの側で、各対象（`ValueCtx::object_id`）から指す対象の表（グラフの模型）を操作と同時に持ち、根から `BTreeSet` で辿る。期待する集合の計算に、VM とヒープの `Trace`、内部の層の辿りを使わない（同じ誤りを共有すると比べる意味がない）。
- 比べるもの: `Heap::collect` の後の `Heap::object_ids` の集合が、独立に辿った集合と一致する（数でなく `ObjId` の集合で比べる。生きている一個を誤って解放し、不要な一個を残す誤りは、数では見つからない）。比べる回収は `HeapConfig::stress` を真にした設定で行う。この設定では、参照カウントも回収ごとに循環の回収を行い、循環を切って新たに数が 0 になった対象まで解放し終える（10-08「区間と回収」）ので、両方の方式でちょうど一致する。回収の後に、残った対象の中身（文字列、値の並び、セルの中身）が、テストの側で覚えた値と一致する。
- 無作為の値は、テストの中の小さな疑似乱数（xorshift など）で作り、種を固定する。`scripts/check.sh` では少ない回数、`scripts/check-heap.sh` では多い回数で走らせる（00-02 の `check-heap.sh` の表の「到達可能性の比較の長い実行」）。回数は環境変数か `#[ignore]` の別のテストで切り替え、どちらにしたかを冒頭のコメントに書く。
- 失敗したら、種と操作の番号を報告に出して再現できるようにする。

### VM に通すテスト

R05 の組み立てで作るプログラム（R09 のテストの補助を使ってよい）を、二つの方式と回収の強制で VM に通し、結果と出力が方式によらず同じになることを確かめる。プログラムには、第 1 段の測定のワークロード（[R12](R12-stage1-measurement.md)）の形を小さくしたものを含める。

- 長いリストを作って辿り、捨てる
- 構成子の二分木を作って辿る（共有の多い形を含む）
- 深い末尾でない再帰の底で値を作り、続けて戻る
- 大きさの違う文字列と値の並びを混ぜて作る
- 大きな生きている構造を保ったまま、短命な値を多く作る
- 捕捉のある関数の値を作って呼ぶ
- 構成子で作ったリストを写しながら要素を変える関数（`case` で分けた値を `CONR` で作り直す。後述の「`CONR` による再利用」）

各プログラムは、`HeapConfig::stress` を真にした設定（安全点ごとに回収）で、`heap-verify` の構成のもとで実行し、`Heap::take_fault` が不具合を返さないことを確かめる。実行の後に、`RunState` を根とした到達可能性（上の独立の計算は VM の状態を読めないので、ここでは `Heap::verify` と、方式による結果の一致で確かめる）を確かめる。

### `CONR` による再利用

参照カウントの方式で `CONR` の再利用が実際に起きることは、R04（ヒープの口）と R09（命令）の両方を要るので、本作業が確かめる（R09 は `reuse_ctor` が `None` を返す経路だけを確かめる）。構成子で作ったリストを写しながら要素を変える関数を、分けた値を `CONR` の A に置く形で組み立て、二つの方式と回収の強制の有無で VM に通す。

- 参照カウントの方式では、`HeapStats::reuses` が写した要素の数だけ増え、`CONR` の結果の対象の `object_id` が前の値と同じになる。
- 同じリストをほかの `Slot`（別のレジスタか `RootStack`）も指しているときは、再利用しない（`reuses` が増えず、前のリストが読めるまま残る）。
- 候補と引数の別名: 候補のレジスタ A と、引数のレジスタ（A と別のレジスタ）が同じ対象を指す `CONR` を組み立てる（A の `LastUse` は `sole: true` になる）。`reuse: true` と `reuse: false` の両方で、結果の値が構造の等しさで等しく、回収の後の到達できる対象が同じであり、結果の対象が自分自身を指さない。
- `HeapConfig { reuse: false, .. }` の設定とマーク・スイープの方式では、`reuses` が 0 のままである。
- どの組み合わせでも結果と出力が同じであり、`heap-verify` の構成で不具合を記録しない。

### 世代・毒・対象ごとの確保

- `heap-verify` の構成で、根に入れない `Slot` を Rust の変数に残して回収する（H4 の違反を意図して作る）。マーク・スイープでは、その `Slot` が指す対象が解放され、回収の後に `load` すると `StaleReference` が記録される。参照カウントでは、その `Slot` 自身が数に数えられているので対象は解放されず、`Heap::verify(roots)` が、根と対象から数えた参照の数と頭の数の食い違い（`CountMismatch`）を報告する。二つのテストは、根の漏れがどちらの方式でも見つかることを示す。
- `heap-per-object` の構成で、上のテストが解放した領域を読まずに世代の食い違いを見つける（Miri で走らせ、未定義動作が報告されない）。
- 毒: 解放した対象の中身の領域が `POISON_BYTE` で埋まっていることを、内部の層のテスト用の補助で確かめる（R01 のテストと重なるなら、足さない。`test-audit` の作成時の関門で判断する）。

### Miri

`scripts/check-heap.sh` の Miri の行が、`runtime::heap` の単体テストと、小さな VM のプログラムのテストを実行することを確かめ、足りなければテストの名前の絞り込みを足す。Miri で時間のかかるテストは、`cfg!(miri)` で回数を減らす。R01・R03・R04 の百万の規模のテスト（大量の確保、深い構造、連鎖の解放）が Miri で縮めた規模になっていることも確かめ、なっていなければ縮める（大きな規模の確かめは通常の実行に残す）。`mio` やスレッドを含む部分は第 1 段にないので、IO 実行器を外す必要は第 2 段で判断する（00-02 の Miri の行）。

## 受け入れテスト

- `Heap::verify` の残りの検査: 参照カウントの数を内部の層のテスト用の補助で一つずらすと `CountMismatch`、根から辿れる対象を内部の層で解放すると `ReachableFreed` を返す。正しいヒープではどちらも返さない。
- 到達可能性の比較: 両方の方式で、`check.sh` の回数（数百の操作の列を数十）と `check-heap.sh` の回数（それより十分多く）の比較が一致する。
- VM に通すテスト: 前述の七つの形のプログラムが、二つの方式 × 回収の強制の有無の四つの組み合わせで同じ結果と出力になり、`heap-verify` の構成で不具合を記録しない。
- `CONR` による再利用: 前述の「`CONR` による再利用」の五つの場合。
- 根の漏れの検出: 意図して根から外した `Slot` が、`heap-verify` の構成で、マーク・スイープでは読み出しの `StaleReference`、参照カウントでは `Heap::verify` の `CountMismatch` として見つかる。`heap-per-object` の構成でも、Miri が未定義動作を報告せずに同じ結果になる。
- コンパイルの失敗: R02 と R07 の `compile_fail` の例が `scripts/check.sh` のテストで走っている（走っていなければスクリプトを直す）。

## 確認の観点

[実装の確認の観点](../00-common/00-04-review-checklist.md)の「二つのメモリの管理の確かめ方（第 1 段の間）」に加えて、次の点を読む。

- 到達可能性の独立の計算が、ヒープの `Trace` や内部の層の辿りを使っていないか（同じ誤りを共有すると比べる意味がない）。
- 一方の方式だけで通るテストを、機能で限って黙って外していないか。
- 回収の強制のテストが、実際に安全点ごとに回収しているか（`collections` の数で確かめているか）。

## 難易度の理由

個々のテストは難しくないが、独立の計算を本体と別の考え方で書き、二つの方式と構成の組み合わせで漏れなく走らせる設計が要る。意図して不変条件を破るテストを、未定義動作にならない範囲で作る注意も要る。
