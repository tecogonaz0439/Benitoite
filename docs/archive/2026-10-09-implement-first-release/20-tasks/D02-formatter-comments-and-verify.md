## 手順の要点

1. コメント: 行末のコメントは、その行に残し、前の字句との間に空白を一つ置く。コメントだけの行は、後の最初のコードの行の段に置き、その行が閉じの字句で始まるときは役割の表の `inner_level` の段に置く。後にコードの行がなければ段 0。本文は変えない（行末の空白を除く）。`//!` の行はファイルの先頭（シェバンの行の直後）に置いたままにする。
2. 空の行: 役割の表の `blank_before` と `top` から、06-03「空の行」の規則を当てる。`blank_before` が `Remove` の行の前にコメントだけの行があるときは、行の最初の字句の種類で、除く空の行の位置を分ける。閉じの字句（`end`・`)`・`]`。`inner_level` が `Some`）・`else`・`with` で始まる行では、その行の直前（コメントだけの行の後）の空の行だけを除き、コメントだけの行の前の空の行は「ブロックの中」の規則（一つまで保つ）に従う。そのほかの字句（構文の中身の最初の行、属性の後の宣言など）で始まる行では、前のコードの行とコメントだけの行の間の空の行を除き、コメントだけの行と字句の行の間の空の行は一つまで保つ（06-03「空の行」の「コメントだけの行を含めて数える」）。凍結した `BlankBefore` が理由を持たないための近似であり、中身が空の構文の中のコメントと、構文の中身の最初の文が `with` の文である場合は外れうる。外れる場合を完了の報告に書く（型は変えない）。トップレベルの宣言の間は、import どうし・定数どうし（間のコメントだけの行を含む）を除いて、ちょうど一つにする。宣言の後の行末のコメントの行を宣言の最後の行とする。ファイルの先頭と終わりの空の行を除き、シェバンの行と `//!` の行の後は一つまでにする。
3. 行末と文字: 改行を LF にし、行末の空白とタブを除き（複数行の文字列の内容の行を除く）、ファイルを改行一つで終える。字句の間と行頭のタブは、空白と字下げの規則で決め直す（文字列・文字・コメントの中のタブは変えない）。先頭の U+FEFF は残す。シェバンの行は行末の空白も含めてそのまま残す。
4. 複数行の文字列: 開きの `"""` を含む行の字下げの変化の量 `b - a` だけ、内容の行と閉じの行を動かす（06-03「複数行の文字列」の手順）。内容の空の行は何もない行にする。
5. `verify`: 両方のソースを `lex` と `resolve_newlines` にかけ、字句の列（種類と、文字列の字句は値、NEWLINE（改行の判定の後の `LineBreak`）と `Eof` は種類だけ、ほかは字面。NEWLINE の span は元の改行（CR LF を含む）を指すので、字面で比べると CR LF のファイルが必ず食い違う）とコメントの並び（種類と、行末の空白を除いた本文）を順に比べる。一致すれば、`after` を `parse`（`kind` で）にかけて構文の誤りがないことを確かめる。食い違いは、最初のものを説明する文字列にする（字句の添字、前後の字句の種類と字面）。
6. `format_source`: 10-17「整形の流れ」の手順 1〜6。字句の誤りと構文の誤りは、字句解析の診断と構文解析の診断をこの順につないで `FormatError::Syntax` にする。
7. 標準ライブラリのソースの正規形のテスト: `STDLIB` のすべての項目を `SourceKind::Prelude` で `format_source` にかけ、`changed` が偽であることを確かめる。偽でなければ、どのモジュールのどの行が変わるかを示して失敗させる。ソースを直さずに作業を止めて報告する（10-14「置く作業と既存のファイル」、10-15 の同じ定め）。ただし、整形で変わるのが空白（字下げ・空の行・字句の間の空白）だけなら、`format_source` の結果で標準ライブラリのソースと 10-14・10-15・10-18 の写しを直してよい（字句と型は変わらない）。直してよいのは、字下げ・空の行・字句の間の空白・行末の空白・最後の改行・改行の種類だけである。直す前に、その差分が 06-03 の規則に合うことを確かめる（D01・D02 の不具合による差分なら、ソースでなく整形を直す）。直したファイルを完了の報告に書く。U3 と U4 のソース（10-15・10-18）も同じテストの対象になる。

## 受け入れテスト

段ごとの単体テストとして置く。

| 場合 | 期待 |
|---|---|
| 06-03「整形の例」 | 整形の前のソースから、整形の後のソースがバイト列として得られる |
| コメント | 行末のコメントの前の空白が一つになる。`else` の前、`end if` の前のコメントだけの行の段。ファイルの終わりのコメントだけの行が段 0 になる。`///` の行と宣言の間に空の行が入らない |
| 空の行 | 宣言の間の空の行（ない・二つ以上）が一つになる。import どうし・定数どうしの空の行が一つまで保たれる。ブロックの最初の文と `end` の前の空の行が除かれる。`case` の前の空の行が一つまで保たれる |
| 行末と文字 | CR LF が LF になる。行末の空白とタブが除かれる。最後の改行が加わる。U+FEFF が残る。シェバンの行が変わらない。字句の間のタブが空白になる。文字列の中のタブが変わらない |
| 複数行の文字列 | 開きの行が深くなる場合と浅くなる場合で、内容の行と閉じの行が同じだけ動き、値が変わらない（整形の前後の字句の値が同じ）。内容の空白だけの行が何もない行になる |
| 冪等性 | 上のすべての出力を整形すると、同じバイト列になる |
| 構文の誤り | 構文の誤りのあるソースは `FormatError::Syntax` になり、診断を持つ |
| 検証（字句） | `verify` に、字句を一つ変えた出力、字句を一つ除いた出力、改行を加えて文の区切りを変えた出力を与えると、それぞれ `Err` になる |
| 検証（コメント） | コメントを一つ落とした出力、本文を変えた出力を与えると `Err` になる |
| 検証（構文） | 字句とコメントが同じでも、ドキュメントコメントと宣言の間に空の行を入れて構文の誤りになる出力を与えると `Err` になる |
| 標準ライブラリのソース | すべての `STDLIB` の項目が正規形である |

## 完了条件

- `scripts/check.sh` が通る（00-02「完了条件の共通の検査」）
- `print`・`verify`・`format_source` に `todo!()` が残っていない
- 受け入れテストのすべての場合を確かめるテストがある

## 確認の観点

- 整形が字句を加えも除きもしない形で書かれているか（字句の字面を元のソースから写しているか）。検証に頼って誤りを見逃す作りになっていないか
- 複数行の文字列の内容の行を、ほかの行の空白の規則（行末の空白の除去、タブの置き換え）から外しているか

## 難易度の理由

規則の数は多いが、どれも 06-03 が行の単位で定めており、役割の表（D01）がそろっていれば、行を順に処理する書き方で書ける。検証は二つの列の比較である。
