## 作るもの

パスは、`testdata/` は処理系のクレートから、`tools/` はリポジトリの根からの相対パスである。

| テスト（`testdata/acceptance/`） | 方式 | 完了条件の行 |
|---|---|---|
| `json_summary` | `run` | 同梱の Agent Skill だけを与えた LLM が JSON ファイルを読んで集計するスクリプトを書く。LLM の試行は処理系のテストに含めない（07-03）ので、本作業では、同じ課題（D23 の JSON の集計の課題）の解のスクリプトを `.files/` の JSON で動かすテストを置く。完了の判定のときの試行で得たスクリプトは、U3・U4 を終えた後にこのテストに加える（[90-after-completion.md](../90-after-completion.md)） |
| `process_run`・`process_shell` | `run` | 外部コマンドを引数の配列で起動するスクリプト（`Process.run`）と、シェルで実行するスクリプト（`Process.shell`）。どちらも POSIX の環境にあるコマンド（`printf`・`sort` など）だけを使い、出力が環境によらないように書く。`sort` を使うときは、入力を小文字の ASCII だけにするか、`Process.Command` の `environment` で `LC_ALL=C` を渡す（並べ方がロケールで変わるため） |
| `test_replaces_effects` | `test` | 外部コマンドの起動（`Process.run`）、プロセスの終了（`Process.exit`）、ファイルの書き込み（`File.writeText`）を、テストのコードのハンドラで差し替えて `test` を実行し、それらの操作を外部に行わずにテストが通る。書き込みの差し替えは、テストの関数の中で、ハンドラの外の本物の `File.exists` により、書こうとしたファイルがないことを確かめる（`Result.mapError(_, IOError.message)` を挟んで `Assert.equal` で比べる）。ゴールデンテストの実行器は、実行の後に一時ディレクトリの中身を確かめないので、`.files/` で確かめることはできない |
| `fmt_comments` | `fmt` | コメント（行末のコメント、コメントだけの行、ドキュメントコメント）を含むスクリプトを整形し、コメントが保たれる。整形後も同じ検査結果になることは、D04 のフォーマッタの性質の確かめが、このテストの `check` の版（`fmt_comments_check`、`.mode` が `check`）で確かめる |

- `testdata/acceptance/INDEX.md`: 「初回リリース版の完了条件」の表のテストの名前の欄を埋める。
- `tools/spec-coverage/spec_coverage.py` と `tools/spec-coverage/README.md`: 初回リリース版の表の空の行を誤り（終了状態 1）にする（C17 の手順 4 が U3・U4 に残したこと）。

## 手順の要点

1. 各テストのスクリプトの先頭に `// spec:` の行で、確かめる仕様の節を書く（07-03「ゴールデンテスト」）。`// spec:` の行には `docs/archive/2026-10-09-design-first-release/01-spec/` の章と見出しだけを書く（既存の受け入れテストの `// spec: 01-07 エフェクトの型と権限制御の区別` の形）。03-xx・06-xx などほかの部の節は、`// spec:` でない普通のコメントで書く。仕様の網羅の道具が `// spec:` の行を 01-spec の見出しと照らし合わせるためである。
2. `process_run`・`process_shell` は、ゴールデンテストの実行器では実際にコマンドを起動する（テスト用のハンドラ表で置き換えない）。コマンドの出力が OS の違いで変わらないものを選ぶ。
3. `json_summary` の解のスクリプトは、D23 の課題 `tools/skill-eval/tasks/` の JSON の集計の課題と同じ入力と期待する出力にする。D23 がまだ取り込まれていなければ、07-03 の表の行（JSON ファイルを読んで集計する）に合う課題を本作業で決め、D23 が同じものを使うよう完了の報告に書く。
4. 受け入れテストの非公式のモジュールは取り込みの名前で import する。
5. 受け入れテストは、すべて成功するものにする。`test` の方式で失敗するテストを置くと、その JSON の期待値が F333b（ADR 0333 の決定 2 のテストの JSON の注記）で変わるためである。
6. 仕様の網羅の道具を改めた後、`python3 tools/spec-coverage/spec_coverage.py` が終了状態 0 で終わることを確かめる。

## 受け入れテスト

| 場合 | 期待 |
|---|---|
| 各テスト | ゴールデンテストの実行器で通る。`run`・`test` の方式のテストは二つの IO の方式で通る（`fmt` の方式は Direct の方式だけで実行される） |
| 索引 | 初回リリース版の表のすべての行にテストの名前がある。仕様の網羅の道具が終了状態 0 |
| 空の行の検出 | 表の行のテストの名前を一つ消すと、道具が終了状態 1 で終わる（道具の `--self-test` に場合を加える） |
| 差し替えの確かめ | `test_replaces_effects` で、差し替えたハンドラを外すと、実際にファイルが書かれる（手で確かめ、完了の報告に書く。ハンドラが操作を実際に遮っていることの確かめ） |
