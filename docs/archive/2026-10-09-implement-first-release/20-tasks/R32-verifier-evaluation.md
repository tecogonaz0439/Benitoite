# R32 検証器による範囲の確かめの省略の評価

- 依存する作業: [R14](R14-stage1-wrap-up.md)、[R18](R18-tail-window-and-slot-access.md)（R15〜R18 の後の VM で測る。ADR 0313 の決定 6）
- 難易度: 4（1〜5。README の「作業一覧」）
- 規模の見込み: 中（500〜1500 行）
- ブランチ: impl/R32-verifier-evaluation

## 目的

[OPEN-064](../../2026-10-09-design-first-release/open-issues.md#open-064) を決める材料を作る。読み込みのときにコンパイル済みプログラムを検証し、振り分けのループの実行中の範囲の確かめを `unsafe` で省くと、どれだけ速くなるかを、局所の状態を持つだけの今の VM（ADR 0263 の決定 1）と同じ命令列で比べて測る（同 決定 2）。

本作業が取り込むのは、検証器（`bytecode::verify`）とそのテスト、測定の道具と記録である。範囲の確かめを省く `unsafe` の変更は、測定のためだけのリビジョンに置き、本番の枝には取り込まない。採るかは設計者が決める。

性能の回復（R15〜R18）の後の本測定では、fib(35) は最小実行版の VM の 0.955 倍、loop は 1.069 倍だった（[R18 の記録](../../../../tools/bench/results/2026-10-06-r18-ab41855.md)）。設計者は loop の差を認めて第 2 段（R20）を起動し、本作業を R20 と並行して前倒しで進めることを承認した（2026-10-06、[ADR 0313](../../2026-10-09-design-first-release/decisions/0313-vm-performance-recovery-before-stage-2.md) の帰結）。測定では、省略の効果に加えて、loop が最小実行版の VM に届くかを示す。

採ると決まったら、別の作業で、省く確かめを表にしたうえで入れ、[実装の規約](../00-common/00-02-conventions.md)と AGENTS.md の規則（「`Stop::Internal` で返す」を「検証器が拒む」に読み替える規則、`unsafe` を許す箇所）を改める（00-02「失敗を panic で表さない」「`#[allow]` を書いてよい箇所」、00-01「`unsafe` を書いてよいモジュール」）。

## 手順の要点

### 検証器（10-07「読み込みのときの検証器」）

`verify` は、次のことを確かめ、最初に見つけた違反を `VerifyError` で返す。

- 原型の表: `CompiledProgram::main` が表の中にある。各原型の `positions` と `code` の長さが等しい。`num_params` ≤ `num_regs`（呼び出しが引数を窓の先頭へ写す前提）。
- 生存の情報（10-07「生存の情報」、[ADR 0314](../../2026-10-09-design-first-release/decisions/0314-clear-dead-registers-at-safepoints.md)。`src/bytecode/liveness.rs` の `LiveInfo`）: `starts` と `items` の形（長さと範囲、`items` のレジスタが `num_regs` の中）。`live_in_starts` の長さが命令の数＋1 で、0 から始まって単調に増え、最後が `live_in` の長さに等しい。`live_in` の各値が `num_regs` の中で、命令ごとの区間の中で昇順。`call_writes` の長さが命令の数で、値が `num_regs` の中。`compute_liveness` で計算し直して一致を比べる形で確かめてもよい。
- 呼ばれた原型の入口: すべての原型で `live_in_at(0)` が 0..`num_params` に含まれる（R18 が末尾呼び出しで新しい窓の中を消さない前提。範囲の安全性には要らないが、静的に確かめられるので確かめる）。
- 表の中の番号: 定数の記述（`ConstDesc` の `Ctor`・`List`・`Map`・`Set` の子の番号が自分の番号より小さく表の中にあること、`Ctor`・`Func`・`Dict` が指す番号）、`CLOSURE`・`LAZY` の対象の原型の `captures`（作る側の `num_regs` と捕捉の表の中）、実装の表のメソッドと上位の実装、型クラスの表の上位、操作の表の組み込みの関数、ハンドラの節の操作、`top_fns` の原型の番号が、それぞれの表の中にある。
- 命令ごと: 命令の種類の番号が `Opcode` にある。読み書きするレジスタの番号（引数の並びは先頭から数の分まで）が原型の `num_regs` の中にある。`METHOD`・`TAILMETHOD` の位置の `method_traits` が型クラスの表の中の番号を持ち、C がその型クラスのメソッドの並びの中にある。`method_traits` の長さが命令列と同じで、ほかの位置が `None` である（ADR 0310）。原型・定数・分岐表・ハンドラの記述・構成子・実装・操作・組み込みの関数の参照の番号が、それぞれの表の中にある。`GETCAP` の番号が捕捉の表の中にある。跳ぶ先（`JMP`・`JMPF` の sBx、分岐表の各跳ぶ先）が命令列の中にある。命令列の最後の命令から次の命令へ落ちない（最後が `RETURN`・`TAILCALL`・`TAILMETHOD`・`ESCAPE`・`JMP`・`SWITCH` のどれか。生存の情報の計算と同じ扱い）。命令列が空の原型の扱い（拒むか、どこからも呼ばれない原型に限って受理するか）は作業が決め、完了の報告に書く。
- `PRIM`・`IO`・`CON`・`DICT`・`PERFORM` は引数の数を持たず、表から読む（10-07 の命令の表）。表の数から決まる引数の並び（`R[C]` から数の分）が `num_regs` に収まる。組み込みの関数の参照の `arity` が、その関数の宣言（`builtin_decl`）の引数の数と一致する。`HANDLE` の節の関数の数がハンドラの記述の節の数と合う。

`VerifyError::message` は、`InternalError` の説明と同じく処理系を調べるための文字列であり、診断の表と `text` に載せない（AGENTS.md「文言」）。

実行時の値によるもの（区画の所有、確保の失敗、呼び出しの入れ子の上限、継続の使用済み、呼ぶ関数の値の原型の引数の数、窓の大きさが呼ぶ側と呼ばれる側で合うこと）は、読み込みのときには保証できない（ADR 0263 の決定 2）。これらは確かめの対象にせず、測定の記録の表に「実行中に確かめ続けるもの」として挙げる。範囲の確かめを省くことが、VM の構成が保つ不変条件（窓の大きさが実行中の原型の `num_regs` に等しいこと。`call` が枠を作るときに成り立たせる。定数の値の表の長さが `program.consts.len()` に等しいこと）にも依る場合は、表に「VM の構成が保証するもの」の行を設けて挙げる。R20 以降はハンドラ・継続・`Lazy` で枠を作る経路が増えるので、採る場合にはそれぞれの経路で再び確かめる必要があることを記録に書く。

検証器は Rust の再帰を使わない（命令列を一度走査するだけでよい）。

### 測定のリビジョン

- 本作業の枝 `impl/R32-verifier-evaluation` の本番のコミット（検証器とテストまで）に、範囲の確かめを省く変更と、確かめの失敗を数える口を加えたものを、測定のリビジョンとする。実装担当はコミットしないので、作業ディレクトリの写し（`target/r32-unchecked/` の下）で変更を作ってテストと短い測定を行い、本番の版との差分を `target/r32-unchecked.patch` に書き出す。オーケストレータが、本番のコミットから別の枝 `impl/R32-unchecked` を切って差分をコミットし、タグ（例 `r32-unchecked`）を付けて残し、記録にコミットを書く。この枝は本番に取り込まない。
- 基は R20 を含まないコミット（作業を始めたときの `san_benito`）とし、比べる二つの版が同じ基から作られていることを記録に書く。作業の途中で `san_benito` を取り込まない。
- 測定のリビジョンでも `cargo test`（ゴールデンテストを含む）を通す。読み込みのときに `verify` を呼び、受理したプログラムだけを実行する形にし、検証の時間も測って記録に書く。
- 窓のスライスを命令をまたいで持つ形（10-09「振り分けのループの局所の状態」）は、本作業では測らない。

### 検証器のテスト（ADR 0263 の決定 2 の最後の箇条）

- 変異のテスト: コード生成が作った正しいプログラム（ゴールデンテストのスクリプトをコンパイルしたもの）の命令の被演算子・種類・跳ぶ先・表の長さを一か所ずつ無作為に変え、範囲の外になる変異を検証器が必ず拒むことを確かめる。乱数はテストの中の小さな生成器で作り、依存を加えない。種は固定する。
- 受理した入力の実行: 検証器が受理した変異（範囲の中に収まった変異）と元のプログラムを、範囲を確かめる VM で実行し、省く予定の確かめ（レジスタ、定数などの範囲）が一度も失敗しないことを確かめる。今の VM は範囲の確かめの失敗も値の種類の違いも同じ `Stop::Internal` で返すので、この確かめは測定のリビジョンで行う。測定のリビジョンの VM に、省く予定の確かめの失敗を数える口を置き、受理した変異を実行して数が 0 であることを確かめ、変異の数と結果を測定の記録に書く。本番の枝の受け入れテストには含めない。
  - 実行する変異からは、跳ぶ先（`JMP`・`JMPF` の sBx と分岐表）と、組み込みの関数の参照の番号を変えるものを除く。跳ぶ先の変異は呼び出しを含まない無限ループを作りうる（VM に命令の数の上限がない）。組み込みの関数の番号の変異は IO の関数を呼びうる。これらは「拒むこと」の確かめ（変異のテスト）だけに使う。
  - 実行には、実 IO に触れないテスト用の IO（`builtins::funcs::stage1_io::TestIo`）を使う。対象のプログラムは段 1 の命令（`Opcode::in_stage1`）だけを使うものに限り、R20 の取り込みの影響を受けないようにする。
- fuzzing だけを安全性の根拠にしない（相談の第 2 回の問い 4）。本作業のテストは、検証器が保証することの表の各行に、変異のテストの場合を対応させる。

### 測定

1. 省く確かめの候補を、効果の大きい添字の読み書きから絞る。候補ごとに、検証器が保証することの表（命令と位置、レジスタ、定数・原型・捕捉、呼び出し、ハンドラと区画。相談の第 2 回の問い 4 の表の形）を作る。
2. 測定のためのリビジョンで、候補の読み書きを `get_unchecked` などの `unsafe` に替える。`unsafe` の各ブロックに、表のどの行が成り立つので範囲の中にあるかを `// SAFETY:` で書く。レジスタの `Vec` を伸ばした後に位置を読み直す規則（ADR 0263 の決定 1）を守る。範囲の外の `get_unchecked` は未定義動作であり、`Vec` の伸長は要素の位置を変えうる（相談の第 2 回の問い 4 が挙げた一次資料: Rust の `Vec` の文書の「Guarantees」と `slice::get_unchecked` の文書）。測定のリビジョンでは、lint の `unsafe_code` を振り分けのループのファイルだけで許してよい。
3. 同じ命令列（同じコンパイル済みプログラム）を、本番の版（測定のリビジョンの基のコミット）と測定のリビジョンで実行して比べる。ベンチマークは fib・loop・tree・eval（命令の振り分けの割合が大きいもの）を中心に、07-02 の集合を使う。
   - 実装担当は、`*.args.small` の入力の短い測定だけを行う（両方の版の `stage1_bench` を交互に数回走らせ、最小の時間を比べる。R15〜R18 の「性能の確かめ方」と同じ。比較の版の展開と target は作業ディレクトリの `target/` の下に置き、終えたら消す）。
   - 時間の本測定はオーケストレータが、設計者の確認を得てから行う。fib と loop は `tools/bench/gate.py` で、最小実行版の VM（`d4668a9^`）と本番の版と測定のリビジョンを同じ機会に測る。基準は R18 の値（fib 1.965 s、loop 1.060 s）である。tree と eval は、両方の版の `examples/stage1_bench.rs` を同じ手順（スキル `benchmark`、10 回の中央値）で測る。実装担当は、オーケストレータが測れるように、二つの版のビルドの手順と、測る入力を完了の報告に書く。
4. 生成された機械語（候補の読み書きの箇所）で、範囲の確かめの分岐が消えているかを確かめる（`cargo asm` などの道具を加えずに、`--emit asm` の出力で見る）。今の VM で最適化がすでに確かめを消している箇所は、省いても効果がない。
5. 記録（実装担当が短い測定までを書き、オーケストレータが本測定の結果を書き加える）に、比べた構成（コミット、ビルドの設定）、候補ごとの表、ベンチマークごとの時間の差、機械語の所見、実行中に確かめ続けるものの一覧、採る場合に要る規約の改め（00-02 と AGENTS.md の規則、lint の許可）を書く。採るかの案を示してよいが、決めるのは設計者である。

## 受け入れテスト

- `verify` の単体テスト: 確かめる候補のそれぞれについて、正しいプログラムを受理し、その一か所を範囲の外にしたプログラムを拒む。`VerifyError` が原型と命令の位置を持つ。
- 変異のテスト（上）。受理した入力の実行は測定のリビジョンで行い、結果を記録に書く（上）。
- 既存のゴールデンテストのプログラムのすべてを、検証器が受理する。

## 確認の観点

- 検証器が、10-07 の「確かめる候補」を漏れなく確かめているか。実行時の値によるものを、検証で保証したことにしていないか。
- 変異のテストが、表の各行を少なくとも一つの変異で確かめているか。
- 測定が、振り分けのループの局所の状態の改善（ADR 0263 の決定 1）の効果と混ざっていないか（両方の構成が決定 1 を含むか）。
- 本番の枝に、測定のためだけのコード（範囲の確かめの失敗を数える口など）が残っていないか。

## 難易度の理由

検証器そのものは表を引いて範囲を確かめるだけだが、どの確かめを省いてよいかを、検証器の保証と実行時の保証の対応で一つずつ示す必要がある。`unsafe` の誤りは未定義動作になるので、測定のリビジョンでも `// SAFETY:` の根拠を厳密に書く。
