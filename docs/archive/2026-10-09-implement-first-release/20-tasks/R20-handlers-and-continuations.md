# R20 ハンドラと一度だけ再開できる継続

- 依存する作業: [R14](R14-stage1-wrap-up.md)、[C02](C02-remaining-interfaces.md)、[R15](R15-vm-dispatch-performance.md)・[R16](R16-liveness-at-safepoints.md)・[R17](R17-call-path-and-constants.md)・[R18](R18-tail-window-and-slot-access.md)（性能の回復。ADR 0313 の決定 1）
- 難易度: 5（1〜5。README の「作業一覧」）
- 規模の見込み: 大（1500 行超）
- ブランチ: impl/R20-handlers

R14 は第 1 段の完了（F18 までのフロントエンドを含む）を待つので、本作業の時点で、`handle`・`resume` のコード生成（F15）とパイプライン（F18）は揃っている。ただし、完了を判定するテストは `bytecode::asm` で組み立てたプログラムを VM の実行の入口で実行して確かめる（後述の「受け入れテスト」）。

## 目的

利用者が定義するエフェクトのハンドラを VM で実行できるようにする。`HANDLE` で `handle` の枠を底に持つ区画を積み、`PERFORM`（と、処理するハンドラのある `IO`）で操作を処理するハンドラを探し、区画の所有を継続の値へ移して節を呼び、`RESUME` で区画を積み重ねへ戻す。継続は一度だけ再開でき、区画を写さない（ADR 0160）。引き継いだハンドラの探索と、末尾で再開する節の直接の実行（ADR 0151）も、この作業で書く。

あわせて、`RETURN` が包む枠を処理する一般の手順（02-08「実行の手順」）を入れる。第 1 段の `RETURN` は呼び出しの枠だけを降ろしていた。本作業の後は、`RETURN` が自分の解放の枠、自分の呼び出しの枠、自分を包む枠の順に処理し、包む枠の種類ごとの処理を「枠を降ろす原因と処理」の関数に渡す。R21〜R24 は、この手順に枠の種類ごとの処理を足していく。

## 作るもの

- `src/vm/dispatch.rs`: `HANDLE`・`PERFORM`・`RESUME` の命令の振り分けと、`IO` の節の探索、`RETURN` の包む枠の処理。処理の本体は、`dispatch.rs` の中で宣言する非公開の子のモジュール `src/vm/dispatch/handlers.rs` に置き、`dispatch.rs` には `match` の分岐から呼ぶ行と、`RETURN` の遅い経路への分岐・`run_until_exit` の先頭の戻りの再開状態の続き・止める手順（`cleanup`）の必要な変更だけを加える。`HANDLE`・`PERFORM`・`RESUME` と `RETURN` の遅い経路の本体は `#[inline(never)]` か `#[cold]` の関数として `handlers.rs` に置き、`execute` を膨らませない。後続の作業（R21〜R25・R34・R35・R37）も同じ形で子のモジュールを加えるので、同じファイルの同じ箇所を変える量を減らすためである。
- `src/vm/state.rs`: `RunState` の欄のうち、本作業が要るもの（後述の「実行中のタスクの番号」と、実行中のタスクの戻りの再開状態 `Option<ReturnWork>`。10-09「戻りの再開状態」）と、第 2 段の `pub(crate) scheduler: Scheduler` と `pub(crate) resources: ResourceTable`（どちらも `default()` で作る。10-09「実行ごとの状態」）。後の二つは本作業では使わなくてよい。R21〜R25 が同じ欄を使えるように、ここで置く。関数の中身は R24（リソースの表）と R25（スケジューラ）が書く。二つの欄は言語の値を持たないので、`RunState` の `Trace` は辿らない。
- `src/vm/unwind.rs`: `unwind_handle` と `unwind_drop` の、原因が `Return` の場合の中身（後述の「R21 との分担」）。原因がほかの場合は `Stop::Internal` を返す仮の中身にして、`todo!()` を残さない。シグネチャは枠を参照で受け取るので、呼び出し側は対象の `OtherFrame` を `others` から値で取り出し（`pop`）、その参照を渡して呼ぶ。`Popped` なら取り出した枠を `NoGcCtx::discard` で手放し、`Wait` なら枠を `others` に戻す（`push`。10-09「枠を降ろす原因と処理」の「枠を `Vec` から値で取り出し」）。`src/vm/unwind.rs` の `todo!()` の仮置き（00-02）は、R20・R22・R23・R24 がそれぞれ受け持つ関数を書き換える。R22〜R24 は R21 の後に並行して進めるので、仮置きの許可とコメントは、四つのうち最後に `todo!()` を書き換えた作業（取り込みの時点でファイルに `todo!()` が残っていない作業）が消す。

`vm/handler.rs` の型（`HandlerRecord`・`ContState`）は C02 が置いたものを使い、変えない。

### R21 との分担

10-09「作業の割り当て」と「枠を降ろす原因と処理」は、`unwind_handle`・`unwind_drop` の原因が `Return` の場合（E-HRet と、節が値を返して `drop` の枠に戻る場合）を本作業に、ほかの原因の場合を R21 に割り当てる。原因が `Return` の列は、ハンドラを普通に使うだけで通る経路だからである。

- `unwind_handle` の `Return`: 属するタスク（`HandlerRecord::members`）が残っていれば `Wait(TaskEnd(HandleEnd))`、なければ `Popped`。値を戻り先に入れるのは、`RETURN` の処理が `ReturnWork` の段と戻り先に従って行う（10-09「戻りの再開状態」）。本作業の時点ではタスクがないので `members` は常に空である。待つ場合の処理は R25 が確かめる。
- `unwind_drop` の `Return`: 継続が「使用済み」なら `Popped`（E-Drop）。「捕まえた区画の並び」なら、`host_mut` の中で継続を「使用済み」にしながら区画の並びを取り出し、`Traverse { segments, cause: DropRel }` を返す（E-DropRel）。`Traverse` を受けて区画を辿る処理は R21 が書くので、本作業の VM は `Traverse` を受け取ったら `Stop::Internal`（`"E-DropRel is not implemented yet"` の類）で止める。
- 原因が `Cancel`・`DropRel`・`Stop` の場合は、R21 が書く。本作業では `Stop::Internal` を返す仮の中身にする。

戻る値は、10-09 の `ReturnWork`（戻りの再開状態）の `value` に置く。値だけでなく、戻り先、処理の段階、戻りを始めた命令も同じ欄に置く。待つ間にほかのタスクが自分の `RETURN` を処理しても、上書きされないようにするためである（相談の第 6 回の指摘 1）。本作業は、実行中のタスクの分を `RunState` の欄に置き、R25 がタスクを切り替えるときにタスクの対象の `TaskObj::returning` と移し合う形にする。

## 手順の要点

### 実行中のタスクの番号

`HandlerRecord::evaluated_by` と `unwind_*` の引数 `at` は `TaskId` を要るが、タスクの表は R25 が作る。本作業では、`RunState` に「実行中のタスクの番号」の欄を置き、第 1 段の唯一のタスクに決まった番号（`TaskId { index: 0, generation: 0 }`）を入れる。R25 がタスクの表から実際の番号を入れる形に改める。引き継いだハンドラの連鎖も同じく、実行中のタスクの欄として `RunState` に置き（空の並び）、R25 がタスクの対象の `inherited` から移す形に改める。

### `HANDLE A B C`（E-Handle）

1. 上限を確かめる。新しい区画に積む `handle` の枠一つと、本体の呼び出しの枠一つと、本体の原型のレジスタの数を `StackMeter::fits` で確かめ、超えれば `CallStackTooDeep` で止まる。
2. 切り替えの位置の処理（中断の印、予算、遅い経路）を行う。本体の呼び出しは切り替えの位置である（02-08「タスクの切り替え」）。手順 1・2 と、回収・切り替えの後の再開は、10-09「呼び出しの前の安全点」に従う。
3. `HandlerRecord { clauses: R[B+1]…, desc: 原型の C 番目のハンドラの記述, evaluated_by: 実行中のタスク, members: [], body_finished: false }` を `alloc_host` で作る。節の数はハンドラの記述の節の数である（10-07「オペランドの補足」）。
4. 局所の状態を書き戻し、新しい区画を積む。区画の底に `OtherFrame { depth: 0, kind: Handle(HandleFrame { record, ret: 実行中の区画の regs の中の A の位置, at: この命令 }) }` を置き、その上に本体の呼び出しの枠（`ret: None`、`call_site: Some(この命令)`、`boundary` は本体の原型の `Proto::boundary`）を積む。本体は引数をとらない。
5. 新しい区画の局所の状態を読み直して続ける。

### `RETURN` の包む枠の処理（02-08「実行の手順」、ADR 0262 の決定 3）

降ろす呼び出しの枠が区画の中で下から c + 1 番目で、その枠の上に解放の枠か包む枠があるとき、次の順に行う（ない場合は、後述の普通の戻り）。処理の途中の状態は、実行中のタスクの `ReturnWork`（10-09「戻りの再開状態」）に置く。戻る値は、手順 1 の前に `ReturnWork::value` へ移し、`stage` を `OwnReleases`、`at` をこの `RETURN` にする。

1. 深さ c + 1 の解放の枠を上から順に処理する（原因 `Return`）。解放の枠を積む `USE` は R24 が入れるので、本作業の時点では現れない。処理は `unwind_release` を呼ぶ形で書いておく。
2. 呼び出しの枠の `ret` を読んで戻り先（`ReturnWork::dest`）を決め、段を `Wrapping` にする。呼び出しの枠を `Vec` から取り出して `NoGcCtx::discard` で手放し、窓の外になったレジスタを `clear` し、`StackMeter::shrink` する。
3. ほかの枠の `Vec` の上から、深さ c の包む枠を順に処理する。深さ c の解放の枠か、深さが c より小さい枠に達したら止める。呼び出し元の解放の枠には進まない。包む枠のない普通の呼び出しでは、最も上のほかの枠の深さと種類を見るだけで処理を終える（fib のような呼び出しの多いプログラムで、この確かめの費用を増やさないため）。判定は、最も上のほかの枠の深さが降ろす呼び出しの枠の深さ以上かの一回の比較（例 `others.last().is_some_and(|o| o.depth >= calls.len() - 1)`）とし、今の `ret.is_none()` による `main` の終わりの判定より前に置く。`handle` の本体の呼び出しの枠も `ret: None` なので、順序を誤ると本体の戻りを `main` の終わりと取り違える。
4. 包む枠は種類ごとに `unwind_*` を原因 `Return` で呼び、結果に従う。`Popped` なら、枠を `Vec` から取り出して `NoGcCtx::discard` で手放し（`unwind_*` は枠の `Slot` を手放さない。10-09「枠を降ろす原因と処理」）、`StackMeter::shrink` して次へ進む。`Wait` なら枠と `ReturnWork` を残してタスクを待たせる（待たせる処理は R25 以降。待ちが解けたら、命令を実行する前に `ReturnWork` の段から続ける）。`Retry`（セルの更新の枠。R23）と `Traverse`（`drop` の枠。R21）はそれぞれの作業が扱う。包む枠を一つ `Popped` で降ろすたびに回収の要求（`collect_requested`）を確かめ、要求があれば `ReturnWork` を残したまま `Collect` で安全点へ戻る。`run_until_exit` は、先頭で実行中のタスクの `ReturnWork` が残っていれば、局所の状態を読み込む前に（最も上の区画に呼び出しの枠がない状態がありうるため）その段から続ける。止める手順（`cleanup`）は、残っている `ReturnWork` を `discard` する（10-09「戻りの再開状態」）。
5. 包む枠を処理して区画が空になったら、区画を降ろす。区画の底の `handle` の枠を降ろすときは、その `ret`（すぐ下の区画の位置）を戻り先にする。
6. 戻り先に値を入れ（タスクの最初の呼び出しの枠から戻ったときは、その値でタスクを終える）、`ReturnWork` を消して、戻り先の区画の最も上の呼び出しの枠の命令の位置から続ける。

普通の戻り（戻る呼び出しの枠の上に解放の枠も包む枠もない `RETURN`）は、`ReturnWork` を通さず、R15 が作った直接の経路のまま戻る（[ADR 0313](../../2026-10-09-design-first-release/decisions/0313-vm-performance-recovery-before-stage-2.md) の決定 3、10-09「戻りの再開状態」）。最も上の枠の深さと種類を見るだけで普通の戻りと判定し（ADR 0262 の決定 3）、普通の呼び出しと戻りの経路に、`ReturnWork` の構築、動的確保、枠を降ろす状態機械を足さない。`ESCAPE` は R21 が入れる。

### `PERFORM A B C` と、処理するハンドラのある `IO`（E-Op）

1. ハンドラの連鎖を内側から調べ、操作 B（`IO` では `BuiltinRef::op`）の節を持つ最初のハンドラの記録を探す。連鎖は、実行中のタスクの積み重ねの `handle` の枠を上から順に並べ、その後にタスクが引き継いだ連鎖を続けたものである（02-08「ハンドラの記録とハンドラの連鎖」）。区画の底の枠が `handle` の枠なので、区画を上から順に見ればよい。
2. 探す途中で `CallFrame::chain_resume` を持つ呼び出しの枠（引き継いだハンドラの末尾で再開する節を直接呼んだ枠）に達したら、それより下の区画を調べずに、引き継いだ連鎖の記録した位置へ移って調べ続ける（相談の第 2 回の問い 3 の「節内の探索は、選ばれたハンドラの外側へ進む」）。
3. 見つからないとき、`PERFORM` なら処理系の不具合（`Stop::Internal`）とする。`IO` なら、処理系が操作を行う経路（第 1 段の実行の関数。R26 の後は送り出しの列）に進む。
4. 見つけた記録の `evaluated_by` が実行中のタスクなら（E-Op）。区画を切り離した後に失敗すると、切り離した区画がどの積み重ねにも属さなくなり、止める手順がその中の解放の枠を辿れない（相談の第 6 回の指摘 3）。そこで、失敗しうる確かめをすべて切り離す前に行う。
   1. 節の関数の値（ハンドラの記録の `clauses` の該当する位置）を読み、関数の値であることと原型の引数の数（操作の引数の数と継続の一つ）を確かめる（違えば `Stop::Internal`）。上限を、`drop` の枠一つと節の呼び出しの枠一つと節の原型のレジスタの数で確かめる（超えれば `CallStackTooDeep`）。ここまでは何も変えない。
   2. 切り替えの位置の処理を行う（節の呼び出しは切り替えの位置である）。手順 1・2 と、回収・切り替えの後の再開（ハンドラを探し直すところから実行し直す）は、10-09「呼び出しの前の安全点」に従う。
   3. 呼び出しを成立させる。局所の状態を書き戻し、次の順に行う。(a) 継続を切り離した後に最も上になる区画（見つけた `handle` の枠を底に持つ区画のすぐ下の区画）の `regs` の末尾に節の窓を確保し、操作の引数を、操作を呼んだ枠の窓から節の窓へ置く（`load` で読んで写す。R16 の後の VM は `LastUse` で移さない。[ADR 0314](../../2026-10-09-design-first-release/decisions/0314-clear-dead-registers-at-safepoints.md)）。操作を呼んだ枠の `pc` は、局所の状態を書き戻すときに次の命令へ進めて保存する。(a2) まだ積み重ねにある、切り離す区画の各呼び出しの枠の窓を、「結果が書かれる前の呼び出し元」の規則（`live_in(pc)` から `call_write(pc − 1)` を除いた集合の外）で `NoGcCtx::clear` により空にする（後述の「回収の前の整理」）。生存の情報を引けない枠は空にせず、`Stop` を返さない。(b) 見つけた `handle` の枠を底に持つ区画から積み重ねの先頭までの区画を `Vec` から切り離す（`split_off`。区画の中身は写さない）。(c) `ContState::Captured(区画の並び)` の継続の対象を `alloc_host` で作る。(d) 最も上の区画に `drop` の枠（`Drop { cont }`、深さはその区画の呼び出しの枠の数）を積む。(e) 継続の値を節の窓に置き、節の呼び出しの枠を積む（`ret` は切り離した `handle` の枠の `ret`。E-Op の継続 `(drop κ) :: K2`）。操作を呼んだ命令の結果のレジスタは、継続の中の最も上の呼び出しの枠に残る（その枠の `pc` は操作の次の命令を指す）。区画の所有を移すだけなので、切り離した区画の分の計数は変えない（02-08「呼び出しの入れ子の上限」）。
   4. 手順 3 の (b) から (d) の間には、`Stop` を返しうる処理を置かない（`split_off`・`alloc_host`・`new_slot` は失敗しない）。レジスタの範囲の外などの処理系の不具合は、(a) の前か (d) の後に検出する。こうすると、止まりうるどの時点でも、区画は元の積み重ねか、積み重ねの `drop` の枠から辿れる継続のどちらかが所有する。
5. 見つけた記録の `evaluated_by` が実行中のタスクでない（引き継いだハンドラの）とき:
   1. 節の `ClauseDesc::tail_resumptive` が偽なら、節を実行せずに `RuntimeError::InheritedHandlerClause { operation }` で止まる（`operation` は `OpInfo::name`）。
   2. 真なら、手順 4.1 と同じく節の関数の値と上限（節の呼び出しの枠一つと節の窓）を確かめ、手順 4.2 と同じく切り替えの位置の処理を行う。そのうえで、継続を捕まえずに `ContState::Direct` の継続の対象を作り、節の関数を、操作を呼んだ命令からの普通の呼び出しとして呼ぶ（結果のレジスタは操作の命令の A）。呼び出しは `CALL` と同じ手順（10-09「呼び出しの前の安全点」の手順 3）に従うが、`call::<TAIL>` の引数の読み方（`B + 1` からの並び）と本体は変えず、`handlers.rs` に専用の関数を書く（普通の呼び出しの経路に費用を足さない。ADR 0313 の決定 3）。節の呼び出しの枠の `chain_resume` に、見つけたハンドラより外側の連鎖の始まりの位置を記録する。

### `RESUME A B C`

- 継続 `R[B]` が「捕まえた区画の並び」なら（E-Resume）: 上限の確かめはしない（区画の所有を戻すだけで、計数は捕まえたときから含まれている）。局所の状態を書き戻し、`host_mut` で継続を「使用済み」にしながら区画の並びを取り出し、実行中の積み重ねの上に戻す。戻した区画の底の `handle` の枠の `ret` を、この `RESUME` の結果のレジスタ（実行中の区画の `regs` の中の A の位置）に付け替える。戻した最も上の呼び出しの枠の、`pc − 1` の命令（操作を呼んだ `PERFORM` か `IO`）の A のレジスタに再開の値 `R[C]` を入れ、その枠の局所の状態を読み直して続ける。
- 「使用済み」なら `RuntimeError::ContinuationResumedTwice` で止まる（E-ResumeErr）。
- 「直接の再開」なら、再開の値を `R[A]` に入れて続ける。末尾で再開する節では `RESUME` の後に `RETURN` が続くので、その値が操作の呼び出しの結果になる。

`RESUME` は切り替えの位置ではない（02-08「タスクの切り替え」の命令の並びに含まれない）が、上限の確かめの対象である（02-08「呼び出しの入れ子の上限」）。「捕まえた区画の並び」の再開は計数を変えないので、確かめは常に通る。

### 回収との関係

継続の対象の区画は、`ContState` の `Trace` で辿られる。区画を切り離す、戻す、`host_mut` で状態を変えるときは、区間の中で行い、局所変数の `Value` を区間の外へ持ち出さない。回収の強制（機能 `gc-stress`）のビルドで、区画の移動の直後の安全点で回収してもテストが通ることを確かめる。

降ろした枠と区画の `Slot` は、`NoGcCtx::discard` でちょうど一度手放す（10-09「枠を降ろす原因と処理」の `Popped` の受け持ち）。`unwind_handle`・`unwind_drop` は枠を借りて読むだけにし、`Traverse` で返した区画は手放さない。

### 回収の前の整理（ADR 0314）

R16 の後の VM は、回収のために区間を閉じる前に、各枠の窓のうち再開の後に読まれうるレジスタの集合に含まれないものを空にする（[ADR 0314](../../2026-10-09-design-first-release/decisions/0314-clear-dead-registers-at-safepoints.md) の決定 2・3）。本作業が加える枠の状態を、決定 5 の「命令の入口」（live_in(pc) を残す）と「結果が書かれる前の呼び出し元」（live_in(pc) から命令 pc − 1 の結果のレジスタを除いて残す）のどちらかに分類する表を、完了の報告に書き、分類どおりに空にする。

- `HANDLE`・`RESUME`・節の呼び出しを成立させる手順は、`CALL` と同じく、呼び出し元の枠の `pc` を次の命令へ進めてから保存し、その間に回収を挟まない。進めずに保存すると、`pc − 1` の命令の結果のレジスタを消す（相談の第 9 回の指摘 1）。
- 継続を捕まえるとき、継続の中の最も上の呼び出しの枠（`pc` は操作の次の命令を指す）は「結果が書かれる前の呼び出し元」である（操作の結果は、継続を再開したときに書かれる）。捕まえた区画はヒープの対象（`Host`）の中にあり、回収の前に可変で辿れないので、捕まえるときに各枠の窓を決定 3 の規則で空にし、捕まえている間は窓を変えない。空にするのは、手順 4.3 の (a2)（引数を節の窓へ写した後、区画を切り離す前。区画はまだ積み重ねにあるので `NoGcCtx::clear` で書ける）とする。(b)〜(d) の間（`host_mut` の中の `SlotOps::clear`）で行うと、生存の情報を引けないときに `Stop` を返す処理を手順 4.4 の区間に置くことになるからである。
- 最も上の区画に呼び出しの枠がない状態が起きうるなら、その区画の扱いを表に書く。分類を確かめていない状態は、空にしない。
- 受け入れテスト: ハンドラの本体の中、節の中、再開した本体の中で回収が起きる設定（`gc-stress`）で、`CALL r0 …; RESUME …; r0 を使う` と `CALL r0 …; HANDLE …; r0 を使う` の形の値が残ることを確かめる。

## 受け入れテスト

完了を判定するテストは、`bytecode::asm` で組み立てたプログラムを `Vm::new`・`start_main`・`run_stage1` で実行して確かめる（R09 と同じ形。相談の第 6 回の指摘 7）。境目を狙った形（上限の直前、区画の移動の直後の回収）を確実に作れ、コード生成の誤りと VM の誤りを切り分けられるからである。操作とハンドラの記述は、`ProgramBuilder` の `program`（`pub(crate)`）の `ops`・`handlers` に直接加えてよい（`asm.rs` は変えない）。同じ場合を、`pipeline` の関数（10-13 の `check_text`・`desugar_checked`・`compile`）でコンパイルした小さなスクリプトを `runtime::run::run_program` で実行する統合テスト（`tests/` の下）にも書く。スクリプトの統合テストはコード生成（F15）との組み合わせを確かめるものであり、`asm` のテストの代わりにしない。スクリプトでは、`handle` の本体や節の中の `return`（コード生成が `ESCAPE` を出す。R21）と、`resume` を呼ばずに値を返す節（E-DropRel。R21）を使わない。ゴールデンテストでの確かめは C12 が行う。

- 末尾で再開する節: 操作を 3 回呼ぶ本体が、節の返す値を使って結果を作る。`handle` の式の値が本体の値になる。
- 継続を保存して後で再開する節: 節が `resume` の前後に計算をし、`handle` の式の値が「節の値」になる（E-Resume の戻り先の付け替え）。操作の呼び出しの結果のレジスタに再開の値が入る。
- 入れ子のハンドラ: 内側の `handle` が処理しない操作を外側の `handle` が処理する。内側の本体の中から外側の操作を呼び、再開した後も内側のハンドラが有効である（捕まえた区画に内側の `handle` の枠が含まれる）。
- 節の中で同じ操作を呼ぶと、そのハンドラより外側のハンドラが処理する（深いハンドラの探索の順序）。
- 二度目の再開: 継続を二度再開しようとするスクリプト（型検査を通る形で書けるもの。書けなければ `asm` で組み立てる）が `ContinuationResumedTwice` で止まり、止まった命令が二度目の `RESUME` である。
- 長い繰り返し（定数の空間）: 各反復で `handle` と節が終わってから次の反復へ末尾呼び出しする形（反復ごとに `HANDLE` を評価し、本体が操作を呼び、節が末尾で再開するか、`resume` の後に値をそのまま返す）を 100 万回繰り返すプログラムが、`max_call_stack_bytes` を小さく（例 1 MiB）しても止まらずに終わる。
- 再開の後に計算を積む節: 一つの `handle` の中で本体が末尾再帰で操作を呼び続け、節が `resume` の後に加算する（`RESUME; ADDI; RETURN`）形は、各 `resume` の後の計算のために節の呼び出しの枠と `drop` の枠が残るので、定数の空間では走らない（相談の第 6 回の指摘 6。コア計算の「末尾呼び出しの保証の読み替え」もこの増え方を許す）。少ない回数（例 100 回）で正しい結果になることと、小さな `max_call_stack_bytes` で `CallStackTooDeep` で止まり、報告の枠の数が計数と一致することを確かめる。引き継いだハンドラの末尾で再開する節の直接の実行を繰り返す形は、R25 が定数の空間で確かめる。
- 上限: `handle` を入れ子に深く積むプログラムが `CallStackTooDeep` で止まり、報告の枠の数が計数と一致する。
- 上限の直前の `PERFORM`: `drop` の枠と節の呼び出しの枠と節の窓の分だけが足りない `max_call_stack_bytes` で `PERFORM` すると、`PERFORM` の命令で `CallStackTooDeep` で止まり、`StopInfo::frames` に操作を呼んだ枠が含まれ（区画を切り離していない）、止める手順の後に計数が 0 に戻る（今の `cleanup` はほかの枠を `discard` するだけで `StackMeter::shrink` を呼ばないので、本作業がほかの枠の数だけ `shrink` する形に改める。捕まえた継続の区画の分を減らすのは R21）。リソースを捕まえる形（止めたときに解放がちょうど一度行われる）は、`USE` の入る R24 が確かめる。
- 戻りの再開状態: `RETURN` の処理の途中の状態が `ReturnWork` にあることを、包む枠のある戻り（`handle` の本体の戻り、節の戻り）の結果で確かめる。待ちを挟む場合（属するタスクの終わりを待つ間に別のタスクが値を返す）は、タスクを起動できる R25 が確かめる。
- 枠だけが持つ値の解放（相談の第 6 回の指摘 5）: 捕捉した値を持つクロージャを `HANDLE` の本体と節にし、その値を枠（`CallFrame::func`、`HandleFrame::record` の節）だけが持つ状態で、`handle` が値を返した後と、節の中の 0 の除算で止めた後に回収し、`Heap::object_ids` にクロージャと捕捉した値の対象が残らない。
- 根の置き場ごとの回収の強制（R03「根の列挙の引き渡し」の表の、本作業の行）: `HeapConfig::stress` を真にした設定で、値が次の置き場だけに残る状態を作って回収し、回収の後にその値を読んで結果が正しいことを確かめる。`handle` の枠のハンドラの記録（節の関数の値の捕捉だけに残る値）、`drop` の枠の継続の値と、保存した継続の区画（捕まえた区画のレジスタだけに残る値を、節の中の呼び出しで回収した後に `resume` で読む）、戻りの再開状態（`ReturnWork::value` だけに残る戻る値。包む枠の処理の途中で回収を起こす）。
- `RETURN` の包む枠の処理: 包む枠のない呼び出しの結果が変わらない（第 1 段の VM のテストがそのまま通る）。R15 の動的確保がないことを確かめるテストがそのまま通る。
- 性能: 取り込みの前に、オーケストレータが設計者の確認を得てから fib・loop を測り、ADR 0313 の決定 5 の取り込みごとの関門を判定する。基準は R18 の値（fib 1.965 s、loop 1.060 s。[記録](../../../../tools/bench/results/2026-10-06-r18-ab41855.md)）。`IO` の節の探索は `IO` の命令で `BuiltinRef::op` があるときだけ行い、`PRIM` の経路に足さない。実装担当は、作業を始めたときの `san_benito` の HEAD と本作業の版を fib(30)・loop 300 万回で交互に数回走らせて比べ、完了の報告に書く（比較の版の展開と target は作業ディレクトリの `target/` の下に置き、終えたら消す）。
- 回収の強制のビルドで、上のテストがすべて通る。
- 呼び出しの前の安全点: 節の呼び出しの直前（手順 4.2）で回収が起きる設定で、操作の引数に定数の表に残らないヒープの値を渡し、節が正しい引数を受け取り、節が一度だけ呼ばれ、予算が一度だけ減ることを確かめる（R09 の同じテストの `PERFORM` 版）。
- 引き継いだハンドラと末尾で再開する節の直接の実行は、タスクを起動できる R25 の受け入れテストで確かめる。本作業では、`RunState` の引き継いだ連鎖にテストから記録を入れた場合の探索の順序（`chain_resume` で連鎖を移ること）を、VM の単体テストで確かめてよい。

## 確認の観点

- [実装の確認の観点](../00-common/00-04-review-checklist.md)の「VM」の行。とくに、区画を切り離す・戻す前に局所の状態を書き戻し、後に読み直しているか。
- 深さの規則（ほかの枠の深さ d と呼び出しの枠の数 c で `d ≥ c` ならほかの枠が上）が、区画を戻した後も成り立つか。区画の中の相対値だけを使い、戻す先の深さに合わせて書き換えていないか（相談の第 2 回の問い 1）。
- `RETURN` が呼び出し元の解放の枠に進んでいないか。
- 節の呼び出しの枠の `ret` と、`RESUME` での `handle` の枠の `ret` の付け替えが、E-Op と E-Resume の継続の形に一対一で対応しているか。
- `PERFORM` で、失敗しうる確かめ（節の関数の値、上限）をすべて区画の切り離しの前に行っているか。切り離してから `drop` の枠を積むまでの間に `Stop` を返しうる処理がないか。
- 普通の戻りが `ReturnWork` を作らず、普通の呼び出しと戻りの経路に処理を足していないか（ADR 0313 の決定 3）。
- 戻る値、戻り先、段を `ReturnWork` に置き、待ちをまたいで保っているか。`RunState` の一つの欄を複数のタスクで使い回す形になっていないか。
- 引き継いだハンドラの直接の実行で、節の中の操作の探索が、見つけたハンドラより外側へ進むか（操作を呼んだ側の内側のハンドラを飛ばすか）。

## 難易度の理由

区画の所有の移動、戻り先の付け替え、`drop` の枠、包む枠の処理の順序が互いに絡み、どれかを誤ると E-Op・E-Resume の意味からずれる。誤りの多くは値が一つ違うだけの形で現れ、原因の特定が難しい。後続の R21〜R25 がこの作業の区画と `RETURN` の形の上に作るので、形を誤ると後の作業すべてに及ぶ。
