# IFC-D8: 0.0.14 の必須例と、未対応の例を拒否する範囲の案

2026-10-27、IF10.07。設計者が選ぶための判断案であり、採択済みの決定でも、実装・証明の完了報告でもない。

## 決めることと既に決まっている境界

IFC-D8 で決めるのは、公開 CSV の集計表示・トークンによる取得件数と所定の成否の表示・機密ファイルの固定 API 送信を、入力から出口と成否まで接続し、正当な形の受理・禁止する変更の拒否・保証の説明をそろえる 0.0.14 の必須条件とし、残る例を接続を閉じる改造・サーバモード・対象外へ分け、未対応経路へ到達しうる実行対象や必要な契約を解析できない実行対象は全体を実行前に拒否するか、必須例を選ばないか、Task と保存の二例も必須に加えるかである。

[README の版の割り振りと方式](../README.md#設計者の決定2026-10-27版の割り振りと情報フロー制御の方式)、P1〜P6、[判断14](../decisions.md#判断-14-保証と後の宛先の契約)・[判断19](../decisions.md#判断-19-情報フロー制御の方式と今回の成果物)・[判断21](../decisions.md#判断-21-実装と提供の境界)を保つ。0.0.13 は判断案・棚卸し・契約の設計、0.0.14 は情報フロー制御（information-flow control）の独立した実装、その後は必要な接続とサーバモードである。サーバは `0.1.0` より前であり、接続を閉じる改造とサーバの版番号は未定である。

方式は案 G とし、内部の判定と Lean の証明は汎用の束、最初の範囲は管理者が定める有限の束、機密性と完全性、用途を限った非機密化（declassification）とエンドースメント（endorsement。信頼の付与、または完全性レベルの引き上げ）、推論する一階の印の要約とする。この方式の採否や、方針の書式の境界を実装より前に設計する順序は再選択しない。

[IFC-D2](../if10.01/ifc-d2.md)・[IFC-D3](../if10.02/ifc-d3.md)・[IFC-D4](../if10.03/ifc-d4.md)・[IFC-D5](../if10.04/ifc-d5.md)・[IFC-D6](../if10.05/ifc-d6.md)・[IFC-D7](../if10.06/ifc-d7.md)の案A（D5だけは案B・候補(ii)）を仮の前提にする。設計者はどれもまだ選んでいない。各文書の IFC-D8 への申し送りに従い、入力契約と実対象の対応、送信と応答の公開、包みからの取り出しと非機密化、公開と完全性の信頼、承認と未対応機能の実装を分ける。別案で変わる点は後掲の依存表に示す。

D5案Bの固定originも案Aの単一候補として同じ印・観測の条件を用いる。以下のR全体への被覆の説明をこの意味で適用し、動的設定の受理は別案Aに限る。

[00-01「保証の範囲」](../../../design/00-overview/00-01-goals.md#保証の範囲)と[07-01「脅威モデル」](../../../design/07-quality/07-01-security-model.md#脅威モデル)に従い、LLM・スクリプト・依存パッケージ・外部入力を信頼しない。セキュリティ型システム（security type system）が保証するのは規則への適合であり、意図との一致、外部操作の成功、停止ではない。0.0.14 の保証は、起動側による同じ方針・信頼する契約・検査したコードと依存の組の保護を前提にする。処理系自身の実行時の権限制御と OS の強制はサーバへ残す。

## 推す案と二つの代案

案Aは「三例を必須」、案Bは「必須例を選ばない」、案Cは「Task と保存を加えた五例を必須」とする。[元の問いD8](../study/questions.md#0013-の中で決めること設計の判断として文書にするもの)の「全例」を、任意 URL への秘密送信や未信頼のシェル本文まで無条件に通す意味にはできない。案Cでは、接続の前倒しを比較できるよう、逐次以外で追加する正当な利用を Task と専用保管口に絞る。汎用の外部コマンドの隔離まで前倒しする案は、判断14と版の順序を変える別の判断を要する。

|---|---|---|---|

## 三例を必須にする場合の受け入れ条件

「受理必須」は正当な形を少なくとも一つ受理し、禁止する変更を拒否することを受け入れ条件とする意味であり、どんな入力でも受理する意味ではない。新しい術語として採用した扱いにはせず、用例は未確認である。

案A・Cの「必須」は、作例の構文解析が通ることや、小モデルの送信が成功することだけでは満たさない。0.0.14の計画には、実装した標準の入口から出口まで同じ契約で処理する受理例と、そこから禁止する依存を加えた拒否例を割り当てる。非干渉性は本番の規則と信頼条件に対する別の証明・レビューの対象であり、三例のテストだけで証明したとはしない。

| 必須例 | 0.0.14で受理できる形 | 対応して拒否する変更と、受け入れで確認すること |
|---|---|---|
| 公開CSVの集計・表示 | 信頼する起動側が、実入力との対応と内容・成否を公開と認定した契約を渡す。CSVの内容は未信頼のまま集計し、公開の報告先へデータとして表示する。任意のパスの字面だけでこの契約を得られない | 契約のない一般読み取り、秘密の列や別の秘密による分岐を報告へ混ぜた形を拒否する。読み取り・解析の失敗、長さ等による停止、表示の有無と出力失敗も含めて接続する。公開入力の分類への信頼と、集計値の正しさは別である |
| トークンによる取得件数と所定の成否の表示 | 登録した一種類のトークンを固定操作の認証欄だけに使い、公開かつ信頼する呼出条件で逐次取得する。D3の限定契約で件数と所定の粗い成否・正常復帰だけを非機密化し、完全性は未信頼のまま表示する | トークン・応答本文・ヘッダ・生の失敗文の表示、未承認の本文へのトークン混入、別の捕捉・条件の秘密を加えた報告を拒否する。件数だけでなく認証失敗・通信失敗・変換失敗と終了状態の対応を契約で示す。APIが承認範囲を越えて秘密を反映しないことは承認する信頼条件である |
| 機密ファイルの固定API送信 | D4の認定した入力契約から機密ファイルを得て、秘密のまま、指定した本文の用途で許した固定APIへ送る。認証があればその分類も認証欄の契約へ結ぶ。同じ検査済み要求を使い、要求のscheme・各欄・pcとR全体の条件を満たす。自動追従・自動再試行は含めない | 別のホストを含むR、未承認の要求欄、秘密で選ぶ公開の後続、応答や生の成否の無断表示を拒否する。送信の受理は応答の公開とは別に記録する。応答・成否を秘密に保つ最小形でも、失敗と正常復帰から公開の終了状態や後続が変わる接続を閉じる |

D5の候補(ii)を前提にすると、必須例1・2は失敗を値として扱う形を要する。公開CSVの解析失敗や公開化したAPI成否も完全性は未信頼であり、それに依存する `die`・Assertの失敗・非再開を受理する条件にはしない。成功・失敗を未信頼のデータとして固定した公開の報告先へ表示し、両枝を同じ正常終了へ合流させ、その後に信頼を要する操作を置かない最小形を目指す。APIの非機密化は完全性の信頼を付与しない。

この最小形でも、読み取り・入力上限・解析・出力の停止を含む全経路が値へ戻せるか、後続のpcが規則に適合するかは未確認である。IF30と0.0.14の試作で確認し、満たせなければ必須例は未達として、契約・規則または必須条件の再選択を設計者へ返す。D4の公開CSVの提供はA1（起動側の読み取り済みデータ）を仮の候補とし、A2（字面と実対象の対応の信頼条件を補うFile読み取り）も比較する。両形の費用は未見積もりであり、方法を選ぶ前に三例の費用が確定した扱いにはしない。

三番目の必須条件に、受付結果の公開を自動的には加えない。公開する場合は送信用の独立したD3の契約を要し、取得件数用の契約を流用しない。公開しない形も、戻り値を捨てて一定文字列を出すだけで受理できるとはしない。最初の制御規則では失敗・正常復帰を安全に合成できないと分かった場合、必要な限定契約か規則を設計して証明するまで、その必須例は未達である。必須化を選んだ後に、理由を示さず接続を閉じる改造へ送って0.0.14を受け入れない。

受け入れの証拠には、同じ方針・契約の版とプログラム・依存の組、入力の分類の根拠、受理／拒否と診断、公開する観測と未公開の値、人間へ示す要約と信頼条件を含める。実IOを使う確認は制御した入力と相手で行い、標準の取得・要求保持・非追従の送信・実際の出力を通す。模擬ハンドラだけの成功を実IOの接続の代わりにせず、公開のダミー値を置いただけで秘密の入力分類を検査した扱いにしない。試験用の認証値等を秘密として分類することはできるが、実在APIの秘密の非反映をその試験から保証しない。

## 拒否の単位と、解析できない場合の扱い

三案とも、保証を示す単位を実行入口一つと、その入口から到達しうる計算全体にする案とする。依存パッケージ、関数の別名・高階の受け渡し、ハンドラの節と捕捉環境、継続・正常と異常の後続も含む。秘密を直接引数に渡した操作だけを拒否単位にすると、公開の引数だけで起動した子が独立に秘密を読む例を除けないためである。

| 状態 | 判定と拒否の範囲の案 |
|---|---|
| 未対応のTask・共有状態・資源保持・汎用Process・WASM等に到達しうる | その実行対象全体を実行前に拒否する。Taskを逐次化する、Readerを保持しない入力へ変える等、対応範囲へコードを直して再検査する。案Cで閉じた限定Task・保管口だけはこの一覧から外す |
| 未対応の名前はあるが、その実行から到達しないと健全に示せる | 名前が存在するだけで全リポジトリを拒否しない。ただし、今回の入力では通らなかったという実行結果や、秘密の分岐で選ばれなかったことを静的な非到達の根拠にしない |
| 呼出先・入口分類・印・宛先の上限が不明でも、健全な保守的要約を作れる | 一般入力は秘密の結び、対象はありうる候補全体、完全性は未信頼として判定する。その上限でも全出口の条件を満たせれば受理の候補になる。未分類や分類の網羅性が不明な入力を健全に表せなければ次行の拒否とし、秘密登録が空だから公開とはしない。Topを選んだ現在値一つに置き換えない |
| 到達可能性、契約の同一性、起動入力との対応、必要な要約を示せない、または解析の予算を使い切る | 保証を付ける実行を拒否し、不明な位置と足りない根拠を示す。未知を公開・信頼済み・未使用にせず、警告を出して保証付きで続行したり、実行時に試して判断したりしない |
| コード違反、方針の不足、未対応の機能 | 診断で区別する。秘密の実値・長さ・秘密依存の実行結果を出さず、入力と依存した位置・候補・出口を示す。未対応は人間の承認だけでは通さない |
| 複数のテスト入口をまとめて実行する依頼 | 各入口の全体を検査し、一つでも拒否なら、その依頼のテストを一つも開始しない案とする。07-01の既存の上限付きtestの準備順と同じく、先の入口が外部操作を行った後に後の拒否が分かる形を避ける |

この範囲は、新しいCLIモード・スイッチ・API名の提案ではない。通常実行に既存機能を残す場合、その入口には情報フロー制御の保証を付けず、上の拒否を通常実行への自動切替で回避しない。公開だけの既存プログラムから機能を一律に削除する判断でもない。汎用Processには独立した秘密の取得がありうるので、「言語内で秘密取得を呼ばない」ことだけで保証の対象に戻さない。

## 典型8例の全案での扱い

以下は実装後に目指す受理／拒否であり、現在の動作確認ではない。「受理」はその欄と三例の表の全契約を満たす形に限り、「非必須候補」は0.0.14で閉じれば受理、閉じなければ拒否して明示した行き先へ送る意味である。「対象外」は保証を付ける実行では拒否し、通常実行が残っても保証を与えない意味である。提供を後の改造へ回すことは、受理の約束ではない。

任意URLの行は、秘密を受け取ってよい相手を限定しない例である。この禁止フローも検査の対象に含める。分類はD2の「対象／拒否」に揃え、LLM出力のシェル入力も同じとする。D2の「対象候補」は本表の「受理必須／非必須候補」、D2の「後の版」は本表の「未対応で拒否して後の改造へ」、D2の「対象外」はgh/git等の保証外の通常実行に対応する。IF30でこの対応を一つの分類へ集約する。単に版を後へ送って同じ無条件送信を受理へ変えない。狭いRへ直す場合も、公開／未信頼の設定ではD5案Aの積の底の制限により拒否しうる。三例の宛先は固定なので、動的な宛先検査を必須にはしない。未信頼入力による失敗の扱いは、上の必須例の条件として別に残る。

LLMの行は実行時の外部入力の用途を扱う。生成前に悪意のある文書を読んだLLMが、危険な操作をコードの定数として書く問題まで、実行時の入力の印だけで検出できるとはしない。固定操作へ変える代替も元の任意シェル本文とは別の例である。

## 試作と外部一次資料が支える範囲

[SD §2〜§4](../spikes/SD/findings.md#2-送信と観測の規則)は、同じ宛先値の所属、`pc ⊔ label(d) ⊔ label(v)` の許す受け手によるR全体への被覆、公開pcのfail・非再開・失敗しうる宛先検査を小モデルで確かめた。実IOの成否、緩和との合成、本番の一般ハンドラ・ストア・Task・解放は未接続である。積では宛先検査の入力に公開かつ信頼する印を求める十分条件も保つ。[SH2の観察の制約](../spikes/SH2/findings.md#評価の一致と観察の制約)は、純粋で全域的な応答関数の下での型・効果と値・Emit列の一致であり、情報フロー制御や非干渉性の証明ではない。

[S3 §5](../study/usage-and-flow.md#5-情報フロー制御と-lio)と[S5の接続の規則案](../study/information-flow.md#6-現在の仕組みとの接続の規則案)も、効果の除去と秘密の依存を分け、Task・資源保持・外部コマンドを引数だけの照合で通さない論点として読む。古い版の割り振りと訳語はREADMEの決定で読み替える。SD・SH2の短い実績から本番の工数を下げず、再試作もしない。

2026-10-27に、[Jif 3.3.0公式文書「Label checking」](https://www.cs.cornell.edu/jif/doc/jif-3.3.0/label_checking.html)の「Program counter labels」「Normal and exceptional termination」「Basics of label checking」を確認した。同文書はpcで到達から分かる情報を追い、正常終了と例外の有無にも印を付け、先行式の正常終了の印を後続のpcへ渡す規則を説明する。三例の成否と後続も受け入れで確認する参考であり、BenitoiteのTask・保存・非再開が接続済みであるという根拠ではない。

他システムでこの三例または五例がどの費用で動くか、各実在APIが秘密を反映しないか、実在ハーネスの方針保護、LLMの生成・修正成功率は本枝では未確認である。構文・API名や承認画面の方式を一次資料の先行例から決定しない。

## IFC-D2〜D9への依存と申し送り

| 判断・枝 | 仮の前提と渡す条件、別案が選ばれた場合の差 |
|---|---|

| IFC-D3／IF10.02 | 案Aの許した要求由来だけの件数・所定の成否・呼出条件の非機密化を使う。D3案Bでは二番目の公開報告を必須とする案A・Cと両立しないので、回答か必須例を再選択する。送信できても応答を公開できない境界は残る。D3案Cなら広い例外による受理であり、件数等以外の公開を拒否する必須条件と説明を改めて判断する |

| IFC-D9／IF10.08 | 実行入口全体と同じ方針・入力／出口契約・固定変換の識別と版・承認を結ぶ。例の追加、受け手・R・公開欄や成否・用途の拡大、分類の緩和と変換の差し替えの再承認・再検査、旧キャッシュの無効化を扱う。具体の書式やCLI名を本枝で固定しない |

判断21に従い、型・エフェクト・印・契約の意味をネットワーク・暗号・保管バックエンド・サーバから分ける。構成で変えるのは使えるモジュールと関数だけであり、外した機能は検査時に拒否する。HTTPを外した構成に認証取得や送信の受理を要求せず、対応する構成ごとの提供範囲を示す。同じ例を通すために規則の意味を構成で変えない。

## 設計者への一つの問い

共通の前提は、未対応または必要な契約を解析できない経路を含む実行入口全体を実行前に拒否することである。正当な受理・禁止する変更の拒否・成否と診断・要約の対応をそろえる条件は、選ぶ必須例すべてに課す。D5の候補(ii)では例1・2を失敗の値と同じ正常終了で扱い、その接続とD4の提供方法・未見積もりの費用は確認を要する。

IFC-D8は、0.0.14の必須例を、逐次の三例（案A）、指定なし（案B）、限定Taskと専用保管口を加えた五例（案C）のどれにするか。

推すのは案Aである。理由: 入力分類・限定した非機密化・送信条件がつながる三つの作業を受け入れ条件にできる。案Cの未見積もりの並行・保存の接続を追加せず、案Bに残る実用範囲の不確定さを減らせるが、失敗の接続やCSVの提供を未確認のまま受け入れ完了にはできない。
