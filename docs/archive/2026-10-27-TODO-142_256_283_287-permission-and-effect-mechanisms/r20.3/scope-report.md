# Scope の選択と受理の担当記録

本記録は局所解析から範囲の選択・受理までの自己点検であり、独立レビューではない。

## 接続した契約

- `ScopeBodyInput::rule_calls()` は番号付けと定数の展開に依存しない、構文順の全規則呼び出しの一覧である。定数の値式には呼び出しを許さないため、定数の展開は要らない。返す `ScopeCall` の `preorder` は未採番であり、照合しない。
- `ScopeAnalysis::required_ranges()` は同じ番号の全記録状態で規則の添字を選ぶ。記録のない呼び出しは既存の局所解析が事実のない状態で抽象引数を読み取る。`selected_ranges()` は全状態で同じ範囲を選べたときだけ非 Top を返す。
- `ScopeAnalysis.stopped` は最後の Run の状態である。内側だけの本体予算の超過から外側へ戻ったときの回復は、既存の `Enter`/`Leave` のままである。途中で失った事実は戻さない。
- 予算で最後の Run または番号付けが止まった本体では、全ての規則呼び出しに Top を要求し、非 Top の契約を `BudgetExceeded` で拒否する。Lean より保守的な選択として依頼で指定された扱いである。停止時の拒否番号は `None` とし、接頭辞の番号を表示にも使わない。
- `PipeLeft` は Lean の `acceptCall … []` に合わせて Top を要求する。検査の pattern がパイプの左辺のリテラルでも狭い範囲を得ない。
- 検査は pattern と整数リテラル・const の直接参照から選ぶ。射影と拡大は `id == success_id` を満たす同じ Ok 成功値の事実だけから元範囲を選ぶ。拡大の行き先にはこの規則から制約を追加しない。
- `accept_call()` は列の各選択位置と全状態を照合する。列の不足は `NotCovered`、未知からの非 Top は `UnknownSource`、予算からの非 Top は `BudgetExceeded` となる。Top の契約は常に受理する。列の追加位置の制約と個数は署名の型付けに委ねる。
- `ScopeInputs::lookup()` は収集時に一度作った `BindingMap<usize>` の索引で元定義の束縛から本体を読む。関数ごとに本体全件を走査する二乗の処理を避ける。補間の確定は本体の並びを変えず、この索引を維持する。Clone/Default も同じ構造を保つ。
- `accept_body()` は構文順の全規則呼び出しで最初の拒否を返す。予算以外の入力停止を規則なしや未知として受理しない。照合用の番号と事実の索引を使い、呼び出し数に対する二乗の走査を避けた。

## 補間の型と番号の確定

型制約の前には、補間に変換関数が必要かが未確定のことがある。`analyze_pending()` は未確定の変換に一時の番号ラベルを割り振り、一度だけ局所解析を行う。型の確定後、補間の変換の有無だけを共有された不変の表として更新し、`numbered()` の確定番号を `renumber()` へ渡す。

この処理は予算の数え方を変えない。`Structure::number()` は各イベントの操作を計上した後で `Event::Converter` の真偽に分岐する。真偽によって変わるのは `next` の加算だけであり、子の展開・読み取るイベントの個数・深さ・停止するイベントは変わらない。既定の番号付けの操作上限の下では番号の表現限界にも届かない。局所解析は同じ lower 命令列を同じ順に読むため、事実の保持・忘却・費用も変わらない。

`renumber()` は元の文と呼び出しの NodeId の対応から、記録の鍵、呼び出しの鍵、共有 arena 内の事実の由来、抽象引数と transfer の結果の由来を全て更新する。事実の arena の複写は全体で一度だけ行い、記録ごとの複写を避ける。確定後の受理では一時の番号を使わない。この扱いを補間の前後の呼び出しと予算0〜39の独立したテストで検査した。

## テストの棚卸し

| 位置 | 判断 | 理由 |
|---|---|---|
| `scope/tests.rs::source_preorder_keeps_nested_bodies_guards_and_named_arguments` の二つの match 腕 | 二腕の pattern を `/a/**` へそろえる | 新しい不変添字では `/a/**` と `/b/**` の二つの Result を一つの match の結果型へ統一できない。番号と名前付き引数の検査を維持するため、文字列の内容だけをそろえた。番号の独立期待値は不変である。異なる範囲の結果の拒否は統合検査が担う |
| `scope/local_tests.rs` の saved_result、direct_projections、request_ok、joins、bodies、try の6件 | `rejected_source` を明示し、E0519 が1件以上あり、誤りは E0519 だけであることを要求する | 別名・再包装・未知呼び出し・合流・本体境界・無記録位置で非 Top の成功値を射影する入力は、新しい必須判定が拒否する。非受理の入力でも局所解析の事実と忘却の独立期待値を検査する目的を維持した |
| `scope/local_tests.rs` の `other: Scope.PathIn` と `other: Http.RequestIn` | Top の注釈を維持 | 別個体が未知であることの検査であり、期待型から所属を得ない |
| `scope/accept_tests.rs` の4件 | 追加 | 範囲の被覆と理由、予算位置より後の呼び出し、PipeLeft、補間後の全ての鍵の更新は既存の局所解析テストでは検査しない |

## 検査と初回の失敗

最初の `cargo test -p benitoite --lib typeck::scope --no-run` は、並行作業中の IR の重複した ranges と未追加の型検査出力 call_ranges で終了101となった。続くコンパイルは親担当の scoped_calls の追加途中、次は内部診断の引数型で終了101となった。Scope のコードのコンパイルエラーはなかった。誤って `--no-default-features --no-run` の同等のコンパイルも一度開始した。特殊構成のテスト全件の実行には数えない。

初回の Scope の21件は14成功・7失敗（実行部分1.44秒）であった。6件は型制約の解決の順序のため本来の E0519 より先に E0401 となる問題、残り1件は同じく解決の順序で E0403 となった。親担当が解決の順序を直した後、20成功・1失敗となり、残る番号のテストの異なる match の範囲を上表どおり追随した。E0401 や E0403 を許容する期待値にはしていない。最後の結果と所要は `scope-focused.json` と `scope-focused.log` に残す。

## 自己点検と申し送り

Lean の `ruleDeclarations`・`checkRule`・`projectRule`・`widenRule`・`argIndex`・`Required.ofIndex`・`acceptRanges`・`acceptCall`・`acceptBody` と照合した。今回の範囲の受理に `atomicCoverOnly` はなく、一原子どうしの `NotCovered` を返す。原子の和に関する理由は既存の効果の受理が担う。

R20.5 は採用する予算の測定と全体の扱いを閉じる。補間の確定前後に番号付け費用が変わらないことを維持する。R20.4 は節の添字の選択、R30 は新七 IO の実登録、K10 は未採番の拒否番号の表現と非 Top の全交換比較を照合する。今回の局所検査を全比較の成功とは数えない。

Lean・scripts・依存・git の状態を変更していない。言語の値の保持・確保器・根・障壁・安全点を変更していない。新しい CARGO_TARGET_DIR と target 外の一時ビルドを作っていない。削除対象はない。private と docs/todo を読んでいない。
