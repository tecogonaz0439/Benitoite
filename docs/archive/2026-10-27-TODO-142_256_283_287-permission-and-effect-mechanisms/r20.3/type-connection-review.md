# 型制約への接続の補助レビュー

取りまとめから依頼された読み取りの点検である。`typeck/scoped_calls.rs` と context・solve・decls・generate・calls の接続を、`ScopeAccept`・`CheckAccept` の受理の規則と照合した。本番とテストは変更せず、実行の追加も行っていない。これは今回の実装に対する補助レビューであり、取りまとめが別に行う正式な独立レビューを代替しない。

## 指摘

| 番号 | 重さ | 箇所 | 問題と修正案 | 確認の状態 |
|---|---|---|---|---|
| F1 | 中 | `scoped_calls::resolve` の最終の fallback と `solve.rs` の再訪 | 初稿は未確定の一件だけを fallback で確定し、残り全件を毎回走査していた。独立した未注釈の検査 N 件でも、false/true の再訪で N+(N−1)+… の二乗の走査になる。検査の成功型は Scope の入力値の型に依存しないため、検査の producer を一括で確定し、次の再訪で射影・拡大の候補を読む二相にする | 指摘を受け、取りまとめが `Pending.check` と `checks_pending` を使う一括処理へ変更した。変更後の読解では、一件ずつの fallback による二乗の再訪はなくなった。新しい性能測定は行っていない |
| F2 | 中 | `decls::check` の本体走査と `scoped_calls::accept_program` | Rust は AST 上の Fn/Impl の順に解析を保存し、その順で受理していた。Lean の `CheckAccept.acceptProgram` は `names.defs` の全件を先に受理し、その後に `names.impls` の全メソッドを受理する。impl が先に書かれた入力で両方が E0519 になると、最初の拒否名が異なる。解析はそのままにし、受理する本体を通常定義／実装メソッドに安定して分け、通常定義を先に判定する | 取りまとめが受理の本体を安定した二群に分ける修正を実施した。`scoped_calls::acceptance_checks_definitions_before_implementation_methods` を含む局所の24件は成功した |
| F3 | 中 | `scoped_calls::accept_program` の停止した本体の入口 | `analysis.stopped` が予算以外の停止でも、入口は `input.rule_calls()` を走査するだけである。収集できた呼び出しが空なら、判定を一度も呼ばず次の本体へ進みうる。`ScopeAnalysis::accept_body` には非予算停止を最初に拒否するガードがあるが、この入口はそれを使っていない。renumber の前後に非 BudgetExceeded の停止を必ず内部の診断へ変換するガードを置く | 取りまとめが renumber 後に非予算停止を内部の診断へ変換するガードを追加した。読解で確認した。通常のソースでの到達は未再現のままである |
| F4 | 軽 | 同関数の `body.spans.get(&call.node)` | 拒否を得ても span がなければ診断を追加せず return する。現在の正常な経路では `scope_shape` が全ての直接の呼び出しの span を保存するため、入力が整合していれば到達しない。将来の収集と型生成のずれを成功へ変換しないため、欠落時は内部の診断を必ず追加する | 取りまとめが span の欠落時も必ず内部の診断を追加する修正を実施した。読解で確認した。到達例は未再現である |

F2〜F4 は規則や保証を変更する必要のある指摘ではない。既存の Lean の順序と入力の完全性へ合わせる実装上の修正である。

## 問題がなかった点

- 局所解析は `prepare_scope` で本体の型制約生成より前に一度だけ実行する。最終の `renumber` は補間の型が決まった後の番号ラベルだけを写し直し、事実と局所解析の費用を再計算しない。
- 直接の標準の呼び出しの同定は `active_scope_call` と登録済みの `ScopeCall.binding` を照合する。関数値・間接呼び出し・穴のある部分適用は対象の ScopeCall がないので、標準署名の個数の Top を明示して具体化する。パイプの右辺は規則の対象であり、選択は PipeLeft の Top に従う。
- `scope_shape` は対象の不透明型だけを一時的な型変数にし、利用者の範囲変数を作らない。候補を取り出す `candidate` は認定された種類の不透明型・型引数なし・閉じた範囲に限る。未知の成功値へ型注釈を付けても、最後の `analysis.accept_call` で unknownSource を拒否する。
- 引数の不変の添字は通常の型の等しさで照合される。規則が選んだ範囲より狭い成功型を注釈から得た場合は、受理の被覆で拒否する。規則が選ぶ位置の契約がその範囲を覆うことと、型の等号の不変性を混同していない。
- widen の元は同じ一時的な source の候補から読み、行き先は destination の期待型から読む。行き先が未確定なら E0407 として拒否し、Top を既定の行き先として補わない。確定した列は `RangeSignature::admits` にも通すため、行き先による元の範囲の被覆を確認する。受理の規則は行き先の位置へ追加制約を置かない。
- 最終の受理は全ての記録状態を `ScopeAnalysis::accept_call` で確認する。範囲の列が不足すれば notCovered、事実のない位置では Top だけを受け入れる。予算超過時は番号に依存しない全呼び出しの一覧を使う。
- `decls::check` はトップレベルの全関数と実装の全メソッドに同じ `check_function` を使い、`finish_scope` が本体の解析と確定列を保存する。型・宣言の誤りがすでにあるプログラムは成功の受理には進まない。
- 本体の後の警告と区間解析は、局所解析の入力・範囲候補・受理の結果へ戻らない。型確定後の補間の変換の有無は番号ラベルの確定にだけ使い、必須の判定の事実を警告から得る循環はない。
- `prepare_scope` と `accept_program` の元本体の `.iter().find` は定義数と本体数の積の走査だったが、Scope 担当が `ScopeInputs::lookup(binding)` の索引を追加し、取りまとめがそれを使う形へ変更した。呼び出し位置の記録も fact_indices の索引を通しており、各呼び出しの受理で全記録を走査しない。

## 差として残る範囲

予算で停止した本体の全規則に Top を要求することは、今回の依頼で了承された Rust 側の保守的な判定である。未完成の番号を根拠にした狭い契約は受理しない。Lean の規則・主定理・前提を変える必要は見つからなかった。F2 の拒否順序の差は、許される保守的な差とは分けて上に指摘し、修正と局所の検査で確認した。
