### 判断 2 用語

【決定】総称は情報フロー制御（information-flow control）、型による方式はセキュリティ型システム（security type system）、性質は非干渉性とする。機密性の印を下げる操作は非機密化（declassification）、完全性の印を上げる操作はエンドースメント（endorsement。信頼の付与、または完全性レベルの引き上げ）とする。これらを「情報の流れの型」「開示」「検査」という独自の訳語へ置き換えない。

理由: 設計者が選んだ術語にそろえ、既存の「静的検査」「検査済みの値」との混同を避ける。

出どころ: README「用語」「訳語」。出典と訳語の選択の経緯も同節を参照する。情報フロー制御の用語を現行設計書の用語集へ入れる時期は 0.0.14 とする。

### 判断 3 角括弧と複数対象の略記

【決定】範囲を `File.Read["/data/**"]`、`File.Write["/data/reports/**"]`、`Http.Connect["api.example.com", 443..445]` と書く。ポートの一点は `443` と書く。名前だけの原子はその種類の全対象（Top）の上限である。範囲引数は閉じたリテラルに限り、式、補間、定数参照、範囲変数、否定、一般の述語を認めない。

`File.Write["/data/a/**", "/data/b/**"]` のように一つの角括弧へ複数対象を書く略記を認め、構文解析で原子の列へ展開する。型に用いる `Scope.PathIn`・`Http.RequestIn` の範囲は一つのままである。`Failure.Fail[E]` は引き続き型を引数とし、範囲引数と区別する。二つ目以降の `uses` の修飾と最長一致、`uses A, List[Integer]` に対する既存の E0209 を保つ。

同名の異なる範囲を別原子として保持する。同じ原子の明示重複は、略記の展開後も既存どおり誤りとする。推論結果の合併で構造重複を取り除くこととは区別する。ファイル単位の宣言上限を局所の推論やハンドラで取り消さない。

理由: 名前の直後に対象を示し、同じ構造の原子列で既存の行の規則へ接続する。範囲の指定と型引数を混同せず、冗長な契約も構造として保存する。

出どころ: README Q1・P2、[language-rules A1](study/language-rules.md#a1-uses方針の対象表示の書き方q1q11決定済みの旧-r18) と「決まっていること」旧 R18。ネットワークの複数組の具体的な文法と fmt の細則は DET-02 を参照する。

### 判断 4 対象の領域と字面の上限

【決定】パスは絶対形式の完全一致と末尾 `/**` の木、ホスト名は完全一致・`*.` のちょうど一段・`**.` の一段以上、ポートは `0 ≤ lo ≤ hi ≤ 65535` の閉区間とする。木は幹自身を含み、ホスト名の両ワイルドカードは幹自身を含まない。`/data/**` は `/database` を含まない。既存 Scope のパス・ホスト名の形式の規則を土台にし、IP アドレスの正規化した IPv4・IPv6 の完全一致と CIDR を追加する。

保証の対象は正規化した API 引数の字面である。パスのリンク解決後の実体、DNS 解決先、OS の隔離を保証へ加えない。パスの相対形式、`.`・`..`、空要素など既存の不正を、補完して狭い範囲として受理しない。既知の不正な注釈は拒否し、Top へ置き換えて受理しない。動的入力の検査は実行時にも行う。

理由: 純粋な検査の意味を保ち、静的な字面の上限と後の実体の照合を分ける。IP の直接指定は LAN の HTTP 接続に必要である。

出どころ: README Q1・Q3、[language-rules A2](study/language-rules.md#a2-閉じたパターンと正規化q1q3)・A8。IP の入力制限・正規形・CIDR の細則は明示的に未採択の案であり DET-01 に置く。

### 判断 5 構造の等号と保守的な被覆

【決定】扱い1を採る。型の等号は正規化した原子の構造と並びの一致であり、範囲の包含とは別の関係である。範囲の包含は、左の各原子を右のいずれか一原子が丸ごと覆うことで判定する。Top は同じ種類の全対象を覆い、別の種類・Fail・未確定の行変数を範囲原子で覆わない。Fail の型と行変数の規則は保つ。

正規化は構造の整列と重複除去に限り、広い原子に包含される狭い原子を消さない。相互包含から型の等号を導かない。一原子を複数原子の和で覆う完全な判定は行わない。例えば `0..9` を `0..4` と `5..9` の和で覆ったと判定できない場合を、仕様と診断へ明示する。

理由: 等号が必要な代入・合成の補題を構造の一致で保てる。意味上同じ集合でも判定が通らないことを、対象が必ず範囲外であることと区別できる。

出どころ: README P2、[language-rules A3・B1](study/language-rules.md#a3-包含不完全性診断q12q13)、[SA §3・§7](spikes/SA/findings.md)。比較した扱い2の詳細は SA に置く。

### 判断 6 範囲を添字に持つ標準値型

【決定】旧 `Scope.CheckedPath`・`CheckedHost`・`CheckedEndpoint` を保ち、新しい公開型は `Scope.PathIn[R]` と `Http.RequestIn[H,P]` に限る。ここで R と H,P は閉じた範囲を説明するメタ記号であり、利用者が宣言する範囲変数ではない。裸の新型は Top を表す。値型の添字は一範囲であり、和や部分的な省略を認めない。公開の `HostIn`・`EndpointIn` は加えない。

値型の添字は不変である。`PathIn["/data/a/**"]` と `PathIn["/data/**"]` を暗黙に同じ型にせず、包含を静的に確認した場合の失敗しない明示拡大を設ける。拡大は同じ対象・同じ要求を保持し、戻り値の注釈から行き先の閉じた添字を一意に決める。狭小化と包含未確認の場合には再検査を要する。一般の `Ty.Le` に非関数の共変を加えない。

新型は利用者が構築・更新・表現パターンで分解できず、自動アクセサで内部を取り出せない標準型として登録する。一般の `@opaque` レコードへ値添字を導入しない。内部表現の再利用と所属不変条件の対応は実装と証明で示す。

理由: 所属を値の受け渡しに保ち、既存の非関数の型の包含から等号を得る規則を維持する。明示拡大により、広い上限へ渡すだけの再検査を避ける。

出どころ: README Q4・Q6、[language-rules A4](study/language-rules.md#a4-範囲を持つ値と新しい-io-の入口q2q4q7)。明示拡大と射影の公開名・完全な署名は DET-03 に置く。

### 判断 7 検査の具体化と HTTP 要求の保持

【決定】新しい純粋な検査は、認定した標準関数の直接呼び出しに限って閉じた範囲を具体化する。条件にはリテラルと、既存の定数評価で値が分かる `const` の直接参照を使える。局所 bind の一般的な定数伝播、任意の純粋関数の実行、期待型から未知の条件を逆算する推論は加えない。間接呼び出し、関数値化、穴のある部分適用、pipe から狭い戻り型を得ない。旧検査関数の関数値としての使用は保つ。

未知の条件の成功値は Top の型になるが、その動的条件の検査を省かない。新しい純粋な検査の成功を `delta_typed` に接続し、型の添字への所属を保存する。旧成功値から新型への無検査変換は加えず、認定した射影で条件を得ても新検査を残す。

`Http.RequestIn` は検査した同じ要求と実効 host/port を不透明に保持する。URL の更新には再検査を要する。新送信はリダイレクトを追わず 3xx の応答を返す。純粋な要求検査の失敗は専用の `Http.RequestCheckError`、通信の失敗は従来の `NetworkError` に分ける。

理由: 値引数から得る所属と期待型の注釈を取り違えない。要求と検査済み endpoint を別の値として受け取ることによる対象の食い違いを避ける。

出どころ: README Q5・Q7、[language-rules A4・A5](study/language-rules.md#a5-scope-の成功の局所解析と公開契約q5決定済みの旧-r12r13)。検査 API 名、誤り型の構成子、scheme とポートの細則は DET-03・DET-04 を参照する。

### 判断 8 最初の範囲付き IO の七操作

【決定】次の七操作を既存の種類の新しい操作として登録する。操作の集合と型契約を決定とし、公開名と契約引数名は、検査・射影・拡大の名前とともに DET-03 の未決とする。表の名前は A4 にある候補名である。R、H,P は一つの閉じた範囲または Top を表し、型・引数とエフェクトの添字は同じ範囲を指す。

| 操作の候補名（未採択） | 型契約 |
|---|---|
| `File.readTextIn` | `function(path: Scope.PathIn[R]) -> Result[String, IOError] uses File.Read[R]` |
| `File.readBytesIn` | `function(path: Scope.PathIn[R]) -> Result[Bytes, IOError] uses File.Read[R]` |
| `File.writeTextIn` | `function(path: Scope.PathIn[R], text: String) -> Result[Unit, IOError] uses File.Write[R]` |
| `File.appendTextIn` | `function(path: Scope.PathIn[R], text: String) -> Result[Unit, IOError] uses File.Write[R]` |
| `File.writeBytesIn` | `function(path: Scope.PathIn[R], content: Bytes) -> Result[Unit, IOError] uses File.Write[R]` |
| `File.appendBytesIn` | `function(path: Scope.PathIn[R], content: Bytes) -> Result[Unit, IOError] uses File.Write[R]` |
| `Http.sendIn` | `function(request: Http.RequestIn[H,P]) -> Result[Http.Response, NetworkError] uses Http.Connect[H,P]` |

旧 String の IO、旧 Checked 型、Unofficial の import、`IO.All` の展開は保つ。新型と純粋な検査も同じ標準の所有元で認定し、同じ綴りの利用者関数を認定しない。通常の `.bnt` ラッパーから旧 IO を呼んだだけで Top を消したことにしない。Rust の実処理は共有できるが、新署名と同じ対象を使う接続を設ける。

新 IO の関数値は、明示された期待型の入力が一つの閉じた添字を決めるときに具体化できる。決まらない場合は、入力・結果・効果を明示したラムダを求め、添字について未確定の多相な関数値を作らない。

`readLinesIn` 等の追加操作、再帰・中間親・二対象・資源の保持が要る操作、Reader/Writer、Listen、Process、Console、Clock、Random の範囲付き版は必須集合に加えない。旧操作は Top のままとする。

理由: 単一対象で完結する最小の集合を固定し、その入力所属と実 IO の対象をつなぐ。旧入口の使用まで新しい検査済み値を必須にしない。

出どころ: README Q2(a)・Q6、[language-rules A4・A7](study/language-rules.md#a7-互換性の帰結と組込み構成決定-q2)。

### 判断 9 成功値の局所解析と公開契約

【決定】解決済みの標準の所有元・関数・契約引数位置を確認し、直接の検査または一度保存した Result の由来から、`Result.Ok` の同じ成功値番号へだけ条件を結び付ける。同じ成功値の直接射影だけを認定する。別個体、別名、再包装、未知の呼び出し、値の合流、本体の境界では局所由来を忘れる。ラムダ、handle の保護本体と節、Task の入口も局所由来を初期化する。型に既に明示された添字は通常の型として保つ。

認定不能と予算超過は Top と理由を返し、狭い契約が必要なら包含未確認として拒否する。後段の区間警告の解析結果を、先行する型の受理条件へ流用しない。共有する基盤は `BindingScope`、標準認定、引数位置、成功値の識別、忘却の小さい操作に限り、既存の `RangeState` 全体を作り直さない。

公開・非公開を問わずトップレベル関数の引数型・戻り型・エフェクト上限を明示する既存規則を保つ。ラムダと局所呼び出しは推論するが、本体から公開契約を自動的に拡大しない。

理由: 同じ成功値に関する根拠だけを狭い型に使い、注釈を信用した受理を避ける。契約を検査する解析と、未知を誤りと断定しない警告解析の役割を分ける。

出どころ: README P3・Q5、[language-rules A5](study/language-rules.md#a5-scope-の成功の局所解析と公開契約q5決定済みの旧-r12r13)、「決まっていること」旧 R12・R13。

### 判断 10 行多相と型の包含

【決定】既存のエフェクト変数は範囲原子を含む行全体へ具体化する。閉じた範囲は型代入で変わらず、行代入は元の範囲原子を保つ。範囲変数を新設しない。最外側の関数のエフェクトの拡大は認め、入れ子の関数型、List の要素、新しい標準値型の添字へ暗黙の共変を広げない。

理由: 既存の高階関数が行を受け渡す規則で足り、型の等号と範囲の包含を別の制約として保てる。

出どころ: README P2・Q4、[language-rules A6](study/language-rules.md#a6-エフェクト変数高階関数ハンドラq8q9)。

### 判断 11 名前全体のハンドラと節の添字

【決定】名前を除くのは、その名前の全操作の節がそろうときだけである。範囲の一部だけの処理を加えない。節自身の IO は出力の上限へ加える。節が別の対象へ書けば、その対象を外側へ残す。

新操作の節の引数には、節を検査する前の保護本体の効果から、同名の閉じた一原子 S だけがあれば S を与える。複数原子、同名 Top、未確定の行変数、同名原子なしの場合は Top とする。節の本体や期待される出力から S を逆算しない。同じ値の R への所属と R の S への被覆から S への所属を得る専用補題を使い、一般の値型の共変へ広げない。

七操作を追加した後、旧 `Http.send` の節だけのハンドラは部分ハンドラとなり `Http.Connect` が残る。0.0.12 で旧11操作をすべて処理した `File.Read` の完全ハンドラと旧12操作をすべて処理した `File.Write` の完全ハンドラも、操作の追加により部分ハンドラとなり、それぞれのエフェクトが残る。この仕様上の帰結と不足節を、現行仕様の反映と改造の記録に残す。CHANGELOG に書くかは DET-09 の回答に従う。契約や許可を自動で広げず、旧節から新節を合成しない。`0.1.0` の公開までは移行案内・移行例を一切作らない。ワンショット、節を外側で実行する意味、State を処理できないこと、行変数を除けないこと、Task が継承する節を末尾再開に限る規則は保つ。

理由: 捕捉前の入力所属を節で使え、節が実際に行う別対象の IO も上限へ現れる。新操作の追加と、既存の全操作の網羅規則を整合させる。

出どころ: README Q2・Q8、[language-rules A6・A7](study/language-rules.md#a6-エフェクト変数高階関数ハンドラq8q9)、[SK §4](spikes/SK/findings.md)。

### 判断 14 保証と後の宛先の契約

【決定】静的な上限の記述と検査成功は操作の許可を意味しない。範囲は内容の流れ、意図との一致、IO の成功、停止、外部コマンド内の操作を保証しない。実行時の権限制御をサーバモードより先に単独で入れず、隔離はそれまでハーネスと OS に委ねる。

`Http.Connect` の範囲は host/port の組であり scheme を持つ origin とは異なる。後の情報フロー制御へ渡す R は http/https の両方の可能性を覆う保守的な上限とする。https の origin だけを許す契約を host/port の一致だけで満たしたことにせず、scheme の精度は別の要求契約で足すか、両方を覆う必要を残す。

理由: 対象の型の上限と許可、情報の分類、実体への強制を混同しない。scheme のない範囲から余分な精度を導かない。

出どころ: README Q3・Q10・版の割り振り、[language-rules A8](study/language-rules.md#a8-保証の範囲と後の情報フロー制御への受け渡しq3q10)。

### 判断 15 対象一致の信頼条件と証明する対象

【決定】`io_target` を、引数の対象と実際の事象の対象を結ぶ、計画済みの信頼条件として明示する。範囲付きの単一対象 IO は具体化済み署名の対象と同じ対象だけを使う。旧 Top の IO はリダイレクト・再帰・複数対象を含む同じ操作種類の全対象として扱う。対象ありの操作を対象なしと報告せず、追加の対象を隠さない条件を全 IO に課す。

入力の所属は値の型付けと純粋な検査の保存から、事象の初期上限への所属は `io_target`・被覆・同じ効果の保存から導く。対象健全性そのものを仮定にしない。`io_op` は名前だけの単集合から、具体化した入力添字・効果・対象位置の対応を検査する形へ変える。元の操作名、`opEff`、`neffs = 0`、全操作一覧への所属を保ち、任意の効果を許す条件へ緩めない。

進行・保存・空効果の健全性・脱糖の型保存の既存の結論を保ち、一段と到達先からの対象健全性を別に証明する。多段の言明は初期の同じ ε を保つ。`delta_typed` は新純粋な検査の所属を含む結果型保存、`io_typed` は応答の型、`io_exists` は応答の存在であり、対象の定理を抱き合わせない。純粋な検査と七 IO を既存欄の対象となる表へ加えることは、新しい信頼条件の欄の追加に数えない。既存欄の意味を変える場合と、計画済みの `io_target` 以外の欄を加える場合は停止条件に当たる。`io_op` の内容の変更と `io_target` の追加を前提の変更として列挙し、引数名が同じことを前提不変の根拠にしない。

理由: 検査済みの値だけでは、実装が別の対象へ作用しないことを導けない。小モデルの成功と、Rust・OS の実装を証明したことを区別する。

出どころ: README P1・SK の結果、[language-rules B2・B3](study/language-rules.md#b2-io_op-と-io_target-の分離)、[SK §3・§5](spikes/SK/findings.md)。信頼条件を構造体にどう分けるかは L00 のレビュー事項である。

### 判断 17 利用者エフェクトは Q9 の (c)

### 判断 18 権限の判定の独立小モデル

【決定】docs/todo の TODO-256 の第一項は、操作の種類について、事象⊆宣言上限と宣言上限⊆方針から事象⊆方針を導く独立の系にする。第三項は抽象対象述語の `Allow(k,t) ∧ ¬Deny(k,t)`、deny 優先、追加方針との共通部分による狭小化、空対象と種類判定の分離を扱う。

理由: 種類の静的な判定と対象の方針の代数を小さく検査できる。独立モデルを本番の実行時強制や非干渉性の証明の代わりにしない。

### 判断 21 実装と提供の境界

【決定】範囲の代数と型・エフェクトの規則を、ネットワーク、暗号、Wasmtime、サーバの依存から分ける。構成で変えるのは使えるモジュールと関数の集合だけとし、外したモジュールを検査時に拒否する。同じ原子の意味を構成で変えず、64ビットのポインタ幅だけを前提にした表現を増やさない。

最初の勧告照合の設計者の判断は「組み込まない」である。今回に依存やツールチェーンの更新を加えない。候補の再照合での新しい勧告・未照合は表示・記録・報告とし、それだけを検査不合格や受け入れ停止の条件にしない。

理由: 組込み向けの分離を保ち、範囲を導入する改造と更新の判断を混ぜない。

出どころ: AGENTS.md「改造の設計で守ること」「テストの運用」、[language-rules A7](study/language-rules.md#a7-互換性の帰結と組込み構成決定-q2)、[security-advisories.md「評価と設計者の判断」](security-advisories.md#評価と設計者の判断)。
