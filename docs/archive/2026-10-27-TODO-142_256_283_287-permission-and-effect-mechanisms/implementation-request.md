## 時間の扱い

> 時間: この枝の見込みは〈plan.md の該当する行の見込み〉である。着手時の点検では見込みを理由に止まらない（分けるべきと考えたら、進めたうえで区切りを提案する）。作業中に見込みの上端の2倍を超えたら、ビルドと検査が通る区切りで止め、閉じた範囲・残り・その時点の所要時間を results.md に書いて報告する。

2倍を超えたことに気付いた時点で原因と残りを調べ、途中報告する。通る区切りへ戻すことができない場合は、その事実と失敗を隠さず報告し、成功した扱いで次の枝へ進めない。時間の超過を理由に保証・検査を緩めない。独立した停止条件に当たった場合は時間の残りにかかわらず停止する。

見込みは能動時間（設計・証明・実装・文書修正などに担当が作業する時間）であり、検査・測定・レビュー・設計者の回答待ちは別に記録する。実績の外側の時間には作業末の検査を含め、能動時間と混同しない。各枝の取り込みで取りまとめが [time-policy.md](time-policy.md) の表を追記する。過去の短い実績だけで担当が見込みの幅や依頼範囲を変えない。

## 作業ごとの検査

途中は関係するテストだけを直接実行し、末尾はplanの当該workを一度実行する。Rustの既定lib全件・関連統合テスト・clippy・fmtはその入口へ任せ、別に重ねない。R10/R20 の共有型と R30 の標準ライブラリの変更は全ての入力読者を対象にし、既定では全統合ターゲットを選ぶ。L の work も原則を自動分類とし、01-12/07-04 の例・集計の選択を dry-run で照合する。対象を狭める必要があれば、先に取りまとめが根拠と新しい割り当てを計画へ記す。文書・Python/シェルだけ・Leanだけの枝にRust全libを追加しない。

実行前に種類と対象を報告し、同じ基準と指定のdry-runで選択と理由を確認する。長い検査、heap、全件の特殊構成は見込み時間も示す。長い新規実行は短い局所試行の所要から取りまとめが見込みを更新し、必要な了承を得てから始める。既に了承された範囲と、benchmarkのshortの手順を優先する。

ヒープの不変条件や安全点を越える値の保存を変えた枝は、compile_failを含むdoc、局所heap-verify/gc-stress、必要なcheck-heapを次の利用側の前提にする前に通す。既存の表現を使うだけで不変条件や保持を変えない場合は、対象外にできる差分の根拠を結果に残す。必要な検査を最終のchangeへ送って完了にしない。

stageは新しい接続だけ、changeは改造全体の回帰、releaseは実際の候補との照合である。自分の作業の完了のために後の全件検査を先取りしない。同じ状態の検査を引用する場合は07-03の条件を満たす。失敗や追加変更の後は古くなった検査だけを再実行し、最初の失敗と修正も残す。期待値・入力の大きさ・ignore・時間制限を実行時間短縮のために緩めない。テストを書く・変える際には、リンク先を確認して読める公開のtest-auditの作成時の関門を通す。

依存の勧告の検査は、二manifestに共通deny.tomlとlockedを使い、勧告あり・照合済み0件・照合不能を対象別に分ける。勧告あり・取得不能・道具不在は表示・記録して終了0、設定の誤り・実行器の不具合は終了1である。生の出力、対象別の結果、DB/lock/日時/構成を結果の隣へ保存する。新しい勧告は取りまとめへ報告し、取りまとめが設計者へ報告して次の改造の最初の判断へ引き継ぐ。検出だけで候補の受け入れを停止しない。

分類不能・基準不明で終了3になったら、該当ファイルまたは基準、停止までに選ばれた検査と不足する対象を示す。計画の名指しがあればその指定で進め、なければ取りまとめを通じて設計者の続行方法の判断を待つ。指定の誤りの終了2は計画を直す。名指しの部分選択の終了0を、水準全体の完了と呼ばない。releaseも自動の終了0のほかに候補・版・同梱物・実CLIの手動照合が要る。

short性能比較は取りまとめが処理系の取り込みごと、少なくとも段の区切りごとに行う。担当が別の測定器を作らず、必要なシナリオを結果へ申し送る。長いtargets/fullを担当が追加して開始しない。利用者向けの保証は静的な上限に限り、型の範囲を許可・実体の隔離・情報の流れの制御と説明しない。

PM の独立 Lean モデルは単一ファイルの終了0だけを成功とせず、plan の出力検索で sorry を拒否し、全 theorem/lemma と使用定義の #print axioms から sorryAx と未承認の公理を拒否する。R10/R30 は機能を外す境界・32ビット・代数の依存方向をレビューする。現行の入口にない構成の実ビルドを確認済みとしない。LR-U5 の URL 解析器は R30/K10、LR-U7 の外部ハンドラの件数と未確認は R30/V10 が引き継ぐ。具体的な観点と制約は plan の検査表を正とする。

## 結果の書き方と完了報告

普通のresults.mdは、次の欄を短く記す。

| 欄 | 内容 |
|---|---|
| 作業と状態 | 作業ID、B_WORKの完全ID、必要なら段の基準。閉じた範囲と未完の範囲 |
| 変更と接続 | 守った契約、変更したファイル、生成元と生成物、現行設計書への反映。未接続を成功としない |
| 検査 | 正確なコマンド・構成・対象、dry-runの選択、終了状態、外側の経過時間。生ログを同じディレクトリへ置く |
| 最大常駐量 | 作業末の検査を計時で包み、OS の time が示す最大常駐量（RSS、resident set size）の原値・単位とMiB（2^20 バイト）/GiB（2^30 バイト）の換算・計測方法を記す。並行しないプロセスの最大値と一括実行全体を区別する。取得不能は理由を書き、監視が捕捉しなかった0を実使用0としない |
| 失敗と修正 | 初回の失敗、原因、修正、必要な再実行。失敗を消して最終0だけを残さない |
| ずれと申し送り | 計画からのずれ、未決・停止条件・後続の担当と時期、取りまとめが転記すべき条件。docs/todoへ担当が直接書かない |
| 時間 | 開始/終了と外側の所要、分かる範囲の能動時間、検査/測定/回答待ち、上端2倍の報告と区切りの有無 |

検査の具体的な計時方法もplanの表を正とする。macOSでは外側のtimeの最大常駐量を残し、Linux等の別機を使う場合は道具・単位の差を明記する。手元の絶対パスは公開の記録へ保存せず、リポジトリ・ホーム・一時ディレクトリをプレースホルダへ置き換える。

結果を別の状態へ引用する場合だけ、07-03「結果の保存と引用」の全欄を追加する。基準とHEADの完全ID、差分の有無と一覧、入力・期待値・生成元/生成物・設定・交換器・manifest・道具/固定版、件数と成功/失敗/無視/除外、終了・時間・環境制限、元記録と以後の変更、関係状態が一致する理由、判断者と日付を記す。別状態への引用には未コミット差分と未追跡入力のSHA-256も保存する。実施しなかった検査は担当と時期を明記し、その枝が受け持つ失敗を後へ送って完了にしない。

最後に、変更とその目的、検査と結果、最大常駐量、計画からのずれ、未決/未完、後続への申し送りを日本語で短く報告する。残りの検査・測定・レビュー・受け入れを示す場合は、見込み時間を一つの表にまとめ、不明は不明と書く。実装の成功と設計者の受け入れ、公開の操作を区別する。
