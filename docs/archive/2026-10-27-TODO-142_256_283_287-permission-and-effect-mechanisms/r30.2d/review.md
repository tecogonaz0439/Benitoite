# 担当間のレビュー

Rust・Pythonの実装担当とは別の担当が、設計、両実装、テスト、互換と文書を読み取り専用で確認した。実行の証拠は results と各ログに分ける。取りまとめによる独立レビュー・受け入れはこの担当間の確認で代替しない。

| 確認点 | 対応 |
|---|---|
| 型と効果の添字、署名の範囲の情報 | `ix`・`rkinds`・`admission`・`shape` を保持し、宣言・依存・カスタム・Trait実装の意味ハッシュへ含めた |
| 利用者の設定キーの誤整数化 | 有効な `json.keys` に bits/family 等がある場合の失敗を再現し、範囲の文脈だけを整数化するよう修正した |
| inventory/hashだけの版変更による移行 | 旧版記録の `migration` が null になることを確認し、旧記録と `semanticHashesComparable: false` を保持する条件へ修正した |
| 非ASCIIの添字の整列 | Pythonも `ensure_ascii=False` とし、`/z` と `/あ` の独立期待値へ照合した |
| shape の参照 | 番号・種類だけでなく範囲変数列、対象と効果の添字、効果の形の整合を検査する |
| 旧承認 | 旧manifestは拒否し、旧本文を認証して新previewを要求する。receiptは正確なmanifestと記録のハッシュに結び付ける |
| 生成器の対応範囲 | 範囲変数を持つカスタム署名と非Topの未対応注釈を理由付きで拒否する |

最初のレビューで提示した「IPのbitsが1と10なら中間文字列と最終整数で順序が逆転する」という反例は誤りだった。bitsの後にはfamilyに先立つカンマがあり、両形式とも1→10となる。最終JSONで整列する変更は契約を明示する整備として残し、旧不具合の再現済み修正とは扱わない。Rustテストの誤った順序期待値も訂正した。同じnominal型の異なる範囲を二つのFailure型にする入力はE0514で拒否されるため除いた。これらの失敗ログは保存した。

再確認時点で未解決の指摘は0件である。その後のW-Rで検出されたclippyの二箇所は、enumの分岐を列挙して修正した。型の表の範囲の種類は既存の分岐で一緒に計算し、意味とJSONの契約は保つ。

W-Rが後で検出したゴールデンの差は、Traitへimportと空行を加えたことによるsecondaryの2行・35バイトの移動だった。原文のShowのバイト範囲を独立に確認して期待値だけを追随した。診断コード・文言・primaryは保ち、局所フィルタは成功した。
