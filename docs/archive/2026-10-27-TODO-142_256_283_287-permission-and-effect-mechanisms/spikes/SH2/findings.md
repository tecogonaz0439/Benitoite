2026-10-27。対象は docs/todo の TODO-287 と、S1「Lean の小モデルの試作案と見積もり」の二行目である。
設計者の決定 P6 に従い、0.0.13 に含める、本番を変更しない任意の試作として行った。

**指定された小モデルの範囲を満たした。案2 は後の重い候補と学習の題材に残し、0.0.13 の中心にはしない。**
SH を拡張し、精緻化（elaboration）の型・効果の保持、元の評価との値と記録（trace）の一致を一般の定理として証明した。

### 効果集合の等号が表すもの

`elaborate_typing` の結論は `FTyped (elaborate t) (drop .local e)` である。
結果型 `a` は変換関数の型でも保持し、出力の効果は `e` から Local を除いた集合そのものである。
`remaining_effects` は、Local 以外の任意の `op` について `drop .local e op ↔ e op` を示す。
したがって、Emit と Other に加え、外側で残る Ask も型から余分に除かない。
内部だけの Ask の除去は、元の `HTyped.local` の規則ですでに表している（124〜126 行）。

ただし、この等号は**選択した効果の上限の変換**についてのものである。
両方の型付けに弱化があるので、木が持つ最小の効果集合の等号や、各操作が必ず実行されることは述べていない。
型保存だけなら、操作を余分に消した変換にも大きな上限を付けられる場合がある。
実際の動作については、節点の保持と `eval_agrees` を別に示した。
`AlgTyped` も上限の契約なので、二つの誤変換をその契約だけで排除するとは主張しない。

### 評価の一致と観察の制約

`evalH` は `elaborateWith`・`handleReader`・`run` を呼ばず、元の木を直接評価する。
Local の内部を局所値で評価してから、元の外側の値で後続を評価し、記録を連結する（158〜161 行）。
`eval_agrees` はこの評価と、精緻化後を一階のハンドラで評価した結果の組全体の等号である。
定理は型付けの仮定を要さず、すべての木に成り立つ。

Other は Local が解釈しない一階の操作であり、要求値 `Nat` と応答値 `Nat` を持つ。
`other_survives_local` は、応答を選ぶ前の木の形で要求と後続の各枝を転送する。
最後の評価だけが任意の純粋で全域的な `oracle : Nat → Nat` を使う。
同じ要求には同じ応答が返り、Other 自体の要求回数・順序は Emit の trace に含めない。
そのため評価一致だけから、状態付き・非決定的な応答や Other の事象列の保持を導くことはできない。

`no_emit_trace` の記録の空性もこの観察に限る。
構文に自由変数はなく、後続を表す Lean の関数と oracle は純粋で全域的である。
この条件下の空の Emit trace を、Benitoite の VM・WASM・解放・OS における「実 IO なし」の保証には読み替えない。
情報フロー制御（information-flow control）やセキュリティ型システム（security type system）のモデルでもなく、非干渉性は証明していない。

### 意図した差し替えと、二つの誤り

入力は外側の値が 3、局所値が 7 の `scopeExample` で共通とし、`run` と oracle も共通にした。

| 選択する部品 | 値と Emit の trace | 判定の根拠 |
|---|---|---|
| `execution` | `(10, [7, 3])` | 元の評価と一般に一致。内部だけ局所化する |
| `recording` | `(10, [7, 7, 3])` | Local の入口に 7 の記録を一つ追加する意図した契約。任意の木でも値を保つが、追加記録を型に含める必要がある |
| `wrongScope` | `(14, [7, 7])` | 後続まで局所化する。元の評価との値・記録の一致に対する反例 |
| `wrongHide` | `(10, [3])` | 内部の Emit を隠す。値だけを比較する検査では、この誤りを見落とす |

さらに、混合型の例は `(4, [])`、入れ子の例は `(3, [11, 7, 3])` になった。
Other の例は、応答関数が `n + 1` なら `(52, [42])`、`n + 100` なら `(151, [141])` になった。
いずれも大きな具体計算を kernel に展開する証明にはせず、`#guard` で検査した。

## 2. 設計者向けの解説（コードの読み方、約30行）

`HTree.local` は、指定値・内部計算・後続の三つを受け取る操作である（72 行）。
内部を `HTree b` として受け取る点が、この操作の高階性である。
後続の `Denote b → HTree a` だけなら、一階の操作にもある継続の形である。
内部の結果型 `b` と、全体の結果型 `a` は分けている。
そのため、Bool を返す内部から Nat を返す後続へ接続できる（358〜360 行）。

変換先の `Free` には Local がない（74〜78 行）。
`LocalAlg` は、Local 一回を一階の木でどう表すかを指定する関数の型である（97 行）。
この部品は、精緻化済みの内部と、精緻化済みの後続の各枝を受け取る。
`elaborateWith` は、その部品を Local の節で使う共通の変換器である（105〜111 行）。
他の操作の節を変えずに、`execution` を `recording` へ差し替えられる。

実行用の `execution` は、内部の Ask を指定値で処理してから後続をつなぐ（99 行）。
記録用の `recording` は、その一階の木の先頭へ Emit を一つ追加する（103 行）。
同じ元の木から、異なる一階の木を生成する点が、ここで試した差し替えである。
二つの出力は同じ `run` で評価するので、今回の差は評価器の切り替えによるものではない（374〜377 行）。
記録用の変換は、任意の元の木でも最終的な値を保つ（321〜331 行）。

Benitoite の現在のテストでは、言語のハンドラで一階の操作への応答を差し替えられる。
その説明は設計書 06-04「利用者プログラムのテスト」と 02-09「組み込みの操作とハンドラ表」にある。
この操作は、個々の要求と継続を、実行時にハンドラの節で処理するものである。
SH2 は、内部計算を引数に持つ操作を、一階の木へ変換する節を差し替えている。
範囲の展開方法を部品にし、その後に残る一階の操作の解釈と分けた点に追加の構造がある。

ただし、現在の一階のハンドラでも Reader の処理や記録は表現できる。
今回の結果は、同じ動作が現在の機構では表現できないことを示してはいない。
追加の価値は、Local の内部と後続の区別を、元の構文と変換部品の契約として表せる点にある。
その境界を誤ると、後続も 7 を読み、結果が 14 になる（343・381 行）。
Emit を隠す別の誤りでは値は 10 のままなので、記録の一致も検査する（352・382 行）。

型の上限を保つ証明だけでは、この二つの意味上の誤りを排除できない。
実行用には型保存と一般的な評価一致を別々に証明した（214・257 行）。
記録用には追加の Emit が必要で、実行用と同じ部品の型契約は付けられない（296・334 行）。
実行用とテスト用を差し替えるときは、保存する値・意図して変える記録・必要な効果を明示する。
本番の継続ストアやワンショットの再開に、この部品を接続する作業は残っている。

なお、言語のハンドラと、未処理の組み込み操作を実行する Rust のハンドラ表は別である。
後者をテスト専用の表全体に取り替える説明にはしていない（設計書 02-09「組み込みの操作とハンドラ表」）。

これは SH と同じ **11 ファイル・14 名の候補表**である。
数え方は、SH の固定した候補の名前を、現在の参照上の宣言へ照合し、表の名前を数えたものである。
関連する宣言の検索には `git grep -n -E '…' san_benito -- formal/Benitoite/Surface formal/Benitoite/Release` を用いた。
新しい構文の場合を加えると、表以外の帰納法・相互再帰・補助定理にも波及するため、この件数は変更数の上限ではない。
数十の定義・補題を点検する見込みは維持するが、厳密な全件数は棚卸ししていない。

SH2 の後続は Lean の関数であり、束縛・代入の正しさをホスト言語に委ねている。
本番では de Bruijn 番号を使う構文と `rename`・`instantiate` に接続しなければならない。
さらに `Surface/Lemmas/Scoped.lean:76` の `HasTypeQ.desugar_scoped` と、`HasTypeQ.desugar` の `BuilderCtx`・`EnvClean` などの前提を作る必要がある。
これらは、今回の帰納法が短かったことから容易だとは判断できない。

実行上の接続先は `Release/Syntax.lean` の `Comp.letIn`（263 行）・`Comp.handle`（275 行）・`Comp.resume`（277 行）である。
本番の `Release/Semantics.lean` の `E_Op`（275 行）は継続を保存し、`drop` を含むワンショットの再開規則と結び付いている。
SH2 の `handleReader` は木の全域的な変換関数であり、その保存領域・再開・破棄を再現していない。
既存のコアを保つ限定案でも、内部と後続の配置、効果の出典、交換形式、Rust との対応と差分検査を接続する必要がある。
資源の解放・取消し・仮想時間・Task の動作を含める場合は、この限定案の見積もりとは分けて扱う。

## 4. 主な定理の言明・前提・公理

| 主な定理 | 限定案での見込み | 今回が示した範囲 |
|---|---|---|
| `Release.progress` | Release の構文・型付け・遷移を保つ限り、言明・前提を保つ方針 | 正の構文と全域的な精緻化は定義できた。本番の前提への接続は未証明 |
| `Release.preservation` | 同じ条件で、言明・前提を保つ方針 | 小モデルの結果型・効果の保持は証明した。本番の遷移の保存とは別である |
| `Release.effect_soundness` | 同じ条件で、言明・前提を保つ方針。出力の `WellTyped`・`EffectsOk` が必要 | Emit の記録の空性は証明した。本番の定理が排除する IO・解放事象・未処理操作の全体には接続していない |
| `Surface.desugar_typed` | 拡張した表層の `WellTyped` から既存コアの型付けと `EffectsOk` を導く形を保つ方針。型付けの規則と証明の場合は増える | `elaborate_typing` の構造を参考にできる。本番の束縛・効果変数・組込みを含む保存は未証明 |

今回、新しい独自公理や、精緻化の正当性を無証明で仮定する宣言は必要にならなかった。
固定した標準の精緻化を全域的に定義して証明する限定案では、追加の公理が必要となる根拠は見つかっていない。
これは本番の既存の `Builtins.Assumptions` を除けるという意味ではない。
任意の変換を利用者に登録させる案では、型の契約と意味の契約をどう検査するかを別に設計する必要があり、未試作である。
