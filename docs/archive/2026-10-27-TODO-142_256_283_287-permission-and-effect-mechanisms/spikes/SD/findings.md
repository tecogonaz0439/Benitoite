# SD: 範囲を宛先の上限に使う送信と非干渉性

**D5 は、次の条件を加えて採用する案を推す。** 範囲 R を添字に持つ検査済みの宛先を使い、`pc ⊔ label(d) ⊔ label(v)` の開示先が R 全体を覆うことを静的に求めれば、今回の小モデルでは、受け手ごとの実際の受信列について非干渉性が成り立った。本文だけの開示先を検査する規則では足りない。

- 実行時の宛先は R に属し、送信は検査した同じ値を使う。R の添字を消して任意の宛先と交換できる入口を設けない。
- 宛先の値の印と `pc` も、本文の印と合わせて R 全体に照合する。秘密による宛先の選択は、その秘密を R 内の全受け手へ開示できるときに限って許す。
- 検査済みの宛先による送信そのものは、範囲への所属の再検査で失敗しない。検査済みの宛先を作る際の失敗は別に追う。
- 成功／失敗を公開し、失敗が後続の送信を止める今回の規則では、明示的な `fail` は `pc ⊑ ⊥`、失敗しうる宛先検査は `pc ⊔ label(raw) ⊑ ⊥` を要求する。検査成功を理由に宛先の印を公開へ下げない。
- 非再開も後続の送信を止める。今回の最小モデルでは、非再開の操作を `pc ⊑ ⊥` に限る。本番でこの制限を緩めるなら、継続を破棄した依存を `handle` の出口から後続の計算へ引き継ぐ規則が必要であり、今回その一般形は証明していない。

この判断は、情報フロー制御（information-flow control）の送信を検査するセキュリティ型システム（security type system）の条件である。利用者による操作の許可や OS の隔離を与えるものではない。版の割り振りは設計者の決定を保ち、0.0.13 で案4の範囲とこの契約を準備し、情報フロー制御の実装は 0.0.14 とする。

## 2. 送信と観測の規則

`Range` は閉じた `Scope` の有限列であり、その意味は各要素の対象集合の和である。各 `Scope` は操作種別・解析済みのホスト／パスの要素列のパターン・ポート区間を持つ。型の等号は構造の等号を保ち、意味上の包含と分けた。`RangeCover` はSAと同じ一原子ずつの被覆であり、これから集合の包含を導く。分割した区間を合わせて一原子を覆う完全な判定器は作っていない。宛先の型をより広いRへ拡大できることは、その広いRへの送信も許せることを意味しない。Rを広げると、開示先による被覆の条件も厳しくなる。

送信の規則は次である。`InRange R x` は、実際の対象xがR内のいずれかのScopeを満たすことを表す。

```text
Γ ⊢ d : checked R          Γ ⊢ v : t
∀ x, InRange R x → (pc ⊔ (label(d) ⊔ label(v))) ⊑ sink(x)
─────────────────────────────────────────────────────────
Γ ; pc ⊢ send(R, d, v)
```

宛先は構文上の定数でなく、普通の変数や束縛した式の値である。`Base.checked R` の値の通常の型付けに、Rへの所属を含めた。`EnvTyped`、`eval_type`、`envTyped_push` が、入力・式・局所束縛を通じてこの条件を保つ。`CheckedDest R` は所属の証明を持つ構造体であり、評価器ではその証明を消した `Value.dest` を使う。`send_uses_checked_value` が、型付きの評価結果から同じ宛先を持つ `CheckedDest R` を取り出せることを示す。

SG の `FlowLattice`・`System`・`Observer` は汎用のままである。観測は変更した。SGのように出口の印で事象を投影する代わりに、今回の `observe` は事象の実際の宛先と観測者の宛先を比較し、一致した事象をすべて残す。観測した送信を、宛先の値の秘密性を理由に消すことはしない。事象には宛先と本文が含まれるため、列の一致は内容・有無・回数・順序の一致である。

受け手には、その出口の印を読める `Observer` を対応付ける。任意の束の決定可能な順序については、出口 `sink(o)` を閾値にする `receiverAt` でこれを構成できる。SF段2の宛先集合の具体化では、印は `Event → Bool`、順序は受け手集合の逆包含、結びは共通部分、最小元は全受け手である。`Readers.covers_iff` は、上の全称条件が、開示先の集合がR全体を含む条件そのものであることを示す。**包含の向きは `R ⊆ 開示先` である。**

非干渉性の前提は、同じプログラム・同じ方針・同じ範囲の解釈・両環境の通常の型付け・観測者に見える入力の一致である。宛先の印が見えるときは、二実行の宛先の値も一致する。見えないときは、その観測者への受信を送信規則から否定できる。この場合分けを `noninterference` の送信の場合で示した。後者を、出力を観測から隠す定義で済ませていない。

`forged_checked_value_counterexample` は、SGでは不要だった `EnvTyped` を今回の定理へ加える理由を示す。Rの外のlogsを検査済みの宛先と偽って渡せば、本文の秘密をそのままlogsへ送れてしまう。本番では、型の添字を付けるだけでなく、偽造できない入口と実際の対象への接続を守る必要がある。

## 3. 失敗と非再開の条件

`Result` は `done`・`failed`・`aborted` と、それまでの送信列を持つ。順次実行は `done` のときだけ後半の列を連結し、失敗・非再開なら後続を打ち切る。`observeResult` は終了状態を隠さない。`noninterference` は二実行が成功するという前提を持たず、`trace_noninterference` はその受信列だけの系である。

宛先を検査する `check R raw body` は、所属に成功した同じ宛先を束縛してbodyを実行し、失敗なら `failed` で終わる。型付けは `pc ⊔ label(raw) ⊑ ⊥` を求める。これにより、観測者に同じ入力を持つ二実行では検査結果も一致する。成功した宛先の印にも `pc ⊔ label(raw)` を残す。この検査は範囲への所属の確認であり、開示や、用途への信頼を与える endorsement ではない。

この規則は十分条件であり、最も緩い条件だとは主張しない。秘密のraw値でも常に検査が成功すると証明できる場合、両枝が同じ失敗を起こす場合、失敗の依存を印付きの結果として捕捉して後続へ伝える場合を精密に受理する規則は試していない。特に、今回の規則をそのまま機密性と完全性の積に使うと、失敗しうる検査の入力を公開かつ信頼するものに限るため、公開だが未信頼の設定の検査も拒否しうる。案Gの用途別の検査へ一般化するには、許した失敗への依存や制御の契約を別に設計する必要がある。

非再開は `perform` が `aborted` を返し、最寄りの `handle` がその状態を `done` にして戻る形である。`handle` の中で `perform` の後にある送信は消えるが、`handle` の外の計算は続く。`abortLeak` では秘密が真なら送信が消え、偽ならlogsへ1を送る。両実行とも `done` なので、終了コードだけを同じにする規則では防げない。今回は `perform` に `pc ⊑ ⊥` を求め、`high_pc` の帰納法で秘密のpcから非再開を起こせないようにした。

この非再開モデルには、操作の引数、節による環境の捕捉、節からの送信、継続の値、再開、節を外側で実行する規則、`with` の解放がない。RV-S5 F1-2の一般のハンドラの未達は残る。非再開を一つ加えた最小の制御と、それが後続列を変える反例だけを確認した。

今回の `Covers` は意味上の全称条件であり、任意の束とRに対する実行可能な制約解法を与えない。閉じたScopeの所属は計算できるが、無限個の対象の `sink` を任意関数で定義しても、その全称条件を計算できるとはいえない。本番では管理者が定める有限の束と有限の方針から、包含の健全な判定へ接続する必要がある。

モデルの送信には実際のIOの成否がない。HTTPの応答、認証の成功、リダイレクト、DNS、URLの正規化、ファイルのリンク・差し替え、時間・資源・発散、外部コマンド、許した受け手の再配布は証明の対象外である。実対象がRを守ることと、外部応答や診断が公開してよい依存だけを持つことは本番の別の契約となる。D5が除くのは検査済みの送信における範囲の再照合の失敗であり、これらすべての失敗ではない。

| 主定理 | 言明と前提への見込み |
|---|---|
| `Release.progress` | 通常の型・遷移の保証を維持する。範囲付きの値の導入と検査の失敗を既存の最終状態／遷移へ接続し、型付けで許す操作の応答の存在を保つ必要がある |
| `Release.preservation` | 通常の型の保存は弱めず、検査済みの宛先のRへの所属を値・束縛・ストア・継続で保存する補題を加える。印とpcについての保存は別に追加する |
| `Release.effect_soundness` | 空効果からIO・解放の事象等が起きない既存の保証を残す。実対象が宣言した範囲に入ることは追加の対象の健全性であり、非干渉性も別の二実行の定理である |
| `Surface.desugar_typed` | 通常の型と範囲の添字を脱糖が保つことを接続する。情報フロー制御の型付けと観測の対応も追加する。表層の型付けの前提を、非干渉性そのものを仮定する形に置き換えない |

新しい `noninterference` の前提は、SGの束・型付け・初期環境の可視部分の一致に加え、**両環境の `EnvTyped`** と **受け手と出口の印の対応**である。固定した方針とRの解釈も共通にする。前者は宛先のRへの所属を含む。本番ではこれを実対象までつなぐ信頼の条件と、外部応答の二実行の関係条件が別途必要になる。既存の `io_typed` だけで得られたことにはしない。

ソースに証明穴や独自の公理宣言はなく、最終ログにも未証明の定理はない。表示した11件の公理依存はすべてLean標準の `propext`・`Quot.sound` だけであった。試作142から写した範囲の包含の証明には標準の古典論理を使う部分があるが、非干渉性を仮定してはいない。実APIの対象の健全性や応答の関係は未接続であり、公理で埋めていない。

## 6. 規模の見直しと推す判断

試行前の比較基準は、採用済みの案Gについて [S6](../../study/information-flow-generality.md)「規模の見積もり」の **Lean 154〜374時間、処理系・文書等182〜420時間** とする。その内数の、案4との宛先の上限・入力契約の接続は **Lean 6〜16時間、処理系等8〜20時間** である。これは本試作で実測した本番の工数ではない。

今回、Rを添字に持つ宛先を汎用の束のモデルへ追加し、宛先別の受信列と失敗を含む二実行の証明を一つにできた。したがって、宛先が実行時の値であるという理由だけで、送信ごとの実行時の開示先の照合へ切り替える必要は見つからなかった。Rのために束の代数や非干渉性を別体系で作り直す必要も、このモデルにはなかった。

一方、型付き環境の範囲への所属が証明に加わり、それを外す反例ができた。処理系の実対象の保証、全失敗の依存、一般のハンドラ、制約の推論と診断は残る。**本番全体もD5接続の内数も、現時点では上記の幅を下げない。** 小モデルが短時間で通ったことから、Rustや本番Leanの工数を外挿しない。失敗や非再開に関する保守的な拒否を緩める追加工数は不明であり、上記の確認済みの実装に含まれたとはしない。

共通条件の三択では、**「設計を変えれば中心にできる」**に対応する。ただし、これは版の割り振りを変更する判断ではない。0.0.13の中心は案4のまま、Rを持つ検査済みの宛先と失敗の契約を準備し、0.0.14の情報フロー制御では冒頭の条件を持つD5を採る案を推す。D5の送信規則自体の原理上の未確認は、この小モデルの範囲では解消した。一般の非再開・失敗の扱いを本番まで閉じたとはしない。
