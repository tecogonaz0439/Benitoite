# SK: 範囲付きの IO の型付けと対象の健全性

関門の判定は **「信頼の条件を加えれば閉じた」** である。閉じた範囲、SA の扱い1、名前全体を処理する一階のハンドラに限った小モデルで、範囲付きの IO の型付け、一段・多段の実行の対象の健全性、対象を書き換える節を含むハンドラの規則を証明した。対象の健全性そのものを公理や仮定にはしていない。

追加する信頼の条件は、組み込みが事象として出す操作名・操作の種類・対象が、呼び出した組み込みと引数の対象に一致することである。検査済みの値の不変条件だけから、この実装の振る舞いは導けない。シグネチャ・結果の型・応答の存在がすべて正しくても、別の対象へ操作する反例を証明した。したがって、実際の対象については設計者の決定 P1 の分岐を使う。

四つの主な定理の**結論を弱める必要は、小モデルと移植先の点検では見つからなかった**。ただし、既存の `io_op` の内容は変わり、`Builtins.Assumptions` に対象についての条件をまとめる場合は、その引数が要求する内容も増える。同じ引数名を保つだけで「前提は不変」とは扱わない。本番の四定理、ストア・継続、脱糖の型の保存を移植して通した結果ではない。

対象の表現は、試作142と SA の解析済みの要素列、パターン、ポート区間である。ファイルの対象はパスの要素列、ホストの対象は逆順のラベル列で表す。ファイルの例ではポート0とダミーの全区間を使う。`IOEvent` は操作名と、操作の種類・対象の列・ポートを持つ。引数と応答は `ioResponse` に残す。

型の等号と包含は SA の扱い1をそのまま分けた。`Eff` は原子の所属関数と Fail 列の組であり、正規化で原子を除去しない。範囲の包含は一原子ずつの被覆、範囲のない名前は同じ操作の種類の全対象の上限である。閉じた範囲の整形式には SA と同じ `lo ≤ hi ≤ 65535` を使う。範囲の変数、一般の glob、和をつないだ完全な包含は加えていない。

実行のモデルは、単位値を返す一引数の IO、直列の計算、一つの操作の種類の全操作を処理するハンドラである。節は固定した一階の計算であり、節の後で残りの本体を一度だけ再開する。節をハンドラの外で実行し、残りの本体に同じハンドラを付け直す点を Release の `E_OpPrim` に合わせた。例の固定した節は、受け取った引数を無視して別の対象へ操作する。

関数・束縛・型代入・ストア・継続の場所・解放・利用者のエフェクト・入れ子のハンドラ・非再開はモデルに含めない。`Outcome` は値・エラー・終了を区別するが、結果は捨てる単位値に縮小した。このため、小モデルの保存の証明に `io_typed` は要らない。本番の結果の型の保存に `io_typed` が不要になる、という結果ではない。

## 3. `io_op` の変更と信頼の条件

### 3.1 シグネチャの条件の変更

本番の `Builtins.Assumptions.io_op` は、`s.opEff = some l`、`s.eff = Eff.single l`、`s.neffs = 0`、組み込みの操作の一覧への所属を一緒に要求する。このうち、範囲付きの入口で変えるのはエフェクトの形と引数の型との対応である。操作を捕捉するための名前 `opEff` と、対象の上限を表す原子は分ける。

試作の `PrimSig.IOShape` は、次のいずれかを要求する。

| 入口 | 引数の型 | シグネチャのエフェクト | 操作の種類 |
|---|---|---|---|
| 範囲なし | `raw` | `singleton (name k)` | `k` |
| 範囲付き | `checked s` | `singleton (bounded s)` | `s.scope.kind = k` |

両方で `neffs = 0` と操作の一覧への所属を保つ。`boundedSig s` は任意の閉じた `s` で定義する。実行例の操作名は有限の5件に縮小し、シグネチャごとに閉じた範囲を固定した。任意の閉じた範囲を本番の呼び出しへどう具体化するかという構文・束縛・交換の実装は試していない。本番の `io_op` はその具体化後の引数型と上限が上の形になるように定め、単に「任意の効果でよい」と緩めない。

この表は、対象を持つ入口の部分だけのモデルである。本番の `Console.Write`・`Process.Exit` など、パス・ホスト・ポートを引数に持たない既存の IO に `raw` の対象引数を要求する変更はしない。それらには従来の引数型と名前だけの上限を残し、観測も対象を持つ場合と持たない場合を区別する。対象を持つ操作が対象なしの観測として抜けないことを、シグネチャと観測の対応の条件に含める。複数の対象を使う入口を範囲付きへ移す証明は今回含めておらず、まず従来の範囲なしの上限で扱う。これらまで一対象の `IOShape` で覆ったと解釈しない。

`effect_ops` は、操作一覧からシグネチャ・IO の種類・`opEff` へ戻る現在の役割を保つ。範囲付きの入口も同じ操作の種類へ登録する。試作の逆向きの条件は `IOShape` も返すが、この部分は `io_op` から既に得られ、新しい独立の信頼条件ではない。対象が実際に合うという保証を `effect_ops` に混ぜない。

`io_typed` は、型の付いた引数に対する応答が戻り値の型を持つ、という保証を保つ。試作のように `ioResponse` に事象の対象を加える場合は、その引数を増やすだけで、結論に対象の健全性を抱き合わせない。`io_exists` も、型の付いた呼び出しに事象と応答が存在する形へ移す。実行前に失敗する場合も、応答をエラーとして表せる。捕捉された操作の節へ進むためには、外部の応答の存在を要求しない。

### 3.2 新しく信頼する振る舞い

新しい条件は `Builtins.TargetAgreement.io_target` であり、`Builtins.Assumptions` がこれを明示的に含む。

```text
ioResponse b v ev o
  → ev.name = b
  ∧ ev.site = (signature(b).kind, v.target, v.port)
```

これは、一回の組み込みの振る舞いと実引数を結ぶ条件である。最終の計算の型 `ε`、実行全体、ハンドラ、対象の上限への所属は、この条件の言明に含めない。そこから `argument_bound`・包含の健全性・保存を使い、対象の健全性を証明する。

| 境界 | 試作での扱い | 本番で必要な扱い |
|---|---|---|
| 検査済みの値が範囲内である | `Checked s` の部分型と `Value.HasType` の定義から証明した。`check_sound` は対象を変えないことも示す | `HasTypeV` に同じ不変条件を持たせ、検査の成功値・定数・受け渡しで保存する。不透明な外部値として扱うなら、その生成・読み込みの正しさを組み込みの契約へ明示する |
| 組み込みがその対象だけへ操作する | `io_target` として信頼する。`bad` はこの条件だけを満たさない | IO 実行器・組み込みの関数が、検査済みの対象を使い、別の対象や操作を事象から隠さないことを信頼する |
| 事象の対象と実 OS の対象の対応 | モデルの `ioResponse` は実際の対象を表す仕様上の関係とする。Rust・OS との対応は証明していない | 正規化、パス解決、リンク、接続先の解決や再接続などで対象が変わるときにも、保証する対象の意味との対応を保つ契約が要る。ホスト名の上限と解決後の IP の上限を同じものと扱わない |

本番の現在の `Event.io b ws o` は**要求の引数**を記録しており、実装が操作した別の対象を記録する欄はない。引数から対象を取り出すだけなら、試作の `request_argument_bound` のように、新しい振る舞いの条件なしで所属を示せる。しかし、その結果を実際の対象の健全性と言い換える根拠はない。実際の対象を言明するには、事象の観測を関係へ加えるか、現在の事象が実際の操作を忠実に表すことを同じ信頼の境界で明記する必要がある。

P1 で受け入れる条件は、この未証明の実装との対応を含む。試作でパスや DNS の解決の正しさまで証明したとはしない。0.0.13 の範囲を、正規化した API の対象の上限にする場合も、その意味と OS の実体の制限を分けて記す。実行時の権限制御や OS の隔離を実装したという結果ではない。

## 4. ハンドラが別の対象へ操作する規則

ハンドラの出力の上限を `ε`、本体の上限を `εm`、処理する操作の種類を `k` とすると、規則は次である。

```text
body : Unit ! εm
εm ⊑ (ε ∪ {name k})
clause : Unit ! ε
──────────────────────────────────
handle body with clause : Unit ! ε
```

節が別に `εc` を推論する形なら、最後の前提を `clause : Unit ! εc` と `εc ⊑ ε` に分ければよい。処理する名前を節自身のエフェクトから差し引かない。節はハンドラの外で実行するため、同じ操作の種類であっても、節が実行する操作の対象を全体の上限へ含める。

反例では、本体の対象を `out/a.txt`、節の対象を `outside/b.txt` とした。全体の上限を B とする正しい型付けでは、A の操作は捕捉され、B の事象だけが出る。誤った規則 `WrongHandleRule` は節を任意の `εc` で型付けして全体との包含を要求しないため、全体を空効果と認めて同じ B の事象を出す。元の A だけを上限に残す案も、`original_target_budget_rejected` で拒否した。

本番の `Typing.lean` の `C_Handle`・`HasTypeClausesQ.cons` と、`Semantics.lean` の `ContTy.K_Handle` は、既に節を出力の上限で検査する形である。ここへ範囲の包含を通す。節の対象を自動的に元の本体の範囲へ固定する規則へ変える必要はない。`handled` は引き続き操作名全体を表し、範囲の一部だけを処理するハンドラは加えない。試作の種類全体の捕捉は、本番ではその種類の操作一覧の全操作に節がある場合に対応する。

### 5.3 四つの主な定理と追加する完了条件

| 定理 | 保つ結論 | 前提と証明の変更 |
|---|---|---|
| `Release.progress` | 型の付いた全状態は終状態か遷移できる | `BuiltinOnly` と IO のシグネチャを広げる。`io_exists` は観測も返す。対象一致の条件は進行そのものには不要。小モデルでは `BasicAssumptions` だけで証明した |
| `Release.preservation` | `StateTy → Step → StateTy`、および内部の同じ `Eb` の保存 | 範囲付きの引数型・包含・ハンドラ節・継続を扱う。一般の結果の型には既存の `io_typed` を使う。結果を相互包含へ弱めたり、型の一致を失ったりする案は採らない |
| `Release.effect_soundness` | 空効果なら IO・解放の事象がなく、処理されない利用者の操作もない | 旧 `no_event` の IO の部分を新しい形へ移す。小モデルの空効果の定理は対象一致を要求しない。解放と利用者の操作の部分は本番で保ち、試作から証明済みとはしない |
| `Surface.desugar_typed` | 脱糖後の `WellFormed ∧ WellTyped ∧ EffectsOk` | `hsig` の `Scoped` に閉じた範囲と検査済みの引数型を通す。実際の IO の振る舞いの新しい条件を、この定理の前提へ加える必要はない。表層とコアで同じシグネチャ・範囲を使う |

四つの結論は保つ案であるが、型付けなどの定義と `io_op` の内容は変わる。さらに、一つの `Builtins.Assumptions` へ `io_target` を入れたまま既存の主定理に渡すなら、主定理の `hb` は従来より多くを要求する。不要な依存を避けるには、小モデルと同じく既存部分の条件と対象の振る舞いの条件を分け、対象の健全性だけに後者を渡す。どちらの構成を採っても、その差をレビュー対象に含める。

新しく追加する本番の完了条件は、既存の四定理とは別に、少なくとも次の二つとする。

1. `StateTyE P B Eb s` かつ `Step P B s (some (io ... target ...)) s'` なら、その事象の操作の種類と対象が `Eb` に属する。`ContTy` の対象の伝播と、型の付いた引数・`io_target` を組み合わせる。保存の定理の結論へこの条件を押し込む必要はない。
2. 初期の計算の型が `A ! ε` なら、任意の有限の実行の全 IO 事象と、到達先で次に出る IO 事象が初期の `ε` の上限に属する。`preservationE` と上の一段の補題で証明する。脱糖の型の保存は初期の型付けをコアへ渡すために使う。

本番の `Steps` は事象列を保持しないため、事象列付きの関係を追加するか、到達状態と次の遷移を量化する形を使う。後者は既存の `Steps` を変更せず言明できる。どちらでも、空効果だけを保証する従来の定理を対象の健全性の代わりにしない。

## 7. 推す判断

**P1 の信頼の条件を列挙し、レビューで受け入れる構成で、案4を 0.0.13 の中心にできる。** `io_op` は操作の種類・引数の範囲・シグネチャの上限を結び、実際の操作の対象は別の `io_target` で実引数へ結ぶ。その条件から、包含とハンドラ・保存の規則を経て、実行全体の対象の健全性を証明する。
