# SB: 定数端点の整数区間を持つ関数契約の型付けと置換

2026-10-26。捨てる前提の実現可能性の試作である。本番の改造・実装計画の確定・主定理の拡張は行っていない。

**定数端点に限った関数契約は、0.0.13 の中心にできると判断する。** 試作 022 の表では「閉じた整数区間・長さを Release の型と部分型へ直接追加」の行を基準にする。関数契約という名前だけで「n・長さに依存する篩」の行へ移す必要はない。ただし、一般の関数の反変・共変を加える費用は残る。見直した幅は **Lean 48〜96時間、処理系・配布文書等 56〜120時間**であり、元の前の行（32〜80時間・40〜100時間）の上側から少しはみ出す。値に依存する型の置換を避けられることと、既存の等号による証明をそのまま残せることは別である。

## 1. 対象と写した定義

本番の読み取りと件数調査の基準は、`san_benito` を読み取り時に解決した `65b165272b42c3f3621ad59bc2a2c6c9cec9c46e` である。作業ツリーの Lean は参照せず、`git show` と `git grep` で読んだ。参照資料は、共通条件、設計原則 00-01、用語集 00-04、試作 022 の `findings.md`・`Intervals.lean`・`Contracts.lean`、`targets-and-capabilities.md` §2.6 とした。

区間は `bottom` または `closed lo hi valid` であり、`valid` は `min64 ≤ lo ∧ lo ≤ hi ∧ hi ≤ max64` である。所属は閉区間 `lo ≤ n ∧ n ≤ hi` とした。試作 022 は半開区間だったので、その反例の `[0,10)`・`[0,5)` は `[0,9]`・`[0,4]` に置き換えた。第6弾の `Subset` と同じく、空集合の特例と端点の比較を使い、所属による包含との同値を証明した。

端点は言語の項や値の変数ではなく、型構文に格納する整数の定数である。Lean の定理が `i : Interval` を引数に取ることは、対象言語で実行時の変数を型に使うことを意味しない。例えば固定した Port の検査は `Result[Int[1,65535], RangeError]` を返せる。一方、実行時の `lo`・`hi` を受け取って、その値によって返す型を変える API は本案の対象外である。

型の等号は構造の一致に保つ。区間から Integer へ忘れる規則、区間の包含、関数の引数の反変・結果の共変、効果の包含を `Ty.Le` に加えた。他の型構成子の引数は不変とした。特に Reference や List に範囲の共変を足さず、`Fail[A]` と `Fail[B]` の間にも範囲の包含による変換を足していない。

## 3. 型付け・置換・実行時検査の分担

呼び出しは、本番の `C_App` と同様に「関数型の要求する引数の型で、引数に型が付く」とした。実際の引数がより狭い型なら `V_Sub` 相当の規則で要求型へ広げる。複数引数でも各位置で同じ操作ができる。新しい特別な呼び出し規則で狭める必要はない。

関数自身を部分型で広げた場合、呼び出し側の引数型を A'、元の関数の引数型を A とすれば A' ≤ A が得られる。その包含で引数を A に広げてから本体へ代入する。元の本体の結果 R は呼び出し側の結果 R' に対して R ≤ R' なので、代入後の結果を広げる。C の `beta_preservation` と F の `arguments_for_native_contract` が、この二つの向きを分けて確かめている。

値の置換の結論は、`Γ ⊢ v : A` から `Δ ⊢ v[σ] : A` のままである。型 A に `σ` を適用する項は現れない。ラムダと let の下では、変数番号をずらして捕獲を避けるが、端点はずらさない。型変数の置換は別の操作であり、区間の枝を恒等にして型構造へ再帰する。C の型置換の証明は一引数と単純な効果の範囲であり、本番の正規化・型付き失敗・行の置換との交換まで通したものではない。

区間から Integer へは値の表現を変えずに広げられる。逆向きには、リテラルの所属の静的な証拠か、実行時検査の成功の証拠を要する。`rawMake` は `Option Int` を返し、成功時に元の入力と同じ整数であることと所属を証明した。検査済みの値を別の整数と取り違えてはいない。検査前の動的な Integer を無条件で区間型へ移す規則はなく、0を Port として型付けできないことも証明した。

この試作には、算術の区間推論、経路条件からの変数型の絞り込み、検査の除去はない。第6弾の警告の健全性から、これらの型付けの証拠を流用することもしない。`x + 1` の範囲、ハンドラが返す値の範囲、既存 API のすべての成功値の所属は、それぞれ本番で証明・検査する対象となる。

### 4.2 言明の形を保てる範囲と、別に増える作業

Boolean・Reference・Lazy・List・Map・Set・Bytes・辞書・データ型等の最外構成子で、引数を不変に保つものは、対応する等号の逆転を維持できる。既存の canonical form の証明は、一般の非関数補題を限定した補題へ置き換え、新しい区間導入の不可能な枝を処理する。これら全部が意味を変える定理になるわけではない。

一方、新しい `Ty` の枝は `Order/Types`、`Normalize`、`TypeSubst`・`TypeSubstLemmas`、`Scope`、`Finite`、型の書き出しにも追加する必要がある。これらは `Ty.Le` の文字を使わなくても影響を受ける。本番の `Ty.Le` は現在の等号との選言から構造的な包含へ移す必要があり、有限な判定器、反射・推移、判定と規則の一致も要る。試作の反射・推移の閉包を、そのまま探索して判定する実装にはしない。

`Lemmas/SubstTyping.lean` の通常値の置換の言明は保てる見込みである。`SubstOk` の像を同じ型の値として扱い、区間導入の枝を加える。ストアの場所、専用の局所参照、継続、捕捉を隠す境界は C へ写していないので、本番での確認が残る。`Lemmas/TySubstMain.lean` には、区間の恒等の枝と関数の包含を型置換が保つ証明を接続する。

## 6. 規模の見直しと推す判断

試作前の比較対象は、試作 022 の「閉じた整数区間・長さの直接追加」32〜80時間・40〜100時間と、「n・長さへの依存等」80〜200時間・80〜240時間である。本案は前者に近い。値の変数を含む型のスコープ・値による型の置換・関係を保持する経路条件が増えなかったことが根拠である。

ただし、前者の下限で本番を終えられるとは見ない。等号の逆転を使う Release の69定理と Surface の15定理を確認する必要があり、関数の一般の包含は入れ子の整形式にも及ぶ。本試作の短い証明時間を84定理へ掛け算する見積もりにはしない。

| 本番の段階 | Lean の能動作業時間 | 処理系・配布文書等の能動作業時間 | 含める作業・検査・レビュー |
|---|---:|---:|---|
| 型の表現・構造の一致・正規化 | 8〜16時間 | 8〜16時間 | 端点の妥当性、全構成子への接続、順序・正規化・型の書き出しの確認 |
| 包含・逆転・整形式 | 10〜20時間 | 12〜28時間 | 関数の反変・共変、判定器、引数列、型変数との制約、型の合流 |
| 置換・呼び出し・状態の保存 | 14〜28時間 | 12〜28時間 | 通常値・型の置換、ストア・継続・組み込みの契約、関係する回帰検査 |
| 表層の検査・脱糖・交換 | 12〜24時間 | 16〜32時間 | 型注釈・定数・検査成功の導入、Rust/Lean の比較と実行例、生成物・診断・Skill・移行の説明 |
| 定義・言明・仮定のレビューと修正 | 4〜8時間 | 8〜16時間 | 主定理の接続の点検、残る反例の確認と受け入れ資料 |
| **合計** | **48〜96時間** | **56〜120時間** | 各欄を加算した暫定の幅である |
| 全体の検査・外部レビュー・設計者の受け入れ待ち | 不明 | 不明 | 本番の全ビルド・Rust/Lean の全比較・必要な構成と実 CLI の検査、レビュー・受け入れの待ち時間。上の能動作業時間へ含めない |

処理系側の見積もりは、固定した版の `typeck/infer.rs:26` の `ITy`、`generate.rs:32` の `flow`、`solve.rs:680` の `equal`・`:822` の `flow_inner` を読んだ推定である。現行の `flow_inner` は関数の引数と結果を `equal` で揃え、効果だけを包含へ流す。区間の端点を追加するだけでは済まず、等号と有向の包含を使う箇所を分ける必要がある。Rust の変更行数や全呼び出し箇所の調査、実装はしていない。

中心にする範囲は、**64ビット Integer の定数端点、関数の引数・結果、構造の一致としての型の等号、既存の値表現、検査付きの動的入力の導入**に限る。注釈の範囲外端点や逆転は拒否し、空区間を公開構文に出すかは先に決めることを推す。試作の `interval` 関数は第6弾の解析領域と同じ交差・空への正規化であり、その振る舞いを型注釈の仕様として決めたものではない。

長さの篩、`Int[0,n]`、リストの値と添字の対応、線形の経路条件、一般の再帰不変条件、SMT、検査の除去、範囲付きエフェクト、捕捉検査を重ねない。この範囲なら、部分型と置換を一つの学習の中心にでき、値に依存する型へ進む前の区切りにもなる。

## 7. 再現・実際の時間・作業の境界

Lean は手元で一度も起動していない。最終の検査と静的な照合はリポジトリの根で次を使う。

```sh
zsh work/m013/remote-lean.sh SB Contracts.lean 6144 180

python3 work/m013/spikes/SB/inventory.py 65b165272b42c3f3621ad59bc2a2c6c9cec9c46e
```

検査以降に Lean の最終ソースは変更していない。`verify.py` は現在のソースのハッシュを記録するものであり、別機からハッシュを受け取る仕組みではない。本番の `check.sh`・`lake build`・`check-formal.sh` の検査結果への引用はしない。

書き込みはこの `work/m013/spikes/SB/` のみとした。指定された別機検査の道具が使うロックと転送先は共通条件による。追跡ファイル・formal・docs・crates・docs/todo を編集せず、git の状態を変える操作も行っていない。別セッションの変更はそのままにした。

運用上の逸脱として、最初の読み取りをまとめた際に共通条件の例外を適用する前に `private/AGENTS.md` も読んだ。直後に報告し、この試作には適用せず、その後 `private/` は読んでいない。
