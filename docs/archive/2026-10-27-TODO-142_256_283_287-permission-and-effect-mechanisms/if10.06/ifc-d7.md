# IFC-D7: 人間に示す要約と、承認を同じ方針へ保存する責任の案

2026-10-27、IF10.06。設計者が選ぶための判断案であり、採択済みの決定でも、実装・証明の完了報告でもない。

## 決めることと既に決まっている境界

IFC-D7 で決めるのは、人間に作業・秘密の取得元と分類・受け手と宛先候補全体・用途・公開する値と成否・信頼条件・変更差分と再利用範囲の要約を示し、秘密登録と送信・非機密化・エンドースメントの契約の変更を区別して承認した結果を同じ方針へ保存し、0.0.14 ではその提示・保存・保護を信頼する起動側の責任、サーバモードでは承認の確認・保存・失効と実行時の強制をサーバの責任にするか、技術的な方針全体を人間が承認するか、方針編集を LLM へ委任するかである。

[README の版の割り振りと方式](../README.md#設計者の決定2026-10-27版の割り振りと情報フロー制御の方式)、P1〜P6、[判断14](../decisions.md#判断-14-保証と後の宛先の契約)・[判断19](../decisions.md#判断-19-情報フロー制御の方式と今回の成果物)・[判断21](../decisions.md#判断-21-実装と提供の境界)を保つ。0.0.13 は判断案・棚卸し・契約の設計まで、0.0.14 は情報フロー制御（information-flow control）の独立した実装、その後は必要な接続とサーバモードである。内部の判定と Lean の証明に汎用の束を使い、最初は管理者が定める有限の束、機密性と完全性、用途を限った非機密化（declassification）とエンドースメント（endorsement。信頼の付与、または完全性レベルの引き上げ）、推論する一階の印の要約を扱う決定は戻さない。

[IFC-D2](../if10.01/ifc-d2.md)・[IFC-D3](../if10.02/ifc-d3.md)・[IFC-D4](../if10.03/ifc-d4.md)・[IFC-D5](../if10.04/ifc-d5.md)・[IFC-D6](../if10.05/ifc-d6.md)の案A（D5だけは案B・候補(ii)）を仮の前提とする。設計者はどれもまだ選んでいない。各文書の IFC-D7 への申し送りに従い、起動側による方針・契約・検査済み成果物の保護、固定操作の限定契約、認定した入力だけの精密化、R 全体への被覆、取得・印を保つ取り出し・非機密化の分離を引き継ぐ。別案が選ばれたときの差は後掲の表に分ける。

D5案Bの固定originも案Aの単一候補として同じ印・観測の条件を用いる。以下のR全体への被覆の説明をこの意味で適用し、動的設定の受理は別案Aに限る。

[00-01「保証の範囲」](../../../design/00-overview/00-01-goals.md#保証の範囲)と[07-01「脅威モデル」](../../../design/07-quality/07-01-security-model.md#脅威モデル)では、利用者が作業と許す操作を決め、LLM・ハーネス・スクリプト・外部入力は信頼しない。セキュリティ型システム（security type system）が検査するのは規則への適合であり、承認によって作業の意図、外部 API の正しさや成功、停止まで証明できるとはしない。サーバ前の隔離はハーネスと OS に委ねる。D2案Aは、07-01に「信頼する起動側」という役割を一つ加える案である。人間の判断を改変されない形で渡す部分を指す説明上の呼び名であり、未信頼のLLMが方針も編集できる通常の利用ではその前提を満たさない。

本書の「狭小化」は、許す操作・対象・受け手・用途を削減するか緩和契約を無効にし、入力分類・束・信頼条件を変えず許可が広がらない変更を指す作業上の説明である。用例は未確認であり、新しい術語として採用した扱いにはしない。適用条件はD9で比較する。

## 推す案と二つの代案

案Aは「人間向けの要約で変更を承認」、案Bは「束・制約と方針全体を人間が承認」、案Cは「方針編集を LLM へ委任」とする。[元の問いD7](../study/questions.md#0013-の中で決めること設計の判断として文書にするもの)と [S6 の Q8](../study/information-flow-generality.md#設計者に決めてもらう問い)の三案を具体化した。全案を同じ方針へ保存する比較とし、独立した情報フロー制御用の許可ファイルを追加する案にはしない。方針の具体的な書式と所有・識別の決定は IFC-D9 へ残す。

| 比較する点 | 案A: 人間向けの要約で変更を承認（推す） | 案B: 束・制約と方針全体を人間が承認 | 案C: 方針編集を LLM へ委任 |
|---|---|---|---|
| 人間に示すもの | 作業、秘密、取得・取り出し、受け手、R全体、用途、結果・成否、信頼条件、差分と保存範囲。技術的な詳細は根拠として参照できるようにする | 同じ意味を持つ登録・束の順序・機密性と完全性・pc・要求各欄・成否・制約・契約の版と差分を技術的な一覧として示す。一般の人向けの要約を承認の主な接点にしない | 人間は作業と編集を委任する範囲を指示し、LLMが分類・受け手・緩和を編集する。編集結果の報告はできるが、変更ごとの人間の承認を要しない |
| 承認の単位 | 秘密登録、送信先・用途、非機密化、エンドースメントを別の変更として示す。必要な変更の組を人間が選び、整合する一つの方針の更新として確定する | 正規化した方針の一つの改訂全体を、人間が承認または差し戻す。個別の意味の違いを人間が一覧から読む | 作業またはプロジェクト単位の委任で、以後はLLMの編集を受け付ける。狭める変更だけの委任なら緩和はできず、本案の代わりにはならない |
| 承認結果の保存場所 | 秘密登録・出口・契約を同じ方針の改訂へ反映し、その改訂と人間の承認の対応を保存する。秘密の実値は取得元・保管口に置き、方針に複写しない | 案Aと同じ方針と承認の対応。保存形式を変える必要はない | 同じ方針へ編集を保存し、委任の範囲と編集者を記録する。人間が各変更を承認した記録とは区別する |
| 0.0.14での責任と保証 | 信頼する起動側が提示・人間の承認・保存・保護と検査した組の実行を担う前提。処理系は受け取った方針の規則に適合する対応済みフローを静的に検査する。製品の承認画面・保護された保存・実行時の強制を先行実装したとはしない | 同じ責任と静的保証。人間が技術的な一覧を正しく理解したことは保証しない。説明を難しくしても静的規則は強くならない | 受け取った現在の方針への静的適合まで。LLMが例外を追加できるため、人間が確認した秘密・受け手・緩和に適合するという前提は成立しない。D2案Aの説明を維持できない |
| サーバモードの責任 | 権限のある人間の承認と改訂を結び、保存・未承認の変更の拒否・失効・再検査・実行する組との対応を管理する。同じ方針から操作ごとの照合とOSの制限へ接続する | 案Aと同じ強制。技術的な一覧を人間が承認する操作が主な接点になる | 委任範囲内のLLMの編集を許す強制になる。人間の変更ごとの承認へ戻す場合、委任で作った登録・例外の再確認が要る |
| 保証しないこと | 秘密登録や入力・外部APIの信頼条件の真実性、要約と真の作業意図の一致、外部操作の成功、停止、時間・資源の量による漏れ、受け手の再配布。起動側が前提を満たさない実行の隔離も保証しない | 案Aと同じ。人間が全制約を読んだことを、内容や意図の証明にしない | 案Aの限界に加え、委任範囲でLLMが許した漏れや信頼の付与を、人間が許さなかったことを理由に止める保証を与えない |
| 利用者への説明案 | 「この秘密をこの相手のこの欄に使い、この結果と成否だけを報告する方針への変更を確認する。保存した範囲は後の対応する実行にも使う。実行の成功や内容の正しさを保証する承認ではない」 | 「秘密登録・印・受け手・緩和の制約と変更を一覧で確認し、この方針の改訂全体を承認する。読み取れなければ管理者へ差し戻す」 | 「この作業の分類・受け手・緩和の変更をLLMに任せる。以後の変更を人間が個別に確認したとは扱わない」 |
| 後の版への影響 | 承認の意味と同じ方針への接続を保って、提示・保存を起動側からサーバへ移せる。保管口等の追加にも新しい契約の承認が要る | 後から要約を主な接点へ追加すると、技術的な改訂と要約の対応を検証する作業が要る。方針の意味と保存は共用できる | LLMを権限変更の判断者として信頼する境界の変更が要る。人間の承認へ戻す際の既存許可の扱い・再確認と運用の見直しが増える |
| IFC-D2〜D6への依存 | D2〜D4・D6の案AとD5の案B・候補(ii)を仮の前提とする。入力契約、許した要求由来だけの緩和、R全体、実際の取り出しと契約使用を要約へ結ぶ | 同じ静的義務と信頼条件を技術的に表示する。生の制約を出すだけで入力の認定や緩和の根拠が不要になるわけではない | 各静的義務は残るが、方針保護と契約の承認を未信頼のLLMに委ねる点がD2案Aと衝突する。07-01の信頼関係と00-01の利用者の役割の再判断が必要 |
| IFC-D8・D9への依存 | D8で受理する例を定め、未対応を承認で通さない。D9で所有者・版・識別・承認の対応・正規化・変更時の無効化と狭小化を定める | 同じ義務。D9の正規化した改訂全体が承認の単位になる | 未対応機能を編集だけで受理できるとはしない。D9で委任の範囲・変更権限・失効を追加し、人間の承認が要る変更をどこまで残すか再判断する |
| 費用の見込みと根拠 | 案G全体の既存見込みはLean 154〜374時間・処理系等182〜420時間。方針の入力・版・分類・キャッシュの接続は4〜10時間・10〜24時間という内数。人間向け要約と承認・保存・サーバ接続のD7単独の費用は不明 | 同じ入力・契約・キャッシュは必要。要約の作成は減りうるが、制約の一覧・差分・全体承認と利用者の確認負担が残る。削減幅と合計は不明 | 承認画面の一部は省けても、委任の認証・範囲・失効・編集履歴と後の再確認が要る。追加費用と合計は不明。方針をテキスト編集できることだけを低費用の根拠にしない |

費用の出どころは [synthesis「大きさの見込み」](../study/synthesis.md#大きさの見込み)、[S6「規模の見積もり」](../study/information-flow-generality.md#規模の見積もり)、[S5 §8.2](../study/information-flow.md#82-見積もりの根拠と対象)である。未実装で確度の低い能動時間の見込みであり、D7の確定予算でも実測でもない。上記の内数を全体へ再加算しない。0.0.14の見込みには、0.0.13の判断と書式の境界の設計、サーバの保存・承認、OSの強制、一般のTask・Process・WASM接続、長い検査・測定の実時間、独立レビューと設計者の回答待ちは含まない。本枝の文書作成の見込み0.5〜1時間とも区別する。

案CでLLMが編集案だけを作り、人間が差分を確認して保存するなら案Aまたは案Bに当たる。案Cの相違は、秘密の分類を弱め、受け手や緩和を増やす編集の最終判断まで委任する点にある。現在の決定のままその委任を実装してよいという提案ではない。

## 案Aで人間に示す要約の項目

要約は、信頼する処理が同じ方針・解決済みの契約・検査対象から得た内容に結び付ける案とする。LLMが作業の名前や説明案を作ることはできるが、その文章を権限の根拠にしない。項目が不明なら不明と示し、未確認の契約や未対応の機能を承認操作だけで受理へ変えない。

| 項目 | 人間が判断する内容と、表示の条件 |
|---|---|
| 作業と対応範囲 | 何を取得・送信・報告するか、対応している版と機能、静的保証かサーバの強制まで含むか。作業名は意図の説明であり、検査済みの事実とは区別する |
| 秘密の登録と入力 | 作業上の名前、取得元の種類と安全に表示できる識別、機密性と完全性の分類、入力契約、実対象との対応を信頼する条件。秘密が実際に存在するかや取得に成功したかを調べて表示する操作にはしない |
| 取得と取り出し | 実際に使いうる取得・印を保つ取り出しの要約。取り出し後も派生値と制御を追うこと、取得・取り出しだけでは公開できないこと |
| 受け手と宛先候補全体 | 相手、scheme・host・portと必要な操作・要求欄、静的上限R全体。大きい候補集合はパターンとその意味を示し、現在の一つの宛先で代表させない。秘密を受け取れる相手の集合とは別々に示す |
| 用途と要求 | 認証欄、本文などの用途、固定操作・変換、呼ぶ条件と回数の契約、リダイレクト・再試行の有無。自由な「報告用」という注記だけで制限したと扱わない |
| 非機密化 | 公開する結果の欄・粗い成否・正常復帰と終了状態への対応、報告先、許した要求由来の範囲、なお秘密に保つ本文・捕捉・条件等。公開する承認により、件数や認証の成否自体から分かる情報も相手へ渡ることを示す |
| エンドースメント | どの未信頼入力をどの固定した条件で確認し、どの用途だけに信頼を付与するか、成否と呼出条件。非機密化とは別に示す。使わない例では「なし」とし、公開応答を信頼する命令へ変えない |
| 信頼条件と残る限界 | 入力分類・外部API・固定変換に何を信頼するか。応答の完全性が未信頼であること、実IOの成功・外部での保存完了・停止まで保証しないこと |
| 差分・保存と再利用 | 所有者、方針と契約の識別・改訂、以前から何を広げるか、保存先の方針、どの後の実行にも適用するか、取り消す方法。未保存・未承認・未対応を、保存して実行可能になった状態と区別する |

秘密の実値・実際の長さ・応答本文・秘密依存の成否は、承認画面・診断・記録へ含めない。登録名やパス自体が秘密なら、公開してよい別の表示名を用意するか、その人間と表示先に許される範囲へ制限する必要がある。伏字にしても、秘密の値で確認画面を出すかどうかが変わるなら依存は残る。最初の案では公開かつ信頼する設定から実行前に同じ要約を作り、秘密依存の途中の承認を汎用の例外にしない。

実際の取り出しと契約使用は、`main` から除去できるエフェクトの名前だけで集計しない。[S6 の Q7 後の注意](../study/information-flow-generality.md#設計者に決めてもらう問い)とD6の申し送りに従い、解決済みの実操作と契約の同一性へ結ぶ。未信頼のハンドラや同じ綴りの関数で要約から消せないことが必要である。高階の呼び出し等を正確に列挙できなければ保守的な候補を示すか拒否し、不明を「使わない」にしない。この対応の実装・健全性は0.0.14の仕事である。

## 承認の単位、保存、実行の分担

案Aの承認は、人間が同じ方針のどの契約を変えるかを決める操作とする。秘密の登録は、その取得元を秘密として扱う指定であり、全出口へ送れる許可ではない。既に許した受け手へ印を保って送る場合と、公開する値を増やす非機密化、信頼する用途を増やすエンドースメントを分けて確認する。

| 段階 | 0.0.14の信頼する起動側への前提 | サーバモードで保存・強制する責任の案 |
|---|---|---|
| 候補の準備と提示 | LLMの提案を候補として受け取り、実値を使わず、同じ検査対象・正規化した方針・契約に対応する要約と差分を提示する | 候補の提出者と承認できる人間を分け、信頼する処理で要約と差分を作る。LLMの文章を承認済みの方針とみなさない |
| 選択と整合 | 秘密登録、送信先・用途、非機密化、エンドースメントの変更を人間が選ぶ。必要な組の一部を拒否したら、残りの組を再検査し、実行できると推定しない | 選んだ変更が同じ改訂として整合することを確認する。未回答を承認と扱わず、古い方針を見た承認で別の更新を上書きしない |
| 保存 | 同じ方針の所有者が管理する場所へ、人間が承認した登録・出口・契約と承認との対応を保存し保護する。手動の更新でも、表示した内容との一致を起動側が担う | 権限のある人間の承認と適用先の改訂を結び、更新を一括して保存し、未承認の緩和を拒否する。別置きの履歴を持つ場合も、独立した許可源にしない |
| 実行との対応 | 保存した方針、契約、検査したコードと依存の組を使う。差し替え・別起動・方針改変を処理系が止める保証は先取りしない | 保存した改訂と実行する成果物を対応させ、操作の照合とOSの強制へ接続する。拒否の有無・診断・後続への依存も設計する |
| 変更と失効 | 受け手・R・用途・公開する欄と成否の拡大、分類の緩和、固定操作や変換の差し替え等では、旧承認を根拠にせず差分を再提示する | 失効・変更した方針や契約に依存する検査結果とキャッシュを無効にする。進行中の実行への適用時点は別に設計し、実行済みの送信が取り消せるとはしない |

保存するのは秘密の取得元の参照・分類・出口・契約と承認の対応であり、トークン等の実値は別の保管口に置く。同じ秘密登録から、内容と派生値の分類と、後の実アクセスの除外を導く案をD9へ渡す。秘密の一覧を二つ管理せず、サーバ前に実アクセスを拒否する機能を加えない。「同じ方針」は同じ権限判断の入力を指し、履歴や秘密の実値まで一つの物理ファイルに入れる意味にはしない。

保存した契約の承認は、明示した作業範囲と方針の改訂の下で、失効するまで後の対応する実行にも使う案とする。有効期限を設ける場合も、その期限を確認時に示す。各実行はその時点の方針と契約へ適合する必要があり、コードや依存の変更後の再検査を省けない。同じ契約のまま実装だけ変わった場合にも必ず人間が再承認するかはD9で定めるが、契約・権限の拡大は再提示する。秘密の入力や許す受け手が変わるのに、作業名が同じだから承認を再利用する扱いにはしない。

一回の操作だけを許す承認の消費は別の責任である。[S3「先に決める接点」](../study/usage-and-flow.md#0013-とサーバモードで先に決める接点)に従い、サーバの消費状態、失効、再試行、同時実行の判定が要る。本枝の「一回取得する」という固定契約は一実行内の呼出条件であり、方針を保存した後に世界全体で一回だけ使える権利を作るものではない。0.0.14の起動側が単発の承認を独自に管理しても、その消費を製品が保証したとはしない。

厳しくする変更も、旧検査結果をそのまま使ってよい根拠にはしない。何を狭小化とみなし、どの更新権限で適用できるかはD9へ残す。秘密登録を削る変更は、削除という見た目に反して分類を弱めうるため、人間への再提示の候補になる。

## 三つの典型例での要約と承認操作

以下は架空の入力と固定操作を使った比較用の表示文案であり、文言・構文・公開API名・UIを決めるものではない。実在のサービスの挙動と外部APIの秘密の非反映は未確認である。案A・Bでは人間が変更を承認しても、必要な契約と接続が実装されるまで実行の受理を意味しない。0.0.14では提示・保存を起動側の前提として読み、サーバでの操作は接続を閉じた後の案として読む。

承認操作の例は、案Aでは人間が項目ごとの変更を選んで「選んだ変更を方針へ保存」または「差し戻す」、案Bでは改訂全体を読んで「方針全体を承認して保存」または「差し戻す」、案Cでは委任範囲を指定して「方針編集を委任する」または「委任しない」を選ぶ形とする。これらの操作名も比較のための仮の文言であり、画面やコマンドの決定ではない。

### 認証付き取得の件数と成否

D3案Aの例に合わせ、公開かつ信頼する設定から、`https://api.service.example:443` の固定した `GET /issues` を一実行内に一回呼ぶ。登録した「サービス用トークン」を認証ヘッダだけに使い、件数と定めた成否を公開の報告先へ表示する。リダイレクトと自動再試行はしない。

| 案 | 利用者に示す文の例 | 承認の操作と保存の例 |
|---|---|---|
| A | 「課題の取得件数を報告する。サービス用トークンを登録した取得元から受け取り、認証欄に使う。宛先候補はこのHTTPS APIだけで、固定した取得を一回行う。公開するのは今回の取得件数と『成功／認証失敗／通信失敗／応答の変換失敗』だけで、同じ正常終了へ戻る。トークン・本文・ヘッダ・生の失敗情報は公開しない。APIと固定変換が承認した件数・成否以外に秘密を反映しないことを信頼する。結果は未信頼のデータで、命令として使う許可は含まない」 | 人間は「秘密の登録」「このAPIの認証欄への使用」「件数と所定の成否の非機密化」を区別して確認し、この組を同じ方針へ保存する。エンドースメントはなし。成否の公開や信頼条件を承認しなければ公開報告を外して再検査する。保存した範囲は次回の同じ契約にも適用すると明示する |
| B | 「方針の改訂候補: 入力tは機密／未信頼、要求のRは当該host/port、別契約でHTTPS・GET・パス・認証欄・本文なしを限定する。結果の件数・四分類の成否と正常復帰に限定した非機密化を行い、完全性は未信頼のままとする。捕捉・pc・未承認の要求欄の依存は保持する。束・出口・全制約・信頼条件と変更前後は別添の一覧を参照する」 | 人間は全一覧とAPIへの信頼条件を確認し、方針の改訂全体を承認して保存するか差し戻す。成否だけを断る場合は候補を作り直し、その全体を改めて承認する |
| C | 「課題件数を報告するため、サービス用トークンの登録・認証先・応答の公開範囲の編集をLLMに任せる。変更ごとの人間の確認は行わない」 | 人間が委任を許すと、LLMが同じ方針へ変更を保存する。後から応答の本文も公開可能に編集した場合、その編集を人間が承認したとは記録しない。D3案Aの限定を管理者が不変条件として残すなら、LLMにもその範囲を越す編集を許せない |

案Aで示す成否の語は、これから許す結果の種類であり、秘密を取得して判明した実際の成否ではない。APIへの信頼を承認できなければ、整数へ変換することだけを理由に件数を公開しない。報告先の追加・成否と終了状態の対応の変更・検索条件や呼出回数を未信頼入力に選ばせる拡張も、同じ承認が覆うと推定しない。

### 機密ファイルの固定API送信

この例では結果の公開と送信先の承認を分ける。D4案Aの入力契約で「機密報告」と認定したファイルを、上記APIの固定した `POST /reports` の本文へ送る。必要なトークンは認証欄だけに使い、宛先と呼出条件は公開かつ信頼するものとする。

| 案 | 利用者に示す文の例 | 承認の操作と保存の例 |
|---|---|---|
| A | 「機密報告を報告APIへ送る。承認対象の入力契約を使い、実際の入力がこの分類に対応することを起動側に信頼する。宛先候補全体は指定のHTTPS APIで、機密報告は本文、トークンは認証欄だけに使う。一回送信し、リダイレクト・自動再試行はしない。原ファイルとトークンは秘密のまま保つ。応答・受付の有無・送信の成否を公開する許可は、この送信許可には含めない」 | 人間は入力登録・分類と、本文及び認証欄の受け手・用途を確認して同じ方針へ保存する。成否も報告したければ、D3の別の固定契約と信頼条件を示し、『受付応答あり／送信失敗／応答の変換失敗』等の限定した非機密化を追加して承認する。取得用の件数契約を流用しない |
| B | 「入力fとtの分類、要求各欄、pcと宛先の印、R内の全対象に対する出口制約を一覧で確認する。要求契約がHTTPS・POST・パス・欄を限定する。応答・成否はfとtの依存を保持し、非機密化とエンドースメントは追加しない」 | 人間は入力の認定根拠と全制約を読み、方針の改訂全体を承認して保存する。成否を公開する追加契約があれば、その改訂全体で改めて確認する |
| C | 「機密報告の送信に必要な入力登録と受け手・用途の編集をLLMへ任せる。送信後の成否を公開する変更も委任範囲へ含めるかを指定する」 | LLMが委任範囲内の方針変更を保存する。別の送信先や広い応答公開を認める編集まで委任すれば、それを人間の個別確認で止めることはできない。委任範囲を越す変更の拒否は別に必要である |

案A・Bで、送信後に公開の終了状態や後続の表示が変わるなら、応答の本文を捨てるだけでは足りない。成否の契約と制御への接続が閉じるまで受理済みにしない。追加する粗い受付情報も外部での処理完了や永続保存の保証ではない。

R全体への被覆は、今回選んだ一つの宛先が許されることより厳しい。候補に未承認のログ用ホストもあれば、案A・Bの承認画面はその不足を示し、検査した狭いRを使う修正か受け手の変更を区別して求める。host/portだけからHTTPSを導かず、別の要求契約でschemeを固定する。公開／未信頼の設定から宛先を作って拒否される場合にも、人間が表示を確認しただけで完全性を引き上げず、必要なら用途を限るエンドースメント契約を別に示す。

### OAuthトークンの保存と再読

取得時だけでなく、保存して別の実行で読み直した後も分類を保つ例である。D2〜D6の案AとS6の受理表では、0.0.14の初期の範囲で通す前提にしない。次の文案は、専用の保管口・再読・実対象の対応と成否への接続を閉じた後の承認を設計するためのものである。

| 案 | 利用者に示す文の例 | 承認の操作と保存の例 |
|---|---|---|
| A | 「OAuthで得たサービス用トークンを専用の保管先へ保存し、次の実行でも同じ秘密の分類で読み直して、指定APIの認証欄だけに使う。トークンの実値は方針へ複写しない。存在・保存の成否・再読の成否も秘密として扱い、公開報告は含めない。0.0.14の初期の範囲では保存と再読の接続が未対応なので、この承認だけでは実行できない」 | 人間は保管先の登録、書き込みと再読の分類、認証先・用途、保存後の再利用範囲を一組として確認する。対応後に同じ方針へ保存し、実値は保管口へ保存する。初期の未対応時点では有効な実行承認として登録しない。保管先や再読の契約を変えれば再提示する |
| B | 「保管口と再読の入力契約の同一性、保存先の出口分類、戻り値・存在・成否・pcの分類を一覧で確認する。秘密の分類を保存と再読で保持する。実対象への対応は未接続、0.0.14では未対応として拒否」 | 未対応の時点では実行を承認できず差し戻す。接続後、人間が全契約と制約を確認して方針の改訂全体を保存する。実値を一覧へ出さない |
| C | 「トークンの保管先と再読時の分類・受け手をLLMに設定させる。ただし、未対応の保存機能を設定だけで使えるようにはできない」 | LLMの編集権限を与えても未対応の実行は拒否する。接続後、LLMに再読時の公開分類まで変更させれば、保存前と同じ秘密を保つという人間の意図との一致は保証できない |

方針の保存と秘密の実値の保存は別の操作である。OAuthの認証手順全体、実際の保管バックエンド、OSのアクセス制限、安全なメモリ消去やダンプからの秘匿を本枝は確認していない。保存先のパスの字面が固定であることだけで、再読した実値と分類の対応を認定しない。

## 外部の方式と既存試作から確認できる範囲

2026-10-27に、[Jif 3.3.0公式文書「Label checking」](https://www.cs.cornell.edu/jif/doc/jif-3.3.0/label_checking.html)の本文を確認した。同文書の「Downgrading」は非機密化とエンドースメントに十分な権威を求め、方針の所有者の権威と結び付けている。「Normal and exceptional termination」は正常終了と例外の有無によって分かる情報にも印を付ける。これは緩和を行う者と値・成否を分けて扱う先行例であり、人間の承認画面や方針の保存方式の事例として引用するものではない。

この資料から、案Aの要約を読めば人間が誤らないこと、Benitoiteの限定契約がJifと同じ非干渉性を満たすことは導かない。他システムの承認UIの使いやすさ、LLMへ方針を編集させた場合の成功率、各案の確認負担と実装費用の差は未確認である。

[SD §2〜§4](../spikes/SD/findings.md#2-送信と観測の規則)は、同じ宛先値の所属、`pc ⊔ label(d) ⊔ label(v)` とR全体への被覆、公開pcでのfail・非再開・失敗しうる宛先検査を小モデルで確かめた。承認画面や保存の対応、実IOの成否、非機密化・エンドースメントとの合成、本番の一般ハンドラを証明したものではない。[SH2「評価の一致と観察の制約」](../spikes/SH2/findings.md#評価の一致と観察の制約)も、純粋で全域的な応答関数の下での型・効果と値・Emit列の一致の独立モデルであり、承認や情報フロー制御、非干渉性の証明ではない。

[S3 §5](../study/usage-and-flow.md#5-情報フロー制御と-lio)と[S5のハンドラの規則案](../study/information-flow.md#ハンドラワンショットの継続)も踏まえ、エフェクトを除いたことから秘密の依存や実際の契約使用を要約から消さない。SD・SH2は再試作せず、短い実績から本番の見込みも下げない。

## 設計者への一つの問い

共通の前提は、変更結果を同じ方針の改訂へ結び、秘密の実値を方針へ複写せず、承認で未対応の機能を通さないことである。案A・Bでは0.0.14の提示・承認・保存・保護はD2の信頼する起動側への前提とし、後のサーバへ承認・保存・失効と強制を接続する。承認の再利用と純粋な狭小化の適用条件はD9で選ぶ。

IFC-D7は、人間の承認の接点として変更の意味を示す要約（案A）、技術的な方針改訂全体（案B）、最終判断のLLMへの委任（案C）のどれを選ぶか。

推すのは案Aである。理由: 人間が秘密・受け手・用途・公開範囲と信頼条件の変更を判断でき、案Bで求める束や制約全体の理解を主な接点にせずに済む。要約と実際の方針・契約・検査対象の対応を保証する処理は必要であり、その費用は未確定である。
