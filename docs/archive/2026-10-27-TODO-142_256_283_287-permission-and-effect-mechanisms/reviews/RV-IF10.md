# RV-IF10: 情報フロー制御の判断案 IFC-D2〜D9（IF10.01〜.08）のレビュー

2026-10-27。Opus 5.5 のサブエージェント（effort medium）が、ブランチ `m013/if10` の HEAD `eec06547`（基準 `10099543`）の `if10.01`〜`if10.08` の判断案と results.md を読んだ。実装の担当（Codex）とは別の担当である。ファイルと git の状態は変えていない。ネットワークを使い、Jif 3.3.0 の文書と LIO の論文（2011）の本文を確かめた。応答を取りまとめが保存した（作業用のディレクトリの絶対パスは `<wt>` に置き換えた）。

## A. 読めば確定する指摘

### A1【重大】D5 案Aの「積の底」の制限が、未信頼の入力による失敗まで拒否する（D5 と D8 の整合）

- 場所: `if10.04/ifc-d5.md` の比較表の「fail・非再開」「機密性と完全性の積」の行、「案Aの被覆・合成印と積の制限」、表「明示的なfail」。関係するのは `if10.07/ifc-d8.md` の必須例1・2。
- 問題: D5 は「公開 pc の十分条件を積の底として用い」、`pc ⊑ ⊥` の ⊥ を「公開かつ信頼する印」としている。そう読むと、fail と非再開は、機密性だけでなく完全性でも pc が「信頼する」である位置に限られる。D3・D4 の案Aでは、ファイルの内容と HTTP の応答はすべて未信頼なので、CSV の解析の失敗で `die` する、応答の内容で失敗して終える、といった普通の処理がすべて拒否される。それでも D5 は、この制限の影響を「公開／未信頼の設定からの宛先検査を拒否しうる」としか書かず、問いの文面も同じである。D8 は、必須例1の「読み取り・解析の失敗…も含めて接続する」がこの制限と両立するかを確かめていない。SD は機密性だけのモデルであり、完全性の成分にまで同じ十分条件を課すのは SD を外挿した設計の選択である。
- 修正案: D5 に、制限が完全性の成分に及ぶ範囲を明記する。候補は (i) 信頼を要する後続の操作が失敗で消える場合に限る条件にする、(ii) 今の十分条件を保ち、拒否される典型（未信頼の入力による `die`・Assert・非再開）を例に挙げる、の二つ。問いの文面も「公開／未信頼の設定」に限らない形に直す。D8 は必須例1・2で、失敗を値として扱う形が前提かどうかを書く。

### A2【重大】D5 案Aの推す理由が、他の案Aのもとでは使い道が見当たらない

- 場所: `ifc-d5.md` の「設計者への一つの問い」の推す理由と例の表。関係するのは `ifc-d4.md`・`ifc-d8.md` の該当箇所。
- 問題: 案Aを推す理由は、案Bと違って「実行時の設定から選ぶ宛先も静的に検査でき」ることである。しかしこの形が受理されるのは、宛先が「公開かつ信頼する入力」から作られる場合だけである。D4 案Aでは設定ファイルが未信頼、D3 では応答も未信頼であり、どの入力が「公開かつ信頼する」になるのか（コードの定数、起動側が渡す値、方針の値）は八つの案のどれにも書かれていない。D8 は、必須の三例はどれも宛先が固定なので D5 案Bでも成り立つと書いている。0.0.14 の範囲で案Aが案Bに勝る点を支える根拠が示されていない。
- 修正案: D5 に「公開かつ信頼する入力の出どころ」の候補と、それがどの判断（D4・D7・D9）で決まるかを書く。問いには「三例は案Bでも満たせ、案Aの追加の利点は信頼する動的な設定を設けた場合に限る」と添える。案Aは案Bを単一の候補として含むので、費用の差が不明なまま案Aを選ぶ根拠もあわせて書く。

### A3【中】「信頼する起動側」が 07-01 の信頼関係にない新しい役割である

- 場所: `ifc-d2.md` の「関係する者と守る対象」と「案Aで明示する前提と観測」の表。`ifc-d7.md` も関係する。
- 問題: 07-01「関係する者」は、コーディングエージェント（LLM とハーネス）を信頼しない。D2 案Aは「利用者が信頼する起動側」が方針と契約を保護することを前提にしており、07-01 の表にない役割を足すことになる。「信頼関係を保つ」という記述と食い違う。主な利用の形（ハーネスの中で LLM が `benitoite` を起動し、方針のファイルも編集できる）で、どの部品がこの役割を担うのかが示されていない。「検査を通すために LLM が方針を緩める」形が 0.0.14 の保証の外になることも書かれていない。
- 修正案: D2 で「07-01 の信頼関係に新しい役割を一つ加える」と明記する。0.0.14 で前提を満たす具体的な構成の例（ハーネスの権限設定で方針を書けないようにする、など。どれも処理系の外）と、満たさない主な利用の形での保証の意味を書く。

### A4【中】D9 の代案B・Cは、すでに決まったことと衝突する

- 場所: `ifc-d9.md` の比較表の「既存決定との整合」の行と「設計者への一つの問い」。
- 問題: 案C（書式の設計をサーバまで待つ）は、README と判断19の【決定】「方針の書式の境界…は実装より前に設計する」に反する。案B（暫定の別文書）は、判断19の理由（許可の仕組みを二度設計しない）と衝突する。問いは実際には選択の余地がほとんどない。本当に未決なのは中身（項目の一覧、コードだけを変えたときの承認の再利用、純粋な狭小化を自動で適用する条件、TODO-109 へ記録すること）であり、これらには代案が示されていない。
- 修正案: B・C は「決定済みにより採らない」と一行で退け、中身の選択肢を問いにする（例: コードだけの変更で承認を再利用する案と、いつも再承認する案）。

### A5【中】D6 案Aを推す理由が、案Bとの違いを示していない

- 場所: `ifc-d6.md` の「設計者への一つの問い」。
- 問題: 推す理由の「派生値・制御まで追う」「トークン・パスワード・機密ファイルの受け手を区別できる」は、表を見るかぎり案B（印だけ）でも同じである。`Secret` の型を加える利点（診断の分かりやすさ、保証を付けない通常の実行でも直接の表示を止めること、型の上で取り出しが見えること）が論証されていない。案Aで等値を禁じる理由も書かれていない。
- 修正案: 案Bより得るものと、その費用（Lean 2〜6時間・処理系等 8〜20時間の内数）を対にして理由に書く。

### A6【軽】典型例の分類の語が D2 と D8 で食い違う

`ifc-d2.md` は、任意 URL への webhook と LLM の出力をシェルへ渡す例を「対象／拒否」とする。`ifc-d8.md` は同じ例を「対象外」（保証を付ける実行では拒否）とし、両文書の「対象外」の定義も違う。D2 の分類（対象／対象候補／後の版／対象外）と D8 の分類（受理必須／非必須候補／対象外／後送）は IF30 で一つに揃える必要がある。今の段階では、D8 に対応を一行書けば足りる。

### A7【軽】棚卸しの扱いの引用に誤りがある

`ifc-d8.md` は「Process P03、E06〜E09の一般の環境変数取得は保守的」と書くが、`inventory/console-process.md` では E06・E09 は「契約を設ける」、P03・E07・E08 は「保守的」である。修正案は「P03・E07・E08 は保守的、E06・E09 は契約を設ける」。ほかに確かめた ID と、三文書の SHA-256 および記録中の HEAD は一致した。

### A8【軽】リンク先がこの枝にない

`ifc-d4.md` と `ifc-d8.md` の `inventory/` へのリンクは、IF20 の枝にしかなく、`m013/if10` の上では切れている。取り込む順（IF20 を先に取り込む）を取りまとめが守るか、本文に「IF20 の取り込み後に有効」と書く。ほかの相対リンクと見出しの参照に切れはなかった。

### A9【軽】用語と造語

- 「開示先」（`ifc-d5.md`、`if10.04/results.md`）は README・decisions の写しだが、README が declassification の訳としては使わないと決めた「開示」を含む。同じ文書の「許す受け手の集合」に揃えるのを勧める。
- 定義なしの作業用の語がある。「合成印」（D5）、「狭小化」（D7・D9）、「後送」「受理必須」（D8）、「保証を付ける対象」（D2 が説明用と断っている）、「信頼する起動側」（A3）。0.0.14 で用語にするなら、用例を調べる必要がある（例: 「狭小化」に当たる narrowing / attenuation）。
- 手元の絶対パス、docs/todo へのリンク、旧訳語の判断名としての使用は見つからなかった。

### A10【軽】問いの文が長く、複数の選択を一文に詰めている

D3・D7・D8 の問いは、一つの案に複数の小さな選択を束ねている。D7 の案Aは要約の項目・承認の単位・責任の分担、D8 の案Aは必須の三例と「実行対象全体を拒否する」という拒否の単位である。D8 の拒否の単位は三案に共通で、代案（出口ごとの拒否）は一文で退けられている。問いの一文は「何を選ぶか」に絞り、案に共通する条件は前提として分けるのを勧める。

## B. 確かめないと分からない点

- B1（A1 の続き）: 完全性の成分で、fail・非再開を未信頼の pc に許した場合に、完全性の二実行の性質（D2 の「信頼する操作と結果の観測が一致」）が破れるか。終了状態を「信頼する観測」に含めるかが分かれ目である。SD は機密性だけなので、0.0.14 の試作で確かめる項目として IF30 へ渡すべきである。
- B2: D8 必須例1（公開 CSV）を 0.0.14 で実際に提供する形が決まっていない。D4 は「起動側が読み取り済みのデータを用意する」形と、「実対象との対応を信頼の条件として補う」形を示している。後者は事実上「字面の照合（案C）＋承認した信頼の条件」である。どちらを採るかで必須例の費用と保証の説明が変わり、どちらも見積もられていない。
- B3: D5 案C（出口で実行時に照合して送らない）は、00-01・判断14 がサーバより前に入れないとした「実行時の権限制御」に当たるか。D5 は当たらない扱いと再判断が要る扱いの両方に読める。どちらかを明記する。

## C. 問題がなかった点

- 八つの案はどれも冒頭で「採択済みではない」と書き、前の判断の案Aを仮の前提とし、別の案が選ばれたときに変わる点を依存の表に分けている。相手の案の中身との対応も、A6 以外では食い違いがなかった。
- 判断14（host/port と origin の違い、R は http/https の両方を覆う）、判断21（ネットワーク等の依存と切り離す、構成で意味を変えない）、P3（`Secret` の型は 0.0.14）、Q9(c)、訳語は、すべての案で守られている。構文・API 名・ファイル名を決定として書いた箇所はない。
- 費用の数値は S6「規模の見積もり」と一致し、内数を二重に足さないこと、不明なものを不明と書くことが徹底されている。
- SD・SH2 は再試作されておらず、確かめた範囲と未接続の範囲が分けて書かれている。
- 07-01 との対応（検査報告と実行の間のソースの同一性を保証しないこと、上限付き test の準備の順序）は 07-01 の本文と一致した。
- 一次資料: Jif 3.3.0「Label checking」の「Program counter labels」「Normal and exceptional termination」「Basics of label checking」「Downgrading」を確かめ、引用は主張の範囲に収まっている。LIO（Stefan ほか 2011）の `unlabel` の規則と、並行への拡張が将来の課題であることを本文で確かめた。D2 が引く節の番号（§2.2・§7）は、PDF の抽出の都合で確かめていない。Rust std の `canonicalize` と TOCTOU の節は未確認であり、07-01「ハーネスとの分担」がシンボリックリンクの差し替えへの防御を保証の外としていることを、D4 もあわせて引くのが望ましい（軽）。

## D. 八つの問いをまとめて尋ねるときの注意

1. 先に D2 に答えてもらう。0.0.14 の保証の枠と「信頼する起動側」の意味（A3）が、ほかの七つの前提である。主な利用の形でこの前提を満たす構成があるかを添える。
2. 次に D4・D3・D6。D4 は B2（公開 CSV を提供する形）とあわせて尋ねる。
3. D5 は D4 の後。「公開かつ信頼する入力」の出どころ（A2）と、積の制限が完全性に及ぶ範囲（A1）を問いに含める。
4. D8 は D3〜D6 の後。必須の三例が D5 の積の制限と B2 の形で実際に成り立つかに左右される。D3 案B・D4 案B・D6 案Cのどれかを選んだ場合は、D8 を選び直す必要が出る。
5. D7・D9 は最後。D9 は代案B・Cがすでに決まったことで退けられる（A4）ので、中身の小さな選択を問いにし直してから尋ねる。
6. 両立しない組（D3 案B と D8 案A、D6 案C と D8 案A、D7 案C と D2 案A）を一覧にして渡す。
