# RV-L50: L10〜L50 の形式化の全体のレビュー

2026-10-28。L50.4 の前の全体の独立レビューとして、Opus 5.5 のサブエージェント（effort medium）が、本線 `310564ea` の `8e32e06e..310564ea` の formal・設計書の差分と、README・decisions・plan-l10-l50・plan の停止条件、RV-L00・RV-L10〜RV-L40 とその対応、`l10.*/`〜`l50.*/` の results.md、01-12・07-04 の全体を読んだ。実装の担当とは別の担当である。リポジトリのファイルと git の状態は変えず、Lean はリポジトリの外の一時ファイルを `lake env lean -M 12288` で確かめただけである（`#print axioms` の抜き取りと grep による照合）。全体のビルドは走らせていない。応答を取りまとめが保存し、末尾に対応を加えた。

結論: 重大な指摘はない。中4件・軽6件。L50.4 で直してから R 段へ進めば足りる。

## 読めば確定する問題

### 中1: 表層の対象健全性に、結論まで届く例がない

- 箇所: `Surface/CoverExamples.lean` の `program_target_sound`、`Surface/Theorems.lean` の `surface_target_sound`。
- 問題: 例の main は `()` なので IO の事象に到達せず、結論は空に成り立つ。主定理のうち、非 Top の本番の例に結論まで当たっていないのはこの定理だけである（コアの側は `ioCall_reach_target_sound`・`handleLog_reach_target_sound`・`callF_reach_target_sound`・`callH_reach_target_sound`・`handleEtc_rejected` が当たる）。計画の「全 Top や空だけを非 Top の本番接続の成功と数えない」に照らして未了である（RV-L40 軽8）。
- 修正案: `ModelTargets` の表で、main が `Scope.checkPathIn` の結果を照合して `File.writeTextIn` へ渡す表層のプログラムを作り、到達した書き込みの事象の観測 `/data/a.txt` が上限 `{File.Write[/data/**]}` に許され、`/etc/passwd` が許されないことを `surface_target_sound` から導く。被覆の小例の `f`・`h` を main から呼ぶ形にすれば兼ねられる。

### 中2: L40.6c の案 α で変わった前提が、停止の表の行に書かれていない

- 箇所: plan-l10-l50 の停止の表の「節の添字 S と継続の型」の行、README の L40.6c の項、07-04「形式化で仮定するもの」の【決定】。
- 問題: 停止の表が例外として受け入れたのは「C-Sub を被覆にして L30.1 を証明し直すこと」だけだが、L40.6c は `Ty.Le`・C-Eff・表層の `E_Sub`・`B_Sub`・K-Handle と K-Handle-Fail の節の効果の前提も被覆にした。その結果、`delta_typed`・`io_typed`・`io_exists` の意味が値の型付けを通じて変わり、入力の型付けが広がる欄は表への要求が強まる。計画の停止条件は既存の欄の意味を変える場合を停止条件とする。07-04 と README の確認点 (16) に書かれているので隠れてはいないが、RV-L20 中1 と同じ類の、表にない前提の内容の変更である。
- 修正案: 停止の表の行に、これらの被覆化と三つの欄の意味の変化を明記する。設計者の確認を「欄の意味の強化を受け入れるか」という具体の問いに分ける。

### 中3: 検査器は `handle` の保護本体を構造上の包含で調べ、型付けより狭い

- 箇所: `Surface/Check.lean` の `.handleE` の腕（`acceptEff q (child path 0) (union q ε h) εbody`）、`Surface/Typing.lean` の `E_Handle`。
- 問題: 型付けは保護本体の `HasBlockQ` に `B_Sub`（被覆）を挟めるが、検査器は推論した本体の効果をそのまま構造上の包含で調べる。上限 `{File.Write[/data/**]}` の関数の中に `File.Write` を処理しない `handle` を置き、その本体で `/data/a.txt` へ書くプログラムは、型付けでは型が付くが検査器は断る。健全性の問題ではないが、L50.2 の R20 への申し送りどおりに Rust もこの位置を構造上の包含にそろえると、利用者から見える制限になる。部分適用も同じ形だが、型付けの側も構造上の包含である。
- 修正案: 検査器が本体の効果の各原子を ε の覆う原子へ写した効果 εb' を作り、それを構造上の包含で調べ、節の添字も εb' から選ぶ形にして型付けに合わせる（コアは変えない）。今の形を保つなら、制限として R40 の診断と 07-04 に書く。設計者に尋ねる。

### 中4: 接続定理の出現の番号の一致を示す補題がない

- 箇所: `Surface/ScopeSound.lean` の `scope_check_connection`・`scope_local_connection`・`scope_local_typed(_of_typed)`、`CheckAccept.accepted_check_connection`。
- 問題: 前提の出現の一覧の番号 k の式・`hreach`・`hrhs` は同じ k と同じ式を使うが、実行で到達した文の右辺が出現の一覧の k 番目と一致することは補題になっていない（L40.6 の申し送り）。言明は健全だが、実際の実行に定理を当てられることが示されていない。
- 修正案: `ReachBlock` の全ての構成子について出現の一覧の先行順の位置を辿る補題を置く（見込み 1〜2時間）。置かないなら、07-04「形式化で仮定するもの」に「番号の一致は R20 が同じ数え方で保証する」と信頼の対象として書く。

### 軽5: `stateTy_of_old` について、07-04 の書き方が補題の中身より強い

- 箇所: 07-04「証明する性質」の BA の段落、`Release/Lemmas/PresHelpers.lean` の `stateTy_of_old`。
- 問題: 補題の前提は新しい `StateTyE` と旧の `BuiltinOnlyOld` の組であり、旧の型付けの規則と旧の `ContTy` で型の付く状態は扱っていない。中身は `BuiltinOnlyOld.toNew` の一行である。
- 修正案: 「旧の `BuiltinOnly` を満たす末尾で新しい `StateTyE` が付く状態は `StateTy` に入る（`stateTy_of_old`）。旧の型付けの規則で型の付く状態との比較は示していない」に直す。

### 軽6: 「`CoreAssumptions` の欄は以前と同じ、`io_op` だけを変えた」という文が誤読を招く

- 箇所: 07-04「証明する性質」の信頼条件の分離の段落と「形式化で仮定するもの」、`Release/Assumptions.lean` の `CoreAssumptions` の docstring。
- 問題: 欄の名前と並びは同じだが、内容は `io_op` のほかにも変わっている（前の段落と L40.6c による意味の変化）。
- 修正案: 「欄の名前と並びは以前と同じ。L20.7 で内容を変えたのは `io_op` だけで、ほかの欄の内容の変更は前の段落のとおり」とする。

### 軽7: `release_exists` は `Ty.Le` の被覆化の影響を受けないのに、受けると書いている

- 箇所: 07-04「形式化で仮定するもの」の【決定】。
- 問題: `release_exists` の入力は `.opaqueTop o` の値であり、`Ty.Le` は関数の型でないところでは等号なので、V-Sub で型付く値の集合は変わらない。
- 修正案: 影響する欄の列挙から `release_exists` を外す。

### 軽8: 実例の表で `topTargeted` の形と資源の解放が一度も使われていない

- 箇所: `Release/ModelTargets.lean`・`ModelHttp.lean`・`Model.lean`。
- 問題: 三つの表のどれも `isResource := fun _ => false` なので、`release_exists` は空に成り立つ。旧 Top の形（`topTargeted`）の項目を持つ表もない。証明は一般形で閉じているので健全性の問題ではない。
- 修正案: 実例の表に `topTargeted` の IO の項目を一つ足し、`ShapeOk` と `io_target` を満たすことを示す。資源の型の項目もあればなおよい。

### 軽9: 構造上の包含のまま残した位置の一覧が足りない

- 箇所: 07-04「証明する性質」の L40.6c の段落。
- 問題: K-Empty（`Eff.Sub ε ε0`）、K-Let、K-Guard、状態の型付けの `ε1 ⊆ ε`、表層の `HasMain` の `Eff.Sub d.eff allowed`、部分適用も構造上の包含のままだが、一覧にない。C-Eff・E_Sub と組めば足りるので健全性の問題ではないが、R20 が境界を写す資料として欠ける。
- 修正案: 構造上の包含のまま残す位置を一覧にし、計算の側の被覆（C-Eff・E_Sub・B_Sub）で埋められるという理由を添える。

### 軽10: 局所解析の信頼の対象が「形式化で仮定するもの」に集まっていない

- 箇所: 07-04「形式化で仮定するもの」。
- 問題: 交換の `scopeAcceptance` の `patterns`・`hosts`（処理系の解析器が読んだ結果を Lean が信頼する）、`primResolve` が名前の解決を終えた構文を前提にする点、整数のリテラルの表し方の差、中4 の番号の一致が、この節にない。
- 修正案: Scope の局所解析の箇条を一つ足して、上の四点を載せる。

## 問題がなかった点

1. 既定の import の閉包に `sorry`・`admit`・`native_decide`・`axiom` はない。主定理11個と接続定理・例9個の `#print axioms` は標準の三公理だけに依存する。この改造で足した `maxHeartbeats` は `HasTypeCQ.inv_handle_failure` の一つだけである。既定の import の閉包の外にあるのは 0.0.8 の `Release/LegacyCheck.lean` だけである。
2. 主定理の言明の差は、`hb` の型を `CoreAssumptions` にしたこと、`step_sound` の `horacle` に観測を足したこと、新しい定理を足したことだけである。前提の内容の変更は、中2 を除いて停止の表か README の決定の行で説明されている。
3. 信頼条件の欄、表のデータ、型の注釈の範囲の正規形を解析器が保証すること、旧 Top の完全性の文言は 07-04 に載っている。
4. `WrongHandleTyped` は本番の規則から `ClauseSig` を替えただけであり（RV-L30 軽3 の点検は完了）、`handleEtc_rejected` で本番の型付けが断ることまで閉じている。
5. 被覆と許可の定義、K-Handle と K-Handle-Fail の写しは Lean と一致する。今回の改造の 07-04 の行には全て「Rust は未接続」がある。設計書が引く Lean の名前の抜き取り約40個は全て実在する。
6. 設計書と formal の差分に、「模型」、手元の絶対パス、docs/todo へのリンク、【未決】【要検証】はない。
