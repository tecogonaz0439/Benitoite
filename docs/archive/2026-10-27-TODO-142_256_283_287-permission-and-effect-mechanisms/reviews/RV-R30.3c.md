## 問題がなかった点

- 拒否の網羅: URL の角括弧の中の小文字と大文字、`::ffff:7f00:1`、`::ffff:7f00:0001`、`0::ffff:…`、`::0:ffff:…`、全展開の形は、パターン `::/0` と `127.0.0.1` のどちらでも `Scope.InvalidTarget` になった。先頭 0 の IPv4 部、`::ffff:127.1`、zone 付き、IPvFuture は既存の形式不良として InvalidTarget。IPv4 の受け手に届いたのは正当な `127.0.0.1` の 1 件だけで、`[::1]` と `[0:0:0:0:0:0:0:1]` は IPv6 の受け手へ正しく送られた。旧 `checkHost`・`checkEndpoint` では `::ffff:0.0.0.0`、`::ffff:255.255.255.255`、末尾ドット付き、16 進の形がすべて InvalidTarget になり、直前と直後の `::fffe:ffff:ffff` と `::1:0:0:0` は受理された。
- macOS のソケット: IPv4 へ接続したのは `::ffff:127.0.0.1` だけで、`::127.0.0.1`（IPv4 互換）、`::7f00:1`、`64:ff9b::127.0.0.1`、`::ffff:0:127.0.0.1` はどれも IPv4 に届かなかった。
- 入口の網羅: `HostTarget::Ip` を作る経路は `checked_scope::host_format`（旧二入口と静的な既知の引数の検査が共用）と `checked_request::endpoint` の二つだけで、両方が `host_target` を通る。送信側が IPv4 へ戻す呼び出しもない。
- 判定: `bits >> 32 == 0xffff` は `::ffff:0:0/96` にちょうど一致する。URL は `Ipv6Addr` で数値にしてから判定するので表記の違いに依らない。失敗の順（パターン、対象、ポート、所属）を保ち、未知のパターンと既知の射影の対象の組が E0460 になるのは「未知をどの値で埋めても Error」に合う。
- 静的と動的と交換: 共有の表（`checked-scope.json`）の期待を InvalidTarget/E0460 に改め、射影の旧入口の 2 例を除外（E0460）として加えた。R30.1 の正規化と矛盾しない。
- ほかの埋め込みの形: RFC 4291 §2.5.5.1・§2.5.5.2、RFC 3493 §3.7、RFC 6052 §2、RFC 8215 の読み方は正しい（外部の通信をしない条件のため、節の番号と URL は開いて確かめていない）。IPv4 互換の形と NAT64 を追加で拒否しない判断は macOS の実測とも合う。
- Lean: `productionRules`・`productionRules_sound`（`Surface/ScopeSound.lean` 439〜455 行）は `pat`・`tgt`・`hostPattern`・`reqTarget` をどんな関数でも受け取り、仮定を置いていない。`ModelHttp.checkRun` は `reqTarget = none` を invalidUrl に、endpoint 以外の種類を scopeFailure に対応させる。よって Lean の変更は要らない。旧 `checkHost`・`checkEndpoint` は `productionRules` の対象の外。01-12 の文字列の解析は形式化の外という記述とも合う。
- 規約と記録: 設計書に作業の ID はない。利用者向けのリファレンスと Skill に食い違う記述はない。`work.json` は check.sh 自身の終了 0、外側 489.627 秒で results.md と一致する。H を要らないとした判断に同意する。
