# RV-L40: L40.3b・L40.4〜L40.6（表層の範囲・検査済みの要求・接続定理）の定義・言明・仮定のレビュー

2026-10-28。L40 の段の後半の独立レビューとして、Opus 5.5 のサブエージェント（effort medium）が、本線 `ce6d22ff` の `f02f0ca2..ce6d22ff` の formal・設計書・改造の文書を読んだ。実装の担当とは別の担当である。リポジトリのファイルと git の状態は変えず、Lean はリポジトリの外の一時ファイル1件を `lake env lean -M 12288` で確かめただけである（`#check` 6件、`#print axioms` 24件）。応答を取りまとめが保存し、末尾に対応を加えた。

結論: 重大な指摘はない。中3件・軽7件。証明と主定理の字面に誤りは見つからなかった。中の3件は、主定理が扱うプログラムの集合と、文書の主張・設計者への確認の範囲とのずれである。

## 読めば確定する問題

### 中1: 判断 5 の被覆による効果の上限の包含を、表層の型付けが表さない。`acceptAtom` はどこにも接続していない

- 箇所: `Surface/Typing.lean` の `E_Sub`・`B_Sub`（`Eff.Sub` は構造上の包含）、`Surface/ScopeAccept.lean` の `acceptAtom`・`acceptAtoms`、L40.4 の results「RV-L30 の条件への対応」1、01-12「Scope の必須の判定の受理と拒否の理由」の冒頭の【決定】。
- 問題: 判断 5 は効果の範囲の包含を一原子の被覆で判定すると定めるので、上限 `File.Write["/data/**"]` の関数の本体が `File.Write["/data/a.txt"]` を持つ場合も受理される。表層の型付けは構造上の `Eff.Sub` だけを持ち、値型の共変もないので、この本体は `p.WellTyped` に入らない。`acceptAtom` は例のほかに呼ぶ箇所がなく、型付けと組み合わせても構造上の包含と同じ集合しか通らない（`acceptAtom_of_mem`）。したがって `desugar_typed`・`surface_effect_soundness`・`surface_target_sound` は、被覆だけで受理されるプログラムについて何も言わない。L40.4 の「被覆を Release に入れる必要は出なかった」は、表層にこの包含を入れなかったから出なかっただけであり、停止の表が条件にした判断を実際には行っていない（RV-L30 の「確かめないと分からない点」の2点目が開いたまま）。
- 修正案: 設計者が選ぶ。(a) 表層の被覆による包含を、脱糖で明示の拡大を差し込む形にし、コアの構造上の包含は保つ。(b) 効果の上限の包含を構造上に限り、判断 5 の被覆は拡大の許容と範囲の受理だけに使うよう判断を読み替える。(c) 形式化が扱うのは構造上の包含の部分集合だと 07-04 と 01-12 に明記して受け入れる。どれを選ぶまでも、L40.4 の results の当該の文の読み方を記録する。

### 中2: 表層の「節の添字は規則の値だけ」は、本体の効果を広げれば Top に届くので、型付けの集合を狭めていない

- 箇所: `Surface/Typing.lean` の `E_Handle`・`HasClausesQ`・`B_Sub`、L40.5 の results、README の L40.5 の項と確認点 (14)、01-12 の表層の `handle` の箇条。
- 問題: `E_Handle` の εbody は型付けの導出が選ぶ本体の効果である。`B_Sub` で同じ名前の別の原子を足すと `Eff.clauseRange` は Top になり、`handled` は名前の全ての範囲の原子を除くので `Eff.Sub εbody (ε ∪ handled)` も成り立つ。したがって Top の操作の型で型付ける節も表層の型付けで導出できる見込みが高い（規則の字面からの判断で、Lean では組んでいない）。「範囲の変数を持つ表では狭まる向き」は型付けの関係については成り立たない見込みである。「一意に選ぶ」は、εbody を固定したとき（`cons_sig_unique`）と最小の効果を使う検査器（`clauseOpSigIn_eq`、`handle_case`）についての性質である。
- 修正案: 表層の導出で Top の添字に届く例を Lean で確かめる。01-12・README (14) を「規則の値を選ぶのは εbody を固定した型付けと検査器であり、`B_Sub` で広げた本体の効果からは Top にも届く。`p.WellTyped` は狭まらない」に直す。停止の表の行への当てはめは変わらない。

### 中3: 必須の判定の受理は、検査器にもプログラム全体の述語にもつながっていない。設計者への確認点にも入っていない

- 箇所: L40.4 の results のずれ 3、`CheckTables.checkProgram`、`Surface/ScopeSound.lean` の接続定理の前提 `hacc : acceptBody …`、README の L40.4 の項。
- 問題: Lean の型検査器（`checkProgram`）は、許容される範囲の列なら何でも受理する。`acceptBody` は本体ごとの独立の関数で、`p.WellTyped` か `checkProgram` と全ての定義の本体の受理とを合わせた述語も、それを前提にする定理もない。接続定理は一つの本体と表層の具体の評価（`ReachBlock`。L40.3 の過大近似の評価）について述べ、脱糖したコアの実行の到達から `ReachBlock` を得る補題はない（07-04 には限界が書いてある）。判断 9 の「狭い契約は被覆を確かめたときだけ受理」は、Lean ではまだどの定理の前提にもなっていない。
- 修正案: README の確認点に加える。L50.2 か L50.4 の行に、検査器の入口へ受理を組み込むことと、プログラム全体の受理の述語を置くことを明記する。コアの実行と `ReachBlock` の対応の補題を置くか、置かない判断を記録する。

### 軽4: 範囲の列が空のとき、接続定理の S の部分が空に成り立つ

- 箇所: `ScopeAccept.acceptRanges`（`rs = []` を常に受理する）、`scope_check_connection`・`scope_local_connection`。
- 問題: 接続定理は型付けを前提にしないので、列の長さの条件が入らない。`rs = []` の呼び出しでは S の結論が何も言わない。
- 修正案: `acceptRanges` に列の長さの一致を求めるか、接続定理に `rs.length = s.nranges`（または `RangeAdmissible`）を前提として加える。

### 軽5: 「既知の Top」は `acceptCall` の経路では作られず、拒否の理由の割り当てが文書と食い違う

- 箇所: `Required.ofIndex`（Top は必ず `unknown` か `exceeded` になる）、01-12「Scope の必須の判定の受理と拒否の理由」。
- 問題: 引数の型に明示された Top から来た Top も `unknownSource` と報告され、本体のどこかで予算を超えていれば `budgetExceeded` と報告される。`acceptRange (.known .top)` の例は本体の受理では起きない場合を確かめている。
- 修正案: 文書を実際の割り当てに合わせる。明示の Top を区別したいなら、記録に由来の印を持たせる。R20 と DET-05 の照合の観点に入れる。

### 軽6: `fromEff` の判定は既定の候補では何も拒否しない。07-04 が主張より強く読める

- 箇所: `Exchange/Convert.lean` の `fromEff`、07-04 の「表層の節の添字と脱糖の範囲」の行。
- 問題: 今の経路に黙った欠落がない根拠は論証だけである。範囲付きの不透明型は `fromTy` が、範囲の列は `fromVal` が誤りにするので、この二つは防げている。
- 修正案: 07-04 に「この版の既定の候補では何も拒否しない」と書く。候補に検査器の `q.atoms` を渡し、検査器の不変条件から `unlistedAtom?_complete` の前提を満たす補題を置けば、完全性を Lean で示せる（L50.1 でもよい）。

### 軽7: `scope_local_typed` の前提 `hc` は局所解析から得られない

- 箇所: `Surface/ScopeSound.lean` の `scope_local_typed`、L40.6 の results。
- 問題: `CheckedModels` を `Val.target?` で述べたので、`Scope.PathIn` の値が検査済みの要求の値でないことは利用側が別に示す必要がある。`Boundary.checkDelta` は要求の検査でも `.checked` を作り、`ModelHttp.checkRun` は `.checkedRequest` を作るので、同じ要求の検査に成功値の形が違う二つのモデルが並ぶ。
- 修正案: L50.3 の整理の対象に明記し、`hc` を値の型付けから得る系を置く。

### 軽8: 表層の対象健全性が空に成り立たないことを示す表層の例がない

- 箇所: `Surface/Theorems.lean` の `surface_target_sound`。
- 問題: 構成は正しいが、範囲付きの上限を持つ表層のプログラムで前提を満たし観測が空でない例がない。
- 修正案: `ModelTargets` か `ModelHttp` の表で、`checkPathIn` と `writeTextIn` を使う小さな表層のプログラムの例を L50.4 で置く。

### 軽9: `Http.RequestIn` に要求を持たない値を許すことの影響

- 箇所: `HasTypeVQ.V_Checked`、`ModelHttp.valueRun`。
- 問題: 「到達した `Http.RequestIn` の値は検査した要求を保持する」という不変条件はなく、検査した要求が送信まで保たれることは検査の δ の出力についてだけである。射影の δ が要求を作り出す表も仮定を満たす。対象健全性への影響はない。
- 修正案: 判断 7 の保証は R30 と K10 の照合にあり、Lean は対象だけを保証すると 07-04 に一文で書く。

### 軽10: L40.4 の「表層の型付けが旧と同値」は前提の水準の補題だけ

- 箇所: L40.4 の results。
- 問題: `ePrim_premises_iff_old`・`clauseSig_iff_old_of_rangeFree`・`sel_congr_of_rangeFree` は規則の前提の同値で、型付けの関係全体の同値は説明にとどまる（RV-L20 軽9 と同じ限界）。
- 修正案: README の受け入れた限界の項に L40.4・L40.5 の分を加える。

## 確かめないと分からない点

- 中2: 表層の導出で `B_Sub` により Top の添字に届くことは、規則の字面からの判断である。
- 中1: Rust の型検査器が判断 5 の被覆で効果の上限を受理するかは、R20 の前なので確かめられない（判断 5 の文面はそう読める）。
- 接続定理の前提にした番号の一致が全ての `ReachBlock` の構成子で成り立つかは、補題がなく例で確かめた範囲だけである（L50.4 に入れた）。

## 問題がなかった点

1. 九つの主定理の字面は変わっていない。前提の内容の変更は停止の表の「値の所属の規則」「表層の側の前提」「節の添字 S と継続の型」の行に収まる。
2. Release の C-Sub と `Eff.Sub` は構造上の包含のままである。
3. 受理の判定: `acceptRange` は Top を覆うのが Top だけであることを満たし、DET-05 の四つの理由を返す。健全性は番号の重複を仮定しない全称の形で述べる（RV-L30 軽5 は閉じた）。受理の判定と接続定理は区間解析の評価と警告を import しない。受理を被覆にしても、S への所属は δ の確かめと被覆の健全性から得られるので健全である。
4. `clauseRangeIn_eq` の前提は、検査器の `handle_case` で不変条件から満たされている。
5. `valContent` は表のデータと読むのが妥当である（誤った値は `delta_typed` で捕まる）。旧の像の補題と `ModelHttp.assumptions` は空ではない。
6. 抜き取りの24件の公理は標準の三公理の部分集合だけである。sorry・admit・native_decide・axiom・`maxHeartbeats` の追加はない。
7. 新しい 07-04 の行はどれも「Rust は未接続」と書く。「模型」、手元の絶対パス、docs/todo へのリンク、【未決】【要検証】はない。
