# RV-R30.3: RequestIn の実通信への引き渡しの照合の独立レビュー

2026-10-29。対象は R30.3 の未コミットの差分（02-09・03-09・07-04 の文書だけ）と `r30.3/` の results.md・ログ。作業用のディレクトリは書き換えず、scratchpad の target で処理系を一度ビルドし、ループバックの受け手（`127.0.0.1` と `::1` の 18081・18082）に対して 25 件の URL を、`checkRequestIn` で狭いパターンとちょうど一つのポートに検査してから `requestInValue` で取り出して `Http.send` で送った。外部への通信はしていない。台本・受け手・出力は `r30.3/rv-probes/` に写した（絶対パスは `<probes>` に伏せた）。

結論: R30.4 へ進んでよい。中2・軽5。検査の後に要求や endpoint を取り替える経路はなく、受理した URL は検査と同じ host・port へ送られる。条件は、中1 を R30.3 の取り込みの前に直すことと、中2・軽1・軽2 を R30.4 の依頼の契約に書き足すこと。

## 問題がなかった点

- 経路の表の行番号と内容は今の実装と一致した（`endpoint`・`request_url`・`alloc_fields`・`request_in_value`・`widen_request_in`・`read_request`・`PreparedRequest`・`validate_request`・`execute`・`make_agent`・`send_done`・`complete`）。検査の後に別の要求や endpoint へ取り替える経路はない。`send_done` は `_args` を使わず、作業用のスレッドには `Lend::Nothing` と Rust が所有する値だけを渡す。`RequestIn` は Opaque として登録され、作るのは `checked_request::check` だけで、参照実行器も同じ組み込みの関数（`call_builtin_scoped`）を呼ぶ。
- URL と実効 endpoint: 検査と送信の両方が同じ文字列を同じ `http::Uri` で読む。ureq の `DefaultResolver::host_and_port` は `authority.host()` と既定のポートで接続先を決め、`Authority::port` は `rfind(':')` で探すので、角括弧の中の `:` が既定のポートとすり替わる入力はない。受理した URL（大文字の scheme、先頭に 0 を付けたポート、`?@…`・`#@…`・`/@…`・`//…`、`[0:0:…:1]`、`LocalHost`）はすべて検査した host と port に接続した。`[::1:18082]`、ポートの後の余分な `:`、`\@`、`%3A`、末尾のドット、`+` 付きのポート、userinfo、`http:host`、`http:/host` は拒否された。fragment は wire に出ず、query は保たれた。
- 非追従の前提: ureq 3.4.2 は `max_redirects(0)` のとき追従せずに 3xx を返す（`config.rs` の `max_redirects_do_error` は `max_redirects > 0` を条件とする）。
- V-Checked の保証の所在の記述は Lean の `checkRun`・`valueRun`・`firstTarget` と一致し、言い過ぎはない。
- work: 変えた三章を読む検査はなく、文書だけとして検査を選ばなかったことは妥当。設計書の変更に新しい作業の ID はない。
