### 1. 設計者の決定との整合

**R1（中）synthesis 第2節・第4節の案1「実用で得るもの」、推す理由2**

- 問題点: 設計者は実用の機能を権限制御と同じ重みで評価するよう指示した（README「設計者の決定」）。共通の条件の観点3は、効果を具体的な `.bnt` の擬似コードで示し、今の仕組みとの差を必ず示すよう求めている。案1 の実用の価値（関数の境界を越える数値の条件、契約と生成器の一致）は、2.1 の表の一行と 2.2 の一項目で述べるだけで、利用者（LLM が書く日常の自動化のスクリプト）のどの誤りを、第6弾の局所の区間の解析と `Range` の検査済みの値（`CheckedInteger` など）が既に捕まえない形で捕まえるのかを示していない。一方、利用者の目に見えるテストの機能（`Task.withTimeout` の仮想時間、`with` の解放の順の観測）は、第5節で「新しい項目として登録する」に回され、どの案にも入っていない。実用の評価が「重い項目の副産物として何が得られるか」の向きになっており、実用の機能を起点に案を比べていない。

### 2. 推す案の論証

**R3（重大）synthesis「推す案と理由」の理由1、案1「権限制御で得るもの」**

- 問題点: 理由1 は「型の重い候補のうち案1 だけが、サーバモードの実行前の判定と表示に使える情報（既知の対象の上限）を作る」とする。しかし案1 は「既存の API の引数に篩を課すと動かなくなるので、0.0.13 では課さない」としている。IO の関数がポートを `Integer` で受け取るままなら、利用者の関数の引数に付けた篩は、実際の操作の対象と結び付かない。S2 は、篩が「対象」に使えるのは「篩を満たす値だけを IO が使う規則まで接続すれば」とし（S2 §2.2）、範囲付きのエフェクトについても「IO が任意の `String` を受け取る規則のままならこの価値は得られない」と書く（S2 §1.3）。従って、案1 の範囲のままでは数値の対象の上限 `R` は得られず、権限制御への寄与は「後の範囲付きのエフェクトの部品」に留まる。パスとホストの字面の上限は Scope の局所解析が担うが、これは重い項目でなく、案3 にも入っている。案1 と案3 の権限制御での差は、ほぼ無くなる。
  - なお synthesis 6.1 は、S2 の §1・§2 を「見出しと比較表と申し送りだけ」読んだとしている。上の二つの条件はその読んでいない本文にある。
- 修正案: 次のどちらかにする。(a) 案1 に、ポートを受け取る IO の関数の新しい入口（篩付きの引数、または `CheckedEndpoint` を受け取る版）を加え、それが互換性と大きさに与える影響を見積もる。(b) 理由1 を取り下げ、案1 の権限制御での寄与を「数値の契約と包含の部品」と書き直し、推す理由を実用と形式化の再利用に絞る。(b) の場合、推す案の比較をやり直す（R4）。

**R4（重大）synthesis 第4節の案の並び、第5節の「範囲付きのエフェクト」の行、questions の Q1**

- 問題点: TODO-142（範囲付きのエフェクト）を中心にする案を比べていない。比べるべき理由は四つある。
  1. TODO-283 の表で「対象」の行に直接対応するのは範囲付きのエフェクトであり、S2 は「操作の種類」と「対象」に直接対応し関数の契約の差分にも使えるとする（S2 §1.2）。ポート・パス・ホストの三つを一つの仕組みで扱う。
  2. 見積もりは Lean 28〜65時間・処理系 34〜80時間（試作 142）で、案1 の中心（32〜80・40〜100）より小さい。S2 は「この値を上限とはできない」と注意しており（S2 §1.6）、案1 の値も R5 のとおり過小の疑いがあるので、どちらが小さいかは未確定だが、案1 を明らかに下回る根拠はない。
  3. docs/todo の TODO-250「形式化の重さによる組み方」の案は、改造1 を TODO-142、TODO-022 を「ほかが落ち着いてから」の最後としている。synthesis は後半だけを引き、順序を逆にする理由を書いていない。
  4. 第5節は範囲付きのエフェクトを「後（案1 の後）」とし、理由に S2 §9.3 を挙げる。しかし §9.3 は、範囲付きのエフェクトに「実際の操作の対象」を結ぶ定理が要ると書くだけで、TODO-022 の篩型が先に要るとはしていない。パスとホストの包含の判定器は案1 では作られない（S2 §9.1 の一行目は、パス・ホストに新しい対象領域が要るとする）。「範囲付きのエフェクトへ進む道の一段」（要約・理由3）は根拠が弱い。整数の区間の包含は第6弾で既にある。
  - 範囲付きのエフェクトは 0.0.8 の三種類のうち二つ（エフェクトに値を持たせる、エフェクトを外す規則）に当たり、`mutual_cover_not_equality` の反例で `Eff.eq_of_sub_of_sub` を保てない（S2 §1.6）。不利な点は実在するので、比べた結果として退けるのはありうる。比べずに後へ回すのが問題である。
- 修正案: 案4「範囲付きのエフェクト（閉じたパターンに限る）を中心に、Scope の局所解析を表層の段として相乗りさせる」を加え、案1 と同じ項目（得るもの・形式化の難所・大きさ・互換性）で比べる。範囲なしの `File.Write` を全対象の上限として残せば追加として始められる（S2 §1.7）ことも書く。TODO-250 の順序を変えるなら、その理由を書く。Q1 の選択肢に案4 を加え、Q2 の試行に「範囲付きのエフェクトの包含と型の等号の扱いの短い試行」を加える。

**R5（重大）synthesis 案1 の「大きさ」「形式化」、推す理由3**

- 問題点: 案1 の中心は「閉じた整数区間の篩型を、関数の引数と戻り値の契約に置く」ことで、大きさに試作 022 の Lean 32〜80時間・処理系 40〜100時間を使う。しかし試作 022 の `findings.md` の見積もりの表では、この値は「閉じた整数区間・長さを Release の型と部分型へ直接追加」の行であり、「関数の契約へ拡張」は値に依存する篩と同じ次の行（Lean 80〜200時間・処理系 80〜240時間）に入っている。docs/todo の TODO-022「篩型の本実装」も、段を「定数の端の区間の型と部分型 → 関数の契約 → 値に依存する範囲」と分けている。端点を定数に限った関数の契約が前の行に収まるのか、次の行の一部が要るのかを synthesis は論じていない。また理由3 の「重い項目の中で新しい難所が少ない」は、S2 §2.6 の「主な難所である部分型・置換・主定理への接続は残る」「`Ty.Le.eq_of_not_fn` 等の補題を変える」「三種だけが重い改造の全てではない」と食い違う。
- 修正案: 案1 の範囲を「定数の端点の区間の型と部分型」と「関数の契約」のどこまでとするかを明記し、見積もりの行を合わせる。関数の契約まで含めるなら、次の行のどの部分が要るかを示して幅を広げる。理由3 は「区間の包含・交差・合流の定義と証明を再利用できるが、部分型・置換・主定理への接続は新しい難所として残る」と書き直す。

### 4. 見積もりの根拠

**R9（中）synthesis 案1・案3 の「大きさ」**

- 問題点: 三点ある。
  1. 案1 は篩型（32〜80・40〜100）と Scope の解析（12〜28・16〜36）を足して 44〜108・56〜136 とする。S2 §11 は自らの比較の表について「各行の範囲が重なるので合算しない」と書いている。二つは区間の領域と成功値の要約の基盤を共有するので、単純に足すと重なりを二重に数える一方、統合の検査とレビューの費用は数えていない。足し方の根拠を書いていない。
  2. 案3 は「hefty の最初の試行 10〜20分、全体で 1〜3時間」を Lean の時間の幅に並べる。10〜20分は TODO-142 の試作の実績から取った最初の試行の時間であり（S1「本番へ入れる場合の大きさ」の表）、他の行の本実装の時間と性質が違う。また案3 はハンドルの小モデル（Lean 8〜20時間）を含め、Q2 は「サーバモードの設計の前に回す」とする。それが 0.0.13 の中か後かが読み取れない。
  3. `Secret` は三案すべての相乗りだが未見積もりで、表示・JSON・`die`・テストの報告・機械向けの診断の経路を確かめていない（synthesis 6.1）。相乗りが軽いという前提が崩れると、どの案でも重い項目の枠と競合する。三案に共通なので案の順位は変えないが、Q6 の推す内容（相乗りさせる）の前提である。
- 修正案: 案1 の合計は「篩型の行を中心に、Scope の解析が共有の基盤の上に加える分」として幅を示し直すか、合算しない理由を書く。案3 の試作の時間は別の列にし、ハンドルの小モデルを案3 に含めるかを Q2 と揃える。`Secret` の経路の棚卸しを Q6 の前提として明記する（今は「確かめてから決める」とあるので、その結果が出るまで Q6 を決められないことを Q6 にも書く）。

### 5. 事実の正しさ

結論を左右する誤りは見つからなかった。確かめたのは次のものだけである。

- 7.3 の「操作の宣言はエフェクト変数を持てない」: san_benito の `crates/benitoite/src/syntax/parser/effects.rs` の 716〜719行のテストが、`effect E` の中の `function op[effect A, effect B]() -> Unit uses Console.Write` に E0510 を三つ求めることを確かめた。一致する。

- 1.2 の「既存の IO の関数は対象を `String` で受け取る」: docs/todo の TODO-142（0.0.9 の記述）が「既存の IO の関数は今も `String`・`Integer` を受け取り、検査済みの値を求めない」と書いており、一致する。この事実が R3 の根拠である。
- 外部の事実（7.2 の V1〜V4）は結論を左右しないので確かめていない。

### 7. S4-notes の所見

**R13（中）S4-notes の冒頭「重大に当たるものはなかった」と S2 の所見**

- 問題点: S2 の本文に、S4 の推す理由を弱める条件が二つある（S2 §1.3 と §2.2 の「IO が検査済みの値や篩を求めない限り対象の価値は得られない」、S2 §11 の「合算しない」）。S4-notes はこれを扱わず、S2-1（Scope の解析の価値と費用）だけを中として挙げた。読んでいない節があることは冒頭に明記してあり誤りではないが、S2 の §1・§2 は S4 が推す案の根拠そのものであり、読む範囲の選び方が結論に響いた。また S2-1 は Scope の解析の価値が費用に見合うかを問う所見だが、synthesis は Scope の解析を三案すべてに入れたままで、S2-1 への答えを書いていない。
- 修正案: S4-notes に、S2 §1.3・§2.2 の条件を案1 の論証が満たしていないこと（RV-S4 の R3）を S2 の所見でなく S4 自身の課題として記す。S2-1 については、synthesis で Scope の解析を入れる理由（費用に対して得るもの）を一段落で答える。

**R14（軽）S4-notes の S2-2・D6**

- 問題点: S2-2 と D6 は、Scope の解析が「Release と主な定理を変えないので重い項目に当たらない」とする。結論は妥当だが、S2 §3.6 は Lean 12〜28時間を見込み、案1 の篩型と Lean の段を取り合う。D6 自身がそう書いているので誤りではないが、「重い項目に当たらないので相乗りできる」と「Lean の段の長さで順序を決める」が同じ所見に並び、相乗りの可否の結論が読み取りにくい。
- 修正案: 「相乗りは決まりの上では可能。ただし Lean の段を伸ばすので、案1 と組むなら第6弾と篩型の後に回す」と一文で結論を書く。

### 8. 用語と文章

判断を誤らせる用語の問題は見つからなかった。「上限」「方針」「精緻化」が用語集にないことは synthesis 7.4 が自ら挙げている。一点だけ、要約と理由3 の「範囲付きのエフェクトへ進む道の一段」「契約と包含の土台」は、整数の篩型がパスとホストの範囲の土台にもなるように読める。S2 §9.1 のとおり、土台になるのはポートの整数の範囲だけである（R4 の4）。読み手が案1 の権限制御への寄与を大きく取らないよう、「ポートの範囲の土台」と限って書くのがよい。

## 推す案についての判断

案1 を推すことには、今の論証のままでは同意しない。権限制御への寄与（理由1）は、IO の関数が篩付きの値を受け取らない限り成り立たず、案1 はそれを範囲から外している（R3）。大きさは関数の契約を含まない段の見積もりを使っている疑いがあり（R5）、範囲付きのエフェクトを中心にする案と比べていない（R4）。実用の価値も、今の局所の区間の解析と検査済みの値との差で示されていない（R1）。代わりに推すのは、Q1 に案4（閉じたパターンに限った範囲付きのエフェクトを中心にし、Scope の局所解析を表層の段として相乗りさせ、範囲なしの `File.Write` などを全対象の上限として残す）を加え、範囲を決める前の試行（Q2）を「範囲付きのエフェクトの型の等号と包含の扱い」と「端点を定数に限った関数の契約の型付けと置換」の二つにして、結果を見てから重い項目を選ぶ進め方である。理由は三つある。一つ目に、案4 は「対象」の行に直接答え、ポート・パス・ホストを一つの仕組みで扱うので、「権限制御に使う型と仕組みを決める」という 0.0.13 の位置付けに最も近い。二つ目に、案4 の見積もりは案1 の中心と同じ程度かそれ以下で、TODO-250 の既存の順序（TODO-142 を先、TODO-022 を後）とも一致する。三つ目に、案4 は 0.0.8 の難しい三種類のうち二つに当たるので、試行の前に推し切るのは早く、試行で行き詰まった場合の退き先は、権限制御の寄与で案1 とほぼ差がない案3 になる。どちらの重い項目を選ぶ場合でも、IO の関数が対象を何で受け取るかを、0.0.13 で決める問いとして設計者に示す必要がある。
