## 指摘

### 中1: IFC-D1 の行き先が落ちている

- 箇所: decisions-transfer.md「回答で決まらず残った点」と末尾の段落。
- 問題: decisions.md「情報フロー制御の設計者への問い」は「IFC-D1 の対象表記と方針の対応も IF10 の IFC-D9 と合わせて確定する」と書くが、IF10.08・IF10.09・IF30 のどれも IFC-D1 を扱っておらず、U01〜U11 にもない。
- 修正案: U 表に「IFC-D1（対象表記と方針の対応）は八つの問いに含めず、回答していない」を足す。決まっている境界には policy-items.md の「操作の種類・対象の許可と対象範囲の解釈」の行を書き（0.0.13 の閉じた範囲と意味を対応させる。範囲の構文は判断3を再選択しない）、行き先を TODO-109 と 0.0.14 の境界設計とする。末尾の段落の「本表の残り」に IFC-D1 を名指しする。

### 中2: 「固定 origin に限る」が適用される範囲を広く断定している

- 箇所: decisions-transfer.md「IFC-D5」第1段落、acceptance.md の EX04 の行、handover.md TODO-269「3.」の冒頭。
- 問題: 転記の文は「0.0.14 はコードの固定 origin への要求に限り、動的設定からの宛先選択は受理しない」と書き、すべての HTTP 要求を一律に限るように読める。判断案の言い方は狭く、D5 の案 B の説明は「秘密の送信先はコードの固定した origin に限る」であり、例はどれも秘密の本文を送る場合である。D8 は「公開だけの既存プログラムから機能を一律に削除する判断でもない」と書く。棚卸しの EX04 は、公開の本文だけを任意 URL へ送る形を別の候補として挙げているが、acceptance.md の EX04 はこれを落としている。
- 修正案: 決定の文を「秘密や未信頼の依存を含む送信（L が積の底でない送信）」の宛先を固定 origin に限る形に絞る。公開かつ信頼する本文だけを動的な宛先へ送る形の扱いと、保証を付ける実行と通常実行の区別の有無と形を U 表に未決として足し、EX04 の「まだ候補・未確認の接続」の欄にも書く。

### 中3: 「保証を示す実行」を定義なしに使っており、モードの有無が決まったように読める

- 箇所: decisions-transfer.md「IFC-D4」、acceptance.md の冒頭と EX07 の行。
- 問題: D2 は、この語を「新しい術語や CLI モードとして採用する提案ではない」と断り、通常実行にどの既存機能を残すかを D8 と IF20 へ渡している。IF30 はこの断りなしに「保証を示す実行では拒否する」「通常実行が残っても」と書き、二つのモードを持つことが決まったように読める。U10 の用語の点検にもこの語は入っていない。
- 修正案: 初出に D2 と同じ断り（保証を付ける対象として検査する実行を指す説明であり、CLI のモードや切り替えの決定ではない）を添える。通常実行を残すかとその形は U 表に未決として足し、この語を U10 の点検の対象に加える。

### 中4: 非機密化とエンドースメントの契約をどこまで設計したかの区分がない

- 箇所: handover.md TODO-269「1.」と全体の構成。
- 問題: README と判断19は、0.0.13 で非機密化とエンドースメントの契約の設計まで行うとし、plan.md も TODO へ契約を写すとする。IF30 の中で契約の条件は散らばっており、エンドースメントの契約は「用途を限る別の契約を要する」「具体的契約と合成は0.0.14で設計する」とあるだけである。このまま「契約の設計」を済んだこととして TODO-269 へ写すと、具体的な契約がもうあるように読める。
- 修正案: handover.md に小節「非機密化とエンドースメントの契約（0.0.13 で決めた範囲）」を足し、決めた項目と条件（固定操作・変換・版の同定、許した要求由来だけを緩めること、値・粗い成否・用途・呼出条件、完全性を未信頼に保つこと、外部 API の非反映を信頼条件とすること、エンドースメントを非機密化と別に承認すること）、0.0.14 へ送ったもの（固定 API ごとの具体的な契約、エンドースメントの確認条件と合成）、根拠（U04・U06）を分ける。TODO-269「1.」の言い方も「契約の項目と条件の設計」に直す。

### 中5: EX03 の受理表から IF20.02/C19 が落ちている

- 箇所: acceptance.md の EX03 の行の「依存する棚卸しの ID」。
- 問題: 棚卸しの EX03 は応答・失敗を「C08〜C14・C18〜C20」と書くが、受理表は C19 を外している。C19（通信前の要求検査と停止）は、http.md が「秘密依存の検査失敗で要求や後続が消えるため、値だけの契約では足りない」と分類する行であり、機密ファイルを本文に入れる EX03 では照合が要る。

## 問題がなかった点

- 採択表8行と転記の文8件は、D4 が A・A1、D5 が B と候補 (ii)、それ以外が A という回答と一致し、選ばれなかった案は決定に混ざっていない。
- 具体的な構文・ファイル名・API・版番号・費用は、どの文書でも未決として分けてある。
- 判断14（静的な上限を許可と読まない、host/port は origin ではない、`R ⊆ 許す受け手の集合`）と判断21 に矛盾しない。案 C を実行時の権限制御として扱う整理も保たれている。
- 0.0.13・0.0.14 で実装しない内容を実装済みのように書いた箇所はなく、現行の設計書は変えていない。
- 転記の文は decisions.md の形（【決定】・内容・理由 1〜3 文・出どころ）に合い、handover.md は TODO の本文を読んでいないことを明記している。
- D9 の条件（秘密登録の削除と分類の緩和を除く、包含か更新権限が分からなければ自動で適用しない、失効した承認を使わない）は判断案と一致する。
- 受理表は、中2・中5 を除き、回答と棚卸しの行に合っている。表の行数は記載どおりで、手元の絶対パスと docs/todo へのリンクはない。
