## 所見

### 観点1: SF の定理

#### F1-1（中）段1の非干渉の言明は空虚でないが、失敗のない言語での結果であり、段4との比べ方が対称でない

- 場所: `spikes/SF/findings.md` 冒頭の二段落・§2「実行時監視と拒否」・§6、`Model.lean` の `SF.noninterference` と `Dynamic.Examples.unconditional_trace_equality_fails`。
- 確かめたこと: `noninterference` は任意の `System`・`Observer`（`visible` が底を見え、結びで論理積、`flows` で下に閉じる）に対する一般の言明で、前提は `Typed` と `LowEq` だけである。`TwoPoint.states_low_eq` が秘密だけの違う二状態を与え、`safeProgram_typed` が受理する例、`reject_explicit`・`reject_implicit` が拒否する例を与えるので、前提は充足可能で、受理する集合も空でない。`observe` は見える宛先の事象を値・順序・有無ごと残すので、観測を弱めて自明にしてはいない。この点は findings の説明と合う。
- 問題点: 段1の言語には失敗も拒否もなく（`run` は全域）、静的方式の「拒否した実行を観測に含めても一致する」という性質は、失敗が起きえないから成り立っている。段4の反例 `rejectionChangesSuffix` は、実行時の失敗が秘密の pc の下で起きると停止の有無で漏れることを示すが、同じ問題は静的方式でも、秘密の pc の下の部分的な操作（算術の失敗、範囲外、`Fail`、HTTP の失敗、出口の実行時の照合）で起きる。findings §6 の「出口で秘密の値を拒否するだけで、静的方式と同じ保証になるとは判断しない」は正しいが、冒頭の「静的方式を中心にできる」の根拠として段4の反例を読むと、静的方式が失敗の経路でも優れることまで SF が示したように読める。SF は静的方式の失敗の扱いを一つも試していない。
- また、反例の二つの出力列は `[]` と `[(console, 2)]` で、前者は後者の接頭辞である。実行時の監視に通常求める「拒否した側の出力は他方の接頭辞」という形（進行に依存しない非干渉）は、この例では成り立っている。SF が否定したのは、S5 §1.1 の強い観測（成功/失敗を観測に入れる）であり、監視の標準の保証ではない。
- 修正案: findings §2・§6 に次の二点を足す。(1) 段1〜3の言語は失敗を持たないので、静的方式の失敗・拒否の扱い（S5 §6「正常・異常の制御と `die`」の規則案）は未試作であり、段4の反例は静的方式の本番でも同じ形で現れうる。(2) 段4で否定したのは「拒否を含む出力列の一致」であり、接頭辞の形は反例と矛盾しない（証明はしていない）。可能なら段1に `fail` を一つ加え、秘密の pc の下の `fail` を拒否する規則で拒否を含む一致が成り立つことを、次の短い試作（S5 8.3 の順2）で確かめる。

#### F1-2（中）段3の「ハンドラ」は関数の呼び出しと同じ形で、効果の除去との「両立」は定理で結ばれていない

- 場所: findings §1 の表の段3、§2「一階の操作とハンドラ」、§6 第3段落の「制限したハンドラと効果除去との両立の疑問」を解消したという記述。`Model.lean` の `Handlers.runH`・`HandlerOK`・`HandleTyped`・`handled_ask_removed`。
- 確かめたこと: `runH` の `ask` は、節の `work`（`ask` を含まない `Cmd`）を走らせ、純粋な式 `reply` を捕まえた環境で評価して、必ず一度だけ続きへ渡す。継続を値として持たず、非再開・再開の前後の処理・入れ子・節の中の操作がない。この形は、捕まえた環境を持つ関数の呼び出しを本体の中で展開したものと同じであり、情報の流れの規則（`callPc`・引数の印・返り値の印）も関数の要約の規則と同じ形である。findings はこの制限を §2 で正しく書いている。
- 問題点: `handled_ask_removed` は、`HandleTyped` が付けるエフェクトから `ask` が消えるという命題で、証明は `work_no_ask`（`Cmd` に `ask` の構成子がない）だけで済む。非干渉の証明は `Effects` を一度も使わない。つまり「効果の除去と印の保持が両立する」ことは、二つの判断を独立に置いた構成から従う事実であって、両者の関係を示す定理ではない。`effect_erasure_does_not_erase_secret` も、エフェクトの行に `ask` がないのに漏れる具体例であり、情報の流れの判断を効果から独立に持つ必要を示すだけである。この試作から「本番の深いハンドラ・節を外側で走らせる規則・非再開と両立する」見込みは得られない。S5 §6「ハンドラ・ワンショットの継続」が要る規則（非再開を `handle` の出口の印へ加える、捕まえた pc）は、SF のどの定理にも対応しない。
- 修正案: findings §6 の「制限したハンドラと効果除去との両立の疑問」を「末尾で一度だけ再開する節（関数の呼び出しと同じ形）に限れば、情報の流れの判断を効果の判断と独立に置ける」へ弱める。§5 の見積もりの「使える一階のハンドラと失敗経路」の行の幅は、SF では縮まっていないと明記する。次の試作に、非再開の節（秘密の pc で再開の有無を選ぶ）と、節の中の公開の出力を含める。

#### F1-3（中）段2の宛先は構文上の定数で、実際の URL が実行時の値である本番との差が書かれていない

- 場所: findings §2「宛先集合と試作142のパターン」、`Model.lean` の `Cmd.send (dest : D)`・`Readers.system`（`sink := singleton`）。
- 問題点: SF の `send` は宛先を型付けの時点で決まる定数として持ち、`flows (pc ⊔ label e) (sink d)` を静的に判定する。本番の HTTP の宛先は、文字列の連結や設定の読み取りで作る実行時の値である。S5 §1.3 は「宛先パターンは出口の照合に使う」とし、§1.2 の表は「固定した HTTPS origin」に限るとするが、(a) 宛先を字面の定数に限る（その場合、設定から URL を読むスクリプトは書けない）か、(b) 出口で実行時に照合する（その場合は段4の反例と同じく、秘密の pc の下の照合の失敗が停止で漏れるので、照合が失敗しうる送信を秘密の pc の下で禁じる規則が要る）かのどちらかになる。SF はどちらも試していない。findings はこの差を「URL の解析…はモデルの外」とだけ書く。
- 修正案: findings §2 か §6 に、宛先が実行時の値になる本番では (a)・(b) のどちらを採るかが未決で、(b) なら段4の反例が静的方式にも当てはまることを書く。S5 §1.3 にも同じ選択を問いとして置く（観点7の F7-2）。

#### F1-4（軽）`Readers` の観測者は一つの宛先だけを見る

- 場所: `Readers.observer`・`credential_hidden_at_logs`。
- 確かめたこと: `observer o` は宛先 `o` の事象だけを見る。複数の宛先が共謀する観測者（`visible l = l a && l b`）も `Observer` の法則を満たすので、一般の定理 `noninterference` は適用できる。この点は問題ない。
- 問題点: 設計者の場面で残る漏れは、許した宛先そのものが攻撃者に読まれる場合（S5 §1.3 が書く「許したサイトに攻撃者の投稿領域がある」）である。これは非干渉の定理の外であり、SF の定理名 `permitted_send` が「安全な送信」と読まれないよう注意が要る。
- 修正案: findings §2 に「許した宛先への送信は、その宛先が秘密を再配布しないことを前提にする」と一文を足す。

### 観点2: 推す組み方 (i) の論証

#### F2-1（重大）(i) の利点に挙げた「今回の具体的な事故を先に扱える」の範囲が、攻撃者の模型に応じて分けられていない

- 場所: S5 §11 の Q1、§8.1 の (i) の行、§1.1。
- 問題点: (i) の初段は「秘密の取得口が到達可能なプログラム」で汎用の `Process.run` などを拒否する（§6「タスク・共有可変セル・Lazy」）。しかし、Benitoite の API で秘密を一度も読まず、`Process.run` で `curl` などを起動して外部コマンドにクレデンシャルのファイルを読ませるスクリプトは、この条件に当たらないので受理される。WASM も同じである。したがって (i) の初段が防ぐのは「LLM が誤って、Benitoite の API で読んだ秘密を別の宛先へ送るスクリプトを書く」場合であり、プロンプトの注入などで LLM が意図して漏らす場合は防がない。後者を防ぐには、秘密の所在を方針で知り、全プログラムの外部コマンドを拒否するか、子のプロセスの読み取りを OS のサンドボックスで止める必要があり、これはサーバモード（ADR 0177・0183）の範囲である。§1.2 の方針の改変（LLM が方針で `service-token` を公開にする）も同じで、改変を防ぐ信頼する実行側はサーバモードより前にはない（観点4の F4-1）。
- この区別は Q1 の比べ方を変える。意図した漏れを防ぐ時期は (i) でも (iv) でもサーバモードの時期で決まり、(i) が早めるのは誤りによる漏れの防止だけである。S5 は「今回の具体的な事故を先に扱える」とだけ書き、この差を示していない。
- 修正案: §1.1 に攻撃者の模型の表（誤りによる漏れ／意図した漏れ、サーバモードの前／後）を置き、各組み方で防げる升目を示す。Q1 の推す理由を「誤りによる漏れを、サーバモードより一版早く静的に拒否できる」と正確に書く。

#### F2-2（重大）案4 の範囲が静的な情報の流れの検査に要る「宛先の静的な上限」を与える点を、(i) と (iv) の比べに入れていない

- 場所: S5 §1.3、§8.1 の (iv) の行と §8.2 の「(iv) 後の情報流」の行（「範囲付き効果の利用は精密化に役立つが、二実行の証明の代わりにならない」）。
- 問題点: 静的方式の送信の条件 `label(payload) ∪ pc ∪ label(target) ⊆ Accept(d)` は、宛先 `d` を検査の時点で知る必要がある。SF も宛先を構文上の定数としている（F1-3）。設定から URL を作る普通のスクリプトでは、`d` は実行時の値になる。そのとき取れる道は、(a) 宛先を字面の定数や方針の固定 origin に限る、(b) 出口で実行時に照合し、照合が失敗しうる送信を秘密の pc の下で禁じる、(c) 宛先の値の型に静的な上限 `R` を持たせ、`Accept` が `R` の全体を覆うことを静的に求める、の三つである。(c) はまさに案4 の範囲付きの検査済みの値（S4 4.1 の D-IO の選択肢3）が与えるものであり、実行時の照合の失敗による停止の漏れ（段4の反例の形）を避けられる。S5 は案4 を「パターンを印にする」案として退けたが、パターンを宛先の引数の上限に使う組み方は検討していない。
- このため、(iv) で案4 を先に入れると、後の情報の流れの改造は (c) を使えて初段の制限（固定 origin のみ）を緩められる可能性がある。逆に (i) で先に入れると、HTTP の認証付きの API を固定 origin の専用関数として作り、案4 の後に D-IO の入口と二重になる恐れがある。S5 §8.2 の「後へ回すだけで工数を減らさない」は、この相乗りを数えていない。
- 修正案: §1.3 に (a)〜(c) を並べ、初段がどれを採るかを明記する。§8.1 の (iv) の行に「案4 の範囲を宛先の静的な上限に使えば、静的な出口の検査を固定 origin の外へ広げられる」を加え、(i) を選ぶ場合は HTTP の入口を後の D-IO と二重にしない設計の条件を書く。（要検証: (c) の規則が非干渉を保つことは、SF の段2に宛先の集合を持つ `send` を加える短い試作で確かめられる。）

#### F2-3（中）(i) を選ぶと失う案4 の成果と S4 の相乗りの扱いが書かれていない

- 場所: S5 §8.1、§10 の「S3・S4 の更新点」、§11。
- 問題点: S4 4.5 は、案4 が 0.0.13 の位置付け（サーバモードに先立ち権限制御に使う型と仕組みを決める）に最も近い理由として、ポート・パス・ホストの上限を関数の型に示すこと、関数の契約の差分として対象の広がりを利用者に示せること（原則2・3）を挙げた。これはサーバモードの承認の画面と権限の変更の表示（ADR 0177 の決定5が「サーバモードで実現する」とした原則2・3）の入力になる。S5 は (i) で案4 を後へ回す損失を「案4の型の添字は入れない」とだけ書き、(a) 承認の画面が対象の上限を示せないままサーバモードの設計に入るのか、(b) S4 4.1 の D-IO・D-拒否などの「0.0.13 で決めること」は (i) でも 0.0.13 に残すのか、(c) S4 4.2 の相乗り三つ（Scope の局所解析、`Secret` の最小の型、TODO-256 の第一項・第三項）を (i) でも入れるのか、を示していない。特に `Secret` の型（TODO-154）は (i) の前提（§5 の例は `Secret.reveal` を使う）であり、相乗りでなく重い項目の一部になるはずだが、§8.2 の見積もりの行に現れない。
- 修正案: §8.1 に、(i)・(iv) それぞれで 0.0.13 に入るもの・決めるもの・サーバモードの設計の開始時に未決のまま残るものの三列の表を置く。S4 4.1 の六つの決定と 4.2 の三つの相乗りを行に取り、(i) での扱いを一つずつ書く。`Secret` の型を (i) の見積もりの行に入れる。

#### F2-4（中）S5 が SF を読まずに書かれ、SF の後も推す理由と見積もりが更新されていない

- 場所: S5 冒頭の「並行する SF のファイルと結果は読まず」、§8.3 の順1・2、§10 の「SF との接続」。

### 観点3: 最初の段の制限の実用性

#### F3-1（重大）認証した API の応答が秘密のままなので、「トークンで API を呼び、結果を表示する」典型例が初段で書けない

- 場所: S5 §5「認証先と別の許可済みホストの区別」の第2〜3段落、§1.2 の方針の書式案、§10 の「一般の declassification を初段に入れない」。
- 問題点: S5 は「応答は認証情報に依存しうるので、許された送信の後でも公開へ自動的に落とさない」「認証への応答の成功/失敗はトークンの内容に依存しうる」とする。この規則では、認証付きの要求の応答の本文も、成功/失敗も、それで分岐した後の pc も秘密の印を持つ。設計者の場面の日常の自動化（課題の一覧を取って表示する、API の結果を報告のファイルへ書く、`try ... or return` で失敗を報告して終える）は、応答か成功/失敗を公開の出口（stdout・報告のファイル・`die`・終了の状態）へ流すので、ほぼすべて拒否される。§1.2 の方針の書式案には、応答を公開と分類する項目（方針による限定した declassification、または応答の分類）がない。S5 はこの帰結を例で示しておらず、§8.3 の順3と §10 の「互換性の受け入れ」も、ファイルの分類と Task/Process の拒否だけを挙げる。
- 修正案: (1) §5 に、応答を表示する例を加え、初段の規則で拒否されることを明記する。(2) 方針に「origin X への秘密 C の送信に対する応答は、受け手 R に公開してよい」と書く項目を置く案を、限定した declassification として検討し、非干渉の言明をその分だけ弱めた形（許す開示を除いた非干渉）で書く。(3) これを入れないなら、(i) の初段で書ける実用例が「秘密を送るが結果を見ない」ものに限られることを Q1 の判断材料に明記する。

#### F3-2（重大）一般のファイル読み取りを秘密の分類の和へ上げる近似は、秘密を一つでも方針に書くと、ファイルを読むほぼすべてのスクリプトを拒否する

- 場所: S5 §1.2 の表の「クレデンシャルのファイル」の行と最後の段落、§6「タスク・共有可変セル・Lazy」の限定案、§11 の Q5。
- 問題点: S5 は、字面のパスでは別名・リンクを除けないので、一般の読み取りを「方針が管理するファイルの秘密の分類すべてへ依存する」と近似する。この近似では、方針に秘密を一つでも書けば、CSV を読んで集計を表示する、設定のファイルを読んで処理する、といった秘密と無関係のスクリプトでも、読んだ内容が秘密の印を持ち、stdout へ出せなくなる。さらに、そのスクリプトは「秘密の取得口が到達可能なプログラム」になるので、§6 の限定案により Task・`Reference`・`Lazy`・`Process.run` も拒否される。S5 はこの近似の費用を「複数の秘密のうち一つを正しい認証先へ送る例も拒否しうる」とだけ書き、影響を大きく小さく見ている。
- 修正案: 近似の影響を §1.2 に正しく書く（方針に秘密があると、ファイルを読むスクリプトの出力はすべて拒否）。代わりの案として、(a) 秘密のファイルは専用の取得口（例: `Secret.fromFile`）だけで読み、一般の読み取りは実パスが方針の秘密の場所に当たれば実行時に拒否する（このとき一般の読み取りの結果は公開と扱える。拒否は公開のパスと外部の環境だけで決まるので、秘密の pc の下でなければ漏れない）を並べる。(a) は TODO-109 の既定の方針（スタンドアロンでも `{secrets}` の読み取りを除く）と同じ向きだが、実行時の権限制御に当たるので ADR 0177 との関係を問いにする（F4-1）。

#### F3-3（中）秘密を URL や認証ヘッダ以外の欄に含める典型例と、外部コマンドを使う典型例の退き先が示されていない

- 場所: S5 §1.2 の表の HTTP・外部コマンドの行、§1.3 の `label(target) = Public` の条件、§6「WASM と外部コマンド」。
- 問題点: 初段は「固定した HTTPS origin、認証ヘッダへの注入に限定」し、宛先の印を公開に限る。次の日常の例は初段で書けないが、S5 は退き先を示していない。
  - URL そのものが秘密である Webhook（チャットの受信 Webhook の URL）。宛先の印が秘密になるので送れない。
  - トークンを URL の経路や問い合わせの欄に入れる API、要求の本文に署名や鍵を入れる API（HMAC の署名を独自のヘッダで送る形を含む）。`channel=authorization-header` の外になる。
  - `git push`・`gh` など外部コマンドに認証を任せる例。秘密を Benitoite で読まずに `Process.run` を呼ぶなら初段の制限に当たらず、そのまま書ける（情報の流れの保証の外）。トークンを環境変数で渡すなら拒否される。どちらも初段では保護も退き先もない。
  - トークンで複数のページを並行して取る例（Task）。逐次に書き直せば通るはずだが、S5 は示していない。
  - OAuth の更新で得た新しいトークンを保存し直す例。§1.2 の「秘密用の可変な保存先は…拒否できる範囲」で拒否される。
- 修正案: §5 か §8.3 の順3に、典型例ごとに「初段で受理／拒否／保証の外」と退き先（逐次に書き直す、スクリプトを分ける、後の版を待つ）を並べた表を置く。§10 の「実際の自動化の例で設計者に示す」をこの表で前倒しする。Q1 の判断はこの表を見てからにする（F7-1）。

### 観点4: ADR 0177・0183・0147 との整合

#### F4-1（重大）サーバモードより前に「開示の許可」を方針で与える形は、ADR 0177 が避けた「許可の与え方を二度設計する」に当たりうるが、S5 は実行時か静的かの区別だけで整合を主張している

- 場所: S5 §1.2 の第2段落（「信頼する実行側が方針を渡し」）、§8.1 の最後の段落、§11 の Q2。ADR 0177 の「検討した代替案」の第1項、ADR 0183 の帰結の最後の項。
- 確かめたこと: ADR 0177 が実行時の権限制御を先に入れない理由は、「許可を与える方法は、設定をサーバ側で持つというサーバモードの設計と切り離せない。サーバモードより前に権限制御を実装すると、許可の与え方を二度設計することになる」である。ADR 0183 は方針のファイルの形をサーバモードの章で定めるとする。san_benito の処理系には方針のファイルを読む実装がない（`git grep` で `policy.toml` に当たる箇所がない）。
- 問題点: S5 の `allow-disclosure` は、秘密の分類ごとに送ってよい宛先を利用者が与える「許可」であり、ADR 0177 の懸念はそれが静的に検査されるか実行時に検査されるかに依らない。Q2 の「ADR 0177 の操作の実行時権限制御を先行させず」は、ADR 0177 の文言の一部（実行時）にだけ答え、理由の部分（許可の与え方の設計）に答えていない。さらに、§1.2 は保証の前提に「LLM が方針を変えられないこと」「信頼する実行側が方針を渡すこと」を置くが、サーバモードより前のスタンドアロンモードでは、方針のファイルは LLM と同じ OS の利用者の権限で書き換えられる。この前提を満たす仕組みは、ADR 0177 の決定3のとおりハーネスか OS に委ねるしかない。
- 修正案: Q2 を、(a) 0.0.13 では方針の入力を暫定の形とし、サーバモードで書式を作り直す（二度の設計を受け入れる）、(b) 方針の書式のうち秘密の分類と開示先の部分だけを先に ADR で決め、ADR 0183 の帰結（書式はサーバモードの章で決める）を改める、(c) 0.0.13 では秘密の分類と開示先をスクリプトの外の固定の形（例: 標準ライブラリの専用の取得口の引数と、処理系の起動の引数）だけで与え、方針の書式に触れない、の三つの選択として問い直す。どれでも、方針の完全性をハーネスか OS に頼ることを 00-01「保証の範囲」の改訂案に書く。

#### F4-2（中）既存の方針の決定（TODO-109 の `[secrets]`・`{secrets}`・既定の除外）との関係が書かれていない

- 場所: S5 §1.2 の書式案（「既存 TOML の構文ではない」）。docs/todo の TODO-109、TODO-154。
- 問題点: TODO-109 は、方針の TOML に `[secrets]`（`paths`）とパスの記号 `{secrets}` を置き、スタンドアロンの既定の方針で `{secrets}` の読み書きを除くと記録している（ADR 0200・0216 などを出どころとする）。TODO-154 は、スタンドアロンの既定で `Secret.Read` を許し `Secret.Reveal` を許さない案を持つ。S5 の `secret <名前>: sources:` はこれらと重なるが、S5 はどちらにも触れない。`secret.sources.file` と `[secrets].paths` を同じものにするか、`{secrets}` の既定の除外を専用の取得口だけ外すか、`Secret.Reveal` のエフェクトの役割（権限の確認に現れる）を情報の流れの下で残すかで、書式と承認の画面が変わる。
- 修正案: §1.2 に TODO-109・TODO-154 の既存の案との対応表を置き、残す・置き換える・未決を分ける。F3-2 の (a) を採るなら、`{secrets}` の既定の除外がそのまま一般の読み取りの拒否になることを書く。

#### F4-3（軽）ADR 0147 とは整合するが、検査の結果が利用者の方針に依存することの帰結が書かれていない

- 場所: S5 §1.2 の第2段落、§6「ハンドラ・ワンショットの継続」の最後の段落。
- 確かめたこと: スクリプトに許可も印も書かせず、方針の側で秘密と開示先を決める形は、ADR 0147（スクリプトは権限を宣言しない）と ADR 0117 と整合する。この点は S5 の主張どおりである。
- 問題点: 同じスクリプトの `check` の結果が、利用者ごとの方針で変わる。LLM は拒否の理由を知るために方針の内容（秘密の名前と開示先）を診断で見る必要があり、ハーネスの下で書いたスクリプトを別の機械で使うと拒否されうる。また ADR 0183 の一つの方針から導くという決定に従うなら、`allow-disclosure` の宛先は通信の許可（`Http.Connect` の対象）に含まれる必要があるが、その制約が書かれていない。
- 修正案: §1.2 に「開示先は通信の許可の部分集合でなければ方針の誤りとする」と、「検査の結果は方針の版に依存し、診断は方針のどの項目で拒否したかを示す」を加える。

### 観点6: 設計原則

#### F6-1（中）診断が、コードで直せる拒否と、方針の変更が要る拒否を区別することを求めていない

- 場所: S5 §9 の表の「5. 原則・診断」の列（「由来と出口の位置を示す」）、§10 の未確認の事実。S5 の第2節の観点5は読んでいない。
- 問題点: 情報の流れの拒否には、(a) 出力を秘密の分岐の外へ出す・逐次に書き直すなどコードで直せるもの、(b) 開示先や応答の分類を方針に足さないと通らないもの、(c) 初段では書けない機能（Task・`Process.run` 等）によるもの、がある。LLM が (b)・(c) をコードで通そうとすると、秘密をファイルへ書いて読み直す、外部コマンドに読ませるといった迂回を試み、拒否が繰り返されるか、保証の外（F2-1・F3-3 の `Process.run`）へ逃げる。原則1・4 に照らすと、診断は由来・経路・出口に加え、この三分類と「方針の変更は利用者に依頼する」ことを機械向けの出力で示す必要がある。
- 修正案: §2 か §9 に、診断の欄として「拒否の種類（コード／方針／未対応の機能）」を加え、各種類で LLM に勧める行動を書く。§8.3 の順5の受け入れ条件に、迂回を試みる修正を拒否し続けることの確認を入れる。

#### F6-2（中）プログラマでない利用者が、暗黙の流れによる拒否と方針の書き方を理解できるかが検討されていない

- 場所: S5 §1.2 の書式案、§5 の例。
- 問題点: 「`service-token` は `api.service.example` の認証ヘッダにだけ送れる」は利用者に説明できる。しかし「アップロードの成否がトークンで決まるので『完了しました』を表示できない」（F3-1）のような暗黙の流れの拒否は、原則3 の利用者に説明しにくい。また §1.2 は方針の管理者が `sources`（キーストアの項目、環境変数の名前、ファイル）と開示先を書くとするが、プログラマでない利用者が書くことを前提にした書き方か、承認の画面で提示されたものを承認する形かが決まっていない。後者はサーバモードの承認の画面に依存する。
- 修正案: §5 に、拒否の理由を利用者向けに説明する文の例を加える。方針の秘密の項目を誰がどう作るか（利用者が書く／専用の取得口の初回の使用で提案し利用者が承認する）を問いに加える（F7-1）。

## Q1 について推す案

(iv) を推す。ただし、情報の流れの「決めること」は 0.0.13 に残す変形とする。0.0.13 の重い項目は案4（S4 4.5 の進め方）とする。情報の流れは 0.0.13 で次の三つまで行う。(1) F7-1 の Q7〜Q13 の答え（守る相手、応答の分類、宛先の決め方、ファイルの分類、方針の書式、`Secret` との統合、承認の画面）、(2) 入口と出口の棚卸しと典型例の受理表、(3) `fail`・非再開・宛先の集合を加えた短い Lean の試作（F5-3）。実装は 0.0.14 で、サーバモードより前に、方針の書式（TODO-109）の設計と並べて行う。

理由は四つある。第一に、(i) が早めるのは、誤りによる漏れの静的な拒否だけである。意図した漏れを防ぐ時期は、方針の完全性と外部コマンドの制限が要るので、どちらの組み方でもサーバモードで決まる（F2-1）。第二に、初段の制限の下では、設計者の場面の典型例の多くが書けない見込みである（応答の表示、ファイルを読むスクリプト、Webhook、外部コマンド。F3-1〜F3-3）。それを解く方針の項目（応答の分類、秘密の場所）は方針の書式と承認の画面に属し、ADR 0177・0183 の理由から、サーバモードの設計に近い版で一度に決める方が二度の設計を避けられる（F4-1・F4-2）。第三に、案4 の範囲は、静的な出口の検査に要る宛先の上限を与えて、後の情報の流れの初段を固定 origin の外へ広げる（F2-2）。あわせて、承認の画面と権限の差分という 0.0.13 の位置付けに直接つながる（F2-3）。第四に、案4 は SA で等号と包含の代数が閉じており、(i) は必須の作業（`Secret` の型、方針の入力、応答の分類）が見積もりから抜けている（F5-2）。

この案は前倒しの決定を取り消さない。情報の流れはサーバモードより前に入り、S5 §8.1 が懸念した「サーバモードの設計の開始前に入口・出口と方針の分類を固定する」ことも 0.0.13 の決定で満たす。(i) を選んでよいのは、次の二つがともに成り立つ場合である。一つは、典型例の受理表で Q8 の応答の分類を入れれば日常の自動化が通ると確かめられること。もう一つは、設計者が案4 の表示より、誤りによる漏れの早い拒否を重く見ること。その場合も、Q11 の方針の書式を先に ADR で決めてから実装に入ることを条件とする。
