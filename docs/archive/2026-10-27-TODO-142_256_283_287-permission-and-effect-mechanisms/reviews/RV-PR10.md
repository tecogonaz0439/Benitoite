# RV-PR10: R10〜R40・UB20・K10 の作業単位の下書きの独立レビュー

2026-10-28。対象は PR10 の下書き `plan-r10-r40.md`（基準 `23738a46`。確認点 (1)〜(17) の了承に合わせて取りまとめが確認点の節を直した後の版）。独立レビューの担当が読み取りだけで行った（ビルドとテストは走らせていない。所要約10分）。結論: 重大2件・中4件・軽9件。対応は末尾の「対応」の節に記す。

## 指摘

### 重大1: K10.1 を R40.3 の後に置くと、遅くとも R30.2 で通常の `desugar_export` が通らない（観点1）

- 箇所: 前提の第4段落、K10.1、表「K10 までの全比較の不一致」、取りまとめへ返す点4。
- 問題: 下書きは「Top だけの旧入力を保てる箇所に限って旧版を保つ」としているが、旧版を保てなくなる時点を特定していない。通常テストの `export`（`tests/desugar_export.rs` 244行以降）は、どの入力についても `exchange::named_builtin_tables` を呼ぶ。`tests/desugar_export/builtins.rs` の繰り返しは `entry != EffectOp && !used` のときだけ項目を飛ばすので、効果の操作は使われていなくても常に書き出される。署名は `complete_stdlib()` から取り、効果は `surface.eff` で書く。そのため `File.readTextIn` などを登録する R30.2（`Http.sendIn` は R30.4）の時点で、`uses File.Read[R]` の範囲の変数を v14/v6 で表せなくなる。表せるのは Lean の旧版の読者が Top として読む形だけである（`formal/Benitoite/Exchange/Version.lean` 235〜255行）。新しい操作だけを除外する案も、Lean 側で名前の全操作の一覧（全操作の節がそろったかの判定）が変わり Rust と食い違うので採れない。
- 修正案: K10.1 のうち型表の署名の `rvar`・`rkinds`・`shape`、効果の原子の `{"value","ix"}`、表データの書き出しを、R30.2 より前（新しい枝か R30.2 の中）に置く。`scopeAcceptance`、`limits`、区間の Surface 15、全書き出し元の版の照合は K10.1 に残す。前倒しを plan「計画の変更」に記録し、R30・K10 の幅を取り直す。

### 重大2: R20 には、実ソースで判定する対象がない（観点1・5）

- 箇所: 前提の第3段落、R20.2〜R20.5 の完了の条件、取りまとめへ返す点3。
- 問題: Lean の局所解析の規則は新しい六つの宣言（`checkPathIn`・`checkRequestIn`・`pathInValue`・`requestInValue`・`widenPathIn`・`widenRequestIn`）にしかない（`formal/Benitoite/Surface/ScopeState.lean` 600〜626行の `ruleDeclarations` と `Rules.lookup`）。既存の `Scope.checkPath`・`checkHost` は規則の対象でなく、局所解析を当てると Lean と食い違う。一方で下書きは新 API の登録を R30.1/.3 まで行わず仮登録も禁じるので、R20.2・R20.3 の受理の入口・R20.5 の予算の実測は通常の入口で確かめられない。R20.4 の完了の条件の「L50.4 中3 の差」の例は、R30.2 で登録する `File.writeTextIn` の節を要する。
- 修正案: 純粋な四入口（検査と射影）の宣言と実行本体を R20.1 の前（新しい枝 R20.0 か R10.6 の後の一枝）に置き、この時点の静的な範囲は常に Top とする（「未知なら Top」は仕様どおりの値で、実行時の検査も省かないので仮の成功値に当たらない）。R20.3 で規則による範囲の選択と `widen*` の戻り注釈の被覆の確認を接続する。R20.4 の中3 の例は完了の条件から R30.2 へ移し、R20.4 では節の添字の選び方を lib の単体テストで確かめる。第3段落を Lean の規則表に合わせて直す。

### 中1: 一枝の上端6時間は R/K について未承認（観点4）

- 箇所: 冒頭の表「一枝の上端」。
- 問題: plan「作業の数と時間」は後続の枝の上端を3時間以下とし、6時間は L10〜L50 だけの設計者の決定である。
- 修正案: 6時間の上端を R/K にも適用するかを設計者に確かめる。3時間なら枝の数は約2倍になる。

### 中2: 段末の stage が、同じ HEAD の W-R と重なる（観点4）

- 箇所: R10.6・R20.6・R30.5 の検査欄、表の S-10/20 と S-30/40。
- 問題: 段末の枝の全統合の W-R の直後に走らせる S-* の `tests_related` は、同じ HEAD の部分集合になる。AGENTS.md「テストの運用」は重なる単位を後の側の `--only` から外すよう求める。R40.3 では W-40 と S-30/40 が `cli_process`・`test_command`・`golden` で重なる。
- 修正案: stage は HEAD が変わる取り込みの後に置くか、07-03 の引用の条件で W-R を引用する。R40.3 の S-30/40 から重なる3ターゲットを外す。

### 中3: 局所比較と予算の測定のコマンドがない（観点4・5）

- 箇所: K10.1・K10.2 の局所照合と小入力の比較、表の F 行、R20.5 の予算の測定。
- 問題: 検査表にコマンドがなく、要る Lean の交換実行ファイルのビルドも担当と `-M` の扱いも割り当てていない。plan は「表のコマンドにまだ値を与えられない枝は起動しない」としている。
- 修正案: `cargo test --test desugar_export <smoke名>` の出力を Lean の入口（`check-formal.sh` の該当行と同じ指定）へ渡す手順、Lean のビルドは排他の道具と `-M 12288` で行うこと、R20.5 の測定の入口（lib の単体テストか example か）と記録する欄を表に加える。

### 中4: R10.2 の一度の切り替えは、二つに分けられる（観点1）

- 箇所: R10.2、停止条件の R10.2 の行。
- 問題: 効果の原子（`EffectName`。src の17ファイルに56か所）と型の添字（`Ty::Con`。src の51ファイルに288か所）は別の型で、それぞれ単独でコンパイルを閉じられる。下書きの数は src だけで、`tests/` にも `Ty::Con` が8ファイルに33か所、`EffectName::` が3ファイルにある。確定した呼び出しの範囲の列を IR に運ぶ部分は、それを作る R20.3 まで要らない。
- 修正案: R10.2a（効果の原子と効果集合）と R10.2b（型の添字と不透明標準型）に分ける。IR の範囲の列は R10.5 か R20.3 へ移すことを検討する。読者の数に tests/ を足す。L 段の「一度の切り替えの試行ビルド」と同じ形の行を R10.2 にも置く。

- 検査で使う統合ターゲット（21個）、`--only` の単位名、`test_range_exchange.py`、`formal_interval.py`、short の入口が実在する。
