# IFC-D3: 認証付き API の値・成否・用途を限る契約の案

2026-10-27、IF10.02。設計者が選ぶための判断案であり、採択済みの決定でも、実装・証明の完了報告でもない。

## 決めることと既に決まっている境界

IFC-D3 で決めるのは、認証付き API について、公開する値・成否・用途・呼出条件を固定した操作の契約で限定し、外部 API が許した結果以外に秘密を反映しないことを承認する信頼条件として残し、機密性を緩める非機密化（declassification）と完全性に信頼を付与するエンドースメント（endorsement）を分けて応答の完全性を未信頼に保つか、応答を常に秘密に保つか、origin ごとに応答を一括で公開可能にするかである。

[README の版の割り振りと方式](../README.md#設計者の決定2026-10-27版の割り振りと情報フロー制御の方式)、P1〜P6、[判断19](../decisions.md#判断-19-情報フロー制御の方式と今回の成果物)を前提にする。0.0.13 は判断案と契約の設計まで、0.0.14 は情報フロー制御（information-flow control）の独立した実装、その後は必要な接続とサーバモードである。内部の判定と Lean の証明に汎用の束を使い、最初は管理者が定める有限の束、機密性と完全性、用途を限った非機密化とエンドースメント、一階の印の要約を扱うという選択は戻さない。

[IFC-D2 の案A](../if10.01/ifc-d2.md)を仮の前提とする。IFC-D2 はまだ設計者が選んでいない。0.0.14 では、起動側が方針と信頼する契約を保護し、検査したプログラム・依存・方針・契約の組を実行することを前提に、対応済みの逐次計算を静的に検査する。後のサーバモードで強制と接続した範囲に保証を加える、という案である。別案が選ばれたときの差は後掲の表に分ける。

[00-01「保証の範囲」](../../../design/00-overview/00-01-goals.md#保証の範囲)と[07-01「脅威モデル」](../../../design/07-quality/07-01-security-model.md#脅威モデル)に従い、利用者は作業と許す操作を決め、LLM・スクリプト・外部入力を信頼しない。セキュリティ型システム（security type system）が検査するのは規則への適合であり、作業の意図、外部 API の正しさや成功、停止を保証しない。サーバ前の隔離をハーネスや OS に委ねる境界も保つ。

## 推す案と二つの代案

案Aは「固定した操作の契約で限定」、案Bは「応答を常に秘密に保持」、案Cは「origin ごとに応答を一括で公開可能」とする。[元の問いD3](../study/questions.md#0013-の中で決めること設計の判断として文書にするもの)の三案を具体化した。案Bの「常に」は認証要求に由来する依存をこの種の契約で緩めないという意味であり、別の秘密の分類を捨てたり、完全性の追跡を省いたりする案ではない。

| 比較する点 | 案A: 固定した操作の契約で限定（推す） | 案B: 応答を常に秘密に保持 | 案C: origin ごとに一括で公開可能 |
|---|---|---|---|
| 公開する単位 | 解決済みの標準操作と契約の版を同定し、要求各欄、公開する結果の欄・成否の分類、受け手と用途、呼出条件を固定する。契約にない応答と依存は秘密のまま | 認証した要求の結果・成否・正常復帰の依存を保つ。件数だけの抽出も通常の派生値として扱い、公開の報告を拒否する | 指定した origin からの応答の本文・ヘッダ・成否を広く公開可能にする。呼出側の別の秘密や未承認の要求の依存は保持するが、応答の欄や操作別の公開範囲は絞らない |
| 0.0.14 で保証すること | 方針と信頼条件の下で、許した要求由来の値・成否・呼出条件だけを緩め、残る秘密の流れと未承認の影響を拒否する。未対応経路は保証を付ける対象で拒否する | 応答の緩和を導入しない範囲で、認証と他の秘密への依存を保持して禁止出口を拒否する。秘密の受け手への適法な送信まで禁止する意味ではない | 承認した広い公開範囲を例外にした、残りのフローの規則への適合。API が秘密を反映しても、広い例外に含めれば検査では止めない |
| 保証しないこと | APIによる秘密の非反映、報告の正しさ、外部操作の成功、停止、時間・資源使用量による漏れ、受け手の再配布を保証しない。D2案Aの方針保護と隔離の限界も残る | 案Aの共通の限界が残る。応答の公開を拒否しても、検査外の読み取りや方針改変を止めたことにはならない | 案Aの共通の限界に加え、origin内の広い承認範囲の情報を秘密に保つ保証を与えない |
| 外部 API についての信頼条件 | 公開すると定めた要約・成否を越えて、認証情報や非公開データを結果へ反映しないこと。固定変換の実装が余分な本文や依存を混ぜないことも必要。受け入れなければ案Bの扱いへ戻す | 応答を公開するための「秘密を反映しない」という信頼は不要。要求の送信先・分類・実装が契約を守る前提は依然必要 | 同じ origin の全対象操作・応答欄・失敗について、反映を許すか、反映しないことを広く信頼する必要がある。origin の一致だけからその性質を導けない |
| 非機密化とエンドースメント | 結果の機密性だけを契約内で緩める。応答は未信頼のまま。信頼を要する用途には別の用途別エンドースメント契約が必要 | 機密性を保持する。完全性も未信頼のまま。形式の確認やエンドースメントから公開可能性を導かない | 広い非機密化であり、エンドースメントにはしない。完全性は未信頼のまま。全応答を信頼済みへ変える追加案はこの比較に含めない |
| 利用者への説明案 | 「この認証情報で、この操作を行い、件数と定めた成否だけを報告する。API がそれ以外の秘密を反映しないことを信頼する。報告内容の正しさは保証しない」 | 「認証付き API の結果と成否は秘密として扱う。公開の件数報告もできない。送信を許したことから公開は許されない」 | 「この origin の応答は広く公開可能になる。本文に認証情報などが含まれれば、それも公開されうる。応答を命令として信頼する許可は含まない」 |
| 後の版への影響 | 契約の追加・版の変更を同じ方針の承認に結ぶ。サーバで保存・実行・拒否を接続しても外部 API の信頼条件は残す。Task 等へは個別の接続が必要 | 件数と成否の表示を後に必要とすれば、この判断と受理表を改め、限定契約を追加する。サーバ化だけでは秘密の応答が公開にはならない | 限定契約へ移る際に、従来の公開出力を拒否しうる。API の変更が origin 内の広い承認へ影響する。判断19の用途を限る境界との整合を取り直す必要がある |
| IFC-D2 への依存 | D2案Aの前提付き静的保証として設計する。D2案Bでも契約の静的義務は同じ。D2案Cなら契約保護と実アクセスへの強制を前倒しする | 保証を付ける実行範囲と方針保護はD2に従う。応答の緩和を省いても迂回防止は得られない | D2のどの案でも、広い承認は検査の例外として残る。強制を早めても、承認済みの過剰な公開を止める保証は加わらない |
| IFC-D4〜D6 への依存 | D4の入力分類、D5のR全体への被覆・pc・失敗の観測、D6の取得・取り出し・非機密化の分離を要する | D4・D5・D6は同様に必要。応答の公開契約だけを設けない。認証情報の送信や秘密のファイルの分類は省けない | D4・D5・D6は同様に必要。origin を送信範囲や入力分類の代用にせず、応答の一括緩和を取り出しの一般規則にしない |
| IFC-D7〜D9 への依存 | D7で秘密・受け手・公開値・成否・用途・信頼条件を示す。D8で典型例の必須化、D9で契約の所有者・同一性・変更承認を決める | D7で表示できない結果を説明し、D8で認証付き件数報告を必須にしない整合が必要。D9の分類と送信契約は残す | D7で応答全体の公開を説明し、D8で受理表を見直す。D9で広い承認とAPI変更の扱いが必要。狭い契約の承認と同じ表示にしない |
| 費用の見込みと根拠 | 案G全体の既存見込みはLean 154〜374時間・処理系等182〜420時間。関連する固定APIの非機密化はLean 12〜30時間・処理系等10〜24時間、用途別エンドースメントと相互作用も同じ幅の行がある。いずれも全体に含まれる。D3単独の切り分けとAPIごとの信頼確認時間は不明 | 限定応答の変換・関係条件・成否の緩和は省けるが、保持する分類・pc・完全性・拒否の実装は残る。削減幅と合計は不明。案Gから関連行を単純に引く根拠はない | 欄を選ぶ実装は減りうる一方、広い信頼範囲と承認・変更・移行の費用が増えうる。増減・合計とも不明。origin の許可リストだけで実装が終わるとは見積もらない |

費用の出どころは [synthesis「大きさの見込み」](../study/synthesis.md#大きさの見込み)と [S6「規模の見積もり」](../study/information-flow-generality.md#規模の見積もり)である。未実装で確度の低い能動時間の見込みであり、実測ではない。関連行は機密性だけの比較案から案Gへ積み上げた内訳であって、今回の判断案の作成時間でもD3だけの確定予算でもない。サーバ・OSの強制、一般のTask/Process/WASM接続、検査・測定の実時間と設計者・独立レビューの待ちは含まない。

## 案Aの契約が定める範囲

以下は [S6 の応答の分類と契約](../study/information-flow-generality.md#api-応答の分類と許す開示f3-1)と [synthesis の契約の行](../study/synthesis.md#0013-で決めて文書にする情報フロー制御の設計の判断)を具体化した案である。契約書式・構文・公開API名を決めるものではない。例の origin・パスは架空であり、実在サービスの振る舞いは未確認である。

| 契約の項目 | 案Aで定める内容 |
|---|---|
| 操作の同一性 | 信頼する標準操作と結果変換の解決済みの識別、契約の版。同名の利用者関数・模擬ハンドラに権限を移さない |
| 許す要求 | origin、メソッド、パス、許す引数、認証情報を入れる欄、本文の有無と分類、リダイレクトと再試行の扱い。初期の例はリダイレクトと自動再試行をしない |
| 公開する値と受け手 | 応答から固定変換で得る欄と範囲、公開の報告先。本文全体・エラー本文・ヘッダの暗黙の公開を含めない |
| 公開する成否 | 正常復帰、成功か失敗か、許す失敗の分類、報告と終了状態への対応。通信・復号・構文解析・変換の失敗を残さず分類する。契約で分類できない経路は公開に近似せず、秘密の結果として保持するか未対応として拒否する |
| 用途と呼出条件 | 報告に用いる操作・出口と、誰が要求・引数・呼出しの有無・回数を選べるか。最初の例では信頼する公開の設定から固定し、別の秘密や未信頼入力で任意に変更できる呼び出しを受理しない |
| 保持する依存 | 契約が緩める要求の依存だけを特定する。他の捕捉値・呼出側pc・要求本文・後処理で混ぜた秘密、及び応答の未信頼の完全性を保持する |
| 信頼条件と承認 | 公開する結果を越えた秘密の反映がないという外部APIの条件、固定変換の正しさ、承認者と根拠、契約の変更時の再確認。保存形式と承認の実装はD7・D9へ残す |

用途の限定は、許す操作と引数・結果変換・出口を処理系が照合できる条件にする。「報告用」と注記しただけでは用途を制限したことにならない。公開してよい件数を人間が読んだ後の再配布や、作業の真の意図まで保証する案でもない。公開の数値として使えても、未信頼の結果からシェル本文・送信先・信頼する操作を決める権限は得られない。別の用途を許すには、その用途の固定した条件を満たすエンドースメントの契約が要る。

機密性を緩める範囲は、印からある秘密の分類を一括で消す操作にはしない。同じ分類の認証情報が、承認した認証ヘッダと未承認の本文の両方に現れた場合、ヘッダに関する承認で本文の依存まで消すと範囲を越える。由来を区別できない解析は、残る依存を保守的に保持して公開を拒否する。由来の表現と健全性の証明は0.0.14で設計する。

また、許可した件数や認証の成否そのものは、利用アカウントや認証情報に依存しうる。契約はその限定した情報を公開する承認を含む。「APIが秘密を反映しない」という信頼条件は、承認した件数・成否以外へ秘密を符号化して漏らさない、という範囲で読む。件数を整数へ変換するだけでは、APIによる秘密の符号化を排除した証明にならない。完全性を未信頼に保つことも、この機密性の信頼条件の代わりにはならない。

## 契約の具体例

### 認証付き取得の件数と成否

典型8例の二番目を、逐次の一回の取得として具体化する。取得する課題には非公開の本文があり、利用者が許す公開情報は件数と粗い成否だけである。

| 項目 | 契約の内容案 |
|---|---|
| 入力と要求 | 登録したサービス用トークンを認証ヘッダだけに使う。`https://api.service.example:443` に、固定した `GET /issues` と公開かつ信頼する検索条件を送る。本文なし、リダイレクトなし、自動再試行なし |
| 公開する値 | 固定変換が得た当該応答の課題件数一つ。全件取得していない結果を全課題の総数と説明しない。公開の報告先に「取得件数」のデータとして出す |
| 公開する成否 | 正常に結果へ戻った事実と「成功／認証失敗／通信失敗／応答の変換失敗」という固定した分類。詳細なHTTP状態・復号・解析等の失敗はこの分類に集約し、生の例外文や応答本文は出さない。この分類自体を公開する承認を求める |
| 秘密に保つ値 | トークン、応答本文、課題の本文・名称・識別子、ヘッダと生の失敗情報。件数と成否の契約から、これらの表示・JSON・ログを許さない |
| 完全性と用途 | 件数と成否は公開してよい未信頼データである。表示できても真の件数や成功を保証しない。応答内の命令、報告先のパス、次の送信先を信頼する判断に用いない |
| 呼出条件 | 公開かつ信頼する設定の下で一回呼ぶ。別の秘密で呼ぶか否かを分岐しない。未信頼の検索語や応答で公開範囲・操作・回数を任意に選ぶ形は、この契約では通さない |
| 外部APIへの信頼 | 件数と定めた成否を越えて、トークンや非公開本文を公開値へ反映しないことを承認する。サービスの実挙動と変換実装は本作業では未確認。承認できなければ件数と成否も秘密のままにする |

成否の分類も固定変換の一部である。本例では、所定の成功応答と件数の変換に成功した場合を「成功」、契約で指定した認証拒否の応答を「認証失敗」、通信・復号までの失敗を「通信失敗」、その他のHTTP応答や本文・件数の形式不一致を「応答の変換失敗」にまとめる案とする。具体の状態コードやデータ形式は契約の設計時に固定し、任意のエラー本文を分類名として使わない。

失敗を値として捕捉し、承認した成否から固定の報告を選ぶ場合も、その成否が非機密化の対象であることを契約へ含める。プロセスの正常終了と失敗終了を使い分けるなら、その対応も承認範囲として明記する。本例の既定案は、結果を報告して同じ正常終了へ戻り、成否に応じた終了状態の変更を暗黙に加えないことである。`die` で生の本文や秘密依存の診断を出す経路は別の公開出口として拒否する。

### 機密ファイルの固定 API 送信

典型8例の三番目では、ファイルを許した受け手へ送れることと、その成否を公開できることを別に定める。次の二段をまとめて一つの「送信許可」にしない。

| 項目 | 契約の内容案 |
|---|---|
| 入力と要求 | D4で認定する入力契約から「機密報告」のファイルを得る。サービス用トークンは認証ヘッダだけ、機密報告は本文だけに入れる。固定した `POST /reports` を `https://api.service.example:443` へ送る。公開かつ信頼する設定で一回呼び、リダイレクトと自動再試行をしない |
| 送信してよい情報 | 当該APIを、トークンの認証ヘッダと機密報告の本文の許した受け手に登録する。宛先・URLの各欄・ヘッダ・本文・呼出側pcを検査し、D5の案を採るなら、合わせた印の許す受け手がR全体を覆うことを求める |
| 送信後の分類 | 元のファイルとトークンの印を保持する。応答・成否は両者への依存を保守的に保持する。受け手に送れたことから、ローカルの公開ログや成否表示への非機密化は導かない |
| 追加して公開する場合 | 別の固定した応答契約を承認した場合だけ、「受付応答あり／送信失敗／応答の変換失敗」の固定分類を報告する。受付応答は、外部での処理完了や永続保存の保証と説明しない。通信断で実際に受け付けられたか不明でも、その不明性を成功へ置き換えない |
| 追加契約が残す秘密 | 応答本文・ヘッダ・受領識別子、機密報告の内容・長さ・存在や送信条件のうち承認していない情報、認証情報。他の捕捉・条件・要求欄の依存も保持する |
| 追加契約の信頼条件 | 外部APIと固定変換が、承認した粗い受付・失敗の情報を越えて、ファイルの内容やトークンを公開結果へ反映しないこと。本文に応じた受付可否をどこまで公開するかも承認する。取得用の契約をこの送信用の応答に流用しない |

応答を秘密に保つ場合も、正常に戻ったか失敗したかで公開の後続を変える経路には検査が要る。秘密の成否を捨てて一定の報告を出すだけで受理できるかは、失敗の捕捉と継続の規則に依存する。SDは実IOの成否を含まないため、この形を本番で受理済みとは扱わない。

[判断14](../decisions.md#判断-14-保証と後の宛先の契約)のとおり、host/port の範囲だけでは上記のHTTPS originへの限定を満たさない。要求契約でschemeを精密に扱うか、http/https双方を覆う保守的な条件が要る。最初に検査した同じ宛先を用い、要求作成後のURL差し替えや別originへの追従をこの契約の例外として通さない。

### 許した要求以外の依存が残る例

次表は案Aで求める可否の設計条件であり、本番を動かした再現結果ではない。

| 変更した例 | 保持する依存と帰結 |
|---|---|
| 固定取得の件数だけを契約の報告先へ表示する | 認証要求に由来する許した依存だけを緩める。ほかの条件を満たせば受理候補 |
| 別の機密設定が真のときだけ取得・表示する | 呼出側pcの機密設定の依存が残る。件数が一定でも要求や表示の有無で分かるため、公開の報告は拒否する |
| 件数の変換が捕捉した別の秘密を足して返す | 固定変換の同一性に合わず、捕捉した秘密も残る。標準操作と同じ名前を付けても公開できない |
| 認証トークンを要求本文や検索条件にも混ぜる | 許した認証ヘッダ以外の由来を保持する。同じトークンの分類でも一括で消さず、固定取得の契約違反として拒否する |
| 機密ファイルの送信応答から本文や受領識別子も表示する | 粗い受付・失敗の追加契約では許していない。元のファイルと認証への依存を保ち、公開を拒否する |
| 公開してよい応答をシェル本文や次の送信先にする | 応答の未信頼の完全性が残る。用途を限る別のエンドースメントなしには信頼する操作へ使えない。汎用Process自体もD2案Aでは保証を付ける対象の未対応経路である |

## 観測と保証の言明へ渡す条件

案Aでは、同じコード・方針・契約の版、対応する公開入力と外部応答を前提に、許さない秘密だけが異なり、許した非機密化の値・成否・呼出条件が対応する二実行がともに終了したとき、残りの公開観測が一致するという非干渉性を目指す。観測には値、宛先、要求・報告の有無と順序、公開の失敗と終了状態を含める。許した値を同じと仮定しただけでは、APIが秘密をその値へ符号化していないことの証明にはならず、上記の信頼条件が別に残る。

完全性では、同じ方針・コード・信頼する入力、対応する外部応答の下で、未信頼の入力だけが異なり、許したエンドースメントの事実・成否・呼出条件が対応する二実行がともに終了したとき、信頼する操作と結果の観測が一致することを目指す。公開の件数報告そのものを、信頼する正しい結果としてこの結論へ含めない。未信頼入力に許す選択を広げるなら、値だけでなく緩和の発生と引数・用途を選べる範囲も再検討する。

[SD §2〜§4](../spikes/SD/findings.md#2-送信と観測の規則)は、`pc ⊔ label(d) ⊔ label(v)` の許す受け手がR全体を覆う条件と、公開pcでのfail・非再開・失敗しうる宛先検査を小モデルで確かめた。実IOの成否、一般のハンドラ、Task、解放、非機密化・エンドースメントとの合成は未接続である。D3の成否契約を加えただけで、秘密のpcを周囲ごと公開に戻したり、SDの条件を満たしたと扱ったりしない。

[SH2の観察の制約](../spikes/SH2/findings.md#評価の一致と観察の制約)は型・効果と値・Emit列の一致の独立モデルであり、情報フロー制御や非干渉性の証明ではない。S3の[情報フロー制御とLIO](../study/usage-and-flow.md#5-情報フロー制御と-lio)の接続の論点とS5の[ハンドラ・継続の規則案](../study/information-flow.md#ハンドラワンショットの継続)も踏まえ、効果の除去や模擬への差し替えだけで、捕捉・条件・本文の秘密が消える契約にはしない。SD・SH2は再試作していない。

## 外部の方式から確認できる範囲

2026-10-27に、次の一次資料の本文を確認した。外部の方式についての事実と、Benitoiteへ採る設計案を分ける。

| 一次資料 | 確認した事実 | この判断案での使い道と限界 |
|---|---|---|
| [Jif 3.3.0公式文書「Label checking」](https://www.cs.cornell.edu/jif/doc/jif-3.3.0/label_checking.html)の「Program counter labels」「Normal and exceptional termination」 | 到達を表すpcと、正常終了・例外の有無から分かる情報を追う | 値の非機密化だけでは成否や制御の条件が済まない先行例である。Benitoiteの失敗・継続への接続済みを意味しない |
| 同文書の「Downgrading」「Declassification expressions」「Endorsement」 | 機密性と完全性を緩める次元を分け、権威の条件を置く。robustnessは緩和の決定と対象への未信頼入力の影響を制限する条件である。式の非機密化は例外・正常終了の印をそのまま保つ | 完全性を保持し、呼出条件も契約で扱う参考になる。Jifの条件と案Aの限定契約が同等であるという証明はなく、Jifと同じrobustnessを保証したとはしない |

Jifの構文や公開APIを採る提案ではない。今回確認したのは版を固定した文書の記述であり、現在の他システムの対応状況、各外部APIが秘密を反映しない性質、LLMの生成・修正成功率は未確認である。費用の実測資料としても使わない。

| IFC-D4／IF10.03・IF20 | 認証情報と機密ファイルの分類を入力契約で得る。一般読み取りが複数の秘密の結びなら、認証だけの限定契約で他の分類を消さない。精度が足りなければ拒否する。字面のパスだけで精密化しない |
| IFC-D5／IF10.04・IF20 | 送信を許す契約と応答の非機密化を分ける。R全体への被覆に宛先・本文・pcを含め、schemeの不足を残す。粗い成否の契約と公開pc、検査失敗、非再開、後続観測の合成は未証明として設計する |

## 設計者への一つの問い

共通の前提は、送信と応答公開を別の契約にし、未承認の捕捉・条件・本文の秘密と、応答の未信頼の完全性を保つことである。公開を認める案では、その範囲を越えて外部APIが秘密を反映しないという信頼条件を人間の承認へ提示する。

IFC-D3は、認証付きAPIの応答を公開する単位として、固定操作の限定契約（案A）、公開しない扱い（案B）、origin単位の一括公開（案C）のどれを選ぶか。

推すのは案Aである。理由: 件数と成否の報告に必要な公開を認めつつ、案Cが認める応答本文等の公開を契約から除ける。固定変換・成否・呼出条件の設計と外部APIへの信頼の確認が必要であり、案Bより費用が増える。
