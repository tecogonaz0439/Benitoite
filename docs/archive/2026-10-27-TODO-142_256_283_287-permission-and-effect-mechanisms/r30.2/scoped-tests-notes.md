# R30.2 の実ソースによる型の確認

## 対象と作成時の関門

追加した主な検査の境界は `pipeline::check_text` と `pipeline::desugar_checked`、その出力を読む公開の IR 検査器である。`tests/scoped_calls/file_io.rs` を親の統合ターゲットへ登録した。本番のコードと公開 API、テスト専用の署名・差し込み口は変えていない。既存の検査は残した。

| 守る契約 | 想定する退行 | 既存の検査が届かない理由 |
|---|---|---|
| 六 File 操作の入力添字と潜在効果の一致、直接呼び出し・期待入力付き関数値・期待型なしの既定値・不適合入力の診断 | 新操作が旧 `TopTargeted` に分類される、入力だけが具体化される、期待入力を無視する | 既存の四経路の単体検査はテスト専用の宣言表を使い、本番の六登録と通常の脱糖を通らない |
| 検査の成功型へ入る型制約と既定値 | 注釈のない検査を常に非 Top または常に Top に固定する、Top を後から狭くする | 既存の Scope 検査だけでは、登録した実 File 操作へ渡す型制約を確かめられない |
| 節の引数の射影・拡大の受理位置と所属の根拠 | 節の狭い型の注釈だけから所属を作る | 新操作の実登録前には実ソースの節を使用できなかった |
| 処理しない書き込みと節の引数の不変添字の区別 | 未処理の書き込みの存在だけで handle を拒否する、節の添字を宣言上限へ広げる | L50.4 の例は Lean の検査器の例であり、Rust の通常ソースを通していなかった |
| 完全な File.Write ハンドラの節が別対象へ行う IO は外側へ残る | 保護本体と節の効果を一緒に消す | 既存の旧操作の検査では、新しい対象引数の型から別対象を選ぶ経路を使わない |
| 実装メソッドから新操作を使い、辞書の解決と通常 IR を通す | 範囲変数を持つ署名で辞書の個数を誤る、失敗診断が欠落する | 仮の署名の単体検査では通常の型クラスの解決と脱糖を通らない |

## 六署名と PendingIo

`readTextIn`・`readBytesIn`・`writeTextIn`・`appendTextIn`・`writeBytesIn`・`appendBytesIn` の全てを、実際の標準宣言を読み込んだ通常ソースで確認した。各署名は入力の `PathIn` と効果の原子に同じ `rvar 0` を保持する。通常解析の宣言表で、種類の列 `[Path]`、範囲変数一個、`Single(Path, 対象位置0)` も独立期待値と照合した。受理した全入力は通常の脱糖と IR の再検査まで成功した。

| 経路 | 六操作に共通する結果 |
|---|---|
| `PathIn["/data/**"]` の対象引数で直接呼ぶ | 呼び出しの列、関数型の入力、潜在効果が全て `/data/**` |
| 狭い入力を持つ関数型を期待して関数値を返す | 同じ三箇所が `/data/**` |
| 期待する入力型が最後までない、未使用の `bind operation <- File.*In` | 同じ三箇所が Top |
| String の対象引数で呼ぶ | 六操作とも E0401 |

R20.3b の第四経路は、解決の途中でテストの宣言表を意図的に破損させる内部診断の検査である。実ソースから同じ破損は作らない。本検査は本番の署名への不適合入力が E0401 になることを確かめ、登録表の破損の内部診断は既存の単体検査に残す。通常ソースの四経路を確認したことを、宣言表の破損を再現したこととは扱わない。

注釈のない関数値でも、後の呼び出しが狭い入力型を制約すれば、その型から具体化される。Top の既定値は、期待入力が最後まで決まらない場合の値である。

## 検査結果の型の制約

| 検査から File.readTextIn への経路 | 検査と IO の列 |
|---|---|
| 成功型を `PathIn["/data/**"]` と注釈し直接渡す | 両方 `/data/**` |
| 成功型の注釈なしで直接渡す。パターンは既知の `/data/**` | 規則の既定値から両方 `/data/**` |
| 成功型の注釈なしで、入力が裸の `PathIn` の通常関数へ渡し、その関数が IO を行う | 型制約から両方 Top |
| 前の Top の値を `widenPathIn` で `/data/**` へ変えようとする | E0519 `notCovered` |

## 節の引数の射影・拡大

操作は実際の `File.readTextIn` を使い、射影・拡大は全て `bind` の右辺の直接の呼び出しにした。狭い S は保護本体の単一の `File.Read["/data/a"]` から選ばれる。

| 保護本体の対象の型と節の添字 | 節の処理 | 結果 |
|---|---|---|
| `PathIn["/data/a"]`、S=`/data/a` | `bind text <- Scope.pathInValue(path: captured)` | E0519 `unknownSource` |
| 同上 | `bind wide: PathIn["/data/**"] <- Scope.widenPathIn(path: captured)` | E0519 `unknownSource` |
| 裸の `PathIn`、S=Top | `bind text <- Scope.pathInValue(path: captured)` | 受理、脱糖と IR 再検査も成功 |
| 同上 | `bind wide: PathIn <- Scope.widenPathIn(path: captured)` | 受理、脱糖と IR 再検査も成功 |
| 同上 | `bind wide: PathIn["/data/**"] <- Scope.widenPathIn(path: captured)` | E0519 `unknownSource` |

節の狭い引数には入口で事実がない。`bind` の位置へ直すだけでは、狭い添字の引数は射影・拡大できない。回避するには受け取る入力を裸の `PathIn` にし、Top のまま射影する。狭い所属を保ったまま処理するなら、同じ狭い型を受ける通常関数や IO へそのまま渡せる。後者の形は次の受理例で確認した。規則を変更していない。

## L50.4 中3 と別対象の IO

| 実ソースの形 | 結果 |
|---|---|
| `/data/a.txt` へ書く保護本体を `Tick` だけのハンドラで囲み、関数の上限を `File.Write["/data/**"]` とする | 受理、脱糖と IR 再検査も成功 |
| `File.writeTextIn` の節が捕捉したパスを `PathIn["/data/a.txt"]` の引数へ渡す | 受理、脱糖と IR 再検査も成功 |

| 前の関数の上限を `File.Write["/data/a"]` だけにする | E0519 `notCovered` |

## 名前解決、実装メソッドと直接の読者

`import Benitoite.Unofficial.IO.File as Files` は、組み込みのエフェクトを宣言するモジュールの改名を禁じる E0339 で拒否される。File について別名を使えるという受理は確認しておらず、既存規則を広げていない。同綴りの利用者の File 操作の認定の全照合は R30.5 へ残す。

`Read[String]` の実装メソッドで `Trait.Show.show` と `File.readTextIn` を使い、狭いパスを渡す通常関数から呼ぶ入力は受理され、脱糖と IR 再検査が成功した。呼び出す値を Integer に変えて実装を欠かせると E0705 となる。

`typeck/traits/solve.rs` の使用箇所の辞書の期待個数は `signature_at_top` で読まれ、個数に範囲は影響しない。`ir/desugar/decls.rs` は Scheme と `range_signatures` をともに写す。ハンドラは節の選択後の具体化を使い、State の note の読者も `signature_at_top` のままである。本番コードの読者の変更は要らなかった。

## 局所実行と失敗

実行コマンドは全て `cargo test --test scoped_calls file_io:: -- --nocapture` である。初回は終了101、5件中3件成功・2件失敗だった。Trait の import が不足して E0332 となったことと、別対象の効果の拒否を E0501 と期待していたことが原因である。import を加え、現行規則の E0519 と一致する独立期待値へ直した。その後の [再検査](scoped-file-after.log) は終了0、5件成功、外側6.001秒だった。

完全な Write ハンドラへ強めた際には、追加した節の `path` が外側の引数を隠して E0338 となった。外側の引数を `protectedPath` に改名した。[記録](scoped-file-complete-handler-initial.log)は終了101、外側3.632秒である。

注釈なしの関数値を後で狭い入力で呼ぶ例を、期待型なしの Top の例と最初に取り違えた。実際には後の入力から狭く具体化される。[記録](scoped-file-unannotated-initial.log)は終了101、外側5.825秒である。Top を要求する通常関数へ渡す形へ直し、既知パターンだけで非 Top を既定にできる形も対にして確認した。

六署名のメタデータを加えた後、File を別名で取り込む形を受理と期待したが、既存の E0339 で拒否された。[記録](scoped-file-alias-initial.log)は終了101、外側6.446秒である。既存規則どおりの拒否を確認する期待値に直した。

最終の [局所実行](scoped-file-final.log) は終了0、6件成功・失敗0・無視0・対象外23件、外側9.176秒である（ビルドの排他待ちを含む）。[計時](scoped-file-final.json)は Python の単調時計で採った。作業末の全統合と clippy・fmt は取りまとめ担当が実行する。この局所検査を W-R の完了とは扱わない。最終の局所実行前に Rust の新規テストファイルだけを rustfmt で整形した。登録と公開の規則を変更する停止条件には該当しない。
