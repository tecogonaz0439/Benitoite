標準のモジュールの種類と完全名、宣言名、解決済みの束縛番号、`BuiltinFn` の種類を照合する。規則名は Lean の `ScopeState.ruleDeclarations` の六つに限る。現在の標準ソースに実在する四入口を認定する。同じ綴りの利用者の関数、旧 Scope、関数値を局所に保存した間接呼び出し、穴のある部分適用は入れない。import の別名は同じ標準宣言を指す場合に認める。

|---|---|---|---|
| `Scope.checkPathIn` | `Benitoite.Scope` | pattern 0、path 1 | 認定する |

| 対象 | 鍵・位置の対応 |
|---|---|
| 本体 | 元定義の識別名と `surface_preorder = 0` |
| 関数・定数 | `<module>.<name>`。入口モジュール名が空なら `.name` |
| 実装メソッド | `<module>%impl:<宣言の0始まり位置>:<メソッドの0始まり位置>:<name>`。区間解析と共通の列挙・変換 |

| 入れ子 | lambda・lazy・保護本体・節とも囲む定義の識別名と通しの番号 |

入口の辞書数は、関数では Scheme の全制約、メソッドではその先頭の実装自身の制約を除いた列である。これは既存の脱糖 `definition` の辞書の取り出しと、Lean の `MethodInput.names` に合わせる。型の確定を待たず、宣言の署名と実装の情報だけで得られる。`ScopeEntry.positions[index]` は Lean の `entryScope.idAt(index) = index` に対応する Rust の束縛である。`Release.binds` は引数の列を逆順にするため、メソッドの例は `[other, value, None]`、関数の例は `[value, None]` となる。

## 入力の取り出しと循環の不在

`typeck/source_input.rs` へ元定義の列挙を移し、区間解析と Scope が共有する。`typeck/scope/` の構造収集は宣言検査の後、定数の検査と関数の本体の型生成より前に実行する。入力は AST・名前解決・宣言の Scheme・実装の制約の情報であり、本体の解決済み全型表を引数にしない。

構造収集は AST を変更・複製せず、明示した積み重ねで元位置・文・呼び出し・引数の位置を収集する。補間の変換関数だけは、値が String かどうかで個数が変わるため、その位置を構造入力へ先に保存する。`Body::finish` の冒頭で推論中の補間の型を読み、変換の有無の Boolean だけを補完する。型全体の finalize、区間解析の `BodyInput`、整数の区間、警告、観測は読まない。未確定の変換は推測せず `PendingInterpolation` で止める。全本体の処理後、構造入力とこの小さい補助表を `TypeckOutput.scope_inputs` へ保持する。定数の本体は一度だけ保存し、参照を束縛番号で共有する。`ScopeBodyInput.numbered()` を読むときに、同じ構造から出現・文・呼び出し・引数の番号を `ScopeNumberedInput` として作る。

したがって、構造入力の作成は型生成に先行し、番号の正規化で読む後の情報も補間の Boolean に限る。型確定後の警告から必須判定へ戻る依存はない。R20.2/.3 で局所解析と型制約を接続する際も、この番号用の補完と構造入力を区別する必要がある。入力型へ区間解析の全入力を埋め込んだ仮置きではない。

全ての元定義の列挙は保つ。`contains_rules()` の表は、定数の参照を逆向きに辿って規則対象の呼び出しの存在を伝えるもので、定数の束縛番号を BTreeMap の索引で引いて逆参照表を作り、規則の有無の伝播では各参照辺を一度だけ辿る。R20.2 は規則のない本体の自明な受理のために番号列を展開する必要がない（Lean の `acceptFn_noRules`）。この照会は番号・規則・予算を変えず、不要な定数の重複展開を避けるための入力の読み取りである。共有構造の Debug は定義数だけを表示する。

名前付き引数は `arguments`・`argument_preorders` をソース順に保ち、`source_to_contract`・`contract_to_source` を別に持つ。引数の開始番号は走査中の引数の位置から記録し、元の NodeId で番号表を検索し直さない。同じ const の値式を複数の位置へ展開しても、その出現を区別できる。

## 出現番号と Lean の対応

Scope の本体は Lean の `ScopeAccept.occurrences` が用いる `Interval.preorderBlock` に対応し、最初の右辺は `bodyKey` の 0 である。既存の区間解析は `bodyRoot` の合成 block 式を番号 0 に置き、最初の右辺を 1 とする。この根の違いを保ち、式の子を辿る規則を一致させた。`ScopeOccurrence.reachAt_occurrences` が示す文の始まりと右辺の番号の一致を、Scope 入力の記録でも保つ。

式を自分、宣言の欄の順の子の順で数える。容器と専用構築器の束縛自身は数えない。腕は guard、本体、残りの腕、節は本体を宣言の順に辿る。入れ子も囲む定義の番号である。constructor の呼び出しの頭、穴、専用構築器への参照は表層の対応に従って省く。const は使用位置の constE の後に元の値式を展開する。リスト展開は concatenate、前の要素、展開する式、後の要素、補間は全ての値式、必要な全ての変換関数の順である。直接の負のリテラルは一出現とする。

取得した番号は接頭辞として保持し、深さ・整数表現・参照の欠落・未確定の補間で止まった後の番号を詰めて再開しない。現時点の深さの取得上限は 4096 である。Scope の操作数・保持数・本体／全体の予算はまだ計上しておらず、R20.5 の対象である。

### 暫定の上限と後続の接続

`DEFAULT_NUMBERING_OPERATIONS = 100_000` は、区間解析の本体の番号付けに使う操作数予算と同じ大きさの暫定値である。Scope の局所解析の採用値としたものではない。上限の引数は必須であり、上限を通さない読み取りの入口は残していない。イベントの操作数はこの枝の番号付けの計上であり、R20.5 の局所解析の計上単位を実装済みとはしない。予算の超過の理由は `budgetExceeded` と、本体／全体・操作数／保持数の区別を表せる形で保持する。今回実装した停止は本体の操作数だけである。

22段・40段の共有定数は、深さ上限に達する前に操作数で停止する。上限0のときは出現・文・callの保存を行わず、正の上限では規則のcall0と文の開始 `[0,4]` を含む接頭辞を保存する。出現番号が0から連続すること、出現数が操作数上限以内であること、停止後の葉や文を詰めて補わないことを確かめる。gc-stressで規模を下げるのは、同じ停止目的を保ちながら常時回収下の入力処理を抑えるためであり、ignoreや時間制限の緩和は加えていない。
