# IFC-D2: サーバモードの前後で宣言する情報フロー制御の保証の案

2026-10-27、IF10.01。設計者が選ぶための判断案であり、採択済みの決定でも、実装・証明の完了報告でもない。

## 決めることと既に決まっている境界

IFC-D2 で決めるのは、LLM・スクリプト・外部入力に誤りや悪意がありうる状況で、利用者の秘密と信頼する操作を守るため、0.0.14 の保証を方針の保護と対応済み経路を前提とする誤り防止の静的検査に限り、意図した迂回に対する保証はサーバモードで強制との接続を閉じた範囲に加えるか、誤り防止に限り続けるか、サーバモードより前から隔離も保証するかである。

[README「版の割り振りと情報フロー制御の方式」](../README.md#設計者の決定2026-10-27版の割り振りと情報フロー制御の方式)は、0.0.13 を判断・棚卸し・契約の設計、0.0.14 を情報フロー制御（information-flow control）の独立した実装、その後を必要な接続とサーバモードの実装に割り当てた。サーバモードの版番号は未定であり、`0.1.0` より前という順序だけが決まっている。内部の判定と Lean の証明に汎用の束を用い、最初は管理者が定める有限の束、機密性と完全性、用途を限った非機密化（declassification）とエンドースメント（endorsement。信頼の付与、または完全性レベルの引き上げ）、一階の印の要約を扱う決定も再選択しない。

[判断14](../decisions.md#判断-14-保証と後の宛先の契約)は、型の対象上限を許可とせず、実行時の権限制御をサーバモードより前に単独で入れないとしている。[00-01「保証の範囲」](../../../design/00-overview/00-01-goals.md#保証の範囲)は、それまでの隔離をハーネスや OS に委ね、静的検査から意図との一致・外部操作の成功・停止を導かない。[判断19](../decisions.md#判断-19-情報フロー制御の方式と今回の成果物)の方式を、この境界の中でどの保証として提供するかが今回の選択である。

## 関係する者と守る対象

[07-01「脅威モデル」](../../../design/07-quality/07-01-security-model.md#脅威モデル)の信頼関係に、「信頼する起動側」という役割を一つ加える案である。この説明上の呼び名は、利用者が承認した方針・契約と検査済み成果物の組を、未信頼の書き手による変更から保護して処理系へ渡す部分を指す。既存の術語として採用する提案ではなく、用例は未確認である。利用者は作業と許す操作を決め、処理系・依存するクレート・OS は規則どおり動くと信頼する。LLM とハーネス、スクリプト、依存パッケージ、外部入力は信頼しない。攻撃者は、LLM が読む文書や実行中の応答へ指示を混ぜたり、生成するコードを介して検査を迂回する操作を試みたりしうる。

誤りの主体は、コードを作成・修正する LLM、スクリプトや依存パッケージの書き手である。利用者や管理者が秘密の登録・受け手・信頼する関数を誤って選ぶ可能性もあるが、静的検査はその意図の正しさを保証しない。「誤りを対象」とする案でも、LLM やスクリプトを善意として信頼する前提へ変えない。

守る対象は、登録した秘密の内容と派生値、その秘密に依存する制御、及び未信頼の入力が用途の承認を経ずに決めてはならない操作と結果である。秘密を読めることと、あるホストへ接続できることを別々に許しても、その秘密をそのホストへ送ってよいとは限らない。完全性についても、公開してよい応答を、シェル本文などの信頼を要する用途にそのまま使ってよいとはしない。

セキュリティ型システム（security type system）は、書き手の意図を判別しない。同じ禁止フローは、誤って書かれた場合も意図して書かれた場合も拒否する。各案の差は、方針の書き換え、外部コマンドによる独立した読み取り、検査を経ない起動まで含めて、製品が迂回を止めると宣言する時期と範囲にある。

「保証を付ける対象」は、同じ方針・契約と検査対象の対応を前提に、情報フロー制御の保証を示す実行の範囲を指す説明である。新しい術語やCLIモードとして採用する提案ではない。

## 推す案と二つの代案

案Aは「サーバモードの前は前提付きの誤り防止、サーバモードで強制と統合」、案Bは「情報フロー制御の保証は誤り防止に限定」、案Cは「0.0.14 から敵対的なコードの隔離も保証」とする。[元の問いD2](../study/questions.md#0013-の中で決めること設計の判断として文書にするもの)の三つの選択肢を具体化したものである。

| 比較する点 | 案A: 前提付きの誤り防止から強制へ統合（推す） | 案B: 誤り防止に限定 | 案C: 0.0.14 から隔離も保証 |
|---|---|---|---|
| 攻撃者・誤りの主体の扱い | LLM 等は信頼しない。0.0.14 では検査内の禁止フローを拒否するが、検査外への意図した迂回を処理系が防ぐとは宣言しない。サーバで迂回への強制を接続する | LLM 等は信頼しない。静的な禁止フローの拒否は案Aと同じ。サーバでも情報フロー制御と強制を合わせた隔離の保証は宣言しない | LLM 等が意図して迂回する場合も、対象とする実行では方針改変・検査省略・子プロセス等の迂回を止めると宣言する |
| 0.0.14 で保証すること | 保護された同じ方針・検査と実行の対応・信頼する入出力契約の下で、対応する逐次計算の内容・派生値・制御を追い、禁止された出力と未承認の影響を静的に拒否する。未対応経路は保証を付ける対象では拒否する | 案Aと同じ静的保証。誤り防止に限るという説明を、後の版でも維持する | 案Aの静的保証に加え、信頼する実行側が方針と検査済み成果物を保護し、対象外の実アクセスや起動を強制的に止める必要がある。現行計画のままでは提供できない |
| 0.0.14 で保証しないこと | 方針の保護自体、外部コマンドの独立した IO、検査を経ない実行、ハーネスによる独立の読み取りの隔離。下の共通の除外も残る | 案Aと同じ。警告だけに弱めたり、禁止フローを任意に通したりする案ではない | 全 OS・全外部コマンドへの一般保証は根拠がない。対象構成と禁止機能を限定し、全迂回が閉じるまで隔離を宣言できない。共通の除外は残る |
| サーバモードの版で加える保証 | 同じ方針の保存・変更の承認、実行時の操作ごとの照合、OS の強制を接続し、対応済み構成では意図した迂回も方針の範囲で止める。子の独立したアクセスもその接続の対象にする | 00-01 で予定する操作の権限制御と OS の隔離は提供する。ただし、内容の流れまで含めた一体の保証は追加せず、情報フロー制御は前提付きの静的保証に留める | 0.0.14 へ先行させた強制をサーバの保存・承認へ接続する。別の暫定方針を作れば、同じ方針へ戻す設計と照合も要る |
| 00-01 との関係 | 静的検査と実行時の権限制御を分け、サーバ前の隔離をハーネスや OS に委ねる決定を保つ | 同じ決定を保つ。ただし synthesis が推す「サーバで意図した漏れにも対応」という到達範囲を採らない | サーバ前に処理系自身の強制を提供するなら00-01と判断14の変更が必要。既存ハーネスへ委ねたままなら案Aの前提付き保証であり、案Cの製品による隔離保証にはならない |
| 利用者への説明案 | 「0.0.14 は、承認した方針と対応機能の範囲で情報の流れを実行前に検査する。方針と実行環境の保護は起動側が担う。サーバモードでは接続を確認した構成について、実行時の制限も同じ方針で強制する」 | 「情報の流れの検査は、方針と入出力契約を前提とする誤り防止である。サーバの操作制限と内容の流れの保証は、それぞれの範囲を確認する」 | 「対応する構成では0.0.14から、方針保護と実アクセスの制限も実行側が強制する」。その構成と根拠がない段階では使えない説明である |
| 後の版への影響 | 必須例に必要な接続を独立した改造へ割り当て、サーバ前に拒否・失敗の観測を閉じる。Task 等の一般接続を自動的に必須にしない | 強制と情報フロー制御の接続を受け入れ条件にしない。後に一体の保証へ進むには保証の追加判断と接続の計画が要る。単純な操作制限から内容の保護を推論させない説明が続く | 方針保護・成果物の同一性・OS と子の制限・拒否の観測を0.0.14以前の前提に移す。版の割り振りと重い改造の順序を設計者が見直す必要がある |
| IFC-D3〜D9への依存 | 全てに依存する。D3〜D6で入口・出口・緩和の契約、D7・D9で所有と承認、D8で対応範囲を確定する。回答前は下の8例も候補である | D3〜D6・D8の静的な義務は同じ。D7・D9も方針の正しい入力のために必要。サーバでの一体の保証を外しても、信頼する契約や所有者を省略できない | D3〜D9を全て先に閉じたうえで、方針改変・実行時拒否・OS の迂回への強制が要る。D2への回答だけでは前倒しできない |
| 費用の見込みと根拠 | 0.0.14の案GはLean 154〜374時間、処理系等182〜420時間という既存の能動時間の見込みを維持する。サーバとの接続・OS の強制・独立レビュー待ちの時間は不明 | 同じ案Gを実装するため、0.0.14は案Aと同じ見込みを使う。省ける接続と時間の削減幅は不明。保証の呼び方だけで証明や棚卸しが減る根拠はない | 案Gの費用に、サーバ前へ移す強制と接続の費用が加わる。追加分と合計は不明。既存見込みはサーバ・OS・一般のTask/Process/WASM接続を含まないため、それを上限にできない |

費用の出どころは [synthesis「大きさの見込み」](../study/synthesis.md#大きさの見込み)と [S6「規模の見積もり」](../study/information-flow-generality.md#規模の見積もり)である。実測ではなく、検査・測定の実時間や設計者の回答待ちを含まない。案Bでも、非干渉性を弱い警告やテストだけに置き換える費用の削減は見込まない。案Cを選ぶには、既存決定の変更と再見積もりが必要であり、この文書はその変更を承認した扱いにしない。

全案で、意図との一致、外部操作の成功、停止、時間・資源使用量による漏れ、許した受け手による再配布、信頼する処理系・OS等の不具合を突く攻撃は保証しない。外部APIが認証情報を応答へ反映しないことも静的検査だけでは証明できず、契約を信頼する条件として承認するか、応答を秘密に保つ。

## 案Aで明示する前提と観測

案Aを選ぶ場合、0.0.14 の保証には次の前提を付ける。これらは処理系が既に実装した機能の一覧ではない。

| 前提 | 0.0.14での責任と保証の限界 | サーバモードとの接続 |
|---|---|---|
| 方針と信頼する契約の保護 | 利用者が信頼する起動側が、秘密の登録・受け手・非機密化とエンドースメントの契約を渡す。未信頼のLLMにそれらを自由に緩和させない。処理系自身が保存や変更承認を強制するとは宣言しない | 所有者・版・識別子・承認が必要な変更を同じ方針で保存し、未承認の変更を実行側が拒む。D7・D9の判断が要る |
| 検査と実行の対応 | 検査したプログラム・依存・方針・標準契約の組を実行することを前提にする。検査後の書き換えや別方針での再起動まで防ぐ保証を先取りしない | 保存した承認と実行する成果物を結び、変更時の再検査と再承認を接続する |
| 入口・出口と実対象の対応 | 一般のファイル読み取りは保守的な分類、精密な公開入力は認定した範囲・入力契約を使う案とする。リンクや差し替えを字面だけで排除しない。HTTPでは対象上限と要求各欄・応答・リダイレクトの契約を照合する | 実パスや通信先への強制、実行時拒否と公開の失敗の関係を閉じる。実対象の除外と内容の分類を同じ秘密登録から導く設計へ渡す |
| 未対応経路の拒否 | 保証を付ける対象では、未対応のTask・共有状態・汎用Process・WASM等を、依存や高階の呼び出しも含めて静的に拒否する。解析不能を公開として通さない | 必須例に必要なものだけ、契約と強制を接続した後に対応へ変える。サーバ化だけで一括受理しない |

処理系の外でこの前提を満たす構成の例として、人間が管理する方針・契約の領域をLLMの書き込み可能範囲から外し、承認済み入力を渡す起動用の処理だけを利用者が管理する形がある。検査したコードと依存の組も別の保護された領域で固定し、LLMが別方針・別成果物で起動した実行を、その承認の対象に数えない。ハーネスの権限設定やOSのアクセス制限でこの分離を作る構成案であり、特定製品の設定を確認した報告でも、0.0.14の処理系に保護機能を加える案でもない。

主な利用の形で、ハーネス内のLLMが `benitoite` を自由に起動し、方針のファイルも編集できる場合は、この前提を満たさない。その場合に言えるのは「今回渡された方針への静的な適合」までであり、「利用者が承認した方針を守る」保証は付けられない。検査を通すためにLLMが方針を緩める行為は、0.0.14の処理系が止める保証の外である。前提を満たす構成の準備と、その実行への対応付けはD7・D9とIF30で確認する。

通常実行にどの既存機能を残すか、拒否をどの単位で判定するかはD8とIF20の棚卸しへ渡す。外部コマンドを許す通常実行が残る場合、子が独立して秘密を読む操作はこの保証の外である。その実行に「情報フロー制御で安全」という成功表示を与えない。

この区別は、[synthesisの保証表](../study/synthesis.md#版の割り振りと各版の保証)が併記する「未対応の機能を拒否」と「Process.runで独立して読ませる例は通る」の読み分けでもある。前者は保証を付ける対象、後者は検査外の子の振る舞いまで隔離しない版全体の限界として扱う。後者を、前者の対象で汎用Processを無条件に受理する根拠にはしない。

非干渉性の契約案では、同じコードと方針、対応する公開入力と外部応答を前提に、許さない秘密だけが異なる二実行がともに終了したとき、受け手の見る値・宛先・操作の有無と順序・公開の失敗と終了状態が一致することを求める。完全性では、同じ方針の下で信頼する入力とコードを固定し、対応する外部応答を伴い、未信頼の入力だけが異なる二実行がともに終了したとき、信頼する操作と結果の観測が一致することを求める。非機密化とエンドースメントを認めた場合は、許した値・成否・呼出条件が対応する二実行について、残りの観測が一致するという条件へ限定する。LLMが生成時に注入を読んで悪いコマンドを定数として書いた場合まで、実行時の入力の印だけで検出できるとはしない。

完全性で正常／失敗の終了状態を常に「信頼する観測」に含めるかは、RV-IF10のB1に対する未確認の項目である。D5は確認前の候補(ii)としてfail・非再開を公開かつ信頼するpcに限る。未信頼pcでそれらを許す候補(i)については、後続の信頼する操作が消える場合と、終了状態だけが変わる場合をIF30が0.0.14の試作へ渡す。機密性の公開観測に終了状態を含める条件は保つ。

発散と終了の差を除外しても、正常終了と失敗終了の違いを一律に除外しない。[SD §2〜§4](../spikes/SD/findings.md#2-送信と観測の規則)は、小モデルで受け手の受信列と終了状態を観測し、`pc ⊔ label(d) ⊔ label(v)` の受け手がR全体を覆う条件、公開pcでのfail・非再開・宛先検査を確かめた。一般のハンドラ・実IOの成否・Task・解放・緩和との合成には未接続であり、本番全体の保証には外挿しない。[SH2](../spikes/SH2/findings.md)も型・効果と値・Emit列の一致の独立モデルであり、方針保護や非干渉性の証明ではない。両試作をやり直す必要も、短い実績から案Gの費用を下げる根拠もない。

## 典型8例の扱い

「対象」は情報フロー制御の規則で可否を判断する範囲を指し、受理を意味しない。「対象候補」はD3〜D9の回答と契約の実装後に受理を目指すもの、「後の版」は0.0.14では保証付きで受理せず未対応として拒否するもの、「対象外」は通常実行が残っても情報フロー制御の保証を付けないものを指す。サーバの版を含む後の版での受理は、必要な契約と接続を閉じた場合に限る。出どころは [S6「典型例の受理と退き先」](../study/information-flow-generality.md#典型例の受理と退き先)と [planのIF10の行](../plan.md#本番を変えない並行作業)である。

| 典型例 | 案A | 案B | 案C |
|---|---|---|---|
| 公開CSVの集計・表示 | 対象候補／0.0.14。公開入力の契約を用いる。未知の一般読み取りは秘密の結びとして表示を拒否しうる | 対象候補／0.0.14。案Aと同じ。サーバでも静的保証の前提を表示する | 対象候補／0.0.14。ただし公開入力と実ファイルの対応、方針の保護を強制する範囲が先に必要 |
| 認証付き取得の件数と成否の表示 | 対象候補／0.0.14。固定API操作の値・成否・呼出条件を限る契約が必要。外部APIの信頼条件を承認し、完全性は未信頼のまま保つ | 対象候補／0.0.14。同じ契約が必要。誤り防止だけを目的にしても自由な印の緩和は認めない | 対象候補／0.0.14。同じ契約に加え、その登録・差し替えを攻撃者に許さない実行側が必要 |
| 機密ファイルの固定API送信 | 対象候補／0.0.14。入力分類、同じ検査済み宛先、R全体への被覆、制御・要求各欄を確認する。応答の公開は別契約 | 対象候補／0.0.14。同じ静的条件。外部実体の保護は独立した前提のまま | 対象候補／0.0.14。同じ条件と実アクセスへの強制が必要。host/portだけからHTTPSのoriginへの限定を導かない |
| 任意URLへの秘密のwebhook送信 | 対象／拒否。任意の受け手を許したと近似しない。公開設定から作る検査済みの狭いRへ変更すれば別の受理候補となる | 対象／拒否。案Aと同じ | 対象／拒否。早期の隔離を入れても、任意URLが秘密の受け手として適切になるわけではない |
| Taskによる認証付きの並行取得 | 後の版。0.0.14では未対応として拒否し、逐次化した例を候補にする。結果・失敗・待機・取消しの接続後に再判断 | 後の版。逐次化は同じ候補。一般の接続を必須とせず、追加時も静的保証に限定 | 後の版。0.0.14で拒否する境界自体も迂回できないことが必要。早期隔離から並行の非干渉性は導けない |
| OAuthトークンの保存と再読 | 後の版。保存先と再読の分類が対応する保管口が必要。サーバの承認・保存との責任も接続する | 後の版。保管口の契約なしでは拒否。対応後も実ファイル保護を前提とする静的保証に限定 | 後の版。分類保存に加え、保管領域や登録の改変を防ぐ強制が必要。全OSの保管口は未見積もり |
| gh/gitへの認証の委任 | 0.0.14は対象外。保証を付ける対象では汎用起動を拒否する。後の版で専用契約・子のIOの分類・OSの隔離を接続して再判断 | 同じく0.0.14は対象外、保証を付ける対象では拒否。後に通常の起動を許しても、子を含めた一体の情報フロー制御の保証は追加しない | 汎用起動は拒否。後の版で専用契約と子の強制を閉じるまで受理しない。コマンド名の許可だけでは条件を満たさない |
| 実行時のLLM出力をシェル入力にする | 対象／未信頼のシェル本文として拒否し、汎用Processも未対応とする。後の版ではデータとして扱う狭いAPIや固定操作への変換を検討 | 対象／拒否。案Aと同じ静的理由。通常のシェル起動が残っても保証の対象外 | 対象／拒否。固定操作の契約と強制を閉じてから再判断する。隔離の導入や任意のエンドースメントだけで任意シェル本文を受理しない |

初めの三例を0.0.14の必須例にするかはD8の選択として残す。任意URLへの秘密送信は、未対応だから後でそのまま通す例には分類しない。受け手を制限する変更が必要である。最後の例は実行時の未信頼入力の用途の問題であり、生成前の注入によって危険な定数が書かれる問題とは区別する。

## 外部の方式から確認できる範囲

2026-10-27に次の一次資料の本文を確認した。既存調べの結論だけを根拠に、Benitoiteの保証が実装済みとは扱わない。

| 一次資料 | 確認した事実 | この判断案での使い道と限界 |
|---|---|---|
| [Jif 3.3.0公式文書「Label checking」](https://www.cs.cornell.edu/jif/doc/jif-3.3.0/label_checking.html)の「Program counter labels」「Normal and exceptional termination」「Downgrading」 | pcはその位置への到達から分かる情報を表す。正常・例外の終了にも印を付ける。非機密化とエンドースメントには次元・権威・robustnessの条件を置く | 値だけでなく制御・成否・緩和の条件を契約へ含める先行例である。Jifと同じrobustnessをBenitoiteが既に持つという根拠にはしない |
| Stefanほか、[Flexible Dynamic Information Flow Control in Haskell（2011）](https://www.scs.stanford.edu/~deian/pubs/stefan:2011:flexible.pdf) §2.2・§7 | 未信頼のLIOコードが通常のIO計算を混ぜてIFCを迂回できない制限と、信頼するコードからの実行を説明する。並行への拡張は同論文の将来課題である | 検査・追跡の外のIOを自由に残したまま一体の保証を宣言しない参考となる。2011年論文の範囲だけを参照し、後のLIOの並行対応の現状は未確認である |

これらは保証の前提を比較する資料であり、案A〜Cの実装時間を測定した証拠ではない。

## IFC-D3〜D9への依存と申し送り

次表は案Aを選ぶ場合の条件案である。各枝の判断を先に採択したものとして扱わず、別案が選ばれた場合は比較表の差を反映する。

| 判断・枝 | 渡す条件と、その判断へ残すこと |
|---|---|
| IFC-D3／IF10.02 | 固定APIの値・成否・用途・呼出条件と、外部APIが秘密を反映しない信頼条件を区別する。認証の応答を公開しても完全性は未信頼のままにする。許した要求由来だけを緩め、他の捕捉・条件・本文の秘密を残す契約を選ぶ |
| IFC-D4／IF10.03・IF20 | 精密な入力契約と保守的な一般読み取りを分ける。パスの字面だけで公開としない。サーバ前に秘密ファイルの実行時拒否を追加した扱いにしない。未分類の入力を公開としない境界を具体化する |
| IFC-D5／IF10.04 | R全体への被覆に宛先・本文・pcの印を含める条件と、失敗・非再開の公開観測を渡す。`R ⊆ 許した受け手の集合` の向きを保つ。機密性と完全性の積では公開かつ未信頼の設定も保守的に拒否しうる点、schemeを持たない上限とoriginの差を残す |
| IFC-D6／IF10.05 | 取得、印を保つ取り出し、許可された非機密化を分ける案を評価する。`Secret` の伏字やエフェクトの除去だけで派生値の漏れまで防げると説明しない |
| IFC-D7／IF10.06 | 人間への作業・秘密・受け手・用途の要約と、秘密登録・緩和の承認を設計する。0.0.14の起動側への前提と、サーバが保存・強制する責任を分けて示す |
| IFC-D8／IF10.07・IF20 | 上の8例について対象・拒否・後の版・通常実行の保証外を確定する。初めの三例の必須化は未採択である。拒否単位と解析不能時の扱い、サーバ前に必要な接続の範囲を選ぶ |
| IFC-D9／IF10.08・IF30 | 同じ方針の所有者・版・識別子・承認が必要な変更・正規化済み入力を定める。方針・標準契約・成果物の対応と変更時の無効化を設計する。IFCだけの暫定許可ファイルを作らない決定を前提とし、承認の再利用と許可を狭める更新の条件を評価する |

[判断21](../decisions.md#判断-21-実装と提供の境界)に従い、どの案でも中核の規則をネットワーク・暗号・サーバの依存から分ける。構成で変えるのは利用できるモジュールと関数だけであり、型・エフェクト・印の意味を変えて保証を成立させる案にはしない。

## 設計者への一つの問い

追加の前提は、07-01の信頼関係に「信頼する起動側」の役割を設けることである。LLMが方針も編集できる主な利用の形では、利用者が承認した方針を守る保証を付けられない。この役割を処理系の外で満たす構成と、その確認の責任を上の表に示した。

IFC-D2は、0.0.14では方針の保護と対応済み経路を前提とする誤り防止の静的保証に限り、サーバモードで強制との接続を閉じた範囲へ意図した迂回への保証を加える案A、情報フロー制御の保証を誤り防止に限り続ける案B、既存の版の割り振りと00-01を見直して0.0.14から隔離も保証する案Cの、どれを選ぶか。

推すのは案Aである。理由: 00-01と既に決まった版の順序を保ち、0.0.14の静的な規則への適合とサーバの強制をそれぞれ確かめてから、両者を接続した範囲の保証を宣言できる。案Bより後の責任が明確になり、案Cが必要とする未見積もりの強制をサーバ前へ移さずに済む。
