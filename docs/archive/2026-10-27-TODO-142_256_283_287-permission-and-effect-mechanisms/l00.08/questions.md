## L00 で分かったこと

1. 格納方式の二案は、どちらも Top に特化した切り替えでは既定の全入口を通せた。二案とも「黙って Top に狭まる」危険があり、明示の構築関数を使う形が要る（[L00.01](../l00.01/results.md)）。
2. 対象の領域 `Scope.Domain.Range` は格納方式によらない一つの型として置けた。DET-01 の決まった三点を反映し、残る字句の細則は zone ID と IPvFuture を除いて帰納型を変えない（[L00.02](../l00.02/results.md)）。
3. 元の操作 b・閉じた範囲 R・実対象の一致 `io_target` は別の契約に分けられた。純粋な検査・明示拡大・七つの IO は表の項目の追加で表せ、新しい信頼条件の欄は `io_target` だけで足りた（[L00.03](../l00.03/results.md)）。ただし表のデータ `effKind`・`valKind`・`admitsR` の正しさは、信頼の対象として列挙していなかった（RV-L00 中3、問 11）。
4. 対象の健全性は旧の条件からは従わない（`target_not_from_core`）。観測を応答の関係に含める形（O1）なら新しい欄は要らず、到達先の言明は一段の言明から従う（[L00.04](../l00.04/results.md)）。本番の言明の案は操作の名前と対象の種類を落としているので、採用定義の配置で名前と種類を保つ形に直す予定である（RV-L00 中1・中2）。
5. 局所解析は、規則の表と一つの適用で書け、必須の判定は Range の警告の解析を読まない形にできた（[L00.05](../l00.05/results.md)）。
6. 母集団 691 宣言（定理 502）を分類した。棚卸しの 306 定理の約 9 割は両案とも点検のみで、値の所属・節の添字などの費用（印 NT・CS・NV・NS）は格納方式によらないと依存の印から推測した（[L00.06](../l00.06/results.md)）。
7. 案 (i) に署名の具体化を足すと、節の添字を Top に置いた `E_OpPrim` は sorry なしで閉じ、`Builtins.Assumptions` は変わらなかった。ただしこれは閉じた非 Top の値がない条件での空の成立である。節の添字を任意にすると閉じず、S を選ぶ規則と継続の型の変更が要る（[L00.06b](../l00.06b/results.md)）。
8. 案 (ii) から暗黙の変換を外すと、変更の少なさは Top の構築関数の書き換えでほぼ打ち消された。`E_OpPrim` は sorry のまま残り、原子の符号は作り直しが要った（[L00.06c](../l00.06c/results.md)）。二案の `E_OpPrim` と欄の量化の差は、定数が範囲を持つかという試行の条件の差である（RV-L00 中5、問 1）。
9. 非空の例を骨格の定義だけで書けた。値の所属は「新しい葉の規則」か「定数の規則の言明の変更」の二案が採れ、`Const.type` だけを変える案は採れない（[L00.07](../l00.07/results.md)）。
10. Q9 の (c) の境界は L00 の骨格で保たれており、後の (a) の足しやすさは格納方式より範囲の変数の表し方で決まる（[UB10](../ub10/results.md)）。どの枝でも停止条件に当たる事項はなく、公理は `propext`・`Classical.choice`・`Quot.sound` だけだった。

### 問 2 範囲の変数の表し方

- 選ぶもの: 署名表の範囲の変数を、型と原子の範囲の位置に置くか、別の形で持つか。
- 選択肢:
  1. （推す）型と原子の範囲の位置を `Ix`（閉じた範囲 `fixed R` か範囲の変数 `rvar i`）にし、署名表の項目をデータで持つ（L00.03 の模型）。
  2. 本番の型の範囲の位置は閉じた `Range` のままにし、署名表だけが `Ix` を持つ別の型を使い、具体化を型の変換にする（L00.07 の P3）。
  3. 表の項目を範囲の列から署名への関数として持つ（L00.03 の代案）。
  4. 対象の位置を一つだけ入れ替える（L00.01 の案 (ii)・L00.06b の `PrimSig.inst` の形）。
- 推す理由: 1 は明示拡大（範囲二つ）と検査（結果の型だけに R）を同じ具体化で表し、形の検査を Bool の計算で確かめられる（[L00.03](../l00.03/results.md)「署名の範囲の変数の表し方」）。後の (a) でも利用者の宣言をデータのまま持てる（[UB10](../ub10/results.md)「二案のどちらで足しやすいか」）。4 は明示拡大と検査の結果を表せず、3 は形の検査が全称の命題になる。
- 費用（未測定）: 1 は問 3 の条件と、範囲の変数の代入を型代入・行代入と別に持つ費用、`sig_scoped` の内容の拡張を要する（L00.03「既存の条件の意味の差」）。`Ix` を本番の `Ty` に置く費用（整形式性、`rvar` の代入、P1〜P5）は二案とも測っていない。案 (i) では構成子の引数の型が `Ix` になり、プログラムの型に `rvar` が入りうるので、格納方式の費用を変えうる（RV-L00「確かめないと分からない点」、注意 3）。
- 変わる後の段: L20（整形式性・shift/subst・署名の具体化・`sig_scoped`）、L20.2、L40（脱糖が具体化した R を渡す）、L50（署名表の交換）、R10（Rust の署名表の表し方）。

### 問 3 範囲の変数の条件の置き場所（問 2 で 1 を採る場合）

- 選ぶもの: プログラムの型（利用者の宣言・関数の定義・ラムダの注釈）に `rvar` が現れないことを、どこで要求するか。
- 選択肢:
  1. （推す）P1 型の整形式性。`Ty.WF` に範囲の変数の個数の文脈を加え、プログラムの型は 0、組み込みの署名は項目の `nranges` で検査する。
  2. P2 宣言ごとの整形式性（`OpDecl.Scoped` などに「`rvar` を含まない」を加える）。
  3. P4 `Program.EffectsOk` の連言に加える。
  4. P5 脱糖の出力に `rvar` が現れない補題だけにする。
- 推す理由: 条件がないと、範囲の変数を書いた利用者の操作は呼び出せない操作になり、未解決の変数を `main` の上限へ運ぶ（[L00.07](../l00.07/results.md)「範囲の変数の条件の置き場所」の `rvar_uninhabited`・`rvar_atom_uncovered`）。P1 は型変数の `Ty.WF C.length` と同じ形で、定義・ラムダ・注釈を一箇所で覆う。P2・P4 は定義やラムダで漏れうり、P5 だけでは脱糖を通らない交換の入力を覆わない（同節）。
- 費用（未測定）: `Ty.WF` の引数が増え、整形式性の保存と shift/subst の証明へ波及する。`desugar_typed` の `WellFormed` の結論に、P5 と同じ内容の義務が加わる。
- 変わる後の段: L20、L40（`desugar_typed`）、L50（交換の入力の検査）。

### 問 4 範囲の整形式性と正規形の置き場所

- 選ぶもの: L00.02 の `Range.WF`・`Range.FitsKind`・`Range.Canonical` を型の整形式性に入れるか（L00.01 の申し送り 6）。
- 選択肢:

### 問 26 DET-06 `effects.bounds` の JSON

- 選ぶもの: `check --report=json` の任意欄 `effects.bounds` の構造を下のとおりにするか。
- 選択肢:
  1. （推す）[language-rules A1](../study/language-rules.md#a1-uses方針の対象表示の書き方q1q11決定済みの旧-r18) の形を採る。各要素は `name` と `scope`、宣言の上限は `basis: declaredUpperBound`。`scope.kind` を L00.02 の `Range` の構成子に一対一で対応させ、Top は `{"kind":"all"}`、パスは `pathExact`・`pathTree`（`path` に幹）、endpoint は `{"kind":"endpoint","host":…,"ports":{"minimum":…,"maximum":…}}` とする。host はホスト名の `exact`・`one`・`many`（`name`）と、IP の完全一致（`address`）・CIDR（`address`・`prefixLength`）とし、IP には `family`（`v4`・`v6`）を置き、アドレスは正規形の文字列で書く。未知は Top の要素で表し、空の配列にしない。解析が終わらなかった報告は `bounds` を置かず、旧版と同じく `expanded` の各名前を全対象として読ませる。既存の形式の版を保つ。
