# IFC-D6: Secret の型と分類ごとの印、三つの操作の役割の案

2026-10-27、IF10.05。設計者が選ぶための判断案であり、採択済みの決定でも、実装・証明の完了報告でもない。

## 決めることと既に決まっている境界

IFC-D6 で決めるのは、P3 が型の実装を 0.0.14 へ送った `Secret` を不透明な表現と直接の表示・等値・JSON 変換の制限に使い、分類ごとの印を取り出した値・派生値・制御の追跡に使って、取得・印を保つ取り出し・許可された非機密化を分けるか、`Secret` を設けず印で扱うか、`Secret` の機密性を最も厳しい印一つへまとめるかである。

[README の版の割り振りと方式](../README.md#設計者の決定2026-10-27版の割り振りと情報フロー制御の方式)、P1〜P6、[判断14](../decisions.md#判断-14-保証と後の宛先の契約)・[判断19](../decisions.md#判断-19-情報フロー制御の方式と今回の成果物)・[判断21](../decisions.md#判断-21-実装と提供の境界)を前提にする。0.0.13 は判断案・入口と出口の棚卸し・契約の設計まで、0.0.14 は情報フロー制御（information-flow control）の独立した実装、その後は必要な接続とサーバモードである。内部の判定と Lean の証明には汎用の束を使い、最初は管理者が定める有限の束、機密性と完全性、用途を限った非機密化（declassification）とエンドースメント（endorsement。信頼の付与、または完全性レベルの引き上げ）、推論する一階の印の要約を扱う決定は戻さない。

README P3 は `Secret` の型を印なしで先に作らないという時期の決定であり、[未決表の IFC-D6](../decisions.md#情報フロー制御の設計者への問い)への回答ではない。案A・Cの型の実装は 0.0.14 に置く。案Bを選ぶ場合は、P3 が送った型の実装自体を不要にする変更も設計者の回答に含め、取りまとめが範囲へ反映する。どの案も本枝で型・構文・API・方針書式を実装または確定しない。

[IFC-D2](../if10.01/ifc-d2.md)・[IFC-D3](../if10.02/ifc-d3.md)・[IFC-D4](../if10.03/ifc-d4.md)・[IFC-D5](../if10.04/ifc-d5.md)の案A（D5だけは案B・候補(ii)）を仮の前提とする。設計者はどれもまだ選んでいない。各文書の IFC-D6 への申し送りに従い、方針と検査済み成果物の保護を起動側の前提にし、認定できる入力契約だけを精密化し、送信条件と応答の非機密化を分ける。許した要求由来以外の本文・宛先・捕捉・条件の依存を保持する。別案が選ばれたときの差は後掲の表に分ける。

D5案Bの固定originも案Aの単一候補として同じ印・観測の条件を用いる。以下のR全体への被覆の説明をこの意味で適用し、動的設定の受理は別案Aに限る。

[00-01「保証の範囲」](../../../design/00-overview/00-01-goals.md#保証の範囲)と[07-01「脅威モデル」](../../../design/07-quality/07-01-security-model.md#脅威モデル)に従い、LLM・スクリプト・外部入力は信頼しない。セキュリティ型システム（security type system）が検査するのは規則への適合であり、意図との一致、外部操作の成功、停止は保証しない。サーバ前の隔離はハーネスと OS に委ね、`Secret` を操作の許可を持つケーパビリティの値にしない。

## 推す案と二つの代案

案Aは「`Secret` と分類ごとの印を併用」、案Bは「`Secret` を設けず分類ごとの印で扱う」、案Cは「`Secret` の機密性を最も厳しい印に統一」とする。[元の問いD6](../study/questions.md#0013-の中で決めること設計の判断として文書にするもの)と [S6 の Q7](../study/information-flow-generality.md#設計者に決めてもらう問い)の三案を具体化した。案Bの元の表記は「廃止」だが、現行に実装済みの型があるという意味にはしない。

| 比較する点 | 案A: Secret と分類ごとの印を併用（推す） | 案B: Secret を設けず印で扱う | 案C: Secret の機密性を最も厳しい印に統一 |
|---|---|---|---|
| 型と印の分担 | `Secret` は不透明な包みと直接操作の制限、印は分類・由来と派生値・pc の追跡を担う。包みの中の分類を最上位へ潰さない | 通常の `String`・`Bytes` 等に分類の印を付ける。秘密専用の型による操作制限は設けず、通常の計算と出口を印の規則で検査する | 不透明な型の制限は案Aと同じ。包んだ値の機密性はすべて機密性の束の最上位とし、取り出した後もそれを保つ。完全性は別に保持する |
| 三つの操作 | 取得は入力契約から分類を得る。取り出しは表現を変えても印を保つ。非機密化だけが固定した許可の契約内で機密性を緩める | 取得から通常型の印付き値を得るため、包みから取り出す独立操作は不要。使用・変換で印を保つ義務と非機密化の境界は案Aと同じ | 取得時に最も厳しい機密性へ上げる。取り出しで下げず、用途を限る別契約だけが非機密化できる。元の分類に戻す一般操作を設けない |
| 直接の操作と表示 | `Secret` 自体の汎用表示・補間・等値・JSON 変換を認めず、専用の受け口か印を保つ取り出しへ誘導する。診断等の固定した伏字は、実値・長さ・存在・成否に依存しない場合だけ候補にする | 印付きの通常値の比較・文字列処理・JSON への変換を許し、結果にも依存を保つ。公開の出力や秘密依存の合否は拒否する。型による直接操作の制限や固有の伏字表示はない | 案Aと同じ型の制限。伏字からは、どの受け手に渡せるか判断できない。全分類を許す出口でなければ利用を拒否しうる |
| 0.0.14 で保証することの案 | 保護された同じ方針・入力契約と対応済み経路の下で、秘密の包みの直接操作と、取り出し後も含む禁止フロー・未承認の影響を静的に拒否する | 同じ前提の下で分類・派生値・pc による禁止フロー・未承認の影響を拒否する。印の規則を同じく閉じれば、包みがないことだけを理由に非干渉性の目標を弱めない | 同じ前提の下で最上位へ上げた保守的な禁止フローと未承認の影響を拒否する。分類別なら受理できる操作も断るが、その拒否を避けるため受け手を広く承認した扱いにはしない |
| 保証しないこと | 入力分類と信頼する契約の真実性、意図、外部操作の成功、停止、時間・資源の量による漏れ、受け手の再配布、検査外の迂回の隔離。伏字だけで派生値・合否を保護したとはしない | 案Aの共通の限界。通常型に印があっても、方針の誤分類や未対応の外部経路は補えない | 案Aの共通の限界。最上位にしても方針外の秘密を自動発見せず、実体へのアクセスを強制的に止めることにもならない |
| 完全性との関係 | 取得元の完全性を保持し、取り出しも非機密化も信頼を付与しない。必要な用途だけ別のエンドースメント契約へ渡す | 同じ。通常の文字列・真偽値として計算できても、信頼する操作を任意に決めてよいとはしない | 機密性を最上位にしても完全性を「信頼する」にしない。積全体を一つの印に潰す案ではない |
| 利用者への説明案 | 「この秘密は直接表示しない型で受け取り、文字列へ取り出した後も由来を追う。取得・取り出し・送信を許しても、公開する許可にはならない」 | 「秘密も通常の文字列等で処理できるが、由来の印を追い、許されない出力と分岐を断る。表示用の特別な秘密型は設けない」 | 「包んだ秘密はすべて最も厳しく扱う。サービス用トークンだけを許した相手への認証でも、そのままでは断る場合がある」 |
| 後の版への影響 | 分類別の専用受け口と通常値の処理を共通の印で接続できる。新しい表示経路・保存口・外部境界にも同じ義務が残る | 型の種類と取り出しAPIは増えない。後で包みを足すなら受け口・表示・診断の契約を見直す。印の付かない経路を残す理由にはしない | 精密化を追加する際に型・入口・要約・契約と受理表を見直す。分類別の認証を専用の特権で補うなら、その非機密化と信頼の契約の追加が要る |
| IFC-D2〜D5への依存 | D2の前提付き保証、D3の許した由来だけの緩和、D4の取得元の分類、D5の本文・宛先・pc と R 全体への被覆を用いる | 同じ義務。D4の入口から通常型へ印を直接与え、D3・D5の受け口を印の契約にする | 同じ義務だが、分類を失うとD3の由来の区別とD5の受理が難しくなる。D4の一般読み取りの厳しい印を取り出しで戻さない |
| IFC-D7〜D9への依存 | D7で三つの操作と秘密・受け手・用途を説明し、D8で受理例、D9で分類と固定契約の所有・版・承認を定める | D7で包みのない説明、D8で同じ禁止フロー、D9で同じ分類・契約の管理が必要。P3の型の実装の扱いを変更する | D7で正当な利用も拒否する理由を説明し、D8で認証・機密ファイル送信を再評価する。D9で全秘密の受け手の拡大を安易な回避にしない |
| 費用の見込みと根拠 | 案G全体はLean 154〜374時間・処理系等182〜420時間。内数に `Secret` の型・全表示経路・標準受け口の統合がLean 2〜6時間・処理系等8〜20時間ある。D6全体だけの切り分けは不明 | 型・専用受け口・取り出しの接続は省けるが、通常値の印・表示等の出口・二実行の証明は残る。既存の統合行を丸ごと引けず、削減幅と合計は不明 | 分類別の包みの処理は減りうるが、通常値の分類・pc・完全性は残る。拒否を許容する費用、専用契約を増やす費用、精密化のやり直しを含む増減と合計は不明 |

費用の出どころは [synthesis「大きさの見込み」](../study/synthesis.md#大きさの見込み)と [S6「規模の見積もり」](../study/information-flow-generality.md#規模の見積もり)である。未実装で確度の低い能動時間の見込みであり、実測でも本枝の文書作成の予算でもない。型の統合行は案G全体の内数であり、通常値・pc・非機密化の規則全体の費用ではない。サーバの保存と承認、OS の強制、一般の Task・Process・WASM 接続、長い検査・測定の実時間、独立レビューと設計者の回答待ちは含まない。小モデルの所要時間を理由に見込みを下げない。

## 案Aの役割の分担と三つの操作

`Secret` は秘密のデータを保持する不透明な型、印は値と計算の依存を表す情報として扱う案である。分類を型引数へ公開するか、文字列以外を包めるか、印をどこへ格納するかは0.0.14の設計に残す。以下の `String`・`Bytes` は取り出した後の通常型の説明であり、`Secret` の具体的な宣言を定めない。

| 操作 | 得るもの・保つもの | 得られない許可と残る義務 |
|---|---|---|
| 取得 | 解決済みの取得操作と方針の登録・入力契約から `Secret` と分類を得る。取得元の完全性、存在・成否・正常復帰の依存も別に扱う | 取得できることから送信・公開を許さない。未登録の項目を公開として取得せず、取得名が動的なら候補の分類を保守的に結ぶか拒否する。バックエンドと成否の契約が未対応なら、その入口は使えない |
| 印を保つ取り出し | 内容を `String`・`Bytes` 等の通常値として使えるようにし、元の機密性・完全性と取り出しに至るpcの依存を保持する | 表示・別の宛先への送信・用途への信頼は与えない。コピー・再包装・射影・JSON解析・符号化・長さの計算も依存を保つ。印を表す構文や取り出しAPI名は確定しない |
| 許可された非機密化 | 方針が同定する固定操作・変換の契約内で、許した要求由来の結果・成否・呼出条件だけについて機密性を緩める | 原値や同じ分類の他の値を一括で公開にせず、完全性も緩めない。他の捕捉・条件・本文の秘密を保持する。機密性を緩めること自体の承認と信頼条件が必要である |

案Bと比べて型を加える利点は、秘密の取得値を型で見分け、直接表示等への診断を入口で出せることと、通常型へ変える取り出しを明示できることである。情報フロー制御の保証を付けない通常実行にもこの型を提供するなら、型の直接操作の制限は残せる。一方、取り出した通常値の派生値や制御まで保護するのは印の規則の役割であり、型だけで同じ保証は得られない。

直接の等値を禁じるのは、比較結果一ビットも秘密に依存しうるため、通常型としての比較へ進む前に取り出しを明示させる設計の選択である。等値禁止自体が非干渉性に必須という主張ではない。印を保つ取り出し後の比較は可能であり、結果・pc・出口を検査する。代価は専用型・受け口・取り出し・表示と診断の保守であり、既存の統合見込みLean 2〜6時間・処理系等8〜20時間の内数に属する。案Bとの差分額は切り分けられていない。

元の調べが使う `Secret.Read`・`Secret.Reveal`・`reveal` は既存文書の候補名として読む。取得のエフェクト、取り出した表現、非機密化の権限を同じ名前で区別できると仮定しない。三つの意味の区別を先に選び、具体のAPIと要約の表示は後で設計する。

取得元を正しく分類する信頼条件は、印を保つ規則とは別に必要である。D4案Aの認定済み入力契約なら該当する分類を使い、認定不能の File の一般読み取りなら秘密の結びを使う。秘密を含む全文から都合のよい欄だけ取り出すことや、既存値を `Secret` で包むことは、その分類を精密に認定する操作にはならない。

許した受け手への送信は、非機密化せず秘密のまま行える候補である。D5案Aなら `pc ⊔ label(d) ⊔ label(v)` の許す受け手に R 全体を含める。さらに要求各欄の契約と完全性、操作の許可との区別が残る。送信後も元の値は同じ秘密であり、応答や成否の公開にはD3の別契約が要る。host/port の上限だけでHTTPS originへの限定を導かないという判断14も保つ。

## トークン・パスワード・秘密を含むファイルの例

以下は架空の入力・方針による設計条件であり、実行して再現した結果でも、構文・API名の決定でもない。機密性の分類を t（サービス用トークン）、p（ログイン用パスワード）、f（機密報告）とする有限集合の例を使う。これは内部の汎用の束を集合へ固定する判断ではない。「型、機密性／完全性」の順に記す。三入力はすべて未信頼の完全性を持つと仮定し、秘密の取得元であることだけを理由に信頼を付与しない。

受け手は、tだけを認証欄で受け取れるサービス、pだけを所定の認証欄で受け取れるログイン先、fだけを本文で受け取れる報告先に分かれるとする。宛先と呼出条件は公開かつ信頼するもの、受け口は未信頼の内容をデータとして許すものとする。通常のログ・診断・テスト報告はどの秘密も受け取れない。この前提を満たす契約と本番への接続後に初めて「受理候補」と呼ぶ。

案Cの最も厳しい印は機密性の束の最上位 `⊤C` であり、この例では `{t,p,f}` に当たる。対象範囲の `Top` とも、完全性を含む積全体の最上位とも区別する。その印の許す受け手は全分類の条件を同時に満たす必要があり、各秘密の受け手の和集合へ広げない。

| 入力・操作 | 案A: 併用 | 案B: 印だけ | 案C: 最も厳しい機密性 |
|---|---|---|---|
| 登録したトークンを、tだけの秘密だと認定した入口から取得 | `Secret`（内容はString相当）、`{t}／未信頼`。直接の表示・等値・JSON変換は不可。t用の認証受け口へ渡す候補 | `String`、`{t}／未信頼`。文字列操作・比較は可能、派生値にもtを保つ。公開表示は拒否し、t用の認証受け口は候補 | `Secret`、`⊤C／未信頼`。t用の受け口はp・fを許さないので拒否。型が認証用であることを理由に例外にしない |
| 登録したパスワードを、pだけの秘密だと認定した入口から取得 | `Secret`（内容はString相当）、`{p}／未信頼`。所定のログイン受け口へ渡す候補。直接の等値は不可 | `String`、`{p}／未信頼`。比較結果は `Bool`、`{p}／未信頼`となり、公開の合否報告は拒否 | `Secret`、`⊤C／未信頼`。p用の受け口も拒否。取り出した後の比較結果も最上位のまま |
| ファイル内容を、fだけを含むと認定した入力契約から取得 | 通常のFile入力なら `Bytes`（テキストなら `String`）、`{f}／未信頼`。専用の秘密取得口で包むなら `Secret` に同じ印を保つ。f用の本文送信は候補 | 同じ通常型、`{f}／未信頼`。包みは設けず、f用の本文送信は候補 | 通常のFile入力のままなら `{f}／未信頼` を保持するが、`Secret` で取得・包装する形は `⊤C／未信頼` となりf用の送信を拒否。包みの有無で受理差が生じる |
| 認定できない一般読み取りで、上記ファイルを取得 | `Bytes` 等、`{t,p,f}／未信頼`。包んでも取り出しても変わらず、fだけの報告先への送信を拒否 | 同じ通常型・印で拒否。パスや内容を人間が知っているだけでは精密化しない | 通常入力も保守的な結び。包装しても精度は回復せず、同じ送信を拒否 |
| トークンを取り出して文字列連結・符号化・JSONへの変換を行う | 取り出し後は `String` 等、少なくとも `{t}／未信頼`。変換結果の公開ログ・別の許可済みホストへの送信は拒否 | 取り出しを挟まず同じ計算ができるが、同じ印と拒否が残る | 包まれたトークン由来なら `String` 等、`⊤C／未信頼`。変換しても下がらず、さらに多くの出口を拒否 |
| パスワードを取り出して候補文字列と比較し、結果で表示・Assertの合否・終了状態を変える | `Bool` と分岐のpcにpの依存が残る。実値の表示を伏せても公開の観測は拒否 | 比較自体は通常操作だが、その結果とpcは同じくpに依存する。公開の観測は拒否 | 包み由来なら結果とpcは最上位。公開の観測は拒否 |
| 秘密を含むファイルから公開らしいタイトルや行数・長さだけを抽出 | `String`・`Int` 等、少なくとも取得時の機密性を保持する。fで得たならf、一般読み取りなら全分類の結び。公開表示は拒否 | 同じ通常型・印と拒否。JSONの解析成功や欄名から公開を導かない | 通常入力なら元の印、包みからなら最上位。いずれも抽出だけで公開にしない |

案Cは `Secret` を最上位へ上げる比較案であり、通常の値まで二点の分類に変える案ではない。通常のFile入力からの派生値やpcを追わなければ、包みを避けた読み取りが迂回になる。逆に、分類の精密な通常値へ取り出せる特別規則を加えると、分類を保持する案Aに近づく。最上位に潰した後で、型や受け口の名前だけから元の分類を復元する規則は使わない。

### 非機密化を使う例と使わない例

| 例 | 案A | 案B | 案C |
|---|---|---|---|
| t用の固定APIへ認証情報を送り、その値を保持する | 非機密化なしの受理候補。トークンと派生値はtのまま | 同じ候補。通常のStringでも受け口・用途の契約を満たす必要がある | 包み由来の最上位ではtだけの受け口に合わず拒否。受け手の和集合を許す補正はしない |
| その固定APIの応答から、D3案Aで承認した件数と粗い成否だけを報告する | 固定変換の結果と成否だけの非機密化の候補。結果の型はIntと所定の成否に相当し、機密性は承認範囲で公開、完全性は未信頼のまま。原トークンはtのまま | 同じ結果と保持条件。包みの廃止から自由な印の除去を導かない | まず送信の条件を満たせない。最上位からの専用の緩和を足すなら、由来と呼出条件の根拠を持つ別契約が必要であり、D3の契約をそのまま流用した扱いにしない |
| パスワードの比較結果一つを公開する | 取り出しだけでは拒否。この比較の値・成否・呼出条件・用途を別に承認した固定契約がなければ通さない | 同じ拒否。比較関数が純粋であることも公開の根拠にしない | 同じく拒否。全秘密の印を一括で下げて比較結果を出す一般操作は設けない |
| f用の固定APIへファイルを送った後、ローカルのログや応答も表示する | 送信は候補だが、公開は別契約なしでは拒否。原ファイル・トークン・未承認の応答欄は秘密に保つ | 同じ。送信を通常値の処理にしても結果の分類は残る | 通常入力を精密に保った場合でも公開には別契約が必要。包みで最上位にした場合は送信から拒否しうる |

件数と成否の非機密化は、外部APIと固定変換が承認した情報以外へ秘密を反映しないというD3の信頼条件を要する。実在のサービスの挙動は本枝では未確認である。トークンが承認した認証欄と未承認の要求本文の両方へ入った場合、分類tを一括で除くと本文の依存まで失う。同じ分類でも許した由来だけを緩め、区別できなければ秘密のまま保持するか拒否する。

## 伏字、エフェクトの除去、非干渉性の境界

固定した伏字の表示を認める場合も、秘密依存の値・構造・合否をまとめて公開にしない。例えばパスワードの比較結果で伏字を出すか否かを変えれば、本文を伏せても一ビットの違いが残る。診断・JSON・テスト失敗・Propertyの反例・機械向けの報告・終了状態も出口として扱う。[S5「テスト・ログ・失敗の保護」](../study/information-flow.md#テストログ失敗の保護)の条件を、表示実装だけで満たしたとしない。

エフェクトを処理して型から除くことは、引数・捕捉・節の結果・pcの依存を消す根拠にならない。公開ダミーだけを返す模擬の取得口と、本物の秘密を受け取って普通の文字列を返す節は別に判断する。公開ダミーを包む場合も、本物の入力分類の証拠を捏造せず、秘密を包み直す場合も元の依存を消さない。一般のハンドラと継続への具体的な規則と健全性は0.0.14へ残す。

また、実際の取り出しと非機密化の契約の使用を、人間への要約から消してよいとはしない。[S6 の Q7 後の注意](../study/information-flow-generality.md#設計者に決めてもらう問い)に従い、`main` から除去できるエフェクトの名前だけを承認の目印にしない。解決済みの取得・取り出し・固定変換と契約の同一性に結ぶ要約の設計をD7・D9へ渡す。要約を正しく作れることは、値の印を導入しただけでは証明できない。

[SD §2〜§4](../spikes/SD/findings.md#2-送信と観測の規則)は、同じ宛先値の所属、本文・宛先・pc、R全体への被覆、公開pcでのfail・非再開・失敗しうる宛先検査を小モデルで確かめた。`Secret` の取得・取り出し・非機密化、一般ハンドラ、実IOの成否、Task・解放との合成は確かめていない。機密性と完全性の積では、公開／未信頼の設定も拒否しうる十分条件を、取り出しの許可だけで緩めない。

[SH2「評価の一致と観察の制約」](../spikes/SH2/findings.md#評価の一致と観察の制約)は、純粋で全域的な応答関数の下での型・効果と値・Emit列の一致を示す独立モデルであり、情報フロー制御や非干渉性の証明ではない。[S3 §5](../study/usage-and-flow.md#5-情報フロー制御と-lio)と [S5 のハンドラの規則案](../study/information-flow.md#ハンドラワンショットの継続)も踏まえ、エフェクトの除去や純粋性と公開可能性を別に扱う。SD・SH2は再試作していない。

非干渉性の目標はD2・D3の案Aを引き継ぐ。同じコード・方針・契約と対応する公開入力・外部応答の下で、許さない秘密だけが異なり、許した非機密化の値・成否・呼出条件が対応する二実行がともに終了したとき、残りの公開観測が一致することを求める。観測には値・宛先・操作の有無と順序・公開の失敗・終了状態を含む。完全性は、信頼する入力等を固定し、未信頼の入力だけを変え、許したエンドースメントの事実・成否・呼出条件が対応する場合の、信頼する操作と結果の観測を別に扱う。この言明は設計条件であり、本枝で証明した結果ではない。

## 外部の方式から確認できる範囲

| 一次資料 | 確認した事実 | この判断案での使い道と限界 |

## 設計者への一つの問い

共通の前提は、分類の印で派生値とpcを追い、取得・表現の変更・非機密化を区別することである。

IFC-D6は、分類ごとの印に不透明なSecretの型を併用する案A、通常型と印だけにする案B、Secretの機密性を最上位へまとめる案Cのどれを選ぶか。

推すのは案Aである。理由: 案Bに対して、型による直接表示等の診断と、取り出しを明示する接点を増やせ、保証を付けない通常実行に型を提供する場合も直接操作の制限を保てる。代価は型・専用受け口・取り出し等の接続と保守であり、Lean 2〜6時間・処理系等8〜20時間という既存の内数のうち、案Bとの差分は不明である。受け手の分類別の区別と非干渉性は案Bでも目指せるため、案Aだけの利点には数えない。
