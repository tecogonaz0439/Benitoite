## 1. 守る対象と方針の最小案

### 1.1 攻撃と保証する命題

守る対象は、方針で秘密と指定した入口から得た内容と、それに依存する計算結果である。操作の許可とは別に、各秘密について、どの出口へ送ってよいかを検査する。例えば `service-token` を読め、`api.service.example` と `collector.example` の双方へ接続できても、同トークンの送信先は前者だけとする。秘密を別の文字列へ変換する、レコードへ入れる、秘密で分岐して定数を送る場合も対象にする。

最初の保証は、固定した方針・公開入力・外部環境の下で、ある受け手に許していない秘密の内容だけを変えた二実行が、ともに終了した場合、その受け手が観測できる結果と事象列が一致することである。事象には内容だけでなく、宛先、ファイル名、要求の有無と順序、公開する失敗の種類を含める。外部環境は、受け手に見えない秘密へ勝手に依存した公開応答を返さないという関係条件を要する。独立に選んだ任意の IO 応答二つを比較しても定理にはならない。

停止するか、何秒かかるか、メモリ・CPU・通信量の物理的な差からの漏れ、OS・外部サービス・ハーネスによる独立の読み取り、許した受け手からの再配布は対象外である。TINI の「ともに終了」は弱い条件であり、片方だけが終了する攻撃は排除しない。終了状態の番号や例外の文言を、単に「停止の問題」としてすべて除外する案は採らない。二つの終了実行の成功/失敗の違いは観測に入れ、秘密依存の `die`・Assert・未処理の失敗を検査する。

### 1.2 一つの方針へ追加する情報

次は ADR 0183 と docs/todo の TODO-141・149 に追加する**概念上の書式案**であり、既存 TOML の構文ではない。操作の allow/deny は既存の方針の部分に残す。

```text
secret service-token:
  sources:
    file: <user-config>/service/credentials
    environment: SERVICE_TOKEN
    keystore: service=service, account=upload
    prompt: service-login
  allow-disclosure:
    https: origin=https://api.service.example:443, channel=authorization-header

secret private-config:
  sources: file=<user-config>/private/**
  allow-disclosure: []

outputs:
  stdout, stderr, log, diagnostic, test-report, die: public
  file <project>/report/**: public
  file <user-config>/service/credentials: stores=[service-token]
```

方針の管理者が秘密の入口と開示先を決める。スクリプトには許可も印の方針も宣言させず、印を下げる関数を自由に作らせない。LLM が修正できるプロジェクトの設定で `service-token` を公開に変更できると保証の前提が失われる。信頼する実行側が方針を渡し、検査済みのプログラム・依存・方針の版を結び付ける。方針、ソースの分類、標準 API の契約が変わったら、キャッシュと検査結果を無効にする。

狭める実行方針は、操作の許可を減らし、開示先を減らし、入口の秘密の分類を増やせる。入口を公開へ変えること、秘密の分類を削除すること、開示先を追加することは、許可を広げる変更として扱う。重なる秘密の指定はすべて課す。`deny` は引き続き優先する。秘密をファイルへ保存して読み直すときも、その保存先は同じ分類を保つ必要があり、保存と再読を印の除去に使えないようにする。

| 入口・出口 | 最小の規則案 | 0.0.13 での実装範囲案 |
|---|---|---|
| クレデンシャルのファイル | 読み取りの全経路で方針の分類を得る。通常の `File.readText`・バイト列・リーダも迂回にしない | ファイルを秘密の入口として扱う静的契約を入れる。対象を絞れない読み取りは、ありうる秘密の分類の和へ上げる |
| キーストア、`Secret.prompt` | 方針の項目の識別名から印を得る。値・実際の長さは診断へ出さない | IFC の契約を先に定める。OS ごとのバックエンドと承認画面の全実装を前提にしない。存在しない API は使えず、汎用コマンドによる代用も保護対象のプログラムでは拒否する |
| 環境変数、引数、標準入力 | 指定した名前や入力口を秘密にする。子プロセスへの暗黙の環境継承も入口・出口として扱う | 環境変数の直接の読み取りを対象にする。入力名が未知なら分類の和。未分類の入力の扱いは方針の信頼条件として明記する |

| ファイルへの出力 | 名前・作成の有無・書く内容・flush を検査。秘密用の保存先には分類を保持 | 公開の報告は既存 API に静的検査を追加。秘密用の可変な保存先は、再読の対応を閉じるまで拒否できる範囲にする |

| stdout・stderr・ログ・診断・Assert・Property・`die` | 本文・付加情報・失敗した事実・反例・スタックの位置を出口として検査 | 公開を既定にする。秘密の値だけ伏せても判定結果が漏れる場合は静的に拒否する |

方針にない秘密を内容から自動発見する保証はない。TODO-138 のハーネスの `read_file` は処理系を通らない別の入口であり、本案で制御できない。ハーネス側の除外と方針の意味を揃える必要がある。TODO-120 の書き込み範囲は保存する場所を制限する規則であり、その場所へ保存してよい情報の分類とは別である。

静的方式のファイルの分類には保守的な退避が要る。パスの字面が公開用のディレクトリの下でも、リンクや別名で秘密のファイルを読めるなら、その字面だけで公開と判定しない。最初は一般のファイル読み取りを、方針が管理するファイルの秘密の分類すべてへ依存すると近似できる。これでは複数の秘密のうち一つを正しい認証先へ送る例も拒否しうる。分類を一つに絞る専用の取得口を信頼するか、実対象の分類を保持する実行時の入口を加えるかは別の判断である。実パスの同一性が未確認のまま、案4の字面の包含でこの制約を外さない。

### 1.3 印の束と宛先のパターン

二点の束 `Public ⊑ Secret` は SF の最初の定理と表示防止には適する。しかし秘密を送れる受け手を二つ以上区別するには、出口ごとの特権的な開示規則が別に要る。その規則を隠したまま「二点だから簡単」とは数えない。

最小の本番案は、固定した有限集合 `S`（秘密の分類の識別子）に対して `Label = P(S)` とする。公開は空集合、結び `l₁ ⊔ l₂` は和集合、順序は包含、未知は `S` 全体である。秘密を混ぜるほど制約が増える。各出口 `d` で許す分類を `Accept(d)` とし、送信の条件を次とする。

```text
label(payload) ∪ pc ∪ label(target) ⊆ Accept(d)
```

専用の秘密の取得口へ渡す項目名が方針に存在しない場合は拒否する。分類の集合が空のときに未知も空集合となり、未知の秘密を公開と判定する規則は設けない。一般の入力のどれを秘密と指定したかという方針の網羅性と、指定した秘密の依存を検査が失わないことは、別の条件である。

最初の HTTP の契約は `label(target) = Public` も要求する。送信先の選択自体を秘密の出口へ認める一般化はしない。値を送った後も印は残る。`Secret.reveal` も表現を `String` に変えるだけで、依存の集合を消さない。認証の送信を許したことから、その値のログや後の別の送信が許されることはない。

受け手の集合を直接印にする別案では、公開は全受け手、順序は逆包含、混合は共通部分になる。`{A,B}` と `{B,C}` の秘密を混ぜた結果の送信先は `{B}` であり、和集合ではない。両案の意味は対応するが、有限の分類を持つ案なら、由来の説明を保ち、束の計算を有限の集合演算に閉じられるので推す。

案4のホストの完全一致・一段・多段のパターンは、`allow-disclosure` の照合に再利用できる。パターンをそのまま値の印にする案は推さない。混合に共通部分が要り、複数パターンの和・否定・公開の全受け手・HTTP 以外の出口も扱う必要がある。SA が証明した一原子ずつの被覆は、この束の閉包と等号の証明ではない。パターンの構造の等号と意味上の包含を分ける SA の扱い1は保てるが、情報流の新しい代数は別に証明する。

秘密の認証は最初は完全一致の origin を推す。ホストのパターンだけでは scheme・port・送る欄を指定できず、許したサイトに攻撃者の投稿領域がある場合も識別できない。自動リダイレクトは秘密付き要求では使わず、3xx を結果として返す限定 API とする案が小さい。追従を許すなら、各要求の送信前に新しい origin と全秘密欄を再照合する規則・実装が要る。最初の宛先の照合だけでは足りない。

## 2. 静的推論（FlowCaml 型）の評価

### 1. 何を表せるか

F は、利用者が指定した束と方針に対する全型推論、P は参照・例外・let 多相を持つ逐次 ML の制約推論を示す。これを Benitoite の推論器を流用する証拠とはしない。本案では既存の型推論の後へ追加の情報流判断を置き、型の情報を付けた表層の構文と解決済みの名前から、値・pc・正常/異常の継続・出口の制約を推論する。局所変数とラムダへ印の構文を要求しない。

関数の要約は、引数・捕捉値の印から結果と正常/異常経路の印を求め、呼出時の pc で許される出口を制約する。単に「結果は全引数の和」とするだけでは、公開を表示するコールバックを秘密の分岐内で呼ぶ場合を見落とす。再帰する呼び出しは有限分類上の単調な制約として反復する。高階関数は結果の依存だけでなく、渡した関数の出口の条件も保持する。計算量や解析の予算を超えた場合は印を未知へ上げるか検査不能として拒否し、公開へ戻さない。

診断の案は「`service-token` の入口 → 結合した式/分岐 → `collector.example` への送信」を位置で示し、「この秘密に許される宛先」と「今回の宛先」を並べる。実値、長さ、秘密の比較結果を出さない。記号的な制約式だけを利用者へ表示しない。

### 2. 権限制御での使い道

TODO-283 の「値の流れ」を実行前に制限する。操作の種類と対象の許可、回数、許可を持つ者、狭める動的範囲は別である。案4なしでも、固定した認証先の標準 API と方針の分類で、この制限を始められる。スクリプトが宣言した送信先の注釈を許可にはしない。

ADR 0183 の実行前の段は、今のエフェクト照合に情報流の制約の検査を追加する。サーバモードの後は動的な実対象の照合と OS の隔離を同じ方針から導く。サーバモードの前に新しい操作の許可判定器を単独で出す案ではない。方針で分類した入力について静的な情報流を検査し、その前提と限界を追加する案である。この位置付けも設計者に確認する（末尾 Q2）。

### 3. 実用の機能での使い道

公開用の報告へ秘密の欄を紛れ込ませる修正と、テスト・ログの漏れを実行前に指摘できる。現在の一階のハンドラは模擬入力を渡せ、`@opaque` は構成子を隠せるが、普通の文字列に変換した後の依存や、分岐による漏れを追わない。`with`・Task・区間解析もその代わりにはならない。具体例は第5節に示す。

探索・バックトラック・構文解析の制御、生成器、破壊的な配列更新、解放の確実性は増えない。性能上は値の実行時表現を保てる利点がある一方、検査時間と要約の保持量が増える。速くなるという測定の根拠はない。

### 4. 今の設計との両立

効果の集合と印の判断を分け、ハンドラで効果を除いても引数・節の pc・継続の依存を残す。ワンショット、深い再開、節の外側での実行、`State` とエフェクト変数の処理禁止は保つ。詳細な規則案と拒否する境界は第6節にまとめる。

### 5. 設計原則との関係

実行前の拒否は原則1、由来と出口を示す診断は原則4に合う。印を利用者へ書かせず標準 API と推論に集めれば、原則3・5・6の負担を抑えられる。ただし公開関数の依存契約と方針の変更の確認は必要である。依存のパッケージを含めて要約を再検査し、作者の宣言をそのまま信頼しない。

LLM の生成・修正の成功率は未測定である。注釈をなくしただけで成功率が上がるとは断定できない。最初は未知の流れの拒否理由を「取得元を一つに絞れない」「この関数の呼出時の pc が秘密」等へ分け、方針を広げることを既定の修正案にしない。

### 6. 形式化の費用

第7節の八群が必要で、TODO-250 の重い項目である。既存 Release の型を直接増やさず、追加の判断・印付き意味論・消去と持ち上げを別モジュールへ置く案なら、四つの主定理の言明と前提の意味を保てる見込みがある。これは新しい非干渉の定理が軽いという意味ではない。

有限の分類なら一般の型の等号の計算は避けられる。効果へ印を入れず、許された送信でも印を除かない設計なら、0.0.8 の三種類をすべて同時に増やす必要もない。新しい情報流の型付けの置換・継続の保存・二実行の証明は、それでも残る。

### 7. 互換性と構成

新しい印の構文は要らないが、秘密の入口と公開の出口をつなぐ既存のコードは拒否されうる。保護の方針があるプログラムでの Task・Process・WASM 等の拒否も互換性の変更である。公開だけのコードと、分類していない値の通常の型の意味は保つ。検査を任意の警告に落として同じ保証を宣言する互換案は採らない。

中核の分類と制約は小さな自作の有限集合で扱い、OS のキーストア・ネットワーク・Wasmtime を検査器に直接依存させない。構成でモジュールを外しても情報流の規則は同じで、未提供 API を検査時に拒否する。分類数を64個に固定した一機械語の実装は必須にせず、番号の上限と変換を検査する。

### 8. 学習の価値

既存の型の安全性と、二実行の観測を比べる性質の違いを、型推論・pc・開示の方針・消去の各部分で学べる。一般のコエフェクト構文を同時に足さずに、TODO-269 の目的である値の流れを追う規則を読むことができる。

## 3. 実行時の印（LIO 型）の評価

### 1. 何を表せるか

L の方式は、通常値のすべてに印を付けて各演算で伝播させる方式とは違う。Labeled に包んだ値を読むと実行中の現在の印が上がり、その印と出力先を照合する。clearance は印の上限、toLabeled は指定した上限の下で計算し結果を包む仕組みである。2011年の証明は逐次のモデルである。

Benitoite 向けには二つを区別する。(b1) LIO に近く、秘密を開くと現在の印を単調に上げる。(b2) 通常の値にも印を付け、演算・分岐・保存先へ伝播する。b1 は公開値まで以後の出力を制限しやすく、b2 は実行しなかった腕と可変セルを含む pc の規則が難しい。単純な値の汚染追跡だけを LIO の非干渉と呼ばない。

### 2. 権限制御での使い道

実行時に読んだ取得元・実際の宛先と方針を比べられるため、静的に対象を一つに絞れない場合を受理しやすい。照合は外部への要求を作る前に行い、実行中の拒否そのものにも現在の印を付ける。低い印へ戻してエラーを表示することはできない。

操作の権限の最終判定と、情報の流れの最終判定は別の条件である。どちらかを利用者のハンドラへ委ねて迂回できる形にはしない。サーバモード前の実行時強制に当たるかという既存方針との調整も必要であり、静的案より先行実装しやすいとは決められない。

### 3. 実用の機能での使い道

動的に選んだ秘密を必要なときだけ開き、適合する出口へ送るスクリプトを、全経路の静的な拒否より柔軟に動かせる。一方、認証情報を開いた後に無関係な公開集計を表示するだけでも、b1 は拒否しやすい。結果を包んで現在の印を戻す境界を導入すると、書き手が計算を分ける負担と、正常/異常の復帰の規則が増える。

### 4. 今の設計との両立

b1 では `Secret` 相当の包みとリソース・セルの印を持ち、現在の印を `RunState`、捕まえた継続、タスク、解放の枠へ引き継ぐ。すべての即値の表現変更は必須でない。b2 では通常レジスタ、`Slot`、閉包の環境、コレクションの辺、Host に保持する値と Rust 所有の IO 引数まで整合させる必要がある。`ObjHeader` の GC の印を秘密度に流用できない。

例えば値と分類番号を別の構造体にすれば現行の16バイトの保証を再検討する。実際に何バイトになるかはレイアウトを測るまで不明である。レジスタに平行した印の配列なら値の16バイトは保てても、全コピーと区画移動に同期が要る。ヒープ対象一個の可変な印は共有する公開の別名まで秘密にするか、印を消してしまう問題を起こすため、それだけでは十分でない。永続構造の共有も含めて設計する。

### 5. 設計原則との関係

標準の入口で自動的に包めば、局所の注釈は省ける。ただし実行して初めて拒否するので原則1の優先に劣る。失敗を直すには入力の由来と現在の印が上がった位置の履歴が必要で、秘密の実値を履歴へ残さない。LIO の上限や計算境界を LLM に書かせる範囲の成功率は未測定である。

### 6. 形式化の費用

Release を変更しない独立した監視機械は作れる。しかし拒否して止まる遷移は通常の Release の遷移ではなく、既存の進行の定理をそのまま監視機械の進行に使えない。通常の一歩へ消去できる場合と、情報流違反で安全に拒否する場合を分け、後者から低い出口へ漏れないこと、すべての実行経路が監視されることを証明する。

必要なのは「許可した出口でしか印付きの値を書かない」という一実行の補題だけではない。現在の印を上げる規則、低いストアの不変性、例外・復帰・toLabeled の条件、二実行の消去後の観測の一致が要る。四つの既存の主定理を保てても、これらは重い新規定理になる。

### 7. 互換性と構成

表面の型を保てる場合も、現在成功する実行を途中で拒否する。実行の前に終わったファイル書き込みや HTTP の要求は戻らない。b2 は VM・ヒープ・安全点・Host の保持を変える広い実装となる。GC の検証と特殊構成の点検が必要で、32ビットでも印を表現できる番号と上限を用意する。

### 8. 学習の価値

動的 IFC、消去による証明、現在の印と上限の違い、例外と可変状態の関係を学べる。静的推論器より小さな最初の例は作れるが、Benitoite の全 VM の監視へ広げる費用とは分けて評価する。

## 4. 静的・動的の混合の評価

### 1. 何を表せるか

(c) の候補は、秘密の入口から得た値の印を動的に持ち、静的解析が分岐・呼び出し・復帰の pc と保存先への制約を与える形である。実際に読んだ秘密の分類を使える一方、実行しなかった腕の代入による漏れも静的に扱える。ただし「秘密の値だけ動的、ほかは今までどおり」では、秘密で選んだ公開定数が印を持たず漏れる。

### 2. 権限制御での使い道

固定した送信先は静的に拒否し、動的な対象は実際の値で照合する分担が可能である。同じ分類・方針・出口の意味を両方に使い、静的に通ったため動的な照合を省く箇所は、その一致を証明する必要がある。操作の許可と OS の隔離の必要は変わらない。

### 3. 実用の機能での使い道

同じ関数が公開と秘密の双方の値を扱うスクリプトで、静的に全体を秘密とする拒否を減らせる可能性がある。公開用の報告、ログの定型文と秘密の欄の分離にも利点がある。ただし実際にどれだけ拒否が減るかは未測定で、アルゴリズムや生成器の機能が増えるものでもない。

### 4. 今の設計との両立

秘密の動的な印と、コンパイラが出す pc の情報をレジスタ・ハンドラ・再開・解放の同じ場所に対応させる。最適化が分岐を消したり式を前へ移したりしても、両方の情報の対応を保たなければならない。名前の解決と型の検査だけを接続すれば済む方式ではない。

### 5. 設計原則との関係

既知の誤りを静的に報告し、未知を動的に判定する分担は原則1に合う。局所の印を推論できるが、「検査時に拒否する場合」「同じコードが実行時に拒否される場合」の説明を要する。静的と動的で同じ違反に違う理由を出さない診断の設計が必要である。

### 6. 形式化の費用

静的解析の健全性、動的な印の監視の健全性、その対応の三つが必要になる。静的案と動的案の安いところだけを足した費用にはならない。印の具体値を実行時まで残し、pc だけを抽象化する関係と、消去・持ち上げの定理を新設する。最初の重い項目としては静的限定案より不確実性が大きい。

### 7. 互換性と構成

静的拒否と動的拒否の双方があり、移行の説明も両方を要する。動的の取得口だけを OS ごとの機能へ分けることはできるが、情報流の意味は全構成で同じにする。実行時の印を省く構成を作り、同じソースの保証だけを変える案は採らない。

### 8. 学習の価値

抽象解釈と実行時監視の対応を学べる。ただし最初から混合を選ぶと、流れの規則の問題と静動の接続の問題を同時に切り分ける必要がある。静的限定案の拒否例が実用上の障害になるという証拠を得てから選ぶ方が判断しやすい。

### 漏れの種類と三方式の比較

| 漏れ・機能 | (a) 静的推論 | (b) 実行時の印 | (c) 混合 |
|---|---|---|---|
| 秘密をそのまま文字列・ヘッダ・ファイルへ渡す | 出口の制約で事前に拒否 | 送信前に印と出口を比較 | 既知は事前、未知は実行時に拒否 |

## 5. 利用者に見える機能と `.bnt` の例

すべて未実装 API を含む擬似コードであり、現在の構文に寄せた案である。印の構文や許可の宣言をスクリプトへ追加する例ではない。

### 認証先と別の許可済みホストの区別

```bnt
// 案: 方針の service-token を受け取る。取得元と宛先は実行側の方針が決める。
bind token <- try Secret.fromEnvironment(name: "SERVICE_TOKEN") or return
bind response <- ServiceApi.upload(token: token, body: publicReport)

// 案: collector.example への接続自体は許されていても、token は送れない。
Http.send(Request.post(url: "https://collector.example/collect", body: Secret.reveal(token)))
```

`ServiceApi.upload` は信頼する固定 origin の認証用の標準 API という案である。同名の利用者の関数を作っても信頼する契約を得られない。実装を検査した普通のライブラリとして公開する場合は、その本体も情報流の判断を通す。応答は認証情報に依存しうるので、許された送信の後でも公開へ自動的に落とさない。

取得の Result の形も契約に含める。例えば環境変数の存在が公開のメタデータで、二実行で異なるのが内容だけなら、最初の `or return` の分岐は内容への依存を要しない。存在の有無も秘密とする方針なら、その分岐の正常/異常の継続にも印を付け、公開の終了報告へつながる使用を拒否する。認証への応答の成功/失敗はトークンの内容に依存しうるので、取得の存在の扱いから公開へ戻さない。

現行の `Secret` の計画なら専用の受け取り口への送信は可能である。本案が追加するのは、同じ秘密を別の許可済みホストへ送ることの拒否と、reveal 後も依存を保つことである。案4だけではこの違いは表せない。

### 設定を含むレコードから公開の報告を作る

```bnt
// 案: レコードの形は公開。title と count は公開、token の中身は秘密。
bind settings <- { title: "日次処理", count: publicCount, token: token }
bind report <- { title: settings.title, count: settings.count }
Console.writeLine(Json.encode(report))              // 案: 許す
Console.writeLine(Json.encode(settings))            // 案: Secret の変換禁止または情報流違反

if Secret.reveal(settings.token) = "guess" then
  Console.writeLine("一致")                         // 案: pc が秘密なので拒否
end if
```

レコードの各欄の印と、形・構成子の選択の印を分ける案である。秘密で選んだレコードから公開値に見える欄を射影する場合は、形の印も射影へ加える。最小実装で全レコードを一つの印へまとめるなら最初の `report` の例も拒否される。その場合、この実用の機能を達成済みとしない。0.0.13 の最小範囲には、静的に形の分かる不変レコードの欄の区別まで含める案を推す。未知の再帰的な構造と可変セルは全体の印へ保守的にまとめるか拒否する。

秘密のファイルを丸ごと JSON として読み、`token` 以外の欄だけを取り出しても、その欄を自動的に公開とはしない。公開の欄を信頼するスキーマで別に取得するか、許す開示を方針で別に決める必要がある。上の例は、公開入力と秘密入力から形の分かるレコードを組み立てた場合に限る。

### テスト・ログ・失敗の保護

```bnt
// 案: 模擬の取得口から公開のダミー値を入れ、認証の組み立てを試験する。
bind dummy <- Secret.fromString("dummy-for-test")
bind request <- buildRequest(token: dummy, body: publicReport)
Assert.equal(actual: request.publicPath, expected: "/reports")

// 案: 本物の秘密から決まる比較の合否は、値を伏せても公開できない。
Assert.equal(actual: Secret.reveal(token), expected: "guess") // 拒否
Log.info(message: "token=" + Secret.reveal(token))            // 拒否
die(Secret.reveal(token))                                    // 拒否
```

`Secret.fromString` は表示を制限する包みを作るが、入力が公開のダミーなら、本物の取得元の機密度を捏造することはない。逆に秘密を包み直しても由来は消えない。現在のハンドラでもダミー値と記録を使うテストは書ける。本案の差は、本物を使うテストが秘密の比較の結果や Property の縮小した反例を報告することを、表示の実装とは独立に拒否できる点である。実行器が全失敗値を `<secret>` に変えるだけでは、合否の一ビットは保護できない。

## 6. 現在の仕組みとの接続の規則案

### ハンドラ・ワンショットの継続

現在の効果の除去の式は保つ。追加する情報流判断では、操作が呼ばれた条件、実引数、節を閉じ込めた環境、継続が持つ依存を保持する。概念上は、節の入口の pc を `呼出側 pc ⊔ 操作の発生の印 ⊔ 節の選択の印` とする。各実引数の印は引数に残し、それを使って分岐・出力するときに加える。最初は全実引数の印を節の pc へも加える保守的な規則を選べる。

`resume(v)` は、捕まえた pc、節の pc、再開する値の印を結合した条件で続きを実行する。深いハンドラの再設置で印を初期化しない。節が外側で走ることは、秘密度を外側の低い値へ戻す根拠にならない。再開せず継続を捨てる選択は、`handle` の正常/異常の出口の印へ加える。継続を捨てるときの解放にも同じ条件を渡す。

根拠となる現行の遷移は `Release/Semantics.lean:275–309` の `E_Op`・`E_OpFail`・`E_OpPrim`・`E_Resume`・`E_DropRel` である。`vm/handler.rs` の `Captured(Vec<Segment>)` と `Used` の区別を保ち、情報流の追跡を継続の多重化へ使わない。二度目の再開の失敗にも公開の報告の規則を課す。

模擬の `Secret.Read` が公開のダミー値を返す場合は、実物の秘密を読んでいないという本体の検査から公開を導ける。一方、本物を読んだ節が定数を返しても、その読み取りを理由にすべてを公開へ落とす一般の規則は設けない。`Secret.Reveal` の効果が処理されても、引数の秘密の印は除けない。信頼する取得口の名前の文字列で契約を選ばず、解決済みの組み込みの識別子と実際に呼ぶ経路を照合する。

エフェクト変数と `State` を処理できない規則、操作の宣言の一階の制限は保つ。値と関数の依存の多相は追加の判断に置き、エフェクト変数を印の変数と同一視しない。ADR 0147 の「スクリプトは権限を宣言しない」と ADR 0117 の「権限の値を設けない」も保てる。`Secret` は秘密のデータの包みであり、操作を許す権限の値ではない。

### 正常・異常の制御と `die`

`if`・match の選択・guard・短絡の実行条件の印を、該当する腕の pc へ加える。`try ... or return`、Fail の節、途中の return では、後続へ進んだ事実も秘密へ依存しうるため、正常と異常の継続の印を分ける。両腕で同じ公開定数を返す場合に pc を下げる最適化は、最初の版では要求しない。

秘密依存の算術エラー・範囲外・未処理の失敗も出口になる。最小案では、秘密を引数にとる部分的な組み込みは Result へ閉じる契約を持つものだけ認めるか、その使用を拒否する。値を出さずにスタックや成功/失敗だけ出す例外を作らない。時刻やメモリ不足を保証から外す範囲と、通常の言語の失敗の報告の範囲を区別する。

### タスク・共有可変セル・Lazy

一般化する場合、子の初期 pc は親の生成位置の pc と捕捉した秘密を含む。結果と失敗、await から戻る条件、取消しの有無、共有セルへの書き込みにも印が要る。引き継いだハンドラの節を子で実行する場合も、子の pc を使い、末尾再開の制限は保つ。Task の引き継ぎの現行の保証だけで情報流が保存されるとはしない。

共有セルの初期の案は、保存内容の印を固定し、`pc ⊔ label(value) ⊑ label(cell)` のときだけ書く規則である。読むとセルの印を結果へ加える。可変な印を上げる方式は、低い別名と実行しなかった代入の扱いが増える。Lazy も、メモ化の状態・失敗・待機による観測を含める必要がある。

0.0.13 の限定案は、秘密の取得口が到達可能なプログラムで、利用者の Task・Reference・Lazy と汎用外部呼び出しを拒否する。単に秘密の値を引数に渡すところだけの拒否では足りない。公開のタスクが秘密の計算の終了を待つ、共有状態を観測する、外部コマンドが自分で秘密を読む経路が残るためである。関数の別名・高階の受け渡し・依存パッケージを含めた到達可能性と境界の制約で拒否し、解析不能なら受理しない。公開だけの既存プログラムの機能を一律に削除する案ではない。

### `with` と解放

情報流の照合を通常の IO 操作だけに置かない。バッファへデータを受け入れる時点で、そのリソースの保存先に対する分類を検査する。解放時の flush は、受け入れ済みのデータの分類と、解放を起こす制御の印を保つ。途中で拒否したからといって解放を飛ばす案は、現在の保証に反する。

静的限定案では、公開の制御で取得したリソースと、秘密から独立した正常/異常の解放経路を先に許す。秘密の分岐で公開の writer を開く、秘密で非再開を選び公開の flush の有無を変える場合を拒否する。秘密のバッファを持つ writer の一般の持ち出しは、保存先の分類と後の再読まで閉じるまでは拒否する。内部の fd の close 自体と、その結果を公開ログへ書くことは別の契約にする。

対応先は `Release/Semantics.lean:235–271,299–324` の use・解放・error/exit/drop と、`ContTy.K_Release`・`K_Drop` である。`State` の効果を変えなくても、追加の情報流判断ではこれらを場合分けする必要がある。

### WASM と外部コマンド

取り込みなしの WASM が外部に作用しないことと、結果が公開であることは異なる。一般化するなら、入力・選択した関数・呼出時 pc と、コンポーネントの保持する状態の印を、結果・失敗・外部型の資源へ加える。同じインスタンスを次の公開の呼び出しが使う場合も情報が残る。外部型を含まない純粋の宣言でも、共有するゲストの状態の非依存を未確認のまま公開の結果としない。

最小案は保護対象のプログラムで WASM を拒否する。将来ホストの操作を与えるときは、TODO-048・213 の一か所の入口へ情報流も接続し、ハンドラで除ける効果と秘密への依存を別に扱う。現在まだ入れていない「外部の関数の効果を除けない」という将来の制限を、現行実装の規則と書き違えない。

外部コマンドは、公開の引数しか渡さなくてもクレデンシャルを自分で読める。最初は秘密を扱うプログラムから拒否する。後に許すなら、コマンドを信頼する専用アダプタ、読む入力と出す先の契約、秘密を渡す標準入力/環境、子からの出力の分類、OS の隔離を一組で設計する。OS の接続先制限だけから秘密の宛先の制限を導かない。

この制限は言語の Task・利用者が呼べる外部処理への制限であり、標準の HTTP 実装の Rust のワーカまで禁止するものではない。標準の実装の内部は、入力を外へ渡す前の照合、応答の分類、公開の診断へ秘密を混ぜないことを信頼する境界に置く。標準ライブラリの内部で使う状態を、利用者の共有セルを素通しにする理由にはしない。

### 7.2 主定理を保つ形と、追加の保証

提案する証明の順は次である。

1. 追加判断に通る表層から、既存の表層の型付けと、追加のコアの情報流判断を得る。未知の構文・境界を受理しないことも示す。
2. 印付きの意味論を既存の Release の項と状態に対応させる。印を消した一歩が既存の一歩になることだけでなく、**受理したプログラムの既存の任意の一歩を、印付きの一歩へ持ち上げられること**を示す。前者だけでは、漏れる一歩を印付きモデルから削った証明になりうる。
3. 追加判断・印付きストア・pc が遷移で保たれ、低い観測のない高い計算が低いストアを変えないことを示す。解放・失敗・非再開も含める。
4. 観測者に許さない秘密を消去した二状態の関係から、ともに終了する二実行の観測が等しいという TINI を得る。
5. 標準の入口・出口・失敗報告の具体的な契約と、処理系の書き出し・検査の接続を確かめる。小モデルだけの定理を実 CLI の保証へ読み替えない。

既存の `Release.progress`・`preservation`・`effect_soundness`・`Surface.desugar_typed` は、普通の型と既存の実行についての言明として残せる見込みである。追加の判断を通らないプログラムにまで、情報流の定理を主張しない。情報流の受理範囲の前提を新定理へ明記し、主定理の引数名を残しただけで前提が不変だったとは数えない。

組み込みの型保存は情報流の関係条件を含まない。新たに、公開の入力が同じなら公開の結果・失敗・事象も同じであること、秘密の取得の応答が方針どおり分類されること、秘密の要求を承認された origin にだけ送ること等を要求する。これらを定理の明示的な引数と信頼する実装の契約として区別する。非干渉そのものを公理にして未証明部分を埋めない。実物の OS・HTTP を Lean で証明するわけではないことも保証へ書く。

### 7.3 実行時方式を保証と呼ぶ条件

監視機械を別にすれば、既存 Release のファイルを変更せずに済む場合はある。その場合でも、(1) 秘密の読み取りと全出口が監視を通ること、(2) 印・pc・ストア・継続の更新が正しいこと、(3) 拒否と復帰で低い観測を変えないこと、(4) 二実行の低い観測が一致すること、(5) 実 VM がその機械を実装しているという接続が必要である。単一の送信関数の「印が含まれるなら拒否する」補題だけでは情報流の保証にならない。

特に動的 pc を if の末尾で無条件に戻す方式、toLabeled 相当から失敗だけを公開で返す方式、ハンドラの外側で現在の印を初期化する方式は採らない。L の仕組みをそのまま実装したと主張するには、その上限・包み・ストアと復帰の条件も必要である。Release を変えないことと、TODO-250 の軽い項目であることは別である。

## 10. 統合の担当への申し送り

- **推す案**: (i)。情報流を 0.0.13 の中心とし、有限の秘密の分類・静的推論・固定した認証先・逐次・標準の入口/出口へ限る。案4の Release の改造は別の版へ回す。方針の内部のホストの照合は再利用してよい。
- **推す案**: `Secret` の表示/等値なしと情報流の印を併用する。reveal は印を保ち、許された送信はその一回の出口での受理とする。任意のラベル除去・一般の declassification は初段に入れない。
- **推す案**: 未対応の Task・共有セル・Lazy・WASM・外部コマンドを、秘密を扱うプログラムから静的に拒否する。公開だけの別のプログラムで既存の機能を使えることと、秘密と組み合わせる保証を区別する。
- **推さない案**: (ii) の完全な動的 IFC を、Release を変えないという理由だけで軽い相乗りにすること。(iii) を共通のパターンがあるという理由だけで重い項目一つに数えること。
- **推さない案**: 二点の印だけで宛先別の許可が得られるとすること。公開/秘密の値の印だけで pc を省くこと。Secret の伏字だけで Assert の合否、die の終了状態、非再開や flush の有無まで保護したとすること。
- **判断に要る未確認の事実**: 高階の要約と失敗の pc の推論の実際の受理率・検査時間。秘密のファイルを字面でなく実対象から一つに分類する接点。標準の入口/出口の全棚卸し。印を伏せた診断で LLM が意図どおり修正できる率。どれも本調査で実測していない。
- **SF との接続**: SF の定理の印、観測、停止の条件、IO 応答の仮定を第7節の八群へ対応付ける。単純な if の非干渉の成功から、ハンドラ・解放・実 VM への持ち上げの成功を推定しない。
- **S1 との重複**: 節の外側、再開と非再開、解放、Task の引き継ぎ。新しい高階エフェクトは前提にしない。権限を狭める高階の境界を秘密度を下げる境界にしない。
- **S2 との重複**: ホスト/パスのパターン、対象の同一性、検査済みの値と本物の IO、SA の等号/包含の分離。CheckedHost の成功は秘密の送信の許可ではない。
- **S3・S4 の更新点**: TODO-269 を後へ保つ判断の部分は今回の設計者の前倒し決定に従って再統合する。S4 の Secret と Scope と小モデルの相乗りを自動的に全部維持しない。情報流を中心にする場合、Scope の精密化と Secret の別実装で Lean の前半が増えないよう、同じ分類・契約へまとめて再計画する。
- **互換性の受け入れ**: 保守的なファイルの分類、秘密を扱うプログラムの Task/Process 等の拒否、秘密の応答を公開の成功表示に変えられない場合を、実際の自動化の例で設計者に示す。この制約を受け入れられなければ (iv) を選び、サーバモードより前の情報流の独立改造を具体化する。
