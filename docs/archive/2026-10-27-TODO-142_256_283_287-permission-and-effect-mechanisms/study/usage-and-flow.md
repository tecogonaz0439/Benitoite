## 判断の案

使用回数の制限、別名参照の制限、情報の流れの制限は、それぞれ異なる保証である。線形型で値を一度使っても、その一度の関数呼び出しが秘密を外へ送ることは防げない。情報フロー制御（information-flow control）でも、承認を二度使うことは別に制限しなければならない。一意性を使う破壊的な更新は、権限の制限を追加せずに、純粋な関数の実装を速くする用途を持つ。

S3 が推す順序は次のとおりである。

1. 0.0.13 の判断では、型の印を全関数へ加えることを前提にしない。サーバ側の承認の消費、秘密の受け取り口、実際の出力の判定、継続とタスクの扱いの接点を先に決める。
2. TODO-154 の組み込みの不透明型 `Secret` を TODO-269 より先に作る方針を維持する。表示を防ぐ保証と、秘密に依存する公開出力を防ぐ保証を分けて記す。`Secret` の実装を 0.0.13 に含めるかは、S4 と設計者の判断に残す。
3. 線形型・アフィン型・一意型・graded types・コエフェクト・情報フロー制御を、サーバモードの成立条件にしない。TODO-269 を前倒しするだけの、Benitoite の実用例・推論器・診断の証拠は今回得られていない。
4. 型の印を利用者に求めない一意性の利用を、TODO-028 の候補として残す。現行ヒープは参照カウント方式ではないため、Perceus の移植を小さな最適化とは見積もらない。局所構築器の拡張、内部だけの所有の解析、参照カウント方式への変更を比べる。

## 1. 線形型・アフィン型と所有・借用

### 1. 何を表せるか

線形型は資源をちょうど一度使う制約、アフィン型は高々一度使う制約である。ただし「使う」の定義は API と評価の規則に依存する。L1 の線形矢印は、結果をちょうど一度消費すれば引数もちょうど一度消費するという保証であり、停止や OS の close の成功の保証ではない。閉じる関数だけが最終的に資源を消費できる API と組み合わせて、閉じ忘れを制限する。

調べた方式の差は次のとおりである。

| 方式 | 書く印と推論 | 診断・適用上の差 |
|---|---|---|
| Linear Haskell（L1・L2） | 関数の矢印へ使用の多重度を付ける。2018年の試作には推論があるが一般の理論は残課題。閲覧した GHC の文書では線形矢印と多重度多相の矢印は宣言し、通常の署名なし関数は通常の矢印になる | 関数・高階関数・データの欄を通じた使用制約を検査する。型全体の一意性とは区別する |
| Rust（L3） | 非 Copy の所有の移動と、共有/可変の借用を区別する。参照型と寿命の関係が API に現れる | 移動後の使用、重なった可変借用の位置を示す。所有だけから解放の必達は得られず、安全な `mem::forget` もある |
| Idris 2（L5） | QTT の 0 は実行時に消去、1 は線形、明示引数の多重度の指定なしは無制限。暗黙に束縛する型変数の消去とは区別する。0 は「承認を0回だけ使える」の代用ではない | 線形名を二度使った診断や hole の残りの多重度を表示する。状態の添字と組み合わせて手順も表せる |
| Austral（L6） | Free/Linear の分類を型宣言に持ち、線形な値を含む型も線形にする。借用を設ける | 未消費と再使用を検査する。標準の API の内側は信頼の境界に置く |

### 2. 権限制御での使い道

TODO-283 の「何回使えるか」に直接対応する。承認を表す偽造できない値がアフィンで、承認を消費する操作しか実行できなければ、同じ値からの二度の実行を静的に拒否できる。承認を使わず取り消すのも普通なので、承認そのものには「必ず一回」より「高々一回」が合う。

しかし、承認を誰でも複製・再発行できる入口があれば、この保証は成立しない。承認を渡す方式は ADR 0117 の「ケーパビリティの値を設けない」の見直しでもあり、型の印だけを追加して済む案ではない。再試行・別ジョブ・別プロセスを含む一回の承認には、サーバ側の同じ承認の識別と消費が引き続き要る。

現在の方針から導くなら、操作の種類・対象の許可を既存のエフェクトとサーバの方針で判定し、回数はサーバの消費状態で判定する案を先に比較する。OS のサンドボックスは許可対象を制限する層であり、一個の承認の消費をそのまま設定に変換できるとは見込まない。共通の方針のうち、どの制約をどの層で強制するかを表示する。

### 3. 実用の機能での使い道

次は構文を決めない `.bnt` の擬似コードである。`Approval` がアフィンという制約は宣言側にあると想定する。

```text
// 案: Approval はサーバだけが発行でき、sendOnce が消費する。
bind receipt <- try ApprovedMail.sendOnce(approval: approval, message: message) or return
ApprovedMail.sendOnce(approval: approval, message: another) // 検査で再使用を拒否
```

一方、ファイルでは読み取りのたびに handle を消費して返す形より、現在の `with` で何度も読む形が短い。線形・借用を足す利点は、閉じた後の使用とスコープ外への持ち出しを実行前に検出できることにある。`with` は既に取消しや非再開の破棄でも解放するため、単に通常終了時の close を要求するだけなら得るものが少ない。異常経路も含む解放の仕組みは残す必要がある。

テストでは「この模擬入力を二度読まない」「生成した資源を片付ける」等の制約が書ける。ただしスクリプト全体へ所有を導入すると、探索の分岐で入力を共有する・バックトラック時に状態を保存する作業にも、共有と複製の選択が必要になる。一般の探索の書きやすさが自動的に上がるとは判断しない。

### 4. 今の設計との両立

B4 のワンショットは継続の複製を抑えるが、資源の所有の証明には足りない。resume を呼ばずに捨てるときに、捕まえた線形資源を誰が消費するかを定める必要がある。選択肢は、捨てられる資源をアフィンにして `with` の解放へ任せる、または線形資源を捕まえる節に後始末の義務を課す、である。

深い再開の間と節の外側では、捕捉した値を使える範囲を分ける。ハンドラを子タスクへ引き継ぐ現行規則も、線形な環境を複製できないので、そのまま一般化できない。共有できる環境だけを引き継ぐか、資源を一つの子へ移す規則が要る。通常のエフェクト変数・State の制約と、将来の WASM の除去禁止は保てるが、外部 API も所有を守る信頼の契約を持たなければならない。

### 5. 設計原則との関係

二度目の使用、最初の消費、宣言位置を結ぶ診断は原則1・4に合う。型の印を標準のリソース宣言に限定すれば、普通の利用箇所の注釈は減らせる。しかし、資源を含む List・Result・閉包や高階関数にも制約が伝わり、関数をまたぐ所有までライブラリ内へ隠すことはできない。

推論で消せるのは印の記述であり、複製したい箇所と移したい箇所の選択ではない。原則3の利用者には「この承認は一回で消費する」と示し、型の多重度をそのまま表示しない。LLM の成功率の改善・悪化は未測定である。

### 6. 形式化の費用

一般導入は重い。Release の環境の分割、弱化・縮約の条件、置換、関数の型、継続とストアの所有、破棄時の解放を変更する。Surface の分岐・捕捉・再帰・型クラスの辞書にも消費の対応を通す。少なくとも「型の構成と代入」「使用環境と置換」「ストア・継続」「進行・保存」「エフェクト健全性」「Surface の検査・脱糖」の6群を再検討する見込みである。

0.0.8 の三種類へは、使用回数を持つ関数型の比較と多重度の計算が該当しうる。回数をエフェクトに書けば効果の中身と除去も変わる。既存の進行・保存を証明し直すだけでなく、資源の消費に関する結論を追加しなければ、静的な使用回数の保証にならない。追加公理で済ませる案は推さない。物理の close の成功や停止を主定理へ紛れ込ませない。

### 7. 互換性と構成

通常型を無制限のまま残す追加なら旧コードへの直接の影響を抑えられる。既存の File.Reader 等を線形へ変える場合は、引数へ渡す・捕捉する・タスク間で共有する標準の例と同梱 Skill に書き直しが生じる見込みである。所有の規則を Cargo の機能ごとに変えることは避ける。消費の番号と計数には幅の検査を設け、ポインタ幅を使用回数の上限と同一視しない。

### 8. 学習の価値

構造規則、所有、借用と線形性の違い、継続が資源を保持する意味を学べる。ただし一般の所有体系は学習と実装の対象が大きい。後で小さな資源 API を対象に試作し、現行 `with` の保証をどれだけ増やすかを先に確かめる価値がある。

## 2. Clean の一意型

### 1. 何を表せるか

Clean の一意型は、更新する時点で対象へのほかの参照がないことを属性で保証する。L4 は属性の自動推論と属性多相を説明し、関数引数が一意なら安全な破壊的更新に使えるとしている。使用を一度に制限する線形矢印と、実行時に別名参照がない保証を区別する。高階関数が一意な値を捕まえた場合、その関数自体の共有も制限する必要がある。

### 2. 権限制御での使い道

資源の持ち主を一つにして、同時の更新・閉じた後の使用を制限する基礎になる。しかし、対象への唯一の参照を持っていても、その対象をどの宛先へ送ってよいかや、何回の外部操作を許すかは決まらない。承認の権限を一意な値で表すなら ADR 0117 の見直しとなる。ADR 0183 の方針・IO の実行時判定・OS の制限を置き換える用途には推さない。

### 3. 実用の機能での使い道

動的計画法の表、訪問済み集合、作業用の配列を一意に受け渡せれば、純粋な関数の形を保った更新を実装できる。次は一意な表を受けて一意な表を返す API の案である。名称・型の印は未決定である。

```text
// 案: nextRow は唯一の所有を受け取り、更新後の所有を返す。
function nextRow(table: UniqueTable[Integer], row: Integer) -> UniqueTable[Integer]
  return UniqueTable.set(table: table, index: row, value: score(table, row))
end function
```

この例を成立させるには `score` の読み取りの借用と `set` への所有の移動を区別する。`UniqueTable` という名前だけの通常の `@opaque` ラッパーでは B1 の複製を禁止できない。現在の局所構築器はこの問題を第二級の局所参照に限定して避けるが、任意位置の更新や作業用の表は提供していない。一意型は関数をまたぐ組立てにも広げられる分、契約が増える。

探索の履歴を残したい場合は、共有を許して複写する永続値と、一意な作業領域を分ける必要がある。性質のテストでは、古い版を残す場合と捨てる場合の結果が一致することを確認する用途がある。速さと書きやすさの実測は今回行っていない。

### 4. 今の設計との両立

現在の通常の値を不変に保つ API の裏で使えるが、公開型で保証するなら閉包・Lazy・Reference・保存継続・Task の別名も追う。B4 の節が外で実行する規則とワンショットは保てるものの、資源を節と再開先の両方から使えない条件が要る。共有するハンドラ環境の引き継ぎには一意型を無条件に含められない。B5 の効果の除去や WASM の規則は変更の必要性を別に判定する。

### 5. 設計原則との関係

Clean の推論は「すべての局所変数に人が印を書く」必要がないことの先行例になる。しかし一意性が失われる呼び出しと、更新したい呼び出しの二箇所を示す診断が要る。公開の API の契約まで隠すと、複写を許すのか拒否するのかが不明になる。日常のスクリプトへ型の分類を広げるより、局所 API と内部最適化を先に比較する。

### 6. 形式化の費用

一般導入は大〜極大の見込みである。単純な型の健全性に加え、ヒープ上の別名の排他性を表す意味と、共有で属性が変わる関係が必要になる。Release の関数型・型代入・ストア・捕捉・継続、Surface の属性制約と脱糖が対象になる。属性の計算は三種類のうち「型の計算」に当たりうる。効果から State を除くことまで同時に行わなければ、効果の除去の追加は避けられる。一般の一意性の結論を B9 の抽象ストアだけで物理ヒープへ証明したとはしない。

### 7. 互換性と構成

新しい一意なコレクションに限るなら既存コードを保てるが、共有版と一意版の API を二重に持つ費用がある。普通の List に一意性を必須とすれば B7 の共有を使う例が影響を受ける。一意性の意味は構成によらず同じにし、ランタイムの実装を WASM 実行系へ依存させない。

### 8. 学習の価値

線形性と別名の解析の違い、属性多相、参照透過性を保つ更新を学べる。Perceus と比べると、型で性能の条件を保証することと、同じ API の実行時に条件を調べることを区別して学べる。

## 3. Granule の graded modal types

### 1. 何を表せるか

G1 は、線形な型へ回数・区間・セキュリティの束などを添字として加える。回数の合成は足し算と掛け算等の資源の代数で定め、単なるエフェクト名の集合と異なる情報を表す。2019年論文の型検査は双方向で、トップレベルに署名を要求し、制約を解く。一般の型推論・主要型は同論文では未達である。未使用・二重使用の線形性の診断の例がある。[G1](https://www.cs.kent.ac.uk/people/staff/dao7/publ/granule-icfp19.pdf)

### 2. 権限制御での使い道

回数の添字を持つなら「高々 n 回」を契約へ表せる。ただし変数を n 回使うことと、実際の外部操作が n 回起こることは別である。操作を行う関数の契約に両者を結ぶ規則が要る。再帰の深さや入力の長さが動的なら、静的な有限上限を得られない場合もある。既存の効果の集合は同じ名前を重複しても一個にするため、回数を現在の和集合へ混ぜることはできない。

セキュリティの grade も選べるが、回数の grade を導入しただけで非干渉が得られることはない。承認の残数はサーバ側の状態と照合し、OS へ導く対象の制限とは分ける。

### 3. 実用の機能での使い道

次は API が同じ入力を最大二度使うと記す案である。Benitoite の構文ではない添字をコメントで示す。

```text
// 案: source の使用上限は2。clone を許す意味と実際の取得回数は別途定義する。
function compareCopies(source: FetchSource) -> Boolean uses File.Read
  bind first <- FetchSource.read(source)
  bind second <- FetchSource.read(source)
  return first = second
end function
```

消費型のストリーム、生成器を決めた回数だけ使う API、読み取りの回数に上限を持つ試験には用途がある。一方、通常のファイルの二度の read は異なる行を返す場合もあり、「使用回数を数える」だけで記録と再生の意味は得られない。現在のハンドラは操作列を観測・記録できる。graded types の追加の利点は、その回数について関数をまたぐ契約を検査することである。

型の添字を使えば表の大きさや手順の精度を上げる余地もあるが、動的なサイズの配列処理の全部を正確な自然数の式にすると、日常のスクリプトの型が複雑になる。今の Range の実行時検査と局所の区間解析は、既知の範囲を利用する限定した段として別に使える。

### 4. 今の設計との両立

回数だけを値の使用環境へ加える場合も、分岐・高階関数・保存継続での合成が要る。操作を処理したときに回数を型から除く案は、節内の再操作と resume の潜在的な使用まで計算しなければならない。外側で走る節と深い再開を混同しない。子タスクへ要求を引き継ぐなら、予算を分配するのか共有するのかを定める。エフェクト変数を現在の規則のまま残しても、grade の変数について別の推論・契約が増える。

### 5. 設計原則との関係

正確な回数・制限区間・無制限のうちどれを既定にするかで診断が変わる。Granule の先行例を根拠に「印をすべて推論で隠せる」とは判断できない。固定した小さな回数を標準 API の宣言内で使う方が、任意の代数と制約をスクリプトに公開するより原則4・6に合わせやすい。LLM にどちらが有利かは期待結果まで測定しなければ分からない。

### 6. 形式化の費用

一般化は極大の見込みであり TODO-250 の重い項目になる。grade の代数・順序、型の計算と制約解決の健全性、使用環境の置換、継続・効果の関係、Surface の型保存が増える。効果に回数も持たせるなら、0.0.8 の三種類をすべて含む可能性がある。最初から任意の grade や SMT の回答を公理として受け入れる案は推さない。閉じた有限の代数を決め、その判定の健全性を独立に証明する試作が先である。

### 7. 互換性と構成

今の関数をすべて「無制限」として取り込む設計は可能だが、有限回を要求する高階関数から既存関数を呼べるかが新しい制約になる。SMT を採る場合も言語の中核や VM へ大きな依存を直接足さず、組込み向けの構成を保つ。機能で型の意味を切り替える案は避ける。回数のあふれを許可の拡大へ変換しない。

### 8. 学習の価値

線形論理、半環、区間、セキュリティの束を同じ枠で読む学びがある。しかし、最初の実装で任意の資源の代数まで扱う必要はない。有限回数だけの計算と、現在の効果の集合の計算を比べる試作が適する。

## 4. 文脈の要求を追うコエフェクト

### 1. 何を表せるか

C1・C2 のコエフェクトは、計算が文脈へ要求するものを型判断で追う。C2 は文脈全体の flat と変数ごとの structural を区別し、暗黙の引数では名前と型の組の集合を追う。関数を作った時点の要求と、呼んだ時点の要求を分ける規則がある。値の由来や使用に使える枠組みであるが、一般のコエフェクトだけで漏洩の方針が決まるわけではない。[C2 §2.4・3〜4](https://tomasp.net/academic/papers/structural/coeffects-icfp.pdf)

論文の例は要求の計算を示すが、Benitoite の行多相・再帰・ハンドラを含む推論器と、診断の製品仕様を与えない。C1 の暗黙の引数のモデルでは、要求を定義時と呼出時へ分ける複数の判断があり、主要なコエフェクトが一意に得られるとはしない。暗黙の引数の未充足・名前と型の不一致を示す診断は設計できる見込みだが、これは本調査の提案である。

### 2. 権限制御での使い道

「この計算は時計・設定を要する」等を追い、必要な文脈を与える境界を明確にできる。文脈に権限の値を入れれば「誰が権限を持つか」とも重なるが、その案は ADR 0117 の変更となる。要求の集合へ `Secret` を入れるだけでは、秘密を読んだ後の公開出力や分岐の影響を拒否できない。情報の流れの規則を具体的に加える必要がある。

ADR 0183 の分担では、文脈を与える者を方針の管理側に限り、要求があることを許可されたことと同一視しない。OS のサンドボックスも要求の型から直接得られるものではなく、許可の方針から対象の制限を作る。

### 3. 実用の機能での使い道

次は現在の仕組みに寄せた案である。`runJob` が呼ぶ関数は省略し、差し替える境界だけを示す。

```text
// 現行の方向: 組み込みの時計の操作はハンドラで差し替えられる。
bind fixed <- sampleInstant()
bind result <- handle
  runJob()
with
  case Clock.now() -> resume(fixed)
end handle

// 将来案: 設定値の文脈。context/require の構文は未決定。
// runJob は Settings と固定された時刻の要求を型に持つ。
bind result <- Context.run(settings: testSettings, now: fixed, body: lambda() return runJob())
```

固定時刻や読み取り専用の設定を各引数へ繰り返し渡す負担は減らせる。現在も設定のレコードを明示引数にし、時計をハンドラで差し替えられる。追加で得るものは、暗黙に要る文脈の一覧と、その充足の静的な検査である。時計の操作の記録・再生や失敗の注入そのものを新しく可能にする仕組みではない。

乱数の種には別の注意が要る。同じ種を暗黙に何度も読むだけでは、毎回同じ生成器の先頭を使ってしまう。現在の純粋な `Random.fromSeed` の生成器を明示して次の生成器へ進めるか、Random.Generate の操作をハンドラで差し替える方式と比べる。タスクごとの列の分割・引き継ぎや、順序が変わっても再現するかは、コエフェクトの要求だけでは決まらない。構文解析や探索でも、読み取り専用の設定の局所化は可能だが、取り消し・バックトラック時の状態の巻き戻しは別の意味を要する。

### 4. 今の設計との両立

通常の辞書引数へ脱糖できる制限した文脈なら B5 の効果を保てる可能性がある。しかし関数生成時に捕捉するか呼び出し時に要求するかで型と意味が変わる。純粋な関数が外の可変な時計や設定を無注釈で読めるようにしては B1 の契約に合わない。明示の文脈引数にするか、要求を関数型に残す必要がある。

動的な局所上書きは S1 の local/scoped effects と重なる。節はハンドラの外側で走るため、どの設定が節・resume の本体・子タスクに見えるかを別々に決める。現在の深いハンドラと引き継ぎを自動的に変えない。State・エフェクト変数の処理禁止、WASM のホスト操作の扱いも、文脈の要求とは別に維持する。

### 5. 設計原則との関係

読み取り専用の設定の要求は、名前・型・供給位置を絞れば推論でかなり隠せる。ただしスコープ外で必要になる要求は公開の契約へ残る。明示引数、辞書、ハンドラと同じ用途の第四の書き方を増やすなら、原則5に照らして省ける負担を実例で示す必要がある。現在のテストの固定だけを理由に一般導入する案は推さない。

### 6. 形式化の費用

固定した辞書への変換だけなら Surface の型付け・脱糖と要求計算の健全性が主対象で、中の見込みである。ただし既存 Release への正しい変換を作れて初めて、コアを変えない案と呼べる。動的な束縛・文脈多相・要求の減算を一般化すれば、Release の関数型、代入と評価、捕捉・継続の規則まで広がり大〜極大になる。三種類では型の計算、要求を効果に併記するなら効果の中身と除去が該当する。

既存の主定理の結論を保つ脱糖案でも、要求が充足されるという新しい性質は別に証明する。タスクは B9 の外側なので、その文脈引き継ぎまで既存の性質1で保証したとはしない。

### 7. 互換性と構成

明示引数の既存 API を残し、新しい読み取り専用 API だけで使えば追加にできる。時計・設定・乱数の既存 API をまとめて暗黙化すると、公開の型とテストの前提が変わる。要求の検査は OS や Wasmtime に依存させず、構成ごとに存在する文脈の提供者だけを変える。

### 8. 学習の価値

型とエフェクトの双対、文脈の分割、暗黙の引数と動的スコープの差を学べる。日常のテストに対する実利は、まず明示レコード・ハンドラ・限定した文脈の三案で同じ小例を比べると判断しやすい。

## 5. 情報フロー制御と LIO

### 1. 何を表せるか

情報の流れの制御は、秘密の入力を変えても許されない公開の観測が変わらないようにする規則を持つ。秘密をコピーした明示の流れだけでなく、秘密で分岐して定数を表示する暗黙の流れも対象になる。印の意味・観測・許す開示を定めて初めて非干渉を主張できる。

| 確認した方式 | 推論・注釈・判定 | 限界と診断 |
|---|---|---|
| Jif（I1） | 値の印と program-counter label（pc）を使う。局所の印は推論するが、省略したメソッド引数等は規則による既定値であり、すべての省略を推論するのではない | 分岐による依存も検査する。メソッドの印と方針が必要。文書は停止と時間による漏れを制御しないと明記する |
| FlowCaml（I2） | 作者の説明では、型の印をソースへ要求せず、宣言した方針に対する情報の流れを推論・検査する。背景の ML の体系は参照・例外・let 多相を持つ制約ベースの推論 | 推論が強くても、型の中の印・順序制約は残る。詳細な実際の拒否文言の品質は本調査では評価していない |
| LIO（I3） | Labeled で包み、実行時の現在の印と clearance を追う。読むと現在の印が上がり、低い出力先への書き込みを拒否する。toLabeled で結果を包む | 静的にすべての流れを推論する方式ではない。2011年論文の保証は逐次のモデルであり、Benitoite のタスクへそのまま適用しない |

FlowCaml は「局所変数へ印を書かずに推論できるか」への肯定的な先行例である。しかし推論は、何を秘密とするか・誰への何の出力を許すかを発見しない。入力と出力先の方針は必要である。[Jif](https://research.cs.cornell.edu/jif/doc/jif-3.3.0/language.html)、[FlowCaml](https://www.normalesup.org/~simonet/soft/flowcaml/)、[LIO](https://www.scs.stanford.edu/~deian/pubs/stefan:2011:flexible.pdf)

### 2. 権限制御での使い道

TODO-283 の「値がどこへ流れるか」に直接対応する。たとえば Secret 用の入力から得た値の印と、標準出力・ファイル・HTTP の宛先の印を比較し、許さない公開を拒否する。宛先別に許すには公開/秘密の二点だけでは不足する場合があり、秘密の分類と受け手の集合、許可の順序を決める必要がある。

TODO-154 の `Secret` は、等値や表示を持たず、決まった受け取り口へそのまま渡す案である。これはうっかり表示の防止にはなるが、受け取り口が許す外部送信はできる。Secret.Read と Http.Connect がともに許されたことから、送信先がその秘密の受け手として適切であるとは導けない。Secret.Reveal で普通の String へ出した後も、情報の流れを追わない版では間接の漏れを防がない。

ADR 0183 の方針へ将来追加するなら、秘密の取得元、出力の分類、許す開示の規則を同じ方針の情報として管理する。ただし OS のパス・通信先制限だけでは、値の由来を強制できない。外部コマンドへ秘密を渡した後の保証は、コマンドを信頼の境界へ含めるか、その外を保証しないかを選ぶ必要がある。

### 3. 実用の機能での使い道

次は TODO-154 の API の案を使う擬似コードである。現行に Secret の実装があるという意味ではない。

```text
// 案: 取り出さず認証専用の受け取り口へ渡す。
bind token <- try Secret.fromKeystore(service: "report", account: "upload") or return
bind response <- try ReportApi.upload(token: token, body: report) or return

// 将来の IFC の案: reveal 後も依存を保持する場合。
bind text <- Secret.reveal(token)
if text = "guess" then
  Console.writeLine("yes") // 値の印だけでなく、この分岐の pc も理由に拒否する
end if
```

前半は不透明な値と専用の受け取り口で実現でき、各局所変数へ秘密度の印を要求しない。後半を拒否するには、普通の String の値にも由来の関係を保つ新しい規則が必要である。`@opaque` の通常レコードや CheckedPath の実行時検査、数値の区間解析だけではこの関係を表せない。

実用上は、設定や認証情報を含むレコードから公開用の報告を作る、試験の失敗ログに入力を漏らさない等に用途がある。ログ・JSON・die の説明・終了状態・記録と再生・性質のテストの反例表示も出力先として扱う必要がある。探索や整列を直接速くする方式ではないが、秘密を含むデータの変換の許される組合せを検査できる。

資源と並行では、取り消したか・時間切れになったか・エラーになったか自体も観測になる。秘密で変わるファイルへの書き出しを `with` の解放が行う場合、公開の判定を通常の IO の操作だけに置くと漏れを見落とす。現在の State による解放の例外を、そのまま情報の流れの例外にはできない。

### 4. 今の設計との両立

効果を持たない計算も秘密へ依存するため、現在の「純粋」から「公開」を導かない。ハンドラが操作の効果を型から除いても、節へ渡された秘密、節で選んだ結果、再開後の分岐の依存は消えない。節が外側で走るときにも pc と引数の印を適切に渡す。ワンショットと深い再開は継続の複製の問題を抑えるが、非干渉の代わりにはならない。

子タスクには、ハンドラだけでなく秘密度の文脈をどう引き継ぐかが必要になる。Task の結果、Reference の更新、待ち・取消し、スケジューラを介する観測を対象にするかを定める。エフェクト変数を処理できない現行規則を保つことはできるが、印の多相とその制約は別に増える。

WASM へ秘密を渡すなら、純粋な外部関数でも結果は秘密に依存する。IO の効果がないことだけを理由に印を公開へ落とせない。外部型の状態、ホスト操作、外部コマンド、解放時の出力も含めた契約が要る。Secret.Reveal を模擬ハンドラで偽の値へ置き換える場合と、本物を取り出して開示する場合は区別する。現在の「処理した効果を除く」規則を一律禁止するのでなく、本物の取り出しと許された開示の実行点を信頼の契約へ結ぶ案を調べる。

### 5. 設計原則との関係

「秘密から作った値なので表示できない」という理由を宣言・分岐・出力の位置へ結べれば原則1・4に合う。FlowCaml のように局所の印を推論し、標準の入力・出力 API に方針の注釈を集めれば、書き手の記述量は減らせる。しかし公開関数や高階関数が秘密度を保存する契約、明示的な開示、宛先の区別はライブラリ内へ完全には閉じ込められない。

推論結果の大きな制約式をそのまま診断へ出すと、LLM による修正の負担が残る。逆に全体を `<secret>` としか説明しなければ、修正すべき分岐や受け取り口を判断できない。秘密の実値を出さず、依存した束縛・pc を上げた位置・拒否する出力先を示す診断が必要である。この形式で期待結果まで達成できるかは未測定であり、TODO-269 の懸念を解消したとはしない。

### 6. 形式化の費用

極大の見込みで、TODO-250 の重い項目に当たる。進行・保存は一回の実行の不変条件だが、非干渉には秘密だけが異なる二回の実行の公開の観測を関係づける定理が要る。I2 は二実行を扱う言語への拡張と保存を経由し、I3 は観測者に見えない部分の消去を使う。どちらの証明も Benitoite のハンドラ・保存継続・タスク・外部操作について既に成立しているわけではない。

少なくとも「印の順序と推論」「値・関数の型」「pc と制御」「可変ストア」「ハンドラ・継続」「公開事象と開示」「二実行の関係」「Surface と脱糖」の8群が増える見込みである。B9 の外側のタスク・物理出力・外部処理との接続は追加の対象になる。効果へ印付きの内容を入れる、開示や処理で印を除く、束の式を計算する案は、0.0.8 の三種類すべてへ関わりうる。

既存の主定理を残せる消去の方式でも、非干渉の結論を新設する必要がある。停止非依存の非干渉を最初の候補にするか、時刻・停止・資源枯渇まで対象にするかで費用が変わる。組み込みと外部関数の依存保存・許された開示に関する仮定を追加するなら、仮定の意味と実装の信頼範囲を明記する。根拠のない非干渉の公理を加える案は推さない。

### 7. 互換性と構成

全値に公開の既定を与えるだけでは、既存の入力経路から来る秘密を見落とす。対象にする秘密の入力を先に限定し、その入力以外も含めるときに API・標準ライブラリ・診断・Skill を移行する必要がある。LIO 型の実行時拒否なら表面の型変更を減らせるが、現在通る処理が実行時に拒否されうる。

印の意味を構成で変えず、キーストア・ネットワーク・サーバの実装を中核の型検査から分ける。Secret のビット列や印の番号をポインタ幅へ依存させず、機能を外した構成は対応モジュールを検査時に拒否する。

### 8. 学習の価値

非干渉、束、pc、開示、観測の定義を学ぶ価値は高い。型安全の証明との差も明瞭である。ただし学びの価値を理由にサーバモードと同時に複数の重い形式化を行う根拠にはしない。逐次・二点の印・限定した出力の小モデルから始める判断が妥当である。

## 6. 参照カウントと一意性を使う破壊的な更新

### 1. 何を表せるか

R1 の Perceus は、明示的な制御のある内部言語に、正確な参照カウントの増減と再利用の処理を挿入する。ユーザーの型に一意の印を要求せず、実行時に共有されていない対象を更新・再利用し、共有されていれば必要な部分を写す。FBIP はその更新を使う関数の書き方である。型の印がないことは、静的解析も所有の規則も不要という意味ではない。[R1 §2〜3](https://xnning.github.io/papers/perceus.pdf)

Lean は参照カウントと借用の解析を使い、共有配列は写し、非共有の配列や文字列を更新する。Roc でも Str の一意時の更新が説明されている。これらの通常の関数の型は、更新が必ずその場で行われることを要求しない。一意型による静的な更新の保証と、実行時に機会があれば更新する方式の差である。[Lean](https://lean-lang.org/doc/reference/latest/Run-Time-Code/Reference-Counting/)、[Roc](https://www.roc-lang.org/docs/alpha4/Str/)

### 2. 権限制御での使い道

この方式自体は、承認の二度の使用や秘密の送信を拒否しない。一意な承認のメモリを持っていても、その値を何度も読み操作する API なら回数の制限にならない。回収時に OS のリソースを閉じる案も、現在の `with` と State の解放の意味を変えるため、性能の最適化へ混ぜない。ADR 0183 の静的・動的・OS の方針はそのまま残せる。

### 3. 実用の機能での使い道

一つの最新版だけを持つ集計、動的計画法の作業用の表、グラフの訪問済み集合、配列の整列には候補となる。古い版を使わない更新で複写を省ければ、普通の関数の受け渡しのまま、確保と道筋の複写の費用を減らせる。次は現在の構文に寄せた案で、`Table` の API と最適化は未実装である。

```text
// 案: 値の意味は不変。更新前の table を後で使わない場合にだけ再利用する。
function relax(table: Table[Integer], from: Integer, to: Integer, cost: Integer) -> Table[Integer]
  bind candidate <- Table.get(table: table, index: from) + cost
  bind old <- Table.get(table: table, index: to)
  return Table.set(table: table, index: to, value: Integer.minimum(a: old, b: candidate))
end function
```

旧版を履歴へ保存して探索を戻す場合は、共有した部分を写す必要がある。外側の根が一意でも子ノードが別の根と共有されうるため、子への更新も一意性を確かめる。参照カウントだけで RRB 木が連続した配列になったり、平衡木の操作が定数時間になったりすることはない。DP の密な表や整列には、専用配列・局所の任意位置更新を用意する別の設計も比較する。

現在は ListBuilder 等が追記の局所化を提供している。小さな出力を順に作る仕事では、その API を使う方が先である。一方、任意位置更新・Map の局所更新・関数をまたぐ更新は B8 の範囲を越える。TODO-028 では、API を追加する費用、内部の解析の費用、回収の方式全体を替える費用を同じ候補表へ置く価値がある。

### 4. 今の設計との両立

Benitoite の現行値は B6 のとおり `Copy` であり、複製や上書きのたびの参照カウントはない。対象の頭の印や通し番号は共有数ではない。GC で生きているか分かることから、唯一の所有者かは分からない。Rust の一時的な `&mut` を得ても、別の Benitoite の値が同じ対象を指していないという保証にはならない。

既存の生存の解析と根の整理は材料になるが、Perceus 型の導入には、少なくとも通常レジスタ、閉包、コレクションの辺、Reference、Lazy、保存継続、Task の結果、Host 内の Slot の複製・破棄を漏れなく扱う必要がある。ワンショットでも、捕まえた区画を保持する間の所有と、再開しないときの破棄は残る。深いハンドラ・節の外側での実行・子タスクの共有を、明示的な内部の制御へ対応させなければならない。

その上で比較する案は三つある。

| 案 | 現行に使える範囲 | 足りないもの |
|---|---|---|
| 局所構築器・組み込み関数の専用作業領域を拡張する | 外へ出ない所有を構文または内部の局所領域で決める。一般の値の GC を保つ | 任意添字・Map・freeze/copy の契約、外へ出ない証明。現行で既にできるのは追記と copy まで |
| コンパイラ内部だけで共有されないことを証明する | 解析が証明した箇所に限り更新し、未知なら複写する。ユーザーの型を変えず、GC も保てる可能性 | 関数の呼び出し・閉包・継続・子ノードを含む別名の証明。現在この解析が存在する証拠はない |
| 正確な参照カウントと reuse を導入する | 実行時の一意性で、同じ API を共有値にも非共有値にも使う | Copy な値と根の設計、増減命令、借用の解析、循環の扱い、回収と上限・待ち時間の再設計 |

三つ目では、循環が作れる Reference・Lazy 等をどう回収するかが残る。Perceus の garbage-free の主張は循環のない範囲に条件があり、Lean の検証可能な部分の非循環性も現行 Benitoite の保証ではない。マーク・スイープを循環の回収に残す混合方式は候補になるが、全体の費用と一意性判定の正しさは未確認である。

### 5. 設計原則との関係

型の印なしの方式は、同じ純粋なコードを維持できる点で原則5・6と相性がよい。共有を増やす小修正で速さが変わりうるため、性能上の一意性を言語の正しさと同一視しない。必要なら開発用の共有の可視化を検討できるが、通常の権限確認に内部の参照数を出す必要はない。書き方を FBIP へ寄せる案の LLM の成功率は未測定である。

### 6. 形式化の費用

表面の値の意味と型・エフェクトを保てる実装最適化なら、既存 Release の規則と主定理の変更は避けられる見込みがある。ただし B9 は物理の再利用を証明していない。安全性には、最適化前の不変値と更新後のヒープの観測が一致すること、古い共有版を変えないことが必要である。これは既存のエフェクト健全性の引用だけで済まない。

局所構築器の新操作は現在の専用コア・ストア・Surface の場合を増やすため中〜大、一般の所有の解析とヒープ対応の証明は大〜極大の見込みである。ユーザーの型の計算や効果の除去を足さなければ0.0.8の三種類は直接避けられるが、それでヒープの証明が軽くなるとは限らない。実装だけを先行する場合も、保証の範囲を限定し、到達可能性・GC stress・Miri 等の適切な検査を後の計画へ割り当てる。本調査では実行していない。

### 7. 互換性と構成

同じ純粋な結果と既定の資源の上限の意味を保つ範囲では、ソースの互換性を保ちやすい。ただし一意時の領域の再利用で確保量や停止時間が変わる。ObjId を再利用の前後でどう扱うか、要素数・容量の計数、エラー時に旧値を壊さないことを点検する。リソースの解放を GC に移す変更は含めない。

回収の実装を選べる境界は作れても、構成によって型の意味を変えない。将来の複数スレッドに参照カウントを拡張する費用は、現在の単一 VM スレッドと区別する。カウント・容量のあふれを検査し、64ビットのポインタや usize の幅だけを前提に新実装を作らない。

### 8. 学習の価値

正確な生存、所有と借用の内部解析、参照カウントの命令の挿入、再利用と永続性の両立を学べる。既存の mark-sweep と比較して、回収の方式とデータ構造の選択が別の問題であることも学べる。TODO-028 の候補としては推すが、今回の調べを採用や性能改善の証拠にはしない。

## 7. typestate とセッション型

### 1. 何を表せるか

typestate は、開いた/閉じた等の状態を型へ表し、操作の入力と出力の型で遷移を指定する方法である。L5 の `Door Closed -> Door Open` は線形な入力と組み合わせ、古い状態の値を再使用できなくする。セッション型は送受信の順序と相手側との対応を型へ表す。T1 の CP/GV は特定の線形の規則と接続を持ち、その条件で通信の性質を示す。[Idris 2](https://idris2.readthedocs.io/en/latest/tutorial/multiplicities.html)、[T1](https://homepages.inf.ed.ac.uk/wadler/papers/propositions-as-sessions/propositions-as-sessions.pdf)

### 2. 権限制御での使い道

「承認前/承認済み/消費済み」「トランザクション開始/終了」を区別できる。しかし状態の型が変わっても、旧状態の別名が使えるなら手順は守れない。線形/アフィンの所有か、サーバ側の状態の検査が必要になる。操作対象の許可、秘密の流れ、OS の制限は別の規則である。

### 3. 実用の機能での使い道

次は状態名を別の不透明型で表す API の案である。一般の型レベルの状態の計算を必須としない。

```text
// 案: commit は Transaction.Active を消費する。
bind active <- try Transaction.begin(database) or return
Transaction.write(transaction: active, rows: rows)
bind done <- try Transaction.commit(active) or return
Transaction.write(transaction: active, rows: extra) // 旧状態の再使用を拒否したい
```

日常のファイル処理は現在の `with` で開く・読む・閉じるを局所化できる。通常の API に複数の戻り値と状態名を要求して得る差は小さい。接続の認証、複数段のアップロード、トランザクションなど、間違った順序に具体的な費用がある API へ限定する価値はある。整列・DP の作業領域には、状態の詳細より一意な更新領域の方が直接の利点になる。

テストでは不正な順序を型検査で拒否でき、模擬の通信にも同じ手順を要求できる。ただし外部が切断する・失敗する・取消すことは消せず、Result と後始末は残る。セッション型を採るだけで外部サーバや全 Task のデッドロック不在は得られない。

### 4. 今の設計との両立

異なる `@opaque` 型で入口を分けることは B1 で表せるが、古い値の使用禁止は現行型だけでは表せない。実行時に状態を検査するライブラリ案は追加で作れる。静的に全経路を保証する案は所有と同じく捕捉・継続の破棄・Task の引き継ぎを変更する。非再開の節でも rollback が必要なら、現在の `with` の解放と整合する契約を定める。B5 の State と WASM の制約を手順の型だけを理由に除かない。

### 5. 設計原則との関係

状態ごとに使える操作を限定し「commit 済み」を診断する API は原則1・4に合う。一方、一般のスクリプトへプロトコルの型の式を公開すると原則6の負担が大きい。標準ライブラリ内部の実行時状態と、少数の異なる不透明型で済む範囲を先に選ぶ。一般のセッション型の構文を0.0.13へ足す案は推さない。

### 6. 形式化の費用

既存型のラッパーと実行時検査なら小〜中で、組み込みの契約と解放の性質が対象になる。静的な消費を含む typestate は第1節の所有の費用に加え、状態遷移の不変条件が要る。一般のセッション型は大〜極大で、Task と通信の意味、接続の双対、進行の言明を新設する。B9 の逐次コアの進行を、通信全体の進行へ読み替えない。型レベルでプロトコルを計算する案は三種類の「型の計算」に当たりうる。

### 7. 互換性と構成

別モジュールの専用 API なら追加にできる。既存 File や Task の型を状態付きへ変えるなら標準ライブラリ・examples・Skill の移行が要る。ネットワークを外した構成でも中核の型の規則は保ち、該当モジュールを提供しない。状態番号は有限の列挙や検査済みの番号で持ち、ポインタ幅を意味に使わない。

### 8. 学習の価値

型による状態機械、線形性との関係、通信の双対と進行を学べる。日常のスクリプトの実益を確かめるなら、一般体系より一つの失敗しうる手順の API を比べる方が適する。

## 統合の担当への申し送り

- **推す案**: TODO-269 の時期を維持する。0.0.13 は採否・順序・接点の判断とし、サーバモードを一般の所有・コエフェクト・非干渉の完成へ依存させない。Secret を先に作る決定を保つ。
- **推す案**: TODO-154 では、等値も表示も持たない組み込み型と専用の受け取り口を先に評価する。現在の `@opaque` の等値、文字列補間の対象、手動/生成の表示、JSON、die・テスト・機械向け診断の全入口を別々に確認する。`<secret>` を含む表示に長さや内容の断片を混ぜない。
- **推す案**: 一回限りの承認はサーバの共通の実行時判定で管理する案を先に比較する。試行と成功、予約と消費、同時実行、再試行、失効を区別する。線形なトークンはそれを置き換えるのでなく追加の選択肢として扱う。
- **推す案**: TODO-028 に、局所の更新領域、内部の一意性解析、参照カウントと reuse の三案を比較する候補を渡す。最初の性能の試行では単一路の更新と履歴を残す更新、密な DP 表・グラフ・整列・文字列構築を分け、確保量・共有時の複写・回収停止も調べる。今回ベンチマークは実行していない。
- **推さない案**: 線形型だけで「必ず close が成功する」「外部操作が一度だけ成功する」と説明すること。`with` の取消し・継続破棄の解放を線形型で自動的に置き換えること。
- **推さない案**: `Secret` と Reveal の効果だけで「秘密が外へ漏れない」と説明すること。コエフェクトの要求の一覧だけで非干渉を保証すること。FlowCaml の推論の成功を Benitoite の LLM の生成・修正の成功率の証拠にすること。
- **推さない案**: mark-sweep の生存の印や、ヒープ内の一時的な Rust の可変借用を、一意性の証拠として破壊的更新に使うこと。Perceus を参照数の検査一箇所の追加と見積もること。
- **判断に要る未確認の事実**: Benitoite のレジスタの生存と別名情報から、どの更新を一意と証明できるか。旧い参照カウント方式のコードを再利用できるか。循環の回収と正確な RC の混合方式の費用。現行の専用構築器の任意位置/Map 拡張の具体的な費用。いずれも TODO-028 の試作で確かめる。
- **判断に要る未確認の事実**: 印を推論して簡略化した診断で、LLM が失敗した課題を正しく修正できるか。高階関数・Task・ハンドラ・WASM の境界で必要になる公開注釈の量。LIO の後続の並行の研究と現行 Benitoite のスケジューラの対応。今回の文献の性能値からは判断しない。
- **S1 との重複**: 継続を捨てるときの所有と解放、再開回数、local の文脈、状態の巻き戻し、承認予算の動的な範囲。深い再開・節の外側・子タスクの引き継ぎのどれを変えるかを共通の契約表で確かめたい。
- **S2 との重複**: 一回限りの承認を値にすると ADR 0117 の見直しになる。秘密の取得元と宛先の結合には、CheckedPath 等の検査結果の同一性、方針の失効と実物の対象の照合が関わる。対象を表す値と、操作を許す権限の値を混同しない。
- **S4 への判断材料**: 推論と標準 API の内側への限定で、記述量は減らせる。一方、公開関数の契約・高階関数の制約・共有の選択・公開してよいかの方針は消えない。0.0.13 へ形式化の重い一般体系を複数同時に入れる根拠は、今回の調べにはない。
