# S1: 高階エフェクト・ケーパビリティ・ハンドラの選択の調査と判断案

調査日: 2026-10-26。対象は docs/todo の TODO-287 と、TODO-283 の「どの範囲の計算で権限を狭めるか」「権限を誰が持つか」のうちエフェクトに関わる部分である。採用や実装範囲の決定ではない。共通条件は common.md（依頼の共通の条件。git の外の作業用のディレクトリに置いた）、設計者の決定は [README](../README.md) に従う。

## 判断案

最初に行う学習用の試作には、**hefty algebras のうち、計算引数と後続の計算を分け、一階の操作とハンドラへ精緻化する部分**を推す。既存のワンショットの継続と実行系を保ちながら、高階の操作を抽象化する意味、精緻化の型保存、残るエフェクトの追跡を調べられるためである。試作だけで汎用の高階エフェクトの採用を決めず、0.0.13 への本実装の採否は設計者へ返す。

実用上は、操作の差し替え・記録・固定した時計と乱数・失敗の注入の多くを、今の一階のハンドラで既に書ける。増える価値は、`local`・再試行・時間切れ・資源を使う計算の範囲そのものを、差し替え可能な操作として扱えることである。探索のために同じ継続を複数回再開すること、資源の解放を保証すること、権限を強制することは、それぞれ別の設計が要る。

Effekt の方式には、注釈の軽さと、ハンドラの選択をレキシカルに固定できる利点がある。ただし、そのまま移すと、Benitoite の一級の関数、`uses` の読み方、継続の寿命、権限の説明を広く変える。全面移行を最初の改造に含める案は推さない。権限を狭める境界は、通常のハンドラを飛び越えても実際の外部操作で必ず照合する仕組みとして、サーバモードと一緒に設計する。

## 1. scoped effects

### 1. 何を表せるか

操作が、通常の引数に加えて「この操作の範囲に含める計算」と「範囲の後の計算」を別々に持つ。`catch`・Reader の `local`・探索で最初の結果だけを採る `once` が例である。Wu・Schrijvers・Hinze（2014）は、高階の構文と `weave` によってハンドラを内部の計算へ適用する方法を示す。Bosman・van den Berg・Tang・Schrijvers の λsc（2023年のプレプリント、LMCS 2024）は、これを組込みの構文・型付け・操作的意味論として定める。[Effect Handlers in Scope](https://www.cs.ox.ac.uk/people/nicolas.wu/papers/Scope.pdf) §8–10、[A Calculus for Scoped Effects & Handlers](https://arxiv.org/pdf/2304.09697) §3–8 [R1–R2]。

λsc は、型を変えるハンドラの多相性と、未知の scoped operation の明示的な forwarding を扱う。推論器では、ハンドラが結果に適用する型オペレータを注釈し、高階の単一化を避ける。これは Benitoite の現在の局所単相の束縛・結果型を変えないハンドラへ、単に操作の引数を一つ足す変更ではない。診断は少なくとも、内部の計算の型、範囲を出た値の型、forwarding の不足を別々に示す必要がある。

後続研究には Yang らの *Structured Handling of Scoped Effects*（ESOP 2022）があり、構造を保つモデルとハンドラの融合の法則を与える [R3]。この論文の要旨と導入は確認したが、圏論の構成全体は精査していない。本実装の見積もりを、そのモデルの移植が済んだ前提では作らない。

### 2. 権限制御での使い道

TODO-283 の「計算の範囲」を直接表す。`within(root, action)` の内部へ判定器を適用し、後続へ適用しない構造を明示できる。「対象」はパスの照合器、「誰が持つか」は追加のケーパビリティや権限文脈が担当する。scoped operation 自体から対象の包含・一回性・秘密の非干渉は得られない。

ADR 0183 の方針から作る実行時の判定器が外部操作を照合し、scoped operation は有効な方針を親との共通部分にする要求として使う案がある。OS のサンドボックスは実行全体の上限を強制し、細かい内部の範囲は処理系の判定器が扱う。通常のハンドラで処理しただけの要求に、方針を広げる権能を与えない。

### 3. 実用の機能での使い道

`local` の入れ子、探索の `once`、構文解析器の局所的な選択と失敗の扱いを、ライブラリが別々に解釈できる。現在も `withConfig(config, action)` という通常の関数の内部に一階の `ask` のハンドラを書ける。高階の操作が増やすのは、`withConfig` 自体を記録したり、別の局所化の意味へ差し替えたりすることになる。

```text
// 現行の構文に寄せた擬似コード。withConfig は普通の関数である。
withConfig(config: testConfig, action: lambda() return importReport() end lambda)

// 拡張案。localConfig の境界自体を操作として捕捉する。
Scoped.localConfig(config: testConfig, action: lambda() return importReport() end lambda)
```

局所状態をどの分岐へ引き継ぐかはハンドラの組み合わせの意味である。配列の破壊的な更新を安全に閉じる保証は、持ち出しや共有を制限する別の規則が要る。性能には融合の研究上の動機があるが、Benitoite の VM での効果は未測定である。

### 4. 今の設計との両立

ワンショットと高階の計算引数は独立であり、内部の計算を一回実行する限定案は考えられる。ただし、λsc の例をそのまま採れば、複数回使う継続や結果型を変えるハンドラも含む。深いハンドラと節の外側実行を保つなら、内部の計算にどのハンドラを付け直すか、未知の操作をどう forwarding するかを新たに規定する。

タスクへは、末尾再開の既存の規則だけで新しい内部計算の処置を説明できない。まず子タスクを起動しない scoped operation に限るか、子へ引き継ぐ実装を標準のものに固定する選択が要る。`State` と未知の行は外さず、外部関数は捕捉経路がない限り外さない。ADR 0147 は維持でき、ケーパビリティ値を加えなければ ADR 0117 の変更も必須ではない。

### 5. 設計原則との関係

範囲を字面で示す利点は原則3に合う。一方、ハンドラの型オペレータや forwarding を一般の利用者に書かせると、原則1・4・6の負担が大きい。標準ライブラリだけに宣言・forwarding を閉じる案と、利用者定義まで公開する案を分ける。原則5のため、通常の関数・`with` と同じ役割の構文を別々に増やす前に、差し替える必要のある境界を選ぶ。

### 6. 形式化の費用

Release の `Comp`・操作署名・節・継続・型付け・遷移・代入と、Surface の対応する定義を変える。内部の計算と後続の計算の型の関係、未知の操作の forwarding、処理によるエフェクト除去が主な追加である。一般の型オペレータを加えれば「型の計算」、範囲の識別子を効果に含めれば「エフェクトに型を持たせる」にも当たる。TODO-250 の重い項目に当たる。

進行・保存・健全性を新構文へ拡張し、脱糖の型保存も増やす。公理の追加は採用条件にせず、必要な補題を証明する案とする。小さい限定モデルと、本番の λsc 相当の導入を分ける（後掲の見積もり）。

### 7. 互換性と構成

既存の一階の宣言を維持した追加は考えられるが、型を変えるハンドラまで既存の `handle` に混ぜると推論・診断が変わる。標準ライブラリ・Skill の宣言と例、形式化の交換器にも追加が要る。ネットワークや WASM を中核へ依存させる必要はなく、64ビットのアドレスを前提とする設計も要らない。

### 8. 学習の価値

計算引数と継続の区別、ハンドラの合成、状態と失敗の相互作用を学べる。すべての λsc を最初に実装すると、多相性・型オペレータ・forwarding を同時に理解する負担が大きいため、最初の小モデルの候補としては hefty 型の精緻化を先に推す。

## 2. hefty algebras と Heftia

### 1. 何を表せるか

Bach Poulsen・van der Rest の *Hefty Algebras: Modular Elaboration of Higher-Order Algebraic Effects*（POPL 2023、doi:10.1145/3571255）は、高階の操作の木を、一階の操作とハンドラを使う計算へ変換する精緻化を合成可能にする。操作の内部計算と後続を再帰的に変換し、その結果へ操作ごとの elaboration algebra を適用する。高階の操作を関数として直接定義する場合と違い、操作のインターフェースを保ったまま変換方法を替えられる。[論文本文](https://casperbp.net/store/hefty-algebras.pdf) §2–5 [R4]。

論文は Agda で構成し、型の universe と container によって正の再帰として表す。これは Benitoite で一般の Agda の依存型や任意の型計算を公開する必要があるという主張ではない。Heftia の公式 README と Haddock は、この精緻化を着想源に挙げ、Reader・例外・非決定性・資源の利用範囲などを扱う実装を提供する [R5]。README の他方式に対する優位性や速度の主張は、独立に検証した結果として採らない。

### 2. 権限制御での使い道

「計算の範囲」と、高水準の操作から実際の操作への対応の記録に向く。`Git.commit` を `Process.run` へ変換したとき、その対応を表示に残せる。ただし、通常の一階のハンドラによる変換にも同じ対応を記録できる。権限の表示を改善するためだけに、高階の操作を必須にはしない。

実行前の許可の照合は選択済みの精緻化の出力の効果で行い、高水準の名前は説明用の対応として添える案を推す。「Git なので Process.Run を許した」という独立の許可規則を追加すると ADR 0183 と二重になる。実行時の対象の照合と OS の上限は同じ方針から導く。

### 3. 実用の機能での使い道

再試行の方針・時間切れの方針・ログの局所変換を、実行・テスト・説明のそれぞれへ変換できる。擬似コードは後掲の例B〜Dに示す。現在の `retry(action)` は通常の高階関数として書けるが、`Retry.run` という操作を宣言すれば、呼ぶ側を変えずに「一度だけ試す」「所定の失敗を注入する」解釈へ替えられる。

探索や生成器の操作も表せるが、変換先の制御能力を超える実行は自動で得られない。現在の継続へ変換する限り、マルチショットの探索や継続を保存する生成器には別の拡張が要る。変換がインライン化できる可能性と、実行時の木の構築が増える可能性は両方ある。性能の判断は TODO-028 の測定へ残す。

### 4. 今の設計との両立

最も両立しやすいのは、精緻化後に現在の一階の `handle` と通常の関数だけを残す限定案である。ワンショット、深いハンドラ、節の外側実行を維持できる。精緻化は `State` を消せず、未知の効果変数は出力へ保持する。型付きの失敗を扱う場合も、既存の NoFail と `Failure.Fail[E]` の規則を守る。

一方、任意の計算引数を、外側の節で元の関数値として呼ぶ実装はこの案ではない。内部の計算のハンドラ文脈を含む変換を定義し、その型を検査する必要がある。タスクの継承と非再開の節の制約も変換先に残る。外部関数の実行を直接追加する精緻化は、捕捉できない効果を型に残さなければならない。ADR 0147・0117 を維持する実装範囲を選べる。

### 5. 設計原則との関係

利用者のコードを `Retry.run` の呼び出しに留め、宣言と変換を標準ライブラリの内側に閉じれば、原則4・6の負担を抑えられる。原則2・3のため、選択した変換と残る組み込み効果の変更を示す。未定義の変換、計算引数の残る効果、実際の変換先を対応づける診断が要る。同じ `with` の別構文を増やすことは、精緻化方式の必須条件ではない。

### 6. 形式化の費用

変換先の Release を変えないなら、既存の進行・保存の言明を保ち、拡張した Surface からの `desugar_typed` と `EffectsOk` の証明を増やす。ただし、新しい表層の効果署名・型付け・計算引数の束縛と置換は必要であり、小さな表示機能の変更にはならない。利用者定義の多相な高階操作まで含めると、「エフェクトを外す規則」と「型の計算」、表現次第で型と効果の相互再帰に当たり、TODO-250 の重い項目となる。

`ElaborationTyped` のような条件を単なる公理として渡すのでなく、許可する精緻化の本体を型検査するか、定義ごとに証明する。本番全体との接続と独立した小モデルを分ける。

### 7. 互換性と構成

一階の既存コードは保てる見込みである。標準ライブラリで実装を替える API の検査結果・Skill の例・生成した参照文書・交換形式には影響する。構成ごとに、精緻化の出力が存在しないモジュールを呼ぶ場合は検査で拒否する。変換の一般部から WASM・ネットワークへ直接依存させず、値や識別子の表現も64ビット専用にしない。

### 8. 学習の価値

構文木の畳み込み、代数としての解釈、合成可能な脱糖、型と実際の操作の対応を一つの小モデルで学べる。既存の実行系を使える範囲を選びやすいため、最初の試作に最も向く。

## 3. latent effects

### 1. 何を表せるか

書誌は Birthe van den Berg・Tom Schrijvers・Casper Bach Poulsen・Nicolas Wu、*Latent Effects for Reusable Language Components*、APLAS 2021、LNCS 13008、182–201頁、doi:10.1007/978-3-030-89051-3_11 である。書誌は[出版元](https://link.springer.com/chapter/10.1007/978-3-030-89051-3_11)、内容は[拡張版の本文](https://arxiv.org/pdf/2108.11155) §3–5 と付録を確認した [R6]。

この方式は、関数抽象・名前呼び・必要呼び・多段階計算など、計算をその場で実行せず後で実行する言語部品を組み合わせるための仕組みである。木に効果の状態を表す関手 `l` とその状態を保持し、後で部分計算を実行するときにも、その解釈に必要な情報を与える。通常の関数型の効果注釈に「潜在」と付けたものとは異なる。Haskell 埋め込みの型やハンドラを書く負担があり、Benitoite 用の推論器と診断をそのまま得られる論文ではない。

### 2. 権限制御での使い道

「計算の範囲」を、遅延した計算までどう解釈するかに関係する。権限を狭めた中で作った遅延計算を後で実行するとき、作成時の方針と実行時の方針をどう使うかを設計する材料になる。「誰が持つか」は、保存した解釈の状態が権限の保持を意味する場合に関わる。

ただし、論文は OS の権限や失効の仕組みを与えない。後で強い文脈へ出たことによって許可が復活しないよう、実行時の現在の方針と作成時の上限を交差させる、といった別の保証が要る。これを採用しただけで ADR 0183 の三層が揃うわけではない。

### 3. 実用の機能での使い道

評価器を、遅延・メモ化・引用と評価・例外・局所状態の部品から作る用途に向く。日常のスクリプトでは現在の `lazy` と関数値で足りる場合が多く、`Lazy` の評価自体を再解釈できる要求がなければ追加の利益は小さい。

```text
// 現行の構文に寄せた擬似コード。通常の lazy と値の明示的な受け渡し。
bind later <- lazy buildReport(config) end lazy

// 拡張案。評価の延期そのものを操作にする。
bind later <- Deferred.suspend(action: lambda() return buildReport(config) end lambda)
Deferred.force(later)
```

後者の「作成時の状態で評価するか、force 時の状態で評価するか」を変えることが追加の表現力である。テストでは計算の実行順とメモ化の回数を記録できるが、単なる記録や乱数の固定のためだけには要らない。性能には保持する状態と木の量の費用があり、未測定である。

### 4. 今の設計との両立

継続の再開回数とは独立だが、計算を後へ残すことは現行の `resume` の持ち出し禁止、`with` の解放、子タスクの寿命と衝突する。保存するものを通常の `lazy` の計算に限り、継続や生きたリソースを保持しない制限案は考えられる。任意の latent handler では、この制限が保たれる証明が必要になる。

深いハンドラ・節の外側実行を保つかは、保存する文脈の選択次第である。`State`・未知の行・外部の効果は保存状態へ移したというだけで外せない。スクリプトの権限宣言は不要だが、権能を含む保存状態を値として公開するなら ADR 0117 の見直しに当たる。

### 5. 設計原則との関係

処理系を作る人には部品の再利用という価値がある一方、一般のスクリプトでは作成時と実行時の違いが説明の負担となる。原則1・3・4のため、持ち出せる値と再実行の意味を先に限定する必要がある。原則5・6から、既存の `lazy` と重なる公開構文を最初から増やす案は推さない。

### 6. 形式化の費用

保存した計算・環境・ハンドラの状態・評価の遅延と復元を型付けし、置換・ストア・実行に接続する。エフェクトの除去と、型の変換を伴う handler carrier の計算が重なる。遅延の定理だけで資源・タスクの安全性を代用できない。Release と Surface の進行・保存・効果健全性・脱糖の型保存の拡張を要する重い項目である。安全性を公理として追加する案は推さない。

### 7. 互換性と構成

別の構文として追加するなら既存のコードを保てるが、既存の `lazy` の意味を置き換えるなら評価順・失敗・捕捉・例・テストが変わる。中核に置くならサーバや WASM に依存させず、組込み向けにも評価戦略を同じにする。64ビットのポインタ保存を仕様にしない。

### 8. 学習の価値

言語の評価戦略、環境の保存、メモ化、言語機能の合成には価値が高い。しかし、今回の権限制御とテストのための最初の題材には範囲が広い。hefty の後の学習候補とする。

## 4. Effekt のエフェクトをケーパビリティとして読む方式

### 1. 何を表せるか

Brachthäuser・Schuster・Ostermann の OOPSLA 2020 の論文は、効果型を「計算が文脈から要するケーパビリティ」と読む。関数を二級の block とし、値と別の環境で扱い、System Ξ の明示的なケーパビリティの受け渡しへ変換する。block を結果として返したりデータ構造へ保存したりしないことで、ハンドラの範囲外でケーパビリティを使うことを防ぐ。[論文拡張版](https://ps.informatik.uni-tuebingen.de/publications/brachthaeuser20effekt.pdf) §1.6、§3–6 [R7]。

公式の contextual effect polymorphism では、block 引数の効果は呼び出し位置の文脈が処理し、`map` のような関数がそのすべてを行変数で書き直す負担を減らす [R8]。ただし `/ {}` を Benitoite の `uses` なしと同じ意味で読めない。現在の文書では、計算は既定で二級であり、`box` と capture set で一級の値として扱う方法も説明する [R9–R10]。2020年の「全関数を二級に限る」体系と、現行のボックス化のある体系を区別する。

### 2. 権限制御での使い道

「誰が持つか」を、名前のあるケーパビリティを受け取る範囲として明確にできる。局所的に制限した実装を渡すことで「計算の範囲」も表せる。ただし、ファイルを扱う言語上のインターフェースへのアクセスと、OS の許可は別である。外側の強いケーパビリティを既に捕捉したコールバックへ弱いものを渡しても、その捕捉を消せない。

現在の Effekt の公式文書は、組込みの外部への作用を自由に再解釈できる通常の control effect と同じにせず、second-class resource として説明している [R10]。したがって「Effekt では File の全操作をハンドラで無条件に差し替えられる」とは扱わない。Benitoite で採る場合も、実行時の最終照合を維持し、ADR 0183 の方針を発行元と上限にする設計が要る。

### 3. 実用の機能での使い道

二つの局所状態や時計を明示的に選べるため、環境依存のコードのテストと、構文解析器・局所状態を使うアルゴリズムの合成に向く。明示的に同じインターフェースを受け取る関数レコードは現在も渡せるが、scope の外へ出ないという検査は得られない。

```text
// 現行案: 関数の値を持つレコードを渡す。捕捉や寿命は通常の値の規則に従う。
processWith(read: lambda(path) return File.readText(path) end lambda)

// 拡張案: 二級の block 引数 file を受け取り、その範囲でだけ呼ぶ。
function process(block file: FileCapability) -> Report
  ... file.readText("input.txt") ...
end function
```

後者の `block` は提案の擬似構文である。日常の自動化では、標準のファイル API をそのまま使えることが優先されるので、全呼び出しに明示的なケーパビリティを加える案は負担が大きい。2020年の論文では、二級の継続をキューへ保存できないため幅優先探索を直接書けない制約も報告する。多相性の軽さと、実装できるアルゴリズムの範囲を合わせて評価する。

### 4. 今の設計との両立

通常の一級の関数をすべて二級に変える案は、コレクション・戻り値・遅延・コールバックの契約を変える。二級 block を追加する案なら既存コードを保てる可能性があるが、二種類の関数と変換の規則が要る。capture set を追う案は、さらに型と診断を増やす。

ワンショットは維持できるが、Effekt の継続は本来マルチショットも利用するので、その例をそのまま持ち込めない。レキシカルなハンドラの選択は、現在の動的な最内ハンドラの選択からの変更である。タスクへの block の受け渡しは寿命と捕捉を別途検査する。`State` を消さず、外部の操作を残す限りで接続する案を選ぶ。ケーパビリティ値を導入するなら ADR 0117 を見直す。スクリプト自身による許可の宣言は必要なく、ADR 0147 は維持できる。

### 5. 設計原則との関係

原則1・4には、持ち出しを検査で拒否できる点と行変数を減らせる点が合う。ただし、現行の `uses` の読みに慣れた LLM と人間には誤読の危険がある。原則3のため、capture した資源も権限の表示に含める必要がある。原則5・6のため、二種類の関数を使い分ける必要がある場面を測ってから決める。

### 6. 形式化の費用

値と block の構文・型・環境、別々の置換、ケーパビリティの束縛と寿命、必要なら box と capture set、継続とストアの条件を加える。主定理の対象となる項・環境を変え、進行・保存・効果健全性・脱糖の型保存を組み直す。現行の「純粋」だけでは capture した外部資源を説明できないので、健全性の前提と保証対象も明示し直す必要がある。TODO-250 の重い項目であり、公理の追加で済ませない。

### 7. 互換性と構成

全面移行は標準ライブラリ、既存の関数値の例、テスト、Skill、形式化の交換形式へ広く影響する。追加の block に限る場合も公開 API を変える範囲の棚卸しが要る。ケーパビリティの抽象部分は中核に置き、実際の File・Http・WASM の実装は構成で外せる境界に置く。実装のポインタ幅を権能の意味に含めない。

### 8. 学習の価値

型と文脈、二級の値、非脱出、レキシカルスコープ、暗黙の引数の変換を学ぶ価値が高い。現在の保証の読み方そのものを再設計するため、最初の一つの学習試作と本番導入を同時に行う案は推さない。

## 5. 名前付きハンドラ・mask・lift・Frank の調整

### 1. 何を表せるか

これらは、操作をどの解釈へ渡すかを選ぶ仕組みである。Koka の `mask<eff>` は、そのラベルの操作を最内のハンドラから一段外へ送る。重複する効果ラベルと行でこれを表し、単なる「効果を無くす」操作ではない [R11]。Xie・Cong・Ikemori・Leijen の OOPSLA 2022 は、ハンドラ名を値として指定し、rank-2 の多相性で名前の脱出を制限する体系を示す [R12]。

この論文の scoped effects は、ハンドラ名の有効範囲を維持する仕組みを指す。§1の Wu らの「計算引数を持つ scoped operation」と、名前が同じだから同一の体系とは扱わない。Effekt は明示的なケーパビリティまたはその解決で呼ぶ先を決める [R9]。Frank は引数の port の adjustment と ambient ability で、その引数の評価中に受け取る操作を型付けし、演算子を Core Frank の関数とハンドラへ変換する [R13]。

`lift` は資料ごとに意味が違う。ハンドラを飛び越すための効果行・根拠の調整、一階の計算を高階の木へ入れる操作、Haskell のモナド変換子の `lift` を、同じ API とみなさない。注釈と診断は、宛先名の寿命、不足している外側のハンドラ、重複ラベルの段数を扱う。

### 2. 権限制御での使い道

明示的な宛先は「誰が持つか」、局所の解釈の選択は「計算の範囲」に関わる。しかし **操作の送り先を選べることは、権限の制限を強制できることではない**。通常の権限チェック用ハンドラが `mask` で飛び越せるなら、信頼しないスクリプトへの境界には使えない。名前付きの強い権能を既に持つコードにも同じ問題がある。

ADR 0183 から作る判定器を、どの宛先へ送っても実 IO の入口で適用する。範囲の狭まりは、ハンドラの探索とは独立した文脈として維持する案を推す。OS の上限を解除する操作として `mask`・`lift` を公開しない。

### 3. 実用の機能での使い道

複数の Reader、局所と共有の状態、監査用と画面用の出力、テスト用と本番用の時計を区別できる。現在は別のエフェクト名を宣言するか、節が外側で動く規則を使って転送できる。名前付きハンドラは同じインターフェースの複数の実体を、型と値で区別する点が増える。

```text
// 現行の構文に寄せた擬似コード。節は外側で動くので、二重に装飾しない。
handle
  Log.write("done")
with
  case Log.write(message) ->
    Log.write("[job] " + message)
    resume(())
end handle

// 拡張案。二つの名前付きの出力先を選ぶ。
audit.write("job completed")
screen.write("完了")
```

構文解析で二つの入力状態を区別したり、局所のヒープを持つアルゴリズムを組み合わせたりする用途にも向く。Frank の複数引数の処置は有用な比較対象だが、それだけで Benitoite に複数の継続を公開する案を推さない。性能は宛先の解決を静的にできる可能性がある一方、根拠や寿命の管理が増え、未測定である。

### 4. 今の設計との両立

名前付き方式は追加の形として設計できるが、名前の寿命と捕捉を追わない追加では範囲外の使用が残る。`mask` の重複ラベルは、集合としての現在のエフェクト表現にそのまま入らない。Frank の port と shallow な処置を取り込むなら、現在の深いハンドラの規則と区別して定める必要がある。

ワンショットは保てるが、タスクが名前や外側への段数を継承する意味を加える必要がある。`State` と未知の行は外さず、外部関数の保証も維持する。名前を権能として使う案は ADR 0117 の見直しであり、ADR 0147 の権限宣言の導入は不要である。

### 5. 設計原則との関係

明示した宛先は原則1・4の診断を明確にする。一方、`mask` の段数と入れ子の順によって意味が変わると、LLM の修正後の影響を読みにくい。原則2・3のため、方針の強制と通常の転送を別に説明する。現在の外側で動く節で済む用途には、新構文を増やさない（原則5・6）。

### 6. 形式化の費用

名前付き方式はハンドラ名・束縛・操作参照・寿命・継続の探索を Release と Surface に加える。rank-2 の範囲識別子を採れば効果に型を持たせる変更になる。`mask` は行の重複と一段の除去の法則を、現在の集合と除去の証明から組み直す。Frank の port まで採ると型と脱糖も大きく変わる。いずれも全機能の導入は重い項目であり、進行・保存・効果健全性・脱糖の型保存を拡張する。公理の追加は不要とする設計を目指す。

### 7. 互換性と構成

名前付き形式を追加する案は既存コードを保てる可能性がある。`mask` のために集合を重複行へ置き換える案は、型表示・同一性・推論・Skill の例へ影響する。中核に新しいネットワーク依存を要さず、ハンドラ名も論理的な識別子として幅から独立に表せる。

### 8. 学習の価値

動的な捕捉とレキシカルな選択、行と集合、非脱出と生成的な名前の違いを学べる。権限の強制のためには選択だけでは足りない理由も明確になる。hefty の試作と同時の導入は避ける。

## 6. マルチショットとワンショットの継続

### 1. 何を表せるか

マルチショットは、同じ捕捉済み継続を複数回再開する。Koka の公式 tour は、選択の全結果の列挙と状態との相互作用を示す [R11]。Eff の解説は、同じ `decide` の継続を真と偽で実行する最大値・列挙・バックトラックのハンドラを示す [R14]。これは一階の選択操作だけでも使う能力であり、高階エフェクトを導入することとは独立である。

Multicore OCaml の実装論文では、形式的な意味と実装の最適化を区別している。OCaml 5 の公式文書は、並行処理にはほぼワンショットで足り、スタックの複写を避けられ、線形な資源を複数回使う問題も避けられることを、マルチショットを提供しない理由として挙げる [R15]。高々一回は動的に検査し、再開されない継続の解放を自動的に保証する線形型がある、という意味ではない。

### 2. 権限制御での使い道

TODO-283 の「何回使えるか」に関係するが、マルチショットは回数制限を与える仕組みではない。むしろ承認の利用・資源の取得・監査の出力を繰り返す可能性を増やす。「計算の範囲」や「誰が持つか」の保証も追加しない。ADR 0183 の実行時の判定器は、各再開先の実際の操作にも適用する必要がある。

### 3. 実用の機能での使い道

全解探索、構文解析の曖昧性の列挙、バックトラック、確率の離散分布の厳密な列挙・重み付きの集計に向く。乱数から一回サンプリングするだけなら、現在の `Random` の差し替えで足りる。再試行は `action` を再び呼べばよく、捕捉した継続の複写を必須にしない。例Eに具体的な差を示す。

生成器は「一回ごとに一度再開する」能力で足りるものがあり、マルチショットそのものを要しない。ただし、呼び出し側へ続きを渡す pull 型の生成器は、Benitoite の現在の節の外への継続の持ち出し禁止を変える必要がある。push 型の生成は一階の操作と末尾再開で既に書ける。

### 4. 今の設計との両立

現行の消費済み継続の規則を直接変える。スタックを複写しても、捕捉した `Reference`・ファイル・タスク・WASM の resource が独立に複製されるわけではない。同じファイルの二度の close、分岐間での参照の共有、二度のプロセス起動、子タスクの所有の重複について意味を決める必要がある。

選択肢は、(a) 現行のワンショットを維持し、探索は木や明示的な再実行で書く、(b) 資源・タスク・外部呼び出しを含まない限定された探索の計算に複数再開を許す、(c) 複製できる計算を型で区別して一般化する、である。今は(a)を推す。(b)にも捕捉した値を検査する規則が要り、表面の `uses` から `State` を省いただけでは不十分である。

深いハンドラと節の外側実行は維持できるが、タスクの継承と解放をそのまま維持する保証はない。エフェクト変数・`State`・外部の効果を消さない既存の制限を緩める理由にはならない。ADR 0117・0147は変更しなくてよい。

### 5. 設計原則との関係

探索の記述は短くなるが、LLM が再実行される IO を見落とすと、原則2・3を損なう。複製できない捕捉を静的に断るなら原則1に合うものの、型と診断は増える。日常の自動化ではワンショットを既定とし、探索用の明示的な木やライブラリを使う方が原則4〜6と両立させやすい。

### 6. 形式化の費用

Release の継続ストアの消費・複写・解放・状態の型付けと、保存の証明を変える。再開回数を効果に持たせなくても、資源と継続を複製する規則の変更自体が重い。静的な区別を足せば S3 のアフィン性や線形性と重なる。Surface の許可する使用箇所と型保存も変わる。既存の健全性の前提・結論を保てるかは設計次第であり、試作前に保てると断定しない。資源の安全性の公理を増やす案は推さない。

### 7. 互換性と構成

以前エラーだった二度の再開を許すだけでも、解放の時期と既存のエラー検査が変わる。別の探索 API に限定する案の方が影響を狭められる。実装のスタック複写は特定のポインタ幅や WASM のスタックに依存させず、外部の資源を複写できると仮定しない。性能は捕捉と再開の方式に依存し、未測定である。

### 8. 学習の価値

限定継続、制御の反転、探索と状態、複製と資源の関係を学べる。高階の操作を学ぶための前提ではない。資源の規則を変える独立の重い題材として扱う。

## 7. fused-effects

### 1. 何を表せるか

`fused-effects` は高階の効果のデータ型と、意味を与える carrier を分ける。`Reader.local` と `Catch.catchError` は計算を引数にとる操作であり、内部の計算を carrier に適用する `Algebra` の処理が必要になる。利用側は `Has (Reader r) sig m` などを書き、実行側が carrier の構成を選ぶ。[公式 README](https://github.com/fused-effects/fused-effects)、[Reader の carrier](https://raw.githubusercontent.com/fused-effects/fused-effects/main/src/Control/Carrier/Reader.hs) [R18]。

資源の `bracket` と IO の例外の `catch` は、別パッケージ `fused-effects-exceptions` の `Control.Effect.Exception` が GHC の例外 API を包む。`catchError` は任意の IO の例外まで捕捉する操作ではない。注釈・型クラスの解決・carrier の選択が利用者の書く型と診断に現れる。

### 2. 権限制御での使い道

`local` に似た方針の局所化は「計算の範囲」に使える。誰が持つかは carrier の環境と公開する API の設計に依存し、`Has` の証拠だけで OS の権能を得るものではない。Benitoite へは、方針から作る判定器を内部の計算へ適用する設計を参考にできる。ADR 0183 の三層を carrier の合成だけで実現できたとはみなさない。

### 3. 実用の機能での使い道

`local` と `ask` の両方を記録する、失敗の処置を差し替える、構文解析中だけ環境を変える用途がある。現在の一階の `ask` の差し替えとの差は、範囲の入口と出口も操作として扱える点である。

既知の意味の問題は、`fused-effects-exceptions` 自身の README が説明する。値で渡す State carrier と `finally` を組み合わせると、cleanup が行った状態更新が最終結果から失われる場合があり、必要なら IORef の carrier を使うと案内している。[公式の注意と例](https://github.com/fused-effects/fused-effects-exceptions/blob/master/README.md) [R19]。これは資源の解放そのものが必ず行われないという主張とは異なる。解放の実行と、解放が変更したモデル上の状態の保持を分ける必要がある。

### 4. 今の設計との両立

carrier を Haskell のモナドの型で選ぶ実装を、そのまま Benitoite の深いハンドラへ置き換えることはできない。参考にするのは内部計算へ解釈を適用する方法と、状態と例外の相互作用である。ワンショット・節の外側実行・タスク継承は引き続き Benitoite の規則で定める。`State` や捕捉できない外部処理を外さず、権限の宣言やケーパビリティ値を追加する必要もない。

### 5. 設計原則との関係

型クラスと carrier の注釈を一般のスクリプトへ移すと原則4・6の負担になる。標準の解釈を固定すれば負担を減らせるが、解釈の順で状態の意味が変わる点を原則2・3に沿って説明する必要がある。原則5のため、`with`・`Task` の既存の入口と重ねる理由を具体化してから公開する。

### 6. 形式化の費用

調査結果を現在の関数やドキュメントに反映するだけならコアは変わらない。同等の高階操作を言語へ入れるなら§1または§2と同じ変更に加え、carrier と forwarding の法則の証明が要る。エフェクト除去と型計算の重い項目になる。`finally` の状態の扱いを公理で仮定せず、観察する結果を定義する。

### 7. 互換性と構成

Haskell ライブラリを Rust の処理系へ直接依存させる案ではない。採る操作の型によって、標準ライブラリ・例・テスト・Skill の変更量が決まる。構成と64ビットの前提を増やす理由はない。

### 8. 学習の価値

構文と carrier、ハンドラの合成、例外と状態の違いを学べる。型が通ることと、期待する状態の意味が得られることが別である実例として価値がある。

## 8. polysemy

### 1. 何を表せるか

`Sem r a` の効果の列 `r` に対して、`Reader.Local`・`Error.Catch`・`Resource.Bracket` のような計算引数を持つ操作を定義する。一階の操作の解釈と高階の `interpretH` を分け、後者は内部の計算を実行する `runT`・`bindT` などと、短絡した結果を判定する Inspector を使う。`Final` へ解釈する経路も別にある。[公式リポジトリ](https://github.com/polysemy-research/polysemy)、[Resource のソース](https://raw.githubusercontent.com/polysemy-research/polysemy/master/src/Polysemy/Resource.hs) [R20]。

利用側は `Member`・`Members` の制約、解釈側は weaving の状態と実行戦略の型を扱う。宣言の自動生成やプラグインで一部を軽くできるが、意味の選択が不要になるわけではない。

### 2. 権限制御での使い道

「計算の範囲」の要求を操作として宣言でき、記録用・実行用の解釈を切り替えられる。「誰が持つか」は通常の効果の列だけでは個別の権能の所持を表さない。IO に落とした後の操作は、その実行入口で ADR 0183 の判定器へ照合する必要がある。

### 3. 実用の機能での使い道

`bracket`・`local`・`catch` の範囲そのものをテストの対象にできる。`runResource` と `resourceToIOFinal` は別の解釈であり、後者には、IO で解釈されない他の効果が Resource に対して局所状態の意味になるとの公式の注意がある [R20]。解放の記録を State に保存するとき、その記録をどの解釈まで保持するかを決める必要がある。

`NonDet` の API が存在することと、一般のマルチショットの継続を公開することは同一ではない。`NonDet` は枝の計算を含む操作として構成される。今回の確認では、あらゆる `catch`・状態・非決定性の組み合わせについて、限定継続の意味と一致する定理は確認していない。ライブラリ間の「意味が壊れている」とする広い評価を、そのまま本調査の結論にしない。確認できた局所状態の注意を採用判断の根拠とする。

### 4. 今の設計との両立

`interpretH` の計算引数の扱いは参考になるが、Benitoite の継続を自動で複写できる根拠にはならない。ワンショット・深いハンドラ・節の外側実行・末尾再開の子タスクという既存の意味に合わせた変換を別途定める。`State` と未知の行の消去は認めず、外部の実 IO が残る解釈では残る効果も表示する。ADR 0117・0147は維持できる。

### 5. 設計原則との関係

利用側の短さには原則6上の利点がある。一方、`Final` と通常の高階解釈の違いを一般の利用者へ選ばせると、診断と結果の説明が難しくなる（原則3・4）。標準ライブラリの内側へ選択を閉じ、同じ用途の公開入口を増やさない（原則5）方が Benitoite には合う。

### 6. 形式化の費用

同じ weaving の方式を採れば、結果を包む状態の型と、短絡した結果を検査する法則を型保存へ接続する。型計算とエフェクト除去が関わる重い項目である。Release へ高階の木を入れるか Surface の精緻化で済ませるかで、主定理の変更範囲が違う。Inspector の正しさを新しい公理として加える案は推さない。

### 7. 互換性と構成

参考にして操作を追加する限りで既存コードを保てる。状態の意味を変えるなら既存のテストの期待結果をそのまま移せない。Haskell・IO・GHC を中核へ依存させる案ではなく、組込み向けと整数幅の境界を保てる。

### 8. 学習の価値

高階の操作の短絡・状態の保持・実 IO への変換の違いが学習題材になる。hefty との比較には向くが、最初の小モデルで weaving と Inspector まで再現する案は推さない。

## 9. effectful

### 1. 何を表せるか

`effectful` の `Eff` は、IO を基盤に環境を渡す具体的な表現をとる。動的な高階操作は `LocalEnv` と `localSeqUnlift` などで、呼ばれた位置の計算を解釈側へ実行する。公式の Reader の実装は `Local` を `localSeqUnlift` と `interpose` で扱う。例外 API の `bracket`・`catch` は、この基盤で Haskell の例外と資源管理を扱う。[README](https://raw.githubusercontent.com/haskell-effectful/effectful/master/README.md)、[Dynamic](https://raw.githubusercontent.com/haskell-effectful/effectful/master/effectful-core/src/Effectful/Dispatch/Dynamic.hs)、[Reader](https://raw.githubusercontent.com/haskell-effectful/effectful/master/effectful-core/src/Effectful/Reader/Dynamic.hs)、[Exception](https://raw.githubusercontent.com/haskell-effectful/effectful/master/effectful-core/src/Effectful/Exception.hs) [R21–R23]。

型の制約と static/dynamic dispatch の選択、unlift のスレッドと寿命の条件がある。unlift を範囲外や不適切なスレッドで使う誤りを、すべて静的に防ぐ体系ではない。公式ソースには実行時の検査と、非推奨の持ち上げ操作の注意がある。

### 2. 権限制御での使い道

環境を局所的に替えることは「計算の範囲」に使える。ただし、IO を実行する能力を持つ解釈へ渡しただけでは権限の限定を証明しない。Benitoite では、解釈側の実 IO にも型と ADR 0183 の方針を適用する必要がある。Haskell の IO 基盤を、中核の型から見えない外部操作の入口として移さない。

### 3. 実用の機能での使い道

通常のアプリケーションの例外・局所環境・共有状態・資源管理と接続しやすい。状態を IO 側に置くため、StateT の状態が例外によって失われる問題を避ける方針をとる。一方、公式 README は、残りの計算を捕捉して後で再開するハンドラを提供しないと明記し、全分岐を収集する NonDet と Coroutine を例に挙げる [R21]。

したがって、`bracket` が容易な方式を選べば探索と生成器も同時に容易になる、とはいえない。Benitoite の実用上の優先事項が「IO と資源の確実な後処理」なら参考になるが、現在の継続による制御を置き換える理由にはしない。公開される速度の比較は本処理系の測定ではない。

### 4. 今の設計との両立

方式全体への置換は、現在の再開と非再開による制御・深いハンドラを同じ意味で保てない。局所の計算を正しい環境へ戻す API の設計だけを参考にする。タスクを越す unlift の寿命も既存の継承規則とは別に検査する。`State`・未知の効果・外部効果を型に残し、ADR 0117・0147を維持する形は考えられる。

### 5. 設計原則との関係

資源処理の利用側が単純なのは原則6に合う。unlift の寿命を実行時の失敗に任せる設計は、検査で見つけられる範囲を先に拒否する原則1と比較が要る。原則3・4から、ライブラリの内部の環境の選択を利用者へ出さず、何が捕捉可能かを診断に示す必要がある。

### 6. 形式化の費用

IO 基盤の解釈を外部の仮定に置けば、小さく見える代わりに、今のコアの保証を移したことにならない。既存のコアで高階 API を変換する案なら§2の費用であり、effectful と同じ実行方式の証明ではない。置換する場合は実行・環境・例外・資源と主定理の再構成という重い項目になる。隠れた IO を公理で正当化する案は推さない。

### 7. 互換性と構成

全面置換は既存の継続を使うコードとテストへ影響する。一般的な環境の API の設計だけを参考にするなら影響を限定できる。実装は Rust の中核で自作し、Haskell の実行系や WASM へ依存させず、64ビットだけを前提にしない。

### 8. 学習の価値

状態を値で渡す方式と実際の可変セルに置く方式、環境の切り替え、例外と資源の関係を学べる。限定継続の学習の代替にはならず、比較対象として読む価値がある。

## 10. Unison の abilities

### 1. 何を表せるか

Unison は `ability` で要求のインターフェースを定義し、関数型の矢印に `{Store a, e}` のような要求を書き、`Request` の照合を行うハンドラで処理する。高階関数は渡す関数と呼び出し全体の両方へ ability の変数を伝える。値の通常終了を処理する節もある。[言語リファレンス](https://www.unison-lang.org/docs/language-reference/abilities-and-ability-handlers/)、[Using abilities part 1](https://www.unison-lang.org/docs/fundamentals/abilities/using-abilities-pt1/) [R24–R25]。

これだけを理由に、λsc と同じ高階の scoped handler を持つと分類しない。確認した公式資料では、`local`・`catch` 相当は遅延計算とハンドラを組み合わせる書き方として説明できるが、任意の高階操作の forwarding と健全性を定める体系は確認できなかった。ability の型引数として計算を表すことと、汎用の高階ハンドラの保証を区別する。

### 2. 権限制御での使い道

ability はまず「操作の種類」と未処理の要求を表す。特定の人や関数が持つ OS の権能を、単語の ability だけから読み取らない。計算の範囲はハンドラで囲むことで表せるが、対象の限定と実 IO の権限の強制は別途必要になる。ADR 0183 の許可の発行元と三層を省ける根拠にはならない。

### 3. 実用の機能での使い道

偽の Key-Value Store や Stream の解釈、時計・乱数の抽象化、状態と失敗を伴うコードのテストに使える。多くは現在の Benitoite の一階のハンドラと同じ利点である。公式の FAQ は、IO を要するテストに `io.test` を案内する。実 IO 全体を任意の利用者定義のハンドラで消せる、とはこの資料から判断しない。[Writing abilities](https://www.unison-lang.org/docs/fundamentals/abilities/writing-abilities/)、[FAQ](https://www.unison-lang.org/docs/fundamentals/abilities/faqs/) [R26]。

### 4. 今の設計との両立

高階関数の効果の伝播は Benitoite に既にある。FAQ には同じ ability の二重の要求を許さない制限があり、型引数だけが異なる場合も例に挙げる [R26]。名前付きの別インスタンスを自由に選べる方式と同じには扱えない。継続の回数・持ち出し・タスク・資源の振る舞いについて、今回の公式資料の確認だけで Benitoite と同一だとはいえない。

用語と利用者向けの説明を参考にする限り、深いハンドラ・外側の節・`State`・未知の行・外部関数・ADR 0117・0147の規則を変える必要はない。

### 5. 設計原則との関係

要求と処理を型に表す説明は原則3・4に参考になる。省略できる注釈と推論された要求を明確に示し、単語だけ変える追加構文を導入しない（原則5）。効果多相の高階関数が現行でも書けることを、原則6の既存の利点として扱う。

### 6. 形式化の費用

概念の説明を参考にするだけなら、コア・Surface・主定理を変えない。型を変える return 節や別の継続の規則まで移すなら、結果型・節・脱糖の型付けを変えるため別見積もりになる。今回未確認の高階の体系を、形式化費用が小さい既成の解決として数えない。

### 7. 互換性と構成

既存の一階のハンドラの設計を保ちつつ文書に生かせる。Unison のコードベース管理・分散実行・ライブラリへの移行は本作業の範囲外である。中核の依存や64ビットの前提を増やさない。

### 8. 学習の価値

操作要求・遅延計算・`Request` の型とハンドラの関係を比較する題材になる。高階の操作の追加の価値を説明するには、一階でも得られる利点を見分ける対照例として向く。

### 例A: 局所の読み取り制限

```text
// 現行案。isWithin は純粋な対象照合、denied は IOError を作る補助関数の仮名。
// 部分ハンドラなので、この関数の File.Read は残す。
function readWithin[T, effect E](root: String,
    action: function() -> T uses File.Read, E) -> T uses File.Read, E
  return handle
    action()
  with
    case File.readText(path) ->
      if isWithin(root: root, path: path) then
        // 節は外側で実行するので、ここで実際の読み取りまたは外側の偽実装へ進む。
        resume(File.readText(path))
      else
        resume(Result.Error(denied(path)))
      end if
  end handle
end function

readWithin(root: "./data", action: lambda() return importReport() end lambda)
```

この例が制限するのは `readText` だけである。File.Read に属する他の操作、すでに開いたリソース、ホスト経由の操作まで制限したことにはならない。`Scope.checkPath` の字面の検査も、シンボリックリンクを含む実際の許可の判定とは別である。完全な一階のハンドラを書く場合も、全操作を処理した後に外側で本物を呼べば、その節の `File.Read` は残る。

```text
// 拡張案。操作宣言に effect E と計算引数を許す（現在は書けない）。
effect Restrict
  function within[T, effect E](root: String,
      action: function() -> T uses E) -> T uses E
end effect

Restrict.within(root: "./data", action: lambda() return importReport() end lambda)

// 実行用の精緻化: 親の方針と root の制限を交差させ、action の間だけ設定する。
// テスト用の精緻化: 境界を記録し、偽 File の解釈の下で action を実行する。
```

`uses E` は「計算の E を保持する」契約を示す説明用の形である。高階操作自身を表す Restrict の効果も呼び出し時に生じ、精緻化で処理する。任意の E を消去する宣言ではない。実行用の方針の設定は仮の機能であり、サーバモードの前にこの形で権限制御を実装する提案ではない。

範囲の継承は呼び出しのスタックだけでなく子タスクにも必要である。方針はハンドラの宛先と独立に保持し、弱い範囲の内側から強い名前付きケーパビリティを使っても、最終の照合で親との共通部分を超えさせない。既に開いた Writer の解放を途中で禁止すると後処理を壊すので、取得時の許可で完了させる操作と新しい操作を分け、範囲を出る条件と表示を設計する必要がある。

### 例C: 時計を替えるテストと、時間切れ・再試行のテスト

```text
// 現行案。download の結果の失敗を見て retryDownload が action を再度呼ぶ。
// retryDownload は通常の関数であり、Clock.sleep を使うものとする。
handle
  retryDownload(maxAttempts: 3, action: lambda() return download() end lambda)
with
  case Clock.sleep(milliseconds) -> resume(())
  // download の各操作も偽実装へ差し替え、失敗・成功の順序を注入する。
end handle
```

現在でも、言語上の `Clock.sleep` を待たずに終え、乱数や外部操作を固定し、`Reference` に回数を記録できる。部分的な操作だけを処理した場合は効果の注釈を残す。再試行が `Result.Error` を見て動くなら、捕捉した継続の二度目の `resume` は使わない。

```text
// 現行案。Clock を差し替えても、この Task の内部の期限判定は模擬しきれない。
Task.withTimeout(milliseconds: 1000, action: lambda() return download() end lambda)

// 拡張案。境界そのものを操作として解釈する。
Deadline.withTimeout(milliseconds: 1000, action: lambda()
  return Retry.run(maxAttempts: 3, action: lambda() return download() end lambda)
end lambda)

// テスト用の解釈案:
// 仮想時間を 400ms ずつ進める失敗を二回、三回目は成功する action を使う。
// 全体の期限なら三回目の途中で取消し、各試行の期限なら三回目の成功を返す。
```

最後の二行の違いを検査するには、仮想時計とスケジューラの統合が要る。高階のテストハンドラが単に `None` を返す場合は、期限に達したときの呼ぶ側の分岐をテストできるが、実際の取消し・解放の統合をテストしたことにはならない。また、処理中の `Task.withTimeout` は `Clock.Time` と `State` を残す。前者を処理しても、後者を外して純粋な時間切れを装ってはならない。

### 例D: with の解放の順の記録

```text
// 現行案。readText や writeText の記録はハンドラでできる。

  with inner <- openInner()

  end with

```

通常の関数で明示的に `record("inner"); close(inner)` と書けば、その関数の呼ぶ順は記録できる。しかし、途中の失敗・非再開・取消しで VM が行う解放順のテストの代わりにはならない。現在の `with` の保証はそのまま使えるが、それをスクリプト内の一階の操作として再解釈する手段はない。

```text
// 拡張案。資源を使う計算の範囲を抽象化する。
Managed.withResource(acquire: lambda() return openOuter() end lambda,
  use: lambda(outer)
    return Managed.withResource(acquire: lambda() return openInner() end lambda,
      use: lambda(inner) return useBoth(outer: outer, inner: inner) end lambda)
  end lambda)

// 記録用の精緻化の観察結果案:
// acquire outer, acquire inner, use, release inner, release outer
```

実行用は既存の `with` とその解放へ変換し、記録用は偽資源の解釈へ変換する案である。両者が異常終了と取消しで同じ順を持つ保証は、精緻化と実行系の接続で確かめる。解放で実際に行う flush と送信は `State` として残す。実 VM の自動解放まで記録可能にするなら、信頼する監査の経路または解放の事象の観測を別に追加する必要がある。

## 精緻化後に型から消えた操作を実行させない条件

### 現在の保証と、追加で結ぶべき保証

docs/todo の TODO-048・213 は、ホスト操作が言語のハンドラを通らない間、その効果をハンドラで型から外さない必要を記録する。ADR 0150 の経緯も同型であり、解放を File.Write などの捕捉可能な操作と称して型から消すと、実際の flush は処理系が行ってしまうため、解放を処理できない `State` とする形で整理した。現在の規範的な根拠は 01-10「解放のエフェクト」と 07-01「各機構が保証すること」である。

ここで必要な性質は、次の三つを分けて結ぶことである。

1. **精緻化の型保存**: 元の計算と、選択した精緻化の契約から、変換先の計算の型と残る効果を導く。未知の E と、返す関数・遅延値の内部の効果を保持する。
2. **変換先の効果と実際の操作の対応**: 捕捉可能とした操作は、既存のハンドラが捕捉できる経路だけで実行する。捕捉できない処理は `State` または該当する残る効果として明記し、処理したことにしない。
3. **方針の強制と説明の一致**: 実際の対象・回数・有効な方針は実行入口で照合する。利用者に示した精緻化・型・出典対応と実行する成果物を一致させる。型保存だけでは、表示する説明の正しさまでは導けない。

現行の Lean のエフェクト健全性は純粋な計算の無事象性を述べる。`State` だけを持つ計算が、既存リソースの解放により書き出す例は現在の保証が明示的に認める。したがって「File.Write が型にないなら、解放による書き込みも一切ない」という新しい主張を、既存の定理から導いたことにはできない。権限の表示には、取得済み資源の後処理が何を完了させるかも示す必要がある。

### 方式別の防止策

| 方式 | 誤った消去を防ぐ設計条件 | それだけでは証明されない部分 |
|---|---|---|
| scoped effects | 範囲内計算と後続の効果を別に型付けする。節・forwarding の残る効果を検査し、型保存を証明する | 実行系が一部をハンドラ外で行う場合の対応、解放・タスク・ホスト呼び出し |
| hefty algebras | 精緻化本体を型検査し、出力の効果に基づいて実行前の照合を行う。操作を直接 IO 呼び出しへ展開する抜け道を作らない | 出典対応の表示、選んだ変換の同一性、変換先の組込みの実装の正しさ |
| latent effects | 保存する計算・環境・状態の型に必要な効果と寿命を残す。保存したから処理済みとみなさない | 後の実行時の方針、失効、解放済みの資源とスケジューラ |
| Effekt | block の非脱出または capture set を検査する。外部資源を要求する capture も純粋性・権限の説明で追う | 捕捉した権能の対象範囲、OS の許可、方針を狭めた後の行使 |
| 名前付き・mask・lift | 宛先と残る行を検査する。方針の照合を飛び越せない実 IO の入口に置く | 正しい宛先に送ったことだけでは、送った操作の対象が許可内とはいえない |
| マルチショット | 複製できる捕捉を区別し、各再開時の外部操作を照合する。監査と承認を暗黙に複製しない | 再実行された処理の冪等性、共有資源の安全性、外部操作の巻き戻し |
| fused-effects・polysemy | 内部計算への carrier・weaving の適用を検査し、短絡・cleanup の観察結果を法則で定める | Haskell の IO と通常の効果が同じ経路を通る保証、状態と cleanup の期待する意味 |
| effectful | 環境の復元、unlift の寿命とスレッドの条件、実 IO の残る効果を明示する | IO 基盤であること自体は Benitoite の効果健全性の証明にならない |
| Unison から説明を参考にする案 | 関数の効果の伝播とハンドラの消去を現行どおり検査する | 未確認の汎用の高階 forwarding の保証は採らない |

### 選択した精緻化の変更とテストの意味

実行用に `Deadline` を `Task.withTimeout` へ変える解釈を選んだなら、`Clock.Time` と `State` を結果に残す。テスト用に決められた値へ変える解釈なら、その値へ変える際に実際に使う効果だけを残す。両方が同じ効果型でなければならないと決める必要はないが、実行用の型を偽の解釈で検査して本物を走らせる形は拒否する。

失敗の注入で「解放すべき資源を作らない」偽実装を使うテストと、本物の `with` の取消し時の解放を調べるテストも別に扱う。前者だけを根拠に、実行用の解放と取消しの統合の正しさを宣言しない。Haskell の既知の注意は、この区別が型の正しさと別に必要であることを示す材料になる。

## Lean の小モデルの試作案と見積もり

### 推す試作の範囲

**固定した Reader の局所化を、hefty 型の高階の木から一階の操作とハンドラへ精緻化する独立モデル**を推す。TODO-142 の試作と同様、`import Std` だけの独立ファイルとし、`formal/` の本番の定義を変えない。今回は試作案の調査だけであり、Lean のコードもビルドも作成・実行していない。

最初の構文は、戻す値の型を Unit・Boolean・Nat の小さな集合に限り、一階の `ask`・`emit` と、高階の `local(n, body)` を持つ。`body` と後続を構文上で別に持つ。効果は有限の `Ask`・`Emit` と、保存すべき未解釈の一階の操作を一つだけ用意する。任意の型ラムダ、任意の高階署名、行変数、参照セル、継続値、タスク、外部関数、解放は入れない。これは hefty algebras 全体の形式化ではなく、その精緻化の構造を学ぶ部分モデルである。

変換先は、一階の操作・順次実行・Reader のハンドラを持つ小さな構文とする。`local(n, body)` は、body の `ask` だけを n で処理する計算へ変換し、後続は同じ処理の中へ入れない。木を畳み込む順序、型の異なる部分計算を表す方法、Lean の正の再帰の制約が初期の難所になる。

証明する候補を次のように限定する。

| 定義・定理の候補 | 個数の目安 | 確かめること |
|---|---:|---|
| 値の型、元の構文、変換先の構文、効果集合、二つの評価、精緻化 | 7〜10定義群 | 内部と後続の区別を構文に保持する |
| 順次実行と畳み込みの法則 | 4〜8補題 | `local` の範囲が後続まで延びない。部分計算の変換順を変えない |
| 型保存と残るエフェクト | 4〜8補題 | 変換後の結果型が一致し、`Emit` と未知の操作を消さない |
| 評価と trace の一致 | 4〜8補題 | 元の評価と精緻化後の評価で値と記録が一致する |
| 異なる変換の比較と誤った消去の反例 | 3〜6例 | 実行用と記録用の変換の違い、後続まで `local` を適用する誤り、`emit` を隠す誤りを区別できる |

「残る効果なしなら実 IO なし」の最小の類似物として、Emit を外した型を持つ閉じた計算の trace が空であることを示す。ただし、純粋な木の評価ではすべての関数がホストの IO をしない前提が既にある。この結果を、Benitoite の VM・WASM・解放・OS の保証に読み替えない。

## 統合の担当への申し送り

- **推す案**: hefty 型の精緻化の小モデルを先に試す。固定した `local` と残る `Emit` を使い、内部と後続の範囲、型保存、残る効果、trace の一致を調べる。成功しても一般の高階エフェクトの採用を自動では決めない。
- **推す案**: 0.0.13 の候補を選ぶなら、少数の標準の高階操作を既存の一階コアへ精緻化する限定案と、利用者が自由に署名を定義する一般案を別に判断する。標準だけの案でも、実用上の差し替えの価値は得られる。
- **推す案**: ワンショット・深いハンドラ・節の外側実行・`State` の非処理・未知の行の保持を既定として保つ。`with`・`Task` を高階操作で包んでも、この保証を勝手に弱めない。
- **推す案**: 権限の最終照合は、普通のハンドラの選択と独立させる。方針の共通部分、子への継承、取得済み資源の後処理、実行前の説明と実行成果物の同一性をサーバモードの設計に含める。ADR 0183 の一つの方針と、サーバモードより前に権限制御だけを入れない決定を維持する。
- **推さない案**: 権限の表示をよくすることだけを理由に、高階エフェクトを必須とする。高水準と実 IO の対応の記録は、一階のハンドラのままでも追加できる。
- **推さない案**: `Clock` の一部を差し替えただけで実際の時間切れを仮想化したと扱う、Managed の偽解釈だけで VM の解放順を検証したと扱う、または `State` を消して純粋とする。
- **推さない案**: Effekt への全面移行、一般の latent effects、資源を含むマルチショット、重複行の mask を最初の一つの改造へまとめる。いずれも別の型と実行の問題を持つ。
- **判断に要る未確認の事実**: 本番の Surface の型付けで、限定した高階署名の計算引数をどこまで追加推論できるか。最小の変更で精緻化後の `EffectsOk` と出典対応を検査できるか。Lean の小モデルと処理系の試作で確認する必要がある。
- **判断に要る未確認の事実**: `Deadline` の仮想時間を VM のタイマーへ接続する API と、外部関数実行中の取消しの範囲。`Managed` の記録で本物の自動解放をどこまで観測できるか。今回の調査では実装・実測をしていない。
- **判断に要る未確認の事実**: 一般の latent effects と、現在の `with`・タスク・型付きの失敗との接続。Unison の任意の高階操作の forwarding と健全性。Haskell ライブラリの全組み合わせの意味の一致。未確認のまま「安全」または「不可能」と断定しない。
- **S2との重なり**: CheckedPath の適合と許可の違い、権能の発行と縮小、外側の強い権能の捕捉、パスの実対象の照合。範囲の型を導入しなくても計算の範囲を狭める API は作れるが、対象の静的な保証は得られない。
- **S3との重なり**: 継続・承認・リソースの複製、一度だけの行使、非脱出、局所の破壊的更新。高階という分類から、アフィン性や非干渉を導かない。秘密の流れを追う時期は変更しない。
- **S4へ返す判断**: 学習試作だけを行うか、標準の限定された高階操作まで次の実装候補とするか。後者なら、最初の題材を `local`・再試行・時間切れ・資源のどれにするか。時間切れと資源は実行系の追加作業も必要なので、型保存の見積もりだけで採否を決めない。
