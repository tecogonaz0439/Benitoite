## 前提と調査の範囲

本書で新しく使う `scope R: Path`・`scope R: Endpoint` は範囲パラメータを表す構文案である。`scope` は新たな構文上の区別の案であり、既存のキーワードではない。Path と Endpoint は標準の対象の種類を指定するこの位置の名前で、一般の値型ではない。Endpoint はホスト名または IPv4/IPv6 とポートの組を指す。型パラメータ `T`、行パラメータ `effect E` と区別する。名前と表記の最終決定は Q9 の採否の後に行う。

## 三案の比較

| 案 | 利用者が新しく書ける契約 | 範囲の意味と実 IO の上限 | 名前全体の処理・行多相 | 主な制限 |
|---|---|---|---|---|
| (a) 標準の範囲引数だけ | 一つの利用者エフェクトの操作を、異なる標準対象の範囲に具体化できる | 操作に渡す認定された対象値が R 内である。実 IO は節自身の標準 IO の行で別に追う | 同名の全範囲を一節群で処理する。行 E は原子と範囲を保つが、E の内部から名前を除かない | 型引数なし。最小案は対象種類一つ・範囲引数一つ。R は操作の認定値引数に限る |
| (b) 型引数と標準の範囲引数 | 型 T と範囲 R を操作間で共有できる | (a) と同じ。型の引数を加えてもハンドラの IO を R 内に制限したことにはならない | 名前全体を除くなら T の全具体化も処理する。型/行/範囲の代入が要る | 型と範囲の束縛、剛な型、型の中の行と正規化まで一般化する |
| (c) 利用者エフェクトは現状のまま | 標準の範囲型を、固定の範囲の操作引数として使う | ハンドラの節の範囲付き IO から外側の上限を得る | 現在の全操作処理と行多相を維持する | エフェクト名に範囲は表示されず、任意の R を一宣言で抽象化できない |

### (a) 標準対象の範囲引数だけを持たせる

最小の案は、一つの宣言に Path または Endpoint の範囲パラメータを一つ認めるものである。エフェクト自体の型パラメータは加えない。次は新構文を含む `.bnt` の案であり、実行していない。操作はエフェクトを宣言するモジュールの関数なので、このモジュール内では `write` と呼ぶ。

```bnt
import Benitoite.Unofficial.Scope
import Benitoite.Unofficial.IO.File

effect Report[scope R: Path]
  function write(path: Scope.PathIn[R], text: String) -> Result[Unit, IOError]
end effect

function save(path: Scope.PathIn["/data/reports/**"], text: String) -> Result[Unit, IOError] uses Report["/data/reports/**"]
  return write(path: path, text: text)
end function

function saveToFile(path: Scope.PathIn["/data/reports/**"], text: String) -> Result[Unit, IOError] uses File.Write["/data/reports/**"]
  return handle
    save(path: path, text: text)
  with
    case write(path, text) ->
      resume(File.writeTextIn(path: path, text: text))
  end handle
end function
```

`Scope.PathIn[R]` の R は宣言内だけで束縛した範囲パラメータである。通常の関数宣言に独立した範囲多相を増やさず、呼び出しでは認定された入力の添字から閉じた R を決める。単なる String を渡して R への所属を推測する方式にはしない。操作自身の既存の型パラメータは使えるが、R と型パラメータを同じ引数列の種類として解釈しない。

Endpoint の場合は、たとえば `effect Fetch[scope R: Endpoint]` に `function send(request: Http.RequestIn[R]) -> Result[Http.Response, NetworkError]` を宣言する。具体化する行は `uses Fetch["192.168.1.0/24", 80]` となる。宣言内の RequestIn[R] はホスト/IP とポートの一組をまとめて束縛する書き方の案であり、値型へ複数の範囲を認める変更ではない。範囲の具体化を複数並べる略記は A1 と同じ原子列へ展開できる。二番目以降の引数付き参照をモジュールで修飾する既存の規則も保つ。

操作の範囲に意味を与えるため、最小案では各操作にその R を持つ PathIn または RequestIn の値引数を一箇所要求する。R が操作の戻り型、List などの内部、高階の引数・結果の中に現れる形は初段で認めない。たとえば `function choose() -> Scope.PathIn[R]` は範囲付き操作として宣言できない。この制限なら呼び出し側の R から節側の上限 S へ同じ値の所属を移し、操作の結果型は同じに保てる。対象のない操作へ形だけ R を付ける宣言、複数の対象・範囲の組、結果に R を返す一般の範囲多相は別の拡張になる。

この範囲が約束するのは、渡す認定対象と操作の効果原子の添字の対応である。宣言の整形式の検査と、呼び出しの型検査がこの約束を守らせる。利用者操作には実 IO がないため、`Report[R]` だけから「節のすべての IO が R 内」を導くことはできない。節が `/tmp/log/**` へ追加で書けば File.Write["/tmp/log/**"] を外側へ加える。Report を処理する前後で、実 IO の根拠を Report の範囲だけに置き換えない。

名前全体のハンドラも維持する。全操作の節があれば、Report のすべての範囲の原子を取り除く。節を R の値で実行時に選別せず、操作名の同一性で選ぶ。節の引数には Q8 と同じ規則を使い、保護本体の同名原子が一つならその S、複数・Top・未確定の行変数なら Top を与える。上の saveToFile は一原子なので狭い S のまま転送できる。二つの異なる範囲を使う本体なら節の入力が Top になり、同じ転送でも外側が File.Write の Top になる。受け取った値を節内で固定の範囲へ再検査すれば、その成功の枝だけは狭い IO にできる。

形式化では、呼び出し側の `opSigAt(o,R)` と節側の `opSigAt(o,S)` を分け、同じ値の R 所属と R の S への被覆から S 所属を導く。結果に R が現れない制限により resume の入力型は変えない。複数原子を常に Top とする保守性は、独自の範囲集合を新しく解く費用を避けるためである。宣言表に認定する対象の引数位置を保持し、具体化した署名と実行時の引数列まで同じ位置を追う。辞書を前置する操作では利用者に見える位置とコアの位置を対応させる。R→Sへ移すのはその認定位置だけで、操作自身の型引数Tや他の引数の潜在エフェクト、別の範囲は書き換えない。ただし操作が第一級の関数値になった場合、部分ハンドラ、未処理の利用者操作、継続・ストアでもこの対応を保存する証明は新しく要る。

精度を高める別案は、節を任意の剛な R の下で検査し、節の IO を本体に現れる各 R に具体化して合併する方式である。これは一般の範囲の束縛・代入と節のエフェクトの具体化を加える。最小案 (a) の費用には含めず、Q9 を採る場合でも次の検討に分ける。範囲を値で選別して一部だけ処理する方式は、名前全体のハンドラという決定も変えるため比較の本体から外す。

行の多相は `Report[R]` を含む行全体を E に渡せる。たとえば既存の `function twice[effect E](act: function() -> Unit uses E) -> Unit uses E` は、そのまま使える。E の一部から Report だけを取り除くことは引き続きできない。範囲パラメータは原子の引数、行パラメータは原子集合全体の束縛なので、行多相だけで宣言の範囲パラメータの束縛・代入を済ませたことにはならない。

### (b) 型引数と範囲引数の両方を持たせる

一般の案は、宣言の型パラメータを操作間で共有する。値型パラメータを認め、型構成子パラメータ・利用者の型関数・一般の値依存型までは加えない。R の位置と対象種類は (a) の制限を保った場合を見積もる。

```bnt
// 案。import は (a) と同じ。効果宣言の型引数と範囲引数を増やす。
effect Store[T, scope R: Path]
  function lookup(path: Scope.PathIn[R], fallback: T) -> T
  function put(path: Scope.PathIn[R], value: T) -> Unit
end effect

function setting(path: Scope.PathIn["/data/settings/**"], fallback: String) -> String uses Store[String, "/data/settings/**"]
  return lookup(path: path, fallback: fallback)
end function

// T のどの具体化でも扱える、保存しないハンドラの例。
function ignoreStore(path: Scope.PathIn["/data/settings/**"], fallback: String) -> String
  return handle
    setting(path: path, fallback: fallback)
  with
    case lookup(path, fallback) -> resume(fallback)
    case put(path, value) -> resume(())
  end handle
end function
```

現在の `function lookup[T](...) -> T` の T は操作ごとの全称型である。(b) は `Store[String,R]` のように一つの効果の型引数を具体化し、lookup と put の署名の T に同じ型を使う。この共有は現行の独立した操作型パラメータでは表せない。

名前全体を処理する決定を保つなら、一つの Store ハンドラはすべての T と R の具体化を処理しなければならない。節では T を剛な型として検査する。上の例は受け取った fallback をそのまま返すため任意の T で成立するが、String を作って任意の T として再開する節は拒否する。特定の String 用キャッシュから lookup の結果を返すような節は、この名前全体の規則では書けない。`Store[String,R]` だけを処理して他の T を残す方式は、効果の具体化を選ぶハンドラという別の設計になる。

効果の包含では T の構造の等号を要求し、R についてだけ被覆を使う。型引数 T の内部には関数の潜在エフェクトが入りうるため、型と行の代入・自由変数・正規化・継続とストアを同時に読む必要がある。同名でもTが異なる複数原子なら、節のS選択は一原子とはみなさずTopにする。型の等号を意味的な範囲の相互包含へ変えない。Failure.Fail の専用の失敗成分と NoFail の規則を、利用者エフェクトの一般的な除去規則として流用しない。

(a) と同様、範囲が約束するのは認定対象の所属であり、節自身の IO は外へ残る。行 E は Store[T,R] を含む行を保持し、E から Store の一部を差し引けない。(b) も範囲を節内の全称変数として保つ高度な具体化は含めない。

### (c) 利用者エフェクトは今のままにする

(c) は標準の範囲型だけを導入し、利用者エフェクトの宣言・名前・除去の規則を変えない。次は PathIn と *In の追加だけを前提にした例である。利用者エフェクトを引数化する新構文は含まない。

```bnt
// 案。import は (a) と同じ。
effect Report
  function write(path: Scope.PathIn["/data/reports/**"], text: String) -> Result[Unit, IOError]
end effect

function save(path: Scope.PathIn["/data/reports/**"], text: String) -> Result[Unit, IOError] uses Report
  return write(path: path, text: text)
end function

function saveToFile(path: Scope.PathIn["/data/reports/**"], text: String) -> Result[Unit, IOError] uses File.Write["/data/reports/**"]
  return handle
    save(path: path, text: text)
  with
    case write(path, text) ->
      resume(File.writeTextIn(path: path, text: text))
  end handle
end function
```

操作の通常の引数型に固定の PathIn を使うことは、0.0.13 の標準範囲型を一般の型位置で使用できる設計の範囲である。引数の所属はその型が担保する。Report 自体には範囲が現れず、操作宣言を読むまで対象が分からない。一つの Report 宣言を任意の R に具体化できず、異なる固定範囲ごとに宣言を分けるか、裸の PathIn と節内の再検査を使う必要がある。

この例の最終的な上限は File.Write["/data/reports/**"] になる。Report の範囲引数がなくても、実 IO の範囲が型から分からないわけではない。節が引数を無視して別のパスへ書けば、その File.Write の範囲が外側へ残る。単なる String を受ける操作では、Report の名前へ対象を自動記録しない。現在の全操作の節、操作自身の剛な型パラメータ、行 E を除かない規則を保つ。

通常の関数へ PathIn を渡し、File.Write[R] の閉じた契約を明示する方法も使える。操作の差し替えが要らないライブラリは、この方法で利用者エフェクトを新しく宣言せずに範囲の上限を提供できる。

## 権限の表示で何が得られるか

範囲引数を加えても、処理済みのライブラリのエフェクト名は main の型から消える。三案とも全操作の節があると名前を除き、main に未処理の利用者エフェクトを残せない規則を保つためである。docs/todo の TODO-054 の 1（`Git.Commit` を処理すると `Process.Run` だけが残る問題）は、(a)・(b) だけでは解決しない。型検査器の E0506 と、名前全体の除去を変えずに「利用者エフェクトの範囲が権限の許可項目へ残る」とは約束できない。

(a)・(b) の価値は、ハンドラで処理する前のライブラリ契約に対象の上限を表示し、同じエフェクト宣言を複数の範囲で再利用できることである。(c) の型にも最終の標準 IO の上限は残る。この差と、どのライブラリの要求を実現する IO かという説明の差を分ける。

docs/todo の TODO-287 の「精緻化と権限の表示」は、`Git.commit → Process.run` のような対応を表示の由来として残す方向である。これを範囲付き IO に合わせれば、「Report.write を File.writeTextIn で実現し、外側の上限は File.Write[R]」と説明できる見込みがある。処理済みのラベルを実 IO の許可として復活させず、既存の上限へ説明を関連付ける。この方向は (c) でも有用である。

ただし、SH2 の小モデルは本番の束縛・継続ストア・推論・脱糖へ未接続である（README「試作 SH2 の結果」）。実行時の分岐、高階の値、任意の手書きハンドラを含む由来を完全に復元できるとは確認していない。0.0.13 の機械向け表示に将来の任意の由来欄を追加できる境界を保つことと、精緻化の本実装や由来解析を行うことは分ける。見積もりに後者は加えない。

## 推す案と理由

0.0.13 は (c) とし、将来の (a) のための境界点検だけを行う案を推す。標準の範囲付き IO と固定範囲の操作引数により、実 IO の対象の上限は得られる。一方、(a)・(b) を入れても処理済みの名前は main から消えるため、権限の表示にライブラリ名を残す目的への寄与は、費用に比べて限られる。精緻化の由来を表示する方向は別に検討できる。

(a) はライブラリの同じ宣言を範囲ごとに再利用する価値があるので、不要と結論しない。しかし、今回の最小案でも範囲の束縛と名前全体の除去を一般化し、48〜106時間の追加を見込む。既に重い標準範囲の本番接続へ重ねる前に、独立した小モデルと固定範囲での利用経験を根拠に採否を決めるのが妥当である。(b) は特定のTだけを処理できない制限もあるので、型引数を足すことの具体的な用途とハンドラの単位を別に確かめてから選ぶ。
