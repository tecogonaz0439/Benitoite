# IFC-D4: File の入力を分類する単位と精度の案

2026-10-27、IF10.03。設計者が選ぶための判断案であり、採択済みの決定でも、実装・証明の完了報告でもない。

## 決めることと既に決まっている境界

IFC-D4 で決めるのは、File の入力分類を読み取り操作とその対象範囲に結び付く入力契約の単位で定め、実対象との対応を認定できる入力だけを精密に扱って一般の読み取りは秘密の結びとし、パスの字面の非交差から公開を導かずサーバ前に `{secrets}` の実行時拒否を加えないか、すべてを保守的に扱うか、字面だけの分類に保証を限るかである。

[README の版の割り振りと方式](../README.md#設計者の決定2026-10-27版の割り振りと情報フロー制御の方式)、P1〜P6、[判断14](../decisions.md#判断-14-保証と後の宛先の契約)・[判断19](../decisions.md#判断-19-情報フロー制御の方式と今回の成果物)・[判断21](../decisions.md#判断-21-実装と提供の境界)を前提にする。0.0.13 は判断案・棚卸し・契約の設計、0.0.14 は情報フロー制御（information-flow control）の独立した実装、その後は必要な接続とサーバモードである。内部の判定と Lean の証明に汎用の束を使い、最初は管理者が定める有限の束、機密性と完全性、用途を限った非機密化（declassification）とエンドースメント（endorsement。信頼の付与、または完全性レベルの引き上げ）、一階の印の要約を扱う決定は戻さない。

[IFC-D2 の案A](../if10.01/ifc-d2.md)と[IFC-D3 の案A](../if10.02/ifc-d3.md)を仮の前提とする。どちらも設計者はまだ選んでいない。D2案Aでは、起動側が同じ方針・契約と検査済み成果物を保護する前提の下で、対応する逐次計算を静的に検査する。D3案Aでは、固定 API の許した要求由来の値・成否・呼出条件だけを緩め、他の捕捉・条件・本文の秘密を保持する。両文書の申し送りに従い、一般読み取りに残る他の秘密を認証だけの契約で消さない。別案が選ばれた場合の差は後掲の表に分ける。

[00-01「保証の範囲」](../../../design/00-overview/00-01-goals.md#保証の範囲)と[07-01「脅威モデル」](../../../design/07-quality/07-01-security-model.md#脅威モデル)は、外部入力・LLM・スクリプトを信頼せず、静的検査、実行時の権限制御、OS の隔離を分けている。セキュリティ型システム（security type system）は秘密らしい内容を自動発見する仕組みでも、外部入力の正しさを証明する仕組みでもない。入力の分類が妥当であるという信頼条件と、その分類を派生値・制御・出口まで失わないという検査の義務を分ける。

## 推す案と二つの代案

案Aは「認定できる入力契約だけ精密化」、案Bは「File の入力をすべて秘密の結び」、案Cは「パスの字面で分類」とする。[元の問いD4](../study/questions.md#0013-の中で決めること設計の判断として文書にするもの)の三案を具体化したものである。案Bは、File に対して案Aの精密化の例外を設けない比較案とする。専用の秘密取得や File 以外の入力の扱いはD6等の判断に残る。

| 比較する点 | 案A: 認定できる入力契約だけ精密化（推す） | 案B: File の入力をすべて秘密の結び | 案C: パスの字面で分類 |
|---|---|---|---|
| 入力を分類する単位 | 解決済みの読み取り操作、対象範囲、入力契約の識別と版を組にする。実対象と返る情報の分類を契約で認定できる場合だけ精密化する | 操作ごとの値・成否は追うが、File の入力には共通の保守的な機密性を与える。公開範囲を精密化しない | 正規化したパスの字面と登録したパターンを照合する。秘密の登録に交差しない字面は公開とする |
| 精密と保守的の境界 | 対象候補の分類をすべて覆うと認定できる契約は、その分類の結びとする。認定できない一般読み取りは、ありうるファイルの秘密の分類すべての結びとする | 認定済みの公開 CSV も機密報告も同じ結び。対象が一つに見えても精密化しない | 字面が既知なら分類を選び、未知のパスは全分類の結び。リンク先や差し替えによる別の分類は追わない |
| 0.0.14 で保証すること | 同じ方針・契約・実入力との対応を前提に、分類された内容・派生値・制御の禁止フローを静的に拒否する。成否・誤り・停止への依存も契約に含む。認定不能を公開にしない | 分類の網羅性を前提に、File 由来の禁止フローを保守的に拒否する。精密な公開入力のための実対象の認定に依存しない | 字面から割り当てた印に対する規則への適合だけ。実対象が別の秘密である場合の保護は、この印付けから導けない |
| 保証しないこと | 入力契約の真実性、意図、IO の成功、停止、時間・資源使用量の差、外部コマンドの独立した IO、許した受け手の再配布。サーバ前の隔離と方針保護自体も提供しない | 案Aの共通の限界が残る。全分類の結びでも方針外の秘密を自動発見せず、検査外の読み取りを隔離しない | 案Aの共通の限界に加え、字面上は公開でも実際には秘密を読む経路の保護を保証しない。D2案Aの説明と受理表をそのまま使えない |
| 完全性 | 外部で変更されうる入力は未信頼。機密性を精密化しても信頼を付与しない。用途を限る別契約でのみエンドースメントする | 同じく未信頼。機密性が厳しいことは完全性の保証ではない | 同じく未信頼。公開パスとの一致を信頼する設定や命令である根拠にしない |
| 実行時の拒否との関係 | 一般読み取りを秘密に分類し、許さない出口への流れを静的に拒否する。`{secrets}` への一般アクセスを実行時に拒否する機能はサーバ前に加えない | 案Aと同じ順序。厳しい印を付けることと、読み取り操作そのものを実行時に止めることを分ける | 実行時に実対象を照合しない。その不足を秘密アクセスの実行時拒否で埋めるなら、この案の費用と既存決定を見直す別の選択になる |
| 利用者への説明案 | 「この入力は承認した契約の範囲で公開または指定の秘密として扱う。普通のファイル読み取りは秘密を含む可能性を残すため、表示や送信を断ることがある。公開データであることと、内容を信頼できることは別である」 | 「File から読む情報はすべて秘密を含む可能性があるものとして扱う。公開 CSV の集計表示も、そのままでは通らない」 | 「入力パスの字面で分類する。公開用の名前が実際に秘密を指す場合は保護できない」。ファイルの内容全体を保護する説明はできない |
| 後の版への影響 | 同じ秘密登録から内容の分類と実アクセスの除外を導き、サーバで実対象の強制・拒否・承認へ接続する。認定対象を増やすときは契約と証拠を追加する | 公開 File 入力を通すには、後で精密化を追加して契約と受理表を改める。サーバ化だけで結びを下げない | 実対象に基づく方式へ直すと、既に公開として通した出力を拒否しうる。最初の受理例と保証を改めて照合する必要がある |
| IFC-D2・D3への依存 | D2案Aの前提付き静的保証を使う。D3の限定契約でも、入力に残る他の秘密・pc・未信頼性は保つ | D2の保証範囲は同じ。D3では全分類の結びが認証以外も含むため、件数表示・機密ファイル送信の拒否が増えうる | D2で意図した秘密の保護を字面に限定する再判断が必要。D3の限定契約は、入力で失った依存を復元できない |
| IFC-D5〜D9への依存 | D5のR全体への被覆、D6の印を保つ取得・取り出し、D7の信頼条件の説明、D8の必須例、D9の同じ方針の所有と版に接続する | 同じ義務が残る。D8でFile経由の公開 CSV を必須にする場合は整合しないため、例か案の再選択が必要 | 同じ義務は残るが、D5以降の出口の検査だけでは入力誤分類を補えない。D7・D8・D9に保証の縮小を明示する必要がある |
| 費用の見込みと根拠 | 案G全体はLean 154〜374時間・処理系等182〜420時間という既存見込み。入力契約と宛先上限の共通接続はLean 6〜16時間・処理系等8〜20時間、方針の入力・版・分類・キャッシュは4〜10時間・10〜24時間という内数がある。D4単独の費用と入力の認定・運用費は不明 | File の精密化の定義・承認・実対象との対応の点検は減るが、保守的な分類・成否・pc・出口の検査は残る。共通接続も残るため、上記の行を丸ごと引けない。削減幅と合計は不明 | 字面照合の実装は限定できるが、保証の縮小の説明・後の再設計・受理表の見直しが要る。費用の増減と合計は不明。実対象の同定やOSの強制を小さい追加費用と仮定しない |

費用は [synthesis「大きさの見込み」](../study/synthesis.md#大きさの見込み)、[S6「規模の見積もり」](../study/information-flow-generality.md#規模の見積もり)、[S5 §8.2](../study/information-flow.md#82-見積もりの根拠と対象)に基づく。未実装の能動時間の見込みであり、実測でもD4の予算でもない。サーバの保存・承認、OS の実対象の保証の全実装、一般のTask・Process・WASM接続、検査・測定の実時間とレビュー・回答待ちは含まない。本枝の文書作成の見込み0.5〜1時間と混同しない。

## 案Aの入力契約と認定の条件

入力の分類はファイル名だけにも、返る文字列の型だけにも結び付けない。範囲付きの値が示すのは、正規化したAPI上の対象の上限である。その範囲から実際に得られる情報の分類を絞れる根拠を、別の入力契約で与える案とする。[S6「ファイルの分類」](../study/information-flow-generality.md#ファイルの分類f3-2)が示す専用の取得口・用意された入力データ・起動側の隔離は、その根拠の候補である。

| 契約の項目 | 案Aで求める内容 |
|---|---|
| 同一性と適用範囲 | 読み取り操作の解決済み識別、契約の識別と版、対象範囲、相対パスの基準、分類を返す情報の種類を定める。同名の関数・模擬ハンドラへ契約を移さない |
| 実入力との対応 | 契約で指定した分類の入力を実際に渡す者と、その根拠を示す。リンク・別名・差し替え、途中のパス要素の変更、保存後の再読、特殊なファイルをどう除外または包含するかを定める。字面の検査成功だけでは認定しない |
| 機密性 | 内容だけでなく、長さ・件数・存在・名前・メタデータ・成否・誤り文言・停止で分かる情報を分類する。重なる秘密の指定はすべて課し、一つの指定を優先して他を消さない |
| 完全性と用途 | 内容が公開でも、外部で変更されうるなら未信頼を保つ。書式の解析成功や範囲への所属を理由に信頼する操作の選択へ使わせない。信頼を付与する場合は用途と条件を限る別のエンドースメント契約が要る |
| 値と成否の関係 | 本文だけ公開と認定し、誤りや存在について根拠がなければ、その情報は秘密のまま保持する。成功時だけ後続が走る条件も追う。公開の集計表示を目指す契約では、後続を変える成否と停止も含めて接続を閉じる |
| 所有・変更と適用不能 | 信頼する起動側が、承認した同じ方針・契約と分類済み入力を渡す。対応を示せない呼び出しは一般読み取りの結びへ戻すか、未対応として静的に拒否する。契約を公開へ緩めたり差し替えたりする変更はD7・D9の承認と再検査へ渡す |

サーバ前の具体的な受理候補としては、信頼する起動側が読み取り済みのデータを用意し、内容と成否を含む契約を付け、スクリプトがその契約を任意のパス文字列へ付け直せない形がある。この「信頼」は入力分類との対応への信頼であり、CSV の記載内容の正しさや用途上の完全性の信頼とは別である。提供方法・構文・公開API名は0.0.14の設計に残す。

隔離された範囲から直接 File を読む方法も候補だが、隔離が読み取りの間に実対象の分類を保つ根拠が必要である。単にハーネスがあること、リンクを一度調べたこと、絶対パスへ変換したことだけではその根拠としない。サーバ前はその対応を処理系が強制する保証を加えず、信頼条件として提示する。承認できなければ精密化しない。

一般読み取りの「秘密の結び」は、その入力が取りうる秘密の分類をすべて含める保守的な上限である。汎用の束を分類の集合へ固定する決定ではなく、後の例では有限の分類による具体例として書く。APIの全対象を表すTopと、機密性の最も厳しい印は別の概念である。秘密登録が空の場合や網羅性が不明な場合に、空の結びから未知の入力を公開と認定しない。未分類を保守的な印で表せない方針では、保証を付ける対象で未対応として拒否する。内容の自動判定でこの不足を補う案ではない。

一般読み取りに印を付けるだけでその呼び出し自体をすべて拒否するわけでもない。返る情報の受け手が結びに含む全分類を許すなど、出口の条件を満たす使い方は候補になる。ただし、OSへ渡すパス、操作を呼ぶ条件、失敗による後続の変化もD5・D8と入口・出口の棚卸しで扱う。保守的な戻り値の印だけで、秘密に依存する読み取り要求を無条件に許した扱いにはしない。

## 公開CSVを提供する二つの形と未見積もりの費用

RV-IF10のB2として、案Aの公開CSVを実際に提供する形は次の二つを比較する。どちらも、入力との対応を認定する者への信頼と、CSVの内容自体の未信頼性を分ける。

| 形 | 対応の根拠と費用の未確認 |
|---|---|
| A1: 起動側が読み取り済みデータを渡す（案Aの中で推す） | 読み取った内容と成否に契約を付け、スクリプトが任意パスへ付け直せない入力を用意する。起動側の取得・受け渡しと標準入口への接続の費用は未見積もりである |
| A2: Fileの読み取りに実対象との対応の信頼条件を補う | 字面の照合に、読み取りの間も実対象が分類に対応するという承認済みの信頼条件を加える。実質は字面の照合（案C）とこの信頼条件の組であり、その条件の具体化・説明・維持の費用は未見積もりである |

A1は、スクリプト内の可変なパスと入力契約を結ぶ責任を減らせるため推す。ただし、これだけで起動側の読み取りが正しいと証明されたわけではなく、二つの形の費用差も不明である。D4の回答にはA1・A2のどちらを選ぶかを添え、IF30で0.0.14の計画へ具体的な提供方法と費用の確認を渡す。D8の必須例は、方法と費用を確定するまでは接続済みとしない。

[07-01「ハーネスとの分担」](../../../design/07-quality/07-01-security-model.md#ハーネスとの分担)も、シンボリックリンクの差し替えへの防御を処理系の保証の外としている。A2の信頼条件はその防御を実装した保証ではない。

## File の棚卸しに対応する例

IF20.01の [inventory/file.md](../inventory/file.md) を、取り込みの前の別の作業用のディレクトリで読み取った。本文の `../inventory/` へのリンクはIF20の取り込み後に有効になる。読んだ内容のSHA-256は `58bf2c837cbec61c010f7eea3eafac49ccc41e71641b3577b8a451186f6a1b0c` である。同記録が対象とするソースのHEADは `1009954381de6dd2f4a082b16221f3c762303bd3` であり、本枝でソースの全経路を再調査・実行した意味ではない。後の集約のため、依存する所見を次表にも記す。

| 棚卸しの行 | 確認済みとされた経路 | D4で残す条件 |
|---|---|---|
| F01・F04・F05 | 全文・Bytes・行リストの内容、長さや件数、成否・誤り、入力上限等による停止 | 読み方や返る型で機密性を下げない。行数だけの表示も元入力の依存を保つ |
| F06〜F10 | 存在、種類・サイズ・更新時刻、列挙した名前と階層、リンク解決後のパスと各成否 | 本文以外の外部状態も入力として扱う。パスの正規化を公開化や実対象固定の操作としない |
| F02・F03・F11、F24・F26と解放 | Reader/Writerが対象と状態を保持する。解放後使用やWriterのflush・失敗が別の観測になる | 一般読み取りの結びを決めても、資源の保持・解放の契約は閉じない。未対応で拒否する候補を維持する |
| F12〜F15・F25、F19 | 書き込みとcopy、二パスのrename、保存先からの再読の対応 | 公開の名前へ書く・コピーする・改名することで秘密の分類を消さない。保存と再読の契約が閉じない使い方は拒否する |
| U-F01〜U-F07 | 入力契約・実対象、誤りの全文、観測範囲、資源保持、範囲付き操作の接続、全出口、特殊ファイル等に未確認がある | 特にU-F01をこの判断案だけで解消済みとしない。成否・停止はIF20.04〜.06、実装との再照合はR30後へ渡す |

次の例は分類規則を比較する架空の例であり、ファイルを用意して再現した結果でも、構文・API名の決定でもない。方針に「認証情報」と「機密報告」という秘密の分類があると仮定し、「全分類の結び」は両者を含むものとする。「公開／未信頼」のように機密性／完全性を併記する。公開の集計・表示も、出口と成否・pcの契約が接続された後の受理候補である。

| File の典型と前提 | 案Aの印と帰結 | 案Bの印と帰結 | 案Cの印と帰結 |
|---|---|---|---|
| 公開CSV。`<project>/data/sales.csv` の内容と成否を公開と認定した入力契約から得る。内容は外部で作られうる | 公開／未信頼。集計・表示の候補。件数や列名を命令として信頼する許可は得ない | 全分類の結び／未信頼。契約があってもFile入力の例外を設けず、公開集計を拒否 | 公開／未信頼。字面が公開範囲にあれば通すが、契約で実対象を認定したことは分類の条件にしない |
| 同じ公開CSVを、契約なしで一般の全文読み取りまたは行読み取りから得る | 全分類の結び／未信頼。人間が公開CSVだと知っていても、その事実を契約へ結ばなければ公開表示を拒否 | 全分類の結び／未信頼。同じ拒否 | 字面が秘密登録と非交差なら公開／未信頼。実対象が同じである保証は残らない |
| 設定ファイル。`<project>/config/report.json` は報告名と宛先を含み、内容と成否を公開と認定できるが、外部で変更されうる | 公開／未信頼。表示の候補だが、送信先などの信頼する選択へそのまま使う許可はない。D5の保守的な規則では宛先の検査自体も拒否しうる | 全分類の結び／未信頼。設定由来の表示や宛先選択が広く拒否されうる | 字面が非交差なら公開／未信頼。公開分類だけで宛先の完全性を満たしたことにはしない |
| 秘密を含む設定。`<config>/service.json` を全文取得し、認証情報を含むと認定した契約がある。別の秘密を含まないことも契約に含む | 認証情報／未信頼。認証を許した操作の候補。JSON解析後に報告名だけ射影しても自動的に公開にはしない | 全分類の結び／未信頼。認証先が認証情報だけを許す場合、機密報告への依存も残り送信を拒否 | 字面が認証情報の登録に合えば認証情報／未信頼。登録外の別名から読む場合の保護はできない |
| 機密報告。`<project>/reports/input.bin` が機密報告だけに属すると認定した入力契約から得る | 機密報告／未信頼。その分類を許した固定APIへの送信の候補。応答や成否の公開はD3の別契約が必要 | 全分類の結び／未信頼。送信先が認証情報も受け取れるとは限らず、正当なアップロードも拒否しうる | 字面に機密報告の登録があれば機密報告／未信頼。登録漏れや別名を自動発見しない |
| リンクや差し替えのありうるパス。`<project>/data/current.csv` が、字面は公開範囲でも実際には認証情報を指しうる。対応を認定する契約はない | 全分類の結び／未信頼。公開表示を拒否。範囲への所属や一度のリンク解決だけで公開にしない | 全分類の結び／未信頼。同じ拒否 | 公開／未信頼となりうる。認証情報の漏れを機密性の規則で止められない。未信頼の完全性を保持してもこの誤分類は補えない |

案Aで、設定ファイルの一部だけを公開として取得したければ、その欄を公開と認定する専用の入力契約か、用途を限る別の非機密化の契約が要る。秘密を含む全文から欄を射影するだけでは足りない。[S5「設定を含むレコードから公開の報告を作る」](../study/information-flow.md#設定を含むレコードから公開の報告を作る)の、公開入力と秘密入力を別に得てレコードを作る場合とも区別する。入力の形やJSON解析の成功は、秘密を反映しないことの証拠にはならない。

成否・存在・長さ等が本文と同じ分類を持つという認定がない場合は、表の機密性をそれらへ無条件に流用しない。IF20の棚卸しは、誤り文言のOSごとの実内容や特殊ファイルの全挙動を未確認としている。公開CSVの本文に契約があっても、秘密依存の失敗・停止で公開の後続が変わるなら、その表示は契約と規則を閉じるまで受理済みにはしない。

## パスの字面、実対象、実行時の拒否

字面の範囲に属する値を得ることと、そのパスから読む情報の分類を認定することは別である。読み取りの前後でファイルシステムの状態が変わりうる場合、字面上の公開範囲と秘密範囲が交差しなくても実対象まで非交差とは限らない。一般の動作に関する根拠は後掲のRust公式文書、現行のFileについての読み取りの範囲はIF20.01の所見に限る。リンクを拒む特定の操作があることから、全操作・全パス要素・別名・外部変更への防御を導かない。

案Cはこの差を保証から外す選択である。実対象まで保護するというD2案Aの目的を保つなら、字面だけの案Cは採れない。実対象との対応を契約の前提として補う場合は案Aに相当する。その不足を実行時のアクセス拒否で補う場合は、サーバ前に権限制御を単独で入れない00-01と判断14の変更判断、方針の保護・実対象の照合・全経路の強制・拒否と後続の観測の設計、追加費用の見積もりが必要であり、費用は不明である。

案Aでサーバへ渡すのは、同じ秘密登録から「一般アクセスを除外する対象」と「取得した内容・派生値の分類」を導くという責任の境界である。`{secrets}` は既存の調べが実アクセスの除外を表すために使う表記であり、本枝は書式やAPIとして確定しない。秘密を取得する専用の入口を認めることと、一般アクセスの除外を解除することも別である。

[SD §2〜§4](../spikes/SD/findings.md#2-送信と観測の規則)は、宛先・本文・pcとR全体への被覆、公開pcでのfail・非再開・失敗しうる宛先検査を小モデルで確かめた。Fileのリンク・差し替え、実IOの成否や一般のハンドラは対象外であり、File入力の認定や新しい実行時拒否を正当化する証明としては使わない。機密性と完全性の積へそのまま適用すると、公開だが未信頼の設定でも拒否しうる制限も残す。

[SH2の観察の制約](../spikes/SH2/findings.md#評価の一致と観察の制約)は型・効果と値・Emit列の一致の独立モデルであり、情報フロー制御や非干渉性を証明していない。[S3 §5](../study/usage-and-flow.md#5-情報フロー制御と-lio)も踏まえ、模擬ハンドラ・効果の除去・純粋な変換を、入力の秘密やpcの依存を消す根拠にしない。両試作は再実行していない。

## IFC-D2・D3の別案とIFC-D5〜D9への依存と申し送り

| 判断・枝 | 渡す条件と、その判断へ残すこと |
|---|---|

| IFC-D5／IF10.04 | 精密な入力分類でも送信の許可にはしない。宛先・本文・pcを合わせ、その印の許す受け手がR全体を覆う条件へ渡す。一般読み取りの結びは複数の秘密を許す宛先を要しうる。公開／未信頼の設定を、公開かつ信頼する宛先と同じに扱わない |

## 設計者への一つの問い

共通の前提は、内容・成否と実対象との対応を分け、サーバ前に実行時のアクセス拒否を加えないことである。

IFC-D4は、認定できる入力契約だけ精密化する案A（公開CSVの提供はA1を推す。A2も比較する）、File入力をすべて秘密の結びにする案B、字面だけで分類する案Cのどれを選ぶか。

推すのは案A・A1である。理由: 公開CSVと機密ファイル送信に必要な分類の精度を残し、認定できない一般読み取りを保守的に扱える。A1・A2の具体的な提供方法と費用はともに未見積もりであり、案Aの採択だけでD8の必須例が実装可能と確定した扱いにしない。
