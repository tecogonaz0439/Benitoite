## 転記用の文

### IFC-D2: 保証の範囲と信頼する起動側

【決定】案 A を採る。0.0.14 の情報フロー制御（information-flow control）は、保護された同じ方針・信頼する契約・検査と実行の対応、及び対応済みの逐次の経路（Task 等は未対応として拒否する）を前提に、誤りによる漏れと未承認の影響を実行前に拒否する静的な保証とする。意図した迂回への保証は、同じ方針と実行時の照合・OS の強制との接続を閉じたサーバモードの構成に加える。

07-01 の信頼関係に「信頼する起動側」（用例を確かめていない説明上の呼び名）の役割を一つ加える前提を受け入れる。これは承認済みの方針・契約と検査したコード・依存の組を保護して渡す部分を指す。07-01 の既存の「処理系を起動する側」（隔離の担い手）とは別の役割として、0.0.14 で情報フロー制御を実装するときに 07-01 へ反映する。0.0.13 では設計書を変えない。LLM が方針も編集して自由に起動できる使い方では、今回渡した方針への適合までしか言わず、人間が承認した方針の保護や検査外の起動の隔離を保証しない。

理由: 静的検査と実行時の権限制御を分ける既存の版の順序を保ち、両者を接続した構成での保証を別に確認できる。起動側への前提を、0.0.14 が提供する保護機能と誤認させないためである。

出どころ: 2026-10-27 の [README の IFC-D2 の回答](../README.md#設計者の決定2026-10-27情報フロー制御の判断-ifc-d2d9)、[問い1](../if10.09/designer-questions.md#1-ifc-d2-どこまでの保証をいつ提供するか)、[D2「案Aで明示する前提と観測」](../if10.01/ifc-d2.md#案aで明示する前提と観測)、[RV-IF10 対応 A3・B1](../reviews/RV-IF10-handling.md)。

### IFC-D4: 認定した入力と公開 CSV

【決定】案 A・A1 を採る。実対象と返る情報の分類との対応を認定できる入力契約だけを精密にし、認定できない一般の読み取りは、ありうる秘密の分類の結びとして扱う。パスの字面の非交差だけから公開を導かず、分類の網羅性が不明な入力を空の結びで公開にしない。保守的に表せない入力は「保証を示す実行」（用例を確かめていない説明上の呼び名）で拒否する。この語は保証を付ける対象として検査する実行を指す説明であり、CLI のモードや切り替えの決定ではない。通常実行を残すかとその形は U14 の未決事項とする。

公開 CSV は、「信頼する起動側」（用例を確かめていない説明上の呼び名）が読み取り済みの内容と成否を契約付きで渡す形とする。契約を任意のパスへ付け直せる形にせず、入力との対応への信頼と、CSV の内容自体の完全性を分け、内容は未信頼に保つ。サーバ前に一般アクセスの実行時拒否を加えず、後の「実体アクセス除外」（用例を確かめていない説明上の呼び名。秘密の実対象への一般アクセスを除外すること）と内容の分類は同じ秘密登録から導く。

理由: 公開 CSV の集計と機密ファイル送信に必要な分類の精度を残し、認定できない読み取りは保守的に扱える。A1 はスクリプト内の可変なパスと契約を結ぶ責任を減らせるが、具体的な提供方法・費用と起動側の取得の正しさは未確認である。

出どころ: 2026-10-27 の [README の IFC-D4 の回答](../README.md#設計者の決定2026-10-27情報フロー制御の判断-ifc-d2d9)、[問い2](../if10.09/designer-questions.md#2-ifc-d4-入力分類をどの根拠で精密にするか)、[D4「案Aの入力契約と認定の条件」](../if10.03/ifc-d4.md#案aの入力契約と認定の条件)・[公開 CSV の二つの形](../if10.03/ifc-d4.md#公開csvを提供する二つの形と未見積もりの費用)、RV-IF10 対応 B2。

### IFC-D3: 認証付き API の限定した応答公開

【決定】案 A を採る。認証付き API では、解決済みの固定操作・変換と版を同定する契約によって、公開する件数等の値・所定の成否・用途・呼出条件を限る。送信の許可と応答の公開を分け、許した要求由来だけを非機密化（declassification）し、未承認の捕捉・条件・本文の秘密を保持する。応答の完全性は未信頼に保つ。

外部 API と固定変換が承認した結果を越えて秘密を反映しないことを、人間が承認する信頼条件とする。承認できなければ結果と成否も秘密に保つ。公開応答を信頼する命令・宛先の選択へ使うには、用途を限る別のエンドースメント（endorsement。信頼の付与、または完全性レベルの引き上げ）の契約を要する。

理由: 件数と成否の報告に必要な公開を認めつつ、本文・ヘッダ・生の失敗情報の広い公開を契約から除ける。値を整数等へ変換したことだけでは、外部 API が秘密を符号化していないことを証明できないためである。

出どころ: 2026-10-27 の [README の IFC-D3 の回答](../README.md#設計者の決定2026-10-27情報フロー制御の判断-ifc-d2d9)、[問い3](../if10.09/designer-questions.md#3-ifc-d3-認証付きapiの応答をどの単位で公開するか)、[D3「案Aの契約が定める範囲」](../if10.02/ifc-d3.md#案aの契約が定める範囲)・同「契約の具体例」。

### IFC-D6: Secret と分類ごとの印

【決定】案 A を採る。0.0.14 で `Secret` の不透明な型と分類ごとの印を併用する。型は直接の汎用表示・補間・等値・JSON 変換を制限し、印は取り出した通常値・派生値・pc の機密性と完全性を追う。取得、印を保つ取り出し、固定契約内の許可された非機密化を分け、包装・射影・解析成功・範囲検査・送信を印の除去や信頼の付与にしない。

理由: 印だけの案に比べ、型による直接操作の診断と取り出しを明示する接点を増やせる。等値の禁止は比較前に取り出しを明示させる選択であり、非干渉性に必須の条件とはしない。専用型・受け口・取り出し・表示経路の接続と保守の費用は残る。

出どころ: 2026-10-27 の [README の IFC-D6 の回答](../README.md#設計者の決定2026-10-27情報フロー制御の判断-ifc-d2d9)と P3、[問い4](../if10.09/designer-questions.md#4-ifc-d6-分類の印にsecretの型を併用するか)、[D6「案Aの役割の分担と三つの操作」](../if10.05/ifc-d6.md#案aの役割の分担と三つの操作)、RV-IF10 対応 A5。

### IFC-D5: 固定 origin と失敗・非再開

【決定】宛先は案 B、失敗の条件は候補 (ii) を採る。0.0.14 で秘密や未信頼の依存を含む送信（宛先・本文・pc の結びで得る印 L が機密性と完全性の積の底でない送信）は、コードの固定 origin への要求に限り、動的設定からの宛先選択は受理しない。公開かつ信頼する本文だけを動的な宛先へ送る形は U13 に残し、受理・拒否を一律に確定しない。印 L と要求各欄を静的に照合し、固定先を単一候補として扱う場合も、静的上限 R 全体が許す受け手の集合に含まれることを求める。host/port の上限だけから HTTPS origin を導かず、scheme を限定する要求契約を要するか、http/https 双方を覆う条件を残す。

fail・Assert の失敗・非再開は、公開かつ信頼する pc、すなわち機密性と完全性の積の底に限る。失敗しうる宛先検査にも pc と入力が公開かつ信頼する条件を保ち、固定 origin の採用を動的検査の受理へ広げない。公開でも未信頼の CSV や HTTP 応答による通常の `die`・Assert の失敗・非再開は拒否するため、必須例では失敗を値として扱う接続を要する。

理由: 必須三例の宛先は固定であり、信頼する動的設定の入口と差分費用を確定せずに範囲を広げる必要がない。完全性の条件は検証前に精密化せず、通常の失敗処理を制限する費用を受け入れる。

出どころ: 2026-10-27 の [README の IFC-D5 の回答](../README.md#設計者の決定2026-10-27情報フロー制御の判断-ifc-d2d9)、[問い5](../if10.09/designer-questions.md#5-ifc-d5-宛先の範囲と失敗非再開の制限をどう組み合わせるか)、[D5「三つの案と推す範囲」](../if10.04/ifc-d5.md#三つの案と推す範囲)・[完全性の二候補](../if10.04/ifc-d5.md#完全性へ制限を課す二つの候補と確認項目)、判断14、RV-IF10 対応 A1・A2・B1・B3。

### IFC-D8: 必須三例と拒否の単位

【決定】案 A を採る。0.0.14 は、公開 CSV の集計表示、トークンによる逐次取得の件数と所定の成否の表示、機密ファイルの固定 API への送信の三例を必須にする。各例で正当な形を少なくとも一つ受理し、禁止する変更を拒否し、入力から出口・成否・診断・要約まで同じ方針と契約への対応を示す。送信の受理から応答の公開を導かない。

未対応または必要な解析ができない経路に到達しうる実行入口は、依存・高階呼出し・ハンドラ・後続を含む全体を実行前に拒否する。健全な保守的要約があればその上限で判定するが、不明を公開・信頼済み・未使用として通さない。必須例の接続不足を後の改造へ回しただけで、0.0.14 の受け入れを完了にしない。

理由: 入力分類、限定した非機密化、送信条件がつながる三つの作業を受け入れ条件として確かめられる。未見積もりの並行・保存の接続を必須に加えず、実用範囲を具体化できる。

出どころ: 2026-10-27 の [README の IFC-D8 の回答](../README.md#設計者の決定2026-10-27情報フロー制御の判断-ifc-d2d9)、[問い6](../if10.09/designer-questions.md#6-ifc-d8-0014で必須にする実用例はどれか)、[D8「三例を必須にする場合の受け入れ条件」](../if10.07/ifc-d8.md#三例を必須にする場合の受け入れ条件)・同「拒否の単位と、解析できない場合の扱い」、[IF20 の EX01〜EX08・V01〜V07](../inventory/remaining-and-examples.md#典型8例と入口出口の照合)。

### IFC-D7: 人間への要約と承認

【決定】案 A を採る。人間には、作業、秘密と取得・取り出し、受け手と R 全体、用途、公開する値と成否、信頼条件、変更差分と再利用範囲を示す。秘密登録、送信先・用途、非機密化、エンドースメントの変更を区別して承認し、一つの整合する方針の改訂へ結ぶ。秘密の実値・実際の長さ・秘密依存の成否を要約・診断・履歴へ含めない。

0.0.14 の提示・人間の承認・保存・保護は「信頼する起動側」（用例を確かめていない説明上の呼び名）への前提とし、サーバモードで承認の確認・保存・失効と実行時の強制へ接続する。要約は同じ正規化済み方針・解決済み契約・検査対象に対応させ、除去可能なエフェクト名だけで実際の契約使用を集計しない。承認によって未対応の機能を受理へ変えない。

理由: 人間が受け手・用途・公開範囲・信頼条件の変更を判断できる接点にする。要約と実際の方針・契約・検査対象との一致を確認する責任は残る。

出どころ: 2026-10-27 の [README の IFC-D7 の回答](../README.md#設計者の決定2026-10-27情報フロー制御の判断-ifc-d2d9)、[問い7](../if10.09/designer-questions.md#7-ifc-d7-人間は何を読んで承認するか)、[D7「案Aで人間に示す要約の項目」](../if10.06/ifc-d7.md#案aで人間に示す要約の項目)・同「承認の単位、保存、実行の分担」。

### IFC-D9: 一つの方針と更新・再利用

【決定】案 A を採る。一つの方針に、種類・対象の許可、有限の束と入力分類、秘密登録、入口・出口と緩和契約、所有・識別と版、承認と検査対象の対応を結ぶ。正規化済み入力の境界を情報フロー制御の実装前に設計し、保存・UI の実装はサーバへ残す。秘密の実値・履歴・サーバ状態を一つの物理ファイルへ集める意味にはしない。

通常のコード・依存だけの変更は、方針と信頼する契約の意味が変わらず、入口全体の再検査と要約の照合で既存の承認範囲内と確認できれば承認を再利用する。同じ束・入力分類・信頼条件の下で許す操作・対象・受け手・用途を削減するか緩和契約を無効にするだけの変更は、制限を加える権限を持つ起動側・サーバが包含を確認し、承認済みの基準と変更を記録して新しい組を再検査した場合に限り、追加の承認なしに適用する。秘密登録の削除や入力分類の緩和はこれに含めず、意味・包含・更新権限が不明なら再提示へ戻す。失効した承認と旧検査結果は使わない。

理由: 承認範囲内の修正と許可の削減のたびに、人間へ同じ判断を求めずに済む。意味・包含・更新権限の照合と記録を条件にし、記述の削除だけで保護が弱まる変更を自動適用することを避ける。

出どころ: 2026-10-27 の [README の IFC-D9 の回答](../README.md#設計者の決定2026-10-27情報フロー制御の判断-ifc-d2d9)、[問い8](../if10.09/designer-questions.md#8-ifc-d9-既存の承認をどこまで再利用するか)、[D9「承認の再利用と許可を狭める変更の四案」](../if10.08/ifc-d9.md#承認の再利用と許可を狭める変更の四案)・同「再承認・再検査が要る変更と狭小化」「方針書式の設計順序と記録先」。
