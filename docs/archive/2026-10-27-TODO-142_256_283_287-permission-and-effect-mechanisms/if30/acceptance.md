# IF30.02: 典型8例の受理表と0.0.14の信頼条件

2026-10-27。[README の回答](../README.md#設計者の決定2026-10-27情報フロー制御の判断-ifc-d2d9)に従い、D2・D3・D6〜D9 は案 A、D4 は案 A・A1、D5 は案 B と候補 (ii) を組み合わせる。以下の受理は、0.0.14 の情報フロー制御（information-flow control）の実装と接続後に満たすべき条件である。現在の処理系で実行して確かめた結果ではない。

## 受理・拒否と行き先

「0.0.14 の必須」は、正当な形を少なくとも一つ受理し、禁止する変更を拒否する受け入れ条件を指す。「接続を閉じる改造」「サーバモード」は、その範囲を後の計画で具体化する行き先であり、受理の約束ではない。「対象外」は0.0.14の情報フロー制御の保証を付けない意味とし、「保証を示す実行」（用例を確かめていない説明上の呼び名）では拒否する。この語は保証を付ける対象として検査する実行を指す説明であり、CLI のモードや切り替えの決定ではない。通常実行を残すかとその形は [U14](decisions-transfer.md#回答で決まらず残った点) の未決事項である。任意 URL への秘密送信と未信頼のシェル本文は、禁止する流れとして判定する対象である。

ID は [IF20 の典型例の照合](../inventory/remaining-and-examples.md#典型8例と入口出口の照合)と同じ `IF20.nn/ID` で記す。各枝の対応は、.01 が [File](../inventory/file.md)、.02 が [Http](../inventory/http.md)、.03 が [Console・Process](../inventory/console-process.md)、.04 が [表示・JSON・ログ](../inventory/display-json-log.md)、.05 が [失敗・終了](../inventory/failure-exit.md)、.06 が [残りと典型例](../inventory/remaining-and-examples.md)である。入口を成否として参照する行を、報告の出口と数え直さない。

## 棚卸しの候補差と未確認の扱い

[RV-IF20 対応](../reviews/RV-IF20-handling.md)と[枝によって候補が違う経路](../inventory/remaining-and-examples.md#枝によって候補が違う経路)に従う。引数の UTF-8 は IF20.03/E02 の保守的な入力分類を保ち、報告は E03 と IF20.05/D11 の契約候補へそろえる。解放失敗の報告は IF20.05/S09、引数と入力上限の停止は S13・S20、解放後使用は S10、捕捉した panic と捕捉外の終了は H03・H09 を正とする。File の初期候補や IF20.04/C29 の総括行へ戻して上書きしない。

出口の「保守的」は材料の入力の結びを保持する候補であり、受け手への出力を許す意味にはしない。D2・D7・D9 は同じ方針への対応と要約の条件を定めたが、ソース・設定・OS の誤り文言・panic の全内容や受け手を個別に認定してはいない。該当する27行を一律に公開又は契約完了へ昇格させない。必要な契約を示せない報告を含む実行には、D8 の保守的判定又は入口全体の拒否を適用する。

## 0.0.14 の保証が前提にする信頼条件

信頼条件は、静的規則が証明する性質と、処理系の外で用意する対応を分けて示す。以下は採択した案が要求する前提であり、実在ハーネスや API について成立を確認した報告ではない。

| 処理系の判定と実際の出力の対応 | Rust の検査器と標準ライブラリが、Lean で形式化した規則と観測のとおりに判定し出力することを信頼する | 判断15の `io_target` と同じ位置の信頼条件である。Rust と Lean の比較は検査であり証明ではない。対応の不備を形式化した定理だけで排除しない | 判断15、D2、要求と実通信先の対応 |

外部環境の前提を定理の仮定へ写すことは、上表の外の条件とは別の形式化の義務である。0.0.14 の計画の [P06](handover.md#0014-の計画へ渡す義務) へ渡し、公開入力・外部応答、時計・乱数・OS の失敗等の関係を観測の言明へ対応させる。明示的な TimedOut・上限・終了状態を、物理時間や資源量の保証外という理由で除外しない。完全性の終了状態の扱いは RV-IF10 B1 の確認事項であり、IF20.05/U-FE02・U-FE05 も照合する。

意図との一致、外部操作の成功、停止性、物理時間・資源使用量による漏れ、許した受け手による再配布、安全なメモリ消去・ダンプからの秘匿、信頼する処理系・OS 等の不具合を突く攻撃は、この回答で保証へ追加していない。サーバで意図した迂回への保証を加える場合も、接続を確認した構成と信頼条件を明示する。

## 必須三例の受け入れへ残す条件

D5 候補 (ii) の下では、EX01・EX02 の成功・失敗を未信頼の値として固定した公開先へ表示し、同じ正常終了へ合流させ、その後に信頼を要する操作を置かない最小形を確認する必要がある。読み取り・変換・入力上限・出力停止までこの形にできるかは未確認であり、`Result.Error` を作ること、`Failure.toResult` を呼ぶこと、終了コードだけをそろえることを解決済みの根拠にしない。EX03 も、秘密の応答を捨てるだけでは公開の後続と終了への影響が消えるとはしない。

0.0.14 の担当は、同じ方針・契約・コード・依存の組、認定入力の根拠、受理／拒否と診断、公開する観測と秘密に保つ値、要約と信頼条件を証拠にする。制御した入力と相手で標準の実 IO を通す確認を割り当て、模擬ハンドラだけの成功で置き換えない。接続できなければ必須例は未達として、契約・規則又は必須条件の再判断を設計者へ返す。個々の未決と引継ぎ先は [判断の残り](decisions-transfer.md#回答で決まらず残った点)と [handover.md](handover.md)に記す。
