## 一次資料

以下の URL は全て 2026-10-27 に確認した。実装依存の parser の受理集合は、この RFC の記録から推定しない。

| 資料 | 確認した内容 |
|---|---|
| [RFC 3986 §3.2.2](https://www.rfc-editor.org/rfc/rfc3986#section-3.2.2) | URI の host は IP-literal・IPv4address・reg-name を分け、IPv4address と一致する入力は最初の一致で IPv4 と解釈する。IPv6 は URL 内で角括弧に包む。IPv4 は四つの dec-octet、各値0〜255、複数桁の先頭0を認めない文法である |
| [RFC 5952 §4](https://www.rfc-editor.org/rfc/rfc5952#section-4) | IPv6 の生成する表記では各16ビット欄の先頭0を省き、小文字を使う。連続0は最長の列を `::` にし、同長なら最初を選ぶ。一つだけの0欄を `::` にしない。同節は正当な RFC 4291 の入力形式を受理することも要求するため、「Benitoite の範囲注釈は正規形だけ」という制約を一般の IPv6 parser の適合要件と混同しない |
| [RFC 5952 §5〜7](https://www.rfc-editor.org/rfc/rfc5952#section-5) | IPv4 を埋め込む既知の接頭辞では、末尾32ビットにドット十進を使う混合表記を推奨する。例は `::ffff:192.0.2.1`。URL での角括弧は RFC 3986 に従う。接頭辞の表記もアドレスと同じ方法を使う |
| [RFC 4291 §2.2〜2.3](https://datatracker.ietf.org/doc/html/rfc4291#section-2.2) | IPv6 は128ビット、末尾32ビットを四つの十進数で表す形式もある。接頭辞長は左から連続する有効ビット数である。§2.3 はノードのアドレスとその接頭辞を一つの文字列に併記する表記も認めるため、ホストのビットが非0なら一律に RFC 違反という説明はできない |
| [RFC 4291 §2.5.5.2](https://datatracker.ietf.org/doc/html/rfc4291#section-2.5.5.2) | IPv4-mapped IPv6 は上位80ビットが0、続く16ビットが FFFF、末尾32ビットが IPv4 アドレスである |
| [RFC 4632 §3.1](https://www.rfc-editor.org/rfc/rfc4632#section-3.1) | IPv4 の CIDR は四オクテット、斜線、0〜32 の接頭辞長で表す。対象集合はビット境界にそろった2のべき乗個の連続したアドレス。`0.0.0.0/0` は全32ビット空間を含む |

## 本作業への提案

これは現行の仕様でも、RFC が要求する Benitoite の規則でもない。IP を認める設計者の決定を具体化する案である。

1. 範囲注釈と `Scope.checkHost`・`checkEndpoint` のパターンの IP は正規形だけ受理する。IPv4 は十進4欄、各0〜255、各1〜3桁、単独の0以外の先頭0を禁止する。`0.0.0.0`・`255.255.255.255` も字面としては受理する。使用可能な接続先であることまで保証しない。省略形、整数一個、八進・十六進形、`127.0.0.01`、`999.999.999.999` をホスト名へ読み替えない。
2. 通常の IPv6 は RFC 5952 §4 の生成規則にそろえる。範囲の文字列は `"::1"` とし、URL の `http://[::1]/` の角括弧を持ち込まない。アドレス文字列に port を混ぜない。zone identifier と IPvFuture は範囲の初段から外す。正規形を拒否する診断は候補の正規形を示せるが、黙って注釈の文字列を修正しない。
3. IPv4-mapped IPv6 は IPv6 の128ビットの数のまま扱い、正規表示を `::ffff:192.0.2.1` とする。IPv4 へ射影して同一視しない。IPv4 CIDR は mapped IPv6 を含まず、IPv6 CIDR は IPv4 を含まない。IPv6 の `/0` は mapped の範囲も含む。この規則から実際のソケットの接続方式や DNS の安全性は導かない。
4. CIDR の長さは IPv4 では0〜32、IPv6 では0〜128。接頭辞長の十進表記も単独0以外の先頭0を禁止する。CIDR の入力でホストのビットが0でない場合は拒否する。`192.168.1.5/24` の代わりに `192.168.1.0/24` を診断で示す。この選択は権限の範囲を入力より広げる修正を黙って行わないための言語側の制約であり、RFC 一般が全ての host/prefix 表記を禁止するという説明にしない。
5. 完全一致を幅と等しい接頭辞長の CIDR と同じ内部形にするなら、`192.168.1.1/32` と `192.168.1.1`、`::1/128` と `::1` を正規化でそろえ、構造的な同一原子として重複を診断する。包含しているだけの別原子は重複とはしない。
6. 対象を hostname / ipv4 / ipv6 の直和で区別する。ホスト名の exact・one・many と IP の exact・CIDR の所属と被覆は、同じ分類の中でだけ判定する。`*.`・`**.` が数字ラベルを末尾一致で拾ったり、DNS を引いて IP 範囲との包含を判定したりしない。
7. `RequestIn` では同じ request の URL を解析して host を取り出し、IPv6 の URL 用角括弧を除いたアドレスを数値化して分類する。URL は一般の有効な IPv6 表記を受理し、内部の endpoint は正規化する案が自然である。パターンの注釈の正規形限定と URL 入力の制約は別に明記する。省略された port は scheme の既定の実効 port へ直し、同じ分類の IP/CIDR とポート区間を検査する。ホスト名なら DNS を引かず名前の規則で検査する。IP として不正な数字・コロン表記をホスト名へ逃がさない。検査後に URL を取り替えられない不透明値に保持し、`sendIn` に同じ request を渡す。

旧 Scope への影響は入力集合の変更である。03-06 の「IPv4 形式・IPv6 を拒否」を変更し、Rust の host_word/host_pattern と Lean の Word だけの入力を共通の hostname/ipv4/ipv6 表現へ一般化する。従来 InvalidPattern/InvalidTarget だった正規 IP と整列した CIDR が成功または OutsideScope になり得る。既存のホスト名とワイルドカードの所属は保つ。DNS をしない純粋な字面の検査であることは保つ。移行の案内を書く提案は含まない。

## CIDR の包含と Lean の枝

IP のビット幅を w（32 または128）、正規 CIDR のネットワーク値を b、接頭辞長を p とする。妥当性は `p ≤ w`、`b < 2^w`、`b % 2^(w-p) = 0`。対象集合は閉区間 `[b, b + 2^(w-p) - 1]` である。同じ分類の原子 R が S に被覆される条件は `lo(S) ≤ lo(R)` と `hi(R) ≤ hi(S)` である。従って所属・被覆の健全性・反射性・推移はポートの閉区間と同じ順序関係に帰着できる。

ただし CIDR をこの区間へ変換する補題は追加で要る。長さの境界、区間の非空、上端が2^w未満、ビットの接頭辞一致と区間所属の同値、完全一致との対応を分ける。単に既存のポート補題だけを引用して parser と接頭辞の正しさまで証明済みとはしない。`/0`・`/32`・`/128` と最大アドレスを含む例が要る。

Lean の候補は `IpAddress w := {n : Nat // n < 2^w}` と正規 CIDR の妥当性を持つ構造である。Nat は上端計算に固定幅のオーバーフローを持ち込まない。BitVec 32/128 からの変換を別補題にする案も比較できる。Rust では IPv4 に u32、IPv6 に u128 又は16バイト配列を使え、usize にアドレスを詰めない。幅と等しいシフトや上端+1のオーバーフローを避ける設計が要る。この選択は64ビットの機械だけを前提にしない。

`study/language-rules.md` B1 の Scope/Domain と Checked/Scope の枝で hostname/ipv4/ipv6 の分類を最初から定義し、B4 の L10 で数値区間の所属・被覆・推移を閉じる。L40 で URL/Scope 検査と局所事実、L50 で数値化した対象の交換を接続する。略記の原子への展開は Surface より前に完了させ、Lean の構文と交換に略記を残さない。IP/CIDR の追加を理由に API ごとの Ty 構成子を増やす必要はない。
