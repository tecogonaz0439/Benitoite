この文書の中心の用語を先に定める。秘密の値の流れを追って漏れを防ぐ仕組みの総称を「情報フロー制御（information-flow control）」、その型による方式を「セキュリティ型システム（security type system）」、保証する性質（ある観測者に許していない秘密だけを変えた二つの実行で、その観測者が見る結果が変わらないこと）を「非干渉性（noninterference）」と呼ぶ（README「設計者の決定（2026-10-27、用語）」）。印を下げる操作は「開示（declassification）」、完全性の印を上げる操作は「検査（endorsement）」と書く（S6 の用法。用語集には未登録）。「範囲付きのエフェクト」「案4」「扱い1」は docs/todo の TODO-142 と S4b・SA の語である。

## 版の割り振りと各版の保証

保証は、00-01「保証の範囲」の区別に従い、静的検査が保証すること・表示だけで保証しないこと・どの版でも保証しないことを分けて書く。設計者が挙げた場面は「LLM が書いたスクリプトがクレデンシャルを読み、許した宛先へ送ってしまう」である。この場面には二つの形があり、防げる時期が違う（RV-S5 F2-1）。

- **誤りによる漏れ**: LLM が誤って、クレデンシャルを読む処理と、別の目的で許した宛先へ送る処理をつないでしまう。
- **意図した漏れ**: プロンプトの注入などで、LLM が漏らすつもりでスクリプトを書く。外部コマンドに読ませる、方針を書き換えるなど、検査を避ける経路も使いうる。

| 版 | 利用者に与える保証 | 与えない保証 | 場面への効果 |
|---|---|---|---|
| 0.0.12（今） | `main` の型の組み込みのエフェクトを実行前に `--allow-effects` と照合する（操作の種類だけ） | 対象・値の流れ・実行時の強制。隔離はハーネスと OS に委ねる | `File.Read` と `Http.Connect` を両方許せば、どちらの形も防げない |
| 0.0.13（案4） | 関数と `main` の型に、パス・ホスト・ポートの対象の上限を示す。上限を越える関数の呼び出しを契約違反として実行前に報告する。範囲のない `File.Read` などは全対象の上限として残る | 上限は許可でない（型の範囲を許可にしない原則）。上限が方針を越えたときの実行前の拒否はサーバモードで決める。値の流れは追わない。実行時の強制はない | 誤りによる漏れの一部を利用者が気付けるようになる。クレデンシャルのパスと送信先のホストが定数か検査済みの値から作られていれば、実行前に表示される `main` のエフェクトに両方が現れる。パスを `String` のまま渡すと全対象の上限になり、表示から読めない。読んだ値が送信先へ流れるかは分からない |
| 0.0.14（情報フロー制御、案 G） | 方針で秘密と登録した入口から得た値と、その派生値・それに依存する分岐を、方針が許さない出口へ送るプログラムを検査で拒否する（逐次の計算と標準の入口・出口に限る。未対応の機能の使用は検査で拒否する）。完全性の印で、未信頼の入力が検査を経ずに用途を限った操作を決めることを拒否する | 方針を誰が保護するか（サーバモードまで信頼する実行側がない）。外部コマンド・WASM の先での読み取り。許した受け手からの再配布。停止・時間・資源の量による漏れ | 誤りによる漏れを、方針が改変されていない前提で静的に拒否できる。秘密の登録がないファイルの一般の読み取りは保守的に秘密の結びとして扱う案なので（問い D4）、クレデンシャルのファイルを `File.readText` で読む場合も対象になる。意図した漏れは防がない（`Process.run` で外部コマンドに読ませるスクリプトは、Benitoite の入口から秘密を読まないので通る） |
| 接続を閉じる改造（版は未定） | 失敗・対象・実行時の拒否の意味と方針の接続を閉じる。設計者が日常の利用に必須とした例に要る機能（Task など）を、別の中心として加える | 0.0.14 と同じ | 0.0.14 で拒否していた典型例の一部が通るようになる。防ぐ範囲は 0.0.14 と同じ |
| サーバモード（`0.1.0` より前） | 信頼する実行側が方針を保存・承認し、実行時に操作ごとに照合し、OS のサンドボックスで子のプロセスの読み取りを制限する。一つの方針から三層を導く（ADR 0183） | 許した受け手からの再配布。外部 API が秘密を応答へ反映しないこと（信頼の条件として承認する）。停止・時間による漏れ | 意図した漏れも、方針の範囲で防げるようになる。外部コマンドによるクレデンシャルの読み取りを OS が止め、方針の改変を承認なしにはできなくなる |

## 0.0.13 の範囲

### 中心

中心は案4 である。範囲は S4b 4.3 の案4 と SA §6 の条件に揃える。

- 閉じたパターン（パスの完全一致と木、ホストの完全一致・一段・多段、ポートの閉じた区間）に限る。範囲のない `File.Write` などを全対象の上限として残す。処理単位は名前全体とし、範囲の一部だけを処理するハンドラは入れない。
- 型の等号は範囲の原子の構造の一致とし、範囲の包含を別の関係にする（SA の扱い1）。SA は扱い1 の和・代入・合成の補題を通し、`eq_of_sub_of_sub` を直接使う本番の5定理（2ファイル）がもともと構文上の所属の一致を証明していることを確かめた（SA §3）。冗長な原子を除く扱い2 も代数上は成立したが、`mem_norm`・`mem_union`・`canonical_ofAtoms` の言明を変え、Lean が10〜17時間多い（SA §6）。扱い2 を選ぶ理由は SA で見つかっていない。
- 包含は一原子ずつの保守的な被覆に限る。`0..9` と `0..4 ∪ 5..9` のように対象集合が同じでも包含を認めない場合があり（SA の `semantic_eq_not_norm_eq`）、その不完全性を仕様と診断に書く。
- 範囲を添字に持つ検査済みの値を受け取る IO の入口を加え、その入口が範囲付きのエフェクトを持つ（S4b 4.1 の D-IO の選択肢3）。今の `String` を受け取る入口は、範囲のないエフェクトを持つものとして残す。

計画の最初の段は関門とし、次の三つを本番を変えない Lean の試作で確かめる。SA は、範囲付きの IO を型付けするには、IO のシグネチャのエフェクトを `Eff.single l` に限る `io_op` の形か操作の型付けの設計を変える必要があると報告した（SA §5）。この変更は主な定理の前提を変えうるので、本番の作業を始める前に確かめる。

1. 範囲付きの IO の操作の型付けと、`io_op` を変える形。既存の `io_op` の変更と、対象についての新しい信頼の条件を分けて列挙する。
2. 対象の健全性の言明。実際の事象の操作の種類と対象が宣言の上限に属することを、進行・保存・脱糖の型の保存のどこへ移すか。既存の空のエフェクトの健全性と別の完了条件にする（SA §7 の4）。
3. ハンドラの節が対象を書き換える場合に、節が行わせる操作の対象を上限に含める規則（S4b 4.3）。

関門の判定は「主な定理（進行・保存・エフェクトの健全性・脱糖の型の保存）の言明を弱めず、対象の健全性を公理にせずに、前提の変更を列挙できたか」とする。SA の推す判断は、この接続を「代数からは見込みがあるが、前提の内容まで含めた本番全体では未確認」としており（SA §5）、新しい対象の健全性を公理にして埋める案を採らない。閉じない場合の選択肢は問い P1 に置く。

範囲のパターンの書き方は、TODO-109 の方針の対象の並びと同じ書き方にする案を推す。TODO-109 は `Http.Connect` と `Http.Listen` の対象の書き方を「権限制御の分野で扱う」残る点としている。型の範囲と方針の対象で書き方が違うと、利用者は同じ役割の記法を二つ読むことになり（原則5）、0.0.14 で範囲を宛先の上限に使うときに変換が要る。決めるのは書き方の対応だけで、型の範囲を許可にしない原則は変えない（問い D1）。
