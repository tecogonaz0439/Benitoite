| 主張 | 例 | 必要な根拠 |

## 1. 範囲付きのエフェクト

### 1.1 何を表せるか

計算のエフェクトに対象集合の上限を付ける方式である。TODO-142 の `File.Write["/data/reports/**"]` や、ホスト・ポートの組はこの案に当たる。これは既存構文ではない。定数のパターンだけなら、任意の依存型や SMT を入れずに包含を判定する余地がある。ただし、範囲内の引数しか操作に渡せない規則を併せて定める必要がある。

近い一次資料として、F* の [Programming and Proving with Indexed Effects](https://fstar-lang.org/papers/indexedeffects/indexedeffects.pdf) の本文 §1.2・§3・§4.1 を確認した（2026-10-26）。`GST a R/RW` のような索引とその合成、操作の集合を索引にした計算を、型・エフェクトからモナドの明示形へ変換する。確認した例は状態・操作の種類であり、TODO-142 と同じパス glob・DNS ホストの包含を標準の型検査が扱う先行例ではない。今回確認した一次資料の範囲では、そのまま流用できる同形の方式は見つからなかった。

注釈の案は「公開境界に閉じた範囲、局所呼び出しでは定数・検査済み値から推論」である。動的な文字列は任意対象を表す上限へ戻すか、明示した検査を要求する。診断は「求める範囲」「分かった範囲」「包含を確認できない理由」を分ける。包含の不成立と、解析の未知・予算超過を同じエラー原因にしない。

### 1.2 権限制御での使い道

TODO-283 の「操作の種類」と「対象」に直接対応し、変更後の関数契約の差分にも使える。「権限を持つ者」「回数」「秘密の流れ」は表さない。方針との関係は第7節で比較する。宣言の範囲は実行側に示す要求の上限であり、それを書けば許可されるという意味にはしない。

ハンドラが処理する前の操作対象と、節が実際に行わせる操作対象も分ける。入力が `/data/reports/a` でも、節が `/tmp/cache/a` へ書き換えれば、外部に行う計算の上限には後者が要る。単に元の範囲を `main` まで集める表示では誤る。型の対象上限・実行時の判定・OS の設定を、ADR 0183 に従って一つの方針に照合する。

### 1.3 実用の機能での使い道

次は報告を書き出す日常の自動化の `.bnt` 擬似コードである。`CheckedPath[...]` と範囲引数は案であり、現在は書けない。

```bnt
// 案: CheckedPath の添字と File.Write の範囲を接続する場合
function saveReport(path: Scope.CheckedPath["/data/reports/**"], text: String)
    -> Result[Unit, IOError] uses File.Write["/data/reports/**"]
  return File.writeText(path: path, text: text)
end function
```

現在も `Scope.checkPath` の成功から `Scope.path` を取り出して `File.writeText` を呼べる。追加価値は、別の文字列を渡す誤りと関数の境界での範囲拡大を、契約違反として報告できることである。索引だけを足し、IO が任意の `String` を受け取る規則のままならこの価値は得られない。

対象の限定だけでは探索・バックトラック・構文解析の制御は増えない。テストの操作の差し替え・乱数や時計の固定・失敗注入は今のハンドラで書ける。範囲を持つと「テストが行いうる実 IO の上限」の記述を細かくできるが、生成器や偽の資源を自動的に得られるわけではない。取消し・解放・トランザクションの原子性も増えない。静的な範囲が分かっても、OS への判定を省けるという性能上の結論は出せない。

### 1.4 今の設計との両立

ワンショット再開・深いハンドラ・節を外で実行する規則は保てる。ただし、処理単位を名前全体に保つか、一部範囲だけ処理するかを決める必要がある。前者なら全操作を処理した名前の範囲を除き、節の範囲を足す。後者は集合差・未処理対象への転送・範囲別の節選択まで必要になり、最初の案には推さない。エフェクト変数を除けない規則は保つ。

タスクへは型で求めた範囲と実行側の制限を引き継ぐ。節が末尾再開であるという現在の条件は別に残す。`State` の解放・既存のリソースの後処理を範囲付き IO の処理で消さない。WASM のホスト操作を言語のハンドラへ渡す前は、外部のエフェクトを除けない規則を維持する（docs/todo の TODO-048・213）。現在は元ゲストの取り込み自体を禁止しているので、この規則は将来の接続条件である。

範囲は関数契約であり、ソースに許可を授ける構文を復活させなければ ADR 0147 と両立する。値を要しない案は ADR 0117 を保てる。検査済み値を証拠として併用しても、その値が許可を授けなければケーパビリティの再導入にはならない。

### 1.5 設計原則との関係

境界を越える対象の違反を実行前に報告し、既存契約の変更を比較できる点は原則1・2に合う。一方、型の文字列・和・包含の診断が複雑になると LLM の修正負担が増える。公開注釈を少数のパターンに限り、利用者にはコードの型をそのまま読ませず、第7節の操作と対象の表を示す案が原則3・4に合う。LLM の生成・修正成功率は未測定である。

篩型と範囲付きのエフェクトをそれぞれ別のパターン文法で作る必要はない。対象値の所属と計算の対象上限で、同じ意味の定義・包含器を使う。ただし二者の保証は区別する。汎用的な述語構文を先に足すことは、原則5・6から推さない。

### 1.6 形式化の費用

0.0.8 で難所になった三種のうち「エフェクトに値を持たせる」「エフェクトを外す」に当たる。閉じたパターンに限定すれば一般の型の計算は避けられる。試作の `Scope.lean` は `patLe_iff`・`portLe_iff`、和・行代入の法則を証明したが、Release の型付け・継続・ストア・ハンドラへは未接続である。

特に `mutual_cover_not_equality` は、広い原子と「狭い原子＋広い原子」が相互包含でも構造上等しくないことを示す。現行 `Eff.eq_of_sub_of_sub` の前提・結論をそのまま残せない。構造の等号を保ち意味上の包含だけ別にする案、冗長な原子を除く正規形を証明する案を選ぶ。`split_ports_not_complete` のとおり、一原子ずつの被覆では和による完全な包含も得られない。

必要な新しい結論は「実際の事象の対象が宣言範囲に入る」である。進行・保存・脱糖の型保存の各場合を移し、組み込みの対象の取り出し・保持・使用の契約を証明または明示した信頼条件とする必要がある。現行の `io_op` と結果型の仮定だけから導いたことにしない。未証明の対象健全性を新しい公理にして費用を小さく数える案は推さない。

試作の見込みは Lean 28〜65時間・処理系34〜80時間で、和による完全な包含は各20〜50時間・12〜30時間の追加だった。これは過去の暫定見込みであり、本実装の実測ではない。対象意味と第6弾との接続を加えると、この値を上限とはできない。直接変更20〜35ファイル・広い影響先50〜80ファイルの点検という試作の概数を、最初の設計固定時に取り直す。TODO-250 の重い項目一つに数える。

### 1.7 互換性と構成

範囲なしの `File.Write` を全対象の上限として残せば、範囲注釈は追加として始められる。既存のすべての IO 引数を検査済み型へ変えるなら、標準ソース・ゴールデン・examples・Skill の例・ハンドラの節を広く移行することになる。影響件数は未集計であり、試作の Lean の言及数をコードの移行件数に使わない。

パターンのデータと包含の判定を小さい中核に置き、ネットワーク・WASM・暗号・サーバの実装へ直接依存させない。ポートは0〜65535、整数の意味は言語の幅で決める。文字列長・ノード数・予算の加算はホスト幅に応じた検査を行い、64ビットの `usize` を前提にしない。

### 1.8 学習の価値

エフェクトの行を対象集合の上限として解釈すること、構造の等号と意味上の包含の違い、操作の実引数と静的契約の接続を学べる。単にパターンの包含が証明できることと、処理系が範囲を守ることの間に何が要るかを読む題材になる。形式化の費用に見合う、独立した学習の中心にできる案である。

## 2. 篩型と範囲の解析

### 2.1 何を表せるか

篩型は、基礎となる型に値の条件を加える方式である。三つの先行例を一次資料で確認した。以下は2026-10-26に確認した文書・該当例の比較であり、各処理系を実行した結果ではない。

| 方式・一次資料 | 表現・注釈・推論 | SMT と証明できないとき |
|---|---|---|
| [Liquid Haskell の仕様](https://ucsd-progsys.github.io/liquidhaskell/specifications/)、[公式 tutorial](https://ucsd-progsys.github.io/liquidhaskell-tutorial/Tutorial_01_Introduction.html)、[設定と診断](https://ucsd-progsys.github.io/liquidhaskell/options/) | Haskell の型に論理条件を付ける。関数署名、型別名、データの条件、長さ等を論理へ移す measure を記す。局所の篩を推論し、関数の入出力の契約で呼び出しを検査する。診断は推論型・期待型と関係する変数の文脈を示す | SMTLIB2、既定 Z3。証明義務を満たせないと篩の検証に失敗する。`assume`・検査を外す指定は別であり、保証を得た証拠に数えない |
| [F* の篩と部分型](https://fstar-lang.org/tutorial/book/part1/part1_getting_off_the_ground.html)、[SMT との接続](https://fstar-lang.org/tutorial/book/part1/part1_prop_assertions.html) | `x:t{p}`、依存する関数契約、lemma・assert・tactic 等で証明を補う。単純な条件は自動で扱えるが、任意の性質が注釈なしで推論される方式ではない | 既定の自動証明は SMT。証明不能は位置付きの型・assert のエラー。公式例は証明の具体化や fuel/ifuel の調整を案内する。assume/admit が残った証明を完了としない |
| [Dafny reference §5.6.3・§13.7](https://dafny.org/latest/DafnyRef/DafnyRef.html)、[公式 guide のループ・配列・探索の例](https://dafny.org/latest/OnlineTutorial/guide) | subset type と、requires/ensures・invariant・decreases・ghost/lemma を組み合わせる。Dafny 全体を篩型だけの言語とは分類しない。添字・整列性・探索の正しさは契約と不変条件から検査する | Boogie・Z3 を用いる。未証明や時間切れを検証成功としない。真でも自動証明できないことがあり、補題・不変条件・検証の分割が要る |

注釈量を行数比で比べる測定は今回行っていない。公式の例から確認できるのは、短い数値範囲に少数の署名で済む場合と、再帰・整列性・ループで補題や不変条件を要する場合があることである。「SMT があるので注釈がほぼ不要」「証明不能なら自動で実行時検査になる」と一般化できない。

第6弾の解析は篩型そのものではない。公開型・関数契約を変えず、局所の正常値を整数の閉区間で近似する。SMT を使わず自作し、関数の境界を越えないという決定を、F* 等の採用によって暗黙に変えない。次の段には、(a)局所解析の対象を増やす、(b)閉じた端点の篩を型へ加える、(c)他の値・長さに依存する契約を加える、という別々の選択肢がある。

### 2.2 権限制御での使い道

パス・ホスト・ポートの所属を値の条件で表せば、TODO-283 の「対象」に使える。篩を満たす値だけを IO が使う規則まで接続すれば、範囲付きのエフェクトへの証拠にもなる。篩だけでは「利用者が許可した」「誰が権限を取得できる」「操作が何回使える」は得られない。

一般の述語や SMT を権限の方針の言語にする案は推さない。方針は、プログラマでない人が操作と対象を理解できる必要がある。型で細かい性質を証明しても、実行側は同じ対象意味に基づいて方針を照合し、OS で表現できない部分を処理系の判定で補う。未知の篩を許可に読み替えない。

### 2.3 実用の機能での使い道

添字の範囲を実行前に除外するには、整数と対象リストの長さの関係が要る。次は依存する篩を導入する場合の擬似コードである。構文 `Integer{...}` と `List.getProven` は案である。

```bnt
// 案: i と xs の関係を関数契約に保持する場合
function at[T](xs: List[T], i: Integer{0 <= value and value < List.length(xs)}) -> T
  return List.getProven(xs: xs, index: i)
end function
```

現在の `Range.checkIndex` は成功値に元のリスト・添字・要素を保存し、`Range.get` が要素を返すので、実行時に検査した後の利用は既に書ける（03-06「Range」）。上の追加価値は、その関係を呼び出しの前に証明し、成功を返す API として契約へ残せることである。第6弾の `i` と `n` の独立した区間からは `i < List.length(xs)` を一般には得られない。

空でないリストも `NonEmptyList` で検査と安全な `head` が既にある。次の段の価値は、既知の構築や枝から非空を推論して受け渡しを減らすことになる。整列済みのリストは要素どうしの関係であり、長さの区間では表せない。現行でも宣言モジュール内で検査する `@opaque` な包みは書ける。ソートの実装が整列性を保存すると静的に証明するには、比較の法則・再帰の契約・要素の関係の扱いが新しく要る。局所の構築器の持ち出し禁止・破壊的更新の隔離は、篩とは別に現行の専用規則で守る。

テストには、閉じた整数範囲から有効入力を作る用途がある。現在も `Property.integer(low: 5432, high: 5439)` を使える（`src/prelude/stdlib/Test/Property.bnt:112`）。新しい篩があれば、その同じ条件から呼び出しを生成し、境界の値を加える余地がある。任意の論理条件から生成できるとはしない。整列済みなら列を生成してソートする等の専用方式が要り、空条件・生成の偏り・縮小時の条件保存も定める。第8節で tools/derive との接続を示す。

篩が探索・解析器の前提と結果を表せても、多重再開や探索順の制御を追加するものではない。解放・取消し・トランザクションも別の機構である。検査の消去を行えば速度に関係する可能性はあるが、意味保存が未証明の段階では実行時検査を残す。解析・SMT の費用も含めた性能の改善は未測定である。

### 2.4 今の設計との両立

局所解析だけなら、型とハンドラの既存規則を保てる。型へ導入する場合は、節が作る値も篩を満たすことを検査しなければならない。例えば IO の結果を無条件に特定範囲だとする function summary を置くと、ハンドラが別の値を返すことに対応できない。純粋な Scope の検査はこの問題を避けやすい。

ワンショット・深いハンドラ・節の外実行・タスク引き継ぎは篩と独立に保つ。可変セルの読出しや他タスクの更新をまたいで古い篩の事実を再利用しない。`State`・エフェクト変数・将来の WASM の未転送操作を処理して除く権限は与えない。篩を許可の証拠にしなければ ADR 0147・0117 を変更しなくてよい。

### 2.5 設計原則との関係

固定の範囲違反を明確に診断できる段から始めれば、原則1・4に合う。未知を「反例がある」と表示せず、「この関係を確認する情報がない」と診断する必要がある。LLM に一般の lemma や solver の燃料調整を日常のスクリプトごとに要求すると、修正の成功率への懸念が増える。利用者の権限画面には篩の論理式を表示せず、意味を定めた対象パターンへ翻訳する。

閉じた区間の API・非空の API を標準ライブラリの内側へ置けば、現在の書き方を大きく増やさずに利用できる。公開篩・自動挿入の実行時検査・証明付き API を同時に導入すると、同じ失敗が型エラー・Result・実行時エラーのどれになるか分かりにくくなる。各段で一つの契約を定める。

### 2.6 形式化の費用

局所解析の追加は Surface と独立解析層で行える。閉じた端点の篩を Release へ加えるだけなら、エフェクトに値を入れる変更でも、エフェクトを外す変更でもない。型の等号を構造の一致に保ち、範囲の包含を別にすれば、三種のうち「型の計算（計算した後の型の等しさ）」も必須ではない。しかし、新しい値の部分型は `Ty.Le.eq_of_not_fn` 等の非関数型の包含を等号へ戻す補題を変える。三種だけが重い改造の全てではない。

値依存の条件まで許せば、型・項の束縛・移動・代入が結び付く。条件の算術的同値を型の等号にも使うなら、型の計算の難所が加わる。どちらの設計でも、型の意味、組み込みの篩の保存、ストア・継続・関数契約、検査器の健全性、脱糖の型保存を通す必要がある。

第6弾の `NormalSoundness`・`WarningSoundness` は対象構文の評価関係に対する定理であり、Release・VM との意味の一致は証明していない。警告の証明を、そのまま安全な添字 API の前提や検査除去の証明にはできない。新しい型付けへ接続するか、篩を消去する脱糖と実行をつなぐ意味の定理を別に作る。SMT の健全性を公理として足す必要はなく、まず自作の有限判定器の健全性を証明する案を推す。

docs/todo の TODO-022 の試作 `findings.md` は、閉じた区間の Release 導入を Lean 32〜80時間・処理系40〜100時間、値依存を各80〜200時間・80〜240時間と見込んだ。これも実測ではない。第6弾で数値領域の再利用は増えたが、主な難所である部分型・置換・主定理への接続は残る。篩型の本実装は TODO-250 の重い一項目とし、範囲付きのエフェクトや捕捉検査と同時に本実装しない案を推す。

### 2.7 互換性と構成

追加の局所解析を警告に限れば通常の受理を保ちやすいが、`--deny-warnings` への影響を確認する必要がある。関数が篩を要求するように変えると、動的入力に検査を挿入する移行が要る。全 IO・全添字 API の一括変更は推さない。生成器が不透明型を無検査で構築する変更も避ける。

SMT を必須依存にしなければ組込み構成を保ちやすい。仮に後で外部 solver を比較しても、solver の有無で型・エフェクトの意味を変える構成は作らず、検査の受理範囲・保証を明示する別の設計判断を要する。言語整数と数学上の中間値を区別し、ホストのポインタ幅で条件の真偽が変わらないようにする。

### 2.8 学習の価値

抽象解釈の近似と型の契約の違い、部分型、関数の入出力の関係、定理を solver に委ねる範囲と小さい判定器の健全性の違いを学べる。閉じた整数区間だけでも独立した学習の中心になる。整列性・値依存・任意の SMT 論理は、その中心の完了に必要な条件にはしない。

## 3. 検査済みの値の不透明型と表層の解析

### 3.1 何を表せるか

現行の `CheckedHost`・`CheckedPath`・`CheckedEndpoint` は、保存した条件への字面の所属を表す不透明な通常のレコードである。同じ型でも条件が異なる。`@opaque` はモジュール外の構築・更新・表現パターン・自動アクセサを隠す属性であり、これらのレコードを Release の組み込み `Ty.opaque` と同一視しない（07-04「01-12 との対応」）。

延長は三つに分かれる。(a)既存の純粋 API を保ち、成功の同じ値の射影を局所の解析で追う。(b)検査済み型を受ける IO のラッパーを加える。(c)既存 IO 全体に検査済み型を必須とする。(b)(c)でも型の名前だけでは特定条件への所属を証明できず、保存した条件の照合・再検査、または型の索引が要る。名前を `AllowedPath` に変えるだけで許可の証拠にはならない。

### 3.2 権限制御での使い道

(a) は「対象」を実行前に説明する補助情報になる。(b) は検査した値と操作の引数を一致させやすい。(c) は全経路での強制に近づくが、スクリプトが作る条件と方針との一致は別に残る。許可そのものを表す値は、信頼する実行側が発行し、方針・実行の識別と失効を定める必要があり、第4節のケーパビリティの案になる。

現行 Scope の文字列の条件を、ファイルシステムで解決したパスの制限と同じ意味に変更しない。リンク先・DNS・HTTP のリダイレクト・検査後の変更は、サーバモードの実行時判定が扱う。0.0.13 で純粋な成功の解析だけを加える場合は「許可」や「隔離」と報告しない。

### 3.3 実用の機能での使い道

次は現行の API の形に合わせた擬似コードである。新しい解析を足した場合の情報をコメントに示した。関数の宣言・型自体は変えない案である。

```bnt
function writeReport(raw: String, text: String) -> Result[Unit, String] uses File.Write
  return match Scope.checkPath(pattern: "/data/reports/**", path: raw) with
    case Result.Ok(checked) ->
      bind path <- Scope.path(checked)
      // 案: この同じ値の射影は、字面として /data/reports/** に属すると解析する
      return File.writeText(path: path, text: text)
        |> Result.mapError(r: _, f: lambda(error) IOError.message(error))
    case Result.Error(_) -> Result.Error("出力先が報告用の範囲に入らない")
  end match
end function
```

現在もこの検査・分岐・書き込みは書ける。追加価値は、同じ局所の値を後で別条件の検査へ渡す場合の確実な不適合の報告と、対象の説明の材料である。呼び出し先の関数まで範囲を伝える価値はない。IO の対象上限に使うなら、対象の引数だけでなくハンドラの置換を反映する別の解析が要る。

アルゴリズムには、`CheckedIndex` の同じ対象への射影や非空の検査の function summary を次の段の候補にできる。第6弾はそれらを対象外としたので、追加には値と元のコレクションの対応の証明を要する。整列性は検査関数と不透明な包みで実行時に扱え、一般の証明器を先に作る必要はない。

テストでは無検査の内部値を作らず、通常の検査関数から有効値を作れる。ただし実 OS の権限を表す型にした場合は、テストが任意に発行できる構成子を追加しない。純粋な検査済み値のテストと、偽の IO による動作のテストを分ける。実行時の検査を必須に保つ案に、検査除去による性能改善は見込まない。

### 3.4 今の設計との両立

(a) は通常の Call・Result・レコードを保つ。純粋な標準 Scope 関数を同定するため、IO 操作のハンドラによる置換と直接衝突しない。ハンドラの保護本体・節・ラムダ・タスクは第6弾と同じく別の解析入口とし、外の局所事実を推測で引き継がない。`resume` の回数・深さ・節の外実行、エフェクト変数・`State`・外部操作の消去禁止は保つ。

(b)(c) のラッパーをハンドラで差し替える場合は、その戻り値に主張する条件を節が守るかを検査する。実 OS のハンドルをテストで差し替えるときも解放は `State` のままにする。ADR 0117 は、純粋な検査済み値が許可を授けない限り変更不要である。ADR 0147・0177 も保つ。

### 3.5 設計原則との関係

(a) は注釈と新構文を増やさず、第6弾と同じ診断の由来・未知への退避を使えるため、原則4〜6に合う。一方、型の契約として残らないので、関数境界を越えた変更を見落とさないという原則2への効果は限られる。型導入の代わりになると説明しない。

(b) は同じ IO の書き方を増やすが、同じ値を使うことを API が要求するという理由を明示できる。(c) は短いスクリプトにも必ず検査と取り出しを要求するため、対象全体の意味を決める前には推さない。LLM による成功率・診断の修正率は三案とも未測定である。

### 3.6 形式化の費用

(a) は `Checked.Scope` と Surface の解析層の拡張が中心で、Release の型・エフェクト・主定理を変えずに設計できる見込みがある。第6弾の成功値の番号・所有元・直接射影の認定、忘却・予算・独立交換を構造として再利用する。Scope 用の対象領域と標準の評価規則、その規則が検査の小モデルと一致する証明は新しく要る。

その場合の保証も A1 と同じく対象構文の評価関係までとなる。そこから「実 IO の対象が方針内」を得たことにはならない。型・エフェクトに値を持たせる変更も、エフェクトを除く変更も避けられるが、実操作の保証へつなぐなら重さを再評価する。(b)(c) の実行時 API だけの追加は、通常の型保存と成功値の意味の小証明を分ける。独自の公理は必要ない。

(a) の限定版は Lean 12〜28時間・処理系16〜36時間・文書等4〜8時間の暫定見込みとする。根拠は第6弾が Range 成功の追加を各6〜12時間・10〜18時間と見込んだことと、今回は一段/多段のパターン・文字列・ホストとポートの積を加えることである。実測からの外挿ではない。新規の領域・標準規則・成功記録・健全性・交換で概ね6〜12ファイル、補題20〜45件を計画前の目安とする。既存の主定理全体を移す重い本実装より小さいが、S1 の重い改造へ当然に相乗りできるとはしない。

### 3.7 互換性と構成

(a) を報告・警告に限り、現行 E0459〜E0462 の拒否範囲を勝手に広げなければ、既存 API と生成コアを保てる。新たに静的拒否する案なら、動的な `Result.Error` を観察するコードとの非互換を別に数える。Range の失敗を通常の値として保つ規則を Scope へ機械的に移したり、その逆をしたりしない。

検査本体は現行のヒープに依存しない `builtins/checked_scope` に保ち、解析から OS・ネットワークへ問い合わせない。文字列・パターンの予算は整数端点だけの予算と別に費用を数え、32ビットでも溢れない形で制限する。構成から外したモジュールを、標準の名前だけを手掛かりに補って受理しない。

### 3.8 学習の価値

検査して作る API の不変条件、名目型が表すことの限界、実行時の成功から局所の事実を得る function summary、解析と実行の意味の接続を学べる。篩型の型導入へ進む前に、パターンの領域が実際のスクリプトで使えるかを確かめる段として適する。

## 4. object-capability と資源のハンドル

### 4.1 何を表せるか

object-capability は、偽造できない参照によって対象と操作の権限を与え、その参照を渡して委譲する方式である。次の言語・仕組みを調べた。確認日は全て2026-10-26である。言語全体の方式、資源 API、参照の別名に対する制約を同一視しない。

| 調べた対象・一次資料 | 確認した範囲と相違 |
|---|---|
| Pony の [Object Capabilities](https://tutorial.ponylang.io/object-capabilities/object-capabilities)、[Derived Authority](https://tutorial.ponylang.io/object-capabilities/derived-authority)、[Trust Boundary](https://tutorial.ponylang.io/object-capabilities/trust-boundary) | 対象と操作の権限を持つ参照を受け渡し、権限を限定して渡す。C-FFI は信頼の境界となる。モジュールを取り込むだけで外部の資源へ自由に届く経路を残さないことが前提である |

Benitoite に移す場合の最小案は、実行側から発行された根・権利の集合を保持する不透明な `Directory` 等を引数に渡し、操作はそれを必須とする方式である。型注釈は `Directory` と普通の関数型に抑えられるが、同じ型の異なる根は値として照合する。根の同一性まで静的に区別したいなら、生成的な名前や第5節の捕捉の仕組みを加える必要がある。診断は型の違いと、実行時の根・権利の不足を分ける。

### 4.2 権限制御での使い道

TODO-283 の「権限を誰が持つか」に直接対応する。ファイルの根・接続先の集合・読書きの権利を値に保持すれば、「対象」「操作の種類」も限定できる。権限を減らした値を作って渡すことは attenuation の一形態になるが、「この計算の間だけ有効」という寿命までは通常の値だけでは表さない。回数・秘密の流れも自動では制限しない。

実行側は ADR 0183 の方針から初期のハンドルを発行し、同じ方針から実行時の判定と OS の制限を導く案にできる。スクリプトが任意の絶対パスから許可済みハンドルを作れる API を残すと、この保証は成立しない。生の IO を併存させる移行期には「ケーパビリティを持たない関数は絶対に操作できない」と説明できず、従来のエフェクトと実行側の制限を引き続き保証の基準にする。

「持つ者」は、直接の引数だけでなく、レコード・閉包・返された関数を通して操作に届く計算も含む。ログへの追記関数だけを渡す設計も権限の委譲になりうる。型に `Directory` が見えないコールバック経由の権限を見落とさないことが、ADR 0117 の再検討点である。

### 4.3 実用の機能での使い道

次は、出力用の根を引数に渡す `.bnt` の擬似コードである。`Directory` とその操作は案であり、現在の API にはない。

```bnt
function exportReport(root: Directory, text: String) -> Result[Unit, IOError] uses File.Write
  return Directory.writeText(root: root, path: "report.txt", text: text)
end function

// 案: テストは同じ振る舞いの偽の根を渡す
bind fake <- FakeDirectory.empty()
bind result <- exportReport(root: fake, text: "売上の集計")
Assert.equal(actual: FakeDirectory.read(fake, "report.txt"), expected: "売上の集計")
```

この例の偽の根には設計上の選択がある。`Directory` が OS ハンドルを表す具象的な不透明型だけなら、`FakeDirectory` を同じ型として任意に作ることはできない。実際の一時ディレクトリを使うか、操作をハンドラへ通すか、普通の関数を欄に持つ操作の組・型クラス等の差し替え可能な抽象を設ける必要がある。テスト専用に偽造できる許可トークンの構成子を公開する案は採らない。

ハンドラとの比較では、関数が二つの根や二つの接続を同時に受け取るとき、どちらを使うかを引数で指定できる点が追加価値になる。今もハンドラの節でパス・要求の引数を調べ、失敗の注入・記録再生・固定時計・固定乱数を実装できる。値の注入がないとテストできないわけではない。操作の組を普通の関数として渡す依存の注入も現在のレコード・関数で書けるので、その便宜だけをケーパビリティ本実装の採用理由にしない。

アルゴリズムには、表や状態の操作の組を渡す形で再利用できるが、それは外部権限の値でなくても書ける。Pony の reference capabilities は共有・移送の検査に役立つ別の拡張で、現行の局所構築器に対し、持ち出し・タスクへの移送を安全に許せる可能性を調べる対象になる。object-capability の値だけでは更新の競合・解放・一回限りの使用を解決しない。取消しは既に行った書き込みを巻き戻さず、トランザクションにもならない。ハンドル保持による解決の再利用と、委譲・失効の確認の費用はともに測定対象である。

### 4.4 今の設計との両立

資源の操作を従来どおりエフェクトの操作として発行すれば、ワンショット・深いハンドラ・節の外実行・タスクの引き継ぎは保てる。ハンドルが与えるのは操作対象と権利、エフェクトが表すのは実際に行わせうる操作の種類、と分担させる案である。型の `uses File.Write` をハンドルがあるから消す設計は、既存の保証を変えるので推さない。

ハンドラが IO を偽の操作に置き換えるなら、外部権限の検査は実際のホスト操作の直前で行う。ハンドラが別の実 IO を呼ぶ場合はその操作も検査を通す。`State` の解放を処理したエフェクトとして除かず、資源の根と権利は後処理が終わるまで保持する。タスクにハンドルを渡すなら、子を待つ前に親が閉じる場合、取消し、共有、失効を設計する。捕捉検査を持たない案では解放後の使用の実行時拒否が残る。

WASM へ資源を渡す場合も、ホストの表で有効性と権利を検査し、現行の外部境界の規則を保つ。単なるゲストの整数を許可のハンドルとして信用しない。ADR 0147 は、発行元をソース外の実行側に保てば両立する。ADR 0117 の「値を設けない」は変更を要する。`main` に新引数を必須とするか、実行側が渡す限定 API を別に設けるかも選択肢であり、以前の `Capabilities` 全体をそのまま戻すことは推さない。

### 4.5 設計原則との関係

操作の種類と対象の委譲という異なる役割に分けられるなら、エフェクトと値の併用は原則5への違反と直ちに決まらない。現在の値なしの IO と同じことを全て二重に書かせるだけなら、ADR 0117 の記述量と重複の指摘が今も成り立つ。少数の資源の境界へ閉じ込める案と、全関数へ根を渡す案を比較すべきである。

利用者にはハンドル ID・型引数・捕捉集合を読ませず、「報告用の保存先への追記だけ」「この処理へ渡す接続先」と対象・操作を示す。LLM は引数の渡し忘れを型で直せるが、根の違いが同じ名目型だと型だけでは誤配布を検出できない。捕捉と発行元まで追うことの価値は別に評価する。

### 4.6 形式化の費用

不透明な通常値と普通のエフェクトだけなら、Ty/Eff の表現を保った API を作る余地がある。しかし `Ty.opaque` の型が付くことだけから、ハンドルの非偽造性・根から出ないこと・委譲が権限を広げないことは導けない。資源表・発行元・権利・対象解決と事象の関係を定義し、到達可能な値と実行の不変条件を証明する必要がある。既存の値の型保存だけを権限の定理と呼ばない。

生成的な根の名前や捕捉を型へ加えなければ、三種の難所を必ず伴うわけではない。一方、権限を型から除く規則、寿命・地域名、参照の別名まで加えると保存・代入・ストア・継続・脱糖が広がり、重い項目になる。進行には権限の拒否や失効した資源の応答を含め、成功しかない規則にしない。OS の処理の正しさは新しい公理で保証したことにせず、形式化の内外と信頼条件を分ける。

API のみの試作と、型の規則・全 IO を置換する本実装は見積もりを分ける。少数の資源の API と純粋な委譲の小モデルは Lean 8〜20時間・処理系16〜40時間の見込み、権限の安全性を含む本実装の時間は不明とする。根拠は現行 `Checked.Scope` の検査・保存と、既存のリソース実行器を使える点である。ただし実パス・接続・取消しの保証はその類例に含まれないので、サーバ・OS 層までこの幅に含めない。Pony 全体の参照規則の移植は別の重い項目である。

### 4.7 互換性と構成

必須ハンドルへ全 IO を切り替えると、引数・ハンドラのパターン・公開署名・テスト・examples・Skill の例の移行が広い。ソース全体の件数は未集計である。追加のハンドル API を用意するだけなら互換性を保てるが、古い入口が残る限り、言語全体の object-capability の保証を宣言できない。

権利とハンドルの中核の意味を OS ごとのバックエンドから分け、ネットワーク・ファイル・WASM を構成で外せるようにする。cap-std の使用は IO 基盤での選択肢であり、型・エフェクトの中核を既製のライブラリに置き換える案ではない。導入の適合性・必要機能・ライセンス・版固定はこの調査では評価していない。資源 ID・世代・権利のビット幅をポインタへ詰める64ビット専用の前提を増やさない。

### 4.8 学習の価値

外部の権限を値として委譲すること、参照と権利の関係、失効、閉包から届く権限、API の非偽造性と OS の資源の意味を学べる。Pony の reference capabilities も有力な学習の題材だが、権限のハンドルと同じ課題として一度に実装しない。将来のサーバモードの発行・委譲の小モデルとして調べる価値がある。

## 5. Scala 3 の capture checking

### 5.1 何を表せるか

Scala 3 の公式文書 [Capture Checking Basics](https://docs.scala-lang.org/scala3/reference/experimental/capture-checking/basics.html)、[Capability Polymorphism](https://docs.scala-lang.org/scala3/reference/experimental/capture-checking/polymorphism.html)、[Scoped Capabilities](https://docs.scala-lang.org/scala3/reference/experimental/capture-checking/scoped-capabilities.html) を確認した（2026-10-26、表示版3.10.0の experimental の文書）。確認時の文法を Benitoite や過去版の Scala の確定構文として扱わない。

`T^{c,...}` は値が捕捉するケーパビリティの参照を型に記す。`A ->{c} B` には関数の捕捉が現れ、捕捉集合の包含を型の適合に使う。局所の logger が保持する file system への参照を通じた間接の捕捉も扱う。通常の変数・関数の局所の型は推論できるが、公開境界や捕捉を制限する型には注釈が要る。公式例の診断は、実際の捕捉集合と要求された集合、外へ出せない参照を示す。scoped capability の例は、閉じるファイルを捕捉した関数が外へ出るのを拒否する。

この機構は対象の文字列の篩を推論するものではない。`fs` と `otherFs` の権限が何であるかは、その値を発行する API の意味で決まる。capture checking という原語を用い、今回新しい日本語の術語は提案しない。定着した日本語訳の一次資料は確認できなかった。採用時に用語集へ追加するなら、日本語表記を設計者に選んでもらう。

### 5.2 権限制御での使い道

「権限を誰が持つか」を、引数の型だけでなく、返す関数・遅延した値・格納先を通して静的に追える。ADR 0117 の閉包に関する理由を見直す直接の先行例である。捕捉していることは実際に使うことの証明ではなく、使いうる権限の上限である。

方針から発行する値が対象を限定すれば、対象と持つ者を組み合わせられる。capture checking のみで、初期権限・DNS・リンク・外部コマンド・ホストの実装を制限したことにはならない。ADR 0183 による発行・実行時判定・OS の強制と組み合わせる必要がある。参照の捕捉と秘密の情報の流れの非干渉は別であり、S3 の課題を解消したことにしない。

### 5.3 実用の機能での使い道

次は閉じる資源を捕捉したラムダの持ち出しを検出する案の擬似コードである。現行では閉じた後の使用を実行時に拒否する。capture の型表記は採用未定なので記さない。

```bnt
// 案: makeWriter の戻り値が writer を捕捉すると型で追う
function makeWriter(path: String)
    -> (function(text: String) -> Result[Unit, IOError] uses File.Write)
    uses File.Write, State, Process.Exit
  with writer = try File.openWriter(path: path, mode: File.WriteMode.Replace) or die do
    return lambda(text) File.writeLine(writer: writer, text: text)
    // 案の検査: 閉じる writer を捕捉する値をこの with の外へ返せない
  end with
end function
```

これは寿命と捕捉を接続する案であり、captured という属性一つを加えるだけでは実現しない。局所の構築器は今も捕捉・格納を専用規則で拒否する。一般の捕捉検査を作る価値は、限られたコールバックへの受け渡しや局所状態の抽象化を、個別の禁止より広く安全に許せる可能性にある。探索・解析器の継続の再開回数は別の機構である。

テストでは偽の IO・時計・乱数の値を渡せば、どの実行側の資源に届きうるかまで型で確認する用途がある。今のハンドラによる差し替えに加わるのは、関数や遅延値に保存された権限の上限であって、記録再生や失敗注入の存在ではない。解放・時間切れ・取消しで資源が無効になる範囲を型に結ぶには、タスクの寿命や返す値の規則も必要になる。捕捉を追うだけでトランザクションや確実な解放は得られない。最適化や性能への効果は未確認である。

### 5.4 今の設計との両立

既存エフェクトに捕捉の検査を加える案と、ケーパビリティの捕捉をエフェクトの基礎にする案がある。前者なら `resume` の回数や深いハンドラを保てるが、節の外で実行する計算が何を捕捉するか、継続・Task・Lazy・Reference・辞書に何を格納するかを全て検査する必要がある。名前のエフェクトから自動で捕捉集合が得られるとはしない。

タスクのハンドラの引き継ぎと、資源の参照の受け渡しは別の関係にする。親の制限を抜けた子が資源を使わない条件、ハンドラ終了時の待ち合わせ、解放の `State` を残す条件を接続する。エフェクト変数・`State`・未転送の WASM の効果を除けない規則は維持する。権限を授ける構文を作らなければ ADR 0147 を保てるが、権限の値を採用する部分は ADR 0117 の変更になる。

### 5.5 設計原則との関係

捕捉を含めた契約と逸脱を実行前に示せることは原則1・2に合う。一方、捕捉集合の依存・局所の名前を外へ出さない規則・多相の診断は複雑になり、LLM が新しい書き方をどの程度修正できるかは未測定である。通常の利用を推論に寄せ、局所資源の抽象の作者へ注釈を集中させられるかが採用条件になる。

Scala の公式文書の高階関数の例は、厳格な List と遅延した List で結果の捕捉が違うことを示す。Benitoite でも実行時のエフェクトと、値が後まで保持する資源の違いを診断で説明する必要がある。両者を同じ表示語で済ませる案は原則4に合わない。

### 5.6 形式化の費用

値の参照が型に入るため、型と値の環境、束縛・移動・代入・一般化・適合、閉包・ストア・継続の型付けを変える。寿命を含めるなら新鮮な名前と外への持ち出し禁止も要る。捕捉集合の計算が必要でも、それだけで三種の「型の計算（計算後の型の等号）」に当たるとは限らず、集合の構造の等号と包含を分ける設計を比較する。権限を局所で隠してエフェクトも除くなら、別に「エフェクトを外す」難所が加わる。エフェクト自体に値を入れない構成でも、軽い表層 lint では済まない。

進行・保存・エフェクト健全性・脱糖の型保存は、新しい型と値環境の条件を持つ場合を通す必要がある。現行の形を全て変更せず追加の定理として示すかは小モデルで判断する。Scala の定理を参照するだけで Benitoite の証明が成立するわけではない。独自の公理で捕捉検査の健全性を仮定しない。

Benitoite の構文・Task・with に限定した独立小モデルは Lean 8〜20時間、全体への移植は時間不明とする。根拠は TODO-248 の試作が、引数・戻り値だけでは閉包を通る持ち出しを防げず、局所文脈・ストア・継続まで要すると示した点である。0.0.13 で本実装するなら、篩型・範囲付きエフェクトとは別の重い一項目として範囲を絞る必要がある。

### 5.7 互換性と構成

現在許される資源の捕捉・持ち出しを拒否するので、既存コードの受理を狭める可能性がある。匿名関数・Lazy・Task・Reference・型クラス辞書・生成コード・標準 API の全てに影響先がある。Scala の標準ライブラリの移行実績を Benitoite の移行件数に代用できず、件数は未集計である。

型検査は OS のライブラリを直接必要としないため、構成の境界は保てる。ただしサーバ構成だけ捕捉の意味が変わる設計は避ける。名前・資源の ID はポインタ幅に依存しない意味で扱い、32ビットでも同じ型の適合を判定する。

### 5.8 学習の価値

高階の値が保持する権限、型が局所の値の名前を参照するときの置換、資源の寿命、多相性を学べる。ADR 0117 の問題への解が「ケーパビリティは型に現せない」という必然ではないと確認できる。一方、0.0.13 の範囲を決める前に既存の所有・捕捉・ハンドラの規則との小モデルを作るべき案である。

## 6. Effekt のケーパビリティと捕捉（S1 との重複）

### 6.1 何を表せるか

公式 tour の [Captures](https://effekt-lang.org/tour/captures) を本文まで確認した（2026-10-26）。計算・関数・ケーパビリティは既定で第二級であり、ハンドラが導入する能力を暗黙または明示して渡す。値として保存・返却する場合は box を使い、その型の capture set で能力が有効な範囲にあるかを検査する。公式例は能力そのものと、それを閉じ込めた関数の持ち出しを型エラーにする。2020年論文は今回は本文を精読しておらず、公式 tour の現在の説明を根拠とする。論文の方式・高階エフェクトの詳細は S1 に委ねる。

### 6.2 権限制御での使い道

「誰が操作できるか」と「どの範囲の計算で能力を使えるか」に対応する。ただし、エフェクトの要求は呼び出し側のハンドラで満たせる要求であり、OS の操作を許可されたこととは区別する。固定した特定能力の捕捉と、文脈に要求するエフェクトも違う。パス・ホストの範囲と実行側の発行方針は別途必要である。

### 6.3 実用の機能での使い道

次は能力を明示する場合の擬似コードである。第二級引数とその構文は未決の案である。

```bnt
// 案: どの保存先の操作を要求するかを明示する
function buildReport(output: ReportSink, rows: List[Row]) -> Unit
  ReportSink.write(output: output, text: formatRows(rows))
end function
```

能力をハンドラで与えるなら、実ファイル・メモリ上の記録・失敗の注入という解釈を変えられる。現在も一階のエフェクトとハンドラで同じ差し替えは書ける。追加価値は、どのインスタンスかの明示、能力を使う計算の受け渡しと保存を型で制限することにある。探索・資源の括り・時間切れ等の高階の例は S1 の評価に委ねる。この断片だけでそれらや性能の改善を得たとはしない。

### 6.4 今の設計との両立

既定の第一級のラムダと、第二級の計算・box の区別を加える点が大きい。既存の名前による動的なハンドラ選択から、能力を引数として選ぶ規則へ変えるなら、深いハンドラ・節の外実行・ワンショット・タスクの引き継ぎとの対応を個別に決める必要がある。Effekt の説明を根拠に現在の制約を自動的に解除しない。

エフェクト変数・`State`・外部の未転送操作の消去制限は、移す方式でも同じ保証を成立させる条件として残す。権限の宣言を作らなければ ADR 0147 を保てるが、能力の値・第二級の計算の導入は ADR 0117 と関数の値の規則を見直す。S1 がその変更を本実装の候補とする場合、S2 の捕捉検査を独立の相乗りとして二重計上しない。

### 6.5 設計原則との関係

能力の引数を暗黙に渡し、必要な境界だけ明示できれば、ADR 0117 の引数を渡し続ける負担を減らせる。一方、第二級・box・capture の区別は新しい学習と診断を要する。現在の一階のハンドラで済む短い自動化に、どの書き方が増えるかを比較して採否を決める。LLM の成功率は未確認である。

### 6.6 形式化の費用

計算と値の区別、能力の束縛と捕捉、ハンドラの能力への変換、型の適合と脱糖を変える。三種の難所のうちエフェクトの除去に関係する重い項目である。能力の名前や捕捉の表現によっては、エフェクトに値を持たせる変更や、計算後の型の等号にも関係するが、捕捉集合を計算するという理由だけで三種全部に分類しない。主定理の前提・結論と追加の名前の扱いは S1 の小モデルの設計で確定する。既存の定理がそのまま使えるとはしない。独自の公理を追加する案は推さず、時間は S1 と統合するまで不明とする。

### 6.7 互換性と構成

現行の普通の関数値へ第二級の制約を広く課すなら、コールバック・返す関数・格納する関数・Task・Lazy・Skill の例への移行が必要になる。限定した新機能として追加する案でも、同じ役割の二つの関数の書き方を保守する費用がある。外部依存を必須にしない自作の型規則として実装するなら組込み構成を保てるが、資源の実装の境界は第4節と同じ条件を要する。

### 6.8 学習の価値

エフェクトを文脈から要求する能力として読むこと、字句的な能力の範囲、第二級と第一級の値、捕捉とエフェクトの違いを学べる。S1 の高階エフェクトの比較に統合する価値があり、S2 だけで採否と作業規模を確定しない。

## 7. 型の範囲と実行側の方針

### 7.1 上限・要求・許可の関係

型や健全な解析で求める範囲 `R` は、計算が実際に行いうる操作の上限である。実際に必要な最小の許可とは限らない。宣言が広い、到達しない枝がある、解析が未知へ戻った、という理由で余分な対象を含みうる。従って利用者への表示は「許可の確認に使う操作対象の上限」とし、「必ず全部の対象へ操作する」と説明しない。

ここでは `P` を、利用者の方針の許可から deny を引き、実行ごとの狭める指定と共通部分を取った集合とする。スクリプトは `P` を宣言せず、範囲の型・検査条件・希望する根を記述できても、その記述自体では権限を取得しない。ADR 0147 の削除した `permissions` と、検査を受ける関数契約を分ける。

| 比較する方式 | 実行前・実行中の扱い | 判断案 |
|---|---|---|
| 型の範囲をそのまま許可にする | スクリプトが `R` を広く書けば権限も広がる | 推さない。許可を利用者がソース外で決めるという前提に反する |
| 宣言上限の包含を必須にする | `R ⊆ P` を確認できた実行だけを開始する。不成立・未知は拒否。実行中も `P` を強制する | 公開契約を厳格に守る実行の選択肢。上限の過大近似による拒否と、実際の方針違反の証明は別だと報告する。未知の文字列を常に拒否するのか、明示した検査へ直すのかを決める必要がある |
| 種類を実行前、動的な対象を実行時に照合する | 種類の上限を先に照合する。対象は既知・未知を示し、実際の外部操作の直前に `P` を検査する | 現在の将来方針に最も近い。純粋な Scope の補助解析を追加しても、対象の権限制御はサーバモードで行う。既知の契約違反を先に検出する仕組みと併用できる |
| 型の要求と方針の共通部分で実行する | 既知の `R` は自動的な追加許可にせず、実行可能な対象を `R ∩ P` に限る。動的な範囲は実行時検査へ残す | 対象の型と実事象の接続があるなら有力。ただし宣言上限が `P` を越えた場合も開始する規則なら、ADR 0183 の事前拒否との変更点を設計者が選ぶ必要がある |
| 方針から限定したハンドルを発行する | 実行側が `P` から根・権利を作って渡す。派生値は親より広げない。必要なら失効を使用時にも確認する | 将来の資源 API の候補。型に書いた範囲の静的契約とは併用可能。捕捉・閉包・WASM・古い生 IO の経路まで扱う条件が必要 |

範囲付きの契約として `R` を厳密に要求するのか、利用者への参考の解析結果として使うのかも分ける。前者の未知は契約を満たしたことにできない。後者の未知は情報が得られないこととして報告し、実行時の判定へ渡せる。第6弾の警告の A1 だけから、前者の保証へ移ることはできない。

ADR 0183 の決定4は「方針を超えると分かったプログラムは実行しない」である。上限の包含必須へ強める場合、広い `R` のまま実際は狭い対象しか使わないプログラムも拒否する。この保守的な拒否を設計として選べるが、「実際の操作が許可外だと証明した」とはしない。逆に既知の範囲まで一律に切り詰めて開始するなら、同決定の扱いを明示して変更する。S2 だけで既存の決定を読み替えない。

また、docs/todo の TODO-023・141 には「操作の種類を許し、対象の並びは空なら、実行前の判定は通る」という方針がある。対象包含の必須化はこの方針も変えうる。対象の deny を差し引いた包含、和の被覆、一段・多段のホスト、存在しないファイルの作成先について、判定できない範囲を含めて設計者が選ぶ必要がある。

### 7.2 OS の制限との接続

OS が強制できる集合を `S` とすると、ADR 0183 の方針は、表現できない指定がある分 `P ⊆ S` を許し、その差を処理系の判定で埋める形である。実行側の判定が `P` を強制して初めて、両者の組合せ `P ∩ S` が `P` になる。「OS が型と方針の共通部分を全て直接強制する」とは書かない。型の範囲も実行時に強制する設計なら、全体は `R ∩ P ∩ S` となる。

この式は、全て同じ対象と操作の意味に翻訳できていることを前提とする。現在の Scope の字面と、リンクの解決後の実体は別である。ファイルを扱う場合はリンク・rename・新規作成・検査と使用の間の変更、ネットワークではホスト名・解決した IP・ポート・リダイレクト・プロキシのどこで判定するかをサーバモードで決める。WASI の descriptor 相対の解決は設計の参考になるが、Benitoite の各 OS に同じ保証が実装済みとはしない。

解放時のバッファの書き出しと、既に開いたリソースの利用も含めて対象の権利を保持する必要がある。方針を実行ごとに固定する案と、世代・失効を使用時に検査する案は別に比較する。取消し・時間切れが、既に行った外部操作を取り消す保証にはならない。外部コマンドの内部の操作は言語の型で追えず、OS 等の制限が必要である（07-01「ハーネスとの分担」）。

### 7.3 利用者へ示す形の案

権限の画面は、操作・対象・確度・実行中の制限・前回との差を示す。型の記法やケーパビリティの名前を覚えなくても判断できる形にする。次はサーバモードの表示案であり、0.0.13 で権限制御や承認画面を実装する提案ではない。

| 行う可能性のある操作 | 対象について分かっていること | この実行で許す範囲 | 実行中の扱い |
|---|---|---|---|
| ファイルへの書き込み | 報告用のフォルダ以下。根自身を含む。契約で確認済み | 解決した `/data/reports/2026/` 以下 | その外への書き込みを拒否する。実体の解決後にも判定する |
| HTTPS での外部送信 | `api.example.com` の443番。契約で確認済み | 同じ接続先 | 転送先が変わると再判定する |
| ファイルの読み取り | 実行時の入力から決まるため、検査時に対象を限定できない | 解決した `/data/inbox/` 以下 | 対象が決まった時点で判定し、外なら止める |

`契約で確認済み` と表示できるのは対象の健全性まで接続した場合に限る。現行 Scope の成功の補助解析だけなら「この文字列は指定の条件を満たすと推定。実際の操作対象の上限は未確認」と別の確度にする。未知の欄を空白や「なし」にしない。

差分は、例えば「今回から保存先が `/data/reports/2026/**` から `/data/**` へ広がった」「型のエフェクトは同じだが接続先が増えた」「解析できていた対象が動的になった」と表示する。操作が実際に発生するか、結果が利用者の意図どおりかはこの上限からは分からない。ケーパビリティを使う場合は、利用者の方針上の名前に結び付け、「集計処理に報告フォルダへの追記だけを渡す」と示す。内部の資源 ID だけを権限の説明にしない。

## 8. アルゴリズムと Property の次の段

権限と同じ重みで実用性を比べると、最初の篩型を整数の閉じた契約に絞る案と、資源のケーパビリティを導入する案では得られるものが違う。日常の自動化で、ポート・件数・時間・分割幅の条件を関数間で保ちたいなら前者が直接役立つ。二つの保存先や接続を処理に選んで渡したいなら後者が適する。次表は現在との差と、追加で必要な仕組みを整理したものである。

| 用途 | 現在書けること | 次の段の追加価値と条件 |
|---|---|---|
| 固定のポート・件数・シフト量 | Range の検査、局所の整数区間と警告 | 閉じた篩を公開関数の契約へ置く。呼び出し・戻り値の照合で関数境界の情報を保てる |
| 安全な添字 | `Range.checkIndex` が元リストと要素を保持し、`Range.get` が要素を返す | 同じリストとの関係、または `i < length(xs)` の関係を保持する。独立した整数区間だけでは一般に足りない |
| 空でないリスト | `NonEmptyList.fromList` と安全な head | 構築や分岐から非空を導き、余分な実行時の再検査を減らす。ただし生成コアの検査を消すなら意味保存が要る |
| 整列済みのデータ・二分探索 | 専用の純粋な検査と不透明な包み、通常の再帰 | 要素間の順序、比較の法則、再帰の契約と中間の整数の範囲を結ぶ。一般の篩や専用の整列済み API が候補 |
| 局所の配列・表の更新 | 現行の専用構築器が持ち出しを拒否する。Reference の更新は State | 捕捉・共有・所有の型を加えるなら安全に渡せる範囲が広がる可能性がある。篩だけでは更新の隔離にならない |
| 偽のファイル・通信・時計・乱数 | 一階のハンドラ、または普通の関数を引数で渡す | 特定の偽の根・接続を明示して二つ以上使い分ける。許可済みハンドルの偽造を許さず、共通の操作の抽象を設計する |
| 記録・再生・失敗注入 | 操作の節で記録・応答の変更ができる | 捕捉検査があれば保存する関数の実権限を追える。再生の正しさや並行順序は別の契約 |
| 解放・時間切れ・取消し | with・TaskGroup・Task の既存の手順 | 捕捉した資源の持ち出しの静的拒否、限定ハンドルの子への配布。トランザクションの巻戻しは別の設計 |

tools/derive は型の構造に従って生成器・縮小器を合成するが、欄どうしの関係は推論しない。不透明な型自身の Property・JSON の構築を自動生成せず、その型を欄に持つ場合は欄全体の手書き関数を要求する（`tools/derive/README.md`「Property generation contracts」と412〜415行、03-06「外部生成の宣言情報」）。この境界を篩の導入の機会に無条件で外さない。

範囲から生成器を導く場合の最初の案は、閉じた整数区間だけを対象に、型の条件と `Property.integer` の端点を同じ宣言情報から作ることである。次の擬似コードの二つ目の関数は現在存在しない。現在も一つ目を明示して書けるので、利点は同じ端点の二重記述を減らし、契約の変更と生成器の変更を揃えられることである。

```bnt
// 現行 API の形: 明示した端点から生成器を作れる
bind ports <- Property.integer(low: 5432, high: 5439)
// 案: 閉じた篩の宣言情報から同じ生成器を導く
bind ports <- Generated.genDatabasePort()
```

有効値の生成器だけでは境界の外の診断を確かめられない。最小値・最大値・直外・逆転・空条件・動的入力は別に用意する。縮小器も、例えば正の数を0に縮めて篩を破らないようにする。複数欄で `minimum <= value <= maximum` を保つ場合や、生成したリスト長に合わせて添字を選ぶ場合は欄全体の手書き関数が当面適する。任意述語を満たすまで棄却するだけの生成器は、空の条件で終わらず、稀な条件で大半を捨てるため、停止・上限・分布の契約が別に要る。

0.0.13 で生成器を候補にするなら、型へ篩を入れる本実装の後に tools/derive の独立の追加として選ぶ。検査した結果から推定しただけの局所範囲を、元の型の全値域だとみなして生成器の定義には使わない。パス・ホストの場合も、文字列の所属を満たす値と、実在・接続可能・許可済みの対象を生成することは別である。

### 9.2 パターンへの絞り込みと合流

整数の凸包をパスに置き換えるだけでは精度の設計を終えられない。例えば二つの完全一致パスを共通の親の木へ合流すると、元の二つ以外の対象も含む。これは健全な上限になりうるが、権限画面の要求を過度に広げる。有限個のパターンの和を保持して上限で Top に戻す案と、共通の親まで広げる案を比べ、最初は前者を推す。合流数・要素数・文字列長に予算を置く。

単一の exact/tree のパスの交差は、包含なら狭い側、根の要素列が分かれるなら空として扱える。ホストの exact/one/many も、ラベル数と suffix の条件を併せれば交差を有限手順で扱える見込みである。これは追加の判定器と証明の案であり、現行の定理にはない。特に、試作の tree に一段の上限はなく、現行 `*.` へそのまま当てはめられない。

所属の真の枝には交差を使える。偽の枝の「木から子の木を除く」等は、現行の正のパターン一つで表せないことがある。初段は偽枝を元の上限のままにする保守的な案にし、除外・補集合・任意の glob を範囲の型へ一度に導入しない。方針側の deny を無視してよいという意味ではなく、方針との比較器はそれを別に扱う必要がある。

現行の純粋な Scope API は、Result の成功を使うことで所属の事実を得られる。任意の `String.startsWith` の真を、構成要素単位の木への所属と同じとみなす規則は作らない。`/data/report-old` と `/data/report` のような区切り、ホストのラベル境界、文字列の正規化を確認する必要がある。URL 全体を `CheckedHost` と同じ条件で扱う案も採らない。

### 9.3 再利用できない保証

第6弾の A1 は「解析が安全と言った操作は必ず成功する」という定理ではない。正常値の所属と、解析した警告の位置へ到達し正常な引数を得た場合の失敗についての条件付きの定理である。未知・取消し・資源の失敗・到達・停止性・プログラムの意図を保証しない。Scope の成功を解析に加えても、同じ条件を保つ必要がある。

篩の型を導入する場合は、関数の引数と戻り値の篩、値の置換、呼び出し、部分型、組み込みの意味との一致が新しく要る。範囲付きエフェクトの場合は、その上で「実際の操作の対象」を結ぶ新しい定理が要る。ケーパビリティの場合は、発行・非偽造性・参照からの到達・権限を広げない委譲・失効・タスク・後処理が要る。いずれも、対象の小さなモデルの証明件数を増やすだけで完成する範囲ではない。

## 10. ADR 0117 の理由を現在の条件で判定する

ADR は初回リリース時点の経緯として読み、現在の保証は07-01等と照合した。以前の `Command`・`Exit`・`FileWrite` という名前を、現在の型名として復活させない。

| ADR 0117 の理由・帰結 | 今も成り立つか | 見直す場合の条件 |
|---|---|---|
| 閉包が権限を捕捉すると、普通の関数型からは権限の到達を読めない | 捕捉を追わない普通のケーパビリティの値では成り立つ。エフェクトを残せば操作の種類は従来どおり読めるが、どの根かは通常型からは分からない | Scala の capture checking、Effekt の box/capture は、この不足を型で扱う先行例である。ただし Benitoite の型と置換の改造が要る |
| ケーパビリティとエフェクトは同じ操作を二重に制限する | 操作の種類だけを同じように書くなら成り立つ。対象・発行元・委譲を値が担うなら役割に差がある | 原則5に対する理由を「種類はエフェクト、対象と委譲は値」と具体化し、利用者に二つの権限設定を書かせない |
| `main` から引数を渡し続ける記述量が残る | 明示した値だけの方式では成り立つ | 少数のライブラリ境界へ集中する、限定した文脈引数を推論する、Effekt のように暗黙渡しと明示渡しを統一する等を比較する。新しい暗黙規則の診断の費用も数える |
| ハンドラがあればテストのための特別な値の発行は不要 | 現在も成り立ち、残す価値がある | 値の注入を足してもテスト専用の偽造可能な許可値は作らず、同じ操作を既存ハンドラまたは普通の操作の抽象へ通す |
| 影響の大きい操作の保証を型のエフェクトで述べられる | 現在も成り立つ。対象の上限を述べる保証はまだない | ケーパビリティ採用後も公開のエフェクト契約を残す案を先に比較する。根の保持を理由に `File.Write` を消さない |
| `main` にケーパビリティの引数が要らない | 現行コードの簡潔さとして成り立つ | 実行側の発行の入口を `main` の引数にするかは別の設計判断である。値の採用から自動で旧 `Capabilities` 全体を戻さない |

従って、ADR 0117 を全面的に逆転する案は推さない。「対象を限定するハンドルは種類のエフェクトと異なる役割を持つ」「捕捉を型に出す方式がある」の二点は見直す根拠になる。一方、テストだけを理由に権限の値を復活させる必要はなく、引数の伝播と形式化の費用も残る。0.0.13 では採否と順序を決めるまでとし、実際の許可済みハンドルの発行はサーバモードと合わせるという ADR 0177 の決定を保つ。

## 12. 統合の担当への申し送り

- **推す案**: 方針・型の上限・純粋な検査済み値・実 OS の対象を分ける。サーバモードでは ADR 0183 の一つの方針を保ち、動的な対象を実行時に照合する前提に、範囲の静的な情報を追加する。型の範囲に許可を授けさせない。
- **推す案**: S2 の中で0.0.13に入れやすい実装候補は、固定パターンに対する Scope 成功の同じ値の直接射影の局所解析である。第6弾の function summary と同じく、別個体・再包装・関数境界・合流で情報を仮定しない。これは対象の説明と局所診断の追加であり、範囲付き型の本実装や権限制御の代替ではない。
- **本実装を優先する場合の候補**: docs/todo の TODO-022 が示す型への導入の方向を踏まえ、閉じた整数区間の関数契約を一つの重い項目とし、後にパス・ホストへ広げる案を比較する。S1 が高階エフェクトを重い中心に選ぶ場合は、範囲付きエフェクト・篩型・capture checking の本実装を同じ改造へ重ねない。
- **推す調べ**: 資源のハンドルの発行・委譲と、捕捉される権限の違いを小モデルで確かめる。ADR 0117 の閉包の理由は普通の値には今も当てはまるが、Scala・Effekt には対処する先行例がある。許可済みハンドルの実際の発行・失効・OS 接続は ADR 0177 に従いサーバモードへ合わせる。
- **推さない案**: Scope の成功を許可に読み替える、全 IO を未設計の Checked 型へ一括変更する、任意の文字列述語・一般 SMT・範囲付きエフェクト・捕捉検査を同時に入れる、A1 の警告の健全性だけで検査を消す、テスト専用の偽造可能な権限トークンを公開する、という案は推さない。
- **設計者の判断が要る点**: 対象の上限の包含を必須にするか、動的な対象を残すか。ADR 0183 の事前拒否と対象が空の方針の扱いをどう保つか。契約の範囲と実行時の許可の共通部分を、どの層で何に対して強制するか。機械的に一つの方式へ決めない。
- **未確認の事実**: 同形のパス・ホスト条件をエフェクト引数として自動推論する先行例は今回見つからなかった。E 固有の仕組みは本文取得に失敗し未確認。Wyvern の現行実装の対応範囲、Scala・Effekt の方式を Benitoite の Task・with・WASM と結ぶ形式化、OS ごとの厳密な解決と強制、DNS・redirect・失効の契約、変更対象コードの件数、実際の性能・LLM の成功率は未確認である。
- **S1 と重なる点**: Effekt の能力・box、高階操作による権限の限定、ハンドラでのエフェクトの除去と実 IO の対応、外部ライブラリの意味を権限表示へ残す問題（docs/todo の TODO-054）。S2 は対象と発行・委譲の条件を渡し、ハンドラの方式・高階の制御の選択は S1 に委ねる。
- **S3 と重なる点**: Pony の reference capabilities、捕捉した資源の寿命・別名、失効・一回限りの使用、秘密を保持する能力。S2 は「持つ者」と「対象」を扱い、回数・線形性・情報の流れの保証を主張しない。docs/todo の TODO-269 の時期の決定も変えない。
- **統合時の注意**: 全 API を別方式へ移す決定は行っていない。0.0.13 の実装範囲は設計者の判断待ちであり、ここでの調べを実装開始の承認に読み替えない。今回の成果は本ファイルだけであり、ソース・テスト・Lean・設計書・docs/todo・git の状態を変更していない。
