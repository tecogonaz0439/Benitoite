## 判断の案と証拠の範囲

**案 G を推す。ただし、実装で受け付ける束は、方針の管理者が宣言する有限の束から始める。機密性と完全性、限定した開示と endorsement、推論する一階の印の多相を、情報流という一つの重い項目の内部で設計する。** 数学的な規則は具体の束から独立させる。任意のプログラムで束の演算を定義する機能、実行中の束の変更、高階の印の多相、一般の段階付きの型まで同時に導入する案ではない。

版の組み方は RV-S5 の (iv) を基にする。0.0.13 は案4（範囲付きのエフェクト）を中心とし、情報流の実装は 0.0.14 の独立した改造とする。0.0.13 で、情報流の保証、方針と API の境界、サーバモードの承認が必要とする情報を先に決める。サーバモードを `0.1.0` より前に実装する決定は保つ。

理由は、束を抽象化する部分より、関数・失敗・継続・入口と出口を結ぶ部分の費用が大きいためである。完全性を後で加えて旧コードにも必須にすると、旧コードをそのまま受理することと衝突する。方針と標準 API を最初から二種類の印に対応させれば、この移行を避けられる。一方、S5 の案 L を厳密に保つと、認証の応答を表示する例と、広い範囲からファイルを読む例の制限が残る。汎用化だけでこれらが解消するとは判断しない。

## 比較で共通にする規則と脅威モデル

### 数学的な汎用性と実装で受け付ける定義

印の規則を一般にすることと、方針の管理者が任意のプログラムで束を実装することは分ける。前者では、束 `L`、順序 `⊑`、底 `⊥`、結び `⊔` を引数にし、通常の式の結果に入力と pc の結びを付ける。SF の `System`・`Observer` は既にその形の一部であり、`noninterference` は二点の印に固定されていない。SF の `System` 自体には束の全法則が入っておらず、証明に必要な可視性の法則は `Observer` に置かれている点に注意する。

実装で推す形は、有限の要素と順序の表、または有限集合の積などの既知の構成から、処理系が結び・交わりを確定する形である。任意の表には、順序の反射・反対称・推移、上下端、全ての二要素の最小上界・最大下界を検査し、不成立の表は方針の誤りとして拒否する。名前・表の大きさに予算を設ける。単に DAG であることだけでは束であると認定しない。秘密の分類のべき集合のような既知の構成は、検証済みの構成法と集合の演算を使い、全要素を列挙した巨大な順序表へ展開しない。

数学的な定理は任意の束に対して書ける。一方、無限の束、利用者コードで書く順序判定、意味上の等号、実行時に増える主体を実装へ許すには、停止する判定器とその健全性が別に要る。本調査の案 G の時間には含めず、その拡張の費用は未見積もりとする。有限であっても任意の束は分配束とは限らないので、有限集合の和と積だけに依存した推論の簡約を一般の束へ適用しない。

### 操作の許可と情報流の許可

TODO-283 の六行に対し、案 L は主に「値の流れ」を、案 G は機密性の流れと未信頼の入力による影響を表す。操作の種類は既存のエフェクト、対象の上限は案4、回数は別の使用回数の仕組み、権限を持つ者はサーバの主体、権限を狭める範囲は方針の適用範囲が担う。積の束の要素に回数を追加すれば線形性も保証できる、とはしない。

送信では、操作の許可、対象の上限、内容の機密性と完全性を全て検査する。対象の実行時の値が必ず範囲 `R` に入る契約がある場合、次の条件を使う案である。

```text
実際の宛先 d ∈ R
全ての d ∈ R について pc ⊔ label(target) ⊔ label(payload) ⊑ sink(d)
かつ、操作の種類と実対象が利用者の方針で許される
```

`R` が許可された通信先に含まれるだけでは、全宛先がその秘密を受け取ってよいとはいえない。機密性だけの案 L でも同じ条件が要る。秘密や未信頼の条件でどの宛先を選ぶかも pc と対象の印で追う。全称条件の判定は有限・制限した範囲の保守的な被覆に限り、不明なら受理しない。

案4の型は対象の字面の上限を与える候補である。DNS、リンク、検査後の差し替え、リダイレクト、子プロセスの独立した IO を抑える保証は別に要る。宛先の実行時照合に失敗すること自体が秘密に依存する場合も、失敗と公開の後続処理の印を検査する。型の範囲があるという理由で、失敗の漏れが全部なくなったとはしない。

### 守る相手と、保証する二実行

| 場面 | L | G | P |
|---|---|---|---|
| LLM の誤りで、処理系の入口から得た秘密を別の出口へ送る | 検査対象の構文と API の閉じた範囲で拒否 | 同左。完全性も検査する | Phase 1 は L、Phase 2 は G |
| 実行中のネットワーク・LLM 応答・ファイルの内容がコマンド等の決定に混入する | 機密性の規則では拒否できない | 入力の分類、pc、用途別の出口の契約が揃えば無承認の影響を拒否 | Phase 1 は既存の検査済み API に頼り、一般の追跡は Phase 2 |
| LLM が生成時に悪意ある指示を読み、悪いコマンドを定数として書く | 意図の一致を保証しない | 同左。実行時の未信頼の値がなく、完全性の印だけでは検出しない | 両段で同じ |
| スクリプトが秘密を読まずに外部コマンドへ独立して読ませる、方針を書き換える | 単独では保証しない | 単独では保証しない | 両段で同じ |
| サーバによる方針の保護・外部コマンドと WASM の経路の制限を併用する | その強制の範囲で意図した迂回も対象にできる | 同左。信頼する検査関数の保護も必要 | 到達する版と構成を明記する |

機密性の基本命題は、許されていない秘密だけが異なる二実行がともに終了したとき、観測者が見られる値・宛先・操作の有無と順序・公開する失敗が同じになることである。完全性の基本命題は、信頼する入力とコードを固定し、未信頼の入力だけを変えた二実行がともに終了したとき、信頼する操作・結果の観測が同じになることである。外部応答にも対応関係を課す。時間・資源の物理的な差、発散と終了の差、許した受け手による再配布は別の範囲である。

開示・endorsement を使う場合は、基本命題を無条件には主張しない。許した関数が開示した情報、または承認した用途別の値と成否が一致する二実行について、残りの観測が一致する、という関係条件を設計する。単に「方針で許された呼び出しなら任意に印を下げられる」として非干渉を名乗らない。詳細は後述の API 応答と形式化の節に示す。

## 案 L: 有限の秘密の分類と開示先、機密性のみ

### 1. 何を表せるか

S5 の有限の分類 `S` の集合を値の印とし、`⊥ = ∅`、順序を包含、結びを和集合とする。出口 `d` が受け付ける分類を `Accept(d)` とし、値・対象・pc の分類が全てそこに入ることを求める。これは有限の束の一例である。分類を受け手集合へ変換したときは、分類の和は許す受け手の共通部分に対応する（SF の Readers）。分類の異なる二集合が同じ受け手集合へ写る場合もあり、この写像を自動的に単射とはしない。

局所の印と pc を推論し、関数の引数・結果・捕捉値・失敗の依存を要約する。S5 は本番の制約推論の完成を示していない。単相の要約で呼び出しをまとめるなら、公開と秘密の両方で使う関数の結果が全て秘密になる場合がある。印について一般化した要約を導入するなら、束が有限でも印の多相の費用が要る。

診断には入口、値または分岐の依存、出口、拒否した方針の項目を示す。分類名を文字列型の別名にするだけでは、分岐や関数を越える流れを検査できない。

### 2. 権限制御での使い道

「読める」と「接続できる」の両方を許した中でも、読む秘密ごとに送信先を制限できる。TODO-283 の値の流れの行に対応する。対象の上限は案4から受け取り、回数・主体・局所の権限の狭め方は追加しない。実行前の判定は情報流の制約を検査し、サーバの実行中の判定と OS の制限は別に同じ方針から導く。

方針の完全性を LLM と同じ利用者権限のファイルだけで守れるとはしない。サーバ前の提供はハーネス・OS に前提を委ね、意図した迂回を一般に防ぐ宣言をしない（RV-S5 F2-1）。

### 3. 実用の機能での使い道

秘密を含むレコードから公開の欄だけを取り出す、ログに秘密由来の値を混ぜない、秘密で分岐した報告を拒否する用途がある。欄ごとの印と、レコードの形・リストの長さの印を分けられれば、全体に秘密の和を付ける方式より受理を増やせる。これは推論の精密さの改善であり、束の汎用性とは独立である。

```bnt
// 案 L の擬似コード。Secret・API は未実装の提案である。
function main() -> Unit uses Secret.Read, Http.Connect, Console.Write
  bind token <- Secret.read("service-token")
  bind result <- Api.listIssues(token: token)
  Console.writeLine(Api.summary(result))
end function
```

S5 の厳密な規則では、応答と成否が token に依存しうるため、最後の表示を拒否する。API の応答を方針で開示する限定規則を足すなら、後述の **L+** となり、元の案 L より保証と費用が増える。

探索・バックトラック、配列の破壊的な更新、生成器の書き方を直接増やさない。既存の局所構築器・一階ハンドラがその実装を担い、L はそこでの秘密の記録や結果の流れを検査する。時計・乱数・失敗の注入も既存ハンドラの役割であり、L の新しい利益は模擬応答も本物と同じ情報流の契約に従わせられる点である。解放・時間切れ・取消し・トランザクションの追加機能や、性能の改善は得られない。印の推論と診断の費用は未測定である。

### 4. 今の設計との両立

既存の効果の規則とは別の判断にできる。ワンショット、深い再開、外側での節の実行、エフェクト変数と State を処理しない規則を維持する。節の pc は呼び出し元と捕捉値に依存させ、非再開による後続の欠落と解放にも印を伝える。SF の末尾で必ず一度再開する小モデルから、この一般の場合の成立はまだ導けない。

最初は秘密を扱う構成で Task・共有 Reference・Lazy・WASM・汎用 Process を拒否する S5 の境界を保つ。ただし秘密を自力で読む外部コマンドの迂回は、秘密の取得 API への到達可能性だけでは塞げない。保護された実行全体の経路を棚卸しする。Task を後で許すときはハンドラと pc の両方を引き継ぐ。WASM は現行の取り込みなし・純粋または State の範囲と、TODO-048・213 の将来の規則を区別する。将来の外部 IO の効果を、IFC の導入を理由に除去可能にしない。

スクリプトに権限の宣言や値のケーパビリティを足す必要はない。分類は外部の方針が与える。`Secret.reveal` は普通の文字列を得ても印を保つ。効果を処理しても秘密の印や開示許可を消さない。

### 5. 設計原則との関係

「この秘密はこの宛先の認証にだけ送る」という確認は原則3に合う。一方、「認証の成否が秘密に依存するので完了と表示できない」は利用者の期待と衝突する。L の簡単な方針の書式だけではこの制限を減らせない。診断を分かりやすくすることと、使えるスクリプトが増えることも別である。

分類と依存は推論し、拒否を「コードを直せる」「方針の管理者の判断が要る」「機能が未対応」の三種類に分ける。LLM に許可の追加や外部コマンドへの迂回を自動提案させない。構文の新設を抑えられる点は原則5に合うが、印のない関数へ秘密が混ざる誤りを必ず出口で報告する仕組みは要る。

### 6. 形式化の費用

有限集合の法則自体は小さい。主な費用は、値と関数の情報流判断、正常・異常の pc、二ストア・継続・解放の対応、二実行の観測、表層・交換への接続にある。S5 の Lean 88〜210時間を基準にし、SF の小モデルの成功だけで縮めない。SF の Lean 62〜148時間という別見積もりには本番のストア等の不足がある（RV-S5 F5-1）。補正した見積もりは後掲する。

通常の Ty・Eff・Step を保ち、追加判断と消去・持ち上げを証明できれば、四主定理の既存の言明は保てる見込みである。情報流は独立した重い項目であり、案4の「エフェクトに値を持たせる変更」と同じ版へ相乗りさせない。

### 7. 互換性と構成

普通の型検査では通るコードでも、方針付きの検査で拒否される。S5 の一般のファイル読み取りを全秘密の和へ上げる規則を保つと、公開 CSV の集計も表示できなくなる。秘密と関係のない入力を精密に認定する境界がなければ、標準ライブラリ・examples・Skill の例の広い移行が要る見込みである。影響する実件数は未集計である。

情報流の解析と方針のデータ型は、ネットワーク・サーバ・Wasmtime の依存から分離する。構成で API がない場合は検査時に拒否し、同じ API の印の意味を構成ごとに変えない。秘密の数を `u64` のビット数へ固定せず、可変長の集合と大きさの上限を使う。

### 8. 学習の価値

pc、暗黙の流れ、一実行の型安全と二実行の非干渉の差を学べる。有限集合に固有の推論は読みやすい。一方、完全性・用途別の検査・一般の束の検証は後へ残る。L を完成形とするなら、日常の自動化の注入への対策は別の型と API として学ぶことになる。

## 案 G: 利用者が定める束と、機密性・完全性

### 1. 何を表せるか

機密性の束 C と完全性の束 I を独立に定め、内部の印を積 `C × I` とする案を推す。二つの束を別々の制約として実装しても、積と同じ順序と結び、両方を満たす出口の条件を持てば同じ規則になる。表示と診断では二種類を分ける。一つの未区分の束では、方針の変更がどちらの保証を緩めたか説明しにくい。

I の順序は、依存を合成する順序として「信頼する ⊑ 未信頼」と定める。計算に未信頼の値が混ざれば結びは未信頼となる。通常の日本語の「信頼が高い」という向きと順序記号を混同しない。`(公開, 未信頼)` と `(秘密, 信頼する)` は比較不能になりうる。複数の信頼元や用途を区別する束も許すが、「パス用に検査した値」を「SQL 文用に検査した値」と等置しない。

通常の値の流れと pc は積の結びで合成する。任意の分岐から印を下げる式は設けず、方針が指す特定の標準関数・検査済みのライブラリ関数だけに、declassification または endorsement の契約を与える。識別は名前の綴りでなく、解決済みの宣言、コードと契約の同一性、方針の版で行う。アプリケーションが同名の関数を書いても許可を得られない。

#### 印の多相を含める三つの範囲

| 選択 | 得るもの | 費用・診断 | 判断 |
|---|---|---|---|
| 多相なし、関数ごとに固定の印 | 実装の最初の規則は小さい | 全呼び出しの和で精度を落とすか、印ごとの関数複製が要る。公開の入力の処理まで拒否しうる | 比較用。G の完成形には推さない |
| トップレベルの関数・標準関数に、推論する一階の制約付き要約 | 例: `∀ c i. String@(c,i) → String@(c,i)`。map 等では入力、関数、捕捉、結果、pc の依存を表す | 一般化、呼び出しごとの具体化、制約の解釈、再帰の検査が増える。主診断では実際の由来に戻して示す | **推す**。利用者のスクリプトへ印変数の注釈を必須にしない |
| 利用者が明示する任意階の印の多相、動的な印、束を越える多相 | 異なる束を使うライブラリの高度な抽象化 | カインド、スコープ、代入、等号、推論の制限が増える。費用未見積もり | 最初に入れない |

上の型の `@` は説明用の記法であり、Benitoite の構文の提案として固定しない。ここでいう一階は、印についての量化を関数の要約の最外部に限る rank-1 の意味であり、一階のエフェクトと同じ分類ではない。一階の要約でも、型・効果の多相とは別の変数の種類が要る。可変状態に依存する値を無制限に一般化せず、再帰は定義の内部で単相に検査するなど、受理する規則を固定する。J3・F2 は多相と推論を分けて検討する根拠であり、その推論器をそのまま移植する提案ではない。

一般の有限束に対する推論では、最も一般的な要約を簡単な結びの式で常に返せるとは仮定しない。制約付きの要約を残し、関数の本体は、その制約を満たす全ての具体化について検査する。都合のよい一組の印が存在することだけで多相な署名を認定しない。有限でも候補の組合せが大きくなりうるため、判定の予算と、不明なら拒否する診断を設ける。主型の存在・実装する推論の完全性・実行時間は未確認である。

### 2. 権限制御での使い道

L の機密性に加え、操作を決めた入力の由来を検査できる。例えば、外部応答が選んだ実行ファイル・シェル文・書き込み先を、方針で認めた検査を経ずに使うことを拒否できる。これは TODO-283 の「値の流れ」を逆向きの保証にも使うものであり、コマンドの実行許可やパスの上限を代替しない。

方針の管理者は C・I の定義、入口の印、出口の契約、信頼する検査関数と開示関数を定める。アプリケーションには変更させない。実行中に利用者が方針を狭めるときも、機密性の送信先を減らすことと、完全性で信頼する入力・検査・用途を減らすことを区別する。I を C と同じ字面の大小比較で「狭める」と定義しない。

### 3. 実用の機能での使い道

#### 注入の防止と既存の仕組みの差

次の表は G に対する提案であり、現行の型検査の保証ではない。外部の入力の内容と制御の依存を追い、出口側が用途ごとの契約を要求することが前提である。

| 場面 | 今ある防止策と不足 | G で増えることと残る限界 |
|---|---|---|
| `Process.run` の引数に外部文字列を渡す | program と arguments を分けるため、通常の引数をシェルのプログラム本文として連結しない。コマンド側のオプション・式・設定の解釈は残る | executable・環境・作業ディレクトリ・危険な引数の用途を検査する。全 arguments を「信頼する」にすると日常の文字列検索等まで拒否するため、コマンド専用の契約が要る |
| シェル文にネットワークや LLM の出力を連結する | `Process.shell` は文字列をシェルに渡す。エフェクトは混入した文字列の由来を追わない | 未信頼の本文と、未信頼の条件で選ばれた定数の本文を拒否する。包括的な「安全なシェル文字列」への endorsement は推さない |
| 外部入力をパスとして使う | Scope は字面の範囲を確認し、`@opaque` は検査済み値の偽造を防ぐ。現行 IO は未検査の String でも呼べる | 検査済みの同じ値を使うことと、方針の根の下にあることを全出口で求める。リンク・差し替えを防ぐには実対象の同定と OS の強制が要る |
| SQL 文へ文字列を連結する | エフェクトだけでは SQL の文法とデータを区別できない。現行の SQL API の存在は本調査で確認していない | 将来の API では SQL の構造を信頼する値、パラメータを未信頼でも渡せるデータとして分けられる。パラメータ化だけで十分な用途なら新しい印の利益は主に全経路での強制である |
| LLM の提案からコマンドを選ぶ | LLM が書くスクリプトが検査関数を呼び忘れうる | 実行時の提案をデータとして受ける場合に、許可リストへの変換を強制する。生成時に悪い定数を書いた場合の意図の不一致は検出しない |

```bnt
// 案 G の擬似コード。以下の Validator・Search・DataFile は提案 API である。
// input は公開でも未信頼である。
function search(input: String) -> Result[String, String] uses Process.Run
  return Search.literal(pattern: input, file: "notes.txt")
end function

function bad(input: String) -> Unit uses Process.Run
  Process.shell("grep " + input + " notes.txt") // 未信頼のシェル本文として拒否
end function

function save(relative: String, text: String) -> Result[Unit, String] uses File.Write
  bind path <- try Validator.reportPath(relative) or return
  // 検査の成功値の同じ path を使う。用途は「報告先」にだけ限定する。
  return DataFile.writeText(path: path, text: text)
end function
```

`Search.literal` は、固定の実行ファイル、固定オプション、データとしての pattern と file の契約を持つ案である。`run` が引数を分けて渡す部分は現行にもあるため、その点を G の成果に数えない。未信頼の pattern まで信頼する値に上げる必要はなく、危険な解釈をしない出口でデータとして受ける契約にする。Process を IFC に接続する証拠がない最初の版では、この例は拒否され、既存機能との差を示す将来の接続目標に留まる。

`Validator.reportPath` は固定した根、正規化、用途の検査が成功した値だけを返す、方針で許した endorsement の例である。普通の Scope をアプリケーションが好きなパターンで呼ぶことは、利用者の許可を得ることとは違う。Scope の全成功を自動的に全用途の「信頼する」へ変える案は採らない。検査の成否に外部入力が影響するため、成否の依存と承認した事実も契約に残す。

```bnt
// 案 G の擬似コード。DB は将来の API の例である。
function findCustomer(db: DB.Connection, name: String) -> Result[List[Customer], String] uses DB.Read
  return DB.query(db: db, sql: "select * from customers where name = ?", parameters: [name])
end function
```

この場合、name が未信頼であることは通常のデータの検索には支障がない。SQL 断片へ変換する endorsement を増やすより、構文とデータを分けた API を使う方が契約を狭くできる。完全性の印は SQL の意味や外部コマンドの内部を自動解析しない。検査関数が何でも受理するなら、印を付け替えても注入の防止にならない。

アルゴリズムの制御機能は L と同じく増えない。追加の実用価値は、ファイル・HTTP・LLM の結果を共通に未信頼と扱い、検査を通した用途を後の関数でも保てることにある。模擬 IO・記録と再生では、信頼する fixture と本物の未信頼の入力の分類を明示し、テストだけ印を外す抜け道を作らない。Property の生成器・失敗の注入には「未信頼の入力を変えても未承認の操作は増えない」という評価目標を追加できるが、生成器の実装は既存の仕組みで行える。

資源の解放、取消し、時間切れ、トランザクションは別の実行規則である。G はその成否が未信頼の条件や秘密に依存することを検査する。静的な印を消去すれば VM の値全てへの実行時タグを避けられる見込みはあるが、推論・方針の検査・コード量の費用は残る。性能改善を採用理由にせず、TODO-028 との比較は実装後の測定に委ねる。

### 4. 今の設計との両立

L の接続条件に、完全性の pc、開示・検査関数の契約が加わる。節を外側で実行することは、pc を公開・信頼する状態へ初期化する理由にならない。未信頼の分岐で呼び出した操作を、外側の節が信頼するコマンドへ変換する場合も、明示した endorsement の契約がなければ拒否する。

ハンドラによって組込みの効果が消える場合も、代わりに走る節を含めて印の要約を検査する。WASM のホスト IO の効果を除けない将来の制限と、情報流の検査を通せない境界を混同しない。純粋な外部関数も、入力に依存する結果・失敗を返すため、秘密を公開へ変換できる関数にはしない。State を持つ外部の型は、共有状態を通した流れの契約がない限り最初の範囲から除く。

権限はスクリプトに宣言させず、ケーパビリティの値も導入しない。標準関数が情報流の印を緩められるという事実は、通常の関数値として権限を運ぶ設計とは異なる。高階に渡す場合も、関数の要約に固定の契約を保ち、呼び先の正体が不明なら印の緩和を認めない。

### 5. 設計原則との関係

非プログラマに束の順序表を書かせることを標準の使い方にしない。通常は、処理系が用意する機密性と完全性の既定の構成を使い、管理者が「このファイルは秘密」「この応答は外部のデータ」「この検査の後だけ報告先に使える」を選ぶ。独自の束は管理者向けの上級の設定にする。利用者が自分で束を定められる能力と、全利用者が束を理解する義務は区別する。

利用者に示す承認の例は「サービスのトークンを API の認証欄へ送り、課題の件数と要求の成否を報告する。API が返した文字列をコマンドとして実行しない」である。LLM 向けには、由来位置、pc の原因、実際の C と I、必要な出口の契約、方針の項目、拒否の種類を構造化して出す。秘密の実値は出さない。複雑な制約式や印変数の番号は詳細表示へ回す。

多相の要約によって、同じ変換関数を公開・秘密の双方で使える点は原則1・4・6に合う。一方、推論の予算切れを「公開」へ近似することは許さず、不明として拒否する。診断の理解と LLM の修正成功率は未測定であり、原則3に適合したと認定するには実例での受け入れが必要である。

### 6. 形式化の費用

L の本番への接続は全て必要である。その上に、任意の束を引数に取る規則と、方針の有限表の検証、積と射影の補題、完全性の観測、用途別 endorsement、開示・承認した値を除いた関係条件、一階の制約多相の健全性が加わる。二つの束という理由で全証明を二倍にはしない。開示のない部分の置換・pc・観測の補題は同じ代数で共有できる。

単一の G の改造は、情報流を一つの中心に据えた大きな改造である。範囲の正規化や新しい高階エフェクトを同時に入れると、TODO-250 の二つ目の重い項目になる。G の中でも一般の State・Task まで広げる部分は、独立した後の改造に分ける。

### 7. 互換性と構成

L と比べると、公開でも未信頼の入力を操作の決定へ使う既存コードが追加で拒否される。引数配列へ文字列を渡すだけの適切な使用も、出口の契約が粗ければ拒否される。標準のラッパーを狭く作り、データは未信頼のまま通せる受け口を設ける必要がある。これは G の API 設計と移行の費用であり、束の汎用化によって自動的に減らない。

束の定義を機能フラグで変えない。機能で除かれたネットワーク等の契約は使えなくする。方針の解釈・制約判定を中核へ、サーバの保存・認証・UI、OS の制限を境界の外へ置く。有限要素の番号・積・表の大きさは検査済みの上限で扱い、64ビットのタグやポインタ幅に意味を依存させない。

### 8. 学習の価値

束の抽象化と具体化、制約の一般化、二種類の非干渉、信頼する計算の境界、例外を許した保証の定義を学べる。Granule の全ての段階付きの型を入れずとも、具体の代数に依存しない型規則と、その実装の検証を学べる。学習量は多いが、提供時期との衝突は対象 API と実行機能の範囲で調整し、保証を緩めない。

## 案 P: Phase 1 を L、Phase 2 を G とする

### 1. 何を表せるか

Phase 1 は案 L、Phase 2 は案 G の受理範囲となる。段階に分けること自体は新しい表現力を増やさない。数学的なコアは Phase 1 から束を引数に取り、公開の入力形式だけを有限の秘密の分類のプリセットに限る構成が可能である。Phase 1 が「具体のビット集合しか表現できない型検査器」を意味する必要はない。

一方、汎用の内部表現だけ先に作っても、I の推論、endorsement の規則、用途別 API、診断まで自動的に完成するわけではない。L と G で変わる部分を契約として先に決めることが、作り直しを減らす条件である。

### 2. 権限制御での使い道

Phase 1 では機密性による誤りの拒否を先に提供し、Phase 2 で未信頼の入力による操作の決定を検査する。両段とも案4とサーバの方針を使う。Phase 2 の前にサーバモードを実装する場合、完全性の印と検査関数の承認・監査を後から追加する費用が出るため、UI・通信・保存の契約を Phase 1 で予約する。

### 3. 実用の機能での使い道

Phase 1 の擬似コードと受理・拒否は L と同じである。完全性がない間の `save`・`search` は、既存の不透明型と用途別 API で検査を強制する。これは現在も一部作れる対策であり、Phase 1 の IFC が注入を防いだと数えない。Phase 2 では G のように、通常の関数や分岐を越えて未信頼の依存を追う。

段階案の実用上の利点は、先に機密性の診断を利用者に提示して改善できることである。ただし、認証応答と一般のファイル読み取りを厳密な L のままにすると、最初の利用例の多くが拒否される。Phase 1 の受理例が少なければ、フィードバックを早く得られるという利点も小さい。L+ へ変える場合は元の P からの変更を明示する。

### 4. 今の設計との両立

各段に L・G の接続条件をそのまま課す。Phase 1 で情報流を効果の行に符号化し、Phase 2 で別の判断へ移す方式は避ける。既存のハンドラの意味と情報流の意味を二度変えることになるためである。Phase 1 で未対応とした Task 等を Phase 2 で当然に受理する必要はなく、汎用化と実行機能の拡張は別の改造にする。

### 5. 設計原則との関係

管理者が最初に理解する内容は L までで済む。一方、Phase 2 で同じ公開のスクリプトが「外部入力だから実行不可」となると、以前の説明との違いを示す必要がある。互換モードの暗黙の選択や、完全性の印の自動消去は原則2・3に反する。移行時に検査結果と保証の差を明示する。

### 6. 形式化の費用

汎用のコアで Phase 1 を証明すれば、Phase 1 の定理を G の定理の系として置く見込みがある。必要な埋め込みと観測の条件は後掲する。失敗・非再開・実際の IO への持ち上げが未証明なら、代数だけの系をもって「本番の作り直しがない」としない。

Phase 1 に汎用の型の表現を予約する費用、Phase 2 に旧データの読込みと旧定理の系の維持、二回の回帰・文書・レビューへの修正が加わる。同じ最終範囲に対する合計は、G を一度で入れるより安いとは見込まない。

### 7. 互換性と構成

旧コードと旧方針をそのまま通せるのは、Phase 2 が旧方針の意味をそのまま保つ場合に限る。旧方針を「完全性の束は一要素で、完全性の制限をしない」という明示した旧プロファイルとして読むなら成立する見込みがある。全ての旧入力へ新しい未信頼の印を自動付与し、旧 Process の呼び出しに信頼する印を要求すると、旧受理を保てない。

したがって、P は「機密性の互換を保ち、完全性の採用時には方針と必要なコードを移行する」か、「完全性を検査しない旧プロファイルを残す」のどちらかを要する。旧プロファイルの結果を G の完全性の保証と表示しない。どの構成でも旧プロファイルの意味は同じに保ち、サーバは必要な保証を持たないプロファイルを登録時に拒否できるようにする。

### 8. 学習の価値

有限集合から一般の束への具体化、保守的な言語拡張、旧定理を系にする手順を学べる。変更が何を保存し、何を保存しないかを読む題材にもなる。反面、同じ表層・交換・API を二度保守する作業は、情報流の理論を新たに学ぶ量とは別の費用である。

## RV-S5 の重大の所見への答え

### API 応答の分類と許す開示（F3-1）

**一般の束を導入するだけでは、認証応答を公開できない。方針が許す開示を、API の契約と保証の言明に加える必要がある。** `response` が token に依存するなら、普通の規則では機密性の印も token 以上になる。この依存は、印の要素を増やしても消えない。

方針に「この宛先への認証付きの要求の応答は公開してよい」と書くことは可能である。しかしその規則を無条件に適用すれば、その API が token を本文に反映した場合も公開される。これは許可した漏れに含まれる。API が反映しないという未検証の性質を、束の法則から証明することはできない。

推すのは、固定の API 操作を、許された関数だけが公開用の結果へ変換する契約である。次は **TODO-109 への追加を考える概念上の書式案** であり、既存の TOML ではない。

```text
flow:
  confidentiality: finite-secrets(service-token, private-data)
  integrity: trusted <= external
  sources:
    keystore(service): (service-token, trusted)
    http-response(api.service.example): (response-policy, external)
  release:
    issue-summary:
      function: resolved-standard-operation(Api.listIssueSummary, contract-version)
      request:
        origin: https://api.service.example:443
        method: GET
        path: /issues
        credential-channel: authorization-header
        body: none
        redirects: none
      release-to: report
      released-value: issue-count, selected-summary-fields
      released-outcome: success-or-error-category
      retain-labels: private-data
      control: approved-call-context
  endorse:
    report-path:
      function: resolved-validator(Validator.reportPath, contract-version)
      input: external
      result-use: report-file-target
      checked-rule: within-policy-report-root
```

応答の欄、HTTP の成功・失敗の区別、通信・復号・変換の失敗、公開する診断、正常に戻った事実を含めて、何を公開するかを決める。本文だけ印を下げ、結果の Result の構成子や pc を秘密のままにすると典型例はまだ通らない。逆に周囲の pc を全て公開に戻すと、API と無関係な別の秘密で呼び出しを選ぶ漏れが生じる。専用関数の契約は、許可された要求に由来する印だけを緩め、他の捕捉値・条件・payload の秘密を残す。

機密性を緩めても、応答の完全性は `external` のままにする。公開してよいデータであることは、コマンドとして信頼してよいことを含まない。開示を起こす操作とその引数・呼出条件を未信頼の入力が選べる場合は、選べる操作・値・用途を限定し、その限定を明示した承認にする。J2 の robustness はこの問題を区別する先行例であり、単純な関数の許可リストと同じ保証を自動的に与えない。

この方針の下での命題は、例えば「issue-summary が公開すると定めた値と成否が同じ二実行について、ほかの公開の観測は同じ」である。公開する要約に token が混じらないことは、信頼する API・変換関数の契約に属する。外部 API を信頼できないなら、要約でも任意の反映がありうる。機械的な token 文字列の置換も、符号化や別の依存の除去を証明するものではない。外部 API の信頼条件を受け入れない場合は応答を秘密として保つ。

| 案 | F3-1 への答え | 典型例への帰結 |
|---|---|---|
| L（厳密な S5） | 許可された一回の送信と、応答の印を区別する。一般の印の緩和を入れない | 認証の結果の表示は拒否のまま |
| L+（比較上の補正案） | 上の固定 API に限る開示を追加する。完全性の追跡はしない | 信頼する固定関数と方針の契約に限れば表示できる。L の見積もりへ追加が要る |
| G | C の限定した開示と I の保持、呼出条件の完全性を同じ契約で検査する | 条件を満たす API の報告を受理し、応答を未検査のコマンドにする使用は拒否できる |
| P | 厳密な Phase 1 は L。Phase 1 から表示を使うなら P を L+ → G へ変更する | 「S5 のまま有用な API 例が通る」とはしない。Phase 2 で開示と完全性を接続 |

### ファイルの分類（F3-2）

束の汎用化は、どのファイルを読んだかという情報を増やさない。候補が全ファイルなら、L・G とも全分類の結びへ上げる。G の完全性を追加すると、外部で変更されうる一般のファイルはさらに未信頼になる。

推す境界は、秘密の場所と公開のデータの場所を方針で分け、案4の範囲付きの読取り口へその区別を結ぶことである。対象範囲が秘密の分類と交差しないと認定できる場合だけ、公開の内容を得る。ただし字面のパスの非交差だけではリンクを介した読取りを排除できない。サーバ前は、専用の取得口・信頼する入力としてのデータ・ハーネスの隔離の範囲を明示する。一般の File.readText の全経路について保証できないまま、秘密ファイルの読み取りだけに特別な印を付けて全体の非干渉を宣言しない。

現実的な初段の提案は、実対象の同定を保証できない一般読取りを保守的に秘密の和とし、公開の入力が必要な例には、信頼する実行側が用意したデータの入力契約を使うことである。これで通らない既存例は拒否のまま明示する。一般読取りで `{secrets}` を実行時に拒否する機能をサーバ前に加える場合は、それ自体が権限制御の先行となるので、ADR 0177 の変更判断を要する。

G ならレコードや検査済み入力を精密に追える可能性はあるが、同じ精密化は L にも可能である。P はこの分類と実対象の契約を Phase 1 に決めない限り、Phase 2 で方針と API を設計し直す。

### 宛先の上限と案4（F2-2）

三案とも、固定 origin、公開の段階での実行時検査、静的な上限 R の三つを区別する。推すのは案4の R を使い、許された開示先が R 全体を覆うことを要求する方式である。秘密を読む前に、公開の設定値から R 内の検査済み宛先を作る。宛先に秘密の依存がある場合は、その印も残す。

L は有限分類ごとの被覆、G は C と I の契約の被覆、P は両段で同じ R の意味を使う。HTTP の全要求・リダイレクト・認証欄をこの契約へ結ぶ。旧 String の入口は全対象の上限として残せても、情報流付きの検査では条件を証明できず拒否される場合がある。案4を先に入れる利益はこの入口の共用であり、二実行の証明を不要にすることではない。

### 方針の書式と二度の設計（F4-1）

三案とも、静的な照合というだけで ADR 0177 の懸念を免れない。秘密の開示や endorsement の許可も、誰が保存し、誰が変更できるかを要する。TODO-109 と、サーバの保存・承認・失効・監査・子への受け渡しの境界を先に設計し、IFC のためだけの暫定の許可ファイルを別に作らない案を推す。

サーバモードの詳細な実装を先に始める必要はないが、方針の入力の所有者、識別子、版、狭める操作、承認が必要な変更、解析器へ渡す正規化済みのデータを先に決める。TODO-109 の書式の一部をサーバの実装より先に確定する判断を設計者に求める。既存の ADR 0183 の「書式をサーバモードの章で決める」という順序をそのまま守る場合は、IFC の公開可能な実装を待つか、二度の設計を受け入れる必要がある。

TODO-109 の `[secrets].paths` と `{secrets}` は実対象へのアクセスの除外、IFC の分類は読んだ内容と派生値の流れとする。同じ秘密の登録から両者を導き、独立した二つのパスの一覧にしない。`Secret.Read` の専用取得口を許すことと、一般の File.Read の除外を外すことを分ける。C・I の緩和、開示の追加、信頼する検査関数の差し替えも承認が必要な方針変更として扱う。

## 形式化の増分と Phase 1 の定理を系にする条件

### SF を土台に増える定義と命題

| 群 | L にも必要な本番への接続 | G で増えること |
|---|---|---|
| 印の代数 | 有限分類と出口の解釈、判定器の健全性 | 束を引数にする法則、有限表の検証、C×I の結び・射影・順序。SF の一般形を再利用できる |
| 値・関数・型付け | 欄・形・閉包・捕捉・関数要約・置換 | 印変数の環境、一般化・具体化、制約の含意の健全性。多相なしならこの増分の一部を避けられる |
| 制御と継続 | 正常・異常の pc、Fail・die・escape・非再開・解放、既存の任意の一歩の持ち上げ | 完全性の pc と用途別 endorsement の呼出条件、開示によって緩めてよい依存の区別 |
| ストアと観測 | 対応する確保場所、継続と構築器のセル、事象列、二状態の関係 | 機密性の観測と信頼する操作の観測の二つの射影。C と I それぞれの非干渉 |
| 標準 API と外部応答 | 入口・出口・失敗の契約、対応する応答 | declassification・endorsement の許可と関係条件、用途別の検査済み値の意味 |
| 表層・交換 | 情報流の追加判断、脱糖・推論結果の検査・実装との比較 | 束と変数の識別、積、制約、許可された緩和の証拠、方針の版の受け渡し |

SF の段1〜3には再帰・失敗・本番のストアがなく、段3の節は必ず末尾で一度再開する。SF の動的監視の反例は拒否を含む出力列の一致を否定するが、静的方式の本番の失敗の扱いを証明していない（RV-S5 F1-1〜F1-3）。S6 もこの不足を解消していない。SG が束と積の埋め込みを証明しても、この表の本番への接続は別に残る。

G で証明が楽になるのは、式・pc・通常の代入に関する補題を具体の分類ごとに繰り返さずに済む部分である。例えば観測者の可視性を `visible(l) = (l ⊑ o)` とすれば、結びが可視である条件は両辺の可視性の論理積になり、SF の構造を使える。完全性では「観測できる」を「信頼する結果として数える」と読み替え、未信頼の入力だけを変える関係を別に定義する。

一方、全ての用途の完全性や robustness を、単なる二値の順序の反転だけで証明できるとはしない。開示の値・タイミング・検査の成功条件が両次元に関わるためである。Granule の別の様相が必要になった事情も、単純な双対という説明の適用範囲を限定する材料である。本案はその様相計算を再現せず、依存の順序を揃えた積と、明示した例外の契約を選ぶ。

開示を含まない G の命題は、C と I に対して独立に証明し、積の判断から両方の前提を得る形を候補にする。開示・endorsement を含む場合には、「許した関数である」「用途が一致する」だけでなく、二実行で許す開示・承認された事実が対応すること、他の依存を緩めないことを明記する。この条件の正確な言明と証明は未試作であり、新しい公理で済ませない。

### 四主定理と形式化の重さ

追加の判断を旧コアへ消去し、受理した旧コアの任意の遷移を追加判断付きの遷移へ持ち上げられるなら、進行・保存・エフェクトの健全性・脱糖の型の保存は普通の型安全の言明として残す見込みがある。消去方向だけでは、漏れる旧遷移を追加モデルから落としてしまう可能性が残る。新しい情報流判断の保存と二実行の定理を別に示す。

L・G とも、コアの情報流の判断と Surface の接続を先に Lean で作り、01-12 へ規則を写す対象となる。現行の外部関数の型保存の仮定に、情報流の関係条件を黙って追加しない。別の契約として定理の引数とし、Rust・OS まで確かめた範囲を分ける。Task・共有状態の自由な接続は別の重い改造とする。

TODO-250 の三種類との関係では、案4はエフェクトの原子に範囲を持たせる。IFC は主に別の判断を増やすが、印の多相と正規化は型に関わる計算、ハンドラの効果除去との接続は除去後も依存を保つ証明を要する。既存 Ty を変えなければ軽い、とは判断しない。L・G・P の各実装段は、いずれも重い項目として扱う。

Phase 1 の分類集合の束を `L₁`、Phase 2 を `C × I` とし、旧方針では I を一要素とする。埋め込み `F : L₁ → C × I` は少なくとも次を満たす必要がある。

```text
F(⊥₁) = ⊥₂
F(a ⊔₁ b) = F(a) ⊔₂ F(b)
a ⊑₁ b  iff  F(a) ⊑₂ F(b)              // 旧受理を正確に保つ
visible₁(o, a) = visible₂(Fo(o), F(a))  // 観測の意味も保つ
```

入口・出口の印、関数と pc の制約、外部応答の関係条件、失敗と開示の観測も同じ写像で対応させる。検査器が旧導出を受け付けること、推論器がその導出を実際に見つけること、旧形式の読取りと正規化が同じ意味を返すことは、別々に確認する。型規則の保存だけで処理系の互換を証明したとはしない。

この条件の下で、G の一般定理を I 一要素、開示・endorsement なしへ具体化し、消去・観測の対応を使えば L の非干渉を系にできる見込みがある。L+ なら固定した開示の関係条件も同じ意味で具体化する。逆に Phase 2 の全利用者に未信頼の入力を強制する場合は、この埋め込みでは旧コードの受理を保てない。

ここでいう「作り直さない」は、意味と証明の構成を再利用できることを指す。定理の引数・交換形式の読取り・テストの移行・診断の追記がゼロになるという約束ではない。SG の結果はこの埋め込みの代数と小言語の部分へ対応付け、上表全体の完了とは扱わない。

## 統合の担当への申し送り

- **推す案**: G。利用者が定める有限の C/I、固定した標準・検査済み関数だけの declassification/endorsement、推論する一階の印の要約を、一つの情報流の改造として設計する。数学的な規則は一般の束を引数にする。
- **推す版の組み方**: RV-S5 の (iv)。0.0.13 は案4、0.0.14 は情報流。TODO-109 とサーバの承認・保存の責任を IFC の実装前に設計し、サーバ前の完全な隔離は宣言しない。必要な拒否の意味との接続を別の段に置き、サーバモードは `0.1.0` より前とする。
- **推さない案**: 束を一般にすれば認証応答・ファイル分類・宛先の不明さが解けるという判断。L の厳密な規則のまま日常の API の表示が通るという説明。全ての用途で使える endorsement と任意の本文の開示を追加すること。
- **P を採る条件**: 初段を早く提供する利益を設計者が選び、再利用条件と旧プロファイルを Phase 1 に固定すること。L+ を初段に入れるなら名前と範囲を明示すること。完全性の後付けと旧コードの無変更の受理の両方を約束しないこと。
- **未確認の事実**: 本番の失敗・非再開・継続・解放を含む非干渉、R を持つ実際の送信と実対象の対応、限定開示/endorsement の関係条件の証明、一階の制約推論の健全性と実用の受理率、全入口出口の棚卸し、方針の変更と成果物の対応、診断から LLM が直す成功率。今回これらを実装・測定していない。
- **S1 との重複**: ハンドラの外側、非再開、解放、Task の引き継ぎ。高階エフェクトは IFC の前提にせず、権限を狭める高階境界で印を緩めない。
- **S2 との重複**: 案4の R、検査済みの同じ対象、方針の許可と字面の上限の区別、対象の同一性。ホストやパスのパターンをそのまま束にする提案にはしない。
- **S3 との重複**: 一般の段階付きの型、コエフェクト、印の束と多相。使用回数の代数と情報の依存の代数を、一種類の添字という理由だけで同じ規則にしない。
- **SG との接続**: 埋め込み・積・観測の証明を、上記の再利用条件のうち実際に扱った箇所へ限定して引用する。汎用の小モデルの成功から、実装の互換・方針の書式・本番の非干渉の完成を導かない。
