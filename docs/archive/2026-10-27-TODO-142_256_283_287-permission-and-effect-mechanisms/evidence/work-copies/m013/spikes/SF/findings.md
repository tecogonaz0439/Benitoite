## 2. 小モデルの規則と保証の範囲

### 二点の印とpc

構文は整数・真偽値・変数・等値比較、`let`、順次実行、`if`、固定した宛先への `send` である。整数は数学的な `Int` とし、本番の64ビット整数の範囲や演算の失敗は写していない。環境は変数番号から値への全域関数であり、束縛できない変数は扱わない。`let` は局所的に環境を延ばすだけで、外の状態を変更しない。出力は宛先と値の組の列であり、順序と出力の有無も観測する。

値の静的な印を `label(e)`、制御への依存を `pc` とする。二点の順序は `公開 ⊑ 秘密`、定数は公開、比較の結果は両辺の結びである。`if` の両枝は `pc ⊔ label(条件)` で検査する。`let` が束縛する値の印は `pc ⊔ label(式)`。出力の条件は `pc ⊔ label(値) ⊑ sink(宛先)` である。型の規則 `EType` は、これとは別に整数と真偽値を区別する。

`high_pc` は、観測者に見えないpcで型が付いた計算は、観測者へ出力しないと示す。非干渉の証明では、条件が公開なら二実行で同じ枝を選び、条件が秘密なら別の枝を選んでも両枝の公開出力が空になる。この分け方により、明示の流れと暗黙の流れの両方を扱った。

この言語には再帰もループもなく、全ての計算が終了する。その範囲で出力列の完全な一致を証明しており、停止を観測から除いた主張も満たす。**発散を含む言語のTINIを証明した結果ではない。** 時間、メモリ、OSの終了状態、送信の成功・失敗、通信量の物理的な差も観測に含めていない。

### 宛先集合と試作142のパターン

印を「受け取ってよい宛先」の集合 `A` とする場合、公開は全宛先、最も厳しい印は空集合である。`A ⊑ B` は `B ⊆ A`、`A ⊔ B` は `A ∩ B` となる。印が厳しくなるほど許す宛先が減る。集合の表現は `String → Bool`、ホストの接続例では `List String → Bool` とした。

宛先 `d` の出力の印を単元集合 `{d}` にすると、`A ⊑ {d}` は `d ∈ A` と同値になる（`Readers.flows_to_singleton_iff`）。API用の秘密を変えてよい二状態は、ログ用ホストの観測者から見れば同値である。APIの観測者に対しては、その秘密の一致を初期状態の条件に求める。許したAPIへの出力まで、秘密を変えても同じになるとは主張していない。

試作142から写したのは、正規化済みのホストの要素列、`Pattern`・`Matches`・`patLe` とその健全性の最小部分である。`patLe b a = true` から、受け手の集合としての `a ⊑ b` が導けた。元の包含をそのまま同じ向きに使うと、狭い受け手を広げてしまう。

ただし、完全一致の `api.example.com` と `logs.example.com` の共通部分は空であり、試作142の各単一パターンは少なくとも一つの対象に一致する。この空集合を表せないため、元の文法だけを印の束にはできない。生のパターン列にも、`[p]` と `[p,p]` のように意味が同じで構造が違うものがある。本番では集合の式・正規形・意味上の同値を別に定めるか、S5 §1.3 のように有限の秘密の分類を追い、宛先パターンは出口の照合に使う方が扱いやすい。

SFは任意の受け手集合に対する `flows` の判定器を作っていない。束の数学的な成立は、推論と等号判定の実装可能性の証拠ではない。ホストのワイルドカードは試作142と同じく頂点を除く一段以上の子孫を許す。URLの解析、scheme・port・要求の欄、DNS、リダイレクト、実際の送信先、利用者の操作の許可はモデルの外である。

### 一階の操作とハンドラ

`ask(arg)` を処理するハンドラは、導入時の環境を捕捉する。節は引数を受け取り、出力を行ってから純粋な式の結果で継続を一度だけ末尾再開する。捕捉した秘密を返す例、引数に秘密を渡す例、秘密の分岐内で操作を呼ぶ例を含めた。処理本体からの再度の `ask` も同じハンドラで処理する。

操作の署名は引数・返り値の通常の型と印、および呼び出し元pcの上限 `callPc` を持つ。節の検査pcは `callPc ⊔ 引数の印` とする。呼び出し時には `pc ⊑ callPc` を要求し、継続へ束縛する結果の印には呼び出し元のpcも加える。節の返り値の印が署名の返り値の印へ流れることを、ハンドラの契約で確認する。`callPc` は一つの固定した上限なので、精密なpc多相の推論より保守的である。

`HandleTyped` のエフェクトは、本体から `ask` を除き、節の出力のエフェクトを加える。一方、情報の流れの前提は残す。秘密を返す節の結果を公開と偽ると、呼び出し元だけは通っても `HandlerOK` が成立しない。秘密の引数を公開へ送る節も拒否する。秘密で呼び出しの有無が変わる操作に、公開へ定数を送る節を付ける場合は、呼び出し元pcの条件が拒否する。

この結果は、本番の `C_Handle` の効果の除去そのものが非干渉に反するという意味ではない。除いた効果から情報の印まで消す規則が不適切だと示す。節の非再開、末尾以外での再開、継続の保存・破棄、節内で外側のハンドラへ操作すること、入れ子のハンドラ、多相な操作、失敗のハンドラは試していない。

### 実行時監視と拒否

動的方式は、値の印を環境の値と対応させ、式の評価と束縛で印を計算する。分岐ではpcを上げ、実際に選んだ枝だけを実行する。出口の検査に失敗すると、その操作を出力せず、既に出した列を残して全体を停止する。受理した実行と実行器の対応も両向きに証明した。

二実行がともに `.done` なら、公開部分が同じ初期状態からの公開出力列は一致する。静的方式が拒否する到達しない枝も、動的方式では通せる。ただし、これは**正常終了を二つとも仮定する命題**である。

次の有限な反例では、秘密が真なら出口で拒否されて空列、偽なら最後の `send` が実行されて `[2]` となる。拒否のメッセージや終了状態を観測から除いても、列が違う。

```text
if secret then send(public, 1) else skip
send(public, 2)
```

したがって、拒否も終了した実行に数えて公開の失敗を観測するS5 §1.1 の本番案を、今回の監視だけで満たせるとはいえない。この反例はLIO全体への反例ではない。例外の印、捕捉、現在の印の復元などを持たない、SFの停止する監視への反例である。

証明の手間も動的方式だけが小さくはならなかった。静的方式は型付け導出へ帰納し、動的方式は実行された枝の受理関係へ帰納した。後者には、成功の関係と実行器の対応の証明、および拒否した実行の扱いが増えた。可変ストアやタスクを含めた方式間の費用差は未測定である。

`Release/Types.lean`・型代入・正規化・交換の既存の定理を全面的に変更するかは、配置の選択に依存する。印を通常の `Ty` や `Eff` の内部へ入れる案と、追加の判断と要約へ置く案を同じ費用とは数えない。

## 4. 四つの主定理を変えずに追加できるか

**静的方式を追加の判断にすれば、その見込みがある。** 現行の構文・型・遷移を残し、情報流の注釈・判断・事象列・二実行の関係を別モジュールに置く。注釈付きの表現を使う場合には、既存表現への消去と遷移の対応を証明する。これにより、旧定理は従来の型安全の定理として残せる。SFでも `Typed` が参照する実行関数 `run` は印を受け取らず、非干渉を別の定理として証明した。ただし、本番への消去・持ち上げは未証明である。

| 主定理 | 既存の言明・前提を保つ見込み | 別に必要になるもの |
|---|---|---|
| `Release.progress` | 追加の静的判断だけなら保つ。現行 `StateTy` の意味も保つ | 追加判断が付く状態の進行を使う入口、既存判断との対応 |
| `Release.preservation` | 同上。既存定理へ非干渉の前提を足さない | 情報流判断・pc・ストア・継続の保存。二実行の関係を保つ補題 |
| `Release.effect_soundness` | 効果の意味を変えなければ保つ。空効果の無事象と非干渉は別の保証 | 公開事象列と許す送信の定理、外部応答・解放の情報流契約 |
| `Surface.desugar_typed` | 通常の表層型付けと脱糖を保てば保つ | 表層の情報流判断の健全性、脱糖の前後の情報流判断と観測の対応 |

非干渉の新しい定理には、追加判断の成立、固定した方針、観測者から見た初期状態の同値、適切に対応する外部入力・応答を前提にする必要がある。組み込みの契約にも、秘密への依存を失わないことと、公開の観測に関する二実行の条件が要る。現行の `Builtins.Assumptions` からそれらは導けない。旧定理の前提を強めて「そのまま」と呼ぶ案は推さない。

今回、新たな論理公理を要求する理由は見つからなかった。本番でも、根拠のない非干渉を `axiom` にする必要はない。未解釈の外部処理を定理の引数の契約として扱うなら、その仮定と、Rust・OSまで実装を確認した範囲を区別する。

動的方式で拒否の遷移や印付きの状態を追加する場合は、その機械と旧 `Step` の対応が別に要る。旧定理を消去後のモデルのために残すことと、実際の監視付き機械について四定理を証明することは異なる。後者を今回達成したとはいえない。

## 5. 本番の規模の見直し

試行前の指定資料S3 §5.6 は「極大」とし、印・値/関数・pc・ストア・ハンドラ/継続・観測/開示・二実行・表層/脱糖の8群を挙げていた。SFの試行前には時間の数値の見積もりを固定していないため、増減率は出さない。今回、印の代数と有限な逐次計算、限定したハンドラは短い試作で成立したので、その3点を未確認の難問として積み増す理由はなくなった。一方、8群のうちストア・一般の継続・表層/実装の接続は残り、全機能の案を小さな改造へ評価し直す根拠はない。

次は、固定方針・有限の秘密の分類・逐次処理に絞り、追加の静的判断を置く本番案の、LLMによる実装・証明の作業時間の粗い見積もりである。S5の最小案に対応するが、その全規則をSFで試作した見積もりではない。区間の形式化の完成待ち、人間のレビュー待ち、長い検査の待ち時間は含めない。基準の変更や実装調査で幅が動く。

| 作業の群 | Lean | Rust・検査・文書 |
|---|---:|---:|
| 印・固定方針・観測の定義、入力と出口の契約 | 4〜8時間 | 8〜16時間 |
| 追加の判断、関数の要約、置換・呼び出し・pc | 12〜28時間 | 20〜44時間 |

全てのハンドラ、共有可変状態、Task、WASM、外部コマンド、解放まで自由に秘密と組み合わせる版は、依然として「極大・未見積もり」とする。上の時間に含めない。動的方式も、局所の型推論を減らせる一方で、印の保持先と拒否/例外の証明が増える。全実装を上より短くできる根拠は得られなかった。

## 6. 推す判断と受け入れに残る条件

**限定した静的方式へ設計を変えれば中心にできる、という暫定判断を推す。** 目的である「読める秘密を、接続自体は許された別のHTTP宛先へ送る」を、操作の許可とは独立した情報流の契約で拒否する。印の推論を既存の型・効果とは別に置き、有限の秘密の分類と固定した方針から始める。宛先パターンをそのまま束の要素にすることや、効果の除去で秘密度まで下げることは避ける。

この判断には、保護対象のプログラムで、契約と証明のない操作を検査時に拒否する設計が必要である。Task・汎用Process・WASM等へ秘密の値を明示的に渡さないだけでは、相手が自分で秘密を読む可能性を排除できない。秘密の入口の全経路、公開の失敗・診断・テストの報告、関数とハンドラの境界を、最初の計画で閉じる必要がある。未対応を素通しにして、本番全体の非干渉を宣言する根拠にはしない。

SFが解消したのは、小さな印の代数と二実行の証明、および制限したハンドラと効果除去との両立の疑問である。S5の関数の推論、失敗の扱い、標準APIの契約、秘密の取得元の分類、実HTTPへの接続、LLMが診断から修正する成功率は未確認である。本番に進めるなら、これらを計画・検査・レビューの受け入れ条件として具体化する必要がある。SFの終了0を本番の受け入れ完了には引用しない。
