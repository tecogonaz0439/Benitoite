# SG: 汎用の束・完全性の印・段階の互換性

**汎用の証明を土台にして、Phase 1 の利用者向けの範囲を有限の秘密の分類に限る案を推す。** この小モデルでは、Phase 1 の型付けを独立に定義しても、任意の束を引数に取る型付けの具体化と双方向に一致した。完全性を積の次元として加えた非干渉にも、同じ証明を使えた。有限の分類だけに証明を固定しておく必要は見つからなかった。

ただし、Phase 2 で endorsement を加えると、許した検査結果への依存を保証の言明に明示する必要がある。また、既存の入力を「信頼しない」と再分類した場合まで、以前の全プログラムが受理されるとはいえない。**束の汎用化の互換性と、新たな完全性の規則を適用した場合の互換性は別である。**

## 2. 汎用の束で増えた証明と減った証明

`FlowLattice` は順序の反射・推移・反対称、最小元、結びの最小上界、交わりの最大下界の法則を持つ構造体である。非干渉が使う部分は結びと順序であり、交わりも反対称性も帰納法の本体では使わない。実際には最小元を持つ結び半束まで仮定を弱められる。今回、完全性との積と有限集合のインスタンスを、束として同じインターフェイスに置いた。

観測者の閾値を `o` とし、`l` が見えることを `l ⊑ o` とした。結びの最小上界の法則から `(a ⊔ b) ⊑ o ↔ a ⊑ o ∧ b ⊑ o` を、順序の推移から可視性の下方閉包を導く。SFで観測者ごとに渡した法則を、`atLevel` の一度の証明へ集められた。観測する列は、出口の印が閾値以下である事象だけを残す。この定義では、一つの宛先の物理的な受信列に限定せず、その閾値で見える出口をまとめて観測する。

| 増減 | 内容と実際の証拠 |
|---|---|
| 増えた | 束の法則を明示する構造体、閾値の観測者を法則から作る証明、決定可能な順序と数学的な順序の区別 |
| 増えた | 有限集合・汚染の二点・積が法則を満たす証明。積の法則は任意の二つの束について一度証明 |
| 増えた | Phase 1 の独立な型付けと、汎用の型付けを両方向へ移す証明。これは互換性の証拠を作る費用であり、非干渉そのものの費用ではない |
| 減った | 印の具体例ごとの非干渉の帰納法。`expr_low_eq`・`lowEq_push`・`high_pc`・`noninterference` の **4件の証明本体はSFと文字列で一致**した。`inventory.py` が `:= by` 以下を照合している |
| 減った | 完全性のための新しい帰納法。積のインスタンスと閾値を変えるだけで、完全性と機密性の定理がともに汎用定理の適用になった |
| 減った | 各インスタンスでの結びの交換・結合・冪等・単位則の再証明。束の法則からの4件の補題へ集約 |
| 別に増えた | endorsement の承認と許した依存、fail の成功/失敗の観測。これは束の汎用化の費用ではなく、対象言語と保証を増やした費用 |

汎用の束が論理上の構造体であることと、利用者が任意の式で書いた順序・結びを実装で判定できることは別である。`lattice_noninterference` は決定可能な順序を引数にする。決定不能な場合の `arbitrary_lattice_noninterference` は標準の古典論理による非計算的な観測者を使い、実行できる型検査器や制約解法を与えない。任意の束に対する数学的な証明が通ったことを、任意の利用者定義に対する型推論の実装可能性へ読み替えない。

実際の試作では、最初の時計から有限版の双方向の対応が通るまで3分22秒、完全性・endorsement・failまでの最初の警告なしの検査まで10分04秒だった。後者は各段を独立に測った時間ではなく、読み取りと修正を含む累積時間である。本番の工数へこの速度を外挿しない。

## 3. Phase 1 から Phase 2 へ残せる定義と、変える必要のある部分

有限版の印は `Fin n → Bool` であり、公開は全てfalse、結びは各分類についてのor、順序は包含である。出口の `Accept(d)` に含まれる分類だけを送れる。S5 §1.3の有限な秘密の分類に対応する。未分類の秘密を自動発見する規則も、分類の集合が空のときに未知を公開へ落とす取得規則も作っていない。秘密の取得口の網羅性はモデルの外である。

`PhaseTyped` は `Typed` の別名でも変換の像でもなく、有限集合の和と包含で独立に定めた帰納的判断である。`phaseLabel`・`PhaseLowEq`・`phaseObserve` も有限版で定めた。両版は同じ通常の型・構文・実行の定義を共有する。`phase_iff_generic` は全ての `n`・方針・環境の型・pc・プログラムについての同値であり、一つの受理例だけの証拠ではない。同じ方針と分類を保つ限り、Phase 1 のプログラムと出力列の意味を変えずに、汎用の定理を使える。

| 対象 | Phase 2 での扱い |
|---|---|
| 有限の分類、和、包含、出口のAccept | 汎用の束のインスタンスとして残せる。消して別の分類を作る必要はない |
| Phase 1 の型付けと通常の非干渉 | 今回の範囲では作り直し不要。具体化との同値と、系の定理として残せる |
| 構文・通常の型・実行・観測する列 | 同じインスタンスではそのまま使う。利用者のプログラムを書き換える変換はない |
| 機密性に完全性の次元を加える場合 | 全てをtrustedへ埋め込むと受理を保存できる。`phase1_lifts_to_product` が証拠。ただし、この埋め込みだけでは旧入力に対する新しい完全性の保護は得ない |
| 旧外部入力をuntrustedに再分類する場合 | 完全性の制約が増え、旧コマンド実行が拒否されうる。上の同値定理では互換性を保証しない。入力の分類とAPIの契約を移行の対象にする必要がある |
| endorsement を含む保証 | 定理の言明が変わる。許した検査結果の一致を加えるか、許した影響を別に定義する。通常の完全性の非干渉のまま全プログラムへ広げられない |
| 失敗のないPhase 1から、公開の失敗を加える場合 | 言語・実行・型付け・観測・`high_pc`・非干渉を拡張する必要がある。これはPhase 2まで放置するべき互換性の作業ではなく、公開の失敗を保証するPhase 1自体に必要 |
| 推論器、関数/操作の要約、方針の入力書式、診断・交換・キャッシュ | 今回は未試作。束のインターフェイスを最初から分離すれば再利用しやすいが、作り直し不要とは証明していない |

したがって、**「段階に分けると数学的な定理を必ず捨てる」という懸念は、この範囲では否定できる**。一方、最初のAPIや方針の書式を有限集合の実装へ結び付けてから汎用化しても実装の修正が不要だ、という証拠はない。

## 4. 完全性・endorsement・失敗の保証

### 完全性の双対の非干渉

完全性は信頼度の高低を逆にした汚染の順序で表し、`trusted ⊑ untrusted` とする。結びはどちらかがuntrustedならuntrustedである。機密性との積では、両成分で流れてよい場合だけ流せる。公開のconsoleは公開の機密性を求めるが、信頼しない値も受け取れる。コマンドの出口execは全ての機密性の分類を受け取れる一方、trustedを要求する。

完全性の観測者の閾値は「全ての秘密の分類・trusted」とした。今回の3出口ではexecだけが可視となることを `sees_exec_only` で示した。二環境のtrustedな入力を一致させ、untrustedな入力を任意に変えても、型が付いたプログラムのexecの内容・有無・順序は変わらない。信頼しない値で分岐して定数のコマンドを実行する例も、pcの汚染を通じて拒否する。

### endorsement で許す依存

方針は外から固定して渡す `Policy` とし、許す規則の番号、検査する関数、許す結果についての性質を持つ。モデルの `check_sound` は、検査に成功した結果が文字列で、方針の `approved` を満たすという契約である。この契約の具体例を、`/usr/bin/true` と `/usr/bin/false` だけを許す純粋な検査の実装について証明した。両文字列はモデルの事象の内容であり、OSのコマンドを実行してはいない。

未検査の入力をexecへ渡すプログラムは拒否される。許した検査を通して得た文字列をtrustedとして束縛する `checkedExec` は受理され、実際に生じるコマンドの事象が `approved` を満たすことも示した。未許可の規則の番号は型付けで拒否され、実行の関数でも出力しない。

このendorsementは、**top-levelに一回、入力の機密性は公開、呼び出し元の完全性はtrusted**に限る。任意の秘密を公開にする機能はない。検査に失敗すると空の列で終わり、その失敗の種類や診断は観測しない。段4の失敗をこの実行器へ接続した証明ではない。一般の関数・ハンドラ・高いpcの内部での検査も試していない。

`endorsement_noninterference` は元の観測可能な入力の一致に加え、検査の `Option Value` の結果の一致を前提にする。検査に失敗したかどうかもこの一致に含める。成功した二つの別の許可済みコマンドを比べると、元の完全性の同値は成立してもexecの事象が違う。よって、この前提なしの通常の完全性の非干渉は成立しない。逆に、機密性については、入力を公開に限った条件から検査結果の一致を導けるため、通常の非干渉を保つ。

### 失敗を含む静的方式

段4(a)はRV-S5 F1-1に答える追加である。`Failure.Result` は出力列を持つdone/failedの二種類とし、failの前の出力は残し、後の出力を打ち切る。投影は出力先を隠してもdone/failedを区別する。全ての実行が有限に終わる小言語であり、「両方がdone」という前提は置いていない。

failには `pc ⊑ bottom` を要求する。これにより、見えないpcからは可視の出力も公開の失敗も生じず、`high_pc` は投影した結果が `done []` と示せる。順次実行の証明には、結果の投影が打ち切りを伴う合成を保つ補題 `observe_then` を追加した。秘密への分岐でfailする例は拒否され、公開の出力の後に無条件でfailする例は受理される。failの存在自体を排除した証明ではない。

この規則は保守的である。秘密の枝がどちらも必ず同じfailを起こす場合などを、精密な制御解析で受理することは試していない。算術・添字・外部応答・解放等で暗黙に起きる失敗を、今回の `.fail` と結ぶ規則もまだない。秘密のpcの下でそれらを許す本番の静的方式は、同じ失敗の漏れを持ちうる。SFの実行時監視の反例は、静的方式一般の優越も、接頭辞による弱い保証の否定も示さない。

## 5. 本番で手が入る定義・定理と公理

[inventory.py](inventory.py) は、固定コミットの `git show` で構成子を集め、`git grep -l -E` で `HasTypeVQ|HasTypeCQ` と `HasTypeClausesQ|ContTy|E_OpPrim|E_Resume` をRelease/Surfaceから探した。字句上の参照はそれぞれ43ファイル・33ファイルである。両者は重なり、コメントも含むため、合計を変更ファイル数とはしない。

| 本番の定義・定理 | 今回のモデルとの距離・概数 |
|---|---|
| `Release/Syntax.lean`: `Val`・`Comp`・`Clause` | 構成子15・13・2。今回は関数・コレクション・節を含まない。汎用の束を用意しても、これらの依存を追う規則は別に必要 |
| `Release/Typing.lean`: `HasTypeVQ`・`HasTypeCQ`・`HasTypeClausesQ` | 主な接続はこの3判断。値・計算は各17規則。`C_If`・`C_Match`・`C_App`・`C_Handle`・`C_Handle_Fail`・`C_Resume/L`のpcと結果・捕捉の要約が対象 |
| `Release/Semantics.lean`: `Frame`・`Cell`・`State`・`ContTy`・`CellOk`・`StoreOk`・`StateTy` | 枠7・セル6・状態4・継続の型付け10規則。局所構築器・継続のセルも含め、二実行の対応が必要。SGの環境のpushだけでは足りない |
| 同 `Step`・`Event`・`Steps` | 68遷移・事象2種。既存の `Steps` は事象列を保持しない。`E_IOErr`・`E_OpFail`・`E_ResumeErr`・`E_Err*`・`E_Exit*`・`E_RelErr` 等の成功/失敗と後続の打ち切りを接続する必要がある |
| `Release/Assumptions.lean`: `Builtins.Assumptions.delta_typed`・`io_typed`・`io_kind`・`release_exists` | 現状は主に一実行の通常の型と応答についての契約。公開応答の二実行の対応、失敗の印、許す検査・開示の契約はここからは導けない |
| `Surface/Typing.lean`・`Desugar.lean`・`Check*`・`Lemmas/*` | 表層の追加判断と脱糖後の印の対応を新設する。SGの単一構文の同値は、実際の脱糖の対応ではない |
| Rustの型検査・関数/操作の要約・APIの契約・診断・交換 | 有限集合の演算を束の操作として分離することはできるが、実装していない。利用者が束を定義する書式・法則の検査・制約解法・方針との整合が追加の対象 |

通常の型・エフェクト・実行の意味を残し、情報の流れの判断を追加する案では、現行の四主定理の言明を弱める必要は今回見つからなかった。これは本番への接続を証明した結果ではない。

| 主定理 | 保てる条件と追加する証明 |
|---|---|
| `Release.progress` | 既存の型付け・遷移を保てば言明を残せる。追加の情報流判断の進行と、拒否する構成の境界は別に示す |
| `Release.preservation` | 通常の型の保存は残せる。印付きの値・pc・継続・二ストアの関係についての保存を新設する |
| `Release.effect_soundness` | エフェクトの意味を保てば言明を残せる。空効果の一実行の性質から非干渉は導けない |
| `Surface.desugar_typed` | 通常の脱糖と型付けを保てば言明を残せる。情報流の判断・観測・方針の対応を別に証明する |

新しい非干渉の定理には、束の法則、固定した方針、情報流の型付け、観測者から見た初期状態の同値が必要である。本番の外部入力については、二実行の応答を関係付ける契約も必要になる。endorsementには許した検査結果の一致等が増え、公開の失敗を扱うにはその失敗がpcの規則に従うことも必要になる。既存の四定理へこれらを黙って追加し、以前と同じ保証だと扱わない。

独自の公理は要らなかった。表示した15件の公理依存は、実行できる有限版と失敗版ではLean標準の `propext`・`Quot.sound` の範囲である。決定不能な順序も許す `arbitrary_lattice_noninterference` だけは標準の `Classical.choice` も使う。これは実装可能な判定器の仮定を消した数学的な版であり、独自の `axiom` で非干渉を仮定したものではない。

## 6. 本番の規模の見直しと推す判断

試行前の比較基準はS5 §8.2の限定案、Lean **88〜210時間**、処理系・文書等 **94〜212時間** とする。RV-S5 F5-1のとおり、ストアと失敗等を含まないSFの小さい別見積もりを、費用が下がった根拠にはしない。今回、分類のインスタンスを変えるだけで主たる帰納法を再利用できたので、**束の汎用化のために二実行の証明全体をもう一度作る費用を積み増す根拠はなくなった**。しかし、関数・ストア・ハンドラ・解放・実APIの接続は残るため、本番全体の基準の幅は縮めない。

| 範囲 | Leanの見直し | 処理系等の見直し |
|---|---|---|
| Phase 1を有限の分類とし、内部の判断・証明を汎用にする | S5の「分類・束」内で計画する。有限版から汎用版への全面的な非干渉の再証明は計上しない | 抽象化する境界、有限集合の実装、方針の分類との接続を最初から分ける。Rustの試作がないため、基準の時間は下げない |
| Phase 2で別の束のインスタンスだけを加える | 法則・観測者・型付けとの対応が主な追加。今回のSFの4証明の再利用が根拠 | 順序と結びの決定可能な実装、診断・交換・キャッシュの対応が追加。ソースの変更件数と時間は未測定 |
| 利用者が定める束の公開機能まで同じ版へ入れる | 書式の意味、法則を満たす条件、制約解法の健全性が未試作。**追加工数は不明** | 入力・検査・推論・契約表示・版の固定・移行の追加工数は不明。数学的な定理の短さから見積もらない |
| 完全性と一般のendorsementを本番の全機能へ広げる | 積の束自体は解決したが、権威・許した依存・制御/失敗との合成・二ストアが残る。追加工数は不明 | 信頼する入口/検査/出口の実装と、外部コマンドの直接の読取・環境・副作用等が残る。SGのexec事象では認定しない |
| 公開の失敗を含むPhase 1 | S5の正常/異常のpcの作業を減らさない。今回のfailは最小の原理の証拠 | 暗黙の失敗、診断、実際の終了処理の経路の点検を減らさない |

共通条件の三択では、推す判断は **「限定案へ設計を変えれば0.0.13の中心にできる」** である。具体的には、利用者向けの初段を有限の秘密の分類と固定方針に限り、内部の型付けと定理は最初から束で抽象化する。公開の失敗は初段の保証に含め、未対応のハンドラ・ストア・外部操作を素通しにしない。汎用の利用者定義の束や一般のendorsementを0.0.13へ全て含められる、という判断は推さない。

この判断の根拠は、Phase 1の独立な規則と汎用の規則の同値、具体化による非干渉、積での証明の再利用、公開のfailを含む非干渉の成立である。設計者が段階案を選んでも、この小モデルで確かめた定義と定理を捨てる必要はない。残る難所の大部分は束の具体性ではなく、既存の全ての値・制御・失敗・外部操作を二実行の保証へ接続することにある。
