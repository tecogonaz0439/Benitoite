## Lean と実装の読解

`Release/TargetTable.lean` の13項目を読んだ。検査2・射影2・拡大2・File6・Http1であり、Http の型は `clientRequestTy = .data "Http.ClientRequest" []` を用いる。`valContent` と要求検査の第4引数・射影の戻り値が同じ型であることを、同ファイルと `ModelHttp.clientRequestDecl` の五欄へ照合した。

`Release/Typing.lean` の V-Checked・V-CheckedRequest、`Scope/Domain.lean` の `Range.Mem`・`Range.top_mem`・`Target.WF` は別の条件である。値の型付けの前提に `Target.WF` はない。Rust の `builtins/funcs/scope.rs::path_in_result` は動的条件と静的 R を確かめ、入力の String を一欄へ保持する。`http_client/checked_request.rs` は同じ要求を三欄の欄0に保持し、射影と送信が同じ欄を読む。`file.rs::retained_path` と `checked_request.rs::retained_request` は、対象を持たない定数へ代替する分岐を持たない。これらは通常の型検査済みプログラムの経路の照合であり、raw なホスト呼び出しの任意値を保証しない。

`Release/ModelHttp.lean::check_send_preserves` は、検査成功値から同じ要求が射影され、同じ対象を保持し、その対象一つの観測を返す応答が関係に属することを示す。実ソケットの通信内容との一致や拡大の δ は結論に含まれない。Rust の実通信への対応は R30.3/.4 の実装と制御した相手による証拠を用い、Lean の証明へ読み替えない。

`Surface/ClauseIxRule.lean::clauseIxIn` は範囲変数を持つ組み込み操作だけに `clauseRangeIn` を使い、それ以外は Top とする。L50.4 中3の結果と R20.6「保持の再照合と R30 への契約」、RV-R20・RV-R20.6を再読した。保護本体の推論した効果から節の添字を選ぶこと、型付けは被覆で広げた本体からも選べるため検査器がより狭いことは、07-04の本文と表に既に記録されている。処理しない書き込みを含む handle の受理と、捕捉した狭い不変の値を広い引数へ渡す節の拒否を区別する記述も保った。

初期の同じ ε、BA の末尾、旧像の同値の射程も再照合した。到達先の対象健全性の本文は `stateTyE_init_eff`・`steps_preserve` により初期の ε を同じ末尾へ保ち、`StateTy` の存在量化した末尾を使わない。BA の本文は `BuiltinOnly.iff_old` の同値を旧像に限り、`stateTy_of_old` を旧の型付け全体の同値としない。被覆についても `Eff.covers_iff_sub_old`・`Ty.le_iff_leOld` は旧の原子・規則の前提の射程に限り、非 Top 全体の型付けの同値へ広げない。表の BA の一文だけが本文より広く読めたため修正した。停止条件に該当する規則や保証の変更は要らなかった。
