## 警告との分離

コードの順序は次のとおりである。`decls::check_recorded` が宣言検査後に構造入力を集め、`check_function` が規則を持つ本体の局所解析を制約生成前に行う。型制約と節の選択を解き、最終の節との一致を確認する。その後、本体後検査・旧定数警告・旧 Scope/Regex の既知不良検査を行う。全本体の後で `accept_program` が確定列を必須の記録と照合し、最後に `interval::AnalysisState` が型確定後の入力を解析して警告を追加する。公開の宣言契約へ本体の推論結果を書き戻す接続はない。

本体の型検査または旧既知不良検査の誤りは `interval.invalidate` によりその本体を無効にする。全本体の後の必須の E0519 はこの無効化を行わず、区間解析は続く。どちらも別の正常な定義の警告を取り消さない。この二つを文書上でも区別した。

| 通常入口の検査 | 独立した期待値と確認した退行 |
|---|---|
| Scope の同時保持を1件から513件へ増やす | 末尾の動的な検査に狭い戻り型を要求し、通常の型検査が返す E0519 を比較する。1件保持では unknownSource、513件保持では budgetExceeded となる。両入力で、同じ本体の停止前と後続の正常な本体の W0401 を二件ずつ保ち、コード・主文・注記も一致する。テスト側の解析し直しを超過の根拠にしない |
| Scope の E0519 と旧 Scope の E0459 | 同じ本体と後続の正常な本体に除数0の候補を置く。各入力の誤りは意図した一件だけで、E0519 は W0401 二件、E0459 は一件となる。本体の無効化の違いを回帰テストで確かめる |
| 必須拒否と旧検査の本体無効化（補足 CLI） | 同じ本体と後続の正常な本体に警告候補を置く。E0519 は両方の W0401 を保ち、E0459 は誤りのある本体だけ無効にする。両入力の終了は期待する2で、[台本](warning-order-probes.py) は終了0。[入力ハッシュ・診断位置](warning-order-probes.json)を保存した |
| Range の成功範囲を0と1へ変更 | W0401 の有無が変わっても、両方を受理し、Scope の確定した範囲の列を同じに保つ |
| 算術4,000行を500行ごとの8ブロックへ配置 | 区間解析が本体操作数の予算で実際に止まったことを公開の集計で確認する。それでも先の Scope 検査の `/data/**` の列と狭い戻り型を受理する |
| Top を宣言した関数から狭い戻り値を要求 | 本体の検査条件が `/data/**` でも、利用側が宣言上の Top を狭い型として使うと E0401 になる |

513件を一直線に保存する形は、Range 自身の本体予算にも届く。そこで、同じ本体の超過後の地点に新しい警告が必ず出るとは期待せず、停止前の候補と後の正常な定義の候補を検査する。Scope が原因で Range の予算が止まったという意味ではない。両方の状態と上限は別であり、これらの有限の入力を全入力に対する独立性の証明とは呼ばない。

補足 CLI の実行ファイルは引き継いだ debug の実体で、ハッシュを保存した。この補足が使う E0519・E0459 と警告の経路には本枝の本番差分がなく、作業版の公開入口の検査は W-R に含む。

作成時の関門では、既存の小予算の局所解析の検査が通常の警告の駆動・本体の無効化・確定した型の引渡しを通さない点を不足とした。上の契約を既存の公開の入口で検査し、解析の内部の関数を置き換えていない。
