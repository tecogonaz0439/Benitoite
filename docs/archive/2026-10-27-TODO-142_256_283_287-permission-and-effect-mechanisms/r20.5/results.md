## 計上と Lean の対応

`ScopeLimits` の操作数・保持数の状態は、Range の警告の予算から独立している。「全体」は一つの定義の中の入れ子の本体を含む範囲であり、別の定義との合計ではない。これは `ScopeLower.analyzeBody` が初期値から始まる意味に合わせた。測定 JSON の `whole_operations_total` は入力内の各定義の測定値の合計であり、本番の予算カウンタではない。

| 計上点 | 操作数 | Lean の対応 |
|---|---:|---|
| 直接の呼び出しの同定と表の参照 | 1 | `stepCost.call`。表層の funName/primName の頭。登録済み組み込み操作を含み、利用者の操作・間接呼び出しを含めない |
| 局所引数の読み取り | 1 | `readCost` |
| 同じ成功値の再照合 | 1を加える | checked の `readCost`。受理の問い合わせでは再計上しない |
| 引数の直接の射影の適用 | 1を加える | `argCost.proj` |
| 呼び出しの結果の事実の書き込み | 1 | `stepCost.call` の transfer が some の場合 |
| Ok の腕 | Result の読み取り1、由来を写せればさらに1 | `stepCost.okArm`。事実の書き込みを重ねて数えない |
| 別名 | 1 | `stepCost.alias`。checked の再照合を重ねて数えない |
| join の一段による忘却 | 事実のある位置数 | `stepCost.join`。`ScopeLower` の通常ソースの経路はこの一段を発行しない |
| リテラル・整数・other の引数 | 0 | `argCost.lit/int/other` |
| 受理の再照合・rejoin・本体の入口と出口 | 0 | `Required.ofIndex`・`ScopeLower.rejoin`・`Run.enter/leave`。これらに伴う忘却も無料 |

保持数は事実を持つ位置ごとに1であり、由来もその項目に含む。判定順は、本体操作数→全体操作数→本体保持数→全体保持数である。`Budget.admit` と同じく失敗した計上は採用せず、全ての事実を忘れる。停止後は `Run.step` の stopped 分岐と同じく位置だけを増やし、転送・費用の再計算を行わない。

`ScopeMetrics` は承認した操作数、候補を含む保持最大数、最初の超過の種別と文の先行順番号を記録する。Ok の一段の超過は、それを導入した match の位置に対応する。番号ラベルを確定するときは超過の記録の番号も同じ対応で更新する。

番号付けのイベントは、局所解析と別のカウンタで1ずつ数える。R20.5b で `DEFAULT_NUMBERING_OPERATIONS = 200_000` に分離した。`numbered_with_budget` と本番の `analyze_pending_with_limits`・最終の `renumber` はこの独立した上限を使う。`ScopeNumberingBudget.operations` は入れ子と共有定数の展開を含めて定義ごとに数え、局所解析の `limits` は読まない。番号付けの費用を Lean の `stepCost` に加えない。番号付けが止まった場合だけ、取得済みの接頭辞から事実を作らず、全規則を Top として扱い、番号を未確定とする。停止は `NumberingLimit { max_operations }` とし、局所解析の `BudgetExceeded { scope, resource }` と区別する。これは Lean にない Rust だけの資源制限である。

## 入口と出口の通常ソースのテスト

`nested_budget_entry_and_exit_follow_run_enter_leave` は、外側で Result を一つ保存し、lambda の内側でリテラルによる検査を四つ行い、外側で保存した Result を照合する。外側の検査は2操作、内側の検査も各2操作、外側の Ok は2操作である。番号は外側の検査0、lambda 4、内側の検査5/9/13/17、外側の match 22である。期待値は `Run.enter/leave` と `rejoin` から手で作った。

| 上限（指定しない欄は100） | 内側の最初の超過 | 先行順番号 | 外側 match 22 の事実数 | 結果 |
|---|---|---:|---:|---|
| 本体操作数5・全体操作数100 | Body/Operations | 13 | 1 | 外側は4操作で完了し、直接射影の由来が残る |
| 全体操作数8 | Whole/Operations | 17 | 0 | 外側も同じ理由で止まる |
| 本体保持数1 | Body/Items | 9 | 1 | 内側の超過は戻さない。外側の Ok で別に Body/Items を超える |
| 全体保持数1 | Whole/Items | 5 | 0 | 外側の保持を足した最初の内側の検査で超え、外側も止まる |

種別だけでなく停止番号も照合するので、入口で操作数を0に戻さない、全体の消費を0へ戻す、外側の保持を足さない退行を捕まえる。R20.5b の `numbering_budget_preserves_prefix_and_counts_only_admitted_events` は、通常ソースの Unit の本体を3イベントと手計算し、上限0・上限1・上限2・既消費を含む累積・ちょうど上限の五形で、接頭辞と失敗したイベントの非計上を確かめる。既存の `budget_forgetting_keeps_positions_and_literal_conditions` も残し、位置を保つ忘却と小上限を確かめた。

テストの作成時の関門では、本物の読み込み・名前解決・型検査が返す `ScopeBodyInput` を使う境界を選んだ。既存の同一上限のテストでは入口と出口の区別を検査できない。実装の非公開の段を差し替える注入の入口は増やしていない。

R20.5 時点の新規の通常テストは3件、測定の ignored テストは1件で、既存テストの削除はない。当時の配置別の差分は [集計](line-counts.json) に保存した。R20.5b は lib の六規則の停止のテストと、通常入口の注記のテストを加え、既存の理由の表と番号付けの境界のテストを更新した。追加のテスト専用の本番入口はない。

## 拒否理由と診断

| 理由 | 分類 |
|---|---|
| `notCovered` | 既知の範囲を契約が覆わない、または必要な範囲の列が不足する |
| `atomicCoverOnly` | 同名の非 Top の閉じた原子が二つ以上あり、一原子では被覆を確認できない。和による実際の被覆を証明した理由ではない |
| `unknownSource` | 非超過の本体で由来を認定できず Top となる。明示の Top もこの分類に含む |
| `budgetExceeded` | 最後の Run に予算の超過が残る本体で、規則が Top を選ぶ位置。超過の前後を区別しない |

`Required.ofIndex` と同じく、最後の Run が超過しても記録済みの非 Top とリテラルの条件を保つ。局所の文字列を定数伝播しない。番号付けだけの超過による全規則 Top の制限は上記のとおり別に扱う。原子の和を調べない局所の一範囲の受理は `atomicCoverOnly` を発行せず、同名原子の分類は既存の効果の被覆検査が担う。

`exceeded_reason_applies_to_top_at_every_location_but_preserves_literals` は、超過前後の局所文字列の条件をどちらも budgetExceeded とし、リテラルだけ既知のままにする。明示の Top の引数も既存の受理テストの表へ追加した。新しい退行テストは B_WORK の accept.rs に一時的に戻した状態で意図した失敗を確認し、直後に修正版へ戻した（[失敗ログ](required-before.log)・[計時](required-before.json)）。git の状態を変える操作は使っていない。

E0519 の局所解析の超過には `budgetScope`（body/whole）と `budgetResource`（operations/items）を使う補足を残した。R20.5b では番号付けの停止を `numberingLimit` と専用の注記・修正案に分け、全規則が Top を要求することと、定義を分けるか小さくする案内を示す。文言は `diag::codes`、値の語は `typeck/text.rs` に置く。E0521 は R20.5 の変更のまま保ち、RV-R20.5 軽3の再現・文言・const の扱いは R20.6 へ引き継ぐ。

01-06・02-05・02-10 と、01-12・07-04 の対応の記述を更新した。01-06 の「一意」を最終の効果と選んだ S の一致へ改め、循環の解の選び方を新しく決めていない。診断表から `gen_skill` を実行し、同梱の `skill/references/diagnostics.md` を再生成した。

### ハンドラの費用と対策案

逐次・後の節からの lambda・完全な File.Read の再推論・連鎖候補を測った。Scope の規則を含まないこれらの本体は Scope の必須解析を省略するので、局所の計上は0である。400組の完全 Read の入力は番号イベント30,803、400段の鎖は24,019であり、R20.5b の番号上限200,000には届かない。規則なしの本番の型検査はこの番号付けを呼ばない。これらのハンドラの入力を局所解析の採用上限の根拠から外した。ハンドラの効果伝播の費用は Scope の予算では抑えられない。

再推論は完全 Read の群で1回、連鎖10/40/400段で2回を観測した。H 回の再推論を起こす通常ソースの最悪例は未発見であり、H 回ならおよそ三乗になるというレビューの指摘を実測済みとしない。測定した最大の入力と、理論上の最悪の回数を区別する。

推す対策は、`finish_next` ごとに `propagate_effects` の全体の処理と `effect_inputs` の逆引き表の構築を繰り返さず、追加の制約で影響する部分だけ更新し、索引を再利用することである。選んだ S と最終の効果の一致の再確認、再推論の上限と E0521 は保つ。これは効果の解決の方式の手当てであり、本作業の Scope の計上単位は変えない。差分が大きいため R20.6 で別の実装作業へ分けるか、取りまとめが後の項目へ登録する案を申し送る。本作業で方式を置き換えず、依頼どおり測定と対策案を出して進めた。

W-R は `run-command.py` が `/usr/bin/time -p scripts/check.sh ...` をパイプを挟まずに直接起動し、check.sh から伝わる終了状態0を保存した。`time -l` は使っていない。最大常駐量は、新しい Python プロセスの `getrusage(RUSAGE_CHILDREN)` による補助値である。macOS の原値は bytes、MiB は2^20 bytesで換算し、一括実行の子の最大値であって並行プロセスの合計ではない。Q の入力別RSSは、同じ release の実行ファイルを入力ごとの新しいプロセスで起動し、38件すべて終了0かつソースのハッシュ一致を確認した。Q と同じ入力・上限の補助測定であり、採用値の根拠に別構成を混ぜていない。

W-R は一度の実行で成功し、以後の実装・テスト・設計書・生成物の変更はない。作業記録とハッシュの保存だけを続けた。ヒープの根・障壁・保持の方式は変更しておらず、追加の H は不要とした。`lake build`・`check-formal.sh`・short は実行していない。
