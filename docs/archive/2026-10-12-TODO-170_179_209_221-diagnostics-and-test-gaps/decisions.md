# 判断とその理由

調査（`study.md`）の後に、利用者から見える振る舞い・診断の文言の方針・凍結した型に関わる八つの問いを設計者に尋ねた（Q1〜Q8）。どれも推奨どおりの答えだった。残りの点は、調査の推奨どおりとした（R1〜）。

## 設計者に尋ねた問い

### Q1 TODO-170: 利用者の宣言が prelude の名前を隠したことを、どう示すか

- 選択肢: 注記だけ／警告にする／行わない。
- 設計者の答え: **注記だけ**（推奨）。
- 内容: 隠した名前で誤りが起きたときだけ、その診断に注記を添える。添える先は、名前解決の E0303・E0330（最初の段が隠した参照のとき）と、型の不一致の E0401・E0410（期待と実際の型に、利用者が宣言した prelude と同じ名前の型が含まれるとき）である。E0303・E0330 では、隠された prelude の束縛がその名前を持てば、`Benitoite.` を前に挿入する置き換え付きの help を示す。型の不一致では `Benitoite.X` で prelude の型を書けることを help で示す（置き換えなし）。
- 理由: 型やレコードの名前に `Task`・`Result` を使うのは正当である。警告を抑える手段がない（02-10「警告の扱い」）ので、警告にすると正しいプログラムにも出続け、`--deny-warnings` で通らなくなる（`study.md` の A 部 3 節）。
- 02-04「名前の引き方」に残る「型検査器が注記を添える」の記述を、実装した範囲に合わせて書き直す。

### Q2 TODO-179: E0303 の補助をどこまで広げるか

- 選択肢: 表＋一覧／表だけ／一覧だけ。
- 設計者の答え: **表＋一覧**（推奨）。
- 内容: 0.0.0 の旧名（約 28 項目。モジュールの改名 `Int`→`Integer` などは E0301・E0302 で示す）と、他言語の名前の別名（`Map.insert`→`set` など 20〜30 項目）を一つの表にし、近い名前より先に引く。当たれば候補一つとして置き換え付きの help を示す。表にも近い名前にも当たらなければ、そのモジュール（型）で使える名前の一覧を注記で示す。表の行の正しい名前が今の標準ライブラリにあることを確かめる単体テストを置く。
- 理由: Skill の評価で、LLM が名前を推測して誤る例が多かった。今の近い名前（編集距離 2 以下）は、`Map.insert` に何も示さず、`Int` に `IO`・`Set` を示す（A 部 2 節 (b)）。

### Q3 TODO-179: 診断のモジュールの名前をどう示すか

- 選択肢: 書いた形／書いた形＋本来の名前。
- 設計者の答え: **書いた形**（推奨）。
- 内容: E0303・E0330 の見出しとラベルのモジュールの名前を、参照に書いた段（`String`・`Benitoite.String`・別名 `S`）で示す。修正案の文も同じ形で書く（`S.byteLength`）。E0330 の `public` を付ける修正案は、宣言のあるファイルを直す案内なので、本来の名前で示す。
- 理由: 02-05「ソースに書いた形で示す」に従う。今は `import Benitoite.Unofficial.IO.Console` で取り込んだものも `Benitoite.IO.Console` と示し、書いた名前とも取り込んだ名前とも合わない（A 部 2 節 (b)、B 部 1 節）。

### Q4 TODO-179: E0339 の修正案に、別名への参照の書き換えを含めるか

- 選択肢: 含める／含めない。
- 設計者の答え: **含める**（推奨）。
- 内容: エフェクトを宣言するモジュールの改名（`as`）を拒む E0339 の修正案で、`as` を消す編集に加え、同じファイルの別名への参照を本来の名前に書き換える編集を含める。E0321 の修正案（別名を残す）は、適用すると E0339 になる二段の流れのままとする。
- 理由: 今は `as` だけを消すので、適用すると E0302 になり、誤ったモジュールの取り込みを勧める遠回りになる（C 部 7 節）。名前解決の段は参照の位置を知っている。

### Q5 TODO-179: 文章の形の診断で、端末の制御文字をどこまで逃がすか

- 選択肢: 全文＋双方向の制御文字／全文だけ。
- 設計者の答え: **全文＋双方向の制御文字**（推奨）。
- 内容: 見出し・注記・help・段の名前を含め、文章の形の描画の一か所で逃がす。双方向の書式の制御文字（U+202A〜U+202E、U+2066〜U+2069 など）も対象にする。JSON の出力は逃がさない。`main` が返す `Result.Error` の文字列は利用者の出力なので対象外とする。
- 理由: 今は抜粋とファイル名の行だけを逃がし、E0101・E0125 の見出しのパス、ラムダの段の名前、注記と help は逃がさない。双方向の制御文字はどこでも逃がさず、表示を入れ替えて読み手を欺ける（C 部 6 節）。

### Q6 TODO-179: `handle` の節から操作の型パラメータの値が出る誤りをどう示すか

- 選択肢: E0401＋注記／専用の診断コード。
- 設計者の答え: **E0401＋注記**（推奨）。
- 内容: 剛な型を操作の型パラメータの名前で示し（`Option[T]`）、「`T` は操作 `Swap.store` の型パラメータで、その型の値は節の外へ出せない」旨の注記と、節を指す補助の位置を加える。凍結した `TyNames` は変えない。
- 理由: 今は「expected `Option[_]`, found `Option[_]`」と読めず、外側の関数が型パラメータを持つと、その名前を誤って示す（C 部 8 節）。専用のコードは、コードの表と Skill の文書の変更が増える。

### Q7 TODO-209: 標準ライブラリの上限の定数と処理系の定数をどう合わせるか

- 選択肢: 非公開の組み込みの関数／ソースを読むテスト／コメントだけ。
- 設計者の答え: **非公開の組み込みの関数**（推奨）。
- 内容: 非公開の組み込みの関数（`Regex.maxStringBytes`。名前は作業で確かめる）が `MAX_STRING_BYTES` を返し、`Regex.bnt` は数を直接書かずにそれを呼ぶ。
- 理由: 値の出どころが一つになり、突き合わせのテストが要らない。非公開の組み込みの関数（`findAt`・`spanAt`）と引数のない組み込みの関数（`Bytes.empty`）の前例がある。ソースを読むテストは字面で探すテストで壊れやすい（D 部 1 節）。対応する定数は、この 1 組だけだった。

### Q8 TODO-179: 主スレッドで起きた panic の報告のスレッドの名前

- 選択肢: 凍結した `FaultThread` に `Main` を加える／呼び名を変える・設計書で読み替える。
- 設計者の答え: **`Main` を加える**（推奨）。凍結した型の変更の了承を得た。
- 内容: `FaultThread::Main`（表示は `main`）を加え、`fmt`・`test`・`skill` の本体と CLI の外側の境界の panic をそう呼ぶ。
- 理由: 今は主スレッドの panic も「the panic occurred in the compiler thread」と示す（C 部 2 節）。`Stage` の呼び名を変えると、段のスレッド（64 MiB のスタックの別のスレッド）の panic を正しく呼べなくなる。

## 推奨どおりとした問い

- R1 E0416 の位置: 理由 `FnBody` の位置を本体の最後の式文にする（最後の文が式文でなければブロック全体）。E0438 も同じ位置へ移し、同じ本体に E0416 を報告したときは E0438 を出さない。戻り値の型を書いたラムダで E0416 を出したときは、`LambdaReturn` の E0401 を重ねない（A 部 1 節・2 節 (a)）。
- R2 E0416 の `return` の修正案: 本体の戻り値の型が Unit でないとき、`return ` を挿入する修正案を最初に示し、`discard` を出さない。戻り値の型を書いていないラムダでは、`return` と `discard` の両方を置き換え付きで示す。`-> Unit` は今のまま。
- R3 旧名の help に版を書く（「0.0.1 で改名」）。別名の表の行は A 部 2 節 (b) の候補を、今の標準ライブラリの名前と突き合わせて作業が決める。
- R4 修飾した名前の途中の段が見つからないとき（`IO.Console.write` を import なしで書いた）も、E0302 と同じ足りない import の修正案を出す。
- R5 E0321: 最後の段が標準ライブラリのモジュールの最後の段と大文字小文字を区別せずに一致するものを、距離の候補より先に示す。候補の案内は note でなく help に揃える。
- R6 E0304: レコードを値や呼び出しの位置に書いたとき、フィールドの名前を使った構築の形を help で示す（置き換えなし）。レコードの E0303 で `new`・`create` などを書いたときも同じ。E0212（波括弧で構築した）の案内は、構文解析器の回復が絡むので扱わない。
- R7 E0201: 文の終わりで直前が名前の `[` に出会ったとき、呼び出しは型引数を取らないことを help で示す。`名前[…](` の形なら `[…]` を消す置き換えを付ける。
- R8 `IO.All` の表示: 型を表示するとき、`IO.All` の 10 個のエフェクトをすべて含む集合を `IO.All` とまとめる。利用者が 10 個を一つずつ書いた場合も同じに示す（B 部 2 節 (a)）。
- R9 E0211 の `!` などの経路（`foreign.rs`）は、記号が演算子を置けない位置にあり、置き換えても誤りが残るので、edits を付けない。02-10「修正案」の規則に合うので、理由をコメントに書くだけにする（B 部 2 節 (b)）。
- R10 `pattern_arity` の E0412 は書いたパスで構成子を示す。`uses_then_bracket` の E0209 は位置を型全体にし、E0316 と同じく括弧で囲む置き換えを付ける（B 部 2 節 (d)）。
- R11 定数の鍵の文は、テストの実行器と同じ `Show.show` の形で示す（文字列の鍵は引用符付き）。`bound_failure` の文字列は `typeck` の `text` に移す（B 部 3 節）。
- R12 E0507 の注記 `state` は、操作を宣言したモジュールが Prelude か Stdlib のときだけ付ける（TODO の見出しと向きが逆だが、本文と出どころは絞る向きである。B 部 4 節）。
- R13 表示の小さな点（B 部 5 節）: (a) テストの表に期待する種類（note か help か）を加える。(b) JSON で `waiting` があれば `trace` がなくても書く。(c) ソースの表にないファイルを指す edit が一つでもあれば、その修正案の edits を空にする。(d) BOM 付きのファイルの抜粋で BOM を除き、印の桁を合わせる。
- R14 コード生成の制限の診断（L0101〜L0104）は、定義ごとに一つにまとめる。L 系の診断だけで終わるときも最後の件数の行を書く（C 部 1 節）。
- R15 `case_length` が頼る前提を doc に書き、外れたら `InternalError` を返す確かめを置く。原型ごとの上限 65536 と全体の表の上限 65535 を 02-07 に明記する（振る舞いは変えない）。
