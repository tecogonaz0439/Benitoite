## C1 基本の言語の骨格

### 目的

型の情報を付けた表層の構文、表層の型付け、脱糖の関数、性質 1 の言明という枠組みを固め、基本の言語の主な要素で性質 1 を証明する。性質 2・3 と組み合わせ、「型の付く表層のプログラムの `main` のエフェクトが空なら、実行は IO の事象を伴わない」を表層から言える形にする。後の段階は、この枠組みに要素を足す作業になる。

### 対象

01-12「表層からの脱糖」のうち、次の要素とする。

- 名前とリテラル: 局所の束縛の名前、トップレベルの関数の名前、組み込みの関数の名前、引数のない構成子、リテラル、`-n`、`()`、`(e)`。
- 呼び出し: 構成子の呼び出しと、そのほかの呼び出し。
- 演算子: `⊕_T`、単項の `-`、`not`・`and`・`or`。
- リスト、ラムダ、`if`（`else` あり、`else if`、`else` なし）。
- ブロック: `bind x <- e`、`bind _ <- e`、`shadow`、式文、最後の文の各形。
- `return`: 末尾位置とそうでない位置（`escape` に移す）。
- トップレベルの関数とプログラム。

型は、基本型、代数的データ型、`List`、関数の型、型パラメータに限る。

### 作業

1. 型の情報を付けた表層の構文（`Syntax.lean`）を定める。局所の束縛は de Bruijn の番号、多相な名前は型引数とエフェクト引数、演算子はオペランドの型、ラムダは引数の型とエフェクトを持つ（`decisions.md` の D2）。
2. 表層の型付け（`Typing.lean`）を帰納的な関係として定める。判断は `Δ; Γ; R ⊢ e : A ! ε` の形を出発点とし、文の並びの判断と、末尾位置の判定を持つ。式と文の型は 01-06「式と文の型」の表と「必ず抜ける文」に合わせる。
3. 脱糖（`Desugar.lean`）を、01-12 の表の行ごとの場合を持つ関数として定める。脱糖が作る新しい変数の分だけ、後に続く部分の番号をずらす。
4. 定義と定理の言明だけを書いた時点（証明は `sorry`）で、`decisions.md` の D10 の決定のとおり、Claude Code の Opus 5.5（effort medium）がレビューする（必要なら GPT-6-Astra に相談する）。1〜3 と 5・6 の言明と 7 の脱糖の例を前半の作業 C1a、5・6 の証明と 7 の実行の例を後半の作業 C1b とし、どちらも Codex の GPT-6.1-Sol（high）が実装する。観点は、07-04「レビューと、見つかった誤りの扱い」の四つに、「表層の構文が許すのに脱糖の場合がない要素」と「性質 1 の言明が前提を増やしすぎていないか」を加える。
5. 性質 1（`desugar_typed`）を証明する。言明は、表層のプログラムに型が付き範囲の条件を満たせば、脱糖したプログラムが `Release` の `Program.WellFormed`・`Program.WellTyped`・`Program.EffectsOk` を満たす、という形を出発点にする。
6. 性質 1 と `Release.effect_soundness` を組み合わせた定理（`surface_effect_soundness`）を証明する。
7. `Examples.lean` に、対象の各行について、小さな表層の項の脱糖が 01-12 の表の右辺と一致することを `decide` で確かめる例を置く。脱糖したプログラムを `Release` の実行の関数で実行する例も置く。

### 完了条件

- `formal/` の `lake build` が `sorry` なしで通る。
- `desugar_typed` と `surface_effect_soundness` が使う公理が、Lean の標準の `propext`・`Classical.choice`・`Quot.sound` だけである（`formal/README.md` の `#print axioms` の手順に二つの定理を加えて確かめる）。

### 反映すること

## C3 Rust の脱糖との差分テスト

### 目的

Lean の脱糖と Rust の脱糖が、同じ入力に同じコアの項を作ることを、ゴールデンテストの入力と無作為に生成したプログラムで確かめる（`decisions.md` の D7）。以後の段階は、形式化した範囲を差分テストの範囲に加えることを完了条件にする。

### 作業

1. 交換用の表現（`formal/Benitoite/Exchange/`）を定める。エフェクトの集合を有限の並びで表す型と、Lean の `Eff`・`Ty` へ写す関数を持ち、`ToJson`・`FromJson` を導出する。
2. Rust の側に、テスト専用の書き出しを作る。ゴールデンテストの各入力について、型の情報を付けた表層の構文（AST と名前解決・型検査の表を一つの木にまとめたもの）と、Rust の脱糖が作ったコア IR を、交換用の表現の JSON に書く。`serde` の導出は本番のコードに加えず、テストのコードの中で `serde_json` の値を組み立てる。テストを加えるときは、スキル `test-audit` に従う。
3. Lean の実行ファイル（`formal/DesugarDiff/Main.lean`、`lakefile.toml` の `lean_exe`）を作る。JSON を読み、Lean の脱糖を適用し、Rust のコア IR と比べる。比べる前に、変数の番号の付け方の違いと、02-06「コア IR」が定める表し方の違い（辞書と継続の分類、定数の定義、`eq[T]`・`ne[T]`）を正規化する。形式化の範囲の外の要素を含む入力は、その要素の名前とともに「対象外」として数える。
4. 形式化の検査のスクリプト（`scripts/check-formal.sh`）を作る。`lake build`、書き出しのテスト、差分テストの実行ファイルを順に走らせ、一致・不一致・対象外の数を示す。
5. 差分テストを走らせ、不一致を、Rust の脱糖の誤り、01-12 の規則の読み違い、正規化の不足に分けて記録し、直す。Rust の誤りは処理系を直し、規則の読み違いは Lean の定義と 01-12 の写しを同じ変更で直す。

### 完了条件

- C1・C2 の範囲に収まるゴールデンテストの入力が、すべて一致する。
- 無作為に生成したプログラム（固定の種で 1,000 件を出発点とする）のうち、範囲に収まるものが、すべて一致する。
- 対象外として数えた入力の数と、対象外の要素ごとの内訳を、改造のディレクトリに記録する。
- `scripts/check.sh` が通る（Rust のテストを加えたため）。

### 反映すること

- 07-03「処理系のテスト戦略」: 差分テストの種類に、Lean の脱糖と Rust の脱糖の差分テストを加える。
- 07-04: 「道具と置き場所」に、差分テストと形式化の検査のスクリプトを加える。「前提」の「処理系が 01-12 の規則に従うことは…確かめる」に、脱糖については差分テストで確かめることを加える。

## C7 パターンの拡張

### 仕様の作業（先に行う）

01-12 は、パターンの拡張の意味を「…に移したものと同じ意味を持つ」と文で書き、`⟦·⟧` の規則を持たない（`study.md` の (a) の 3）。処理系はパターンの拡張をコア IR に残す。形式化の前に、次のどちらかを決める。

- (i) 01-12 に、パターンの拡張をコア計算の `match`・`if`・組み込みの関数へ移す `⟦·⟧` の規則を書く。ガードが `false` のときの次の分岐への移動を、残りの分岐の複製か関数で表す必要がある。コア計算は変わらない。
- (ii) コア計算の `match` にパターンの拡張を加え、段階 B の定義と証明（性質 2・3）を広げる。処理系のコア IR の形に近い。

この選択は、C7 を始めるときに、改造のディレクトリで決める（本書では決めない）。

C2 の定義のレビュー（`formal/reviews/2026-10-10-surface-c2-definitions/` の指摘 5）を受け、C7 では次のものも決める。

- 分岐の表し方を、選択肢の並びとガードを持つ形（例: `(alts : List Pattern) (guard : Option Expr) body rest`）に変える。
- 選択肢は同じ名前の変数をパターンの違う位置で束縛してよいので、選択肢ごとの束縛の対応（名前から番号への写像）を型の情報を付けた表層の構文に持たせる（処理系は名前で共有している）。
- ガードの付いた分岐は照合しなかったら次の分岐へ進むので、上の (i) では残りの分岐の複製か関数、(ii) ではコアの `match` の拡張で表す。網羅性（`Exhaustive`）はガードの付いた分岐を数えない形にする。

`decisions.md` の D9 の推奨（形式化した範囲に触れる改造を対象にする）に従う手順である。C1 の完了の時点で AGENTS.md と 07-04 に書く。
