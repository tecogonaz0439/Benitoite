## 背景

関数型スクリプト言語 Benitoite の「コア計算と脱糖」（`docs/design/01-spec/01-12-core-calculus.md`）のうち、コア計算は Lean 4 で形式化し、進行と保存・エフェクトの健全性を証明し終えた（`formal/Benitoite/Release/`）。今回は、性質 1（型の付く表層のプログラムを脱糖した結果は、型の付くコアのプログラムになる）の段階 C1 として、基本の言語の骨格の定義と定理の言明を `formal/Benitoite/Surface/` に書いた。証明はまだ `sorry` である。計画と判断は `docs/2026-10-09-TODO-162-desugar-formalization/`（`plan.md` の「C1 基本の言語の骨格」、`decisions.md` の D2・D5・D6）。

C1 の対象は、01-12「表層からの脱糖」のうち、名前とリテラル、呼び出し、演算子（`⊕_T`、単項の `-`、`not`・`and`・`or`）、リスト、ラムダ、`if` の各形、ブロックの各文、`return`（末尾とそれ以外）、トップレベルの関数とプログラムである。`match`・パターン・パイプ・プレースホルダは C2、制御の構成・型クラスなどは後の段階で扱う。

実装担当に事前に与えた決まり（妥当性もレビューの対象とする）:

- 表層は名前解決と型検査を終えた「型の情報を付けた表層の構文」とする（D2）。表層の型とエフェクトは `Release.Ty`・`Eff` を使う。
- 演算子は、表 `opPrim : 演算子 → 型 → Option (組み込みの関数の名前 × 型引数)` を脱糖と型付けに引数として与え、型は `B.sig` から決める（02-06 と Rust の `table::operator_builtin`・`equality_builtin` に合わせた。組み込みの関数の仮定を増やさないため）。
- 呼ばれる側がトップレベルの関数・組み込みの関数の名前のときは、Rust の `prepare` に合わせて `f[T̄;Ē](x̄)` を直接作る。01-12 の表は `let y ⇐ ⟦e0⟧ in … y(x̄)` と書くので、01-12 の表を Lean に合わせて直す予定である（D6 により形式化した範囲の脱糖は Lean を正とする）。
- 末尾位置は、表層の型付けと脱糖の両方が受け取る（Rust の `Position`、01-08「末尾呼び出し」）。

実装担当の完了の報告は同じディレクトリの `report.md` にある。まずそれを読むこと。

## 観点

07-04「レビューと、見つかった誤りの扱い」の 1・3・4 に、この段階の観点を加える。

1. 脱糖の関数の各場合が、01-12 の表の行（と、上記の決まりで変えた箇所は Rust の脱糖）と一致しているか。番号のずらし（`Comp.rename` の使い方、引数を `let` で束縛した後の番号）に誤りがないか。
2. 表層の型付けの規則が、01-06 の規則を表しているか。01-06 で型が付くのに表層の型付けで型が付かない、またはその逆の場合（余計な制限や緩和）。特に `Exits`（必ず抜ける文）、末尾位置と `return` の型、`and`・`or`・`if` のエフェクト、`E_Sub`・`B_Sub`。
3. 表層の構文が許すのに脱糖の場合がない要素、または脱糖の場合があるのに型付けの規則がない要素。
4. 定理の言明（`desugar_typed`、`surface_effect_soundness`）が性質 1 と、性質 1 と `Release.effect_soundness` の組み合わせを表しているか。前提を増やしすぎていないか（性質を弱めていないか）、結論が弱すぎないか。`hb : B.Assumptions (desugarProgram …)` を置くことの妥当性。
5. このままの定義で定理が偽になる反例（証明できない理由）が見えるか。見えるなら、原因を 01-12 の規則の誤り／書き写しの誤り／表現の都合に分ける。特に、`opPrim` が `B.sig` と合わない場合、`Exits` と関数の結果の型、非末尾の `return` の結果の型、`WellFormed` の条件の足りなさ。
6. 後の段階（C2 の `match`・パターン・パイプ、C4 のハンドラ・`try`、C5 の型クラス）を足すときに、今の枠組み（判断の形、構文の相互帰納、番号のずらし方）が妨げにならないか。
