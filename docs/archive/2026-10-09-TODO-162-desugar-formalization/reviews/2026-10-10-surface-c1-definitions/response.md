# 回答: 脱糖の形式化 C1（定義と言明）のレビュー

レビュー担当: Claude Code の Opus 5.5（effort medium）、2026-10-10。反例の確かめに使ったファイルは `counterexample-1.lean`（`lake env lean` で通る）。

## 指摘 1

- 重さ: 高（`desugar_typed` が偽になる）
- 場所: `Surface/Theorems.lean` の `desugar_typed` の前提。関わる規則は `Typing.lean` の `E_Prim`・`E_Call`・`HasTypes.cons`
- 問題: 表層の型付けは `B.sig` の型に条件を付けないので、継続の型 `.cont …` を返す組み込みの関数をそのまま値として受け渡せる。コアの `V_Var` は継続の型の変数に型を付けない（`a ≠ .cont …`）。反例: `mk : () → Cont(Unit→Unit!{})` と `use : (Cont(Unit→Unit!{})) → Unit` を組み込みの関数とし（`ntys = 0`・`neffs = 0`・純粋）、`f() -> Unit = { use(mk()) }` は表層で型が付き（Lean で検査済み、`tyBody`）、`hwf` も成り立つ。脱糖の `let x ⇐ mk[]() in use[](x)` は、`x` の型が `Ty.Le` で変えられない継続の型なので、`V_Var` も `V_Sub` も使えず型が付かない。`E_Binary` でも、`opPrim` の項目の結果の型が継続の型でありうるので同じことが起きる。`surface_effect_soundness` は `hb.sig_scoped` が同じ条件を与えるので偽にならない。
- 原因の分類: 表現の都合（段階 B のハンドラのためにコアは継続の型の変数を `resume` の外で禁じ、表層はその制限を写していない）
- 直し方の案: `desugar_typed` に `hsig : ∀ b s, B.sig b = some s → s.Scoped` を加える。`Builtins.Assumptions.sig_scoped` と同じ条件なので仮定の種類は増えない。`surface_effect_soundness` では `hb.sig_scoped` から得る。別案の `E_Prim` に `VarsIn` を加える形は規則が重くなる。

## 指摘 2

- 重さ: 中（証明で問題になる）
- 場所: `Typing.lean` の `E_Lam`・`E_ReturnOther`・`B_Bind`
- 問題: 非末尾の `return` の脱糖 `let x ⇐ ⟦e⟧ in escape x` の `V_Var`、引数とリストの要素の変数、`E_Local` から `V_Var` への対応は、型が継続の型を含まないことを要するが、表層の型付けの判断はこれを保証しない。条件は R・Γ・ラムダの引数の型・`B_Bind` の型が `Scoped` であることからだけ得られ、性質 1 の帰納法で `HasType` の導出と `Expr.Scoped` を同時に運ぶ必要がある。
- 原因の分類: 表現の都合
- 直し方の案: (a) 「`HasType C Γ R` の導出のもとで Γ と R が継続の型を含まないなら部分の導出でも成り立つ」という不変条件の補題を立て、`Def` の水準で `hwf` から入れる。(b) `E_Lam`・`B_Bind` に `VarsIn` を前提として加える。C4 で継続の型が表層の Γ に入ることを考えると (a) がよい。

## 指摘 3

- 重さ: 中（後の段階の妨げ）
- 場所: `Desugar.lean` の全体の方式（D2「パイプとプレースホルダは Lean の脱糖の中で 01-02 の規則で展開する」）
- 問題: 今の脱糖は表層の番号を変えずコアの出力の側だけで番号をずらす。01-12 のパイプの行 `let t ⇐ ⟦e1⟧ in ⟦e'⟧`（`e'` は展開した表層の式）を文字どおり書くと、表層の式の上の新しい変数と `Expr.rename`、表層の型付けの弱化の補題が要る。プレースホルダも同じ。
- 原因の分類: 表現の都合
- 直し方の案: C2 では、パイプとプレースホルダを表層の式を作らず直接コアへ移す場合として書く（例: `e1 |> f(a)` を `let t ⇐ ⟦e1⟧ in let x ⇐ ⟦a⟧↑1 in … f(t, x)`）。01-12 の表は D6 に従い Lean に合わせて直す。避けられないなら `Expr.rename` と `HasType.rename` を C2 の作業に明示する。

## 指摘 4

- 重さ: 低
- 場所: `Typing.lean` の `E_ReturnTail`
- 問題: 末尾の `return` の構文の注釈 `resultTy` を `r` と等しくすることを求めている。脱糖は注釈を使わず、01-06 は `return` の型を「その位置で求められる任意の型」とする。E2 で Rust が末尾の `return` に `r` 以外の型を書くと余計に拒む。性質 1 は損なわれない。
- 原因の分類: 表現の都合
- 直し方の案: `E_ReturnTail : HasType (some r) .tail e r ε → HasType (some r) .tail (.returnE a e) r ε` とし、注釈を無視する。

## 指摘 5

- 重さ: 低
- 場所: `Typing.lean` の `E_Sub`・`B_Sub`
- 問題: 01-06「エフェクトの包含」は包含が働く位置を列挙するが、Lean はどの位置でも許す。型注釈のない `bind` に広げた型を付けられる、`uses` のないラムダに本体より大きなエフェクトを付けられる、推論の「最小の集合」を表さない、の点で緩い。広げる方向だけで、コアも `V_Sub`・`C_Sub` を全ての位置で持つので、性質 1 の妨げにならない。
- 原因の分類: 表現の都合
- 直し方の案: 規則は今のまま。01-12 の写しと 07-04 の対応の表に「表層の型付けは 01-06 より緩い包含を許す（性質 1 は緩い側で示すので、より強い）」と書く。

## 指摘 6

- 重さ: 低
- 場所: `Syntax.lean` の `Expr.Exits` の `.paren`
- 問題: 01-06「必ず抜ける文」は `(return e)` を挙げないが、Lean は必ず抜けるものとして扱う。01-08 は括弧を末尾位置について透過的に扱うので自然な拡張だが、01-06 との差になる。
- 原因の分類: 01-06 の規則の不足
- 直し方の案: 01-06 に「括弧で囲んだ式は、中の式が必ず抜けるとき必ず抜ける」を加えるか、01-12 の写しに差を記す。

## 指摘 7

- 重さ: 低
- 場所: `Theorems.lean`、`Typing.lean` の `HasMain` の `MainReturn`
- 問題: `surface_effect_soundness` の証明に `MainReturn` は要らず、前提を余計に強くしている。ほかの前提（`tparams = []`・`neffs = 0`・`params = []`・`d.eff ⊆ ∅`）は要る。`hb : B.Assumptions (desugarProgram …)` は妥当（`Release.effect_soundness` と同じ形で、`Assumptions` が P に依存するのは `delta_typed` などの `HasTypeV P` を通してだけで、表層の側で書ける代わりの条件がない）。
- 原因の分類: その他（言明の選び方）
- 直し方の案: 01-07 の条件を写すことに意味があるなら残して docstring に「健全性には不要」と書く。そうでなければ `HasMain` を実行に要る条件と 01-07 の条件に分ける。

## 指摘 8

- 問題: 01-12 の表を Lean に合わせるときに、名前を直接呼ぶ形（Rust の `prepare` の `Fn`・`BuiltinFn` と一致を確認）、表に行がない最後の文の `{ bind _ <- e }`（Lean も Rust も `let z ⇐ ⟦e⟧ in return ()`）、C1 の対象外とした「引数を持つ構成子を呼び出さずに値として使う」行を落とさないこと。`plan.md` の C2 の対象に三つ目が明記されていない。

## 指摘 9

- 重さ: 低
- 場所: `Typing.lean` の `E_Binary`・`E_Neg`、`Syntax.lean` の `OpPrim`
- 問題: 01-06「演算子の型付け」の型の集まりは、`opPrim` が `none` を返す範囲として表されるだけで、表層の型付けに現れない。定理は任意の `opPrim`・`B` について言うので性質 1 としては強いが、表層の型付けが 01-06 を表すかは `opPrim` の選び方に委ねられる。`ts = Operator.typeArgs` の制限は Rust の `binary` と一致する。
- 原因の分類: 表現の都合
- 直し方の案: C3 の差分テストで Rust の `OPERATORS` 表から作った `opPrim` を使う。01-12 の写しに「演算子の型の集まりは `opPrim` の定義域で表す」と書く。

## 観点ごとの結論

1. 脱糖の各場合と 01-12 の表・Rust の対応、番号のずらし（`letChain`、`boundVars`、`and`/`or`/`if`/`discard`/`seq` の `rename (·+1)`、名前のある `bind` でずらさないこと）は問題なし。末尾位置の受け渡しは 01-08 と Rust の `Position` と一致。表との食い違いは指摘 8。
2. 表層の型付けは、`Exits`、関数とラムダの本体の条件、末尾と非末尾の `return` の型、`and`/`or`/`if` のエフェクトについて 01-06 と同じプログラムを受け入れることを場合分けで確かめた。差は指摘 4・5・6。
3. 構文の全ての要素に脱糖の場合と型付けの規則があり、問題なし（構成子を値として使う形は指摘 8）。
4. 定理の言明は、指摘 1 の前提の不足と指摘 7 を除き妥当。結論の三つは性質 1 として十分。
5. 反例は指摘 1。`opPrim` と `B.sig` が合わない場合は型付けで拒むので偽にならない。
6. 判断の形と相互帰納の構成は C4・C5 を妨げない。妨げになりうるのは指摘 3 と指摘 2。
