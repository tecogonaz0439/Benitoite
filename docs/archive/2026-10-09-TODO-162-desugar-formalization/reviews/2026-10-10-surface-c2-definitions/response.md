# 回答: 脱糖の形式化 C2（定義）のレビュー

レビュー担当: Claude Code の Opus 5.5（effort medium）、2026-10-10。性質 1 を偽にする反例は見つからなかった（Lean の一時ファイルによる確かめはしていない）。

## 観点ごとの結論

1. 脱糖と 01-12・01-02 の一致: 問題なし（パイプの右辺の形ごとの移し先、プレースホルダの評価の時期と順、穴の番号、`upRen` によるパターンの束縛の保護を確かめ、`match_pair_scope_row`・`partial_indirect_row`・`pipe_outer_call_row` の番号を手で検算した）。01-12 の文面の更新は指摘 1。
2. 型付けと 01-05・01-06: パイプ・`match`・`bind p`・`Exits` は問題なし。プレースホルダは指摘 2。
3. 構文と規則の過不足: 文法が誤りとする形を表せる箇所がある（指摘 6）。性質 1 を偽にしない。
4. 反例: 見えない。`PatTy`・`Exhaustive`・`Inhabits` は構成子の表だけで決まり、`D.patternProgram.cons = p.cons = (desugarProgram _ p).cons` なので前提の不足もない。`B_BindPat` の脱糖の `HasTypeArms.nil` が求める `Ty.WF` は `HasBlock.clean` と `Ty.VarsIn.wf` から得られる。証明に要る補題: `PatTy`・`Exhaustive` の構成子の表についての合同、`PatTy` の δ が継続型を含まず範囲内であること（`cd.Scoped` から）、`(desugarArms ..).map Prod.fst = arms.patterns`、`binds holeTypes` の下への弱化。
5. C3 の正規化: 末尾に記す。
6. 後の段階: 指摘 3（C5）と指摘 5（C7）。C4 はプレースホルダの環境が `hideConts` と R を持つので妨げは見えない。

## 指摘

### 1（中）パイプの規則が 01-12 の表の文面と一致しない

- 場所: `Desugar.lean` 66〜84 行、01-12「呼び出し」のパイプの行
- 問題: 01-12 の `let t ⇐ ⟦e1⟧ in ⟦e'⟧` を文字どおり移すと `let x ⇐ return t` ができるが、Lean は作らない。処理系の `pipe` も同じ形で、左単位則により意味は同じ。規則 2 の裸の構成子名を `return C[T̄](t)` に移す形も同じ省略の帰結。01-12 は Lean の写しなので文面を直す必要がある。
- 分類: 表現の都合（処理系に合わせた決定）
- 案: 01-12 のパイプの行に「展開で差し込んだ t は値のまま引数の位置に置く（`let x ⇐ return t` を作らない）」を加え、07-04 の段階 C2 の行に記す。

### 2（低）プレースホルダの型付けが、展開した式の型付けより狭い

- 場所: `Typing.lean` 101〜113 行（`E_PartialCall`・`E_PartialCon`）、212〜214 行（`HasHoleArgs.hole`）
- 問題: 展開した式では `return f(…)` を E_Sub でラムダの戻り値の型 r へ広げられるが、`E_PartialCall` は呼ぶ関数の型を `.fn ps r εcall` に固定する。穴の型 t も、展開した式では受け入れる側の型 t' へ広げられるが、`HasHoleArgs.hole` は t = t' を求める。処理系は戻り値の型に呼び出しの結果の型を使うので実際の入力ではまず起きない。
- 分類: 書き写しの誤り（01-06「展開した式として型を決める」より狭い）
- 案: `E_PartialCall` を `f : .fn ps r0 εcall` と `Ty.Le r0 r` で書き、`HasHoleArgs.hole` を `Ty.Le t a → … (t :: as)` に変える。または狭いままにし 07-04 に明記する。

### 3（中）呼び出しを組み立てる処理の重複

- 場所: `Desugar.lean` 60〜65 行（`.call`）、69〜84 行（`.pipe` の三つの分岐）、87〜93 行（`.partialCall`）
- 問題: `directCallee` の分岐、`letChain` の深さ、番号の計算を四か所で別々に書いている。C2b でそれぞれに補題が要り、C5 ではメソッドの呼び出しと辞書の引数を四か所すべてに足すことになる（処理系は `call(c, inserted)` の一つにまとめている）。
- 分類: 表現の都合
- 案: `callComp (shift : Nat) (inserted : List Val) (f : Expr) (ms : List Comp) : Comp` のような補助の関数一つで、通常の呼び出し・パイプの規則 1・規則 2・プレースホルダの本体を書く。

### 4（中）穴の番号が二つの計数と切り捨ての引き算に依存する

- 場所: `Desugar.lean` 151〜155 行（`.var (n - 1 - i)`）
- 問題: 「通った穴の数 + 残る穴の数 = 総数」の不変条件と切り捨ての処理が要る。ある穴の番号は、それより右の穴の個数に等しい。
- 分類: 表現の都合
- 案: `.hole _ rest => .ret (.var rest.holeTypes.length) :: …` とし、`i` を除く。

### 5（中）C7（パターンの拡張）を足すときの構造の制約

- 場所: `Syntax.lean` 138〜140 行（`Arms.cons pattern body rest`）、`Desugar.lean` 158〜162 行
- 問題: 選択肢は同じ名前の変数を違う位置で束縛してよく、本体を選択肢ごとに複製するときに番号の付け替えが要る（処理系は名前で共有）。ガードは、コアの `match` に照合しなかったら次の分岐へ進む形がない。`Exhaustive` はガード付きの分岐を数えない形にする必要がある。
- 分類: 表現の都合（今の段階の誤りではない）
- 案: C7 の計画に、`Arms.cons` を `(alts : List Pattern) (guard : Option Expr) body rest` に変えること、選択肢ごとの束縛の対応を構文に持たせること、ガードのためにコアの `match` を拡張するかを C7 の定義のレビューで決めることを書く。

### 6（低）文法が誤りとする形を表層の構文で表せる

- 場所: `Syntax.lean` 138〜140 行、188〜190 行（`Arms.Exits .nil => True`）、108 行（`.pipe`）
- 問題: 分岐のない `match`（`Inhabits` の値がない型で型付けでき、`Exits` が真になるので、戻り値の型が Unit でない関数が `return` なしで通る）、空の分岐の本体、括弧のないパイプの右辺の `.pipe`・`.returnE`。どれも性質 1 を偽にしない。
- 分類: 表現の都合
- 案: 構文で禁じる必要はない。コメントか 07-04 に「文法より広い」と記す。分岐のない `match` を禁じるなら `E_Match` に `arms ≠ .nil` を加える。

### 7（低）網羅性の判定が 01-05 より広いことを写しに明記する

- 場所: `Typing.lean` 168〜174 行・257〜268 行
- 問題: 値を作れない構成子の引数を持つ分岐を覆わなくても網羅とみなす、`Character` を列挙し尽くした場合を網羅とみなす、選ばれない分岐の検査を表さない、の三点で広い。`bind p` も同じ広さを受け継ぐ。
- 分類: 表現の都合
- 案: 07-04 の段階 C2 の行に「形式化が広い箇所」として記す。

### 8（低）01-12「型の情報を付けた表層の構文と型付け」の写しの更新

- 問題: `match` の結果の型、穴の型、部分適用の戻り値の型とエフェクト、構成子を値として使う形の引数の型、パターンの束縛の型と `Nontrivial` の区別、パイプの規則 1・2 の型付け、プレースホルダの環境（`hideConts`、R は呼び出しの結果の型）が写しに載っていない。
- 分類: その他（設計書への反映の待ち）
- 案: C2 の反映で加える。

## C3 の差分テストで正規化が要るもの

`let x ⇐ return V` の有無のほかに次の二点。

- `match` の表し方: 処理系のコア IR は行（`MatchRow { pattern, arm }`）と分岐（`MatchArm { vars, guard: None, body }`）に分け、変数を名前で束縛する。Lean は `(Pat × Comp)` の並びでパターンの左から番号を付ける。分岐の番号を並びの位置に揃え、`vars` の順を照合の順に揃えて番号へ写し、構成子の識別（`adt`・`tag` と `ConName`）を対応させ、負の整数のパターンを定数に揃える。決定木へ変換した後（`decision.rs`）の形と比べない。
- ラムダの付随情報: 構成子を値として使う形とプレースホルダが作るラムダは、処理系では `BodyId`・引数の名前・型の注釈を持つ。C1 のラムダと同じ正規化で足りる。

パイプの入れ子の `let`、プレースホルダの穴の再束縛の位置、呼ぶ関数の評価の順、括弧の扱いは、処理系と一致しており正規化は要らない。
