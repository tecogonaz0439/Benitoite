1. **重さ: 中 — 入れ子の `handle` で、型が付く入力を拒否する**

   **場所:** [Check.lean:379](../../../../../formal/Benitoite/Surface/Check.lean:379) の `handleE`、同391行以降の `resume`、同506行以降の `inferClauseTypes`。

   **問題:** 緩い検査で `resume` の引数のエフェクトを式のエフェクトに加えるだけでは、継続ごとの包含条件を保存できない。内側のハンドラがそのエフェクトを処理すると、外側の継続に必要な条件も探索結果から消える。

   `Release.Examples.builtins` の `print : Integer → Unit ! {Console.Write}` を使うと、次の表層構文で再現する。`eInt` は整数リテラルの略記である。

   ```lean
   pr := .call (.primName "print" [] []) (.cons (eInt 8) .nil)

   inner := .handleE (.last (.resume 0 pr))
     (.cons (.prim "print") 1 0 (.last (.resume 0 .unit)) .nil)

   outer := .handleE (.last (eInt 7))
     (.cons (.prim "print") 1 0 (.last inner) .nil)
   ```

   `inner` の本体の `resume 0` は外側の継続を、節の `resume 0` は内側の継続を指す。外側の許容エフェクトを `{Console.Write}`、内側を空集合にすれば、`E_Handle`・`E_Resume` などから `outer : Integer ! {Console.Write}` を導ける。この導出は標準入力から Lean で確認し、`sorryAx` に依存しないことも確認した。一方、検査関数は外側の候補を空集合のまま安定させ、最後の厳密な検査で `effect exceeds the allowed effect` を返す。同じ外側の節を `{Console.Write}` で `checkClauses .strict` に渡すと成功する。

   別の早期拒否もある。内側の**節**から外側の継続を再開する構文では、387行の無条件の `.strict` により、外側の緩い探索中にも未確定の外側エフェクトを厳密に検査してしまう。こちらも具体的な入力で拒否を確認した。

   いずれも成功時の健全性を否定するものではないが、入れ子のハンドラを E2c で検査すると、処理系の誤りと区別すべき偽の不一致になる。既存の `effectfulResume` はハンドラが一段なので、この問題を検出しない。

   **修正案:** 式が返すエフェクトとは別に、各継続について必要な包含条件を収集し、内側で処理したエフェクトを差し引いても条件を失わないようにする。探索中の外側の継続と、検査を確定できる内側の継続も区別する。候補が決まった後の厳密な再検査は維持し、上記の入れ子の例を評価例に加える。387行の `.strict` を単に `mode` に置き換えるだけでは、最初の例は解消しない。

2. **重さ: 中 — `lazy` では、推論結果への `Ty.Le` だけで規則の許す型を受け入れられない**

   **場所:** [Check.lean:375](../../../../../formal/Benitoite/Surface/Check.lean:375) の `lazyE`、同41行の `accept`、[decisions.md:88](../../../../2026-10-10-TODO-162-desugar-formalization-phase3/decisions.md:88) の Q10。

   **問題:** `F₀ = () → Unit ! ∅`、`F₁ = () → Unit ! {Console.Write}` とする。環境が `[some F₀]` のとき、次の式には `Lazy[F₁]` を付けられる。

   ```lean
   .lazyE (.last (.local 0))
   ```

   導出は、本体に `B_Sub` を適用して `F₀` を `F₁` に広げ、その後 `E_Lazy` を適用すればよい。しかし検査関数は `Lazy[F₀]` を返し、期待型 `Lazy[F₁]` への `accept` は失敗する。`Ty.Le` は `Lazy` の内側を広げないためである。規則による導出と検査の失敗を、どちらも Lean で確認した。

   この二つの `Lazy` 型は `Ty.Le` で比較できないため、Q10 の「最小の型は一意に決まり、後で包含を確かめれば足りる」という根拠は、表層構文全体には成立しない。外側の `ite` の結びや束縛の注釈でも同じ制限が現れる。Rust がこの具体例を受理することまでは確認していないため、E2c での発生は未確認だが、宣言的な規則との差として明示する必要がある。

   **修正案:** 期待型が `Lazy[T]` の位置では本体を `T` に対して検査するなど、期待型を構文の内側へ渡す検査を設ける。期待型がない分岐の結びでも同様の問題を扱う必要がある。変更範囲を限定するなら、この制限と E2c での判別方法を明記し、Q10 の最小型についての説明を修正する。`Ty.Le` 自体を再帰的な包含へ広げる変更は、既存規則の変更になるため、この検査関数の修正とは分けるべきである。

3. **重さ: 中 — 構成子の部分適用の否定例が、戻り値の境界の誤りを検出できない**

   **場所:** [CheckExamples.lean:211](../../../../../formal/Benitoite/Surface/CheckExamples.lean:211)。

   **問題:** 一引数の `Option.Some[Integer]` に、`return` を含む式と穴の二引数を渡している。そのため、部分適用の戻り値として構成子の型を使う処理に誤りがあり、最初の `return` を受け入れてしまっても、残った穴が引数個数の不一致で拒否される。現在の `.toBool = false` は、その退行を検出できない。直前の成功例には穴しかなく、`return` が参照する `R` を確かめていない。

   **修正案:** 二引数の構成子を使い、式一つと穴一つで引数個数を合わせる。例えば `Pair[Integer, Integer]` について、非穴の引数に置く `return` の値を `Pair` にした成功例と、`Integer` にした失敗例を対にする。これにより、部分適用の内側の `R` が構成子の戻り値型であることを、引数個数の不一致に隠されずに確認できる。

健全性の言明11件、`Input.Sound`、`ImplNamesComplete` と出力の `AtomsIn` には今回の確認で反例を見つけておらず、E2b は報告7の共通の相互帰納命題と三分割の方針で進めてよいが、E2c へ進む前に上記の偽の拒否への対処方針と評価例を整える必要がある。
