## E1 網羅性の検査

### 01-05 と 02-05 が定める手順

01-05「網羅性の検査」（`docs/design/01-spec/01-05-data-types.md` 202〜211 行）は、最初の文で「対象の型に属するどの値についても照合するパターンが少なくとも一つある」ことを求め、続く箇条で次の判定の規則を置く。

- 誤りの診断に、どのパターンにも照合しない値の形の例を一つ以上示す。
- `Integer`・`String`・`Character` は、リテラルと範囲だけでは網羅とみなさない。`Character` はすべてを列挙しても同じである。
- `Boolean` は `true` と `false`、`Unit` は `()` で網羅できる。`Float`・`Byte`・`Decimal`・`Map`・`Set`・`Bytes` はワイルドカードか変数でしか照合できない。`List[T]` はリストのパターンで長さによって判定する。
- ガードの付いた分岐は覆うものに数えない。コンマで並べた選択肢は、それぞれを別の分岐として数える。

01-05「選ばれない分岐の検査」（227〜249 行）は、分岐 pi が選ばれないことを「pi に照合する値のうち、p1〜p(i−1) のガードの付いていない分岐のどれにも照合しないものが存在しない」と定める。ガードの付いた分岐自身も対象にし、選択肢は別の分岐として数え、選ばれない選択肢が一つでもあれば誤り（`case 1, 1 ->` など）とする。判定は値を作れるかではなく構成子とパターンの形で行い、どの構成子にも値があるものとして扱う。

02-05「本体の後の検査」（`docs/design/02-impl/02-05-typechecker.md` 313〜324 行）は、手順を有用性（usefulness）の判定で定める。

- 有用性: パターンの並び q が行列 P に対して有用であるとは、q に照合し P のどの行にも照合しない値の並びがあることである。
- 行列: 選択肢ごとに一行にし、ガードの付いた分岐の行は加えない。分岐 pi は、前の行（ガードの付いた分岐の行を除く）の行列に対して有用でなければ選ばれない。選択肢は別の行として判定し、「同じ分岐の前の選択肢も前の行に数える」。
- 網羅性: ワイルドカード一つの並びが全行の行列に対して有用なら、網羅していない。判定の途中で反例を作る。必ず照合するパターン: p 一つの行列に対してワイルドカードが有用でなければ、必ず照合する。
- 覆っている分岐の診断（E0602・E0608 の補助の位置）: pj 一つの行列に対して pi が有用でない最初の j があれば pj だけを、なければ p1〜pk に対して有用でない最小の k を求め、その中で pi と重なる分岐をすべて示す。重なりの定義も 02-05 にある。
- 型ごとの構成子: 代数的データ型とレコードは宣言の構成子の全体、`Boolean`・`Unit` は値の全体。`Integer` と `Character` はリテラルと範囲を区間として扱い、列に現れる端で交わらない区間に分け、どのリテラルと範囲にも照合しない値が一つあるものとして扱う。`String` はリテラルを並べても網羅しない。`List[T]` は、列の残りのないパターンの長さの最大 a、残りのあるパターンの前の要素の数の最大 p と後の要素の数の最大 s から m = max(a+1, p+s) を決め、長さ k（0 ≤ k < m）の構成子と、長さ m 以上の構成子（前の p 個と後の s 個を引数に持つ）を置く。そのほかの型は構成子を持たない。

### Lean の `Exhaustive` と照合

`Release/Typing.lean:242-243` は網羅性を値の形で定める。

```lean
def Exhaustive (P : Program) (a : Ty) (ps : List Pat) : Prop :=
  ∀ v, Inhabits P a v → ∃ p ∈ ps, (Pat.matchVal p v).isSome
```

- 値の形 `Inhabits`（214〜239 行）: 定数は `c.type` に属する。構成子の値は、`P.cons c = some cd`、型引数の数が合い、引数が宣言の型に属するとき、データ型 `cd.data` に属する。リストは各要素が属するとき属する。関数の型・型パラメータ・セル・明示遅延・継続・マップ・集合・バイト列・辞書・型パラメータの適用・型構成子には、どの値も属する。`Inhabits` は帰納的な定義なので、有限の値だけを含む。
- 照合 `Pat.matchVal`（`Release/Subst.lean:278-305`）: 定数のパターンは `Const.matches`（`Release/Syntax.lean:145-151`）で比べ、`Integer`・`String`・`Character`・`Boolean`・`Unit` だけが照合する（`Float`・`Byte`・`Decimal` の定数のパターンは何にも照合しない）。範囲は `Integer` か `Character` の両端を含む。リストは 01-05 と同じ意味である。
- 網羅性に数えるパターン: `unguardedPats`（`Release/Subst.lean:354-357`）と `Arms.unguardedPatterns`（`Surface/Syntax.lean:323-326`）は、ガードのない分岐の選択肢をすべて並べる。`C_Match`（`Release/Typing.lean:341-343`）と表層の `E_Match`（`Surface/Typing.lean:272-277`）が使う。表層では、ほかに `B_LastPat`・`B_BindPat`（417〜429 行。一つのパターンの網羅性）、`E_TryResult`・`E_TryOption`（288〜303 行）、`E_RecordUpdate`（139〜148 行）が `Exhaustive` を前提に持つ。
- 照合の実行（`Release/Semantics.lean:141-160`）: 分岐を順に調べ、選択肢は `firstAlt` で左から調べる。ガードが `false` なら、同じ分岐の残りの選択肢を調べずに次の分岐へ進む（155〜156 行）。01-12 の E-GuardF（`docs/design/01-spec/01-12-core-calculus.md` 260・270 行）と同じである。

### 言える定理

手順が判定に使うのは「有用でない」という答えだけなので、次の補題を中心に置く。

- 補題 U（有用でないことの健全性）: 型の並び Ā、行列 P、問い q について、手順が「有用でない」と答えるなら、Ā の値の形に属するどの値の並び v̄ についても、q が v̄ に照合すれば、P のどれかの行が v̄ に照合する。

網羅性と選ばれない分岐は、この補題の系である。

- 系 1（網羅性）: 手順がワイルドカードを全行の行列に対して有用でないと判定すれば、`Exhaustive P a (unguardedPats arms)` が成り立つ。行列の行がガードのない分岐の選択肢と同じだからである。束縛の文の左辺の「必ず照合する」も同じ形で `Exhaustive P a [p]` になる。
- 系 2（選ばれない選択肢）: 手順が分岐 i の選択肢 j を選ばれないと判定すれば、値の形のどの値 v についても、v で照合を始めた実行は分岐 i の選択肢 j を選ばない。「選ぶ」は、前のガードのない分岐の選択肢がどれも照合せず、分岐 i の前の選択肢も照合せず、選択肢 j が照合することとして、`firstAlt` で定める（前のガードの付いた分岐は、ガードが `true` になって先に選ばれうるが、そのときも選択肢 j は選ばれないので、定義から外してよい）。行列に入れる行が、選択肢 j の前に実際に照合を試みて選ばれるものの部分集合であれば、系 2 は補題 U から出る。今の処理系の行（ガードの付いた分岐の中の前の選択肢を入れない）でも、02-05 のもう一つの読み（入れる）でも、この条件を満たす。

補題 U は、型の付いたパターンを前提にしなくても成り立つように手順を書ける。そのためには、手順の中で次の二つを「有用」の側に倒す。

1. 構成子のパターンの引数の数が宣言と合わないとき、その行は照合しないものとして落とし、問いなら照合しうるものとして扱う。
2. 問いがワイルドカードでなく、型の構成子のどれにも特殊化できないとき（型パラメータの型に構成子のパターンを書いた形など）、「有用」と答える。処理系の 385 行の繰り返しは、このとき何も試さずに「有用でない」を返す。型パラメータの型にはどの値も属するので、構成子のパターンに照合する値があり、「有用でない」は補題 U に反する。型の付いた入力では起きない。

逆向き（`Exhaustive` → 手順が網羅と判定）は成り立たない。反例は三種類ある。(i) `Character` のすべての値を覆う範囲（01-05 が意図して網羅とみなさない）。(ii) 値を作れない型の構成子を引数に持つ構成子（`data T X(L) Y end data` で `L` の値がないとき、`case T.Y` だけで `Exhaustive` は成り立つが、手順は `T.X(_)` を反例にする。01-05 の「どの構成子にも値があるものとして扱う」）。(iii) ガードの付いた分岐の中の前の選択肢（今の処理系の行の作り方のとき）。`Integer` は Lean の `Int` に上限がないので、全体を覆う範囲は書けず、反例にならない。反例の正しさ（手順が有用と答えたとき、反例の形の値が実際にどの行にも照合しない）は、(i)(ii) のために値の形の上では成り立たない。成り立たせるには、構成子ごとに値があり、`Integer`・`Character` に「どのリテラルにも照合しない値」が一つあるとする広げた値の形を定める必要がある。

### 型の情報と、Lean に足すもの

- データ型の構成子の一覧: 手順は型 `.data d ts` の構成子をすべて並べる。`Release.Program.cons`（`Release/Syntax.lean:323` の `Program`）と `Surface.Declarations.cons`（`Surface/Syntax.lean:391-397`）は構成子の名前から宣言を引く関数なので、データ型から構成子を数え上げられない。`ctors : DataName → List ConName` を手順の引数にし、条件「`P.cons c = some cd` なら `c ∈ ctors cd.data`」を補題 U の前提に置けば、`Release` と `Surface` の構造を変えずに済む。一覧に余分な名前があっても、手順が有用と答える場合が増えるだけで、補題 U は保たれる。
- 構成子の引数の型: `cd.args.map (Ty.subst ts [])`。`Inhabits.con` と同じである。
- `Character`: Lean の `Char` は Unicode のスカラー値で、サロゲートを含まない。処理系はサロゲートの範囲だけの区間を構成子から外す（`patterns.rs:228`）。Lean の手順も外さないと、`'a'..'\u{D7FF}'` と `'\u{E000}'..'\u{10FFFF}'` の後の `'a'..'\u{10FFFF}'` で答えが食い違う（処理系は選ばれないと判定し、外さない手順は有用と判定する）。外す場合の健全性は、サロゲートの範囲に `Char` がないことから出る。
- `Integer`: 処理系は `i64` を `i128` に広げて区間の端を計算する。Lean は `Int` で同じ計算ができ、溢れの扱いは要らない。
- 型パラメータ・関数の型など: `Other` だけを構成子にする。ワイルドカードの問いは、ワイルドカードの行がなければ有用になり、値の形と合う。
- 停止: 処理系の再帰は、行列のワイルドカードでない節の数と列の数の辞書式の順で減る（列がすべてワイルドカードの場合は列が一つ減り、特殊化の場合はワイルドカードでない節が一つ以上消える）（推測。証明していない）。Lean では、この順で停止を示すか、燃料を持たせて尽きたら「有用」と答えるかを選ぶ。燃料の方式でも補題 U は成り立つ。

### 文書の食い違い

1. 01-05「網羅性の検査」の最初の文は意味の定義（どの値にも照合するパターンがある）で、続く箇条の `Character` の規則（すべてを列挙しても網羅とみなさない）は、この定義と矛盾する。全体を列挙した `match` は最初の文を満たすからである。意味の定義（`Exhaustive`）と、保守的な判定の規則を分けて書く必要がある。
2. 02-05 の有用性の定義（「q に照合し P のどの行にも照合しない値の並びが存在する」）は意味の定義だが、続く型ごとの規則（`Integer`・`Character` に残りの値を一つ置く、どの構成子にも値があるとする）は、この定義どおりの値では成り立たない。有用性を、広げた値の形の上で定義し直すか、「次の規則で判定する」と書き、意味の定義と分ける必要がある。
3. 02-05 は、同じ段落で「ガードの付いた分岐の行は行列に加えない」と「同じ分岐の前の選択肢も前の行に数える」を述べ、ガードの付いた分岐の中の選択肢について二つが食い違う（TODO-178 (b)）。01-05 の「コンマで並べた選択肢は、それぞれを別の分岐として数える」を文字どおりに読むと、ガードの付いた分岐の各選択肢を別のガードの付いた分岐として数えることになり、処理系と同じ（数えない）側になる。
4. 01-12 の 187 行は、コア計算の C-Match の網羅性の定義を 01-05「網羅性の検査」に従うとするが、同じ章の 462 行と 07-04 の対応の表（段階 A と段階 C の行）は、形式化の網羅性を値の形で定め、01-05 の手順より広いとする。187 行を値の形の定義に直す必要がある。

Rust 言語との違いを一つ記す。Rust の言語リファレンスは、`|` で並べたパターンとガードについて、ガードが `false` なら同じ分岐の次の選択肢を調べ、ガードが複数回実行されうると定める（The Rust Reference「Match expressions」の例）。Benitoite（01-12 の E-GuardF）は同じ分岐の残りの選択肢を調べずに次の分岐へ進み、OCaml のマニュアルの or パターンとガードの説明（照合した左の選択肢の束縛でガードを調べ、`false` なら節を選ばない）と同じである。Rust の規則なら、ガードの付いた分岐の中の前の選択肢は後の選択肢を覆わない。Benitoite の規則では覆う。

### 検査の関数を書くときの難しさ

1. エフェクトの表現: 表層の構文と型の `Eff` は関数（`Atom → Bool`、`Release/Syntax.lean` の `Eff`）なので、包含 `Eff.Sub`（すべての原子についての全称）を一般には判定できず、`Ty` も `DecidableEq` を持たない。交換形式（`Exchange/Syntax.lean`）は原子のリストで持ち、`Eff.toRelease`（`Exchange/Convert.lean:10`）で関数にする。検査の関数を表層の構文の上に書くなら、入力の全原子の集合を引数に取り、その上で包含と等しさを判定し、「表層の式に現れるエフェクトがその集合の外の原子を含まない」ことを健全性の定理の前提に置く。この前提は、変換が作った式について成り立つが、変換は `partial def`（51・117・193 行など）なので Lean では証明できない（信頼する）。交換形式の上に書く案は、変換を全域の関数に書き直さない限り、定理が変換をまたげない。
2. エフェクト変数の置き換え: `fnTy`（`Release/Typing.lean:76-77`）は `Ty.subst ts es` で `Eff.substRho` を使う。有限の原子の集合の上で判定するには、置き換えた結果がやはりその集合（とエフェクトの引数の原子）の中に収まることの補題が要る。
3. 包含の規則: `E_Sub`・`B_Sub`（`Surface/Typing.lean:326-328`・430〜432 行）は型の最も外側の関数の型のエフェクトだけを広げる（`Ty.Le`）。検査の関数は最小の型とエフェクトを求め、規則が型を決める位置（引数、注釈、分岐の結果）で `Ty.Le` と `Eff.Sub` を確かめれば足りる。`ite` は結果の型の注釈を持たないので、二つのブロックの型の結び（最も外側の関数のエフェクトの和）を求める。
4. `handle` のエフェクト: `E_Handle`（316〜320 行）の ε は注釈を持たず、節の本体の環境の継続の型 `.cont sg.ret t ε` の中にも現れる。`resume` は ε を結果のエフェクトにするので、ε は「本体のエフェクトから処理する操作を除いたもの」と「節の本体のエフェクト」の和の最小の不動点として求める（原子の集合が有限なので、繰り返しで止まる）。
5. 網羅性: `Exhaustive` は値についての全称で、判定できない。検査の関数は E1 の手順で判定し、系 1 で `Exhaustive` を得る。このため、データ型の構成子の一覧（E1 と同じ）が書き出しに要る。
6. 組み込みの関数: 表層の型付けは `Builtins` を引数に取る（`B.sig`・`B.sat`・`PrimSig.admits`・`B.isResource`・`B.effects`。`Release/Typing.lean:43-74`）。性質 1 は任意の `B` について証明してあるが、E2 では処理系の組み込みの関数の表から具体的な `B` を作る必要がある。`sat`（等値・鍵の制約）と `admits`（演算子の型の集まり）は `Prop` なので、判定できる形（01-06 の等値の型・鍵の型の規則の写し）で書く。表そのもの（名前・型・制約・エフェクト）は書き出しに足す。
7. 既定の型と R: 型検査が決めなかった型変数を既定の型（`Unit`）にした箇所のうち、表層の型付けが注釈どおりの型を求める位置で食い違う。分かっているのは f04 の末尾位置の `match` である。`insertByCount`（`testdata/syntax/f04_list_spread.bnt` 2〜9 行）は、分岐がすべて `return` で抜ける `match` を本体の最後に置く。`E_Match` の結論の型は注釈の `Unit` そのもので、末尾位置の `return` は R（`List[...]`）の型しか持たない（`E_ReturnTail`）ので、分岐の型が `Unit` に合わず、本体のブロックも `d.ret` に合わない。注釈を R に置き換えれば型が付く。ほかの位置（末尾でない `return` の注釈、空のリストの要素の型）は、表層の型付けが任意の正しい型を許すので食い違わない（推測）。
8. TODO-190: ガードの中の外側の `resume` は、表層の型付けで型が付かない（ガードを `hideConts` の環境で検査する）。処理系は受け付けるので、E2 は既知の差として数える必要がある（脱糖の差分テストの `knownDifferences` と同じ扱い）。
9. 交換形式の付随情報: 表層の構文はほとんどの型の情報を持つ（関数の名前の型引数、ラムダの引数・戻り値・エフェクト、`match` の結果の型、プレースホルダの呼び出しの戻り値とエフェクト、辞書の根拠）。E2 のために新しく要るのは、組み込みの関数の表と構成子の一覧と原子の集合である（推測。照合する式の型は検査の関数が求められる）。
