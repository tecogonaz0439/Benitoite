## 1. プレースホルダの引数の中の `return`・`try`・`resume`

### 今のコード

型検査（`typeck/generate.rs` の `call`）は、プレースホルダを含む呼び出しで、エフェクトの受け先だけを新しい変数に差し替える（268〜275 行）。呼ばれる関数の式（274 行）とプレースホルダでない引数（279〜290 行）は、外側の `ctx.ret`（戻り値の型）と `ctx.clauses`（節の情報）のまま検査する。展開後のラムダの戻り値の型 `ret` は、引数を検査した後の 292 行で作る。`return` は `ctx.ret` で検査し（1105〜1119 行の `return_expr`）、`try` も `ctx.ret` を使い（`typeck/effects/mod.rs:39-54`）、`resume` は `ctx.clauses.last()` を使う（同 56〜68 行。節がなければ `debug_assert!(false)`）。ラムダの中の `resume` を禁じるのは構文解析器で、ラムダ（`syntax/parser/exprs.rs:850-851`）と `lazy`（`syntax/parser/effects.rs:378-379`）の本体を `ClauseContext::Blocked` にし、`check_resume`（同 268〜277 行）が E0509 を出す。プレースホルダの引数（`syntax/parser/exprs.rs:465-480` の `push_arg`）は対象外である。引数を読み終えるまで `_` があるかは分からないので、構文解析器は先に読んだ引数を Blocked にできない。

脱糖（`ir/desugar/exprs.rs:314-360` の `placeholder`）は、呼ばれる関数とプレースホルダでない引数を展開したラムダの本体に置くが、ラムダの脱糖（同 499〜503 行）と違い、継続（`self.conts`）と戻り値の型（`self.return_ty`）を退避しない。コア IR の検査器（`ir/check.rs` の V-Lam、446 行）はラムダの本体で継続を外すが、検査器を呼ぶのはテストの補助（`ir/desugar.rs:372`）だけで、本番の経路は呼ばない。

### 直し方の案

型検査で、呼ばれる関数とプレースホルダでない引数を、ラムダの本体と同じ環境で検査する。すなわち、展開後のラムダの戻り値の型 `ret` を引数の検査より前に作り、その間だけ `ctx.ret` を `Some(ret)` にし、`ctx.clauses` を空にする（外側の節を隠す）。引数の中に書いた `handle` は自分の節を積むので、その節の中の `resume` は今のまま受け付ける。`resume` を検査するときに節がなければ E0509 を出す（今の `debug_assert!(false)` を置き換える）。これは Lean の表層の型付けの `partialCall`（`Benitoite/Surface/Typing.lean:186-191`。呼ばれる関数とプレースホルダでない引数を `hideConts Γ` と `some r` で検査する）と同じ形である。`return_annotation`（戻り値の型注釈の位置）もラムダと同じく外す。

脱糖の `placeholder` でも、ラムダと同じく `self.conts` を空にし、`self.return_ty` を展開後のラムダの戻り値の型にする。型検査を通ったプログラムでは引数の中に外側の継続を指す `resume` は現れないので、現れたら `InternalError` にする。

構文解析器でプレースホルダの引数の `resume` を報告する案もある（呼び出しの引数を読み終えた後に、`_` があれば引数の式を辿って `resume` を探す）。`return` の型の直しは型検査でしかできないので、`resume` も型検査で報告するほうが変える箇所が一つにまとまる（`decisions.md` の Q2）。

## 2. 誤りのある型の別名

`typeck/decls.rs:286-320` の別名の展開は、引数の数の誤り（292〜299 行）や循環のときに `unit()` を返す。別名の本体の型の誤り（`self.ty` の中で報告した誤り）があっても、展開した型（`Unit` に置き換わった部分を含む）をそのままキャッシュ `alias_types` に入れる（303〜308 行、731〜736 行）。invalid（誤りのある宣言の集まり）に入るのは別名の宣言自身だけである（790 行）。

再現: `type Bad = Option[Integer, Integer]` と `function f(x: Bad) -> Integer` を書き、`f(Option.Some(1))` を呼ぶと、E0410（`Option` の型引数の数）に加えて、呼び出しの位置に E0401 が出る。後者は前者から派生した誤りで、02-05「誤りの報告と検査の継続」の「宣言の検査で誤りを報告した宣言は、その誤りの部分を誤りの型にして、後の手順を続ける」に合わない。

直し方の案: 本体に誤りのあった別名を記録し（invalid の印か、キャッシュに誤りの印を持たせる）、その別名を展開した側を誤りの型にする。宣言の型（`Ty`）は誤りの型を持たないので、関数の引数の型に使ったときは、シグネチャを invalid にして本体と呼び出しの検査で誤りを重ねないようにするか、推論の型（`ITy::Error`）へ移すときに誤りにする。どちらの形にするかは実装の作業で決める（仕様の判断は要らない）。受け入れテストは、上の例で E0410 だけが出ること。

## 5. 標準ライブラリの型クラスの孤立した実装（E0701・E0702）

`typeck/traits/impls.rs:70-100` は、孤立した実装に E0701 を出した後も、その実装を重なりの表 `seen` に登録し、重なりを検査する。単体テスト（`typeck/traits/tests.rs:478-483`）は `[E0701, E0702]` を正として固定している。

再現: `import Benitoite.Trait` と `implement Trait.Show[Integer] … end implement` を書いて `check` すると、CLI は次を出し、終了状態 3 で終わる。

```text
internal error: internal compiler error
   = note: the error occurred in the check stage
   = note: the panic occurred in the compiler thread
   = note: error[E0702]: `Show` is implemented more than once for `Integer`
  --> <benitoite>/Trait.bnt:74:1
```

E0701 は表示されない。CLI の `report_check`（`cli/mod.rs:410-427`）が、主な位置が prelude（標準ライブラリを含む）のソースにある誤りを見つけると（`prelude_error`、399〜409 行）、処理系の不具合として報告するためである。E0702 の主な位置は後に処理した実装（標準ライブラリの実装）に付く。利用者の誤りが処理系の不具合に見えるので、TODO-178 の記述（E0702 が余分に出る）より重い。

直し方の案: E0701 を出した実装は重なりの検査に加えない（`seen` に登録せず、比べない）。単体テストの期待を `[E0701]` に直し、CLI の経路で E0701 だけが出て終了状態 2 になる受け入れテストを加える。02-05「誤りの報告と検査の継続」の「誤りのある実装は、型クラスと型構成子の組の表に加えたうえで、その実装を引いた制約について誤りを重ねて報告しない」は、制約を解く表の話であり、重なりの検査とは別である。孤立した実装を重なりの検査に加えないことを 02-05 の「型クラスと実装」の節に一文で書く。CLI の `prelude_error` は、標準ライブラリの誤りを見つける安全網として残す。

## 9. 組み込みの関数の原型の共有

## 10. 定数の評価器の値の大きさ
