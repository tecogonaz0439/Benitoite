# 調査 B: WIT の型を使った値の受け渡し

2026-10-13。調査と設計の案であり、設計者の決定ではない。処理系の実装と設計書は変更していない。Q1〜Q3 の答えを前提とし、型の名前・演算・リテラルは調査 A に委ねる。

ホストは Benitoite、ゲストは呼び出す Wasm のライブラリを指す。ゲストのバイト単位の記憶領域を線形メモリ（linear memory）、呼び出す側と呼ばれる側の間で値を並べる規則を ABI（application binary interface）と呼ぶ。値をメモリやコアの数の形へ書く操作が lowering、そこから型の付いた値として読む操作が lifting である。Rust の型ごとに汎用の処理から機械語を作ることを具体化（monomorphization）と呼ぶ。

最大 RSS（resident set size）は、プロセスが実際のメモリに保持した領域の最大量である。Wasm の命令の実行量を制限する燃料（fuel）と、ゲストからホストへ作る値の量を制限する hostcall fuel は別の予算である。

## 1. 調査の結果と推す案

Wasmtime 49.0.2 の通常の公開 API には、コンポーネントの型を受け取り、任意のホスト表現からそのコンポーネントのメモリへ書く変換器を登録する仕組みがない。`ComponentType`・`Lower`・`Lift` を自前で実装するには `unsafe impl` と互換性を保証しない API が要る。コンポーネントのインスタンスから内部のコア関数やメモリを取得する公開 API もない。したがって、当初の「一つの Rust の変換器でゲストのメモリへ直接書く」方式を、そのまま現在の規約の下で実現することはできない。根拠は第 2 節に示す。

一方、型に応じた Wasm の補助コードを生成し、元のコンポーネントと組み合わせる方式は実現できた。補助コードとホストの間だけを `list<u8>` に揃え、補助コードから元の WIT 関数を Component Model の規則で呼ぶ。ホストには型を読んでバイト列を作る変換器を一つ置ける。Rust の型の組み合わせごとの具体化を増やさず、利用者の定義するレコードにも対応する設計にできる。ただし、元のゲストへ直接書く方式ではなく、補助コードのメモリを経る方式である。

推す案は、通常の値にこの補助コード方式を段階的に導入し、既存の型付きの速い経路と外部の型を含む動的経路を併用することである。短い試作では、3 欄のレコード 10 万個の往復が動的経路の 19.719 ms・最大 RSS 112.72 MiB から、補助コード方式の 7.974 ms・57.11 MiB になった。戻り値の受け渡しの予算も 18,100,000 B から 3,200,008 B になった。しかし、追加の Wasm 命令・メモリ・生成器の実装を要する。これを全型の完成実装とみなして既存の経路を削除する根拠は、今回の試作にはない。

### 2.1 自前の `ComponentType`・`Lower`・`Lift`

三つの trait は公開されているが、いずれも `unsafe trait` である。自前の実装は `unsafe impl` になる。型付きの受け渡しに使う内部の型は `component::__internal` から参照できるので、「外部クレートから一切使えない」ことが問題ではない。同モジュールは API の互換性の保証に含めないと明記されている。現規約の例外を作らずに採る案ではない。

出典: `W/src/runtime/component/func/typed.rs:498–545,573–668`（[trait と関連型](https://github.com/bytecodealliance/wasmtime/blob/v49.0.2/crates/wasmtime/src/runtime/component/func/typed.rs#L498)）、`W/src/runtime/component/mod.rs:153–176`（[互換性の保証の対象外](https://github.com/bytecodealliance/wasmtime/blob/v49.0.2/crates/wasmtime/src/runtime/component/mod.rs#L153)）。

`typecheck` は実行時の `InterfaceType` と型の表を受け取るので、実際のレコードの欄などを調べることはできる。しかし、`self` を受け取らず、ホストの値や呼び出しごとの変換表は渡されない。そのうえ、平らにした引数の形（flat representation）、メモリ内の大きさ・整列条件（alignment）は、関連型 `Lower` と定数 `ABI` で Rust の型ごとに決まる。型付きの呼び出しはその個数で、引数や結果をメモリ経由にするかを選ぶ。

したがって、`typecheck` でどの型でも許可するだけでは正しくならない。例えば、`bool` と文字列と 3 欄のレコードでは、平らにした値の個数もメモリ内の大きさも違う。リストの根だけならポインタと長さに固定できるが、要素型の動的な大きさを扱う実装や、ほかの根の形への対応が別に要る。すべての型の ABI を型検査の後に自由に差し替える登録口はない。

出典: `W/src/runtime/component/func/typed.rs:195–245,499–545`（[型付きの呼び出しの分岐](https://github.com/bytecodealliance/wasmtime/blob/v49.0.2/crates/wasmtime/src/runtime/component/func/typed.rs#L195)）。これはソースからの設計上の帰結であり、`unsafe impl` の試作は行っていない。

### 2.2 コア関数とメモリを直接操作する案

コンポーネントの `Instance::get_export` が返すのは、書き出しの種類と検索用の番号である。`get_module` は書き出されたコアモジュールを返すが、内部で既に起動したコアインスタンスを返さない。別にそのモジュールを起動しても、元のコンポーネントのメモリ・状態・resource の表にはならない。内部のコア項目を解決する `lookup_vmdef` とメモリの参照を得る関数は `pub(crate)` である。

出典: `W/src/runtime/component/instance.rs:201–239,289–317,449–470`（[書き出しと内部の参照](https://github.com/bytecodealliance/wasmtime/blob/v49.0.2/crates/wasmtime/src/runtime/component/instance.rs#L201)）、`W/src/runtime/component/types.rs:1221`（[ComponentItem](https://github.com/bytecodealliance/wasmtime/blob/v49.0.2/crates/wasmtime/src/runtime/component/types.rs#L1221)）。

独立したコアモジュールなら、安全な `Instance::get_func`・`get_memory`、`Memory::read`・`write`・`data_mut`、`Func::call` を使える。生のポインタを読む必要はない。しかし、任意のコンポーネントをその方式で扱うには、内部の複数のモジュールの組み立て、文字列の符号化、引数・戻り値の配置、再入の制限、post-return、resource の所有と借用を自分で再実装しなければならない。コアの Wasm のメモリ隔離を使うことと、Component Model の契約を守ることは別である。

出典: `W/src/runtime/instance.rs:484,542`（[コア Instance](https://github.com/bytecodealliance/wasmtime/blob/v49.0.2/crates/wasmtime/src/runtime/instance.rs#L484)）、`W/src/runtime/memory.rs:354–449`（[安全なメモリ操作](https://github.com/bytecodealliance/wasmtime/blob/v49.0.2/crates/wasmtime/src/runtime/memory.rs#L354)）、`W/src/runtime/func.rs:961`（[コア Func::call](https://github.com/bytecodealliance/wasmtime/blob/v49.0.2/crates/wasmtime/src/runtime/func.rs#L961)）。

この案は推さない。既存の `@external` が受け付けるコンポーネントを一般に扱えず、ABI 違反の検出と外部の型の管理まで新しく受け持つためである。ゲストに独自のコア関数の書き出しを要求する案も同じ理由で推さない。

### 2.3 `Val` の再利用

引数の `Val::List`・`Val::Record` が持つ並びと、欄名・文字列の領域は、処理系が所有しているので再利用できる。呼び出し中の引数は `&[Val]` として借りられる。レコードの欄名を初回だけ作り、その後は位置で値を更新すれば、呼び出しごとの欄名の確保を省ける。ただし、引数の構造や長さが変わる場合、不要な子の値を捨てる処理と保持領域の上限も要る。

戻り値では、渡した `results` の初期値は無視され、Wasmtime が新しい `Val` を作って上書きする。外側の結果用の並びだけを再利用しても、レコードの欄名やリストの内部領域を再利用することにはならない。動的な値の一つの大きさと hostcall fuel の量も変わらない。

出典: `W/src/runtime/component/values.rs:72–95,273–285,1019–1049`（[動的な値と確保](https://github.com/bytecodealliance/wasmtime/blob/v49.0.2/crates/wasmtime/src/runtime/component/values.rs#L72)）、`W/src/runtime/component/func.rs:229–237,380–385`（[戻り値の上書き](https://github.com/bytecodealliance/wasmtime/blob/v49.0.2/crates/wasmtime/src/runtime/component/func.rs#L229)）。

今回の再利用の試作は、同じ形・同じ長さの引数を毎回更新する有利な条件である。それでも最大 RSS を減らせず、Boolean のリストでは準備も速くならなかった。大きな領域を呼び出しの後も保持する費用があるので、全呼び出しの既定の方式には推さない。

### 2.4 型付きの呼び出しの追加と Wasmtime への提案

既知の型に `bindgen!` や derive を使うことはできる。しかし、処理系のビルドの後に分かるレコードの欄を Rust の型として具体化できない。`Boolean` や `String` のリストだけを追加しても、引数の組み合わせの増大と利用者の型への対応という二つの問題は残る。新しい数の幅ごとに既存の組み合わせ表を広げる案は推さない。

戻り値の `WasmList<T>` を使い、公開の `get` で要素を順に読む方法もある。しかし、要素には `T: Lift` が必要で、ビルド後に分かる任意のレコードの型を読む解決にはならない。既知の型の中間の並びを減らす候補としては別に検討できるが、今回この方法は試していない（`W/src/runtime/component/func/typed.rs:1749–1819`、[WasmList の要素の読み出し](https://github.com/bytecodealliance/wasmtime/blob/v49.0.2/crates/wasmtime/src/runtime/component/func/typed.rs#L1749)）。

上流へ提案するなら、型と値を別に持ち、名前を値ごとに所有しない動的な表現、または型を読んで値を順に書く・読む安全な API が候補になる。後者では、予算・文字列の符号化・resource・post-return・ゲストを呼ぶ間の再入の制限を Wasmtime が保持する設計を求める。現在の `Val::lift`・`load` は `pub(crate)` であり、戻り値の構築先を差し替える公開の登録口ではない（`W/src/runtime/component/values.rs:99,243`）。提案の採用も時期も未確認であり、3a の完了をそれに依存させない。今回、上流への送信は行っていない。

## 3. バイト列を受ける補助コードの方式

### 3.1 呼び出しの構成

ホストの共通の呼び出し型を `TypedFunc<(&[u8],), (Vec<u8>,)>` とし、次の手順で値を渡す。

1. 照合済みの型の表から、値の大きさ・整列条件・欄の位置・場合の番号を求める。ホストは言語の値を辿り、ポインタをバイト列の先頭からの位置に置き換えた表現を作る。
2. `list<u8>` として補助コードのメモリへ渡す。補助コードは相対位置をメモリ内の位置へ直し、元の関数の引数の形を作る。
3. 元のコンポーネントの関数を `canon lower` でコア関数に変え、補助コードから呼ぶ。元のゲストの `realloc`・文字列の符号化・ABI の検査・post-return は Component Model の実行系が処理する。
4. 結果が補助コードのメモリへ戻ったら、散らばった文字列やリストを一つのバイト列へ詰め直す。参照先を先頭からの位置に直して、`list<u8>` としてホストへ返す。
5. ホストは型の表を使ってバイト列を読み、言語の値を作る。要素数・長さ・範囲・UTF-8 を、言語の値を確保する前に検査する。

ホストの変換器は型を読む一つの処理にできるが、Wasm の補助コードは型に応じて生成する。型ごとの仕事そのものが消えるのではない。処理系の実行ファイルへ Rust の具体化を全組み合わせ分入れる方式から、読み込んだ契約に必要な Wasm のコードを作る方式へ変えるのである。

試作は、元のコンポーネントを入れ子に置き、補助用のメモリを持つモジュールと呼び出し用のモジュールを追加した。元の関数の型はそのまま保つ。コンポーネントの合成と `Component::from_binary`・`Linker::instantiate`・`get_typed_func`・`TypedFunc::call` だけを使い、Rust の試作に `#![forbid(unsafe_code)]` を付けた。外部の取り込みを持たないゲストに、新しい外部権限を加える必要はなかった。

```mermaid
flowchart LR
    H[Benitoite の値と型の表] -->|共通の変換器| B[相対位置を使うバイト列]
    B -->|型付きの list u8| A[生成した補助コードのメモリ]
    A -->|canon lower で元の WIT 関数を呼ぶ| G[元のゲストの値とメモリ]
    G -->|Component Model の検査と変換| A
    A -->|詰め直した list u8| B
    B -->|共通の変換器| H
```

### 3.2 バイト列の形と検査の分担

試作では、32 bit のポインタを使うメモリ内の標準の並べ方（canonical ABI）に合わせ、先頭 8 バイトに根のリストの位置と要素数を置いた。文字列・リストは位置と長さ、レコードは欄の宣言順と整列条件に従う。欄名は型の表だけに保存し、値ごとには入れない。

この並べ方と、平らにした結果が一個に収まらないときの間接の戻り値の規則は、[Canonical ABI の Alignment・Element Size・Flattening](https://github.com/WebAssembly/component-model/blob/main/design/mvp/CanonicalABI.md#alignment)を確認した（閲覧日 2026-10-13。特に `alignment`・`elem_size_record`・`flatten_functype`）。試作の元の関数はリストを返すので、`canon lower` で得るコア関数は引数の位置・長さに加えて結果を書き込む位置を受け取る。Wasmtime 49.0.2 でもこの形を検証・実行できた。

ホストとのバイト列の形式は WIT の契約そのものではない。元の WIT 契約の照合は今の位置で行い、補助コードの `list<u8>` を照合できたことだけで元の契約を通してはならない。補助コードは型から生成し、任意のユーザー入力のコードとして扱わない。生成したバイナリも Wasmtime のコンポーネントの検証に通す。

戻り値の ABI 違反は、元のゲストから補助コードへ移す段階で Component Model が検出する。それとは別に、補助コードの不具合やバイト列の読み方の不一致を検出する検査がホスト側に要る。`offset + size`・`count × element_size` の溢れ、範囲外の参照、重複参照による展開量の増大、要素数と文字列の長さを、制限付きの作業列で検査する。試作の Rust の再帰・`unwrap`・入力の形が同じという仮定は、本体へ移さない。

### 3.3 性能と実装の費用

補助コード方式はコピーをなくす方式ではない。ホストの連続したバイト列、補助コードの入力、元のゲストの値、補助コードの結果、詰め直した結果が必要になる。Wasmtime がコンポーネント間の変換を最適化することはありうるが、今回の測定からコピーの正確な回数は求めていない。ホストで要素ごとの `Val` と欄名を作らない利点と、追加の Wasm の走査の費用を比較して選ぶ方式である。

実装には、バイナリの組み立て、型から補助コードを生成する処理、両方向のバイト列変換、補助用の確保と解放、制限の検査が要る。試作は WAT を Python で生成したが、本体ではバイナリを生成する案を推す。オフラインのレジストリには `wasm-encoder` 0.258.3・0.259.0・0.261.0 があり、今回は新しい依存の取得をしていない。直接の依存にどの版を加えるかは、Wasmtime と本体の依存を揃える実装プランで決める。

元のゲストのメモリに加えて補助用のメモリを一つ、コアインスタンスを二つ使う。現在の Store 全体の 64 MiB と個数 16 の制限に、この分も含める。自動的に上限を広げる案は推さない。特に大きな `Bytes` は、今の型付きの経路より先にメモリの上限へ達しうる。

純粋な外部の呼び出しでインスタンスを毎回捨てる規則はそのまま使える。状態を持つインスタンスに補助コードを付ける場合は、元のゲストの状態を残し、補助コードの一時領域だけを呼び出しの後に再利用する必要がある。試作の単純な確保器は解放せず、呼び出しごとに Store を捨てる。状態を持つ場合の一時領域の再利用は未確認である。

ビルドは `cargo build --offline --release`、target は `P/target` に限った。Wasmtime の機能は本体と同じ `runtime`・`component-model`・`std`・`cranelift`、Wasm の燃料は有効、上限 10^10、Wasm のスタックは 512 KiB とした。試作の release 設定は `debug = 0` と既定の最適化で、LTO は使っていない。本体の release の `overflow-checks = true` は試作に指定していないため、統合後の速度とバイナリの大きさは別に確認する。

これは、設計者が指定した各数回の短い調査である。電源とほかのアプリケーションの状態を改めて確認していないため、正式な性能の測定として扱わない。`benchmark` スキルの本測定・プロファイル・比較言語・結果の保管場所・コミットの手順は、今回の測定範囲と書き込み先の指定に合わせて適用しなかった。

各型・各方式で別プロセスを 3 回起動した。一プロセス内は 6 回呼び、初回を除く 5 回、計 15 回の中央値を時間として示す。毎回新しい Store とインスタンスを作る。コンパイル・インスタンス化・入力値の初期作成・結果の照合・値の解放は時間の表に含めず、呼び出しに必要な変換を分けて計った。最大 RSS は 3 プロセスの最大で、コンパイル、初期作成、全 6 回の実行、結果の照合と保持も含む。

`/usr/bin/time -l` は、この実行環境で `sysctl kern.clockrate: Operation not permitted` により RSS を出力できなかった。代わりに Python の `os.wait4` が返す `rusage.ru_maxrss` を使った。記録はこの macOS 上のバイト値であり、表は 2^20 で割った MiB である。

ゲストは値をそのまま返す関数である。各方式の元のゲストは同じ WAT から生成した。ホストの入力と戻り値は、`bool`・`i64`・`String`・欄名を持たないレコード・リストからなる共通の小さな値の木である。Benitoite のヒープ、永続リスト、回収、VM は含まない。「今の動的な経路」の比較対象は、今と同じ Wasmtime の `Val` の表現と `Func::call` を使う境界の試作であり、`benitoite run` の全経路の測定ではない。

### 4.2 入力と方式

| 型 | 入力 |
|---|---|
| `List[String]` | 100,000 要素。文字列は `s0000000` など、それぞれ UTF-8 で 8 B |
| `List[Boolean]` | 1,000,000 要素。真と偽を交互に置く |
| レコードのリスト | 100,000 要素。欄は `id: s64`, `active: bool`, `label: string`。label は 8 B |
| 入れ子のリスト | `list<list<bool>>`。外側 1,000 要素、内側各 100 要素 |

「動的」は毎回 `Val` を作る。「再利用」は引数の `Val` を最初に作り、その領域へ毎回値を書き直す。「補助」は型を使ったバイト列の変換と生成した補助コードを使う。再利用の初期構築は時間に含めないが RSS に含める。補助のバイト列の領域も容量を再利用する。戻り値は三方式とも共通の値の木を毎回作り、入力との一致を時間外で確かめた。

### 4.3 時間と最大 RSS

単位は時間が ms、RSS が MiB である。準備は言語の値に相当する共通の木から Wasmtime へ渡す表現への変換、call は Wasmtime の呼び出しと両方向の ABI 変換、結果の変換は共通の木を作る処理である。合計は各試行の三つの時間の和の中央値なので、各列の中央値の和とは必ずしも一致しない。

|---|---|---:|---:|---:|---:|---:|
| `List[String]` | 動的 | 0.719 | 4.869 | 0.768 | 6.356 | 48.12 |

| `List[Boolean]` | 動的 | 1.200 | 12.838 | 1.759 | 15.601 | 339.73 |
| 同上 | 再利用 | 1.743 | 12.828 | 1.800 | 16.314 | 339.80 |
| 同上 | 補助 | 1.548 | 4.115 | 2.045 | 7.714 | 77.31 |
| レコードのリスト | 動的 | 4.291 | 13.263 | 1.979 | 19.719 | 112.72 |
| 同上 | 再利用 | 0.858 | 12.367 | 1.974 | 15.225 | 116.66 |
| 同上 | 補助 | 1.373 | 4.097 | 2.474 | 7.974 | 57.11 |

補助方式は、レコードで合計約 2.47 倍、Boolean のリストで約 2.02 倍、入れ子で約 2.18 倍の速さになった。文字列のリストは約 1.22 倍で、結果を共通の木にする処理はむしろ長かった。文字列の内容を写す費用は残るので、`Val` の大きさの比をそのまま時間の改善率にはできない。

コンパイルの中央値は、元のゲストが約 0.9〜1.0 ms、補助を含むゲストが約 2.4〜3.1 ms であった。インスタンス化の中央値は約 5〜15 µs である。これらは小さな生成コードの数字であり、実際の大きなコンポーネントを包む費用は未確認である。

### 4.4 受け渡しの量と Wasm の燃料

`Store::hostcall_fuel()` は設定した上限を返し、消費後の残量を返さない。そのため、各型・方式について新しい Store で上限を変えて呼び、成功する最小値を二分探索で求めた。下表は式からの推測だけでなく、実際の呼び出しでその境界を確認した値である。各境界の確認は一組につき一回、最大 64 呼び出しで行い、時間・RSS の測定とは別プロセスにした。

出典: `W/src/runtime/component/store.rs:480–517`（[上限の getter と設定](https://github.com/bytecodealliance/wasmtime/blob/v49.0.2/crates/wasmtime/src/runtime/component/store.rs#L480)）。同説明は、ホストからゲストへ渡す引数をこの予算で制限しないとする。したがって、下表の hostcall fuel は戻り値の量である。引数の上限は、現実装と同じくホストが別に検査する必要がある。

| 型 | 動的・再利用の hostcall fuel（B） | 補助の hostcall fuel（B） | 動的・再利用の Wasm 燃料 | 補助の Wasm 燃料 |
|---|---:|---:|---:|---:|
| `List[String]` | 4,800,000 | 1,600,008 | 2,200,197 | 27,300,908 |
| `List[Boolean]` | 40,000,000 | 1,000,008 | 56 | 83,000,439 |
| レコードのリスト | 18,100,000 | 3,200,008 | 2,200,221 | 31,801,005 |
| 入れ子のリスト | 4,040,000 | 108,008 | 22,042 | 8,577,431 |

動的なレコードは、外側の要素 40 B、欄の値 3 × 40 B、欄名 `id`・`active`・`label` の合計 13 B、文字列 8 B で、一要素 181 B となる。補助のレコードは整列込みで 24 B、文字列が 8 B、根の記述が 8 B なので `100,000 × 32 + 8` となる。リストや文字列の参照のための記述と詰め物も受け渡すので、内容のバイト数だけにはならない。

動的な量を確かめた実装の根拠は `W/src/runtime/component/values.rs:273–285,1019–1038`、補助が返す `list<u8>` の量の根拠は `W/src/runtime/component/func/typed.rs:1767–1778`（[型付きリストの予算](https://github.com/bytecodealliance/wasmtime/blob/v49.0.2/crates/wasmtime/src/runtime/component/func/typed.rs#L1767)）である。引数は戻り値と同じ値を渡すので、今回のホスト表現の論理上の量も同じである。ただし、Wasmtime が引数の hostcall fuel を消費したという意味ではない。

Wasm の燃料は `Store::get_fuel` の呼び出し前後の差である。新しい Store の初期化から呼び出しまでを含む。動的な変換の多くはネイティブのホストコードで行うため、Wasm の燃料には入らない。一方、補助の走査は Wasm の命令なので燃料を消費する。Boolean のリストでは 56 から約 8,300 万に増えても、時間は短くなった。燃料が多いことをそのまま遅さと解釈しないが、既存の `--wasm-fuel` で到達できる入力の大きさは変わりうる。

### 4.5 戻り値の確認と試作の限界

全 12 組の測定で、戻り値を共通の木に直して入力との一致を確かめた。補助では、返ったバイト列とホストが作ったバイト列の一致も確認した。これに加えて、4 型 × 3 方式 × 入力の大きさ 0・1・33・100 の 48 条件、不正な UTF-8 の戻り値が拒否される 2 条件、元のゲストの post-return が文字列の領域を壊しても戻り値が保たれる 2 条件の、計 52 条件を確認した。入れ子の入力は要素総数を 100 で割って外側の長さを作るため、100 未満の条件は外側が空である。

不正な UTF-8 の試しは、元のゲストが最初の文字列の一バイトを `0xff` にして返す形である。補助方式でも元の WIT の文字列の検査が残ることを確認した。post-return の試しは、元のゲストの後処理が同じ位置を `0xff` に上書きする形である。結果が先に別の領域へ写されることを確認した。Wasmtime の同期の `call` が post-return を自動で実行する根拠は `W/src/runtime/component/func/typed.rs:111–115` と `W/src/runtime/component/func.rs:234` である（[同期 call の後処理](https://github.com/bytecodealliance/wasmtime/blob/v49.0.2/crates/wasmtime/src/runtime/component/func/typed.rs#L111)）。追加で二度呼ぶ設計にはしない。

今回、行きだけと帰りだけの ABI 変換時間は分離していない。準備と結果の構築を分け、往復の call と戻り値の予算を測った。ゲストが新しく作る巨大な結果、UTF-16 のゲスト、多数の文字列長の組み合わせ、すべての判別子・数の幅・resource・取り込み・非同期呼び出し・メモリの制限器を含む経路は未確認である。RSS の減少を Benitoite 全体の RSS の減少として扱わない。

## 5. 型の範囲と戻り値の本体への取り込み

通常の値の変換表は、一つの表からホストの変換と補助コードの生成の両方に使う案を推す。基本型・レコード・リスト・タプル・直和型などを、それぞれ次の処理にする。ここでの拡張可能性は設計案であり、試作済みの範囲は前節の四つに限る。

| 種類 | 共通の変換器で行うこと | 試作以外に要る確認 |
|---|---|---|
| 幅の決まった数・Boolean・Character | 決まった幅で読み書きする | 範囲、文字の妥当性、浮動小数の扱い、各幅 |
| String・Bytes・List | 長さと参照先を記録し、要素を走査する | UTF-8 以外のゲストとの変換、空値、長さと総量の上限 |
| record・tuple | 型の表の欄順と位置で読み書きする | 任意の欄数・欄型・整列条件。型名と欄名は照合で扱う |
| variant・enum・Option・Result | 場合の番号と、選んだ場合の中身を読み書きする | 判別子、場合ごとの大きさ・整列、平らにした形の合流 |
| flags・map | 採用した WIT 型に対応する並べ方を生成する | 調査 A の採否、Wasmtime の有効化設定、鍵の規則 |
| resource を含む型 | 当面は既存の動的経路を使う | 同じ Store 内の型と対象の同一性、所有と借用、解放 |

戻り値は、最初にバイト列を検査し、言語のリストを小さな葉ごとに作る。要素数分の中間の `Vec<Value>` は作らない。明示の作業列を使い、回収しない区間の `Value<'epoch>` を Store や長生きする作業領域へ保存しない。この方針は、今の `typed.rs` と `convert.rs` の値の管理に合わせるものである。

`ResourceAny` は、ただの 32 bit の番号ではない。Store 内の型・対象・所有と借用の状態を持ち、解放が要る。公開 API から任意の番号で `ResourceAny` を作ることはできない。バイト列に数を詰めるだけで、既存の外部の型の値を同じものとして返せるとは判断しない。

出典: `W/src/runtime/component/resources/any.rs:26–60,287–323`（[ResourceAny の生成と状態](https://github.com/bytecodealliance/wasmtime/blob/v49.0.2/crates/wasmtime/src/runtime/component/resources/any.rs#L26)）。将来は、resource を別の WIT の引数として保持する補助コードや、型ごとの資源の表を設ける案があるが、今回は実現性・費用とも未確認である。`own` の引数を使った後の値を使えなくする問題も、転送の圧縮だけでは解決しない。

## 6. 3b のホストの関数へ使えるか

今の動的経路は、3b でも `LinkerInstance::func_new` により使える。ホストへ来た引数は `Val`、ホストから返す値も `Val` であり、今回の名前と値の確保の費用は逆向きにも現れる。型が既知なら `func_wrap` を使えるが、型の組み合わせをビルド時に決める制約は同じである。

出典: `W/src/runtime/component/linker.rs:504–511,630–740`（[型付きと動的なホストの関数](https://github.com/bytecodealliance/wasmtime/blob/v49.0.2/crates/wasmtime/src/runtime/component/linker.rs#L630)）。

補助コード方式は、通常の値に対して向きを逆にした構成へ一般化できる見込みである。ゲストが要求する元の WIT の関数を補助コンポーネントから与え、その本体が引数をバイト列へ詰めて共通のホスト関数を呼ぶ。ホストは同じ型の表で言語の値を作り、結果を同じ形式で詰め、補助コードが元の WIT の結果へ戻す。補助の公開の取り込みは、例えば「関数の番号とバイト列を受け、バイト列を返す」少数の固定した型にできる。これは設計案であり、この逆向きの合成の試作は行っていない。

3b で共通にできるのは、型の表・相対位置を使う形式・通常の値の変換器・補助コードの読み書きの処理である。ハンドラへの操作の受け渡し、タスクの切り替え、待つ間の根の保存、取り消し、ゲストへの再入、resource の所有権は別に設計する。同期の固定した型を先に使えても、それだけでは待つホスト関数の実行は実現しない。

hostcall fuel はホスト関数を呼ぶごとに初期の予算を使うため、3b では一回の外部の呼び出しの中で小さな転送を繰り返せる。ホストの引数の合計・戻り値の合計や保持量を、呼び出しごとの予算とは別に集計する必要がある（`W/src/runtime/component/store.rs:499–502`）。この点は 3a の一往復の上限をそのまま複製しない。

## 7. 既存の経路との併用と実行ファイルの大きさ

初めの振り分けは、既存の型付きの経路に入る関数を今のまま呼び、ほかの通常の値だけからなる関数に補助コードを使い、resource を一つでも含む関数を既存の動的経路で呼ぶ案を推す。新しい数の型やリストを加えるたびに、既存の具体化の組み合わせ表を拡張しない。失敗時に別の経路で再実行する案は採らない。特に状態を持つ呼び出しでは、最初の試行が既に状態を変えている場合があるためである。

導入は、4 種の試作から一般の非再帰の通常の値へ広げ、型の表の範囲で扱えることを照合の時点で確定する。補助の生成に非対応の型がある期間は、呼ぶ前に動的経路と決める。ABI 違反・制限超過・実行の失敗を受けて動的経路へ切り替えない。

TODO-240 の記録の +2.17 MB は、642 通りへ絞る前の 1,554 通りの具体化の増分である。現在の実装は、数のリストを含む 3 引数の組を動的経路へ戻している。その +2.17 MB 全体を、今から削除できる量として扱ってはならない。過去の増分と最終の範囲は、[TODO-240 の Q2](../../archive/2026-10-13-TODO-240-typed-list-transfer/decisions.md#q2-実行ファイルの大きさ)と、今の `crates/benitoite/src/external/typed.rs`・02-09「外部の関数の実行」で確認した。

試作では、共通のホストコードの方式をコンパイル時に固定して、不要な方を最適化で除いた二つのバイナリも作った。依存・ビルド設定・入力生成・WAT の読み込みは共通にし、コピーした実行ファイルに `strip` を行った。

| 試作のバイナリ | strip の前（B） | strip の後（B） |
|---|---:|---:|
| 動的のみ | 15,699,968 | 11,369,064 |
| 補助のみ | 15,609,328 | 11,301,928 |
| 両方式と再利用を含む | 15,727,264 | 11,386,104 |

この試作では、補助のみは動的のみより strip 後に 67,136 B 小さく、両方式は動的のみより 17,040 B 大きかった。ただし、生成器は Python の外部ファイルで、本体に必要なバイナリ生成器も Benitoite との変換も含めていない。WAT の解析器も含む独立バイナリであり、本体の増減の見積もりには使わない。「固定した一つの Rust の呼び出し型の追加が、数百の組み合わせの具体化を要求しない」ことの確認に限る。本体へ併用したときの増分は未確認である。

生成したコンポーネントのバイナリは、元のゲストが 340〜382 B、補助を含むものが 1,387〜1,663 B であった。型ごとの増分は約 1.0〜1.3 KB で、実行ファイルへ全型を埋め込む費用ではない。ただし、読み込んだコンポーネントごとの生成コード、Cranelift でコンパイルしたコード、メモリ、初回の時間は増える。多数の型を持つライブラリでの量は未確認である。生成した補助コードは契約ごとに共有し、コンパイル済みコードは同一の実行内で再利用する案を推す。

既存の型付きの経路をすべて補助へ置き換えれば、今の組み合わせの具体化を削れる見込みはある。しかし、短い数の関数までバイト列に詰める固定費、大きな `Bytes` の追加のメモリと燃料を今回測っていない。動的経路を削れば resource と未対応の型の受け渡しも失う。このため、全置換の本体の増減と性能は未確認とし、3a の最初の変更では併用を推す。

|---|---|---|---|
| **A: 補助コードを導入し、既存の経路と併用する（推す案）** | 任意のレコードを型から扱う設計にできる。非公開 API と手書きの `unsafe` が要らず、今回の大きな複合値で費用を減らせた | 生成器・両方向の変換・制限・解放の実装が要る。固定した Rust の呼び出し型と生成器が加わる。本体の増分は未確認。追加メモリ・燃料・コンパイル時間が要る | 型システムやコレクションの表現を転送のために変えない。境界の変換表を広げる |
| B: 今の二経路を続け、必要なら引数の `Val` を再利用する | 変更が小さく、外部の型を含む既存の実行をそのまま使える | 再利用の管理だけなら作業は少ない。大きな新しい依存は不要。戻り値の 40 B の値と欄名の確保が残る。速い型を追加するたびに具体化が増える | 中核を変えない。新しい型にも動的な変換を足す |
| C: `unsafe` の例外と非公開 API を認め、自前の trait 実装または Wasmtime の改造を行う | ホストの値から直接変換する API を自分で設計できる可能性がある | 型付き trait だけでは任意の ABI の問題が残る。実行系の改造・更新ごとの保守・安全性の確認が要る。速度と実行ファイルの量は未確認 | 中核への直接の変更は不要だが、プラグイン基盤の保守を自分で受け持つ範囲が広がる |

推す理由: A は今回の規約の下で動き、問題の中心であるレコードの値ごとの確保を減らせた。既存の速い経路と外部の型の動的経路を残せば、未確認の費用と所有権の仕組みを同時に置き換える必要がない。作業量を最優先して今回の転送の改善を見送るなら B とする。

### Q11 既存の速い経路を残す範囲

問い: Q10 で A を選ぶ場合、3a の最初の変更で今の型付きの速い経路を残すか。

| 選択肢 | 利点 | 費用（作業・実行ファイル・性能） | 言語の中核への影響 |
|---|---|---|---|
| **A: 今の範囲を残し、型の組み合わせを増やさない（推す案）** | 小さな数の関数と大きな `Bytes` の既存の費用を保つ。新しい複合型は共通の仕組みで扱う | 三経路の振り分けと検査が要る。現在の具体化は残るので、実行ファイルの縮小は当初の目的にしない。補助の追加量は統合後に測る | なし。振り分けは照合済みの境界の型だけで決める |
| B: resource を含まない関数はすべて補助へ置き換える | 非 resource のホストの受け渡しを一つにでき、既存の具体化を削れる見込みがある | 短い関数と `Bytes` の比較測定、上限と回帰の確認が増える。本体の正味の縮小量は未確認。追加のコピー・メモリ・燃料が全関数へ及ぶ | なし。ただし、型や経路で変わる上限の説明を更新する |

推す理由: 今回の測定は既存の速い型の置換を確かめていない。A で複合値の改善を入れ、B を選ぶための短い関数・大きなバイト列の測定を別に行う。resource の動的経路は、どちらを選んでも残す。

### Q12 補助コード方式の受け渡しの予算

問い: 補助の予算を、実際に受け渡すバイト列の長さで数えてよいか。

| 選択肢 | 利点 | 費用（作業・実行ファイル・性能） | 言語の中核への影響 |
|---|---|---|---|
| **A: 根の記述と詰め物を含むバイト列の長さで数える（推す案）** | Wasmtime が返す `list<u8>` の hostcall fuel と一致し、要素ごとの `Val` の費用を数えずに済む | ホストの引数の事前検査、補助コード内での結果の展開量の検査が要る。実行ファイルへの追加は検査のコードで、量は未確認。旧経路と予算の単位が異なる点を説明する | 型の意味は変えない。転送と線形メモリの上限の説明が変わる |
| B: 元の `Val` と同じ仮想の量も数え、両方を制限する | 動的経路と同じ大きさで止まり、転送の上限について既存の挙動を保ちやすい | 型と値を辿る追加の計数と検査が要る。実際の表現を減らしても、大量の Boolean やレコードが旧予算で止まる。実行ファイルへの量は未確認 | 型の意味は変えない。仮想の費用を保証の一部として残す |

推す理由: 既存の速い経路も実際の表現に合わせて予算を変えている。A にし、`--wasm-stats` は経路と実際の表現の量を示す。補助の追加のメモリは Store 全体の上限で数え、ホストの値の構築量と要素数は別に制限する。「バイト列の長さがプロセス全体のメモリの上限である」とは説明しない。

## 9. 推す案どおりにする点

以下は、Q10〜Q12 の答えがその案を許す場合に実装プランへ入れる細部である。未決の答えを先に確定した扱いにはしない。

- **R-B1: 規約と公開 API。** 受け渡しのために `runtime::heap` の外へ手書きの `unsafe` を加えず、`component::__internal` を本体の依存先にしない。`TypedFunc::new_unchecked`・`deserialize` も使わない。通常の `Component::from_binary` の検証を通す。
- **R-B2: 型の表。** 実行前に元の WIT の契約を今の規則で照合する。型の表をホストの両方向の変換と補助コードの生成で共有し、欄名と場合の名前は表に一度だけ保存する。引数の数をバイト列の形式に含め、戻り値なしも表で表す。試作の一つのリストという制約を本体の仕様にしない。
- **R-B3: 値の管理。** 回収しない区間の値を長生きする Wasmtime の状態に保存しない。言語のリストはカーソルで読み、戻り値は小さな葉ごとに作る。型と値の走査は予算付きの明示の作業列で行う。
- **R-B4: 上限と診断。** 引数の量をコンパイル・インスタンス化より先に検査する。結果の詰め直しも増分ごとに転送の上限を検査してから確保する。ホストのデコード時はバイト列の長さに加え、言語の値の総構築量を制限する。上限超過とゲストの ABI 違反を今の診断に合わせ、実行の失敗後に別経路で再実行しない。
- **R-B5: メモリと燃料。** 補助のメモリとコアインスタンスも現在の Store 全体の制限へ含める。生成した走査も Wasm の燃料と中断の対象とし、量を少なく見せるために燃料の計数を切らない。既定の上限を自動的に広げない。
- **R-B6: 後処理。** 元の関数の post-return は Component Model に任せる。補助の一時領域の寿命と再利用は別に定める。resource は当面、現在の Store・対象の表・解放待ちの列を使う動的経路で扱う。
- **R-B7: 生成と共有。** 本体では WAT の文字列の生成・解析を介さずにバイナリを組み立てる。同じ照合済みの契約の生成コードを同一実行内で共有する。永続のコンパイル済みコードのキャッシュは今回の案に含めない。
- **R-B8: 取り込み前の確認。** 任意の欄型・直和型・新しい数の幅・flags・map を扱う範囲に合わせ、両方向の値、不正な結果、符号化、予算の境界、post-return、状態を持つ経路の解放を確認する。既存の型付きの経路も含む本体の実行ファイルの大きさと短い関数・大きな `Bytes` を測り、今回の試作の数字で代用しない。3b では逆向きの合成とホスト呼び出しごとの予算を追加で確かめる。
