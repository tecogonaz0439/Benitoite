# 調査 A: WIT に合わせた言語の型

調査日: 2026-10-13。対象は TODO-020・241 のフェーズ 3a である。本書は調査と設計案であり、設計者の採択を表すものではない。Q1〜Q3 の答えは [decisions.md](../decisions.md) にある。Q2 の数の型の役割は未決、Q3 の見た目は仮の形で導入してよい、という前提で案を比べる。

推す案は、WIT の数の型のうち足りない七つを境界のための基本型として加え、`flags` は引数のない構成子の集合、`map` は既存の `Map` で表すことである。具体的な型引数を与えた非再帰の型と、複数の引数を持つ構成子も受け渡せるようにする。任意の長さの組は、既存の `data` の一つの構成子で表せるようにする。型の算術や新しい組の構文を加える判断は、境界で受け渡せる型を増やす判断と分ける。

WIT は外部に公開する型と関数を書く言語である。正準 ABI（canonical ABI）は、その値を Wasm の引数やメモリにどう並べるかの取り決めである。Benitoite の値の表現を正準 ABI と同じにすることと、境界で正準 ABI へ変換することは別の判断である。

本書でいう幅（bit width）は、値を表すビットの数である。binary32・binary64 はそれぞれ IEEE 754 の単精度・倍精度の形式を指す。即値（immediate value）は別のヒープの対象を作らず、値の保存領域に直接保持する数などである。構成子のペイロード（payload）は、その構成子に添える値を指す。具体化（monomorphization）は、型の組み合わせごとに Rust の関数の実体を生成することである。型引数の置き換え（type substitution）は、`Box[T]` の `T` に `Integer` などの具体的な型を入れることであり、Rust の具体化とは区別する。

未確認なのは、新しい型を加えた後の実行ファイルの増分、CPU の時間、最大 RSS、LLM の生成・修正の成功率である。以下の作業量は変更箇所からの見積もり、性能への影響は表現からの見込みであり、新しい実装を測った値ではない。

ADR 0105 が変更先として挙げた章は 01-04・01-06・03-06 である。その判断は、基本型に Byte を加える、等値と順序比較を認める、算術と専用リテラルを設けない、失敗する縮小変換を Option で表す、という四点に整理できる。現在の実装ではさらに、Byte の定数・即値・鍵の順序・組み込みの型付き引数・Lean の基本型・Skill に対応がある。したがって今回の案1でも、当時の三章だけを直す計画では足りない。ADR の「基本型は七つ」はその時点の記録であり、Decimal を含む現在の八つという一覧を上書きしない。

## 3. WIT の型と現行の対応

基本型と合成の型の種類は C1 と W1、Benitoite の側は 03-10 と `src/external/types.rs` で確認した。表の「なし」は現行の宣言で対応づけられない意味であり、Wasm が値を保持できないという意味ではない。

| WIT | 現行の Benitoite | 制限・不足 |
|---|---|---|
| `bool` | `Boolean` | 等値だけ。順序の比較演算子を持たない |
| `s8` | なし | Integer から範囲を調べて暗黙に渡す対応はない |
| `s16` | なし | 同上 |
| `s32` | なし | 同上 |
| `s64` | `Integer` | 全範囲が一致する |
| `u8` | `Byte` | 算術は持たない |
| `u16` | なし | 値は Integer に収まるが型の対応がない |
| `u32` | なし | 同上 |
| `u64` | なし | 2^63〜2^64−1 は Integer に収まらない |
| `f32` | なし | Float の精度を実行時に落として渡す対応はない |
| `f64` | `Float` | NaN の符号や追加のビット情報の往復は保証しない（C3） |
| `char` | `Character` | Unicode のスカラー値。サロゲートは含まない |
| `string` | `String` | 言語内は UTF-8。境界の符号化と予算は実行方式で扱う |
| `list<T>` | `List[T]`、`list<u8>` には `Bytes` も対応 | 内側の T も受け渡せる必要がある。戻る宣言に従い Bytes と List[Byte] を区別する |
| `tuple<A,B>` | 標準の `Pair[A,B]` | 束縛の番号で標準の型だと判定する。同じ名前の利用者の型を特例にしない |
| `tuple<A,B,C>` | 標準の `Triple[A,B,C]` | 3 要素は既に対応する |
| 4 要素以上の `tuple`、0・1要素の組 | なし | Pair の入れ子は入れ子の tuple になる。平らな4要素の tuple の代用にはならない |
| `option<T>` | 標準の `Option[T]` | 内側の T に Unit は使えない |
| `result<T,E>` | 標準の `Result[T,E]` | Unit の側は WIT のペイロードを省く。両側 Unit なら `result` |
| `record` | 型引数を持たないレコード | 欄の数・宣言順・正規化した名前・型を照合する |
| `variant` | 型引数を持たず、各構成子の引数が0か1個の data | 複数引数の構成子は受け渡せない |
| `enum` | 型引数を持たず、全構成子が引数を持たない data | 同じ data はペイロードなしの variant にも対応する |
| `flags` | なし | Boolean のレコードも Set[enum] も現行では対応しない |
| `resource` | `@external` で宣言する外部の型 | 引数は borrow、戻り値は own。own の引数は対象外。01-10 のリソースの型とは別である |
| `map<K,V>`（Wasmtime 49.0.2） | なし | `Map` は現在 E1010。検査と実行の設定を揃え、対応と予算を追加する必要がある（W2） |

受け渡せない形は、具体的な型引数を与えた型でも型パラメータのある利用者のレコード・data、構成子の引数が2個以上の data、直接・間接の再帰である。型の別名を展開した後の形で判定する。外部の関数自体の多相な型パラメータも受け付けない。言語内の多相な関数から、具体的なシグネチャの外部の関数を呼ぶこととは区別する。

`Decimal`・`Map`・`Set`・関数の値・Task・Lazy・Reference・01-10 のリソースなどは現在対応しない。Unit は関数の戻り値なしと Result の省略した側だけに使え、引数・List・Option・組・レコードの欄には使えない。Wasmtime の API にある future・stream・error-context・固定長のリスト（W1）は、今回指定された型の集まりに含めず、引き続き拒否する。

型の照合には、深さ100、根の型ごとの節点100,000、検査一回の合計1,000,000という現行の上限がある。新しい合成の型にも適用し、展開の予算の超過を「未対応の基本型」と取り違えない。

## 4. 幅の決まった数の二案

### 4.1 型の集まりと名前の候補

WIT の数の型十種のうち三種には既存の型を使い、残る七種に基本型を加える。下の名前は Q5 のための候補である。

| WIT | 推す名前 | 値の範囲・精度 |
|---|---|---|
| `s8`・`s16`・`s32` | `Integer8`・`Integer16`・`Integer32` | −2^(n−1)〜2^(n−1)−1 |
| `s64` | 既存の `Integer` | −2^63〜2^63−1 |
| `u8` | 既存の `Byte` | 0〜255 |
| `u16`・`u32`・`u64` | `UnsignedInteger16`・`UnsignedInteger32`・`UnsignedInteger64` | 0〜2^n−1 |
| `f32` | `Float32` | IEEE 754 の binary32。正負の零・無限大・NaN を含む |
| `f64` | 既存の `Float` | IEEE 754 の binary64 |

`s64` 用に別の Integer64、`u8` 用に別の UnsignedInteger8、`f64` 用に別の Float64 を作ると、同じ値・役割を持つ型が二つになる。名前を揃えるだけの目的でそれらを足すことは推さない。完全に揃えるなら既存の名前の改名という別の費用を伴う判断になる。

### 4.2 案1: 範囲・精度を保つ境界のための型

案1では、新しい型に等値・同じ型どうしの大小の比較、明示の変換、文字列への変換を持たせ、算術を持たせない。整数型は鍵の型、Float32 は等値の型だが鍵の型ではない。Byte の既存のビット演算は保ち、新しい型のビット演算の一式は今回追加しない。

| 操作の候補 | 型と意味 |
|---|---|
| `Integer8.fromInteger` など | `Integer -> Option[T]`。範囲内なら Some、範囲外なら None。負値を符号なしへ渡して折り返さない |
| `Integer8.toInteger` など | `T -> Integer`。Integer8・16・32 と UnsignedInteger16・32 の全値を正確に広げる |
| `UnsignedInteger64.toInteger` | `UnsignedInteger64 -> Option[Integer]`。2^63以上なら None。この型だけ全域の変換にならないことを説明と診断で示す |
| `UnsignedInteger64.parse` | `String -> Option[UnsignedInteger64]`。十進の0〜2^64−1を受け付ける。負号・範囲外・数字でない入力は None。先頭と末尾の空白は受け付けない |
| `UnsignedInteger64.toDecimal`・`fromDecimal` | 前者は全値を正確に Decimal にする。後者は数学的に整数で0〜2^64−1なら Some、それ以外は None。`1.0m` も整数として受け付ける |
| `T.toString`、文字列補間 | 幅のある整数は十進表記。Float32 はその値へ読み戻せる表記とし、文字列補間も同じ関数を呼ぶ |
| `Float32.fromFloat` | `Float -> Option[Float32]`。最近接偶数丸めを行い、有限値が丸めで無限大になるときは None。もとからの無限大・NaN は Some。小さな有限値の丸めによる零は認め、正負の零を保つ |
| `Float32.toFloat` | `Float32 -> Float`。有限値を正確に広げる。NaN の追加のビット情報の保存は契約にしない |
| `Float32.isNaN`・`isInfinite` | 変換を通しても作れる特殊値を調べる。比較の意味は Float と同じ |

整数の各幅から Float への変換は `T.toInteger` と `Integer.toFloat` を組み合わせられる。u64 の全域から Float へ移す必要があれば `toDecimal` と既存の Decimal の変換を使えるが、丸めで下位の情報を失うことは避けられない。整数の幅どうしを直接変換する56通りの関数は設けず、Integer に収まる値は Integer、u64 の全域は Decimal を介す。Decimal の96 bit の係数は u64 の全値を正確に保持できる。Decimal を WIT の u64 の宣言型にする案とは異なり、境界では常に独立した u64 の型を使う。

Float から Integer に収まる幅の整数へは、既存の `Float.truncate` で0の方向に切り捨て、その Option の中身を `T.fromInteger` に渡す。NaN・無限大・Integer の範囲外は最初の変換で None、目的の幅の範囲外は次の変換で None になる。u64 の上半分に Float から直接移す関数は今回設けない。既存の `Decimal.fromFloat` は binary64 の正確な整数値ではなく `Float.toString` の十進表記を読んだ値を返すため（01-04「型の変換」）、これを u64 への正確な変換と説明しない。u64 の正確な境界値を作る場合は十進の parse・Decimal リテラル・外部からの戻り値を使う。

計算は、例えば Integer32 を Integer にしてから行い、結果を `Integer32.fromInteger` で検査する。u64 の全域の加減算も Decimal の整数値に変換して行えるが、Decimal の除算や丸めの規則は固定幅の整数の `div` の代わりにはならない。幅を保つ数値計算が主用途のライブラリには案1の制約が残る。

案1は、境界での型の食い違いを実行前に検出でき、通常の集計や文字列の長さには既存の Integer を使い続けられる。費用は、外部の結果を計算するたびに変換と Option の処理が要ることである。LLM が `x + 1` と書いても型検査で止まるので、診断には「Integer にして計算し、fromInteger の結果を扱う」という修正例を付ける。成功率の改善は見込みであり、今回 LLM を呼ぶ評価は行っていない。

### 4.3 案2: 幅ごとに算術を持つ普通の数の型

案2では、整数の幅ごとに `+`・`-`・`*`・`div`・`mod`、符号付き整数に単項の `-`、Float32 に `+`・`-`・`*`・`/`・単項の `-` を持たせる。二辺は同じ型とし、結果もその型にする。符号なしの単項の `-` は静的な誤り、整数の `/` は静的な誤りとする。Float32 の演算は各演算の後に binary32 へ丸め、0による除算は Float と同じく無限大・NaNを返す。

案2の中にも、整数の範囲を超えたときの選択がある。

| 溢れの規則 | 利点 | 費用と誤りの見つけ方 |
|---|---|---|
| 2a 実行時エラー（案2を選ぶなら推す） | 既存の Integer と同じ。意図しない大きな結果を返さない | 幅ごとの checked な演算と診断が要る。動的な値の溢れは実行して分かる。定数式では既存の警告・誤りの二段の扱いを広げる |
| 2b 2^nで折り返す | バイナリの計算に使える。失敗を調べる分岐が減る場合がある | 既存の Integer と意味が分かれる。境界の型を変更すると演算の意味も変わり、型検査を通った意図しない値が出やすい。符号付きは2の補数として結果を解釈する規則が要る |

2aでは符号付きの最小値を −1 で `div` したら実行時エラー、同じ組の `mod` は0、0による `div`・`mod` は実行時エラーにする。符号なしの `0 - 1` も実行時エラーにする。2bでも0による除算は実行時エラーとし、符号付き最小値を −1 で割る結果まで折り返すかを明記する必要がある。2bを採るなら最小値へ折り返し、剰余は0とする案が一貫する。

案2では Byte にも同じ整数の算術を持たせることを推す。Byte を従来のままにすると、u8だけが計算できない例外となり、LLMへの説明と診断が増えるためである。これは Byte の既存の契約の拡張でもある。Q4 の案2にはこの拡張の費用を含めた。Integer の現在の溢れの規則は変えない。

暗黙の昇格（integer promotion）、すなわち幅の違う二つの数を自動的に共通の幅へ変える規則は入れない。例えば Integer32 と UnsignedInteger32 を混ぜると、数としての全範囲を片側に収められない。u64とs64の全範囲を同時に収める既存の整数型もない。どの型に変換したかをスクリプトに残す方が、原則2と4に適合する。

案2は外部から受けた数をそのまま計算でき、幅を保つ処理を書きやすい。一方、通常のIntegerとの変換はなお要り、接尾辞なしの `1` を混ぜた `x + 1` は型の誤りになる。期待される型に合わせて整数リテラルの型を変える案ならこの誤りは減らせるが、名前の使い方によりリテラルの型が変わる推論規則まで追加する費用がある。Q3が認めた「仮の形」を、その推論規則まで仮に変更してよいという了承とは扱わない。

### 4.4 u64 の値の表現

u64の全範囲はi64に収まらない。推す実装は、他の基本型と区別した即値の `u64` を保持し、型と値の種類を対応させる形である。上半分を負の Integer として使い回すと、大小の比較・表示・変換が符号付きの意味に戻る誤りを作りやすい。

| 表現の案 | 利点 | 費用・中核への影響 |
|---|---|---|
| 独立した `u64` の即値（推す） | 全値を正確に保持し、比較とWITの変換が直接できる | Value・Slot・定数・参照インタプリタの種類を増やす。64 bitのペイロードは既存のFloatと同じ幅であり、16バイトを保てると見込むが、追加後の検査は必要 |
| `i64` のビットを使い回す | ペイロードの場所を共有できる | u64という別の型の印はなお必要。符号なしの順序・変換を全箇所で選ぶ。型の印を消してIntegerと同じ値にする案は契約を守れない |
| Decimalまたは二つの32 bitの値のレコード | 全範囲を既存の構成で表せる | 全ての比較・変換に特別扱いか分解が要る。Decimalはヒープの確保が増え、二分した値は利用者にビットの知識を求める。WITのu64の宣言型として一般のDecimalやPairを受け付けると意味が広すぎる |
| Integerを多倍長へ変更 | u64の全値をIntegerで計算できる | 既存の64 bitと溢れの契約、VM、ライブラリ、形式化を変える。今回の境界の対応のための変更としては大きい |

UnsignedInteger64 の値を作る手段は外部の戻り値だけに限らない。`parse` と Decimal との正確な変換で、上半分をスクリプトから渡せるようにする。整数リテラルを追加する場合も、その値を最初に i64 として解析してからu64へ変換する実装にはしない。

### 4.5 f32 の精度と記憶域

Float32 の言語上の値は binary32 とする。倍精度で計算を続け、外部へ渡す直前だけ丸める形では、途中の比較や演算が binary32 の意味にならない。案1では値を作る変換時、案2ではそれに加えて各算術の結果で丸める。

| VM の保持の案 | 利点 | 費用・性能の見込み |
|---|---|---|
| 別の種類の `f32` の即値（推す） | Rustのf32で精度の不変条件を保ちやすく、WITのf32へ直接変換できる | 新しい値の種類と読み出し関数が要る。Value全体が16バイトなので、通常のListは小さくならない |
| binary32へ丸めた値を別の種類のf64で保持 | Floatの補助関数の一部を再利用できる。有限のf32の値はf64に正確に広げられる | 全ての生成と演算でf32へ戻す規則が必要。値の種類の追加は避けられない。保存するf64をFloatと区別しない案は静的な型と値の対応を失う |

f32からf64への有限値の変換が正確で、逆方向が最近接の値への丸めになることは [Rust Reference「Numeric cast」](https://doc.rust-lang.org/reference/expressions/operator-expr.html#numeric-cast) で確認した。Float32 の十進リテラルを設ける場合は、数字列から直接 f32 に丸める。数字列→f64→f32では二重の丸めが生じうるので、仕様の最近接丸めを実装したことにはならない。

単精度の大量保持には、要素を詰めた専用の配列か、List内部の特別な葉など、別の変更が必要である。本書はその変更を範囲に含めない。正準ABIでは `list<f32>` の要素は4バイト、`list<f64>` は8バイトである（C3）。これを少ない確保で利用できるかは調査Bの方式に依存する。新しい型を動的なValで渡すだけでは、W1の各要素の表現は小さくならない。

### 4.6 仮のリテラルとパターン

Q6には次の三案を出す。案1を選んだ場合は変換関数で開始することを推す。Q3は仮の構文を入れることを許すが、必要のない構文を追加する理由にはならない。

| 見た目の案 | 例（仮） | 利点・費用 |
|---|---|---|
| 関数による変換だけ（推す） | `Integer32.fromInteger(42)`、`UnsignedInteger64.parse("18446744073709551615")`、`Float32.fromFloat(1.5)` | 字句とパーサを増やさず、範囲外をOptionで処理できる。定数の直接の記述や案2の短い演算には冗長になる。文字列のparseは静的な範囲検査にはならない |
| 幅を明記する接尾辞 | `42s32`、`18446744073709551615u64`、`1.5f32`。u8はByte、s64はInteger、f64はFloat | 幅と範囲を実行前に確定できる。数の字句・AST・formatter・定数・Skill・Leanを変える。既存のmとの境目、不正な接尾辞、整数と浮動小数の区別を定める必要がある |
| 期待される型で決まる接尾辞なしのリテラル | `bind x: Integer32 <- 42` | 利用者とLLMの記述が短い。未確定のリテラルの型と既定値、型変数の制約、呼び出し・演算の診断を再設計する。費用が最も大きい |

接尾辞案では整数の既存の十進・十六進・八進・二進の形を許し、`-128s8` は負号を含めて範囲を調べ、`128s8` は拒否する。負号付きのu系は値が0の場合も拒否する。f32は小数点か指数を持つ形に限り、丸めで無限大になるリテラルを拒否する。NaN・無限大は変換関数で作る。接尾辞なしの整数と浮動小数は従来どおりIntegerとFloatとする。

新しい型のリテラル・範囲パターンは、接尾辞を式に認める場合も当面設けない案を推す。Byte・Float・Decimalと同じく、束縛・ワイルドカードとガードの比較で調べる。固定幅整数の全域の網羅性を新しいパターンで扱う判断は別途必要であり、案2の算術を持たせるだけでは必要にならない。

| 言語・一次資料 | 確認した事実 | 二案への示唆 |

| Rust: [TryFrom](https://doc.rust-lang.org/std/convert/trait.TryFrom.html)、[整数の演算と溢れ](https://doc.rust-lang.org/reference/expressions/operator-expr.html#overflow)、[u64 の checked_add・wrapping_add](https://doc.rust-lang.org/std/primitive.u64.html#method.checked_add) | 幅ごとの整数に演算があり、失敗する縮小変換をTryFromで扱える。算術の溢れの検査はビルドの設定で変えられ、検査付きと折り返す関数を別に持つ | 案1のOptionによる変換に先例がある。案2でRustの通常の演算をそのまま使うとBenitoiteの溢れの契約をビルド設定に委ねるので、checkedな操作を選ぶ |
| Kotlin: [Numbers](https://kotlinlang.org/docs/numbers.html)、[Unsigned integer types](https://kotlinlang.org/docs/unsigned-integer-types.html) | 代入・関数の引数では明示の変換が要るが、混ざった算術では自動的に変換する。例のInt＋Longの結果はLong。Intの溢れとByteへの縮小変換は折り返す。ULongは0〜2^64−1、符号なしの型は対応する符号付き型の記憶域を使う | 幅のある型と通常の計算を共存させる先例である。変換が明示でも範囲の誤りを検出するとは限らず、案1の変換はこれより厳しくする。混ざった算術の自動変換はBenitoiteへ採り入れない |
| Swift: [Basic Operators の公式の原稿](https://github.com/swiftlang/swift-book/blob/main/TSPL.docc/LanguageGuide/BasicOperators.md) | 通常の算術は溢れを検出し、折り返す演算子を別に持つ | 案2aに近い。Benitoiteでは整数の既存の規則と合わせ、折り返す別演算子の追加は今回行わない |

| F#: [Basic Types](https://learn.microsoft.com/en-us/dotnet/fsharp/language-reference/basic-types) | sbyte・byte・int16・uint16・int32・uint32・int64・uint64・float32を持ち、幅ごとの接尾辞を示す | 案2の型の集まりと接尾辞に先例がある。F#の通常の算術の溢れについては、この資料だけでは確認していないので本書の根拠にしない |

### 4.8 変更箇所と作業量の見積もり

作業量は、LLMの実装とレビューを一つの変更単位として数えた概算である。単位は「独立に完了条件を検査できる作業」で、所要日数や週次のレートの消費量を表さない。七種をまとめた数の型だけの見積もりであり、調査Bの新しい受け渡し方式は含めない。

| 作業の分野（2節に対応） | 案1、変換関数だけ | 案2a、接尾辞つき |
|---|---|---|
| 仕様・API・診断 | 2作業。範囲、変換、u64、f32、比較と表示 | 3作業。左に加え、算術・溢れ・字句・定数式 |
| Leanの定義・証明・交換 | 2〜3作業。基本型・定数、比較・補間、性質1〜3と検査の関数 | 3〜5作業。左に加え、表層の新リテラル・負号、算術への対応 |
| 型の表・型検査・標準ライブラリ | 2〜3作業。新しい型、鍵、変換と比較の登録 | 3〜4作業。左に加え、整数の集まり・符号なしの負号、定数評価・警告 |
| VM・参照系・値の表現 | 2作業。即値、Slot、変換、等値と鍵 | 3作業。左に加え、定数と各幅の演算 |
| 境界と統合 | 1〜2作業。七種の対応と両方向の変換、予算、文書とSkillの生成 | 1〜2作業。境界の形は案1と同じ |
| 合計の目安 | 9〜12作業 | 13〜17作業 |

案1に接尾辞を足す場合は、案1の目安に字句・定数・Leanのリテラルのための2〜3作業を加える。案2を変換関数だけで開始すれば、接尾辞関係の1〜2作業を減らせる。期待される型で決まるリテラルは、推論と診断の再設計があるのでこの見積もりの外である。証明の修正量は場合分けの実際の失敗を見て精査する必要があり、上限を保証する見積もりではない。

どちらの案も、新しい基本型を足すためのソースの分岐と組み込みの表が増える。案2はそれに幅ごとの演算の本体が加わる。新しい外部ライブラリへの依存は必要ない見込みである。実行ファイルの増分は未確認であり、七種を今のTypedFuncの全組み合わせに追加した場合の増分と、言語内の数の実装の増分を混同しない。

型付きの経路の増大の既知の例は [TODO-240のQ2](../../archive/2026-10-13-TODO-240-typed-list-transfer/decisions.md#q2-実行ファイルの大きさ) である。1,554通りを具体化した段階でstrip後に2.17 MB増え、最終的には642通りへ絞った。「新しい型の追加で必ず2.17 MB増える」という測定ではない。全組み合わせへ新しい数を足す方針は採らず、調査Bが選ぶ方式の後に数える。

通常の数の演算は、案1では変換とOptionの構築・処理が増え、案2ではその費用を省ける場合がある。ゲストへの受け渡しの形式は両案で同じなので、案2を採ること自体で境界の確保は減らない。既存のInteger・FloatのVM命令は維持し、新しい数の算術は組み込みの関数で始めれば、既存の振り分けのループへの変更を小さくできる。

## 5. 合成の型の受け渡し

### 5.1 flags: 引数のない構成子の集合

flagsは、名付けた複数の項目を同時に選ぶ値である。enumは一つの項目を選ぶ値なので、enumのdata一つをそのままflagsにするだけでは全値を表せない。

| 言語の表し方 | 利点 | 作業・大きさ・性能・中核への影響 |
|---|---|---|
| `Set[D]`、Dは引数のない構成子だけのdata（推す） | 空集合を含む全ての選び方を表せる。構成子の綴りを型で検査し、既存のSetの操作を使える | 境界の照合と変換を追加する。VM・構文・Leanの言語内の規則を増やさない。選んだ項目の数に応じた木の値が要り、小さなビット列より言語内の記憶域は大きい |
| 全欄Booleanのレコード | 各項目を明示でき、構築時に全欄の検査がある | 境界だけの変更で済み、全欄の走査が必要。falseを含め全項目の欄を保持する。recordとflagsの二つに対応する規則の説明が要る |
| 専用のflags型・構文 | 言語内でもビット列で保持でき、項目数が多い場合は小さくできる | 新しい型・値・操作・構文・Lean・Skillが要り、実行ファイルも増える。今回の境界の対応を超えて中核を変える |
| IntegerやBytesをビット列として使う | 既存の値で保持できる | 未知の項目のビットや幅の誤りを型で防げない。WITの名前との照合を利用者へ押し付けるため推さない |

推す対応の例は、言語側の `data Permission` に引数のない `Read`・`Write` を宣言し、外部の引数を `Set[Permission]` にする形である。WITは `flags permission { read, write }` とする。言語内の値は `Set.fromList([Permission.Read, Permission.Write])` で作る。項目の一覧はSetの値を調べて決めず、Dの全構成子から決める。

照合は項目の数・宣言順・正規化した名前を現行のenumと同じ規則で比較し、各構成子のタグからWITの項目の位置へ写す表を作る。Subsetや数値のマスクへの暗黙の変換はしない。Setの各項目は一回しか現れず、戻り値もSetとして組み直す。Set[D]とWITのlistやenumを自動的に照合する規則は足さない。

Wasmtimeの動的なflagsは選んだ項目の名前の列を持つので、名前の複製の費用はなお残る（W1・W4）。専用の言語型を足さなくても、境界の変換表には項目の番号を持たせられる。番号での受け渡しを公開APIで実現できるかは調査Bが決める。

取得した最新のCanonicalABIの `lift_flat_flags`・`lower_flat_flags` は1〜32項目を前提にする（[同文書の2890–2893, 2990–2992行](https://github.com/WebAssembly/component-model/blob/main/design/mvp/CanonicalABI.md#L2890-L2893)）一方、Wasmtime 49.0.2のW4には複数の32 bit語を扱う分岐がある。この差からどちらかの上限を推定しない。対応させる項目数は49.0.2の実際の型の検査と配置に合わせ、32項目を超える境界と空のflagsは調査B・実装前の照合で確かめる。未確認の項目数まで受け渡せると約束しない。

### 5.2 map: 既存のMapとWITのmap

mapは既存の `Map[K,V]` で表せる。言語のMapは鍵を昇順で持ち、鍵は一意である。WITのmapは組の列であり、重複と順序を保存してもよく、組み直す場合は後の組の値を採る（C2）。既存のMap.fromListの意味と一致する。

| 案 | 利点 | 作業・大きさ・性能・中核への影響 |
|---|---|---|
| `Map[K,V]` に対応する（推す） | 既存の検索・更新・反復を使える。重複を後勝ちとし、鍵の順を言語内で保てる | 対応・予算・変換、map機能の設定を追加する。読み込みは一般にO(n log n)、書き出しはO(n)。ソースと実行ファイルの小さな追加が見込まれるが増分は未確認。中核のMapの規則は変えない |
| `List[Pair[K,V]]` にもmapを自動対応させる | 元の順序と重複を保ち、木を作る費用が要らない | list<tuple>とmapの二つの対応が増え、関数の型だけでは重複の意味が見えにくくなる。境界の診断・説明の作業が増える |
| 今回は保留する | 実装を増やさず現状を保てる | mapを公開するライブラリを使えず、型の見直しという今回の目的の一部を残す |

推す鍵の範囲は、WITの文書で確認した `bool`・s/u各幅・`char`・`string` のみである。これらに対応するBoolean・幅のある整数・Character・Stringは、言語内でも鍵の型である。Decimal・Unit・Bytes・レコード・data・組などは、言語内の鍵として使えても外部のmapの鍵には受け付けない。Float・Float32はどちらでも鍵にしない。

wasmparser 0.258.3のW5の箇所は複合の鍵を拒否していないので、Wasmtimeでバイナリを受け付けたことだけをWITの文書の鍵の規則の根拠にしない。宣言の側で上の共通範囲を静的に検査する。複合の鍵の対応は、WITとツールチェーンの版ごとの確認なしに広げない。

値Vは、再帰しない受け渡せる型なら入れ子にできる。外部の型を含むときは、引数でborrow・戻り値でownにする現在の規則を再帰的に適用し、Stateを要求する。言語内のMapからは鍵の順に一意な組を出す。戻り値は元の組を順に加えて後の値を採り、最後に鍵の順で保持する。重複した数を差し引く前の全組に受け渡しの予算を課す。そうしなければ、大量の重複を持つ戻り値で予算を逃れられる。

現行の「一つの操作で作る値の大きさの上限」はString・Bytes・Listに当たり、Map・Setの要素数には当たらない（02-09「一つの操作で作る値の大きさの上限」、`src/typeck/consts.rs:449` の注記）。今回のmapに存在しないMap固有の上限を当てず、外部の受け渡しの予算で組の数と内側の値を制限する。動的な経路では少なくとも各組の二つのValと内側の値の費用を数え（W3）、要素数からの費用計算に溢れがあれば確保前に拒否する。これはプロセス全体のメモリの上限を保証するものではない。全組をいったんList[Pair]にすることは要件にせず、既存のカーソルと挿入・構築のAPIを通す。検査と実行は共通の `external::engine_config` でmap機能を明示的に有効にする。

### 5.3 型引数を持つ型

型パラメータを持つレコード・dataも、外部の関数の宣言で具体的な型引数が決まれば、WITの具体的な型に照合できる。WIT側に多相な型を追加するという意味ではない。

推す例は `Box[T]` のvalue欄にIntegerを与えた `Box[Integer]` を `record box { value: s64 }` にする対応である。外部の関数自体はこの具体的な型をシグネチャに書く。パラメータ・エフェクト変数・未確定の型構成子を残す外部のシグネチャは、引き続き静的に拒否する。

| 案 | 利点 | 費用・中核への影響 |
|---|---|---|
| 具体的な型引数を欄の型へ置き換えて照合する（推す） | 同じレコード・dataを言語内と外部の境界で使える。コピーの型宣言を減らせる | 型展開と診断の作業が要る。型ごとのRustの具体化は要件にしない。検査時の型展開は増えるが実行時の型は既に固定できる。言語内の多相・VM・Leanの規則は変えない |
| 現行の一律拒否を保つ | 実装と照合が簡単 | 境界用の型を作り直す量が増え、欄の変更の反映漏れが起きやすい。中核への影響はない |

再帰の検出を今のBindingIdだけで行う形のまま広げると、有限の `Box[Box[Integer]]` を再帰と誤判定する。宣言の欄に現れる名付けた型どうしの循環と、型引数を通した有限の入れ子を区別する必要がある。

実装案は、まず型パラメータを葉として扱った宣言の依存関係を調べ、展開して使う型の宣言の循環を拒否することである。`Box[T]` の欄のTにはBoxへの循環がない。`Nest[T]` の欄が `Nest[List[T]]` なら宣言自身への循環がある。その後、具体的な型引数を代入して展開する。再帰の検査は標準のListやOptionを通る依存も調べる。実際の到達する型に対して検査し、使わない宣言の循環だけで外部の宣言を拒否しない。

型引数を渡された型をさらに展開する場合にも深さと節点の予算を課す。共有する展開の結果を再利用しても予算の意味は現行どおり「型の出現ごと」に保つ。置き換えのために大きなTyの木を無制限に複製してから予算を数える実装は避け、型引数の環境を持って欄を辿る段階から数える。具体的な型を鍵にする場合は型のハッシュや表示自体の費用も制限する。

### 5.4 三要素以上の組と複数引数の構成子

3要素の組は既にTripleで渡せる。残る課題は、4要素以上の平らなtupleと、利用者のdataの複数引数の構成子である。WITのvariantの各場合のペイロードは高々一つなので、複数の値をその一つのtupleへまとめる。

| 案 | 利点 | 費用・中核への影響 |
|---|---|---|
| 一つの構成子を持つdataをtupleへ写し、variantの複数引数もtupleへまとめる（推す） | 任意の要素数を既存のdataで表せる。Pair・Tripleと同じ構成子の値を使える | 境界の変換表と構成子のタグの保存を拡張する。言語内の型・構文・Leanを変えない。各形のRustの具体化を要件にしない |
| Four・Fiveなどの標準の型を追加する | Pair・Tripleからの説明が容易 | 新しい標準モジュールとSkillが増え、要素数の上限を別に決める。型の数を増やしても全てのtupleを扱えない |
| 任意の長さのtuple型と `(a,b,c,...)` を言語に追加する | WITと同じ形で書け、要素数を選ばない | パーサ・型検査・パターン・脱糖・VM・Leanの拡張が要る。既存のPair・Tripleとの関係も決める。作業と実行ファイルの追加が最も大きい |
| 明示のrecordかPair・Tripleにまとめた構成子だけを許す | 現行の照合をほぼ保てる | 外部の既存の平らな4要素以上のtupleを扱えず、コピーの型が増える |

推す例は、言語側で一つの構成子 `Coordinates(Integer, Integer, Integer, Integer)` を持つdataを宣言し、WITの `tuple<s64,s64,s64,s64>` に照合する形である。tupleには名前付きの項目がないので、構成子の名前は照合せず、引数の数・順・型を照合する。レコードは名前を契約にするので、tupleへ暗黙に写さずrecordに対応させる。

variantの例は、dataの `Rectangle(Float, Float)` を `rectangle(tuple<f64,f64>)` に写す形である。引数が0個ならペイロードなし、1個ならその型を直接ペイロードとし、2個以上なら平らなtupleにまとめる。Unitを省略する一般規則は足さない。Resultの省略と関数の戻り値のUnitだけを現行の特例に保つ。

既存の `OnePair(Pair[Integer,Integer])` のような1引数の構成子と、`Two(Integer,Integer)` のような2引数の構成子は、同じWITのペイロードの形に対応しうる。戻り値をどちらに組み直すかは宣言の型で決める。変換表には、単一ペイロードを一つの言語の欄へ置く形か、tupleの各成分を構成子の複数の欄へ置く形かを明記する。途中で作業用の言語のPairを確保する必要はない。

一つの構成子のdataが、WITのtupleとvariantの両方に候補を持つ場合は、WITの実際の型の種類で対応を選び、確定した種類を変換表に残す。現在はコンポーネントを読む前に宣言から対応表を作るので、この段階でtupleかvariantの一方に決め打ちしない。従来受け渡せた1構成子のvariantをtupleに変えてしまわないようにする。

0要素のtupleは言語のUnitと同一視せず、今回の追加の対象にしない。1要素のtupleは1引数の構成子を持つdataなら同じ規則で表せる案とするが、コンポーネントの版ごとの受理と、標準のPair・Tripleの特例との優先順位を照合の確認条件に含める。平らな組の要素数には型の節点の予算を適用する。

### 5.5 合成の型の費用と調査Bへ渡す条件

flags・map・型引数・複数引数の構成子を既存の型で表す案なら、主な変更は `external::{types,convert,mod,stats}`、照合の診断、03-10と02-09、利用者向け文書である。flagsとmapで各1〜2作業、型引数の置き換えと循環の検査で2作業、tupleと複数引数の構成子で1〜2作業、統合で1作業、計6〜9作業が目安である。調査Bの実装との共通部分があるので、数の型の見積もりと単純に足して全体の期限にはしない。

新しい言語の中核の構成は不要でも、受け渡しの性能はそのままでは改善しない。動的なAPIならレコード・variant・flagsで名前の文字列を作り、list・tuple・mapでValを作る（W1）。[フェーズ2の測定](../../../tools/bench/results/2026-10-13-wasm-efc47689.md) では6 MBのList[Byte]は約2.8 GBのRSSと193 msを要した。[TODO-240の短い測定](../../../tools/bench/results/2026-10-13-typed-list-f8a7470e.md) では、型付きの経路で受け渡し量は240,000,000から6,000,000バイト、RSSは290 MiB、時間は約53 msになった。残る言語のリストの保持の費用は型の名前を増やすだけでは減らない。

調査Bの方式には次の条件を渡す。

1. 型の対応表は、新しい基本型七種とflags・map・任意の要素数の組・構成子のまとめ方を表せること。型引数は照合で具体化し、実行時に未確定の型を残さないこと。
2. 既存の型の言語内の値の表現を正準ABIと同じにすることを前提にしないこと。外部の呼び出しのための型ごとのRustの全組み合わせを増やすことも前提にしないこと。
3. 型の照合の予算、実行時の要素数の上限、受け渡しの両方向の予算を、入れ子の新しい型にも適用すること。mapの重複は縮める前、flagsは選んだ全項目を数えること。
4. 外部の型のborrow・own、State、値の根の保持、回収しない区間、UTF-8の検査、ゲストの開始より先に引数の誤りを報告する順序を守ること。
5. 新方式の実行ファイルの増分と、数の型の実装の増分を分けて比較できること。公開のAPIで実現できない場合は、動的な経路の費用が残る型を明記すること。

## 7. 推す案どおりにする点

以下は設計者に独立の判断を求める細部ではなく、前節で選んだ案を具体化するための提案である。前節と異なる案を選んだ場合は、該当する点を合わせて改める。

1. Integer・Floatの既存の値の範囲と精度を保つ。七つの新しい基本型の間にも暗黙の変換を入れない。s64・u8・f64との対応はInteger・Byte・Floatを使う。
2. 新しい整数は比較・表示・鍵の型、Float32はFloatと同じ等値・順序比較とNaNの規則を持ち、鍵にしない。新しい数を文字列補間の集まりに加え、toStringと同じ表示を使う。
3. u64は独立したu64の即値で保持し、toIntegerはほかの幅からの変換と異なりOptionを返す。上半分も作って渡せるようにparseとDecimalの正確な変換を用意する。一般のDecimalをWITの数の宣言型に自動対応させない。
4. Float32は別のf32の即値で保持する。fromFloatは4.2節の丸め・範囲外の規則に従い、toFloatは有限値を正確に広げる。NaNの追加情報の保持は保証しない。単精度の通常のListが小さくなるとは説明しない。
5. 案2を選ぶ場合はByteにも同じ整数の算術を持たせ、単項の負号は符号付きに限る。整数のdiv・modとFloat32の各演算の規則を4.3節どおり明記する。Rustの通常の演算の溢れの設定を言語の規則の代わりにしない。
6. 新しい基本型のリテラル・範囲パターンは設けず、比較のガードを使う。接尾辞案を選ぶ場合は式の定数としてのみ追加し、直接の負号と型ごとの範囲を静的に確認する。
7. 型の展開は具体的な型引数を欄へ代入する。循環する宣言とBoxの有限の入れ子を区別し、変化する型引数の再帰も拒否する。未確定の型・関数の多相・予算超過は静的に報告する。
8. flagsの項目、recordの欄、variantの構成子は現行の名前の正規化・順序・重複の検査を使う。tupleは成分の数・順・型だけを照合する。戻り値の言語の構成は宣言の型と確定した変換表から復元する。
9. mapの重複は全組を数えてから後の値を採り、鍵の順にする。WITの文書で確認した基本型の鍵だけを受け付け、検査と実行で同じmap機能の設定を使う。
10. resourceの借用・所有の方向、State、失敗後のStoreの破棄を既存の規則に保つ。新しい合成の型でも内側の外部の型を検出する。
11. 基本型を増やす実装はLeanの定義・性質1の証明・検査の関数を先に直し、01-12と07-04を同じ変更で更新する。境界だけの追加は07-04の外部の型の対象外の行に明記する。範囲と丸めの正しさを形式化で証明したと説明しない。
12. 実装時はSkillの生成元を直してgen_skillで再生成する。今回の調査では処理系・設計書・Skillを生成・変更しない。必要な確認条件は、数の範囲の両端、u64の上半分、f32の丸めと特殊値、mapの重複、flagsの空集合、具体的な型引数、有限の入れ子と再帰、4要素以上の組、借用・所有と上限である。テストを追加する段階でtest-auditに従い、既存の検査の責任との重複を避ける。
