# Z4・P37〜P40a（補助の合成の直し、文書、測定の道具）のレビュー

2026-10-14、Opus 5.5。範囲は `git diff 2d8da3f3 3d598c02`。cargo は走らせていない。

Z4 で G7 の High 1・Medium 1〜3・Low 1〜3 は直った（関数ごとの合成、インスタンス数の事前の見積もりによる動的な経路への振り分け、宣言ごとの別の予算、診断の欄の分離、統計）。テストを弱めた形跡はない。設計書は実装とよく一致し、規約違反（【未決】、まだない機能の記述、見出しの改名、リンク切れ）はない。重い問題は測定の道具に集中している。

## High

1. `examples/wit_transfer_cost.rs`: 段ごとの計時で、補助の経路は言語の値から転送形式への符号化を測るが、typed と dynamic は JSON から `Val` への読み込みを測り、処理系の動的な変換を測っていない。復号も例の中の関数を使う。このままでは dynamic と補助の比較に意味がない。動的な経路も処理系の変換の関数で計時するか、比較に使わないと記録に明記する。

## Medium

1. 比較の入力が typed の宣言と補助専用の宣言を同じファイルに置くので、P18 の版では静的検査でファイルごと使えず、typed の部分も測れない。開始前の版との比較（短い数・大きな Bytes）に道具が対応していない。旧い構文と型だけで書いた typed だけのスクリプトを別に置き、開始前の版も読めるようにする。
2. P36a の補助の版は Z4 の前なので、同じゲストに 18 の宣言を置く入力がインスタンス数の上限で実行時に失敗しうる。道具は実行の失敗を例外として扱い本測定全体が止まる。保存した版の実行の失敗も分類して記録する。
3. CLI の測定の入力は一つの実行で typed と補助の両方を呼ぶので、大きい入力で経路ごとの時間と RSS を分けられない。経路ごとに一つの宣言だけを呼ぶ設定を足すか、計時の例に大きい入力を足す。
4. 言語リファレンスの `dynamic` の行と CHANGELOG に、G7「文書に書くこと」の一部（インスタンス数の見積もりによる振り分け、関数ごとの合成、補助が使うインスタンス 3 個、補助のメモリが約 3〜4 倍で既定の 64 MiB に達しうること、経路による trap の文言の違い、typed と dynamic は `incomplete_calls` を増やさないこと）が抜けている（設計書には書いてある）。

## Low

1. `external/adapter/component.rs` の `core_instances`: 未知の Payload で検査全体が内部エラーになる。保守的に上限の値を返して動的な経路へ回す。
2. `wit_transfer_cost.rs`: 補助のインスタンス化の時間に `Linker::new` を含めており、本番より大きく出る。
3. `wit_transfer_bench.py`: `--quick` でも保存した版の manifest がないと失敗する。
4. 01-04「型の一覧」の前の段落に確度の印がない。

## 確かめて問題がなかった点

03-10 の型の対応の表、三つの経路と振り分けの順、関数ごとの合成の鍵、宣言ごとの予算と E1010 の位置、補助のメモリとインスタンスが Store の上限に数えられること、経路ごとの受け渡しの量の数え方、取り込みのないゲストに限ること、trap の分類と文言の注記は、Z4 のコードと一致する。01-spec の接尾辞・別名・表示名・演算子の表は stdlib の参照と一致し、実装方式の記述は入っていない。言語リファレンスの接尾辞の節には仮の形である旨がある（Q3）。
