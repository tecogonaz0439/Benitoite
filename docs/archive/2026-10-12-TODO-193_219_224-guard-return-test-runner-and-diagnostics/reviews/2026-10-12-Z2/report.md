### 誤った型の名前の反例を探した結果

机上では次の経路を調べ、どれも「真の型を含まない候補から一つに決まる」か「別の起動の型引数で置き換える」に至らないことを確かめた。

- **e2 の最初の段**: 組み込みの関数は `Io` の命令で呼び、枠を作らず末尾呼び出しにもならない（vm/dispatch/handlers.rs:47–64）。したがって確認の時点の最も内側の枠は、確認を実行している起動である。ラムダ・`handle` の本体と節・`lazy` の本体は別の原型に移す（02-07）ので、最初の段で止まる。`with` の本体は同じ原型の中にあり、同じ起動として扱って正しい（`p6.bnt` の 3 件目で名前が出る）。
- **e2 の次の段**: `CALL` の呼び出し元の枠は、呼ばれた枠が戻るまで一つ外側に残る。継続の一番外側の枠は `handle` の本体（`HANDLE` で呼ぶ）か、それを `TAILCALL` で置き換えた枠であり、呼び出しの位置が `CALL` にならない。そのため、`resume` で継続を別の枠の上に戻しても、`CALL` の条件で止まる。`TAILCALL` の枠の呼び出しの位置は末尾呼び出しの命令を指すので、多相の自分への末尾呼び出しでも正しい（`selftail.bnt` は 2 件とも `Color.Red`・`Color.Green`）。
- **呼び出しの位置の表**: `calls` の鍵の span はファイルを含み、`callee == binding` で照らす。部分適用の閉包・関数を値として渡す・括弧・パイプの経路では、枠の呼び出しの位置が合成のラムダか組み込みの関数の命令になり、表に項目がないか、命令の原型が呼び出しを書いた関数の原型と違うので止まる。
- **e3 の完全性**: トップレベルの関数の起動は、どれもその関数の名前の使用から生じる。`Collector::expr` は式の種類をすべて辿り（`match` に `_` がない）、引数の `_`（`Arg::Placeholder`）は式を持たない。型クラスの宣言は本体を持たず、関数の引数に既定値はない。局所の束縛は多相にならない（01-06）ので、使用の型引数の中のパラメータは、書いたトップレベルの関数のものである。実装のメソッドと定数の中の使用は、具体的な型なら候補に入り、パラメータを含めば決めない。
- **重なりを除く鍵**: パラメータを含む項目は `(型引数, 書いた関数)`、具体的な項目は型引数だけで除く。パラメータの意味は書いた関数で決まるので、この鍵で別の候補を一つにまとめることはない。循環する項目は `seen` の鍵に深さを残し、深さ 8 で決めない側に倒れる。

## 所見

### 重大

### 中

1. **文書の「一段の末尾呼び出し」「二段以上続いた場合」が実装と食い違う**（02-11:61・65、06-04:146・148、`docs/reference/benitoite.md`:737・739、CHANGELOG.md:83）。
   - 問題点: 型パラメータを持つ関数 `twoStep[T]` が末尾で `checkSame(a, b)` を呼ぶと、`twoStep` の枠が消えるので、`twoStep` の型引数は枠から分からず、e3 に移る（`p7.bnt`。テストは `twoStep` を普通に呼び、`twoStep` を `Dir` でも使うと型不明になる）。型パラメータを持つ関数どうしの末尾呼び出しは一段だけである。しかし 02-11 は「二段以上続いた場合」に枠から決まらないと書き、06-04・言語リファレンス・CHANGELOG は「一段の末尾呼び出しでも型を求められる」（including a single tail call）と書く。読み手は、補助の関数の最後の行で別の補助の関数を呼ぶ最も普通の形でも枠から決まると読む。枠から決まる一段の末尾呼び出しは、具体的な型を書いた呼び出し（テストの関数の最後の行など）からの末尾呼び出しだけである。W5 からの記述だが、Z2 で書き直した文なので、ここで直すのがよい。
   - 修正案: 02-11 は「型パラメータを持つ関数が末尾呼び出しで別の関数を呼んだ場合（呼び出し元の枠が消え、その型引数が枠から分からない）や、関数を値として渡した場合など、枠から決まらないときは」とする。06-04 の「一段の末尾呼び出しでも型を求められる」は「具体的な型を書いた呼び出しが末尾呼び出しでも、型を求められる」とする。言語リファレンスと CHANGELOG は「including a tail call from a caller with concrete types」と「When a generic helper reaches the check through a tail call, its caller's type arguments are lost, so ...」の趣旨に直す。

2. **e2 が普通の `CALL` を辿って名前を決めることを確かめるテストがない**（`crates/benitoite/src/runtime/assert/tests.rs`）。
   - 問題点: 新しいテストは、どれも「誤った名前を出さない」側（正しい名前か型不明のどちらでも通る）である。既存の `generic_helpers_recover_constructor_names` の `twoLevels`・`nonTail` は、補助の関数をその型だけで使うので、e2 が最初の段で止まっても、e3 が同じ名前を出して通る。したがって、次の段へ進む条件（`Call`・一つ外側の枠の原型・呼び出しを書いた関数の原型）が誤って強すぎるようになっても、どのテストも落ちない。この条件は H1 の直しの中心であり、片側だけを確かめている。
   - 修正案: `p8.bnt` の形（形が同じ `Color` と `Dir` の両方で `outer[T]` → `checkTwice[T]` → `checkSame[T]` を普通に呼ぶ）を、両方の名前が正しく出る期待で一件加える。e3 では決まらない形なので、e2 の段の続け方を確かめられる。

### 軽微

1. **利用者向けの文書に処理系の内部の語が出る**（`docs/reference/benitoite.md`:737・739、SKILL.md:135、CHANGELOG.md:83）。
   - 問題点: 言語リファレンスの「even if an outer invocation has the same function prototype」の prototype は VM の原型の語で、利用者には意味が通らない。「Unexpandable uses」「Repeated uses of the same type count once toward the candidate limit」も、探索の実装の説明である。SKILL.md の読み手（LLM）が取る行動（比べる値の型を具体的にする）には要らない。
   - 修正案: リファレンスは「even if an outer call of the same function is still running」とする。SKILL.md は「Checks in generic helpers recover constructor names when the caller's types can be determined; otherwise ...」の程度に縮め、上限と展開の話を除く。CHANGELOG の上限の文は残してよい。

2. **`lazy` の中の確認を挙げている**（02-11:63、言語リファレンス:737、SKILL.md:135、CHANGELOG.md:83）。
   - 問題点: `lazy` の本体は純粋でなければならず（言語リファレンス:623）、`Assert.Check` のエフェクトを持つ確認は書けない。起こらない場合を挙げると、読み手は書けるものと読む。
   - 修正案: 「ラムダ・`handle` の本体と節の中の確認」とし、`lazy` を除く。

3. **02-11・06-04 の文の読みにくさ**（02-11:61、06-04:148）。
   - 問題点: 02-11 の「直後の枠」は、枠を内側から並べたときの次（一つ外側）を指すが、向きが読み取りにくい。06-04 の「全使用箇所の型引数を展開でき、値の形から一つに決まる型を使う」は、条件と使う型が一つの連体修飾に詰まっている。
   - 修正案: 「直後の枠」を「一つ外側の枠」とする。06-04 は「全使用箇所の型引数を展開でき、しかも値の形から型が一つに決まるときだけ、その型を使う」とする。

4. **`incomplete_instances` の説明が実際より広い**（assert.rs:52）。
   - 問題点: 「型コンストラクタの引数など、全使用箇所を展開できない関数」とあるが、この集まりに入るのは型引数に `TypeArg::Head` を含む使用がある関数だけである。実装のメソッドの中の使用は、`concrete_instances` の `writer?` で別に扱う。
   - 修正案: 「型引数に型コンストラクタを含む使用がある関数。その使用を候補に写せないので、候補の集まりが欠ける」とする。

5. **改造のディレクトリに Z2 の判断が残っていない**（`docs/2026-10-12-TODO-193_219_224-guard-return-test-runner-and-diagnostics/decisions.md`）。
   - 問題点: W5 のレビューの H2 は、補足 7 の「捨てる」を「決めない」と読むことを改造の記録に残すよう求めた。また、修正案より強い「`CALL` に限る」条件の理由（消えた起動と外側の起動が同じ関数なら原型の一致では防げない）、L1 を直さない判断、ラムダの中の確認が使用箇所の候補だけを使うことによる精度の低下（補助の関数を形が同じ二つの型で使うと、ラムダの中の確認は型不明になる。W5 では偶然正しく出ることが多かった）も、どこにも書いていない。実装者は改造のディレクトリを変えていない（指示の範囲外）。
   - 修正案: オーケストレータが decisions.md の Q3・R6 の後に、上の四点と理由を書き足す。ラムダの中の確認の精度を上げる方法（閉包を作った起動の型引数を記録するなど）は、必要なら docs/todo の項目にする。
