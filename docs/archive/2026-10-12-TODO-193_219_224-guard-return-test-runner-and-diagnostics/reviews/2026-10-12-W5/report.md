# W5（8cb1b9a7）のレビュー

対象: コミット `8cb1b9a7`（Recover constructor names in Assert reports from static types）。`crates/benitoite/src/runtime/assert.rs`・`runtime/assert/tests.rs`・`vm/dispatch/handlers.rs`、02-11・06-04・言語リファレンス・SKILL.md・CHANGELOG。照らした文書は `plan.md`「作業 W5」、`decisions.md` の Q3・R6、`study.md` B 部 2 節、事前点検の補足 `W4W5-pf.md`「W5 への補足」、実装者の報告 `W5-report.md`。実行の確かめは `target/debug/benitoite test`（W5 を含むビルド）で行い、入力は `orch9/w5r/` に置いた。

## 結論

差し戻す（重大 2 件）。計画の範囲・凍結の扱い・規約・性能はおおむね良い。`orch9/b/ctor.bnt`・`ctor_nontail.bnt` は全件が名前で書かれる。ただし、誤った型の名前を示す反例を、実行で 3 つ作れた。

- 末尾呼び出しで呼び出し元の枠が消えた後、e2 が同じ関数の別の起動（外側の枠）を拾う（H1）。
- 逃げた閉包を、同じ関数の別の起動の中で呼ぶ（H1）。
- e3 が実装のメソッドの中の使用を黙って捨て、残った一つの候補を採る（H2）。

どれも「左右の値の形に合う」ことで誤りが通る。形が同じ二つの型（`Color`＝`Red`/`Green` と `Dir`＝`Up`/`Down`）で、`Color` の値を `Dir.Up` と書く。06-04 が掲げる「決まらない型の名前を推測して報告しない」に反する。H1・H2 を直し、反例を退行のテストに加えるまで取り込まないことを勧める。

## 観点ごとの確かめ

### (1) 計画と判断との一致

- 凍結した型で触れたのは、`AssertTable` の欄の追加（`owners`・`calls`・`instances`）と、`evaluate` の引数の追加（`program`・`frames`）だけである。`render_value` のシグネチャ、`CheckFailure`・`AssertVerdict` は変えていない。新しい公開の型は `CallTypeArgs` で、補足 3 の例のとおりである。補足 4 の方式（引数を足す。閉包で渡し、失敗のときだけ呼ぶ。`Passed` の枝で窓を取り直す）のとおりである。
- e1（`has_params` のフィルタを消す）、R6（実行器だけの `text::UNKNOWN_CONSTRUCTOR`。共有の `base::literal` の定数は変えない）、文書の追記の位置（02-11「テストの実行」と 06-04「結果の報告」の箇条。`###` は足さない）も、補足どおりである。
- 補足 7 は「実装のメソッドの中の型パラメータを含む項目も捨てる」とした。実装はこれを文字どおり行った。しかし「捨てる」を「候補の集まりから黙って除く」と読むと、集まりが不完全なまま一つに決まる（H2）。補足の書き方にも原因がある。正しくは「捨てる＝決めない（候補を使わない）」である。実装者自身も、探索の上限を超えたときは「未探索の候補が曖昧さを生む」として途中の候補を使わない。この扱いと一貫していない。

### (2) 正しさ

- **e2 の枠の辿り方**（`recover_type`、assert.rs:635〜）: `remaining.find(|frame| frame.proto == proto)`（658 行）は、外側へ向かって同じ原型の枠を探す。その枠が、いま辿っている呼び出しの直接の呼び出し元であるかは確かめていない。末尾呼び出しで呼び出し元の枠が消えていると、同じ関数のもっと外側の別の起動の枠を拾う。確認がラムダの中にあるときも、最初の段で同じ問題が起きる。後の照合（`fits`）は、形が同じ型を区別できないので防げない（H1）。
- **型引数の置き換え**: `substitute` は `Ty::Param(i)` を `args[i]` に一度だけ置き換える。代数的データ型の構成子の欄の置き換え（`fits` の `substitute(ty, &args)`）も一段ずつ行うので、変数の取り違えはない。`calls` の鍵の `Span` は `file` を含む（base/mod.rs:50）ので、モジュールをまたいでも衝突しない。束縛は `BindingId` で区別するので、同じ名前の関数も混ざらない。
- **e3 の判定**（`recover_type` の後半）: 左右の両方に合う候補が二つ目に見つかった時点で、置き換え前の型を返す。「両方に合うものが一つだけ」のときだけ採っており、判定そのものは正しい。ただし、真の型が候補の集まりにあることが前提である。集まりが欠ける経路が二つある（H2）。
  - `concrete_instances` の 724 行は、`writer` が `None`（実装のメソッド・定数）か使用のない関数のとき、型パラメータを含む項目を `continue` で捨てる。
  - `Collector::instance`（476 行）は、型引数に `TypeArg::Head` を含む使用を記録しない（490 行）。
- **`fits` の 4,096 ステップ**: 真の型が候補にあれば、真の型は必ず合う。上限で打ち切られた別の候補が「合う」とされても、二つ合うので決まらない側に倒れる。打ち切りが誤った名前を生むのは、候補の集まりが欠けているとき（H2）か、e2 が誤った枠から置き換えたとき（H1）だけである。H1・H2 を直せば、上限の扱いは安全である。`fits` は `render_typed` と同じ基準で判定する（組み込みの型の分類 `Basic`・`Collection`・`Opaque`・`Resource` をすべて扱う）。真の型を誤って退ける経路は見当たらない。
- **深さ 8・項目数 64**: 打ち切ったときに `None`（決めない）を返すので、安全である。ただし、64 の判定を重なりを除く前の使用の数で行う（706 行）。そのため、同じ型で 65 回使った補助の関数では、e3 が働かない（M1。実行で確かめた）。自分を呼ぶ型パラメータの関数は、自分への使用 `[Param(0)]` が循環になり、必ず上限に当たって決まらない（L1）。
- **実装のメソッド**: 確認が実装のメソッドの中にあるときは `owners` に載らないので、復元しない。その扱いは安全である。問題は、実装のメソッドが型パラメータのある補助の関数を使うときに、e3 の材料から黙って落ちることである（H2）。
- **成り立つ確認の経路**: `values_equal` の後に早く返すので、型の復元の処理は通らない。

反例（実行で確かめた。どれも左右の真の値は `Color.Red`・`Color.Green`）:

| 入力（`orch9/w5r/`） | 形 | 出力 |
|---|---|---|
| `tail_wrong.bnt` | `viaTail[Dir]` の中のラムダで `viaTail[Color]` を呼び、その末尾で `checkSame` | `left: Dir.Up` / `right: Dir.Down` |
| `lambda_tail_wrong.bnt` の 1 件目 | 補助の関数 `each[T]` が末尾で `List.forEach(…, lambda … Assert.equal …)`。`each[Dir]` の中で `each[Color]` | `Dir.Up` / `Dir.Down` |
| `escape_wrong.bnt` | `keep[Color]` が返した閉包を `keep[Dir]` の起動の中で呼ぶ | `Dir.Up` / `Dir.Down` |
| `impl_wrong.bnt` | `implement[T] Check[Option[T]]` が `twoStep(a, b)`、`twoStep` が末尾で `checkSame`。別のテストで `twoStep(Option.Some(Color.Red), …)` | `Option.Some(Color.Red)` / `Option.Some(Color.Green)`（真の値は `Dir.Up`・`Dir.Down`） |
| `many_uses.bnt` | `twoStep(Color.Red, Color.Red)` を 64 回、失敗は 2 段の末尾呼び出し | `<constructor #0 of an unknown type>`（1 回に減らすと `Color.Red`） |

### (3) 性能

- 成り立つ確認: `evaluate` は比較の後すぐに返す。足した費用は、閉包を作ることと、`assert_check`（`#[cold]`）の `Passed` の枝で窓を取り直すことだけで、無視できる。`run` の経路は `AssertTable` を持たないので変わらない。
- `AssertTable::build`: 利用者のモジュールの宣言を一度余計に辿る（関数の束縛の集合を作る）。名前のノードごとに表を引き、型引数を写す。費用はファイルの使用の数に比例し、ファイルごとに一度である。問題ない。
- 失敗の経路: 枠を `frames()` と `stop_info` で二度集める（補足どおり）。`recover_type` は、段ごとに `program.top_fns` を線形に探す（652 行）。深い再帰（自分を呼ぶ補助の関数）では、枠の数×トップレベルの関数の数になる（L2）。失敗のときだけなので軽微である。

### (4) 実装の規約

- `unwrap`・`expect`・添字はない。実行時の値を辿る `fits` は、明示の積み重ねで書いている。`concrete_instances` も積み重ねである。`Ty` を辿る `has_params`・`substitute` の再帰は、AST と同じく型の木を辿るもので、許される。
- 文言 `UNKNOWN_CONSTRUCTOR` は `text` に置いた。大域の状態はない。`as` の変換はない（`usize::try_from` を使う）。
- コメント: `recover_type` に、手順（e2→照合→e3）を説明するコメントがない（L3）。

### (5) テストの質（test-audit の観点）

- 新しい振る舞いを、VM を通した `CheckFailure` の境界で一度ずつ確かめている。実装者は、直す前のコードで落ちることも報告した。ゴールデンを足さない判断も、補足どおりである。
- `numberChoice`・`textChoice` は、右の値の形で初めて決まる場合を確かめる。`sharedUnknown` は、`fits` の上限が働くこと（指数的な照合が終わること）を確かめる。どちらも関門として価値がある。
- 欠けているのは、誤った名前を出さないことの確認である。H1・H2 の反例の形（別の起動の枠を拾う、逃げた閉包、実装のメソッドの中の使用）を、「名前を出さない（unknown になる）」期待で加えるべきである。今のテストは「決まるべきものが決まる」側に偏っている。

### (6) 文書と実装の一致、文章

- 02-11 の手順は、実装の手順（e2→形の照合→e3、決まらない位置は形から）と一致する。ただし、「確認を書いたトップレベルの関数の枠の呼び出しの位置」が、実装では「外側で最も内側の同じ関数の枠」になっている。直接の呼び出し元であることの条件がない（H1 を直すときに、02-11 の文も直接の呼び出し元に限ると書く）。
- 06-04 の理由「決まらない型の名前を推測して報告しない」は、H1・H2 の反例で破られている。直せば一致する。
- 02-11 の【決定】「探索する項目は 64 個まで」は、重なりを含む使用の数で数えているのか、展開した項目の数なのかが読み取れない（M1 を直すときに、重なりを除いた数と書く）。
- 実装のメソッドの中の確認を復元しないことは、どの文書にも書いていない（L4）。
- 言語リファレンス・SKILL.md・CHANGELOG の英文は、実装の振る舞いと合っている（H1・H2 を除く）。日本語の文は常体で、規範に反する表現は見当たらない。

## 所見

### 重大

- **H1** `crates/benitoite/src/runtime/assert.rs:658`（`recover_type` の e2 のループ）。問題点: 枠を `find` で外側へ探すので、末尾呼び出しで直接の呼び出し元の枠が消えたとき、同じ関数の外側の別の起動の枠を拾い、その呼び出しの型引数で置き換える。確認がラムダの中にあるとき（最初の段）も同じである。逃げた閉包を同じ関数の別の起動の中で呼んだときも、別の起動の枠を拾う。形の同じ型は `fits` を通るので、誤った型の名前を示す（`tail_wrong.bnt`・`lambda_tail_wrong.bnt`・`escape_wrong.bnt`）。修正案:
  - (a) 最初の段は、`frames[0].proto` が確認を書いた関数の原型と等しいとき（確認が関数の本体に直接あるとき）だけ e2 を使う。ラムダ・`handle`・`lazy` の中なら e2 を使わず e3 へ進む。ラムダの定義元の起動は、枠からは決められないためである。
  - (b) 次の段は、`frame.call_site` の `at.proto` が、`frame` の直後の枠の原型と等しく、かつ呼び出しを書いた関数の原型であるときだけ続ける。そうでなければ（末尾呼び出しで枠が消えたか、ラムダの中から呼んだ）、`owner = call.owner` で e2 を止め、e3 へ進む。
  - 反例 3 つを「`<constructor #n of an unknown type>` になる（または e3 で正しく決まる）」期待のテストとして加える。02-11 の文も「直接の呼び出し元の枠」に直す。
- **H2** `crates/benitoite/src/runtime/assert.rs:724`（`concrete_instances`）と同 490 行（`Collector::instance`）。問題点: e3 の候補の集まりが欠けたまま一つに決まる。
  - `writer` が `None`（実装のメソッド・定数）か使用のない関数のとき、型パラメータを含む項目を `continue` で黙って捨てる。
  - 型引数に `TypeArg::Head` を含む使用は、そもそも `instances` に載らない。
  - その結果、実装のメソッドを通って別の型で呼ばれた補助の関数を、ほかのテストの具体的な型で書く（`impl_wrong.bnt`: 真の値 `Dir` を `Option.Some(Color.Red)` と報告）。
  - 修正案: 展開できない項目に当たったら `None`（決めない）を返す。`Head` を含む使用は、その関数の集まりを「不完全」と印して、e3 で決めない（例: `instances` の値に不完全の印を持たせるか、別の `HashSet<BindingId>` を表の欄に足す。欄の追加は Q3 の了承の範囲）。補足 7 の「捨てる」も「決めない」と読むよう、改造のディレクトリの記録に残す。

### 中

- **M1** `crates/benitoite/src/runtime/assert.rs:706`・`concrete_instances` の `steps`。問題点: 64 の上限を、重なりを除く前の使用の数で判定する。同じ補助の関数を同じ型で 65 回使うと e3 が働かない（`many_uses.bnt`）。テストのファイルでは、補助の関数を何十回も使うのが普通の形である。修正案: 初めの項目を `(args, writer)` で重ならないように集めてから上限を判定する（具体的な項目は `args` だけで重なりを除いてよい）。02-11 の【決定】の「探索する項目」を「重なりを除いた項目」と書く。

### 軽微

- **L1** `concrete_instances`。問題点: 自分を呼ぶ型パラメータの関数は、自分への使用（`[Param(0)]`、`writer` が自分）を展開し続けて上限に当たり、e3 が決まらない。安全側だが、再帰する補助の関数で名前が出ない。修正案: `writer == owner` で、型引数が自分の型パラメータの恒等の並びである項目を飛ばす。または、展開済みの `(writer, args)` を記録して循環を除く。
- **L2** `crates/benitoite/src/runtime/assert.rs:652`。問題点: e2 の段ごとに `program.top_fns` を線形に探す。深い再帰では、枠の数×関数の数になる。失敗のときだけだが、`owner` が変わらない間は同じ探索を繰り返す。修正案: 前の段と `owner` が同じなら原型を使い回すか、`top_fns` から一度だけ表を作る。
- **L3** `crates/benitoite/src/runtime/assert.rs:635`。問題点: `recover_type`・`concrete_instances`・`fits` の手順と、安全側に倒す条件（何を見たら決めないか）を書いたコメントがない。H1・H2 の修正で条件が増えるので、なおさら要る。修正案: 各関数の前に、手順と「決めない」条件を、02-11「テストの実行」を根拠に数行で書く。
- **L4** `docs/design/06-tooling/06-04-test-runner.md:146`・`docs/design/02-impl/02-11-embedding.md:59`。問題点: 実装のメソッド（`implement` の中の関数）の中の確認では型を復元しないことが書かれていない。利用者には、補助の関数と同じく名前が出ない理由が分からない。修正案: 06-04 の箇条に「実装のメソッドの中の確認では、呼び出し元から型を求めない」と一文足す。言語リファレンスにも一文足す。
