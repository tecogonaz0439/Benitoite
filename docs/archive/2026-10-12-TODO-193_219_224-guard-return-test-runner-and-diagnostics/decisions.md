# 判断とその理由

調査（`study.md`）の後に、利用者から見える振る舞い・言語の規則・凍結した型に関わる四つの問いを設計者に尋ねた（Q1〜Q4）。Q2 のほかは推奨どおりの答えだった。作業の途中で、作業 W4 の範囲を尋ねた（Q5。W4 をやめた）。残りの点は、調査の推奨どおりとした（R1〜）。

## 設計者に尋ねた問い

### Q1 TODO-193: ガードの中のプレースホルダの呼び出しの引数の `return` を、どう扱うか

- 選択肢: 拒否を続ける／受け付ける。
- 設計者の答え: **拒否を続ける**（推奨）。
- 内容: 処理系の振る舞いは変えない。ガードと `lazy` の本体の中では、内側の `lambda … end lambda` の本体の中を除き、プレースホルダを含む呼び出しの呼ぶ関数と引数の中にも `return` と `try` を書けないことを、言語仕様（01-05・01-02・01-12）に書く。Lean の表層の型付けはこの形に型を付けるので、07-04「01-12 との対応」の表に、形式化のほうが広いことを書き足す。E0218 の助言を「`lambda ... end lambda` の中なら書ける」に改め、`_` の呼び出しの引数は例外にならないことを説明に加える。
- 理由: この形には使い道がなく、書いた人（LLM を含む）は囲む関数から抜けるつもりで書く見込みが高い（比べた言語のうちプレースホルダの書き方を持つ Scala は、この `return` を囲むメソッドからの return とする）。受け付けると、誤読したコードが型が合えば黙って通るので、設計原則 1・3 に反する（`study.md` の A 部 3 節）。
- 場所によらず一律に拒否する案（A 部 3 節の選択肢 C）は、Lean の定義と証明の手直しを伴うので、この改造では行わない。

- 設計者の答え: **並行の実行は TODO に残して将来に対応する。今回は処理系も設計書も今のままとする。**
- 内容: 処理系は一つずつ順に動かしたままにする。06-04 の「並行に動かしてよい」と 02-11 の「一つずつ順に実行する」の記述も変えない。並行の実行は docs/todo の項目に残す（調べた障害と測った時間は `study.md` の B 部 1 節）。

### Q3 TODO-219: `Assert` の報告の `<constructor #タグ>` をどう直すか

- 選択肢: 静的に型を復元する／表示の説明だけを足す／値に構成子の番号を持たせる。
- 設計者の答え: **静的に型を復元する**（推奨）。
- 内容: B 部 2 節の (e)。型パラメータを含む型でも具体的な部分は型に従って書く（e1）。失敗したときに呼び出しの枠を外へ辿り、各枠の呼び出しの位置で型検査が記録した型引数で型パラメータを置き換える（e2）。枠がないとき（末尾呼び出しなど）は、プログラムの中のその関数の型引数の集まりのうち、値の形に合う型が一つだけならその型を使う（e3）。決まらなければ、型が分からないことを示す表示にする（(d) の表示）。
- 凍結した型とシグネチャ: 凍結した `AssertTable`（10-18 の `file=`）に欄を足し、`evaluate`（10-18 の `sig=`）に枠を渡す形を加えることを、この問いの答えで了承を得たものとする。値の表現・バイトコード・ヒープは変えない。
- 理由: 型の情報は今も呼び出しの位置の静的な表から引いており、同じ仕組みを広げるだけで、調べた例はすべて名前で書ける。値に番号を持たせる案は、凍結した `Value` とヒープの内部の層に触れ、組み込みの関数の約 150 箇所を直す変更になり、`Assert` の表示のためだけには大きい。

## 推奨どおりとした問い

### R1 TODO-193: E0218 の文言は最小の案にする

A 部 3 節の選択肢 B の「最小」の案。構文解析器は変えず、助言の文と説明の文だけを改める。プレースホルダを含むかを `)` の後で調べて助言を替える「丁寧」の案は、選択肢 A と同じ保留の仕組みが要り、この形は稀なので行わない。`lazy` の本体の中の同じ形も、ガードと同じ扱いとして仕様に書く。

### R2 TODO-224 の 1: 表記を `base` の下の中立のモジュールへ移す

C 部 1 節の案 A。`quoted`・`escape_into` と `Show.show` の形の記号の表を `base` の下の新しいモジュールへ移し、型検査・テストの実行器・報告の書き出しがそこを引く。出力は変えない。`builtins/funcs/traits.rs` の写しの統一は、大きさの見積もりの直しを伴うので、作業で無理なくできるときだけ行う。

### R3 TODO-224 の 2: 本体の型の表示を一つの関数に集める

C 部 2 節の案 A。剛な型の名前の付け替えと、出力用の `finalize` の既定値を診断へ持ち込まないことを、本体の型を表示するすべての経路に当てはめる。剛な型の制約の help（`check_rigid_bound`）は、外側の関数でなく操作の宣言に制約を書く案内にする。

### R4 TODO-224 の 3: 波括弧のレコードは一件の E0212 と置き換え付きの help にする（Q5 で取り消した）

C 部 3 節の案 A。名前の直後の `{`（式とパターン）と、式の始まりの `{ 小文字の名前 :` を見つけ、対応する `}` まで読み飛ばして E0212 を一件にする。中身が「小文字の名前 `:`」か `..` で始まるときは、`{`→`(`、`}`→`)` の置き換えを付ける。そのほか（名前のない形、`=`、省略形、空）は文だけにする。

### R5 TODO-224 の 4: 移し替えの条件は制約の向きの決まりで判定する

C 部 4 節の案 A は、失敗した制約のどちらの側が変数を定めるパターンかを知る必要がある。事前点検で、`Reason`・`ReasonKind` が凍結の対象（10-05 の `file=src/typeck/infer.rs`）であり、`ReasonKind::Pattern` の制約を作る 6 か所はどれも `expected` が値の側・`found` がパターンの側であることを確かめた（`match` の分岐のパターンも同じ）。そこで `Reason` に印を足さず、理由が `Pattern` のときだけ `found` の側の記録を調べて移す。

### R6 TODO-219 の後半: 型の分からない構成子の表示

型が一つに決まらないときの表示は、タグだけの `<constructor #0>` をやめ、型が分からないことを読み取れる形にする（例: `<constructor #0 of an unknown type>`）。06-04 と Skill の文書に、型パラメータを持つ補助の関数では型が決まらないことがあり、そのときは比べる値の型を具体的にすればよいことを書く。

## 作業の途中でオーケストレータが決めた点

### R7 宣言の流れ込みの報告の位置: 使う側の失敗を後へ回す範囲（W3 のレビューの H1、Z1 のレビューの M1・M2）

W3 は、変数を使う側の失敗（呼び出しの引数など）をその場で報告するようにした。そのため、束縛の失敗を宣言へ移した変数を正しく使っている箇所に偽の E0401 が出て、本当の誤りが報告されなくなった（オーケストレータが再現を確かめた）。Z1 で使う側の失敗を後へ回し、Z3 で後へ回す対象を、束縛の失敗を宣言へ移した変数（の根）に当たる E0401 だけに絞った。範囲を広げすぎると、W3 の前は一件だった報告が二件になったり、先の誤りが後の誤りに入れ替わったりしたためである。変数を別の型に包んで使う形（`[s]`、`Option.Some(s)`）と演算子の被演算子（`s + 1`）に残る偽の報告は、この改造では直さず docs/todo の項目にした。Q4 の「報告の位置の取り違えを直す」の中の判断として、設計者に尋ねずに決めた。

### R8 `Assert` の型の復元で確信できないときの扱い（W5 のレビューの H1・H2、Z2 のレビューの軽微 5）

W5 は、同じ関数の別の起動の枠を拾う場合と、候補の集まりが欠けたまま一つに決まる場合に、誤った型の名前を示した。決まりを「誤った型の名前を示すより、型が分からないことを示す」とし、Z2 で次のように直した。

- 枠を使うのは、確認がその関数の本体に直接あるときだけとする。呼び出し元へ進むのは、呼び出しの命令が普通の `CALL` で、その原型が直後の枠の原型と同じときだけとする。末尾呼び出しで消えた枠と、残った別の起動が同じ関数のときは原型が一致するので、原型の一致だけでは区別できないためである。
- 展開できない使用（実装のメソッドの中の使用、型構成子の引数を含む使用）がある関数は、実体の集まりを不完全とし、それでは決めない（W5 のレビューの「捨てる」を「決めない」と読んだ）。
- 自分を呼ぶ型パラメータを持つ補助の関数で型が決まらない点（W5 のレビューの L1）は直さず、決まらない場合として文書に書いた。
- この結果、ラムダの中の確認や、型パラメータを持つ関数どうしの末尾呼び出しでは、W5 より型が決まりにくくなった。Q3 の範囲の中の判断として、設計者に尋ねずに決めた。
