### TODO-247 ラムダの終端省略・名前付き引数と、else・shadow を非推奨とする文書の改訂

- 状態: 方針あり
- 出どころ: 2026-10-14 の設計者との相談と TODO 追加の依頼

一行の短いラムダで `end lambda` が冗長になり、読みやすさを損ねるという設計者の指摘を受け、本体が単文かつ一行の場合に終端を省略できるようにする。同じ改造で、`if` の構文は維持し、`else` による分岐を文書上で非推奨とし、`match … with` を推奨する。また、`shadow` の構文とリファレンスでの紹介は残し、文書上で非推奨と明記する。

ラムダの方針:

- 本体が単文かつ一行で完結する場合に、`end lambda` の省略を認める。終端を付けた従来の形も引き続き認める。
- 本体が複数の文からなる場合、または複数行に書く場合は、従来どおり `end lambda` で閉じる。他の構文の終端省略は、この項目の対象にしない。
- 値を返す `return` の規則は維持する。最後の式を暗黙の戻り値とする規則は導入しない。戻り値が `Unit` の場合に本体の終わりで `()` を返す規則も維持する。
- 引数の型、戻り値の型、`uses` を明示する形でも、同じ条件で終端を省略できるようにする。型注釈とエフェクト推論の規則は維持する。

変更後の書き方の例（まだ現在の処理系では受け付けない省略形を含む）:

注（2026-10-14、設計者）: 次の例は、名前付き引数の方針（後述）を決める前に書いた。複数の引数を名前なしで渡しており、名前付き引数の方針と合わない。改造では、名前付き引数の方針に合わせて例とラムダの書き方を再検討する。

```text
List.map(xs, lambda(x) return x * 2)
List.map(xs, lambda(x: Integer) -> Integer return x * 2)
List.map(xs, lambda(x) return x * 2 end lambda)

List.map(xs, lambda(x)
  bind adjusted <- x + 1
  return adjusted * 2
end lambda)
```

実装前に決める点は、本体の終わりを判別する規則である。引数の区切りのコンマ、閉じ括弧、改行、演算子の優先順位、ラムダの入れ子、終端付きと省略形の混在を扱い、読み方が一意になる文法を定める。「単文」と「一行」の判定には、入れ子のブロックと継続行をどう扱うかも含める。短い形に文を追加したときに、意図と違う範囲を受け付けないよう、診断とフォーマッタの出力方針も定める。

`if` と文書の方針:

- `if … then … else … end if` と `else if` を含む現在の構文、型付け、実行の意味は変更しない。非推奨は文書上の案内とし、構文の禁止や処理系の警告は導入しない。
- `else` と `else if` による選択は非推奨とし、値や処理を選ぶ場合は `match … with` を推奨する。条件成立時だけの処理や早期リターンには、`else` のない `if` を推奨する。
- 同梱の Agent Skill（`crates/benitoite/skill/SKILL.md` と手で書く参照文書）、言語リファレンスなどの利用者向けマニュアル、設計書の説明と例に、この方針を反映する。既存構文が有効であることと推奨する書き方を区別し、ラムダの終端省略も同じ変更で説明する。
- 置き換えの説明では、条件の評価回数と順序、選ばれた分岐だけを評価すること、`return` の作用先を保つ。エフェクトや `return`・`try` を含む条件をガードに移さない。ガードの制約に当たる `else if` は、必要に応じて真偽値に対する `match` を入れ子にする。
- Skill の生成される参照文書は手で編集せず、生成元の変更後に `cargo run -p benitoite --example gen_skill` で作り直す。日本語訳はリリース時に英語版に合わせて更新する。

改造を始めるときは、文法と診断、構文解析器とフォーマッタ、必要なテスト、設計書と利用者向け文書の更新を実装プランに含める。形式化した範囲との対応は 07-04「01-12 との対応」の規則に従って判定し、範囲の内側なら処理系より先に Lean の定義と必要な証明を直し、範囲の外側なら対象外として記録する。

`shadow` と文書の方針（2026-10-14、設計者の追記依頼）:

- `shadow` は有効な構文として維持し、リファレンスで構文と意味を紹介する。その説明に非推奨であることを明記する。構文の禁止や処理系の警告は導入しない。
- 同じ局所名への束縛は原則一回とし、途中で得た値にはその意味を表す別の名前を付けることを推奨する。`shadow` による同じ名前の再利用は、必要な場合に限る。
- `bind` と `shadow` を分けた理由は、名前の再利用を明示させることに加え、意図的な再利用も意図しない再利用も抑えることである。この設計意図を、同梱の Agent Skill、言語リファレンスなどのマニュアル、設計書に反映する。
- `shadow` の用法を説明する例は残してよいが、非推奨であることを添える。一般の推奨例では別の名前を `bind` する形を優先し、`shadow` を通常の値の更新方法として案内しない。生成される Skill の参照文書と日本語訳の扱いは、上記の文書更新の方針に従う。

名前付き引数と関数型の方針（2026-10-14、設計者が推奨案を了承）:

- 関数呼び出しの引数を `名前: 式` で指定できるようにする。パラメータが二つ以上の関数では、すべて名前付きで指定し、名前なしの指定と混在を認めない。パラメータが一つなら、名前なしと名前付きのどちらの呼び方も認める。引数のない呼び出しは `f()` のままとする。
- 名前付き引数の記述順は宣言順と異なってよい。各パラメータを一度ずつ指定し、指定漏れ、重複、未知の名前は静的な誤りとする。デフォルト引数や引数の省略は、この方針には含めない。
- 呼ぶ関数の式を先に評価し、引数の式はソースに書いた順に左から右へ評価する。評価した値を宣言上の位置に対応付ける。名前による並べ替えによって、式の評価順序を変えない。
- 関数型にもパラメータ名を持たせ、関数を値として受け渡した場合も名前付きで呼び出せるようにする。パラメータ名と宣言順を型の契約の一部とし、型の適合では対応する位置の名前の一致を要求する。名前や宣言順が異なる関数型を暗黙に変換せず、引数の並べ替えや名前の読み替えのためのラッパーを自動生成しない。引数と戻り値の型、エフェクトの適合は既存の規則と整合させる。
- 公開関数のパラメータ名の変更も、名前付きで呼ぶ側との互換性に影響する契約の変更として扱う。標準ライブラリ、組み込みの関数、ラムダ、高階関数の関数型で使う名前を揃える。
- 名前と位置の対応付けは型検査・脱糖・コード生成の段階で完了させ、VM の呼び出しは位置による方式を維持する。呼び出しのたびの名前検索や引数用の辞書の確保は導入せず、関数・クロージャの値に呼び出しのためのパラメータ名を保持させない。指定順と宣言順が異なる場合の値の配置の費用と、コンパイル時の処理・メモリの増加は、実装後に確認する。実行時間への影響がないと測定前に断定しない。

例: `function add(a: Integer, b: Integer) -> Integer` に対し、`add(a: 1, b: 2)` と `add(b: 2, a: 1)` は認め、`add(1, 2)` と `add(1, b: 2)` は誤りとする。単一パラメータの `function increment(value: Integer) -> Integer` には、`increment(1)` と `increment(value: 1)` の両方を認める。

実装前に、名前を持つ関数型の表記と推論、部分適用のプレースホルダ、パイプラインで挿入する引数、型クラスのメソッド、エフェクトの操作、外部の関数との対応を定める。構成子や属性など関数呼び出し以外の位置引数への適用範囲も区別する。ラムダの終端省略の例を含め、既存の複数引数の呼び出し例・Skill・マニュアル・ソース・テストを新しい規則に合わせ、互換性を壊す変更として版と移行手順を扱う。上記の形式化との対応の規則も適用する。

包括的な分岐のパターンについての Skill の推奨（2026-10-14、設計者の追記依頼）:

- `match` の最後で、それまでの分岐が受けなかった値を受ける場合、同梱の Skill では `case _ -> …` より `case other -> …` のような名前付きのパターンを推奨する。記号だけの `_` より、残りの値を受ける分岐であることを読み取りやすくするためである。
- `other` は予約語や特別な構文ではなく、照合した値を束縛する通常の変数であることを説明する。分岐内でその値を使わない場合も、読みやすさのために名前を付けてよい。
- `other` という名前に固定せず、対象に応じて `otherCode` などの意味が分かる名前を選ぶ。外側で見えている局所名を隠すパターンは誤りとなるため、既存の名前と衝突しない名前を使う。
- `case _ -> …` は有効な構文として残し、構文や型付け、網羅性の規則、処理系の警告は変更しない。名前付きのパターンもすべての値に照合することを説明し、包括的な分岐の後に別の分岐を置かない。構成子の内部などに使う `_` や、部分適用・値を捨てる束縛の `_` 全般を非推奨にする変更ではない。
- Skill の案内と例に反映し、マニュアルなどの包括的な分岐の推奨例も整合させる。生成文書は生成元から作り直す。
