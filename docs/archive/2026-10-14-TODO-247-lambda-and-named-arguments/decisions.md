# 設計者への問いと判断の案

## 前提

[TODO の写し](todo-items.md) で了承済みの方針は、判断の前提とする。二つ以上のパラメータを持つ関数では全ての引数を名前付きにし、位置指定との混在を認めない。名前付きの指定順は自由だが、式の評価はソース順である。関数型のパラメータ名と宣言順は契約に含め、位置ごとの名前の一致を要求する。暗黙の名前の読み替えやラッパーの生成はしない。

`else`・`shadow`・包括的な分岐の `_` は、現在の構文と意味を維持する。文書上の推奨を変え、処理系の警告は加えない。この点への再承認を求める問いではない。

Q1〜Q15 は、2026-10-14 に設計者がすべて推す案で決定した。各問いの選択肢と理由は、判断の記録として残す。詳しい設計と命名表は [design.md](design.md)、作業の順序は [plan.md](plan.md) に記す。新たな問い R1 以降には設計者の回答をまだ得ておらず、今回の依頼に従って推す案を暫定の方針とする。Q の決定と R の暫定方針を区別する。推す理由は [00-01「目的と設計原則」](../design/00-overview/00-01-goals.md) に基づく。LLM の成功率を測った結論ではない。

## Q1 短いラムダを、どこで終えるか

答え（2026-10-14、設計者）: 推す案

問い: 終端を省く場合、どこまでが本体かを次の規則で決めてよいか。引数や型注釈を含むラムダ全体が一行であることも必要とするか。

| 選択肢 | 内容 |
|---|---|
| A（推す案） | ラムダの開始から本体の単文の終わりまでを、同じ物理行に限定する。単文の式を今の優先順位で読み、外側のコンマ・閉じ括弧・ブロック境界・行末で終える |
| B | 本体だけを一行に限定し、引数や型注釈は複数行でもよい。本体の開始と物理行の判定を別に定める |
| C | 論理的な一文なら改行や継続行も許す |

推す案は A である。理由: 書き手が字面から省略できる範囲を判断でき、改行後の文や演算子が意図しない範囲に入る場合を診断しやすい（原則 3・4）。TODO の「本体が一行」より厳しい制限なので、この追加条件を設計者が選ぶ必要がある。C は TODO の複数行では終端が要る方針を変更する案になる。

コンマや閉じ括弧は、内側の呼び出しを閉じるものではなく、短いラムダを置いた外側の式の区切りである。`lambda(x) return g(a: x, b: 2)` の `g` 内のコンマでは終えない。`lambda(x) return x + 1 |> increment` はパイプまで本体に入る。外側にパイプや呼び出しを付ける場合は `(lambda(x) return x + 1)` のように囲む。改行を空白として読む位置でも、その改行をまたぐ省略形は誤りにする。

単文は現在の文の規則を使う。一行で閉じた `if` や `match` が一つの式である場合は認め、入れ子のブロックを理由に全て禁じる規則は加えない。`return` は省かない。`Unit` の本体の終わりで `()` を返す規則も維持する。調査の根拠と例は [frontend.md](study/frontend.md) にある。

## Q2 ラムダを入れ子にし、終端付きと短い形を混ぜるときはどう示すか

答え（2026-10-14、設計者）: 推す案

問い: どちらのラムダの終わりか迷う形を避けるため、短い形を含む入れ子では内側のラムダを括弧で囲む規則にするか。

| 選択肢 | 内容 |
|---|---|
| A（推す案） | 外側か内側に省略形がある直接の入れ子では、内側のラムダ全体を括弧で囲む。両方が終端付きの既存の形は維持する |
| B | `end lambda` は最も内側のラムダを閉じると決め、括弧なしの混在も許す |
| C | 省略形のラムダの中にラムダを書けなくする |

推す案は A である。理由: `lambda(x) return lambda(y) return x + y end lambda` だけでは、書き手が内側と外側のどちらを短い形にしたつもりかを確認しにくい。括弧なら終わりを示せ、入れ子自体を禁じずに済む（原則 3・4・6）。B は文法として一意にできても、意図とのずれを検査できないことがある。

`lambda(x) return (lambda(y) return x + y) end lambda` は内側だけが短い形、`lambda(x) return (lambda(y) return x + y end lambda)` は外側だけが短い形になる。終端付きの本体へ短いラムダを束縛する場合や、別の呼び出しの引数として置く場合は、その構文の区切りを使う。全てのラムダを常に括弧で囲む案ではない。

## Q3 TODO の `List.map` の例に、名前付き引数の例外を作るか

答え（2026-10-14、設計者）: 推す案

問い: `List.map(xs, lambda(x) return x * 2)` は、名前付きの形に直すか。それとも短いラムダを渡す場合の例外を設けるか。

| 選択肢 | 内容 |
|---|---|
| A（推す案） | 例を `List.map(xs: xs, f: lambda(value) return value * 2)` に直す。通常呼び出しの例外は作らない |
| B | 第 1 引数を受け手として名前なしにし、残りを名前付きにできるようにする |
| C | 最後の関数引数、または標準ライブラリに限って名前なしを許す |

推す案は A である。理由: 了承済みの「二つ以上なら全て名前付き、混在なし」を保ち、関数や引数の種類で規則を分けずに済む（原則 4・5）。B・C は了承済みの方針を変更する選択肢であり、単に古い例を残すためには推さない。外側の契約名 `xs`・`f` は現在の宣言にあるが、内側の `value` は Q10 の候補である。

パイプを使う例は `xs |> List.map(f: lambda(value) return value * 2)` とする案になる。パイプから来る値をどう数えるか、重複をどう報告するかは Q6 で決める。

## Q4 関数の型に名前をどう書き、何を推論するか

答え（2026-10-14、設計者）: 推す案

問い: `function(value: Integer) -> Integer` のように、関数型の全ての引数に名前を必須とするか。呼ぶ関数の名前と順が分からない場合は注釈を求めるか。

| 選択肢 | 内容 |
|---|---|
| A（推す案） | 引数がある関数型には `名前: 型` を必須とする。宣言・ラムダから名前を取り、型とエフェクトは現在の規則で推論する。呼び出しだけで契約順を確定しない |
| B | 古い `function(Integer) -> Integer` も残し、使用箇所の文脈から名前を補う |
| C | 名前のない型は位置指定でしか呼べない関数型として残す |

推す案は A である。理由: 名前を契約に含める方針を、型の表記と一致させられる。B は文脈で契約が変わり、C は同じ役割の関数型と呼び方を増やす（原則 2・4・5）。引数がない型は `function() -> R` のままとする。

推論中の関数の契約が、宣言や他の型の制約から最終的に定まれば受け付ける。例えば未注釈の `g` への `g(b: 2, a: 1)` だけから `b`・`a` 順の契約を作り、後で `a`・`b` 順の関数を渡せなくする読み方は避ける。定まらなければ注釈を求める。この制約は使い勝手の負担になるが、名前と順序が一致する契約を保つ。根拠は [型の調査](study/types-and-calls.md) と [OCaml の公式の例](study/other-languages.md) にある。

## Q5 高階関数に渡すラムダの引数名も揃えるか

答え（2026-10-14、設計者）: 推す案

問い: `List.map` が `function(value: T) -> U` を要求するとき、`lambda(value)` を必要とし、`lambda(x)` には名前を直す案を示してよいか。

| 選択肢 | 内容 |
|---|---|
| A（推す案） | 全ての位置の契約名を一致させる。一引数でも一致が必要であり、実際に書いたラムダ名を型に残す |
| B | ラムダだけは期待する型の名前に読み替え、本体の局所名は自由にする |
| C | 呼ぶラベルと本体の局所名を別に書く構文を新設する |

推す案は A である。理由: 了承済みの名前の一致を適用し、契約の暗黙の変更を避ける（原則 2・4）。B は型の名前の読み替えを認める方針への変更になる。C は、`value` を契約名としながら本体では `line` と呼べる利点があるが、名前を書く場所と診断の規則が増える。今回は追加しない案を推す。

このため `List.map` に渡すラムダの名前は揃えなければならない。`line` のような用途固有の名前を直接の引数名に使うことはできず、必要なら本体で別名を `bind` する。既存の関数の名前が違えば明示のラムダで包む。使わない引数も期待する契約名に合わせ、単に `_unused` に変える案内を一律に出さない。これは短いラムダの記述量を増やしうる負担として、方針の意味を明記する。

## Q6 パイプで入る引数には、どう名前を対応させるか

答え（2026-10-14、設計者）: 推す案

問い: パイプは今と同じ第 1 パラメータへ入れ、残りの明示引数だけに名前を要求する規則でよいか。

| 選択肢 | 内容 |
|---|---|
| A（推す案） | 直接の穴がない呼び出しには第 1 パラメータを補う。複数パラメータなら、残りの明示引数を全て名前付きにする |
| B | 第 1 以外も含め、名前が未指定の唯一のパラメータへ自動で入れる |
| C | 自動の第 1 引数挿入を廃止し、必ず `対象名: _` を書く |

推す案は A である。理由: 現在のパイプの意味を保ちつつ、書き手が位置引数を混在させる例外を作らずに済む（原則 4・5・6）。B は引数を足したときに挿入先が変わり、C は既存の糖衣を広く壊す。引数が何個必要かは、パイプで補う値も含めた関数の宣言で決める。

`xs |> List.map(f: action)` は認め、`xs |> List.map(action)` は残りの名前がない誤りにする。`xs |> List.map(xs: ys, f: action)` は第 1 パラメータの重複である。直接の穴がある `xs |> List.map(xs: _, f: action)` は、Q7 の一引数の部分適用を呼ぶ現在の規則に従う。右辺を括弧で囲む場合も、現在どおり関数値への一引数適用にする。

パイプの評価は左辺、右辺の関数の式、明示引数のソース順とし、左辺を一度だけ評価する。通常呼び出しと同じ順だという説明に置き換えない。

## Q7 `_` から作る関数の引数名と順をどう決めるか

答え（2026-10-14、設計者）: 推す案

問い: 名前付きの穴の引数名を、元の関数の契約名にし、穴をソースに書いた順で並べてよいか。

| 選択肢 | 内容 |
|---|---|
| A（推す案） | `f(a: _, b: 2)` の穴は契約名 `a` を引き継ぐ。複数の穴はソースでの出現順に並べる |
| B | 穴を元の宣言の順に並べ、契約名を引き継ぐ |
| C | 生成する契約名を `arg1`・`arg2` などにし、元の名前を引き継がない |

推す案は A である。理由: 現在の「穴を左から順に引数にする」規則を保ち、型に出る名前を元の指定から判断できる（原則 2・4・5）。B は、ソース順と生成する契約順の関係を変える。C は意味が分かる名前を失う。

`f(b: _, a: _)` は `function(b: B, a: A) -> R` になる。`function(a: A, b: B) -> R` を要求する場所へ渡すなら、穴の指定順を揃える必要がある。固定引数と呼ぶ式を評価する時期は、作った関数を呼ぶときのままとする。穴が二つなら、パイプで一つだけ値を渡しても不足であり、自動の再部分適用にはしない。直接の構成子の穴は位置指定のまま、Q9 の位置名を使う。

## Q8 名前付き引数をどの呼び出しに適用するか

答え（2026-10-14、設計者）: 推す案

問い: 通常の関数、組み込み、ラムダや関数値、型クラスのメソッド、エフェクトの操作、外部の関数に同じ規則を適用し、構成子・属性・束縛は区別してよいか。

| 選択肢 | 内容 |
|---|---|
| A（推す案） | 関数型を持つ値を呼ぶ共通の規則にする。直接の構成子、属性、ハンドラの節の束縛、`resume` は専用の規則を維持する |
| B | 直接の関数宣言だけを名前付きにし、関数値や特殊な関数呼び出しは位置指定のままにする |
| C | 構成子や属性の引数も全て名前付きへ変える |

推す案は A である。理由: 関数を値にしただけで呼び方を変えず、静的な型の契約から呼び方を決められる（原則 1・4・5）。B は関数型にも名前を持たせる了承済みの方針と合わない。C は名前を持たない構成子の宣言や属性の文法まで変更するため、範囲が広がる。

型クラスの契約名は宣言を正とし、実装でも一致させる。エフェクトの操作を呼ぶ側は操作宣言の名前を使うが、ハンドラの `case E.op(x, k)` は値を束縛する形なので、その局所名を固定しない。外部の関数は Benitoite の宣言名を使い、既存の WIT との個数・型の位置での照合を保つ。外部の引数名と新たに一致を求める案にはしない。

## Q9 構成子を関数値として渡すときの名前はどうするか

答え（2026-10-14、設計者）: 推す案

問い: 名前を宣言していない構成子を関数値にする際、位置を表す `arg1`・`arg2` の契約名を付けるか。

| 選択肢 | 内容 |
|---|---|
| A（推す案） | 直接の構築・パターンは位置指定のまま。関数値では宣言上の位置に `arg1`・`arg2` を付ける |
| B | 構成子の宣言にフィールド名を加え、直接の構築も名前付きにする |
| C | 引数を持つ構成子を関数値として使う機能をなくし、明示のラムダを要求する |

推す案は A である。理由: 現在の機能を保ち、構成子の宣言とパターンの改造を増やさずに契約名を一意にできる（原則 4・5・6）。名前は利用者の局所名ではなく位置の説明である。意味を表す名前が必要な高階関数には、明示のラムダで合わせる。

例えば直接の `Pair.Pair(left, right)` は維持する。`bind make <- Pair.Pair` の後は `make(arg1: left, arg2: right)` とする。`Pair.Pair(_, right)` で作る一引数の関数にも、第 1 位置の `arg1` を付ける。レコードの取り出す関数に与える一引数の契約名は、Q10 の命名表で同様に決める。

## Q10 標準ライブラリと高階関数の引数名をどう揃えるか

答え（2026-10-14、設計者）: 推す案

問い: 既存の外側の引数名をできるだけ維持し、まだ名前のない高階の型には役割ごとの標準名を追加する進め方でよいか。

| 選択肢 | 内容 |
|---|---|
| A（推す案） | 既存の `xs`・`f`・`initial` などを維持し、単一の値に `value`、畳み込みに `acc`・`value` などの標準名を定める。必要な既存名の変更は個別に一覧化する |
| B | 今回、外側の名前も含めて全標準ライブラリを全面的に改名する |
| C | 高階の型にも用途ごとの異なる名前を付け、名前の共通化はしない |

推す案は A である。理由: 公開名の余分な変更を減らしつつ、よく渡す関数の型を揃えられる（原則 2・4・6）。C では同じ働きの関数でも用途ごとに名前を合わせ直す負担が増える。全てを `value` にできるとは断定せず、引数の役割で分ける。

命名表は、標準ライブラリの宣言、組み込みの型、高階の型、型クラスと実装、レコードの取り出す関数、内部の演算用の関数を含める。表を作り、`List.map` に既存関数を直接渡せる組と書き直しが必要な組を確認してから、関数型を変更する。Rust の組み込みの本体の変数名を公開契約として無条件に採用しない。

## Q11 互換性を壊す変更を、どの版と手順で提供するか

答え（2026-10-14、設計者）: 推す案

問い: 次のリリースで新しい呼び方へ統一し、古い言語の版と位置指定には移行を案内する誤りを出す方式でよいか。

| 選択肢 | 内容 |
|---|---|
| A（推す案） | 互換性を壊す変更を版の表へ記録する。旧い呼び方は受理せず、既知の宣言名を使った修正案と移行文書を提供する |
| B | 一定の期間は古い位置指定も受け付け、警告にとどめる |
| C | 言語の版ごとに古い文法と型の契約を維持する |

推す案は A である。理由: 現在の版の判定の仕組みを使え、並行する文法や名前のない関数型を維持せずに済む（原則 2・4・5）。B は名前必須を実際に要求する時期を別に定める必要があり、C は複数の型の規則と標準ライブラリを保つ範囲へ広がる。

設計者は変更を含む版番号を `0.0.5` に決めた（2026-10-15）。`language` の宣言のないソースも現在の規則で検査する。名前を加える修正では、引数の式を元の記述順に保つ。名前を揃えるための改名は、別の局所名との衝突も確認する。現在の版の機構と移行量は [migration.md](study/migration.md) にある。

## Q12 フォーマッタは短い形をどう出すか

答え（2026-10-14、設計者）: 推す案

問い: 短い形か終端付きかは書き手の選択を保ち、短い形を自動で改行しない方式でよいか。

| 選択肢 | 内容 |
|---|---|
| A（推す案） | 終端の有無を保ち、短いラムダ全体は同じ物理行に保つ。引数の順も変えない |
| B | 条件に合う終端付きのラムダを自動で短くし、長くなったら終端を足す |
| C | 整形後は全て終端付きにする |

推す案は A である。理由: 今の字句を保つ整形と検証の仕組みに沿い、整形で本体の範囲が変わる事故を避けやすい（原則 3・4）。B・C は `end lambda` を増減するため、字句列の一致による現在の検証だけでは使えず、同じ意味を保つ新しい検証が要る。

長い行を複数行にする場合は、書き手が先に終端を付ける。単純に行を分割して終端のない複数行を出す方式にはしない。物理行と本体の範囲を保つ確認は、現在の検証にも追加する必要がある。

## Q13 非推奨と推奨の説明を、どの文書と例へ反映するか

答え（2026-10-14、設計者）: 推す案

問い: Skill と現行マニュアルに加え、設計書の説明と一般の推奨例へ反映し、有効な構文の説明とその検査例は残す範囲でよいか。

| 選択肢 | 内容 |
|---|---|

## R4 Q10 の具体名と関数型内の名前をどう定めるか

## R20 見出しの行に始めた本体の終端を同じ物理行に限定する
