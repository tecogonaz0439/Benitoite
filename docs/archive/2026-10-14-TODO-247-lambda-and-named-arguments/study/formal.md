# 形式化の範囲と修正の案

## 判定の根拠

[07-04「01-12 との対応」](../../design/07-quality/07-04-formal-semantics.md#01-12-との対応) は、形式化した範囲の構文・型・脱糖を変えるときに、処理系より先に Lean の定義、表層の型付け、脱糖、性質 1 の証明を直すと定める。対象外なら同じ表に対象外の行を加えるか、既存の行へ書き足す。Lean の定義を変えた場合は、01-12 の写しと対応表も同じ変更で直し、定義と言明のレビューを受ける。

現在は段階 C1・C2・C4・C5・C6・C7 が完了している。呼び出し・ラムダは C1、パイプ・部分適用・構成子を関数値として使う形は C2、利用者の操作とハンドラは C4、型クラスは C5 に含まれる。段階 E2 は型検査が書き出した表層の型情報を Lean で検査する。名前付き引数全体を、字句や名前解決の変更というだけの理由で対象外にはできない。

| 変更 | 判定の案 | 理由と必要な記録 |
|---|---|---|
| 単文・一行のラムダの終端省略 | 綴りと境界の解析は対象外。受理後のラムダは既存の C1 の範囲内 | 同じ本体・型・作用先へ写すなら、表層の型付き構文を増やす必要はない。対象外の記録と、同じ表層へ写せる確認が要る |
| `else`・`shadow`・包括的な分岐の文書上の推奨 | 形式化の規則の変更なし | 構文、型付け、脱糖、警告を変えない。置き換え例の意味は実装時に検査する |
| 呼び出しの名前から位置への対応、順序の異なる指定 | C1・C2 の範囲内 | ソース順の計算と宣言順の値の並びが異なる。現在の呼び出しの表現と脱糖を変える |
| 関数型に契約名と宣言順を持たせる | 型付けと C1・C2・E2 の範囲内 | 等しい関数型の条件と、ラムダ・関数値の適合が変わる。現行の型では名前を検査できない |
| 名前付きの穴、パイプの挿入 | C2 の範囲内 | 穴から生成する関数型と、挿入する位置の検査が変わる |
| エフェクトの操作・ハンドラへの接続 | B1・C4・E2 の範囲内 | 操作のシグネチャに名前を持たせ、書いた順の計算を保つ必要がある |
| 型クラスのメソッドと実装 | B2・C5・E2 の範囲内 | メソッド型、実装の一致、辞書を通じた呼び出しが関数型を使う |
| 構成子を関数値へ変える際の契約名 | C2 の範囲内 | 生成するラムダの型が変わる。直接の構成子とパターンを変えなくても該当する |
| 外部の関数と WIT の対応 | 外部の宣言を含むプログラムは既存の対象外 | 対応表の外部境界の行へ、Benitoite の契約名から位置へ写す処理を追記する。一般の関数型は対象外にしない |
| 属性の文字列引数・フォーマッタ・移行診断 | 対象外 | 型付き表層への入力前の処理と道具である。形式化の対象を増やすこととは分ける |

終端省略の「対象外」は、ラムダ自体を証明の範囲から外す案ではない。省略形の解析後に従来と同じラムダを渡すことを前提とした判定である。本体の境界や `return` の意味まで変える案を選ぶなら、判定し直す。

## 現在の Lean の表現

[Release/Syntax.lean](../../../formal/Benitoite/Release/Syntax.lean) の `Ty.fn` は引数型の `List Ty` と戻り値とエフェクトを持ち、名前を持たない。`Val.lam` のパラメータも型の並びで、局所変数は de Bruijn の番号である。ソースの局所変数の綴りを一致させる規則は、現在のコアの型にはない。

[Surface/Syntax.lean](../../../formal/Benitoite/Surface/Syntax.lean) は現在、Release の型を使う。`Expr.call` は呼ぶ式と `Exprs`、`partialCall` は `HoleArgs`、`pipe` は左右の式を持つ。レコードには `positions : List Nat` があり、ソース順に評価する値と宣言中の位置を別に表している。引数の並べ替えも、このように型の情報を付けた入力に位置対応を持たせる案を検討できる。ただし、レコードの証明がそのまま関数呼び出しに使えるという確認はしていない。

現在の入力へ、ソース順で引数の式だけを渡すと、宣言順の型との照合ができない。宣言順へ式を並べた入力だけを渡すと、元の評価順を証明や差分検査から落としてしまう。関数型の契約名も先に消すと、名前が不一致の関数値を Rust 側が誤って受理しても、Lean の検査が見つけられなくなる。

## Q14 の選択肢と推す案

二つの形式化の方式が考えられる。

1. 共有する関数型に契約名を加え、コアの静的な型にも保持する。形式化のラムダや関数のシグネチャに、型の契約名を決める注釈を足す。実際の VM の値には追加しない。
2. 表層専用の名前を持つ型を新設し、コアへ移すときに名前を消す。その型の適合と、名前を消した後の型の適合が対応することを証明する。

推す案は 1 である。現在の Surface が Release の型を使っているため、型の対応を別に全面的に定義する案より、現在の「名前も契約」という方針を同じ型で明示できる。ただし、型を扱う全証明への影響は広い。これは調査に基づく実装方式の候補であり、証明を試した結論ではない。名前を変数の番号へ置き換える今の仕組みと、呼び出しの契約名の保持を混同しない。型に保持する契約名は、局所変数の束縛名を指すものではない。

VM の関数値やクロージャへ名前を保持させない方針とは矛盾しない。Lean の型と注釈は静的なモデルの情報であり、Rust の実行時の値のレイアウトを表すものではない。Core IR の型に名前が残る場合でも、それを実行時へ持ち込まない境界を実装プランで決める。

## 修正する場所と確かめる性質

以下は判断後の実装プランへ含める修正候補である。今回の作業では変更していない。

| 場所 | 修正候補 |
|---|---|
| `formal/Benitoite/Release/Syntax.lean`・`Typing.lean`、型の置き換え・遷移・補題 | 関数型、ラムダ、関数・組み込み・操作・メソッドのシグネチャに契約名を保持する。名前の個数・一意性・位置一致を定める。型の置き換えは契約名を変えない |
| `formal/Benitoite/Surface/Syntax.lean`・`Typing.lean`・`Desugar.lean`・`WellFormed.lean` | 通常呼び出しと穴の引数に、ソース順と対象位置の対応を持たせる。全位置を一度ずつ指定する条件、パイプの位置、穴の契約名を定める |
| `formal/Benitoite/Surface/Lemmas/Calls.lean`・`CallHead.lean`・`Typing.lean`・`Theorems.lean` など | ソース順の束縛の後で値だけを位置順へ配置しても、呼び出しと生成するラムダの型が保たれることを性質 1 に含める。補題の最終的な分け方は定義後に決める |
| `formal/Benitoite/Surface/Check*.lean` | 契約名の適合、位置対応、穴とパイプの検査を追加し、検査の健全性を維持する |
| `formal/Benitoite/Exchange/`、`crates/benitoite/tests/desugar_export/` | 名前とソース順・位置対応を交換形式に含める。組み込みのシグネチャの書き出し、表層の出力の検査、脱糖の比較を接続する |
| `formal/Benitoite/Release/BuiltinTable.lean` などの組み込みの表 | 公開と内部の関数型の契約名を、処理系が書き出す型と揃える |
| `docs/design/01-spec/01-12-core-calculus.md`、07-04 の対応表 | Lean の規則の写し、評価順と位置対応の脱糖、範囲内と対象外の区別を更新する |

性質 1 の型の保存だけでは、ソースの IO の順が意図どおりであることや、構文解析で短いラムダを正しく閉じたことまで分からない。脱糖にソース順の `let` を残し、参照インタプリタと VM の検査、Lean との脱糖の差分検査、作用順を観測できる例で補う必要がある。名前を正しく位置に対応させる条件を交換形式へ書く際に、名前付きの指定を検査前に無条件で位置指定へ変換してしまわない。

実装時は、Lean の定義と言明を先に作り、性質 1、進行と保存、エフェクトの健全性、表層の検査の健全性を弱めずに維持する。`lake build` が `sorry` なしで通ること、定義と言明のレビュー、`scripts/check-formal.sh` の比較を必要な順に行う。今回はビルドや証明の試行を行っていない。
