# 型と呼び出しの実装への影響

## 現在の型と検査

[01-06「型システム」](../../design/01-spec/01-06-type-system.md) の「型」は、関数型を引数の型・戻り値の型・エフェクトで比べる。引数名は等しさの条件に入っていない。[types/mod.rs](../../../crates/benitoite/src/types/mod.rs) の `FnTy.params` と `Scheme.params` は `Vec<Ty>`、[typeck/infer.rs](../../../crates/benitoite/src/typeck/infer.rs) の `IFnTy.params` は `Vec<ITy>` であり、いずれも名前を持たない。

[typeck/generate.rs](../../../crates/benitoite/src/typeck/generate.rs) の `call_body` は、パイプで入る式とソースの引数を並べ、関数型の引数と位置で照合する。`call_constraint` は必要な個数の新しい型変数を作って、呼ぶ値がその関数型であるという制約を加える。ラムダの型は、パラメータの型注釈または新しい型変数から作る。パラメータ名は局所の束縛に使うが、関数型には残さない。

[typeck/solve.rs](../../../crates/benitoite/src/typeck/solve.rs) は関数型の引数の数と対応する型、戻り値、エフェクトを検査する。関数型を確定する処理、エフェクトの包含、型引数の置き換え、診断用の型の表示にも同じ型表現が使われる。名前の一致を追加するなら、通常の等しさだけでなく、包含で渡せる関数型、分岐の型の合流、型の別名、入れ子の関数型にも通す必要がある。

TODO で了承済みの契約を実装すると、`function(value: T) -> U` を要求する場所へ、`lambda(x) return …` を直接渡せない。引数が一つでも、位置で呼べることと、関数値の型の名前が一致することは別の規則である。名前が違えば `lambda(value) return existing(value)` のような明示の書き直しが要る。これは推論で吸収できる型変数の差ではない。

Q4・Q5 では、関数型の引数名を必須とし、ラムダが実際に書いた名前をその型の名前にする案を推す。名前のない型に文脈ごとの名前を暗黙に足すと、同じ関数値の契約が渡す先で変わる。呼ぶ関数の型が最終的にも分からない場合は、呼び出しの順を契約にせず、注釈を求める。処理系の内部で未確定の名前をどう表すかは、判断後の実装プランで定める。

## 名前の対応と評価順序

[01-08「評価順序」](../../design/01-spec/01-08-evaluation.md#評価順序) と [ir/desugar/exprs.rs](../../../crates/benitoite/src/ir/desugar/exprs.rs) の `call` は、呼ぶ式を先に、引数をソース順に評価する。脱糖は途中の計算を `pending` に蓄え、値を位置引数として `invoke` に渡す。

名前付き引数では、評価する順と呼び出す位置を別々に持つ必要がある。例えば、宣言が `f(a, b)` でソースが `makeFunction()(b: readB(), a: readA())` なら、次の順を保つ。

1. `makeFunction()` の結果を保存する。
2. `readB()` の結果を保存する。
3. `readA()` の結果を保存する。
4. 保存した A の値、B の値を、宣言の位置で渡す。

型検査で引数の各ノードから宣言の位置への対応を決め、脱糖でソース順の束縛を作ってから値の参照を並べる案である。式そのものを宣言順へ並べ替えると、IO の順序、途中の失敗、`return`・`try` の作用が変わる。レコードの脱糖が位置対応を使う構造は参考になるが、呼ぶ式の評価、部分適用、辞書やパイプの扱いも要るので、そのまま共用できるとは断定しない。

[bytecode/codegen/emit.rs](../../../crates/benitoite/src/bytecode/codegen/emit.rs) の `app`・`method`・`vals` は、値の並びを連続するレジスタへ置いて呼ぶ。`Call` と `TailCall`、組み込み、外部の呼び出しも位置で扱う。脱糖後に位置対応を終えるなら、VM の呼び出し命令やクロージャに名前を加える必要はない。静的な型表現を変えるため、IR の型を組み立てる関数やコード生成中の型の参照には修正が及ぶ。値の保存と配置の費用が増えないこと、末尾呼び出しと確保数の性質が保たれることは、実装後に確かめる。

## パイプと部分適用

現在の `pipe` は左辺を先に一度だけ評価し、右辺が直接のプレースホルダを持たない呼び出しなら第 1 引数へ入れる。括弧で囲んだ右辺や部分適用へは、右辺の関数を作ってから一引数で呼ぶ。これは通常呼び出しの順序とは別の、明示のパイプの規則である。

Q6 の案は、第 1 パラメータへの挿入を保ち、書き手が書く残りの引数はすべて名前付きにする。`xs |> List.map(f: lambda(value) return value * 2)` は `xs` を第 1 パラメータへ渡す。`xs` を引数欄にも指定すると重複として誤りにする。第 1 以外の空いている場所を探して自動挿入する規則は加えない。

現在の `placeholder` は、直接の `_` をソースの左から順に新しいパラメータへ置き換えたラムダをコアへ作る。呼ぶ式と固定した引数を評価するのは、部分適用を作る時点ではなく、作った関数を呼ぶ時点である。`return`・`try` はそのラムダに作用し、外側の継続を `resume` で再開できない。

Q7 の案は `f(a: _, b: 2)` のように `_` にも対象の名前を付け、生成する関数の契約名を元のパラメータ名から取る。二つ以上の穴は、今と同じくソースでの出現順に並べる。例えば、宣言が `f(a: A, b: B)` でも `f(b: _, a: _)` の型は `function(b: B, a: A) -> R` になる。契約の順を揃えたい場合は穴の指定順を揃える。内部の新しい局所名は、従来どおり他の名前と衝突しないものにする。型の契約名と、この内部名は区別する。

## 呼び出しの種類ごとの境界

| 対象 | 現在の扱いと根拠 | Q8・Q9 の案で必要な扱い |
|---|---|---|
| 通常の関数・ラムダ・関数値 | 呼び出しは共通の `CallExpr`。宣言の引数名は AST にある | 同じ名前付きの規則を適用する。直接の宣言だけに限定しない |
| 型クラスのメソッド | [01-06「型クラス」](../../design/01-spec/01-06-type-system.md#型クラス初回リリース版)、`typeck/traits/impls.rs` の `check_methods` は宣言と実装の引数型などを比べる。脱糖は辞書を渡す | 呼ぶ側の契約は型クラスの宣言から決め、実装にも名前の一致を要求する。辞書と自己の制約の引数は内部の引数で、利用者の引数数に数えない |
| 利用者のエフェクトの操作 | [01-06「エフェクトの宣言とハンドラの型付け」](../../design/01-spec/01-06-type-system.md#エフェクトの宣言とハンドラの型付け初回リリース版)。操作の宣言を関数型にする。`typeck/decls.rs` が関数宣言に対応する情報を作る | 操作を呼ぶときは名前付きにする。ハンドラの節の `case E.op(x, k)` は呼び出しではなく束縛なので、節の局所名を操作の契約名に固定しない |
| 組み込みの関数 | [builtins/table.rs](../../../crates/benitoite/src/builtins/table.rs)、[builtins/iface.rs](../../../crates/benitoite/src/builtins/iface.rs) の宣言の仕組みと標準ライブラリの `@builtin` 宣言。VM は個数と位置で呼ぶ | 公開の契約名を標準ライブラリと揃える。Rust の変数名だけから契約名を決めない |
| 外部の関数 | [external/check.rs](../../../crates/benitoite/src/external/check.rs) は宣言の引数と WIT の引数を `zip` し、個数と型を位置で照合する | Benitoite の宣言名で呼び、渡す位置を決めてから外部境界へ渡す。WIT の引数名との一致を新たに条件にしない |
| データ構成子 | 01-02「プログラムと宣言」で引数は名前を持たないと定める。構成子を値として使う形は、脱糖でラムダを作る | 直接の構築とパターンは位置指定を維持する。関数値として使う場合は Q9 の別の判断が要る |
| レコード | 既に名前付き。構築・更新・パターンと取り出す関数は別の形 | フィールドの規則を維持する。取り出す関数を値にしたときの一引数の契約名は定める必要がある |
| 属性 | 01-02「属性」で、引数は補間のない文字列リテラル。`Attribute.args` は `Vec<StrArg>` | 関数呼び出しの対象外。`@external("wasm", "…", "…")` を維持する |
| `resume` | 継続の再開のための専用の構文。一般の関数値ではない | 呼び出しの引数名の対象外。型・継続の規則を保つ |

構成子を値として使うと、今は `function(A, B) -> Data` のような型になる。名前を必須にした関数型との間でこのままでは契約を決められない。Q9 は `arg1`・`arg2` という位置を表す契約名を生成する案を推す。名前付きの構成子宣言を新設する案や関数値としての利用を禁止する案より、現在の機能を保ち、対象の境界を小さくできる。直接の `Pair.Pair(a, b)` と、値に束縛した後の `make(arg1: a, arg2: b)` が異なることは明記する必要がある。

## 標準ライブラリの契約名

[List.bnt](../../../crates/benitoite/src/prelude/stdlib/List.bnt) の現在の宣言は、`map(xs, f)`、`filter(xs, p)`、`fold(xs, initial, f)`、`forEach(xs, f)` である。渡す関数の型は `function(T) -> U` や `function(A, T) -> A` であり、名前はまだない。`mapFrom`・`foldFrom` など内部の補助関数への位置呼び出しも多い。

Q10 では、既存の外側の名前 `xs`・`f`・`p`・`initial` を維持し、新たに名前が要る関数型には、単一の値は `value`、畳み込みは `acc`・`value` のように役割ごとに揃えた名前を使う案を推す。ここで示す組は候補であり、全標準ライブラリの命名表を作った結果ではない。`String.toString` など一引数の既存関数をそのまま `List.map` に渡せるかも、実際の宣言名を比べて決める。既存の公開名を揃えるために変更する場合は、それも契約の変更として一覧にする。

組み込みの関数の公開名、宣言名、組み込みの型の表、高階の引数型、型クラスの宣言と実装で食い違いを残すと、標準ライブラリそのものを型検査できなくなる。内部の演算子や補間用の組み込みも関数型を持つため、公開の呼び方と内部の位置呼び出しの区別を実装プランに書く。Rust の型付き組み込みの仕組みは維持し、利用者に内部の辞書や VM の引数を名前付きで指定させない。

## 型やシグネチャの変更の扱い

この改造では `Arg`・`FnType`・`FnTy`・`Scheme` などの表現変更が必要になる見込みである。AGENTS.md の「型とシグネチャを変えない」に従い、現在の型を変更する承認なしに実装を始めることはできない。今回は調査だけなので、型や欄を変えていない。判断後のプランで必要な変更を具体的に列挙し、設計者がその変更を含むプランを判断できるようにする。
