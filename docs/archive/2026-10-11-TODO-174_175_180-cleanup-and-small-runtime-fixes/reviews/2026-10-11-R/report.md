## 指摘

### 1. 設計書 02-08「呼び出しの入れ子の上限」が、USE の新しい振る舞いと食い違う（要修正。設計書の反映で直す）

- 問題: 設計書は、枠を積む命令（`USE` を含む）が上限を超えるときは「その操作を行わずに」止まると書いている。今の `USE` は、上限を超えるときも解放の枠を積み、計数を一つ増やしてから `CallStackTooDeep` を返す。コードのコメントは 01-10「解放の時期と順序」「解放の失敗」を引いているが、02-08 のこの決まりの例外であることには触れていない。
- 直し方: 02-08:172 に、`USE` だけは解放の枠を積んでから止めること、報告の枠の数は積む前の値であることを書き足す（理由: 止める手順で解放の枠を通し、バッファと解放の失敗を失わないため）。あわせて、`resource.rs:31-32` のコメントに `02-08「呼び出しの入れ子の上限」` を加えると、例外であることがコードからも読める。
- 同じ改造で設計書に反映が要る箇所（漏れ防止のための一覧）:
  - 02-09「IO 実行器」: poll の失敗が 1,000 回続くと処理系の不具合として止まること。
  - 02-09「プログラムの実行の流れ」: 書き出し用のスレッドの起動に失敗すると、実行の前に終了状態 3 で止まること。getrandom の失敗を確かめる位置。
  - 07-02「測る項目」: `record_pauses`、`pause_total_nanos`、`pause_max_nanos`。

### 2. `IdleWake::Failed` の報告の文で、1000 を直接書いている（任意）

- 場所: `src/vm/dispatch/tasks.rs:300-304`、`src/runtime/io/event.rs:8`・`226-229`
- 問題: VM 側の文 `"event loop wait failed 1000 times in a row: {reason}"` は、`POLL_FAILURE_LIMIT` とは別に回数を書いている。定数を変えても、文の回数は変わらない。
- 直し方: `event.rs` の側で、回数を含めた説明を作る（例: `IdleWake::Failed(format!("{POLL_FAILURE_LIMIT} consecutive failures: {error}"))`）。VM 側は `format!("event loop wait failed: {reason}")` とする。

### 3. 停止時間の統計のテストが、0 より大きい時間を前提にしている（任意）

- 場所: `src/runtime/heap/core/mark_sweep.rs:316-320`
- 問題: `after.pause_total_nanos > before.pause_total_nanos` と `after.pause_max_nanos > 0` は、一回の回収の停止時間が 0 ナノ秒にならないことを前提にしている。時計の分解能が粗い環境では、まれに 0 になり得る。直す前は、並びが一つ増えたことを確かめる頑健な形だった。
- 直し方: `>=` に緩める。回収が記録されたことは、すでにある `after.collections - before.collections == 1`（307 行）で確かめられる。

### 4. `HeapStats::pause_total_nanos` の `///` が、欄が何かを言っていない（任意）

- 場所: `src/runtime/heap/stats.rs:44`
- 問題: 「停止時間の件数は collections と等しいため、合計だけを別に保持する」は件数を持たない理由だけを書いており、この欄が何の値で、単位が何かを書いていない。
- 直し方: 例「回収の停止時間の合計（ナノ秒）。件数は `collections` と常に等しいので、別の欄に持たない（設計書 07-02「測る項目」）。」

### 5. セルの更新の再現テストは、呼び直しを通ったことを自分では確かめていない（任意）

- 場所: `tests/vm_reference_cells.rs:14-85`
- 問題: R0101 が起きるのは、呼び直しの経路だけではない。タスクの選び方が変わって、起動したタスクが `Reference.update` より先に `Reference.set(r, 0)` を済ませると、一回目の呼び出しで 0 除算が起きる。このときも呼び出し位置は `Reference.update` を指すので、テストは呼び直しを通らないまま通る。今の `FifoPicker` では、直す前に失敗することが確かめられている（報告では、期待 296 に対して 382 を指した）。退行を防ぐ力が残るかどうかは、選び方の実装に依存する。
- 直し方の例: 更新の関数が一回目に受け取る値が 1 であることを、プログラムの側で区別できるようにする。たとえば、一回目に呼ばれたかどうかを別の `Reference` に記録し、二回目に呼ばれたときだけ除算する。そうすれば、R0101 が起きたことが、呼び直しを通った証拠になる。

### 6. 起動の履歴の測定で、直した後の深さ 1,000 の時間が外れ値になっている（任意）

- 場所: 実装担当の報告「4. 起動の履歴の測定の結果」
- 問題: 直した後の深さ 1,000 は 0.399 秒で、直す前（0.039 秒）より遅く、直した後の 2,000・4,000（約 0.020 秒）よりも遅い。一回きりの測定なので、初回の起動の費用（キャッシュが温まっていないなど）の可能性が高い。ただし原因は確かめていない。
- 直し方: 記録に残すなら、深さ 1,000 だけでも数回測り直して中央値を書く。改造の判断（費用が O(1) になったこと）は、最大 RSS と 2,000・4,000 の値で十分に支えられている。

### 7. USE の上限で、解放が待つ（Wait）場合はテストで確かめていない（任意）

- 場所: `src/vm/dispatch/resource/tests.rs:746-800`
- 問題: 確かめているのは、待たない `FileReader` の解放だけである。上限を超えた計数のまま `unwind_release` が `Wait` を返し、待ちを終えた後に `Popped` で計数を戻す経路は、コードを読んで正しいと判断したが、テストはない。
- 直し方: 依頼文の補足が「要らない」としたので、必須ではない。足すなら、`Wait` を返すテスト用の資源で同じ三つの場合を回し、最後に `meter.bytes() == 0` を確かめる。

## 確かめて問題がなかった点

1. **USE の上限**
   - `frames` は積む前に取っている（`resource.rs:30`）。
   - 解放の枠を積んだ後に `grow(1, 0)` を一度呼ぶ。`grow` と `shrink` は飽和演算である（`budget.rs:112-122`）。止める手順では、`advance_work` が `Popped` で `shrink(1, 0)` するので、増減の対が合う。
   - `unwind_release` は呼び出しの枠を積まないので、上限を超えた計数のまま `fits` で再び失敗することはない。
   - テストは、報告の `frames: 1`、位置（`main` の pc 0）、解放がちょうど一回であること（二重に閉じない）、`release_failures` の件数、最後の `meter.bytes() == 0` を確かめている。直す前に失敗することも確かめてある。
2. **SpawnHistory**
   - 並び順は、直す前と同じ「自分の起動 → 親 → …」である（`state.rs` の `records`）。
   - 起動したタスクの枠は `frame_records()` で作る。これは、直す前に使っていた `stop_info(...).frames` と同じ式である。起動ごとの費用は、今の呼び出しの深さに比例するだけで、履歴の長さによらない。
   - 鎖は、先に作った親だけを指すので、`Rc` は循環しない。
   - `Drop` は `try_unwrap` の繰り返しで鎖を外し、ほかの所有者が残る段で止まるので、再帰しない。10 万段の鎖を落とすテストもある。
   - `RunState` はもともと `Send` でないので、`Rc` にしても性質は変わらない。
   - taskOrigins のテストは、起動の位置を偶数と奇数で交互にし、50 段と `main` を合わせた 51 段の順序を確かめている。直す前と後の両方で通る。
3. **poll の失敗**
   - 成功と EINTR で 0 に戻す。そのほかの失敗だけを数え、1,000 回目は眠らずに `Failed` を返す。
   - 計数は飽和するので、`Failed` の後にまた失敗すれば、すぐに `Failed` が返る。
   - 止める手順の途中で `Failed` が返った場合も、`switch` が `stop_without_progress` に回すので、手順が詰まらない。
   - `EventLoop::take` は、実行ごとに 0 から数え始める。
   - `IdleWake` を網羅して `match` しているのは一か所だけである。
4. **起動の順序**
   - `run_entry` は、getrandom → イベントループ → 中断の登録 → 出力 → 起動の失敗の確かめ → stdin → `IoRuntime::new` の順に進む。
   - 片方の口だけが起動した場合は、早く戻ると `Drop` の `finish` で書き出し用のスレッドを止める。何も書いていないので詰まらない。起動に失敗した口は `thread` が `None` なので、`Drop` は何もしない。
   - 終了状態 3 と説明の文は、テストで確かめている。
   - 本番で `OutputPort::start` を呼ぶのは `run_entry` だけである（残りはテストの補助）。
5. **pause_nanos**
   - 停止時間の合計と最大は、いつも更新する。並びは、印が立っているときだけ記録する。
   - `collections` が増えるのは `mark_sweep.rs:195` だけで、停止時間を記録するのと同じ経路である。
   - `bench_run` と `stage1_support` は印を立てるので、出力の書式は変わらない（`tools/bench/remeasure.py` も並びを読むだけ）。
   - `unsafe` も不変条件の一覧も増えていない。
6. **小さな点**
   - `CellUpdate.at` は三か所すべてに足してある。`retry` は呼び出し位置にこれを使い、`precall` の印は変えていない。
   - FORCE は、`host_mut` の後に `?` が残っていない。
   - `resume_return` を直接呼ぶようにして、使われなくなった `unwinding::resume` を消した。
   - `poll_outputs` の頭で `reflect_cancellation` を呼ぶ。
   - lazy のテストは、二度目の FORCE の後も `Done` で同じ値であることを確かめている。
   - 乱数の計算は、元のコードの写しで、生成する列は変わらない。依存の向きは builtins から runtime になった。
   - sched のテストは、中身を変えずにファイルの末尾へ移してある。
7. **規約**
   - 本番のコードに `unwrap`・`expect`・`panic!`・添字・`unsafe` は増えていない（`unwrap_or`・`unwrap_or_else` は許されている形）。
   - 処理系の不具合の説明は、表にも `text` にも載せていない。
   - 新しいコメントは日本語で、設計書の節を引いている。引いた節（02-08「明示遅延」「実行時エラーの情報の記録」、02-09「IO 実行器」「出力のバッファ」「プログラムの実行の流れ」「メモリの管理」、01-10「解放の時期と順序」「解放の失敗」、07-02「測る項目」、03-07「Random」）は、すべて実在する。
   - 実装プランや作業の ID を含む新しいコメントはない。sched のテストを移した箇所に残る「実装プラン R24」「00-02」は、そのまま写したもので、決まりどおりである。
8. **テストの質（test-audit）**
   - 1・2 は、直す前に失敗することを確かめてある。
   - 3・4 は、新しく足した判定の関数と読み口を単体で確かめている。OS の失敗を注入できないので、これで妥当である。
   - 6 は、報告の中身が変わらないことを確かめるテストとして妥当である。
   - どのテストも、内部の欄ではなく、報告と振る舞いで確かめている。
