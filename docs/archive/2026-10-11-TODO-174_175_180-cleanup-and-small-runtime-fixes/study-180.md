### 4-c. `USE` が呼び出しの深さの上限で止まったときのリソース

- **今の位置**: `vm/dispatch/resource.rs:28-33`。黙って閉じる処理は `runtime/io/resources.rs:354-365`（`close_all_silently`）。`FileWriter` の drop は `builtins/funcs/file.rs:1174-1182` で、バッファを書き出さずに捨てる。
- **所見**: 今も成り立つ。上限を超えると解放の枠を積まずに `CallStackTooDeep` で止まるので、そのリソースは実行の終わりに書き出さずに捨てられる。
  - よくある `with w = try File.openWriter(...)` では、開いた直後で何も書いていないので失うものはない。
  - 開いてから書き込みをし、その後で `with w = r do` のように束縛した場合は、書いた内容が失われる。
  - 01-10「解放の時期と順序」は、資源の不足で止まるときは、開いているすべての `with` のリソースを解放してから止まると定める。呼び出しの深さは処理系が上限を設ける資源なので、「保証しない」の例外にも当たらない。
- **再現テスト**: Rust の単体テスト（`vm/dispatch/resource/tests.rs`）がよい。`VmConfig::max_call_stack_bytes` を小さくし、`USE` で枠一つだけ上限を超える形を作る。.bnt では、上限にちょうど当たるのが `USE` になるように作るのが難しい。判定は次の二つで行う。
  1. 止める手順で解放の枠を処理したこと。リソースの表で、`close_all_silently` ではなく解放によって解放したになっていること。
  2. `FileWriter` なら、一時ファイルに書いた内容が書き出されていること。
- **直し方の案**（推し）: 上限を超えるときも解放の枠を積み、計数を一つ増やしてから `Err(CallStackTooDeep)` を返す。報告の `frames` は、積む前の値を使う。止める手順の辿りが、`UnwindCause::Stop` でその解放の枠を処理するので、書き出して閉じる。上限を一枠超えるのはこの止まる直前だけで、すぐに止まるので量は限られる。
- **代わりの案**: 上限を超えたときに、その場で同期的に解放する。待つ処理（`File.Writer` の書き出し、`TaskGroup` の子の終わり）を同期で行うことになり、遅い経路の作りに合わないので推さない。
- **振る舞いの変化**: 利用者に見える。この端の場合に、書いた内容が残るようになる。解放が失敗すれば、それを注記として報告する。終了状態と主な報告（資源の不足）は変わらない。
- **影響する設計書**: 02-08「呼び出しの入れ子の上限」（172 行の `USE` の扱い）と「リソースの解放の枠」に、「`USE` が上限を超えるときは解放の枠を積んでから止める」と理由を一文で書く。関連は TODO-168（中断のテストで書き込みのリソースの解放を確かめる）。

## 7. OS の待ち（poll）が失敗し続けるとき（later-issues の 59）

  2. `EventLoop` に、続けて失敗した回数の計数を持たせる。成功したら 0 に戻す。
  3. 計数が決めた値に達したら `Failed` を返す。
  4. VM は `tasks.rs:291` の match で `Err(Stop::Internal(...))` にする。説明は内部の不具合の説明なので、診断の表にも `text` にも載せない。

- **振る舞いの変化**: 利用者に見える（終了状態 3 の処理系の不具合の報告）。ただし、OS の待ちが壊れたときだけである。

- **影響する設計書**: 02-09「IO 実行器」に「イベントループの待ちの失敗が続いたら処理系の不具合として報告する」と一文で書く。関門の性能には影響しない（待つときだけの経路である）。
- **設計者への問い**: 何回（何秒）続いたら報告するか。
  - A. 一回目の失敗で報告する。単純だが、`kevent` の `ENOMEM` のような一時的な失敗でも止まる。
  - B. 続けて N 回で報告する。例えば N = 1,000 で、1 ミリ秒の眠りを挟むので約 1 秒になる。時計を読まないので結果が決まる。**推し**。
  - C. 続けて失敗している時間が T 秒を超えたら報告する。時計を読む処理が要る。
  
  あわせて、報告の種類を処理系の不具合（終了状態 3）にすることの了承を得たい。資源の不足の種類は、処理系が上限を設けるものだけに限られている（`runtime/mod.rs:86-105`）。

## 9. 書き出し用のスレッドの起動の失敗（later-issues の 60）

- **今の位置**: `runtime/io/output.rs:74-93`。`Builder::spawn` の失敗を `WriteFailure::Io` に記録している。この失敗は `tasks/io.rs:534-538` と `services.rs` で `RuntimeError::WriteFailed`（R0201「failed to write to standard output」）になる。比べる例を二つ挙げる。
  - 作業用のスレッドの起動の失敗は `Outcome::Panicked`、すなわち処理系の不具合として報告する（`runtime/sched/parts.rs:217-241`）。
  - イベントループの作成の失敗は、実行の前に `internal_end`（終了状態 3）にする（`runtime/run.rs:207-218`）。
- **所見**: 今も成り立つ。スクリプトはそのまま走り、最初の書き込みで R0201 になる。報告の reason は OS の文言（例えば `Resource temporarily unavailable`）である。
- **直し方の案**:
  - A. 実行の前に失敗にする。`OutputPort::start` を `Result` を返す形にするか、起動の失敗を問う関数を加える。`run_entry` で `internal_end("cannot start output thread: ...")`（終了状態 3）にする。イベントループの作成の失敗と同じ扱いで、スクリプトの外部への作用が始まる前に止まる。**推し**。シグネチャを変えると、`OutputPort::start` を呼ぶ 22 か所（ほとんどがテスト）が変わる。問う関数を加える形なら `run.rs` だけで済む。
  - B. `writer_bug(...)` で `WriteFailure::Panicked` として記録し、最初の書き込みか最後の転送で処理系の不具合にする。変更は 1 か所で済むが、スクリプトが途中まで走る。
  - C. 今のまま R0201 とし、文言だけを変える。資源の不足の種類は処理系が上限を設けるものに限られるので、新しい種類は加えない前提である。
- **振る舞いの変化**: 利用者に見える（終了状態が 1 から 3 になり、報告も変わる）。ただし、スレッドを作れない環境でだけである。
- **影響**:
  - 02-09「プログラムの実行の流れ」の終わり方の表の「処理系の不具合（panic 境界で捕捉した Rust の panic）」の行は、イベントループの作成の失敗を今も含んでいない。A か B を選ぶなら、「実行を始める準備の失敗」も含むように書き直すか、注記を足す。
  - 02-09「出力のバッファ」にも、起動の失敗の扱いを一文書く。
  - 診断の表（`diag/codes.rs:871` の R0201）は変えない。R0201 は本当の書き込みの失敗に使い続ける。
- **設計者への問い**: A・B・C のどれにするか。推しは A（処理系の不具合、終了状態 3、実行の前に止める）。

### 11-b. 起動の履歴（SpawnHistory）が深さの 2 乗に増える

- **今の位置**: `vm/dispatch/tasks.rs:567-582`、`vm/state.rs:209-212`、`vm/mod.rs:78-85`（`SpawnRecord`）。消すのは `tasks.rs:773`（タスクが終わったとき）。読むのは `state.rs:150-154`・`tasks.rs:967-974`・`io.rs:236-240`。
- **確かめた結果**: 読んだ限り成り立つ。起動のたびに親の履歴の全体を `clone` して新しいタスクの履歴にする。各段の `spawner_frames` は、起動したタスクのその時点の呼び出しの枠の全体の写しである。
  - 親が子の終わりを待つ形（`Task.all` や `TaskGroup` の入れ子の再帰）で深さ n の鎖を作ると、生きている履歴の段の数の合計は n(n+1)/2 になり、写す時間も O(n²) になる。
  - 呼び出しの入れ子の計数は枠とレジスタだけを数え、履歴を数えない。上限の既定は 1 GiB で（`vm/mod.rs:20-24`）、一枠 96 バイトとして数百万枠まで許す。このため、鎖が上限より先にメモリを使い尽くしうる。
  - 報告（`runtime/report.rs:435-447`）は履歴を全部並べ、段を省かない。
- **再現の案**: 鎖の深さ n を 1,000・2,000・4,000 と変えた .bnt を走らせ、時間と最大の常駐メモリがおよそ 4 倍ずつ増えることを見る。これは一度の測定で、テストとして残さない。残すテストは、深い鎖で失敗したときに `taskOrigins` の段の数と順序が正しいことを確かめるものにする（直した後も振る舞いが同じことの確かめ）。大きさで確かめるテストにするなら `#[ignore = "long: ..."]` を付ける。
- **直し方の案**:
  1. 履歴を、親へのつながりを持つ共有の鎖にする。例えば `struct SpawnNode { record: SpawnRecord, parent: Option<Rc<SpawnNode>> }` とし、`RunState` が別のスレッドへ移るなら `Arc` を使う。起動ごとの費用は O(1)、合計は O(n) になる。止まったときだけ鎖を辿って `Vec` にする。親のタスクが先に終わっても鎖は共有で残るので、`TaskGroup` を子に渡して起動させる場合も履歴を失わない。
  2. （任意）各段の `spawner_frames` を、報告が使う段（利用者のソースにある最も内側の呼び出し）に絞る。呼び出しの深い所から多くのタスクを起こす場合の、起動の数×深さの量を減らせる。ただし、起動のときに位置の表を引く必要があり、変更が大きくなる。
- **振る舞いの変化**: 内部だけ。報告の中身は変えない。
- **heap**: 履歴は言語の値ではなく、ヒープの外に置く Rust の値なので、`runtime::heap` に触れない。
- **影響する設計書**: 02-08「実行時エラーの情報の記録」（320 行）は材料の中身だけを定めているので、変更は要らない。
