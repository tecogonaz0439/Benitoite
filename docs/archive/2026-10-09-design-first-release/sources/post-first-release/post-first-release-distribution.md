# 配布の改造の検討（導入のスクリプト、macOS の署名と公証）

- 作成: 2026-10-03
- 扱い: 検討用のメモ。初回リリース版の完成後に、設計書（05-01・ADR・OPEN-060）へ移す。
- 関係する検討: [パッケージ管理](post-first-release-package-management.md)の「パッケージと WASM の署名」「macOS の Gatekeeper と Rust の実行ファイル」

## 設計者の方針（2026-10-03）

- 導入のスクリプトは、技術的に難しくなければ用意する。ADR 0233 は「`curl … | sh` の形の導入のスクリプトは用意しない」としたので、この決定を改める。
- 設計者は Apple Developer Program の組織のアカウントを持っている。macOS の実行ファイルの署名と公証は、正式リリースを目処に行う。ADR 0233 の決定 4（初回リリース版では行わない）は、初回リリース版についてはそのままでよい。

## 導入のスクリプト

### 難易度

低い。Gatekeeper の面でも、スクリプトが `curl` で取得したファイルには隔離の属性が付かないので、署名と公証がなくても止められない見込みである（パッケージ管理のメモの Gatekeeper の節）。

### スクリプトが行うこと

1. 環境を判定する。`uname -s` と `uname -m` から、配る三つのアーカイブ（macOS の arm64、Linux の x86_64 と arm64。ADR 0176）のどれかを選ぶ。WSL2 は Linux として扱う。対応しない環境（Intel の macOS など）では、ソースからのビルドの手順（`cargo install`）を示して終える。
2. 版を決める。既定は最新の版とし、オプションか環境変数で版を指定できるようにする。
3. アーカイブと `SHA256SUMS` を取得する。`curl` を使い、なければ `wget` を使う。
4. ハッシュを確かめる。Linux は `sha256sum`、macOS は `shasum -a 256` を使う。一致しなければ、何も置かずに終える。
5. 一時ディレクトリに展開し、実行ファイルを置き場所に移す。既定は `~/.local/bin` とし、`sudo` を使わない。置き場所はオプションか環境変数で変えられる。
6. 置き場所が `PATH` に含まれなければ、追加の方法を示す。シェルの設定のファイルは書き換えない。
7. 次の手順（`benitoite skill install` など）を示す。スクリプトの中では実行しない。

### ADR 0233 が挙げた懸念への対策

ADR 0233 は、導入のスクリプトを退けた理由として、利用者が中身を読まずにシェルで実行すること、スクリプトの保守と試験の手間を挙げた。

- **中身を読まずに実行すること。** 文書では、`curl -fsSL <URL> | sh` の一行と並べて、「取得して読んでから実行する」手順も示す。スクリプトは短く保ち、上の 7 つの手順だけを行う。
- **途中までの取得で実行されること。** 通信が途中で切れると、パイプで渡された途中までのスクリプトが実行されうる。全体を関数で包み、最後の行でその関数を呼ぶ形にして、末尾まで届かなければ何も実行されないようにする（広く使われる書き方）。
- **保守と試験。** POSIX の sh の範囲で書き、`shellcheck` で検査する。リリースの試験（ADR 0234。開発機の上で行う）に、macOS と、コンテナの中の Linux（x86_64 と arm64）で、スクリプトで導入して `benitoite --version` が動くことを確かめる項目を加える。
- **置き場所の信頼。** `SHA256SUMS` は同じ置き場所から取るので、置き場所が乗っ取られた場合は防げない（ADR 0233 の帰結と同じ）。プロジェクトの鍵を設けたら（パッケージ管理のメモの「公式の追加のライブラリ」）、`SHA256SUMS` に SSH の署名を付け、スクリプトが `ssh-keygen -Y verify` で確かめる形に広げられる【要検証: 対象の環境の OpenSSH が `-Y verify` を持つか】。鍵はスクリプトに埋め込む。

### スクリプトの置き場所

- GitHub Releases の各版の資産として置き、版を固定した URL で取得できるようにする。
- 最新の版を指す一定の URL（`https://github.com/<所有者>/<リポジトリ>/releases/latest/download/install.sh` の形）を文書に載せる【要検証: GitHub の「最新のリリースの資産」の URL の規則】。

### Agent Skills との関係

エージェントにも、この一行で導入させられる。ただし、エージェントが利用者の確認なしにネットワークから取ったスクリプトを実行することになるので、同梱の Skill の文書では、導入は利用者が行うか、利用者の確認を得てから行うよう書く。

## macOS の署名と公証（正式リリースを目処）

### 必要なもの

- Developer ID Application の証明書（実行ファイルの署名）。`.pkg` で配るなら、Developer ID Installer の証明書も要る。Developer ID の証明書を作れるのは、チームのアカウントの持ち主である（ADR 0233 の背景）。
- 公証の資格情報。`xcrun notarytool` に、App Store Connect の API の鍵か、アプリ用のパスワードを渡す。

### 手順の骨子

1. `codesign` で、hardened runtime（`--options runtime`）と安全な時刻印（`--timestamp`）を付けて署名する。Rust で作った実行ファイルも、ほかの言語で作ったものと同じ手順で署名できる。
2. `notarytool submit` で公証に出す。単体の実行ファイルはそのまま出せないので、zip などに包んで出す【要検証: 受け付ける形式】。
3. 公証の結果（ticket）を `stapler` で添付する。添付できるのは `.app`・`.dmg`・`.pkg` だけで、単体の実行ファイルと zip には添付できない（二次資料）。添付しない場合、Gatekeeper は初めて実行するときにネットワークで ticket を確かめる見込みである【要検証】。

### 配る形の選択肢

| 形 | 長所 | 短所 |
|---|---|---|
| 署名と公証をした実行ファイルを `tar.gz` で配る（今の形のまま） | 配り方を変えない。導入のスクリプトと Linux の手順と揃う | ticket を添付できず、オフラインで初めて実行するときに確かめられない見込み |
| `.pkg` のインストーラ | ticket を添付できる。ブラウザで取得した利用者がダブルクリックで導入できる | Installer の証明書と、パッケージを作る手順が要る。置き場所が `/usr/local/bin` などになり、管理者の権限を求める |
| `.dmg` | ticket を添付できる | CLI の道具の配り方としては一般的でなく、利用者が自分で `PATH` に置く手間が残る |

当面の見立て: `tar.gz` の実行ファイルに署名と公証をする形を基本とし、ブラウザで取得する利用者のために `.pkg` を加えるかを、正式リリースの前に決める。

### 注意する点

- **hardened runtime と JIT。** 今の処理系はバイトコードの VM であり、実行中に機械語を作らないので、特別な権限（entitlement）は要らない見込みである。後の版で WASM の実行系を入れ、JIT のコンパイルを使う実行系を選ぶと、`com.apple.security.cs.allow-jit` などの権限が要る【要検証】。外部の関数の層の実行系を選ぶとき（OPEN-051）に、あわせて確かめる。
- **署名の鍵の置き場所。** リリースの試験と手順は開発機の上で行う（ADR 0234・0292）ので、証明書は開発機のキーチェーンに置き、公証の資格情報も開発機に置く。CI に置くかは、CI でリリースを作ると決めたときに検討する。
- **Linux の配布物。** Linux には Gatekeeper に当たる仕組みがないので、署名は `SHA256SUMS` への SSH の署名（前述）で代える。
- **Homebrew。** ソースからビルドする formula で配れば、署名と公証は関係しない。ビルド済みのものを cask で配るなら、公証が要る方向にある（パッケージ管理のメモの Gatekeeper の節）。

## 時期

設計者が次の時期を了承した（2026-10-03）。

| 項目 | 時期の案 |
|---|---|
| 導入のスクリプト | 初回リリースの前の改造（難易度が低く、ブラウザで取得したときの Gatekeeper の警告を避ける手順にもなる） |
| `SHA256SUMS` への署名と、スクリプトによる検証 | プロジェクトの鍵を設けるとき |
| macOS の署名と公証 | 正式リリースを目処（設計者の方針） |
| `.pkg` のインストーラ | 正式リリースの前に要否を決める |

## 設計書に移すときの候補

- ADR 0233 の決定 2（導入のスクリプトを用意しない）を改める ADR。スクリプトの手順、置き場所、試験（ADR 0234 の試験の項目の追加）を定める。
- 正式リリースで署名と公証を行う方針の ADR（ADR 0233 の決定 4 と帰結を改める）。配る形（`tar.gz` か `.pkg`）は OPEN として登録する。
- OPEN-060 に、確かめた事実（Gatekeeper の条件、Homebrew、導入のスクリプト）と、残る要検証の項目（公証に出す形式、ticket のネットワークでの確認、`tar.gz` の展開で隔離の属性が引き継がれるか）を記す。
- 05-01「配布形態」の改訂。
