## 現状

パッケージ管理は、設計書の上でまだ議論していない。決まっていること・登録済みの論点は次のとおりである。

- 章 06-05「パッケージ管理」は「未着手」で、目的と範囲に「依存解決、ロックファイル」とあるだけである。
- 初回リリース版はパッケージ管理と外部の関数の層を含めない（ADR 0137、03-01）。
- 設定ファイルは設けない。根のディレクトリは実行を始めるファイルのあるディレクトリである（ADR 0126・0127）。設定ファイルを設けるかは OPEN-048 で決める。
- 標準ライブラリは `Benitoite`、吟味の前のものは `Benitoite.Unofficial` の名前空間に置く（ADR 0128・0286）。外部のパッケージの名前空間・取得元・エフェクトとの関係は OPEN-049 で決める。
- モジュールはすべてソースを読み、プログラム全体を検査する（ADR 0156）。

## 他の言語の方式

下の記述は、知識の範囲で確かなものだけを書いた。設計書へ移すときは、一次資料で確かめて 08-03 の調査記録に加える。

### 中央のレジストリと版の範囲の解決（Rust の Cargo、npm、Python の pip・uv）

設定ファイル（`Cargo.toml`・`package.json`・`pyproject.toml`）に、パッケージの名前と版の範囲（`^1.2` など）を書く。道具が中央のレジストリ（crates.io・npm・PyPI）から範囲に合う最新の版を選び、選んだ結果をロックファイル（`Cargo.lock`・`package-lock.json`・`uv.lock`）に記録する。

- 長所: 名前だけで依存を書ける。検索・文書・利用の統計が一か所に集まる。版の範囲により、修正版を自動で取り込める。
- 短所: レジストリの運営が要る。名前の早い者勝ちと、似た名前による攻撃（typosquatting）が起きる。導入の時点で任意のコードを実行する仕組み（Cargo の `build.rs`、npm の `postinstall`、Python の `setup.py`）が、供給網の攻撃の主な経路になっている。範囲で解く方式は、ロックファイルがないと実行ごとに結果が変わる。
- LLM との関係: LLM が存在しないパッケージ名を書き、その名前を攻撃者が先に登録する事例（slopsquatting と呼ばれる）が報告されている【要検証: 出典を確かめる】。名前だけで取得できる方式ほど、この攻撃が通りやすい。

### URL をパッケージの名前にする（Go のモジュール）

モジュールの名前が取得元のパス（`github.com/user/repo`）を兼ねる。`go.mod` に必要な最小の版を書き、道具は「要求された版のうち最大のもの」を選ぶ（最小版選択、MVS）。`go.sum` に中身のハッシュを記録し、公開のチェックサムのデータベースと照合する。プロキシが取得したものを保存する。

- 長所: レジストリへの登録が要らない。MVS は解が一意で、新しい版が出ても結果が変わらないので、ロックファイルの役割を `go.mod` が兼ねる。導入の時点でコードを実行しない。
- 短所: 取得元を移すと名前が変わる。大きな版を上げるときは名前に `/v2` を付ける規則があり、初学者が戸惑う。プロキシとチェックサムのデータベースは Google が運営している。

### URL と中身のハッシュを直接書く（Roc、初期の Deno）

Roc は、アプリケーションのヘッダに、中身のハッシュを含む HTTPS の URL を書く（08-03 に記録済み）。中央のレジストリも設定ファイルもない。Deno は当初 URL で取り込み、後に設定ファイル（`deno.json`）の import の対応表、ロックファイル（`deno.lock`）、独自のレジストリ（JSR）と `npm:` の指定を加えた。

- 長所: 一つのファイルで完結する。ハッシュが一致しなければ使わないので、取得元が改ざんされても気付ける。運営が要らない。
- 短所: 版を上げるには URL とハッシュを書き換える必要があり、人間が手で書く形ではない。同じパッケージを複数のファイルが別の版で取り込みうる。Deno が設定ファイルとレジストリを後から加えたことは、URL だけの方式が規模の大きいプロジェクトで不便だったことを示している可能性がある【要検証: Deno の変更の理由を一次資料で確かめる】。

### 版の付け方を道具が強制する（Elm）

Elm のパッケージ管理は、公開する前に API の差分を調べ、関数を消したり型を変えたりしたのに大きな版を上げていなければ、公開を拒む。パッケージは Elm だけで書き、JavaScript を含められない（含められるのは公式の組織のパッケージだけである）。

- 長所: 版の番号が API の互換性を表すことを、道具が保証する。外部の関数を含められないので、パッケージは型の上で純粋なことが保証される。
- 短所: 外部の関数を使えないことへの不満が利用者から大きく、コミュニティが分かれる一因になった。

### 互いに動作を確かめた版の組を配る（Haskell の Stackage）

Stackage は、同時にビルドとテストが通る版の組（スナップショット）を定期的に公開する。利用者はスナップショットの名前を一つ選ぶ。

- 長所: 依存の組み合わせの問題を、配る側が先に解いておける。
- 短所: 組を選んで保つ人手が要る。組に入っていないパッケージは別に指定する。

### 一つのスクリプトに依存を書く（Python の PEP 723、Ruby の `bundler/inline`、Elixir の `Mix.install`、Kotlin の `@file:DependsOn`）

設定ファイルを置かずに、スクリプトの先頭のコメントや式で依存を書く（08-03 に記録済み）。

- 長所: 一つのファイルのスクリプトのまま配れる。Benitoite の「個人用の道具を手軽に作る」用途と、Agent Skills のスクリプトに合う。
- 短所: 複数のファイルのスクリプトでは、依存をどのファイルに書くかの規則が要る。ロックファイルを持たない形では、実行ごとに版が変わりうる（uv は PEP 723 のスクリプト用のロックファイルを作れる【要検証】）。

### 中身のハッシュで定義を指す（Unison）

Unison は、定義をその中身（構文木）のハッシュで識別し、名前はハッシュに付ける別名として扱う。

- 長所: 版の衝突が原理の上で起きない。同じ定義の二つの版を同時に使える。
- 短所: ファイルとテキストのエディタを前提とする開発の流れと大きく異なり、専用の道具が要る。Benitoite の「ソースのファイルを LLM が書く」前提とは合わない。

### Perl の CPAN

Benitoite が精神を受け継ぐ Perl は、CPAN という中央の置き場と、利用者が投稿したテストの結果を集める仕組み（CPAN Testers）を早くから持った。

- 長所: 「たいていのことは誰かが既に書いている」状態を作り、Perl の怠惰の美徳を支えた。
- 短所: 品質のばらつきが大きく、どれを選ぶかの判断を利用者に委ねる。

## Benitoite に固有の条件

他の言語と比べるときに効く、Benitoite の条件は次のとおりである。

1. **パッケージのエフェクトが型に現れる。** パッケージの関数の型には `uses` が付くので、パッケージが行いうる外部の操作は、ソースを読まずに型から分かる。版を上げてエフェクトが増えれば、型が変わる。設計原則 2（契約と権限の変更を見落とさせない）に照らすと、依存の更新でエフェクトが増えたことを、利用者に示す仕組みが作れる（Elm の API の差分の検査を、エフェクトまで広げた形）。
2. **導入の時点でコードを実行する仕組みが要らない。** 外部の関数の層がなく（ADR 0137）、ソースを読んで全体を検査する（ADR 0156）ので、ビルドのスクリプトに当たるものがない。後の版の外部の関数は、ビルド済みの WASM のモジュールに限る（ADR 0139）ので、外部の関数の層を加えても、導入の時点のビルドは要らない（後述の「パッケージに WASM を含める場合」）。
3. **書き手は主に LLM、確認するのは人間である。** 利用者が依存の追加を確認するとき、名前と版より「そのパッケージがどのエフェクトを使うか」の方が判断しやすい。名前だけで取得できる方式は、LLM が書いた存在しない名前や似た名前を通しやすい。
4. **一つのファイルのスクリプトと Agent Skills が主な用途である。** Skill はディレクトリを単位に配るので、依存を Skill のディレクトリの中に写して置く（vendoring）形と相性がよい。設定ファイルを親のディレクトリへ辿って探す方式は、起動した場所で効く設定が変わるので避けた（ADR 0127）。
5. **サーバモードでは、登録したスクリプトに署名を求められる**（ADR 0190）。依存も同じ信頼の範囲に入れるには、依存の中身をハッシュで固定する必要がある。
6. **初回リリース版の後に、標準ライブラリを `Unofficial` から標準へ移す仕組みがある**（ADR 0286）。公式が配る追加のライブラリ（git のラッパーなど）を、パッケージとして配るか、標準ライブラリに入れるかの線引きが要る。

## 論点

議論を始めるための論点を挙げる。順序は依存の順である。

1. **パッケージ管理を設けるか、どの版で設けるか。** 設けない場合は、標準ライブラリを厚くし、手元のファイルを写して使う（vendoring）だけにする。Benitoite の用途（個人の道具、Skill）では、これで足りる範囲がどこまでかを先に見積もる。
2. **名前の付け方と取得元。** 中央のレジストリ（Cargo 型）、URL を名前にする（Go 型）、URL とハッシュを直接書く（Roc 型）のどれにするか。運営の手間と、LLM による誤った名前への耐性が主な比較の軸になる。
3. **依存を書く場所。** 設定ファイル（OPEN-048 とあわせる）、実行を始めるファイルの先頭（PEP 723・Roc 型）、その両方。
4. **版の解決。** 範囲で解いてロックファイルに記録する（Cargo 型）か、最小版選択（Go 型）か、版を固定して書く（Roc 型）か。
5. **エフェクトとの関係。** 依存の追加と更新のときに、パッケージが使うエフェクトを利用者に示すか。エフェクトの増加を、大きな版の変更として扱わせるか（Elm 型の強制）。パッケージが使えるエフェクトを、利用する側が制限できるようにするか（「このパッケージには File.Read だけを許す」）。最後のものは、コマンドの代替の検討の選択肢 Y（ライブラリの単位で許可する）と同じ問いである。
6. **外部の関数の層との関係。** パッケージに外部の関数（WASM のモジュール。ADR 0139）を含められるようにするか。含めても条件 2 は崩れないが、中身をソースとして読めないこと、資源の消費の上限などの別の論点が生じる（後述の「パッケージに WASM を含める場合」）。Elm のように公式のパッケージだけに限る選択肢もある。
7. **名前空間。** パッケージのモジュールを `import 何.何` の形でどう書くか（OPEN-049）。`Benitoite`・`Benitoite.Unofficial`・利用者のモジュールとの衝突の扱い。

## 暫定の見立て

議論の叩き台として、現時点の見立てを書く。決定ではない。

- 運営の手間を考えると、初めは中央のレジストリを持たず、URL とハッシュで固定する方式（Roc 型）か、Go 型の方式から始めるのが現実的である。ハッシュによる固定は、サーバモードの署名（条件 5）とも合う。
- 版の解決は、範囲で解く方式より、固定するか最小版選択にする方が、LLM と利用者の両方にとって結果を予測しやすい。
- 条件 1 を活かし、依存の追加と更新のときにエフェクトの差分を示す仕組みを、他の言語にない Benitoite の特徴にできる可能性がある。
- パッケージに WASM を含めることは、ADR 0139 の制約（ホストの関数を通してしか外に作用できない）の下では、エフェクトの保証を崩さない。含めるかは、残る論点（ソースとの対応、資源の上限）を外部の関数の層の設計（04 部、OPEN-051）とあわせて決める。

## パッケージに WASM を含める場合

後の版の外部の関数は、WASM のモジュールの関数に限り、C の ABI の共有ライブラリは呼ばない（ADR 0139 の決定 1）。Rust のコードは、作者が WASM にビルドしてから使う。したがって、パッケージに含めうるのは Rust のソースやネイティブのコードではなく、ビルド済みの WASM のモジュールである。両者は性質が大きく違う。

| 観点 | Rust のソース・ネイティブのコード（Benitoite は採らない） | ビルド済みの WASM のモジュール（ADR 0139） |
|---|---|---|
| 導入の時点のビルド | 要る。コンパイラと C のライブラリが要り、環境ごとに失敗しうる | 要らない。作者がビルド済みのものを配る |
| 導入の時点の任意のコードの実行 | ビルドのスクリプト（`build.rs` など）が実行される | ない |
| 環境の差 | OS と CPU ごとに別のバイナリが要る | 一つの形式で、処理系の WASM の実行系が動く環境ならどこでも動く【要検証: 対応しない環境の有無】 |
| 外への作用 | 処理系を通らずに、ファイル・ネットワーク・プロセスに触れられる。Deno の文書は、FFI を許すことは実質的にすべてを許すことだと書く | 処理系が与えるホストの関数（標準ライブラリの IO の操作）を通してしか作用できない（決定 4）。実行時の権限制御を通る |
| エフェクトの宣言の信頼 | 宣言を信用するしかない（Haskell・OCaml・Rust の FFI と同じ） | モジュールが取り込むホストの関数を処理系が読めるので、宣言したエフェクトがそれを含むかを検査できる（決定 4）。ホストの関数を取り込まないモジュールは、実行環境の隔離により純粋であることが保たれる |

このため、WASM を含めても、条件 1（エフェクトが型に現れる）と条件 2（導入の時点でコードを実行しない）は保たれ、依存関係地獄の問題 4（ネイティブのビルド）も生じない。Rust のコードについて論点 6 で心配した性質の崩れは、WASM には当てはまらない。

ただし、WASM に特有の論点が残る。

1. **中身をソースとして読めない。** 利用者や LLM がパッケージを吟味するとき、WASM の部分はバイナリである。ハッシュで固定できるのは「配られたものが変わっていないこと」までで、「公開されたソースからビルドしたものであること」は保証しない。対策の候補は、WASM の元のソースをパッケージに同梱させる、再現可能なビルドで照合できるようにする、公式のパッケージだけはこちらでビルドして配る、などである。エフェクトは処理系が検査できるので、ソースを読めないことの影響は「宣言したエフェクトの範囲の中で、意図と違うことをする」可能性に限られる（Benitoite のソースのパッケージでも、静的検査は意図との一致を保証しないので、性質としては同じである）。
2. **資源の消費。** WASM の関数は、処理系の VM の外で計算する。無限ループや大量のメモリの確保を止めるには、実行系の側で計算量（Wasmtime の fuel など）とメモリの上限を設ける必要がある【要検証: 採る実行系での手段】。中断の印（ADR 0163）を WASM の実行中にどう効かせるかも決める必要がある。
3. **モジュールのパスの基準。** ADR 0139 の決定 3 は、WASM のモジュールのパスを根のディレクトリからのパスとしている。パッケージの中の WASM は、パッケージの根からのパスとする規則が要る。
4. **処理系の大きさ。** WASM の実行系を処理系に含めると、配布物が大きくなる。パッケージに WASM を含めないなら、実行系は外部の関数の層の利用者のためだけに要る。

この論点は、外部の関数の層の未決事項（OPEN-051: 値の対応、失敗の扱い、ホストの関数の範囲、WASM の実行環境）とあわせて決める。

## 公式のライブラリの名前と取得元

URL の方式を採ると、公式のライブラリ（git のラッパーなど、標準ライブラリに入れずに別に配るもの）にも URL が要るか、という問いが生じる。ライブラリを三つの層に分けて考える。

| 層 | 例 | 名前 | 取得元 |
|---|---|---|---|
| 標準ライブラリ | `Benitoite.Text.Path` | `Benitoite.*`（ADR 0128） | 処理系に同梱。URL は要らない。版は処理系の版に従う |
| 公式の追加のライブラリ | git のラッパー | 未決（下の案） | 未決（下の案） |
| 第三者・利用者のライブラリ | 個人の道具 | ヘッダで付けた別名 | URL とハッシュ、または手元のパス |

### 名前と取得元を分ける

Roc は、ヘッダで URL に短い別名を付け（`pf: platform "https://…"`）、モジュールは別名で取り込む（`import pf.Stdout`）。URL が現れるのはヘッダの一か所だけで、本文のコードには現れない。Benitoite でも同じように、import の名前と取得元を分ければ、URL の長さや置き場所の移転は、ヘッダ（または設定ファイル）の一行の問題に限られる。ハッシュで中身を固定すれば、URL は「どこから取ってくるか」だけを表し、信頼の根拠はハッシュが担う。

### 公式の追加のライブラリの案

- **(a) ほかと同じく URL とハッシュで書く。** 例: このリポジトリの GitHub Releases（ADR 0233）に、ライブラリのアーカイブを置く。規則が一つで済み、処理系に特別扱いが要らない。しかし、URL が長く、リポジトリを移すと URL が変わる。LLM が公式の URL を書き誤ったとき、ハッシュの照合で取得は失敗するが、誤りの原因（URL の誤り）は分かりにくい。
- **(b) 予約した短い名前を、処理系が公式の取得元に対応させる。** 例: `benitoite:git@1.2`（Deno の `jsr:@std/…` に近い）。処理系が、名前から取得元とハッシュを引く対応表を持つ。対応表を処理系に埋め込めば、取得元を移しても処理系の更新で追従でき、ハッシュも処理系が保証する。しかし、公式のライブラリの更新が処理系のリリースに縛られる。対応表をネットワークから取る形にすると、それは小さなレジストリであり、運営が要る。
- **(c) 自前のドメインの URL を名前にし、実際の置き場所へ転送する。** Go の `golang.org/x/…` のような、名前と置き場所を分ける仕組み（vanity import path）に当たる。名前は移転しても変わらない。しかし、ドメインの取得と維持が要り、ドメインを失うと名前が他人に渡る危険がある。
- **(d) 公式の追加のライブラリを設けず、標準ライブラリ（`Benitoite.Unofficial` を含む）に入れる。** 名前と取得元の問題は生じない。しかし、処理系の配布物が大きくなり、git のラッパーのように外部のコマンドの版に追従するものも、処理系のリリースに縛られる。

### 暫定の見立て（この節）

- 標準ライブラリには URL を付けない。
- 公式の追加のライブラリは、(b) で処理系に対応表を埋め込む形が、LLM にとって書きやすく（短い名前を誤りにくい）、ハッシュの保証も処理系が持てる点で有力である。公式のライブラリの更新を処理系のリリースと切り離したくなった時点で、対応表を取得する形（小さなレジストリ）へ広げる。
- 第三者のライブラリは、ヘッダで別名を付けた URL とハッシュ（Roc 型）で書く。手元のライブラリはパスで書けるようにする。

## 非公式のモジュールを公式の追加のライブラリへ移せるか

設計者の方向: 公式の追加のライブラリは (b)（予約した短い名前を、処理系に埋め込んだ対応表で取得元とハッシュに変える）を有力とする。そのうえで、`Benitoite.Unofficial.*` のモジュールの行き先を、標準ライブラリ（`Benitoite.*`）だけでなく、公式の追加のライブラリにもできるかを検討する。

### 二つの軸を分ける

ADR 0286 の「標準」「非公式」は、吟味の状態を表す。公式の追加のライブラリにするかは、配り方の問題である。二つは別の軸なので、組み合わせとして次の行き先がありうる。

| 吟味の状態＼配り方 | 処理系に同梱 | 公式の追加のライブラリ |
|---|---|---|
| 吟味の前 | `Benitoite.Unofficial.*`（現在） | 版 0.x として配る、など |
| 吟味の後 | `Benitoite.*` | 版 1.0 以上として配る、など |

ただし、ADR 0286 の決定 7 は「吟味を終えたモジュールは標準に移す」と定めているので、行き先を増やすには、この決定を改める ADR が要る。取り込みの名前が変わり、互換性を壊す変更になる点は、標準へ移す場合と同じである。

### 移せるかを決める制約

公式の追加のライブラリは、取得したソースを読む普通のパッケージである。このため、次の二つの制約がある。

1. **組み込みのエフェクトを宣言するモジュールは移せない。** `File.Read` などの組み込みのエフェクトは、処理系が名前で照合し（ADR 0128 の決定 6）、実行時の権限制御の対象になる。パッケージが組み込みのエフェクトを定めると、権限制御の根拠がパッケージの側に移る。Roc で言えばプラットフォームに当たる部分であり、処理系に残す。該当するのは `Console`・`File`・`Process`・`Clock`・`Random`・`Http` である。`Clock` は prelude の `Task.race`・`Task.withTimeout` からも使われる。
2. **Rust で実装した組み込みの関数（`@builtin`）を使うモジュールは、そのままでは移せない。** `@builtin` は標準ライブラリのソースにだけ書ける（ADR 0157 の決定 3）。移すには、次のどれかが要る。
   - (i) Benitoite で書き直す。依存のない純粋なコードになるが、`Regex`・`Hash` のように速さが要るものは遅くなる。
   - (ii) Rust の実装を処理系に残し、`@builtin` を公式の追加のライブラリにも許す。名前空間は分けられるが、実装は処理系に同梱されたままで、処理系のリリースから切り離せない。得られるのは名前の整理だけである。
   - (iii) 外部の関数の層（ADR 0139 の WASM）ができた後、実装を WASM としてパッケージに含める。処理系から切り離せるが、外部の関数の層を待つ必要がある。

### 移す候補を選ぶ基準（案）

- 処理系に残す: 組み込みのエフェクトを宣言するもの。標準のモジュールが依存するもの。多くのスクリプトが使うもの（`Path`・`Json` など。Agent Skills の典型の作業で使う）。
- 公式の追加のライブラリにする: 外部の仕様やコマンドの版に追従して変わるもの（git のラッパー）。使う場面が限られるもの。Benitoite だけで書けるもの、または外部の関数の層ができた後のもの。

この基準では、現在の非公式のモジュールのうち、移す候補になりうるのは `Csv`・`Encoding`・`Hash` くらいである。どれも `@builtin` を使う見込みなので【要検証: 実装プランで各関数の実装の形を確かめる】、移す時期は外部の関数の層の後か、Benitoite で書き直すと決めたときになる。一方、git のラッパーは `Process` の上に Benitoite で書けるので、制約にかからず、最初から公式の追加のライブラリとして作れる。

## 依存関係地獄を言語仕様で防げるか

「依存関係地獄」は一つの問題ではなく、原因の違う複数の問題をまとめて呼んだ語である。原因ごとに分けると、言語仕様で防げるもの、道具で防ぐもの、どちらでも防げないものに分かれる。

### 原因の分類

| 問題 | Python での現れ方 | 防ぐ層 |
|---|---|---|
| 1. 版の衝突（ダイヤモンド依存） | A は C の 1.x を、B は C の 2.x を要する。一つのプロセスで、一つの名前のモジュールは一つしか読めない（`sys.modules`）ので、両立できない | 言語仕様（モジュールの同一性の規則） |
| 2. 環境の汚染 | システムの Python や共有の `site-packages` に入れたものが、別のプロジェクトに効く | 道具（venv・uv）。言語仕様で「共有の導入先」を持たないことにもできる |
| 3. 再現しない | 版の範囲で解き、ロックファイルがないと、実行する日によって版が変わる | 道具（ロックファイル、ハッシュによる固定） |
| 4. ネイティブのコードのビルド | C の拡張のビルドに、コンパイラ・C のライブラリ・ABI の一致が要る。環境ごとに失敗する | 言語仕様（パッケージに何を含められるか） |
| 5. 版の番号が互換性を表さない | 小さな版の更新で API が変わる | 言語仕様と道具（API の差分の検査） |
| 6. 処理系の版との不一致 | パッケージが新しい（古い）Python の機能に依存する | 言語仕様（パッケージごとの言語の版） |

uv が大きく改善したのは主に 2 と 3 である（速い解決、プロジェクトごとの環境、ロックファイル）。1 と 4 は Python の言語とパッケージの形式に根があり、道具だけでは取り除けない。

### 言語仕様で取りうる手段

**(1) 同じパッケージの複数の版を、一つのプログラムに共存させる（問題 1）。** モジュールの同一性を「名前」ではなく「パッケージの識別（版またはハッシュ）とモジュールのパス」で決める。Rust は、互換性のない版（`1.x` と `2.x`）の同じクレートを一つのビルドに含められる。npm は `node_modules` を入れ子にして共存させる。Go は大きな版を名前に含める（`/v2`）ので、別のモジュールとして共存する。

共存させると、C 1.x の型と C 2.x の型は別の型になる。A から受け取った C 1.x の値を、B の C 2.x を要する関数に渡すと、型の誤りになる。Rust ではこれが「`expected C::Foo, found C::Foo`」のような分かりにくい誤りになる【要検証: 現在の rustc の診断の文面】。Benitoite では、診断に版（またはハッシュ）と、どの依存の経路で入ったかを示せば、LLM が原因を読み取れる。

Benitoite の既存の規則は、共存に向いている。

- トップレベルには関数・型・定数式しか置けず（ADR 0055・0123）、モジュールが可変の大域の状態を持たない。同じモジュールが二つ読まれても、「登録の表が二つに分かれる」のような、複製による不具合が起きない。
- 型クラスの実装は、型クラスか型を宣言したモジュールにしか書けない（孤立した実装の禁止、ADR 0061）。版の違う型は別の型なので、実装が重なることもない。

**(2) 公開の依存と非公開の依存を区別する（問題 1 を小さくする）。** パッケージ A が C を使っていても、A の公開の関数の型に C の型が現れなければ、C の版が B と食い違っても利用者には影響しない。食い違いが問題になるのは、A の公開の API に C の型が現れる場合（公開の依存）だけである。Rust はこの区別を RFC 1977（public/private dependencies）で提案した【要検証: 現在の安定化の状況】。Benitoite は、公開の契約に型とエフェクトが含まれる（ADR 0154）ので、「非公開と宣言した依存の型が、公開の関数の型に現れたら誤り」と静的に検査できる。こうすれば、利用者が版を揃える必要があるのは公開の依存だけになる。

**(3) 公開の契約の差分で、版の付け方を検査する（問題 5）。** Elm と同じく、公開の関数の型の変更を検査し、互換性を壊す変更なのに大きな版を上げていなければ、公開を拒む。Benitoite では公開の契約がエフェクトを含むので、「エフェクトが増えた」ことも互換性を壊す変更として扱える。これは権限の変更を見落とさせない設計原則 2 にも沿う。

**(4) パッケージに含められるものを、ソースと WASM に限る（問題 4）。** ネイティブのコードとビルドのスクリプトを含めなければ、環境ごとのビルドの失敗が起きない。外部の関数の層は WASM で作る方針である（ADR 0139）。WASM は環境に依存しない一つの形式なので、パッケージに含めても問題 4 は生じない【要検証: WASM の実行系が対応しない環境の有無】。

**(5) パッケージごとに言語の版を宣言する（問題 6）。** Rust の edition は、クレートごとに言語の版を選び、版の違うクレートを一つのビルドで混ぜられる。Benitoite でも、パッケージが前提とする言語の版を宣言し、処理系が版ごとの規則で読むようにできる。ただし、処理系が複数の版の規則を保つ負担が生じる。正式リリース版の前（0.x の間）は互換性を壊す変更がありうる（ADR 0236）ので、それまでは「対応する処理系の版の範囲」を宣言するだけにとどめる案もある。

**(6) 共有の導入先を持たない（問題 2）。** パッケージは、ハッシュで識別して読み取り専用の置き場（Go のモジュールのキャッシュ、Nix のストアに近い）に保存し、どのスクリプトがどの版を使うかは、そのスクリプトの依存の記述（とロックファイル）だけで決まるようにする。「導入する」操作がなく、ほかのプロジェクトの状態が効かない。

### 言語仕様でも防げないもの

- 版の違う二つのパッケージの間で、同じ値を受け渡したい場合（問題 1 の本体）。型が違うので、変換の関数を書くか、どちらかの版に揃えるしかない。言語仕様にできるのは、その必要を明確な診断で示すことまでである。
- 意味の互換性。型とエフェクトが変わらなくても、振る舞いが変わることはある。(3) が保証するのは、型とエフェクトの互換性だけである（静的検査の保証の範囲と同じ）。
- 依存の数そのものの増加。標準ライブラリと公式の追加のライブラリを厚くして、小さな第三者のパッケージに頼る場面を減らすのは、言語仕様ではなく、ライブラリの方針の問題である。

### 暫定の見立て（この節）

(1)・(2)・(3)・(6) は、Benitoite の既存の規則（大域の状態がない、孤立した実装の禁止、公開の契約にエフェクトを含める）と組み合わさるので、他の言語より少ない追加で入れられる見込みがある。特に (2) と (3) は、型とエフェクトを静的に追跡する言語だから検査できるもので、Benitoite のパッケージ管理の特徴にできる。(4) は外部の関数の層の設計に、(5) は正式リリース版の互換性の方針に依存するので、それらとあわせて決める。

## パッケージと WASM の署名

設計者の問い（2026-10-03）: git のラッパーのような公式の追加のライブラリにも、有志が作るパッケージとあわせて署名を求めるべきか。WASM のモジュールは署名できるか。

### 現在の署名の範囲

サーバモードの登録のときの署名は、既定では求めない。求めるときは、実行を始めるファイルから import で辿るすべてのファイルについて、根のディレクトリからの相対パスと SHA-256 のハッシュを並べた一覧に、SSH の署名を付ける（ADR 0190・0202、06-07「署名」）。署名の名前空間は `benitoite-script` である。

パッケージを加えると、二つの穴が生じる。

- パッケージのファイルは根のディレクトリの外（取得したものの置き場）にあるので、今の一覧の規則では対象にならない。
- `@external` が指す WASM のモジュールは import で辿るファイルではないので、根の中にあっても一覧に入らない（ADR 0139 の決定 3 はパスを根の下に限るが、一覧の規則は import だけを数える）。

### 署名で確かめたいことを分ける

署名に求めるものは、二つに分かれる。

| 確かめたいこと | 手段 | 求める度合い |
|---|---|---|
| 完全性（取得したものが、スクリプトの作者が選んだものと同じか） | 依存の記述に書いた中身のハッシュ | 常に必須 |
| 出所（誰が作ったものか） | パッケージの作者の署名 | 下記 |

完全性は、署名がなくてもハッシュで保てる。スクリプトの依存の記述（ヘッダか設定ファイル）が依存のハッシュを含み、スクリプトの署名がその記述を含むので、スクリプトの作者の署名一つで、依存の中身まで固定される（依存の依存も、それぞれの依存の記述のハッシュを通して連鎖する）。したがって、一覧の規則を「import で辿るファイル、`@external` が指すファイル、依存の記述」に広げれば、前述の穴の一つ目と二つ目は、パッケージの作者の署名がなくても塞がる。

出所の署名が効くのは、依存を加えるときと更新するときである。ハッシュは「前と同じもの」を保証するが、新しい版のハッシュは、置き場所が乗っ取られていても、乗っ取った者の版のハッシュとして書かれうる。作者の署名を確かめれば、新しい版が前の版と同じ作者のものかを確かめられる。

### 公式の追加のライブラリ

公式の追加のライブラリは、処理系に埋め込んだ対応表で名前からハッシュを引く（前述の (b)）。対応表が処理系の一部なので、完全性の根拠は処理系の配布物そのものになり、ライブラリごとの署名がなくても、取得したものが公式の版であることは確かめられる。

それでも、公式のライブラリにはプロジェクトの鍵で署名を付けておくのがよい。理由は次の三つである。

- 対応表をネットワークから取る形（小さなレジストリ）へ広げたとき、対応表とライブラリを確かめる根拠が要る。
- 処理系の配布物自体には署名がない（`SHA256SUMS` にも署名しない。ADR 0233）。公式の鍵を設けるなら、配布物の `SHA256SUMS` にも同じ鍵で署名でき、信頼の根拠を一つにできる。
- 有志のパッケージと同じ形式で署名しておけば、検証の仕組みを一つにできる（設計者の問いの「あわせる形」）。

### 有志のパッケージ

同じ形式の署名を付けられるようにするが、既定では求めない。

- 求めると、作者の鍵をどう配り、利用者がどれを信頼するかの仕組みが要る。中央の鍵の登録所や透明性の記録（Sigstore など）は、中央のレジストリを持たない方針（前述の見立て）と同じ理由で、初めは持たない。
- 代わりに、最初に加えたときの作者の鍵を、ロックファイル（または依存の記述）に記録し、更新のときに同じ鍵の署名を求める（最初の使用で信頼する形、TOFU）。鍵が変わったら、更新を止めて利用者に示す。署名のないパッケージは、ハッシュだけで扱い、依存を加えるときに「出所を確かめられない」と示す。
- サーバモードの方針で、依存にも信頼する鍵の署名を求める設定を選べるようにする（既存の `allowed_signers` を使う）。

### 署名の形式

スクリプトの署名（ADR 0202）と同じ形にする。パッケージの全ファイル（ソース、WASM のモジュール、依存の記述）の相対パスとハッシュの一覧に、SSH の署名を付ける。名前空間は、スクリプトと区別するために別の値（`benitoite-package` など）にする。名前空間を分けないと、パッケージに付けた署名を、スクリプトの登録の署名として使い回せてしまう。

### WASM のモジュールの署名

WASM のモジュールは、ただのバイト列のファイルなので、上の一覧に含めれば、パッケージやスクリプトの署名で覆える。別の仕組みは要らない。

WASM には、モジュールの中のカスタムセクションに署名を埋め込む形式の提案もある（WebAssembly の tool-conventions に書式があり、`wasmsign2` が実装する）。モジュールの一部のセクションだけを署名したり、複数の署名を付けたりできる【要検証: 提案の現在の状態】。Benitoite では、ファイルの一覧への署名で足り、形式を一つに保てるので、採らない。WASM を他の処理系と共有する場面が生じたら、検証だけ対応するかを考える。

WASM はソースとして読めない（前述の「パッケージに WASM を含める場合」）。署名が保証するのは「誰がそのバイト列を配ったか」までで、「公開されたソースからビルドしたか」は保証しない。このため、WASM を含む有志のパッケージには、署名のないものを加えるときの警告を強める（または署名を必須にする）案がある。

### 暫定の見立て（この節）

- 署名の一覧の対象を、import で辿るファイルに加えて、`@external` が指す WASM のモジュールと、依存の記述まで広げる。スクリプトの作者の署名一つで、依存の中身まで固定される。
- 公式の追加のライブラリには、プロジェクトの鍵で署名する。鍵を設けるなら、処理系の配布物の `SHA256SUMS` にも署名する。
- 有志のパッケージは、同じ形式の署名を任意とし、更新のときに作者の鍵の一致を確かめる。サーバモードでは、方針で依存の署名を必須にできる。
- WASM は、ファイルの一覧に含めて同じ署名で覆う。WASM を含む有志のパッケージの扱いは、外部の関数の層とあわせて決める。

## 特定の版のライブラリを読み込む仕掛けと、取得元の制約

設計者の問い（2026-10-06）: 特定の版のライブラリを読み込むようにする仕掛けを検討する。あわせて、取得元の制約（git のリモートリポジトリにあるものに限る、など）を検討する。

この節は、前述の見立て（中央のレジストリを持たない、URL とハッシュで固定する、署名の一覧に依存の記述を含める）を前提とする。依存を書く場所（論点 3）と名前空間（論点 7、OPEN-049）は未決なので、例の書き方は仮のものである。

### 版を何で指すか

git のリポジトリから取得するとき、版を指す手段は三つある。性質がそれぞれ違う。

| 手段 | 例 | 人が読めるか | 変わりうるか | git に依存するか |
|---|---|---|---|---|
| タグ | `v1.2.0` | 読める。互換性の程度も版の番号で表せる | 変わる。タグは付け直せる（強制の push） | する |
| コミットの ID | `3f2a…`（40 桁） | 読めない | 変わらない。ただし SHA-1 である | する |
| 中身のハッシュ | `sha256-…` | 読めない | 変わらない | しない。ファイルの一覧と中身から計算する |

他の言語は、この三つを組み合わせている。

- Go のモジュールは、版をタグ（`v1.2.0`）で指し、タグのないコミットは版の番号の形に直した名前（pseudo-version）で指す。`go.sum` に記録するのはコミットの ID ではなく、モジュールのファイルの一覧と中身から計算したハッシュである。このため、git から取っても、プロキシからアーカイブで取っても、同じハッシュで確かめられる。
- Cargo の git の依存は、`tag`・`branch`・`rev` のどれかで指し、選んだコミットの ID を `Cargo.lock` に記録する。crates.io は、git の依存を持つクレートの公開を受け付けない。
- Swift Package Manager は、依存を git の URL と版の範囲で書き、範囲に合うタグを選ぶ。選んだコミットの ID を `Package.resolved` に記録する。
- Zig は、`build.zig.zon` にアーカイブの URL と中身のハッシュを書く。ハッシュの対象は、パッケージが `.paths` で挙げたファイルに限る。
- npm は、git の URL に `#semver:^1.2` を付けて、タグを範囲で選べる。

案: 依存の記述にはタグ（版）を書き、信頼の根拠は中身のハッシュに置く。コミットの ID は、取り直すための手掛かりとして添える。

- タグは、利用者と LLM が読み、`update` のときに比べるためのものとする。タグが付け直されても、ハッシュが合わなければ使わないので、気付ける。
- 中身のハッシュは、Go と同じく、git の外で計算する（ファイルのパスを並べ、パスと中身から SHA-256 で計算する。計算の規則は Benitoite が定める）。git のコミットの ID を根拠にしない理由は三つある。取得の手段（git、アーカイブ、手元の写し）によらず同じ値で確かめられること。SHA-1 の衝突の弱さに依らないこと。署名の一覧（前述の「パッケージと WASM の署名」）が使う SHA-256 と揃うこと。
- コミットの ID は、タグが消えたり付け直されたりしたときに、元のコミットを取り直すために使う。

### 依存の記述の形（仮）

依存を書く場所は論点 3 で決めるが、どこに置くかによらず、一つの依存の記述は次のものを含む。

```text
dependency Git
  source  "https://github.com/example/benitoite-git"
  version "v1.2.0"
  commit  "3f2a…"
  hash    "sha256-…"
```

- `Git` は、取り込みに使う別名（Roc の `pf:` に当たる）である。本文は `import Git.Repo` のように別名で取り込み、URL は本文に現れない（前述の「名前と取得元を分ける」）。
- `commit` と `hash` は、人や LLM が手で書くものではない。`benitoite add https://… v1.2.0` のような命令が取得して計算し、書き込む。LLM が `hash` のない記述を書いたら、検査はそれを誤りとし、書き込むための命令を診断で示す。ハッシュのない記述を、実行のときに黙って取得して使うことはしない。

取得した結果を別のロックファイルに記録する形（Cargo 型）も考えられる。しかし、版とハッシュを依存の記述の一か所に書けば、一つのファイルのスクリプトのまま配れ（条件 4）、スクリプトの署名が依存の中身まで覆う（前述の「署名で確かめたいことを分ける」）。このため、記述に直接書く形（Roc 型）を有力とする。

依存を書けるのは、根ごとに一か所（実行を始めるファイルか、プロジェクトの設定ファイル）に限る案を採る。モジュールのファイルごとに依存を書けると、どのファイルを取り込むかで取得するものが変わり、全体を見渡せなくなるからである。パッケージの側にも、そのパッケージの依存を書く場所が一か所要る（パッケージの根に置く依存の記述）。

### 版の選び方と、同じパッケージの複数の版

依存の依存が同じパッケージを違う版で求めることがある（A は C の `v1.2.0` を、B は C の `v1.3.0` を求める）。前述の「依存関係地獄を言語仕様で防げるか」の (1) で、モジュールの同一性をパッケージの識別で決めれば共存できるとした。何をパッケージの識別にするかで、扱いが分かれる。

- **(i) 版ごとに別のパッケージとする。** 識別は中身のハッシュである。C の `v1.2.0` と `v1.3.0` が両方読まれ、それぞれの型は別の型になる。A が C の型を公開の関数に出していると、A と B の間で C の値を受け渡せない。修正版の違いだけで型が分かれるので、この誤りが頻繁に起きる。
- **(ii) 大きな版ごとに一つとし、その中では最小版選択で選ぶ（Go 型）。** 識別は取得元と大きな版（`v1`）である。求められた版のうち最大の `v1.3.0` を一つだけ読む。`v1` と `v2` は共存する。

案: (ii) を採る。選んだ結果（依存の依存も含めて、読むパッケージのすべて）を、根の依存の記述に書き込む。Go も、`go.mod` に依存の依存を書き出す形に改めている（Go 1.17 からの module graph pruning）。根の記述が全体を挙げていれば、スクリプトの署名一つで全体が固定され、利用者は読むものを一か所で確かめられる。

0.x の版（`v0.3.1` など）は互換性を約束しないので、`v0.3` と `v0.4` を別の大きな版として扱う（Cargo の版の範囲の規則と同じ考え方）か、0.x の間は版ごとに別とするかを決める必要がある。

### 取得元の制約

取得元の候補は次のとおりである。

| 記号 | 取得元 | 用途 |
|---|---|---|
| S1 | git のリモートリポジトリ（HTTPS） | 公開のパッケージ |
| S2 | git のリモートリポジトリ（SSH） | 非公開のリポジトリ（社内など） |
| S3 | アーカイブの URL（`.tar.gz` など）とハッシュ | git を使わずに配るもの |
| S4 | 手元のパス | 開発中のパッケージ、写して置いたもの（vendoring） |
| S5 | 予約した短い名前（`benitoite:git` など） | 公式の追加のライブラリ（前述の (b)） |

案: S1・S2・S4・S5 を受け付け、S3 は後で要望が出てから考える。git のリモートリポジトリに限る（S3 を受け付けない）利点は次のとおりである。

- タグの一覧を取得元から読める（`git ls-remote` に当たる操作）ので、`update` のときに新しい版を示せる。アーカイブの URL には版の一覧がない。
- 取得の手段が一つで、処理系に含める取得の仕組みが一つで済む。
- ホスティングの自動生成のアーカイブ（GitHub のタグのアーカイブなど）は、同じタグでもバイト列が変わることがある【要検証: GitHub の 2023 年の事例】。中身のハッシュを git の外で計算する案なら、この問題は S1 では生じない。

S4 の手元のパスは、開発の途中の確認と、Skill のディレクトリに写して置く用途に限る。公開するパッケージの依存の記述には S4 を書けないことにする（crates.io が git の依存を受け付けないのと同じ理由で、受け取った側では辿れないから）。写して置いたものも、記述のハッシュで確かめる。

S1・S2 の取得には、次の制約を付ける。

1. **プロトコル**: `https://` と SSH に限る。`http://`・`git://`（暗号化も認証もない）、`file://`（手元のパスは S4 で書く）は受け付けない。
2. **版の指し方**: 記述に書く版は、版の番号の形のタグ（`v1.2.0`）に限る。タグのないコミットを使うときは、Go の pseudo-version のように、コミットの ID から作った版の番号で書く。ブランチの名前は、指すコミットが変わるので、記述に書けない。`add` の命令にブランチの名前を渡した場合は、その時点のコミットに直して書き込む。
3. **一つのリポジトリに複数のパッケージ**: Go と同じく、パッケージの根をリポジトリの中のディレクトリにでき、そのタグを `sub/v1.2.0` の形にする案がある。設けるかは決める。
4. **読むもの**: 指したコミットの木（tree）を、作業ツリーに展開せずに、git のオブジェクトから直接読む。チェックアウトをしないので、hooks、`.gitattributes` の filter（Git LFS の smudge など）、`core.fsmonitor` が起動しない。これは自前のエージェントハーネスの git の操作（[自前のエージェントハーネス](post-first-release-agent-harness.md)の G2）と同じ理由であり、同じ git のライブラリで行う【要検証: ライブラリが木の読み取りと、浅い取得（指したコミットだけの取得）に対応しているか】。
5. **パッケージに含めるファイル**: `.bnt` のソース、WASM のモジュール（外部の関数の層の後）、依存の記述、使用許諾の文書、説明の文書に限り、それ以外のファイルは読まず、ハッシュの対象にも入れない（Zig の `.paths` に近い）。次のものは誤りとする: サブモジュール（版を固定していない別の取得元を持ち込む）、根の外を指すシンボリックリンク、大文字と小文字だけが違う二つのパス（macOS の既定のファイルシステムで衝突する）。大きさの上限も設ける。
6. **取得元のホスト**: 処理系は特定のホスト（GitHub など）に限らない。利用者の方針（サーバモードの方針のファイル）で、許すホストの一覧を書けるようにする。ハーネスのウェブの取得のドメインの一覧と、同じ形にできる。
7. **認証**: S2 は利用者の SSH の鍵（`ssh-agent`）を使う。HTTPS の非公開のリポジトリの認証（git の credential helper を使うか）は、[秘密の扱い](post-first-release-secrets.md)とあわせて決める。

### 取得する時点と保存の場所

- 取得は、依存の記述にハッシュがあるものに限る。ハッシュのないものは取得しない（前述）。
- スタンドアロンモードでは、`run` と `check` が、手元にない依存を取得してよい。ハッシュで確かめるので、取得するものは記述が決めたものと同じである。利用者が怠惰のまま実行できることを優先する。ネットワークを使わない指定（`--offline` など）も設ける。
- サーバモードでは、実行のときに取得しない。登録のときに取得して確かめ、実行は保存したものだけを使う。
- 取得したものは、利用者のキャッシュのディレクトリに、中身のハッシュを名前にして読み取り専用で置く（前述の (6)）。プロジェクトの中に写す命令（`benitoite vendor` など）も設け、Skill のディレクトリにまとめて配れるようにする。
- 取得元のリポジトリが消えた、タグが付け直された、といった場合に備えるプロキシ（Go の proxy.golang.org に当たるもの）は、中央のレジストリを持たないのと同じ理由で持たない。備えは、写して置くことで利用者が行う。タグが付け直されていたら（記述のコミットの ID とタグの指すコミットが違えば）、その旨を示し、記述のコミットの ID で取り直す。

### 依存を加えるときに利用者へ示すもの

LLM が存在しないリポジトリの名前を書くと、攻撃者がその名前でリポジトリを作れる（slopsquatting の git 版）。名前だけで取得する方式より取得元の URL がはっきりするが、URL の所有者が意図した相手かは、利用者でなければ判断できない。このため、`add` は取得の後、次のものを示して確認を求める。

- 取得元の URL（ホストと所有者の名前を目立たせる）と、版、コミットの ID。
- パッケージが使うエフェクト（条件 1）。
- 署名の有無と、署名した鍵（前述の「有志のパッケージ」の TOFU）。

`update` では、加えて前の版からのエフェクトの差分を示す（前述の見立て）。

### 暫定の見立て（この節）

- 依存の記述には、別名、取得元、版（タグ）、コミットの ID、中身のハッシュを書く。後の二つは命令が書き込み、ハッシュのない記述は取得せずに誤りとする。
- 中身のハッシュは、git の外で、パッケージに含めるファイルから SHA-256 で計算する。
- 版の選び方は、大きな版ごとに一つとし、その中で最小版選択で選ぶ。選んだ結果を根の記述に書き出す。
- 取得元は、git のリモートリポジトリ（HTTPS・SSH）、手元のパス（公開するパッケージでは使えない）、公式の短い名前に限る。アーカイブの URL は後で考える。
- git からは、作業ツリーに展開せずにオブジェクトから読み、hooks や filter を起動しない。サブモジュール、根の外を指すシンボリックリンク、大文字と小文字だけが違うパスは誤りとする。

残っていること:

- 依存を書く場所（論点 3。実行を始めるファイルか、プロジェクトの設定ファイルか）と、記述の構文。
- 0.x の版の扱い。一つのリポジトリに複数のパッケージを置く形（`sub/v1.2.0`）を設けるか。
- 中身のハッシュの計算の規則（パスの正規化、改行の扱い、実行の属性を含めるか）。
- 根の記述の版と、依存の依存が求める版が食い違ったときの規則（根が古い版を書いていたら誤りにするか）。
- HTTPS の非公開のリポジトリの認証。
- 【要検証】git のライブラリの、木の読み取り・浅い取得・タグの一覧への対応。GitHub のアーカイブのバイト列が変わった事例。

## macOS の Gatekeeper と Rust の実行ファイル（OPEN-060 の確認の途中経過）

設計者の問い（2026-10-03）: ADR 0233 の「Gatekeeper が Developer ID の証明書を確かめる」は、Swift 以外（Rust）でビルドした CUI の実行ファイルにも当てはまるか。

- Gatekeeper の確認は、実行ファイルを作った言語によらない。Mach-O の実行ファイルに隔離の属性（`com.apple.quarantine`）が付いていると、初めて実行するときに確かめる。属性は、Safari などのブラウザ、メール、AirDrop がダウンロードしたファイルに付ける。公証の要件にも、アプリケーションと並んでコマンドラインのツールが挙がる（二次資料による。Apple の一次資料の本文は取得できなかった【要検証】）。
- `curl` でダウンロードしたファイルには隔離の属性が付かず、Gatekeeper の確認は起きない（二次資料）。
- arm64 の macOS では、実行ファイルに少なくとも ad-hoc の署名が要る。Rust のビルドでもリンカが自動で付ける。手元の `target/debug/benitoite` で確かめた（2026-10-03）: `codesign -dv` は `flags=0x20002(adhoc,linker-signed)`、`Signature=adhoc`、`TeamIdentifier=not set`。`spctl --assess --type execute` は `rejected`（隔離の属性が付けば、Gatekeeper に止められる評価）。
- macOS Sequoia（15）からは、Control を押しながら開いて確認を越える方法がなくなり、システム設定の「プライバシーとセキュリティ」で「このまま開く」を選ぶ必要がある（二次資料）。
- ブラウザで取得した `tar.gz` を展開したとき、中の実行ファイルに隔離の属性が引き継がれるかは、展開に使う道具による見込み【要検証】。

Homebrew と導入のスクリプトについて（2026-10-03 に手元の macOS で確かめた）:

- Homebrew の formula で入れた実行ファイルには、隔離の属性が付かない。`/opt/homebrew/Cellar/ada-url/4.0.0/bin/adaparse` などの属性は `com.apple.provenance` だけで、署名は ad-hoc だった。Gatekeeper の確認は起きない。
- Homebrew の cask で入れたアプリケーションには、隔離の属性が付く（手元の `/Applications/Android Studio.app` などに `com.apple.quarantine` があった）。Homebrew 5.0 は、署名と公証のない cask を非推奨にし、2026-09 までに公式の tap から外すとした。`--no-quarantine` の指定も廃止の方向である（二次資料）。
- `curl … | sh` の形の導入のスクリプトは、中で `curl` などを使って取得するので、隔離の属性が付かず、確認は起きない見込みである（取得に使う道具による）。
- Benitoite を Homebrew で配るとき（ADR 0233 の決定 3 で初回リリース版の後に検討する）は、ソースからビルドする formula にすれば、署名と公証がなくても Gatekeeper の問題は生じない。ビルド済みの実行ファイルを配る形は Homebrew の分類では cask に当たり、公証が要る方向にある（goreleaser も、ビルド済みのものを formula で配る `brews` を非推奨にした。二次資料）。

ADR 0233 の文書の手順は、「ブラウザで取得したら属性を外すか、システム設定で許可する」「`curl` で取得すれば確認は起きない」を書けば足りる見込みである。Agent Skills からエージェントに導入させる場合は、`curl` で取得するので確認は起きない。
