# コマンドを代替するライブラリとエフェクトの検討

- 作成: 2026-10-02
- 状態: 検討メモ（初回リリース版の実装を終えた後に、設計書の ADR と OPEN に移す）
- 調べた範囲: 設計書 03-06・03-07・03-08・03-09・01-07・06-06・06-07・07-01、実装プランの 10-15・10-16（いずれも 2026-10-02 の時点）

## 目的と範囲

コーディングエージェントがシェルで実行するコマンド（cp・mv・rm・mkdir・grep・sed・git など。sh・python・perl・ruby などのスクリプトの処理系は除く）を、Benitoite のライブラリでどこまで代替できるかを整理する。そのうえで、足りない機能の実装の難易度と、外部コマンドを包むライブラリ（git など）のエフェクトと権限の設計を検討する。

初回リリース版の完成後、ただし初回リリースの前に、初回リリース版を改造して取り込むことを想定する。

## ライブラリを作る方針

設計者の方針（2026-10-03）として、コマンドを代替するライブラリは次のように作る。

1. **既設の関数で足りるものは、新しく作らない。** 初回リリース版の `File`・`Path`・`String`・`List`・`Regex` などを組み合わせて書ける操作（後述の表の ○ の行）には、コマンドに当たる関数を加えない。
2. **コマンドの操作をそのまま再現しない。** コマンドの名前・オプション・出力の形式（`grep -rn` の出力の行、`sed` の式、`find` の述語など）をなぞる関数は作らない。加えるのは、組み合わせても書けない機能か、書けても安全や性能の面で処理系が持つべき機能に限る。
3. **言語の作りに合った形で作る。** 結果は文字列の出力ではなく、レコードやリストなどの型の付いた値で返す。外部の資源はリソースとして `with` で開き、後始末を言語に任せる。権限の対象（パス、コマンドなど）が型と権限の確認に現れる形にする。失敗は `Result` と `IOError` で返す。

外部のコマンドを包むラッパー（git など）も、コマンドの引数を組み立てる薄い層ではなく、同じ方針で、操作を型の付いた関数とエフェクトとして表す（後述の「git の提供のしかた」「エフェクトの設計」）。

後述の表と候補の一覧は、どの機能が足りないかを示すためにコマンドの名前で整理したものであり、コマンドに当たる関数を作る一覧ではない。

## 代替のライブラリが要る理由

`Process.run` を使えば、どのコマンドも実行できる。しかし、そうするとエフェクトは `Process.Run` の一つになり、`rm -rf` も `ls` も同じ型に見える。起動したコマンドが中で行う操作は、処理系の検査の外にある（03-07「外部コマンドの起動とシェル」、07-01「ハーネスとの分担」）。

`File.removeTree` のようにライブラリの関数で書けば、エフェクトは `File.Write`、権限の対象はパスになる。利用者は、実行の前に何を許すかを読み取れ（原則 3）、サーバモードの実行時の権限制御も対象を照合できる。コマンドをライブラリで代替することは、静的検査と権限の表示の両方の精度を上げる。

## 初回リリース版での対応

初回リリース版のファイル操作は `File`（03-07）と `Path`（03-08）、テキスト処理は `String`・`List`（03-06）と `Regex`（03-08）で書ける。ただし、コマンドを丸ごと置き換える関数はなく、部品を組み合わせて書く。実装プランの関数の一覧（10-15・10-16）は設計書と一致している。

| コマンド | 初回リリース版での対応 | 評価 |
|---|---|---|
| `mkdir -p` | `File.createDirectory`（途中のディレクトリも作る） | ○ |
| `rmdir`・`rm`・`rm -r` | `File.remove`（ファイルと空のディレクトリ）、`File.removeTree` | ○ |
| `mv` | `File.rename` | △ ファイルシステムをまたぐ移動の扱いを定めていない |
| `cp` | `File.copy`（普通のファイルだけ） | △ `-r` がない。1 GiB まで。`readBytes` と `writeBytes` で写すので、実行の権限などの属性を引き継がない |
| `ls`・`find` | `File.listDirectory`・`File.walk`・`File.info` | △ glob と名前による絞り込みがない。`File.walk` は `.git` も辿る |
| `stat` | `File.info`（種類・大きさ・更新時刻） | △ 権限の属性と所有者を返さない |
| `realpath`・`basename`・`dirname` | `File.canonicalize`、`Path` の関数 | ○ |
| `cat`・`head`・`tail` | `File.readText`・`File.readLines`・`File.openReader`、`List.take`・`List.drop` | ○ |
| `grep` | `File.readLines` と `Regex.isMatch`・`Regex.find` | △ 再帰の検索、行番号、バイナリの判定、.gitignore への対応を利用者が書く |
| `sed`・`sed -i` | `Regex.replaceAll`・`Regex.replaceAllWith` と `File.writeText` | △ 行の範囲の指定がない。書き換えが原子的でない |
| `sort`・`uniq`・`cut`・`tr`・`wc` | `List.sort`、`Set`、`String.split`・`String.replace`・`String.lines` | ○ 組み合わせて書く |
| `awk` | 一般のコードで書く | △ |
| `jq` | `Json.parse`・`Json.get`・`Json.at` | △ 問い合わせの言語はない |
| `curl`・`wget` | `Http.get`・`Http.send`（https に対応） | ○ |
| `base64`・`sha256sum` | `Encoding`、`Hash.sha256` | ○ md5・sha1 はない |
| `date`・`sleep` | `Clock`、`Time` | ○ |
| `env`・`pwd` | `Process.environmentVariable`・`Process.workingDirectory` | ○ |
| `cd` | 実行全体の作業ディレクトリは変えられない。`Process.Command` の `workingDirectory` でコマンドごとに指定する | △ |
| `touch` | `File.appendText(p, "")` で作れる | × 更新時刻を変えられない |
| `chmod` | なし | × |
| `ln -s`・`readlink` | なし（`File.info` でシンボリックリンクかは分かる） | × |
| `mktemp` | なし | × |
| `which` | なし（`Process.run` が `IOErrorKind.NotFound` を返すだけ） | × |
| `diff`・`patch` | なし | × |
| `tar`・`gzip`・`unzip` | なし（gzip は ADR 0137 で除外した） | × |
| `git`・`cargo`・`npm`・`make` | `Process.run` で起動する | 後述の「git の提供のしかた」 |

`Process.run` 自体にも、エージェントの用途で足りない点が二つある。一つは、起動したコマンドが終わるまで待つ形しかなく、開発用のサーバのように裏で動かし続けて後で止める使い方ができないことである。`Task.withTimeout` で取り消したときに子プロセスを止めるかは、設計書の中に記述を見つけられなかった【要検証】。もう一つは、出力を `String` で返すので、出力が UTF-8 でないコマンドの結果を受け取れないことである。

## 加える機能の候補と実装の難易度

関数を一つ加えるごとに、型付きの組み込みの宣言、IO 実行器の作業用のスレッド、権限の表の行、ゴールデンテスト、クレートのライセンスの確認（ADR 0138）が付いてくる。費用を左右するのは、関数の数よりもエフェクトと権限の設計である。

| 難易度 | 対象 | 実装の手段の候補 | 難しい点 |
|---|---|---|---|
| 低 | `cp -r`・`ln -s`・`readlink`・`chmod`・`touch`・`mktemp`・`which`・md5・sha1 | Rust の標準ライブラリ（`fs::set_permissions`、`os::unix::fs::symlink` など）、`tempfile`・`which`・`sha1`・`md5` のクレート | chmod とシンボリックリンクの意味が Unix と Windows で違う。touch の時刻の設定を標準ライブラリだけで行えるかは【要検証】 |
| 低 | `mv` のファイルシステムをまたぐ移動 | 写してから消す | rename が失敗したときに写して消す処理と、途中で失敗したときの状態の定義 |
| 中 | grep -rn（rg 相当）、glob | `ignore`・`globset`・`grep-searcher`（ripgrep の部品） | 結果の値の大きさの上限（ADR 0049）、バイナリのファイルの判定、.gitignore の扱い、結果を返すレコードの形 |
| 中 | 原子的な書き換え、sed -i 相当 | 一時ファイルに書いてから rename する | 一時ファイルの置き場所（同じファイルシステムに置く必要がある）、権限の属性の引き継ぎ |
| 中 | diff | `similar` | 出力の形式（unified 形式など）。patch の適用は別に難しい |
| 中 | 裏で動かすプロセス（起動・待つ・止める） | `std::process` と IO 実行器 | タスクの取り消し、リソースの状態の遷移（ADR 0266）、`with` での後始末との関係。ランタイムに手を入れる |
| 中 | tar・gzip・zip | `tar`・`flate2`・`zip` | 展開のときに `../` やシンボリックリンクを使って外へ書く抜け道への対策 |
| 高 | git の自作、jq の問い合わせ言語、awk | — | git は機能が多く、設定・hooks・認証の仕組みまで含めて互換を保つ負担が大きい |

候補は、前述の「ライブラリを作る方針」に照らして、作る前に見直す。例えば、grep 相当の検索は、行の文字列を返す関数ではなく、ファイル・行番号・一致した範囲を持つレコードのリストを返す関数にする。jq 風の問い合わせや awk に当たるものは、`Json` の関数と一般のコードで書けるので、問い合わせの言語は作らない方向で見直す。

優先度の暫定の案は次のとおりである。

- 高: grep 相当の検索、glob、原子的な書き換えと置換の補助、`File.copyTree` と属性の引き継ぎ、権限の属性の取得と設定、一時ファイルと一時ディレクトリ（`with` で消えるリソースにする）
- 中: diff、which、touch、シンボリックリンクの作成と読み取り、裏で動かすプロセス、出力をバイト列で受け取る `Process.run`
- 低: tar・gzip・zip、md5・sha1、jq 風の問い合わせ

対象と優先度は、勘ではなく、実際のエージェントの記録（Claude Code のセッションのログなど）からシェルで実行したコマンドの頻度を数えて決めるのがよい。

## 1 GiB を超えるファイルの扱い

前述の「ライブラリを作る方針」のもとで、1 GiB を超えるファイル（インストールのパッケージ、バックアップなど）の操作は少なくないので、対策を検討する。

### 上限がかかる箇所

上限の元は、一つの操作で作る `String`・`Bytes` の値を 2^30 バイト（1 GiB）までとする規則である（ADR 0049、02-09「一つの操作で作る値の大きさの上限」）。ファイルの名前の変更（`File.rename`）・削除・情報の取得は内容を読まないので、上限に関係しない。上限がかかるのは、内容全体を一つの値に読む関数である。

| 操作 | 現在の関数 | 大きなファイルでの問題 |
|---|---|---|
| コピー | `File.copy` | `File.readBytes` と `File.writeBytes` で書いた標準ライブラリのソースの関数なので、1 GiB まで（ADR 0291） |
| ダウンロード | `Http.get`・`Http.send` | 応答の本体を `Bytes` で返すので、1 GiB まで。インストールのパッケージのダウンロードで問題になる |
| チェックサムの確認 | `Hash.sha256(data)` | `Bytes` を受け取る純粋な関数なので、ファイル全体を読む必要があり、1 GiB まで |
| 外部コマンドの出力 | `Process.run` | 標準出力を集めて返すので、1 GiB まで（`Process.runAttached` は集めないので問題ない） |

`File.openReader`・`File.readChunk`・`File.openWriter`・`File.writeChunk` を使えば、利用者のスクリプトは今でも少しずつ読み書きでき、上限なく写せる。足りないのは、それを一つの関数で書ける形である。

ADR 0291 は、`File.copy` を組み込みの関数にする案を、二つの組み込みのエフェクト（`File.Read` と `File.Write`）にまたがる組み込みの関数を置く仕組みが `File.copy` のためだけに要るとして退けた。同時に、帰結に「1 GiB を超えるファイルを写す必要が生じたら、後の版で組み込みの関数に改めてよい」と書いている。

### 案

- **(A) `File.copy` を、少しずつ読み書きする標準ライブラリのソースの関数に書き直す。** `File.openReader` と `File.openWriter` で開き、`File.readChunk`（例えば 1 MiB ずつ）と `File.writeChunk` を繰り返す。上限がなくなり、新しい仕組みは要らない。
  - 型が変わる。`with` でリソースを開くと、解放の関数のエフェクト `State` が要る（01-07、ADR 0150）ので、型は `uses File.Read, File.Write, State` になる。`uses IO.All` のスクリプトは `IO.All` が `State` を含むので影響を受けないが、`uses File.Read, File.Write` と細かく書いたスクリプトは誤りになる。
  - OS の速いコピー（Linux の `copy_file_range`、macOS の APFS のクローンなど）を使えない【要検証: Rust の `std::fs::copy` と `std::io::copy` がどの OS の機能を使うか】。読みと書きのたびに作業用のスレッドとの受け渡しと `Bytes` の確保が起きる。速さは測って確かめる。
  - 途中で失敗すると、書きかけのファイルが残る。同じディレクトリの一時的な名前に書いてから `File.rename` で置き換えると、失敗しても元の `to` が壊れない。
- **(B) 開いたリソースどうしを流す操作を加える。** 例: `File.transfer(reader, writer)`（`File.Write` の操作。`reader` の残りをすべて `writer` に書く）。読む権限は `File.openReader` で、書く権限は `File.openWriter` で確かめ済みなので、一つの操作が二つのエフェクトにまたがらない。作業用のスレッドの中で一度に流すので、受け渡しの回数が減り、OS の速いコピーも使える見込みがある。`File.copy` は、開く・流す・閉じるを呼ぶソースの関数になり、型は (A) と同じく `State` を含む。
  - 同じ形で、ダウンロードを `Writer` に流す操作（`Http.sendTo(request, writer)` など。`Http.Connect` の操作）や、外部コマンドの出力を `Writer` に流す設定も作れる。
- **(C) 二つのエフェクトにまたがる組み込みの関数を置く仕組みを作る。** 型を `uses File.Read, File.Write` のまま保てる。しかし、この関数はどのエフェクトの操作でもないので、`File.Read` を処理するハンドラ（テストの差し替えなど）が、コピーの読みを捕らえられない。処理系が行う操作だけが実行時の権限制御の対象になる規則（01-07）との関係も決め直す必要がある。

### チェックサムの確認

`Hash.sha256` に、少しずつ計算する純粋な関数を加える。例: `Hash.sha256Start() -> Hash.Sha256State`、`Hash.sha256Update(state, data) -> Hash.Sha256State`、`Hash.sha256Finish(state) -> Bytes`。状態は中身を見せない値（ADR 0168 の前例）とし、純粋な関数のまま、`File.readChunk` と組み合わせて大きなファイルのハッシュを計算できる。ファイルを一度で計算する `Hash.sha256File(reader)` のような関数は、これを使ったソースの関数で書ける。

### 設計者の決定（2026-10-03）

(B) を採る。初回リリース版の実装を終えた後、実際の初回リリースの前の改造で直す。初回リリース版の実装には (A) も入れない。

### 見立て（この節）

- (B) を採る。(A) と同じく `File.copy` の型に `State` が加わるが、一つの操作が一つのエフェクトに属する規則を保ったまま、速いコピーとダウンロードの流し込みにも同じ形を使える。言語の作り（リソースを `with` で開き、権限は開くときに確かめる）に合う。
- (C) は採らない。ハンドラで差し替えられない IO を作ると、エフェクトの規則の例外になる。
- 少しずつ計算するハッシュの関数を加える。
- `File.copy` の型に `State` が加わる変更は、初回リリースの前に行うので、リリースした版の利用者には互換性を壊す変更にならない。

## git の提供のしかた

git は機能が多く、自作は現実的でない。選択肢は三つある。

| 案 | 内容 | 長所 | 短所 |
|---|---|---|---|
| 自作 | Rust で git を実装する | 外部のコマンドが要らない | 作業量が大きすぎる |
| Rust の git のライブラリ（gitoxide など） | 処理系に組み込む | 起動の費用がない。hooks が動かない | push・rebase などへの対応の状況は【要検証】。バイナリが大きくなる。利用者の git の設定（認証、署名など）と挙動がずれる |
| git の CLI を包む | `git status --porcelain=v2 -z` のような機械向けの出力を指定して呼び、結果をレコードにする | 利用者の環境と挙動が一致する。実装が軽い | git が要る。git の版による出力の違いへの対応が要る |

CLI を包む案を第一の候補とする。この案では、git が hooks・credential helper・diff driver・ssh などの別のプログラムを起動しうることを、保証の範囲に含めて考える必要がある。リポジトリの `.git/config`（`core.fsmonitor` など）や、`git -c alias.x='!コマンド'` のような大域のオプションからも、別のプログラムを起動できる。そのため、git の読み取りの操作であっても、「読むだけ」とは言えない。保証の範囲は「git を、このサブコマンドで起動すること」までとし、セキュリティモデルの「ハーネスとの分担」と同じ形で明記する。読み取りの操作で hooks や fsmonitor を無効にして起動するか（`-c core.hooksPath=…` などで抑えられる範囲）は【要検証】である。

## エフェクトの設計

### 現在の設計の制約

現在の設計には、外部コマンドを包むライブラリのエフェクトについて、三つの制約がある。

1. 利用者が定義するエフェクトは、`main` の型に現れない（01-07「プログラムの入口」）。必ずハンドラで処理するので、ライブラリで `Git.Commit` を宣言して中で `Process.run` を呼んでも、`main` の型と実行前の権限の表示に残るのは `Process.Run` だけである。
2. エフェクトをまとめる仕組みは、組み込みの `IO.All` だけである（01-07「組み込みのエフェクト」）。利用者がエフェクトのまとめや階層を宣言する構文はない。
3. `Process.Run` の許可は、コマンドの名前を単位とし、引数を問わない（ADR 0073・0184）。`git` を許すと、`git log` も `git push --force` も許す。

### 選択肢

- **A. ライブラリのエフェクト**（言語を変えない）: `Git` のモジュールで `Git.Read`・`Git.Write` などを宣言し、既定のハンドラが `Process.run` で git を呼ぶ。型付きの結果と、ハンドラによるテストでの差し替えは得られる。権限の表示は `Process.Run(git)` に戻るので、原則 3 の改善にはならない。
- **B. git を組み込みのエフェクトにする**: 標準ライブラリのモジュール（仮に `Benitoite.Tool.Git`）で `Git.Read`・`Git.Write` などを宣言し、まとめた `Git.All` を `IO.All` と同じ仕組みで置く。許可の単位に git のエフェクトを加え、対象をリポジトリのパスやリモートの URL にする。組み込みのまとめは既にあるので、言語の変更は小さい。道具ごとに組み込みのエフェクトを足すと表が膨らむので、対象は少数に限る。
- **C. `Process.Run` の許可の対象を、引数の先頭まで細かくする**: `"Process.Run" = ["git status", "git log"]` のように書けるようにする。`Process.command` の引数が定数なら、処理系が実行の前に起動するコマンドの一覧を作って表示する（`Process.shell` を名前で参照しているかを調べるのと同じ考え方）。どの道具にも使えるが、関数の型の上では `log` と `push` を区別できない。git では前述の大域のオプションと設定から別のプログラムを起動できるので、先頭の語の照合だけでは抜け道が残る。
- **D. 利用者がエフェクトのまとめや階層を宣言できるようにする**: `effect Git = Git.Read | Git.Write` のような構文を加え、型の包含の規則（ADR 0046）を拡張する。利用者のエフェクトが `main` に現れない制約が残る限り、権限の表示は改善しない。A を整理する手段にとどまる。

### git のエフェクトの分け方の叩き台

| エフェクト | 操作の例 | 対象 |
|---|---|---|
| `Git.Read` | status・log・diff・show・blame・ブランチの一覧 | リポジトリ |
| `Git.Write` | add・commit・ブランチの作成・switch・stash・tag | リポジトリ |
| `Git.Rewrite` | reset --hard・rebase・commit --amend・clean・branch -D | リポジトリ |
| `Git.Remote` | fetch・pull・push・clone | リモートの URL |

残る論点は次のとおりである。

- `Git.Rewrite` を分けると、取り消しにくい操作を利用者が見分けやすくなる（原則 3）。分け方を誤ると、エージェントが書くコードへの診断が増える。
- `push --force` は `Git.Remote` と `Git.Rewrite` の両方に当たる。
- `Git.Remote` を、ネットワークのエフェクトと同じく `IO.All` の外に置くか。
- `Git.Write` で作業ツリーのファイルが変わることを、`File.Write` の許可とどう関係づけるか。

## Process.run の位置付けと既定の方針

### 三段の順

外部コマンドを使う操作は、次の順で選ぶ。

1. 標準ライブラリの関数
2. コマンドを包む外部のライブラリ
3. `Process.run`（1 にも 2 にもないときの最後の手段）

この順は、現在の設計書のどこにも書かれていない。書く場所と手段の候補は次の三つである。

- Agent Skill（06-06）の言語の規則の要約に、「標準ライブラリにある操作を `Process.run` で行わない」を加える。
- `Process.command` のコマンドの名前が定数で、標準ライブラリに同じ操作があるとき（`cp`・`mv`・`rm`・`mkdir` など）、置き換え先の関数（`File.copy` など）を示して警告する。原則 1・3 に沿い、実装も軽い。
- 03-07 の「外部コマンドの起動とシェル」に順の考え方を書き、ADR に記録する。

### 既定の方針

スタンドアロンモードでは `Process.Run` を既定で許し、利用者が個人用の道具を手軽に作れるようにする。サーバモードでは既定で許さず、エージェントが勝手にコマンドを起動しないようにする。この方針は、既に ADR 0185 の既定の方針と一致している（06-07「方針のファイル」）。

```toml
[defaults.standalone.allow]
"Process.Run" = true
shell = true

[defaults.exec.allow]              # server exec。Process.Run と shell を書かないので許さない
"Process.Environment" = []
```

登録したスクリプトは、登録のときに利用者が承認したエフェクトで動き、エージェント用のプロファイルでは `"Process.Run" = ["git"]` のようにコマンドを限って許せる。初回リリース版は実行時の権限制御を持たないので、スタンドアロンモードでは現在も実質的にすべてを許している。

サーバモードを加えた後のスタンドアロンモードは、OS のサンドボックスを掛けた子プロセスで動き（ADR 0204）、既定の書き込みの範囲は作業ディレクトリと一時ディレクトリの下だけである。`Process.Run` を許していても、起動したコマンドもこの範囲に制限される。作業ディレクトリの外へ書く個人用の道具（パッケージの導入など）は、既定の方針のままでは失敗する。個人用の道具を手軽に作れるという目的に照らして、この既定で困らないかを確かめる必要がある。

### サーバモードでのラッパーのライブラリの扱い

三段の順を前提にすると、サーバモードでは問題が一つ生じる。ラッパーのライブラリの中身は `Process.run` であり、そのエフェクトは `main` に現れない（前述の制約 1）。そのため、`Process.Run` を許さない既定の方針では、ラッパーのライブラリを使っても、生の `Process.run` と同じく拒否される。権限の上では、2 段目を 3 段目と区別して扱う仕組みがない。

| 案 | 内容 | 費用 | 注意点 |
|---|---|---|---|
| X. よく使う道具を標準ライブラリに上げる | 前述の B。`server exec` の既定で `Git.Read` だけを許す、といった設定ができる | 中（道具ごと） | 対象を少数に絞る |
| Y. ライブラリを単位に許可する | ラッパーのライブラリが、起動するコマンドを宣言する。承認したライブラリの中からの `Process.run` だけを許す | 大 | パッケージ管理（06-05、未着手）、実行時にどのライブラリから呼んだかの判定、ライブラリそのものの信頼（署名）を前提とする |
| Z. `Process.Run` の対象を引数の先頭まで細かくする | 前述の C。ラッパーは書きやすさのための層になる | 小〜中 | 照合を厳密にしないと抜け道が残る。git では大域のオプションの禁止や、設定・hooks を無効にした起動が要る |

暫定の推奨は、エージェントが日常的に使う少数の道具（まず git）を X で標準ライブラリに上げ、それ以外は Z を一般の仕組みとし、Y はパッケージ管理の設計とあわせて後で検討する組み合わせである。
