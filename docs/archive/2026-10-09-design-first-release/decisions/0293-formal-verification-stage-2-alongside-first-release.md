# 0293. 形式検証の段階 2 を初回リリース版の実装と並行して始め、コア計算の進行と保存・エフェクトの健全性を証明する

- 状態: 採択
- 日付: 2026-09-30
- 関連章: [形式意味論と検証](../07-quality/07-04-formal-semantics.md), [コア計算と脱糖](../01-spec/01-12-core-calculus.md), [ロードマップ](../00-overview/00-03-roadmap.md)
- 関連する未決事項: [OPEN-068](../open-issues.md#open-068), [OPEN-069](../open-issues.md#open-069)

## 背景

[ロードマップ](../00-overview/00-03-roadmap.md)の「形式検証の時期」は、段階 2（証明支援系で、選んだ性質を証明する）を初回リリース版の後に行うとし、対象とツールを[形式意味論と検証](../07-quality/07-04-formal-semantics.md)で選ぶとしていた（[ADR 0213](0213-formal-verification-stage-1-in-first-release.md)）。

[コア計算と脱糖](../01-spec/01-12-core-calculus.md)には、初回リリース版の規則（ストア、`escape`、`with` の解放、ハンドラと一度だけ再開できる継続、プロセスの終了）と、継続とストアの型付けまでが書かれている。同章の「確かめる性質」は、進行と保存（性質 2）とエフェクトの健全性（性質 3）を挙げ、どれも証明していないと記す。性質 2 を支える説明の一部（`drop` の枠が `release` の枠についての前提を要らないことなど）は、日本語の論証だけで書かれている。

設計書のレビューは、これまで日本語の文書を読んで矛盾を探す形で行ってきた。この形では、指摘が正しいかを確かめる手段が、指摘を読んで考えることしかない。実行時の振る舞いについての指摘は、実装のときに再現テストで確かめることにした（[OPEN-062](../open-issues.md#open-062)）が、コア計算の規則そのものの誤りは、差分テスト（段階 1）でも、規則どおりに作った参照インタプリタと VM がともに誤る場合には見つからない。

初回リリース版の実装では、値の表現とランタイムを作り直し、ハンドラと継続を区画の切り離しで実装する（[ADR 0240](0240-runtime-redesign-in-first-release-plan.md)、[ADR 0160](0160-one-shot-continuations-as-stack-segments.md)）。01-12 のハンドラの規則に誤りがあれば、この実装の作り直しに響く。

## 決定

1. 形式検証の段階 2 を、初回リリース版の後まで待たず、初回リリース版の実装と並行して始める。
2. 証明する性質は、[コア計算と脱糖](../01-spec/01-12-core-calculus.md)の「確かめる性質」の性質 2（進行と保存）と性質 3（エフェクトの健全性）とする。
3. 二つの段に分けて進める。段階 A は、01-12 の最小実行版の範囲（「構文」「型付け規則」「実行の規則」）で二つの性質を証明する。段階 B は、01-12 の「初回リリース版の拡張」のうちコア計算に構成を加えるものを加え、同章が示す初回リリース版の読み替えの形で二つの性質を証明する。
4. 次のものは対象にしない。性質 1（脱糖の型の保存）、型推論のアルゴリズム（[型システム](../01-spec/01-06-type-system.md)）、並行処理のタスクと引き継いだハンドラ（01-12 も状態の型付けに含めない）、「置き換えてよい等式」、処理系の実装（VM・バイトコード・ランタイム）の正しさ。
5. 段階 2 の完了は、初回リリース版の完了条件に含めない。
6. 証明の途中で 01-12 の規則の誤りが分かったときは、段階 1 の反例と同じく、ADR を添えて規則を直す（[ADR 0213](0213-formal-verification-stage-1-in-first-release.md) の決定 4）。直した規則が初回リリース版の実装プランの作業に響くときは、オーケストレータが実装プランを改める。

## 検討した代替案

- **ロードマップどおり、初回リリース版の後に始める**: 初回リリース版の実装の負担が増えない。しかし、ハンドラと継続の規則の誤りが見つかる時期が、それを実装した後になる。段階 2 の作業は処理系のソースに触れないので、実装の作業と並べて進めても互いの作業を止めない。
- **型推論まで対象にする**: 設計者が学びたい型システムの中心は推論にある。しかし、推論の健全性を示すには、宣言的な型付け（01-12 のコア計算の型付けとは別の、表層の型付け）と推論のアルゴリズムの両方を形式化する必要があり、型クラスの解決も含めると規模が段階 A・B を大きく超える。性質 2・3 を先に証明しておけば、推論の結果を脱糖した先の性質は証明済みになる。
- **性質 1（脱糖の型の保存）を含める**: 表層の構文と型付けを形式化する必要があり、上と同じ理由で規模が大きい。脱糖の誤りは、段階 1 の差分テストと、脱糖した結果の型の検査（処理系のテスト）で見つけられる見込みがある。
- **処理系の実装の正しさを証明する**: 処理系は Rust で書き、証明支援系の外にある。VM とランタイムの正しさの証明は、コンパイラの検証の規模の仕事になり、言語全体の機械的証明を目標としない方針（[形式意味論と検証](../07-quality/07-04-formal-semantics.md)の「非目標」）に反する。

## 帰結

- ADR 0213 の「段階 2 は、これまでどおり初回リリース版の後に行う」を改める。ADR 0213 の状態を「採択（段階 2 の時期を 0293 で改めた）」とする。
- [ロードマップ](../00-overview/00-03-roadmap.md)の「形式検証の時期」の段階 2 の時期を改める。
- [形式意味論と検証](../07-quality/07-04-formal-semantics.md)に、対象、進め方、道具、01-12 との対応を書き、状態を「草稿」にする。
- [コア計算と脱糖](../01-spec/01-12-core-calculus.md)の「確かめる性質」に、性質 2・3 を段階 2 で証明することを加える。
- 証明できるまでの間、性質 2・3 は証明していない性質のままであり、宣言する保証（[ロードマップ](../00-overview/00-03-roadmap.md)の「各マイルストーンで宣言する保証」）は変わらない。
