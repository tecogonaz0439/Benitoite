# 0151. タスクが引き継いだハンドラで処理する操作は、末尾で再開する節に限る

- 状態: 採択
- 日付: 2026-09-29
- 関連章: [並行処理](../01-spec/01-11-concurrency.md), [エフェクト](../01-spec/01-07-effects.md), [評価意味論](../01-spec/01-08-evaluation.md), [型システム](../01-spec/01-06-type-system.md)
- 関連する未決事項: なし

## 背景

`handle` の本体の中で起動したタスクは、そのハンドラを引き継ぐ。タスクの中で呼んだ操作は、タスクを起動した位置で有効だったハンドラが処理し、節はその操作を呼んだタスクの中で実行する（[ADR 0118](0118-effect-handlers.md) 決定 7）。テストで、並行処理を含むコード（要求ごとにタスクを起動する HTTP サーバなど）の組み込みの操作を差し替えるためである。

一方、節の中の `resume(v)` は、本体の続きを実行し終えたときの `handle` の式の値を返し、その型は `handle` の式の型である（[型システム](../01-spec/01-06-type-system.md)）。子のタスクの中で節を実行するとき、`resume(v)` が再開するのは子のタスクの続きであり、それを実行し終えて得られるのは子のタスクの結果である。子のタスクの結果は、`handle` の式の値でも、その型の値でもない。したがって、次の例の `resume(())` の値は定まらない。

```text
let answer = handle
  let _ = Task.all([lambda() ping() end lambda])
  1
when ping():
  let n: Integer = resume(())
  n + 1
end handle
```

節が `resume` を呼ばずに終わる場合と、節の中の `return` と `try` が `handle` を含む関数を終える場合も、節を実行する子のタスクと、`handle` を評価する親のタスクが異なるので、意味が定まらない。複数の子のタスクが同時にこうした節を実行すると、どの節の値を `handle` の式の値にするかがタスクの切り替えに依存し、純粋な関数の結果が実行ごとに変わりうる。この問題は、外部の検証者による 01-spec のレビューで指摘された。

## 決定

1. タスクは、これまでどおり、起動した位置で有効だったハンドラを引き継ぐ。
2. 節の本体のどの終わり方も末尾位置の `resume(v)` であり、節の中に `return` と `try` がないとき、その節を末尾で再開する節と呼ぶ。末尾で再開するかどうかは、節ごとに構文から決まる。
3. タスクの中で呼んだ操作を、そのタスクが引き継いだハンドラ（そのタスクの外で評価を始めた `handle`）が処理するときは、その操作の節が末尾で再開する節でなければならない。末尾で再開する節は、操作を呼んだタスクの中で実行し、`resume(v)` に達したら、操作の呼び出しの結果を `v` とする。節の値は使わない。
4. 3 の場合に、操作の節が末尾で再開する節でなければ、節を実行せずに実行時エラー（引き継いだハンドラの節の誤り）とする。
5. `handle` を評価したタスク自身が呼んだ操作は、節の形によらず、これまでどおり処理する。節が `resume` を呼ばずに終わったときは、本体の中で起動した、終わっていないタスクを取り消す。

## 検討した代替案

- **`handle` の本体の中でタスクを起動したら実行時エラーにする**: 規則は単純になる。しかし、並行処理を含むコードのテストで、組み込みの操作を差し替えられなくなる。ハンドラを加えた主な理由がテストでの差し替えである（[ADR 0118](0118-effect-handlers.md)）。
- **子の節の値を親の `handle` の値に合流させる一般の意味を定める**: 節の形を制限しない。しかし、子の続きを実行し終えた後で親の `handle` の値を待つと、親が子の終わりを待っているので、待ち合わせが循環する。循環を避ける規則と、複数の子が同時に節を終えたときにどれを採るかの規則が要り、後者は結果を実行ごとに変えうる。
- **タスクはハンドラを引き継がない**: 子のタスクの操作は、処理系が実際に行うか、処理されないまま残る。前者では、組み込みのエフェクトを処理したハンドラが型から除いたエフェクトの操作を処理系が行い、エフェクトの保証が破れる。後者では、型の付いたプログラムが操作を処理できずに止まる。
- **末尾で再開しない節を型検査で拒む**: 節がタスクの中から呼ばれるかどうかは、本体が呼ぶ関数の中でタスクを起動するかによるので、`handle` の式だけを見ても決まらない。すべての節を末尾で再開する形に限ると、状態を持つハンドラや中断するハンドラを書けなくなる。

## 帰結

- テストの差し替えの典型である、値を決めてすぐに再開する節（`when File.readText(path): resume(Result.Ok("..."))`）は、並行処理を含むコードでも使える。
- 中断するハンドラ（`resume` を呼ばない節）と、再開の結果を使う節は、そのハンドラを評価したタスクの中の操作にだけ使える。
- 末尾で再開する節は、節の本体のエフェクトを除けば、操作ごとに値を決めるので、純粋なハンドラを引き継いだタスクの結果は、タスクの切り替えに依存しない。
