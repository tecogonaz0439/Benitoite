# 0115. 初回リリース版で、構造化された IO の並行処理をライブラリと `with` で提供する

## 背景

並行処理は、実装するかどうかも決めていなかった（[OPEN-006](../open-issues.md#open-006)、[ロードマップ](../00-overview/00-03-roadmap.md)の「将来拡張」）。初回リリース版で、スクリプトから簡易な HTTP サーバ（HTML を返す、REST API を提供する）を動かせるようにする。そのためには、接続を待ち受けている間や、一つの要求を処理している間に、ほかの要求の処理が止まらない必要がある。最終的には、複数のコアで並列に計算することも目指す。

処理系の側には、次の前提がある。

- 一つの実行を同時に進めるスレッドは一つだけであり、排他制御は入れていない（[ADR 0015](0015-shared-program-per-execution-state.md)）。
- 言語の値は、スレッドの間で受け渡せない参照カウント（Rust の `Rc`）で管理している（[ADR 0078](0078-reference-counting-in-minimal.md)）。Rust の文書は、`Rc` がスレッドの間で送れないことと、複数のスレッドで使うには `Arc`（アトミックな参照カウント）を使うことを述べている。
- 言語の関数の呼び出しを Rust のスタックに載せず（[ADR 0016](0016-calls-off-go-stack.md)）、IO の命令で VM を止めて再開する方式を持つ（[ADR 0029](0029-two-io-execution-modes.md)、[ADR 0088](0088-keep-both-io-execution-modes.md)）。VM の状態を保ったまま、別の計算に切り替えられる。
- Benitoite は直接形式であり、IO を行う関数は `uses IO` で型に現れる（[ADR 0005](0005-direct-style-effects.md)）。

他の言語は次のとおりである。いずれも各言語の文書で確かめた。

- Go は `go` 文と `select` 文を構文として持つ。`go` 文で起動した関数の戻り値は捨てられ、起動した側は終わりを待たない。
- Kotlin の `coroutineScope`、Swift の TaskGroup、Python 3.11 の `asyncio.TaskGroup`、Trio の nursery、OCaml の Eio の `Switch`、Java の `StructuredTaskScope` は、子のタスクがスコープより長く生きない構造化された並行処理（structured concurrency）を提供する。いずれもライブラリの関数か型であり、構文で提供するのは Swift の `async let` だけである。Java の `StructuredTaskScope` は、JDK 21〜27 でプレビューであり、JEP 543 が正式化を提案している。
- 構造化された並行処理では、子のタスクの一つが失敗すると、ほかの子を取り消して失敗を親に伝える（Kotlin、Python、Trio、Eio、Java）。
- OCaml 5 の Eio は、効果ハンドラによって、並行のコードを並行でないコードと同じ書き方で書けるとしている。Swift・Python・Rust は `async` と `await` を構文に持つ。
- Erlang は、プロセスごとに独立したヒープを持つ。OCaml 5 の Domain は OS のスレッドに 1 対 1 で対応する。

## 決定

1. 初回リリース版で、タスク（task）による並行処理を提供する。タスクは、ほかのタスクと並行に進む計算である。
2. 初回リリース版の処理系は、同時に一つのタスクだけを進める。IO の完了を待つタスクがあれば、ほかのタスクを進める。IO を行わずに計算を続けるタスクがあっても、処理系は一定の量を実行するごとにタスクを切り替え、ほかのタスクを止め続けない。切り替える位置はプログラムから指定できず、プログラムはそれに依存してはならない。
3. 並行処理は構造化する。タスクを起動する操作は、`Task.all`・`Task.allOk`・`Task.race`・`Task.withTimeout` と、リソースの型 `TaskGroup` だけとする。これらの呼び出しが終わるとき、または `TaskGroup` を束縛した `with` を抜けるとき、そこで起動したタスクはすべて終わっている。起動した側が終わりを待たないタスク（Go の `go` 文にあたるもの）は設けない。
4. 並行処理は、ライブラリの関数と `with` で表し、専用の構文を設けない。`async` と `await` は設けない。タスクを起動する関数と待つ関数は IO エフェクトを持ち、普通の関数と同じ書き方で呼ぶ。
5. タスクの間のやりとりは、タスクの結果の値で行う（fork-join）。可変のセルは、タスクの間で共有してよい。セルの一つの操作は、ほかのタスクの操作と混ざらない。読んで書き換える操作は `Reference.update` で行う。チャネルは初回リリース版に含めない。
6. どれかのタスクで実行時エラーが起きたら、プログラム全体を止める（[ADR 0064](0064-no-exceptions-runtime-errors-uncatchable.md) と同じ）。`Task.allOk` は、`Result.Error` を返したタスクがあれば、ほかのタスクを取り消して、その `Result.Error` を返す。
7. 並行処理のために予約語を加えない。タスクを待つ関数と起動する関数は、他の言語で広く使われる名前（`Task.await`・`TaskGroup.spawn`）にする。`async`・`await`・`spawn`・`select` を予約語にして、他の言語の書き方を書いたときに診断で Benitoite の書き方を示すかは、[OPEN-012](../open-issues.md#open-012) の測定の題材とする。
8. 複数のコアで並列に計算することは、初回リリース版の後に目指す。並列にしても、本 ADR が定める意味は変えない。方式は [OPEN-044](../open-issues.md#open-044) で決める。
9. HTTP サーバを書くためのネットワークの操作と、その権限は、[OPEN-045](../open-issues.md#open-045) で決める。

## 検討した代替案

- **IO の地点だけでタスクを切り替える（協調的な切り替え）**: 実装が簡単で、切り替わる位置がソースから読み取れる。しかし、一つの要求の処理が長い計算を続けると、HTTP サーバのほかの要求がすべて止まる。また、将来に並列に実行すると、どの位置でもほかのタスクの操作が混ざるので、協調的な切り替えを前提に書いたプログラムの結果が変わる。
- **初回リリース版から複数のコアで並列に実行する**: 言語の値を `Arc` に替えるか、タスクごとにヒープを分けて値を写す必要がある。前者は参照の数の増減のたびにアトミックな操作の費用がかかり、後者は値の表現と回収の方式（[OPEN-036](../open-issues.md#open-036)、[OPEN-039](../open-issues.md#open-039)）と一体で設計する必要がある。HTTP サーバを動かすのに必要なのは IO の並行であり、並列はその後に回す。
- **`async` と `await` を構文に加える**: IO を行う関数は、すでに `uses IO` で型に現れる。`async` を加えると、同じ区別を二通りに書くことになる（設計原則 5）。
- **`parallel … end parallel` のような専用のブロックを設ける**: スコープを字句で示せる。しかし、スコープを抜けるときに後始末をする仕組みは、リソーススコープの `with` がすでに持つ。同じ役割の構文を増やさない（設計原則 5）。
- **構造化しない（Go の `go` 文にあたる起動を設ける）**: 書き方は短い。しかし、起動したタスクの失敗や終わりを、起動した側が見落とす。プログラムを止めるときに、どのタスクが残っているかも分からなくなる。
- **アクターやチャネルを基本にする**: 要求ごとに処理を分ける HTTP サーバは、fork-join とタスクの集まりで書ける。チャネルは、必要になったときに std に加えられる。
- **STM を設ける**: 同時に一つのタスクだけを進める間は、セルの操作が混ざらないことを処理系が保証できる。並列にするときに、改めて検討する（[OPEN-044](../open-issues.md#open-044)）。
- **並行処理の語を予約語にし、診断で書き方を示す**: LLM が他の言語の書き方で書いたときに、対応する書き方を示せる。しかし、使わない語を予約するために、ライブラリの関数に `await`・`spawn` のような自然な名前を付けられなくなる。予約語を増やさない方針（[ADR 0093](0093-no-reserved-words-for-absent-constructs.md)）とも合わない。

## 帰結

- HTTP サーバは、接続を受け付けるたびに `TaskGroup.spawn` で要求の処理を起動する形で書ける。サーバを止めるまで、`TaskGroup` の `with` を抜けない。
- 一つの要求の処理で実行時エラーが起きると、サーバ全体が止まる。要求の処理の失敗は、`Result` で返す必要がある。
- VM は、タスクごとに呼び出しの情報を持ち、一定の量を実行するごとに切り替える仕組みを持つ必要がある。切り替えの量と仕組みは、初回リリース版の実装プランで定める。
- 取り消したタスクが始めていた IO は、取り消しの時点で終わっているとは限らない。取り消しは、外部の操作が起きなかったことを保証しない。
