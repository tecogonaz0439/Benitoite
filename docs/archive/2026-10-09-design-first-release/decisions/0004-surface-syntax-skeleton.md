# 0004. 表層構文の骨格として、ドット記法をモジュール修飾に限り、シグネチャを必須にし、改行で文を区切り、括弧で関数を適用する

## 背景

最小実行版の構文解析器を作る前に、表層構文の骨格を決める必要がある（[ロードマップ](../00-overview/00-03-roadmap.md)の「着手の前に必要な決定」）。[目的と設計原則](../00-overview/00-01-goals.md)は、表層構文を「LLM による生成・修正の成功率」と「人間による読みやすさ」で選び、波括弧を使う C 系の見た目の関数型言語の構文を暫定の候補としている。

骨格のうち、後から変えると構文解析器・型検査器・言語リファレンスのすべてに影響する点が四つある。

1. ドット記法の扱い（OPEN-001）。`x.method()` の `method` を `x` の型から解決すると、名前解決が型推論に依存する。制約を順に解く HM 推論とは相性が悪く、サブタイピングを入れると HM の主要型が失われる（[設計メモ](../sources/fp-language-design.md) 2.3）。
2. トップレベルの関数の型シグネチャを必須にするか。
3. 文を何で区切るか。
4. 関数の適用の形と、部分適用の書き方。

どの選択も、LLM の成功率が上がるという見込みに基づく。見込みそのものは【要検証】である（OPEN-012）。

## 決定

1. サブタイピングは入れない。ドット記法は、モジュールの修飾（`List.map`）に限る。値に続くドット（`xs.map(f)`）は構文として認めない。関数をつなげて書くときはパイプ `|>` を使い、`x |> f(a)` を `f(x, a)` の糖衣とする。初回リリース版のレコードのフィールド参照にドットを使うかは、[OPEN-023](../open-issues.md#open-023) で決める。
2. トップレベルの関数は、引数の型、戻り値の型、エフェクトを持つ型シグネチャを必ず書く。関数の本体の中の局所束縛とラムダの型は推論する。
3. 文は改行で区切り、`;` は使わない。行が続くかどうかは、字句構造で定める単純な規則で判定する。判定に迷う形は、別の意味に解釈せず構文エラーにする。
4. 関数は `f(x, y)` の形で適用する。関数は多引数とし、カリー化しない。部分適用は、プレースホルダ `_` を使った `f(_, y)` か、ラムダで明示する。

この四点を満たす範囲の具体的な文法（キーワード、演算子の優先順位、改行の規則など）は、字句構造と構文の章で【方針】として定める。OPEN-012 の測定の結果、この骨格を変えるときは、新しい ADR で本 ADR を置き換える。

## 検討した代替案

### ドット記法

- **`x.f(a)` を `f(x, a)` の糖衣とし、`f` を字面のスコープで探す（UFCS）**: メソッド呼び出しに近い見た目になる。しかし、`xs.map(f)` の `map` がスコープに直接なければ解決できない（`List.map` と、将来の別のコレクションの `map` が並ぶ）。LLM は型に基づいて解決されることを期待して書くので、意図との食い違いが診断として現れる。また、`x |> f(a)` と役割が重なり、原則 5（同じ役割の構文を増やさない）に反する。
- **型主導で解決し、解決できない箇所に型注釈を要求する（Rust 系）**: LLM に最もなじみのある見た目である。しかし、推論が局所的になり、「型注釈が必要」という、誤りの原因ではなく処理系の都合を述べる診断が増える（原則 4）。同じ `x.len()` の意味が `x` の型によって変わるので、構文の判断基準の「暗黙に文脈で意味が変わる箇所が少ない」にも反する。学習の面でも、教科書どおりの HM を変形せずに実装する機会を失う。

採った案の弱点は、LLM が `xs.map(f)` と書く誤りが起きうることである。この誤りには、`xs |> List.map(f)` と書くよう修正案を示す診断で対処する。弱点がどの程度問題になるかは、OPEN-012 の測定課題に含めて確かめる。

### 型シグネチャ

- **省略を許し、HM で全体を推論する**: 記述量は少ない。しかし、LLM が関数の本体を直すと、推論された契約（型とエフェクト）が黙って変わり、変わった契約のまま検査を通る。原則 2（契約の変更を見落とさせない）を守るには、推論結果の差分を別の仕組みで示す必要が生じる。また、HM の型エラーは、誤りを含む箇所ではなく、矛盾が見つかった呼び出し側で報告されやすい。シグネチャがあれば、誤りを「シグネチャに反する本体」として関数の中で報告できる。

記述量が増える点は、書き手が主に LLM なので、原則 4（記述量の少なさより、検査と診断の明確さを優先する）により許容する。

### 文の区切り

- **`;` を必須にする（Rust 系）**: 改行の規則が要らず、文法は単純になる。しかし Rust では、ブロックの末尾の式に `;` を付けるかどうかでブロックの値が変わる（付けると Unit になる）。これは「暗黙に文脈で意味が変わる」規則であり、LLM も人間も誤りやすい。利用者が文字列の書式だけを直すときに `;` を壊す余地も生じる（原則 3）。

採った案の弱点は、行の継続の規則が要ることである。JavaScript の自動セミコロン挿入のように規則が複雑だと、それ自体が誤りの原因になる。このため、規則を字句の段で判定できる単純なものに限る。

### 関数の適用

- **括弧を使い、カリー化する（`f(x)(y)`、`f(x, y)` をその糖衣とする）**: 部分適用を暗黙に書ける。しかし、引数が足りない呼び出しも正しい式になり、関数の値が返る。誤りは、離れた位置の型エラー（関数型と整数型の不一致など）として現れる。
- **並置で適用する（ML 系の `f x y`）**: カリー化が自然に書ける。しかし、C 系の見た目という暫定の候補から外れる。

採った案なら、引数の個数の誤りを、呼び出しの位置で「引数は 2 個必要だが 1 個しかない」という診断として報告できる。`|>` を「左の値を第 1 引数に入れる」糖衣にすれば、カリー化なしでもパイプで関数をつなげられる。Scala のプレースホルダ `_` は、どこまでをラムダに展開するかの規則が分かりにくい。このため、`_` を「一つの呼び出しの直接の引数」に限る。

## 帰結

- OPEN-001 は決着する。初回リリース版のレコードのフィールド参照（`r.name`）は、ドット記法と同じ型主導の解決の問題を持つので、[OPEN-023](../open-issues.md#open-023) として分けて扱う。
- 型推論は、トップレベルの関数のシグネチャを既知とし、関数の本体の中で HM 推論を行う形になる（[型システム](../01-spec/01-06-type-system.md)で定める）。
- OPEN-012 の測定課題に、ドット記法の不在（`|>` で書かせること）、シグネチャの記述、改行による区切り、部分適用の書き方を含める。
