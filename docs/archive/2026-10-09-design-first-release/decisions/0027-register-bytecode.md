# 0027. バイトコードをレジスタ型にする

- 状態: 採択
- 日付: 2026-09-26
- 関連章: [バイトコードとコード生成](../02-impl/02-07-bytecode.md), [仮想機械](../02-impl/02-08-vm.md)
- 関連する未決事項: [OPEN-009](../open-issues.md#open-009)

## 背景

実行方式は自作のバイトコード VM である（[パイプライン](../02-impl/02-01-pipeline.md)）。命令の形には、値をスタックに積み降ろしするスタック型（JVM、CPython）と、命令が操作対象のレジスタの番号を持つレジスタ型（Lua 5）とがある。

設計メモは、JIT なしの VM を第 2 層（非 JIT だが効率的な設計）に近づける手段として、値の表現のコンパクト化とレジスタ VM 化を挙げている（[設計メモ](../sources/fp-language-design.md) 9）。Go には computed goto がなく、命令の振り分けの費用が評価ループに乗る（同）。

処理系の中間表現は、計算を `let` で一歩ずつ区切るコア計算の形である（[ADR 0017](0017-ir-in-core-calculus-form.md)）。

## 決定

バイトコードはレジスタ型にする。各関数の呼び出しは、自分のレジスタの並びを持ち、命令はオペランドとしてレジスタの番号を持つ。中間表現の `let` で束縛した変数と関数の引数は、レジスタに割り当てる。

## 検討した代替案

- **スタック型**: コード生成が最も簡単である。しかし、同じ計算に要る命令の数が増え、命令ごとに Go の振り分けの費用がかかる。中間表現の変数をレジスタに割り当てる素直な対応も使えない。

## 帰結

- 中間表現の変数とレジスタが一対一に近く対応するので、コード生成は変数へのレジスタの割り当てが中心になる。
- 命令の数が減り、命令の振り分けの回数が減る。効果の大きさは性能測定で確かめる（[OPEN-009](../open-issues.md#open-009)）。
- 命令は複数のオペランドを持つので、一つの命令の大きさはスタック型より大きくなる。命令の符号化は[バイトコードとコード生成](../02-impl/02-07-bytecode.md)で定める。
