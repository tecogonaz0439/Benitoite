# 0282. E-DropRel の途中に届いた取り消しは辿り終えてから行い、外部の操作に移る前の要求は取り消しと全体の停止で失効させる

- 状態: 採択
- 日付: 2026-09-30
- 関連章: [仮想機械](../02-impl/02-08-vm.md), [ランタイム](../02-impl/02-09-runtime.md)
- 関連する未決事項: なし

## 背景

取り消しの要求は、対象のタスクに印を立てて予算を 0 にし、タスクは次に切り替えの位置の処理を行うときに取り消しの手順に移る（[ADR 0263](0263-dispatch-loop-locals-and-verifier.md)、[仮想機械](../02-impl/02-08-vm.md)の「取り消し」）。実装プランのレビュー（[相談の第 6 回](../../2026-10-09-implement-first-release/studies/u2-runtime/consult/06-plan-vm-review.md)の指摘 2、[相談の第 7 回](../../2026-10-09-implement-first-release/studies/u2-runtime/consult/07-plan-scheduler-review.md)の指摘 4）は、この規則だけでは定まらない場合を二つ挙げた。

一つ目は、節が `resume` を呼ばずに終わり、捨てる継続の区画を辿っているタスク（E-DropRel）に要求が届く場合である。辿りの途中には、ブロックする解放の完了を待つ位置があり、要求はその間に届きうる。規則をそのまま当てると、タスクは辿り終えた後に戻りの処理を続け、利用者のコードを評価してから、次の切り替えの位置で取り消しの手順に移る。これは、取り消したタスクを通常の実行に戻さないとした [ADR 0266](0266-task-and-resource-state-machines.md) の決定 5 と食い違う。一方、辿りの途中で原因を取り消しに改めることは要らない。取り消しと E-DropRel は、枠を降ろす処理の同じ列で処理するからである（[仮想機械](../02-impl/02-08-vm.md)の「枠を降ろす原因と処理」）。

二つ目は、外部の操作に移る前の要求である。組み込みのエフェクトの操作の要求は、送り出しの列に置かれてから、部品に渡され、ハンドラ表の関数が呼ばれ、外部の操作の記録に移る（[ADR 0264](0264-single-dispatch-queue-for-builtin-operations.md)）。要求と応答の方式では、要求を外側の実行器に返した後、応答を渡される前に VM が進み、別のタスクが要求を出したタスクを取り消すことがある。貸すリソースの返却や出力の転送の完了を待つ要求も、列の外で残る。外部の操作の記録から配送を外す規則（ADR 0266 の決定 3）は、まだ記録のない要求には及ばない。後から要求を処理すると、既に降ろした枠のレジスタを読むか、取り消したタスクの操作の副作用を起こしうる。全体の停止のときに残る要求にも同じことが起きる。仕様は、取り消しが操作の起きなかったことを保証しない（[並行処理](../01-spec/01-11-concurrency.md)の「取り消し」）。したがって、要求を処理しても失効させても仕様には反しないが、どちらにするかは既存の ADR からは導けない。

## 決定

1. E-DropRel で継続の区画を辿っているタスクに取り消しの要求が届いたら、要求を記録するだけにし、辿りの原因を変えず、解放の完了の待ちも外さない。辿り終えた時点で要求があれば、戻りの処理（`RETURN` と `ESCAPE` の続き）に進まず、残りの枠を取り消しを原因として降ろす。タスクは、辿り終えてから取り消しの手順に移るまでの間、通常の実行に戻らない。次の切り替えの位置まで待つことはしない。
2. 解放の枠の処理が解放の完了（または解放の前の返却）を待っているタスクには、要求で待ちを外さない。解放が終わってから取り消しの手順に移る。続けて戻る処理と後始末の途中の回収の位置からは、取り消しの手順に移らない。どちらも ADR 0266 の決定 5 と ADR 0263 の決定 3 から導かれる規則であり、決定 1 とあわせてここに記す。
3. 取り消しと全体の停止では、要求を出したタスクの、外部の操作に移る前の要求（送り出しの列にある要求、要求と応答の方式で応答を待つ要求、貸すリソースの返却か出力の転送の完了を待つ要求）を失効させる。失効させた要求では、組み込みの関数を呼ばない。
4. 要求を処理する側（直接呼び出しの方式の部品と、要求と応答の方式で外側の実行器が呼ぶ処理）は、要求が失効していないことと、要求を出したタスクが同じ世代のまま、その要求の応答を待っていることを確かめてから、組み込みの関数を呼ぶ。失効した要求の処理を求められたら何もしない。

## 検討した代替案

- **E-DropRel の途中でも、次の切り替えの位置で取り消しの手順に移る（元の規則をそのまま当てる）**: 規則を増やさずに済む。しかし、辿り終えた後の戻りの処理で利用者のコードを評価してしまい、ADR 0266 の決定 5 に反する。
- **要求が届いた時点で、辿りの原因を取り消しに改める**: 早く取り消しに移れる。しかし、取り消しと E-DropRel は同じ処理なので、原因を改めても降ろし方は変わらない。改める処理と、そのテストだけが増える。
- **外部の操作に移る前の要求も、外部の操作と同じく最後まで行い、結果を捨てる**: 要求の段階を問わず一つの規則で済む。しかし、取り消したタスクのために新しく副作用を起こすことになり、応答を待つ要求では既に降ろした枠のレジスタから引数を読む必要が生じる。まだ始めていない操作は始めないほうが、利用者が取り消しから予想する結果に近い。

## 帰結

- 取り消しの要求が届いてから利用者のコードを評価しないことは、E-DropRel の途中に届いた場合も含めて成り立つ。
- 始めた外部の操作は、これまでどおり取り消しの後も続く（ADR 0266 の決定 3）。失効させるのは、外部の操作に移る前の要求だけである。
- 要求の段階ごとに要求を持つ場所を一つに決め、取り消しと止める手順で失効させる。形は実装プランのスケジューラと IO 実行器の章で定める。二つの方式のそれぞれで、遅れて処理を求められた失効した要求のテストを置く。
- [仮想機械](../02-impl/02-08-vm.md)の「取り消し」と、[ランタイム](../02-impl/02-09-runtime.md)の「IO 実行器」「タスクの待ちと取り消し」「止める手順でランタイムが行うこと」を改める。
