# 0097. `Err` と `None` を呼び出し元へ返す構文を、前置の `try` とする

- 状態: 採択（決定 3 の波括弧の扱いを [0108](0108-keyword-blocks-closed-by-end.md) で改めた）
- 日付: 2026-09-27
- 関連章: [エラー処理](../01-spec/01-09-errors.md), [構文](../01-spec/01-02-syntax.md), [コア計算と脱糖](../01-spec/01-12-core-calculus.md)
- 関連する未決事項: [OPEN-029](../open-issues.md#open-029)（本 ADR で決着）, [OPEN-012](../open-issues.md#open-012)

## 背景

設計書は、`Result` の `Err` と `Option` の `None` を呼び出し元へそのまま返す構文として、後置の `?` を方針としていた（[OPEN-029](../open-issues.md#open-029)）。これは Rust の書き方である。前置の `try` は Swift と Zig が使う。Swift の `try` は右の式全体にかかる。これらの言語の書き方は、一次資料で確かめていない。

## 決定

1. `try 式` を、`Result.Error` と `Option.None` を呼び出し元へそのまま返す構文とする。意味は、これまでの `?` と同じである。`try` をキーワードにする。
2. `try` は、右の式全体（パイプを含む）にかかる。`try e |> f(_)` は `try f(e)` である。
3. `try` の直後に `{` を書くことは誤りとする。診断は、例外を捕らえる構文がないこと（[ADR 0064](0064-no-exceptions-runtime-errors-uncatchable.md)）と、`Result` か `Option` を返す式に `try` を付けることを示す。ブロックの値に `try` をかけるときは、`try ({ ... })` と書く。
4. 後置の `?` は設けない。LLM が `e?` と書いたときは、`try e` と書くよう診断で示す。

## 検討した代替案

- **後置の `?`（Rust）**: 記述量が少なく、パイプの末尾に付けられる。しかし、式の中の一文字の記号なので、読み手が見落としやすい。
- **`try` を単項演算子と同じ強さにする（`(try e) |> f(_)`）**: 規則は単項の `-` と同じになる。しかし、パイプの結果にかけるときに括弧が要り、括弧を忘れると別の意味で型検査を通ることがある。
- **構文を設けず、`Result.andThen` などでつなぐ**: 構文が増えない。しかし、失敗しうる呼び出しが続くと、ラムダが入れ子になる。

`try` は、多くの言語で例外を捕らえる構文（`try { ... } catch`）の語でもある。LLM がその書き方をする誤りは、決定 3 の診断で扱う。

## 帰結

- [OPEN-029](../open-issues.md#open-029) は決着する。
- [エラー処理](../01-spec/01-09-errors.md)と[構文](../01-spec/01-02-syntax.md)の `?` の規則を `try` の規則に改める。パイプの右辺の末尾の `?` を付け直す規則は要らなくなる。
- 脱糖は、これまでの `?` と同じく `escape` を使う（[コア計算と脱糖](../01-spec/01-12-core-calculus.md)）。
- `try` と `?` の LLM の書き誤りの率を、[OPEN-012](../open-issues.md#open-012) の測定の対象に含めるかは【未決】である。
