# 0313. 第 2 段の前に VM の性能を回復する区切りを置き、普通の呼び出しの規約と性能の関門を定める

- 状態: 採択（決定 6 の OPEN-064 は、R18 の後の VM で評価し、[0315](0315-keep-dispatch-range-checks.md) で範囲の確かめを省かないと決めた）
- 日付: 2026-10-05
- 関連章: [仮想機械](../02-impl/02-08-vm.md), [性能](../07-quality/07-02-performance.md)
- 関連 ADR: [0259](0259-compare-mark-sweep-and-rc-in-stage-1.md), [0262](0262-segment-frames-split-call-and-wrapping.md), [0263](0263-dispatch-loop-locals-and-verifier.md), [0268](0268-staged-runtime-rebuild.md), [0269](0269-correct-adr-0240-performance-assessment.md)
- 関連する未決事項: [OPEN-063](../open-issues.md#open-063), [OPEN-064](../open-issues.md#open-064), [OPEN-009](../open-issues.md#open-009)

## 背景

第 1 段の測定（[第 1 段の測定の要約](../../../../tools/bench/results/2026-10-05-stage1-5b300d4-summary.md)の「振り分けのループ（最小実行版との比較）」）で、初回リリース版の VM は最小実行版の VM より 5〜6.6 倍遅かった。fib(35) は 10.1 s 対 2.06 s、loop は 6.6 s 対 1.0 s である（同じ計算機で、最小実行版はコミット `d4668a9^` を測り直した値）。CPython 3 の fib は 1.27 s だった。[ADR 0269](0269-correct-adr-0240-performance-assessment.md) の決定 1 は、振り分けのループに局所の状態を持たせれば（[ADR 0263](0263-dispatch-loop-locals-and-verifier.md) の決定 1）、fib と loop は最小実行版より速くなると見ていた。今の VM は、その見立てに達していない。fib と loop は確保が 10 回ほどしかないので、この差はメモリの管理の方式からは来ていない。

遅さの大半は、R09 が書いた VM が ADR 0263 の決定 1 と、実装プラン 10-09「振り分けのループの局所の状態」を守っていないことから来ている。プロファイルと実装を読むと、命令ごとの費用には次のものがある。

1. レジスタを読み書きするたびに、実行中の区画と呼び出しの枠を表から 2〜3 回引き直す。局所に持つのは命令の位置と窓の先頭だけで、レジスタの窓そのものを局所に持たない。
2. `JMP`・`JMPF` でも、局所の状態を書き戻して読み直す。
3. 回収の要求の知らせを、確保をする命令の後だけでなく、すべての命令の後に調べる（10-09 は、確保をする命令と組み込みの関数の呼び出しの後と定める）。
4. `CALL`・`TAILCALL` のたびに、引数のレジスタの番号の `Vec` と、引数の値の `Vec` を確保する。算術と比較の命令も、被演算子を読むたびに `Vec` を確保する。引数は、集めた後に一つずつ呼ばれた側の窓に写す。プロファイルでは、`Vec` の作成が全体の 13〜25%、`malloc` が 9〜14% を占めた。
5. 命令ごとに、原型の表から実行中の原型を引き直す。
6. 命令の番号から命令の種類を得る関数がインライン化されず、`LOADK` は即値の定数でも、先に定数の値の表（順序付きの写像）を引く。
7. `RETURN` がレジスタの `Vec` を縮め、次の `CALL` が伸ばし直して中身を初期化し直す。
8. `runtime::heap` の公開の層の小さな関数（`Slot` と `NoGcCtx` の読み書き）が、クレートの境界をまたいでもインライン化されない形で呼ばれる。
9. 算術の命令を一つの関数で受け、命令の種類を条件の連鎖で判定し直す。

凍結したシグネチャを変えずに振り分けのループと `#[inline]` だけを変えた試作で、費用の大きさを確かめた（[相談の第 8 回](../../2026-10-09-implement-first-release/studies/u2-runtime/consult/08-vm-performance.md)の依頼文の「試作」）。1 と 4 を直すと 2.6〜2.85 倍、2・3 と呼び出しと戻りの後に局所の状態を直接設定することで、さらに 13%、8 で、さらに 11% 速くなった。合わせて fib は 3.65 倍、loop は 4.4 倍速くなったが、fib(35) に換算して 2.8 s であり、最小実行版の 2.06 s に届かない。残りの大きな費用は、生存の情報（10-07「生存の情報」、[ADR 0259](0259-compare-mark-sweep-and-rc-in-stage-1.md) の決定 2）に従って命令ごとに行う、最後の使用のレジスタの `take` と使わなくなったレジスタの `clear` の書き込みである。試作でこれを除くと 20〜26% 速くなった（除いた形は正しさを保たないので、費用の見積もりにだけ使った）。

ADR 0259 の決定 2 が命令ごとに消すことを定めたのは、参照カウントとマーク・スイープの間で生きている値の集合を揃えるためだった。参照カウントを外してマーク・スイープだけになった今（R14）、命令ごとに消す理由は回収の精度だけになった。GPT-6.1-Sol への相談（相談の第 8 回）では、消す処理を回収の安全点へ移す案は妥当だが、今の生存の情報は命令ごとに消すことを前提にした差分であり、安全点ごとの生きているレジスタの集合を別に作る必要があるという指摘を受けた。安全点の根は命令の位置だけでは決まらない（呼び出しの前後、組み込みの関数の完了を待つ間の引数、捕まえた継続、枠を降ろす途中）。同じ相談で、改善の順序（上の 1〜9 → 生存の情報の処理 → OPEN-063 → OPEN-064）と、第 2 段の前に普通の呼び出しと戻りに何を足さないかを規約として固定すること、作業を取り込むたびに fib と loop を測る関門を置くことを勧められた。

設計者は、この性能の差を初回リリース版の最重要の課題とし、第 1 段の締め（R14）の後、第 2 段（R20）の前に性能の回復の区切りを挟むことを承認した（2026-10-05）。本 ADR の決定（関門の基準、R15 に限る凍結の例外、確保を数えるテストの確保器、R32 の依存）も、同じ日に設計者が承認した。

## 決定

1. **性能の回復の区切り**: 第 1 段の締め（R14）と第 2 段の最初の作業（R20）の間に、性能の回復の作業を置く。
   - R15 は、背景の 1〜9 を直し、生存の情報のうち即値のレジスタへの書き込みだけを省く（後述の 2 の「即値の安い経路」）。生存の情報の扱い（ADR 0259 の決定 2）は変えない。
   - R16 は、生存の情報の処理を回収の安全点へ移す作業である。R15 の結果を見て、起動するかを決める（決定 4）。
   - R20 は R15 を待つ。R16 を起動した場合は R16 も待つ。R20 を待つ第 2 段の作業は、R20 を通じて R15 の後になる。
2. **振り分けのループの局所の状態の守り方**（ADR 0263 の決定 1 の具体化）: 振り分けのループは、次のことを守る。
   - 実行中の原型（命令の並び、定数、生存の情報）と、レジスタの窓（実行中の区画のレジスタのうち、窓の先頭から窓の大きさの分）を、局所の状態から得る。命令の処理の中で、区画・呼び出しの枠・原型を表から引き直さない。引き直すのは、呼び出し・戻り・回収・待ち・タスクの切り替え・継続の移動・止める手順の境目と、レジスタの `Vec` を伸ばした後だけとする。窓の先頭と大きさを局所に持てば、窓のスライスは命令ごとに実行中の区画（区画の並びの最後）から作ってよい（10-09「振り分けのループの局所の状態」）。
   - 跳ぶ命令（`JMP`・`JMPF` など）は、局所の命令の位置だけを変え、局所の状態を書き戻さない。
   - 回収の要求の知らせは、確保をする命令と組み込みの関数の呼び出しの後にだけ調べる（10-09 の定めのとおり）。
   - 呼び出しと戻りの後は、呼び出しの手順が決めた行き先（呼んだ原型と新しい窓、戻り先の枠）から局所の状態を直接設定してよい。これは `LoopLocals::load` で読み直すことと同じ状態を作る。
   - 即値の安い経路: 生存の情報が最後の使用か使わなくなったと示すレジスタに即値（ヒープの対象を指さない値）が入っているときは、`take` の代わりに読むだけにし、`clear` を省いてよい。即値はヒープの対象を保持しないので、回収の結果を変えない。宛先のレジスタに書く処理は省かない（宛先にはヒープの対象を指す古い値がありうる）。
3. **普通の呼び出しと戻りの規約**: 普通の呼び出しは、関数の値か辞書のメソッドを呼び、包む枠（`update`・セルの更新・`handle`・`drop`）を積まない呼び出し（`CALL`・`TAILCALL`・`METHOD`・`TAILMETHOD`）とする。普通の戻りは、戻る呼び出しの枠の上に解放の枠も包む枠もない `RETURN` とする（[ADR 0262](0262-segment-frames-split-call-and-wrapping.md) の決定 3 の「最も上の枠の深さと種類を見るだけで、処理する枠がないと分かる」場合）。VM は、普通の呼び出しと戻りで次のことを守る。
   - レジスタ・呼び出しの枠の `Vec` の容量が足りている間は、Rust の動的確保をしない。容量が足りないときに伸ばす確保は許す。
   - 引数は、呼び出し元の窓から呼ばれた側の窓へ直接写す。中間の集まり（`Vec` など）に集めない。末尾呼び出しでは写し元と写し先が重なりうるので、まだ読んでいない引数を、書き込みと窓の片付けで壊さない順に写す。
   - 普通の戻りでは、戻りの再開状態（10-09 の `ReturnWork`）を作らず、枠を降ろす状態機械を通らない。戻る値を戻り先のレジスタに直接書く。`ReturnWork` を作るのは、解放の枠か包む枠を処理する戻りと、`ESCAPE` だけとする。待ちうる経路の状態を保存する費用は、その経路で払う。
   - 戻りでレジスタの `Vec` を縮めずに記憶域を残す場合は、使用中の終端（最も上の呼び出しの枠の窓の終わり）と `Vec` の長さを分け、使用中の終端より後ろのレジスタをつねに `Unit` に保つ。呼び出しの新しい窓の先頭、上限の計数、片付ける範囲、区画のレジスタの数（`Segment::reg_count`）は、使用中の終端に従わせる。この形を採るかは、R15 が測って決める。
   - 第 2 段の作業（R20〜R29 など）が呼び出しと戻りに処理を加えるときも、普通の呼び出しと戻りの経路に、この規約に反する処理を足さない。
4. **生存の情報の処理**: 命令ごとの `take`・`clear` を回収の安全点へ移すかは、R15 の結果（目標に届いたか、残りの費用の内訳）を見て決め、移す場合は R16 で行う。移す場合は、ADR 0259 の決定 2（使わなくなったレジスタを命令ごとに根から除く）を、新しい ADR で改める。その ADR は少なくとも次のことを定める。安全点ごとの生きているレジスタの集合の作り方、呼び出しの前後と組み込みの関数の完了を待つ間の根、捕まえた継続と枠を降ろす途中の区画の根、回収の前に死んだレジスタを `Unit` にするか根から除くだけにするか。
5. **性能の関門**:
   - 第 2 段の開始の関門: R15（R16 を起動した場合は R16 も）を取り込んだ後の VM で、fib(35) と loop（`tools/bench/programs/` の入力）の実行の段の時間の中央値が、それぞれ最小実行版の VM（`d4668a9^`）以下であること。最小実行版の VM は、同じ計算機・同じ条件・同じ測定の機会に測り直す。測るのはオーケストレータであり、ほかの作業を止めて行う（スキル `benchmark`）。目指すのは ADR 0269 の見立て（最小実行版より速いこと）であり、関門はその最低限とする。
   - 取り込みごとの関門: 関門を通った時点の fib と loop の時間を基準として記録する。それ以後、VM・`runtime::heap`・コード生成・生存の情報を変える作業は、取り込みの前に fib と loop を測り直す。どちらかが基準より 5% を超えて遅くなったら、理由を記録し、設計者の合意を得てから取り込む。合意を得て取り込んだ場合は、その時点の値を新しい基準にする。
   - 構造の関門: 普通の呼び出しと戻りで Rust の動的確保が起きないことを、テストで確かめる（呼び出しの回数を変えても確保の回数が変わらないことを数える）。
   - 関門に届かなかったら、第 2 段を始めずに、測った値と残りの費用の内訳を設計者に示し、次の手（R16、OPEN-063、OPEN-064 の前倒しなど）を決める。
6. **OPEN-063・OPEN-064**: 窓を重ねる形（[OPEN-063](../open-issues.md#open-063)）と、検証器による範囲の確かめの省略（[OPEN-064](../open-issues.md#open-064)）は、R15（と R16）の後の VM で測り直して決める。R13 の比較（[OPEN-063 の記録](../../../../tools/bench/results/2026-10-05-open-063-4754e8a.md)）は、引数の `Vec` を作る VM での比較なので、決める根拠に使わない。R32（OPEN-064 の評価）は R15 を待つ。

## 検討した代替案

- **第 2 段を先に進め、性能は後でまとめて直す**: 第 2 段の作業が早く始まる。しかし、第 2 段はハンドラ・タスク・リソースの枠を呼び出しと戻りに加えるので、後で直すほど、どの変更の費用かを切り分けにくくなる。第 2 段の作業が今の遅い呼び出しの手順を前提に書かれると、直すときにその作業の部分も書き直すことになる。
- **R15 で、生存の情報の処理を安全点へ移すことまで行う**: 測った 20〜26% を一度で取りに行ける。しかし、安全点ごとの生きている集合を新しく作る必要があり、根の決め方には第 2 段の継続と待ちが関わる（背景の Sol の指摘）。正しさの条件が重く、R15 の機械的な改善と混ぜると、どちらの効果か、どちらが壊したかが分からない。ADR 0263 の「二つを同時に入れると、どちらの効果か分からない」と同じ理由である。
- **先に OPEN-064（範囲の確かめの省略）を採る**: 範囲の確かめは、背景の費用のうち小さな部分にすぎない。費用の大半は確かめそのものではなく、確かめのたびに表を引き直す組み立てにある。ADR 0263 の決定 2 のとおり、局所の状態を守った後に比べる。
- **関門を ADR 0269 の見立て（最小実行版より明らかに速いこと）か CPython の水準にする**: 目標としては望ましい。しかし、R15 と R16 でどこまで届くかの見込みは試作からの外挿にすぎず、届かないときに第 2 段が止まり続ける。最低限の関門を最小実行版の VM とし、見立ては目指す値として残す。
- **値を 8 バイトにする（OPEN-065）**: 値の写しと比較の費用を減らせる。しかし、今の費用の大半は値の大きさではなく、呼び出しの手順と表の引き直しにある。上の改善の後に、残りの費用を見て検討する。

## 帰結

- ADR 0269 の見立ては、実装が ADR 0263 の決定 1 を守っていなかったために確かめられていない。見立てそのものは誤りと決まっておらず、R15（と R16）の後の測定で改めて確かめる。ADR 0269 の状態に、見立てを確かめる測定を本 ADR の関門に移したことを記す。
- R09 の確認では、振り分けのループが局所の状態を守っているかを、性能の観点で読まなかった。実装の確認の観点（実装プラン 00-04）に、VM と `runtime::heap` を変える作業で、命令ごとの表の引き直しと、普通の呼び出しと戻りでの動的確保を読む観点を加える。
- 実装プラン 10-09「振り分けのループの局所の状態」「戻りの再開状態」に、決定 2・3 を反映する。特に、`RETURN` が処理を始めるときに戻る値をつねに `ReturnWork::value` へ移すという記述は、決定 3 の普通の戻りを除く形に改める。決定 3 の記憶域を残す形を R15 が採る場合は、`Segment::reg_count`（10-09 の `file=` のコード）の中身を使用中の終端に従う形に改める。
- 実装プラン README の作業一覧と「依存と順序」に R15・R16 を加え、R20 と R32 の依存に R15 を加える。
- [性能](../07-quality/07-02-performance.md)の「測定の結果の使い方」に、決定 5 の関門を加える。
- 第 2 段の開始の関門の経過（2026-10-06）: R15〜R18 を取り込んだ後の本測定（[R18 の記録](../../../../tools/bench/results/2026-10-06-r18-ab41855.md)）で、fib(35) は 1.965 s（最小実行版の VM の 0.955 倍）で関門を通り、loop は 1.060 s（同 1.069 倍）で届かなかった。命令ごとの手直しの効果が R17 の 5〜8% から R18 の 0〜3% に減ったことから、設計者は loop の 1.07 倍を認めて関門を通すことに合意し、R20 の起動と、範囲の確かめの省略の評価（R32）を R20 と並行して進めることを承認した。取り込みごとの関門の基準は、R18 の値（fib 1.965 s、loop 1.060 s。同じ記録）とする。
- R20 の後の経過（2026-10-06）: R20 を取り込む前の本測定（[R20 の記録](../../../../tools/bench/results/2026-10-06-r20-0d38ab7.md)）で、R20 は同じ機会の R18 に対して fib 0.964 倍、loop 0.903 倍になり、最小実行版の VM に対しても fib 0.922 倍、loop 0.964 倍で、第 2 段の開始の関門を合意によらずに満たした。最初の版は loop が 5% を超えて遅く、振り分けのループのレジスタの割り当ての変化を機械語で特定して直した。基準を R20 の値（fib 1.898 s、loop 0.960 s。同じ記録）に改める。
- 取り込みごとの関門の測り方の改め（2026-10-06）: 本測定のたびに設計者の確認と待ちが要り、時間がかかるので、設計者の判断で決定 5 の取り込みごとの関門の測り方を次のように改める。(1) 作業ごとには、実装担当が短い測定（作業を始めた版と交互に走らせ、最小値で比べる）と、release の振り分けのループの頭の機械語の命令の数とスタックへの退避の数を完了の報告に書く。短い測定で 5% を超えて遅いか、ループの頭が増えたら、取り込む前にオーケストレータが CPU プロファイルで原因を調べる。(2) 本測定は、R40 を取り込んだ後（R26 を二つに分けたので、本物の IO 実行器が入った後に測る。2026-10-06 に改めた）と、VM・ランタイムを変える作業（R21〜R29、R36、R39、R40）をすべて終えた後（R33 の前）の 2 回だけ、オーケストレータが行う。最後の回は、R20 以後の各取り込みのコミットをそれぞれビルドして同じ機会に測り、どの作業で時間が変わったかを特定する。(3) 本測定で基準より 5% を超えて遅くなっていたら、理由を記録し、設計者の合意を得て直すか認めるかを決める。遅れの発見が後になる分、後の作業が遅い形を前提に書かれる危険を、(1) の機械語の数で補う。
