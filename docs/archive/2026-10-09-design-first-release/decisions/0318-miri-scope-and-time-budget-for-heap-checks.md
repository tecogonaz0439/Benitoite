# 0318. Miri で走らせる VM のテストを選んだものに限り、ヒープの検査に時間の上限を設ける

- 状態: 採択
- 日付: 2026-10-06
- 関連章: [処理系のテスト戦略](../07-quality/07-03-compiler-testing.md)
- 関連 ADR: [0260](0260-heap-and-unsafe-boundary.md), [0266](0266-task-and-resource-state-machines.md)
- 関連する未決事項: なし

## 背景

[処理系のテスト戦略](../07-quality/07-03-compiler-testing.md)の「ヒープとランタイムの確かめ方（初回リリース版）」は、「ヒープのモジュールと小さな VM のプログラムに未定義動作がない」ことを Miri の単体テストで確かめると定め、時間のかかる検査を別のスクリプト（`scripts/check-heap.sh`）で行うとした。実装プランの作業 C00 が書いたスクリプトは、Miri の対象をモジュールの名前の頭 `runtime::heap::` と `vm::` で絞っていた。そのため、後の作業が `vm::` の下に加えたテスト（ハンドラ、タスク、リソース、`Lazy`、セルの振る舞いのテスト）も、すべて Miri で走るようになった。

2026-10-06 の作業 R26 で、`check-heap.sh` の Miri の段は、164 件のテストのうち 89 件を通すのに 2 時間半を要した（全体は 5 時間以上の見込み）。同じ日に同じマシンで、ほかの段の時間を測った結果は次のとおりである。

| 段 | 件数 | 時間 |
|---|---|---|
| Miri（`runtime::heap::` だけ） | 37 件 | 約 1 分 |
| Miri（対象ごとの確保、`runtime::heap::`） | 37 件 | 約 1 分 |
| 到達可能性の比較の長い実行（20000 列、各 320 操作。Miri ではない） | 1 件 | 約 2 分 |

時間を要したのは、`vm::` の下の約 125 件の Miri の実行だけだった。これらの VM のテストは `scripts/check.sh` でも走り、期待した振る舞いはそこで確かめている。処理系で `unsafe` を書いてよいのは `runtime::heap` の内部の層だけであり（[ADR 0260](0260-heap-and-unsafe-boundary.md)）、VM のテストを Miri で走らせる価値は、ヒープの `unsafe` のコードを VM の実際の使い方で通すことにある。その目的には、すべての VM のテストは要らない。テストの範囲を決めたときに、テストが増えたときの時間を見積もっていなかった。

## 決定

1. `check-heap.sh` の Miri の段は、`runtime::heap::` のテストと、Miri のために選んだ VM のテストだけを走らせる。選んだ VM のテストは、Miri 専用のモジュール `vm::miri_tests` に置く。`vm::` のほかのテストは Miri で走らせない（`check.sh` では、これまでどおり走らせる）。
2. `vm::miri_tests` には、ヒープの `unsafe` のコードを VM の実際の使い方で通す代表の形を、一つの形につき一件程度置く。対象とする形は、安全点での回収と生きているレジスタの整理（ADR 0314）、継続の捕捉・再開・破棄、タスクの待ちの間の回収、`Lazy` の結果とセルの書き込み（書き込みの障壁）、リソースの貸し借りと返却、IO の完了の待ちである。各テストは Miri で数秒から数十秒で終わる大きさにする。
3. `check-heap.sh` の全体は、10 分以内に終わるようにする。テストを加える作業は、その時間に収まることを確かめ、完了の報告に `check-heap.sh` の時間を書く。収まらなければ、テストの大きさを Miri のときだけ縮めるか、`vm::miri_tests` に置かない。
4. 到達可能性の比較の長い実行（20000 列）は変えない。
5. `check-heap.sh` は、`runtime::heap` を変える作業の完了条件とすることに加え、オーケストレータが `vm/` を変えた作業を取り込むときにも実行する。

## 検討した代替案

- **`vm::` のすべてのテストを Miri で走らせ続け、重いテストだけを Miri のときに縮める**: 各作業がこれまでしてきた方法である。テストが増えるたびに時間が伸び、作業ごとに縮める判断が要る。縮めても、件数が多いので 1 回の実行が数時間になる。
- **VM のテストを Miri で走らせない**: 最も速い。しかし、ヒープのテストだけでは、安全点での回収、継続、タスクの待ちといった VM の使い方の組み合わせを通せない。
- **到達可能性の比較の列を減らす**: 2 分で済むので、減らす理由が小さい。

## 帰結

- `scripts/check-heap.sh`、実装プランの 00-02「完了条件の共通の検査」、作業 R26・R40 の文書を合わせて改める。
- 作業 R26 が `vm::miri_tests` を作り、それまでの作業の形と R26 の形の代表のテストを置く。後の作業は、代表の形を加えるときだけ、このモジュールにテストを加える。
- これまでの作業が Miri のために縮めたテスト（`cfg!(miri)` で反復を 64 にしたものなど）は、Miri で走らなくなる。縮める処理は残っていても害がないので、消さなくてよい。
