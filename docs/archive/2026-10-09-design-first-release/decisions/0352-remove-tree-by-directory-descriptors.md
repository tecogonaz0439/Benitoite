# 0352. `File.removeTree` をディレクトリの記述子を基準に辿る形で作り、`rustix` を依存に加える

- 状態: 採択
- 日付: 2026-10-09
- 関連章: [IO のモジュール](../03-interop/03-07-io-modules.md)、[ライブラリの構成](../03-interop/03-01-library-structure.md)

## 背景

`File.removeTree` は、シンボリックリンクを辿らずに消すと文書で約束している（03-07 の File の表）。実装（実装プランの L11）は、深い入れ子でも Rust の再帰を使わないように、`std::fs::remove_dir_all` を使わず、パスで辿る明示の積み重ねで作った。

公開の前のセキュリティのレビューで、パスで辿るために、消している途中に別のプロセスが途中のディレクトリをシンボリックリンクに差し替えると、リンクの先を消すことを確かめた（20,000 個のファイルのうち 18,415 個が消えた）。Rust の標準ライブラリの `remove_dir_all` の脆弱性 CVE-2022-21658 と同じ種類の競合である。セキュリティモデルが保証の外とする「権限の判定から操作までの間の差し替え」（07-01「ハーネスとの分担」）とは別に、標準ライブラリの文書が約束する振る舞いが破れている。

この競合を塞ぐには、開いたディレクトリの記述子を基準に、`openat`（`O_NOFOLLOW`・`O_DIRECTORY`）、`fstatat`（`AT_SYMLINK_NOFOLLOW`）、`unlinkat` で辿る必要がある。Rust の標準ライブラリはこれらを公開していない。`libc` を直接呼ぶには `unsafe` が要るが、`unsafe` を書いてよいのは `runtime::heap` の内部の層だけである（実装プラン 00-02）。

## 決定

1. `File.removeTree` を、ディレクトリの記述子を基準に辿る形に作り直す。シンボリックリンクはリンクそのものを消し、途中の構成要素が差し替えられても、リンクの先を辿らない。深い入れ子でも Rust の再帰を使わず、明示の積み重ねで書く（00-02「再帰の深さ」）。開いたままにする記述子の数には上限を設ける。
2. システムの呼び出しの安全な包みとして、クレート `rustix`（https://github.com/bytecodealliance/rustix 、`Apache-2.0 WITH LLVM-exception OR Apache-2.0 OR MIT`）を直接の依存に加え、版を固定する。`rustix` は MIT を選べるので、`deny.toml` のライセンスの許可を変えない。
3. 同じ弱さがあれば、`File.walk` も同じ方法で直す。

## 検討した代替案

- **`std::fs::remove_dir_all` を使う**: 標準ライブラリの実装は 1.58.1 以降この競合に安全である。しかし、内部で再帰し、深さごとに記述子を開いたままにするので、深い入れ子でスタックや記述子の上限に当たりうる。L11 がこれを避けた理由は今も成り立つ。
- **文書に注意を書き、直しは公開の後に回す**: 公開の時点で、約束と振る舞いが食い違ったままになる。

## 帰結

- 直接の依存が一つ増える。`cargo deny check licenses` の対象になり、第三者のライセンスの一覧（ADR 0235・0334）にも載る。
- 実装は Codex が行い、競合を起こす再現のテストを加える。
