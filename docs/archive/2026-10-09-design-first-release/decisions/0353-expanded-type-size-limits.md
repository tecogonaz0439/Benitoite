# 0353. 別名の展開と推論で作る型に、深さとノード数の上限を設ける

- 状態: 採択
- 日付: 2026-10-09
- 関連章: [フロントエンド](../02-impl/02-03-frontend.md)

## 背景

構文解析器は、ファイルごとの AST の入れ子の深さを 1000 で止め（E0208）、後の段の再帰の深さはその定数倍に収まるとしていた（02-03「入れ子の深さ」）。公開の前のセキュリティのレビューで、型の別名を重ねると、型検査が別名を展開した型の深さが宣言をまたいで積み上がり、この上限を素通りすることを確かめた。約 240 KB のスクリプトで、`benitoite check` がスタックを溢れさせて異常終了した（終了状態 134）。また、型を木として複製するので、同じ型引数を複数の位置へ置く別名や束縛を倍々に重ねると、数百バイトのスクリプトで検査の時間とメモリが指数的に増えた。

## 決定

1. 別名の展開と推論で作る型の木に、深さ（根を 1 として）1000 段、ノード数 16,384 個の上限を設ける。深さは構文の上限に揃える。ノード数は、既存のテストと境界の正しいプログラムが通り、倍々の増え方を小さな木の段階で止められる値とする。
2. 上限は、型を複製する前と、推論の型の木を作る途中で数え、超えた時点で止めて E0208 を報告する。新しい診断のコードは設けない。
3. 規則は 02-03「入れ子の深さ」に【方針】として書く。

## 検討した代替案

- **型を辿る処理をすべて明示の積み重ねで書く**: スタックの溢れは防げるが、倍々の増え方による時間とメモリの爆発は防げない。単一化・最終化・表示・コード生成のすべてを書き換える量も大きい。
- **型を共有する表現（ハッシュコンスなど）に改める**: 大きさの爆発は抑えられるが、型検査の内部の表現を広く変える。初回リリースの前の直しとしては大きすぎる。

## 帰結

- 上限は型ごとに掛かるので、多数の宣言による総メモリの使用量は別に増えうる。時間とメモリの資源の上限は、ハーネスに委ねる方針（ADR 0237）のままである。
