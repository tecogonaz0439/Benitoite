# 0007. データ構成子を型名で修飾し、prelude の List の中身を隠し、選ばれない分岐を誤りにする

- 状態: 採択（決定 1 の一部を [0099](0099-qualified-option-result-constructors.md) と [0102](0102-pair-and-triple.md) で改めた）
- 日付: 2026-09-26
- 関連章: [構文](../01-spec/01-02-syntax.md), [名前・スコープ・モジュール](../01-spec/01-03-names-modules.md), [代数的データ型とパターンマッチ](../01-spec/01-05-data-types.md), [標準ライブラリ](../03-interop/03-06-stdlib.md)
- 関連する未決事項: [OPEN-012](../open-issues.md#open-012)

## 背景

最小実行版の代数的データ型とパターンマッチ（[ロードマップ](../00-overview/00-03-roadmap.md)）を定めるにあたり、次の三点を決める必要がある。

1. データ構成子を式とパターンの中でどう書くか。修飾なしの名前（`Circle`）にするなら、構成子の名前はプログラム全体で一意でなければならない。型名で修飾する（`Shape.Circle`）なら、ドットの左に型名が来るので、ドットをモジュールの修飾に限るとした [ADR 0004](0004-surface-syntax-skeleton.md) の決定 1 を広げることになる。
2. prelude のリスト（リストリテラル `[a, b]` の型）を、構成子を公開した代数的データ型（cons リスト）にするか、中身を隠した型にするか。
3. `match` の中に、前の分岐がすべて受けてしまうために決して選ばれない分岐があるとき、誤りにするか警告にするか。網羅していない `match` を実行前に誤りとして報告することは、ロードマップの完了条件ですでに定めている。

## 決定

1. データ構成子は、式でもパターンでも、型名で修飾して書く（`Shape.Circle(1.0)`、`Shape.Circle(r) => ...`）。ただし、prelude の `Option` と `Result` の構成子（`Some`・`None`・`Ok`・`Err`）は、修飾せずに書く。構成子の名前は、同じ型の中で一意であればよい。
2. これに伴い、[ADR 0004](0004-surface-syntax-skeleton.md) の決定 1 のうち「ドット記法は、モジュールの修飾に限る」を、「ドット記法は、モジュールの修飾と、型名による構成子の修飾に限る」に改める。値に続くドット（`xs.map(f)`）を認めないことと、サブタイピングを入れないことは変えない。
3. prelude の `List[T]` は、構成子を公開しない型とする。リストは、リストリテラルと、`List` モジュールの関数（`List.head` など）だけで作り、分解する。内部の表現は[標準ライブラリ](../03-interop/03-06-stdlib.md)で定める。リストをパターンで分解する構文は、最小実行版に含めない。
4. 決して選ばれない分岐を含む `match` は、網羅していない `match` と同じく、型検査の誤りとする。

## 検討した代替案

### 構成子の書き方

- **修飾せずに書き、構成子の名前をプログラム全体で一意にする（Haskell・OCaml・Elm と同じ）**: 記述は短く、ドットをモジュールの修飾に限ったままにできる。しかし、別の型で同じ構成子の名前（二つの型の `Error` など）を使えず、LLM が名前を付けるときに衝突を避ける必要が生じる。修飾した名前なら、読み手は構成子を見ただけでどの型の値かが分かり、名前の衝突も起きない。

修飾した名前の解決は、ドットの左の名前（型名かモジュール名）と右の名前の組だけで決まる。値の型から名前を探すことはないので、ADR 0004 が避けた型主導の名前解決にはならない。`Some`・`None`・`Ok`・`Err` を例外とするのは、使う頻度が高いうえに、Rust などで修飾なしに書く形が定着しているからである。

### List の表現

- **cons リストの代数的データ型として構成子を公開する（Haskell・OCaml と同じ）**: `match` で先頭と残りに分解でき、関数型の教科書どおりに書ける。しかし、内部の表現が利用者のコードから見えるので、後から永続ベクタなどに変えられなくなる。添字による参照や末尾への追加も O(n) に固定される。中身を隠しておけば、表現を標準ライブラリの設計で選べ、永続データ構造を実装して学ぶ機会も残る。

採った案の弱点は、最小実行版ではリストを `match` で分解できないことである。再帰でリストを処理するときは `List.head` などの関数を使うか、利用者が自分で定義した代数的データ型を使う。リストのパターンを加えるかは、初回リリース版以降で、リストの内部表現を決めた後に検討する。

### 選ばれない分岐

- **警告にする（Rust・OCaml と同じ）**: 書きかけのコードを試しに実行できる。しかし、決して選ばれない分岐は、分岐の順番の誤りなど、意図との食い違いを示すことが多い。警告は、LLM も利用者も見過ごしやすい（原則 1）。

どの判断も、LLM が誤りにくいという見込みは【要検証】であり、OPEN-012 の測定課題に、構成子の修飾と、リストを関数で扱う課題を含めて確かめる。

## 帰結

- 構文の `Name` と `Pattern` の規則で、ドットの左に型名を書けるようにする。ドットの左の大文字識別子は、モジュールか型を指す。
- 名前・スコープ・モジュールの章で、型名とモジュール名が同じ名前空間を共有するかを定める必要がある（最小実行版では、`List`・`String`・`Int` などが型の名前でもありモジュールの名前でもある）。
- 初回リリース版でモジュールを加えると、他のモジュールの型の構成子は `Module.Type.Ctor` の形になりうる。この書き方は、モジュールを設計するときに決める。
- 最小実行版の完了条件の「代数的データ型で定義したリスト」は、prelude の `List` ではなく、利用者が定義した代数的データ型を指す。
