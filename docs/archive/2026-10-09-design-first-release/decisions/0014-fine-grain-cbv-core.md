# 0014. 言語の意味を、値と計算を分けるコア計算への脱糖で定め、コア計算を正とする

- 状態: 採択
- 日付: 2026-09-26

- 関連する未決事項: なし

## 背景

設計メモは、言語全体ではなく小さなコア計算を定義し、表層構文をそこへの脱糖（desugaring）として定義するとしている（[設計メモ](../sources/fp-language-design.md) 25.2）。ロードマップは、コア計算の構文・型付け規則・簡約規則を数学記法で書く段階 0 を、最小実行版の実装プランより前に行うとしている（[ロードマップ](../00-overview/00-03-roadmap.md)）。

[ADR 0005](0005-direct-style-effects.md) は、表層では外部に作用する処理を直接形式で書くと決め、モナドを学ぶ場の一つとして、値と計算を区別するモナド的なコア言語を定め、表層をそこへ脱糖するとした。

コア計算を定めると、同じ規則を文章（[評価意味論](../01-spec/01-08-evaluation.md)）と形式の規則の二か所で述べることになる。食い違ったときにどちらに従うかを決めておく必要がある。

## 決定

1. コア計算は、fine-grain call-by-value の形をとる。項を値と計算に分け、計算は `return V` と `let x ⇐ M in N` でつなぐ。計算の型は、結果の型とエフェクトの集合の組（`A ! ε`）である。
2. 実行の規則は、計算と継続の組を状態とする抽象機械で定める。末尾呼び出しの保証は、継続を伸ばさない遷移として定める（[ADR 0013](0013-evaluation-order-and-tail-calls.md)）。
3. 最小実行版の表層の意味は、表層の式をコア計算へ脱糖し、抽象機械で実行した結果として定める。範囲は最小実行版のすべての構文とする。
4. コア計算と評価意味論の記述が食い違うときは、コア計算を正とし、評価意味論を直す。評価意味論は、コア計算の規則を文章で要約したものと、コア計算の外にある規則（`main` の呼び出し、実行時エラーの報告、資源の不足）を持つ。

## 検討した代替案

### コア計算の形

- **call-by-push-value**: 値型と計算型を分け、計算を値として持つには thunk で包む。正格評価と遅延評価の両方を表せ、初回リリース版の明示遅延や代数的エフェクトの理論とつながる。しかし、型と規則の種類が増える。最小実行版の言語は正格評価だけなので、その一般性を使う箇所がない。
- **モナドの型 `T` を明示する計算的メタ言語**（Moggi）: モナドが型 `T_ε A` として見える。しかし、表層の関数の型との対応で `T` を付け外しする規則が増え、脱糖と型付け規則が長くなる。fine-grain call-by-value の計算の判断 `M : A ! ε` は、計算的メタ言語の `T_ε A` 型の項に対応するので、モナドとの対応はこの形でも説明できる。

fine-grain call-by-value では、`return` がモナドの単位（pure）に、`let x ⇐ M in N` が bind に当たり、モナド則は `let` についての等式として現れる。末尾位置は「`let` の左側にない計算」として構文から定まるので、末尾呼び出しの保証を抽象機械の上で述べやすい。

### どちらを正とするか

- **評価意味論を正とし、コア計算をそれに一致すべきモデルとする**: 形式の規則に慣れていない読み手には分かりやすい。しかし、文章の曖昧さをコア計算で解消できない。曖昧な箇所でコア計算がどちらかの解釈を選んでも、正は文章なので、解釈が定まらない。

## 帰結

- 表層の構文を加えるときは、脱糖の規則を[コア計算と脱糖](../01-spec/01-12-core-calculus.md)に加える。脱糖で表せない構文（初回リリース版の可変状態、代数的エフェクトなど）を加えるときは、コア計算を拡張する。
- 処理系の中間表現は、コア計算と同じ形である必要はない（[中間表現と脱糖](../02-impl/02-06-ir-and-lowering.md)）。処理系の実行結果は、コア計算の抽象機械の実行結果と一致しなければならない。
- 型検査（[型システム](../01-spec/01-06-type-system.md)）を通ったプログラムを脱糖した結果に、コア計算の型付け規則で型が付くこと、型が付いた計算が実行の途中で行き詰まらないこと、エフェクトが空集合の計算が IO を起こさないことは、証明していない。形式検証の段階 1 で、反例を探して確かめる（[ロードマップ](../00-overview/00-03-roadmap.md)、[形式意味論と検証](../07-quality/07-04-formal-semantics.md)）。
- コア計算の規則の誤りは、実装の誤りとして現れる。処理系のテスト（[処理系のテスト戦略](../07-quality/07-03-compiler-testing.md)）の期待値を、コア計算の規則から導けるようにする。
