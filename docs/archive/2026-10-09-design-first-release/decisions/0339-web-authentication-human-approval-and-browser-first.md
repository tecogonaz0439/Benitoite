# 0339. 初回リリース版の後のウェブの認証は、人間による承認の操作を必ず挟み、ブラウザに任せる形を本命とする

- 状態: 採択
- 日付: 2026-10-08
- 関連章: [ネットワークのモジュール](../03-interop/03-09-network.md)
- 関連する未決事項: [OPEN-089](../open-issues.md#open-089), [OPEN-091](../open-issues.md#open-091), [OPEN-092](../open-issues.md#open-092), [OPEN-093](../open-issues.md#open-093)

## 背景

スクリプトが HTTP の要求を送ると、認証を求められることがある。初回リリース版の HTTP のクライアントは、要求のヘッダを書けるので Basic や Bearer のトークンは送れるが、認証のための仕組みは持たない（[ネットワークのモジュール](../03-interop/03-09-network.md)の「クライアント」）。

設計者は、2026-10-02 に、認証の方式ごとの実現性を検討した（[秘密の情報の扱いの検討メモ](../sources/post-first-release/post-first-release-secrets.md)の「3. ウェブの認証」）。メモが一次資料で確かめた範囲（出典はメモの末尾）では、パスキー（WebAuthn）について次のことが分かっている。

- WebAuthn でフィッシングを防いでいるのは、署名するデータにクライアント（普通はブラウザ）が要求の出どころ（オリジン）を正しく入れることである。認証器はオリジンを確かめず、クライアントを信用する。
- macOS に保存したパスキーは、サイトの側がアプリを名指しする associated domain か、Apple に申請するブラウザ向けの権限がなければ使えないので、Benitoite の CLI から任意のサイトの認証には使えない。
- Bitwarden の CLI はパスキーでのログインに対応していない。
- パスキーで署名を作れても、サイトから挑戦（challenge）を受け取り署名を送る手順はサイトごとに違い、HTTP の標準の手順はない。

一方、OAuth のデバイス認可（RFC 8628）や、認可コードと PKCE をループバックの宛先で受ける形（RFC 8252）では、利用者がブラウザで承認し、スクリプトはトークンだけを受け取る。パスキーはブラウザの中で OS の仕組みのまま使える。

設計者は、この検討から二つのことを判断した。認証のときには人間による承認の操作を必ず挟むこと（メモの「3. ウェブの認証」の冒頭の条件）と、ウェブの認証はブラウザに任せる形を本命とすること（メモの「4. 物理キーによる操作ごとの承認」の冒頭）である。本 ADR は、この二つを記録する。

## 決定

初回リリース版の後に、標準ライブラリや公式のライブラリでウェブの認証を支える機能を加えるときは、次の方針に従う。初回リリース版（`0.1.0`）の HTTP のクライアントは変えない。

1. 認証のときには、人間による承認の操作を必ず挟む。承認を挟む位置は、方式ごとに次のとおりとする。ブラウザに任せる形ではブラウザでの承認、物理キーと OS の認証器ではキーや OS が求める操作（キーへの接触、PIN、生体認証）、パスワードやトークンを渡す方式では、処理系が用意する秘密の入力の経路（[OPEN-089](../open-issues.md#open-089)）での入力や承認である。
2. ウェブの認証は、ブラウザに任せる形を本命とする。サイトが対応していれば、OAuth のデバイス認可、認可コードと PKCE をループバックの宛先で受ける形などで、利用者がブラウザで承認し、スクリプトはトークンだけを受け取る形を第一に支える。処理系が WebAuthn のクライアントになる形は、本命としない。

決定 1 は、初回リリース版にある機能（スクリプトが自分で組み立てた `Authorization` のヘッダを `Http.send` で送ること）を制限しない。パスワードやトークンを渡す方式で、承認を求めるたびに挟むか、サーバモードの登録のときの承認で済ませるかを方針で選べるようにするかは、[OPEN-089](../open-issues.md#open-089) で決める。

## 検討した代替案

- **処理系が WebAuthn のクライアントになり、パスキーで直接ログインする**: 物理キーや Windows のプラットフォームの API なら可能な見込みである。しかし、macOS に保存したパスキーには使えず、ログインの手順はサイトごとに違うので、汎用の HTTP のクライアントとして任意のサイトに自動でログインすることはできない。クライアントがオリジンを自由に決められるので、スクリプトが別のサイトの署名をキーに作らせる危険もある。この形は、物理キーなどに限った後の検討とする（[OPEN-092](../open-issues.md#open-092)）。
- **ログインのフォームを HTTP のクライアントで自動化する機能を中心にする**: パスワードを送ってクッキーを保てば、多くのサイトに使える。しかし、JavaScript で組み立てるページ、ボットの検出、CAPTCHA があれば使えず、ログインの自動化を利用規約で禁じるサイトもある。クッキーを保つ仕組みの要否は要望を見て決める（[OPEN-091](../open-issues.md#open-091)）。

## 帰結

- [ネットワークのモジュール](../03-interop/03-09-network.md)に「ウェブの認証（初回リリース版の後）」を設け、本 ADR の決定を【決定】として書く。
- HTTP のヘッダに秘密を渡す受け取り口、ホストが変わるリダイレクトでの扱い、TOTP のための HMAC、OAuth の手順の例など、加える機能の範囲と順は [OPEN-091](../open-issues.md#open-091) で決める。
- 物理キーを使う機能は、ウェブの認証よりも、サーバモードの承認の画面での操作ごとの承認に用いる方向で検討する（[OPEN-093](../open-issues.md#open-093)）。
