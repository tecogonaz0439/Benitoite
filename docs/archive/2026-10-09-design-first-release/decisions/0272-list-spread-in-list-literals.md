# 0272. リストリテラルに、リストのパターンと同じ形の展開 `..e` を一つまで書ける

- 状態: 採択
- 日付: 2026-09-30
- 関連章: [構文](../01-spec/01-02-syntax.md), [代数的データ型とパターンマッチ](../01-spec/01-05-data-types.md), [型システム](../01-spec/01-06-type-system.md), [評価意味論](../01-spec/01-08-evaluation.md), [コア計算と脱糖](../01-spec/01-12-core-calculus.md)
- 関連する未決事項: [OPEN-012](../open-issues.md#open-012)

## 背景

初回リリース版のリストのパターンは、`..` で残りの部分を表せる（`[first, ..rest]`、`[first, .., last]`。[ADR 0121](0121-pattern-extensions.md)）。一方、リストリテラルに書けるのは要素の式の並びだけであり、先頭に要素を加えたリストは `List.prepend(rest, first)`、二つのリストの連結は `List.concatenate(xs, ys)` と書く。

構文だけの測定の第一段階（[ADR 0246](0246-syntax-measurement-in-two-stages.md)）で、OpenCode と LongCat 2.5 Preview Free が最初に書いたスクリプトの構文の誤り 21 件のうち 11 件は、式の中にリストのパターンと同じ形を書いたもの（`[first, ..insertByCount(pair, rest)]`、`[p, ..sorted]` など）だった（[測定の集計](../../../../tools/syntax-measure/results/stage1-opencode.md)）。この誤りは構文の案によらず現れ、どれも `..` を末尾に置く形だった。LLM は、パターンで分解した形のままリストを組み立てようとする。本言語では、一部を変えたレコードの構築も `T(..e, f: v)` と `..e` で元の値を表しており（[ADR 0057](0057-record-declaration-construction-update.md)）、`..` の後の式を「元の値の中身をここに並べる」と読む書き方は、すでに言語の中にある。

リストは永続ベクタで表し、先頭と末尾への追加と連結はどれも O(log n) である（[標準ライブラリ](../03-interop/03-06-stdlib.md)）。展開をリストリテラルに加えても、計算量の見積もりは変わらない。

## 決定

1. リストリテラルの要素の一つを、展開 `..e` にできる。展開は一つのリストリテラルの中に一つまでとし、位置は問わない（`[x, y, ..rest]`、`[..init, last]`、`[a, ..mid, z]`、`[..xs]`）。組み立てられる形は、リストのパターンで分解できる形と同じである。
2. リストリテラルの型を `List[T]` とすると、展開の式 `e` の型は `List[T]` でなければならない。ほかの要素の規則は変えない。
3. 値は、展開の前の要素、`e` の値の要素、展開の後の要素を、この順に並べたリストである。要素と `e` は書いた順に、左から右へ評価する。
4. 結果の大きさの上限の検査（[ADR 0049](0049-size-limit-for-built-values.md)）は、`List.concatenate` と同じく、値を作る前に行う。
5. 一つのリストリテラルに展開を二つ以上書いたとき（`[..xs, ..ys]`）は構文エラーとし、診断は `List.concatenate` で書く修正案を示す。JavaScript の `...xs` や Python の `*xs` の形で書いたときは、`..xs` を修正案として示す。
6. 定数式の中のリストリテラルにも展開を書ける。展開の式も定数式でなければならない。

## 検討した代替案

- **展開をいくつでも、どこにでも書ける（`[..xs, ..ys, z]`）**: JavaScript と Python の書き方に近く、書けるものは最も広い。しかし、`List.concatenate` と同じ役割の書き方を増やす（設計原則 5）。組み立てられる形と分解できる形も食い違う。
- **展開を末尾だけに書ける（`[x, y, ..rest]`）**: 測定で観測した誤りはすべて覆える。しかし、パターンでは書ける `[..init, last]` を式では書けないという、分解と組み立ての食い違いが残る。
- **展開を加えず、専用の診断だけを出す**: 構文は増えない。しかし、LLM が分解した形のまま組み立てる書き方は案によらず多く、診断で毎回書き直させるより、同じ形を認めるほうが、生成の成功率を第一とする構文の基準（[目的と設計原則](../00-overview/00-01-goals.md)）に合う。

## 帰結

- 先頭や末尾に要素を加えたリストを、パターンで分解したときと同じ形で書ける。`List.prepend`・`List.append`・`List.concatenate` は残る。二つ以上のリストの連結は、引き続き `List.concatenate` で書く。
- 脱糖は、展開のあるリストリテラルを、要素の束縛と `List.concatenate` に当たる組み込みの関数の呼び出しに移す（[コア計算と脱糖](../01-spec/01-12-core-calculus.md)）。コア計算とバイトコードに新しい形は加えない。
- 構文だけの測定の案 V00〜V15 は、この変更の前の文法で測ったものであり、測定の道具の文法は変えない。第二段階の測定で、展開を書く誤りが減ったかを確かめる。
