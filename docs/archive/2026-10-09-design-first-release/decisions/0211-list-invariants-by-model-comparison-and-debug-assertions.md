# 0211. リストの不変条件は、単純なモデルとの突き合わせのテストと、デバッグビルドの debug_assert で確かめる

- 状態: 採択
- 日付: 2026-09-29
- 関連章: [標準ライブラリ](../03-interop/03-06-stdlib.md), [処理系のテスト戦略](../07-quality/07-03-compiler-testing.md), [性能](../07-quality/07-02-performance.md)
- 関連する未決事項: なし

## 背景

[標準ライブラリ](../03-interop/03-06-stdlib.md)の「List の内部の表現」は、`List[T]` を分岐の数を 32 とする RRB 木で表し（[ADR 0104](0104-list-as-persistent-vector.md)）、処理系のテストで次の三つの不変条件を確かめるとしていた。

1. 各ノードの要素の数の表は、子の要素の数の和と一致する。長さは、木と末尾の葉の要素の数の和である。
2. どの関数も、引数のリストのノードと葉を変更しない。
3. 木の高さは、要素の数に対して O(log n) に収まる。

一方、[処理系のテスト戦略](../07-quality/07-03-compiler-testing.md)の「テストの設計の原則」は、観察可能な振る舞いを確かめ、実装の詳細を確かめないと定める（[ADR 0080](0080-test-design-principles-and-test-audit.md)）。1 と 3 は、木のノードの中身と形を調べないと確かめられないので、テストに書くと実装の詳細を確かめることになる。緩和したノードを詰め直す条件など、木の形の細部は実装プランで定めるので、細部を変えるたびにそうしたテストが壊れる。2 は、関数を呼ぶ前後で引数のリストの要素の並びを比べれば、公開の関数だけで確かめられる。

## 決定

1. リストのテストは、観察可能な振る舞いを確かめる。無作為に選んだ操作の列を、リストと単純なモデル（Rust の `Vec`）の両方に同じ順に適用し、要素の並びと長さが一致することを確かめる。あわせて、操作の前後で引数のリストの要素の並びが変わらないことを確かめる（不変条件 2）。
2. 構造の不変条件（不変条件 1）は、テストではなく、実装の中の `debug_assert!` で、デバッグビルドのときだけ確かめる。実装の細部を変えるときは、この確認も一緒に書き直す。
3. 木の高さ（不変条件 3）は、テストでは確かめない。[性能](../07-quality/07-02-performance.md)の測定で、大きなリストの添字の操作の時間として観察する。

`debug_assert!` が見つけるのは処理系の不具合であり、言語の規則で定めた失敗ではない。AGENTS.md の「実装の規約」の「失敗を panic で表さない」は、言語の規則で定めた失敗を `Stop` か `Err` の値として返すことを求める規約なので、この決定はそれと食い違わない。`debug_assert!` はデバッグビルドでだけ有効であり（`debug_assertions` の設定。リポジトリの `Cargo.toml` の release のプロファイルはこれを有効にしていない）、リリースのビルドの振る舞いを変えない。`cargo test` はデバッグビルドで実行するので、決定 1 のテストが操作を適用するたびに、不変条件 1 も確かめられる。

リポジトリの `Cargo.toml` の `[workspace.lints]` が誤りにする lint のうち、Clippy の `panic` は `panic!` の使用を検出する lint であり（[Clippy のソース](https://github.com/rust-lang/rust-clippy/blob/master/clippy_lints/src/panic_unimplemented.rs)の lint の説明 "Checks for usage of `panic!`"）、`debug_assert!` を検出しない。Clippy 0.1.98 で、同じ lint の設定のクレートに `debug_assert!` と `debug_assert_eq!` を書いて検査し、`panic!` だけが誤りになることを確かめた（2026-09-29）。ほかの誤りにする lint（`unwrap_used`・`indexing_slicing` など）も、`debug_assert!` そのものは検出しない。ただし、`debug_assert!` の条件の式の中の添字や算術は、それぞれの lint の対象になる。

## 検討した代替案

- **07-03 に、内部の不変条件を確かめるテストを例外として認める規定を置く**: ADR を添えて、永続コレクションの構造の不変条件に限り、実装の詳細を確かめるテストを許す。しかし、木の形の細部を変えるたびにテストの書き直しが要る点は変わらない。実装の中の `debug_assert!` なら、確認が実装の隣にあるので、細部を変える作業の中で一緒に書き直せる。例外を認めると、ほかの段でも同じ例外を求める理由を作ることにもなる。

## 帰結

- 03-06 の「List の内部の表現」の不変条件の項を、確かめ方ごとに書き直す。07-03 の「持ち主の境界」の段の一覧に、ランタイムの永続コレクションを加える（[ADR 0212](0212-test-owner-boundaries-in-testing-chapter.md)）。07-02 の測る項目に、大きなリストの添字の操作を加える。
- AGENTS.md の「実装の規約」は `debug_assert!` に触れていない。実装プランで規約を見直すときに、処理系の不具合を見つけるために `debug_assert!` を使ってよいことと、その条件の式にも lint が掛かることを、AGENTS.md の「実装の規約」に加える。
