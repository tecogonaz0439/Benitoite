# 0300. 継続の型の値を `resume` の第一引数に限り、K-Drop に `State` の条件を加え、ストアの型付けで Ψ と σ の場所を一致させる

- 状態: 採択
- 日付: 2026-09-30
- 関連章: [コア計算と脱糖](../01-spec/01-12-core-calculus.md), [形式意味論と検証](../07-quality/07-04-formal-semantics.md)
- 関連する未決事項: なし

## 背景

形式検証の段階 B1 の定義と定理の言明を、Codex の GPT-6.1-Sol にレビューさせた（2026-09-30。`formal/reviews/2026-09-30-stage-b1-definitions/`）。[コア計算と脱糖](../01-spec/01-12-core-calculus.md)の規則のままでは性質 2（進行と保存）が成り立たない反例が、次の三つ示された。

一つ目は、継続の値の受け渡しである。01-12 は、V-Lam の前提と `lazy M` の検査で、環境から継続の型を持つ変数を除き、「ラムダの本体と `lazy` の本体では `resume` に型が付かない」とする。しかし、コア計算は継続の型の値を普通の値として扱うので、`λ(q: Cont(Unit → Unit ! {})). resume q ()` のようにラムダの引数で継続を受け取れる。リストに入れた継続を、ラムダの中でパターンで取り出すこともできる。こうして、継続 κ を作った節と違う R の場所で `resume κ V` が実行されると、C-ResumeL の「R が等しい」が成り立たず、保存が破れる。表層では、節の継続は `resume(v)` の形でだけ使え（[型システム](../01-spec/01-06-type-system.md)の「エフェクトの宣言とハンドラの型付け（初回リリース版）」）、継続を値として書く手段はない。コア計算の規則がこの制限を写していなかった。

二つ目は、`drop` の枠である。01-12 は「`drop` の枠は、κ を作った `handle` の枠より下にあるので、K' の中の `release` の枠が `State` を許していれば、`drop` の枠の位置でも許している。したがって、K-Drop は、`release` の枠についての前提を加えなくてよい」とする。この論証は、実行で到達する状態の性質（κ を作った枠との上下関係）を使っているが、状態の型付けは、この関係を持たないストアと `drop` の枠の組み合わせにも型を付ける。E-DropRel が `releases(K')` を継続の先頭に加えた後、`release` の枠を型付けするのに要る `State` を、`drop` の枠の位置のエフェクトが含むとは限らず、保存が破れる。

三つ目は、ストアの型付けである。01-12 は「ストア σ が Ψ のもとで型が付くとは、σ のすべての場所について次が成り立つこと」とし、Ψ が型を与える場所に σ の中身があることを求めていない。空のストアと `Ψ(ℓ) = Reference[Integer]` のもとで、`⟨Reference.get[Integer](ℓ), [], ∅⟩` に型が付くが、E-RefGet は σ(ℓ) を要するので遷移できず、進行が破れる。

## 決定

1. 継続の型の値（節の変数 k と、継続の場所 κ）は、`resume` の第一引数にだけ書ける。V-Var は継続の型を持つ変数に型を付けず、継続の場所は値として型が付かない。`resume` の型付けは、第一引数が節の変数のとき C-Resume（環境の中の継続の型を使う）、継続の場所のとき C-ResumeL を使う。V-Lam の前提と `lazy M` の検査で環境から継続の型を持つ変数を除く規則は残す（ラムダの本体と `lazy` の本体では `resume` に型が付かない）。
2. K-Drop に、「Ψ(κ) の継続の型のエフェクト ε' が `State` を含むなら、ε も `State` を含む」を前提に加える。E-Op が積む `drop κ` の枠では、ε' は `handle` の式のエフェクトであり、`drop` の枠の位置のエフェクトと等しいので、この前提は成り立つ。E-DropRel などで継続の先頭に加えた `drop` の枠についても、`State` はどの `handled(H)` にも含まれないので成り立ち続ける。
3. ストアの型付けに、「Ψ が型を与える場所は、σ に中身がある」を加える（σ と Ψ の場所が一致する）。

## 検討した代替案

- **継続を普通の値のままにし、環境の中の継続にも作った節の R を記録して、`resume` で R を確かめる**（レビューの案）: 継続の受け渡しを許すなら要る。しかし、表層は継続の受け渡しを許さないので、コア計算で許す理由がない。継続を値として持ち運べる規則は、ラムダやデータ型を通る経路のすべてで R を追う必要があり、規則が大きくなる。
- **K-Drop を変えず、状態の型付けを「実行で到達する状態」に限る**: 到達可能性を状態の型付けに持ち込むと、性質 2 を「型が付いた任意の状態」についての言明として示せなくなる。

## 帰結

- 01-12 の「ハンドラ」の型付けの規則と説明、「確かめる性質」の K-Drop とストアの型付けを改める。K-Drop についての「前提を加えなくてよい」とする説明を改める。
- 形式化（`formal/`）の段階 B1 は、この規則で書く。
- 処理系の実装と実装プランは変えない（処理系は表層の `resume(v)` だけを扱い、継続を値として受け渡さない）。
