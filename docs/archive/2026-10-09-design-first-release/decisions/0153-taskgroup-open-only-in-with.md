# 0153. `TaskGroup.open` は `with` の束縛の式にだけ書ける

- 状態: 採択
- 日付: 2026-09-29
- 関連章: [並行処理](../01-spec/01-11-concurrency.md), [リソース管理](../01-spec/01-10-resources.md)
- 関連する未決事項: なし

## 背景

並行処理は構造化されており、`TaskGroup` で起動したタスクは、その `TaskGroup` を束縛した `with` を抜ける時点で終わっている。したがって、`main` の呼び出しが終わった時点で、終わっていないタスクはない（[ADR 0115](0115-structured-io-concurrency.md)、[並行処理](../01-spec/01-11-concurrency.md)）。

一方、リソースの型の値は、`with` を使わずに `let` で束縛することもでき、その値はスクリプトが解放しない限り解放しない（[リソース管理](../01-spec/01-10-resources.md)）。`TaskGroup` もリソースの型なので、`let group = TaskGroup.open()` と書けば、起動したタスクの終わりを誰も待たないまま `main` を抜けられる。構造化の保証と食い違う。この食い違いは、外部の検証者による 01-spec のレビューで指摘された。

## 決定

1. `TaskGroup.open()` の呼び出しは、`with` の束縛の式（`with group = TaskGroup.open() do`）としてだけ書ける。それ以外の位置の呼び出しと、`TaskGroup.open` を関数の値として参照すること（引数に渡す、`let` で束縛するなど）は、型検査の誤りとする。
2. 診断は、`with` で束縛する書き方を修正案として示す。
3. `with` で束縛した `TaskGroup` を、関数の引数に渡したり、ラムダに捕捉したりするのはよい。`with` を抜けた後の `TaskGroup.spawn` は、これまでどおり実行時エラー（解放したリソースの使用）とする。

## 検討した代替案

- **範囲を表す関数に替える**: `TaskGroup.open` をやめ、`TaskGroup.run(lambda(group) … end lambda)` のように、集まりを受け取る関数を渡す形にする（Kotlin の `coroutineScope` と同じ形）。特別な規則は要らない。しかし、`with` と同じ役割の書き方が増え（原則 5）、`TaskGroup` をリソースとして扱う規則（解放の時期と順序、取り消し）を別に書き直す必要がある。
- **`let` で束縛した `TaskGroup` も、`main` の終わりやプログラムの停止で終わりを待つ**: 書き方の制限はない。しかし、タスクが終わる時点が、グループを開いた範囲と対応しなくなり、構造化の保証が「`main` の終わりまでに終わる」に弱まる。

## 帰結

- `TaskGroup` は、`with` の束縛の外で作れないので、どの `TaskGroup` も、束縛した `with` を抜ける時点で解放され、そこで起動したタスクの終わりを待つ。
- ほかのリソースの型（ファイル、ネットワーク）は、これまでどおり `let` で束縛できる。
