# 0149. `Http.Exchange` の解放の失敗を実行時エラーにせず、報告もしない

- 状態: 採択
- 日付: 2026-09-28
- 関連章: [リソース管理](../01-spec/01-10-resources.md), [ネットワークのモジュール](../03-interop/03-09-network.md), [評価意味論](../01-spec/01-08-evaluation.md), [並行処理](../01-spec/01-11-concurrency.md), [コア計算と脱糖](../01-spec/01-12-core-calculus.md)
- 関連する未決事項: なし

## 背景

`with` のブロックを抜けるときの解放が失敗したときは、実行時エラー（リソースの解放の失敗）とする（[リソース管理](../01-spec/01-10-resources.md)の「解放の失敗」）。並行処理では、どのタスクで実行時エラーが起きても、プログラム全体を止める（[並行処理](../01-spec/01-11-concurrency.md)の「失敗と停止」、[ADR 0115](0115-structured-io-concurrency.md)）。

HTTP サーバの受け付けた一つの要求と応答の組は、リソースの型 `Http.Exchange` で表し、`with` で束縛したときの解放は `Http.closeExchange` と同じ操作である（[ADR 0142](0142-http-api-shape.md)、[ネットワークのモジュール](../03-interop/03-09-network.md)）。`Http.closeExchange` は、応答を送っていなければ状態コード 500 の応答を送ってから接続を閉じるので、クライアントが先に接続を切っていれば、`NetworkErrorKind.ConnectionReset` などで失敗しうる。

`Http.serve` は、受け付けた要求ごとにタスクを起動し、タスクの中で `Http.Exchange` を `with` で束縛する。したがって、この規則のままでは、要求の処理の途中でクライアントが接続を切るだけで、そのタスクで実行時エラーが起き、サーバ全体が止まる。ブラウザが読み込みを中止する、クライアントが時間切れで諦めるなど、接続が切れることは、サーバを動かしていれば普通に起きる。

## 決定

1. `Http.Exchange` の解放が失敗しても、実行時エラーにしない。`with` のブロックを抜けるときのほか、タスクの取り消し、ハンドラが本体の続きを捨てるとき、実行時エラーか資源の不足でプログラムが止まるとき、`Process.Exit` の操作でプロセスを終えるときの解放にも当てはめる。
2. 失敗は報告しない。標準エラー出力にも、止まる理由の報告にも書かず、捨てる。解放が失敗した `Http.Exchange` も、解放済みとする。
3. `Http.closeExchange` は、これまでどおり `Result[Unit, NetworkError]` を返す。解放の失敗を調べたいスクリプトは、`with` のブロックの最後でこの関数を呼び、`Result` を調べる。
4. 解放の失敗を実行時エラーにしないリソースの型は、初回リリース版では `Http.Exchange` だけとする。`Http.Listener`・`File.Reader`・`File.Writer`・`TaskGroup` の解放の失敗は、これまでどおり実行時エラーとする。
5. [リソース管理](../01-spec/01-10-resources.md)の「解放の失敗」の規則を、リソースの型を定める章が例外を定められる形に改める。例外にするリソースの型は、その型を定める章に示す。

## 検討した代替案

- **実行時エラーのままにする**: 解放の規則が一つで済む。しかし、クライアントが接続を切るたびにサーバが止まる。止まらないようにする手段は利用者の側になく、`Http.serve` を使うだけの簡単なサーバでも起きる。
- **規則は変えず、`Http.serve` の中と下の層を使う例で `Http.closeExchange` を明示して呼び、結果を捨てる**: 規則の例外が要らない。しかし、下の層で書くスクリプトは、どれもこの呼び出しを忘れずに書く必要がある。忘れても、接続が切れるまでは正しく動くので、テストでは気付きにくく、サーバを動かしてから止まる（原則 1、原則 3）。
- **ネットワークのリソースの型をすべて例外にする（`Http.Listener` も含める）**: 規則が「ネットワークのリソースの型」で言える。しかし、待ち受けを閉じる操作は相手の接続に依存せず、失敗するのは処理系か OS の異常である。異常を黙って捨てる理由がないので、例外は、相手の都合で普通に失敗する `Http.Exchange` に限る。
- **解放の失敗を、どのリソースの型でも実行時エラーにしない**: 例外の規則が要らない。しかし、`File.Writer` の解放の失敗は、書いた内容がファイルに残らなかったことを表し、黙って捨てるとスクリプトの結果を気付かれずに誤らせる（[ADR 0068](0068-release-resources-on-stop.md) が止まる途中でも解放するとした理由と同じ）。
- **実行時エラーにはせず、標準エラー出力に報告する**: 接続が切れたことを利用者が知れる。しかし、切断はクライアントの普通の振る舞いであり、要求ごとに報告すると、スクリプトが自分で書いた標準エラー出力の内容が埋もれる。応答を送れたかを知りたいときは、`Http.respond` の `Result`（`NetworkErrorKind.ConnectionReset` など）で分かる。

## 帰結

- [リソース管理](../01-spec/01-10-resources.md)の「解放の失敗」に、リソースの型ごとの例外を置く。[ネットワークのモジュール](../03-interop/03-09-network.md)に、`Http.Exchange` がその例外であることを書く。
- [評価意味論](../01-spec/01-08-evaluation.md)の実行時エラーの種類の表の「リソースの解放の失敗」は、例外のリソースの型を除く。
- [コア計算と脱糖](../01-spec/01-12-core-calculus.md)では、`Http.Exchange` の事象 `release(V)` の応答を常に `ok` とする。
- [ADR 0068](0068-release-resources-on-stop.md) の「解放に失敗したときは、止まる理由の報告に、解放の失敗を加える」は、`Http.Exchange` には当てはまらない。
- 後の版でリソースの型を加えるときは、解放の失敗が相手の都合で普通に起きるかを確かめ、例外にするかを決める。
