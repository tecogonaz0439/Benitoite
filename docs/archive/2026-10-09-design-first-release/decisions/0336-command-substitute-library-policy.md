# 0336. コマンドを代替するライブラリは、既設の関数で足りるものを作らず、コマンドの操作を再現せず、言語の作りに合わせて作る

- 状態: 採択
- 日付: 2026-10-08
- 関連章: [ライブラリの構成](../03-interop/03-01-library-structure.md), [IO のモジュール](../03-interop/03-07-io-modules.md)
- 関連する未決事項: [OPEN-079](../open-issues.md#open-079), [OPEN-080](../open-issues.md#open-080), [OPEN-081](../open-issues.md#open-081), [OPEN-082](../open-issues.md#open-082)

## 背景

コーディングエージェントは、作業の多くをシェルのコマンド（`cp`・`mv`・`rm`・`grep`・`sed`・`git` など）で行う。Benitoite のスクリプトでも `Process.run` を使えばどのコマンドも起動できるが、そうするとエフェクトは `Process.Run` の一つになり、`rm -rf` も `ls` も同じ型に見える。起動したコマンドが中で行う操作は処理系の検査の外にある（[IO のモジュール](../03-interop/03-07-io-modules.md)の「外部コマンドの起動とシェル」、[セキュリティモデル](../07-quality/07-01-security-model.md)の「ハーネスとの分担」）。同じ操作をライブラリの関数で書けば、エフェクトは `File.Write` などになり、権限の対象はパスになる。利用者は実行の前に何を許すかを読み取れ（設計原則 3）、サーバモードの実行時の権限制御も対象を照合できる。

設計者は、2026-10-02〜03 に、初回リリース版の標準ライブラリでどのコマンドをどこまで代替できるかと、足りない機能、外部コマンドを包むライブラリのエフェクトを検討した（[コマンドを代替するライブラリの検討メモ](../sources/post-first-release/post-first-release-command-libraries.md)）。メモは、足りない機能をコマンドの名前で整理した。その整理をそのまま関数の一覧にすると、コマンドの名前・オプション・出力の形式をなぞる関数が並び、型の付いた値やリソースといった言語の作りが生かされない。そこで設計者は、ライブラリを作る方針を三つ定めた（2026-10-03）。本 ADR は、その方針を記録する。どの機能を加えるか、どの順で加えるかは決めない（[OPEN-079](../open-issues.md#open-079)）。

## 決定

初回リリース版の後に、コマンドを代替する機能を標準ライブラリ（公式の追加のライブラリを設けるときはそれも含む。[OPEN-078](../open-issues.md#open-078)）に加えるときは、次の方針に従う。

1. 既設の関数を組み合わせて書ける操作には、コマンドに当たる関数を新しく作らない。例えば、`mkdir -p` は `File.createDirectory` で、`cat`・`head` は `File.readLines` と `List.take` で書けるので、それに当たる関数を加えない。
2. コマンドの操作をそのまま再現しない。コマンドの名前・オプション・出力の形式（`grep -rn` の出力の行、`sed` の式、`find` の述語など）をなぞる関数は作らない。加えるのは、既設の関数を組み合わせても書けない機能か、書けても安全や性能の面で処理系が持つべき機能に限る。
3. 言語の作りに合った形で作る。結果は文字列の出力ではなく、レコードやリストなどの型の付いた値で返す。外部の資源はリソースとして `with` で開き、後始末を言語に任せる。権限の対象（パス、コマンドなど）が型と権限の確認に現れる形にする。失敗は `Result` と `IOError` で返す。

外部のコマンドを包むライブラリ（git のラッパーなど）も、同じ方針で作る。コマンドの引数を組み立てる薄い層にせず、操作を型の付いた関数とエフェクトとして表す。どう包むか、エフェクトをどう分けるかは [OPEN-082](../open-issues.md#open-082) で、そのエフェクトを権限の表示にどう出すかは [OPEN-081](../open-issues.md#open-081) で決める。

## 検討した代替案

- **コマンドごとに、同じ名前とオプションの関数を用意する**（`grep(pattern, path, recursive: true)` が一致した行の文字列を返す、など）: エージェントはシェルでの書き方をそのまま写せる。しかし、結果を文字列で返すと、利用する側が出力を再び解析することになり、型の検査が効かない。オプションの組み合わせごとに振る舞いを定める負担も大きい。
- **方針を定めず、要望が出た関数から加える**: 早く加えられる。しかし、関数を一つ加えるごとに、型付きの組み込みの宣言、IO 実行器の作業用のスレッド、権限の表の行、ゴールデンテスト、クレートのライセンスの確認（[ADR 0138](0138-crates-and-licenses-for-stdlib.md)）が付いてくる。既設の関数で書ける操作まで加えると、この費用が増え、同じ役割の関数が並ぶ（設計原則 5）。

## 帰結

- [ライブラリの構成](../03-interop/03-01-library-structure.md)に「コマンドを代替するライブラリの作り方（初回リリース版の後）」を設け、本 ADR の決定を【決定】として書く。初回リリース版の標準ライブラリには影響しない。
- grep に当たる検索は、行の文字列を返す関数ではなく、ファイル・行番号・一致した範囲を持つレコードのリストを返す関数にする方向になる。jq 風の問い合わせの言語や awk に当たるものは、`Json` の関数と一般のコードで書けるので、作らない方向で見直す。どちらも、加える機能の範囲とあわせて [OPEN-079](../open-issues.md#open-079) で決める。
- 外部コマンドを使う操作で、標準ライブラリ、コマンドを包むライブラリ、`Process.run` をどの順で選ばせるかと、それをエージェントにどう示すかは [OPEN-080](../open-issues.md#open-080) で決める。
