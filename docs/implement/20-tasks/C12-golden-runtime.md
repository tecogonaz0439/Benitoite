# C12 ゴールデンテスト: ランタイム

- 依存する作業: [C10](C10-golden-runner.md), [R29](R29-runtime-builtins.md), [R23](R23-reference-cells.md)（R23 に依存する理由は「手順の要点」の「依存に加えた作業」）
- 難易度: 2（1〜5。[README](../README.md) の「作業一覧」の目安）
- 規模の見込み: 大（テストのスクリプトと期待値のファイルが中心。Rust のコードはほとんど書かない）
- ブランチ: impl/C12-golden-runtime

## 目的

初回リリース版で加わる実行時の振る舞い（ハンドラと継続、`Lazy`、`Reference`、タスクと `TaskGroup`、リソースと `with`、出力、IO の二つの方式）を、CLI のゴールデンテストで確かめる。VM・スケジューラ・ランタイムの単体テストは R20〜R31 が書いた。本作業は、利用者のスクリプトから見える振る舞い（出力、終了状態、実行時エラーの報告、解放の失敗の報告）を固定する。ゴールデンテストの実行器が、`run` のテストを IO の二つの方式で走らせ、参照インタプリタとの差分を確かめるので（C10）、ここで置くテストはそれらの確かめの対象にもなる。

## 作るもの

パスは処理系のクレート `crates/benitoite/` からの相対パスである。

- `testdata/handlers/`・`testdata/concurrency/` のテスト（07-03 の区分）
- `testdata/eval/`・`testdata/io/` に加えるテスト（`Lazy`・`Reference`・リソース・出力・標準入力）

処理系の `src/` と実行器は変えない。

## 手順の要点

### 何をテストにするか

| 区分 | 確かめる振る舞いの例 |
|---|---|
| `handlers` | 利用者が定義したエフェクトの操作を `handle` で処理する。末尾で再開する節と、継続を保存してから再開する節。`resume` を呼ばずに本体を捨てる節（本体の `with` のリソースが解放されること）。入れ子の `handle` で内側から外側の操作を探すこと。組み込みの操作をハンドラで差し替えること（01-07「影響の大きい操作（初回リリース版）」） |
| `eval` | `lazy` の値を初めて使うときに一度だけ評価すること。`Reference` のセルの読み書きと更新。定数の値 |
| `concurrency` | `Task` の起動と待ち、`TaskGroup` の開閉と、その中のタスクの取り消し、失敗の伝わり方、行き詰まりの報告（R1001）。07-03 のとおり、出力の順序がタスクの切り替えの時機によらないように書く |
| `io` | `with` で開いたファイルの解放、解放の失敗の報告、`Process.exit` で止める途中の解放、標準入力を読むスクリプト（C10 が加えた `.stdin` のファイルを使う）、出力の転送（改行のない出力の後の入力の読み込みなど、02-09「出力のバッファ」の転送の時点） |

- 各テストの先頭に `// spec:` の行を書く。
- 切り替えの順序そのもの、取り消しと完了の順序の入れ替え、時間の待ちの長さに依存する振る舞いは、ゴールデンテストで確かめない。順序を与えるスケジューラと仮想の時間（07-03 の同名の節）で、R25〜R31 の単体テストが確かめる。実時間に依存するテスト（`Clock.sleep` の長さを測るものなど）も置かない。
- 中断の要求（`SIGINT`・`SIGTERM`）は、CLI を別のプロセスとして起動するテストで R31 が確かめるので、本作業では扱わない。
- ネットワーク（`network` の区分）と標準ライブラリのモジュール（`stdlib` の区分）は U3 が加える。
- `.stdin` の読み方（C10 の実行器）は、標準入力を読むテストで確かめる。C10 が確かめずに残した場合である（C10「受け入れテスト」）。

### 差分テストとの関係

タスクを起動する組み込みの関数を使うテストは、参照インタプリタが実行しないので差分テストから外れる（C10）。`handlers`・`eval` のテストは、なるべくタスクを使わずに書き、差分テストの対象に残す。どのテストが差分テストの対象になったかを、実行器の出力（外した数）で確かめ、完了の報告に書く。

### 依存に加えた作業

`Reference` を VM に組み込み、`Reference.new`・`get`・`set` の本体を書くのは R23 である。R25 が R23 に依存するので、R23 は R29 の依存の連なりにも入るが、`Reference` のテストが直接使う作業なので依存に明示する。

### 見つけた不具合の扱い

C11 と同じとする。期待する結果を設計書から決め、実際の結果が食い違うテストは `testdata/` に置かず、スクリプト・期待値・実際の結果・設計書の節を完了の報告に添える。[OPEN-062](../../design/open-issues.md#open-062) の項目に当たる食い違いを見つけたら、その項目の番号を添える（再現テストは R30 が持つ）。

## 受け入れテスト

| 場合 | 期待 |
|---|---|
| 区分 | `handlers`・`concurrency` の区分があり、上の表の振る舞いの例のそれぞれにテストがある |
| IO の方式 | `concurrency` のテストが、IO の二つの方式で同じ結果になる（実行器が確かめる。07-03「IO の方式のテスト」の二つ目の段落） |
| 差分テスト | `handlers` と `eval` に加えたテストのうち、差分テストの対象になったものの数を完了の報告に書く |
| 節の網羅 | 上の「読む設計書の節」の、見出しに「（初回リリース版）」を付けた節と、01-10・01-11 の節のそれぞれに、`// spec:` の行で指すテストが一つ以上ある（一覧を完了の報告に書く） |
| 新しいテストの関門 | 加えたテストのすべてが `test-audit` の作成時の関門を通っている |

## 完了条件

- `scripts/check.sh` が通る（00-02「完了条件の共通の検査」）
- 受け入れテストのすべての場合を確かめている
- 設計書と食い違う実際の結果を、期待値に固定していない

## 難易度の理由

C11 と同じく、処理系のコードを書かずにスクリプトと期待値を書く作業である。注意が要るのは、タスクを使うテストの出力を切り替えの時機によらない形にすることと、ゴールデンテストと単体テストの受け持ちを分けることである。
