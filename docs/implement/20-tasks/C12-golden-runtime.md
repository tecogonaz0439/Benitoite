# C12 ゴールデンテスト: ランタイム

- 依存する作業: [C10](C10-golden-runner.md), [R29](R29-runtime-builtins.md), [R23](R23-reference-cells.md)（R23 に依存する理由は「手順の要点」の「依存に加えた作業」）
- 難易度: 2（1〜5。[README](../README.md) の「作業一覧」の目安）
- 規模の見込み: 大（テストのスクリプトと期待値のファイルが中心。Rust のコードはほとんど書かない）
- ブランチ: impl/C12-golden-runtime

## 目的

初回リリース版で加わる実行時の振る舞い（ハンドラと継続、`Lazy`、`Reference`、タスクと `TaskGroup`、リソースと `with`、出力、IO の二つの方式）を、CLI のゴールデンテストで確かめる。VM・スケジューラ・ランタイムの単体テストは R20〜R31 が書いた。本作業は、利用者のスクリプトから見える振る舞い（出力、終了状態、実行時エラーの報告）を固定する。ゴールデンテストの実行器が、`run` のテストを IO の二つの方式で走らせ、参照インタプリタとの差分を確かめるので（C10）、ここで置くテストはそれらの確かめの対象にもなる。

## 手順の要点

### 何をテストにするか

| 区分 | 確かめる振る舞いの例 |
|---|---|
| `handlers` | 利用者が定義したエフェクトの操作を `handle` で処理する。末尾で再開する節と、継続を保存してから再開する節。`resume` を呼ばずに本体を捨てる節（本体の `with` のリソースが解放されること。観測の方法は後述の「解放の観測」）。入れ子の `handle` で内側から外側の操作を探すこと。組み込みのエフェクトの操作をハンドラで処理すること（01-07「利用者が定義するエフェクトとハンドラ（初回リリース版）」の、組み込みのエフェクトの操作も `handle` で処理できるとする段落と `readPort` の例） |
| `eval` | `lazy` の本体が `Lazy.force` まで評価されないこと（`Lazy.force` を呼ばない `lazy` の本体の 0 の除算は起きない。`Lazy.force` を呼ぶと、最初の `Lazy.force` の位置で実行時エラーになる）。二度目の `Lazy.force` が一度目と同じ値を返すこと。`Reference` のセルの読み書きと更新。定数の値 |
| `concurrency` | `Task` の起動と待ち、`TaskGroup` の開閉と、その中のタスクの取り消し、失敗の伝わり方、行き詰まりの報告（R1001）、取り消したタスクの結果の待ち（R1002。[ADR 0317](../../design/decisions/0317-await-on-cancelled-task-is-runtime-error.md)。例: `resume` を呼ばない節で、長い `Clock.sleep` で待つタスクを取り消し、その `Task` を `Reference` に入れておいて、`handle` の後で `Task.await` で待つ）。出力の順序がタスクの切り替えの時機によらないように書く（後述の「時機に依存しないテストの書き方」） |
| `io` | `with` で開いたファイルの解放（観測の方法は後述の「解放の観測」）。`File.closeReader` を呼んだ後の `with` が二度目の解放をせず、二度目の `File.closeReader` が `Result.Ok(())` を返すこと（01-10「解放の失敗」の最後の段落）。`Process.exit` で止まる実行の終了状態と出力の書き出し。標準入力を読むスクリプト（C10 が加えた `.stdin` のファイルを使う）。出力の転送（改行のない出力の後の入力の読み込みなど、02-09「出力のバッファ」の転送の時点） |

- 各テストの先頭に `// spec:` の行を書く。
- 切り替えの順序そのもの、取り消しと完了の順序の入れ替え、時間の待ちの長さに依存する振る舞いは、ゴールデンテストで確かめない。順序を与えるスケジューラと仮想の時間（07-03 の同名の節）で、R25〜R31・R39 の単体テストが確かめる。実時間に依存するテスト（`Clock.sleep` の長さを測るものなど）も置かない。
- 中断の要求（`SIGINT`・`SIGTERM`）は、CLI を別のプロセスとして起動するテストで R31 が確かめるので、本作業では扱わない。
- ネットワーク（`network` の区分）と標準ライブラリのモジュール（`stdlib` の区分）は U3 が加える。
- `.stdin` の読み方（C10 の実行器）は、標準入力を読むテストで確かめる。C10 が確かめずに残した場合である（C10「受け入れテスト」）。
- 解放の失敗の報告（R0401、止める途中の解放の失敗の注記）は、ゴールデンテストでは作れない。U2 のリソース（`File.Reader`・`TaskGroup`）の解放は失敗せず、失敗を差し込む開発用の環境変数もないためである。報告の組み立ては R38 の単体テストが、止める手順での解放の失敗のまとめ方は R28 の単体テストが、偽の資源で確かめる。01-10「解放の失敗」の節の網羅には、上の `File.closeReader` の二度目の呼び出しのテストを当てる。
- 出力の転送について、ゴールデンテストで固定できるのは、標準出力に書かれた内容と順序だけである。転送が起きる時点そのもの（入力の読み込みが始まる前に出力先に届いていること）は、R29 の単体テストと、R30 の R13 の再現テストが確かめる。
- 空のディレクトリを要するテストは、ディレクトリの中にファイルを置くか、既存のディレクトリを使う。`.files/` の中の空のディレクトリは git に残らないので、ほかの環境で実行したときにテストの前提が崩れる。

### 解放の観測

解放そのものは出力に現れない。リソースが解放されたことは、次の方法で観測する。`with` で束縛した `File.Reader` を `Reference` に入れてブロックの外へ持ち出し、ブロックを抜けた後でその `File.Reader` に `File.readLine` を呼ぶ。解放済みなら、実行時エラー（解放したリソースの使用。01-10「解放したリソースの使用」）で止まる。`handle` の節が `resume` を呼ばずに本体を捨てる場合も、本体の `with` で束縛した `File.Reader` を同じ方法で持ち出して確かめる。

`Process.exit` で止める途中の解放は、この方法で観測できない（`Process.exit` の後にスクリプトは続かない）。止める途中の解放は R29 と R28 のプログラムでの確かめが受け持ち、C12 は終了状態と、`Process.exit` の前に書いた出力が書き出されることだけを固定する。

### 時機に依存しないテストの書き方

実行器は、`run` のテストを直接呼び出し（`Direct`）と要求と応答（`Request`）の二つの方式で実行し、結果が一致することを確かめる（C10）。タスクの切り替えの時機で結果が揺れるテストは、方式の間で食い違って失敗する。次のように書く。

- `Task.race`・`Task.withTimeout` は、勝ち負けの差が明らかな場合だけに使う。すぐ値を返す関数と、長い `Clock.sleep` で待つ関数を競わせる（負けた側は取り消されるので、実時間では待たない）。ほかに、空のリストの `Task.race` が `Option.None` を返す場合と、要素が一つの場合を使う。`Task.withTimeout(0, …)` や、短い待ちどうしの比較は使わない。
- 出力は、`Task.all`・`Task.await`・`TaskGroup` を束縛した `with` の終わりの後に書く。待つ操作の後の操作は、待ったタスクのすべての操作の後に起きる（01-11「タスクの切り替え」）ので、「タスクが一行書き、`main` が `Task.await` で待った後に一行書く」順序は安定する。
- 行き詰まりの報告（R1001）の注記は、タスクを起動した順に並ぶ（02-10「実行時エラーと資源の不足の報告」）ので安定する。作り方の例: `TaskGroup.spawn` で起動したタスクが、`Reference` に自分の `Task` が入るまで回って待ち、入ったら自分を `Task.await` で待つ。
- `Clock.monotonicMilliseconds` などの時刻の値は出力しない。
### 使ってよい標準ライブラリ

テストは作業の時点の標準ライブラリ（`src/prelude/stdlib/` の `.bnt`）にある名前だけを使う。U3 が加える関数と型クラスの実装（`Process.run`・`Process.shell`、`Benitoite.IO.Random`、`Benitoite.Network.Http` など。[10-14](../10-interfaces/10-14-prelude-and-stdlib-sources.md)「モジュールの一覧」の U3 が加えるものの段落）は使わない。設計書の例が使っていても、その名前が無いことを設計書との食い違いとして扱わない。

- IO のモジュールは非公式の名前（`import Benitoite.Unofficial.IO.Console`・`File`・`Process`・`Clock`。ADR 0286）で import する。
- `Task.race`・`Task.withTimeout` を呼ぶ関数の `uses` に書く `Clock.Time` には、`Clock` の import が要る（01-11「タスクを起動する関数」）。`Task` は prelude のモジュールなので、`Task` の関数を呼ぶだけなら import は要らない。
- 01-11「例」の節は U3 の名前（`Http`・`Process.run`）で書かれている。この節は、U2 の名前で書いた同じ形のテスト（`TaskGroup.spawn` でタスクを起動し、`TaskGroup` を束縛した `with` の終わりで待つ）で網羅する。
- 02-10「解放の失敗の報告」の例が使う `File.Writer` は、U2 にない。この例を写したテストは置かない（解放の失敗の報告は前述のとおり単体テストが受け持つ）。

### 差分テストとの関係

タスクを起動する組み込みの関数を使うテストは、参照インタプリタが実行しないので差分テストから外れる（C10）。`handlers`・`eval` のテストは、なるべくタスクを使わずに書き、差分テストの対象に残す。どのテストが差分テストの対象になったかを、実行器の出力（外した数）で確かめ、完了の報告に書く。

### 依存に加えた作業

`Reference` を VM に組み込み、`Reference.new`・`get`・`set` の本体を書くのは R23 である。R25 が R23 に依存するので、R23 は R29 の依存の連なりにも入るが、`Reference` のテストが直接使う作業なので依存に明示する。

### 見つけた不具合の扱い

C11 と同じとする。期待する結果を設計書から決め、実際の結果と比べる。実際の結果が設計書と食い違うときは、期待値を実際の結果に合わせない（書き直しの指定 `BENITOITE_BLESS` で作った期待値は、設計書と照らしてから残す）。食い違ったテストは `testdata/` に置かず、スクリプトと、設計書から決めた期待値と、実際の結果と、設計書の節を、完了の報告に添える（`scripts/check.sh` を通すために期待値を曲げない）。`tests/golden.rs` の CLI の外の検査（`run` のケースの VM と参照インタプリタの比較、直接呼び出しと要求と応答の比較など）だけで落ちるケースも、処理系の不具合として同じく `testdata/` に置かずに報告する。`tests/golden.rs` に除外の表を足さない。結果が揺れるケースを `NONDETERMINISTIC_CASES` に足すこともしない（揺れないように書き直す。前述の「時機に依存しないテストの書き方」）。報告を受けたオーケストレータが、直す作業を起こすか、設計書を改めるかを決める。

[OPEN-062](../../design/open-issues.md#open-062) の項目に当たる食い違いを見つけたら、その項目の番号を添える（再現テストは R30 が持つ）。

## 完了条件

- `scripts/check.sh` が通る（00-02「完了条件の共通の検査」）

## 難易度の理由

C11 と同じく、処理系のコードを書かずにスクリプトと期待値を書く作業である。注意が要るのは、タスクを使うテストの出力を切り替えの時機によらない形にすることと、ゴールデンテストと単体テストの受け持ちを分けることである。
