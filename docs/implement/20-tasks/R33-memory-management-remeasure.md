# R33 メモリの管理の確定のための測り直し

- 依存する作業: [R30](R30-open-062-reproduction.md)、[R36](R36-persistent-vector.md)、[R37](R37-map-and-set.md)、[C16](C16-bench.md)
- 難易度: 3（1〜5。README の「作業一覧」）
- 規模の見込み: 小（500 行未満。ワークロードと記録）
- ブランチ: impl/R33-memory-remeasure

## 目的

第 1 段の測定（R12）で暫定に採ったメモリの管理の方式を、ハンドラ・タスク・IO・永続コレクションを加えた後に測り直し、停止の時間と保持する量を確かめる（[ADR 0259](../../design/decisions/0259-compare-mark-sweep-and-rc-in-stage-1.md) の決定 4、[ADR 0268](../../design/decisions/0268-staged-runtime-rebuild.md) の決定 5）。その記録を設計者に示し、設計者が方式を確定して ADR に記録し、[OPEN-036](../../design/open-issues.md#open-036) を決着させる。

本作業は、測って記録し、確定してよいかの案を示すところまでを行う。方式を確定するのも、ADR を書くのも、本作業ではない。HTTP のワークロード（07-02 の http）と map のワークロード（U3 の `Map` の関数を要る。C16 の「目的」）は U3 の作業の後に測る。設計者は、OPEN-036 の決着をこの分の測り直しまで待つと決めた（2026-09-30。[README](../README.md) の「U3・U4 で決めたこと」の 11）。ベンチマークは U3 の L41 が加え、測定は U3・U4 を終えた後に行う（[90-after-completion.md](../90-after-completion.md)）。

## 作るもの

- ワークロード: 07-02「初回リリース版の完了時の測定」の handler（末尾で再開する節と、継続を保存してから再開する節の二つの形。後者は `resume` の後に計算が続く節、つまり末尾でない再開の意味である。C16 の作るものの表を参照）、tasks、cycle は、C16 が `tools/bench/programs/` に置いたもの（`handler.bnt`・`tasks.bnt`・`cycle.bnt`）を使い、二つ目を作らない。入力の大きさを変える必要があれば、C16 の `BENCH_INPUTS` の値を改める。
- 測定の道具: R12 が作った道具（`HeapStats` を読む例のプログラムと、記録を作るスクリプト）を使う。足りない項目を読む変更だけを加える。
- 測定の記録: `tools/bench/results/<日付>-memory-remeasure-<コミット>.md` と、スキル `benchmark` の手順で作る `.html`。

## 手順の要点

1. 測る構成は、今の本番の枝（暫定に採った方式と k）である。暫定に採らなかった方式は、R14 がリビジョンとして残したが、そのリビジョンにはハンドラ・タスクなどがないので、新しいワークロードでは比べられない。記録には、第 1 段のワークロード（fib・loop・list・tree・eval・string と R12 の追加のワークロード）について、第 1 段の記録の同じ方式の値と今の値を並べ、ハンドラなどを加えたことによる変化を示す。
2. 測る項目は、ADR 0259 の決定 3 の項目のうち、採った方式に意味のあるもの（実行時間、確保の量、生きている量、最大常駐メモリ、回収か解放で止まる時間の p50・p95・p99・最大、辿った根の数。参照カウントなら、参照の数の増減の回数と省けた回数、再利用の率、遅らせた解放の量）と、07-02 の「回収の費用」の項目（回収か解放にかかる時間の合計、止まる時間の分布、最大常駐メモリ）である。止まる時間は `HeapStats::pause_nanos` から求める。
3. ワークロードは、handler・tasks・cycle と、list・tree・eval である（map と http は U3 の後。「目的」）。tasks は、同時に存在するタスクの数を変えて、最大常駐メモリを測る（07-02「並行処理でのメモリ」）。cycle は、採った方式が循環を回収していること（最大常駐メモリが繰り返しの数に比例して増えないこと）を確かめる。
4. リストの表現が永続ベクタに変わった（R36）ので、list の値を第 1 段と比べるときは、表現の変化による差が含まれることを記録に書く（ADR 0268 の決定 4。永続ベクタの変更を方式の比較に混ぜない）。
5. スキル `benchmark` の手順に従う（計算機を静かにする、10 回の中央値、CPU プロファイルの所見）。
6. 記録の最後に、「採った方式を確定してよいか」の案と、その根拠（止まる時間の最大や保持する量が、ハンドラやタスクで第 1 段の見込みから外れていないか）を書く。外れているときは、ADR 0259 の帰結の増分の回収や、ADR 0277 の見直しが要るかの所見を書く。決めるのは設計者である。

## 受け入れテスト

測定の作業なので、処理系のテストは加えない。ワークロードは次を満たす。

- 各ワークロードが、本番のビルドで終了状態 0 で終わり、決まった出力を書く（出力を記録に書き、測定のたびに同じであることを確かめる）。
- 各ワークロードの本言語での実行時間が、07-02 の決め方（1 秒から 10 秒程度）に収まる入力の大きさにしてある。

## 完了条件

- `scripts/check.sh` が通る（ワークロードの `.bnt` と道具の変更が、書式と lint の検査を通る）
- 測定の記録が `tools/bench/results/` にあり、比べた構成（コミット、ビルドの設定）、入力、結果、確定してよいかの案が書かれている
- 完了の報告に、記録の要約と、map と http の測り直しで確かめる点を書いている

## 確認の観点

- 測った構成とコミットが記録にあり、再現できるか。
- 止まる時間の分布（p50・p95・p99・最大）を、平均だけでなく示しているか。
- 表現の変化（永続ベクタ）や、新しい機能の費用と、メモリの管理の方式の費用を区別して書いているか。
- 決定を記録に書き込んでいないか（案にとどめているか）。

## 難易度の理由

処理系を変えない測定の作業であり、道具は R12 のものを使える。ワークロードの入力の大きさを決めることと、方式の費用をほかの費用から分けて読むことに注意が要る。
