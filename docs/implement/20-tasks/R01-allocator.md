# R01 確保器と対象の頭

- 依存する作業: [C01](C01-stage1-interfaces.md)
- 難易度: 5（1〜5。README の「作業一覧」）
- 規模の見込み: 大（1500 行超）
- ブランチ: impl/R01-allocator

## 目的

ヒープの内部の層の土台（確保器、対象の頭、対象の列挙）を作る。値の表現（[ADR 0258](../../design/decisions/0258-sixteen-byte-value-enum.md)）と `unsafe` の境界（[ADR 0260](../../design/decisions/0260-heap-and-unsafe-boundary.md)）の決定のうち、「ヒープの対象は自前の確保器が確保した塊の中に頭付きで置き、値は `NonNull` で指す」「`unsafe` はヒープのモジュールに閉じ込める」を、この作業で形にする。以後の R02〜R04・R06・R11 は、本作業が作る内部の層の安全な関数だけを呼んで、公開の層と二つのメモリの管理を書く。

本作業は `unsafe` を書く最初の作業である。`unsafe` の一つ一つが引く不変条件と、それを確かめるテストを、後の作業が読んで引き継げる形で残すことが、この作業の成果の半分を占める。

## 手順の要点

### 内部の層が持つもの

`HeapCore` は、区間の中で `&HeapCore` から確保するので、変わる欄を内部の可変性（`Cell`、`RefCell` など）で持つ（10-08「内部の層の入口」）。少なくとも次のものを持つ。

| 欄の役割 | 内容 |
|---|---|
| 確保器 | 塊の並びと、大きさの区分ごとの空きの並び。大きな対象（塊に収まらないもの）は別に確保する |
| 対象の列挙 | 生きている対象をすべて辿る手段（マーク・スイープの掃き出し、`Heap::object_ids`、ヒープの検証器が使う） |
| 測定の記録 | `HeapStats` の確保と解放の項目（`allocations`・`allocated_bytes`・`peak_heap_bytes`・`frees`）。`frees` は解放の関数だけが数え、R03・R04 は足さない。回収の項目は R03・R04 が更新する |
| 設定 | `HeapConfig` の写し |
| ヒープの番号（すべての構成） | 不変条件 H9 を確かめるために `Slot` に書く `HeapNo`（10-08「根の保存領域」、[ADR 0281](../../design/decisions/0281-heap-number-in-slot-and-contract-safety.md)）。`HeapCore` を作るときに、プロセスで一つの `static` の `AtomicU32` から `fetch_add` で得る。番地から作らない（ヒープを捨てて作り直すと番地が再び使われ、古い `Slot` を見分けられない）。この計数器は、00-02「大域の状態」の例外である |

方式ごとの状態（印、参照の数、遅らせた解放の並び、生きているセルの表）の欄は、R02 が方式の境目を作り、R03・R04 が中身を書く。本作業は、頭の中に印か参照の数を置く場所だけを用意する。

### 対象の頭と配置

- 頭は、種類（10-08 の `ObjKind` と、`Fields` のときの `FieldsKind`）、長さ、32 ビットの印（`tag`）、方式ごとの語（マーク・スイープでは印、参照カウントでは参照の数と、解放の候補に並んでいることの印）を持つ。機能 `heap-verify` の構成では、確保の世代も持つ。ヒープの番号は `Slot` と `HeapCore` にあり、頭には置かない。
- 配置の切り上げは、`Slot` と `Value` の整列（8 バイト以上）を満たす。値の並びを持つ対象とセルの中の値は、ヒープの番号を持たない 16 バイトの値として置いてよい（対象と同じヒープにあることが確保の時点で決まるため。10-08「根の保存領域」）。対象の中の値は、参照カウントの数に数える（不変条件 H6）。
- 文字列と `Bytes` の中身を対象の中に置くか、別の領域に置くかは本作業が決める。別の領域に置くときは、その容量を `allocated_bytes` と生きている量に含める（ADR 0259 の決定 6。10-08「設定と測定の記録」）。
- `Opaque` と `Host` の対象は、Rust の値（`Box<dyn OpaqueData>`・`Box<dyn HostData>` など）を持つ。解放するときに、その Rust の値の `drop` を呼ぶ。`Host` の対象が持つ `Slot` の扱い（参照カウントの数を減らしてから捨てる）は R02・R04 が方式の側で書く。この `drop` は Rust の記憶域を返すだけであり、言語のリソースの解放やタスクの取り消しを代わりに行わない（10-08「根の保存領域」の最後の段落。後始末の順序は VM が守る）。
- `Value<'static>` の大きさが 16 バイトであることは、10-08 の `value.rs` の定数の表明（`heap-verify` を無効にした構成）が確かめる。本作業は、頭と中身の大きさを定数で表し、テストで確かめる。

### 確保と解放

- 確保は、大きさの区分ごとの空きの並びから取り、なければ塊から切り出し、塊が足りなければ新しい塊を Rust の確保器（`std::alloc`）から得る。確保した量の計算は溢れを検査する（`checked_add` など）。Rust の確保器が失敗したときは、`std::alloc::handle_alloc_error` に任せる（02-09「panic 境界」のとおり abort で終わる）。
- 解放は、内部の層の関数 1 つ（例: `free_object`）に集める。`HeapStats::frees` を一つ増やすのはこの関数だけである。解放する前に、`Opaque`・`Host` の Rust の値を捨てる。解放した領域は、機能 `heap-verify` の構成では `POISON_BYTE`（10-08）で埋め、頭の世代を進める。
- 機能 `heap-per-object` の構成では、塊を使わず、対象ごとに `std::alloc` で確保し解放する（ADR 0260 の決定 7 の最後の箇条）。このとき、解放した領域は Rust の確保器に返るので、読むと未定義動作になる。世代の確かめ（R02 の `NoGcCtx::load`）が解放した領域を読まずに済むように、世代と生死を内部の表（番地から世代への表など）で持つ（10-08「確かめ方の口」の「対象ごとの確保」の行）。
- 区間の中では、どの対象も解放せず動かさない（不変条件 H1）。本作業の確保器は対象を動かさない（非移動）。解放の関数は、回収（区間の外）からだけ呼ばれる。これを型で表すため、解放の関数は `&mut HeapCore` を取る形にするか、区間の中から呼べない位置にだけ置く。

### 対象の列挙と識別

- 生きている対象を列挙する手段（塊の頭を順に辿る、または生きている対象の表）を用意する。マーク・スイープの掃き出し（R03）、`Heap::object_ids`（R02）、ヒープの検証器（R02・R11）が使う。
- `ObjId` は番地から作る（10-08 の `ObjId` のコメント）。`ValueCtx::object_id` は即値に `None` を返す。
- `ValueCtx::kind` は即値に `None` を返し、対象の頭の種類を返す。`ValueCtx::same_object` は、両方が対象でその番地が等しいときに限り `true` を返す。

### `unsafe` の書き方

- `unsafe` のブロックは操作を一つだけ含め、直前に `// SAFETY:` のコメントで、前提とする不変条件の番号（10-08 の H1〜H11）と、それが成り立つ理由を書く（00-02「`unsafe` の書き方」。lint `undocumented_unsafe_blocks`・`multiple_unsafe_ops_per_block` が形を確かめる）。
- 内部の層の各ファイルの先頭の `//!` に、そのファイルが関わる不変条件の一覧を書く。10-08 の H1〜H11 で足りない局所の不変条件（例: 「空きの並びの項目は、確保器が切り出した範囲の中を指す」「頭の長さの欄は、確保したときの中身の大きさと一致する」）は、ファイルの先頭で番号（例: `A1`）を付けて定め、`// SAFETY:` から引く。
- 内部の層の `unsafe fn` には、呼び出し側が守る条件を `/// # Safety` の節で書く。公開の層（`ctx.rs` など）には `unsafe` を書かない（H10）。本作業が `ctx.rs` に書く三つの関数も、内部の層の安全な関数を呼ぶだけにする。
- ポインタの計算は、確保した範囲の中に収まることを、計算の直前の確かめか、確保の時点で決まった長さから示す。範囲の外を指しうる計算（添字を使う読み出し）は、長さと比べてから行う。

### 本作業が決めて、完了の報告の「判断したこと」に書くもの

- 塊の大きさ、大きさの区分、大きな対象の境目
- 文字列と `Bytes` の中身の置き場所
- 頭の配置と大きさ（`heap-verify` の有無の両方）
- 内部の層で追加した局所の不変条件の一覧

## 受け入れテスト

テストは内部の層の関数を直接呼んで書く。二つのメモリの管理の機能（`gc-mark-sweep`・`gc-refcount`）のどちらでも通るように書く（00-02「テストの規約」）。

- 種類ごとの確保と頭: 各 `ObjKind`（`Fields` は各 `FieldsKind`）の対象を確保し、頭から読んだ種類・長さ・`tag` が確保したときの値と一致する。長さ 0 の値の並び、長さ 0 の文字列も含める。
- 大きさの区分の境目: 区分の上限ちょうど、上限より 1 大きい大きさ、大きな対象の境目の前後で確保し、読み書きした中身が壊れない。
- 解放と再利用: 確保・解放を繰り返したとき、空きの並びから領域が再利用され、`allocations`・`frees`・`allocated_bytes` の前後の差が、確保と解放の回数とちょうど一致する。
- ヒープの番号: 同時に作った二つのヒープの番号が違う。ヒープを捨てて作り直したとき、新しいヒープの番号が、捨てたヒープの番号と違う（番地が同じになっても）。
- 毒（`heap-verify`）: 解放した対象の中身の領域（塊の構成）が `POISON_BYTE` で埋まり、頭の世代が進む。`#[cfg(feature = "heap-verify")]` で限る（理由をコメントに書く）。
- 対象ごとの確保（`heap-per-object`）: 確保と解放を繰り返しても、内部の表の世代と生死が確保の状態と一致する。`#[cfg(feature = "heap-per-object")]` で限る。
- 列挙: 確保した対象と解放した対象を混ぜた後、列挙の結果が、生きている対象の集合と一致する（テストが別に持つ `BTreeSet` と比べる）。
- `Opaque`・`Host` の中身の `drop`: `drop` を数える Rust の値を入れた対象を解放すると、`drop` が一度だけ呼ばれる。
- 大量の確保: 100 万個の小さな対象と、大きさの違う対象を混ぜて確保・解放しても、壊れない（Miri では `cfg!(miri)` で 1,000 個程度に減らし、大きな規模の確かめは通常の実行に残す）。
- 数値の溢れ: 大きさの計算が溢れる大きさ（`u32::MAX` に近い長さ）の確保が、溢れを検査して失敗として扱われる（panic や未定義動作にならない）。

これらのテストは、`scripts/check-heap.sh` の Miri の実行（00-02「完了条件の共通の検査」）でも通る。

## 完了条件

- `scripts/check.sh` と `scripts/check-heap.sh` が通る（00-02「完了条件の共通の検査」）
- 受け入れテストのすべての場合を確かめるテストがある
- `unsafe` が `src/runtime/heap/core.rs` とその子のモジュールの中だけにある
- すべての `unsafe` のブロックが一つの操作だけを含み、`// SAFETY:` のコメントが不変条件の番号を引いている
- 完了の報告の「`unsafe`」の欄に、`unsafe` のブロックの数と、それぞれが引く不変条件を挙げている

## 確認の観点

[実装の確認の観点](../00-common/00-04-review-checklist.md)の「ヒープの内部の層（R01〜R04、R06）」に加えて、次の点を読む。

- `// SAFETY:` のコメントが引く不変条件が、そのブロックの直前までのコードで実際に成り立つか（コメントの形でなく中身を読む）。Codex にも同じ観点で読ませる（00-03「確認と取り込み」の 3）。
- 塊の中のポインタの計算に、確保した範囲の外を指す場合がないか。長さの欄を信じて読む箇所で、その長さが確保の時点の値から変わりうる経路がないか。
- `heap-per-object` の構成で、解放した領域を読む経路（世代の確かめ、列挙）がないか。
- ヒープの番号の計数器（ADR 0281 が認めた例外）のほかに、大域の可変状態を持っていないか。計数器が番地から番号を作っていないか。
- 解放の関数が、区間の中から呼べる形になっていないか（H1）。

## 難易度の理由

生のポインタで対象を配置し、確保と解放を自分で管理する。誤りは未定義動作になり、テストでは偶然通ることがある。`unsafe` の一つ一つについて、どの不変条件に頼るかを言葉で示し、それを Miri と毒と世代で確かめる流れを最初に作る作業であり、後の作業の `unsafe` の書き方の手本にもなる。
