# R16 生存の情報の処理を回収の安全点へ移す

- 依存する作業: [R15](R15-vm-dispatch-performance.md)
- 難易度: 4（1〜5。README の「作業一覧」）
- 規模の見込み: 中（300〜900 行の変更。`src/bytecode/liveness.rs` と `src/vm/dispatch.rs` が中心）
- ブランチ: impl/R16-liveness-at-safepoints

## 目的

VM が命令ごとに行う、最後の使用のレジスタの `take` と使わなくなったレジスタの `clear`（10-07「生存の情報」）をやめ、回収の安全点で、各枠の生きているレジスタの集合に含まれないレジスタをまとめて `Unit` にする形に移す（[ADR 0314](../../design/decisions/0314-clear-dead-registers-at-safepoints.md)）。R15 の後の本測定（[記録](../../../tools/bench/results/2026-10-05-r15-cc96baa.md)）で、VM は最小実行版の VM に fib で 1.32 倍、loop で 1.74 倍届かず、命令ごとの生存の情報の処理が fib で 21%、loop で 31% を占めた（[ADR 0313](../../design/decisions/0313-vm-performance-recovery-before-stage-2.md) の決定 4・5。設計者が起動を承認した）。

振る舞いは変えない。回収の時点で生きている値の集合は、命令ごとに消していたときと同じか、それより小さくする（ADR 0314 の帰結）。

次のことは本作業の範囲に入れない。

- 第 2 段の根（捕まえた継続、待つタスク、枠を降ろす途中の区画）。第 1 段の VM にはない。R20〜R25 が ADR 0314 の決定 5 に従って扱う。
- 命令ごとの項目（`LastUse`・`Dead`）の計算の変更と削除。項目は残し、VM が読まなくなるだけである（ADR 0314 の決定 4）。
- 窓を重ねる形（OPEN-063）、範囲の確かめの省略（OPEN-064）、値の大きさ（OPEN-065）、`unsafe` の追加。
- R15 の形（局所の状態、引数の直接の写し、インライン化）を崩す変更。

## 相談で指摘された条件

GPT-6.1-Sol への相談（[相談の第 8 回](../studies/u2-runtime/consult/08-vm-performance.md)の回答の 1）で、安全点へ移すときの正しさの条件として、次のものが挙げられた。[ADR 0314](../../design/decisions/0314-clear-dead-registers-at-safepoints.md) は、これらを次のように扱う。1 は決定 3・4（命令ごとの live_in）、2 は決定 6、3 は決定 3（呼び出しの途中の枠では結果のレジスタを除く）、4 は決定 3（完了を待つ枠は live_in(pc) で引数を含む）、5 は決定 5（第 2 段の作業が自分の根に当てる）、6 は決定 2（`Unit` にする）、7 は決定 7、8 は本文書の「性能の確かめ方」。

1. 今の生存の情報は、前の命令が `Dead`・`LastUse` のレジスタを消したことを前提にした差分である（`bytecode::liveness` の生成）。命令ごとに消すのをやめると、以前に死んだ値は今の命令の `Dead` に現れず、残り続ける。安全点ごとの生きているレジスタの集合（かその補集合）を、別に作る必要がある。
2. `LastUse` は所有の唯一性を意味しない。マーク・スイープでは読み出しを `load` に変えてよいが、得た `Value<'epoch>` は区間の中だけで使い、回収をまたぐ引数・結果・一時的な値はレジスタ・枠・根の保存領域に置く。
3. 根は命令の位置だけでは決まらない。呼び出しの前は関数と引数が要り、呼び出しが成立した後の呼び出し元の枠は、呼び出しをまたいで使う値だけが要る。結果を入れるレジスタは、書かれるまで古い値を根から外せる。「次の命令の生きている集合」をそのまま使うと、結果として読む予定のレジスタの古い値を余分に保持する。入口・呼び出しの途中・完了待ちを区別して定める。
4. 組み込みの関数の完了を待つ間は、引数を追加の根として残す。今の規約も、待ちうる `IO`・`PRIM` の引数に `LastUse` を付けない（10-07）。完了の処理が読み直す引数を、命令の実行後の集合だけで消さない。組み込みの関数の区間の中では回収せず、待ちへ移る前に保存を終える。
5. 捕まえた継続、止まっているタスク、枠を降ろす途中の区画も対象である。実行中の窓だけを片付けても足りない。継続には再開に要る値を、後始末には枠が使う値を残す。`RETURN`・`ESCAPE` の値は、窓を消す前に戻りの再開状態へ移す。区画を移す途中に回収や失敗を挟まない規約も保つ。
6. 根から除くだけで `Unit` にしない案では、回収した対象を指す古い `Slot` が残る。その後の読み出し・再走査・上書き・破棄が古い対象に触れない契約まで要る。ヒープの番号（ADR 0281）は、同じヒープの中の回収済みの参照を防がない。今の `Segment::trace` はすべてのレジスタを辿るので、回収の前に死んだ値を `Unit` にする形のほうが、継続を含む既存の `Trace` と合わせやすい。
7. `Lazy`・`Reference` の更新の API は保つ。止めて行う今のマーク・スイープでは、命令ごとに消すのを遅らせるために新しい書き込みの障壁は要らない。ただし、セル・`Lazy`・タスクの結果・継続の状態を更新する箇所を散らすと、将来の世代別の回収や増分の回収に要る障壁を入れにくくなる（ADR 0259 の決定 7）。
8. 費用を安全点へ移した結果は、fib・loop だけでなく、確保の多い負荷（list・tree・live・roots）でも測る。回収の回数と停止の時間が増えないことを確かめる。

条件 3〜5 のうち継続と待ちに関わる部分は、第 1 段の VM には現れない。本作業は第 1 段の VM の根（実行中のタスクの区画）だけを扱い、第 2 段の作業（R20〜R25）が ADR 0314 の決定 5 に従って自分の根に当てる。

## 作るもの

- `src/bytecode/liveness.rs`: 10-07 の `file=src/bytecode/liveness.rs` のコードのとおりに、`LiveInfo` に命令ごとの入口の生きているレジスタ（`live_in_starts`・`live_in`）と、呼び出しの命令の結果のレジスタ（`call_writes`）の欄を加え、引く関数 `live_in_at`・`call_write` を書く。`compute_liveness` がこれらを埋める。入口の生きている集合は、今の計算が求めている `live_in` をそのまま使う。命令ごとの項目（`starts`・`items`）の計算は変えない。
- `src/vm/dispatch.rs`（と子のモジュール）: 命令の処理から生存の情報の処理をなくす（手順 2）。回収へ出る前に枠のレジスタを空にする関数を加える（手順 3）。
- テスト: `src/bytecode/liveness.rs` のテスト（入口の集合と結果のレジスタ）と、`src/vm/tests.rs` の回収の精度と安全性のテスト（後述の「受け入れテスト」）。

凍結したコードの扱いは次のとおりとする。

- 10-07 の `file=src/bytecode/liveness.rs` のコードは、オーケストレータが ADR 0314 に合わせて改めた。本作業はそのとおりに書く。ほかの `file=`・`sig=` のコード（`Proto`・`CompiledProgram`・`LoopLocals`・`CallFrame`・`Segment`・`NoGcCtx` など）は変えない。
- R15 が凍結したファイルに加えた `#[inline]` の属性の扱い（00-03 の R15 の例外）は、本作業でも同じ範囲で認める（`LiveInfo::live_in_at`・`call_write` に付けてよい）。

## 手順の要点

1. **生存の情報の拡張**: `compute_liveness` が、命令ごとの `live_in`（昇順のレジスタの並び）と、呼び出しの命令（`CALL`・`METHOD`・`HANDLE`・`FORCE`・`UPDATE`・`PERFORM`・`IO`・`RESUME`。10-07「生存の情報」）の結果のレジスタ（`reg_use` の `write`）を埋める。`TAILCALL`・`TAILMETHOD`・`ESCAPE`・`RETURN` は再開しないので、呼び出しの命令に含めない。テスト用のバイトコードの組み立て（`asm.rs`）とコード生成は `compute_liveness` を呼ぶだけなので、変えなくてよい。読み込みのときの検証器が `LiveInfo` の形を確かめているなら、新しい欄の長さ（命令の数に 1 を足した数、または命令の数）も確かめる。
2. **命令ごとの処理をなくす**: 振り分けのループと命令の処理から、`proto.live.at(pc)` を引く処理、`Dead` の `clear`、`LastUse` の `take`・`move_slot` をなくし、被演算子はすべて `NoGcCtx::load` で読む。局所の状態の補助の型が生存の情報への参照を持つ必要もなくなる。`CONR` は、前の値の形の確かめ（10-07「その場での再利用の命令」の手順 2。`conr_matches_con_and_rejects_invalid_candidates` が確かめる）を残し、前の値を `take` でなく `load` で読み、`reuse_ctor` を呼ばずに新しい対象を作り、引数のレジスタを `clear` しない（マーク・スイープの `reuse_ctor` はつねに `None` なので、振る舞いは変わらない。10-07 の同節を改めた）。`TAILCALL`・`TAILMETHOD` で窓を片付ける処理、`RETURN` で窓を `clear` する処理（窓の外になったレジスタ）は残す。普通の呼び出しで引数を写した後に元のレジスタを `take` する処理はなくす（元のレジスタは、回収のときに呼び出しの途中の枠の規則で空になる）。
3. **回収の前に空にする**: VM が回収のために区間を閉じる前（`LoopExit::Collect` を返す前。呼び出しの前の安全点、戻りの後、止める手順の途中のすべて。どれも `run_epoch` が `LoopExit::Collect` を返す一か所に集まるので、そこで行う。`cleanup` は `program` を受け取らないが、`run_epoch` は持っている）に、`state.stack` のすべての区画の、すべての呼び出しの枠について、ADR 0314 の決定 3 の集合に含まれない窓のレジスタを `NoGcCtx::clear` で空にする。
   - 最も上の区画の、最も上の呼び出しの枠（タスクの最も内側の枠）は live_in(pc)。
   - ほかの枠は、`call_write(pc − 1)` が `Some(dest)` なら live_in(pc) から dest を除いた集合。`None`（呼び出しの命令でない）か pc が 0 なら、その枠は空にしない。`heap-verify` の構成では、その場合を `Stop::Internal` にする（第 1 段の VM では起きない）。
   - 窓は、枠の `base` と `size` で決まる範囲とする。区画の `regs` のうち、どの窓にも入らないレジスタは、今の規則（窓の外は `Unit`）のまま触れない。
   - live_in は昇順なので、窓のレジスタを先頭から走査し、live_in と突き合わせて空にする（レジスタの数に比例する手間）。命令の位置が原型の命令の数を超えるなど、生存の情報を引けないときは、その枠を空にしない（`heap-verify` の構成では `Stop::Internal`）。
   - `live_in_at` の `None`（引けない）と `Some(&[])`（生きているレジスタがない）を取り違えない。前者は窓をすべて残し、後者は窓をすべて空にする。
   - `live_in` と `call_write` のレジスタの番号は原型の中の相対の番号（窓の先頭からの位置）であり、`CallFrame::ret` は区画の中の位置である。結果のレジスタを除くときに、窓の先頭を二重に足さない。
   - 昇順であることと番号が窓の大きさの中にあることを、空にし始める前に確かめる。外れたら、その枠を空にしない（`heap-verify` の構成では `Stop::Internal`）。読み込みのときの検証器は仮置きなので、検証器が新しい欄を確かめることを前提にしない。
4. **区間の中の値**: 手順 2 で `take` を `load` に変えた箇所で、読んだ `Value<'epoch>` を回収をまたいで使っていないかを確かめる（10-08 の不変条件 H4）。呼び出しの前の安全点の手順（10-09）は、関数の値と引数をレジスタに残したまま回収するので、変えない。
5. **テストの見直し**: 命令ごとに消すことを前提にしたテスト（命令の実行の直後にレジスタが `Unit` であることを確かめるテストなど）があれば、回収の後の状態を確かめる形に直し、直したテストと理由を報告する。生存の情報の項目そのもののテスト（R05）の期待は変えない。ただし、`LiveInfo` の構造体のリテラル（`liveness.rs` のテスト）に新しい欄を足すのはよい（空の原型では `live_in_starts` は `[0]`、`live_in` と `call_writes` は空。10-07）。`roots_constants_and_waiting_arguments_survive_collection`（`vm/tests.rs`）のコメント「動的な文字列は待つ IO の引数だけが持つ」は、命令ごとに消さなくなると成り立たなくなる（ほかのレジスタにも値が残る）。テストの意図（待つ IO の引数だけが値を持つ状態で回収しても残ること）を保つように直すか、直さない理由を報告する。

## 受け入れテスト

- 振る舞い: 既存のテスト（VM、R11 のヒープの確かめ、ゴールデンテスト、参照インタプリタとの差分）が通る。`scripts/check.sh` の `gc-stress` の構成でも通る。`tests/call_allocations.rs` が通る（普通の呼び出しと戻りに確保を足さない）。
- 生存の情報: 分岐と後ろ向きの跳躍を含む原型で、`live_in_at` が流れの解析の入口の集合と一致すること、呼び出しの命令で `call_write` が結果のレジスタ、それ以外で `None` であることを、`asm.rs` で組み立てた原型で確かめる。
- 回収の精度（`bytecode::asm` で組み立て、ヒープに残る対象を `Heap::object_ids` で数える）: 回収は、`HeapConfig::stress` の設定で `run_stage1` の中で起きる回収を使う（要求と応答の方式で `IO` の要求のところで止め、その時点のヒープを確かめるなど）。R09・R11 の既存のテストは `vm.heap.collect(&vm.state)` を直接呼んでおり、その経路では空にする処理が走らないので、そのまま真似ない。テストの側で `heap.collect` を直接呼ぶなら、先に空にする関数（VM のテストから呼べる `pub(super)` などにしてよい）を呼ぶ。
  - 最も内側の枠: 大きなヒープの値を最後に使った後、同じ枠が呼び出しの前の安全点で回収すると、その値が回収されている。
  - 呼び出しの途中の枠: 呼び出し元が、呼び出しの後に使わない引数のヒープの値と、結果のレジスタの古いヒープの値を持ったまま呼び、呼ばれた側の中で回収すると、どちらも（呼ばれた側が持っていなければ）回収されている（`x = f(x)` の形）。
- 生存の情報の期待する集合は、テストの中で手で書く。`compute_liveness` の結果から期待値を作らない。
- 回収の安全性:
  - 呼び出しをまたいで使う値が、呼ばれた側の中の回収の後も正しく読める（既存のテストで足りれば加えない）。
  - 連続する呼び出し: 前の `CALL` の結果を次の `CALL` の引数に使い、次の呼び出しの前の安全点で回収しても、引数が残る（最も内側の枠に結果のレジスタを除く規則を当てる誤りを捕まえる）。
  - 回収の後の上書き: 回収で空にしたレジスタに、後で新しい値を書いても正しく動く（`heap-verify` の構成で、回収済みの対象に触れない）。
  - 止める手順の途中の回収（実行時エラーで枠を降ろしながら回収する場合）で、正しく止まる。
  - 呼び出しの前の安全点で回収した直後（`call_budget` を 1 にし、回収を強制する）に、関数の値と引数が残っていて、呼び出しが正しく成立する。
  - 戻りの後の回収で、結果のレジスタの値が残る。
  - 末尾呼び出しと深い再帰（上限で `CallStackTooDeep`、100 万回の末尾再帰）が今のとおり動く。

### 性能の確かめ方

R15 と同じく分担する。

- 実装担当: release のビルドで、作業を始めたときの `san_benito` の HEAD と本作業の版を、fib(30)・loop 300 万回で交互に数回走らせ、最小の時間を比べる（R15 の「性能の確かめ方」の手順。比較の版はリポジトリの外に `git archive` で展開してよい）。あわせて、確保の多い負荷（`tools/bench/programs/stage1/` の live・roots と、list・tree）で、回収の回数と停止の時間（`stage1_bench` の出力の `collections`・`pause_nanos`）と最大のヒープの量を比べる。`pause_nanos` はヒープの `collect` の中だけを測り、本作業が加える回収の前の整理を含まないので、整理の時間を別に測る（測定用の写しに計時を足してよい。本番のコードに計時を残さない）。深い再帰の中で確保して回収が繰り返される負荷（深さと窓の大きさと回収の頻度を変える。入力の小さな `.bnt` を作業ツリーの外に作ってよい）でも、整理と回収を合わせた時間を比べる。生きている量が減ると回収の閾値も下がるので、回収の回数が増えたことだけを失敗とはみなさない。
- 実装担当: 生存の情報の大きさ（`live_in` の要素の数と、`Proto` ごとの最大）を、標準ライブラリとゴールデンテストの最大のプログラムについて報告する。
- オーケストレータ: 取り込みの前に、ほかの作業を止めて `tools/bench/gate.py` で関門を測り（最小実行版の VM を同じ機会に測り直す）、確保の多い負荷を `tools/bench/stage1.py --measure` で測る。記録を `tools/bench/results/<日付>-r16-<コミット>.md` に残す。

### 目標に届かなかった場合

R15 と同じく、範囲の外の手（値の表現、範囲の確かめの省略など）に進まず、届かなかった値と、残りの費用の内訳（R15 の手順 10 と同じ方法）を報告して止まる。範囲の中の変更が正しく速くなっていれば、作業は完了として取り込む。

- 完了の報告に、短い測定の値（fib・loop と確保の多い負荷の回収の回数と停止の時間）と、残りの費用の内訳を書いている

## 確認の観点

[実装の確認の観点](../00-common/00-04-review-checklist.md)の「すべての作業で読む観点」に加えて、次の点を読む。

- 空にする集合が ADR 0314 の決定 3 のとおりか。最も内側の枠とそれ以外の枠を取り違えていないか（呼び出しの前の安全点で止まった最も内側の枠に、結果のレジスタを除く規則を当てると、命令 pc − 1 の結果を消してしまう）。
- 回収へ出るすべての経路（呼び出しの前の安全点、戻りの後、止める手順の途中）で、区間を閉じる前に空にしているか。
- live_in が、流れの解析の入口の集合（書かれる前に読まれうるレジスタ）になっているか。跳躍の先と分岐の合流で欠けていないか。
- `take` を `load` に変えた箇所で、読んだ値を回収をまたいで使っていないか。
- 窓の外のレジスタ、包む枠の `Slot`、根の保存領域に触れていないか。
- R15 の局所の状態と、普通の呼び出しと戻りの確保なしの性質を崩していないか。

## 難易度の理由

規則は一つの関数に集まるが、空にしてよいレジスタを一つでも誤ると、回収の強制の下でだけ現れる誤り（回収済みの値を読む）になる。最も内側の枠と呼び出しの途中の枠の区別、命令の位置の慣例（呼び出し元の枠の位置が呼び出しの次を指すこと）に依存する。
