## 目的

初回リリース版のパターンの拡張（選択肢、ガード、範囲、リストのパターン）の型付けと、本体の後のパターンの検査（網羅性、選ばれない分岐と選択肢、束縛の文の必ず照合するパターン）を書く。パターンの検査は、[10-05](../10-interfaces/10-05-types.md) の `src/typeck/patterns.rs` の `check_match` と `is_irrefutable` で、型検査を終えた型とタグで表したパターンの上で行う。

本作業は、F07 が置いたフック P1〜P5 の中身と、`patterns.rs` の関数を書く。F08・F09 と並行して進める（F07 の文書の「F07〜F10 の分け方」）。基本のパターン（ワイルドカード、変数、リテラル、`()`、構成子、レコード）の型付けと、分岐の各選択肢を対象の型と等しくすることは F07 が書いた。選択肢で束縛する名前の違い（E0604）と、パターンの変数と定数の名前の重なり（E0603）は、名前解決（F06）が報告済みである。

## 手順の要点

### 範囲とリストのパターン（P1）

- 範囲のパターン `lo..hi`: 両端（`RangeEnd`）が同じ種類のリテラル（`Integer` のリテラルと負の数、または `Character` のリテラル）でなければ E0606。整数の端は F07 の整数リテラルと同じ規則で範囲を検査し（`negative` なら符号を含めて判定する。範囲の外は E0408）、下端が上端より大きければ E0605。型は端の型（`Integer` か `Character`）。誤りがなければ `range_bounds` に `(ConstValue, ConstValue)` を記録する。
- リストのパターン `[p1, ..rest, pn]`: 型は `List[α]`（α は新しい変数）。`before` と `after` の各要素のパターンの型を α と等しくする（理由 `Pattern`）。`ListRest` の名前があれば、その束縛の型を `List[α]` とし、`expr_types` に `ListRest` のノード番号で `List[α]` を記録する。名前がなくても `ListRest` のノード番号で記録してよい。`..` が二つ以上あるパターンは構文解析器が E0250 で報告済みである。
- パターンの中の子のパターンを辿るのは、F07 のパターンの生成の関数で行う。

### 選択肢（P2）

一つの分岐の選択肢のパターンは、名前解決で、最初の選択肢の `VarPat` が束縛を宣言し、ほかの選択肢の同じ名前の `VarPat` は参照の表でその束縛を指す（10-04「名前解決の表」の最後の段落）。P2 は、二つ目以降の選択肢の `VarPat` ごとに、そのノードの型と、参照の表が指す束縛の型を等しくする。解けなければ E0401 とし、鍵 `because_alternatives` の注記を付ける（01-05「パターンの拡張（初回リリース版）」の「すべての選択肢は、同じ名前の変数を同じ型で束縛しなければならない」）。等しくする制約は、`Body::unify` ですぐ単一化せず、`Body::add(Constraint::Equal { …, reason })`（`reason` の種類は `ReasonKind::Alternatives`）で加えて遅らせる。すぐ単一化すると、対象とパターンを等しくする制約（理由 `Pattern`）より先に解かれ、対象の型の誤りに `because_pattern` でなく選択肢の注記が付くことがあるためである。名前のある残りのパターン（`..rest`、`ListRest`）も、二つ目以降の選択肢では参照の表で最初の束縛を指す（10-04）ので、`VarPat` と同じく扱う。`ReasonKind::Alternatives` と、`solve.rs` の注記の鍵の対応は、オーケストレータが前もって加えてある。

### ガード（P3・P5）

- P3: ガードを、E を空集合、R を「なし」として辿る（02-05「制約の生成」の `match` の行）。本プランの決定: F09 の `lazy` の本体と同じ形で書く。新しいエフェクトの変数 ε（`ctx.fresh_effect()`）を作り、`ctx.expr_in(g, ε, None)` でガードを辿り、`Constraint::EffSub { sub: ε, sup: fixed(EffectSet::empty()), reason }`（`reason` は `context::reason(ガードの式の span, ReasonKind::MatchGuard)`）を加える。`fixed(EffectSet::empty())` を直接渡して辿ると、ガードの中の呼び出しが加える含まれる制約の理由が `CallEffect` になり、`solve.rs` が E0504 でなく E0501 を出す（P5 に回るのは、理由が `MatchGuard` で、上限が変数を持たない含まれる制約だけである）。ε を挟めば、呼び出しの制約は上限が変数なので報告されず、ε に集まったエフェクトを `MatchGuard` の制約が報告し、ε が記録した呼び出しの位置が主な位置になる。あわせて等しい(ガードの型, `Boolean`)（理由 `MatchGuard`）を加える。解けなければ E0401 に鍵 `because_condition` の注記が付く（`solve.rs` の対応はオーケストレータが前もって加えてある）。ガードの中の `return`・`try` は構文解析器が E0218 で報告済みである。
- P5: 理由が `MatchGuard` の含まれる制約が解けなかったとき、E0504 とし、そのエフェクトを生じた呼び出しを主な位置、本体の中で条件を調べる修正案（鍵 `body`）を示す。

### 本体の後のパターンの検査（P4）

F07 の本体の文脈が記録した `match` と束縛の文を、次の順に調べる。

1. 対象の型を `finalize` する前に誤りの型を含むか（`solver.contains_error`）調べ、含めば飛ばす（02-05「誤りの報告と検査の継続」）。`finalize` は誤りの型を `Unit` に変えるので、`finalize` の後では調べられない。分岐のパターンのどれかで誤り（E0408・E0412・E0413・E0429・E0430・E0605・E0606 など、パターンの型付けの誤り）を報告した `match` も飛ばす。パターンの誤りは、パターンのノードごとに次の手がかりで判定する。
   - E0412・E0413: F07 のパターンの生成が、構成子のパターンのノードの型に誤りの型を記録している（`record_type(p.id(), ITy::Error)`）。P4 は `finish` の前に呼ばれるので、本体の文脈の `expr_types`（`finalize` する前の `ITy`）で調べる。
   - E0408（と浮動小数・`Decimal` のリテラルの E0409・E0420・E0421）: リテラルのパターンのノードについて、`lit_values` に値がない。
   - E0429・E0430: `records::pattern` は型を誤りの型にしない。レコードのパターンのフィールドの名前を `AdtTable` の `record` のフィールドと照らし、宣言にない名前があれば E0429、同じ名前が二度現れれば E0430 として判定する。
   - E0605・E0606（と端の E0408）: P1 が、誤りを報告した範囲のパターンについて `range_bounds` を記録しない。`range_bounds` に値がない範囲のパターンを誤りとみなす。
2. AST のパターンを `Pat` に移す（10-05「パターンの検査（F10 の境界）」の箇条）。変数のパターンと `..rest` の変数は `Wild`。構成子のパターンは、参照の表の束縛（`BindingKind::Ctor { data, tag }`）から `Pat::Ctor { adt: data, tag, args }`。レコードのパターンは、フィールドを宣言の順に並べた `Ctor`（タグ 0）にし、書かないフィールドは `Wild`。リテラルの `negative` は負の値にする。範囲は `range_bounds` の値で `IntegerRange`・`CharacterRange`。リストは `List { before, rest, after }`。
3. `match` は、分岐ごとに選択肢の並びとガードの有無から `ArmPats` を作り、`check_match` を呼ぶ。結果を次のように診断にする。
   - `Unreachable { arm, alt, covered_by }`: 本プランの決定: 選択肢が一つの分岐は E0602（主な位置はそのパターン）とする。選択肢が二つ以上の分岐は、選ばれない選択肢ごとに E0608（主な位置はその選択肢のパターン）とする。ただし、その分岐のすべての選択肢が選ばれないときは、分岐として E0602 を一つだけ出し、主な位置を分岐のパターン全体（最初の選択肢の始まりから最後の選択肢の終わりまで）にする。補助の位置（鍵 `covering`）には、覆っている前の選択肢のパターンの span を並べる。`covered_by` は分岐の番号だけを持ち、どの選択肢が覆うかと、同じ分岐の前の選択肢が覆うこと（`case 1, 1 ->`）を表せないので、P4 は覆う選択肢を求め直す。そのために、`patterns.rs` に、02-05 の選び方を選択肢の単位で行い、覆う選択肢の（分岐, 選択肢）の並びを返す補助の関数（10-05 の `sig=` の外。`pub(super)` でよい）を足してよい。`check_match` の `covered_by` は、その並びの分岐の番号から自分の分岐を除き、重なりを除いて昇順にしたものとする。分岐として一つの E0602 にまとめるときは、各選択肢の覆う選択肢を重なりを除いて並べる。
   - `NonExhaustive { witness }`: E0601。主な位置は `match` の対象の式、`witness` を埋め、分岐を加える修正案（鍵 `add_arm`）を示す。
4. 束縛の文（左辺が変数と `_` 以外のパターン）は、`is_irrefutable` が偽なら E0607 とし、`match` で分岐する修正案（鍵 `match`）を示す（01-05「必ず照合するパターン（初回リリース版）」）。型板の `{witness}` は、`is_irrefutable` が真偽値しか返さないので、左辺のパターン一つの分岐（ガードなし）で `check_match` を呼び、`NonExhaustive` の `witness` から得る。`{ty}` は、対象の型を `solver.finalize` で `Ty` にし、`Ty::show`（`TyNames` は `solve.rs` の `show` と同じく本体の文脈から作る）で文字列にする。

### 有用性の判定（`patterns.rs`）

02-05「本体の後の検査」の方法で書く。

- 行列の行は選択肢ごとに一つ。ガードの付いた分岐の行は、後の行を覆うものに数えないので行列に加えない。ガードの付いた分岐自身の選択肢も、判定の対象にする。
- 選ばれない選択肢の判定と `covered_by` の選び方は、02-05 の同節の最初の箇条のとおり（pj 一つで覆う最初の j があれば pj だけ、なければ p1〜pk の行列で覆う最小の k を求め、そのうち pi と重なる分岐をすべて）。重なりの定め（ワイルドカードと変数、構成子、リテラルと `()`、範囲の交わり、リストの長さと要素）も同箇条のとおり。
- 型ごとの構成子の集まりは、02-05 の「判定では、型ごとの構成子の集まりを次のように扱う」の箇条のとおり。`Integer`・`Character` は、列に現れる区間の端で値の範囲を互いに交わらない区間に分けて構成子のように扱い、どのリテラルと範囲にも照合しない値が一つあるものとして扱う（範囲をどう並べても網羅しない）。`List[T]` は長さの構成子（ちょうど k と、m 以上）。値を作れない型（`data L Mk(L)`）も、構成子で作った値があるものとして扱う。
- 型の構成子の数とタグ、引数の型は `AdtTable`（`field_types`）から得る。行列の再帰は、利用者のプログラムの入れ子の深さ（構文解析器が上限を設ける）とパターンの数に比例するので、Rust の再帰で書いてよい（00-02「再帰の深さ」）。
- 反例（`witness`）の表示の形（本プランの決定）: 構成子は型名で修飾した名前（`Tree.Node(Tree.Leaf, _, _)`、`Option.None`）とし、型の名前と同じ名前の構成子（`Pair`）とレコードは修飾しない（レコードは `Person(name: _, age: _)` の形）。`Boolean` は `true`・`false`、`Unit` は `()`、ほかの値（`Integer`・`Character`・`String` などの残りの値）は `_`。リストは、長さがちょうど k の構成子を k 個の要素の反例を並べた形（すべて `_` なら `[_, _]`。k が 0 なら `[]`）とする。長さが m 以上の構成子（a・p・s・m は 02-05「本体の後の検査」の `List[T]` の項の定義）は、前に max(p, m − s) 個、後に s 個の要素を並べ、間に `..` を置く。前の max(p, m − s) 個は、構成子の前の p 個の引数の反例の後に、max(p, m − s) − p 個の `_` を足したものである。m が 0 なら `[..]` とする。前の要素を p 個にすると、示す形が長さ p + s 以上のリストに照合し、m > p + s のとき m より短い、分岐に照合するリストまで含んでしまう（`[]` と `[x]` の分岐では a = 1、p = s = 0、m = 2 で、反例は `[..]` ではなく `[_, _, ..]`）。
- `is_irrefutable(ty, pat)` は、`pat` 一つの行列に対してワイルドカードが有用でないとき真である。

### 型検査の再帰の深さ（F07 の共有の処理）

00-02「再帰の深さ」は、処理系のテストに深い入れ子を含め、スレッドのスタックの大きさを変えずに通すことを求める。取り込み済みの F07 の型検査（`typeck/generate.rs` の式・パターン・ブロックを辿る関数と、そこから呼ぶ `records.rs`・`decls.rs`・`solve.rs` などの再帰）は、1 段あたりのスタックの使用量が大きく、既定のテストのスレッド（2 MiB）で、二項演算の入れ子が 200 段前後、構成子のパターンの入れ子が 900 段で溢れる。本作業は、F07〜F10 が分岐を加え終えた最後の作業なので、次の限られた変更に限って `src/typeck/` の共有のファイルを直してよい（本プランの決定）。

- 振る舞い（型、診断、出力の表）を変えずに、1 段あたりのスタックの使用量を減らす。大きな `match` の分岐の本体を `#[inline(never)]` を付けた非公開の関数に分ける、大きな値を再帰の枠に置かない、などで行う（F03 が構文解析器で行ったのと同じ方法）。再帰を明示の積み重ねに書き換えることまでは求めない（AST を辿る処理は再帰で書いてよい。00-02）。
- 構文解析の入れ子の上限（1000）の内側の深さで、式（二項演算、括弧、ラムダ、`if`、`match`）とパターン（構成子、リスト）の深い入れ子を、既定のテストのスレッドのまま型検査できることを確かめるテストを加える。リリースビルドの関数の展開で溢れないよう、分けた関数には `#[inline(never)]` を付ける。
- F07〜F09 の既存のテストの結果を変えない。直したファイルと関数は、完了の報告の「判断したこと」に挙げる。

## 受け入れテスト

テストは F07 の `typeck::test_support` で検査し、診断をコードと主な位置で確かめる。`check_match` と `is_irrefutable` は、`Pat` と `Ty` を手で組んだ単体テストでも確かめる。

| 場合 | 入力の要点 | 期待する結果 |
|---|---|---|
| 01-05 の拡張の例 | `command` のリストのパターンと選択肢、`score` のガードと範囲 | 診断なし。`range_bounds` に `90..100` などの値、`..rest` の `expr_types` が `List[String]` |
| 網羅性 | 01-05 の `Tree` の `match` で `Tree.Leaf` だけ | E0601、反例 `Tree.Node(_, _, _)` の形 |
| リストの網羅 | `[]` と `[_, ..]` の二つの分岐 | 診断なし。`[]` と `[x]` だけなら E0601 と反例 `[_, _, ..]` の形 |
| 範囲は網羅しない | `Integer` の `match` を `0..9` と `10..100` と負の範囲で並べる | E0601（反例 `_`） |
| 選ばれない分岐 | 01-05「選ばれない分岐の検査」の二つの例 | 前者は E0602（補助の位置は最初の分岐）、後者（ガード付きの前の分岐）は診断なし |
| 選ばれない選択肢 | `case 1, 1 ->` | E0608（主な位置は 2 番目の `1`、補助の位置は 1 番目） |
| 範囲の重なり | `case 1..10 ->` の後の `case 5 ->` | E0602（補助の位置は範囲の分岐） |
| 範囲の誤り | `case 5..1 ->`、`case 1..'z' ->` | E0605、E0606 |
| ガード | `case n if n < 0 -> …` のガードが `Integer` を返す式。テストの中で宣言した `function ready() -> Boolean uses Console.Write`（本体で `Console.writeLine` を呼んで `true` を返す）を、ガードで呼ぶ `case n if ready() -> …` | 前者は E0401（理由のガード）。後者は E0504 だけ（主な位置は `ready()` の呼び出し）と修正案で、E0401 も E0501 も出さない |
| ガードの付いた選ばれない分岐 | `case _ -> …` の後の `case x if x > 0 -> …` | E0602 |
| 選択肢の型 | 選択肢が同じ名前の変数を違う型で束縛する（`case Option.Some(x), x -> …` に当たる形） | E0401（鍵 `because_alternatives`） |
| 必ず照合するパターン | 01-05「必ず照合するパターン（初回リリース版）」の三つの例、`bind [..rest] <- xs`、`bind [x] <- xs` | 1・2 番目と `[..rest]` は診断なし、3 番目と `[x]` は E0607 と修正案 |
| 値を作れない型 | `data L Mk(L) end data` 相当と `case L.Mk(_) ->` | 診断なし |
| 誤りの型を含む対象 | `match Option.None() with case Option.Some(_) -> … end match`（引数のない構成子に `()` を付けた式は、F07 が E0413 を報告して型を誤りの型にする） | E0413 だけで、E0601 を出さない |
| 手で組んだ行列 | `check_match` に `Boolean`・`Unit`・`Option`・区間・リストの長さの組み合わせ | 網羅と選ばれない選択肢の判定、`covered_by` の選び方が 02-05 のとおり |
| 深い入れ子 | 入れ子の深い構成子のパターン（構文解析器の上限の程度） | スタックが溢れない |

ゴールデンテスト: 上の表の診断なしの例（リストの網羅、ガード付きの分岐、必ず照合するパターンの例）を、`testdata-next/patterns/` に `check` の方式のテスト（`.bnt`、`check` を書いた `.mode`、`0` を書いた `.exit`。`.bnt` の先頭に `// spec:` の行）として置く。01-05 の拡張の例は、F04 が置いた `testdata-next/patterns/f04_commands.bnt`・`f04_scores.bnt` と同じ内容なので、足さない。期待値は C05 が確かめ、誤りの診断のゴールデンテストは C11 が書く。

## 難易度の理由

有用性の判定に、区間の分割と、長さを構成子とするリストのパターンを加える必要があり、選ばれない分岐の補助の位置の選び方にも細かい規則がある。型付けの部分は小さい。
