# R18 末尾呼び出しの窓の片付けと Slot の読み書きの費用を減らす

- 依存する作業: [R17](R17-call-path-and-constants.md)
- 難易度: 3（1〜5。README の「作業一覧」）
- 規模の見込み: 小（100〜500 行の変更。`src/vm/dispatch.rs` と `src/runtime/heap/core.rs`）
- ブランチ: impl/R18-tail-window-and-slot-access

## 目的

R17 の後の本測定（[記録](../../../tools/bench/results/2026-10-06-r17-9eedd64.md)）で、fib(35) は最小実行版の VM を下回った（1.974 s 対 2.059 s）が、loop は 1.10 倍（1.098 s 対 0.997 s）で、[ADR 0313](../../design/decisions/0313-vm-performance-recovery-before-stage-2.md) の決定 5 の関門に届かなかった。記録の「残りの費用」が挙げた次の二つを直す。設計者が本作業の起動を承認した（2026-10-06）。

1. 末尾呼び出しの後に、新しい窓の中の古い値を消している（loop で 4.9%）。10-09 が空にすることを求めるのは、窓を縮めたときと枠を降ろしたときに窓の外になったレジスタだけである。窓の中の古い値は、回収の前の整理（[ADR 0314](../../design/decisions/0314-clear-dead-registers-at-safepoints.md) の決定 2・3）が空にする。
2. `Slot` から値への変換とヒープの番号の確かめ（fib・loop で 10%）。`HeapCore` の `Slot` の読み書き（`slot_load`・`slot_store`・`slot_take`・`slot_clear`・`slot_move_slot`・`slot_new_slot`・`slot_release`）と、それが呼ぶ `check_slot_heap`・`checked_object`・`retime`・`retain`・`release`（とマーク・スイープの `mode.retain`・`mode.release`、`src/runtime/heap/core/mark_sweep.rs`）が、同じ `Slot` の種類を何度も判定している可能性がある。

振る舞いは変えない。ADR 0313 の決定 2・3、ADR 0314、ヒープの番号の確かめ（[ADR 0281](../../design/decisions/0281-heap-number-in-slot-and-contract-safety.md)）は変えない。

次のことは本作業の範囲に入れない。

- 値と `Slot` の表現（大きさ、配置）の変更。OPEN-065。
- 範囲の確かめの省略（OPEN-064、R32）と、振り分けのループの `unsafe`。
- 命令の集合とコード生成の変更。
- `runtime::heap` の公開の層の型とシグネチャ（10-08 の `file=`・`sig=`）の変更。

## 作るもの

- `src/vm/dispatch.rs`: 末尾呼び出し（`TAILCALL`・`TAILMETHOD`。どちらも `call::<true>` を通る）の窓の調整。「不要になった値の消去は省かない（10-09）」という今のコメントは 10-09 の読み方として誤りなので、直す。
- `src/runtime/heap/core.rs` と `src/runtime/heap/core/mark_sweep.rs`（内部の層）: `HeapCore` の `Slot` の読み書きの関数と、それが呼ぶ補助の関数の本体。`SlotRaw` は凍結した `slot.rs` の非公開の型なので、`Slot::raw`・`set_raw`・`is_immediate` を通して読む（即値を先に分ける手は `is_immediate` で書ける）。内部の層の関数の本体は作業が決めてよい（10-08 の冒頭）。ファイルの先頭の `//!` の不変条件の一覧と、`// SAFETY:` のコメントの対応を保つ。`unsafe` のブロックは加えない（加える必要が生じたら、作業を止めて報告する）。
- `src/vm/tests.rs`: 末尾呼び出しの回収のテスト（後述の「受け入れテスト」）。
- `src/bytecode/codegen/tests.rs`（なければ `codegen` の中の `#[cfg(test)]` のモジュール）: 手順 1 の前提（コード生成の出力では命令 0 の入口の集合が引数に含まれる）を確かめるテスト。

凍結したコードは変えない。`file=` のファイルの小さな関数に、R15 と同じ範囲の `#[inline]` の属性を加えることだけは認める（00-03「インターフェースの凍結」の R18 の例外）。

## 手順の要点

一つずつ入れ、入れるたびに既存のテストを通し、短い測定で効果を確かめる。効果のなかった変更は、コードが単純になるものだけを残す。

1. **末尾呼び出しの窓**: 末尾呼び出しで引数を窓の先頭へ写した後、新しい窓の中（引数の後ろから新しい窓の終わりまで）の古い値を消さない。新しい窓が古い窓より小さいときは、窓の外になったレジスタ（新しい窓の終わりから古い窓の終わりまで）を、今のとおり `clear` して `Vec` を縮める。新しい窓が大きいときに伸ばした分は、今のとおり `Unit` で埋める。
   - 安全である理由: コード生成（`bytecode::codegen`）の出力では、呼ばれた原型の命令 0 の入口で生きているレジスタは引数（0 から `num_params` − 1）だけである（引数でないレジスタは書かれる前に読まれない）。このとき、どの命令の入口の集合にも、引数でないレジスタは、命令 0 からの道筋のすべてで書かれた後にしか入らない。回収の前の整理は、新しい枠の窓のうち生きている集合に含まれないレジスタを空にする。生存の情報を引けない枠は保守的に残すが、そのときは古い値が根として辿られる（回収済みの対象を指すことはない）。
   - `RETURN` で枠を降ろすときに、降ろした窓を `clear` する処理は変えない（窓の外になる）。
   - 前提はコード生成の出力の性質であり、`compute_liveness` が保証するものではない（テスト用の `bytecode::asm` で組み立てた原型は、書く前に読むレジスタを持ちうる。そうした原型では、読まれる値が `Unit` でなく古い値になりうるが、回収済みの対象を指すことはない。検証器（R32）はまだない）。ゴールデンテストと仕様の例（`crates/benitoite/testdata/` と `tests/spec_examples.rs` が使う例）のプログラムと標準ライブラリをコード生成し、すべての原型で `live_in_at(0)` が 0..`num_params` に含まれることを確かめるテストを加える。成り立たない原型が見つかったら、本手順を採らずに報告する。
2. **`Slot` の読み書き**: release のビルドを逆アセンブルし（`objdump -d --demangle` など）、`MOVE`・`ADDI` などの命令の処理の中で、`Slot` の読み書きが何回種類を判定しているか（ヒープの番号の比較、対象かどうかの判定、`retime` の `match`、`retain`・`release` の判定）を数える。重複している判定を、一度の判定にまとめる。たとえば次の手を、測りながら選ぶ。
   - `slot_load` で、対象を指さない値（即値）の場合を先に分け、ヒープの番号の比較と `checked_object` と `retime` の `match` を、対象を指す場合だけにする。
   - `slot_store`・`slot_take`・`slot_clear` で、前の値と新しい値の対象かどうかの判定を一度ずつにする（マーク・スイープの `retain`・`release` は何もしないが、判定と分岐が残っていれば減らす）。
   - `retime` が値を組み立て直す `match` を、表現が同じであることを使って短くできるか確かめる（`unsafe` は使わない）。
   ヒープの番号の比較（ADR 0281。対象を指す `Slot` ではすべての構成で行う）、`heap-verify` の構成の確かめ、`#[cfg(test)]` の通知の計数は残す。
3. **残りの費用の内訳**: 1・2 の後に、R15〜R17 と同じ方法で fib と loop の残りの費用を報告する。

`[profile.release]` の設定は変えない。

## 受け入れテスト

- 振る舞い: 既存のテスト（VM、R11 のヒープの確かめ、ゴールデンテスト、参照インタプリタとの差分、`runtime::heap` の単体テスト）が、期待を変えずに通る。`scripts/check.sh` の `gc-stress` の構成でも通る。`tests/call_allocations.rs` が通る。
- 末尾呼び出し: 窓が大きくなる・小さくなる・変わらない末尾呼び出しで、新しい窓の中に古いヒープの値が残った状態から、回収の強制の下で正しく動き、回収の後にその古い値の対象が回収されている（ADR 0314 の整理で空になる）ことを、`bytecode::asm` で組み立てたプログラムで確かめる（R16 の回収の精度のテストの書き方に倣い、`run_stage1` の中で起きる回収を使う）。100 万回の末尾再帰と上限の `CallStackTooDeep` は既存のテストで確かめる。
- `Slot`: ほかのヒープの `Slot` を読み書きしたときに `ForeignHeap` の不具合として扱う既存のテストと、`heap-verify` の構成で回収済みの対象を読んだときの `StaleReference` の既存のテストが通る（足りなければ加える）。

### 性能の確かめ方

- 実装担当: R17 と同じく、作業を始めたときの `san_benito` の HEAD と本作業の版を、fib(30)・loop 300 万回で交互に数回走らせ、最小の時間を比べる。比較の版の展開と target は作業ディレクトリの `target/` の下に置き、終えたら消す。
- オーケストレータ: 取り込みの前に、設計者の確認を得てから、`tools/bench/gate.py` で関門を測る（最小実行版の VM と R17 の版を同じ機会に測り直す）。記録を `tools/bench/results/<日付>-r18-<コミット>.md` に残す。

### 目標に届かなかった場合

R15〜R17 と同じく、範囲の外の手に進まず、届かなかった値と残りの費用の内訳を報告して止まる。範囲の中の変更が正しく速くなっていれば、作業は完了として取り込む。

## 完了条件

- `scripts/check.sh` と `scripts/check-heap.sh` が通る（`runtime::heap` の内部の層を変えるため）
- 末尾呼び出しが新しい窓の中を消さず、窓の外になったレジスタだけを消している
- 完了の報告に、手順ごとの効果の表、手順 1 の安全である理由の確かめ、手順 2 で数えた判定の回数（変更の前と後）、残りの費用の内訳、凍結したファイルに加えた属性の一覧を書いている

## 確認の観点

[実装の確認の観点](../00-common/00-04-review-checklist.md)の「すべての作業で読む観点」、VM の行と `runtime::heap` の行に加えて、次の点を読む。

- 末尾呼び出しで、窓の外になったレジスタを必ず `clear` しているか（窓の外は `Unit`）。新しい窓の中の古い値が、回収の前の整理で空になる前提（命令 0 の入口の集合が引数に含まれる）が成り立つか。
- `Slot` の読み書きで、ヒープの番号の比較を、対象を指すすべての場合に行っているか。`heap-verify` の確かめと `#[cfg(test)]` の通知を落としていないか。内部の層の不変条件（H1〜H11、ファイルの `//!` の一覧）と `// SAFETY:` の対応を崩していないか。`unsafe` を加えていないか。

## 難易度の理由

変更は小さいが、`runtime::heap` の内部の層の読み書きに触れるので、ヒープの番号の確かめと検証の構成の確かめを一つでも落とすと、ほかのヒープの値や回収済みの対象を読む誤りを見逃す。末尾呼び出しの変更は、ADR 0314 の回収の前の整理に依存する。
