# 作業の進め方

本章は、実装 LLM が一つの作業を始めてから終えるまでの手順と、複数の LLM が並行して作業するときの決まり、オーケストレータ（Claude Code）が作業を配って取り込む手順を定める。最小実行版の進め方（最小実行版の実装プランの 00-03）を引き継ぎ、作業の ID、最小実行版の実装からの移行、インターフェースの凍結の二段階、メモリの管理の機能、第 1 段の後の確認を加える。

## 作業を始める前に読むもの

1. リポジトリの `AGENTS.md`（C00 の後は、本プランの実装の規約を写した節を含む）。
2. 本実装プランの [README](../README.md) と、本章、[実装の規約](00-02-conventions.md)、[リポジトリとクレートの配置](00-01-repository-layout.md)。
3. 担当する作業の文書（`20-tasks/<ID>-*.md`）。
4. 作業の文書の「読む設計書の節」に挙げた節と、「インターフェース」に挙げた `10-interfaces/` の章。

作業の文書に書いたファイルのパスは、`src/`・`tests/`・`testdata/` で始まるものは処理系のクレート `crates/benitoite/` からの相対パス、それ以外（`scripts/`・`tools/`・`fuzz/`・`docs/` など）はリポジトリの根からの相対パスである。

設計書の節は、作業の文書が挙げたものを読めば足りるように作業を分けてある。挙げていない節を読む必要を感じたら、読んでよい。最小実行版の設計書と実装プランの写し（`docs/archive/`）は、経緯を調べるときだけ読み、作業の根拠にしない。

## 作業の ID

作業の ID は、単位ごとに頭の文字で分ける（[README](../README.md) の「作業の ID」）。`C` は単位をまたぐ作業、`F` は U1、`R` は U2 である。U2 は、第 1 段を `R01`〜`R19`、第 2 段以降を `R20` 以降とする。最小実行版の `T` の ID とは重ならない。

## 最小実行版の実装からの移行

最初の作業 C04 が、最小実行版のモジュールを `crate::legacy` の下（`src/legacy/`）へ移した。以後、最小実行版の CLI とテストは `legacy` で動き続け、初回リリース版のモジュールは C04 が空けた最終的なパスに置いた。移行の締め（C18）が `legacy` を消したので、今のクレートには初回リリース版のモジュールだけがある（[README](../README.md) の「決めたこと」の 11、[リポジトリとクレートの配置](00-01-repository-layout.md)の「移行の間の配置」）。C18 が残した `dead_code` の許可の取り外しと `vm::stage1` の削除は、U1・U2 を終えた後に行う（[すべての作業を終えた後に行うこと](../90-after-completion.md)の「移行の締めの残り」）。

- どの作業も、取り込みの後にクレートがコンパイルでき、`scripts/check.sh` が通る状態を保つ。テストを消したり飛ばしたりして通すことはしない（移行の間に消したのは、C05 と C18 が決めたものだけである）。
- 移行の間は、`src/legacy/` を変えてよいのは 00-01「移行の間の配置」の表に挙げた作業だけとし、初回リリース版のモジュールと `legacy` は互いに参照しなかった（両方が使うのは `base` だけだった）。C18 が `legacy` を消すときに、初回リリース版のモジュールを直さずに済むようにするためである。

## ブランチと並行作業

- 一つの作業を一つのブランチで行う。ブランチの名前は `impl/<ID>-<短い名前>`（例 `impl/R01-allocator`）とし、`san_benito` から分ける。
- 複数の LLM が同時に作業するときは、`git worktree add ../Benitoite-<ID> impl/<ID>-<名前>` で作業ごとに作業ディレクトリを分ける。
- 作業を始められるのは、作業の文書の「依存する作業」がすべて `san_benito` に取り込まれた後である。
- 作業が触れてよいファイルは、作業の文書の「作るもの」に挙げたファイルと、そのファイルのテストである。`src/lib.rs` と各 `mod.rs` の `pub mod` の宣言はインターフェースを置く作業（C01・C02）が置くので、作業は変えない。ただし、作業が `sig=` で受け持つファイルの中に、非公開の子のモジュールを宣言して加えることはしてよい。例外は、移行の作業（C04 と C18 が `lib.rs` を改めた。U1・U2 の後の `dead_code` の許可の取り外しは、オーケストレータが行う）と、組み込みの関数の本体の親 `src/builtins/funcs/mod.rs`（組み込みの関数を書く作業が子のモジュールを加える。10-11「登録と第 1 段の扱い」）である。ほかの作業のファイルを変える必要が生じたら、作業を止めて報告する。
- この決まりにより、並行する作業のブランチは同じファイルを変えない。`san_benito` への取り込みで衝突が起きたら、後から取り込む側が直す。
- 例外として、次の作業は、ほかの作業が置いたファイルを、作業の文書の「作るもの」に挙げた範囲で改める。オーケストレータは、同じファイルを改める作業を同時に起動せず、一つを取り込んだ後の `san_benito` から次の作業の作業ディレクトリを作る。

| ファイル | 置いた作業 | 改める作業と範囲 | 順序 |
|---|---|---|---|
| `src/cli/tools.rs` の `run_tool` と `print_licenses` | F18（振り分けの `match` と仮の中身。振り分けの形は F18 の持ち物であり、各作業は自分の分岐の中身だけを改める） | D03（`fmt` の分岐）、D11（`test` の分岐）、D22（`skill` の分岐）、D30（`print_licenses`） | D11 は D03 に依存する。D22 と D30 は依存でつながらないので、D03・D11・D22・D30 のうち二つ以上を同時に起動しない |
| `src/cli/mod.rs` のテスト `usage_errors_and_unavailable_tools_have_two_lines_and_exit_two` の、名前を並べたループ | F18（まだ使えないサブコマンドの `TOOL_UNAVAILABLE` を確かめるテスト） | D03（ループから `"fmt"` を外す）、D11（ループから `"test"` を外す）。どちらも、外した分を自分の作業のテストに置き換える | D11 は D03 に依存する |
| VM の `IO` の命令の処理と、IO 実行器の `Deliver` の処理・`runtime::io::event` | R20・R26・R40 | D10（`Assert.Check` の分岐。10-18「`Assert.Check` の処理」）、L30（準備の待ちの規則。10-16） | D10 と L30 を同時に起動しない |
| `src/runtime/heap/core.rs`（内部の層の入口） | R01 | R02（方式の境目の宣言、方式ごとの状態の初期化、確保と解放の方式への通知、`TraceSink` の拡張）、R03・R04・R06・R11（それぞれの方式・対象の種類・検証器を内部の層につなぐのに要る範囲） | 依存の順に起動する。R03 と R06 は依存でつながらないので、同時に起動しない |
| `src/diag/render.rs` | F16 | D11（10-18 が加えた四つの関数と、`render_one_text`・`render_json_line` の共通化） | D11 と、`render.rs` を改めるほかの作業を同時に起動しない |

## インターフェースの凍結

インターフェースは、二つの作業で二段階に置く（[README](../README.md) の「決めたこと」の 3）。

| 作業 | 置く章 | 置いた後に始められる作業 |
|---|---|---|
| C01 | U2 第 1 段が使う章: クレートの骨組み（10-01 の `lib.rs`）、命令の集合と符号化・コンパイル済みプログラムの形・生存の情報（10-07。共有の章であり、第 2 段と U1 の命令も含めて一度で凍結する）、値とヒープの第 1 段の分（10-08）、VM の第 1 段の分（10-09）、組み込みの関数の型付きの形と番号と表の引き方（10-11） | U2 第 1 段（R01〜R14） |
| C02 | 共有と U1 の残りの章（10-01 の `lib.rs` のほか、10-02〜10-06、10-12〜10-14）と、10-08〜10-11 の `task=C02` の分 | U1（F01 以降）と U2 第 2 段（R20 以降） |

- C01 と C02 の章は、どちらも本プランの作成者（Claude Code）が書き、`tools/extract_interfaces.py check` でコンパイルできることを確かめてから、設計者の確認を経て凍結する。
- C01 は `tools/extract_interfaces.py place --task C01 --overwrite`、C02 は C01 を取り込んだクレートに `place --task C02 --overwrite` で置く（`--overwrite` は、見出しの属性 `replace` の付いたファイル、C01 では `src/lib.rs`、C02 では `src/base/mod.rs` を置き換えるために要る）。道具は、`file=` のコードをそのまま置き、`sig=` の関数の宣言を本体が `todo!()` の関数（`todo!()` の仮置き）として置き、書く前に rustfmt で整える（[実装の規約](00-02-conventions.md)の「`todo!()` の仮置き」）。置いたファイルの書式は章のコードと違うことがあるが、内容は同じである。置いた直後のクレートはコンパイルでき、`scripts/check.sh` を通る。`check --task C02` は、C01 と C02 を順に重ねて、この結果を確かめる。
- 10-07 は、第 1 段の VM が実行する命令（最小実行版の言語の分）だけでなく、U1 と第 2 段が使う命令も含めて C01 で凍結する。第 1 段の VM は、そのうち最小実行版の言語の分を実装し、ほかの命令は `Stop::Internal` を返す形で置く（[README](../README.md) の「決めたこと」の 4）。こうすると、第 2 段で VM の振り分けのループを作り直さずに、命令の処理を足していける。
- C02 は、C01 が置いたファイルを変えない。第 2 段の分を足す章（10-08〜10-11）と組み込みの表（10-12）は、C01 の `file=` のコードの後に、別のファイルか追加の `sig=` として足す。C01 の `lib.rs` と各 `mod.rs` は、C02 が置くモジュールも宣言しておき、道具が作った中身のないモジュールを C02 が埋める（[README](../README.md) の「インターフェースの読み方」）。C01 の型を変える必要が生じたら、C02 を書く前に設計者に示す。
- C01・C02 が置いた `file=` のコードと、作業の「作るもの」に挙げていないファイルは、作業が変えない。凍結したファイルを作業が変えてよい例外は次の六つだけであり、どちらも変えたものを完了の報告の「判断したこと」に挙げる。
  - 診断コードの表 `src/diag/codes.rs`（[10-02](../10-interfaces/10-02-diagnostics.md)）: コードを出す作業は、そのコードの文言の型板の言い回しと説明を直し、型板の埋め込みの鍵（`extras`）と修正案の鍵（`fixes`）を加えてよい。範囲は 10-02「型板の直し方」で定める。コードを加える・消す・報告の種類を変える・番号を変える必要が生じたら、作業を止めて報告する。
  - 組み込みの関数の本体の親 `src/builtins/funcs/mod.rs`（`sig=`。[10-11](../10-interfaces/10-11-builtin-interface.md)・[10-12](../10-interfaces/10-12-builtin-table.md)）: 組み込みの関数を書く作業は、作るものに挙げていなくても、子のモジュールの宣言と、表の部分の並び `PARTS` の末尾に部分を加えてよい（本章「ブランチと並行作業」）。
  - R15 の性能の回復（[ADR 0313](../../design/decisions/0313-vm-performance-recovery-before-stage-2.md)）: `file=` のファイルの小さな関数に `#[inline]` の属性（release のビルドだけ `inline(always)` にする `cfg_attr(not(debug_assertions), inline(always))` を含む）を加えることと、戻りでレジスタの `Vec` を縮めない形を採る場合に `Segment::reg_count`（`src/vm/frame.rs`）の本体を使用中の終端に従わせること。型・シグネチャは変えない。範囲は [R15](../20-tasks/R15-vm-dispatch-performance.md) の「作るもの」で定める。
  - R16 の生存の情報の処理の移動（[ADR 0314](../../design/decisions/0314-clear-dead-registers-at-safepoints.md)）: 10-07 で改めた `file=src/bytecode/liveness.rs` のとおりに `LiveInfo` の欄と `live_in_at`・`call_write` を書くこと、それらに R15 と同じ範囲の `#[inline]` の属性を加えること。
  - R17 の呼び出しの手順と定数の読み出し（[ADR 0313](../../design/decisions/0313-vm-performance-recovery-before-stage-2.md)）: `file=` のファイルの小さな関数に、R15 と同じ範囲の `#[inline]` の属性を加えること。
  - R18 の末尾呼び出しの窓と `Slot` の読み書き（[ADR 0313](../../design/decisions/0313-vm-performance-recovery-before-stage-2.md)）: `file=` のファイルの小さな関数に、R15 と同じ範囲の `#[inline]` の属性を加えること。

## 構文の改めとテストの移行

最小実行版のテストは古い構文で書いてあり、C05 までは `legacy` の構文解析器で動いた。構文の改め（F02）は初回リリース版の `syntax` に入るので、F02 を取り込んでも既存のテストは通り続けた。F02 は単独で取り込んだ。

テストの移行は、書き直し（C03）と切り替え（C05）の二つの作業で行う（[README](../README.md) の「決めたこと」の 5）。

- C03 は、F02 の直後に、ゴールデンテスト 197 件を新しい構文へ書き直して `testdata-next/` に置く。最小実行版の言語の機能だけを使い、構文だけを改める。F02 の構文解析器で読めることを確かめるテストを加え、`scripts/check.sh` で走らせる（構文の誤りを期待するテストは、構文の誤りとして報告されることだけを確かめる）。以後の U1 の作業が構文解析器を変えても、このテストが通り続けるようにする。期待する出力と診断の位置は、この時点では確かめない。
- C05 は、F18 の後に、書き直したテストを `testdata/` に移し、初回リリース版の実行器（C10）で、回収の強制の下で走らせ（第 1 段の間に行ったので、二つのメモリの管理のそれぞれで走らせた）、参照インタプリタ（F14）との差分も確かめる。期待する出力が書き直しの前と変わるのは、次のものに限り、変わった箇所を完了の報告に挙げる（[README](../README.md) の「決めたこと」の 14）。
  - 診断の位置と文言のように、構文の改めから説明できるもの
  - JSON の形式の `helps` の各要素が、文字列から、文 `message` と置き換え `edits` を持つオブジェクトになったこと（02-10「JSON の形式」、10-02）
  - 診断の件数の打ち切りの行が、警告も数えるので `more errors` から `more diagnostics` になったこと（10-02）
  - `--version` の出力に Unicode の版の行が加わったこと（10-13）
  - 10-02 が書き直した文言の型板（初回リリース版の構文と型の名前に合わせたもの）による文言の違い
  - そのほか、C05 の文書の「受け入れる期待値の変化」の表に挙げたもの（初回リリース版の規則で加わった警告、細かく分けた診断コード、`taskOrigins`、呼び出しの履歴の段の規則による変化など）

  それ以外の違いが出たら、期待する出力を改めずに報告する。古い構文のテストと、それを走らせる `legacy` の実行器の部分と、C03 の読めることを確かめるテストを消す。あわせて、`main.rs` を初回リリース版の CLI に切り替え、CLI のプロセスのテストとベンチマークのプログラムを新しい構文に移す。

U2 第 1 段の完了の条件（[ADR 0268](../../design/decisions/0268-staged-runtime-rebuild.md) の決定 3）の「最小実行版のすべてのテスト」は、C05 が初回リリース版のパイプラインで走らせる、書き直したテストを指す。したがって、第 1 段の測定（R12）と締め（R14）は、C05 の取り込みを待ち、U1 の F18 までの全体を待つ。それまでの第 1 段の作業（R01〜R11、R13）は、手で組み立てたバイトコードのプログラム（[10-07](../10-interfaces/10-07-bytecode.md)「第 1 段で実行するプログラム」）による単体テストで、VM と二つのメモリの管理を確かめた。

最小実行版の言語の範囲のプログラムを F15 のコード生成で移すと、10-07 の命令の表の段が 1 の命令だけになる（10-07「第 1 段で実行するプログラム」）。C05 で段が 2 の命令に出会って `Stop::Internal` で止まるテストがあれば、コード生成か本プランの誤りとして報告する。

U2 第 2 段（R20 以降。R38 を除く）は、R14 の後に始める（README の「依存と順序」）。移行の締め（C18）は、C05 と C13 の後に `legacy` を消した。

## 作業の手順

1. 作業の文書の「作るもの」と「手順の要点」に従って実装する。受け持つ `sig=` の関数は、C01・C02 が置いた `todo!()` の仮置きを本体に書き換える。書き換えた後のファイルに `todo!()` が残っていなければ、ファイルの先頭の仮置きのための許可とコメントを消す（[実装の規約](00-02-conventions.md)の「`todo!()` の仮置き」）。
2. テストを書く。新しいテストは、スキル `test-audit` の作成時の関門を通してから加える。作業の文書の「受け入れテスト」は、少なくとも満たすべき場合の一覧であり、一つの場合に一つのテストを書くことを求めるものではない。
3. `scripts/check.sh` を実行し、すべての検査が通ることを確かめる（[実装の規約](00-02-conventions.md)の「完了条件の共通の検査」）。`check.sh` は、既定の機能（マーク・スイープ）と回収の強制で検査する（第 1 段の間は、二つのメモリの管理の機能でそれぞれ検査した）。`runtime::heap` を変えた作業は、`scripts/check-heap.sh` も実行する。移行の間（C04〜C18）は、`check.sh` が `legacy` の最小実行版のテストも実行した。通らなければ、作業の範囲の外のテストであっても、完了としない。
4. 作業の文書の「完了条件」をすべて満たしたことを確かめる。あわせて、受け持つ関数に `todo!()` が残っていないことを確かめる（作業の文書が、後の作業に残すと定めた関数を除く）。
5. 完了の報告を書く（後述の「完了の報告」）。実装 LLM はコミットしない。確認を終えた作業は、オーケストレータがコミットする。

## 型やシグネチャを変える必要が生じたとき

`10-interfaces/` の型とシグネチャを変えずに実装できないと分かったら、実装を進めずに、次のことを報告して止まる。

- 変えたい型またはシグネチャと、変えた後の形
- 変えないと実装できない理由（どの設計書の節の、どの規則を満たせないか）
- 影響する作業（その型を使うほかの作業）

報告を受けたオーケストレータが実装プランの改め方を設計者に示し、合意を得てから作業を続ける。設計書と実装プランが食い違うと気付いたときも、同じく止まって報告する。U1 と U2 が共有する章（10-06・10-07・10-11・10-12）を変えるときは、その章を使う作業のうち取り込み済みのものへの影響も示す。

## 完了の報告

作業を終えたら、次の項目を報告する。報告は、作業を依頼した会話の最後の応答として書く（Codex では、オーケストレータが `-o` で指定したファイルに書き出される）。

| 項目 | 内容 |
|---|---|
| 作業 | 作業の ID と名前、作業ディレクトリ、ブランチ |
| 作ったもの | 追加・変更したファイル |
| 検査の結果 | `scripts/check.sh` の結果（通ったか）。`runtime::heap` を変えた作業は `scripts/check-heap.sh` の結果も |
| 受け入れテスト | 作業の文書の受け入れテストの各項目を、どのテストで確かめたか |
| `unsafe` | 加えた `unsafe` のブロックの数と、それぞれが引く不変条件（`runtime::heap` の作業だけ） |
| 判断したこと | 作業の文書に書いていなかったことを、自分で決めた箇所と理由 |
| 残したこと | 作業の範囲で実装しなかったこと、気付いた問題 |

実装の確認は、[実装の確認の観点](00-04-review-checklist.md)に従って行う。

## 作業の状態

README の作業一覧の「状態」の欄は、次の値をとる。欄を更新するのは、オーケストレータである。

| 状態 | 意味 |
|---|---|
| 未着手 | 依存する作業が終わっていないか、担当が決まっていない |
| 着手可 | 依存する作業がすべて取り込まれ、担当が決まった |
| 作業中 | 実装 LLM が作業している |
| 確認中 | 完了の報告を受け、実装を確認している |
| 完了 | 確認を終え、`san_benito` に取り込んだ |

## オーケストレータによる進め方

本節は、オーケストレータ（Claude Code）が作業を配り、確かめ、取り込む手順を定める。実装 LLM は本節を読まなくてよい。

### 担当と起動の方法

作業ごとの担当は、README の作業一覧の「担当」の欄のとおりとする。難易度によらず Codex（GPT-6.1-Sol、推論の度合い high）が実装する（[ADR 0308](../../design/decisions/0308-implementation-by-codex-sol.md)。[ADR 0285](../../design/decisions/0285-implementer-assignment-for-first-release.md) を改めた）。すべての作業を、オーケストレータが 00-04 の観点で確かめる。Codex は実装に専念させ、レビューに使わない。オーケストレータは作業を実装しない。ただし、D31 と D32 は、ネットワークと設計者の機械での試行を要するので、Codex に割り当てず、オーケストレータが作業の文書に従って設計者と行う（[ADR 0292](../../design/decisions/0292-release-checks-needing-network-by-orchestrator.md)。README の作業一覧の担当は「オーケストレータと設計者」）。Codex は、Bash で `codex exec` をバックグラウンドで起動する。

Codex の起動のコマンドは次のとおりである。

```sh
codex exec -m gpt-6.1-sol -c model_reasoning_effort=high -C <作業ディレクトリ> -s workspace-write -o <報告のファイル> - < <依頼の文面のファイル>
```

- `-s workspace-write` のサンドボックスでは、作業ディレクトリの外に書き込めず、ネットワークも使えない。ネットワークが要る準備は、オーケストレータが作業の前に済ませる。U1・U2 では、nightly の Rust と Miri の部品の導入（C00 の前。`rustup component add --toolchain nightly miri`）と、`mio` の取得（`mio` を加える作業の前）が当たる。
- worktree のコミットは作業ディレクトリの外に書き込むので、Codex はコミットできない。コミットはオーケストレータが行う。

GPT-6-Astra は、実装の担当にも確認の担当にも使わない。設計の相談に使うときは、設計者に知らせて了承を得てから行い、送った依頼と回答を検討資料の `consult/` に残す（[ADR 0253](../../design/decisions/0253-first-release-plan-location-and-units.md) の決定 3）。

### 依頼の文面

どの担当にも、次の内容を依頼の文面として渡す。

1. 作業の ID と、作業の文書のパス（`docs/implement/20-tasks/<ID>-*.md`）。
2. 作業ディレクトリのパスと、そこから出ないこと。
3. 本章の「作業を始める前に読むもの」を読み、「作業の手順」に従うこと。コミットしないこと。
4. 型やシグネチャを変える必要が生じたら、本章の「型やシグネチャを変える必要が生じたとき」に従って止まること。
5. 最後の応答を、本章の「完了の報告」の表の形で書くこと。

### 配る順

依存を満たした作業から起動する。U2 第 1 段のうち R01〜R11 と R13 は C01 の後に始められ、U1 を待たない。R12 と R14 は C05 を待つ。U1 は C02 の後に始め、C03 は F02 の後に始める。Codex に同時に起動する作業の数と、配る順の列は、担当を決めるときに README に書く。

### 確認と取り込み

1. 作業ごとに `git worktree add ../Benitoite-<ID> -b impl/<ID>-<名前> san_benito` で作業ディレクトリを作り、担当を起動する。
2. 完了の報告を受けたら、状態を「確認中」にし、作業ディレクトリで `scripts/check.sh`（`runtime::heap` を変えた作業は `scripts/check-heap.sh` も）を実行し、差分を[実装の確認の観点](00-04-review-checklist.md)に従って読む。
3. 難易度 5 の作業は、オーケストレータが特に念入りに確かめる。`runtime::heap` の作業では、`// SAFETY:` のコメントが引く不変条件が実際に成り立つかを読む。
4. 問題があれば、同じ担当（直らなければ別の担当）に、問題の一覧を添えて直させ、2 に戻る。
5. 問題がなければ、作業ディレクトリでコミットする。コミットメッセージはスキル `git-workflow` に従い、1 行目を `<ID> <作業の名前>` で始める。
6. `san_benito` に取り込み（`git merge --no-ff impl/<ID>-<名前>`）、取り込んだ後の `san_benito` で `scripts/check.sh` が通ることを確かめ、状態を「完了」にする。通らなければ取り込みを戻し、原因の作業を 4 に戻す。どの取り込みの後も `check.sh` が通ることが、移行の間の決まり（本章の「最小実行版の実装からの移行」）の前提である。作業ディレクトリは `git worktree remove` で消す。
7. 取り込みで依存を満たした作業の状態を「着手可」にし、起動する。

### 第 1 段の後の確認

U2 第 1 段の測定（R12）を終えたら、第 1 段の締め（R14）を起動する前に、測定の記録を設計者に示し、暫定に採るメモリの管理の方式と閾値の係数 k を確かめる（[ADR 0268](../../design/decisions/0268-staged-runtime-rebuild.md) の帰結）。設計者の確認を経た方式を、R14 の作業の文書に書いてから起動する。あわせて、第 2 段（R20）を起動する前に、[OPEN-071](../../design/open-issues.md#open-071)（`Opaque`・`Host` の対象が持つ別の領域の容量の数え方）を決め、10-08 と作業の文書に反映する。
