# 配布形態

## 目的と範囲

処理系を利用者に配る形を定める。対象は、リリースの形と公開するリポジトリ、ソースからのビルド、配布物のライセンスと第三者の OSS の著作権表示、互換性の方針である。

初回リリース版の範囲を最初にリリースした版（`0.0.1`）は、ソースコードだけのリリースである。実行ファイルを配る形（対応環境ごとの実行ファイル、配布物の置き場所、導入の手順、リリースの試験）は、初回リリース版に含めない（docs/todo の TODO-073）。モバイルと処理系コアの WASM 化は、初回リリース版に含めない。

## 前提

バージョンの付け方（メジャー・マイナー・パッチ、メジャーバージョンが 0 の間の扱い）は[ロードマップ](../00-overview/00-03-roadmap.md)の「バージョンとコードネーム」で定めた。本章の互換性の方針は、それに従って、メジャーバージョンが 0 の間の各版で変えてよいものを定める。

処理系・標準ライブラリ・同梱の Agent Skill のライセンスは `MIT OR Apache-2.0` である。依存のクレートと、許可するライセンスは[ロードマップ](../00-overview/00-03-roadmap.md)の「利用する既存の OSS のライセンス」に従う。同梱の Agent Skill の中身と導入のサブコマンドは [Agent Skills 対応](../06-tooling/06-06-agent-skills.md)で定める。

## 仕様

### リリースの形と公開するリポジトリ

【決定】初回リリース（`0.0.1`）は、ソースコードだけのリリースとし、実行ファイルを配らない。git のタグは `v0.0.1` とする。以後のソースだけのリリースは `0.0.2`・`0.0.3`…とし、実行ファイルを配る最初のリリースを `0.1.0` とする（版の表は[ロードマップ](../00-overview/00-03-roadmap.md)の「バージョンとコードネーム」）。`0.0.x` のリリースで利用者が処理系を導入する手順は、後述の「ソースからのビルド」だけである。理由: 実行ファイルを配るには、環境ごとのビルドと試験を行うリリースのスクリプトが要り、それを初回リリースの後に回したからである。

【決定】このリポジトリは、初回リリース（`0.0.1`）のときに GitHub で公開した。設計メモとコミットのメールアドレスも公開する。公開するリポジトリの形は次のとおりとする。

- 公開するブランチは、当面 `san_benito` だけとする。
- 公開する履歴は集約した。最初の 5 本のコミットを残し、それより後のコミットを一つのコミットにまとめた。集約の前の履歴の写しは設計者の手元に残す。
- `san_benito` のコミットのメッセージは、原則として英語にする。タイトルは英語だけで書き、本文は、英語の箇条書き、タイトルの日本語の訳、日本語の箇条書きの順に書く。ほかのブランチには適用しない。

公開する前の文書が参照するコミットの番号とタグの多くは、集約で公開の履歴から消えた。これらの参照は書き換えずに残す。参照先は初回リリース前の開発の履歴にあり、その履歴は設計者の手元のリポジトリにだけ残る。

### 対応環境（初回リリース版）

【決定】処理系は、次の環境を対象とする。初回リリース版は、各環境の実行ファイルを配らず、各環境での確かめも行っていない（docs/todo の TODO-073）。

| 環境 | Rust のビルド先 | 実行ファイルの依存 |
|---|---|---|
| macOS（arm64） | `aarch64-apple-darwin` | OS のシステムライブラリだけ。macOS 11.0 以降 |
| Linux（x86_64） | `x86_64-unknown-linux-musl` | なし（musl を静的にリンクする） |
| Linux（arm64） | `aarch64-unknown-linux-musl` | なし（musl を静的にリンクする） |

- Windows は、WSL2 の中の Linux で、上の Linux 向けの実行ファイルを使う。Windows で直接動く実行ファイルは、初回リリース版では作らない。
- ビルドに使う Rust のツールチェーンの版は、リポジトリの `rust-toolchain.toml` で固定する。
- ソースからビルドした実行ファイルは、ビルドした機械の既定のビルド先（Linux では glibc）になる。処理系を開発するときの手元のビルドも、既定のビルド先でよい。

### ソースからのビルド

【決定】ソースからビルドして導入する手順（`cargo install`）を、利用者向けの文書に書く。

- 同梱の Agent Skill の生成する文書（設計書の[構文](../01-spec/01-02-syntax.md)の章から作る文法など）は、生成の道具で作ってリポジトリに置いてある。処理系のビルドは、それを実行ファイルに埋め込むだけであり、設計書を読まない。生成物が古くないこと（いまの構文の章・標準ライブラリのソース・診断の表から生成したものと一致すること）は、処理系のテストで確かめる。理由: ビルドの中に別の抽出器を書くと、標準ライブラリのソースと診断の表の読み方を処理系と二重に持ち、両者が食い違うおそれがあるからである。
- 【方針】手順は、リポジトリを取得して、処理系のクレートのディレクトリを `cargo install --locked --path` に指定する形とする。crates.io への公開は初回リリース版では行わない。
- ソースからのビルドは、機能 `bundled-licenses` を付けないので、第三者のライセンスの一覧を埋め込まない（後述の「ライセンスの表示」）。

### ライセンスの表示

【決定】第三者のライセンスの表示 `THIRD_PARTY_LICENSES` は、次のように作り、示す。

- `THIRD_PARTY_LICENSES` は、開発機の上で cargo-about を使って生成する（`scripts/release/licenses.sh`）。依存のクレートはビルド先によって違いうるので、ビルド先ごとに生成する。
- 【方針】`THIRD_PARTY_LICENSES` には、実行ファイルに含む依存のクレートごとに、名前・版・ライセンス・著作権表示・ライセンス文を載せ、Apache-2.0 のものは NOTICE ファイルの内容も載せる（[ロードマップ](../00-overview/00-03-roadmap.md)の「利用する既存の OSS のライセンス」）。
- 【決定】配布物（crates.io のパッケージ）のライセンスの文に著作権の行がないクレートは、そのクレートの `Cargo.toml` の `authors` を著作者として添える。ライセンスのファイルがパッケージにないクレートは、そのライセンスの SPDX の標準の文を載せ、`authors` を添える。上流のリポジトリの文を取って補うことはせず、`THIRD_PARTY_LICENSES` はネットワークを使わずに、ロックファイルと取得済みのパッケージだけから生成できるようにする。理由: 生成の結果が、ネットワークの状態や上流のリポジトリの変化に左右されないようにするためである。
- 【決定】`authors` も空のクレートは、`Cargo.toml` の `repository` の URL を添える。ライセンスのファイルも `authors` もない graviola と rustls-graviola は、選べるライセンスのうち Apache-2.0 の SPDX の標準の文を載せ、repository の URL を添える。
- 機能 `bundled-licenses` を付けたビルドは、生成した `THIRD_PARTY_LICENSES` を処理系のクレートの `licenses/` に置いたうえで、実行ファイルに埋め込む。`benitoite --licenses` は、埋め込んだ一覧を標準出力に書く（[CLI](../06-tooling/06-01-cli.md)の「コマンドラインの形」）。生成したファイルはリポジトリで追跡しない。生成と埋め込みをまとめて行うリリースのスクリプトは初回リリース版に含めない（docs/todo の TODO-073）。
- 【方針】機能 `bundled-licenses` を付けないビルド（開発のビルドと、ソースからのビルド）の `--licenses` は、処理系自身のライセンスと、第三者のライセンスの一覧を含まないビルドであることを書く。
- 同梱の Agent Skill のディレクトリにも、Skill のライセンス文を置く（[Agent Skills 対応](../06-tooling/06-06-agent-skills.md)の「同梱の Agent Skill の構成」）。

【決定】処理系自身の著作権表示は、次のように書く。

- 著作権表示は `Copyright (c) 2026 tecogonaz and Benitoite contributors` とする。`LICENSE-MIT` と、リポジトリの README の著作権表示に使う。
- 初回リリース（`0.0.1`）の README は、処理系のコードの大部分を LLM が生成したことと、ライセンスが著作権で保護される部分に適用されることを書いていない（docs/todo の TODO-073）。

### 互換性の方針

【決定】`0.1.0` より前の `0.0.x` のリリースでは、どのリリースでも互換性を壊す変更をしてよい。`0.1.0` から `1.0.0` の前までの互換性は、次のとおりとする。

| 版 | 例 | 変えてよいもの |
|---|---|---|
| マイナーの版 | `0.1.0` から `0.2.0` | 言語・標準ライブラリ・CLI・診断の互換性を壊す変更を含めてよい |
| パッチの版 | `0.1.0` から `0.1.1` | 不具合の修正だけを含め、互換性を壊さない |

- パッチの版で直す不具合は、処理系が仕様と食い違う振る舞いである。仕様（言語・標準ライブラリ・CLI・診断コードと JSON の形）は、パッチの版では変えない。仕様と食い違う振る舞いに頼っていたスクリプトは、パッチの版で動かなくなることがある。
- 【方針】診断の文言と修正案の中身は、互換性の約束に含めない。パッチの版でも改めてよい。ハーネスは、診断を文言ではなくコードと JSON の欄で見分ける。
- 互換性を壊す変更は、`CHANGELOG` に、移行の手順とともに記録する。
- 非公式のモジュール（[標準ライブラリ](../03-interop/03-06-stdlib.md)の「標準のモジュールと非公式のモジュール（初回リリース版）」）を標準に移すと、取り込みの名前が変わる。これは互換性を壊す変更であり、マイナーの版で行う。非公式のモジュールも、パッチの版では変えない。
- 廃止した診断コードの番号は、別の意味で使い回さない。
- 処理系はコンパイル済みプログラム（バイトコード）を保存も配布もしない（[パイプライン](../02-impl/02-01-pipeline.md)）ので、バイトコードは 0.x の間の互換性の対象にしない。
- 同梱の Agent Skill は、同じ版の処理系だけを対象にする。処理系を更新したときは、`benitoite skill install` を実行し直す。
