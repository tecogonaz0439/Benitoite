# スクリプト実行と埋め込み

## 目的と範囲

スクリプトの実行のライフサイクル。コンパイル済みプログラムと実行ごとの状態（ハンドラ表、診断、リソースの追跡など）の分離、実行環境の入力、結果の返却、中断の要求、後始末を扱う。CLI の一回の実行とテストの実行器の繰り返しの実行で保持する状態の範囲を区別し、中断や資源の上限のうち処理系が実装する部分とハーネスに委ねる部分を示す。言語から観測できるエントリポイントは[評価意味論](../01-spec/01-08-evaluation.md)、中断時の解放規則は[リソース管理](../01-spec/01-10-resources.md)、終了コードと標準入出力は[CLI](../06-tooling/06-01-cli.md)が扱う。

本章は、初回リリース版（[ロードマップ](../00-overview/00-03-roadmap.md)）の範囲を定める。初回リリース版でスクリプトを実行する手段は、CLI の `run`（`run` を省いた実行とシェバンによる実行を含む）と、CLI の `test` によるテストの実行である。サーバモードによる実行、REPL、スクリプトを埋め込んだ実行ファイル、Rust のライブラリとして処理系を呼び出す API は、初回リリース版に含めない。

## 前提

コンパイル済みプログラムは実行の間で共有でき、実行中に変わる状態は実行ごとに分ける。実行ごとの状態の中身と、実行の流れ・止める手順・中断の要求の扱いは[パイプライン](02-01-pipeline.md)、[仮想機械](02-08-vm.md)、[ランタイム](02-09-runtime.md)で定める。コマンドラインの形とオプションは [CLI](../06-tooling/06-01-cli.md) で、テストの書き方と結果の報告は[利用者プログラムのテスト](../06-tooling/06-04-test-runner.md)で定める。

## 仕様

### 状態の分け方

【方針】スクリプトの実行に関わる状態を、次の四つに分ける。

| 状態 | 中身 | 作る時期 | 共有 |
|---|---|---|---|
| 検査の状態 | ソースの表（実行を始めるファイル、import で辿ったモジュール、読んだ標準ライブラリのソース）、ノード番号と束縛の番号の数え上げ、名前解決と型検査の表、診断の一覧 | 検査ごと | しない |
| コンパイル済みプログラム | [バイトコードとコード生成](02-07-bytecode.md)の「コンパイル済みプログラム」。トップレベルの定数の値の記述を含む | 検査を通ったプログラムのコード生成ごと | 複数の実行とスレッドで共有してよい |
| 外部実行の準備 | 遅延初期化する Engine、通常・生成補助の Component の表、起動全体の中断を見張るスレッド | 最初の外部呼び出し | 一回の test 起動の通常テスト・複数入口・doc の例で共有する。run 単独は専用の所有者を持つ |
| 実行ごとの状態 | [ランタイム](02-09-runtime.md)の「実行ごとの状態」（タスクと呼び出しの情報、ハンドラ表、イベントループ、リソースの表、出力先と出力のバッファ、実行の入力、実行時エラーの情報など） | 実行ごと | しない |

【方針】初回リリース版のトップレベルに置ける値は定数だけであり、定数の値はプログラムの実行の前に定まる。定数の値の記述はコンパイル済みプログラムに置き、言語の値は実行の中で記述から作る（[パイプライン](02-01-pipeline.md)の「コンパイル済みプログラムと実行ごとの状態」）。可変のセルとリソースは実行の中でだけ作れるので、実行の間に持ち越すモジュールの状態はない。

### 実行を始めるファイルとプログラムの読み込み

【決定】`run`・`check` にディレクトリを指定したときは、そのディレクトリの `main.bnt` を実行を始めるファイルとし、ファイルを指定したときは、そのファイルを実行を始めるファイルとする。根のディレクトリは、実行を始めるファイルがあるディレクトリである。処理系は、根の直下の `package.bnt` を設定ファイルとして読み、親のディレクトリを遡って探さない（[パッケージ](../06-tooling/06-09-packages.md)）。`test` にディレクトリを指定したときは、その下の `.bnt` のファイルをそれぞれ実行を始めるファイルとし、根のディレクトリは指定したディレクトリとする。ただし、`package.bnt` と、指定したディレクトリより下で直下に `package.bnt` を持つディレクトリの下全体を除く（[利用者プログラムのテスト](../06-tooling/06-04-test-runner.md)の「テストの実行」）。

【決定】`benitoite [オプション] <スクリプトのパス> [スクリプトの引数...]` は `benitoite run` と同じ意味である。シェバンによる実行は、OS がシェバンの行に従ってこの形で処理系を起動するものであり、CLI の `run` による一回の実行と同じである（[CLI](../06-tooling/06-01-cli.md)の「`run` を省いた実行とシェバン（初回リリース版）」）。字句解析はシェバンの行を読み飛ばす（[字句構造](../01-spec/01-01-lexical.md)の「シェバンの行（初回リリース版）」）。

【決定】読み込みの段は、実行を始めるファイルから始め、import が指すファイルを辿って読む。根のディレクトリの下のファイルのうち、import で辿れないものは読まない。名前解決と型検査は、プログラム全体を一つの単位として行う（[名前解決とモジュール読込](02-04-resolver.md)）。

【方針】`Process.scriptDirectory()` が返す実行を始めるスクリプトのディレクトリは、実行を始めるファイルのパスから、実行を始めるときに一度だけ求め、実行の入力に入れる。シンボリックリンクを解決した絶対パスとし、作業ディレクトリに依存させない（[エフェクト](../01-spec/01-07-effects.md)）。

### CLI の一回の実行

【方針】`run` は、次の順に処理する。

1. コマンドラインを解釈し、実行を始めるファイルを決める。使い方の誤りがあれば、終了状態 2 で終わる（[CLI](../06-tooling/06-01-cli.md)）。
2. 中断の要求（`SIGINT`・`SIGTERM`）を受ける設定をする（[ランタイム](02-09-runtime.md)の「中断の要求」）。
3. 検査の状態を作り、読み込みから外部の関数の照合までの段を行う。誤りがあれば、診断を書いて終了状態 2 で終わる（[パイプライン](02-01-pipeline.md)）。警告は書き、`--deny-warnings` を指定していなければ次へ進む。
   `--allow-effects` があれば、同じ段のスタックで main の宣言上限を取り出し、許す集合との包含を比較する。不足なら E0512 を加えて脱糖へ進まず、終了状態2で拒否する。検査失敗・標準ソースの不具合は先に扱い、不明な契約を比較しない。比較に通った同じ検査済みプログラムを次へ渡し、ソースの再読・再検査はしない（[CLI](../06-tooling/06-01-cli.md#実行前のエフェクト上限の照合)）。
4. 脱糖とコード生成を行い、コンパイル済みプログラムを作る。処理系の制限に当たれば、診断を書いて終了状態 2 で、処理系の不具合が起きれば、その報告を書いて終了状態 3 で終わる（[診断エンジン](02-10-diagnostics.md)）。検査の状態は、ここで不要になる。
5. 実行ごとの状態を作り、`main` を実行して、終わり方に応じて終える（[ランタイム](02-09-runtime.md)の「プログラムの実行の流れ」）。

`check` は、1 と 3 だけを行う。どちらも、終わったときにすべての状態を捨てる。

### テストの実行

【方針】`test` は、実行を始めるファイルごとに 1・3・4 と同じく検査とコード生成を行い、そのファイルに書いたテストの関数を実行する（[利用者プログラムのテスト](../06-tooling/06-04-test-runner.md)の「テストの実行」）。一つのファイルのテストは、同じコンパイル済みプログラムを共有する。上限を指定しない場合、検査の誤りがあるファイルのテストは実行せず、ほかのファイルへ進む。

【決定】ファイルごとの処理は、準備と準備済みの成果物の実行に分ける。準備は段の大きなスタックで検査・脱糖・コード生成を行い、実行の入力（`RunInput`）の作成と、全テストの束縛に対応する原型の確認まで済ませる。AST・型表・コア IR の破棄も同じ段で終える。呼び出し側へ返すのは、ソースと診断を持つ検査結果（`program: None`）と、コンパイル済みプログラム・各テストとその原型の一覧・確認の表・実行の入力、または準備の失敗である。実行はこの成果物を消費し、ソースの再読・再検査・再コンパイル、原型の再検索、実行の入力の再作成を行わない。理由: 検査した内容と実行する成果物を一致させ、準備の失敗をそのファイルの最初のテストより前に報告し、深い構造の走査と破棄を段のスタック内で終えるためである。

【決定】上限を指定しない実行器は、一つのファイルの準備と実行を終えてから、次のファイルを準備する。全ファイルの成果物を保持せず、検査の誤りで実行しないファイルも従来どおり数える。

【決定】`test --allow-effects` は、同じ準備を `ExecuteLimited` のモードで使う。型検査を通った各テストの契約を比較してから脱糖へ進み、成功した全入口の組 `(EntrySpec, Prepared)` を Vec に保持する。保持するのは上記の所有する成果物だけであり、AST・型表・コア IR は入口ごとの段で捨てる。全入口の準備と診断の確認が成功した後、その Vec を順に消費する。ソース・対象の探索・検査・コンパイル・実行準備をやり直さず、各テストの `RunEnv` と `RuntimeParts` は従来どおり別に作る。入口ごとの準備中に依存ファイルが変わる可能性はあり、全対象が一時点のスナップショットであることは保証しない。探索後に追加されたファイルも実行対象へ加えない。

【決定】上限付きの実行器は、各入口の準備の前と、全入口の準備を終えて最初のファイルの実行を始める前に、中断の印を読む。後者も [ランタイム](02-09-runtime.md#中断の要求)の「中断の要求」に定める、テストの実行器がファイルとテストを始める前の読み口に当たる。全体拒否の報告では印を読み直さず、開始前の確認で観測した中断か、準備が返した失敗の終了状態をそのまま使う。準備中に不具合が起きた場合、その後の要求を確認するためだけの読み取りは行わない。理由: 実行を始める前の中断を確認しつつ、終了直前のためだけに大域の状態の読み口を増やさないためである。

【決定】`test --check` は、同じ入口の探索と準備処理を非実行のモードで使い、`require_main=false` で外部の関数の照合まで行って終える。確認の表・脱糖・コード生成・実行用の入力・VM・`RuntimeParts` は作らない。AST と型表の破棄は通常の準備と同じ段のスタック内で終え、ソースと診断を持つ検査結果（`program: None`）と、同じ `collect_tests` が集めた所有するテスト一覧・束縛で照合する関数契約・プログラム全体の shell の参照を返す。診断を出した後、通常の検査の誤りなら次の入口へ進み、テストの結果と集計は出さない。中断は既存の入口の開始前の確認だけを使う（[利用者プログラムのテスト](../06-tooling/06-04-test-runner.md#テストの非実行の検査)）。

【決定】`test --check --report=json` は、通常の非実行の検査と同じ段の境界を使い、返されたソース・診断・テストの情報を一つの報告に組み立てる。入口ごとの準備の直後に、ソースの識別情報とハッシュ・診断・テストを JSON にし、ソース本文と行表は次の入口へ進む前に捨てる。探索の各入口には指定パスの番号を持たせ、探索を繰り返さずに requestedTargets と対応させる。通常の検査失敗では次へ進み、不具合と中断では処理済みの結果を保って未着手の入口を不完全とする。検査結果に AST を残さず、ソースの再読や再検査で不足を補わない。

【決定】テストは、一つずつ別の実行として動かす。

【方針】テストの実行器は、テストごとに次のように実行する。

- 実行ごとの状態を作り、`main` の代わりにテストの関数を、引数なしで最初のタスクとして呼ぶ。次に進めるタスクを選ぶ部品・時計・作業用のスレッドの仕事の実行は本番のものであり、ネットワークの失敗の表は空である（[ランタイム](02-09-runtime.md)の「組み込みの操作とハンドラ表」）。
- `Assert.Check` の操作は、テストの実行器が、最初のタスクのハンドラの連鎖の最も外側に置く組み込みのハンドラで処理する。このハンドラは、起動したタスクにも引き継がれる。確認が成り立てば操作の呼び出しに `()` を返して続け、成り立たなければ、確認の失敗を理由に[仮想機械](02-08-vm.md)の「止める手順」でそのテストの実行を止める。利用者が `Assert.Check` を処理する言語のハンドラを書いたときは、そちらが先に処理する（[ランタイム](02-09-runtime.md)の「操作の振り分け」）。
- 【方針】`Assert.equal`・`Assert.notEqual` で比べる値の型は、型検査が呼び出しの位置に記録した型引数を、呼び出しの式の span で引く。

  型パラメータを含むときは、最も内側の枠が確認を書いたトップレベルの関数の原型と一致する場合だけ、その枠の呼び出しの位置の型引数で置き換える。

  次の段へ進むのは、呼び出しが通常の `CALL` であり、その命令の原型が一つ外側の枠の原型と呼び出しを書いたトップレベルの関数の原型に一致する場合だけとする。末尾呼び出しは一段の型引数を使った後に枠の探索を止める。具体的な型を書いた呼び出し元からの末尾呼び出しなら、その一段で型が決まる。理由: 末尾呼び出しで消えた枠と同じ原型の別の起動が残っていても、その起動の型引数を使わないためである。

  ラムダの本体・`handle` の本体と節の中の確認では、定義元の起動を枠から決められないので、最初から使用箇所の候補を求める。実装のメソッドの中の確認では、呼び出し元から型を求めない。

  型パラメータを持つ関数が末尾呼び出しで別の関数を呼んだ場合は、呼び出し元の枠が消え、その型引数が枠から分からない。この場合や、関数を値として渡した場合など、枠から決まらないときは、プログラム中のその関数の全使用箇所の型引数を辿る。候補の集まりが完全で、比べる二つの値の形に合う型が一つだけなら、その型を使う。実装のメソッドの中の型パラメータを含む使用や、型コンストラクタの引数を含む使用など、展開できない項目があれば候補を使わない。

  復元した型が二つの値の形に合わなければ、確認の位置の型から候補を求め直す。決まらない位置だけを値の形から書き、構成子は `<constructor #n of an unknown type>` と書く。自分を呼ぶ型パラメータの補助の関数でも、使用箇所の探索が循環して型が決まらないことがある。値の表現とバイトコードは、値の型の情報を持たない。理由: 実行時の値に型の情報を持たせると、値の表現と値を作るすべての組み込みの関数の変更が必要になるため、報告に使う型を静的な表と失敗時の枠から求める。
- 【決定】使用箇所の型引数を辿る探索は深さ 8、探索する項目は重なりを除いて 64 個までとし、上限を超えた場合は候補を使わない。型パラメータを含む項目は型引数とそれを書いた関数の組で、具体的な項目は型引数だけで重なりを除く。値の形との照合は明示の積み重ねで行い、4,096 ステップを超えた残りは合うとみなす。理由: 型引数の循環や多数の使用箇所、共有した構造を持つ値によって、失敗の報告の処理が長引くことを避けるためである。
- テストの関数が `()` か `Result.Ok(())` を返せば成功、`Result.Error(message)` を返すか、確認の失敗、実行時エラー、資源の不足、`Process.exit` で止まれば失敗とする。実行時エラーと資源の不足の報告は、[診断エンジン](02-10-diagnostics.md)の実行時エラーの報告と同じ内部の表現で作り、テストの結果に含める。
- 標準入力は空の入力とし、標準出力と標準エラー出力は、テストごとに捕らえて結果に含める。捕らえる出力先も、ほかの出力先と同じく書き出し用のスレッドによる転送と完了の待ちを通し、結果に含める前に最後の転送の完了を待つ（[ランタイム](02-09-runtime.md)の「出力のバッファ」）。基準のディレクトリは、処理系を起動したときの作業ディレクトリとする。コマンドライン引数は空の並びとする。
- テストの実行器は、実行時の権限制御の判定を行わない。
- 処理系の不具合が起きたときは、ほかのテストを続けず、その報告を書いて終了状態 3 で終わる。

【決定】test の外部実行の準備は、起動が持つ `ExternalSession` を既存の内部の実行設定で各実行へ渡す。公開の `RunEnv`・`VmConfig` に共有用の欄を加えない。Store・Instance・外部ハンドル・解放待ち・言語ヒープ・出力・実行番号は実行ごとに分ける。外部を呼ばなければ Engine・Component の実行用コンパイルと見張りを作らない。静的な宣言の照合は入口とdocの例ごとに行う。理由: 準備の反復を減らしながら、実行の状態と検査の契約を保つためである。

【方針】テストの実行器は、テストを一つずつ順に実行する。テストごとに実行ごとの状態を分けるので、処理系の中の状態はテストの間で持ち越さない。ただし、テストが外部の状態（ファイル、環境）を共有すれば結果が変わりうるので、テストはほかのテストの実行に依存してはならない（[利用者プログラムのテスト](../06-tooling/06-04-test-runner.md)）。

【方針】`test` の実行中に中断の要求を受けたときは、実行中のテストを止める手順で止め、残りのテストを実行せずに、それまでの結果を報告して終了状態 130 で終える。テストの関数が値で終わった後に中断の印を見つけたときも（[ランタイム](02-09-runtime.md)の「中断の要求」）、そのテストの結果を報告せず、数にも入れずに中断として終える。

### 実行の入力と結果

【方針】スクリプトが実行の外から受け取るものは、次のものに限る。

| 入力 | CLI の `run` | テストの実行器 | 使う操作 |
|---|---|---|---|
| コマンドライン引数 | スクリプトのパスより後の引数 | 空の並び | `Process.arguments` |
| 標準入力 | 処理系のプロセスの標準入力 | 空の入力 | `Console.Read` の操作、`Process.runAttached` |
| 環境変数 | 処理系のプロセスの環境変数 | 同じ | `Process.environmentVariable`、外部コマンドの起動 |
| 基準のディレクトリ | 処理系を起動したときの作業ディレクトリ | 同じ | 相対パスを受け取る操作、`Process.workingDirectory`、外部コマンドの起動 |
| 実行を始めるスクリプトのディレクトリ | 実行を始めるファイルから求める | 同じ | `Process.scriptDirectory` |
| ファイルシステム | OS | 同じ | `File` の操作 |
| 外部コマンド | OS | 同じ | `Process.Run` の操作 |
| 時刻 | OS の時計。単調な時計の起点は実行を始めた時点 | 同じ | `Clock.Time` の操作 |
| 乱数の種 | 実行を始めるときに OS の乱数から決める | 同じ | `Random.Generate` の操作 |
| ネットワーク | OS | 同じ | `Http.Listen`・`Http.Connect` の操作 |

言語のハンドラで処理した組み込みの操作は、上の入力を使わない。初回リリース版は実行時の権限制御を行わないので、利用者の許可は実行の入力に含めず、組み込みの操作はすべて行える。

【方針】実行の結果は次のものである。CLI の `run` では、出力は処理系のプロセスの標準出力と標準エラー出力に書き、終わり方は終了状態で表す。テストの実行器では、処理系のプロセスを終えずに、これらを結果として受け取る。

| 結果 | 内容 |
|---|---|
| 終わり方 | `main`（テストではテストの関数）が値を返した、`Result.Error` を返した、実行時エラー、資源の不足、確認の失敗（テストだけ）、`Process.exit`、中断の要求、処理系の不具合 |
| 終了状態 | CLI の終了状態と同じ値（[CLI](../06-tooling/06-01-cli.md)の「終了状態」）。`Process.exit` では指定した値、中断の要求では 130 |
| 出力 | スクリプトが標準出力と標準エラー出力に書いた内容 |
| 報告 | 警告、`main` の `Result.Error` の文字列、実行時エラー・資源の不足・解放の失敗・処理系の不具合の報告（[診断エンジン](02-10-diagnostics.md)） |

【決定】内部の報告付き終了を実行した結果は、どちらの IO の方式でも、採用した停止理由に情報がある場合だけ `RunEnd.die_failure` に原因・任意の説明・ソース位置を保持し、終了状態は 1 とする。文字列は所有し、実行中のヒープの値を結果に残さない。通常の `Process.exit` と、言語のハンドラで処理した呼び出しの情報は保持しない。取り消された要求や、先に採用された別の終了・中断・処理系の不具合へ情報を転記しない。`main_error` は引き続き `main` の `Result.Error` の文字列だけを表す。本番のソースからの実行でも、この終了結果と位置・原因・任意の説明を保持する。

### 資源の上限と中断

【方針】処理系が実装する資源の上限は、呼び出しの情報の大きさ（すべてのタスクと保存した継続を合わせて数える）と、一つの操作で作る文字列・`Bytes`・リストの大きさ（[ランタイム](02-09-runtime.md)の「一つの操作で作る値の大きさの上限」）である。CLI の実行時間とヒープの使用量の上限は、処理系を起動する側（Agent Skills を実行するハーネス、シェル、OS）に委ねる。

【決定】CLI の `run` と `test` は、中断の要求（`SIGINT`・`SIGTERM`）を受けたら、すべてのタスクを取り消し、`with` のリソースを解放し、出力を書き出してから、終了状態 130 で終える。解放の途中で二度目の要求を受けたら、OS の既定の振る舞いで終える。仕組みは[ランタイム](02-09-runtime.md)の「中断の要求」で定める。`check` と `fmt` は中断の要求を特別に扱わず、OS の既定の振る舞いに任せる。`fmt` は、途中で中断されてもファイルを壊さないように、整形の結果を一時ファイルに書いてから名前の変更で置き換える。
