# パイプライン

## 目的と範囲

処理の段と段間で受け渡すデータ構造、VM の再入可能性（reentrancy）、実行方式の選定。各段の中の作り方は、段ごとの章（[ソース管理と位置情報](02-02-source-and-spans.md)から[スクリプト実行と埋め込み](02-11-embedding.md)まで）が定める。

本章は、初回リリース版（[ロードマップ](../00-overview/00-03-roadmap.md)）の処理系の構成を定める。初回リリース版のプログラムは、実行を始めるモジュールと、そこから import で辿れるすべてのモジュールからなる（[名前・スコープ・モジュール](../01-spec/01-03-names-modules.md)の「実行を始めるモジュール（初回リリース版）」）。REPL、LSP サーバ、MCP サーバ、スクリプトを埋め込んだ実行ファイルの経路は、初回リリース版に含めない。

## 前提

処理系の段の並びと、「検査」と「実行」の区別は[全体像](../00-overview/00-02-architecture.md)で定めた。言語の意味は[コア計算と脱糖](../01-spec/01-12-core-calculus.md)で定め、処理系の実行結果はコア計算の実行結果と一致しなければならない。

## 仕様

### 実行方式

【方針】実行方式は、自作のバイトコード VM（JIT なし）とする。

### 段と段の間のデータ

【方針】処理系は、スクリプトを次の段で順に処理する。各段は入力を書き換えず、新しいデータを出力する。

| 段 | 入力 | 出力 | 定める章 |
|---|---|---|---|
| 読み込み | 実行を始めるファイルのパス、処理系に埋め込んだ標準ライブラリのソース、構文解析した各ファイルの先頭の部分と import の宣言 | ソース（ファイル ID と内容のバイト列）の表と、モジュールの表（モジュールの名前、ファイル ID、import の宣言が指すモジュール） | [ソース管理と位置情報](02-02-source-and-spans.md)、[名前解決とモジュール読込](02-04-resolver.md) |
| 字句解析 | ソース | span 付きの字句の列 | [字句解析器と構文解析器](02-03-frontend.md) |
| 構文解析 | 字句の列 | モジュールごとの、span 付きの抽象構文木（abstract syntax tree、AST）とコメントの一覧 | [字句解析器と構文解析器](02-03-frontend.md) |
| 名前解決 | すべてのモジュールの AST | 名前の参照ごとに、それが指す束縛を定めた表と、モジュールごとの公開の表 | [名前解決とモジュール読込](02-04-resolver.md) |
| 型検査 | 名前解決の結果を伴う AST | 式の型、型の引数、演算子の型、ラムダのエフェクト、宣言の型、型クラスの制約の解き方の各表と、定数の値（[型検査器](02-05-typechecker.md)の「出力」） | [型検査器](02-05-typechecker.md) |
| 外部の関数の照合 | 型検査の結果と外部の関数の属性 | コンポーネントのバイト列、書き出しの名前、型の変換表（名前解決の出力の外部の関数の表に入れる） | [外部の関数](../03-interop/03-10-external-functions.md) |
| 脱糖 | 型検査の結果を伴う AST | コア IR と下位 IR（中間表現の二つの段階） | [中間表現と脱糖](02-06-ir-and-lowering.md) |
| コード生成 | 下位 IR と定数の値 | コンパイル済みプログラム | [バイトコードとコード生成](02-07-bytecode.md) |
| 実行 | コンパイル済みプログラムと、実行の入力（コマンドライン引数、標準入出力のつなぎ先、ハンドラ表） | 実行の結果（出力、終了状態、実行時エラーの情報） | [仮想機械](02-08-vm.md), [ランタイム](02-09-runtime.md), [スクリプト実行と埋め込み](02-11-embedding.md) |

【決定】読み込み・字句解析・構文解析は、ファイルごとに続けて行う。読み込みの段は、実行を始めるファイルから始め、ファイルを一つ読むたびに字句解析と構文解析を行い、その import の宣言が指すモジュールを、読むファイルの一覧（作業の一覧）に積む。入口の解析の直後に、根の `package.bnt` と依存ごとの `package.bnt` を読み、依存の表を作る。根とパッケージの下のファイルのうち、import で辿れないものは、根と依存の直下の `package.bnt` を除いてソースとして読まない。`hash` を書いた依存では、照合のために対象のファイルをバイト列として読む（[パッケージ](../06-tooling/06-09-packages.md)）。理由: Agent Skills のディレクトリには、説明の文書や別のスクリプトなど、取り込まないソースが置かれうるからである。作業の一覧の進め方とファイル ID の振り方は[ソース管理と位置情報](02-02-source-and-spans.md)で、モジュールの名前からファイルを探す方法と循環の検出は[名前解決とモジュール読込](02-04-resolver.md)で定める。

【決定】名前解決と型検査は、プログラム全体を一つの単位として行う。名前解決は、すべてのモジュールのトップレベルの宣言を先に集めて公開の表を作り、その後で本体を解決する。型検査は、宣言をプログラム全体で先に検査し、その後で関数の本体を一つずつ検査する。モジュールの間の参照は、検査全体で一意な束縛の番号で結び付ける（リンク）。変わったモジュールだけを検査し直すインクリメンタルな処理は、初回リリース版では行わない。理由: 型クラスの実装はプログラム全体で有効であり、トップレベルの関数の型注釈が必須なので、宣言を先に集めれば本体を順序によらず検査できるからである。

【決定】名前解決と型検査は AST を変更せず、AST のノードを鍵とする表として結果を出力する。理由: AST の定義が一つで済み、フォーマッタも同じ AST を使えるからである。表の中身は[名前解決とモジュール読込](02-04-resolver.md)と[型検査器](02-05-typechecker.md)で定める。

公開の検査（[名前・スコープ・モジュール](../01-spec/01-03-names-modules.md)の「公開（初回リリース版）」）は、名前解決の段で行う（[名前解決とモジュール読込](02-04-resolver.md)）。[コア計算と脱糖](../01-spec/01-12-core-calculus.md)は公開の検査を脱糖の前に終えるとしており、脱糖の段はモジュールと公開を扱わず、束縛の番号で定義を指す。

【決定】標準ライブラリのソースは、利用者のモジュールと同じ構文のモジュールとして書き、利用者のモジュールと同じ段を通して、同じコンパイル済みプログラムに含める。読むのは、prelude のモジュールと、import で辿れる標準ライブラリのモジュールだけである。標準ライブラリのソースは、処理系の実行ファイルに埋め込んだ文字列として持ち、読み込みの段はファイルシステムから読まずにソースの表に加える（[ソース管理と位置情報](02-02-source-and-spans.md)、[名前解決とモジュール読込](02-04-resolver.md)）。

【方針】コンパイル済みプログラムをファイルに保存しない。実行のたびにソースから作る。

### 定数の評価

【方針】トップレベルの定数（[構文](../01-spec/01-02-syntax.md)の「定数（初回リリース版）」）の値は、型検査の段の中で、関数の本体の検査の前に求める（[型検査器](02-05-typechecker.md)の「検査の単位と手順」の手順 4）。型検査器は、定数の宣言の型を検査した後、型の付いた定数式の AST を評価する専用の評価器で、定数を一つずつ評価する。評価器は、基本型の演算と `Map.fromList`・`Set.fromList` などの組み込みの関数を、実行時と同じ規則で計算する。実行時の組み込みの関数はヒープの値を受け取るので、評価器はそれを直接は呼ばない。値の表現によらない計算（`Decimal` の算術、`Float` の文字列への変換、鍵の順序の基本型の値の比較）は、基本のデータの上の Rust の関数として共有のモジュールに置き、評価器と組み込みの関数の両方がそれを呼ぶ（[型検査器](02-05-typechecker.md)の「定数の検査と評価」）。定数どうしの循環は名前解決で誤りにしてある（[名前解決とモジュール読込](02-04-resolver.md)）ので、参照される定数から順に評価できる。

計算が実行時エラーの条件に当たるときは、検査の誤りとする。評価の結果は値の記述としてコード生成に渡し、コード生成はそれを定数表に置く。定数を実行の前に一度だけ計算して共有しても、観測できる違いはない（[コア計算と脱糖](../01-spec/01-12-core-calculus.md)の「トップレベルの定数」）。評価器と値の記述の形は[型検査器](02-05-typechecker.md)と[バイトコードとコード生成](02-07-bytecode.md)で定める。

### 中間表現

【決定】処理系の中間表現（intermediate representation）は、[コア計算と脱糖](../01-spec/01-12-core-calculus.md)のコア計算と同じ形にする。項を値と計算に分け、計算は `return` と `let` でつなぐ。各ノードは、型とエフェクトと、由来するソース上の位置を持つ。脱糖の段は、コア計算と脱糖の章の脱糖の規則を実装する。中間表現は、コア計算と同じ形のコア IR と、コア IR の `match` を判定の木に置き換えた下位 IR の二つの段階からなる（[中間表現と脱糖](02-06-ir-and-lowering.md)）。理由: 中間表現をコア計算と同じ形にしておくと、脱糖の規則と実行の規則を中間表現の上でそのまま確かめられるからである。

【決定】パターンの選択肢、ガード、範囲、リストのパターンは、コア計算と同じくコア IR の `match` に含め、判定の木に変換する段で扱う。型クラスの制約は、型検査が記録した制約の解き方に従い、脱糖の段が実装の辞書の引数として加える。

### 検査と実行の経路

【方針】ツールごとに、次の範囲の段を通す（[全体像](../00-overview/00-02-architecture.md)）。

| 経路 | 通す段 | 定める章 |
|---|---|---|
| `check` | 読み込みから外部の関数の照合まで（定数の評価を含む） | [CLI](../06-tooling/06-01-cli.md) |
| `run`（`run` を省いた実行とシェバンによる実行を含む） | 読み込みから実行まで | [CLI](../06-tooling/06-01-cli.md)、[スクリプト実行と埋め込み](02-11-embedding.md) |
| 通常の `test` | 入口ごとに読み込みからコード生成までを一度行い、テストの関数ごとに別の実行として実行する | [利用者プログラムのテスト](../06-tooling/06-04-test-runner.md) |
| `test --check` | 入口ごとに読み込みから外部の関数の照合まで（定数の評価を含む）。テストを実行しない | 同上 |
| `fmt` | 指定したファイルの読み込みと構文解析だけ。import を辿らない | [フォーマッタ](../06-tooling/06-03-formatter.md) |

`check`・`run`・`test` の経路は、外部の関数の照合までの段を同じ実装で行う。外部の関数の照合までに誤りが見つかったときの振る舞いは、どの経路でも `check` と同じである。

CLI の `check` と `run` は、非公開の準備関数を共有する。準備関数は `main` を必須として一度検査し、`run` のときだけ、検査を通ったプログラムを脱糖・コンパイルする。標準ライブラリのソースに誤りがある場合はコンパイルへ進まない。深い AST と中間表現は段のスレッドで破棄し、呼び出し側へはソースと診断を持つ検査結果（プログラムは持たない）、任意のコンパイル結果、報告に使うコマンドの種別、報告を指定した場合の契約の抽出結果だけを返す。run の上限の照合も同じ段内で済ませ、不足の診断を検査結果へ加える。準備中の panic とスレッドの作成の失敗は処理系の不具合として返し、呼び出し側が診断を出す。コンパイル中に捕らえた panic はコンパイル結果に保持し、検査の診断の後に報告する。理由: 検査と実行の準備を同じ処理に保ち、深い構造の破棄で呼び出し側のスタックが溢れることを防ぐためである。

`check --report=json` は、この一回の検査から `main` の宣言名・名前の位置・`Scheme.effects` と、標準の `IO.Process.shell` への参照の有無を取り出す。`types.main` の束縛を `resolved.decls` とトップレベルの関数宣言に照合し、型表や宣言の欠落、エフェクト変数、利用者エフェクト、未展開の `IO.All`、未知の組み込み番号は内部エラーとする。エフェクトは組み込みの表から正規名へ写して辞書順に並べる。宣言した上限を使い、本体の最小の集合を推論し直さない。

shell の判定は、読み込んだモジュールの種類と完全なモジュール名で `IO.Process` の有無を確かめ、読み込んでいれば標準の shell の束縛を `resolved.refs` の全件の値と比較する。一致するノードが `types.expr_types` にある式の参照だけを数え、ハンドラの節の操作名は除く。ハンドラの本体の式は含める。未読なら参照なし、既読で束縛がなければ内部エラーとする。到達しない関数や依存の参照も含む。判定のための import や AST の式の再走査は加えない。抽出と AST の破棄は段のスレッド内で終え、所有する小さな情報だけを返す。報告のために検査や読み込みを繰り返さない。報告の形は [CLI](../06-tooling/06-01-cli.md#main-の非実行の検査報告)で定める。

`test --allow-effects` は、各入口を一度だけ検査し、入口のテスト関数ごとの宣言上限を同じ共通の契約抽出と包含の判定で照合する。不足があれば脱糖へ進まない。成功した入口はコンパイル済みプログラムと実行の入力・全テストの原型まで保持し、全入口が成功してから順に実行する。AST とコア IR は入口ごとの段で捨て、実行のために再読・再検査・再コンパイルを行わない。上限なしの逐次実行との違いと所有は[スクリプト実行と埋め込み](02-11-embedding.md#テストの実行)で定める。

【決定】処理系のプロセスの中で実行を一つだけ行う CLI の `run` を除き、`Process.exit` はプロセスを終えず、その実行だけを終える。テストの実行器での実行では、標準入力を空の入力につなぎ、標準出力と標準エラー出力を実行ごとに捕らえて結果に含める。理由: テストの実行器は一つのプロセスの中で複数のテストを実行するので、一つのテストがプロセスを終えたり処理系の標準入出力を使ったりすると、ほかのテストの実行と結果の報告が壊れるからである。

`test --check --report=json` は、通常の実行と同じ探索と `collect_tests` の一覧を使い、型表から宣言上限を取り出す。確認の表・脱糖・コード生成・実行用の入力は作らない。抽出と AST・型表の破棄は入口ごとの段内で終え、所有するテスト情報・ソース・診断だけを返す。報告の組立ではソースと診断を JSON に変換し、次の入口へ進む前にソース本文と行表を捨てる。

処理系は、実行の前に宣言したエフェクトの上限を報告し、指定した集合への包含を静的に照合できる。実行時の権限制御は持たない。

【決定】中間表現をコア計算の実行の規則どおりに実行する参照インタプリタ（reference interpreter）を、処理系に含める。参照インタプリタは、脱糖の段が作るコア IR（[中間表現と脱糖](02-06-ir-and-lowering.md)）を入力とし、判定の木への変換、コード生成、VM を通さない。テストだけに使い、同じプログラムを参照インタプリタと VM で実行して結果を突き合わせる差分テスト（differential testing）に使う。利用者が使う経路には含めない。理由: VM はバイトコードを実行し呼び出しの情報を独自のデータ構造に持つので、形がコア計算の抽象機械から離れており、手で書いた期待値だけでは一致を確かめられるプログラムが限られるからである。タスクはコア計算に含まれないので、差分テストはタスクを使わないプログラムに限る。差分テストの進め方は[処理系のテスト戦略](../07-quality/07-03-compiler-testing.md)で定める。

外部の関数の検査を通った宣言は、合成したトップレベルの関数として脱糖し、外部の関数の表と呼び出しの命令を生成する（[中間表現と脱糖](02-06-ir-and-lowering.md)の「コア IR」、[バイトコードとコード生成](02-07-bytecode.md)の「コンパイル済みプログラム」）。

### 宣言だけの収集

【決定】`pipeline::declarations::collect_declarations(entry, fs)` は、読み込み・字句解析・構文解析・import と宣言の名前解決・宣言の型と制約の検査を行う。本体の名前解決と型検査、定数の評価、外部コンポーネントとの照合、実行は行わない。本体も構文解析するので、本体の構文の誤りは拒否する。名前解決と型検査の宣言の処理は通常の `check` と共用し、同じスタックと panic 境界で動かす。

返す `DeclarationResult` は `sources`・`diagnostics`・`inventory` を持つ。宣言に誤りがあれば `inventory` は `None` となる。成功した `DeclarationInventory` はソース、読み込み時の全ファイルのパスと生バイト列、モジュール表、AST、宣言の名前解決表と型表を所有する。本体の参照・式の型・定数値は収集しない。依存のハッシュ検証だけが読んだファイルも保持し、同じパスを異なる内容で二度読んだ場合は読み込みの誤りにする。`CheckedProgram` は返さず、通常の検査の成功を示す報告にも使わない。理由: 生成前の関数を本体から呼んでいる段階でも、生成道具が正しく解決した宣言の構造を必要とするためである。

### 誤りが見つかったときの段の進め方

【決定】検査の各段（読み込みから外部の関数の照合まで）は、出力と診断の組を返す。誤りの診断が一つでもあれば、次の段を行わない。警告の診断は、次の段に進むことを妨げない。

【決定】読み込み・字句解析・構文解析はファイルごとに続けて行うので、一つのファイルに誤りがあっても、作業の一覧のすべてのファイルの構文解析を終えるまで続ける。どれか一つのファイルに読み込みか構文の誤りがあれば、そこで止め、名前解決に進まない。

各段の中では、誤りから回復して処理を続け、その段で見つけられる誤りをできるだけ多く報告する。構文解析器の回復の方法は[字句解析器と構文解析器](02-03-frontend.md)で、型検査器が回復して検査を続ける単位は[型検査器](02-05-typechecker.md)で定める。

【決定】警告は、`check` でも `run` でも、誤りと同じ形で報告する。オプション `--deny-warnings` を指定したときは、警告を誤りとして扱う。

【方針】`--deny-warnings` を指定しても、検査の段は警告を理由に途中で止めず、外部の関数の照合まで進める。照合を終えた時点で警告が一つでもあれば、誤りとして扱い、脱糖に進まない。途中で止めると、後の段で見つかる警告を報告できないからである。

脱糖とコード生成の段は、型検査を通ったプログラムだけを受け取るので、利用者のプログラムの誤りを報告しない。これらの段で処理を続けられない状態になったときは、処理系の不具合として扱う。その報告の形は[診断エンジン](02-10-diagnostics.md)で定める。

実行時エラーを標準エラー出力に書く形式も、[診断エンジン](02-10-diagnostics.md)で定める（[評価意味論](../01-spec/01-08-evaluation.md)）。

### コンパイル済みプログラムと実行ごとの状態

【決定】外部の関数の表には、関数の修飾した名前、コンポーネントの表示のパス、読み込んだバイト列、書き出しの名前、型の変換表、引数の数だけを持つ。Wasmtime の `Engine`・`Component`・`Store` は実行ごとの状態にだけ置く。理由: コンパイル済みプログラムを複数の実行とスレッドで共有し、実行間で Wasm の状態が混ざるのを防ぐためである。

【決定】コード生成が出力するコンパイル済みプログラム（バイトコード、定数表、関数の表、ソース上の位置の表）は、生成の後に変更しない。複数の実行と複数のスレッドが、同じコンパイル済みプログラムを同時に読んでよい。

【決定】実行中に変わる状態は、実行ごとに作るオブジェクト（実行ごとの状態）に持たせる。一つの実行を同時に進めてよいスレッドは一つだけとし、一つの実行を複数のスレッドで同時に進めるための排他制御は入れない。タスクの切り替えも、この一つのスレッドの上で、実行ごとの状態の一部であるスケジューラが行う。理由: テストの実行器のように一つのプロセスの中で複数の実行を扱う場面があり、共有するものを変更しないプログラムだけに限れば、実行どうしの排他制御が要らないからである。

【方針】スレッドの間で共有するコンパイル済みプログラムには、スレッドをまたいで共有できる型（Rust の `Send` と `Sync` を満たす型）だけを持たせる。実行中の言語の値は実行ごとのヒープに置き（[ランタイム](02-09-runtime.md)の「メモリの管理」）、一つの実行の中だけで使うので、定数表には実行中の値そのものを置かない。定数表には値の記述を置き、`LOADK` が実行中の値を作る（[バイトコードとコード生成](02-07-bytecode.md)の「値の移し方」）。

実行ごとの状態は、次のものを含む。

| 状態 | 内容 | 定める章 |
|---|---|---|
| 呼び出しの情報 | タスクごとの、戻り先、引数、局所の変数の積み重ね。`handle` の枠で区切った区画の連なりとして持ち、捕まえた継続の区画もここから移す | [仮想機械](02-08-vm.md) |
| ハンドラの連鎖 | タスクごとの、評価中の `handle` の並び。タスクを起動するときは、起動したタスクの連鎖を引き継ぐ | [仮想機械](02-08-vm.md) |
| スケジューラ | 進められるタスクの待ち行列と、外部に作用する操作の完了を待つタスクの表 | [仮想機械](02-08-vm.md), [ランタイム](02-09-runtime.md) |
| ハンドラ表 | 言語のハンドラが処理しない組み込みの操作を行う Rust の関数の表。`run`・`test` の実行は本番のハンドラ表を使い、テスト用のハンドラ表は処理系のテストだけで使う | [ランタイム](02-09-runtime.md) |
| イベントループと待ちの表 | イベントループ、作業用のスレッドから完了を受け取る通路、外部に作用する操作の完了を待つタスクの表 | [ランタイム](02-09-runtime.md) |
| リソースの表 | 開いているリソースと解放したリソースの記録。`with` で束縛したリソースは、呼び出しの情報の解放の枠が表の番号で指し、プログラムが止まるときはその枠を辿って解放する | [ランタイム](02-09-runtime.md), [仮想機械](02-08-vm.md) |
| 実行の入力 | コマンドライン引数、相対パスを解決する基準のディレクトリ、実行を始めるスクリプトのディレクトリ、標準入出力のつなぎ先 | [スクリプト実行と埋め込み](02-11-embedding.md) |
| 出力先と出力のバッファ | 標準出力と標準エラー出力の書き出し先と、書き込んだがまだ書き出していない出力 | [ランタイム](02-09-runtime.md) |
| 中断の要求の読み口 | 中断の印を読むところ。CLI ではプロセス全体の印を読む | [ランタイム](02-09-runtime.md) |
| 大きさの計数 | 呼び出しの入れ子の大きさ（すべてのタスクと保存した継続の枠を合わせて数える）。ヒープの使用量には上限を設けない | [仮想機械](02-08-vm.md) |
| 実行時エラーの情報 | 実行時エラーまたは資源の不足の種類と、呼び出しの履歴とタスクの起動の履歴を作る材料 | [仮想機械](02-08-vm.md), [ランタイム](02-09-runtime.md) |

初回リリース版は実行時の権限制御を持たないので、実行ごとの状態に権限の情報を置かない。

【決定】処理系のどの段も、パッケージ変数などの大域的な可変状態を持たない。初期化の後に変更しない表（組み込みの関数の表など）は、大域に置いてよい。この規則は処理系のコードに、実行だけでなく検査の段にも適用する。依存のクレートが内部に持つ大域の状態はこの規則の対象とせず、[03-01「使う Rust のクレート」](../03-interop/03-01-library-structure.md#使う-rust-のクレート)に書く。

【決定】中断の要求（`SIGINT`・`SIGTERM`）を受けたことを表す印は、この規則の例外とし、プロセス全体で一つ持つ。印を書くのはシグナルの登録の仕組みだけであり、VM はタスクを切り替える位置と外部に作用する操作を待つ位置で印を読む。印を立てるのは CLI の `run` と `test` である。

### 関数の呼び出しと処理系のスタック

【決定】VM は、呼び出しの情報を実行ごとの状態の中に VM が管理するデータ構造として持ち、言語の関数の呼び出しと戻りで Rust の関数を入れ子に呼ばない。データ構造の形は[仮想機械](02-08-vm.md)で定める。理由: すべての末尾呼び出しを記憶域を増やさずに実行し、深すぎる呼び出しの入れ子を実行時エラーと同じ手順で止め、実行を途中で止めて別のタスクに切り替えられるようにするためである。

組み込みの関数（Rust で実装した関数）は、VM から Rust の関数として呼ぶ。初回リリース版には、関数を引数にとる組み込みの関数がある（`Task.all`・`TaskGroup.spawn`・`Reference.update` など）。タスクを起動する関数は、受け取った関数を新しいタスクの最初の呼び出しとして、そのタスクの呼び出しの情報に積む。組み込みの関数が受け取った関数を呼ぶときに、Rust の関数を入れ子に呼ばずに済ませる方法は、[仮想機械](02-08-vm.md)と[ランタイム](02-09-runtime.md)で定める。

【決定】検査・脱糖・コンパイルの段は AST と中間表現を再帰で辿るので、その深さは入れ子の上限（[字句解析器と構文解析器](02-03-frontend.md)の「入れ子の深さ」）で抑えられるが、使う Rust のスタックの量は最適化の水準などで変わる。そこで、これらの段を呼ぶパイプラインの公開の関数は、内部で 64 MiB のスタックを持つスレッドを作って段を実行し、結果を待つ。読み込みから型検査までを行う関数は、スレッドの中で panic を捕らえ、処理系の不具合の診断にして結果の診断の一覧に入れて返す（[診断エンジン](02-10-diagnostics.md)）。脱糖とコンパイルを行う関数は、スレッドの中の panic を呼び出し側のスレッドで再び起こす。実行（VM）は呼び出し側のスレッドで行う。理由: 最適化しないビルドでは、上限いっぱいの入れ子で構文解析や型検査が 2 MiB 前後のスタックを使い、Rust のスレッドの既定のスタック（2 MiB）では溢れることがあるからである。スタックが溢れると、処理系は診断を出さずに異常終了する。

【決定】段の 1 回の再帰が使うスタックの量を、次のように抑える。

- 再帰で辿る振り分けの関数（構文解析・名前解決・型検査・脱糖・判定の木への変換・コード生成のそれぞれの、式や計算を種類で振り分ける関数）は、大きな分岐の中身を `#[inline(never)]` の補助の関数に分け、振り分けの関数の枠には分岐ごとの局所変数を置かない。診断を組み立てるなど誤りのときだけ通る処理は、`#[cold]` と `#[inline(never)]` の関数に出す。
- ブロックの文の並び、リストの要素、呼び出しの引数、レコードのフィールドは、脱糖で `Let` の連なりになる。脱糖の文の並び、判定の木への変換の `Let` の連なり、コード生成の `Let` は、連なりの長さだけ再帰せず、ループで下りてから後ろ向きに組み立てる。`else if` の連なりの脱糖も同じである。下ろす順は再帰で書いたときと同じにし、変数とラベルの番号の割り当てを変えない。

理由: 最適化しないビルドでは関数のすべての分岐の局所変数が枠に並び、最適化したビルドでは一か所から呼ぶ補助の関数が呼び出し元に展開されて枠が戻るので、どちらでも振り分けの関数を細く保つ必要がある。文の数で再帰が積み重なると、入れ子の上限は文の数を抑えないので、平らなブロックでも溢れうる。

【決定】入れ子の上限の深さで段を通すテストを、明示した大きさのスタックを持つスレッドで行う（[処理系のテスト戦略](../07-quality/07-03-compiler-testing.md)の「実装の規約と静的な検査」）。テストは、構文解析から型検査までと、脱糖・判定の木への変換・コード生成を、段のスレッドを通さずにそのスレッドで行い、作った AST と中間表現もそのスレッドの中で捨てる。スタックの大きさは 16 MiB とする。理由: 上限の深さで最も多くを要する形は、最適化しないビルドではレコードの更新元の入れ子で約 12.8 MiB、最適化したビルドではリストのパターンの入れ子で約 3.1 MiB を要した（2026-10-11 の測定。arm64 の macOS、16 KiB 刻みの二分探索）。16 MiB は、最適化しないビルドで約 20 % の余裕を残し、本番の段のスレッド（64 MiB）より小さいので、枠が大きくなる退行を捕まえられる。
