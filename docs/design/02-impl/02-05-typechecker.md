# 型検査器

## 目的と範囲

制約生成と単一化、型クラス解決と辞書挿入、エフェクト検査。

本章は、初回リリース版（[ロードマップ](../00-overview/00-03-roadmap.md)）と、その後に加えた幅付きの数の型検査を定める。対象は、宣言の検査、定数の検査と評価、型とエフェクトの推論、型クラスの制約の解決（どの辞書を渡すかの決定）、パターンマッチの検査（網羅性、選ばれない分岐、必ず照合するパターン）、リテラルの範囲の検査、`main` の検査、警告である。決めた辞書を引数として加える変換は、脱糖の段が行う（[中間表現と脱糖](02-06-ir-and-lowering.md)）。

## 前提

型とエフェクトの規則は[型システム](../01-spec/01-06-type-system.md)で、パターンの規則は[代数的データ型とパターンマッチ](../01-spec/01-05-data-types.md)で、リテラルの範囲と算術の警告は[基本型の意味論](../01-spec/01-04-types-basic.md)で、`main` の条件とエフェクトの宣言とハンドラの意味は[エフェクト](../01-spec/01-07-effects.md)で、`try` の規則は[エラー処理](../01-spec/01-09-errors.md)で、`with` の規則は[リソース管理](../01-spec/01-10-resources.md)で、タスクの集まりの規則は[並行処理](../01-spec/01-11-concurrency.md)で、定数式の形と属性は[構文](../01-spec/01-02-syntax.md)で定める。本章はそれを実装する方法を定める。

型検査器は、名前解決に誤りのないプログラムの AST と名前解決の表を受け取る（[名前解決とモジュール読込](02-04-resolver.md)、[パイプライン](02-01-pipeline.md)の「誤りが見つかったときの段の進め方」）。プログラムは、実行を始めるモジュールから import で辿れるすべてのモジュールと、読み込んだ標準ライブラリのソースからなる（[パイプライン](02-01-pipeline.md)）。

【方針】次の誤りと警告は、型検査の前に名前解決が扱う（[名前解決とモジュール読込](02-04-resolver.md)の「宣言の検査」）。型検査器はこれらを検査しない。

- 名前の種類の誤り（型を書く位置のエフェクト変数、`uses` の後のエフェクトでない名前など）と、名前の衝突（トップレベルの関数・定数・エフェクトの操作の名前の重なりを含む）
- 初回リリース版の `uses IO`。修正案として `uses IO.All` を示す（[エフェクト](../01-spec/01-07-effects.md)）
- 公開の契約の誤り（[名前・スコープ・モジュール](../01-spec/01-03-names-modules.md)の「公開（初回リリース版）」）
- 定数どうしの参照の循環と、型の別名の循環
- 上位の型クラスの関係の循環
- 実装の中の関数の名前が型クラスのメソッドと一対一に対応しないこと（メソッドの欠けと、宣言にないメソッド）と、一つの型クラスの中のメソッドの名前の重なり
- `match` の分岐のパターンの変数に、その位置で見える定数と同じ名前を付けた誤り（[代数的データ型とパターンマッチ](../01-spec/01-05-data-types.md)）
- 束縛の文の `bind` と `shadow` の書き分けの誤りと、ラムダの引数・`match` の分岐のパターンの変数・`handle` の節の引数・`with` の束縛が局所の名前を隠す誤り（[名前・スコープ・モジュール](../01-spec/01-03-names-modules.md)の「シャドーイング」）
- `main` の位置。名前解決は、実行を始めるモジュールのトップレベルの関数 `main` だけを入口として引き、その束縛を型検査器に渡す
- `@deprecated` を付けた宣言の参照の警告

【方針】次の誤りは、構文上の文脈だけで決まるので、構文解析器が報告する（[字句解析器と構文解析器](02-03-frontend.md)の「文脈の制限」）。型検査器はこれらを検査しない。

- `resume` を `handle` の節の中に直接書いていないこと（節の中のラムダと `lazy` の本体の中を含む）
- `lazy` の本体の中と、`match` の分岐のガードの中の `return` と `try`（内側の `lambda … end lambda` の本体の中を除く。その中のプレースホルダを含む呼び出しの呼ぶ関数と引数は、この例外に当たらない）
- 利用者のソースの `@builtin`、`@external` を付けない本体のない関数の宣言、組み込みの制約 `ordered`

## 仕様

### 検査の単位と手順

【決定】型検査は、プログラム全体を一つの単位として行う。宣言をプログラム全体で先に検査し、その後で関数の本体を一つずつ検査する。変わったモジュールだけを検査し直すインクリメンタルな処理は行わない（[パイプライン](02-01-pipeline.md)）。

【方針】型検査は次の順に行う。

1. 宣言の検査: すべてのモジュールの型の宣言、レコード、型の別名、エフェクトの宣言、型クラスの宣言、実装の宣言の頭部（型パラメータ、制約、対象）、関数のシグネチャ（標準ライブラリのソースの関数、型クラスのメソッド、実装のメソッドを含む）、定数の宣言の型、`main` を検査し、宣言の型を決める。
2. 型の要約: すべての型の宣言について、等値の型の要約と鍵の型の要約を求める（後述）。
3. 実装の検査: 実装の重なり、上位の型クラスの制約、実装のメソッドの型を検査する。
4. 定数の検査と評価: 定数式の型を検査し、値を求める。
5. 本体の検査: トップレベルの関数（標準ライブラリのソースの関数を含む）と、実装のメソッドの本体を一つずつ検査する。各本体の検査は、制約の生成、制約の解決、本体の後の検査の三段階からなる。

ある本体の検査の結果は、ほかの本体の検査に影響しない（[型システム](../01-spec/01-06-type-system.md)）。本体の検査で使う型変数と制約は本体ごとに作って捨て、大域に置かない（[パイプライン](02-01-pipeline.md)の「コンパイル済みプログラムと実行ごとの状態」）。

本体の文脈 `Body` は、宣言側のモジュールの ID を明示的に受け取る。関数・実装メソッド・定数では名前解決の束縛から引き、型クラスの制約の補助検査では呼び出し側の本体または実装の所属を渡す。内側の lambda・ガード・lazy は同じ文脈を使い、所属を変えない。理由: 本体の持ち主を表すノードの有無から所属を推測すると、定数や内側の式の扱いが分かれるためである。

本体内のノード番号の表 `BodyNodeMap` と局所束縛の表 `BodyBindingMap` は、実在する番号だけを `BTreeMap` に保持する。宣言ごとの `Scope` の型・エフェクトパラメータも `BodyBindingMap` に保持する。どちらもプログラム全体の番号を鍵とし、番号の昇順で走査する。理由: 全体の番号までの空き領域を本体・宣言ごとに確保・走査すると、小さな関数の数に対して費用が二乗で増えるためである。

型表の `AdtDef.extensible` は、`data`・レコード宣言の `@extensible` を反映する。指定のない宣言では `false` である。

標準の Result・Option の宣言には指定を許さない。解決済みの標準型の束縛番号で識別し、指定があれば型表へ登録する前に処理系の不具合として報告して検査を止める。利用者の同名の型にはこの制限を適用しない。理由: 失敗を伝播する標準型が閉じているという前提を、変更された標準ライブラリのソースにも適用するためである。

`CoverageView` を作る補助は、指定が真で本体と所属パッケージが異なる型の束縛番号を集める。パッケージの比較は名前解決の公開範囲と同じ `resolve::same_package` を使う。本体の後検査でこの集合を一度作り、`check_match`・`check_binding` と内部の有用性・重なり・覆っている選択肢の探索へ同じ参照を渡す。受理した属性は、この集合を通してソース照合と交換出力の両方へ反映する。

【決定】標準の `SourceLocation.here()` は、パイプラインが名前解決後・型検査前に通常のLocationレコードと三つのリテラルへ展開する。型検査器はその通常レコードを検査し、位置のための型やエフェクトの規則を追加しない。展開された定数も既存の定数の検査と評価を通す。

### 出力

【決定】`TypeckOutput.effective_effects` はトップレベル関数の束縛から、有効な最外側の効果行と元位置の表を引く。`EffectiveEffects.effects` は Scheme の効果と同じ正規化済み集合、`origins` は元の効果一つごとの集合・修飾名・span・ファイル由来かどうか、`wrote_io_all` は両リストのいずれかに IO.All を書いた印である。同じ効果を両方に書いた場合も元位置を両方残す。IO.All の元位置には展開した各効果を対応させ、Fail の元位置には別名展開後の失敗型を対応させる。元の `FnDecl.uses` と `Module.file_uses` は変更しない。

【決定】型検査器は AST を変更せず、ノード番号を鍵とする表を出力する（[パイプライン](02-01-pipeline.md)の「段と段の間のデータ」）。ただし、宣言の型の表と定数の値の表は、名前解決の束縛の番号を鍵とする。実装は束縛を作らないので、宣言の型の表の実装の頭部だけは、実装の宣言のノード番号を鍵とする（[名前解決とモジュール読込](02-04-resolver.md)の「束縛と表」）。実装の中のメソッドは束縛を作るので、束縛の番号を鍵とする。脱糖は、名前を使う箇所のノード番号から参照の表で束縛の番号を得て、宣言の型を引く。

| 表 | 鍵 | 値 | 使う段 |
|---|---|---|---|
| 呼び出しの対応 | 呼び出しのノード番号 | 直接呼び出しの解決済み束縛（パイプ・穴・間接呼び出しはなし）、パラメータの個数、明示引数のソース順に並べた宣言位置、パイプの位置 0 への挿入の有無、穴のソース順の名前（`CallPlan`） | 脱糖 |
| 式の型 | 式・パターン・束縛の文・引数のノード番号 | 型 | 脱糖 |
| 型の引数 | 多相な名前（トップレベルの関数、構成子、標準ライブラリの関数、エフェクトの操作、型クラスのメソッド、レコードの構築とフィールドを取り出す関数）を使う箇所のノード番号 | その使用で型パラメータとエフェクト変数を置き換えた型（型構成子を含む）とエフェクトの集合 | 脱糖（[コア計算と脱糖](../01-spec/01-12-core-calculus.md)の `[T̄; Ē]`） |
| 演算子の型 | 二項演算と単項演算のノード番号 | オペランドの型 | 脱糖（同 `⊕_T`） |
| 補間の型 | 文字列補間の `${e}` の e のノード番号 | e の型 | 脱糖（同 `str_T`） |
| ラムダのエフェクト | ラムダのノード番号（プレースホルダを含む呼び出しを含む） | ラムダの型のエフェクトの集合 | 脱糖 |
| 辞書の解決 | 型クラスの制約を持つ名前を使う箇所のノード番号と、その名前の制約の番号の組。実装の宣言のノード番号と、その型クラスの上位の型クラスの組 | 辞書の求め方（後述の「型クラスの制約の解決」） | 脱糖 |
| `try` の種類 | `try` のノード番号 | `Result` か `Option` か、と、`TryActionInfo::Return { ret }` または `Die { show, exit }` | 脱糖（同「関数の境界と `escape`」） |
| ハンドラの節 | `handle` のノード番号 | 節ごとの操作の束縛の番号、末尾で再開する節かどうか、Fail の節で固定したエラー型（通常節はなし）。`handled(H)` のエフェクトの集合 | 脱糖 |
| 宣言の型 | トップレベルの関数、標準ライブラリのソースの関数、構成子、定数、エフェクトの操作、型クラスのメソッド、実装のメソッド、レコードの構築とフィールドを取り出す関数の束縛の番号。実装の頭部は、実装の宣言のノード番号 | 型パラメータ（型構成子を表すものを含む）、エフェクト変数、制約、引数の契約名と型、戻り値の型、エフェクト。実装の頭部では、型クラス、対象、型パラメータの制約 | 脱糖 |
| 定数の値 | 定数の束縛の番号 | 定数の評価器が求めた値（後述の「定数の検査と評価」） | 脱糖、コード生成 |
| リテラルの値 | リテラルの式とリテラルのパターンのノード番号 | 型検査器が範囲を確かめて求めた値（`-n` の形は符号を含めた値） | 脱糖 |
| 範囲のパターンの両端 | 範囲のパターンのノード番号 | 両端の値 | 脱糖 |

【決定】構築器の宣言と直接操作は、通常の型表と別の`builders`・`builder_ops`へ記録する。宣言はBuilderId・BuilderKind・元の位置、操作は対象のBuilderId・種類・操作・通常引数のソース順を保持する。BuilderKindに対応する通常のTyは作らず、構築器の束縛と対象の名前をlocals/expr_typesへ載せない。呼び出しのラベルと個数は既存の契約検査へ渡し、対象の内部スロットを普通の式として推論しない。このスロットは外部へ出す型ではない。ListBuilderの明示された要素型は通常の型注釈の規則で検査してBuilderKind.Listに保持し、操作と対象の分類の不一致はE0464とする。

`TypeckOutput` のノード・束縛の表は、従来どおり全体番号を鍵とする密な `base::NodeMap`・`base::BindingMap` である。`Body::finish` は本体内の表に実在する要素だけを辿り、型とエフェクトを確定して同じ番号で全体の表へ移す。未登録の番号は欠けたままとし、番号を詰め直さない。

【決定】呼び出しの対応表は、引数の式を辿る順を変えず、脱糖が保存した値の参照を宣言順へ配置するために使う。位置引数の呼び出し、直接の構成子、プレースホルダとパイプの自動挿入にも対応表を記録する。名前付き引数の AST を検査する補助は、既知の契約への未知・重複・不足と、対応する引数型を検査する。未知・重複・不足がある呼び出しから引数型の制約を派生させない。名前付き引数の解析からこの検査へ接続し、対応が誤っている位置から型不一致を連鎖させない。理由: 各段で対応を再推測せず、検査した結果を脱糖へ渡すためである。

このほか型検査器は、型の宣言、型クラスの宣言、実装、エフェクトの宣言の表と、`main` の情報（束縛の番号と、戻り値の型が `Result[Unit, String]` か）を出力する。`main` の情報は、`main` を検査する経路で誤りがなかったときだけ出力する。

【方針】表に書く型には、推論に使った型変数を残さない。関数の本体の検査を終えた時点で決まっていない型変数は、次のように置き換える。どれも値の意味に影響しない（[型システム](../01-spec/01-06-type-system.md)の「型の推論と型注釈」）。

- 制約を持たない値の型の変数は `Unit` に置き換える。
- 制約を持たない型構成子の変数は、型引数を一つとる prelude の型 `Option` に置き換える。
- 決まっていないエフェクトの変数は空集合に置き換える。

制約（演算子の型の集まり、等値、鍵、型クラス、`try` の対象、リソース）を持つ型変数が決まっていなければ、置き換えずに誤りとする（後述の「本体の後の検査」）。

### 契約名と保留した呼び出し

【決定】`FnTy` と `Scheme` は、`params` と同じ長さで重複のない `param_names` を持つ。名前と順を型の等しさ・ハッシュ・名前付きの型表示に含める。宣言収集と型検査の出力確定で整形式を検査する。実装メソッドの利用者の契約名は、型クラスの宣言と位置ごとに比較し、辞書の内部引数を数えない。

【決定】推論では型・エフェクトとは別に契約変数を管理する。未確定の呼び出しには、ソース順の引数型、ラベルと位置、穴、自動挿入の情報を保存する。引数式はソース順に一度だけ検査し、契約が確定してから対応先への Flow を作る。通常の等しさ・Flow・型クラス・エフェクトと保留呼び出しの解決を、変化がなくなるまで反復する。最後まで未確定なら E0455 とし、正常な出力へ渡さない。エラー済みの子から推論診断を重ねない。

【決定】契約が既知の位置指定は、生成時に共通の対応の検査を行い、その位置で制約を加える。保留する位置指定の呼び出しでも、推論用の型変数は呼び出し位置のハンドラの節の範囲で作る。名前が未確定でも、一引数の位置指定では引数型と位置 0 の型を先に結んでよい。ただし契約名は確定せず、契約と個数の検査は保留する。理由: 自己適用の無限型と、節内で使える型変数の範囲を、契約名の推論とは別に検査するためである。

保留した呼び出しの結果を式文や本体の末尾で捨てる場合は、その結果の型が決まってから `Unit` との一致を調べる。値の破棄の E0416 を、呼ぶ関数型全体の不一致へ付け替えない。

【決定】対応付けは呼ぶ値の種類と関数型の契約を取得し、パイプの位置 0 を先に占め、ソース順のラベルを宣言位置へ対応させる。未知・重複を調べた後に未指定の位置を宣言順に求め、誤りのない場合だけ `CallPlan` を作る。`source_to_param` は明示引数と同じ長さ、`hole_names` は穴のソース順である。`direct_callee` はソースが名前の直接呼び出しである場合の関数の束縛IDであり、パイプ・穴・間接呼び出しでは `None` とする。直接の構成子は位置指定、構成子値は生成した契約名、レコード構成子値はフィールド名を使う。

穴の引数を脱糖で直接の値参照へ移しても、`source_to_param` と `hole_names` から穴を除かない。脱糖は穴と固定式の両方の値をこの対応へ渡す。固定式の評価順と穴のパラメータ名を保つ具体的な束縛方法は、[中間表現と脱糖](02-06-ir-and-lowering.md#脱糖)で定める。

### 宣言の検査

【決定】別名の準備後、ファイル単位の宣言の具体型と効果を、空の型・効果パラメータ環境で一度だけ検査する。各リストの重複を別々に検査し、`Module.decls` の直下の `Item::Fn` に限って個別の効果と集合として合併する。全関数の Scheme と NoFail を合併後に確定してから本体を検査する。入口・外部関数も有効な効果行を使い、元の AST の uses の有無だけでは判定しない。

【決定】合併後の失敗型が複数なら E0514 とし、追加元を主位置、個別の uses を補助位置とする。ファイルの宣言内の誤りは関数ごとに繰り返さない。ファイルに由来する E0506・E0812 では、そのファイルの宣言を一関数の修正範囲とする自動編集を出さない。

【方針】宣言の検査は、次の誤りを報告する。

- 型の宣言とレコード: 構成子がない、型引数の個数が合わない（[代数的データ型とパターンマッチ](../01-spec/01-05-data-types.md)）。値の型を書く位置に型引数を与えない型構成子や、型構成子を表す型パラメータをそのまま書いた（後述の「型の形」）。
- 型の別名: 型パラメータを右辺で使わない、与えた型引数の個数が型パラメータの数と違う、型パラメータを持つ別名に型引数を与えずに書いた（[型システム](../01-spec/01-06-type-system.md)の「型の別名（初回リリース版）」）。
- 関数のシグネチャ: 型引数の個数が合わない、エフェクト変数の規則（一つの `uses` に二つ以上のエフェクト変数、引数の型に現れないエフェクト変数、`uses` の中の重複。[型システム](../01-spec/01-06-type-system.md)）に反する。組み込みの制約を、関数・実装・メソッドの型パラメータ以外（型構成子を表す型パラメータ、型の宣言の型パラメータ、上位の型クラスの位置）に書いた。型クラスの制約の型クラスが、型パラメータの形（値の型か型構成子か）と合わない。
- エフェクトの宣言: 操作のシグネチャが、関数のシグネチャと同じ規則に反する。
- 型クラスの宣言: メソッドがない、型クラスの引数を引数の型にも戻り値の型にも含まないメソッドがある、上位の型クラスの引数の形（値の型か型構成子か）が合わない。
- 定数: 後述の「定数の検査と評価」。
- `main`: `check` と `run` の経路で、実行を始めるモジュールにない、または[エフェクト](../01-spec/01-07-effects.md)の「プログラムの入口」の条件を満たさない。初回リリース版の条件は、引数・型パラメータ・エフェクト変数を持たないこと、戻り値の型が `Unit` か `Result[Unit, String]` であること、エフェクトが `IO.All` を展開した集合、ネットワークのエフェクト、`Log` の和集合に含まれることである。利用者が宣言したエフェクトと `Assert.Check` を `main` の `uses` に書くと、この条件に反する。 `test` の経路では、`main` がなくてよい。あれば同じ条件で検査する（[利用者プログラムのテスト](../06-tooling/06-04-test-runner.md)）。
- `@test` を付けた関数: [利用者プログラムのテスト](../06-tooling/06-04-test-runner.md)の規則に反する。引数・型パラメータ・エフェクト変数を持つ、戻り値の型が `Unit` でも `Result[Unit, String]` でもない、`uses` に利用者が宣言したエフェクトを書いた、のいずれかである。

【方針】標準ライブラリの関数の型は、組み込みの関数（`@builtin` を付けた本体のない宣言）を含め、標準ライブラリのソースの宣言のシグネチャから読む。順序の比較演算子の型の集まりの制約は、標準ライブラリのソースに組み込みの制約 `ordered` として書いてある（`List.sort[T: ordered]` など。[型システム](../01-spec/01-06-type-system.md)の「標準ライブラリの関数の型」）。型検査器は、`ordered` を、集まり(α, 順序の比較演算子の型の集まり) の制約として扱う。

【方針】型の別名は、宣言の型と型注釈を内部の型に移すときに、右辺の型を型引数で置き換えて展開する。内部の型は、ソースに書いた型のノードを覚えておき、診断では書いた型（別名を含む）を示し、展開した型が書いた型と異なるときは展開した型を添える（[型システム](../01-spec/01-06-type-system.md)の「型の別名（初回リリース版）」）。

【決定】型の宣言を検査した後、すべての型の宣言について、[型システム](../01-spec/01-06-type-system.md)の「等値の型」の要約を求め、本体の検査の等値の型の判定に使う。

【方針】同じ手順で、「無条件に含む」とする型を `Float` だけにした要約（鍵の型の要約）も求め、鍵の型の判定に使う（[型システム](../01-spec/01-06-type-system.md)の「鍵の型（初回リリース版）」）。

### 実装の検査

【方針】実装の宣言について、次を検査する（[型システム](../01-spec/01-06-type-system.md)の「型クラス（初回リリース版）」）。

- 対象の形: 型構成子に相異なる型パラメータを並べた形か、型パラメータを持たない型でなければならない。関数の型は対象にできない。型構成子を引数にとる型クラスの実装では、対象は型引数の個数が合う型構成子の名前でなければならない。実装の型パラメータは、すべて対象に現れなければならない。
- 孤立した実装: 対象の形の検査で決めた対象の型構成子と、型クラスについて、`implement` を、型クラスを宣言したモジュールか、対象の型構成子を宣言したモジュールに書いていなければ誤りとする（[型システム](../01-spec/01-06-type-system.md)の「型クラス（初回リリース版）」）。モジュールは、束縛の番号が持つモジュールの ID で比べる。診断コードは型クラスの区分（`E07nn`）である。孤立した実装は、次の重なりの検査に加えない。理由: 重なりの誤りを孤立した実装の誤りから派生させないためで、特に標準ライブラリの型クラスを利用者が実装したとき、標準ライブラリの実装の位置に重なりの誤りを示さないためである。
- 重なり: 同じ型クラスと型構成子の組に、二つ以上の実装があれば誤りとする。対象の形が上の制限を満たすので、二つの実装が重なるのは、型クラスと対象の型構成子が同じときに限る。型検査器は、型クラスと型構成子の組から実装を引く表を作り、重なりを検査し、制約の解決に使う。
- 上位の型クラスの制約: 型クラス C の上位の型クラス S ごとに、`S[対象]` の制約を、実装の型パラメータの制約だけを使える制約として、後述の「型クラスの制約の解決」の手順で解く。解けなければ誤りとする。解いた辞書の求め方を「辞書の解決」の表に記録する。
- メソッド: すべてのメソッドを一度ずつ定義し、宣言にないメソッドを定義していないことは、名前解決が名前で検査済みである（[名前解決とモジュール読込](02-04-resolver.md)の「宣言の検査」）。各メソッドの型は、型クラスの宣言のメソッドの型の、型クラスの引数を対象で置き換えたものと等しくなければならない。ただし、エフェクトは宣言のエフェクトに含まれればよい（[型システム](../01-spec/01-06-type-system.md)の「エフェクトの包含」）。

### 定数の検査と評価

【決定】文字列補間は、先にすべての式を左から各一度評価し、その後に書式化と連結を行う。書式付きの各値は、実行時と同じ本体から出力の各片と全バイト数を求める。全長の論理上限、`usize` への変換、共有予算を確かめた後に文字列を確保する。書式なしの数の変換に使う128バイトの見込みを、書式付きの出力には使わない。最終の連結も全長を求めて予算を検査してから一度だけ確保する。

【方針】定数の宣言は、次の順に検査する。

1. 形の検査: `=` の右辺が、[構文](../01-spec/01-02-syntax.md)の「定数（初回リリース版）」の定数式の形でなければ誤りとし、引数のない関数として書く方法を修正案として示す。呼び出してよい関数（`Map.fromList` など）は、綴りではなく名前解決が決めた束縛で `Benitoite` の名前空間のどの関数かを照合する。宣言の型は、型パラメータを含まない。
2. 型の検査: 定数式を、関数の本体と同じく制約の生成と解決で検査する。エフェクトの受け先（後述）は空集合であり、定数式の型を宣言の型と等しくする（[型システム](../01-spec/01-06-type-system.md)の「定数の型（初回リリース版）」）。定数を参照する箇所の型は宣言の型なので、各定数は独立に検査できる。
3. 評価: 型の検査を通った定数の値を、定数の評価器で求める。

【方針】定数の評価器は、型の付いた AST の定数式を直接評価する、型検査の段の中の評価器である。基本型の演算、文字列補間の変換、`Map.fromList`・`Set.fromList` は、実行時と同じ規則で計算し、同じ式の値を実行時の値と一致させる。実行時の組み込みの関数はヒープの値を受け取るので、評価器はそれを直接は呼ばない。そのかわり、値の表現によらない計算（`Decimal` の算術と文字列への変換、`Float` の文字列への変換、鍵の順序のうち基本型の値どうしの比較）を、基本のデータ（整数、浮動小数点数、`Decimal` の表現、文字列の断片）の上の Rust の関数として共有のモジュールに置き、評価器と実行時の組み込みの関数の両方がそれを呼ぶ。構成子の値やリストを辿る部分は、値の表現ごとに評価器と組み込みの関数がそれぞれ持ち、同じ規則で書く。評価器は、次のように動く。

- 各定数を一度だけ評価し、値を覚える。定数の名前を評価するときは、その定数の値を先に求める。定数どうしの参照は循環しない（名前解決が検査済み）ので、評価は終わる。
- 計算が実行時エラーの条件（`Integer` の溢れ、0 による除算など。[基本型の意味論](../01-spec/01-04-types-basic.md)）に当たれば、型検査の誤りとし、その条件と、計算が失敗した部分式の位置を示す。
- `Map.fromList` の引数に同じ鍵の組が、`Set.fromList` の引数に同じ要素が二つ以上あれば、型検査の誤りとし、重なる鍵の位置を示す。同じかどうかは鍵の順序で判定する。
- 型の検査か評価に失敗した定数を参照する定数は、評価せず、誤りを重ねて報告しない。
- 一つの操作で作る文字列とリストの大きさを、作る前に、実行時と同じ上限（[ランタイム](02-09-runtime.md)の「一つの操作で作る値の大きさの上限」）で確かめる。加えて、定数の評価の全体で作る値の大きさの和を 64 MiB までとする（大きさは作った値のメモリの量を下回らないように見積もり、評価の途中で捨てた値も差し引かない）。上限か予算を超えれば型検査の誤りとし、どの上限を超えたかを示す。予算を超えたときは、それ以後の定数を評価しない。理由: `check` は利用者が実行を許可する前に LLM の書いたスクリプトを検査する段なので、実行時（ヒープに上限を設けない）より厳しく、検査そのものが資源を使い尽くさないようにするためである。大きな値は、引数のない関数として書けば実行時に作れる。

【決定】重複の誤りと警告に示す鍵は、`Show.show` と同じ形で書き、文字列と文字を引用符付きで逃がす。表示は末尾の `…` を含めて 4,096 バイトまでとし、UTF-8 の文字の途中では切らない。理由: 鍵の構造を示しながら、改行で見出しが割れることと、長い値が診断を際限なく長くすることを防ぐためである。

求めた値は「定数の値」の表に書く。値は、基本型の値、文字列、構成子（レコード、`Pair`・`Triple` を含む）を適用した値、リスト、マップ、集合のいずれかを組み合わせたものである。

【決定】定数の評価器も新しい七種を区別し、幅付きの整数の算術は範囲を検査し、`Float32` の生成と各演算の結果は `f32` に丸める。幅ごとの算術を共有の数値の計算の関数で行い、補間は実行時と同じ表示の規則を使う。あふれと整数の除数 0 は `const` 内では E0435、通常の式の定数部分では後述の W0401・W0402 の対象とする。符号なしの負値になる減算もあふれとして扱う。理由: 同じ式の実行時の結果と静的な評価を一致させ、確実に失敗する定数を実行へ渡さないためである。

【方針】定数の評価器は、本体の中の算術の警告（後述の「警告」）にも使う。そのために、定数式の形の部分式に加えて、後述の「警告」の算術の確実な誤りの対象とする組み込みの関数（`Integer.floorDivide`・`Integer.absolute` など）の呼び出しも評価できるようにする。警告のための評価は、警告を調べる式ごとに定数と同じ大きさの予算を持ち、上限か予算に当たったら、警告も誤りも出さずにその評価をやめる。

### 型とエフェクトの表現

`Body` の推論中の型・エフェクト・呼び出しと節の補助情報は、前述の本体内の疎な表に保存する。`check_type_limits` はその表に実在する型だけを番号順に再検査する。型クラスの補助検査も、同じ表から節の型パラメータと操作の位置を引く。

【決定】幅付きの数は、組み込みの型の番号で区別する。組み込みの正の名前と別名は名前解決で同じ番号に結び付け、推論に別の型として持ち込まない。型の診断には、数の型の名前の表の表示名を使う（[名前解決とモジュール読込](02-04-resolver.md)の「標準ライブラリのソースの持ち方」）。型クラスの実装の重なりも同じ番号で判定するため、例えば `Integer` と `Integer64` に同じ型クラスを別々に実装することはできない。

【方針】推論の中で扱う型は、次のいずれかである。

| 型 | 内容 |
|---|---|
| 名前の型 | 型構成子と型引数。型構成子は、基本型（`Byte`・`Decimal` を含む）、`List`・`Map`・`Set`・`Bytes`、代数的データ型（prelude の `Option`・`Result`・`Pair`・`Triple` など、レコードを含む）、組み込みの不透明型（`IOError`・`NetworkError`・`Reference`・`Lazy`・`Task`、リソースの型）と、標準ライブラリのモジュールが宣言する不透明型（`Regex.Pattern`・`Regex.Match`・`Random.Generator`。組み込みの不透明型と同じく扱う）と、外部の型である。外部の型は専用の型構成子で宣言の束縛の番号を指し、型引数を持たず、等値の型ではない |
| 関数の型 | 引数の型の並び、戻り値の型、エフェクト |
| 型パラメータ | 検査している関数（実装のメソッドでは、実装とメソッド）で宣言した型パラメータと、`handle` の節の中の操作の型パラメータ。ほかの何とも等しくない。宣言した組み込みの制約と型クラスの制約を持つ（操作の型パラメータは組み込みの制約だけを持つ） |
| 型構成子の適用 | `F[A]`。F は型構成子を表す型パラメータか、型構成子の変数 |
| 型変数 | まだ決まっていない型。値の型の変数と、型構成子の変数がある。制約（演算子の型の集まり、等値、鍵、`try` の対象、リソース）を持ちうる |
| 誤りの型 | 誤りを報告した箇所の型。どの型とも等しいものとして扱う（後述の「誤りの報告と検査の継続」） |

【方針】型の形は、値の型と、型引数を一つとる型構成子の二つである（[型システム](../01-spec/01-06-type-system.md)の「高カインド型（初回リリース版）」）。宣言の検査は、型を書く位置ごとに求める形と書いた型の形が合うかを検査する。単一化は次の規則を加える。

- `F[A]` と `D[B1, …, Bn]` を等しくするときは、D のとる型引数の個数が 1 の場合に限り、F を D と等しくし、A と B1 を等しくする。それ以外は誤りとする。
- `F[A]` と `G[B]` を等しくするときは、F と G、A と B をそれぞれ等しくする。
- `F[A]` と関数の型・基本型を等しくするときは誤りとする。

【方針】エフェクトは、確定した要素の集合と、まだ決まっていないエフェクトの変数（高々一つ）との組で表す。確定した要素は、エフェクトの名前と、検査している関数で宣言したエフェクト変数である。エフェクトの名前は、宣言したモジュールの同一性と名前の組で識別する。宣言したエフェクト変数は、ほかの何とも等しくない一つの要素として扱う（[型システム](../01-spec/01-06-type-system.md)）。一つの `uses` に書けるエフェクト変数は一つまでであり、多相な名前の置き換え、ラムダ、呼び出し、流れ込む制約、`handle` が作るエフェクトも、それぞれ変数を一つだけ持つので、変数が二つ以上になることはない。

【方針】`uses` に書いた `IO.All` は、宣言の型と型注釈を内部の型に移すときに、`State` と `Benitoite.IO` の下のすべての組み込みのエフェクトの名前の集合に置き換える。この集合は処理系が組み込みの表として持ち、どの標準ライブラリのモジュールを読み込んだかによらない。ネットワークのエフェクトと `Assert.Check`・`Log` は含めない。宣言の一番外の `uses` に `IO.All` を書いたかを W0501 のために覚える。診断で型を示すときは、`IO.All` の 10 個をすべて含む集合を `IO.All` とまとめて示す。

型変数は、単一化のために union-find で表す。

【決定】確定した `EffectSet` は名前・宣言した行・型付きの失敗の列を持つ。失敗の列は型の固定順序で整列し、重複を除く。型と効果の同時代入は Fail 内部へも再帰する。推論の `IEffect` は失敗の型を推論中の型で保持し、効果の包含の解決と同時に不変の型として結ぶ。確定後の純粋な集合の和は、内部の上限の複数 Fail を消さない。

【決定】`Scheme.no_fail` はシグネチャの全体から計算した行の番号を保存する。具体化した行の像について、Fail がなく、その中の行も呼び出し側の署名の NoFail に含まれることを検査する。本体から行の条件を補わない。式の結果の型とソースの効果を保存し、解決後に具体化後の単一 Fail と NoFail を検査する。Fail の handle は、本体の残りの効果と節の出力を別の推論変数に置き、節の再 raise を本体の上限へ入れない。

【決定】標準の Fail と raise は標準専用の宣言表で定め、名前解決、型検査、Skill の生成が同じ表を読む。Fail の節の情報には、非再開の種類を示す固定エラー型を保存する。操作の型引数のうち T だけを剛な型にし、E は本体と節の制約から固定する。未確定の E は既定値で消さず E0517 とする。

### 制約の種類

以下の試行(A, R, τ) は、本番で受理する裸の try と明示した Return の経路である。Die の制約は「制約の解決」の末尾で区別して定める。

【決定】型検査器は、関数の本体を辿って制約を集め、その後で解く。理由: 解く順序を選べるので宣言や型注釈から生じた制約を先に解いて宣言に合わない使い方の側を誤りとして報告でき、各制約が理由を持つので診断に「何が期待され、なぜ期待されたか」を示せるからである。エフェクトの包含は集合の包含関係であり型の単一化だけでは扱えないが、制約として集めれば型の制約と同じ枠組みで扱える。制約は次の種類である。

| 制約 | 意味 |
|---|---|
| 等しい(A, B) | 型 A と B は等しい |
| 流れ込む(A, B) | 型 A の値を、型 B が求められる位置に使う。A と B の最も外側がともに関数の型なら、引数の型と戻り値の型は等しく、A のエフェクトは B のエフェクトに含まれる（[型システム](../01-spec/01-06-type-system.md)の「エフェクトの包含」）。それ以外なら A と B は等しい。解き方は「制約の解決」で定める |
| 集まり(A, S) | 型 A は、型の集まり S のどれかである。S は、演算子の型付けの集まり、文字列補間の集まり（[型システム](../01-spec/01-06-type-system.md)の「演算子の型付け」）、標準ライブラリの関数の型が持つ演算子の型の集まりである |
| 等値(A) | 型 A は等値の型である |
| 鍵(A) | 型 A は鍵の型である |
| 型クラス(C, τ) | 型または型構成子 τ は、型クラス C を実装している |
| 試行(A, R, τ) | `try` の対象の型 A は `Result` か `Option` であり、最も内側の関数かラムダの戻り値の型 R がそれに合い、`try` の式の型は τ である |
| リソース(A) | 型 A はリソースの型である |
| 含まれる(X, Y) | エフェクト X は、エフェクト Y に含まれる |

【決定】流れ込む制約を生成する位置は、関数の呼び出し（メソッドの呼び出しを含む）の各引数、リストリテラルの各要素、`if` の各分岐と `match` の各分岐の本体、束縛の文の型注釈、`return` の式と最も内側の関数かラムダの戻り値の型である（[型システム](../01-spec/01-06-type-system.md)の「エフェクトの包含」）。

【方針】これに、リストリテラルの展開の式、レコードの構築と更新の各フィールドの式（[代数的データ型とパターンマッチ](../01-spec/01-05-data-types.md)の「レコード（初回リリース版）」）、`handle` の本体と各節の本体、`resume` の引数と節の操作の戻り値の型を加える（[型システム](../01-spec/01-06-type-system.md)の「エフェクトの包含」）。ほかの位置の型の一致は、等しい制約で表す。関数とラムダの戻り値の型は、`return` の式の流れ込む制約で扱い、本体のブロックの型は `Unit` と等しくする（後述の「制約の生成」の「関数の本体」と「ラムダ」）。ラムダの戻り値の型注釈は、制約を介さずそのまま R' になる。

各制約は理由を持つ。理由は、制約が生じた位置の span と、生じた事情の種類（「f の第 2 引数」「if の二つの分岐」「束縛の文の型注釈」など）と、関連する位置（引数の型を宣言した箇所など）からなる。理由は、制約が解けなかったときの診断に使う。

### 制約の生成

【決定】数のリテラルの型は接尾辞で決め、接尾辞がなければ従来どおり `Integer` または `Float` とする。文脈から別の幅へ変えず、二項演算の両辺に同じ型を求める。新しい整数の数字列はまず `u64` の大きさとして読み、符号付きの直接の負号は `i128` で符号を適用してから目的の幅へ検査する。`Float32` は字面から直接 `f32` へ丸め、無限大になるリテラルを拒否する。範囲外は静的な誤りであり、求めた値は幅ごとの `ConstValue` として「リテラルの値」の表に記録する。理由: 符号付きの最小値と `u64` の上半分を受理し、後の脱糖で幅と丸め済みの値を保つためである。

直接の負号と括弧を挟む負号を区別する。`-128s8` は符号込みで範囲を検査して `Integer8` の −128 とし、`-(128s8)` は内側の正のリテラルが範囲外になる。符号なしの単項の負号は零にも許さない。新しい七種と `Byte` の定数・範囲パターンは許さず、`s64` のパターンは既存の `Integer` のパターンとして扱う。

演算子の型の集まりは、二項の `+`、二項の `-`・`*`、単項の `-`、整数の `div`・`mod`、`/` を分けて持つ。新しい整数六種を二項算術と整数除算に、`Float32` を二項算術と `/` に加え、単項の負号の集まりには新しい符号付き整数三種と `Float32` を加える。`Byte` は算術の集まりに入れない。新しい七種は順序比較と補間の集まりに加え、等値の制約も満たす。鍵の制約には新しい整数六種だけを加え、`Float32` を入れない（[型システム](../01-spec/01-06-type-system.md)の「演算子の型付け」「鍵の型（初回リリース版）」）。

【方針】本体を辿り、構文ごとに次の制約を生成する。E は、いま辿っている位置のエフェクトの受け先であり、呼び出しなどのエフェクトは E に含まれなければならない。関数の本体では宣言した `uses` の集合、ラムダの本体では後述のラムダの E'、`handle` の本体と節では後述の εM と εh、`lazy` の本体とガードでは空集合である。R は、最も内側の関数かラムダの戻り値の型であり、`lazy` の本体とガードの中（内側のラムダの本体と、プレースホルダを含む呼び出しの呼ぶ関数と引数を除く）では「なし」である。「なし」の位置の `return` と `try` は、構文解析器が誤りにしてある（前述の「前提」）。ガードと `lazy` の本体の中（内側の `lambda … end lambda` の本体の中を除く）のプレースホルダを含む呼び出しの呼ぶ関数と引数では、R は展開後のラムダの戻り値の型だが、そこの `return` と `try` も構文解析器が誤りにしてある。`fresh` は新しい型変数、またはエフェクトの変数である。

| 構文 | 生成する制約と型 |
|---|---|
| 局所の束縛の名前 | 束縛したときの型をそのまま使う（多相にしない） |
| 定数の名前 | 宣言の型。定数は多相でない |
| 多相な名前 | 宣言の型の型パラメータを `fresh` の型変数（型構成子を表す型パラメータは型構成子の変数）に、エフェクト変数を `fresh` のエフェクトの変数に置き換える。型パラメータの制約は、置き換えた型変数についての制約（型クラスの制約は型クラス、`equality` は等値、`key` は鍵、`ordered` は順序の比較演算子の型の集まりについての集まり）として加える。置き換えを「型の引数」の表に記録する |
| エフェクト L の操作の名前 | 多相な名前と同じく置き換える。型のエフェクトは {L} である |
| 型クラスのメソッド `C.m` | 型クラスの宣言のメソッドの型の、型クラスの引数を `fresh` の α（型構成子を引数にとる型クラスでは型構成子の変数）に置き換え、メソッドの型パラメータとエフェクト変数を多相な名前と同じく置き換える。型クラス(C, α) と、メソッド自身の制約を加える |
| リテラル | [型システム](../01-spec/01-06-type-system.md)の「式と文の型」の型。`Decimal` のリテラルは `Decimal` |
| 呼び出し `f(n1: a1, …, nn: an)` | 等しい(f の型, `function(n1: β1, …, nn: βn) -> ρ` エフェクト ε)。各ソース引数 ai を契約名で宣言位置 j に対応付け、流れ込む(ai の型, βj)。対応と契約が未確定なら保留する。含まれる(ε, E)。型は ρ。β・ρ・ε は `fresh` |
| プレースホルダを含む呼び出し | [構文](../01-spec/01-02-syntax.md)の規則で展開したラムダとして扱う。呼び出す関数とプレースホルダでない引数の式は、展開したラムダの本体の中にあるものとして辿る |
| パイプ `x \|> e` | [構文](../01-spec/01-02-syntax.md)の規則で展開した呼び出しとして扱う。`e` が括弧の式なら規則 2 で `(e)(x)` とし、規則 1 のプレースホルダの有無は `e` の呼び出しの直接の引数だけで判定する |
| 二項演算・単項演算 | [型システム](../01-spec/01-06-type-system.md)の「演算子の型付け」に従い、オペランドの型を `fresh` の α と等しくし、集まり(α, S) または等値(α) を加える。α を「演算子の型」の表に記録する |
| 文字列補間 | 各 `${e}` について、集まり(e の型, 文字列補間の集まり)。`${e:spec}` は種類と符号・ゼロ埋めから型の集まりを選ぶ。e の型を「補間の型」の表に記録する。型は `String` |
| リストリテラル | 各要素について流れ込む(要素の型, α)。展開の要素 `..e` については流れ込む(e の型, `List[α]`)。型は `List[α]` |
| レコードの構築 `R(g1: e1, …)` | R の型パラメータを `fresh` の ᾱ に置き換え、各フィールドについて流れ込む(式の型, フィールドの型[ᾱ])。書かないフィールド、宣言にないフィールド、二度書いたフィールドは誤りとする。型は `R[ᾱ]` |
| レコードの更新 `R(..e, g1: e1, …)` | 等しい(e の型, `R[ᾱ]`)（ᾱ は `fresh`）。各フィールドについて流れ込む(式の型, フィールドの型[ᾱ])。型は `R[ᾱ]` |
| `if` | 等しい(条件の型, `Boolean`)。各分岐について流れ込む(分岐の型, α)。`else` がなければ等しい(分岐の型, `Unit`) で、型は `Unit` |
| `match` | 各分岐の各選択肢について等しい(パターンの型, 対象の型)。一つの分岐の選択肢が束縛する同じ名前の変数の型を等しくする。ガードは、E を空集合として辿り、等しい(ガードの型, `Boolean`)。各分岐の本体について流れ込む(本体の型, α) |
| ブロック | 最後でない式文について等しい(式の型, `Unit`)。式文が名前と式の比較 `x = e` で、型が `Boolean` のときは、診断は変数を書き換えられないことと、`shadow x <- e` で同じ名前を束縛し直す書き方を示す（[構文](../01-spec/01-02-syntax.md)の「演算子の優先順位と結合性」）。束縛の文 `bind x: T <- e`（`shadow` も同じ）は流れ込む(e の型, T) で、x の型は T。型注釈がなければ、x の型は e の型とする。`bind p <- e`（p が変数と `_` 以外のパターン）は等しい(p の型, e の型)。ブロックの型は、最後の文が式ならその型、束縛の文なら `Unit`、文がなければ `Unit` |
| `return e` | 流れ込む(e の型, R)。型は `fresh` |
| `try e` | 試行(e の型, R, τ)。型は τ（`fresh`） |
| `with x1 = e1, …, xn = en do B end with` | 各 ei についてリソース(ei の型)。xi の型は ei の型。含まれる({State}, E)。型は B のブロックの型 |
| `lazy B end lazy` | B を、E を空集合、R をなしとして辿る。型は `Lazy[B のブロックの型]` |
| `handle B with case … end handle` | T・εM・εh は `fresh`。B を、E を εM として辿り、流れ込む(B のブロックの型, T)。含まれる(εM, handled(H) と εh からなるエフェクト)。各節は、操作の引数を操作の引数の型（操作の型パラメータは、節ごとのほかの何とも等しくない型パラメータに置き換える）に束縛し、E を εh として辿り、流れ込む(節の本体の型, T)。含まれる(εh, E)。型は T |
| `resume(v)` | 流れ込む(v の型, 節の操作の戻り値の型)。型は、囲む `handle` の T |
| ラムダ | 引数の型は型注釈か `fresh`。本体の E' は、`uses` を書いていればその集合、書いていなければ `fresh` のエフェクトの変数。本体の R' は、戻り値の型注釈があればその型、なければ `fresh`。等しい(本体のブロックの型, `Unit`)。本体のブロックが必ず抜けなければ（[型システム](../01-spec/01-06-type-system.md)の「必ず抜ける文」）、等しい(R', `Unit`)。型は実際のパラメータ名を保持する `function(名前: 引数の型) -> R'` エフェクト E' |
| 関数の本体 | R は宣言した戻り値の型、E は宣言した `uses` の集合。等しい(本体のブロックの型, `Unit`)。R が `Unit` でなく、本体のブロックが必ず抜けなければ誤りとする |
| ワイルドカードのパターン | 型は `fresh` |
| 変数のパターン | 型は `fresh`。変数の束縛の型もそれとする |
| リテラルのパターン | リテラルの式と同じ型（`-n` の形は `Integer`）。整数リテラルの範囲は、`-n` の形なら符号を含めた値で検査する（`-9223372036854775808` は範囲に収まる） |
| 範囲のパターン | 型は両端のリテラルの型。両端の型が違う、`Integer` と `Character` のどちらでもない、下端が上端より大きい範囲は誤りとする |
| `()` のパターン | 型は `Unit` |
| 構成子のパターン | 構成子の宣言の型を多相な名前と同じく置き換え、引数のパターンの型と構成子の引数の型を等しくする。型は構成子の型。パターンの個数が構成子の引数の個数と違えば誤りとし、引数のパターンはすべて型を誤りの型として辿る。引数を持たない構成子に括弧を書いたとき（`Tree.Leaf()`）は、括弧を取り除くよう示す（[代数的データ型とパターンマッチ](../01-spec/01-05-data-types.md)） |
| レコードのパターン | フィールドを宣言の順に並べた構成子のパターンとして扱い、書かないフィールドはワイルドカードとする。宣言にないフィールドと、二度書いたフィールドは誤りとする |
| リストのパターン | 型は `List[α]`（α は `fresh`）。各要素のパターンの型は α、`..rest` の rest の型は `List[α]` |

`handled(H)` は、一つ以上の操作を持ち、そのすべての操作の節を `handle` が持つエフェクトの集合である（[コア計算と脱糖](../01-spec/01-12-core-calculus.md)の「ハンドラ」）。`State` は操作を持たないので含まれない。含まれる(εM, handled(H) と εh からなるエフェクト) は、[コア計算と脱糖](../01-spec/01-12-core-calculus.md)の C-Handle の前提 `εM ⊆ ε ∪ handled(H)` を、後述の最小の解を求める手順でそのまま解ける形にしたものである。εM の要素のうち handled(H) にないもの（エフェクト変数を含む）が εh に加わり、`handle` の式のエフェクトになる。

【方針】呼び出しの関数の式が、引数を持たない構成子を指す名前（`Tree.Leaf`、`Option.None`）で、引数が 0 個のとき（`Tree.Leaf()`）は、関数でない値を呼んだ誤りの代わりに、引数を持たない構成子に括弧を付けた誤りとし、括弧を取り除くよう示す（[代数的データ型とパターンマッチ](../01-spec/01-05-data-types.md)）。構成子の呼び出しの引数の個数の誤りは、呼び出しの等しい制約が関数の型どうしの引数の個数の違いとして報告する。定数の名前を呼び出したとき（`maxRetries()`）は、括弧を外す書き方を示す（[構文](../01-spec/01-02-syntax.md)の「定数（初回リリース版）」）。

ラムダの式そのもののエフェクトは空集合なので、ラムダの本体の中の呼び出しの含まれる(ε, E') は、外側の本体の E に影響しない（[型システム](../01-spec/01-06-type-system.md)の「式のエフェクト」）。`lazy` の値を作る式のエフェクトも空集合である。

【方針】整数リテラルと浮動小数リテラルの範囲は、制約を生成するときに検査する。単項の `-` を整数リテラルに直接適用した式は、符号を含めた値で判定する（[基本型の意味論](../01-spec/01-04-types-basic.md)）。

### 書く位置の検査

【方針】制約を生成しながら、名前が何を指すかで決まる次の書く位置の規則を検査する。構文上の文脈だけで決まる `resume`・`return`・`try` の位置は、構文解析器が検査済みである（前述の「前提」）。

- `TaskGroup.open` は、`with` の束縛の式として呼び出す形（`with group = TaskGroup.open() do`）でだけ書ける。それ以外の位置の呼び出しと、関数の値としての参照は誤りとし、`with` で束縛する書き方を修正案として示す。`TaskGroup.open` かどうかは、綴りではなく束縛の番号で照合する。
- `handle` の節の `case` には、エフェクトの操作を書かなければならない。ふつうの関数と、`State` を型に持つ組み込みの関数（可変のセルとタスクの集まりの関数、`Task.await`、リソースを解放する関数）を書くと誤りとする（[エフェクト](../01-spec/01-07-effects.md)）。宣言したモジュールが Prelude または Stdlib で、型に `State` を含む場合だけ、`State` に操作がなく処理できないことを注記する。
- 一つの `handle` に同じ操作の節を二つ書くと誤りとする。同じ操作かは、書いた綴りではなく操作の束縛の番号で比べる（[エフェクト](../01-spec/01-07-effects.md)）。

【方針】`handle` の各節について、末尾で再開する節かどうかを構文から判定し、「ハンドラの節」の表に記録する。末尾で再開する節とは、節の本体のどの終わり方も末尾位置の `resume(v)` であり、節の中（内側のラムダの中を除く）に `return` と失敗を返す `try`（裸または `or return`）がない節である（[並行処理](../01-spec/01-11-concurrency.md)の「タスクとハンドラ」）。末尾位置は[評価意味論](../01-spec/01-08-evaluation.md)の「末尾呼び出し」の定め方に従う。この判定は誤りを生じない。

【決定】構築器の分類注釈とnewの組は、名前解決が確認した専用の宣言表から検査する。宣言と直接操作自体はStateの包含制約を作らず、普通の引数の型と効果は通常の制約で照合する。名前解決では通常変数式を作る前に対象を識別し、lambda・lazy・節・穴のある普通のCallの子を辿る前に捕捉境界を切り替える。部分適用の型検査も、呼び出し先と固定引数を生成ラムダのエフェクト文脈で検査する。理由: 戻り値の型だけでは、局所構築器の持ち出しを検出できないためである。

### 制約の解決

【方針】集めた制約は、次の順に解く。

1. 宣言と型注釈から生じた制約を解く。対象は、`return e` の流れ込む(e の型, R)（R は最も内側の関数かラムダの戻り値の型。戻り値の型注釈のないラムダの R も含む）と、束縛の文の型注釈から生じた流れ込む制約である。ラムダの引数の型注釈と戻り値の型注釈は、制約を介さずそれぞれ引数の型と R' になる。ラムダの `uses` から生じる含まれる制約は、手順 3 で解く。宣言に合わない使い方の側を誤りとして報告するために、これらを先に解く。
2. 残りの型の制約（等しい、流れ込む、集まり、等値、鍵、試行、リソース）を解く。
3. エフェクトの制約（含まれる）を解く。
4. 型クラスの制約を解く（後述の「型クラスの制約の解決」）。

同じ手順の中の制約は、生成した順に解く。制約は、本体を先頭から辿り、各構文の子を左から右に辿り終えた後にその構文の制約を生成する。関数の本体の制約は、本体を辿り終えた後に生成する。

【決定】書式付き補間も `OneOf` の制約を使う。種類省略の幅・寄せは `TySet::INTERP`、整数の種類は Byte を含む `FORMAT_INT`、`f` は `FORMAT_FIXED`、`s` と `c` は各一型とする。種類省略の符号・ゼロ埋めは `FORMAT_NUMBER` とし、`s`・`c` と符号・ゼロ埋めの併用は空集合となる。型変数を具体化してから適合を検査し、未確定なら E0407、型パラメータや既知の不適合な型なら E0468 を報告する。書式と値の元位置を制約の理由に保持し、具体化済みの型を既存の `interp_types` へ記録する。

診断済みの原因から型全体が未確定になった値は、その由来を保持して、値の型に依存する書式の不適合を抑える。どの型にも適合しない空集合の書式は、回復中も E0468 を報告する。部分だけが未確定な `List[Error]` などは、既知の外側と書式の不適合を報告する。束縛自身の明示契約と、正常な関数が宣言した結果型も適合の根拠に残す。利用側の注釈や引数型から回復変数へ流し込まれた型は根拠にしない。

適合した各式の型は `interp_types` に保持し、脱糖が対応する内部の書式化頭を選ぶ。定数評価も解析済みの書式を受け取り、実行時と同じ `base::format` の本体で書式化する。

【決定】効果の包含制約は登録順の列を正本とし、関数型の単一化で加える重複の照合には私有の構造キーの索引を使う。キーは生の推論変数番号、関数の契約名、Fail列の順、固定の効果、理由の種類と全欄、元位置、型の対を保持し、既存の制約の等号と同じ意味にする。通常の包含制約は重複も登録順に保持する。キーに正規化後の可変の推論結果を使わない。理由: 理由や使用位置の異なる制約をまとめず、重複の線形探索を除くためである。

【決定】効果の伝播は登録番号の待ち行列で行い、一巡のFailの処理では開始時の番号を一度ずつ登録順に処理する。列全体を複製せず、その番号の一項だけを複製する。次に通常の行の効果を登録順に伝え、行またはFailの伝播が変わった場合は全登録番号を次の巡へ再投入する。毎巡すべてを再投入して巡ごとの処理の数は変えず、列全体の複製と重複の線形探索を除く。巡の途中に加わった制約のFailは次の巡で処理する。理由: 単一化による型・契約名・行の変更の依存を部分的に追跡すると、診断を確定する順序が変わるおそれがあるためである。

【決定】Failの型を確定するときは、入口で一度、現在の推論状態に従って型変数・型構成子・契約名を置き換える（zonk）。正規化済みの型引数・関数の引数と戻り値を辿って確定型を作り、子の部分木を再びzonkしない。zonkが正規化せずに保持する潜在効果は、通常の効果の確定を通し、その中の各Fail型の入口で正規化する。未知型・誤りの型・未確定の型構成子は回復用のUnitとし、剛な型と型パラメータは保持する。可変の推論状態をまたいで確定結果を記憶しない。理由: 同じ部分木の反復した正規化を避け、型の深さに伴う確定の費用を減らすためである。

【方針】型の制約は、次のように解く。

- 等しい: 単一化（unification）する。型変数を、それ自身を含む型と等しくする必要が生じたら誤りとする（出現検査、occurs check）。関数の型どうしの単一化では、引数の個数が違えば誤りとし、エフェクトは含まれる制約を両方向に加える。型構成子の適用は、前述の「型とエフェクトの表現」の規則で単一化する。
- 流れ込む(A, B): 両辺をいまの単一化の状態で置き換えてから、最も外側の形で次のように分ける。
  - 両辺とも関数の型: 引数の個数が違えば誤りとする。対応する引数の型を単一化し、戻り値の型を単一化し、含まれる(A のエフェクト, B のエフェクト) を加える。
  - A が関数の型で、B が型変数: B を、A と同じ引数の型と戻り値の型を持ち、エフェクトを `fresh` のエフェクトの変数 ρ とした関数の型と等しくする。含まれる(A のエフェクト, ρ) を加える。
  - A が型変数で、B が関数の型: A を、B と同じ引数の型と戻り値の型を持ち、エフェクトを `fresh` のエフェクトの変数 ρ とした関数の型と等しくする。含まれる(ρ, B のエフェクト) を加える。
  - 両辺とも型変数: どちらかが決まるまで後に回す。
  - どちらかが誤りの型: 満たされたものとする。
  - それ以外（一方が関数の型でない型で、他方がそれと異なる形か型変数）: 等しいとして単一化する。

  後に回した制約は、手順 2 の制約を一通り解いた後に、生成した順に解き直す。解き直して一つでも片付いた制約があれば、残りをもう一度解き直す。片付くものがなくなったら、残りを等しいとして単一化する。

  この解き方では、関数の型が求められる位置に、エフェクトの違う関数が順序によらず流れ込める。例えば `[lambda() () end lambda, lambda() Console.writeLine("a") end lambda]` では、最初の要素で要素の型 α が関数の型 `function() -> Unit` エフェクト ρ に決まり、二つの要素のエフェクト（空集合と {Console.Write}）がそれぞれ ρ に含まれるという制約が生じて、ρ は {Console.Write} になる。要素の順序を入れ替えても同じである。
- 集まり・等値・鍵: 型変数に制約として付ける。型変数が決まったとき、または制約を持つ型変数どうしが等しくなったときに、[型システム](../01-spec/01-06-type-system.md)の「演算子の型付け」「等値の型」「鍵の型（初回リリース版）」の規則で判定する。等値の型の判定では、関数の型と等値を持たない組み込みの不透明型を含む型を、等値の型でないとする。代数的データ型とレコードは等値の型の要約で、鍵の型の判定の `Float` は鍵の型の要約で判定する。型パラメータは、`equality` か `key` を宣言していれば等値の型、`key` を宣言していれば鍵の型として扱い、宣言していなければ誤りとして、制約を加える書き方を修正案として示す。型構成子の適用 `F[A]` は、等値の型でも鍵の型でもないものとして扱う。
- 試行(A, R, τ): 型変数 A に付け、A が決まったときに判定する。A が `Result[T, E1]` なら、τ を T と等しくし、R を `Result[β, E1]`（β は `fresh`）と等しくする。A が `Option[T]` なら、τ を T と等しくし、R を `Option[β]` と等しくする。A がそれ以外の型なら誤りとする。R が `Result` で、`Result.Error` の型が E1 と違うために単一化が失敗したときは、`Result.mapError` で変換する書き方を修正案として示す（[エラー処理](../01-spec/01-09-errors.md)）。判定した種類と R を「`try` の種類」の表に記録する。
- リソース(A): 型変数 A に付け、A が決まったときに、A がリソースの型でなければ誤りとする。

【方針】エフェクトの制約は、確定した要素の集合と、エフェクトの変数との間の包含関係である。次のように、条件を満たす最小の集合を求めてから検査する（[型システム](../01-spec/01-06-type-system.md)の「エフェクト変数の具体化」）。以下、エフェクト X の確定した要素の集合を F(X)、X の変数を v(X)、変数 v の現在の集合を S(v) と書き、X の現在の要素を F(X) と S(v(X)) の和集合とする。

1. 各エフェクトの変数の集合を空集合から始める。
2. 含まれる(X, Y) のうち Y がエフェクトの変数を持つものについて、X の現在の要素のうち F(Y) に含まれないものを S(v(Y)) に加える。F(Y) に含まれる要素は、Y の確定した要素で満たされるので加えない。どの変数の集合も増えなくなるまで繰り返す。要素を加えるときは、その要素がどの呼び出しから来たかを記録する。
3. 含まれる(X, Y) のうち Y がエフェクトの変数を持たないもの（宣言した `uses`、ラムダの `uses`、`lazy` の本体とガードの空集合）について、X の現在の要素が F(Y) に含まれるかを検査する。含まれない要素があれば誤りとし、その要素と、それを生じた呼び出しの位置を示す（[型システム](../01-spec/01-06-type-system.md)の「式のエフェクト」）。`lazy` の本体の誤りでは引数のないラムダを使う書き方を、ガードの誤りでは本体の中で条件を調べる書き方を修正案として示す。

手順 2 は、どの解でもその変数に含まれていなければならない要素だけを加えるので、得られる集合は各変数について最小である。単一化が加える両方向の含まれる制約も、同じ手順で解く。手順 2 を終えた時点で、Y が変数を持つ制約はすべて満たされている。

例えば、次の `main` の `choose` の呼び出しでは、`E` を置き換えたエフェクトの変数を ε、第 1 引数のラムダのエフェクトの変数を ρ とする。第 1 引数から含まれる(ρ, Console.Write と ε からなるエフェクト)、第 2 引数から含まれる(空集合, ε)、`main` の本体から含まれる(ε, 空集合) が生じ、ラムダの本体の `Console.writeLine` の呼び出しから ρ は `Console.Write` を持つ。手順 2 は、ρ の `Console.Write` が一つ目の制約の右辺の確定した要素に含まれるので、ε に加えない。ε は空集合のままであり、手順 3 の検査を通る。第 2 引数を `Console.Write` を生じるラムダに変えると、ε に `Console.Write` が加わり、手順 3 で `main` の本体の誤りになる。

```text
import Benitoite.Unofficial.IO.Console

function choose[effect E](unused: function() -> Unit uses Console.Write, E, act: function() -> Unit uses E) -> Unit uses E
  act()
end function

function main() -> Unit
  choose(unused: lambda() Console.writeLine("not called") end lambda, act: lambda() () end lambda)
end function
```

【決定】Die の型検査では、試行の制約に Return の戻り値か Die の標準 exit の参照を保持する。Die も入力が Result/Option であることと成功型を検査するが、囲む戻り値を制約しない。入力が確定するまで特殊な制約を解き直し、Result の失敗型が分かった段階で標準 Trait.Show の Class 制約を登録する。辞書の解決後に `TryActionInfo::Die` へ辞書と標準 IO.Process.exit の束縛番号を保存する。Option の show は None である。表示の実装不足は E0705、型パラメータの制約不足は E0706 とし、Show の実装か Result.mapError による変換を案内する。Return の型と診断は従来の規則を保つ。

Die は Process.Exit を式のエフェクトへ加える。説明は元の字句スコープで検査し、String への Flow と空のエフェクト集合への EffSub を生成する。String でない場合は E0401、効果がある場合は E0511 とし、効果が生じる位置を主位置、説明の括弧を副位置にする。説明を検査する間は外側の継続を隠し、直接の resume を E0509 と `die_message` の help で拒否する。内側に書いた lambda の return は通常の関数境界で検査する。末尾再開の判定では、Die 自体を途中の return や末尾の resume とみなさず、入力と説明の内部だけを走査する。定数式ではすべての try を引き続き拒否する。

この Die の検査は本番の parser・ローダから公開の名前解決と型検査を通す。E0501 の修正案には `uses Process.Exit` を示し、標準 Process の import がなければ import も示す。Die の脱糖は [02-06「内部の終了報告」](02-06-ir-and-lowering.md#内部の終了報告) に従い、説明・表示・終了の順序と辞書を保持する。

### 型クラスの制約の解決

【決定】型クラスは、実装の辞書を引数として渡す形で実装し、型ごとに関数を複製すること（単相化）はしない。型検査は、関数の本体の検査を終えた後に型クラスの制約を解き、制約ごとに辞書をどう得るかを表に記録する。脱糖はこの表に従って辞書の引数を加える。理由: トップレベルの関数はシグネチャを必ず書くので多相の再帰を書け、単相化ではその複製が終わらないことがあるからである。辞書を渡す形は、コア計算の型クラスの意味（[コア計算と脱糖](../01-spec/01-12-core-calculus.md)の「型クラス」）とも形が揃う。

【方針】辞書の求め方は、次の三つのいずれかを根とする木である。

- 実装: 実装 I（実装の宣言のノード番号で指す）と、I の型パラメータに与える型と、I の型パラメータの制約ごとの辞書の求め方の並び。
- 受け取った辞書: いま検査している関数・実装・メソッドが宣言した制約の番号と、そこから上位の型クラスを辿る道筋（型クラスの並び。辿らなければ空）。
- 節が受け取った辞書: 節のノード番号、操作の宣言の制約の番号と、上位の型クラスへの道筋。外側の定義の同じ制約番号とは区別する。

【方針】型クラス(C, τ) は、生成した順に、次のように解く。上位の型クラスの制約（実装の検査）と、実装の型パラメータの制約（下の 2）も同じ手順で解く。

1. τ をいまの単一化の状態で置き換える。τ が誤りの型を含めば、何もしない。
2. τ の最も外側が型構成子 D（値の型の `D[…]`、または型構成子の位置の D）なら、型クラスと型構成子の組の表から実装 I を引く。なければ誤りとする。I の型パラメータを τ の型引数で置き換え、I の型パラメータの制約を同じ手順で解き、その結果を子とする実装の求め方を記録する。
3. τ が型パラメータなら、その型パラメータに宣言した制約の中から、C そのものか、C を上位の型クラスに持つ（上位の型クラスの上位を含む）型クラスの制約を探す。見つかれば、受け取った辞書の求め方を記録する。候補が複数あれば、C そのものを優先し、次に辿る道筋の短いものを、同じ長さなら先に宣言した制約を選ぶ。見つからなければ誤りとし、制約を加える書き方を修正案として示す（[型システム](../01-spec/01-06-type-system.md)の「型クラス（初回リリース版）」）。
4. τ が剛な型なら、所属する節の操作の宣言の制約を上記3と同じ優先順で探す。具体的な実装を選び直さず、節が受け取った辞書の根拠を記録する。宣言の制約は節のノード番号ごとに保持し、遅延した制約も同じ所属で解く。実装が要求する組み込み制約の補助検査にも、節の型パラメータと診断の操作名を渡す。
5. τ が型変数のままなら誤りとし、型注釈を書くよう示す。
6. それ以外（関数の型、型構成子を表す型パラメータの適用 `F[A]`）は、実装がないものとして誤りとする。

【決定】上位の型クラスへの道筋は、宣言集合が固定した一つの本体の検査に限り、出発と到着のクラスの組で記憶する。道筋がない結果も含め、元の幅優先探索の結果を使う。候補の辞書と上位クラスの走査は宣言順を保ち、型や行の単一化の結果は記憶しない。理由: 繰り返す道筋の探索を除き、同じ長さの候補で先に宣言した制約を選ぶ規則を保つためである。

孤立した実装と重なる実装は誤りとしてあるので、2 で引く実装は高々一つである。組み込みの制約（`equality`・`key`・`ordered`）は型クラスの制約ではなく、等値・鍵・集まりの制約として解き、辞書を持たない。

【方針】一つの型クラスの制約を解く仕事量に予算を設ける（[型システム](../01-spec/01-06-type-system.md)の「型クラス（初回リリース版）」）。仕事量は、解く途中で作る辞書の求め方の部品ごとに 1 と、2 で実装の型パラメータに写す型の節の数の合計で数え、上限を 32,768 とする。型の節は、型構成子の適用と関数の型の引数と戻り値を一節ずつ数える。部品の子の制約も親と同じ予算で数えるので、入れ子の段ごとに倍になる辞書も一つの制約の予算に収まらなければ止まる。上限を超えた制約は誤り（`E0715`）とし、診断は制約が生じた位置を示す。一つの使用（メソッドや制約を持つ関数を使った一つの位置）の制約のどれかで上限を超えたら、その使用の残りの制約は解かず、`E0715` を一度だけ出す。実装の上位の型クラスの制約（「実装の検査」）も、制約ごとに同じ予算で解く。理由: 同じ型パラメータに二つ以上の制約を求める実装を入れ子にすると、辞書の部品の数は入れ子の段ごとに倍になる。型の節を数えるのは、部品の数が少なくても大きな型を写す辞書を止めるためである。上限は、リポジトリのソース（標準ライブラリ・ゴールデンテスト・例など）で測った仕事量の最大（14）の約 2,300 倍である。

### 本体の後の検査

【決定】型と引数の対応を確定し、本体の検査と警告の処理を終えた後、誤りのない本体の定数引数を `checked_args` で追加検査する。対象は解決済みの標準束縛 `Regex.compile` とScopeの `checkHost`・`checkPath`・`checkEndpoint` の直接Callである。`consts::std_call` と `standard_argument` により束縛と引数を同定し、`CallPlan.direct_callee` により間接・穴・パイプを除外する。呼び出しは本体内のソース位置順に並べ、同じ呼び出しの引数もソース位置順に取得する。モジュールと本体の順は従来の検査順を保つ。

定数の取得は既存の形の検査と評価器を使い、`Known { value, argument_span, const_origins }`・`Unknown`・`BudgetExceeded`・`Invalid` を区別する。取得不能と予算超過では追加拒否しない。評価済みconstを再評価せず、constごとに直接参照したconstの集合だけを保存する。直接参照の保存領域は新規要素ごとに64バイトを計上し、集合を複製せず移して保存する。計上先は、トップレベルconstの評価では全constで共有する評価予算、追加検査の定数取得では `CheckedArgsState` の取得予算である。この計上を加えたため、const間の参照が多い入力は、以前より早くトップレベルconstの評価予算に達し、E0435で拒否される場合がある。推移的な由来は診断時に訪問済み集合と明示の積み重ねで求める。同じ直接参照の集合については、選んだ位置と正確な省略数を `CheckedArgsState` に記憶し、本体・Regex/Scopeをまたぐ診断で再利用する。constの補助位置は直接参照を優先し、値の出どころである連鎖の起点と合わせて最大8件とする。途中の宣言も含めた残りの件数はnoteで示す。型や名前の誤りがある本体と、評価失敗の入力には診断を重ねない。`Decls` が持つ `CheckedArgsState` の64 MiBは全対象呼び出しで共有し、トップレベルconstと警告の既存予算から独立させる。新しい値と複製を既存の `EvalBudget` の規則で数える。Regexの組み立ては別の暫定予算（一パターン1 MiB、全体8 MiBのソース長、異なるパターン256件まで）を使い、同一入力の結果を一検査内で再利用する。

Regexの組み立てと失敗表示は `builtins/checked_regex` のヒープに依存しない処理を実行時と共有する。構造化したSyntaxはE0457、CompiledTooBigはE0458、それ以外は追加拒否せず実行時へ残す。Patternの埋め込みやOkへの置換は行わない。

Scopeの形式・所属・失敗順は、ヒープに依存しない `builtins/checked_scope` を実行時と共有する。パターンE0459、対象E0460、端点・portの形式E0461、所属E0462を順に検査する。Endpointは既知の端点一つでも範囲外なら拒否し、二端点が既知なら順序も検査する。ホストの二入力が既知ならホスト所属、整数の三入力が既知ならポート所属を検査する。未知の引数が先行する失敗の種類を変えることはあっても、静的拒否した入力が実行時Okになることはない。成功時の文字列の複製は静的検査では行わず、Call・Result・実行時検査を保つ。

Scopeの一次位置は不良の引数である。所属不良では対象を一次、条件を補助位置とする。逆転した端点はmaximumPortを一次、minimumPortを補助位置とし、ポート所属では二端点を補助位置とする。関係する引数のconst由来も、合わせて最大8件の補助位置と省略数のnoteで示す。

【決定】Rust の `MatchIssue::NonExhaustive` と `BindingCheck` は、反例の文字列と別に、含まれる将来の形の型の束縛番号の集合を返す。探索中の各列の反例と記憶にも表示と集合を一緒に保持し、構成子・リストの反例を組み立てるときに集合を合わせる。一つの探索で view は不変であり、異なる view の間で記憶を共有しない。

将来の形の表示は data で `<future constructor of TypeName>`、record で `<future shape of TypeName>` とし、`TypeName` は `AdtDef.name` を使う。E0601/E0607 は束縛番号から宣言の副位置と包括的なパターンの help を作る。E0601 の将来の形を含む反例には、反例を構文として書く従来の `add_arm` の案内を付けない。E0607 の将来の形に対する help は、`match ... with` に書き換え、ガードなしの `case _ ->` の分岐を加えるよう案内し、従来の `match` への案内は重ねて付けない。通常の反例の表示と案内は保つ。理由: 将来の形はソースで書ける構成子ではなく、表示文字列だけでは同名の型の宣言を区別できないためである。

【決定】Lean の定義には、データ型ごとの指定 `CoverageView := DataName → Bool` と `shapesWithView` を定義している。`shapesWithView(P, ctors, view, ty, column)` は、従来の `shapes` の並びの末尾に、`ty = data d ts` かつ `view d = true` のときだけ `Shape.future d` を一つ追加する。将来の形は欄を持たず、変数と `_` だけで特殊化でき、反例には `CoverageWitness.future d` として型の出どころを残す。整数の残りの形 `other` の有無は全域の被覆で決め、文字列の `other` は常に残す。Rust も下記の Lean の規則と同じ条件を使う。Release の view 付き有用性の再帰はこの列挙を使い、入れ子の構成子の欄とリストの要素にも同じ view を渡す。Rust の `shapes` も同じ view による将来の形の追加を使い、`Shape::Future(BindingId)` として型の出どころを保持する。ソースの属性と型表を直接作る独立入力の両方から指定を渡し、判定を比較する。Lean の表層への接続は後の段落に記す。理由: 追加する形の判定と現在の値についての健全性を検査するためである。

【決定】`checkMatchWithView` は網羅性・選ばれない選択肢・覆っている選択肢の説明に同じ view を使う。`coveringAlternativesWithView` の単独行と接頭辞の有用性、および `overlapsWithView` の再帰も同じ指定を渡す。`irrefutableWithView` は束縛の左辺の判定に同じ有用性を使う。旧入口は `closedView` を渡すラッパーであり、反例・位置・覆う分岐・燃料切れの記録まで含めて結果が一致する。燃料の計算は view に依存せず、燃料切れ・不整合では有用と答える。任意の view の判定で有用でないときに、現在の値が元の行に照合するという補題 U と、そこから得る網羅性・到達不能の健全性を証明している。理由: 将来の形を考慮しても既知の構成子を失わず、現在の値についての保証を保つためである。

【決定】Lean の表層の宣言表 `Declarations` は、本体の view を持つ（既定は `closedView`）。ソースの `matchExhaustive`・`bindingExhaustive` は同じ宣言表の view を渡す。完全な構成子の一覧と view 付き判定の成功を `ViewExhaustive` として型付け規則へ渡し、その証拠から現在のコアの `Exhaustive` を導く。record 更新・Result/Option の try の内部照合には明示的に閉じた view を渡す。getter は現在のコアの照合を直接生成し、単一構成子の `Exhaustive` を使う。Program の `functionViews`・`methodViews` と交換形式 11/4/4 へ接続済みである。Rust の通常の書き出しも 11/4/4 を使い、所属・標準型の識別・型の表示と view を交換する。ソースの属性から型の指定と本体ごとの view を反映する。独立した網羅性 4 の出力には型表の拡張指定と view を含める。理由: 将来の形を外部のソース照合で考慮しつつ、内部の合成照合が扱う現在の値の保証を維持するためである。

【決定】Lean の反例表示 `CoverageWitness.showWithTypes` は、既存の `ConName → Option CoverageDisplay` に加えて、`DataName → Option CoverageTypeDisplay`（型名 `typeName` と record の印 `isRecord`）を受け取る。将来の形は `<future constructor of TypeName>`、record は `<future shape of TypeName>` と表示し、構成子・リストの内側にも同じ型表示表を使う。型表示がないときは、従来の未知の構成子と同じく `_` とする。既存の `show` は空の型表示表を渡す入口として保持している。理由: 実在しない構成子名を作らず、将来の形の出どころから表示を決めるためである。

【決定】`Release/CoverageExtension.lean` の `ConstructorExtension P P' view` は、既存の構成子の宣言を変えず、`P.cons c = none` である新しい構成子を view が真の型にだけ追加する関係である。構成子以外の表は `Inhabits` が参照しないため制約しない。

`usefulWithView_extension_exhaustive` は、`CtorsComplete P ctors`、`CtorsComplete P' ctors'`、この拡張関係、および `usefulWithView P ctors view [A] (ps.map (fun p => [p])) [wild] = none` から `Exhaustive P' A ps` を導く。入れ子とリストを含み、将来の実行結果の一致は主張しない。`Represents.future` は証明内で追加後の値を将来の形に対応させる関係であり、現在の `Val` と `Inhabits` には新しい場合を足さない。理由: 現在の値についての健全性に加え、許可された構成子追加の後の値も元の分岐が覆うことを保証するためである。

定数の宣言側の所属と `E_Const` の使用側の view の対応、および交換時の制限は、[形式意味論と検証](../07-quality/07-04-formal-semantics.md)の「01-12 との対応」を正とする。

【方針】制約をすべて解いた後、次を検査する。

- 制約（集まり、等値、鍵、試行、リソース）を持つ型変数が決まっていなければ誤りとし、型注釈を書くよう示す（[型システム](../01-spec/01-06-type-system.md)、[エラー処理](../01-spec/01-09-errors.md)）。
- 各 `match` について、網羅していないことと、選ばれない分岐があることを検査する（[代数的データ型とパターンマッチ](../01-spec/01-05-data-types.md)）。
- 変数と `_` 以外のパターンを左辺に書いた束縛の文について、パターンが必ず照合することを検査する。必ず照合しなければ誤りとし、`match` で分岐する書き方を修正案として示す（同「必ず照合するパターン（初回リリース版）」）。
- 警告の対象を調べる（後述の「警告」）。

【方針】パターンの検査は、パターンの行列に対する有用性（usefulness）の判定で行う。パターンの並び q が、パターンの並びの行列 P に対して有用であるとは、q に照合し、P のどの行にも照合しない値の並び（各値は、対応する型の値の形をしたもの。01-05「網羅性の検査」）が存在することである（意味の定義）。型検査は、この定義を直接調べず、後述の型ごとの構成子の規則に従う再帰の手順で判定する。Lean の型ごとの規則は、`String` と、値域に覆われない部分がある `Integer` に、どのリテラルと範囲にも照合しない「残りの値」を置き、値を一つも作れない型の構成子にも値があるものとして扱う。したがって、手順が有用と答えても、意味の定義どおりの値の並びがあるとは限らない。逆向きは成り立つ。手順が有用でないと答えれば、値の形をしたどの値の並びについても、q に照合するなら P のどれかの行に照合する（補題 U）。補題 U は、Lean の定義の手順について形式化で証明した（[形式意味論](../07-quality/07-04-formal-semantics.md)の「01-12 との対応」）。このため、手順が網羅したと判定した `match` は 01-05 の意味の定義で網羅しており、選ばれないと判定した選択肢は、値の形をしたどの値についても選ばれない。

【決定】有用性の手順は、Lean の定義（`formal/` の `Benitoite/Release/Coverage.lean`）を正とし、本節の手順の記述はその写しとする。理由: 脱糖とコア計算の規則と同じく、形式化した規則に二つの正を持たないためである（07-04「01-12 との対応」）。処理系の手順と Lean の手順の一致は、型の合う入力について、差分テストで確かめる（[処理系のテスト戦略](../07-quality/07-03-compiler-testing.md)の「差分テスト」）。

【方針】行列を作るときは、コンマで並べた選択肢をそれぞれ一つの行にする。同じ分岐の左の選択肢は、分岐のガードの有無によらず、後の選択肢の判定の行に加える。ガードの付いた分岐の選択肢は、後の分岐を覆うものに数えないので、後の分岐の判定と網羅性の判定の行列には加えない。

- `match` の選択肢 q は、それより前の行（前の分岐のうちガードの付いていない分岐の選択肢と、同じ分岐の左の選択肢）からなる行列に対して有用でなければ、選ばれない選択肢である。ガードの付いた分岐の選択肢も、この判定の対象にする（同「選ばれない分岐の検査」）。選ばれない選択肢が一つでもあれば誤りとし、その選択肢を示す（`case 1, 1 ->` と `case 1, 1 if g ->` の 2 番目の `1` など）。
- 診断に示す覆っている前の分岐は、次のように選ぶ。前の行のうち、その一行だけからなる行列に対して q が有用でない最初の行があれば、その行の分岐だけを示す。なければ、前の行の先頭から k 行の行列に対して q が有用でない最小の k を求め、その k 行のうち q と重なる行の分岐をすべて示す。q と同じ分岐は示さない。二つのパターンが重なるとは、両方に照合する値があることである。ワイルドカードと変数はどのパターンとも重なる。構成子のパターンどうしは、構成子が同じで対応する引数がすべて重なるときに重なる。リテラルと `()` のパターンどうしは、値が等しいときに重なる。範囲のパターンは、リテラルを両端の等しい範囲とみなし、範囲が交わるときに重なる。リストのパターンどうしは、両方が照合する長さのうち、その長さで対応する位置の要素のパターンがすべて重なるものがあるときに重なる。
- ワイルドカード一つからなる並びが、すべての分岐からなる行列に対して有用であれば、`match` は網羅していない。判定の途中で、どの分岐にも照合しない値の形を作り、診断に示す。
- 束縛の文 `bind p <- e`・`shadow p <- e` の p は、p 一つからなる行列に対してワイルドカードが有用でなければ、必ず照合する。

【方針】判定では、型ごとの構成子の集まりを次のように扱う。

- 以下の「列」は、行列の先頭の列のパターンに、問いの先頭のパターンを加えたものである。
- 代数的データ型とレコードは宣言の構成子の全体、`Boolean` は `true` と `false`、`Unit` は `()` で、すべてを並べれば網羅したとみなす。代数的データ型の構成子は、値を作れるかを問わず構成子に数える。
- Lean の `Integer` は、リテラルと範囲を区間として扱う（リテラルは両端の等しい区間とする）。`integerBounds` は `min64`・`max64 + 1` と列の下端・上端の直後を集め、`integerAtoms` は値域内の最小区間を作る。上端の直後は数学上の Int で計算する。列の一つのリテラルか範囲が区間全体を覆うかを `integerCovered` で判定し、覆われた区間だけを下端の昇順に列挙する。隣接区間も合併せず、残りの列の再帰で相関を保つ。`integerHasOther` は覆われない最小区間が一つでもある場合に真となり、その場合だけ先頭に `other` を置く。全域を覆う場合は変数や `_` なしで網羅的と認める。各値の区間か `other` への所属の一意性は `integer_atoms_partition`、全域の被覆と `other` の不要性との同値は `integer_full_no_other` で示す。ガード行は後の分岐の被覆へ数えない。Rust は端点に開始と終了の印を付けて整列し、活動中の区間数を更新しながら一度走査する。各小区間を入力の全区間と比較する二重ループを使わず、Lean と同じ順序を保つ。`max64 + 1` は `i128` のまま扱い、`Integer` に戻さない。
- `Character` は、有効な値域 `[0, 0xD7FF] ∪ [0xE000, 0x10FFFF]` を区間で分割する。分割の端は0・0xD800・0xE000・0x110000と、列に現れるリテラル・範囲の下端および上端の直後である。`charPartition` はサロゲートと値域外を除き、入力が覆わない有効な区間も列挙する。文字には「残りの値」を置かない。`char_partition_cover` は全てのLeanのCharがこの分割に属することを、`char_partition_query` は問いの端をまたがずに特殊化できることを示す。残りの列を再帰して欄どうしの相関を保つ。全域の一範囲・サロゲート前後の二範囲・リテラルとの和を網羅的と認め、全域の一範囲を束縛の左辺にも認める。Rustの処理系も同じ分割と特殊化を使う。
- `String` は、列に現れる文字列のリテラルをそれぞれ構成子とし、先頭に残りの値の構成子を置く。Rust は出現順の配列と挿入済みの集合を併用し、重複を除いて最初の出現順を保つ。したがって、リテラルを並べても網羅したとはみなさない。
- `List[T]` は、長さによる分け方を構成子として扱う。列に現れる残りのないパターンの長さの最大を a、残りのあるパターンの `..` の前の要素の数の最大を p、後の要素の数の最大を s とし、m を a + 1 と p + s の大きいほうとする。ただし、残りのないパターンが列に一つもなければ、a + 1 の項を 0 とする（m は p + s）。構成子は、長さがちょうど k のもの（0 ≤ k < m。要素 k 個を引数に持つ）と、長さが m 以上のもの（前の p 個と後の s 個の要素を引数に持つ）である。残りのあるパターンは、前の要素と後の要素の間をワイルドカードで埋めて、それぞれの構成子の引数の並びに移す。
- `Float`・`Byte`・`Decimal` と新しい七種の数の型、`Map`・`Set`・`Bytes`、関数の型、組み込みの不透明型、型パラメータ、型構成子の適用、決まらなかった型変数は、ワイルドカードと変数のパターンでしか照合できないので、構成子を持たない型として扱う。

【方針】一つの `match` と一つの束縛の文の判定ごとに、仕事量の予算を設ける（[代数的データ型とパターンマッチ](../01-spec/01-05-data-types.md)の「網羅性の検査」）。仕事量は、手順が構成子で分ける段ごとに調べる行列のセルの数（パターンの数）と、後述の記憶の鍵を作るために写すセルと型の数の合計で数え、上限を 2^20（1,048,576）とする。`match` では、選ばれない選択肢の判定、覆っている分岐の判定、網羅性の判定のすべてが一つの予算を使う。予算を超えたら判定をやめ、その `match` については選ばれない選択肢と網羅していないことの診断を出さず、判定を終えられなかったこと（`E0609`）だけを `match` の位置に出す。束縛の文では `E0609` を左辺のパターンの位置に出す。理由: 予算に当たる前に見つけた診断を混ぜると、同じソースで予算の大きさによって診断が変わる。網羅していると決めつけて通すと、照合が実行で失敗しうる。

追加の予算は、列挙・キーの仕事量16,777,216、記憶するキーと結果のセル合計1,048,576、文字列キーのUTF-8の合計16 MiBとする。列挙では処理する境界・比較・走査するパターン節を各1と数え、文字列のハッシュではUTF-8のバイト数も加算する。キーのセルには入れ子のパターンと型の節、結果には反例の入れ子の節を含む。型の契約名も文字列キーへ数える。複製・形の列挙の拡張・記憶への挿入の前に該当する上限を検査する。予算のいずれかを超えれば同じ `E0609` とし、全プログラムの独立した別の誤りは残す。

行列が大きければ、指数的な探索でなくても探索セルの予算に当たる。手順は先頭から続くワイルドカードだけの列をまとめて一度に落とし、列ごとに行列を写す仕事量を数えない。新しい計上により、従来通った入力が列挙や記憶の予算に当たることもある。

【決定】文字区間の反例は、未被覆の区間の下端を実在するCharへ戻して表示する。ASCIIの可視文字は文字リテラルにし、改行・復帰・タブ・逆斜線・単一引用符はそれぞれ `\n`・`\r`・`\t`・`\\`・`\'` で逃がす。それ以外は、小文字の十六進数のUnicodeエスケープを使う。例えば `'a'` だけの分岐に対する反例は `'\u{0}'` である。複合パターンの表示にも同じ規則を使う。燃料切れや空の行列などで問いの形を返す既存の処理は保ち、反例全体が常に実在する値であるとは主張しない。表示した文字が元のパターンに照合しないことを例で確認し、表示の正しさの全体定理は加えない。RustとLeanの表示は同じ規則を使う。

【方針】一つの `match` と一つの束縛の文の判定の間、構成子で分ける段の入力（型の並び、行列、問い）ごとに、有用性の結果（反例を含む）を覚え、同じ入力の判定には覚えた結果を返す。記憶は判定の結果を変えず、列の選び方も変えない。記憶のハッシュが衝突しても、型の並び・行列・問いの構造の等値で照合し、比較の走査も予算へ数える。view は判定中に変わらず、記憶表を別の view や別の `match` に流用しない。交換の抽象的な反例は Lean と一致させる。ソースの `E0601` は別の内部入口で整数の具体値を選び、整数の `other` には最初の未被覆区間の下端を示す。行列が空のため整数全域が未被覆なら、整数を直接照合する診断は `min64` を示す。複合パターンの空の行列に対して問いの形を返す処理は保つ。理由: 分岐の多い `match` では同じ部分の行列が何度も現れ、記憶がなければ予算に当たる。

【方針】予算と `E0609` は、Lean の手順にない処理系の差であり、形式化の対象外とする（[形式意味論](../07-quality/07-04-formal-semantics.md)の「01-12 との対応」）。予算を超えた `match` と束縛の文は受け付けないので、受け付けた `match` と束縛の文の判定は予算の内側で終わっている。その結果は Lean の手順の結果と同じである。したがって、補題 U を処理系の判定に結び付ける論証は変わらない。

【方針】手順が内部の不整合（型の並びと問いの長さが合わない、構成子のパターンの引数の数が宣言と合わない、ワイルドカードでない問いをどの構成子にも特殊化できない、構成子の引数の型を求められない）に当たったときは「有用」と答え、反例として問いの形を示す。問いや型の並びと長さの違う行は、判定の前に除く。この不整合は、構成子の引数の数の誤りなどを報告した後のパターンで起きうる。理由: 有用の側に倒せば網羅性の誤りを隠さず、補題 U も型の付いたパターンを前提にせずに成り立つ。Lean の定義は、このほかに型と合わない問いと行も除く（処理系は、型検査を通ったパターンでは起きないので除かない）。Lean の定義は、入力の大きさから決めた回数で再帰を打ち切り、尽きたときも「有用」と答える。差分テストでは、打ち切った回数が 0 であることを確かめる。

### 警告

【決定】幅付きの整数の演算子と、`Integer8`・`Integer16`・`Integer32`・`Integer`・`Integer64`・`UnsignedInteger16`・`UnsignedInteger32`・`UnsignedInteger64`・`UnsignedInteger` の `absolute`・`floorDivide`・`floorModulo` の直接呼び出しを、算術の確実な誤りの警告の対象とする。解決済みの標準束縛・演算の種類・整数の幅を対応させた同じ表を、候補の選択と評価に使う。import の別名を認め、利用者の同名関数、関数値経由、穴、パイプ、`Byte` は対象としない。引数は宣言の契約名 `n`・`a`・`b` から取り出す。理由: ソース上の綴りや引数順から演算を推測せず、一般の関数の本体を実行しない範囲で確実な失敗を検出するためである。

除数が 0 なら、被除数が不明でも W0401 を出す。符号付き最小値の `absolute` と `floorDivide(最小値, −1)` は W0402 とし、`floorModulo(最小値, −1)` は 0 なので警告しない。符号なしの `absolute` と、除数が 0 でない除算には、このあふれはない。各幅の検査付き演算を使い、`u64` の上半分を `i64` へ変換しない。評価できる引数は既存の定数式に限り、既存の予算を適用する。警告は実行時の成功・失敗や停止の規則を変えない。

【方針】型検査器は、次の警告を出す。警告は検査と実行を止めない。警告の報告の仕方と `--deny-warnings` は[診断エンジン](02-10-diagnostics.md)と[パイプライン](02-01-pipeline.md)の「誤りが見つかったときの段の進め方」で定める。

- `uses IO.All` を狭められる: `uses` に `IO.All` を書いた、本体を持つ関数（実装のメソッドを含む）について、エフェクトの制約を解いた後、本体が生じるエフェクトの集合（含まれる(X, 宣言した `uses`) の X の現在の要素の和集合）を求める。その集合と `IO.All` を展開した集合の共通部分が、展開した集合より小さければ警告とし、本体が生じるエフェクトの集合を `uses` の書き方で示す（[エフェクト](../01-spec/01-07-effects.md)）。本体が誤りの式（`Expr::Error`）を含む場合は、置換で失われた引数のエフェクトを含めて集合を求められないため、この警告を出さない。
- 算術の確実な誤り: 本体の中の除算（`div`・`mod`・上記の整数モジュールの `floorDivide`・`floorModulo`、`Decimal` の `/`）の除数が定数式で、定数の評価器が求めたその値が 0 のとき。溢れうる演算のすべての引数が定数式で、定数の評価器による計算が整数の溢れか `Decimal` の溢れの条件に当たるとき（[基本型の意味論](../01-spec/01-04-types-basic.md)）。定数の宣言の中の同じ条件は、警告ではなく誤りである（前述の「定数の検査と評価」）。
- 重なる鍵: 定数式の外で、`Map.fromList` の引数がリストのリテラルであり、その中の組の鍵が定数式で同じ値になるものが二つ以上あるとき。`Set.fromList` の要素も同じである。

【決定】ファイル単位の宣言に IO.All がある場合も、本体が IO.All の一部しか生じない関数ごとに W0501 を出す。主位置は関数名、補助位置はファイルの IO.All とし、自動編集を付けない。個別とファイルの両方に IO.All があっても一関数に一件とする。個別 IO.All だけの縮小は、ファイルの宣言とほかの個別宣言で賄う分を除いて置換し、ファイルの宣言を編集しない。理由: ほかの関数の契約を保ち、同じリストに効果を重複して書く修正案を避けるためである。

【方針】算術の確実な誤りと重なる鍵の警告は、利用者のモジュールの関数のうち、本体の検査で誤りを報告しなかったものだけについて調べる。prelude と標準ライブラリのモジュールの本体は調べない。

### 誤りの報告と検査の継続

【決定】一つの関数の本体の中でも、誤りを報告した後に検査を続け、互いに独立した誤りをすべて報告する。

【方針】制約が解けず、両辺のいずれにも誤りの型を含まない場合は、誤りを報告し、その制約の両辺に現れるまだ決まっていない型変数を、すべて誤りの型にする。誤りの型を含む場合は、既知の構造の不一致を報告し、その報告を理由に変数を誤りの型にしない。その後は次のように扱う。

- 型の一致と流れ込む制約では、誤りの型である部分だけを未知として扱う。複合型の既知の外側と別の部分の不一致は報告する。誤りの部分との比較によって、正常な値が定める型を無効にしない。
- 型が誤りの型である関数の呼び出しは、エフェクトの検査で何の要素も生じない。
- 対象の型全体が誤りの型である `match` と束縛の文は、パターンの検査から外す。一部分だけが誤りの場合の範囲は後述する。
- 誤りの型になった型変数は、「本体の後の検査」で決まっていない型変数として扱わない。

宣言の検査で誤りを報告した宣言（型の宣言、シグネチャ、実装の頭部）は、その誤りの部分を誤りの型にして、後の手順を続ける。本体に誤りのある型の別名を使った宣言と型注釈も、誤りを報告した宣言と同じく扱う（そうした別名をシグネチャに使った関数は、シグネチャに直接誤りを書いた関数と同じく、本体を検査しない）。誤りのある実装は、型クラスと型構成子の組の表に加えたうえで、その実装を引いた制約について誤りを重ねて報告しない。対象の型構成子を決められない実装（対象が関数の型など、誤りのある別名を対象に使ったもの）は表に加えられないので、型構成子を持たない型についてのその型クラスの制約で誤りを重ねて報告せず、重なりの検査にも加えない。

【方針】型の誤りの診断は、期待した型、実際の型、その型が期待された理由（制約の理由）を示す。型は、ソースに書いた形（型の別名を含む）で示す。ただし、`IO.All` の 10 個をすべて含むエフェクトの集合は、個々の名前を明記した場合も `IO.All` とまとめ、残りの名前、エフェクト変数の順に続ける。決まっていない型変数は `_` で示す（表に書く型の `Unit` への置き換えは診断に使わない）。仕様が修正案を求めている次の場合は、それを示す。

- `Float` が期待される位置に整数リテラルを書いた場合は、`2.0` のような浮動小数リテラルを示す（[基本型の意味論](../01-spec/01-04-types-basic.md)）。
- `+` の集まりの制約か、`+` の二つのオペランドを等しくする制約が解けず、一方のオペランドの型が `String` で他方が `String` でない型（誤りの型を除く）の場合は、他方の値を文字列に変換してから連結するよう示す。他方の型が `Integer`・`Float`・`Character` なら、それぞれ `Integer.toString`・`Float.toString`・`Character.toString` を示す（[基本型の意味論](../01-spec/01-04-types-basic.md)）。
- 書式なしの文字列補間の集まりの制約が解けない場合は、E0422 を報告する（[型システム](../01-spec/01-06-type-system.md)の「演算子の型付け」）。普通の型パラメータが `Show` の制約を持つ場合は、診断の位置のモジュールで取り込んだ名前に合わせて `Trait.Show.show` で変換する案を示す。持たない場合は、同じ import の別名に合わせて `Trait.Show` の制約と `Trait.Show.show` の変換を案内し、置き換えは付けない。いずれも `Benitoite.Trait` を取り込んでいなければ、`import Benitoite.Trait` を書くことから案内する。剛な型には、操作の型パラメータの値を `String` に変換できないことを説明し、型が分かる値を補間するよう示す。理由: `Show` の制約を足すだけでは補間できず、明示的に `Trait.Show.show` で文字列へ変換する必要があるためである。
- `Float` を含む型を鍵にした場合は、`Integer` や `String` に変換して鍵にする書き方を示す（[型システム](../01-spec/01-06-type-system.md)の「鍵の型（初回リリース版）」）。
- E0401 では、期待と実際の型（型引数と関数の引数・戻り値の型を含む）の一方に、診断の位置と同じ利用者のモジュールで宣言した型 `X` が含まれ、他方に prelude の同じ名前の型 `X` が含まれる場合だけ注記と修正案を添える。E0410 では、書いた型が解決した宣言が、診断の位置と同じ利用者のモジュールで prelude と同じ名前の型を宣言しているか調べる。対象の名前は、prelude のモジュールのうち名前が一段のものと、`Unit`・`State` である。見つかれば、prelude の名前を隠していることを注記し、`Benitoite.X` で prelude の型を書く修正案を示す。置き換えは付けない。理由: 無関係な型の不一致に prelude の案内を添えず、利用者の型を意図した可能性があるときに自動で型を置き換えないためである。
- 型が決まらない場合は、型注釈を書くよう示す（[型システム](../01-spec/01-06-type-system.md)）。
- エフェクトの誤りは、宣言に含まれないエフェクトと、それを生じた呼び出しの位置を示す（同）。

診断の形式は[診断エンジン](02-10-diagnostics.md)で定める。

【決定】本体の型を示すすべての診断で、ハンドラの節の剛な型は、操作の宣言の型パラメータの名前で示す。表示する名前が外側の関数や別の節の型パラメータと重なる場合は、書いた操作の名前で修飾する（`store.T`）。修飾した名前も重なる場合は、末尾に `#` と 2 から始まる番号を付けて区別する（`store.T#2`）。一つの診断の本文と注記に現れる型には、共通の名前の表を使う。その型が節の外へ出るために単一化が失敗した場合は、E0401 に、操作の名前とその型の値を節の外へ出せないことを示す注記、および節の操作の名前を指す補助の位置を加える。報告を後へ回す場合も脱出の情報をその失敗とともに保存し、別の失敗へ持ち越さない。理由: 外側の関数の型パラメータと取り違えず、未確定の型との食い違いの原因を示すためである。

【決定】剛な型の `equality`・`key` の制約が足りない場合は、E0406・E0424 の修正案で、操作の宣言の型パラメータに制約を書くよう示す。修正案には操作の名前と宣言に書いた型パラメータの名前を示し、置き換えは付けない。理由: 外側の関数に制約を足しても、操作が宣言した制約は変わらないためである。

【決定】関数とラムダの本体の型を `Unit` と比べる制約（理由 `FnBody`）と、`return` を通らずに本体の末尾へ到達する診断（E0438）は、最後の文が式文ならその式を指し、そうでなければ本体のブロック全体を指す。同じ本体に E0416 を報告した場合は、E0438 と、ラムダの戻り値の型を `Unit` と比べる理由 `LambdaReturn` の E0401 を重ねない。理由: 最後の式に `return` を欠いた一つの原因を、直す式の位置で示すためである。

【決定】本体の最後の式文の E0416 では、ほかの制約を解決した後の戻り値の型で修正案を選ぶ。戻り値の型が `Unit` なら、型注釈の有無によらず値を捨てる修正案を示し、`return` は案内しない。戻り値の型が `Unit` 以外に決まっていれば、`return` の修正案を最初に示す。戻り値の型を書いていないラムダでは、戻り値の型が未確定か `Unit` 以外の場合に、`return` と値を捨てる修正案の順に両方を示す。`return` の置き換えは、戻り値の型が未確定か、最後の式の型と戻り値の型が解決後に等しい場合だけ、式の先頭への `return ` の挿入として付ける。型が異なる場合は文だけを示す。値を捨てる修正案には置き換えを付け、該当する場合は再代入の書き方への修正案も示す。E0416 の対象となったラムダの本体には、戻り値を既定の `Unit` と比べる制約を重ねない。理由: `Unit` が要求されるラムダで値を返すと別の型の誤りになるためである。戻り値を要求する本体で値を捨てると、末尾に到達する誤りが残るため、戻り値の型を明記した本体では値を捨てる案を示さない。戻り値の型を書いていないラムダでは、制約に合う範囲で、値を返すか捨てるかを利用者が選ぶ。

【決定】宣言からの要求、束縛の値、型の部分、再束縛、使用の要求の依存を、単一化の結果と分けて保持する。変数間の辺には共通の番号と理由を付け、List の要素・構成子の欄・関数の引数と戻り値などへの経路は元の型の形で保持する。zonk 後も関係を失わず、使用ごとに履歴全体を複製しない。値側の型が確定した束縛と、宣言から仮に決まった束縛を区別する。依存の連結成分にはunion-findを使い、宣言の理由と値側の確定の有無を根ごとに保持する。回復の記録がない本体では、回復元を探索しない。型付けに成功する制約の解決順と結果は変えない。

【決定】診断済みの誤りの式と、呼び出し不能などで結果が未確定になる呼び出しについては、原因ID（元の診断の一次位置のファイルIDとUTF-8バイト範囲）と型の部分への経路を、元の型変数に対応付けて保持する。経路は値全体、型引数、関数の引数・戻り値・失敗型の各部分を区別する。束縛・リストの要素・レコードの欄・構成子の引数・注釈のないラムダの戻り値から、値を作る向きの依存を記録する。パターンと高階引数から部分を取り出す場合は、経路を射影する。関数型の引数部分では依存の向きを逆にし、コールバックの引数注釈を呼び出し側の値の型の根拠にしない。右辺から束縛への関係と、束縛自身の明示契約を、Declared制約を解く前に記録する。原因は値を作る向きに伝え、明示契約のある束縛では止める。同じ部分に正常な値もあれば、その値が与える型の根拠を残す。

zonkは、値全体に原因があれば誤りの型を返す。一部分に原因がある変数では、使用側が先に具体化した形に代えて元の値の形を辿り、未知の部分だけを誤りの型にする。利用側の期待型を、元の値の確定情報にしない。原因の追跡にも型の深さ・節数の既存の予算を用い、追跡できない部分を理由に診断を抑えない。原因と経路は本体の推論の内部だけに保持し、実行用の型と交換形式には加えない。成功時には値の組と必要な外形の索引を配列へ記録し、依存表と部分の経路は診断の処理で必要になってから構築する。記録時には更新が必要なことだけを印し、生成の終わり、保留した呼び出しの解決後、使用の再確認前に原因を更新する。同じ部分の既知・未知の判定は、その更新の間で再利用する。

たとえば、`bind f <- 誤りの式`の後で`bind n: Integer <- f`としても、fをOptionパターンに使う派生したE0401は報告しない。一方、`bind f: Integer <- 誤りの式`のfと、前の例のnは自身の明示契約を持つため、後でStringとして使う不一致を報告する。`List[誤りの型]`と`List[Integer]`の要素の比較は抑えるが、`List[誤りの型]`と`Integer`の外側の不一致は報告する。引数が誤りであっても、正常な関数の宣言した結果がIntegerなら、その結果をStringとして使う不一致を報告する。同じ関数と別関数の独立した誤りも報告する。

後で解く呼び出しの結果と、その結果を含む複合型に依存するE0401は、呼び出しの診断が確定するまで保留する。原因の確定前に成功した要求も、確定後の既知の構造で再確認する。解いた呼び出しの結果は保留の集合から除き、保留への依存は値を作る向きの辺に沿って印を伝えて判定する。成功した要求は一度だけ保存し、診断済みの原因がある場合に限って再確認する。原因の診断がなければ通常の型検査の結果を用いる。保留中の失敗のうち、剛な型の脱出は原因の有無にかかわらず報告する。ほかのE0401は、解決後に両辺が等しければ取り消し、誤りの型を含む部分だけに依存する不一致を抑える。原因の式を直した後は、すべての使用を通常の型検査で検査し直す。理由: 利用側の要求どうしの衝突を診断済みの値の型の根拠にせず、束縛自身の契約と値の既知の部分による独立した誤りを残すためである。

【決定】後検査は、型の一部に誤りがあることだけで全体を抑制しない。演算子・補間の型集合は既知の外側で判定し、比較可能性・鍵の制約は必要な型引数ごとに調べる。型クラスは、既知の型構成子に実装がなければ報告し、実装が要求する部分が誤りの型ならその解決を抑える。引数の個数・ラベルの検査は維持し、関数の引数や結果の一部が誤りでも、既知のエフェクトの禁止を検査する。

パターンの対象の一部分が誤りの場合、外側の構成子・リストの長さだけを照合し、内側を変数かワイルドカードとするパターンに限って網羅性・選ばれない分岐・必ず照合する束縛を検査する。内側にも構成子やリテラルなどの照合がある場合は、そのパターンを含む後検査を見送る。型クラスも、先に解決した部分が誤りなら後の部分の診断が残らない場合がある。未知の部分に依存する検査から、独立した診断だけをすべて抽出する保証はしない。根の診断は残し、誤りを含むプログラムは外部照合・脱糖・実行へ進めない。

手順 2 の束縛や部分パターン、`try` の成功型が宣言由来の仮の型と食い違い、その位置が宣言へ流れ込む式の外側にある場合は、食い違った部分を宣言側の要求へ移す。期待した型は宣言側、実際の型は値側とし、一次位置・副位置・理由と型を保存してから根を無効にする。移した報告が別の誤りからの派生として抑えられても、その根と同じ型の部分に依存する根を無効にする。

宣言由来の型に依存する使用の失敗だけを保留し、原因側の報告と根の無効化を終えてから採否を決める。包んだ値、演算子、再束縛の使用でも、値側の型なら成功する比較は報告しない。値側の型でも失敗する要求は独立した誤りとして元の使用位置に残す。成功した使用の制約も元の型変数とともに保持し、回復が生じた本体では、元の型でも失敗した使用の内側に限り、元の型で成功した部分が値側の型で矛盾しないか再確認する。宣言の型では成功する使用に、回復だけを理由とする新しい誤りを加えない。たとえば`gl([s, "x"])`では、sをIntegerへ回復しても文字列要素が適合しないため、その要素の誤りを残す。型変数を含むことだけを理由に抑えず、全 E0401 を一律に遅らせない。宣言へ流れ込む式の内側の失敗では、部分式の位置とリテラルなどの修正案を保つ。理由: 正しい使用への偽の報告を抑えながら、値側にある本当の誤りを宣言の不一致へ取り違えないためである。

【決定】`return` と束縛の型注釈の、宣言の型への流れ込む制約が、別の宣言の流れ込みが先に決めた型変数と食い違った場合（E0401）は、その場では報告せず、型変数を誤りの型にしない。手順 2 と後へ回したほかの報告を終えた後に、その型変数が誤りの型を含まなければ報告する。理由: 宣言どうしの食い違いでは、変数を定める束縛との食い違いを先に示すためである。先にその変数を誤りの型にすると、束縛との食い違いが派生した誤りとして抑えられる。

【決定】`try` の戻り先の型が合わない E0441・E0442 では、注記の戻り先を関数、ラムダ、プレースホルダの呼び出しが作る関数に分ける。プレースホルダの場合は、その呼び出しを補助の位置で示す。ラムダの本体へ入る際は、外側がプレースホルダの呼び出しでも戻り先をラムダに替える。理由: `try` が抜ける境界と、注記が示す戻り値の持ち主を一致させるためである。
