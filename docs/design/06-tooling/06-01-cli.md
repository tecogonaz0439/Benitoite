# CLI


## 目的と範囲

処理系のコマンドラインを定める。対象は、`run`・`check`・`test`・`fmt`・`skill`・`package` のコマンドラインと終了状態、版と対応する形式の問い合わせ、非実行の検査報告、実行前のエフェクト上限の照合、`run` と `check` の振る舞い、`run` を省いた実行とシェバン、予約したサブコマンドの名前、オプション `--licenses` である。`test` の振る舞いと結果の報告の形は[利用者プログラムのテスト](06-04-test-runner.md)で、`fmt` の整形の規則は[フォーマッタ](06-03-formatter.md)で、`skill` が書き出す Skill と書き出す先は [Agent Skills 対応](06-06-agent-skills.md)で定める。

初回リリース版の CLI は、処理系をサーバとして動かさずに起動する形（スタンドアロンモード）だけを持ち、実行時の権限制御と OS のサンドボックスを掛けない。サーバモードのサブコマンド、MCP サーバ、スクリプトの署名と検証、`repl` は初回リリース版に含めない。これらの名前は予約する（後述の「予約したサブコマンドの名前（初回リリース版）」）。

## 前提

`run` と `check` が通す処理系の段は[パイプライン](../02-impl/02-01-pipeline.md)で、`run` の処理の順序は[スクリプト実行と埋め込み](../02-impl/02-11-embedding.md)と[ランタイム](../02-impl/02-09-runtime.md)で、診断の形式は[診断エンジン](../02-impl/02-10-diagnostics.md)で定める。

## 仕様

### コマンドの名前

【決定】処理系のコマンドの名前は `benitoite`、スクリプトのファイルの拡張子は `.bnt` とする。短い別名のコマンド（`bnt` など）は設けない。シェバンの行も `benitoite` を使う。言語の名前は Benitoite である。

### コマンドラインの形

【方針】`run` と `check` のコマンドラインは次の形とする。

```text
benitoite run   [オプション] <スクリプトのパス> [スクリプトの引数...]
benitoite check [オプション] <スクリプトのパス>
benitoite --help
benitoite --version
benitoite --version=json
```

- 処理系のオプションは、スクリプトのパスの前に書く。サブコマンドの前に書いてもよい。`--help`・`--version`・`--version=json`・`--licenses` は、最初の引数にだけ書ける。
- スクリプトのパスより後の引数は、`-` で始まるものも含めて、処理系は解釈せず、書いた順にスクリプトに渡す（`Process.arguments()`。[エフェクト](../01-spec/01-07-effects.md)）。
- スクリプトのパスは一つだけ指定する。拡張子は検査しない。
- スクリプトとモジュールは、普通のファイルから読む（[ソース管理と位置情報](../02-impl/02-02-source-and-spans.md)の「ソースとファイル ID」）。パイプを指すパス（`benitoite check /dev/stdin` にパイプをつないだ場合や、`benitoite run <(...)`）は、ファイルを読めない誤り（E0101）として終了状態 2 で終わる。パイプから得たスクリプトは、一時ファイルに書いてから、そのパスを渡す。
- `test`・`fmt`・`skill`・`package` のコマンドラインは、後述の「`test` のコマンドライン（初回リリース版）」「`fmt` のコマンドライン（初回リリース版）」「`skill` のコマンドライン（初回リリース版）」「`package` のコマンドライン」で定める。
- `--help` は使い方を標準出力に書き、終了状態 0 で終わる。`--version` は処理系の版と、文字の分類と変換が従う Unicode の版（[標準ライブラリ](../03-interop/03-06-stdlib.md)の「Character」）を標準出力に書き、終了状態 0 で終わる。
- 【決定】`benitoite --licenses` は、処理系の実行ファイルに埋め込んだ第三者のライセンスの表示を標準出力に書き、終了状態 0 で終わる（[配布形態](../05-platform/05-01-distribution.md)の「ライセンスの表示」）。オプションなので、`run` を省いた実行のスクリプトのパスと取り違えない。

### 版と対応する形式の問い合わせ

【決定】`benitoite --version=json` は、標準出力へ UTF-8 の単一の JSON オブジェクトと末尾の LF を書く。欄の順序は契約に含めない。最初の引数にだけ指定でき、後続の引数は使い方の誤りとする。`--version=` の値は `json` だけを受け付ける。従来の `--version` は処理系と Unicode の版の二行を保ち、後続の引数を無視する。理由: 機械向けの問い合わせを明示し、既存の版表示を使う呼び出しを保つためである。

| 欄 | 型と意味 |
|---|---|
| `schemaVersion` | 整数 `1`。版問い合わせ自身の形式の版 |
| `kind` | 文字列 `"version"` |
| `name` | 文字列 `"benitoite"` |
| `version` | 処理系のパッケージの版の文字列 |
| `unicodeVersion` | `char::UNICODE_VERSION` の三つの整数を `.` でつないだ文字列 |
| `displayWidthUnicodeVersion` | 任意の文字列欄。表示の幅の Unicode の版。この版では常に `"17.0.0"` を出力し、導入前の版では欠ける。`unicodeVersion` とは別に扱う |
| `build` | 下表のビルド情報 |
| `formats` | 形式名から、対応する整数の配列へのオブジェクト |
| `loaderEnvironment` | 下記の明示したローダ変数の拒否のポリシー |

ビルド情報は、ビルド時に埋め込んだ値を返す。実行時に環境変数や Git を読んで更新しない。採取条件・明示入力・再採取の限界は[配布形態](../05-platform/05-01-distribution.md)の「ソースからのビルド」で定める。

| `build` の欄 | 型と意味 |
|---|---|
| `commit` | 完全な Git オブジェクト ID の小文字十六進文字列。不明なら null |
| `dirty` | boolean または null。未指定では自動採取せず null とする |
| `target` | Cargo の `TARGET` を埋め込んだ文字列 |
| `provenance.commit` | `environment`・`git`・`unknown` のいずれか |
| `provenance.dirty` | `environment`・`notCollected` のいずれか |

null は不明を表し、変更なしとは扱わない。明示入力の `unknown` は値を null、由来を `environment` とする。dirty の未指定は値を null、由来を `notCollected` とする。この情報はビルドの自己申告であり、ソース全体の同一性や実行ファイルの信頼を証明しない。

【決定】現在の `formats` は次の九つを持つ。`testCheckReport` と `testResults` は `[1, 2]`、ほかは `[1]` とする。ハーネスは、処理系の版の大小から能力を推測せず、必要なキーと理解する整数が含まれることを確認する。未提供の形式のキーや空の配列は出さない。

| 形式名 | 契約 |
|---|---|
| `version` | 本節の単一 JSON |
| `diagnostics` | 既存の診断と失敗の報告の JSON Lines。0.0.6 の `kind: "die"`・`code: null` を含む |
| `testResults` | 版1は既存の `test`・`testSummary` の JSON Lines。0.0.6 のテストの `failure.die` を含む。版2は `--doc` の例と集計も含む |
| `checkReport` | 「main の非実行の検査報告」の単一 JSON |
| `testCheckReport` | 「テストの非実行の検査報告」の単一 JSON。版1は通常test、版2は `--doc` |
| `effectLimit` | 「実行前のエフェクト上限の照合」の引数・包含の判定・E0512。出力オブジェクトの名前ではない |
| `loaderEnvironment` | `Process.run`・`Process.runAttached` の `Command.environment` に明示したローダ変数の拒否と下表のポリシー |
| `skillList` | 「`skill` のコマンドライン（初回リリース版）」の文書一覧の単一 JSON |
| `skillDocument` | 同節の一文書の単一 JSON |

【決定】`loaderEnvironment` のポリシーは次の欄を持つ。拒否は CLI の指定によらず適用し、既存の不正入力の検査の後、パスの絶対化と子の起動の前に行う。拒否のメッセージには元の名前の辞書順で最初の禁止名を含め、値を含めない。詳しい入力規則と継承の限界は [IO モジュール](../03-interop/03-07-io-modules.md#process) で定める。

| 欄 | 値と意味 |
|---|---|
| `schemaVersion` | 整数 `1` |
| `mode` | `"always"`。全実行に適用 |
| `deniedPrefixes` | `["DYLD_", "LD_"]`。明示した変数名の禁止接頭辞 |
| `nameComparison` | `"asciiCaseInsensitive"`。ASCII の大小を区別しない |
| `inherited` | `"unchanged"`。親から継承した変数は変更・除去しない |
| `errorKind` | `"InvalidInput"`。言語の `Result.Error(IOError)` として返す失敗の種類 |

既存の診断・テスト結果の行には `schemaVersion` や版の開始行を加えない。`--version=json` を持たない旧版が、対応する形式を自己申告したとは扱わない。欄の削除、型・必須性・意味の変更、成功の判定に新しい解釈が要る分類の追加では該当形式の版を上げる。無視しても意味が変わらない任意欄の追加は同じ版でよい。

問い合わせの成功は終了状態 0、使い方の誤りは 2、処理系の不具合は 3、標準出力への書き込み失敗は 1 とする。使い方の誤りは既存の文章の形式、不具合は既存の報告を標準エラー出力へ書く。

### ディレクトリの指定（初回リリース版）

【決定】`run`・`check` のスクリプトのパスに、ディレクトリを指定できる。ディレクトリを指定したときは、そのディレクトリの `main.bnt` を実行を始めるファイルとし、`main.bnt` がなければ使い方の誤りとして終了状態 2 で終わる。ファイルを指定したときは、`package.bnt` を除き、ファイルの名前によらず、そのファイルを実行を始めるファイルとする。`package.bnt` を入口に直接指定すると、設定ファイルを入口にできない誤りとする。

```text
benitoite run ./report            # ./report/main.bnt を実行する
benitoite run ./report/main.bnt   # 同じ
```

- どちらの場合も、実行を始めるファイルがあるディレクトリを根のディレクトリとする。import で取り込めるのは、根のディレクトリとその下のファイル、記述した依存のパッケージのモジュール、標準ライブラリだけである（[名前・スコープ・モジュール](../01-spec/01-03-names-modules.md)）。
- 処理系は、根の直下の `package.bnt` を設定ファイルとして読む（[パッケージ](06-09-packages.md)）。作業ディレクトリや親のディレクトリを辿って設定ファイルを探さない。根のディレクトリは作業ディレクトリに依存しないので、どのディレクトリから起動しても、同じファイルを取り込む。
- `test` と `fmt` にディレクトリを指定したときは、`main.bnt` だけでなく、そのディレクトリとその下のディレクトリにある、すべての `.bnt` のファイルを対象とする。`test` では、名前が完全に `package.bnt` に一致するファイルと、指定したディレクトリより下で直下に `package.bnt` を持つディレクトリの下全体を除く。各ファイルの根のディレクトリは、指定したディレクトリとする。`fmt` は設定ファイルとパッケージの中も整形する。
- Agent Skills から実行するスクリプトは、Skill のディレクトリの下の一つのファイル（と、その下のモジュール）として実行する。スクリプトの置き場所を基準にファイルを扱うには、`Process.scriptDirectory()`（[IO のモジュール](../03-interop/03-07-io-modules.md)の「Process」）を使う。

### `run` を省いた実行とシェバン（初回リリース版）

【決定】`benitoite [オプション] <スクリプトのパス> [スクリプトの引数...]` を、`benitoite run` と同じ意味とする。オプションを除いた最初の引数がサブコマンドの名前（`run`・`check`・`test`・`fmt`・`skill`・`package`）か、予約した名前（後述）であれば、サブコマンドとして扱う。サブコマンドと同じ名前のファイルを `run` を省いて実行するときは、`./check` のようにパスとして書く。スクリプトのパスにディレクトリを指定できることも、`run` と同じである。

```text
benitoite report.bnt input.csv        # benitoite run report.bnt input.csv と同じ
benitoite ./check                     # 名前が check のファイルを実行する
```

【決定】スクリプトをシェバンで実行するときは、スクリプトの 1 行目に次の行を書き、ファイルに実行の権限を与える（[字句構造](../01-spec/01-01-lexical.md)の「シェバンの行（初回リリース版）」）。

```text
#!/usr/bin/env benitoite
```

- OS は、`benitoite` に、スクリプトを起動したときのパスとスクリプトの引数を渡す。これは `run` を省いた実行に当たる。`PATH` から見つけたスクリプトには絶対パスが渡るので、サブコマンドの名前と取り違えない。
- Linux は、シェバンの行のインタプリタの名前より後を、空白で分けずに一つの引数として渡す。`#!/usr/bin/env benitoite run` は Linux では動かないので、`run` を書かない形を推奨の形とする。処理系のオプションをシェバンの行に書くには `#!/usr/bin/env -S benitoite --max-call-stack=2GiB` のように `env -S` を使う。`env -S` を持たない環境（BusyBox など）では、この形は動かない。
- シェバンの行に権限を書く仕組みはない。スクリプトは権限を宣言しない。初回リリース版は実行時の権限制御を持たない（[エフェクト](../01-spec/01-07-effects.md)）。
- Windows の OS はシェバンを解釈しない。`benitoite run` か `benitoite <スクリプトのパス>` で実行する。

### 予約したサブコマンドの名前（初回リリース版）

【決定】後で加えるサブコマンドの名前 `server`・`mcp`・`sign`・`verify`・`repl` と、加える候補の `lsp`・`agent` を予約する。予約した名前を最初の引数に書くと、その機能がまだないことを示す使い方の誤りとして、終了状態 2 で終わる。予約した名前と同じ名前のファイルは、`./server` のようにパスとして書けば実行できる。予約しなければ、`benitoite server` は名前が `server` のファイルを実行し、後でサブコマンドを加えた版で同じコマンドラインの意味が変わる。

`package` は初回リリースの後に実装したサブコマンドである。

### `skill` のコマンドライン（初回リリース版）

【決定】`skill` は、処理系の実行ファイルに埋め込んだ同梱の Agent Skill の一覧と本文の取得、コーディングエージェントが Skill を読み込む場所への導入と除去を行う。

```text
benitoite skill install   [--user | --project] [--agent <名前>]...
benitoite skill uninstall [--user | --project] [--agent <名前>]...
benitoite skill list [--format=text|json]
benitoite skill show [--format=text|json] <論理名>
```

- `skill` は、予約した名前と違い、実装したサブコマンドである。名前が `skill` のファイルを `run` を省いて実行するときは、`./skill` と書く。
- `install`・`uninstall` は、書き出した先と消した先のディレクトリのパスを標準出力に書く。
- `list`・`show` の `--format` は `=` の形だけを受け付け、`text` または `json` とする。省略は `text`。`show` の論理名と `--format` の順序は自由とする。重複、未知の値、`install`・`uninstall` への指定は使い方の誤りとする。
- text の `list` はすべての同梱文書の論理名を辞書順に一行ずつ LF で終えて書く。`show` は指定した一つの文書の本文だけを書き、末尾に改行を補わない。両方とも HOME とインストール先を参照せず、ファイルやディレクトリを作らない。
- JSON の `list` は `schemaVersion:1`・`kind:skillList`・`producer`・`documents` を持ち、`documents` は `name`・`byteLength`・`contentHash` の辞書順の配列とする。JSON の `show` は `schemaVersion:1`・`kind:skillDocument`・`producer`・`name`・`byteLength`・`contentHash`・`text` を持つ。どちらも末尾に LF を付けた単一オブジェクトとし、JSON Lines にはしない。オブジェクトの欄の順序は契約に含めず、JSON を解析して欄と値を読む。`producer` は検査報告と同じ処理系名・版・ビルド情報である。`byteLength` は版の置換後の UTF-8 本文のバイト数、`contentHash` は同じ全バイト列の SHA-256 を `algorithm:sha256` と小文字十六進の `value` で表す。
- 論理名は埋め込み一覧の相対名と完全一致するものだけを受け付け、大文字小文字を区別する。不正名・未知名、余分な引数、取得に対する `--user`・`--project`・`--agent` は使い方の誤りとし、標準出力を空にして標準エラー出力へ説明する。取得する本文と論理名の規則は [Agent Skills 対応](06-06-agent-skills.md)の「同梱文書の取得」で定める。
- 終了状態は、成功が 0、出力の書き込みに失敗した場合、ファイルを書けない・消せない場合と、既存のディレクトリを置き換えないと決めた場合が 1、使い方の誤りが 2、埋め込み一覧の不正名・重複などの処理系の不具合が 3 である。
- `--agent` の名前、書き出す先、既存のディレクトリの扱いは [Agent Skills 対応](06-06-agent-skills.md)の「Skill の導入（初回リリース版）」で定める。

### `test` のコマンドライン（初回リリース版）

【決定】`test` のコマンドラインは次の形とし、パスを一つ以上指定できる。

```text
benitoite test [オプション] <パス>...
```

- ファイルを指定したときは、そのファイルに書いたテストの関数を実行する。ディレクトリを指定したときは、その下のすべての `.bnt` のファイルのテストの関数を実行する（「ディレクトリの指定（初回リリース版）」）。ただし、`package.bnt` と、`package.bnt` を持つ下のディレクトリ（パッケージの根）は除く（[パッケージ](06-09-packages.md)）。テストの実行の規則は[利用者プログラムのテスト](06-04-test-runner.md)の「テストの実行」で定める。
- 上限を指定しない場合、検査の誤りがあるファイルは、そのファイルのテストを実行せず、診断を標準エラー出力に書く。ほかのファイルのテストは続けて実行する。
- テストごとの結果と、成功と失敗の数の集計は、標準出力に書く。`--diagnostics=json` を指定したときは、結果も JSON Lines の形で書く。報告の形は[利用者プログラムのテスト](06-04-test-runner.md)の「結果の報告」で定める。

【決定】`test --check <パス>...` は、通常の `test` と同じ入口を選び、`main` を要求せず外部の関数の照合まで行う。テストを実行せず、報告を指定しなければ成功時も標準出力は空とする。警告と誤りは、`--diagnostics` の形式で標準エラー出力に書く。検査の誤りがあってもほかの入口の検査を続ける。`--deny-warnings` を受け付けるが、明示した `--max-call-stack` と全 `--wasm-*`、`--allow-effects` は、既定値と同じ値でも併用できない。検査範囲と中断の扱いは[利用者プログラムのテスト](06-04-test-runner.md#テストの非実行の検査)で定める。

【決定】`test --doc` は、各入口の通常のテストの後へdocの例をソース位置順に加える。全入口と全実行例の検査・コンパイル・指定したエフェクト上限の照合を、最初の実行より前に終える。`--doc --check` は例も検査するが、main・テスト・出力の照合は実行しない。`--doc` のない呼び出しはdoc本文を実行用に解析しない。独立した仮想モジュールと四モードの規則は[利用者プログラムのテスト](06-04-test-runner.md#docの例)で定める。

【決定】`test` の終了状態は次のとおりとする。複数に当たるときは、表の上の行の値で終わる。

| 値 | 該当する場合 |
|---|---|
| 130 | 中断の要求を受けて終えた |
| 3 | 処理系の不具合（`internal error`）が起きた |
| 2 | 検査の誤りがある（`--deny-warnings` を指定して警告がある場合と、処理系の制限で実行できない場合を含む）。ファイルを読めない。CLI の使い方の誤り |
| 1 | 失敗したテストがある |
| 0 | 上のどれでもない |

【決定】全体拒否の集計が成功数0・失敗数0でも、非実行数があれば成功とは扱わない。文章の集計は `FAILED` とし、非実行数を `; {count} files not run` で示す。探索未完了・使い方の誤り・対象数を確定できない外側の不具合では集計を書かない。成功した空の対象は、非実行数0・中断なしの集計と終了状態0を返す。JSON Lines の kind・欄・型と形式1は保つ。

### `fmt` のコマンドライン（初回リリース版）

【決定】`fmt` のコマンドラインは次の形とする。

```text
benitoite fmt [オプション] <パス>...
```

- 指定したファイルを整形し、元のファイルを書き換える。ディレクトリを指定したときは、その下のすべての `.bnt` のファイルを整形する（「ディレクトリの指定（初回リリース版）」）。
- `fmt` は構文だけを扱い、名前解決と型検査を行わない。型検査の誤りがあるファイルも整形できる。
- 字句の誤りか構文の誤りがあるファイルは書き換えず、診断を標準エラー出力に書く。ほかのファイルの整形は続ける。構文解析器が報告するそのほかの誤り（属性の誤りなど）だけがあるファイルは整形する（[フォーマッタ](06-03-formatter.md)の「構文の誤りがあるファイル」）。
- `fmt` が読むファイルも、普通のファイルに限り、ソースの大きさの上限（256 MiB）より 1 バイト多い分までだけ読む（[ソース管理と位置情報](../02-impl/02-02-source-and-spans.md)の「ソースとファイル ID」）。FIFO などはファイルを読めない誤り（E0101）とする。
- オプション `--check` を指定したときは、ファイルを書き換えない。整形で変わるファイルの名前を、`would reformat <パス>` の形で標準エラー出力に書く。パスに含まれる端末の制御文字は、診断のファイルの表示名と同じく逃がす（[診断エンジン](../02-impl/02-10-diagnostics.md)の「文章の形式」）。
- `fmt` は標準出力に書かない。
- `fmt` は、`check` と同じく中断の要求を特別に扱わず、OS の既定の振る舞いに任せる。途中で中断されてもファイルを壊さないように、整形の結果を元のファイルと同じディレクトリの一時ファイルに書き、名前の変更（rename）で元のファイルと置き換える。
- コマンドラインで直接与えたパスがシンボリックリンクのときは、リンクを辿り、リンクの先のファイルを整形する。一時ファイルはリンクの先のファイルと同じディレクトリに作り、名前の変更でリンクの先のファイルを置き換える。リンクそのものは変えない。ディレクトリを指定したときに、その下にあるシンボリックリンクは辿らず、対象にしない。
- 一時ファイルは、作る時点から所有者だけが読み書きできる許可（0600）で作り、内容を書き終えた後に元のファイルの許可の設定を写す。理由: 書いている間に、元のファイルを読めないほかの利用者が一時ファイルの中身を読めないようにするためである。
- 次の三つの場合は、元のファイルを置き換えずに残し、ファイルを書けない誤り（E0125）として、置き換えを拒んだ理由を注記に示す。判定はリンクを辿った先のファイルで行い、複数に当たるときは上の項目の理由を示す。`--check` はファイルを置き換えないので、これらの場合も拒まない。理由: 所有者の書き込みの許可がないことは、利用者が書き換えを望まない印である。固いリンクのあるファイルを名前の変更で置き換えると、ほかの名前に古い中身が残り、所有者の違うファイルを置き換えると所有者が変わるが、どちらも利用者が気付く機会がない。
  - 所有者が、`fmt` を実行した利用者と違うファイル。
  - 所有者の書き込みの許可がないファイル（0444、0464 など。グループやほかの利用者の書き込みの許可は見ない）。
  - 固いリンクが二つ以上あるファイル。
- 一時ファイルを作れないか書けないとき、または名前の変更で元のファイルを置き換えられないときは、元のファイルを変えずに残し、一時ファイルを作っていれば消す。失敗の理由を診断として標準エラー出力に書き、一時ファイルを消せなかったときは、そのことも同じ診断に含める。ほかのファイルの整形は続ける。
- 整形の規則（正規形、コメントの保持）は[フォーマッタ](06-03-formatter.md)で定める。

【決定】`fmt` の終了状態は次のとおりとする。複数に当たるときは、表の上の行の値で終わる。

| 値 | 該当する場合 |
|---|---|
| 3 | 処理系の不具合（`internal error`）が起きた |
| 2 | 構文の誤りがあるファイルがある。ファイルを読めない、または書き換えられない。CLI の使い方の誤り |
| 1 | `--check` を指定して、整形で変わるファイルがある |
| 0 | 上のどれでもない |

### `package` のコマンドライン

【決定】手元のパスの依存を追加・更新し、入口の先頭の記述を設定ファイルへ移す命令を次の形で受け付ける。

```sh
benitoite package add    [オプション] <別名> --path <ディレクトリ> [<根か入口>]
benitoite package update [オプション] [<別名>] [<根か入口>]
benitoite package move   [オプション] <入口>
```

【決定】`--path <値>` と `--path=<値>` の両方を受け付ける。値は UTF-8 の文字列とし、指定した根からの相対パスか絶対パスとして解決して、その文字列を記述に写す。三つの命令は `--diagnostics=text|json` を受け付ける。結果は文章だけを標準出力に書き、診断と使い方の誤りは標準エラー出力に書く。`--json` は設けない。

【決定】`add`・`update` の根か入口を省けば作業ディレクトリを根とする。ファイルならそのファイルを入口とし、ディレクトリなら `main.bnt` があるときだけそれを入口とする。`package.bnt` 自体を指定した場合はそのディレクトリを根とし、入口にはしない。明示した `package.bnt` が存在しなければ E0101 とし、ほかのファイルへ書かない。`update` の位置引数が一つの場合、大文字で始まる識別子なら別名とし、ほかはパスとする。識別子の形のパスは `./Name` と書く。`move` の入口は必須であり、ディレクトリは使い方の誤り、`package.bnt` は E0928 として拒否する。理由: ファイルを変更する命令では、移す入口を明示させるためである。

【決定】`add` は既に依存のあるファイルに書く。どちらにもなければ、`package.bnt` があるときはそこへ、なければ入口へ書く。どちらもなければ E0927 とし、入口の指定を求める。`update` は同じ場所の依存を更新し、別名を省けば `hash` のある依存だけを対象とする。別名を指定したときは `hash` がなければ加える。`move` は入口と同じディレクトリの `package.bnt` へ移す。意味と書き込みの条件は[パッケージ](06-09-packages.md)の「`benitoite package`」で定める。

標準出力には、変更したファイル、依存の別名とパッケージの名前、ハッシュ、エフェクト、コンポーネントの検査結果を書く。`update` は保存した記録とのエフェクトの増減を示し、記録がないか形が誤っていれば `(not recorded)` と現在の一覧を示す。ハッシュが変わらずエフェクトだけを更新したときは、ハッシュを一つだけ示す。対象がない一括更新は `no dependencies with hash to update` と書く。ハッシュとエフェクトの記録が同じなら `unchanged` の一行を書き、ファイルを置き換えない。`move` は移した項目と二つのファイルを書く。パスなどに含まれる端末の制御文字は逃がす。

【決定】終了状態は次のとおりとする。

| 値 | 該当する場合 |
|---|---|
| 3 | 処理系の不具合 |
| 2 | 字句・構文の誤り、依存の検証の誤り、読み書きの失敗、使い方や命令の前提の誤り |
| 0 | 成功。`update` で変わらなかった場合と対象の依存がない一括更新も含む |

### オプション

【方針】`run`・`check`・`test` は次の表のうち、そのコマンドを対象とするオプションを受け付ける。【決定】`fmt` は、`--diagnostics` と `--check` を受け付ける。

| オプション | 意味 | 既定 |
|---|---|---|
| `--diagnostics=text` または `--diagnostics=json` | 診断・実行時エラー・資源の不足・処理系の不具合の報告の形式（[診断エンジン](../02-impl/02-10-diagnostics.md)）。`json` を指定しても、単一の検査報告に収める場合を除く使い方の誤り、`main` が返した `Result.Error` の文字列、ヒープの確保の失敗で abort するときのメッセージは文章のまま書く。`test` では、テストの結果の報告の形式も決める | `text` |
| `--max-call-stack=<大きさ>` | 呼び出しの情報の合計の上限。`512MiB`・`2GiB` のように、`KiB`・`MiB`・`GiB` を付けた整数で書く。`run` と `test` で意味を持ち、`test` では一つのテストごとの上限とする | `1GiB` |
| `--wasm-memory=<大きさ>` | `run`・`test` の外部の関数の Store 全体（補助を含む）の線形メモリの上限 | `64MiB` |
| `--wasm-fuel=<整数>` | `run`・`test` の外部の関数の呼び出しごとの燃料 | `10000000000` |
| `--wasm-transfer=<大きさ>` | `run`・`test` の引数と戻り値それぞれの受け渡しの予算。補助では構築の予算にも同じ値を使う | `256MiB` |
| `--wasm-stats` | `run`・`test` の起動全体の外部の関数の消費量を JSON の一行で標準エラー出力に報告 | 指定しない |
| `--deny-warnings` | 警告を誤りとして扱い、警告があれば検査の誤りと同じく終了状態 2 で終える。`check`・`run`・`test` で意味を持つ | 指定しない |
| `--report=json` | `check` と `test --check` の検査結果を単一の JSON として標準出力に書く。分離した値は受け付けない。明示した `--diagnostics=text` との併用は使い方の誤りとする | 指定しない |
| `--allow-effects=<集合>` または `--allow-effects <集合>` | `run` の main または `test` の各テストの宣言上限が、指定した原子的な組み込みエフェクトの集合に含まれるかを実行前に照合する。空文字列は空集合。サブコマンドを省いた実行でも受け付ける | 上限を掛けない |
| `--doc` | `test` で入口のdocの例を検査・実行する | なし |
| `--check` | `test` はテストを実行せず外部の関数の照合まで行う。`fmt` はファイルを書き換えず、整形で変わるファイルがあれば終了状態 1 で終える | 指定しない |

知らないオプション、値の誤ったオプション、スクリプトのパスがない場合、同じオプションを二度書いた場合、そのサブコマンドが受け付けないオプションを書いた場合、`check` でスクリプトのパスの後に引数を書いた場合は、使い方の誤りとして、誤りの内容と `--help` を使うよう示す文を標準エラー出力に書き、終了状態 2 で終わる。ただし、単一報告を指定した `check` と `test --check` は報告内に収める。

【決定】`check` はスクリプトより前のオプションの範囲を最後まで走査し、有効な `--report=json` が一つでもあれば、使い方の誤りを `checkReport` の `usageError` に収める。`--diagnostics=text` との併用や未知のオプションと report の順序を入れ替えても、報告の種類は変わらない。明示した diagnostics=text と、省略時の既定値は区別する。途中の誤りは最初のものを保持し、走査後に併用条件、パスの有無を検査する。理由: 誤りの位置によって機械向けの報告が文章へ変わることを防ぐためである。

`run`・`check`・`test` の値を取るオプションは、`run`・`test` の `--allow-effects` を除き `=` を用いた指定だけを受け付ける。誤りの後の走査でも、既知の値を取る diagnostics・max-call-stack・report・allow-effects・wasm-memory/fuel/transfer に `=` がなければ、直後の一引数を分離値として消費する。この消費規則は、コマンドの語を選ぶ走査にも適用する。`run`・`test` の `--allow-effects` 以外の分離値の指定は従来どおり拒否する。`check` が受け付けない wasm のオプションは未知のオプション、`--allow-effects` はコマンドに適さないオプションとして拒否する。例えば `check --allow-effects --report=json main.bnt` の report の字面は allow-effects の分離値なので、報告モードを選ばない。スクリプトの後の字面も報告モードを選ばない。有効な report がなければ、使い方の誤りは従来の文章の二行を標準エラー出力へ書く。`run` は report を受け付けない。

【決定】`--wasm-memory` と `--wasm-transfer` は、バイト数か `KiB`・`MiB`・`GiB` つきの整数を受け取り、1 MiB 以上 4 GiB 以下を許す。`--wasm-fuel` は 1 以上 2^64−1 以下の十進整数を受け取る。符号・小数・空の値・範囲の外・重複の指定は使い方の誤りである。`--wasm-stats` は値を取らず、`--wasm-stats=` のように値を付けた指定は、値を取らないことを示す使い方の誤りである。`check` と `fmt` はこの四つの引数を受け付けない。経路で受け渡しの量の数え方が異なる。補助の転送形式は u32 の全長に限られ、CLI で 4 GiB を指定してもその表現上限を超えられない。補助のコピーもメモリと燃料へ含め、既定値を自動で上げない。統計は経路ごとの `routes`・事前の振り分けの `fallback_reasons`・補助の論理上の構築量の `construction_bytes`・内部の報告の `adapter_failures` を含む。上限の数え方と報告の欄は [03-10「実行」](../03-interop/03-10-external-functions.md#実行)で定める。理由: 上限の値を実行前に確かめ、単位の解釈を一意にするためである。

### 実行前のエフェクト上限の照合

【決定】標準内部宣言Log.Logは、型表示・許可名・検査報告でLogと表示する。利用者が同じ綴りで宣言したエフェクトには適用しない。LogはIO.Allに含めず、宣言上限に残るときは明示的な許可を要求する。schemaVersion=1とbasis=declaredUpperBoundを保ち、本体が実操作を呼ばない場合も宣言上限を報告する。

【決定】main と `@test` の宣言上限に残る未処理の `Failure.Fail[E]` は、通常の入口の型検査で E0506 として拒否する。Fail は `IO.All` の展開、`--allow-effects` の許可名、検査報告の `expanded` に含めない。Fail を handle または toResult で処理した入口だけを契約の抽出へ渡し、未確定の行や NoFail の条件も成功した空集合へ補わない。検査報告と上限の照合の形式番号は変えない。

【決定】`run --allow-effects` は、main の検査成功後、脱糖・コード生成より前に、main の宣言した原子的エフェクトの集合が指定した集合に含まれるかを組み込みの ID で比較する。余分な許可は拒否しない。`IO.All` の宣言は、型検査で展開済みの集合として比較する。本体が使わない宣言上限も比較に含める。照合した同じ検査済みプログラムだけをコンパイルし、ソースの再読や再検査を行わない。理由: 検査した契約と実行する成果物を一致させるためである。

【決定】main と `@test` の上限は、個別の `uses` とファイル単位の宣言を合併した Scheme から得る。本体が純粋でも、ファイルから追加した `Console.Write`・`Log` 等を許可の照合から除かない。E0512 では関数名を主位置とし、不足した効果のファイルの追加元を補助位置で示す。同じ IO.All の展開先が複数不足しても、その追加元は一度だけ示す。

【決定】集合は正規名のカンマ区切りで、順序を問わない。正規名は `State`・`Console.Read`・`Console.Write`・`File.Read`・`File.Write`・`Process.Run`・`Process.Exit`・`Process.Environment`・`Clock.Time`・`Random.Generate`・`Http.Listen`・`Http.Connect`・`Assert.Check`・`Log` の14個とする。名前への変換は型表示と検査報告が使う共通の変換に従う。空文字列は空集合とし、重複名、空の要素、空白、未知名、`IO.All`、利用者定義名、import の別名、`*` を使い方の誤りとする。値を trim しない。二度の指定と値の欠落も使い方の誤りとする。`check`・`test --check`・`fmt` はこのオプションを受け付けない。`run` のスクリプト以後にある同名の引数は、そのままスクリプト引数とする。

【決定】不足時は main の名前を主位置とする E0512 を一件返し、終了状態2で拒否する。不足と許可の集合を正規名の辞書順にカンマと空白で区切った注記とし、空集合は `(none)` と表示する。help は必要なエフェクトを確認してから許可を変えるよう案内し、編集を付けない。既存の検査失敗と処理系の不具合を優先し、E0512 に置き換えない。診断は既存の文章または JSON Lines の形式で標準エラー出力へ書き、拒否したスクリプトの標準出力や外部操作を開始しない。

【決定】`test --allow-effects` は、各入口の `@test` の宣言上限を同じ集合と比較する。`Assert.Check` も比較に含め、取り込んだモジュールのテストや実行対象でない関数の契約は含めない。不足した関数ごとに E0512 を入口順・宣言順で出す。全入口の検査・照合・コンパイル・実行準備が成功するまで一つもテストを始めず、成功した成果物を保持して順に消費する。通常の検査失敗・不足・コンパイル制限では後の入口の準備も続け、全体を終了状態2で拒否する。不具合は3、中断は130で止める。探索完了後、実行開始前に全体を拒否した場合はテストの結果行を作らず、集計の `passed`・`failed` を0、`filesNotRun` を全入口数とする。詳細は[利用者プログラムのテスト](06-04-test-runner.md#テストの実行)で定める。

この照合は宣言した契約への静的な制約であり、実行時の権限制御や OS のサンドボックスではない。検査報告と後の実行は別の検査であり、報告の `expanded` を許す集合に渡してもソースの内容を固定しない。報告後に許す集合の外のエフェクトを追加すれば実行の前の型検査（E0501 など）か E0512 で拒否するが、同じ `File.Write` のまま書き込み先や内容だけを変えた場合は拒否できない。操作の対象、外部コマンドが行う操作、意図との一致、実行の成否、停止性を保証しない。

上限付き `test` は入口の選択を一度だけ行い、準備を終えた成果物を実行する。入口ごとの準備の間に依存が変われば、異なる内容の成果物を持ちうるが、それぞれの契約を照合する。全対象の一時点のスナップショットは保証せず、選択後に追加されたファイルを途中から実行対象に加えない。

### サブコマンドの振る舞い

【方針】`check` は、スクリプトを読み込みから外部の関数の照合まで検査する（[パイプライン](../02-impl/02-01-pipeline.md)）。誤りがなければ終了状態 0 で終わる。報告を指定しない場合、警告があれば、誤りがなくても警告を標準エラー出力に書く（`--deny-warnings` を指定したときを除き、終了状態は 0 のまま）。誤りも警告もなければ何も出力しない。誤りがあれば、診断を標準エラー出力に書き、終了状態 2 で終わる。報告を指定した場合の出力は次節で定める。

【方針】`run` は、スクリプトを検査し、誤りがなければ実行する（[スクリプト実行と埋め込み](../02-impl/02-11-embedding.md)）。検査の誤りは `check` と同じく報告して終える。処理系の制限による誤り（`L` で始まる診断コード）はコード生成の段で見つかるので、`run` と通常の `test` でだけ報告される（[診断エンジン](../02-impl/02-10-diagnostics.md)）。このため、`check` または `test --check` が終了状態 0 で終えたスクリプトを、`run` または通常の `test` が終了状態 2 で終えることがある。

### main の非実行の検査報告

【決定】`benitoite check --report=json <スクリプト>` は、`main` を必須とする通常の検査を一度行い、単一の JSON オブジェクトと末尾の LF を標準出力に書く。利用者の関数は実行せず、脱糖・コンパイルもしない。`--diagnostics=json` を併記でき、診断は報告内だけに収め、標準エラー出力へ重ねて書かない。キーの順序と JSON の空白は契約に含めない。

【決定】`targets[0].main.effects.expanded` と `aggregateEffects.expanded` は、ファイル単位の宣言の追加分も含む。受け手は本節末尾の成功条件をすべて確認したうえで、合併後の宣言上限を人間へ示す。main の行だけを読み、個別の `uses` がないことを純粋な契約と扱わない。通常の `check` の標準出力には、上限を表示する行を加えない。

| 必須欄 | 型と意味 |
|---|---|
| `schemaVersion`・`kind` | 整数 `1`、文字列 `checkReport` |
| `producer` | `{name, version, build}`。版とビルド情報は「版と対応する形式の問い合わせ」と同じ |
| `status` | 検査と抽出の成功は `ok`、検査・読み取りの失敗は `checkError`、使い方の誤りは `usageError`、内部エラーの診断があれば `internalError` |
| `complete` | `status: ok` の場合だけ true |
| `targetsComplete` | 入口を選べた報告では true、使い方の誤りでは false。型検査の成功とは独立 |
| `executed` | 常に false |
| `requestedTargets` | `[{requestIndex: 0, path: 指定したパス}]`。パスなしの使い方の誤りでは空配列 |
| `targets` | 下記の Target 一件。使い方の誤りでは空配列 |
| `sources` | 読み込んだ全ソース。[ソース管理と位置情報](../02-impl/02-02-source-and-spans.md#検査報告のソース識別)で定める |
| `sourceSets` | `[{targetId: "t0", sourceIds: ファイルID順のソース識別値の配列}]`。ソースを一件も保持しなければ sourceIds は空配列。使い方の誤りでは sourceSets 全体が空配列 |
| `aggregateEffects` | 完全な成功では main の Effects、それ以外は null |
| `diagnostics` | 既存の診断 JSON と同じオブジェクトの配列。順序も通常の検査と同じ。使い方の誤りだけ `kind: "check"`・`code: null` を認める |
| `diagnosticTargets` | 診断一件ごとに `{diagnosticIndex: 0始まりの添字, targetId: "t0"}`。使い方の誤りの targetId は null |

Target は `targetId: "t0"`、`requestIndex: 0`、`entry`（入口の表示名）、`root`（根の表示名）、`sourceId`（入口の識別値。読めなければ null）、`kind: "main"`、`status`、`complete`、`main` を持つ。`status` と `complete` は報告全体と同じ値とする。`main` は成功時に次の欄を持ち、検査失敗では全体を null とする。

| Main の欄 | 値 |
|---|---|
| `symbol` | `main` |
| `location` | 名前の位置。既存の診断と同じ `{file,start:{line,column,offset},end:{line,column,offset},label:""}`。行と列は1始まり、offsetは元のバイト列の0始まり |
| `effects` | `{basis: "declaredUpperBound", expanded: 正規名の辞書順の配列}` |
| `processShellReference` | 標準の `IO.Process.shell` への式の参照があれば `present`、なければ `absent` |
| `shellReferenceScope` | `checkedProgram` |

Effects は宣言した上限であり、本体が実際に行う操作の最小集合ではない。`IO.All` は `Clock.Time`・`Console.Read`・`Console.Write`・`File.Read`・`File.Write`・`Process.Environment`・`Process.Exit`・`Process.Run`・`Random.Generate`・`State` の十個へ開く。`Http.Connect`・`Http.Listen`・`Log` は `IO.All` に含めず、宣言にあれば報告する。`main` に `Assert.Check` を宣言した場合は、通常の検査と同じく E0415 で拒否する。純粋な成功は `expanded: []`、不明な集合は Effects 全体の null とする。

`or die` の `Process.Exit` は型検査の集合から得る。完全なハンドラで処理して宣言した上限から外せば報告にも含めず、宣言に残せば報告にも残す。裸の `try` と `or return` は `Process.Exit` を加えない。理由: 構文からエフェクトを推測して後付けすると、ハンドラで処理した結果と宣言した上限を取り違えるためである。

shell は入口・依存・標準ソースを含む検査対象全体の式の参照であり、main からの到達性は調べない。直接の呼び出しに加え、関数の値の取得と、呼ばれない関数の中の参照も含める。IO.Process の import だけ、コメントと文字列、同名の利用者定義、ハンドラの操作名だけは参照に含めない。IO.Process が未読なら absent とし、判定のために読み込まない。main が null なら shell の参照も未確定であり、参照なしとは推定しない。

E0414（main なし）、E0101（読み取り）、構文・名前・型の誤りでも、読み込めたソースと既存の診断を残す。`--deny-warnings` で昇格した警告も `checkError` とする。標準ソース内の誤りでは通常の check と同じく内部エラーの診断一件だけを返す。標準ソース内の誤りと契約の抽出の失敗は `internalError` とし、成功した空集合にはしない。終了状態は成功0、検査失敗2、内部エラー3、出力への書き込み失敗1とする。

使い方の誤りは終了状態2、`status: "usageError"` とする。指定したパスは requestedTargets に残し、パスがなければ空配列にする。入口は未確定なので targets・sources・sourceSets は空配列、aggregateEffects は null、targetsComplete・complete は false とする。診断は位置とコードを持たず、誤りの説明を message に入れ、secondary・notes・helps は空配列にする。ディレクトリに main.bnt がない誤りもこの形式で返す。

【決定】報告モードの確定後は、入口の選択、検査と契約の抽出、報告の組立と JSON の直列化までに捕捉できた panic を `internalError`・終了状態3の単一報告へ収める。段のスレッドで捕捉した panic は、既存の診断が持つ段・スレッド・内容を保つ。確定した入口と、報告側へ渡し終えたソースを保持し、検査や読み取りを繰り返して補わない。検査段の巻き戻しでソースを持ち出せなかった場合は sources を空配列、入口の sourceId を null とし、選択済みの Target と sourceIds が空配列の sourceSets の行を残す。いずれも complete は false、main と aggregateEffects は null であり、成功した空集合にはしない。

【決定】JSON 全体と末尾の LF を組み立ててから書き込みを一度だけ試みる。書き込みか flush の失敗は終了状態1とし、途中の出力に別の報告を継ぎ足さず、標準エラー出力へも再送しない。理由: 一つの報告の断片と、別の失敗報告が混ざることを防ぐためである。

【決定】報告の受け手は、完全な単一の JSON、理解する schemaVersion と kind、status:ok、complete:true、終了状態0のすべてを確認してから aggregateEffects を確定した集合として使う。未知の status・エフェクト名を成功や空集合へ読み替えない。この条件はテストの検査報告にも適用する。理由: 部分的に成功した入口があっても、全体の検査が成功したとは限らないためである。

報告の認識前の初期化失敗、報告の境界の外側や失敗報告自身の組立の panic、abort、強制終了、出力の切断には完成した報告を保証しない。失敗報告の組立が内部エラーを返した場合は、書き込み前に限り既存の標準エラー出力の経路で終了状態3を返す。中断は OS の既定に任せる。

### テストの非実行の検査報告

【決定】`benitoite test --check --report=json <パス>...` は、[利用者プログラムのテスト](06-04-test-runner.md#テストの非実行の検査)で定める同じ探索・検査・テストの収集を一度行い、単一の JSON と末尾の LF を標準出力に書く。診断を標準エラー出力へ重ねず、テストの実行結果と集計も出さない。`--diagnostics=json` を併記できる。明示した `--diagnostics=text` との併用は使い方の誤りとする。

【決定】報告は「main の非実行の検査報告」と同じ共通欄を持ち、`kind` は `testCheckReport`、`schemaVersion` は通常testでは1、`--doc` では2とする。`requestedTargets` は全指定パスを指定順に持ち、各項目は `requestIndex` と `path` を持つ。`targetsComplete` は探索を最後まで終えたかを示す。`complete` は探索と全入口の検査・抽出に成功した場合だけ true とし、`executed` は false とする。`status` と終了状態は、成功が `ok`・0、検査・探索の失敗が `checkError`・2、使い方の誤りが `usageError`・2、処理系の不具合が `internalError`・3、既存の確認点で捕捉した中断が `interrupted`・130 である。書き込みと flush の失敗は1で終える。

Target の共通欄は `targetId`・`requestIndex`・`entry`・`root`・`sourceId`・`kind`・`status`・`complete` とする。`kind` は `tests` とし、`main` は出さない。`tests` の各項目は `function`・`description`・`location`・`effects` を持つ。説明の省略は null、明示した空の説明は空文字列である。位置は通常のテストの JSON と同じ名前の位置とし、`label` は空文字列とする。エフェクトは宣言した上限の原子的な正規名を辞書順で重複なく並べ、`Assert.Check` も残す。`processShellReference` と `shellReferenceScope` は Target に置き、検査対象全体に対して main の報告と同じ規則で求める。

成功したテストなしの入口は `tests: []`、未確定の入口は `tests: null`・`processShellReference: "unknown"` とする。通常の検査の誤りの後も次の入口を検査し、成功した入口の結果を保持する。不具合と中断では未着手の Target も残し、中止原因の status と complete:false を付ける。探索に失敗した場合は先に選び終えた入口だけを未検査の参考情報として残し、どの入口も検査せず、各 Target は checkError・complete:false とする。空ディレクトリは targets:[] の成功である。

`aggregateEffects` は全体が complete:true の場合だけ全テストの和を Effects の形で持ち、それ以外は null とする。成功した空の対象は空集合である。sources は Target 順と FileId 順を保ち、同じファイルの明示した重複も別の識別値で表す。sourceSets は全 Target に一行ずつ持ち、未着手の入口の sourceIds は空配列とする。diagnosticTargets は診断一件に一行を持ち、診断の添字と対象の targetId を対応させる。探索全体・使い方の誤りの targetId は null とする。

【決定】test の全オプションの範囲を最後まで走査し、有効な `--report=json` が一つでもあれば、先行する使い方の誤りも testCheckReport に収める。`--check` のない `test --report=json` も usageError・2とし、実行しない。既知のオプションの分離値はその場で消費し、値を report 指定に取り違えない。report を認識しなければ従来の文章の使い方の誤りを返す。

【決定】探索から検査・抽出・報告の組立と直列化までの捕捉できた panic は、単一の internalError の報告へ収める。処理済みの入口と持ち出し済みのソースだけを保持し、検査や読み取りを繰り返さない。検査段の巻き戻しでソースを持ち出せなかった入口は sourceId:null・空の sourceIds とする。直列化後の書き込みは一度だけ行い、失敗後に報告を継ぎ足さない。完成した報告の保証外は main の報告と同じとする。中断の確認点と保証の範囲は[利用者プログラムのテスト](06-04-test-runner.md#テストの非実行の検査)で定める。

【決定】版2は共通欄とTarget.testsを保ち、Targetへ `docExamples` と `ignoredDocBlocks` を追加する。抽出できた0例は空配列、抽出未完了はnullとする。各例は `id`（path:line:doc:index）・`mode`（test/check/error/run）・元の `location`・仮想入力の `sourceId`・`status`・`complete`・`effects`・`tests`・`expectedDiagnosticCodes`・`observedDiagnostics` を持つ。未確定の効果とテスト一覧はnull、確定した空は空配列とする。期待した静的拒否は例の成功としてobservedDiagnosticsだけへ保存する。期待不一致や予期しない拒否は例・Target・全体をcomplete:false、checkErrorとする。実行時の期待不一致は例単位のテスト失敗である。

【決定】版2のaggregateEffectsは、通常テストとtest/run例の宣言上限だけを合併する。check/error例を実行権限へ足さない。sources/sourceSetsには元コメントと実際に検査した仮想入力を含め、例の診断にはdiagnosticTargetsの `docExampleId` で所属を示す。期待した拒否の診断は通常のdiagnosticsへ重ねない。`--doc` のJSON LinesはtestResults版2であり、理解するハーネスだけが指定する。行にschemaVersionや開始行は足さず、最後の行はtestSummaryとする。

### 標準入出力

【方針】

- `run` と、報告を指定しない `check` では、標準出力には、スクリプトが書いた内容だけを書く。`check --report=json` は単一の検査報告を、`--help`・`--version`・`--version=json`・`--licenses` はそれぞれの問い合わせの結果を標準出力に書く。`test`・`fmt`・`skill`・`package` が標準出力に書くものは、「`test` のコマンドライン（初回リリース版）」「`fmt` のコマンドライン（初回リリース版）」「`skill` のコマンドライン（初回リリース版）」「`package` のコマンドライン」で定める。
- `run` と、単一報告を指定しない `check` の標準エラー出力には、スクリプトが書いた内容、診断、実行時エラー・資源の不足・処理系の不具合の報告、`main` が返した `Result.Error` の文字列、使い方の誤りを書く。
- `check --report=json` と `test --check --report=json` は、警告・使い方の誤り・捕捉した不具合を含む診断を、標準出力の単一報告に収める。標準エラー出力へ重ねず、書き込み失敗後の報告も加えない。完成した報告の保証外の失敗は、各報告の節で定める。
- `run` で `--wasm-stats` を指定した場合は、実行の終わりに外部の関数の上限と消費量を JSON の一行で標準エラー出力へ書く。
- `run` では、スクリプトは `Console.Read` の操作で標準入力を読める（[IO のモジュール](../03-interop/03-07-io-modules.md)、[スクリプト実行と埋め込み](../02-impl/02-11-embedding.md)）。

### 終了状態

【決定】通常の `run` と `check` の終了状態は、次の 4 つとする。単一の検査報告の終了状態は「main の非実行の検査報告」で定める。`test`・`fmt`・`skill`・`package` の終了状態は、「`test` のコマンドライン（初回リリース版）」「`fmt` のコマンドライン（初回リリース版）」「`skill` のコマンドライン（初回リリース版）」「`package` のコマンドライン」で定める。

| 値 | 意味 | 該当する場合 |
|---|---|---|
| 0 | 成功 | `check` で誤りがない。`run` で `main` が `()` か `Result.Ok(())` を返した |
| 1 | スクリプトの実行の失敗 | `main` が `Result.Error` を返した。実行時エラー、資源の不足で止まった。コマンドライン引数が正しい UTF-8 でない |
| 2 | 検査の誤りと使い方の誤り | 検査の誤りがある。`--deny-warnings` を指定して警告がある。処理系の制限で実行できない。スクリプトのファイルを読めない。CLI の使い方の誤り |
| 3 | 処理系の不具合 | 処理系の不具合（`internal error`）が起きた |

単一の検査報告では、書き込みか flush の失敗による終了状態1を、報告内の status に対応する値より優先する。版の問い合わせの出力失敗も1とする。

【決定】`run` は、上の表に加えて、次の終了状態で終わることがある。

- スクリプトが `Process.exit(code)` でプロセスを終えたときは、`code`（0 以上 255 以下。[IO のモジュール](../03-interop/03-07-io-modules.md)）で終わる。`code` が 1〜3 のときは上の表の値と重なるので、ハーネスは、標準エラー出力に処理系の形式の失敗の報告があるかで区別する。`Process.exit` で終えたときは、解放と出力の書き出しの失敗の報告に加え、`--wasm-stats` を指定していれば統計の行を書く。統計の行だけでは失敗と判定しない。
- 中断の要求（`SIGINT`・`SIGTERM`）を受けて、リソースを解放してから終えたときは、130 で終わる。

【決定】内部の終了結果 `RunEnd` は、`main` の `Result.Error` の文字列とは別に、明示的な失敗終了の原因・任意の説明・ソース位置を `die_failure` に保持できる。原因と説明は所有した文字列とし、説明なしと空の説明を区別する。描画の入口は、`EndKind::Exited(1)` にこの情報がある場合だけ、`error: explicit failure exit` と位置、説明があれば `message: ...` の注記、常に `cause: ...` の注記を出す。JSON は既存の診断の形式で `kind: "die"`・`code: null` とし、主文・主位置・注記を同じ内容にする。

出力の最後の転送を終えてから、この報告を一度だけ描画し、解放・書き出しの失敗は `reports` の順で後に描画する。補足の失敗によって終了状態 1 を変えない。通常の終了・中断・処理系の不具合は従来の分類を保つ。ソースの `or die` から終了操作を実行し、採用した終了理由に限って `die_failure` を保持する。

【決定】処理系がヒープの確保に失敗したときは、Rust の標準ライブラリの既定の振る舞いで終わる。標準エラー出力にメッセージを書いてプロセスを abort し、終了状態は OS が決める。処理系はこのときの終了状態を定めない。OS の側でメモリが足りなくなったときの終わり方も定めない（[ランタイム](../02-impl/02-09-runtime.md)）。このとき、標準エラー出力に処理系の形式の診断はない。上の表のどの値でもない終了状態で終わったとき、または処理系の形式の診断がないときは、処理系が異常に終わったものとして扱う。【決定】処理系はヒープの使用量に上限を設けない。メモリの使用量を抑えるときは、処理系を起動する側（ハーネス、`ulimit`、コンテナなど）で上限を掛ける。

標準出力か標準エラー出力の読み手が先に終わった（パイプが閉じた）ときは、書き込みの失敗による実行時エラーとして扱い、終了状態 1 で終わる（[ランタイム](../02-impl/02-09-runtime.md)）。

`run` と `test` は、中断の要求を受けたら、すべてのタスクを取り消し、`with` のリソースを解放し、出力を書き出してから、終了状態 130 で終わる。解放の途中で二度目の中断の要求を受けたら、OS の既定の振る舞いで終わる（[スクリプト実行と埋め込み](../02-impl/02-11-embedding.md)）。`check`・`fmt`・`package` は、中断の要求を特別に扱わず、OS の既定の振る舞いに任せる。

### 開発用の設定

【方針】IO の実行方式（直接呼び出しと、要求と応答。[ランタイム](../02-impl/02-09-runtime.md)）は、利用者向けのオプションにしない。処理系の開発者が性能測定などで切り替えるために、環境変数 `BENITOITE_DEV_IO_MODE` を読む。値は `direct`（直接呼び出し）か `request`（要求と応答）で、既定は `direct` とする。この環境変数は開発用であり、利用者向けの文書には載せず、予告なく変えることがある。
