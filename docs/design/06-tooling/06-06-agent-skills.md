# Agent Skills 対応


## 目的と範囲

処理系に同梱する Agent Skill（Benitoite のスクリプトをコーディングエージェントに書かせるための Skill）について、次のものを定める。

- Skill の構成と、各ファイルの作り方
- Skill を利用者の環境に導入し、同梱文書を取得するサブコマンド `skill`
- Skill がエージェントに求める、実行の前の確認の手順
- Skill の評価の方法
- LLM 向けと設計者向けの言語の文書（英語の言語リファレンスと、日本語の訳）の位置付け

構文の制約付きの生成（tree-sitter の文法などを使うもの）と、学習データに入るための取り組み（`llms.txt` など）は、初回リリース版に含めない。

## 前提

【決定】初回リリース版の処理系は、実行時の権限制御も OS のサンドボックスも持たない。スクリプトは、処理系を起動した利用者の OS の権限で行える操作をすべて行え、スクリプトが触れる範囲の制限は、処理系を起動する側（ハーネスのサンドボックス、コンテナ、OS の権限）に委ねる（[セキュリティモデル](../07-quality/07-01-security-model.md)の「ハーネスとの分担」）。

Agent Skills の仕様（[Specification](https://agentskills.io/specification)、2026-09-29 に確認）では、Skill は `SKILL.md` を置いたディレクトリである。`SKILL.md` は YAML の前付けと Markdown の本文からなり、前付けの `name` と `description` は必須である。`name` は英小文字・数字・ハイフンで書き、親のディレクトリの名前と一致させる。任意の欄に `license` と `metadata` がある。エージェントは、起動のときに `name` と `description` だけを読み、Skill を使うと決めたときに `SKILL.md` の本文を読み、`references/` などのほかのファイルは必要になったときに読む。仕様は、`SKILL.md` を 500 行より短くし、詳しい参照の資料を別のファイルに分けることを勧めている。

利用者が作る Skill の中の Benitoite のスクリプトは、Skill のディレクトリの下の一つのファイル（と、その下のモジュール）として実行し、スクリプトの置き場所を基準にファイルを扱うには `Process.scriptDirectory()` を使う（[CLI](06-01-cli.md)の「ディレクトリの指定（初回リリース版）」）。本章の Skill は、これとは別に、エージェントに Benitoite の書き方を教えるための Skill である。

## 仕様

【決定】生成する文法は構文の章の文法と、コードブロックの外にある名前付き引数・穴・パイプの条件を合わせて説明する。標準ライブラリの型表示には公開のパラメータ名と内側の関数型の名前を保持する。構文の章・標準宣言・診断の表を変えた場合は生成器で参照文書を作り直し、生成物は手で編集しない。

### 同梱の Agent Skill の構成

【決定】失敗処理の手本は、入口で原因を報告して終了する `or die` と、再利用する関数で失敗を返す `or return` を書き分ける。裸の try は今後も返す意味に固定し、警告や整形による自動変更は行わない。Skill は、die の任意の戻り値・Process.Exit・Result の Show 制約、説明→表示→終了の順、成功側の未評価、4 種の標準失敗型の表示を案内する。Process.Exit の人間向けの説明には、失敗の原因と説明が標準エラー出力へ報告されることも含める。終了操作のハンドラによる処理、テストの失敗と続行、静的検査が停止性や外部操作の成功を保証しないことも示す。

【決定】同梱の Agent Skill は、手で書く短い `SKILL.md` と、必要なときに読む参照の文書（`references/` の下のファイル）からなる。理由: エージェントは `SKILL.md` の本文を Skill を使うと決めたときに読み、ほかのファイルは必要になったときに読むので、常に読む部分を短くし、詳しい資料を必要なときだけ読ませられるからである。Skill の名前は、コマンドの名前に合わせて `benitoite` とする。

| ファイル | 内容 | 作り方 |
|---|---|---|
| `SKILL.md` | 作業の手順と、主な言語の規則の要約。後述の「実行の前の確認」の手順を含む | 手で書く |
| 文法 | EBNF による文法の全体 | [構文](../01-spec/01-02-syntax.md)の「初回リリース版の文法の全体」から生成する。日本語の注釈（`(* … *)`）は除く |
| 標準ライブラリのリファレンス | モジュールごとの関数・型・エフェクトの宣言と説明。モジュールごとに、標準か非公式かの状態と、取り込みの名前（`import Benitoite.Unofficial.IO.Console` など）を示す | 標準ライブラリのソースの宣言の型とドキュメントコメントから生成する |
| 診断コードの説明 | 診断コードごとの誤りの意味と、よくある直し方 | 処理系の中の診断の表のコードの説明から生成する（[診断エンジン](../02-impl/02-10-diagnostics.md)の「診断コード」） |
| イディオム集 | よく行う処理（ファイルの読み書き、JSON・CSV の処理、外部コマンドの起動、HTTP、テストなど）の書き方 | 手で書く |
| 実行前の検査の契約（`references/inspection.md`） | ハーネスの連携や JSON の解釈で必要な、版・ビルド情報、非実行の報告、エフェクト上限の照合、テストの集計、同梱文書の取得の契約 | 手で書く |
| よくある誤り集 | ほかの言語の書き方を持ち込んだ誤りと、その直し方 | 手で書く |
| 既知の言語との対応表 | ほかの言語の構文・関数と、Benitoite の書き方の対応 | 手で書く |
| ライセンス文 | Skill のライセンス（`MIT OR Apache-2.0`）の文 | 処理系のリポジトリのライセンス文を写す |

- 【決定】Skill は英語で書く。
- 【決定】生成は、処理系のクレートを使う生成の道具で行い、生成物をリポジトリに置く。処理系のビルドは、置いた生成物と手で書く文書を処理系の実行ファイルに埋め込む。配る Skill は、同じ実行ファイルの処理系と同じ版になる。生成物が、いまの構文の章・標準ライブラリのソース・診断の表から生成したものと一致することを、処理系のテストで確かめる。生成の道具は `cargo run -p benitoite --example gen_skill` で実行する。
- 【決定】標準ライブラリのソースでは、ファイル単位のエフェクトの宣言を使わず、関数ごとの個別の `uses` で契約を書く。標準ソースを解析する既存の検査で、ファイルの宣言がないことを確かめる。理由: 原文から切り出す署名に有効な契約の効果を欠かさず、標準の契約を個別に読めるようにするためである。この規約は同梱するソースに適用し、利用者が書く宣言や `@builtin` の構文の規則は変えない。
- 【決定】標準ライブラリの宣言は `public` から切り出し、関数の本体と定数の右辺を除く。型・エフェクト・型クラスは宣言全体を含める。属性は `@extensible` だけをソースの表記で `public` の前に出力し、`@builtin` など他の属性は出力しない。理由: 型の使用条件をリファレンスにも示し、処理系の実装用の指定は含めないためである。
- 【決定】`SKILL.md` と、手で書くイディオム集、よくある誤り集、既知の言語との対応表に載せたコードの例は、処理系のテスト（`tests/skill_examples.rs`。言語リファレンスの例と同じ検査器を使う）で検査する。例は、実行して出力を比べる例、検査だけの例、`test` で実行する例、検査の誤りを期待する例を区別して書く。期待する出力を書いた例は、実行して出力も比べる。標準ライブラリのドキュメントコメントの代表例は、元ソースから共通の抽出・実行部へ渡して `tests/stdlib_doc_examples.rs` で検査する。生成された宣言の一覧は実行例として収集しない。公開docを生成文書へ載せる際は、フェンスの印・字下げ・期待を保つ。
- 【方針】`SKILL.md` の前付けは、`name: benitoite`、Skill を使う場面を書いた `description`、`license: MIT OR Apache-2.0` と、`metadata` の欄に処理系の版を持つ。
- 【方針】参照の文書は、Agent Skills の仕様の勧めに従い、一つのファイルを一つの主題に絞る。

【方針】`SKILL.md` には、次のものを書く。

1. 作業の手順。スクリプトとテストで手順を分ける。診断コードの意味が分からないときは、診断コードの説明の文書を読む。
   - スクリプト: スクリプトを書く、通常の `benitoite check` で検査する、診断を読んで直す、を検査が通るまで繰り返す。後述の「実行の前の確認」の直前に一度 `benitoite check --report=json` を実行して宣言上限を取得し、確認を終えてから `benitoite run --allow-effects=<集合>` で実行する。報告が失敗した場合は通常の検査で修正し、確認の前に報告を取り直す。
   - テスト: `check` は `main` のないファイルを誤りとする（[型検査器](../02-impl/02-05-typechecker.md)の「宣言の検査」の `main` の項）ので、テストのファイルには使わない。テストを書く、通常の `benitoite test --check` で非実行の検査をする、診断を読んで直す、を検査が通るまで繰り返す。確認の直前に一度 `benitoite test --check --report=json` を実行し、選択したテストの宣言上限の和を取得する。確認を終えてから `benitoite test --allow-effects=<集合>` で実行する。報告が失敗した場合は通常の `test --check` で修正し、確認の前に報告を取り直す。
2. 主な言語の規則の要約。ほかの言語と違い、LLM が書き誤りやすい規則（ブロックを `end` で閉じること、局所の束縛を `let` ではなく `bind x <- e` と書き、局所の名前として見えている名前を隠すときだけ `shadow x <- e` と書くこと、パターンで分岐する式を `match 対象 with` と `case パターン -> 本体` で書き、ハンドラの節も `with` と `case 操作(引数) -> 節` で書くこと、戻り値の型を `->` の後に書くこと、代数的データ型を `data … end data` で宣言すること、`Option` と `Result` の構成子を型名で修飾すること、IO のモジュールを import すること、非公式のモジュールを `Benitoite.Unofficial` の下の名前で取り込むこと、関数のシグネチャに `uses` でエフェクトを書くことなど）を短く並べる。
3. 参照の文書の一覧と、それぞれを読む場面。書く前にイディオム集と使用する標準モジュールの文書を読む。`references/inspection.md` は、ハーネスとの連携や報告の解釈が必要なときに読むよう案内する。
4. 版の確認。エージェントは `benitoite --version` の版と、`SKILL.md` の前付けの版を比べる。違うときは、利用者に `benitoite skill install` を実行し直すよう伝える（[配布形態](../05-platform/05-01-distribution.md)の「互換性の方針」）。機械可読な能力は `benitoite --version=json` の `formats` で確かめ、リリース番号から推測しない。導入せずに同梱文書を読むには `benitoite skill list` と `benitoite skill show <論理名>` を使う。

【決定】主な言語の規則の要約には、35 のキーワードを名前に使えないことと、非予約語・文脈で読む語の区別を含める。`die` は名前や単独の式には使えず、try の失敗時の処置としてだけ受理すること、`extensible` は普通の識別子であり、引数なしの属性として data・record に使えることを明記する。語の一覧は誤り集へ案内し、生成する文法の導入にも同じ区別を記す。四つの標準失敗型の指定、外部の record の分解には包括的な分岐が必要なこと、構築・更新・getter は使えることも案内する。手書きの idioms には、構成子追加後の網羅性と実行結果の違い、record の欄の追加を互換とする保証がないこと、WIT の構造照合を緩めないことを記す。

【決定】主な言語の規則の要約には、`Process.shell` に渡す文字列を POSIX の sh の範囲で書き、bash などに固有の書き方（配列、`[[ ]]` など）を使わないことを含める。あわせて、シェルの機能が要らなければ `Process.shell` より `Process.run` を使うよう指示する。`/bin/sh` の実装は OS と設定によって違う（[IO のモジュール](../03-interop/03-07-io-modules.md)の「Process」）ので、POSIX の sh の範囲に限れば、どの機械でも同じ意味になる。

### 言語の文書と日本語の訳

【決定】LLM 向けと利用者向けの文書は英語で書き、英語の版を正とする。

- 英語の言語リファレンスは `docs/reference/benitoite.md` に置く。そのコードの例は、処理系のテストで検査する。
- 設計者が読むために、`SKILL.md` と手で書く参照の文書（イディオム集、実行前の検査の契約、よくある誤り集、既知の言語との対応表）と、言語リファレンスの日本語の訳を作る。生成する参照の文書は訳さない。日本語の版は、リリースのたびに英語の版から LLM が訳して作る。
- 日本語の版の各ファイルの先頭に、訳であること、訳した元の版、英語の版を正とすること、エージェントが使うためのものではないことを書く。
- 日本語の版は Skill のディレクトリの外に置き、`benitoite skill install` が書き出すものに含めない。`SKILL.md` からも日本語の版を参照しない。
- 【方針】日本語の版は `docs/ja/` の下に置く。

### Skill の導入（初回リリース版）

【決定】同梱の Agent Skill は処理系の実行ファイルに埋め込み、サブコマンド `skill` で各エージェントの置き場所に書き出す。理由: Skill を実行ファイルに埋め込むと、配る Skill が同じ版の処理系と必ず一致するからである。

```text
benitoite skill install   [--user | --project] [--agent <名前>]...
benitoite skill uninstall [--user | --project] [--agent <名前>]...
```

- `install` は、埋め込んだ Skill を、指定したエージェントの置き場所の `benitoite/` に書き出す。`uninstall` は、`install` が書き出した Skill を消す。
- `--user` は利用者の単位の置き場所に、`--project` は作業ディレクトリの下の置き場所に書き出す。既定は `--user` である。`--project` は、リポジトリの根を探して辿らない。
- `--user` の置き場所の基準は、環境変数 `HOME` の値とする。`install`・`uninstall` は、`HOME` がないか空のとき、絶対パスでないとき、存在するディレクトリでないときは、何も書き出さず、消さず、ディレクトリも作らずに誤りを報告し、終了状態 1 で終える。`HOME` がシンボリックリンクのときは、リンクの先がディレクトリかを確かめる。理由: 誤った `HOME` の下や作業ディレクトリの下で、意図しない導入や除去を行わないためである。
- `--agent` は複数指定できる。省いたときは、次の表のすべてのエージェントの置き場所に書き出す。書き出す先が同じ別々のエージェント（`codex` と `opencode`）を指定したときは、一度だけ書き出す。同じ名前の `--agent` を二度書くこと、`--user` と `--project` を両方書くことは、使い方の誤りとする。

| `--agent` | `--user` | `--project` |
|---|---|---|
| `claude-code` | `~/.claude/skills/benitoite/` | `./.claude/skills/benitoite/` |
| `codex` | `~/.agents/skills/benitoite/` | `./.agents/skills/benitoite/` |
| `opencode` | `~/.agents/skills/benitoite/` | `./.agents/skills/benitoite/` |

表の置き場所は、各エージェントの文書で確かめた、エージェントが Skill を読み込む場所である（Claude Code は [Extend Claude with skills](https://code.claude.com/docs/en/skills)、Codex CLI は [Build skills](https://learn.chatgpt.com/docs/build-skills)、opencode は [Agent Skills](https://opencode.ai/docs/skills/)。2026-10-08 に確認）。opencode は `.claude/skills` と `.agents/skills` の両方を読むので、`--agent` を省くと、同じ名前の Skill を二か所から読む。opencode v2.0.21 のソース（タグ `v2.0.21` の `packages/core/src/config/plugin/compatibility.ts`）では、`.claude` の置き場所を先に、`.agents` の置き場所を後に読み、Skill のディレクトリの名前を鍵にして、後に読んだものが先のものを置き換える。したがって、二か所の `benitoite` は一つの Skill として扱われ、`.agents/skills/benitoite/` の中身が使われる。`install` は二か所に同じ中身を書き出すので、どちらが使われても結果は変わらない。置き場所はエージェントの版で変わりうるので、リリースのたびに文書で確かめ直す。

- 書き出す先に `benitoite/` がすでにあるとき、それが `install` の書き出したもの（`SKILL.md` の前付けの `metadata` に処理系の版の欄があるもの）なら置き換える。そうでなければ書き出さずに失敗とする。`uninstall` も、`install` が書き出したものだけを消す。
- `install` の書き出したものかの判定では、`SKILL.md` がシンボリックリンクでない普通のファイルであるときだけ、1 MiB の上限まで読む。リンク、FIFO などの普通のファイルでないもの、上限を超えるものは、`install` の書き出したものでないとする。理由: リンクの先のファイルを置き換えの根拠にせず、FIFO を読んで止まらないようにするためである。読み方は、ソースの読み方（[ソース管理と位置情報](../02-impl/02-02-source-and-spans.md)の「ソースとファイル ID」）と同じく、開いた記述子で普通のファイルかを確かめる。
- 置き換えは、同じ親のディレクトリの一時ディレクトリに書き出してから名前を変えて行う。途中で止まっても、半端な Skill を残さない。途中で強制終了されると、親のディレクトリに `.benitoite.install-<pid>` か `.benitoite.old-<pid>` が残ることがある。`install` と `uninstall` は、自分の pid のもの以外を消さない。これらの名残は、Skill の置き場所の `benitoite/` を変えない。理由: 並行に動く別の実行の一時ディレクトリを壊さないためである。
- `install`・`uninstall` は、書き出した先と消した先のディレクトリのパスを標準出力に書く。この報告と誤りの報告のパスに含まれる端末の制御文字は、診断のファイルの表示名と同じく逃がす（[診断エンジン](../02-impl/02-10-diagnostics.md)の「文章の形式」）。
- 終了状態は、成功が 0、`--user` の `HOME` が前述の条件を満たさない場合、ファイルを書けない・消せない場合、既存の `benitoite/` を置き換えないと決めた場合が 1、使い方の誤りが 2、処理系の不具合が 3 である。

`skill` のコマンドラインの位置付け（`run` を省いた実行との関係）は [CLI](06-01-cli.md)の「`skill` のコマンドライン（初回リリース版）」で定める。

### 同梱文書の取得

【決定】text の `skill list` は、実行ファイルに埋め込んだすべての文書の論理名を辞書順に一行ずつ LF で終えて標準出力へ書く。`skill show <論理名>` は、その文書の本文だけを標準出力へ書き、末尾の改行を補わない。導入先を作らずに、同じ版の文書を取得できる。

【決定】`list`・`show` は `--format=text|json` を受け付け、省略時は text とする。`=` の形だけを受け付け、show の論理名と format の順序は自由とする。重複、未知の値、余分な引数、取得に対する scope/agent オプション、install/uninstall に対する format は使い方の誤りとする。

【決定】JSON は末尾に LF を付けた単一オブジェクトとする。オブジェクトの欄の順序は契約に含めない。list は `schemaVersion:1`・`kind:skillList`・`producer`・`documents` を持ち、documents は論理名の辞書順の配列とする。各項目は `name`・`byteLength`・`contentHash` を持つ。show は `schemaVersion:1`・`kind:skillDocument`・`producer`・`name`・`byteLength`・`contentHash`・`text` を持つ。producer は検査報告と同じ処理系名・版・ビルド情報であり、定義は [CLI](06-01-cli.md) の「main の非実行の検査報告」に従う。

【決定】byteLength は版の置換後の UTF-8 本文のバイト数、contentHash は同じ全バイト列の SHA-256 とする。contentHash は `algorithm:"sha256"` と、小文字十六進64桁の `value` を持つ。list・show・install で同じ本文を使い、末尾の改行を補ってから数えることはしない。能力は `--version=json` の `formats.skillList` と `formats.skillDocument` の `[1]` で示す。

【決定】論理名は埋め込み一覧 `bundle::FILES` の相対名そのものとし、`SKILL.md`、`references/stdlib/IO.File.md`、`LICENSE-MIT` など、ライセンス文を含む全件を対象とする。区切りは `/` とし、大文字小文字を区別する。拡張子の省略や別名を認めず、空名、先頭 `/`、空の成分、`.`・`..` の成分、バックスラッシュ、コロンを含む名を拒否する。一覧との完全一致だけを受け付け、入力を OS のパスとして開かない。

【決定】取得する本文は `install` と同じ処理で作り、`SKILL.md` の `{{benitoite-version}}` を処理系の版へ置き換える。それ以外の文書の本文は置き換えない。HOME、作業ディレクトリ、インストール済みの文書を調べず、ファイルやディレクトリを作らない。CLI は共通の引数解析の後、install/uninstall の分岐だけで HOME を取得する。公開の `run_skill(args, env, home)` は渡された home を導入・除去に使い、環境変数から補完しない。list/show はこの入口でも home を使わない。

【決定】不正名・未知名は使い方の誤りとし、JSON の指定時も標準出力を空にして標準エラー出力へ説明し、空の成功文書を返さない。不正名の説明は ``invalid Skill document name `{name}` ``、未知名の説明は ``unknown Skill document `{name}`; use `benitoite skill list` `` とする。終了状態は成功0、出力の書き込みの失敗1、使い方の誤り2、埋め込みの不整合などの処理系の不具合3とする。埋め込み一覧は全件の論理名を検証し、不正名や重複があれば一部だけを成功として返さない。

### 実行の前の確認

【決定】`SKILL.md` に、エージェントがスクリプトを実行する前の確認の手順を書く。

1. エージェントは、スクリプトを初めて実行する前と、`main` のエフェクトが前に利用者に示したときより増えたときに、成功した `check --report=json` の main.effects と aggregateEffects が示す宣言上限を、利用者に分かる言葉で示す（「ファイルを書き換える（`File.Write`）」「外部のコマンドを起動する（`Process.Run`）」など）。コードを説明するときは `uses` のシグネチャとも比べ、宣言した未使用のエフェクトも含める。テストでは、成功した `test --check --report=json` の、選択したテストの effects と aggregateEffects の和を使う。
2. 書き込み（`File.Write`）、外部コマンドの起動（`Process.Run`）、ネットワーク（`Http.Connect`・`Http.Listen`）のエフェクトを含むときは、実行の前に利用者に確かめる。
3. `SKILL.md` には、初回リリース版の処理系は実行中に操作を制限しないことを書き、エージェントのサンドボックスの中で実行することを勧める。

この手順で確認するエフェクトは、`main`（テストではテストの関数）が宣言した上限である。検査を通ったスクリプトは、`main` の `uses` にない組み込みの操作を行わない（[ロードマップ](../00-overview/00-03-roadmap.md)の「初回リリース版で宣言する保証」）。テストの関数も同じく、その `uses` にない組み込みの操作を行わない。シグネチャを手で読んで確認する場合、検査や修正の後に宣言が変われば、利用者に示した上限と異なる可能性がある。宣言上限の取得と実行前の包含の照合には、次の CLI を利用できる。

【決定】ハーネスは、main には `check --report=json`、テストには `test --check --report=json` を使い、型検査済みの宣言上限を取得できる。必要な形式は `--version=json` の `formats` で確認する。完全な単一の JSON、既知の形式の版と kind、status:ok、complete:true、終了状態0を確認した場合だけ、`aggregateEffects` を確認に使う。`expanded` は正規名の集合、任意欄 `bounds` は各原子の名前と範囲を示し、どちらも宣言上限である。この処理系は Effects を出すとき常に `bounds` を置き、契約の解析が未完了なら Effects 全体を null にする。受け手は `bounds` のない旧版などの Effects を、`expanded` の各名前の全対象の上限として読む。一部の入口だけが成功した報告や null を、成功した空集合と扱わない。テストの和には `Assert.Check` も残す。エフェクトは実際に使う最小集合ではなく宣言した上限であり、shell の参照は依存と到達しない関数を含む検査対象全体に対する参考情報である。範囲の形と Top、doc の check/error 例が返す空の Effects の扱いは [CLI「main の非実行の検査報告」](06-01-cli.md#main-の非実行の検査報告)の Effects の規則に従う。

`bounds` は実行時の権限、パスの実体の隔離、情報フロー制御を表さない。処理済みの利用者エフェクト名を `expanded`・`bounds`・`--allow-effects` の集合へ戻さない。診断の由来の説明も、宣言上限や許す集合へ加えない。名前による実行前の照合は `bounds` の範囲を使って操作を制限するものではなく、許した名前の全対象を上限として比較する。

【決定】利用者に確認した正規名の集合は、カンマでつないで `run --allow-effects=<集合>` または `test --allow-effects=<集合>` に渡せる。空集合は `--allow-effects=` とする。実行前の検査が成功しても、その宣言上限が許す集合を超えれば E0512 で拒否し、上限付き test は全入口の準備が成功するまで一つも開始しない。引数と診断は [CLI](06-01-cli.md#実行前のエフェクト上限の照合)で定める。

【決定】ハーネスと同梱 Skill は、報告全体と各 Target にある区間解析（interval analysis）の追加欄 `intervalAnalysis` を、型・エフェクトの検査と契約抽出の `complete` から分けて読む。`basis: localIntervals` と `coverage: all/some/none` は解析範囲を表し、報告の受け入れ判定には関わらない。`complete: true` と `coverage: some` は両立する。警告がないことは `all` でも安全を意味せず、未対応や予算の上限により警告を得られない範囲がある。`--deny-warnings` による拒否後も集計は保持される。件数、段停止、実消費、Target と doc の例の集約は [CLI「区間解析の追加報告」](06-01-cli.md#区間解析の追加報告)に従い、手書きの `references/inspection.md` で説明する。`SKILL.md` は受け入れ規則と保証の限界を示して同文書へ案内し、詳細な欄の表は重ねない。main・通常 test の形式番号1と doc test の2、既存の必須欄と受け入れ規則を保つ。

ハーネスは、W0401・W0402・W0404 の局所解析の注記を、対象位置へ到達し、オペランドまたは全引数の評価が正常に終わった場合の失敗として説明する。プログラム全体が必ず失敗するとは説明しない。W0404 は純粋なシフト関数の直接引数だけであり、エフェクトの操作と HTTP のレコード欄は対象外とする。未知・未対応・予算超過だけを理由に、コードの修正や宣言上限の変更が必要だとは扱わない。解析の対象は[型検査器](../02-impl/02-05-typechecker.md#区間解析の範囲と保証)、証明と実装の比較の限界は[形式意味論と検証](../07-quality/07-04-formal-semantics.md#区間解析の対象構文の評価関係)に従う。

報告と後の実行は別の検査であり、ソースのハッシュや許す集合を渡しても、実行する内容は固定されない。同じエフェクトのまま操作の対象や内容が変わる場合、静的な上限照合では拒否できない。利用者への説明と確認を行うかはハーネスに依存し、処理系はその手続きを強制しない。

【決定】ファイル単位の宣言を使う場合も、完全な単一の JSON、理解する schemaVersion と kind、status:ok、complete:true、終了状態0をすべて確認してから、`targets[0].main.effects` の `expanded` と、存在する場合は `bounds` を宣言上限として人間へ示す。これは個別の `uses` とファイルの宣言を合併した上限であり、実際に行った操作ではない。`bounds` がなければ各名前の全対象の上限として読む。失敗や不明を空集合へ変えず、上限を自動で許可へ変換しない。同梱 Skill は、既存の必須欄と受け入れ規則には処理系の報告仕様の版を固定して参照し、範囲の追加欄はその実行ファイルに同梱した `references/inspection.md` で説明する。純粋な引数や Property の関数が必要なときは、ファイルの宣言のない別ファイルへ置く例を示す。main 内の handle ではファイルの宣言の追加分を取り消せず、doc の例は外側の宣言を引き継がないことも案内する。

`package add`・`update` は、依存の公開の契約にある組み込みのエフェクトと、その記録の変更を報告する（[パッケージ](06-09-packages.md)）。この報告は、ここで定める実行前の確認に代わるものではない。

【方針】手順を成り立たせるために、`SKILL.md` に次のことも書く。

- `main` の `uses` には、`IO.All` ではなく細かいエフェクトを並べて書く。`IO.All` と書いたスクリプトは、書き込みと外部コマンドの起動を含むものとして扱う。
- 組み込みのエフェクトごとに、利用者に示す言葉の対応表を載せる（[エフェクト](../01-spec/01-07-effects.md)の組み込みのエフェクトの表に対応させる）。
- `Process.Run` を含むときは、起動するコマンドの名前も利用者に示す。起動したコマンドが行う操作は、処理系の検査の外にあるからである（[セキュリティモデル](../07-quality/07-01-security-model.md)の「ハーネスとの分担」）。
- `benitoite test` で実行するテストの関数も外部の操作を行いうるので、テストの関数のエフェクトにも同じ手順を当てる。

この手順は、利用者が操作を理解するためのものであり、隔離の代わりにならない。手順を守るかはエージェントに依存し、処理系は強制しない。エフェクトの名前は操作の種類を表し、範囲付きの原子はパスの文字列や接続先の上限も表す。外部コマンドが行う操作や、シンボリックリンクを解決した後のファイル、DNS で解決した後の接続先を、この範囲から保証しない。処理系は実行時の権限制御を持たない。

宣言を読む開発用の `derive_inventory` は、本体の検査と実行を行わない（[外部生成の宣言情報](../03-interop/03-06-stdlib.md#外部生成の宣言情報)）。その終了0は、ここで使う `check`・`test --check` の成功や、実行前のエフェクト上限の確認に代用しない。

外部生成の領域を扱う場合は、道具の preview の差分と提案する記録を確認し、その manifest のハッシュを指定して apply する。通常の `check`・`test` の後に道具の `check` も行う（[外部生成の管理と照合](../03-interop/03-06-stdlib.md#外部生成の管理と照合)）。型検査だけでは型の変更後も通る古い出力を検出できないためである。JSON のレコード変換は生成道具と Json.Codec で提供する。Property のレコード生成器・縮小器も同じ領域へ生成できる。生成対象にファイル単位の `uses` がある場合、JSON・Property の生成は事前に拒否する。型パラメータを持つ型では使用するパラメータのGen/Shrinkerを宣言順に渡し、phantomには要求しない。同一モジュール内の正則な再帰の生成器は、[有限基底と総予算](../03-interop/03-08-text-and-data.md#レコードのproperty生成器)に従い、子の生成器の作成をGen.run内へ遅らせる。縮小器は候補の要求まで再帰する組み立てを遅らせ、容器の削除の後に欄順で一欄だけを縮小する。Show/Orderも通常の制約付きimplementとして生成する。宣言inventoryと意味ハッシュは版4、生成記録・manifest/receiptの外枠は版3、生成規則は3.1.0-syntax-batch5、設定は版1を使う。旧本文をハッシュで照合してから新previewを確認し、旧manifestを新applyに流用しない。種だけで旧版の生成分布の再現を約束しない。JSONの対応範囲とは区別する。生成した JSON の往復は通常の `@test` 一件から Property.check で試す。反例の報告には生成記録の版と設定ハッシュを添える。型の構造だけで欄間の条件を保証せず、必要な場合は型全体の生成器・縮小器を手書きする。

【決定】docの例を含めるときは、検査報告と実行の両方へ `--doc` を付ける。版2のtestCheckReportとtestResultsへの対応を問い合わせ、通常testとtest/run例だけのaggregateEffectsを確認する。check/error例を実行権限へ足さない。doc例はimportとusesを自ら明記し、公開APIの境界を通る。利用者testはimport先と標準docを再帰的に集めない。同梱標準docの代表例の検査は開発時に行う。

### Skill の評価

【決定】同梱の Agent Skill は、次の方法で評価する。

- 約 10 の課題を用意し、各課題に入力と期待する出力を添える。ロードマップの完了条件の JSON の集計の課題（[ロードマップ](../00-overview/00-03-roadmap.md)の「完了条件」）を含め、ファイルの処理、CSV、外部コマンドの起動、HTTP、テストを書くことを題材に含める。
- 評価は、二つ以上のハーネスで行う。使えるハーネスと起動のコマンドは `tools/skill-eval/harnesses.json` に定める（Claude Code、Codex CLI、Antigravity の CLI など）。エージェントには同梱の Skill だけを与え、ほかの文書とインターネットを使わせない。
- 課題の成功は、エージェントの書いたスクリプトが、決めた回数（例えば 10 回）以内の検査と修正の繰り返しで `check` を通り、期待する出力を得ることとする。
- 課題ごとに複数回試行し、成功率と、成功までの検査と修正の回数を記録する。記録には、処理系と Skill の版、ハーネスとモデルの版を残す。
- 課題と記録は `tools/` の下に置き、評価の手順はプロジェクトのスキルとして書く。
- 同じ仕組みを、構文の案ごとに Skill を差し替えて期待結果までを測る評価にも使う（docs/todo の TODO-017）。
- 評価は、構文・標準ライブラリ・Skill を変えたリリースのときに行う。

【方針】評価の細部は次のとおりとする。

- 課題は `tools/skill-eval/` に、記録はその下の `results/` に置く。評価の手順のスキルの名前は `skill-eval` とする。
- 検査と修正の回数は、エージェントが処理系を起動した回数として数える。評価では、処理系の起動を記録する包みのコマンドを `benitoite` の名前で `PATH` に置く。
- HTTP の課題の接続先は、評価の道具が同じ機械の上に立てるサーバとする。
- ロードマップの完了条件の JSON の集計の課題は、各ハーネスで、試行の過半数が成功したときに満たしたものとする。ほかの課題の成功率は、Skill を改めるための材料として記録し、合格の基準を設けない。
