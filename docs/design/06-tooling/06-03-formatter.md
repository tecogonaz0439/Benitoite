## 目的と範囲

正規形の定義、入力表現、コメントの保持、整形後の再解析による検証。入力表現は[字句解析器と構文解析器](../02-impl/02-03-frontend.md)が保持する情報に依存する。

現在の版は、初回リリース版（[ロードマップ](../00-overview/00-03-roadmap.md)）のフォーマッタを定める。対象は、整形の規則（字句の間の空白、字下げ、コメント、空の行、行末と文字、複数行の文字列）、フォーマッタの入力、整形後の検証、構文の誤りがあるファイルと標準ライブラリのソースの扱い、フォーマッタのテストである。

## 前提

フォーマッタは、CLI の `fmt` から使う。`fmt` のコマンドライン、`--check`、終了状態、書き換えの手順（一時ファイルと名前の変更）は [CLI](06-01-cli.md) の「`fmt` のコマンドライン（初回リリース版）」で定め（[ADR 0207](../decisions/0207-fmt-command-line.md)）、本章では繰り返さない。`fmt` は構文だけを扱い、名前解決と型検査を行わない。

整形の規則は、[字句構造](../01-spec/01-01-lexical.md)と[構文](../01-spec/01-02-syntax.md)の規則を前提とする。特に、文は改行で区切り、改行を文の区切り（NEWLINE）とするか空白とするかは、改行の前後の字句と、開いている括弧とブロックで決まる（[字句構造](../01-spec/01-01-lexical.md)の「改行による区切り」）。行頭の字下げの量は、プログラムの意味に影響しない（同章の「空白」）。表層構文を見直したときは、本章の規則もあわせて見直す（[ロードマップ](../00-overview/00-03-roadmap.md)の表層構文の確定）。

## 仕様

### 整形の考え方

【決定】フォーマッタは設定を持たない。字下げの幅、字句の間の空白、空の行の数は処理系が決め、設定ファイルとオプションで変えられない（[ADR 0225](../decisions/0225-formatter-without-configuration.md)）。

【決定】フォーマッタは、書き手が置いた改行の位置を保ち、行の中の空白、字下げ、空の行、行末の空白、ファイルの終わりの改行だけを整える。行の長さに上限を設けず、長い行を折り返さず、行を結合しない（[ADR 0226](../decisions/0226-formatter-keeps-line-breaks.md)）。

【決定】フォーマッタは、空白と字下げだけを変え、字句を加えも除きもしない。括弧を加えたり外したりせず、末尾の `,` を加えたり除いたりせず、import の宣言を並べ替えない（[ADR 0227](../decisions/0227-formatter-changes-only-whitespace-and-verifies-tokens.md)）。

この三つにより、整形の結果は、元のソースの字句の並び、字句の間の改行の有無、コメントの本文と順序から一つに決まる。この結果を、そのソースの**正規形**（canonical form）と呼ぶ。同じ字句の並びでも、書き手が改行を置いた位置が違えば、正規形は違う。正規形のソースを整形すると、同じソースになる（冪等性）。

以下の節の規則は、どれも【方針】である。規則の元にした決定は、各節で ADR を示す。

### 字句の間の空白

【方針】同じ行に並ぶ二つの字句の間には、空白を一つ置く。ただし、次の表の位置には空白を置かない。行の先頭の空白は字下げ（次節）で決め、行の末尾には空白を置かない。

| 位置 | 例 |
|---|---|
| `(`・`[` の後と、`)`・`]` の前 | `f(x)`、`[1, 2]`、`()` |
| `,` の前 | `f(a, b)` |
| `:` の前 | `x: Integer`、`bind n: Integer <- 0` |
| `.` の前と後 | `Console.writeLine` |
| `..` の後と、`,` の後でない `..` の前 | `Person(..p, age: 1)`、`[first, ..rest]`、`90..100` |
| 呼び出しの引数の並び、宣言・ラムダ・操作の引数の並び、関数の型の引数の型の並び、型引数と型パラメータの並び、構成子とレコードのパターンの括弧、属性の引数の並びを開く `(`・`[` の前 | `f(x)(y)`、`List[Integer]`、`function getOr[A](opt: Option[A], default: A)`、`lambda(x)`、`function(Integer) -> Integer`、`implement[T: Show] Show[Option[T]]`、`resume(())` |
| 単項の `-` の後 | `-x`、`-(a + b)` |
| `@` の後 | `@test` |
| 補間の開始と中間の字句（StrStart・StrMid）の後と、補間の中間と終わりの字句（StrMid・StrEnd）の前 | `"total: ${total}"` |

表の位置のほかは空白を一つ置くので、二項演算子（`=` と `->`・`<-`・`|>`・`&`・`and`・`or`・`div`・`mod` を含む）の前後、`,` と `:` の後、キーワードの前後には、空白が一つ入る。括弧の式、リストリテラル、リストのパターン、`()` の値、括弧の型を開く `(`・`[` の前も、同じく空白を一つ置く（`return (x)`、`not (a or b)`、`case [x, ..rest] ->`、`else (if b then 1 end if)`）。ただし、`(`・`[` の直後と、単項の `-` の直後では、表の規則が優先する（`f((a))`、`-(x)`）。`not` はキーワードなので、後に空白を一つ置く。

連続する行の束縛の文の `<-` の列は揃えない。`bind` と `shadow` の語の長さや、左辺の名前の長さが違っても、`<-` の前の空白は一つである。揃えると、一つの名前を変えただけで周りの行の空白も変わり、変更の差分が広がるからである（行末のコメントの列を揃えないのと同じ理由。[ADR 0228](../decisions/0228-formatter-comments-blank-lines-and-characters.md)）。

`(`・`[` の前に空白を置くかは、その括弧が呼び出しや引数の並びを開くか、式や型をまとめるかで決まり、前の字句だけでは決まらない。フォーマッタは、これを構文解析の結果から判断する（後述の「入力表現」）。単項の `-` と二項の `-` の区別も同じである。

### 字下げ

【方針】字下げの一段は、空白 2 つとする。トップレベルの宣言（import の宣言と属性を含む）が始まる行の段は 0 である。行の段は、その行の最初の字句で決める。行の最初の字句とは、行の先頭が文字列の字句の途中（複数行の文字列の内容の行と、閉じの `"""` の行）でない行の、最初の字句である。複数行の文字列の内容の行は、後述の「複数行の文字列」の規則で動かす。

行の段を決めるために、構文ごとに、開きの字句と、区切りの字句、閉じの字句を次のように定める。開きの字句を含む行を、その構文の開きの行と呼ぶ。

| 構文 | 開きの字句 | 開きの行と同じ段に置く行 | 開きの行より一段深くする行 |
|---|---|---|---|
| 関数の宣言（本体を持つもの）、代数的データ型・レコード・型クラス・実装・エフェクトの宣言 | `function`・`data`・`record`・`trait`・`implement`・`effect` | `end` で始まる行 | 本体の文、構成子、フィールド、メソッド、操作、実装の中の関数の宣言の行 |
| `lambda`・`with`・`lazy` | 同じ語 | `end` で始まる行 | 本体の文の行、`with` の 2 つ目以降の束縛の行 |
| `if` | `if`（`else` の直後の `if` を除く） | `else` で始まる行、`end` で始まる行 | 分岐の文の行 |
| `match` | `match` | `end` で始まる行 | 分岐の `case` で始まる行（分岐の本体の文の行は、その `case` の行より一段深くする） |
| `handle` | `handle` | 節の並びを始める `with` で始まる行、`end` で始まる行 | 本体の文の行、節の `case` で始まる行（節の本体の文の行は、その `case` の行より一段深くする） |
| 丸括弧・角括弧 | `(`・`[` | 閉じ括弧で始まる行 | 括弧の中の要素の行 |

関数の宣言と、代数的データ型・レコード・型クラス・実装・エフェクトの宣言は、改行による区切りの規則ではブロックの開きとして数えない（[字句構造](../01-spec/01-01-lexical.md)の「改行による区切り」）が、字下げでは開きの字句として扱う。`match` の分岐と `handle` の節の並びを始める `with` と、分岐のガードの `if` は、開きの字句ではない。`match` の `with` は `match 対象` と同じ行に書く（[構文](../01-spec/01-02-syntax.md)の「パターンマッチ」）ので、行の最初の字句にならない。

行の段は、次の順に規則を当てはめて決める。

1. 行の最初の字句が、閉じの字句（`end`・`)`・`]`）か、`if` の `else` か、`handle` の節の並びを始める `with` であれば、その字句が属する構文の開きの行と同じ段とする。
2. 行の最初の字句が `match` の分岐か `handle` の節の `case` であれば、`match` か `handle` の開きの行より一段深くする。
3. 行の最初の字句が、並びの要素の最初の字句であれば、その要素を囲む構文の表の規則で段を決める。並びの要素とは、文、トップレベルの宣言とその属性と import の宣言、宣言の中の構成子・フィールド・メソッド・操作・関数の宣言、`with` の束縛、括弧の中の要素（引数、リストの要素、フィールドの引数、パターンの要素、型引数など）である。`if` の分岐の文は、その分岐を始めた `if` か `else` の行より、`match` の分岐と `handle` の節の本体の文は、その `case` の行より、一段深くする。
4. 上のどれにも当たらない行を、続きの行と呼ぶ。続きの行は、その最初の字句を含む最も内側の並びの要素が始まる行より、一段深くする。この規則では、`match` の分岐と `handle` の節も並びの要素に数える（分岐と節の頭の続きの行は、その `case` の行より一段深くなる。[ADR 0326](../decisions/0326-match-arm-and-handler-clause-head-continuation.md)）。一つの要素の続きの行が複数あっても、段はどれも同じである。

規則 4 により、次の書き方は、どれも前の行の続きとして一段深くなる。

```text
bind total <- price
  * quantity

bind n <- lines
  |> List.filter(lambda(l) return l <> "" end lambda)
  |> List.length
```

一つの行で複数の構文を開いたときは、最も内側の構文の開きの行で段を決めるので、深くなるのは一段だけである。

```text
List.forEach(items, lambda(item)
  bind name <- Item.name(item)
  Console.writeLine(name)
end lambda)
```

`lambda` の本体の文は、`lambda` の開きの行より一段深い。`end lambda)` の行は `end` で始まるので、`lambda` の開きの行と同じ段になる。

### コメント

【方針】コメントの本文は変えない。本文の中の空白とタブも変えない。ただし、行末の空白は除く（後述の「行末と文字」）。`//` の後に空白を加えることもしない。

【方針】コードの後に同じ行で書いたコメント（行末のコメント）は、その行に残し、前の字句との間に空白を一つ置く。連続する行の行末のコメントの列は揃えない（[ADR 0228](../decisions/0228-formatter-comments-blank-lines-and-characters.md)）。

【方針】コメントだけの行は、その後の最初のコードの行（コメントだけの行と空の行を除いた行）と同じ段に置く。ただし、その行が閉じの字句（`end`・`)`・`]`）で始まるときは、閉じる構文の中の行と同じ段（開きの行より一段深い段）に置く。後にコードの行がないときは、段を 0 とする。この規則により、`else` の前のコメントは `else` と同じ段に、`end if` の前のコメントは分岐の文と同じ段に置かれる。

【方針】ドキュメントコメント（`///`・`//!`）も、コメントだけの行として同じ規則で字下げする。`///` の行は説明する宣言の直前にあり（[構文](../01-spec/01-02-syntax.md)の「ドキュメントコメント（初回リリース版）」）、フォーマッタは行を動かさないので、宣言との結び付きは変わらない。空の行の規則（次節）は、`///` の行と宣言の間、`///` の行と属性の間に空の行を加えない。`//!` の行は、ファイルの先頭（シェバンの行があればその直後）に置いたままにする。

### 空の行

【方針】空の行とは、空白とタブだけからなる行と、何もない行である。複数行の文字列の内容の行は、空の行として扱わない。空の行は、次の規則で整える（[ADR 0228](../decisions/0228-formatter-comments-blank-lines-and-characters.md)）。

- トップレベルの宣言（import の宣言を含む）の最後の行と、その後の最初の行の間には、空の行をちょうど一つ置く。空の行がなければ加え、二つ以上あれば一つにまとめる。後に行がなければ（ファイルの終わりであれば）置かない。
- ただし、import の宣言の後に import の宣言が続くときと、定数の宣言の後に定数の宣言が続くときは、書き手の空の行を、一つまでにまとめて保つ。空の行がなければ加えない。二つの宣言の間にコメントだけの行があるときも同じである。
- 属性の行と宣言の間、`///` の行と属性の間の空の行は除く。
- ブロックの中と括弧の中では、書き手の空の行を一つまでにまとめて保つ。
- 構文の中身の最初の行（開きの行の次の行。コメントだけの行を含めて数える）の前の空の行と、閉じの字句で始まる行と `else` で始まる行と `handle` の節の並びを始める `with` で始まる行の前の空の行を除く。構文の中身とは、ブロック、分岐と節の本体、宣言の中身、括弧の中である。`match` の分岐と `handle` の節の `case` の前の空の行は、一つまでにまとめて保つ。
- ファイルの先頭の空の行を除く。シェバンの行と `//!` の行の後の空の行は、一つまでにまとめて保つ。
- ファイルの終わりの空の行を除く。

トップレベルの宣言の範囲は、属性とドキュメントコメントを含めて、最初の行から `end` の行まで（`end` のない宣言は最後の字句の行まで）とする。宣言の後に行末のコメントがあれば、その行を宣言の最後の行とする。宣言の間にコメントだけの行があるときは、前の宣言の直後に空の行を一つ置き、コメントだけの行と次の宣言の間は、書き手の空の行を一つまでにまとめて保つ。

### 行末と文字

【方針】ソースの文字は次のように整える（[ADR 0228](../decisions/0228-formatter-comments-blank-lines-and-characters.md)）。

- 改行は LF とする。CR LF は LF にする。複数行の文字列の中の改行も LF にする。複数行の文字列の値の改行は、ソースの改行によらず U+000A である（[字句構造](../01-spec/01-01-lexical.md)の「複数行の文字列と raw 文字列（初回リリース版）」）ので、値は変わらない。
- 文字列リテラル・文字リテラル・コメントの外のタブは、字下げと字句の間の空白の規則で決め直す。行頭のタブは字下げの空白に、字句の間のタブは前述の表の空白（空白一つか、空白なし）に置き換わる。文字列リテラル・文字リテラル・コメントの中のタブは変えない。
- 行末の空白とタブを除く。ただし、複数行の文字列の内容の行（空の行を除く）の行末の空白は、文字列の値に含まれるので変えない。
- ファイルは改行一つで終える。最後の行に改行がなければ加える。
- ファイルの先頭の U+FEFF（バイト順マーク）は、あれば残し、なければ加えない。
- シェバンの行は、行末の空白も含めて、書いたとおりに残す。

ドキュメントコメントの本文の行末の空白も除く。Markdown の行末の二つの空白による改行（hard line break）は、この規則で失われるので、ドキュメントコメントでは行末の `\` で書く（CommonMark の[行末の `\`](https://spec.commonmark.org/0.31.2/#hard-line-break)による改行）。

### 複数行の文字列

【方針】複数行の文字列（`"""`・`r"""`）の内容の行と閉じの `"""` の行は、開きの `"""` を含む行の字下げの変化と同じ量だけ動かす（[ADR 0227](../decisions/0227-formatter-changes-only-whitespace-and-verifies-tokens.md)）。

- 開きの `"""` を含む行の、整形の前の字下げの文字数を `a`、整形の後の字下げの文字数を `b` とする。字下げの文字数は、空白もタブも 1 文字として数える。
- `b > a` のときは、内容の行（空の行を除く）と閉じの `"""` の行の先頭に、`b - a` 個の文字を加える。加える文字は、整形の前の閉じの `"""` の前の空白の並びの最初の文字（空白かタブ）とし、その並びが空であれば空白とする。
- `b < a` のときは、それらの行の先頭から `a - b` 個の文字を除く。ただし、除く数は、閉じの `"""` の前の空白の並びの文字数を超えない。
- 内容の空の行は、何もない行にする。空白だけの行は、字下げを除いた後に空の行になる（[字句構造](../01-spec/01-01-lexical.md)）ので、値は変わらない。

内容の行は、どれも閉じの `"""` の前の空白の並びで始まる（空の行を除く）ので、この規則で動かしても、除かれる字下げと内容の相対的な位置は変わらず、文字列の値は変わらない。整形の後の開きの行の字下げは正規形の字下げなので、二度目の整形では `a = b` となり、内容の行は動かない。

### 整形の例

【方針】次のソースを整形すると、その次のソースになる。

```text
import Benitoite.IO.Console
data Shape
    Circle(Float)
    Rect(Float,Float)
end data
function area(s: Shape)->Float
    return match s with
    case Shape.Circle(r)  ->  3.14159*r*r    // circle
    case Shape.Rect(w,h)->
    w*h
    end match
end function
function main() -> Unit uses Console.Write


    bind shapes<-[ Shape.Circle(1.0), Shape.Rect(2.0,3.0) ]
    // total area
    bind total <- shapes
    |> List.map(area)
    |> List.fold(0.0, lambda (acc, a) return acc+a end lambda)
    Console.writeLine("total: ${ total }")
end function
```

```text
import Benitoite.IO.Console

data Shape
  Circle(Float)
  Rect(Float, Float)
end data

function area(s: Shape) -> Float
  return match s with
    case Shape.Circle(r) -> 3.14159 * r * r // circle
    case Shape.Rect(w, h) ->
      w * h
  end match
end function

function main() -> Unit uses Console.Write
  bind shapes <- [Shape.Circle(1.0), Shape.Rect(2.0, 3.0)]
  // total area
  bind total <- shapes
    |> List.map(area)
    |> List.fold(0.0, lambda(acc, a) return acc + a end lambda)
  Console.writeLine("total: ${total}")
end function
```

整形の前後で、字句の並びと、字句の間の改行の有無は同じである。変わったのは、字句の間の空白、字下げ、宣言の間の空の行（加えた）、`main` の本体の最初の行の前の空の行（除いた）、行末のコメントの前の空白である。`Shape.Rect(w, h)` の分岐の本体は、書き手が `->` の後で改行したので次の行に残り、`case` の行より一段深くなる。`|>` で始まる二つの行は `bind total` の文の続きの行なので、文より一段深くなる。

### 入力表現

【方針】フォーマッタは、ファイルを一つずつ字句解析と構文解析にかけ（[字句解析器と構文解析器](../02-impl/02-03-frontend.md)）、次の三つを入力にする。

| 入力 | 使いみち |
|---|---|
| 字句を切り出す工程が作る、字句と改行の印の列（それぞれ span を持つ） | 字句の並び、書き手の改行の位置、空の行の位置、複数行の文字列の字下げを知る。整形の結果の字句を書き出す元にする |
| コメントの一覧（本文、種類、span） | コメントを元の行に書き戻す |
| AST | 構文の開き・区切り・閉じの字句（前述の「字下げ」の表）、並びの要素の最初の字句、`(`・`[` が呼び出しや引数の並びを開くか、`-` が単項か二項かを知る |

改行による区切りの判定は、ブロックを開く語として `lambda`・`if`・`match`・`with`（分岐の並びを始めるものを除く）・`lazy`・`handle` だけを数える（[字句構造](../01-spec/01-01-lexical.md)の「改行による区切り」、[字句解析器と構文解析器](../02-impl/02-03-frontend.md)の「処理の流れ」）ので、関数の宣言や代数的データ型の宣言の中身の段は、字句の列だけでは決まらない。`case` が `match` の分岐か `handle` の節か、`if` がガードかも、構文解析の結果で決まる。そこで、フォーマッタは AST を辿って、字句の位置（span）ごとに、字下げと空白の規則に要る役割（開き・区切り・閉じの字句か、並びの要素の最初の字句か、呼び出しの括弧か、単項の `-` か）の表を作る。

整形の結果は、AST を出力し直して作らない。字句と改行の印の列を先頭から辿り、字句の字面をそのまま書き出し、字句の間に、前述の規則で決めた空白・字下げ・空の行と、コメントを置いて作る。書き手の改行の位置は AST に残らず、字句と改行の印の列の span に残るからである（[ADR 0226](../decisions/0226-formatter-keeps-line-breaks.md)）。複数行の文字列の字句は、字面を行ごとに書き出し、内容の行を前節の規則で動かす。

### 整形後の検証

【方針】フォーマッタは、整形の結果をファイルに書く前に、整形の結果を字句解析して、次の二つが整形の前と一致することを確かめる（[ADR 0227](../decisions/0227-formatter-changes-only-whitespace-and-verifies-tokens.md)）。

- 字句の並び。改行による区切りの判定の後の列（NEWLINE を含む）で比べる。字句は、種類と、文字列の字句（文字列リテラルと、補間の開始・中間・終わり）では字句が持つ値（複数行の文字列では字下げを除いた後の文字列）、NEWLINE と入力の終わりでは種類だけを、ほかの字句では字面で比べる（改行の字面は CR LF から LF に変わるため）。入力の終わりの直前の NEWLINE は比べない（最後の改行を加える規則で、整形の前になかった NEWLINE が後に現れるため。この NEWLINE は文を区切らない）。
- コメントの並び。コメントの種類と、行末の空白を除いた本文を、順に比べる。

【方針】あわせて、整形の結果を構文解析し、字句の誤りと構文の誤りがないことを確かめる。ここで誤りとして扱うのは、後述の「構文の誤りがあるファイル」で整形を断る誤りと同じ範囲である。ドキュメントコメントと宣言の結び付きは、字句の並びではなく、行の隣り合いで決まる（[字句解析器と構文解析器](../02-impl/02-03-frontend.md)の「コメントとドキュメントコメント」）ので、字句とコメントの比較だけでは確かめられないからである。

【方針】一致しないか、構文の誤りがあれば、そのファイルを書き換えず、処理系の不具合として報告する。ほかのファイルの整形は続け、`fmt` は終了状態 3 で終える（[CLI](06-01-cli.md) の「`fmt` のコマンドライン（初回リリース版）」）。`--check` を指定したときも、同じ検証を行ってから、整形の結果を元のファイルと比べる。検証を通り、整形の結果が元のファイルとバイトの並びで同じであれば、ファイルを書き換えない。

この検証は、フォーマッタの実装の誤りで字句が変わったり、改行が文の区切りになったり、区切りでなくなったりすることを、ファイルを書き換える前に見つけるためのものである。字句の並び（NEWLINE を含む）が同じであれば、構文解析の結果の AST も同じ形になるので、型検査の結果も変わらない。

### 構文の誤りがあるファイル

【方針】字句の誤り（診断コードが `E01nn` のもの）か構文の誤り（`E02nn` のもの）があるファイルは、整形せず、書き換えない。診断を標準エラー出力に書き、ほかのファイルの整形を続ける（[ADR 0207](../decisions/0207-fmt-command-line.md)）。構文の誤りから回復した AST（誤りのノードを含むもの）は、字下げの役割を決めるのに使えないからである。診断コードの区分は[診断エンジン](../02-impl/02-10-diagnostics.md)の「診断コード」で定める。

【方針】構文解析器が報告するそのほかの誤り（属性の誤りの E0801・E0803・E0804、`resume` を書けない位置の E0509 など）だけがあるファイルは、型検査の誤りがあるファイルと同じく整形し、`fmt` はそれらの診断を書かない（[ADR 0333](../decisions/0333-fmt-refusal-test-json-notes-http-method-and-process-input.md) の決定 1）。

### 標準ライブラリのソース

【方針】処理系に同梱する標準ライブラリのソース（[標準ライブラリ](../03-interop/03-06-stdlib.md)の「標準ライブラリのソースの書き方」）も、本章の規則で整形した正規形で置く。標準ライブラリのソースは、本体のない `@builtin` の関数の宣言を含み、構文解析器に標準ライブラリのソースとして解析させる必要がある（[字句解析器と構文解析器](../02-impl/02-03-frontend.md)の「標準ライブラリのソースの構文」）。CLI の `fmt` は利用者のソースとして解析するので、標準ライブラリのソースは、処理系のテストの中で、フォーマッタの関数に標準ライブラリのソースであることを指定して確かめる（次節）。

### テスト

【方針】フォーマッタは、次のテストで確かめる。テストの種類と置き方は[処理系のテスト戦略](../07-quality/07-03-compiler-testing.md)で定める。

| 確かめること | テスト |
|---|---|
| 整形の規則の個々の場合（空白の表、字下げの規則、コメント、空の行、行末と文字、複数行の文字列） | ゴールデンテストの `fmt` の方式。`.formatted` に期待する正規形を置く（[ADR 0224](../decisions/0224-golden-test-format-for-first-release.md)） |
| `--check` の終了状態と、変わるファイルの報告 | ゴールデンテストの `fmt-check` の方式 |
| 整形の後に `check` の診断が変わらないこと、整形が冪等であること | `check` と `run` のすべてのゴールデンテストで、テストの実行器が自動で確かめる（[ADR 0224](../decisions/0224-golden-test-format-for-first-release.md)） |
| 任意の入力で処理系の不具合が起きないこと、冪等性、整形の前後の診断 | fuzzing |
| 整形後の検証が、字句の並びの違いとコメントの違いを見つけること | 段ごとの単体テスト。検証の関数に、字句を変えた結果とコメントを落とした結果を与える |
| 同梱する標準ライブラリのソースが正規形であること | 段ごとの単体テスト。すべてのモジュールを、標準ライブラリのソースとして整形し、元と同じであることを確かめる |

## 未決事項
