# 秘密の情報の扱いの検討（初回リリース版の完成後に向けて）

- 作成: 2026-10-02
- 扱い: 検討用のメモ。初回リリース版の完成後に、設計書（03-07・01-07・06-07・07-01・ADR・OPEN）へ移す。
- 関係する検討: [コマンドを代替するライブラリ](post-first-release-command-libraries.md)、[パッケージ管理](post-first-release-package-management.md)

## 目的と範囲

パスワード・API キー・アクセス用のトークンなどの秘密の情報（以下、秘密）を、スクリプトが安全に受け取り、外部コマンドや HTTP の要求に渡す方法を検討する。対象は次の二つである。

1. 外部コマンドに渡す環境変数を、スクリプトの環境変数から切り離す方法（`Process.Command` の改造）。
2. 秘密を、人間の手入力、OS のキーストア、パスワードマネージャから受け取る方法。スタンドアロンモードとサーバモードの両方と、コーディングエージェント（Claude Code・Codex・OpenCode など）の上で実行する場合を含める。

## 1. 外部コマンドに渡す環境変数の制御

### 現在の仕様

`Process.Command` の `environment: Map[String, String]` は、スクリプトの環境変数に加えるか、同じ名前の変数を置き換える（03-07「Process」）。スクリプトの環境変数を引き継がない手段も、特定の変数を消す手段もない。

### 問題

外部コマンドは、スクリプトの環境変数をすべて受け取る。スクリプトを起動した環境にほかの秘密（別のサービスのトークンなど）があれば、そのコマンドに必要がなくても渡る。例えば、Proton Pass CLI のアクセス用のトークンを渡すつもりで起動したコマンドが、クラウドの認証情報の環境変数も受け取る。

サーバモードでは、子プロセスが受け取る環境変数は `--env` で名前を指定したものなどに限られる（06-07「サブコマンド」、ADR 0220）ので、問題はスタンドアロンモードで大きい。

### 案

- **(a) 引き継ぐかを選ぶ欄を加える。** `inheritEnvironment: Bool`（既定は `true`）。`false` にすると、`environment` に書いた変数だけを渡す。Rust の標準ライブラリの `Command::env_clear` に当たる。
- **(b) 消す変数の名前の並びを加える。** `removeEnvironment: List[String]`。Rust の `Command::env_remove` に当たる。
- **(c) `environment` の値の型を `Map[String, Option[String]]` にし、`Option.None` で消す。** 欄は増えないが、普通の使い方（値を渡す）でも `Option.Some` が要り、書き方が重くなる。
- **(d) 既定で引き継がない。** 安全な既定だが、`PATH`・`HOME`・`LANG` などがなくなり、多くのコマンドが動かなくなる。個人の道具を手軽に作る用途に反する。

暫定の見立て: (a) を採る。必要な変数だけを渡したいときは、`inheritEnvironment: false` にし、要る変数をスクリプトが `Process.environmentVariable` で読んで `environment` に入れる。読む変数は `Process.Environment` の対象（変数の名前）として権限の確認に現れるので、どの変数を子に渡すかを利用者が確かめられる。(b) は (a) と役割が重なる（設計原則 5）ので、要望が出てから考える。

### 確かめること

- 【要検証】環境変数を引き継がないとき、`program` をどの `PATH` で探すか。Rust の `Command` が、親の `PATH` と子に渡す `PATH` のどちらを使うかを、一次資料で確かめる。Benitoite の仕様としては、子に渡す環境の `PATH` で探すと決めるのが分かりやすい。
- レコードに欄を加えると、レコードのリテラルで `Process.Command` を作っているスクリプトが壊れる。`Process.command` とレコードの更新で作る書き方は壊れない。0.x の間の互換性の方針（ADR 0236）の範囲で扱えるかを確かめる。
- 後述の「秘密の型」を採るなら、秘密を値に持つ環境変数の欄（`secretEnvironment: Map[String, Secret]` など）もあわせて決める。

## 2. 秘密の受け取り方

### 実行の形ごとの難しさ

秘密を人間から受け取るときに問題になるのは、入力をどこから受け取るかと、入力した秘密がコーディングエージェント（LLM）に見えないかである。

| 実行の形 | 端末 | 問題 |
|---|---|---|
| A. スタンドアロンモードを、人間が端末で実行する | ある | ほぼない。端末から、入力を表示せずに読めばよい |
| B. スタンドアロンモードを、エージェントが実行する | ないことが多い。エージェントの道具は、コマンドを端末なしで起動し、出力を捕らえて LLM に渡す【要検証: 各エージェントの道具の実際の起動のしかた】 | 標準入力に秘密を入れる手段が、エージェントの会話に秘密を書くことしかない。そうすると、秘密が LLM とその記録に渡る |
| C. サーバモード（エージェントが MCP やサブコマンドで実行を頼む場合を含む） | ない。子プロセスの標準入力は空の入力である（03-07「Console」） | 子プロセスは OS のサンドボックスの中で動き、端末も GUI も持たない |

いずれの形でも、スクリプトの標準入力（`Console.readLine`）で秘密を読むのは避ける。標準入力はデータの入力に使われ（パイプでつながれうる）、エージェントの下では LLM が書いた内容である。秘密の入力は、処理系が用意する別の経路で受け取る。

### 人間からの入力の経路

- **A の経路: 制御端末から読む。** 処理系が、標準入力ではなく制御端末（Unix の `/dev/tty`）から、入力を表示せずに一行を読む。`ssh`・`sudo` のパスワードの入力と同じ形である。Rust では端末の表示を止めるクレート（`rpassword` など）で書ける【要検証: クレートが C のライブラリに依存しないか（ADR 0143 の方針）】。難易度は低い。
- **C の経路: 承認の画面で受け取る。** サーバモードには、認証を要する要求を、利用者が別の端末で開く承認の画面（`benitoite server approve`）で受ける仕組みがある（06-07「認証と承認」、ADR 0188）。秘密の入力もこの待ちの列に入れる。スクリプトが秘密を求めると、ジョブは「待ち」になり、承認の画面にスクリプトの名前・ジョブ・秘密の説明（スクリプトが付けた名前）を示す。利用者が承認の画面で秘密を入れると、デーモンが子プロセスへパイプで渡す（コマンドライン引数や環境変数には載せない）。監査の記録には、求めたことと応じたかだけを残し、値は残さない。待ちが 5 分で拒否に変わる規則（ADR 0201）もそのまま使える。エージェントに見えるのはジョブが待っていることだけで、秘密は見えない。既存の仕組みを広げる形なので、難易度は中程度である。
- **B の経路: 端末の外で受け取る。** 次の候補がある。
  - (B1) A と同じく制御端末から読み、端末がなければ失敗にする。エージェントの下では使えないが、秘密が漏れることはない。
  - (B2) スタンドアロンモードにも C と同じ形の「別の端末で開く入力の画面」を設ける。スクリプトは待ちになり、「別の端末で `benitoite secret-input` を実行してください」と案内する。デーモンがないので、実行中の処理系が一時的な通信口（Unix ドメインソケットなど）を開く。エージェントがその入力の画面を自分で実行して値を入れることはできるが、そのとき入るのはエージェントが知っている値であり、人間の秘密は漏れない。
  - (B3) OS の GUI の入力欄を出す。macOS の `osascript` の入力欄、Linux の `pinentry` など【要検証: 表示を隠した入力欄を出せるか、それぞれの手段】。デスクトップのセッションがない環境（SSH の先、コンテナ）では使えない。

  暫定の見立て: B1 を既定にし、B2 を加える。B2 は C の承認の画面と同じ使い勝手にできる。サーバモードを加えた後は、スタンドアロンモードからも、デーモンが動いていればその承認の画面を使える形が考えられる。

### OS のキーストア

macOS のキーチェーン、Linux の Secret Service（GNOME Keyring・KWallet など、D-Bus で使う）、Windows の資格情報マネージャを、一つの API で読む。Rust の `keyring` クレートなどがある【要検証: 各 OS での実装の依存（Linux で C の libdbus に依存しないか。純粋な Rust の `zbus` を使う形があるか）】。

- **キーストアの錠を開けるパスワード。** 多くの場合、OS のログインで錠が開いている。錠が閉じていれば、OS が自分の入力欄で求める。Benitoite はキーストアのパスワードを扱わず、OS に任せる。OS の入力欄は、スクリプトが偽装できない経路（trusted path）でもある。
- **粒度。** macOS は、項目ごとに「どのアプリケーションに読ませるか」を利用者に尋ねる【要検証: 署名のない実行ファイルや、更新で中身が変わった実行ファイルでの振る舞い】。利用者が `benitoite` に「常に許可」を与えると、どのスクリプトもその項目を読めるようになる。このため、OS の許可とは別に、Benitoite の権限（後述の `Secret.Read` の対象として項目の名前）で、スクリプトごとに絞る必要がある。
- **環境の制約。** Linux の Secret Service は、デスクトップのセッションと D-Bus を要する。SSH の先のサーバやコンテナでは、普通は使えない【要検証】。
- **サーバモード。** 子プロセスは OS のサンドボックスの中で動き、キーストアの通信先（macOS の securityd、Linux のセッションの D-Bus）に届かない見込みである【要検証】。`~/Library/Keychains` は既定で秘密を置く場所に含めて拒否している（06-07「既定の方針が指す場所」）。デーモン（サンドボックスの外）が、方針で許された項目だけを代わりに読み、子プロセスへパイプで渡す形にする。

### パスワードマネージャ

1Password（`op`）、Bitwarden（`bw`）、Proton Pass などは、それぞれ CLI を持つ。Benitoite からは外部コマンドとして使う（`Process.Run`）。よく使うものは、公式の追加のライブラリとしてラッパーを用意できる（パッケージ管理の検討の (b) の形）。

錠を開ける方法は製品ごとに違う【要検証: 各製品の CLI の文書】。

- デスクトップのアプリケーションと連携し、そちらの生体認証などで錠を開ける形。Benitoite はマスターパスワードに触れずに済むので、これを第一に勧める。
- CLI がマスターパスワードを求め、セッションのトークンを返す形（`bw unlock` が返すトークンを環境変数で渡す、など）。マスターパスワードは上の「人間からの入力の経路」で受け取り、秘密の型のまま CLI の標準入力か環境変数に渡す。返ってきたトークンも秘密の型で受け取る。
- アクセス用のトークン（サービスアカウントなど）を環境変数で渡す形。トークンはキーストアに置き、キーストアから読んで渡すのがよい。スクリプトの中やリポジトリのファイルに書かない。

### 秘密の型

秘密を普通の `String` で扱うと、スクリプトが（LLM が書いた誤りでも）標準出力や記録に書き出せる。エージェントの下では、標準出力はエージェントが捕らえて LLM に渡すので、秘密が LLM に渡る。サーバモードでは、標準出力はジョブの出力として保存される（03-07「Console」）。

そこで、中身を見せない型 `Secret` を設ける案がある。標準ライブラリには、中身を見せない値の前例がある（ADR 0168）。

- `Secret` は、文字列への変換・文字列への埋め込み・表示を持たない。表示が要る場面（診断や値の表示）では `<secret>` と示す。等値の比較も持たない（比べた結果から中身を推測させないため）。
- 受け取り口を、秘密を外へ渡す決まった関数に限る。候補は、外部コマンドの環境変数（前述の `secretEnvironment`）と標準入力、HTTP の要求のヘッダ（`Authorization` など）。
- どうしても文字列が要る場合のために、`Secret.reveal(s)` を設け、専用のエフェクト（`Secret.Reveal`）を要するようにする。こうすれば、秘密を文字列として取り出すスクリプトであることが、権限の確認に現れる（設計原則 3）。

### エフェクトと権限

組み込みのエフェクトを加える案を示す。

| エフェクト | 操作 | 権限の対象 |
|---|---|---|
| `Secret.Read` | `Secret.prompt(label)`（人間からの入力）、`Secret.fromKeystore(service, account)`（キーストア） | 入力の説明の名前、キーストアの項目の名前 |
| `Secret.Reveal` | `Secret.reveal(s)` | なし |

- 既定の方針: スタンドアロンモードでは `Secret.Read` を許し、`Secret.Reveal` は許さない案がある。サーバモードでは、どちらも許さず、登録のときの承認で項目を指定して許す。
- 秘密は、受け取った後に外へ送れる。`Secret.Read` と `Http.Connect`（または任意のコマンドの `Process.Run`）を両方使うスクリプトは、秘密を外へ送れることになる。権限の確認では、この組み合わせを目立つように示す案がある。どの宛先に送るかまでを静的に追うことは、型とエフェクトの範囲を越える。保証は「秘密を受け取るスクリプトであることと、外部に作用しうることが権限に現れる」までである。
- 偽の入力欄（スクリプトが `Console` で「パスワードを入れてください」と書き、`Console.readLine` で読む）を防ぐ手段は、言語の側にはない。処理系の入力の経路が、スクリプトが変えられない見出し（処理系の名前、スクリプトの名前、`Secret.Read` の求めであること）を示すことと、文書で「秘密は処理系の入力欄にだけ入れる」と案内することで補う。

### 保証しないこと

- メモリからの消去。ヒープの回収やコピーによって、秘密の写しがメモリに残りうる。`Secret` の値を使い終えたら消す努力はするが、保証はしない【要検証: ヒープの設計（ADR 0260）の上で、どこまで消せるか】。
- 同じ利用者の権限で動くほかのプロセスからの読み取り（デバッガによる読み取りなど）。サーバモードの OS のサンドボックスが、どこまで防ぐかを確かめる【要検証】。
- 秘密を受け取った外部コマンドや HTTP の宛先が、秘密をどう扱うか。

### パスワードマネージャのラッパーの候補

設計者の判断: 主なパスワードマネージャのラッパーは必要になる。公式の追加のライブラリとして用意する（パッケージ管理の検討の (b) の形）。候補と実現の形は次のとおりである。各製品の CLI の名前・機能・錠の開け方は【要検証】であり、作るときに各製品の文書で確かめる。

| 製品 | 実現の形 | 錠の開け方（見込み） |
|---|---|---|
| Proton Pass | CLI を `Process.Run` で呼ぶ | アクセス用のトークンを環境変数で渡す（設計者の確認による） |
| KeePass 系（KeePassXC など） | (i) `keepassxc-cli` を呼ぶ、(ii) データベースのファイル（`.kdbx`）を処理系が直接読む | マスターパスワード、鍵のファイル、YubiKey のチャレンジレスポンス |
| 1Password | CLI（`op`）を呼ぶ | デスクトップのアプリとの連携（生体認証）、サービスアカウントのトークン |
| Bitwarden | CLI（`bw`）を呼ぶ | マスターパスワードで錠を開け、セッションのトークンを環境変数で渡す |

KeePass 系は、ほかと違ってファイルとして手元にあるので、(ii) の形も取れる。(ii) は外部のコマンドに依存しないが、処理系がマスターパスワードと復号した中身を扱うことになり、`.kdbx` の形式を読む実装（Rust のクレートの有無とその依存は【要検証】）も要る。まず (i) で作り、(ii) は要望があれば検討する。

ラッパーの関数は、取り出した値を `Secret` の型で返す。ラッパーが外部のコマンドの標準出力から秘密を読むので、ラッパーの中では文字列を `Secret` に包む関数が要る。これを誰でも使える関数にすると、`Secret.Reveal` を経ずに文字列を秘密として扱う経路が増えるだけなので害は小さい（秘密を作ることは、秘密を取り出すことと違って漏洩につながらない）。

## 3. ウェブの認証

HTTP の要求で認証を求められる場面を、認証の方式ごとに分けて検討する。設計者の条件として、認証のときには人間による承認の操作を必ず挟む。

### 方式ごとの実現性

| 方式 | 実現性 | 必要なもの |
|---|---|---|
| HTTP の認証（Basic・Bearer のトークン） | 容易 | HTTP の要求のヘッダに `Secret` を渡す受け取り口 |
| ログインのフォーム（ユーザ名とパスワードを送り、クッキーで状態を保つ） | ページによる | クッキーを保つ仕組み、HTML のフォームを読む関数。JavaScript で組み立てるページ、ボットの検出、CAPTCHA があれば、HTTP のクライアントでは扱えない |
| ワンタイムパスワード（TOTP） | 容易 | HMAC（現在の `Benitoite.Hash` にない見込み）。TOTP の種はキーストアやパスワードマネージャに置く |
| OAuth のデバイス認可（RFC 8628） | 容易 | HTTP のクライアントだけ。スクリプトは URL と符号を示し、人間がブラウザで承認する |
| パスキー（WebAuthn）を、OS やパスワードマネージャに保存したもので使う | OS による。macOS は不可、Windows は可能な見込み、Linux は標準の API がない（下記） | — |
| パスキーを、スマートフォンに保存したもので使う（hybrid） | 可能だが重い（下記） | QR コード、Bluetooth、中継のサーバとの通信 |
| パスキー・FIDO2 を、YubiKey などの物理キーで使う | 可能だが重い（下記） | CTAP2 で USB の HID と通信する実装 |
| ブラウザを操作して認証する | 可能だが重い | WebDriver BiDi などでブラウザを動かすラッパー |

### パスキー（WebAuthn）の仕組みと制約

WebAuthn では、認証器（OS のキーストア、パスワードマネージャ、物理キー）が、サイトの識別（RP ID）と、クライアントが作る「どのオリジンで求められたか」を含むデータに署名する。フィッシングを防いでいるのは、この「オリジン」をブラウザが正しく入れることである。認証器の側はオリジンを確かめず、クライアントを信用する。

この仕組みから、次のことが言える。

- **OS とパスワードマネージャのパスキー。** 保存した場所と OS によって違う（2026-10-02 に確かめた範囲。出典は節末）。
  - macOS（iCloud キーチェーンと、OS に組み込まれたパスワードマネージャ）: Apple の文書は、パスキーの登録と認証の要求には `webcredentials` の associated domain が要り、なければ誤りを返すと書く。associated domain は、サイトの側が自分のサーバに置くファイル（`apple-app-site-association`）でアプリを名指しして初めて成り立つので、任意のサイトには使えない。例外はブラウザ向けの制限付きの権限（`com.apple.developer.web-browser.public-key-credential`）で、Apple への申請が要る。したがって、Benitoite の CLI から macOS に保存したパスキーで任意のサイトに認証することは、できない。
  - Windows: `webauthn.dll` の API（`WebAuthNAuthenticatorGetAssertion` など）は、呼び出し側が RP ID を渡す形である。ブラウザ以外のアプリケーションからも呼べる見込みで、Windows Hello と、そこから使える認証器に届く【要検証: 署名のない実行ファイルからの呼び出し、サードパーティのパスワードマネージャのパスキーが届くか】。
  - Linux: デスクトップに標準の FIDO2 の API がまだない。Credentials for Linux の計画（`credentialsd`、XDG のポータルの提案）が進んでいる段階である。
  - パスワードマネージャの CLI: Bitwarden の CLI は、パスキーでのログインに対応しておらず、要望として出ている段階である。パスワードマネージャのパスキーは、ブラウザの拡張か OS の仕組みを通して使うもので、CLI から使う手段は見当たらない（ほかの製品は【要検証】）。
- **スマートフォンのパスキー（hybrid）。** 手元の機械に QR コードを示し、スマートフォンで読み取って Bluetooth の近接を確かめてから、スマートフォンが署名する方式（CTAP 2.2 の hybrid の通信）がある。スマートフォンに保存したパスキー（iCloud キーチェーン、Google パスワードマネージャ、パスワードマネージャのアプリ）を、OS の制約を受けずに使える可能性がある。Rust の `libwebauthn` は、USB・BLE・hybrid の認証器に対応すると書いている（Linux 向け）【要検証: macOS での Bluetooth の利用、C のライブラリへの依存、hybrid の中継のサーバの扱い】。人間の承認は、スマートフォンの生体認証で行われ、スマートフォンがサイトの名前（RP ID）を示す。
- **物理キー（YubiKey など）。** 物理キーは USB（または NFC）の上の CTAP2 で通信し、オリジンを確かめない。したがって、処理系が CTAP2 を話せば、ブラウザでなくても WebAuthn の認証を行える。人間の承認は、キーに触れる操作（利用者の存在の確認）と PIN（利用者の確認）で、キー自身が求める。ブラウザ以外のクライアントが物理キーを使う例として、OpenSSH の FIDO の鍵（`sk-` の鍵）がある。
  - 難しさ: FIDO2 の Rust のクレートは C のライブラリ（hidapi・libfido2）かシステムのライブラリに依存する（06-07「認証と承認」に記録済み）。C コンパイラを避ける方針（ADR 0143）との関係を決める必要がある。サーバモードでは、子プロセスのサンドボックスから USB の機器に届かない見込みなので、デーモンが代わりに通信する。
  - 危険: クライアントがオリジンを自由に決められるので、スクリプトが「このサイトの認証」と偽って、別のサイトの署名をキーに作らせる（フィッシング）ことができてしまう。防ぐには、オリジンをスクリプトに書かせず、処理系が決める必要がある。具体的には、WebAuthn の操作を HTTP のモジュールの中に置き、署名に入れるオリジンと RP ID を、処理系が実際に接続している宛先（TLS で確かめたホスト）から決める。RP ID がそのホストに合わなければ拒む。こうすれば、ブラウザがしている確かめを処理系が代わりに担える。
- **ウェブのログインの手順は、サイトごとに違う。** パスキーの署名を作れても、ウェブのログインに使うには、サイトから挑戦（challenge）を受け取り、署名をサイトに送る必要がある。この受け渡しは、サイトの JavaScript が `navigator.credentials.get()` の前後で、サイトごとの宛先と形式で行うもので、HTTP の標準の手順はない。したがって、処理系が WebAuthn のクライアントになっても、汎用の HTTP のクライアントとして「任意のサイトにパスキーで自動でログインする」ことはできず、サイトごとのラッパーが要る。API としてパスキーの手順を公開しているサービスは、この限りでない。
- **ブラウザに任せる。** OAuth のデバイス認可や、ブラウザで承認してトークンを受け取る形なら、パスキーはブラウザの中で OS の仕組みのまま使え、Benitoite はトークンだけを受け取る。サイトが対応していれば、これが最も安全で、実装も軽い。

### 注意する点

- **リダイレクトと認証のヘッダ。** 現在の HTTP のクライアントは、リダイレクトを最大 10 回まで辿る（03-09）。認証のヘッダや秘密を含む要求を、別のホストへのリダイレクトで送り直すと、秘密が別のホストに渡る。`Secret` を渡したヘッダは、ホストが変わるリダイレクトでは送らないと決める必要がある（curl も既定でそうしている【要検証】）。権限の判定は OPEN-052 とあわせる。
- **サイトの利用規約。** ログインの自動化を禁じるサイトがある。言語の側で扱う問題ではないが、ラッパーや文書で API とトークンの利用を先に勧める。
- **人間の承認の位置。** 物理キーと OS の認証器は、キー自身や OS が人間の操作を求める。パスワードやトークンを使う方式では、承認は前述の「人間からの入力の経路」（承認の画面など）で挟む。サーバモードでは、`Secret.Read` の求めのたびに承認の画面を通すか、登録のときの承認で済ませるかを方針で選べるようにする案がある。

### 暫定の見立て（この節）

- まず、HTTP のヘッダへの `Secret` の受け取り口、ホストが変わるリダイレクトでの扱い、HMAC（TOTP）、OAuth のデバイス認可の例を用意する。これで、トークンと API を使う多くの自動化に足りる。
- ログインのフォームの自動化は、クッキーを保つ仕組みの要否とあわせて、要望を見て決める。
- 物理キーによる WebAuthn は、処理系がオリジンを決める形でなら安全に作れる。C のライブラリへの依存の判断（ADR 0143）と、サーバモードの生体認証・FIDO2 の対応（06-07 で後の版とした）とあわせて検討する。
- パスキーを本命とするなら、ブラウザに任せる形（OAuth の認可コードと PKCE をループバックの宛先で受ける形（RFC 8252）、デバイス認可、ブラウザの操作）を第一とする。保存した場所と OS を問わず、OS の承認の画面のまま使える。
- 処理系が WebAuthn のクライアントになる形は、物理キー、Windows のプラットフォームの API、スマートフォン（hybrid）に限って可能であり、macOS に保存したパスキーには使えない。

## 4. 物理キーによる操作ごとの承認（YubiKey 5.8・CTAP 2.3・previewSign）

設計者の判断: ウェブの認証は、ブラウザに任せる形を本命とする。そのうえで、YubiKey 5.8 の「AI エージェントの重要な操作に署名する」機能を、パスワードマネージャからの取得やウェブの認証に使えるかを検討する。

### 確かめた事実（2026-10-02、出典は末尾）

- YubiKey 5.8 は 2026-07-21 に発表された。CTAP 2.3 への対応と、WebAuthn の署名の拡張（previewSign）の先行の対応を含む。
- CTAP 2.3（2026-02-26 公開）は CTAP 2.2 と後方互換の小さな改訂で、hybrid の通信に BLE を加えたこと、初期化の長押し、版の文字列などを含む。AI エージェントの操作の承認は、CTAP 2.3 そのものの機能ではなく、previewSign の拡張の用途である。
- previewSign は、認証の鍵とは別の署名用の鍵の組を登録のときに作り、後で依頼された任意のデータを、そのまま署名する。普通の認証の署名は、ブラウザが作るデータ（オリジンを含む）と認証器のデータに署名するが、previewSign は依頼されたデータだけに署名するので、文書の署名などの既存の形式に入れられる（Corbado の解説による。二次資料）。
- previewSign は W3C の WebAuthn の提案の段階（版 4、2025-08-26）である。YubiKey 5.8 の対応は先行の提供で、本番に使わないよう示されている。2026-09 の時点で、安定版のブラウザはこの拡張を出していない（同じく二次資料）。
- 物理キーには画面がないので、利用者は何に署名しているかをキーの上で確かめられない（WYSIWYS の問題）。

### 署名を確かめるのは誰か

署名は、公開鍵を持つ側（依頼した側）が確かめて初めて意味を持つ。操作ごとの承認として成り立つには、「この署名がなければ操作を進めない」と決める確かめ役が要る。

- **パスワードマネージャからの取得。** Proton Pass や KeePass 系の CLI が、取得の前に previewSign の署名を求めて確かめる仕組みは、現時点で見当たらない（KeePassXC は、YubiKey のチャレンジレスポンスでデータベースの錠を開けられるが、項目ごとの承認ではない）。パスワードマネージャ自身を確かめ役にすることはできない。
- **ウェブの認証。** 確かめ役はサイトである。サイトが重要な操作の承認に previewSign を採れば、ブラウザに任せる形の中で、ブラウザが処理する。Benitoite の側で用意するものはない。ブラウザとサイトの対応を待つことになる。
- **Benitoite のデーモン。** デーモンを確かめ役にすれば、Benitoite の中で操作ごとの承認を作れる。これが適用できる場所である。

### Benitoite のデーモンを確かめ役にする形

サーバモードには、利用者が別の端末で開く承認の画面がある（06-07「認証と承認」、ADR 0188）。生体認証と FIDO2 のキーは後の版で加えるとしている。ここに物理キーを使う。

1. 利用者は、承認の画面から物理キーを登録する。デーモンは公開鍵を保存する。
2. スクリプトが承認を要する操作を求める（秘密の取得 `Secret.Read`、`Secret.Reveal`、`require_approval` のスクリプトの実行、登録、設定の変更）。
3. デーモンは、操作の内容を書いた文書を作る。スクリプトの名前とハッシュ、ジョブの ID、エフェクトと対象（例: Proton Pass の項目の名前）、時刻、一度だけ使う値（nonce）を含める。
4. 承認の画面がこの内容を示し、利用者は内容を読んでキーに触れる（必要なら PIN も入れる）。キーは内容のハッシュに署名する。
5. デーモンは公開鍵で署名を確かめてから、操作を進める。署名は監査の記録に残す。後から「誰が、いつ、何を承認したか」を確かめられる。

この形は、previewSign がなくても、普通の FIDO2 の認証の署名で作れる。認証の挑戦（challenge）に操作の内容のハッシュを入れれば、キーの署名が内容に結び付く。こうすれば、YubiKey 5.8 に限らず、FIDO2 に対応した既存のキーで使える。previewSign の利点（認証と別の鍵、データをそのまま署名するので既存の署名の形式に入れられる、第三者が WebAuthn の構造を知らずに確かめられる）は、署名を Benitoite の外へ渡して確かめさせる場合に効く。標準化と対応が進んでから採ればよい。

### 承認が守りになる条件

- **秘密がデーモンを通してしか手に入らないこと。** エージェントが自分のシェルでパスワードマネージャの CLI を直接実行できるなら、デーモンの承認を迂回できる。守りになるのは、パスワードマネージャのアクセス用のトークンなどを、デーモンだけが持つ場合である。トークンはデーモンの保護したデータの場所（秘密を置く場所として、スクリプトとエージェントのサンドボックスから読めない場所）に置き、エージェントには渡さない。
- **画面が偽れないこと。** キーに画面がないので、利用者が読むのは承認の画面である。承認の画面はエージェントが操作できない別の端末で開く（ADR 0188）ので、この条件はサーバモードでは成り立つ。スタンドアロンモードをエージェントが実行する場合は、別の端末の入力の画面（前述の B2）が要る。
- **利用者が内容を読むこと。** キーへのタッチが示すのは、人がその場にいて触れたことまでであり、内容を読んだことではない。承認の画面は、内容を短く示し、頻繁に求めすぎない（承認の疲れを避ける）工夫が要る。

### 実装の課題

- FIDO2 の Rust のクレートの C のライブラリへの依存（06-07 に記録済み）。前述の `libwebauthn` が純粋な Rust で USB の HID を扱えるかを評価する【要検証】。
  - ADR 0143 は HTTP と TLS のクレートを選んだ決定であり、「C コンパイラを避ける」こと自体を一般の方針として決めた ADR はない。この性質は、ADR 0138・0143 の帰結（選んだクレートが C のコードを含まない）として成り立っており、ADR 0176（Linux 向けを musl で静的にリンクする）がそれを前提にしている。ADR 0143 も `aws-lc-rs`（C コンパイラを要する）を代わりの案として残しているので、絶対の禁止ではない。06-07 の「C コンパイラを避ける方針（ADR 0143）」は、この点で言い過ぎであり、設計書へ移すときに直す。
  - FIDO2 を加えるときは、次の二つを分けて扱う。(1) 調査: ビルドに C コンパイラが要るか、実行時に共有ライブラリ（Linux の libudev など）を読み込むか。後者は musl の静的な実行ファイル（ADR 0176）と両立しない。macOS の IOKit のような OS の部品のフレームワークを使うことは、C コンパイラを要しない。(2) 判断: 依存の基準（ビルドは Rust のツールチェーンだけ、実行時は OS の部品以外の共有ライブラリを読まない）を一般の方針として ADR にし、FIDO2 をその範囲で作るか、例外を認めるかを決める。
  - Windows の利用者は WSL2 の中で Linux 向けの実行ファイルを使う（ADR 0176）。WSL2 の中からは、既定では USB の機器が見えず、usbipd-win などで機器を渡す必要がある見込みである【要検証】。
- Windows では、ブラウザ以外のアプリケーションが FIDO の機器に直接触れるには、OS の WebAuthn の API を通す必要がある見込み【要検証】。
- 承認の頻度の設計（一度の承認で同じジョブの同じ対象の取得を許す期間など）。

## 設計書に移すときの候補

- `Process.Command` に `inheritEnvironment` を加える ADR（03-07）。
- `Secret` の型、`Secret.Read`・`Secret.Reveal` のエフェクト、受け取り口を定める ADR（01-07・03-07・03-09）。
- 秘密の入力の経路（制御端末、承認の画面、スタンドアロンモードの別の端末）を定める ADR（06-01・06-07）。
- 既定の方針への `Secret.*` の追加（07-01）。
- OS のキーストアとパスワードマネージャの扱いを OPEN として登録する（環境の制約とクレートの依存を確かめるまで）。
- パスワードマネージャのラッパー（Proton Pass・KeePass 系・1Password・Bitwarden）を公式の追加のライブラリとして用意する方針。
- HTTP の認証（`Secret` のヘッダ、リダイレクト、TOTP、OAuth のデバイス認可）を 03-09 に加える ADR。
- 承認の画面に物理キーによる操作ごとの承認を加える ADR（06-07。後の版とした FIDO2 の対応を具体化する）。秘密をデーモンだけが持つ配置もあわせて決める。
- 物理キーによる WebAuthn を OPEN として登録する（オリジンを処理系が決める規則、C のライブラリへの依存、サーバモードでの代理）。
