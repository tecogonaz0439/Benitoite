## 目的と範囲

処理系が自前のエージェントハーネス（利用者の依頼から LLM にスクリプトを書かせ、検査と修正を繰り返す仕組み）を持つ場合に、どの LLM をどの方法で呼ぶかを検討する。

外部のハーネス（Claude Code、Codex CLI、OpenCode など）から処理系を使う場合（06-06、06-07 の MCP の中継）は、使うモデルをハーネスの側で設定するので、本メモの対象外とする。ハーネスで何をするか（対話の形、道具の一覧、権限の確認の出し方）も、別に検討する。

本メモでは、あわせて次の二つも扱う。どちらも、自前のハーネスとは別の機能である。

- MCP のサンプリング（候補 I）。自前のハーネスより先に実装する。
- Claude Code・Codex の CLI を包む外部ライブラリと、そのエフェクト（候補 J）。スタンドアロンモードとサーバモードで、スクリプトから使う。

## 自前のハーネスが使う提供者

### A. OpenAI 互換の API（Chat Completions と Responses）

ベースの URL と API キーを設定で与え、OpenAI の API と同じ形の要求を送る。OpenAI のほか、OpenAI 互換の口を持つサービスを同じ実装で呼ぶ。F と G はこの実装で扱い、設定の例として文書に載せる。

- 手元の推論サーバ（Ollama、llama.cpp の server、LM Studio、vLLM）: 推論を別のプロセスに任せるので、処理系に推論のコードと GPU への依存が入らない。これらの多くが OpenAI 互換の口を持つ【要検証】。
- 中継のサービス（OpenRouter、LiteLLM のプロキシ）: 一つの API キーで多くの提供者のモデルを呼べる。

Chat Completions は、互換を名乗るサービスの多くが対応している形である。Responses は OpenAI が新しく勧める形だが、互換のサービスの対応は Chat Completions より少ない【要検証】。両方を実装し、設定でどちらを使うかを選ぶ。

「互換」の範囲はサービスごとに違い、道具の呼び出し（tool calling）、構造化した出力（JSON Schema）、ストリーミングの対応と細かい形が揃っていない場合がある【要検証】。ハーネスは、提供者ごとに使える機能を表で持つ。

### B. Sign in with ChatGPT

利用者が自分の ChatGPT のアカウントでサインインし、ChatGPT のプランの範囲で AI の機能を使う仕組みである（[OpenAI Cookbook の記事](https://developers.openai.com/cookbook/articles/sign-in-with-chatgpt)。2026-10-04 に確認）。記事で確かめたことは次のとおりである。

- 申し込みなしで使えるのは、オープンソースのプロジェクトと、手元で動かす個人のプロジェクトである。有料のアプリやリモートで提供するアプリは、ウェイトリストに申し込んで承認を受ける。
- 認可は OAuth で行う。アプリは手元に UUID の識別子を保存し、ブラウザで認可を受ける（動的なクライアントの登録）。スコープには、利用者を識別するもの、リフレッシュトークンを得る `offline_access`、`chatgpt.tokens.use.direct` を伴う `resource.invoke` を含める。
- 得たアクセストークンで、公開されている Responses API を呼ぶ。ChatGPT の会話の履歴は読めない。
- 記事は、配布の前に OpenAI の規約とポリシー、DevKit のライセンスを読むよう求めている。

Benitoite への当てはめ:

- 手元で動く CLI のオープンソースの処理系なので、申し込みの要らない区分に入ると読める。サーバモード（06-07）でリモートから提供する形は、承認の要る区分に移る可能性がある【要検証】。
- 呼ぶ先が Responses API なので、A の Responses の実装を使い回せる。B に固有なのは認証（OAuth とトークンの更新）だけである。
- 【要検証】OpenAI の規約とポリシー、DevKit のライセンス。DevKit を使わずに OAuth を自分で実装してよいか。
- 【要検証】使えるモデル、プランごとの使用量の上限、レート制限。記事には書かれていない。

### D. Anthropic の Messages API

Claude を API キーで呼ぶ。Messages API は OpenAI 互換の形ではないので、A とは別の実装が要る。Anthropic は OpenAI の SDK から呼べる互換の口も出しているが、機能の一部に限られる【要検証】。道具の呼び出しやプロンプトのキャッシュを使うので、Messages API を直接実装する。

Claude の購読（Pro、Max）のアカウントでサインインして、他社のアプリから使う仕組みは、承認なしには使えないと理解している【要検証】。B に当たるものは候補にしない。

### E. Google の Gemini API

Gemini を、Gemini API の固有の形で呼ぶ専用の実装を作る。初めは OpenAI 互換の口を A の Chat Completions で呼んで代用する方針だったが、2026-10-04 に、専用に実装する方針へ改めた。理由は、後述の無料枠で使えることである。

Gemini API には、利用者の購読とは別に、開発者の API キーに付く無料枠がある（[Gemini Developer API の料金](https://ai.google.dev/gemini-api/docs/pricing)、[レート制限](https://ai.google.dev/gemini-api/docs/rate-limits)。2026-10-04 に確認）。B は Plus と Pro のプランに限られ、ChatGPT の無料プランでは使えないので、費用をかけずに自前のハーネスを使う手段になる。

- 料金のページは、多くのモデルに無料枠があるとする。利用者は Google AI Studio で API キーを作る。
- 無料枠では、送った内容が Google の製品の改善に使われる。有料の枠では使われない。
- レート制限のページは、上限を保証せず、実際の値は AI Studio で確かめるよう案内している。上限に達したときの振る舞い（待ってからやり直す、別の提供者を案内する）を決める。
- 使える地域は限られる。日本で使えるかは【要検証】。
- Gemini アプリの購読（無料プラン、Google AI Pro など）と API の利用の関係は、上の二つのページに書かれていない。別の製品と読めるが【要検証】。

専用の実装について決めること:

- 固有の API の要求と応答の形、認証のヘッダ、道具の呼び出しと構造化した出力の書き方を一次資料で確かめる【要検証】。
- 既存の crate を使うか、要求を自分で組み立てるか。
- OpenAI 互換の口は、A の実装でも呼べる（[Gemini API の OpenAI の互換性](https://ai.google.dev/gemini-api/docs/openai?hl=ja)。2026-10-04 に確認）。互換の口はベータ版で、Responses API への対応は挙げられておらず、対応していない引数は誤りにならずに無視される。専用の実装を作った後も、利用者が A の設定で互換の口を呼ぶことは妨げない。

### C. 自己ホスト（優先度は低い）

Gemma 4 などの公開された重みを取得し、処理系の中で推論する。ネットワークも API キーも要らない。手元のモデルは A（手元の推論サーバ）でも使えるので、C を作るのは、サーバの導入なしで動くことの価値が確かめられてからとする。

- Rust の推論のライブラリの候補は、candle（Hugging Face）、mistral.rs、llama.cpp の Rust の束縛（`llama-cpp-2` など）である。どれがどのモデルの形式（safetensors、GGUF）と、どの加速（Metal、CUDA）に対応するかは【要検証】。
- 処理系の実行ファイルが大きくなり、ビルドが GPU の環境に依存する。処理系の本体に入れず、機能フラグか別の実行ファイルに分ける。配布の検討とあわせて決める。
- 重みは数 GB になる。取得の場所、保存の場所、ハッシュによる確認を決める。
- 【要検証】Gemma の利用規約。Gemma は OSI の定義によるオープンソースのライセンスではなく、独自の利用規約で配られている。処理系と一緒に配ってよいか、利用者に取得させるかを確かめる。
- 小さいモデルが Benitoite のスクリプトを書けるかは、学習のデータに Benitoite がない分だけ不利である。Skill の評価（06-06「Skill の評価」）で成功率を測ってから、勧めるモデルを決める。

### H. クラウドの基盤（優先度は低い）

Amazon Bedrock、Google Cloud の Vertex AI、Azure OpenAI を呼ぶ。企業の利用者は、契約と認証（IAM）をクラウドの基盤にまとめていることが多い。C と同じく検討はするが、実装の優先度は低い。

- 認証が API キーではなく、各クラウドの署名や資格情報の仕組みになるので、実装の量が多い。各クラウドの SDK（Rust の crate）を使うか、署名を自分で実装するかを決める【要検証】。
- Azure OpenAI は A に近い形で呼べる可能性がある【要検証】。呼べるなら、A で扱い、認証だけを加える。
- 認証の情報は、各クラウドの既存の設定（資格情報のファイルや環境変数）から読むのが利用者の手間が少ない。どこまで読むかを決める。

### K. Apple の Foundation Models（今回は採用しない）

macOS の Foundation Models フレームワークで、Apple Intelligence と同じ端末の中のモデルを呼ぶ（[WWDC26 macOS guide](https://developer.apple.com/wwdc26/guides/macos/)、[What's new in the Foundation Models framework](https://developer.apple.com/videos/play/wwdc2026/241/)。2026-10-04 に確認）。検討はするが、今回は採用しない。端末の中のモデルの文脈の長さが 8,192 トークンであり、同梱の Skill の文法の参照、スクリプト、診断を渡すと足りなくなるおそれが大きいためである。

資料で確かめたことは次のとおりである。

- フレームワークは Swift の API である。macOS 27 では `fm` の CLI と Python の SDK も用意された。Rust の処理系からは、`fm` を子プロセスとして起動するか、Swift の小さな橋渡しを FFI で呼ぶことになる。
- 端末の中で推論するので、料金がかからず、ネットワークなしで動く。WWDC26 でモデルが作り直され、道具の呼び出しが改善されたとされる。
- Apple のサーバで動く Private Cloud Compute のモデルは、文脈が 32,000 トークンで、推論の深さを選べる。料金なしで使えるのは、App Store Small Business Program に入っていて、初回のダウンロードが 200 万未満のアプリである。App Store の外で配る CLI が当てはまるかは【要検証】。

見直す契機は、端末の中のモデルの文脈が長くなったとき、Private Cloud Compute を App Store の外の CLI から使えるとわかったとき、またはスクリプトから LLM を呼ぶモジュール（「残っていること」）の手元の提供者として短い作業に使う場面が出てきたときである。日本語への対応と、ハードウェアの条件は【要検証】。

### L. Claude Code の CLI を経由して、Claude の購読で使う（採否は未決）

公式の Claude Code の CLI（`claude`）を子プロセスとして起動し、モデルの呼び出しだけを任せる。利用者が CLI でログインした Claude の購読（Pro、Max）で動くので、API キーも、トークンごとの課金も要らない。処理系は認証の情報を持たない。D（API キー）とは別の候補とする。

Hermes Agent の公式のプラグイン（[Claude Subscription DirectSDK](https://hermes-agent.nousresearch.com/docs/plugins/claude-subscription-directsdk)。2026-09-20 に公開、実験的な扱い。2026-10-04 に確認）が、この形をとる。文書で確かめた作りは次のとおりである。

- 公式の `claude` を、専用の一時ディレクトリで子プロセスとして起動する。Python の Agent SDK は使わず、CLI の stream-json の形で直接やり取りする。
- Claude Code の組み込みの道具、スキル、設定の読み込みを無効にする。Hermes の道具は MCP で Claude に見せるが、CLI の側での実行は `dontAsk` の設定で拒み、Hermes が実行する。
- プラグインは認証の情報を持たない（「This plugin has no credentials of its own; everything goes through `claude`」）。CLI がログインしているアカウントを、そのまま使う。
- 毎回の要求は、購読の Agent SDK の使用量から差し引かれる。使用量は `claude -p` と同じ割合で数えられ、対話で使うときのおよそ 1.7 倍である。

規約との関係は次のとおりである。

- Anthropic のサポートの記事（[Use the Claude Agent SDK with your Claude plan](https://support.claude.com/en/articles/15036540-use-the-claude-agent-sdk-with-your-claude-plan)。2026-10-04 に確認）は、購読の使用量から差し引く使い方として、Agent SDK、`claude -p`、「third-party apps that authenticate with your Claude subscription through the Agent SDK」を挙げる。Anthropic は、これらを 6 月 15 日から購読とは別の月ごとのクレジットに移す予定だったが、取りやめ、今は「still draw from your subscription's usage limits」としている。
- Agent SDK のページ（[Agent SDK overview](https://code.claude.com/docs/en/agent-sdk/overview)。2026-10-04 に確認）は、承認なしに「third party developers」が「claude.ai login」を提供することを認めない。L は、処理系が自分でログインを提供せず、利用者が公式の CLI で済ませたログインを使う形なので、この注意書きに触れない形をとる。
- ただし、Hermes のプラグインを Anthropic が個別に承認したという発表は見つけていない。サポートの記事の扱いは、変更を取りやめた後の当面のものであり、変わりうる。採るときに、改めて規約を確かめる【要検証】。

Benitoite で作るときの見立て:

- J（Claude Code・Codex の CLI を包む外部ライブラリ）と、CLI の起動、stream-json の読み取り、時間の上限と取り消しの部品を共有できる。違いは、J が CLI をエージェントとして使う（CLI の道具で作業させる）のに対し、L はモデルの呼び出しだけに使い、道具の実行を自前のハーネスが持つことである。
- 自前のハーネスの道具は、MCP で CLI に見せる。処理系はすでに MCP のサーバの機能を持つ（06-07、ADR 0182）ので、それを使えるかを確かめる。
- 気を付けること: 規約の扱いが変わりうること、対話より使用量を多く数えられること、CLI の版によって出力の形と設定（道具の無効化、`dontAsk` など）が変わりうること【要検証】。CLI が見つからない、ログインしていない、使用量の上限に達したときの振る舞いを決める。
- 利用者への表示では、購読の使用量が減ることと、CLI がログインしているアカウントを使うことを示す。

### 作りの見立て

1. 提供者を差し替えられる層を作る。ハーネスは、会話の送信、道具の呼び出し、構造化した出力、ストリーミングを、提供者に依らない形で扱う。
2. A（Chat Completions と Responses）を作る。
3. B を作る。A の Responses を使い回し、OAuth を加える。
4. D を作る。
5. E を作る。
6. C は、A の手元の推論サーバで足りない理由がはっきりしてから作る。
7. H は、利用者の要望を見て作る。

LLM の API のクライアントは、言語の中核でも処理系の主要部でもないので、既存の OSS（Rust の crate）を使ってよい（00-01「目的の衝突」）。ただし、OpenAI 互換の口の細かい違いを吸収する層は、自分で持つ方が扱いやすい可能性がある。使う crate の候補（`async-openai`、`genai` など）と、その対応の範囲は【要検証】。

### 認証の情報の保管

API キーと、B の OAuth のリフレッシュトークンは、長く使える秘密の値である。[秘密の情報の扱い](post-first-release-secrets.md)で検討した仕組み（OS のキーストア、パスワードマネージャ、`Secret` の型）で保管し、設定ファイルに平文で書かせない。環境変数（`OPENAI_API_KEY` など）から読むことは、既存の道具との互換のために許す。

ハーネスが起動するスクリプトや外部コマンドに、これらの秘密を渡さない。秘密の検討の「外部コマンドに渡す環境変数の制御」と同じ問題である。

### 利用者への表示

ハーネスが LLM を呼ぶことはスクリプトのエフェクトではないが、利用者には次のことを示す。

- どの提供者のどのモデルを使うか。手元で推論するか、外部へ送るか。
- 外部へ送る場合に、何を送るか（依頼の文、スクリプト、診断、ファイルの中身）。特に、ファイルの中身を送る前に利用者に確かめるか。
- B と L では、利用者の購読の使用量が減ること。L では、どのアカウントを使うか（CLI がログインしているアカウント）も示す。
- E の無料枠では、送った内容が Google の製品の改善に使われること。

## I. MCP のサンプリング（自前のハーネスより先に実装する）

処理系は、`benitoite mcp` で MCP のサーバとして振る舞う（06-07、ADR 0182）。MCP には、サーバがクライアントの側の LLM に生成を頼む「サンプリング」の機能がある。これを使うと、処理系は API キーも認証も持たずに、利用者がハーネスで使っている LLM を使える。

- 【要検証】主なハーネス（Claude Code、Codex CLI、OpenCode）がサンプリングに対応しているか。対応していないハーネスでは使えないので、サンプリングがないときの振る舞い（機能を使えないと報告する）を決める。
- 何にサンプリングを使うかを決める。候補は、スクリプトから LLM を呼ぶモジュール（「残っていること」）を、MCP の上で動くときにサンプリングへ振り向けることである。ハンドラを差し替えれば、同じスクリプトが、MCP の上ではサンプリングで、スタンドアロンモードでは A・B・D の提供者で動く。
- サンプリングの要求は、クライアントの側で利用者の承認を挟むことがある【要検証】。処理系の側で権限の確認をどう重ねるかを決める。

## J. Claude Code・Codex の CLI を包む外部ライブラリ

自前のハーネスとは別に、スタンドアロンモードとサーバモードで動くスクリプトから、Claude Code（`claude -p`）と Codex CLI（`codex exec`）を起動するための外部ライブラリを設ける。認証と購読の扱いは各 CLI が持つので、ライブラリは認証を実装しない。ライブラリの包み方は、[コマンドを代替するライブラリ](post-first-release-command-libraries.md)の git の CLI を包む案と同じ形をとる。

### 専用のエフェクトを設ける理由

`Process.run` でも CLI は起動できるが、エフェクトは `Process.Run` の一つになり、ほかのコマンドの起動と区別できない。エージェントの CLI の起動には、普通のコマンドの起動と違う性質があるので、専用のエフェクトで区別する。

- **結果が決まらない**: 同じ依頼と同じ入力でも、出力が毎回変わりうる。普通のコマンドは、同じ入力に同じ出力を返すことを期待して使う。利用者は、結果を確かめる前提で実行を許可する必要がある。
- **起動した先が任意の操作を行いうる**: エージェントは、自分の判断でファイルを書き換え、コマンドを実行し、ネットワークに接続する。処理系の検査は、エージェントが中で行う操作に及ばない。
- **外部へ情報を送る**: 依頼の文と、エージェントが読んだファイルの中身が、LLM の提供者へ送られる。
- **購読の使用量と料金を消費する**。

### 決めること

- エフェクトの名前と細かさ。CLI ごとに分ける（`ClaudeCode.Run`、`Codex.Run` など）か、`Agent.Run` のような一つにまとめて対象（CLI の名前）で区別するか。権限の確認では、どの CLI をどの作業ディレクトリで起動するかを示す。
- 保証の範囲。git の検討と同じく、「この CLI を、この設定で起動すること」までとし、エージェントが中で行う操作は処理系の検査の外にあると明記する（07-01「ハーネスとの分担」）。
- エージェントに許す操作を、CLI の設定で絞る手段をライブラリの引数に出すか。例えば、Codex のサンドボックスの指定や、Claude Code の使ってよい道具の指定である【要検証】。絞った設定を、権限の確認に示す。
- 結果の型。最後の応答の文だけを返すか、構造化した出力（JSON の出力の形）を読んで、使った道具や変更したファイルも返すか。非対話で起動したときの出力の形は、CLI ごとに違い、版によって変わりうる【要検証】。
- 時間の上限と取り消し。エージェントは長く動くことがあるので、時間の上限と、取り消しのときに子プロセスを確実に止める方法を決める。
- テストの方法。結果が決まらないので、ライブラリを使うスクリプトのテストでは、エフェクトのハンドラを差し替えて決まった応答を返す。
- 外部ライブラリとして配る方法。[パッケージ管理](post-first-release-package-management.md)の検討とあわせて決める。
- 【要検証】各 CLI の規約が、別のプログラムからの起動を許すか。購読のアカウントで非対話の起動を繰り返すことが、規約や使用量の上限に触れないか。

## 残っていること

- L（Claude Code の CLI を経由して、Claude の購読で使う）を採るか。
- スクリプトから LLM を直接呼ぶモジュール（`Llm.Complete` など）を設けるか。設けるなら、J と同じく結果が決まらないことを専用のエフェクトで表し、提供者（A・B・D、I のサンプリング）をハンドラで差し替えられる形を検討する。J のエフェクトとの関係（どちらも「LLM の生成」として一つの群にまとめるか）も決める。
