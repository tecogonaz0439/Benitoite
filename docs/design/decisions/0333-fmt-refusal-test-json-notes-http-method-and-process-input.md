# 0333. `fmt` が整形を断る誤り、テストの JSON の注記、HTTP の要求の方法、外部コマンドの入力の書き込みの細目を決める

## 背景

2026-10-07 から 2026-10-08 にかけて、実装プランの作業の確認で、設計書が定めていないか、設計書と実装が食い違う点が四つ見つかった。どれも設計者が 2026-10-08 に判断した。

1. **`fmt` が整形を断る誤りの範囲**（D04 の確認）。06-03「構文の誤りがあるファイル」は、字句の誤りか構文の誤りがあるファイルを整形しないとし、型検査の誤りがあるファイルは構文解析を通るので整形できるとしていた。実装（`format_source`）は、字句解析と構文解析が出した診断が一つでもあれば、整形を断る（`FormatError::Syntax`）。構文解析器は、構文の誤り（`E02nn`）のほかに、属性の誤り（E0801・E0803・E0804）と `resume` を書けない位置（E0509）も報告する（02-03「文脈の制限」）。これらは構文の形の誤りではないが、今の実装ではこれらのファイルも整形できない。
2. **テストの JSON の報告での解放の失敗**（D11 の確認）。`benitoite test` の文章の形では、確認の失敗（`"assert"`）の詳細に止める途中の解放の失敗の注記を、`Process.exit`（`"exit"`）の詳細に解放の失敗の報告を示す。JSON Lines の形の `failure` は、ADR 0252 の決定 6 の項目しか持たず、`"assert"` と `"exit"` ではこれらが落ちる。`"runtime"` は実行時エラーの報告の JSON の項目をそのまま持つので、解放の注記を `notes` に含む。
3. **HTTP のクライアントの要求の方法と本体、名前の解決の失敗、ヘッダの値の制御文字**（L32 の確認）。03-09 は、要求の方法と本体の組み合わせが正しくない場合（`GET`・`HEAD` に空でない本体など）と、標準でない方法（`PURGE`、小文字の `get` など）の扱いを定めていなかった。実装は、これらを送らずに `NetworkErrorKind.InvalidInput` を返す。名前を解決できない場合は、`ureq` の既定の解決器が `Io` の誤りとして返すので、実装はこれを包んで `HostNotFound` に寄せている。要求のヘッダの値は、ADR 0331 の決定 1 が CR・LF・NUL を実行時エラーとするのに対し、実装は L30 のサーバと同じく、そのほかの制御文字も実行時エラーとする。
4. **外部コマンドの入力の書き込みが読み切られない場合**（L13 の確認）。`Process.Command` の `input` を指定したとき、子が入力を読み切らずに終わると、処理系の書き込みが `BrokenPipe` の誤りになる。`head` のように入力の一部だけを読むコマンドでは、普通に起きる。03-07 はこの場合の扱いを定めていなかった。実装は、誤りにせず成功として扱う。

## 検討した代替案

設計者には、問題ごとに次の案を示した。

1. `fmt` の範囲
   - **今の振る舞いを 06-03 に書く**: 実装を直さずに済む。しかし、構文解析を通り AST の形が決まるファイルを整形しないことになり、「型検査の誤りのファイルは整形できる」と同じ理由で整形できるはずのファイルを断る。属性の誤りは書き手が直すまで残りやすく、そのファイルの整形も止まる。
   - **字句の誤りと構文の誤りに限る（採用）**: 06-03 が整形を断る理由（構文の誤りから回復した AST は字下げの役割を決めるのに使えない）に当たる誤りだけで断る。
2. テストの JSON の報告
   - **stderr に診断として書く**: `run` の `Process.exit` の解放の失敗と同じ形になる。しかし、テストの結果は標準出力の JSON Lines に書くので、一つのテストの失敗の情報が二つの出力先に分かれ、読み手（主に LLM とテストの道具）が対応を付けにくい。
   - **今のままにする**: JSON の読み手だけが解放の失敗を知る手段を持たない。文章の形と JSON の形で、示す情報が食い違ったままになる。
   - **`"assert"` と `"exit"` にも `notes` を持たせる（採用）**: `"runtime"` と同じ欄の名前と形で、一つの行に収まる。
3. HTTP のクライアント
   - **標準でない方法も送れるようにする**: `PURGE` などの拡張の方法を使うサーバと通信できる。しかし、`ureq` の既定の検査を外す必要があり、小文字の `get` のような書き誤りも、そのまま送られて相手のサーバの応答としてしか現れない。
   - **標準の方法に限り、それ以外を `InvalidInput` とする（採用）**: 実装済みの振る舞いであり、書き誤りを送る前に `Result.Error` で知らせる。
4. 外部コマンドの入力
   - **誤り（`IOError`）にする**: 入力をすべて渡せなかったことを書き手が知れる。しかし、`head` のように入力の一部だけを読むことが正しい振る舞いのコマンドで、子が正常に終わったのに `Result.Error` になり、終了状態と集めた出力も失われる。
   - **成功として扱う（採用）**: Python の `subprocess.Popen.communicate` と同じ扱いである。子が入力を読まなかったことは、子の終了状態と出力から判断できる。

## 決定

1. `fmt` が整形を断るのは、字句の誤り（`E01nn`）か構文の誤り（`E02nn`）があるファイルだけとする。構文解析器が報告するそのほかの誤り（属性の E0801・E0803・E0804、`resume` を書けない位置の E0509 など）だけがあるファイルは、型検査の誤りがあるファイルと同じく整形し、それらの診断を書かない。整形後の検証で整形の結果を構文解析するときも、断る対象と同じく字句の誤りと構文の誤りだけを誤りとして扱う。
2. ADR 0252 の決定 6 を改め、`test` の JSON Lines の形の `failure` で、`"assert"` と `"exit"` にも、`"runtime"` と同じ形の `notes`（注記の文字列の配列）を持たせる。
   - `"assert"` の `notes` は、実行時エラーの報告の `notes` と同じ並びとする。止める途中の解放の失敗ごとの注記（02-10「解放の失敗の報告」の、実行時エラーで止める途中の解放の注記と同じ文）を並べ、最後に末尾呼び出しの注記を置く。文章の形の詳細に示す注記と同じ並びである。
   - `"exit"` の `notes` は、止める途中の解放の失敗ごとに、実行時エラーで止める途中の解放の注記と同じ文を一つずつ並べる。失敗がなければ空の配列とする。
3. HTTP のクライアント（`Http.get`・`Http.send`）は、次の扱いとする。
   - 要求の方法は、標準の方法（`GET`・`HEAD`・`POST`・`PUT`・`DELETE`・`CONNECT`・`OPTIONS`・`TRACE`・`PATCH`。大文字と小文字を区別する）に限る。それ以外の方法（`PURGE`、小文字の `get` など）は、送らずに `NetworkErrorKind.InvalidInput` を返す。
   - 方法と本体の組み合わせが正しくないとき（`GET`・`HEAD`・`CONNECT` に空でない本体）も、送らずに `NetworkErrorKind.InvalidInput` を返す。
   - 名前を解決できないときは、解決器が返す誤りの形によらず `NetworkErrorKind.HostNotFound` を返す。
   - ADR 0331 の決定 1 を改め、`Http.send` の要求と `Http.respond` の応答の `headers` の値は、CR・LF・NUL に加えて、そのほかの制御文字（水平タブを除く 0x01〜0x1F と 0x7F）を含むときも、送る前に実行時エラー（引数の定義域の外）とする。値に許すのは、水平タブ、見える文字（0x21〜0x7E）、空白、0x80 以上のバイトである。名前の規則は ADR 0331 のまま変えない。
4. `Process.run`・`Process.runAttached` で `input` に `Option.Some` を指定したとき、子が入力を読み切らずに終わり、子の標準入力への書き込みが `BrokenPipe` の誤りになっても、誤りにしない。書けた分で入力を終えたものとし、子の終了状態と集めた出力を成功として返す。`Process.shell` は `input` を指定できないので、この場合は起きない。

## 帰結

- 06-03「整形後の検証」「構文の誤りがあるファイル」と 06-01「`fmt` のコマンドライン（初回リリース版）」に決定 1 を書く。実装プランの 10-17「整形の流れ」「整形後の検証」「`fmt` の実行」を改める。今の実装（`format_source` と `verify`）は、字句解析と構文解析の診断が一つでもあれば誤りとするので、後の作業で直す必要がある。
- 06-04「結果の報告」に決定 2 を書く。実装プランの 10-18「JSON Lines の形」、D11・D12 の作業文書を改める。今の実装は `"assert"`・`"exit"` に `notes` を書かないので、後の作業で直し、解放の失敗を起こすテストを置く必要がある。ADR 0252 の状態に、決定 6 を本 ADR で改めたことを記す。
- 03-09「サーバの接続と要求の読み方」「クライアント」「失敗の種類」に決定 3 を書く。ADR 0331 の状態に、決定 1 の値の規則を本 ADR で改めたことを記す。L30・L32 の実装は既にこの規則で動くので、実装の直しは要らない。
- 03-07「Process」に決定 4 を書く。L13 の実装は既にこの扱いで動くので、実装の直しは要らない。
