# 0278. 第 1 段は新しい構文へ書き直したテストで完了とし、メモリの管理に触れない第 2 段の作業は先に進めてよい

- 状態: 採択
- 日付: 2026-09-30
- 関連章: [仮想機械](../02-impl/02-08-vm.md), [ランタイム](../02-impl/02-09-runtime.md), [処理系のテスト戦略](../07-quality/07-03-compiler-testing.md)
- 関連する未決事項: [OPEN-036](../open-issues.md#open-036)

## 背景

[ADR 0268](0268-staged-runtime-rebuild.md) の決定 3 は、第 1 段の完了の条件の一つを「最小実行版のすべてのテストが、両方式と回収の強制の下で通る」とした。決定 1 は、第 2 段以降（ハンドラと継続、タスクとスケジューラ、IO 実行器、出力の転送、リソース、`Lazy` と `Reference`）を第 1 段の後に加えるとした。

初回リリース版の実装プランを作る中で、実装した最小実行版は波括弧の C 系の構文（`fn … { }`、`let`、`match 対象 { パターン => 式 }`）で書かれており、初回リリース版の構文（キーワードで始めて `end` で閉じるブロック）と全く違うことが分かった（[構文](../01-spec/01-02-syntax.md)）。最小実行版のテストを新しい構文で走らせるには、構文解析だけでなく、名前解決・型検査・脱糖・コード生成まで、初回リリース版のフロントエンドの全体が要る。

## 決定

1. ADR 0268 の決定 3 の「最小実行版のすべてのテスト」は、最小実行版のテストを、言語の機能を変えずに初回リリース版の構文へ書き直したものとする。第 1 段は、初回リリース版のフロントエンドがそろい、書き直したテストが二つのメモリの管理と回収の強制の下で通ったときに完了とする。最小実行版の構文のテストを新しい VM で走らせるための一時的な経路は作らない。
2. フロントエンドがそろうまでは、第 1 段の VM と二つのメモリの管理を、手で組み立てたバイトコードのプログラムによる単体テストで確かめる。
3. 第 2 段以降の作業のうち、二つのメモリの管理に共通の API だけを使い、根の持ち方や確保の負荷を変えないもの（型クラスの命令、`Decimal` と `Byte` の命令、`Map` と `Set` の木、実行時エラーの報告など）は、第 1 段の測定を待たずに進めてよい。これらの作業は両方式でテストを通す。
4. ハンドラと継続、タスクとスケジューラ、IO 実行器、出力の転送、リソース、`Lazy` と `Reference` の VM への組み込み、`List` の永続ベクタへの移行は、ADR 0268 のとおり第 1 段の測定の後に行う。これらは根の持ち方や確保の負荷を変え、二つの方式の比較に影響するからである（ADR 0268 の決定 4）。

## 理由

最小実行版の構文のテストを通しても、初回リリース版の処理系の正しさの根拠にならない。捨てる経路を作ると、その経路に固有の誤りを直す作業が増えるだけである。一方、第 1 段の測定を待つ間に U2 の作業を止めると、U1 の完成までの時間を活かせない。二つの方式の比較に影響しない作業に限れば、先に進めても測定の公平さは損なわれない。

## 検討した代替案

- **最小実行版の構文のテストで第 1 段を完了とする**: 第 1 段の測定を U1 と並行して行える。しかし、最小実行版のフロントエンドと新しい VM をつなぐ使い捨てのコード生成が要り、そのテストは初回リリース版の構文の正しさを示さない。設計者は採らなかった。
- **第 2 段の作業をすべて測定の後にする**: ADR 0268 の文言どおりである。しかし、比較に影響しない作業まで止める理由がない。

## 帰結

- ADR 0268 の状態の欄に、本 ADR で決定 1・3 の読み方を定めたことを記す。
- 第 2 段のうち決定 4 の作業は、U1 がそろい、第 1 段の測定を終えた後に始まる。
