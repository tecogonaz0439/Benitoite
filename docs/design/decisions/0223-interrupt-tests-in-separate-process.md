# 0223. 中断の要求のテストは、CLI を別のプロセスとして起動し、実際にシグナルを送って行う

- 状態: 採択
- 日付: 2026-09-29
- 関連章: [処理系のテスト戦略](../07-quality/07-03-compiler-testing.md), [仮想機械](../02-impl/02-08-vm.md), [ランタイム](../02-impl/02-09-runtime.md)
- 関連する未決事項: なし

## 背景

処理系のテストは、処理系を別のプロセスとして起動せず、処理系の Rust の API を直接呼ぶ。例外は、プロセス全体に関わる振る舞い（panic hook の設定と、処理系の不具合の報告の順序）だけであった（[処理系のテスト戦略](../07-quality/07-03-compiler-testing.md)の「前提」）。

初回リリース版の CLI は、`SIGINT` と `SIGTERM` を受けたらプロセス全体で一つの中断の印を立て、VM はタスクを切り替える位置と待つ位置で印を調べ、リソースを解放し、出力を書き出してから終了状態 130 で終える。解放の途中で二度目の中断の要求を受けたら、OS の既定の振る舞いで終える（[ADR 0163](0163-interrupt-releases-resources.md)）。この振る舞いは、シグナルの登録、印の読み書き、止める手順、出力の書き出しの組み合わせで決まる。

Cargo は、統合テストをビルドするときに、同じパッケージのバイナリの実行ファイルの絶対パスを環境変数 `CARGO_BIN_EXE_<name>` に入れ、テストは `env!` でこれを読める（[The Cargo Book: Environment variables Cargo sets for crates](https://doc.rust-lang.org/cargo/reference/environment-variables.html#environment-variables-cargo-sets-for-crates)）。

## 決定

1. 中断の要求のテストも、CLI を別のプロセスとして起動するテストで行う。
2. テストは、ビルドした `benitoite` の実行ファイルを `CARGO_BIN_EXE_<name>` で見つけ、子プロセスとして起動する。
3. スクリプトは、準備ができたことを示す行を標準出力に書いてから待つ（標準入力を読む、または長く待つ）。テストは、その行を読んだ後にシグナルを送る。
4. テストは、終了状態が 130 であること、バッファに残っていた出力が書き出されたこと、`with` のリソースが解放されたこと（書き込みで開いたファイルの内容が書き出されていること）を確かめる。
5. 解放の途中で二度目のシグナルを送り、OS の既定の振る舞いで終えることを確かめる場合を一つ置く。
6. これらのテストは Unix に限る。初回リリース版の対象の環境は、どれも Unix 系である（[ADR 0176](0176-first-release-targets-and-static-linux-build.md)）。

## 検討した代替案

- **中断の印を直接立てる API でテストする**: 別のプロセスが要らず、テストが速く、送る時機を正確に決められる。しかし、シグナルの登録と、シグナルから印を立てるまでの経路を確かめられない。この経路の誤り（登録の漏れ、`SIGTERM` の扱いの漏れ）は、利用者が Ctrl-C を押したときに初めて表に出る。

## 帰結

- [処理系のテスト戦略](../07-quality/07-03-compiler-testing.md)の「前提」の例外に、中断の要求を加える。
- 別のプロセスを起動するテストは、API を呼ぶテストより遅い。場合の数は、上の決定の範囲に抑える。
- Windows を対象の環境に加えるときは、Ctrl-C と Ctrl-Break の送り方を改めて決める。
