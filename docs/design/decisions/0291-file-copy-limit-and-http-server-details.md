# 0291. `File.copy` を読み書きの関数で書いて写せる大きさを 1 GiB までとし、HTTP のサーバの接続と要求の読み方を定める

- 状態: 採択（決定 1 を [0337](0337-file-transfer-for-large-copies.md) で改めた。初回リリース版は決定 1 のまま）
- 日付: 2026-09-30
- 関連章: [IO のモジュール](../03-interop/03-07-io-modules.md), [ネットワークのモジュール](../03-interop/03-09-network.md)
- 関連する未決事項: [OPEN-062](../open-issues.md#open-062)

## 背景

U3 の実装プランを書く途中で、設計書が定めていない次の点が見つかった（`docs/implement/README.md` の「U3 の作業の文書で見つかった点」の 1 と 3）。実装プランは、仮の扱いを決めて書き、設計者に確かめるとしていた。

- `File.copy` の型は `function(String, String) -> Result[Unit, IOError] uses File.Read, File.Write` である（[IO のモジュール](../03-interop/03-07-io-modules.md)の「File」）。操作の宣言には `uses` を書けず、一つの操作は一つのエフェクトにしか属さない（[構文](../01-spec/01-02-syntax.md)の「エフェクトの宣言とハンドラ（初回リリース版）」）。そのため、`File.copy` を組み込みのエフェクトの操作にすると、この型を与えられない。
- [ネットワークのモジュール](../03-interop/03-09-network.md)は、HTTP のサーバが一つの接続で受け付ける要求の数、chunked の本体を読むか、要求の頭（要求の行とヘッダ）の大きさ、応答に処理系が付けるヘッダ、UTF-8 でない要求の扱いを定めていない。UTF-8 でない要求の扱いは、[OPEN-062](../open-issues.md#open-062) の R14 が挙げた反例でもある。

設計者は、実装プランの仮の扱いを設計書に載せることにした（2026-09-30）。

## 決定

1. `File.copy` は、`File.readBytes` と `File.writeBytes` を呼ぶ標準ライブラリのソースの関数とする。内容を一度 `Bytes` の値に読むので、写せるファイルの大きさは `Bytes` の上限（2^30 バイト、1 GiB）までとなる。上限を超えるファイルでは、`File.readBytes` と同じく資源の不足として停止する（[ランタイム](../02-impl/02-09-runtime.md)の「一つの操作で作る値の大きさの上限」）。
2. HTTP のサーバは、一つの接続で一つの要求だけを受け付ける。応答に `connection: close` を付け、応答を送った後か `Http.Exchange` の解放のときに接続を閉じる。
3. 要求の本体は、`content-length` と `transfer-encoding: chunked` のどちらでも読む。どちらもなければ本体を空とする。両方があるとき、または形が正しくないときは、HTTP として正しくない要求として状態コード 400 を返す。
4. 要求の頭の大きさの上限を 64 KiB（65,536 バイト）、ヘッダの数の上限を 100 とする。どちらかを超えた要求には、処理系が状態コード 431 の応答を返す。
5. 要求の対象（パスとクエリ）かヘッダの値が `Http.Request` の `String` の値にできない（正しい UTF-8 でない）要求は、HTTP として読めない要求として、処理系が状態コード 400 の応答を返す。
6. 応答の `content-length` と `connection` は処理系が付ける。利用者の `headers` に同じ名前（大文字と小文字を区別しない）の組があれば、処理系の値で置き換える。

## 検討した代替案

- **1 で `File.copy` を組み込みの関数にし、読み書きを作業用のスレッドで少しずつ行う**: 大きさの上限がなくなる。しかし、二つの組み込みのエフェクトにまたがる組み込みの関数を置く仕組みを、`File.copy` のためだけに加えることになる。スクリプトが写すファイルの多くは 1 GiB に収まると見込む。
- **2 で持続的な接続を扱う**: 接続を作り直す費用が減る。しかし、[ネットワークのモジュール](../03-interop/03-09-network.md)は `Http.closeExchange` を「接続を閉じる」と定め、`Http.Exchange` を接続と一対一に扱う。持続的な接続を扱うと、一つの `Http.Exchange` の解放で接続を閉じるかを別に決める必要が生じる。
- **3 で chunked の本体を読まない**: 読む処理が簡単になる。しかし、HTTP/1.1 のサーバは chunked の本体を読めることが求められる（RFC 9112）。
- **4 で頭の大きさに上限を設けない**: 大きなヘッダを受け付けられる。しかし、頭が終わらない接続でメモリを使い続ける。
- **5 でクエリを OPEN-062 の R14 の修正の候補のとおり扱う（パーセント符号化を戻せないものを受け取ったままにする）**: `Http.pathSegments` の扱いと揃う。しかし、新しい規則を加えることになる。既にある「HTTP として正しくない要求には 400 を返す」規則に寄せ、R14 の再現テストの結果を見て改めるかを決める。

## 帰結

- [IO のモジュール](../03-interop/03-07-io-modules.md)の「File」に決定 1 を、[ネットワークのモジュール](../03-interop/03-09-network.md)の「サーバ」に決定 2〜6 を【方針】として書く。
- 決定 5 により、`?q=%FF` のようにパーセント符号化を戻すと正しい UTF-8 にならないクエリを持つ要求にも 400 を返す。OPEN-062 の R14 のクエリの行は、成り立つべき性質（受け取ったままの文字列になる）を満たさず、再現する見込みである。実装プランの L33 が再現テストを書き、その結果を見て、決定 5 を改めるかを OPEN-062 の決着のときに決める。ヘッダの行は、R14 の修正の候補（状態コード 400）と一致する。
- 決定 1 の上限は、1 GiB を超えるファイルを写す必要が生じたら、後の版で組み込みの関数に改めてよい。
