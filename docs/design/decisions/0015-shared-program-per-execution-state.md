# 0015. コンパイル済みプログラムを実行の間で共有し、実行中の状態を実行ごとに分ける

## 背景

設計メモは、評価器と VM を複数の goroutine から再入可能（reentrant）に設計するかを、今決めるべきこととしている。span と同じく後付けが難しいからである（[設計メモ](../sources/fp-language-design.md) 5.3, 6）。

最小実行版と初回リリース版には並行処理を含めない（[ロードマップ](../00-overview/00-03-roadmap.md)）。並行処理のモデルも、実装するかどうかも決めていない（[OPEN-006](../open-issues.md#open-006)）。一方で、並行処理を入れなくても、一つのプロセスの中で複数の実行を扱う場面がある。MCP サーバは、同じプロセスの中でスクリプトを繰り返し検査・実行する。埋め込み API（[スクリプト実行と埋め込み](../02-impl/02-11-embedding.md)）を使う Go プログラムは、同じスクリプトを何度も、あるいは複数の goroutine から実行しうる。

設計メモは、並行処理を実装する場合の Go 上の形として、評価器の共有状態をロックやアトミックで守る案（5.2 A(i)）、実行単位ごとに独立した VM を持たせてメッセージだけをやり取りする案（同 A(ii)）、独自のスケジューラを持つ案（同 B）を挙げている。今の決定は、これらのどれを後で選んでも作り直しにならない形であることが望ましい。

## 決定

1. コード生成が出力するコンパイル済みプログラム（バイトコード、定数表、関数の表、ソース上の位置の表）は、生成の後に変更しない。複数の実行と複数の goroutine が、同じコンパイル済みプログラムを同時に読んでよい。
2. 実行中に変わる状態（呼び出しの情報、IO ハンドラ、資源の追跡、出力のバッファ、実行時エラーの情報）は、実行ごとに作るオブジェクトに持たせる。一つの実行を同時に進めてよい goroutine は一つだけとする。
3. 処理系のどの段も、パッケージ変数などの大域的な可変状態を持たない。初期化の後に変更しない表（prelude の定義の表など）は、大域に置いてよい。
4. 一つの実行を複数の goroutine で同時に進めるための排他制御は、入れない。

## 検討した代替案

- **一つの VM を複数の goroutine で共有し、共有状態を排他制御で守る**（設計メモ 5.2 A(i)）: 並行処理のモデルの選択肢は広がる。しかし、最小実行版には並行処理がないので、排他制御の費用と実装の難しさを、使わないうちから負うことになる。後でこの形が必要になっても、決定 2 の実行ごとの状態に排他制御を加えれば済み、変更はランタイムの中に収まる。
- **再入を考えない**: 一つのプロセスで一つの実行だけを想定し、大域的な状態も許す。最も簡単である。しかし、MCP サーバの繰り返し実行、埋め込み、並行処理のどれを加えるときにも、大域に置いた状態を引数で渡す形に改めることになる。改修は組み込みの関数・IO ハンドラ・VM など状態に触るすべての箇所に及び、見落としは並行に実行したときにだけ不具合として現れる。

## 帰結

- MCP サーバと埋め込み API は、一度コンパイルしたプログラムを使い回し、実行ごとに新しい状態を作れる。
- 並行処理を実装するとき、実行単位ごとに独立した VM を持つ形（設計メモ 5.2 A(ii)）は、実行ごとの状態を増やすだけで実現できる。言語の値は変更できないので、実行単位の間で値を渡すときに複製は要らない。ただし、変更できる Go のハンドルを値に入れられるようになった場合は、その扱いを別に決める必要がある（[設計メモ](../sources/fp-language-design.md) 5.2）。
- 実行ごとの状態を増やせば、その分だけメモリを使う。一つの実行が使うメモリの量は見積もっていない。並行処理を実装するときに[性能](../07-quality/07-02-performance.md)の測定項目に加える。
- 一つの実行を同時に進める goroutine を一つに限るので、Go 側の任意の goroutine から言語の関数を呼び戻す API（`net/http` のサーバなど）は、この決定だけでは扱えない。初回リリース版のコールバックの扱いは[ランタイム](../02-impl/02-09-runtime.md)で定める。
- 処理系の実装では、大域的な可変状態を持たないことを、レビューとテストで確かめる。
