# 0222. HTTP のテストは同じスクリプトの中のループバックの通信で行い、テスト用のハンドラ表は再現しにくい失敗だけを作る

- 関連章: [処理系のテスト戦略](../07-quality/07-03-compiler-testing.md), [ランタイム](../02-impl/02-09-runtime.md), [ネットワークのモジュール](../03-interop/03-09-network.md)
- 関連する未決事項: なし

## 背景

初回リリース版の標準ライブラリは、`Benitoite.Network.Http` の HTTP のサーバ（TLS なし）とクライアント（HTTPS を含む）を持つ（[ADR 0141](0141-http-scope-in-stdlib.md)）。サーバは `httparse` と `mio` の上に自作し、IO 実行器のタスクの切り替えに組み込む。クライアントは `ureq` を作業用のスレッドで呼ぶ（[ADR 0143](0143-http-and-tls-crates.md)）。

処理系のテストは、処理系の外の依存をテスト用のハンドラ表で置き換える（[処理系のテスト戦略](../07-quality/07-03-compiler-testing.md)の「テストの設計の原則」）。一方で、HTTP のサーバの実装の危険の多くは、イベントループ、タスクの切り替え、要求の解析と応答の生成の組み合わせにある。ネットワークの操作をすべてテスト用のハンドラ表で置き換えると、これらの組み合わせを確かめられない。

`Http.listen` は、ポートに 0 を与えると OS が空いているポートを選び、選ばれたポートを `Http.listenerPort` で調べられる（[ネットワークのモジュール](../03-interop/03-09-network.md)の「サーバ」）。

## 決定

1. HTTP のテストの主な方法は、実際のループバックの通信とする。ゴールデンテストでは、一つのスクリプトが `Http.listen("127.0.0.1", 0)` で待ち受け、サーバをタスクで動かし、同じスクリプトからクライアントとして接続する。
2. テスト用のハンドラ表のネットワークの項目は、ループバックでは起こしにくい失敗（名前の解決の失敗、接続の拒否、接続のリセット、時間切れ）を、決まった結果として作るためだけに使う。ネットワークの操作は本番と同じく実際に行い、テストが指定した操作にだけ失敗を返す。
3. HTTPS のクライアントは外部に接続しなければ確かめられないので、証明書の検証を伴う接続は処理系のテストに含めない。手元で動かす TLS のサーバで TLS の組み立てを確かめるかは、初回リリース版の実装プランで決める。

## 検討した代替案

- **ネットワークの操作をすべてテスト用のハンドラ表で置き換える**: テストが OS のソケットに依存せず、結果が常に決まる。しかし、`mio` のイベントループ、待つタスクの切り替え、HTTP の要求の解析と応答の生成を一緒に確かめられず、サーバの実装の主な危険がテストから外れる。

## 帰結

- 外部のネットワークに出ずに、サーバとクライアントの両方の実装を一つのテストで確かめられる。ポートを 0 にするので、テストを並べて実行してもポートが衝突しない。
- ループバックの通信を使うテストは、OS のソケットに依存する。テスト用のハンドラ表は、ネットワークの操作を本番と同じく行い、テストが指定した操作にだけ指定した失敗を返す。
- HTTPS の証明書の検証は、処理系のテストでは確かめられない。
