## 背景

VM のレジスタ、構成子の引数、リストの要素、組み込みの関数の引数と戻り値は、すべて言語の値である。値の表現は、組み込みの関数すべてが触るので、後から変えると広く手が入る。

設計メモは、Go 製のインタプリタが遅くなりやすい理由の一つに interface 経由の値の表現を挙げ、第 2 層に近づける手段として、タグ付き構造体で interface を避ける値の表現を挙げている（[設計メモ](../sources/fp-language-design.md) 9）。最小実行版の完了後の性能測定は、Go での実装を続けるかの判断に使う（[ロードマップ](../00-overview/00-03-roadmap.md)）。

## 決定

VM の値は、次の三つの欄を持つ Go の構造体で表し、ポインタではなく値として受け渡す。

- 種類の印: 値の種類（Int、Float、Bool、Char、Unit、およびヒープの対象の種類）
- 即値の欄: 64 ビット。Int・Float・Bool・Char の値をそのまま入れる
- 参照の欄: ヒープの対象（文字列、関数の値、構成子を適用した値、リスト、`IoError`）への参照

`unsafe` パッケージは使わない。欄の具体的な Go の型は[仮想機械](../02-impl/02-08-vm.md)で定める。

## 検討した代替案

- **Go の interface（`any`）で表す**: 実装が最も素直で、型スイッチで振り分けられる。しかし、整数や浮動小数を `any` に入れるときにヒープの確保が起きうる。数値の計算の多いプログラムで確保と GC の費用が増え、最小実行版の性能測定が、Go での実装を続けるかの判断を、実装言語でなく値の表現のせいで不利な方へ引きうる。

## 帰結

- 数値・真偽値・文字の演算は、ヒープを確保せずに済む。
- 一つの値の大きさは、`any` 一つより大きくなる。レジスタとリストの要素のメモリの使用量が増える分と、確保が減る分のどちらが大きいかは、性能測定で確かめる（[OPEN-009](../open-issues.md#open-009)）。
- 組み込みの関数は、種類の印を見て欄を読む。印と欄の組み合わせの誤りは Go の型では防げないので、値を作る関数と読む関数を VM に用意し、組み込みの関数はそれだけを使う。
