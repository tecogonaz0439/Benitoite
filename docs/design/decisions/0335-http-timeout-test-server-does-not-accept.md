# 0335. HTTP のクライアントの時間切れのテストで、サーバは要求を受け付けない

- 状態: 採択
- 日付: 2026-10-08
- 関連章: [ネットワークのモジュール](../03-interop/03-09-network.md), [処理系のテスト戦略](../07-quality/07-03-compiler-testing.md)
- 関連 ADR: [0330](0330-http-details-from-u3-preflight.md), [0274](0274-deterministic-scheduler-and-virtual-time-for-tests.md)

## 背景

ADR 0330 の決定 4 は、L32 の HTTP のクライアントの時間切れのテストに限り、実時間の短い待ち（100 ミリ秒程度）を許し、テストのサーバは「クライアントのタスクの結果を待ってから応答し、接続を解放する」と定めた。2026-10-08 に D32 が Linux のコンテナ（x86_64 は Rosetta の模倣）で `scripts/check.sh` を走らせたところ、このテストが 30 秒の上限で止まった。調べた結果（作業 FLNX）、クライアントが要求を送り終える前に時間切れになると、サーバの `Http.accept` は次の要求を待ち続ける（03-09 の定めどおりの振る舞い）。模倣が遅いと、100 ミリ秒の間に要求が届かないことがある。開発機でも、時間切れを 1 ミリ秒にすると同じ停止が起きた。決定 4 のサーバの形は、時間切れが要求を送り終えた後に起きることを前提にしており、実時間に依存していた。決定 4 のうち設計者が決めたのは実時間の待ちを許すことであり、サーバの形はオーケストレータが決めた細部だったので、オーケストレータが改めた。

## 決定

L32 の時間切れのテストのサーバは、待ち受けを開くだけで要求を受け付けず（`Http.accept` を呼ばず）、クライアントのタスクの結果を待ってから待ち受けを閉じる。接続は待ち受けの backlog に留まり、待ち受けを閉じるときに OS が閉じる。クライアントの時間切れが接続・送信・応答の待ちのどの段で起きても、結果は `NetworkErrorKind.TimedOut` になる（L32 は ureq の `Error::Timeout` を段によらず `TimedOut` に分ける）。実時間の短い待ちを許すことは、ADR 0330 の決定 4 のまま変えない。ADR 0330 の決定 4 のサーバの形の文を、この決定で改める。

## 検討した代替案

- **決定 4 の形のまま、時間切れを長くする**: 模倣の遅さに対して余裕を持てるが、どの長さでも実時間に依存することは変わらず、テストの時間も延びる。
- **サーバが要求を読み終えたことをクライアントに知らせてから時間を数え始める**: ureq の時間の上限は要求の送り始めから数えるので、テストの側からは合わせられない。

## 帰結

- 時間切れを 1 ミリ秒にしてもテストが止まらず通ることを確かめた。`timeout_global` を渡さない退行では 30 秒の上限でテストが失敗するので、テストは関門として効く。
- L32 の作業文書の時間切れのテストの記述を、この形に合わせて改めた。
