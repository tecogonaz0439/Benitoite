# 0357. 初回リリース版では中間表現の最適化を行わず、初回リリース版の後に変換ごとに試作して測る

- 状態: 採択
- 日付: 2026-10-09
- 関連章: [中間表現と脱糖](../02-impl/02-06-ir-and-lowering.md)
- 関連する ADR: [0158](0158-type-classes-by-dictionary-passing.md)
- 関連する未決事項: [OPEN-009](../open-issues.md#open-009)

## 背景

02-06「最適化」は、初回リリース版で行う中間表現の最適化を、性能の測定の結果を見て決めるとしていた。候補は三つある。辞書が呼び出しの位置で決まっているメソッドの呼び出しを直接の呼び出しに置き換えること、`let` の右側の入れ子を平らにすること、`let x ⇐ return V in M` を `M[V/x]` に置き換えることである。

2026-10-09 の完了時の性能の測定（測定の記録 `tools/bench/results/2026-10-09-first-release-4304d507f6bf.md` の「中間表現の最適化の候補」）で CPU プロファイルを採った。fib・loop・trait では時間の 85% ほどが VM の命令の振り分けにかかっていた。しかし、三つの変換がそれぞれどれだけの命令を省くかは、プロファイルからは分けて読めなかった。測定で大きな費用が見つかったのは、HTTP のリソースの表の走査、`List.range` の構築、出力の IO の受け渡しで、どれも中間表現の変換とは別の箇所である。

## 決定

1. 初回リリース版では、中間表現の最適化を行わない。
2. 初回リリース版の後に、三つの候補を変換ごとに試作し、変換を入れた版と入れない版を測って採否を決める。変換は、01-12「置き換えてよい等式」の向きに従うものと、観測できる振る舞いを変えないことを示せるものに限る規則（02-06）を保つ。

## 検討した代替案

- **効果の見込める変換を初回リリース版に一つ入れる**: どの変換の効果が大きいかを示す測定がない。変換を入れると、脱糖とコード生成の確認の範囲が増える。

## 帰結

- 02-06「最適化」の記述と、07-02 の中間表現の最適化の項目を改めた。
- 測定で見つかった、中間表現の変換とは別の性能の問題（リソースの表の走査、`List.range` の構築、出力の受け渡し、大きなスクリプトの検査の時間）は、処理系の改善の候補として扱う。リソースの表の走査は、初回リリース版の前に直す。
