# 0188. サーバモードの認証は、コーディングエージェントが操作できない経路で、利用者がその場にいることを確かめる

- 状態: 採択
- 日付: 2026-09-29
- 関連章: [セキュリティモデル](../07-quality/07-01-security-model.md)
- 関連する未決事項: [OPEN-055](../open-issues.md#open-055)

## 背景

設計者は、サーバモードで、設定の変更・スクリプトの登録・削除と、認証を要すると設定したスクリプトの実行に、認証を求めることを提案した。手段の候補は、パスワード、OS の鍵保管庫、YubiKey などの物理キーである（[OPEN-055](../open-issues.md#open-055)）。

コーディングエージェントに `server register … --password …` のようなコマンドを実行させると、エージェントはパスワードを知る。以後、エージェントは自分で認証を通れる。脅威モデルは、エージェントを信頼しないものとして扱う（[ADR 0179](0179-threat-model-and-server-mode-premise.md)）。

## 決定

1. 認証を求める操作は、`server settings` による設定の変更、`server register`・`server unregister`、認証を要すると設定したスクリプトの実行（`server job start`）とする。
2. 認証は、コマンドの引数や、コマンドを実行した端末では行わない。デーモンは、利用者が別の端末で開いた承認のための対話の画面（TUI）に確認を求め、利用者はそこで承認する。承認の画面を開くコマンドの名前と形は、サーバモードの章で定める。
3. 初めの版の認証の手段は、パスワードとする。パスワードは、Argon2id で派生したハッシュだけを保存する。
4. Touch ID などの生体認証と、FIDO2 のキー（YubiKey など）へのタッチは、後の版で加える。CLI から Touch ID を使えるか、純 Rust の FIDO2 のクレートがどこまで使えるかは【要検証】である。

## 検討した代替案

- **パスワードをコマンドの引数か、コマンドを実行した端末で入れる**: 作るのは簡単である。しかし、エージェントがコマンドを実行した場合、エージェントがパスワードを見る。
- **初めから OS の仕組み（macOS の Touch ID、Linux の polkit など）に任せる**: パスワードを自前で管理しない。しかし、OS ごとの差が大きく、SSH で接続しているときには使えない場合がある（【要検証】）。

## 帰結

- エージェントは、承認の画面を開いている利用者の操作なしに、認証を要する操作を完了できない。
- 利用者は、エージェントとは別の端末で承認の画面を開く必要がある。SSH で接続しているときは、別の SSH のセッションで開く。
- 承認の画面が開いていないときの振る舞い（待つか、誤りとするか）と、承認を待つ時間の上限は、サーバモードの章で定める。
- ADR 0179 の前提が崩れた場合（エージェントが承認の画面を開けるなど）は、この認証も迂回されうる。
