# 0289. 解放した後の `Http.Exchange` に `Http.requestOf` を使うと実行時エラーとし、要求の内容を解放のときに手放す

- 状態: 採択
- 日付: 2026-09-30
- 関連章: [ネットワークのモジュール](../03-interop/03-09-network.md)
- 関連する未決事項: なし

## 背景

[ネットワークのモジュール](../03-interop/03-09-network.md)の「サーバ」は、`Http.requestOf` を解放した後の `Http.Exchange` にも使え、受け付けた要求を返すと定めていた。要求は受け付けた時点で読み終えているので、関数は外部に作用する操作を行わない、という理由である。

U3 の実装プランを書く途中で、この規則の費用が分かった（`docs/implement/README.md` の「U3 の作業の文書で見つかった点」の 2）。解放は接続を閉じて OS の資源を手放すので、解放の後も要求を返すには、要求の内容（本体を含む）を接続と別に持ち、実行の終わりまで残す必要がある。`Http.serve` で長く動くサーバでは、受け付けた要求の数に比例してメモリが増え、実行の終わりまで減らない。

## 決定

1. 解放した後（解放を始めた後を含む）の `Http.Exchange` に `Http.requestOf` を使うと、実行時エラー（解放したリソースの使用）とする。`Http.respond` と同じ扱いである。
2. 処理系は、受け付けた要求の内容を、その `Http.Exchange` を解放するときに手放す。受け付けた要求の数に比例してメモリが増えることはない。
3. 要求を解放の後にも使うときは、解放の前に `Http.requestOf` で `Http.Request` の値を得ておく。得た値は言語の値であり、解放の後も使える。
4. `Http.requestOf` の型（`function(Http.Exchange) -> Http.Request`）は変えない。外部に作用する操作を行わないことも変えない。

## 検討した代替案

- **解放の後も使える規則を保ち、要求の内容を実行の終わりまで残す**: 03-09 の規則を変えずに済む。しかし、長く動くサーバのメモリが要求の数に比例して増え続ける。`Http.serve` はサーバを長く動かすための関数なので、この費用は避けられない場面で生じる。
- **`Http.accept` が返す `Http.Exchange` の値に要求の値を持たせ、値が使われなくなったら回収する**: 解放の後も使え、メモリも増え続けない。しかし、実装プランで凍結した値の表現（リソースの値はリソースの表の番号を持つ）を変えることになる。要求を解放の後に読む必要は、解放の前に値を得れば満たせるので、表現を変えるほどの利点はない。
- **残す要求の数に上限を設け、古いものから捨てる**: メモリは抑えられる。しかし、解放の後の `Http.requestOf` が要求を返すかどうかが、ほかの要求の数で変わり、利用者が振る舞いを予測できない。

## 帰結

- [ネットワークのモジュール](../03-interop/03-09-network.md)の「サーバ」の規則を改める。
- `Http.serve` の標準ライブラリのソースは、`with` の範囲の中で `Http.requestOf` を呼ぶので、振る舞いは変わらない。[並行処理](../01-spec/01-11-concurrency.md)の例も同じである。
- 解放の後に `Http.requestOf` を呼んでいたスクリプトは実行時エラーになる。この規則は初回リリース版の実装の前に改めたので、利用者のスクリプトへの影響はない。
- 実装プランの 10-16「受け付けた要求の保存」と L30 を、解放のときに要求の内容を手放す形に改める。
