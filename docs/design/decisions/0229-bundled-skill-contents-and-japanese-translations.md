# 0229. 同梱の Agent Skill を短い SKILL.md と必要なときに読む参照の文書で構成し、参照の文書は生成できるものを処理系のビルドで作り、日本語の訳を設計者向けに別に置く

- 状態: 採択（決定 5 の生成の時点を [0288](0288-skill-documents-generated-by-tool-and-committed.md) で改めた）
- 日付: 2026-09-29
- 関連章: [Agent Skills 対応](../06-tooling/06-06-agent-skills.md), [構文](../01-spec/01-02-syntax.md), [標準ライブラリ](../03-interop/03-06-stdlib.md), [診断エンジン](../02-impl/02-10-diagnostics.md)
- 関連する未決事項: [OPEN-011](../open-issues.md#open-011), [OPEN-047](../open-issues.md#open-047)

## 背景

設計メモは、言語仕様・標準ライブラリのリファレンス・イディオム集を専用の Agent Skill として言語の公式配布物に同梱すると決め、Skill に入れるものとして、文法（EBNF）、標準ライブラリのリファレンス、イディオム集、よくある誤り集、既知の言語との対応表を挙げた（[設計メモ](../sources/fp-language-design.md) 23.1、23.3）。Benitoite は学習データにない言語なので、LLM は Skill に書いたことを頼りにスクリプトを書く。

Agent Skills の仕様（[Specification](https://agentskills.io/specification)、2026-09-29 に確認）では、Skill は `SKILL.md` を置いたディレクトリである。エージェントは、起動のときに `name` と `description` だけを読み、Skill を使うと決めたときに `SKILL.md` の本文を読み、ほかのファイル（`references/` など）は必要になったときに読む。仕様は、`SKILL.md` を 500 行より短くし、詳しい参照の資料を別のファイルに分けることを勧めている。

参照の資料を手で書くと、文法や標準ライブラリを変えたときに Skill の記述が古いまま残るおそれがある。Skill の読み手の LLM は、古い記述に従ったスクリプトを書き、処理系の診断と食い違う。

設計者は、Skill の内容を自分でも読んで学びたいとした。ただし、エージェントには英語の版だけを使わせたいとした。

## 決定

1. 同梱の Agent Skill は、手で書く短い `SKILL.md` と、必要なときに読む参照の文書（`references/` の下のファイル）からなる。`SKILL.md` には、作業の手順（書く、`check` を実行する、診断を読んで直す、`run` か `test` で実行する）と、主な言語の規則の要約を書く。
2. 参照の文書は、文法（EBNF）、標準ライブラリのリファレンス、診断コードの説明、イディオム集、よくある誤り集、既知の言語との対応表とする。
3. 生成できる参照の文書は生成する。
   - 文法は、[構文](../01-spec/01-02-syntax.md)の「初回リリース版の文法の全体」の EBNF から作る。
   - 標準ライブラリのリファレンスは、標準ライブラリのソースの宣言の型とドキュメントコメントから作る。
   - 診断コードの説明は、処理系の中の診断の表のコードの説明から作る。
4. イディオム集、よくある誤り集、既知の言語との対応表は手で書く。これらに載せたコードの例は、ゴールデンテストと同じ仕組みで検査し、期待する出力を書いた例は実行して出力も比べる。
5. 生成は処理系のビルドのときに行い、生成した Skill を処理系の実行ファイルに埋め込む。配る Skill は、同じ実行ファイルの処理系と同じ版になる。
6. Skill は英語で書く。読み手が LLM であり、言語リファレンス（`docs/reference/`）も英語で書いているからである。
7. 設計者が読むために、Skill の内容と言語リファレンスの日本語の訳を作る。
   - 正は英語の版とする。日本語の版は、リリースのたびに英語の版から LLM が訳して作る。
   - 日本語の版の各ファイルの先頭に、訳であること、訳した元の版、英語の版を正とすること、エージェントが使うためのものではないことを書く。
   - 日本語の版は Skill のディレクトリの外に置き、`benitoite skill install` が書き出すものに含めない。置き場所は `docs/ja/` の下とする【方針】。
8. `docs/reference/` の英語の言語リファレンスは、現在は最小実行版の範囲だけを扱う。初回リリース版の範囲に書き直すことは、初回リリース版の作業に含める。

## 検討した代替案

- **Skill をすべて手で書く**: 生成の仕組みが要らず、文章を読み手に合わせて自由に書ける。しかし、文法・標準ライブラリ・診断を変えるたびに、Skill を手で合わせる必要がある。合わせ忘れた記述は、処理系の検査を通らないスクリプトを LLM に書かせる。生成すれば、処理系と Skill の食い違いが構造上生じない。
- **Skill を日本語でも書き、利用者の言語に合わせて選ばせる**: エージェントが読む版が二つになり、訳の誤りが LLM の書くスクリプトに入りうる。評価（[ADR 0232](0232-skill-evaluation-with-tasks-and-harnesses.md)）も版ごとに要る。

## 帰結

- 処理系のビルドは、設計書の構文の章の EBNF を読む。ソースからビルドするにはリポジトリの全体が要る（[配布形態](../05-platform/05-01-distribution.md)の「ソースからのビルド」）。EBNF の注釈（`(* … *)`）は日本語なので、生成するときに除く。
- 診断の表に持つコードの説明は、サーバモードの MCP の道具 `explain`（[ADR 0210](0210-mcp-in-server-chapter-and-explain-tool.md)）より前に、初回リリース版の Skill の読み手を持つ。初回リリース版の実装プランは、すべての診断コードに説明を書くことを作業に含める。
- 標準ライブラリのドキュメントコメントに書いた例は、初回リリース版では検査しない（[OPEN-047](../open-issues.md#open-047)）。手で書く参照の文書の例だけを検査する。
- 日本語の訳は、処理系の動作にも Skill の評価にも使わない。訳の誤りは、設計者の学習の妨げにはなるが、利用者のスクリプトには影響しない。
- Skill の名前は、コマンドの名前に合わせて `benitoite` とする。コマンドの名前を [OPEN-011](../open-issues.md#open-011) で変えたときは、Skill の名前も変える。
