# 0234. リリースの試験は、配る実行ファイルを使い、三つの環境のすべてを開発機の上で一つのスクリプトから行う

- 状態: 採択
- 日付: 2026-09-29
- 関連章: [配布形態](../05-platform/05-01-distribution.md), [処理系のテスト戦略](../07-quality/07-03-compiler-testing.md), [Agent Skills 対応](../06-tooling/06-06-agent-skills.md)
- 関連する未決事項: [OPEN-060](../open-issues.md#open-060)

## 背景

初回リリース版は三つの環境で実行ファイルを配り、各環境の実行ファイルはその環境の OS の上でビルドする（[ADR 0176](0176-first-release-targets-and-static-linux-build.md)）。完了条件の最後の行は、配る実行ファイルを各環境で実行し、ほかの条件が同じ結果になることである（[ロードマップ](../00-overview/00-03-roadmap.md)の「完了条件」）。処理系のテストは外部コマンドの起動をテスト用のハンドラ表で置き換えうるので、実際の起動は各環境での確認で確かめる（[処理系のテスト戦略](../07-quality/07-03-compiler-testing.md)の「受け入れ例と仕様の項目の対応」）。

開発機は macOS（arm64）である。設計者は、リリースの試験を GitHub Actions などの CI で行わず、すべて開発機の上で行うよう指示した（2026-09-29）。

## 決定

1. リリースの試験は、配る実行ファイルそのものを使い、三つの環境のそれぞれで行う。ビルドと試験は、開発機の上で一つのスクリプト（`scripts/release.sh` など）から行う。CI は使わない。
2. 環境ごとのビルドと試験の場所は次のとおりとする。
   - macOS（arm64）: 開発機の上で直接行う。
   - Linux（arm64）: 開発機の上の Linux のコンテナか軽量の仮想機械の中でビルドし、試験する。Linux の上でビルドするので、[ADR 0176](0176-first-release-targets-and-static-linux-build.md) の決定 4 を満たす。
   - Linux（x86_64）: x86_64 を模倣するコンテナ（Linux の仮想機械の Rosetta か QEMU）の中でビルドし、試験する。遅いが、リリースのときにしか行わない。
3. 各環境で次のものを確かめる。
   - `scripts/check.sh` が通る。
   - 受け入れテスト（`testdata/acceptance/`）を配る実行ファイルで実行し、期待する結果になる。外部コマンドの起動（`Process.run`・`Process.shell`）は、実際に起動する。
   - Linux の実行ファイルが、glibc のない最小のコンテナの中で起動する（musl で静的にリンクしたことの確認）。
   - `benitoite skill install` が、Skill を正しく書き出す。
4. Agent Skill の評価（[ADR 0232](0232-skill-evaluation-with-tasks-and-harnesses.md)）は、構文・標準ライブラリ・Skill を変えたリリースでだけ行う。
5. 使うコンテナと仮想機械の道具と、x86_64 の模倣の上で Rust のビルドとテストが動くかは【要検証】であり、リリースの手順を書くときに選ぶ（[OPEN-060](../open-issues.md#open-060)）。

## 検討した代替案

- **一つの環境だけで試験する**: 試験の手間と時間が最も少ない。しかし、musl の静的なリンク、外部コマンドの起動、OS ごとのパスとシグナルの扱いは、環境ごとに違いうる。配る実行ファイルを、その環境で一度も動かさずに配ることになる。

## 帰結

- リリースは、開発機（macOS の arm64）がなければ行えない。
- x86_64 の模倣の上の試験は、時間がかかる。模倣の上で動かない試験があれば、その試験を x86_64 の試験から外すかを、リリースの手順を書くときに決める。
- [ADR 0176](0176-first-release-targets-and-static-linux-build.md) の帰結は、Windows では WSL2 の中で完了条件を確かめるとした。設計者は Windows の機械と、その上の WSL2（Ubuntu 26.04 LTS）を持っている。WSL2 に SSH でログインできるようにすれば、リリースのスクリプトが開発機から SSH で WSL2 に実行ファイルを送り、受け入れのテストを動かせる。そこで、WSL2 での確認は、初回リリース版の完了を判定するときとマイナー版のリリースのときに、SSH を通してスクリプトから行う【方針】。パッチ版では省く。WSL2 に SSH でログインする設定（WSL2 の中の SSH サーバと、Windows の側からの接続の通し方）は【要検証】である（[OPEN-060](../open-issues.md#open-060)）。
