## 目的と範囲

目指す方向、保証の範囲、目的の優先順位、想定する利用者、言語全体に通す設計原則、目的が衝突したときの判断基準を定める。

## 前提

言語の名称は `Benitoite`（ベニトアイト）とする（[ADR 0132](../decisions/0132-language-name-benitoite.md)）。CLI のコマンドの名前は `benitoite`、スクリプトのファイルの拡張子は `.bnt` とする（[ADR 0241](../decisions/0241-command-name-and-extension.md)）。本章でいう「利用者」は Benitoite のスクリプトを使う人を、「設計者」は Benitoite を設計・実装する人を指す。

## 仕様

### 目指す方向

> 怠惰・短気・傲慢を再び
> （Laziness, Impatience, and Hubris — Again）

上はこの方向を一言で示す標語である。三つの美徳の英語表記は、Larry Wall らの『Programming Perl』での呼び方に合わせる。Perl の文書 `perlglossary` は、同書の第 4 版の用語集に基づき、laziness・impatience・hubris をプログラマの三つの美徳と定義している（[ADR 0245](../decisions/0245-perl-virtues-source-and-fact-check-timing.md)）。

【方針】Benitoite は、利用者が「怠惰・短気・傲慢」（Larry Wall のいうプログラマの三大美徳）のままで、言語の詳細を学ばずに、LLM によるスクリプトの作成・修正を通じて作業を自動化できることを目指す。利用者は、行いたい作業と、スクリプトに許可する操作を決める。言語処理系（以下、処理系）は、スクリプトが型とエフェクトの規則に適合しているかを検査する。LLM は、コードの作成・修正と、診断の説明を担う。

標語の「怠惰・短気・傲慢のままで」は、利用者に求める習得・調査・再確認の負担を減らす、という本言語の設計上の解釈である。三つの美徳と、減らしたい負担、設計上の目標の対応は次のとおりである。

| 標語 | 減らしたい利用者の負担 | 設計上の目標 |
|---|---|---|
| 怠惰 | 言語の習得と、定型的なコードの作成 | 作業の指示から LLM がコードを作成・修正し、処理系がそれを検査できる |
| 短気 | 試行錯誤と、失敗の原因の調査 | 静的に検出できる誤りを実行前に報告し、実行時の失敗には、原因と対処の判断に必要な情報を付ける |
| 傲慢 | 修正のたびにコード全体を読み直すこと | 既存の契約への違反と、契約そのものの変更を確認でき、修正の影響を判断する材料を得られる |

この方向は最終的に到達できるかどうかが分からない目標である。

### 保証の範囲

【方針】静的検査で確認するのは、言語仕様が定める型とエフェクトの規則にスクリプトが適合していることである。検査を通ったことだけを根拠に、処理結果が利用者の意図に合うこと、外部との通信やファイル操作が成功すること、処理が終了することは保証しない。例えば、集計の条件を「以上」から「超える」へ変えても、型とエフェクトは変わらないことがある。

【方針】エフェクトの静的な追跡と、実行時に許可する操作の制御（権限）は、別の機構として区別する（[設計メモ](../sources/fp-language-design.md) 3.2）。同じ「ファイルの読み取り」というエフェクトでも、読む対象は実行時まで確定しないことがある。利用者には、実行前に確認できる操作の範囲と、実行時まで確定しない事項とを分けて示す。

【決定】実行時の権限制御と、それを OS のサンドボックスでも強制する仕組みは、処理系をサーバとして動かす形（サーバモード）とあわせて、初回リリース版の後に提供する（[ADR 0177](../decisions/0177-server-mode-after-first-release.md)、[OPEN-055](../open-issues.md#open-055)）。それまでの版が提供する保証は静的検査だけであり、スクリプトは処理系を起動した利用者の OS の権限で行える操作をすべて行える。スクリプトが触れる範囲の制限は、処理系を起動する側（Agent Skills を実行するハーネスのサンドボックス、コンテナ、OS の権限）に委ねる。実行時の権限制御を持たない版も、宣言する保証の範囲をロードマップに示したうえで、利用者に提供してよい。

各マイルストーンで提供する検査と権限制御の範囲は[ロードマップ](00-03-roadmap.md)で定める。

### 目的と優先順位

【方針】Benitoite の目的は次の二つである。

| 目的 | 位置づけ |
|---|---|
| Perl の精神を受け継ぎ、利用者が「怠惰・短気・傲慢」のままで使えるスクリプト言語であること | 表向きの目的 |
| 設計者自身が、関数型プログラミング（型システム・エフェクト・永続データ構造など）と言語処理系（解析器・仮想機械・ランタイムなど）を学ぶこと | 実質的な目的 |

「表向き」「実質的」は呼び名であり、どちらも実際に追う目的として扱う。

【決定】設計者は処理系を手で実装しない。処理系は LLM が実装する（[ADR 0076](../decisions/0076-initial-implementation-in-rust.md)）。実質的な目的の学習は、設計書を作る過程と、LLM が書いた実装を読み、必要なときに LLM へその実装を選んだ理由を質問することで行う。

表向きの目的は、目指す方向をそのまま目的として定めたものである。Agent Skills から実行できることは、この目的を実現する手段として位置付ける。Agent Skills では LLM がスクリプトを書いて実行するので、利用者は言語を学ばずに済み、目指す方向で LLM に割り当てた分担が成り立つ。Agent Skills からの実行の詳細は [Agent Skills](../06-tooling/06-06-agent-skills.md) で定める。

### 想定する利用者と接点

【方針】想定する利用者はプログラマに限らない。利用者は LLM にスクリプトを書かせ、次の二つの接点で Benitoite に関わる。

1. **主な接点**: コードを読まずに、実行前にスクリプトが行いうること（エフェクトと権限）を確認し、実行後に結果と失敗の理由を確認する。権限の確認は、実行時の権限制御とあわせてサーバモードで提供する（前述の「保証の範囲」）。
2. **副次的な接点**: 出力する文字列の書式など、コードの表面の一部をときどき直接直す。

コードを書くのは主に LLM である。処理系が出す情報の第一の読み手は、用途によって分ける。コードの誤りの診断は LLM を第一、人間を第二の読み手とする。権限の説明と実行結果は、利用者が判断に使うので、人間を第一の読み手とする。

### 設計原則

【方針】言語の各章は次の原則に従う。原則どうしが衝突したときは、番号の小さいものを優先する。

1. **静的に検出できる誤りを実行前に報告する**: 型検査・エフェクト検査で検出できる誤りを、実行時まで持ち越さない。
2. **変更後も契約を検査し、契約と権限の変更を見落とさせない**: コードを修正したら、型とエフェクトの契約への適合を再検査する。契約そのものを変えた場合は、既存の契約への適合とは区別して示す。LLM が実装と契約を同時に変えると、変更後の契約で検査が通っても、以前の契約を守ったことにはならないからである。実行に必要な権限の変更も、エフェクトの変更とは別に確認できることを目指す（[OPEN-015](../open-issues.md#open-015)）。
3. **利用者が許可する操作と実行結果を理解でき、直接編集する箇所を壊しにくくする**: 権限の説明と実行結果は、プログラマでない人にも読める形で示す。文字列補間のように利用者が直接直しうる箇所は、完成形に近い見た目にし、誤りを実行前に検出する。
4. **記述量の少なさより、検査と診断の明確さを優先する**: 書き手は主に LLM なので、記述量を減らすことより、処理系が検査でき、診断が明確になることを優先する。
5. **同じ役割の構文を、必要な理由なく増やさない**: 同じ役割の書き方が複数あると、LLM の出力が揺れ、差分の確認が難しくなる。上位の原則（特に原則 3）に資する場合は、重複を認めてよい。
6. **簡単なことは簡単に、難しいことも可能に**: テキスト処理・コマンドの実行・短いスクリプトを簡潔に書ける。

原則 2 を具体化する方針として、共有された可変状態を制限する。共有された可変状態を減らすと、修正の影響が及ぶ範囲を型とエフェクトから追いやすくなる。ただし、影響が離れた箇所に及ばないことまでは保証しない。

### 構文の判断基準

【方針】表層構文は、次の二点で評価して選ぶ。設計者の好みは基準にしない。

1. LLM による生成・修正の成功率。構文解析と型検査の通過だけでなく、課題の期待結果を満たすことまで含めて測る。
2. 人間による読みやすさ

1 を満たしやすいと見込む構文の性質は、次のとおりである。

- 学習データに多い既存言語の見た目に近い
- 暗黙に文脈で意味が変わる箇所が少ない
- ブロックの範囲が字面で閉じており、編集する範囲を判断しやすい

この見込みから、波括弧を使う C 系の見た目の関数型言語（Rust、Scala 3、Gleam など）の構文を暫定の候補とする。この見込みは仮説であり、優位性は【要検証】である（[OPEN-012](../open-issues.md#open-012)）。この候補に沿った表層構文の骨格（ドット記法の扱いを含む）は [ADR 0004](../decisions/0004-surface-syntax-skeleton.md) で決めた。

### 目的が衝突したときの判断基準

【方針】表向きの目的と実質的な目的が衝突したとき（例: 既製品を使えば早いが、自作すると学べる）は、次の線引きで両立させる。ここでいう「自作」は、既存の OSS を使わずにこのプロジェクトで設計・実装することを指す。実装を行うのは LLM である。

- 言語の中核（型システム・エフェクト・コレクション）は自作する。
- 言語処理系の主要部（字句解析器・構文解析器、中間表現・バイトコード・VM）も、実質的な目的の学習の対象なので自作する。
- それ以外の基盤（GC、プラグインの実行環境など）は既存の OSS を使う。

【方針】中核の自作に時間がかかり、利用者向けの機能を出す時期と衝突した場合は、提供する機能の範囲と時期を調整する。提供済みの機能について宣言した保証を、学習目的を理由に弱めない。
