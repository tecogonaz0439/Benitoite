# ロードマップ

## 目的と範囲

初回リリース版の範囲（含めるものと含めないもの）と、その完了条件を定める。あわせて、初回リリース版で利用者に宣言する保証、版の番号とコードネーム、自作する部分と既存の OSS を使う部分の区分、利用する既存の OSS のライセンス、形式検証の範囲、実装の分担を定める。

各機能の中身は個別の章で定める。初回リリースの後の改造と検討の項目は docs/todo/ に置く（設計者が手元に持つ非公開の別のリポジトリ）。

## 前提

[目的と設計原則](00-01-goals.md)の二つの目的と、目的が衝突したときの判断基準を前提とする。特に、中核の自作に時間がかかる場合は提供する範囲と時期で調整し、提供済みの機能について宣言した保証は弱めない。

処理系の構成と段は[全体像](00-02-architecture.md)に従う。処理系は Rust で書き、LLM が実装する。

「初回リリース版」は、機能の範囲の名前である。その範囲を最初にリリースする版が `0.0.1` である。

## 仕様

### バージョンとコードネーム

【決定】処理系のバージョンは、メジャー・マイナー・パッチの三つの数を `.` でつないだ形（`1.2.3` など）で表す。

【決定】初回リリース版の範囲を最初にリリースする版は `0.0.1` とする。`0.0.1` はソースコードだけのリリースとし、実行ファイルは配らない。git のタグは `v0.0.1` とする。メジャーバージョンが 0 の間は、互換性を壊す変更をしてよい。`0.0.x` の間はどのリリースでも、`0.1.0` より後はマイナーバージョンを上げる版（`0.x.0`）に限る。リリースの形と互換性の方針の詳細は[配布形態](../05-platform/05-01-distribution.md)で定める。

【決定】コードネームは、メジャーバージョンが 1 の間まで `San Benito` とする。`0.0.1` のコードネームは `San Benito` である。

### 初回リリース版で宣言する保証

【方針】初回リリース版で、静的検査と実行時の権限制御について宣言する範囲は次のとおりとする。ここに書いていない保証を、初回リリース版の処理系が満たしていると宣言しない。

| 項目 | 宣言する範囲 |
|---|---|
| 静的検査が保証すること | 型の規則への適合。エフェクトの規則への適合（組み込みの細かいエフェクト（`File.Read`・`Process.Run` など）の区別を含む。関数を引数にとる関数は、エフェクト変数で多相にする）。型のエフェクトに含まない組み込みの操作（プロセスの終了、外部コマンドの起動など）を行わないこと。利用者が定義するエフェクトが、どこかのハンドラで処理されること |
| 実行時の権限制御 | 行わない。スクリプトは、処理系を起動した利用者の OS の権限で行える操作をすべて行える。隔離は、処理系を起動する側（ハーネスのサンドボックス、コンテナ、OS の権限）に委ねる |

【決定】初回リリース版には外部の関数の層を実装しないので、外部に作用する経路は標準ライブラリの IO とネットワークの関数だけであり、どれも IO 実行器を通す。

### 初回リリース版

#### 範囲

【方針】初回リリース版には、次のものを含める。

| 領域 | 含めるもの |
|---|---|
| 言語 | 単一のファイルのスクリプトと、モジュールと import（名前で取り込み、根のディレクトリの下に限る）、ディレクトリを指定した実行。関数の定義と適用、局所の束縛の文 `bind`・`shadow`、条件分岐、代数的データ型の宣言 `data` とパターンで分岐する式 `match … with`（網羅性の検査を含む）、戻り値の型の `->`、HM 型推論、末尾呼び出しの保証。型クラス（辞書渡し。上位の型クラスを含む）、利用者が書ける組み込みの制約 `equality`・`key`、レコード、可変状態、明示遅延（`lazy`・`Lazy.force`）、リソーススコープ、文字列補間、複数行の文字列と raw 文字列、パターンの拡張（ガード・選択肢・範囲・リスト）、トップレベルの定数、型の別名、ドキュメントコメント、エラー処理、属性（`@test`・`@deprecated`）、構造化された IO の並行処理 |
| 基本型 | `Integer`・`Float`・`String`・`Character`・`Boolean`・`Unit`・`Byte`・`Decimal`（[基本型の意味論](../01-spec/01-04-types-basic.md)） |
| エフェクトと権限 | エフェクトの注釈と検査、エフェクト変数、組み込みの細かいエフェクト、モジュールの中で宣言するエフェクト、利用者が定義するエフェクトとハンドラ、スクリプトのディレクトリを返す関数。契約の変更を処理系が表示する機能は含めず、同梱の Agent Skill の手順で示す。権限の宣言の構文は設けない。実行時の権限制御、実行前の権限の表示、権限の変更の表示は含めない |
| ライブラリ | 名前空間 `Benitoite` の標準ライブラリ。prelude の Option・Result・リストと永続コレクション、`Benitoite.IO` の下の IO を行うモジュール（標準出力と標準エラー出力、ファイル、コマンドライン引数、外部コマンドの起動 `Process.run`・`Process.shell` を含む）、`Benitoite.Trait` の標準の型クラス。テキストとデータを処理する純粋なモジュール（`Benitoite.Path`・`Json`・`Regex`・`Csv`・`Time`・`Encoding`・`Hash`）。`Benitoite.Network.Http` の HTTP のサーバ（TLS なし）とクライアント（HTTPS を含む）。実装に使うクレートは[ライブラリの構成](../03-interop/03-01-library-structure.md)で定める |
| 処理系 | [全体像](00-02-architecture.md)の全段（字句解析から VM とランタイムまで）。span、コメントの保持、構文エラーからの回復を備える |
| ツール | CLI の `run`・`check`・`test`・`fmt`・`skill`、シェバンによる実行（いずれも処理系をサーバとして動かさずに起動する形）、同梱の Agent Skill |
| 診断 | 診断コード、span、ソースの抜粋を持つ診断。`help:` による修正案を、直し方を示せる検査の誤りの診断に付ける（[診断](../02-impl/02-10-diagnostics.md)の「修正案」） |
| 配布 | 処理系の単一バイナリ（macOS の arm64、Linux の x86_64・arm64。[配布形態](../05-platform/05-01-distribution.md)）。`0.0.1` はソースコードだけのリリースとし、実行ファイルを配らない |

【方針】エフェクトは、外部に作用する処理を組み込みの細かいエフェクトに分け、プロセスの終了・外部コマンドの起動など影響の大きい操作もエフェクトで制限する。ケーパビリティの値は設けない。`IO` は、組み込みのエフェクトをまとめた名前として使う。利用者が定義するエフェクトとハンドラ（代数的エフェクト）も含める。

並行処理は、スクリプトで簡易な HTTP サーバ（HTML を返す、REST API を提供する）を動かせる水準とする。一つのタスクが接続を待ち受けたり計算を続けたりしている間も、ほかのタスクを止めない。複数のコアでの並列化は含めない（[並行処理](../01-spec/01-11-concurrency.md)）。HTTP サーバの API は[ネットワークのモジュール](../03-interop/03-09-network.md)で定める。

【方針】次のものは初回リリース版に含めない。JIT コンパイラ、複数のコアでの並列化、REPL、LSP サーバ、パッケージ管理、外部の関数（WASM のモジュールの関数）、WASM プラグイン、スクリプトを埋め込んだ実行ファイルの生成、処理系コアの WASM 化、モバイル向けの提供、サーバモード、実行時の権限制御、OS のサンドボックスによる強制、MCP サーバ、エージェントハーネス。

#### 完了条件

【方針】初回リリース版は、次の条件をすべて満たしたときに完了とする。

| 条件 | 期待する振る舞い |
|---|---|
| 同梱の Agent Skill だけを与えた LLM が、JSON ファイルを読んで集計するスクリプトを書く | 検査・診断・修正を繰り返して検査を通り、期待する出力を得る |
| 外部コマンドを引数の配列で起動するスクリプト（`Process.run`）と、シェルで実行するスクリプト（`Process.shell`）を実行する | どちらも期待する出力を得る |
| 影響の大きい操作（外部コマンドの起動、プロセスの終了、ファイルの書き込み）を、テストのコードのハンドラで差し替えて `test` を実行する | それらの操作を外部に行わずにテストが通る |
| コメントを含むスクリプトに `fmt` を適用する | コメントが保たれ、整形後も同じ検査結果になる |

[配布形態](../05-platform/05-01-distribution.md)で定める各環境での確かめは、初回リリース版の完了条件に含めない（docs/todo の TODO-073）。

### 自作する部分と既存の OSS を使う部分

【方針】目的が衝突したときの判断基準（[目的と設計原則](00-01-goals.md)）に従い、処理系の各部分を次のように分ける。ここでいう自作は、既存の OSS を使わずにこのプロジェクトで設計・実装することであり、実装は LLM が行う。

| 部分 | 区分 | 理由 |
|---|---|---|
| 型検査器（HM 型推論・型クラス・エフェクト検査） | 自作 | 言語の中核 |
| 永続コレクション | 自作 | 言語の中核 |
| 字句解析器・構文解析器 | 自作 | 実質的な目的（言語処理系の学習）の対象 |
| 中間表現・バイトコード・VM | 自作 | 実質的な目的の対象 |
| 診断エンジン | 自作 | LSP の形式に依存しない独自の表現を持つ |
| メモリの管理（言語の値の回収、確保器、根の列挙） | 自作 | 目的と設計原則の線引きに対する、メモリの管理についてだけの例外とする。値の表現、メモリの管理、VM の枠の持ち方は互いの設計を縛り合うので、回収を外部のクレートに任せると、学ぶ対象の中心が欠けるからである |
| 10 進の小数（`Decimal`）の算術 | 自作 | 言語の中核にも処理系の主要部にも当たらないが、結果の桁数と丸めの規則（[基本型の意味論](../01-spec/01-04-types-basic.md)）を一か所で守るために、目的と設計原則の線引きの例外として自作する |
| 標準ライブラリが包む機能（正規表現・JSON・CSV・時刻・Base64・SHA-256・OS の乱数など） | 既存 | 中核にも主要部にも当たらない基盤。使うクレートは[ライブラリの構成](../03-interop/03-01-library-structure.md)で定める |

### 利用する既存の OSS のライセンス

【方針】処理系と標準ライブラリは、Rust（標準ライブラリ）を基盤として実装する。Rust のライセンスは、MIT と Apache-2.0 のどちらかを選べる形である。標準ライブラリの実装に使うクレートと、依存に許可するライセンスは[ライブラリの構成](../03-interop/03-01-library-structure.md)の「使う Rust のクレート」と「依存のライセンス」で定める。

性能の比較対象は測定に使うだけで、配布物には含めない。

いずれも許容型のライセンスであり、処理系のバイナリに含めて配布するときは、著作権表示とライセンス文を配布物に添える必要がある。Apache-2.0 のものは NOTICE ファイルの内容も添える。【方針】添える一覧は、手で管理せず、配布するバイナリが実際に含むモジュールから生成する。ライセンスはバージョンによって変わりうるからである。表示の方法は[配布形態](../05-platform/05-01-distribution.md)で定める。

【決定】処理系・標準ライブラリ・同梱の Agent Skill・言語の文書・設計書のリポジトリのライセンスは、MIT と Apache-2.0 のデュアルライセンス（`MIT OR Apache-2.0`）とする。著作権表示は `Copyright (c) 2026 tecogonaz and Benitoite contributors` とする（[配布形態](../05-platform/05-01-distribution.md)の「ライセンスの表示」）。

### 形式検証の範囲

【方針】初回リリース版の形式検証は、次の三つの段階から成る。

| 段階 | 内容 |
|---|---|
| 0 | コア計算の構文・型付け規則・簡約規則を数学記法で書く（[コア計算と脱糖](../01-spec/01-12-core-calculus.md)） |
| 1 | 実行可能な意味論を用意し、ランダムに生成したプログラムで反例を探す（証明ではない） |
| 2 | 証明支援系で、選んだ性質を証明する |

【決定】段階 1 の実行可能な意味論には、参照インタプリタを初回リリース版の範囲に広げたものを使う。型の付くプログラムを無作為に生成し、VM と参照インタプリタの両方で実行して結果を比べ、反例を探す（[処理系のテスト戦略](../07-quality/07-03-compiler-testing.md)の「差分テスト」）。反例から[コア計算と脱糖](../01-spec/01-12-core-calculus.md)の規則の誤りが分かったときは、規則を直す。

【決定】段階 2 は、[コア計算と脱糖](../01-spec/01-12-core-calculus.md)の進行と保存、エフェクトの健全性を、Lean 4 で証明する。段階 2 の完了は初回リリース版の完了条件に含めない。対象、進め方、01-12 との対応は[形式意味論と検証](../07-quality/07-04-formal-semantics.md)で定める。

### 設計から実装までの分担と進め方

【決定】処理系は LLM が実装する。設計者は処理系を手で実装せず、LLM が書いた実装を読み、必要なときに実装の理由を LLM に質問して学ぶ（[目的と設計原則](00-01-goals.md)）。設計書と実装が食い違ったら、言語仕様を正として実装を直すか、設計書を改める。

【決定】実装プランと処理系のソースコードは、設計書と同じリポジトリに置く。
