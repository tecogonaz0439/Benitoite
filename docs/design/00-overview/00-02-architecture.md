# 全体像

## 目的と範囲

Benitoite を構成する要素（言語仕様・処理系・ライブラリ・ツールチェーン・配布物）と、それらの関係を定める。各要素の中身は個別の章で定め、本章はどの要素がどの要素に依存し、どの情報がどこからどこへ渡るかだけを扱う。対象は初回リリース版の構成である。

## 前提

[目的と設計原則](00-01-goals.md)で定めた分担を前提とする。利用者は作業と許可する操作を決め、処理系は型とエフェクトの規則への適合を検査し、LLM はコードの作成・修正と診断の説明を担う。

## 仕様

### 構成要素

【方針】Benitoite は次の要素から成る。

| 要素 | 内容 | 定める章 |
|---|---|---|
| 言語仕様 | 正しいプログラムの条件と、その実行の意味。処理系の実装方式に依存しない | `01-spec/` |
| 処理系 | 言語仕様に従ってスクリプトを検査・実行するプログラム。Rust で書く | `02-impl/` |
| ライブラリ | core（prelude）と std | `03-interop/` |
| ツールチェーン | CLI・フォーマッタ・テストランナー・同梱の Agent Skill | `06-tooling/` |
| 配布物 | 上記を利用者の環境に届ける形態 | `05-platform/` |

言語仕様だけが規範であり、他の要素は言語仕様に従う側に立つ。処理系の振る舞いと言語仕様が食い違うときは、言語仕様を正として処理系を直す。

初回リリース版は、外部の関数（WASM のモジュールの関数）、WASM によるプラグイン、LSP サーバ、MCP サーバ、パッケージ管理を含めない。

### 言語仕様と処理系の境界

【決定】処理系は Rust で書き、LLM が実装する。性能を測定した後に実装言語を見直す段階は設けない。【方針】実行方式は、自作のバイトコード VM（JIT なし）とする。言語の値の回収は処理系が行う。【決定】初回リリース版は、循環する値も回収できる、止めて行う非移動のマーク・スイープで言語の値を管理する（[ランタイム](../02-impl/02-09-runtime.md)の「メモリの管理」）。方式は、改良した参照カウントと比べて選んだ。理由: 循環する値を、循環を集める仕組みを別に足さずに回収できるからである。

実行方式を差し替えても、処理系を別の言語で書き直しても言語仕様を変えずに済むように、`01-spec/` には VM・バイトコード・実装言語の型など実装方式に依存する記述を置かない。例えば、末尾呼び出しの保証は `01-spec/` で「深い末尾再帰でもスタックを使い果たさない」という観測可能な性質として定め、それを VM でどう実現するかは `02-impl/` で定める。

### 処理系の段

【方針】処理系は、スクリプトを次の段で順に処理する。

```text
ソースの読み込み ─ ファイル ID を付けたソースのバイト列
  │
  ▼
字句解析・構文解析 ─ span 付きの AST
  │
  ▼
名前解決・モジュール読込 ─ 依存グラフ、束縛の解決
  │
  ▼
型検査（型推論・型クラス解決・エフェクト検査）
  │                              ┌──────────────┐
  ├─ 各段が出す診断 ─────────────▶│ 診断エンジン │──▶ CLI
  ▼                              └──────────────┘
中間表現への脱糖・パターンマッチのコンパイル
  │
  ▼
バイトコード生成
  │
  ▼
VM とランタイム（IO 実行器・リソース追跡）
```

型検査までの段を「検査」、それ以降を「実行」と呼ぶ。検査だけを行う経路（`check`）と、検査の後に実行まで行う経路（`run`）があり、実行は検査を通ったスクリプトに対してだけ行う。これは設計原則 1（静的に検出できる誤りを実行前に報告する）を処理系の構造で担保するためである。処理系のテストでは、バイトコード生成と VM の代わりに、参照インタプリタ（reference interpreter）で中間表現を実行する経路も使う（[パイプライン](../02-impl/02-01-pipeline.md)の「検査と実行の経路」）。

【方針】span（ソース上の位置）は、すべての AST ノードの必須フィールドとする。脱糖（desugaring）で生成したノードにも由来位置を持たせ、どの段で出た診断もソース上の位置を示せるようにする。位置情報の扱いは[ソース管理と位置情報](../02-impl/02-02-source-and-spans.md)で定める。

各段の間で受け渡すデータ構造と、検査と変換を終えたプログラムを実行ごとの状態と分けて持つ形は、[パイプライン](../02-impl/02-01-pipeline.md)で定める。

### 診断の流れ

【方針】診断は、出力の形式に依存しない内部の表現として診断エンジンに集め、CLI がそれを出力の形式に変換する。内部の表現は LSP の `Diagnostic` をそのまま使わず、ファイル ID・span・診断コード・補助位置・修正案を持つ。

### スクリプトの作成から実行までの流れ

【方針】初回リリース版では、利用者・LLM・処理系は次の順に関わる。

1. 利用者が、行いたい作業を LLM に指示する。
2. LLM がスクリプトを書き、処理系で検査する。検査に失敗したら、LLM は診断を読んでスクリプトを直し、再び検査する。
3. 処理系が、検査を通ったスクリプトを実行する。
4. 処理系が、実行結果と失敗の理由を利用者に示す。

手順 2 は CLI の `check` を、手順 3 は CLI の `run` を通じて行い、手順 3 の実行は処理系のランタイムが行う。

【決定】初回リリース版では、処理系は実行に必要な権限を示さず、実行の許可も求めず、実行中の操作も拒否しない。実行前の権限の表示、利用者による実行の許可、実行中の許可の外の操作の拒否は、初回リリース版に含めない（[目的と設計原則](00-01-goals.md)の「保証の範囲」）。

### エフェクトと権限の置き場所

【方針】エフェクトの静的な追跡、エフェクトの意味を与えるハンドラ、実行時に許可する操作の制御（権限）は、別々の機構として扱う。初回リリース版が持つのは前の二つであり、置かれる場所も異なる。

| 機構 | 置き場所 | 定める章 |
|---|---|---|
| エフェクトの静的な追跡 | 型検査器 | [エフェクト](../01-spec/01-07-effects.md), [型検査器](../02-impl/02-05-typechecker.md) |
| ハンドラ | VM とランタイム | [エフェクト](../01-spec/01-07-effects.md), [仮想機械](../02-impl/02-08-vm.md) |

【方針】初回リリース版は実行時の権限制御を持たず、スクリプトが触れる範囲の制限と、敵対的なコードからの隔離を、Agent Skills を実行するハーネス側のサンドボックス（コンテナや OS の権限）に委ねる。言語側だけでセキュリティ境界を完結させる前提は置かない。分担の詳細は[セキュリティモデル](../07-quality/07-01-security-model.md)で定める。

### ライブラリと処理系の関係

【方針】ライブラリは次の層で構成する。初回リリース版には外部の関数を呼ぶ層を実装しない。標準ライブラリの作り方（言語で書く部分、Rust の組み込みの関数、クレートを包む関数）と使うクレートは[ライブラリの構成](../03-interop/03-01-library-structure.md)で定める。

| 層 | 内容 | 処理系との関係 |
|---|---|---|
| core / prelude | 言語独自の型と永続コレクション（Option・Result・ADT など） | 一部はコンパイラが特別扱いする |
| std | ファイル・プロセス・テキスト処理などを慣用的な API で提供するもの | Rust で実装した関数として VM から呼ぶ |

コンパイラが特別扱いする型・演算（Result・Option・IO など）と、ライブラリとして書く部分との境界は [ライブラリの構成](../03-interop/03-01-library-structure.md)で定める。

【方針】外部に作用する処理は、ランタイムの IO 実行器を通す。初回リリース版では、外部に作用する経路は標準ライブラリの IO とネットワークの関数だけであり、どれも処理系の一部として IO 実行器を通す。理由: 外部に作用するすべての経路が一か所を通るようにしておけば、操作の制御を後で加えるときに、その一か所に置けば迂回されないからである。

### ツールチェーンと処理系の関係

【方針】ツールチェーンの各ツールは、処理系の同じ検査の段（字句解析から型検査まで）と同じ診断エンジンを共有する。ツールごとに別の解析器を持たない。ツールごとに解析器を持つと、同じスクリプトに対する診断がツールによって食い違い、LLM と利用者がどちらを信じればよいか判断できなくなるからである。この方針により、構文解析器には、フォーマッタのためにコメントを保持することが求められる。詳細は[字句解析器と構文解析器](../02-impl/02-03-frontend.md)で定める。

| ツール | 使う段 |
|---|---|
| CLI の `check` | 検査 |
| CLI の `run` | 検査と実行 |
| CLI の `test` | 検査と実行（テスト用のハンドラを差し替える） |
| CLI の `fmt` | 字句解析・構文解析（コメントを保持する） |

### 配布物

【方針】処理系は、依存のない単一の実行ファイルとして作れるようにする。C のライブラリへの依存を避けるビルドの方針と、対応環境は[配布形態](../05-platform/05-01-distribution.md)で定める。初回リリース版は、スクリプトを埋め込んだ実行ファイルを作る機能を含めない。

【方針】言語仕様・std のリファレンス・イディオム集を専用の Agent Skill にまとめ、処理系の実行ファイルに同梱する。Agent Skills を実行する環境に処理系を入れる経路は[配布形態](../05-platform/05-01-distribution.md)で、同梱の Agent Skill は [Agent Skills 対応](../06-tooling/06-06-agent-skills.md)で定める。
