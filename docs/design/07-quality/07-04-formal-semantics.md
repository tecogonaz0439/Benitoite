# 形式意味論と検証

## 目的と範囲

形式検証の段階 2（証明支援系で、選んだ性質を証明する。[ロードマップ](../00-overview/00-03-roadmap.md)の「形式検証の範囲」）の対象、進め方、道具、[コア計算と脱糖](../01-spec/01-12-core-calculus.md)との対応を定める。段階 1（参照インタプリタと VM の差分テストで反例を探す）は[処理系のテスト戦略](07-03-compiler-testing.md)の「差分テスト」で扱う。

本章は、段階 2 の段階 A と段階 B（段階 B1・B2）と、脱糖の型の保存を扱う段階 C と、性質の前提を処理系の出力に結び付ける段階 E（後述）を定める。値の範囲を型で表す篩型は、初回リリース版に含めず、本章の対象にも含めない。

## 前提

形式化するのは、[コア計算と脱糖](../01-spec/01-12-core-calculus.md)が定めるコア計算である。01-12 は、表層のプログラムの意味を、コア計算への脱糖と抽象機械の実行で定める。同章の「確かめる性質」は、脱糖の型の保存（性質 1）、進行と保存（性質 2）、エフェクトの健全性（性質 3）を挙げる。

段階 2 が証明するのは、Lean の定義について言明した定理だけである。処理系（Rust の VM とランタイム）が 01-12 の規則に従うことは、段階 1 の差分テストと処理系のテスト（[処理系のテスト戦略](07-03-compiler-testing.md)）で確かめる。処理系の脱糖が Lean の脱糖と同じコアの項を作ることは、脱糖の差分テスト（07-03「差分テスト」）で確かめる。

## 仕様

### 証明する性質

【決定】段階 2 では、01-12 の性質 2（進行と保存）と性質 3（エフェクトの健全性）を証明する。理由: コア計算の規則そのものの誤りは、規則どおりに作った参照インタプリタと VM がともに誤るので、段階 1 の差分テストでは見つからないからである。

【決定】01-12 の性質 1（脱糖の型の保存）を、表層の構文の要素を段階に分けて加えながら証明する。対象は、型の情報を付けた表層の構文（elaborated surface syntax。01-12「型の情報を付けた表層の構文と型付け」）とその型付けを満たすプログラムである。性質 1 と性質 3 を組み合わせ、表層のプログラムの `main` のエフェクトが空なら、脱糖したプログラムの実行は IO の事象を伴う遷移をしないことも証明する。理由: 構文を加える改造で、文法が許すのにコア計算へ写す規則がない抜けと、写した結果に型が付かない誤りを、Lean の検査で見つけられるようにするためである。性質 1 を証明していない範囲は、後述の「01-12 との対応」の表に記す（docs/todo の TODO-162）。

【決定】性質 1〜3 の前提を処理系の出力に結び付ける段階 E を加える。段階 E1 は、型検査が使う網羅性と選ばれない選択肢の判定の手順（[型検査器](../02-impl/02-05-typechecker.md)の「本体の後の検査」）を Lean の関数で定義し、手順が網羅と判定すれば値の形で網羅的であること（コア計算の C-Match と表層の型付けが前提にする網羅性）と、選ばれないと判定した選択肢が実行で選ばれないことを証明する。段階 E2 は、表層の型付けを計算する検査の関数を Lean で定義してその健全性を証明し、処理系の型検査が書いた型の情報（型の注釈、型引数、辞書）を、テストの入力ごとにこの関数で検査する。理由: 性質 1 は入力が表層の型付けを満たし照合が値の形で網羅的であることを前提に持ち、処理系の型検査と網羅性の判定がこの前提を満たすことは、性質 1〜3 の証明からは分からないからである。

【決定】次のものは対象にしない。

- 型推論のアルゴリズムと型クラスの解決（[型システム](../01-spec/01-06-type-system.md)）の健全性と完全性。段階 E2（後述）は、型検査が書いた型の情報をテストの入力ごとに検査するだけである。
- 並行処理のタスクと、タスクが引き継いだハンドラ（[並行処理](../01-spec/01-11-concurrency.md)。01-12 も状態の型付けに含めない）。
- 01-12 の「置き換えてよい等式」と「末尾呼び出しの保証」。
- 処理系の実装（VM・バイトコード・ランタイム）の正しさ。

【決定】幅付きの数の追加後の定義についても、性質 1〜3 と表層の検査の健全性を証明している。対象は基本型・定数・演算子・比較・補間・リテラルの脱糖と制約であり、各幅の値域・実行時の溢れ・Float32 の丸めの実装は証明の対象に含めない。理由: 型とエフェクトの規則の保証と、数の実装をテストで確かめる範囲を区別する。

### 進め方

【決定】段階 2 は、次の段に分ける。段階 2 の完了は、初回リリース版の完了条件に含めない。段階 B は、制御の構成を扱う段階 B1 と、型の構成を扱う段階 B2 に分ける。理由: 段階 B の対象は広く、制御の構成と型の構成とでは証明で扱う補題が異なるので、分けて定義と言明のレビューを受けてから証明に入るためである。

段階 A・B1・B2 は、どれも完了している。

- 段階 A は、性質 2・3 と、遷移を計算する関数と遷移の関係の一致を証明した。定理が使う公理は、Lean の標準の `propext` と `Quot.sound` だけである。
- 段階 B1 は、性質 2・3 と、遷移を計算する関数が返す遷移が関係の遷移であること（健全性）を証明した。定理が使う公理は、Lean の標準の `propext`・`Classical.choice`・`Quot.sound` だけである。仮定が矛盾しないことは、仮定を満たす組み込みの関数の例（`formal/` の `Model.lean`）で確かめる。
- 段階 B2 は、段階 B1 の定理を、`Map`・`Set`・`Bytes` と型クラスの辞書（高カインド型を含む）を加えた定義について証明した。定理が使う公理は、段階 B1 と同じである。進行の定理は、段階 B1 と違い、プログラムに型が付くことを前提に持つ。実装の定義がメソッドの本体と上位の型クラスの辞書を持つことを、D-Impl から導くためである。組み込みの関数についての仮定は加えていない。型クラスの実装を持つプログラムが定理の前提を満たすことは、`Model.lean` の例で確かめる。

段階 C1・C2・C4・C5・C6・C7 は完了している。定理の言明は、どの段階でも同じである。初回リリース版の拡張のうち、可変のセルの関数、`Lazy.force`、プロセスの終了の関数、`handle` の外の組み込みの操作、関数の型パラメータの組み込みの制約は、表層では組み込みの関数の呼び出しなので、段階 C1 の範囲に含まれる。

- 性質 1 の定理は、表層のプログラムが範囲の条件と表層の型付けを満たし、組み込みの関数の型が次節の「組み込みの関数の型の変数」の条件を満たすことを前提に、脱糖したプログラムが段階 B の `Program.WellFormed`・`Program.WellTyped`・`Program.EffectsOk` を満たすことを言明する。組み込みの関数の型の条件を前提に置くのは、脱糖が加える変数に型が付くには、その型が継続の型を含まないこと（V-Var）が要り、組み込みの関数が返す値の型についてはこの条件から得るからである。
- 表層の形の性質 3 は、性質 1 の前提に、段階 B の性質 3 の仮定と、表層の `main` が型パラメータ・エフェクト変数・引数を持たずエフェクトが空であることを加え、`main[;]()` からの実行について段階 B の性質 3 の結論を言明する。
- 定理が使う公理は、段階 B1 と同じである。組み込みの関数についての仮定は加えていない。

【決定】段階 E は、段階 B・C の定義と定理を変えずに、段階 E1 の定義と証明を `Benitoite.Release` に、段階 E2 の定義と証明を `Benitoite.Surface` に新しいファイルとして加える。各段階は、段階 A〜C と同じく、定義と定理の言明のレビューを受けてから証明に入る。

| 段 | 対象 | 証明する定理 |
|---|---|---|
| 段階 E1 | 網羅性と選ばれない選択肢の判定の手順（02-05「本体の後の検査」の有用性の手順） | 補題 U（手順が有用でないと答えれば、値の形をしたどの値の並びも、問いに照合するなら行列のどれかの行に照合する）と、その系として、網羅性、必ず照合するパターン、選ばれない選択肢、選ばれない選択肢を実行の規則の照合に結ぶ系 |
| 段階 E2 | 表層の型付け（01-12「型の情報を付けた表層の構文と型付け」）の全体を計算する検査の関数と、プログラム全体の検査 | 検査の関数の健全性（検査に通れば表層の型付けが成り立つこと）と、プログラム全体の検査に通れば利用者の定義と実装に型が付くこと |

段階 E1・E2 は 2026-10-10 に完了した。定理が使う公理は、段階 B1 と同じである。

- 段階 E1 は、02-05 の有用性の手順を Lean の関数で定義した。定義した後は Lean の定義を正とし、02-05 をその写しとする（後述の「01-12 との対応」）。値の形で網羅的であることを、手順の側から示す向き（手順 → 値の形の網羅性）だけを言明する。逆向きは成り立たない（01-05「網羅性の検査」）。定理は、手順に渡す構成子の一覧が、プログラムが宣言したすべての構成子を含むことを前提に持つ。選ばれない選択肢の系は、パターンの照合だけで定めた選択の上で言明し、照合した選択肢の束縛の並べ替えが成功すること（分岐の型付けから得る）を前提に加えた系で、実行の規則の照合（`firstAlt` と分岐の順）でも選ばれないことを示す。反例の文字列と覆っている分岐の選び方は、Lean の関数で計算するが証明しない（差分テストで処理系と比べる）。
- 段階 E2 の検査の関数は、式の最小の型とエフェクトを求め、規則が型を決める位置で包含を確かめる。`if` の結果の型は二つの型の結び、`handle` のエフェクトは不動点の反復で求め、網羅性は段階 E1 の手順で判定する。エフェクトの集合は原子から真偽値への関数なので（前述の「01-12 との対応」の構文の行）、検査の関数は入力の原子の有限の集合を受け取り、その上で包含と型の等しさを判定する。健全性の定理は、式の注釈と環境の型の原子がその集合に入ることを前提に持つ。健全性は、式・ブロック・分岐・節・型を指定した引数の並び・要素の並び・プレースホルダの引数の並び・辞書・辞書の並び・定義・実装の検査の 11 件で言明する。プログラム全体の検査は、利用者の定義と実装を検査し、通れば、信頼する標準ライブラリの宣言で補った宣言表のもとで利用者の定義と実装に型が付き、利用者のエフェクトの名前が組み込みのエフェクトの名前と重ならないこと（`CheckedUnder`）を結論する。標準ライブラリの宣言を補わないプログラムでは、`Program.WellTyped` を結論する。
- 段階 E2 の検査の関数は、表層の型付けについて完全ではない。`lazy` の本体は最小の型で検査し、期待する型を内側へ渡さないので、`Lazy` の中の関数の型のエフェクトを包含で広げてはじめて型が付く入力を拒否する（テストの入力には現れなかった）。入力の原子の集合に `State` がなければ `with` を拒否するが、集合を作るときに `State` を必ず加える。どちらも健全性を損なわない。

### 形式化で仮定するもの

【方針】01-12 は、組み込みの関数の型と値（関数 δ）と IO の応答を、ほかの章に委ねている。形式化では、これらの中身を定義せず、次の性質を定理の仮定として与える。Lean の `axiom` としては置かず、定理の引数（`formal/` の `Builtins.Assumptions`）として明示する。

| 仮定 | 内容 | 01-12 の根拠 |
|---|---|---|
| δ の型の保存 | 型 `(Ā) → B ! ε` の IO を行わない組み込みの関数 `b[T̄; Ē]` に、置き換えた型 `Āθ` の値を渡すと、`δ(b[T̄; Ē], W̄)` は定義されていて、型 `Bθ` の値か `error(r)` を返す（θ = [T̄/ᾱ, Ē/ρ̄]） | 「実行の規則」の E-Prim・E-Err |
| IO の応答の型 | 型 `(Ā) → B ! ε` の IO を行う組み込みの関数 `b[T̄; Ē]` に型 `Āθ` の値を渡したときの応答は、型 `Bθ` の値か `error(r)` である | 「確かめる性質」の性質 2 の「IO の応答は、関数の戻り値の型の値であるとする」 |
| IO の応答の存在 | IO を行う組み込みの関数 `b[T̄; Ē]` に型 `Āθ` の値を渡すと、起こりうる応答が少なくとも一つある | E-IO・E-IOErr で遷移できること（性質 2 の進行） |
| 組み込みの関数のエフェクト | IO を行う組み込みの関数の型のエフェクトは、組み込みのエフェクトの名前（段階 A では `IO`）を含む | 性質 3 が IO の事象の不在を型から導くための前提 |
| 組み込みの関数の型の変数 | 組み込みの関数の型は、宣言した型パラメータとエフェクト変数だけを使う | 01-12 は名前の束縛として暗黙に前提する |
| 制約の保存 | 型パラメータの制約（V-Prim の「T̄ が b の型パラメータの制約を満たす」）を満たす型は、型とエフェクトの置き換えの後も制約を満たす | E-Fun の置き換えの後も V-Prim が成り立つための前提 |

「組み込みの関数のエフェクト」は、01-12 に明文の規則がなく、[エフェクト](../01-spec/01-07-effects.md)が組み込みの関数ごとに与えるエフェクトから読み取れる性質である。「制約の保存」は、段階 A の範囲では制約が演算子の型の集まりと等値の型に限られ、型パラメータが制約を満たさないので成り立つ。

【方針】段階 B1 では、上の表の仮定を初回リリース版の組み込みの関数に広げ、次の仮定を加える。

| 仮定 | 内容 | 01-12 の根拠 |
|---|---|---|

【方針】段階 E2 で処理系の出力を検査した結論（プログラム全体の検査に通った入力が `CheckedUnder` を満たすこと）は、定理の前提のほかに、次のものを信頼する。

- 標準ライブラリの関数と実装の宣言のシグネチャ。標準ライブラリの本体は検査しない。
- 処理系の書き出し（JSON）から表層の構文への変換が、処理系の型検査の出力を写していること。変換は `partial def` で書いた交換用の表現の関数であり、証明の対象にしない。
- 宣言・本体・組み込みのエフェクトに現れる原子が、検査の関数に渡す有限の集合にすべて入ること。集合は入力の JSON の全体から集める。

組み込みの関数の表（名前、型パラメータと制約、引数と戻り値の型、エフェクト）は、処理系の表を書き出して Lean で具体的な組み込みの関数の欄にする。等値と鍵の制約と演算子の型の集まりは、01-06 の規則を写した判定の関数で定め（`Release/BuiltinTable.lean`）、型検査の判定の結果は信頼しない。

【方針】抽象機械の遷移は、関係として定義するとともに、一歩の遷移を計算する関数としても定義し、両者が一致することを証明する。関数の形は、小さなコア計算のプログラムを Lean の中で実行し、01-12 の規則の書き写しの誤りを証明の前に見つけるために使う。段階 B1 の関数は、新しい場所と応答の選び方を固定するので、型が付いた状態について、関数が返す遷移が関係の遷移であること（健全性）だけを証明する。

六つの入口は corpus 10・組み込みと標準ライブラリの型表 3・網羅性 3 を受け付ける。新しい try の処置のない corpus 9 と型表 3、属性のない閉じた旧形式 8/2/2 も互換入力として受け付ける。同じ検査へ渡す corpus と型表の版の組を揃える。新版の必須欄、契約名・ラベル・位置の欠落を自動補完しない。旧版に属性・view・新しい型表示の欄を混ぜた入力は、空や false の指定でも拒否する。網羅性 2 の `RawDecl.typeName` は旧来からある欄として保つ。現在の Rust の通常の書き出しは 10/3/3 であり、その全件と独立入力を比較する。型表の dataDecls と corpus の dataTypes は補充した標準型も含め同じ宣言順から作る。所属は宣言側のモジュールから求め、builtin の印は解決済みの標準ライブラリの BindingId から出す。`coverage_export` は既存の閉じた乱択 1 万件を保持し、同じ型・パターンに拡張指定と作者側／外部側の view を加えた網羅性 3 の独立入力も 1 万件出力する。data・record・入れ子・束縛・ガード・選ばれない選択肢の境界入力を併せ、`check-formal.sh` が `future-corpus.json` を `coverageDiff` で比較する。対象外の理由も照合する。段階 A の `Core` は保持する。

corpus 9 以降の `Input.dataTypes` は、型の識別名ごとの `name`・`typeName`・`isRecord`・`extensible`・`package`・`builtin` を必須とし、属性しか使われない宣言も含む。`package` は解決済みの所属パッケージの識別名である。`builtin` は表示名とは独立した標準型の識別（`"result"`・`"option"`、それ以外は `"ordinary"`）であり、標準の Result・Option に extensible を指定した入力を Lean でも拒否する。型表 3 の `DataEntry` に同じ情報を保持し、型表を使う入口では corpus と全件・順序を含めて一致を確かめる。Rust の書き出し器は同じ宣言の並びから両方を出力する。

corpus 10 は try の処置をタグで区別する。`tryResult`・`tryOption` は裸の return、`tryResultReturn`・`tryOptionReturn` は明示 return であり、後者も同じ表層の規則へ変換する。`tryResultDie` は成功型 `ty`、構成子 `ok`・`err`、表示辞書 `dict`、メソッド参照 `showMethod`、組み込み参照 `exit`、入力 `inner`、任意の説明 `message` を必須とする。`tryOptionDie` は `ty`・`someCon`・`noneCon`・`exit`・`inner`・`message` を必須とし、辞書を持たない。説明なしも `message: null` を明示する。try のタグに属さない欄、複数のタグ、新しいタグを含む旧版を拒否する。理由: 処置や説明を未知の欄として読み捨て、異なる意味の入力を検査済みとすることを防ぐためである。

辞書・メソッド・exit は解決済みの識別名を保ち、局所名の綴りで選び直さない。Rust の組み込みの終了エフェクトは交換内では `Process.Exit` とし、表層・コア・型と操作の表に同じ識別名を使う。`Expr.lambdaEffects` は入力に続いて説明を辿る。独立した corpus 10 の期待コアは入力一回と失敗側の説明・表示・exit の順、自由変数の移動、辞書名と lambda のエフェクトを比較する。`test_try_exchange.py` はこの入力と必須欄・版・参照の破損を六入口で検査し、`check-formal.sh` から実行する。交換の変換自体は証明の対象に含めない。Rust の交換器も corpus 10 を出力する。Die は本番の parser から型・脱糖・交換へ接続し、独立入力の表層と期待コア、および通常のソース入力を六入口で照合する。内部の終了報告の付加情報は交換するコアに含めず、説明・表示の計算、表示辞書の使用、exit の呼び出しと公開の引数を保持する。

die の型保存は、説明・表示の停止、必ず終了操作に達すること、ホストへの報告の一回性を結論しない。脱糖は既存の exit に整数 1 を渡すが、`E_Exit` の応答の終了状態と引数の対応は組み込みの応答に委ねる。これらは型保存の定理と、Rust の実行・報告を確かめる検査とで保証の範囲を分ける。

record の印は構成子のフィールドの有無と照合する。`SurfaceDef.coverageView` は関数・実装メソッドごとの型の識別名（`DataTypeInfo.name`）の一覧であり、表示名 `typeName` は使わない。

各 `SurfaceDef.package` と `ConstantEntry.package` は本体の宣言側の所属である。網羅性 3 は独立入力の各 case、プログラム単位の各 match/binding に `package` と同じ一覧を持つ。Lean は宣言の extensible が真で所属が本体と異なる型を計算し、受け取った view の集合と完全に一致することを検査する。未知・閉じた型・重複・指定漏れ・作者側の余分な指定を拒否する。関数名、実装名とメソッド名の組に重複した view も拒否する。

原ソースから所属・標準型の識別を解決するのは Rust の責務であり、その解決自体は証明しない。`validateDataTypes` は result・option の印をそれぞれ多くとも一つとし、所属を stdlib に限る。構成子を持つ型表と網羅性入力では、Result の Ok(T)・Error(E)、Option の Some(T)・None の表示名・型引数数・引数型・非 record を検査する。型表の構成子の表示名は constructorName で交換し、標準型以外では省略できる。corpus 単独には構成子表がないため、形の検査は型表との照合を行う入口が担う。corpus 9 以降は型引数や定数の本体を含め、入力に現れる data 型がすべて dataTypes にあることを検査する。旧版は形式ごとの既知の欄を辿って閉じた既定を補い、新版の必須欄を補完しない。

Rust のソース照合の判定は、本体の所属と型表の `@extensible` の指定から作る view を使い、反例に将来の形の型の束縛番号を保持する。Exchange は各 `SurfaceDef.coverageView` を `Program.functionViews`・`methodViews` と checker の材料へ渡す。関数を単独で選ぶ検査と全件の検査も同じ指定を使う。corpus 8 の互換入力は閉じた view を使う。

`CoverageDiff` は網羅性 3 の宣言から構成子の表示表と型の表示表を作り、`CoverageWitness.showWithTypes` へ渡す。`CoverageProgramDiff` も型表から将来の形の表示名と record の印を得る。将来の形を、既知の構成子の表示に使う表や実行時の構成子へ追加しない。

### 01-12 との対応

【決定】拡張可能な型の網羅性については、`Release/Coverage.lean` に view と将来の形を扱う判定を定義している。閉じた view と従来の列挙の一致（`shapesWithView_closed`）、既存の形の保存（`mem_shapesWithView`）、任意の view で現在の値の特殊化の証拠を保つこと（`shapesWithView_cover`）、将来の形を変数と `_` だけが覆うこと（`specialize_future_iff`）を証明している。Release の有用性の全再帰と網羅性・束縛・選ばれない選択肢の判定には view を接続している。

任意の view と燃料で成り立つ補題 U は `usefulFuelWithView_none_sound`・`usefulWithView_none_sound`、その系は `checkMatchWithView_exhaustive_sound`・`irrefutableWithView_sound`・`checkMatchWithView_unreachable_sound` である。実行時の非選択へ結ぶ系は `checkMatchWithView_unreachable_runtime`・`checkMatchWithView_unreachable_runtime_of_C_Match` である。`CtorsComplete`・`Inhabits`・`Exhaustive` と既存の健全性定理の言明は変更していない。将来の形に実在の値を割り当てる仮定も加えていない。旧入口は閉じた view を渡す互換ラッパーであり、反例や燃料切れの記録を含む結果全体の一致を示している。01-12 と 02-05 にこの判定を写す。現在の処理系の書き出しは新版の情報を渡し、六入口の旧版の互換入力だけは閉じた既定を補う。ソースの `@extensible` を型表と本体ごとの view に反映する。独立入力は拡張指定と本体ごとの view を使う。理由: 現在の値についての保証と、判定用の形の性質を区別するためである。

【決定】`Release/CoverageExtension.lean` の `ConstructorExtension P P' view` は、既存の構成子の宣言を変えず、`P.cons c = none` である新しい構成子を view が真の型にだけ追加する関係である。構成子以外の表は `Inhabits` が参照しないため制約しない。

`usefulWithView_extension_exhaustive` は、`CtorsComplete P ctors`、`CtorsComplete P' ctors'`、この拡張関係、および `usefulWithView P ctors view [A] (ps.map (fun p => [p])) [wild] = none` から `Exhaustive P' A ps` を導く。入れ子とリストを含み、将来の実行結果の一致は主張しない。`Represents.future` は証明内で追加後の値を将来の形に対応させる関係であり、現在の `Val` と `Inhabits` には新しい場合を足さない。理由: 現在の値についての健全性に加え、許可された構成子追加の後の値も元の分岐が覆うことを保証するためである。

定数は `public const` によってパッケージの外から参照できる。ただし、Rust の定数式の形の検査（`typeck/consts.rs` の `bad_shape`）は `match`・`if`・ラムダ等を E0433 で拒否する。

Lean の `E_Const` は定数式の形の制限を形式化せず、使用側の `D.view` で展開した本体を検査する。したがって任意の交換入力では、宣言側の view で検査する Rust と同じ受理結果を保証しない。現在の Rust が書き出す定数にはソース照合がなく、この違いは拡張可能型の網羅性の結果を変えない。corpus 9 以降の `ConstantEntry.package` は宣言側の所属を保持するが、`E_Const` の指定の切り替えには使わない。`readCorpus` は定数の本体を再帰的に検査し、ソースの match と束縛を含む入力を拒否する。これは交換の前提の検査であり、E_Const の型付け規則は変更しない。

【決定】`Surface.Declarations.view` は既定が閉じた view である。ソースの match/bind の型付けに `ViewExhaustive` を求め、`exhaustive_view`・`matchExhaustive_view`・`bindingExhaustive_view` で checker の成功から証拠を構成する。`ViewExhaustive.exhaustive` によって従来のコアの `Exhaustive` を導き、型保存へ接続する。従来の各 `*_sound` の結論も保つ。合成した record 更新と try の判定は明示的に閉じた view を使い、getter は現在のコアの単一構成子の網羅性を使う。`Declarations.withView_*`、`Input.Sound.withView`、`constructors_withView_sound` は、宣言の射影・原子集合・構成子の完全性が view の選択に依存しないことを示す。`Surface.Program` の `functionViews` と `methodViews` は関数・実装メソッドごとの指定を持ち、`declarationsFor` は view だけを選ぶ。`Program.WellTyped` と全プログラムの checker は同じ本体の指定を使う。型保存の補題を任意の view へ一般化し、`desugar_typed`・`surface_effect_soundness`、`checkProgram_sound`・`checkProgram_empty` と実名一致の結論を保つ。`declarations` は閉じた互換入口である。Exchange は本体ごとの指定を Program と検査の材料へ接続している。`surfaceCheck` の単独の関数の検査と `surfaceCheckAll` の関数・実装メソッドの検査も、その本体の指定を使う。旧版の互換入力は閉じた既定で検査する。理由: ソースの追加条件を現在のコアの保証へ接続し、後続の本体ごとの指定で宣言の契約を保つためである。

【決定】段階 A・B で形式化した規則と、段階 C7 で形式化したコア計算の `match` の規則（次の表で段階 A・B とした節と、`match` の行）は、Lean の定義を正とし、01-12 の規則はその写しとする。写しが Lean の定義と食い違うときは、写しを Lean の定義に合わせる。次の表で形式化の型付けを 01-12 より広くしたと記した箇所は、Lean の定義に 01-12 の条件を加えたものを規則とする。段階 E1 で形式化した網羅性と選ばれない選択肢の判定の手順も、Lean の定義を正とし、02-05「本体の後の検査」の手順の記述はその写しとする（処理系が Lean の定義と違う点は、02-05 に差として記す）。形式化の対象外の節は、01-12 を正とする。理由: 01-12 の規則の誤りや抜けは、Lean の定義を書く過程、証明の作業、定義と言明のレビューで見つかり、01-12 の記述だけを読むレビューでは見つからなかったからである。01-12 の写しは、参照インタプリタと脱糖を実装する人が読むために残す。

【決定】形式化した規則を変えるときは、Lean の定義と 01-12 の写しを同じ変更で直す。取り込む前に、`formal/` の `lake build` が `sorry` なしで通ることを確かめる。

【決定】Lean の定義の名前は、01-12 の規則の名前に対応させる（規則 `E-Op` の遷移は構成子 `E_Op`、規則 `C-Sub` の計算の型付けは構成子 `C_Sub`、規則 `K-Handle` の継続の型付けは構成子 `K_Handle` とする）。01-12 の節と形式化の対応は、次の表で管理する。形式化のために 01-12 と違う形で書いた箇所は、「表現の違い」の欄にその内容と理由を記す。01-12 が規則の名前を付けずに文で書いた規則は、Lean では名前を付けた構成子として書く。`Reference.update` の遷移は `E_RefUpdate`、`lazy` と `escape` の型付けは `C_Lazy`・`C_Escape`、場所の値の型付けは `V_LocRef`・`V_LocLazy`、操作の型付けは `V_Op` である。

### レビューと、見つかった誤りの扱い

【決定】形式化のレビューでは、次のものを確かめる。証明の本体は、Lean の検査を通ればレビューしない。理由: 証明の正しさは Lean の検査が保証するので、人が確かめるべきなのは、定義と言明が意図した規則と性質を表していることだけだからである。

1. Lean の定義が、変更の理由と 01-12 の規則の意図と一致していること。
2. 01-12 の写しが、Lean の定義と一致していること。
3. 定理の言明が、01-12 の性質と一致していること（性質を弱めていないこと）。
4. 定理の仮定が、前述の「形式化で仮定するもの」に挙げたものに限られること。

【決定】証明が通らないときは、原因を、規則の誤り、Lean の定義の書き写しの誤り、形式化の表現の都合のどれかに分けて記録する。規則の誤りと判断したものは、反例となる状態か、証明が行き詰まった場合の組を添えて報告し、前述の決まりに従って Lean の定義と 01-12 の写しを直す。直した規則が処理系の実装に響くときは、処理系も同じ改造で直す。

【方針】定義と定理の言明は、レビューを経て設計者と合意する。段階 A・B では Claude Code が定義と言明を書いた。段階 C からは、定義・言明・証明を Codex の GPT-6.1-Sol が書き、Claude Code（Opus 5.5）がレビューする。証明の本体は、Lean の検査で正しさを確かめるので、担当を問わない。

### 非目標

- 【方針】言語全体の機械的証明は目標としない。
- 【決定】処理系の実装が 01-12 の規則に従うことの証明は目標としない。理由: 処理系は Rust で書き、証明支援系の外にあり、その証明はコンパイラの検証の規模の仕事になるからである。
