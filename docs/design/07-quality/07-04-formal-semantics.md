# 形式意味論と検証

## 目的と範囲

形式検証の段階 2（証明支援系で、選んだ性質を証明する。[ロードマップ](../00-overview/00-03-roadmap.md)の「形式検証の範囲」）の対象、進め方、道具、[コア計算と脱糖](../01-spec/01-12-core-calculus.md)との対応を定める。段階 1（参照インタプリタと VM の差分テストで反例を探す）は[処理系のテスト戦略](07-03-compiler-testing.md)の「差分テスト」で扱う。

本章は、段階 2 の段階 A と段階 B（段階 B1・B2）と、脱糖の型の保存を扱う段階 C と、性質の前提を処理系の出力に結び付ける段階 E（後述）を定める。値の範囲を型で表す篩型は、初回リリース版に含めず、本章の対象にも含めない。

## 前提

形式化するのは、[コア計算と脱糖](../01-spec/01-12-core-calculus.md)が定めるコア計算である。01-12 は、表層のプログラムの意味を、コア計算への脱糖と抽象機械の実行で定める。同章の「確かめる性質」は、脱糖の型の保存（性質 1）、進行と保存（性質 2）、エフェクトの健全性（性質 3）を挙げる。

段階 2 が証明するのは、Lean の定義について言明した定理だけである。処理系（Rust の VM とランタイム）が 01-12 の規則に従うことは、段階 1 の差分テストと処理系のテスト（[処理系のテスト戦略](07-03-compiler-testing.md)）で確かめる。処理系の脱糖が Lean の脱糖と同じコアの項を作ることは、脱糖の差分テスト（07-03「差分テスト」）で確かめる。

## 仕様

### 証明する性質

【決定】段階 2 では、01-12 の性質 2（進行と保存）と性質 3（エフェクトの健全性）を証明する。理由: コア計算の規則そのものの誤りは、規則どおりに作った参照インタプリタと VM がともに誤るので、段階 1 の差分テストでは見つからないからである。

【決定】01-12 の性質 1（脱糖の型の保存）を、表層の構文の要素を段階に分けて加えながら証明する。対象は、型の情報を付けた表層の構文（elaborated surface syntax。01-12「型の情報を付けた表層の構文と型付け」）とその型付けを満たすプログラムである。性質 1 と性質 3 を組み合わせ、表層のプログラムの `main` のエフェクトが空なら、脱糖したプログラムの実行は IO の事象を伴う遷移をしないことも証明する。理由: 構文を加える改造で、文法が許すのにコア計算へ写す規則がない抜けと、写した結果に型が付かない誤りを、Lean の検査で見つけられるようにするためである。性質 1 を証明していない範囲は、後述の「01-12 との対応」の表に記す（docs/todo の TODO-162）。

【決定】性質 1〜3 の前提を処理系の出力に結び付ける段階 E を加える。段階 E1 は、型検査が使う網羅性と選ばれない選択肢の判定の手順（[型検査器](../02-impl/02-05-typechecker.md)の「本体の後の検査」）を Lean の関数で定義し、手順が網羅と判定すれば値の形で網羅的であること（コア計算の C-Match と表層の型付けが前提にする網羅性）と、選ばれないと判定した選択肢が実行で選ばれないことを証明する。段階 E2 は、表層の型付けを計算する検査の関数を Lean で定義してその健全性を証明し、処理系の型検査が書いた型の情報（型の注釈、型引数、辞書）を、テストの入力ごとにこの関数で検査する。理由: 性質 1 は入力が表層の型付けを満たし照合が値の形で網羅的であることを前提に持ち、処理系の型検査と網羅性の判定がこの前提を満たすことは、性質 1〜3 の証明からは分からないからである。

【決定】専用構築器の形式化は、内容の型と論理上限、専用の Step/step の実行、型付き通常引数に対する一操作の全域性と型・範囲の保存、通常の Reference セルの不変、継続の保存・再開での専用セルの保持、解放枠を持たない継続の破棄を含む。C_BuilderLet/C_BuilderOp と局所置換を進行・保存・エフェクトの健全性へ接続する。表層の性質1は専用コアへの脱糖を使う。表層の専用操作は通常引数の効果だけを持ち、宣言は後続の型と効果を保つ。七判断とcheckerから旧refsを除き、通常Referenceと解放のStateは保つ。local_steps_invariant は、任意の有限接頭辞の後も現在の項・枠・保存継続の専用参照が実在するセルを指し、型付きの通常値が自由な専用参照を捕捉しないことを示す。Byte/Bytes の既存の Nat による抽象化には範囲外の値も含まれるため、専用追記では内部エラーにして内容を保持する。これに対応する実装の Byte の範囲外入力は存在せず、言語の診断は追加しない。

【決定】次のものは対象にしない。

- 型推論のアルゴリズムと型クラスの解決（[型システム](../01-spec/01-06-type-system.md)）の健全性と完全性。診断済みの原因と型の部分を追跡する失敗時の推論・診断の回復も含む。段階 E2（後述）は、成功した型検査が書いた型の情報をテストの入力ごとに検査するだけであり、誤りを含む木を型付きの入力として受け付ける規則は加えない。
- 並行処理のタスクと、タスクが引き継いだハンドラ（[並行処理](../01-spec/01-11-concurrency.md)。01-12 も状態の型付けに含めない）。
- 01-12 の「置き換えてよい等式」と「末尾呼び出しの保証」。
- 処理系の実装（VM・バイトコード・ランタイム）の正しさ。

【決定】幅付きの数の追加後の定義についても、性質 1〜3 と表層の検査の健全性を証明している。対象は基本型・定数・演算子・比較・補間・リテラルの脱糖と制約であり、各幅の値域・実行時の溢れ・Float32 の丸めの実装は証明の対象に含めない。理由: 型とエフェクトの規則の保証と、数の実装をテストで確かめる範囲を区別する。

段階 C1・C2・C4・C5・C6・C7 は完了している。定理の言明は、どの段階でも同じである。初回リリース版の拡張のうち、可変のセルの関数、`Lazy.force`、プロセスの終了の関数、`handle` の外の組み込みの操作、関数の型パラメータの組み込みの制約は、表層では組み込みの関数の呼び出しなので、段階 C1 の範囲に含まれる。

- 性質 1 の定理は、表層のプログラムが範囲の条件と表層の型付けを満たし、組み込みの関数の型が次節の「組み込みの関数の型の変数」の条件を満たすことを前提に、脱糖したプログラムが段階 B の `Program.WellFormed`・`Program.WellTyped`・`Program.EffectsOk` を満たすことを言明する。組み込みの関数の型の条件を前提に置くのは、脱糖が加える変数に型が付くには、その型が継続の型を含まないこと（V-Var）が要り、組み込みの関数が返す値の型についてはこの条件から得るからである。

| 段 | 対象 | 証明する定理 |
|---|---|---|

| 段階 E2 | 表層の型付け（01-12「型の情報を付けた表層の構文と型付け」）の全体を計算する検査の関数と、プログラム全体の検査 | 検査の関数の健全性（検査に通れば表層の型付けが成り立つこと）と、プログラム全体の検査に通れば利用者の定義と実装に型が付くこと |

段階 E1・E2 は 2026-10-10 に完了した。定理が使う公理は、段階 B1 と同じである。

- 段階 E1 は、02-05 の有用性の手順を Lean の関数で定義した。定義した後は Lean の定義を正とし、02-05 をその写しとする（後述の「01-12 との対応」）。値の形で網羅的であることを、手順の側から示す向き（手順 → 値の形の網羅性）だけを言明する。逆向きは成り立たない（01-05「網羅性の検査」）。定理は、手順に渡す構成子の一覧が、プログラムが宣言したすべての構成子を含むことを前提に持つ。選ばれない選択肢の系は、パターンの照合だけで定めた選択の上で言明し、照合した選択肢の束縛の並べ替えが成功すること（分岐の型付けから得る）を前提に加えた系で、実行の規則の照合（`firstAlt` と分岐の順）でも選ばれないことを示す。反例の文字列と覆っている分岐の選び方は、Lean の関数で計算するが証明しない（差分テストで処理系と比べる）。
- 段階 E2 の検査の関数は、式の最小の型とエフェクトを求め、規則が型を決める位置で包含を確かめる。`if` の結果の型は二つの型の結び、`handle` のエフェクトは不動点の反復で求め、網羅性は段階 E1 の手順で判定する。エフェクトの集合は原子から真偽値への関数なので（前述の「01-12 との対応」の構文の行）、検査の関数は入力の原子の有限の集合を受け取り、その上で包含と型の等しさを判定する。健全性の定理は、式の注釈と環境の型の原子がその集合に入ることを前提に持つ。健全性は、式・ブロック・分岐・節・型を指定した引数の並び・要素の並び・プレースホルダの引数の並び・辞書・辞書の並び・定義・実装の検査の 11 件で言明する。プログラム全体の検査は、利用者の定義と実装を検査し、通れば、信頼する標準ライブラリの宣言で補った宣言表のもとで利用者の定義と実装に型が付き、利用者のエフェクトの名前が組み込みのエフェクトの名前と重ならないこと（`CheckedUnder`）を結論する。標準ライブラリの宣言を補わないプログラムでは、`Program.WellTyped` を結論する。
- 段階 E2 の検査の関数は、表層の型付けについて完全ではない。`lazy` の本体は最小の型で検査し、期待する型を内側へ渡さないので、`Lazy` の中の関数の型のエフェクトを包含で広げてはじめて型が付く入力を拒否する（テストの入力には現れなかった）。入力の原子の集合に `State` がなければ `with` を拒否するが、集合を作るときに `State` を必ず加える。どちらも健全性を損なわない。

### 形式化で仮定するもの

【方針】01-12 は、組み込みの関数の型と値（関数 δ）と IO の応答を、ほかの章に委ねている。形式化では、これらの中身を定義せず、次の性質を定理の仮定として与える。Lean の `axiom` としては置かず、定理の引数（`formal/` の `Builtins.Assumptions`）として明示する。

| 仮定 | 内容 | 01-12 の根拠 |
|---|---|---|
| δ の型の保存 | 型 `(Ā) → B ! ε` の IO を行わない組み込みの関数 `b[T̄; Ē]` に、置き換えた型 `Āθ` の値を渡すと、`δ(b[T̄; Ē], W̄)` は定義されていて、型 `Bθ` の値か `error(r)` を返す（θ = [T̄/ᾱ, Ē/ρ̄]） | 「実行の規則」の E-Prim・E-Err |
| IO の応答の型 | 型 `(Ā) → B ! ε` の IO を行う組み込みの関数 `b[T̄; Ē]` に型 `Āθ` の値を渡したときの応答は、型 `Bθ` の値か `error(r)` である | 「確かめる性質」の性質 2 の「IO の応答は、関数の戻り値の型の値であるとする」 |
| IO の応答の存在 | IO を行う組み込みの関数 `b[T̄; Ē]` に型 `Āθ` の値を渡すと、起こりうる応答が少なくとも一つある | E-IO・E-IOErr で遷移できること（性質 2 の進行） |
| 組み込みの関数のエフェクト | IO を行う組み込みの関数の型のエフェクトは、組み込みのエフェクトの名前（段階 A では `IO`）を含む | 性質 3 が IO の事象の不在を型から導くための前提 |

【決定】型付けの規則は、ラムダで作る関数型と、V-Sub・C-Subで広げた先の型に整形式を求める（01-12「型付け規則」）。型の変数の範囲、関数型の契約名、内部の潜在効果のCanonicalは、この条件の一部であり、失敗型の内部まで再帰して検査する。型の包含の定義は意味上のエフェクトの包含を保ち、型付けを組み立てる証明では結果の型の整形式も示す。C-Effは型を保って計算の最上位のエフェクトだけを広げる。元の導出から型の整形式を引き継ぎ、計算の最上位のエフェクトにはCanonicalを求めない。節の継続の構築には外側の効果のWFを、K_Letには保存する環境の型のWFを求める。ストアの継続型の効果にはWFとCanonicalを要求し、保存時に正規化する。これは型付けの前提であり、`Builtins.Assumptions` の欄の追加ではない。

- 進行と保存が使う状態の型付けでは、継続の末尾の効果は組み込みの名前だけを含み、Failの列は空である（`BuiltinOnly` の `ε.fails = []`）。未捕捉のFailのない状態に限る条件であり、エフェクトの健全性の前提は変えない。
- プログラムの定義の集まり Σ に型が付くこと（すべての定義が 01-12 の「定義」の型付けを満たすこと。段階 B2 では、すべての実装の定義が D-Impl を満たすことを含む）。
- 各定義の中の型パラメータとエフェクト変数が、その定義が宣言したものに限られること、構成子の引数の型の中の型パラメータが、代数的データ型が宣言したものに限られること。01-12 は名前の束縛として暗黙に前提するが、形式化では変数を番号で表すので、別に言明する。段階 B1 では、定義の型（引数、戻り値、エフェクト）と本体、操作の宣言の型について言明する。本体の範囲は、E-Fun の後の状態が型の変数を含まないことに要る。段階 B2 では、型クラスのメソッドの型と、実装の定義（辞書の引数の型、対象、上位の型クラスの辞書、メソッドの本体）についても言明する。
- 段階 B1 では、エフェクトの宣言が操作の宣言と合っていること、利用者が宣言したエフェクトの名前が組み込みのエフェクトの名前と重ならないこと。

【方針】段階 E2 で処理系の出力を検査した結論（プログラム全体の検査に通った入力が `CheckedUnder` を満たすこと）は、定理の前提のほかに、次のものを信頼する。

- 標準ライブラリの関数と実装の宣言のシグネチャ。標準ライブラリの本体は検査しない。
- 処理系の書き出し（JSON）から表層の構文への変換が、処理系の型検査の出力を写していること。変換は `partial def` で書いた交換用の表現の関数であり、証明の対象にしない。
- 宣言・本体・組み込みのエフェクトに現れる原子が、検査の関数に渡す有限の集合にすべて入ること。集合は入力の JSON の全体から集める。

組み込みの関数の表（名前、型パラメータと制約、引数と戻り値の型、エフェクト）は、処理系の表を書き出して Lean で具体的な組み込みの関数の欄にする。等値と鍵の制約と演算子の型の集まりは、01-06 の規則を写した判定の関数で定め（`Release/BuiltinTable.lean`）、型検査の判定の結果は信頼しない。内部の `%Format.<基本型名>` は `Exchange/Builtins.lean` の `validateFormat` で、`Surface.FormatSpec.headName` と `converterType` に照合する。値の書式化（formatting）を行う未知の頭、契約名や引数・戻り値の型の不一致、型・効果パラメータ、効果、非純粋な種類、操作や型クラスの制約を拒否する。この照合は交換境界の検査であり、δや `Builtins.Assumptions` に数の書式化・表示の幅の算法の仮定を加えない。

### 道具と置き場所

【決定】証明支援系には Lean 4 を使う。形式化は、リポジトリの根の `formal/` に Lake のプロジェクトとして置き、処理系の Cargo のワークスペースには含めない。Lean の版は `lean-toolchain` で固定する。検査は既定の `lake build` で行い、`sorry` がないことを確かめる。`scripts/check.sh` の work/change は、formal に分類する変更で `formal_build` を選ぶ。この単位は既定のビルドだけで、下の全比較とは区別する。水準なしの互換指定 `--only formal` もビルドだけであり、旧 `--full` は形式化を含めない。時期と結果の引用は [処理系のテスト戦略](07-03-compiler-testing.md#実装の規約と静的な検査)に従う。外部のライブラリ（Mathlib など）には依存しない。理由: 対象はコア計算の型付けと抽象機械の性質であり、並行を扱う道具（Iris、TLA+）は要らない。Lean 4 は依存型の証明支援系であると同時に関数型のプログラミング言語でもあり、規則を書き写した定義をそのまま実行して誤りを探せる。

【決定】脱糖の差分テストと、段階 E の処理系の出力の検査（07-03「差分テスト」）の Lean の側は、`formal/` の交換用の表現（`Benitoite.Exchange`）と実行ファイル（脱糖の `desugarDiff`、組み込みの関数の表の `builtinCheck`、網羅性の判定の `coverageDiff`・`coverageProgramDiff`、型検査の出力の `surfaceCheck`・`surfaceCheckAll`）に置く。`lake build`、実行ファイルのビルド、処理系の書き出し、比較を、形式化の検査のスクリプト `scripts/check-formal.sh` にまとめ、`scripts/check.sh` には含めない。形式化した範囲（後述の「01-12 との対応」）に触れる改造は、処理系より先に定義・証明・写しをそろえ、既定の `lake build` が `sorry` なしで通ることと、定義・定理の言明・仮定のレビューを完了する。Rust と Lean の接続を閉じる区切りと最終の関係状態で `check-formal.sh` 全体を確認する。07-03 の条件を満たす成功は引用し、同じ接続の全比較を作業ごとに反復しない。Lean だけを先行した段では、新機能を含む Rust との全比較を成功済みとせず、未接続の契約と検査の担当・時期を計画へ残す。理由: 比較は Lean のツールチェーンを要するので、Lean を持たない環境でも Rust の検査を通せる今の形を保つ。

【決定】交換の読者はcorpus 8・9・10・11・12・13・14、builtins・stdlib・coverage・coverage-programの各2・3・4・5・6を受理する。名前・行の効果の列は集合として読み、型内部も同じ変換を行う。書き戻しの `fromEff` と比較の `canonicalJson` は、Lean側の原子の符号順で整列して重複を除く。比較では両辺の列自体を正規化し、支持の一覧で要素を切り捨てない。基本型の別名以外の型の形と、契約名・引数・節の並びは保持する。理由: Rustの列順へ内部の符号順を要求せず、表現の移行による順序だけの差分を避けながら、効果の要素の違いを検出するためである。

【方針】抽象機械の遷移は、関係として定義するとともに、一歩の遷移を計算する関数としても定義し、両者が一致することを証明する。関数の形は、小さなコア計算のプログラムを Lean の中で実行し、01-12 の規則の書き写しの誤りを証明の前に見つけるために使う。段階 B1 の関数は、新しい場所と応答の選び方を固定するので、型が付いた状態について、関数が返す遷移が関係の遷移であること（健全性）だけを証明する。

【決定】`Surface.Declarations.view` は既定が閉じた view である。ソースの match/bind の型付けに `ViewExhaustive` を求め、`exhaustive_view`・`matchExhaustive_view`・`bindingExhaustive_view` で checker の成功から証拠を構成する。`ViewExhaustive.exhaustive` によって従来のコアの `Exhaustive` を導き、型保存へ接続する。従来の各 `*_sound` の結論も保つ。合成した record 更新と try の判定は明示的に閉じた view を使い、getter は現在のコアの単一構成子の網羅性を使う。`Declarations.withView_*`、`Input.Sound.withView`、`constructors_withView_sound` は、宣言の射影・原子集合・構成子の完全性が view の選択に依存しないことを示す。`Surface.Program` の `functionViews` と `methodViews` は関数・実装メソッドごとの指定を持ち、`declarationsFor` は view だけを選ぶ。`Program.WellTyped` と全プログラムの checker は同じ本体の指定を使う。型保存の補題を任意の view へ一般化し、`desugar_typed`・`surface_effect_soundness`、`checkProgram_sound`・`checkProgram_empty` と実名一致の結論を保つ。`declarations` は閉じた互換入口である。Exchange は本体ごとの指定を Program と検査の材料へ接続している。`surfaceCheck` の単独の関数の検査と `surfaceCheckAll` の関数・実装メソッドの検査も、その本体の指定を使う。旧版の互換入力は閉じた既定で検査する。理由: ソースの追加条件を現在のコアの保証へ接続し、後続の本体ごとの指定で宣言の契約を保つためである。

### レビューと、見つかった誤りの扱い

【決定】形式化のレビューでは、次のものを確かめる。証明の本体は、Lean の検査を通ればレビューしない。理由: 証明の正しさは Lean の検査が保証するので、人が確かめるべきなのは、定義と言明が意図した規則と性質を表していることだけだからである。

1. Lean の定義が、変更の理由と 01-12 の規則の意図と一致していること。
2. 01-12 の写しが、Lean の定義と一致していること。
3. 定理の言明が、01-12 の性質と一致していること（性質を弱めていないこと）。
4. 定理の仮定が、前述の「形式化で仮定するもの」に挙げたものに限られること。

【決定】証明が通らないときは、原因を、規則の誤り、Lean の定義の書き写しの誤り、形式化の表現の都合のどれかに分けて記録する。規則の誤りと判断したものは、反例となる状態か、証明が行き詰まった場合の組を添えて報告し、前述の決まりに従って Lean の定義と 01-12 の写しを直す。直した規則が処理系の実装に響くときは、処理系も同じ改造で直す。

【方針】定義と定理の言明は、レビューを経て設計者と合意する。段階 A・B では Claude Code が定義と言明を書いた。段階 C からは、定義・言明・証明を Codex の GPT-6.1-Sol が書き、Claude Code（Opus 5.5）がレビューする。証明の本体は、Lean の検査で正しさを確かめるので、担当を問わない。

### 非目標
