# 処理系のテスト戦略


## 目的と範囲

テストの設計の原則、ゴールデンテスト、型検査器・VM のテスト、fuzzing、言語仕様の例の検査、実装の規約と静的な検査を定める。ロードマップの完了条件として挙げた受け入れ例と、言語仕様の各項目とを対応づける方針も扱う。

ランダムに生成した型の付くプログラムで反例を探すことは、形式検証の段階 1 として行う（[ロードマップ](../00-overview/00-03-roadmap.md)の「形式検証の範囲」）。後述の「差分テスト」に、その要点だけを書く。初回リリース版の後に実験的として加えた外部の関数は、`testdata/external/` のゴールデンで照合・実行・失敗を、`tests/external_signals.rs` でプロセス全体のシグナルと中断を確かめる。

## 前提

処理系のテストは、Rust の標準のテストの仕組みで書き、`cargo test` で実行する。テストは、処理系を別のプロセスとして起動せず、処理系の Rust の API を直接呼んで検査と実行を行う。ただし、プロセス全体に関わる次の振る舞いは、API からは確かめられないので、CLI を別のプロセスとして起動するテストで確かめる。

- panic hook の設定と、処理系の不具合の報告が標準エラー出力に出る順序（[ランタイム](../02-impl/02-09-runtime.md)の「panic 境界」）。そのテストでは、開発用の環境変数 `BENITOITE_DEV_PANIC` で意図して panic を起こす。
- 中断の要求（`SIGINT`・`SIGTERM`）を受けたときの振る舞い。後述の「中断の要求のテスト（初回リリース版）」で定める。

API を呼ぶテストは、本番と同じ IO の実装で実行する。標準出力と標準エラー出力はメモリに捕らえ、ファイルはテストごとの一時ディレクトリに置いて、そこを作業ディレクトリにする。外部コマンドは実際に起動し、ネットワークの操作も実際に行う（後述の「HTTP のテスト（初回リリース版）」）。テスト用の実装に差し替えられる部品は、スケジューラの次に進めるタスクを選ぶ部品・時計・作業用のスレッドに出す仕事の実行（後述の「順序を与えるスケジューラと仮想の時間（初回リリース版）」）と、ネットワークの失敗の表（後述の「HTTP のテスト（初回リリース版）」）だけである。

## 仕様

### テストの設計の原則

【決定】処理系のテストは、Vladimir Khorikov『Unit Testing Principles, Practices, and Patterns』（邦訳『単体テストの考え方/使い方』）の考え方に沿った次の原則で書く。新しいテストは、プロジェクトのスキル `test-audit`（`.claude/skills/test-audit/`）の作成時の関門を通してから加える。同書の要約は、原典の該当箇所で確かめていない（docs/todo の TODO-160）。

【方針】原則は次のとおりである。

- **テストの価値**: テストは維持の費用がかかる。退行を捕まえる力、振る舞いを変えない作り直しに耐えること、速いフィードバック、読みやすさの四つで価値を判断する。作り直しに耐えることは、ほかの性質と引き換えに手放さない。
- **確かめるもの**: 観察可能な振る舞い（observable behavior）を確かめ、実装の詳細（implementation detail）を確かめない。処理系では、観察可能な振る舞いは、各段の公開の関数と型が返す結果、診断、スクリプトの出力と終了状態である。段の中の非公開の関数や、中間のデータの並びの順序などは確かめない。
- **テストの単位**: テストの単位は、クラスや関数ではなく、振る舞いの単位である。処理系の中の段や型を、テストダブル（test double）で置き換えない。
- **テストダブルを使う範囲**: テストダブルは、処理系の外にあり、処理系が管理しない依存（ファイル・プロセス・標準出力・環境変数など）にだけ使う。処理系では、前述の「前提」に挙げた差し替えの部品（タスクを選ぶ部品・時計・作業用のスレッドに出す仕事の実行・ネットワークの失敗の表）がこれに当たる。ファイル・プロセス・標準出力は置き換えず、一時ディレクトリと出力の捕捉で隔てる。
- **確かめ方の優先順位**: 出力を確かめるテストを最も優先し、次に状態を確かめるテスト、最後に呼び出しのやり取りを確かめるテストとする。処理系の段の多くは外部に作用しない関数なので、出力を確かめるテストで書ける。
- **網羅率**: 網羅率を目標にしない。網羅率は、テストの足りない箇所を探す手がかりとしてだけ使う。
- **テストの形**: 準備・実行・確認（Arrange・Act・Assert）の三つの部分に分けて書く。似た場合は、表の形のテスト（パラメータを並べたテスト）の行として足す。
- **持ち主の境界**: 一つの契約は、最も適した境界の一つのテストで守る。別の層にテストを足すのは、その層に固有の危険があるときに限る。持ち主の境界は、次の三つである。
  1. 処理系の各段（モジュールの読み込み、字句解析、構文解析、名前解決、型検査、脱糖、判定の木への変換、コード生成、VM、VM のスケジューラ、ランタイム、フォーマッタ）の公開の関数と型。ランタイムには永続コレクションを含み、リストを単純なモデルと突き合わせるテストはその公開の関数を境界にする。段の中の非公開の関数は、境界ではない。ただし、ヒープの内部の層の入口（`runtime::heap::core`）は、`unsafe` の不変条件を確かめるテストの境界とする。
  2. CLI のゴールデンテスト。
  3. 言語仕様の例の検査と、参照インタプリタとの差分テスト。
- **退行テスト**: 不具合を直したときに足すテストは、直す前のコードで失敗し、直した後に通ることを確かめてから加える。

【決定】持ち主の境界は、前述の三つとする。持ち主の境界は本章で定め、スキル `test-audit` の「持ち主の境界」の節は本章と同じ内容を書く。二つが食い違ったときは本章を正とし、スキルを直す。

【方針】テストが増えたときは、`test-audit` の監査の手順で、価値の低いテストを定期的に整理する。整理の時期は、改造を終えるときとする。

### テストの種類

【方針】処理系のテストは、次の種類を基本とする。

| 種類 | 内容 |
|---|---|
| 段ごとの単体テスト | 字句解析（改行の判定を含む）、構文解析（AST の形、誤りからの回復）、名前解決、型検査（制約と診断）、脱糖、判定の木への変換、コード生成、VM の命令、ランタイムを、段ごとに Rust のテストで確かめる |
| ゴールデンテスト（golden test） | スクリプトを `check` または `run` し、結果を期待値のファイルと比べる |
| 差分テスト | 同じスクリプトを、参照インタプリタと VM で実行して結果を比べる |
| IO の方式のテスト | 同じスクリプトを、IO の二つの方式で実行して結果を比べる |
| コア IR の検査 | 脱糖の結果に、コア計算の型付け規則で型が付くことを確かめる |
| fuzzing（ファジング） | 任意の入力で、処理系の検査の段が不具合を起こさないことを確かめる |

### テストの種類（初回リリース版）

【方針】初回リリース版では、前述の種類を次のように広げ、種類を二つ加えた。各行の詳細は、右の列に示した節で定める。

| 種類 | 初回リリース版で加えるもの | 詳細 |
|---|---|---|
| 段ごとの単体テスト | モジュールの読み込み（根のディレクトリの下のファイルの探索、循環する import の診断）、パターンの拡張を含む判定の木への変換、フォーマッタ、VM のスケジューラ、ランタイムの永続コレクション。スケジューラは、切り替える順序を指定できるスケジューラで確かめる（[仮想機械](../02-impl/02-08-vm.md)の「タスクの切り替え」）。リストは単純なモデルと突き合わせる | 後述の「ほかの章が求めるテスト（初回リリース版）」 |
| ゴールデンテスト | 複数のモジュールからなるスクリプト、`test`・`fmt`・`fmt-check` の方式、CLI のオプション。すべての `check` と `run` のテストで、フォーマッタの性質を確かめる | 後述の「ゴールデンテストの形式（初回リリース版）」 |
| 差分テスト | 無作為に生成した型の付くプログラム | 後述の「差分テスト」 |
| IO の方式のテスト | タスクを待たせる操作を含むスクリプト | 後述の「IO の方式のテスト」 |
| コア IR の検査 | コア計算の初回リリース版の拡張（[コア計算と脱糖](../01-spec/01-12-core-calculus.md)の「初回リリース版の拡張」）の型付け規則 | 後述の「コア IR の検査」 |
| fuzzing | モジュールの読み込み（複数のファイルからなる入力）とフォーマッタ | 後述の「fuzzing」 |
| 中断の要求のテスト（新たに加える） | CLI を別のプロセスとして起動し、シグナルを送る | 後述の「中断の要求のテスト（初回リリース版）」 |
| HTTP のテスト（新たに加える） | 同じスクリプトの中のループバックの通信 | 後述の「HTTP のテスト（初回リリース版）」 |

### ゴールデンテスト

【決定】ゴールデンテストは、スクリプトのファイルと、期待する結果のファイルを並べて書く。実際の結果で期待値のファイルを書き直す指定を用意する。

【方針】テストは、処理系のソースの `testdata/` の下に、区分ごとのディレクトリ（`lexical`、`syntax`、`names`、`types`、`effects`、`patterns`、`eval`、`io`、`acceptance` など）を作って置く。一つのテストは、同じ名前で拡張子の違う次のファイルからなる。

| ファイル | 内容 | 必須 |
|---|---|---|
| `<名前>.bnt` | スクリプト | 必須 |
| `<名前>.mode` | `check`・`run`・`test`・`fmt`・`fmt-check` のどれか | 必須 |
| `<名前>.exit` | 期待する終了状態（[CLI](../06-tooling/06-01-cli.md)の「終了状態」） | 必須。期待値の書き直しでは省いてよい |
| `<名前>.stdout` | 期待する標準出力 | `run`・`test` のとき |
| `<名前>.stderr` | 期待する、スクリプトが書いた標準エラー出力と `main` の `Result.Error` の文字列 | `run` で書くとき |
| `<名前>.diag.json` | 期待する診断、実行時エラー、資源の不足の報告。JSON の形式（[診断エンジン](../02-impl/02-10-diagnostics.md)）で、一行に一つ | 報告があるとき |
| `<名前>.args` | スクリプトに渡すコマンドライン引数。一行に一つ | 任意 |
| `<名前>.stdin` | スクリプトの標準入力に与えるバイト列。ないときは空の入力を与える | 任意 |
| `<名前>.files/` | テストの一時ディレクトリ（作業ディレクトリ）に写すファイルとディレクトリ | 任意 |
| `<名前>.text.stderr` | 期待する、文章の形式の診断 | 任意。文章の体裁を確かめるテストだけに置く |
| `<名前>.text.stdout` | 期待する、文章の形式の標準出力（`test` の報告） | `test` のとき任意。文章の体裁を確かめるテストだけに置く |

診断は JSON の形式で比べ、文言・コード・位置・補助の位置・注記・修正案がすべて一致することを求める。文章の形式の体裁は、少数のテストの `.text.stderr` で確かめる。

スクリプトの先頭のコメントに、そのテストが確かめる仕様の項目を書く（`// spec: 01-05 網羅性の検査` など）。一つのテストが複数の項目を確かめてよい。

### ゴールデンテストの形式（初回リリース版）

【決定】初回リリース版では、ゴールデンテストの置き方と方式を次のように広げる。前述の表のファイルは、そのまま使う。

| ファイル | 内容 | 必須 |
|---|---|---|
| `<名前>/` | `<名前>.bnt` の代わりに置くディレクトリ。実行を始めるファイル `main.bnt` と、それが取り込むモジュールを入れる。処理系にはディレクトリを与える（[CLI](../06-tooling/06-01-cli.md)の「ディレクトリの指定（初回リリース版）」）。期待値のファイルはディレクトリの隣に置く | `<名前>.bnt` かこのディレクトリのどちらか |
| `<名前>.mode` | `check`・`run` に加えて、`test`・`fmt`・`fmt-check` のどれか | 必須 |
| `<名前>.options` | CLI のオプション（`--deny-warnings` など）。一行に一つ | 任意 |
| `<名前>.formatted` | 期待する整形の結果。スクリプトがディレクトリのときは、同じ構成のディレクトリ `<名前>.formatted/` | `fmt` のとき |

対応する元のスクリプトがない `.formatted` のファイルと、`fmt` 以外の方式のケースに置いた `.formatted` は、実行器が誤りにする。環境変数 `BENITOITE_BLESS=1` を与えた期待値の書き直しでは、それらを削除する。書き直しでは `.exit` がなくてもよく、実際の終了状態を書く。`fmt` の方式で冪等性の確かめが失敗したテストは、期待値を書き直さない。

方式ごとに確かめるものは、次のとおりである。

| 方式 | 確かめるもの |
|---|---|
| `test` | 終了状態、`.stdout` のテストの結果の報告と集計（[利用者プログラムのテスト](../06-tooling/06-04-test-runner.md)の「結果の報告」）、検査の誤りの診断 |
| `fmt` | 整形の結果が `.formatted` と一致することと、実際の整形の結果を再び整形しても変わらないこと（冪等性）。構文の誤りで整形できないファイルは、冪等性の確認から除く。整形は、テストの一時ディレクトリに写したものに対して行い、元のファイルを変えない |
| `fmt-check` | `--check` を指定したときの終了状態と標準エラー出力 |

【決定】`check` と `run` のすべてのゴールデンテストについて、テストの実行器が次の二つを自動で確かめる。

- `fmt` の結果を `check` したときに、元のスクリプトと同じ診断が出る。
- `fmt` を二度適用しても、二度目で変わらない（冪等性）。

【方針】整形で位置が変わるので、同じ診断かどうかは、診断のコードと文言の並びで比べ、位置は比べない。構文の誤りがあるスクリプトは `fmt` が書き換えないので、この二つの確認から除く。

【方針】初回リリース版では、区分のディレクトリに次のものを加える。

| 区分 | 主な内容 |
|---|---|
| `modules` | モジュールと import、公開、根のディレクトリ、ディレクトリを指定した実行 |
| `traits` | 型クラスの宣言と実装、制約、上位の型クラス |
| `handlers` | 利用者が定義するエフェクトとハンドラ、組み込みの操作の差し替え |
| `concurrency` | タスク、`TaskGroup`、取り消し、失敗の伝わり方 |
| `network` | HTTP のサーバとクライアント（後述の「HTTP のテスト（初回リリース版）」） |
| `stdlib` | 標準ライブラリのモジュールの関数 |
| `warnings` | 警告と `--deny-warnings`（後述の「警告のテスト（初回リリース版）」） |
| `test` | `test` の方式 |
| `fmt` | `fmt` と `fmt-check` の方式 |

【方針】`concurrency` と `network` のテストのスクリプトは、出力の順序がタスクを切り替える時機によらないように書く（`Task.all` の結果を受け取ってから書くなど）。タスクを切り替える順序そのものは、段ごとの単体テストで、切り替える順序を指定できるスケジューラを使って確かめる（[仮想機械](../02-impl/02-08-vm.md)の「タスクの切り替え」）。

### 差分テスト

【決定】同じプログラムを参照インタプリタと VM で実行し、結果を突き合わせる差分テストを行う。参照インタプリタは、VM と値の実装を共有しない。共有すると、値の実装の不具合が両方に同じく現れ、差分テストで見つからないからである。ただし、組み込みの関数の本体は、参照インタプリタも VM と同じ実装を呼ぶ（[仮想機械](../02-impl/02-08-vm.md)の「参照インタプリタ」）。したがって、差分テストは評価・値の表現・ヒープ・VM の不具合を見つける手段であり、組み込みの関数の不具合は見つけない。組み込みの関数は、関数ごとの単体テストで確かめる。ただし、応答を組み立てるだけの `Task`・`TaskGroup` の七つの組み込みの関数は、スクリプトの受け入れテストで確かめ、独立した境界条件（`Task.withTimeout` の期限の正規化）だけを単体テストにする。

【方針】差分テストの対象は、`run` のゴールデンテストと、[性能](07-02-performance.md)のベンチマーク（入力を小さくしたもの）のうち、タスクを起動する組み込みの関数を使わないものとする。タスクはコア計算に含まれず、参照インタプリタはタスクを起動する組み込みの関数を実行しない（[中間表現と脱糖](../02-impl/02-06-ir-and-lowering.md)の「参照インタプリタの範囲」）。

差分比較から外した理由ごとの件数と名前、および回収の強制の構成でゴールデンテストから除いたケースの件数と名前は、`CARGO_TARGET_TMPDIR` の下の `golden-summary.txt`（回収の強制の構成では `golden-summary-gc-stress.txt`）で確認できる。最後の実行の集計を残し、ファイルの先頭に、その実行のフィルタと選んだ件数も記録する。

【方針】比べるのは、標準出力と標準エラー出力に書いた内容、終わり方（値で終わったか、どの種類の実行時エラーで止まったか）、実行時エラーの位置である。資源の不足で止まるゴールデンテストのスクリプトは、比べる対象から外す。ベンチマークは正常に終わること（値で終わること）を求め、資源の不足で止まったときも失敗とする。処理系の制限（`L` のコード）で止まることを期待するゴールデンテスト（期待する終了状態が 2 で、期待する診断に `L` のコードを含むもの）も、比べる対象から外す。処理系の制限は抽象機械の規則にないからである。期待していない処理系の制限に当たったときは、差分テストは失敗する。参照インタプリタが処理系の不具合（`Stop::Internal`）で止まったときも、差分テストは失敗する。結果が食い違ったときは、[コア計算と脱糖](../01-spec/01-12-core-calculus.md)の規則に照らして、どちらが誤っているかを調べる。

【方針】長いリストに標準ライブラリの高階関数を使う `list_hof_long` は、差分比較から外す。理由: 参照インタプリタは組み込みの関数を呼ぶたびに引数と結果のリストの全体を変換し、`List.map`・`filter`・`fold` の実装は要素ごとに組み込みの関数（`get`・`append`）を呼ぶので、コードからは、呼び出しごとの変換量はリストの長さに比例し、このケース全体の変換量は長さの二乗に比例すると見積もられる。2026-10-12 の測定では、要る根だけを読み、回収を予算に従わせた実装でも、5 万要素の差分比較が 300 秒の上限に達して終わらなかった。参照インタプリタは簡単さを優先する道具であり、このケースの値は VM 側のゴールデンの期待値で確かめる。

回収の強制の構成を除き、このケースの CLI の二方式の比較とコア IR の検査も行う。

【決定】差分テストの対象に、無作為に生成した型の付くプログラムを加える。これは形式検証の段階 1 であり、参照インタプリタを実行可能な意味論として使う。反例から 01-12 の規則の誤りが分かったときは、規則を直す（[ロードマップ](../00-overview/00-03-roadmap.md)の「形式検証の範囲」、[形式意味論](07-04-formal-semantics.md)）。

【決定】脱糖についての差分テストとして、処理系の脱糖と、性質 1 を証明した Lean の脱糖（[形式意味論](07-04-formal-semantics.md)）が、同じ入力に同じコアの項を作ることを確かめる。入力は、ゴールデンテストの入力と、無作為に生成したプログラム（形式化の範囲に収まる構文だけを使う設定で、固定の種の 1,000 件）である。処理系の側は、型の情報を付けた表層の構文と脱糖したコア IR を JSON に書き出し（統合テスト `tests/desugar_export.rs`）、Lean の実行ファイルが Lean の脱糖の結果と比べる。比べる前に、変数の名前と番号、`match` の行と分岐の表し方、比べない付随情報（型の注釈、由来、ラムダの番号と引数の名前）を揃える。書き出しは、処理系の脱糖が関数の戻り値の型で移す位置（末尾位置の `with` の本体から伝わる位置）の `return` と `match` の型の注釈を、関数の戻り値の型にする（01-12「型の情報を付けた表層の構文と型付け」）。形式化の範囲の外の要素を含む定義は、要素の名前とともに対象外として数える。`scripts/check-formal.sh` がこれをまとめて走らせ、範囲の内の定義が一致しなければ失敗する。理由: 性質 1 は Lean の脱糖についての定理なので、処理系の脱糖が Lean の脱糖と同じであることを確かめないと、処理系について何も言わないからである。

【決定】形式化の段階 E（[形式意味論](07-04-formal-semantics.md)）が Lean の手順と検査の関数について証明した性質を処理系に結び付けるため、次の四つの検査を `scripts/check-formal.sh` に含める。入力は、四つ目の網羅性の手順の差分テストを除き、脱糖の差分テストと同じ入力のうち型検査を通ったもの（ゴールデンテストの 258 入力と無作為な 1,000 プログラム）である。理由: 段階 E の定理は Lean の定義についてのものなので、処理系の判定と出力が Lean の定義と一致することを入力ごとに確かめないと、処理系について何も言わないからである。

- 組み込みの関数の表の検査（Lean の実行ファイル `builtinCheck`）: 入力ごとに処理系の組み込みの関数とデータ型の宣言の表を書き出し、入力が使うすべての組み込みの関数と構成子が表にあって Lean の表現に変換できること、宣言から Lean が求めた型の要約（等値の型・鍵の型か）が処理系の書き出しと一致することを確かめる（約 9 万 3 千項目）。
- 型検査を通ったプログラムの網羅性の確かめ（`coverageProgramDiff`）: 脱糖の書き出しに、照合する式の型と各分岐のガードの有無を加え、すべての `match`（約 1 万 6 千）とパターンを左辺に書いた束縛の文（約 6 千）について、Lean の手順が網羅と判定し、選ばれない選択肢がなく、束縛の左辺が必ず照合すると判定することを確かめる。`try` とレコードの更新が脱糖で作る照合は、型検査の網羅性の判定に対応しないので含めない。
- 型検査の出力の検査（`surfaceCheckAll`）: 利用者の関数の定義と実装（約 4 万 9 千）を、Lean の表層の検査の関数で検査する。末尾位置の `match` で分岐がすべて抜けるとき、型検査は決めなかった型を既定の型のまま注釈に残しうるので、この場合に限り注釈を関数の戻り値の型に置き換えてから検査し、置き換えた数を書き出しの記録と比べる（分岐の値は使われないので、注釈は意味を持たない）。型を Lean の表現に変換できない組み込みの関数（`Task.await`・`TaskGroup.spawn`）を使う定義は、対象外として数える。
- 網羅性の手順の差分テスト（`coverageDiff`）: 統合テスト `tests/coverage_export.rs` が、固定の種で無作為な型（データ型の宣言を含む）と分岐の並びを 10,000 件生成し、境界の入力 20 件（網羅性の誤りを期待するゴールデンテストと同じ形、`Integer` の両端、`Character` のサロゲートの前後、リストの長さの境）を加えて、処理系の網羅性の判定を直接呼んだ結果を書き出す。Lean の実行ファイルが、網羅しているか、反例の文字列、選ばれない選択肢の位置、覆っている分岐、束縛の左辺が必ず照合するかとその反例を比べる。網羅性の誤りを期待する入力は型検査を通らず脱糖の書き出しに現れないので、この差分テストで比べる。書き出しは、処理系の網羅性の判定の仕事量の予算（[型検査器](../02-impl/02-05-typechecker.md)の「本体の後の検査」）に当たった件数と、一回の判定の仕事量の最大を記録し、予算に当たった件数が 0 でなければ失敗する。予算に当たった入力は処理系が結果を出さず、Lean と比べられないからである。

四つの検査のどれかで処理系と Lean の結果が違うとき、Lean の手順の燃料が尽きたとき、書き出しの読み込みに失敗したときは、スクリプトは失敗する。2026-10-11 の時点で、不一致と燃料切れは 0 件である。検査の関数が型検査の誤りを見つけられることは、処理系が 0.0.2 まで受け付けていた型検査の誤り（プレースホルダの引数の中の `return`・`try`・`resume`）の例を検査の関数が拒否することで確かめる（`formal/` の `Surface/CheckCounterexamples.lean`）。

【方針】書き出しのテストには `#[ignore = "formal: ..."]` を付け、`scripts/check-formal.sh` が走らせる（スクリプトの全体で約 9〜10 分。大半は脱糖の書き出し）。水準なしの互換指定 long/full の `--include-ignored` でも走るが、そのときは書き出しが処理系の不具合なく終わることだけを確かめる。新水準の long_only は formal の対象を選ばない。理由: 比べるには Lean のツールチェーンが要るので、Rust の普段の検査から分ける（07-04「道具と置き場所」）。

### IO の方式のテスト

【方針】`run` のゴールデンテストのすべてを、IO の二つの方式（直接呼び出しと、要求と応答。[ランタイム](../02-impl/02-09-runtime.md)）で実行し、どちらの方式でも期待値と一致することを確かめる。

【方針】どちらの方式でも、組み込みの操作の応答に「待つ」があり、待つタスクはスケジューラの待ちの表に移り、操作が完了したら進められるタスクの待ち行列に戻る（[ランタイム](../02-impl/02-09-runtime.md)の「IO 実行器」）。この移り変わりも二つの方式で同じ結果になることを、`concurrency` と `network` の `run` のテストを両方の方式で実行して確かめる。

形式化との差分検査では、全入力を corpus 8・型表 2・網羅性 2 へ書き出し、六つの正式入口（desugarDiff・builtinCheck・coverageDiff・coverageProgramDiff・surfaceCheck・surfaceCheckAll）で比較する。入力識別子・除外理由・対象内の定義数・対象外の理由を manifest と照合する。名前・対応位置・穴・挿入の情報を壊した入力は、意図した契約の誤りとして拒否されることを確認する。

### コア IR の検査

【方針】ゴールデンテストと差分テストで脱糖を通るすべてのスクリプトについて、脱糖の結果をコア IR の検査器（[中間表現と脱糖](../02-impl/02-06-ir-and-lowering.md)）にかけ、型が付くことを確かめる。型が付かなければ、処理系の不具合としてテストを失敗させる。

### 派生した診断が出ないことのテスト

【方針】型検査は、関数の本体の中でも誤りの後に検査を続ける（[型検査器](../02-impl/02-05-typechecker.md)）。これを確かめるために、次のゴールデンテストを置く。

- 一つの関数に、互いに独立した型の誤りが複数あるスクリプト。すべての誤りが報告されることを確かめる。
- 一つの誤りが、後の式の型に波及しうるスクリプト（誤った型の変数を、後で何度も使うなど）。最初の誤りだけが報告されることを確かめる。

期待値のファイルは診断の一覧すべてを持つので、余分な診断が出ればテストは失敗する。

### fuzzing

【方針】cargo-fuzz で、字句解析・構文解析・名前解決・型検査に任意のバイト列と、既存のテストのスクリプトを変形したものを与える。確かめる性質は次のとおりである。

- 処理系の不具合（Rust の panic、処理系の不具合の報告）が起きない。
- すべての診断の span が、ソースの範囲の中にある。
- 誤りがないと判定したスクリプトは、脱糖とコード生成を不具合なしに通る。

【方針】初回リリース版では、次の二つを fuzzing の対象に加える。

- モジュールの読み込み: 複数のファイルからなる入力（ファイルの名前と中身の組の並び）を、根のディレクトリの下に置いたものとして読み込み、型検査まで通す。確かめる性質は、前述の三つと同じである。
- フォーマッタ: 任意の入力に `fmt` を適用する。処理系の不具合が起きないこと、構文の誤りのない入力について冪等性が成り立つこと、整形の前後で `check` の診断が同じであること（前述の「ゴールデンテストの形式（初回リリース版）」と同じ比べ方）を確かめる。

【方針】fuzzing のクレートは、リポジトリの `fuzz/` に置く。cargo-fuzz は libFuzzer を使い、nightly の Rust のコンパイラを必要とする（[Rust Fuzz Book](https://rust-fuzz.github.io/book/cargo-fuzz/setup.html)）。ほかの検査は stable の Rust で行うので、`fuzz/` は Cargo のワークスペースから除き、fuzzing だけ nightly で実行する。

【方針】fuzzing は、後述の完了条件の検査には含めず、別に実行する。短時間の実行は `scripts/fuzz-short.sh` で行う。このスクリプトは、`scripts/fuzz-seed.sh` でゴールデンテストのスクリプトを変形の元の入力として写してから、各対象を短時間ずつ動かす。長時間の実行は、対象ごとに時間を指定して別に行う。

### ほかの章が求めるテスト（初回リリース版）

【決定】try の処置は、構文と整形の境界で処置・説明・改行と再解析を、型検査で戻り値・Show・説明の純粋性・Process.Exit を検査する。die の入力一回、成功側の未評価、説明→Show の順、ハンドラ後の情報の破棄、Direct/Request の結果、子タスクの取消しと解放は、それぞれの公開の実行境界で確認する。純粋な説明と表示の一回性は、結果だけでは区別できないため、独立した期待コアの失敗側の let でも確認する。CLI と test runner は文章・JSON の報告順、一回性、終了状態と次のテストの続行を確認する。これらは型保存の証明と分担し、裸の try の成功・失敗の検査も保つ。

【方針】ほかの章が処理系のテストに委ねた確認を、次のテストで受け持つ。

| 確かめること | 求めた章 | テストの種類 |
|---|---|---|
| 標準ライブラリのソースのすべてのモジュールが、名前解決と型検査を誤りなしに通る。`@builtin` の名前がすべて組み込みの関数の表にあり、宣言の型が Rust の実装と合う | [名前解決とモジュール読込](../02-impl/02-04-resolver.md)の「標準ライブラリのソースの持ち方」 | 段ごとの単体テスト（名前解決と型検査） |
| 組み込みの関数の実装が持つ構成子のタグの定数が、標準ライブラリのソースの型の宣言の順と一致する | [バイトコードとコード生成](../02-impl/02-07-bytecode.md)の「コンパイル済みプログラム」 | 段ごとの単体テスト（コード生成） |
| 組み込みの関数が、[標準ライブラリ](../03-interop/03-06-stdlib.md)などで定めた意味どおりに結果・実行時エラー・応答を返す。参照インタプリタは VM と同じ組み込みの関数の実装を呼ぶので、差分テストではこの確認を受け持てない | [仮想機械](../02-impl/02-08-vm.md)の「参照インタプリタ」 | 段ごとの単体テスト（ランタイムの組み込みの関数）。組み込みの関数ごとに書く。応答を組み立てるだけの `Task`・`TaskGroup` の七つは、スクリプトの受け入れテストで確かめる |
| タスクの切り替え、待ち、取り消しの動き | [仮想機械](../02-impl/02-08-vm.md)の「タスクの切り替え」 | 段ごとの単体テスト（VM のスケジューラ）。切り替える順序を指定できるスケジューラで、切り替えの位置ごとにテストが与えた順序でタスクを選ぶ |
| IO の二つの方式で、タスクの待ちを含めて同じ結果になる | [ランタイム](../02-impl/02-09-runtime.md)の「IO 実行器」 | IO の方式のテスト |
| リストの操作の列が、単純なモデル（Rust の `Vec`）と同じ要素の並びと長さを作る。どの関数も引数のリストを変更しない | [標準ライブラリ](../03-interop/03-06-stdlib.md)の「List の内部の表現」 | 段ごとの単体テスト（ランタイムの永続コレクション） |
| `Map` と `Set` の操作の列が、単純なモデル（Rust の `BTreeMap`・`BTreeSet`）と同じ内容と鍵の順序を作る。木の平衡の条件は、テストではなく `debug_assert!` で確かめる | [標準ライブラリ](../03-interop/03-06-stdlib.md)の「Map と Set（初回リリース版）」 | 段ごとの単体テスト（ランタイムの永続コレクション） |
| 標準ライブラリのソースが正規形である（整形しても変わらない） | [フォーマッタ](../06-tooling/06-03-formatter.md)の「標準ライブラリのソース」 | 段ごとの単体テスト（フォーマッタ）。標準ライブラリのソースとして整形する |
| 整形後の検証（字句の並びとコメントの比較）が、整形の誤りを見つける | [フォーマッタ](../06-tooling/06-03-formatter.md)の「整形後の検証」 | 段ごとの単体テスト（フォーマッタ）。検証の関数に、字句やコメントを変えた出力を与える |

### 警告のテスト（初回リリース版）

【方針】警告は、`check` でも `run` でも報告し、`--deny-warnings` を指定したときは誤りとして扱う（[CLI](../06-tooling/06-01-cli.md)の「オプション」）。これを `warnings` の区分のゴールデンテストで確かめる。同じスクリプトについて、`.options` のないテスト（警告を報告し、`check` は終了状態 0 で終え、`run` は実行する）と、`.options` に `--deny-warnings` を書いたテスト（終了状態 2 で終え、実行しない）を並べる。診断の件数の行が誤りと警告を分けて数えることは、`.text.stderr` で確かめる。

### HTTP のテスト（初回リリース版）

【決定】HTTP のテストの主な方法は、実際のループバックの通信とする。`network` の区分のゴールデンテストでは、一つのスクリプトが `Http.listen(host: "127.0.0.1", port: 0)` で待ち受け、選ばれたポートを `Http.listenerPort` で調べ（[ネットワークのモジュール](../03-interop/03-09-network.md)の「サーバ」）、サーバをタスクで動かして、同じスクリプトからクライアントとして接続する。イベントループ、タスクの切り替え、HTTP の要求の解析と応答の生成を、外部のネットワークに出ずに一緒に確かめる。

【決定】ネットワークの失敗の表は、ループバックでは起こしにくい失敗（名前の解決の失敗、接続の拒否、接続のリセット、時間切れ）を、決まった結果として作るためだけに使う（[ランタイム](../02-impl/02-09-runtime.md)の「組み込みの操作とハンドラ表」）。【方針】失敗は、Rust のテストから、処理系の実行に差し替えの部品として渡すネットワークの失敗の表で与える。ゴールデンテストの形式に、失敗を指定するファイルを加えない。

【方針】`network` の区分のテストのスクリプトは、ループバックのアドレスにだけ接続する。

【決定】HTTPS のクライアントは外部に接続しなければ確かめられないので、証明書の検証を伴う接続は処理系のテストに含めない。【方針】手元で動かす TLS のサーバで TLS の組み立てを確かめることもしない。

### 中断の要求のテスト（初回リリース版）

【決定】中断の要求のテストは、CLI を別のプロセスとして起動するテストで行う。理由: シグナルはプロセス全体に届き、中断の印もプロセスで一つなので、テストのプロセスの中で送ると、ほかのテストを巻き込むからである。テストは次の手順で進める。

1. ビルドした `benitoite` の実行ファイルを、Cargo が統合テストのビルドのときに設定する環境変数 `CARGO_BIN_EXE_<name>` で見つけ（[The Cargo Book: Environment variables Cargo sets for crates](https://doc.rust-lang.org/cargo/reference/environment-variables.html#environment-variables-cargo-sets-for-crates)）、子プロセスとして起動する。
2. スクリプトは、準備ができたことを示す行を標準出力に書いてから待つ（標準入力を読む、または長く待つ）。
3. テストは、その行を読んだ後に `SIGINT` か `SIGTERM` を送る。
4. 終了状態が 130 であること、バッファに残っていた出力が書き出されたこと、`with` のリソースが解放されたこと（書き込みで開いたファイルの内容が書き出されていること）を確かめる。

初回リリース版（`0.0.1`）の中断のテスト（`crates/benitoite/tests/interrupt_process.rs`）は、手順 4 のうち、終了状態と出力だけを確かめている。`with` を使う場合は読み込みのリソースを開いたまま中断するものだけで、書き込みで開いたファイルの内容が書き出されていることは確かめていない。手順は本節のとおりとし、テストを足す（docs/todo の TODO-168）。

【決定】解放の途中で二度目のシグナルを送り、解放を待たずに OS の既定の振る舞いで終えることを確かめる場合を一つ置く。これらのテストは Unix に限る。処理系の対象の環境は、どれも Unix 系である（[配布形態](../05-platform/05-01-distribution.md)の「対応環境（初回リリース版）」）。

【決定】同じ別プロセスのテストで、準備の行の後に待ちを挟まず、並びの崩れた大きなリストの `List.sort` を実行し、その後に呼び出しを通らずに `main` が値で終わる場合も確かめる。準備の行と 2 MiB の詰め物を一回で書き、親は準備の行の後の読み取りを止めて `SIGINT` を送る。`Unit` を返す場合と `Result.Error` を返す場合について、両 IO 方式で終了状態 130、受け付けた出力の転送、`Result.Error` の文字列を報告しないことを確かめる。この手順は、最後の転送の完了より前にシグナルを送ることを保証するが、`List.sort` の途中で届くことは保証しない。

ランタイムの単体テストでは、シグナルを送らず既存の読み口で印を立て、呼び出しのない `main` とテストの関数が値で終わる場合を両 IO 方式で確かめる。

【方針】`test` の実行中の中断（実行中のテストを止め、それまでの結果を報告して終了状態 130 で終える。[スクリプト実行と埋め込み](../02-impl/02-11-embedding.md)の「テストの実行」）も、同じ手順で一つ確かめる。

### 順序を与えるスケジューラと仮想の時間（初回リリース版）

【決定】処理系のテストのために、スケジューラの次に進めるタスクを選ぶ部品、時計とタイマー、作業用のスレッドに出す仕事の実行を、テスト用の実装に差し替えられるようにする。テスト用の実装は、テストが与えた順序でタスクを選び、テストが時間を進めたときにだけタイマーを満了させ、テストが指示した時点で仕事を VM のスレッドで実行して完了を返す。差し替えは処理系のテストだけが行い、利用者が書くテスト（`benitoite test`）と CLI からは使えない。

【決定】切り替えの順序に依存する振る舞いの再現テストは、実時間の待ちやスレッドの実行の順序の偶然に頼らず、この仕組みで順序を与えて書く。

### 実時間の待ちの上限とテストの後片付け

スケジューラの差し替えで順序を与えられない、実際のスレッドとループバックの通信を待つ Rust のテストの決まりである。

【方針】実時間の待ちの上限は停止の検出にだけ使い、内側の待ち（10〜30 秒）より外側の待ち（120 秒）を長くする。回収の強制の構成でだけ上限を延ばすことはしない。理由: 内側の待ちが続いたときに外側が先に時間切れになるのを避け、構成ごとの上限を追わずに停止の原因を調べられるようにするためである。

【方針】時間切れの文言には待っていたものを書き、時間切れのときは中断の印を立てるか、保持しているロックを放してから失敗させる。中断の印で解けない待ちがあるので、時間切れのときは止まったスレッドを待たずに離す。理由: 止まった待ちを報告に残し、残った実行やロック、スレッドの終了待ちによって後の検査が止まるのを避けるためである。

【方針】テストの後片付けを行う `Drop` は panic しない。理由: 巻き戻しの途中で二度目の panic を起こすと、最初の失敗の報告が失われるためである。

【方針】ポートの競合は、競合と分かる結果のときだけ、最初の試行に加えて 3 回までやり直す。理由: 偶然の競合で落ちる頻度を減らしながら、競合以外の失敗を再試行で隠さないためである。

### 実装の規約と静的な検査

処理系は LLM が実装する。実装 LLM は、文章で書いた規約を読んでも守りきれないことがある。そこで、規約はできるだけ、型の定義、コンパイラと lint、テストで守らせ、文章で頼む規約は、それらで決めにくいものに限る。

【方針】処理系設計（`02-impl/`）が定めるデータ構造は、実装の前に、Rust の型の定義と、主要な関数のシグネチャとして示す。型には、構文木・値・命令・誤りの種類の列挙型と、意味の違う整数（ファイル ID、位置、レジスタの番号など）を取り違えないための専用の型を含める。実装 LLM は、示した型とシグネチャを変えずに中身を書く。型やシグネチャを変える必要が生じたときは、実装を進めずに報告し、示した型を改めてから続ける。

【方針】規約のうち道具で確かめられるものは道具で確かめ、確かめた結果を各作業の完了条件にする。

【決定】検査は、作業（work）・段（stage）・改造（change）・リリース（release）の四水準で責任を分ける。水準は検査の時期を表し、単体・統合といった対象の区分とは別である。作業でも本物の部品をつないだ統合テストを行う。具体的な基準・契約・コマンド・構成・対象・担当・見込み時間・結果の保存先を、改造の計画の「検査の割り当て」に集める。[共通依頼文](../../workflow/implementation-request.md)と[実装プランの雛形](../../workflow/change-plan-template.md)を改造のディレクトリへ写して使い、`check.sh` と本節を変えるときは同じ変更で保守する。

理由: 作業中の局所検査、初めてつながる部品の検査、改造全体の回帰、実際の公開候補の受け入れを割り当てれば、同じ全件の反復を減らしながら必要な構成を残せる。

#### 四水準の責任と例外

| 水準 | 担当・確認すること | 実行する検査の集合 | 次の時期に任せるもの |
|---|---|---|---|
| work（作業） | 実装担当。変更した契約と入力の利用側が通ること | 途中は関係するテストのみ。Rustを変える作業の終わりに既定のlib全件・関連統合テスト・clippy・fmtを各一度。関係する生成物・仕様集計・文書例・道具の自己検査。ヒープ（heap）等の例外は下表 | examples のビルド（change で行う）、全件の特殊構成、全ターゲットのテスト、長いテストの全件、公開候補の確認 |
| stage（段） | 取りまとめ担当。初めてつながる部品間の受け渡し | 計画で名指しした接続の検査だけ。最後の作業で同じ接続まで確認済みなら本節の条件で引用 | 作業のlib全件やlintの再実行、段数を理由にした全件検査 |
| change（改造） | 取りまとめ担当。統合後の回帰と構成の選択漏れ | Rustの変更があれば、既定・heap-verifyのworkspace all-targets、既定の文書コメントのテスト（doctest）、heap-verify+gc-stressのlib/tests、二構成のclippy（既定はlib/tests、heap-verifyはworkspace all-targets）、fmt、規約の機械検査、生成Skillと仕様集計、長い対象のみ。道具・依存等の変更には対応する検査も行う | 公開候補の版・配布・実CLIの確認。済んだヒープ・形式化の全比較は関係状態が同じなら引用 |
| release（リリース） | 公開の取りまとめ担当。実際の候補と証拠の一致 | 改造の検査記録との照合、候補の識別、版・同梱物・生成物・移行案内、実CLIの代表例、配布手順。最適化した構成のrelease_stackを一度 | 同じ関係状態の回帰全件の反復。タグや公開の操作は別の指示に従う |

【決定】作業途中は関係するテストだけを直接実行する。作業末は `scripts/check.sh --level work --base <前の作業の取り込みのコミット> [--test <関連ターゲット> ...]` を一度実行し、計画の名指しがあれば `--only` を使う。最初の作業は計画で固定した開始版を基準にする。work が未実装の移行中だけは計画に直接のコマンドを書く。文書・シェル・Pythonだけ、またはLeanだけの作業には関係しないRustの全libを要求しない。Rustの作業末のlib全件・関連統合テスト・clippy・fmtはこの入口で各一度実行し、直接のコマンドを重ねない。

共有の型や入力を変えたら、その入力を読む側まで関連統合テストを広げる。例えばgoldenの追加はcodegen corpus・verifyの読者も、構文の移行はRust文字列中の入力も対象にする。ファイルの分類だけでは決めきれない対象と構成を計画へ補う。

段の検査は、新しい接続、複数作業の相互作用、共有契約の切り替えがあるときに行う。最後の作業で同じ接続まで確認済み、独立した文書変更だけ、または直後の改造全体の検査がその接続を覆う場合は、引用元と省く理由を記す。レビューと指摘修正後の再検査は残す。失敗の修正や関係する追加変更の後は、古くなった検査だけを再実行し、初回の失敗も記録する。期待値・大きさ・ignore・時間制限を実行時間の短縮のために緩めない。

| 例外の条件 | 作業時・接続時に必要な検査 | 改造末の扱い |
|---|---|---|
| 確保・回収・ポインタの生存・根・書き込みの障壁の不変条件を変える | 関係する既定・heap-verify、doc_default（compile_fail を含む文書テスト）、局所のgc-stress、必要な長い対象と `check-heap.sh`。次の作業の前提にする前に成功させる | 最後の関係変更に対する成功を引用できれば繰り返さない |
| VM等で安全点を越える値の保存を変える | 場所がheap/の外でも関係するheap-verifyとgc-stress。GC本体に及ぶならcheck-heapも加える | 全件の特殊構成も一度実行する |
| ヒープのコメント等だけを変える | 実装・入力・構成に影響しない根拠を記録し、計画に明示して絞る | パスだけを理由にMiriを反復しない |
| 形式化の内側の規則・脱糖を変える | 処理系より先に定義・証明・01-12の写し・必要な対応表。既定の `lake build` とsorryの拒否、定義・言明・仮定のレビュー | RustとLeanが接続した区切りと最終の関係状態で `check-formal.sh` 全体。成功済みなら引用 |
| 再帰の形・枠・最適化やビルド設定を変える | 関係するrelease_stackを名指しする | 公開するなら最終候補の構成に対応する成功をそろえる。公開しない改造ならchangeで行う |

#### 入口・基準・終了状態

【決定】`scripts/check.sh` の引数なしはworkである。`--level work|stage|change|release` で水準を指定し、work/changeは変更から自動選択する。stageは計画の `--only` を必須とし、releaseは分類せず、Rustの変更がなくても `release_stack` だけを自動選択する。releaseでは、版・コミット・未コミット状態・ビルド構成・同梱物で実際の候補を識別し、回帰の証拠・生成物・移行案内・実CLIの代表例・配布手順を手動で照合する。受け入れの判定者と保存先を計画に固定し、check.shの終了0だけで完了にしない。タグや公開の操作は別の明示の指示に従う。

`--base` の既定は `origin/san_benito` だが、計画には完全なコミットIDを固定する。workは前の作業の取り込み、stageは段の開始、changeは改造の開始を使う。releaseは改造の開始版を表示するだけで、候補は別に識別する。自動選択は基準から現在の作業ツリーまでのステージ済み・未コミット・未追跡を含める。`git diff --name-only --no-renames <基準> --` と `git ls-files --others --exclude-standard` の重複を除き、削除と改名の旧パスも分類する。無視したファイルを入力に使うなら計画と結果へ明記する。

`--test <統合テスト名>` はwork/stageで繰り返せる。tests_related・heap_local・stress_localへ同じ対象を渡し、一回のCargo呼び出しにまとめる。Rustの自動workで省略したtests_relatedは `cargo test -p benitoite --test '*'` とする。`*` は一つの引数としてCargoへ渡す。libだけに閉じる変更で統合テストを省くなら、理由と明示的な `--only` を計画へ書く。対象の存在は実行時のCargoが判断し、通常テストの件数は解析しない。

| 指定 | 保つ意味・新しい制限 |
|---|---|
| 水準なしの `--only` | 従来の13名（rust・default_lib・long・release_stack・licenses・heap・spec_examples・reference_examples・skill・spec_coverage・skill_eval・python・formal）と実行集合を保つ。policy_selftestも名指しできる。rustは従来のfmt・両lint・heap-verifyのworkspace test・gc-stress・規約・Skill・集計。longはrustを追加してinclude-ignored。default_libは単独でも指定可能。formalはlakeだけ、heapはcheck-heapだけ |
| 水準なしの `--full` | 従来のrust・default_lib・long・release_stack・licenses・spec_examples・spec_coverage・reference_examples・skill・skill_eval・pythonを保つ。heap・formal・check-formal全体や二構成all-targetsは追加しない。releaseの別名にはしない |
| `--level` と `--only` | 当該水準の検査名だけを許す。名指しした検査だけを走らせ、差分の分類も分類による停止も行わない。`--base` は表示に使うだけ。部分選択と表示する。rust・long・python・skill・formal等の旧複合名は拒否 |
| `--test` | work・stageのtests_related・heap_local・stress_localだけに使う。水準なしの旧only/fullとの併用を拒否。存在しないターゲットは実行時にCargoが失敗し、check.shは検査失敗の1を返す。dry-runでは存在を確認しない |
| `--base` | work/changeの自動選択だけがコミットの存在を検査する。旧only/full、新水準のonly、releaseでは表示だけ |
| `--dry-run` | 計画表示だけで、ビルド・テスト・生成をしない。停止なら水準指定の有無によらず3。旧自動選択の「停止予告を出して0」の扱いは引き継がない |
| `--none` | 設計者が不要と判断したときの明示指定。ほかの実行指定と併用しない |

【決定】指定の誤りは終了2とする。`--full` と `--level`、full/only/noneの相互併用、不正な水準、値の欠落、空のonly要素、重複した単一オプション、空・重複・不要なtest、stageのonly欠落、明示したtests_relatedや局所検査の対象欠落を含む。計画の指定を直し、設計者への選択の質問へ置き換えない。

自動分類の分類不能と基準不明は、検査を始めず `== stop:` を示して終了3とし、dry-runも同じとする。該当ファイルまたは基準を示し、設計者に当該水準の `--level … --only`（停止までに選んだ単位を案内し、分類不能のファイルに必要な単位を補う）、互換の `--full`・水準なしの `--only`、`--none`のどれにするかを尋ね、その答えに従う。既に計画で名指しされた検査はその指定で進める。検査失敗と必要な道具の不在は1、選んだ検査の成功は0であり、水準全体の完了とは区別する。

検査前に設計者へ種類を知らせ、計画と同じ基準・指定へ `--dry-run` を付けて確認する。長い検査・heap・全件の特殊構成は見込み時間も知らせる。dry-runはビルド・テスト・生成を行わず、水準・基準・変更数・検査名・完全なコマンド・構成・対象・理由・包含で省く検査・後の担当を表示する。分類しない指定では `changed files not classified` と表示する。見込み時間は検査ごとの固定値で、実行時も同じ選択を使う。

#### 長い対象と方針の自己検査

【方針】大きさそのもので確かめるテスト（百万規模の構造や深い入れ子で、Rustの再帰を使わないこと・空間が一定であることを確かめるテスト）には `#[ignore = "long: ..."]` を付ける。Miriでだけ縮めて走らせるヒープのテストは `#[cfg_attr(not(miri), ignore = "long: ...")]` とする。大きさを縮めて通常のテストへ戻すことや、環境変数で飛ばして成功に見せることはしない。

【決定】長い対象の一覧は作らない。`long_only` は heap-verify と heap-verify+gc-stress の構成ごとに、`cargo test --workspace <構成> --lib --tests -- --ignored --skip export_coverage --skip export_desugar_corpus` を一回実行する。二つの `--skip` は形式化の書き出しを除き、その実行は check-formal に任せる。libtest の並列実行を使い、各ターゲットの要約の成功件数の合計が 0 なら失敗にする。長いテストを足すときはソースに前述の ignore 属性を付けるだけでよく、別の一覧への登録は要らない。

`release_stack` は `cargo test --release -p benitoite --lib -- pipeline::tests::stages_fit_the_measured_stack_ --include-ignored` で選び、成功件数がちょうど 10 であることを求める。テストの属性・名前・期待値は変えない。再帰の形・枠・最適化やビルド設定を変える作業では関係する release_stack を名指しし、公開しない改造なら change へ、公開するなら最終候補の構成へ対応する成功を割り当てる。

`scripts/check/run_ignored.py` はこの一括実行と要約の件数確認だけを担う。入口は `python3 -B scripts/check/run_ignored.py --kind long|release-stack --configuration heap|stress|release` とし、long は heap/stress、release-stack は release の組み合わせだけを許す。cargo metadata とターゲットごとの列挙は呼ばない。要約の欠落、失敗・無視・測定の混入、Cargo の失敗を成功にしない。ビルドの進捗を含む標準エラーと、標準出力を逐次表示する。

水準なしの旧long/fullは従来のinclude-ignoredを保ち、formalの書き出しも実行する。これをcheck-formal全体の成功とは数えない。旧fullはheap・formal・check-formal全体や二構成all-targetsを追加せず、releaseの別名にもならない。

検査方針の自己検査は `scripts/check/test_policy.py` で、本物のcheck.shの入口から選択・実行・停止・失敗伝播と、実行器の選別・件数を確かめる。一時Gitリポジトリに本物のスクリプトを写し、代用はcargo・lake・check-heap.shだけとする。GitとPythonは本物を使う。旧指定の基準は `fixtures/legacy-commands.json` に固定し、後の実装から期待値を作り直さない。三つのシェルの `bash -n` もこの自己検査内で行う。構成ごとの一括実行、形式化の書き出しの除外、成功件数と失敗伝播を確かめる。

#### 結果の保存と引用

【決定】普通の作業は、基準のコミット、走らせたコマンド、終了状態、外側の時間、計画からのずれと申し送りだけを記す。失敗した場合は原因と修正も残す。結果を引用するときに限り、以下の全欄を記録する。自動キャッシュは作らず、担当者が関係する入力の一致を判断する。結果は改造の `<小文字作業ID>/results.md`、段・改造・公開候補の集約は `results.md` に置く。

| 記録する欄 | 必要な内容 |
|---|---|
| 対象の状態 | 基準の完全なコミットID、対象HEAD、差分の有無とファイル一覧。別の状態へ結果を引用するときだけ、未コミット差分と未追跡入力の内容のSHA-256も保存する。HEADだけで同一としない |
| 検査の入力 | 関係するソース、テストと入力・期待値、生成元・生成物、設定、交換器・入力の一覧（manifest）、実行する道具の版またはハッシュ |
| 実行 | 水準、正確なコマンドと構成・ターゲット・フィルタ、ツールチェーン、対象件数・成功/失敗/無視/対象外、終了状態、外側の経過時間、環境の制限 |
| 引用 | 元の結果の場所、以後の変更、影響しない理由、判断者と日付。引用できない場合は再実行する検査 |
| 修正 | 初回の失敗、原因、修正、再実行。環境要因という推定を機能の成功で置き換えない |

引用時はHEADと差分の有無・一覧を残し、別の状態へ引用するときは未コミット差分と未追跡入力のSHA-256も保存する。日本語訳でも実行例の抽出対象なら入力の変更である。標準ソース・Cargo設定・build.rs・文書例・生成物・期待位置・交換器・manifest等の変更が、どの検査を古くするかを確認する。影響を説明できない結果は引用しない。引用して省いた検査は計画に記し、必要な残りを `--only` で指定する。

ビルドキャッシュと検査の証拠を区別し、生ログをtarget/やwork/に置いても、引用に要る状態・コマンド・件数・結論は追跡する文書へ残す。コミットだけが変わり意味上の入力が同じなら回帰の結果を引用できるが、ビルド情報・版・同梱物は実際の公開候補で確認する。

| 検査 | 道具 | 確かめること |
|---|---|---|
| 書式 | `cargo fmt --check` | ソースが rustfmt の書式に従っている。書き換えずに確かめる（[rustfmt](https://github.com/rust-lang/rustfmt)） |
| lint | Clippy。警告を誤りとして扱う | 下の表の lint と、Clippy の既定の lint に違反しない |
| テスト | `cargo test`（ゴールデンテストは、ケースを並べて走らせる） | 本章のテストが通る。テストを加える・変えた作業では、`test-audit` の作成時の関門を通している（前述の「テストの設計の原則」） |
| 言語仕様の例 | 処理系のクレートの `tests/spec_examples.rs`（後述の「言語仕様の例の検査」） | 言語仕様の例が、初回リリース版の文法の全体で読める |
| 仕様の項目の集計 | `tools/spec-coverage/` の自己テストと本番の集計 | ゴールデンテストと仕様の節の対応を集計する道具（後述の「受け入れ例と仕様の項目の対応」）が正しく動き、テストの印が実在する節を指し、完了条件の索引に欠けがない |
| 回収の強制 | `cargo test` を機能 `gc-stress` で実行する（後述の「ヒープとランタイムの確かめ方（初回リリース版）」） | 安全点ごとに必ず回収する設定でも、テストが通る |
| 既定の構成の lint | `cargo clippy -p benitoite --lib --tests --no-default-features --features gc-mark-sweep` | work/change の `lint_default`（互換指定の `rust` も含む）で、`heap-verify` のない側のコードにも lint を掛ける |
| 既定の構成のライブラリのテスト | `lib_default`: `cargo test -p benitoite --lib`。互換の `default_lib`: `cargo test -p benitoite --lib --no-default-features --features gc-mark-sweep` | 既定の構成（機能 `gc-mark-sweep` だけ）でも、ライブラリのテストが通る。Rust の work では `lib_default`、change では `test_default_all` に含める。旧名 `default_lib` は互換の only/full で保持し、長いテストは含めない |
| 仮置きの許可の残り | `scripts/check.sh` の中の検査 | `todo!()` のないファイルに、`AGENTS.md` の `todo!()` の仮置きのための許可が残っていない |
| `unsafe_code` の語の場所 | `scripts/check.sh` の `check_unsafe_allows` | `source_rules`（互換指定では `rust`）で、`unsafe_code` を含むファイルが `src/runtime/heap/core.rs`・`src/runtime/heap/core/` の直下の Rust ファイル・`tests/call_allocations.rs` に限られることを確かめ、外れたファイルと当たった行番号を示す。語を単語として探すので、許す一覧の外ではコメントにもこの語を書かない。子のモジュールへの属性の継承や、`#[path]` で指定した子のファイルの場所は確かめない |
| Skill の生成物 | `cargo run -p benitoite --example gen_skill` | 同梱の Agent Skill の生成物が、構文の章・標準ライブラリのソース・診断の表から作り直したものと一致する |
| 依存のライセンス | cargo-deny の licenses の検査と許可する一覧の比較 | `scripts/release/about.toml` の `accepted` が `deny.toml` の `[licenses]` の `allow` と同じ並びであることと、依存するクレートのライセンスが、許可したライセンスの一覧に入っている（[cargo-deny](https://embarkstudios.github.io/cargo-deny/checks/licenses/index.html)） |

【方針】警告を誤りとして扱う指定は、リポジトリの `.cargo/config.toml` に `[build] warnings = "deny"` と書く（Clippy が勧める `CARGO_BUILD_WARNINGS=deny` と同じ設定を、ファイルに置いたもの。[Clippy の README](https://github.com/rust-lang/rust-clippy/blob/master/README.md)）。コマンドの引数（`cargo clippy -- -D warnings`）に頼らないので、検査のコマンドを変えても警告は誤りのまま残る。

【方針】lint の水準は、コマンドの引数ではなくワークスペースの `Cargo.toml` の `[workspace.lints]` の表に書き、クレートの `Cargo.toml` の `[lints]` で引き継ぐ（[The Cargo Book: lints](https://doc.rust-lang.org/cargo/reference/manifest.html#the-lints-section)）。実装 LLM がコマンドの引数を変えて検査を緩められないようにするためである。次の lint を誤りの水準にする。Clippy の lint の意味は [Clippy の lint の一覧](https://rust-lang.github.io/rust-clippy/stable/index.html)による。

| lint | 検出するもの | 誤りにする理由 |
|---|---|---|
| `unsafe_code`（rustc。`deny` にする） | `unsafe` のブロックなど | 水準を `deny` にし、処理系の本体ではヒープの内部の層（`src/runtime/heap/core.rs` と `src/runtime/heap/core/` の直下の Rust ファイル）でだけ `#[allow(unsafe_code)]` を書く。テストでは、確保を数える確保器（`tests/call_allocations.rs`）にだけ書く。許す箇所は `AGENTS.md` の `#[allow]` を書いてよい箇所の表に載せる。`scripts/check.sh` は `unsafe_code` の語を書いたファイルの場所を確かめる。振り分けのループで範囲の確かめを省くための `unsafe` は許さない（[仮想機械](../02-impl/02-08-vm.md)） |
| `wildcard_enum_match_arm` | 列挙型の `match` での `_` の分岐 | 構文木・値・命令の種類を加えたときに、処理の漏れを型の検査で見つけるため（[実装言語の比較](../08-appendix/08-01-implementation-language-comparison.md)） |
| `unwrap_used`・`expect_used` | `Option`・`Result` の `unwrap`・`expect` | 失敗を panic にせず、`Result` で扱うため |
| `panic`・`todo`・`unimplemented` | `panic!`・`todo!`・`unimplemented!` | panic は処理系の不具合に限る（[ランタイム](../02-impl/02-09-runtime.md)の「panic 境界」）。作りかけの箇所を残さない |
| `dbg_macro` | `dbg!` | デバッグの出力を残さない |
| `indexing_slicing` | panic しうる添字と範囲の指定 | 添字の誤りを panic にせず、`get` などで扱うため |
| `arithmetic_side_effects` | 溢れうる算術の演算 | 溢れを見落とさないため。言語の `Integer` の演算は、溢れを検査して実行時エラーにする（[基本型](../01-spec/01-04-types-basic.md)） |
| `let_underscore_must_use` | `#[must_use]` の値を `let _ =` で捨てること | 失敗しうる呼び出しの結果を、黙って捨てないため（下の `unused_must_use` の抜け道を塞ぐ） |
| `clone_on_ref_ptr` | 参照カウントのポインタへの `.clone()` | 参照カウントの複製を `Rc::clone(&x)` の形で明示し、値の複製と見分けるため |
| `undocumented_unsafe_blocks` | 直前に `// SAFETY:` のコメントのない `unsafe` のブロック | `unsafe` の操作が前提とする不変条件と、それが成り立つ理由を書き残すため |
| `multiple_unsafe_ops_per_block` | `unsafe` の操作を二つ以上含むブロック | 操作ごとに前提を書くため |

`Result` は `#[must_use]` を付けた型であり（[core::result のソース](https://github.com/rust-lang/rust/blob/master/library/core/src/result.rs)）、値を使わずに捨てると rustc の lint `unused_must_use` が警告する（[rustc の lint の一覧](https://doc.rust-lang.org/rustc/lints/listing/warn-by-default.html#unused-must-use)）。警告を誤りとして扱うので、`Result` を捨てたコードはビルドが通らない。

これらの lint を個別に許す指定（`#[allow(...)]`）を書いてよい箇所と、許す lint は、リポジトリの AGENTS.md の「実装の規約」の表に定める。その箇所にも、許す理由をコメントで書く。テストのコードでは、`panic`・`unwrap_used`・`expect_used` などを許してよい。

【方針】リリースのビルドでも、整数の溢れの検査（Cargo のプロファイルの `overflow-checks`）を有効にする。既定では、dev のビルドでは有効、release のビルドでは無効である（[The Cargo Book: profiles](https://doc.rust-lang.org/cargo/reference/profiles.html#overflow-checks)）。有効にすると溢れで panic するので、処理系の内部の溢れは処理系の不具合として報告される。言語の `Integer` の溢れは、この検査に頼らず、演算の関数が検査して実行時エラーにする。

【決定】ワークスペースの `Cargo.toml` の `[profile.dev.package]` で Cranelift・Wasmtime と関連する解析クレートの `opt-level` を 2 にする。理由: debug のビルドでも大きな WASM コンポーネントの検査を短時間で終えるためである。

【方針】道具では確かめにくい規約は、AGENTS.md の「実装の規約」に書き、実装を確かめるときに読む。

- 言語の値は、ランタイムのヒープの公開の層の関数を通して作る（[ランタイム](../02-impl/02-09-runtime.md)の「メモリの管理」）。
- 利用者のプログラムの大きさや深さに比例して、処理系の再帰を深くしない。構文解析器の入れ子の深さの上限（[字句解析器と構文解析器](../02-impl/02-03-frontend.md)の「入れ子の深さ」）の内側で再帰するか、明示の積み重ねを使う（[仮想機械](../02-impl/02-08-vm.md)）。
- 依存するクレートは、設計者が認めたものに限る。外部のコードを写さない。使う場合は出典とライセンスを記録する。

【方針】実装を確かめるときは、道具で確かめにくい点を、決まった観点の一覧で読む。一覧には、`#[allow]` とその理由、`as` による数値の変換、誤りを文字列で表している箇所、示した型から外れた箇所を含める。【決定】処理系は LLM が実装し、オーケストレータの Claude Code がすべての作業を確かめる。実装を担う LLM は、自分の作業のレビューに加わらない。

【方針】命名、コメント、モジュールの分け方など、型と道具とテストで決めにくい書き方の規約は、リポジトリの AGENTS.md の「実装の規約」の節に書く。会話ごとのプロンプトに頼らず、どの LLM とハーネスも同じ規約を読むようにするためである。

### ヒープとランタイムの確かめ方（初回リリース版）

【決定】ヒープのモジュールの `unsafe` と、タスクとリソースの状態の扱いは、次のテストで確かめる。検査時期は前述の四水準と例外の表に従う。ヒープの不変条件の変更は、局所の既定・heap-verify・gc-stress と必要な長い対象・`scripts/check-heap.sh` を次の作業の前提にする前に通す。VM 等で安全点を越える値を変える場合も局所の特殊構成を加える。nightly の Miri と到達可能性の長い比較は `check-heap.sh` に置く。heap/ のパスからは work/change の `heap_checks` を自動で選ぶが、コメントだけの変更は理由を記し、計画に明示して絞れる。最後の関係状態への成功を引用できれば反復しない。GitHub Actions は使わない。

| 確かめること | テストの種類 |
|---|---|
| ヒープのモジュールと小さな VM のプログラムに未定義動作がない | Miri での単体テスト。Miri で動かせないテストは理由を添えて除く。VM のテストは、ヒープの `unsafe` のコードを VM の使い方で通す代表の形を選んだものだけを走らせ、別のスクリプトの全体を 10 分以内に収める |
| 根の数え漏れがない | 回収の強制。安全点ごとに必ず回収する設定で、ゴールデンテストと差分テストを走らせる。長さに比例した生きている構造を持ち、安全点ごとに辿ると二次の時間になって終わらないケース（5 万要素のリストなど）は、実行器の中の一覧に名前で書いて回収の強制のビルドでだけ除き、除いた名前を示す |
| ヒープの形が壊れていない | 機能 `heap-verify` の構成でのヒープの検証器。解放した領域を毒で埋める。値に確保の世代を持たせ、参照を作る前に生存を確かめる。文字列の対象を借りるときに UTF-8 として正しいかを確かめる |
| 既定の構成でもライブラリのテストが通る | 機能 `gc-mark-sweep` だけ（`heap-verify` なし）のライブラリのテスト。work の `lib_default`、change の `test_default_all` で走らせる。水準なしの互換指定では `default_lib` を保つ |
| 回収しない区間の外へ値を持ち出せない。別の実行のヒープの値を混ぜられない。作業用のスレッドへ値を渡せない | work の heap は doc_default でコンパイルの失敗のテストも行う。根の保存領域を通して別のヒープの値を混ぜる誤りは、保存した値のヒープの番号の比較（すべてのビルド）の単体テスト |
| 回収が、到達できる対象を残し、到達できない対象を除く | 確保・参照の書き換え・根の追加と削除を無作為に組み合わせ、独立に計算した到達可能性と比べるテスト |
| タスクの状態とリソースの状態の組み合わせごとの遷移（[ランタイム](../02-impl/02-09-runtime.md)の「リソースの追跡」） | 段ごとの単体テスト（VM のスケジューラとランタイム）。取り消しと完了の順序を入れ替えて、返却と解放が一度ずつ行われることを確かめる |

### 受け入れ例と仕様の項目の対応

【方針】ロードマップの完了条件（[ロードマップ](../00-overview/00-03-roadmap.md)の「完了条件」）のうち処理系のテストで確かめる行に、`testdata/acceptance/` のゴールデンテストを一つ以上対応させる。対応は、完了条件の行ごとに、テストの名前を並べた一覧として、テストのディレクトリに置く。

【方針】仕様の各章（`01-spec/`）の節ごとに、それを確かめるテストがあるかを、テストの先頭のコメント（前述の `// spec:`）から集計できるようにする。確かめるテストのない節は、一覧として出力する。

【方針】ロードマップの完了条件の各行は、次のように確かめる。前述の一覧には、処理系のテストで確かめる行だけを載せる。

| 完了条件の行 | 確かめ方 |
|---|---|
| 同梱の Agent Skill だけを与えた LLM が、JSON ファイルを読んで集計するスクリプトを書く | LLM を動かす試行は処理系のテストに含めず、完了の判定のときに別に行う。試行で得たスクリプトを、`acceptance` の `run` のテストとして残す |
| `Process.run` と `Process.shell` のスクリプト | `acceptance` の `run` のテスト。テストは外部コマンドを実際に起動する |
| 影響の大きい操作をテストのコードのハンドラで差し替えて `test` を実行する | `acceptance` の `test` の方式のテスト |
| コメントを含むスクリプトに `fmt` を適用する | `acceptance` の `fmt` の方式のテストと、前述のフォーマッタの性質の確認 |

【方針】仕様の節の集計の対象には、見出しに「（初回リリース版）」を付けた節も含める。集計の道具は `tools/spec-coverage/` にある。

### 言語仕様の例の検査

【方針】言語仕様（`01-spec/`）に載せたコードの例が、[構文](../01-spec/01-02-syntax.md)の「初回リリース版の文法の全体」で読めるかと、局所の束縛の規則に合うかを、処理系で確かめる。構文の章や例を変えたときに、例が文法と食い違ったまま残ることを防ぐためである。

- 検査は、処理系のクレートの `tests/spec_examples.rs` が、初回リリース版の構文解析器と名前解決で行う。例を取り出し、プログラム・文の並び・型・パターンのいずれかとして読み、局所の束縛の規則の診断を確かめる。利用者のモジュールを import する例は、そのモジュールに空のソースを当てて名前解決まで進める。依存の記述を持つ例では、指定したパスにパッケージの設定と空のモジュールを補い、依存の解決も本物の読み込みを通す。依存の読み込みに失敗した例を、名前解決を通ったものとして数えない。
- 文法で読めなくて正しい例と、局所の束縛の規則に反して正しい例（字句の一覧、誤りの例、本体を省略した宣言など）は、Rust のテストの中の一覧に登録する。テストは、一覧の例が今も読めないか規則に反することを確かめる。
- 付録の[関数型言語の構文の比較](../08-appendix/08-04-fp-syntax-comparison.md)の Benitoite の例（`text` のコードブロック）も、同じテストで確かめる。付録は、その例が初回リリース版の文法で読めることを前提に書いてあるからである。
- 言語仕様の例は、非公式のモジュールも標準に加えた後の名前で import を書く（[名前・スコープ・モジュール](../01-spec/01-03-names-modules.md)の「標準ライブラリの名前空間と prelude（初回リリース版）」）。処理系で例を検査するときは、非公式のモジュールの import の宣言を、取り込みの名前（`import Benitoite.Unofficial.IO.Console`）に置き換えてから検査する。
