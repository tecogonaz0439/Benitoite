# 改造の実装プランの雛形

この文書を改造のディレクトリへ写し、`<...>` を具体化して実装プランにする。検査の正は [07-03「実装の規約と静的な検査」](../design/07-quality/07-03-compiler-testing.md#実装の規約と静的な検査)、形式化の順序の正は [07-04「01-12 との対応」](../design/07-quality/07-04-formal-semantics.md#01-12-との対応)とする。[共通依頼文](implementation-request.md)とともに、`scripts/check.sh`・07-03 と同じ変更で保守する。写した後は相対リンクを直す。docs/todo の番号は文字で参照し、リンクを作らない。

## 前提と依存

- 改造名・目的・範囲: `<今回実装する内容と対象外>`
- 採用する判断: `<decisions.md の節>`
- 改造の開始版: `<完全なコミットID>`
- 作業の基準: `<前の作業の取り込みの完全なID。最初の作業は開始版>`
- 形式化の内外: `<07-04 の判定、必要な定義・証明・写し・対応表>`
- 共通依頼文: `<この改造へ写して具体化した依頼文のパス>`

作業は機能ごとに30〜60分を目安とし、版・訳・CHANGELOG・最後の照合は最後の1作業にまとめる。形式化の内側は、処理系より先に定義・証明・写しを直し、既定の lake build が sorry なしで通ることと定義・言明・仮定のレビューを完了する。形式化の内側の項目が複数あれば、全項目の Lean を最初の段にまとめ、完了してから処理系の段へ進む。先行する Lean だけの段では、Rust との新しい全比較を完了扱いせず、後の接続担当を明記する。

作業の数だけこの節を置く。具体的な検査の正は下の表一箇所に集め、作業の節や依頼文に全コマンド一式を重ねない。

## 検査の割り当て

各行を具体的なコマンド・構成・対象へ置き換える。作業ごとの検査は当該 work 行にだけ置く。実行前に、同じ基準と指定の dry-run を確認する。途中の局所検査は関係するテストだけを直接実行し、末尾の検査を先取りしない。失敗や追加変更の後は古くなった検査だけを再実行する。

| 水準 | 基準・対象の状態 | 契約・入力の読者 | コマンド・構成・対象 | 担当 | 見込み時間 | 結果の保存先 |
|---|---|---|---|---|---|---|
| work `<ID>` | `<直前の取り込みの完全なID>` | `<変更と利用側>` | `scripts/check.sh --level work --base <ID> --test <関連ターゲット>`。`<必要なら --test を繰り返す、または理由付きの --only に具体化>` | `<実装担当>` | `<予算>` | `<小文字作業ID>/results.md` |
| stage `<段>` | `<段の開始版>` | `<新しい接続・相互作用・共有契約の切り替え>` | `scripts/check.sh --level stage --base <ID> --only tests_related --test <接続のターゲット>`。`<他の名指し、または省く理由と引用元>` | `<取りまとめ>` | `<予算>` | `results.md` |
| change | `<改造の開始版と統合後の状態>` | `<全変更と所定構成>` | `scripts/check.sh --level change --base <ID>`。`<引用して除くものがあれば残りの --only を列挙>` | `<取りまとめ>` | `<予算>` | `results.md` |
| release | `<実際の候補の版・コミット・差分・構成・同梱物>` | `<候補と証拠の一致、受け入れ条件>` | `scripts/check.sh --level release --base <改造の開始ID>` と `<実CLI・版・生成物・移行案内・配布の具体的な照合>` | `<受け入れの判定者>` | `<予算>` | `results.md` |

Rust の work は lib 全件・関連統合テスト・clippy・fmt を上の入口に任せ、直接のコマンドを重ねない。`--test` を省いた自動 work は全統合ターゲットとなる。共有入力を変えるなら入力を読む全ターゲットを名指しする。work が未実装の移行中だけは直接のコマンドを書く。文書・シェル・Pythonだけ、Leanだけの作業に Rust の全 lib を追加しない。

全件の特殊構成・長い対象・check-heap・check-formal・release_stack には、次の表で実行または引用の割り当てを必ず置く。対象外なら理由を記す。上のコマンドに含まれるものは重ねず、その行を参照する。

| 必要な検査 | 実行または引用の割り当て | 契約・対象・構成・コマンドまたは引用元 | 担当・時期・保存先 |
|---|---|---|---|
| 既定・heap の all-targets、doc、stress 全件、二構成 lint | `<change 行>` | `<change の選択、引用で除く場合の根拠>` | `<担当・時期・results.md>` |
| long_only | `<change 行、局所の必要な長い対象も記す>` | `<heap/stress。formal の書き出しを成功に含めない>` | `<担当・時期・results.md>` |
| 局所の heap-verify・gc-stress と check-heap.sh | `<必要な work 行、または理由付きの対象外>` | `<不変条件・安全点を越える値。統合なら heap_local/stress_local と --test、libなら直接の Cargo コマンド。heap_checks と成功の引用元>` | `<次の作業の前提にする前、担当・保存先>` |
| Lean の既定ビルド・レビュー | `<形式化を先行する work 行、または理由付きの対象外>` | `<formal_build または lake build、sorry の拒否、定義・言明・仮定のレビュー>` | `<処理系より先、担当・保存先>` |
| check-formal.sh 全体 | `<接続を閉じる区切りと最終の関係状態、または理由付きの対象外>` | `scripts/check-formal.sh`。`<六入口・独立入力・交換と manifest、最後の成功の引用元>` | `<担当・時期・results.md>` |
| 性能の比較の段 | `<性能に関わる改造は short、約束した目標は targets、要所だけ full。性能と関係しなければ short は任意>` | `python3 tools/bench/compare/run.py --tier <選んだ段> --state before=<開始版> --state after=<候補>`。`<targets の JSON と状態、full の --confirm-full、quick と見込み、本測定前の了承を具体化>` | `<担当・改造末・見込み時間・tools/bench/results/ の記録と results.md>` |
| release_stack | `<release 行。公開しない改造なら必要な change 行>` | `<再帰の形・枠・最適化・ビルド設定を変えるときは関係作業にも名指し。最終候補の構成へ対応する結果>` | `<担当・時期・results.md>` |

段の検査を省く場合は理由と引用元を記す。終了0は選んだ検査の成功であり、release の受け入れは候補と証拠の手動照合を終えて判定する。水準なしの旧 only/full は互換指定であり、change/release の代わりにしない。指定の誤り2は計画を直し、分類不能・基準不明3では該当箇所を示して設計者の当該水準の `--level … --only`（停止までに選んだ単位を案内し、分類不能のファイルに必要な単位を補う）、互換の `--full`・水準なしの `--only`、`--none` の判断に従う。

## 結果とレビュー修正の管理

| 結果ID | 結果記録の参照先 | 後の変更 | 引用可否と理由 | 再実行の担当 |
|---|---|---|---|---|
| `<結果>` | `<小文字作業ID>/results.md` | `<差分>` | `<入力・生成物・道具・構成が一致する根拠、判断者と日付>` | `<担当>` |

普通の作業の results.md は、基準のコミット、走らせたコマンド、終了状態、外側の時間、計画からのずれと申し送りだけを記す。失敗した場合は原因と修正も残す。結果を引用するときに限り、07-03「結果の保存と引用」の全欄を記す。基準と HEAD の完全な ID、差分の有無と一覧、コマンド・構成・入力・ツールチェーン・件数・終了状態・時間・環境の制限、元の記録、以後の変更、関係状態が一致する理由、判断者と日付を残し、別の状態への引用には未コミット差分と未追跡入力の SHA-256 も保存する。未実施は担当と時期を明記し、この作業が受け持つ失敗を後へ送って完了にしない。
