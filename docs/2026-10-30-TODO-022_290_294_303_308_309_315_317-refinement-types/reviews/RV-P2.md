## 中

- **M1. 操作数（operations）は全仕事量の下界であり、「ステップ数」の定義にそのまま使えない**（読めば確定）: `rust/src/search.rs` の各節点の全走査（257行）、`todo.remove(0)`/`insert(0)`、Or と整数分枝での `todo.clone()`・`facts.clone()`（288・290・410行）、`stages.push(…clone…)`（324行）、`rows.iter().find`、`wrap`、`normalize`、最後の `check` に tick がない。走査とコピーは事実の数に比例し、数えない仕事は多項式の因子で大きくなりうる。修正案: 本番のステップは、探索のすべての反復（走査・複製・正規化を含む）で数える抽象的な単位とし、作業量を定数倍で抑えることを定義の要件とする。検査器の費用は証明書の大きさで抑える（M2）。定義は版に結び付け、診断と JSON に版と上限を出す。
- **M2. Rust の検査器は事前検査の上限の下でも二次の費用になりうる**（読めば確定、時間は未測定）: `rust/src/checker.rs` の `check_at`（167・170・184・187行）が Cases と Split のたびに `todo` と `facts` の全体を複製する。修正案: 本番の検査器は事実を一本の積み重ね（Vec）に置き、枝を出るときに長さを戻す形にして、費用を証明書の大きさ×係数の数に線形にする。
- **M3. 証明書の文法が調べ 4.2 の案と違うのに、どちらを採るかを書いていない**: 試作は残りの論理項の列の先頭を `consume`/`cases` で読む形で、検査器が否定標準形を自分で計算し直すので `normalizationTrace` が要らないことを示した（良い結果）。一方、EqProof・`substitute`・`builtinLemma` は試作にない。修正案: 「試作の列の形を採り、trace を除く。EqProof・substitute・builtinLemma・sort の検査を足す」と明記し、足す規則の健全性の証明が見込みのどの行に入るかを書く。
- **M4. 関係のない選言のために探索の枝と証明書が指数的に増える**: 証明書に使わない項を捨てる規則がなく、探索も先行する線形の事実だけで矛盾が出るかを確かめずに Or を展開する。`≠` は正規化で Or になるので、`x != 0` のような条件が10個ほどで 2^10 になり枝の上限1,024を使い切る。修正案: 健全性が自明な「捨てる」規則を足し、探索は Or を展開する前にそこまでの連言で線形の矛盾を試す。代表例にこの形がないので、上限の材料にも欠けている。
- **M5. 見込みの 112→70 時間の置き換えの根拠が「中心の規則が閉じた」ことに偏っている**: 検査器の行（Lean 2〜4時間）に EqProof・substitute・builtinLemma・sort の拒否の健全性が明示されていない。正規化の行（Lean 2〜6時間）に表層の `<`・`-`・定数倍の正規化と、各幅の整数と数学上の整数の対応（溢れたら Stop になることとの対応）が入っていない。試作が数分で閉じたのは数学上の Int と密な係数の列だけを扱ったからである。修正案: 検査器の行の Lean を 4〜10 程度、正規化の行を「各幅の整数と数学上の整数の対応」を名指しして 4〜10 程度、中心を約80時間とするか、P3 で接続の面を確かめるまで旧い中心112を残す。
- **M6. measure の純化の言明は本番の健全性の言明にそのままでは使えない**: `source_check_sound`（P2.lean:528）に、(1) 長さの非負性などの組み込みの補題を事実として検査器へ渡す口がない、(2) 鍵から番号への写しが構成で固定されており、本番では「同じ鍵には同じ番号」と鍵の値の不変を仮定として外に出す必要がある、(3) 言語の算術（各幅、溢れたら Stop）との対応がない、(4) 欄の連鎖と別名を扱っていない。修正案: 計画の Lean の骨格に、これらの仮定を持つ言明を先に置く。

- L2. 分枝限定の子は、それまでに導いた行もすべて入力として Fourier–Motzkin をやり直す（search.rs:412・418）。branch_triangle の生成数22は実装の分で増えている。
- L3. 単位の扱いが揃っていない（digits は数を作るたび、生成数と証明書の大きさは append のたび、`go` の `inspect` は入力の行も数える）。表に「入力の制約は生成数に含めないが、操作数には含める」と一行加える。
- L4. 反例の扱いは健全。ただし、純化した変数のモデル（負の長さなど）を Rust の `solve` は `Model` として返す。本番では実現できるかを確かめるまで「反例」と出さない分類が要る。計画の受け入れの基準へ写す。
- L5. 最大常駐量を補助の値で区別して記録したのは適切。

## 既定値（一つの条件あたり 100,000 ステップ）の材料について

- 測った操作数は、1桁の係数・3〜6本の制約の小さな例のもので、564 は「実用に近い」と言える根拠にならない。本番の文脈には、経路の条件・各幅の上下限（Int64 の 2^63 は19桁で試作の digits 18 を超える）・measure ごとの非負性・`≠` の選言が積み重なり、最大の数は大きく変わりうる（実行しないと分からない）。
- 100,000 で通るのは16本・二段の例（85,628）までで、32本の例は上限をわずかに超えて止まる。余裕は約14%で、M1 の定義を直せば数は変わる。
- 重みについて: 固定幅の算術に桁数の上限を置くなら一回の算術の費用は定数で、桁数で重みを付ける意味は薄い（多倍長なら limb の数で重みを付ける）。証明書の大きさは append ごとに既に操作数へ入っており、重みとして足すと二重に数える。推すのは、ステップ数を全仕事量の上限とし、桁数・証明書の大きさ・枝の数・生成数を別の上限として残す形。単一の重み付きの数にするなら測り直しが要る。
- 結論: 「100,000（仮）」は桁の目安として計画に置いてよい。ただし、M1 の定義で本番の探索を作った後に測り直すこと、測り直しには文脈の事実を含む本番に近い入力（M4 の選言、各幅の上下限）を使うこと、検査器の費用は別に抑えること（M2）を計画に明記する。
