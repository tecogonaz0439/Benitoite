## 重大

- **重1. 相対形の意味が既存の File の文字列 API と食い違う**: 推す案は、動的な対象の相対パス（CLI 引数の `data/in.txt` など）まで `{project}` から解決する。現行仕様では IO の相対パスは実行ごとの基準のディレクトリ（CLI の run では起動時の cwd、テストでは実行ごとに与える基準のディレクトリ）から辿る（01-07:213・215、03-07:97、用語集 321「基準のディレクトリ」）。同じ相対の文字列が `File.readText("data/x")` では cwd から、`checkPathInAt(..., path: "data/x")` では project から解決され、スクリプトの外の cwd から起動すると、検査は成功するのに意図と別のファイルを読み書きしうる。docs/todo の TODO-324 の方針（ADR 0072「相対パスは作業ディレクトリから辿る」）とも逆になる。修正案: 「パターンの相対形の基準」と「動的な対象の相対形の基準」を別の行の問いにし、対象の相対形は拒否するか既存の基準のディレクトリ（`{cwd}`）で解くかを選択肢として示す。TODO-324・ADR 0072 との関係を明記し、制限の表に「対象の相対形を拒否する」案を加える。
- **重2. `{cwd}`・`~`・`--project-root` で同じ契約でも実際の対象が変わる危険を、表示と保証の範囲で扱いきれていない**: check の時点で未確定のものを work/tmp/secrets に限っているが、cwd と home も実行の時点では check の時点と違いうる（ハーネスの LLM が check し、別の場所で run する流れ）。`--project-root=/` なら `{project}/**` は事実上 `/**` になる。07-01 は検査報告と後の実行の間のソースの同一性を保証せず、`--allow-effects` は名前だけを照合するので、契約も検査報告も同じまま操作の対象が変わることをどの機構も止めない。原則2に対する新しい穴であり、00-01 の「範囲付きのエフェクトは、操作の対象の静的な上限」という文言も σ に依存する上限へ意味が変わる。修正案: check の報告で cwd・home・project を「check の時点の値」として出し、run の準備のときの値と分ける。07-01 と 00-01 の改める文言を案として示し、絶対形式の保証は変わらず新しい形は σ を変数とする上限であると書く。`--project-root` の上書きを許すか（既定の根と違うときに警告するかを含む）を独立の行にする。
- **重3. TODO-250 の「1回の改造に入れる形式化の重い項目は一つだけ」との関係を書いていない**: TODO-303 は Scope.Domain・主定理の前提・delta_typed・HasTypeV の意味を変え、外部型の交換は Release・Surface の全型構成子に及ぶ。どちらも形式化の重い変更に当たる。修正案: 設計者が含めると決めたことが TODO-250 の方針の例外であることと理由を明記し、行き詰まったときの切り分け方を Q08 の受け入れ条件に加える。

## 中

- **中1. `{cwd}` の定義が既存の「基準のディレクトリ」と揃っていない**: テストの実行器と埋め込みでは実行ごとの基準のディレクトリが作業ディレクトリの代わりになる（01-07:215。`Process.workingDirectory` もこれを返す）。S03 は基準の種類全体を「基準」と呼ぶが、用語集の「基準のディレクトリ（base directory）」は cwd 相当を指す。「プロジェクト根」は用語集になく、既存の「パッケージの根」（用語集 188行）や入口の根との関係も書いていない。修正案: `{cwd}` を「その実行の基準のディレクトリ」と定義し、基準の種類の総称には別の語を出典付きの候補で示す。プロジェクトの根とパッケージの根の関係と、用語集の行を追加する案を書く。
- **中2. 外部型の「全面的な交換」の完了条件が狭く、費用を少なく見ている可能性がある**: 完了条件は `externalType` による除外0件だけを挙げるが、07-04:759 には外部の宣言を持つプログラム全体を `excluded: ["external function"]` として脱糖の差分・surfaceCheckAll・網羅性の比較から除く別の除外があり、「外部の関数を組み込みの仮定の欄として与える実装は持たない」とある。Lean の表層検査で外部関数の呼び出しを型付けするなら `borrow`・`own`・`State` を表す必要があり、12〜32時間に収まる根拠がない。修正案: 完了条件に `external function` の除外0件を加えるか対象外と明記し、費用の内訳を見直す。
- **中3. 費用の尺度が明示されていない**: 算術は一貫している（66〜157・中心111.5、418〜953・中心685.5）。ただし本体は「棚卸しの上端×0.15〜0.35＋余裕」の較正後の尺度で、S03 の数字は係数を掛けていない「変更面の棚卸しから置いた見込み」である。S02 の 10.4 の慣行（対案は直接の差額）には合うが、二つの尺度を足しているのかが読み取れない。修正案: 52〜120時間などが能動時間の直接の見込み（較正後の尺度。S02 の 10.4 と同じ扱い）であることを Q09 に一文で書く。
- **中4. TODO-290 の return を「本体の内数」としたが範囲が広がっている**: §3.1 は値の形と所属の近似もこの境界で扱うとするが、8〜20時間を S02 のどの棚卸しの行が吸収するかを示していない。修正案: 吸収する行を名指しし、広げた分は本体の余裕を使うと明記する。
- **中5. `{secrets}` をサーバモードより前に入れる問題**: 方針ファイル（TODO-109）・秘密の扱い（TODO-323）・サーバ（TODO-324）が未設計のまま、ソースでの意味、仮 CLI の `--scope-base=secrets=`、空の一覧と未指定の区別を固めることになる。TODO-109 の既定の一覧は `~` で始まるが、仮 CLI は絶対形式だけを受ける。スタンドアロンで使う実益も示されていない。修正案: 「`{secrets}` を今回ソースに入れるか、方針の実装まで予約語として拒否するか」を独立の問いにし費用の差を添える。仮 CLI の `--scope-base` で `~` を許すかも明記する。
- **中6. 制限の表の漏れ**: (a) 動的な対象の相対形の基準、(b) `--project-root` の上書きを許すか、(c) `--scope-base=secrets=` の空の指定と非空の指定を混ぜられない、(d) 成功値の射影が相対の入力に対して絶対パスを返すこと（03-06 の「pathInValue は同じパスを変更せず返す」を変える互換の決定）。
