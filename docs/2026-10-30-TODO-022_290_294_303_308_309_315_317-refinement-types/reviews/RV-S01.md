## 重大

**S1. 入れ子の関数への包含が、現行のエフェクトの包含の規則を変えるのに書かれていない**

- 場所: 調べ 6.1 の二つ目の段落の末尾（「入れ子の関数でも同じ有向の規則を使い」）、8.3 の `fn_left` の行、問いの Q05 と L07。
- 根拠（読めば確定）: `Release/Typing.lean:332` の `Ty.Le` は最も外側の関数の潜在効果の被覆だけを認め、docstring に「入れ子の関数型・リストの要素・値型の添字へは広げない」とある。用語集 00-04:248 はエフェクトの包含を「型の最も外側の関数の型にだけ働く」と定める。01-06:141 は「関数型の等号、引数型・戻り値型…の照合に被覆を使わず」と定める。Rust の `flow_inner` も入れ子を `equal` で比べる。
- 問題: 引数を反変、結果を共変にして入れ子へも及ぼすと、篩だけでなくエフェクトの被覆も入れ子の位置で働く。受理が広がり、`CoverCompat`（`Ty.LeOld`）、`EffectCover`、Surface の `tyLe` と `tyJoin`、診断にも影響する。この変更が選択肢として示されていない。
- 修正案: (1) 篩の包含もエフェクトの被覆も現行どおり最も外側に限る、(2) 篩だけ入れ子にする、(3) 両方を入れ子にする、の三案を独立した問いにし、Lean・Rust の費用と互換性への影響を書く。6.1 の表の「ラムダ引数の注釈は構造の等号」との不整合（名前付きの関数 `f(x: Integer)` は Port を求める位置に反変で通るのに、`lambda(x: Integer)` は等号で断られる）も書く。

**S2. 主な定理の前提の中身が変わることへの設計者の承認が、問いにない**

- 場所: 調べ 8.4（表と「前提の個数が同じでも…」の段落）、問いの「決定済みの前提」。
- 根拠: 07-04:36〜50 は、V-Checked、V-CheckedRequest、範囲の列などを加えたとき、言明の字面を保ったまま `StateTy`、`Program.WellTyped`、`delta_typed`/`io_typed`/`io_exists`/`release_exists` の中身が変わったと書き、そのつど「設計者が承認した前提の変更」または「停止条件の例外」として記録している。所属の葉の規則と篩の結果型は同じ種類の変更である。
- 問題: 調べは「外形は変更不要の見込み」とするだけで、変わる中身を承認の対象として示していない。問いには「判明したら相談」としかない。
- 修正案: 値の型付けに所属の葉を加えることと、篩の型を持つ値を量化する欄の中身が広がることについて、問いを一つ加える。07-04 の前例と同じく、篩のない型では中身が以前と同値になる補題（`*_iff_old`）を受け入れ条件にすると書く。8.4 の表に `step_sound` と `effect_soundness_noLamNames`（どちらも `Release/Theorems.lean` の主定理）を加える。

## 中

**M1. 算術を入れない案 A が実用になるかを、一続きのスクリプトで示していない**（観点3）

- 場所: 調べ 1.1・1.2、問いの Q01。
- 問題: 1.1 の表は、引数にリテラルを渡す誤りがほとんどである。範囲外の値の多くは計算か入力から生まれる。再試行の `remaining - 1`、ページ送りの `offset + limit`、割合の計算、設定ファイルからの読み取りで、`checkRefined` と Result の処理が何回要るかが示されていない。
- 修正案: 5〜6種の一続きのスクリプト（30〜50行程度）を A・B・C で書き比べ、明示の検査の数と Result の分岐の数を表にする。案の候補に、全域の純粋関数 `clamp` 相当（端点へ丸める。Result が要らず、証明は min と max だけで済む見込み、実測ではない）と、「検査して失敗なら停止する」形（実行時の停止が増えるので原則2との関係を書く）を加える。B の費用の論拠に、あふれは正常値を返さない失敗なので正常な結果の区間だけを型にするならあふれの有無の証明は要らないこと、一方で加算の結果の型が引数の型に依存する署名（δ の型付け）になることが本当の費用であることを書き添える。

**M2. 型の骨格の比較に、既存の添字の形が入っていない**（観点5）

- 場所: 調べ 8.1、問いの Q07、Q08 の P1。
- 根拠: 0.0.13 は範囲を、Lean では `Ty.opaque o ix`（`Release/Types.lean:47`）、Rust では `ITy::Con(TyCon, Vec<ITy>, RangeIndex)`（`infer.rs:29`）という添字の欄で入れた。Rust の `IntKind::of_type`（`interval/domain.rs:44`）は第三の欄を `_` で無視している。
- 問題: 比較は「専用の `Ty.range`」と「一般の `Ty.refined base spec`」の二案だけで、既存の構成子に篩の添字を持たせる形（`.base ι spec` など）がない。この形なら構成子が増えず、既存の場合分けへの影響も小さい見込みである。また `refined` は基の型を `Ty` として持つので、入れ子 `refined (refined …)` を断るか、関数や Reference を基にするのを断るか、全域の区間 `Integer[min64..max64]` と `Integer` が別の表現になることの扱い（受理・拒否・正規化）を整形式で決める必要があるが、書かれていない。
- 修正案: P1 の比較に第三の案を加える。全域の区間の扱いを L04 と同じ並びの問いにする。

**M3. 型の端点に const 参照を許す案（L10）が、既存の構文とずれる**

- 根拠: 範囲のパターンの両端は「リテラル（負の数を含む）」に限る（01-05:206）。`Http.Connect[...]` のポートの閉区間もリテラルに限る（01-07「閉じた範囲引数」）。一方、01-12:1456 の `rangeFixedInteger` と 01-06:61 の局所規則は const の直接参照と括弧を読む。

- 修正案: L10 にこの差と、どちらに揃えるかの選択肢を加える。前例として `rangeFixedInteger` を引く。
