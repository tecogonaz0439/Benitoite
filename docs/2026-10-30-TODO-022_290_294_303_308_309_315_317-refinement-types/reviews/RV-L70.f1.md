## 観点ごとの根拠

### 1. 判定の追加と既存の規則の独立性

追跡ファイルの本番差分は、根の import の追加3行と07-04の追加8行だけである。新規三モジュールは既存の定義を import して補助の判定・定理・適用例を足しており、既存の Lean モジュールの本文を変更していない。主な十言明、型付けの規則、Step の規則、`CoreAssumptions`、`TargetAgreement`、前段の実署名への変更もない。

既定 import への追加と、既存の規則が新しい判定を読むことは区別できる。全 Lean ソースの import を独立に検索した結果、三モジュールを直接 import するのは `formal/Benitoite.lean` だけであり、既存の規則のモジュールへ戻る依存経路はない。追加した Decidable のインスタンスも新しい判定を対象とし、既存の判定を置き換えていない。したがって、型付けや網羅性の全入力についての不変性は、少数の適用例から推測する必要がなく、定義と依存関係の不変性で確認できる。

警告の判定を拒否や Bottom の規則として追加した箇所はない。具体の適用例は、その独立性に加えて警告対象の範囲でも従来の規則が使えることを確認するものであり、全入力の量化の代用にはされていない。

### 2. 射影形だけを表す host の判定と非空性

`IPPattern.mappedOnly_iff` は任意の IP パターンについて、WF・Canonical・`mappedBlock.Covers` の判定を「正規な条件に所属する全アドレスが射影形」と同値にしている。`mappedBlock_matches_iff` が数値の `/96` と URL 側の `isIPv4MappedHost` をつなぎ、被覆の健全性と完全性を両方向で使う。完全一致と CIDR の二構成子は `mappedOnly_exact_iff`・`mappedOnly_cidr_iff` で別に特徴づけられる。最大 prefix の `/128` をそのまま CIDR として正規形に数えず、文字列の解析が完全一致へそろえる既存の規則とも整合する。

host の条件の全構成子も扱われている。IP の条件は上記の同値を使い、名前の条件は `NamePattern.nonempty` から射影形でない対象を取り出す。名前の条件を空の集合とみなして全称命題を自明に真にする証明ではない。`RangeExpr.MappedHostOnly` は host の範囲と endpoint の host の欄を扱い、endpoint ではポートの区間の WF も要求する。他の範囲の形は判定の外である。

`not_url_target` は全ての URL の解析成功を量化し、`not_request_target` は実際の `Val.reqTarget` が読む同じ URL の解析へ帰着する。射影形を拒否する対象の入口の性質を、範囲の集合自体の空性へ取り違えていない。`witness` は任意の判定成立範囲と適合する種類について、整形式の対象と `SnapshotMem none` を同時に返す。endpoint ではポート区間の下端を使い、その区間の WF から上端以下を得るため、空の区間を証人にしていない。

Bottom と不可能な腕に関する補題も、この非空性を使っている。`member_true` は同じ対象を保持した値の自己観測で所属を真に評価し、`not_refuted` は論理の健全性から所属だけを仮定にした矛盾の導出を否定する。`not_exhaustive_nil` は任意の P・不透明型名・範囲添字について、既存の `Inhabits` と網羅性の定義にこの値を渡し、腕なしの網羅を否定する。これは網羅性が使う所属関係の証人であり、任意の不透明型名と添字に対する実行時の型付き値の構築を主張するものではない。`scopePattern_typed` は任意の型付けの文脈で従来の `V_ScopePattern` を使う。矛盾する追加の経路条件まで含めて到達可能とする主張もない。

完全一致・CIDR の含む／含まないは全称の同値で閉じ、例では `/96`・`/97`・`/120`・正規化される `/128` と、広い `/95`・`::/0`・IPv4・IPv4互換の形を対照している。WF・Canonical・被覆の各条件が欠ける例と、endpoint の不正なポート区間もある。ホスト名の文字列の評価を時間切れで除いたことは記録されているが、ホスト名の構成子は全称の証明で扱われており、場合の漏れにはならない。

### 3. 起点差と全ての有効な起点の値での不所属

`PathBasesDiffer` は、pattern と対象の `base?` が双方 some であり、その名前が違うことだけを述べる。pattern の起点は全5種、起点からの対象は cwd と home の2種を持つ。`based` の補題と `TargetInput.base?_eq_basedPath?` は、この実際に書ける組全体を扱う。Top・絶対形・secrets の pattern と絶対形の対象は判定から外れ、未知の値や間接呼出しを既知の直接入力として扱う定義も足していない。後二者の検出は R60 の受け持ちのままである。

`OutsideAllEnvs` の量化は `∀ σ, σ.Valid → ...` であり、対象がその σ で解決したときの不所属を要求する。一つの σ での不所属を受け取ってこの全称命題を返す補題はない。`outsideAllEnvs_based_iff` は同じ起点なら接頭辞の打消しで元の pattern と要素列の不所属へ帰着し、違う起点なら完全一致と「幹と要素列のどちらも他方の接尾辞でないこと」へ帰着する。二つの列に共通の後置部分がある場合だけ起点の列を選んで一致させられる、という特徴づけである。

この逆方向で使う環境は、単に存在を仮定していない。`PathEnv.exists_pair` は異なる起点の値を独立に置き、root・cwd・home と任意の work・tmp の全場合で lookup と Valid を証明する。WF の仮定は環境へ置く列の正規性を供給する。木の条件では起点の列を選べば常に所属させられるため、全環境での不所属は成立しない。一方、起点が違えば不所属になる有効な環境も構成できる。検査2では正規な pattern と対象を記号のまま残し、At が成功する環境と不所属になる環境の双方の存在を同時に確認した。

At との接続では、`checkAt_ok_mem` が成功から同じ σ による対象の解決と所属を取り出す。したがって `OutsideAllEnvs.checkAt_not_ok` はどの有効な σ とどの上限でも成功しないことを示す。逆方向は pattern の WF・種類 path と対象の解決先の WF を明記し、Top を上限にした成功を構成する。静的な上限が狭いための失敗を、pattern 自体への不所属と同一視していない。`outsideAllEnvs_iff_checkAt` は起点からの形だけに限らず、絶対形・secrets も含む任意の範囲の式と対象の形を量化している。

この同値は、診断 E0462 の実装やエラー分類そのものではない。形式不良と種類違いの検査は従来の `checkAt` が所属より先に行い、直接の既知入力を選ぶ診断側の条件は R60 に残る。補助命題が提供するのは、全環境での不所属だけを根拠にできることと、単一環境の観測で代用できないことの数学的な条件である。この範囲で L70.36 の受け持ちを満たす。

### 4. 種類 host の範囲パラメータ

`fitsKind_host_iff` は全ての範囲の式を場合分けし、host に適合する形を Top と host 条件の絶対形に尽くしている。`host_absolute`・`mem_host_env` は解決と所属が起点の値を読まないことを示すが、`snapshotMem_host` では snapshot を持つ所属に従来どおり σ.Valid が加わる。この条件を黙って消していない。

`covers_host_iff` は内側が Top の場合も含む。非Topの条件が名前だけなら IP の対象を、IPだけなら名前の対象を選べるので、host の全対象を覆えない。従って path の根の木と Top の区別から生じる完全性の制限を、そのまま host に持ち込む必要はない。内側の WF は前提に残り、整形式でない条件を空疎な包含で覆う証明にもなっていない。

具体化は既存の `Builtins.RangeAdmissible` を使う。`host_image` は任意の署名・任意の位置 i を量化するので、host が唯一の範囲パラメータ又は位置0である場合に制限されない。`single_host_iff` はその一変数の場合を同値にするもので、Top 以外には WF・Canonical と元の `B.admitsR` を要求する。Top の場合の許容も従来の全Topの枝による。`Ty.instR_scoped_rvar` は任意の種類と番号 i を量化し、検査2でも path・host・Top の列の位置1の host への置換を確認した。host の受理のために種類・署名・置換の定義を変える必要がなかった、という L70.39 の範囲の説明は正しい。

使う位置がない宣言については、`PrimSig.Scoped` の例が範囲変数の個数を上限として扱う形成を確認し、具体化の例が引数と結果の型を変えず、path・based・secrets を host の位置で拒否することを示す。ただし、これは組込み署名についての証拠である。現在の核の利用者関数には範囲パラメータの列と具体化の列がなく、表層の `FunDecl.rangeParams` に列があるだけでは脱糖・適用の保存を結論できない。最新計画の群 K の決定と合わせて情報1のとおり受け入れる。host を添字に持つ標準の型・エフェクトの新設や、未使用の診断の決定を F1 が済ませたとは記録されていない。
