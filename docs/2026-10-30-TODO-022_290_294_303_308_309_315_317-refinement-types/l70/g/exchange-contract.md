# 交換の論理の証明書の位置と番号

コーパス16、付随の表8を一組とする。版の判定を通った一つの入力ごとに、論理の証明書の一覧を持つ。一行は `path : List Nat`、`index : Nat`、`certificate`、`actions` の四欄であり、同じ `(path, index)` が二度現れたら交換の読み込みを拒否する。前提とゴールは入力の欄に含めず、推論が同じソースと署名から求める。

## 位置の決め方

位置は、全プログラムを検査する入口の `CheckTables.checkProgram` が渡す位置から始める。通常の関数の根は `[0, i]` であり、`i` は材料の `defs` の宣言順の0始まりの番号である。本体はこの根に `[1]` を付ける。実装の根は `[1, i]`、メソッドの本体は `[1, i, 1, j]` である。`j` は材料から作る `methods` の、重複を除いた宣言順の一覧の番号である。辞書と署名の検査にも同じ宣言の根を使う。関数だけを選ぶ入口も、全プログラムの同じ位置を渡す。

本体の中は `CheckInfer.inferBlockExpected`・`inferBlock`・`inferExpr` の子の番号を順に追加する。式列・穴・腕・節も、同じ関数の対応する子を使う。この順序は JSON のオブジェクトのキーの並び、名前の文字列のハッシュ、評価にかかった時間、証明の探索の回数から決めない。推論の入力は書き出したソースと署名であり、探索の成否と関係なく同じ位置が得られる。

## 部分型と実引数の番号

論理の問い合わせの鍵は `CheckInfer.logicProof` が受ける位置と番号そのものである。`inferLe` の型の再帰では、篩の基底型へ進むと `[0]`、依存列の引数へ進むと `[0]`、残りの列へ進むと `[1]` を位置に付ける。data の型引数も先頭に `[0]`、残りに `[1]` を付ける。新しい型の部分へ進むと番号は既存の関数が指定する0へ戻る。List・Lazy・Mapの値の型へ進む場合は位置と番号を保つ。

値の実引数の篩の導入は番号0、要素の部分型は番号1である。式又はブロックの期待型への変換、呼出しの結果の部分型は番号0を使う。`or die` の二つの結果の照合は、それぞれ番号0と1を使う。同じ問い合わせを再推論又は再検査で読むときは、同じ鍵の証明書を使う。入力に書いた証明書がその位置の前提とゴールに適合するかは、論理の検査器が再検査する。

この契約は問い合わせを外部の信頼条件にしない。鍵がない場合は、同じ前提の使用又は閉じた述語の候補を既存の推論が作る。不正な証明書を成功又は unknown に変えない。証明書と会計の操作列の構文の実装・往復・既定 import の読者は本体の交換の変更と同時に照合する。
