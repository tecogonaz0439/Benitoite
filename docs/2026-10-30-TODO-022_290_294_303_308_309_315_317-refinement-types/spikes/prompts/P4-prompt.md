# P4: 部分型の文脈を論理の埋め込みで表す案を確かめる捨てる試作

`spikes/prompts/P-common.md` の共通条件に従う。書き込み先は `spikes/P4/`。上限は 3 時間（最初の1時間で progress.md）。設計者は 2026-10-30 にこの試作の追加を了承した。

## 背景
試作 P3b（`spikes/P3/`）は部分型の導出の置換と移動を証明したが、葉の含意と型付けの文脈 Γ を意味の述語（`Interp → (V → Value) → Prop`）で表していた。そのレビュー `docs/2026-10-30-TODO-022_290_294_303_308_309_315_317-refinement-types/reviews/RV-P3.md` の重大 S1 は、本番の Γ（`List (Option Ty)` の構文の文脈）へ移すには、(i) 葉の文脈を篩の述語の有限の列とする論理の埋め込みにし、篩の canonical forms で Φ を作る、か、(ii) 全ての値の型に意味の所属を定める意味のモデル（ストアと再帰があるので step-indexed な論理関係に近い）を作る、かを選ぶ必要があると指摘した。取りまとめは (i) を推す。この試作は (i) が本番の骨格で成り立つかを確かめる。

手元の `formal/.lake` の成果物は HEAD のソースより古い（RV-P3 の M2）。最初に `cd formal && /usr/bin/time -l lake build` を一度実行して作り直す（`lakefile.toml` の `-M 12288` が効く。経過時間と最大常駐量を記録する。sandbox で `/usr/bin/time -l` が使えなければ、`lake build` の終了状態と経過時間だけを記録する）。30分を超えたら止めて記録する。作り直した後、P3b の `P3b-Nat.lean` と `P3b-BoundaryProofs.lean` を検査し直し、HEAD で通るかを記録する（RV-P3 M2 の受け入れ条件）。

## やること
1. **論理の埋め込みの定義**: 本番の変数の表現（Nat の de Bruijn と `Ty.WF`、P3b-Nat の形）を使い、型付けの文脈を「通常の束縛の型」と「篩の述語の有限の列 Φ（構文の論理項）」に分けて持つ形を定める。部分型の葉の含意は `Entails Φ p`（P2 の検査器の健全性に接続できる構文の含意）で表す。
2. **canonical forms**: 閉じた型付きの値 `v : refined(carrier, p)` なら `p[v]` が成り立つ（篩の述語の意味が真になる）補題を、整数・長さ（`List`）・レコードの欄（名目の `data` の欄の射影として）・`Reference` の中身を読まない形で示す。`Http.RequestIn` については、RV-P3 M5 の「要求の保持と端点の一致」を型の意味に入れた形で一つ示す。
3. **埋め込みの保存**: 値の置換と移動で、Φ と `Entails` が保たれること（`HasTypeVQ.subst` の `V_Sub` の枝に当たる補題を、Φ を構文の列とした形で一つ通す）。束縛の下で Φ に述語を足す規則（`if` の分岐の条件で Φ を広げる）を一つ示す。
4. **P3b の結果との対応**: P3b の `TyLe/TelLe/FieldsLe.bind` と `Eff.cover_bind` が、葉を `Entails Φ` に置き換えても同じ形で証明できるかを、代表一つで確かめる。P3b の M6 の接続（`M6Body.lean` の `checked_subtype`）を、この形の葉へ持ち上げる言明を書く（証明は代表でよい）。
5. **見込みの更新**: RV-P3 が挙げた「本番に残る命題」1〜10 のうち、この形で閉じたもの・残るものを書き、本番の見込み（P3 の estimates.md の行1・2・4）を更新する案を書く。(ii) の意味のモデルが必要になる箇所が見つかったら、その箇所と理由を書く。
