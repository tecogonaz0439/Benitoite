# 篩型の本実装（0.0.14）

2026-10-30 に始めた改造である。扱う項目は docs/todo の TODO-022（篩型）を中心に、TODO-290（区間解析の Rust と Lean の比較の残り）、TODO-294（Lean の関数名 `admit` の改名）、TODO-303（範囲のパスを基準のディレクトリからの相対で書く）、TODO-308（範囲付きの値の射影と拡大を受理する位置の制限）、TODO-309（IPv4 射影の範囲だけを指す host パターン）、TODO-315（E0519 の表示）、TODO-317（コードのコメントと期待値の作業の ID）。

## 目的

値の範囲を型で表す篩型（refinement types）を、実用（権限制御を含む）に要る全体として型の規則へ導入する。0.0.12 の区間解析は型を変えない静的な解析であり、本改造は、その判定の中核を再利用して、範囲を型と関数の契約に書けるようにする。

## 設計者の決定

- 2026-10-30: 0.0.14 の中心を TODO-022 の本実装とする。0.0.13 の試作 SB が推した最初の段（64ビット `Integer` の定数端点の区間の型、関数の引数と結果の契約、構造の一致による型の等号、既存の値の表現、検査付きの動的な入力からの導入）を出発点とする。範囲は調べの後に確定する。
- 2026-10-30: 一般の述語と SMT ソルバ（docs/todo の TODO-311）は今回は相乗りしない。
- 2026-10-30: 実装を段に分けない。段に分けても目先の費用が小さくなるだけで総費用は減らず、段ごとの固定費用（テスト・リリースなど）が積み重なる。他の関数型の言語の実装を参考に、権限制御などでの実用を想定して、篩型の全体を設計から実装まで行う。これにより、上の「SB の範囲を出発点とする」と調べ S01 の「最初の段」の案は退けた。TODO-311 の境界は、この方向で改めて問う。
- 2026-10-30: 調べ S02 の問いの層 A（[study/questions-full.md](study/questions-full.md) の Q01・Q03・Q04（F3・変性・旧受理の拡大・ほかの行）・Q07・Q12）は、案 I を基に推す案を一括で採る。範囲は実用に要る全体（整数の各幅・Byte・Character・Float・Decimal の値域、String・List・Bytes の長さ、Map・Set の大きさ、レコードの欄、値に依存する端点と線形の関係、算術・分岐・関数と高階関数の契約、権限用途）とし、一般の述語は量化子のない線形の整数算術と論理の結合までを自作の手続き（遅延した DNF、Fourier–Motzkin、整数の分枝限定、証明書を検査器で確かめる）で判定する。利用者の measure・未解釈関数・SMT（docs/todo の TODO-311 の残り）は含めない。総費用は中心574時間・352〜796時間の見込み（実測ではない）を暫定とし、捨てる試作の後に更新する。
- 2026-10-30: 層 B・C は推す案を一括で採る。例外として、TODO-303 を今回含め、TODO-290 の外部の型の全面的な交換も今回含める（推す案はどちらも独立に判断するだった）。L17（判定の予算）は意味を説明して確かめ直す。層 C の捨てる試作 P1〜P3 は14〜20時間を上限として行う。構文は暫定とし、予備測定は少数の試行で時間と料金を見積もってから別に了承を得る。これにより改造の名前に TODO-290・294・303・308・309・315・317 を足した。
- 2026-10-30: L17（判定の上限）は固定にせず、引数で指定できるようにする。単位は時間やメモリでなく、自作の手続きの操作の回数（ステップ数）とする（Dafny・SPARK などの先例。時間は機械と負荷で変わる）。指定はコマンドラインの引数（`check`・`run`・`test` で同じ。案は `--proof-steps=<整数>`）と、ソースの関数ごとの指定の両方とし、コマンドラインで全体の既定値を決め、関数ごとの指定がその関数で上書きする。引数を指定しなければ既定値を使う。使った回数と効いていた上限と出どころを診断と `check --report=json` に出す。既定値を下げる変更は受理が狭まる変更として BREAKING_CHANGES に登録する。利用者に見せる呼び名は「ステップ数の上限（steps）」とする（「予算」は使わない）。既定値の数字は取りまとめが案を示す。
- 2026-10-30: ステップ数の上限の既定値は、一つの条件あたり 100,000 ステップを仮の値とする（捨てる試作 P2 の測定で、実用に近い例の最大が 564、重い例が 85,628）。係数の桁数と証明書の大きさは別の上限を設けず、重みを付けてステップ数に数える（下の 2026-10-30 の訂正で改めた）。実装の後に実際のスクリプトで測り直して確定し、設計者に諮る。
- 2026-10-30: プロジェクトの設定ファイル（`package.bnt`）で上限を指定できるようにする。`--proof-steps` は根の設定と各パッケージの設定に書け、依存のパッケージは自分の設定の値で検査する。`--max-call-stack` と `--wasm-memory`・`--wasm-fuel`・`--wasm-transfer` は根の設定にだけ書ける。`--allow-effects` は設定ファイルに書けない。優先の順はコマンドライン、根の `package.bnt`、処理系の既定値で、`--proof-steps` だけはソースの関数ごとの指定がその関数で上書きする。効いていた値と出どころを `check --report=json` と実行前の確認に示す。
- 2026-10-30（訂正）: ステップ数には重みを付けない。判定の手続きのすべての処理（走査・複製・正規化を含む）を1回ずつ数え、ステップ数が実際の仕事量を一定の倍率の中で抑えるように定義する。証明書は書き足すたびに数えるので既にステップ数に入る。係数は固定の幅の整数で持ち、幅に収まらなくなったら上限とは別の理由で「判定できない」を返して診断に示す。利用者が指定するのは `--proof-steps` の一つの数のままである（[RV-P2](reviews/RV-P2.md) の M1・既定値の節）。
- 2026-10-30: 見込みが増えた二項目を、続けて今回含める。TODO-290 の外部の型の全面的な交換は追加 12〜32時間（中心22）から 40〜96時間（中心68）へ約3倍（`external function` の除外も0件にし、外部の関数の呼び出しの規則を Lean に入れるため。今まで比べていなかった入力で見つかる食い違いの修正は見込みに含めない）、TODO-303 は 36〜88時間から 60〜140時間（中心100）へ約1.6倍（[RV-S03b](reviews/RV-S03b.md) の重2）。総額は中心約746時間・454〜1,037時間の見込み（実測ではない）。
- 2026-10-30: 範囲のパスの相対形の基準（プロジェクトの根の既定）は、入口の根のディレクトリ（実行を始めるファイルがあるディレクトリ。`package.bnt` を読む場所と同じ）のままとする。祖先の `package.bnt` を遡って探す案は、範囲の基準と import の根が分かれるので採らない。リポジトリの根から使うスクリプトは、ディレクトリを指定して `main.bnt` を入口にする運用を手本にする（[study/questions-riders.md](study/questions-riders.md) の Q11 の C）。
- 2026-10-30: 入口の指定で実行の形を分ける。ファイルを指定したとき（シェバンや `run` を省いた実行を含む）は単体のスクリプトとして実行し、`package.bnt` を読まない（依存のパッケージは使えない。同じディレクトリの下のモジュールの import はできる）。ディレクトリを指定したときはプロジェクトとして `<dir>/package.bnt` と `<dir>/main.bnt` を使う。`check`・`test`・`fmt` も同じ規則とする。ファイルの隣に `package.bnt` があっても警告しない（明示的にファイルを指定しているため）。範囲のパスの相対形の基準は、どちらの形でも入口のルートディレクトリ（ファイルを指定したときはそのファイルのディレクトリ、ディレクトリを指定したときはそのディレクトリ）とし、パス変数の名前は `{root}` とする（`{project}` は使わない）。`package.bnt` に書く上限はプロジェクトとして実行するときだけ効く。まだ利用者がいないので、影響はこのプロジェクトのテストだけである（設計者）。
- 2026-10-30: 捨てる試作に P4（部分型の文脈を、篩の述語の有限の列とする論理の埋め込みで表す案を確かめる。上限3時間）を足す（[RV-P3](reviews/RV-P3.md) の重大 S1。意味のモデルを作る案は、見込みにない大きな作業になりうるので先に (i) を確かめる）。

- 2026-10-30: Lean の骨格の二点を推す案で決める（[RV-P4](reviews/RV-P4.md)）。(1) 値を代入して閉じた後の条件は、閉じた条件の式を計算する評価器とその健全性を作り、「閉じていて評価が真なら導ける」規則を加えて導く（状態の型付けに条件を残して運ぶ案は採らない）。(2) 検査した `Http.RequestIn` の値の型付けの規則に、要求が型の変数を含まないこと（`groundVal`）と、URL の対象が保持する端点と一致することを前提として加える。これは 07-04 と `Syntax.lean` のコメントに記録した既存の決定（これらを処理系の側で保証する）を 0.0.14 で改めるものである。論理の埋め込みで足りるのは、篩の条件が一階の観測（整数・長さ・不変な欄など）だけを読む場合（L02）であり、ストア・継続・ハンドラでの閉じ方は較正の段で確かめ、行き詰まったら止めて相談する。
- 2026-10-30: 実装プラン（[plan.md](plan.md)・[decisions.md](decisions.md)・[implementation-request.md](implementation-request.md)）を了承する。計画の了承の時点で答えが要る三つの問いは推す案で決める。U01: Lean の変数の表現は本番の Nat の de Bruijn と `Ty.WF` を保つ。U08: 判定の内部の上限は置かず、すべての仕事をステップ数で数える。U09: 依存のパッケージの `--proof-steps` は、依存の `package.bnt` に値があればそれを使い、なければコマンドラインの値（なければ処理系の既定値）を使う。依存の `package.bnt` に入口だけで効く鍵（`--max-call-stack` など）があれば誤りにする。改造の文書を `san_benito` へコミットしてから L00a を起動することも了承する。
- 2026-10-31: L00a の区切りで、残りの見込みの読み方は (ii) とする。L10〜L70・R・D・V の能動時間の見込みは計画のまま保ち、記録から読める実績の上限（外側の時間は能動時間の上限）を情報として添える。L00a の担当の能動時間は約3.3時間以下（記録の外を含めても約4.3時間以下）で、計画の7〜14時間に対する比の上限は群で違う（埋め込み・移動・置換・被覆は0.2〜0.45以下、二度の反例を含んだ相互置換・文脈の狭めは0.5〜1.05以下）。L00b の終わりと本番の追随の最初の一群の後にも同じ形で上限を添える（[l00a.16b/estimate.md](l00a.16b/estimate.md)、[RV-L00a.16](reviews/RV-L00a.16.md)）。L00a で取りまとめが行った契約の二度の改訂（値の置換で型注釈を正規化する、芯が継続の型の篩を整形式から除く）も、この区切りで設計者に報告した。L00b を起動する。
- 2026-10-31: 篩の述語の閉じた評価は、片側だけで真偽が決まる `or`・`and` を、もう一方が観測できなくても結果とする（強い Kleene の三値）。構文と書ける形は変わらない。述語では、通常の短絡の `or` と違い、順序が結果に影響しない。観測できない部分が結果を左右する場合は評価失敗のままであり、失敗を真に変えない。
