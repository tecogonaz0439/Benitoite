### 1.2 Liquid Haskell の実装から採る点と採らない点

Liquid type inference の核は、述語を無制限に発明することではなく、有限の候補（qualifiers）から条件の連言を選ぶことである。原論文は、まず HM の型を求め、同じ構造の型へ述語変数を付け、部分型制約を生成し、不動点計算で候補を絞る。この有限性と決定可能な含意の検査が、推論を終えられる理由になる。Benitoite でも型の構造の等号、値が流れる向き、述語の含意を分ける。ただし、現行の推論をそのまま HM 全体と呼ばず、局所の非多相性と明示した関数契約を保つ。[Liquid Types §1・§3・§4](https://ranjitjhala.github.io/static/liquid_types.pdf)

measureは、リストの `len` のように構成子ごとに定義した関数を論理式で使う仕組みである。単に利用者の純粋関数を名前だけ登録する規則ではない。長さの関数の結果をその論理上のmeasureの値と等しい型にし、構成子の型へ長さの等式を付ける。案 I では組込みのmeasureと非再帰の別名を閉じた集合として提供し、案 II では利用者の measure の停止・構成子との対応を検査する。[Spec Reference: Measures](https://ucsd-progsys.github.io/liquidhaskell/specifications/#specifying-measures)

abstract refinements は、`p` のような述語そのものを関数や data のパラメータにする。型パラメータに `Port` を代入して保つこととは異なり、特定の整数演算や高階の走査を使っても p を保つ契約を書ける。原論文は、未解釈の述語と合同閉包を使い、具象化の推論を liquid inference へ戻す。案 II の費用にはこの型検査・具象化・診断を含める。「SMT を足せば abstract refinements もただで使える」としない。[Abstract Refinement Types §2・§3](https://ranjitjhala.github.io/static/abstract_refinement_types.pdf)

依存型と篩型は、互いに排他的な分類ではない。F* は両方を使う。今回の Benitoite の案は、同じ値の表現を持つ型へ条件を付け、関数の型の中の値の参照を論理へ制限するものである。Idris/Agda のように、任意の型族と型の計算、証明項の構築をスクリプト全体へ導入する提案ではない。Lean/Coq の部分集合の型は意味の参考になるが、kernel の変換規則と、含意を使う自動の部分型の判定を同じ仕組みとは扱わない。

実際のLiquid Haskellは、取得した[開発版README](https://raw.githubusercontent.com/ucsd-progsys/liquidhaskell/develop/README.md) と[公式のpluginの説明](https://ucsd-progsys.github.io/liquidhaskell/blogposts/2020-08-20-lh-as-a-ghc-plugin.lhs/)では、GHCのpluginとして通常のコンパイルの中で検査する。2008年のOCamlのDsolveの実装と、現在のHaskellの検査器を同じ実装とは呼ばない。Benitoiteへ採るのは、元の型の構造を求める処理と、述語の制約の生成・解決を分ける設計である。

Fluxの著者の[実装の説明（§4）](https://arxiv.org/html/2207.04034v2)も、位置との対応を求める処理、未知の述語を含むHorn制約を作る検査、有限の候補による推論を分ける。可変位置の強い更新はRustの所有権の条件に依存するため、Referenceを持つBenitoiteへその部分をそのまま採らない。今回の値依存は、不変な値とそのmeasureの値に限る。

### 1.3 SMT と専用の決定手続きの区別

| 系統 | 判断するもの | できることと限界 | Benitoite への示唆 |
|---|---|---|---|
| SMT を使う言語 | Liquid Haskell・F*・Dafny・Flux、GNATprove の自動証明の一部 | 論理式を複数の理論で検査する。量化・再帰・非線形まで全部を決定できるという意味ではない | 他言語の表現力と、既製ソルバの開発費用を区別する。既存 OSS の採用は本案にない |
| 区間の包含・抽象解釈 | 上下端、交差、凸包、演算の正常値の近似 | `0<=x<=10` に強い。`x+y<=n` や `2*x=1` の整数の矛盾を一般には決定しない | 現行 Interval を高速な近似として再利用し、関係の判定の代わりにはしない |
| 差分制約 | `x-y<=c`、等号を二方向の不等式へ変換 | 添字と上限の差、残り件数を扱う。一般の `2*x+3*y<=n` は表せない | 速い専用経路として使えるが、全体の公開論理をここだけへ狭めない |
| Presburger 算術の手続き | 整数の加減算・定数倍・比較・論理結合等 | 整数の格子を扱い、有理数上の線形演算だけの検査とは異なる。一般の変数どうしの積は別問題 | 案 I は量化子のない線形整数の部分を公開する。SMT-LIB の QF_LIA と QF_IDL の区別が参考になる |
| コンパイル時評価・ライブラリ規則 | refined・Iron | 既知値の所属と登録した含意を検査。関数の任意の本体の条件を推論する仕組みとは異なる | 動的入力の検査を明示し、条件の登録を証明の代用にしない |
| 証明項の検査 | Lean・Coq、依存型言語の証明の利用 | 証明を構成できれば一般の性質も扱える。完全自動の探索とは別 | ソルバの出力を小さな検査器で検査する信頼境界を採る |

理論名の範囲は [SMT-LIB の論理の定義](https://smt-lib.org/logics-all.shtml) で確認した。区間・差分・線形整数の使い分けと実装順は本担当の設計案であり、上表の言語がすべてその順に実装したという調査結果ではない。Lean の [omega の説明](https://lean-lang.org/doc/reference/latest/Tactic-Proofs/Tactic-Reference/#omega) を2026-10-30に再取得し、dark/grey shadows を実装しておらず完全な決定手続きではないという記述と、選言を場合分けする設定の説明を確認した。これは取得した latest の説明であり、本リポジトリの固定版を実行して確かめた結果ではない。Lean の戦術で例が通ることを、自作する公開判定器の完全性の証明にしない。

差分制約をグラフの負の閉路で検査する方法は、[MIT 6.006 の講義17（差分制約の節）](https://courses.csail.mit.edu/6.006/spring11/lectures/lec17.pdf) で確認した。閉路上の不等式を足すと `0<0` に至るため、探索した閉路を小さい証拠として検査できるという設計に使える。

## 2. Benitoite の用途から選ぶ全体の範囲

### 2.1 用途・型・必要な規則

| 用途 | 篩を付ける型と条件 | 定数/値依存 | 算術・絞り込み・契約 | 推す範囲と残る保証の限界 |
|---|---|---|---|---|
| 設定の読取り | Integer の port/retries、Decimal/Float の比率、String の長さ、List の要素と長さ、record の欄間の関係 | 両方。設定値を読んだ後の `count<=maximum` も要る | decode の成功から導入し、関数の結果へ条件を残す | 同じ改造に含む。JSON の形が正しいことだけで篩を導入しない |
| ファイルの権限 | 正規化済みパスへの所属、`PathIn[R]` | 固定 R と、同じ種類の範囲パラメータ R | 検査成功、包含による拡大、引数・戻り値・ハンドラ節を通す | 字面の対象の上限を保つ。実体・symlink・OS の隔離は保証に加えない |
| ネットワークの権限 | host/IP/CIDR と port、`RequestIn[H,P]` の保持 endpoint | 固定した対象範囲と範囲パラメータ、動的入力の所属 | 検査済み要求を型の契約から射影し、送信の効果へ結ぶ | DNS/TLS の副次通信と情報フロー制御を加えない。文字列長だけで安全な URL と認めない |
| port | Integer/UnsignedInteger16 等の閉区間、用途に応じて0または1から65535 | 両方。動的な下限・上限も可 | `p+1`、分岐、関数の引数・結果 | 全整数幅と Byte の所属を含む。異なる幅を暗黙変換しない |
| IP/CIDR・パスの構築 | 既存の正規化・所属の意味を持つ対象型 | 文字列の入力は動的、公開する範囲は閉じた記号 | 正規化と所属を標準の全域な検査で確かめる | 任意の文字列連結から正規な対象を自動で証明する規則は含めない（L15） |
| 件数・添字 | 非負整数、`0<=i<List.length(xs)` | 値依存が必須 | increment/decrement、二変数の比較、同じ xs を引数にした契約 | リストと添字を同じ束縛へ関連付ける。長さを調べた別の短いリストへ転用しない |
| 割合・予算の配分 | Integer の百分率、Decimal/Float の値域、`used+remaining=limit` | 両方 | 整数の線形算術と分岐、丸める演算の正常結果の値域 | Float/Decimal を数学的実数と同じ線形式にしない。丸め後に再検査できる（L04・L05） |
| 再試行・分割・ページ送り | `remaining>=0`、`offset+limit<=total`、正の chunk size | 値依存が必要 | 再帰の宣言契約、正の枝の `remaining-1`、加算の正常結果 | 残り回数の数値条件を保つ。callback の呼出し回数と停止性はこの型だけでは保証しない |
| 文字の範囲 | Character、Byte、ASCII の数字・英字等 | 定数端点と変数との比較 | 比較の真偽、toInteger/fromInteger の契約 | Unicode scalar の欠けた領域を整数の全区間と同一視しない |
| 文字列の長さ | String の `byteLength` と `characterCount` を別のmeasureにする | 両方 | 連結、分岐、変換、結果の長さの契約 | 「文字数」という単一の曖昧な尺度を作らない。表示幅・書記素数と同一視しない |
| List・Bytes の長さ | 不変な列の長さ、長さの上下限・等式 | 両方 | literal/cons/append/concatenate/map/reverse/filter/take/drop の契約 | map は正常に返れば同じ長さ、filter は0以上入力長以下。割当ての成功までは保証しない |
| 空でないリスト | `List[T]{xs \| List.length(xs)>0}` | 定数0との関係、値依存のまま関数間で保つ | パターン照合・head/tail/map の契約 | NonEmptyList の役割を同じ型の条件へ移す。head を成功する形で使える入口も同時に用意する |
| 複数リストと添字 | `length(xs)=length(ys)`、添字が両方の長さ未満 | 値依存が必須 | zip 相当、matrix の行長、引数どうしと結果の関係 | 案 I の線形の長さの関係で扱う。要素どうしの一般の整列性は案 II の問いにする |
| 不変な record の整合 | 例 `start<=end`、`offset+count<=total` | 値依存 | 構築・更新時に外側の述語を再検査、アクセサの論理項と対応 | record の更新を、古い外側の述語を保つ操作と決めつけない |
| Map/Set の大きさ | size の上下限 | 両方 | 新規/既存の鍵による増分の違いを保守的に近似 | size の条件は含める。任意の鍵の存在・要素間の関係は案 II。鍵の型の不変性を別に保つ |

### 2.2 一つの改造でそろえる受け入れの用途

S01 の「定数の引数を渡せる」だけの例を受け入れ条件にしない。次の六つを、入力・分岐・計算・関数境界を通るスクリプトとしてそろえる案を推す。下表の回数は提案する規則上の必要箇所の数であり、実行回数や LLM の成功率の実測ではない。

| 一続きの用途 | 動的検査を置く箇所 | その後に自動で保つ条件 | 失敗処理 |
|---|---|---|---|
| 設定ファイルから port と retries と非空リストを読む | decode の各欄と record の関係の検査 | 検査後の関数呼出し・record の受渡しでは再検査0箇所 | conversion の失敗を Result で返し、try/or return で一度伝播する |
| 再試行の残りを減らす | 外部から受けた上限を1箇所 | `remaining>0` の枝で `remaining-1>=0`。各回の再検査0箇所 | callback の失敗と入力不良を別に扱う |
| ページの offset と件数を進める | 外部の total/limit を検査 | `limit<=total-offset` の枝で次の offset が total 以下。関数の結果にも残す | 最後の短いページを計算する分岐を含める |
| リストと添字を関数へ渡す | 未知の i を境界で1箇所、又は if の比較 | 同じ xs の `List.at`（新入口の案）で追加の Result 分岐0箇所 | 旧 List.get は Option のまま使える |
| Decimal/Float の設定比率を計算して使う | 入力時と、丸め後の計算結果を必要に応じ各1箇所 | 検査後の受渡しと比較の枝は条件を保つ | 数学的実数の恒等式で検査を消さない |
| 狭い PathIn/RequestIn を関数・節・高階関数へ渡す | check…In を外部入力の境界で1箇所 | 戻り値、入れ子の射影、保持値の拡大、狭い IO への転送に再検査0箇所 | 検査の Error はそのまま処理し、射影位置の都合で Top へ変えない |

新しい型の書き方の例は次である。値に依存する関数の引数は宣言順に束縛する。長さの上端を排他的に書くために、新たな半開区間の略記を必須にしない。

```text
type Port = Integer{p | 1 <= p and p <= 65535}
type NonEmptyList[T] = List[T]{xs | List.length(xs) > 0}

function nextOffset(
  total: Integer{n | n >= 0},
  offset: Integer{i | 0 <= i and i <= total},
  limit: Integer{k | 0 <= k and k <= total - offset}
) -> Integer{j | offset <= j and j <= total}
  return offset + limit
end function

function pick[T](xs: List[T],
  i: Integer{k | 0 <= k and k < List.length(xs)}) -> T
  return List.at(xs: xs, i: i)
end function
```

`offset+limit` が機械整数の値域内にあることは、total が同じ Integer の値で、上の前提があることから導く案である。これは新しい規則での机上の導出であり、処理系・Lean で再現していない。この例を、すべての算術が止まらない保証には広げない。関係のない上限の積、非線形な割合、丸めのある計算では、証明できる正常結果の条件と、実行時エラーがないことを分ける。

## 3. 範囲付きの値・エフェクト・TODO-308

### 3.1 統一する対象と残す違い

0.0.13 は `Ty.opaque o ix`、Rust では `ITy::Con(TyCon, Vec<ITy>, RangeIndex)` として範囲を保持する。01-06「範囲付きの不透明標準型」は添字を不変とし、射影・拡大の受理に同じ本体内の局所の由来を要求する。エフェクトの被覆は、型の等号にも型引数の照合にも使っていない。この現在の仕様と、以下の変更案を区別する。

| 案 | 値型・射影・拡大 | エフェクトへの接続 | 実用と総費用 |
|---|---|---|---|
| U0: 不変な値型と現在の局所解析を保つ | 元と先の範囲を明示 API で照合。型の引数を信用する規則だけを別途足せば TODO-308 は解消可能 | 現在の単一対象の shape と範囲の具体化を使う | 篩型の部分型とは別の拡大規則が残る。現在の位置制限を残す根拠にはならない。U1 より本体で12〜36時間少ない見込みだが、後で U1 に移すなら追加の固定費用と既存機能との接続のやり直しを要する |
| U1: 保持型を残し、所属と値の部分型を統一（推す） | `PathIn[R]<:PathIn[S]` は R が S に覆われるとき。`RequestIn` は同じ要求と保持 endpoint のまま比較。射影は型の不変条件から受理 | 「最も具体的」は、その IO 呼出しに渡す式の、部分型による拡大を当てる前に合流・通常の型制約から得た入力型の添字 R と定義する。明示注釈で S へ広げて保存した値なら S を使う。操作を関数値として使う場合は期待する入力型又は後の呼出しの入力制約から、拡大前の契約を一度具体化する。制約が最後までなければ Top（01-06「範囲付きの不透明標準型」）。結果型や周囲の許容効果から狭い R を逆算しない | 関数・節の型と一般の値の受渡しを同じ規則で扱える。共通の骨格・費用へ計上済み |
| U2: PathIn を String の篩、RequestIn を ClientRequest の篩へ完全に置換 | path の字面の所属は表せるが、request の解析済み endpoint と元の要求の関係を別に保持する必要がある | 再解析、DNS、実効 endpoint の選択を篩の消去に巻き込むおそれがある | 今回は推さない。同じ HTTP 対象を使う条件を失えない。U1 に加え32〜96時間の見込みで表現・同一性・IO の応答の再検証が要る |

U1 で統一するのは、値の所属を前提にする導入・条件の除去・拡大・関数の契約である。効果の原子は計算の対象の上限であり、値そのものの型ではない。一つの効果原子を複数の原子の和で覆うように変えたり、ハンドラの選択を論理同値で変えたりはしない。型の等号は構造で判定し、範囲の相互被覆だけで型を同一視しない。

既存の `widen…In` は、明示的に契約の上限を広げたいときの互換 API として残せる。暗黙の部分型と意味が重なるため、新規の例では通常の型注釈への受渡しを示す。API の削除も Q03 で選べるようにし、黙って二方式を増やさない。 `check…In` は所属を新しく検査する操作なので残す。`…Value` は保持するデータを取り出す操作なので、値の部分型と同じ役割ではない。

### 3.2 TODO-308 を閉じるための証明と受け入れ

型の不変条件として必要なのは、単に「添字を持っている」ことではなく、**その型の値が実際にその対象を保持し、対象が添字の範囲に属すること**である。次の四つをそろえて初めて、局所の由来に代えて型の契約を使える。

1. 構築する全経路で所属を示す。check の Ok、拡大、関数の結果、標準の定数、外部入力の変換、ストアからの取得を含める。未知の通常値へ狭い型を注釈するだけの導入は認めない。
2. 部分型の拡大で保持対象と RequestIn の要求全体が変わらないこと、狭い対象の所属から広い対象の所属が従うことを示す。Top から狭い添字へは証明なしに進めない。
3. 関数の呼出し側が引数の型を検査し、宣言した結果を本体で検査する。節の引数には、捕えた操作の具体化済みの型と添字から所属を与える。節の名前だけから所属を与えない。
4. 表層で型から射影を受理したことを、脱糖したコアの同じ値の型付けへ結ぶ。従来の `ScopeAccept` の局所状態の接続定理だけを、新しい型規則の証明として使わない。

構築経路の点検は、次表を入口とする。「読んだ」は当該の分岐を確認したという意味であり、全経路の不変条件の証明を終えたという意味ではない。Rust の内部から値を渡す経路も、信頼する実装として扱う範囲を決める必要がある。

| 経路 | 今の不変条件・確認できた範囲 | 根拠のファイル | U1で必要な確認（未確認分はP3） |
|---|---|---|---|

## 4. 一般の述語と自作のソルバの境界

### 4.1 案 I と案 II

「決定可能」と「実装が必ず短時間で答える」は区別する。案 I も、有限の予算を超えれば unknown を返す実装とし、受理には検査済みの証明を要求する。これは整数区間だけへ範囲を縮める案ではない。

| 比較 | 案 I: 決定可能な論理の篩（推す） | 案 II: 一般の述語と自作 SMT を含める |
|---|---|---|
| 書ける条件 | 量化子なしの線形整数の比較、定数倍、And/Or/Not、標準の長さ・欄・構成子の検査・範囲所属。Float/Decimal は専用の値域の検査と比較として分ける | 案 I に、利用者の構造再帰 measure、論理上の関数、未解釈関数の等号、述語のパラメータを加える。量化と一般の反射の範囲は別行で決める |

| 推論 | 局所の単点・線形式・分岐の条件と、明示した公開契約。有限の候補に限る局所の抽象化 | liquid inference の候補述語、measure の展開、abstract refinement の具象化も必要になる |
| ソルバ | 自作の線形整数の手続き、論理結合の分解、範囲の代数、専用の比較。既存 SMT の呼出しなし | 自作の命題探索、線形整数、合同閉包、理論間の等式共有、展開・予算管理。Z3/cvc5 等は採用しない |

### 4.2 推す探索手続き・証明書・measureの境界

案Iでは、**否定標準形からの遅延したDNFの場合分けと、有理数上のFourier–Motzkin消去＋整数の分枝限定（branch-and-bound）**を自作する案を推す。単体法・CDCL(T)の全体は今回の既定にしない。次の手順はBenitoiteへの提案であり、実装済みの手続きではない。

1. 含意 `Φ⇒p` を `Φ and not p` の矛盾へ写す。Notを原子へ押し、整数の `<` を `<=` と1の差へ、等式を二不等式へ、不等号の否定や不等式でないことを適切な選言へ正規化する。FloatのNotはNaN等の専用の意味に従い、整数の規則を流用しない。
2. Andは同じ枝に追加し、Orは二つの枝へ分ける。DNF全体を先に実体化せず、深さ優先で必要な枝だけ展開し、全枝の矛盾の証拠を集める。これはDNFに相当する場合分けであり、節学習を持つDPLL/CDCLと同じ実装とはしない。
3. 各枝で区間と差分制約を先に処理する。残った線形条件は正確な有理数によるFourier–Motzkin消去を使い、矛盾なら非負線形結合の証拠を復元する。整数係数で割り切れる左辺には丸めのcutを使う。
4. 有理数上の消去は整数に対して不完全であり（例 `2*x=1`）、分枝限定も有界でない領域では停止を保証しない。そのため探索は予算で止めてunknownとする。有理数モデルしか得られなければ、整数である元の変数xの非整数値qを選び、`x<=floor(q)` と `x>=floor(q)+1` に分けて両枝を調べる。枝の矛盾がそろえば証明できる。無矛盾な整数モデルは元の条件で検証するが、measureを独立変数へ写したモデルが実際の値で実現できるとは限らない。その場合は反例と断定しない。

選言と実数の消去の基礎は [Avigadほか『Logic and Mechanized Reasoning』第14章](https://avigad.github.io/lamr/decision_procedures_for_arithmetic.html)（否定標準形・DNF・Fourier–Motzkin）、命題探索の別案は[同第6章](https://avigad.github.io/lamr/decision_procedures_for_propositional_logic.html)（Tseitin変換・DPLL）で確認した。LIAの決定可能性は [Chistikov, 2024](https://drops.dagstuhl.de/entities/document/10.4230/LIPIcs.FSTTCS.2024.1) を参照した。整数への拡張で分枝限定とcutを組み合わせる実例は [Dutertre・de Moura, CAV 2006, §6](https://yices.csl.sri.com/papers/cav06.pdf) で確認した。同論文は単体法を基礎とし、Fourier–Motzkinの爆発も指摘している。ここで消去を推すのは証拠の実装を小さく点検できる案としてであり、性能上の優位は未確認である。P2で消去の生成量が実用の予算を超えるなら、同じ証明書を出す単体法への変更を費用付きで設計者へ戻す。いずれも取得日2026-10-30。上記4の分枝と丸めの組合せ・予算・証明書は本担当の案であり、これらの資料の手続きをそのまま採ったとはしない。Cooper/Omegaの完全な変数消去は対案として残すが、原論文を取得できていないCooperの細部を確定の根拠にしない。

証明書の整数・等号部分は次の有限木と導出列を候補にする。対象範囲の所属/被覆とFloat/Decimalの比較・特殊値は、別の有限の規則表と証明した専用の検査器に結び、LIAの変数へ無条件に置き換えない。実際のバイナリ形式や番号付けはP2後に固定する。参照番号はその枝の祖先又は同じ枝の先行する導出だけを指し、兄弟の枝の事実・循環・範囲外・sort違いを拒否する。`derive` は一つの事実を導いて後続の反証で使う形とする。

```text
Linear = integerConstant + sum(integerCoefficient * integerVariable)
Fact   = le(Linear, integerConstant) | pathEq(Path, Path)
EqProof = refl(Path) | assume(equalityFactId)
        | sym(EqProof) | trans(EqProof, EqProof)
        | alias(bindingId) | field(fieldId, EqProof)
        | measure(measureId, EqProof)
Derive = input(factId)
       | combine([(nonnegativeInteger, deriveId)], expectedFact)
       | round(deriveId, positiveDivisor, expectedFact)
       | substitute(EqProof, deriveId, expectedFact)
       | builtinLemma(registeredLemmaId, arguments, expectedFact)
Refute = derive(Derive, Refute)
       | falseConst(deriveId) | falseFormula(formulaId)
       | clash(literalId, negatedLiteralId)
       | andIntro(formulaId, Refute)
       | orCases(formulaId, leftRefute, rightRefute)
       | intCases(variableId, integerCut, leRefute, geRefute)
Certificate = (normalizationTrace, Refute)
```

`combine` は非負の整数倍の加算であり、有理数の乗数は正の共通分母を掛けて除く。`round` は `d*t<=b`（dは正、tは整数線形式）から `t<=floor(b/d)` を得る規則に限り、負数の床も数学上の定義で検査する。gcdによる等式の不整合は二不等式とroundから導出できるため、別の信用する規則を必須にしない。`assume` は実際に文脈にある同じsortの等号だけを読み、`falseFormula` と `clash` は文脈のfalse又は同じ原子とその否定だけを認める。`orCases` は文脈にある選言の両枝、`intCases` は全整数を覆う二分岐の両方を検査する。`andIntro` では対象のAndの両方を文脈へ加える。`falseConst` は変数が消えた偽の比較だけを受理する。`builtinLemma` はソルバが任意の補題を登録する入口ではなく、証明した有限の規則表の要素に限る。正規化も無検査の文字列の書換えにしない。

案Iのmeasureの項は、次の形に制限する（L01・L02・L07・L31）。これにより必要な等号と合同性の範囲を決める。

```text
Path = self | valueVariable | Path.visibleImmutableField
MeasureTerm = builtinMeasureId(Path)
IntegerTerm = integerLiteral | integerPath | MeasureTerm
            | IntegerTerm + IntegerTerm | IntegerTerm - IntegerTerm
            | integerLiteral * IntegerTerm
```

`List.length(r.items)` はrから欄への連鎖なので許す。`length(map(f,xs))`、`measure1(measure2(x))`、Referenceの現内容、非公開欄の任意の射影は型内で許さない。通常の式を一度評価して変数へ束縛した値なら、その変数を根としてmeasureを使える。脱糖で一度の束縛を作れるため、呼出し式を通常の引数位置に書くことまで禁じない。

measureの項は、根と可視な欄の列とmeasureIdを鍵に、新しい論理変数へ写す（purification）。別名の束縛の同一性、明示して証明したPathの等号、同じ欄と同じmeasureへの合同性だけをEqProofで検査する。構成子が一致すると確かめた枝でのみ部分的な欄の補題を使う。recordやListの等号から要素全体を比較して新しい等号を発見する完全な理論や、異なるmeasure間の合同閉包は加えない。長さ保存等の関数契約は、評価済みの入力/結果のPath間の線形事実を与える。これが案IIの利用者定義の関数・再帰measure・一般の未解釈関数の合同閉包との境界である。案Iにも上記の限定した合同性の証明は必要で、その費用を第10.1節の「論理への写し」に含める。 等号の反射・対称・推移・合同の一般の規則は [Avigadほか第12章§12.1](https://avigad.github.io/lamr/decision_procedures_for_equality.html#equality) で確認した（取得日2026-10-30）。本案はそこで扱う一般の関数記号への合同閉包の一部に項を限定する提案である。

論理の決定可能性は、**予算を置いたこの実装の完全性を意味しない**。分枝数・係数の桁数・消去の生成数・証明書の大きさ・操作数が上限を超えればunknownとする。同じ入力・版・予算・安定した変数順なら同じ結果になる規則を定める一方、論理的に同値な式への書換えや版の違いで予算内の成否が変わりうる。公開する制限としてこの予測可能性の限界を示す。超過の診断とJSONには、必要な条件、超過した資源の種類、上限と消費量、版と予算設定を出し、候補不足・未対応の演算・検証済みの反例と区別する。条件を分ける、補助注釈を付ける、明示checkを使うという修正を示し、unknownをTopへ変えて通さない。

機械幅と長さの上限を、探索の停止の論拠に使う案も比較した。各幅の整数は有限値域を持つ。Rustの [runtime/mod.rs](../../../crates/benitoite/src/runtime/mod.rs) は一操作のListの上限を2^24、String/Bytesを2^30バイトとし、[list.rs](../../../crates/benitoite/src/runtime/list.rs) は長さの表現と検査を持つ。ただし「一操作で作る値」の制限を、全抽象値と外部から受ける値の長さの不変条件にそのまま使うことはできない。

全構築経路について上限を証明し、有限個の元の整数変数と長さ変数の区間を各分岐で厳密に縮めれば、区間幅の有限性を分枝限定の停止に使える。補助線形式は元の変数から決まり、端点や係数まで機械幅に切り詰める必要はない。この論拠は本担当の数学上の検討であり、Leanで未証明である。第7.2節の任意の有限列を含むモデルを保つ基準案では長さ変数に一律の上限を仮定しないため、有限領域による完全性・停止は採用条件にしない。上限を型の意味へ取り込む対案は、全構築経路とモデルの変更をP2/P3で見積もり、Q07の独立の行で選ぶ。どちらでも実用の予算内で必ず判定できるとは約束しない。

整数の例 `2*x=1` では、二不等式をそれぞれ2で丸めると `x<=0` と `-x<=-1` が得られ、加算して `0<=-1` となる。この説明は机上の導出であり、新検査器の実行結果ではない。P2ではこの証拠、負数の床、不正な乗数・分岐漏れ・巨大な証明書の拒否を確認する。

### 4.3 手続きの証明と証明書の検査

| 方式 | 信用するもの | Lean で示すこと | 費用・運用の差 |
|---|---|---|---|
| D: 判定器そのものを証明 | 証明したアルゴリズムと、それを Rust が実装する接続 | `solve Γ p = proved → Γ ⊨ p`、必要なら完全性・停止。Rust の一致は有限比較か別の証明が要る | 探索の最適化のたびに大きい証明を直しうる。案 I の基準額より Lean12〜40時間増、Rust は0〜16時間増の見込み |
| C: 自作の探索＋証明書の検査（推す） | 構文を論理へ写す規則と、小さな検査器 | `check Γ p cert = true → Γ ⊨ p`、置換・正規化との対応。部分型の受理がこの含意へ還元されること | 探索は不信として扱える。Rust にも検査器を持ち、本番の受理で検査する。証明書形式・大きさ・不良入力の上限が要る |

証明書方式でも、「Lean で検査器を証明したから Rust が常に健全」とは言えない。Rust の検査器・論理への変換・型の消去の正しさは、それぞれ実装と形式化の接続の問題である。今回の受け入れは、Lean の定理に加え、独立した固定期待値と Rust/Lean の有限比較を要求する。探索だけを外部 OSS に委ねる案も採らない。

案 II でも同じ信頼境界を使える。合同閉包には等号の反射・対称・推移・関数への合同、measure の展開には検査済みの定義と引数への代入を証拠にする。利用者が「この含意は正しい」と登録するだけの公理の入口を設けない。

## 5. 型の規則と推論

### 5.1 等号・所属・部分型

論理の文脈 Φ は、その地点で使える不変な値の条件を集めたものである。型の文脈 Γ は値の型を持つ。`{v:T | p}` は説明用の数式であり、表層構文の候補は第6節に示す。

| 規則 | 推す内容 | 他言語との比較・予測のしやすさ |
|---|---|---|
| 型の等号 | 別名展開・束縛名の付け替え・決めた正規化の後の構造の一致。一般の論理同値を使わない | 含意探索の時間や import した補題で型の同一性が変わらない |
| 篩の部分型 | 同じ値の表現を持つ T/S に対して、構造の部分型と `Γ;Φ,v:T ⊨ p⇒q` を確かめる。同じ条件を解釈するmeasureの意味の一致も要求する | Liquid Haskell の含意への還元を参考にする。数の幅の拡大など、実際の変換は別の関数 |
| 導入 | 式 e の結果を一度だけ値 x に束縛し、x の事実から要求する p(x) を証明する | F* の代入による導入に対応する。注釈を根拠に同じ条件を仮定しない |
| 条件の除去・拡大 | `T{p}<:T`、p⇒q のとき `T{p}<:T{q}`。値・評価回数・潜在効果を変えない | 静的な受渡しとして予測できる。保持する RequestIn を生の要求に暗黙変換する操作にはしない |
| 入れ子の篩 | `(T{p}){q}` を両方の条件へ平坦化する。内側の型引数にある篩はその位置に残す | 表現の違いを不変な型引数の等号の違いとして残さない |
| 全域と空 | `T{true}` は T へ正規化する。`T{false}` は空の型として認め、値を作れないことを証明する | `0<=i<n` は n=0 のとき自然に空になる。空であることだけを宣言の誤りにはしない |
| 定数 | 定数評価後に所属を検査し、宣言した篩型を与える。別名を名目型にしない | `const port: Port = 443` を認める。同じ条件の別名は用途の違いを防がない |

述語の整形式と、述語を満たす値の存在を別の判定にする。型の中の線形式は数学上の整数で扱い、`max64+1` を logical endpoint として表せる。ただしその値を Integer のリテラルとして構築する規則は増やさない。Character の所属は Unicode scalar の集合との交差、長さは非負整数としての所属である。

### 5.2 入れ子の関数: F1〜F3 の選び直し

| 案 | 関数の関係 | 受理の変化・実用 | 判断 |
|---|---|---|---|
| F1 | 篩も効果も最も外側だけ。引数と結果は等号 | callback と関数を返す関数でラッパーが増える。値依存の結果契約も流しにくい | 推さない。全体の利用で独立した例外が多い |
| F2 | 篩を再帰的に反変/共変で比較。入れ子の効果は等号 | 篩の高階利用はできるが、純粋な callback と効果の上限付き callback の受渡しに例外が残る | 対案。S01 の推奨を自動的に引き継がない |
| F3 | 同じ規則を再帰し、引数は反変、結果と潜在効果は共変 | 狭い入力を求める callback に、広い入力を処理できる関数を渡せる。旧型でも入れ子の効果の違いを受理するよう広がる | **推す**。篩と効果の違いは表示しつつ、関数の位置による例外を減らす |

一引数なら、`(x:S1)->S2(x) ! εS <: (x:T1)->T2(x) ! εT` の検査は、`T1<:S1` と、**渡し先が受け取る x:T1 の文脈**での `S2(x)<:T2(x)` と効果の被覆を求める。複数の引数は、宣言順の依存する列を、前の引数を同じ論理変数に対応させながら検査する。引数名の契約と個数は保つ。反変の検査中に、本体が受け取る値を期待型の狭い型として検査し直さない。

名前付き関数とラムダには同じ関係を使う。注釈付きラムダは自分の注釈で本体を検査し、全体を渡し先へ部分型で照合する。注釈なしなら期待する関数型を引数へ渡す。これにより、名前を付けたかどうかで反変の方向が変わらない。関数の純粋性は停止性を意味せず、型に書いた正常な結果の契約から停止を結論しない。

F3で使う効果の関係は、[01-06「エフェクトの包含」](../../design/01-spec/01-06-type-system.md#エフェクトの包含)と現行の [solve.rs](../../../crates/benitoite/src/typeck/solve.rs) の `flow_inner` を読んで、次のように選ぶ案とする。型の等号を効果の被覆へ変える案ではない。以下では一原子の被覆と構造上の包含を、01-06と同じ言い方で区別する。

| 入れ子の位置・照合の用途 | 一原子の被覆か構造上の包含か | エフェクト変数Eと行 | Failの扱い | 旧プログラムの受理への影響 |
|---|---|---|---|---|
| 関数の引数型の中の関数 | 外側の関数の反変に従い型の比較方向を反転し、そこで比較する関数自身の潜在効果には一原子の被覆を使う。負の位置だから構造上の包含へ切り替えるわけではない | 呼出し/関数値化で新しく作った推論変数だけに上下の制約を集める。反変の位置でも本体の中でほかの何とも等しくないEを具体化しない | `Fail[A]` のAは構造上の等号。不変位置の中の関数へ再帰して広げない | 以前等号を要求したcallback型が反変/共変で一致しうる。純粋なcallbackを受ける高階関数等の受渡しが増える |
| 関数の結果型の中の関数 | 結果の共変に従い、その関数の潜在効果を一原子の被覆で広げる | 結果に現れる行は入力側から解いた同じ具体化を用い、渡し先ごとに本体の中のEを書き換えない | 同上 | 純粋な関数を返す値を、効果上限のある関数を返す契約へ渡せる |
| 型引数の中の関数 | 第5.3節の共変位置では同方向、反変位置では逆方向の一原子の被覆。不変位置は関数型全体の等号を要求する | 行の原子の同一性は構造で判定する。変性不明のF[A]から行制約を推測しない | List[Result[T,A]]のAの共変とFail[A]の不変を区別する | Q04-VでListの共変も採ったときに限り、`List[function()->Unit]` の変数を効果付きListへ渡せる。ReferenceやFail内では広がらない |
| 関数・メソッド・ラムダ本体の効果と宣言上限、呼出し、resumeでの効果の照合 | 現行の一原子の被覆を保つ。型の入れ子とは別の計算の効果の照合である | 本体の中の同じ行原子は自身にだけ一致する。具体化済みならその集合で比較する | Fail原子は同じエラー型だけで覆う | この関係自体は現行どおり。ただし渡せる関数値が増えるため全体の受理は広がる |
| ハンドラ保護本体と各節、Fail節、純粋の要求、部分適用の潜在効果の推論 | 現行の構造上の包含を保つ。入れ子の関数値の受渡しに一原子の被覆を使ったことを、ハンドラが除く原子の変更に使わない | 除く行/原子を構造で保持する。部分適用で新しい効果を発明しない | 捕捉・再送・継続にあるエラー型は不変 | これらの照合の入口の規則は保つ。入れ子の型の受渡しが変わる影響は別に比較する |
| ファイル宣言の合併、main/testの上限、型の等号 | 現行の構造上の規則を保つ | 同名の行だけを一致させる | 不変 | 入れ子を扱うために宣言上限や型の同一性を広げない |

呼出しや関数値化ごとに新しく作ったEの具体化は、正負の位置から得た全制約の解決後に決める。現行どおり最小の集合が一意ならそれを使い、比較不能な最小候補が残るなら注釈を求める。負の位置の都合だけでEを空へ決めたり、部分型の判定のたびに別々のEへ置換したりしない。本体の中の `uses E` を上限とする位置へ渡す具体的な効果は、入れ子でも空だけを許す（同じEの行原子同士は構造で一致する）。`uses Console.Write` を任意のEで受理する規則は追加しない。反変の比較で本体の中のEが必要効果の側に回る場合は、上限にも同じ行原子Eが必要であり、空集合や具体的な名前付き原子では覆えない。上限がEと別の原子の和なら、E自身を同じEが構造で覆う。この推論が制約の登録順によらないことと、行/型/範囲/値の置換で一原子の被覆が保たれることは、P1/P3と本体の証明の条件である。

### 5.3 型構成子の引数の変性

| 位置 | 推す変性 | 理由と必要な証明 |
|---|---|---|
| List[T]、Option[T]、Result[T,E]、Pair[A,B] | 読み出す成分は共変 | 不変な構築済みデータを渡すだけなら、全要素を同じ値のまま広い型で読める。Result の E の共変と、後述の Fail の不変を混同しない |
| Lazy[T] | T を共変 | 現在の lazy は純粋であり、force の正常結果を広げられる。保存する遅延値のストアの型付けも広げる補題が要る |
| 利用者の不変な data/record | 宣言から正負の出現を計算し、検証した変性を使う。正負が混ざる引数は不変 | 関数を欄に持つ型の負の出現、相互再帰、opaque の公開境界を含む。型引数の共変を全 ADT に無条件で与えない |
| Reference[T] | 不変 | 広い値を書き込む経路を防ぐ。List[Reference[T]] の外側が共変でも、Reference の内側は広げられない |
| Map[K,V] | K は不変、V は共変 | 値は不変な木から読む。鍵の比較・辞書・探索の意味を暗黙変換で変えない |
| Set[T] | 不変 | 要素が鍵として使われるので、所属と比較の契約を保つ |
| 型クラスの辞書、Fail[E]、内部の継続型 | 既存の対応する位置は不変 | 辞書の入力と出力、Fail の捕捉と再送、継続の再開のプロトコルを部分型だけで変えない |
| 型構成子を表す変数 F[A]、外部型 | 変性が証明・宣言されない位置は不変 | 未知の F が Reference である可能性や、外部の ABI を推測しない |
| PathIn/RequestIn の範囲 | 値を渡すときは共変、型の等号では構造を比較 | 第3節の不変条件と同じ対象の保持の証明に限定する |

共変を採ると `List[Port]` を `List[Integer]` へ渡せる案になる。一方で Map の鍵が同じ条件の別名なら、別名展開の等号で通る。相互に含意する別構造の条件は、一般の論理同値による等号にはしないので、鍵を変えるには明示の変換が要る。これらは L11・L12 の独立した利用制限として問う。

### 5.4 値依存の束縛・置換・有効範囲

公開する関数の契約では、後の引数型と結果型が前の引数の不変な値を参照できるようにする。Named argument は評価をソース順に一度ずつ行い、宣言上の引数の位置への対応表を作ってから契約へ同時に代入する。位置の入替えで条件の意味を変えない。

型の中に任意の実行式を埋めず、論理上の項だけを置く。局所変数、定数、値の不変な欄、標準の長さなどを論理変数に結ぶ。呼出し `makeList()` の長さを型で直接何度も読む代わりに、脱糖の際にその結果を一度だけ束縛する。ソースで bind を強制するかは構文の問いにするが、推すのは通常の式位置を制限せず、内部の束縛で同じ値に結ぶ案である。

measureで参照できる欄は、その位置から可視な不変の欄か、意味を検査した公開の射影に限る。篩の条件の解析を理由に、opaque な型の非公開の欄を外から読むことは認めない。型構成子の変性の検証も、欄の型だけでなく、述語・型クラスの制約・公開する射影での正負の出現を含めて行う。

局所の名前が外へ出る場合は、内部の存在量化された値と事実、又は外で使える条件への射影を使う。例えば `return i` の型が局所の xs の長さに依存するなら、呼出し先で使える引数の長さへ言い換えるか、xs と i を一緒の record に格納する必要がある。内部の存在変数を、呼出し先が自由に選べる全称変数として扱わない。公開の新しい existential 構文は必須にせず、通常の record と外側の篩で関連する値をまとめる案を推す。

Reference から読んだ n は、取り出して束縛した値の snapshot として使える。その後のセルの内容へ同じ条件を帰属させない。List の長さと外側の record の数値欄は不変なので、内部の Reference の要素が変わってもその長さの条件は保たれる。セルの中身・ファイルの存在・DNS の応答・開いている資源の状態は、不変な値に対するmeasureとしては登録しない。

添字の安全性に必要なのは、対象リストの長さとの関係である。同じ長さだと証明できた別のリストにも添字を使える。これと「元のリストの同じ要素を保持する」CheckedIndex の契約は異なるので、CheckedIndex を単なる整数の別名へ置き換えない。

### 5.5 推論・合流・経路条件

| 接点 | 推す規則 | 結果の予測と診断 |
|---|---|---|
| 型の構造の推論 | 現行の Equal と Flow を分離したまま、構造の型変数を解く。Flow は `Γ;Φ;from<:to` と理由を保持する | union-find の等号へ部分型を混ぜない。呼出し・戻り値・欄など、失敗した契約の位置を保つ |
| 局所リテラル | 表示の通常型に加え、論理事実 `x=443` を記録する | `bind p <- 443` の後から Port と証明できる。注釈なしを理由に全情報を失わない |
| 型変数 | 同じ `T` を受け返す関数は篩を持つ型で具体化できる。型の構造が未定なら述語の判定を待つ | `identity` の T を初回の引数だけで広い Integer に固定して後の期待型を失わない |
| 既存の多相 | 関数の型パラメータを使い、局所の束縛は非多相のまま | 篩を加えたことを理由に polymorphic reference を導入しない |
| 合流 | 同じ構造の型なら、各枝の値と事実の合流を作る。単純区間には凸包、関係には必要な候補述語を保つ | `if flag then port else 443` でも両方の上限を示せれば Port に使える。枝の変数の自由な参照を外へ残さない |
| 合流の上限 | 各入力が結果の部分型であることを証明する。期待型があれば各枝をその型で検査 | 最小上界を常に発見すると約束しない。比較不能な関数の反変部分の合流には注釈を求める |
| if/guard/match | 真の枝へ p、偽の枝へ not p。六比較、And/Or/Not、短絡、構成子・非空の判定を読む | `not (x<0 or x>=n)` から二つの境界を使える。任意の Boolean 関数は、検証した契約がある場合に限る |
| 再帰 | 宣言した関数契約を帰納的な仮定として本体を検査し、正常に返る値の条件を示す | 停止性を篩の健全性と混同しない。公開契約を本体解析から勝手に強めない |
| 候補述語の範囲 | 局所の式・比較・要求する契約から有限に作る。新しい候補を無制限に探索しない | 論理上は真でも候補不足なら注釈や条件の分割を案内する。公開契約は明示した型のまま |
| try・or return/or die・パイプ・mapError | Result/Option の構造の制約を解いた後まで対象の篩の認定を遅らせ、内側へ期待型を伝える | `bind port: Port <- try check(value: raw) or die` に内側の Result 注釈を必須にしない。対象がなお複数なら注釈を求める |
| 予算 | 論理の分岐数・係数の桁数・証明書の大きさ・探索の操作数を明示して制限する | 超過は unknown。関数契約の意味を Top に変更して受理しない。予算と候補の不足を区別して示す |

現行 Rust の接点は [infer.rs](../../../crates/benitoite/src/typeck/infer.rs) の `Constraint::{Equal,Flow,Try,EffSub}` と [solve.rs](../../../crates/benitoite/src/typeck/solve.rs) である。登録順によって型が変わる懸念は S01 の机上の懸念であり、本番で再現した不具合とはしない。制約の並べ替え、引数の named argument の順、if の枝の順を変えた入力を、同じ公開契約と受理理由で比べることを受け入れ条件にする。

### 5.6 算術・検査不能・検査の消去

| 値・演算 | 正常結果の型に使う関係 | 実行時エラー・証明の限界 |
|---|---|---|
| 整数の加減算・定数倍・単項負号 | 数学上の結果との等式、各幅の値域との交差 | 交差だけでは「あふれない」と言えない。結果の篩は正常に返った値の契約。あふれの不在を求める API/最適化では別に値域内を証明する |
| 変数どうしの積・除算・剰余・ビット演算 | 入力の区間から健全な正常結果の近似を出せる場合に使い、それ以外は通常型 | 案 I の型内の線形式には一般の積を入れない。動的な計算そのものは許し、計算後の if/check で篩を得られる |
| Character/Byte | スカラー値/バイト値への射影と比較の対応 | Character の加算は新設しない。surrogate の穴を埋めない |
| Float/Float32 | 有限値の区間・NaN/無限大の分類、比較の真偽。負の枝では NaN を明示的に残す | `not (x<0)` から x>=0 は一般には導けない。`x+1>x` も丸めで成り立たない。これらの机上の注意を既存版の再現済み不具合としない |
| Decimal | 値の大小による区間、丸める各演算について証明した正常結果の近似 | scale の違う同じ数は等しいが、表示の scale は残る。数学上の有理数の恒等式を、丸める演算の契約に無条件で使わない |
| List/String/Bytes | 長さの等式、連結の和、filter/take/drop の上下限 | byteSlice には UTF-8 境界の条件も要る。長さ内だけで文字境界と証明しない |

Float/Decimal の算術結果の一般の関係を自動で証明するソルバは基準案へ含めない。ただし、それらの値にも篩を書き、入力・算術結果を明示的に検査し、比較による所属と関数契約を使える。これは型の対象からそれらを外す判断とは異なる。L04・L05 と費用表で独立して選ぶ。

証明できない式は静的に拒否し、暗黙の実行時検査を挿入しない案を推す。診断では「反例がある」「候補が不足する」「予算超過」「扱わない演算」を分け、反例と呼ぶのは実際にモデルを検証できた場合だけとする。動的入力には、期待する篩を対象にした純粋な `Result` の検査を明示し、既存の try/or return/or die で失敗を処理する。通常の型へ勝手に戻して成功扱いにはしない。

静的な篩の証拠は実行時表現から消す。これは、明示した check の呼出しや Result を自由に消してよいという意味ではない。同じ入力が成功することを証明できた check は、引数の評価順・回数・停止・失敗の観測を保ったまま `Result.Ok(value)` へ置き換えられる場合に限る。失敗の処理・エラーの payload・権限の検査を消す変換には、別の意味の保存を要求する。

## 6. 構文と術語

### 6.1 候補の比較

| 候補 | 値依存・長さ・契約への適合 | 推す判断 |
|---|---|---|
| `Integer[lo..hi]` | 閉区間には短い。List の長さ、欄の関係、Or を表すには別の形式が要る。Integer の型引数と範囲の添字も同じ括弧になる | S01 の第一候補から外し、区間だけの略記を入れる対案とする |
| `T{v \| predicate}` | v を明示的に束縛し、Integer・String・List・record の同じ形式を使える | **暫定で推す**。LLM の成功率が高いと確認したわけではない |
| `{v:T \| predicate}` | Liquid Haskell の形に近く、束縛と型の順が明示される | 有力な比較対象。通常の型が名前から始まる現行の文法との差がある |
| `T where v => predicate` | 波括弧を避けられるが、where と矢印の用途を増やす | 比較対象。既存の宣言の where との区別が要る |
| `requires`/`ensures` の独立した契約節 | 引数どうしの関係を書きやすいが、型の篩と同じ条件を二方式で書くことになる | 型で表せる契約には追加しない。例が型だけでは読みにくい場合に再検討する独立の問いにする |

推す表記の案は次である。`List.length` 等は既存の関数名に対応するが、型の中では証明した組込みの measureとして解釈する。普通の関数呼出しを評価する意味にはしない。

```text
type Port = Integer{p | 1 <= p and p <= 65535}
type ShortName = String{s | 1 <= String.characterCount(s)
                           and String.characterCount(s) <= 64}
type NonEmptyList[T] = List[T]{xs | 0 < List.length(xs)}
type Ratio = Decimal{v | 0m <= v and v <= 1m}
type ASCIIDigit = Character{c | '0' <= c and c <= '9'}

function prefix[T](xs: List[T],
  n: Integer{k | 0 <= k and k <= List.length(xs)})
  -> List[T]{ys | List.length(ys) = n}
  ...
end function
```

既存の type 別名はそのまま使う。値のパラメータを持つ別名は `type Bounded(n: Integer) = Integer{i | 0<=i and i<n}` のように型引数と括弧を分ける案を比較する。これは新しい構文であり、単に既存の別名がすでに対応しているとはしない。型と値のパラメータを区別して宣言でき、引数と同じ束縛・置換を使う形を推す。

関数の範囲パラメータについても、値の整数パラメータと対象範囲のパラメータを区別する。例として「範囲 R は path の種類、入力は PathIn[R]、効果は File.Read[R]」という署名を同じ改造で書けるようにする。正確な宣言の字面は、既存の `effect E` と型パラメータとの混同を課題で測ってから固定する。内部の範囲変数を表す文字列をそのまま公開構文にはしない。

候補を具体的に比べられるよう、値の別名の適用を `Bounded(n)`、範囲の種類を `range R: path` と書く案を置く。`range` と `path` はこの文脈の新しい構文候補であり、実行時の値型の名前ではない。

```text
type Bounded(n: Integer) = Integer{i | 0 <= i and i < n}
function pick[T](xs: List[T], i: Bounded(List.length(xs))) -> T
  return List.at(xs: xs, i: i)
end function

function read[range R: path](path: Scope.PathIn[R])
  -> Result[String, IOError] uses File.Read[R]
  return File.readTextIn(path)
end function
```

対案は、別名の値引数にも種類付きの角括弧を使う形式と、範囲パラメータに `scope` を使う形式である。前者は短いが型引数との構文上の区別が増え、後者は Scope モジュール名と役割が近い。候補の字面と束縛の意味を混ぜず、どちらの候補でも同じ期待型・範囲の具体化の規則を測る。

### 6.2 端点・長さ・書ける式

型の条件では、値変数、定数、数値の加減算・定数倍、組込みの measure、比較と論理結合を許す。定数端点と値依存端点を別の構文にしない。整数の閉区間と半開区間は、それぞれ `lo<=v and v<=hi` と `lo<=v and v<hi` で書ける。これにより Integer の最大値の後の値を実行時に構築せず、添字も `i<n` と書ける。

String の条件には `byteLength` と `characterCount` をそのまま書く。任意の「len」を導入してどちらかを暗黙に選ばない。List と Bytes の長さは別の組込みの measureであり、数値の結果は同じ論理上の非負整数である。構文の条件の中の `a<b<c` は、既存の比較の連鎖でないため認めず、and で二つの条件を書く案を推す。

型の注釈の篩は、その右の代入値の条件を仮定する構文ではない。関数の契約の変更と、その契約に適合する本体の変更を、診断 JSON と公開する型の差分でも区別する必要がある。

### 6.3 構文を測る課題

候補2形式、生成・境界の変更・診断からの修正を含む8課題、各2試行の **32試行**を短い予備測定の候補とする。課題は、定数区間、動的端点、非空リスト、二リストの同長、UTF-8 の二つの長さ、再試行の減算、型別名と callback、PathIn の関数境界である。構文誤りと、型・効果・期待結果の達成を別々に採点する。少数の差を統計的な優位と呼ばない。

準備4〜8時間の見込み（実測ではない）は第10節の文書・表層の費用に含める。LLM の料金・レート・実行の待ちは未見積もりであり、測定自体は設計者の了承後に少数の試行から見積もる。本担当は LLM を呼ぶ測定をしていない。測定をしない選択でも、暫定の構文を実測済みとは書かない。

measureの説明に使っていた「標準観測」は正式語として採らず、本文を「組込みの measure」へ直した。measureの意味は[Liquid Haskellの仕様](https://ucsd-progsys.github.io/liquidhaskell/specifications/)の構成子ごとの定義を参照し、案Iでは第4.2節の有限の規則へ限定する（取得日2026-10-30、外部の利用者定義measureと本案の限定は異なる）。「篩の忘却」は「篩の条件を外して元の型へ渡す」と説明し、「四欄」は `delta_typed`・`io_typed`・`io_exists`・`release_exists` の名前を列挙し、「再接続」は「既存機能との接続のやり直し」と書く。これらの説明語を新しい術語として用語集へ追加しない。日本語の「観測」は、IO事象の観測など現行設計書の意味と混同しない。

新しい正式な語を用語集へ追加する作業は実装側で行う。本書は用語集を変更しない。原語と訳語の候補はQ06で設計者が今選ぶ。未回答のまま実装担当が正式な訳語を決めない。

## 7. Lean の骨格と証明の組み直し

### 7.1 一度で値依存を含める骨格

| 骨格 | 全体の範囲に対する評価 | 判断 |
|---|---|---|
| 型ごとに range/length/nonempty の構成子を増やす | 値の変数と論理の置換を各構成子へ重ね、String と List と scope の合成条件に同じ処理が増える | 比較用に留める |
| 既存の base/list/opaque 等へ別々の添字を足す | 今の opaque ix の再利用に近いが、二つの値の関係、外側の record の条件、異なるmeasureの値を結ぶAnd/Or に共通の述語が結局必要 | 専用の高速表現としては使えるが、意味の共通骨格にはしない |
| `Ty.refined carrier pred` と依存する関数の引数列 | 条件の整形式・所属・含意・束縛と置換を共通化できる。型の構成子が一つ増える影響と、平坦化の証明が要る | **推す**。三案の小比較で変更面を確かめてから固定する |

以下は宣言の案であり、Lean の検査を通したコードではない。

```text
LogicSort = integer | boolean | character | floatKind | decimal
            | stableValueShape | targetKind
LogicTerm = literal | self | valueVar(index)
            | observer(id, arguments) | supportedArithmetic(op, arguments)
Pred      = true | false | compare | targetMember | constructorTest
            | and | or | not

Ty        = ... | refined(carrier : Ty, pred : Pred)
Fn        = (names, dependentParameterTelescope, resultType, latentEffects)
WF        = carrier WF + pred sorts/scopes + permitted observers

DenotePred(ρ, value, pred)      -- その値で条件が成り立つこと
Subtype(Γ, Φ, source, target)   -- 論理含意を使う有向の関係
CheckCertificate(Φ, p, cert)   -- 検査の関数
```

論理項は Rust/Lean の実行式や任意の `Prop` を格納する欄にしない。型・行・範囲の変数の番号と、値の変数の番号を分離する。self は篩の値を束縛し、関数の引数列は前の値を後の型・結果・必要な効果へ束縛する。移動量・cutoff・代入環境にそれぞれの種類を持たせる。

型の意味は、型付きの値の環境 ρ の下で、その値が carrier の型を持ち、述語が成り立つこととする。構文の整形式を持たない任意の条件を `HasTypeV` の葉へ与えない。関数・Reference・資源を通常のデータのようにmeasureの引数にすることは L02 で断り、関数の契約は依存する関数型の規則で扱う。

### 7.2 篩の種類と演算の規則表

規則表は有限で閉じた定義にする。実装時に任意の「健全である」という仮定を足して登録する入口にはしない。

| 種類・操作 | 論理上の意味 | 導入と演算の証明 | 置換・変性の注意 |
|---|---|---|---|
| 各幅整数・Byte | 数学上の整数と各型の値域 | literal/check、線形演算の正常結果、あふれ不在を別命題にする | u64 最大値をホストの符号付き64ビットへ落とさない。Byte の算術は増やさない |
| Character | Unicode scalar の値と順序 | 比較、整数との変換、区間の所属 | surrogate の領域を除く意味を保つ |
| Float/Float32 | 特殊値を含む値の分類と順序、有限区間 | literal/check と比較の意味。算術の近似を使うなら丸め・特殊値を含む局所補題が要る | 任意の実数の公理へ置き換えない |
| Decimal | coefficient/scale による数の意味と表示する scale | check、大小、証明した丸め後の近似 | 同じ数の scale の違いを消す最適化にしない |
| List/Bytes/String | 要素数・byteLength・characterCount | 構築、append/concatenate/reverse/map/filter、文字列の連結と変換 | 不変な長さだけを読む。値の置換で同じ列のmeasureへ写ること |
| data/record/Option/Result | 構成子の種類と不変な欄のmeasure | 構築・match・アクセサ・更新の各規則 | 欄に関数/Reference があればその中身にmeasureを適用しない。型引数の変性の検証 |
| PathIn/RequestIn | 保持対象への範囲の所属。RequestIn は要求全体も保持 | check、射影、拡大、同じ値、選んだ IO 対象との対応 | 範囲の変数と値の変数の二種類の置換。target の種類が合うこと |
| 論理結合・線形の関係 | 真偽・整数の比較の意味 | 含意の証明書、分岐の条件、型の導入 | 論理変換・係数の演算にもあふれない表現が要る |

Float の現在の Lean モデルや Byte/Bytes の抽象化は、実装の全ビットの意味を既に証明しているわけではない（07-04）。篩の所属へ数値の性質を使うなら、抽象値の領域を精密にする部分と、標準の delta の契約の信頼条件を明記する部分を先に分ける。「既存の進行・保存がある」だけで有限値や長さの意味まで証明済みにしない。

現行の [Release/Syntax.lean](../../../formal/Benitoite/Release/Syntax.lean) では、Integer は値域の証拠を持つ一方、幅付き整数は生の Int、Byte と bytes の要素は Nat、Decimal は Int と Nat の組である。`V_Const` と `V_Bytes` は、それだけでは各幅の値域やDecimalのscaleの条件を求めない。これは読めば分かるモデルの抽象化であり、Rust が範囲外の値を作るという再現結果ではない。

この抽象化はSyntax.leanのコメントと07-04「01-12との対応」の幅付きの数の行に記録された決定である。以下は未記載の漏れを埋める案ではなく、**値域を型付けの前提にしないという既存の決定を改める案**であり、Q07で承認を求める。

全整数幅の篩を通常型の値域から導入するには、この差を解消する必要がある。推すのは、表現可能性の述語を定め、値の葉の型付け・定数/bytes の整形式・標準deltaの結果に要求する形でモデルを精密にする案である。構成子のpayloadを直ちに証拠付きへ置換する案と比較する。Floatの値の等号はIEEEの比較と論理上の値の同一性を分け、NaNへ等号の反射律を無条件で適用しない。

範囲付きの不透明型のTopにも、現在のモデルでは保持対象のない `Const.opaque` の枝があり、`shapeAt` が旧Topの形として扱う。推すU1では「この型の値は対象を保持する」をTopまで述べ、標準の対象型に限ってその枝を排除する整形式/値の型付けを加える。通常の資源型のopaque定数まで排除しない。非Topの所属だけで十分とする対案なら、Topの抽象値の枝と射影失敗を明記して残す。この二つはP3とQ07で選び、現行型の不変条件が既に全値で成り立つと仮定しない。

基準案の長さの意味は、任意の有限列に対する数学上の非負整数とする。実際の構築上限を全抽象値へ課す対案と、有限領域の分枝限定の停止への利用は第4.2節で比較し、Q07で独立に問う。基準案では確保上限を使った完全性を主張しない。現行RustのList.lengthはu32の長さをi64へ写し、Stringの長さは検査付きの個数変換を使う。論理上の長さの上限と実際の確保上限を混同せず、標準関数の正常結果がmeasureの値と等しいことを示す。巨大な抽象列でも長さを返す成功が必ずあると、`delta_typed`だけから結論しない。同欄はerrorのOutcomeも許す。

### 7.3 最初にそろえる置換と意味の補題

| 群 | 必要な言明の案 |
|---|---|
| 整形式 | 論理項の sort と参照範囲、型の `WF`/`VarsIn` が型・行・範囲・値の各置換で保たれる |
| 論理の意味 | `eval(subst p, ρ) = eval(p, extended/substituted ρ)` に相当する交換。self と外側の値変数を別に扱う |
| 所属 | 篩の導入・条件の除去・拡大、組込みのmeasureの同じ値への対応、内部の存在変数の導入/除去が所属を保つ |
| 部分型 | 反射・推移・整形式の正則性、含意の弱化と置換、構成子の変性、依存する関数の反変/共変 |
| 値の置換 | `Γ,x:S,Δ ⊢ e:T` と `Γ ⊢ v:S` から `Γ,Δ[v/x] ⊢ e[v/x]:T[v/x]`。型と Δ と効果の中にも代入が入る |
| 合流 | `join a b = j` なら a<:j と b<:j。自由な値変数を外へ漏らさず、公開契約へ暗黙に加えない |
| 判定 | 証明書の検査成功なら含意が成り立ち、部分型の検査成功なら意味上の部分型が成り立つ |
| 実行との接続 | 算術・長さ・範囲の成功の意味から、Release の同じ値の型付けと標準 delta の契約を得る |

ストアの型・継続の型・閉包にも、自由な局所名のない閉じた解釈が要る。実行状態の型付けでは、評価済みの不変な値を論理環境で閉じるか、その閉じた解釈を存在量化する。ソースの局所名をストアの型に残さない。依存する値の型が閉じる条件を主定理の外へ新しい未検査の仮定として押し出さず、状態の型付けの規則と保存で示す案を推す。

この部分が本番の骨格の主な未知である。先に単純区間の本体を作ってから値依存を追加する進め方ではなく、試作でこの閉じ方と関数・ストア・節の置換まで確かめ、骨格を固定する。

### 7.4 主定理の言明と前提の中身

| 定理・契約 | 保つ結論の案 | 変わる中身と設計者の承認対象 |

| `step_sound` | 選択条件を満たす oracle/rel/fresh の下で、計算関数 step の返す遷移は関係 Step の遷移 | 型付き入力と新検査/算術の delta の対象が変わる。逆方向の全遷移の一致を追加したとはしない |

| `Surface.desugar_typed`・`HasTypeQ.desugar` | 表層の結果型と効果を同じ内容でコアへ保存 | 値依存の束縛を作る脱糖、引数の評価順、型内の値の置換を追加。単に篩を消した通常型が付くという結論へ弱めない |
| 表層の checker の健全性 | checker が受理した情報から表層の型付けが成り立つ | Φ、証明書、依存する呼出し、合流、網羅性を読む。型推論そのものの完全性を証明したことにはしない |
| 網羅性・非選択 | 網羅と答えた場合、篩を満たすどの値も腕が覆う。非選択とした腕は選ばれない | Month の有限区間と非空 List を初期の領域へ反映。LIA の unknown では腕を除かず、保守的な検査へ戻す |
| 検査の消去 | 元と変換後の値・失敗・効果の観測が対応する | 成功を証明した純粋で全域な検査と静的証拠だけを対象にする。引数の評価を消さない |

`Builtins.Assumptions` の `delta_typed`・`io_typed`・`io_exists`・`release_exists` は、型付き値を量化するため、欄の文字列を保っても意味が変わる。新しい所属の値、依存する結果、組込みの measureを満たす delta を扱う。入力の型付けが広がる要求と、結果の型付けが広がる要求の方向は別に点検する。`sig_scoped`、`store_shape`、`sat_unconstrained`・`sat_local`・`admits_local` などの型と変数の整形式を読む条件も、値の変数と変性を含むよう変わる。

新しい意味の補助条件を「その手続きは健全」とだけ仮定しない。定義したmeasureと証明書の検査器については証明し、VM/標準 delta の実装との対応は既存の信頼条件と有限比較の範囲として明記する。標準の意味に追加の独立した仮定が要ると分かった場合は、定義・言明・仮定の差を取りまとめが設計者へ戻す。

旧型・旧署名・旧表については、実装が表す値域・scale・対象の保持の条件を満たす旧入力の導出を新規則へ埋め込む。上記の精密化で除く範囲外の抽象定数まで、無条件に埋め込めるとはしない。Rustが書き出す旧入力がその条件を満たすことも接続で確認する。

F3・共変・範囲の部分型によって旧型でも受理が広がるため、**全旧型で新旧の Ty.Le やdelta_typed・io_typed・io_exists・release_exists全体が同値**とは要求しない。表現可能性と対象の保持を満たし、入れ子の効果と不変位置を旧の等号で揃えた限定部分では規則の前提の同値を、それ以外の適格な旧入力では導出の保存をそれぞれ示す。delta_typed・io_typed・io_exists・release_existsの量化範囲を限定しないまま同値と書かない。Q07 は、この前提の中身の変更と、S01 の全面的な同値条件の置換を承認対象にする。

### 7.5 Release 75・Surface 20 の定理の組み直し

S01 の集計は、Ty.Le と関数の等号等の補題の直接参照を宣言ごとにまとめ、Release 75・Surface 20 としている。本担当は関連する実ファイルを読み直したが、この件数の全再集計や推移的な依存解析は行っていない。この数を修正が要る定理の上限とはしない。

| 現行の群 | 全体の範囲での直し方 |
|---|---|
| `Lemmas/Basic` の `eq_of_not_fn`・`eq_of_not_fn_left` | 一般には偽になるので削る/使わない。篩を外した形の保存と、構成子別の逆転へ分ける。List の共変もあるため「整数以外なら等号」に置換するだけでは足りない |
| `fn_left`・`fn_right`・`fn_fn'` | 引数と結果の等号の代わりに、同じ依存する引数列の束縛の下での反変・共変と潜在効果の被覆を返す。引数名と個数の一致を保つ |
| Inversion・Canonical・Progress | Const・List・data・opaque・Reference・Lazy のそれぞれについて、同じ値の形と carrier の所属を取り出す。篩の条件を外すことから逆向きの導入を作らない |
| MembershipBase・Membership・TargetPropagation | PathIn/RequestIn の構造の等号を、保持対象の所属と拡大の単調性へ替える。一般の数値の所属と scope の対象の種類の違いを残す |
| TypeRegularity・型/行/範囲の置換 | 型の全位置、Fail の内側、述語の自由変数、深い関数の整形式を扱う。新しい値の置換との交換を追加する |
| SubstTyping・Rename・Preservation・PresMain | Δ と結果型にも入る値の代入を使う。β の引数を本体の契約へ広げ、結果の依存型を呼出し側へ戻す |
| BuilderTyping・StoreOk・Lazy・継続 | 可変セルは不変を保ち、外の安定した値への依存を閉じる。構築器の長さを通常値として copy した地点の事実と区別する |
| Surface CallHead・Typing・ExtensionsScoped | 型付きの依存する呼出しと新しい部分型をコアへ同じ値で写す。partial application の捕捉済みの値の依存も扱う |
| FiniteTools の tyLe/tyJoin と checker | 文脈 Φ と証明書の検査へ接続し、有限支持・正規化・合流の健全性を直す。旧 Bool の比較だけの関数へこっそり論理探索を追加しない |
| Exhaustiveness と Coverage.erase | 篩を満たす値についての網羅性へ転送する。条件を忘れた型の値がすべて篩を満たすという逆方向の同値は使わない |

Core は別の小さな型体系であり、S01 が挙げた Core 24件を自動で改造へ加えない。Release の型構成子・EffR の相互再帰、順序・正規化・交換を読む箇所も直接参照の件数の外から点検する。

### 7.6 再利用と Lean 先行の順序

`formal/Benitoite/Interval/Domain.lean` は `Release.Syntax` を import している。Release.Types からそのまま読むと循環するため、数値の種類・上下限・区間・数学上の演算の領域を Release より下の共有層へ分け、型との対応を上に残す。0.0.12 の `Subset`・`subset_iff`・meet/join・正常値と失敗の区別・分岐による絞り込みを再利用候補とする。Byte は七種の整数解析の対象ではないので追加の所属を定める。

既存の Interval の中心の健全性は、独立した対象構文の評価関係についての A1 である。今回、篩の型の証拠に使う操作については、Release の算術・標準 delta と同じ意味への対応を証明する。単に Rust/Lean の区間が一致する有限比較を、この一般の意味の接続の証明として代用しない。

0.0.13 の `Scope/Domain`・`Cover`・`IPCover`・`Signature`・範囲の具体化と置換、`Release/Lemmas/Membership*` の同じ対象の保持を再利用する。整数の下限とパスの範囲を同じ未型付けの整数欄へ混ぜない。範囲パラメータを利用者へ公開する変更では、現在 nr=0 を要求する宣言の境界と、実行状態では具体化済みに閉じる条件を同時に直す。

順序は、骨格と主定理の言明・仮定の案のレビュー → measureの意味と置換 → 証明書の検査 → 部分型と Release の保存 → 表層・脱糖・網羅性 → 01-12 の写しと07-04の対応表 → 既定の Lean ビルドが sorry なしで成功した定義・証明のレビュー → Rust の接続とする。規則と補題はこの骨格へ小さく足し、一つの大変更で長期間ビルド不能にする計画を避ける。

本調べの時点ではこの順を実行していない。Lean の実際の検査は取りまとめの手元の機械で行う予定である。型・型付け・脱糖・網羅性は07-04「01-12 との対応」の内側なので、Rust を先行させて後から規則を正当化しない。

## 8. 既存機能・互換性・公開する面

### 8.1 Range の包みと NonEmptyList

| 既存機能 | 推す扱い | 理由・互換性 |
|---|---|---|
| `Range.CheckedInteger` | 動的な minimum/maximum/value を保持する包みを残し、射影する値にその bounds の篩を付ける | 同じ型の値ごとに異なる境界を実行時に保持する役割がある。単なる Port の別名へ移すと minimum/maximum の公開 API と失敗の情報を失う |
| `CheckedLength[T]` | 同じ元のリストと minimum/maximum/length を保持する包みを残し、lengthValues の結果に長さの条件を付ける | 篩の導入と、その境界をデータとして持ち運ぶことを区別する。Reference 要素の共有も保つ |
| `CheckedIndex[T]` | values/index/element の包みと get を残す。index に対象 values の長さの条件を持たせる | 現在 get はチェック時に保持した element を返す。単なる整数へ移すとその契約を失う。新しい List.at は対象 xs と i の関係を検査する別の入口 |
| `NonEmptyList.NonEmptyList[T]` | `List[T]{xs \| length(xs)>0}` の型別名へ移す案を推す。fromList/head/tail/map/toList の公開する意味を保つ | 非空という条件のためだけの表現を篩と重ねない。値の表現・型の同一性と Assert の内部表示は変わるので破壊的変更として記録する |
| `Range.checkInteger/checkLength/checkIndex` | エラーの優先順・保持する入力・戻り値を保つ。成功値の契約を強くする | 定数の失敗を Result.Error とする既存 API に、突然静的拒否を追加しない。篩を要求する新 API の静的導入とは別の契約 |
| 新しい一般の篩の check | 期待する篩と基の値から `Result[篩付きの型, 検査のエラー]` を返す | 範囲を runtime に保存する包みが不要な入力に使う。対象の型が決まらなければ注釈を求める。API 名は構文測定と合わせて決める |

Checked 系を残すのは単に移行を先送りするためではない。動的に選ばれた境界・元の値・キャッシュした要素をまとめる役割があり、篩を付けた単一の値とは保持するデータが違うからである。実装では通常の record と、その不変な欄を結ぶ篩として仕様を記述できるかを確かめ、特別な局所解析の認定を恒久的に残さない。

NonEmptyList の別名化では、既存の等値と鍵の順序、map の評価順と効果、fromList の Error、Reference 要素の共有を照合する。内部の first/rest の表示が変わることを、意味の一致の証拠で隠さない。opaque な名目型として保持する対案は、独立した型の同一性が必要な利用の有無とともに Q08 で選ぶ。

### 8.2 標準署名と安全な入口

| モジュール・機能 | 同じ改造で付ける契約 | 既存の呼出しへの方針 |
|---|---|---|
| List/Bytes/String の長さ | 結果が非負、結果が入力のmeasureの値と等しい | 旧来の Integer 期待型へ条件を外して渡せる |
| literal/append/prepend/concatenate/reverse/map/filter | 正確な長さ又は健全な上下限、要素の型の保持 | map が効果を持つ callback を呼んでも、正常に返る結果の長さの契約は使える。失敗・停止は別 |
| List.get/head/tail、String.characterAt、Bytes.get | Option の正常な形と入力条件との対応を表層の match/try で使う | 既存の Option の意味を保つ。知らない入力で失敗しうる API を突然静的拒否へ変えない |
| List.at、非空の head の入口（名前は案） | 添字又は非空の事前条件が満たされれば T を返す | 既存の Range.get と NonEmptyList.head を使う移行案も比べる。動的 API と静的契約の API は失敗の表現が異なるため、必要な役割の違いを説明する |
| 数値の変換 | 成功値の値域、整数と Character の穴、有限値の条件 | 暗黙の幅変換を増やさない。UnsignedInteger64 の全域を Integer に狭めない |
| File/Http/Scope | 対象の値の添字と潜在効果の結び付き、保持値の不変条件 | 一般の篩の推論結果から勝手に別の対象範囲を発明しない |
| Json.Codec | decode の値に要求する篩を明示検査して返す。encode は篩を条件を外して既存の変換を使える | conversion path と expected/found/reason を保ち、入力 payload をエラーへ写さない |

すべての標準 API の引数を一括で狭い型へ変更することは推さない。変更する入口と、その根拠の契約を表に列挙する。入力を狭める変更は旧コードを拒否しうるので、旧の動的な API を保つか、移行の破壊的変更として独立に選ぶ。今回必須なのは、一般の値と添字の関係を標準 API で実際に利用できることまでである。

標準の List.map は現在、補助の再帰関数を使った通常の Benitoite の関数である。長さ保存の契約を付けるならその本体も検査し、組込みの関数であるかのように無条件で信用しない。List.get の Some/None と長さの契約を与え、補助関数の accumulator と添字の関係を明示して証明できる形へ直す必要がある。

### 10.5 見込みを更新する条件

P1〜P3の後に、骨格の破損箇所と補題の実績、標準本体の契約の本数、論理の証明書の大きさを使って幅を作り直す。Q12で総費用の受け入れを保留して試作だけを選んだ場合は、本体へ着手する前に新しい係数・余裕・総額を示して再承認を得る。予算の係数だけで残りを機械的に縮めない。各作業の最初の30〜60分で不確かな接続を確かめ、見込みの2倍を超えたと気付いた時点で原因と残りを取りまとめへ報告する。

短い試行を経ずに、全比較・長い性能測定・多数の LLM 試行の所要を確定しない。時間を理由に公開範囲・主定理・失敗時の扱いを弱める判断は担当だけで行わず、どの契約が変わるかを示して設計者へ戻す。

| L23 | 一般の check の対象の篩が期待型から一意に決まらなければ注釈を求める | try/mapError/パイプを通して確定する場合は受理する案。内側の Result 注釈を常に求める制限は採らない |
| L24 | 型から不可能と証明した腕でも、名前解決・型の構造・効果の宣言の検査を省略しない | 到達不能を理由に別型の式を通す Typed Racket の例の挙動は採らない。網羅性で腕を除くのは検査済みの矛盾がある場合だけ |
| L25 | 消去するのは静的証拠と意味の保存を示した検査に限る | Result・評価順・失敗の payload・保持する要求を勝手に消さない |
| L26 | Property の自動生成は単純な区間・長さ・非空を基本とし、任意の関係の良い生成器の合成を約束しない | 関係を持つ record は手書きの構築/縮小や検査付きの候補を要する。対象外は明示的に断る |
| L27 | 局所名に依存する型を公開位置へ漏らさず、公開の existential 構文は必須としない | 関係する値を record へまとめるか、外で使える条件へ言い換える。内部では存在変数を使える |
| L28 | 構成で除いたモジュールのmeasure・標準関数は型検査で断る | 組込み構成で同じ述語を無検査で受理しない。型の意味は構成で変えない |
| L29 | 旧の動的標準 API の引数を一括で狭めない | 静的に安全な戻り型の入口は追加/移行する。既存の Option/Result API を単に型の都合で拒否する変更は別に選ぶ |
| L30 | IPv4 射影だけの host pattern は警告し、静的拒否にはしない案を推す | 常に Error になる既知の入力を説明できる。拒否なら書ける pattern を狭めるので、警告/拒否/現状維持を独立に選ぶ |
| L31 | 案Iのmeasureの引数は変数と可視な不変の欄の連鎖に限り、measureの入れ子を型内に書かない | `List.length(r.items)` は書ける。一般の実行式は一度評価して変数へ束縛し、その変数のmeasureを使う。一般の論理関数の入れ子は案IIと費用を選ぶ |

L01・L18 は案 II を選べばそのまま採用できない。案 II の場合は、measure の構造再帰・純粋性・全域性、未解釈関数と量化の範囲、証明不能の処置を、同じ粒度の独立した制限へ置き換える。案 II を「何でも自動で証明する」と解釈しない。
