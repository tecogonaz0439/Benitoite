## 2. TODO-303 の判断の案

### 2.1 パスの解決に使う名前と入口のルートディレクトリ

【決定の反映】範囲の相対パターンの起点は、入口のルートディレクトリのままとし、パス変数を `{root}` とする。ファイル指定はそのファイルの親、ディレクトリ指定は指定したディレクトリである。祖先の package.bnt の探索は採らない。範囲だけの起点と import の探索根を分ける旧の上書き案は Q13 で見直し、今回は追加しない案を推す。日本語の呼び名は Q10 の候補であり、本文では候補(A)の「入口のルートディレクトリ」を仮に使い、採択済みとはしない。

ファイル指定とディレクトリ指定は、package.bnt の扱いも異なる。ファイル指定では隣の設定を読まず、依存のパッケージを使えない。同じディレクトリ以下のモジュールの import はできる。ディレクトリ指定では、そのディレクトリを root として package.bnt と main.bnt を使う。test/fmt の収集など残る細則と変更箇所は第7節へまとめる。動的な対象の裸の相対形は別判断 Q11/R17 とし、既存の基準のディレクトリから読む案を維持する。この決定から対象の起点まで変更済みとは扱わない。

`{root}` は依存の中でも入口側を指す。依存パッケージ自身の場所とは区別し、ライブラリの資源は範囲や値の引数で渡す。依存が使えるのはプロジェクトとしての検査/実行だけになる。

| パス変数 | 値・位置付け | 状態 |
|---|---|---|
| root | 元の入口指定から決まるディレクトリ。ディレクトリ指定の test で見つけた各ファイルも指定元の root を引き継ぐ | 名前・起点は回答済み。上書きを加えない案は Q13 |
| cwd | 既存の「基準のディレクトリ」。CLI run は起動時の作業ディレクトリ、テスト/埋込みは実行ごとに与えた値。Process.workingDirectory と同じ値 | 定義を維持する案。OS の current_dir を後から読み直さない |
| home | 起動側の固定したホームを ~ で表す | 利用者と結び付け、サーバ自身の HOME で代用しない案 |
| work・tmp | 起動側が明示する実行ごとのディレクトリ | 供給・字句規則は Q04・Q14 |
| secrets | 起動側が明示する有限の対象一覧 | 導入時期と CLI の細則は Q14 |

入口の選択は作業ディレクトリに依存しないが、裸の動的対象は cwd に依存する。run で root/cwd が同じでも静的な被覆で同一視しない。ディレクトリ指定で main.bnt を起動する手本を使えば、リポジトリ直下からの通常の起動では両者を揃えられる。別の場所から絶対パスで起動した場合には再び分かれる。

### 2.2 パターンと動的な対象の書き方・相対形

パターンは操作の上限を記述し、対象は実際に渡された一つのパスである。両方で名前の解析を共有するが、裸の相対形の既定を別々に決める。**パターンの起点と root の名前は回答済み、Q11/R17 は対象**の残る判断である。

| 入力 | パターンでの意味（推す案） | 動的な対象での意味（推す案） |
|---|---|---|
| `/data/a` | 従来の absolute の exact | 従来どおりの絶対パス |
| `/data/**` | 幹を含む tree | 対象に wildcard の意味を与えず、`*` は通常のファイル名の文字として扱う |
| `data/a`、`./data/a` | root からの exact | **その実行の基準のディレクトリ**から解決する |
| `data/**`、`./data/**` | root からの tree | `*` は通常の文字。パターンとしては解釈しない |
| `.` | root 自身の exact | その実行の基準のディレクトリ自身 |
| `{root}`、`{root}/data/a` | root の exact | 明示した root から解決する |
| `{root}/**`、`./**` | root の tree | 対象に tree の意味は与えない |
| `{cwd}`、`{cwd}/data/a` | その実行の基準のディレクトリからの exact | 同じ値から解決する |
| `~`、`~/data/a` | 起動側が固定した home からの exact | 同じ値から解決する新しい明示記法。旧 File に `~` 展開はなく、文字として扱う。At では新たに home と解く |
| `{work}/out/a`、`{tmp}/a` | 当該実行の work・tmp からの exact | 明示した同じ名前で解決する |
| `{secrets}` | 登録した exact/tree の有限の対象一覧全体。導入時期は Q14 | 一覧から一つの対象を自動で選ばず、対象としては拒否する |

パターンの相対形を root から読み、対象の相対形を基準のディレクトリから読む案では、両者の解決結果が異なれば所属検査で拒否する。対象をパターンの起点へ移して検査を成功させない。例えば root が `/srv/root`、基準のディレクトリが `/srv/inbox` の場合、pattern `data/**` と target `data/x` はそれぞれ `/srv/root/data/**` と `/srv/inbox/data/x` になり、所属しない。root のファイルを操作するなら、対象を `{root}/data/x` 又は対応する絶対パスと明示する。

[01-07](../../design/01-spec/01-07-effects.md#io-を行う組み込み関数)、[03-07「共通の規則」](../../design/03-interop/03-07-io-modules.md#共通の規則)、[用語集](../../design/00-overview/00-04-glossary.md) は、旧 File の相対対象をその実行の基準のディレクトリから読む。推す案はこの**対象の起点**を維持する。新しい At でも、受理する共通の正規な裸の相対対象は旧 File と同じ場所を指す。At が旧 File のすべての非正規な字句も受け付けるという意味ではない。リンクや外部からの交換がある実体まで同じであるとの保証にも広げない。

docs/todo の TODO-324 と過去の ADR 0072 は、実行時の許可と対象の相対形を作業ディレクトリから辿り、リンクを解決して照合する方針である。このうち対象の起点は維持する。**静的なパターンと後の方針の裸の相対形を root にする部分は、ADR 0072 の許可パターンの既定とは異なる変更案**であり、ソースの起点は回答済みで、後の方針への対応は Q05 で選ぶ。従来の許可を維持して移す場合は `{cwd}` を明示する。実対象のリンクを解決する権限制御の方針は TODO-324 に残し、字面の所属に置き換えない。過去の ADR は編集しない。

対象の相対形の選択肢は次である。

| 選択肢 | 利点・実用への影響 | 推す判断 |
|---|---|---|
| その実行の基準のディレクトリから読む | CLI 引数の `data/in.txt` が旧 File と同じ場所を指す。root のパターンと異なれば拒否する | **推す**。原則1・2・3 |
| 裸の相対対象を拒否する | 起点の取り違えを早期に示せるが、CLI 引数をそのまま検査できず、絶対化又は明示の名前が必須になる | R17 の独立した制限案として選べる。これによる節約は0〜2時間の直接の見込み |
| root から読む | パターンと短い対象が揃いやすいが、旧 File と同じ文字列の意味が違う | 推さない。S03 の案を撤回する。選ぶなら旧 File との受理差と移行を別に承認する |

#### ディレクトリ指定を手本にする日常の例

【決定の反映】リポジトリの根 `/srv/repo` に package.bnt と main.bnt、作業対象 data/in.txt を置き、main.bnt から同じディレクトリ以下の補助モジュールを import する。リポジトリの根から `benitoite run . data/in.txt` と実行する形を手本にする。型のパターン data/** は `{root}/data/**`、対象 data/in.txt は cwd の下へ解決され、この起動ではどちらも /srv/repo/data を指す。以下は採る規則の結果であり、未実装の変更を実行した記録ではない。

| 指定と起動場所 | 実行の形・設定 | root / cwd | data/** と data/in.txt の所属 |
|---|---|---|---|
| /srv/repo から run . data/in.txt | プロジェクト。package.bnt と main.bnt | 両方 /srv/repo | 成功 |
| /srv/repo から run main.bnt data/in.txt | 単体。隣の package.bnt を読まない | 両方 /srv/repo | 所属は成功。ただし依存や設定の上限は使わない |
| /srv/repo から run scripts/fix.bnt data/in.txt | 単体。package.bnt を読まない | /srv/repo/scripts と /srv/repo | scripts/data/** と data/in.txt が分かれ、拒否 |
| /srv/inbox から run /srv/repo data/in.txt | プロジェクト | /srv/repo と /srv/inbox | repo/data/** と inbox/data/in.txt が分かれ、拒否 |

scripts 配下にスクリプトを置き、作業場所から相対引数を渡す形自体は使える。その用途では `{cwd}/data/**` と起点を明記する案を推す。入口側の data を読むなら対象に `{root}/data/in.txt` を渡す。祖先の package.bnt を遡る方式や範囲の root だけを上書きする方式で、対象を暗黙に移さない。

この手本により、通常のプロジェクトの実行で起点を揃える方法が定まったため、Q11で既定の四案を再び選ばせない。対象の相対形をどう読むか、root/cwd が違う既知の組への警告、対象の正規形は未回答のまま Q11/R17・Q16b・Q17へ分ける。旧 File が ~ やパス変数を展開しない点と、At の射影した絶対パスを渡す必要も変わらない。

#### パターンと対象それぞれの正規形

パターンの相対形は型の表示で `{root}` に揃える。`.` と先頭の `./` だけを略記として受け付け、途中の dot、すべての `..`、空要素、根以外の末尾 `/`、NUL、逆斜線は拒否する。パターンの wildcard は末尾 `/**` だけとする。`a/../b` も拒否する R02 は、根内だけの正規化を認める対案（追加2〜6時間の直接の見込み）と独立に選ぶ。

`~user`、任意の環境変数、独自の `{name}` は展開しない。`{work}` と普通の名前 `work` は別物であり、裸の `work/a` はパターンなら root、対象なら基準のディレクトリから読む。ホームの別名 `{home}` は増やさない。これらの規則は String 全般の補間を変えるものではない。

対象の正規形は **Q17・R23** で独立に問う。推す案は、At の対象にも次の字句規則を適用し、不正な部分を消してから所属を検査しないことである。これは旧 File の受理を狭める変更ではなく、新しい At の受理の条件である。

| 対象の入力 | 推す扱い | 利用者への影響 |
|---|---|---|
| data/in.txt、./data/in.txt、. | 受理し cwd から解く。先頭の ./ 一つと . の別名を解決する | CLI の通常の相対引数を渡せる |
| ../in.txt、a/../b、{root}/../x | .. を相殺可能でも InvalidTarget にする | 一つ上の入力を指す相対 CLI 引数は直接渡せない。起動側が意図した絶対形を供給するか、別のパス変数で明示する |
| ./a//b、a/./b、././a、空文字、根以外の末尾 / | 空要素・途中の dot・余分な末尾を InvalidTarget にする | OS が受け付ける一部の綴りには明示の整形が要る |
| /、{root}、~、{work} | 根自身として受理する | / は末尾 slash の拒否の例外 |
| NUL、逆斜線、非 UTF-8 | R07 と同じく受理領域へ追加しない | OS の全パスを表せるとはしない |

対象の字句と診断の追加確認は2〜4時間を増分へ計上する。対案の、dot・空要素・末尾だけを正規化して受理する拡張は更に2〜6時間、.. も字句で相殺する拡張は更に4〜10時間の見込みである。後者はリンクを含む OS のパス解決と別の対象を指しうるため、その意味も改めて選ぶ必要があり、原則1・2・4から推さない。OS に実際の対象を問い合わせて正規化する案は純粋な At の設計を変え、費用未調査として別に判断する。 字句上の .. の相殺とリンクの解決の違いは、[Rust 公式 Path::components の説明](https://doc.rust-lang.org/std/path/struct.Path.html#method.components)でも確認できる（取得日2026-10-30）。この API を新たに使う実装を決めたという意味ではない。

### 2.3 静的な比較と U1・PathIn の篩

型と被覆の判定はホストのディスク、HOME、基準のディレクトリ、方針を読まない。check の報告で現在の値を採取する処理は、この判定の後の説明用の処理として分け、型の等号や被覆の証拠に使わない。概念上の表現は次とする。名前は説明用であり、実装宣言の確定ではない。

```text
PathBase  = absolute | root | cwd | home | work | tmp
PathAtom  = exact(base, components) | tree(base, components) | secrets
BaseEnv   = パス変数の値の表。単一の絶対ディレクトリ又は secrets の有限の対象一覧
Member(σ, R, p) = p が、σ で解決した R のいずれかの対象に属する
```

`absolute` の意味は従来の `/` からの要素列のままとする。ほかの基準はタグと接尾の要素列で保持する。`secrets` は、登録済みの exact・tree の有限和を表す一つの名前であり、通常のディレクトリの要素列とは分ける。

| 比較 | 静的な結論 | 実行時の結論との関係 |
|---|---|---|
| `{root}/data/a` から `{root}/data/**` | 被覆を認める | どの有効な基準 σ でも所属を保存する |
| `data/**` と `{root}/data/**` | 正規化後は構造上も同じ | 表示だけの違いを型の違いにしない |
| `{root}/data/**` と `/srv/job/data/**` | 被覆を認めない | 当該起動で根が `/srv/job` でも、型検査の結論へ取り込まない |
| `{work}/**` と `{cwd}/**` | 被覆を認めない | 同じ場所に割り当てられた起動でも同じ |
| `{tmp}/**` と `/tmp/**` | 被覆を認めない | `{tmp}` をシステム全体の一時ディレクトリと同一視しない |
| `{secrets}` と `{secrets}` | 被覆を認める | 同じ実行・同じ改訂の一覧を指すことを条件にする |
| `{secrets}` とほかの path 原子 | 被覆を認めない | 方針を知る実行前の照合では一覧を展開して別に比べられる |
| 任意の path 原子から File.Read の Top | 従来どおり認める | `/**` は absolute の原子であり、Top と同一ではない |

異なる基準を検査時に絶対化する対案なら一部の不受理を減らせるが、型の契約・キャッシュ・承認の再利用が実行環境へ依存する。推す案では、実行時の検査で所属を新しく示すか、同じ基準の契約へ揃える。基準が違うという診断は「実際に範囲外」とは説明しない。原則1・2・4に従う。

U1 では `PathIn[R] <: PathIn[S]` を R が S に覆われるときに限り認める。意味は、保持した**解決済みの同じ絶対パス p**について `Member(σ,R,p)` から `Member(σ,S,p)` を導くことである。値の部分型、篩の `targetMember`、File の潜在効果で同じ σ・R を使う。新しい At の入力が相対形や明示のパス変数を含む場合、成功値の射影は解決済みの絶対パスを返す案を **R20** で独立に問う。03-06 の「同じパスを変更せず返す」は、At の入力と返る文字列の同一性を意味しない文言へ改める必要がある。旧 checkPathIn が受理する正規な絶対パスでは返る文字列を変えない。

#### 本体の後の追加検査と、基準の差の警告

03-06 の E0462 は、既知の条件と対象がどの未知値でも所属不良になる場合の拒否である。新しい At でも形式不良は E0459/E0460、同じ起点などで全有効 σ に対する所属不良を示せる場合は E0462 とする。`pattern="data/**"` と `target="data/in.txt"` の起点はそれぞれ root/cwd なので、check の観測値で失敗したことを E0462 の根拠にしない。σ が変われば所属する場合があり、単に基準が違うだけでは全環境での不良を示せない。

**Q16b** では、このような直接呼出しのリテラル又は既存の const 取得で分かるパターン・対象の組へ、基準が違うという静的警告を出す案を推す。条件は、両方を正しく解析でき、単一の起点が確定し、その名前が違うこととする。Top・secrets の一覧・未知/間接の呼出しは対象外とし、既存の取得形と予算、標準/依存の警告の抑制を保つ。主文の候補は `this path pattern and target use different path bases`、note に root/cwd と「解決先によって所属する場合がある」、help に意図した起点の明示を示す。自動修正や必ず失敗するという説明はしない。check の観測値による成否は参考の表示へ分ける。手本どおりリポジトリの根からrun .で起動してroot/cwdが同じでも、data/**とdata/in.txtをリテラルで書けば起点名が違うため警告が出る。

追加は2〜6時間の直接の見込みである。警告の符号は未割当とし、実装計画で診断表と照合する。通常の JSON diagnostics の warning として受理し、--deny-warnings では同じ符号で error・checkError・complete=false・終了2とする。通常の警告だけなら status=ok・complete=true・終了0。専用の JSON の版を追加せず本体の版変更にまとめる。対案は警告せず At の Error のみとすることで、2〜6時間を省くが、CLI の動的な引数だけの場合と同じく実行まで起点差に気付きにくい。追加の補助命題は解析した起点名の相違であり、所属不良を結論にせず、主定理の前提は増やさない。

String に付けた長さの条件や文字列の連結だけから、この所属を得る規則は追加しない。必要な専用の所属述語の意味と証拠の規則を篩型の `Pred.targetMember` に置く。PathIn 自体は U1 のとおり不透明な保持型として残す。RequestIn の保持する要求・endpoint は、このパスの変更のために置換しない。

### 2.4 純粋な検査へパス変数の値を渡す方法

現行の `Scope.checkPathIn` は `ValueCtx` だけを受け、IO の services を読まない。基準を追加するだけで同関数から HOME や cwd を読むと、この境界が変わる。次の選択肢を独立に判断する。

| 方法 | 利点・費用 | 判断 |
|---|---|---|
| 純粋な check に暗黙の実行基準を読ませる | 呼出しは短い。全 delta・const 評価・キャッシュの意味を実行基準で添字付けし、固定前の評価を禁じる必要がある | 推さない。実行環境の依存がソースの引数にも効果にも出ない |
| 記号同士だけを純粋に比較し、IO で解決する | 元の純粋 API と文字列の保持を使いやすい | 絶対パスの外部入力と相対の契約を検査しにくく、旧 File へ射影した文字列を渡す意味も分かれやすい |
| **固定した基準の不透明な値を明示的に渡す** | 環境の取得と純粋な所属検査を分ける。入口で一度取得し、多くの検査へ使える | **推す**。原則1・2・4・6。新しい API と、実行の基準に対応する値だけを発行する不変条件を費用へ含める |

API の仮名は `Process.pathBases() -> Scope.PathBases uses Process.Environment`、`Scope.checkPathAt(bases, pattern, path)`、`Scope.checkPathInAt(bases, pattern, path)` とする。PathBases は許可を与える値ではなく、当該実行の root の解釈を保持する。標準の不透明型とし、ソースで任意の表から作ったり、JSON や外部の関数から偽造したりできない。既存の Process.Environment の処理を差し替えるハンドラも、任意の表からこの値を作れない。

`Process.pathBases()` は、複数のパス変数の値とその実行との対応を保持した検査用の不透明な値を返す。これに対し、既存の `Process.workingDirectory()` は基準のディレクトリ一つを、`Process.scriptDirectory()` は各スクリプトの親のディレクトリ一つを文字列で返す（workingDirectory は Result に包む）。これら既存の二つから任意の表を作り、PathBases の代わりに渡す API にはしない。

旧 `checkPath`・`checkPathIn` は、従来の絶対形式同士の純粋な検査として残す。新しい相対形や記号は At の入口で使う。二つの入口が必要なのは、絶対形式だけで閉じる旧呼出しには実行環境を要求せず、環境依存の検査には明示の引数を要求するためである。既存の絶対パスのプログラムへ Process.Environment を一律に足さない。

```text
// 提案の API の例。検査済みの Benitoite コードではない。
function readInput(input: String) -> Result[String, ScopeError]
  uses Process.Environment, File.Read["{root}/data/**"]
  bind bases <- Process.pathBases()
  bind checked: Result[Scope.PathIn["{root}/data/**"], ScopeError]
    <- Scope.checkPathInAt(bases: bases, pattern: "data/**", path: input)
  // 入口側の data を意図した例。cwd の相対引数を読む契約は {cwd}/data/** とする。
  // checked の Ok の PathIn を File.readTextIn へ渡す。
  // File の IOError と ScopeError の結合は実際の API の例で明示する。
  ...
end function
```

PathBases の取得は実行開始前に固定した値を返し、呼ぶたびに HOME や cwd を読み直さない。取得可能なものは同じ実行の同じ基準だけとする。実行を越えて保存・復元する入口は提供しない。基準が異なる実行の値を使える埋込み API を後に設けるなら、実行の識別と再検査が必要である。Lean でも、任意の `Const.opaque` をこの標準型の値として型付ける旧の抽象化は使わず、当該 σ に対応する発行値だけを型付ける。ここで新たな実行時の許可トークンを導入したとは説明しない。

### 2.5 実行開始・動的検査・IO の対象の照合

実行の準備で、基準の指定を絶対化し、単一のディレクトリ基準のリンクを一度解決して固定する。根自身がリンクの場合も、選んだ実体の絶対名を以後の基準とする。子のパスのリンクはこのとき解決しない。したがって根の選択は確かめるが、根以下の実体の隔離・後からのリンクの交換・rename への耐性を保証しない。同じ実体へ至る別のリンク名を絶対パスの対象として渡しても、解決後の基準の字面に一致しなければ所属しない。`{root}/data/a` など起点を明示した対象なら、そのパス変数の固定した字面へ解決する。裸の相対対象は root ではなく、その実行の基準のディレクトリから解く。

| 基準 | 固定する入力と失敗時の扱い |
|---|---|
| root | 元の入口指定から決まるディレクトリ。実行の形・元の指定・解決済みの root を報告し、モジュール探索と範囲で同じ値を使う。上書きは加えない案を Q13 で問う |
| cwd | **その実行の基準のディレクトリ**。CLI の run は起動時の作業ディレクトリ、テスト・埋込みは各実行へ与える値。Process.workingDirectory と同じ値から一度固定し、OS の作業ディレクトリを後から読み直さない |
| home | スタンドアロンでは起動時の HOME、サーバでは起動側が指定する要求者のホーム。未設定・空・相対形・解決不能を別のユーザーやデーモンのホームで埋めない |
| work・tmp | 当該実行の起動側が明示した二つのディレクトリ。OS 全体の temp を tmp に代用しない。スタンドアロンの仮 CLI `--scope-base=work=<dir>`・`--scope-base=tmp=<dir>` と埋込み API で渡せるようにする。CLI の値は絶対形又は `~` からの明示形を受け付け、起動側の home で解決する。指定先の作成・成果の保存・削除は起動側の責任とし、処理系が暗黙に作成・削除しない |
| secrets | 起動側の登録済み対象一覧。exact のファイルも tree のディレクトリも表せる解析済みの範囲の列。仮 CLI `--scope-base=secrets=<絶対形又は ~/ からのパターン>` の繰返し又は埋込み API で渡す。`~/.ssh/**` などは引用してシェルの展開と区別し、処理系が固定した home で解く。空一覧は仮 CLI の `--scope-base=secrets=` 又は API の空列で明示し、非空指定と混ぜない。方針が実装されたら同じ意味の一覧をそこから供給する。未指定と、明示した空一覧を区別する |

`--scope-base` は対象名の解決の入力であり、File.Read などの許可は与えない。新しい暫定の権限方針ファイルは作らない。サーバの本人確認・承認・保存、既定の秘密の一覧やジョブのディレクトリの管理は docs/todo の TODO-109・110・145・324 の責任に残す。今回、これらのサーバ機構を実装したとは扱わない。

一つの実行が使いうる、展開済みの契約とパターン定数に現れる基準は、利用者コード・依存・テストを含めて準備時に照合する。未束縛ならコードを実行せずに、欠けた基準と必要な指定を示す。動的な文字列にだけ現れる未束縛の基準は、At の検査で理由を付けた `Result.Error` にする。Top に置き換えたり cwd へ退避したりしない。基準を使わない実行には、その基準の指定を求めない。

At の検査は、渡された固定済みの表だけを使う。動的条件と静的添字の裸の相対形は root、対象の裸の相対形はその実行の基準のディレクトリとして、それぞれ絶対形式へ解決してから照合する。成功時は同じ解決済みの絶対パスを PathIn に保持する。`{secrets}` への所属は、与えられた対象が一覧のいずれかに属することとして検査する。対象に `{secrets}` を書いて一覧の一つを勝手に選ぶことはしない。

At の所属失敗は **Q16a・R22** の互換の判断として、既存の `OutsideScope(String,String)` の引数を変更せず、新しい構成子 `OutsideScopeAt(PathScopeMismatch)`（名称は案）を追加する。保持するレコードには元の pattern/target、解決済みの pattern/target、それぞれの起点名（absolute/root/cwd/home/work/tmp）、不合格だった条件の種類（動的条件又は静的添字）を入れる。複数原子の範囲は各原子の解決先と起点名の列で保持する。例えば元入力が data/**・data/in.txt でも、解決先 /srv/repo/scripts/data/**・/srv/repo/data/in.txt と root/cwd を報告できる。secrets の条件は有限の解決済みパターン列と一覧名で保持し、各場所は通常の要約に展開せず詳細で読む。情報フローの分類を取り除く操作にはしない。

旧 API の OutsideScope はそのまま使い、At の形式不良は InvalidPattern/InvalidTarget の優先順を保つ。Show は既存の引用・エスケープ・4096バイト上限を新しい構成子にも適用し、保存データは切り詰めない。閉じた公開 data の構成子追加なので、既存の ScopeError を全列挙した match は修正が必要になる。追加4〜10時間（記録・公開構成子・Show・交換/型付け・互換案内を含む）を見込む。対案は旧二引数へ解決済みの文字列を詰める方法だが、元入力との関係や起点が構造として得られず、旧 API と欄の意味も変わるため推さない。別の At 専用エラー型は既存 match への追加を避けるが、二系列の失敗処理と変換が必要で、更に2〜6時間の見込みである。原則2・3・4から構成子追加を推す。

六つの File の範囲付き IO は、その保持した絶対パスを使う。型付けの σ と IO 側の σ の一致は実行全体の条件に含める。`Http.sendIn` は七つ目として回帰と対象一致を確認するが、path の基準を Http の host に解釈しない。ハンドラが別の対象へ転送した場合は、その転送先の IO の効果を通常どおり残す。

| 論点 | 推す案 | 対案・実用への影響・原則 |
|---|---|---|
| 方針の相対パターンと `.` | ソースと同じ root 基準。同じ解析済みの対象の型へ写す | server exec のときだけ work 基準にする対案は、同じ記述の意味を変える。work は明示する。原則2・3・5 |

`{secrets}` は秘密の型ではない。範囲検査やパスの射影は、値・成功/失敗・宛先に付く情報フローの印を除かない。登録一覧のメタデータや、その所属検査の結果の分類は docs/todo の TODO-323 の入力契約に含める必要がある。今回の篩型だけでその非干渉性を証明したとはしない。

#### check の値・実行開始時の値・保証の文言案

check は型を記号のまま検査した後、root・cwd・home を含め、採取できた**check の時点の値**と出どころを表示する。採取できない値は未確定とする。work/tmp/secrets だけを特別に未確定とする S03 の記述を改める。check で得た値も、後の run の値を固定した証拠にはしない。

run の準備では**その実行に使う固定済みの値**を別の報告として出す。root・cwd・home が check と違っていても、型の字面が同じなら現在の名前だけの `--allow-effects` はそれを止めない。実行準備の表示は標準エラー又はハーネスへ渡す API の報告とし、スクリプトの標準出力に混ぜない。test も入口ごとの値を対応付ける。

| 表示・機械向けの内容の案 | check | run の準備 |
|---|---|---|
| 報告する時点 | check の時点で観測した値。例: `phase=check` | 当該実行のために固定した値。例: `phase=runPreparation` |
| 各パス変数 | 名前・値の種類・指定元・観測できた値又は未確定 | 名前・値の種類・指定元・固定した絶対値。必要な値が欠ければ開始しない |
| 入口の指定と形 | 元のファイル/ディレクトリ指定、実行の形、解決できた root | 同じ情報と固定した root。test の収集元も保存する |
| 契約・対象 | 記号付き bounds と、check 時の σ で解決できた説明用の対象 | 同じ契約と実行時の σ に対する解決先。check 時の値を使ったふりをしない |
| secrets | 登録一覧の名前・状態・件数。通常の要約へ個々の場所を載せない | 同じ区別。一覧の値と改訂は当該実行で固定する |

報告の時点と指定元の構造は篩型本体の JSON の版変更へまとめる。表示用文字列から解析し直させない。check と run の報告の値を比較すれば差は分かるが、現在の run は以前の check の報告を受け取って照合する入口を持たない。**表示を追加しただけで、check と run の σ の一致、承認後の不変性、変更の自動拒否を保証するとは書かない。** その対応を強制するには、承認対象へ σ と契約を結び付け、同じ組を保護して起動するハーネス又はサーバの接続が要る。今回その強制を実装済みにはしない。

Q13 の推す案は、範囲だけを上書きする引数を追加しないことである。ディレクトリの指定は実行の形も選ぶので、元の指定を保存して表示する。`run .` と `run ./main.bnt` は同じソースでも設定の扱いが異なる。この差を表示し、隣の package.bnt を読まないファイル指定には警告しない。root/cwd が常に同じになるとの保証にはしない。

| Q13の選択肢 | 判断と費用 |
|---|---|
| rootの上書き引数を追加しない（推す） | ディレクトリ指定を使い、原内訳の上書き警告の1〜3時間を外す。原則2・5 |
| --rootをディレクトリ指定の別表記として追加 | ファイル指定と併用せず、プロジェクトを選ぶ同じ操作に限定する。推す案へ更に2〜6時間。同じ役割の記法が増えるため推さない |
| 範囲のrootだけを別の場所へ上書き | 入口と範囲の起点を揃える既決定とは異なり、通常の未回答の細則としては採れない。希望する場合は決定そのものの変更として方式と費用を再提示する |

次は **Q12 で選ぶ文言案**であり、設計書は変更していない。

| 改める場所 | 文言の案 |
|---|---|
| 00-01「保証の範囲」の範囲付きエフェクトの段落の後へ追記 | 既存の「情報フロー制御（information-flow control）は実装していない」、その理由と07-01への参照を含む段落は残し、その後へ「絶対形式の範囲の意味は従来どおりである。パス変数を含む範囲は、実行ごとに固定したパス変数の値の表 σ をパラメータとする上限であり、静的検査はその表の絶対値を固定せずに規則への適合を検査する。同じ契約でも σ が変われば絶対パスの対象は変わりうる。」を加える。追記の理由: 原則2・3に従い、契約の一致と解決先の一致を区別するためである |
| 07-01「各機構が保証すること」のエフェクトの行と File の段落 | 「範囲付きの File の操作は、当該実行で固定した同じ σ の下で所属を検査し、成功値に保持した同じ解決済みの絶対パスを使う。絶対形式の範囲の保証は変わらない。パス変数を含む範囲の保証は、その σ の下での字面の上限であり、実体の隔離や許可を意味しない。」 |
| 07-01 の検査報告と後の実行についての段落 | 「検査報告と後の実行の間のソースとパス変数の値の同一性は保証しない。cwd・home・入口の指定などで、同じ範囲の契約でも操作の絶対パスが変わりうる。check の報告は check 時の値、実行準備の報告はその実行の値を示す。名前だけの --allow-effects はこの差を照合・拒否しない。承認した契約・σ・実行対象の同一性の強制は、起動側との別の接続を要する。」 |
| 03-06 の PathIn の射影の説明 | 「pathInValue は成功値が保持する解決済みの同じ絶対パスを返す。旧 checkPathIn の正規な絶対入力は同じ文字列を保つ。新しい checkPathInAt の相対形又はパス変数を含む入力では、入力の文字列そのものではなく、検査した解決先を返す。」 |
| 06-06「実行の前の確認」へ追記 | 「check の報告に出す root/cwd/home 等の値は、その時点の観測値である。パス変数を含む契約を説明するときは起点の名前も示し、実行に用いる値は run の準備の報告で確かめる。run はその報告の後に自動で続行し、人間の承認を待たない。ファイル指定は隣の package.bnt を読まず、そのことへの警告も出さない。実行前に人間の再確認を必須にする場合は、起動側が契約と値を確かめ、保護して渡す手続きが必要である。」 |
| AGENTS.md のコンセプトの保証の範囲 | 00-01 の文言が採択され実装へ反映された変更で、同じ σ への依存と保証の限界を要約へ写す。今回は編集しない |

この提案は「静的な上限」の意味を、絶対値が一定の上限から、σ をパラメータとする上限へ拡張する判断である。既存の絶対形式の保証を弱める判断とは分ける。00-01 の設計原則そのものを変更する案ではない。

### 2.7 形式化と主定理の前提

Lean の意味は、解析済みの不変な基準の表 σ を実行全体のパラメータにする。OS のパスの解決、リンク、HOME の取得、方針の読み込みの正しさを Lean の内部で証明したとはしない。

| 変更する対象 | 証明・前提の案 |
|---|---|
| `Scope.Domain` の path、範囲の所属 | 基準付き exact/tree と対象一覧の名前を追加。`Member(σ,R,p)` は絶対パスに対する意味。基準の列と秘密の一覧は有限の解析済み入力とする |
| `Cover`・`RangeCover` | 同じ基準の被覆の反射・推移・健全性と、すべての有効な σ で解決後の包含が従うことを証明する。現在の `PathPattern.covers_iff` は、任意の要素列の旧領域での完全性である。異なる基準を加えた解決後の意味に対して、その完全性をそのまま主張しない |
| U1 の `Subtype`・`Pred.targetMember`・HasTypeV | PathIn の値の型付けは、同じ σ で所属する保持対象を持つことを要求する。PathBases の値は同じ σ を指す場合だけ型付く。構造の等号と範囲の被覆を分けたままにする |
| 純粋な delta | At の検査の成功から、保持した絶対パスの動的条件と静的 R への所属を示す。`delta_typed` の意味に新しい値と所属が加わる。任意の「正しい根の表」をソースで作れる仮定は置かない |
| 実行の準備と IO | 起動側が選んだ根を一度解決し、同じ σ を検査・保持値・IO へ渡すという条件を明記する。`io_target` は保持した解決済みの同じ対象との一致を要求する。実パスやリンク先の隔離まで結論を広げない |
| 進行・保存・step_sound・効果・対象の健全性 | 状態の整形式に「σ が固定され、必要な基準が与えられる」を加える。`CoreAssumptions` と `TargetAgreement` の区別を保ち、対象の定理は σ の下で所属する観測を結論とする。必要な IO 応答の存在・型も同じ σ の保持値を量化する |
| 表層と交換 | 基準タグ・対象一覧の名前・解決用の値を脱糖と交換で保持し、型付き表層からコアへ同じ所属を保つ。Rust と Lean のパス字句解析・OS の解決そのものは、証明済みとしない |

単に `io_target` の文言を足すだけでは、誤った PathBases を持つ値から狭い PathIn を作れる問題を防げない。発行・delta の成功・値の型付け・σ の固定を先に定義する。追加する信頼条件と主定理の意味の差を、取りまとめの定義・言明・仮定のレビューへ独立に出す。新しい公理や結論の弱化が必要になった場合は、この案を了承済みの変更へ読み替えない。

## 3. TODO-290 の判断の案

### 3.1 return の近似と比較

正常な継続に渡す値と、その本体から返る値を別に持つ。Rust の `returned` を JSON へ足すだけでは、Lean の近似と健全性に対応がない。共通の値の近似の型を作り、正常成分と戻り値成分がそれを共有する案を推す。整数各幅の比較をここで完成し、値の形と所属には篩型本体が実装する共通の表現を再利用する。return 比較のために独立した全値域の解析をもう一つ新設する見積もりではない。

| 経路 | 推す規則と比較の対象 |
|---|---|
| `return e` | e の既存の return・失敗を保つ。e に正常値があればその値を当該本体の戻り値成分へ加え、式の正常成分を Bottom にする |
| 順次実行 | 先行の return を保存し、先行に正常な継続がある場合だけ後続の戻り値と合流する。return 後の番兵値を正常値や戻り値へ混ぜない |
| if・match・guard・短絡 | 到達しうる枝だけを合流する。枝の条件で得た区間を、その枝から返る値へも使う。guard 自身や左オペランドからの return と、枝の正常値を区別する |
| try・Fail・exit | return を Fail として捕まえない。失敗・exit は返る正常値の範囲へ加えない。try/mapError の契約と合わせる |
| lambda・lazy・局所関数などの別本体 | 独立した本体の戻り値を親の戻り値へ合流しない。所有する本体のキーを保つ |
| 本体の末尾 | その本体の正常な最終結果と明示 return を合わせたものを、関数の結果の契約と照合する。本体で推論した結果を宣言した公開契約へ勝手に加えない |
| 未対応・予算超過 | 未知になった戻り値を Bottom と偽らない。既知の帰結と未証明・停止を区別し、受理に使う結果は未証明なら拒否する。警告用の停止と必須の篩の判定の予算は分ける |

Lean の `BaseApprox`、`baseJoin`、`baseThen`、`.abrupt`、予算付き解析と独立入力の結果を、正常成分を消しても戻り値を失わない形に変える。評価関係の `.returned v` に対する所属の健全性を、`EvalPartial`・Block・腕の相互帰納に沿って示す。正常値と警告だけの既存の定理を、戻り値にも適用できると読み替えない。

交換では Integer64 だけでなく、既存の六幅の `returned_widths` も出す。新版の interval-corpus・report では戻り値の欄を必須とし、欠落を Bottom で補完しない。旧版を読む必要があれば明示の変換で unknown とし、新比較に合格した件数へ加えない。期待値、実観測、Lean の結果の三者を照合する。

比較対象は親・独立入力・別本体の正常値と戻り値、キー・候補・停止・予算・保存順である。`return 7` だけの本体は、正常値の Bottom と戻り値の一点7の二つを区別して記録する。全 Top を拒む件数の関門でも、戻り値の非 Top の情報を独立に数える。値を変えた負例、戻り値の欠落、別本体からの混入、早期 return の後の混入を比較器が拒むことを受け入れ条件にする。

理由: 関数の結果の篩の検査に直結するので原則1・2を満たす。正常値と戻り値を同じ欄へ合併する対案は、早期 return の後続を誤って到達可能にしうるため採らない。旧比較を保つ対案では、篩型の結果の契約の根拠が不足する。

### 3.2 外部型の全面的な交換

「全面的」は、外部型が型のどの位置にあっても、それだけを理由に元定義・別本体・独立入力を落とさずに交換し、外部の宣言があるだけでプログラム全体を除外する経路もなくすことを推す。S03 で明示しなかった二つ目の完了条件を加える。

現行の [07-04「01-12 との対応」](../../design/07-quality/07-04-formal-semantics.md#01-12-との対応) と [書出し器](../../../crates/benitoite/tests/desugar_export.rs) は、外部の宣言がある入力全体を `excluded: ["external function"]` として、脱糖の差分・surfaceCheckAll・網羅性の比較から外す。この除外は区間の `externalType` とは別である。**両方とも当該理由による除外0件**を完了条件とし、前者を対象外として残す案は推さない。

外部の関数の内部、Wasmtime の ABI の全変換、GC による回収とゲスト側の所有の全実装の安全性を今回新しく証明する範囲にはしない。しかし、borrow/own の向き・同じ resource の同定・State を持つ署名・外部呼出しの抽象的な規則は、型付けして交換するために必要であり、今回の作業と費用へ含める。単なる構成子一つの追加として12〜32時間に収まるとした S03 の見積もりは撤回する。

| 方法 | 評価 |
|---|---|
| 外部型を消して Unit、整数、通常のデータ型又は Top にする | 型の同一性と入れ子の構造を失うので採らない |
| 既存の opaque 名の文字列に外部型の名前を埋める | 補題の変更は少ない可能性があるが、通常の不透明型との衝突・偽造・資源の分類が表示文字列に依存する。専用の識別表を結局要する |
| **専用の external 型と有限の宣言表を追加する** | **推す**。通常の不透明標準型・型変数・外部型の同一性を分けられる。篩の外側の型としても使える。原則1・2・4 |

Rust の `TyCon::External(BindingId)` の同一性は、解決した型宣言の同一性である。交換では、一入力内で安定した宣言表の番号へ写し、外部型の型ノードにその番号を入れる。別名は同じ束縛へ写し、別宣言を同じ WIT の表示名だけで潰さない。実装の `ExternalTypeSpec` が持つ component・instance・resource の対応も表に記録するが、それだけを言語の型の等号にはしない。

表の出どころには、論理的なパッケージ/モジュールの同定と宣言の位置を使う。手元の絶対パスやインスタンスの生のポインタを型の同一性にしない。重複番号・未知番号・同じ番号への異なる宣言・不正な型引数を読者が拒否する。現行の外部型は型引数を持たないので、この性質を表の kind と整形式性へ書く。外部型が高カインドの型構成子として使えない現行規則を、交換の追加を理由に緩めない。

必要な経路は次である。

| 層 | 今回の対応 |
|---|---|
| Exchange / Release の型 | `external id` を追加し、型の整形式・等号・部分型・型/行/範囲/値の置換・シフトで、閉じた名目型として保つ |
| Surface の型・式と宣言 | 関数の引数/結果、List・record・ADT・辞書・制約・Fail・継続など、Rust が現在受理する入れ子を再帰的に保つ。外部型自体の内部表現は公開しない |
| 外部関数の頭と署名 | 解決した宣言・名前付き引数・署名・境界の型の対応を交換する。外部型を含む署名の State、引数の borrow、戻り値の own、同じ component/resource の対応を保持する。宣言だけで入力全体を除外する分岐を除く |
| Interval の型と未知値 | 外部型を一般の非整数の値の型として保持する。外部呼出しの結果が整数なら宣言の型の Top とし、実際に得た値や呼出し元の観測から本体の解析を狭めない |
| 全比較の manifest・ledger | 区間の `externalType` と、脱糖・表層検査・網羅性の `external function` の両方の除外を0件にする。元定義・別本体・独立入力の数と順、元の予算の状態を比較する。元定義を追加した分だけを数え直し、過去の14件を新しい候補の固定件数にしない |
| 負例と件数の関門 | 古い除外の免除の検査に加え、未知の external 番号・型の差替え・本体の欠落・独立入力の欠落を不合格にする。型を含む入力で警告候補や非 Top の値があっても交換できることを確認する |

#### 外部呼出しを型付けするための接続

[03-10「宣言の形」「照合」](../../design/03-interop/03-10-external-functions.md#照合) に従い、別名と構造の型を展開した署名が外部型を含む場合だけ State を要求する。引数の外部型は borrow、戻り値は own として同じ component/resource へ照合した事実を、型の対応の表に保つ。外部型は01-10のリソース型には含まれないので、通常の with の解放や `isResource=true` を与えない。これらは現在の Rust の照合を読むことで確認した範囲であり、Lean に既にこの接続があるという意味ではない。

現在の `Release/Typing.lean` の PrimKind に、任意の外部呼出しを表す種類はない。State は操作を持たないため、State 付き外部関数を通常の IO の操作に偽装して `io_op` を満たしたとはできない。別の外部呼出しの規則を、固定した宣言表と抽象的な応答関係で与える案を推す。応答関係は同じ外部型の値を返せ、失敗も表し、State 付きの結果を同じ引数から常に同じ値を返す純粋な delta と仮定しない。外部型を含まない関数にも、既存の取り込みなし・実行ごとのインスタンスという条件を保った署名を与える。

必要な条件の候補は「宣言表の整形式」「応答の結果の型」「呼出し可能な引数に応答が存在すること」「外部の IO の対象を生じないこと」である。説明用に external_typed・external_exists・external_no_targets と呼ぶが、正式な欄名と構造体への配分は骨格の試作で決める。borrow/own の位置と resource の同定は、読者が検査する宣言表の条件に置く。借用の寿命やゲストのメモリ安全性を新しい言語の線形型として証明する案ではない。

外部呼出しの結果に現れる不透明な値の型付け、進行・保存・step_sound、State と外部の IO を区別した効果・対象の定理、Surface の呼出し・脱糖の規則を接続する。新しい信頼条件を既存の delta_typed の「値の型が一つ増えた」だけに隠さず、**Q08 と Q15 の承認対象**にする。応答関係だけの過大近似で目的の定理を保てず、ホストの状態を新しい機械状態へ加える必要が分かった場合は、その定義・主定理の前提と費用の差を設計者へ戻す。これを40〜96時間の保証上限にはしない。

閉じた評価に外部の実装が必要な入力は、評価比較では `notClosed` 等の理由を明示できる。しかし、解析比較・型の交換・列挙・脱糖・surfaceCheckAll・網羅性から外部の宣言を含む入力を除く理由にはしない。通常の実 CLI の外部関数の既存の照合と実行の検査も、同じ候補の受け入れへ含める。

### 3.3 篩型本体と共有する作業・形式化

戻り値の近似は、篩型本体の依存する結果の契約、return/try の型付け、通常の値の近似の型を共有する。外部型は、篩を付ける前の型の構成子・同一性・整形式・置換・型の交換・公開型の表示を共有する。外部型の値に長さなどの意味を与えていない measure を許すことと、外部型を篩の外側に保持することは別である。

| 定理・前提 | 変更の範囲 |
|---|---|
| 区間の `NormalSoundness`・`WarningSoundness` と予算付きの健全性 | 既存の保証を保ち、戻り値の所属の命題を加えて証明する。実行結果の `.returned` と同じ本体の結果を結ぶ。未知な呼出しを勝手に定数として扱う仮定を置かない |
| Release の進行・保存・step_sound | external 型と抽象的な外部の値の型付け・置換の各場合を追加する。外部呼出しは署名どおりの結果又は既存の失敗になるという現在の信頼する実装との境界を保つ |
| delta_typed・io_typed・io_exists・release_exists と外部呼出しの条件 | delta_typed・io_typed・io_exists・release_exists が量化する型と値の領域の変化を点検する。外部呼出しは専用の応答関係と条件を追加して接続し、State を落とさず、State を IO の操作とはしない。external は01-10のリソース型へ加えず、release_exists の対象を勝手に広げない |
| 表層検査・脱糖の性質1・網羅性 | external を不透明な名目型として保ち、通常の内部構成子や表現パターンを与えない。篩付きの型を交換から落とすことで性質1の結論を弱めない |
| 有限の全比較 | 型・解析結果・予算・入力集合の一致を確かめる。外部 ABI の全入力に対する安全性の証明や、Rust/Lean の意味保存の一般定理とは区別する |

既存の opaque 名への写しを採る場合にも、external のタグ・表と、通常の型に化けない単射な写しの証明が要る。専用構成子より確実に安いとは未確認であり、更新した40〜96時間の見込みから機械的な節約を引かない。

## 4. TODO-309 の判断の案

### 4.1 警告の条件と文言

IPv4 射影の IPv6 は、上位96ビットが `0x00000000000000000000ffff` の128ビット値である。[RFC 4291 §2.5.5.2](https://www.rfc-editor.org/rfc/rfc4291.html#section-2.5.5.2) を2026-10-30に確認した。現行の対象の検査も `bits >> 32 == 0xffff` で拒否している。パターンを解析して得た閉区間の全体がこの `/96` に入る場合だけ警告する。

| 条件・例 | 扱い |
|---|---|
| 完全一致 `::ffff:127.0.0.1`、同じ意味の正規な `/128` | 警告する |
| 正規な `::ffff:0.0.0.0/96`、その中の `/97`〜`/127` | 警告する。prefix が96以上でネットワークの上位96ビットが一致することを数値で判定する |
| `::/0` など、射影以外の IPv6 も含むもの | この警告は出さない |
| IPv4 互換の形、NAT64、普通の IPv4、DNS の名前 | この警告の対象にしない |
| 非正規の表記・host bits のある CIDR など、解析で不正と分かるもの | 従来の誤りを出す。この警告を重ねて不正入力を受理しない |
| 実行時にだけ決まる動的 pattern | この静的警告を出さない。動的な対象検査の拒否は保つ |

静的に解析できる effect の範囲引数、`Http.RequestIn` の範囲引数、`Scope.checkHost`・`Scope.checkEndpoint`・`Http.checkRequestIn` の条件を対象とする。文字列リテラルと、現行規則で認定する const の参照を使い、一般の文字列の連結を新たに評価する解析は追加しない。同じ元の指定は元の位置で一度だけ報告し、型の具体化や import の回数で増殖させない。標準ライブラリ・依存パッケージの警告を通常の報告から除く現行方針も保ち、この警告の追加だけで全依存の警告を公開しない。

符号は **W0405** を仮割当とする。調査時点の `diag/codes.rs` では W0401〜W0404 が使用済みで、W0405 はなかった。本実装時に並行変更との衝突を再確認する。

```text
warning[W0405]: this host pattern matches only IPv4-mapped IPv6 addresses
  label: no supported host target matches this pattern
  note: Scope.checkHost, Scope.checkEndpoint, and Http.checkRequestIn reject
        IPv4-mapped IPv6 addresses as targets
  help: use an IPv4 address or an IPv4 CIDR to match IPv4 targets
```

日本語の説明は「この host パターンは IPv4 射影の IPv6 だけを表す。対象の検査がこの形を拒否するため、有効な host の対象には一致しない」とする。IPv4 を指定することが意図だと断定せず、IPv4 への自動修正はしない。一つの原子への警告から、同じ行にある他の原子を含めて「この IO は必ず失敗する」とも説明しない。

通常は警告付きで受理する。既知の不良として E0459 にする対案は、現在許される空の契約の記述や実行時の Error を調べるコードを拒否するので推さない。何も知らせない対案は原則1・3・4に対して不足する。`--deny-warnings` を利用者が指定した場合だけ、既存の共通の規則に従って検査を不合格にする。

### 4.2 check --report=json と形式化

警告は既存の `diagnostics` に、`kind: check`・`severity: warning`・`code: W0405`、元の範囲指定の span、label・note・help を載せる。`diagnosticTargets` も通常の対応を使う。警告だけなら `status: ok`・`complete: true`・終了0を保ち、effects・bounds は元の宣言どおりである。範囲を消したり IPv4 へ書き換えたりしない。

`--deny-warnings` では現行の `Diagnostic::deny_warning` に従い、コード W0405 を保ったまま severity を error にし、昇格の理由の note を添える。check の報告は `status: checkError`・`complete: false`・終了2とする。TODO-309 専用の終了状態や JSON の schemaVersion は設けない。診断の追加だけでは欄の形を変えないためである。test の非実行の報告でも同じ元指定を入口へ対応付ける。

Lean の範囲の代数は変えない。IPv4 射影の IPv6 も数学的には IPv6 の集合の要素であり、パターンを空集合や Bottom へ正規化しない。補助命題を置くなら、「このパターンに一致する値は、現行の対象検査が受け入れる host ではない」とする。`Member` の否定や、不可能な腕の除去の証拠へそのまま使わない。進行・保存・`io_target` の前提はこの警告のためには変えない。

| 同じ改造へ合成する | 個別の定義のレビューと、合成した主定理・表層・交換のレビューを両方条件にする。元の四つの主定理や対象の結論を弱めて通さない |

## 7. ファイル指定とディレクトリ指定で実行の形を分ける変更

### 7.1 回答済みの境界と、残る細則

【決定の反映】ファイル指定は単体のスクリプト、ディレクトリ指定はプロジェクトとする。ファイル指定では、シェバン、run を省いた起動、明示の run/check/test/fmt のいずれも隣の package.bnt を読まない。隣にあることへの警告も出さない。単体では依存のパッケージを使えず、入口と同じディレクトリ以下のモジュール及び標準ライブラリの import は使える。ディレクトリ指定では指定先の package.bnt と main.bnt を使い、祖先の設定は探さない。

設定の `--proof-steps`・`--max-call-stack`・`--wasm-memory`・`--wasm-fuel`・`--wasm-transfer` が効くのはプロジェクトのときだけである。単体では CLI→処理系の既定値、プロジェクトでは CLI→入口側の package.bnt→処理系の既定値とする。proof-steps の関数ごとの指定は当該関数で上書きし、依存パッケージの proof-steps は自分の設定を使うという既決定も維持する。設定の構文そのものと判定のステップ計数の本体は S02 側の費用であり、ここでは実行の形による読み分けと出どころの接続だけを数える。allow-effects は設定へ書けない。

### 7.4 testdata とテストの呼出しの棚卸し
