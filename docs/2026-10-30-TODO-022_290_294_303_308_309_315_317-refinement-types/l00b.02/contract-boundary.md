# L00b.02: 公開契約の改訂が必要な箇所

2026-10-31。B_WORK は `2c8b9cc5380dc2956e245cb95d7849ad98c4bcdf`。本書は実装担当の停止報告であり、取りまとめによる契約の改訂・独立レビュー・設計者の判断を代替しない。提供範囲を減らす提案ではない。

## 全 sort の観測と Transport

`.02a` は整数に加え、長さ・大きさ・不変な欄などの観測を、移動・置換の補題とともに追加する指定である。一方、現行の公開欄は次の型を持つ。名前空間は `Benitoite.Release.Refinement` である。

```lean
Transport.values :
  Transport θ Γ Φ Δ Ψ →
  ∀ i a, Γ[i]? = some (some a) → a.IntegerCarrier →
    termSorted Δ (θ.values i)
```

本体は [Transport.lean](../../../formal/Benitoite/Release/Refinement/Transport.lean) の `structure Transport` にある。もう一つの欄 `facts` は `Γ.facts ++ Φ` の像の含意であり、自由変数の全 sort を検査する欄ではない。

この条件は、List の位置の像を一切制約しない。次の命題の匿名の証拠を [boundary-check.lean](boundary-check.lean) で型検査した。

```text
∀ t : Term,
  Transport ⟨Ty.tvar, [], [], fun _ => t⟩
    [some (list Integer)] [] [] []
```

特に t を整数0にも、行き先の空文脈では束縛されない変数にもできる。source の List は IntegerCarrier でなく、source の型に篩はないので facts も空である。これは現在の整数だけの体系の不具合ではない。全 sort の拡張に整数だけの移送条件をそのまま使えないことを示す入力である。

未証明の言明は、全 sort に拡張した `Pred.Sorted` に対する `Pred.sorted_bind` と、それを使用する `Ty.LeQ.bind` / `Ty.LeQ.rawBind` の新しい場合である。例えば、外側の List の長さを同じ長さと比較する条件は、元の文脈で sort が合い、`le_refl` で導ける。上の置換を適用すると、その List の観測位置に整数0や束縛されない変数が来る。sort 不適格を観測失敗として拒否する契約では、移送先の sort を現行の `Transport.values` から導けない。

この長さの条件については、まだ本番に長さの構成子がないため、拡張後の反例を実行してはいない。実行済みなのは、任意の t を現行 Transport が受け入れる命題である。現行の `Ty.LeQ.bind` が偽だとは主張しない。

必要な改訂の候補は、有限構文の sort 判断を固定し、`Transport.values` を全 sort の観測の保存へ広げることである。例えば `Sort`、`Ty.HasSort : Ty → Sort → Prop`、`Term.HasSort : Ctx → Term → Sort → Prop` を定めた後、欄を次の形へ改める。これら三名と署名は**提案**であり、予約名・承認済みの契約・実装ではない。

```text
values : ∀ i a s,
  Γ[i]? = some (some a) → Ty.HasSort a s →
  Term.HasSort Δ (θ.values i) s
```

整数を観測する既存の入口は、この欄の整数の特殊化として保持する。新判断は構文と宣言を検査するものであり、任意の Prop や関数の評価を格納しない。`SubstOk` から新しい欄の証拠を導く義務も、型付き像の観測の補題として同じ変更に含める。`Transport.extend` / `up` / `extendNone`、`Pred.sorted_bind`、`Ty.LeQ.bind` / `rawBind` とそれらの読者は追随が必要である。sort の全分類と不変な欄の宣言表との接続は、取りまとめが完全署名として確定する必要がある。

対案は、既存の Transport を整数だけに残して全 sort 用の別判断と別の置換定理を作る方式である。ただし、既存の LeQ の篩の規則が全 sort の述語を受け取るなら、同じ LeQ に対する現在の `bind` の全称的な言明をそのまま残すことはできない。判断の分割か定理の前提の変更が必要になる。全 sort を L10 へ先送りして今回を完了とすること、整数以外の観測を拒否すること、sort 不適格な像を既定の正常値に変えることは解決にしない。

本件はユーザーの「契約の型・公開の欄を変える必要が出たら、実装を進めずに報告する」と共通依頼文「実装の条件」の公開署名の停止条件に該当すると判断した。公開欄の変更を行う前に停止した。`Transport` の改訂が承認済みの提供範囲の具体化で済むか、主定理への追加判断が必要かは取りまとめがレビューで確かめる。

## 外部宣言表の配置

`.02b` の外部 ID・宣言表・専用応答関係を置く位置も、現在の公開欄の追加を伴う候補がある。

現行 `Program` の欄は `defs`、`cons`、`ops`、`effects`、`classes`、`impls` の六つである。[契約](../l00a.06a/contracts.md)は「新しい六欄の表現。拡張は L00b/L10」とする一方、「依存列と状態の閉じた環境・σ/外部表を含む完全署名」を後続の詳細化へ送っている。公開された `HasTypeVQ` / `HasTypeCQ` の引数には外部表がない。

候補Aは `Program` に `externals : ExternalId → Option ExternalDecl` を追加し、専用応答を新しいモデルの欄として定める方式である。候補Bは外部表を型付け・意味論の明示引数にする方式である。Aは `Program.mk` の公開欄、Bは既存の型付けの公開署名を変更する。新しい外部の判断だけに渡す方式なら、既存の相互判断への接続と、主定理が使う一つの固定表との一致を完全署名で明記する必要がある。ここではいずれも採用しなかった。

専用応答を既存の `Builtins.delta` に隠す案は、計画「全 L 作業の停止条件」の「既存 δ の変更に隠さない」に合わない。精密な外部状態を新設する案も採らない。`ExternalId`・`ExternalDecl`・応答関係の完全署名と配置は、sort の契約と分けて取りまとめへ返す。
