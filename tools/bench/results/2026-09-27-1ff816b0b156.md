## 所見

### 1. 比較対象に対する相対の位置

- CPython 3.9.6（JIT なし）に対して、loop（0.95 倍）と eval（0.87 倍）では速くなり、println ではほぼ同じ（0.98 倍）になった。fib（1.67 倍）、tree（1.56 倍）、lines（2.7 倍）ではまだ遅く、list（9.6 倍）と string（9.2 倍）では大きく遅い。
- OCaml のバイトコード（`ocamlrun`）は、関数の呼び出しと代数的データ型の処理で Benitoite より 1 桁速い（fib 13 倍、loop 14 倍、list 13 倍、tree 8.6 倍、eval 20 倍）。同じく正格評価の関数型の言語をバイトコードの VM で実行する処理系なので、これが VM の設計と値の表現で詰められる余地の目安になる。OCaml は整数をボックス化せずタグ付きの語で表し、参照の数を数えずに GC で回収する。Benitoite は値を Rust の列挙型で持ち、参照を持つ値の複製と解放のたびに参照の数を増減する（ADR 0028、ADR 0078）。
- 文字列と入出力では、Benitoite が OCaml のバイトコードより速い（string 0.40 倍、lines 0.45 倍）。
- println では、Lua（6.37 秒）、Rust（5.04 秒）、OCaml（5.6〜5.9 秒）が Benitoite（1.55 秒）と CPython・Ruby（1.4〜1.6 秒）より大きく遅い。これらの版は一行ごとに出力を書き出していると見られる（OCaml の `print_endline` は一行ごとに出力を送り出す）。比較の条件が揃っていないので、この比較から結論を出さない。比較対象の書き方を揃えるのは今後の課題とする。
- IO の二つの方式の差は、println で 11%（request が遅い）、lines で 2% になった。呼び出しの費用が減った分、方式の差が相対的に大きく見える。

### 2. 遅い部分の原因の内訳と、設計で直せるか

- **命令の振り分けと呼び出しの定まった費用:** 最適化の後は、`Vm::run` の self（命令を一つずつ取り出して振り分ける費用、原型と命令と枠を引く費用）が 34〜61% を占め、`call`・`ret`・`tail_call`・`load_const` が続く。値の複製と解放（参照の数の増減）は 5〜20% に下がった。さらに減らすには、振り分けのループの組み立て（毎命令の原型と枠の引き直しを避ける）を見直す必要がある。
- **コード生成の余分な MOVE:** O2 の担当は、変数を一時のレジスタへ写す MOVE が多い（loop の一回の反復で MOVE が 8 回）と報告した。コード生成でこれを減らせば、振り分ける命令の数そのものが減る。
- **リストと文字列の確保:** list・tree・string・lines では、セルと文字列の確保と解放（malloc と free）がなお 10〜45% を占める。最大常駐メモリも比較対象より大きい（tree 747 MB、OCaml は 104 MB）。値の表現（ADR 0028）とセルの大きさを見直すのは設計の変更になるので、v1 の設計の中で扱う。
- string と lines の分割と検索（`split`、`lines`、`memchr`）は Rust の標準ライブラリの処理で、処理系の側で詰める余地は小さい。

### 3. 言語処理系を学ぶという目的への影響

OCaml のバイトコードとの 1 桁の差は、値の表現（ボックス化と参照の数による管理）と、命令の振り分けの組み立てから来ていると見られる。どちらも VM の設計の中心にあり、設計者が次に読み比べる題材として価値がある。次に取り組む候補は、(a) コード生成の余分な MOVE を減らす、(b) 振り分けのループで原型と枠の引き直しを避ける、の二つで、どちらも設計書の決定（命令の形、値の表現）を変えずに行える見込みである。

### 測定の道具についての注記

- 確保と解放の統計の「解放回数」は、リストのセル、構成子の引数、関数の値の解放だけを数え、文字列（`Str`）と `IoError` の解放を数えない。そのため、println と string・lines で確保と解放の回数が大きく食い違うが、漏れではない（println の最大常駐メモリは 5 MB で増えない）。
- string は List の要素数の上限で抑えられ、約 0.4 秒で 1 秒に届かない。
