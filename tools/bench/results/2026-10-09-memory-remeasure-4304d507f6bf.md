## 測定の構成と再現の条件

作業は R33 と初回リリース版の完了時の測定である。作業ディレクトリは `.`、ブランチは `impl/R33-memory-remeasure`、HEAD は `4304d507f6bf` である。段階 1 の道具と入力の未コミットの変更を含む。本体・Cargo.toml・Cargo.lock の HEAD に対する差分はなく、段階 1 に保存した変更ソースの SHA-256 はすべて一致したため、了承された手順に従い本測定前のビルドと共通検査を省略した。測定後の共通検査は別に実行する。

計算機は Apple M4、32 GiB、Mac16,10、macOS 27.0.1、Rust 1.98.1 である。CPU 型番は段階 1 の `system_profiler SPHardwareDataType -json` の確認を引き継ぐ。通常の環境取得関数が型番を読めないため、生成表の arm64 表示を補った。CPython 3.9.6、Ruby 4.0.7 の YJIT 有無、Lua 5.5.1、OCaml 5.5.1 の bytecode/native、Rust 1.98.1 の 7 構成を使った。CPython は macOS 付属の `/usr/bin/python3` とし、JIT を持たないため JIT 有効の構成を飛ばした。処理系の導入は行っていない。

既定の release、`gc-mark-sweep`、k=1（100%）、要求の下限 4 MiB、stress なし、呼び出し予算 10,000 を基本とする。予算を変えた系列は各行に値を示す。時間には計数用ビルドを使わず、確保統計だけ別の alloc-stats ビルドで取得した。計算機を静かにした状態で、R33、本測定、プロファイル試行を順に実行した。測定同士やビルド・検査を重ねていない。コミット、方式や k の変更、OPEN 本文の更新、ADR の作成は行っていない。

[段階 1 の記録](2026-10-09-r33-trial-4304d507f6bf.md)とその JSON・HTML・入力プランを残した。本測定の入力は了承済みのプランを変更せず使った。string と lines は長さの上限による 1 秒未満の例外である。R12 の同入力の追加入力、ヒープ API の循環 4 形、タスク数の小さいメモリ系列、HTTP の共通 1,000 要求は、長さを揃えた比較または単位測定として 1 秒未満も残す。HTTP の共通要求数・予算 40,000・計算あり・1 クライアントは約 10.16 秒で、目安をわずかに超える。各回を延ばすための待ち時間は加えていない。

時間と RSS の読み方は次のとおりである。

- R33 の実行時間は `bench_run` の `run_nanos` の 10 回の中央値で、検査・脱糖・コード生成を除く。各段の値と各回の停止標本・出力照合・コマンドは付属 JSON に保存した。wall は RSS ラッパーの起動も含み、性能の表には使わない。
- 完了時の主な比較表は CLI の起動から終了までの時間である。「検査を差し引いた近似」は run と check の別々の中央値の差であり、コード生成を厳密に除く値ではない。主表の生の時間標本は既存の `run.py` が出力しないため、表の中央値と再実行コマンドを残した。
- 最大 RSS は、独立した Python ラッパーが対象を一つだけ子プロセスとして起動し、`resource.getrusage(RUSAGE_CHILDREN)` で得た最大値の、10 回中の最大である。ラッパー自身と HTTP クライアントのメモリを含めない。R12・最小実行版の `/usr/bin/time -l` とは取得経路が異なり、細かい差をそのまま方式の差としない。
- 停止百分位は R33 では全実行の停止標本を合わせた nearest-rank、完了時の既存表では各回の百分位の中央値である。R33 の「最大」は全標本の最大、完了時の既存表の「最大」は各回の最大の中央値である。停止 0 回は標本がないことを表し、0 ms の停止を測った意味ではない。
- `live_bytes` は最後の回収で数えた生存量であり、終了時の到達可能量ではない。`peak_heap_bytes` は言語の対象について数えた最大であり、VM の枠・タスク表・確保器の空き領域などを含む RSS 全体とは異なる。

### println の時間増加の候補

最小実行版から direct の時間が約 120% 増えた println では、`tasks::io::boundary` が self 1.4%・total 42.9%、`serve` が 2.3%・31.1%、その中の `serve_inner` が 1.9%・25.9% を占める。これらは同じ呼び出しの入れ子であり、total を加算しない。`tasks/io.rs` の `serve` は要求を取り出して待機状態を検査し、`serve_inner` は引数を読み直し、IO 用の文脈を作り、組み込みを呼び、結果をレジスタへ戻してタスクを起こす。`boundary` は未処理の要求・完了・解放・出力を扱う。行ごとにこの処理を通る費用は追加調査の候補である。

### HTTP のタスク完了とリソース表の走査

計算なしの HTTP では、1 クライアントの `tasks::finish_task` が self 42.0%・total 65.5%、`ResourceTable::remove_waiter` が self/total 23.4% である。8 クライアントは 38.2%・68.2% と 29.7% だった。約 40% と約 25% の費用は、ソース上の全項目の探索と対応する。`remove_waiter` は `finish_task` に含まれるため、total 同士は加算しない。

`vm/dispatch/tasks.rs` の `finish_task` は、タスクが完了するたびに `state.resources.entries` の全項目を走査し、TaskGroup の子を探す。その後 `runtime/io/resources.rs` の `remove_waiter` が再び全項目を走査し、各 waiters を `retain` する。`builtins/funcs/http_server.rs` の `accept` は要求ごとに HttpExchange を登録し、`ResourceTable::finish_release` は解放後も項目を `Released` として残す。表を消すのは実行終了時の `close_all_silently` である。したがって要求数 n に対し表は O(n) に増え、各要求の処理タスクの完了時にその時点の表を O(n) で走査するため、累積の走査量は O(n²) になる。waiters が空でも全項目を訪れる。OS の資源の解放漏れを観測したという意味ではなく、解放済みの状態の記録も毎回の探索対象になる性能問題である。

終了状態の検査を保ちつつ、タスクから関係するリソースを引ける索引、TaskGroup だけの管理、解放済みの状態と活動中のリソースの分離を調べる案とする。今回の 20,000 要求のプロファイルはこの候補を支持するが、要求数を変えた HTTP の比較や改善後の計測は行っていない。`finish_task` の self すべてを一つの走査の費用と断定しない。計算ありでは同関数の self は 1/8 クライアントで 0.2%/1.0%、振り分けの self は 69.5%/67.7% であり、計算の費用で表の探索が相対的に小さくなっている。

### mixed・returns の List.range と欄の確保

mixed の `List.range` は self 9.9%・total 71.4%、`HeapCore::alloc_fields` は self 41.5%・total 47.7% である。returns は 10.2%・62.6% と 40.1%・45.1% だった。この欄の確保は主に range が構築する RRB 木の中にあり、mixed の型の違いの費用や returns の戻りの費用だけを測る負荷とは読めない。

`builtins/funcs/list.rs` の `range` は全整数を一時の `Vec<Value>` に作り、`runtime/list.rs` の `from_values` が 32 要素ごとの葉と親を構築する。`runtime/list/rrb.rs` の `leaf` と `branch` はそれぞれ `alloc_fields` を呼ぶ。`runtime/heap/core.rs` の `alloc_fields` は欄ごとの値の種類・参照を検査し、領域を確保した後に欄を一つずつ書き込む。インライン展開される `allocate` のヘッダ初期化・対象の登録・統計と予算の更新も self に含まれうる。整数の葉では参照の検査の分岐を通るが、既定ビルドで検証用の世代の表を全整数について探索しているとはしない。

mixed は毎回 1,024 要素の range、returns は底で 2,560,000 要素の range を 200 回作るため、全要素の列挙・欄の書き込みを繰り返す。全量の一時 Vec を経由せず、上限とヒープの不変条件を保って葉を順に作る構築器、欄の初期化と登録の手順を調べる候補がある。malloc の self は 6.2%/1.6% にとどまり、alloc_fields の約 40% を malloc だけの問題とはしない。命令やソース行の細かな内訳と変更後の短縮幅は、この関数単位の標本から分けて測れない。

## 採った方式を確定してよいか（案）

案として、初回リリース版の方式にマーク・スイープ、k=1 を採ることを支持する。循環数を増やしても保持量が安定し、10 万タスクでも最大 RSS は約 211 MB、handler の最大停止は約 4.41 ms、調整要求数の HTTP は約 2.64 ms であった。ハンドラやタスクを加えたことにより、保持量が繰り返し回数に比例して増える状態や、第 1 段の約 100 ms を超える停止がこれらの新機能の主負荷で発生する状態は観測しなかった。k を変えた比較は今回行っておらず、k=1 が最適であるという案ではない。

一方、map 約 42.6 ms、tree 約 59.5 ms、string 約 176 ms、lines 約 195 ms の停止と、大きな値を保持する負荷の RSS 1.1〜3.1 GB は残る。短い停止を必要とするサーバまで現行方式で十分とする根拠はない。増分の回収は、最大停止を短くするための別の検討候補として残す案である。初回リリース版の前に必要とするかは、宣言する用途と停止時間の要求を設計者が判断する。現在の単純な HTTP と循環の記録だけから、増分の回収は不要と決めない。特に大きな生きている Map/List と HTTP を組み合わせた負荷は追加の材料になる。

ADR 0277 は参照カウントの数え方と遅らせた解放についての決定であり、今回採った MS には該当しない。その見直しを今回の測定から提案する理由はない。RC を再び候補にする場合には、R12 の遅らせた解放・循環回収の保持量と停止、および新機能を加えた同等の RC 構成が必要である。

これは設計者に示す案であり、方式・k・増分回収の採否を決定していない。CPU プロファイルの取得・集計と原因の所見の補完を終え、今回依頼された記録の補完は完了した。回収と別に、HTTP の O(n²) の全表走査と List.range の欄の確保が性能問題の候補として分かったため、方式の選択だけで全費用が解消するという案にはしない。採否は取得済みの記録に基づく設計者の判断として残す。


## 中間表現の最適化の候補についての所見

fib/loop は振り分けの self が 85.5%/87.2%、trait は 84.3% であり、命令数や呼び出しの費用を減らす候補を調べる材料になる。一方、値の受け渡し・辞書の解決は独立した関数として分かれておらず、let の入れ子の平坦化、return の置換、辞書が決まったメソッドの直接呼び出しの効果は分けて測れない。mixed/returns の欄の確保と HTTP の表の全走査を、これらの変換だけで取り除ける費用とはしない。三つの候補の試作・命令数・変換の有無の比較を別作業にする案であり、優先順位と採否は決定しない。候補ごとの材料は[完了時記録](2026-10-09-first-release-4304d507f6bf.md#中間表現の最適化の候補についての所見)に記す。
