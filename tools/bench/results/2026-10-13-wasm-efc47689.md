## 外部の関数の呼び出しの費用（TODO-232、`wasm_cost`）

空に近い関数を 10,000 回呼んだ一回あたりの時間（Wasmtime の API を直接使う。処理系の経路は含まない）:

| 呼び方 | 一回あたり |
|---|---:|
| インスタンスの作成だけ | 0.67 µs |
| 毎回インスタンスを作る動的な値の呼び出し（今の純粋な外部の関数の形） | 0.71 µs |

処理系を通した一回の費用は、Hash の 0 B の C の速い経路の 13.2 µs から A の 0.25 µs を引いた約 13 µs と見られる（Store の作成と上限の設定、値の変換、VM の経路を含む。内訳は測っていない）。

燃料の単位あたりの時間: 最小のループ（`br` 一つごとに燃料と epoch を確かめる）で 0.32 ns、Fuzzy（実際のコード）で 0.028〜0.055 ns。したがって、燃料 10^10 を使い切る時間は、最小のループで約 3.2 秒、実際のコードで約 0.3 秒である。

## 所見

1. **WASM で書けるか（TODO-212）。** Hash・Regex・Json は三つとも、取り込みのないコンポーネントとして書け、ゴールデンの範囲で A と同じ結果を返した。Regex は resource（外部の型）で正規表現を持てば、一回の照合が A の約 3 倍（0.74 µs と 0.22 µs）で済む。毎回パターンを渡す形は約 77 倍遅く、resource が要る。Json は越え方で結果が分かれた。値の木をまるごと受け渡す parse・stringify は A の 10〜80 倍遅い。文字列から文字列の pretty・validate と、文書を持って一部だけ読む read は A と同じか速い（A は値の木を作るため）。
2. **境界の費用。** 処理系を通した一回の外部の呼び出しは約 13 µs で、Wasmtime の呼び出しそのもの（0.7 µs）より大きい。小さな仕事を何度も呼ぶ使い方（Hash の 0 B、Regex の毎回の照合）では、この固定費が支配する。大きなバイト列は速い経路で 1 MB あたり約 4.5 ms（Hash の計算を含む）で渡せ、動的な経路より 7 倍速く、RSS も 60 分の 1 だった。
3. **Benitoite で書き直す場合（B）。** B は A の約 100 倍遅い（100 KB の parse で 59 ms と 0.58 ms）。TODO-097 の手段 (i)（Unofficial のモジュールを Benitoite で書き直す）は、Json のような構文解析では VM の速さが大きく効く。
4. **上限の既定の値（Q12〜Q14 の材料）。** 線形メモリは、10 MB の Json の C の parse・pretty が約 75 MiB を使い、既定の 64 MiB を超えた。燃料は最大でも既定の 38 %（Hash 32 MiB）で余裕がある。実際のコードで 10^10 は約 0.3 秒に当たる。受け渡しの予算は、動的な経路の `List[Byte]` 6 MB で 89 % に達した。既定の値を変えるかは設計者が決める（docs/todo の項目）。
5. **コンパイルの費用（TODO-228）。** 実際の命令の 64 MiB のコンポーネントは、検査と実行のたびにコンパイルに約 30 秒、最大 RSS 約 1.8 GiB を要する。大きさの上限を下げるか、コンパイル済みのコードの再利用（TODO-047）が要るかを判断する材料になる。

原因の内訳（約 13 µs の固定費の中身など）は見立てであり、CPU プロファイルは取っていない。
