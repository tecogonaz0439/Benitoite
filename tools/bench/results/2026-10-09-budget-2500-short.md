- `remeasure.py` の plan に各条件を 3 行ずつ置き、各行を 1 回実行した。順序は tasks → HTTP 1 クライアント → HTTP 8 クライアントを 3 周。変更前の全標本、ビルド、変更後の全標本の順である。別のウォームアップは行っていない。
- 測定中にビルド・テスト・別エージェントの作業を並行して動かしていない。電源状態とほかのアプリケーションの停止は未確認である。
- 実行時間は `bench_run` の `run_nanos`。検査・脱糖・コード生成は含めない。RSS は `resource.getrusage` のラッパーを使った。
- 各表は 3 回の中央値。HTTP の応答中央値と最大は各実行の全要求から求めた値の中央値であり、3 回を合わせた最大値ではない。応答時間は接続開始から本体読了まで、要求/秒は最初の送信から最後の応答までを Python の `perf_counter_ns` で測る。Python の接続・スレッド・読み出しの費用を含む。

## 所見

tasks の実行時間の中央値は約 0.75% 短くなった。3 標本の短い比較であり、この小さな差から計算の性能が改善したとは断定しない。
計算あり HTTP の応答中央値は、1 クライアントでは変更前の約 26.9%、8 クライアントでは約 26.6% となった。
同じ要求数で、応答時間が約 4 分の 1 になる傾向を確認した。

今回は設計者が決めた定数の変更の確認であり、他言語との比較や CPU プロファイルは実施していない。
処理系の方式・アルゴリズムを変えず、タスクを切り替えるまでの計算量の設定だけを変えた。
この短い測定から、CPU の費用の内訳や新たな最適化の候補は判断しない。
