# R32 検証器と範囲の確かめの省略の評価（2026-10-06）

実装担当による短い測定の記録である。[R32](../../../docs/implement/20-tasks/R32-verifier-evaluation.md) と [ADR 0263](../../../docs/design/decisions/0263-dispatch-loop-locals-and-verifier.md) に従い、本番には検証器とテストだけを加えた。省略を採るかと、省く確かめの範囲は設計者が決める。

本番の `pipeline`・CLI・ランタイムには検証器を接続していない。測定の写しでは `pipeline::compile` のコード生成の後に検証し、受理したプログラムだけを実行する。検証の時間はコンパイルの段に含まれ、`stage1_bench` の `run_nanos` には含まれない。デバッグの VM は候補の箇所を `get` で調べ、release の VM だけが `get_unchecked` を使う。

測定の写しの release は、上記の検証を行うパイプラインから実行するための実験である。公開の `CompiledProgram` を手で作って直接 VM に渡す口を検証済みの型で制限する変更は含めていない。採る場合には、実行を開始するすべての口で検証済みであることを保証する必要がある。

## 検証器が確かめること

1. `main` と `top_fns` の原型の番号。原型ごとの `positions` と `method_traits` の長さ、`num_params <= num_regs`。空の原型は、参照されているかによらず拒む。`main = None` は検査だけのプログラムとして受理する。
2. 定数の子の番号が親より小さいこと、構成子・関数・辞書の番号。定数の構成子の引数の数、定数の関数が捕捉を持たず、定数の辞書が制約の引数を持たないこと。
3. 型クラスの上位、実装の型クラス・メソッド・上位の実装を作る辞書の式、操作と組み込みの参照、ハンドラの節の操作の番号。実装のメソッドと上位の数、辞書の式の実装の引数の数と制約の引数の位置。
4. 組み込みの番号・引数の数・権限が `builtin_decl` と一致すること。組み込みの参照に操作の番号があれば、その操作が表にあること。
5. 全 68 命令の種類、読み書きするレジスタ、引数の並び。`PRIM`・`IO`・`CON`・`CONR`・`DICT`・`PERFORM` の数は各表から読む。空の並びでも始点が窓の終端を越えないこと。
6. `LOADK` の原型内の定数の位置、`GETCAP` の捕捉の位置、`CLOSURE`・`LAZY` の原型と作る側の捕捉の出所。`METHOD`・`TAILMETHOD` の型クラス・メソッド・引数の並びと、それ以外の位置の `method_traits = None`。
7. `JMP`・`JMPF` の跳ぶ先と、`SWITCH` の表と各跳ぶ先。最後の命令から次の命令へ落ちないこと。
8. `HANDLE` の記述と、記述の節の数から決まる関数の並びが窓の中にあること。節の関数の実行時の値の引数の数は、静的に保証したものに含めない。
9. 生存の情報の開始位置・終端・単調性、レジスタの範囲、命令入口のレジスタの昇順、`call_writes` の長さと範囲。`compute_liveness` で再計算し、すべての欄の一致も確かめる。
10. 各原型の `live_in_at(0)` が引数のレジスタだけを含むこと。表と命令の走査、辞書の式の走査に Rust の再帰を使わない。

全体の表の違反には `main`（なければ 0）を原型の番号として記録し、`pc = None` とする。命令に属する違反には、その原型と命令の位置を記録する。`VerifyError::message` は調査用の説明であり、利用者向けの診断の表には加えていない。

## 保証と省略候補の対応

表の ID は、測定の写しの `dispatch.rs` の `SAFETY` コメントの ID と一致する。「省略」は今回の release の写しで省いたもの、「保持」は今回も実行中に確かめるものを示す。

| ID と分類 | 検証器が保証すること | 省略候補と今回の扱い | 対応する変異・テスト |
|---|---|---|---|
| V1 命令と位置 | 全命令の種類、分岐先、末尾からの落ちの禁止 | `execute` の命令の読み出しを省略。跳ぶ先の計算の検査は保持 | 単体の opcode・分岐・末尾のケース、無作為の opcode・sBx の変異 |
| V2 レジスタ | 読み書きの番号と、表の数による引数の並びが `num_regs` の中 | `reg_ref` と `reg_mut` の添字を省略。窓のスライスの作成と引数のスライスは保持 | 全 68 命令、CALL・HANDLE・CON の範囲、空の LIST の終端、オペランドの変異 |
| V3 原型内の定数 | `LOADK` の Bx が原型の `consts` の中で、その値が全体の表の中 | `LOADK` の原型内の定数番号の読み出しを省略 | 原型内・全体の定数番号、Bx の変異 |
| V4 定数の記述 | 子の番号と構成子・原型・実装の番号が表の中で、子は親より先 | `LOADK` の記述と保存した値の表の読み出しを省略。定数を組み立てる中の検査は保持 | Ctor・List・Map・Set・Func・Dict の単体の変異、全体の定数番号の変異 |
| C 呼び出し・捕捉 | 引数の並び、CLOSURE・LAZY の原型と捕捉の出所、GETCAP の番号、METHOD の型クラスと位置 | 呼ぶ関数の値の原型・捕捉・引数の数と、戻り先の状態の検査は保持 | 捕捉の Reg と Capture、METHOD・TAILMETHOD、CALL の範囲、表の変異 |
| H ハンドラと区画 | HANDLE の記述・操作・節の関数の並びの範囲 | 所有、枠の対応、節の値のシグネチャ、再開する状態と継続の使用済みの検査は保持 | ハンドラ・操作の表と HANDLE の数の単体の変異。段 2 の変異の実行は行わない |
| L 生存の情報 | 開始位置とレジスタの範囲・順序、再計算との一致、入口が引数だけを読むこと | 生存の情報の読み出しの検査は保持 | starts・items・live_in_starts・live_in・call_writes・入口の単体の変異、表の長さの無作為の変異 |
| M1 VM の構成 | 検証器だけでは保証しない | 実行中の枠の `size = proto.num_regs` と、窓が初期化済みの領域に収まること。`start_main` と呼び出し・戻り・末尾呼び出しが成り立たせる。窓を作る範囲の検査は保持 | 既存の VM の窓・呼び出し・戻り・伸長のテストと、受理した変異の実行 |
| M2 VM の構成 | 検証器だけでは保証しない | 定数の保存領域の長さは `program.consts.len()`。`RunState::new` が作り、長さを変えない | 既存の定数の保存と回収のテスト、受理した変異の実行 |
| R 実行時の値 | 検証器だけでは保証しない | 下記の実行時の検査をすべて保持 | 既存の VM の不整合・上限・停止のテスト |

M1・M2 は、検証器の保証と組み合わせて候補の範囲を保証する。窓のスライスと要素への参照を命令をまたいで保持する変更はしていない。レジスタの `Vec` を伸ばす経路の後は、従来どおり局所の状態を読み直す。

R20 以降は、ハンドラ・継続・Lazy などで枠を作る経路が増える。採る場合には各経路で M1 と、命令位置・戻り先の不変条件を確かめ直す必要がある。今回の段 1 の変異の実行から、その新しい経路の保証を主張しない。

## 実行中に確かめ続けること

- 区画の所有と現在の区画・枠の存在、窓の初期化済みの範囲、呼び出しの枠の引数の数と窓の大きさ、戻り先。
- 値の種類、実行時の関数の原型と捕捉した値、FIELD の値のフィールド、GETDICT と SUPER の辞書の値の位置。辞書の式の `Super.index` は、制約の辞書の型クラスがこの表にないので、値から確かめる。
- 確保の失敗、文字列・コレクションなどの大きさの上限、呼び出しの入れ子の上限、継続の使用済み、ハンドラと解放の枠の対応。
- Slot のヒープの番号、型ごとの演算の失敗、組み込みの応答と停止、回収の根の保存。

## 検査と変異の結果

本番のテストは [verify.rs の単体テスト](../../../crates/benitoite/src/bytecode/verify.rs) と [統合テスト](../../../crates/benitoite/tests/verify.rs) である。単体では全 68 命令を受理し、表・引数の並び・分岐・捕捉・生存の情報の違反を拒む。誤った別の検査に拒まれても通らないように、違反の説明と原型・命令の位置も確認する。

統合テストはゴールデンテストの入口を辿り、コンパイルできた 158 プログラムをすべて受理した。固定種 `0x32_b017_5eed_0263` の生成器で各プログラムの 10 か所を別々に選び、一回につき一か所を変えた。同じ値を書き直すだけの変異は生成しない。命令の種類・レジスタのオペランド・sBx・Bx・定数番号・位置とメソッドと生存の表の長さまたは開始位置を変える。

| 検査 | 数または結果 |
|---|---:|
| 元のコンパイル済みプログラム | 158、すべて受理 |
| 一か所ずつの変異 | 1,580 |
| 拒否 | 1,538。必ず範囲外にする変異をすべて拒否 |
| 受理 | 42 |
| 測定の写しで実行した元のプログラム | 133 |
| 測定の写しで実行した受理した変異 | 31 |
| 実行から除いた元のプログラム・変異 | 元の 25、変異の 11 |
| 省略候補の範囲の検査の失敗 | **0** |
| それ以外の内部停止 | 0 |
| デバッグ実行の 5,000 万命令の上限への到達 | 0 |

実行は `TestIo` と Direct の方式を使った。段 1 の命令だけを持ち、`main` があるものに限る。sBx・SWITCH の跳ぶ先、組み込みの番号や種類を変えたものは実行から除く。TestIo でも File.readText の Worker は実際にファイルを読むため、IO の宣言のうち出力・Script.arguments・Process.exit 以外を参照するプログラムも除いた。変異が停止しない場合を防ぐ命令の数の上限と 1 MiB の呼び出しの上限は、測定の写しのデバッグ実行だけに使う。31 変異は、この上限に達さずに実行を終えた。

測定の写しの検査の失敗は `r32-range-failure:` から始まる `Stop::Internal` で区別する。実行ごとに最初の停止のこの印を数える。計数の口を確かめる対のテストでは、verify が拒む故意の範囲外をデバッグの実行器だけに渡し、失敗が 1 件になることを確認した。本番にはこの口とテストを加えていない。

| 共通の検査 | 結果 |
|---|---|
| 本番の `scripts/check.sh` | 成功。fmt・clippy、通常と GC stress のテスト、仮置きの許可、仕様の集計、ライセンスの全検査が通った（実行ログ `target/r32-check.log`） |
| 測定の写しの `cargo test --workspace --no-default-features --features gc-mark-sweep,heap-verify` | 成功。ゴールデンテストと rustdoc を含む |

機能指定なしの `cargo test --workspace` は、既存の `dead_large_list_is_reclaimed_after_its_last_use` と `suspended_callers_release_old_arguments_and_results_before_collection` の GC のアサーションで失敗した。前者は同じ本番の版でも再現した。`heap-verify` を有効にした共通検査の構成では両方とも通る。これらの既存のテストは本作業で改めていない。

## 機械語の所見

両方の release のライブラリを `cargo rustc -p benitoite --release --lib -- --emit=asm` で出した。追加の道具は導入していない。AArch64 の `dispatch::run_until_exit` に展開した命令の処理を比較した。

本番では命令を読む直前の `cmp x28, x24` と `b.ls` が範囲外の命令位置へ分岐し、LOADK の原型内の定数を読む直前にも `cmp x9, x8` と `b.ls` があった。省略した版では、どちらも比較と範囲外の経路を経ずに、該当の添字でロードする。レジスタの読み書きの範囲外の経路にも、以下の差があった。

| `run_until_exit` の範囲外の説明を参照する箇所 | 本番 | 省略した版 |
|---|---:|---:|
| `pc outside code` | 1 | 0 |
| `register outside current window` | 81 | 0 |
| `constant index missing` | 1 | 0 |
| `constant cache index missing` | 1 | 0 |
| `constant description missing` | 1 | 0 |

これはプログラム全体の文字列の有無だけを数えたものではなく、その文字列を渡す機械語の経路を、振り分けの関数の中で確認した値である。定数を組み立てる別の関数の範囲外の経路は残る。

振り分けの関数のアセンブリは、ラベルと指示を含めて 15,135 行から 8,033 行、`cmp` は 890 箇所から 513 箇所へ減った。これらには値の種類などの判定と、最適化による配置・複製の変化も含まれるため、差をすべて添字の比較の個数として読まない。今回の候補では本番の最適化後にも範囲外の経路が残っており、省略した版で消えた。一つの命令で同じレジスタを二度読む場合など、すでに共通化された検査まで、独立に削減したものとは数えない。

範囲外の `get_unchecked` は未定義動作であり、Vec の伸長は要素の位置を変えうる。2026-10-06 に [slice の一次資料](https://doc.rust-lang.org/std/primitive.slice.html#method.get_unchecked) と [Vec の Guarantees](https://doc.rust-lang.org/std/vec/struct.Vec.html#guarantees) で確認した。NoGcCtx の寿命が Vec の伸長まで防ぐという前提は置かない。

## 二つの版のビルドと本測定への引き継ぎ

実装担当の写しとビルドは `target/r32-unchecked/` に残してある。差分は本番の版に対するものであり、本番の検証器とテストを取り込んだ後のコミットへ適用する。

```sh
# 本番の作業ディレクトリの根で実行する。
cargo build --release -p benitoite --example stage1_bench --example verify_bench --target-dir target/r32-checked-build

# 写しを残した場合の測定の版。
cargo build --release -p benitoite --manifest-path target/r32-unchecked/Cargo.toml --example stage1_bench --example verify_bench --target-dir target/r32-unchecked-build

# 写しを消した場合は、本番のコミットを同じ根の target 以下へ展開して差分を適用する。
mkdir -p target/r32-unchecked-source
git archive R32_PRODUCTION_COMMIT | tar -x -C target/r32-unchecked-source
git apply --directory=target/r32-unchecked-source target/r32-unchecked.patch
cargo build --release -p benitoite --manifest-path target/r32-unchecked-source/Cargo.toml --example stage1_bench --example verify_bench --target-dir target/r32-unchecked-build

# 測定のリビジョンの全テストと、範囲を確かめる実行器の変異の実行。
cargo test --workspace --manifest-path target/r32-unchecked-source/Cargo.toml --no-default-features --features gc-mark-sweep,heap-verify
cargo test --manifest-path target/r32-unchecked-source/Cargo.toml --test verify -- --nocapture
```

オーケストレータは別の枝 `impl/R32-unchecked` にこの差分をコミットし、タグを付ける。本番の版には取り込まない。コミットの記入と本測定は、実装担当の作業の後に行う。

本測定は設計者の確認を得て、ほかのアプリケーションと Codex の作業を止め、同じ機会に測る。fib・loop は gate.py の次の手順で、最小実行版の VM と比較する。

```sh

cargo build --release -p benitoite --manifest-path target/r32-legacy-source/Cargo.toml --target-dir target/r32-legacy-build
python3 tools/bench/gate.py --version r32-checked=target/r32-checked-build/release/examples/stage1_bench --version r32-unchecked=target/r32-unchecked-build/release/examples/stage1_bench --legacy target/r32-legacy-build/release/benitoite --legacy-programs target/r32-legacy-source/tools/bench/programs --iterations 10 --output tools/bench/results/2026-10-06-verify-full.json
```

| 本測定の負荷 | 入力 | 測り方と基準 |
|---|---:|---|
| fib | 35 | gate.py、10 回の中央値。R18 の基準は 1.965 s |
| loop | 15,000,000 | gate.py、10 回の中央値。R18 の基準は 1.060 s。最小実行版に届くかも判定 |
| tree | 22 | 両方の stage1_bench を `--factor 100 -- tools/bench/programs/tree.bnt 22` で 10 回ずつ交互に実行し、run_nanos の中央値 |

検証だけの時間は各入力の `.bnt` に verify_bench を適用し、実行の段と分けて記録する。本測定の結果、比較のコミット、本番と最小実行版の相対の位置を、この記録に追記する。

## 本測定（2026-10-06、オーケストレータ）

設計者の了承を得て、ほかの Codex の作業を止めて測った。Apple M4・32 GB、release。fib・loop は `tools/bench/gate.py`（10 回、各版を交互に）で、最小実行版の VM（`d4668a9^`）、R18 の版、R20 の作業中の版と同じ機会に測った。tree・eval は二つの版の `stage1_bench` を交互に 10 回ずつ走らせた。時間は実行の段（`run_nanos`）の中央値である。省いた版の時間には、読み込みのときの `verify`（約 0.35 ms）が `pipeline::compile` の中で加わるが、実行の段には含まれない。

| 負荷 | 本番の版 | 省いた版 | 省いた版 ÷ 本番の版 | 最小実行版の VM |
|---|---:|---:|---:|---:|
| fib(35) | 1.983 s | 2.103 s | 1.061 | 2.055 s |
| loop（1,500 万回） | 1.064 s | 1.024 s | 0.962 | 0.996 s |
| tree(22) | 1.794 s | 1.842 s | 1.027 | — |
| eval(30,000) | 1.468 s | 1.435 s | 0.978 | — |

同じ機会の R18 の版は fib 1.961 s、loop 1.062 s だった（本番の版と VM のコードは同じ）。生の標本は [2026-10-06-r20-r32-gate.json](2026-10-06-r20-r32-gate.json)（gate.py の出力）と [2026-10-06-r32-tree-eval.json](2026-10-06-r32-tree-eval.json) にある。

範囲の確かめを省くと、機械語の範囲の外への分岐は 81 箇所から 0 箇所になったが、時間は負荷によって 2〜4% 速くも 3〜6% 遅くもなり、一貫した改善はなかった。loop は最小実行版の VM の 1.028 倍まで縮むが、届かない。遅くなった負荷は、コードの配置の変化によるものと見る（推測。プロファイルでは確かめていない）。範囲の比較と分岐は、分岐予測が当たり続けるので、命令ごとの費用のうち小さな部分にすぎない（相談の第 2 回の予測「改善なし〜中程度」と合う）。

設計者は、範囲の確かめを省かないと決めた（2026-10-06）。検証器とそのテストは本番に残す。

## 採る場合に必要な変更

本測定の後、設計者は省略を採らないと決めた（上の「本測定」）。以下は、将来改めて採る場合の手順として残す。
