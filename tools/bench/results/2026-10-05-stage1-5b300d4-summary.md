## 再利用

RC の `reuses` は、mixed（10,002 回、確保の約 0.1%）を除いて 0〜2 回（list では 1,350 万回の確保に対して 2 回）だった。また、参照の増減を省いた回数 `rc_elided` は、すべてのワークロードと構成で 0 だった。改良した参照カウントの二つの改良（増減を省くことと、その場での再利用）が、どちらもほぼ働いていない。その場での再利用（`CONR`）はこれらのワークロードではほとんど働いておらず、RC と RC-noreuse の差は誤差の範囲である。`CONR` を生成する条件（F15）と、再利用できる場面がワークロードにあるかは、別に確かめる必要がある。

|---|---:|---:|---:|

参考: CPython 3（JIT なし）の fib は 1.27 s（`run.py` の記録）。

初回リリース版の VM は、最小実行版より 5〜6.6 倍遅い。値の大きさ・確保器・コード生成も変わったので、この差をメモリの管理の方式の効果とは扱わない。CPU プロファイル（fib・list・tree・eval、両方式）の所見は次のとおり。

- `read_many` が呼び出しのたびに引数を `Vec` に集めている。`Vec::from_iter` が呼び出し先を含めて全体の 13〜25%、`malloc` が 9〜14% を占める。
- 枠の引き直し（`RunState::frame`・`absolute`。VM に方式ごとの違いはなく、プロファイルでの関数への割り当ての差である）が、全体の 7〜11% を占める。`reg_mut`・`write`・`read_one` の範囲の確かめも重い。
- 回収の関数（`mode::collect`）は、list-ms でも 10% 程度にとどまる。

ADR 0269 の決定 1・2 は、振り分けのループの局所の状態（ADR 0263）で最小実行版より速くなると見込んでいた。今の VM はその見立てに達していない。原因はメモリの管理ではなく、呼び出しの引数の受け渡しと枠の参照の作り方にある。方式の比較は同じ VM の上の相対比較なので有効だが、絶対値の改善は R09 の振り分けのループの見直しとして別に扱う必要がある。

## 案（設計者の判断の材料）

- **暫定に採る方式の案: マーク・スイープ。** すべてのワークロードで RC より速い（5〜171%）。循環の回収の停止の合計も 8〜15 倍短い。ただし今回の比較は、改良がほぼ働いていない参照カウント（`rc_elided` が 0、再利用がほぼ 0）との比較である。fib・loop の 5〜6% と string の 57% の差は、増減の素朴な費用である（string は 1,600 万回の増加に対して減少 32 回、解放 0）。参照カウントの実装の成熟度の差を含みうる。RC の利点は、生きている大きな構造を保つ負荷での停止の短さ（tree で 0.27 ms 対 102 ms）と、list・roots での最大 RSS の小ささである。HTTP のサーバを想定して停止を重く見るなら RC にも理由があるが、list の 135 ms の連鎖の解放があり、停止の短さは負荷による。
- **k の案: 1（既定のまま）。** k=2 は list で 6%、tree で 2% 速いが、roots の最大 RSS が 43% 増える。k=0.5 は最大 RSS を 15〜20% 減らすが、list で 4% 遅い。
- **RC を採る場合:** 遅らせた解放の条件は、list の長い連鎖を一度に解放しないよう、解放の量に上限を設ける見直しが要る。循環の回収の閾値は、循環の負荷での停止（大きなリストで 15.8 ms）を見て見直す。
- **停止の長さ:** マーク・スイープの最大停止（list・tree で約 100 ms）は、サーバの応答時間としては長い。第 2 段（R33）で、インクリメンタル化や世代の回収の要否と合わせて測り直す。
- **8 バイトの値（OPEN-065）:** 算術の結果はすべて符号付き 63 ビットに収まった。loop の累積では 31 ビットに収まる割合が 50%、47 ビットが 90% だった（counts の記録）。振り分けのループの費用の大きさを考えると、値の大きさより先に、上の呼び出しと枠の参照の改善を検討する価値がある。

- 呼び出しの回数の予算（タスクがない）。
