時間と RSS の読み方は次のとおりである。

- R33 の実行時間は `bench_run` の `run_nanos` の 10 回の中央値で、検査・脱糖・コード生成を除く。各段の値と各回の停止標本・出力照合・コマンドは付属 JSON に保存した。wall は RSS ラッパーの起動も含み、性能の表には使わない。
- 完了時の主な比較表は CLI の起動から終了までの時間である。「検査を差し引いた近似」は run と check の別々の中央値の差であり、コード生成を厳密に除く値ではない。主表の生の時間標本は既存の `run.py` が出力しないため、表の中央値と再実行コマンドを残した。
- 最大 RSS は、独立した Python ラッパーが対象を一つだけ子プロセスとして起動し、`resource.getrusage(RUSAGE_CHILDREN)` で得た最大値の、10 回中の最大である。ラッパー自身と HTTP クライアントのメモリを含めない。R12・最小実行版の `/usr/bin/time -l` とは取得経路が異なり、細かい差をそのまま方式の差としない。
- 停止百分位は R33 では全実行の停止標本を合わせた nearest-rank、完了時の既存表では各回の百分位の中央値である。R33 の「最大」は全標本の最大、完了時の既存表の「最大」は各回の最大の中央値である。停止 0 回は標本がないことを表し、0 ms の停止を測った意味ではない。
- `live_bytes` は最後の回収で数えた生存量であり、終了時の到達可能量ではない。`peak_heap_bytes` は言語の対象について数えた最大であり、VM の枠・タスク表・確保器の空き領域などを含む RSS 全体とは異なる。

採り直した CPU プロファイルでは、回収の total は list 約 20%、map 約 31%、handler の二つの形約 14%、cycle 約 10% だった。停止合計/実行の割合とも概ね対応する。fib・loop・eval の回収は 0 回で、これらの差を回収の費用としない。fib と loop はともに 12 回・1,056 bytes の確保であり、振り分けの self は約 86%/87%、call の self は約 14%/12% である。呼び出し前の中断の印と予算の検査は call に含まれ、関数として分かれていないため分けて測れない。

## 所見 3：言語処理系を学ぶ目的への影響

VM を改めた後は、R12 の回収をしない負荷の時間が大きく短くなった。一方、永続コレクション、IO の経路、継続、型検査の費用は残る。これらは、値の共有・根の走査・中間表現から出す命令・イベントループの公平さを、具体的な負荷で学ぶ題材である。優先する候補は、数値の大きさだけでなく、契約を保ったまま変えられることと、測り直して費用を確かめられることから設計者が選ぶ。今回の記録から実装言語の変更や JIT の導入を提案する根拠はない。

### HTTP のタスク完了とリソース表の走査

計算なしの HTTP では、1 クライアントの `tasks::finish_task` が self 42.0%・total 65.5%、`ResourceTable::remove_waiter` が self/total 23.4% である。8 クライアントは 38.2%・68.2% と 29.7% だった。約 40% と約 25% の費用は、ソース上の全項目の探索と対応する。`remove_waiter` は `finish_task` に含まれるため、total 同士は加算しない。

`vm/dispatch/tasks.rs` の `finish_task` は、タスクが完了するたびに `state.resources.entries` の全項目を走査し、TaskGroup の子を探す。その後 `runtime/io/resources.rs` の `remove_waiter` が再び全項目を走査し、各 waiters を `retain` する。`builtins/funcs/http_server.rs` の `accept` は要求ごとに HttpExchange を登録し、`ResourceTable::finish_release` は解放後も項目を `Released` として残す。表を消すのは実行終了時の `close_all_silently` である。したがって要求数 n に対し表は O(n) に増え、各要求の処理タスクの完了時にその時点の表を O(n) で走査するため、累積の走査量は O(n²) になる。waiters が空でも全項目を訪れる。OS の資源の解放漏れを観測したという意味ではなく、解放済みの状態の記録も毎回の探索対象になる性能問題である。

終了状態の検査を保ちつつ、タスクから関係するリソースを引ける索引、TaskGroup だけの管理、解放済みの状態と活動中のリソースの分離を調べる案とする。今回の 20,000 要求のプロファイルはこの候補を支持するが、要求数を変えた HTTP の比較や改善後の計測は行っていない。`finish_task` の self すべてを一つの走査の費用と断定しない。計算ありでは同関数の self は 1/8 クライアントで 0.2%/1.0%、振り分けの self は 69.5%/67.7% であり、計算の費用で表の探索が相対的に小さくなっている。

mixed の `List.range` は self 9.9%・total 71.4%、`HeapCore::alloc_fields` は self 41.5%・total 47.7% である。returns は 10.2%・62.6% と 40.1%・45.1% だった。この欄の確保は主に range が構築する RRB 木の中にあり、mixed の型の違いの費用や returns の戻りの費用だけを測る負荷とは読めない。

`builtins/funcs/list.rs` の `range` は全整数を一時の `Vec<Value>` に作り、`runtime/list.rs` の `from_values` が 32 要素ごとの葉と親を構築する。`runtime/list/rrb.rs` の `leaf` と `branch` はそれぞれ `alloc_fields` を呼ぶ。`runtime/heap/core.rs` の `alloc_fields` は欄ごとの値の種類・参照を検査し、領域を確保した後に欄を一つずつ書き込む。インライン展開される `allocate` のヘッダ初期化・対象の登録・統計と予算の更新も self に含まれうる。整数の葉では参照の検査の分岐を通るが、既定ビルドで検証用の世代の表を全整数について探索しているとはしない。
