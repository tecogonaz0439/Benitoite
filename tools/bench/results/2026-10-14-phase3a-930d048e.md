## CLI 全体の時間と最大 RSS

各セルは「実時間 ms / 最大 RSS MiB」である（1 MiB = 1,048,576 B）。`combined` は一つのスクリプトで複数の宣言を呼ぶ組、`typed`・`adapter` は各経路だけを呼ぶ比較用スクリプトである。numbers 版の `adapter` 行は、スクリプトが狙う経路を示し、その版の実装では動的に呼ぶ。

`—` は計時の標本がない。start は既存の型だけで書いた短い数と Bytes の typed だけを測った。numbers は numbers・flags・maps・records・tuples・variants・nested と short-numbers の adapter が `unsupported-wit-contract`（E1008・E1009・E1010 の範囲の静的検査の失敗）になり、計時から除外された。失敗の時間を成功の時間に混ぜていない。

### adapter から final への固定費の変化

次の差は final − adapter、割合は adapter を基準とする。補助の宣言数は final の独立例で計時した宣言の数であり、CLI の共有の鍵の数を測った値ではない。独立例は宣言ごとに生成・コンパイルを行う。numbers の `flipU64` と `unsignedAlias` のように、CLI では同じ鍵を共有できる宣言も別々に計時する。records と variants は一つの宣言を複数の値で呼ぶため、呼び出し数と宣言数も異なる。

| 契約 | 独立例の補助の宣言数 | 一回の組の差（ms） | 二十回の組の差（ms） |
| --- | ---: | ---: | ---: |
| numbers | 16 | +40.730 (+49.2 %) | +39.788 (+29.4 %) |
| flags | 7 | +15.827 (+59.3 %) | +14.914 (+48.4 %) |
| maps | 3 | +7.837 (+14.0 %) | +8.804 (+3.9 %) |
| records | 4 | +4.674 (+19.6 %) | +4.662 (+18.1 %) |
| tuples | 3 | +4.213 (+20.4 %) | +4.258 (+19.7 %) |
| variants | 4 | +4.376 (+15.5 %) | +3.934 (+12.0 %) |
| nested | 1 | +0.232 (+0.8 %) | -0.151 (-0.2 %) |
| utf16 | 1 | +0.119 (+0.6 %) | +0.133 (+0.5 %) |
| primitives | 3 | -6.524 (-0.4 %) | +5.312 (+0.3 %) |

numbers・flags・maps・records・tuples・variants は、final の方が adapter より遅い。一回の組の増加はそれぞれ 40.730・15.827・7.837・4.674・4.213・4.376 ms である。二十回の組でも増加は 39.788・14.914・8.804・4.662・4.258・3.934 ms と近く、反復数に比例していない。最大 RSS の増加はこの六契約の一回の組で 0.14〜0.69 MiB に収まる。nested・utf16 と一宣言だけの short-numbers・large-bytes の adapter は、上の六契約ほどの増加を示していない。primitives は一回の組で短縮、二十回の組で延長しており、この差だけで遅延を断定しない。

この差の主因は、Z4 で補助の合成を関数ごとに分け、異なる共有の鍵の分だけ合成とコンパイルが増えたことと推定する。final の実装では、一つの合成に元ゲストを含め、各鍵の初回に `Component::from_binary` でコンパイルしてから同じ実行内で保存する。元ゲストの再検査にもコンパイルがある。同じ鍵を共有する宣言は合成を共有するため、費用は呼び出し数やソース上の宣言数そのものに比例するとは限らない（[合成の準備](../../../crates/benitoite/src/external/adapter/component.rs)、[実行とキャッシュ](../../../crates/benitoite/src/external/adapter/runtime.rs)、[外部の関数の設計](../../../docs/design/03-interop/03-10-external-functions.md)）。

JSON の統計では、adapter と final の経路・転送量・構築量の合計は全契約・両反復数で一致し、試行間でも変わらなかった。例えば numbers は両版とも一回の組で adapter 16 回・typed 2 回、引数と戻り値は各 103,002 B、構築量は 918,016 B である。経路変更や転送量の増加では、この 40 ms の差を説明できない。古い adapter 版の `construction_bytes.incomplete_calls` は typed の呼び出しで増えるが、final は全組で 0 であり、この欄の意味も異なる。

ただし、段別計時は final だけであり、adapter の CLI のコンパイル時間・回数を直接測っていない。JSON の `routes` は呼び出し数であって合成数ではなく、`construction_bytes` も合成数ではない。そのため、Z4 が差の何 ms を占めるかは確定できず、コンパイル増加を主因とする説明は推定である。

| short-numbers | 1 | +2.665 | +21.07 % | +2.02 |

## 段別計時（isolated_costs）

### 比較に使える範囲

JSON の `limits` に従い、次の値は CLI 全体の内訳として扱わない。final の小さい独立入力だけを測った値である。準備・生成・コンパイルは関数・経路ごとに一度だけ測り、Component を同一プロセスで保持する。呼び出しごとに新しい Store とインスタンスを作る。`cold` はその関数・経路の最初の入力の呼び出し、`same-session` は続く呼び出しであり、インスタンスの再利用ではない。

`call` は Wasmtime の canonical ABI の変換と post-return を含む。typed と dynamic の比較では同じゲストの同じ書き出しを呼ぶ。補助と dynamic の比較では同じ書き出しの仕事を、補助を合成した Component と元の Component で呼ぶ。

G8 の High 1 に対応して、typed／dynamic のホスト変換・転送量・構築量は独立例では `null` である。typed／dynamic の JSON から Val への変換や例固有の復号を、処理系の動的変換の時間として扱わない。補助の `host_pack_nanos`・`host_decode_nanos` との大小比較も行わず、未測定を 0 として合計しない。

## CPU プロファイルの要約

この二つの JSON には CPU プロファイルがなく、本記録の作成でも取得していない。Cranelift のコンパイルは段別計時で測っているが、CLI の起動・静的検査・入力作成・ホスト変換の CPU 時間の比率は分からない。

## 所見

- 性能の関門は fib・loop とも改造の前より遅くなっていない。外部の関数を使わない VM の実行段では今回の関門を通った。
- CLI 全体では、numbers・flags・maps・records・tuples・variants が adapter より遅い。一回と二十回の増加が近く、経路・転送量・構築量は変わっていない。Z4 で関数ごとの合成とコンパイルが増えたことを主因と推定する。final の段別計時でも生成・合成より Cranelift のコンパイルの方が大きい。ただし adapter の段別計時を欠くため、原因の定量的な分離はできない。
- start と final の typed の比較では、短い数の固定費が約 2〜3 ms、大きい Bytes の起動と入力準備を含む固定部分が約 31〜41 ms 増えている。繰り返しの呼び出し時間の増加とは分けて扱う必要がある。
- 段別計時では、補助を合成した Component は元の Component よりコンパイル・インスタンス化の費用が大きい。typed と dynamic の call の比較は同じ書き出しで行えるが、処理系のホスト変換を含む経路全体の比較はできない。特に flags の補助の復号には、call より長い時間がかかる例があった。
- 補助の Bytes は numbers の動的な変換より転送量と RSS を減らした。一方で補助の初回コンパイル、転送バッファ、言語の値の構築には費用が残る。小さいスカラーと大きい可変長の値では、改善する費用と増える費用を分けて判断する必要がある。ほかの言語の処理系との相対の位置は、この測定では評価していない。
- 学習の材料としては、関数ごとの合成が宣言間のインスタンス数の干渉を避ける代わりに、元ゲストを含むコードのコンパイルを増やす点を追える。性能を直す際は、別の宣言を追加しても既存の関数が資源上限に達しないという Z4 の目的を保って比較する。
