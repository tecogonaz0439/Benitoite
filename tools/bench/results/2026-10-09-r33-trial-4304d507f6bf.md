## R12 のヒープ API の循環 4 形

release の `stage1_heap_bench` でも各一回の測定と `remaining=0` の照合に成功した。

### タスク数と循環数

タスク数の測定は計算を各 1 反復にした。計算時間の測定の 30,000 反復を 100,000 タスクへ流用すると、
一回だけでも約 210 秒の計算となる見込みで、10 回の測定を不必要に延ばす。
全タスクを作り終えるまでゲートを開かないため、1 反復でも指定数の未完了タスクが同時に存在する。

| タスク数 | 各タスクの反復 | 実行秒 | RSS bytes | 0タスクとの差/個 bytes |
| --- | --- | --- | --- | --- |
| 0 | 1 | 0.000139 | 17809408 | — |
| 1000 | 1 | 0.001979 | 18972672 | 1163.264 |
| 10000 | 1 | 0.088543 | 36831232 | 1902.182 |
| 100000 | 1 | 4.960905 | 211009536 | 1932.001 |

循環数 1,000,000 と 10,000,000 では、ともに RSS が 25,395,200 bytes、最大ヒープが 4,194,880 bytes だった。
回収は 30 回と 305 回、最後の生存量はともに 576 bytes だった。
この一回の試行では、循環の数を 10 倍にしても保持量が比例して増えなかった。
本測定では 100,000、1,000,000、10,000,000 の三点を各 10 回確かめる。

### RSS の道具の変更と読み方

`/usr/bin/time -l` は `time: sysctl kern.clockrate: Operation not permitted` となり、RSS を出さなかった。
`ps` も実行を拒まれた。Python の `resource.getrusage` は使えたため、`rss.py` を加えた。
一個だけ対象を起動する独立したラッパーから子の最大 RSS を取り、`bench-rss:` 行に出す。
HTTP にも同じ経路を使い、時間切れではラッパーとサーバのプロセス群を終了する。
`BENITOITE_BENCH_RSS=resource` を指定しない既存の `run.py` は、従来どおり OS の道具を使う。

`/usr/bin/true` の試行は 1,048,576 bytes だった。17〜18 MB の値をラッパーに由来する固定の下限とは判断していない。
R12 の OS の道具との値の一致は、この環境では確認できなかった。小さい値の変化は、パイプラインや標準ライブラリの変更も含み、GC 単独の影響として読まない。タスク一個あたりの近似は同じ方式での 0 タスクとの差を使う。
ラッパーの起動は `bench_run` の実行時間に含まれない。CLI の時間の測定には RSS ラッパーを入れない。

## 想定外のことと残した点

1. `/usr/bin/time -l` と `ps` で RSS が取れなかった。独立した getrusage のラッパーで取得できた。過去との測り方の差を記録する。
2. C16 の仮入力、R12 の追加入力は多くが 1 秒未満だった。入力と反復数を調整した。
3. handler 5,000,000 操作は両形で R0901 となった。処理系のクラッシュではなく資源の上限による正常な診断である。深さを増やす案を取りやめ、独立した反復へ改めた。
4. returns は List の長さの上限まで深さを増やしても約 0.10 秒だった。独立した反復を加えた。
5. string と lines は上限まで増やしても 1 秒未満だった。上限による例外を記録して既存の比較用入力を残す。
6. HTTP は共通の要求数で全条件を 1〜10 秒にできなかった。共通の要求数と、条件別に調整した要求数の両方を測る。
7. tasks の RSS 測定は、計算用の反復数を流用すると長くなりすぎる。専用の `--task-memory-work` を加えた。
8. 出力の不一致、予期しない終了、時間切れ、クラッシュはなかった。除外する比較対象は CPython の JIT 有効の構成だけである。
9. CPU プロファイルは未採取である。samply 0.13.1 の存在は確認した。本測定とは別に取る。
10. 中間表現の最適化の有無の比較は、候補の変換を実装する別の作業が必要である。この試行は現在の実装だけを対象にする。
11. musl と glibc の比較は同じ Linux の計算機を要し、今回の macOS では行っていない。U4 の配布の確認の後の分として残す。

## 未決事項についての所見

OPEN-036 の方式の確定は、この短い試行からは提案しない。
循環数を増やした際の保持量は安定していたが、大きな値を作る試行では tree で約 66 ms、
string で約 106 ms、lines で約 223 ms の停止があった。
HTTP の計算タスクは整数を更新するだけで、大きな生きているグラフを保持するタスクではない。
HTTP の停止が数 ms であっても、すべてのサーバの負荷で短い停止となるとは判断できない。
本測定の最大停止・保持量・応答時間を確認し、止めて回収する方式のまま確定してよいか、
増分の回収を検討する必要があるかの案を示す。ADR 0277 は参照カウントの方式についてのもので、今回の MS の測定から見直しの要否を決めない。

OPEN-009 は、同じ入力の R12 と比べる材料と、比較対象との出力の一致を得た。
10 回の測定と CPU プロファイルの後に、相対の位置、遅い部分の原因の見立て、学ぶ目的への影響を整理する。
最小実行版の 8 本との比較では、loop の入力を変えた影響を避けるため、15,000,000 の値も別に残す。

OPEN-067 は、同じ 100,000 操作 × 100 回で tail が 2.520420 秒、saved が 2.697697 秒だった。
差は一回の値で約 7% だが、直接の実行を試した差ではない。
この値から区画の切り離しを省く最適化の効果や採否を断定しない。本測定とプロファイルの後に検討する。
