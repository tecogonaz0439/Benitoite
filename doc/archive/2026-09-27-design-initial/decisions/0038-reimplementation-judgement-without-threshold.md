# 0038. 実装言語の見直しは、数値の基準を置かず、決めた観点で測定結果と費用を並べて判断する

- 状態: 置換済み（[0076](0076-initial-implementation-in-rust.md) により）
- 日付: 2026-09-26
- 関連章: [性能](../07-quality/07-02-performance.md), [ロードマップ](../00-overview/00-03-roadmap.md)
- 関連する未決事項: [OPEN-016](../open-issues.md#open-016), [OPEN-009](../open-issues.md#open-009)

## 背景

最小実行版の完了後に性能を測定し、Go での実装を続けるか、Rust・Zig などで再実装するかを判断する（[OPEN-016](../open-issues.md#open-016)、[ロードマップ](../00-overview/00-03-roadmap.md)）。OPEN-016 は、判断基準を決める必要があるとし、基準には性能だけでなく、Go に依存して設計した部分を設計し直す費用と、go.* の層を廃止または置き換える費用も含めるとしている。

測る前に数値の基準（「CPython の 2 倍以内なら続ける」など）を置けば、結果を見てから基準を動かすことを防げる。一方、測定の前には、どのベンチマークで何が遅くなるか、その原因を設計で直せるかが分からない。

## 決定

継続か再実装かを決める数値の基準は置かない。測定の後に、次の観点で結果を並べた記録を作り、それに基づいて ADR で判断する。

1. 比較対象（CPython、Ruby、gopher-lua、同じ処理を Go で書いたもの）に対する、ベンチマークごとの相対の位置
2. 遅い部分の原因の内訳と、それが Go に固有のもの（computed goto がないこと、境界検査、GC の書き込みバリアなど。[設計メモ](../sources/fp-language-design.md) 9）か、処理系の設計で直せるものか
3. 再実装する場合に設計し直す範囲と、go.* の層・wazero によるプラグイン・`CGO_ENABLED=0` の製品方針を廃止または置き換える費用（[OPEN-016](../open-issues.md#open-016)）
4. 実質的な目的（言語処理系を学ぶこと）への影響（[目的と設計原則](../00-overview/00-01-goals.md)）

測る項目と記録の形は[性能](../07-quality/07-02-performance.md)で定める。

## 検討した代替案

- **ベンチマークの幾何平均が CPython の 2 倍（または 1.5 倍）以内なら続ける、と事前に決める**: 結果を見て基準を動かすことを防げる。しかし、一つの値では、遅さの原因が Go に固有か設計で直せるかを区別できない。設計で直せる遅さを理由に再実装する誤りや、その逆が起こりうる。

## 帰結

- 判断の根拠が、数値の基準ではなく、観点ごとの記録として残る。
- 結果を見てから判断するので、判断が恣意的にならないよう、4 つの観点すべてについて記録を書いてから判断する。
- OPEN-016 は、判断を下すまで未決のまま残す。本 ADR は、判断の進め方を決めたものである。
