# 0005. 外部に作用する処理を直接形式で書き、関数のシグネチャにエフェクトを注釈する

- 状態: 採択
- 日付: 2026-09-26
- 関連章: [構文](../01-spec/01-02-syntax.md), [型システム](../01-spec/01-06-type-system.md), [エフェクト](../01-spec/01-07-effects.md), [コア計算と脱糖](../01-spec/01-12-core-calculus.md), [仮想機械](../02-impl/02-08-vm.md), [ロードマップ](../00-overview/00-03-roadmap.md)
- 関連する未決事項: [OPEN-003](../open-issues.md#open-003)（本 ADR で決着）, [OPEN-009](../open-issues.md#open-009), [OPEN-012](../open-issues.md#open-012), [OPEN-022](../open-issues.md#open-022), [OPEN-024](../open-issues.md#open-024)

## 背景

[ADR 0004](0004-surface-syntax-skeleton.md) で、トップレベルの関数のシグネチャにエフェクトを書くと決めた。エフェクトの書き方は、外部に作用する処理を言語の上でどう表すかによって、構文の骨格ごと変わる。候補は二つある。

- **モナドの `IO[T]`**: 外部に作用する処理は `IO[T]` 型の値を返し、do 記法などで順につなぐ（Haskell 系）。
- **直接形式とエフェクト注釈**: 外部に作用する関数も普通に呼び、関数の型にエフェクトを持たせる（Koka・Flix 系）。

設計メモは、パラダイムを「非純粋・正格ベース（Scala 寄り）＋ Flix 的な効果追跡」とし（[設計メモ](../sources/fp-language-design.md) 1）、エフェクトの最終目標を代数的エフェクトとしている（同 3.3）。一方で、効果型の例として `IO[String]` を挙げ、IO のコンストラクタを公開せず `pure`・`map`・`flatMap` などの操作だけを公開する抽象型を推奨していた（同 3.5、OPEN-003）。

実質的な目的の一つは、設計者が関数型プログラミングを学ぶことであり、モナドはその対象に含まれる。

## 決定

外部に作用する処理は、直接形式で書く。外部に作用する関数も普通の関数として呼び、結果を `let` で束縛する。

関数の型はエフェクトを持つ。トップレベルの関数のシグネチャには、`uses IO` の形でエフェクトを書く。`uses` を書かない関数は純粋である。純粋な関数の中で、エフェクトを持つ関数を呼ぶことは、型検査の誤りとする。

IO は値の型ではなく、エフェクトの名前である。利用者は IO の計算を値として構築したり、パターンマッチで分解したりできない。これにより OPEN-003 の懸念（IO のコンストラクタを公開すると内部表現を差し替えられなくなる）は生じず、OPEN-003 は決着する。

エフェクト多相（高階関数に、純粋な関数とエフェクトを持つ関数の両方を渡せること）の書き方と規則は、[OPEN-022](../open-issues.md#open-022) で決める。

モナドを学ぶ場は、表層構文ではなく、次の三か所に設ける。

1. [コア計算と脱糖](../01-spec/01-12-core-calculus.md)では、値と計算を区別するモナド的なコア言語を定め、表層の直接形式をそこへ脱糖（desugaring）する。
2. 外部に作用する処理の内部表現は、自由モナドによる表現と、VM のオペコードによる表現の両方を試作し、実測して比べてから選ぶ（[設計メモ](../sources/fp-language-design.md) 3.6、OPEN-009）。
3. v1 の型クラスで高カインド型を扱い、利用者が `Monad` を型クラスとして定義できるようにするかを、[OPEN-024](../open-issues.md#open-024) で決める。Option・Result をつなぐ操作は、最小実行版から提供する。

## 検討した代替案

- **モナドの `IO[T]` と do 記法**: 言語の IO を通じてモナドを学べる。操作ごとに、外部に作用するかどうかが `<-` の有無として字面に現れる利点もある。しかし、次の理由で採らない。
  - 外部に作用するコードは、学習データの大半で直接形式で書かれている。モナドの IO が多く使われるのは Haskell と一部の Scala のライブラリである。LLM の誤り（`=` と `<-` の取り違え、`pure` の書き忘れ、`map` と `flatMap` の取り違え、`IO[IO[T]]` の入れ子）を招きやすいと見込まれる。
  - 失敗しうる IO は `IO[Result[T, E]]` の入れ子になり、モナド変換子か、入れ子の match が必要になる。スクリプトでは頻繁に現れる形である。
  - 束縛の構文が `let` と `<-` の二つになり、原則 5（同じ役割の構文を増やさない）に反する。
  - 代数的エフェクトとハンドラを導入する段階で、書き方そのものを変えることになりやすい。
  - [目的と設計原則](../00-overview/00-01-goals.md)は、表層構文を設計者の好みではなく LLM の成功率と読みやすさで選ぶとし、学習の目的は「何を自作するか」で満たすとしている。表層にモナドを採るには、この基準を改める必要がある。
- **モナドの `IO[T]` を抽象型として公開し、直接形式の糖衣を別に用意する**: 同じ役割の構文が二つになる（原則 5）。

直接形式の弱点は次のとおりである。

- 外部に作用する処理を値として扱う（リストに入れる、再試行の関数に渡す）には、引数のない関数で包む必要がある。
- 高階関数のためのエフェクト多相が、最小実行版から必要になる（OPEN-022）。
- 引数の評価順序などが、そのまま副作用の順序になる。評価順序は[評価意味論](../01-spec/01-08-evaluation.md)で厳密に定める。
- 純粋性の保証は型検査だけに基づく。外部に作用する組み込み関数と go.* のラッパーのすべてにエフェクトを付けることが前提になる（go.* を一律に IO として扱う方針は、この前提を守るためのものである）。
- 呼び出しの位置では、その呼び出しが外部に作用するかどうかが字面で分からない。作用の有無は関数単位で `uses` に現れるので、利用者が権限を確認する目的（原則 3）には足りる。

直接形式が LLM にとって有利だという見込みは【要検証】であり、OPEN-012 の測定課題に、外部に作用する処理と Result を組み合わせる課題を含めて確かめる。

## 帰結

- 最小実行版の「IO の型」は、IO エフェクトとその検査を指すことになる（[ロードマップ](../00-overview/00-03-roadmap.md)）。
- エフェクトの段階導入（単一の IO、ケーパビリティ、代数的エフェクト）は、`uses` に書くエフェクトの種類を増やす形で進められる。ケーパビリティの細分化（例: ファイルの読み取りだけ）を `uses` と対応させると、権限の表示に使いやすい。
- 型検査器は、最小実行版からエフェクトを型の一部として扱う（[型システム](../01-spec/01-06-type-system.md)、[エフェクト](../01-spec/01-07-effects.md)）。
- 内部表現の二つの試作は、最小実行版の範囲で処理系設計（`02-impl/`）の章を書くときに扱う。
