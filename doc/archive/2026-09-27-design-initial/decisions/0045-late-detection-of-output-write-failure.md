# 0045. 標準出力と標準エラー出力への書き込みの失敗は、後で検出してよい

- 状態: 採択
- 日付: 2026-09-26
- 関連章: [エフェクト](../01-spec/01-07-effects.md), [評価意味論](../01-spec/01-08-evaluation.md), [コア計算と脱糖](../01-spec/01-12-core-calculus.md), [ランタイム](../02-impl/02-09-runtime.md)
- 関連する未決事項: なし

## 背景

[エフェクト](../01-spec/01-07-effects.md)と[コア計算と脱糖](../01-spec/01-12-core-calculus.md)は、書き込みの失敗を、`Console.println` などを呼び出した時点で起きる実行時エラーとしていた。[評価意味論](../01-spec/01-08-evaluation.md)の停止の手順は、実行時エラーの後に来るはずだった評価と IO を一つも行わないとしている。

一方、[ランタイム](../02-impl/02-09-runtime.md)は、標準出力と標準エラー出力への書き込みをバッファに溜めて、まとめて書き出す。この方式では、書き込みの失敗は書き出すときまで分からない。失敗した書き込みの後も評価と IO が進み、報告する位置も呼び出しの位置と異なる。仕様と実装の観測できる振る舞いが一致しない。

## 決定

標準出力と標準エラー出力への書き込みの失敗は、書き込みの関数を呼び出した時点ではなく、後で検出してよい。処理系は、失敗を検出した時点で、書き込みの失敗による実行時エラーとして停止する。この報告は、ソース上の位置を持たない。失敗を検出するまでに行った評価と IO は、取り消さない。

処理系は、失敗を遅くともプログラムを終える前の書き出しで検出する。書き出す時期（バッファが満ちたとき、終える前など）は処理系の設計で定める。

## 検討した代替案

- **書き込みのたびにすぐ書き出す**: 失敗を呼び出しの時点で検出でき、仕様を変えずに済む。しかし、書き込みのたびにシステムコールが起き、多くの行を出力するスクリプトが遅くなる。標準出力への書き込みが失敗するのは、パイプの読み手が先に終わった場合など限られた場合である。
- **行ごとに書き出す**: 失敗を行の単位で検出できる。しかし、改行を含まない書き込みでは検出が遅れるので、仕様の例外は結局必要になり、性能も落ちる。

## 帰結

- C の標準入出力ライブラリなど多くの言語の処理系と同じく、出力の失敗の検出が遅れうる。
- 標準出力と標準エラー出力への書き込みの失敗は、コア計算の抽象機械の規則ではなく、評価意味論の停止の手順の例外として定める。
- ファイルへの書き込みを加えるとき（v1）は、失敗を呼び出しの時点で検出するかを別に決める。
