# 0010. 型名とモジュール名に一つの名前空間を使い、局所の束縛のシャドーイングを許す

- 状態: 採択
- 日付: 2026-09-26
- 関連章: [構文](../01-spec/01-02-syntax.md), [名前・スコープ・モジュール](../01-spec/01-03-names-modules.md), [代数的データ型とパターンマッチ](../01-spec/01-05-data-types.md)
- 関連する未決事項: [OPEN-012](../open-issues.md#open-012)

## 背景

データ構成子を型名で修飾すると決めた（[ADR 0007](0007-constructors-and-list.md)）ので、ドットの左の大文字の名前は、モジュール（`Console`）を指すことも型（`Shape`）を指すこともある。prelude では、`List`・`String`・`Int` などが型の名前でもあり、関数を収めるモジュールの名前（`List.map`）でもある。型の名前とモジュールの名前を同じ名前空間に置くかを決める必要がある。

また、局所の束縛で、外側にある同じ名前を隠す束縛（シャドーイング）を許すかを決める。値は変更できないので、値を段階的に変換するときに、同じ名前を束縛し直す書き方が現れやすい。

## 決定

1. トップレベルの大文字の名前（型、モジュール、エフェクトの名前）は、一つの名前空間を共有する。型の名前は、同じ名前のモジュールを兼ねる。そのモジュールには型の構成子が入り、prelude の型ではその型を扱う関数も入る（`Shape.Circle`、`List.map`）。同じ名前の型とモジュールを別々に定義することはできない。
2. 局所の束縛（`let`、関数とラムダの引数、パターンの変数）は、外側で見えている同じ名前を隠してよい。同じブロックの中で、先の `let` と同じ名前を束縛してもよい。

## 検討した代替案

### 名前空間

- **型とモジュールの名前空間を分ける**: 型を書く位置では型として、ドットの左ではモジュールとして名前を引く。同じ名前の型とモジュールを別のものとして定義できる。しかし、`Shape` が型としてもモジュールとしても現れるときに、二つが別物でありうると、読み手は定義を探す場所を二つ持つことになる。prelude の `List` のように型とその操作を一つの名前にまとめる書き方と、利用者の型の構成子の修飾を、同じ規則で説明できなくなる。

### シャドーイング

- **同じブロックでの束縛し直しを禁じ、内側のブロックでだけ隠すことを許す**: 同じ名前が同じブロックで別の値を指す混乱は避けられる。しかし、`let text = String.trim(text)` のような段階的な変換を書くたびに別の名前が要る。LLM が学習したコードの多い Rust では、同じブロックでの束縛し直しが普通に使われる。
- **一切許さない**: 名前の取り違えは起きにくくなる。しかし、名前を考える手間が増え、LLM が Rust や ML 系の書き方で生成したコードの多くが誤りになると見込まれる。

シャドーイングによって古い値を誤って使う誤りは、値を変更できない言語では型の誤りとして現れることが多い（変換の前後で型が変わる場合）。型が同じ場合の取り違えは検出できない。この点を LLM が誤りやすいかは【要検証】であり、OPEN-012 の測定で確かめる。

## 帰結

- ドットの左の大文字の名前は、トップレベルの名前空間から一通りに解決できる。型から名前を探す解決にはならない。
- v1 で利用者がモジュールを定義できるようにするとき、型と同じ名前のモジュールに関数を加えられるか（型とその操作を一つの名前にまとめる書き方を利用者に許すか）を、モジュールの設計で決める。
- `Some`・`None`・`Ok`・`Err` は修飾せずに使うので、型の名前にもモジュールの名前にも使えない。
