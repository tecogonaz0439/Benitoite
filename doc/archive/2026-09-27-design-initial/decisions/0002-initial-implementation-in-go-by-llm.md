# 0002. 初期実装は Go で LLM が行い、性能を測定してから実装言語を見直す

## 背景

設計メモ 0.3 は実装言語を Go と決めており、付録A で Rust・Zig・Swift と定性的に比較している。ただし、この比較はベンチマークも試作も経ていない（同 付録A）。一方で、Go 上のバイトコード VM は、computed goto がないこと、配列の境界検査、interface を経由する値表現などのために、C で書かれた同種の処理系より遅くなる可能性がある（同 9）。性能は実測するまで判断できない（OPEN-009）。

また、処理系の実装は設計者が手で書くのではなく、LLM に行わせる。設計書の作成から実装プランの作成までを Claude Code（Claude Opus 5.5）が担う。実装を担う LLM は検討中であり、OpenCode と DeepSeek V4.1 Flash の組み合わせを最有力候補とする。設計者は当初から処理系を手で実装することを想定していない。実質的な目的（関数型プログラミングと言語処理系の学習）は、LLM が書いた実装を読み、必要なときに LLM へその実装を選んだ理由を質問することで追う。

## 決定

初期実装は Go で行う。Go を選ぶ根拠は、設計メモ 付録A の比較（GC をランタイムに任せられること、`go/types` で標準ライブラリのラッパーを自動生成できること、goroutine を使えること）とする。

初期実装は LLM が実装プランに従って行う。設計書と実装プランは Claude Code が作成する。どの LLM がどの部分を実装するかは、実装プランを作る中で決める（[OPEN-017](../open-issues.md#open-017)）。

初期実装の性能を測定した後に、Go での実装を続けるか、Rust・Zig などで再実装するかを決める（OPEN-016）。再実装する場合も LLM が行う。

## 検討した代替案

- **最初から Rust で実装する**: 性能の上限は高いと見込まれる。しかし、GC を自作するか GC クレートに頼る必要が生じやすく、Go の標準ライブラリを自動でラップするという設計（3層ライブラリの go.*）の前提が成り立たない（設計メモ 付録A）。性能を測る前に、この二つを失う判断はしない。
- **最初から Zig で実装する**: GC を完全に自作する必要があり、1.0 前で言語仕様が変わりうる（設計メモ 付録A）。
- **実装言語を Go に固定する**: Go 上の VM が遅すぎた場合に、言語仕様を変えずに処理系だけを作り直す道を閉ざしてしまう。

## 帰結

- 言語仕様（`01-spec/`）を実装方式に依存させない規約は、実行方式の差し替えだけでなく、実装言語の変更にも備える意味を持つ。
- 再実装する場合、Go に依存して設計した部分（GC をランタイムに任せること、go.* の層とラッパー自動生成器、wazero によるプラグイン、`CGO_ENABLED=0` の製品方針）は作り直すか廃止することになる。go.* の名前空間は言語仕様に現れるので、再実装の判断は言語仕様にも影響する（OPEN-016）。
- 実装プランを作る LLM と実装する LLM が別になりうるので、実装プランは、設計書と実装プランだけを読めば実装できる粒度で書く必要がある。
- 目的と設計原則の章でいう「自作」は、既存の OSS を使わずにこのプロジェクトで設計・実装することを意味し、設計者が手で書くことを意味しない。
- 性能を測定する対象・ベンチマーク・判断基準は[性能](../07-quality/07-02-performance.md)で定め、測定の時期は[ロードマップ](../00-overview/00-03-roadmap.md)で定める。
