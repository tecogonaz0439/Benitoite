# 名前解決とモジュール読込

## 目的と範囲

名前解決と、複数モジュールを実行可能な形にまとめる工程。モジュールの識別と探索、依存グラフ、循環検出、型検査の単位（全体を一括で処理するかモジュールごとか）、モジュール間のシンボル参照の接続（リンク）、初期化の実装、インクリメンタル処理を扱う。依存の取得・バージョン選択・ロックは[パッケージ管理](../06-tooling/06-05-package-manager.md)が扱う。

現在の版は、最小実行版（[ロードマップ](../00-overview/00-03-roadmap.md)）の範囲だけを定める。最小実行版のプログラムは一つのソースファイルであり、利用者が定義するモジュールと import はない（[名前・スコープ・モジュール](../01-spec/01-03-names-modules.md)）。そのため、モジュールの探索、依存グラフ、循環検出、リンク、初期化、インクリメンタル処理は、v1 でモジュールを加えるときに定める。本版が定めるのは、prelude の持ち方と、一つのソースファイルの名前解決である。

## 前提

名前の種類、有効範囲、シャドーイング、修飾された名前の解決の規則は[名前・スコープ・モジュール](../01-spec/01-03-names-modules.md)で定める。本章はそれを実装する方法を定める。名前解決は構文エラーのない AST だけを受け取る（[ADR 0019](../decisions/0019-stop-after-failing-stage.md)）。

## 仕様

### prelude

【方針】prelude は、次の二つから成る。

| 部分 | 内容 | 持ち方 |
|---|---|---|
| 組み込みの表 | 基本型、`List`・`Option`・`Result` の型と構成子、中身を見せない型 `IoError`、型を持たないモジュール（`Console` など）、エフェクトの名前 `IO`、組み込みの関数（[コア計算と脱糖](../01-spec/01-12-core-calculus.md)の `b`）の名前・型・Rust での実装 | 処理系の Rust のコードに書いた表 |
| prelude のソース | [標準ライブラリ](../03-interop/03-06-stdlib.md)の表で実装の欄をソースとした関数（`List.map`、`Option` と `Result` の関数など）と、その補助の関数（`mapInto` など）の定義。[コア計算と脱糖](../01-spec/01-12-core-calculus.md)の Σ に含まれる定義に当たる | 言語で書いたソースファイル。処理系に埋め込む（後述） |

組み込みの表は、初期化の後に変更しないので、大域に置いてよい（[ADR 0015](../decisions/0015-shared-program-per-execution-state.md)）。組み込みの関数の型は、型パラメータに付ける制約（等値の型であること、演算子の型の集まりのどれかであること。[型システム](../01-spec/01-06-type-system.md)）を含めて、表に書く。

組み込みの関数には、「prelude のソースの中だけで使える」印を付けられる。印を付けた関数は、prelude のソースの定義を書くために使う内部の操作（リストの先頭を取り出すなど）であり、利用者のプログラムからは見えない。

【方針】prelude のソースのファイルは、処理系のソースコードの中に置き、Rust の `include_str!` マクロで処理系に埋め込む。`include_str!` は、指定したファイルの内容を、コンパイルのときに `&'static str` の値として読み込む（[include_str!](https://doc.rust-lang.org/std/macro.include_str.html)）。prelude のソースのファイルが複数あるときは、ファイルごとに埋め込み、読み込みの段は、ファイルの名前の順にソースの表に加える。表示名は `<prelude>/` にファイルの名前を続けたものとする（[ソース管理と位置情報](02-02-source-and-spans.md)）。

【方針】prelude のソースでは、関数の宣言の名前をモジュールの名前で修飾して書ける。その構文は[字句解析器と構文解析器](02-03-frontend.md)の「prelude のソースの構文」で定める。修飾した関数は、修飾に書いたモジュールに入る。そのモジュールは組み込みの表にあるモジュールでなければならず、なければ prelude のソースの誤り（処理系の不具合）とする。

【方針】prelude のソースの、モジュールの名前で修飾しないトップレベルの関数（補助の関数）は、prelude のソースの中からだけ参照できる。利用者のプログラムの名前解決では、これらの名前を引かない。したがって、利用者のトップレベルの関数が補助の関数と同じ名前（`mapInto` など）を持っても、名前の衝突にならない。二つは束縛の番号で区別する。

【方針】prelude のソースの関数の本体では、名前を次のように引く。

- 修飾しない小文字の名前は、局所の束縛、prelude のソースの補助の関数の順に引く。利用者のトップレベルの関数は引かない。
- 修飾された名前 `A.b` は、prelude の名前の表のモジュール `A` から引く。モジュールには、組み込みの関数、修飾した prelude のソースの関数、「prelude のソースの中だけで使える」印を付けた組み込みの関数が入る。
- 型の名前は、prelude の型だけを引く。利用者の型は引かない。

印を付けた組み込みの関数も、ほかの組み込みの関数と同じくモジュールに属し、修飾して使う。

prelude のソースに書く定義の一覧は[標準ライブラリ](../03-interop/03-06-stdlib.md)で定める。

【方針】最小実行版では、検査のたびに、prelude のソースも利用者のソースと同じく読み込みから型検査までの段を通す。prelude のソースの誤りは処理系の不具合であり、処理系のテストで検出する（[処理系のテスト戦略](../07-quality/07-03-compiler-testing.md)）。

### 束縛

【決定】名前解決は AST を変更せず、次の二つの表を出力する（[ADR 0022](../decisions/0022-side-tables-keyed-by-node.md)）。

| 表 | 鍵 | 値 |
|---|---|---|
| 束縛の表 | 束縛の番号 | 束縛の種類、名前、宣言したノードのノード番号（組み込みの表のものは表の項目）、span |
| 参照の表 | 名前を使う箇所のノード番号 | 束縛の番号 |

束縛の種類は、トップレベルの関数、prelude のソースの関数（修飾した関数と補助の関数）、組み込みの関数、データ構成子、局所の束縛（引数、`let`、ラムダの引数、パターンの変数）、型、型パラメータ、エフェクト変数、エフェクトの名前、モジュールである。

宣言したノードは、束縛の種類ごとに次のとおりである（[字句解析器と構文解析器](02-03-frontend.md)の AST のノード）。トップレベルの関数と prelude のソースの関数は関数の宣言、データ構成子はデータ構成子の宣言、型は型の宣言、型パラメータとエフェクト変数は型パラメータの宣言、引数は引数、`let` の束縛は `let` 文、パターンの変数は変数のパターンのノードである。

名前を使う箇所は、式の名前、名前の型、`uses` の並びの中のエフェクトの名前、構成子のパターンのノードである。修飾された名前は、ドットの右の名前が指す束縛を参照の表に載せる。

束縛の番号は、ノード番号と同じく、検査ごとに持つ数え上げの状態から振る。

### 解決の手順

【方針】名前解決は、次の順に行う。

1. prelude の名前の表を作る。組み込みの表の名前と、prelude のソースの修飾した関数を、モジュールごとに集める。prelude のソースの補助の関数は、モジュールと別の表に集める。続けて、prelude のソースの各関数について、手順 3 と 4 を前述の「prelude のソースの関数の本体」の引き方で行う。
2. 利用者のプログラムのトップレベルの宣言（型、構成子、関数）を集め、トップレベルの名前の表を作る。[名前・スコープ・モジュール](../01-spec/01-03-names-modules.md)の「トップレベルの名前空間」の誤り（名前の重複、prelude の名前との衝突など）と、一つの型の宣言の中の構成子の名前の重複（[代数的データ型とパターンマッチ](../01-spec/01-05-data-types.md)）をここで報告する。すべての宣言を先に集めるので、宣言の順序によらず参照できる。
3. 各宣言の型（引数の型、戻り値の型、構成子の引数の型）と `uses` の名前を解決する。
4. 各関数の本体を、有効範囲の積み重ねを持って辿り、名前を解決する。

手順 3 と 4 は、トップレベルの宣言ごとに独立に行い、ある宣言の誤りは、ほかの宣言の解決を妨げない。

【方針】有効範囲の積み重ねは、関数の本体、ブロック、ラムダ、`match` の分岐に入るときに一段積み、出るときに降ろす。各段は、名前から束縛の番号への表を持つ。`let` は、右辺を解決した後で、束縛した名前を現在の段に加える。同じ段に同じ名前を加えたときは、後の束縛で置き換える（[ADR 0010](../decisions/0010-shared-namespace-and-shadowing.md)）。

名前を引く順序は、[名前・スコープ・モジュール](../01-spec/01-03-names-modules.md)の「修飾しない名前の解決」と「修飾された名前の解決」に従う。パイプとプレースホルダは AST に書かれたままの形で辿る。プレースホルダは名前ではないので、解決しない。

### 誤りと修正案

【方針】名前解決は、次の誤りを報告する。一つの誤りを報告した後も、ほかの名前の解決を続ける。解決できなかった名前は、参照の表に載せない。

- 見つからない名前（修飾しない名前、モジュールの名前、モジュールの中の名前）
- 種類の合わない名前（式の中にドットなしで書いた型の名前など。[名前・スコープ・モジュール](../01-spec/01-03-names-modules.md)）
- 名前の重複（トップレベル、一つの型の宣言の中の構成子、引数の並び、一つのパターンの中、型パラメータの並び）
- 型パラメータの名前がトップレベルの大文字の名前と同じ場合
- 型を書く位置のエフェクト変数とエフェクトの名前（種類の合わない名前の一つ。[型システム](../01-spec/01-06-type-system.md)）
- `uses` の並びの中の、エフェクト変数でもエフェクトの名前でもない名前（型、型パラメータ、モジュールの名前）

【決定】`uses` の並びの 2 番目以降にエフェクトでない名前があれば、それは関数の型の後の `uses` の並びを最長一致で読んだために、型の並びの次の要素が取り込まれたものでありうる。この場合の診断は、`help:` で、`uses` を持つ関数の型を括弧で囲む書き方（`fn((fn() -> Unit uses IO), Int) -> Unit`）を示す（[ADR 0047](../decisions/0047-parenthesized-types-and-uses-binding.md)、[ADR 0035](../decisions/0035-help-suggestions-without-rewriting.md)）。並びの最初の名前であれば、エフェクトの名前ではないことだけを示す。

【方針】見つからない名前の診断には、綴りの近い名前を修正案として示す。候補は、その位置で見える同じ種類の名前（修飾しない名前ならその位置で有効な局所の束縛とトップレベルの関数、修飾された名前なら同じモジュールの名前）のうち、編集距離（edit distance。ここではレーベンシュタイン距離）が 2 以下のものとし、距離の小さいものから最大 3 つを示す。単位を持たない `String.length` などには、[基本型の意味論](../01-spec/01-04-types-basic.md)が定める修正案を示す。`Option` と `Result` のモジュールで見つからない名前が `unwrap` か `expect` であれば、`unwrapOr` と `match` を修正案として示す（[ADR 0043](../decisions/0043-option-result-rust-names-no-unwrap.md)）。

### 型検査の単位

【方針】最小実行版では、prelude のソースと利用者のソースを、一つの単位として型検査器に渡す。型検査器は、その中の関数の本体を一つずつ検査する（[型検査器](02-05-typechecker.md)）。
