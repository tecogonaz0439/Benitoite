## 目的と範囲

メモリの管理、IO 実行器、リソース追跡、panic 境界、実行ごとの状態管理。ホスト関数呼び出しの実行基盤も扱う。具体的には、処理系の外の関数・型を VM に登録する形式、引数・戻り値を渡す実行時インターフェース、オペークハンドルの同一性・生存期間・解放後の利用の扱い、同期コールバックで外部の関数から言語側へ戻るときの VM 状態と呼び出し規約、IO の構築と実行の分離・権限確認・外部の誤りの変換を行う場所である。ホスト関数呼び出しを設けるかは、v1 のライブラリの提供方法とあわせて決める（[OPEN-035](../open-issues.md#open-035)）。複数スレッドからの同時利用（[ADR 0015](../decisions/0015-shared-program-per-execution-state.md)）と、コールバックによる VM への再入とは別の事項として扱う。

現在の版は、最小実行版（[ロードマップ](../00-overview/00-03-roadmap.md)）の範囲だけを定める。対象は、メモリの管理、実行ごとの状態、IO 実行器とハンドラ表、出力のバッファ、資源の追跡、panic 境界、プログラムの実行の流れである。外部の関数・型の登録、オペークハンドル、コールバック、権限の確認は、v1 でライブラリの提供方法とケーパビリティを加えるときに定める（[ADR 0077](../decisions/0077-abolish-go-layer.md)、[OPEN-035](../open-issues.md#open-035)）。

## 前提

IO の関数の振る舞い、出力の順序、プログラムの入口は[エフェクト](../01-spec/01-07-effects.md)で、実行時エラーと資源の不足による停止は[評価意味論](../01-spec/01-08-evaluation.md)で定める。VM の実行の手順は[仮想機械](02-08-vm.md)で定める。

## 仕様

### メモリの管理

【決定】最小実行版は、ヒープに置く言語の値を参照カウントで管理する（[ADR 0078](../decisions/0078-reference-counting-in-minimal.md)）。最小実行版の言語では値どうしの参照が循環しないので、使わなくなった値はすべて回収される。

【決定】ヒープの対象の確保と、対象が指す値を辿る処理は、ランタイムの一か所に閉じ込める。v1 で循環する値を回収する方式を加えるときに、そこを差し替える。長いリストや深い木の値を解放するときは、解放が再帰的に連鎖して処理系のスタックを使い果たさないよう、明示の積み重ねで解放する（[ADR 0078](../decisions/0078-reference-counting-in-minimal.md)）。

v1 で可変のセルを加えると、値どうしの参照が循環しうる。循環する値を回収する方式は【未決】である（[OPEN-036](../open-issues.md#open-036)）。

### 実行ごとの状態

【方針】ランタイムは、実行を一つ始めるたびに実行ごとの状態を作る（[ADR 0015](../decisions/0015-shared-program-per-execution-state.md)）。実行ごとの状態は、VM が使うもの（[仮想機械](02-08-vm.md)）に加えて、次のものを持つ。

| 状態 | 内容 |
|---|---|
| ハンドラ表 | IO の操作から、それを行う Rust の関数への表 |
| 出力のバッファ | 標準出力と標準エラー出力それぞれのバッファ |
| 実行の入力 | コマンドライン引数の並び |
| 実行時エラーの情報 | 実行時エラーまたは資源の不足の種類、止まった命令、呼び出しの履歴の材料（[仮想機械](02-08-vm.md)の「実行時エラーの情報の記録」） |
| 書き込みの失敗の記録 | 標準出力と標準エラー出力それぞれについて、書き出しに失敗したか、失敗の理由（Rust の `std::io::Error` の文字列） |

### ハンドラ表

【方針】IO を行う組み込みの関数（[エフェクト](../01-spec/01-07-effects.md)の「IO を行う組み込み関数」）は、それぞれ一つの IO の操作に当たる。ハンドラ表は、IO の操作ごとに、引数の値の並びを受け取って応答の値か実行時エラーの種類を返す Rust の関数を持つ。

ハンドラ表には次の二つを用意し、実行を始めるときにどちらかを実行ごとの状態に入れる。

| ハンドラ表 | 使う場面 | 内容 |
|---|---|---|
| 本番のハンドラ表 | `run` | 標準出力・標準エラー出力への書き込み、ファイルの読み込み、コマンドライン引数の読み取りを実際に行う |
| テスト用のハンドラ表 | 処理系のテスト、v1 の `test` | 書き込みをメモリに記録し、ファイルの内容とコマンドライン引数を与えられた値から返す |

`File.readText` の本番のハンドラは、ファイルを読めないとき、および内容が正しい UTF-8 でないときに、`Err` を表す値を応答とする（[ADR 0012](../decisions/0012-invalid-utf8-input.md)）。

### IO 実行器

【決定】IO の命令の実行には、直接呼び出しと、要求と応答の二つの方式があり、処理系の内部の設定で切り替える（[ADR 0029](../decisions/0029-two-io-execution-modes.md)）。

【方針】IO 実行器は、VM の実行関数を呼んでプログラムを最後まで実行する部分である。

- 直接呼び出しの方式では、VM の実行関数を一度呼び、VM が命令の実行中にハンドラ表の関数を直接呼ぶ。IO 実行器は、VM が値で終わるか実行時エラーで止まるまで待つ。
- 要求と応答の方式では、VM の実行関数が要求を返して止まるたびに、IO 実行器がハンドラ表からその操作の関数を引いて実行し、応答を渡して VM の実行を再開させる。VM が値で終わるか実行時エラーで止まるまで繰り返す。

二つの方式は同じハンドラ表を使う。どちらの方式を使うかは、利用者向けの CLI のオプションにはせず、処理系のテストとベンチマークから選べるようにする。処理系のテストは、両方の方式で同じ結果になることを確かめる（[処理系のテスト戦略](../07-quality/07-03-compiler-testing.md)）。最小実行版の性能測定の後に、二つとも残し、既定を直接呼び出しとすると決めた（[ADR 0088](../decisions/0088-keep-both-io-execution-modes.md)）。

### 出力のバッファ

【方針】標準出力と標準エラー出力への書き込み（`Console.print`・`Console.println`・`Console.eprintln`）は、それぞれのバッファに溜める。バッファの中身は、書き込みの呼び出しの順に出力に現れる。二つの出力の間の順序は保証しない（[エフェクト](../01-spec/01-07-effects.md)）。

【方針】バッファの中身を書き出すのは、次の二つの時点だけである。

| 時点 | 書き出すもの |
|---|---|
| 書き込みの関数がバッファに追加した結果、そのバッファの中身が 64 KiB（65,536 バイト）以上になったとき | そのバッファの中身すべて |
| プログラムを終える前（後述の「プログラムの実行の流れ」の手順 4。panic 境界で処理系の不具合を報告する前も含む） | 標準出力、標準エラー出力の順に、それぞれのバッファの中身すべて |

【決定】書き出しの失敗は、書き込みの関数を呼び出した時点ではなく、書き出したときに検出する。遅くとも、プログラムを終える前の書き出しで検出する（[ADR 0045](../decisions/0045-late-detection-of-output-write-failure.md)）。

【方針】書き出しに失敗したときは、次のように扱う。

- 失敗を書き込みの失敗の記録に残し、その出力の以後の書き込みは、バッファに溜めずに捨てる。失敗した出力を、もう一度書き出そうとはしない。
- 書き込みの関数の中の書き出しで失敗したときは、そのハンドラは書き込みの失敗の実行時エラーの種類を返す。VM はそこで止まる。この実行時エラーは、ソース上の位置と呼び出しの履歴を持たない（[仮想機械](02-08-vm.md)の「実行時エラーの情報の記録」）。失敗を検出するまでに行った評価と IO は取り消さない。
- 終える前の書き出しで失敗したときの報告は、後述の「プログラムの実行の流れ」で定める。

【方針】Unix 系の OS では、Rust の標準ライブラリが `main` の前に SIGPIPE を無視する設定にし、読み手の終わったパイプへの書き込みは `ErrorKind::BrokenPipe` の誤りになる（[on-broken-pipe](https://doc.rust-lang.org/beta/unstable-book/compiler-flags/on-broken-pipe.html)、2026-09-27 に確認）。処理系はこの既定の設定を変えない。パイプの読み手が先に終わった場合も、書き込みの失敗の実行時エラーとして扱える（[ADR 0079](../decisions/0079-rust-readings-of-go-based-decisions.md)）。

【方針】処理系が標準エラー出力に書く報告（`main` の `Err` の文字列、実行時エラー・資源の不足・処理系の不具合の報告）は、バッファを通さずに、バッファを書き出した後で標準エラー出力に直接書く。報告の書き込みがさらに失敗したときは、それを報告せず、終了状態だけを定めどおりにする。

### 資源の追跡

【方針】呼び出しの情報は VM が実行ごとの状態の中にデータとして持つ（[ADR 0016](../decisions/0016-calls-off-go-stack.md)）。その大きさは、VM が数えて上限を設ける（[ADR 0030](../decisions/0030-call-stack-size-limit.md)、[仮想機械](02-08-vm.md)）。

【決定】最小実行版では、ヒープの使用量に上限を設けない。ヒープが足りなくなったときは、[評価意味論](../01-spec/01-08-evaluation.md)の資源の不足の手順によらずに終わる（[ADR 0044](../decisions/0044-heap-exhaustion-outside-stop-procedure.md)）。終わり方は、メモリの不足がどこで起きるかによって次のように分かれる。

- 処理系のヒープの確保が失敗したとき: Rust の標準ライブラリの既定の振る舞いで、標準エラー出力にメッセージを書いてプロセスを abort する（[handle_alloc_error](https://doc.rust-lang.org/std/alloc/fn.handle_alloc_error.html)）。abort は巻き戻しを伴わないので、下の panic 境界は働かない。終了状態は OS が決め、処理系は定めない（[ADR 0079](../decisions/0079-rust-readings-of-go-based-decisions.md)）。
- 確保が失敗する前に、OS の側でメモリが足りなくなったとき（Linux の overcommit の設定による場合など）: プロセスがどう終わるかは確かめておらず、処理系は終わり方を定めない。

どちらの場合も、出力のバッファに残った内容は書き出されないことがある。

処理系がヒープの使用量に上限を設けるかは、v1 で決める（[OPEN-031](../open-issues.md#open-031)）。

### 一つの操作で作る値の大きさの上限

【決定】一つの組み込みの関数の呼び出しで作る文字列の大きさ（バイト数）とリストの長さに、処理系が上限を設ける。組み込みの関数は、値を作る前に結果の大きさを計算し、上限を超えるときは値を作らずに、資源の不足として[評価意味論](../01-spec/01-08-evaluation.md)の手順で停止する（[ADR 0049](../decisions/0049-size-limit-for-built-values.md)）。

【方針】上限の値は次のとおりとする。最小実行版では、利用者が変える手段を設けない。

| 値 | 上限 |
|---|---|
| 文字列 | 2^30 バイト（1,073,741,824 バイト、1 GiB） |
| リスト | 2^24 要素（16,777,216 要素） |

【方針】上限を確かめる対象は、結果として `String` か `List` の値を新しく作る組み込みの関数（IO を行う関数を含む）と、`CONCAT` の命令のすべてである。上限を超えたときは、資源の不足の種類「作る値が大きすぎる」を返す（[仮想機械](02-08-vm.md)の「組み込みの関数の呼び出し」）。報告には、計算した結果の大きさと上限を含める。

- 結果の大きさは、値を作り始める前に、引数から計算する。計算は Rust の `i64` の溢れを検査する演算（`checked_mul` など）で行う（`String.repeat(s, n)` では、`n` が「上限 ÷ `s` のバイト数」を超えるかで判定する、など）。`String.replace` のように、引数から大きさを求めるのに走査が要る関数は、先に出現を数えてから大きさを計算する。
- `File.readText` は、ファイルを上限より 1 バイト多い分まで読み、上限を超えたら資源の不足とする。
- `List.prepend` と `List.append` も、結果の長さ（元の長さに 1 を加えた値）を確かめる。
- 結果の大きさが引数の大きさを超えない関数（`List.take`・`List.tail`・`String.trim` など）は、引数が上限の中にあるので、確かめなくてよい。

どの操作も上限を確かめるので、上限を超える文字列とリストの値は作られない。

この上限は、一つの操作で作る値だけを抑える。小さな値を何度も作ってヒープが足りなくなる場合は、上の「資源の追跡」に従って終わる。

### panic 境界

【決定】処理系は、panic が巻き戻しを行う設定でビルドし、IO 実行器は VM の実行全体を `catch_unwind` で囲む（[ADR 0079](../decisions/0079-rust-readings-of-go-based-decisions.md)）。`catch_unwind` が捕らえるのは巻き戻しによる panic だけであり、abort で終わる場合（ヒープの確保の失敗など）は捕らえない（[catch_unwind](https://doc.rust-lang.org/std/panic/fn.catch_unwind.html)）。

【方針】組み込みの関数やハンドラの中で Rust の panic が起きたとき（処理系の不具合）は、実行時エラーとしては扱わず、処理系の不具合として報告する。報告の前に出力のバッファを書き出し、処理系の不具合の報告を標準エラー出力に直接書いて、終了状態 3 で終わる（[ADR 0037](../decisions/0037-exit-status-values.md)）。報告の形式は[診断エンジン](02-10-diagnostics.md)で定める。

組み込みの関数とハンドラは、言語の規則で定めた失敗（除算の 0、IO の失敗など）を panic で表さず、実行時エラーの種類か `Err` の値として返す。

【方針】Rust の panic hook は、panic を `catch_unwind` が捕らえる前に呼ばれ、既定の hook は標準エラー出力にメッセージを書く（[set_hook](https://doc.rust-lang.org/std/panic/fn.set_hook.html)）。既定の hook のままでは、出力のバッファより先に、診断の形式によらないメッセージが出る。そこで、処理系を使うプログラム（CLI、将来の MCP サーバなど）は、起動の直後、スレッドを作る前に一度だけ、処理系の hook を設定する。処理系の hook は標準エラー出力に何も書かず、panic の内容、panic の起きたソース上の位置、バックトレースを、panic したスレッドのスレッドローカルな記憶域に記録する。panic 境界は、捕らえた後にこの記録を取り出して報告に使う。hook はプロセス全体で一つなので、実行ごとに設定し直さない。

【方針】CLI は、検査の各段（字句解析からコード生成まで）の処理も `catch_unwind` で囲み、そこで捕らえた panic も、同じく処理系の不具合として報告する（[診断エンジン](02-10-diagnostics.md)の「処理系の不具合と処理系の制限の報告」）。hook の出力が出ないことと報告の順序は、処理系の API を呼ぶテストでは確かめられないので、CLI を別のプロセスとして起動するテストで、標準エラー出力の内容を確かめる（[処理系のテスト戦略](../07-quality/07-03-compiler-testing.md)）。

### プログラムの実行の流れ

【方針】`run` は、コンパイル済みプログラムを受け取った後、次の順に処理する（[エフェクト](../01-spec/01-07-effects.md)の「プログラムの入口」）。

1. コマンドライン引数を検査する。正しい UTF-8 でない引数があれば、その引数の位置を示す診断を出し、`main` を呼ばずに終了状態 1 で終わる（[ADR 0012](../decisions/0012-invalid-utf8-input.md)、[ADR 0037](../decisions/0037-exit-status-values.md)）。
2. 実行ごとの状態を作り、本番のハンドラ表と、コマンドライン引数を入れる。
3. IO 実行器で `main` を実行する。
4. 出力のバッファを、標準出力、標準エラー出力の順に書き出す（「出力のバッファ」）。
5. 終わり方に応じて、次の報告を標準エラー出力に直接書き、次の終了状態で終わる。

| 終わり方 | 報告 | 終了状態 |
|---|---|---|
| `main` が `()` または `Ok(())` を返した | なし | 0 |
| `main` が `Err(msg)` を返した | `msg` と改行（[ADR 0011](../decisions/0011-io-failure-and-entry-point.md)） | 1 |
| 実行時エラーで止まった | 実行時エラーの報告（[評価意味論](../01-spec/01-08-evaluation.md)） | 1 |
| 資源の不足で止まった | 資源の不足の報告 | 1 |
| 処理系の不具合（panic 境界で捕捉した Rust の panic） | 処理系の不具合の報告（「panic 境界」） | 3 |

手順 4 の書き出しに失敗したときは、次のようにする。

- 終わり方が `main` の `()` か `Ok(())` であれば、書き込みの失敗の実行時エラーの報告を書き、終了状態 1 で終わる。
- 終わり方が `main` の `Err(msg)` であれば、`msg` と改行を書いた後に、書き込みの失敗の実行時エラーの報告を書き、終了状態 1 で終わる。
- 終わり方が実行時エラーか資源の不足であれば、先の報告に、書き出しの失敗を注記として加え、終了状態 1 で終わる。
- 終わり方が処理系の不具合であれば、その報告だけを書き、終了状態 3 で終わる。

標準エラー出力に書く報告の形式は[診断エンジン](02-10-diagnostics.md)で定める。終了状態の値は [CLI](../06-tooling/06-01-cli.md) の「終了状態」と同じであり、[ADR 0037](../decisions/0037-exit-status-values.md) に従う。
