## 手順の要点

### 例の取り出し

grammar_check.py と同じ規則で取り出す。Python の道具と検査の対象を揃えるためである。

- 対象のファイルは `env!("CARGO_MANIFEST_DIR")` から `../../doc/archive/2026-09-27-design-initial/01-spec/` の `*.md` を名前の順に読む。
- 例は、`` ```text `` の行から次の `` ``` `` の行までのコードブロックである。
- EBNF の規則のブロック（`^\s*[A-Z][A-Za-z]*(\([A-Z]\))?\s+=\s` に当たる行を含み、最後が `.` で終わるもの）と、文字列リテラルとコメントを除いて ASCII でない文字が残るブロック（数式）は除く。grammar_check.py の `is_source` と同じ判定である。正規表現のクレートは使わず、行ごとの文字の検査で書く。
- 最小実行版の範囲の例だけを対象にする。ブロックの前にある最も近い `###`・`####` の見出しに「（v1）」を含むブロックは除く。見出しに「（v1）」がなくても、v1 の構文を含むブロックは除く。v1 の構文を含むかは、文字列リテラルとコメントを除いた本文に次のどれかがあるかで判定する: `import `、`record `、`trait `、`impl `、`lazy `、`with `、`permissions`、`pub `、`?`、`..`、および文字列リテラルの中の `${`。
- 文法で読めなくて正しい例は、テストの中の定数の表（章のファイルの名前と、例の最初の空でない行の組）で除く。初めの表は grammar_check.py の `EXPECTED` の 8 個と同じにする。grammar_check.py の `EXPECTED` を変えたら、この表も変える（表の先頭のコメントにそう書く）。

### 読み方

grammar_check.py の `check` は、例を `Program`、`Stmts`（文の並び）、`Type`、`Pattern` の順に試す。処理系の `parse` はプログラムだけを読むので、同じ四つを次のように包んで試し、どれかが診断なしで読めれば通ったとする。包み方は本プランで決めたものである。

| 試す形 | 包み方 |
|---|---|
| プログラム | そのまま |
| 文の並び | `fn example_wrapper() -> Unit {` の行、例、`}` の行 |
| 型 | `fn example_wrapper(x: ` 例 `) -> Unit {}`（例は 1 行のときだけ試す） |
| パターン | `fn example_wrapper() -> Unit {` の行、`match () {` の行、例 ` => ()` の行、`}` の行、`}` の行（例は 1 行のときだけ試す） |

各形について、`lex`（ファイル ID は `FileId(0)`、バイト列は例の文字列）、`resolve_newlines`、`parse`（`SourceKind::User`）を順に呼び、字句の誤りと構文の誤りの両方がないかを見る。名前解決と型検査は行わない（例の中の名前は仮のものがある。grammar-check の README「確かめないもの」）。

### 失敗の報告

読めない例があれば、すべての例を試した後でテストを失敗させる。失敗の文には、例ごとに章のファイル名と例の先頭の行番号、プログラムとして読んだときの最初の診断のコードと文言を並べる。最後に、読めた例・除いた例・読めなかった例の数を示す。

## 受け入れテスト

| 場合 | 期待 |
|---|---|
| 現在の 01-spec の全章 | 読めなかった例が 0 個でテストが通る |
| 読めた例の数 | grammar_check.py が「ok」と数える例のうち最小実行版の範囲のものと、ほぼ同じ数になる。数の差を完了の報告に書く |
| 試しに壊した例 | 01-02「例」のプログラムの `}` を一つ消したコピーをテストの中で読むと失敗として数えられる（例を取り出した後の判定の関数を、文字列を与えて呼ぶテストで確かめる） |
| v1 の節の例 | 01-02「モジュールと import（v1）」の例が対象から除かれる |

最初に通したときに読めない例が見つかったら、処理系の構文解析器の誤りか、例の誤りかを調べる。構文解析器の誤りなら T11・T12 の側の不具合として報告する。例の誤り（設計書の側）なら、作業を止めて報告する（設計書は本作業で変えない）。

## 完了条件

- scripts/check.sh が通る（00-02「完了条件の共通の検査」）
- 受け入れテストのすべての場合を確かめるテストがある
- 除いた例の表が grammar_check.py の `EXPECTED` と一致している

## 難易度の理由

処理系の関数を順に呼ぶだけで、アルゴリズムの難しさはない。Markdown からの例の取り出しと除く規則を grammar_check.py と揃える細かさと、例を包む形の決まりが手間の中心である。読めない例が見つかったときに、構文解析器と設計書のどちらの誤りかを見分ける判断が要る。
