# T25 ゴールデンテストの実行器

- 依存する作業: [T24](T24-pipeline-cli.md), [T18](T18-core-check.md), [T19](T19-refinterp.md)

## 目的

スクリプトと期待値のファイルを並べたゴールデンテスト（ADR 0039）を読み、処理系の API で検査・実行して、結果を期待値と比べる実行器を作る。同じ実行器の中で、IO の二つの方式のテスト、参照インタプリタとの差分テスト、コア IR の検査を行う（07-03「テストの種類」）。あわせて、CLI を別のプロセスとして起動するテスト、仕様の項目とテストの対応を集計する道具、完了条件とテストの対応表の形を用意する。テストのスクリプトの大部分は T26〜T28 が書き、本作業は実行器が働くことを示す少数のテストだけを置く。

## 手順の要点

### テストの見つけ方と表示名

- `crates/benitoite/testdata/` の下の区分のディレクトリ（`lexical`・`syntax`・`names`・`types`・`effects`・`patterns`・`eval`・`io`・`acceptance`・`runner`）を辿り、`*.bnt` を一つのテストとする。区分のディレクトリの一覧はコードに書かず、`testdata/` の直下のディレクトリをすべて辿る。`<名前>.files/` の中の `.bnt` はテストとみなさない。
- 検査は `pipeline::check_text(name, bytes)` で行い、表示名 `name` は `testdata/` からの相対パス（`<区分>/<名前>.bnt`）とする。【新しい決定】CLI では表示名がコマンドラインのパスになるので、ゴールデンテストの期待値の表示名は CLI と一致しない。CLI の表示名は `cli_process.rs` で確かめる。
- テストは一つの `#[test]` 関数の中で全部を順に実行し、失敗したテストをすべて集めてから、失敗の一覧（テストの名前と、期待値と実際の差分）を示して失敗させる。一つ目の失敗で止めない。環境変数 `BENITOITE_GOLDEN_FILTER` に文字列を与えたら、名前にその文字列を含むテストだけを実行する（調べるときに使う）。

### 期待値のファイル

07-03「ゴールデンテスト」の表の組を読む。

| ファイル | 読み方 |
|---|---|
| `.mode` | `check` か `run`（前後の空白と改行を除く）。ファイルがないとき、ほかの値のときは実行器の誤りとし、理由を示してそのテストを失敗させる |
| `.exit` | 10 進の整数 |
| `.stdout`・`.stderr` | バイト列のまま比べる。ファイルがなければ空を期待する |
| `.diag.json` | 一行に一つの報告。ファイルがなければ報告がないことを期待する |
| `.args` | 一行に一つの引数。ファイルがなければ引数なし |
| `.files/` | ディレクトリの中のファイルを、ディレクトリからの相対パス（`/` 区切りの文字列）を鍵として `TestIo` の `files` に入れる |
| `.text.stderr` | あるときだけ、文章の形式の報告（色なし）を比べる |
| `.opts` | 【新しい決定】実行の選択肢。一行に一つの `名前=値`。最小実行版では `max-call-stack=<大きさ>`（06-01 の `--max-call-stack` と同じ書き方。`cli::parse_size` で読む）だけを受け付ける。T28 が、呼び出しの入れ子の上限に達するテストで使う。ファイルがないときは `vm::DEFAULT_MAX_CALL_STACK` を使う |

JSON は読み取らない。実際の報告を `diag::render::render_json_line` で一行ずつ文字列にし、期待値のファイルの行と文字列として比べる（10-02「診断の書き出し」の最後の段落が、項目の順と空白を決めてある）。

### `check` のテスト

1. `check_text` を呼ぶ。
2. 誤りがなければ終了状態 0、報告なし。誤りがあれば終了状態 2、`diagnostics` を順に JSON にしたものが `.diag.json` の期待値である。
3. `.text.stderr` があれば、`render_check_text(diags, sources, 動詞, 表示名, TextOptions { color: false })` と比べる。動詞は `.mode` の値（`check` か `run`）である。
4. `.stdout`・`.stderr` は空を期待する。

### `run` のテスト

1. `check_text` を呼ぶ。誤りがあれば `check` と同じく扱う（終了状態 2。`.text.stderr` の動詞は `run`）。
2. `desugar_checked` を呼ぶ。`Err` なら処理系の不具合として、実行器がテストを失敗させる（期待値で扱わない）。成功したら、コア IR の検査（`ir::check::check_program`）の結果が空であることを確かめる（07-03「コア IR の検査」）。
3. `compile` を呼ぶ。`CompileError::Limit` なら終了状態 2 と、その診断の JSON を期待値と比べる。`Internal` なら実行器の失敗とする。
4. `.args` の各行を `OsString` にして `runtime::run::check_args` に渡す。`Err` なら終了状態 1 と、その報告の JSON を比べる。
5. `ExecMode::Direct` と `ExecMode::Request` のそれぞれで、`TestIo::new(args, files)` を作り、`run_with` を呼ぶ。実際の結果は次のとおりとする。
   - 終了状態: `RunEnd::exit_code`
   - 標準出力: `TestIo::stdout`
   - 標準エラー出力: `TestIo::stderr` の後に、`main_error` があればその文字列と改行を続けたもの（CLI が書く順と同じ。10-08 の `RunEnd` のコメント）
   - 報告: `RunEnd::reports` を JSON にしたもの。`.text.stderr` があれば、各報告の `render_one_text`（色なし）をつなげたものと比べる。処理系の制限（手順 3）とコマンドライン引数の誤り（手順 4）の報告も、同じく `render_one_text` で比べる
6. 二つの方式の結果を、それぞれ期待値と比べる（07-03「IO の方式のテスト」）。失敗の一覧には、どちらの方式で食い違ったかを示す。

### 書き直しの指定

環境変数 `BENITOITE_BLESS=1` を与えたときは、比べる代わりに、実際の結果で期待値のファイルを書き直す（ADR 0039）。

- `ExecMode::Direct` の結果で書き直す。二つの方式の結果が食い違うときは、書き直さずに失敗させる。
- 期待値が空になるファイル（`.stdout`・`.stderr`・`.diag.json`）は、書き直すときに消す。`.mode`・`.args`・`.files/`・`.opts` は書き直さない。`.text.stderr` は、あるときだけ書き直す。
- `scripts/check.sh` は書き直しの指定を使わない。書き直した差分は、人（またはレビューする LLM）が読んでからコミットする。

### 差分テスト

`run` のすべてのテストについて、次のように参照インタプリタ（`refinterp::run`）と VM の結果を突き合わせる（07-03「差分テスト」）。

- 参照インタプリタには、新しい `TestIo`（同じ引数とファイル）を渡す。VM の側は、上の手順 5 の `ExecMode::Direct` の実行で使った `TestIo` を使う。
- 比べるものは、`TestIo::events`（IO の事象の列）、終わり方、実行時エラーの位置である。
- 終わり方: VM が値で終わったら、参照インタプリタも `RefOutcome::Returned` でなければならない。`main` の結果の値（`()`、`Ok(())`、`Err(msg)`）も比べる。止まったときは、`Stop` の種類（`Runtime` の列挙子、`Internal`）が一致しなければならない。
- 位置: VM の位置は、`runtime::report::stop_diagnostic` の主な位置の span とする。参照インタプリタの位置は `RefOutcome::Stopped` の `origin` とする。二つの位置が両方とも利用者のソースにあるときだけ比べる。prelude のソースの中で止まったときの主な位置の選び方（02-08「実行時エラーの情報の記録」）は参照インタプリタにないので、比べない。
- 資源の不足（`Stop::Resource`）で止まったテストは、差分テストの対象から外す（ADR 0018）。書き込みの失敗は `TestIo` では起きない。
- 【新しい決定】性能のベンチマーク（07-03「差分テスト」の対象）は、`tools/bench/programs/<名前>.bnt` に並べて `tools/bench/programs/<名前>.args.small`（一行に一つの引数）がある場合だけ、同じ差分テストにかける。ファイルが一つもなければ、何もしない。ベンチマークのスクリプトは T31 が置く。期待値のファイルは持たず、差分テストだけを行う。各スクリプトについて、`check_text` → `desugar_checked` → `compile` → `.args.small` の行を `check_args` に渡す → `TestIo::new(args, 空の表)` → `run_with`（`ExecMode::Direct`）を行い、同じ `CoreProgram` を `refinterp::run` に新しい `TestIo` で与えた結果と、上と同じ規則で比べる。

### CLI を別のプロセスとして起動するテスト

`env!("CARGO_BIN_EXE_benitoite")` で処理系の実行ファイルを起動し、終了状態と標準出力・標準エラー出力を確かめる（07-03「前提」）。スクリプトは一時的なディレクトリ（`std::env::temp_dir()` の下にテストごとの名前で作る）に書く。

| 場合 | 期待する結果 |
|---|---|
| 使い方の誤り（サブコマンドなし、知らないオプション、スクリプトのパスなし） | 終了状態 2。標準エラー出力に `error:` の行と `--help` を使うよう示す行 |
| `--version`・`--help` | 終了状態 0。標準出力に版または使い方 |
| 固定の文字列を出力するスクリプトを `run` | 終了状態 0。標準出力がその文字列 |
| 存在しないスクリプトを `check` | 終了状態 2。E0101 の報告。表示名がコマンドラインのパス |
| `BENITOITE_DEV_PANIC=check` で `run` | 終了状態 3。標準エラー出力が `internal error` の報告で始まり、その前に panic hook の出力がない |
| `BENITOITE_DEV_PANIC=run` で、`Console.println` を呼ぶスクリプトを `run` | 終了状態 3。標準出力に最初の `Console.println` の内容が書き出されており、標準エラー出力は `internal error` の報告だけ |
| `--diagnostics=json` の処理系の不具合 | 報告が JSON の一行で、`kind` が `"internal"`、`code` が `null` |
| 読み手が先に終わったパイプ | 終了状態 1。標準エラー出力に R0201 の報告 |
| 正しい UTF-8 でないコマンドライン引数（Unix だけ。`std::os::unix::ffi::OsStrExt::from_bytes` で作る） | 終了状態 1。R0301 の報告。`main` を呼ばない |

読み手が先に終わったパイプのテストは、次のように作る。【新しい決定】スクリプトは、出力のバッファの大きさ（64 KiB）を十分に超える量（例えば 1 行 100 バイトを 10,000 行）を標準出力に書く。テストは子のプロセスの標準出力をパイプにし、子のプロセスを起動した直後に読み手の側を閉じてから、子のプロセスの終わりを待つ。バッファが 64 KiB を超えた時点で書き出しが起こり、閉じたパイプへの書き出しが失敗するので、実行中の書き込みの失敗として止まる。書き出しの時期によって、止まるのが実行の途中か終える前の書き出しかが変わりうるが、どちらでも終了状態 1 と R0201 になる（02-09「プログラムの実行の流れ」）。Windows では、このテストと UTF-8 のテストを `#[cfg(unix)]` で外す。

### 仕様の項目の集計の道具

`tools/spec-coverage/spec_coverage.py`（Python 3 の標準ライブラリだけ）を作る。07-03「受け入れ例と仕様の項目の対応」の二つの方針を満たす。

- `testdata/` の下のすべての `.bnt` の先頭のコメントから、`// spec: <章の番号> <節の見出し>` の行を集める。一つのテストが複数の行を持ってよい。
- `doc/archive/2026-09-27-design-initial/01-spec/` の各章の `###` と `####` の見出しのうち、「（v1）」を含まず、「v1 の」で始まらない見出しを、最小実行版の範囲の節とする。ただし、構文の章の「v1 の文法の全体」と「最小実行版に含めない構文」など、規則を持たない節は、道具の中の除外の一覧に登録する。
- 章の番号は、ファイル名の先頭（`01-05` など）で照合する。`// spec:` の行の見出しが章に存在しなければ、誤りとして示す（書き間違いを見つけるため）。
- 確かめるテストのない節を一覧にして出力する。終了状態は、見出しの書き間違いがあれば 1、なければ 0 とする（テストのない節があっても 0。一覧は判断の材料であり、完了条件の検査ではない）。
- `testdata/acceptance/INDEX.md` の表を読み、ロードマップの最小実行版の完了条件の 8 行それぞれに、存在するテストの名前が一つ以上あることを確かめる。欠けていれば終了状態 1 とする。

`INDEX.md` の形は次のとおりとし、本作業では完了条件の 8 行とベンチマークの行の見出しだけを置き、テストの名前の欄は空にしておく（T28 が埋める）。道具は、テストの名前の欄が空の行を「欠けている」と報告する。T28 が終わるまで、道具は終了状態 1 になる。

```markdown
| 完了条件 | テスト |
|---|---|
| 固定の文字列を標準出力に書く | `acceptance/hello.bnt` |
```

## 受け入れテスト

- `testdata/runner/` に、次の 4 本を置き、すべて通る。`check` の誤りなし（`.exit` が 0）、`check` の誤りあり（`.diag.json` と `.text.stderr` を持つ）、`run` で標準出力と `main` の `Err` を持つもの（`.stderr` を持つ）、`run` で `.args` と `.files/` を使うもの。
- 実行器の検出力: 上の 4 本のどれかの期待値を 1 バイト変えると、テストが失敗し、失敗の一覧にそのテストの名前と差分が出る（手で確かめ、完了の報告に書く。テストとしては残さない）。
- 書き直しの指定: 期待値のファイルを消した状態で `BENITOITE_BLESS=1 cargo test --test golden` を実行すると、ファイルが作られ、続けて指定なしで実行すると通る（手で確かめ、完了の報告に書く）。
- 差分テストとコア IR の検査が、`testdata/runner/` の `run` のテストに対して実行されている（失敗の一覧の形で、差分テストの失敗とコア IR の検査の失敗を区別して示す）。
- `cli_process.rs` の表の場合がすべてある。
- `spec_coverage.py` が、`testdata/runner/` の `// spec:` の行を集め、書き間違いのない行で終了状態 0（INDEX.md の欠けを除く）、見出しを書き間違えた行を含む一時的な入力で終了状態 1 になる（道具の中に小さな自己テストの関数を置き、`--self-test` で実行する）。

## 完了条件

- scripts/check.sh が通る（00-02「完了条件の共通の検査」）
- 受け入れテストのすべての場合を確かめるテストがある
- `scripts/check.sh` に `python3 tools/spec-coverage/spec_coverage.py --self-test` を加える必要があれば、完了の報告に書く（`scripts/check.sh` は T00 のファイルなので、本作業では変えない）

## 難易度の理由

扱う組み合わせ（`check` と `run`、二つの IO の方式、差分テスト、コア IR の検査、書き直しの指定、別のプロセスのテスト）は多いが、どれも公開の API を呼んで結果を比べる処理であり、アルゴリズムの難しさはない。注意が要るのは、標準エラー出力の組み立ての順と、差分テストで位置を比べる条件を 07-03 と 02-08 に合わせることと、パイプのテストを不安定にしないことである。
