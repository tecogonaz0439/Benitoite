## 目的

型検査の全体の手順を書く。宣言の検査（型の宣言、関数のシグネチャ、`main`、等値の型の要約）で宣言の型を決め、各関数の本体を辿って制約を生成し、T14 の `Solver` で解き、T16 の `check_match` でパターンを検査して、02-05「出力」の表を作る。型検査の結果は脱糖（T17）が使うので、表の鍵と値は 10-05 の定めに正確に合わせる。

## 手順の要点

### 全体の流れ

1. 宣言の検査（`decls.rs`）。宣言の型の表（`decl_types`）と代数的データ型の表（`adts`）を作る。
2. prelude のソースの関数の本体を、ファイルの順・宣言の順に検査する。続けて、利用者の関数の本体を宣言の順に検査する。本体ごとに `Solver::new` で新しい状態を作る。
3. 本体ごとに、制約の生成、`solve`、E0407、パターンの検査、表への記録を行う。

誤りの診断があっても、ほかの本体の検査は続ける（02-05「検査の手順」、ADR 0024）。診断の並べ替えは呼び出し側（10-09 の `check_path`）が行うので、ここでは生じた順に返してよい。

### 宣言の検査（`decls.rs`）

AST の型（`TypeExpr`）から `Ty` への変換は、名前解決の参照の表で名前の束縛を引いて行う。`BindingKind::Type(c)` は `Con(c, 型引数)`、`BindingKind::TypeParam { index }` は `Param(index)`、`FnType` は `Fn`（`uses` の `EffectRef` が `Effect` なら `io`、`EffectVar { index }` なら `EffVar(index)`）、`ParenType` は中の型とする。

- 代数的データ型の表: 最初に `Option`（型パラメータ `T`、構成子 `Some`（タグ 0、引数 `[Param(0)]`）、`None`（タグ 1））と `Result`（`T`・`E`、`Ok`（0）、`Err`（1））を加える。構成子の束縛の番号は `ResolveOutput::prelude` から取る。続けて利用者の型の宣言を、ソースの順に加える。`con` は `TyCon::Adt(型の宣言の束縛の番号)`、タグは構成子を書いた順に 0 から振る。
- E0411: 構成子のない型の宣言。
- E0410: 型引数の個数の誤り。基本型・`List`・`Option`・`Result`・`IoError` は `TyCon::builtin_arity`、利用者の型は宣言の型パラメータの数、型パラメータは 0 個と比べる。`name`・`expected`・`found` を埋める。本体の中の型注釈にも同じ検査を行う。
- 型の宣言と関数のシグネチャで誤りを報告した宣言は、「壊れた宣言」として記録する。壊れた関数を使う箇所の型は `ITy::Error` とし、壊れた関数の本体は検査しない。壊れた型の宣言の構成子も同じく扱う。これにより、宣言の誤りから派生した誤りを本体で報告しない（ADR 0024 の趣旨を宣言に広げる。本作業で決める）。
- 等値の型の要約: 01-06「等値の型」の手順 1〜3（ADR 0082）を、すべての型の宣言について同時に、変わらなくなるまで繰り返して求め、`AdtDef::eq_summary` に入れる。`Option` と `Result` も同じ手順で求める（どちらも `always = false`、依存する型パラメータはすべて）。
- 関数の宣言の型: prelude のソースの関数と利用者の関数について `Scheme` を作る。型パラメータの並びは `is_effect` でないものを順に、エフェクト変数の並びは `is_effect` のものを順に並べる（名前解決の `index` と同じ順）。型パラメータの制約はすべて `ParamConstraint::None`。
- エフェクト変数の規則（01-06「関数の型とエフェクト」）: シグネチャと本体の型注釈のすべての `uses` の並びについて、エフェクト変数が二つ以上あれば E0417、同じ名前が二度あれば E0419（`name`）。シグネチャで宣言したエフェクト変数が、引数の型のどこにも現れなければ E0418（`name`）。
- 構成子の宣言の型: 型の宣言の型パラメータを型パラメータとし、引数の型を引数、`D[Param(0), …]` を戻り値の型、空集合をエフェクトとする（10-05「型検査の出力」の最後の段落）。`Option`・`Result` の構成子も加える。
- `main`: 利用者のトップレベルの関数に `main` がなければ E0414（主な位置なし。修正案 `define`）。あれば、01-07「プログラムの入口」の条件を確かめ、満たさない条件ごとに E0415 の注記（`params`・`type_params`・`ret`・`effects`）を一つの診断に並べる。主な位置は関数の名前。戻り値の型が `Result[Unit, String]` なら `returns_result = true`。

### 本体の制約の生成（`generate.rs`）

02-05「制約の生成」の表を、構文ごとに一つの関数で実装する。本作業で決める点と、表を読むときに迷いやすい点は次のとおりである。

- 生成の順序: 子を左から右に辿り終えた後に、その構文の制約を加える。関数の本体の `Flow` は、本体を辿り終えた後に加える（02-05「制約の解決」）。
- 本体のエフェクト E: トップレベルの関数の本体では `IEffect { fixed: 宣言した uses, var: None }`、`uses` を書いたラムダの本体では同じく固定、`uses` を書かないラムダの本体とプレースホルダを含む呼び出しの本体では新しい変数（`fresh_effect`）である。
- 呼び出しの理由の `related`（E0401・E0402 の補助の位置 `declared`。T14）: 呼び出される式が、トップレベルの関数・prelude のソースの関数・引数を持つ構成子を指す `NameExpr` のとき、`CallArg { index }` の `related` は、その宣言の i 番目の引数の型の span（prelude のソースの関数では prelude のソースの span、構成子では構成子の宣言の i 番目の引数の型の span）とする。`Call` の `related` は、同じ条件で、関数の宣言（構成子では構成子の宣言）の名前の span とする。組み込みの関数とそのほかの呼び出しでは `None` とする。
- 呼び出しのエフェクトの `EffSub(ε, E)` の理由の種類: E が固定で関数の本体なら `FnUses`（`related` は関数の宣言の `uses` の並びの span、なければ関数の名前の span）、固定でラムダの本体なら `LambdaUses`（`related` はラムダの `uses` の並びの span）、E が変数なら `CallEffect`。`span` は呼び出しの式の span。
- 局所の束縛: 束縛の番号から `ITy` への表を本体ごとに持つ。局所の束縛の名前はその型をそのまま使い、多相にしない（ADR 0009）。
- 多相な名前（`TopFn`・`PreludeFn`・`Builtin`・`Ctor` を指す `NameExpr`、および `CtorPat`）: 宣言の型の型パラメータを新しい型変数に、エフェクト変数を新しいエフェクトの変数に置き換える。組み込みの関数の型パラメータの制約（`ParamConstraint::Equality`・`OneOf`）は、`Solver::constrain_equality`・`constrain_one_of` で置き換えた型変数に移す。置き換えた型変数とエフェクトを本体の終わりに `finalize` して、`type_args` に記録する。引数を持つ構成子を呼ばずに値として使う名前の型は、構成子の宣言の型の関数の型である。引数を持たない構成子の名前の型は `D[T̄]` である。
- 組み込みの関数の型パラメータの制約の理由: `List.contains`（等値）と `List.sort`（集まり）の制約が満たされないときは、E0406・E0405 の `op` に関数の修飾した名前（`List.contains` など）を示す。理由は `ReasonKind::BuiltinParam { name }`（10-05）とし、`span` をその名前を使う箇所の span とする。
- 呼び出し `f(a1, …, an)`: `Equal { expected: f の型, found: fn(β1, …, βn) -> ρ（エフェクト ε）, reason: Call }`、各引数に `Flow { from: ai の型, to: βi, reason: CallArg { index: i } }`（index は 1 から数える）、`EffSub(ε, E)`。型は ρ。呼ばれる式の型が誤りの型を含むときは、`EffSub` を加えない（02-05「誤りの報告と検査の継続」の 2 番目の項目。`Solver::contains_error` は解いた後にしか使えないので、生成の時点で `ITy::Error` と分かっている場合に限る）。
- 引数を持たない構成子の呼び出し（`Tree.Leaf()`、`None()`）: 呼ばれる式が引数を持たない構成子を指す `NameExpr` で、引数が 0 個のときは、呼び出しの制約を作らずに E0413（`name`、修正案 `remove`）を報告し、式の型を `ITy::Error` とする（02-05「制約の生成」の表の後の段落）。
- プレースホルダを含む呼び出し: 01-02 の規則で展開したラムダとして扱う。プレースホルダごとに新しい型変数 πk を作って `expr_types` のプレースホルダのノードに記録する。本体のエフェクトを新しい変数 E' とし、呼ばれる式とプレースホルダでない引数を E' のもとで辿り、呼び出しの制約を作る。式の型は `fn(π1, …) -> ρ`（エフェクト E'）、`lambda_effects` の呼び出しのノードに E' を記録する。
- パイプ `x |> e`: 先に x を辿る。e が括弧の式なら規則 2（ADR 0050）、e が直接の引数にプレースホルダを含まない呼び出しなら規則 1（x を第 1 引数に加える。`CallArg` の index は x が 1、元の引数が 2 から）、それ以外なら規則 2 として、展開した呼び出しの制約を作る。規則 1 で e が呼び出しを重ねた形（`g(a)(b)`）なら、最も外側の呼び出しに加える。展開した呼び出しの制約の理由の span は、パイプの式全体の span とする。
- 二項演算・単項演算: 01-06「演算子の型付け」と 02-05 の表のとおり。`+ - * /` は `Equal(α, 左)`・`Equal(α, 右)`（理由 `Operands`）と `OneOf(α, ADD または ARITH)`（理由 `Operator`）、型は α。比較の `< <= > >=` は `ORD` で型は `Bool`。`== !=` は `Equality(α)` で型は `Bool`。`%` は二つのオペランドを `Int` と等しくし（理由 `Operator { op: Bin(Rem) }`。E0401 の注記 `because_int_operands` になる。T14）、型は `Int`。単項の `-` は `ARITH`。`&& || !` はオペランドを `Bool` と等しくし（`Logic`）、型は `Bool`。`operand_types` には α（論理演算子では `Bool`）を記録する。
- 整数リテラルを直接オペランドにとる単項の `-`（`-9223372036854775808`）: 符号を含めた値で範囲を判定し、式の型を `Int` とする（オペランドの制約を作らない）。`operand_types` には `Int` を記録する。括弧で囲んだ `-(n)` はこの扱いにしない。
- `int_literal`: 型を求められた側（`Equal` の `found`、`Flow` の `from`）の式が 10 進の整数リテラルのとき、その数字列を `Reason::int_literal` に入れる。
- `if`・`match`・ブロック・リストリテラル・ラムダ・関数の本体・パターン: 02-05 の表のとおり。`Equal` の `expected` には、求める側の型（`Bool`、`Unit`、`match` の対象の型、構成子の引数の型）を置く。
- 流れ込む制約の `priority`: 関数の本体と宣言した戻り値の型、`let` の型注釈、ラムダの戻り値の型注釈から生じた `Flow` は `Priority::Declared`、ほかはすべて `Normal`（02-05「制約の解決」の手順 1）。`related` には、型注釈（宣言した戻り値の型）の span を入れる。

### リテラルの範囲

- 整数リテラル: 基数と数字列から値を `u128` で計算し（溢れれば範囲の外）、`i64::MAX` を超えれば E0408（注記 `range`）。直接の単項の `-` の下では、`2^63` まで許す。リテラルのパターン（`LitPat`）の整数も同じく検査し、`negative` なら `2^63`（`i64::MIN` の絶対値）まで許す。範囲の外の整数のパターンを含む `match` は、パターンの検査（`check_match`）から外す。
- 浮動小数リテラル: 字面（`_` を除いたもの）を Rust の `str::parse::<f64>` で読み、無限大になれば E0409。Rust の `f64` の文字列からの変換は最も近い値に丸める（最近接偶数）。これを 01-04「Float」の丸めの規則として使う。
- 範囲の外のリテラルも、式の型は `Int` または `Float` とし、検査を続ける。

### 解いた後の検査と記録

1. `solve` の診断を加える。
2. `Solver::undetermined` の各理由について E0407（主な位置は理由の span、修正案 `annotate`）を報告する。
3. パターンの検査: 本体の各 `match` について、対象の型を `finalize` する前に `contains_error` で調べ、誤りの型を含むなら飛ばす。分岐のパターンのどれかで E0412・E0413・E0408 を報告した `match` も飛ばす。それ以外は、AST のパターンを `Pat` に変換して（変数のパターンは `Wild`、`-n` は負の値、構成子のパターンは参照の表の `Ctor { con, tag }`）`check_match` を呼ぶ。
   - `Unreachable`: E0602。主な位置はその分岐のパターンの span、`covered_by` の各分岐のパターンの span に補助の位置 `covering`。
   - `NonExhaustive`: E0601。主な位置は `match` の対象の式の span、`witness` を埋め、修正案 `add_arm`。
4. 表への記録: 生成のときに記録した `ITy` と `IEffect` を `finalize`・`finalize_effect` して、`expr_types`・`type_args`・`operand_types`・`lambda_effects` に入れる。

`expr_types` の鍵は、すべての式、すべてのパターン、`let` 文（束縛した変数の型）、関数とラムダの引数、プレースホルダのノードである。脱糖（T17）はこれらを引くので、漏れがあると処理系の不具合になる。

## 受け入れテスト

テストは、テストのモジュールの補助の関数で、prelude のソース（`crate::prelude::SOURCES`）と利用者のソースを字句解析・改行の判定・構文解析（T02・T03・T11・T12）と名前解決（T13）に通してから `typecheck` を呼ぶ。診断はコードと主な位置で確かめる。

| 場合 | 入力の要点 | 期待する結果 |
|---|---|---|
| prelude のソース | 利用者のソースは `fn main() -> Unit { () }` だけ | 診断なし（prelude のソースに誤りがないことの検査） |
| 01-02 の「例」のプログラム | `Shape`・`area`・`totalArea`・`main` | 診断なし。`List.map` を使う箇所の `type_args` が `[Shape, Float]` と空のエフェクト |
| 局所の束縛は多相にしない | 01-06「多相」の `id(1)` と `id("one")` | E0401 |
| 型が決まらない | 01-06「演算子の型付け」の `f` | E0407 |
| 型が使い方で決まる | 同じ節の `g` | 診断なし |
| エフェクト変数 | 02-05 の `choose` の例 | 診断なし |
| エフェクト変数（違反） | 同じ例の第 2 引数を `fn() { Console.println("x") }` に変えたもの | E0501 |
| 純粋な関数から IO | 01-06「式のエフェクト」の `greet` | E0501（主な位置は `Console.println(...)` の呼び出し） |
| ラムダの `uses` | `fn f[effect E](a: fn() -> Unit uses E) -> Unit uses E` の本体で、`let g = fn() -> Unit uses E { Console.println("x") }` | E0502（主な位置は `Console.println(...)` の呼び出し、補助の位置はラムダの `uses`） |
| `main` がない | `fn f() -> Unit { () }` だけ | E0414 |
| `main` の誤った形 | `fn main(x: Int) -> Int { x }` | E0415、注記 `params` と `ret` |
| 型引数の個数 | `fn f(x: List) -> Unit { () }` | E0410 |
| 構成子のない型 | `type T {}` | E0411 |
| エフェクト変数の規則 | `uses E, F`（二つのエフェクト変数）、`uses IO, IO`、引数に現れないエフェクト変数 | それぞれ E0417、E0419、E0418 |
| 引数のない構成子に括弧 | 式の `Tree.Leaf()` とパターンの `Tree.Leaf()` | どちらも E0413。派生の誤りなし |
| パターンの引数の個数 | `Shape.Rect(w)` | E0412（`name` は `Shape.Rect`、`expected` は 2、`found` は 1） |
| 整数リテラルの範囲 | `9223372036854775807`、`9223372036854775808`、`-9223372036854775808`、`-(9223372036854775808)` | 2 番目と 4 番目だけ E0408 |
| パターンの整数リテラルの範囲 | 分岐のパターン `-9223372036854775808` と `9223372036854775808` | 2 番目だけ E0408。その `match` は網羅性を検査しない |
| 浮動小数リテラルの範囲 | `1e308`、`1e309` | 後者だけ E0409 |
| 式文 | ブロックの途中の `1 + 2` | E0416 |

## 難易度の理由

02-05 の制約の生成の表は一行ずつは短いが、パイプとプレースホルダの展開、多相な名前の置き換えと記録、本体のエフェクトの種類ごとの理由の付け方、リテラルの範囲、派生した誤りの抑止を、すべて整合させる必要がある。出力の表は脱糖が前提にするので、記録の漏れは後の段で初めて処理系の不具合として現れる。宣言の検査にも、等値の型の要約の不動点の計算とエフェクト変数の規則がある。
