# 第I部 言語設計

## 1. パラダイムと評価戦略

FP要素ごとに、スクリプト実行モデルへの依存度が大きく異なる。

| 機能 | 実行モデルへの依存度 | 補足 |
|---|---|---|
| ADT・パターンマッチ | ほぼなし | フロントエンドの話 |
| Hindley-Milner型推論 | ほぼなし | 同上(ただし2.3・2.4の制約あり) |
| 型クラス(辞書渡し) | 小 | インスタンス解決は静的解析で完結 |
| 末尾呼び出し最適化 | 中〜大 | 再帰が基本操作なので優先度高。Go自体はTCOを持たないため、VM側で実現する |
| 暗黙の遅延評価(Haskell的) | **大** | 評価器の作り替え、副作用モデルとの不整合、スペースリーク |
| 明示の遅延評価(Scala/Clojure的) | 小 | 局所的な追加で済む |

【決定】正格評価をデフォルトとし、遅延は明示構文でオプトイン。TCOまたは `recur` 的な明示ループ構文を早期に用意する。

【決定】当初の3択(純粋/非純粋/マルチパラダイム)に対し、**Scala寄り(非純粋・正格)+Flix的な効果追跡**を採る。なお「正格評価の選択」と「非純粋性の選択」は独立した判断であり、一方が他方を含意するわけではない。

## 2. 型システム

### 2.1 基盤
HM型推論+型クラス(辞書渡し)。厳密には型クラスを入れた時点で「素のHM」ではなく限定型(qualified types)の推論になる。

### 2.2 型クラスの一貫性(coherence)
問うべき性質は「解決順序に依存しない」という実装上の決定性ではなく、**異なる有効な型付け導出・辞書翻訳から得たプログラムの意味が一致すること**。孤立インスタンス(orphan instance)や重複インスタンスの規則をここで決める必要がある。

### 2.3 表層構文とHM推論の緊張関係 【未決】
LLMフレンドリーさのために表層構文をScala/Rust/Goに寄せる方針(23章)だが、`x.method()` のようなドット記法は、`x` の型が分からないと `method` を解決できない(型主導の名前解決)。これは制約を順に解くHMとは相性が悪く、OCaml/Haskellがドット記法を避けている理由でもある。また、Scala的なサブタイピングを入れるとHMの主要型が失われる(Scalaが局所型推論である理由)。

選択肢:
- (a) サブタイピングは入れない。ドット記法は「モジュール修飾」または「パイプ `|>` の糖衣」に限定する(Gleam・F#・Roc系)
- (b) ドット記法を型主導で解決し、解決できない箇所には型注釈を要求する(Rust系。推論は局所的になる)

いずれにしても、構文決定の前に型推論側の制約として確定させるべき事項。

### 2.4 可変状態とlet多相 【未決】
可変参照を含む式を無制限にlet一般化すると型安全性が崩れる(OCamlのvalue restrictionの理由)。可変セルやGo interopのハンドルを公開する以上、(a) value restriction(または relaxed value restriction)、(b) 可変状態の生成を効果に閉じ込めて一般化を制限、のいずれかを決める。効果ハンドラと多相性の組合せも同種の問題を持つため、コア計算(25章)の検証対象として適切。

### 2.5 基本型の意味論 【未決・元資料に欠落】
Go interopと診断基盤に直結するため早期に決める。
- **文字列**: Goの `string` はUTF-8のバイト列。言語側の `String` の添字・長さをバイト/コードポイント/書記素のどれで定義するか。LSPの既定位置エンコーディング(UTF-16)との変換も8章の内部表現で扱う
- **整数**: Goの `int64` は黙ってラップアラウンドする。任意精度 / 固定幅+オーバーフロー検出 / 固定幅+ラップ のどれにするか
- **エラー**: Goの `error`・`panic` と、言語側の `Result`・例外(持つなら)の対応規則

## 3. エフェクトシステム

### 3.1 なぜ必要か
層3(go.*)から生のGo stdlibを呼べる以上、ファイルI/O・プロセス終了・乱数・goroutine起動などあらゆる副作用が可能になる。効果追跡がなければ型から純粋性を判断できず、メモ化・並列化の安全性やDI(24章)の前提が崩れる。

### 3.2 3つの別々の機構
以下は概念として別物であり、自動的には結びつかない。
- **効果型(静的な追跡)**: 計算が要求する効果を表す型情報。例: `IO[String]`
- **ハンドラ**: 効果の意味・制御の戻し方を与える実装
- **実行権限制御**: その実行主体に具体的にどの操作を許すか

`IO[String]` という型だけでは「このディレクトリの読み取りだけ許可」は表現できない。ケーパビリティ値による権限制御が実効性を持つには、(1)利用者コードが偽造できない、(2)許可外の資源への参照を得る経路がない、(3)生interopを含む全経路が同じ制御を通る、の3条件が必要。**go.* から `os.Open` を直接呼べる経路が残る限り、ケーパビリティは迂回可能**。

### 3.3 方式と段階的ロードマップ

| 方式 | コスト | 概要 |
|---|---|---|
| (a) 単一の粗い `IO[T]` | 低 | go.* 経由は全て一律IO |
| (b) ケーパビリティ渡し | 中 | 既存の型システムで実現可能。3.2の条件下で権限制御にもなる |
| (c) 代数的エフェクト | 高 | 効果の区別・効果多相・推論・ハンドラ(Flix/Koka/Unison流)。HMとは行多相(row polymorphism)で自然に統合できる(Koka) |

【方針】
1. go.* 経由は全て `IO[T]`。IOの実行時期・順序・失敗時の扱いを定義する
2. 同時に、`os.Exit`・`exec.Command` 等はケーパビリティなしには呼べないようにする。ただし3.2の迂回経路を塞がない限り実効的な権限制御ではない
3. 人間が純粋と確認したGo関数から層2へ昇格
4. 代数的エフェクトへ発展。ただし(a)(b)(c)は前段を置き換える一直線ではなく、最終構成でも併用しうる独立の軸

Goには純粋性の注釈がなく自動判定は事実上不可能なので、go.* は実態に関わらず保守的にIO扱いとする。なお乱数は「生成器の状態を明示的に引き回す純粋関数」として層2に置く余地がある(Haskellの `System.Random` にも純粋APIがある)。

### 3.4 IOで包むだけでは純粋にならない
IO値の**構築時に**Go関数を実行し、結果をIO型に格納するだけでは副作用は分離されない。実行器が明示的に評価するまで遅延させる必要がある。また、IOから得た可変Go値(`*bytes.Buffer` 等)の読み取り・別名参照経由の書き込みも同じ規則の対象になる。オペーク値で包んでも値自体が不変になるわけではない。

### 3.5 IOの公開インターフェース 【未決・抽象型を推奨】
利用者がIOのコンストラクタにパターンマッチできると、その構造が公開APIになり、後から内部表現(3.6)を差し替えられなくなる。`pure`・`map`・`flatMap` 等の操作だけを公開する**抽象型**にしておけば、実装方式を自由に変えられる。性能最適化より先に決めるべき事項であり、本改訂では抽象型を推奨とする。

### 3.6 IOの内部実装方式
- **自由モナド的なデータ表現**: ADT+継続クロージャでGoに自然に表現でき、トランポリンでGoスタックも消費しない。ただし素朴な実装は左結合のbind列で計算量が悪化しうる
- **効率的な表現**: Freer(実装形式)、Church/Codensity(継続による表現変換)、type-aligned sequence(bind追加をO(1)にするキュー構造)は別々の技法。構築・実行・再解釈それぞれの計算量を区別して選ぶ
- **VMオペコードへの直接コンパイル**: 自作VMの利点を活かし、IO操作をVM専用オペコード化し、ディスパッチ先を差し替え可能なGo関数テーブルにする(本番/テストでハンドラを入れ替え)。継続の利用回数やハンドラの動的スコープの保存に注意。Rocのplatformが近い発想だが、一般化はしない

【方針】3.5で抽象型にする前提なら、v1から素朴な自由モナドを経由する必然性は薄い。実装の分かりやすさで選び、実測(左結合の長いbind列・深い再帰・効果の多い処理)で判断する。なお「Python/Ruby水準」はOS連携の水準についての方針であり、速度目標として合意したものではない。

## 4. リソース管理
OSリソース(ファイル・接続・WASMインスタンス)の決定的な解放は、GC(メモリ回収)とは別問題。ファイナライザは非決定的でリークしやすいため、Haskellの `bracket` / Rustの `Drop` に相当する**明示的なリソーススコープ構文**を用意する。エフェクトシステム(3章)と一体で設計する。

## 5. 並行処理

【方針】実装するかは未定。実装する場合もリリース後、標準ライブラリ相当として提供する。

### 5.1 既存FP言語のモデル

| モデル | 先行事例 | 特徴 |
|---|---|---|
| アクター | Erlang/Elixir、F# `MailboxProcessor` | 状態共有なし。F#は標準ライブラリで専用構文不要 |
| CSPの後付け | Clojure `core.async` | `go` ブロックを状態機械へ変換。任意のブロッキング操作が協調的になるわけではない |
| ランタイムの軽量スレッド | Haskell `forkIO`+STM、Racket threads/places | STMは合成可能なトランザクション |
| エフェクトハンドラで表現 | OCaml 5 | 並行APIをライブラリとして分離する基盤になるが、スケジューラ・I/O待機・取消・例外伝播は別途実装が必要。また静的な効果安全性は提供しない |
| ホストに委譲 | Gleam(BEAM) | 実績あるモデルを継承 |

### 5.2 Go実装であることの分岐
- **A(推奨寄り)**: 言語のプロセス/チャネルをgoroutine/channelに薄くマッピング。(i)評価器の共有状態をロック/アトミックで保護、または(ii)プロセスごとに独立VMを持たせメッセージパッシングのみ、のいずれか。どちらでも可変Go値・コールバック・終了処理の同期が必要
- **B**: 独自スケジューラ。決定的な実行順序でテストしやすいが、Goの再実装になる

WASMコア(21章)を採る場合、単一スレッド・host呼び出し中の全goroutineブロックにより、Aの前提(M:N並列)は成り立たない。

不変コレクション(10章)はメッセージパッシングを安全にするが、要素に可変なGoハンドルを入れられる場合、要素の安全性までは保証しない。

### 5.3 今決めるべきこと
- **今**: 評価器/VMを複数goroutineから再入可能に設計するか(spanと同じく後付けが難しい)
- **後回し可**: チャネル/アクター/STMの選択、実装時期

# 第II部 処理系

## 6. 実行モデルとアーキテクチャ

- スクリプト形式の実行(シェバン対応を含む)をサポート
- 【決定】基準案は**自作バイトコードVM**。将来の単一バイナリ化は `go:embed` によるソース/バイトコード埋め込みで実現
- 代替案: 言語→Goソースへのトランスパイル→`go build`。学習順序としては VM → トランスパイル を推奨。ただしトランスパイル方式は利用時にGoツールチェーンを要求する点、3.6のVMオペコード最適化とは別経路になる点に注意
- 【未決】VMの再入可能性(5.3)

## 7. メモリ管理(GC)

【決定】自作GCは不要。言語の値を通常のGoヒープオブジェクトとして表現すれば、GoのGCが管理する。VM方式でもトランスパイル方式でも同じ。yaegi・gopher-lua・Tengoも独自GCを持たない。永続コレクションのノード(HAMT等)も通常の構造体・ポインタで実装すればそのまま扱える。

性能面: GoのGCは非世代別・非移動の並行マーク&スイープ。Go 1.26でデフォルトになった Green Tea GC は小オブジェクトのマーク/スキャンを改善しており、FP的な短命小オブジェクト大量生成に効く方向の改善。いずれにせよ実測してから対策する。

自作が必要になるのは、`unsafe` による非ボックス化表現や独自アリーナを導入する場合のみで、v1では想定しない。

## 8. 診断基盤(エラーメッセージ・MCP・LSP)

### 8.1 アーキテクチャ
```
コア: lexer / parser / 型検査器 → 内部診断データ(プロトコル非依存)
        ↓                ↓               ↓
   CLI (yourlang check)   MCPサーバ        LSPサーバ
                          (Agent向け)      (エディタ向け・優先度低)
```
- MCPはGo公式SDK(`github.com/modelcontextprotocol/go-sdk`)でstdio実装が軽量
- MCPツール例: `check(code)`, `run(code)`, `explain(error_code)`, `search_stdlib(query)`

### 8.2 内部診断表現
LSPの `Diagnostic` を直接内部形式にせず、**ファイルID・span・診断コード・補助位置・修正案**を持つ独自表現とし、各アダプタで変換する。LSPの位置はGo文字列のバイト位置と一致しない(位置エンコーディングはネゴシエーション対象)。脱糖などで生成された合成ノードの由来位置の扱いも定義する。

### 8.3 Rust風エラーメッセージ
【決定】**spanを全ASTノードの必須フィールドとして字句解析器・構文解析器の最初の版から入れる**(後付け困難)。
実装難易度: エラーコード+解説(低)< `expected X, found Y`(低〜中)< span+ソース抜粋(中・必須)< `help:` の自動修正提案(高・後回し)

### 8.4 実装順序
1. span必須のコア解析エンジン → 2. `check` CLI → 3. MCPの `check`/`run` → 4. LSP(診断のみ) → 5. ホバー・補完・`help:`

## 9. 性能の見込み(定性)

スクリプト言語の実行性能はおおむね3層に分かれる。
1. **ボックス化された値の素朴なインタプリタ**: CPython、Ruby MRI(JITなし)、Perl
2. **非JITだが効率的な設計**: PUC-Lua(レジスタVM+コンパクトな値表現)
3. **JIT搭載**: V8、LuaJIT、Ruby YJIT

本言語(JITなしVM)は第1層付近が目安。ただし2点補正する。
- **静的型付けの利点**: HM型検査済みなので、動的言語が払う実行時型チェックの多くを省ける。これは第1層より有利に働く
- **Goホストの不利(元資料の「CPython/Ruby MRIと近い状況」を修正)**: CPython等はC実装で computed goto によるディスパッチ等が使えるが、Goには computed goto がなく、配列の境界検査、interface経由の値表現、GCのライトバリアも評価ループに乗る。Go製インタプリタ(gopher-lua、goja等)はC製の同種処理系より遅い傾向がある。よって**素朴に作ると第1層の下側になる可能性も考慮する**【要検証】

第2層に近づける手段は、値表現のコンパクト化(タグ付き構造体で interface を避ける等)とレジスタVM化。JITはiOS制約(22章)とも衝突するため、v1では対象外。

# 第III部 Go相互運用と標準ライブラリ

## 10. 3層ライブラリ構造

Go stdlibの多くはポインタ経由の可変状態を前提にしているため、そのまま公開せず、慣用的なライブラリを被せる。先行例: F#の `list`、Clojureの永続コレクション、Elmの完全隠蔽、Scala.jsの `js.Dynamic`。

```
層1: core / prelude — 言語独自。永続コレクション、Option/Result、ADT
層2: std           — 慣用ラッパー。値渡し的APIはほぼ1:1、可変APIはカプセル化
層3: go.*          — 未対応Go APIへの低レベル脱出口。自動生成の対象、一律IO
```

層2への分類基準:
- **(a) 薄くラップ可**: `strings`・`strconv`・`math`、ワンショットのハッシュ関数(`sha256.Sum256`)
- **(b) カプセル化で隠蔽可**: `strings.Builder`・`bytes.Buffer`・`sort`、状態を持つ `hash.Hash`
- **(c) 作り直し**: 永続コレクション、並行プリミティブ、ストリーミングI/Oの遅延シーケンス化

判定はパッケージ名や値渡しの形だけでは決まらない。スライスは値渡しでも基底配列を共有しうるため、引数の別名参照・戻り値・呼び出すコールバックまで確認して昇格させる。

層1の永続コレクション(Okasaki『Purely Functional Data Structures』)は学習上の本丸として腰を据えて取り組む。進め方は「層3を自動生成で先に立ち上げ、層1を育てる」。

## 11. 自動ラッパー生成

### 11.1 先行事例: yaegi `extract`
公開シンボルを静的解析で列挙し、`reflect.ValueOf(...)` を用いたGoソースを `go generate` で生成。Goバージョンごとにビルドタグ付きファイルに分離。`unsafe`・`syscall` を除外し、`os.Exit`・`exec.Command` 等は `unrestricted` パッケージに隔離してオプトイン。

### 11.2 生成パイプライン案
1. `go/packages`+`go/types` で公開シンボルの型情報を取得
2. シグネチャを分類(単純な値変換 / `(T, error)` / コールバック引数 / interface引数 / メソッド)
3. 分類ごとにトランポリン関数を生成(`text/template` または `go/ast`+`go/format`)。yaegiとの違いは、生のGo値ではなく Result/Option・クロージャ表現への**型変換を行う関数**を生成すること
4. バージョン別ファイルとして出力

### 11.3 注意点
- **ビルドタグ**: `//go:build go1.19` は新しいGoでも真になる。下限タグだけで版別ファイルを併置すると重複定義・登録の上書きが起きる。最低対応版の共通生成物+追加差分、または上限条件を設ける
- **型分類だけでは決まらない変換規則**: `(T, error)` の部分結果(`io.Reader.Read`)、`nil` と typed nil、公開変数、ポインタ同一性、panic、呼び出し後も保持されるコールバック
- **ジェネリクス**: 型パラメータを持つGo関数はリフレクションで未具体化のまま呼べないため、具体化する型を生成時に決める必要がある(元資料に欠落)
- 「大半の関数をオペークハンドルで扱える」割合は未検証【要検証】

## 12. ラップ対象外・困難なもの

- **除外**: `unsafe`(型安全性の前提が崩れる)、`plugin`(実行時 `dlopen` 前提で静的配布と非互換)
- **cgo**: 単一バイナリと原理的に非互換ではない(外部リンカによる静的リンク構成がある)。【決定】v1ではビルド・クロスコンパイル簡素化のための**製品方針**として `CGO_ENABLED=0` を採り、cgo依存ライブラリは対象外。逆に「cgoなら常に静的配布できる」とも断定しない
- **goroutine/channel・非同期コールバック**: `net/http` サーバーのように任意のgoroutineからコールバックされるAPIは評価器アーキテクチャの課題(5.3)。v1は同期的に完結するAPIのみ
- **可変前提API**: `*bytes.Buffer`・`io.Writer` 等。10章で対処

## 13. Goバージョン追従

- **追加**: 新リリースごとに新旧シンボル差分を取るCIジョブ。単純なものは自動生成、難しいものは人がレビュー
- **削除**: Go 1互換性保証によりほぼ起きない。防御的に「ラップ済みシンボル消失でCIを落とす」
- **非推奨**: `// Deprecated:` を生成時に検出し言語側でも警告
- **周期**: Goは年2回の major release(1.x)。1.x.y は minor revision
- **限界**: 互換性保証にはセキュリティ修正・未規定動作・バグ修正・`unsafe`/OS境界の例外がある。名前の増減は検出できても意味の変化は検出できない。自動化は「検出と単純な生成」までとし、振る舞い検証・公開判断は別工程。層2も層3経由でGoの挙動に依存するため、影響を層3に完全には閉じ込められない

## 14. 相互運用のテスト

1. **差分テスト**: 言語経由の呼び出しとGo直接呼び出しを比較。同一の前提・初期状態が必要。層2で意図的に意味を変えた箇所は言語側仕様を正とする。時刻・乱数・ファイルに依存する関数は単純比較できない
2. **Fuzzing**: `go test -fuzz` は書かれたfuzz targetの入力探索を自動化するもので、比較ロジックや有効入力範囲は自分で書く
3. **stdlibの `_test.go` からのテーブル抽出**: リテラル中心のテーブルなら `go/ast` で抽出可能。補助関数や動的な期待値を含むものは困難。`strings`・`strconv`・`encoding/json` から着手

最低ラインは全ラップ関数の自動スモークテスト(型検査が通る)。「panicしない」を一律の合格基準にはしない(panicが仕様の入力、ブロックする操作、状態変更する操作は別基準)。

# 第IV部 OS連携・シェル

## 15. 位置づけ

【決定】POSIX sh 準拠は採らず、**Python/Ruby と同水準のOS連携**に留める。理由は不可能だからではなく、**互換モードの実装・維持コストが、一貫した構文・学習目的・LLMフレンドリーな文法という設計目標に見合わない**から。

POSIX shの意味論を再現しようとした場合の摩擦(不可能性ではない):

| 観点 | 摩擦 |
|---|---|
| 型 | 単語分割は `String -> List[String]` として表現可能。算術展開の暗黙の数値化は摩擦として残る |
| スコープ | `export`(子プロセスへの環境継承)と言語内スコープは別物。位置パラメータは関数呼び出し時の一時置換 |
| 効果 | `$?` は暗黙のグローバル状態。`$(...)` はパーサが効果を付与できる。`pipefail` は POSIX.1-2024 に含まれる |
| 並行 | 外部プロセス間のパイプは自作VMの再入を要しない。ジョブ制御と `trap`(実行タイミング規則あり)は課題 |
| 構文 | 文脈依存のクォート除去・展開順序で文法が不規則になり、LLMフレンドリーの方針と相性が悪い |
| 低レベル | ジョブ制御は処理系内部で `syscall` を使いうるが、それを利用者に公開することとは別 |

先行事例 **Babashka** は「bashを置き換えず協調する」と明言しており、本方針と同じ位置づけ(付録B)。

## 16. API設計

- (a) **実用サブセット**: 外部コマンド実行・パイプ・単純なリダイレクト・基本的な制御構造。単語分割・動的スコープ・ジョブ制御・`trap` は対象外
- (b) **本物のシェルへの脱出口**: `sh("...")` を1つの効果付き呼び出しとしてシステムのシェルに委譲。実行環境に互換シェルが存在することに依存する

【決定】(b)を主軸に(a)を併用。**引数配列・作業ディレクトリ・環境を明示して直接起動する `exec` 系API** と、**文字列をシェルに解釈させる `sh(...)`** は別APIとする(`os/exec.Command` 自体はシェル構文を解釈しない)。

優先的にラップするstdlib: `os`, `os/exec`, `io`, `bufio`, `path/filepath`, `strings`, `encoding/json`。

# 第V部 拡張

## 17. 外部Goライブラリ

生成パイプラインは標準/外部を区別しないため技術的には適用可能だが、公開APIに現れる型の**推移閉包**全体への対応が必要になり、外部ライブラリ対応はstdlib対応状況に依存する。

緩和策:
- 中身を解釈しない汎用**オペークGo値**型(一度作れば広く効く)
- **橋渡し型**への優先投資: `error`・`context.Context`・`io.Reader`/`io.Writer`・`time.Time`/`time.Duration`
- コールバック・interface実装・ジェネリクスを含むAPIは個別対応。cgo依存は12章の製品方針により対象外
- 外部ライブラリにはGo本体のような互換性保証がないため、バージョン固定・断念基準を別途定める

【決定】公式サポートは基盤(オペークハンドル・橋渡し型)+go.* 経由の汎用素通しまで。人気ライブラリのネイティブラッパーはコミュニティに委ねる。

## 18. プラグイン境界

- **密結合(言語製ライブラリを静的リンク)**: Cargo/Cabal/go.mod 型の標準的パッケージ管理を踏襲すればよい
- **疎結合(言語非依存)**:

| 系統 | 先行事例 | 特徴 |
|---|---|---|
| 常駐RPC | HashiCorp `go-plugin`、Neovim、Babashka pods | 別プロセス+ローカルRPC。プラグインは別実行ファイルになるため「ホストが1ファイル」と「配布一式が1ファイル」は別 |
| 単発exec | CNI | 呼び出しごとに起動、stdin/stdoutでJSON |
| WASMサンドボックス | Extism | プロセス内サンドボックス。`go:embed` と両立しうる |

多くはHTTPではなく stdio/Unixソケット+軽量RPC(gRPC・MessagePack・bencode)を使う。仕様に含めるべき要素: トランスポート、メッセージ形式、型のマーシャリング規約(推移閉包問題と直結)、バージョニング・ディスカバリ、エラー伝播とプロセス障害時の扱い。

【方針】単一バイナリ化・セキュリティ・言語非依存性を同時に満たす候補として**WASM系統が有力**。

## 19. WASMプラグイン基盤

### 19.1 ランタイム
自作はJSエンジン自作並みの規模なので既存OSSを使う。`CGO_ENABLED=0` の下では **wazero**(Go製・依存ゼロ・Core Spec 1.0/2.0)が事実上唯一の選択肢。wasmtime-go/wasmer-go はcgo経由のため、製品方針と不一致で不採用。
- Interpreterモード: 全Goターゲットで動作、実行時コード生成なし(iOSでも使える見込み、22章)
- Compilerモード: 大幅に高速、amd64/arm64限定、実行時にネイティブコードを生成

### 19.2 ABIは自作
wazeroはバイトコード実行と線形メモリ管理のみ。`Result[T]` やADTの線形メモリ上の表現(ABI)は別途必要。【方針】実行エンジンは既存OSS、ABI・マーシャリング規約は型システムと一体で自作(Extism規約に乗る選択肢もある)。

### 19.3 エフェクトとの合流
WASMはデフォルトでOS資源にアクセスできず、ホスト関数(またはWASI)経由でのみ許可される。これはケーパビリティ渡し(3章)と同型であり、go.* 向けとプラグイン向けの権限制御を同じパターンで扱える可能性がある。

### 19.4 メモリ管理の責任分界
プラグイン内部のメモリ管理は実装言語次第(Rust: 所有権 / 標準Go: 線形メモリ内に独立したGoランタイム+GC / TinyGo: 独自GC / C: 手動 / AssemblyScript: 軽量GC)で、ホストからは不可視。ホストが管理すべきは:
1. **インスタンスのライフサイクル**: `module.Close(ctx)` を明示スコープ(4章)で管理
2. **境界を越えるデータ**: プラグイン側の `alloc`/`free` を使う明示プロトコル。どちらのGCも生存を管理しない

`WithMemoryLimitPages` で制限できるのは**ゲストの線形メモリ単位**。コンパイル済みコード・エンジン管理情報・host関数のGo側確保・複数インスタンスの合計は別途管理が必要。

# 第VI部 配布・プラットフォーム

## 20. 単一バイナリ

【決定】依存なしの単一バイナリ生成は言語仕様策定時に考慮し、実装は後回し。基準案は VM+`go:embed`(6章)。`CGO_ENABLED=0` によりクロスコンパイルが容易。

Agent Skills の文脈では、**スキルを実行する環境に処理系がどう入るか**(スキル同梱のバイナリか、事前インストールか、初回取得か)が実運用上の最大の論点になる。単一バイナリはこの点で効く(23章)。

## 21. WASMコア化(条件付き代替案)

【方針】現時点では基準案にしない。OS連携を試作して必要な追加実装量を確認してから採否を決める。19章のWASMプラグイン基盤とは独立した判断。

構成案:
```
① 処理系コア(GOOS=wasip1 GOARCH=wasm)→ interpreter.wasm(全プラットフォーム共通)
② 各プラットフォーム向けに、wazero+①を go:embed したネイティブランチャー
```
- Go 1.21(2023年8月)で `wasip1` が標準対応
- TinyGo はバイナリが小さいがstdlibは部分集合。cgoは Clang 経由で対応(対応範囲に制限あり)。GCモードはターゲット依存
- `wasm-opt`(Binaryen)で後処理最適化

**wasip1の制約**:
- ソケットの新規作成ができない(既に開かれたソケットへの操作のみ)。`net/http` サーバーは標準 `wasip1` で動かない
- 真の並列実行がない。host関数呼び出し中は全goroutineがブロック

このため、外部コマンド実行・ネットワーク・Go interop・プラグイン呼び出しをネイティブランチャー側に実装し、host import 経由で呼ぶ設計が必要になる(ハンドル表・マーシャリングを含む)。「起動するだけの薄いランチャー」では済まない。また `.wasm` 単体は実行可能ファイルではなく、「全プラットフォーム共通」はランタイム依存への置き換えでもある。WASIの縮小POSIX的な思想は15章と一致するが、縮小の度合い(ネットワーク・並行性)は想定より大きい。

## 22. モバイル・Android系プラットフォーム

将来スマートフォン・タブレット・デスクトップ的Android(Googlebookを含む)でコーディングハーネスを動かす展望について。

### 22.1 iOS
- **JIT(実行時コード生成)はOSレベルで不可**: `com.apple.developer.cs.allow-jit` はブラウザエンジン等に限られる。wazero Compilerモードは使えない見込みで、Interpreterモードに倒す。**JITなしVMである本処理系自体は衝突しない**(macOSのHardened Runtime用 `com.apple.security.cs.allow-jit` とは別物)
- **サブプロセスを起動できない(元資料に欠落、影響大)**: iOSのサンドボックスでは `fork`/`exec` による外部プロセス起動が許されない。したがって16章の `exec` 系APIと `sh(...)` は動かず、シェルもない。Agent Skills の多くはシェル・外部コマンドを前提にするため、iOSでは「言語処理系は動くがスキルの大半は動かない」可能性が高い。iOS向けには exec/sh を持たないプロファイル(ケーパビリティが最初から存在しない構成)として定義するのが自然【要検証】
- ビルド: `GOOS=ios` は cgo(外部リンク)を要求する

### 22.2 Android
- JITやインタプリタの自作にOSレベルの障壁はない
- **実行可能ファイルの配置制約(元資料に欠落)**: targetSdk 29(Android 10)以降、アプリの書き込み可能領域に置いたファイルを `exec` できない(W^X)。処理系をアプリに同梱する場合はネイティブライブラリ領域に配置する等の手当てが必要。ダウンロードした外部バイナリを実行する運用は取れない【要検証】
- ビルド: gomobile でアプリに組み込む場合は cgo が必要。単体のCLIバイナリ(Termux等で使う形)なら `CGO_ENABLED=0` で作れるはず【要検証】。いずれにせよ12章の方針に「ターゲットごとの明示的な例外」を設ける

### 22.3 Googlebook
元資料では2026年5月発表、Android/ChromeOS統合基盤、2026年秋にOEM各社から発売予定とされている。本改訂者はこれを独自に確認できていない【要検証】。Android基盤であれば22.2の範囲でほぼ吸収され、差分は主にデスクトップ的UI層になる見込み。

### 22.4 ストア審査
OS技術制約とは別に、App Store/Play Store の審査ポリシー(ダウンロードしたコードの実行等)がある。スキルをアプリ内蔵にするか都度取得するかで適用が変わるため、運用上の課題として別途整理する。

| 環境 | JIT | 本処理系 | wazero Compiler | wazero Interpreter | 外部プロセス起動 |
|---|---|---|---|---|---|
| iOS | 不可 | 影響なし | 不可の見込み | 可の見込み | **不可** |
| Android | 可 | 影響なし | 可 | 可 | 可(配置制約あり) |
| Googlebook | Androidに準ずる見込み | 影響なし | 同左 | 同左 | 同左 |

# 第VII部 エージェント対応と利用者向けテスト

## 23. Agent Skills・Agentic Coding への対応

学習データにない言語をエージェントに書かせるための方針。

### 23.1 短中期
1. **コンテキスト供給**: 文法(EBNF)・stdlibリファレンス・イディオム集・よくある誤り集・既知言語との対応表をAgent Skillとして整備。Agent Skillsは必要に応じた段階的読み込みを想定しており、全文が毎回注入されるわけではない
2. **フィードバックループ**: 構造化された具体的な診断(8章)で「コンパイル→読解→修正」だけで収束させる
3. **LLMフレンドリーな言語設計**: 不規則な構文・特殊ケースを減らし、既知言語に寄せた表層構文にする(2.3の型推論上の制約と両立させる)
4. **制約付き生成**: tree-sitter文法等による構文制約付き生成は補助策。ただしエージェント側がその機構を持つ必要がある

### 23.2 中長期(訓練データに入るために)
public リポジトリの継続公開、テキスト中心でクロール可能な公式ドキュメント、Q&Aの蓄積、Rosetta Code への掲載、一貫したパッケージドキュメント、`llms.txt` 対応。

### 23.3 結論
【決定】言語仕様・stdlibリファレンス・イディオム集を**専用Agent Skillとして言語の公式配布物に同梱**する。訓練データに入るのはボーナス。

### 23.4 セキュリティの役割分担(元資料の補足)
言語内のケーパビリティ(3章)は「スキルが意図せず危険な操作をしない」ための設計上の防壁であり、敵対的なコードに対する隔離はエージェント側ハーネスのサンドボックス(コンテナ・OS権限)が担う。3.2の迂回経路の問題もあるため、言語側だけでセキュリティ境界を完結させる前提は置かない。

## 24. 利用者プログラムのテスト

### 24.1 DI
DIの成立条件は「差し替えたい依存を外部から供給できること」だけで、IOの内部表現(即時実行かデータ構造か)とは独立。
```text
loadConfig(readText, path) = parseConfig(readText(path))
本番:   loadConfig(osReadText, "app.conf")
テスト: loadConfig(path => "port=8080", "app.conf")
```
ケーパビリティ渡しなら偽のケーパビリティを引数で渡すだけ、代数的エフェクトならハンドラ差し替えだけでよく、DIコンテナは不要(先行例: Haskell tagless final/free、ZIO の `R`、Elm `Cmd`)。free encoding の利点(実行前検査・別インタプリタでの解釈)はDIとは別の利点。

### 24.2 テストランナー
Go `testing` の慣習(表形式テスト)を参考に `yourlang test` としてCLIに統合。

### 24.3 プロパティベーステスト
ADTの構造からジェネレータを合成するderive機構と、基底型の生成・縮小規則を用意して自動生成を**支援**する。値の分布・再帰の大きさ・縮小・アプリ固有の不変条件は型情報だけでは決まらない(QuickCheckの `Arbitrary` 同様)。14章のGo fuzzing基盤との共有は選択肢として扱う。

# 第VIII部 形式的検証

## 25. 仕様記述と証明

### 25.1 証明したい性質の分解
- **型健全性**(progress/preservation): 値・例外・効果・発散をどこまで意味論に含めるかを決めないと保証内容が確定しない。終了性や業務上の正しさは含意しない
- **型クラスのcoherence**(2.2)
- **エフェクトシステムの健全性**: 純粋と宣言された関数が副作用を起こせないか(DIの成立とは独立だが、それ自体に価値がある)
- **並行プロトコル**: デッドロック・レースの不在

道具は性質とモデルで選ぶ。「型理論系=証明支援系、並行=モデル検査」という分類は排他的ではない(Iris は Coq 上で並行性を扱い、TLA+ にはTLCに加え証明系TLAPSがある)。

### 25.2 進め方
言語全体ではなく小さな**コア計算**を定義し、表層構文はそこへの脱糖として定義する(Featherweight Java 系統)。コアでの証明を処理系全体に適用するには、脱糖・コンパイル・FFI(go.*)の意味保存が別途必要。RustBelt や DOT の規模を踏まえ全体証明には早期着手しないが、「小さな言語の全体証明は常に非現実的」とまでは言わない。

1. **段階0(紙と鉛筆)**: BNF、型付け規則・簡約規則を数学記法で記述
2. **段階1(PLT Redex)**: 実行可能な意味論+ランダム生成による反例探索(証明ではない)。現段階の不確実性に見合う投資
3. **段階2(証明支援系)**: 学びたい性質と最も壊れやすい機能の組合せから対象を選ぶ。2.4(可変状態とlet多相)、3章(効果とハンドラと多相)は有力候補

### 25.3 ツール候補

| ツール | 特徴 |
|---|---|
| Coq(Rocq) | PL形式化の定番。Software Foundations |
| Agda | パターンマッチ定義が簡約規則と自然に対応。PLFA |
| Lean 4 | モダンなタクティック、コミュニティの勢い。学ぶこと自体に価値 |
| F* | SMT(Z3)による自動証明。実装検証まで見据える場合 |
| K Framework | 書き換え論理。意味論を実行可能なリファレンス実装にできる |
| Iris | Coq上の並行分離論理 |
| TLA+ | 状態機械としての並行性。TLC(有限モデル検査、証明ではない)+TLAPS |

## 付録A. 実装言語の比較(Go以外を選んだ場合)

**位置づけ**: 【決定】実装言語はGo。本付録は「もし変えたら何が失われるか」の参考であり、いずれもベンチマーク・試作を経ていない定性評価。

Goで「無料」だったもの: (1) GC(7章)、(2) `go/types` による巨大stdlibの自動ラップ(11章)、(3) goroutine(5章)。

| | Rust | Zig | Swift |
|---|---|---|---|
| GC | 標準なし。`Rc`/`Arc` は循環でリーク。環境・クロージャ・サンクを扱うには自作GCかGCクレートが必要になりやすい | 標準なし。`Allocator` 明示が思想。完全自作 | ARC(循環でリーク、`weak`/`unowned` で手当て) |
| stdlib自動ラップ | proc macro/ビルドスクリプトで部分的に可能。stdlib自体が小さく(HTTP・非同期はクレート)、対象範囲の再定義が必要 | 前提が成立せず、`@cImport` によるCライブラリラップという別設計になる | 実行時リフレクション(`Mirror`)が弱い。Foundation依存の歴史 |
| 並行 | `async`/`await` はあるが実行に Tokio 等の外部ランタイムが必要 | 1.0前で流動的。言語組み込みasyncは一度削除され、`Io` インターフェースによる再設計が進行中【要検証: 版番号】 | `actor`+構造化並行性が言語組み込み。アクターモデルとの親和性が最も高い |
| 単一バイナリ/クロスコンパイル | 良好 | 最も強力(多数のlibcを同梱) | 従来は弱いとされたが、Linux向け静的リンクSDK(musl)が提供されており改善している【要検証】 |
| 加点 | wasmtime/wasmer がRust製。`logos`・`chumsky`・`salsa` 等パーサ/処理系エコシステム | Cとの相互運用、クロスコンパイル | 並行処理設計の完成度 |

定性比較(元資料の工数倍率「1.3〜1.8倍」等の数値は、根拠のない見かけの精度を与えるため本改訂で削除):

| 観点 | Go | Rust | Zig | Swift |
|---|---|---|---|---|
| 処理系の実装難易度 | 低〜中 | 中〜高 | 高 | 中〜高 |
| インタプリタの実行速度(見込み) | 中(9章の不利あり) | 速(ただし自作GC/RCの設計次第) | 速(全て自作次第) | 中(ARC操作が評価ループに乗る) |
| 常駐メモリ(見込み) | 中(ランタイム同梱) | 低〜中 | 低 | 中 |
| 既存インフラ再利用 | 高 | 中 | 低 | 中 |

元資料では Rust の実行速度を「GC一時停止なし」としていたが、上表のGC行の通り実際には自作GCを持つ可能性が高く、その場合はGCコストが生じる。言語選定を見直す場合はプロトタイプで計測する。
