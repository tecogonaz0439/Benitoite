## 目的と範囲

サブコマンド体系（run / check / test / fmt / skill / repl）。

現在の版は、初回リリース版のスタンドアロンモードの CLI を定める（[ロードマップ](../00-overview/00-03-roadmap.md)）。対象は、`run`・`check`・`test`・`fmt`・`skill` のコマンドラインと終了状態、`run` と `check` の振る舞い、`run` を省いた実行とシェバン、予約したサブコマンドの名前、オプション `--licenses` である。`test` の振る舞いと結果の報告の形は[利用者プログラムのテスト](06-04-test-runner.md)で、`fmt` の整形の規則は[フォーマッタ](06-03-formatter.md)で、`skill` が書き出す Skill と書き出す先は [Agent Skills 対応](06-06-agent-skills.md)で定める。最小実行版のサブコマンドは `run` と `check` である。`test`・`fmt`・`skill` とシェバンによる実行は初回リリース版で、`repl` は初回リリース版の後で加える。

初回リリース版の CLI は、処理系をサーバとして動かさずに起動する形（スタンドアロンモード）だけを持ち、実行時の権限制御と OS のサンドボックスを掛けない。サーバモードのサブコマンド（`server …`）と MCP サーバの `mcp` は、初回リリース版の後に加える（[ADR 0177](../decisions/0177-server-mode-after-first-release.md)）。サブコマンドの体系は [ADR 0181](../decisions/0181-server-subcommands.md) と [ADR 0182](../decisions/0182-mcp-server-as-stdio-relay.md) で決めた。オプションと振る舞いは[サーバモード](06-07-server.md)で定める。スクリプトに署名を付ける `sign` と、署名を検証する `verify` も、サーバモードとあわせて通常のサブコマンドとして加える（[ADR 0190](../decisions/0190-ssh-signatures-for-scripts.md)）。これらのサブコマンドの名前は、初回リリース版で予約する（後述の「予約したサブコマンドの名前（初回リリース版）」）。

サーバモードを加えた後のスタンドアロンモードは、サーバが書く利用者単位の方針のファイルを起動のたびに読む。このファイルは、後述の「処理系は、プロジェクトの設定ファイルを読まない」の対象外である（[ADR 0187](../decisions/0187-standalone-reads-user-policy-file.md)）。そのときのスタンドアロンモードは、スクリプトを OS のサンドボックスを掛けた子プロセスで実行し（[ADR 0204](../decisions/0204-standalone-runs-in-sandboxed-child.md)）、サンドボックスを掛けられないときは警告を出す（[ADR 0197](../decisions/0197-when-os-sandbox-is-unavailable.md)）。詳しくは[サーバモード](06-07-server.md)の「スタンドアロンモード」で定める。

## 前提

`run` と `check` が通す処理系の段は[パイプライン](../02-impl/02-01-pipeline.md)で、`run` の処理の順序は[スクリプト実行と埋め込み](../02-impl/02-11-embedding.md)と[ランタイム](../02-impl/02-09-runtime.md)で、診断の形式は[診断エンジン](../02-impl/02-10-diagnostics.md)で定める。

## 仕様

### コマンドの名前

【決定】処理系のコマンドの名前は `benitoite`、スクリプトのファイルの拡張子は `.bnt` とする。短い別名のコマンド（`bnt` など）は設けない（[ADR 0241](../decisions/0241-command-name-and-extension.md)）。言語の名前は Benitoite である（[ADR 0132](../decisions/0132-language-name-benitoite.md)）。

### コマンドラインの形

【方針】最小実行版のコマンドラインは次の形とする。

```text
benitoite run   [オプション] <スクリプトのパス> [スクリプトの引数...]
benitoite check [オプション] <スクリプトのパス>
benitoite --help
benitoite --version
```

- 処理系のオプションは、サブコマンドの後、スクリプトのパスの前に書く。
- スクリプトのパスより後の引数は、`-` で始まるものも含めて、処理系は解釈せず、書いた順にスクリプトに渡す（`Process.arguments()`。[エフェクト](../01-spec/01-07-effects.md)）。
- スクリプトのパスは一つだけ指定する。拡張子は検査しない。
- 初回リリース版で加える `test`・`fmt`・`skill` のコマンドラインは、後述の「`test` のコマンドライン（初回リリース版）」「`fmt` のコマンドライン（初回リリース版）」「`skill` のコマンドライン（初回リリース版）」で定める。
- `--help` は使い方を標準出力に書き、終了状態 0 で終わる。`--version` は処理系の版と、文字の分類と変換が従う Unicode の版（[標準ライブラリ](../03-interop/03-06-stdlib.md)の「Character」）を標準出力に書き、終了状態 0 で終わる。
- 【決定】初回リリース版では、`benitoite --licenses` を加える。処理系の実行ファイルに埋め込んだ第三者のライセンスの表示を標準出力に書き、終了状態 0 で終わる（[ADR 0235](../decisions/0235-third-party-licenses-generated-and-shown-by-option.md)、[配布形態](../05-platform/05-01-distribution.md)の「ライセンスの表示」）。オプションなので、`run` を省いた実行のスクリプトのパスと取り違えない。

### ディレクトリの指定（初回リリース版）

【決定】初回リリース版では、`run`・`check` のスクリプトのパスに、ディレクトリを指定できる。ディレクトリを指定したときは、そのディレクトリの `main.bnt` を実行を始めるファイルとし、`main.bnt` がなければ使い方の誤りとして終了状態 2 で終わる。ファイルを指定したときは、ファイルの名前によらず、そのファイルを実行を始めるファイルとする（[ADR 0127](../decisions/0127-directory-run-and-root.md)）。

```text
benitoite run ./report            # ./report/main.bnt を実行する
benitoite run ./report/main.bnt   # 同じ
```

- どちらの場合も、実行を始めるファイルがあるディレクトリを根のディレクトリとする。import で取り込めるのは、根のディレクトリとその下のファイルと、標準ライブラリだけである（[名前・スコープ・モジュール](../01-spec/01-03-names-modules.md)、[ADR 0126](../decisions/0126-import-by-module-name.md)）。
- 処理系は、プロジェクトの設定ファイルを読まない。作業ディレクトリや親のディレクトリを辿って設定ファイルを探すこともしない。根のディレクトリは作業ディレクトリに依存しないので、どのディレクトリから起動しても、同じファイルを取り込む。設定ファイルは [OPEN-048](../open-issues.md#open-048) で検討する。
- `test` と `fmt` にディレクトリを指定したときは、`main.bnt` だけでなく、そのディレクトリとその下のディレクトリにある、すべての `.bnt` のファイルを対象とする（[ADR 0206](../decisions/0206-test-command-line-and-exit-status.md)、[ADR 0207](../decisions/0207-fmt-command-line.md)）。`test` では、各ファイルの根のディレクトリは、指定したディレクトリとする。
- Agent Skills から実行するスクリプトは、Skill のディレクトリの下の一つのファイル（と、その下のモジュール）として実行する。スクリプトの置き場所を基準にファイルを扱うには、`Process.scriptDirectory()`（[IO のモジュール](../03-interop/03-07-io-modules.md)の「Process」）を使う（[ADR 0131](../decisions/0131-script-directory-and-permission-base.md)）。

### `run` を省いた実行とシェバン（初回リリース版）

【決定】初回リリース版では、`benitoite [オプション] <スクリプトのパス> [スクリプトの引数...]` を、`benitoite run` と同じ意味とする（[ADR 0135](../decisions/0135-shebang-line-and-implicit-run.md)）。オプションを除いた最初の引数がサブコマンドの名前（`run`・`check`・`test`・`fmt`・`skill`。`skill` は [ADR 0230](../decisions/0230-skill-embedded-and-installed-by-subcommand.md)）か、予約した名前（後述）であれば、サブコマンドとして扱う。サブコマンドと同じ名前のファイルを `run` を省いて実行するときは、`./check` のようにパスとして書く。スクリプトのパスにディレクトリを指定できることも、`run` と同じである。

```text
benitoite report.bnt input.csv        # benitoite run report.bnt input.csv と同じ
benitoite ./check                     # 名前が check のファイルを実行する
```

【決定】スクリプトをシェバンで実行するときは、スクリプトの 1 行目に次の行を書き、ファイルに実行の権限を与える（[字句構造](../01-spec/01-01-lexical.md)の「シェバンの行（初回リリース版）」）。

```text
#!/usr/bin/env benitoite
```

- OS は、`benitoite` に、スクリプトを起動したときのパスとスクリプトの引数を渡す。これは `run` を省いた実行に当たる。`PATH` から見つけたスクリプトには絶対パスが渡るので、サブコマンドの名前と取り違えない。
- Linux は、シェバンの行のインタプリタの名前より後を、空白で分けずに一つの引数として渡す。`#!/usr/bin/env benitoite run` は Linux では動かないので、`run` を書かない形を推奨の形とする。処理系のオプションをシェバンの行に書くには `#!/usr/bin/env -S benitoite --max-call-stack=2GiB` のように `env -S` を使う。`env -S` を持たない環境（BusyBox など）では、この形は動かない。
- シェバンの行に権限を書く仕組みはない。スクリプトは権限を宣言しない。実行時の権限制御は初回リリース版の後にサーバモードとあわせて加える。許可は、利用者単位の方針のファイルで与える（[ADR 0183](../decisions/0183-single-policy-for-all-permission-layers.md)、[ADR 0187](../decisions/0187-standalone-reads-user-policy-file.md)、[サーバモード](06-07-server.md)）。残る細部は [OPEN-052](../open-issues.md#open-052) で決める（[ADR 0177](../decisions/0177-server-mode-after-first-release.md)、[エフェクト](../01-spec/01-07-effects.md)、[ADR 0147](../decisions/0147-remove-permission-declaration-syntax.md)）。
- Windows の OS はシェバンを解釈しない。`benitoite run` か `benitoite <スクリプトのパス>` で実行する。

### 予約したサブコマンドの名前（初回リリース版）

【決定】初回リリース版では、後で加えるサブコマンドの名前 `server`・`mcp`・`sign`・`verify`・`repl` と、加える候補の `lsp`・`package`・`agent` を予約する（[ADR 0209](../decisions/0209-reserved-subcommand-names.md)）。予約した名前を最初の引数に書くと、その機能がまだないことを示す使い方の誤りとして、終了状態 2 で終わる。予約した名前と同じ名前のファイルは、`./server` のようにパスとして書けば実行できる。予約しなければ、`benitoite server` は名前が `server` のファイルを実行し、後でサブコマンドを加えた版で同じコマンドラインの意味が変わる。

### `skill` のコマンドライン（初回リリース版）

【決定】`skill` は、処理系の実行ファイルに埋め込んだ同梱の Agent Skill を、コーディングエージェントが Skill を読み込む場所に書き出し、また消す（[ADR 0230](../decisions/0230-skill-embedded-and-installed-by-subcommand.md)）。

```text
benitoite skill install   [--user | --project] [--agent <名前>]...
benitoite skill uninstall [--user | --project] [--agent <名前>]...
```

- `skill` は、予約した名前（後述）と違い、初回リリース版で実装するサブコマンドである。名前が `skill` のファイルを `run` を省いて実行するときは、`./skill` と書く。
- `skill` は、書き出した先と消した先のディレクトリのパスを標準出力に書く。
- 終了状態は、成功が 0、ファイルを書けない・消せない場合と、既存のディレクトリを置き換えないと決めた場合が 1、使い方の誤りが 2、処理系の不具合が 3 である。
- `--agent` の名前、書き出す先、既存のディレクトリの扱いは [Agent Skills 対応](06-06-agent-skills.md)の「Skill の導入（初回リリース版）」で定める。

### `test` のコマンドライン（初回リリース版）

【決定】`test` のコマンドラインは次の形とし、パスを一つ以上指定できる（[ADR 0206](../decisions/0206-test-command-line-and-exit-status.md)）。

```text
benitoite test [オプション] <パス>...
```

- ファイルを指定したときは、そのファイルに書いたテストの関数を実行する。ディレクトリを指定したときは、その下のすべての `.bnt` のファイルのテストの関数を実行する（「ディレクトリの指定（初回リリース版）」）。テストの実行の規則は[利用者プログラムのテスト](06-04-test-runner.md)の「テストの実行」で定める。
- 検査の誤りがあるファイルは、そのファイルのテストを実行せず、診断を標準エラー出力に書く。ほかのファイルのテストは続けて実行する。
- テストごとの結果と、成功と失敗の数の集計は、標準出力に書く。`--diagnostics=json` を指定したときは、結果も JSON Lines の形で書く（[ADR 0208](../decisions/0208-test-report-destination.md)）。報告の形は[利用者プログラムのテスト](06-04-test-runner.md)の「結果の報告」で定め、形の細部は【未決】である（[OPEN-058](../open-issues.md#open-058)）。

【決定】`test` の終了状態は次のとおりとする。複数に当たるときは、表の上の行の値で終わる（ADR 0206）。

| 値 | 該当する場合 |
|---|---|
| 130 | 中断の要求を受けて終えた（[ADR 0163](../decisions/0163-interrupt-releases-resources.md)） |
| 3 | 処理系の不具合（`internal error`）が起きた |
| 2 | 検査の誤りがある（`--deny-warnings` を指定して警告がある場合と、処理系の制限で実行できない場合を含む）。ファイルを読めない。CLI の使い方の誤り |
| 1 | 失敗したテストがある |
| 0 | 上のどれでもない |

### `fmt` のコマンドライン（初回リリース版）

【決定】`fmt` のコマンドラインは次の形とする（[ADR 0207](../decisions/0207-fmt-command-line.md)）。

```text
benitoite fmt [オプション] <パス>...
```

- 指定したファイルを整形し、元のファイルを書き換える。ディレクトリを指定したときは、その下のすべての `.bnt` のファイルを整形する（「ディレクトリの指定（初回リリース版）」）。
- `fmt` は構文だけを扱い、名前解決と型検査を行わない。型検査の誤りがあるファイルも整形できる。
- 構文の誤りがあるファイルは書き換えず、診断を標準エラー出力に書く。ほかのファイルの整形は続ける。
- オプション `--check` を指定したときは、ファイルを書き換えない。整形で変わるファイルの名前を標準エラー出力に書く。
- `fmt` は標準出力に書かない。
- `fmt` は、`check` と同じく中断の要求を特別に扱わず、OS の既定の振る舞いに任せる。途中で中断されてもファイルを壊さないように、整形の結果を元のファイルと同じディレクトリの一時ファイルに書き、名前の変更（rename）で元のファイルと置き換える。
- 一時ファイルを作れないか書けないとき、または名前の変更で元のファイルを置き換えられないときは、元のファイルを変えずに残し、一時ファイルを作っていれば消す。失敗の理由を診断として標準エラー出力に書き、一時ファイルを消せなかったときは、そのことも同じ診断に含める。ほかのファイルの整形は続ける（[ADR 0247](../decisions/0247-fmt-write-failure-exit-status.md)）。
- 整形の規則（正規形、コメントの保持）は[フォーマッタ](06-03-formatter.md)で定める。

【決定】`fmt` の終了状態は次のとおりとする。複数に当たるときは、表の上の行の値で終わる（ADR 0207）。

| 値 | 該当する場合 |
|---|---|
| 3 | 処理系の不具合（`internal error`）が起きた |
| 2 | 構文の誤りがあるファイルがある。ファイルを読めない、または書き換えられない（[ADR 0247](../decisions/0247-fmt-write-failure-exit-status.md)）。CLI の使い方の誤り |
| 1 | `--check` を指定して、整形で変わるファイルがある |
| 0 | 上のどれでもない |

### オプション

【方針】`run`・`check`・`test` は次の表のオプションを受け付ける。【決定】`fmt` は、`--diagnostics` と `--check` を受け付ける（[ADR 0207](../decisions/0207-fmt-command-line.md)）。

| オプション | 意味 | 既定 |
|---|---|---|
| `--diagnostics=text` または `--diagnostics=json` | 診断・実行時エラー・資源の不足・処理系の不具合の報告の形式（[ADR 0032](../decisions/0032-rust-style-text-and-json.md)、[診断エンジン](../02-impl/02-10-diagnostics.md)）。`json` を指定しても、使い方の誤り、`main` が返した `Result.Error` の文字列、ヒープの確保の失敗で abort するときのメッセージは文章のまま書く。`test` では、テストの結果の報告の形式も決める（[ADR 0208](../decisions/0208-test-report-destination.md)） | `text` |
| `--max-call-stack=<大きさ>` | 呼び出しの情報の合計の上限（[ADR 0030](../decisions/0030-call-stack-size-limit.md)）。`512MiB`・`2GiB` のように、`KiB`・`MiB`・`GiB` を付けた整数で書く。`run` と `test` で意味を持ち、`test` では一つのテストごとの上限とする（[ADR 0206](../decisions/0206-test-command-line-and-exit-status.md)） | `1GiB` |
| `--deny-warnings` | 初回リリース版。警告を誤りとして扱い、警告があれば検査の誤りと同じく終了状態 2 で終える（[ADR 0166](../decisions/0166-warnings-reported-by-run-and-deny-option.md)）。`check`・`run`・`test` で意味を持つ | 指定しない |
| `--check` | 初回リリース版。`fmt` だけで意味を持つ。ファイルを書き換えず、整形で変わるファイルがあれば終了状態 1 で終える（[ADR 0207](../decisions/0207-fmt-command-line.md)） | 指定しない |

知らないオプション、値の誤ったオプション、スクリプトのパスがない場合は、使い方の誤りとして、誤りの内容と `--help` を使うよう示す文を標準エラー出力に書き、終了状態 2 で終わる。

### サブコマンドの振る舞い

【方針】`check` は、スクリプトを読み込みから型検査まで検査する（[パイプライン](../02-impl/02-01-pipeline.md)）。誤りがなければ終了状態 0 で終わる。初回リリース版では、警告があれば、誤りがなくても警告を標準エラー出力に書く（`--deny-warnings` を指定したときを除き、終了状態は 0 のまま。[ADR 0166](../decisions/0166-warnings-reported-by-run-and-deny-option.md)）。誤りも警告もなければ何も出力しない。誤りがあれば、診断を標準エラー出力に書き、終了状態 2 で終わる。

【方針】`run` は、スクリプトを検査し、誤りがなければ実行する（[スクリプト実行と埋め込み](../02-impl/02-11-embedding.md)）。検査の誤りは `check` と同じく報告して終える。処理系の制限による誤り（`L` で始まる診断コード）はコード生成の段で見つかるので、`run` と `test` でだけ報告される（[診断エンジン](../02-impl/02-10-diagnostics.md)）。このため、`check` が終了状態 0 で終えたスクリプトを、`run` が終了状態 2 で終えることがある。

### 標準入出力

【方針】

- `run` と `check` では、標準出力には、スクリプトが書いた内容だけを書く。処理系は、`--help`・`--version`・`--licenses` を除き、標準出力に書かない。`test`・`fmt`・`skill` が標準出力に書くものは、「`test` のコマンドライン（初回リリース版）」「`fmt` のコマンドライン（初回リリース版）」「`skill` のコマンドライン（初回リリース版）」で定める（[ADR 0207](../decisions/0207-fmt-command-line.md)）。
- `run` と `check` の標準エラー出力には、スクリプトが書いた内容、診断、実行時エラー・資源の不足・処理系の不具合の報告、`main` が返した `Result.Error` の文字列、使い方の誤りを書く。
- 最小実行版のスクリプトは標準入力を読まない。初回リリース版の `run` では、スクリプトは `Console.Read` の操作で標準入力を読める（[IO のモジュール](../03-interop/03-07-io-modules.md)、[スクリプト実行と埋め込み](../02-impl/02-11-embedding.md)）。

### 終了状態

【決定】`run` と `check` の終了状態は、次の 4 つとする（[ADR 0037](../decisions/0037-exit-status-values.md)）。`test`・`fmt`・`skill` の終了状態は、「`test` のコマンドライン（初回リリース版）」「`fmt` のコマンドライン（初回リリース版）」「`skill` のコマンドライン（初回リリース版）」で定める。

| 値 | 意味 | 該当する場合 |
|---|---|---|
| 0 | 成功 | `check` で誤りがない。`run` で `main` が `()` か `Result.Ok(())` を返した |
| 1 | スクリプトの実行の失敗 | `main` が `Result.Error` を返した。実行時エラー、資源の不足で止まった。コマンドライン引数が正しい UTF-8 でない |
| 2 | 検査の誤りと使い方の誤り | 検査の誤りがある。`--deny-warnings` を指定して警告がある。処理系の制限で実行できない。スクリプトのファイルを読めない。CLI の使い方の誤り |
| 3 | 処理系の不具合 | 処理系の不具合（`internal error`）が起きた |

【決定】初回リリース版の `run` は、上の表に加えて、次の終了状態で終わることがある。

- スクリプトが `Process.exit(code)` でプロセスを終えたときは、`code`（0 以上 255 以下。[IO のモジュール](../03-interop/03-07-io-modules.md)）で終わる。`code` が 1〜3 のときは上の表の値と重なるので、ハーネスは、標準エラー出力に処理系の形式の報告があるかで区別する。`Process.exit` で終えたときは、解放の失敗を除き、処理系は報告を書かない。
- 中断の要求（`SIGINT`・`SIGTERM`）を受けて、リソースを解放してから終えたときは、130 で終わる（[ADR 0163](../decisions/0163-interrupt-releases-resources.md)）。

【決定】処理系がヒープの確保に失敗したときは、初回リリース版でも最小実行版と同じく、Rust の標準ライブラリの既定の振る舞いで終わる。標準エラー出力にメッセージを書いてプロセスを abort し、終了状態は OS が決める。処理系はこのときの終了状態を定めない。OS の側でメモリが足りなくなったときの終わり方も定めない（[ADR 0044](../decisions/0044-heap-exhaustion-outside-stop-procedure.md)、[ADR 0079](../decisions/0079-rust-readings-of-go-based-decisions.md)、[ランタイム](../02-impl/02-09-runtime.md)）。このとき、標準エラー出力に処理系の形式の診断はない。上の表のどの値でもない終了状態で終わったとき、または処理系の形式の診断がないときは、処理系が異常に終わったものとして扱う。【決定】処理系はヒープの使用量に上限を設けない。メモリの使用量を抑えるときは、処理系を起動する側（ハーネス、`ulimit`、コンテナなど）で上限を掛ける（[ADR 0237](../decisions/0237-no-heap-usage-limit-in-first-release.md)）。

標準出力か標準エラー出力の読み手が先に終わった（パイプが閉じた）ときは、書き込みの失敗による実行時エラーとして扱い、終了状態 1 で終わる（[ランタイム](../02-impl/02-09-runtime.md)）。

最小実行版では、処理系は中断の要求（`SIGINT` など）を扱う設定をせず、そのときの終了状態は OS の既定の振る舞いに従う。初回リリース版の `run` と `test` は、中断の要求を受けたら、すべてのタスクを取り消し、`with` のリソースを解放し、出力を書き出してから、終了状態 130 で終わる。解放の途中で二度目の中断の要求を受けたら、OS の既定の振る舞いで終わる（[ADR 0163](../decisions/0163-interrupt-releases-resources.md)、[スクリプト実行と埋め込み](../02-impl/02-11-embedding.md)）。`check` と `fmt` は、中断の要求を特別に扱わず、OS の既定の振る舞いに任せる（[ADR 0207](../decisions/0207-fmt-command-line.md)）。

### 開発用の設定

【方針】IO の実行方式（[ADR 0029](../decisions/0029-two-io-execution-modes.md)）は、利用者向けのオプションにしない。処理系の開発者が性能測定などで切り替えるために、環境変数 `BENITOITE_DEV_IO_MODE` を読む。値は `direct`（直接呼び出し）か `request`（要求と応答）で、既定は `direct` とする。この環境変数は開発用であり、利用者向けの文書には載せず、予告なく変えることがある。
