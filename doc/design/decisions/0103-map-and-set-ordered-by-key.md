# 0103. マップと集合は、鍵の順序で反復する永続コレクションとし、`Float` を含む型を鍵にしない

## 背景

初回リリース版で、永続コレクションのマップと集合を加える（[ロードマップ](../00-overview/00-03-roadmap.md)）。反復の順序（要素を列にしたときの並び）の決め方は、言語によって違う。ML 系の言語（Haskell の `Data.Map`、OCaml・F# の `Map`、Elm の `Dict`）は、平衡二分木で鍵の順序に並べる。Scala・Clojure・Gleam の既定のマップは、順序を定めない。Kotlin の `mapOf` と Python の `dict` は、挿入の順序を保つ。これらの言語の扱いは、一次資料で確かめていない。

## 決定

1. prelude に、永続コレクションの `Map[K, V]` と `Set[T]` を設ける。更新する関数は新しい値を返し、元の値は変わらない。
2. 反復の順序は、鍵（集合では要素）の順序とする。実装は平衡二分木とする。
3. 鍵に使える型（鍵の型）は、等値の型のうち、`Float` を含まないものとする。利用者の代数的データ型とレコードも鍵にできる。`Float` を含む型を鍵にすると型の誤りとし、`Integer` や `String` に変換するよう診断で示す。
4. 鍵の型の値の順序（鍵の順序）は、すべての鍵の型について定める全順序とする。定義は[標準ライブラリ](../03-interop/03-06-stdlib.md)で定める。
5. 鍵の順序は、マップと集合の中でだけ使う。`<` などの比較演算子が使える型は、これまでどおりとする。
6. リテラルの構文は設けない。`Map.fromList` と `Pair` で作る。

## 検討した代替案

- **挿入の順序（Kotlin・Python と同じ）**: 読んだ順に出力され、スクリプトの利用者の直観に合う。しかし、永続コレクションで挿入の順序を保つのは複雑で、要素を消したときの跡の詰め直しも要る。
- **順序を定めない（ハッシュの木）**: 最も速い。しかし、反復の順序が処理系の版や実行によって変わりえ、利用者が結果を確かめる場面とゴールデンテストで困る。
- **鍵を数・文字列・文字とそれらの組に限る（Elm と同じ）**: 順序の定義が小さくて済む。しかし、利用者の型を鍵にできない。
- **鍵の順序を `<` にも使う**: 比較できる型が増える。しかし、構成子の宣言の順を大小とみなす比較は、利用者が意図しない結果を生みやすい。

`Float` を鍵にしないのは、NaN が自分自身と `==` で等しくないので、鍵にすると取り出せない値ができるからである。

## 帰結

- 反復の順序が実行によって変わらない。
- 操作は O(log n) である。
- 平衡二分木は、設計メモが学習の中心とした永続コレクション（Okasaki『Purely Functional Data Structures』）の題材になる。
- 「鍵の型」は、利用者が関数の型に書けない制約であり、prelude の関数だけが持つ（[ADR 0009](0009-typing-without-type-classes.md) の等値の制約と同じ扱い）。
