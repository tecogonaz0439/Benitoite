# 0087. 検査・脱糖・コンパイルの段は、大きなスタックを持つスレッドで行う

- 状態: 採択
- 日付: 2026-09-27
- 関連章: [パイプライン](../02-impl/02-01-pipeline.md), [字句解析器と構文解析器](../02-impl/02-03-frontend.md)
- 関連する未決事項: なし

## 背景

構文解析器は AST の深さを 1000 に抑え、後の段は AST と中間表現を再帰で辿る（[字句解析器と構文解析器](../02-impl/02-03-frontend.md)の「入れ子の深さ」、[ADR 0086](0086-pattern-nodes-count-toward-nesting-limit.md)）。この設計は、後の段の再帰の深さが上限の定数倍に収まることを保証するが、その深さで使う Rust のスタックの量は保証しない。

最小実行版の実装（2026-09-27）で、最適化しないビルドの各段が上限いっぱいの入れ子で使うスタックを測った。構文解析はおよそ 1.6 MB、型検査は型の合うプログラムでおよそ 1.7 MB、型の合わない深い型を診断に示す場合は 2 MiB を超えた。コード生成は `case` の入れ子でおよそ 0.9 MB である。Rust のテストのスレッドと、`std::thread::spawn` が作るスレッドの既定のスタックは 2 MiB である（[std::thread](https://doc.rust-lang.org/std/thread/index.html)の "Stack size"）。スタックが溢れると、処理系は診断を出さずに異常終了する。

## 決定

1. パイプラインの公開の関数のうち、AST と中間表現を再帰で辿る段を呼ぶもの（`check_path`・`check_text`・`desugar_checked`・`compile`）は、内部で大きなスタックを持つスレッドを作り、段をそのスレッドで実行して結果を待つ。スタックの大きさは 64 MiB とする。
2. スレッドの中で起きた panic は、呼び出し側のスレッドで再び起こし、パイプラインの呼び出し側の panic 境界（[ランタイム](../02-impl/02-09-runtime.md)の「panic 境界」）で処理系の不具合として報告する。
3. 各段の単体テストは、これまでどおりテストのスレッドの既定のスタックで行い、スタックの大きさを変えて通すことはしない。各段の再帰の経路の関数は、引き続きスタックの使用量を小さく保つ。
4. VM は言語の関数の呼び出しで Rust の関数を入れ子に呼ばない（[ADR 0016](0016-calls-off-go-stack.md)）ので、実行（`run_with`）は呼び出し側のスレッドで行う。

## 検討した代替案

- **各段の再帰の関数のスタックの使用量を減らすだけにする**: 設計を変えずに済む。しかし、どの段も既定のスタックに対する余裕が小さく、段や構文を加えるたびに同じ問題が起きうる。スタックの使用量はコンパイラの版や最適化の水準でも変わるので、関数ごとの調整だけでは上限いっぱいの入力で異常終了しないことを保ちにくい。この調整は決定 3 として続ける。
- **後の段をすべて明示の積み重ねで書く**: 再帰の深さに依存しなくなるが、書き直しの範囲が大きい（[ADR 0086](0086-pattern-nodes-count-toward-nesting-limit.md)の検討した代替案と同じ理由）。

## 帰結

- 上限いっぱいの入れ子のプログラムでも、検査・脱糖・コンパイルは既定のスタックの 32 倍の余裕を持つ。
- 段の結果（AST、型検査の表、コア IR、コンパイル済みプログラム）は、スレッドの間で受け渡せる型（`Send`）でなければならない。
- 公開の関数を一回呼ぶたびにスレッドを一つ作る。スクリプトを一回検査・実行するのに作るスレッドは数個であり、その費用は検査の費用に比べて小さい。
- 実装プランでは、パイプライン API の作業（T24）がこの仕組みを実装し、型検査の制約を解く部分（T14）の再帰の関数のスタックの使用量を減らす作業を別に行う。
