# 0146. 実行時エラーを起こしうることは型にもエフェクトにも表さず、実行時エラーはプロセスを異常終了させる

- 状態: 採択
- 日付: 2026-09-28
- 関連章: [基本型の意味論](../01-spec/01-04-types-basic.md), [型システム](../01-spec/01-06-type-system.md), [エフェクト](../01-spec/01-07-effects.md), [評価意味論](../01-spec/01-08-evaluation.md), [エラー処理](../01-spec/01-09-errors.md), [コア計算と脱糖](../01-spec/01-12-core-calculus.md), [標準ライブラリ](../03-interop/03-06-stdlib.md), [他の言語の調査記録](../08-appendix/08-03-language-surveys.md)
- 関連する未決事項: [OPEN-026](../open-issues.md#open-026)（本 ADR で決着）

## 背景

整数の溢れ、`Decimal` の溢れ、0 による除算は、実行時エラーとしてプログラムを止め、関数の型には現れない（[ADR 0006](0006-basic-types-semantics.md)、[評価意味論](../01-spec/01-08-evaluation.md)）。実行時エラーは捕捉できない（[ADR 0064](0064-no-exceptions-runtime-errors-uncatchable.md)）。実行時エラーを起こしうることを型やエフェクトで表すかは、代数的エフェクトを導入するときにあわせて判断することにしていた（[OPEN-026](../open-issues.md#open-026)）。初回リリース版で、利用者が定義するエフェクトとハンドラを加えた（[ADR 0118](0118-effect-handlers.md)）。

仕様が定める実行時エラーのうち、純粋な計算から起きるのは、算術の三つ（整数の溢れ、`Decimal` の溢れ、0 による除算）だけである。ほかの実行時エラー（書き込みの失敗、リソースの解放の失敗、解放したリソースの使用、権限の拒否、継続の二度目の再開）は、IO、リソース、ハンドラに伴って起きる。

他の言語の調べた結果は[他の言語の調査記録](../08-appendix/08-03-language-surveys.md)の「算術の失敗の扱い」に記録した。要点は次のとおりである。

- Rust・Swift・Zig・Roc・Haskell・OCaml・Python は、算術の失敗でプログラムを止めるか例外を投げ、型には表さない。Rust の RFC 560 は、整数の溢れを「a program error (but not undefined behavior in the C sense)」と位置付けた。
- Koka は、何も起こさない関数を `total` とし、例外を投げうる関数に `exn` を付けるが、算術には `exn` を付けない。整数を任意精度にし、0 で割った値を 0 と定めて、算術を全域の関数にしている。
- Koka・Gleam・Pony・Flix・Lean は、0 で割った値を 0 と定める。Flix の文書はこれを「Controversial」と書き、Pony の文書は「might lead to silent errors」と書く。
- Rust・Roc・Gleam は、失敗を値で返す版の関数（`checked_add`、`plus_try`、`int.divide`）を、止める版と別に持つ。

## 決定

1. 実行時エラーを起こしうることは、関数の型にもエフェクトにも表さない。
2. 実行時エラーは、プログラムを実行しているプロセスを異常終了（クラッシュ）させる。止める手順（リソースの解放、出力の書き出し、報告、失敗を表す終了状態）は、[評価意味論](../01-spec/01-08-evaluation.md)の「実行時エラーによる停止」に従う。
3. 算術の失敗を `Option` や `Result` で返す版の関数（Rust の `checked_add` に当たるもの）は、標準ライブラリに設けない。
4. 算術の意味（溢れと 0 による除算を実行時エラーとすること）は、これまでどおりとする。0 で割った値を定めることや、`Integer` を任意精度にすることはしない。
5. 算術の三つの実行時エラー（整数の溢れ、`Decimal` の溢れ、0 による除算）は、次の二段で扱う。
   - 実行の前の検査（コンパイルする言語のコンパイルに当たる）: 実行する前に起きることが確実に分かるものを、警告とする。警告は検査と実行を止めない。対象は次の二つである。
     - 除算（`div`・`mod`・`Integer.floorDivide`・`Integer.floorModulo`、`Decimal` の `/`）の除数が定数式であり、その値が 0 であるとき。割られる数は定数式でなくてよい。
     - 溢れうる演算（`Integer` の `+`・`-`・`*`・単項の `-`・`div`、`Integer.floorDivide`・`Integer.absolute`、`Decimal` の `+`・`-`・`*`・`/`）のすべての引数が定数式であり、その計算が整数の溢れか `Decimal` の溢れの条件に当たるとき（`9223372036854775807 + 1`、`Integer.absolute(-9223372036854775808)` など）。
   - 実行時: 値が実行して初めて分かるとき（変数に 0 や大きな値が入っているときなど）は、これまでどおり実行時エラーとする。

   トップレベルの定数の定数式の中でこれらの条件に当たるときは、これまでどおり警告ではなく検査の誤りとする（[ADR 0123](0123-top-level-constants.md)）。範囲を超える整数リテラルを検査の誤りとすることも、これまでどおりとする（[基本型の意味論](../01-spec/01-04-types-basic.md)）。

## 検討した代替案

- **実行時エラーを起こしうる関数にエフェクト（`Fail` など）を付ける**: 関数の型から、止まりうるかが分かる。しかし、算術を使う関数のほとんどにエフェクトが付き、権限の確認のためのエフェクトの表示が読みにくくなる（原則 3）。IO やリソースに伴う実行時エラーは、エフェクトを付けても防げない。
- **失敗を `Option` で返す算術の関数を加える**: 溢れを扱いたい箇所で、失敗を型に表せる。しかし、同じ演算に二つの書き方ができる（原則 5）。スクリプトで溢れや 0 による除算から回復したい場面は少なく、起きたときは誤りの位置と呼び出しの履歴を報告して止まるので、書き手はその場所を直せる。書き手（LLM）が、要らない場面で `Option` の版を選んで、処理を複雑にするおそれもある。
- **0 で割った値を 0 と定める（Koka・Gleam・Pony と同じ）**: 算術が止まらなくなる。しかし、誤った値を黙って返し、集計などの結果を気付かれずに誤らせる。ADR 0006 が溢れを回り込ませないとしたのと同じ理由で採らない。
- **`Integer` を任意精度にする**: 溢れがなくなる。しかし、0 による除算は残る。ADR 0006 を改めることになり、性能への影響も見積もる必要がある。
- **除数が 0 の定数式の除算と、定数式の溢れを、実行の前に報告しない（GHC・OCaml・Scala 3 と同じ）**: 検査の規則が増えない。Scala 3 のコンパイラのソースは、定数の畳み込みで除算の例外が起きたときに「the code will crash at runtime」として報告しない。しかし、Benitoite の実行の前の検査は、コンパイルする言語のコンパイルに当たり、実行する前に確実に分かる誤りは報告する（原則 1）。
- **除数が 0 の定数式の除算と、定数式の溢れを、検査の誤りにする（Rust・Swift・Go・C# と同じ）**: 実行そのものを止められる。しかし、その式が実行されない分岐にあることもある。Kotlin・javac・GCC と同じく警告にとどめ、実行は妨げない。
- **値の範囲を型で表し、実行の前に証明する（篩型）**: 実行時エラーを起こさないことを証明できる。しかし、形式検証の段階（[設計メモ](../sources/fp-language-design.md) 25）の題材であり、初回リリース版の範囲を大きく超える。ロードマップの将来拡張に残す。

## 帰結

- [OPEN-026](../open-issues.md#open-026) を決着とする。
- 型とエフェクトの検査は、算術の実行時エラーが起きないことを保証しない。これは、静的検査が停止性や処理の成功を保証しないこと（[目的と設計原則](../00-overview/00-01-goals.md)の「保証の範囲」）と同じ扱いである。
- 溢れや 0 による除算を避けたいスクリプトは、演算の前に値を比べて分岐する。
- 除数が 0 の定数式の除算と、定数式の溢れの警告は、[診断エンジン](../02-impl/02-10-diagnostics.md)の区分 `W` に加える。
- 実行時エラーの報告（種類、位置、呼び出しの履歴）の分かりやすさが、失敗への主な手当てになる。報告の形は[診断エンジン](../02-impl/02-10-diagnostics.md)で定める。
