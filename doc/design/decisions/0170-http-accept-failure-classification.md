# 0170. `Http.accept` は、接続ごとの失敗と資源の不足で待ち受けを終えない

- 状態: 採択
- 日付: 2026-09-29
- 関連章: [ネットワークのモジュール](../03-interop/03-09-network.md), [ランタイム](../02-impl/02-09-runtime.md)
- 関連する未決事項: なし

## 背景

`Http.serve` は、受け付け（`Http.accept`）が `Result.Error` を返すと、`try` で受け付けの繰り返しを終え、サーバ全体を終える（[ADR 0142](0142-http-api-shape.md)）。しかし、受け付けの失敗には、待ち受けそのものが使えなくなった失敗のほかに、一つの接続だけの失敗（クライアントが要求を送り終える前に接続を切った）と、一時的な資源の不足（開けるファイル記述子の数の上限に達した）がある。後の二つでサーバを終えると、一つのクライアントの振る舞いや一時的な負荷で、ほかのクライアントへの応答も止まる。この問題は、03-interop の整合の確認で見つかった。

## 決定

1. `Http.accept` の失敗を、次の三つに分ける。
   - 接続ごとの失敗: 受け付けた接続が、要求を読み終える前に切れた、または読み取りに失敗した。
   - 資源の不足: OS が、プロセスまたはシステムの開けるファイル記述子の数の上限、メモリやバッファの不足で、接続の受け付けを拒んだ。
   - 待ち受けの失敗: 上の二つに当たらない失敗。待ち受けそのものが使えなくなった場合である。
2. 接続ごとの失敗では、`Http.accept` はその接続を捨て、失敗を返さずに次の要求を待つ。要求が HTTP として正しくないときに状態コード 400 の応答を返して次の要求を待つのと同じ扱いである。
3. 資源の不足では、`Http.accept` は失敗を返さず、時間をおいて受け付けをやり直す。待つ時間は、続けて失敗した最初の回を 5 ミリ秒とし、失敗するたびに 2 倍にして、1 秒を上限とする。受け付けに成功したら、待つ時間を最初に戻す。続けて失敗し始めたときに一度だけ、処理系は失敗の理由を標準エラー出力に一行書く。待つ間は、ほかのタスクを進め、中断の要求を受け付ける。
4. 待ち受けの失敗だけを、`Result.Error` で返す。`Http.serve` の書き方は変えない。

## 検討した代替案

- **今の形を保ち、注意として書く**: 仕様は簡単である。しかし、`Http.serve` を使うスクリプトは、一時的な失敗でも止まるサーバになる。止まらないサーバを書くには `Http.listen` と `Http.accept` の層で失敗の種類を調べる必要があるが、資源の不足は `NetworkErrorKind.Other` に入り、種類で見分けられない。
- **`Http.serve` の中で失敗の種類を見分け、`Http.accept` は今のまま全部を返す**: `Http.accept` を直接使うスクリプトは、同じ見分けを自分で書く必要がある。見分けるための構成子を `NetworkErrorKind` に加えることにもなる。

## 帰結

- `Http.accept` が返す `Result.Error` は、待ち受けを続けられないことを表す。`Http.serve` の利用者も、`Http.accept` の利用者も、失敗を返されたら待ち受けを終えてよい。
- 資源の不足が続く間、サーバは要求に応えないまま待つ。その間の状態は、標準エラー出力の一行で分かる。
