# 0125. 初回リリース版で、宣言の説明を `///`、モジュールの説明を `//!` のドキュメントコメントで書く

- 状態: 採択
- 日付: 2026-09-28
- 関連章: [字句構造](../01-spec/01-01-lexical.md), [構文](../01-spec/01-02-syntax.md), [標準ライブラリ](../03-interop/03-06-stdlib.md), [LSP サーバ](../06-tooling/06-02-lsp.md), [他の言語の調査記録](../08-appendix/08-03-language-surveys.md)
- 関連する未決事項: [OPEN-012](../open-issues.md#open-012), [OPEN-047](../open-issues.md#open-047)

## 背景

コメントは `//` から行末までであり、処理系はコメントの中身を使わない（[字句構造](../01-spec/01-01-lexical.md)）。スクリプトを書く主な書き手は LLM であり、LLM がモジュールの関数を呼ぶときには、関数の型と説明を MCP サーバや LSP サーバから受け取れるとよい。標準ライブラリの関数の説明も、同じ仕組みで示したい。そのためには、どのコメントがどの宣言の説明かを、処理系が決められる必要がある。

他の言語の調べた結果は[他の言語の調査記録](../08-appendix/08-03-language-surveys.md)の「ドキュメントコメント」に記録した。要点は次のとおりである。

- Rust・Swift・Zig・Gleam・D は、宣言の前の `///` を説明とする。Rust と Zig はモジュールの説明を `//!`、Gleam は `////` で書く。
- 説明する宣言のない位置のドキュメントコメントを、Zig はコンパイルの誤りとし、Rust は位置によって誤り（E0585 など）か警告とし、OCaml は警告とする。Go と D は無視する。
- 説明の中身は、Rust・Swift・Elm・Elixir・Julia が Markdown で書く。OCaml・Kotlin・D は `@param` などの構造化したタグを持つ。
- Rust・Elixir・Python・Zig・D は、説明に書いた例をテストとして実行できる。

## 決定

1. `///` で始まる行は、直後の宣言の説明（ドキュメントコメント）である。連続する `///` の行を一つの説明とする。`//!` で始まる行は、そのファイルのモジュールの説明であり、ファイルの先頭（import の宣言より前）に書く。
2. `///` を付けられる宣言は、トップレベルの宣言（関数、定数、型、型の別名、レコード、型クラス、エフェクト）と、構成子、レコードのフィールド、エフェクトの操作、型クラスのメソッドである。属性を付けた宣言では、説明、属性、宣言の順に書く。
3. 説明する宣言のない位置に `///` を書く場合と、ファイルの先頭以外に `//!` を書く場合は、誤りとする。診断は、普通のコメント `//` に書き換えることを修正案として示す。
4. 説明の中身は Markdown で書く。構造化したタグは設けない。処理系は中身を検査しない。
5. 処理系は、説明を宣言に結び付けて保持し、MCP サーバと LSP サーバが宣言の型とともに示す。標準ライブラリの宣言の説明も `///` で書く。
6. 説明に書いた例をテストとして実行する仕組みは、初回リリース版には設けない（[OPEN-047](../open-issues.md#open-047)）。

## 検討した代替案

- **ドキュメントコメントを設けず、宣言の直前の普通のコメントを説明とする（Go）**: 構文は増えない。しかし、宣言の前に置いた作業のメモも説明として扱われる。どのコメントを説明とするかの規則が、空行の有無のような見えにくい条件に依存する。
- **説明する宣言のない `///` を警告にとどめる（Rust の一部、OCaml）**: 書き換えの手間は減る。しかし、説明を書いたつもりの箇所が宣言と結び付かないことに、気付かないまま進みやすい。
- **`@param`・`@return` の構造化したタグを設ける（OCaml・Kotlin・D）**: 引数ごとの説明を道具が取り出せる。しかし、引数の名前と型はシグネチャから読める。タグの書き方と、引数の名前とタグの食い違いの検査が要る。
- **説明を属性 `@doc("…")` で書く（Elixir）**: 属性の構文を使い回せる。しかし、属性の引数は一行の文字列であり、複数行の説明を書きにくい。

## 帰結

- 字句解析器は、`///` と `//!` のコメントの中身を、宣言に結び付けられる形で残す。構文解析器は、宣言の位置で説明を受け取り、それ以外の位置の説明を誤りとする。
- `////` のように 4 つ以上の `/` で始まるコメントは、ドキュメントコメントではなく普通のコメントである。
- LLM が他の言語の書き方（`/** … */`、`{-| … -}`、`(** … *)`、`@doc`）で説明を書いたときは、`///` の書き方を修正案として示す。
- 説明に書いた例の実行（doctest）を設けるかは、[OPEN-047](../open-issues.md#open-047) で決める。
