# 0239. 参照カウントを残し、`Reference` のセルだけを対象に循環を回収する（暫定）

- 状態: 採択（暫定。[0240](0240-runtime-redesign-in-first-release-plan.md) の見直しで確定するか、ほかの方式の ADR で置き換える）
- 日付: 2026-09-29
- 関連章: [ランタイム](../02-impl/02-09-runtime.md), [仮想機械](../02-impl/02-08-vm.md), [性能](../07-quality/07-02-performance.md)
- 関連する未決事項: [OPEN-036](../open-issues.md#open-036), [OPEN-039](../open-issues.md#open-039)

## 背景

最小実行版は、言語の値を参照カウントで管理する（[ADR 0078](0078-reference-counting-in-minimal.md)）。初回リリース版の可変のセル `Reference[T]`（[エフェクト](../01-spec/01-07-effects.md)の「可変のセル（初回リリース版）」）は、自分を指す値を入れられるので、値どうしの参照が循環しうる。参照カウントだけでは、循環した値は解放されない。循環する値を回収する方式を、`Reference` を実装する前に決める必要がある（[OPEN-036](../open-issues.md#open-036)）。

一方で、値の表現とランタイムは、初回リリース版の実装プランを作るときに作り直す（[ADR 0240](0240-runtime-redesign-in-first-release-plan.md)）。循環の回収の最終的な方式は、その見直しで決める。本 ADR は、見直しの出発点とする暫定の方式を定める。

### 循環を作れる値

参照カウントの対象が循環するには、ある対象が、作られた後に、自分より後に作られた対象を指すようになる必要がある。作った後に中身が変わらない対象は、作る時点で既にある対象だけを指すので、それだけでは循環を作れない。言語仕様と処理系の設計に照らして、中身が変わりうる対象を一つずつ確かめると、次のとおりである。

- **`Reference` のセル**: `Reference.set` と `Reference.update` で、作った後の任意の値を入れられる。循環を作れる。
- **`Lazy` の対象**: 評価の後に結果を書き込むので、中身が変わる。しかし、`lazy` の本体は純粋な式に限る（[ADR 0066](0066-explicit-laziness-pure-body.md)）。本体は `State` のエフェクトを持てないので、セルを作ることも読むこともできない（[エフェクト](../01-spec/01-07-effects.md)）。`let` は再帰的な束縛にならず、ラムダは自分を名前で参照できない（[評価意味論](../01-spec/01-08-evaluation.md)）ので、本体は作ろうとしている `Lazy` 自身を名前で参照できない。したがって、結果が `Lazy` 自身を指すのは、結果に含まれるセルを経由するときに限る。そのような循環はセルを通る。評価の途中の状態が持つ、評価しているタスクと待つタスクは、タスクの表の番号であり、参照カウントの対象を指さない（[仮想機械](../02-impl/02-08-vm.md)の「値の表現」）。
- **継続の対象**: 「捕まえた区画の並び」から「使用済み」に変わる。しかし、継続は言語の値として名前を持たず、`resume` は節の中でだけ直接呼べる（[エフェクト](../01-spec/01-07-effects.md)、[ADR 0155](0155-resume-not-in-lazy.md)）。継続をセルやデータ構造に入れる手段はないので、継続の区画がその継続自身を指すことはない。区画の中のレジスタがセルを指し、そのセルを通る循環はありうるが、それはセルを通る循環である。
- **関数の値**: 捕捉した値は、関数の値を作る時点で既にある値である。関数の値が循環に加わるのは、セルに入れられたときに限る（セルを捕捉した関数をそのセルに入れる場合など）。
- **構成子を適用した値、リスト、マップと集合、`Decimal`、文字列、`Bytes`、辞書、中身を見せない組み込みの値**: 作った後に変更しない（[仮想機械](../02-impl/02-08-vm.md)の「値の表現」、[標準ライブラリ](../03-interop/03-06-stdlib.md)の「List の内部の表現」）。辞書は、実装の番号と、既に作った制約の辞書から作る（[ADR 0158](0158-type-classes-by-dictionary-passing.md)）。
- **リソースと `Task` の値**: 実行ごとの表の番号であり、参照カウントの対象を指さない。リソースの表の項目は言語の値を指さない（[ランタイム](../02-impl/02-09-runtime.md)の「メモリの管理」）。
- **ハンドラの記録**: 作った後に変更しない。節の関数の値と、評価したタスクの番号を持つ。

以上から、言語仕様と処理系の設計が現在のままであるかぎり、参照カウントの対象の循環は、必ず `Reference` のセルを一つ以上通る。この前提は、次の条件に依存する。新しい可変の対象（配列、ハッシュ表、セルを使わない相互再帰の値など）を加えるとき、継続を言語の値にするとき、`lazy` の本体に `State` を許すとき、`let` を再帰的な束縛にするときは、この前提を確かめ直す。

## 決定

1. 参照カウントを残し、`Reference` のセルだけを起点にして循環を回収する。
2. ランタイムは、生きている `Reference` のセルを、弱い参照（Rust の `std::rc::Weak`）の表に持つ。`Reference.new` でセルを作るたびに表に加える。
3. 前回の回収の後に作ったセルの数が閾値を超えたら、タスクを切り替える位置で回収を行う。閾値と、その決め方（固定の値か、生きているセルの数に比例させるか）は、実装プランで定める。
4. 回収は、CPython の循環の回収の手順（内部の参照を差し引く方法。[CPython の GC の設計の文書](https://github.com/python/cpython/blob/main/InternalDocs/garbage_collector.md)）を、セルとセルから辿れる対象に絞って行う。
   1. 表のセルのうち、まだ生きているもの（弱い参照から強い参照を得られるもの）と、その中身から辿れる参照カウントの対象を集める。これを候補とする。辿るときに、ほかのセルに達したら、そのセルも候補に含めて中身を辿る。
   2. 候補の各対象について、強い参照の数（`Rc::strong_count`）を写した数を作る。回収のために得た強い参照の分は、この数から除く。
   3. 候補の各対象の中身が指す候補の対象について、写した数を一つずつ減らす（内部の参照を差し引く）。
   4. 写した数が 0 より大きい対象は、候補の外（枠のレジスタ、タスクの表、定数の値の表など）から参照されている。そこから辿れる候補の対象は、すべて生きているとする。
   5. 生きているとされなかったセルは、どこからも使われない循環の一部である。その中身を `Unit` の値に置き換える。これで循環が切れ、残りの対象は参照カウントで解放される。
5. 回収は、`Rc::strong_count`・`Rc::as_ptr`・`Weak` など、`unsafe` を要しない標準ライブラリの関数だけで行う。対象を見分けるときは、`Rc::as_ptr` で得た番地を表の鍵にする。候補を辿る処理と、中身を置き換えた後の解放は、明示の積み重ねで行う（[ADR 0078](0078-reference-counting-in-minimal.md)）。
6. 回収の費用（回収にかかる時間の合計と、一回の回収で実行が止まる時間の最大）は、[性能](../07-quality/07-02-performance.md)の cycle のベンチマークで測る。

中身を `Unit` に置き換えても、観測できる振る舞いは変わらない。置き換えるセルはどこからも使われず、言語には値を解放するときに走る処理（finalizer）がないからである。リソースは参照カウントでは解放されず、`with` と止める手順だけで解放される（[ランタイム](../02-impl/02-09-runtime.md)の「リソースの追跡」）。

## 検討した代替案

- **初回リリース版では循環を回収しない**: 実装が最も小さい。しかし、セルに関数やデータ構造を入れる書き方（状態を持つコールバックの表など）で、メモリが実行の終わりまで解放されない。HTTP のサーバのように長く動くスクリプトでは、要求ごとに作った循環が溜まり続ける。
- **追跡型の GC を自作する**: 循環をすべての値について一様に回収でき、参照の数を増減する費用もなくせる。しかし、値の表現を、参照カウントから GC が管理する参照に作り直す必要がある。この作り直しは、値の表現の見直し（[ADR 0240](0240-runtime-redesign-in-first-release-plan.md)）で扱う事項であり、本 ADR の暫定の方式として先に決めることはしない。
- **セルに入れられる値を言語の規則で制限する**: たとえば、関数とセルを含む値を入れられないようにすれば、循環は起きない。GC は要らない。しかし、状態を持つ処理を関数の値でまとめる書き方ができなくなり、言語仕様を回収の方式の都合で狭めることになる。

## 帰結

- 最小実行版の参照カウントの実装と、確保と辿る処理を一か所に閉じ込めた構成（[ADR 0078](0078-reference-counting-in-minimal.md)）をそのまま生かせる。セルを使わないプログラムは、回収の費用を払わない。
- 回収は、セルから辿れる対象をすべて辿るので、大きなデータ構造を入れたセルがあると、一回の回収の時間が延びる。止まる時間の最大を、cycle のベンチマークと、大きなリストをセルに入れた場合で確かめる。
- 本 ADR は暫定である。[ADR 0240](0240-runtime-redesign-in-first-release-plan.md) の見直しが別の方式（追跡型の GC など）を採れば、その ADR が本 ADR を置き換える。[OPEN-036](../open-issues.md#open-036) は、見直しまで未決のまま残す。
- 循環ではないが、参照カウントでも本 ADR の回収でも解放されない値がある。タスクの表の項目は、終わったタスクの結果と、終わっていないタスクの枠の積み重ねを持つ。`Task` の値は表の番号なので参照カウントに現れず、項目をいつ表から外すかを、現在の設計は定めていない。表の項目は回収の候補の外にある参照として働くので、項目が残るかぎり、そこから辿れるセルと値は解放されない。`TaskGroup.spawn` で要求ごとにタスクを起動するサーバでは、項目が溜まり続けるおそれがある。見直し（ADR 0240）では、タスクの表の項目の寿命（`Task` の値を参照カウントの対象にするかなど）もあわせて決める。
