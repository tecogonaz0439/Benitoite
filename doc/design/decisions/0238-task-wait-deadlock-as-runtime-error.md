# 0238. タスクどうしが待ち合って進めなくなったら、実行時エラーにする

- 状態: 採択（判定の前に要求と未処理の完了を処理すること、返却・解放・出力の完了の待ちを外部の完了の待ちとして数えることを [0266](0266-task-and-resource-state-machines.md) で補った。外部の待ちとして数えるのは、タスクを起こしうる完了だけであることを [0283](0283-deadlock-counts-only-waits-that-can-wake-tasks.md) で定めた）

## 背景

`Task` の値を可変のセルに入れると、二つのタスクが互いを `Task.await` で待つプログラムを書ける（[並行処理](../01-spec/01-11-concurrency.md)）。評価の途中の `Lazy` の終わりを待つ場合や、`handle` と `TaskGroup` の解放がタスクの終わりを待つ場合（[仮想機械](../02-impl/02-08-vm.md)の「タスクの切り替え」）も、待つ先をたどると元のタスクに戻ることがある。このとき、どのタスクも進めない。

進めるタスクがないこと自体は、外部に作用する操作の完了を待つときにも起きる（標準入力の読み取り、`Http.accept` の次の要求、`Clock.sleep` と `Task.withTimeout` のタイマーなど）。この場合は、操作が完了すればタスクが進む。これに対し、外部に作用する操作を一つも待っていないときは、実行の外から何が起きても、待つタスクが進むことはない。処理系は、進められるタスクの待ち行列と、外部に作用する操作の完了を待つ表（待ちの表）の両方が空であることで、この状態を見つけられる。

最小実行版の処理系の設計は、この状態を停止しないプログラムと同じく扱い、中断の要求まで待ち続けるとしていた。

## 決定

1. 進められるタスクがなく、外部に作用する操作の完了を一つも待っておらず（タイマーを含む）、待つタスクがあるときは、実行時エラー（タスクの待ち合いの行き詰まり）とする。
2. 報告には、待つタスクのそれぞれについて、何を待っているか（`Task.await`・`Task.all` などの呼び出し、`Lazy.force`、`handle` の終わり、`TaskGroup` を束縛した `with` の終わり）と、その位置を示す。
3. 止める手順は、ほかの実行時エラーと同じ（[評価意味論](../01-spec/01-08-evaluation.md)の「実行時エラーによる停止」）とする。
4. 外部に作用する操作の完了を待つタスクがあるあいだは、この実行時エラーにしない。`Http.accept` や標準入力の読み取りを待つ状態は、外部に作用する操作の完了を待つ状態であり、行き詰まりではない。

## 検討した代替案

- **停止しないプログラムと同じく、中断の要求まで待ち続ける**: 規則を加えずに済む。しかし、処理系は確実に見つけられる状態を報告せずに黙って止まり続けることになり、利用者と LLM は、停止しない計算なのか、待ち合いなのか、外部の入力を待っているのかを見分けられない。静的に検出できない誤りでも、確実に見つけられるものは原因とともに報告するほうが、原則 1 と原則 3 に沿う。

## 帰結

- 待ち合いで止まったプログラムは、終了状態 1 と、待つタスクごとの待つ位置を示す報告で終わる。報告の形は[診断エンジン](../02-impl/02-10-diagnostics.md)で定める。
- 待ち合いに加わっていないタスクが外部に作用する操作を待っているあいだは、待ち合いに加わったタスクがあっても実行時エラーにならない。そのタスクの操作が完了し、ほかにも待つものがなくなった時点で、実行時エラーになる。一部のタスクだけが待ち合う状態を、その時点で見つける規則は設けない。
- 検出は、スケジューラが進めるタスクを選ぶときに、二つの表が空かを確かめるだけで行え、待つ先の関係をたどる必要はない。
