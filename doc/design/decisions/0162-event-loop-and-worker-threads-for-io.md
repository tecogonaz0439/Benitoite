# 0162. IO を mio のイベントループと作業用のスレッドで行い、組み込みの操作の応答に「待つ」を加える

- 状態: 採択
- 日付: 2026-09-29
- 関連章: [ランタイム](../02-impl/02-09-runtime.md), [仮想機械](../02-impl/02-08-vm.md), [パイプライン](../02-impl/02-01-pipeline.md)
- 関連する未決事項: なし

## 背景

最小実行版の IO は、組み込みの関数の呼び出しが終わるまで VM を止めて行った。実行方式は、ハンドラ表の関数を直接呼ぶ方式と、要求を返して止まる方式の二つがあり、既定は直接呼び出しである（[ADR 0029](0029-two-io-execution-modes.md)、[ADR 0088](0088-keep-both-io-execution-modes.md)）。ADR 0088 は、並行処理を設計するときに二つの方式の扱いを見直すとした。

初回リリース版では、外部に作用する操作の完了を待つ間に、ほかのタスクを進める（[並行処理](../01-spec/01-11-concurrency.md)）。HTTP のサーバは `mio` の上に自作し、クライアントは同期の API の `ureq` を作業用のスレッドで呼ぶ（[ADR 0143](0143-http-and-tls-crates.md)）。言語の値は `Rc` なので、スレッドの間で渡せない。

## 決定

1. ランタイムは、VM と同じスレッドで `mio` のイベントループを動かす。ソケットの待ち受けと読み書き、時間の経過の待ち（`Clock.sleep`、`Task.withTimeout`）は、イベントループで待つ。
2. ブロックする操作（ファイル、外部コマンドの起動と終わりの待ち、標準入力、HTTP のクライアント、名前の解決）は、作業用のスレッドで行う。引数は `Send` を満たす Rust の型に変えてから渡し、結果は VM のスレッドで言語の値に変える。完了は channel と `mio::Waker` で知らせる。
3. 組み込みの操作の応答に「待つ」を加える。直接呼び出しの方式では、ハンドラ表の関数が「完了」か「待つ」を返す。要求と応答の方式では、IO 実行器が応答を返すまでタスクを待たせる。どちらの方式でも、待つタスクはスケジューラの待ちの表に移り、完了したら進められるタスクに戻る。
4. 二つの実行方式を残し、既定を直接呼び出しとする ADR 0088 の決定 1〜3 は変えない。決定 4 の見直しは、本 ADR で行ったものとする。
5. 標準出力と標準エラー出力への書き込みは、これまでどおり VM のスレッドでバッファに書き、待つ操作にしない。

## 検討した代替案

- **`tokio` の単一スレッドの実行環境を使う**: 非同期の IO の部品がそろう。しかし、ADR 0143 は HTTP のサーバを `mio` の上に作ると決めており、VM を async で書かない限り、`tokio` の実行環境を VM の外側で回す二重の構造になる。
- **すべての外部に作用する操作を作業用のスレッドで行う**: 仕組みが一つになる。しかし、接続ごとにスレッドを占める HTTP のサーバになり、多数の接続を待つ場面に向かない。
- **要求と応答の方式に一本化する**: 待つ仕組みを一か所に集められる。しかし、ADR 0088 の測定で、IO の多いスクリプトでは直接呼び出しの方が速かった。

## 帰結

- ハンドラ表の関数の型が、完了と待つの二つを返す形に変わる。
- 作業用のスレッドで起きた panic は、境界で捕らえて VM のスレッドへ処理系の不具合として渡す。
