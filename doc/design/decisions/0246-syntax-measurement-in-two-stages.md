# 0246. 構文の種類ごとの LLM の生成精度を、構文だけの測定と、期待結果までの測定の二段階で測る

- 状態: 採択
- 日付: 2026-09-29
- 関連章: [ロードマップ](../00-overview/00-03-roadmap.md), [Agent Skills 対応](../06-tooling/06-06-agent-skills.md)
- 関連する未決事項: [OPEN-012](../open-issues.md#open-012)

## 背景

構文の判断基準は、LLM による生成・修正の成功率（期待結果の達成まで含める）である（[目的と設計原則](../00-overview/00-01-goals.md)）。構文の種類ごとの LLM の生成精度の測定（[OPEN-012](../open-issues.md#open-012)）は、初回リリース版の実装プランを作る前に行うとしていた（[ロードマップ](../00-overview/00-03-roadmap.md)の「着手の前に必要な決定と試作」）。OPEN-012 には、省略形のキーワードと省略しない語、予約語の範囲、`case` の書き方など、比べる案が積み上がっている。初回リリース版を出した後に予約語を加えると、その語を識別子に使ったスクリプトが誤りになるので、キーワードと予約語は初回リリース版の前に決めきる必要がある。

一方、期待結果を満たす率まで測るには、型とエフェクトを検査して実行できる処理系が要る。初回リリース版の処理系は、実装プランを作った後に作る。同梱の Agent Skill の評価の仕組み（課題ごとの入力と期待する出力、複数のハーネス、決めた回数以内の検査と修正、成功率と修正の回数の記録）は定めてある（[ADR 0232](0232-skill-evaluation-with-tasks-and-harnesses.md)）。

設計者は、LLM を使った測定に OpenCode を使える。OpenCode で使うモデルは Claude より能力が低いことがあり、設計者は、そのほうが測定に向く可能性があると考えている。

## 決定

1. 測定を二段階に分ける。
2. 第一段階は、初回リリース版の実装プランを作る前に行う、構文だけの測定である。
   - 文法を確かめる道具（`tools/grammar-check/`）の文法を、構文の案ごとに切り替えられるようにする。切り替える点は、OPEN-012 に挙げた論点（省略形のキーワード、予約語、`case` の書き方など）である。
   - 同梱の Skill の文法の参照の文書を、案ごとに差し替える。
   - LLM に課題のスクリプトを書かせ、構文の誤りの率と、診断を読んで 1 回で直せた率を比べる。
   - 型とエフェクトは測らない。
   - 結果から、キーワードと予約語を決める。
3. 第二段階は、初回リリース版の検査器ができた後、初回リリース版を提供する前に行う、期待結果までの測定である。Skill の評価の仕組み（ADR 0232）を使い、期待する出力を得たかまで測る。構文は、大きな問題が見つかったときに限り、ADR を作って改める。
4. どちらの段階でも、OpenCode をハーネスの一つとして使う。使うモデルと、LLM を呼ぶ回数は、測定を計画するときに設計者と相談して決める。

## 検討した代替案

- **第一段階を省き、検査器ができてから一度だけ測る**: 測定の準備が一度で済み、期待結果まで測れる。しかし、キーワードと予約語が決まらないまま構文解析器と検査器を作ることになり、測定の結果で変えると、実装と Skill を作り直すことになる。予約語は初回リリース版の後に加えられないので、第二段階で問題が見つかっても直せる範囲が狭い。

## 帰結

- 第一段階の前に、文法を確かめる道具を、案ごとの文法を持てる形に改める。道具は、初回リリース版の構文解析器を実装するときに処理系の検査に置き換える予定であり、第一段階はその前に終える。
- 第一段階は構文の誤りだけを測るので、型とエフェクトにかかわる案（省略しない型の名前、エフェクトの書き方など）の比較は第二段階に回る。
- ADR 0232 のハーネスに OpenCode を加える。
- 結果は、ハーネスとモデルの版に依存する。記録には、ADR 0232 と同じく、ハーネスとモデルの版を残す。
