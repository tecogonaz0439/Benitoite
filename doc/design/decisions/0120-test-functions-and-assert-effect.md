## 背景

初回リリース版の CLI には `test` のサブコマンドがある（[ロードマップ](../00-overview/00-03-roadmap.md)）。テストでは、組み込みの操作をハンドラで差し替える（[ADR 0117](0117-capabilities-as-effects.md)、[ADR 0118](0118-effect-handlers.md)）。テストの印は属性 `@test` で表す（[ADR 0119](0119-attributes-test-and-deprecated.md)）。実行時エラーは捕捉できない（[ADR 0064](0064-no-exceptions-runtime-errors-uncatchable.md)）。実行中の状態は実行ごとに作る（[ADR 0015](0015-shared-program-per-execution-state.md)）。

他の言語は次のとおりである。いずれも言語か道具の文書で確かめた。

- Zig・Rust・D・Roc・OCaml の inline tests は、テストをコードと同じファイルに書ける。Rust は、同じファイルのテストから非公開の関数にも触れられる。
- 期待の確認は、Rust の `assert_eq!`、Zig の `expectEqual`、Gleam の `assert`、pytest の `assert` が、失敗したときに両辺の値を示す。真偽値だけを受け取る `assert!` や Zig の `expect` は、失敗したことしか示さない。
- Flix は、期待の確認を `Assert` エフェクトの操作とし、テストの実行器をそのハンドラとする。
- Rust（テストごとのスレッド）・Elixir（テストごとのプロセス）・Zig は、一つのテストの失敗でほかのテストを止めない。Go は、テストの中の panic がテストのプログラム全体を止める。

## 決定

1. テストは、`@test` を付けたトップレベルの関数とする。テストの関数は、型パラメータと引数を持たず、戻り値の型は `Unit` か `Result[Unit, String]` とする。`@test("説明")` の形で、結果に示す説明を付けられる。説明がなければ、関数の名前を示す。
2. テストはどのモジュールにも書ける。同じモジュールの非公開の関数も呼べる。`run` はテストの関数を実行しない。`test` は、指定したファイルのテストの関数を実行する。
3. 期待の確認は、組み込みのエフェクト `Assert` の操作で行う。操作は `Assert.equal`・`Assert.notEqual`・`Assert.isTrue`・`Assert.fail` とする。`Assert` は `IO` に含めない。`main` のエフェクトには `Assert` を含められない。
4. テストの実行器は `Assert` のハンドラとして働く。確認が失敗すると、そのテストを失敗として打ち切る（`resume` しない）。失敗の報告には、`Assert.equal` と `Assert.notEqual` の両方の値を示す。
5. テストの関数は、組み込みのエフェクトを使える。利用者が定義するエフェクトは、テストの関数の中で処理しなければならない。実際に行う IO には、テストの関数を書いたファイルの `permissions` の宣言を当てる。宣言がなければ、宣言の要らない操作だけを許す。実行の前の権限の種類の検査（[ADR 0074](0074-static-permission-check-by-name-reference.md)）は、`test` では行わない。ハンドラで差し替える操作を名前で参照しても、宣言を要しない。
6. テストは、一つずつ別の実行として動かす。一つのテストで実行時エラーが起きても、そのテストが失敗するだけで、ほかのテストは続ける。テストは、ほかのテストの実行の順序に依存してはならない。
7. テストの関数の中で標準出力と標準エラー出力に書いた内容は、実行器が受け取り、そのテストが失敗したときに示す。
8. 表形式のテストとプロパティベーステストの専用の仕組みは、初回リリース版には設けない。プロパティベーステストは [OPEN-046](../open-issues.md#open-046) で検討する。

## 検討した代替案

- **`test "名前" … end test` のキーワードの構文**: テストを関数と区別して書ける。しかし、宣言の付加情報を属性で表すと決めた（[ADR 0119](0119-attributes-test-and-deprecated.md)）ので、テストも属性で表す。テストを関数にすると、`return` と `try` を普通の関数と同じ規則で書ける。
- **期待の確認を `expect 条件` のキーワードにする（Roc・Gleam・pytest）**: 書く量は少ない。しかし、失敗したときに両辺の値を示すには、条件の式の形を処理系が解析して値を記録する必要がある。関数の `Assert.equal` なら、両辺が引数として渡るので、そのまま示せる。
- **期待の確認を、エフェクトを持たない関数にする**: 失敗を関数の外に伝えるには、実行時エラーか戻り値が要る。実行時エラーは捕捉できないので、テストを一つずつ別の実行にしない限り、一つの失敗でほかのテストが止まる。戻り値にすると、確認のたびに `try` が要る。エフェクトにすれば、補助の関数の中でも確認でき、`main` のエフェクトに含められないので、本番のコードに紛れ込まない。
- **テストの IO をすべて許す**: 実際のファイルやコマンドを使うテストを書きやすい。しかし、宣言のない操作がテストでだけ行えると、実行時の権限制御の意味が場面によって変わる。外部の状態に左右されるテストも増える。

## 帰結

- 実行時エラーで止まったテストの報告には、実行時エラーの報告と同じ内容（種類、位置、呼び出しの履歴）を含める。
- テストの結果の表示の形と、`test` の終了状態は、[利用者プログラムのテスト](../06-tooling/06-04-test-runner.md)と [CLI](../06-tooling/06-01-cli.md) で定める。
- `Assert` の報告で値を示すために、処理系は、どの型の値も人間が読める形に書き出せる必要がある。この表記は言語から呼べる関数にはしない。
