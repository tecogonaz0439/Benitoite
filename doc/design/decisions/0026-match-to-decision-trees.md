# 0026. match を判定の木にコンパイルする

- 状態: 採択
- 日付: 2026-09-26
- 関連章: [中間表現と脱糖](../02-impl/02-06-ir-and-lowering.md), [バイトコードとコード生成](../02-impl/02-07-bytecode.md), [コア計算と脱糖](../01-spec/01-12-core-calculus.md)
- 関連する未決事項: なし

## 背景

`match` の意味は、分岐を上から順に試し、最初に照合したパターンの分岐を選ぶことである（[コア計算と脱糖](../01-spec/01-12-core-calculus.md)の E-Match）。パターンは入れ子にでき（`Tree.Node(Tree.Leaf, x, _)`）、実行の方法には、分岐ごとにパターン全体を順に照合する方法と、分岐のパターンをまとめて、値の各部分を一度ずつ調べる判定の木にする方法とがある。

処理系の中間表現はコア計算と同じ形であり（[ADR 0017](0017-ir-in-core-calculus-form.md)）、パターンマッチのコンパイルはコア計算にない変換である。VM の実行結果は、参照インタプリタとの差分テストで確かめる（[ADR 0018](0018-reference-interpreter.md)）。

## 決定

`match` は、判定の木（decision tree）にコンパイルする。判定の木は、値の一つの部分の構成子または定数で分岐する節の入れ子であり、葉で分岐の本体を選ぶ。コンパイルは分岐の順序を保ち、どの値についても、元の `match` で最初に照合する分岐と同じ分岐を選ぶ。

複数の葉が同じ分岐の本体を選ぶ場合は、本体を複製せずに共有する。コンパイルの手順と共有の仕方は[中間表現と脱糖](../02-impl/02-06-ir-and-lowering.md)で定める。

## 検討した代替案

- **分岐を上から順に試す**: [コア計算と脱糖](../01-spec/01-12-core-calculus.md)の規則とそのまま対応し、実装が短い。しかし、分岐が多いと、値の同じ部分を分岐ごとに何度も調べる。最小実行版の後の性能測定（[性能](../07-quality/07-02-performance.md)）は、Go での実装を続けるかの判断に使うので、代数的データ型を多く使うプログラムの結果が、実装言語でなくこの方式の費用で悪く出るおそれがある。判定の木を後から加える場合も、コード生成の作り直しが要る。

## 帰結

- 値の各部分を一度ずつ調べるので、分岐の数が増えても照合の費用が分岐の数に比例して増えにくい。
- 処理系で広く使われるパターンマッチのコンパイル技法を、実装で学べる。
- コンパイルが分岐の順序を保つことは、参照インタプリタとの差分テストで確かめる。参照インタプリタは、判定の木にする前の中間表現を 01-12 の規則どおりに実行する。
- 判定の木を作る順序（どの部分を先に調べるか）によって木の大きさが変わる。最小実行版では単純な選び方を使い、性能測定の結果を見て改める。
