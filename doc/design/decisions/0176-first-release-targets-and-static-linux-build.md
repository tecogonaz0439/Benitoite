# 0176. 初回リリース版の対応環境を macOS（arm64）と Linux（x86_64・arm64）とし、Linux 向けは musl で静的にリンクする

- 状態: 採択
- 日付: 2026-09-29
- 関連章: [配布形態](../05-platform/05-01-distribution.md), [ロードマップ](../00-overview/00-03-roadmap.md)
- 関連する未決事項: [OPEN-009](../open-issues.md#open-009)

## 背景

ロードマップは、初回リリース版で処理系を単一バイナリとして配り、完了条件を「[配布形態](../05-platform/05-01-distribution.md)で定める各環境」で確かめるとしていた。しかし、対応する環境と、単一バイナリの作り方は決めていなかった。

Rust の実行ファイルは使うクレートをすべて取り込むが、標準ライブラリは OS の機能を C ライブラリ経由で使う。

- **macOS**: C ライブラリは OS の一部であり、どの macOS にも入っている。対応する最低の OS の版だけを気にすればよい。Rust の `aarch64-apple-darwin` は macOS 11.0 以降を対象とする（Rust の Platform Support）。
- **Linux**: 既定のビルド先（`*-linux-gnu`）は、実行する機械の glibc を実行時に読み込む。そのため、ビルドした環境より古い glibc の環境では動かないことがある。glibc を静的にリンクしても、`getaddrinfo` などのホスト名の解決は、実行時に glibc の共有ライブラリを読み込もうとする。
- **musl**: ビルド先 `*-linux-musl` は、musl を実行ファイルに取り込み、依存のない実行ファイルを作る。C ランタイムの部品は Rust のツールチェーンに同梱されている。`x86_64-unknown-linux-musl` と `aarch64-unknown-linux-musl` は、公式の標準ライブラリが配られる水準（Tier 2 with Host Tools）である。

依存のクレートは、C コンパイラを要しないものを選んである（[ADR 0143](0143-http-and-tls-crates.md)）。

## 決定

1. 初回リリース版の対応環境を、次の三つとする。
   - macOS（arm64。`aarch64-apple-darwin`）
   - Linux（x86_64。`x86_64-unknown-linux-musl`）
   - Linux（arm64。`aarch64-unknown-linux-musl`）
2. Windows は、WSL2 の中の Linux で、Linux 向けの実行ファイルを使う形で対応する。x86_64 の Windows でも arm64 の Windows でも同じである。Windows で直接動く実行ファイルは、初回リリース版では配らない。
3. Linux 向けに配る実行ファイルは、musl で静的にリンクする。処理系を開発するときの手元のビルドは、既定のビルド先（glibc）でよい。
4. 各環境の実行ファイルは、その環境の OS の上でビルドする。macOS の上で Linux 向けの実行ファイルをリンクするには、Linux 向けのリンカが要るからである。
5. musl の標準のメモリ確保が処理系の性能に与える影響を、初回リリース版の完了時の性能の測定で確かめる（[OPEN-009](../open-issues.md#open-009)）。影響が大きければ、メモリ確保の差し替えか、glibc の実行ファイルもあわせて配ることを検討する。
6. FreeBSD・OpenBSD・NetBSD は、余力があれば、初回リリース版の後から正式リリース版までの間に対応を検討する。

## 検討した代替案

- **Linux 向けも既定のビルド先（glibc）で配る**: 性能の心配がない。しかし、対応する最低の glibc の版を決め、それを保つビルドの環境を用意する必要がある。musl を使うディストリビューション（Alpine など）では動かない。
- **glibc で静的にリンクする**: 一つのファイルになるが、ホスト名の解決で実行時に共有ライブラリを読み込もうとする。HTTP のクライアントとサーバはホスト名を解決するので、環境によって名前を解決できない。
- **musl と glibc の両方を配る**: 利用者が選べるが、ビルドと試験が倍になる。性能の測定の結果を見て、5 で改めて検討する。
- **Windows で直接動く実行ファイルも配る**: WSL2 を使わない利用者も使える。しかし、Windows に固有の違い（`Process.shell` が使うシェル、シェバンが効かないこと、パスの区切り）を確かめる作業が増え、x86_64 と arm64 の二つのビルドが加わる。
- **BSD 系の OS も対象にする**: OS ごとに別のビルドが要る。OpenBSD は Rust の対応の水準が低く（Tier 3）、使うクレート（OS のルート証明書で検証する `rustls-platform-verifier` など）が対応しているかも確かめる必要がある。

## 帰結

- 完了条件の「各環境」は、決定 1 の三つである。Windows では WSL2 の中で確かめる。
- 仕様の中の Windows に固有の記述（[CLI](../06-tooling/06-01-cli.md)のシェバン、[IO のモジュール](../03-interop/03-07-io-modules.md)の `Process.shell` のシェル）は、Windows で直接動く実行ファイルを配るときのために残す。
