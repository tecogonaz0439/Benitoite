# 0064. 例外の仕組みを設けず、実行時エラーは捕捉できないものとする

- 状態: 採択
- 日付: 2026-09-26
- 関連章: [エラー処理](../01-spec/01-09-errors.md), [評価意味論](../01-spec/01-08-evaluation.md), [リソース管理](../01-spec/01-10-resources.md)
- 関連する未決事項: [OPEN-026](../open-issues.md#open-026)

## 背景

最小実行版では、外部の状態によって失敗しうる操作は `Result` を返し（[ADR 0011](0011-io-failure-and-entry-point.md)）、整数の溢れや 0 による除算は実行時エラーとしてプログラムを止める（[ADR 0006](0006-basic-types-semantics.md)）。実行時エラーを捕捉する手段はない（[評価意味論](../01-spec/01-08-evaluation.md)）。v1 のエラー処理で、例外の有無を決める（[エラー処理](../01-spec/01-09-errors.md)）。

## 決定

v1 には、例外を投げて捕まえる仕組み（`throw` と `try`・`catch` など）を設けない。回復できる失敗は `Result` と `Option` の値で表す。実行時エラーは捕捉できず、評価意味論の手順でプログラムを止める。

## 検討した代替案

- **実行時エラーを捕捉する関数だけを設ける**（`Process.catch(fn() { ... })` のように、実行時エラーを `Result` に変える）: 長く動く処理で、一部の失敗の後も処理を続けられる。しかし、失敗の経路が関数の型に現れないまま増え、検査で見落としやすくなる（原則 1）。

## 帰結

- 関数が失敗しうるかは、戻り値の型（`Result`・`Option`）で読み取れる。実行時エラーを起こしうることは型に現れない（[OPEN-026](../open-issues.md#open-026)）。
- 実行時エラーは、Rust の panic と同じく、スクリプトの誤りか、処理系が扱えない状況を表すものとして扱う。
- MCP サーバで繰り返し実行するときも、一つの実行の実行時エラーはその実行だけを止める（[スクリプト実行と埋め込み](../02-impl/02-11-embedding.md)）。
