# 0006. 文字列の位置を扱う関数に単位を明示し、整数を 64 bit にして溢れを実行時エラーにする

## 背景

設計メモは、基本型の意味論のうち次の三点を未決としていた（[設計メモ](../sources/fp-language-design.md) 2.5、OPEN-002）。

- 文字列の長さと位置を、バイト・コードポイント・書記素クラスタのどれで数えるか。
- 整数が範囲を超えたときに、任意精度にするか、固定幅で溢れを検出するか、固定幅で回り込ませるか。
- Go の error・panic と、言語側の Result・例外をどう対応させるか。

三点目は Go の API をどう取り込むかに依存し、実装言語を見直した後に初回リリース版で決めればよい（[ロードマップ](../00-overview/00-03-roadmap.md)）。本 ADR は一点目と二点目を決め、三点目を [OPEN-025](../open-issues.md#open-025) に分ける。あわせて、整数の除算の丸め方と、文字列の連結に `+` を使うかを決める。どちらも、LLM が他の言語の感覚で書いたときに結果が変わりうる点である。

Go と Rust は、文字列を UTF-8 のバイト列として持ち、長さと添字をバイトで数える。X 文字目（X 番目のコードポイント）を取り出すには、先頭から復号してたどる必要がある。Python はコードポイントで数え、`len("あ")` は 1 になる。LLM が生成するスクリプトの多くは Python の感覚で書かれると見込まれる一方、処理系は Go で実装し、Go の文字列とそのまま受け渡したい。

## 決定

### 文字列

1. 文字列は Unicode のスカラー値の列であり、UTF-8 で符号化したバイト列としても扱える。文字列は常に正しい UTF-8 である。
2. 位置や長さを扱う操作は、関数名に単位を入れる。バイト単位の操作は `byte`、コードポイント単位の操作は `char` を名前に含める（`String.byteLength`、`String.charCount`、`String.charAt` など）。単位を持たない `String.length` は設けない。
3. バイト単位の長さは、文字列の長さによらない時間で求まる（Go・Rust と同じ）。コードポイント単位の操作は、文字列の長さに比例する時間がかかってよい。
4. コードポイント 1 個を表す基本型 `Char` を設ける。X 文字目の取得は `Char` を返す。
5. 位置を指定する操作は、位置が範囲外のとき、またはバイト位置が文字の途中を指すときに、実行時エラーではなく `None` を返す。
6. `+` で文字列を連結できる。両辺はどちらも String でなければならず、他の型からの暗黙の変換はしない。

### 整数

1. `Int` は 64 bit の符号付き整数である。
2. 演算の結果が範囲を超えたときは、実行時エラーとする。回り込んだ値を返さない。
3. 整数の除算 `/` は 0 の方向に切り捨て、剰余 `%` の符号は被除数と同じにする（Go・Rust と同じ）。負の無限大の方向に丸める除算と剰余は、関数（`Int.floorDiv`、`Int.mod`）として提供する。
4. 任意精度の整数は、必要になったときに別の型として初回リリース版以降に加える。

これらの範囲の具体的な規則は、[基本型の意味論](../01-spec/01-04-types-basic.md)で【方針】として定める。

## 検討した代替案

### 文字列の単位

- **コードポイントだけで数える（Python と同じ）**: `length` を LLM の期待どおりにできる。しかし、内部を UTF-8 のまま持つと、`length` も位置の指定も O(n) になり、「O(1) に見えて O(n)」の関数になる。Go の文字列とバイト位置で受け渡す手段もなくなる。
- **バイトだけで数える（Go・Rust と同じ）**: 実装は単純で速い。しかし、日本語の文字列で X 文字目を取り出す手段を利用者が自分で書くことになる。
- **`length` をバイト単位にし、コードポイント版に `char` を付ける**: Go・Rust の名前に近い。しかし、Python や JavaScript の感覚で書く LLM が、`length` を文字数のつもりで使うと、ASCII の文字列では正しく動き、日本語の文字列でだけ黙って誤った結果になる。
- **書記素クラスタで数える（Swift と同じ）**: 見た目の 1 文字と一致する。しかし、結果が Unicode の版に依存し、分割の表を持つ外部のライブラリが要る。書記素クラスタで分割する関数は、標準ライブラリに別に置けば足りる。

採った案では、単位を持たない `String.length` を LLM が書くと、名前解決の誤りになる。この誤りには、`byteLength` と `charCount` を修正案として示す診断で対処する。黙って誤った結果になる経路はない。

### 1 文字の型

- **1 文字の String を返す（Python と同じ）**: 型は増えない。しかし、「ちょうど 1 文字である」ことを型で表せず、Go の `rune`・Rust の `char` とも対応しない。

### 範囲外の位置

- **実行時エラーにする（Go の添字と同じ）**: 書くのは簡単だが、誤りは実行するまで分からない。`Option` を返せば、範囲外の場合の処理を書くことを型検査が求める（原則 1）。

### 整数の範囲

- **任意精度（Python・Ruby と同じ）**: 溢れが起きず、LLM の Python 的な期待に最も合う。しかし、VM が小さい整数と大きい整数の二つの表現を持つことになり、実装と性能の負担が増える。Go の `int64` と受け渡すたびに範囲の検査も要る。スクリプトで扱う整数（件数、サイズ、時刻など）の多くは 64 bit に収まると見込み、溢れを検出して止めれば黙って誤ることはない。
- **64 bit で回り込ませる（Go・Java と同じ）**: 最も速いが、誤った結果に実行後まで気付かない。原則 1 に反する。

### 整数の除算

- **負の無限大の方向に丸める（Python・Ruby と同じ）**: 剰余が常に除数と同じ符号になり、曜日の計算などで便利である。しかし、C 系の見た目の構文で C 系と結果が違うと、読み手が取り違えやすい。Go の演算とも合わない。

### 文字列の `+`

- **`+` を数値に限り、連結は関数と文字列補間に限る**: `+` の型付けが単純になる。しかし、LLM が `"a" + b` と書く誤りが頻発すると見込まれる。`+` を Int・Float・String に使えるようにすると、型クラスのない最小実行版では、組み込みの演算子として特別に型付けする必要がある（[型システム](../01-spec/01-06-type-system.md)で定める）。

どの判断も、LLM が誤りにくいという見込みは【要検証】であり、OPEN-012 の測定課題に、日本語の文字列の操作と整数の除算を含めて確かめる。

## 帰結

- 字句構造に文字リテラル（`'a'`）を加える。構文のリテラルとパターンにも加える。
- 型システムは、型クラスのない最小実行版で、`+` と比較演算子を複数の基本型に使えるように型付けする規則を定める必要がある。
- 標準ライブラリは、位置を使わずに済む文字列の操作（分割、行への分解、前方一致、置換、文字の列への分解など）を揃える。スクリプトの文字列処理の多くを、位置を指定せずに書けるようにするためである。
- 内部表現の工夫（ASCII だけの文字列でコードポイントの位置を O(1) で求めるなど）は、仕様に含めず処理系の設計で扱う。
- 診断の位置（行・列）をどの単位で表示するかは、この決定とは独立に[ソース管理と位置情報](../02-impl/02-02-source-and-spans.md)で定める。
- Go の `int64` と `string` は、Int・String とそのまま対応する。Go の他の整数型との変換と、正しくない UTF-8 を含む Go の文字列の扱いは、Go 型との対応規約（削除した章）で定める。
