# 0150. リソースの解放のエフェクトを `State` にし、解放をエフェクトの操作から外す

- 状態: 採択
- 日付: 2026-09-29
- 関連章: [リソース管理](../01-spec/01-10-resources.md), [エフェクト](../01-spec/01-07-effects.md), [コア計算と脱糖](../01-spec/01-12-core-calculus.md), [IO のモジュール](../03-interop/03-07-io-modules.md), [ネットワークのモジュール](../03-interop/03-09-network.md)
- 関連する未決事項: なし

## 背景

`with` のエフェクトは、束縛する式と本体のエフェクトに、リソースの型の解放のエフェクトを加えたものである（[ADR 0067](0067-with-resource-scope.md)）。解放のエフェクトは、リソースの型ごとに、`File.Reader` は `File.Read`、`File.Writer` は `File.Write`、`Http.Listener` と `Http.Exchange` は `Http.Listen`、`TaskGroup` は `State` と定めていた。`with` の解放は、`File.closeReader` などの解放する関数と同じ操作であり、これらの関数は組み込みのエフェクトの操作だった。

組み込みのエフェクトの操作は、ハンドラで処理できる（[ADR 0118](0118-effect-handlers.md) 決定 3）。`File.Read` のすべての操作を処理するハンドラは、`handle` の式のエフェクトから `File.Read` を除く。ところが、コア計算の `with` の解放（E-Release）は、ハンドラを調べずに処理系が実際に行う。したがって、開いた `File.Reader` を引数で受け取り、`with` で束縛して抜ける関数を、`File.Read` を処理するハンドラで囲むと、型の上ではエフェクトのない式が、実物のファイルを閉じる。エフェクトを含まない関数は外部に作用する操作を処理系に行わせない、という保証（[セキュリティモデル](../07-quality/07-01-security-model.md)）と食い違う。この食い違いは、外部の検証者による 01-spec のレビューで指摘された。

## 決定

1. すべてのリソースの型の解放のエフェクトを `State` にする。`with` のエフェクトは、束縛する式と本体のエフェクトに `State` を加えたものである。
2. リソースを解放する関数（`File.closeReader`・`File.closeWriter`・`Http.closeListener`・`Http.closeExchange`）の型のエフェクトも `State` にする。これらの関数は、エフェクトの操作ではなく、`Reference` の関数と同じく `State` を型に持つ組み込みの関数とする。
3. `State` は操作を持たず、ハンドラで処理できない（[ADR 0130](0130-builtin-effect-names-and-placement.md)）ので、`with` の解放と解放する関数は、どのハンドラの中でも処理系が実際に行う。
4. 解放は、実行時の権限制御の対象にしない。権限は、リソースを開くときに判定する。
5. 解放の失敗の扱い（実行時エラー、`Http.Exchange` の例外。[ADR 0149](0149-http-exchange-release-failure.md)）と、解放する関数が返す `Result[Unit, E]` は変えない。

## 検討した代替案

- **解放もハンドラを通す**: `with` の解放を、解放する関数の操作の呼び出しとして扱い、ハンドラが処理できるようにする。型の規則は今のままでよい。しかし、実行時エラーで止まる途中、節が本体の続きを捨てるとき、タスクを取り消すときにも節を実行する規則が要り、節がさらに操作を呼んだり `resume` を呼ばなかったりする場合を定める必要がある。また、ハンドラが解放を差し替えると、実物のファイルや接続が閉じられずに残る。
- **解放のエフェクトを、ハンドラが除かないように型で別に追跡する**: 解放は、リソースを受け取った別の関数の中で起きることもあるので、`handle` の本体を見るだけでは、除いてはならないエフェクトを決められない。関数の型に、解放のエフェクトを別に書く仕組みが要る。

`File.Writer` の解放は、書いた内容を書き出す。この書き出しは、`File.write` などの操作で書いた内容を完了させるものであり、新しい内容を書かない。`Http.Exchange` の解放は、応答を送っていなければ状態コード 500 の応答を送る。これも、受け付けた要求への応答を完了させるものである。どちらも、`State` のエフェクトとして、既に開いたリソースの状態を変える処理として扱う。

## 帰結

- 解放する関数の呼び出しを、テストでハンドラによって差し替えることはできなくなる。リソースの型は中身を見せない型なので、ハンドラの節がリソースの値を作ることはできず、差し替えが役に立つ場面は少ない。
- リソースを受け取って `with` で束縛する関数は、`uses State` を持つ。`State` は `IO.All` に含まれ、許可を要しない。
- `TaskGroup` の解放の扱いは変わらない。
