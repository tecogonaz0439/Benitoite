# 0059. 型クラスで高カインド型を扱い、prelude には Functor・Monad を入れない

- 状態: 採択（標準の型クラスを import が要る `Benitoite.Trait` に置くことを [0134](0134-standard-type-classes.md) で決めた）
- 日付: 2026-09-26
- 関連章: [型システム](../01-spec/01-06-type-system.md), [ロードマップ](../00-overview/00-03-roadmap.md), [代数的データ型とパターンマッチ](../01-spec/01-05-data-types.md)
- 関連する未決事項: [OPEN-024](../open-issues.md#open-024)

## 背景

表層の IO を直接形式にしたので、言語の中でモナドを抽象として扱う場は、型構成子を引数にとる型クラス（高カインド型）に依存する（[ADR 0005](0005-direct-style-effects.md)、[OPEN-024](../open-issues.md#open-024)）。設計者の目的の一つは、関数型プログラミングを学ぶことである（[目的と設計原則](../00-overview/00-01-goals.md)）。一方、prelude は `Option.map`・`Option.andThen` などを型ごとのモジュールの関数として定めている（[標準ライブラリ](../03-interop/03-06-stdlib.md)）。

## 決定

型クラスの引数に、型構成子（`F[_]`）をとれるようにする。型構成子を引数にとる型クラスは、利用者が定義できる（`trait Functor[F[_]]`）。

prelude には、`Functor`・`Monad` などの型構成子を引数にとる型クラスを入れない。

## 検討した代替案

- **高カインド型を扱い、prelude に Functor・Monad も入れる**: 抽象を言語全体で使える。しかし、同じ操作に `Option.map` と `Functor.map` の二つの書き方ができ、同じ役割の構文を増やさない原則（原則 5）に反する。LLM の生成もぶれる。
- **高カインド型を扱わない**: 型推論と辞書渡しが最も単純になる。しかし、言語の中でモナドを抽象として書く場がなくなる。

## 帰結

- 型の種類（カインド）を区別する必要が生じる。型クラスと関数の型パラメータで `F[_]` と書いたものだけが型構成子であり、ほかの型パラメータは値の型である。
- 設計者は、`Functor`・`Monad` を自分で定義し、`Option`・`List` などに実装して、モナドを学べる。
- LLM が書く普通のスクリプトには、高カインド型は現れない。prelude に加えるかは、利用の実績を見て後で判断できる。
