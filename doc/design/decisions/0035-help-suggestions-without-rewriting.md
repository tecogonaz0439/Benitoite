# 0035. `help:` の修正案は最小実行版から簡易版を示して v1 で広げ、処理系はソースを直接修正しない

- 状態: 採択
- 日付: 2026-09-26
- 関連章: [診断エンジン](../02-impl/02-10-diagnostics.md), [ロードマップ](../00-overview/00-03-roadmap.md), [MCPサーバとLSPサーバ](../06-tooling/06-02-mcp-lsp.md)
- 関連する未決事項: なし

## 背景

設計メモは、`help:` による自動の修正提案を実装の難しい項目として後回しにしており（[設計メモ](../sources/fp-language-design.md) 8.3, 8.4）、ロードマップはこれを受けて「`help:` による修正案の提示」を v1 の後に回していた。一方、仕様の各章は、最小実行版の診断にも修正案を示すことを求めている（値に続けたドットに `|>` の書き方を示す、`Float` の位置の整数リテラルに `2.0` を示す、など。[字句構造](../01-spec/01-01-lexical.md)、[構文](../01-spec/01-02-syntax.md)、[基本型の意味論](../01-spec/01-04-types-basic.md)、[型システム](../01-spec/01-06-type-system.md)）。

修正案を示すことと、ソースを修正することは別の事柄である。コードの誤りの診断の第一の読み手は LLM であり、LLM はコードの作成と修正を担う。利用者は、コードの表面の小さな修正を直接行う（[目的と設計原則](../00-overview/00-01-goals.md)）。

## 決定

1. 最小実行版は、`help:` による修正案の簡易版を示す。簡易版の修正案は、診断コードごとの型板に識別子や型の名前を埋めて作る文であり、書き換えの例のコードを含んでよい。対象は、少なくとも仕様の各章と処理系の各章が修正案を求める診断とする。
2. v1 で、修正案を示す診断を、検査の誤りの診断全般に広げる。利用者のソースの該当箇所を使って、書き換えた後のコードの例を組み立てて示すことも v1 で加える。
3. 処理系は、ソースを直接修正しない。修正案を示すだけとし、ソースを修正するのは、利用者か、利用者から指示を受けた LLM である。

## 検討した代替案

- **修正案の提示をすべて v1 の後に回す**（従来のロードマップ）: 最小実行版の実装は減る。しかし、仕様の各章が求める修正案を示せず、LLM が最小実行版で誤りを直す手掛かりが減る。
- **処理系が修正案をソースに適用する**（`fix` のようなコマンドで、処理系が自らソースを書き換える）: 利用者や LLM の手間は減る。しかし、ソースを修正するのは利用者と LLM の役割であり、処理系が利用者の確認なしにソースを変えると、何がなぜ変わったかを利用者が把握しにくくなる（原則 3）。

## 帰結

- 最小実行版から、LLM は `help:` の文を手掛かりに誤りを直せる。
- 最小実行版の診断の内部の表現では、修正案は文の並びとして持つ（[診断エンジン](../02-impl/02-10-diagnostics.md)）。LLM やエディタが扱いやすいように、修正案に書き換えの範囲と置き換える文字列を添えるかは、v1 で修正案を広げるとき、または MCP サーバと LSP サーバを設計するときに決める。添えた場合も、それを適用するのは利用者か LLM（エディタでの利用者の操作を含む）であり、処理系ではない（[MCPサーバとLSPサーバ](../06-tooling/06-02-mcp-lsp.md)）。
