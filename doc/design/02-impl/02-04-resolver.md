## 目的と範囲

名前解決と、複数モジュールを実行可能な形にまとめる工程。モジュールの識別と探索、依存グラフ、循環検出、型検査の単位（全体を一括で処理するかモジュールごとか）、モジュール間のシンボル参照の接続（リンク）、初期化の実装、インクリメンタル処理を扱う。依存の取得・バージョン選択・ロックは[パッケージ管理](../06-tooling/06-05-package-manager.md)が扱う。

現在の版は、初回リリース版（[ロードマップ](../00-overview/00-03-roadmap.md)）の範囲を定める。初回リリース版のプログラムは、実行を始めるモジュールと、そこから import で辿れるすべてのモジュールからなる（[名前・スコープ・モジュール](../01-spec/01-03-names-modules.md)）。パッケージの取り込みは [OPEN-049](../open-issues.md#open-049) で決めた後に本章へ加える。

## 前提

名前の種類、有効範囲、シャドーイング、修飾された名前の解決、モジュールと import、公開、循環する import の規則は[名前・スコープ・モジュール](../01-spec/01-03-names-modules.md)で定める。本章はそれを実装する方法を定める。

ファイルは、読み込みの段が import を辿って読み、読むたびに構文解析する（[パイプライン](02-01-pipeline.md)、[ソース管理と位置情報](02-02-source-and-spans.md)）。名前解決は、すべてのファイルに読み込みと構文の誤りがないときだけ、すべてのモジュールの AST を受け取る（[ADR 0019](../decisions/0019-stop-after-failing-stage.md)、[ADR 0156](../decisions/0156-module-loading-and-whole-program-checking.md)）。

## 仕様

### モジュールの表

【方針】読み込みの段は、読んだモジュールごとに次のものを持つ表（モジュールの表）を作り、名前解決に渡す。

| 項目 | 内容 |
|---|---|
| モジュールの ID | モジュールのファイルのファイル ID と同じ値（[ソース管理と位置情報](02-02-source-and-spans.md)） |
| 名前 | 根のディレクトリからの名前（`Lib.Text`）。標準ライブラリのモジュールでは `Benitoite` の名前空間の名前（`Benitoite.IO.Console`） |
| 種類 | 実行を始めるモジュール、利用者のモジュール、prelude のモジュール、prelude でない標準ライブラリのモジュールのどれか |
| 取り込み先 | import の宣言ごとの、取り込むモジュールの ID |

モジュールの表は、読み込みを終えた後は変更しない。

### モジュールの探し方

【方針】読み込みの段は、import の宣言の名前（[名前・スコープ・モジュール](../01-spec/01-03-names-modules.md)の「モジュールと import（初回リリース版）」、[ADR 0126](../decisions/0126-import-by-module-name.md)）から、次の手順で読むモジュールを決める。

1. 名前の最初の要素が `Benitoite` であれば、標準ライブラリのモジュールとして、処理系に埋め込んだ標準ライブラリのソースから引く（後述の「標準ライブラリのソースの持ち方」）。ファイルシステムは探さない。見つからなければ誤りとする。根のディレクトリの直下に `Benitoite` という名前のファイルやディレクトリがあれば、診断は、それを取り込めないことを添える。
2. それ以外の名前 `A.B.C` は、根のディレクトリ（実行を始めるファイルのあるディレクトリ。[ADR 0127](../decisions/0127-directory-run-and-root.md)）の下の `A/B/C.bnt` を指す。途中のディレクトリと最後のファイルは、ディレクトリの項目の一覧を読み、名前が大文字と小文字まで一致する項目を選ぶ。大文字と小文字だけが違う項目しかないときは、見つからない誤りとし、診断はその項目の名前を示す。【決定】ファイルを開けたかどうかでは照合しない。大文字と小文字を区別しないファイルシステム（macOS の既定の APFS など）では、名前の大文字と小文字が違っていてもファイルを開けるからである。ディレクトリの項目の一覧には保存した名前が現れるので、一覧で照合すれば、ファイルシステムが大文字と小文字を区別するかどうかに関わらず同じ結果になる（[ADR 0244](../decisions/0244-import-name-matching-by-directory-listing.md)）。モジュールの名前は ASCII の識別子なので、Unicode の正規化の違いは照合に影響しない。
3. 選んだファイルのシンボリックリンクを解決した絶対パスが、根のディレクトリ（これもシンボリックリンクを解決したもの）の下になければ誤りとする。
4. 選んだファイルが実行を始めるファイルであれば誤りとする。

これらの誤りは読み込みの段の誤りであり、診断は、import の宣言のモジュールの名前の span を主な位置とする。

### 依存グラフと循環の検出

【方針】モジュールの表の取り込み先は、モジュールを頂点、import の宣言を辺とする有向グラフ（依存グラフ）を表す。読み込みの段は、すべてのファイルを読み終えた後、依存グラフの循環を調べる。

- 実行を始めるモジュールから、import の宣言の順に深さ優先で辿る。辿っている途中のモジュール（深さ優先の道筋の上にあるモジュール）に戻る辺を見つけたら、その辺で閉じる循環を一つ報告する。
- 深さ優先の探索は、明示の積み重ねを使った繰り返しで書く。モジュールの数に比例して処理系の再帰を深くしない。
- prelude のモジュールは、import で取り込まずに使えるので、依存グラフに prelude への辺はない。標準ライブラリのモジュールの間の循環は、処理系の不具合であり、処理系のテストで検出する。

【決定】循環の診断は、循環を作る import の並びを、モジュールの名前で `Lib.A -> Lib.B -> Lib.A` の形に示す（[ADR 0054](../decisions/0054-no-import-cycles.md)）。主な位置は循環を閉じる import の宣言とし、循環の中のほかの import の宣言を補助の位置として示す。

実行を始めるモジュールは取り込めない（前節の手順 4）ので、循環に実行を始めるモジュールが含まれることはない。循環の検出は、構文の誤りのあるファイルがあっても、構文解析できた import の宣言について行い、ほかの読み込みの誤りと一緒に報告する。

### 標準ライブラリのソースの持ち方

【決定】標準ライブラリは処理系と一緒に配るモジュールの全体であり、prelude はそのうち import なしで使える部分である（[名前・スコープ・モジュール](../01-spec/01-03-names-modules.md)、[ADR 0128](../decisions/0128-prelude-and-benitoite-namespace.md)）。標準ライブラリのソースは、利用者のモジュールと同じ構文のモジュールとして書き、`public` を付けたものを公開する。モジュール `Benitoite.X.Y` のソースは、標準ライブラリの根の下の `X/Y.bnt` に置き、診断などに示す表示名は `<benitoite>/X/Y.bnt` とする。組み込みの関数は、本体のない関数の宣言に `@builtin("名前")` を付けて宣言する（[ADR 0157](../decisions/0157-stdlib-sources-as-modules-with-builtin-attribute.md)）。

【方針】標準ライブラリのソースのファイルは、処理系のソースコードの中の標準ライブラリの根のディレクトリに置き、Rust の `include_str!` マクロで処理系に埋め込む。`include_str!` は、指定したファイルの内容を、コンパイルのときに `&'static str` の値として読み込む（[include_str!](https://doc.rust-lang.org/std/macro.include_str.html)）。処理系は、根からの相対パス（`IO/Console.bnt`）から内容を引く表を持ち、読み込みの段はこの表でモジュールを引く。

【決定】読むのは、prelude のモジュールと、import で辿れる標準ライブラリのモジュールだけである（[ADR 0156](../decisions/0156-module-loading-and-whole-program-checking.md)）。

【方針】標準ライブラリの実装は、次のものから成る。

| 部分 | 内容 | 持ち方 |
|---|---|---|
| 標準ライブラリのソース | 標準ライブラリのモジュール。型・レコード・型クラス・実装・エフェクトの宣言、言語で書く関数（[標準ライブラリ](../03-interop/03-06-stdlib.md)で実装の欄をソースとした関数と、その補助の関数）、`@builtin` を付けた組み込みの関数の宣言 | 処理系に埋め込んだソースファイル |
| 組み込みの関数の表 | `@builtin` の名前から、Rust の実装への対応 | 処理系の Rust のコードに書いた表 |
| 組み込みの型の表 | ソースに宣言の構文がない、中身を見せない型（基本型、`List`・`Map`・`Set`・`Bytes`・`Reference`・`Lazy`・`Task`・`TaskGroup`・`IOError`・`NetworkError`・`Regex.Pattern`・`Regex.Match`・`Random.Generator` など。[ADR 0168](../decisions/0168-regex-match-and-stdlib-opaque-values.md)）の、名前、型パラメータの数、属する標準ライブラリのモジュール | 同上 |
| 組み込みのエフェクトの表 | ソースの宣言で表せないエフェクト（操作を持たない `State` と、ほかのエフェクトをまとめた `IO.All`）と、`IO.All` がまとめるエフェクトの一覧 | 同上 |
| 標準ライブラリのモジュールの一覧 | すべての標準ライブラリのモジュールの名前と、prelude に入るか | 同上 |

これらの表は、初期化の後に変更しないので、大域に置いてよい（[ADR 0015](../decisions/0015-shared-program-per-execution-state.md)）。

【方針】標準ライブラリのソースは、次のように扱う。

- 名前解決は、`@builtin` の名前が組み込みの関数の表にあることを確かめる。なければ、標準ライブラリのソースの誤り（処理系の不具合）とする。宣言の型が Rust の実装と合うことは、処理系のテストで確かめる。
- 組み込みの型は、属するモジュールのトップレベルの型として束縛を作る。組み込みのエフェクトの表のエフェクトは、`State` を prelude の名前として、`IO.All` を prelude のモジュール `Benitoite.IO` のトップレベルのエフェクトとして束縛を作る。
- `Console.Write` などの操作を持つ組み込みのエフェクトは、標準ライブラリのソースに普通のエフェクトの宣言として書く。どのハンドラも処理しない操作は、処理系が、操作の `Benitoite` の名前空間の名前でハンドラ表を引いて行う（[ランタイム](02-09-runtime.md)、[ADR 0130](../decisions/0130-builtin-effect-names-and-placement.md)）。
- 標準ライブラリのソースの中だけで使う組み込みの関数と補助の関数は、`public` を付けずに宣言する。宣言したモジュールの中からだけ使え、利用者のモジュールの名前と束縛の番号で区別されるので、同じ名前でも衝突しない。
- 標準ライブラリのモジュール `Benitoite.X` が同じ名前の型 `X` を宣言しているとき（`Benitoite.List` の型 `List` など）、名前 `X` は、型を書く位置ではその型を、修飾の段ではそのモジュールを指す。`List.map` の `List` は、型 `List` のモジュールとして、モジュール `Benitoite.List` のトップレベルの名前を引く（[名前・スコープ・モジュール](../01-spec/01-03-names-modules.md)の「トップレベルの名前空間」）。

【方針】標準ライブラリのソースの誤りは処理系の不具合であり、処理系のテストで検出する（[処理系のテスト戦略](../07-quality/07-03-compiler-testing.md)）。検査のたびに、読む標準ライブラリのモジュールも利用者のモジュールと同じく名前解決から型検査までの段を通す。

### 束縛と表

【決定】名前解決は AST を変更せず、次の表を出力する（[ADR 0022](../decisions/0022-side-tables-keyed-by-node.md)）。

| 表 | 鍵 | 値 |
|---|---|---|
| 束縛の表 | 束縛の番号 | 束縛の種類、名前、宣言したモジュールの ID、宣言したノードのノード番号（組み込みの型と組み込みのエフェクトは表の項目）、span、`public` を付けたか、`@deprecated` の文字列 |
| 参照の表 | 名前を使う箇所のノード番号 | 束縛の番号 |
| 公開の表 | モジュールの ID と名前 | そのモジュールが公開する束縛の番号 |
| prelude を隠した参照の表 | 利用者の名前が prelude の名前を隠した参照のノード番号 | 隠された prelude の束縛の番号 |

【決定】束縛の番号は、検査全体で一意であり、宣言したモジュールの ID を持つ。モジュールの間の参照は、参照の表でこの番号に結び付ける（リンク。[ADR 0156](../decisions/0156-module-loading-and-whole-program-checking.md)）。脱糖より後の段は、定義を束縛の番号で指すので、モジュールの名前と公開を扱わない（[コア計算と脱糖](../01-spec/01-12-core-calculus.md)の「モジュールと import、公開」）。

【方針】束縛の番号は、ノード番号と同じく、検査ごとに持つ数え上げの状態から振る。トップレベルの宣言の束縛には、モジュールの ID の順に、各モジュールの中では宣言の順に番号を振るので、同じソースの集まりからは同じ番号が振られる。

【方針】束縛の種類は次のとおりである。

| 束縛の種類 | 宣言したノード |
|---|---|
| トップレベルの関数（実装の中の関数を含む） | 関数の宣言 |
| 組み込みの関数 | `@builtin` を付けた本体のない関数の宣言 |
| 定数 | 定数の宣言 |
| データ構成子 | データ構成子の宣言 |
| 型、組み込みの型 | 型の宣言、組み込みの型の表の項目 |
| 型の別名 | 型の別名の宣言 |
| レコード | レコードの宣言 |
| フィールド（フィールドを取り出す関数を兼ねる） | フィールドの宣言 |
| 型クラス | 型クラスの宣言 |
| メソッド | メソッドの宣言 |
| エフェクト、組み込みのエフェクト | エフェクトの宣言、組み込みのエフェクトの表の項目 |
| エフェクトの操作 | 操作の宣言 |
| モジュール | import の宣言（取り込んだモジュールに付けた名前）。prelude のモジュールと名前空間の根 `Benitoite` は、モジュールの表の項目 |
| 型パラメータ、エフェクト変数 | 型パラメータの宣言 |
| 局所の束縛 | 引数、`let` 文と `let` のパターンの変数、ラムダの引数、パターンの変数（リストのパターンの残りの変数を含む）、`with` の束縛、`handle` の節の引数 |

実装（`implement`）は名前を持たないので、束縛を作らない。実装の中の関数は束縛を作るが、モジュールのトップレベルの名前の表と公開の表には入れない。型検査器と脱糖は、実装を宣言のノード番号で指す。実装の中の関数の宣言の名前は、型クラスのメソッドを使う箇所として、参照の表でメソッドの束縛に結び付ける。

名前を使う箇所は、式の名前、名前の型、`uses` の並びの中のエフェクトの名前、構成子のパターンとレコードのパターン、レコードの構築とパターンのフィールドの名前、`handle` の節の操作の名前、制約と `implement` と上位の型クラスに書いた型クラスの名前、import の宣言のモジュールの名前、実装の中の関数の宣言の名前のノードである。修飾された名前は、段ごとに指す束縛を定め、最後の段が指す束縛を参照の表に載せる。

### 解決の手順

【決定】名前解決は、プログラム全体を一つの単位として行う。すべてのモジュールのトップレベルの宣言を先に集めて公開の表を作り、その後で本体を解決する（[ADR 0156](../decisions/0156-module-loading-and-whole-program-checking.md)）。

【方針】名前解決は、次の順に行う。モジュールは、どの手順でもモジュールの ID の順に扱う。

1. トップレベルの名前を集める。各モジュールのトップレベルの宣言（関数、定数、型、型の別名、レコード、型クラス、エフェクト）と、宣言の中の名前（構成子、フィールド、メソッド、エフェクトの操作）の束縛を作り、モジュールごとのトップレベルの名前の表と公開の表を作る。組み込みの型とエフェクトの束縛もここで作る。[名前・スコープ・モジュール](../01-spec/01-03-names-modules.md)の「トップレベルの名前空間」の誤り（名前の重複、`Benitoite` という名前）、一つの型の宣言の中の構成子の名前の重複、一つのレコードの中のフィールドの名前の重複、エフェクトとモジュールの同じ名前、操作と同じモジュールの関数・定数の同じ名前を、ここで報告する。
2. import の宣言を解決する。各 import の宣言に付けた名前（最後の要素か `as` の名前）の束縛を、モジュールの表の取り込み先に結び付ける。import の宣言の誤り（後述）を、ここで報告する。
3. 宣言のシグネチャを解決する。関数・メソッド・操作の引数の型と戻り値の型と `uses`、型パラメータの制約、構成子の引数の型、フィールドの型、型の別名の右辺、定数の型の注釈、型クラスの上位の型クラス、`implement` の型クラスと対象の型を解決する。
4. 宣言の検査を行う（後述の「宣言の検査」）。
5. 本体を解決する。関数（実装の中の関数を含む）の本体と、定数の定数式を、有効範囲の積み重ねを持って辿り、名前を解決する。
6. 本体の後の検査を行う。定数の循環と定数式の形を判定する（後述の「宣言の検査」）。

手順 3 と 5 は、宣言ごとに独立に行い、ある宣言の誤りは、ほかの宣言の解決を妨げない。すべての宣言を先に集めるので、宣言の順序とモジュールの順序によらず参照できる。

### import の宣言の誤り

【方針】名前解決は、import の宣言について次の誤りを報告する（[名前・スコープ・モジュール](../01-spec/01-03-names-modules.md)の「モジュールと import（初回リリース版）」）。ファイルが見つからないなどの誤りは、読み込みの段が報告済みである（前述の「モジュールの探し方」）。

- 二つの import の宣言に付けた名前が同じ場合。診断は、少なくとも一方に `as` を書くよう示す。
- `as Benitoite` と書いた場合。
- 取り込んだモジュールに付けた名前が、同じファイルの型・レコード・型クラス・エフェクト・型の別名の名前と同じ場合。
- 一つのファイルの中で、同じモジュールを二度取り込んだ場合（別々の名前を付けた場合を含む）。

import の宣言に付けた名前が prelude の名前と同じときは、誤りにしない。利用者の名前が prelude の名前を隠す（後述の「名前の引き方」）。

### 宣言の検査

【方針】名前解決は、名前と宣言の関係だけで判定できる次の検査を行う。型を比べる検査（実装の重なりなど）は型検査器が行う（[型検査器](02-05-typechecker.md)）。

| 検査 | 内容 | 定める箇所 |
|---|---|---|
| 公開する契約 | `public` を付けた関数・型・レコード・型クラス・エフェクト・定数・型の別名のシグネチャ（関数の型の内側を含む）と `uses`、上位の型クラス、制約に、`public` を付けていない同じモジュールの型・型の別名・型クラス・エフェクトを使っていないこと | [名前・スコープ・モジュール](../01-spec/01-03-names-modules.md)の「公開（初回リリース版）」、[ADR 0053](../decisions/0053-private-by-default-with-pub.md)、[ADR 0154](../decisions/0154-public-contract-includes-effects-and-supertraits.md) |
| 型の別名の循環 | 別名が、直接または別の別名を通して自分自身を参照しないこと。診断は循環する別名の並びを示す | [型システム](../01-spec/01-06-type-system.md)の「型の別名（初回リリース版）」、[ADR 0124](../decisions/0124-type-aliases.md) |
| 上位の型クラスの循環 | 型クラスの上位の型クラスの関係が循環しないこと | [型システム](../01-spec/01-06-type-system.md) |
| 孤立した実装 | `implement` を、型クラスを宣言したモジュールか、対象の型を宣言したモジュールに書いていること。束縛の番号が持つモジュールの ID で比べる | [型システム](../01-spec/01-06-type-system.md)、[ADR 0061](../decisions/0061-trait-coherence-orphan-and-overlap.md) |
| 実装のメソッド | `implement` の中の関数の名前が、型クラスのメソッドのどれかであり、すべてのメソッドを一度ずつ定義していること | [型システム](../01-spec/01-06-type-system.md) |
| 定数の循環 | 定数の定数式が、直接またはほかの定数を通して自分自身を参照しないこと。診断は循環する定数の並びを示す。手順 6 で判定する | [名前・スコープ・モジュール](../01-spec/01-03-names-modules.md)、[ADR 0123](../decisions/0123-top-level-constants.md) |
| 定数式の形 | 定数の右辺が、定数式に書けるものだけからなること。呼び出してよい関数（`Map.fromList` など）は、綴りではなく束縛の番号で `Benitoite` の名前空間のどの関数かを照合する（[ADR 0128](../decisions/0128-prelude-and-benitoite-namespace.md)）。手順 6 で判定する | [構文](../01-spec/01-02-syntax.md)の「定数（初回リリース版）」 |
| `main` の位置 | プログラムの入口として、実行を始めるモジュールのトップレベルの関数 `main` だけを引き、その束縛を型検査器に渡す。ほかのモジュールの `main` は普通の関数として扱う。`main` がないときと、条件を満たさないときの誤りは型検査器が報告する | [名前・スコープ・モジュール](../01-spec/01-03-names-modules.md)の「実行を始めるモジュール（初回リリース版）」、[エフェクト](../01-spec/01-07-effects.md) |

【方針】`@deprecated` を付けた宣言を、その宣言の外から名前で参照したときは、名前解決が警告を出し、属性の文字列を示す（[構文](../01-spec/01-02-syntax.md)の「属性（初回リリース版）」、[ADR 0119](../decisions/0119-attributes-test-and-deprecated.md)）。警告は次の段に進むことを妨げない（[パイプライン](02-01-pipeline.md)）。

### 名前の引き方

【方針】有効範囲の積み重ねは、関数の本体、ブロック、ラムダ、`case` の分岐、`handle` の節、`with` に入るときに一段積み、出るときに降ろす。各段は、名前から束縛の番号への表を持つ。同じ段に同じ名前を加えたときは、後の束縛で置き換える（[ADR 0010](../decisions/0010-shared-namespace-and-shadowing.md)）。束縛を段に加える時点は、次のとおりである（[名前・スコープ・モジュール](../01-spec/01-03-names-modules.md)の「局所の束縛の有効範囲」）。

- `let` は、右辺を解決した後で、左辺のパターンが束縛するすべての名前を現在の段に加える。
- `with` の束縛は、書いた順に、右辺を解決した直後にその名前を加える。後の束縛の右辺と本体から、前の束縛を使える（[リソース管理](../01-spec/01-10-resources.md)）。
- `case` の分岐は、パターンの変数を加えてから、ガードと本体を解決する。
- `handle` の節は、引数の名前を加えてから、節の本体を解決する。

【方針】`case` の分岐のパターンについて、次のことを行う（[代数的データ型とパターンマッチ](../01-spec/01-05-data-types.md)の「パターンの拡張（初回リリース版）」、[ADR 0121](../decisions/0121-pattern-extensions.md)）。

- コンマで並べた選択肢は、どれも同じ名前の集まりを束縛していなければならない。名前の集まりが違えば誤りとし、診断は、足りない名前と余分な名前を示す。型が同じかは型検査器が確かめる。
- 選択肢の同じ名前の変数には、同じ束縛の番号を使う。束縛の表の宣言したノードは最初の選択肢の変数のノードとし、ほかの選択肢の変数のノードは、参照の表でその束縛に結び付ける。本体の名前は、照合した選択肢によらず一つの束縛を指す。
- 一つのパターン（一つの選択肢）の中で同じ名前を二度束縛すると誤りとする。リストのパターンの `..rest` の `rest` も、パターンの変数として数える。
- `case` の分岐のパターンの変数に、その位置で見えるトップレベルの定数と同じ名前を付けると誤りとし、診断はガードで比べる書き方を示す（[ADR 0123](../decisions/0123-top-level-constants.md)）。`let` の左辺と引数では、定数と同じ名前をシャドーイングとして許す。

【方針】名前を引く順序は、[名前・スコープ・モジュール](../01-spec/01-03-names-modules.md)の「修飾しない名前の解決」と「修飾された名前の解決」に従い、次のように実装する。

- 修飾しない小文字の名前は、有効範囲の積み重ね（内側から）、同じモジュールのトップレベルの関数・定数・そのモジュールで宣言したエフェクトの操作の順に引く。
- 型を書く位置と `uses` の修飾しない大文字の名前は、その位置で有効な型パラメータとエフェクト変数、同じモジュールのトップレベルの名前、import で付けた名前、prelude の名前の順に引く。利用者の名前が見つかり、同じ名前の prelude の名前もあるときは、その参照を prelude を隠した参照の表に載せる。型検査器は、その参照に関わる診断に、prelude の名前を隠していることと `Benitoite.X` で prelude の側を書けることを添える（[ADR 0128](../decisions/0128-prelude-and-benitoite-namespace.md)）。
- 修飾した名前は、最初の段を、型パラメータとエフェクト変数（型と `uses` の位置だけ）、同じモジュールのトップレベルの大文字の名前、import で付けた名前、prelude の名前、名前空間の根 `Benitoite` の順に引き、次の段からは、直前の段が指すものの中で引く。ほかのモジュールの中で引くときは、そのモジュールの公開の表を使う。
- 名前空間の根 `Benitoite` の中では、prelude のモジュールだけを引く。prelude でない標準ライブラリのモジュールは、取り込んでいても `Benitoite.IO.Console` の形では引けない。
- パイプとプレースホルダは AST に書かれたままの形で辿る。プレースホルダは名前ではないので、解決しない。

### 誤りと修正案

【方針】名前解決は、次の誤りを報告する。一つの誤りを報告した後も、ほかの名前の解決を続ける。解決できなかった名前は、参照の表に載せない。

- 見つからない名前（修飾しない名前、修飾した名前の各段）。診断は、どの段で見つからなかったかを、その段の span で示す。
- 公開されていない名前（ほかのモジュールの、`public` を付けていない宣言の名前）。見つからない名前と区別し、その名前が公開されていないことを示す（[名前・スコープ・モジュール](../01-spec/01-03-names-modules.md)の「公開（初回リリース版）」）。
- 種類の合わない名前（式の中にドットなしで書いた型の名前、型を書く位置のエフェクト、型の別名で修飾した名前など。[名前・スコープ・モジュール](../01-spec/01-03-names-modules.md)、[型システム](../01-spec/01-06-type-system.md)）。`handle` の節に書いた名前は、式の小文字の名前と同じく引き、それが操作であるかは型検査器が判定する（[型検査器](02-05-typechecker.md)の「書く位置の検査」）。
- 名前の重複（前述の「解決の手順」の手順 1、引数の並び、一つのパターンの中、型パラメータの並び）。一つの `handle` の同じ操作の節は、型検査器が報告する（[型検査器](02-05-typechecker.md)の「書く位置の検査」）。
- 型パラメータの名前がトップレベルの大文字の名前か `Benitoite` と同じ場合。
- `uses` の並びの中の、エフェクト変数でもエフェクトでもない名前（型、型パラメータ、モジュールの名前）。
- レコードの構築とパターンのフィールドの名前が、レコードの宣言のフィールドと合わない場合（[代数的データ型とパターンマッチ](../01-spec/01-05-data-types.md)の「レコード（初回リリース版）」）。
- 前述の「import の宣言の誤り」と「宣言の検査」の誤り。

【決定】`uses` の並びの 2 番目以降にエフェクトでない名前があれば、それは関数の型の後の `uses` の並びを最長一致で読んだために、型の並びの次の要素が取り込まれたものでありうる。この場合の診断は、`help:` で、`uses` を持つ関数の型を括弧で囲む書き方（`function((function() -> Unit uses Console.Write), Integer) -> Unit`）を示す（[ADR 0047](../decisions/0047-parenthesized-types-and-uses-binding.md)、[ADR 0035](../decisions/0035-help-suggestions-without-rewriting.md)）。並びの最初の名前であれば、エフェクトの名前ではないことだけを示す。

【決定】`uses IO` の `IO` は、prelude のモジュールであってエフェクトではない。この誤りの診断は、`uses IO.All` を修正案として示す（[エフェクト](../01-spec/01-07-effects.md)の「組み込みのエフェクト」、[ADR 0130](../decisions/0130-builtin-effect-names-and-placement.md)）。

【方針】見つからない名前の診断には、次の修正案を示す。

- 綴りの近い名前。候補は、その位置で見える同じ種類の名前（修飾しない名前ならその位置で有効な局所の束縛と同じモジュールのトップレベルの名前、修飾された名前なら直前の段が指すものの中の名前。ほかのモジュールでは公開した名前だけ）のうち、編集距離（edit distance。ここではレーベンシュタイン距離）が 2 以下のものとし、距離の小さいものから最大 3 つを示す。
- 足りない import の宣言。修飾した名前の最初の段が見つからず、それが標準ライブラリのモジュールの名前の最後の要素（`Console`、`Json` など）と一致するときは、`import Benitoite.IO.Console` のような import の宣言を示す（[名前・スコープ・モジュール](../01-spec/01-03-names-modules.md)の「修飾された名前の解決」）。読んでいない標準ライブラリのモジュールは名前の表にないので、候補は、組み込みの表の標準ライブラリのモジュールの一覧から探す。
- 単位を持たない `String.length` などには、[基本型の意味論](../01-spec/01-04-types-basic.md)が定める修正案を示す。`Option` と `Result` のモジュールで見つからない名前が `unwrap` か `expect` であれば、`unwrapOr` と `case` を修正案として示す（[ADR 0043](../decisions/0043-option-result-rust-names-no-unwrap.md)）。
- `Option` と `Result` の構成子を修飾せずに書いたとき（`Some(x)`、`Ok(x)`、`Err(e)`）は、修飾した書き方を示す（[名前・スコープ・モジュール](../01-spec/01-03-names-modules.md)の「修飾しない名前の解決」）。

### 型検査の単位

【決定】型検査は、プログラム全体（読んだ標準ライブラリのモジュールを含む）を一つの単位として行う。宣言（型、型クラス、実装、関数のシグネチャ）をプログラム全体で先に検査し、その後で関数の本体を一つずつ検査する（[ADR 0156](../decisions/0156-module-loading-and-whole-program-checking.md)、[型検査器](02-05-typechecker.md)）。

### 初期化とインクリメンタルな処理

【方針】トップレベルの値の定義は、実行の前に値の定まる定数に限る（[名前・スコープ・モジュール](../01-spec/01-03-names-modules.md)の「実行を始めるモジュール（初回リリース版）」）。定数の値は型検査の段で求め（[パイプライン](02-01-pipeline.md)の「定数の評価」）、実行を始めるときにモジュールを初期化する処理はない。

【決定】変わったモジュールだけを検査し直すインクリメンタルな処理は、初回リリース版では行わない。検査のたびに、すべてのモジュールを読み込みから検査し直す（[ADR 0156](../decisions/0156-module-loading-and-whole-program-checking.md)）。LSP サーバを設計するときに見直す。
