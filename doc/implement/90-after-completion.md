# すべての作業を終えた後に行うこと

本章は、`20-tasks/` の作業をすべて終えた後に行うことを定める。これらは実装 LLM に割り当てる作業ではなく、オーケストレータ（Claude Code）と設計者が行う。

本プランは、いま U1 と U2 の作業だけを持つ（[README](README.md) の「範囲」）。本章も、U1・U2 を終えた時点で行うことと、U3・U4 を終えた後に行うことを分けて書く。U3・U4 の作業を本プランに書き足すときに、本章の後者の節も書き足す。

## U1・U2 の完了の確認

次の手順で確かめる。

1. `scripts/check.sh` と `scripts/check-heap.sh` がすべて通る（[実装の規約](00-common/00-02-conventions.md)の「完了条件の共通の検査」）。R14 の後なので、`check.sh` は採ったメモリの管理の方式だけで検査する。
2. `crates/benitoite/src/` に `todo!()` の仮置きと仮置きの許可が残っていない（`git grep -n 'todo!()' crates/benitoite/src` と `git grep -n 'allow(clippy::todo, unused_variables)' crates/benitoite/src` がどちらも空。[実装の規約](00-common/00-02-conventions.md)の「`todo!()` の仮置き」）。残っていれば、受け持つ作業に本体を書かせる。
3. U2 第 1 段の完了の条件（[ADR 0268](../design/decisions/0268-staged-runtime-rebuild.md) の決定 3）の四つが満たされたことを、C05・R11・R12・R14 の完了の報告と `tools/bench/results/` の第 1 段の記録で確かめる。
4. 仕様の網羅の道具（C17）が出す「確かめるテストのない節」の一覧を読む。節ごとに、テストを補うか、テストが要らない理由（規則を持たない節、単体テストが受け持つ節、U3・U4 の範囲の節など）を記録する。記録は本章の末尾に日付とともに書く。
5. fuzzing を、四つの対象（C15）それぞれについて長く（目安は 1 時間）実行する。見つけた不具合は、該当する作業の不具合として直させる。
6. 無作為に生成したプログラムの差分テスト（C14）を長く（`BENITOITE_RANDOM_PROGRAMS` を 10^5 以上）実行する。反例は、C14 の文書の「見つけた不具合の扱い」に従って扱い、01-12 の規則の誤りと分かったものは ADR を添えて規則を直す（[ADR 0213](../design/decisions/0213-formal-verification-stage-1-in-first-release.md) の決定 4）。
7. 作業の文書が【要検証】とした事項の結果を集める。少なくとも次のものがある。結果は、関係する設計書の章か ADR に書き、【要検証】を外す。
   - rustdoc の `compile_fail` の例が、ワークスペースの lint と警告の設定の下で期待どおりに働くか（[README](README.md) の「決めたこと」の 8、10-08「コンパイルの失敗のテスト」）
   - Miri で動かせる範囲（`mio` とスレッドを含む部分。00-02「完了条件の共通の検査」、07-03「ヒープとランタイムの確かめ方（初回リリース版）」）
   - nightly の Miri の実行で警告を誤りから外す必要があったか（C00）

## テストの整理

07-03「テストの設計の原則」は、マイルストーンの完了のときと実装プランの区切りのときに、スキル `test-audit` の監査の手順で価値の低いテストを整理するとした。U1・U2 の完了は実装プランの区切りに当たるので、ここで監査する。最小実行版では監査を初回リリース版に回した（`doc/archive/2026-09-27-implement-initial/90-after-completion.md`）ので、最小実行版から持ち越したテストも対象にする。

- 段ごとに一つのまとまりとして監査する（スキル `test-audit` の手順）。対象は、各段の単体テスト、ゴールデンテスト（C05 が移した最小実行版のテストと、C11・C12 が加えたテスト）、差分テスト、ヒープの確かめ方のテストである。
- とくに次の重なりを読む。C05 が移した最小実行版のテストと、C11・C12 が加えた初回リリース版のテストが同じ規則を確かめている箇所。第 1 段で VM を確かめるために手で組み立てたバイトコードのプログラムのテスト（R05・R09・R11）のうち、C05 の後のゴールデンテストが同じ振る舞いを確かめるようになったもの。持ち主の境界（07-03）の外で同じ契約を守っているテストは、境界の側を残す。
- テストを消すときは、消した理由を監査の記録に書く。監査の記録の置き場所と形は、スキル `test-audit` に従う。

## 性能の測定

[性能](../design/07-quality/07-02-performance.md)の「初回リリース版の完了時の測定」に従って測り、`tools/bench/results/` に記録する。手順はスキル `benchmark`（`.claude/skills/benchmark/SKILL.md`）に従う。道具は C16 が用意した。

- U1・U2 の完了の時点で測れるのは、最小実行版の 8 本と、C16 が加えた trait・handler・tasks・cycle・listget である。map（U3 の `Map` の関数を使う）と http（U3 の HTTP）は、U3 の後に測る。
- 入力の大きさを、Benitoite での実行時間が 1〜10 秒になるように調整してから本測定を行う（07-02「ベンチマーク集合」）。
- 最小実行版の記録（`tools/bench/results/2026-09-27-1ff816b0b156.md`）と同じ計算機で測れるときは、8 本について最小実行版からの変化を並べる（07-02 の最後の段落）。
- 呼び出しの回数の予算の初めの値を、tasks の測定で見直す（07-02「初回リリース版の完了時の測定」の実装の選択の影響）。http との釣り合いは U3 の後に見る。
- 中間表現の最適化の候補（02-06「最適化」）は、この測定の結果を見て、取り組むかを設計者が決める。取り組む場合は、変換ごとに作業を起こし、変換の有無で各ベンチマークを測って採るかを決める。
- 記録を 07-02「測定の結果の使い方」の三つの観点で並べ、[OPEN-009](../design/open-issues.md#open-009) の記述を更新する。musl と glibc のビルドの比較は、配布の作業（U4）の後に行う。

## U3・U4 を終えた後に行うこと

U3・U4 の作業を終えた後に、次を行う。

- ロードマップの初回リリース版の完了条件（[ロードマップ](../design/00-overview/00-03-roadmap.md)の「初回リリース版」の「完了条件」）の各行を、07-03「受け入れ例と仕様の項目の対応」の表の確かめ方で確かめる。同梱の Agent Skill だけを与えた LLM の試行と、各環境での単一バイナリの実行は、処理系のテストの外で行う。
- C17 の索引の初回リリース版の表がすべて埋まっていることを確かめる（空の行を誤りにする形への改めは D34 が行う）。
- map・http のベンチマークを加えて測り、OPEN-036 と OPEN-009 を決着させる。
- OPEN-062 の R14 の再現テストの結果を記録し、OPEN-062 を決着させる。

U3 について、次を行う。

- map と http のベンチマーク（L41）を、スキル `benchmark` の手順で本測定する。http は、計算を続けるタスクの有無の二つの形と、呼び出しの回数の予算を変えた実行を測る（07-02）。この測定を R33 の測り直しに加えて、OPEN-036 を決着させる。
- 非公式のモジュール（ADR 0286）のうち、設計者が吟味を終えたものを標準に移すかを決める。移すのは、初回リリース版の後のマイナーの版である（ADR 0286 の決定 7）。

U4 について、次を行う。

- 同梱の Agent Skill の評価（06-06「Skill の評価」）を、設計者の了承を得てから、D23 の道具とスキル `skill-eval` で行う。二つ以上のハーネスで課題ごとに複数回試行し、記録を `tools/skill-eval/results/` に置く。ロードマップの完了条件の JSON の集計の課題が、各ハーネスで試行の過半数で成功したことを確かめ、成功した試行のスクリプトを `testdata/acceptance/json_summary` のテストに加える（07-03「受け入れ例と仕様の項目の対応」の最初の行）。
- 処理系の版（`crates/benitoite/Cargo.toml` の `version`）が `0.1.0`（D31 が改めた。ADR 0090）であり、`CHANGELOG.md` の版と揃っていることを確かめる。
- `scripts/release.sh`（D31）を、WSL2 の段を含めて通す。WSL2 の段と、Gatekeeper の対処が利用者向けの文書のとおりに働くことの確かめは、設計者の機械で設計者が行う。
- 公開の前に、設計メモの扱い（OPEN-061）を設計者が決める。`publish` の段は、その後に設計者の確かめを経て行う。著作権表示（ADR 0290）は D30・D33 が `LICENSE-MIT`・README に書いてある。
- D32 が書いた OPEN-060 の決着の ADR の案を設計者が確かめ、採択したら OPEN-060 を決着にする。

## 実装プランの保管

初回リリース版のすべての単位（U1〜U4）の実装を終え、上の確認を終えたら、本プランを `doc/archive/` へ移す（AGENTS.md「ディレクトリ構成」の `doc/implement/` の行）。

1. `doc/implement/` を `doc/archive/<日付>-implement-first-release/` へ `git mv` で移す。検討資料（`studies/`）も一緒に移す。
2. 移した後の文書の中の相対リンクが切れていないことを確かめる。設計書の章から、移したプランへリンクしない（ADR が経緯として参照するのはよい）。設計書の章に `doc/implement/` へのリンクがあれば、移す前に外す。
3. AGENTS.md の「プロジェクトの概要」「ディレクトリ構成」の `doc/implement/` と `doc/archive/` の行、「実装の規約」の節の冒頭（正は 00-02 とした文）を改める。実装の規約の正を、移した後にどこに置くかは、次の版の実装プランを作るときに決める。それまでは AGENTS.md の節を正とする旨を書く。
4. `.claude/agents/` の実装を担うサブエージェントの定義が、移した後のプランのパスを指すなら、次の版のプランを作るまでの扱いを決めて改める。

## 学習のための読み方

設計者が処理系を読んで学ぶ（[目的と設計原則](../design/00-overview/00-01-goals.md)）ための入口として、次の順を勧める。パスは `crates/benitoite/` からの相対である。各モジュールの先頭の `//!` のコメントが、対応する設計書の章を示す。

1. 開発用の例 `examples/disasm.rs` で、小さなスクリプトのコンパイル済みプログラムを表示し、10-07 の命令の集合と見比べる。
2. `src/runtime/heap/` で、内部の層の `unsafe` と `// SAFETY:` のコメントが引く不変条件、公開の層の `Value<'epoch>`・`NoGcCtx<'epoch>` が型で守っていることを読む（ADR 0260）。二つのメモリの管理のうち採らなかった方式は、R14 が残したリビジョンで読める。
3. `src/vm/dispatch.rs` と `src/vm/frame.rs` で、振り分けのループの局所の状態と、区画と枠の持ち方を読む（ADR 0262・0263）。
4. `src/vm/handler.rs` と `src/vm/unwind.rs` で、一度だけ再開できる継続が区画の移動として実装されていることを読み、01-12 の `handle`・`resume` の規則と、`src/refinterp/` の同じ規則の実装とを見比べる。
5. `src/typeck/` で、型クラスの辞書の解決とエフェクトの検査の順序を読み、`src/ir/desugar.rs` で辞書の受け渡しに変わる様子を読む（ADR 0158）。
6. `src/runtime/sched/` と `src/runtime/io/` で、タスクとリソースの状態の表と、送り出しの列・書き出し用のスレッドを読む（ADR 0264〜0266）。
