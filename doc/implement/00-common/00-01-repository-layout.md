# リポジトリとクレートの配置

本章は、初回リリース版の処理系のソースコード・テスト・道具・測定記録をリポジトリのどこに置くかと、処理系のクレートのモジュールの構成を定める。最小実行版の配置（最小実行版の実装プランの 00-01。`doc/archive/2026-09-27-implement-initial/00-common/00-01-repository-layout.md`）を引き継ぎ、初回リリース版で変える点を書く。

## リポジトリの配置

```text
Benitoite/
├── AGENTS.md                      エージェント向けの指示（ディレクトリ構成と実装の規約を含む）
├── Cargo.toml                     Cargo のワークスペースの定義と lint の水準（C00 で改める）
├── Cargo.lock
├── rust-toolchain.toml            Rust の版の固定（1.98.1 のまま）
├── deny.toml                      cargo-deny の設定
├── .cargo/config.toml             警告を誤りにする設定
├── .claude/                       プロジェクトのスキル（skills/）とサブエージェントの定義（agents/）
├── .agents/skills/                スキルへのシンボリックリンク（Codex・OpenCode 向け）
├── crates/
│   └── benitoite/                 処理系のクレート（lib と bin）
│       ├── Cargo.toml             機能（feature）の定義（次節の「機能」）
│       ├── src/                   処理系のソース（後述の「処理系のクレートのモジュール」）
│       │   └── legacy/            最小実行版の実装（移行の間だけ置く。後述の「移行の間の配置」）
│       ├── tests/                 統合テスト（ゴールデンテストの実行器、差分テストなど）
│       ├── testdata/              ゴールデンテストのスクリプトと期待値
│       ├── testdata-next/         新しい構文で書き直した最小実行版のテスト（C03 が置き、C05 が testdata/ へ移す）
│       └── examples/              開発用の例（disasm、bytecode_stats）
├── tools/
│   ├── grammar-check/             言語仕様と付録 08-04 の例の検査（C13 が両方を処理系の検査に置き換えたら消す）
│   ├── syntax-measure/            構文の案ごとの測定の道具（OPEN-012）
│   ├── spec-coverage/             仕様の網羅の集計
│   └── bench/                     ベンチマークと測定記録（results/）
├── fuzz/                          cargo-fuzz のクレート（ワークスペースに含めない）
├── scripts/
│   ├── check.sh                   完了条件の共通の検査（C00 で広げる）
│   ├── check-heap.sh              nightly の Rust が要る検査と時間のかかる検査（C00 で加える。後述）
│   ├── fuzz-seed.sh
│   └── fuzz-short.sh
└── doc/
    ├── design/                    設計書
    ├── implement/                 本実装プラン
    ├── archive/                   最小実行版の設計書と実装プランの写し
    └── reference/                 言語リファレンス
```

- 測定記録は、最小実行版と同じく `tools/bench/results/` に置く。第 1 段の比べた構成・入力・暫定に採った方式の記録（[ADR 0268](../../design/decisions/0268-staged-runtime-rebuild.md) の決定 3）もここに置く。
- `scripts/check-heap.sh` は、[処理系のテスト戦略](../../design/07-quality/07-03-compiler-testing.md)の「ヒープとランタイムの確かめ方（初回リリース版）」が「別のスクリプト」とした検査を行う。Miri は nightly の Rust の部品であり、Rust 1.98.1 のツールチェーンには入らない（2026-09-30 に `cargo +1.98.1 miri` が使えないことを確かめた）。nightly の Miri の導入は、オーケストレータが C00 の前に行う（[作業の進め方](00-03-workflow.md)の「担当と起動の方法」）。

## 処理系のクレートのモジュール

処理系は、最小実行版と同じく単一のクレート `benitoite` とする。新しいクレートは作らない。最小実行版のモジュールは C04 が `legacy` の下へ移し（後述の「移行の間の配置」）、初回リリース版のモジュールは下の表の最終的なパスに置く。段の間の境界は、クレートではなく凍結した型とシグネチャ（`10-interfaces/`）で守る。

「扱い」の欄の意味は次のとおりである。

- 写して広げる: `src/legacy/` の最小実行版のコードを写し、初回リリース版の機能を加える。
- 作り直す: 新しいインターフェースに合わせて書く。最小実行版のコードは、意味を確かめるために読んでよい。
- 加える: 新しいモジュール。
- 共有する: `legacy` へ移さず、最小実行版の実装と初回リリース版のモジュールが同じものを使う。

| モジュール | 役割 | 扱い | 主な作業 | インターフェース（予定の章） |
|---|---|---|---|---|
| `base` | 専用の整数の型、span、複数のファイルのソースの表、`Decimal` の値の表現 | 共有する（型を加える） | C02, F05, F07 | 10-01 |
| `diag` | 診断の表現、診断コードの表、診断の書き出し | 写して広げる | F16 | 10-02 |
| `syntax` | 字句、AST、構文解析 | 作り直す（構文の改め。文字の読み方は写してよい） | F01〜F04 | 10-03 |
| `modules` | モジュールの探索と読み込み、依存グラフ | 加える | F05 | 10-04 |
| `resolve` | 名前解決 | 写して広げる | F06 | 10-04 |
| `types`・`typeck` | 型とエフェクトの表現、型クラスと辞書、型検査 | 写して広げる | F07〜F10 | 10-05 |
| `ir` | コア IR、下位 IR、脱糖、判定の木、コア IR の検査器 | 写して広げる（IR の型は共有の章で凍結し直す） | F11〜F13 | 10-06 |
| `refinterp` | 参照インタプリタ（テスト専用） | 作り直す（値を VM と分け、組み込みの関数の本体だけを共有する。ADR 0276） | R10, F14 | 10-06 |
| `bytecode` | 命令の符号化、コンパイル済みプログラム、コード生成、生存の情報、逆アセンブラ | 命令の集合を作り直す。コード生成は写して広げる | R05, R09, F15 | 10-07 |
| `runtime::heap` | 確保器、対象の頭、回収しない区間の型、根の保存領域、二つのメモリの管理 | 作り直す | R01〜R04, R06, R11 | 10-08 |
| `runtime`（止まる理由、`list`・`map`・`equal`） | 止まる理由、リスト・マップ・集合・構造の等しさ | 作り直す | R06, R35〜R37 | 10-08 |
| `runtime::panic` | panic 境界 | 写す（名前とシグネチャを変えない） | R09 | 10-08 |
| `runtime::report`・`runtime::run` | 実行時エラーの報告、実行の流れ | 作り直す | R38（報告）、F18・R26・R28（実行の流れ） | 10-13 |
| `vm` | 区画と枠、振り分けのループ、ハンドラ、タスクの対象 | 作り直す | R09, R20〜R25, R34, R35 | 10-09 |
| `runtime::sched`・`runtime::io` | スケジューラ、送り出しの列、IO 実行器、操作の記録、書き出し用のスレッド | 作り直す（最小実行版の `executor`・`real_io`・`test_io` に代わる） | R25〜R28 | 10-10 |
| `builtins` | 組み込みの関数の型付きの形、組み込みの表、組み込みの関数 | 作り直す（型付きの形。関数の意味は写す） | R07, R08, R29 | 10-11, 10-12 |
| `prelude` | prelude と標準ライブラリのソース | 写して広げる | F05, F08 | 10-14 |
| `pipeline`・`cli` | 段をつなぐ公開の関数と CLI（`run`・`check`） | 写して広げる | F18 | 10-13 |
| `legacy` | 最小実行版の実装 | 移行の間だけ置く | C04, C05, C18 | —（凍結しない） |

モジュールの中のファイルの分け方は、10-interfaces がファイルを指定したものはそれに従い、そのほかは作業の文書に従う。作業の文書が指定しないときは、実装 LLM が決めてよい。

参照インタプリタとコア IR の検査器は、最小実行版と同じく `#[cfg(test)]` にせず、ライブラリの公開の関数にする。統合テストと fuzzing のクレートから呼ぶためである。利用者が使う経路（`pipeline` と `cli`）からは呼ばない。

### 移行の間の配置

最小実行版の実装は、C04 から C18 までの間、`crate::legacy` の下に置く（[README](../README.md) の「決めたこと」の 11）。古い CLI とテストを動かし続けたまま、初回リリース版のモジュールを最終的なパスに置くためである。どの作業の取り込みの後も、クレートはコンパイルでき、`scripts/check.sh` が通る。

C04 は、次の手順で移す。振る舞いは変えない。

1. `src/` の下の次のものを `src/legacy/` の下へ、同じ名前のまま移す（`git mv`）: `builtins/`・`bytecode/`・`cli/`・`diag/`・`ir/`・`prelude/`・`refinterp/`・`resolve/`・`runtime/`・`syntax/`・`typeck/`・`types/`・`vm/`・`pipeline.rs`。これらの元のパスは空く。移さないのは `base/`・`lib.rs`・`main.rs` だけである。
2. `src/legacy/mod.rs` を加え、移したモジュールを `pub mod` で宣言する。先頭の `//!` に、最小実行版の実装であり C18 が消すことを書く。
3. 移したファイルの中の `crate::<移したモジュール>` を `crate::legacy::<移したモジュール>` に書き換える。`crate::base` はそのまま残す。
4. `src/lib.rs` を、`pub mod base;` と `pub mod legacy;` だけを宣言する形にする（C01 が 10-01 の `lib.rs` で置き換える）。`src/main.rs` は `benitoite::legacy::cli::main()` を呼ぶ形にする。
5. `tests/`・`examples/`・`fuzz/fuzz_targets/` の `benitoite::<移したモジュール>` を `benitoite::legacy::<移したモジュール>` に書き換える。`testdata/` は変えない。
6. AGENTS.md の「実装の規約」の `#[allow]` の表と「大域の状態」の panic hook の記録の箇所に、`src/legacy/` の下の同じファイルを加える。

C04 の後は、最小実行版の CLI（`benitoite run`・`check`）とゴールデンテスト、差分テスト、fuzzing の対象は `legacy` の実装を通して動く。初回リリース版のモジュールは、C04 が空けたパスに C01・C02 が置く（`10-interfaces/` の `replace` の属性は、C04 の後も残る `src/lib.rs` と `src/base/mod.rs` にだけ付ける）。

移行の間、`src/legacy/` と、`legacy` を通して動くテスト（`tests/` の最小実行版のゴールデンテストの実行器など）を変えてよいのは、次の作業だけである。ほかの作業は `legacy` を読むだけにし、コードを写すときは写した先で変える。

| 作業 | `legacy` で行うこと |
|---|---|
| C04 | 移す（上の手順） |
| C05 | 古い構文のゴールデンテスト（`testdata/`）と、それを走らせる `legacy` の実行器の部分を消し、C03 が新しい構文で書き直したテスト（`testdata-next/`）を `testdata/` に移して初回リリース版の実行器（C10）で走らせる。`main.rs` を初回リリース版の CLI（`benitoite::cli`）を呼ぶ形に改め、CLI のプロセスのテスト（`tests/cli_process.rs`）とベンチマークのプログラム（`tools/bench/programs/` の `.bnt`）を新しい構文に移す |
| C13 | `legacy` の構文解析器で言語仕様の例を読む `tests/spec_examples.rs` を、初回リリース版の検査に置き換える（07-03 が定めたファイルの名前を保つ） |
| C15 | `legacy` のパイプラインを呼ぶ fuzzing の対象（`fuzz/fuzz_targets/`）を、初回リリース版のパイプラインに移す。移した後、`fuzz/` は `legacy` を参照しない |
| C18 | `src/legacy/` を消す。`lib.rs` の `pub mod legacy;` と `dead_code` の許可を外し、テスト・例・fuzzing・測定の道具に残る `legacy` の参照を初回リリース版のモジュールに移す。最小実行版の文書だけを確かめるテスト（`tests/language_reference.rs`）は消す |

`legacy` の中に、初回リリース版の VM で最小実行版のプログラムを動かす経路は作らない（[README](../README.md) の「決めたこと」の 5）。U2 第 1 段の作業は、C05 までは手で組み立てたバイトコードのプログラム（10-07「第 1 段で実行するプログラム」）で確かめる。

C05 の後は、`benitoite` のコマンドは初回リリース版のパイプラインで動く。第 1 段の性能の測定（R12）は、このコマンドで行う。C05 の後の `legacy` は、`legacy` の単体テストと、C18 が移すまでの例・fuzzing の対象のほかでは使われない。

### `unsafe` を書いてよいモジュール

`unsafe` を書いてよいのは、`runtime::heap` の下だけである（[ADR 0260](../../design/decisions/0260-heap-and-unsafe-boundary.md)）。`runtime::heap` は、中身を次の二層に分ける。

| 層 | 内容 | `unsafe` |
|---|---|---|
| 内部の層 | 確保器（塊の確保と解放、対象の頭の読み書き）、区間の寿命を外した生の値、根の保存領域と根の列挙、マーク・スイープのマークと掃き出し、参照カウントの増減と解放 | 書いてよい。`#[allow(unsafe_code)]` は、この層のファイルの先頭に置く |
| 公開の層 | `Value<'epoch>`・`NoGcCtx<'epoch>`、対象を作る関数と読む関数、安全点で回収を行う関数 | 書かない。内部の層の安全な関数だけを呼ぶ |

VM・組み込みの関数・参照インタプリタなど、`runtime::heap` の外のモジュールは `unsafe` を書かない。振り分けのループで範囲の確かめを省く `unsafe`（[OPEN-064](../../design/open-issues.md#open-064)）は、R32 の評価で採ることにした場合に限り、許す箇所をこの表に加える。

### 機能（feature）

処理系のクレートの機能は次のとおりとする。C00 が `crates/benitoite/Cargo.toml` に置く。

| 機能 | 内容 | 既定 |
|---|---|---|
| `gc-mark-sweep` | 回収を安全点に限るマーク・スイープ（[ADR 0259](../../design/decisions/0259-compare-mark-sweep-and-rc-in-stage-1.md)） | 有効 |
| `gc-refcount` | 改良した参照カウントと、ADR 0239 の循環の回収 | 無効 |
| `gc-stress` | `HeapConfig::stress` を常に真として扱う（回収の強制）。安全点ごとに必ず回収し、参照カウントでは回収ごとに循環の回収も行う（10-08「設定と測定の記録」） | 無効 |
| `heap-verify` | デバッグのビルドで、ヒープの検証器、確保の世代による生存の確かめ、解放した領域の毒を有効にする（`Slot` のヒープの番号の比較は、この機能によらずすべての構成で行う。ADR 0281） | 無効 |
| `heap-per-object` | 対象ごとに確保と解放をする構成（塊の中の論理的な解放の誤りを、Miri などで見つけやすくする） | 無効 |
| `alloc-stats` | 確保と解放の回数の計数（最小実行版から引き継ぐ） | 無効 |
| `bundled-licenses` | リリースのスクリプトが生成した第三者のライセンスの表示 `licenses/THIRD_PARTY_LICENSES` を実行ファイルに埋め込む（[10-19](../10-interfaces/10-19-skill-and-distribution.md)「第三者のライセンスの表示」）。D30 が加える。ファイルがなければビルドできないので、`scripts/check.sh` は有効にせず、リリースのスクリプトだけが有効にする | 無効 |

- `gc-mark-sweep` と `gc-refcount` は、どちらか一方だけを有効にする。両方を有効にしたとき、どちらも有効にしないときは、`compile_error!` でビルドを止める。既定のビルドはマーク・スイープとし、第 1 段の締め（R14）で、暫定に採った方式を既定にしたうえで、採らなかった方式の機能を消す。
- 最小実行版の `scripts/check.sh` は `--all-features` で lint とテストを行うが、二つのメモリの管理は同時に有効にできない。C00 は、`check.sh` を機能の組み合わせごとに分けて実行する形に改める。組み合わせは、[実装の規約](00-02-conventions.md)の「完了条件の共通の検査」で定める。
- U1 の作業（F で始まる作業）は、どちらのメモリの管理でもビルドとテストが通るように書く。回収の方式に依存する API は `runtime::heap` の公開の層の外に出さない。
