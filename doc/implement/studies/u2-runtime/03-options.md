# 設計の問いと選択肢

- 状態: 検討中

## この資料の範囲

値の表現とランタイムの作り直しで決める問いを Q1〜Q10 に分け、問いごとに選択肢を比べる。各問いは次の順に書く。

1. 問いと、それを縛る要求（[02-requirements.md](02-requirements.md) の ID）
2. 選択肢の比較の表
3. 先行事例（処理系の名前と、その処理系が何をしているか）
4. 処理系のほかの部分への影響、LLM による実装の難しさ、設計者が学ぶ価値
5. 暫定の推奨と、専門家に聞きたいこと

先行事例の記述は、筆者が知っている範囲の要約であり、細部は一次資料で確かめていない。確かめていない細部には【要検証】を付けた。[ADR 0240](../../../design/decisions/0240-runtime-redesign-in-first-release-plan.md) の決定 1 は作り直しを自作で行うとしているので、GC を提供する Rust のクレートは、使う候補ではなく読む先行事例として挙げる。

## Q1 値の表現

縛る要求: S01、S02、S04、R10、E01、F02。

問いは、レジスタと構造の中に置く一つの値を何バイトで、どう表すかである。今の実装は 24 バイトの Rust の列挙型であり（[01-current-state.md](01-current-state.md) の「大きさ」）、設計書の方針（16 バイト）より大きい。

| 選択肢 | 概要 | 利点 | 欠点 |
|---|---|---|---|
| 1a 今の列挙型（24 バイト） | `Rc<str>` の太いポインタと、構成子のタグと参照の組を選択肢に直接持つ | 変更がない | 値を写すたびに 24 バイトを動かす。方針と合わない |
| 1b 16 バイトの列挙型 | 種類の印と 8 バイトの中身。ヒープの参照はすべて細いポインタ（長さは対象の頭に置く）。引数のない構成子のタグ、リソースの番号は即値にする | `Integer` と `Float` をボックス化しない（S02 を満たす）。`unsafe` なしでも書ける。Rust が選択肢の配置を決める | 8 バイトの表現より、レジスタとリストの要素が倍の大きさになる |
| 1c 16 バイトの手書きの構造体 | 印のバイトと `union` の中身を手で組む（Lua の `TValue` の形） | 配置を完全に制御できる | 1b と配置はほぼ同じになり、`unsafe` の読み出しが増えるだけで得るものが小さい |
| 1d 8 バイトの下位ビットのタグ | 整数の最下位ビットを 1 にして 63 ビットの整数を即値にし、ほかはポインタにする（OCaml の形） | 値が 8 バイトになり、写す費用とメモリが半分になる | 64 ビットの `Integer`（S02）が収まらない。63 ビットを超える整数をボックス化すると、整数の演算のたびに分岐が増え、仕様の範囲の整数で確保が起きる。`Float` はボックス化するので、浮動小数点数の演算のたびに確保する |
| 1e 8 バイトの NaN-boxing | 倍精度の NaN の空きビットにポインタと小さな即値を詰める（LuaJIT の形） | `Float` をボックス化しない | 64 ビットの `Integer` が収まらない（1d と同じ問題）。WASM などのポインタの幅に依存する（F02） |

小さな文字列を値の中に埋め込む表現（8 バイトの中身に 7 バイトまでの文字列を入れるなど）は、1b に加えられる。しかし、`String` を扱うすべての組み込みの関数が二つの表現を区別する必要があり、U3 の文字列の関数の数だけ誤りの機会が増える。文字列の定数は定数の値の表で使い回しているので、効果は string と lines のベンチマークで測ってから決める。

### 先行事例

- **Lua 5.4**: 値は、中身の `union`（ポインタ、整数、浮動小数点数など）と型の印のバイトからなる `TValue` であり、64 ビットの計算機では 16 バイトになる【要検証：`lobject.h` の定義と、5.5 での変更の有無】。整数と浮動小数点数はどちらも 64 ビットの即値である。
- **LuaJIT 2**: 8 バイトの NaN-boxing で値を表す【要検証：GC64 の構成でのポインタの詰め方】。
- **OCaml**: すべての値を 1 語で表し、最下位ビットが 1 の語を 63 ビットの整数、0 の語をヒープのブロックへのポインタとする。浮動小数点数は、浮動小数点数だけの配列とレコードなどの例外を除いてボックス化する。
- **V8**: 小さな整数（Smi）をポインタのタグで即値にし、ほかをヒープの対象にする。ポインタの圧縮を有効にした構成では Smi は 31 ビットである【要検証】。
- **CPython**: すべての値をヒープの対象（`PyObject*`）とし、小さな整数（-5〜256）を前もって作って共有する。

### ほかの部分への影響、難しさ、学ぶ価値

- 影響: 組み込みの関数は今も `as_int` などの読み出しの関数を通して値を読むので、読み出しの関数の名前と形を保てば、1b への変更は機械的に行える。命令とコード生成は変わらない（命令は型ごとに分かれており、値の印を見ずに演算できる）。
- 難しさ: 1b は低い。1d・1e は、整数の溢れの規則（S02）を保つための境界の処理が細かく、LLM が誤りやすい。
- 学ぶ価値: 1d・1e は「なぜ多くの処理系がタグ付きの語を使うのか」を学ぶ題材として価値が高い。ただし、本言語が 64 ビットの整数を仕様にした（[ADR 0006](../../../design/decisions/0006-basic-types-semantics.md)）ことで、その利点を得にくいこと自体が、仕様と表現の関係を学ぶ題材になる。

### 暫定の推奨

1b。値は 16 バイトとし、`Integer`・`Float`・`Byte`・`Boolean`・`Character`・`Unit`・引数のない構成子・リソースの番号を即値にする。ほかはヒープの対象への細いポインタにし、対象の種類は対象の頭に置く。値の型は `Send` にしない（R10 を型で守る）。Q2 で追跡型の GC を選べば、値は `Copy` になる。

専門家に聞きたいこと:

- 64 ビットの整数を仕様に持つ静的型の言語で、8 バイトの表現（大きな整数だけをボックス化するなど）が 16 バイトの表現より速くなった実例があるか。
- 引数のない構成子とリソースの番号を即値にすることに、見落としている損（構造の `=` や表示の分岐が増えるなど）があるか。

相談の第 1 回（[記録](consult/01-memory-and-values.md)の問い 4）を受けて、次のものを第 1 段に加える。64 ビットの整数の仕様は 8 バイトの値を禁じない（小さな整数を即値、大きな整数を箱に入れる形がある）ので、第 1 段の測定で整数の値の範囲と対象の大きさを記録し、8 バイトの案を試す価値を判断する。Rust の既定の表現の列挙型には大きさの保証がない【要検証】ので、値が 16 バイトであることをテストで確かめる。

## Q2 メモリの管理

縛る要求: M01〜M04、R03、R04、R07、C01、E02、P02、F01。

問いは、使わなくなった値をどう回収するかである。今の設計の暫定の方式は、参照カウントに `Reference` のセルを起点にした循環の回収を加えるものである（[ADR 0239](../../../design/decisions/0239-cycle-collection-for-reference-cells.md)）。

言語の性質のうち、この問いの判断にかかわるものを先に挙げる。

- 値は、`Reference` のセル、`Lazy` の対象、継続の対象を除いて、作った後に変わらない（ADR 0239 の「循環を作れる値」）。
- 言語には finalizer がなく、リソースはメモリの管理で解放しない（M03）。したがって、回収の時期は観測できず、方式を自由に選べる。
- 一つの実行は一つのスレッドで進む（C01）。参照の数を原子的に増減する必要はない。
- 言語の値は、枠のレジスタ、継続の区画、タスクの表、ハンドラの記録、定数の値の表といった VM が持つデータ構造の中にしかない（[ADR 0016](../../../design/decisions/0016-calls-off-go-stack.md) により、言語の呼び出しは Rust のスタックを使わない）。例外は、組み込みの関数が実行している間の Rust の局所変数だけである。そのため、追跡型の GC の根を正確に数え上げやすい。

| 選択肢 | 概要 | 利点 | 欠点 |
|---|---|---|---|
| 2a 参照カウント＋セルを起点にした循環の回収（ADR 0239 のまま、改良を加える） | 対象の頭に参照の数を置き、独自の確保器で確保する。コード生成が最後の使用を移動にして増減を減らす。組み込みの関数は、参照の数が 1 の対象をその場で書き換えてよい | 解放が即時で、最大常駐メモリが小さくなりやすい。組み込みの関数が値を持ち続けても安全。最小実行版の作りと知見を生かせる | 値を写すたびに増減が要り、値は `Copy` にならない。循環の回収のために、結局すべての対象の子を辿る処理を書く。二つの機構（参照カウントと回収）を保守する。タスクの表の項目の寿命（M02）は別に決める必要がある |
| 2b Perceus 型の参照カウント | 中間表現で、値の複製（dup）と破棄（drop）を最後の使用に合わせて挿入し、借用を推論し、一意な対象の再利用（reuse）を行う | 不要な増減をコンパイル時に消せる。関数型の更新（木の組み直しなど）を、一意なときはその場の書き換えにできる | 中間表現とコード生成に大きな解析が加わり、U1 と U2 の境界をまたぐ。セルの循環の回収は別に要る。永続ベクタや平衡木の再利用は複雑 |
| 2c 止めて行う非移動のマーク・スイープ | 対象を独自の確保器（大きさの区分ごとの空きリスト、大きな対象は別）で確保する。回収は切り替えの位置（安全点）だけで、全タスクの枠などを根として印を付け、印のない対象を掃く | 値を写す費用が 16 バイトの写しだけになり、値を `Copy` にできる。循環とタスクの表の項目の寿命（M01、M02）を一つの機構で扱える。組み込みの関数の実行中は回収しないので、組み込みの関数は根を登録しなくてよい | 回収による停止が生きている対象の量に比例する。ヒープは生きている量の数倍まで伸びうる。一意な対象のその場の書き換えはできない。根の数え漏れは use-after-free になる（`unsafe` の誤りとして現れる） |
| 2d 世代別の GC | 若い世代を連続した領域に確保して写す GC で回収し、古い世代をマーク・スイープで回収する（OCaml の形） | 短命な対象の多い関数型のプログラムで、確保と回収が最も速くなりやすい | 対象が動くので、写しの後に参照を付け替える。古い対象を書き換える箇所（セル、`Lazy`、タスクの結果、継続の状態）に書き込みの障壁が要る。実装が大きく、誤りの見つけにくい部分が増える |
| 2e タスクごとのヒープ | タスクごとにヒープを分け、タスクの間で値を渡すときに写す（Erlang の BEAM の形） | タスクごとに独立して回収でき、将来の並列（F01）に近い | タスクの間で不変の値を自由に共有し、セルも共有する言語の意味と合わない。起動と `Task.await` のたびに写す費用がかかる |

### 回収の時期を安全点に限ることの意味

2c と 2d は、回収を切り替えの位置（関数の呼び出しと待つ位置）に限れば、組み込みの関数の書き方を単純に保てる。安全点では、生きている言語の値はすべて VM のデータ構造（レジスタ、区画、継続、タスクの表、定数の値の表、ハンドラの記録）の中にあり、Rust の局所変数には残っていない。したがって、組み込みの関数は、実行の途中で値を作っても、値を局所変数に持っても、回収で壊れない。言語にはループがなく、どの繰り返しも関数の呼び出しを通るので、安全点の間に実行する命令の数は関数の本体の大きさで抑えられる。一つの組み込みの関数が作る値の量は、大きさの上限（R08）で抑えられる。

この決め方の条件は二つある。一つは、組み込みの関数が値を実行の外に持ち越さないことである（応答の「待つ」の後で使う値は、Rust の閉包に捕えず、枠のレジスタに残す。Q7）。もう一つは、VM の振り分けのループが、安全点をまたいで値を Rust の局所変数に持たないことである。

### 先行事例

- **CPython**: 参照カウントを主とし、循環は、参照の数から候補の内部の参照を差し引く方法の循環の回収で補う（[gc モジュールの文書](https://docs.python.org/3/library/gc.html)、ADR 0239 が引く [GC の設計の文書](https://github.com/python/cpython/blob/main/InternalDocs/garbage_collector.md)）。世代の数と、3.13 以降の増分の回収の扱いは版で変わっている【要検証】。
- **Swift**: コンパイラが参照の数の増減を挿入する ARC であり、循環の回収は持たず、循環は `weak`・`unowned` の参照で利用者が切る。参照の数の増減は原子的である【要検証：非原子的にする最適化の有無】。
- **Koka（Perceus）と Lean 4**: 参照カウントの増減をコンパイル時に正確に挿入し、一意な対象を再利用する（Reinking, Xie, de Moura, Leijen, "Perceus: Garbage Free Reference Counting with Reuse", PLDI 2021。Ullrich, de Moura, "Counting Immutable Beans", IFL 2019）。
- **OCaml**: 若い世代（minor heap）を写す GC で、古い世代（major heap）を増分のマーク・スイープで回収する。OCaml 5 で複数のドメインに対応した【要検証：OCaml 5 の minor heap の持ち方】。
- **Lua 5.4**: 増分のマーク・スイープを持ち、5.4 で世代別の方式を選べるようにした【要検証：5.5 での既定】。
- **Erlang の BEAM**: プロセスごとのヒープを世代別の写す GC で回収し、メッセージは写して渡す。大きなバイナリはプロセスの外に置いて参照の数で共有する【要検証：外に置く大きさの境目】。
- **Rust のクレート（読む先行事例として）**: `gc-arena` は、生成的な寿命（branded lifetime）で GC の参照を領域の外に持ち出せないようにし、回収を変更の区切りの外でだけ行う【要検証】。`dumpster` は循環を見つける参照カウント型の GC【要検証】、`bacon-rajan-cc` は Bacon と Rajan の同期的な循環の回収を `Rc` に加える【要検証】。

### ほかの部分への影響、難しさ、学ぶ価値

- 影響: 2a は、U1 のコード生成に「最後の使用での移動」を加えると効果が大きい（加えなくても動く）。2b は U1 の中間表現に解析の段を加える。2c は、VM とランタイムの中で根を数え上げる処理を一か所に書き、コード生成は変わらない。2d は 2c に書き込みの障壁が加わる。どの方式でも、リソースは表の番号のまま変わらない。
- 難しさ（LLM による実装）: 2a は中程度（最小実行版で実績がある）。2c は中程度だが、根の数え漏れが静かな記憶の破壊になるので、Q8 の確かめ方と組にする必要がある。2b と 2d は高い。
- 学ぶ価値: 2c は言語処理系の教科書が扱う古典的な GC を自分の処理系で読める。2b は近年の研究の成果を関数型言語の処理系で読める。2d は実用の処理系の多くが採る形である。

### 暫定の推奨

2c を第一の候補とし、2a を代わりの候補として残す。

2c を推す理由は三つある。第一に、測定で費用の大きかった参照の数の増減（eval で約 20%）と `malloc`・`free`（list と tree で約 20%）を、値の写しと独自の確保器に置き換えられる。第二に、循環（M01）とタスクの表の項目の寿命（M02）を一つの機構で扱え、ADR 0239 が前提とする「循環は必ずセルを通る」という条件を将来の言語の変更のたびに確かめ直す必要がなくなる。第三に、回収を安全点に限れば、U3 の組み込みの関数の書き方は今と同じく単純に保てる。

2c を採る場合も、書き込みの障壁を差し込む位置（セルの書き込み、`Lazy` の結果の書き込み、タスクの結果の書き込み、継続の状態の変更）を API の上で一か所ずつに集めておき、後で増分の回収（2c の停止の時間を縮める）や若い世代（2d）を加えられるようにする。

2a を代わりに残す理由は、2c の欠点のうち、最大常駐メモリと停止の時間が、測ってみないと許せるかどうか分からないことである。

設計者の判断（2026-09-30、相談の第 1 回の後）: 第 1 段では 2c と 2a の両方を試作し、同じ値の配置・確保器・VM の上で入れ替えて比べ、測定の結果で一方を採る。2a の試作には、最後の使用での移動と、一意な対象のその場での再利用を含める。これらを含めずに比べると、2a の主な利点を測らないまま 2c を採ることになる（[相談の第 1 回](consult/01-memory-and-values.md)の問い 1・7）。

専門家に聞きたいこと:

- 回収を安全点に限った非移動のマーク・スイープは、関数型のスクリプト言語で、改良した参照カウント（2a）より速くなると見てよいか。見積もりの前提として何を測ればよいか。
- 回収を始める閾値（生きている量に対する倍率など）の、実績のある決め方。
- HTTP のサーバのように長く動くスクリプトで、止めて行う回収の停止は実用の範囲に収まるか。増分の回収を初回リリース版に入れるべきか。
- 2a を選ぶ場合、ADR 0239 のセルを起点にした回収と、Bacon と Rajan の試行の削除（trial deletion）の、どちらが本言語に合うか。

## Q3 ヒープの持ち方と `unsafe` の境界

縛る要求: R02、R04、R05、R06、F02。

問いは、ヒープの対象を Rust の上でどう持ち、`unsafe` をどこに閉じ込め、どう確かめるかである。

| 選択肢 | 概要 | 利点 | 欠点 |
|---|---|---|---|
| 3a `Rc` と `RefCell` | 標準ライブラリの参照カウント | `unsafe` が要らない | Q2 の 2a にしか使えない。対象の頭を自分で設計できず、確保器を差し替えられない |
| 3b 種類ごとの領域と番号 | 対象を種類ごとの `Vec` に置き、値は番号（と世代の番号）を持つ。回収は印のビットの並びと空きリストで行う | `unsafe` なしで追跡型の GC を書ける。古い番号の使用は世代の番号で見つけられる | 読み出しのたびに範囲の確かめと間接参照が一つ増える。大きさの違う対象（文字列、構成子の引数の並び）を置くと、領域の中からさらに `Box` を指す二重の間接になる |
| 3c 自前の確保器と生のポインタ | 大きな塊を確保し、その中に頭付きの対象を並べる。値は `NonNull` のポインタを持つ。`unsafe` はヒープのモジュールに閉じ込め、外には安全な API（対象の中身を借りる関数など）だけを出す | 対象の配置、頭、確保の速さを完全に制御できる。値を `Copy` にでき、間接参照が一段で済む | `unsafe` の不変条件（安全点の外で回収しない、根を漏らさない）が崩れると未定義動作になる |
| 3d GC のクレートを使う | `gc-arena` などを使う | 安全な API が手に入る | ADR 0240 の決定 1（自作）に反する。読む先行事例としてだけ使う |

3c で借用規則が守れる範囲を広げる工夫として、対象の中身を借りる関数を `&Heap` の借用に結び付け、回収する関数に `&mut Heap` を要求する形がある。こうすると、中身の借用を持ったまま回収を呼ぶ書き方は、Rust のコンパイラが拒む。ただし、`Copy` の値（ポインタ）そのものを回収の後まで持つ誤りは、型では防げない。これは Q8 の確かめ方で見つける。

`unsafe` の確かめ方の候補は次のとおりである。

| 手段 | 見つけられるもの | 限界 |
|---|---|---|
| Miri | ヒープのモジュールの単体テストと、小さな VM のプログラムの中の未定義動作（範囲外、解放後の使用、別名の規則の違反） | 実行が遅い。OS の呼び出しや FFI を含むもの（`mio`、スレッド）は動かないことがある【要検証】ので、IO 実行器を外して動かす |
| 回収の強制（stress） | 根の数え漏れ。安全点ごとに必ず回収する設定で、ゴールデンテストと差分テストを走らせる | 実行が遅くなる。完了の条件の検査では一部だけ走らせる |
| ヒープの検証器（デバッグのビルド） | 回収の前後で、すべての対象の頭と、対象が指すポインタが正しい対象を指すかを確かめる | デバッグのビルドだけ |
| 解放した領域を毒で埋める | 解放後の使用を、決まった値の読み出しとして早く表に出す | 見つけられるのは読み出したときだけ |
| AddressSanitizer | 解放後の使用と範囲外の読み書き | nightly の Rust の機能であり、macOS の arm64 での使い方は確かめていない【要検証】 |
| fuzzing | 型の付く無作為なプログラム（[ADR 0213](../../../design/decisions/0213-formal-verification-stage-1-in-first-release.md)）を、回収の強制の下で実行し、参照インタプリタと比べる | 生成器の出来に依存する |

lint は、`unsafe_code` を `forbid` から `deny` にし、ヒープのモジュール（と、Q9 で検証済みのバイトコードの読み出しを入れるなら VM の振り分けのループ）でだけ `#[allow(unsafe_code)]` を書く。各 `unsafe` のブロックには、守る不変条件を `// SAFETY:` のコメントで書かせ、clippy の該当する lint（`undocumented_unsafe_blocks` など【要検証：lint の名前と水準】）で強制する。

### ほかの部分への影響、難しさ、学ぶ価値

- 影響: 3c では、ヒープのモジュールの外は安全な API だけを使うので、組み込みの関数の書き方は 3a と変わらない。
- 難しさ: 3c のモジュールそのものは小さく（確保、頭、印付け、掃き出し、借用の関数）、LLM が書く量は多くない。難しいのは、不変条件を守る側（VM の安全点の扱い）であり、これはレビューと Q8 の確かめ方で補う。
- 学ぶ価値: `unsafe` の不変条件を文章で書き、それを道具で確かめる流れそのものが、Rust で処理系を書くときの題材になる。

### 暫定の推奨

3c。`unsafe` はヒープのモジュールに閉じ込め、Miri・回収の強制・ヒープの検証器・毒で埋めることを、最初の段から完了の条件の検査（`scripts/check.sh` と別のスクリプト）に入れる。

借用を `&Heap` に結び付けるだけでは足りない。回収の前に Rust の局所変数へ写した値を、回収の後に新しい `&Heap` で読む誤りを防げないからである（[相談の第 1 回](consult/01-memory-and-values.md)の問い 5）。設計者の判断（2026-09-30）により、回収しない区間を Rust の寿命で表す。区間ごとに新しい寿命を持つ `Value<'epoch>` と `NoGcCtx<'epoch>` を公開し、区間の中の処理には回収の機能を渡さない。安全点へ戻る前に、値は VM の保存領域（根）へ置き、区間の寿命を外した生の値は、保存領域と根の列挙を管理する小さな内部の実装に閉じ込める。ヒープの取り違え（別の実行のヒープの値を渡す）も、型の印か検査付きの参照で防ぐ。この境界は 2a の試作にも同じ形で使う。寿命の設計が行き詰まったら、番号と世代で指す 3b に切り替える。

確かめ方には、Miri などに加えて次のものを入れる（同じく問い 5）。

- 区間の外への値の持ち出し、別のヒープとの混用、作業用のスレッドへの値の持ち出しが、コンパイルの失敗になることを確かめるテスト
- デバッグのビルドで値に確保の世代を持たせ、参照を作る前に生存を確かめる仕組み（番地だけでは、同じ場所の再利用を見分けられない）
- 確保・参照の書き換え・根の追加と削除を無作為に組み合わせ、独立に計算した到達可能性と比べるテスト
- 塊の中の論理的な解放は、毒や Miri では見つけにくいので、検証用に対象ごとに確保と解放をする構成

専門家に聞きたいこと:

- 3c の安全な API の形として、借用を `&Heap` に結び付ける形は十分か。`gc-arena` のような生成的な寿命まで使う価値はあるか。
- LLM が書く VM で、安全点をまたいで値を持つ誤りを減らすための、コードの書き方の規則や静的な確かめ方。

## Q4 枠の積み重ねと継続

縛る要求: S05〜S09、S14、S15、R09。

問いは、タスクごとの枠の積み重ねを、一度だけ再開できる継続（[ADR 0160](../../../design/decisions/0160-one-shot-continuations-as-stack-segments.md)。【決定】）が区画の所有を移せる形で、どう持つかである。

| 選択肢 | 概要 | 利点 | 欠点 |
|---|---|---|---|
| 4a 区画ごとの `Vec`（設計書の方針） | 区画ごとに枠の `Vec` とレジスタの `Vec` を持ち、`handle` で新しい区画を積む。継続は区画の並びの所有を移す | 捕まえると再開の費用が、区画の数に比例し、中身の大きさによらない | 区画をまたぐ戻り（`handle` の本体からの戻り）で、今の区画を切り替える処理が要る |
| 4b タスクに一本の積み重ねと、区画の境目の位置 | 積み重ねは一本の `Vec` とし、区画は境目の位置で表す。捕まえるときは境目より上を写して切り詰め、再開で写し戻す | 呼び出しと戻りの処理が最も単純 | 捕まえると再開の費用が、捕まえた深さに比例する。ハンドラの中で深い再帰をすると、操作のたびに写す |
| 4c ヒープに置く枠の連結 | 枠を GC の対象にし、呼び出し元への参照で連ねる | 捕まえるのが O(1) | 呼び出しのたびに確保し、fib のような呼び出しの多いプログラムで遅くなる |
| 4d Rust のスタックを使うコルーチン | スタックを切り替える仕組みで、Rust の関数の呼び出しとして言語の関数を呼ぶ | 振り分けのループが単純 | [ADR 0016](../../../design/decisions/0016-calls-off-go-stack.md) に反する。スタックの大きさの上限と WASM への移植（F02）で問題が出る |

枠の持ち方について、次の二つを合わせて検討する。

- **呼び出しの枠と包む枠を分ける**: 呼び出しの枠（原型、命令の位置、窓の先頭、結果のレジスタ）は小さく保ち、解放・`update`・セルの更新・`handle`・`drop` の枠は、別の `Vec` に、属する呼び出しの枠の深さとともに積む。`RETURN` は「この深さに包む枠があるか」を位置の比較一回で調べられるので、包む枠のない普通の呼び出しは速いままになる。
- **窓を重ねる**: 今の `CALL` は、呼び出し元の引数のレジスタを新しい窓の先頭に写す。Lua のように、呼び出し元が関数と引数を窓の末尾に並べ、呼ばれた側の窓をその位置から始めれば、写す処理がなくなる【要検証：Lua 5.4 の `luaD_precall` の窓の置き方】。[仮想機械](../../../design/02-impl/02-08-vm.md)の「実行の手順」の「引数を写す」は【方針】であり、改めるには ADR が要る。

末尾で再開する節について、[ADR 0151](../../../design/decisions/0151-inherited-handlers-tail-resume-only.md) は、引き継いだハンドラの節を継続を捕まえずに実行する。同じ扱いを、`handle` を評価したタスク自身が呼んだ操作の末尾で再開する節にも使えば、handler のベンチマークの末尾で再開する形で、区画の切り離しと戻しを省ける。末尾で再開する節の中には `return` と `try` がなく、`resume(v)` の後は節の値を使わないので、観測できる振る舞いは変わらないと見ている。ただし、節の中で呼んだ操作をそのハンドラより外側で処理する仕組み（[仮想機械](../../../design/02-impl/02-08-vm.md)の「ハンドラと継続」の、節の呼び出しの枠に外側の連鎖を記録する方法）が、自分のタスクの場合にも正しく働くかは確かめる必要がある。

### 先行事例

- **OCaml 5**: エフェクトのハンドラを fiber（ヒープに確保した伸びるスタック）で実装し、`perform` は fiber の連なりを切り離して継続にする。継続は一度だけ再開でき、二度目は例外になる（Sivaramakrishnan ほか, "Retrofitting Effect Handlers onto OCaml", PLDI 2021）。fiber のスタックの伸ばし方の細部は【要検証】。本言語の 4a は、この形に近い。
- **Chez Scheme**: 区画に分けたスタックで第一級の継続を表す（Hieb, Dybvig, Bruggeman, "Representing Control in the Presence of First-Class Continuations", PLDI 1990）。
- **Lua 5.4**: 一つの Lua のスレッド（コルーチン）が一本のスタックを持ち、呼び出しの情報（`CallInfo`）を別の連なりで持つ【要検証】。
- **CPython 3.11 以降**: 枠を、専用の領域に連続して置く形に改めた【要検証】。

### ほかの部分への影響、難しさ、学ぶ価値

- 影響: 窓を重ねる形にすると、コード生成のレジスタの割り当て（呼び出しの引数を窓の末尾に置く）が変わる。U1 と調整する。包む枠を分ける形は VM の中で閉じる。
- 難しさ: 4a は中程度。区画をまたぐ戻り、E-DropRel の辿り、止める手順の辿りが同じ枠の並びを読むので、枠の辿り方を一つの反復子にまとめると誤りが減る。
- 学ぶ価値: 一度だけ再開できる継続が、写さずに所有を移すだけで実装できることは、エフェクトのハンドラの実装を学ぶ中心の題材である。

### 暫定の推奨

4a に、呼び出しの枠と包む枠を分けることを加える。[相談の第 2 回](consult/02-frames-and-dispatch.md)を受けて、次の条件を付ける。

- 包む枠に付ける深さは「その枠を積んだ時点で、その下にある呼び出しの枠の数」とし、同じ深さの枠は積んだ順を保つ。深さとレジスタの位置は区画の中の相対値とする。`RETURN` は、自分の解放の枠、自分の呼び出しの枠、自分を包む枠の順に処理する。
- 上から順に辿る処理は一つの反復子にまとめるが、正常な戻り・E-DropRel・取り消し・止める手順で子タスクの扱いが違うので、処理の規則は経路ごとに書く。辿る位置と処理の状態は、待ちと回収をまたいで保存できる形にする。
- 区画の記憶域の再利用は、後始末を終えた空の容量だけを、上限付きで保管する形で測ってから決める。

窓を重ねる形は、第 1 段で独立した窓と比べる。引数の準備を含む総移動量、レジスタの領域の最大量、長い末尾再帰で測り、呼び出しの部分だけの短縮では決めない。

末尾で再開する節の直接の実行を自分のタスクにも広げることは、第 1 段の範囲に入れない。「末尾が `resume` で `return` と `try` がない」だけでは、節の中の `with` の解放の時期、止める手順と取り消しでの継続の辿り、節の中の操作の探し方が、捕まえる方式と一致しないからである。handler のベンチマークで効果が大きいと分かったら、条件を定めて改めて検討する。

専門家に聞きたいこと:

- 区画ごとの `Vec` を、継続を捨てるときに使い回す（区画の記憶域の再利用）価値はあるか。
- 包む枠を別の `Vec` に分ける形で、止める手順と E-DropRel の「上から順に辿る」順序を保つ方法として、見落としている場合はあるか。

## Q5 スケジューラと IO 実行器

縛る要求: S09〜S11、S13、S14、S16〜S19、C01〜C04、E03、E04、OPEN-062 の R02〜R05・R13。

問いは、スケジューラ、`mio` のイベントループ、作業用のスレッド、出力のバッファ、リソースの表を、どういう部品に分け、二つの IO の方式をどう扱うかである。

### 二つの IO の方式

| 選択肢 | 概要 | 利点 | 欠点 |
|---|---|---|---|
| 5a 今の形を保つ | 直接呼び出しは VM がハンドラ表を呼び、要求と応答は VM が要求を返して止まる。R02 は、切り替えの位置で出した要求があれば VM から戻る規則を加えて直す | 変更が小さい | IO の経路が二本あり、組み込みの操作を加えるたびに二本で同じ振る舞いを保つ必要がある。R02 のような食い違いが、ほかの箇所でも起きうる |
| 5b 要求の置き場を一つにする | 組み込みの操作の呼び出しは、どちらの方式でも「要求」をスケジューラの送り出しの列に置き、タスクを待たせる。送り出しの列を処理する部品を二つ用意する。直接呼び出しの部品は、置かれた要求をその場でハンドラ表に渡し、完了ならすぐにタスクに戻す。要求と応答の部品は、切り替えの位置で列が空でなければ VM から戻り、外側の実行器に渡す | 二つの方式が同じ待ちと完了の経路を通るので、方式による振る舞いの違いが起きる箇所が送り出しの部品に限られる。R02 は構造上起きない | 直接呼び出しで、すぐ完了する操作（出力のバッファへの書き込みなど）にも列を通る費用がかかる。すぐ完了する操作を列に置かずに済ませる近道を設けると、その近道が 5a と同じ二本の経路になる |
| 5c 要求と応答の方式をやめる | 直接呼び出しだけにする | IO の経路が一本になる | [ADR 0088](../../../design/decisions/0088-keep-both-io-execution-modes.md) の決定 1 を改める ADR が要る。Freer モナドの形を学ぶ場が処理系から消える |

### 出力の転送（R04・R13）

設計者が R04 と R13 で選んだ案に沿うと、出力は次の形になる。書き込みは今と同じく VM のスレッドでバッファに加える（一回の書き込みの不可分性 S11 は保たれる）。バッファの中身の出力先への転送は、出力ごとの書き出し用のスレッドで行う。転送していない量が上限を超えたら、書き込んだタスクを「待つ」にする。転送する時点は、64 KiB に達したとき、標準入力を読む前、進められるタスクがなくなったとき、端末への出力で改行を書いたとき、`Process.runAttached` の前、止める手順と終わる前とする。書き出しの失敗は書き出し用のスレッドが記録し、VM のスレッドは次の書き込みか転送のときに読む（[ADR 0045](../../../design/decisions/0045-late-detection-of-output-write-failure.md) の後での検出に収まる）。

### 完了とリソースの返却（R05）

作業用のスレッドから VM のスレッドへ送る完了の型を、「タスクへの結果」と「返すリソース」の二つの欄に分ける。貸したリソースの OS の資源（`File` など）は、作業の中へ所有を移して渡し、完了の中で所有を戻す。Rust の所有の規則は、返すリソースを表へ戻すことを保証しない（値はスコープを抜けるだけで破棄される。相談の第 1 回の指摘）。そこで、返却の欄の処理は個々の組み込みの関数に任せず、完了を受け取る共通の実行機構で必ず行う。VM のスレッドは、タスクが取り消されていて結果を捨てるときも、返却の欄は必ず処理する。

### `handle` とタスクの対応（R03）

タスクの記録に、そのタスクが属する `handle` の番号を持たせる。`handle` の枠は番号と、属する終わっていないタスクの数を持つ。タスクを起動するとき、起動したタスクの積み重ねに `handle` の枠があれば最も上のものに、なければ起動したタスク自身が属する `handle` に属させる。

### タスクの表の項目の寿命（M02）

Q2 で 2c を選べば、`Task` の値をタスクの対象へのポインタにし、終わっていないタスクだけをスケジューラが根として持つ。終わったタスクの結果はタスクの対象に残り、`Task` の値から辿れなくなったら回収される。2a を選べば、`Task` の値を参照の数で数える対象への参照にする。どちらでも、タスクの表の番号を値に持つ今の設計（[仮想機械](../../../design/02-impl/02-08-vm.md)の「値の表現」の `Task` の行）は改める。

### 先行事例

- **Tokio**: 作業を盗むスケジューラと、`mio` の上のイベントループ、ブロックする処理のためのスレッドの集まり（`spawn_blocking`）を持つ【要検証：今の版の構成】。本言語は単一のスレッドのスケジューラなので、Tokio の current-thread の実行器に近い。
- **Node.js（libuv）**: 単一のスレッドのイベントループと、ファイルの操作などのためのスレッドの集まりを持つ【要検証：既定のスレッドの数】。
- **Go のランタイム**: 関数の呼び出しの入り口で、スタックの伸長の確かめに先取りの要求を相乗りさせる【要検証：非同期の先取りを加えた版】。本言語の「呼び出しの回数の予算」は、この相乗りの考え方で安くできる（Q9）。

### ほかの部分への影響、難しさ、学ぶ価値

- 影響: 5b は、組み込みの関数の応答（Q7）の「待つ」と、テスト用のハンドラ表の作りを変える。出力の転送は、テストの実行器の出力先（メモリに捕らえる）にも同じ形で使えるようにする（E03）。
- 難しさ: スケジューラそのものより、止める手順・取り消し・待ちの表・リソースの貸し出しの組み合わせが難しい。状態の遷移（進められる、待つ、止める途中、終わった）と、リソースの状態（開いている、貸している、解放した）を表にして、遷移ごとにテストを置く。
- 学ぶ価値: 5b は、自由モナドの「操作と続き」を、スケジューラの送り出しの列という具体的な形で読める。二つの方式の違いが、列を誰がいつ処理するかの違いに還元される。

### 暫定の推奨

5b。出力の転送、完了の二つの欄、`handle` の番号の記録、`Task` の値の表現は、上に書いた形で進める。すぐ完了する操作の近道は設けずに第 1 段で測り、列を通る費用が println で大きければ、近道を「送り出しの部品の中の分岐」として一か所に置く。近道も、同じ待ちの登録・ハンドラの呼び出し・完了の処理を通す。要求と応答の方式では近道を設けない。

[相談の第 3 回](consult/03-scheduler-and-io.md)を受けて、次の規則を加える。

- 列に置くのは、言語のハンドラで処理されなかった組み込みのエフェクトの操作に限る。純粋な組み込みの関数と `Reference` の操作は待たせない（S11 の不可分性を保つ）。
- タスクを待ちにしてから要求を公開する。進められるタスクが残っていても、切り替えの位置で要求を送り出し、完了を取り込む。IO 実行器は外部の操作の終わりを待って VM を止めない。R02 を防ぐのは、列の形ではなくこれらの規則である。
- 要求と、保存した継続（待っているタスクの枠）との対応を、要求の番号で明示する。
- 出力は、標準出力と標準エラー出力ごとに一つの書き出し用のスレッドを置く。転送の時点は「依頼するだけ」（64 KiB、進めるタスクがなくなったとき、端末への改行）と「それまでの出力の完了を待つ」（標準入力を読む前、`Process.runAttached` の前、止める手順と終わる前）に分ける。完了を待つ間も VM のイベントの処理と中断の確かめを続ける。上限はバッファ・書き出しの列・転送中の量の合計で数え、書き込みを加える前に待たせる。受け付けた出力は、書いたタスクを取り消しても取り下げない。
- タスクの寿命と外部の操作の寿命を分ける。タスクの状態は `Ready`・`Waiting(理由)`・`Unwinding(原因, 辿る位置, 待ち)`・`Done`、リソースの状態は `Open`・`Lent(操作の番号, 閉じる要求)`・`Releasing(操作の番号)`・`Released` とし、組み合わせごとの遷移を表にしてテストを置く。外部の操作は番号で記録し、タスクへの結果の配送を取り消しても記録は消さない。完了の共通の処理は、先に返却の欄を処理し、その後でタスクがまだ結果を待っているかを調べる。
- `handle` は、本体が終わり、属する終わっていないタスクが 0 になるまで記録を残す。子のタスクが起動した孫も同じ `handle` に登録する。全体を止める手順では、`handle` も子孫の終わりを個別に待たない。
- 行き詰まりの判定（ADR 0238）には、リソースの返却・解放・出力の完了の待ちも含める。止める手順の途中では、行き詰まりの誤りで元の停止の理由を置き換えない。
- 作業用のスレッドが panic しても返却の欄を作れるよう、貸したリソースを `catch_unwind` の外で持つ。

設計書 02-09 の出力の規則（「書き込みは待たない」「VM で転送する」）と、取り消しで「結果を捨てる」の記述は、作り直しの設計を ADR にするときに、上の形に揃える。

専門家に聞きたいこと:

- 5b の送り出しの列の形は、要求と応答の方式を Freer モナドとして読むという ADR 0029 の意図を保っているか。
- 出力の書き出し用のスレッドを出力ごとに一つ置く形と、作業用のスレッドの集まりに転送の作業として出す形の、どちらがよいか。
- 取り消しと止める手順の途中で、作業用のスレッドに貸したリソースを待つ状態が行き詰まり（ADR 0238）の判定と食い違わないか。

## Q6 `Lazy` と `Reference` の表し方

縛る要求: S07、S11、S12、S15、M01。

| 対象 | 選択肢 | 概要 |
|---|---|---|
| `Reference` | 6a | ヒープの対象に中身の値と版の番号（64 ビット）を置き、その場で書き換える |
| | 6b | 中身の値を別の不変の対象にし、セルはそれへの参照だけを持つ |
| `Lazy` | 6c | 対象に三つの状態（評価の前：本体の関数、評価の途中：本体の関数と評価しているタスクと待つタスクの並び、評価の後：値）を持つ |
| | 6d | 対象は状態と値だけを持ち、評価しているタスクと待つタスクの並びは、スケジューラの側の表に対象をキーとして置く |

`Reference` は 6a でよい。一つの実行は一つのスレッドで進み、`Reference` の操作は `PRIM` の中で切り替えずに行う（S11）ので、書き換えに排他は要らない。Q2 で 2c を選べば、セルの書き込みは書き込みの障壁を差し込む位置の一つになる（今は何もしない関数にしておく）。2a を選べば、ADR 0239 のとおり生きているセルの表に加える。

`Lazy` は 6c を推す。評価の途中の状態で本体の関数を捨てずに持つのは、取り消しと止める手順で「評価の前」に戻すため（S12）である。評価の後に移ったら本体の関数を捨て、捕捉した値を回収できるようにする。待つタスクの並びはタスクの番号であり、タスクは表から生きているので、GC の辿りの対象にしない。6d は対象を小さくできるが、評価の途中の `Lazy` は同時に少ないので、得るものは小さい。

取り消し・止める手順・E-DropRel の三つで `update` の枠を降ろすときに「評価の前」に戻す処理と、セルの更新の枠を捨てる処理は、枠の種類ごとの「降ろすときの処理」として一つの関数にまとめる。三つの経路で別々に書くと、どれかで戻し忘れる誤りが起きやすいからである。この関数は降ろす原因を受け取り、全体を止める手順の途中では、`Lazy` を待っているタスクを通常の実行に戻さない（戻すと、止めている途中に本体を評価し直せてしまう。[相談の第 3 回](consult/03-scheduler-and-io.md)の問い 4）。捕まえた継続の中の `update` の枠にも同じ処理を使う。

待つタスクの並びは、所有しないタスクの番号とし、GC では辿らない（終わっていないタスクはタスクの表が根として持つ）。番号を使い回すなら世代で確かめる。行き詰まりの判定では、`Lazy` の待ちを内部の待ちとして数え、外部の完了の待ちには数えない。

専門家に聞きたいこと: `Lazy` の評価の途中で評価しているタスクが別のタスクの結果を待ち、そのタスクが同じ `Lazy` を求める場合は、行き詰まり（ADR 0238）として見つかる。この判定に、`Lazy` の待ちを待つタスクとして数える以外の注意は要るか。

## Q7 組み込みの関数の受け渡し

縛る要求: S03、R01、R05、R08、R10、OPEN-062 の R14。U3 の標準ライブラリはこの形で書かれる。

今の形は `fn(&mut Heap, &[Value]) -> Result<Value, Stop>` である。初回リリース版では、応答に「待つ」「タスクの起動」「終了」が加わる（[仮想機械](../../../design/02-impl/02-08-vm.md)の「組み込みの関数の呼び出し」）。

| 選択肢 | 概要 | 利点 | 欠点 |
|---|---|---|---|
| 7a 文脈と応答の型 | `fn(&mut Ctx, Args<'_>) -> Result<Reply, Stop>`。`Ctx` は値を作る関数（大きさの上限の確かめを含む）、リソースの表、出力のバッファ、時計、乱数を持つ。`Args` は型ごとの読み出し（`args.int(0)?` など。型が違えば `Stop::Internal`）。`Reply` は完了・待つ・タスクの起動・終了 | 形が一つで、LLM が真似しやすい。値を作る経路が `Ctx` に限られる（R05） | 引数を読み出す定型の記述が関数ごとに要る |
| 7b 7a に宣言的な包みを加える | 引数と結果を Rust の型で書いた関数（`fn repeat(s: &str, n: i64) -> Result<String, Stop>` など）から、7a の形の関数を `macro_rules!` で作る | U3 の数百の関数の定型の記述と誤りが減る。上限の確かめを包みの側で一律に行える | 包みのマクロが読みにくくなると、設計者が読んで学ぶ妨げになる |
| 7c 小さな基本の関数と言語のソース | 組み込みの関数を小さく保ち、多くを標準ライブラリのソースで書く | Rust の面が減る | 遅い。U3 の設計の範囲を広く変える |

応答の「待つ」は、作業用のスレッドで行う作業（`Send` な Rust の閉包）と、完了を VM のスレッドで言語の値に変える関数の組で表す。後者は言語の値を捕えない。待っている間に要る言語の値（引数など）は、IO の命令の枠のレジスタに残っているので、閉包に捕える必要がない。この規則は、Q2 で 2c を選んだときの根の数え上げを単純に保つ（安全点をまたいで Rust の閉包の中に値が残らない）ためのものであり、2a でも害はない。

外部のバイト列を `String` にする変換（S03、R14 の UTF-8 でないヘッダなど）は、`Ctx` の一つの関数に集め、検査を通らない経路で文字列の値を作れないようにする。

### 先行事例

- **Lua の C API**: 組み込みの関数は仮想のスタックを通して引数を読み、結果を積む【要検証：5.5 での変更】。
- **CPython の Argument Clinic**: 組み込みの関数の引数の宣言から、引数を読み出す定型のコードを生成する【要検証】。7b の考え方に近い。

### 暫定の推奨

7a の形は内部の共通の形式にとどめ、組み込みの関数の実装者には最初から型付きの形を見せる（設計者の判断、2026-09-30。[相談の第 1 回](consult/01-memory-and-values.md)の問い 6）。

- 実装者は、名前と型の付いた引数を受ける関数だけを書く。引数の読み出しと登録の表は、宣言から作る。
- 純粋な関数には、時計・乱数・リソースに触れず、`Wait`・`SpawnTasks`・`Exit` を返せない文脈を渡す。権限の誤りをコンパイルの失敗にする。
- 大きさの検査は確保の前に行う。検査済みの長さを受け取る確保の関数か、上限付きの構築器を使わせる。UTF-8 の検査は値を作る API に集める。
- 作業用のスレッドの仕事と結果は `Send + 'static` とし、完了の処理は環境を捕えない `fn` ポインタにする。完了の保存、起動する関数の登録、取り消しとの競合、リソースの返却は共通の部分が行う。
- U2 の第 1 段で、代表的な関数（純粋な関数、文字列の構築、待つ処理）に小さな包みを作り、誤った引数の型・結果の型・権限・捕捉がコンパイルで止まることを確かめる。

設計者は、この形で書いた関数を、まず非公式のライブラリとして扱い、標準ライブラリには実装を吟味したものから少しずつ加える方向を示した（2026-09-30）。標準ライブラリの範囲と、非公式のライブラリの位置付けは、U3 の実装プランを作るときに設計者と決める。

専門家に聞きたいこと: 回収を安全点に限る前提で、組み込みの関数が値を `Ctx` の外（キャッシュなど）に持ち越す誤りを型で防ぐ方法はあるか。

## Q8 テストの仕方

縛る要求: C03、S19、S20、R06、OPEN-062 のすべて。

| 題材 | 推す形 |
|---|---|
| スケジューラ | 切り替える順序を決める部品を trait にし、テストでは順序を与える実装に替える（[ADR 0161](../../../design/decisions/0161-single-threaded-task-scheduler.md)）。時計とタイマーも仮想の時間に替え、`Clock.sleep` のテストが実際には眠らないようにする。作業用のスレッドも、テストではその場で実行する実装に替えられるようにする |
| 差分テスト | 参照インタプリタは、VM と値の実装を共有しない、`Rc` による安全で単純な値の型に移す。比べるのは観測できる結果（出力、終わり方、`main` の値を共通の形に変えたもの）とする。VM の値の実装の不具合が両方に同じく現れて見逃すことを避けるためである（[01-current-state.md](01-current-state.md) の「参照インタプリタとの結び付き」） |
| IO の二つの方式 | ゴールデンテストを両方の方式で走らせる（今と同じ。[ADR 0088](../../../design/decisions/0088-keep-both-io-execution-modes.md)） |
| `unsafe` | Q3 の表の手段（Miri、回収の強制、ヒープの検証器、毒、fuzzing）を完了の条件の検査に入れる |
| OPEN-062 | 項目ごとに再現テストを、スケジューラの単体テストか `concurrency` のゴールデンテストとして書く |

先行事例として、Rust の並行のテストの道具 `loom`（スレッドの交互の実行を網羅する）と `shuttle`（無作為に探す）【要検証】、SpiderMonkey の `gczeal`（回収を頻繁に起こすデバッグの設定）【要検証】がある。本言語のスケジューラは単一のスレッドなので、`loom` のような道具は要らず、順序を与えるスケジューラで足りる。

専門家に聞きたいこと: 回収の強制と差分テストの組み合わせで、根の数え漏れのうち見つけにくいもの（まれにしか通らない経路の値）を拾う方法。

## Q9 振り分けのループと呼び出しの手順

縛る要求: S05、S09、S17、R01、P03。

[01-current-state.md](01-current-state.md) の「測定から読み取れること」のとおり、fib と loop の差は、値の表現より振り分けのループと呼び出しの手順から来ていると見られる。

| 選択肢 | 概要 | 利点 | 欠点 |
|---|---|---|---|
| 9a 今の形 | 命令ごとに原型と枠を引き直し、レジスタの読み書きごとに範囲を確かめて `Result` を返す | `unsafe` が要らず、どの誤りも `Stop::Internal` になる | 命令ごとの定まった費用が大きい |
| 9b 局所に持つ | 実行中の原型の命令の並び、命令の位置、窓の先頭を、ループの局所変数に持ち、呼び出し・戻り・切り替えのときだけ書き戻して読み直す | `unsafe` なしでも命令ごとの費用が減る | 書き戻し忘れの誤りが起きうる |
| 9c 読み込みのときの検証と範囲の確かめの省略 | コンパイル済みプログラムを実行する前に、検証器が、すべての命令のレジスタ番号が原型のレジスタの数より小さいこと、跳ぶ先と定数と原型の番号が範囲にあることなどを確かめる。実行中はその事実に頼って範囲の確かめを省く | 命令ごとの分岐が減る。WASM の検証と同じ考え方で、`unsafe` の根拠を検証器に置ける | `unsafe` が振り分けのループに入る。検証器の漏れが未定義動作になる |
| 9d 振り分けの方式を変える | 末尾呼び出しによる threaded code（Rust の `become`。安定版にない【要検証：2026 年の時点の状態】）、上位命令（superinstruction）、命令の特殊化 | さらに速くなりうる | nightly に依存するか、コード生成の変更が大きい |

切り替えの位置の処理（中断の印、取り消しの要求、予算）は、呼び出しのたびに三つを調べる代わりに、予算の計数を一つ減らして 0 かを見るだけにし、0 になったときの遅い経路で三つを調べる形にできる。取り消しの要求は、対象のタスクの予算を 0 にすることで、次の切り替えの位置で必ず遅い経路に入る。回収の要求（確保した量が閾値を超えたとき）も同じ方法で安全点に届けられる。中断の印はシグナルの登録の仕組みが書く原子的な真偽値なので、予算を 0 にすることはできない。中断の印の読み出しは呼び出しのたびに行うか、予算を使い切ったときだけ行うかを選ぶ必要があり、後者は [ADR 0163](../../../design/decisions/0163-interrupt-releases-resources.md) の「切り替えの位置で調べる」を改めることになる。緩い順序付けの原子的な読み出しは安いので、前者のままでよいと見ている。

R01 との関係では、9c で省いた確かめは、検証器が同じ条件を `InternalError` として報告する形に移る。「型検査を通ったプログラムでは起きない状態は `Stop::Internal` で返す」という規約は、「検証器が拒む」に読み替えることになり、AGENTS.md の実装の規約に書き加える必要がある。

### 先行事例

- **Lua 5.4**: 振り分けのループ（`luaV_execute`）は、命令の位置とベースのポインタを局所変数に持ち、呼び出しの後で読み直す【要検証】。
- **CPython 3.11 以降**: 実行中に命令を型に合わせて特殊化する（specializing adaptive interpreter。PEP 659）。
- **WebAssembly の処理系**: 読み込みのときにモジュールを検証し、実行中の確かめを省く。

### 暫定の推奨

9b を第 1 段で入れる。9c は、9b を入れた後に同じ命令列で 9b だけの場合と比べ、効果を確かめてから入れる（[相談の第 2 回](consult/02-frames-and-dispatch.md)の見立ては「改善なし〜中程度」）。入れる場合は、省く確かめごとに検証器が保証することを表にし、効果の大きい添字の読み書きから限って省く。検証器は、変異させた入力のテストに加え、受理した入力を安全な実行器で動かして、省く予定の確かめが失敗しないことを確かめる。9d は後に回す。

9b の局所の状態を書き戻す位置は、呼び出し・戻り・切り替えに加えて、回収・待ち・継続の移動・止める手順とする。`NoGcCtx` は `Vec` の伸長による位置の変化を防がないので、ループの局所に生のポインタを持つ場合は、伸長の後に読み直す。

予算の計数への相乗りは、取り消しと回収の要求を知らせる手段としてだけ使い、要求そのものは別に持つ。末尾呼び出しとハンドラの節の暗黙の呼び出しも同じ確かめを通し、待っているタスクの取り消しは起こす処理も行い、回収の要求は実行全体で持ち、回収のためだけに遅い経路に入ったときは予算を初期化しない。中断の印は呼び出しのたびに `Relaxed` で読む。

専門家に聞きたいこと: Rust の安定版で、`match` による振り分けから得られる速さの上限の見込み。9c の範囲の確かめの省略が、9b の後にどれほど速さを上げると見るか。

## Q10 作り直しの進め方

縛る要求: すべて。

| 選択肢 | 概要 | 利点 | 欠点 |
|---|---|---|---|
| 10a 一度に作り直す | 値、ヒープ、VM、スケジューラ、IO 実行器を一度に作り直す | 途中の形を作らずに済む | 選んだ方式が性能で期待を下回ったと分かるのが最後になる |
| 10b 段に分ける | 第 1 段で、値の表現・ヒープ・VM の核（Q1〜Q3、Q9）だけを作り直し、最小実行版のテストをすべて通して測る。第 2 段以降で、区画とハンドラ、タスクとスケジューラ、IO 実行器と出力の転送、リソース、`Lazy` と `Reference` を順に加える | 第 1 段の測定で、Q2 の 2c と 2a の選択を確かめてから、その上に積める | 段の境目で一時的な形（タスクのない VM など）を作る |

### 暫定の推奨

10b。第 1 段では、Q2 の 2c と 2a を、同じ値の配置・確保器・VM の上で入れ替えられる形で両方試作する（設計者の判断。Q2 の「暫定の推奨」）。第 1 段の終わりに、fib・loop・list・tree・eval・string の測定と、回収の強制の下でのゴールデンテストを行い、その結果で Q2 の方式を選び、Q9 の推奨を確かめる。Q9 の改善は、メモリの管理の比較と混ざらないよう、別に測る。参照インタプリタの値の分離（Q8）も第 1 段で行う。第 1 段の完了の条件は、最小実行版のすべてのテストが通ることと、測定の記録を `tools/bench/results/` に残すこととする。

## 推奨のまとめ

| 問い | 暫定の推奨 |
|---|---|
| Q1 値の表現 | 16 バイトの列挙型（1b）。整数・浮動小数点数などは即値、ほかは細いポインタ。`Send` にしない |
| Q2 メモリの管理 | 第 1 段で、回収を安全点に限った非移動のマーク・スイープ（2c）と改良した参照カウント（2a）の両方を試作して比べ、測定で決める（設計者の判断）。障壁を差し込む位置を先に集めておく |
| Q3 ヒープと `unsafe` | 自前の確保器と生のポインタ（3c）。`unsafe` はヒープのモジュールに閉じ込め、Miri・回収の強制・検証器・毒を完了の条件の検査に入れる |
| Q4 枠と継続 | 区画ごとの `Vec`（4a）に、呼び出しの枠と包む枠の分離を加える。窓を重ねる形と、末尾で再開する節の直接の実行は測って決める |
| Q5 スケジューラと IO | 要求の置き場を一つにする（5b）。出力の転送を書き出し用のスレッドに分け、完了を結果と返却の二つの欄にし、タスクに属する `handle` を記録する |
| Q6 `Lazy` と `Reference` | セルはその場で書き換える（6a）。`Lazy` は三つの状態を対象に持つ（6c）。降ろすときの処理を枠の種類ごとに一か所にまとめる |
| Q7 組み込みの関数 | 文脈と応答の型（7a）を内部の形式とし、実装者には型付きの引数と権限ごとの文脈の形を最初から見せる（設計者の判断）。書いた関数はまず非公式のライブラリとし、吟味して標準ライブラリに加える（U3 で決める） |
| Q8 テスト | 順序を与えるスケジューラと仮想の時間。参照インタプリタの値を VM と分ける |
| Q9 振り分けのループ | 局所に持つ（9b）と、検証器による範囲の確かめの省略（9c）。予算の計数への相乗り |
| Q10 進め方 | 段に分ける（10b）。第 1 段の測定で Q2 と Q9 を確かめる |
