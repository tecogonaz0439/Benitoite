# C11 ゴールデンテスト: フロントエンド

- 依存する作業: [C10](C10-golden-runner.md), [F18](F18-pipeline-cli.md), [R34](R34-type-class-instructions.md), [R35](R35-decimal-and-byte.md), [R37](R37-map-and-set.md)（R34・R35・R37 に依存する理由は「手順の要点」の「`run` のテストが要る VM の作業」）

## 目的

初回リリース版で加わるフロントエンドの規則（構文、モジュール、レコード、型クラス、エフェクトの型付け、診断）を、CLI のゴールデンテスト（[処理系のテスト戦略](../../design/07-quality/07-03-compiler-testing.md)の「テストの設計の原則」の持ち主の境界の 2）で確かめる。各段の単体テストは F01〜F18 が書いた。本作業は、CLI から見える契約（利用者と LLM が読む診断、終了状態、実行の結果）を、スクリプトの形で固定する。

## 手順の要点

### 何をテストにするか

- 上の「読む設計書の節」の各節について、規則ごとに、規則を満たすスクリプト（`check` で誤りなし、または `run` で期待する出力）と、規則に反するスクリプト（期待する診断）を置く。一つのテストが複数の規則を確かめてよい。スクリプトの先頭に `// spec: <章の番号> <節の見出し>` の行を書く（07-03「ゴールデンテスト」）。
- 各段の単体テストが同じ契約を確かめている場合、ゴールデンテストを足すのは、CLI から見える形（診断の文言、修正案、位置、終了状態）に固有の危険があるときに限る（07-03「テストの設計の原則」の持ち主の境界）。どの単体テストと重なるかを、スキル `test-audit` の作成時の関門で確かめる。
- 診断は JSON の形式（`.diag.json`）で比べる。文章の形式の体裁は、少数のテストの `.text.stderr` で確かめる（各区分に一件程度）。
- 修正案（`help:`）を持つ診断コードは、コードごとに少なくとも一つのテストで修正案の内容を確かめる（ADR 0035）。とくに、他の言語の書き方（最小実行版の書き方を含む。`let`・`fn`・`{ }`・`:` の戻り値の型・`switch`・`=>` など）への診断は、01-02 が挙げた形ごとに一つ置く。
- 派生した診断が出ないことのテスト（07-03 の同名の節）を、初回リリース版で加わる規則（型クラスの制約の誤り、エフェクトの誤り、モジュールの誤り）について置く。
- 警告のテスト（07-03「警告のテスト（初回リリース版）」）は、同じスクリプトについて、`.options` のないテストと、`.options` に `--deny-warnings` を書いたテストを並べる。件数の行が誤りと警告を分けて数えることを `.text.stderr` で確かめる。
- 複数のモジュールからなるテスト（`<名前>/main.bnt`）で、import、公開、循環する import、見つからないモジュール、ディレクトリを指定した実行（`main.bnt` のないディレクトリを含む）を確かめる。シェバンの行を持つスクリプトも置く。

### `run` のテストが要る VM の作業

レコード・型クラス・`Decimal`・`Byte`・`Map` と `Set` の定数を使う `run` のテストは、コード生成（F15）に加えて、VM がその命令を実行できることを要する。型クラスの命令は R34、`Decimal`・`Byte` の命令と定数は R35、`Map`・`Set` の定数は R37 が VM に加える。これらの `run` のテストを置くために、R34・R35・R37 に依存する。ハンドラ・タスク・`Lazy`・`Reference` の実行は C12 が確かめるので、本作業の `run` のテストで使わない（型付けの規則は `check` のテストで確かめる）。

### 見つけた不具合の扱い

期待する結果を設計書から決め、実際の結果と比べる。実際の結果が設計書と食い違うときは、期待値を実際の結果に合わせない（書き直しの指定 `BENITOITE_BLESS` で作った期待値は、設計書と照らしてから残す）。食い違ったテストは `testdata/` に置かず、スクリプトと、設計書から決めた期待値と、実際の結果と、設計書の節を、完了の報告に添える（`scripts/check.sh` を通すために期待値を曲げない）。報告を受けたオーケストレータが、直す作業を起こすか、設計書を改めるかを決める。直す作業は、そのテストを退行テストとして加える（07-03「テストの設計の原則」の退行テスト）。

## 受け入れテスト

| 場合 | 期待 |
|---|---|
| 節の網羅 | 上の「読む設計書の節」の、見出しに「（初回リリース版）」を付けたフロントエンドの節のそれぞれに、`// spec:` の行で指すテストが一つ以上ある（`python3 tools/spec-coverage/spec_coverage.py` の出力で確かめ、該当する節の一覧を完了の報告に書く。道具が初回リリース版の節を数えるのは C17 の後なので、それまでは手で数える） |
| 修正案 | 修正案を持つフロントエンドの診断コードのそれぞれに、修正案を確かめるテストがある（コードの一覧を完了の報告に書く） |
| 警告 | `warnings` の区分に、07-03 の三つの確かめ（`check` の終了状態 0、`run` の実行、`--deny-warnings` の終了状態 2）がある |
| 複数のモジュール | `modules` の区分に、import・公開・循環・見つからないモジュール・ディレクトリの指定のテストがある |
| 新しいテストの関門 | 加えたテストのすべてが `test-audit` の作成時の関門を通っている（完了の報告に、関門で外したテストの数と理由を書く） |

## 完了条件

- `scripts/check.sh` が通る（00-02「完了条件の共通の検査」。両方式と回収の強制を含む）
- 受け入れテストのすべての場合を確かめている
- 設計書と食い違う実際の結果を、期待値に固定していない

## 難易度の理由

処理系のコードを書かず、規則ごとにスクリプトと期待値を書く作業である。数は多いが、判断が要るのは、単体テストと重ならない範囲を選ぶことと、期待値を設計書から決めることだけである。
