# R32 検証器による範囲の確かめの省略の評価

- 依存する作業: [R14](R14-stage1-wrap-up.md)
- 難易度: 4（1〜5。README の「作業一覧」）
- 規模の見込み: 中（500〜1500 行）

## 目的

[OPEN-064](../../design/open-issues.md#open-064) を決める材料を作る。読み込みのときにコンパイル済みプログラムを検証し、振り分けのループの実行中の範囲の確かめを `unsafe` で省くと、どれだけ速くなるかを、局所の状態を持つだけの今の VM（ADR 0263 の決定 1）と同じ命令列で比べて測る（同 決定 2）。

本作業が取り込むのは、検証器（`bytecode::verify`）とそのテスト、測定の道具と記録である。範囲の確かめを省く `unsafe` の変更は、測定のためだけのリビジョンに置き、本番の枝には取り込まない。採るかは設計者が決める。採ると決まったら、別の作業で、省く確かめを表にしたうえで入れ、[実装の規約](../00-common/00-02-conventions.md)と AGENTS.md の規則（「`Stop::Internal` で返す」を「検証器が拒む」に読み替える規則、`unsafe` を許す箇所）を改める（00-02「失敗を panic で表さない」「`#[allow]` を書いてよい箇所」、00-01「`unsafe` を書いてよいモジュール」）。

## 手順の要点

### 検証器（10-07「読み込みのときの検証器」）

`verify` は、次のことを確かめ、最初に見つけた違反を `VerifyError` で返す。

- 原型の表: `CompiledProgram::main` が表の中にある。各原型の `positions` と `code` の長さが等しい。`live` の形（10-07「生存の情報」の `starts` の長さと範囲）が正しい。
- 命令ごと: 命令の種類の番号が `Opcode` にある。読み書きするレジスタの番号（引数の並びは先頭から数の分まで）が原型の `num_regs` の中にある。原型・定数・分岐表・ハンドラの記述・構成子・実装・操作・組み込みの関数の参照の番号が、それぞれの表の中にある。`GETCAP` の番号が捕捉の表の中にある。跳ぶ先（`JMP`・`JMPF` の sBx、分岐表の各跳ぶ先）が命令列の中にある。命令列の最後の命令から次の命令へ落ちない（最後が `RETURN`・`TAILCALL`・`TAILMETHOD`・`ESCAPE`・`JMP` のどれか）。
- `PRIM`・`IO`・`CON`・`DICT`・`PERFORM` の引数の数が、表の項目の数と合う。`HANDLE` の節の関数の数がハンドラの記述の節の数と合う。

実行時の値によるもの（区画の所有、確保の失敗、呼び出しの入れ子の上限、継続の使用済み、呼ぶ関数の値の原型の引数の数、窓の大きさが呼ぶ側と呼ばれる側で合うこと）は、読み込みのときには保証できない（ADR 0263 の決定 2）。これらは確かめの対象にせず、測定の記録の表に「実行中に確かめ続けるもの」として挙げる。

検証器は Rust の再帰を使わない（命令列を一度走査するだけでよい）。

### 検証器のテスト（ADR 0263 の決定 2 の最後の箇条）

- 変異のテスト: コード生成が作った正しいプログラム（ゴールデンテストのスクリプトをコンパイルしたもの）の命令の被演算子・種類・跳ぶ先・表の長さを一か所ずつ無作為に変え、範囲の外になる変異を検証器が必ず拒むことを確かめる。乱数はテストの中の小さな生成器で作り、依存を加えない。種は固定する。
- 受理した入力の実行: 検証器が受理した変異（範囲の中に収まった変異）と元のプログラムを、範囲を確かめる今の VM で実行し、省く予定の確かめ（レジスタ、定数、跳ぶ先などの範囲）が一度も失敗しないことを確かめる。範囲の確かめが失敗して `Stop::Internal` を返したら、検証器の漏れである。VM の側に、範囲の確かめの失敗を数える口を測定のリビジョンの中にだけ置いてよい。
- fuzzing だけを安全性の根拠にしない（相談の第 2 回の問い 4）。本作業のテストは、検証器が保証することの表の各行に、変異のテストの場合を対応させる。

### 測定

1. 省く確かめの候補を、効果の大きい添字の読み書きから絞る。候補ごとに、検証器が保証することの表（命令と位置、レジスタ、定数・原型・捕捉、呼び出し、ハンドラと区画。相談の第 2 回の問い 4 の表の形）を作る。
2. 測定のためのリビジョンで、候補の読み書きを `get_unchecked` などの `unsafe` に替える。`unsafe` の各ブロックに、表のどの行が成り立つので範囲の中にあるかを `// SAFETY:` で書く。レジスタの `Vec` を伸ばした後に位置を読み直す規則（ADR 0263 の決定 1）を守る。範囲の外の `get_unchecked` は未定義動作であり、`Vec` の伸長は要素の位置を変えうる（相談の第 2 回の問い 4 が挙げた一次資料: Rust の `Vec` の文書の「Guarantees」と `slice::get_unchecked` の文書）。測定のリビジョンでは、lint の `unsafe_code` を振り分けのループのファイルだけで許してよい。
3. 同じ命令列（同じコンパイル済みプログラム）を、今の VM と測定のリビジョンで実行して比べる。ベンチマークは fib・loop・tree・eval（命令の振り分けの割合が大きいもの）を中心に、07-02 の集合を使う。スキル `benchmark` の手順（計算機を静かにする、10 回の中央値）に従う。
4. 生成された機械語（候補の読み書きの箇所）で、範囲の確かめの分岐が消えているかを確かめる（`cargo asm` などの道具を加えずに、`--emit asm` の出力で見る）。今の VM で最適化がすでに確かめを消している箇所は、省いても効果がない。
5. 記録に、比べた構成（コミット、ビルドの設定）、候補ごとの表、ベンチマークごとの時間の差、機械語の所見、実行中に確かめ続けるものの一覧、採る場合に要る規約の改め（00-02 と AGENTS.md の規則、lint の許可）を書く。採るかの案を示してよいが、決めるのは設計者である。

## 受け入れテスト

- `verify` の単体テスト: 確かめる候補のそれぞれについて、正しいプログラムを受理し、その一か所を範囲の外にしたプログラムを拒む。`VerifyError` が原型と命令の位置を持つ。
- 変異のテストと受理した入力の実行（上）。
- 既存のゴールデンテストのプログラムのすべてを、検証器が受理する。

- 完了の報告に、測定の結果の要約と、設計者に決めてもらうこと（採るか、採るならどの確かめを省くか）を書いている

## 確認の観点

- 検証器が、10-07 の「確かめる候補」を漏れなく確かめているか。実行時の値によるものを、検証で保証したことにしていないか。
- 変異のテストが、表の各行を少なくとも一つの変異で確かめているか。
- 測定が、振り分けのループの局所の状態の改善（ADR 0263 の決定 1）の効果と混ざっていないか（両方の構成が決定 1 を含むか）。
- 本番の枝に、測定のためだけのコード（範囲の確かめの失敗を数える口など）が残っていないか。

## 難易度の理由

検証器そのものは表を引いて範囲を確かめるだけだが、どの確かめを省いてよいかを、検証器の保証と実行時の保証の対応で一つずつ示す必要がある。`unsafe` の誤りは未定義動作になるので、測定のリビジョンでも `// SAFETY:` の根拠を厳密に書く。
