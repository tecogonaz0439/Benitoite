# R31 IO の方式のテストと、別のプロセスでの中断の要求のテスト

- 依存する作業: [R28](R28-interrupt-and-stop-procedure.md)、[R29](R29-runtime-builtins.md)
- 難易度: 3（1〜5。README の「作業一覧」）
- 規模の見込み: 中（500〜1500 行）
- ブランチ: impl/R31-io-mode-interrupt-tests

## 目的

二つのテストを書く。

1. IO の方式のテスト: タスクの待ちを含むプログラムが、IO の二つの方式（直接呼び出し、要求と応答）で同じ観測できる振る舞いになることを確かめる（07-03「IO の方式のテスト」、ADR 0029・0088・0264）。
2. 中断の要求のテスト: ビルドした `benitoite` を別のプロセスとして起動し、`SIGINT`・`SIGTERM` を送って、終了状態 130、出力の転送、二度目の要求での終わり方を確かめる（07-03「中断の要求のテスト（初回リリース版）」、ADR 0223）。

どちらもテストを書く作業であり、処理系のコード（`src/`）は変えない。テストが失敗して処理系の誤りが分かったら、作業を止めて報告する。

## 手順の要点

### IO の方式のテスト

07-03 は、`run` のゴールデンテストのすべてを二つの方式で実行するとしており、それはゴールデンテストの実行器（C10）と C12 のゴールデンテストが受け持つ。本作業は、ゴールデンテストでは順序を決めにくい、タスクの待ちを含む移り変わりを、筋書きで順序を与えて二つの方式で比べる。

- 比べるもの: 標準出力と標準エラー出力の内容、終わり方と終了状態、報告、テストが読むファイルの内容。
- 並べる実行: 同じスクリプトを、(a) 直接呼び出し、(b) 要求と応答、のそれぞれについて、R25 の筋書きで与えた二〜三通りの順序と、実際の部品（`RunEnv::parts` が `None`）で実行する。結果が順序によらないはずのスクリプトでは、すべての実行が一致することを確かめる。
- スクリプトの形（それぞれ一つ以上）:
  - 複数のタスクが `File.writeText`・`File.appendText`・`File.readText` を行い、`Task.all` で結果を集める。
  - `File.openReader` と `File.readLine` で読むタスクと、計算を続けるタスクが並ぶ。
  - `StdinSource::Bytes` で与えた入力を、`Console.readLine` と `Console.readAll` で読む。読む前に書いたプロンプトが、読む前に出力に現れる。
  - `Clock.sleep` で待つタスクと、書き込むタスク。仮想の時間で順序を決める。
  - IO の操作の途中で実行時エラーを起こすタスクがあり、止める手順で `with` のリソースが解放される。
  - 引き継いだハンドラが組み込みのエフェクトの操作（`Console.writeLine` など）を処理する場合と、処理しない場合。

### 中断の要求のテスト（07-03 の手順 1〜4）

1. ビルドした実行ファイルを `env!("CARGO_BIN_EXE_benitoite")` で見つけ、`std::process::Command` で子プロセスとして起動する。標準入力・標準出力・標準エラー出力をパイプにする。
2. スクリプトは、準備ができたことを示す行を標準出力に書いてから待つ（`Console.readLine` で標準入力を読むか、`Clock.sleep` で長く待つ）。
3. テストは、その行を読んだ後に、`kill` コマンド（`std::process::Command::new("kill").args(["-INT", &pid])`）でシグナルを送る。Rust の標準ライブラリには任意のシグナルを送る関数がなく、依存のクレートも加えない（[実装の規約](../00-common/00-02-conventions.md)の「依存するクレート」）ので、POSIX の `kill` コマンドを使う。
4. 終了状態が 130 であることと、バッファに残っていた出力が標準出力に書き出されたことを確かめる。

準備を知らせる行が親に届くことは、R13 の規則（端末でない出力でも、進められるタスクがなくなれば転送を依頼する。02-09「出力のバッファ」）に頼る。行が届かずにテストが止まるなら、それは OPEN-062 の R13 の再現であり、R30 の結果と合わせて報告する。子プロセスの待ちには上限の時間を設け、超えたら子プロセスを `Child::kill` で終わらせてテストを失敗にする（テストが止まり続けないようにするための時間であり、結果の判断に実時間を使うのではない）。

置く場合は次のとおりとする。

| 場合 | スクリプト | 送るもの | 確かめること |
|---|---|---|---|
| 標準入力を待つ | 行を書いてから `Console.readLine` | `SIGINT` | 終了状態 130。準備の行の後に書いた出力（読み取りの前に書いた分）が出る |
| 時間を待つ | 行を書き、別のタスクを起動してから `Clock.sleep` | `SIGTERM` | 終了状態 130 |
| 計算を続ける | 行を書いてから末尾再帰で計算を続ける | `SIGINT` | 終了状態 130（切り替えの位置で中断の印が調べられる） |
| `with` のリソース | `with r = File.openReader(..)` の中で待つ | `SIGINT` | 終了状態 130 |
| 二度目の要求 | 止める手順の終わりの出力の転送で止まるように、テストが標準出力を読まないまま多くの出力を書いてから待つ | `SIGINT` を送った後、標準出力を読まずにもう一度 `SIGINT` | 子プロセスが、転送を待たずに OS の既定の振る舞いで終わる（`ExitStatusExt::signal()` が `SIGINT` の番号）|

- `with` のリソースが解放されたことを外から確かめるには、書き込みで開いたファイルの内容が書き出されていることを見る（07-03 の手順 4）が、書き込みのリソース（`File.Writer`）は U3 で入る。本作業では、終了状態が 130 であることまでを確かめ、ファイルの内容の確かめは U3 の `File.Writer` の作業に残す。
- 二度目の要求の場合: 07-03 は「解放の途中で二度目のシグナルを送る」とするが、U2 には解放でブロックするリソースの型がない。止める手順の終わりの出力の転送の完了の待ち（02-09「出力のバッファ」の「止める手順の終わり」）は、同じく止める手順の途中の待ちなので、これで二度目の要求の振る舞いを確かめる。解放の途中の場合は、`File.Writer` が入る U3 で加える。
- `test` の実行中の中断（07-03 の最後の段落）は U4 が加える。

テストはすべて `#[cfg(unix)]` とする（07-03。初回リリース版の対象の環境は Unix 系である）。

## 受け入れテスト

- IO の方式のテスト: 上の「スクリプトの形」のそれぞれについて、二つの方式と複数の順序の実行が一致するテストがある。
- 中断の要求のテスト: 上の表の五つの場合のテストがある。

## 完了条件

- `scripts/check.sh` が通る
- `src/` を変えていない
- U3・U4 に残した確かめ（`File.Writer` の書き出し、解放の途中の二度目の要求、`test` の中断）を、完了の報告の「残したこと」に書いている

## 確認の観点

- 中断の要求のテストで、結果の判断に実時間を使っていないか（待ちの上限は、テストが止まり続けないためだけに使っているか）。
- 子プロセスの標準入出力のパイプを、テストの側で詰まらせて誤った結果にしていないか（二度目の要求の場合のほかは、標準出力と標準エラー出力を読み続ける）。
- IO の方式のテストが、ゴールデンテスト（C12）と同じ確かめを重ねていないか（スキル `test-audit` の重複の観点）。順序を与えた比較に絞っているか。

## 難易度の理由

処理系の機能はそろっているので、書く量は中程度である。別のプロセスのテストは、パイプの詰まりとシグナルを送る時期を誤ると不安定になるので、準備の行を読んでから送る手順を守る必要がある。
