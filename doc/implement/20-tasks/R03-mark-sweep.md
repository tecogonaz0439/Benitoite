# R03 マーク・スイープ

- 依存する作業: [R02](R02-no-gc-region.md)
- 難易度: 4（1〜5。README の「作業一覧」）
- 規模の見込み: 中（500〜1500 行）
- ブランチ: impl/R03-mark-sweep

## 目的

機能 `gc-mark-sweep` の構成の回収を作る。回収を安全点に限る、止めて行う非移動のマーク・スイープである（[ADR 0259](../../design/decisions/0259-compare-mark-sweep-and-rc-in-stage-1.md) の決定 1・5・6）。回収の要求は確保した量と前回の生きている量から決め、確保の関数は印を立てるだけにする。回収は VM が安全点で `Heap::collect` を呼んだときにだけ行う。

本作業は R04（参照カウント）と並行して、R02 が作った方式の境目の向こうに中身を書く。二つの方式は同じ公開の層・同じ確保器・同じ VM の上で入れ替わり、同じ根と同じ生存の情報から、同じ生きている値の集合を持たなければならない（ADR 0259 の決定 2）。

## 手順の要点

### 印付けと掃き出し

- 根は `Heap::collect(roots)` の `roots: &dyn Trace` だけである（不変条件 H4）。`Tracer` で知らされた `Slot` の先の対象に印を付け、明示の積み重ね（`Vec`）で対象の中の `Slot` を辿る。Rust の再帰を使わない（00-02「再帰の深さ」）。`Host` の対象は、その Rust の値の `Trace` で中の `Slot` を辿る（H5）。
- 印を付け終えたら、R01 の列挙で生きている対象をすべて辿り、印のない対象を R01 の解放の関数で解放し、印を消す。
- 辿った根の `Slot` の数を `roots_traced` に足す。解放の数（`frees`）は R01 の解放の関数だけが数えるので、本作業は足さない（二重に数えない）。回収ごとの停止の時間（ナノ秒）を `pause_nanos` に加える。時間は `std::time::Instant` で測る。
- 掃き出しが `Opaque`・`Host` の対象を解放するときの Rust の値の `drop` は、記憶域を返すだけであり、言語のリソースの解放やタスクの取り消しを行わない（10-08「根の保存領域」の最後の段落）。
- 機能 `heap-verify` の構成では、回収の前後に `Heap::verify` と同じ検査を行い、見つけた不具合を `take_fault` で取り出せるように記録する（10-08「区間と回収」）。

### 回収の要求

- 前回の回収からの確保の量 A と、前回の回収で数えた生きている量 L について、`A >= max(trigger_min_bytes, k × L)` を満たしたら要求の印を立てる（10-08「設定と測定の記録」、ADR 0259 の決定 6）。k は `HeapConfig::trigger_factor_percent` ÷ 100 であり、計算は整数で行い、溢れを検査する（例: `L × percent / 100` を `checked_mul` と `checked_div` で求め、溢れたら要求を立てる側に倒す）。
- A と L には、対象の頭、配置の切り上げ、対象が持つ別の領域の容量を含める。L は掃き出しの後に生き残った対象の量を数えて更新し、`live_bytes` に入れる。
- 確保の関数は印を立てるだけであり、確保の途中で回収しない（H1・H2）。
- `take_collect_signal` は、要求の印が前の呼び出しの後に新しく立ったときに一度だけ真を返す。VM はこれを受けて予算を 0 にし、遅い経路で回収する（[ADR 0263](../../design/decisions/0263-dispatch-loop-locals-and-verifier.md) の決定 3）。`collect_requested` は、印が立っている間は真を返し続ける（続けて戻る処理と後始末の位置が、予算と別に調べるため。ADR 0259 の決定 5）。回収を終えたら印を下ろす。
- `HeapConfig::stress` が真なら、`collect_requested` は常に真を返す（10-08「確かめ方の口」）。

### 生きている値の集合を揃える

二つの方式の比較は、生きている値の集合を揃えたうえで行う（ADR 0259 の決定 2）。マーク・スイープでは、使わなくなったレジスタは VM が `NoGcCtx::clear` で空にして根から除く（R09）。本作業の側では、根として渡された `Slot` を漏れなく辿り、それ以外を辿らないことで、この揃え方を保つ。`NoGcCtx::reuse_ctor` はマーク・スイープでは常に `Ok(None)` を返す（R04 が公開の層の関数を書くときにそうする）。

## 受け入れテスト

テストは、公開の層（`Heap::epoch`・`NoGcCtx`・`RootStack`・`Heap::collect`）を通して書く。値の並びの対象は `ValueCtx::alloc_fields`（R06）がまだないので、R02 のテスト用の補助か内部の層の確保の関数で作ってよい。R02 が仮の中身のファイルに置いた「回収後もすべて残る」テストは、中身を置き換えるときに消す。R02 の回収の共通の契約のテストは変えずに通す。解放の数は「増えた」でなく、`HeapStats::frees` の前後の差がちょうど期待する数であることで確かめる。

- 到達と解放: 根から辿れる対象（入れ子の値の並び、`Host` の対象の中の `Slot`、セルの中身）が回収の後に残り、辿れない対象が解放される。`Heap::object_ids` の集合を、テストが操作と同時に持つ独立の模型（本番の `Trace` を使わない）から計算した集合と比べ、`frees` の差が辿れない対象の数と等しい。
- 循環: 値の並びどうしとセルを通して循環する対象の組が、根から辿れなくなったら回収される。
- 深い構造: 長さ 100 万の連結した値の並びと、深さ 100 万の入れ子を根から辿って印を付けても、スタックを使い果たさない。Miri では `cfg!(miri)` で 1,000 程度に縮め、大きな規模の確かめは通常の実行に残す。
- 閾値: `trigger_min_bytes` を小さくした設定で、A が `max(trigger_min_bytes, k × L)` に達した確保の後に `collect_requested` が真になり、達する前は偽である。k を 50・100・200 にした三つの設定で、要求が立つ確保の量が L の 0.5・1・2 倍に従う。
- 信号: 要求が立った後、`take_collect_signal` は一度だけ真を返し、`collect_requested` は回収まで真を返し続ける。回収の後は両方とも偽になる。
- 回収の強制: `HeapConfig::stress` が真の設定で、`collect_requested` が常に真である。
- 記録: 一回の回収の前後で、`collections` の差が 1、`frees` の差が解放した対象の数、`roots_traced` の差が根の `Slot` の数とちょうど等しく、`live_bytes` が残った対象の量になり、`pause_nanos` の長さが `collections` と等しい。
- 検証器（`heap-verify`）: 回収の前後の検査が正しいヒープで不具合を記録しない。

## 確認の観点

[実装の確認の観点](../00-common/00-04-review-checklist.md)の「ヒープの内部の層」「マーク・スイープ（R03）」に加えて、次の点を読む。

- 回収の閾値の計算が ADR 0259 の決定 6 の式どおりか。A と L に頭・切り上げ・別の領域が含まれているか。
- 確保の関数から回収に至る経路がないか（H1・H2）。
- 印を消し忘れて、次の回収で解放すべき対象を残す経路がないか。
- `Host` の対象の中身を辿るときに、`Trace` の実装に頼るほかの近道（中身の型を仮定するなど）を使っていないか。

## 難易度の理由

アルゴリズムは教科書どおりだが、根が `&dyn Trace` の一つに集まっていることに頼っており、根の漏れは本作業の中では見つからない（VM の側の誤り）。本作業は、その前提を崩さないこと、閾値の計算を溢れなく正しく書くこと、参照カウントと同じ口の意味を保つことに注意が要る。
