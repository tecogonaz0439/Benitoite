## 起動の前にオーケストレータが書くこと

本作業は、R12 の測定の記録を設計者が確かめた後に起動する（[作業の進め方](../00-common/00-03-workflow.md)の「第 1 段の後の確認」）。オーケストレータは、起動の前に次の表を埋める。埋まっていなければ、本作業を始めずに報告する。

| 事項 | 設計者の判断 |
|---|---|
| 暫定に採るメモリの管理の方式 | （`gc-mark-sweep` か `gc-refcount`） |
| 回収の閾値の係数 k（マーク・スイープを採る場合） | （50・100・200 のどれか。百分率） |
| 参照カウントを採る場合の、遅らせた解放の条件と循環の回収の閾値 | （R04 の値のままか、改める値） |
| 採らなかった方式の実装を残すリビジョンの名前 | （例: タグ `stage1-rc-final`） |
| 判断を記録した測定の記録 | （`tools/bench/results/` のファイル名） |

## 目的

第 1 段の測定で暫定に採ったメモリの管理の方式を既定にし、採らなかった方式の実装を本番のコードから外す（[ADR 0259](../../design/decisions/0259-compare-mark-sweep-and-rc-in-stage-1.md) の決定 4 と帰結、[ADR 0268](../../design/decisions/0268-staged-runtime-rebuild.md) の決定 5）。採らなかった方式は、比べた構成を再現できるリビジョンとして残し、本番のコードでは保守しない。この後の第 2 段の作業（R20〜R33、R36）は、採った方式の上だけで書く（README の「依存と順序」の「第 2 段の開始」）。

方式は暫定である。ハンドラ・タスク・IO を加えた後に、R33 が停止の時間と保持する量を測り直して確かめ、ADR に記録して [OPEN-036](../../design/open-issues.md#open-036) を決着させる。本作業は OPEN-036 を決着させない。

## 作るもの

- 採らなかった方式の内部の層のファイル（R03 か R04 が書いた方式のファイル）と、そのテストを消す。
- `crates/benitoite/Cargo.toml`: 採らなかった方式の機能を消し、採った方式を既定にする（00-01「機能（feature）」の最初の箇条）。`gc-stress` の説明のうち採らなかった方式の分も改める。
- `src/runtime/heap/mod.rs`: 二つの機能のどちらか一方だけを有効にすることを確かめる `compile_error!` を、採った方式の機能が有効であることを確かめる形に改める。マーク・スイープを採り、k を 1 以外にした場合は、`DEFAULT_TRIGGER_FACTOR_PERCENT` の値を改める。
- `#[cfg(feature = ...)]` で方式に限ったコードとテストのうち、採らなかった方式の側を消し、採った方式の側の `cfg` を外す（残した `cfg` は、消した機能を指して警告になるので残さない）。
- `scripts/check.sh`（と、方式ごとに分けていれば `scripts/check-heap.sh`）: 採らなかった方式の行を消す（00-02「完了条件の共通の検査」の最後の段落）。
- `doc/implement/tools/extract_interfaces.py` など、機能の組み合わせを実装プランの表から作る道具は変えない（実装プランの側の改めはオーケストレータが行う）。

`src/runtime/heap/mod.rs` は C01 が置いた凍結したファイルであり、00-03「インターフェースの凍結」の例外の一覧にない。ここでの変更は、10-08「ヒープのモジュールの構成」と 00-01 が R14 に求めた範囲（機能の確かめと既定の k）に限り、完了の報告の「判断したこと」に挙げる。公開の層の型とシグネチャは変えない。`HeapStats` の参照カウントの項目、`NoGcCtx::reuse_ctor`、`HeapConfig::reuse` と命令 `CONR` は、マーク・スイープを採った場合も残す（公開の層の型と命令の集合を変えないため。`reuse_ctor` は常に `None` を返し、`CONR` は `CON` と同じに振る舞い、項目は 0 のまま。[ADR 0280](../../design/decisions/0280-reuse-by-dedicated-construct-instruction.md) の帰結）。

## 手順の要点

1. 作業を始める前の `san_benito` のコミット（両方の方式が揃った最後のコミット）を、完了の報告に書く。オーケストレータは、取り込みの前に、このコミットに上の表の名前でタグを付ける。採らなかった方式は、このタグから `--features` を変えてビルドすれば再現できる。R12 の測定のためだけのリビジョン（RC-noreuse など）は、R12 の記録に書いたコミットのまま残る。
2. 採らなかった方式のファイルとテストを消し、`cfg` を整理する。R02 が作った方式の境目は、方式が一つになっても残してよい（第 2 段で世代の回収などを加えるときの境目になる。ADR 0259 の決定 7）。仮の中身（R02 が置いた、回収しない中身）が残っていれば消す。
3. 機能と検査のスクリプトを改め、既定のビルドで採った方式が有効になることを確かめる。
4. `scripts/check.sh` と `scripts/check-heap.sh` を実行する。第 1 段の確かめ（R11 のテスト、C05 のゴールデンテストと回収の強制）は、採った方式だけで通る。
5. 実装プランと AGENTS.md に残る「二つのメモリの管理」「第 1 段の間」の記述（00-01「機能（feature）」、00-02 の検査の表と「テストの規約」、00-04「二つのメモリの管理の確かめ方」など）で改めるべき箇所の一覧を作り、完了の報告の「残したこと」に書く。文書の改めはオーケストレータが行う。

## 受け入れテスト

- 既定のビルド: `cargo build -p benitoite` の既定の機能で、採った方式が有効になる（テストの中で、採った方式でだけ成り立つ振る舞いを確かめるテストが既定の機能で走ることで示す。例: マーク・スイープを採ったなら `reuse_ctor` が `None` を返す）。
- 採らなかった機能の消去: 採らなかった機能の名前で `--features` を指定したビルドが、Cargo の誤り（機能がない）で止まる。
- 再現: タグのコミットで、採らなかった方式の機能を指定して `cargo test -p benitoite` が通る（オーケストレータがタグを付けた後に確かめる。完了の報告に確かめ方を書く）。
- 検査: `scripts/check.sh` と `scripts/check-heap.sh` が通る。

## 完了条件

- `scripts/check.sh` と `scripts/check-heap.sh` が通る
- 本番のコードに、採らなかった方式の実装と、その方式の機能を指す `cfg` が残っていない
- 完了の報告に、両方の方式が揃った最後のコミット、変えた凍結したファイルの箇所、文書の改めの一覧を書いている

## 確認の観点

[実装の確認の観点](../00-common/00-04-review-checklist.md)の「すべての作業で読む観点」に加えて、次の点を読む。

- 消したテストが、採らなかった方式だけに意味のあるテストに限られているか。両方の方式で意味のあるテストを、`cfg` の整理のついでに消していないか。
- 公開の層の型とシグネチャを変えていないか。
- 採った方式の既定の値（k、遅らせた解放の条件、循環の回収の閾値）が、上の表の設計者の判断と一致しているか。

## 難易度の理由

判断は設計者が済ませており、作業は消すことと設定を改めることが中心である。消しすぎ（両方式に共通のテストや境目）と消し残し（`cfg`、検査の行）の両方に注意が要る。
