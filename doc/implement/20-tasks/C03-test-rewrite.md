# C03 最小実行版のゴールデンテストを新しい構文へ書き直す

- 依存する作業: [F02](F02-parser-core.md), [F03](F03-parser-modules-records.md)（F03 に依存する理由は「手順の要点」の「import が要る」）
- 難易度: 3（1〜5。[README](../README.md) の「作業一覧」の目安）
- 規模の見込み: 大（197 件のスクリプトと期待値のファイル。書く Rust のコードは小さい）
- ブランチ: impl/C03-test-rewrite

## 目的

最小実行版のゴールデンテスト 197 件（`testdata/` の下。`runner/` の 4 件を含む）を、初回リリース版の構文で書き直し、`testdata-next/` に置く（[作業の進め方](../00-common/00-03-workflow.md)の「構文の改めとテストの移行」）。書き直したテストは、テストと CLI の切り替え（C05）が初回リリース版の実行器で走らせ、U2 第 1 段の完了の条件（[ADR 0268](../../design/decisions/0268-staged-runtime-rebuild.md) の決定 3 の「最小実行版のすべてのテスト」。[README](../README.md) の「決めたこと」の 5）に使う。

この作業では、最小実行版の言語の機能だけを使い、書き方だけを改める。文字列補間・`try`・レコードなど、初回リリース版で加わる機能に置き換えない。期待する出力と診断の位置は、この作業では確かめない（C05 が確かめる）。代わりに、書き直したスクリプトが初回リリース版の構文解析器で読めることを確かめるテストを加え、以後の U1 の作業が構文解析器を変えても読めることを保つ。

## 作るもの

パスは処理系のクレート `crates/benitoite/` からの相対パスである。

- `testdata-next/<区分>/`: `testdata/` の各テストを書き直したもの。区分のディレクトリと名前は `testdata/` と同じにする（`acceptance/INDEX.md` も写し、名前を変えたテストがあれば表を直す）。
- `testdata-next/REWRITE.md`: 書き直しの記録（後述）。C05 が期待する出力を確かめるときに読み、`testdata/` へ移すときに消す。
- `tests/next_syntax.rs`: 書き直したスクリプトが初回リリース版の構文解析器で読めることを確かめる統合テスト。ファイルの先頭に、テストのコードに許す lint の `#![allow(...)]` を書く（[実装の規約](../00-common/00-02-conventions.md)の「`#[allow]` を書いてよい箇所」）。

`testdata/` と、それを走らせる `legacy` の実行器（`tests/golden.rs`）は変えない（[リポジトリとクレートの配置](../00-common/00-01-repository-layout.md)の「移行の間の配置」）。処理系の `src/` も変えない。

## 手順の要点

### 書き直しの規則

一つのテストについて、元のスクリプトが確かめている規則（先頭の `// spec:` の行と、期待値のファイル）を読み、同じ入力の形で同じ規則を確かめるスクリプトにする。

1. 構文の改め: 01-02 の規則で書き直す。波括弧のブロックは、キーワードで始めて `end …` で閉じるブロックにする（`function … end function`、`lambda … end lambda`、`if … then … else … end if`、`match … with case … -> … end match`）。戻り値の型は `->` の後に書く。局所の束縛は `bind`（見えている名前を隠すときは `shadow`）で書く。代数的データ型は `data … end data` で宣言する。演算子は初回リリース版の綴り（`=`・`<>`・`and`・`or`・`not`・`div`・`mod` など）に改める。
2. import が要る: 初回リリース版では、`Console`・`File`・`Process` などの IO のモジュールは prelude になく、import の宣言が要る（01-07「IO を行う組み込み関数」、ADR 0128）。これらは非公式のモジュールなので、`import Benitoite.Unofficial.IO.Console` のように取り込みの名前で書く（03-06「標準のモジュールと非公式のモジュール（初回リリース版）」、[ADR 0286](../../design/decisions/0286-unofficial-modules-imported-under-unofficial.md)）。import の宣言を読むのは F03 の構文解析器なので、この作業は F02 と F03 の後に行う。
3. エフェクトの名前: `uses IO` は、`uses IO.All` か、実際に行う操作のエフェクト（`uses Console.Write` など）に改める（01-07、ADR 0130）。元のテストが `IO` のエフェクトを確かめていたなら、同じ関係（含む・含まない）を初回リリース版のエフェクトの名前で確かめる。どの形にしたかを `REWRITE.md` に書く。
4. 関数の名前: 最小実行版から名前を改めた組み込みの関数と prelude の関数（`Console.println` を `Console.writeLine` に、`Integer.floorDiv` を `Integer.floorDivide` に、など）は、10-12 と 10-14 と 03-06・03-07 の名前に改める。改めた名前の対応表を `REWRITE.md` に書く。元のテストが使う関数が、10-12・10-14 のどこにもない（U3 で加わる、名前が見つからない）ときは、ほかの関数で置き換えずに、そのテストを `REWRITE.md` の「書き直せなかったもの」に挙げる。
5. 他の言語の書き方: 最小実行版の書き方（`fn`・`let`・`{ }`・`:` の戻り値の型など）は、初回リリース版では他の言語の書き方への診断の対象になる。構文の誤りを確かめるテスト（主に `syntax/` と `lexical/`）は、同じ種類の誤り（閉じ忘れ、予期しない字句、閉じていない文字列など）を、初回リリース版の構文の上で起こすように書き直す。元の誤りが初回リリース版の構文では起きない（その規則がなくなった）ときは、最も近い規則の誤りに書き直し、`REWRITE.md` に元の規則と新しい規則を並べて書く。期待値が廃止した診断コード（[10-02](../10-interfaces/10-02-diagnostics.md) の廃止したコードの表: E0111・E0117・E0205・E0307・E0308・E0317）を含むテストは、この場合に当たる。表の「廃止した理由」の欄が示す新しい規則（E0111 なら文字列補間が読めること、E0205 なら波括弧のブロックへの E0212 の診断、など）を確かめるテストに書き直す。
6. 期待値のファイル: `.mode`・`.exit`・`.stdout`・`.stderr`・`.args`・`.files/`・`.diag.json`・`.text.stderr` は写す。中身は変えない（期待する出力が変わるかは C05 が確かめる）。ただし `.diag.json` と `.text.stderr` の位置と文言は、書き直しで変わることが分かっている。C05 が差を読むときの手がかりとして、`REWRITE.md` にテストごとの見込み（「位置だけが変わる」「コードが変わる見込み」など）を書く。
7. `.opts`（最小実行版の実行器の独自の形式。`max-call-stack=64KiB`）は、初回リリース版の `.options`（CLI のオプションを一行に一つ。07-03「ゴールデンテストの形式（初回リリース版）」）に改め、`--max-call-stack=64KiB` と書く。
8. `// spec:` の行は残す。見出しの名前が現在の 01-spec にないときは、同じ規則を定める現在の節の名前に改め、`REWRITE.md` に書く。
9. テストを足したり、二つのテストを一つにまとめたりしない。一つの元のテストに、一つの書き直したテストを対応させる。

### 書き直しの記録（`testdata-next/REWRITE.md`）

次の節を置く。表の行は、機械的な書き直し（手順 1 だけ）で済んだテストには書かない。

- 関数の名前の対応表（手順 4）
- エフェクトの書き方（手順 3。どの形を選んだかと、テストの一覧）
- 規則を改めたテスト（手順 5・8。元の規則と新しい規則）
- 期待値が変わる見込み（手順 6）
- 書き直せなかったもの（手順 4。理由と、どの作業の後に書き直せるか）

### 読めることを確かめるテスト（`tests/next_syntax.rs`）

- `testdata-next/` の下を辿り、`.bnt` のファイル（`<名前>.files/` の中は除く）ごとに、`syntax::lexer::lex`（ファイル ID は `FileId(0)`）、`syntax::newline::resolve_newlines`、`syntax::parser::parse`（`SourceKind::User`、`IdGen` はファイルごとに新しく作る）を順に呼ぶ（[10-03](../10-interfaces/10-03-syntax.md)）。
- 期待値のファイル `.diag.json` の最初の行のコードが字句の誤り（`E01xx`）か構文の誤り（`E02xx`）であるテストは、字句か構文の誤りが一つ以上報告されることを確かめる。コードと位置は確かめない。ただし、`lex` の前の読み込みの段が報告する誤り（E0101 のファイルを読めない誤り、E0102 の正しくない UTF-8）のテストは、`lex` と `parse` が panic せずに終わることだけを確かめる。どのコードが読み込みの段のものかは 10-02 と [10-04](../10-interfaces/10-04-modules-and-resolve.md) の `load_program` で確かめる。
- ほかのテストは、字句と構文の誤りがないことを確かめる。U1 の作業が `testdata-next/` に置いたゴールデンテスト（F02 などが置く。名前とディレクトリは作業ごとに違う）も同じく読む。
- すべてのファイルを試した後に、失敗したファイルの名前と、最初の診断のコードと文言を並べて失敗させる。

このテストは `scripts/check.sh` で走る。C05 が消す。

## 受け入れテスト

| 場合 | 期待 |
|---|---|
| 件数 | `testdata-next/` の `.bnt` のうち本作業が書き直したものの数が、`testdata/` の `.bnt` の数（197）から「書き直せなかったもの」の数を引いたものと一致する。本作業が書き直したものは、`testdata/` に同じ相対パスの `.bnt` があるものとして数える。U1 の作業（F02 など）が `testdata-next/` に置いたゴールデンテストは、`testdata/` に同じ相対パスのファイルがないので数えない |
| 読めること | `tests/next_syntax.rs` が通る |
| テストの検出力 | 書き直したスクリプトの一つから `end function` を一行消したコピーをテストの中で読むと、失敗として数えられる（判定の関数に文字列を与えて呼ぶテストで確かめる） |
| 初回リリース版の機能を使っていない | `testdata-next/` のスクリプトに、文字列補間、`try`、`record`、`trait`、`implement`、`handle`、`lazy`、`with` の束縛、定数の宣言、属性がない（`grep` で確かめ、コマンドを完了の報告に書く。対象は、件数の場合と同じく `testdata/` に同じ相対パスの `.bnt` があるものに限る。U1 の作業が置いたゴールデンテストは、初回リリース版の機能を確かめるものなので対象から外れる）。例外は、廃止したコードのテストを書き直したもの（手順 5）で、`REWRITE.md` の「規則を改めたテスト」に挙げたものだけである |
| 既存のテスト | `testdata/` と `tests/golden.rs` を変えていない。`scripts/check.sh` の最小実行版のテストが通り続ける |

## 完了条件

- `scripts/check.sh` が通る（00-02「完了条件の共通の検査」）
- 受け入れテストのすべての場合を確かめるテストか確認の記録がある
- `testdata-next/REWRITE.md` がある。「書き直せなかったもの」が空でないときは、完了の報告にその一覧を書く

## 確認の観点

[実装の確認の観点](../00-common/00-04-review-checklist.md)の「テストの書き直しと切り替え（C03・C05）」の行に加えて、次を読む。

- 書き直したスクリプトが、元のテストの `// spec:` の規則を、同じ入力の形で確かめているか（無作為に 20 件を選び、元と並べて読む）。
- 構文の誤りのテストで、誤りの種類が元のテストと同じか。

## 難易度の理由

一件ずつは機械的な書き直しだが、件数が多い。判断が要るのは、構文の誤りを確かめるテストと、エフェクトの名前が変わるテストを、同じ規則を確かめる形に保つことである。初回リリース版の機能に置き換えたくなる箇所（`match` で書いた処理を `try` にする、など）で置き換えないことにも注意する。
