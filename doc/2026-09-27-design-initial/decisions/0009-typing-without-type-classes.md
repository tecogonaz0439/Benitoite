# 0009. 型クラスのない間、演算子を閉じた制約で型付けし、等値を構造で判定し、局所の束縛を多相にしない

- 状態: 採択
- 日付: 2026-09-26
- 関連章: [基本型の意味論](../01-spec/01-04-types-basic.md), [代数的データ型とパターンマッチ](../01-spec/01-05-data-types.md), [型システム](../01-spec/01-06-type-system.md), [標準ライブラリ](../03-interop/03-06-stdlib.md)
- 関連する未決事項: [OPEN-004](../open-issues.md#open-004), [OPEN-012](../open-issues.md#open-012)

## 背景

最小実行版には型クラスを含めない（[ロードマップ](../00-overview/00-03-roadmap.md)）。一方で、`+` は `Int`・`Float`・`String` に使え（[ADR 0006](0006-basic-types-semantics.md)）、比較演算子は複数の基本型に使える（[基本型の意味論](../01-spec/01-04-types-basic.md)）。HM 推論では、`fn(a, b) { a + b }` のようなラムダの引数の型は、使われ方が分かるまで型変数のままである。型クラスがなければ、この型変数が「`+` を使える型」であることを表す手段が要る。

代数的データ型の値どうしを `==` で比べられるかも決める必要がある。関数の値は比べられないので、関数を含む型に `==` を使ったときの扱いも含めて決める。

もう一つ、局所の `let` で束縛した値を多相にするか（let 多相）を決める。トップレベルの関数はシグネチャが必須であり、型パラメータも宣言する（[ADR 0004](0004-surface-syntax-skeleton.md)）ので、多相であることはすでに決まっている。局所の束縛を多相にするかどうかで、推論の実装と診断の分かりやすさが変わる。また、v1 で可変状態を加えるときに、多相な束縛が型の安全性を壊す問題（[OPEN-004](../open-issues.md#open-004)）が生じるかも、ここで変わる。

## 決定

1. 演算子のオペランドの型変数は、演算子ごとに決まった型の集まりのどれかであるという制約を持つ。集まりは、`+` が `Int`・`Float`・`String`、`-`・`*`・`/` と単項の `-` が `Int`・`Float`、`<`・`<=`・`>`・`>=` が `Int`・`Float`・`String`・`Char` である。制約を持つ型変数が、トップレベルの関数一つの型検査を終えるまでに具体的な型に決まらなければ、型検査の誤りとし、型注釈を求める。利用者はこの制約を書けず、関数の型パラメータに演算子を使うこともできない。
2. `==` と `!=` は、関数の型を含まない型（等値の型）の値に使える。代数的データ型とリストの値は、構造で比べる。構成子が同じで、対応する引数がすべて等しいときに等しい。関数の型を含む型に `==` を使うと、型検査の誤りとする。順序の比較（`<` など）は、代数的データ型とリストには使えない。
3. 局所の束縛（`let`、ラムダの引数、パターンの変数）は多相にしない。多相なのは、シグネチャで型パラメータを宣言したトップレベルの関数と、データ構成子と、prelude の関数である。
4. prelude の関数は、利用者が書けない制約（等値の型であることなど）を型に持ってよい。

## 検討した代替案

### 演算子

- **型ごとに別の演算子を設ける**（OCaml の `+.` のように、`Float` の加算と文字列の連結に別の演算子を使う）: 推論は制約なしの HM で済む。しかし、LLM が `Float` に `+` を書く誤りが頻発すると見込まれる。`+` で文字列を連結できることは [ADR 0006](0006-basic-types-semantics.md) で決めており、それとも矛盾する。

採った方式は Elm の `number`・`comparable` と同じ種類のもので、集まりは処理系が固定する。型クラスを入れれば、この制約は型クラスの制約に置き換えられる。

### 等値

- **最小実行版では代数的データ型に `==` を使えないようにする**: `match` で比べれば済み、型検査器は単純になる。しかし、`Option[Int]` の値を `Some(3)` と比べるような短いコードが書けず、LLM は `==` を書いて誤りになると見込まれる。関数の型を含むかどうかは型の定義から静的に判定できるので、実行時の誤りにはならない。

### 局所の束縛

- **局所の束縛も多相にする（HM の let 多相）**: `let id = fn(x) { x }` を別の型で何度も使える。設計者は HM の一般化の実装をすべて読める。しかし、次の理由で採らない。
  - 局所の束縛を多相にする必要がある場面は少ない。多相な補助関数はトップレベルに書ける。
  - 多相でない束縛は、型の誤りが見つかった位置と原因の位置が近く、診断が分かりやすい（原則 4）。
  - v1 で可変状態を加えるときに、value restriction のような追加の規則が局所の束縛について不要になる。

採った方式は、Rust の局所変数と、GHC の `MonoLocalBinds` 拡張の考え方に近い。

どの判断も、LLM が誤りにくいという見込みは【要検証】であり、OPEN-012 の測定課題で確かめる。

## 帰結

- 型推論の一般化（型変数を ∀ で束ねること）は、最小実行版の型検査器には現れない。トップレベルの関数の型は宣言された型パラメータで決まり、呼び出しの位置でそれを具体化するだけである。設計者が一般化の実装を読む機会は、v1 で必要になった場合に限られる。
- `List.contains` のように要素の等値を使う prelude の関数は、決定 4 の制約を型に持つ。利用者は同じ形の関数を定義できないので、自分で書くときは比べる関数を引数に取る。v1 で型クラスを入れると、この非対称は解消できる。
- [OPEN-004](../open-issues.md#open-004) は、局所の束縛については生じなくなる。v1 で多相な束縛をほかに加える（型パラメータを持つトップレベルの定数など）ときに、改めて検討する。
- 利用者の関数の型パラメータに `+` や `<` を使えないので、`max` のような汎用の関数は、最小実行版では型ごとに書くか、比べる関数を引数に取る。
