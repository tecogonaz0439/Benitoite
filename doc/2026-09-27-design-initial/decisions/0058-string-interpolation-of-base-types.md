# 0058. 文字列補間には基本型の式を書け、処理系が文字列に変換する

- 状態: 採択
- 日付: 2026-09-26
- 関連章: [字句構造](../01-spec/01-01-lexical.md), [構文](../01-spec/01-02-syntax.md), [型システム](../01-spec/01-06-type-system.md), [基本型の意味論](../01-spec/01-04-types-basic.md)
- 関連する未決事項: [OPEN-012](../open-issues.md#open-012)

## 背景

v1 では、文字列の中に式の値を埋め込む文字列補間を加える（[ロードマップ](../00-overview/00-03-roadmap.md)）。最小実行版では、文字列リテラルの中の `${` を文字列補間のために予約している（[字句構造](../01-spec/01-01-lexical.md)）。型クラスを持たない間、演算子は、演算子ごとに決まった型の集まりの制約で型付けしている（[ADR 0009](0009-typing-without-type-classes.md)）。

## 決定

文字列リテラルの中の `${e}` は、式 `e` の値を文字列にして埋め込む。`e` の型は、`String`・`Int`・`Float`・`Char`・`Bool` のどれかでなければならない。演算子と同じく、`e` の型が型変数のときは、この型の集まりのどれかであるという制約を持つ（[ADR 0009](0009-typing-without-type-classes.md)）。

値は、`String` はそのまま、`Int`・`Float`・`Char` はそれぞれの `toString` の関数と同じ規則で、`Bool` は `true` か `false` の文字列にする。それ以外の型の式を書くと型検査の誤りとし、診断は文字列に変換する関数を修正案として示す。

## 検討した代替案

- **`String` の式だけを書ける**: 規則は最も小さい。しかし、`"${count}"` のような書き方が誤りになり、LLM が生成したスクリプトの誤りが増えると見込まれる。
- **型クラスで文字列化できる型をすべて書ける**: 利用者の型も埋め込める。しかし、型クラスの設計（[OPEN-024](../open-issues.md#open-024)）が決まるまで決められない。型クラスを加えた後に、集まりを型クラスの制約に置き換えて広げることはできる。

## 帰結

- 基本型の値は、変換の関数を書かずに文字列に埋め込める。
- 利用者の型の値を埋め込むには、変換の関数を明示して呼ぶ。
- 集まりを後で型クラスの制約に広げても、書けた式の意味は変わらない。
