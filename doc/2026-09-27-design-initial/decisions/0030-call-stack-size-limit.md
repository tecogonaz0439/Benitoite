# 0030. 呼び出しの入れ子の上限を、呼び出しの情報の合計の大きさで決める

- 状態: 採択
- 日付: 2026-09-26
- 関連章: [仮想機械](../02-impl/02-08-vm.md), [ランタイム](../02-impl/02-09-runtime.md), [評価意味論](../01-spec/01-08-evaluation.md)
- 関連する未決事項: [OPEN-009](../open-issues.md#open-009)

## 背景

処理系は、末尾位置にない呼び出しの入れ子の深さに上限を持ってよく、上限に達したときは実行時エラーと同じ手順で停止する（[評価意味論](../01-spec/01-08-evaluation.md)）。上限の値は処理系の設計で定める。VM は呼び出しの情報を自分で管理するので、入れ子の大きさを数えられる（[ADR 0016](0016-calls-off-go-stack.md)）。

関数型のコードでは、リストを末尾でない再帰で辿ることが多く、入れ子の深さは入力の大きさに比例しうる。呼び出し一つあたりに使うメモリは、関数のレジスタの数によって変わる（[ADR 0027](0027-register-bytecode.md)）。

## 決定

上限は、入れ子の段数ではなく、実行ごとの状態が持つ呼び出しの情報（呼び出しの枠と、レジスタの並び）の合計の大きさで決める。既定の上限は 1 GiB とする。呼び出しによってこの合計が上限を超えるときは、[評価意味論](../01-spec/01-08-evaluation.md)の資源の不足として停止し、呼び出しの入れ子が深すぎることを報告する。

既定の値は、最小実行版の後の性能測定（[性能](../07-quality/07-02-performance.md)）で見直す。利用者が上限を変える手段を設けるかは [CLI](../06-tooling/06-01-cli.md) で定める。

## 検討した代替案

- **段数で決める（100 万段）**: 利用者と LLM に説明しやすい。しかし、レジスタの多い関数と少ない関数とで、同じ段数でも使うメモリが大きく違い、上限がメモリの使用量を抑える目安にならない。
- **段数で決める（1 万段）**: 停止しない再帰を早く止められる。しかし、数万の要素のリストを末尾でない再帰で辿るだけで止まり、関数型の書き方で普通に書いたプログラムが資源の不足で失敗する。

## 帰結

- 小さな関数の再帰なら、数百万段まで深くできる。
- 停止しない再帰（末尾でないもの）は、上限に達するまでメモリを使い続けてから止まる。
- 上限に達したときの報告で、段数を示すことはできる（数えるのは容易である）が、上限そのものは段数でないので、同じプログラムでも関数の形によって止まる深さが変わる。
- 1 GiB は、Go の実行環境や端末によっては大きすぎる可能性がある。モバイルなどメモリの少ない環境での値は、その配布を設計するときに見直す。
