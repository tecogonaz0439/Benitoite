## 目的と範囲

解析器の実装方式、エラー回復、AST の構造。コメントと元の字句をどの段階まで保持するか、構文木を実行・フォーマッタ・LSP のどの用途に使うかも扱う。

現在の版は、最小実行版（[ロードマップ](../00-overview/00-03-roadmap.md)）の範囲だけを定める。字句と文法の規則そのものは[字句構造](../01-spec/01-01-lexical.md)と[構文](../01-spec/01-02-syntax.md)で定め、本章はそれを実装する方法を定める。

## 前提

span は、すべての字句と AST ノードの必須フィールドである（[ソース管理と位置情報](02-02-source-and-spans.md)）。検査の段で誤りがあれば次の段に進まず、各段の中では回復して誤りをできるだけ多く報告する（[ADR 0019](../decisions/0019-stop-after-failing-stage.md)）。

## 仕様

### 処理の流れ

【方針】字句解析と構文解析は、次の三つの工程で行う。

1. 字句の切り出し: ソースのバイト列を先頭から読み、字句と改行の印の列を作る。コメントは字句の列に入れず、別の一覧に集める。
2. 改行の判定: 改行の印ごとに、[字句構造](../01-spec/01-01-lexical.md)の「改行による区切り」の規則で、NEWLINE を置くか空白として捨てるかを決める。規則は改行の直前と直後の字句と開いている括弧の種類を使うので、字句を切り出し終えてから、開いている括弧の積み重ねを持って列を一度辿って判定する。
3. 構文解析: NEWLINE を含む字句の列から AST を作る。

三つの工程は手書きで作る。どの工程も、パッケージ変数などの大域的な可変状態を持たない（[ADR 0015](../decisions/0015-shared-program-per-execution-state.md)）。

### 字句

【方針】字句は、種類、span、字面を持つ。リテラルの字句は、次の値も持つ。

| リテラル | 字句が持つ値 |
|---|---|
| 整数 | 基数と、`_` を除いた数字列。値が `Int` の範囲に収まるかは、単項の `-` との組み合わせで決まる（[基本型の意味論](../01-spec/01-04-types-basic.md)）ので、型検査器が判定する |
| 浮動小数 | `_` を除いた字面。値への丸めと範囲の判定は型検査器が行う |
| 文字列 | エスケープシーケンスを解いた後の文字列 |
| 文字 | エスケープシーケンスを解いた後のスカラー値 |

【方針】字句を切り出す工程は、次の誤りを報告する（[字句構造](../01-spec/01-01-lexical.md)）。

- 許されない文字と、正しくない UTF-8。
- 文字列リテラル・文字リテラル・コメントの外の、字句に使えない記号。`;` を書いたときは、文を改行で区切るよう示す。
- 文字列リテラル・文字リテラル・コメントの中の、双方向の制御文字（U+061C、U+200E、U+200F、U+202A〜U+202E、U+2066〜U+2069）と、ファイルの先頭以外の U+FEFF。文字列リテラルと文字リテラルの中では、エスケープ `\u{...}` で書くよう示す（[ADR 0051](../decisions/0051-lexical-boundaries-and-invisible-characters.md)）。
- 閉じていない文字列リテラルと文字リテラル、正しくないエスケープシーケンス、`${` を含む文字列リテラル（`\$` でエスケープするよう示す）、複数のスカラー値からなる文字リテラル（文字列リテラルを使うよう示す）。
- 整数リテラルと浮動小数リテラルの形の誤り。数値リテラルの直後に識別子に使える文字（英字、数字、`_`）が続く場合（`12abc`、`0xfg`）と、浮動小数リテラルの直後に `.` と数字が続く場合（`1.5.2`）を含む。これらは、数値リテラルの先頭から、続く識別子に使える文字と `.` と数字の並びの終わりまでを一つの誤りの字句にする（[ADR 0051](../decisions/0051-lexical-boundaries-and-invisible-characters.md)）。
- 予約語（[字句構造](../01-spec/01-01-lexical.md)の「キーワード」）。予約語は最小実行版では構文上の意味を持たないので、文字列リテラルとコメントの外に現れれば、どの位置でも誤りとする。診断は、その語が予約語であることと、次の修正案を示す。

| 予約語 | 修正案 |
|---|---|
| `for`・`while`・`loop` | 繰り返しの構文はないので、再帰か、`List.map`・`List.forEach`・`List.fold` などを使う |
| `break`・`continue` | 繰り返しの構文はないので、再帰を使う |
| `return` | ブロックの最後の式の値が、関数の戻り値になる |
| そのほか | 将来の構文のために予約した語であり、識別子に使えないので、別の名前を付ける |

【方針】字句を切り出す工程は、誤りを報告した後も続ける。許されない文字と字句に使えない記号は 1 文字を読み飛ばし、閉じていない文字列リテラルと文字リテラルは行の終わりで閉じたものとして扱う。予約語と、誤りを含むリテラルは「誤りの字句」とする。構文解析器は、誤りの字句を、その位置で期待していた構文（式、型、パターン、名前）の誤りのノードとして扱い、その字句について新たな構文エラーを報告しない。

### コメント

【決定】コメントは AST に入れず、本文と span の組の一覧として構文解析の結果に含める（[ADR 0021](../decisions/0021-comments-beside-ast.md)）。空白と、NEWLINE にならなかった改行は保持しない。

### 構文解析の方式

【決定】構文解析器は手書きの再帰下降（recursive descent）で作る。宣言・文・型・パターンは、[構文](../01-spec/01-02-syntax.md)の EBNF の規則ごとに関数を一つ書く。式の演算子は、演算子ごとの結合の強さの表を使う Pratt 法（Pratt parsing）で解析する（[ADR 0020](../decisions/0020-recursive-descent-with-pratt.md)）。

【方針】演算子の表は次のとおりとする。[構文](../01-spec/01-02-syntax.md)の優先順位と結合性の表と一対一に対応し、数が大きいほど強く結合する。

| 演算子 | 位置 | 左の強さ | 右の強さ | 対応する優先順位 |
|---|---|---|---|---|
| `\|>` | 中置 | 10 | 11 | 1（左結合） |
| `\|\|` | 中置 | 20 | 21 | 2（左結合） |
| `&&` | 中置 | 30 | 31 | 3（左結合） |
| `==` `!=` `<` `<=` `>` `>=` | 中置 | 40 | 41 | 4（結合しない） |
| `+` `-` | 中置 | 50 | 51 | 5（左結合） |
| `*` `/` `%` | 中置 | 60 | 61 | 6（左結合） |
| `-` `!` | 前置 | — | 70 | 7 |
| `(` | 後置（呼び出し） | 80 | — | 8 |

結合しない比較演算子は、比較の右のオペランドを解析した直後に、次の字句がまた比較演算子であれば構文エラーとする。診断は、`a < b && b < c` の形に書き換えるよう示す（[構文](../01-spec/01-02-syntax.md)）。

【方針】構文の規則に伴う次の診断は、構文解析器が出す。

- 値に続けたドット（`xs.map(f)`）は構文エラーとし、`|>` を使った書き方を修正案として示す（[構文](../01-spec/01-02-syntax.md)の「ドット記法」）。
- 呼び出しの直接の引数以外の位置に書いた `_` は構文エラーとする（同「部分適用のプレースホルダ」）。
- 関数の宣言の戻り値の型（と `uses`）の直後に NEWLINE があり、次の行が `{` で始まる場合は、`{` を前の行の末尾に書くよう示す（[字句構造](../01-spec/01-01-lexical.md)の「改行による区切り」）。
- 型の宣言で、構成子の名前の後に空の括弧を書いた場合（`Leaf()`）は構文エラーとし、括弧を取り除くよう示す（[代数的データ型とパターンマッチ](../01-spec/01-05-data-types.md)）。
- 利用者のソースで、関数の宣言の名前をモジュールの名前で修飾した場合（`fn List.map(...)`）は構文エラーとし、修飾を取り除くよう示す。修飾した関数の宣言は、prelude のソースでだけ受け付ける（後述の「prelude のソースの構文」）。

### 型の解析

【決定】型は括弧で囲める（`"(" Type ")"`）。`uses` は、その直前にある最も内側の関数の型に付き、`uses` の後のコンマ区切りの並びはできるだけ長く読む（[ADR 0047](../decisions/0047-parenthesized-types-and-uses-binding.md)）。

【方針】型を解析する関数は、次のように書く。

- `(` で始まる型は、中の型を解析して `)` を求め、括弧の型のノードを作る。括弧の型は、中の型と同じ型を表す。
- 関数の型は、`fn`、引数の型の並び、`->`、戻り値の型を解析した後、次の字句が `uses` であれば、その関数の型の `uses` の並びとして読む。戻り値の型が関数の型であれば、その戻り値の型の解析の中で先に `uses` を読むので、`uses` は最も内側の関数の型に付く。
- `uses` の並びは、最初の大文字の識別子を読んだ後、次の字句が `,` で、その次の字句が大文字の識別子である間、`,` とその識別子を並びに加える。`,` の次が大文字の識別子でなければ、`,` を読まずに並びを終える（その `,` は外側の並びの区切りになる）。
- 並びに読んだ名前がエフェクトの名前であるかは、構文解析器は判定しない。エフェクトでない名前は名前解決が報告する（[名前解決とモジュール読込](02-04-resolver.md)）。ただし、並びの 2 番目以降の名前の直後に `[` が来たとき（`fn(fn() -> Unit uses IO, List[Int]) -> Unit`）は構文エラーとし、`uses` を持つ関数の型を括弧で囲むよう示す。

関数の宣言の `->` の後の型も、この規則で読む。`fn f() -> fn() -> Int uses IO { ... }` の `uses IO` は戻り値の関数の型に付き、`f` 自身は `uses` を持たない。

### AST

【方針】AST は、[構文](../01-spec/01-02-syntax.md)の文法の形をそのまま表す。書かれた形を変えずに保つので、次の構文も AST では独立したノードである。

- パイプ `x |> e`（展開した呼び出しにしない）
- プレースホルダを含む呼び出し（展開したラムダにしない）
- 括弧で囲んだ式 `(e)`
- `else if` の連なり

これらの展開は、型検査器（型を求めるとき）と脱糖の段（中間表現を作るとき）が、[構文](../01-spec/01-02-syntax.md)の展開の規則に従って行う。パイプの右辺が括弧の式のノードであれば、中身によらず規則 2 により `(e)(x)` と展開する。規則 1 の「プレースホルダを含む」かは、右辺の呼び出しの直接の引数だけで判定する（[ADR 0050](../decisions/0050-pipe-with-parenthesized-rhs.md)）。

【決定】AST の各ノードは、span と、一つの検査の中で重ならないノード番号を持つ（[ADR 0022](../decisions/0022-side-tables-keyed-by-node.md)）。ノード番号は、検査ごとに持つ数え上げの状態から振る。prelude のソースと利用者のソースを同じ検査で解析するときは、同じ数え上げの状態を使う。

AST のノードの種類は次のとおりである。

| 分類 | ノード |
|---|---|
| プログラム | プログラム（トップレベルの宣言の並び） |
| 宣言 | 関数の宣言（名前を修飾したモジュールの名前を持ちうる）、型の宣言、データ構成子の宣言、型パラメータの宣言（`effect` を付けたかを持つ）、引数（関数の引数とラムダの引数） |
| 型 | 名前の型（型引数を含む）、関数の型（`uses` の並びを含む）、括弧の型、`uses` の並びの中のエフェクトの名前 |
| 文 | `let` 文、式文 |
| 式 | リテラル、名前（修飾を含む）、`()`、括弧の式、リストリテラル、呼び出し、プレースホルダ、二項演算、単項演算、パイプ、ブロック、`if`、`match`、`match` の分岐、ラムダ |
| パターン | ワイルドカード、変数、リテラル（前置の `-` を含む）、`()`、構成子（修飾、括弧を書いたか、引数を含む） |
| 誤り | 誤りの宣言、誤りの文、誤りの式、誤りの型、誤りのパターン |

名前解決と型検査の表の鍵にするため、名前を束縛する箇所と名前を使う箇所は、それぞれ独立したノードにする。関数の宣言の名前を修飾したモジュールの名前は、関数の宣言のノードの欄として持つ。構成子のパターンは、引数がなくても括弧を書いたかを欄として持つ（`Tree.Leaf()` の誤りを型検査器が報告するため。[型検査器](02-05-typechecker.md)）。

誤りのノードは、構文エラーから回復した箇所に置く。誤りのノードを含む AST は、名前解決以降の段に渡らない（[ADR 0019](../decisions/0019-stop-after-failing-stage.md)）。

### 誤りからの回復

【方針】構文解析器は、構文エラーを報告した後、次の位置まで字句を読み飛ばして解析を続ける。読み飛ばした範囲は、誤りのノード一つで表す。

| 解析していた構文 | 読み飛ばす先 |
|---|---|
| トップレベルの宣言 | 括弧の外にある、行の先頭の `fn` または `type` |
| ブロックの中の文、`match` の分岐、型の宣言の構成子 | 同じ波括弧の中の次の NEWLINE、またはその波括弧を閉じる `}` |
| 丸括弧・角括弧の中の要素 | 同じ括弧の中の次の `,`、またはその括弧を閉じる字句 |

読み飛ばすときは、開いた括弧と閉じた括弧を数え、内側の括弧の中の字句は読み飛ばす先とみなさない。

【方針】一つの誤りから派生した構文エラーを出さないように、構文エラーを報告した後は、字句を一つ以上正しく読み進めるまで、次の構文エラーを報告しない。

### 入れ子の深さ

【方針】構文解析器は、作る AST の深さに上限を設け、上限は 1000 とする。深さは、プログラムのノードを 0 とし、子のノードを親のノードの深さに 1 を加えたものとして数える。次のものは、それぞれ 1 段と数える。

- 式・型・パターン・ブロックの入れ子（`else if` の連なりの各 `if` を含む）。
- 左結合の演算子の連なり（`a + b + c`、`x |> f |> g`）と呼び出しの連なり（`f(a)(b)`）の、演算子と呼び出しの一つ一つ。Pratt 法はこれらを再帰でなく繰り返しで読むが、できる木は左に深くなるので数える。
- ブロックの中の文の一つ一つ。文はどれもブロックの子であるが、`i` 番目（0 から数える）の文の深さは、ブロックの深さに `i + 1` を加えたものとして数える。ブロックは脱糖で `let` の入れ子になる（[コア計算と脱糖](../01-spec/01-12-core-calculus.md)）ので数える。
- 並びの要素の一つ一つ。対象は、リストリテラルの要素、呼び出しと構成子の呼び出しの引数、構成子のパターンの引数、`match` の分岐である。文と同じく、`i` 番目の要素の深さは、親のノードの深さに `i + 1` を加えたものとして数える。リストリテラルと呼び出しは脱糖で要素ごとの `let` の入れ子になり（同章）、構成子のパターンの引数と `match` の分岐は、判定の木への変換で列と `join` の入れ子になる（[中間表現と脱糖](02-06-ir-and-lowering.md)）ので数える。

上限を超えたときは、その位置で構文エラーを報告し、解析を打ち切る。後の段は、AST と、それから作る中間表現を再帰的に辿る。入れ子を作る脱糖と変換は、上に挙げたもの（文と並びの要素）を除けば、構文ごとに定数の段数しか入れ子を増やさない（パイプとプレースホルダの展開、`&&` の `if` への変換など）。したがって、後の段の再帰の深さは、ここで数えた深さの定数倍に収まる。AST と中間表現を破棄するときの処理も、同じ深さの入れ子に沿うので、この範囲に収まる。後の段に、入れ子を要素の数に比例して増やす変換を加えるときは、この節の数え方に加える。

### 構文解析の結果

【方針】構文解析の結果は、次のものからなる。

- AST（プログラムのノード）
- コメントの一覧
- 診断の一覧（字句を切り出す工程と構文解析の誤り）

診断に誤りが一つでもあれば、次の段（名前解決）に進まない。

### 用途

【方針】AST は、実行の経路（名前解決から脱糖まで）、フォーマッタ（v1、[フォーマッタ](../06-tooling/06-03-formatter.md)）、LSP サーバ（v1 の後、[MCPサーバとLSPサーバ](../06-tooling/06-02-mcp-lsp.md)）が共有する。フォーマッタは AST とコメントの一覧を使う。

### prelude のソースの構文

【方針】構文解析器は、解析するソースが prelude のソースかどうかを引数に受け取る。prelude のソースを解析するときだけ、関数の宣言の名前をモジュールの名前で修飾して書くこと（`fn List.map[T, U, effect E](xs: List[T], f: fn(T) -> U uses E) -> List[U] uses E { ... }`）を受け付ける。修飾は大文字の識別子一つと `.` からなり、関数の宣言のノードの欄に入れる。利用者のソースでは、前述のとおり構文エラーとする。修飾した関数がどのモジュールに入るかは[名前解決とモジュール読込](02-04-resolver.md)の「prelude」で定める。
