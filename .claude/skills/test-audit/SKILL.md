# テストの監査

処理系のテストを、少なく、壊れにくく、誤りを確実に捕まえるものに保つためのスキルである。小さな変更のたびにテストを足し続けると、テストが膨らみ、実装を変えるたびに壊れる。このスキルは、テストを足す前に価値を問い、価値の低いテストを定期的に整理する。

テストの設計の原則は、設計書の[処理系のテスト戦略](../../../doc/2026-09-27-design-initial/07-quality/07-03-compiler-testing.md)の「テストの設計の原則」に従う。このスキルは、その原則をテストを書く場面と見直す場面で適用する手順である。原則とこのスキルが食い違うときは、設計書を正とする。

使い方は三つある。

- **作成時の関門**: テストを加える・変えるたびに通す。
- **監査**: 既存のテストから、価値の低いものを探して整理する。一度に一つのまとまり（処理系の段一つなど）を扱う。
- **キャンペーン**: 一つの段のテストの全体を、まとめて見直す。始める前に [CAMPAIGN.md](CAMPAIGN.md) を読む。

## 作成時の関門

テストを加える前に、次の四つに答える。答えられないものがあれば、まだ加えない。

1. そのテストは、どの観察可能な振る舞い、不変条件、独立した契約を守るのか。
2. どんな現実的な退行（regression）があれば、そのテストは失敗するのか。
3. 既存のテストがその失敗を捕まえないのはなぜか。一つの契約には、最も適した境界（下の「持ち主の境界」）に主となるテストを一つ置く。別の層にテストを足すのは、その層に固有の危険（持ち主のテストでは届かない失敗）があるときに限る。似たテストを足す代わりに、表の形のテスト（パラメータを並べたテスト）に行を足すか、共有の準備の処理を使う。重複した準備の処理は、同じ変更の中でまとめる。
4. 本番のコードが必要としない差し込み口（公開の範囲の拡大、フラグ、ラッパー、注入のための引数）を要するか。要するなら、テストを本当の境界へ移す。

次に、下の「価値の低いテストの型」のどれかに当たらないかを確かめる。当たるなら、「残す基準」が、そのテストが独立して守る契約を名指しできない限り、関門を通さない。振る舞いを変えない作り直し（リファクタリング）で壊れるテストは、振る舞いではなく実装を確かめている。持ち主の境界で書き直してから加える。

不具合を直したときの退行テストは、直す前のコードで、意図した理由で失敗し、直した後に通らなければならない。一度も失敗を確かめていない退行テストは、修正ではなくテストダブル（test double）の振る舞いを確かめているだけである。退行テストは持ち主の境界に一つ置けば足りる。同じ場面を、通り過ぎる層ごとに繰り返し書かない。

## 持ち主の境界

処理系では、次のものを持ち主の境界とする。

- 処理系の各段（字句解析、構文解析、名前解決、型検査、脱糖、コード生成、VM、ランタイム）の、公開の関数と型。段の中の非公開の関数は、境界ではない。
- `run` などの CLI の入口から出力・診断・終了状態までを確かめるゴールデンテスト。
- 言語仕様の例の検査（`src/tools/grammar-check/`）と、参照インタプリタとの差分テスト。

ファイル・プロセス・標準出力など、処理系の外にある依存だけを、テスト用のハンドラ表で置き換える。処理系の中の段どうしは、置き換えずに本物をつないで確かめる。

## 価値の低いテストの型

作成時の関門と監査で共通に使う一覧である。作成時の関門はこれに当たる新しいテストを退け、監査はこれに当たる既存のテストを探す。

- 何も確かめない（アサーションのない）、網羅率を稼ぐためだけのテスト。
- 自分自身との比較や、入力をそのまま写す処理を確かめるテスト。
- 固定の準備データ、一覧、定義の一覧を写しただけのテスト。
- ソースや文字列を字面で探すだけのテスト。
- 本当の境界で確かめている内容を、非公開の判定や呼び出しの形で重ねて確かめるテスト。
- 同じ契約を、同じ呼び出しで繰り返すテスト。
- 共有の補助の処理を、使う側ごとに繰り返し確かめるテスト。
- テストのためだけにある公開の範囲、大域の値、ラッパーを保つことだけが目的のテスト。
- テストからしか呼ばれない、本番では使わないコード。
- 期待値を、テストの対象の処理（または同じ仕組み）で作っているテスト。
- 確かめたい振る舞いをテストダブルの側で実装しているテストや、一つのテストダブルで別々の依存をまとめて代用しているテスト。
- 本来なら対象のコードが作るはずの結果や順序を、準備データの側で与えてしまうテスト。
- 宣言した性質を読み直すだけで、その性質が実際に働くことを確かめないテスト。
- 別の理由で通ってしまう否定のテスト（意図と別の検査に拒否された、本番の経路では届かない拒否を確かめている、など）。
- 名前や準備データが、実際に確かめていることより多くを約束しているテスト。

## 残す基準

次のいずれかを独立して守るテストは残す。

- 言語仕様（`doc/2026-09-27-design-initial/01-spec/`）の規則、診断の形式と内容、終了状態、CLI の振る舞い、実行時の権限制御、セキュリティに関わる性質。
- 観察可能な振る舞いとしての順序（評価の順序、出力の順序など）。
- 現実的に起こりうる失敗を捕まえる退行テスト。
- 基準の状態で失敗する既存のテスト。消さずに、処理系の不具合の可能性として再現し、持ち主の側を直す。

遅いことや、静的なことは、削除の理由にならない。実装に似て見えるテストが、実は独立した契約を守っていることもある。消す前に、そうでないことを確かめる。

## 監査の手順

1. **読む**: 候補を判断する前に、テストの全体、対象の本番のコード、その入口・呼び出し元・呼び出し先、似た実装、重なるテスト、変更の履歴を読む。先にリポジトリの AGENTS.md と、テスト戦略の章を読む。
2. **探すだけにする**: 見つける段階では書き換えず、証拠を先に報告する。多くの推測の候補より、確度の高い少数の候補を優先する。
3. **証拠を記録する**: 候補ごとに次をすべて記録する。一つでも欠けたら、その候補はまだ消さない。
   - テストの名前と場所
   - そのテストが実際に捕まえられる失敗
   - テストが確かめている本番のコードの、テスト以外の呼び出し元
   - 残る、より強い持ち主の境界のテスト（または、確かめる必要がない理由）
   - テストやコードが作られた経緯
   - 消すことで一緒に消せる本番のコードやテストの補助
   - 危険と、確かめるためのコマンド
4. **まとめて直す**: 持ち主の境界ごとに、一貫した一まとまりの変更にする。テストのためだけの公開の範囲やラッパーは、別名で残さずに消す。残す退行テストは、正しい持ち主の場所へ移す。本番のコードの行数が減る変更を優先する。同じ実装を言い直しただけの代わりのテストを足さない。不確かな候補を、削除の数を増やすために消さない。
5. **確かめる**: 対象の段と周辺のテストを `cargo test` で実行し、設計書の「実装の規約と静的な検査」の検査を通す。消したテストが守っていた契約が、残したテストで守られていることを確かめる。

## 報告

作業の最後に、次のことを報告する。

- 消したテストの種類と、それが増えた原因
- 本番のコードの簡素化
- 候補にしたが残したテストと、残した理由
- 実際に実行した検査とテスト
- 本番のコードとテストの、それぞれの行数の増減
- 次に行う作業
