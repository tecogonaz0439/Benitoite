# セキュリティの勧告の照合

依存とツールチェーンの勧告を調べ、対象構成と使う機能/APIから影響を評価し、設計者が対応の範囲を判断できる記録を作る。運用の正は [AGENTS.md](../../../AGENTS.md)「改造の進め方」「テストの運用」、検査と保存の正は [07-03](../../../docs/design/07-quality/07-03-compiler-testing.md#実装の規約と静的な検査)である。本スキルの実行だけを根拠に、依存・固定版・処理系の更新や修正を始めない。

## 実行の時点と記録先

| 時点 | 記録と設計者の判断 |
|---|---|
| 改造の最初 | 改造のディレクトリを作った後、対象と実装プランの確定前に照合する。`security-advisories.md` に記録し、計画の「前提と依存」へ照合日・対象・根拠・未照合の範囲・設計者の判断を写す。取りまとめが担当へ必要な条件を渡す |
| 作業中・公開候補 | 計画の検査の割り当てと [git-workflow](../git-workflow/SKILL.md)に従う。同じ改造の `security-advisories.md` に追記し、当該 `results.md` から参照する。最初の照合と今回の差を記す |
| 改造がない時の手動・周期的な照合 | docs/todo の README を読み、該当項目へ照合日・入力・根拠・影響・対応案・判断を追記する。項目の追加と既存項目の扱いは後述の手順に従う |

実行前に、依頼が指定する範囲と操作の制約、既存の計画・照合記録を確認する。照合と記録の許可を、定期登録や更新の実装の許可へ広げない。docs/todo を読めない依頼では、渡された項目の写しを使い、追記案を取りまとめへ渡す。

## 入力と固定版の識別

リポジトリの根から実行する。開始日時とタイムゾーン、対象のコミットと未コミット差分、ワークスペース/fuzz の両 manifest・両 lock・`deny.toml` の SHA-256、対象構成を記録する。終了時にも lock の SHA-256 を照合し、照合中に入力が変わった結果を同じ入力の証拠にしない。

ツールチェーンは、指定された候補の版と実際に使用する版を分けて確認する。版の照会で不足する道具を自動導入・更新せず、実行できなければ未取得とする。

| 対象 | 確認する入力と版 |
|---|---|
| Rust | `rust-toolchain.toml` の固定版と、導入済みの対象ツールチェーンの `rustc --version --verbose`。fuzz・特殊構成に別の版があれば別行で記録する |
| Cargo | その Rust に付属して実行する `cargo --version --verbose`。Rust の版から Cargo の版を推測しない |
| Lean | Lean 担当が引き渡した候補の版を受け取り、`formal/lean-toolchain` と導入済みの対象の `lean --version` を照合する。引き渡しがなければ候補未確認とする |
| elan | Lean 担当が引き渡した候補の版と `elan --version` を照合する。Lean の固定ファイルだけで elan の版まで確認した扱いにしない |

ホストの既定版と固定版が違えば、その違いを記す。版の確認のために Lean のビルドや証明を変更する必要はない。

## ワークスペースと fuzz の二照合

既存の `advisories` 単位を使い、対象別の状態と生の出力を保存する。手動で一度だけ照合する入口は次である。

```sh
python3 -B scripts/check/advisories.py
```

計画の work/change/release で同じ照合を割り当てている場合は、その入口に任せて直接実行を重ねない。`advisories` は change/release で常に選ばれ、work では依存の manifest・二 lock・`deny.toml` の変更時に選ばれる。全水準で名指しできる。基準と実行する検査は計画で固定し、検査前に同じ指定の `--dry-run` を確認する。

二照合の基本コマンドは次のとおりである。実行器は版の取得とともに JSON 出力・詳細ログを指定し、生の終了状態も保持する。

```sh
cargo deny --version
cargo deny --config deny.toml --locked check advisories
cargo deny --manifest-path fuzz/Cargo.toml --config deny.toml --locked check advisories
```

ルートの共通設定を両 manifest に明示し、DB を照合時に更新する。一方の検出や取得不能で他方を省かない。書き込み可能な DB 領域が必要なら、実行器の `--db-path` にそのディレクトリを渡す。実行器は共通設定の写しへ `db-path` だけを加えるので、変更点と有効な設定のハッシュを記録する。追跡する設定へ ignore を足したり、lock を更新したりして結果を変えない。DB 設定の意味は [cargo-deny の公式資料](https://embarkstudios.github.io/cargo-deny/checks/advisories/cfg.html)を参照する。

対象構成は `deny.toml` の graph と manifest の機能を読み、実行したコマンドの選択とともに記録する。lock に含まれること、対象構成で依存が有効であること、影響する機能/APIを利用していることを分ける。必要な依存経路と機能は、対象 manifest・対象プラットフォームを指定した `cargo tree --locked` などで確認し、コマンドと出力を根拠へ加える。調べていない構成へ無影響の結論を広げない。

実行器が表示する `target/check-advisories/` 内の今回の記録を確認し、stdout/stderr・設定の写し・`report.json` を上記の記録先とともに保存する。一時的な target のログだけを参照元にしない。端末の記録を保存するときも、リポジトリの根・ホーム・一時ディレクトリを 07-03 と同じ `<repo>`・`<home>`・`<tmp>` に置換する。実行器が保存した記録の `path_redaction` と、設定の SHA-256 が置換前の実入力の値である旨を保つ。実行器の保存した生の終了状態と表示単位の終了状態は分けて読む。

| 対象別の状態 | 記録と次の処置 |
|---|---|
| 照合済み・検出0件（CHECKED: 0 advisories） | DB・入力・構成・日時を付け、今回その範囲で検出0件だったと記す。両対象がこの状態の場合だけ依存全体を検出0件とする |
| 勧告あり（ADVISORIES FOUND） | 観測した件数、ID、クレートと版、一次資料、修正版を列挙し、影響を評価する。取得不能も併発していれば、その未照合の範囲も残す |
| 取得不能・照合不能（UNVERIFIED） | 対象、失敗した操作、理由、未取得の欄、確認できた範囲を記す。取得失敗・道具不在・不明な出力を検出0件や無影響へ読み替えない |
| 入力・設定・実行器の誤り（ERROR） | `--locked` による lock 更新の拒否は `lock needs update (--locked)` として区別する。生の出力と理由を残し、入力・設定または実行器の不具合として扱う |

表示単位は勧告あり・取得不能・道具不在で終了0、入力・設定・実行器の誤りで終了1となる。生の cargo-deny は勧告検出で非0になりうる。単位の終了0だけでは、二対象の照合完了も勧告の解消も判断できない。

## Rust・Cargo・Lean・elan の勧告

固定版ごとに次の一次資料をその都度確認し、確認日時と参照 URL を残す。依存の cargo-deny が成功したことや Lean のビルドが成功したことを、ツールチェーンの勧告の照合の代わりにしない。

| 対象 | 照合先 |
|---|---|
| Rust・Cargo | [Rust の告知](https://blog.rust-lang.org/)、[rust-lang/rust の勧告](https://github.com/rust-lang/rust/security/advisories)、[rust-lang/cargo の勧告](https://github.com/rust-lang/cargo/security/advisories) |
| Lean | [leanprover/lean4 の勧告](https://github.com/leanprover/lean4/security/advisories)、関連する公式のリリース・修正の記録 |
| elan | [leanprover/elan の勧告](https://github.com/leanprover/elan/security/advisories)、関連する公式のリリース・修正の記録 |
| 共通 | [CVE の記録](https://www.cve.org/)。見つかった ID の個別の記録と上流の修正の根拠を対応させる |

影響する版の範囲と修正版を候補の実際の版と照合する。Lean カーネルの例として [CVE-2026-72844 の記録](https://www.cve.org/CVERecord?id=CVE-2026-72844)も対象とし、本文と公式の修正の記録を取得して範囲を確かめる。一覧だけを見て無影響と判断せず、カーネル・コンパイラ・配布や導入の経路など、影響箇所とこのプロジェクトでの利用を照らし合わせる。

版が未取得、資料を取得できない、版の範囲や使う機能が判定できない場合は、対象ごとに未確認として残す。勧告を見つけなかった場合も、確認した資料と固定版の範囲を示す。依存の検出0件と、四ツールの確認状況は別々に報告する。

## 影響の評価・項目の更新・設計者への報告

勧告ごとに、IDと一次資料、影響する版、対象構成、依存経路、利用する機能/API、影響の根拠、修正版、対応案をまとめる。「影響あり」「対象外」「未確認」を区別し、対象外の判断にも根拠を付ける。修正版がない場合はその旨と可能な対応案を示す。更新で失う互換性や必要な検査も判断材料にする。

記録には次の欄を揃える。取得できない欄は未取得・未確認と書き、空欄で検出0件を表さない。

- 照合の開始・終了日時、入力の識別、コマンド、ツールの版、対象構成、二 lock の前後のハッシュと設定のハッシュ。
- DB の URL・コミット・取得日時、対象別の状態・件数・検出 ID・生の終了状態・単位の終了状態、保存した出力の場所。
- Rust・Cargo・Lean・elan の候補の版と実行版、確認した一次資料と日時、影響する版・修正版・機能/API、未照合の範囲。
- 最初または前回の照合との差、影響の評価と対応案、設計者の判断と日付（回答前は判断待ち）、引き渡す担当と時期。

docs/todo の更新は、その README の採番・分野・目次・履歴の規則に従う。勧告 ID と対象で未完の項目を探し、対応するものがあれば照合日と新しい根拠・入力・判断を追記する。なければ次の番号を確認して分野の文書と目次を揃えて追加する。改造がない時の検出0件や未照合の記録は、該当する勧告照合の運用項目に残す（なければ README に従って記録用の項目を追加し、架空の脆弱性として登録しない）。公開文書から非公開の記録へリンクせず、「docs/todo の TODO-nnn」の形で受け渡す。依頼が直接の更新を認めていなければ、追記案を取りまとめへ渡す。

改造の最初には評価と対応案を示し、今回へ組み込むか別に直すかを設計者に尋ねる。改造がない時も別に修正を始めるかを設計者に尋ねる。既に判断済みの範囲はその指示に従い、照合だけの依頼から更新の実装へ進まない。

change/release で新しい勧告を見つけた場合は、表示・記録し、取りまとめが設計者へ報告する。新しい勧告・未照合を検査の不合格条件や受け入れの停止条件にせず、次の改造の最初の照合で対応を組み込むか判断してもらう。ignore の追加や期限による候補の停止を加えない。最初に対応すると決めた項目の完了条件は保つ。

## 手動と周期的な呼び出し

手動では、スキルを認識する Claude Code のプロジェクトで `/security-advisories` を実行するか、利用するエージェントへスキル名を指定して照合を依頼する。

周期的な呼び出しの例は次のとおりである。周期と実行環境は運用者が選び、登録を依頼された場合に設定する。

- Claude Code: `/loop 1d /security-advisories`。公式資料では間隔付きのプロンプトにスキルを指定でき、セッションを開いておく必要がある。実行を許されたスキルが対象となり、ループには有効期間などの制約がある。設定時に [公式の /loop 手順](https://code.claude.com/docs/en/scheduled-tasks)を再確認する。
- Claude Code Desktop: Code の Scheduled → New task からローカルのタスクを作り、ローカルフォルダにこのリポジトリ、指示に「security-advisories スキルで依存とツールチェーンを照合し、結果を記録・報告する。更新の実装は行わない」、周期に運用者が選んだ頻度を指定する。ローカル実行には起動中のアプリと起きている端末が必要である。画面の違いを含め [Desktop の公式手順](https://code.claude.com/docs/en/desktop-scheduled-tasks)に従う。

公式資料で上記の呼び出し方法と実行条件を確認した日は 2026-10-25 である。手元の版での利用可否・実動作は未確認であり、この記載を実行成功や評価の成績としない。スキルの作成・静的点検には定期実行の登録と LLM の実呼び出しを含めない。
